# Toolformer: Language Models Can Teach Themselves to Use Tools

## Quick Facts
- arXiv ID: 2302.04761
- Source URL: https://arxiv.org/abs/2302.04761
- Reference count: 31
- Primary result: Toolformer enables large language models to learn tool use in a self-supervised way, achieving strong zero-shot performance without human annotations.

## Executive Summary
Toolformer introduces a self-supervised method that allows language models to learn how to use external tools by generating and filtering potential API calls based on their ability to reduce future token prediction loss. The approach works by sampling candidate tool calls, executing them, and keeping only those that improve the model's predictive performance. This enables the model to learn when and how to use tools like search engines, calculators, and translation systems without requiring human-labeled training data. The method achieves substantial improvements on various downstream tasks while maintaining the model's core language modeling capabilities.

## Method Summary
Toolformer works by generating potential API calls using few-shot prompts, executing these calls to obtain results, and then filtering them based on whether they reduce the model's future token prediction loss. The filtering compares cross-entropy loss with and without the API call result, keeping only those calls that provide sufficient loss reduction. The model is then fine-tuned on the augmented dataset containing these filtered API calls. This self-supervised approach requires only a handful of demonstrations for each API and enables the model to learn tool use behavior purely from its own feedback about which calls are helpful for prediction.

## Key Results
- Toolformer achieves substantially improved zero-shot performance on various downstream tasks, including question answering and math problems, while maintaining language modeling ability
- Toolformer-J outperforms much larger models like GPT-3 on several benchmarks, demonstrating the effectiveness of learned tool use
- The approach works across different model sizes, with tool use emerging around 775M parameters and improving with scale up to 6.7B parameters

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** The model learns to use tools by generating potential API calls, executing them, and keeping only those that reduce future token prediction loss.
- **Mechanism:** Self-supervised filtering based on cross-entropy loss reduction. The model samples candidate API calls, executes them to get responses, then compares the loss when including vs. excluding the API call and its result. Only calls that lower the loss are retained.
- **Core assumption:** Future token prediction accuracy is a good proxy for the usefulness of external tool use.
- **Evidence anchors:**
  - [abstract]: "The method works by generating and filtering potential API calls based on whether they help the model predict future tokens"
  - [section]: "We compare two different instantiations of this loss: L+ = Li(e(ci, ri)) vs L− = min(Li(ε), Li(e(ci, ε)))... An API call is helpful if adding it reduces the loss by at least τf"
  - [corpus]: Weak evidence - only neighbor titles mention similar concepts like "Optimizing Agentic Language Model Inference via Speculative Tool Calls" but no direct citations or results.

### Mechanism 2
- **Claim:** The model maintains its general language modeling ability because the augmented dataset contains the same text content as the original dataset, just with helpful API calls inserted.
- **Mechanism:** Dataset augmentation where the only change is inserting API calls that the model itself identified as useful. Since the underlying text is unchanged, the model's language modeling capability is preserved.
- **Core assumption:** Fine-tuning on the original text with useful API calls is equivalent to fine-tuning on the original text alone for maintaining language modeling performance.
- **Evidence anchors:**
  - [abstract]: "Toolformer achieves substantially improved zero-shot performance... without sacrificing its core language modeling abilities"
  - [section]: "Crucially, apart from inserted API calls the augmented dataset C∗ contains the exact same texts as C... As a consequence, fine-tuning M on C∗ exposes it to the same content as fine-tuning on C"
  - [corpus]: No direct evidence in the corpus. The claim is primarily supported by the paper's own experimental results in Section 4.3.

### Mechanism 3
- **Claim:** The model learns to decide when and how to use which tool by being fine-tuned on examples where it chose to use a tool and that choice was beneficial.
- **Mechanism:** The self-supervised filtering process creates a dataset where the model has already decided which tools to use and when, based on its own judgment of what would be helpful. Fine-tuning on this dataset teaches the model to make similar decisions.
- **Core assumption:** The model's own assessment of which API calls are helpful is a good signal for learning tool use behavior.
- **Evidence anchors:**
  - [abstract]: "This is done in a self-supervised way, requiring nothing more than a handful of demonstrations for each API"
  - [section]: "Crucially, as API calls are inserted in exactly those positions and with exactly those inputs that help M predict future tokens, fine-tuning on C∗ enables the language model to decide when and how to use which tool, based purely on its own feedback"
  - [corpus]: Weak evidence - the corpus mentions "Rethinking Stateful Tool Use in Multi-Turn Dialogues" which relates to decision-making but doesn't directly support this mechanism.

## Foundational Learning

- **Concept:** Self-supervised learning and loss-based filtering
  - **Why needed here:** The approach relies on the model's ability to evaluate the usefulness of API calls without human labels, using loss reduction as the criterion
  - **Quick check question:** How does the model determine which API calls to keep during training?

- **Concept:** Few-shot prompting and in-context learning
  - **Why needed here:** The approach uses a small number of human-written examples to prime the model for generating API calls, leveraging the model's in-context learning ability
  - **Quick check question:** What is the purpose of the prompts used when sampling API calls?

- **Concept:** Cross-entropy loss and perplexity
  - **Why needed here:** The filtering mechanism is based on comparing cross-entropy losses with and without API calls, and language modeling performance is measured using perplexity
  - **Quick check question:** How is the "helpfulness" of an API call quantified in this approach?

## Architecture Onboarding

- **Component map:** Language Model -> Prompt Generator -> API Execution Layer -> Loss Evaluator -> Fine-tuning Pipeline
- **Critical path:**
  1. Sample candidate API calls using prompts and in-context learning
  2. Execute sampled API calls to get responses
  3. Filter API calls based on loss reduction
  4. Create augmented dataset with filtered API calls
  5. Fine-tune the language model on the augmented dataset
  6. Deploy with modified decoding strategy for inference

- **Design tradeoffs:**
  - Sampling vs. computational cost: Generating many candidate API calls increases the chance of finding useful ones but is computationally expensive
  - Filtering threshold τf: Higher thresholds ensure only very useful API calls are kept but may result in too few training examples
  - Number of tools: More tools increase versatility but also complexity and potential for noise
  - Modified decoding strategy: Allows more API calls during inference but may lead to overuse

- **Failure signatures:**
  - Language modeling performance degrades: Filtering was too aggressive or API calls disrupt text flow
  - Model doesn't use tools effectively: Filtering threshold too high, few-shot demonstrations inadequate, or model too small
  - Model overuses tools: Modified decoding strategy too permissive, or model learned to rely on tools for simple tasks
  - Tool execution errors: API interfaces not robust to model-generated inputs

- **First 3 experiments:**
  1. **Sanity check filtering:** Run the sampling and filtering process on a small dataset with known useful API calls. Verify that calls reducing loss are kept and those increasing loss are removed.
  2. **Ablation on threshold τf:** Train models with different τf values (e.g., 0.5, 1.0, 2.0) and compare tool usage and performance on downstream tasks to find the optimal balance.
  3. **Modified decoding sensitivity:** Test the model with different values of k (number of top tokens to consider for API calls) on a validation set to find the value that maximizes useful tool use without overuse.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How does Toolformer perform on tasks that require chaining multiple tools, such as using the output of one API call as input to another?
- **Basis in paper:** [inferred]
- **Why unresolved:** The paper explicitly states that Toolformer is unable to chain tools, as API calls for each tool are generated independently. This is a significant limitation that could impact performance on complex tasks requiring multiple steps.
- **What evidence would resolve it:** Empirical results comparing Toolformer's performance on multi-step tasks with and without tool chaining, or a modified version of Toolformer that can chain tools.

### Open Question 2
- **Question:** How does the sample efficiency of Toolformer compare to traditional supervised approaches for learning tool use?
- **Basis in paper:** [explicit]
- **Why unresolved:** The paper mentions that Toolformer is sample-inefficient, processing millions of documents to generate only thousands of useful API calls for some tools. However, it doesn't provide a direct comparison to the sample efficiency of supervised approaches.
- **What evidence would resolve it:** A study comparing the number of examples needed for Toolformer to achieve a certain level of performance versus the number of labeled examples needed for a supervised approach to achieve the same level of performance.

### Open Question 3
- **Question:** How does Toolformer's performance scale with model size beyond 6.7B parameters?
- **Basis in paper:** [explicit]
- **Why unresolved:** The paper investigates scaling with smaller models (up to 1.6B parameters) and shows that the ability to use tools emerges around 775M parameters. However, it doesn't explore performance with models larger than 6.7B parameters.
- **What evidence would resolve it:** Empirical results showing Toolformer's performance on various tasks with models of increasing size beyond 6.7B parameters.

## Limitations
- The approach is computationally expensive due to generating and executing many candidate API calls during training
- Toolformer cannot chain tools, limiting its ability to handle complex multi-step tasks
- The model can be sensitive to the exact wording of its input when deciding whether to call an API

## Confidence
**High Confidence:** The claim that Toolformer maintains language modeling ability while learning to use tools is well-supported by the experimental results. The paper shows that Toolformer-J achieves comparable perplexity to GPT-J on language modeling benchmarks while also demonstrating improved performance on downstream tasks.

**Medium Confidence:** The claim that self-supervised filtering based on loss reduction is sufficient for learning effective tool use. While the experimental results are promising, the evaluation doesn't include ablation studies isolating the contribution of the self-supervised learning mechanism versus other factors.

**Low Confidence:** The claim that Toolformer consistently outperforms much larger models like GPT-3. The comparison doesn't account for potential differences in pre-training data, model architecture, or other confounding factors that could explain the performance differences.

## Next Checks
1. **Ablation on Filtering Mechanism:** Train a version of Toolformer without the self-supervised filtering step (i.e., include all generated API calls) and compare its performance to the filtered version. This would help isolate the contribution of the loss-based filtering mechanism to the overall performance gains.

2. **False Positive/Negative Analysis:** Manually examine a sample of API calls that were filtered out (L+ > L-) and those that were kept (L+ ≤ L- - τf) to estimate the rate of false positives and false negatives in the filtering process. This would provide insight into the reliability of the loss-based filtering criterion.

3. **Computational Cost Analysis:** Measure the total compute time required for the sampling, execution, and filtering steps during training. Compare this to the compute time for standard language model fine-tuning to quantify the additional computational overhead introduced by the Toolformer approach.
