# Towards an Automatic Optimisation Model Generator Assisted with Generative Pre-trained Transformer

## Quick Facts
- arXiv ID: 2305.05811
- Source URL: https://arxiv.org/abs/2305.05811
- Reference count: 6
- Key outcome: 5 out of 10 test cases achieved both valid syntax and specification compliance using GPT-3.5 for automatic MiniZinc model generation with error correction

## Executive Summary
This study presents a framework for automatically generating MiniZinc optimisation models using GPT-3.5 language models. The system takes user-specified requirements through prompts, generates initial code via GPT-3.5, and automatically debugs syntax errors using an iterative correction loop. Tested on 10 optimization problems with discrete and array variables, the framework successfully generated 5 models that were both syntactically valid and met the original specifications. The results demonstrate the feasibility of using large language models for initial optimisation model generation, though manual inspection remains necessary for semantic validation.

## Method Summary
The framework uses GPT-3.5 models to generate MiniZinc code from user prompts specifying variables, domains, and constraints. A fixed-parameter generation process (temperature=0, max_tokens=200) produces initial models, which are compiled using MiniZinc 2.7.1 with Gecode 6.3.0 solver. If compilation fails, an automatic debugging loop triggers GPT-3.5 edit models to fix syntax errors based on error messages. The process continues until models compile successfully or maximum correction steps are reached. Semantic correctness is validated through manual inspection comparing generated code against prompt specifications.

## Key Results
- GPT-3.5 generated syntactically valid MiniZinc models in 8 out of 10 test cases
- Automatic debugging successfully corrected syntax errors in failed compilations
- Only 5 models achieved both syntactic validity and semantic correctness per specifications
- Array variable handling and complex constraint specifications posed challenges for the framework

## Why This Works (Mechanism)

### Mechanism 1
- Claim: GPT-3.5 can generate syntactically valid MiniZinc code when given structured prompts specifying variables, domains, and constraints.
- Mechanism: The model maps natural language specifications into valid MiniZinc syntax by leveraging its training on structured code and formal languages, using fixed prompt parameters (temperature=0, max_tokens=200) to ensure deterministic output.
- Core assumption: GPT-3.5 has sufficient exposure to formal constraint modeling languages in its training corpus to generate correct syntax for MiniZinc constructs.
- Evidence anchors:
  - [abstract] "using a language model to generate an initial version of the model"
  - [section] "The results indicate that the use of GPT-3.5 language models for the generation of optimisation models in MiniZinc is feasible"
  - [corpus] No direct corpus evidence; assumption based on general code-generation capability
- Break condition: The model fails when domain constraints are complex or when array indexing and declarations are required beyond basic variable declarations.

### Mechanism 2
- Claim: Error messages from MiniZinc compilation can be used to trigger targeted corrections via GPT-3.5 text editing models.
- Mechanism: When compilation fails, the error message is fed back into a GPT-3.5 edit model with instructions to fix the specific issue, leveraging the model's ability to understand and modify code based on error feedback.
- Core assumption: GPT-3.5 edit models can parse MiniZinc error messages and generate syntactically correct fixes without requiring full model regeneration.
- Evidence anchors:
  - [abstract] "if it contains build errors, an automatic edition process is triggered"
  - [section] "the error message is used to provide feedback and resolve problems in the model"
  - [corpus] Weak corpus evidence; the edit capability is assumed from general text editing performance
- Break condition: The model cannot fix structural errors that require understanding of the optimization problem semantics, only syntax-level fixes.

### Mechanism 3
- Claim: The framework can distinguish between valid syntax and semantically correct models through separate validation steps.
- Mechanism: MiniZinc compilation validates syntax, while manual inspection validates semantic correctness against the original prompt specifications, creating a two-layer validation system.
- Core assumption: Syntax validation (compilation) and semantic validation (specification matching) are separable concerns that can be automated independently.
- Evidence anchors:
  - [abstract] "The model is then tested and validated"
  - [section] "In order to ensure whether the obtained optimisation model is correct according to the instructions in the prompt, a manual inspection of the generated source code is performed"
  - [corpus] No direct corpus evidence; this is a methodological design choice
- Break condition: Manual inspection becomes infeasible as model complexity increases, limiting scalability.

## Architecture Onboarding

- Component map: User prompt → GPT-3.5 generation model → MiniZinc compiler → Validation → (if error) GPT-3.5 edit model → (repeat) → Valid model + solution
- Critical path: Prompt generation → Model generation → Compilation → (Error? → Fix → Compilation) → Solution
- Design tradeoffs: Using fixed parameters (temperature=0) ensures reproducibility but may limit creative solutions; manual inspection ensures quality but doesn't scale
- Failure signatures: Syntax errors indicate prompt formulation issues; semantic mismatches indicate model understanding limitations; infinite loops indicate error feedback problems
- First 3 experiments:
  1. Generate a simple model with 5 discrete variables and no constraints; verify compilation
  2. Generate a model with array variables and basic constraints; test error correction on syntax errors
  3. Generate a complex model requiring multiple constraints and domains; test end-to-end success rate

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How do different GPT model architectures (beyond GPT-3.5) perform in automatic optimization model generation?
- Basis in paper: [explicit] The authors suggest future research could "explore other language models and evaluate their performance compared to the GPT-3.5 models used in this study"
- Why unresolved: This study only tested two specific GPT-3.5 models, leaving performance comparisons with other architectures unexplored
- What evidence would resolve it: Systematic testing of multiple LLM architectures (GPT-4, Claude, LLaMA, etc.) across diverse optimization problem types with quantitative performance metrics

### Open Question 2
- Question: What are the optimal prompt engineering strategies for specifying complex optimization constraints to language models?
- Basis in paper: [inferred] The study showed varying success rates depending on prompt complexity, with some models missing constraints like "all_different" despite being explicitly requested
- Why unresolved: The paper used relatively simple prompts but didn't systematically explore how prompt formulation affects model accuracy
- What evidence would resolve it: Controlled experiments varying prompt structure, detail level, and constraint specification methods to identify optimal approaches

### Open Question 3
- Question: How can the automatic debugging framework be enhanced to handle structural model errors beyond syntax issues?
- Basis in paper: [explicit] The authors note that models were sometimes "valid" but did not meet specifications, suggesting limitations in current error handling
- Why unresolved: The current framework only addresses syntax errors, while semantic and structural errors in generated models remain challenging
- What evidence would resolve it: Development and testing of enhanced error detection and correction mechanisms that can identify and fix semantic inconsistencies in optimization models

## Limitations

- Manual inspection requirement creates scalability bottleneck for semantic validation as model complexity increases
- Limited test scope (10 cases) with relatively simple specifications leaves uncertainty about performance on complex optimization problems
- Edit model restricted to syntax-level corrections, unable to address structural or semantic errors requiring full model regeneration

## Confidence

- **High confidence**: GPT-3.5 can generate syntactically valid MiniZinc code when given structured prompts with basic variable declarations and simple constraints
- **Medium confidence**: The automatic debugging loop effectively resolves syntax errors through iterative feedback
- **Low confidence**: The framework can reliably generate semantically correct optimization models that fully meet specification requirements

## Next Checks

1. Test the framework on optimization problems with nested array structures and complex constraint dependencies to evaluate edit model limitations on structural fixes
2. Implement automated semantic validation by comparing generated models against prompt specifications using constraint coverage metrics to replace manual inspection
3. Vary the generation model temperature parameter across multiple runs to assess the tradeoff between solution diversity and syntactic correctness
