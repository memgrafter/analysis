# MultiTabQA: Generating Tabular Answers for Multi-Table Question Answering

## Quick Facts
- arXiv ID: 2305.12820
- Source URL: https://arxiv.org/abs/2305.12820
- Reference count: 12
- Primary result: MultiTabQA outperforms state-of-the-art single-table QA models on three datasets for multi-table QA tasks

## Executive Summary
This paper addresses the limitation of existing table question answering research, which is confined to single-table scenarios, by proposing MultiTabQA - a model that answers questions over multiple tables and generates tabular answers. The authors introduce a curriculum learning approach with three training stages: pre-training on single-table SQL-to-table generation, pre-training on multi-table SQL generation, and fine-tuning on natural language questions. The model is evaluated using table-specific metrics at multiple granularities (row, column, and cell levels) across three datasets: Spider, Atis, and GeoQuery.

## Method Summary
MultiTabQA uses a seq2seq transformer encoder-decoder architecture that processes flattened table representations along with questions. The model is trained through curriculum learning: first pre-training on single-table QA using Tapex data, then pre-training on multi-table SQL queries augmented with 132,645 synthetic SQL samples, and finally fine-tuning on natural language questions from three datasets. Tables are flattened in row-major format with table names and headers, and generated outputs are unflattened to produce structured tables. The training pipeline uses progressive task complexity to build reasoning capabilities.

## Key Results
- MultiTabQA achieves higher table exact match accuracy compared to baseline single-table QA models adapted to multi-table settings
- The model demonstrates strong performance across row F1, column F1, and cell F1 metrics, showing granular correctness in generated tables
- MultiTabQA outperforms baselines on Spider, Atis, and GeoQuery datasets, validating its effectiveness for complex multi-table queries

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Curriculum learning by increasing task complexity leads to better convergence and performance than direct fine-tuning.
- Mechanism: The model is first pre-trained on single-table SQL-to-table generation (Stage 1), then multi-table SQL-to-table generation (Stage 2), and finally fine-tuned on natural language questions (Stage 3).
- Core assumption: The difficulty of multi-table natural language QA can be decomposed into simpler, more tractable sub-tasks that build upon each other.
- Evidence anchors:
  - [abstract] "To enable effective training, we build a pre-training dataset comprising of 132,645 SQL queries and tabular answers."
  - [section] "We follow a Curriculum Learning approach by sequentially training the model on sub-tasks of increasing complexity"
- Break condition: If the intermediate stages don't adequately capture the complexity of the final task, or if there's catastrophic forgetting between stages.

### Mechanism 2
- Claim: Table generation requires metrics at multiple granularities to properly evaluate the model's output.
- Mechanism: Instead of only using table exact match (binary), the authors define row, column, and cell exact match metrics to capture different levels of correctness in the generated table structure.
- Core assumption: Evaluating table generation requires measuring not just the final output but the correctness of its components.
- Evidence anchors:
  - [section] "We evaluate the generated tables by introducing table-specific metrics of varying strictness assessing various levels of granularity of the table structure."
- Break condition: If the granular metrics don't correlate well with human judgment of table quality, or if they're too lenient/strict.

### Mechanism 3
- Claim: Pre-training on synthetic SQL queries augments the model's ability to handle diverse multi-table operations.
- Mechanism: The authors generate 132,645 synthetic SQL queries with varying complexity (joins, set operations, aggregations) over the Spider database to create a large pre-training corpus.
- Core assumption: Synthetic data can effectively simulate the diversity of real-world multi-table queries and operations.
- Evidence anchors:
  - [section] "We further augment the modified Spider dataset with 132,645 samples of synthetic queries."
- Break condition: If the synthetic queries don't cover the true distribution of real-world multi-table operations, or if they introduce bias.

## Architecture Onboarding

- Component map: Question + Tables → Encoder → Reasoning → Decoder → Generated Table
- Critical path: Question + Tables → Encoder → Reasoning → Decoder → Generated Table
- Design tradeoffs:
  - Flattening tables vs preserving 2D structure (simpler input but loses spatial relationships)
  - Table exact match vs granular metrics (strictness vs nuanced evaluation)
  - Synthetic data generation vs real data collection (scalability vs authenticity)
- Failure signatures:
  - Table EM drops significantly with more input tables
  - Low column F1 despite reasonable row F1
  - Inability to handle numeric operations correctly
  - Hallucination of table content not present in input
- First 3 experiments:
  1. Run baseline tapex model on Spider validation set to establish comparison point
  2. Test MultiTabQA on single-table queries to verify Stage 1 effectiveness
  3. Evaluate MultiTabQA on multi-table queries with varying numbers of input tables to assess scalability

## Limitations

- The synthetic data generation process may not fully capture the distribution of real-world multi-table operations, potentially creating a gap between pre-training effectiveness and real-world performance
- The flattening approach for table representation may lose important spatial relationships between table elements that could be crucial for certain types of reasoning
- The evaluation metrics, while more granular than simple exact match, may not fully capture semantic correctness when table structure varies but the information conveyed remains equivalent

## Confidence

- **High confidence**: The core claim that MultiTabQA outperforms adapted single-table models on multi-table QA tasks is well-supported by the presented results across three different datasets (Spider, Atis, GeoQuery).
- **Medium confidence**: The effectiveness of the curriculum learning approach, while showing positive results, relies on the assumption that staged training appropriately builds the necessary reasoning capabilities without catastrophic forgetting.
- **Medium confidence**: The claim that synthetic SQL queries effectively augment the model's ability to handle diverse multi-table operations is supported by the results but could be more strongly validated with real-world multi-table query distributions.

## Next Checks

1. **Real-world generalization test**: Evaluate MultiTabQA on a held-out set of real-world multi-table queries from sources not seen during training (beyond the three datasets used) to assess whether the synthetic pre-training data truly covers the breadth of real-world operations.

2. **Ablation study on curriculum stages**: Remove each training stage individually (Stage 1, Stage 2, or Stage 3) and measure the impact on final performance to quantify the contribution of each stage to the overall effectiveness of the curriculum learning approach.

3. **Structural reasoning analysis**: Create test cases that specifically probe whether the model can handle table operations that depend on 2D spatial relationships (e.g., cross-referencing between rows in different tables) to assess the impact of the flattening approach on complex reasoning tasks.
