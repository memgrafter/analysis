# Thistle: A Vector Database in Rust
- arXiv ID: 2303.16780
- Source URL: https://arxiv.org/abs/2303.16780
- Reference count: 3
- Key outcome: A Rust-based vector database using SBERT embeddings tested with exact and approximate nearest neighbor algorithms

## Executive Summary
This paper presents Thistle, a vector database implemented in Rust that uses sentence embeddings from SBERT to perform similarity-based search. The authors compare exact (iterative) and approximate (HNSW, LSH) nearest neighbor algorithms on the MS MARCO dataset, measuring accuracy and runtime across dataset sizes of 100, 1,000, and 10,000 entries. Key findings include: accuracy decreases and runtime increases with dataset size; exact nearest neighbor achieves highest accuracy but is slow; HNSW provides good accuracy (30-40% at N=10,000) with better performance than exact search; LSH showed poor accuracy despite local testing success; and over 99% of query time was spent computing SBERT embeddings. The work demonstrates the feasibility of pure vector-based search while highlighting challenges in runtime efficiency and accuracy that need improvement for production use.

## Method Summary
The authors implemented a pure vector database in Rust using sentence-BERT (SBERT) embeddings to represent text data. They tested three search algorithms: exact nearest neighbor (iterative), HNSW (Hierarchical Navigable Small World), and LSH (Locality Sensitive Hashing). The system was evaluated on the MS MARCO dataset across three scales: 100, 1,000, and 10,000 entries. Accuracy was measured as the percentage of relevant documents retrieved among the top-N results, while runtime was measured for both indexing and querying phases. The experiments compared how each algorithm performed in terms of accuracy, speed, and scalability.

## Key Results
- Accuracy decreases and runtime increases with dataset size
- Exact nearest neighbor achieves highest accuracy but is slow
- HNSW provides good accuracy (30-40% at N=10,000) with better performance than exact search
- LSH showed poor accuracy despite local testing success
- Over 99% of query time was spent computing SBERT embeddings

## Why This Works (Mechanism)
The system works by converting text queries and database entries into fixed-dimensional vector representations using SBERT, then finding semantically similar vectors through nearest neighbor search. Exact search guarantees finding the closest vectors but scales poorly. HNSW creates a multi-layer graph structure that enables logarithmic-time search by probabilistically finding neighbors at different scales. LSH hashes similar vectors into the same buckets to enable sublinear search, though parameter tuning proved critical for performance.

- Sentence-BERT embeddings: Why needed - converts text to comparable vectors; Quick check - verify embeddings preserve semantic similarity
- HNSW algorithm: Why needed - enables fast approximate nearest neighbor search; Quick check - test recall vs. candidates explored ratio
- LSH parameters: Why needed - determines bucket collision probability; Quick check - measure accuracy sensitivity to hash function count
- Vector similarity metrics: Why needed - defines "closeness" between embeddings; Quick check - compare cosine vs. Euclidean distances
- Memory-efficient indexing: Why needed - scales to larger datasets; Quick check - profile memory usage vs. dataset size

## Architecture Onboarding
Component map: Text -> SBERT Encoder -> Vector Store -> Search Algorithm -> Results
Critical path: Query text → SBERT embedding → Nearest neighbor search → Score/rank → Return top-K
Design tradeoffs: Exact search vs. approximate (accuracy vs. speed), memory usage vs. search quality, indexing time vs. query performance
Failure signatures: Poor accuracy (embedding model issues), slow queries (inefficient indexing), memory errors (large datasets)
First experiments: 1) Verify SBERT embeddings produce consistent vectors for identical text, 2) Test HNSW recall with varying edge counts, 3) Measure LSH collision rate for similar vs. dissimilar vectors

- Results may not generalize to other embedding models beyond SBERT
- Memory usage and resource constraints for production deployment not addressed
