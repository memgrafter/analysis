# Neural models for Factual Inconsistency Classification with Explanations

## Quick Facts
- arXiv ID: 2306.08872
- Source URL: https://arxiv.org/abs/2306.08872
- Reference count: 40
- Key outcome: ~87% weighted F1 for inconsistency type classification, ~86% for coarse entity types, ~76% for fine-grained entity types

## Executive Summary
This paper introduces the problem of factual inconsistency classification with explanations, proposing a novel dataset FICLE with ~8K samples annotated with five inconsistency types and detailed explanations. The authors develop a pipeline of four neural models (M1-M4) to predict inconsistency type and explanations including spans, components, and entity types. Using Transformer-based models like DeBERTa, the pipeline achieves strong performance across all subtasks, addressing a gap in detecting and explaining factual inconsistencies without knowledge bases. The work provides a foundation for improving factual consistency in text generation systems.

## Method Summary
The authors propose a four-stage pipeline to detect and explain factual inconsistencies between claim and context sentence pairs. Stage 1 (M1) predicts inconsistent spans (subject, relation, object) from the claim and context spans from the context using span prediction. Stage 2 (M2) predicts the inconsistency type and claim component using the predicted spans from M1. Stage 3 (M3) predicts coarse-grained entity types using the predicted claim component, and Stage 4 (M4) predicts fine-grained entity types. The pipeline uses Transformer-based models (BERT, RoBERTa, DeBERTa, BART, T5) with cross-entropy loss for generation tasks and categorical cross-entropy for classification.

## Key Results
- Weighted F1 of ~87% for inconsistency type classification
- Weighted F1 of ~86% for coarse entity types
- Weighted F1 of ~76% for fine-grained entity types
- IoU of ~94% for claim span detection and ~65% for context span detection

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The pipeline design (M1→M2→M3→M4) enables progressive refinement of predictions by first isolating spans and then using those spans for higher-level classification.
- Mechanism: Span prediction is easier than joint classification because it reduces the output space and provides structured context for subsequent steps.
- Core assumption: Inconsistent spans in claim and context can be reliably localized before classifying their semantic inconsistency type.
- Evidence anchors: [abstract] "The proposed system first predicts inconsistent spans from claim and context; and then uses them to predict inconsistency types and inconsistent entity types", [section] "Stage A: Predict Inconsistent Spans ... Stage B: Predict Inconsistency Type and Claim Component ... Stage C: Predict Inconsistent Entity Types"
- Break condition: If span predictors fail to isolate the correct text, subsequent models receive noisy inputs and cascade failures occur.

### Mechanism 2
- Claim: Using both NLU (BERT/RoBERTa/DeBERTa) and NLG (BART/T5) models allows exploiting strengths of each for different sub-tasks.
- Mechanism: NLU models excel at span prediction (start/end classification), while NLG models better capture global context for classification and generation tasks.
- Core assumption: The architecture differences (encoder-only vs encoder-decoder) translate to complementary performance on different prediction types.
- Evidence anchors: [abstract] "We experiment with multiple Transformer-based natural language classification as well as generative models", [section] "BERT ... RoBERTa ... DeBERTa ... BART ... T5" and Table 6 showing NLG models underperform on context span prediction
- Break condition: If one architecture family consistently underperforms across all tasks, the complementary assumption fails.

### Mechanism 3
- Claim: Embedding-based entity type prediction leverages semantic similarity between class names and input representations.
- Mechanism: Instead of fixed-class classification, the model learns to match input embeddings to entity type embeddings using cosine similarity, capturing richer semantic relationships.
- Core assumption: Entity type class names contain sufficient semantic information to be embedded meaningfully and compared to input representations.
- Evidence anchors: [section] "Further, we also attempt to leverage semantics from entity class names ... using the NLU models ... to obtain embeddings for entity class names", [section] Table 10 showing embedding-based methods outperform traditional classification for coarse entity types
- Break condition: If entity type names are too ambiguous or sparse, embedding similarity becomes unreliable.

## Foundational Learning

- Concept: Intersection over Union (IoU) for span evaluation
  - Why needed here: To measure overlap between predicted and ground truth spans in token space, critical for span prediction tasks.
  - Quick check question: Given predicted span [2,5] and ground truth [3,6], what is the IoU?

- Concept: Weighted F1 score for imbalanced multi-class classification
  - Why needed here: Inconsistency types and entity types have skewed distributions, requiring metric that accounts for class imbalance.
  - Quick check question: Why is weighted F1 preferred over macro F1 when some classes have 10x more samples than others?

- Concept: Pipeline architecture with intermediate representations
  - Why needed here: Each stage depends on outputs from previous stages, creating a directed dependency chain.
  - Quick check question: What happens to downstream accuracy if an upstream span predictor has 80% accuracy versus 95%?

## Architecture Onboarding

- Component map: M1 (span predictor: S/R/T from claim + context span) → M2 (type/classifier: uses M1 outputs) → M3 (coarse entity type) → M4 (fine-grained entity type), all using DeBERTa as final choice
- Critical path: M1 → M2 → M3 → M4, where each stage must complete before next can begin
- Design tradeoffs: Progressive refinement reduces output space per stage but creates cascading failures; using embeddings adds semantic richness but increases complexity
- Failure signatures: High IoU for S/R/T but low for context span suggests span detection issue; high type accuracy but low entity type accuracy suggests context span or component prediction issues
- First 3 experiments:
  1. Train M1 with DeBERTa on span prediction and measure EM/IoU separately for S, R, T, and context span
  2. Train M2 with predicted M1 outputs to verify type classification accuracy
  3. Train M3 with predicted M1/M2 outputs to check coarse entity type prediction before adding embeddings

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the performance of the FICLE system vary when applied to multi-lingual scenarios or cross-lingual transfer settings?
- Basis in paper: [inferred] The authors mention in the conclusion that they plan to extend this work to multi-lingual scenarios in the future.
- Why unresolved: The current work focuses solely on English text and does not investigate performance on other languages or cross-lingual transfer capabilities.
- What evidence would resolve it: Experiments evaluating the FICLE models on multi-lingual datasets or testing cross-lingual transfer from English to other languages would provide evidence of its performance in multi-lingual settings.

### Open Question 2
- Question: How does the FICLE system perform when detecting factual inconsistencies across multiple sentences in a paragraph?
- Basis in paper: [inferred] The authors mention in the conclusion that they plan to extend this work to perform inconsistency detection and localization across multiple sentences given a paragraph.
- Why unresolved: The current work only considers (claim, context) sentence pairs and does not investigate performance on longer text spans or paragraphs.
- What evidence would resolve it: Experiments evaluating the FICLE models on datasets containing factual inconsistencies across multiple sentences in a paragraph would provide evidence of its performance in this setting.

### Open Question 3
- Question: How effective are the proposed methods at detecting and explaining more complex types of factual inconsistencies, such as those involving logical reasoning or commonsense knowledge?
- Basis in paper: [inferred] The current work focuses on five types of factual inconsistencies based on linguistic theories, but does not explicitly address more complex types of inconsistencies that may require additional reasoning or knowledge.
- Why unresolved: The FICLE dataset and experiments do not cover more complex types of factual inconsistencies, and it is unclear how well the proposed methods would generalize to these cases.
- What evidence would resolve it: Experiments evaluating the FICLE models on datasets containing more complex types of factual inconsistencies, such as those requiring logical reasoning or commonsense knowledge, would provide evidence of its effectiveness in these scenarios.

## Limitations

- The cascading pipeline architecture means errors compound multiplicatively, but the paper lacks ablation studies showing how much downstream performance depends on upstream accuracy.
- The entity type prediction relies heavily on embedding similarity between class names and input representations, but this approach isn't validated through qualitative analysis or comparison with traditional classification baselines.
- The evaluation metrics combine different measures without establishing their relative importance for the end task of improving factual consistency in generation systems.

## Confidence

**High confidence** in the span prediction mechanisms (M1) - the use of Transformer-based models for start/end token classification is well-established and the reported IoU scores (>94% for S/R/T) are consistent with state-of-the-art span prediction performance.

**Medium confidence** in the pipeline effectiveness - while individual components show reasonable performance, the paper lacks systematic ablation studies to demonstrate that the progressive refinement approach actually outperforms end-to-end alternatives.

**Low confidence** in the entity type embedding approach - the method assumes that embedding class names captures meaningful semantic relationships, but this isn't validated through qualitative analysis or comparison with traditional classification baselines on the same data.

## Next Checks

1. **Ablation study on pipeline stages**: Train an end-to-end model that predicts inconsistency types and entity types directly from claim and context without intermediate span prediction. Compare performance against the four-stage pipeline to quantify the benefit (or cost) of progressive refinement.

2. **Entity type embedding validation**: For the embedding-based entity type prediction, manually verify 50 random predictions by checking whether the predicted entity type's embedding is truly more similar to the input representation than the ground truth class. This would validate whether the embedding approach captures meaningful semantic relationships.

3. **Error analysis on context span detection**: Since context span prediction has the lowest IoU (~65%), perform detailed error analysis to determine whether failures stem from: (a) span localization errors, (b) semantic misalignment between claim and context spans, or (c) model architecture limitations. This would identify whether improved context understanding or different architectural choices are needed.
