# EVKG: An Interlinked and Interoperable Electric Vehicle Knowledge Graph for Smart Transportation System

## Quick Facts
- arXiv ID: 2304.04893
- Source URL: https://arxiv.org/abs/2304.04893
- Reference count: 22
- One-line primary result: EVKG integrates EV adoption, charging infrastructure, and transmission networks via ontology reuse and linked data, enabling cross-domain SPARQL queries for smart transportation decisions.

## Executive Summary
This paper introduces EVKG, a comprehensive knowledge graph for the electric vehicle industry that integrates EV adoption, charging infrastructure, and electricity transmission networks. EVKG leverages existing ontologies (GeoSPARQL, Time Ontology, SOSA SSN, KnowWhereGraph) to enable rapid integration and semantic interoperability. The knowledge graph supports decision-making in EV technology development, infrastructure planning, and policy-making by providing timely and accurate information through SPARQL queries across multiple domains.

## Method Summary
EVKG was constructed by collecting EV-related datasets from authoritative sources (Atlas EV Hub, US DOE, HIFLD) and transforming them into RDF triples using EVKG ontology modules. The ontology design reuses existing patterns from GeoSPARQL, Time Ontology, SOSA SSN Ontology, and KnowWhereGraph rather than reinventing the wheel. Data was loaded into GraphDB with spatial reasoning enabled, and EVKG entities were linked to external knowledge graphs via owl:sameAs. SPARQL queries were implemented to answer six competency questions demonstrating semantic, geospatial, temporal, and cross-domain querying capabilities.

## Key Results
- EVKG successfully integrates EV adoption data, charging station locations, and transmission networks using reused ontology modules
- Cross-domain queries linking EV data to climate zones and natural disasters are enabled through owl:sameAs links with KnowWhereGraph
- Prematerialized spatial relations improve query performance and avoid sliver polygon problems in geospatial analysis
- Six competency questions demonstrate EVKG's ability to answer complex EV-related questions across multiple domains

## Why This Works (Mechanism)

### Mechanism 1
- Claim: EVKG works because it reuses existing ontologies rather than reinventing the wheel, enabling rapid integration and semantic interoperability.
- Mechanism: By importing ontology modules from GeoSPARQL, Time Ontology, SOSA SSN Ontology, and KnowWhereGraph, EVKG can immediately leverage well-defined spatial, temporal, and semantic constructs, reducing modeling errors and ensuring consistency.
- Core assumption: The reused ontologies are sufficiently expressive and compatible for the EV domain.
- Evidence anchors:
  - [abstract] "Instead of reinventing the wheel, We reuse many ontology design patterns to model the spatial, temporal, and semantics aspect of EV data based on GeoSPARQL (Battle and Kolas, 2011), Time Ontology (Hobbs and Pan, 2006), SOSA SSN Ontology (Janowicz et al., 2019), and KnowWhereGraph (Janowicz et al., 2022) ontology."
  - [section] "Instead of regenerating subgraphs to describe place hierarchy and transportation networks, we build co-reference resolution links between EVKG and KWG on the US zip code area entities and reuse the ontology and subgraph of the national highway planning network."
- Break condition: If the reused ontologies evolve incompatibly or lack required expressiveness for new EV concepts, integration breaks.

### Mechanism 2
- Claim: EVKG achieves cross-domain querying by linking EV-specific data to broader geospatial and environmental knowledge graphs.
- Mechanism: Co-reference resolution links (owl:sameAs) between EVKG and KWG on zip code areas allow SPARQL queries to span EV data, demographics, climate zones, and natural disasters without duplicating triples.
- Core assumption: The shared entities (e.g., zip codes) are semantically equivalent and consistently defined across graphs.
- Evidence anchors:
  - [abstract] "We link the constructed EVKG with some existing knowledge graphs such as KnowWhereGraph (Janowicz et al., 2022), GNIS-LD (Regalia et al., 2018) which are also connected with DBpedia (Auer et al., 2007), Wikidata (Vrandeˇci´c, 2012), and GeoNames (Ahlers, 2013)."
  - [section] "By using the zip code entities as the transit node, we can ask questions across graphs like which zip code areas had more than 10 electric vehicle charging stations in 2021 but were affected by multiple wildfires in the past."
- Break condition: If cross-references are inaccurate or missing, queries will return incomplete or incorrect results.

### Mechanism 3
- Claim: EVKG enables spatial-temporal aggregation and fine-grained analysis by materializing spatial relations and structuring data at multiple administrative scales.
- Mechanism: Prematerialized spatial relation triples (e.g., kwg-ont:sfWithin, kwg-ont:sfContains) speed up geospatial queries and avoid sliver polygon problems; data is aggregated at zip code, county, and state levels for flexible analysis.
- Core assumption: Prematerialized relations are accurate and up-to-date with underlying geometries.
- Evidence anchors:
  - [abstract] "The EVKG encapsulates essential EV-related knowledge, including EV adoption, electric vehicle supply equipment, and electricity transmission network, to support decision-making related to EV technology development, infrastructure planning, and policy-making by providing timely and accurate information and analysis."
  - [section] "So the above geospatial questions can be answered by either using SPARQL queries with GeoSPARQL functions such as geo:sfContains which explicitly compute spatial relations based on the stored spatial footprints of geospatial entities, or using the prematerialized spatial relation properties such as kwg-ont:sfContains."
- Break condition: If spatial relations become stale or misaligned with geometries, query results degrade.

## Architecture Onboarding

- Component map:
  - EVKG ontology modules (EV adoption, charging infrastructure, transmission network)
  - External ontology imports (GeoSPARQL, Time Ontology, SOSA SSN, KnowWhereGraph)
  - Data ingestion pipelines (EV registration, charging stations, transmission lines, place hierarchy)
  - GraphDB triple store with GeoSPARQL support
  - SPARQL endpoint for queries
  - GitHub repository for ontology and queries

- Critical path:
  1. Collect raw EV-related datasets from authoritative sources.
  2. Triplify data using EVKG ontology and external imports.
  3. Load triples into GraphDB with spatial reasoning enabled.
  4. Link EVKG entities to KWG via owl:sameAs.
  5. Expose SPARQL endpoint for competency questions.

- Design tradeoffs:
  - Prematerialized spatial relations vs. on-the-fly computation: trades storage for query speed.
  - Fine-grained zip code aggregation vs. coarser county/state: trades precision for manageability.
  - Reuse vs. custom modeling: trades flexibility for rapid integration.

- Failure signatures:
  - SPARQL queries return empty or wrong results → likely spatial relation mismatch or ontology reuse error.
  - GraphDB performance degrades → likely insufficient indexing or overly complex spatial functions.
  - Data inconsistencies across linked graphs → likely broken owl:sameAs links or stale external data.

- First 3 experiments:
  1. Load a small subset of EV registration data, query for all EVs with a specific connector type in a single zip code.
  2. Add a new charging station, link it to an existing zip code via kwg-ont:sfWithin, and verify spatial queries return it.
  3. Execute a cross-domain query linking EV registrations to climate zone data via KWG, checking owl:sameAs resolution.
