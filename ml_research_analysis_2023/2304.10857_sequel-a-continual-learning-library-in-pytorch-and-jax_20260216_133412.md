# SequeL: A Continual Learning Library in PyTorch and JAX

## Quick Facts
- **arXiv ID**: 2304.10857
- **Source URL**: https://arxiv.org/abs/2304.10857
- **Reference count**: 40
- **Key outcome**: SequeL is a continual learning library supporting both PyTorch and JAX to enable reproducible research across frameworks, demonstrated by reproducing published results on RotatedMNIST (82.3% for MCSGD, 77.42% for LaMAML).

## Executive Summary
SequeL is a modular continual learning library that supports both PyTorch and JAX frameworks, providing a unified interface for diverse continual learning algorithms including regularization-based, replay-based, and hybrid approaches. The library features a modular design with separate framework-specific base classes, Hydra-based configuration management, and a callback system for extensibility. It enables reproducible research by providing complete configuration files and demonstrating correctness through reproduction of published results on benchmarks like RotatedMNIST and SplitMNIST.

## Method Summary
SequeL implements continual learning algorithms through a modular architecture where BaseAlgorithm handles generic continual learning logic (training loops, validation scheduling) while framework-specific base classes (PyTorchBaseAlgorithm and JaxBaseAlgorithm) manage framework peculiarities like CUDA device handling and NumPy conversion. The library uses Hydra configuration files to define all experimental parameters separately from code, enabling reproducible experiments and hyperparameter tuning without code changes. Callbacks provide hooks into training/validation events for metrics tracking, logging, and custom functionality, while multiple logging services (Weights & Biases, TensorBoard, Comet) track experiment progress. The library demonstrates correctness by reproducing published results on RotatedMNIST with specific algorithms and configurations.

## Key Results
- Successfully reproduces published results: 82.3% average accuracy on RotatedMNIST for MCSGD algorithm
- Achieves 77.42% average accuracy on RotatedMNIST for LaMAML algorithm using provided configurations
- Provides complete configuration files and benchmark implementations for SplitMNIST, SplitCIFAR, PermutedMNIST, and RotatedMNIST
- Supports both New Instance (PermutedMNIST, RotatedMNIST) and New Class (SplitMNIST, SplitCIFAR) continual learning scenarios

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Modular design with separate framework-specific base classes enables unified API while respecting framework-specific constraints.
- Mechanism: BaseAlgorithm handles generic continual learning logic while child classes implement framework-specific operations like CUDA device handling for PyTorch and NumPy conversion for JAX.
- Core assumption: Framework-specific details can be isolated without affecting algorithmic logic or data flow.
- Evidence anchors:
  - "The peculiarities and design constraints imposed by the PyTorch and JAX philosophy are handled by the corresponding base classes, PyTorchBaseAlgorithm and JaxBaseAlgorithm."
  - "The BaseAlgorithm offers basic functionality and uses callbacks for specific and custom functionalities."

### Mechanism 2
- Claim: Hydra-based configuration system enables reproducible experiments and hyperparameter tuning without code changes.
- Mechanism: Configuration files define all experiment parameters separately from code, allowing sharing complete experimental setups and facilitating systematic hyperparameter searches.
- Core assumption: All relevant experimental parameters can be expressed as configuration values without requiring code modifications.
- Evidence anchors:
  - "SequeL uses Hydra configuration files to formalize experiments... an experiment defined with Hydra can be easily shared and reported."
  - "Example configuration files along with reproducibility runs tracked via Weights&Biases are provided."

### Mechanism 3
- Claim: Callback system provides extensibility without modifying core algorithm code.
- Mechanism: Callbacks hook into training/validation events allowing metric tracking, logging, and custom functionality to be added without changing the algorithm implementation.
- Core assumption: Training loop events can be meaningfully intercepted to provide useful extensions without breaking the core flow.
- Evidence anchors:
  - "A callback provides hooks for any point in training and validation, similar to Pytorch Lightning [15]."
  - "Each event E in training, e.g., training epoch() is surrounded by four hooks in the following sequence: on before E, on before E callbacks, E, on after E and on after E callbacks."

## Architecture Onboarding

- Component map: Benchmarks -> Backbones -> Algorithms -> Callbacks -> Loggers
- Critical path: load data from benchmark → pass through backbone model → algorithm trains with callbacks monitoring → loggers track results
- Design tradeoffs:
  - Supporting both PyTorch and JAX increases code complexity but enables broader accessibility
  - Using Hydra for configuration enables reproducibility but may limit dynamic experiment variations
  - Callback system provides extensibility but can obscure the core training flow if overused
- Failure signatures:
  - Incorrect device handling: Models not moving to GPU in PyTorch or incorrect NumPy conversion in JAX
  - Data format mismatches: Benchmark outputs not compatible with framework-specific expectations
  - Callback ordering issues: Metrics not available when expected due to callback execution sequence
- First 3 experiments:
  1. Run SplitMNIST with MLP backbone using EWC algorithm (from config file) to verify basic functionality
  2. Run PermutedMNIST with CNN backbone using Naive SGD to test New Instance scenario handling
  3. Run hyperparameter sweep on EWC regularization coefficient using the provided configuration template to test Hydra integration
