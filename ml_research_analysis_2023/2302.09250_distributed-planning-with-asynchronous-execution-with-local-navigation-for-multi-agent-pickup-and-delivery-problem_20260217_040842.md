# Distributed Planning with Asynchronous Execution with Local Navigation for Multi-agent Pickup and Delivery Problem

## Quick Facts
- arXiv ID: 2302.09250
- Source URL: https://arxiv.org/abs/2302.09250
- Reference count: 40
- Method outperforms HTE and RHCR in completion rate, makespan, and planning time for MAPD problems

## Executive Summary
This paper introduces a distributed planning approach with asynchronous execution for the multi-agent pickup and delivery problem in environments with uncertain agent speeds and flexible task endpoints. The method enables agents to plan independently while relying on local node agents to detect and resolve conflicts through reservation systems. By structuring the environment into bi-connected components with oriented edges and tree-structured marginal areas, the approach prevents collisions and deadlocks without requiring global coordination. Experiments on two benchmark environments demonstrate superior performance compared to existing methods, particularly in crowded scenarios and under speed uncertainty.

## Method Summary
The method employs distributed planning where each carrier agent independently plans shortest paths to task destinations while ignoring other agents. Node agents manage reservations for each node in the graph, communicating with neighboring node agents to detect and resolve conflicts. The environment is structured with bi-connected components in the main area, oriented as a strongly connected directed graph to prevent head-on collisions. Tree-structured marginal areas with root node management handle flexible endpoints while preventing congestion. Agents can wait or take detours when conflicts are detected, enabling asynchronous execution despite speed fluctuations.

## Key Results
- Method achieves 100% completion rate in tested environments with 2-40 agents
- Outperforms HTE and RHCR baselines in makespan and planning time, especially in crowded scenarios
- Maintains collision-free operation under flexible endpoint placement and speed uncertainty

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Asynchronous movement with local node agents avoids collisions without global coordination.
- Mechanism: Each carrier agent plans its own shortest path ignoring others. Before moving to the next node, it requests reservation from the node agent managing that node. The node agent communicates with the next node's agent to check availability and either accepts the reservation or suggests waiting/detour. This local conflict detection prevents collisions while allowing asynchronous execution.
- Core assumption: Node agents can reliably communicate with neighboring nodes and agents can asynchronously reserve nodes without global synchronization.
- Evidence anchors:
  - [abstract]: "agents ignore others' paths and rely on local node agents to detect and avoid conflicts"
  - [section 4.3]: "node agent manages the reservation of the corresponding node for the staying (carrier) agent"
- Break condition: If node agent communication fails or becomes delayed, collisions may occur.

### Mechanism 2
- Claim: Graph orientation eliminates head-on collisions and deadlocks.
- Mechanism: The environment's main area is oriented as a strongly connected directed graph using the one-way street theorem. This orientation ensures agents can only move in one direction along edges, preventing them from traversing the same edge in opposite directions and eliminating certain deadlock patterns.
- Core assumption: The main area can be oriented as a strongly connected graph without losing essential connectivity.
- Evidence anchors:
  - [section 4.1]: "we introduced the orientation to the environment such that its main area can be observed as a strongly connected graph"
  - [section 5.3]: "direct edges prevented agents from crossing the same edge in opposite directions"
- Break condition: If the graph cannot be properly oriented (e.g., contains bridges), the mechanism fails.

### Mechanism 3
- Claim: Tree-structured marginal areas with root node management prevents congestion at task endpoints.
- Mechanism: Endpoints in tree-structured areas are managed by root node agents that restrict entry to one agent at a time. This prevents multiple agents from converging on the same endpoint simultaneously while allowing flexible endpoint placement.
- Core assumption: Tree-structured areas can be identified and managed by root nodes without creating bottlenecks.
- Evidence anchors:
  - [section 4.4]: "node agent manages to restrict the number of agents entering tree-structured subgraph to one"
  - [section 3.2]: "Our graph is constituted at a combination of indirect and direct edges"
- Break condition: If too many agents need to access endpoints in the same tree area, performance degrades.

## Architecture Onboarding

- Component map:
  Carrier agent -> Node agent (for next node) -> Node agent (for current node) -> Communication layer -> Node agent (for previous node)

- Critical path:
  1. Task allocation to carrier agent
  2. Carrier agent generates shortest path to destination
  3. For each next node in path, carrier agent requests reservation from current node agent
  4. Node agent checks with next node agent for availability
  5. If accepted, carrier moves; if denied, follows suggestion (wait or detour)
  6. Repeat until task completion

- Design tradeoffs:
  - Simplicity vs optimality: Agents ignore global plans for simplicity
  - Asynchronous vs synchronized: Allows robustness to delays but may create temporary inefficiencies
  - Local vs global conflict detection: Reduces communication overhead but may require more detours

- Failure signatures:
  - Node agent communication failure → potential collisions
  - Graph orientation failure → possible deadlocks
  - Insufficient open nodes → agent movement restrictions
  - High endpoint concentration → congestion and performance degradation

- First 3 experiments:
  1. Test with 2-4 agents on simple bi-connected graph with one endpoint
  2. Test with 10 agents on Env. 1 to verify collision-free operation
  3. Test with moving delay probability to verify robustness to speed fluctuations

## Limitations

- Performance may degrade when agent count approaches half the number of nodes in the main area due to congestion
- Scalability to environments with many task endpoints (more than a few per agent) is not validated
- Specific graph orientation algorithm for creating strongly connected components is not detailed

## Confidence

- **High confidence**: Collision-free execution in tested environments (validated through experiments on Env. 1 and Env. 2 with 2-40 agents)
- **Medium confidence**: Scalability to larger environments (based on limited experimental range and absence of extreme congestion tests)
- **Medium confidence**: Robustness to speed fluctuations (supported by experiments but mechanism not fully explained)
