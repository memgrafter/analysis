# Controllable Data Augmentation for Context-Dependent Text-to-SQL

## Quick Facts
- arXiv ID: 2304.13902
- Source URL: https://arxiv.org/abs/2304.13902
- Reference count: 21
- Primary result: 1.6% average improvement in question match accuracy, 3.3% on complex questions

## Executive Summary
This paper introduces CONDA, a controllable data augmentation method for context-dependent text-to-SQL tasks. The approach addresses limited annotated data by representing context information as SQL dialogue states and using state transfer to generate new examples. A grounding model filters low-quality questions to ensure data quality. Evaluated on SParC and CoSQL datasets using RAT-SQL as the baseline, CONDA demonstrates significant improvements in question match accuracy, particularly for complex queries.

## Method Summary
CONDA operates through a three-stage pipeline: state transfer, dialogue generation, and filtering. It first extracts SQL dialogue states from existing examples, then applies controlled state transitions to generate new states. These states are converted to natural language questions using back-translation, and a grounding model filters out mismatched questions. The method is specifically designed for context-dependent text-to-SQL tasks where understanding dialogue history is crucial for generating accurate SQL queries.

## Key Results
- CONDA improves question match accuracy by 1.6% on average across SParC and CoSQL datasets
- Complex question performance increases by 3.3% with CONDA augmentation
- Generated data shows high diversity in SQL templates, hardness levels, and interaction turns
- The method demonstrates consistent improvements across different evaluation metrics

## Why This Works (Mechanism)

### Mechanism 1
- Claim: CONDA improves text-to-SQL performance by generating diverse, high-quality augmented data through controllable state transitions.
- Mechanism: CONDA represents context information as SQL dialogue states and uses state transfer to generate new examples. A grounding model filters low-quality questions, ensuring data quality.
- Core assumption: State transitions can effectively simulate dialogue context changes, and the grounding model can accurately filter mismatched questions.
- Evidence anchors:
  - [abstract] "We designed the SQL dialogue state to enhance the data diversity through the state transition."
  - [section 3.3] "The task of the transfer model is to generate the new state ˜si based on the database D, the transfer type transf eri, and the previous state si−1."
  - [corpus] Weak evidence - no direct citations for state transfer effectiveness.
- Break condition: If state transitions fail to capture relevant context changes or the grounding model cannot accurately filter mismatched questions.

### Mechanism 2
- Claim: CONDA generates SQL queries and corresponding natural language questions through back-translation.
- Mechanism: CONDA uses a back-translation model to generate NL questions from SQL dialogue states. The model is trained on SQL queries as input and corresponding NL questions as output.
- Core assumption: The back-translation model can effectively learn the mapping between SQL and NL questions.
- Evidence anchors:
  - [section 3.5] "Building upon previous research (LI et al., 2021), CONDA employs back-translation to produce relevant NL questions from SQL dialogue states."
  - [section 3.6] "We utilize a grounding model to identify and filter low-quality questions that mismatch the state information."
  - [corpus] Weak evidence - no direct citations for back-translation effectiveness.
- Break condition: If the back-translation model fails to generate meaningful NL questions or the grounding model cannot effectively filter low-quality questions.

### Mechanism 3
- Claim: CONDA ensures data quality through a grounding model that identifies and filters mismatched NL questions.
- Mechanism: The grounding model identifies entities within the question and checks if they match the transferred state. Questions with mismatched entities are filtered out.
- Core assumption: The grounding model can accurately identify entities and determine if they match the transferred state.
- Evidence anchors:
  - [section 3.6] "We utilize a grounding model to identify and filter low-quality questions that mismatch the state information."
  - [section 4.4] "The training process of the grounding model and the parser models follows the default setting."
  - [corpus] Weak evidence - no direct citations for grounding model effectiveness.
- Break condition: If the grounding model fails to accurately identify entities or determine if they match the transferred state.

## Architecture Onboarding

- Component map: State transfer -> Dialogue generation -> Filter
- Critical path: State transfer → Dialogue generation → Filter
- Design tradeoffs:
  - Controllability vs. diversity: CONDA prioritizes controllability through state transitions, which may limit diversity compared to other methods.
  - Quality vs. quantity: The grounding model ensures data quality but may reduce the quantity of augmented data.
- Failure signatures:
  - Low diversity in generated data
  - Poor performance on complex questions
  - High proportion of filtered-out questions

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the grounding model's performance compare to alternative filtering methods like SQL parser-based filtering?
- Basis in paper: explicit
- Why unresolved: The paper mentions the grounding model is more efficient than parser-based filtering but doesn't provide a direct comparison of their effectiveness in filtering quality data.
- What evidence would resolve it: Experimental results comparing data quality metrics (e.g., question consistency, SQL hardness) between models using grounding vs. parser-based filtering.

### Open Question 2
- Question: What is the impact of different state transfer types on the diversity of generated SQL templates?
- Basis in paper: explicit
- Why unresolved: While the paper lists 11 state transfer types and shows CONDA generates diverse templates, it doesn't analyze which specific transfer types contribute most to this diversity.
- What evidence would resolve it: Detailed analysis showing template diversity metrics (e.g., template count, type distribution) for each state transfer type.

### Open Question 3
- Question: How does CONDA perform on datasets with different domain distributions compared to Spider?
- Basis in paper: inferred
- Why unresolved: The paper only tests on SParC and CoSQL, both derived from Spider. It's unclear if CONDA's effectiveness generalizes to datasets with different domain distributions.
- What evidence would resolve it: Experimental results on additional datasets with varying domain distributions, comparing CONDA's performance to baseline models.

### Open Question 4
- Question: What is the effect of CONDA on rare SQL patterns that are underrepresented in the original training data?
- Basis in paper: inferred
- Why unresolved: While CONDA generates diverse templates, the paper doesn't specifically address its impact on rare SQL patterns that are crucial for generalization.
- What evidence would resolve it: Analysis of SQL pattern frequencies before and after CONDA augmentation, focusing on rare patterns and their impact on model performance.

## Limitations
- Limited empirical evidence for the effectiveness of individual components (state transfer, back-translation, grounding filter)
- Unclear generalizability beyond the specific SQL dialogue state representation
- No analysis of computational overhead or scalability

## Confidence
- High confidence in the core framework: The paper clearly articulates the three-stage pipeline (state transfer → dialogue generation → filtering) and demonstrates measurable performance improvements on benchmark datasets.
- Medium confidence in mechanism details: While the general approach is well-specified, critical implementation details like the exact state transfer types, grounding model architecture, and back-translation specifics are not fully described.
- Low confidence in failure analysis: The paper doesn't provide comprehensive analysis of when or why the method might fail, making it difficult to anticipate edge cases.
