# Baldur: Whole-Proof Generation and Repair with Large Language Models

## Quick Facts
- arXiv ID: 2303.04910
- Source URL: https://arxiv.org/abs/2303.04910
- Reference count: 40
- Key result: Proves 47.9% of Isabelle/HOL theorems automatically, compared to 39.0% for search-based approaches

## Executive Summary
This paper introduces Baldur, a novel approach for automated formal verification using large language models (LLMs). Unlike prior methods that predict one proof step at a time, Baldur generates entire proofs at once using fine-tuned LLMs. The approach also introduces proof repair, where an LLM attempts to fix incorrect proofs using error messages from the proof assistant. Additionally, Baldur explores providing the LLM with context from the same theory file, leveraging in-context learning to improve performance.

## Method Summary
Baldur fine-tunes large language models (specifically Minerva) on complete proofs from the PISA dataset of 6,336 Isabelle/HOL theorems. The approach generates entire proofs in one step rather than iteratively, then uses the proof assistant's error messages to repair failed attempts. Context from preceding lines in the theory file is also provided as input. The method is evaluated on a test set of 254 theorems, comparing proof success rates against state-of-the-art search-based approaches like Thor.

## Key Results
- Baldur (without repair) proves 47.9% of theorems automatically, compared to 39.0% for search-based approaches
- Proof repair further improves performance, proving an additional 1.5% of theorems
- Providing theory file context improves proving power from 40.7% to 47.5% for the same model size
- Baldur complements prior techniques, and together they can prove 65.7% of the theorems

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Whole-proof generation using transformers is possible and is as effective as search-based techniques without requiring costly search.
- Mechanism: Fine-tuning large language models (LLMs) on complete proofs allows them to generate entire proofs in one step, bypassing the need for iterative proof search.
- Core assumption: LLMs trained on sufficient proof data can capture the necessary reasoning patterns to produce valid proofs without intermediate proof states.
- Evidence anchors:
  - [abstract] "We use large language models... to generate whole proofs for theorems at once, rather than one step at a time."
  - [section 3.3] "Our naive proof generation approach with an 8b language model achieves a proof rate of 34.8% with 16 samples and of 40.7% with 64 samples."
  - [corpus] Weak evidence: While related works like Apollo and Proof Automation with LLMs exist, they focus on different proof assistants or approaches, making direct comparison difficult.
- Break condition: If the training data lacks diversity in proof strategies or the proofs are too complex for the model to capture in a single generation step.

### Mechanism 2
- Claim: LLMs can be used to repair proofs, including their own failed proof attempts, and this can boost overall proving power.
- Mechanism: Providing the LLM with both the incorrect proof and the error message from the proof assistant enables it to generate a corrected proof.
- Core assumption: The error message contains sufficient information for the LLM to understand and correct the mistake in the proof.
- Evidence anchors:
  - [abstract] "Giving the learned model additional context, such as a prior failed proof attempt and the ensuing error message, results in proof repair and further improves automated proof generation."
  - [section 3.4] "We observe that the repair approach consistently outperforms the plain proof generation model... This suggests that the information in the error message is crucial for the observed gains of the repair approach."
  - [corpus] Weak evidence: Similar proof repair approaches exist but typically don't leverage error messages as directly as Baldur does.
- Break condition: If the error messages are too cryptic or if the proof error is too complex for the LLM to correct based on the provided context.

### Mechanism 3
- Claim: LLMs can benefit from the context in which the theorem occurred in the theory file, both quantitatively by increasing proving power, and qualitatively by copying and adapting nearby proofs.
- Mechanism: Providing the LLM with preceding lines from the same theory file as context helps it leverage similar proofs and definitions to construct new proofs.
- Core assumption: Proofs in formal verification often reuse patterns and definitions from the surrounding context, which LLMs can learn to exploit.
- Evidence anchors:
  - [abstract] "Giving the learned model additional context... results in proof repair and further improves automated proof generation."
  - [section 3.5] "At 64 samples, the proof rate increases from 40.7% to 47.5% for the same model size."
  - [section A] Examples show the model copying and adapting proofs from the context.
- Break condition: If the context is too sparse or if the theorem requires knowledge not present in the provided context.

## Architecture Onboarding

- Component map: PISA dataset -> Minerva LLM -> Fine-tuning pipeline -> Isabelle/HOL proof checker -> Context extraction -> Inference pipeline with sampling
- Critical path: 1. Extract context and theorem statement 2. Generate proof using fine-tuned LLM 3. Check proof with Isabelle/HOL 4. If failed, generate repair using error message and incorrect proof 5. Repeat proof checking until success or timeout
- Design tradeoffs:
  - Using whole-proof generation vs. step-by-step generation (efficiency vs. flexibility)
  - Providing context vs. not (improved performance but increased input length)
  - Sampling multiple proofs vs. single attempt (increased success rate but higher computational cost)
- Failure signatures:
  - Proof generation fails consistently: Likely due to insufficient training data or model capacity
  - Repair attempts fail: Error messages might be too cryptic or proofs too complex to correct
  - Context doesn't improve performance: Context might be irrelevant or too sparse for the given theorems
- First 3 experiments:
  1. Fine-tune a small LLM on a subset of proofs and evaluate its generation capability
  2. Test the impact of providing context on proof generation success rate
  3. Evaluate the effectiveness of the repair model on artificially generated incorrect proofs

## Open Questions the Paper Calls Out

- **Open Question 1**: How does Baldur's performance scale with increasingly larger language models beyond the 62B parameter model tested?
  - Basis in paper: [explicit] The paper notes that larger models perform better but only tests up to 62B parameters, stating "We observe that the 62b proof generation model with context outperforms the 8b proof generation model with context. One caveat here is that we were not able to tune hyperparameters as well due to the higher cost of these experiments, so an optimally tuned 62b model may perform even better."
  - Why unresolved: The paper only tested two model sizes (8B and 62B) due to computational constraints, leaving open questions about performance at even larger scales.
  - What evidence would resolve it: Experiments with models of 100B+ parameters, systematically varying temperature and other hyperparameters, would show if there's a point of diminishing returns or continued improvement.

- **Open Question 2**: Can Baldur's proof repair capability be extended to handle multi-step error chains rather than just the first error message?
  - Basis in paper: [inferred] The paper notes that error messages typically contain only the first error, limiting the repair model's effectiveness: "When proof checking, the resulting error message is for the first occurring error, typically from the first couple of lines of the predicted proof."
  - Why unresolved: The current repair model only addresses the first error in a proof, while real proofs often have cascading errors that build on each other.
  - What evidence would resolve it: Developing a multi-pass repair system that iteratively addresses errors, potentially using the model's own repaired versions as new inputs for subsequent repairs.

- **Open Question 3**: How does Baldur perform on proof assistants other than Isabelle/HOL, particularly those with more procedural proof styles like Coq?
  - Basis in paper: [inferred] The paper discusses challenges in comparing across proof assistants and notes differences in proof styles: "We used an established benchmark of Isabelle/HOL proofs to fairly compare Baldur to prior work and to increase the chances that our results generalize. However, we observed that search-based proof-synthesis tools for other proof assistants tend to prove a smaller fraction of theorems than we have found in our work."
  - Why unresolved: The paper's evaluation is limited to Isabelle/HOL, and different proof assistants have different proof languages and strategies that may affect LLM performance.
  - What evidence would resolve it: Porting Baldur to Coq and other proof assistants, evaluating on their respective benchmarks, and comparing performance across systems would reveal generalizability.

## Limitations

- Fine-tuning process lacks detailed specification of hyperparameters, making exact replication challenging
- Reliance on error messages assumes these messages are consistently informative and structured for LLM utilization
- Context provision may have diminishing returns or negative effects if context contains irrelevant information
- Evaluation focuses on Isabelle/HOL, raising questions about generalizability to other formal verification settings

## Confidence

- High confidence in the core claims about whole-proof generation being effective
- Medium confidence in the proof repair mechanism
- Medium confidence in the context utilization claims
