# How Efficient Are Today's Continual Learning Algorithms?

## Quick Facts
- arXiv ID: 2303.18171
- Source URL: https://arxiv.org/abs/2303.18171
- Reference count: 28
- Key outcome: Many CL methods use more compute than offline training, but REMIND achieves competitive accuracy with 10x less memory and least compute

## Executive Summary
This paper evaluates the efficiency of continual learning methods for incremental class learning on ImageNet-1K, revealing that many recent CL methods solve catastrophic forgetting at the cost of computational efficiency. While these methods claim to avoid expensive retraining, some actually require more compute than training from scratch. The study introduces the NetScore metric combining accuracy, model size, computational overhead, and memory usage, finding that REMIND is the most efficient method, using compressed feature replay to achieve competitive accuracy with dramatically reduced resource requirements.

## Method Summary
The paper compares seven CL methods (iCaRL, End-to-End, BiC, W A, DER, DER with pruning, and REMIND) on ImageNet-1K using incremental class learning with 10 batches of 100 classes each. Methods are evaluated using NetScore, which combines top-5 accuracy, parameter count, memory usage, and backpropagation updates. REMIND uses compressed feature replay with quantized mid-level CNN features, freezing earlier layers after initialization to reduce compute requirements. The replay buffer budget is 3GB for most methods and 2GB for REMIND.

## Key Results
- REMIND achieves competitive accuracy while using 10x less memory and the least compute among all methods
- DER without pruning achieves closest accuracy to offline model but requires 10x more parameters and almost twice the compute
- Some CL methods use more compute than offline ResNet18 training (115.31 million backprop updates)
- iCaRL, End-to-End, BiC, W A, and DER store current batch data during training, adding significant unaccounted memory overhead

## Why This Works (Mechanism)

### Mechanism 1
- Claim: REMIND is the most efficient continual learning method because it uses compressed feature replay instead of storing raw images.
- Mechanism: REMIND compresses mid-level CNN features and quantizes them to reduce memory usage, allowing it to operate with 10× less memory than methods storing raw images.
- Core assumption: Compressed features retain sufficient information for accurate replay while enabling dramatic memory reduction.
- Evidence anchors:
  - [abstract] "REMIND uses compressed feature replay where mid-level CNN features are quantized to reduce memory overhead."
  - [section] "REMIND uses 2 GB of storage when storing compressed mid-level features, whereas all the remaining methods use 3 GB of storage that corresponds to 20000 raw images (224×224 uint8)."
- Break condition: If feature compression degrades too much information, catastrophic forgetting would increase and accuracy would drop despite lower memory usage.

### Mechanism 2
- Claim: Many continual learning methods are inefficient because they store the current batch data during training, adding significant memory overhead beyond replay buffer.
- Mechanism: Methods like iCaRAL, End-to-End, BiC, W A, and DER temporarily store new batch data in addition to replay buffer, multiplying total memory usage.
- Core assumption: The paper correctly identifies this as an "unaccounted for" memory cost that existing efficiency metrics miss.
- Evidence anchors:
  - [abstract] "Another shortcoming of existing systems is that they do not fully account for the amount of memory or storage used during incremental training."
  - [section] "Each incremental learning batch typically consists of around 100,000 images... Additional memory is also used for the DNN parameters."
- Break condition: If methods could be redesigned to process batches without storing them entirely in memory, this inefficiency could be eliminated.

### Mechanism 3
- Claim: REMIND freezes earlier CNN layers and trains only later layers on reconstructed features, reducing computational updates needed.
- Mechanism: By freezing initial layers after first batch initialization, REMIND reduces the number of parameters being updated during subsequent batches, lowering compute requirements.
- Core assumption: Freezing early layers preserves useful feature representations while allowing efficient adaptation through later layers.
- Evidence anchors:
  - [abstract] "REMIND freezes earlier CNN layers and trains the remaining layers on reconstructed features."
  - [section] "REMIND uses the first batch to initialize the CNN" then freezes layers for subsequent batches.
- Break condition: If early layer features become suboptimal for new tasks, freezing them would prevent necessary adaptation and hurt performance.

## Foundational Learning

  - Why needed here: The paper's efficiency analysis is framed around methods that claim to solve catastrophic forgetting, so understanding this phenomenon is essential
  - Quick check question: What happens to a neural network's performance on old tasks when trained only on new data without any continual learning mechanism?

- Concept: Incremental class learning
  - Why needed here: The paper specifically evaluates methods for incremental class learning on ImageNet, where new classes are introduced in batches
  - Quick check question: In incremental class learning, are classes ever revisited after their initial introduction, or are they seen only once?

- Concept: Memory replay mechanisms
  - Why needed here: All compared methods use some form of replay to mitigate forgetting, making this a foundational concept for understanding their efficiency differences
  - Quick check question: How does replay-based continual learning differ from methods that only use regularization or parameter isolation?

## Architecture Onboarding

- Component map: ImageNet data stream → ResNet18 backbone → replay buffer (raw images or compressed features) → classification head expansion → optimization procedure → accuracy evaluation
- Critical path: Data stream → feature extraction → replay storage/retrieval → parameter updates → evaluation; the efficiency bottleneck typically occurs at replay storage and parameter update stages
- Design tradeoffs: Memory efficiency vs. accuracy (compressed features save memory but may lose information), compute efficiency vs. adaptation capability (freezing layers saves compute but may limit learning), storage requirements vs. real-time constraints (large batches improve performance but require more memory)
- Failure signatures: Methods using more compute than offline training defeat the purpose of continual learning; methods requiring 10× more parameters than offline baseline are impractical; methods that cannot handle arbitrary data orderings fail in real-world scenarios

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How can continual learning algorithms be made computationally efficient while maintaining performance on large-scale datasets like ImageNet-1K?
- Basis in paper: [explicit] The paper argues that many CL methods use more compute than offline models, defeating one of the main goals of CL. It highlights that some methods require 10x more parameters and almost twice the compute compared to offline ResNet18.
- Why unresolved: While the paper identifies efficiency issues, it doesn't provide a clear path to making CL algorithms both efficient and effective on large-scale datasets.
- What evidence would resolve it: A CL method that achieves comparable accuracy to offline models while using significantly less compute and parameters on ImageNet-1K would demonstrate a solution to this issue.

### Open Question 2
- Question: Can continual learning methods be designed to handle arbitrary data orderings, including cases where classes are revisited, rather than being limited to incremental class learning scenarios?
- Basis in paper: [explicit] The paper notes that most CL methods are designed for incremental class learning, which is an extreme edge case. It suggests that CL systems should learn from data in any order, including iid data or data with temporal correlations.
- Why unresolved: Most existing CL methods are tailored for specific scenarios like incremental class learning and don't generalize well to arbitrary data orderings.
- What evidence would resolve it: A CL method that maintains performance across various data orderings, including cases where classes are revisited, would demonstrate a solution to this limitation.

### Open Question 3
- Question: How can continual learning be applied to real-world applications where strong assumptions about data distribution cannot be made, and where efficiency is crucial for on-device learning?
- Basis in paper: [explicit] The paper emphasizes the need for CL systems to be efficient for real-world applications, particularly on-device learning scenarios where devices have limited storage and computation capabilities.
- Why unresolved: While the paper highlights the importance of efficiency for real-world applications, it doesn't provide specific solutions for adapting CL to these scenarios.
- What evidence would resolve it: A CL system that can be efficiently deployed on resource-constrained devices (e.g., mobile phones, IoT devices) and performs well across various data distributions would demonstrate a solution to this challenge.

## Limitations
- Limited to single dataset (ImageNet-1K) and specific CL setting (incremental class learning with fixed batch sizes)
- Does not account for implementation-specific optimizations that could affect real-world efficiency measurements
- Compressed feature replay mechanism in REMIND lacks extensive validation regarding feature quality degradation over multiple incremental steps

## Confidence
- High confidence: The observation that many CL methods use more compute than offline training is well-supported by measured backpropagation update counts
- Medium confidence: The claim that CL methods must be computationally cheaper than periodic retraining for real-world impact depends on unstated assumptions about deployment scenarios
- Low confidence: The assertion that existing CL methods don't fully account for memory usage during training relies on specific implementation details that may vary across codebases
