# An Efficient Sparse Inference Software Accelerator for Transformer-based Language Models on CPUs

## Quick Facts
- arXiv ID: 2306.16601
- Source URL: https://arxiv.org/abs/2306.16601
- Reference count: 40
- Key outcome: Up to 5x speedup over oneDNN dense GEMM and 1.5x over Neural Magic's Deepsparse on Transformer models

## Executive Summary
This paper presents a sparse inference software accelerator for Transformer-based language models on CPUs, leveraging structured sparsity with a 4x1 block size and Intel® Deep Learning Boost (VNNI) instructions. The authors develop sparse GEMM and attention kernels that demonstrate significant performance improvements over existing dense and sparse implementations. The solution achieves up to 5x speedup over oneDNN's dense GEMM kernel and outperforms state-of-the-art sparse libraries by an order of magnitude across various GEMM shapes and sparsity ratios.

## Method Summary
The approach defines a structured sparsity pattern with constant block size 4x1 and implements sparse GEMM kernels using just-in-time (JIT) compilation to generate machine code optimized for specific GEMM shapes. The software leverages Intel® Deep Learning Boost instructions to maximize performance of sparse matrix-dense matrix multiplication operations. The framework includes operator fusion techniques to reduce memory traffic and kernel launch overhead in Transformer attention computations, along with an end-to-end inference pipeline featuring custom memory allocation and thread scheduling. Models are quantized to INT8 precision while maintaining accuracy within 1% of baseline.

## Key Results
- Up to 5x speedup over oneDNN's dense GEMM kernel
- 1.5x speedup over Neural Magic's Deepsparse on same CPU instance
- 37x-345x speedup over ONNX Runtime and PyTorch under latency constraints
- Outperforms existing sparse libraries (oneMKL, TVM, LIBXSMM) by an order of magnitude

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The 4x1 structured sparsity pattern is optimal for VNNI instruction utilization on Intel CPUs.
- Mechanism: VNNI processes 16 groups of 4 adjacent pairs of 8-bit integers in parallel. The 4x1 block size matches the maximum tiling size that fully utilizes computation throughput without register reuse overhead.
- Core assumption: Hardware supports efficient broadcast and permutation operations to restructure sparse weight and input data into VNNI-compatible formats.
- Evidence anchors: [abstract]: "We define a structured sparsity pattern based on constant block size 4x1." [section]: "This also explains why we use the constant block size 4..."
- Break condition: If hardware doesn't support efficient broadcast/permutation operations for the 4x1 pattern, or if register pressure becomes too high for larger models.

### Mechanism 2
- Claim: JIT compilation enables better register utilization and reduces loop overhead for sparse GEMM kernels.
- Mechanism: JIT compilation generates machine code directly for each GEMM shape, unrolling loops and optimizing memory access patterns specific to the sparsity structure, avoiding generic kernel dispatch overhead.
- Core assumption: JIT compilation overhead is amortized over many kernel invocations, and generated code is better optimized than library implementations.
- Evidence anchors: [section]: "To demonstrate the performance of our defined sparsity pattern, we implement the sparse GEMM kernel by leveraging just-in-time (JIT) compilation..."
- Break condition: If JIT compilation overhead becomes significant for small GEMM shapes, or if generated code doesn't optimize well for certain sparsity patterns.

### Mechanism 3
- Claim: Operator fusion reduces memory traffic and kernel launch overhead in Transformer attention computations.
- Mechanism: Fusing element-wise operations (bias addition, activation functions) directly into sparse GEMM kernel keeps intermediate results in registers, eliminating memory writes/reads between operations and reducing kernel launches.
- Core assumption: Fused operations can be implemented efficiently using SIMD instructions and don't introduce significant code complexity that outweighs benefits.
- Evidence anchors: [section]: "Operator fusion is useful in deep learning for reducing the redundant memory and kernel launch overhead..."
- Break condition: If fused operations become too complex to fit in registers, or if compiler can't optimize fused code effectively.

## Architecture Onboarding

- Component map: Model loading and sparse weight extraction -> JIT compilation of sparse GEMM kernels -> Operator fusion and graph optimization -> Inference execution with multi-threading

- Critical path:
  1. Model loading and sparse weight extraction
  2. JIT compilation of sparse GEMM kernels for each unique weight shape
  3. Operator fusion and graph optimization
  4. Inference execution with multi-threading

- Design tradeoffs:
  - Block size vs. flexibility: 4x1 provides optimal VNNI utilization but may not be optimal for all model architectures
  - JIT compilation vs. pre-compilation: JIT offers shape-specific optimization but adds compilation overhead
  - Operator fusion depth vs. code complexity: More fusion reduces memory traffic but increases code complexity

- Failure signatures:
  - Poor performance on small GEMM shapes (JIT overhead not amortized)
  - Suboptimal scaling on multi-threading (load imbalance, memory contention)
  - Accuracy degradation after quantization (insufficient precision)

- First 3 experiments:
  1. Benchmark sparse GEMM kernel performance across different block sizes (4x1, 2x2, 4x4) to verify 4x1 is optimal
  2. Compare JIT-compiled kernel performance against pre-compiled kernels for various GEMM shapes
  3. Measure operator fusion impact by comparing fused vs. unfused attention computations on a small Transformer model
