# BCEdge: SLO-Aware DNN Inference Services with Adaptive Batching on Edge Platforms

## Quick Facts
- arXiv ID: 2305.01519
- Source URL: https://arxiv.org/abs/2305.01519
- Reference count: 40
- Improves throughput-latency trade-off by up to 37.6% while maintaining SLO constraints on edge platforms

## Executive Summary
BCEdge is a learning-based scheduling framework for DNN inference services on edge platforms that optimizes both throughput and latency simultaneously. It employs adaptive batching and concurrent execution of DNN models, leveraging maximum entropy-based deep reinforcement learning to automatically determine optimal batch size and concurrent model count for each incoming request. The framework introduces a utility function to balance throughput and latency trade-offs and incorporates an SLO-aware interference prediction model to reduce latency impact from concurrent execution.

## Method Summary
BCEdge uses maximum entropy-based soft actor-critic (SAC) deep reinforcement learning with discrete action spaces to co-optimize batch size and concurrent model count. The framework maintains per-model request queues, dynamically batches requests, and dispatches them to multiple concurrent instances on edge GPUs. A lightweight neural network predicts latency increases from concurrent execution based on resource utilization, enabling SLO-aware scheduling decisions. The system is evaluated on six DNN models across three NVIDIA Jetson platforms, demonstrating improved utility and reduced SLO violations compared to baselines.

## Key Results
- Improves throughput-latency trade-off by up to 37.6% compared to state-of-the-art solutions
- Reduces SLO violation rate from 9.2% to 4.1% using SLO-aware interference prediction
- Achieves scheduling overhead of 1.3-2.1 ms, maintaining real-time responsiveness

## Why This Works (Mechanism)

### Mechanism 1
- Claim: BCEdge uses maximum entropy-based deep reinforcement learning to automatically co-optimize batch size and concurrent models.
- Mechanism: DRL agent observes system state (model type, input shape, SLO, resource utilization, request queue) and selects discrete actions. Maximum entropy formulation encourages exploration by maintaining policy distribution, speeding up learning and avoiding local optima.
- Core assumption: System state fully captures relevant information for scheduling decisions, and reward function accurately reflects throughput-latency trade-off.
- Evidence anchors: [abstract] Maximum entropy-based DRL maximizes utility by co-optimizing batch size and concurrent models. [section] Maximum entropy formulation enables stronger exploration ability.

### Mechanism 2
- Claim: BCEdge incorporates a lightweight neural network-based interference predictor to estimate latency increases from concurrent execution.
- Mechanism: Predictor takes current resource utilization and concurrent model count as input, estimates added latency, and adjusts scheduling decisions to reduce SLO violations.
- Core assumption: Interference between concurrent models can be modeled as function of resource utilization and model count, learnable by small neural network with negligible overhead.
- Evidence anchors: [abstract] SLO-aware interference prediction model reduces impact of concurrent execution on latency. [section] NN-based predictor reduces SLO violation rate from 9.2% to 4.1%.

### Mechanism 3
- Claim: BCEdge uses dynamic batching and concurrent model instances to maximize edge GPU utilization while respecting SLO constraints.
- Mechanism: Inference requests queued per model type, batched based on scheduler decisions, and dispatched to multiple concurrent instances. Exploits GPU parallelism and reduces per-request overhead.
- Core assumption: Edge platform has sufficient memory and compute for concurrent instances, and batching improves throughput without violating SLO.
- Evidence anchors: [abstract] BCEdge employs adaptive batching and concurrent execution. [section] Dynamic batching merges requests, concurrent instances allow parallel GPU execution.

## Foundational Learning

- **Markov Decision Process (MDP) formulation for scheduling**: Transforms multi-objective optimization into sequential decision problem solvable by DRL. Quick check: What are the state, action, reward, and transition components in BCEdge's MDP?
- **Maximum entropy reinforcement learning**: Encourages exploration of large discrete action space and avoids premature convergence to suboptimal policies. Quick check: How does adding entropy to reward help agent explore better in BCEdge?
- **Neural network interference modeling**: Predicts latency impact of running multiple models concurrently, enabling scheduler to avoid SLO violations due to resource contention. Quick check: What inputs does BCEdge's interference predictor use, and why are they relevant?

## Architecture Onboarding

- **Component map**: IoT devices → Request queues (per model) → Dynamic batching module → Concurrent instance module → Edge GPU execution → Performance profiler → SLO-aware interference predictor → Maximum entropy DRL scheduler (policy/critic/temperature networks) → Feedback loop
- **Critical path**: Request arrival → Queueing → Scheduler decision (batch size + concurrent count) → Batching + Instance dispatch → Execution → Latency/SLO measurement → Interference prediction update → Next scheduling cycle
- **Design tradeoffs**: Batching increases throughput but may increase latency; concurrent execution improves resource utilization but increases interference. Larger neural networks for interference prediction improve accuracy but increase overhead; simpler models are faster but less accurate. Frequent scheduling decisions improve responsiveness but increase overhead; infrequent decisions reduce overhead but may miss dynamic changes.
- **Failure signatures**: SLO violations increasing over time → Interference prediction or scheduler exploration failing. GPU memory overflow → Batch size/concurrent count too high for available memory. Low throughput despite high GPU utilization → Batching or concurrency misconfigured.
- **First 3 experiments**: 1) Run BCEdge with single model and varying batch sizes to measure throughput vs latency trade-off and identify utility peak. 2) Enable two models concurrently with fixed batch sizes and measure interference-induced latency increases; train and test interference predictor. 3) Full multi-model run with scheduler enabled; record utility, SLO violation rate, and scheduling overhead; compare against baselines (DeepRT, TAC).

## Open Questions the Paper Calls Out

The paper does not explicitly call out open questions, but several implicit questions arise from the work:

1. How does BCEdge's performance scale when applied to a heterogeneous edge-cloud environment with varying network latencies between edge devices and the cloud?
2. What is the impact of different DNN model architectures (e.g., transformer-based models) on BCEdge's scheduling efficiency and SLO compliance?
3. How does BCEdge handle dynamic changes in the workload, such as sudden spikes in request arrival rates or changes in the mix of DNN models being requested?

## Limitations

- Evaluation limited to six DNN models and three edge platforms, potentially not capturing full diversity of real-world deployments
- Scheduling overhead (1.3-2.1 ms) is not negligible compared to some SLOs (50-200 ms), potentially impacting latency-sensitive applications
- Missing critical implementation details including exact neural network architecture for interference prediction and specific SAC hyperparameters beyond learning rate

## Confidence

**Confidence: Medium** - Core claims about throughput-latency trade-off improvement are supported by experimental results, but evaluation has notable limitations including limited model diversity and missing implementation details.

**Confidence: Low** - Several critical implementation details are missing from paper, including exact neural network architecture for interference prediction, specific SAC hyperparameters beyond learning rate, and complete state space definition.

## Next Checks

1. **Generalization Test**: Evaluate BCEdge on additional DNN models and edge platforms not included in original training set to assess interference predictor's generalization capability and scheduler's adaptability to new environments.

2. **Scalability Analysis**: Test BCEdge under extreme load conditions (e.g., 10× request rate) to measure performance degradation, memory usage patterns, and SLO violation rates, identifying potential bottlenecks in batching and scheduling pipeline.

3. **Ablation Study**: Perform systematic ablation of interference prediction component by comparing performance with and without predictor, and with various predictor architectures (different neural network sizes and input feature sets) to quantify contribution of interference awareness to overall performance.
