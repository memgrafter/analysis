# Lexi: Self-Supervised Learning of the UI Language

## Quick Facts
- arXiv ID: 2301.10165
- Source URL: https://arxiv.org/abs/2301.10165
- Reference count: 25
- Primary result: Lexi outperforms baseline models on four downstream UI understanding tasks by leveraging functional captions from instruction manuals

## Executive Summary
This paper introduces Lexi, a self-supervised model for learning visio-linguistic representations of UI screens and components. The key innovation is synthesizing functional captions from instructions co-located with UI images in how-to guides, which describe what UI elements do rather than what they look like. Lexi uses a custom UI detector, OCR integration, and four pre-training tasks to learn representations that outperform baselines on UI action entailment, instruction-based retrieval, grounding referring expressions, and UI entity recognition.

## Method Summary
Lexi is pre-trained on a dataset of 114k UI images paired with functional captions extracted from instruction manuals and how-to guides. The model uses a custom UI detector to identify UI elements, OCR to detect text, and a co-attentional transformer architecture to fuse visual and textual features. Pre-training tasks include masked language modeling, masked region modeling with KL divergence, image-text alignment, and part-of-speech tagging. The model is then fine-tuned on four downstream UI understanding tasks.

## Key Results
- Lexi outperforms baseline models on all four downstream tasks
- Functional captions improve context sensitivity handling compared to descriptive captions
- Detected text features significantly improve UI action entailment performance
- POS tagging pre-training task contributes to overall performance gains

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Functional captions solve context sensitivity by describing what UI elements do rather than what they look like.
- Mechanism: By extracting instructions that co-occur with UI images, the captions encode functional semantics that are invariant to visual variations of UI elements.
- Core assumption: UI elements with similar functions appear together in instruction steps, allowing their functional roles to be inferred from surrounding text.
- Evidence anchors: [abstract] "synthesize functional captions from instructions co-located with the image in the webpage"; [section 1] "Rather than describing the appearance of an image, these captions describe the functionality of one or multiple UI elements, in the context of other elements"

### Mechanism 2
- Claim: Detected text features improve alignment between visual UI regions and functional captions.
- Mechanism: Text recognized in UI screenshots (via OCR) is encoded as token embeddings and fused with visual region features, creating multimodal representations that better match caption semantics.
- Core assumption: UI screens contain text that is semantically important for understanding functionality, and this text can be reliably detected and encoded.
- Evidence anchors: [section 4] "each vi is augmented with textual features of the recognized text (computed as dot-product)"; [section 5.7] "The inclusion of the detected text is most beneficial to UI action entailment"

### Mechanism 3
- Claim: POS tagging pre-training task helps the model distinguish technical action verbs from general vocabulary.
- Mechanism: By training to identify noun and verb spans in functional captions, the model learns to attend to action-related words that are critical for UI understanding.
- Core assumption: Functional captions contain distinct verb-object patterns that differ from general language, and these patterns are learnable through POS supervision.
- Evidence anchors: [section 4] "we create a new pre-training task based on (noun-verb) POS tagging"; [section 5.7] "POS and MRM-KL tasks are important to achieve high performance (their absence causes a 2.6% drop in F1 scores)"

## Foundational Learning

- Concept: Masked Language Modeling (MLM)
  - Why needed here: Helps the model learn bidirectional context from captions by predicting masked words using both surrounding text and visual input
  - Quick check question: If you mask 15% of words in a caption like "Tap the Settings icon to open", can the model predict "Settings" using the visual input and context?

- Concept: Cross-modal attention
  - Why needed here: Allows the model to align visual regions with textual descriptions by computing attention between image features and caption tokens
  - Quick check question: When given an image of a settings icon and the caption "Tap the Settings icon", does the model's attention correctly focus on the icon region when processing "Settings"?

- Concept: Weak supervision for entity recognition
  - Why needed here: Functional captions contain technical terms that standard language models struggle with, so weak supervision helps the model learn domain-specific entity patterns
  - Quick check question: Can the model distinguish between "tap" as an action verb versus "tap" as a noun (like water tap) using weak POS supervision?

## Architecture Onboarding

- Component map: UI detector → visual encoder (ResNeXt-101) → text encoder (RoBERTa) → co-attentional transformer layers → task-specific heads
- Critical path: UI detector → visual feature extraction → text detection → feature fusion → co-attention → task output
- Design tradeoffs: Using a custom UI detector instead of Faster R-CNN trades annotation costs for potential detection accuracy, while adding OCR features trades complexity for better caption alignment
- Failure signatures: Poor UI detection → missing or incorrect visual features; OCR failures → lost text context; co-attention misalignment → wrong cross-modal associations
- First 3 experiments:
  1. Test UI detector on a small set of UI screenshots to verify it correctly identifies buttons, icons, and text regions
  2. Verify OCR integration by checking if detected text features improve caption alignment on a few examples
  3. Test co-attention mechanism by visualizing attention weights between image regions and caption tokens on sample pairs

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How would the performance of Lexi change if trained on a more balanced dataset of UI images across different applications and platforms, rather than being skewed towards popular applications?
- Basis in paper: [explicit] The paper mentions that web data used for pre-training is highly skewed towards popular applications, and less popular applications might have less or lower-quality documentation and images online.
- Why unresolved: The paper does not provide experimental results on the impact of dataset imbalance on Lexi's performance. It would be interesting to see how Lexi's performance changes when trained on a more balanced dataset.
- What evidence would resolve it: Experiments comparing Lexi's performance on tasks using a balanced dataset versus the current skewed dataset would provide insights into the impact of dataset imbalance on the model's performance.

### Open Question 2
- Question: Can Lexi be extended to handle instructions and UIs in languages other than English, and how would this affect its performance?
- Basis in paper: [explicit] The paper mentions that the method is currently trained and evaluated on English instructions and UIs that contain text in English, and future work should expand to different languages.
- Why unresolved: The paper does not explore the performance of Lexi on non-English instructions and UIs. It is unclear how the model would handle different languages and how this would impact its effectiveness.
- What evidence would resolve it: Experiments evaluating Lexi's performance on tasks using instructions and UIs in different languages would provide insights into its ability to handle multilingual data.

### Open Question 3
- Question: How would the performance of Lexi change if it were optimized to run on edge devices like mobile phones, considering potential privacy concerns?
- Basis in paper: [explicit] The paper mentions that the model is not optimized to run on edge devices like mobile phones, which may raise privacy concerns for certain scenarios.
- Why unresolved: The paper does not explore the performance of Lexi when optimized for edge devices or discuss potential privacy implications. It would be interesting to see how the model's performance and privacy considerations change when running on edge devices.
- What evidence would resolve it: Experiments evaluating Lexi's performance on edge devices and analyzing potential privacy implications would provide insights into the feasibility and effectiveness of running the model on such devices.

## Limitations

- Dataset Scale Uncertainty: The actual size of the UICaption dataset is uncertain due to duplicate filtering and preprocessing steps, affecting reproducibility and scalability assessments.
- Detector Generalization: The custom UI detector may not generalize well to real-world applications with different UI paradigms beyond tested domains.
- Caption Quality Dependency: The approach relies heavily on functional captions extracted from instructions, but lacks quantitative measures of caption quality or coverage.

## Confidence

## Next Checks

**Check 1: Functional Caption Quality Analysis**
Sample 100 random UI images from the UICaption dataset and their corresponding functional captions. For each, assess whether the caption actually describes the UI element's functionality rather than just its appearance. Calculate the percentage of high-quality functional descriptions. This directly validates Mechanism 1's core assumption.

**Check 2: UI Detector Generalization Test**
Take 50 UI screenshots from applications not in the training data (e.g., mobile banking apps, social media platforms, productivity tools). Run the UI detector and measure detection accuracy for key UI elements (buttons, icons, text fields). Compare against Faster R-CNN baseline to quantify the detector's real-world generalization.

**Check 3: Text Detection Impact Isolation**
Run a controlled ablation study where OCR is intentionally disabled for 100 sample images. Measure the performance drop specifically on UI action entailment task. This isolates the contribution of text detection features and validates Mechanism 2's impact.
