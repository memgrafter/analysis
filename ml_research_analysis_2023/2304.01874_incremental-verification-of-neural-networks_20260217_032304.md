# Incremental Verification of Neural Networks

## Quick Facts
- arXiv ID: 2304.01874
- Source URL: https://arxiv.org/abs/2304.01874
- Reference count: 30
- Key outcome: IVAN achieves 2.4x-43x speedup for incremental verification of updated DNNs

## Executive Summary
This paper introduces IVAN, the first general framework for incremental and complete verification of deep neural networks. IVAN addresses the inefficiency of existing complete verifiers that must be rerun from scratch when deployed DNNs are updated. The framework introduces a novel specification tree data structure that captures the trace of verification decisions, enabling reuse and refinement of proofs from the original network to accelerate verification of the updated network. The method is theoretically grounded with bounds on network perturbations for which incremental verification is effective, and achieves significant speedups on practical network updates like quantization.

## Method Summary
IVAN is built on top of branch-and-bound verifiers and uses a specification tree data structure to capture the trace of ReLU splitting decisions made during verification. The method combines three key techniques: reusing the final specification tree from the original verification, reordering branching decisions based on their observed effectiveness, and pruning ineffective branches to create a more compact tree. The framework can work with various branching strategies like ReLU splitting and input splitting, and is evaluated on MNIST, CIFAR10, and ACAS-XU classifiers with practical updates.

## Key Results
- IVAN achieves a geometric mean speedup of 2.4x over state-of-the-art baselines for image classifiers
- Speedups reach up to 43x on challenging cases for image classifiers
- IVAN achieves 3.8x speedup for ACAS-XU classifiers with network updates

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The specification tree captures the trace of ReLU splitting decisions, enabling reuse across similar network updates.
- Mechanism: IVAN records the branching decisions made during BaB verification of the original network into a tree structure. This tree is then reused as the starting point for verifying the updated network, avoiding redundant splits.
- Core assumption: Networks with similar behavior on the input region will generate structurally similar specification trees.
- Evidence anchors:
  - [abstract]: "IVAN computes a specification tree – a novel tree data structure representing the trace of BaB – from the execution of the complete verifier on the original network."
  - [section]: "IVAN uses a rooted binary tree data structure to store the trace of splitting decisions during BaB execution."
- Break condition: If the network perturbation exceeds the theoretical bounds or if the branching heuristic effectiveness changes significantly, the tree reuse may become ineffective.

### Mechanism 2
- Claim: Pruning ineffective splits from the specification tree creates a more compact and effective tree for the updated network.
- Mechanism: IVAN removes splits that had low improvement scores in the original verification and constructs a new tree using only the effective splits. This reduces the number of nodes and leaves the tree more focused.
- Core assumption: Ineffective splits in the original verification are likely to be ineffective in the updated verification.
- Evidence anchors:
  - [abstract]: "IVAN also improves the branching strategy in BaB for the updated network based on the observed effectiveness of branching choices when verifying the original DNN."
  - [section]: "Our augmented heuristic function 𝐻Δ will have a limited effect if we reuse 𝑇 𝑁 𝑎 0 = 𝑇 𝑁 𝑓 , since the existing tree branches may already be sufficient to prove the property."
- Break condition: If the network update changes the effective branching decisions, the pruned tree may miss important splits.

### Mechanism 3
- Claim: Reordering branching decisions based on observed effectiveness improves verification speed.
- Mechanism: IVAN modifies the original branching heuristic 𝐻 to 𝐻Δ by incorporating observed improvement scores from the original verification. This prioritizes splits that worked well previously.
- Core assumption: Branching decisions that were effective in the original verification will likely be effective in the updated verification.
- Evidence anchors:
  - [abstract]: "IVAN also improves the branching strategy in BaB for the updated network based on the observed effectiveness of branching choices when verifying the original DNN."
  - [section]: "𝐻Δ takes the weighted sum of original branching heuristic 𝐻 and observed effectiveness scores on 𝑁 denoted by 𝐻𝑜𝑏𝑠."
- Break condition: If the network update significantly changes the landscape of effective splits, the reordered heuristic may become suboptimal.

## Architecture Onboarding

- Component map: Specification tree -> Analyzer -> Branching heuristic -> Pruning operation -> Reordering algorithm
- Critical path:
  1. Verify the original network and generate the specification tree.
  2. Prune the specification tree to remove ineffective splits.
  3. Update the branching heuristic based on observed effectiveness.
  4. Verify the updated network using the pruned tree and updated heuristic.
- Design tradeoffs:
  - Tree reuse vs. starting from scratch: Reusing the tree can be faster but may be less effective if the network update is large.
  - Pruning vs. keeping all splits: Pruning can reduce tree size but may miss important splits if the update changes effective branching decisions.
  - Reordering vs. keeping the original heuristic: Reordering can improve effectiveness but may become suboptimal if the update changes the landscape of effective splits.
- Failure signatures:
  - If the network update is too large, the specification tree reuse may become ineffective.
  - If the branching heuristic effectiveness changes significantly, the reordered heuristic may become suboptimal.
  - If the pruning operation removes important splits, the verification may fail.
- First 3 experiments:
  1. Verify a small network with a simple update and compare the time taken with and without IVAN.
  2. Verify a network with a larger update and analyze the effectiveness of the pruned tree.

## Open Questions the Paper Calls Out

### Open Question 1
- Question: What is the precise relationship between the specification tree similarity and the amount of network perturbation for incremental verification effectiveness?
- Basis in paper: [explicit] The paper mentions that for DNN updates that perturb weights within a fixed bound, the final specification trees are identical, and provides theoretical bounds on network perturbations for which incremental verification is effective (Theorem 4).
- Why unresolved: The paper provides bounds for last-layer perturbations but leaves the derivation of perturbation bounds for full IVAN (arbitrary network perturbations) as future work, noting it requires theoretically modeling complex interactions between reuse and reorder techniques.
- What evidence would resolve it: A formal theorem characterizing the maximum allowable perturbation across all layers of the network while maintaining sufficient specification tree similarity for effective incremental verification.

### Open Question 2
- Question: How do different branching heuristics affect the performance of IVAN's incremental verification across various types of network perturbations?
- Basis in paper: [explicit] The paper mentions that IVAN can work with various common BaB branching strategies (input splitting, ReLU splitting) and different state-of-the-art branching heuristics, but doesn't provide comprehensive comparison of their effectiveness in incremental settings.
- Why unresolved: While the paper shows IVAN works with different branching strategies, it doesn't systematically compare how different branching heuristics (like the coefficients of zonotopes method vs. estimation based on coefficients) perform when combined with IVAN's incremental techniques across various perturbation types.
- What evidence would resolve it: A systematic evaluation comparing IVAN's performance with different branching heuristics (random selection, gradient-based, zonotope-based, etc.) across various perturbation magnitudes and network architectures.

### Open Question 3
- Question: What is the impact of hyperparameters α and θ on IVAN's performance across different network architectures and perturbation types?
- Basis in paper: [explicit] The paper mentions sensitivity analysis of hyperparameters α and θ (controlling the balance between original branching heuristic and observed effectiveness, and the threshold for deprioritizing splits) but provides limited empirical analysis.
- Why unresolved: The paper only shows sensitivity analysis for one specific network (FCN-MNIST with int16 quantization) and mentions that performance is less sensitive to hyperparameter changes when using the full IVAN algorithm, but doesn't explore how optimal hyperparameter values vary across different architectures, perturbation types, or property specifications.
- What evidence would resolve it: A comprehensive sensitivity analysis across multiple network architectures, perturbation magnitudes, and property types to identify whether optimal hyperparameter values are problem-dependent or can be automatically tuned.

## Limitations

- Limited to branch-and-bound verifiers: IVAN's effectiveness depends on the underlying BaB framework, which may not generalize to other verification approaches.
- Network perturbation bounds: Practical applicability depends on how closely real-world network updates adhere to theoretical bounds, with architectural changes potentially breaking assumptions.

## Confidence

- High confidence in the specification tree data structure and its ability to capture verification traces for reuse
- Medium confidence in the practical effectiveness of pruning and reordering operations
- Medium confidence in generalizability to diverse real-world scenarios

## Next Checks

1. Cross-architecture validation: Test IVAN on architectures significantly different from the evaluated ones (e.g., Transformers, recurrent networks) to assess generalizability.

2. Update type sensitivity: Systematically evaluate IVAN's performance across different update magnitudes and types, including architectural modifications, to map the boundaries of its effectiveness.

3. Verification property diversity: Test with properties beyond adversarial robustness (e.g., safety constraints, output bounds) to ensure the specification tree approach generalizes across different verification objectives.
