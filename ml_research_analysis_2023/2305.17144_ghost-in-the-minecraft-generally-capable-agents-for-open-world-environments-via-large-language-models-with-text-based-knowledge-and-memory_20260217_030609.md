# Ghost in the Minecraft: Generally Capable Agents for Open-World Environments via Large Language Models with Text-based Knowledge and Memory

## Quick Facts
- arXiv ID: 2305.17144
- Source URL: https://arxiv.org/abs/2305.17144
- Reference count: 40
- Single LLM agent achieves +47.5% improvement in success rate on ObtainDiamond task compared to previous methods

## Executive Summary
This paper presents GITM, a framework that integrates Large Language Models with text-based knowledge and memory to create Generally Capable Agents in Minecraft. The system uses hierarchical goal decomposition where LLM Decomposer breaks down complex goals into sub-goals, LLM Planner generates structured actions for each sub-goal, and LLM Interface executes these actions. The approach achieves remarkable results, obtaining all items in the Minecraft Overworld with 10,000x fewer environment interaction steps than previous RL-based methods.

## Method Summary
The framework implements hierarchical goal decomposition using three LLM components: Decomposer, Planner, and Interface. The LLM Decomposer recursively breaks down goals into prerequisite sub-goals using text-based knowledge from the Minecraft Wiki. LLM Planner generates structured action sequences for each sub-goal, recording successful action lists into text-based memory for future reuse. LLM Interface executes structured actions through hand-written scripts that map to environment interactions. The system is evaluated on the ObtainDiamond task and collecting all Overworld items in Minecraft.

## Key Results
- Achieves +47.5% improvement in success rate on ObtainDiamond task compared to previous methods
- First method to successfully obtain all items in the Minecraft Overworld technology tree
- Requires 10,000x fewer environment interaction steps than previous RL-based methods

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Hierarchical goal decomposition via LLM Decomposer dramatically reduces search space complexity compared to flat RL approaches.
- Mechanism: LLM Decomposer recursively breaks down complex goals like "ObtainDiamond" into prerequisite sub-goals (craft iron pickaxe, mine iron ore, craft furnace, smelt iron ingot, mine diamond ore), each solvable independently.
- Core assumption: LLMs can accurately parse Minecraft crafting recipes and world knowledge from text to generate correct sub-goal trees.
- Evidence anchors: Abstract mentions LLM Decomposer decomposes goals according to text-based knowledge collected from the Internet. Section 3.1 defines goal format as (Object, Count, Material, Tool, Info).
- Break condition: If text-based knowledge contains errors or LLM misinterprets recipes, sub-goal tree will be invalid, leading to failed plans.

### Mechanism 2
- Claim: Structured actions provide abstraction layer that decouples high-level planning from low-level control, enabling efficient execution and easy debugging.
- Mechanism: LLM Planner generates sequences of structured actions (e.g., mine(diamond_ore, iron_pickaxe), craft(iron_pickaxe, {planks:3, stick:2}, crafting_table)) instead of raw keystrokes, bridging LLM symbolic reasoning with environment control.
- Core assumption: Structured actions are sufficiently expressive to cover all necessary interactions in Minecraft.
- Evidence anchors: Abstract mentions structured actions and leveraging LLMs to generate action plans. Section 3.2 describes structured actions with well-defined functions and clear semantics.
- Break condition: If environment API or structured actions implementation has bugs, or if some tasks require actions not in the structured set, execution will fail.

### Mechanism 3
- Claim: Text-based memory stores successful action sequences for common sub-goals, enabling rapid reuse and cumulative learning without parameter updates.
- Mechanism: After successfully completing a sub-goal, executed action sequence is stored in memory. When same sub-goal is encountered again, LLM retrieves and adapts known solution instead of planning from scratch. Memory summarization consolidates multiple solutions into canonical plan.
- Core assumption: Many sub-goals recur frequently enough that memory lookup provides significant speedup.
- Evidence anchors: Abstract mentions LLM Planner records and summarizes successful action lists into text-based memory to enhance future planning. Section 3.2 describes text-based memory for maintaining common reference plans.
- Break condition: If sub-goals are too diverse or memory lookup introduces significant overhead, benefits may be outweighed by costs.

## Foundational Learning

- Concept: Recursive decomposition of goals into sub-goals based on prerequisite relationships
  - Why needed here: Minecraft tasks have inherent prerequisite chains (can't craft iron pickaxe without iron ingots, can't smelt without furnace, etc.). Flat planning fails on such long-horizon tasks.
  - Quick check question: If the goal is "obtain diamond", what are the immediate sub-goals before mining diamond ore?

- Concept: Abstract action interfaces vs. raw environment control
  - Why needed here: LLMs excel at symbolic reasoning but struggle with low-level control. Structured actions bridge this gap.
  - Quick check question: Why is "mine(diamond_ore, iron_pickaxe)" easier for an LLM to plan than a sequence of mouse movements and keystrokes?

- Concept: Text-based knowledge retrieval for world understanding
  - Why needed here: Minecraft has complex crafting recipes, resource distributions, and biome-specific items. LLMs need this knowledge to plan correctly.
  - Quick check question: What information would the LLM need to plan for obtaining diamonds efficiently?

## Architecture Onboarding

- Component map: Goal → LLM Decomposer → LLM Planner → LLM Interface → Environment → Feedback → LLM Planner → ... → Success
- Critical path: The loop continues until all sub-goals are completed, with feedback flowing from environment back to Planner.
- Design tradeoffs:
  - Structured actions vs. learned low-level policies: Structured actions provide interpretability and debuggability but may miss optimal low-level strategies.
  - Text memory vs. learned policy parameters: Memory is explicit and modifiable but may not generalize as well as learned representations.
  - LLM-based planning vs. RL: LLMs can leverage external knowledge and plan symbolically, but may struggle with noisy or partial observations.
- Failure signatures:
  - Decomposer fails: Invalid sub-goal tree, missing prerequisites, or infinite recursion
  - Planner fails: Invalid action sequences, failure to adapt to feedback, or memory retrieval errors
  - Interface fails: API errors, incorrect action mapping, or environment observation parsing issues
  - Knowledge/memory issues: Outdated/incorrect knowledge, memory retrieval misses, or summarization errors
- First 3 experiments:
  1. Single sub-goal test: Give LLM Planner a simple sub-goal (e.g., "obtain 10 wooden planks") and verify it generates correct action sequence using structured actions.
  2. Memory test: Complete a sub-goal, store in memory, then retry the same sub-goal and verify planner retrieves and uses the memory solution.
  3. End-to-end simple goal: Test the full pipeline with a simple multi-step goal (e.g., "craft stone pickaxe") to verify all components work together.

## Open Questions the Paper Calls Out
The paper does not explicitly call out open questions, but based on the framework's capabilities and limitations, several important questions arise regarding multi-agent collaboration, action set optimization, and cross-domain scalability.

## Limitations
- Heavy reliance on the accuracy and completeness of external text-based knowledge sources, which could introduce cascading errors
- Unclear generalization to entirely novel tasks not covered in the knowledge base or memory
- Potential scalability issues with text-based memory as the number of stored solutions grows

## Confidence
- High Confidence: Framework architecture is logically sound and experimental results are clearly presented with substantial improvements over baselines
- Medium Confidence: Mechanism explanations are reasonable but some assumptions lack empirical validation within the paper itself
- Low Confidence: Claims about handling "any long-horizon task" in open-world environments are not substantiated beyond Minecraft domain

## Next Checks
1. Systematically introduce errors or omissions into the text knowledge base and measure impact on agent's success rate to quantify robustness to knowledge quality issues
2. Design tasks requiring combining knowledge in ways not explicitly covered in training knowledge base to evaluate LLM's reasoning and adaptation capabilities
3. Implement larger-scale version with significantly expanded memory to measure memory retrieval times and success rates as stored solutions increase, identifying potential bottlenecks
