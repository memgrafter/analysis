# Training Deep Surrogate Models with Large Scale Online Learning

## Quick Facts
- arXiv ID: 2306.16133
- Source URL: https://arxiv.org/abs/2306.16133
- Reference count: 37
- Key outcome: Online training framework improves model generalization by 68% for FCNN, 16% for FNO, and 7% for Message Passing PDE Solver by eliminating I/O bottlenecks and enabling training on larger, more diverse datasets.

## Executive Summary
This paper introduces an open-source online training framework for deep surrogate models that trains models simultaneously on data streams generated from solver instances executed in parallel. The framework implements several levels of parallelism focused on simultaneously generating numerical simulations and training deep neural networks. This approach suppresses the I/O and storage bottleneck associated with disk-loaded datasets, and opens the way to training on significantly larger datasets. Experiments compare the offline and online training of four surrogate models, including state-of-the-art architectures.

## Method Summary
The framework implements parallel data generation and model training by streaming solver data directly to the training server, bypassing disk storage. The server manages a memory buffer with reservoir sampling to ensure batch diversity and mitigate bias. Training occurs in a data-parallel manner across multiple GPUs, while solver instances run in parallel on multiple nodes. This eliminates I/O bottlenecks and allows training on datasets limited only by computational resources rather than storage capacity.

## Key Results
- Online training improves FCNN generalization by 68% compared to offline training
- FNO performance increases by 16% with online training approach
- Message Passing PDE Solver accuracy improves by 7% through online training
- Framework enables training on datasets up to 328 GB without storage bottlenecks

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The online framework enables training on significantly larger and more diverse datasets by eliminating the I/O and storage bottleneck of disk-loaded datasets.
- Mechanism: By streaming data directly from parallel solver instances to the training server, the framework avoids the need to store intermediate data on disk, allowing the training dataset to be limited only by available computational resources.
- Core assumption: The solver instances can generate data fast enough to keep the training pipeline fed without introducing significant latency.
- Evidence anchors:
  - [abstract] "This approach suppresses the I/O and storage bottleneck associated with disk-loaded datasets, and opens the way to training on significantly larger datasets."
  - [section] "The I/Os and storage are drastically reduced. The training dataset becomes only limited by the amount of computing resources available."
  - [corpus] Weak evidence; related works discuss large-scale training but do not directly address I/O elimination as a core mechanism.
- Break condition: If solver data generation is slower than training consumption, the pipeline will stall, and the framework's advantage diminishes.

### Mechanism 2
- Claim: The framework mitigates bias in online training by using Monte Carlo sampling and a memory buffer with reservoir sampling.
- Mechanism: Parameters for simulations are sampled using Monte Carlo methods, and the memory buffer stores a subset of received data. Batches are drawn randomly from this buffer, ensuring each data point is seen only once, reducing intra-simulation, inter-simulation, and memory biases.
- Core assumption: The memory buffer size and sampling strategy are sufficient to maintain batch diversity without introducing new biases.
- Evidence anchors:
  - [section] "The management of the memory buffer is key to counteract these biases... Different management policies are available ranging from simple queues to reservoir sampling... The one used in the experiments... allows writing incoming data on free slots only, while each (random) read suppresses the corresponding data."
  - [section] "Classical Monte Carlo sampling is used throughout the paper."
  - [corpus] Weak evidence; related works discuss active learning but not specifically the memory buffer strategy for bias mitigation.
- Break condition: If the memory buffer is too small or sampling is not representative, batches may become biased, leading to poor model generalization.

### Mechanism 3
- Claim: The framework's scalability is achieved through multiple levels of parallelism, combining data parallelism in training and task parallelism in data generation.
- Mechanism: The server trains the model in a data-parallel manner across multiple GPUs, while clients run solver instances in parallel on multiple nodes, cores, or GPUs. This parallelism allows for efficient utilization of HPC resources.
- Core assumption: The communication overhead between clients and server does not outweigh the benefits of parallelism.
- Evidence anchors:
  - [section] "The server can be executed on several GPUs... Each GPU is associated with its own memory buffer... When a new client starts a simulation, it establishes connections with each of the server processes."
  - [section] "The framework implements several levels of parallelism focused on simultaneously generating numerical simulations and training deep neural networks."
  - [corpus] Weak evidence; related works discuss distributed training but not specifically the combination of data and task parallelism for online training.
- Break condition: If communication latency or bandwidth becomes a bottleneck, the scalability advantage of the framework is lost.

## Architecture Onboarding

- Component map: Clients -> Server (with Memory Buffer) -> Model Training
- Critical path: Data generation → Streaming to server → Buffer management → Batch assembly → Model training
- Design tradeoffs:
  - Memory buffer size vs. batch diversity: Larger buffers allow more diverse batches but consume more memory
  - Number of clients vs. server capacity: More clients increase data generation speed but may overwhelm the server
  - Data parallelism vs. model complexity: More GPUs speed up training but may not benefit simpler models
- Failure signatures:
  - Pipeline stalls: Solver instances generate data slower than the server consumes it
  - Degraded model performance: Memory buffer is too small or sampling is biased, leading to unrepresentative batches
  - Communication errors: Network issues between clients and server cause data loss or delays
- First 3 experiments:
  1. Train a simple fully connected network on the heat equation with both offline and online modes to compare performance and bias
  2. Test the Lorenz system with streaming and sampling + buffer strategies to observe the impact on batch statistics and model generalization
  3. Scale up to Navier-Stokes with FNO and U-Net architectures, comparing offline and online training on larger datasets
