# Generalized Planning as Heuristic Search: A new planning search-space that leverages pointers over objects

## Quick Facts
- arXiv ID: 2301.11087
- Source URL: https://arxiv.org/abs/2301.11087
- Reference count: 40
- Key outcome: New heuristic search approach for generalized planning using pointer-based representation that solves challenging GP problems intractable for compilation-based methods

## Executive Summary
This paper introduces a novel approach to generalized planning that overcomes the scalability limitations of previous methods by using a pointer-based representation inspired by the Random-Access Machine. The approach represents GP problems and solutions independently of the number and size of classical planning instances, enabling computation of GP solutions that generalize to large sets of instances with many objects and large domains. The method defines a new GP search space, evaluation functions, and a Best-First Generalized Planning (BFGP) algorithm that significantly outperforms classical planning compilation approaches.

## Method Summary
The BFGP algorithm extends classical planning instances with a RAM machine of |Z| pointers and searches through partially specified planning programs using nine evaluation/heuristic functions. The search space is encoded using bit-vectors, and node expansion programs the maximum undefined line reached after execution. The algorithm uses a priority queue sorted by evaluation function values to guide the search, terminating when a solution is found or the search space is exhausted. The method is validated on nine planning domains, showing significant improvements over compilation-based approaches.

## Key Results
- BFGP algorithm successfully solves challenging GP problems with large instances that are intractable for compilation-based methods
- Solutions generalize to much larger sets of instances than used for synthesis
- The approach bridges automated planning and programming by computing algorithmic GP solutions represented as structured programs
- Experimental results show significant improvements in CPU time, memory usage, and number of expanded/evaluated nodes

## Why This Works (Mechanism)

### Mechanism 1
- **Claim**: Pointer-based representation allows generalization to instances with different numbers of objects and large domains.
- **Mechanism**: By using pointers indexed over objects instead of explicit object names, the representation abstracts away the specific number of objects and their identities, allowing the same algorithm to work on any instance size.
- **Core assumption**: The set of pointers and RAM instructions is sufficient to encode all necessary operations for the domain.
- **Evidence anchors**:

  - [section] "The key insight is that by using pointers indexed over objects, we can represent actions and states in a way that is independent of the specific number of objects or their identities. This allows the same algorithm to work on any instance size."
  - [corpus] Weak evidence; corpus neighbors don't directly discuss pointer-based representations.
- **Break condition**: If the domain requires operations that cannot be expressed with the limited set of pointer-based actions and comparisons.

### Mechanism 2
- **Claim**: Best-first search in the pointer-based solution space is tractable due to the reduced search space size.
- **Mechanism**: By limiting goto instructions to only condition on a small set of features (the four joint values of the FLAGS), the number of possible programs is greatly reduced compared to conditioning on arbitrary state variables.
- **Core assumption**: The four features in the FLAGS are expressive enough to guide the search effectively.
- **Evidence anchors**:
  - [abstract] "Second, the paper defines a set of evaluation and heuristic functions for guiding a combinatorial search in our new GP solution space."
  - [section] "Limiting the conditions of goto instructions to any of the four features in L greatly reduces the number of planning programs with n lines, specially when state variables have large domains."
  - [corpus] Weak evidence; corpus neighbors don't directly discuss the search space reduction.
- **Break condition**: If the four features are not expressive enough to distinguish between different states needed for the algorithm.

### Mechanism 3
- **Claim**: The evaluation functions provide an effective heuristic for guiding the search towards valid solutions.
- **Mechanism**: The evaluation functions combine structural properties of the program (e.g., number of goto instructions) with empirical performance on the given instances (e.g., how many goals are still unsatisfied) to guide the search.
- **Core assumption**: The evaluation functions are well-calibrated to distinguish between programs that are close to a solution and those that are not.
- **Evidence anchors**:
  - [abstract] "The computation of these evaluation and heuristic functions does not require grounding states or actions in advance."
  - [section] "Performance-based functions accumulate a set of T costs (one for each classical planning instance in the GP problem) that could actually be expressed as a combination of different aggregation functions."
  - [corpus] Weak evidence; corpus neighbors don't directly discuss the evaluation functions.
- **Break condition**: If the evaluation functions do not provide a good estimate of the distance to a solution, the search may not converge efficiently.

## Architecture Onboarding

- **Component map**: 
  - Classical planning instances -> Pointer-based representation module -> Best-first search module -> Evaluation functions module -> Solution program

- **Critical path**: 
  1. Parse the classical planning instances and build the pointer-based representation.
  2. Initialize the best-first search with the empty program.
  3. At each iteration, expand the best node by programming the maximum undefined line.
  4. Evaluate the new programs using the evaluation functions.
  5. Insert the evaluated programs into the priority queue.
  6. Repeat until a solution is found or the search space is exhausted.

- **Design tradeoffs**:
  - The choice of pointer-based representation vs. explicit object names trades off expressiveness for scalability.
  - The choice of best-first search vs. other search algorithms trades off completeness for efficiency.
  - The choice of evaluation functions trades off informativeness for computational cost.

- **Failure signatures**:
  - If the search fails to find a solution, it may be due to the search space being too large or the evaluation functions not being informative enough.
  - If the search finds a solution that does not generalize, it may be due to the pointer-based representation not being expressive enough.

- **First 3 experiments**:
  1. Run the algorithm on a simple domain like sorting a vector of size 2-3 to verify basic functionality.
  2. Increase the instance size to 4-5 to test scalability.
  3. Test on a more complex domain like blocksworld to verify generalization to different object types.

## Open Questions the Paper Calls Out

### Open Question 1
- Question: Can the BFGP algorithm be extended to handle real-valued state variables by introducing a notion of precision for comparisons?
- Basis in paper: [explicit] The paper mentions that "we are exploring the extension of our approach to GP problems that include real state variables" and suggests "introducing the notion of precision for the comparison of real variables, and redefining accordingly our mechanism for the update of the FLAGs registers."
- Why unresolved: This is mentioned as a future research direction, indicating it has not yet been implemented or tested.
- What evidence would resolve it: Implementation and empirical evaluation of the BFGP algorithm on GP problems with real-valued state variables, demonstrating successful generalization and solution quality.

### Open Question 2
- Question: How can the cost-to-go heuristics in BFGP be improved to be more informed, potentially by incorporating sub-goal discovery or leveraging modern planning heuristics?
- Basis in paper: [explicit] The paper states that "Our cost-to-go heuristics are still less informed than the current heuristics for classical planning" and suggests that "better estimates may be obtained by building on top of the powerful ideas of modern planning heuristics" and considering sub-goals.
- Why unresolved: The paper identifies this as a limitation and suggests it as a direction for improvement, but does not provide a concrete solution.
- What evidence would resolve it: Development and empirical evaluation of enhanced cost-to-go heuristics for BFGP that outperform the current heuristics in terms of solution quality and/or computational efficiency.

### Open Question 3
- Question: Can the performance of the BFGP algorithm be improved by incorporating advanced search techniques such as delayed duplicate detection, non-chronological backtracking, or parallelization?
- Basis in paper: [explicit] The paper mentions several advanced search techniques that could be applied to improve BFGP, including "delayed duplicate detection," "non-chronological backtracking," "limited discrepancy search," and "parallelization of search in solution spaces with different bounds."
- Why unresolved: These are suggested as potential improvements, but the paper does not provide any implementation or empirical evaluation of these techniques.
- What evidence would resolve it: Implementation and empirical evaluation of BFGP with the suggested advanced search techniques, demonstrating improved performance in terms of solution quality, computational efficiency, or scalability.

## Limitations

- The approach's effectiveness on domains requiring complex conditional logic beyond the four FLAG features remains untested
- Experimental validation doesn't include domains where GP has proven particularly challenging, such as domains with complex relational structures
- The claim that this bridges automated planning and programming is more conceptual than demonstrated through experiments

## Confidence

- **High confidence**: The mechanism of pointer-based representation reducing search space complexity
- **Medium confidence**: The claim that this approach can handle problems with "large domains (e.g. integers)" - the experimental validation focuses on bounded integer domains
- **Medium confidence**: The scalability claims, as the comparison baseline (classical planning compilation) is known to have exponential scaling limitations

## Next Checks

1. Test the algorithm on domains requiring complex conditional branching beyond the four FLAG features to verify the expressiveness limits

3. Measure actual memory usage and compare against the claimed scalability improvements, particularly for domains with larger numbers of objects and state variables
