# Score: A Rule Engine for the Scone Knowledge Base System

## Executive Summary
This paper presents Score, a rule engine designed to extend the Scone knowledge base system with simple inference capabilities. The engine implements two types of production rules - if-added rules triggered when new knowledge enters the system, and if-needed rules activated when requested values are missing. Built as a lightweight reasoning layer rather than a complex planner, Score leverages Scone's existing marker-passing infrastructure to efficiently check and fire rules during knowledge base operations.

## Method Summary
The rule engine employs a search-based algorithm that integrates with Scone's marker-passing operations to efficiently evaluate when rules should fire. If-added rules are processed during knowledge insertion operations, while if-needed rules execute during query resolution when values are absent. The implementation uses Common Lisp as the implementation language, with rules defined through a specific syntax that specifies conditions and consequences. The engine maintains rule-checking efficiency by piggybacking on Scone's existing search mechanisms rather than implementing separate inference engines.

## Key Results
- Introduces two complementary rule types (if-added and if-needed) that handle simple inference tasks
- Implements efficient rule checking through integration with Scone's marker-passing operations
- Provides a Common Lisp implementation with clear syntax for defining and using rules
- Demonstrates practical examples of rule-based reasoning within the Scone knowledge base system

## Why This Works (Mechanism)
The rule engine works by leveraging Scone's existing marker-passing infrastructure to efficiently determine when rules should fire. During knowledge insertion, if-added rules are checked using Scone's search capabilities to identify relevant conditions. When queries cannot find values, if-needed rules are activated through the same search mechanism. This integration allows the rule engine to piggyback on Scone's efficient graph traversal operations rather than implementing separate inference engines, maintaining performance while adding reasoning capabilities.

## Foundational Learning
- **Production rules**: Conditional logic statements that trigger actions when specific conditions are met; needed to implement rule-based reasoning in the knowledge base
- **If-added vs if-needed rules**: Two complementary rule types that handle different inference scenarios; needed to cover both proactive (knowledge addition) and reactive (missing values) reasoning cases
- **Marker-passing operations**: Scone's graph traversal mechanism for efficient knowledge retrieval; needed to integrate rule checking with existing search infrastructure
- **Knowledge base augmentation**: Extending a knowledge base with inference capabilities without replacing core functionality; needed to maintain Scone's existing features while adding new reasoning
- **Rule firing**: The process of executing a rule's consequence when its conditions are satisfied; needed to perform the actual reasoning actions

## Architecture Onboarding

**Component Map**: User -> Rule Definition -> Rule Engine -> Scone Knowledge Base -> Marker-Passing System

**Critical Path**: Rule definition (syntax specification) → Rule engine processing (search-based checking) → Scone integration (marker-passing utilization) → Knowledge base update/query response

**Design Tradeoffs**: Simplicity vs. expressiveness (simple rules vs. complex planning), integration depth vs. independence (tight Scone coupling vs. standalone operation), efficiency vs. completeness (fast rule checking vs. comprehensive inference)

**Failure Signatures**: Rules not firing when conditions are met (integration issues), excessive computation during rule checking (inefficient search), incorrect rule execution (syntax or logic errors), conflicts between multiple applicable rules (lack of conflict resolution)

**First Experiments**:
1. Define and test simple if-added rules that modify knowledge base properties when new entities are added
2. Create if-needed rules that generate default values for missing attributes during queries
3. Test rule interactions by defining multiple rules that might fire for the same knowledge base state
