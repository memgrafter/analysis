# Resource Efficient Neural Networks Using Hessian Based Pruning

## Quick Facts
- arXiv ID: 2306.07030
- Source URL: https://arxiv.org/abs/2306.07030
- Reference count: 40
- One-line primary result: EHAP achieves 17%–44% speedup and ~40% memory reduction in Hessian trace computation while maintaining pruning accuracy

## Executive Summary
This work addresses the computational inefficiency of Hessian-based neural network pruning, particularly the high time and memory cost of calculating the Hessian trace for large models. The authors propose Efficient Hessian Aware Pruning (EHAP), which modifies the standard approach by using FP16 precision instead of FP32 when estimating the Hessian trace via Hutchinson's method. This is achieved by leveraging PyTorch's Automatic Mixed Precision to perform backpropagation in FP16, reducing computation time and GPU memory usage. Experiments on ResNet-32, ResNet-56, and WideResNet-28-8 trained on CIFAR-10 and CIFAR-100 datasets show that EHAP achieves speedups of 17% to 44% and reduces GPU memory usage by approximately 40%, while maintaining equivalent pruning accuracy. The method is further combined with INT8 quantization-aware training (QAT) to achieve additional model compression without significant accuracy loss.

## Method Summary
EHAP accelerates Hessian-based pruning by computing the Hessian trace in FP16 precision using PyTorch's Automatic Mixed Precision (AMP) during Hutchinson's method. The approach uses gradient scaling (factor of 2^8) to prevent underflow/overflow in FP16 second-order backpropagation, maintaining the relative ranking of channel sensitivities needed for pruning decisions. After pruning, models are fine-tuned and then compressed further using INT8 QAT with symmetric weights and asymmetric activations. The method is evaluated on CIFAR-10/100 with ResNet and WideResNet architectures, demonstrating significant computational savings while preserving accuracy.

## Key Results
- 17%–44% speedup in Hessian trace computation compared to FP32 baseline
- ~40% reduction in GPU memory usage during pruning
- Equivalent pruning accuracy maintained between FP16 and FP32 implementations
- Additional compression achieved through INT8 QAT without significant accuracy loss

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** FP16 precision for second-order gradient backpropagation preserves relative Hessian trace values sufficient for pruning decisions.
- **Mechanism:** By scaling gradients with a factor of 2^8 and using PyTorch's Automatic Mixed Precision (AMP), the relative ordering of Hessian trace values across channels is maintained while reducing computation time and memory usage.
- **Core assumption:** The absolute value of the Hessian trace is not critical; only the relative ranking of channel sensitivities matters for pruning.
- **Evidence anchors:**
  - [abstract] "we also present the results of pruning using both FP16 and FP32 Hessian trace calculation and show that there are no noticeable accuracy differences between the two."
  - [section] "we find that the optimal scaling factor to use for second-order backpropagation in our experiments is 2^8."
- **Break condition:** If pruning decisions become inconsistent or accuracy drops significantly when switching from FP32 to FP16, the relative sensitivity ranking would be corrupted.

### Mechanism 2
- **Claim:** Static gradient scaling (2^8) prevents underflow/overflow in FP16 second-order backpropagation.
- **Mechanism:** During Hutchinson's method, the gradient scaler multiplies gradients before FP16 backpropagation and unscale afterward, avoiding NaNs or zeros in the second-order computation.
- **Core assumption:** Second-order gradients are much smaller in magnitude than first-order, requiring scaling to fit in FP16 range.
- **Evidence anchors:**
  - [section] "Without scaling, values which are too small will flush to zero (underflow) and those which are too big will turn into NaNs (overflow)."
  - [section] "we adopt AMP's gradient scaler to scale gradients during the backpropagation process."
- **Break condition:** If scaling factor is too small, underflow occurs; if too large, overflow occurs, both breaking the trace approximation.

### Mechanism 3
- **Claim:** Using relative Hessian trace instead of absolute trace enables precision reduction without sacrificing pruning quality.
- **Mechanism:** Since pruning decisions are based on relative sensitivities, the approximation quality of the Hessian trace is preserved even when computed in FP16.
- **Core assumption:** The pruning criterion is based on comparing sensitivity metrics across channels, not on their absolute values.
- **Evidence anchors:**
  - [abstract] "we show that there are no noticeable accuracy differences between the two."
  - [section] "Thus, we do not need a high level of precision for Hutchinson's Method to achieve good results."
- **Break condition:** If the pruning algorithm begins selecting wrong channels due to loss of precision in the relative ranking, accuracy would degrade.

## Foundational Learning

- **Concept:** Hutchinson's Method for Hessian trace estimation
  - **Why needed here:** It provides a stochastic, memory-efficient way to approximate the trace without forming the full Hessian matrix, which is essential for large models.
  - **Quick check question:** What is the expected value of v^T H v when v is drawn from a Rademacher distribution?

- **Concept:** Automatic Mixed Precision (AMP) in PyTorch
  - **Why needed here:** AMP allows selective use of FP16 for computationally intensive operations while keeping critical parts in FP32, reducing memory and time without accuracy loss.
  - **Quick check question:** How does AMP's gradient scaler prevent underflow in FP16 operations?

- **Concept:** Second-order pruning sensitivity metric
  - **Why needed here:** It measures the expected loss change from pruning each channel, enabling more informed pruning than magnitude-based methods.
  - **Quick check question:** How does the trace of the Hessian block H_{p,p} relate to the sensitivity of pruning p-channels?

## Architecture Onboarding

- **Component map:** Pre-trained model → Hutchinson's Method (FP32 baseline) → Pruning → Fine-tuning → Quantization-aware training → INT8 model
- **Critical path:** 1. Compute gradients on batch; 2. For each Hutchinson iteration: draw random Rademacher vector, compute scaled Hessian-vector product in FP16, accumulate v^T Hv; 3. Average over iterations → relative Hessian trace; 4. Rank channels by sensitivity → prune lowest
- **Design tradeoffs:** FP16 reduces memory by ~40% and speeds up by 17-44% but requires careful scaling; larger Hessian batch size possible with memory savings, improving trace accuracy; INT8 quantization after pruning further compresses model but adds fine-tuning overhead
- **Failure signatures:** NaNs or infs in second-order gradients → scaling factor too small/large; sudden accuracy drop after pruning → loss of sensitivity ranking precision; memory errors during Hutchinson's Method → batch size too large for device
- **First 3 experiments:** 1. Run HAP and EHAP on a small ResNet-32 with CIFAR-10; compare timing and accuracy; 2. Vary gradient scaling factor (2^6, 2^8, 2^10) in EHAP; observe stability and accuracy; 3. Increase Hessian batch size in EHAP; measure trace approximation variance and pruning stability

## Limitations
- Assumes relative Hessian trace values are preserved in FP16, which lacks theoretical guarantees for all architectures
- Gradient scaling factor of 2^8 was empirically determined and may not be optimal for other models
- INT8 quantization implementation details are not fully specified, making exact reproduction challenging
