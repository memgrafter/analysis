# MultiTASC: A Multi-Tenancy-Aware Scheduler for Cascaded DNN Inference at the Consumer Edge

## Quick Facts
- arXiv ID: 2306.12830
- Source URL: https://arxiv.org/abs/2306.12830
- Reference count: 21
- Primary result: MultiTASC improves latency SLO satisfaction by 20-25 percentage points over static threshold methods in multi-device cascade inference

## Executive Summary
This paper addresses the challenge of deploying cascade inference systems in multi-device environments where multiple heterogeneous devices share a common server-side model. The proposed MultiTASC scheduler dynamically adjusts forwarding thresholds to balance accuracy, throughput, and latency under varying load conditions. By leveraging a capacity metric, fractional updates, and device-aware prioritization, it maintains high SLO satisfaction rates and throughput even as the number of devices scales to over 40. The scheduler significantly outperforms static baseline approaches in both homogeneous and heterogeneous device scenarios.

## Method Summary
MultiTASC implements a dynamic threshold adaptation mechanism for cascade inference systems where lightweight models run on edge devices and heavier models run on a shared server. The scheduler monitors request queue size and arrival rate to calculate the system's capacity using a knapsack-style algorithm that considers batch sizes and their corresponding latencies. Thresholds are updated using fractional updates (only on a subset of devices per iteration) and prioritized based on device tier, with high-end devices prioritized for threshold decreases and low-end devices prioritized for increases. The system uses the Best-versus-Second-Best (BvSB) metric for forwarding decisions and dynamic batching to optimize server throughput.

## Key Results
- MultiTASC improves latency SLO satisfaction by 20-25 percentage points over static threshold methods
- Maintains high accuracy (within 2 percentage points of static baseline) while improving throughput
- Effectively scales to over 40 devices while maintaining performance in heterogeneous environments

## Why This Works (Mechanism)

### Mechanism 1
- Claim: MultiTASC maintains low latency by dynamically adjusting forwarding thresholds to control server request rate.
- Mechanism: The scheduler uses a Capacity metric to estimate the maximum number of samples the server can process within the SLO, then adjusts forwarding thresholds on each device accordingly using fractional updates.
- Core assumption: The server's capacity can be accurately estimated using a knapsack-like calculation of batch sizes and their latencies.
- Evidence anchors:
  - [abstract] "MultiTASC improves the latency service-level objective (SLO) satisfaction rate by 20-25 percentage points (pp) over state-of-the-art cascade methods"
  - [section] "To calculate the amount of samples that can be processed by the server within a given latency constraint, we introduce the Capacity metric"
  - [corpus] Weak evidence - no direct citations found about Capacity metric in related works
- Break condition: If the server's processing characteristics change (e.g., due to thermal throttling), the precomputed batch latency table becomes invalid and Capacity estimates become inaccurate.

### Mechanism 2
- Claim: Device heterogeneity-aware prioritization improves both accuracy and throughput by selectively updating thresholds based on device tier.
- Mechanism: When decreasing thresholds, MultiTASC prioritizes high-end and mid-tier devices (which maintain higher accuracy even with low thresholds); when increasing thresholds, it prioritizes low-end devices (which benefit most from higher thresholds).
- Core assumption: Different device tiers have different accuracy-latency trade-offs that can be exploited for system optimization.
- Evidence anchors:
  - [abstract] "our scheduler improves the latency service-level objective (SLO) satisfaction rate by 20-25 percentage points (pp) over state-of-the-art cascade methods in highly heterogeneous setups"
  - [section] "Our heterogeneity-aware prioritization strategy updates the threshold values using Eq. (4), but expands the pipeline by selecting which type of devices receive the update"
  - [corpus] No direct evidence found in corpus about device-tier-aware threshold updates
- Break condition: If the device tier classifications become inaccurate (e.g., due to dynamic performance changes), the prioritization strategy may make suboptimal decisions.

### Mechanism 3
- Claim: Fractional update prevents sudden system oscillations by updating thresholds on only a subset of devices per iteration.
- Mechanism: MultiTASC updates thresholds on only P% of devices (where P is a parameter) during each scheduler invocation, allowing previous changes to propagate through the system before making further adjustments.
- Core assumption: Gradual, distributed threshold updates lead to more stable system behavior than simultaneous updates across all devices.
- Evidence anchors:
  - [abstract] "By explicitly considering device heterogeneity, our scheduler improves the latency service-level objective (SLO) satisfaction rate by 20-25 percentage points (pp)"
  - [section] "Changing the thresholds of all devices at once could lead to unwanted, sudden oscillations of the system. To achieve a smoother operation of the system and give enough time for each adaptation step to affect the execution, MultiTASC introduces the fractional update technique"
  - [corpus] No direct evidence found in corpus about fractional update techniques
- Break condition: If the scheduler invocation rate is too slow relative to request arrival rate changes, the system may not adapt quickly enough to maintain SLO compliance.

## Architecture Onboarding

- Component map: Devices -> Forwarding Decision Function -> Request Queue -> Server -> MultiTASC Scheduler
- Critical path: Sample → Device inference → Forwarding decision → Request queue → Server inference → Result return
- Design tradeoffs:
  - Static vs. dynamic thresholds: Static thresholds are simpler but can't adapt to changing load; dynamic thresholds add complexity but maintain SLOs under varying conditions
  - Batch size selection: Larger batches improve throughput but increase latency; MultiTASC uses dynamic batching to optimize this tradeoff
  - Update frequency: More frequent updates allow faster adaptation but increase communication overhead and risk oscillations
- Failure signatures:
  - SLO violations despite MultiTASC: Indicates Capacity metric is inaccurate or threshold updates are too conservative
  - Rapid threshold oscillations: Suggests fractional update percentage is too low or margin M is too high
  - Decreased accuracy: May indicate thresholds are being lowered too aggressively to meet latency targets
- First 3 experiments:
  1. Single-device baseline: Deploy MultiTASC with one device to verify it maintains or improves upon static threshold performance
  2. Controlled load test: Gradually increase request rate to observe how MultiTASC adapts thresholds to maintain SLO
  3. Device heterogeneity test: Deploy devices of different tiers to verify prioritization strategy improves overall system performance

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does MultiTASC perform in heterogeneous environments with more than three device tiers or significantly more device types?
- Basis in paper: [inferred] The paper evaluates performance in a heterogeneous setting with three device tiers (low-, mid-, and high-end), but does not explore more diverse or numerous device categories.
- Why unresolved: The study is limited to three device tiers, and real-world environments may include more varied or numerous device types, which could affect the scheduler's performance and adaptability.
- What evidence would resolve it: Empirical evaluation of MultiTASC in environments with more than three device tiers or a larger variety of device types, measuring performance metrics such as latency, throughput, and accuracy.

### Open Question 2
- Question: What is the impact of using different forwarding decision metrics (e.g., entropy or top-1 softmax) on the performance of MultiTASC?
- Basis in paper: [explicit] The paper mentions that other metrics like top-1 softmax or entropy could be used but does not evaluate their impact on performance.
- Why unresolved: The paper focuses on the Best-versus-Second-Best (BvSB) metric without exploring how alternative metrics might affect latency-accuracy trade-offs or system throughput.
- What evidence would resolve it: Comparative analysis of MultiTASC using different forwarding decision metrics, assessing their effects on system performance metrics such as latency SLO satisfaction, throughput, and accuracy.

### Open Question 3
- Question: How does MultiTASC handle scenarios where the server's processing power is significantly lower than the aggregate computational capacity of the devices?
- Basis in paper: [inferred] The paper discusses scenarios where the server can become overloaded but does not specifically address cases where the server is inherently less powerful than the combined devices.
- Why unresolved: The paper assumes a server with sufficient processing power to assist devices, but real-world scenarios might involve servers with limited computational resources relative to the devices they support.
- What evidence would resolve it: Experimental evaluation of MultiTASC in scenarios where the server's processing power is intentionally limited compared to the aggregate capacity of the devices, measuring the scheduler's ability to maintain performance metrics.

## Limitations
- Capacity estimation relies on precomputed batch latency measurements that may not reflect real-world server load variations
- Device heterogeneity prioritization assumes stable device tier classifications despite runtime performance variability
- Fractional update introduces a hyperparameter that significantly affects system stability but is not thoroughly explored across different workload patterns

## Confidence
- **High confidence** in throughput improvements (20-25 pp) under specific experimental conditions
- **Medium confidence** in generalizability of capacity metric approach to other cascade inference systems
- **Low confidence** in device heterogeneity prioritization's effectiveness in highly dynamic environments
