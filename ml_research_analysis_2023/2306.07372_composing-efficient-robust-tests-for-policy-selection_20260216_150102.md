# Composing Efficient, Robust Tests for Policy Selection

## Quick Facts
- arXiv ID: 2306.07372
- Source URL: https://arxiv.org/abs/2306.07372
- Reference count: 40
- Key outcome: RPOSST selects small, robust test case sets for evaluating RL policies, reducing test cases by up to 98% while maintaining low test score error.

## Executive Summary
This paper introduces RPOSST, a method for selecting small, robust test case sets to evaluate reinforcement learning policies. RPOSST frames test case selection as a two-player game, optimizing under k-of-N robustness measures to handle uncertainty over future deployment policies and test case importance. The method uses regret matching+ and best-arm identification to iteratively refine test case weights and select the most informative tests. Empirical results on toy games, poker datasets, and Gran Turismo™ 7 show RPOSST consistently outperforms baselines in accuracy and reproducibility.

## Method Summary
RPOSST treats test case selection as a two-player game between a protagonist (test designer) and an antagonist (adversary). The protagonist selects test cases and weights to minimize worst-case test score error, while the antagonist chooses future policies and target distributions to maximize this error. RPOSST uses regret matching+ to iteratively update test case weights based on payoff feedback from the antagonist. The method supports both k-of-N robustness (bounding error on the k worst out of N policy-target pairs) and deterministic CVaR-based selection when the uncertainty distribution has finite support. RPOSST can operate in simultaneous or sequential move models, with the latter fixing test cases upfront for reproducibility.

## Key Results
- RPOSST reduces test cases by up to 98% while maintaining low test score error
- Consistent outperformance over baselines in accuracy and reproducibility
- Handles uncertainty over future deployment policies and test case importance
- Supports both k-of-N robustness and deterministic CVaR-based selection

## Why This Works (Mechanism)

### Mechanism 1
- Claim: RPOSST improves test efficiency by treating test case selection as a two-player game, optimizing for k-of-N robustness under uncertainty over future deployment policies and target distributions.
- Mechanism: The algorithm models the test selection problem as a zero-sum game where the protagonist (test designer) selects test cases and weights, while the antagonist adversarially chooses future policies and target distributions to maximize test score error. Regret matching+ is used to iteratively refine the test case weights to minimize the expected worst-case error.
- Core assumption: The tuning policy set ΠTNP sufficiently covers the space of future deployment candidates ΠCDP so that robustness to ΠTNP implies robustness to ΠCDP.
- Evidence anchors:
  - [abstract] "RPOSST treats the test case selection problem as a two-player game and optimizes a solution with provable k-of-N robustness, bounding the error relative to a test that used all the test cases in the pool."
  - [section 4] "By adversarially choosing policies to test, the antagonist forces RPOSST to compose tests that are better at accurately testing the more difficult-to-assess policies in the tuning set."
- Break condition: If the tuning policies do not adequately represent the diversity of future deployment candidates, the k-of-N robustness guarantees fail to hold.

### Mechanism 2
- Claim: RPOSST provides deterministic CVaR-based test selection when the uncertainty distribution Ψ has finite support, enabling efficient and reproducible test design.
- Mechanism: By fixing the ratio k/N and allowing N → ∞, the k-of-N robustness measure converges to the CVaR measure at the k/N fractile. If Ψ has finite support, the entire RPOSST procedure can be run using exact expectations, avoiding sampling noise and enabling direct tracking of the lowest loss test case distribution across rounds.
- Core assumption: The uncertainty distribution Ψ over policies and target distributions has finite support, making exact expectation calculations feasible.
- Evidence anchors:
  - [section 4.2] "If we fix the ratio k/N and allow N → ∞, the k-of-N robustness measure converges toward the CVaR measure at the k/N fractile... A k-of-N algorithm where N → ∞ cannot be implemented with the usual sampling procedure, but it can be implemented if the distribution characterizing our uncertainty, Ψ, has finite support."
- Break condition: If Ψ has infinite or very large support, exact expectation calculations become intractable, and the deterministic CVaR variant cannot be used.

### Mechanism 3
- Claim: The sequential move model of RPOSST ensures reproducible and comparable test results across different deployments by fixing the test case set and weights after optimization.
- Mechanism: In the sequential move model, the antagonist observes the protagonist's chosen test cases before selecting policies and target distributions, forcing the protagonist to update all test case weights as if that specific set was chosen. This results in a single, fixed m-tuple of test cases and weights that can be reused across all future policy evaluations.
- Core assumption: The test case selection and weighting can be determined upfront and remain valid for future policy evaluations, without needing to adapt to each new policy individually.
- Evidence anchors:
  - [section 4.1] "The sequential move model represents the policy testing use case where we select and fix m test cases and test case weights for all future test policies. Test scores are easily reproducible and comparable across test applications since the test cases never change."
- Break condition: If the deployment scenario changes significantly after test construction, the fixed test case set and weights may no longer be appropriate, requiring re-optimization.

- Concept: Two-player game theory and regret minimization
  - Why needed here: RPOSST models test case selection as a two-player game where the protagonist (test designer) and antagonist (adversary) have opposing objectives. Regret minimization algorithms like regret matching+ are used to iteratively improve the protagonist's strategy against a best-responding antagonist.

  - Why needed here: RPOSST optimizes test case selection under k-of-N robustness, which bounds the error on the k worst out of N policy-target distribution pairs sampled from uncertainty distribution Ψ. As N → ∞, this approaches the CVaR measure, providing a deterministic alternative when Ψ has finite support.
  - Quick check question: How does the choice of k and N in the k-of-N robustness measure reflect the designer's tolerance for test score errors on the worst-case policy-target distribution pairs?

  - Why needed here: RPOSST uses online decision processes where the protagonist iteratively updates their test case weights based on payoff feedback from the antagonist. No-regret algorithms like regret matching+ ensure that after T rounds, the protagonist's strategy is close to optimal in terms of minimizing the worst-case loss.

## Architecture Onboarding

- Component map: Result matrix A -> RPOSST optimization (regret matching+) -> Selected m-tuple of test cases and weights
- Critical path:
  1. Evaluate tuning policies on all test cases to construct result matrix A
  2. Run RPOSST optimization game for T rounds:
     a. Protagonist chooses test case weights based on regret matching+
     b. Antagonist samples policies and target distributions from Ψ
     c. Antagonist selects k worst policy-target pairs based on current test case weights
     d. Protagonist receives payoff feedback and updates regret
  3. (Sequential move only) Run Successive Rejects to select final test case selection
  4. Output selected test cases and weights

- Design tradeoffs:
  - Simultaneous vs. sequential move models: Simultaneous allows independent test case sampling per policy but makes results incomparable; sequential fixes test cases upfront for reproducibility but requires upfront optimization.
  - k-of-N vs. CVaR robustness: k-of-N provides probabilistic guarantees with finite N; CVaR offers deterministic optimization when Ψ has finite support.
  - Test size m: Larger m allows more accurate tests but increases computational cost; smaller m is more efficient but may sacrifice accuracy.

- Failure signatures:
  - Poor test accuracy on holdout policies: Indicates tuning policies do not adequately cover the space of deployment candidates or that the uncertainty distribution Ψ is misspecified.
  - High variance in selected test cases across runs: Suggests the optimization landscape is noisy or that the number of rounds T is insufficient for convergence.
  - Computational intractability: Occurs when the number of test cases |T| is very large and the number of rounds T required for convergence is too high.

- First 3 experiments:
  1. Verify the result matrix construction: Evaluate a small set of tuning policies on a subset of test cases and check that the matrix accurately reflects policy performance.
  2. Test RPOSST on a simple domain: Run RPOSST on a toy domain (e.g., Racing Arrows with 50 policies) and verify that it selects test cases that accurately rank holdout policies.
  3. Compare robustness variants: Run both k-of-N and CVaR variants of RPOSST on a domain with finite Ψ support and compare their test accuracy and determinism.

## Limitations
- Limited empirical investigation of RPOSST's scalability to very large test case pools
- Sensitivity of results to the choice of uncertainty distribution Ψ is not fully explored
- No detailed analysis of how to select the tuning policy set for adequate coverage of deployment candidates

## Confidence
- **High**: Core mechanism of framing test selection as a two-player game and empirical results demonstrating efficiency gains on tested domains
- **Medium**: Claims around k-of-N and CVaR robustness, as theoretical guarantees are asymptotic and practical impact of different robustness choices is not fully explored
- **Low**: Scalability and hyperparameter sensitivity claims, due to limited empirical investigation in those areas
