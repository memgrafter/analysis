# Interleaving Pre-Trained Language Models and Large Language Models for Zero-Shot NL2SQL Generation

## Quick Facts
- arXiv ID: 2306.08891
- Source URL: https://arxiv.org/abs/2306.08891
- Reference count: 40
- Key outcome: ZeroNL2SQL framework interleaves PLMs and LLMs, achieving 10-20% better execution accuracy than state-of-the-art methods on zero-shot NL2SQL benchmarks.

## Executive Summary
This paper addresses the challenge of zero-shot natural language to SQL (NL2SQL) translation, where models must convert questions to SQL queries without any labeled data in the target domain. The key insight is that Pre-trained Language Models (PLMs) excel at schema alignment but struggle with complex reasoning, while Large Language Models (LLMs) are superior at reasoning but lack precise schema alignment. The proposed ZeroNL2SQL framework interleaves these models: PLMs first generate SQL sketches using schema alignment, then LLMs complete the queries using complex reasoning and database instance alignment. Experiments on Dr.Spider and KaggleDBQA benchmarks demonstrate significant improvements over both PLM-based and LLM-based approaches.

## Method Summary
The ZeroNL2SQL framework interleaves PLMs and LLMs to leverage their complementary strengths. First, PLMs generate SQL sketches by selecting tables, columns, and keywords from the database schema using a database-aware serialization strategy that prevents overfitting to training data. These sketches are ranked using a question-aware aligner. Next, LLMs complete the top-ranked sketches by generating predicates and other SQL clauses. A predicate calibration module uses multi-level matching to ensure database consistency, correcting LLM errors by finding similar values in the database. Finally, an execution-based selection strategy chooses the SQL query that returns non-null results, ensuring practical usability.

## Key Results
- ZeroNL2SQL outperforms state-of-the-art PLM-based methods by 3.2%–13% on execution accuracy
- ZeroNL2SQL outperforms state-of-the-art LLM-based methods by 10%–20% on execution accuracy
- The framework shows consistent improvements across both Dr.Spider and KaggleDBQA benchmarks

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Interleaving PLMs and LLMs addresses the complementary weakness of each model type.
- Mechanism: PLMs first generate an SQL sketch using schema alignment (SELECT, FROM, KEYWORD clauses), then LLMs complete the query using complex reasoning and database instance alignment.
- Core assumption: PLMs excel at schema alignment but struggle with complex reasoning, while LLMs excel at reasoning but lack precise schema alignment.
- Evidence anchors:
  - [abstract] "PLMs can perform well in schema alignment but struggle to achieve complex reasoning, while LLMs is superior in complex reasoning tasks but cannot achieve precise schema alignment."
  - [section 1] "Our analysis revealed valuable observations regarding the performance of different approaches on addressing the respective difficulties... PLMs: (Pros) PLMs exhibit exceptional proficiency in schema-alignment sub-tasks... (Cons) They are not good at complex reasoning in the zero-shot setting."
  - [corpus] No direct evidence from neighbors - the mechanism is unique to this work.
- Break condition: If PLMs cannot reliably generate valid SQL sketches or if LLMs fail to complete them accurately, the interleaved approach breaks down.

### Mechanism 2
- Claim: Database-aware serialization strategy enables PLMs to select valid tables/columns instead of copying from questions.
- Mechanism: PLMs learn to refer to database elements by indexes (e.g., t0.c2) rather than names, then indexes are translated back to actual names.
- Core assumption: Direct table/column name serialization causes PLMs to overfit to training data and fail on new schemas.
- Evidence anchors:
  - [section 4] "Example 2 (Direct table/column name serialization)... Most existing works use the Spider dataset... We have an observation that the PLM often directly copies column/table names from the question Q during training, rather than selecting from the database."
  - [section 4] "Example 3 (Database-aware serialization)... we use parentheses and indexes to the different parts to serialize the database... In this way, we enforce the PLM to choose the table/column index that best matches the user question rather than directly copying it from the question."
- Break condition: If the index-to-name translation fails or if the PLM cannot learn the indexing mapping effectively.

### Mechanism 3
- Claim: Multi-level matching in predicate calibration finds database-consistent values even when LLM predicts wrong columns.
- Mechanism: The system first tries matching in the predicted column, then expands to the table, and finally to the entire database, using similarity calculations at each level.
- Core assumption: LLM errors in predicate generation can be corrected by finding similar values in the database.
- Evidence anchors:
  - [section 5] "Multi-Level Matching... Given the predicate (column0, value0) predicated by the LLM, there are two types of errors: incorrect predicted value and incorrect predicted column."
  - [section 6] "Table 5: Ablation on different matching methods... Overall, multi-level matching achieves the best performance. The main reason is that in-column matching does not consider LLM's mis-prediction of columns."
- Break condition: If similarity thresholds are too strict or too loose, or if the database lacks sufficiently similar values.

## Architecture Onboarding

- Component map:
  - SQL Sketch Generation Module (PLMs) -> Question-aware aligner -> SQL Query Completion Module (LLMs) -> Predicate calibration -> Execution-based selection

- Critical path:
  1. Input: Question Q + Database schema Dschema
  2. PLM generates SQL sketches (top-k candidates)
  3. Question-aware aligner ranks sketches
  4. LLM completes top-ranked sketch into full SQL
  5. Predicate calibration ensures database consistency
  6. Execution-based selection chooses final SQL

- Design tradeoffs:
  - Top-k hypothesis retention vs. computational cost
  - Similarity threshold tuning in predicate calibration
  - Index-based vs. name-based database serialization
  - Execution-based selection vs. LLM confidence scoring

- Failure signatures:
  - PLM sketch generation fails: Invalid SQL sketches, poor schema alignment
  - LLM completion fails: Incorrect predicates, SQL execution errors
  - Predicate calibration fails: No similar values found, wrong column selection
  - Selection strategy fails: All candidates return NULL results

- First 3 experiments:
  1. Test PLM sketch generation alone on Dr.Spider with database-aware serialization
  2. Test LLM completion alone with synthetic SQL sketches
  3. End-to-end test on a small dataset with simplified predicate calibration

## Limitations
- Database-aware serialization effectiveness may be dataset-specific, relying on patterns observed in Spider training data
- Multi-level matching assumes sufficient semantic similarity between LLM predictions and actual database values
- The approach's performance on databases with significantly different naming conventions or question-schema alignment patterns remains unclear

## Confidence

- **High Confidence**: The interleaving framework architecture and its general effectiveness (Section 6 results showing 10-20% improvement over baselines). The empirical observations about PLM vs LLM complementary strengths are well-supported.
- **Medium Confidence**: The database-aware serialization mechanism's superiority, as it's primarily validated through ablation studies on Spider dataset, with less evidence for cross-dataset generalization.
- **Medium Confidence**: The multi-level matching strategy's effectiveness, though ablation studies support this claim, the similarity threshold tuning and its robustness across diverse database domains remains unclear.

## Next Checks

1. **Cross-dataset validation**: Test ZeroNL2SQL on non-Spider datasets with different schema characteristics to verify if database-aware serialization maintains its effectiveness when question-schema alignment patterns differ from training data.

2. **Similarity threshold sensitivity**: Systematically vary the similarity thresholds in multi-level matching across multiple runs to determine the stability of predicate calibration performance and identify optimal threshold ranges.

3. **Error analysis on failure cases**: Conduct detailed analysis of cases where ZeroNL2SQL fails to identify whether errors stem from PLM sketch generation (schema misalignment), LLM completion (reasoning errors), or predicate calibration (value matching failures), to better understand the relative contribution of each component.
