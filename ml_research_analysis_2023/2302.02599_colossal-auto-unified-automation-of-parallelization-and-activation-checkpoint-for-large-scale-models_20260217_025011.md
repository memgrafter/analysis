# Colossal-Auto: Unified Automation of Parallelization and Activation Checkpoint for Large-scale Models

## Quick Facts
- arXiv ID: 2302.02599
- Source URL: https://arxiv.org/abs/2302.02599
- Reference count: 24
- Primary result: MAP achieves up to 19.4% higher throughput compared to existing methods on GPT-2 models

## Executive Summary
This paper presents MAP, a compiler that automatically parallelizes model training for large models on multi-GPU systems. MAP addresses the challenge of finding efficient distributed execution plans by jointly optimizing intra-op parallelism and activation checkpointing. The system introduces a symbolic profiler to collect memory and computing statistics with minimal overhead, and uses a two-stage solver to optimize execution plans. Experiments demonstrate that MAP achieves significant performance improvements over existing methods like Megatron-LM and Optimus on GPT-2 models.

## Method Summary
MAP employs a symbolic profiler to collect memory and computing statistics with minimal overhead, enabling the compiler to make informed optimization decisions. The two-stage solver first generates a coarse-grained plan considering device mesh topologies, then refines the execution plan by optimizing intra-op parallelism and activation checkpointing. The system supports arbitrary device mesh topologies and generates optimized PyTorch code for distributed training. By jointly optimizing these aspects, MAP can automatically find efficient execution plans for large-scale models that would be difficult to tune manually.

## Key Results
- MAP achieves up to 19.4% higher throughput compared to Megatron-LM and Optimus on GPT-2 models
- The symbolic profiler collects memory and computing statistics with minimal overhead
- The system supports arbitrary device mesh topologies for flexible deployment

## Why This Works (Mechanism)
MAP works by automatically exploring the vast space of distributed execution configurations through its symbolic profiler and two-stage solver. The profiler provides accurate estimates of memory and compute requirements without the need for actual execution, allowing rapid exploration of different parallelization strategies. The two-stage approach first considers high-level device placement decisions, then optimizes fine-grained aspects like operator fusion and checkpointing locations. This hierarchical optimization enables finding configurations that balance memory usage, communication overhead, and computation efficiency in ways that manual tuning would struggle to achieve.

## Foundational Learning
- **Symbolic profiling**: Abstract representation of computation to estimate resource usage without actual execution; needed to enable rapid exploration of configuration space
- **Two-stage optimization**: Hierarchical approach separating coarse device placement from fine-grained operator scheduling; needed to manage complexity of search space
- **Activation checkpointing**: Selective recomputation of intermediate activations to reduce memory footprint; needed for training large models within GPU memory limits
- **Device mesh topologies**: Flexible arrangement of GPUs for distributed computation; needed to adapt to various hardware configurations
- **Intra-op parallelism**: Parallel execution of individual operators; needed to maximize hardware utilization
- **Operator fusion**: Combining multiple operators into single kernel; needed to reduce kernel launch overhead and improve memory locality

## Architecture Onboarding

Component Map:
Symbolic Profiler -> Two-Stage Solver -> PyTorch Code Generator

Critical Path:
Model description -> Symbolic profiling -> Coarse-grained planning -> Fine-grained optimization -> Code generation -> Distributed training execution

Design Tradeoffs:
- Accuracy vs speed in profiling (symbolic vs concrete execution)
- Search space exploration vs optimization quality
- Memory efficiency vs recomputation overhead in checkpointing
- Communication volume vs computation granularity

Failure Signatures:
- Poor performance on irregular computation patterns
- Suboptimal scaling beyond tested model sizes
- Configuration generation failures for complex architectures

## Limitations
- Evaluation only covers models up to 1.5B parameters, raising questions about scalability to truly massive models
- Limited comparison scope, only benchmarking against Megatron-LM and Optimus without testing against other production systems
- No evaluation of non-Transformer architectures or irregular computation patterns common in modern large models

## Confidence

High confidence in:
- Symbolic profiling methodology and its low overhead characteristics
- Two-stage solver's effectiveness for arbitrary device meshes

Medium confidence in:
- Reported throughput improvements given the limited scope of comparison
- System's performance on models significantly larger than those tested

Low confidence in:
- MAP's scalability to truly massive models beyond GPT-2
