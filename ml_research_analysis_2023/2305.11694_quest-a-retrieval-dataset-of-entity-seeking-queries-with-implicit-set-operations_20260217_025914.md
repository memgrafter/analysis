# QUEST: A Retrieval Dataset of Entity-Seeking Queries with Implicit Set Operations

## Quick Facts
- arXiv ID: 2305.11694
- Source URL: https://arxiv.org/abs/2305.11694
- Reference count: 16
- Primary result: A dataset of 3357 queries with implicit set operations (conjunctions and negations) mapped to Wikipedia entities, with human-annotated relevance and attributions.

## Executive Summary
QUEST is a dataset designed to evaluate retrieval systems on entity-seeking queries that involve implicit set operations like conjunctions and negations. The dataset was constructed semi-automatically from Wikipedia categories, paraphrased by crowdworkers for naturalness, and validated for semantic equivalence. Experiments show that even state-of-the-art dual encoder and cross-attention models struggle with these queries, achieving only 0.192 average F1, highlighting the need for improved retrieval systems for complex query operations.

## Method Summary
The dataset was constructed by first generating queries from Wikipedia category names using templatic combinations (intersection and difference). Crowdworkers then paraphrased these queries to be more natural while preserving semantic meaning, and additional workers validated fluency and equivalence. Each query was mapped to a set of relevant Wikipedia entities through transitive closure of category assignments. Relevance judgments and attributions (document spans) were collected from crowdworkers. The dataset was split into train, validation, and test sets across four domains (films, books, animals, plants).

## Key Results
- QUEST dataset contains 3357 queries with implicit set operations (conjunctions and negations) across four domains.
- State-of-the-art retrieval systems achieve only 0.192 average F1 on QUEST, with the best system using a T5-Large dual encoder and cross-attention classifier.
- Models struggle particularly with queries involving intersection and difference operations, with error analysis showing incorrect handling of conjunctions and negations.

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The semi-automatic construction using Wikipedia category names provides high-precision entity sets for training and evaluation.
- Mechanism: Wikipedia categories are manually curated natural language labels that map to groups of related documents, allowing automatic determination of answer sets through transitive closure.
- Core assumption: Wikipedia category assignments are sufficiently complete and accurate to serve as ground truth for entity sets.
- Evidence anchors:
  - [section] "We use categories and their mapping to entities in Wikipedia as a building block for our dataset construction approach, but do not allow access to this semi-structured data source at inference time"
  - [section] "Category assignments to documents allow us to automatically determine the set of answer entities for queries with high precision and relatively high recall"
- Break condition: If Wikipedia categories have poor recall or contain significant noise, the ground truth entity sets would be incomplete, leading to incorrect evaluation of retrieval systems.

### Mechanism 2
- Claim: Paraphrasing by crowdworkers improves query fluency and naturalness while preserving semantic meaning.
- Mechanism: Workers rephrase templatically generated queries to be more natural and unambiguous, then validate fluency and equivalence through additional worker review.
- Core assumption: Paraphrased queries maintain the same semantic constraints as the original templatic queries while sounding more like natural search queries.
- Evidence anchors:
  - [section] "Crowdworkers were asked to paraphrase a templatically generated query so that the paraphrased query is fluent, expresses all constraints in the original query, and clearly describes what a user could be looking for"
  - [section] "We excluded those queries which were rated as not fluent, unnatural or having a different meaning than the original query, based on a majority vote"
- Break condition: If paraphrasing changes the semantic meaning of queries or introduces ambiguity, the dataset would no longer accurately test retrieval for the intended query types.

### Mechanism 3
- Claim: The combination of dense dual encoder retrieval and cross-attention classification provides better performance than sparse retrieval alone for complex set operation queries.
- Mechanism: The dual encoder efficiently retrieves candidate documents from the large corpus, while the cross-attention classifier makes fine-grained relevance decisions using the full query-document context.
- Core assumption: The dual encoder can effectively encode queries with implicit set operations into meaningful representations that correlate with document relevance.
- Evidence anchors:
  - [section] "We evaluated several combinations of retrievers and classifiers, as shown in Figure 3"
  - [section] "As shown in Table 3, the best overall system uses a T5-Large Dual Encoder instead of BM25 for retrieval"
- Break condition: If the dual encoder cannot effectively represent the semantic constraints in complex queries, the retrieval stage will fail to provide relevant candidates, limiting overall system performance.

  - Why needed here: The experiments use T5-based dual encoders for efficient candidate retrieval, requiring understanding of how these models encode queries and documents separately

## Architecture Onboarding

- Component map: Wikipedia category graph → Base queries → Templatic queries → Crowd paraphrasing → Natural queries → Relevance labeling → Ground truth → Dual encoder retriever → Candidate documents (top-100) → Cross-attention classifier → Final relevance scores → F1 score
- Critical path: Query → Dual encoder → Cross-attention classifier → Relevance prediction → F1 score
- Design tradeoffs:
  - Using Wikipedia categories provides high-precision entity sets but may have recall issues
  - Crowd paraphrasing ensures naturalness but adds annotation cost
  - Dual encoder + classifier provides good performance but requires two-stage processing
  - Document truncation to 512 tokens improves efficiency but may lose context
- Failure signatures:
  - Low recall@100 from dual encoder indicates poor query encoding for complex set operations
  - High false positive rate from classifier suggests inadequate sensitivity to negations or conjunctions
  - Low overall F1 indicates issues in either retrieval or classification stages
- First 3 experiments:
  1. Compare dual encoder performance with and without document truncation to assess context impact
  2. Evaluate classifier sensitivity to individual query constraints by ablating constraints from queries
  3. Test retrieval performance on queries with only intersection vs only difference constraints to isolate challenging operations

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How do large language models (LLMs) specifically struggle with negation in complex queries compared to other set operations?
- Basis in paper: [explicit] The paper states that queries involving negation and conjunction are particularly challenging for models and systems are further challenged with combinations of these operations.
- Why unresolved: While the paper identifies that models struggle with negation, it does not provide a detailed analysis of why negation is more challenging than other set operations like intersection or union. The error analysis mentions that models incorrectly treat intersection as union and fail to adequately handle negations, but it does not delve into the underlying reasons for these specific failures.
- What evidence would resolve it: Detailed error analysis showing specific failure cases of LLMs on negated queries, including examples of model outputs and explanations of why the models failed to handle negation correctly.

### Open Question 2
- Question: What is the impact of document truncation on the performance of retrieval models for long documents?
- Basis in paper: [explicit] The paper mentions that document text is truncated to 512 tokens for the dual encoder and 384 tokens for the classifier, and states that this usually provides sufficient context.
- Why unresolved: The paper evaluates the impact of truncation on model performance but does not explore alternative strategies for handling long documents, such as splitting documents into overlapping chunks or using efficient transformer variants.
- What evidence would resolve it: Comparative experiments evaluating the performance of retrieval models using different document truncation strategies or efficient transformer variants for handling long documents.

### Open Question 3
- Question: How does the use of Wikipedia categories as a base for query generation affect the naturalness and representativeness of the dataset?
- Basis in paper: [explicit] The paper acknowledges that using Wikipedia categories does not represent an unbiased sample from a natural distribution of real search queries and that the queries were judged to plausibly correspond to real user search needs.
- Why unresolved: The paper does not provide a detailed analysis of how the use of Wikipedia categories influences the types of queries in the dataset and whether this affects the generalizability of the results to real-world search scenarios.
- What evidence would resolve it: A comparison of the QUEST dataset with other retrieval datasets that use different query generation methods, along with an analysis of the types of queries and their naturalness in each dataset.

## Limitations

- The dataset construction relies heavily on the completeness and accuracy of Wikipedia category assignments, which may have incomplete recall (83.9% for conjunction queries, 77.5% for negation queries).
- The semi-automatic construction approach using Wikipedia categories may not fully capture the breadth of real-world search patterns or represent an unbiased sample of natural search queries.
- The experiments use T5-based models and a specific two-stage retrieval-classification approach, limiting generalizability to other architectures or training methodologies.

## Confidence

- Medium for the claim that QUEST is a challenging benchmark for retrieval systems; High for the methodological description of dataset construction.

## Next Checks
