# Large Language Model Programs

## Quick Facts
- arXiv ID: 2305.05364
- Source URL: https://arxiv.org/abs/2305.05364
- Reference count: 29
- Primary result: 6.4% improvement over chain-of-thought baseline without finetuning

## Executive Summary
This paper introduces Large Language Model (LLM) Programs, a framework for embedding LLMs within algorithms or programs to extend their capabilities beyond what's possible with pure prompting. The authors present a case study on evidence-supported question-answering, where an LLM is used to filter relevant paragraphs and generate reasoning steps. By decomposing complex tasks into manageable subproblems and maintaining state across multiple LLM calls, the approach achieves significant performance improvements while avoiding the context limitations of traditional prompting methods.

## Method Summary
The method involves embedding an LLM (OPT-175B) within an algorithmic framework for evidence-supported question-answering. The system operates in two main phases: first, it filters relevant paragraphs from a large knowledge base using likelihood ranking based on negative log-likelihood (NLL) scores; second, it performs tree search over reasoning steps, generating chains of thought conditioned on different evidence paragraphs and ranking them using NLL and delta ranking strategies. The approach requires no finetuning and systematically decomposes the QA task into isolated subproblems that each fit within the LLM's context window.

## Key Results
- 6.4% improvement over chain-of-thought baseline on StrategyQA dataset
- Successful implementation of evidence-supported question-answering without finetuning
- Demonstration of context management through program decomposition

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Embedding LLMs within programs overcomes finite context limitations by using external program state instead of relying on the LLM's internal context.
- Mechanism: The program maintains state across multiple LLM calls, with each call receiving only step-specific prompts and context, preventing context overflow and allowing systematic processing of larger tasks.
- Core assumption: The program can correctly decompose tasks into subproblems that each fit within the LLM's context window.
- Evidence anchors:
  - [abstract]: "The possibility to parameterise an LLM through such in-context examples widens their capability at a much lower cost than finetuning."
  - [section]: "Hiding information which is irrelevant to the current step allows us to focus on isolated subproblems whose results are further combined in future calls to the LLM."
  - [corpus]: Weak - no direct evidence about context size limitations in corpus.
- Break condition: If task decomposition creates subproblems that still exceed context limits, or if maintaining state across program steps introduces errors that compound over iterations.

### Mechanism 2
- Claim: LLM programs improve systematic generalization by incorporating high-level algorithmic information through program structure rather than relying on pattern matching from training data.
- Mechanism: The program explicitly encodes algorithmic knowledge (like filtering, tree search, recursion) that guides LLM behavior, reducing reliance on statistical shortcuts.
- Core assumption: The programmer correctly understands the optimal algorithm for the task and can implement it.
- Evidence anchors:
  - [abstract]: "We extend this line of reasoning and present a method which further expands the capabilities of an LLM by embedding it within an algorithm or program."
  - [section]: "Embedding an LLM in a program can significantly expand the theoretical and practical capabilities of the system with no or little finetuning and can help the system generalise more systematically."
  - [corpus]: Weak - no direct evidence about generalization patterns in corpus.
- Break condition: If the implemented algorithm is suboptimal or if the LLM's step-level performance degrades when embedded in the program structure.

### Mechanism 3
- Claim: Isolated step-specific evaluation improves overall system performance by allowing targeted optimization of each subproblem.
- Mechanism: Each LLM call is treated as a black box with well-defined inputs/outputs, enabling systematic testing, prompt engineering, and performance measurement for individual steps.
- Core assumption: Subproblem boundaries are correctly identified and performance on isolated steps correlates with overall task performance.
- Evidence anchors:
  - [abstract]: "We obtain a 6.4% improvement over the chain of thought baseline through a more algorithmic approach without any finetuning."
  - [section]: "Understanding the problem decomposition allows for more fine-grained input and output specifications for each subproblem or step of the program."
  - [corpus]: Weak - no direct evidence about evaluation methodologies in corpus.
- Break condition: If errors in individual steps don't propagate predictably, or if step-level optimization doesn't translate to overall performance gains.

## Foundational Learning

- Concept: Programmatic decomposition of complex tasks into manageable subproblems
  - Why needed here: LLMs struggle with tasks requiring long-term planning or maintaining complex state across many steps
  - Quick check question: Can you explain why breaking a task into smaller steps might help an LLM perform better?

- Concept: Tree search and ranking algorithms for exploring solution spaces
  - Why needed here: The paper uses tree search to explore reasoning chains by generating steps conditioned on different evidence paragraphs
  - Quick check question: How does tree search help when you need to explore multiple possible reasoning paths?

- Concept: Negative log-likelihood (NLL) as a ranking metric for generated text
  - Why needed here: The paper uses NLL differences to rank reasoning steps and select the most relevant context
  - Quick check question: What does a lower NLL value indicate about the quality of generated text?

## Architecture Onboarding

- Component map: Input processing layer -> Filtering module -> Tree search engine -> Ranking system -> Output generator -> Program coordinator
- Critical path: Question → Filtering → Tree Search (generate steps → rank → expand) → Answer synthesis
- Design tradeoffs: Single large context vs. multiple small contexts; prompt engineering complexity vs. programmatic control; search breadth vs. computational cost
- Failure signatures: Context overflow errors; compounding errors across steps; poor ranking leading to irrelevant reasoning chains; step-level performance degradation
- First 3 experiments:
  1. Implement and test paragraph filtering with NLL scoring on a small dataset
  2. Build tree search with single-step generation and basic NLL ranking
  3. Add delta ranking metrics and compare performance against NLL-only ranking

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How can we systematically evaluate the performance of individual sub-problems within an LLM program?
- Basis in paper: Explicit. The paper mentions that understanding the problem decomposition allows for more fine-grained input and output specifications for each subproblem or step of the program, which in turn allows for a more manageable and systematic evaluation of the LLM's performance by testing the model on each subproblem in isolation.
- Why unresolved: The paper does not provide a detailed framework or methodology for systematically evaluating the performance of individual sub-problems within an LLM program.
- What evidence would resolve it: A comprehensive evaluation framework that includes specific metrics, test sets, and evaluation procedures for assessing the performance of individual sub-problems within an LLM program.

### Open Question 2
- Question: What are the limitations of using a single call to an LLM with a single prompt for complex tasks?
- Basis in paper: Explicit. The paper mentions that a key characteristic of approaches that use a single call to an LLM with a single prompt is the limitation imposed by the size of the input and the necessity to prompt engineer multiple algorithm steps within one prompt. This can lead to interference between steps which hurts the final performance.
- Why unresolved: The paper does not provide a detailed analysis of the specific limitations and challenges associated with using a single call to an LLM with a single prompt for complex tasks.
- What evidence would resolve it: A thorough investigation into the performance degradation, prompt interference, and other limitations when using a single call to an LLM with a single prompt for complex tasks, along with potential mitigation strategies.

### Open Question 3
- Question: How can we design effective ranking criteria for selecting the most relevant evidence paragraphs in an LLM program?
- Basis in paper: Explicit. The paper presents two ranking strategies for selecting the most relevant evidence paragraphs in the tree search experiment: average negative log-likelihood (NLL) of the chain so far and average NLL difference (ΔP and ΔQ). The authors find that steps conditioned on paragraphs where ΔP + ΔQ is the lowest leads to better reasoning chains.
- Why unresolved: The paper does not provide a comprehensive analysis of the effectiveness of different ranking criteria or a systematic approach to designing optimal ranking criteria for selecting evidence paragraphs in LLM programs.
- What evidence would resolve it: A comparative study of different ranking criteria, including their strengths, weaknesses, and performance on various tasks, along with guidelines for designing effective ranking criteria for selecting evidence paragraphs in LLM programs.

## Limitations

- The paper lacks empirical evidence showing how context overflow is prevented in practice when decomposing tasks
- Claims about systematic generalization improvements are not rigorously validated across diverse tasks
- Critical implementation details about prompt templates, ranking thresholds, and error handling are missing

## Confidence

- **High confidence**: The core observation that embedding LLMs in programs can extend capabilities beyond pure prompting is well-supported by the 6.4% improvement result and aligns with established programming principles.
- **Medium confidence**: The mechanism of using program state to manage context across multiple LLM calls is plausible but under-specified regarding edge cases and error propagation.
- **Low confidence**: Claims about systematic generalization improvements lack sufficient empirical backing, as the paper doesn't compare against other systematic approaches or demonstrate robustness across diverse tasks.

## Next Checks

1. **Context management validation**: Design experiments that deliberately create subproblems exceeding LLM context limits to verify the proposed decomposition approach prevents context overflow and identify failure modes when decomposition is imperfect.

2. **Generalization robustness test**: Apply the LLM program framework to at least three diverse tasks (e.g., mathematical reasoning, code generation, and multi-hop QA) to assess whether improvements generalize beyond the evidence-supported QA domain and identify task-specific limitations.

3. **Algorithmic knowledge encoding audit**: Systematically vary the program's algorithmic components (e.g., different search strategies, filtering methods) while keeping the LLM constant to quantify how much of the performance gain comes from program design versus LLM capabilities.
