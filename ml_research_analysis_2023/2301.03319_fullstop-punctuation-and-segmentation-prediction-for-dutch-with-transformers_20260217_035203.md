# FullStop:Punctuation and Segmentation Prediction for Dutch with Transformers

## Quick Facts
- arXiv ID: 2301.03319
- Source URL: https://arxiv.org/abs/2301.03319
- Reference count: 9
- Primary result: Achieved F1-score of 0.9742 on Dutch punctuation prediction

## Executive Summary
This paper presents FullStop, a transformer-based system for predicting punctuation and segmentation in Dutch text streams. The approach uses a sliding window of 200 words to predict punctuation marks for each word, addressing the common need to process ASR output for improved readability. The system demonstrates superior performance compared to machine translation baselines and provides publicly available models for various use cases including academic lectures and sign language video corpora.

## Method Summary
The FullStop system employs a sliding window approach where each word in a 200-word window is classified with punctuation and segmentation tokens. The method uses XLM-RoBERTa Base architecture, fine-tuned on Dutch speech recognition transcripts. Words are processed with their left and right context, and predictions are made using a classification head that outputs segmentation tokens. The sliding window allows processing of long text streams while maintaining contextual awareness.

## Key Results
- Achieved F1-score of 0.9742 on Dutch test data
- Outperformed machine translation baseline approach for punctuation prediction
- Demonstrated effectiveness for processing ASR output to improve readability and ease manual correction

## Why This Works (Mechanism)
The system leverages transformer architecture's ability to capture long-range dependencies in text while the sliding window approach provides manageable computational overhead. By predicting punctuation and segmentation tokens directly rather than generating full sentences, the model maintains focus on the specific task while benefiting from contextual information within each window.

## Architecture Onboarding

**Component Map**: Input Text -> Sliding Window (200 words) -> XLM-RoBERTa Base -> Classification Head -> Punctuation/Segmentation Tokens

**Critical Path**: The core processing pipeline involves reading text streams, applying sliding window segmentation, passing each window through the transformer model, and generating punctuation predictions for each word position.

**Design Tradeoffs**: Sliding window approach balances context coverage against computational efficiency, while fine-tuning XLM-RoBERTa Base provides strong performance without the cost of training from scratch.

**Failure Signatures**: Poor predictions typically occur at window boundaries, with rare punctuation marks, or when context extends beyond the 200-word window limit.

**First Experiments**: 1) Test with different window sizes (100, 200, 300 words) to measure impact on F1-score; 2) Evaluate on out-of-domain ASR data to assess generalization; 3) Compare inference speed with baseline MT approach.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: What is the optimal sliding window size for the FullStop system when processing ASR output streams?
- Basis in paper: [inferred] The paper mentions using a sliding window of 200 words but states this was chosen empirically and that the number of 200 words was chosen empirically to account for the fact that words get tokenized into more than one token (subword tokenization). They also mention leaving some headroom since some words get decomposed into multiple tokens.
- Why unresolved: The authors chose 200 words empirically without testing other window sizes or providing justification for why this is optimal. Different window sizes might affect performance.
- What evidence would resolve it: Systematic testing of different window sizes (e.g., 100, 200, 300, 400 words) and comparing F1-scores for punctuation and segmentation prediction would show which size performs best.

### Open Question 2
- Question: How would the FullStop system perform if it predicted true case of words in addition to punctuation?
- Basis in paper: [explicit] The authors mention as future work: "The model could also be extended to predict the segmentation tokens and the true case of every word in the sequence. This is a common use case in processing the output of automatic speech recognition systems."
- Why unresolved: The authors acknowledge this as a potential extension but do not test it. Truecasing could improve readability and downstream processing.
- What evidence would resolve it: Training and evaluating a model that predicts both punctuation and true case, then comparing its performance to the current punctuation-only model on the same test sets.

### Open Question 3
- Question: Would a larger model architecture (e.g., XLM-Roberta Large instead of Base) significantly improve performance for Dutch punctuation prediction?
- Basis in paper: [explicit] The authors state: "Comparing the results from Tables 4 and 5 with the finetuned multilingual model from our previous work, we estimate that a size 'large' model could improve the macro F1 by 5%. However, XLM-Roberta large models use more than twice as many parameters as base models, with 550 million parameters compared to 270 million."
- Why unresolved: The authors only estimate potential improvement without actually training or testing a large model. The trade-off between performance gain and computational cost remains unknown.
- What evidence would resolve it: Training and evaluating an XLM-Roberta Large model on the same data and comparing its F1-scores, inference speed, and memory usage to the Base model.

### Open Question 4
- Question: How does the FullStop system handle code-switching scenarios where multiple languages appear in the same text stream?
- Basis in paper: [explicit] The authors mention training a multilingual model "for cases where the language is unknown or where code switching applies" and evaluate it on multiple languages, but do not specifically test mixed-language scenarios.
- Why unresolved: The evaluation is done on monolingual test sets for each language, not on actual code-switching data where languages alternate within sentences or paragraphs.
- What evidence would resolve it: Testing the multilingual model on real or artificially created code-switching data (e.g., Dutch-English alternating sentences) and measuring performance degradation compared to monolingual scenarios.

### Open Question 5
- Question: What is the inter-annotator agreement for human punctuation insertion on ASR output, and how does it compare to the FullStop system's performance?
- Basis in paper: [inferred] The authors note in their qualitative evaluation that "there are often no strict punctuation rules" and that their predictions "could be argued for," suggesting that human agreement might be low, but they do not measure this.
- Why unresolved: The authors compare their system to a gold standard but do not establish how consistent human annotators would be with each other when adding punctuation to unpunctuated ASR output.
- What evidence would resolve it: Having multiple human annotators punctuate the same ASR output and calculating inter-annotator agreement (e.g., Cohen's kappa), then comparing this to the system's F1-scores on the same data.
