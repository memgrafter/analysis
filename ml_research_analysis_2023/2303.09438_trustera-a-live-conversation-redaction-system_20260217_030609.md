# Trustera: A Live Conversation Redaction System

## Quick Facts
- arXiv ID: 2303.09438
- Source URL: https://arxiv.org/abs/2303.09438
- Reference count: 0
- Key outcome: First system to redact PII in real-time spoken conversations to prevent agents from hearing sensitive customer data

## Executive Summary
Trustera is the first system to redact personally identifiable information (PII) in real-time spoken conversations to prevent agents from hearing sensitive customer data. It uses a cascaded pipeline of automatic speech recognition (ASR), natural language understanding (NLU), and a live audio redactor module to detect and mask PII as soon as it is spoken, significantly reducing the risk of PII interception or storage in insecure systems. The ASR uses a hybrid DNN-HMM BiLSTM acoustic model with a 4-gram language model, trained on 40,000 hours of anonymized call data, achieving 21.5% lower word error rate than an offline end-to-end model while reducing CPU usage by 53.2%. The NLU uses a logistic regression classifier to detect PII types in real-time, achieving high recall despite processing partial ASR hypotheses. Trustera is currently deployed in thousands of call centers to secure customer PII.

## Method Summary
Trustera implements a real-time PII redaction system through a cascaded pipeline of ASR, NLU, and live audio redactor (LAR) modules. The ASR uses a hybrid DNN-HMM BiLSTM acoustic model with a 4-gram language model trained on 40,000 hours of anonymized call data, optimized for low CPU usage and high accuracy. The NLU employs a logistic regression classifier trained to detect PII types using context tokens from ASR hypotheses. The LAR monitors ASR output and mutes the audio channel when PII is detected, continuing until the full entity is spoken. The system is designed to process audio faster than real-time, ensuring PII is masked before agents can hear sensitive information.

## Key Results
- Achieved 21.5% lower word error rate than offline end-to-end models while reducing CPU usage by 53.2%
- Successfully deployed in thousands of call centers for real-time PII protection
- Uses hybrid DNN-HMM BiLSTM acoustic model with 4-gram language model for optimal performance

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Real-time PII redaction in live audio is possible by cascading ASR and NLU modules.
- Mechanism: The ASR module converts live speech to text hypotheses in real-time; the NLU module then classifies tokens as PII or non-PII and signals the LAR to mask the corresponding audio.
- Core assumption: ASR hypotheses, even if partial and error-prone, provide sufficient information for NLU to identify PII early enough to trigger masking before sensitive data is transmitted to the agent.
- Evidence anchors:
  - [abstract] "Trustera's architecture consists of a pipeline of automatic speech recognition, natural language understanding, and a live audio redactor module."
  - [section] "The ASR module is a finite state machine (FSM) consisting of a hybrid DNN-HMM BiLSTM acoustic model [8], a 4-gram language model [9] and a pronunciation dictionary."
- Break condition: ASR word error rate becomes so high that NLU cannot reliably detect PII boundaries, or latency exceeds the time window between PII utterance and agent hearing.

### Mechanism 2
- Claim: Using a hybrid DNN-HMM BiLSTM acoustic model with a 4-gram language model provides a better trade-off between CPU usage and accuracy than end-to-end models for real-time redaction.
- Mechanism: The hybrid model processes speech frame-by-frame, allowing immediate partial hypothesis generation; the 4-gram LM constrains ASR output to improve PII detection accuracy while keeping computational cost low.
- Core assumption: End-to-end models, while potentially more accurate offline, introduce too much latency and CPU load for real-time redaction, making them unsuitable for live call center deployment.
- Evidence anchors:
  - [abstract] "The ASR uses a hybrid DNN-HMM BiLSTM acoustic model with a 4-gram language model, trained on 40,000 hours of anonymized call data, achieving 21.5% lower word error rate than an offline end-to-end model while reducing CPU usage by 53.2%."
  - [section] "End-to-end approaches usually require GPUs or they consume a lot of CPU resource, which is cost-prohibitive for call centers."
- Break condition: If call center hardware evolves to support efficient GPU inference, the advantage of hybrid models diminishes.

### Mechanism 3
- Claim: Masking audio immediately upon PII detection, rather than post-call, significantly reduces the risk of PII exposure.
- Mechanism: The LAR module monitors ASR hypotheses in real-time; as soon as a digit or PII indicator is detected, NLU classifies the entity and LAR mutes the audio channel until the full PII entity is spoken.
- Core assumption: The time between initial PII detection and the end of the entity is short enough (e.g., for a 16-digit credit card) that masking can be completed before the agent hears any sensitive data.
- Evidence anchors:
  - [abstract] "As opposed to post-call redaction, audio masking starts as soon as the customer begins speaking to a PII entity."
  - [section] "LAR masks the audio using a beep sound... Audio masking continues until the end of entity is decided."
- Break condition: If entity detection latency exceeds the speaking duration of the PII, sensitive data will be transmitted before masking.

## Architecture Onboarding

- Component map: Audio Input → VAD → ASR Decoder (Agent Channel + Caller Channel) → NLU Classifier → LAR → Masked Audio Output + PII Capture → Payment System
- Critical path: Caller audio → ASR → NLU → LAR → Agent audio mute; any delay in this chain risks PII exposure
- Design tradeoffs:
  - Accuracy vs. Latency: More accurate ASR models increase latency; simpler models risk missing PII
  - CPU vs. GPU: Hybrid models run efficiently on CPUs but may be less accurate than GPU-based end-to-end models
  - Masking vs. Capture: Must mask audio without losing the ability to capture the actual PII value for transactions
- Failure signatures:
  - Agent hears PII: Indicates ASR or NLU failed to detect entity in time
  - False positives (over-masking): NLU misclassifies non-PII as sensitive
  - System lag: CPU usage spikes or latency exceeds real-time threshold
- First 3 experiments:
  1. Simulate a live call with known PII; measure time from first PII word to agent mute activation
  2. Vary ASR model complexity (e.g., switch to simpler LM) and measure impact on WER and CPU usage
  3. Inject synthetic noise into audio and evaluate NLU recall/precision drop

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How can the ASR model be further optimized to reduce CPU usage while maintaining or improving WER on entity recognition?
- Basis in paper: [explicit] The paper discusses optimizing ASR for real-time processing with minimal CPU usage, achieving a 53.2% reduction in CPU usage while improving WER by 21.5%.
- Why unresolved: While significant improvements have been made, further optimization could potentially lead to even better performance, especially for entity recognition which is critical for PII redaction.
- What evidence would resolve it: Experimental results comparing different ASR architectures (e.g., newer end-to-end models, different acoustic models) on CPU usage and WER, particularly on entity recognition tasks.

### Open Question 2
- Question: How can the NLU module be improved to reduce the precision/recall drop when processing partial ASR hypotheses in real-time?
- Basis in paper: [explicit] The paper mentions a large gap between stable and unstable hypotheses when comparing offline and online NLU performance, with the online NLU experiencing a precision drop of 24.3% for CCNUM.
- Why unresolved: The current online NLU model experiences significant performance degradation due to processing partial hypotheses, which is a critical issue for real-time PII redaction.
- What evidence would resolve it: Experimental results comparing different NLU architectures (e.g., more advanced sequence models, models with access to future context) on precision and recall metrics when processing partial ASR hypotheses.

### Open Question 3
- Question: What are the potential risks and mitigation strategies for Trustera in handling ambiguous word-to-digit normalization cases (e.g., "one hundred twenty" -> 120 or 100-20)?
- Basis in paper: [explicit] The paper mentions that word-to-digit normalization may fail in ambiguous cases, which could lead to PII leaks.
- Why unresolved: While the paper acknowledges the issue, it does not provide specific strategies for handling these ambiguous cases or quantify the potential impact on PII redaction performance.
- What evidence would resolve it: A detailed analysis of ambiguous cases in the training data, experimental results comparing different word-to-digit normalization strategies, and an evaluation of the impact on PII redaction performance.
