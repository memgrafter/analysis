# ExeKGLib: Knowledge Graphs-Empowered Machine Learning Analytics

## Quick Facts

## Executive Summary
ExeKGLib is a Python library that leverages knowledge graphs (KGs) to enable users with minimal machine learning knowledge to construct and execute ML pipelines. By abstracting away library-specific details and providing a unified KG-based interface, ExeKGLib simplifies pipeline construction, enhances transparency, and ensures executability. The library supports various tasks such as data visualization, preprocessing, feature engineering, and ML modeling, making it suitable for domain experts, educators, and students.

## Method Summary
ExeKGLib uses knowledge graphs to represent ML pipelines, with a KG-based schema system defining data entities, tasks, and methods. Users construct pipelines by specifying high-level concepts, which are then converted into executable KGs and Python scripts. The library enforces compatibility rules by checking input data types against method requirements. Dynamic mapping from KG task IRIs to Python objects enables extensibility without modifying core execution code. The system utilizes rdflib and SPARQL for KG construction and execution, and integrates with matplotlib and scikit-learn for ML implementations.

## Key Results
- ExeKGLib enables users with coding skills and minimal ML knowledge to build ML pipelines
- The KG-based approach reduces learning overhead by abstracting library-specific details
- Dynamic IRI mapping allows for library extensibility without modifying core execution code

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Knowledge graphs enable ExeKGLib to ensure pipeline executability by modeling data flow and method compatibility.
- Mechanism: The KG schema defines object and datatype properties that link data entities to tasks and methods. ExeKGLib enforces compatibility rules by checking that input data types match method requirements before creating pipeline components.
- Core assumption: KG schema accurately captures all necessary compatibility constraints between data entities, tasks, and methods.
- Evidence anchors:
  - [section] "Throughout the process, the compatibility of the aforementioned KG components is ensured by ExeKGLib based on the KG schemata."
  - [abstract] "ExeKGLib relies on knowledge graphs to improve the transparency and reusability of the built ML workflows, and to ensure that they are executable"
- Break condition: Schema incompleteness or incorrect compatibility rules lead to false positives/negatives during pipeline validation.

### Mechanism 2
- Claim: KG-based pipeline representation simplifies learning for non-ML experts by abstracting library-specific details.
- Mechanism: Instead of requiring users to learn multiple library APIs, ExeKGLib provides a unified KG-based interface where users specify high-level concepts (data entities, tasks, methods) without dealing with library-specific syntax.
- Core assumption: The KG abstraction adequately represents all necessary ML operations while hiding implementation complexity.
- Evidence anchors:
  - [abstract] "ExeKGLib allows users with coding skills and minimal ML knowledge to build ML pipelines"
  - [section] "using our tool to solve a task reduces the overhead prior to the implementation, reduces the effort during the code development"
- Break condition: KG abstraction becomes too restrictive, preventing users from accessing necessary advanced functionality.

### Mechanism 3
- Claim: Dynamic mapping from KG task IRIs to Python objects enables extensibility without modifying core execution code.
- Mechanism: ExeKGLib parses KG task IRIs to retrieve type and properties, then dynamically instantiates corresponding Python objects using rdflib and SPARQL queries, allowing new methods to be added by extending schemas rather than core code.
- Core assumption: IRI naming conventions and property structures are sufficient to uniquely identify and instantiate correct Python implementations.
- Evidence anchors:
  - [section] "Based on the IRI of the next Task (owl:Individual), the Task's type and properties are retrieved and mapped dynamically to a Python object. Such mapping allows for extending the library without modifying the KG execution code."
  - [abstract] "ExeKGLib can be used by a wide range of users and in a variety of scenarios: from domain experts that want to do ML to teachers and students for teaching and learning ML"
- Break condition: Dynamic mapping fails when multiple Python implementations could match a single KG task type.

## Architecture Onboarding

- Component map:
  - User Input -> CSV Column Extraction -> Data Entity Creation -> Task/Method Addition -> KG Serialization
  - KG Parsing -> Task Traversal (ds:hasNextTask) -> Dynamic Python Object Mapping -> Method Invocation
  - CLI Interface (Typer) -> Pipeline Generation/Execution

- Critical path:
  1. User provides CSV and specifies pipeline steps
  2. ExeKGLib constructs executable KG with compatibility checks
  3. User executes KG via CLI or imports ExeKG module
  4. KG is parsed and tasks are executed sequentially

- Design tradeoffs:
  - Flexibility vs. Simplicity: KG abstraction simplifies usage but may limit advanced customization
  - Performance vs. Transparency: KG-based approach adds overhead but improves explainability
  - Extensibility vs. Complexity: Dynamic mapping enables extension but requires careful schema design

- Failure signatures:
  - Pipeline construction fails: Schema compatibility rules too strict or KG not properly constructed
  - Pipeline execution fails: Dynamic mapping fails to find matching Python implementation
  - Performance issues: KG parsing/construction overhead becomes significant for large pipelines

- First 3 experiments:
  1. Create a simple pipeline with one data entity, one task, and one method; verify KG construction and execution
  2. Add a second task to the pipeline; verify ds:hasNextTask linking works correctly
  3. Attempt to add an incompatible method to a task; verify compatibility checking prevents execution

**Low Confidence**: The extensibility claims are weakly supported. While the architecture suggests easy extension through schema modifications, there's no demonstration of adding new methods or adapting to emerging ML paradigms.
