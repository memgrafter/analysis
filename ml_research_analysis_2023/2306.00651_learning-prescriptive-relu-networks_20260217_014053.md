# Learning Prescriptive ReLU Networks

## Quick Facts
- arXiv ID: 2306.00651
- Source URL: https://arxiv.org/abs/2306.00651
- Authors: 
- Reference count: 40
- Primary result: P-ReLU achieves superior prescriptive accuracy compared to causal trees and optimal prescriptive trees while maintaining interpretability through equivalent hyperplane-split prescriptive trees

## Executive Summary
This work introduces Prescriptive ReLU Networks (P-ReLU), a piecewise linear neural network architecture designed to learn optimal treatment policies from observational data with discrete treatments. P-ReLU balances strong prescriptive performance with interpretability by partitioning the input space into disjoint convex polyhedra, where all instances in the same partition receive the same treatment. The network can be converted into an equivalent oblique prescriptive tree with hyperplane splits, providing clear decision rules for treatment assignment.

## Method Summary
P-ReLU is a neural network with ReLU activations that partitions the input space into disjoint convex polyhedra, where each partition receives a specific treatment. The network is trained using a combined loss function that optimizes both prediction accuracy and prescription accuracy, controlled by a hyperparameter μ. The architecture can be easily modified to incorporate prescriptive constraints through additional neurons that model the constraints. After training, P-ReLU can be converted into an interpretable oblique prescriptive tree with hyperplane splits by transforming the output layer to model pairwise treatment outcome differences.

## Key Results
- P-ReLU achieves superior prescriptive accuracy compared to causal trees, personalization trees, and optimal prescriptive trees on both synthetic and real-world datasets
- The model maintains interpretability through conversion to equivalent prescriptive trees with hyperplane splits
- P-ReLU can incorporate prescriptive constraints with minor architectural modifications while preserving performance
- The margin between P-ReLU and competing methods widens when there are more treatments

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The P-ReLU network partitions the input space into disjoint convex polyhedra, where all instances in the same partition receive the same treatment.
- Mechanism: By fixing an activation pattern on the hidden layers, the network degenerates into a linear model. Enumerating all feasible activation patterns partitions the input space into disjoint polyhedra. The output layer assigns treatments based on predicted outcomes.
- Core assumption: ReLU activation creates piecewise linear regions in the input space.
- Evidence anchors:
  - [abstract]: "P-ReLU partitions the input space into disjoint polyhedra, where all instances that belong to the same partition receive the same treatment"
  - [section]: "Theorem 3.1. P-ReLU network partitions the input space X into disjoint treatment polyhedra, where all instances that belong to the same polyhedron receive the same treatment."
- Break condition: If activation function is not piecewise linear or network is not trained to minimize combined error.

### Mechanism 2
- Claim: The P-ReLU network can be converted into an equivalent oblique prescriptive tree with hyperplane splits.
- Mechanism: Replacing the output layer with K(K-1)/2 ReLU neurons to model pairwise treatment differences creates a locally constant network equivalent to an oblique prescriptive tree.
- Core assumption: Locally constant networks are equivalent to oblique prescriptive trees.
- Evidence anchors:
  - [abstract]: "P-ReLU can be converted into an equivalent prescriptive tree with hyperplane splits for interpretability."
  - [section]: "Theorem 3.2. A P-ReLU network can be expressed as an equivalent oblique prescriptive tree."
- Break condition: If transformation to locally constant network is incorrect or equivalence doesn't hold.

### Mechanism 3
- Claim: The P-ReLU network can incorporate constraints with minor modifications to the architecture.
- Mechanism: Adding extra neurons that explicitly model constraints using a large value M to penalize excluded treatments when constraints are satisfied.
- Core assumption: Constraints can be modeled as linear inequalities on input features.
- Evidence anchors:
  - [abstract]: "P-ReLU can be easily modified to incorporate constraints."
  - [section]: "We consider prescriptive constraints of the form, if Ax > b then assign treatment that belongs in T."
- Break condition: If constraints are non-linear or M value is inappropriate.

## Architecture Onboarding

- Component map: Input layer → Hidden ReLU layers → Output layer (K neurons for K treatments)
- Critical path: Forward pass → Treatment assignment via min predicted outcome → Combined loss calculation → Backward pass with gradient descent
- Design tradeoffs:
  - Expressiveness vs. interpretability: Larger networks more expressive but less interpretable
  - Prescription accuracy vs. prediction accuracy: Trade-off controlled by μ hyperparameter
  - Computational efficiency vs. constraint satisfaction: Constraints increase computational complexity
- Failure signatures:
  - Poor prescription accuracy: Network not learning optimal treatment assignment
  - Overfitting: Network memorizing training data instead of learning generalizable patterns
  - Constraint violation: Network not satisfying prescribed constraints

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does P-ReLU performance scale with increasing number of treatments (K) beyond what was tested?
- Basis in paper: [explicit] The paper notes that "the margin between P-ReLU and other methods widens when there are more treatments" but doesn't explore this fully.
- Why unresolved: Experiments only tested up to K=3 treatments, leaving scaling behavior for larger K unexplored.
- What evidence would resolve it: Experiments testing P-ReLU with K>3 treatments on various datasets would reveal whether performance advantage continues to grow with K.

### Open Question 2
- Question: Can the P-ReLU framework be extended to handle continuous treatment spaces?
- Basis in paper: [inferred] Paper focuses exclusively on discrete treatments, but piecewise linear nature suggests potential for continuous treatment extension.
- Why unresolved: Current formulation and proofs are specific to discrete treatments, with no exploration of continuous treatment generalization.
- What evidence would resolve it: Modified P-ReLU architecture outputting continuous values with theoretical analysis for continuous treatment settings.

### Open Question 3
- Question: What is the optimal trade-off between P-ReLU network complexity and interpretability for different application domains?
- Basis in paper: [explicit] Paper states "one of the key advantages of P-ReLU is that it can achieve a balance between strong prescriptive performance and interpretability" but doesn't provide domain-specific guidelines.
- Why unresolved: Experiments use single network architecture (5 layers, 100 neurons) without systematically exploring performance-interpretability trade-off.
- What evidence would resolve it: Systematic study varying P-ReLU architecture across multiple domains with different interpretability requirements, measuring both performance and tree complexity.

## Limitations
- Approach relies on ignorability assumption which may not hold in many real-world observational datasets with unobserved confounders
- Interpretability benefits depend on network depth and width, with deeper networks potentially becoming less interpretable
- Constraint incorporation using big-M formulation may face numerical stability issues with numerous or complex constraints

## Confidence
- High: Theoretical foundation of P-ReLU partitioning input space is well-established through Theorem 3.1 with rigorous proofs
- Medium: Empirical performance claims supported by experiments on synthetic and real-world datasets, though optimal hyperparameter settings require further exploration
- Medium: Conversion mechanism from P-ReLU to interpretable prescriptive trees is theoretically sound but practical implementation details are not fully specified
