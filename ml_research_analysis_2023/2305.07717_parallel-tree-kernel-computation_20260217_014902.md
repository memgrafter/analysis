# Parallel Tree Kernel Computation

## Quick Facts
- arXiv ID: 2305.07717
- Source URL: https://arxiv.org/abs/2305.07717
- Reference count: 3
- Primary result: Parallel implementation achieves 40.75× to 62.96× speedup (average 50.89×) for subtree kernel computation

## Executive Summary
This paper presents a parallel implementation of subtree kernel computation using the MapReduce paradigm. Building on prior work that reduces subtree kernel computation to intersection of rooted weighted tree automata (RWTA), the authors develop parallel algorithms for both RWTA construction and intersection. The approach distributes subtree counting and intersection operations across map and reduce tasks, achieving substantial performance improvements over sequential implementations. The method was evaluated on synthetic tree datasets with varying alphabet sizes, tree depths, and dataset sizes ranging from 1.5GB to 7GB.

## Method Summary
The method implements parallel subtree kernel computation through two MapReduce phases: RWTA construction and RWTA intersection. In the construction phase, mapper tasks extract tree prefixes and emit <subtree, 1> pairs, while reducers aggregate counts to compute subtree weights. The intersection phase maps both RWTA structures, emitting <subtree, (1, weight)> pairs, with reducers identifying common subtrees (Presences=2) and multiplying weights. The final kernel value is computed by summing the weights of the intersected RWTA. The approach leverages data parallelism inherent in subtree counting and intersection operations.

## Key Results
- Parallel algorithm achieves absolute acceleration factors ranging from 40.75× to 62.96× across different datasets
- Average speedup of 50.89× compared to sequential implementation
- Performance advantage increases with larger alphabet sizes due to reduced prefix overlap
- Results demonstrate significant computational benefits for machine learning applications using structured tree data

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Parallel RWTA construction via MapReduce achieves substantial speedup by distributing subtree counting across nodes.
- Mechanism: The MapReduce paradigm splits prefix extraction into map tasks that emit <subtree, 1> pairs, then reduces sum occurrences to compute weights in parallel.
- Core assumption: Subtree occurrences are independent and can be counted in parallel without synchronization.
- Evidence anchors:
  - [abstract] "Our approach relies on the nature of the data parallelism source inherent in this computation by deploying the MapReduce paradigm."
  - [section 3.2] "The Map function splits the prefixes list into subtrees... distributes the key-value pairs as follows: <key, 1>..."
- Break condition: If the dataset has very high subtree overlap (small alphabet), map phase generates excessive duplicate keys causing reducer bottlenecks.

### Mechanism 2
- Claim: Parallel RWTA intersection scales well because common subtrees naturally partition across reducers.
- Mechanism: Map phase emits <subtree, (1, weight)> from both RWTA inputs; reducers detect subtrees present in both (Presences=2) and multiply weights.
- Core assumption: Intersection only requires checking subtree presence in both automata, which is naturally parallelizable.
- Evidence anchors:
  - [section 3.3] "Map function distributes the key-value pairs as follows: <subtree, (1, weight)>... sends the key-value pairs to reducers by key"
  - [section 2.5.2] "if any state q is present in AY then it is added to the automaton A(X,Y)"
- Break condition: When intersection size is very small relative to input sizes, parallel overhead dominates speedup.

### Mechanism 3
- Claim: Performance advantage increases with larger alphabet sizes due to reduced prefix overlap.
- Mechanism: Larger alphabets create more unique subtrees per tree, increasing parallelism granularity and reducing contention in map/reduce phases.
- Core assumption: Alphabet size directly affects subtree diversity and thus parallel work distribution.
- Evidence anchors:
  - [section 4.2] "our parallel algorithm performs better when the alphabet size is larger... as a smaller alphabet size implies a higher frequency of common prefixes"
  - [section 4.1] "We have considered into account mainly three criteria: i) the alphabet size (varying between 2 and 12)"
- Break condition: If alphabet is extremely large, memory overhead for storing all unique subtrees may become prohibitive.

## Architecture Onboarding

- Component map:
  - Master node -> Mapper containers -> Reducer containers -> Output collector
  - Distributed File System stores input tree datasets and intermediate map outputs

- Critical path:
  1. Load tree datasets into HDFS
  2. Mapper phase: Extract prefixes, emit key-value pairs
  3. Shuffle/sort: Group by subtree keys
  4. Reducer phase: Compute weights and intersection
  5. Final aggregation: Sum weights for kernel result

- Design tradeoffs:
  - Memory vs. parallelism: Larger mappers can process more trees but reduce parallelism
  - Shuffle overhead: Too many unique subtrees increases network traffic
  - Fault tolerance: MapReduce framework handles node failures automatically

- Failure signatures:
  - Slow reducers: Indicates skewed data distribution (some subtrees appear much more frequently)
  - Task timeouts: May indicate mapper/reducers are processing trees that are too large
  - Memory errors: Suggests insufficient heap space for storing intermediate results

- First 3 experiments:
  1. Run on smallest dataset (D1) with 2 nodes to verify basic functionality and measure baseline speedup
  2. Scale to medium dataset (D2) with 6 nodes to test performance scaling and identify bottlenecks
  3. Test with varying alphabet sizes (D1s vs D1) to validate the relationship between alphabet diversity and speedup

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the parallel algorithm's performance scale with different cluster sizes and configurations beyond the 6-node setup used in the experiments?
- Basis in paper: [explicit] The paper mentions that "more large datasets have to be generated and tested to confirm the output-sensitive results of our solutions" and "one can investigate different cluster architectures in order to give more insights and recommendations on the cluster parameters tuning."
- Why unresolved: The current experiments only tested the parallel algorithm on a fixed cluster configuration with 6 nodes (1 master + 5 slaves). The scalability with respect to cluster size, node specifications, and network configurations remains unexplored.
- What evidence would resolve it: Comprehensive benchmarking across multiple cluster configurations with varying numbers of nodes, node specifications, and network topologies would provide empirical evidence of scalability patterns and identify optimal cluster configurations for different dataset sizes.

### Open Question 2
- Question: What is the impact of alphabet size on the number of common prefixes between trees, and how does this relationship affect the algorithm's performance characteristics?
- Basis in paper: [explicit] The paper notes that "our parallel algorithm performs better when the alphabet size is larger" and mentions that "a smaller alphabet size implies a higher frequency of common preﬁxes."
- Why unresolved: While the paper observes a correlation between alphabet size and performance, it doesn't provide quantitative analysis of how the number of common prefixes scales with alphabet size, nor does it establish a precise relationship between prefix frequency and computational complexity.
- What evidence would resolve it: Detailed analysis of prefix frequency distributions across different alphabet sizes, coupled with performance measurements that isolate the effect of prefix sharing, would clarify the underlying relationship and enable performance predictions for new datasets.

### Open Question 3
- Question: How can the parallel RWTA construction and intersection algorithms be generalized to support other tree kernel variants like RootedTree and SubSequenceTree kernels?
- Basis in paper: [explicit] The paper states that "three main future works are envisaged" including devising algorithms that "generalise the computation of others kernels such RootedTree, and SubSequenceTree."
- Why unresolved: While the paper demonstrates success with SubTree kernels, the generalization to other kernel types requires handling more complex weight computations and potentially different intersection operations, which are not addressed in the current work.
- What evidence would resolve it: Development and validation of parallel algorithms for RootedTree and SubSequenceTree kernels, including analysis of their computational complexity and performance characteristics compared to the SubTree kernel implementation, would demonstrate the feasibility of generalization.

## Limitations
- Experiments rely entirely on synthetic datasets with controlled parameters, limiting generalizability to real-world tree structures
- Sequential implementation serves as the only baseline, without comparison to other parallel approaches or GPU-accelerated methods
- Memory usage and scalability beyond the tested 7GB dataset size remain unexamined
