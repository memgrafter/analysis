# X-Former: In-Memory Acceleration of Transformers

## Quick Facts
- **arXiv ID**: 2303.07470
- **Source URL**: https://arxiv.org/abs/2303.07470
- **Reference count**: 40
- **Primary result**: Hybrid NVM+CMOS accelerator achieving up to 85x latency and 7.5x energy improvements over GPU for transformer inference

## Executive Summary
X-Former addresses the challenge of efficiently processing large Transformer models by combining non-volatile memory (NVM) and CMOS processing elements in a hybrid architecture. The key innovation is to map static matrix multiplications to NVM tiles while using CMOS tiles for dynamic operations, reducing write latency and energy consumption. A sequence blocking dataflow is introduced to overlap computations and reduce intermediate activation sizes, improving hardware utilization. The approach is evaluated on BERT models, demonstrating significant improvements over both GPU and state-of-the-art NVM accelerators.

## Method Summary
X-Former is a hybrid in-memory hardware accelerator that combines ReRAM crossbars for static weight storage with CMOS tiles for dynamic operations. The architecture splits transformer computations into MVMStatic (where at least one operand remains constant) and MVMDynamic (where both operands change) operations. Static weights are mapped to NVM tiles in the Projection Engine, while dynamic operations are handled by the CMOS-based Attention Engine. A sequence blocking dataflow divides input sequences into smaller blocks, processing them in a pipelined manner to overlap computations and reduce intermediate activation storage from O(SL²) to O(SB²).

## Key Results
- Achieves up to 85x latency improvement and 7.5x energy reduction compared to GTX 1060 GPU
- Delivers up to 10.7x latency and 4.6x energy improvements over state-of-the-art NVM accelerator
- Maintains application-level accuracy while significantly improving hardware utilization through sequence blocking

## Why This Works (Mechanism)

### Mechanism 1
- **Claim**: 85x latency improvement by splitting operations into NVM tiles for static matrix multiplications and CMOS tiles for dynamic ones
- **Mechanism**: Static weights in transformer encoder layers (MVMStatic) are mapped to resistive crossbars in the Projection Engine, eliminating repeated reprogramming overhead. Dynamic operations (MVMDynamic) are handled by the CMOS-based Attention Engine with low write latency and high endurance
- **Core assumption**: Static weights do not change between inference batches
- **Evidence anchors**: Abstract states static matrix multiplications are mapped to NVM tiles; section classifies workloads into MVMStatic and MVMDynamic; corpus provides weak evidence
- **Break condition**: Frequent retraining or online weight updates would require reprogramming, negating NVM benefits

### Mechanism 2
- **Claim**: Sequence blocking dataflow reduces intermediate activation storage from O(SL²) to O(SB²)
- **Mechanism**: Input sequence is divided into smaller blocks of length SB, with Projection and Attention Engines operating on these blocks in a pipelined manner to keep both engines busy and reduce peak memory footprint
- **Core assumption**: Attention computation for a word depends only on the entire sequence, so block processing doesn't change final output
- **Evidence anchors**: Abstract mentions sequence blocking overlaps computations; section describes dividing input sequence into smaller blocks; corpus provides weak evidence
- **Break condition**: If SB is too large, intermediate activation benefit disappears; if too small, parallelization gains diminish

### Mechanism 3
- **Claim**: Hybrid NVM+CMOS design balances high storage density with high endurance
- **Mechanism**: ReRAM crossbars provide high-density storage for static weights in Projection Engine, while 8T-SRAM arrays in Attention Engine handle dynamic operations with low write energy and high endurance
- **Core assumption**: MVMDynamic operations exceed NVM endurance limits, requiring CMOS
- **Evidence anchors**: Abstract mentions NVM limited endurance (106-109 writes); section discusses high write latency and energy when using NVM for Transformers; corpus confirms NVM endurance challenges
- **Break condition**: If NVM endurance improves by orders of magnitude, hybrid split may become unnecessary

## Architecture Onboarding

- **Component map**: Embedding lookup → Projection Engine (NVM tiles for static weights) → Attention Engine (CMOS tiles for dynamic ops) → Projection Engine (feed-forward) → Repeat for each encoder layer

- **Critical path**: 1) Embedding lookup → Projection Engine (static weights) 2) Query/Key/Value generation → Attention Engine (dynamic ops) 3) Attention scores and final output → Projection Engine (feed-forward) 4) Repeat for each encoder layer

- **Design tradeoffs**:
  - NVM density vs. CMOS endurance: High density enables on-chip storage but CMOS needed for frequent dynamic updates
  - Sequence block size vs. hardware utilization: Larger blocks reduce overhead but increase intermediate memory; smaller blocks improve overlap but add scheduling complexity
  - ADC resolution vs. accuracy: Lower resolution saves energy but introduces more analog noise, impacting model accuracy

- **Failure signatures**:
  - Low utilization in one engine: Indicates imbalance in static/dynamic operation distribution or suboptimal block size
  - High energy in ADC: Suggests ADC resolution too high for required precision or inefficient bit-slicing
  - Accuracy drop > 1%: Likely due to accumulated analog errors in NVM crossbar computations

- **First 3 experiments**:
  1. Profile energy and latency breakdown with only Projection Engine active (static ops) to verify NVM benefits
  2. Profile with only Attention Engine active (dynamic ops) to verify CMOS efficiency and ADC overhead
  3. Sweep sequence block size from 32 to 256 on fixed benchmark to find optimal point for hardware utilization and intermediate memory

## Open Questions the Paper Calls Out

### Open Question 1
- **Question**: What is the maximum sequence length that X-Former can efficiently process without significant degradation in performance?
- **Basis in paper**: Inferred from discussion of sequence length impact on performance and NVM write endurance limitations
- **Why unresolved**: Paper doesn't provide specific maximum sequence length beyond which performance degrades significantly
- **What evidence would resolve it**: Experiments with varying sequence lengths showing performance degradation points

### Open Question 2
- **Question**: How does the accuracy of X-Former compare to other Transformer accelerators under different process variations?
- **Basis in paper**: Explicit discussion of process variation impact on X-Former accuracy without comparative analysis
- **Why unresolved**: Only provides accuracy results for X-Former under different process variations, not comparative data
- **What evidence would resolve it**: Comparison of accuracy under different process variations between X-Former and other Transformer accelerators

### Open Question 3
- **Question**: What is the impact of using different NVM technologies on the performance and energy efficiency of X-Former?
- **Basis in paper**: Explicit mention that NVM technology choice affects write latency and energy/bit
- **Why unresolved**: No detailed analysis of different NVM technologies' impact on X-Former's performance and energy efficiency
- **What evidence would resolve it**: Experiments with different NVM technologies showing their impact on performance and energy efficiency

### Open Question 4
- **Question**: How does the sequence blocking dataflow affect the accuracy of X-Former?
- **Basis in paper**: Explicit mention that sequence blocking causes no loss in application-level accuracy without detailed analysis
- **Why unresolved**: Only states no accuracy loss without detailed impact analysis
- **What evidence would resolve it**: Detailed analysis of sequence blocking's impact on accuracy compared to traditional dataflow

## Limitations

- The static/dynamic operation classification assumes transformer models remain unchanged between inference batches, which may not hold for models with frequent updates
- The sequence blocking optimization requires careful parameter tuning and may degrade when accounting for scheduling overhead in real hardware
- Comparative performance metrics against GTX 1060 GPU and state-of-the-art NVM accelerator may not reflect current hardware realities

## Confidence

- **High confidence**: The core mechanism of separating static and dynamic operations is well-founded and directly addresses known NVM limitations
- **Medium confidence**: The sequence blocking dataflow shows promise but requires careful parameter tuning and depends on specific implementation details
- **Low confidence**: Comparative performance metrics may be overstated if newer GPU architectures or alternative NVM techniques are not considered
