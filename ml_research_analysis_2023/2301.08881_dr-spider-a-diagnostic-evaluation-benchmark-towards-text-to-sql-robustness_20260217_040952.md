# Dr.Spider: A Diagnostic Evaluation Benchmark towards Text-to-SQL Robustness

## Quick Facts
- arXiv ID: 2301.08881
- Source URL: https://arxiv.org/abs/2301.08881
- Reference count: 24
- Key outcome: Introduces Dr.Spider benchmark with 17 perturbation types that reveals SOTA text-to-SQL models suffer significant performance drops (14.0% overall, 50.7% on most challenging perturbation)

## Executive Summary
Dr.Spider is a comprehensive benchmark designed to evaluate the robustness of text-to-SQL models against various task-specific perturbations. The benchmark introduces 17 types of perturbations targeting database schemas, natural language questions, and SQL queries, including both semantic-preserving and semantic-changing perturbations. Through systematic evaluation of state-of-the-art models, the authors demonstrate that even the most robust models suffer significant performance degradation when faced with these perturbations, highlighting the need for improved robustness in text-to-SQL systems.

## Method Summary
The authors create Dr.Spider by systematically perturbing the Spider development set across three dimensions: database schemas (DB), natural language questions (NLQ), and SQL queries (SQL). They employ large pre-trained language models to generate diverse natural language paraphrases for NLQ perturbations, addressing the limitation of previous rule-based approaches. The benchmark is evaluated using execution accuracy (EX) and exact set match (EM) metrics, with relative robustness accuracy introduced to account for baseline performance differences between models. The study tests five state-of-the-art text-to-SQL models (RATSQL, GRAPPA, SMBOP, T5-family, Picard) to assess their robustness across different perturbation types.

## Key Results
- SOTA models experience 14.0% average performance drop across all perturbations
- Most challenging perturbation causes 50.7% performance drop in the best model
- DB schema perturbations (column-synonym, column-carrier) cause the highest performance degradation
- PLM-generated NLQ perturbations reveal weaknesses in models' semantic understanding capabilities

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Text-to-SQL models fail on semantic-preserving perturbations because they rely on spurious lexical matching between natural language questions and database schema rather than capturing true semantic intent.
- Mechanism: When a column name is replaced with a synonym (e.g., "winner_name" → "champ_name"), the model fails to recognize that the semantic meaning remains the same, leading to incorrect SQL predictions.
- Core assumption: The model's performance depends heavily on exact string matching between NLQ tokens and DB schema elements.
- Evidence anchors:
  - [abstract] "However, recent studies reveal that text-to-SQL models are vulnerable to task-specific perturbations."
  - [section 1] "Previous studies...have found spurious patterns in the Spider...such as NLQ tokens closely matching DB schemas, leading models to rely on lexical matching between NLQs and DB schemas for prediction instead of capturing the semantics that the task is intended to test."
- Break condition: If the model uses semantic representations that are invariant to lexical variations, this mechanism would break down.

### Mechanism 2
- Claim: Large pre-trained language models (PLMs) can generate more diverse and natural language perturbations compared to rule-based methods, leading to more comprehensive robustness evaluation.
- Mechanism: By prompting PLMs like OPT with in-context examples, the system can generate paraphrases that capture various linguistic phenomena (e.g., keyword synonyms, column carriers) that rule-based methods miss.
- Core assumption: PLMs can simulate human-like paraphrasing behaviors and generate diverse linguistic variations.
- Evidence anchors:
  - [section 3.2] "To tackle this issue, we generate paraphrases with large PLM and prompt it with crowdsourcing paraphrases in each category."
  - [section 4] "Our framework involves the following phases: (1) Crowdsourcing annotators... (2) Task experts review... (3) A pretrained language model (PLM) generates categorized paraphrase perturbations..."
- Break condition: If the PLM fails to capture the semantic nuances of the task or generates non-factual paraphrases.

### Mechanism 3
- Claim: The relative robustness accuracy metric provides a more accurate comparison of model robustness by accounting for the baseline performance on pre-perturbation data.
- Mechanism: Instead of just comparing post-perturbation accuracy, this metric calculates the ratio of correct predictions on both pre- and post-perturbation data, providing a more nuanced view of how much performance degrades due to perturbations.
- Core assumption: Absolute performance drops can be misleading if the baseline performance varies significantly between models.
- Evidence anchors:
  - [section 4] "While the post-perturbation accuracy measures the absolute performance of a model on perturbation data, relative robustness accuracy is to evaluate the regression rate of models against perturbation, which is more precise to compare the robustness of models by considering their performances on the pre-perturbation data."
- Break condition: If all models have similar baseline performance, the relative metric would provide similar insights to absolute accuracy.

## Architecture Onboarding

- Component map: Dr.Spider benchmark -> SOTA text-to-SQL models -> Performance evaluation pipeline -> Results analysis module
- Critical path: Generate perturbations → Apply perturbations to test data → Evaluate model performance → Analyze robustness results
- Design tradeoffs: Using large PLMs for perturbation generation provides diversity but increases computational cost; rule-based methods are faster but less comprehensive.
- Failure signatures: Models showing high accuracy on original data but significant drops on perturbed data indicate reliance on spurious patterns; consistent performance across perturbations suggests true semantic understanding.
- First 3 experiments:
  1. Evaluate a baseline text-to-SQL model on the original Spider dataset to establish performance benchmarks.
  2. Apply DB synonym perturbations and measure the model's robustness against schema variations.
  3. Use PLM-generated NLQ paraphrases to test the model's ability to handle linguistic variations in natural language questions.

## Open Questions the Paper Calls Out

### Open Question 1
- Question: What are the key differences between top-down and bottom-up decoders in terms of their robustness to NLQ and DB perturbations?
- Basis in paper: [explicit] The paper compares the robustness of GRAPPA (top-down decoder) and SMBOP (bottom-up decoder) on DB, NLQ, and SQL perturbations.
- Why unresolved: The paper provides a qualitative analysis but lacks a quantitative comparison of the robustness of top-down and bottom-up decoders on different perturbation types.
- What evidence would resolve it: A detailed quantitative analysis comparing the robustness of top-down and bottom-up decoders on each perturbation type, including a breakdown of the performance on different SQL clauses.

### Open Question 2
- Question: How does the entity linking feature impact the robustness of text-to-SQL models to different types of perturbations?
- Basis in paper: [explicit] The paper compares the robustness of T5-3B models with and without entity linking on column-value and value-synonym perturbations.
- Why unresolved: The paper only examines the impact of entity linking on a limited set of perturbation types. It is unclear how entity linking affects robustness to other perturbation types, such as keyword-synonym or column-carrier.
- What evidence would resolve it: A comprehensive analysis of the impact of entity linking on the robustness of text-to-SQL models to all perturbation types, including a breakdown of the performance on different SQL clauses.

### Open Question 3
- Question: What are the limitations of the current approach for generating NLQ perturbations using large language models?
- Basis in paper: [inferred] The paper relies on large language models to generate NLQ perturbations, but it acknowledges the potential for generating toxic language and the need for expert review.
- Why unresolved: The paper does not provide a detailed analysis of the limitations of the current approach for generating NLQ perturbations, such as the potential for generating ungrammatical or nonsensical questions.
- What evidence would resolve it: A systematic evaluation of the quality of the generated NLQ perturbations, including an analysis of the types of errors and inconsistencies that may arise from the current approach.

## Limitations
- The benchmark is limited to the Spider dataset's academic database domain and may not generalize to enterprise databases.
- Evaluation metrics (execution accuracy and exact set match) assume perfect SQL execution environments and don't capture semantic equivalence with different syntax.
- PLM-generated perturbations depend on prompt engineering quality and may contain systematic biases affecting robustness evaluation.

## Confidence
- High confidence: The claim that text-to-SQL models suffer significant performance drops on semantic-preserving perturbations (14.0% overall drop, 50.7% on most challenging perturbation) is well-supported by the experimental results across multiple SOTA models.
- Medium confidence: The claim that large PLMs can generate more diverse and natural perturbations compared to rule-based methods is supported by the methodology but would benefit from direct comparison studies.
- Medium confidence: The assertion that relative robustness accuracy provides more accurate model comparison by accounting for baseline performance is theoretically sound but would benefit from additional ablation studies.

## Next Checks
1. **Cross-domain validation**: Evaluate the robustness of text-to-SQL models trained on Dr.Spider against completely different database domains (e.g., healthcare, finance) to assess generalizability beyond the academic domain of Spider.

2. **Human evaluation of perturbations**: Conduct human studies to verify that the PLM-generated perturbations are indeed natural and preserve semantic intent as claimed, particularly for the more complex perturbation types like column-carrier and column-value.

3. **Model architecture ablation**: Systematically test different model components (schema linking, encoder-decoder architecture, pre-training objectives) to identify which architectural choices contribute most to robustness against specific perturbation types, beyond the current breakdown analysis.
