# Can a Frozen Pretrained Language Model be used for Zero-shot Neural Retrieval on Entity-centric Questions?

## Quick Facts
- arXiv ID: 2303.05153
- Source URL: https://arxiv.org/abs/2303.05153
- Authors: 
- Reference count: 13
- Zero-NeR method achieves comparable performance to BM25 and SPAR on entity-centric questions using a frozen LUKE model.

## Executive Summary
This paper investigates whether a frozen pretrained language model can be used for zero-shot neural retrieval on entity-centric questions. The proposed Zero-NeR method leverages contextualized keys generated by a frozen LUKE model for named entities in passages, without any fine-tuning. By using multiple retrieval keys per passage and max-pooling over cosine similarities, Zero-NeR significantly improves recall, especially when entity names consist of common words. The method outperforms conventional DPRs and achieves comparable performance to BM25 and SPAR on the EntityQuestions dataset in the Wikipedia domain.

## Method Summary
Zero-NeR uses a frozen LUKE model for named entity recognition and embedding generation. For each passage, it extracts named entities and the title, generating contextualized embeddings for each as retrieval keys. Queries are processed similarly: entities are extracted and embedded with their context. Retrieval is performed by computing cosine similarities between query embeddings and all keys, then max-pooling the scores per passage. No fine-tuning is performed on the LUKE model. The method is evaluated on the EntityQuestions dataset, using top-20 retrieval accuracy (Recall@20) as the primary metric.

## Key Results
- Zero-NeR outperforms conventional DPR models and achieves comparable performance to BM25 and SPAR on entity-centric questions in the Wikipedia domain.
- The contextualized keys significantly improve recall, especially when entity names consist of common words.
- Using multiple retrieval keys per passage, combined with max-pooling, substantially improves retrieval accuracy.

## Why This Works (Mechanism)

### Mechanism 1
Named entity embeddings from a frozen LUKE model act as more discriminative retrieval keys than BM25 term matches when entities consist of common words. The LUKE encoder produces span-level contextualized representations that capture entity semantics regardless of term frequency. These embeddings are used as multiple retrieval keys per passage, and cosine similarity over these keys with max-pooling yields relevance scores. The core assumption is that the pretrained LUKE model has learned rich entity representations during pretraining that transfer directly to retrieval without fine-tuning.

### Mechanism 2
Using multiple retrieval keys per passage improves recall, especially when passages contain multiple relational facts about different entities. Each passage generates i+1 keys (i entity names plus title). Relevance scores are computed per key and max-pooled, allowing retrieval even if only one key matches the query. The core assumption is that passages with multiple entities provide complementary retrieval signals; max-pooling over keys captures the strongest match.

### Mechanism 3
Conditioning entity embeddings on full sentence context (not just entity spans) preserves semantic alignment and improves retrieval accuracy. LUKE's entity-aware self-attention computes entity embeddings conditioned on the full input text, capturing surrounding context. The core assumption is that entity semantics depend on sentence context; embeddings without context lose discriminative power.

## Architecture Onboarding

- **Component map:**
  NER module (LUKE model) → extracts entities from queries and passages
  Frozen LUKE encoder → generates contextualized embeddings for entities and titles
  Index: (passage_id, key_id) → embedding
  Query processor: extract entity → embed with context → score against all keys of each passage
  Max-pooling aggregator → single relevance score per passage
  Top-k selector → final retrieved passages

- **Critical path:**
  NER extraction → embedding generation → similarity scoring → max-pooling → top-k retrieval

- **Design tradeoffs:**
  - No fine-tuning → fast deployment, but relies entirely on pretraining quality
  - Multiple keys → higher recall, but increased storage and computation
  - Context conditioning → better embeddings, but requires full text input during inference

- **Failure signatures:**
  - Low recall when entity extraction fails or returns incorrect spans
  - Poor performance on rare entities due to sparse representation in pretraining
  - Suboptimal when passages lack named entities (few keys per passage)

- **First 3 experiments:**
  1. Verify entity extraction quality on a small sample of EQ questions and passages.
  2. Test retrieval with single vs. multiple keys on a subset of passages to confirm max-pooling benefit.
  3. Compare IDF-dependent retrieval accuracy across BM25, DPR, and Zero-NeR on author (P50) questions.

## Limitations
- Reliance on the quality of the frozen LUKE model's entity representations without any fine-tuning.
- Evaluation limited to the Wikipedia domain and entity-centric questions, restricting generalizability.
- Computational cost of generating and storing multiple contextualized embeddings per passage is not addressed.

## Confidence
**High Confidence:**
- The proposed Zero-NeR method outperforms conventional DPR models and achieves comparable performance to BM25 and SPAR on entity-centric questions in the Wikipedia domain.
- The contextualized keys lead to strong improvements compared to BM25 when entity names consist of common words.

**Medium Confidence:**
- The use of multiple retrieval keys per passage significantly impacts retrieval accuracy, particularly when passages contain multiple relational facts about different entities.
- Conditioning entity embeddings on full sentence context preserves semantic alignment and improves retrieval accuracy.

**Low Confidence:**
- The claim that Zero-NeR is a viable zero-shot baseline for dense retrievers in specialized domains, as the evaluation is limited to Wikipedia and entity-centric questions.

## Next Checks

2. **Single vs. Multiple Keys:** Conduct experiments on a subset of passages to quantify the impact of using single versus multiple retrieval keys per passage, confirming the benefit of max-pooling over keys.

3. **IDF-Dependent Performance:** Compare retrieval accuracy across BM25, DPR, and Zero-NeR on entity-centric questions where the entity names have varying IDF values, especially focusing on author (P50) questions to validate the advantage of contextualized keys for common-word entities.
