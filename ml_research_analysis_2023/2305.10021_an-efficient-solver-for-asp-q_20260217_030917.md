# An efficient solver for ASP(Q)

## Quick Facts
- arXiv ID: 2305.10021
- Source URL: https://arxiv.org/abs/2305.10021
- Reference count: 13
- Key outcome: pyqasp outperforms qasp on known benchmarks and compares favorably with stable-unstable semantics implementation

## Executive Summary
This paper presents pyqasp, a new solver for Answer Set Programming with Quantifiers (ASP(Q)) that builds on the ideas of the previous qasp solver. The key contributions include exploiting the well-founded semantics to simplify ASP(Q) programs, identifying a natural syntactic fragment of ASP(Q) programs that can be directly translated to QBF in Conjunctive Normal Form (CNF), and implementing an algorithm selection strategy that combines several QBF-solving back-ends to further increase performance. Experimental analysis shows that pyqasp outperforms qasp on known benchmarks and compares favorably with the implementation of stable-unstable semantics.

## Method Summary
The pyqasp solver translates ASP(Q) programs into QBF formulas, which are then evaluated by QBF solvers. The implementation includes three main optimizations: well-founded semantics simplification to reduce the search space, direct CNF encoding for a syntactic fragment of ASP(Q) programs called Guess&Check, and an algorithm selection strategy that predicts the best QBF solver based on program features. The solver can be configured with different grounders (gringo or iDLV) and QBF back-ends (RareQS, DepQBF, Quabs), with an automatic selection mechanism based on syntactic features.

## Key Results
- pyqasp outperforms qasp on known benchmarks across multiple problem domains
- Well-founded semantics simplification reduces formula size and improves performance for programs where it applies
- Direct CNF encoding for Guess&Check programs produces smaller formulas than standard encoding methods
- Algorithm selection strategy achieves 98% accuracy on training data and improves overall performance

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Well-founded semantics simplification reduces the search space by removing rules that are trivially satisfied in all stable models.
- Mechanism: The residual program R(P) is obtained by removing rules with false bodies w.r.t. the well-founded model W and deleting literals from the bodies of the remaining rules. This produces smaller CNF formulas with fewer clauses and literals.
- Core assumption: The well-founded model W is a subset of all stable models M, so any rule removed from P in creating R(P) will be satisfied in all stable models of P.
- Evidence anchors:
  - [abstract]: "exploiting the well-founded semantics to simplify ASP(Q) programs"
  - [section 3]: "Proposition 1 Given a program P and its well-founded model W, AS(P ) = AS(R(P ))"
- Break condition: If the well-founded model W = ∅ for every program, then R(P) = P and no simplification occurs.

### Mechanism 2
- Claim: Guess&Check programs can be directly encoded in CNF without requiring Tseytin transformation.
- Mechanism: For Guess&Check programs partitioned into GP (choice rules) and CP (stratified with constraints), the answer sets can be characterized as M = MG ∪ MC where MG ∈ AS(GP) and MC ∈ AS(CP ∪ fix GP(MG)). This modular structure allows direct CNF encoding.
- Core assumption: The interface atoms between GP and CP are defined only in GP, not in CP, ensuring the modularity property holds.
- Evidence anchors:
  - [section 4]: "Deﬁnition 3 An ASP program P is Guess&Check if it can be partitioned into two subprograms GP , Guess,CP , Check"
  - [section 4]: "Proposition 6 Let P be a Guess&Check program then M ∈ AS(P ) iﬀ there exists M′ ∈ AS(GP ) such that M =M′ ∪W and W ∈ AS(CP ∪fix GP (M′))"
- Break condition: If the program cannot be partitioned into GP and CP satisfying the required properties, then the direct CNF encoding cannot be applied.

### Mechanism 3
- Claim: Algorithm selection automatically combines several QBF-solving back-ends to increase performance across different problem domains.
- Mechanism: pyqasp implements an algorithm selection strategy based on syntactic program features (number of quantifiers, existential/universal atoms count, etc.) using random forest classification to predict the best QBF solver for each instance.
- Core assumption: The syntactic features of ASP(Q) programs are predictive of which QBF solver will perform best on that instance.
- Evidence anchors:
  - [section 5.2]: "pyqasp implements an automatic algorithm selection strategy, devised according to the methodology employed in the ME-ASP multi-engine ASP solver"
  - [section 5.2]: "we measured some syntactic program features... and split in 30% test set (329 instances) and 70% training set (765 instances), obtaining: 98% accuracy"
- Break condition: If the training data does not represent the problem domain well, the classifier may select suboptimal solvers.

## Architecture Onboarding

- Component map:
  Parser -> Rewriting Module -> Well-founded Module -> CNF Encoder Module -> QBF Builder -> Solver Wrappers -> Algorithm Selector

- Critical path:
  1. Parse input ASP(Q) program
  2. Apply well-founded simplification (if enabled)
  3. Identify and rewrite Guess&Check programs (if applicable)
  4. Convert each subprogram to CNF
  5. Build QBF formula with appropriate quantifiers
  6. Select QBF solver using algorithm selection
  7. Execute QBF solver and return result

- Design tradeoffs:
  - Memory vs. Performance: pyqasp processes subprograms sequentially rather than caching the entire program, trading some computational overhead for reduced memory usage
  - Encoding Complexity: The well-founded simplification can fail to derive simplifications in some cases (like AC benchmarks), requiring fallback to basic encoding
  - Solver Selection: Algorithm selection adds overhead but improves overall performance across diverse problem domains

- Failure signatures:
  - Memory exhaustion: Indicates need for more aggressive simplification or memory-aware processing
  - Solver timeouts: Suggests algorithm selection failure or need for alternative encoding strategy
  - Incorrect results: Points to bugs in the translation from ASP(Q) to QBF or in the QBF encoding

- First 3 experiments:
  1. Run pyqasp on a simple existential ASP(Q) program with only choice rules to verify direct CNF encoding works
  2. Test well-founded simplification on a program with known well-founded model to verify the residual program is correctly computed
  3. Compare runtime of pyqasp with different QBF back-ends on a small benchmark to verify algorithm selection makes reasonable choices

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the choice of grounder (gringo vs iDLV) affect the performance of pyqasp on different problem domains?
- Basis in paper: [explicit] The paper states that pyqasp can be configured to use either gringo or iDLV as grounders, and mentions that iDLV is used for computing the well-founded model in the well-founded optimization.
- Why unresolved: The experimental analysis only mentions the use of iDLV for the well-founded simplification, but doesn't provide a direct comparison of performance between the two grounders across different problem domains.
- What evidence would resolve it: Experimental results comparing pyqasp's performance with both grounders on a variety of problem domains would provide insights into which grounder is more effective for different types of ASP(Q) programs.

### Open Question 2
- Question: Can the algorithm selection strategy be further improved to handle smaller problem domains like MMC more effectively?
- Basis in paper: [explicit] The paper mentions that the algorithm selection strategy sometimes misses a suitable back-end, especially in MMC which is the smallest and least represented domain in the training set.
- Why unresolved: The current algorithm selection strategy, while effective overall, shows limitations in handling certain problem domains with limited training data.
- What evidence would resolve it: Developing a more robust algorithm selection strategy that can handle smaller problem domains effectively, possibly through techniques like transfer learning or domain-specific heuristics, would demonstrate its improved performance.

### Open Question 3
- Question: How do the different optimizations (well-founded simplification and direct CNF encoding) interact with each other and with the choice of QBF solver?
- Basis in paper: [explicit] The paper presents two main optimizations (well-founded simplification and direct CNF encoding) and shows that their combination can be beneficial in some cases but detrimental in others (e.g., negative effect on AC benchmark).
- Why unresolved: The experimental results show that the effectiveness of these optimizations varies depending on the problem domain and the QBF solver used, but the underlying reasons for these interactions are not fully explored.
- What evidence would resolve it: A detailed analysis of how these optimizations affect the structure and size of the generated QBF formulas, and how these changes impact the performance of different QBF solvers, would provide insights into the interactions between optimizations and solvers.

## Limitations
- Performance gains depend heavily on the effectiveness of well-founded simplification, which may not yield significant improvements for all problem classes
- Algorithm selection strategy may not generalize perfectly to problem domains not represented in the training set
- Some benchmarks (like AC instances) show no simplification benefit from well-founded semantics, requiring fallback to basic encoding

## Confidence
- High confidence: The basic translation of ASP(Q) to QBF and the core implementation of pyqasp
- Medium confidence: The performance improvements claimed over qasp, as these depend on specific benchmark characteristics
- Medium confidence: The algorithm selection strategy's effectiveness across all problem domains
