# Cheaply Evaluating Inference Efficiency Metrics for Autoregressive Transformer APIs

## Quick Facts
- arXiv ID: 2305.02440
- Source URL: https://arxiv.org/abs/2305.02440
- Reference count: 13
- Primary result: Proposes new metrics to fairly compare LLM inference efficiency across providers by factoring out hardware/software optimizations

## Executive Summary
This paper addresses the challenge of comparing inference efficiency across different LLM providers when raw runtime measurements are not directly comparable due to varying hardware/software optimizations. The authors derive a parameterized expression for autoregressive inference runtime as a piecewise linear function of prompt length and a linear function of output length. They introduce two metrics - idealized runtime (estimating performance on standardized hardware) and denoised runtime (factoring out API noise) - that can be efficiently estimated by profiling a small number of queries. The methodology is evaluated on 10 state-of-the-art models, revealing that OpenAI's davinci appears Pareto efficient in capability vs. raw runtime but not when using idealized runtime.

## Method Summary
The authors derive a mathematical expression for autoregressive inference runtime, decomposing it into prompt encoding time (growing piecewise linearly with prompt size) and output generation time (growing linearly with output tokens). They propose two metrics: idealized runtime estimates performance on standardized hardware/software, while denoised runtime factors out noise by using minimum runtimes across trials. Both metrics can be efficiently estimated by profiling a small set of queries with varying prompt and output lengths, then fitting linear regression models to estimate the runtime parameters. The methodology is applied to 10 LLMs across four HELM tasks to analyze capability-efficiency tradeoffs.

## Key Results
- OpenAI's davinci model appears Pareto efficient in capability vs. raw runtime but not when using idealized runtime
- Proposed metrics provide more accurate and comparable measures of inference efficiency than raw runtime
- The methodology can estimate runtime parameters with high accuracy using only a small number of profiling queries
- Models with similar capabilities can have vastly different efficiency profiles when hardware optimizations are factored out

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Autoregressive Transformer inference runtime can be expressed as a piecewise linear function of prompt length and a linear function of output length.
- Mechanism: The runtime is decomposed into prompt encoding time (which grows piecewise linearly with prompt size) and output generation time (which grows linearly with output tokens). This decomposition is possible because the number of floating-point operations for these phases has predictable mathematical forms.
- Core assumption: The hidden size h is much larger than the prompt and sequence lengths (p ≪ 6h and i ≪ 6h), which is true for most LLMs in practice.

### Mechanism 2
- Claim: Idealized runtime can be efficiently estimated by profiling a small set of queries instead of exhaustive profiling.

### Mechanism 3
- Claim: Denoised runtime can factor out noise from performance variation in black-box APIs by using the minimum runtime across multiple trials.
- Mechanism: Since performance noise is a random variable η ≥ 0, running multiple trials and using the minimum runtime across trials for each prompt size and number of generated tokens can estimate the denoised runtime.
- Core assumption: The performance noise is non-negative and can be minimized by selecting the minimum runtime across trials.

## Architecture Onboarding

- Component map: Prompt encoding phase -> Output generation phase -> Linear regression fitting -> Idealized runtime calculation -> Denoised runtime calculation

- Critical path:
  1. Profile a small set of queries with varying prompt and output lengths.
  2. Fit linear regression models to estimate the runtime parameters (prompt encoding time and per-output-token generation time).
  3. Use the estimated parameters to calculate the idealized and denoised runtimes for arbitrary queries.

- Design tradeoffs:
  - Profiling overhead vs. accuracy: Profiling more queries can improve the accuracy of the runtime estimates but increases the overhead.
  - Standardization vs. real-world performance: Idealized runtime provides a fair comparison across models but may not reflect the actual performance users experience with black-box APIs.

- Failure signatures:
  - Poor linear regression fit (low R² value): Indicates that the runtime does not follow the assumed piecewise linear + linear form.
  - Large discrepancy between idealized and denoised runtimes: Suggests that the API provider is using significant optimizations or the hardware/software assumptions are inaccurate.

- First 3 experiments:
  1. Profile a set of queries with varying prompt lengths (e.g., 1, 512, 1024, 1536 tokens) and a fixed number of output tokens (e.g., 64) to estimate the prompt encoding time as a function of prompt length.
  2. Profile a set of queries with a fixed prompt length (e.g., 512 tokens) and varying numbers of output tokens (e.g., 1, 4, 16, 64) to estimate the per-output-token generation time.
  3. Calculate the idealized and denoised runtimes for a set of diverse queries using the estimated parameters and compare them to the raw runtimes to validate the methodology.

## Limitations

- Hardware assumptions uncertainty: The methodology assumes specific hardware characteristics (hidden size much larger than prompt/sequence lengths) that may not hold for all model architectures
- API provider opacity: While denoised runtime aims to factor out API-specific optimizations, the actual performance characteristics of black-box APIs remain opaque
- Generalization scope: Analysis focuses on 10 specific models and four HELM tasks, limiting broader applicability claims

## Confidence

- High confidence: The core mathematical derivation of piecewise linear runtime expressions and the linear relationship between output tokens and generation time
- Medium confidence: The effectiveness of denoised runtime in capturing true model efficiency by using minimum runtime across trials
- Low confidence: The assumption that all models follow the same scaling behavior with prompt length, particularly the piecewise linear relationship
