# ML-driven Hardware Cost Model for MLIR

## Quick Facts
- arXiv ID: 2302.11405
- Source URL: https://arxiv.org/abs/2302.11405
- Reference count: 7
- Primary result: ML-driven hardware cost model for MLIR using NLP-inspired Conv1D+MaxPool+FC architecture achieves 75% error-free register pressure predictions

## Executive Summary
This paper introduces a novel machine learning-based hardware cost model for MLIR, treating MLIR code as text sequences and applying NLP-inspired Conv1D+MaxPool+FC neural architecture to predict hardware characteristics like register pressure and xPU utilization. The model is trained on over 20,000 MLIR samples and demonstrates promising accuracy with 75% error-free predictions for register pressure when both operators and operands are tokenized. The approach shows significant improvements in speed and accuracy compared to LSTM and GNN-based models while maintaining scalability across different MLIR dialects. The results suggest ML-driven cost models could effectively guide compiler optimizations and improve code generation for deep learning workloads.

## Method Summary
The method treats MLIR code as a text sequence and applies a Conv1D+MaxPool+FC neural architecture inspired by NLP models. The approach tokenizes MLIR code, using either operators alone or both operators and operands, and feeds these sequences into the neural network. The model is trained on a dataset of 20K+ MLIR samples to predict hardware characteristics such as register pressure and xPU utilization. The architecture processes the token sequences through convolutional layers with max pooling, followed by fully connected layers to output hardware cost predictions. The model demonstrates low RMSE values (5-7%) for register pressure prediction and shows superior performance compared to LSTM and GNN alternatives in terms of both speed and accuracy.

## Key Results
- Achieved 75% error-free predictions for register pressure when tokenizing both operators and operands
- Demonstrated RMSE values of 5-7% for register pressure prediction
- Showed superior speed and accuracy compared to LSTM and GNN-based models
- Validated scalability across different MLIR dialects

## Why This Works (Mechanism)
The approach works by leveraging the sequential nature of MLIR code and applying NLP-inspired techniques that excel at capturing local patterns and relationships in text data. The Conv1D layers effectively identify local patterns in the token sequences that correspond to hardware characteristics, while max pooling reduces dimensionality and captures the most salient features. The fully connected layers then map these extracted features to specific hardware cost predictions. This architecture is particularly effective because MLIR code, like natural language, has structured patterns where the arrangement and combination of operators and operands directly influence hardware resource utilization.

## Architecture Onboarding

Component Map: MLIR code -> Tokenizer -> Conv1D layers -> MaxPool layers -> FC layers -> Hardware cost predictions

Critical Path: The model processes MLIR token sequences through Conv1D layers to extract local patterns, applies max pooling to identify salient features, and uses fully connected layers to map these features to hardware cost predictions. The tokenization strategy (operators vs. operators+operands) is a critical design decision that significantly impacts prediction accuracy.

Design Tradeoffs: The Conv1D+MaxPool+FC architecture trades the ability to capture long-range dependencies (which LSTMs excel at) for computational efficiency and speed. While this limits the model's ability to understand complex, multi-step relationships in MLIR code, it provides substantial performance benefits and simpler training requirements. The choice between tokenizing operators alone versus operators+operands represents a key accuracy-speed tradeoff.

Failure Signatures: The model may struggle with novel MLIR code patterns not well-represented in the training data, particularly complex operator combinations or rare dialect-specific constructs. Poor tokenization strategies can lead to loss of critical structural information, resulting in inaccurate hardware cost predictions. The model may also fail to generalize across significantly different MLIR dialects if the architectural patterns vary substantially.
