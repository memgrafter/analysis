# Multi-Tenant Optimization For Few-Shot Task-Oriented FAQ Retrieval

## Quick Facts
- arXiv ID: 2301.10517
- Source URL: https://arxiv.org/abs/2301.10517
- Reference count: 10
- Primary result: Fine-tuned Bi-Encoder embeddings with last-layer weight switching achieve top-3 accuracy >70% and 81.5% memory reduction per tenant in few-shot FAQ retrieval.

## Executive Summary
This paper addresses the challenge of scaling few-shot task-oriented FAQ retrieval across multiple business tenants. It proposes a contrastive fine-tuning approach that modifies only the last layer of a shared Bi-Encoder base model, combined with tenant-specific weight switching to minimize memory usage. Experiments across BANKING77, CLINC150, HWU64, and HINT3 datasets show that this method outperforms existing chatbot solutions in both accuracy and efficiency. The approach balances accuracy, cost, and latency for real-world multi-tenant deployments.

## Method Summary
The method involves contrastive fine-tuning of the last layer in sentence Bi-Encoders while keeping base model weights shared across tenants. Tenant-specific weight switching allows each tenant to maintain only a small set of final-layer parameters, significantly reducing memory requirements. Training uses hard sampling of question pairs to maximize contrastive signal in few-shot settings. Inference leverages precomputed embeddings cached in FAISS for fast similarity search, achieving sub-100ms latency and high throughput.

## Key Results
- Fine-tuned MiniLM-L6 Bi-Encoder achieves top-3 accuracy above 70% across all tested datasets in few-shot settings.
- Weight-switching strategy reduces memory requirements by 81.5% per tenant for MiniLM-L6 and 92.5% for MPNet.
- Load testing shows mean latency of 93ms and requests per second (RPS) of 22.9 for the deployed system.

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Fine-tuning only the last layer of a Bi-Encoder while sharing base weights across tenants reduces memory per tenant without sacrificing much accuracy.
- Mechanism: By freezing all layers except the final projection, the base model weights are shared across tenants. Each tenant only needs to store its own small set of tuned final-layer weights. At inference, the base model is loaded once and tenant-specific weights are swapped in per request.
- Core assumption: The base model captures generic semantic features sufficient for all tenants; task-specific adaptation can be achieved by adjusting only the final layer.
- Evidence anchors:
  - [abstract] "We propose a novel approach to scale multi-tenant FAQ applications... by contrastive fine-tuning of the last layer in sentence Bi-Encoders along with tenant-specific weight switching."
  - [section] "The shared base model weights reduce the memory requirement by a significant margin when we scale to a large number of tenants."
  - [corpus] Weak evidence: Corpus lacks studies directly measuring per-tenant memory savings from last-layer-only fine-tuning; only the paper's internal Table 6 provides such data.
- Break condition: If tenant domains diverge so much that the shared base features become inadequate, fine-tuning more layers may be required, eroding memory savings.

### Mechanism 2
- Claim: Question pair training with hard sampling mitigates the scarcity of labeled data in few-shot settings.
- Mechanism: For each intent, all possible question pairs are generated; pairs within the same intent are labeled positive, across intents negative. Hard sampling assigns higher weights to pairs with high cosine similarity for negatives (and low for positives), forcing the model to learn finer distinctions.
- Core assumption: Even with limited examples per intent, the combinatorial explosion of pairs yields enough contrastive signal to train effectively.
- Evidence anchors:
  - [section] "The question pairs are labelled as defined below... This method increases the data size as it generates nC2 question pairs given n questions."
  - [section] "For label 0, the weight is equal to the cosine similarity between the Q-Q pair. For label 1, the weight is (1 - cosine similarity) of the Q-Q pair."
  - [corpus] Weak evidence: No external studies cited on hard sampling effectiveness for few-shot FAQ retrieval; claim relies on internal experiments.
- Break condition: If the pairwise space becomes too sparse or dominated by easy negatives, hard sampling may fail to yield meaningful gradients.

### Mechanism 3
- Claim: Fine-tuned Bi-Encoders outperform Cross-Encoders in few-shot FAQ retrieval under constrained fine-tuning.
- Mechanism: Cross-Encoders must score all query-question pairs during inference, incurring O(N) latency. Bi-Encoders precompute and cache embeddings, so inference is O(1) similarity lookup. In few-shot settings, Bi-Encoders trained with contrastive loss on the last layer retain high accuracy while avoiding Cross-Encoder latency.
- Core assumption: The few-shot constraint makes the cost of exhaustive pairwise scoring prohibitive; cached embeddings preserve most accuracy.
- Evidence anchors:
  - [section] "Cross-Encoder models entail a higher latency as all the question pairs are required to be classified during inference."
  - [section] "We find that the fine-tuned Bi-Encoder shows better performance than all benchmarked chatbot solutions... We also note that online triplet loss based fine-tuning performed marginally better as compared to contrastive Loss."
  - [corpus] Weak evidence: No external benchmarks cited comparing Cross- vs Bi-Encoders under identical few-shot and fine-tuning constraints.
- Break condition: If the cached embedding space becomes too large or dynamic updates are frequent, latency gains may diminish.

## Foundational Learning

- Concept: **Few-shot learning with contrastive loss**
  - Why needed here: FAQ retrieval must generalize from only 5-10 examples per intent; contrastive loss pulls same-intent embeddings together and pushes different-intent embeddings apart.
  - Quick check question: What loss function encourages embeddings of similar items to be close while dissimilar items are far apart?

- Concept: **Siamese/Bi-Encoder architectures**
  - Why needed here: Enables precomputation of question embeddings and fast cosine similarity lookup at inference, critical for low-latency multi-tenant serving.
  - Quick check question: How does a Bi-Encoder differ from a Cross-Encoder in terms of computational complexity at inference time?

- Concept: **Weight sharing and model switching**
  - Why needed here: Allows scaling to many tenants without duplicating large base model weights, reducing per-tenant memory usage from ~110 MB to ~20.5 MB for MiniLM-L6.
  - Quick check question: In a multi-tenant setup, why is it advantageous to load the base model once and only swap final-layer weights per request?

## Architecture Onboarding

- Component map:
  Base Bi-Encoder (shared across tenants) -> Last-layer fine-tuning module (tenant-specific) -> Tenant weight switcher -> FAISS/ANN cache for precomputed embeddings -> Inference API endpoint

- Critical path:
  1. Load shared base model into memory.
  2. Load tenant-specific last-layer weights.
  3. Encode query with base + tenant weights -> query embedding.
  4. Retrieve cached question embeddings from FAISS.
  5. Compute cosine similarities -> rank results.

- Design tradeoffs:
  - Memory vs accuracy: Freezing earlier layers saves memory but may limit adaptation; last-layer-only tuning balances both.
  - Latency vs scalability: Bi-Encoders are fast but require upfront embedding computation; Cross-Encoders are slower but adapt dynamically.

- Failure signatures:
  - High latency spikes -> tenant weight swapping overhead or cache miss storms.
  - Accuracy drop -> insufficient base model generality or poor hard sampling distribution.
  - Memory bloat -> per-tenant weights not unloaded or base model reloaded per tenant.

- First 3 experiments:
  1. Benchmark memory per tenant with last-layer-only fine-tuning vs full fine-tuning on MiniLM-L6.
  2. Measure inference latency with and without FAISS caching for 1K questions per tenant.
  3. Compare top-1 accuracy on BANKING77-5 using contrastive vs triplet loss on the last layer.
