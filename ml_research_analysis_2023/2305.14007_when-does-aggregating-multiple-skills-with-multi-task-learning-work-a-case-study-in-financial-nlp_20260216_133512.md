# When Does Aggregating Multiple Skills with Multi-Task Learning Work? A Case Study in Financial NLP

## Quick Facts
- arXiv ID: 2305.14007
- Source URL: https://arxiv.org/abs/2305.14007
- Reference count: 38
- Primary result: MTL improves performance on 4/6 financial NLP tasks when aggregating diverse but related skills with balanced aggregation size

## Executive Summary
This paper investigates the conditions under which multi-task learning (MTL) effectively aggregates multiple skills in financial NLP. The authors conduct a comprehensive case study using FinDATA, a collection of six diverse financial NLP tasks, and find that MTL success depends on three key factors: skill diversity, task relatedness, and appropriate matching of aggregation size to shared model capacity. They introduce SPAL-FinBERT, an efficient MTL architecture that achieves strong performance with 99.8% fewer trainable parameters than vanilla FinBERT, demonstrating that skill diversity and relatedness enable effective knowledge transfer while proper capacity allocation prevents performance bottlenecks.

## Method Summary
The study fine-tunes P-FinBERT on FinDATA, a collection of six financial NLP tasks covering sentiment analysis, numeric reasoning, semantic role labeling, and causality detection. The authors compare single-task learning (STL) with multi-task learning using their proposed SPAL-FinBERT architecture, which uses frozen pre-trained FinBERT with trainable shared parallel attention layers. They systematically vary task aggregation sizes and measure performance across different skill combinations, using temperature-based batch sampling and 5 random seeds per experiment. The research evaluates both overall MTL effectiveness and task-specific sensitivity to shared capacity constraints.

## Key Results
- MTL improves performance on 4 out of 6 tasks when aggregating diverse but related financial NLP skills
- Skill diversity benefits MTL through implicit data augmentation and feature eavesdropping
- Tasks are more closely related than in GLUE, explaining why diversified skills help each other
- Optimal performance requires matching aggregation size to shared model capacity to avoid overwhelming sensitive tasks

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Skill diversity improves MTL performance through implicit data augmentation and feature eavesdropping.
- Mechanism: When tasks cover different but related skills, the MTL system leverages diverse training signals to improve generalization. Tasks with different skills still share common semantic representations, allowing positive transfer.
- Core assumption: Different financial NLP skills (sentiment analysis, numeric reasoning, SRL, causality) share enough underlying linguistic structure to enable beneficial cross-task knowledge transfer.
- Evidence anchors:
  - [abstract] "Our findings suggest that the key to MTL success lies in skill diversity, relatedness between tasks, and choice of aggregation size and shared capacity."
  - [section 6.1] "skill diversity benefits MTL: the best MTL scores of all tasks are obtained by mixing several different skills while concentrating on sentiment/number understanding skills leads to a performance drop"
- Break condition: If tasks are too diverse with minimal semantic overlap, negative transfer may occur instead of positive transfer.

### Mechanism 2
- Claim: Task relatedness determines the effectiveness of MTL aggregation.
- Mechanism: Related tasks share common feature representations and gradients, enabling positive transfer. The system benefits when tasks are sufficiently related but not redundant.
- Core assumption: Task relatedness can be measured through task embedding similarity and qualitative analysis of skill overlap.
- Evidence anchors:
  - [section 6.2] "FinDATA tasks are more closely related than GLUE tasks though they all cover diverse skills" and "we find that the close relation (measured qualitatively and quantitatively) among Financial NLP tasks explains why diversified skills help each other"
  - [section 6.2] "FSRL positively transfers to all other skills" despite being a different skill type
- Break condition: If task aggregation includes weakly related tasks, negative transfer may overwhelm positive transfer benefits.

### Mechanism 3
- Claim: Aggregation size must match shared model capacity to avoid overwhelming sensitive tasks.
- Mechanism: When too many tasks share limited model capacity, some tasks become performance bottlenecks. Balancing task count with available capacity optimizes overall performance.
- Core assumption: Certain tasks (like causality detection) are more sensitive to capacity sharing than others, and can be overwhelmed by excessive task aggregation.
- Evidence anchors:
  - [section 6.3] "Some tasks are not significantly restricted by the limited shared capacity: SC and NC even achieve the best scores with relatively small shared capacity" while "CD performance gradually improves when we decrease the aggregation size"
  - [section 6.3] "excessive aggregation size in a limited capacity model restricts the performance of some tasks"
- Break condition: If shared capacity is too small relative to task complexity, performance degradation occurs regardless of task relatedness.

## Foundational Learning

- Concept: Multi-task learning optimization
  - Why needed here: Understanding how joint training affects gradient updates across multiple tasks is crucial for interpreting MTL performance
  - Quick check question: What happens to gradient updates when tasks have conflicting objectives during joint training?

- Concept: Task relatedness measurement
  - Why needed here: The paper uses both qualitative and quantitative methods to assess task relationships, which determines aggregation effectiveness
  - Quick check question: How would you measure the similarity between two NLP tasks beyond simple accuracy correlation?

- Concept: Parameter-efficient architectures
  - Why needed here: SPAL-FinBERT demonstrates that frozen pre-trained models with lightweight trainable components can outperform full fine-tuning
  - Quick check question: What are the tradeoffs between adapter-based approaches and shared attention layer approaches?

## Architecture Onboarding

- Component map: Pre-trained FinBERT (frozen) -> Shared Parallel Attention Layers (SPAL) -> Task-specific prediction headers -> Data loader with mixed batching

- Critical path:
  1. Load and preprocess FinDATA tasks
  2. Initialize SPAL-FinBERT with frozen FinBERT and trainable SPAL layers
  3. Implement mixed batching scheme for MTL
  4. Train with task sampling and evaluate on validation sets
  5. Save best checkpoints per task for final evaluation

- Design tradeoffs:
  - Frozen vs. unfrozen pre-trained model: Freezing provides regularization but limits adaptation
  - SPAL hidden size: Larger size increases capacity but also parameter count and risk of overfitting
  - Task sampling strategy: Proportional sampling vs. temperature-based sampling affects convergence

- Failure signatures:
  - Performance degradation on specific tasks indicates capacity bottlenecks
  - Gradient conflicts manifest as unstable training or negative transfer
  - Inconsistent validation scores across tasks suggest poor task balancing

- First 3 experiments:
  1. Baseline: FinBERT fine-tuning on individual tasks to establish performance floors
  2. Full FinDATA MTL: Test overall MTL effectiveness with standard SPAL configuration
  3. Capacity sensitivity: Vary SPAL hidden size to identify optimal capacity for each task type

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How do we quantitatively measure asymmetric task transferability in MTL systems?
- Basis in paper: The authors note that "transferability is asymmetric and thus hard to quantify using symmetric measurements such as cosine similarity between task embeddings or gradients" and give examples where TSA positively transfers to SC but SC negatively transfers to TSA.
- Why unresolved: The authors acknowledge the difficulty in quantifying asymmetric transferability but do not provide a solution or method for doing so. They suggest future work may explore better indicators that address this asymmetry.
- What evidence would resolve it: Development of a quantitative metric or method that can capture and measure the asymmetric nature of task transferability in MTL systems.

### Open Question 2
- Question: How can we determine the optimal task aggregation size and shared capacity for a given MTL system?
- Basis in paper: The authors explore the relationship between task aggregation size and shared capacity, finding that "too many objectives may exhaust the MTL shared capacity and cause interference among tasks" and that "the aggregation size should be appropriate for the shared capacity to avoid overwhelming tasks like CD."
- Why unresolved: While the authors provide some insights into this relationship, they note that it is difficult to determine "exactly each task's sensitivity to capacity sharing and the optimal number of aggregated tasks without some trials on different task combinations."
- What evidence would resolve it: A method or framework for determining the optimal task aggregation size and shared capacity for a given MTL system, potentially through theoretical analysis or empirical studies.

### Open Question 3
- Question: What is the causal impact of each factor (e.g., skill diversity, task relatedness, aggregation size) on MTL performance?
- Basis in paper: The authors acknowledge that "the factors are usually entangled and confound each other" and that "future work may conduct rigorous causal analyses, exploring how much each factor affects MTL performance."
- Why unresolved: The authors recognize the complexity of the relationships between different factors and the need for causal analysis, but do not provide such an analysis in the current work.
- What evidence would resolve it: A causal analysis that isolates and quantifies the impact of each factor on MTL performance, potentially through controlled experiments or advanced statistical methods.

## Limitations
- Findings are based on a single domain (financial NLP) and specific set of six tasks, limiting generalizability
- Qualitative assessment of task relatedness relies on expert judgment that may not be fully reproducible
- Study does not explicitly model or measure negative transfer, focusing instead on overall MTL performance improvements

## Confidence
- **High Confidence**: The finding that skill diversity improves MTL performance through implicit data augmentation and feature eavesdropping, supported by consistent experimental results across multiple task aggregations.
- **Medium Confidence**: The claim that task relatedness determines MTL effectiveness, as the qualitative assessment of relatedness is somewhat subjective despite quantitative backing.
- **Medium Confidence**: The assertion that aggregation size must match shared model capacity, though this appears well-supported by systematic capacity variation experiments.

## Next Checks
1. **Cross-domain validation**: Apply the same MTL framework to non-financial NLP tasks (e.g., GLUE benchmark) to test whether skill diversity benefits transfer across domains, specifically examining whether the positive effects observed in financial NLP generalize to more general language tasks.

2. **Negative transfer measurement**: Implement explicit gradient similarity analysis during training to quantify negative transfer between task pairs, particularly when aggregating tasks with minimal semantic overlap to identify breaking conditions for Mechanism 1.

3. **Dynamic capacity allocation**: Develop an adaptive MTL architecture that adjusts shared capacity allocation based on real-time performance monitoring, testing whether this can prevent the performance bottlenecks identified in Mechanism 3 when aggregation size exceeds shared capacity.
