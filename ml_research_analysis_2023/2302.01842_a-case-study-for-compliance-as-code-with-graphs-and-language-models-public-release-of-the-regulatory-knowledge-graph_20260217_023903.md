# A Case Study for Compliance as Code with Graphs and Language Models: Public release of the Regulatory Knowledge Graph

## Quick Facts
- arXiv ID: 2302.01842
- Source URL: https://arxiv.org/abs/2302.01842
- Reference count: 40
- Primary result: Publicly released KG containing over 1.2 million relationships and 230,000 nodes extracted from Abu Dhabi Global Market regulations

## Executive Summary
This paper presents a comprehensive approach to automating compliance knowledge graph construction using language models and NLP techniques. The method combines manual annotation of regulatory documents with BERT-based entity recognition, coreference resolution, and syntax analysis to extract relationships. The resulting knowledge graph, stored in Neo4j, contains over 1.2 million relationships and 230,000 nodes, demonstrating the feasibility of using graph structures for regulatory compliance automation.

## Method Summary
The method involves manual tagging of regulatory documents with domain-specific entities, training BERT-based models for entity recognition, applying coreference resolution and syntax analysis to extract relationships, and storing the resulting KG in a Neo4j database. The process starts with manual annotation of ADGM regulatory documents, followed by training BERT-based models using spaCy for entity recognition. Coreference resolution and dependency parsing are then applied to extract relationships between entities, which are stored in a graph database for querying and analysis.

## Key Results
- Knowledge graph containing 1,209,207 relationships and 230,363 nodes extracted from ADGM regulations
- Model performance metrics showing F1 scores ranging from 66.11% to 96.98% across different entity types
- Successful demonstration of querying capabilities using Cypher language and Neo4j database
- Proposal for using the KG as structured input for future Graph Neural Networks to automate compliance decision-making

## Why This Works (Mechanism)

### Mechanism 1
Language models can capture regulatory taxonomy interpretations when fine-tuned on labeled examples. Fine-tuning pre-trained BERT models on manually annotated regulatory text allows the model to learn entity boundaries and relationships specific to the compliance domain. Core assumption: Regulatory entities follow consistent linguistic patterns that can be learned from a finite training set. Evidence anchors: "training BERT-based models, which are then applied to the rest of the corpus" and "The models described above were used to extract KG containing... 1,209,207 Relationships". Break condition: Concept drift occurs when regulatory language evolves faster than the model can be retrained.

### Mechanism 2
Knowledge graphs enable explainable compliance automation by structuring regulatory relationships. Extracted entities and relationships are stored in a graph database (Neo4j) where nodes represent regulatory concepts and edges represent relationships, enabling query-based reasoning. Core assumption: Regulatory compliance can be decomposed into explicit entity-relationship patterns that graph traversal can capture. Evidence anchors: "storing the resulting KG in a Neo4j database" and "The Neo4j database allows querying the data through REST in the JSON format". Break condition: Graph becomes too sparse or disconnected to support meaningful compliance reasoning.

### Mechanism 3
Releasing ML models containing regulatory interpretations creates common ground for compliance automation. When regulators release their ML models, companies can apply the same models to their internal policies, creating matching knowledge graphs that enable automated compliance gap analysis. Core assumption: Regulatory interpretation can be captured in ML model weights and applied consistently across different organizational contexts. Evidence anchors: "The interpretation of the rules introduced by the same ML models will allow the system to highlight factual differences between documents" and "The interpretation of the rules introduced by the same ML models will allow the system to highlight factual differences between documents, rather than differences in interpretation". Break condition: Model interpretation becomes too context-dependent or organizations interpret regulations differently enough that automated matching fails.

## Architecture Onboarding

- Component map: Manual annotation pipeline (Clausematch UI → Doccano) → ML training pipeline (spaCy + XLNet → NER models) → Coreference resolution (neuralcoref) → Relationship extraction (spaCy dependency parsing) → Graph storage (Neo4j) → Query interface (Cypher + Bloom)
- Critical path: Annotation → Model training → Entity extraction → Coreference resolution → Relationship extraction → Graph construction → Query capability
- Design tradeoffs:
  - Model granularity vs. performance (single vs. grouped models)
  - Annotation consistency vs. annotation speed
  - Graph expressiveness vs. query complexity
  - Open-source components vs. proprietary solutions
- Failure signatures:
  - Low F1 scores indicate annotation or model issues
  - Disconnected graph indicates relationship extraction problems
  - Inconsistent entity types indicate taxonomy definition issues
  - Slow query performance indicates graph schema problems
- First 3 experiments:
  1. Run annotation tool on 10 sample paragraphs and verify entity consistency across annotators
  2. Train a simple BERT-based NER model on the annotated data and evaluate F1 scores
  3. Extract relationships from 100 paragraphs and verify graph connectivity in Neo4j

## Open Questions the Paper Calls Out

### Open Question 1
What are the specific challenges in developing a single XLNet-based model that can capture all nine entity types simultaneously, and what architectural modifications might overcome these limitations? Basis in paper: "It appears to not be possible to train a single XLNet-based model to capture all of the tags at once" and notes performance issues with the RISK_MIT model showing "poor results" with performance dropping to 43% for some regulatory documents. Why unresolved: The paper identifies the problem but does not explore alternative model architectures or ensemble approaches that might address the multi-entity capture challenge. What evidence would resolve it: Experimental results comparing single-model versus multi-model architectures, including transformer variants, hierarchical models, or ensemble approaches trained on the same dataset with performance metrics across all entity types.

### Open Question 2
How can the KG extraction pipeline be adapted to handle regulatory documents from different jurisdictions while maintaining consistent entity tagging performance? Basis in paper: "extracted taxonomy, KG extraction pipeline and models may require adjustments" when applied to other regulators, and mentions that fine-tuning on new taxonomy "likely to come with a cost of performance on ADGM taxonomy." Why unresolved: The paper identifies the need for adaptation but does not provide a methodology for cross-jurisdictional transfer learning or domain adaptation strategies. What evidence would resolve it: Comparative studies showing model performance on multiple regulatory corpora, transfer learning experiments with pre-trained models on diverse regulatory texts, and metrics quantifying performance degradation when moving between jurisdictions.

### Open Question 3
What specific relation extraction taxonomy and algorithms are needed to enable reinforcement learning agents to navigate over sub-graphs for automated compliance verification? Basis in paper: "KG has to store generalised form of the rules to enable reinforcement learning agents to navigate over sub-graphs" and suggests extending relation taxonomy with "Is a" and "precedence" relationships, but does not specify the complete taxonomy or algorithms. Why unresolved: The paper outlines the vision but does not provide the concrete relation types, extraction methods, or RL algorithms required to implement the compliance verification system. What evidence would resolve it: A detailed relation extraction taxonomy with examples, implementation of RL algorithms for compliance verification on the KG, and empirical results showing successful navigation and decision-making capabilities.

## Limitations
- Manual annotation is time-intensive and may not capture the full complexity of regulatory language evolution
- Model performance varies significantly across entity types, with RISK_MIT achieving the lowest F1 score (66.11%)
- Core assumption that regulatory interpretations can be captured in ML model weights may not hold for jurisdictions with nuanced or context-dependent regulatory frameworks

## Confidence
- **High Confidence**: BERT-based entity recognition effectiveness for structured regulatory text (F1 scores 82.93-96.98% for most entity types)
- **Medium Confidence**: Knowledge graph construction methodology and Neo4j integration for compliance reasoning
- **Low Confidence**: Cross-jurisdictional applicability of released ML models for automated compliance gap analysis
