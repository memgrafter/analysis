# Anserini Gets Dense Retrieval: Integration of Lucene's HNSW Indexes

## Quick Facts
- **arXiv ID**: 2304.12139
- **Source URL**: https://arxiv.org/abs/2304.12139
- **Reference count**: 25
- **Primary result**: Anserini now supports unified dense and sparse retrieval via Lucene HNSW indexes, achieving MRR@10 of ~0.38 and Recall@1k of ~0.97 on MS MARCO passage.

## Executive Summary
Anserini, a Lucene-based toolkit for information retrieval research, is extended to support dense retrieval through integration of Lucene's HNSW indexes alongside existing inverted indexes. This enables a unified software framework for both sparse and dense retrieval, avoiding the need to combine separate Faiss and Lucene stacks. A new dense retrieval model, cosDPR-distil, is trained for cosine similarity using distillation and hard negative mining. Experiments on MS MARCO passage and BEIR datasets show that Anserini's HNSW implementation achieves effectiveness comparable to Faiss, with MRR@10 of ~0.38 and Recall@1k of ~0.97 on MS MARCO. While Faiss offers faster single-threaded indexing, Lucene provides superior multi-threaded search performance. The work offers a single-stack solution for reproducible research and deployment of hybrid sparse-dense retrieval systems.

## Method Summary
The authors integrated Lucene's HNSW indexes into Anserini to unify dense and sparse retrieval within a single Java-based framework. They trained a new dense retrieval model (cosDPR-distil) specifically for cosine similarity, as Lucene's HNSW implementation requires unit-norm vectors. The HNSW indexes were built with configurable parameters (M=16, efC=100) using multi-threaded indexing, and searched with efSearch=1000. The unified framework supports both sparse retrieval (BM25, SPLADE) and dense retrieval, enabling hybrid fusion approaches. Experiments were conducted on MS MARCO passage (8.8M passages, 6.9k dev queries) and BEIR datasets, measuring effectiveness with MRR@10 and Recall@1k, and efficiency with QPS, indexing time, and memory usage.

## Key Results
- Anserini's HNSW implementation achieves MRR@10 of ~0.38 and Recall@1k of ~0.97 on MS MARCO passage, comparable to Faiss baselines
- Multi-threaded search in Lucene HNSW shows better scaling than Faiss, though Faiss is faster with single-threaded indexing
- cosDPR-distil model trained for cosine similarity works effectively with Lucene's HNSW implementation
- Unified framework enables hybrid retrieval without combining separate Faiss and Lucene software stacks

## Why This Works (Mechanism)

### Mechanism 1
Integrating Lucene's HNSW indexes into Anserini unifies dense and sparse retrieval in a single software stack, avoiding the need to stitch together Faiss and Lucene separately. Lucene's latest release includes HNSW support, enabling efficient approximate nearest neighbor search using the same inverted index framework already used for BM25 and learned sparse representations like SPLADE. Core assumption: HNSW implementation in Lucene is functionally equivalent to Faiss for dense retrieval use cases, so swapping out Faiss does not degrade effectiveness or efficiency. Evidence anchors: "Nevertheless, hybrid fusion techniques that integrate sparse and dense retrieval models need to stitch together results from two completely different 'software stacks', which creates unnecessary complexities and inefficiencies." "With this addition, Anserini provides a unified interface for dense and sparse retrieval." Break condition: If Lucene's HNSW performance (accuracy, latency, index size) falls significantly below Faiss under real workloads, unified integration would lose its practical value.

### Mechanism 2
Training a cosine-similarity dense retrieval model (cosDPR-distil) is necessary because Lucene's HNSW implementation requires unit-norm vectors. The Lucene HNSW index normalizes all vectors to unit length; dot-product-based models (trained for inner product) are incompatible unless retrained for cosine similarity. Core assumption: Model distillation and hard negative mining can produce a cosine-based dense retriever with competitive effectiveness compared to dot-product models. Evidence anchors: "Due to an implementation choice in Lucene, proper use of HNSW indexes requires training new models that use cosine similarity as the similarity metric (instead of the more common inner product)." "We have trained such a dense retrieval model, which we share on the Huggingface Model Hub." Break condition: If cosine-based models prove substantially less effective than dot-product models on the same tasks, the cost of retraining outweighs the benefits of unified indexing.

### Mechanism 3
Multi-threaded search in Lucene HNSW indexes provides better scaling than Faiss, making Lucene attractive for high-throughput scenarios. Lucene's implementation is designed to leverage multiple query threads efficiently, whereas Faiss single-threaded performance is higher but scales less effectively. Core assumption: Thread scaling advantage observed in Lucene is reproducible across hardware and workload patterns. Evidence anchors: "Interestingly, Faiss does not exhibit anywhere close to the increase in QPS from multi-threaded search that we observe in Lucene." "Using a single thread, Faiss is substantially faster, but Lucene appears to achieve better multi-threaded performance." Break condition: If Lucene's multi-threaded scaling does not hold under production load or with different hardware, the performance advantage disappears.

## Architecture Onboarding

- **Component map**: IndexHnswDenseVectors -> SearchHnswDenseVectors -> Lucene inverted indexes (BM25/SPLADE) -> cosDPR-distil model -> Pyserini bindings
- **Critical path**:
  1. Prepare JSONL of dense vectors with unit norm
  2. Build HNSW index via IndexHnswDenseVectors with desired M and efC
  3. Run search with SearchHnswDenseVectors using efSearch for accuracy/latency trade-off
  4. Combine results with sparse retrieval outputs for final ranking
- **Design tradeoffs**:
  - M vs index size/effectiveness: larger M improves recall but increases memory
  - efC vs indexing time: higher efC improves search accuracy but slows indexing
  - efSearch vs query latency: larger efSearch improves accuracy but increases latency
  - Multi-threading: speeds up indexing/search but increases resource usage
- **Failure signatures**:
  - Low recall despite high efSearch: vectors may not be properly normalized or M/efC too low
  - Excessive indexing time: try reducing M or efC, or increase threads
  - Search latency much higher than expected: check efSearch setting and segment merging status
  - Mismatch in vector dimensions: verify input vector size matches model expectations
- **First 3 experiments**:
  1. Build HNSW index with default M=16, efC=100, single thread; run single-threaded search with efSearch=1000; measure MRR@10 vs Faiss baseline
  2. Repeat with multi-threaded indexing and search (e.g., 16 threads); compare QPS and effectiveness
  3. Increase efC to 1000; measure impact on indexing time, search accuracy, and query latency

## Open Questions the Paper Calls Out

- **Question**: What specific implementation details in Lucene vs Faiss account for the observed differences in indexing and search performance, particularly Lucene's superior multi-threaded search performance?
- **Basis**: The paper explicitly states that "we have not sufficiently delved in the underlying implementation details to understand the source of these observed performance differences" and notes Lucene's better multi-threaded search performance despite Faiss being faster with single-threaded search.
- **Why unresolved**: The authors acknowledge they haven't investigated the underlying implementation details that cause these performance differences between Lucene and Faiss.
- **What evidence would resolve it**: A detailed technical analysis comparing the HNSW implementation architectures in Lucene and Faiss, particularly focusing on thread management, memory access patterns, and data structure organization during multi-threaded operations.

- **Question**: How does the performance of Lucene's HNSW implementation scale with larger collections beyond MS MARCO's 8.8 million passages?
- **Basis**: The paper only evaluates on MS MARCO passage (8.8M passages) and BEIR datasets, with no mention of scaling to significantly larger collections. The authors note that Anserini "now offers a 'one-stop shop' for reproducible research on common IR test collections" but don't explore performance at scale.
- **Why unresolved**: The experiments are limited to datasets with millions of passages, not billions, and the paper doesn't discuss expected behavior or conduct experiments with larger-scale collections.
- **What evidence would resolve it**: Experimental results comparing Lucene HNSW performance on collections of increasing scale (tens of millions to billions of passages), measuring indexing time, search latency, and memory usage patterns.

- **Question**: How does the cosDPR-distil model's performance change when trained with different hard negative mining strategies or alternative distillation approaches?
- **Basis**: The paper describes using "BM25 hard negatives" and then "mine hard negative passages" with augmented training data, but notes this is just one approach following "best practices" without exploring alternatives.
- **Why unresolved**: The authors present their specific training methodology but don't compare it against other hard negative mining strategies or distillation approaches that could potentially yield better performance.
- **What evidence would resolve it**: Comparative experiments training cosDPR-distil with different hard negative mining approaches (e.g., ANCE-style mining, cross-encoder reranking for negative selection) and different distillation methods, measuring MRR@10 and Recall@1k on MS MARCO and BEIR datasets.

## Limitations

- cosDPR-distil effectiveness on BEIR datasets remains unevaluated, creating uncertainty about cross-domain generalization
- Scalability to larger collections (billions of passages) and production workloads has not been validated
- Performance differences between Lucene and Faiss implementations, particularly Lucene's multi-threaded scaling advantage, lack detailed technical explanation

## Confidence

- **High**: Anserini can successfully integrate Lucene HNSW indexes alongside inverted indexes, providing a unified framework for dense and sparse retrieval
- **Medium**: cosDPR-distil achieves competitive effectiveness on MS MARCO passage when using cosine similarity in Lucene HNSW
- **Low**: Lucene HNSW consistently outperforms Faiss in multi-threaded search scenarios across diverse hardware and workload patterns
