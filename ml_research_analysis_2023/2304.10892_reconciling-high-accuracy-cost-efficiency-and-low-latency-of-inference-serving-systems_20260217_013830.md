# Reconciling High Accuracy, Cost-Efficiency, and Low Latency of Inference Serving Systems

## Quick Facts
- arXiv ID: 2304.10892
- Source URL: https://arxiv.org/abs/2304.10892
- Reference count: 40
- Key outcome: InfAdapter reduces SLO violations by up to 65% and costs by 33% compared to Kubernetes VPA and Model-Switching approaches

## Executive Summary
InfAdapter addresses the challenge of dynamic ML inference workloads by selecting model variants and resource allocations to balance accuracy, cost, and latency. It uses predictive workload forecasting and solves an integer linear program to maximize an objective combining average accuracy and resource/loading costs, while ensuring latency SLO. Experiments with real Twitter traces show InfAdapter achieves better accuracy-cost trade-offs under varying workload conditions compared to existing approaches.

## Method Summary
InfAdapter implements a proactive resource allocation system for ML inference serving that combines LSTM-based workload forecasting with ILP optimization. The system predicts maximum workload for the next minute based on past 10 minutes of request data, then solves an ILP to select model variants and CPU allocations that maximize a weighted objective function combining accuracy and cost while maintaining latency SLO. A weighted round-robin dispatcher routes requests across selected model variants, and the optimization runs every 30 seconds to adapt to changing workloads.

## Key Results
- Reduces SLO violations by up to 65% compared to Kubernetes VPA and Model-Switching approaches
- Reduces costs by 33% while maintaining better accuracy-cost trade-offs
- Achieves proactive resource allocation through LSTM forecasting and ILP optimization
- Works effectively with real Twitter workload traces showing varying patterns

## Architecture Onboarding

- Component map:
  - Monitoring collects request arrival rates from dispatcher
  - Adapter contains LSTM forecaster and ILP solver, predicts workload and solves optimization
  - Dispatcher load balances incoming requests across selected model variants using weighted round-robin
  - Model Servers run TensorFlow Serving instances with model variants in Docker containers
  - Kubernetes Cluster orchestrates containers across physical machines

- Critical path: Request → Dispatcher → Model Server → Response, with Adapter updating configuration every 30 seconds based on predictions

- Design tradeoffs:
  - Batch size vs latency: Disabling batching (batch=1) provides better latency at the cost of lower throughput
  - Inter-op vs intra-op parallelism: Setting inter-op parallelism to CPU core count maximizes throughput
  - Optimization frequency vs computational overhead: Solving ILP every 30 seconds balances responsiveness with solver cost

- Failure signatures:
  - SLO violations: LSTM predictions significantly underestimate actual load
  - Suboptimal accuracy: Regression models overpredict throughput, leading to under-provisioning
  - High cost: Regression models underpredict throughput, leading to over-provisioning
  - System instability: ILP solver fails to find feasible solutions due to overly conservative constraints

- First 3 experiments:
  1. Profile three model variants (Resnet18, Resnet50, Resnet152) across 5 CPU allocations (1, 2, 4, 8, 16 cores) and train linear regression models to predict throughput
  2. Train LSTM forecaster on historical Twitter trace data and validate prediction accuracy on test data
  3. Run InfAdapter with synthetic workload patterns (steady, spike, gradual decrease) and compare accuracy, cost, and SLO violation metrics against VPA and Model-Switching baselines

- Limited evaluation to CPU-only environments without hardware accelerators
