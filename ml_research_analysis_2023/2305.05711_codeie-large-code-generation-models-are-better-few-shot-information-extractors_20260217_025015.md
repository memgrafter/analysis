# CodeIE: Large Code Generation Models are Better Few-Shot Information Extractors

## Quick Facts
- arXiv ID: 2305.05711
- Source URL: https://arxiv.org/abs/2305.05711
- Reference count: 22
- Key outcome: Code-LLMs like Codex outperform fine-tuned IE models and NL-LLMs for few-shot NER and RE tasks when using code-style prompts

## Executive Summary
This paper introduces CODEIE, a novel approach that leverages large code generation models (Code-LLMs) like Codex to perform few-shot information extraction (IE) tasks such as named entity recognition (NER) and relation extraction (RE). The core idea is to recast structured IE tasks into code generation tasks by designing code-style prompts, enabling better alignment between the structured output format and the pre-training distribution of Code-LLMs. Experiments on seven benchmarks demonstrate that CODEIE consistently outperforms fine-tuning moderate-size IE models and prompting natural language LLMs (NL-LLMs) under few-shot settings. The results show that using code prompts with Code-LLMs yields significant improvements in performance, model fidelity, and format consistency compared to text prompts with NL-LLMs or Code-LLMs.

## Method Summary
CODEIE reformulates IE tasks as code generation tasks by converting natural language input into structured Python code representations. The approach uses code-style prompts that represent entities and relations as Python functions, classes, and dictionaries, which are then fed to Code-LLMs like Codex for in-context learning. The generated code is parsed back to extract the structured IE output. The method is evaluated in few-shot settings across seven benchmarks for both NER and RE tasks, comparing performance against fine-tuned models and NL-LLM baselines.

## Key Results
- Code-LLMs with code-style prompts consistently outperform fine-tuned moderate-size IE models and NL-LLMs in few-shot settings
- CODEIE achieves significant improvements in entity F1 for NER and relation strict F1 for RE across all seven benchmarks
- Code-style prompts reduce structural and semantic errors compared to text prompts, leading to higher model fidelity

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Recasting structured IE tasks as code generation aligns output format with Code-LLMs' pre-training distribution
- Mechanism: Code-LLMs are pre-trained on structured code corpora containing syntax and semantics, making structured code prompts more natural than linearized text formats
- Core assumption: Code-LLMs have better representations for structured data due to code pre-training
- Evidence anchors:
  - [abstract] "we propose to recast the structured output in the form of code instead of natural language and utilize generative LLMs of code (Code-LLMs) such as Codex to perform IE tasks"
  - [section 2.2] "we reformulate IE tasks as code generation tasks... such that they can compose a complete piece of code that is semantically equivalent to the original sample while maintaining the syntax of the programming language"
  - [corpus] Weak - no direct corpus evidence supporting this specific mechanism
- Break condition: If Code-LLMs are not sufficiently pre-trained on structured code data or if the code prompt format is poorly designed

### Mechanism 2
- Claim: Code-style prompts reduce structural errors compared to text prompts
- Mechanism: Structured code formats enforce syntax constraints that prevent invalid output structures
- Core assumption: Text prompts allow more free-form generation leading to structural errors
- Evidence anchors:
  - [section 4.2] "we find that NL-LLMs are more likely to generate outputs with structural and semantic errors when performing few-shot IE tasks than Code-LLMs"
  - [section 4.2] "we define two metrics: Structure Fidelity... and Semantic Fidelity... to quantitatively measure the model fidelity"
  - [corpus] Weak - no direct corpus evidence supporting this specific mechanism
- Break condition: If code parser rules are too permissive or if Code-LLMs generate syntactically correct but semantically invalid code

### Mechanism 3
- Claim: Code-LLMs show higher model fidelity (faithfulness to demonstrated samples) than NL-LLMs
- Mechanism: Code-LLMs are more constrained by the code context and less prone to generating out-of-distribution outputs
- Core assumption: Code-LLMs have better understanding of structured input formats
- Evidence anchors:
  - [section 4.2] "Code-LLMs seem to be more faithful to the demonstrated few-shot samples than NL-LLMs"
  - [section 4.2] "Codex is more faithful to the demonstrations provided in the context and therefore is more predictable for IE tasks"
  - [corpus] Weak - no direct corpus evidence supporting this specific mechanism
- Break condition: If Code-LLMs are not pre-trained on diverse enough code datasets or if demonstration samples are too noisy

## Architecture Onboarding

- Component map: Input text -> Code-style prompt transformation -> Code-LLM (Codex) -> Structured code output -> Parse back to IE format -> Evaluation
- Critical path:
  1. Convert input text to code-style prompt
  2. Generate output using Code-LLM
  3. Parse generated code back to structured format
  4. Evaluate against ground truth
- Design tradeoffs:
  - Code prompt design space is large and hard to fully explore
  - Tradeoff between prompt complexity and model performance
  - Code-LLMs vs NL-LLMs: Better performance vs. potentially more flexibility
- Failure signatures:
  - Structural errors in generated code
  - Semantic errors (invalid entity types or relations)
  - Format inconsistency between prompt and generated output
- First 3 experiments:
  1. Compare code prompt vs text prompt using same LLM (GPT-3)
  2. Compare Code-LLM (Codex) vs NL-LLM (GPT-3) using same prompt type
  3. Test different code prompt designs (func def, class init, func exec)

## Open Questions the Paper Calls Out

- Question: How does the performance of CodeIE scale with larger and more diverse code generation models?

- Why unresolved: The paper only reports results on a specific set of models and does not investigate how performance changes with different model sizes or architectures.
- What evidence would resolve it: Experiments comparing CodeIE performance across a range of code generation model sizes and architectures.

- Question: How robust is CodeIE to variations in code prompt design and task formulation?
- Basis in paper: [explicit] The paper explores a few code prompt designs but acknowledges that the design space is large and hard to fully explore.
- Why unresolved: The paper only tests a limited set of prompt designs and does not systematically investigate the impact of different formulations on performance.
- What evidence would resolve it: A comprehensive study of CodeIE performance across a wide range of code prompt designs and task formulations.

## Limitations

- Code prompt design space remains largely unexplored, suggesting potential for further optimization
- Reproducibility challenges due to unspecified hyperparameters and parser implementation details
- Performance on specialized or domain-specific IE tasks outside tested benchmarks remains unclear

## Confidence

- High Confidence: The core claim that Code-LLMs outperform NL-LLMs and fine-tuned models for few-shot IE tasks is well-supported by extensive experimental results across seven benchmarks.
- Medium Confidence: The attribution of superior performance to better format consistency and model fidelity is supported by error analysis, but the exact mechanisms could be more thoroughly validated.
- Medium Confidence: The claim that recasting IE as code generation aligns with Code-LLMs' pre-training distribution is reasonable but not directly empirically validated.

## Next Checks

1. **Hyperparameter sensitivity analysis**: Systematically test different decoding parameters (temperature, max tokens, top-k/p) for Codex to identify optimal settings and assess robustness to hyperparameter choices.

3. **Parser robustness evaluation**: Implement and validate the structural error detection parser on a held-out validation set to ensure accurate measurement of structural and semantic fidelity, and test its sensitivity to different code prompt designs.
