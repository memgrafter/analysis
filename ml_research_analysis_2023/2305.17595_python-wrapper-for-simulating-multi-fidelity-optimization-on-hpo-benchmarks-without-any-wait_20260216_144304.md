# Python Wrapper for Simulating Multi-Fidelity Optimization on HPO Benchmarks without Any Wait

## Quick Facts
- **arXiv ID:** 2305.17595
- **Source URL:** https://arxiv.org/abs/2305.17595
- **Reference count:** 20
- **Key outcome:** Python wrapper enables multi-fidelity HPO simulation with 10^-2 second wait times instead of hours, maintaining correct evaluation order

## Executive Summary
This paper introduces a Python wrapper that enables rapid simulation of multi-fidelity hyperparameter optimization (HPO) by replacing actual training wait times with file-based synchronization. The approach allows workers to process configurations in the same order as real experiments but with negligible waiting time. The wrapper supports both intra-process optimizers like SMAC3 and DEHB, as well as inter-process systems like NePS, while maintaining the ability to restart evaluations from intermediate states. Experimental results demonstrate runtime reductions from hours to seconds while preserving evaluation order integrity, enabling more efficient HPO research with significantly reduced energy consumption.

## Method Summary
The wrapper implements file-based synchronization to coordinate multiple workers during HPO simulation. When a worker finishes evaluating a configuration, it writes a synchronization file indicating completion. Other workers read this file before starting new evaluations, ensuring they process configurations in the same order as they would in actual runtime conditions. The system supports both synchronous and asynchronous synchronization patterns, handles configuration restarts from intermediate states, and works with both single-process and distributed optimizer implementations. The wrapper intercepts optimizer calls to insert the synchronization logic while maintaining the original optimization behavior and evaluation ordering.

## Key Results
- Reduces HPO simulation runtime from hours to seconds while maintaining correct evaluation order
- Supports both intra-process (SMAC3, DEHB) and inter-process (NePS) synchronization patterns
- Enables potential CO2 emission reductions of orders of magnitude compared to naive implementations
- Handles configuration restarts from intermediate states during simulation

## Why This Works (Mechanism)
The wrapper exploits the fact that in simulation mode, the actual computation time is negligible compared to real training. By using file-based synchronization, workers can coordinate their evaluation order without waiting for actual runtimes. The synchronization files act as lightweight communication channels that ensure all workers process configurations in the same sequence they would in a real experiment. This approach maintains the temporal dependencies between evaluations while eliminating the computational bottleneck of actual training time.

## Foundational Learning
- **File-based synchronization:** Workers communicate through filesystem markers to coordinate evaluation order. Needed to replace actual runtime waiting with lightweight coordination. Quick check: Verify synchronization files are created and read correctly by all workers.
- **Multi-fidelity evaluation ordering:** Ensures workers process configurations at appropriate fidelity levels in correct sequence. Needed to maintain realistic optimization behavior. Quick check: Confirm evaluation order matches expected pattern across all workers.
- **State persistence and restart:** Workers can resume evaluations from intermediate states. Needed to handle failures and support realistic benchmarking scenarios. Quick check: Validate that restarted evaluations continue from correct intermediate points.

## Architecture Onboarding

**Component Map:** Optimizer -> Wrapper -> Synchronization Manager -> File System

**Critical Path:** Worker request configuration -> Wrapper determines next configuration via sync files -> Worker evaluates configuration -> Wrapper writes completion to sync file -> Next worker reads sync file

**Design Tradeoffs:** The file-based approach prioritizes correctness and compatibility over raw performance. Alternative approaches like in-memory synchronization would be faster but less portable and harder to debug.

**Failure Signatures:** Missing synchronization files indicate worker failures; stale sync files suggest workers are stuck; incorrect file permissions prevent proper coordination.

**First Experiments:** 1) Single-worker validation to ensure basic functionality, 2) Two-worker test to verify coordination, 3) Multi-fidelity benchmark with 10+ configurations to stress-test ordering logic

## Limitations
- Scalability to larger distributed systems with 50+ concurrent workers remains unverified
- May not capture all edge cases in real-world deployments with non-stationary objectives
- Limited testing on constrained optimization problems and complex benchmark scenarios

- **Medium confidence** in generalizability across different optimizer types and benchmark configurations
- **Low confidence** in scalability claims without testing on larger-scale distributed systems
