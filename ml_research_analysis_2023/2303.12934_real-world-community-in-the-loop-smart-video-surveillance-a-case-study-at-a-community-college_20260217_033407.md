# Real-World Community-in-the-Loop Smart Video Surveillance -- A Case Study at a Community College

## Quick Facts
- arXiv ID: 2303.12934
- Source URL: https://arxiv.org/abs/2303.12934
- Reference count: 40
- One-line primary result: Smart video surveillance system achieves 32.41 FPS throughput with 8 cameras, with end-to-end latency of 5.3–11.11s for object detection and 7.3–20.78s for behavioral anomaly detection.

## Executive Summary
This paper presents a case study for designing and deploying a smart video surveillance system at a community college, addressing challenges in real-time AI processing, low-latency notification, scalability, and privacy. The system uses deep learning models for object detection, person tracking, and behavioral anomaly detection, integrated with cloud and mobile notification services. Experiments with 1–8 cameras show end-to-end latency for suspicious object detection ranging from 5.3 to 11.11 seconds and for anomalous behavior from 7.3 to 20.78 seconds. The system achieves 32.41 FPS throughput with 8 cameras, demonstrating effective real-time detection and notification. The study emphasizes community-in-the-loop design and provides technical and ethical deployment guidelines.

## Method Summary
The system employs a distributed architecture with edge, global, and cloud nodes. The edge node processes video streams using deep learning models (YOLOv5 for object detection, ByteTrack for person tracking, HRNet for pose estimation, and GEPC for anomaly detection) and sends results to a local database. The global node handles human track re-identification and statistical analysis, while the cloud node manages AWS DynamoDB for data storage, AWS SNS for push notifications, AWS AppSync for mobile app integration, and AWS Amplify for user management. The mobile app receives real-time alerts and displays statistics. The system was tested with 1–8 cameras over 20-minute experiments, measuring latency and throughput metrics.

## Key Results
- End-to-end latency for suspicious object detection: 5.3–11.11 seconds (1–8 cameras)
- End-to-end latency for anomalous behavior detection: 7.3–20.78 seconds (1–8 cameras)
- Throughput: 32.41 FPS with 8 cameras

## Why This Works (Mechanism)

### Mechanism 1
- Claim: End-to-end latency remains bounded because AI processing is distributed across edge and cloud nodes.
- Mechanism: The edge node performs real-time object detection, tracking, and behavioral anomaly detection on incoming video frames. This local processing reduces the volume of data sent to the cloud, lowering transmission latency. The cloud node handles notification delivery and data aggregation using AWS services, which are optimized for low-latency operations.
- Core assumption: Edge processing is fast enough to keep up with incoming frames and the cloud notification pipeline is not a bottleneck.
- Evidence anchors:
  - [abstract] "The system uses deep learning models for object detection, person tracking, and behavioral anomaly detection, integrated with cloud and mobile notification services."
  - [section] "The edge node hosts a sophisticated deep learning pipeline, which employs multiple algorithms, including one high-level action anomaly detection model to potentially identify suspicious objects and anomalous activities within the area under surveillance."
  - [corpus] Found related work on edge-based video analytics, supporting the general approach but not this specific implementation.
- Break condition: If edge processing cannot keep up with the frame rate or if cloud notification services experience outages/delays.

### Mechanism 2
- Claim: Scalability is achieved by running independent AI pipelines per camera.
- Mechanism: Each camera has its own AI pipeline running on the edge node. This parallel processing allows the system to handle multiple cameras without a single bottleneck. The global node aggregates results and handles re-identification across cameras.
- Core assumption: The edge node hardware (CPU and GPUs) has sufficient resources to run multiple AI pipelines concurrently.
- Evidence anchors:
  - [abstract] "Experiments with 1–8 cameras show end-to-end latency for suspicious object detection ranging from 5.3 to 11.11 seconds..."
  - [section] "For each camera one AI algorithm pipeline is assigned for processing."
  - [corpus] Limited direct evidence; related work discusses distributed video analytics but not this specific multi-camera pipeline architecture.
- Break condition: When the number of cameras exceeds the edge node's processing capacity, causing pipeline queuing and increased latency.

### Mechanism 3
- Claim: Low-latency notifications are achieved through AWS SNS and direct mobile app integration.
- Mechanism: The cloud node uses AWS SNS to send push notifications directly to end-user devices. The mobile app is built using AWS AppSync for efficient data querying and real-time updates. This bypasses traditional polling mechanisms, reducing notification latency.
- Core assumption: The AWS infrastructure and mobile app are configured for optimal performance and the end-user's network connection is reliable.
- Evidence anchors:
  - [abstract] "...integrated with cloud and mobile notification services."
  - [section] "A cloud-based service sends push notifications to end-users devices to ensure that users are promptly notified in emergencies."
  - [corpus] Found related work on AWS-based notification systems, supporting the general approach but not this specific implementation.
- Break condition: If AWS SNS experiences delays or if the mobile app fails to receive notifications due to network issues.

## Architecture Onboarding

- Component map: Camera feed -> Edge AI pipeline -> Local database -> Global node (re-identification, analysis) -> Cloud node (SNS notification) -> Mobile app
- Critical path: Camera feed -> Edge AI pipeline -> Local database -> Global node (re-identification, analysis) -> Cloud node (SNS notification) -> Mobile app
- Design tradeoffs: Edge processing vs. cloud processing (latency vs. scalability), real-time detection vs. accuracy, privacy vs. security
- Failure signatures: High latency in edge processing (CPU/GPU overloaded), cloud notification delays (AWS service issues), mobile app not receiving notifications (network issues)
- First 3 experiments:
  1. Test single-camera end-to-end latency with a known suspicious object.

## Open Questions the Paper Calls Out

### Open Question 1
- Question: What is the optimal number of cameras for balancing latency and throughput in community-in-the-loop smart video surveillance systems?
- Basis in paper: [explicit] The paper shows that latency increases significantly when scaling from 4 to 8 cameras (11.11s vs 5.78s for object detection), while throughput remains relatively stable.
- Why unresolved: The paper only tests 1, 4, and 8 camera configurations without exploring intermediate values or determining an optimal trade-off point.
- What evidence would resolve it: Systematic testing of 2, 3, 5, 6, and 7 camera configurations to identify the inflection point where latency gains no longer justify the additional cameras.

### Open Question 2
- Question: How does community engagement in the design process affect system acceptance and privacy concerns in smart video surveillance?
- Basis in paper: [explicit] The paper emphasizes "community-in-the-loop" design and mentions privacy considerations but does not empirically measure community acceptance or privacy impact.
- Why unresolved: The paper focuses on technical implementation without validating whether community involvement actually improves system acceptance or addresses privacy concerns.
- What evidence would resolve it: Surveys or interviews with community members comparing acceptance levels between systems designed with and without community input.

### Open Question 3
- Question: What is the false positive rate of the behavioral anomaly detection system under realistic conditions?
- Basis in paper: [inferred] The paper mentions using thresholds to reduce false positives but does not report actual false positive rates or validate system accuracy against ground truth data.
- Why unresolved: The evaluation focuses on latency and throughput metrics rather than detection accuracy, making it impossible to assess real-world reliability.
- What evidence would resolve it: Testing the system against labeled video datasets with known anomalies and calculating precision, recall, and F1 scores under various conditions.

## Limitations
- The exact model configurations, hyperparameters, and training procedures for the GEPC anomaly detector are not fully specified, making exact replication challenging.
- The system's performance with more than 8 cameras remains unknown, as does its behavior under various network conditions and hardware failures.
- The community-in-the-loop design aspects are described but not quantitatively evaluated for their impact on system effectiveness.

## Confidence
- **High confidence**: The reported latency measurements and throughput (32.41 FPS with 8 cameras) are well-supported by the experimental methodology and results.
- **Medium confidence**: The scalability claims rely on reasonable assumptions about edge node capacity but lack detailed resource utilization data during testing.
- **Medium confidence**: The privacy preservation mechanisms are described conceptually but not rigorously evaluated for security vulnerabilities.
