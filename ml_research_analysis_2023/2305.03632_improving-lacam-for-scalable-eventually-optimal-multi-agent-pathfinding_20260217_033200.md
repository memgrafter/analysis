# Improving LaCAM for Scalable Eventually Optimal Multi-Agent Pathfinding

## Quick Facts
- arXiv ID: 2305.03632
- Source URL: https://arxiv.org/abs/2305.03632
- Reference count: 30
- Key outcome: LaCAM* solved 99% of 13,900 MAPF instances with up to 1,000 agents within 10 seconds on a standard desktop PC while ensuring eventual convergence to optima.

## Executive Summary
This work enhances LaCAM, a sub-optimal MAPF algorithm using lazy successor generation, in two ways: (i) LaCAM*, an anytime algorithm that eventually converges to optima, and (ii) improved successor generation to quickly obtain initial solutions. The algorithm uses a configuration generator (PIBT) to generate promising successors one at a time, guided by constraints in a tree structure, dramatically reducing the branching factor compared to classical MAPF approaches. Experiments demonstrate that LaCAM* significantly improves scalability, solving instances with up to 1,000 agents that were previously intractable for existing MAPF algorithms.

## Method Summary
LaCAM* treats MAPF as graph pathfinding on a configuration graph where nodes represent agent configurations. It uses lazy successor generation through a configuration generator (PIBT) that produces connected configurations given constraints from a tree structure. The algorithm maintains Open and Explored sets for high-level search, updating parent-child relationships when shorter paths are discovered using Dijkstra's algorithm on the developed search tree. An improved PIBT configuration generator includes swap operations to resolve livelocks in crowded scenarios. The algorithm continues searching after finding the first solution to ensure eventual convergence to optima.

## Key Results
- Solved 99% of 13,900 MAPF benchmark instances with up to 1,000 agents within 10 seconds
- Demonstrated significant improvement in scalability compared to existing MAPF algorithms
- Achieved eventual optimality through continuous tree refinement and parent relationship updates
- Effective livelock resolution through swap operation in improved PIBT configuration generator

## Why This Works (Mechanism)

### Mechanism 1
- Claim: LaCAM* uses lazy successor generation to dramatically reduce the branching factor in MAPF.
- Mechanism: Instead of generating all possible successor configurations for all agents (which is exponential in the number of agents), LaCAM* uses a configuration generator (PIBT) to generate only promising successors one at a time, guided by constraints in a tree structure.
- Core assumption: A good configuration generator can efficiently produce successors close to the goal, making the search space tractable.
- Evidence anchors:
  - [abstract] "LaCAM is a sub-optimal search-based algorithm that uses lazy successor generation to dramatically reduce the planning effort."
  - [section] "LaCAM tries to relieve this huge-branching-factor issue when a configuration generator is available."
  - [corpus] Weak evidence - no direct citation about lazy successor generation, but related papers mention configuration-based MAPF.

### Mechanism 2
- Claim: LaCAM* achieves eventual optimality by continuously refining the search tree and updating parent relationships.
- Mechanism: When LaCAM* finds the goal configuration, it doesn't terminate immediately. Instead, it keeps searching and updates parent-child relationships between nodes when a shorter path to a configuration is found, using Dijkstra's algorithm on the developed search tree.
- Core assumption: The search space is finite and all possible paths from start to goal will eventually be explored.
- Evidence anchors:
  - [abstract] "LaCAM* which eventually converges to optima, provided that solution costs are accumulated transition costs."
  - [section] "Each high-level node contains a set neigh that stores connected configurations and g-value that represents cost-to-come from the start S... LaCAM* updates neigh (Line 14). This is followed by updates of g-value and parent, performed by Dijkstra's algorithm."
  - [corpus] No direct evidence about eventual optimality through tree refinement.

### Mechanism 3
- Claim: The improved PIBT configuration generator with swap operation reduces planning effort by avoiding livelocks in crowded scenarios.
- Mechanism: PIBT sequentially assigns locations to agents while avoiding collisions. The improved version detects when two agents are stuck in a livelock (periodic swapping) and applies a swap operation to break the deadlock by having one agent temporarily move away from its goal.
- Core assumption: Livelocks in PIBT can be detected by pattern matching and resolved by allowing temporary detours.
- Evidence anchors:
  - [section] "Livelocks in PIBT can be resolved by swap operation... This is done by adjusting vertex scoring at Line 5 in Alg. 2."
  - [section] "The swap_required_and_possible function is a pattern detector and implementation-depending."
  - [corpus] No direct evidence about swap operation for livelock resolution in related papers.

## Architecture Onboarding

- Component map:
  - High-level search -> Constraint tree -> Configuration generator (PIBT) -> Pattern detector -> Dijkstra refinement

- Critical path:
  1. Initialize with start configuration and empty constraint tree
  2. Select node from Open, check if it's goal configuration
  3. If goal found, update N_goal but continue searching
  4. Pop constraint from tree, invoke low-level expansion
  5. Use configuration generator to produce new configuration
  6. If new configuration, create node and add to Open; if known, update neighbors and refine tree
  7. Discard redundant nodes when optimal solution is found

- Design tradeoffs:
  - Memory vs. speed: Storing all explored configurations (Explored table) vs. recomputing
  - Completeness vs. scalability: Maintaining constraint tree for completeness vs. simplified approach for speed
  - Solution quality vs. computation time: Continuing search for optimality vs. returning initial solution quickly

- Failure signatures:
  - Infinite loop in configuration generator: PIBT gets stuck in livelock
  - Memory overflow: Explored table grows too large for big instances
  - Non-termination: Search space not fully explored due to implementation bugs
  - Suboptimal solutions: Pattern detector fails to identify needed swap operations

- First 3 experiments:
  1. Run LaCAM* on a simple 2-agent grid with a narrow corridor to verify livelock detection and swap operation
  2. Test tree refinement on a small MAPF instance where initial solution can be improved through parent updates
  3. Benchmark LaCAM* with original PIBT vs. improved PIBT on instances known to cause livelocks

## Open Questions the Paper Calls Out

- Question: What is the optimal design of the pattern detector for swap_required_and_possible in PIBT?
- Basis in paper: [explicit] The paper states that the swap_required_and_possible function is a pattern detector whose implementation affects the runtime overhead and effectiveness of LaCAM. It mentions that well-tuned implementations can relax the search effort, but the authors do not aim for complete detectors.
- Why unresolved: The paper acknowledges that pattern detectors have runtime overhead and pitfalls that can be complemented by LaCAM, but does not specify what constitutes an optimal implementation.
- What evidence would resolve it: Comparative experiments showing runtime and success rates of LaCAM with various pattern detector implementations across diverse MAPF scenarios.

### Open Question 2
- Question: How can LaCAM* be modified to improve convergence speed for large instances with many agents?
- Basis in paper: [explicit] The paper notes that LaCAM* quickly finds initial solutions and converges to optimal ones for small instances, but convergence speed is slow in large instances due to finding new connections between known configurations becoming rare.
- Why unresolved: While the paper identifies the bottleneck (rare new connections), it does not propose specific modifications to accelerate convergence in large-scale scenarios.
- What evidence would resolve it: Experimental results demonstrating significantly faster convergence times for large instances after implementing proposed modifications to LaCAM*.

### Open Question 3

- Why unresolved: The authors focus on empirical evaluation and practical performance rather than theoretical complexity analysis.
