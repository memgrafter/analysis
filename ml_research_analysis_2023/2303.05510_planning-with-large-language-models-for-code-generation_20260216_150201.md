# Planning with Large Language Models for Code Generation

## Quick Facts
- arXiv ID: 2303.05510
- Source URL: https://arxiv.org/abs/2303.05510
- Reference count: 40
- Primary result: PG-TD achieves better pass rates on competitive programming benchmarks than baseline methods

## Executive Summary
This paper proposes Planning-Guided Transformer Decoding (PG-TD), a novel decoding algorithm that integrates tree search with pre-trained transformer models for code generation. The key innovation is using lookahead search guided by test cases to find tokens that lead to programs with higher pass rates. PG-TD leverages the transformer's next-token probabilities as heuristics within the planner and uses caching mechanisms to reduce redundant computation. The method is evaluated on competitive programming benchmarks and consistently outperforms baseline methods in terms of pass rates and strict accuracy, while also enabling controllable code generation through modified objective functions.

## Method Summary
PG-TD combines a pre-trained transformer model with tree search planning to guide code generation toward higher-quality programs. The algorithm uses an Upper Confidence bounds applied to Trees (P-UCB) strategy to balance exploration and exploitation during search. For each partial program, it evaluates the best possible completion using beam search and public test cases, allowing early pruning of paths that will fail. Two caching mechanisms are employed: tree structure cache to store beam search trees for repeated prefixes, and sequence cache to store the best complete programs found for each prefix. The method is model-agnostic and does not require fine-tuning the transformer backbone.

## Key Results
- PG-TD consistently outperforms baseline methods (beam search, sampling + filtering) on competitive programming benchmarks
- Achieves higher pass rates and strict accuracy across multiple datasets
- Enables controllable code generation by optimizing modified objective functions for code length and comment density
- Caching mechanisms significantly reduce computation time without sacrificing performance

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** PG-TD achieves better pass rates than baseline methods by using lookahead search guided by test cases during generation.
- **Mechanism:** The algorithm integrates a tree search planner that explores multiple token sequences in parallel. For each partial program, it evaluates the best possible completion using beam search and the public test cases. This lookahead allows early pruning of paths that will fail, and bias toward paths that pass more tests.
- **Core assumption:** The transformer's next-token probabilities are good enough to guide the tree search toward high-quality completions, even without fine-tuning.
- **Break condition:** If the transformer's probabilities are not well-calibrated or the search space is too large, the planner may waste budget exploring unpromising paths.

### Mechanism 2
- **Claim:** Information sharing via caching between the transformer beam search and tree search reduces redundant computation.
- **Mechanism:** Two caches are maintained: (1) tree structure cache stores the beam search tree for each partial program so repeated lookahead from the same prefix reuses the tree; (2) sequence cache stores the best complete program found for each prefix so future iterations can return it directly without re-running beam search.
- **Core assumption:** Many tree search iterations will revisit the same partial programs, making caching effective.
- **Break condition:** If the beam size is large or the problem space is highly diverse, caching may store many unique sequences, reducing hit rate and wasting memory.

### Mechanism 3
- **Claim:** PG-TD is model-agnostic and does not require fine-tuning the transformer backbone.
- **Mechanism:** The same transformer model is used both for standard generation and as a heuristic provider inside the planner. By optimizing the planner's reward (pass rate) instead of the model's likelihood, PG-TD adapts to the code generation objective without changing the model weights.
- **Core assumption:** The pre-trained transformer already encodes sufficient knowledge about code syntax and semantics to generate viable programs.
- **Break condition:** If the transformer is trained on a domain very different from the target code, its guidance may be poor, requiring fine-tuning for acceptable performance.

## Foundational Learning

- **Concept:** Markov Decision Process formulation of code generation
  - Why needed here: Provides a formal framework where the planner can optimize pass rate as a reward, rather than token likelihood.
  - Quick check question: In the MDP formulation, what is the reward for a partial program (i.e., before terminal token)?
    - **Answer:** 0 (only complete programs receive pass rate as reward).

- **Concept:** Upper Confidence bounds applied to Trees (UCT) / P-UCB in MCTS
  - Why needed here: Balances exploration of under-visited nodes with exploitation of high-value nodes, using transformer probabilities as a prior.
  - Quick check question: What does the exploration parameter c control in P-UCB?
    - **Answer:** It scales the exploration bonus; higher c leads to more exploration of less-visited nodes.

- **Concept:** Beam search vs. sampling in transformer decoding
  - Why needed here: Beam search gives the most likely completions deterministically, while sampling introduces diversity; PG-TD uses beam search inside the planner for consistent evaluation.
  - Quick check question: In PG-TD, why is beam size typically set to 1 in the evaluation step?
    - **Answer:** To get a single deterministic completion for each partial program, simplifying reward computation and caching.

## Architecture Onboarding

- **Component map:** Problem description -> Transformer encoder -> Tree search planner
- **Critical path:**
  1. Start with root node (problem description + empty program)
  2. Tree search selects node using P-UCB
  3. Expand node: get top-k next tokens from transformer
  4. For each child, run beam search to generate complete program
  5. Evaluate program on public test cases -> reward
  6. Backpropagate reward up the tree, update Q values
  7. Repeat until budget exhausted
  8. Return program with highest reward

- **Design tradeoffs:**
  - Tree search width (k) vs. depth vs. transformer budget
  - Beam size (b) vs. diversity of completions vs. computational cost
  - Exploration parameter (c) vs. exploitation of known good paths
  - Cache size vs. memory usage vs. recomputation savings

- **Failure signatures:**
  - Pass rate stuck near beam search baseline -> planner not exploring effectively
  - Runtime much slower than beam search baseline -> caching ineffective or budget too large
  - Compilation/runtime errors high -> transformer beam search generating syntactically invalid code

- **First 3 experiments:**
  1. Run PG-TD with k=3, b=1, c=4 on a small APPS subset; compare pass rate vs. plain beam search
  2. Enable caching and measure reduction in beam search calls and runtime
  3. Vary c (2, 4, 6) and plot pass rate vs. computation time to find sweet spot

## Open Questions the Paper Calls Out
The paper does not explicitly call out open questions, but several implicit questions remain regarding the impact of different beam sizes, comparison with alternative tree search algorithms, and the effects of various reward functions on performance.

## Limitations
- Effectiveness depends heavily on the quality of transformer's next-token probabilities as heuristics
- Lack of quantitative analysis of caching mechanisms' hit rates and memory overhead
- Performance generalization to domains outside competitive programming remains untested
- No detailed hyperparameter sensitivity analysis provided

## Confidence
- **High confidence:** The core mechanism of integrating tree search with transformer decoding is well-explained and theoretically sound
- **Medium confidence:** Claims of outperforming baselines are supported by experiments, but lack of detailed hyperparameter analysis makes it difficult to isolate key contributors
- **Low confidence:** Model-agnostic assertion is plausible but untested across different model families or domains; caching benefits stated without quantitative backing

## Next Checks
1. **Ablation study on caching:** Measure and report the cache hit rates and memory usage for both tree structure and sequence caches. Compare runtime and pass rates with and without caching to quantify the trade-offs.

2. **Hyperparameter sensitivity analysis:** Systematically vary the exploration parameter c, beam size b, and max children k across a range of values. Plot pass rate vs. computation time to identify optimal settings and understand the robustness of PG-TD to hyperparameter choices.

3. **Cross-domain generalization:** Apply PG-TD to code generation tasks outside competitive programming (e.g., Python scripts for data analysis or web development). Compare performance to baseline methods and assess whether the planner's benefits transfer to other coding styles or problem types.
