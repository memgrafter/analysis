# Candidate Soups: Fusing Candidate Results Improves Translation Quality for Non-Autoregressive Translation

## Quick Facts
- arXiv ID: 2301.11503
- Source URL: https://arxiv.org/abs/2301.11503
- Reference count: 19
- Improves NAT translation quality by 2.51-2.92 BLEU points while maintaining 7.6x speedup over AT models

## Executive Summary
This paper introduces Candidate Soups, a method that fuses multiple candidate translations from non-autoregressive translation (NAT) models to improve translation quality while preserving NAT's fast inference speed. The core idea is to identify common subsequences across candidate translations and select segments with the highest log-probability scores to generate a final translation. Experiments on WMT'14 EN-DE and WMT'16 EN-RO show significant improvements over base NAT models, outperforming autoregressive models on three translation tasks while achieving 7.6x speedup.

## Method Summary
Candidate Soups generates 3-7 candidate translations from NAT models with different length predictions, then identifies common subsequences across all candidates. These common tokens are treated as highly confident predictions and directly included in the final translation. For remaining segments between common tokens, an autoregressive teacher model re-scores each candidate translation in parallel, selecting the segment with the highest average log-probability score. This approach leverages model uncertainty to improve translation quality while maintaining the fast inference speed characteristic of NAT models.

## Key Results
- Improves Vanilla NAT by 2.51 BLEU points on WMT'14 EN-DE
- Outperforms strong autoregressive models on three translation tasks
- Achieves 7.6x speedup compared to autoregressive models
- Significant improvements on long sentences (+7.51 BLEU for 40-60 tokens, +5.01 BLEU for >60 tokens)

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Candidate Soups improves translation quality by fusing common subsequences from multiple candidate translations.
- Mechanism: The method identifies tokens that appear in the same order across all candidate translations (common subsequences) and treats them as highly confident predictions. These are directly added to the final translation. For remaining segments between common tokens, it selects the segment with the highest average log-probability score.
- Core assumption: Tokens that appear consistently across multiple candidate translations generated with different lengths represent the model's most confident predictions due to reduced uncertainty.
- Evidence anchors:
  - [abstract] "Candidate Soups (CDS) can fully use the valuable information in the different candidate translations through model uncertainty."
  - [section 3.1] "we consider tokens that appear in all candidate results with the same word order as certain components"
- Break condition: If the NAT model produces candidate translations with very low diversity (e.g., nearly identical outputs), the common subsequence approach provides minimal benefit since most tokens would already match.

### Mechanism 2
- Claim: Using an autoregressive teacher model for re-scoring enables efficient selection of optimal translation segments.
- Mechanism: After identifying common subsequences, the remaining segments are scored using an AT model that can decode in parallel during re-scoring. The segment with the highest average log-probability is selected for each gap between common tokens.
- Core assumption: AT models can provide reliable probability estimates for NAT-generated segments, and parallel decoding during re-scoring keeps latency low.
- Evidence anchors:
  - [abstract] "while maintaining the inference speed of NAT models"
  - [section 3.1] "we can quickly calculate each edge value by using the AT model to re-score each candidate translation"
- Break condition: If the AT re-scoring model is significantly weaker than the NAT base model, it may select suboptimal segments, degrading overall quality.

### Mechanism 3
- Claim: Introducing length uncertainty during inference creates diverse candidate translations that contain complementary information.
- Mechanism: NAT models predict translation length as part of generation. By generating multiple candidates with different predicted lengths, the model produces translations with varied token sequences, some of which contain correctly translated segments that others miss.
- Core assumption: NAT models with length prediction will generate meaningfully different translations when given different length targets, creating diversity that captures different aspects of the correct translation.
- Evidence anchors:
  - [abstract] "unlike previous approaches that pick the individual result and discard the remainders"
  - [section 3.3] "When there is a disagreement between candidate results, Candidate Soups will find the next token that all candidate translations predict in common"
- Break condition: If the NAT model's length prediction is highly accurate and consistent, generating multiple candidates with different lengths may produce redundant translations with minimal diversity.

## Architecture Onboarding

- Component map:
  - NAT base model -> Common subsequence detector -> AT re-scoring model -> Fuser module

- Critical path: NAT generation → Common subsequence detection → AT re-scoring → Final fusion
- Design tradeoffs:
  - Number of candidates (3-7): More candidates provide more diversity but increase computation
  - AT model size for re-scoring: Larger models provide better scoring but increase latency
  - Length uncertainty vs other uncertainty methods: Length uncertainty ensures quality diversity, while dropout/layer-based methods may be more general but require tuning

- Failure signatures:
  - Minimal BLEU improvement: Candidates are too similar (low diversity) or AT re-scoring is poor
  - Increased latency: AT model is too large or too many candidates are generated
  - Translation quality degradation: AT model selects wrong segments or common subsequence detection fails

- First 3 experiments:
  1. Test on WMT'14 EN-DE with 3 candidates and AT 6E-6D re-scoring to establish baseline performance
  2. Vary candidate count (3, 5, 7) to find optimal tradeoff between quality and speed
  3. Replace AT 6E-6D with smaller AT 3E-1D to measure impact on quality-speed tradeoff

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the performance of Candidate Soups vary with different numbers of candidate translations across different NAT models?
- Basis in paper: [explicit] The paper shows that translation quality generally increases with more candidates up to a threshold, after which it fluctuates or slightly decreases.
- Why unresolved: The optimal number of candidates may depend on the specific NAT model and translation task, requiring further investigation to determine ideal settings for different scenarios.
- What evidence would resolve it: Systematic experiments varying the number of candidates for each NAT model and translation task, showing performance curves and identifying optimal points.

### Open Question 2
- Question: Can Candidate Soups be effectively combined with other uncertainty introduction methods beyond length prediction?
- Basis in paper: [explicit] The paper mentions two alternative methods - using predictions from different decoder layers and maintaining dropout during inference - but finds length-based uncertainty most effective.
- Why unresolved: The relative effectiveness of different uncertainty methods may depend on model architecture, training procedures, or specific translation tasks, requiring more comprehensive evaluation.
- What evidence would resolve it: Comparative experiments systematically evaluating all uncertainty methods across different NAT architectures and translation tasks, measuring both performance gains and computational overhead.

### Open Question 3
- Question: What is the impact of Candidate Soups on very long sentences and how does it compare to traditional autoregressive models?
- Basis in paper: [explicit] The paper shows Candidate Soups significantly improves performance on long sentences (40-60 tokens +7.51 BLEU, >60 tokens +5.01 BLEU) compared to vanilla NAT.
- Why unresolved: While Candidate Soups helps with long sentences, the absolute performance compared to autoregressive models and the scaling behavior for extremely long sentences remains unclear.
- What evidence would resolve it: Detailed analysis of translation quality across sentence length ranges for both NAT with Candidate Soups and autoregressive models, including statistical significance testing and error analysis for the longest sentences.

## Limitations

- Implementation details uncertainty: The paper lacks precise specifications for the common subsequence detection algorithm and tie-breaking rules
- Dataset preprocessing variability: Exact knowledge distillation process and AT teacher model specifications are not detailed
- Speed measurement conditions: Claimed 7.6x speedup depends on specific hardware configurations and batch sizes

## Confidence

**High confidence**: The core Candidate Soups algorithm (finding common subsequences and selecting high-probability segments) is well-specified and should reproduce consistently across implementations.

**Medium confidence**: The quantitative results showing 2.51-2.92 BLEU point improvements and 7.6x speedup claims, as these depend on specific implementation choices and measurement conditions.

**Low confidence**: The comparison to "strong AR models" is somewhat vague, as the paper doesn't specify which exact AT models or configurations were used for comparison.

## Next Checks

**Check 1: Diversity validation** - Measure the pairwise BLEU scores between candidate translations generated by the NAT model. If the average pairwise BLEU exceeds 70%, the diversity is insufficient for Candidate Soups to provide meaningful improvements.

**Check 2: Common subsequence accuracy** - Implement a precision/recall evaluation for the common subsequence detection algorithm. Measure what percentage of truly common tokens are correctly identified versus false positives, as this directly impacts translation quality.

**Check 3: Ablation on candidate count** - Systematically vary the number of candidates from 3 to 7 and measure both BLEU improvement and inference latency. This validates the claimed tradeoff between quality gains and computational overhead.
