# Multilingual End to End Entity Linking

## Quick Facts
- arXiv ID: 2306.08896
- Source URL: https://arxiv.org/abs/2306.08896
- Reference count: 24
- BELA is the first multilingual end-to-end entity linking system, covering 97 languages with 53 samples/sec inference speed on a single GPU.

## Executive Summary
BELA introduces the first multilingual end-to-end entity linking system that jointly detects and links entities in a single pass. The system uses a bi-encoder architecture with kNN search, covering 97 languages through a shared language-agnostic entity index. It achieves competitive results on English end-to-end datasets while demonstrating strong multilingual performance, processing 53 samples per second on a single GPU.

## Method Summary
BELA employs a bi-encoder architecture with separate mention and entity encoders based on XLM-R. The system is trained in two stages: first pre-training the entity encoder on Wikipedia hyperlinks, then jointly training mention detection, entity disambiguation, and rejection heads on Wikipedia data. Mentions are detected and linked through kNN search against a language-agnostic entity index built from Wikipedia titles and descriptions across 97 languages. The model uses hard-negative training and optimizes all components jointly with summed losses.

## Key Results
- End-to-end F1 of 59.0 on Mewsli-9'-test, with mention detection recall of 61.2 and precision of 56.9
- Competitive performance with English-only models despite being highly multilingual
- Inference speed of 53 samples per second on a single GPU
- Covers 97 languages through a shared entity index with approximately 16 million entities

## Why This Works (Mechanism)

### Mechanism 1
- Claim: BELA achieves multilingual end-to-end entity linking by using a shared language-agnostic entity index.
- Mechanism: The entity index is built from Wikipedia titles and descriptions across 97 languages, with each entity assigned a single description language based on mention frequency. This allows BELA to link mentions in any language to entities encoded using descriptions in other languages.
- Core assumption: A language-agnostic entity index can represent entities effectively across multiple languages without requiring separate indexes per language.
- Evidence anchors:
  - [abstract] "Following Botha et al. (2020), mentions in any language are linked to a language-agnostic entity index, enabling high coverage of approximately 16 million entities and 97 languages."
  - [section 3] "We use Wikipedia titles as t(ei) and the first paragraph of the article as d(ei). We use the same data-driven selection heuristic as Botha et al. (2020) to select a single description language li ∈ L for each entity based on the number of mentions of each entity in different languages."
- Break condition: If the chosen description language for an entity is significantly different from the mention language, performance may degrade due to semantic drift or translation issues.

### Mechanism 2
- Claim: The bi-encoder architecture enables efficient end-to-end linking by separating mention and entity encoding into independent components.
- Mechanism: BELA uses separate mention and entity encoders based on XLM-R. Mention encodings are computed once per mention, then used as queries in a kNN search against pre-computed entity embeddings, avoiding expensive cross-attention between mentions and entities.
- Core assumption: Mention and entity encodings can be computed independently without loss of disambiguation accuracy.
- Evidence anchors:
  - [abstract] "BELA combines and extends progress that EL systems have made in recent years across several dimensions: Transformer-based architectures, which achieved significant performance improvements on the ED task..."
  - [section 4.2] "As in BLINK, our ED model is based on dense retrieval, i.e. the encoded mention is used as query in a kNN search among entity embeddings."
- Break condition: If mention context is crucial for disambiguation and cannot be captured by independent encoding, the bi-encoder approach may underperform cross-encoder methods.

### Mechanism 3
- Claim: Joint training of mention detection, entity disambiguation, and rejection heads enables end-to-end optimization for entity linking.
- Mechanism: BELA trains MD, ED, and R heads jointly with summed losses, allowing the model to optimize for the entire entity linking pipeline rather than individual components in isolation.
- Core assumption: Joint optimization of the three components leads to better overall performance than training them separately and combining.
- Evidence anchors:
  - [abstract] "BELA is composed of a Mention Detection (MD), Entity Disambiguation (ED) and Rejection (R) head... MD, ED, and R are trained jointly on another subset of Wikipedia data using 27M samples."
  - [section 5.2] "Outputs from one component are fed as input to the next and losses are summed together."
- Break condition: If the optimization of one component conflicts with another (e.g., MD recall vs ED precision), joint training may lead to suboptimal performance for individual components.

  - Why needed here: BELA uses dense retrieval with kNN search to efficiently match mention encodings to entity embeddings in a 16M entity index.
  - Quick check question: What is the main advantage of using dense retrieval over sparse retrieval methods like TF-IDF in entity linking?

  - Why needed here: BELA's bi-encoder design allows it to process all mentions in a passage in a single forward pass, unlike cross-encoder approaches that require separate passes per mention.
  - Quick check question: How does the computational complexity of a bi-encoder architecture scale with the number of mentions compared to a cross-encoder?

- Concept: Multilingual representation learning
  - Why needed here: BELA uses XLM-R to handle 97 languages and creates a language-agnostic entity index, requiring understanding of how multilingual models represent different languages.
  - Quick check question: What challenges arise when linking mentions in one language to entities primarily described in another language?

## Architecture Onboarding

- Component map: Input text -> Mention Encoder -> Mention Detection -> Mention Encoding -> kNN Search -> Entity Encoder -> Entity Linking -> Rejection Head -> Final output

- Critical path: Input text → Mention Encoder → Mention Detection → Mention Encoding → kNN Search → Entity Encoder → Entity Linking → Rejection Head → Final output

- Design tradeoffs:
  - Bi-encoder vs cross-encoder: Faster inference but potentially lower accuracy
  - Language-agnostic index: Simpler architecture but may miss language-specific nuances
  - Joint training vs separate training: End-to-end optimization but more complex training pipeline

- Failure signatures:
  - Low recall: Mention detection threshold β too high or mention encoder not capturing context well
  - Low precision: Rejection threshold γ too low or entity encoder not distinguishing similar entities
  - Slow inference: kNN search not properly indexed or using suboptimal FAISS configuration

  3. Profile inference speed with different batch sizes to find throughput sweet spot on target GPU

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does BELA's multilingual performance compare to other multilingual EL systems when more diverse training data is available?
- Basis in paper: [inferred] The paper notes that BELA's performance varies significantly across languages (15-74 F1) and hypothesizes this could be due to varying language coverage at training, tokenizer performance differences, and general language-dependent performance differences. They also show that performance increases significantly when trained on exhaustively labeled data.
- Why unresolved: The paper only compares BELA to monolingual models on English datasets and to mGENRE (a multilingual model) on ED only. No direct comparison to other multilingual end-to-end EL systems exists because BELA is the first of its kind.
- What evidence would resolve it: Benchmarking BELA against future multilingual end-to-end EL systems or creating multilingual extensions of existing monolingual systems and comparing performance across diverse languages.

### Open Question 2
- Question: Can BELA's architecture be improved by incorporating cross-attention between mentions and entity descriptions to boost accuracy without significantly impacting inference speed?
- Basis in paper: [explicit] The authors note that BELA performs competitively with English-only models "despite being highly multilingual and lacking sophisticated cross-attention between mentions and entity description, which would make the system impractically slow."
- Why unresolved: The paper prioritizes efficiency over maximum accuracy, leaving open the question of whether more sophisticated attention mechanisms could improve results within reasonable speed constraints.
- What evidence would resolve it: Implementing and benchmarking BELA variants with different levels of cross-attention (e.g., sparse attention, local attention) and measuring the accuracy-speed tradeoff curves.

### Open Question 3
- Question: How does BELA's under-labelling problem in datasets like TAC-KBP2015 affect the validity of its reported precision metrics, and what is the true precision when accounting for all correct entity links?
- Basis in paper: [explicit] The authors acknowledge that TAC-KBP2015 and similar datasets are "under-labeled for end-to-end linking" and provide examples where BELA correctly detects entities that aren't considered true positives due to missing annotations.
- Why unresolved: The precision metrics reported are artificially low because the gold standard is incomplete, making it impossible to determine BELA's actual precision without exhaustive labeling.
- What evidence would resolve it: Manually annotating a representative sample of BELA's predictions on under-labeled datasets to determine the proportion of false positives versus missed gold annotations.

## Limitations

- Evaluation on non-English languages is limited to a single German dataset with only 53 test samples, providing minimal empirical evidence for multilingual performance claims
- Critical hyperparameters and exact training procedures are not fully specified, potentially impacting reproducibility
- Inference speed claims lack context regarding hardware specifications and batch size

## Confidence

**High Confidence**: The architectural design and methodology are well-established. The use of bi-encoder architecture, kNN search, and joint training follows established practices in the field.

**Medium Confidence**: The technical implementation details are sufficiently specified for reproduction, including the use of XLM-R-large, specific data sources (Wikipedia), and evaluation metrics.

**Low Confidence**: Claims about multilingual performance and efficiency across 97 languages are not adequately supported by empirical evidence. The evaluation focuses heavily on English with minimal testing in other languages.
