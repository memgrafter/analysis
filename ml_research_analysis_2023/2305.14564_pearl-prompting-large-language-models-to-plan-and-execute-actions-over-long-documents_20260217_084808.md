# PEARL: Prompting Large Language Models to Plan and Execute Actions Over Long Documents

## Quick Facts
- arXiv ID: 2305.14564
- Source URL: https://arxiv.org/abs/2305.14564
- Reference count: 40
- PEARL achieved 70.9% accuracy on QuALITY questions requiring long context, outperforming zero-shot (64.3%) and chain-of-thought (65.9%) baselines

## Executive Summary
PEARL is a three-stage prompting framework designed to enable complex reasoning over long documents by decomposing the problem into action mining, plan formulation, and plan execution. The framework mines domain-specific actions from training questions, generates executable plans using these actions, and executes them step-by-step over the document. Evaluated on a subset of the QuALITY dataset requiring reasoning over long narrative texts, PEARL demonstrated significant improvements over traditional prompting approaches. The method shows that structured decomposition of reasoning tasks can effectively address the limitations of LLMs when dealing with lengthy documents.

## Method Summary
PEARL implements a three-stage prompting approach using GPT-4: (1) Action mining extracts a domain-specific set of executable actions from training questions and seed actions, (2) Plan generation formulates executable plans by mapping questions to sequences of these actions without seeing the document, and (3) Plan execution evaluates each action against the document text in sequence to produce the final answer. The framework includes self-correction to validate plan syntax and self-refinement to improve plan demonstrations before using them as in-context examples. The approach was evaluated on 1,000 questions from the QuALITY dataset requiring long context reasoning.

## Key Results
- PEARL achieved 70.9% accuracy on questions requiring long context reasoning, outperforming zero-shot (64.3%) and chain-of-thought (65.9%) baselines
- Ablation experiments confirmed each stage of PEARL is critical to performance
- Human evaluation found most generated plans to be reasonable, though some included unnecessary steps or missed critical information

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The three-stage decomposition (action mining → plan formulation → plan execution) enables complex reasoning over long documents by breaking down a hard problem into manageable sub-problems.
- Mechanism: Each stage handles a specific subtask that can be addressed with simpler prompting strategies. Action mining creates a domain-specific vocabulary of executable actions. Plan formulation maps questions to sequences of these actions. Plan execution evaluates each action against the document text in sequence.
- Core assumption: Decomposing complex reasoning into smaller, well-defined actions reduces cognitive load on the LLM and improves accuracy compared to direct long-document reasoning.
- Evidence anchors:
  - [abstract] "PEARL outperforms zero-shot and chain-of-thought prompting on this dataset, and ablation experiments show that each stage of PEARL is critical to its performance."
  - [section 3] "Each stage in PEARL is achieved via zero-shot or few-shot prompting of an LLM... Each stage of PEARL — action mining, plan decomposition, and plan execution — is implemented by applying zero-shot or few-shot prompting to an LLM."
- Break condition: If action mining fails to produce useful actions, or if plan execution cannot handle the intermediate results from previous actions, the entire framework breaks down.

### Mechanism 2
- Claim: Using mined actions as an intermediate representation allows the model to plan without seeing the full document, reducing prompt size and enabling few-shot demonstrations.
- Mechanism: The plan generation stage operates only on questions and the mined action set, not the document text. This keeps the prompt small enough to include in-context examples. The document is only introduced during plan execution.
- Core assumption: The action set captures sufficient reasoning patterns to generate valid plans without document context.
- Evidence anchors:
  - [section 3.2] "When generating the plan, we do not show the LLM the entire document as input, which provides ample space for incorporating few-shot in-context examples."
  - [section 4.1] "As each of the stages in PEARL has critical hyperparameters and implementation details, we describe our specific configurations here."
- Break condition: If the action set is too small or too large (see Figure 7), plan generation quality degrades.

### Mechanism 3
- Claim: Self-correction and self-refinement steps improve the reliability of LLM-generated plans by catching syntax errors and low-quality examples.
- Mechanism: Invalid plans trigger error messages that are fed back to the LLM for correction. Generated plans are executed and evaluated; poor performers are refined before being used as in-context examples.
- Core assumption: The LLM can recognize and fix its own plan generation errors when given explicit feedback.
- Evidence anchors:
  - [section 3.4] "To address this issue, similar to Shinn et al. (2023), we include a self-correction step prior to plan execution and a self-refinement step before incorporating model-generated plans as in-context few-shot examples."
  - [section 5] "Self-refinement improves performance: To reduce human input, the majority of the plan generation demonstrations for PEARL are generated by the LLM with self-refinement. We observe that self-refinement is critical to performance: without it, the overall accuracy drops nearly 3 absolute points."
- Break condition: If the LLM fails to correct plans within the retry limit (only 4 out of 1000 examples in their setup), it falls back to zero-shot baseline.

## Foundational Learning

- Concept: Prompt engineering with few-shot examples
  - Why needed here: Each stage uses carefully structured prompts with in-context demonstrations to guide LLM behavior.
  - Quick check question: What is the difference between zero-shot and few-shot prompting, and why does few-shot work better for plan generation in PEARL?

- Concept: Action space design and abstraction
  - Why needed here: The action mining stage requires balancing specificity (useful for reasoning) with generality (reusable across questions).
  - Quick check question: Why does PEARL use a learned action set rather than a fixed predefined toolbox like Toolformer?

- Concept: Error propagation in multi-stage systems
  - Why needed here: Each stage's output becomes the next stage's input, so errors compound through the pipeline.
  - Quick check question: How does PEARL mitigate error propagation, and what are the main sources of error in their framework?

## Architecture Onboarding

- Component map: Action Mining Module -> Plan Generation Module -> Plan Execution Module -> Answer Mapping -> Accuracy
- Critical path: Question → Action Mining → Plan Generation → Plan Execution → Answer Mapping → Accuracy
- Design tradeoffs:
  - Action granularity vs. plan complexity: Too many actions make plans hard to execute; too few limit expressiveness
  - Document visibility vs. prompt size: Hiding document during plan generation enables few-shot examples but requires the plan to be sufficiently expressive
  - Human input vs. automation: Self-refinement reduces human effort but may introduce noise if not properly validated
- Failure signatures:
  - Action mining produces duplicate or overly specific actions → Plan generation becomes inefficient
  - Plans fail syntax validation → Self-correction retries until fallback
  - Plan execution produces incorrect intermediate results → Final answer is wrong even if plan is reasonable
  - Answer mapping fails to match any option → False negative even with correct generative answer
- First 3 experiments:
  1. Test action mining with a small training set and verify the action set size and diversity
  2. Test plan generation with a simple question and manually verify the generated plan structure
  3. Test end-to-end execution on a single example to verify the complete pipeline works before scaling

## Limitations
- Evaluation is limited to a specific subset of 1,000 questions from the QuALITY dataset, which may not generalize to other long-document reasoning tasks
- The paper doesn't report on robustness to different document types, domains, or question styles
- While self-correction and self-refinement are implemented, the paper doesn't provide detailed error analysis of what types of plan generation failures these mechanisms successfully address

## Confidence
- **High Confidence**: The core claim that PEARL outperforms zero-shot and chain-of-thought baselines on the evaluated dataset subset is well-supported by the experimental results (70.9% vs 64.3% and 65.9% accuracy)
- **Medium Confidence**: The mechanism explanation for why decomposition into three stages improves performance is plausible based on the ablation study, but the paper doesn't provide detailed analysis of which specific stage failures most impact overall accuracy
- **Medium Confidence**: The claim that action mining enables planning without document context is supported by the experimental design, though the relationship between action set size and plan quality (Figure 7) suggests this may not be universally optimal

## Next Checks
1. **Error Analysis**: Conduct detailed analysis of the 4 out of 1000 examples where self-correction failed, and examine the types of plan generation errors that persist despite the self-correction mechanism
2. **Action Set Sensitivity**: Systematically vary the action set size beyond the tested range to identify the optimal number of actions for different question complexity levels and document types
3. **Cross-Dataset Validation**: Test PEARL on a different long-document reasoning dataset (such as NarrativeQA or QAngaroo) to assess generalization beyond the QuALITY dataset subset used in the paper
