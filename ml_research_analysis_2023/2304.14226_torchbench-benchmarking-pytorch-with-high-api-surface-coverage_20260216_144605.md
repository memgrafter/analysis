# TorchBench: Benchmarking PyTorch with High API Surface Coverage

## Quick Facts
- arXiv ID: 2304.14226
- Source URL: https://arxiv.org/abs/2304.14226
- Authors: 
- Reference count: 40
- Key outcome: Introduces TorchBench, a comprehensive benchmark suite covering 2.3x more PyTorch API surface than MLPerf, successfully identifying and fixing performance bugs in PyTorch

## Executive Summary
TorchBench is a comprehensive benchmark suite designed to evaluate PyTorch performance across its extensive API surface. The suite includes 84 deep learning models spanning six domains and has been integrated into PyTorch's continuous integration system. Unlike existing benchmarks, TorchBench covers 2.3x more PyTorch API surface than MLPerf, enabling more thorough performance characterization and regression detection. The benchmark has already proven valuable in identifying and resolving multiple performance issues, including GPU idleness and data movement problems.

## Method Summary
TorchBench was developed through a systematic approach to model selection and benchmarking. The team analyzed PyTorch's API surface using call graph analysis to identify underrepresented operations, then curated models across six domains (CV, NLP, Recommendation, Speech, Multimodal, and GNN) to maximize coverage. The benchmark suite includes both training and inference workloads, with each model tested under multiple scenarios. Performance measurements were conducted on NVIDIA A100 and AMD MI250X GPUs, comparing both native PyTorch execution and TorchInductor-accelerated versions. The benchmarks were integrated into PyTorch's CI/CD pipeline for continuous performance monitoring.

## Key Results
- TorchBench covers 2.3x more PyTorch API surface than MLPerf
- TorchInductor achieved average speedups of 1.34x for training and 1.46x for inference models
- Successfully identified commits causing up to 51.37x performance slowdowns
- GPU idleness and data movement issues were detected and resolved through benchmark-driven development

## Why This Works (Mechanism)
TorchBench works by providing comprehensive coverage of PyTorch's API surface through diverse model selection and systematic benchmarking. The mechanism leverages continuous integration integration to detect performance regressions early, while the extensive model coverage ensures that optimization efforts benefit a wide range of use cases. The benchmark's effectiveness stems from its ability to characterize performance across different hardware configurations and compiler implementations, enabling targeted optimizations and bug fixes.

## Foundational Learning

**PyTorch API Surface Coverage**
- Why needed: Understanding which PyTorch operations are frequently used helps prioritize optimization efforts
- Quick check: Analyze call graphs from production PyTorch applications to identify coverage gaps

**Continuous Integration Performance Testing**
- Why needed: Early detection of performance regressions prevents accumulation of technical debt
- Quick check: Monitor CI test duration and failure rates to ensure benchmark integration is sustainable

**Compiler-Aware Benchmarking**
- Why needed: Different compilers (native PyTorch vs. TorchInductor) have distinct performance characteristics
- Quick check: Compare execution traces across compilers to identify optimization opportunities

## Architecture Onboarding

**Component Map**
TorchBench -> Model Loader -> Execution Engine -> Performance Metrics -> CI/CD Integration

**Critical Path**
Model loading and execution constitute the critical path, where each benchmark must load model weights, prepare data, execute forward/backward passes, and collect performance metrics within a bounded time window to maintain CI/CD efficiency.

**Design Tradeoffs**
The benchmark prioritizes comprehensive API coverage over absolute performance measurement precision, accepting longer execution times to maximize insight value. This tradeoff enables better regression detection but requires careful CI/CD integration to avoid excessive build times.

**Failure Signatures**
Performance regressions typically manifest as increased execution time, GPU idleness, or unexpected memory usage patterns. The benchmark framework captures these through time-series metrics and hardware utilization monitoring.

**3 First Experiments**
1. Run a single model with TorchInductor vs native PyTorch to verify baseline performance difference
2. Execute the smallest model in each domain to validate CI/CD integration
3. Compare performance across different batch sizes to establish scaling characteristics

## Limitations

- Model selection may introduce bias toward specific use cases rather than representing full PyTorch diversity
- Results rely on specific hardware configurations, limiting generalizability to other GPU architectures
