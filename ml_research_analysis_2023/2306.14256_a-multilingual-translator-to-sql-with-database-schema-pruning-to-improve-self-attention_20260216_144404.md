# A Multilingual Translator to SQL with Database Schema Pruning to Improve Self-Attention

## Quick Facts
- arXiv ID: 2306.14256
- Source URL: https://arxiv.org/abs/2306.14256
- Authors: 
- Reference count: 27
- Primary result: Schema pruning + multilingual mT5 increases Spider validation accuracy from 0.718 to 0.736

## Executive Summary
This paper addresses the challenge of long input sequences in transformer-based natural language to SQL (NL2SQL) translation, where self-attention scales quadratically with input length. The authors propose two techniques: database schema pruning to remove irrelevant tables and columns before processing, and a multilingual approach using mT5-large fine-tuned with data-augmented Spider dataset in English, Portuguese, Spanish, and French. Schema pruning reduces the input size to fit within the 512-token limit while preserving relevant information. The multilingual approach leverages data augmentation to improve performance. The proposed method increased the exact set match accuracy from 0.718 to 0.736 on the Spider validation set.

## Method Summary
The authors tackle the problem of long input sequences in NL2SQL by proposing database schema pruning and a multilingual approach. Schema pruning analyzes training queries for each database, identifies unused tables and columns, and removes them before tokenization, reducing the input length. The multilingual approach uses mT5-large fine-tuned on English, Portuguese, Spanish, and French translations of the Spider dataset, with schema tokens kept in English. This data augmentation exposes the model to diverse linguistic patterns while maintaining schema consistency. The pruning technique allows using the entire training dataset without excluding examples due to length constraints, and the multilingual fine-tuning improves exact set match accuracy compared to single-language approaches.

## Key Results
- Schema pruning + multilingual mT5 increased exact set match accuracy from 0.718 to 0.736 on Spider validation set
- Pruning reduced input sequence length to fit within 512-token transformer limit
- Multilingual approach (4 languages) improved performance over English-only fine-tuning
- The pruning technique enabled training on the full dataset without length-based exclusions

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Pruning irrelevant tables and columns reduces the input sequence length so it fits within the 512-token transformer limit.
- Mechanism: The method analyzes all queries in the training set for each database, identifies tables and columns that are actually used, and removes the unused ones from the schema before tokenization. This reduces the total number of tokens in the concatenated question + schema input.
- Core assumption: The schema elements not referenced in any training query for that database are irrelevant for any query against that database.
- Evidence anchors:
  - [section] "This idea allows pruning table and column names that are not used for that pack of questions, reducing in that way the size of the database schema."
  - [section] "The questions related to these three databases are all in the training dataset file train spider.json."
- Break condition: If a held-out or test query requires a table/column removed during pruning, the pruned schema will be incomplete and generation will fail.

### Mechanism 2
- Claim: Multilingual fine-tuning with data augmentation improves exact set match accuracy compared to single-language fine-tuning.
- Mechanism: The model is trained simultaneously on English, Portuguese, Spanish, and French translations of the Spider dataset. Each language contributes new training examples, effectively increasing dataset size and exposing the model to diverse linguistic patterns while keeping schema tokens in English.
- Core assumption: Training on multiple languages with shared schema tokens enriches the learned representations without harming English performance.
- Evidence anchors:
  - [section] "The multilingual model mT5 produces better results when trained with more languages... the increase from 0.684 to 0.715 for the same mT5-large model first trained in English and after with the quad train dataset."
  - [abstract] "We used a multilingual approach with the mT5-large model fine-tuned with a data-augmented Spider dataset in four languages simultaneously: English, Portuguese, Spanish, and French."
- Break condition: If the multilingual model's pre-training data heavily favors English, adding low-resource languages may dilute the effective training signal.

### Mechanism 3
- Claim: Removing the GAP pretraining step from the mT5 variant and applying pruning directly yields competitive accuracy to BART-large with GAP.
- Mechanism: By pruning the schema and training mT5-large on the full dataset without GAP pretraining, the model converges to an exact set match of 0.736, comparable to the 0.718 baseline.
- Core assumption: Schema pruning provides enough data efficiency gains that the expensive GAP step is no longer necessary for this task.
- Evidence anchors:
  - [section] "This makes the training process simpler because a pre-training with the model is not necessary before the final NL2SQL training."
  - [abstract] "Our proposed technique... increased the exact set match accuracy results from 0.718 to 0.736 in a validation dataset (Dev)."
- Break condition: If GAP pretraining captures task-specific patterns that pruning alone cannot, accuracy may drop without it.

## Architecture Onboarding

- Component map:
  - Spider dataset loader -> Schema pruning module -> mT5Tokenizer -> mT5-large encoder-decoder -> SQL decoder -> Exact set match evaluator

- Critical path:
  1. Load and tokenize question + schema
  2. Apply pruning to schema tokens
  3. Concatenate and truncate to 512 tokens
  4. Feed into mT5-large
  5. Decode SQL, evaluate with exact set match

- Design tradeoffs:
  - Pruning vs. longer max sequence length (2048) - pruning yields better accuracy with lower compute
  - Batch size vs. max tokens - reduced batch size for longer sequences to fit GPU memory
  - Manual pruning vs. automatic per-example pruning - manual is one-time per database but inflexible for new queries

- Failure signatures:
  - Sudden drop in validation accuracy after pruning step
  - Out-of-memory errors when increasing max tokens
  - Missing tables/columns in generated SQL due to over-aggressive pruning

- First 3 experiments:
  1. Reproduce baseline RAT-SQL+GAP accuracy on English only.
  2. Fine-tune mT5-large on English-only Spider and compare accuracy.
  3. Fine-tune mT5-large on quad-language Spider (no pruning) and measure accuracy gain.

## Open Questions the Paper Calls Out
The paper does not explicitly call out open questions. However, based on the limitations and the nature of the work, several implicit questions emerge:

- How does schema pruning affect the performance of other NL2SQL techniques besides RAT-SQL+GAP?
- Can schema pruning be performed automatically during inference time for real-world NL2SQL applications?
- What is the impact of using different multilingual models (besides mT5) on the performance of multilingual NL2SQL?

## Limitations
- Schema pruning relies on the assumption that training queries capture all relevant schema elements, risking over-pruning for test queries
- Multilingual approach lacks per-language performance breakdown to identify which languages contribute most to gains
- Comparison to BART-large with GAP pretraining is limited to final accuracy without detailed ablations on GAP necessity

## Confidence

**High Confidence:**
- Schema pruning reduces input sequence length and allows fitting within 512-token limit
- Multilingual data augmentation improves performance

**Medium Confidence:**
- Pruning enables training on full dataset without length-based exclusions
- mT5-large with pruning matches or exceeds BART-large with GAP pretraining

**Low Confidence:**
- Assumption that unused schema elements in training are irrelevant for any query
- Relative contribution of each language to multilingual gains

## Next Checks
1. **Schema Coverage Analysis:** For each database in the validation set, identify which tables/columns were pruned and verify whether they appear in the validation queries. Calculate the percentage of validation queries that would be affected by pruning.

2. **Ablation on Language Contributions:** Train separate models on each language individually (English, Portuguese, Spanish, French) and combinations thereof to quantify which languages contribute most to the accuracy improvements.

3. **GAP Pretraining Necessity Test:** Train mT5-large with schema pruning but also with the GAP pretraining step to determine if the claimed simplification actually maintains or improves accuracy compared to the pruning-only approach.
