# OmniLingo: Listening- and speaking-based language learning

## Quick Facts
- arXiv ID: 2310.06764
- Source URL: https://arxiv.org/abs/2310.06764
- Reference count: 2
- Primary result: Decentralized language learning application using IPFS with user-controlled data sovereignty

## Executive Summary
OmniLingo presents a decentralized architecture for language learning applications built on IPFS, emphasizing user sovereignty over personal data. The system stores language learning materials as JSON metadata and MP3 audio clips distributed via IPFS's content-addressed model. A demonstration client implements gap-filling and pronunciation feedback tasks using speech recognition models, while a privacy-preserving voice contribution system allows users to encrypt and control access to their own data through session keys.

## Method Summary
OmniLingo uses IPFS to store JSON metadata and MP3 audio clips for language learning materials. The system extracts 10,000 clips per language and groups them into 10 difficulty buckets based on characters-per-second metrics. A web client presents gap-filling tasks where learners complete missing words in sentences, and provides pronunciation feedback by aligning speech recognition hypotheses with reference transcripts using the Needleman-Wunsch algorithm. User contributions are encrypted with session keys that can be published or unpublished via IPNS to control access.

## Key Results
- Decentralized architecture using IPFS for content distribution and user data sovereignty
- 10,000 clips per language grouped into 10 difficulty buckets using characters-per-second metric
- Pronunciation feedback system using speech recognition alignment with Needleman-Wunsch algorithm
- Privacy-preserving voice contribution system using session-key encryption

## Why This Works (Mechanism)

### Mechanism 1
- Claim: User data sovereignty is achieved through session-key encryption and IPFS's content-addressable model
- Mechanism: Each contribution is encrypted with a session key. Users control consent by publishing or unpublishing that key via IPNS, which revokes access without modifying stored data
- Core assumption: IPFS's immutability and content addressing enable data to remain accessible while consent can be revoked by key management
- Evidence anchors:
  - [abstract] "The system uses JSON and MP3 files distributed via IPFS to store language data, with a focus on user sovereignty over data."
  - [section 6] "For a given session key, users may have contributed several samples. If a user wishes to revoke their consent for a sample, they signal this by unpublishing the session key."
  - [corpus] Weak evidence; neighboring papers discuss decentralized computing and learning but do not directly support the consent revocation mechanism
- Break condition: If the session key is compromised or if IPNS publication fails, consent revocation becomes unreliable

### Mechanism 2
- Claim: Progressive difficulty adapts learning by grouping clips into buckets based on characters-per-second (CPS) metric
- Mechanism: The system extracts 10,000 clips per language and groups them into 10 difficulty buckets sorted by CPS. Learners are presented with clips from the appropriate bucket based on performance
- Core assumption: Slower speech (lower CPS) correlates with easier comprehension for learners
- Evidence anchors:
  - [section 3] "By default OmniLingo extracts 10,000 clips for each language, grouping them into 10 buckets by a given difficulty metric. The current metric used is characters per second..."
  - [section 4] "Tasks are presented in groups of five, which constitute a level. A learner passes a level when she answers all five tasks in less time than the clip takes to play."
  - [corpus] No direct evidence from corpus; neighboring papers discuss recommendation systems but not language difficulty metrics
- Break condition: If CPS does not correlate with comprehension difficulty for a target language or learner population, progression becomes ineffective

### Mechanism 3
- Claim: Pronunciation feedback is provided by aligning speech recognition hypotheses with reference transcripts
- Mechanism: User recordings are processed through a speech recognition model (e.g., Coqui STT), producing a hypothesis. Needleman-Wunsch alignment identifies mismatches, which are highlighted in red to indicate pronunciation errors
- Core assumption: Alignment-based mismatch detection reliably identifies pronunciation errors that learners can correct
- Evidence anchors:
  - [section 5] "The output of this system is a hypothesis transcript. This hypothesis is then aligned using the Needleman-Wunch algorithm... In the interface, gaps are filled with the characters from the corresponding position in the transcript and coloured red to indicate that the learner should work on their pronunciation..."
  - [corpus] Weak evidence; neighboring papers discuss speech enhancement and audio models but not pronunciation feedback via alignment
- Break condition: If the speech recognition model is inaccurate or alignment fails to detect relevant pronunciation features, feedback becomes misleading

## Architecture Onboarding

- Component map:
  Data layer: IPFS nodes storing JSON indices and MP3 clips
  Privacy layer: Session keys, encrypted objects, IPNS identities
  Application layer: Web client with gap-filling and pronunciation tasks
  Speech layer: Coqui STT models stored on IPFS, WebAudio API for recording

- Critical path:
  1. Load root index (IPFS CID) → language selection
  2. Load encrypted language index → decrypt with session key
  3. Present gap-filling task with clip MP3
  4. Record user speech → run through speech recognition
  5. Align hypothesis → display pronunciation feedback

- Design tradeoffs:
  - Decentralization vs. availability: IPFS provides no guaranteed uptime; users must run nodes or rely on public gateways
  - Privacy vs. usability: Session key management adds complexity; rolling keys can fragment data
  - Model size vs. performance: Large speech models improve accuracy but increase load times

- Failure signatures:
  - Missing or corrupted IPFS CIDs → data unavailable
  - Invalid session key → inability to decrypt user contributions
  - Speech recognition failure → no pronunciation feedback
  - Browser localStorage quota exceeded → client-side data loss

- First 3 experiments:
  1. Deploy a local IPFS node, publish a small language index, and verify CID resolution in the client
  2. Implement session key generation and encryption of a test MP3 clip; verify decryption works only with the correct key
  3. Integrate a lightweight speech recognition model, record test audio, and verify alignment-based feedback is displayed correctly

## Open Questions the Paper Calls Out

### Open Question 1
- Question: What alternative difficulty metrics could be used to group language learning clips beyond characters-per-second?
- Basis in paper: [explicit] The paper states "The current metric used is characters per second... However working on improved difficulty metrics is an ongoing area of research."
- Why unresolved: The authors acknowledge that characters-per-second is not necessarily the optimal metric for determining clip difficulty, but do not propose or test alternative metrics
- What evidence would resolve it: Comparative studies measuring learning outcomes using different difficulty metrics (e.g., phoneme complexity, syntactic complexity, semantic complexity) to determine which best predicts learner success

### Open Question 2
- Question: How can multiple OmniLingo root indices be efficiently merged and synchronized across distributed networks?
- Basis in paper: [explicit] The paper mentions "Multiple OmniLingo root indices can be merged to allow for multiple sources of language data to be used" and discusses using IPFS publish-subscribe protocols for advertising indices
- Why unresolved: The paper only mentions the possibility of merging indices and using IPFS protocols but does not describe the technical implementation or performance characteristics of such a system
- What evidence would resolve it: Implementation and benchmarking of different merging algorithms, showing latency, bandwidth usage, and consistency guarantees under various network conditions

### Open Question 3
- Question: What is the optimal session key management strategy for balancing privacy protection and data utility in the voice contribution system?
- Basis in paper: [explicit] The paper describes a session key system where users can "roll" session keys and revoke consent by unpublishing keys, but acknowledges this creates a trade-off between privacy and data accessibility
- Why unresolved: The paper presents the technical mechanism for consent management but does not evaluate how frequently users should roll keys, how much data loss occurs from revocation, or what user experience results from different strategies
- What evidence would resolve it: User studies measuring retention rates, contribution volumes, and learning outcomes under different session key rotation frequencies and revocation policies

## Limitations
- Privacy mechanism lacks detailed specification of session key lifecycle management and recovery procedures
- Difficulty metric based solely on characters-per-second may not generalize across languages with different speech characteristics
- Speech recognition integration does not address model selection criteria or error handling for recognition failures

## Confidence
- High: IPFS-based decentralization architecture and JSON/MP3 data structure design
- Medium: Progressive difficulty mechanism given its simple CPS metric, though cross-language validation is absent
- Low: Privacy-preserving voice contribution system due to insufficient detail on session key lifecycle management and consent revocation reliability
