# On the Tool Manipulation Capability of Open-source Large Language Models

## Quick Facts
- **arXiv ID**: 2305.16504
- **Source URL**: https://arxiv.org/abs/2305.16504
- **Reference count**: 40
- **Primary result**: Three techniques (model alignment, in-context demonstration retrieval, and system prompts) boost open-source LLMs by up to 90% success rate on tool manipulation tasks

## Executive Summary
This paper addresses the challenge of improving open-source large language models for tool manipulation tasks, where models must generate correct API calls to accomplish user goals. The authors identify three key challenges: API selection, argument population, and non-executable generation. They propose a practical solution requiring only one developer day of supervision per tool, using programmatically generated training data, semantic similarity-based demonstration retrieval, and system prompts for generation regulation. Experiments on ToolBench, a new benchmark of diverse real-world tools, demonstrate that these techniques make open-source LLMs competitive with GPT-4 on 4 out of 8 tasks, achieving up to 90% success rates.

## Method Summary
The approach involves three key techniques: model alignment through instruction tuning with synthetically generated API usage examples from templates; in-context demonstration retrieval using semantic similarity to select relevant examples from a curated pool; and system prompts to regulate generation and ensure only executable code is produced. The method requires one developer day of supervision per tool to create templates and demonstration examples. The synthetic data generation process captures diverse API usage patterns while requiring minimal manual effort. The retriever module enables generalization to unseen API combinations by ensuring each API appears in at least one demonstration example.

## Key Results
- Open-source LLMs achieve up to 90% success rates on tool manipulation tasks after applying the three enhancement techniques
- The approach makes open-source models competitive with GPT-4 on 4 out of 8 ToolBench tasks
- System prompts alone significantly reduce non-executable generation issues
- Model alignment with programmatically generated data improves API selection accuracy
- In-context demonstration retrieval improves argument population, with oracle examples showing up to 45% success rate improvement

## Why This Works (Mechanism)

### Mechanism 1
Open-source LLMs lack internalized API usage knowledge, leading to poor API selection without explicit usage examples. Closed LLMs potentially internalize API usage during training, enabling correct API selection without documentation. Open-source models need training with programmatically generated API usage examples to internalize this knowledge. If model alignment doesn't improve API selection accuracy, or if the improvement is minimal despite comprehensive training data, this mechanism breaks.

### Mechanism 2
Open-source LLMs struggle with argument population without demonstration examples. Without examples, they often fail to populate appropriate values for API arguments. Providing in-context demonstrations improves argument population by showing concrete examples of how to fill API arguments correctly. If in-context demonstrations don't improve argument population accuracy, or if improvements don't generalize to unseen API combinations, this mechanism fails.

### Mechanism 3
Open-source LLMs generate non-executable code (language verbosity, natural language beyond desired code). System prompts provide generation regulation by explicitly instructing models to generate only code in a desired format, preventing natural language generation around API calls. If system prompts don't reduce non-executable generation, or if they introduce new failure modes, this mechanism breaks.

## Architecture Onboarding

- **Component map**: Goal → Action Generator → API Call Generation → Environment Execution → Success/Failure Evaluation
- **Critical path**: User goal flows through the action generator, which uses API documentation access to generate API calls, which are then executed in the environment for evaluation
- **Design tradeoffs**: Model alignment vs. inference-time techniques (alignment requires upfront training but provides better generalization; in-context demonstrations are lighter but may have limited coverage); Template complexity vs. coverage (more complex templates capture more scenarios but require more human effort); Demonstration pool size vs. retrieval accuracy (larger pools provide better coverage but may include irrelevant examples)
- **Failure signatures**: API selection failures (wrong API names, hallucinated APIs, complete failure to select any API); Argument population failures (incorrect values, missing required arguments, wrong data types); Non-executable generation (natural language around code, missing code blocks, syntax errors)
- **First 3 experiments**: 1) Zero-shot evaluation on a simple task (e.g., OpenWeather) to establish baseline capability gap; 2) Apply system prompt alone to measure impact on non-executable generation reduction; 3) Apply model alignment with programmatically generated data to measure API selection improvement

## Open Questions the Paper Calls Out

- **Optimal balance between model alignment data and in-context demonstrations**: The paper shows both techniques improve performance but doesn't systematically study their relative contributions. Controlled experiments varying the amount of alignment data and demonstration examples while measuring performance on tasks with different complexity levels would resolve this.

- **How open-source LLMs internalize API usage knowledge**: The paper observes GPT-4 can select correct APIs without documentation, suggesting it internalizes API usage during training, but doesn't investigate the training mechanisms that enable this internalization or how to replicate it in open-source models. Analysis of model activations or attention patterns during API selection, or experiments training models on API-rich datasets to compare with closed models, would resolve this.

- **Relationship between API complexity score and actual task difficulty**: The paper introduces an API complexity score but only shows moderate correlation with error rates for some models. Systematic correlation studies across more models and tasks, including analysis of where the score fails to predict difficulty and why, would resolve this.

## Limitations
- The synthetic data generation process may not capture the full complexity of real-world API usage patterns, potentially limiting the model's ability to handle edge cases
- The in-context demonstration retriever's effectiveness depends on the quality of the retrieval algorithm, which is not fully specified
- The evaluation focuses on individual task success rates rather than end-to-end multi-step reasoning capabilities across multiple tools

## Confidence
- **High confidence**: The experimental results showing improved success rates (up to 90%) and comparative performance against GPT-4 on 4 out of 8 tasks
- **Medium confidence**: The claim that the approach requires only one developer day of supervision per tool
- **Low confidence**: The assertion that open-source LLMs fundamentally lack internalized API usage knowledge compared to closed models
