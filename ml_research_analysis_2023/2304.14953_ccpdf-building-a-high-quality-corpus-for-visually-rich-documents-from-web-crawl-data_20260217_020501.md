# CCpdf: Building a High Quality Corpus for Visually Rich Documents from Web Crawl Data

## Quick Facts
- arXiv ID: 2304.14953
- Source URL: https://arxiv.org/abs/2304.14953
- Reference count: 37
- Primary result: 1.1 million PDF documents (14.5 million pages) across 11 languages for pretraining multilingual 2D language models

## Executive Summary
This paper presents an efficient pipeline for creating a large-scale, diverse, multilingual corpus of PDF files from Common Crawl web crawl data. The authors propose a multi-step approach including PDF link extraction, URL-based language detection, spam filtering, and optimized text extraction using a born-digital detector to skip OCR for suitable documents. They carefully analyze various processing strategies, including OCR engine selection and language identification methods, balancing data quality and computational efficiency. The resulting CCpdf corpus contains 1.1 million PDF documents (14.5 million pages) across 11 languages, with detailed statistics on document properties, layout, and metadata. The dataset and processing tools are publicly available, offering researchers a valuable resource for pretraining multilingual 2D language models in document understanding tasks.

## Method Summary
The paper describes a pipeline that extracts PDF links from Common Crawl data, uses URL-based language detection to filter and balance documents across 11 target languages, downloads the selected PDFs, and processes them using a born-digital detector to determine whether to use OCR or direct text extraction. The born-digital detector classifies documents as text-based (suitable for direct extraction) or scanned (requiring OCR) using heuristics like visible text length, hidden text presence, and image count. The processed documents are then indexed along with metadata and layout information for use in pretraining language models.

## Key Results
- Successfully created a corpus of 1.1 million PDF documents (14.5 million pages) across 11 languages
- Born-digital detection reduced processing time by skipping OCR for text-based documents
- Domain balancing prevented spam overrepresentation while maintaining dataset diversity
- The corpus includes detailed metadata including creation dates, PDF versions, and layout statistics

## Why This Works (Mechanism)

### Mechanism 1
Using born-digital detection before OCR reduces processing time and improves data quality by avoiding OCR errors on text-based documents. The pipeline classifies PDF files as "born-digital" (text-based) or "scanned" using heuristics like visible text length > 100, hidden text length = 0, and image count = 0. Born-digital files skip OCR and use direct text extraction tools (e.g., DjVu-based tools), while scanned files are processed with OCR.

### Mechanism 2
URL-based language detection reduces the need for expensive content-based language identification. The pipeline uses simple heuristics based on URL patterns (e.g., .pl domains for Polish, lang=en for English) to preliminarily classify documents by language. This guides OCR language model selection and filtering, reducing the need for content-based language detection on all documents.

### Mechanism 3
Balancing document downloads per domain and language ensures diversity and prevents dataset bias. The pipeline limits downloads to at most three PDF files per domain per language, with further limits for English and German due to their higher availability. This prevents overrepresentation of specific domains and ensures a diverse dataset.

## Architecture Onboarding

- **Component map**: Common Crawl data extraction → PDF link extraction → URL-based language detection → Spam filtering → Domain/language balancing → PDF download → Born-digital detection → OCR or direct text extraction → Language identification → Corpus index creation
- **Critical path**: PDF link extraction → URL-based language detection → Spam filtering → Domain/language balancing → PDF download → Born-digital detection → OCR or direct text extraction → Language identification → Corpus index creation
- **Design tradeoffs**: Balancing processing speed (using URL-based language detection) vs. accuracy (using content-based language identification); balancing dataset diversity (limiting downloads per domain) vs. potential underrepresentation of important sources; balancing processing efficiency (using born-digital detection to skip OCR) vs. potential misclassification of documents
- **Failure signatures**: High OCR error rates due to incorrect language detection or misclassification of born-digital documents; dataset bias due to imbalanced domain/language representation; low data quality due to ineffective spam filtering or born-digital detection
- **First 3 experiments**: 1) Test born-digital detection accuracy on a sample of known born-digital and scanned documents; 2) Compare URL-based and content-based language detection accuracy on a sample of manually labeled documents; 3) Evaluate the impact of domain/language balancing on dataset diversity and model performance

## Open Questions the Paper Calls Out

### Open Question 1
How does the quality of OCR processing vary when using URL-based language detection versus built-in language detection mechanisms, and what are the implications for downstream language model performance? While the paper provides a comparison of different strategies, it does not explore the impact of these choices on the performance of language models trained on the resulting corpus.

### Open Question 2
What is the impact of document diversity (in terms of language, domain, and layout) on the effectiveness of 2D language models in document understanding tasks? The paper emphasizes the importance of creating a diverse, multilingual corpus but does not investigate how the diversity of the training data affects the models' ability to generalize across different document types and languages.

### Open Question 3
How does the age distribution of documents in the corpus affect the performance of language models on contemporary document understanding tasks? The paper analyzes the creation dates of documents but does not explore the impact of using older versus newer documents on the models' ability to understand and process contemporary documents.

### Open Question 4
What are the trade-offs between processing time and data quality when using different OCR engines and language detection tools, and how do these trade-offs impact the scalability of corpus creation pipelines? The paper compares the processing time and additional costs of different strategies but does not investigate how these trade-offs affect the feasibility of scaling up corpus creation to larger datasets or more languages.

## Limitations

- The pipeline's reliance on URL-based language detection may misclassify documents when domain patterns don't match content language
- Born-digital detection heuristics could incorrectly classify documents with embedded images or non-standard text structures
- Domain balancing may underrepresent important but less common sources while preventing spam overrepresentation

## Confidence

**High Confidence Claims:**
- The overall multi-step pipeline architecture for PDF corpus creation is technically sound
- Born-digital detection provides computational efficiency gains by reducing unnecessary OCR processing
- Domain balancing effectively prevents spam document overrepresentation

**Medium Confidence Claims:**
- URL-based language detection provides sufficient accuracy for pipeline filtering
- The 100-character threshold for visible text effectively identifies born-digital documents
- The three-document-per-domain limit adequately ensures dataset diversity

**Low Confidence Claims:**
- The specific OCR engine configurations provide optimal text extraction quality
- The born-digital detection heuristics correctly classify all document types
- The language detection accuracy meets research-grade standards
