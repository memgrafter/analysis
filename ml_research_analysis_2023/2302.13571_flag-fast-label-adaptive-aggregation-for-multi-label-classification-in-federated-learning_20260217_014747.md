# FLAG: Fast Label-Adaptive Aggregation for Multi-label Classification in Federated Learning

## Quick Facts
- arXiv ID: 2302.13571
- Source URL: https://arxiv.org/abs/2302.13571
- Reference count: 40
- Key outcome: FLAG achieved 6.3% relative improvement in mAP and reduced training epochs/communication rounds by over 50% in federated multi-label classification

## Executive Summary
This paper addresses the challenge of multi-label classification in federated learning, where data is distributed across multiple clients with heterogeneous label distributions. The authors propose FLAG (Fast Label-Adaptive Aggregation) that weights client contributions based on label distribution and occurrence statistics to improve global model performance. FLAG is evaluated on MS-COCO dataset and demonstrates superior performance compared to state-of-the-art federated learning methods, achieving faster convergence and better accuracy by effectively handling label distribution skew.

## Method Summary
The proposed framework includes CMDA (Clustering-based Multi-label Data Allocation) to simulate client heterogeneity by using k-modes clustering on binary label vectors, and FLAG for weighted model aggregation. FLAG calculates label weights for each client using the formula `label_weight = {∑(N_c,i / N_c)^α}` where α controls the importance of label occurrence vs. distribution. The server aggregates models using these weights, giving more influence to clients with informative label patterns. The method uses TRresNet backbone with Asymmetric Loss function and is evaluated on MS-COCO 2014 dataset with 10 clients.

## Key Results
- FLAG achieved 6.3% relative improvement in mean average precision (mAP) compared to FedAvg
- Reduced training epochs and communication rounds by over 50% while reaching target performance
- Outperformed state-of-the-art federated learning methods including Per-FedAvg, pFedHN, and KT-pFL on multi-label classification tasks

## Why This Works (Mechanism)

### Mechanism 1
FLAG improves federated learning convergence by weighting client model contributions based on label distribution and occurrence. Each client calculates a label weight using the formula `label_weight = {∑(N_c,i / N_c)^α}`, where α controls the importance of label occurrence vs. distribution. The server aggregates models using these weights, giving more influence to clients with informative label patterns. Core assumption: Label distribution and occurrence in each client's data contain sufficient information to predict that client's model quality and relevance to the global task.

### Mechanism 2
Clustering-based Multi-label Data Allocation (CMDA) simulates realistic client heterogeneity for multi-label federated learning. CMDA uses k-modes clustering on binary label vectors to partition the dataset into clients with different label distributions, mimicking real-world scenarios where different clients (e.g., hospitals) have varying label patterns. Core assumption: Multi-label data exhibits natural clustering in label space, and these clusters can represent realistic client heterogeneity.

### Mechanism 3
FLAG reduces communication rounds and training epochs by accelerating convergence to target performance. By weighting contributions based on label statistics, FLAG enables faster global model updates that better represent the multi-label distribution, reaching target mAP in <50% of the epochs/rounds needed by FedAvg. Core assumption: Early weighted aggregation provides more informative global updates than simple averaging, leading to faster convergence.

## Foundational Learning

- Concept: Multi-label classification vs. multi-class classification
  - Why needed here: Multi-label data has samples with multiple labels and label correlations, unlike multi-class where each sample has exactly one label. This affects how data is split and models are trained in federated settings.
  - Quick check question: In multi-label classification, can a single image have both "cat" and "dog" labels simultaneously? (Yes)

- Concept: Dirichlet distribution for client data simulation
  - Why needed here: Traditional federated learning uses Dirichlet distribution to simulate non-i.i.d. label distributions in multi-class settings. However, this approach doesn't work for multi-label data where samples can have multiple labels.
  - Quick check question: Why can't we use Dirichlet distribution for multi-label federated learning? (Because each sample has ≥1 label, creating different distributions than multi-class)

- Concept: Kullback-Leibler divergence for label distribution comparison
  - Why needed here: KL divergence measures how different label distributions are between clients, quantifying label distribution skew that FLAG aims to address through weighted aggregation.
  - Quick check question: What does a KL divergence of 0 between two clients indicate about their label distributions? (Identical distributions)

## Architecture Onboarding

- Component map: CMDA clustering -> Client training -> FLAG weighted aggregation -> Global model distribution
- Critical path: 1) CMDA clusters training labels and partitions dataset into clients; 2) Clients train local models and compute label weights; 3) Clients upload model parameters and label weights to server; 4) Server performs weighted aggregation using FLAG formula; 5) Server distributes updated global model to clients; 6) Repeat until convergence
- Design tradeoffs: FLAG vs. FedAvg (FLAG provides faster convergence and better mAP but requires label weight computation; FedAvg is simpler but slower); CMDA vs. random splitting (CMDA creates realistic heterogeneity but adds clustering complexity; random splitting is simpler but unrealistic); Hyperparameter α (controls trade-off between label occurrence and distribution; needs tuning but FLAG is robust across reasonable values)
- Failure signatures: FLAG underperforms FedAvg (likely due to poor α tuning or uniform label distributions); CMDA creates unrealistic client splits (likely due to inappropriate number of clusters or low label correlation); Slow convergence (could indicate noisy label statistics or insufficient communication rounds)
- First 3 experiments: 1) Implement CMDA with k-modes clustering on binary label vectors and verify label distribution skew via KL divergence heatmap; 2) Implement FLAG aggregation with varying α values (0.0, 0.3, 1.0) and compare mAP and convergence speed against FedAvg; 3) Test FLAG on clients with highest and lowest label heterogeneity to verify performance claims across different heterogeneity levels

## Open Questions the Paper Calls Out

### Open Question 1
How can the degree of client heterogeneity in federated learning be effectively controlled and measured? The paper mentions that controlling the degree of client heterogeneity is a worthwhile direction for analysis, as the clustering method used for client simulation has certain randomness. Developing a standardized method for controlling and measuring client heterogeneity in federated learning, validated through experiments with varying degrees of heterogeneity and their impact on model performance, would resolve this question.

### Open Question 2
How can a dynamic weighted method be developed to improve the weighting of label correlation during the training process in multi-label federated learning? The paper suggests that a dynamic weighted method during the training process is a valuable direction to make multi-label federated learning closer to real-world applications, as the current statistical approach is static. Developing and validating a dynamic weighted method for label correlation during training in multi-label federated learning, comparing its performance to static methods in terms of model accuracy and convergence speed, would resolve this question.

### Open Question 3
How can the FLAG method be extended to handle other types of data heterogeneity beyond label distribution skew, such as quantity skew and acquisition skew? The paper focuses on label distribution skew as a challenge in federated learning, but does not explore how the FLAG method can be adapted to handle other types of data heterogeneity. Extending the FLAG method to handle different types of data heterogeneity and evaluating its performance in terms of model accuracy and convergence speed compared to existing methods would resolve this question.

## Limitations
- Evaluated only on MS-COCO dataset with 10 clients, limiting generalizability to other multi-label datasets and client configurations
- Hyperparameter α requires careful tuning, though the paper claims robustness across reasonable values
- CMDA method simulates client heterogeneity but may not perfectly capture real-world scenarios where clients have different data distributions

## Confidence
- **High confidence**: FLAG's mechanism of weighting client contributions based on label statistics, the experimental setup using MS-COCO with 10 clients, and the reported convergence improvements over FedAvg baselines
- **Medium confidence**: The generalizability of FLAG to other multi-label datasets and client configurations, given the limited evaluation scope
- **Low confidence**: The CMDA method's ability to perfectly simulate real-world client heterogeneity, as this remains a simulation rather than a validation with actual distributed data sources

## Next Checks
1. **Cross-dataset validation**: Evaluate FLAG on other multi-label datasets (e.g., NUS-WIDE, VOC 2007) with varying numbers of labels and client counts to assess generalizability beyond MS-COCO

2. **Privacy and communication analysis**: Measure the communication overhead of FLAG (model size + label statistics) and assess whether the improved convergence justifies the additional computational requirements per client

3. **Real-world deployment simulation**: Implement FLAG in a cross-silo federated learning scenario with heterogeneous data sources (e.g., multiple hospitals with different patient populations) to validate CMDA's effectiveness in simulating realistic client heterogeneity
