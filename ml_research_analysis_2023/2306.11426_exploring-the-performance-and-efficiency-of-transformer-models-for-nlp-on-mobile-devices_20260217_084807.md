# Exploring the Performance and Efficiency of Transformer Models for NLP on Mobile Devices

## Quick Facts
- arXiv ID: 2306.11426
- Source URL: https://arxiv.org/abs/2306.11426
- Reference count: 24
- This paper benchmarks Transformer models for NLP on mobile devices

## Executive Summary
This paper evaluates the performance and efficiency of 12 Transformer models for NLP tasks on two Android smartphones with different computational capabilities. The study systematically measures inference latency, memory usage, and accuracy across multiple quantization schemes and hardware delegates. Results reveal that Transformers are poorly suited for mobile accelerators, with GPU acceleration causing severe accuracy degradation and DSP/NPU accelerators offering minimal speedup due to operation incompatibility. The authors conclude that both system-level optimizations and model-level architectural changes are needed to make Transformer inference practical on mobile devices.

## Method Summary
The study benchmarks 12 Transformer models (BERT Tiny, ELECTRA Tiny, XDistil-L6-H256, MiniLM-L3, MobileBERT, XDistil-L6-H384, MiniLM-L12, RoBERTa Tiny, ELECTRA Small, DistilBERT, DistilGPT2, GPT2 Small) fine-tuned on an emotions classification dataset. Models are evaluated on two Android smartphones (Samsung A71, Samsung S20 FE) using TensorFlow Lite with various quantization methods (FP16, DR8, FX8) and Android delegates (XNNPACK, GPU, NNAPI, HEX). The evaluation includes warm-up iterations, controlled temperature management, and multiple execution runs per model-configuration combination to measure latency, memory footprint, throughput, and accuracy retention.

## Key Results
- Transformers achieve only marginal speedups from GPU acceleration on mobile devices
- DSP and NPU accelerators show poor compatibility with Transformer operations
- GPU delegate causes accuracy degradation below 35% in most models (except MobileBERT)
- Integer quantization accelerates execution and reduces memory requirements

## Why This Works (Mechanism)

### Mechanism 1
- Claim: GPU acceleration is incompatible with Transformers on mobile devices due to accuracy degradation.
- Mechanism: When executing Transformer models with the GPU delegate, the computational graph undergoes transformation that introduces numerical instabilities, causing severe accuracy loss in most models except MobileBERT.
- Core assumption: The GPU delegate's execution path uses lower precision or different accumulation strategies that are not numerically stable for Transformer attention mechanisms.
- Evidence anchors:
  - [abstract] "the results show that Transformers are not accelerator-friendly and indicate the need for software and hardware optimisations"
  - [section] "we found that all of the delegate-processor combinations (columns in Table IV) deliver the accuracy presented in Table I, except for the GPU delegate, where only MobileBERT retains its original accuracy, while for the rest of the discriminative models the accuracy drops drastically (below 35%)"
  - [corpus] Weak - no direct evidence in corpus neighbors
- Break condition: If a Transformer model can maintain full accuracy while using GPU acceleration through numerical stability improvements or alternative execution paths.

### Mechanism 2
- Claim: DSP accelerators cannot provide speedup for Transformer inference due to poor operation compatibility.
- Mechanism: The DSP delegate only supports a small fraction of the computational operations in Transformer models (primarily integer arithmetic), leaving the majority of the graph to execute on CPU, negating any acceleration benefit.
- Core assumption: DSP accelerators are optimized for integer arithmetic operations common in signal processing, while Transformers rely heavily on floating-point attention and normalization operations.
- Evidence anchors:
  - [abstract] "only marginal speedups from the GPU and poor compatibility with DSP and NPU accelerators"
  - [section] "Taking into consideration Table IV, we consider execution on the NPUs purposeless, so we calculate the latency speedups provided by the GPU and DSP only... The DSP is not able to provide any acceleration due to its small compatibility ratio."
  - [corpus] Weak - no direct evidence in corpus neighbors
- Break condition: If DSP architectures evolve to natively support the floating-point and mixed-precision operations required by Transformer models.

### Mechanism 3
- Claim: Quantization to FP16 provides no latency benefit on mobile CPUs but requires significantly more memory.
- Mechanism: Mobile CPUs do not have hardware acceleration for FP16 operations, so they execute FP16 arithmetic using the same pathways as FP32, but with the overhead of data type conversion and reduced memory bandwidth efficiency.
- Core assumption: The lack of native FP16 support on mobile CPUs means quantization to FP16 only saves memory space without improving computational throughput.
- Evidence anchors:
  - [section] "FP16 models achieve the same latency as FP32 models and require at least 70% more memory"
  - [abstract] "integer models accelerate the execution and at the same time reduce the memory requirements"
  - [corpus] Weak - no direct evidence in corpus neighbors
- Break condition: If mobile CPUs gain native FP16 hardware support or if quantization schemes better match the underlying hardware capabilities.

## Architecture Onboarding

- Component map: Android app -> TensorFlow Lite -> Hugging Face Transformers -> Model loading -> Quantization selection -> Delegate assignment -> Execution -> Measurement collection
- Critical path: Model loading → Quantization selection → Delegate assignment → Execution → Measurement collection. The most critical bottleneck is the delegate compatibility check and the subsequent fallback to CPU execution when accelerators cannot handle certain operations.
- Design tradeoffs: The choice between accuracy and performance is central, with GPU acceleration causing accuracy degradation and quantization offering memory benefits but variable latency improvements. The heterogeneity of mobile hardware necessitates device-specific optimization rather than universal solutions.
- Failure signatures: Accuracy drops below 35% when using GPU acceleration (except for MobileBERT), zero speedup from DSP despite integer quantization, and no improvement from FP16 quantization on CPUs. These indicate fundamental mismatches between Transformer operations and mobile accelerator capabilities.
- First 3 experiments:
  1. Measure execution time and accuracy for a simple Transformer model (BERT Tiny) across all delegate combinations to establish baseline performance characteristics and identify accuracy degradation patterns.
  2. Compare quantized vs. floating-point variants of the same model to quantify the tradeoff between memory savings and latency improvements across different processor types.
  3. Test model substitution by replacing GELU activations with ReLU and layer normalization with batch normalization to measure the impact on accelerator compatibility and overall performance.

## Open Questions the Paper Calls Out

### Open Question 1
- Question: Can the Transformer architecture be fundamentally redesigned to be more mobile-friendly while maintaining accuracy?
- Basis in paper: [explicit] The paper suggests model-level substitutions, such as replacing complex layers with simpler ones, as a potential optimization direction.
- Why unresolved: The paper does not explore the full extent of architectural changes that could be made to Transformers to improve their efficiency on mobile devices.
- What evidence would resolve it: Empirical results from experiments testing various architectural modifications, such as replacing GELU activations with ReLU or using simpler normalization techniques, and measuring their impact on latency, memory usage, and accuracy.

### Open Question 2
- Question: What specific hardware optimizations are needed to make accelerators (NPUs, DSPs) more compatible with Transformer models?
- Basis in paper: [explicit] The paper states that Transformers are not accelerator-compatible and that DSPs and NPUs are mostly not Transformer-compatible.
- Why unresolved: The paper identifies the problem but does not delve into the specific hardware changes or design considerations required to improve compatibility.
- What evidence would resolve it: Research and development efforts focused on designing accelerators with Transformer-specific optimizations, such as specialized matrix multiplication units or efficient attention mechanisms, and benchmarking their performance on Transformer models.

### Open Question 3
- Question: How can dynamic runtime environments on mobile devices be effectively managed to optimize Transformer inference performance?
- Basis in paper: [explicit] The paper highlights the dynamic environment of mobile devices, including changing resource availability and competing processes, as a challenge for optimization.
- Why unresolved: While the paper suggests the need for device-dependent and model-aware optimizations, it does not provide specific strategies for managing dynamic runtime environments.
- What evidence would resolve it: Development and evaluation of adaptive inference systems that can dynamically adjust model execution based on real-time device conditions, such as available resources and power constraints, and measure their impact on latency and accuracy.

## Limitations

- The study is limited to 12 Transformer models evaluated on only two Android devices, potentially limiting generalizability to other architectures, tasks, or hardware platforms.
- The paper focuses primarily on inference performance without addressing model loading, initialization costs, or the impact of different sequence lengths on latency.
- The analysis of DSP and NPU accelerators is constrained by their poor compatibility with Transformer operations, making it difficult to assess their true potential with architecture modifications.

## Confidence

- **High confidence**: Transformer models require significant memory and computational resources on mobile devices (supported by extensive latency and memory measurements across 12 models and 4 quantization variants).
- **Medium confidence**: GPU acceleration causes severe accuracy degradation in most Transformer models (well-documented for the tested models but mechanism not fully explained).
- **Medium confidence**: DSP and NPU accelerators provide minimal speedup for Transformer inference due to operation incompatibility (based on delegate compatibility measurements but limited by hardware constraints).
- **Low confidence**: Model substitutions (simpler layers) will significantly improve mobile performance (suggested but not empirically validated in the study).

## Next Checks

1. Test the same 12 Transformer models on additional mobile devices with different SoC architectures (e.g., MediaTek, Qualcomm Snapdragon variants, Apple Silicon) to determine if the performance patterns are device-dependent or universal.

2. Conduct ablation studies by systematically replacing Transformer components (attention mechanisms, layer normalization, GELU activations) with simpler alternatives and measuring the impact on both accuracy and accelerator compatibility.

3. Evaluate a broader range of NLP tasks beyond text classification, including question answering, sequence labeling, and text generation, to determine if the performance limitations are task-specific or inherent to the Transformer architecture on mobile hardware.
