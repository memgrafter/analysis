# Adversarial Robustness and Feature Impact Analysis for Driver Drowsiness Detection

## Quick Facts
- arXiv ID: 2303.13649
- Source URL: https://arxiv.org/abs/2303.13649
- Reference count: 31
- Primary result: Adversarial training with SHAP-selected features significantly improves robustness of driver drowsiness detection models, especially XGBoost.

## Executive Summary
This work evaluates machine learning models for driver drowsiness detection from heart rate variability (HRV) signals, focusing on feature impact and adversarial robustness. Experiments with varying HRV time windows and multiple ML models show that XGBoost is the most reliable, with optimal windows between 120-150 seconds. SHAP analysis identifies the 18 most impactful HRV features, enabling smaller models without loss of performance. Adversarial training, especially with realistic perturbations, greatly enhances model robustness against attacks and faulty input data.

## Method Summary
The study uses the DROZY dataset, computing 31 HRV features from ECG signals using biosppy and pyhrv. Multiple ML models (SVM, KNN, XGB, LGBM) are trained on HRV windows of 60-200 seconds, with feature impact assessed via SHAP. Adversarial robustness is evaluated using the A2PM framework, with models retrained on perturbed data. SHAP enables selection of 18 key features, leading to smaller, equally performant models.

## Key Results
- XGBoost was the most reliable model for driver drowsiness detection.
- The optimal HRV time window was 120-150 seconds.
- SHAP-selected 18 features enabled smaller models with equivalent performance.
- Adversarial training significantly improved model robustness, especially for XGBoost.

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Using a time window of 120-150 seconds captures sufficient HRV dynamics to discriminate drowsy from awake states.
- Mechanism: HRV reflects cardiac rhythm modulation tied to sympathetic-parasympathetic balance; longer windows capture more stable autonomic patterns linked to alertness.
- Core assumption: The driver's autonomic state remains sufficiently consistent over the window to provide meaningful HRV metrics.
- Evidence anchors:
  - [abstract] "optimal time window had between 120 and 150 seconds"
  - [section] "smaller windows would not provide a long enough signal for the detection and larger windows would be prohibitive in terms of a near real-time analysis"
- Break condition: If driver activity (e.g., stress, exercise) changes rapidly within the window, HRV features may become noisy and reduce classification reliability.

### Mechanism 2
- Claim: Adversarial training with one perturbed copy per drowsy sample significantly improves model robustness without excessive data cost.
- Mechanism: Training on adversarial examples forces the model to learn decision boundaries that are resilient to small, realistic perturbations consistent with class correlations.
- Core assumption: The perturbations generated by A2PM are realistic and representative of real-world sensor faults or attacks.
- Evidence anchors:
  - [abstract] "adversarial training enabled them to preserve significantly higher results, especially XGB"
  - [section] "the training data was augmented with realistic adversarial examples that considered the correlations between different features"
- Break condition: If the adversarial perturbations are too conservative, the model may not learn sufficient robustness; if too aggressive, it may overfit to unrealistic noise.

### Mechanism 3
- Claim: Selecting the 18 most impactful HRV features via SHAP preserves classification performance while reducing model complexity.
- Mechanism: SHAP values quantify each feature's contribution to model predictions; removing low-impact features reduces noise and overfitting risk.
- Core assumption: The top-ranked features are both necessary and sufficient for discriminating drowsy from awake states.
- Evidence anchors:
  - [section] "SHAP enabled the selection of the 18 most impactful features and the training of new smaller models that achieved a performance as good as the initial ones"
  - [section] "The most relevant features were selected according to the SHAP rankings for the six models, resulting in 18 numerical features"
- Break condition: If the feature ranking is unstable across models or data splits, the reduced feature set may lose discriminative power.

## Architecture Onboarding

- Component map:
  Data ingestion → HRV feature extraction (biosppy, pyhrv) → Feature selection (SHAP) → Model training (SVM, KNN, XGB, LGBM) → Adversarial robustness testing (A2PM)
- Critical path:
  Feature computation → SHAP ranking → Model training → Adversarial evaluation
- Design tradeoffs:
  Larger HRV windows improve signal stability but reduce real-time applicability; smaller windows increase noise.
  More complex models (e.g., XGB) may yield better robustness but require more tuning and computational resources.
- Failure signatures:
  Sharp drop in F1-score after adversarial attack indicates insufficient robustness.
  Unstable SHAP rankings across models suggest feature selection may not be robust.
- First 3 experiments:
  1. Run feature extraction on a subset of the DROZY dataset and verify the 31 HRV features are computed correctly.
  2. Train a baseline SVM model with a 120-second window and evaluate on the holdout set.
  3. Apply SHAP to the trained model and confirm the top 18 features match those reported.

## Limitations
- The study uses a single driver drowsiness dataset (DROZY), limiting generalizability to other populations or sensor modalities.
- The adversarial perturbations are generated based on A2PM's correlation-based approach, which may not capture all realistic attack vectors or sensor faults.
- The optimal HRV time window (120-150 seconds) is dataset-specific and may not generalize to other driving contexts or HRV acquisition systems.

## Confidence
- **High confidence**: XGB being the most reliable model; adversarial training improving robustness.
- **Medium confidence**: The 120-150 second time window as optimal; 18-feature subset preserving performance.
- **Low confidence**: Generalizability of results to other datasets or real-world deployment scenarios.
