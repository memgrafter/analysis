# Synthesizing a Progression of Subtasks for Block-Based Visual Programming Tasks

## Quick Facts
- arXiv ID: 2305.17518
- Source URL: https://arxiv.org/abs/2305.17518

## Executive Summary
This paper presents ProgresSyn, an algorithm that automatically synthesizes a progression of subtasks for block-based visual programming tasks. The method takes a reference task and its solution code as input, then generates K subtasks that gradually increase in complexity while retaining the visual context of the original task. By leveraging execution traces and symbolic execution, ProgresSyn creates well-spaced subtasks that help learners build up to solving the full reference task. The approach is evaluated on both neural program synthesis performance and novice programmer assistance, showing significant improvements over baseline methods.

## Method Summary
ProgresSyn works by first obtaining an execution trace of the reference solution code on the visual grid, then linearizing this trace to identify valid code breakpoints. The algorithm filters invalid intermediate codes and uses symbolic execution to generate new visual grids for each subtask, making minimal modifications to ensure validity while preserving visual similarity. Finally, it optimizes the sequence of K subtasks to minimize maximum complexity jumps between consecutive solutions, using a greedy algorithm that selects the progression with the best overall quality metrics including task quality, diversity, and dissimilarity.

## Key Results
- ProgresSyn improves neural program synthesizer performance by up to 80% compared to baselines
- The method successfully assists novice programmers in solving tasks from popular block-based programming platforms
- Generated subtasks retain visual context of reference tasks while being well-spaced in complexity

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Execution trace linearization enables safe code segmentation
- Mechanism: The algorithm runs the reference solution code on the target visual grid to produce a full execution trace. This trace records every executed code block and the state of the grid at each step. By linearizing the nested structure into a flat sequence, the algorithm can identify valid breakpoints for generating subtasks without breaking loop invariants or conditional logic.
- Core assumption: The execution trace contains all necessary information to reconstruct valid intermediate programs that are both syntactically correct and semantically meaningful.
- Evidence anchors:
  - [abstract] "reasoning about the execution behavior of the provided solution code on the reference task's visual grids"
  - [section] "This stage 'linearizes' the solution code Cref,∗by obtaining the full execution trace of this code on single visual gridTref vis,1"
- Break condition: If the solution code contains infinite loops or non-terminating constructs, the trace may not complete, making segmentation impossible.

### Mechanism 2
- Claim: Symbolic execution with minimal grid modification preserves task quality
- Mechanism: After generating candidate solution codes from the execution trace, the algorithm uses symbolic execution to create new visual grids for each subtask. It constrains the symbolic execution to the path taken in the original trace and makes only minimal modifications to the grid cells, ensuring the new grid is consistent with the partial code execution while retaining visual similarity to the reference task.
- Core assumption: The trajectory of the avatar through the grid during execution provides sufficient constraints to generate valid, high-quality subtasks without exhaustive search.
- Evidence anchors:
  - [abstract] "The method uses execution traces and symbolic execution to generate high-quality, well-spaced subtasks that retain the visual context of the reference task"
  - [section] "During symbolic execution, we make minimal modifications to the grids of the subtasks w.r.t.Tref vis,1"
- Break condition: If the symbolic execution cannot find an assignment satisfying all constraints, the candidate subtask is discarded.

### Mechanism 3
- Claim: Well-spaced code complexity progression improves learning efficiency

This ensures that each subtask requires only a small incremental increase in code complexity compared to previous subtasks.
- Core assumption: Learners can more effectively acquire new programming skills when complexity increases gradually rather than in large jumps.
- Evidence anchors:
  - [abstract] "well-spaced in terms of their complexity"
  - [section] "Our formalism is based on the intuition that lowering complexity reduces the cognitive load of solving the progression"
- Break condition: If the reference solution code has large complexity gaps between certain code segments, the algorithm may need to create subtasks with artificial intermediate steps that don't correspond to natural program states.

## Foundational Learning

- Concept: Execution trace linearization
  - Why needed here: Enables safe identification of breakpoints in nested code structures without breaking loop invariants
  - Quick check question: Why can't we simply split the solution code at arbitrary points to create subtasks?

- Concept: Symbolic execution with path constraints
  - Why needed here: Allows generation of valid visual grids for partial code execution without exhaustive enumeration
  - Quick check question: How does constraining symbolic execution to the original execution path ensure minimal grid modification?

- Concept: Complexity gap minimization
  - Why needed here: Ensures that solving each subtask provides a manageable incremental challenge to the learner
  - Quick check question: What would happen if we didn't optimize for well-spaced complexity in the progression?

## Architecture Onboarding

- Component map:
  - Execution tracer -> Code validator -> Symbolic executor -> Sequence optimizer -> Quality metrics

- Critical path:
  1. Run reference solution code on visual grid to get execution trace
  2. Filter trace to remove invalid code segments
  3. Generate candidate subtasks with new grids via symbolic execution
  4. Optimize sequence of K subtasks to minimize maximum complexity jump
  5. Validate quality metrics and apply tie-breaking

- Design tradeoffs:
  - Trade-off between trace completeness and computational efficiency
  - Balance between grid modification (for validity) and visual similarity (for context retention)
  - Choice between exhaustive enumeration vs. greedy optimization for sequence selection

- Failure signatures:
  - No valid subtasks generated: Execution trace filtering removes all candidates or symbolic execution fails
  - Subtasks too dissimilar: Quality metrics indicate poor task similarity or excessive complexity jumps
  - Poor performance in practice: User study shows low success rates despite theoretical quality

- First 3 experiments:
  1. Test on simple reference tasks with known solution structure to verify trace linearization works
  2. Verify symbolic execution generates valid grids by checking if generated codes solve their grids
  3. Test sequence optimization by comparing generated progressions against hand-crafted baselines on complexity metrics

## Limitations
- Limited task complexity: Effectiveness on tasks requiring advanced programming concepts like recursion remains unclear
- Grid dependency: Method assumes tasks with visual grids, limiting generalizability to text-based programming problems
- Optimization constraints: Greedy algorithm for sequence optimization may not find globally optimal progressions

## Confidence
- High confidence: Execution trace linearization mechanism and symbolic execution approach are well-grounded theoretically
- Medium confidence: Well-spaced complexity progression claim is supported by experimental results but could benefit from more direct learning outcome measurements
- Low confidence: Generalizability to tasks beyond simple block-based visual programming scenarios needs further validation

## Next Checks
1. Test on complex programming concepts: Apply ProgresSyn to tasks involving recursion, nested loops with multiple conditions, and data structure manipulation
2. A/B learning study: Conduct controlled study comparing learning outcomes between ProgresSyn-generated progressions versus traditional instruction or random subtask sequences
3. Cross-domain adaptation: Adapt algorithm to generate progressions for text-based programming tasks or non-visual domains
