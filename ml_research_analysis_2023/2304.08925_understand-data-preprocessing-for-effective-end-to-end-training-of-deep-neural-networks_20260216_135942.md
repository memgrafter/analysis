# Understand Data Preprocessing for Effective End-to-End Training of Deep Neural Networks

## Quick Facts
- arXiv ID: 2304.08925
- Source URL: https://arxiv.org/abs/2304.08925
- Authors: [Not specified in source]
- Reference count: 31
- Primary result: Data preprocessing is a bottleneck in DNN training pipelines, even with optimized libraries like NVIDIA DALI

## Executive Summary
This paper examines the data preprocessing pipeline for deep neural network training in the public cloud, identifying preprocessing as a bottleneck that limits overall training performance. The authors find that even with NVIDIA DALI's high optimization, preprocessing time exceeds training time per batch, causing GPU underutilization. They propose flexible resource configurations between storage, loading pipeline, and training framework as a solution, demonstrating that matching resources to model characteristics can significantly improve both performance and cost-effectiveness.

## Method Summary
The study uses AWS p3.16xlarge instances with NVIDIA Tesla V100 GPUs to evaluate five DNN models (AlexNet, ShuffleNet, ResNet18, ResNet50, ResNet152) on ImageNet. It tests four data preprocessing pipeline configurations: raw-cpu, record-cpu, raw-hybrid, and record-hybrid using NVIDIA DALI. The paper evaluates different storage options (EBS, NVMe SSDs, DRAM) and explores resource balancing by adjusting CPU allocation for different models. Performance metrics include data preprocessing and model training throughput, CPU and GPU utilization levels, and I/O bandwidth.

## Key Results
- Data preprocessing is a bottleneck, with peak performance reaching only 23% of the ideal case
- Hybrid CPU-GPU preprocessing improves performance but introduces GPU memory constraints and manual configuration complexity
- Flexible resource configurations can improve training speed by 3.03% to 7.86% for different models
- Storage media selection significantly impacts performance, with DRAM providing 1.84× speedup for AlexNet over EBS

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Data preprocessing is a bottleneck in end-to-end DNN training pipelines, even when using high-optimized libraries like NVIDIA DALI.
- Mechanism: The data preprocessing pipeline involves multiple sequential operations (loading, decoding, augmentation, batching) that must complete before training can proceed. When preprocessing time exceeds training time per batch, GPUs sit idle waiting for data.
- Core assumption: GPU training speed has improved faster than CPU-based preprocessing speed, creating an imbalance.
- Evidence anchors:
  - [abstract] "preliminary results show that data preprocessing is a clear bottleneck, even with the most efficient software and hardware configuration enabled by NVIDIA DALI"
  - [section] "most models see improvement when using record files and especially when adopting hybrid data preprocessing" but "peak performance under record-hybrid is only 23% of the ideal case"
  - [corpus] Weak evidence - no direct citations about preprocessing bottlenecks in related papers
- Break condition: When preprocessing speed matches or exceeds training speed per batch, or when training becomes the bottleneck (as with ResNet50/152 in this study).

### Mechanism 2
- Claim: Flexible resource configurations between storage, loading pipeline, and training framework can maximize performance.
- Mechanism: Different DNN models have different computational characteristics. Some are "fast data consumers" (like AlexNet) that process batches quickly and wait for data, while others are "slow data consumers" (like ResNet50/152) that are computation-bound. Resource allocation should match these characteristics.
- Core assumption: Cloud environments allow granular resource allocation (vCPUs, storage types) that can be optimized per workload.
- Evidence anchors:
  - [section] "Our preliminary results indicate that more flexible node configurations would allow more cost-effective executions of diverse DL pipelines: 7.86% and 3.03% speedup of training speed for AlexNet and ResNet50 with more CPU resources allocated, respectively"
  - [section] "Loading data samples from SSD-based storage options almost delivers the best training speed for ResNet18, while using DRAM introduces a 1.84× speedup for AlexNet"
  - [corpus] Weak evidence - related papers don't discuss resource disaggregation for DL training
- Break condition: When resource allocation perfectly matches workload characteristics, or when resource heterogeneity becomes too complex to manage effectively.

### Mechanism 3
- Claim: CPU-GPU co-processing (as enabled by DALI) improves performance by offloading preprocessing from CPUs, but introduces GPU memory constraints and manual configuration complexity.
- Mechanism: By moving preprocessing operations to GPUs, the bottleneck shifts from CPU preprocessing to GPU memory availability and configuration. This requires careful batch size tuning to avoid OOM errors while maintaining throughput.
- Core assumption: GPUs have sufficient memory and computational capacity to handle preprocessing without significantly impacting training performance.
- Evidence anchors:
  - [section] "DALI does deliver better overall performance by enabling CPU-GPU co-processing for preparing training data samples" but "it possesses caveats such as potential Out-Of-Memory (OOM) problems"
  - [section] "eliminating these errors by reducing the batch size to 384" and "such adjustments also need to be done manually"
  - [corpus] No direct evidence in related papers about CPU-GPU co-processing tradeoffs
- Break condition: When GPU memory is insufficient for both preprocessing and training, or when manual configuration overhead outweighs performance benefits.

## Architecture Onboarding

- Component map: Data storage → Metadata parsing → File loading → Decoding → Augmentation → Batching → GPU training

- Critical path: Data storage → Metadata parsing → File loading → Decoding → Augmentation → Batching → GPU training
  - Bottleneck identification: Measure time spent in each stage to identify the slowest component

- Design tradeoffs:
  - CPU-only vs hybrid preprocessing: CPU-only uses fewer resources but may bottleneck; hybrid uses more resources but can improve throughput
  - Raw vs record file formats: Raw files use less storage but random I/O; record files use more storage but sequential I/O
  - Storage media selection: Balance cost vs performance based on model characteristics

- Failure signatures:
  - GPU underutilization (low GPU utilization percentage)
  - CPU saturation during preprocessing (high CPU utilization, low GPU utilization)
  - I/O bottlenecks (high disk wait times, low I/O bandwidth utilization)
  - Memory issues (OOM errors, frequent memory allocation/deallocation)

- First 3 experiments:
  1. Baseline measurement: Run AlexNet and ResNet18 with default configurations (CPU-only, raw data) and measure GPU utilization, CPU utilization, and I/O throughput
  2. Storage optimization: Test ResNet18 with different storage options (EBS, NVMe SSD, DRAM) while keeping preprocessing method constant
  3. Resource scaling: For AlexNet, incrementally increase CPU resources allocated to preprocessing and measure the impact on GPU utilization and overall training throughput

## Limitations
- The study is limited to five DNN models on ImageNet, potentially limiting generalizability to other architectures and datasets
- Results are specific to AWS p3.16xlarge instances and may not apply to other cloud providers or GPU types
- The paper doesn't explore scenarios where training becomes the bottleneck instead of preprocessing

## Confidence
- Claim: Data preprocessing is universally a bottleneck in DNN training pipelines - High confidence
- Claim: Flexible resource configuration improves performance for specific models - Medium confidence
- Claim: Hybrid CPU-GPU preprocessing is always beneficial - Low confidence
