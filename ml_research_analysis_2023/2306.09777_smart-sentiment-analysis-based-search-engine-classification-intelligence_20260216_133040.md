# Smart Sentiment Analysis-based Search Engine Classification Intelligence

## Quick Facts
- arXiv ID: 2306.09777
- Source URL: https://arxiv.org/abs/2306.09777
- Reference count: 16
- One-line primary result: Sentiment analysis-based search engine improves recall to 99% and precision to 50% for Covid category over deep learning and clustering methods.

## Executive Summary
This paper proposes a search engine that combines BM25 ranking with sentiment analysis to resolve polysemy in news retrieval. The system crawls BBC news articles, preprocesses them using NLTK, builds an inverted index, and ranks results with BM25. Sentiment polarity from Sentistrength is then used to filter and classify ambiguous terms like "jaguar" (animal vs. car) within topic categories. Experimental results show high recall and improved precision compared to baseline methods, though scalability and robustness to fake news remain untested.

## Method Summary
The method involves crawling 800 BBC news articles and storing them in a database. Text is preprocessed using NLTK tokenization, stop-word removal, and stemming, followed by inverted index construction for efficient keyword lookups. BM25 ranks documents by relevance, and Sentistrength assigns sentiment polarity (negative, neutral, positive) to each article. The search function combines keyword matching, BM25 scoring, and sentiment filtering to disambiguate polysemous terms and improve retrieval accuracy, evaluated via recall and precision metrics.

## Key Results
- Classified search achieves 99% recall and 50% precision for Covid category.
- Outperforms deep learning and clustering methods in classifying search results.
- Improves recall while accurately retrieving nonpolysemous news.

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The search function resolves polysemy by integrating sentiment analysis to distinguish contextual meaning of ambiguous terms.
- Mechanism: After retrieving search results using BM25 ranking, the system applies Sentistrength to classify the sentiment polarity of each article. This polarity label, combined with category tags, disambiguates terms like "jaguar" (animal vs. car) by filtering articles that match both the keyword and the expected sentiment context.
- Core assumption: Sentiment polarity is consistent enough within topic categories to help disambiguate polysemous keywords.
- Evidence anchors:
  - [abstract] "the proposed search function improves recall value while accurately retrieving nonpolysemous news"
  - [section] "By incorporating users’ behaviors into our search function, it is possible for the search engine to make predictions about users’ intended meanings when they enter polysemous keywords"
  - [corpus] weak - no direct neighbor evidence of sentiment+polysemy integration; closest is "Enhancing search engine precision and user experience through sentiment-based polysemy resolution"
- Break condition: If sentiment polarity varies widely within a category, disambiguation accuracy drops and polysemy resolution fails.

### Mechanism 2
- Claim: Inverted indexing with BM25 ranking improves retrieval efficiency and relevance scoring for keyword searches.
- Mechanism: The NLTK tokenizer splits queries into tokens, stop words are removed, and an inverted index maps each token to document IDs. BM25 then scores documents by term frequency and document length normalization, ranking results before sentiment filtering.
- Core assumption: TF-IDF-style weighting (as in BM25) effectively captures document relevance for short news queries.
- Evidence anchors:
  - [section] "Each entry in the index table contained a specific attribute and the address of records with that attribute value"
  - [section] "The search results are ranked using the BM25 algorithm, which calculates scores based on the similarities between keywords and web articles"
  - [corpus] no direct neighbor evidence; general IR literature supports BM25 but not cited here
- Break condition: If the vocabulary is too sparse or documents are too short, BM25 scores become unreliable and ranking collapses.

### Mechanism 3
- Claim: Pre-processing with NLTK tokenization, stemming, and stop-word removal improves index quality and reduces noise.
- Mechanism: Before indexing, text is tokenized, lowercased, stemmed, and stop words are removed. This yields cleaner tokens, smaller index size, and more accurate keyword matching.
- Core assumption: Stemming reduces morphological variance without losing discriminative power for news content.
- Evidence anchors:
  - [section] "The resulting words are restricted to their primitive form to ensure complete search functionality"
  - [section] "By eliminating stop words, the number of indexes in the corpus was reduced, resulting in improved retrieval efficiency"
  - [corpus] no direct neighbor evidence; general NLP preprocessing assumptions
- Break condition: If stemming conflates distinct terms (e.g., "organ" vs. "organization"), precision suffers and false matches increase.

## Architecture Onboarding

- Component map:
  Web crawler → JSON storage → Database (news table) → NLTK preprocessing → Inverted index builder → BM25 scorer → Sentiment analyzer (Sentistrength) → Search interface → Result renderer
- Critical path:
  1. User query → tokenize → lookup in inverted index → retrieve candidate docs
  2. BM25 scoring → sentiment filtering → display ranked results
- Design tradeoffs:
  - Smaller index (stop words removed) vs. potential loss of phrase meaning
  - Stemming reduces index size but may cause false matches
  - Sentiment analysis adds classification accuracy but increases latency
- Failure signatures:
  - Zero results → token not in index or BM25 filter too strict
  - Irrelevant results → stemming over-aggressive or sentiment polarity noisy
  - Slow response → index too large or sentiment analysis bottleneck
- First 3 experiments:
  1. Query "apple" → verify retrieval of both fruit and tech articles before/after sentiment filter
  2. Remove stop-word filtering → measure index size growth and precision change
  3. Replace BM25 with TF-IDF → compare recall/precision trade-offs

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the proposed search function perform on datasets significantly larger than 800 articles, such as the entire BBC news archive or other major news sources?
- Basis in paper: [explicit] The paper states "the proposed method can be further applied to other search engines to extract a larger volume of data" and mentions the potential to "search for large volumes of data," but does not provide experimental results for such scenarios.
- Why unresolved: The experiments were limited to a sample of 800 BBC news articles, leaving the scalability and performance on larger datasets untested.
- What evidence would resolve it: Experiments comparing the search function's recall and precision rates on datasets of varying sizes (e.g., 10,000, 100,000, or millions of articles) would demonstrate its scalability and robustness.

### Open Question 2
- Question: Can the search function effectively filter out fake news or unreliable sources, and how would it handle news articles from sources with varying credibility?
- Basis in paper: [inferred] The paper acknowledges a limitation: "The methodology cannot filter out fake news sites from the search results," but does not explore solutions or evaluate the impact of unreliable sources on the search function's performance.
- Why unresolved: The study focuses on BBC news, which is a reliable source, and does not address the challenge of distinguishing fake news from legitimate content.
- What evidence would resolve it: Experiments testing the search function on datasets containing a mix of reliable and fake news sources, along with an evaluation of its ability to prioritize credible information, would address this gap.

### Open Question 3
- Question: How would the search function perform if the categories were automatically generated using machine learning or artificial intelligence, rather than manually predefined?
- Basis in paper: [explicit] The paper suggests that "Future work could involve the automatic creation of search categories using artificial intelligence," but does not provide any experimental results or analysis of such an approach.
- Why unresolved: The current implementation relies on manually predefined categories, and the potential benefits or challenges of automated category generation are unexplored.
- What evidence would resolve it: A comparison of the search function's performance using manually predefined categories versus automatically generated categories, along with an analysis of the accuracy and efficiency of the AI-driven approach, would provide insights into its feasibility.

## Limitations
- Small, single-source dataset (800 BBC articles) limits generalizability and scalability testing.
- Reliance on Sentistrength may be brittle for nuanced or noisy text without clear sentiment thresholds.
- No comparison with modern transformer-based retrieval models or ablation study on sentiment's isolated impact.

## Confidence

- **High confidence**: BM25 ranking effectiveness and preprocessing steps (tokenization, stemming, stop-word removal) are well-established IR techniques with predictable impact.
- **Medium confidence**: Sentiment-based polysemy resolution works in this controlled BBC dataset, but scalability and robustness to noisy or mixed-sentiment contexts are unproven.
- **Low confidence**: Claims of outperforming deep learning/clustering methods are weakly supported due to lack of direct experimental comparison or baseline specification.
