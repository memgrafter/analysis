# Constant Memory Attention Block

## Quick Facts
- arXiv ID: 2306.12599
- Source URL: https://arxiv.org/abs/2306.12599
- Reference count: 12
- Primary result: CMAB achieves constant memory and constant computation updates while maintaining competitive performance with state-of-the-art methods

## Executive Summary
This paper introduces the Constant Memory Attention Block (CMAB), a novel attention mechanism that addresses the scalability limitations of traditional attention methods. CMAB achieves constant memory complexity by splitting input data into fixed-size batches and performing rolling updates, while also enabling constant computation updates when new data arrives. The mechanism is applied to Constant Memory Attentive Neural Processes (CMANPs) and Constant Memory Hawkes Processes (CMHPs), demonstrating competitive performance on image generation and temporal point process tasks while significantly reducing memory requirements.

## Method Summary
CMAB is built on attention mechanisms, specifically cross-attention and self-attention operations. The input data is divided into N/BC batches of size up to BC. Instead of computing the output at once, it performs the update N/BC - 1 times using a rolling average approach. When new data points arrive, the updated output can be computed via a rolling average in O(|DU|) operations. This is possible because the query matrix remains constant while the key and value matrices only have new rows appended. The architecture preserves permutation invariance and equivariance properties of neural processes through its design.

## Key Results
- CMANPs achieve 3.93 ± 0.05 log-likelihood on CelebA and 1.09 ± 0.01 on EMNIST
- CMHPs achieve 0.168 ± 0.011 RMSE on Mooc and 0.262 ± 0.037 on Reddit
- Both models demonstrate constant memory usage while maintaining competitive performance with state-of-the-art methods

## Why This Works (Mechanism)

### Mechanism 1
CMAB achieves constant memory complexity by splitting input data into fixed-size batches and performing rolling updates. The input data INPUT is divided into N/BC batches of size up to BC. Instead of computing the output at once, it performs the update N/BC - 1 times using a rolling average approach. After each computation, the memory is freed up, allowing subsequent updates to reuse the same memory space.

### Mechanism 2
CMAB achieves constant computation updates by leveraging the mathematical properties of cross-attention. When new data points DU arrive, the updated output of the first cross-attention can be computed via a rolling average in O(|DU|) operations. This is possible because the query matrix (representing BEMB embeddings) remains constant, while the key and value matrices only have new rows appended.

### Mechanism 3
CMAB preserves permutation invariance and equivariance properties of neural processes. The cross-attention operation is inherently permutation invariant in its keys and values. Since CMAB's output depends on a compressed encoding of the context dataset computed by cross-attention, the entire CMAB output is permutation invariant in the input data. Target equivariance is preserved because predictions are made independently for each target point.

## Architecture Onboarding

- Component map: Input layer -> Cross-attention blocks -> Self-attention blocks -> Output layer
- Critical path:
  1. Input data passes through the first cross-attention with BEMB
  2. Result passes through self-attention to compute higher-order information
  3. Output passes through second cross-attention with IEMB
  4. Result passes through final self-attention to produce OEMB
  5. OEMB becomes IEMB for the next stacked CMAB block

- Design tradeoffs:
  - Memory vs. computation: CMAB trades increased computation for reduced memory usage
  - Fixed latent size: The bottleneck size (LB, LI) limits the amount of information that can be encoded
  - Batch size BC: Must be chosen carefully to balance memory efficiency and computation overhead

- Failure signatures:
  - Memory overflow: If BC is set too large for available memory
  - Degraded performance: If LB or LI are too small to capture necessary information
  - Numerical instability: During the rolling update computation, particularly with very large or very small values

- First 3 experiments:
  1. Memory complexity analysis: Measure memory usage of CMAB vs. standard attention as input size varies
  2. Update efficiency test: Measure computation time for updating with new data points vs. recomputing from scratch
  3. Ablation study: Test performance with different values of LB, LI, and BC to find optimal configuration

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does CMAB performance scale with different values of bottleneck sizes LB and LI?
- Basis in paper: The paper mentions LB and LI are hyperparameters that bottleneck information encoding, but doesn't explore their impact on performance
- Why unresolved: The paper sets LB = LI = 128 across all experiments without exploring sensitivity to these values

### Open Question 2
- Question: What is the theoretical limit of information compression achievable by CMAB compared to traditional attention mechanisms?
- Basis in paper: The paper claims CMAB can encode information in constant memory, but doesn't quantify information capacity limits
- Why unresolved: The paper focuses on practical implementation rather than theoretical bounds on information preservation

### Open Question 3
- Question: How does CMAB's constant memory property affect privacy when processing sensitive sequential data?
- Basis in paper: The paper mentions CMABs have "privacy-preserving properties" but doesn't elaborate on this claim
- Why unresolved: The paper mentions privacy as a benefit but doesn't investigate privacy-utility tradeoffs or provide formal privacy guarantees

### Open Question 4
- Question: What is the computational overhead of CMAB's update mechanism compared to recomputing attention from scratch in streaming applications?
- Basis in paper: The paper claims CMAB updates are "constant computation per datapoint" but doesn't benchmark against alternatives
- Why unresolved: The paper provides theoretical complexity analysis but lacks empirical comparison of update efficiency

### Open Question 5
- Question: How does CMAB's performance degrade with non-stationary data distributions in streaming settings?
- Basis in paper: The paper demonstrates competitive performance on static benchmarks but doesn't test adaptation to distribution shifts
- Why unresolved: The paper focuses on static dataset performance without evaluating robustness to concept drift or non-stationarity

## Limitations
- Implementation details remain unclear, particularly the mathematical formulation for the rolling update equations
- Empirical validation focuses on specific datasets without extensive ablation studies across different domains
- Theoretical analysis of information capacity limits is not provided

## Confidence
- **High Confidence**: The constant memory property claim is well-supported by the architectural description and mathematical formulation
- **Medium Confidence**: The constant computation update claim has theoretical backing but lacks detailed numerical analysis
- **Medium Confidence**: The permutation invariance claims are logically sound but empirical validation is limited
