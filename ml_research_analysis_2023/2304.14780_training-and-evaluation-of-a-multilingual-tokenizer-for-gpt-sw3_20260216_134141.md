# Training and Evaluation of a Multilingual Tokenizer for GPT-SW3

## Quick Facts
- arXiv ID: 2304.14780
- Source URL: https://arxiv.org/abs/2304.14780
- Reference count: 15
- Key outcome: Development and evaluation of a 64k vocabulary multilingual tokenizer for Nordic languages using SentencePiece with BPE algorithm

## Executive Summary
This paper presents the development and evaluation of a multilingual tokenizer for GPT-SW3, a language model for Nordic languages. The tokenizer was trained on a sampled portion of the Nordic Pile dataset using SentencePiece with Byte-Pair Encoding, incorporating features like special tokens, digit splitting, dummy prefix, whitespace concatenation, code tokens, byte fallback, and character coverage. The tokenizer's performance was evaluated using fertility and proportion of continued words metrics across multiple Nordic languages, revealing strengths for Swedish, English, Norwegian, and Danish, while showing limitations for Icelandic and code. The study also analyzed the impact of vocabulary size on performance, demonstrating improved metrics with larger vocabularies.

## Method Summary
The tokenizer was developed using the SentencePiece library with BPE algorithm, trained on 1% of the Nordic Pile dataset with a vocabulary size of 64,000 tokens. The training incorporated multiple features including special tokens, digit splitting, dummy prefix, whitespace concatenation for code, code tokens, byte fallback with 0.9999 character coverage, and preserved language weighting during sampling. The tokenizer was evaluated using fertility (average subwords per word) and proportion of continued words metrics on monolingual evaluation datasets. Performance was compared against monolingual tokenizers, and the impact of vocabulary size (16k-64k) on these metrics was analyzed.

## Key Results
- The tokenizer performs well for Swedish, English, Norwegian, and Danish with fertility and continued words metrics comparable to or better than monolingual tokenizers
- Icelandic and code languages show higher fertility and continued words values, indicating less effective tokenization
- Larger vocabulary sizes lead to improved tokenizer performance, with metrics showing diminishing returns as vocabulary increases
- The tokenizer successfully handles the multilingual requirements of GPT-SW3 with reasonable detokenization quality across all Nordic languages

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The multilingual tokenizer achieves better language coverage by combining byte fallback with character coverage.
- Mechanism: When training data contains rare or unseen characters, the tokenizer decomposes them into UTF-8 byte code units instead of assigning an unknown token. By setting character coverage to 0.9999, the tokenizer reserves vocabulary space for common multi-character tokens while still handling rare characters meaningfully.
- Core assumption: Rare characters are infrequent enough that decomposing them into bytes is more efficient than dedicating vocabulary slots to them.
- Evidence anchors:
  - [abstract] mentions "byte fallback, and a vocabulary size of 64,000"
  - [section] describes "Another feature, related to byte fallback, is character coverage... We opt to use byte fallback with a character coverage of 0.9999."
  - [corpus] shows the approach is used in other multilingual work, though details are weak
- Break condition: If rare characters become common in the target languages, the decomposition into bytes could hurt model performance by losing semantic meaning.

### Mechanism 2
- Claim: Vocabulary size directly impacts tokenizer performance, with diminishing returns beyond 64k tokens.
- Mechanism: Larger vocabularies allow more words to remain intact rather than being split into subwords, improving fertility (average subwords per word) and reducing continued words proportion. The study shows performance improvements plateau as vocabulary grows.
- Core assumption: The relationship between vocabulary size and performance follows a logarithmic curve with diminishing returns.
- Evidence anchors:
  - [abstract] states "The study also analyzed the impact of vocabulary size, showing improved performance with larger vocabularies"
  - [section] shows "larger vocabulary size leads to better tokenizer performance... the curves seem to flatten as the vocabulary size increases"
  - [corpus] provides limited direct evidence but similar patterns exist in literature
- Break condition: If the target languages have highly productive morphology, the relationship might not flatten, requiring even larger vocabularies.

### Mechanism 3
- Claim: Whitespace concatenation significantly improves tokenization efficiency for code data.
- Mechanism: By adding consecutive whitespace tokens (2-24 spaces) to the vocabulary, the tokenizer can represent indented code blocks with fewer tokens, reducing fragmentation of code structure.
- Core assumption: Code data contains significant whitespace patterns that can be captured as vocabulary entries.
- Evidence anchors:
  - [abstract] mentions "whitespace concatenation, code tokens"
  - [section] explains "In order for the tokenizer to decompose such text into fewer tokens, one may add consecutive whitespace tokens to the vocabulary"
  - [corpus] shows this technique is adopted from other work but lacks detailed validation
- Break condition: If code formatting varies widely or uses tabs instead of spaces, this mechanism may provide minimal benefit.

## Architecture Onboarding

- Component map:
  - Nordic Pile sampling -> tokenizer training data preparation -> SentencePiece with BPE -> vocabulary generation -> evaluation datasets -> fertility and continued words metrics

- Critical path:
  1. Sample 1% of Nordic Pile for tokenizer training
  2. Configure SentencePiece with all special features
  3. Train BPE tokenizer with 64k vocabulary size
  4. Evaluate on monolingual datasets using fertility and continued words metrics
  5. Analyze results and compare with monolingual tokenizers

- Design tradeoffs:
  - Vocabulary size vs computational cost: Larger vocabularies improve performance but increase embedding matrix size
  - Byte fallback vs character coverage: Byte fallback handles unknown characters but may lose semantic meaning
  - Special features vs vocabulary efficiency: Features like whitespace concatenation improve code tokenization but consume vocabulary slots

- Failure signatures:
  - High fertility and continued words values indicate poor tokenizer fit for a language
  - Underrepresentation of certain languages in vocabulary leads to poor model performance
  - Excessive vocabulary consumption by special features leaves insufficient space for regular tokens

- First 3 experiments:
  1. Train tokenizer with 32k vocabulary size and compare performance metrics to baseline 64k
  2. Disable byte fallback and evaluate impact on fertility for Icelandic and code languages
  3. Remove whitespace concatenation feature and measure tokenization efficiency on code datasets

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How would the tokenizer's performance change if trained on a balanced multilingual dataset rather than a weighted one?
- Basis in paper: [explicit] The paper discusses using weighted subsets of the Nordic Pile dataset for tokenizer training, with different weights assigned to different language subsets.
- Why unresolved: The paper evaluates the tokenizer's performance on the weighted dataset but does not explore the impact of using a balanced dataset.
- What evidence would resolve it: Training the tokenizer on a balanced dataset and comparing its performance metrics (fertility and proportion of continued words) across languages with the current weighted approach.

### Open Question 2
- Question: What specific language-specific factors contribute to the higher fertility and proportion of continued words for Icelandic and code compared to other languages?
- Basis in paper: [inferred] The paper notes that Icelandic and code have higher fertility and proportion of continued words, suggesting language-specific factors may be at play.
- Why unresolved: The paper hypothesizes potential reasons but does not conduct a detailed analysis of language-specific factors.
- What evidence would resolve it: Conducting a detailed linguistic analysis of Icelandic and code structures, and comparing them with other languages to identify specific factors contributing to higher tokenization metrics.

### Open Question 3
- Question: How does the tokenizer's performance scale with even larger vocabulary sizes beyond 64,000 tokens?
- Basis in paper: [explicit] The paper evaluates the tokenizer's performance with vocabulary sizes up to 64,000 tokens and observes improvements, but does not explore larger sizes.
- Why unresolved: The study stops at 64,000 tokens, leaving open the question of performance with even larger vocabularies.
- What evidence would resolve it: Training the tokenizer with vocabulary sizes significantly larger than 64,000 tokens and measuring the resulting performance metrics to determine if further improvements occur.

## Limitations

- The study uses relatively small sample sizes (1% for training, 0.2% for evaluation) which may not fully capture the complexity of under-represented languages like Icelandic
- The analysis of vocabulary size impact is limited to 16k-64k range, leaving questions about performance at very large scales
- Fertility and continued words metrics don't directly measure downstream model performance, creating a validation gap

## Confidence

- **High**: The tokenizer's overall architecture and use of SentencePiece with BPE is well-established and the basic evaluation methodology is sound
- **Medium**: Performance claims for Swedish, English, Norwegian, and Danish are well-supported by the metrics presented
- **Low**: Claims about tokenizer performance for Icelandic and code are less substantiated due to data limitations and lack of detailed feature impact analysis

## Next Checks

1. **Feature ablation study**: Systematically disable individual features (whitespace concatenation, byte fallback, etc.) and measure their impact on tokenization quality for each language, particularly for Icelandic and code

2. **Downstream model evaluation**: Train small language models using different tokenizer configurations and measure actual performance differences on representative tasks for each Nordic language

3. **Vocabulary size scaling**: Extend the vocabulary size analysis to include much larger sizes (128k, 256k, 512k) to determine if the diminishing returns pattern continues or if new thresholds emerge for the Nordic languages
