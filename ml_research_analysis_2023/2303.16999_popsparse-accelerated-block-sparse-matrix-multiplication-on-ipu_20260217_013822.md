# PopSparse: Accelerated block sparse matrix multiplication on IPU

## Quick Facts
- arXiv ID: 2303.16999
- Source URL: https://arxiv.org/abs/2303.16999
- Reference count: 17
- PopSparse enables sparse matrix multiplication acceleration on Graphcore IPUs, achieving up to 4.9x speedup for 16x16 blocks at 1/32 density

## Executive Summary
PopSparse is a library that accelerates block sparse matrix multiplication on Graphcore IPUs by leveraging hardware characteristics including large on-chip SRAM and fine-grained MIMD architecture. The library supports both static sparsity with fixed patterns at compile time and dynamic sparsity with runtime pattern updates. Benchmarks show PopSparse static sparse outperforms dense FP16 matmul at low densities (around 90%) with large matrices and block sizes, achieving significant speedups compared to dense implementations. IPU sparse performance matches or exceeds GPU sparse implementations, particularly for block sparsity, demonstrating that practical sparse acceleration is achievable at lower sparsity levels than previously shown on GPUs.

## Method Summary
PopSparse library provides APIs for creating sparse tensors with configurable block sizes (1, 4, 8, 16) and densities (1/1, 1/4, 1/8, 1/16, 1/32). The library supports two modes: static sparsity where patterns are fixed at compile time, and dynamic sparsity where patterns can change at runtime. For static mode, the compiler constructs the computation graph based on known sparsity patterns during compilation. For dynamic mode, the maximum non-zero elements are fixed but patterns can be updated during execution. The implementation leverages IPU's large on-chip memory to reduce communication overhead and its MIMD architecture to exploit parallelism in sparse operations. Performance is benchmarked against dense implementations and cuSPARSE/cuBLAS GPU baselines.

## Key Results
- Static sparse outperforms dense FP16 matmul at densities around 90% with large matrices and block sizes
- Static sparsity consistently outperforms dynamic due to lower overhead from compile-time optimization
- IPU sparse performance matches or exceeds GPU sparse implementations for block sparsity
- Achieved up to 4.9x speedup for 16x16 blocks at 1/32 density with m=k=4096, n=1024

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Static sparsity outperforms dynamic sparsity because sparsity pattern is known at compile time, enabling optimal partitioning and reducing runtime overhead.
- Mechanism: The compiler can pre-partition the matrix into balanced tiles without runtime redistribution. No need for dynamic exchange phases to rebalance unbalanced data.
- Core assumption: The sparsity pattern remains fixed for the entire execution.
- Evidence anchors:
  - [abstract] "static, where the sparsity pattern is fixed at compile-time; and dynamic, where it can change each time the model is run."
  - [section 3.2] "With static sparsity, during compile time, the sparsity pattern and matrix shapes (m, k and n) are known to the partitioner...No extra exchange of data is needed."
  - [section 3.3] "With dynamic sparsity, the maximum number of non-zero elements for the sparse operand is fixed, while the sparsity pattern is updated during runtime...additional planning is required for dynamic sparsity during compilation and there is an overhead for partitioning based on a specific sparsity pattern during runtime."
- Break condition: If the sparsity pattern changes frequently between runs, dynamic sparsity may be required despite higher overhead.

### Mechanism 2
- Claim: Block sparsity reduces metadata overhead and improves hardware utilization compared to unstructured sparsity.
- Mechanism: Block sparsity groups non-zero elements into contiguous blocks, reducing the storage and processing cost of sparsity metadata. Hardware can process submatrices instead of individual elements, improving vectorization.
- Core assumption: The block structure aligns with hardware capabilities for processing contiguous data.
- Evidence anchors:
  - [section 1] "one approach to improving sparse compute efficiency is to enforce some degree of structure on the sparsity pattern to better align it with the hardware architecture."
  - [section 3.1] "PopSparse library supports unstructured (block size b = 1) or structured sparsity (b = 4, 8, 16)."
  - [section 5.3] "Block sparsity speeds up sparse computation for two main reasons. First, there is less overhead incurred to store and process the metadata that encode the sparsity pattern. Second, it allows implementations to process non-zero submatrices rather than just vectors, making more effective use of the hardware."
- Break condition: If the application requires very fine-grained sparsity patterns that cannot be efficiently represented with blocks, unstructured sparsity may be necessary.

### Mechanism 3
- Claim: IPU's large on-chip SRAM and fine-grained MIMD architecture enable efficient sparse operations by reducing communication overhead.
- Mechanism: The large SRAM reduces the cost of moving sparse data between memory levels. The MIMD architecture allows parallel processing of non-uniform work distributions inherent in sparse operations.
- Core assumption: Sparse operations have high communication-to-compute ratios that benefit from large on-chip memory and fine-grained parallelism.
- Evidence anchors:
  - [section 2] "IPUs have a number of architectural features that help accelerate sparse operations, firstly they have a large amount of high bandwidth on-chip SRAM which drastically improves performance for communication heavy, low arithmetic efficiency operations."
  - [section 2] "they use a fine grained MIMD processing model that partitions work over 1472 independent compute units, here on described as tiles. This means high degrees of parallelism can be exploited from operations even if they cannot be structured as a single large matrix multiplication."
- Break condition: If the problem size exceeds available on-chip memory, the advantage of large SRAM diminishes.

## Architecture Onboarding

- Component map:
  - PopSparse library (static and dynamic modules) -> IPU hardware (tiles, SRAM, exchange fabric) -> Poplar graph compiler -> Host utilities (partitioner, planner) -> cuSPARSE and cuBLAS GPU baselines

- Critical path:
  1. Host defines sparsity pattern and matrix dimensions
  2. Compiler (Poplar) constructs graph based on pattern (static) or maximum density (dynamic)
  3. At runtime: host provides weight values and reorders them
  4. IPU executes computation and reduction phases
  5. Results returned to host

- Design tradeoffs:
  - Static vs dynamic: performance vs flexibility
  - Block size: metadata overhead vs hardware utilization
  - Feature size: ability to balance work across tiles vs memory constraints
  - Density: sparse speedup vs computational density

- Failure signatures:
  - Dynamic sparsity: unexpected runtime overhead, variable performance based on pattern
  - Static sparsity: compile-time errors when pattern changes between runs
  - Both: poor performance when density is too high or feature size too small

- First 3 experiments:
  1. Benchmark static sparse vs dense with fixed pattern at various densities (d=1/16, 1/32) and block sizes (b=4, 16) for m=k=4096, n=1024
  2. Benchmark dynamic sparse vs static sparse with same parameters but varying patterns to measure overhead
  3. Benchmark IPU static sparse against GPU BSR sparse for direct comparison at low densities (d=1/32)

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does static block sparsity performance on IPU compare to dynamic sparsity when considering different neural network architectures beyond matrix multiplication?
- Basis in paper: [explicit] The paper states that static sparsity consistently outperforms dynamic sparsity, but only benchmarks matrix multiplication.
- Why unresolved: The comparison is limited to SpMM operations and doesn't extend to complete neural network models where different layers and architectures might interact differently with static vs dynamic sparsity patterns.
- What evidence would resolve it: Benchmarking static and dynamic sparsity implementations across various neural network architectures (CNNs, Transformers, etc.) would reveal whether the static advantage holds in realistic scenarios.

### Open Question 2
- Question: What is the practical performance impact of block sparsity patterns on task accuracy for different pruning algorithms?
- Basis in paper: [inferred] The paper mentions that few deep learning works explore block sparsity and that finding block sparse patterns that don't degrade performance is difficult.
- Why unresolved: While the paper demonstrates computational benefits of block sparsity, it doesn't evaluate the accuracy trade-offs when applying different block sparsity pruning methods to actual models.
- What evidence would resolve it: Systematic evaluation of various block sparsity pruning algorithms applied to standard models, measuring both accuracy retention and computational speedup, would quantify the practical trade-offs.

### Open Question 3
- Question: How does PopSparse's performance scale when distributed across multiple IPUs for extremely large sparse matrices?
- Basis in paper: [inferred] The paper benchmarks single IPU performance but doesn't explore multi-IPU scaling, though it mentions IPUs can communicate across all-to-all fabric.
- Why unresolved: Modern large-scale models require massive matrices that exceed single IPU memory, but the paper doesn't investigate how partitioning and communication overhead affects sparse computation across multiple devices.
- What evidence would resolve it: Benchmarking PopSparse with distributed sparse matrix multiplication across multiple IPUs, measuring both weak and strong scaling, would reveal practical limits and optimization opportunities.

## Limitations

- Performance benefits are tied to IPU's unique architecture (large SRAM, MIMD), making generalization to other accelerators uncertain
- Limited comparison scope: Only one GPU model (A100) is used as baseline, though performance varies across GPU generations
- Dynamic sparsity overhead characterization is incomplete across different sparsity patterns

## Confidence

- **High Confidence:** Static sparsity consistently outperforms dynamic sparsity; block sparsity reduces metadata overhead; IPU sparse performance matches or exceeds GPU sparse for block sparsity
- **Medium Confidence:** PopSparse achieves sparse speedup at lower densities than previously shown on GPUs; 4.9x speedup claim for specific configuration
- **Low-Medium Confidence:** Generalization of speedup trends across different matrix dimensions and sparsity patterns; exact overhead quantification for dynamic sparsity
