# Learning When to Speak: Latency and Quality Trade-offs for Simultaneous Speech-to-Speech Translation with Offline Models

## Quick Facts
- arXiv ID: 2306.01201
- Source URL: https://arxiv.org/abs/2306.01201
- Reference count: 0
- Near-offline BLEU scores with minimal latency increase using tunable policies

## Executive Summary
This paper introduces a simultaneous speech-to-speech translation (SimulS2ST) system that achieves near-offline translation quality with low latency by combining an offline speech-to-text model (Whisper) with a text-to-speech system (ElevenLabs) through tunable policy frameworks. The system supports 57 languages to English and evaluates four policies—Greedy, Offline, Confidence-Aware, and Consensus—to determine optimal timing for speech output. Results demonstrate that the proposed policies achieve BLEU scores comparable to offline translation while maintaining significantly lower latency than wait-k baselines, with performance varying based on language similarity to English.

## Method Summary
The system uses a cascaded approach combining OpenAI's Whisper for simultaneous speech-to-text translation and ElevenLabs for text-to-speech synthesis. Four policies control when to output translated speech: Greedy (wait-k baseline), Offline (post-hoc transcription), Confidence-Aware (waits for high confidence), and Consensus (waits for output stability). The system processes audio in a multithreaded pipeline with separate threads for transcription, policy evaluation, and TTS generation. Evaluation uses 75 filtered audio samples from CoVoST2 dev set across four languages (Japanese, Spanish, Russian, Arabic), measuring translation quality via SacreBLEU and latency via Computation-Aware Average Lagging.

## Key Results
- Confidence-Aware and Consensus policies achieve BLEU scores within 1-2 points of offline performance while maintaining 30-50% lower latency than Greedy baseline
- Spanish and Russian consistently achieve better latency-quality trade-offs than Japanese and Arabic, suggesting language structure similarity to English affects performance
- No single policy dominates across all languages, indicating need for language-specific tuning
- System supports 57 source languages with minimal architecture changes

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Cascaded approach achieves near-offline BLEU with low latency by decoupling translation and speech synthesis
- Mechanism: Offline Whisper provides high-quality text translation, spoken only when policies determine sufficient context is available
- Core assumption: Whisper's accuracy is sufficient as SimulST backend without fine-tuning
- Evidence anchors:
  - "These policies achieve offline-level accuracy with minimal increases in latency over a Greedy (wait-k) baseline"
  - "We use an off-the-shelf offline ST model (OpenAI's Whisper [5]) and query it in an online fashion to produce accurate translations with low latency"

### Mechanism 2
- Claim: Tunable policy thresholds let users dynamically balance quality vs. latency
- Mechanism: Confidence-Aware Policy waits until translation confidence exceeds threshold γ; Consensus Policy waits until consecutive outputs stabilize
- Core assumption: Confidence scores and edit distance ratios reliably indicate translation readiness
- Evidence anchors:
  - "we use an off-the-shelf offline ST model (OpenAI's Whisper [5]) and query it in an online fashion"
  - "we found that Whisper's no speech prob field gave better empirical results than the avg logprob field"

### Mechanism 3
- Claim: Multithreading prevents pipeline stalls and keeps average lagging low
- Mechanism: Separate threads for transcription, policy evaluation, and TTS generation allow independent processing
- Core assumption: Thread communication overhead is negligible compared to model inference time
- Evidence anchors:
  - "We implement the SimulST and TTS model on separate threads to prevent unnecessary execution dependencies"
  - "when accepting live microphone input, the recorder is also given a separate thread"

  - Why needed: CP uses edit distance between consecutive outputs to detect stabilization
  - Quick check question: If two consecutive translations differ by only one word, should CP consider the output stable?

## Architecture Onboarding

- Component map:
  Frame buffer → Whisper → Policy → TTS → Audio output
- Critical path:
  Frame buffer → Whisper ST model query → Policy module → TTS generation → Audio output
- Design tradeoffs:
  - Offline model vs. fine-tuned SimulST: Higher accuracy vs. higher latency if not optimized for streaming
  - Confidence vs. consensus: CAP reacts to model certainty, CP to output stability—different failure modes
  - Multithreading: Better latency but higher implementation complexity
- Failure signatures:
  - High latency, low BLEU: Policy thresholds too conservative
  - Low latency, low BLEU: Policy thresholds too aggressive or Whisper underperforming
  - Stuttering audio: TTS thread lagging behind SimulST thread
- First 3 experiments:
  1. Measure latency and BLEU for each policy with varying thresholds on a small dev set
  2. Profile thread execution times to identify bottlenecks
  3. Test language-specific behavior (e.g., Japanese vs. Spanish) to confirm structural similarity effects

## Open Questions the Paper Calls Out

- Question: What is the optimal policy parameter configuration for each language to achieve the best latency-quality trade-off?
- Basis: "no single policy performs the best across all languages" and "practitioners must tune their systems on a per-language basis"
- Why unresolved: Paper only evaluates limited parameter values for Confidence-Aware and Consensus policies
- What evidence would resolve it: Systematic evaluation of wider range of parameter values for each policy and language combination

- Question: How does the system's performance scale with larger datasets and more diverse language pairs?
- Basis: Evaluation on 75 examples from 4 languages limits generalizability
- Why unresolved: Small, fixed dataset and limited language pairs make scalability unclear
- What evidence would resolve it: Evaluation on larger, more diverse datasets and wider range of language pairs

- Question: How does the choice of offline ST model impact performance compared to other models?
- Basis: Paper uses Whisper but does not compare to other models
- Why unresolved: Only evaluates with Whisper, leaving model choice impact unexplored
- What evidence would resolve it: Comparison of system performance using different offline ST models

## Limitations

- Confidence scores from Whisper's "no speech prob" field may not generalize well to all 57 source languages, particularly low-resource languages
- Evaluation corpus contains only 75 samples across 4 languages, limiting statistical power for language-specific conclusions
- ElevenLabs TTS API introduces external latency variability that may affect measured AL_CA scores and create dependencies between translation quality and TTS response times

## Confidence

**High confidence:** Cascaded architecture using offline Whisper with online querying achieves near-offline BLEU scores with minimal latency increase (directly supported by quantitative results).

**Medium confidence:** Language structure similarity to English predicts latency-quality trade-offs (results show Spanish/Russian better than Japanese/Arabic, but small sample size limits generalization).

**Low confidence:** Specific threshold values (γ=0.9/0.5 for CAP, α=0.75/0.5 for CP) represent optimal settings (paper reports these values but lacks systematic sensitivity analysis).

## Next Checks

1. **Corpus expansion validation:** Test four policies on larger, more diverse corpus covering all 57 source languages with 100+ utterances per language to verify Spanish/Russian performance patterns and assess low-resource language behavior.

2. **Threshold sensitivity analysis:** Systematically vary confidence (γ) and consensus (α) thresholds across full range for each policy and language pair, measuring BLEU-AL_CA trade-offs to identify whether reported values represent true optima.

3. **Component isolation latency profiling:** Measure end-to-end latency while independently varying Whisper ST processing time, ElevenLabs TTS response time, and thread synchronization overhead to determine which component contributes most to total latency.
