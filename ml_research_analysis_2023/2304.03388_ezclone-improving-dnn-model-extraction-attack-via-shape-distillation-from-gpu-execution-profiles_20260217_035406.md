# EZClone: Improving DNN Model Extraction Attack via Shape Distillation from GPU Execution Profiles

## Quick Facts
- arXiv ID: 2304.03388
- Source URL: https://arxiv.org/abs/2304.03388
- Reference count: 40
- Key outcome: 100% accuracy in predicting DNN architectures using aggregate GPU profiles

## Executive Summary
EZClone introduces a novel framework for extracting deep neural network architectures through GPU execution profiles as a side-channel. By leveraging aggregate GPU kernel data rather than time-series information, EZClone achieves perfect classification accuracy across 36 PyTorch vision architectures using as few as three kernel features. The framework employs Recursive Feature Elimination to identify the most discriminative features and demonstrates effectiveness across different GPUs and pruned models. This work reveals a new attack vector for architecture extraction that requires minimal computational resources and is easily extensible to new architectures.

## Method Summary
EZClone collects aggregate GPU profiles using NVIDIA's nvprof profiler on 36 PyTorch vision architectures. The method extracts GPU kernel features from these profiles, applies Recursive Feature Elimination to identify the most relevant features, and trains machine learning classifiers (primarily Random Forest) to predict architecture. The approach focuses on aggregate rather than time-series data, requiring only one profile per architecture for training. Feature engineering includes indicator columns for kernel presence and normalization, while models are trained on subsets of GPU kernel features (excluding memory operations) and tested on held-out data.

## Key Results
- 100% accuracy in predicting all 36 PyTorch vision architectures
- Achieves perfect accuracy using only 3 GPU kernel features via RFE
- Successfully transfers across different GPU models
- Maintains effectiveness on pruned DNN models
- Requires minimal computational resources and no time-series information

## Why This Works (Mechanism)

### Mechanism 1
- Claim: GPU kernel execution profiles uniquely fingerprint DNN architectures.
- Mechanism: Different DNN architectures invoke different sets of GPU kernels with distinct timing patterns, and these patterns can be aggregated to distinguish architectures.
- Core assumption: The mapping from DNN layers to GPU kernels is deterministic and stable across runs.
- Evidence anchors:
  - [abstract] "EZClone exploits aggregate (rather than time-series) GPU profiles as a side-channel to predict DNN architecture"
  - [section] "each datapoint of the profile... becomes a feature of the side-channel information H(fθ)"
  - [corpus] Weak: corpus papers focus on operator parallelism and accelerator side-channels, not direct architecture fingerprinting from GPU kernels.
- Break condition: If DNN frameworks change kernel implementations or add layer fusion that obscures individual kernel timing.

### Mechanism 2
- Claim: A small subset of GPU kernel features suffices for accurate architecture prediction.
- Mechanism: Recursive Feature Elimination identifies the most discriminative kernel features, reducing dimensionality while maintaining prediction accuracy.
- Core assumption: The most important kernel features capture sufficient architectural information.
- Evidence anchors:
  - [section] "We run SKLearn's Recursive Feature Elimination (RFE) feature selection algorithm to rank these features"
  - [section] "Figure 3 shows that the same accuracy can be achieved using only 3 features"
  - [corpus] Missing: corpus does not address feature selection for architecture extraction.
- Break condition: If architectural similarity increases and fewer features become insufficient to discriminate between models.

### Mechanism 3
- Claim: EZClone generalizes across different GPUs and pruned models.
- Mechanism: The relationship between kernel features and architecture is preserved across hardware and model sparsity variations.
- Core assumption: Kernel execution patterns are consistent enough across GPUs and pruning levels to enable cross-device and cross-pruning generalization.
- Evidence anchors:
  - [section] "We examine the ability of the EZClone attack to transfer across GPUs"
  - [section] "We investigate whether DNN pruning affects the efficacy of EZClone"
  - [corpus] Weak: corpus neighbors focus on accelerator attacks and distillation, not cross-GPU generalization.
- Break condition: If different GPUs implement kernels with significantly different performance characteristics or pruning changes kernel invocation patterns.

## Architecture Onboarding

- Component map:
  Profile collection -> Feature engineering -> Model training -> Attack execution

- Critical path: Profile collection → Feature selection → Model training → Attack prediction

- Design tradeoffs:
  - More features vs. overfitting (addressed by RFE)
  - Larger candidate set vs. preprocessing time (mitigation: few profiles per architecture)
  - Cross-GPU accuracy vs. need for device-specific training

- Failure signatures:
  - Low accuracy across test sets indicates overfitting or insufficient discriminative features
  - Poor cross-GPU performance suggests hardware-specific timing patterns dominate
  - Zero accuracy on pruned models indicates kernel invocation patterns change significantly

- First 3 experiments:
  1. Profile a single architecture (e.g., ResNet18) with nvprof and examine kernel feature distribution
  2. Train a simple classifier (e.g., Random Forest) on 3-5 architectures using all features, evaluate accuracy
  3. Apply RFE to reduce to top 3 features and verify accuracy remains high

## Limitations
- Limited to PyTorch framework; cross-framework generalizability unknown
- Assumes attacker can collect nvprof profiles, which may not be feasible in production environments
- Relies on deterministic kernel-to-layer mapping that may break with framework updates

## Confidence

- **High confidence**: Architecture fingerprinting through aggregate GPU profiles (100% accuracy on test set)
- **Medium confidence**: Cross-GPU generalization (tested on one additional GPU model)
- **Medium confidence**: Robustness to pruning (tested on one level of pruning)
- **Low confidence**: Real-world attack feasibility (no evaluation in deployed settings)

## Next Checks
