# Learning Logic Specifications for Soft Policy Guidance in POMCP

## Quick Facts
- arXiv ID: 2303.09172
- Source URL: https://arxiv.org/abs/2303.09172
- Reference count: 35
- Primary result: Learned ASP rules from POMCP traces improve performance on larger state spaces and longer horizons while maintaining asymptotic optimality.

## Executive Summary
This paper proposes learning Answer Set Programming (ASP) rules from Partially Observable Markov Decision Process (POMDP) execution traces to guide Monte Carlo tree search in POMCP. The method extracts "good" policies from execution traces, learns logical relations between domain features and actions using Inductive Logic Programming (ILP), and integrates these rules as action priors to bias POMCP exploration. The approach shows improved performance on benchmark domains like rocksample and battery, particularly with larger state spaces or longer planning horizons.

## Method Summary
The method involves three main steps: 1) representing the domain in ASP with user-defined features mapping beliefs to ASP groundings, 2) extracting ILP examples from POMCP execution traces as partial interpretations linking beliefs to executed actions, and 3) learning ASP rules via ILASP that generalize these examples and integrating them into POMCP as action priors. The learned rules bias the Upper Confidence Bound for Trees (UCT) formula by assigning high prior rewards to actions suggested by the rules, reducing the number of simulations needed to find good actions while preserving asymptotic optimality.

## Key Results
- Learned rules improve POMCP performance on rocksample and battery domains, especially with larger state spaces and longer planning horizons
- The approach maintains POMCP's asymptotic optimality while reducing simulation requirements
- Rules are robust to training example quality and quantity, and can be generated efficiently from sub-optimal policies
- Computational overhead of ASP grounding is outweighed by reduced simulation counts

## Why This Works (Mechanism)
### Mechanism 1
- Claim: Learned ASP rules bias Monte Carlo tree search by assigning a high prior reward to promising actions, reducing the number of simulations needed to find good actions.
- Mechanism: For each action grounded by the ASP solver, the UCT formula's value term (V) is increased to the exploration constant c, and the visit count term (N) is set to a fixed high reward value. This creates a "fake" history where many simulations have already succeeded with this action.
- Core assumption: The action-value prior does not affect the asymptotic optimality of POMCP, only its exploration efficiency.
- Evidence anchors:
  - [abstract] "we use ASP statements to guide POMCP exploration and increase performance and scalability in challenging domain instances, e.g., with increased planning horizons"
  - [section] "We introduce a prior in UCT...This is the same as implying that we have already performed N(h) simulations in the current belief, and they achieved a good return value (i.e., an high value of V(h))"
- Break condition: If the learned rules are wrong or biased toward sub-optimal actions, the prior can lead POMCP to converge to worse policies than standard POMCP.

### Mechanism 2
- Claim: ILP learns logical rules that map belief features to actions by generalizing from execution traces of "good" policies.
- Mechanism: The learner extracts partial interpretations from belief-action pairs, where the context is the belief features and the included/excluded sets are the executed/non-executed actions. It then searches for ASP rules that explain these examples.
- Core assumption: The training traces contain "good" policies, so the learned rules are useful.
- Evidence anchors:
  - [section] "we learn logic relations between domain-relevant user-defined features...with the paradigm of ILP under ASP semantics, and we use them to directly advise POMCP simulations"
  - [section] "We make the following assumptions...examples are taken from 'good' traces of execution, i.e., where the policy is nearly optimal"
- Break condition: If the training traces are from poor policies, or if the feature space doesn't capture relevant belief information, the learned rules may not improve or may degrade performance.

### Mechanism 3
- Claim: The modular ASP representation allows efficient grounding of features from particle beliefs and re-use across POMCP nodes.
- Mechanism: Features are computed from particle filters only when nodes are visited. Observable-only features can be re-grounded when the node becomes a root again. The ASP solver is called only when all features are grounded.
- Core assumption: Feature grounding from particles is computationally cheaper than running full simulations.
- Evidence anchors:
  - [section] "We compute the values required to ground ASP features by analyzing all the particles...When we reach a new non-root node, no particle filter is available. However, we still ground features that depend only on the observable part of the state"
- Break condition: If feature grounding becomes expensive (e.g., very large belief spaces or complex features), the overhead may outweigh the benefit of reduced simulations.

## Architecture Onboarding

### Component map:
POMDP domain definition -> Particle filter implementation -> POMCP solver with MCTS/UCT -> Feature map functions -> ASP representation -> ILP learner (ILASP) -> ASP solver (Clingo)

### Critical path:
1. Generate training traces from POMCP on small instances
2. Extract examples (CDPIs) from traces using feature maps
3. Define ILP task and run learner to get ASP rules
4. Integrate ASP rules into POMCP via action priors
5. Validate on larger instances or with fewer particles

### Design tradeoffs:
- More detailed features → more expressive rules but larger search space and longer learning time
- Fewer training examples → faster learning but less robust rules
- Higher prior reward value → more aggressive pruning but risk of missing good actions

### Failure signatures:
- POMCP performance degrades when rules are added → learned rules are wrong or overfit to training data
- Learning takes too long → search space is too large; reduce feature granularity or use more constraints
- No improvement with larger domains → rules don't generalize; check if features capture domain-relevant information

### First 3 experiments:
1. Run POMCP on small battery/rocksample instances, collect traces, learn rules, validate on same size with fewer particles
2. Vary the number of training examples and measure rule coverage/non-covered examples
3. Test rule generalization by scaling grid size (rocksample) or path length (battery) while keeping particles fixed

## Open Questions the Paper Calls Out
1. How does the quality and quantity of execution traces affect the robustness and performance of the learned ASP rules in POMCP?
2. Can the proposed methodology be extended to learn temporal logic specifications for more complex tasks?
3. How can the methodology be adapted to handle non-covered examples in the training set and refine the learned axioms during execution?

## Limitations
- Assumes access to "good" execution traces without specifying how to obtain them without a near-optimal policy
- Feature engineering process is left to expert domain knowledge without systematic guidance
- Computational overhead of ASP grounding and solving at each POMCP node is not thoroughly evaluated

## Confidence

### High: The core mechanism of using ASP rules as action priors in POMCP is well-founded and the asymptotic optimality preservation is theoretically justified.
### Medium: The empirical results showing performance improvements across domains, though the evaluation could benefit from more systematic ablation studies.
### Low: The practical guidance for feature selection and the scalability of the approach to very large domains or complex feature spaces.

## Next Checks
1. **Feature Sensitivity Analysis**: Systematically vary the number and complexity of domain features to quantify their impact on learning time and rule quality.
2. **Trace Quality Robustness**: Evaluate the method using execution traces from progressively worse policies to determine the minimum quality threshold for useful rule learning.
3. **Computational Overhead Measurement**: Instrument the code to measure the exact time spent on ASP grounding and solving versus simulation time savings across different problem scales.
