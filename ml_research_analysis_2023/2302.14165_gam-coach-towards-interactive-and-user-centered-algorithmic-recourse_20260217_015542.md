# GAM Coach: Towards Interactive and User-centered Algorithmic Recourse

## Quick Facts
- arXiv ID: 2302.14165
- Source URL: https://arxiv.org/abs/2302.14165
- Reference count: 40
- Key outcome: Interactive tool enabling personalized algorithmic recourse for GAMs with 41-user study showing improved usability

## Executive Summary
GAM Coach is the first interactive tool enabling end users to generate personalized algorithmic recourse plans for Generalized Additive Models. It adapts integer linear programming to create counterfactual examples while providing an interface for users to specify feature difficulty, acceptable ranges, and the number of features to change. A user study with 41 participants found that GAM Coach is usable and useful, with users preferring personalized recourse plans over generic ones. Participants successfully discovered satisfactory plans by iteratively adjusting preferences and exploring hypothetical inputs, with an average of 2.11 features changed per chosen plan.

## Method Summary
The system formulates counterfactual explanation generation as an integer linear program for GAMs, using binary variables to indicate active feature bins and minimizing distance costs while ensuring counterfactual constraints. It supports continuous and categorical features with pairwise interactions. The interface provides progressive disclosure of feature details, interactive sliders for hypothetical values, and difficulty configuration through multiplier assignments. Precomputation of distance costs and local score gains enables real-time generation, while WebAssembly-based GLPK.js solves the ILP. The approach generates diverse and sparse counterfactual examples that flip model predictions while reflecting user-specified preferences.

## Key Results
- 41 participants successfully generated satisfactory recourse plans using GAM Coach
- Users preferred personalized plans over generic templates
- Average of 2.11 features changed per chosen plan
- Users iteratively fine-tuned preferences to discover actionable plans

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Integer Linear Programming (ILP) formulation enables real-time generation of counterfactual examples for GAMs by converting feature changes into discrete optimization variables
- Mechanism: ILP expresses counterfactual constraints as linear inequalities over binary indicator variables representing active feature bins, allowing efficient minimal-change solutions
- Core assumption: Feature space can be discretized into finite bins with pre-computed score and distance costs
- Evidence anchors: [section] "We express the GAM Coach recourse generation as an integer linear program: min distance (2a) s.t. distance=..." [abstract] "We present GAM Coach, a novel open-source system that adapts integer linear programming to generate customizable counterfactual explanations for Generalized Additive Models (GAMs)"
- Break condition: If feature interactions cannot be bounded or bins grow exponentially, ILP becomes intractable

### Mechanism 2
- Claim: Progressive disclosure interface design enables non-expert users to understand and control complex ML decision-making through simple interactions
- Mechanism: Interface groups features into collapsed cards, revealing details only when users interact to reduce cognitive load
- Core assumption: Users can learn concepts through interaction rather than upfront instruction
- Evidence anchors: [section] "To prevent overwhelming users with too much information (G4), all cards are collapsed by default—only displaying the feature name and feature values" [section] "Users can drag the diamond-shaped thumb on a slider below the chart to experiment with hypothetical values"
- Break condition: If users require immediate understanding of all features simultaneously, design fails educational goals

### Mechanism 3
- Claim: Customizable distance functions reflecting user-specified feature difficulties enable truly actionable recourse plans
- Mechanism: Users assign difficulty multipliers to features, which reweight pre-computed distance costs in ILP objective
- Core assumption: Users can accurately assess their ability to change different features
- Evidence anchors: [section] "Users can click the smiley button on any Feature Card and then select a suitable difficulty option on the pop-up window" [section] "GAM Coach multiplies the distance costs of all bins in that feature with a constant multiplier"
- Break condition: If difficulty assessments conflict with practical constraints, generated plans may still be non-actionable

## Foundational Learning

- Concept: Generalized Additive Models (GAMs) and Explainable Boosting Machines (EBMs)
  - Why needed here: GAMs provide transparent, additive structure making real-time counterfactual generation possible through linear optimization
  - Quick check question: Why can't we use black-box models like neural networks for real-time counterfactual generation in this interface?

- Concept: Integer Linear Programming formulation for optimization problems
  - Why needed here: Understanding how to express optimization objectives and constraints as linear functions is crucial for implementing the counterfactual generation algorithm
  - Quick check question: How would you modify the ILP to generate counterfactual examples that change at most 3 features instead of the default 4?

- Concept: Progressive disclosure and details-on-demand interface patterns
  - Why needed here: These design patterns are essential for making complex ML concepts accessible to non-expert users without overwhelming them
  - Quick check question: What would happen to user comprehension if all feature details were visible by default instead of progressively revealed?

## Architecture Onboarding

- Component map: Frontend HTML/CSS/JavaScript with D3.js visualizations -> GLPK.js WebAssembly module for ILP solving -> Pre-computed EBM model parameters and feature statistics
- Critical path: User interaction → Feature preference configuration → ILP parameter update → WebAssembly solver execution → Plan generation → Interface update
- Design tradeoffs: Speed vs. optimality (pre-computing distances trades some optimality for sub-second response), Complexity vs. usability (progressive disclosure adds implementation complexity but improves experience), Generality vs. performance (model-agnostic interface requires more pre-computation)
- Failure signatures: Solver timeouts indicate model complexity exceeds implementation limits, UI freezes suggest WebAssembly module issues, Empty plan sets indicate conflicting constraints
- First 3 experiments: 1) Test ILP solver performance on different dataset sizes with varying interaction terms, 2) Measure user comprehension with progressive disclosure vs. all-details-visible interface, 3) Validate that difficulty multipliers actually bias plan generation toward easier-to-change features

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the perceived actionability of recourse plans vary based on the end user's familiarity with machine learning concepts?
- Basis in paper: [explicit] Participants self-reported average ML familiarity score of 2.7 on 5-point Likert scale, some found tool complex for users with less loan knowledge
- Why unresolved: Study did not analyze correlation between ML familiarity and satisfaction with recourse plans or ability to generate actionable plans
- What evidence would resolve it: Analyzing relationship between ML familiarity scores and recourse plan actionability ratings, or conducting study with varying expertise levels

### Open Question 2
- Question: How do users' recourse preferences evolve over multiple iterations of using an interactive recourse tool like GAM Coach?
- Basis in paper: [inferred] Participants iteratively fine-tuned preferences and 28% who configured difficulty preferences immediately altered difficulty levels on same features
- Why unresolved: Study did not track how preferences changed over time or if users learned to configure preferences more effectively with repeated use
- What evidence would resolve it: Conducting longitudinal study tracking preference configurations and satisfaction over extended period

### Open Question 3
- Question: How does the inclusion of counterfactual explanations impact users' trust in machine learning models and their willingness to follow recourse recommendations?
- Basis in paper: [explicit] Discusses importance of transparency and mentions users can discover counterintuitive patterns; users more likely to choose plans reflecting configured preferences
- Why unresolved: Study did not measure users' trust in model or likelihood to follow suggested recourse plans
- What evidence would resolve it: Including trust and compliance measures in future studies with trust ratings and likelihood-to-follow assessments

## Limitations
- Current system only supports GAMs and EBMs, limiting applicability to broader range of ML models
- User study based on self-reported satisfaction rather than measuring actual real-world outcomes
- Integer linear programming approach may not scale to high-dimensional feature spaces or complex interaction structures

## Confidence
- High Confidence: Integer linear programming formulation for GAM counterfactual generation is technically sound and well-specified
- Medium Confidence: User study results showing improved usability and preference for personalized recourse plans are promising but based on relatively small sample
- Low Confidence: Claims about real-world actionability of generated plans cannot be fully validated from study alone

## Next Checks
1. Conduct external validation study with larger, more diverse participant pool recruited outside academic settings
2. Track cohort of users over 3-6 months to measure actual implementation of suggested recourse plans and achievement of desired outcomes
3. Implement and evaluate proposed model-agnostic interface with black-box models to assess real-time performance and plan quality preservation
