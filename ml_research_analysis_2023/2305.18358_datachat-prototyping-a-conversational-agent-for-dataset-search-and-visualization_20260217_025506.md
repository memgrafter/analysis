# DataChat: Prototyping a Conversational Agent for Dataset Search and Visualization

## Quick Facts
- arXiv ID: 2305.18358
- Source URL: https://arxiv.org/abs/2305.18358
- Reference count: 0
- Primary result: 61% overall success rate for conversational dataset search queries, with variation by query type (education 83%, data management 74%, funding 26%)

## Executive Summary
DataChat is a prototype chatbot system that leverages a scholarly knowledge graph and large language model to enable conversational dataset search and exploration. Built on ICPSR's dataset metadata, the system converts natural language queries into database queries using GPT-3.5-turbo and presents results through both textual responses and interactive network visualizations. The approach aims to address the challenge that users need significant context and expertise to effectively search for relevant datasets. By providing natural language interaction and relationship visualization, DataChat seeks to improve dataset discoverability and reuse through enhanced connectivity, efficiency, visibility, and interactivity.

## Method Summary
The system uses a three-layer architecture: a Streamlit front-end for user interaction, GPT-3.5-turbo API for natural language processing and Cypher query generation, and a Neo4j graph database containing the ICPSR-SKG. The knowledge graph encodes 1,642 datasets from 2017-2022 with attributes like id, name, date, and relationships to publications, funders, owners, series, locations, and terms. User queries are processed by the LLM to generate Cypher queries, which are executed against the database. Results are displayed in two formats: a DataChatBot tab showing textual responses and the generated Cypher query, and a DataChatViz tab providing interactive network visualizations using the streamlit-agraph package.

## Key Results
- Overall 61% success rate across 105 evaluation queries
- Education-related queries achieved 83% success rate
- Data management-related queries achieved 74% success rate
- Funding-related queries had the lowest success rate at 26%

## Why This Works (Mechanism)

### Mechanism 1
GPT-3.5-turbo successfully converts natural language dataset queries into valid Cypher graph queries, enabling conversational dataset search. The LLM acts as a semantic bridge between user intent and structured query language by mapping linguistic patterns to Cypher syntax patterns.

### Mechanism 2
The scholarly knowledge graph structure enables discovery of implicit dataset relationships that traditional search indexes cannot expose. By encoding entities as nodes and relationships as edges, the graph database can traverse multi-hop connections to surface contextually relevant datasets.

### Mechanism 3
Network visualization enhances user understanding of dataset relationships and improves discovery effectiveness. Interactive visualizations provide cognitive scaffolding that helps users comprehend complex relationship structures that would be difficult to parse from textual results alone.

## Foundational Learning

- **Graph database fundamentals (nodes, edges, properties, Cypher query language)**: Understanding how the SKG stores and retrieves data is essential for debugging query failures and optimizing the system. *Quick check: What Cypher pattern would retrieve all datasets funded by a specific organization?*

- **Large language model prompting techniques and limitations**: The LLM is the critical translation layer between users and the database; understanding its constraints is vital for designing effective prompts and handling failures. *Quick check: What happens when an LLM encounters a query pattern it hasn't seen during training?*

- **Information retrieval evaluation metrics and stakeholder analysis**: The 61% success rate evaluation requires understanding what constitutes "passing" queries and how different stakeholder needs affect performance. *Quick check: Why might funding-related queries have lower success rates than education-related queries?*

## Architecture Onboarding

- **Component map**: Streamlit front-end → GPT-3.5-turbo API → Neo4j ICPSR-SKG database → Streamlit visualization (streamlit-agraph)
- **Critical path**: User query → LLM prompt generation → Cypher query output → Database execution → Result formatting → UI display
- **Design tradeoffs**: LLM flexibility vs. query reliability, visualization richness vs. performance, natural language expressiveness vs. database complexity
- **Failure signatures**: LLM produces invalid Cypher syntax, database returns empty results, visualization fails to render, system timeout on complex queries
- **First 3 experiments**:
  1. Test simple queries (e.g., "List datasets about education") to verify basic LLM-to-Cypher translation works
  2. Test relationship queries (e.g., "Datasets funded by NIH") to verify graph traversal capabilities
  3. Test visualization scaling with 10, 50, and 100 dataset results to identify performance thresholds

## Open Questions the Paper Calls Out

### Open Question 1
What specific improvements in dataset discoverability and reusability could be achieved by expanding the ICPSR-SKG to include more detailed information about funders, research fields, and publication topics? The authors state they plan to add these details in future work, but don't provide analysis on how this would impact search effectiveness.

### Open Question 2
Why does the DataChat system perform significantly worse for funding-related queries compared to education-related and data management-related queries? The evaluation shows a 26% pass rate for funding queries versus 83% and 74% for others, with only speculation about complexity and ambiguity of funding agencies' interests.

### Open Question 3
How does the scalability of the DataChat visualization interface impact user experience as the number of datasets in focus increases beyond three to five? The authors mention plans to enhance scalability but provide no data on user experience or system performance with larger numbers of datasets.

## Limitations

- Knowledge graph completeness issues, particularly for funding relationships, may be conflated with LLM query generation failures
- Visualization system has apparent scalability constraints, potentially limiting practical use with larger dataset collections
- Generalizability to other domains is unproven, with the approach tightly coupled to ICPSR's specific schema and dataset collection

## Confidence

**High Confidence (3-4)**:
- LLM-to-Cypher conversion works for basic dataset queries
- Knowledge graph enables relationship-based dataset discovery
- Conversational interface provides novel approach to dataset search

**Medium Confidence (2)**:
- 61% success rate accurately represents usability
- Visualization component meaningfully improves comprehension
- System addresses genuine user needs for dataset exploration

**Low Confidence (1)**:
- Funding query failures are primarily technical rather than data-coverage issues
- Approach generalizes to other domains without modification
- System scales effectively to larger dataset collections

## Next Checks

1. **Data vs. Interface Failure Analysis**: Execute the same queries directly in Neo4j (bypassing the LLM) to determine whether the 26% funding-related query failure rate stems from data gaps or query generation issues.

2. **Visualization Performance Benchmarking**: Systematically test the streamlit-agraph visualization with increasing dataset counts (10, 50, 100, 500) while measuring render time, memory usage, and user task completion rates.

3. **Cross-Domain Transferability Test**: Replicate the DataChat approach with a different dataset repository (e.g., Dataverse, Zenodo) using their API/metadata schemas to compare success rates and identify consistently challenging schema elements.
