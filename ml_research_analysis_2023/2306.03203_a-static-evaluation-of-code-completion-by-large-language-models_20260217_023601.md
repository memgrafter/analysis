# A Static Evaluation of Code Completion by Large Language Models

## Quick Facts
- arXiv ID: 2306.03203
- Source URL: https://arxiv.org/abs/2306.03203
- Reference count: 40
- We propose a static evaluation framework for code completion models, using AST parsing and Pyflakes to detect errors without execution.

## Executive Summary
This paper introduces a static evaluation framework for code completion models that uses AST parsing and Pyflakes to detect errors without execution. The framework analyzes 1 million Python function completions to reveal error patterns across different model sizes, sampling temperatures, and context conditions. The study finds that higher temperatures consistently increase error rates, while larger models show mixed results in reducing different error types. Context errors significantly amplify generation errors, though most generation errors occur even with correct context. The framework provides an efficient alternative to execution-based evaluation, enabling large-scale analysis of real-world code.

## Method Summary
The authors generate Python function completions using CodeGen models (350M to 16B parameters) with nucleus sampling, varying temperature and model size. They collect code context from public GitHub repositories and mask function bodies as ground truth. The static evaluation pipeline parses context and completions via AST, filters out unparsable cases, and runs Pyflakes to detect static errors. Error rates are compared across model sizes, temperatures, and context error conditions, with analysis focusing on error types like undefined names, unused variables, and syntax issues.

## Key Results
- Undefined Name and Unused Variable are the most common static errors in code completions
- Higher sampling temperatures consistently increase error rates across all error types
- Context errors significantly increase generation errors, with amplification factors of 7-200x depending on error type
- Larger models reduce some error types but not others, with no consistent improvement for undefined names

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Static analysis catches syntax and semantic errors without running code
- Mechanism: AST parsing transforms source code into tree structures; Pyflakes analyzes these trees for errors like undefined names or unused variables
- Core assumption: AST parsing is deterministic and Pyflakes covers common Python error patterns
- Evidence anchors:
  - [abstract]: "We propose a static evaluation framework for code completion models, using AST parsing and Pyflakes to detect errors without execution"
  - [section 4.1]: "We first check c for any errors in the input that need to be excluded, and then do another pass on the full code (c, x)"

### Mechanism 2
- Claim: Model error patterns correlate with sampling temperature
- Mechanism: Higher temperature increases diversity of generated tokens, leading to more syntactically and semantically incorrect code
- Core assumption: Temperature directly influences generation confidence and error likelihood
- Evidence anchors:
  - [section 5.4]: "Across sampling temperatures, we observe in every column that more errors are generated under higher temperatures"
  - [table 3]: Error rates increase consistently across all error types as temperature rises

### Mechanism 3
- Claim: Context errors amplify generation errors through in-context learning
- Mechanism: Large language models learn patterns from context; if context contains errors, models replicate similar errors in completion
- Core assumption: Models treat context as implicit examples to follow
- Evidence anchors:
  - [section 5.5]: "If the model observes errors in context, it is more likely to produce the same type of errors in generation"
  - [table 4]: Error amplification factors ranging from 7-200x when context contains matching errors

## Foundational Learning

- Concept: Abstract Syntax Trees (AST)
  - Why needed here: AST parsing is the first step in static analysis pipeline; understanding tree structure is essential for error detection
  - Quick check question: Can you explain why "print 'hello'" would fail AST parsing in Python 3?

- Concept: Static vs dynamic analysis
  - Why needed here: Static analysis avoids execution cost while catching compile-time errors; critical for large-scale evaluation
  - Quick check question: What's the key difference between how Pyflakes and a debugger would handle undefined variables?

- Concept: Temperature sampling in language models
  - Why needed here: Temperature controls randomness in generation; understanding its impact is crucial for interpreting error patterns
  - Quick check question: If you set temperature to 0.0, what type of generation behavior would you expect?

## Architecture Onboarding

- Component map: Code context → AST parser → Error filter → Pyflakes analyzer → Error aggregator
- Critical path: Context validation → AST parsing → Static analysis → Error reporting
- Design tradeoffs: Execution-based evaluation is more accurate but expensive; static analysis is faster but misses runtime errors
- Failure signatures: Unparseable context (>0.42%), EOF errors from max length limit (7-8%), interpreter version mismatches
- First 3 experiments:
  1. Run static analysis on a single function with known syntax error to verify pipeline
  2. Generate completions at different temperatures and measure error rate changes
  3. Create context with intentional errors and verify generation amplifies them

## Open Questions the Paper Calls Out

### Open Question 1
- Question: What specific mechanisms could be implemented to help language models correctly infer the intended Python interpreter version (2 vs 3) from limited context?
- Basis in paper: [explicit] The paper identifies interpreter version mismatch as a major source of AST errors, noting that Python2-style print statements cause "Print Missing Parentheses" errors in Python3.
- Why unresolved: The paper mentions this as an interesting future direction but doesn't propose specific solutions for how models could detect or adapt to different Python versions.
- What evidence would resolve it: A study comparing different techniques (e.g., context-aware version detection, version-specific model fine-tuning, or explicit version prompts) and measuring their effectiveness in reducing version-related syntax errors.

### Open Question 2
- Question: How does the error amplification effect (context errors leading to generation errors) vary across different programming languages and error types?
- Basis in paper: [explicit] The paper shows that errors in context significantly increase generation errors across various types, with amplification factors ranging from 7-200x depending on the error type.
- Why unresolved: The analysis is limited to Python code and Pyflakes error types; the generalizability to other languages and error detection tools remains unexplored.
- What evidence would resolve it: Comparative studies using static analysis tools for other languages (e.g., ESLint for JavaScript, RuboCop for Ruby) to measure error amplification patterns and identify language-specific versus universal phenomena.

### Open Question 3
- Question: What is the relationship between the length of generated code and the frequency of undefined names, particularly for functions versus variables?
- Basis in paper: [inferred] The paper notes that larger models generate more undefined functions but fewer undefined variables, and speculates that undefined functions could potentially be resolved if longer code generation were allowed.
- Why unresolved: The paper only examines function completions limited to 256 tokens and doesn't explore how error patterns change with generation length or different code structures.
- What evidence would resolve it: Experiments varying maximum generation length and measuring how undefined function versus undefined variable errors scale, potentially revealing whether longer context allows models to resolve more function references.

## Limitations
- Static analysis cannot capture runtime errors, logical bugs, or complex type-related issues that only manifest during execution
- Results are based on Python code from a specific time period (April-August 2022) and permissive licenses, limiting generalizability
- Exact dataset filtering criteria and implementation details remain underspecified, making exact reproduction challenging

## Confidence
- **High Confidence**: The correlation between sampling temperature and error rates is well-supported by consistent patterns across all error types and models
- **Medium Confidence**: The model size effects show mixed results, with some error types decreasing while others remain constant
- **Low Confidence**: The claim that static analysis provides "similar findings" to execution-based evaluation lacks direct validation

## Next Checks
1. **Runtime Validation**: Execute a stratified sample of completions (both error-free and error-containing) in a controlled Python environment to measure false positive/negative rates of the static analysis framework and identify runtime errors that static analysis misses

2. **Cross-Validation with Alternative Static Analyzers**: Run the same dataset through alternative Python static analysis tools (e.g., Pylint, mypy) to verify consistency of error detection and identify patterns that Pyflakes may miss or misclassify

3. **Temporal Generalization**: Generate and analyze completions from GitHub repositories sampled from a different time period (e.g., 2023) to assess whether the observed error patterns and temperature effects hold for newer codebases and evolving Python language features
