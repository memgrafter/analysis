# Translating Natural Language to Planning Goals with Large-Language Models

## Quick Facts
- arXiv ID: 2302.05128
- Source URL: https://arxiv.org/abs/2302.05128
- Reference count: 40
- One-line primary result: GPT-3.5 variants achieve near-perfect translation for fully-specified goals but struggle with numerical reasoning and spatial inference in partial specifications.

## Executive Summary
This paper investigates whether large language models can translate natural language goals into PDDL (Planning Domain Definition Language) specifications. Using GPT-3.5 variants, the authors test translation across two domains—Blocksworld and ALFRED—with tasks ranging from explicit stack constructions to ambiguous, commonsense-rich instructions. The results show that LLMs achieve near-perfect translation for fully-specified goals but struggle with numerical reasoning and spatial inference in partial specifications. Performance is sensitive to prompt examples, with larger or better-matched examples improving results.

## Method Summary
The study uses GPT-3.5 variants (code-davinci-002 for Blocksworld, text-davinci-003 for ALFRED-L) to translate natural language instructions into PDDL goals. The method involves n-shot prompting with predefined PDDL domains and natural language instructions, evaluating success rates under loose and strict criteria. Two domains are tested: Blocksworld (colored blocks stacking) and ALFRED-L (household objects/receptacles), with multiple task types from explicit specifications to ambiguous instructions requiring inference.

## Key Results
- LLMs achieve near-perfect translation for fully-specified goals in Blocksworld domain
- Performance drops significantly for tasks requiring numerical reasoning (50-60% success on NBlocks and KStacks tasks)
- Domain understanding is generally strong, but goal inference falters on tasks requiring counting or hierarchical reasoning

## Why This Works (Mechanism)

### Mechanism 1
- Claim: LLMs achieve near-perfect translation for fully-specified goals due to strong linguistic competence and ability to parse natural language instructions into structured PDDL goals.
- Mechanism: The LLM leverages its extensive training on natural language data to correctly identify entities, predicates, and relationships described in the instruction, then maps these to PDDL syntax using provided domain information.
- Core assumption: The natural language instruction unambiguously specifies the goal configuration without requiring inference or reasoning beyond parsing.
- Evidence anchors: [abstract] "LLMs achieve near-perfect translation for fully-specified goals"; [section] "For ExplicitStacks, goal translation performance was sustained even when the number of blocks in the domain and desired number of stacks were varied"; [corpus] Weak - no direct evidence about why linguistic competence works, only that it exists.
- Break condition: When instructions require numerical reasoning, spatial inference, or commonsense knowledge to fill in missing details.

### Mechanism 2
- Claim: LLMs use commonsense knowledge to furnish missing details from under-specified goals.
- Mechanism: The model draws on learned associations between objects and their typical relationships (e.g., "set a table for two" implies correct tableware) to generate complete PDDL specifications even when instructions are ambiguous.
- Core assumption: The required commonsense knowledge is present in the LLM's training data and can be retrieved through the prompt.
- Evidence anchors: [abstract] "LLMs are able to leverage commonsense knowledge and reasoning to furnish missing details from under-specified goals"; [section] "the LLM was able to apply commonsense reasoning to 'fill the gaps' in the natural language goal specification"; [corpus] Weak - no direct evidence about what commonsense knowledge exists or how it's retrieved.
- Break condition: When tasks require nontrivial numerical reasoning or hierarchical reasoning that exceeds the model's learned associations.

### Mechanism 3
- Claim: Performance is sensitive to prompt examples, with larger or better-matched examples improving results.
- Mechanism: Few-shot prompting allows the model to learn the pattern of translating natural language to PDDL by providing concrete examples of the mapping between instruction types and goal structures.
- Core assumption: The model can generalize from provided examples to handle variations in the same task category.
- Evidence anchors: [section] "Performance is sensitive to the prompts used, with larger or better-matched examples improving results"; [section] "Table III shows that the number of blocks used on the one-shot example significantly affects the performance on target tasks and larger examples generally led to better performance"; [corpus] Weak - no direct evidence about why example size matters or how generalization occurs.
- Break condition: When the test case requires generalization beyond the patterns shown in examples.

## Foundational Learning

- Concept: Natural language understanding and parsing
  - Why needed here: The LLM must correctly identify entities, relationships, and predicates from natural language instructions to translate them into PDDL
  - Quick check question: Given "Put a red block on top of a blue block", what are the entities and relationships the model needs to identify?

- Concept: PDDL syntax and domain structure
  - Why needed here: The model must generate syntactically correct PDDL goals that conform to the specified domain's predicates, objects, and structure
  - Quick check question: If a domain defines predicates (on ?x ?y) and (clear ?x), what PDDL goal would represent "Block A is on Block B and nothing is on Block A"?

- Concept: Commonsense knowledge and world modeling
  - Why needed here: For under-specified goals, the model must infer missing details based on typical object relationships and configurations
  - Quick check question: If asked to "set a table for two", what objects and relationships should the model infer beyond what's explicitly stated?

## Architecture Onboarding

- Component map: Natural language instruction → LLM processing → PDDL goal generation → Planner execution → Action sequence
- Critical path: Natural language instruction → LLM processing → PDDL goal generation → Planner execution → Action sequence
- Design tradeoffs: Using LLMs for translation leverages their linguistic competence but introduces sensitivity to prompt design and limitations in reasoning. Using classical planners for planning leverages their efficiency but requires accurate goal translation.
- Failure signatures: PDDL syntax errors, physically impossible configurations, incorrect object associations, failure to count or perform numerical reasoning, over-reliance on example patterns without proper generalization.
- First 3 experiments:
  1. Test translation of fully-specified goals in Blocksworld with varying numbers of blocks to verify near-perfect performance baseline
  2. Test translation of ambiguous instructions requiring commonsense knowledge (e.g., "set a table for two") to verify commonsense reasoning ability
  3. Test sensitivity to example prompts by varying the number and content of examples in few-shot settings to identify optimal prompt design

## Open Questions the Paper Calls Out

### Open Question 1
- Question: Can the LLM consistently generalize from a single example when the example uses a different number of blocks than the test case?
- Basis in paper: [explicit] The paper shows that performance on NBlocks and KStacks tasks was only 50-60%, with the LLM often blindly copying the prompt example (e.g., outputting 2 stacks when the goal specified 4). Table III shows that the number of blocks in the one-shot example significantly affects performance on target tasks, with larger examples generally leading to better performance.
- Why unresolved: While the paper demonstrates sensitivity to example size, it does not systematically test whether the LLM can generalize across different block counts when only given one example. The paper only shows that larger examples help, but does not determine the limits of this generalization.
- What evidence would resolve it: Experiments testing performance across a range of block counts using a single example with a different block count than the test case, to see if the LLM can correctly infer the desired configuration.

### Open Question 2
- Question: Does the LLM's poor performance on tasks requiring numerical reasoning (e.g., NBlocks, KStacks) stem from a fundamental inability to count, or from difficulty in mapping the counted quantity to the correct PDDL syntax?
- Basis in paper: [explicit] The paper reports that performance on NBlocks and KStacks was only 50-60%, and that the LLM tended to blindly copy the prompt example. The subtask analysis shows that goal inference scores fell when translation failed, suggesting the LLM was unable to integrate information to arrive at a suitable goal.
- Why unresolved: The subtask analysis attempted to distinguish between domain understanding and goal inference failures, but the tests were imperfect due to the constraints of working with black-box LLMs. It is unclear whether the LLM understands the numerical concept but cannot translate it, or if it cannot understand the numerical concept at all.
- What evidence would resolve it: Tests where the LLM is asked to generate the goal in a different syntax (e.g., Python lists) to see if it can correctly represent the numerical concept, even if it cannot generate the correct PDDL.

### Open Question 3
- Question: Can the LLM be prompted to actively validate the achievability of a natural language instruction before attempting translation?
- Basis in paper: [explicit] The paper notes that the LLM tended to presume that given instructions were valid, and would create non-existent objects or add impossible predicates (e.g., "sliced plate") when asked to translate. When explicitly asked to "ask a question if it is not achievable," the LLM would respond correctly that oranges were not present but not that the plate was not sliceable, showing inconsistent validation behavior.
- Why unresolved: The paper only briefly tested this by adding a single prompt, without exploring different prompt structures or validation strategies. It is unclear whether the LLM can be reliably prompted to validate instructions, or what the limitations of such prompting are.
- What evidence would resolve it: Systematic testing of different prompt structures and validation strategies to determine if the LLM can be consistently prompted to validate instructions, and under what conditions it succeeds or fails.

## Limitations
- Limited generalization to complex or unseen configurations beyond prompt examples
- No validation of whether generated PDDL goals are physically achievable or semantically meaningful
- Unclear mechanisms behind sensitivity to prompt examples and limitations in numerical reasoning

## Confidence
- Medium confidence for claims about LLM performance on fully-specified goals
- Low confidence for claims about commonsense reasoning capabilities
- Medium confidence for claims about sensitivity to prompt examples

## Next Checks
1. Test the model with semantically equivalent instructions expressed differently to verify genuine understanding versus pattern matching
2. Evaluate performance on task types not represented in the prompt examples to test whether the model can generalize the translation pattern
3. Implement a post-hoc check that validates generated PDDL goals against physical constraints to determine whether syntactic correctness translates to meaningful, executable goals
