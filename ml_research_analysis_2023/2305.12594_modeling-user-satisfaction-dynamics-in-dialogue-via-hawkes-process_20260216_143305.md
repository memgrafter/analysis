# Modeling User Satisfaction Dynamics in Dialogue via Hawkes Process

## Quick Facts
- arXiv ID: 2305.12594
- Source URL: https://arxiv.org/abs/2305.12594
- Reference count: 22
- Key outcome: F1 score improvements of 9.6%, 4.3%, and 6.9% on MultiWOZ, SGD, and ReDial, respectively, compared to state-of-the-art baseline estimators

## Executive Summary
This paper introduces ASAP (sAtisfaction eStimation via HAwkes Process), a novel approach for user satisfaction estimation in dialogue systems. The method treats user satisfaction scores across dialogue turns as an event sequence and employs a discrete Hawkes process to model the temporal dynamics of satisfaction states. The proposed approach integrates a Transformer-based Hawkes process module with a hierarchical Transformer architecture, achieving substantial improvements over existing baselines on four benchmark dialogue datasets.

## Method Summary
The method combines a base satisfaction estimator with a Hawkes process integration module. The base estimator uses a two-level Transformer architecture: a token-level BERT encoder processes individual (response, utterance) pairs, and a turn-level Transformer encoder captures cross-turn dependencies. The Hawkes process module employs a score-level encoder to model satisfaction dynamics, where past satisfaction events influence future satisfaction probabilities through an intensity function. The model is trained with cross-entropy loss on satisfaction estimation, optionally with user action recognition as an auxiliary task.

## Key Results
- Achieved F1 score improvements of 9.6% on MultiWOZ, 4.3% on SGD, and 6.9% on ReDial in single-task learning
- Outperformed state-of-the-art baseline estimators on all four benchmark datasets
- Demonstrated effectiveness of modeling satisfaction dynamics through Hawkes process integration

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Modeling user satisfaction as a Hawkes process captures the "self-exciting" dynamics where previous satisfaction states influence future states.
- Mechanism: The model treats each turn's satisfaction score as an event in a sequence and uses a Transformer-based Hawkes process to model how past satisfaction events excite (influence) future ones through an intensity function.
- Core assumption: User satisfaction at turn t depends not only on the current dialogue context but also on the history of satisfaction scores across previous turns.

### Mechanism 2
- Claim: The discrete version of Hawkes process adapts continuous-time intensity functions to the turn-based nature of dialogue.
- Mechanism: The model constrains the total intensity λ(t) to always equal 1 and decomposes it into K components (one per satisfaction class) representing probabilities, allowing discrete-time prediction without predicting "when" the next event happens.

### Mechanism 3
- Claim: The two-level architecture (token-level + turn-level encoder) captures both local and global dialogue context before applying satisfaction dynamics modeling.
- Mechanism: Token-level BERT encoder produces semantic representations for each (response, utterance) pair, then the turn-level Transformer encoder captures cross-turn dependencies, providing contextual representations ct that feed into the Hawkes process module.

## Foundational Learning

- Concept: Hawkes Process (self-exciting point processes)
  - Why needed here: Provides the mathematical framework for modeling how past satisfaction events influence future satisfaction probabilities
  - Quick check question: In a Hawkes process, if an event of type k occurs at time t, how does this typically affect the intensity function for future events?

- Concept: Transformer architecture and attention mechanisms
  - Why needed here: Enables the model to capture long-range dependencies across dialogue turns and to implement the discrete Hawkes process in a differentiable way
  - Quick check question: What is the key difference between the attention mechanism used in the turn-level encoder versus the score-level encoder?

- Concept: Multi-task learning and auxiliary objectives
  - Why needed here: User action recognition (UAR) serves as an auxiliary task that provides additional training signal to improve the satisfaction estimator
  - Quick check question: Why might adding UAR as an auxiliary task help the satisfaction estimator, even though the main focus is on modeling satisfaction dynamics?

## Architecture Onboarding

- Component map: Dialogue context -> token-level BERT -> turn-level Transformer -> MLP(ct) + MLP(xt) -> softplus -> intensity function -> satisfaction prediction

- Critical path: Dialogue context → token-level BERT → turn-level Transformer → MLP(ct) + MLP(xt) → softplus → intensity function → satisfaction prediction

- Design tradeoffs:
  - Using Transformer vs. RNN for Hawkes process: Transformers provide better handling of long-range dependencies but increase parameter count
  - Discrete vs. continuous Hawkes: Discrete version simplifies the problem but loses timing information
  - Single-task vs. multi-task: Multi-task can improve performance but requires additional labeled data

- Failure signatures:
  - Performance plateaus or degrades when increasing N (layers in score-level encoder): Indicates overfitting or optimization difficulties
  - Satisfaction sequence contributes little to intensity function: Suggests the Hawkes process module isn't learning meaningful dynamics
  - Large gap between base estimator and full model: Indicates the Hawkes integration is working as intended

- First 3 experiments:
  1. Ablation study: Compare base estimator vs. ASAP on a small dataset to verify Hawkes process contribution
  2. Hyperparameter sweep: Test different values of N (layers in score-level encoder) on validation set
  3. Single-task vs. multi-task comparison: Train with and without UAR auxiliary task to measure performance impact

## Limitations
- No ablation studies isolating the contribution of the Hawkes process versus the hierarchical Transformer architecture
- Datasets are primarily task-oriented dialogues with limited representation of open-domain dialogues
- No statistical significance testing reported for performance differences between ASAP and baseline models

## Confidence
- Confidence Level: Low for claimed performance improvements due to lack of ablation studies and statistical significance testing
- Confidence Level: Medium for the theoretical framework of discrete Hawkes process formulation
- Confidence Level: Medium for the multi-task learning component's effectiveness

## Next Checks
1. **Ablation Study Replication**: Re-run experiments comparing three variants - (a) base hierarchical Transformer without Hawkes process, (b) same architecture with continuous Hawkes process, and (c) the proposed discrete Hawkes process.

2. **Statistical Significance Testing**: Apply paired t-tests or bootstrap confidence intervals to the F1 scores across multiple runs to determine whether the reported improvements are statistically significant.

3. **Cross-Dataset Generalization Test**: Evaluate ASAP on a dataset with substantially different dialogue characteristics (e.g., non-task-oriented social conversations) to assess generalizability beyond the task-oriented domain.
