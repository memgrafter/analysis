# Optimizing L1 cache for embedded systems through grammatical evolution

## Quick Facts
- arXiv ID: 2303.03338
- Source URL: https://arxiv.org/abs/2303.03338
- Reference count: 40
- One-line primary result: GE-based cache optimization achieves 62% average improvement vs baseline with 94% runtime reduction

## Executive Summary
This paper proposes a Grammatical Evolution (GE) framework to optimize L1 cache configurations for embedded systems, focusing on 11 parameters for both instruction and data caches. The approach leverages a BNF grammar to generate Dinero IV simulator calls and caches evaluated configurations to reduce runtime. Tested on the Mediabench suite, the method achieves significant performance and energy improvements while reducing optimization time by 94% compared to non-storing implementations.

## Method Summary
The framework optimizes L1 cache configurations using Grammatical Evolution, which evolves genotypes decoded via a BNF grammar into Dinero IV simulator parameter strings. The optimization considers 11 cache parameters (size, line size, associativity, replacement policy, prefetch algorithm, write policy) for both instruction and data caches. Fitness combines normalized execution time and energy consumption, evaluated using pre-characterized Cacti data and off-line generated traces. A hash map caches evaluated configurations to avoid redundant simulator calls.

## Key Results
- Optimized cache configurations achieve 62% average improvement versus real-world baseline
- Runtime reduction of 94% compared to non-storing GE implementation
- Successful optimization across Mediabench multimedia benchmarks (JPEG, MPEG, GSM, Pegwit, EPIC, ADPCM)

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Grammatical Evolution reduces optimization runtime by 94% versus a non-storing implementation through efficient caching of evaluated cache configurations.
- Mechanism: GE maintains a hash map of previously evaluated cache configurations. When a candidate solution is decoded into a phenotype, the framework first checks if that configuration has been evaluated before. If so, it retrieves the cached fitness value instead of re-running the slow Dinero IV simulation.
- Core assumption: Cache configurations are hashed deterministically from their phenotype strings, and hash collisions are negligible or handled.
- Evidence anchors:
  - [abstract]: "Experimental results for the Mediabench suite show that our proposal is able to find cache configurations that obtain an average improvement of 62% versus a real world baseline configuration."
  - [section]: "The reduced optimization runtimes are caused by two factors... (2) given that our algorithm recalls the evaluation of each individual, the previously evaluated configurations are not sent to the external simulator, but read from the GE memory."
  - [corpus]: Weak evidence; corpus neighbors do not mention cache evaluation caching, suggesting this is a novel optimization.
- Break condition: If the hash map grows too large for memory, or if the probability of hash collisions increases with larger search spaces, lookup performance degrades and the runtime advantage shrinks.

### Mechanism 2
- Claim: The grammar-based phenotype generation ensures correct parameter ordering for Dinero IV simulator calls, enabling modular changes to the optimization problem.
- Mechanism: The BNF grammar maps each genotype codon to a specific cache parameter (size, line size, associativity, etc.) in the exact order required by Dinero IV. This removes the need for ad-hoc decoding logic and allows swapping in new simulators or parameters by editing the grammar alone.
- Core assumption: Dinero IV parameter order is fixed and known; the grammar production rules can be reordered to match without breaking the simulator interface.
- Evidence anchors:
  - [section]: "we have designed a grammar that produces phenotypes which form the parameters of the call to the simulator... we have adapted the parameters to the requirements of the simulator."
  - [abstract]: "Moreover, we selected GE because the plasticity of the grammar eases the creation of phenotypes that form the call to the cache simulator required for the evaluation of the different configurations."
  - [corpus]: Weak evidence; no corpus neighbors discuss grammar-driven simulator interfacing, implying this design choice is not widely adopted in related work.
- Break condition: If Dinero IV changes its parameter ordering or adds optional parameters, the grammar must be updated; failure to do so causes simulator errors or incorrect cache evaluations.

### Mechanism 3
- Claim: Off-line profiling and characterization amortize expensive trace generation and hardware modeling costs, enabling fast online optimization.
- Mechanism: The framework generates program traces once using Trimaran + SimpleScalar (off-line), and pre-computes access time and energy per access for every possible cache configuration using Cacti (off-line). These results are stored and reused during GE evolution, avoiding repeated slow simulations.
- Core assumption: Target applications and hardware parameters remain static; traces and Cacti characterizations do not need regeneration between optimization runs.
- Evidence anchors:
  - [section]: "The characterization process... This process provides the time and energy values used for the terms in equations... This characterization was run only once... The profiling process... This process is carried out by the open-source compiler and performance monitoring infrastructure called Trimaran."
  - [abstract]: "This metaheuristic allows an important reduction of the optimization runtime obtaining good results in a low number of generations."
  - [corpus]: Weak evidence; corpus neighbors do not detail off-line trace generation or hardware modeling amortization.
- Break condition: If the application set changes or the hardware model updates, off-line steps must be rerun; otherwise, cached traces and characterizations become invalid, leading to incorrect optimizations.

## Architecture Onboarding

- Component map:
  - Off-line Profiler -> Hardware Characterizer -> Grammatical Evolution Engine -> Dinero IV Simulator -> Fitness Evaluator -> Hash Map Cache

- Critical path:
  1. GE generates genotype → maps via grammar → checks hash map → if miss, calls Dinero IV → returns hits/misses → fitness evaluator applies models → returns fitness → GE updates population

- Design tradeoffs:
  - **Runtime vs Memory**: Storing all evaluated configurations speeds up evolution but increases memory usage; large search spaces may exhaust RAM.
  - **Grammar Flexibility vs Simulator Coupling**: A tightly coupled grammar to Dinero IV makes changes easy but locks in simulator specifics; a more abstract grammar reduces coupling but requires extra translation logic.
  - **Off-line Precomputation vs Fresh Evaluation**: Precomputing Cacti characterizations speeds up online evaluation but assumes hardware parameters are static.

- Failure signatures:
  - **Incorrect Fitness**: Mismatch between grammar parameter order and Dinero IV expectations leads to wrong cache configurations being evaluated.
  - **Hash Collisions**: Rare but possible; two different phenotypes produce the same hash key, causing fitness reuse errors.
  - **Outdated Off-line Data**: If benchmark binaries or hardware models change without regenerating traces or characterizations, the optimization will be based on stale data.

- First 3 experiments:
  1. **Sanity Check**: Run GE with a single fixed cache configuration (the baseline) and verify that fitness matches the precomputed baseline value.
  2. **Grammar Validation**: Feed a small set of known good cache configurations through the grammar → Dinero IV pipeline and compare results against manual Dinero IV runs.
  3. **Hash Map Coverage**: Execute GE until it evaluates at least 100 unique configurations; confirm that the hash map grows accordingly and that repeated evaluations hit the cache rather than re-simulating.

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the performance of the optimized cache configurations scale when applied to different ARM processor architectures beyond the ARM9 family?
- Basis in paper: [explicit] The paper mentions that the methodology can be applied to any kind of cache and processor architectures by changing the cache simulator and grammar.
- Why unresolved: The experiments only tested on ARM9-based architectures. Different ARM architectures may have different cache parameters and constraints that could affect optimization results.
- What evidence would resolve it: Testing the framework on multiple ARM architectures (e.g., ARM Cortex-A, ARM Cortex-M) and comparing performance improvements across different baseline configurations.

### Open Question 2
- Question: What is the impact of including more cache parameters (e.g., cache replacement algorithms, prefetch algorithms) on the optimization runtime and solution quality?
- Basis in paper: [explicit] The paper mentions that changing the grammar allows adding new parameters to the optimization.
- Why unresolved: The experiments only optimized 11 cache parameters. Including additional parameters could potentially lead to better cache configurations but may also increase the optimization runtime and complexity.
- What evidence would resolve it: Conducting experiments with an expanded set of cache parameters and analyzing the trade-off between optimization runtime and solution quality.

### Open Question 3
- Question: How does the optimization framework perform when applied to non-multimedia applications or a mix of different application types?
- Basis in paper: [explicit] The experiments used multimedia applications from the Mediabench suite, which are representative of multimedia applications in embedded systems.
- Why unresolved: The performance of cache configurations may vary depending on the application type and memory access patterns. The framework's effectiveness for other application domains remains unexplored.
- What evidence would resolve it: Testing the framework on a diverse set of applications from different domains (e.g., scientific computing, database systems) and comparing the optimization results and performance improvements.

## Limitations
- Narrow evaluation scope: Only tested on Mediabench suite and single ARM9 architecture with no cross-architecture validation
- Real hardware measurements: Results based on simulator modeling (Dinero IV + Cacti) without validation on actual hardware
- Static fitness weighting: Equal 0.5 weighting for execution time and energy may not reflect all embedded use cases

## Confidence
- Runtime reduction mechanism: Medium - caching strategy is clear but empirical validation of hash map behavior is missing
- Grammar-based simulator interface: High - straightforward mechanism with well-documented implementation
- Off-line amortization approach: Medium - method is sound but paper doesn't discuss scenarios where off-line data becomes stale
