# Improving Inference Performance of Machine Learning with the Divide-and-Conquer Principle

## Quick Facts
- arXiv ID: 2301.05099
- Source URL: https://arxiv.org/abs/2301.05099
- Authors: 
- Reference count: 32
- Primary result: Up to 2.33x latency improvement for PaddleOCR and up to 2.4x throughput improvement for BERT

## Executive Summary
This paper addresses the challenge of poor CPU inference performance for machine learning models that don't scale well with increased parallelism. The authors propose a Divide-and-Conquer approach that breaks inference jobs into independent parallel parts, with each part allocated CPU cores proportional to its expected computational cost. The method is implemented in OnnxRuntime through a new `prun` API that accepts multiple inputs and dynamically allocates threads based on input sizes. Experimental results show significant performance improvements across multiple use cases, particularly for processing heterogeneous input batches.

## Method Summary
The core method involves dividing a single inference job into multiple independent parts that can be executed in parallel. Each part is allocated a number of CPU cores proportional to its expected computational cost, estimated by the input tensor sizes. This is implemented in OnnxRuntime through a new `prun` API that accepts a list of inputs and internally manages parallel execution with dynamic thread allocation. The approach is particularly effective for models with non-scalable operators and for processing heterogeneous input batches where traditional padding approaches introduce significant computational overhead.

## Key Results
- PaddleOCR end-to-end inference latency improves by up to 2.33x when processing multiple detected text boxes
- BERT throughput improves by up to 2.4x when batching heterogeneous input sequences
- Even with homogeneous inputs, modest but non-trivial gains are observed compared to traditional batching approaches

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Poor scalability of ML models on CPUs can be mitigated by dividing inference jobs into parallel chunks based on input size.
- Mechanism: The Divide-and-Conquer Principle is applied by splitting a single inference job into multiple independent parts, each processed in parallel with a thread allocation proportional to its computational weight (estimated by input size).
- Core assumption: The computational cost of processing an input grows roughly linearly with its size, making input size a valid proxy for relative weight.
- Evidence anchors:
  - [abstract] "the idea is to break the job into independent parts that can be executed in parallel, each with the number of cores according to its expected computational cost."
  - [section 3.1] "we set w_i to s_i / Σs_i, essentially assuming that the amount of computation grows roughly linearly with the input tensors' size."
- Break condition: This mechanism breaks when input size is not a good proxy for computational cost, such as when operators have non-linear complexity or when padding is involved.

### Mechanism 2
- Claim: By processing heterogeneous inputs in parallel with size-based thread allocation, padding overhead can be eliminated.
- Mechanism: Instead of padding all inputs to the same length for batching, each input is processed separately with a thread allocation based on its size, avoiding wasted computation on padding tokens.
- Core assumption: The framework overhead and non-scalable operators have a higher relative cost when processing padded inputs versus processing smaller inputs directly.
- Evidence anchors:
  - [section 2.5] "This situation presents an ideal case for applying the Divide-and-Conquer Principle. Instead of padding the inputs of various lengths up to the longest input in the batch, we can run inference on those inputs (as they are, without padding) using the prun API."
  - [section 4.2] "we show results with the highly popular BERT model... The latter results in wasted computation cycles, since special padding tokens are treated exactly as input tokens by the architecture and dismissed at the end of the computation."
- Break condition: This mechanism breaks when the framework overhead of managing multiple parallel jobs exceeds the savings from avoiding padding, or when the input size variation is minimal.

### Mechanism 3
- Claim: Allocating more threads to larger inputs and fewer to smaller ones improves overall throughput for heterogeneous batches.
- Mechanism: By dynamically allocating computing resources based on input size, the system can achieve better throughput by giving more resources to computationally intensive tasks while avoiding over-provisioning for small tasks.
- Core assumption: The marginal benefit of additional threads decreases for smaller inputs, making it more efficient to allocate those threads to larger inputs.
- Evidence anchors:
  - [section 4.2] "the throughput of the pad-batch version grows, but modestly with the increase in the number of short sequences. This is because... the throughput growth with prun is much more dramatic up to 3 short sequences in a batch and then it declines."
  - [section 4.2] "With more short sequences in a batch, less threads are allocated for the long sequence... its inference latency grows. This causes the overall throughput to decrease."
- Break condition: This mechanism breaks when the overhead of managing multiple thread pools outweighs the benefits of dynamic allocation, or when input sizes are too similar to justify different thread allocations.

## Architecture Onboarding

- Component map: User -> prun API -> Thread allocation algorithm -> Worker threads -> Post-processing coordination -> Results
- Critical path:
  1. User calls prun with list of inputs
  2. System calculates size and relative weight for each input
  3. Thread allocation algorithm assigns cores to each input
  4. Worker threads created and execute inference in parallel
  5. Results collected and post-processed

- Design tradeoffs:
  - Flexibility vs complexity: prun provides more flexibility but requires more complex code
  - Resource utilization vs overhead: dynamic allocation can improve utilization but adds allocation overhead
  - Simplicity vs optimality: simple weight calculation (by size) vs more accurate profiling-based weights

- Failure signatures:
  - No performance improvement: may indicate overhead dominates benefits or inputs are too similar
  - Performance degradation: may indicate oversubscription of cores or framework overhead issues
  - Memory pressure: may occur when processing many large inputs in parallel

- First 3 experiments:
  1. Test prun with homogeneous inputs of varying sizes to verify basic functionality
  2. Test prun with heterogeneous inputs to validate dynamic allocation benefits
  3. Test scalability limits by increasing number of parallel jobs to identify overhead thresholds

## Open Questions the Paper Calls Out

### Open Question 1
- Question: What is the optimal dynamic thread allocation strategy that can adapt to different workload characteristics and model behaviors, rather than using fixed proportional allocation based on input size?
- Basis in paper: [explicit] The authors mention wanting to explore "more dynamic thread allocation strategies" and acknowledge that "the weight of a work chunk does not correlate linearly with its size and/or where the underlying model performs best while running with a single thread"
- Why unresolved: The current implementation uses a static weight calculation based on input size, which may not capture the actual computational complexity or optimal thread usage for different operations within a model
- What evidence would resolve it: Empirical comparison of throughput/latency across various models and input patterns using different allocation strategies (dynamic profiling-based, model-specific heuristics, reinforcement learning approaches) against the current size-based proportional allocation

### Open Question 2
- Question: How can the input chunking process be automated to minimize user code changes while maximizing parallel execution opportunities?
- Basis in paper: [explicit] The authors state they want to "explore ways to automate splitting the input into chunks that can be processed in parallel, lowering the cost (in terms of user code changes) of using prun"
- Why unresolved: Current implementation requires users to manually identify how to break down their inference jobs into parallelizable parts, which limits adoption and may miss optimization opportunities
- What evidence would resolve it: Development and evaluation of an automated chunking mechanism that can identify parallelizable components across different model architectures and compare its performance against manual chunking

### Open Question 3
- Question: What is the performance impact of reusing thread pools between prun invocations compared to creating new thread pools for each call?
- Basis in paper: [explicit] The authors mention they "intend to experiment with reusing thread pools between prun invocations" to address the overhead of thread creation/destruction, particularly for short-running phases
- Why unresolved: Current implementation creates new thread pools for each prun call, which may add overhead that becomes significant for models with many small components or frequent prun calls
- What evidence would resolve it: Benchmark comparison of throughput/latency with and without thread pool reuse across various use cases, including models with many small components versus few large ones

### Open Question 4
- Question: How does the prun approach perform on GPU accelerators compared to CPUs, given that GPU kernels often handle padding differently?
- Basis in paper: [inferred] The authors discuss padding overhead as a motivation for prun and note that related work targets GPU-specific padding elimination techniques, suggesting this is an open comparison
- Why unresolved: All experiments were conducted on CPUs, and the framework overhead and padding characteristics may differ significantly on GPUs due to different kernel implementations and memory architectures
- What evidence would resolve it: Systematic performance comparison of prun versus batching/padding approaches on GPUs across multiple model types, measuring both throughput and latency under various batch sizes and input heterogeneity levels

## Limitations

- The approach's effectiveness depends heavily on input size serving as a reliable proxy for computational cost, which may not hold for all model architectures or workloads.
- The method requires users to manually identify how to break down inference jobs into parallelizable parts, limiting automation and potentially missing optimization opportunities.
- Framework overhead from managing multiple thread pools and coordinating parallel execution may negate benefits for certain use cases, particularly with many small inputs.

## Confidence

**High Confidence**: The core mechanism of breaking inference jobs into parallel chunks and allocating resources proportionally is well-founded and technically sound. The implementation in OnnxRuntime appears correct and the observed performance improvements for the tested scenarios are plausible.

**Medium Confidence**: The performance improvements are demonstrated convincingly for the specific PaddleOCR and BERT use cases tested, but the generalizability to other models and workloads remains uncertain. The claimed benefits may be less pronounced for models without significant padding overhead or for workloads with more uniform input sizes.

**Low Confidence**: The paper does not adequately address potential negative scenarios where the approach might degrade performance, such as when input sizes are very similar or when framework overhead dominates the computational savings. The sensitivity of results to specific hardware configurations is also not explored.

## Next Checks

1. **Robustness Testing**: Test the prun API across a diverse set of models beyond PaddleOCR and BERT, including transformer-based models with different architectures, convolutional networks, and recurrent models to assess generalizability.

2. **Overhead Analysis**: Measure and quantify the framework overhead introduced by the prun API, including thread pool creation/destruction costs, result aggregation overhead, and memory usage patterns across different numbers of parallel jobs.

3. **Edge Case Evaluation**: Systematically test scenarios where the approach might fail or degrade performance, including cases with uniform input sizes, very small inputs, extreme input size variations, and resource-constrained environments with limited core availability.
