# AutoScrum: Automating Project Planning Using Large Language Models

## Quick Facts
- arXiv ID: 2306.03197
- Source URL: https://arxiv.org/abs/2306.03197
- Reference count: 1
- AutoScrum uses LLMs to automate agile project planning tasks including requirements gathering, user story mapping, and task decomposition

## Executive Summary
AutoScrum introduces a novel approach for automating agile project planning using large language models. The system employs Microsoft Guidance syntax to create "Language Programs" that execute natural language programs on GPT-3.5-turbo or GPT-4. Two approaches are presented: a traditional scrum-based method and a shortcut planning method that iteratively generates tasks to bridge current and desired states. The system demonstrates effective generation of requirements, user stories, and task decompositions, though results are enhanced when combined with human review.

## Method Summary
AutoScrum leverages Microsoft Guidance syntax to create structured "Language Programs" that execute natural language programs on GPT-3.5-turbo or GPT-4. The system takes current state and desired state as inputs and generates requirements, features, user stories, and tasks through iterative LLM processing. Two approaches are implemented: a scrum-based method following traditional agile processes, and a shortcut planning method that iteratively suggests the next optimal task based on current and desired states. All programs are designed to return structured JSON responses for automated processing and integration.

## Key Results
- GPT-3.5-turbo effectively generates relevant requirements, user stories, and task decompositions for project planning
- The shortcut planning approach successfully navigates from current to desired states through iterative task generation
- GPT-4 shows more consistent completion status recognition than GPT-3.5, particularly in recognizing when desired states are achieved
- Human review combined with LLM generation produces better results than either approach alone

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Language models can effectively bridge the gap between current and desired states through iterative task generation
- Mechanism: The system uses LLM reasoning to analyze the discrepancy between current and desired states, then generates the next most relevant task to move toward the goal. This process repeats iteratively, with each iteration updating the current state based on completed tasks
- Core assumption: The LLM can accurately assess state differences and prioritize tasks that minimize the distance to the desired state
- Evidence anchors:
  - [abstract]: "The shortcut approach looks at most recent snapshot of the current and desired state and generates the next most reasonable task to do in order to get to the desired state as quickly as possible"
  - [section 4.8]: "This language program is executed iteratively until the desired state is reached"
- Break condition: The model fails to recognize when the desired state is actually achieved, continuing to generate tasks unnecessarily (observed with GPT-3.5 but not GPT-4)

### Mechanism 2
- Claim: Structured natural language programs (Guidance) enable reliable LLM task execution
- Mechanism: The system uses Microsoft Guidance syntax to create "Language Programs" - natural language programs that process input data through the LLM with consistent formatting and response structures
- Core assumption: LLMs can reliably parse and follow structured instructions when provided with clear response formats and temperature settings
- Evidence anchors:
  - [abstract]: "All LLM programs. Guidance language is used for all LLM programs"
  - [section 4.1]: "The process is highly iterative where we will be generating small chunks at a time, reviewing them and then committing them into the database"
- Break condition: The LLM generates invalid JSON or deviates from the specified response format, breaking the automated pipeline

### Mechanism 3
- Claim: Human review combined with LLM generation produces better results than either alone
- Mechanism: The system pairs LLM-generated outputs with human filtering and refinement, allowing the model to brainstorm while humans validate and curate results
- Core assumption: Human judgment can effectively filter LLM outputs to maintain quality while leveraging the model's creative capabilities
- Evidence anchors:
  - [section 4.1]: "You simply don't want to rely completely on the language model. Instead, the language model can brainstorm and suggest the next steps and then you let the team filter the results of the language model as the process progresses at each step"
  - [section 5.1]: "Language models like GPT-3.5 and beyond display incredible ability of guiding the human thought process"
- Break condition: Human reviewers lack the domain expertise to effectively evaluate LLM suggestions, or the review process becomes a bottleneck that negates the efficiency gains

## Foundational Learning

- Concept: Current state and desired state parameterization
  - Why needed here: This forms the core input that drives all LLM reasoning and task generation. Without clear state definitions, the system cannot determine what tasks are needed
  - Quick check question: Can you clearly articulate the measurable difference between where you are now and where you want to be?

- Concept: JSON response formatting and structured outputs
  - Why needed here: The system relies on parsing structured outputs to continue the automated workflow. Understanding how to design prompts that consistently return valid JSON is critical
  - Quick check question: If an LLM returns "I need to buy 5 more chickens" instead of {"task": "Buy 5 more chickens", "status": "progress"}, will your pipeline continue working?

- Concept: Iterative refinement and temperature settings
  - Why needed here: The system's effectiveness depends on understanding how temperature affects output diversity and task selection strategy
  - Quick check question: If you want more aggressive task suggestions versus step-by-step approaches, which temperature setting would you use?

## Architecture Onboarding

- Component map: Input Layer (current state, desired state) -> Processing Layer (Guidance programs) -> LLM Interface (GPT-3.5/GPT-4) -> Output Layer (JSON responses) -> Integration Layer (Python orchestration) -> Storage Layer (database)
- Critical path: Current/Desired state → Requirements generation → Feature extraction → User story mapping → Task decomposition → Iterative planning → Task completion
- Design tradeoffs: GPT-3.5 is more economical but requires more careful prompt engineering; GPT-4 is more capable at state recognition but significantly more expensive
- Failure signatures: Invalid JSON responses, task loops that don't progress toward the goal, or the model failing to recognize when the desired state is achieved
- First 3 experiments:
  1. Test the requirements generation program with a simple current/desired state (e.g., "I have 5 chickens, I want 10") and verify JSON output format
  2. Run the shortcut planning program with a clear state difference and observe whether it correctly identifies the next task and recognizes when done
  3. Test temperature sensitivity by running the same scenario with different temperature settings and comparing task selection strategies

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the performance of GPT-4 compare to GPT-3.5-turbo in the AutoScrum framework for project planning tasks?
- Basis in paper: [explicit] The paper mentions that GPT-4 would provide "vastly better results" than GPT-3.5-turbo, and that GPT-4 "shows more consistent completion status recognition" in the shortcut planning approach.
- Why unresolved: The paper primarily uses GPT-3.5-turbo for experiments and only mentions GPT-4's potential improvements without conducting direct comparative experiments.
- What evidence would resolve it: Direct experimental comparison of GPT-3.5-turbo and GPT-4 using the same AutoScrum framework tasks, measuring metrics like task completion accuracy, reasoning quality, and planning efficiency.

### Open Question 2
- Question: How does the iterative "shortcut planning" approach compare to traditional Scrum methodology in terms of project completion time and resource efficiency?
- Basis in paper: [explicit] The paper presents both approaches but doesn't provide direct comparative results on their effectiveness.
- Why unresolved: The paper demonstrates both methods but doesn't measure or compare their relative performance in real-world scenarios.
- What evidence would resolve it: Controlled experiments applying both approaches to identical projects, measuring completion time, resource usage, team satisfaction, and final product quality.

### Open Question 3
- Question: How does temperature parameter tuning affect the quality and diversity of tasks generated in the AutoScrum framework?
- Basis in paper: [explicit] The paper notes that "increasing the temperature parameter seems to make the model suggest bolder tasks while lower value seems to suggest a more step by step approach."
- Why unresolved: The paper doesn't provide systematic experiments on temperature effects across different types of projects or tasks.
- What evidence would resolve it: Controlled experiments varying temperature across multiple project types, measuring task relevance, innovation, and alignment with project goals at different temperature settings.

## Limitations

- Evaluation relies entirely on synthetic scenarios rather than real-world agile projects
- Only one concrete example (chicken farm expansion) is provided with detailed results
- Human review component is mentioned as essential but not systematically evaluated for its impact on outcomes or efficiency gains

## Confidence

**High Confidence**: The technical implementation using Microsoft Guidance for structured LLM outputs is well-established and the core mechanism of iterative state-based task generation is clearly described and reproducible.

**Medium Confidence**: The claim that GPT-4 better recognizes completion states than GPT-3.5 is supported by the chicken farm example, but broader validation across diverse scenarios would strengthen this conclusion.

**Low Confidence**: The assertion that human review "pairs well" with LLM generation lacks quantitative support - no metrics are provided on how human filtering affects accuracy, efficiency, or project outcomes.

## Next Checks

1. **State Recognition Stress Test**: Create a diverse set of current/desired state pairs across multiple domains (software development, construction, education) and measure GPT-3.5 vs GPT-4 accuracy in recognizing when the desired state is actually achieved.

2. **Human Review Impact Analysis**: Implement the same planning scenarios with and without human review checkpoints, measuring differences in task relevance, completion accuracy, and time efficiency to quantify the true value of human filtering.

3. **Real Project Validation**: Apply the system to an actual agile project with real stakeholders, comparing the LLM-generated plan against traditional scrum planning outcomes in terms of completeness, accuracy, and stakeholder satisfaction.
