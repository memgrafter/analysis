# Alfred: A System for Prompted Weak Supervision

## Quick Facts
- arXiv ID: 2305.18623
- Source URL: https://arxiv.org/abs/2305.18623
- Authors: 
- Reference count: 9
- Primary result: First system for programmatic weak supervision using natural language prompts instead of code-based labeling functions

## Executive Summary
Alfred is a system that transforms weak supervision by enabling users to create training data through natural language prompts rather than code-based labeling functions. It allows subject matter experts to encode their knowledge via prompts for large language and vision-language models, eliminating the need for programming expertise. The system provides a simple Python interface with a high-throughput backend for large-scale data labeling, supporting both text and image data through models like T0++ and CLIP. Alfred achieves 2.9x greater throughput than naive implementations through dynamic batching optimizations and enables seamless local development backed by remote computing clusters.

## Method Summary
Alfred replaces traditional code-based labeling functions with natural language prompts for programmatic weak supervision. Users define prompt templates that encode domain expertise, which are then applied to unlabeled datasets to generate queries for large pre-trained models. The system maps model responses to votes using voter components, aggregates these votes with label models (such as NaiveBayes or NPLM), and produces probabilistic labels for training end models. Alfred implements dynamic batching to group similar-length instances and maximize inference throughput, achieving 2.9x improvement over naive approaches. The system supports both local development and remote model hosting through SSH tunneling, with gRPC for high-throughput remote procedure calls.

## Key Results
- Enables prompt-based weak supervision without requiring programming expertise
- Achieves 2.9x greater query throughput than naive implementations through dynamic batching
- Successfully demonstrates effectiveness on YouTube comment spam detection and pet breeds classification tasks

## Architecture Onboarding

- Component map:
  - Alfred Client -> Alfred Server -> Model Inference -> gRPC Framework
  - Template System -> Voter System -> Label Model -> End Model Training

- Critical path:
  1. Developer creates templates and voters
  2. Alfred Client sends queries to Alfred Server
  3. Server processes queries with dynamic batching
  4. Server returns responses to Client
  5. Client maps responses to votes using voters
  6. Label model aggregates votes to produce probabilistic labels

- Design tradeoffs:
  - Local vs remote model hosting: Remote hosting enables access to larger models but introduces network latency
  - Query caching: Reduces redundant computations but requires storage overhead
  - Exact vs approximate matching: Exact matching is simpler but may miss valid responses

- Failure signatures:
  - Low throughput: Indicates batching algorithm issues or network problems
  - Inaccurate labels: Suggests poor prompt design or model unsuitability for the task
  - High latency: Points to network bottlenecks or inefficient server configuration

## Limitations

- Limited empirical evaluation on only two datasets (YouTube comments and pet images) restricts generalizability claims
- No detailed ablation studies on the impact of different prompt engineering choices or batching configurations
- The system's performance on more diverse and complex tasks remains unverified
