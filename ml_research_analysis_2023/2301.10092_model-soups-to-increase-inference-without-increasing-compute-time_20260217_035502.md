# Model soups to increase inference without increasing compute time

## Quick Facts
- arXiv ID: 2301.10092
- Source URL: https://arxiv.org/abs/2301.10092
- Authors: 
- Reference count: 0
- Primary result: Model soups improve ViT accuracy up to 52.1% but fail for ResNet and EfficientNet

## Executive Summary
This study investigates model soups, a technique that averages weights of multiple fine-tuned models to improve accuracy without increasing inference time. The authors compare three soup recipes (Greedy Soup Sorted, Greedy Soup Random, and Uniform Soup) on ResNet, ViT, and EfficientNet models using the CIFAR-100 dataset. They introduce a new Pruned Soup recipe that outperforms the original methods. Results show that model soups significantly improve performance for ViT models (up to 52.1% accuracy), but perform poorly for ResNet and EfficientNet models (near-random guessing). The study reveals that model soups work best when models converge to the same error landscape during fine-tuning, highlighting a key limitation: soups are effective only for fine-tuning pre-trained models with similar optimization trajectories.

## Method Summary
The study fine-tunes pre-trained models (ResNet, ViT, EfficientNet) on CIFAR-100 with 36 hyperparameter combinations (learning rates: 0.01-0.4, weight decays: 1e-5 to 4e-4) for 10-15 epochs using SGD with momentum 0.9 and batch size 256. The test set is split into validation (5,000 images) and test sets (5,000 images). Three soup recipes are implemented: Greedy Sorted (adds models in descending accuracy order), Greedy Random (adds models randomly), and Uniform (averages all models equally). A new Pruned Soup recipe iteratively removes poorly contributing models while preserving accuracy. Performance is measured by comparing soup accuracy against the best individual model.

## Key Results
- Model soups improve ViT accuracy significantly (up to 52.1% vs individual models)
- Soups perform near-random guessing for ResNet and EfficientNet models
- Pruned Soup outperforms original methods by removing redundant models
- Soups work best when models converge to the same error landscape during fine-tuning

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Model soups improve accuracy by averaging weights of fine-tuned models that converge to the same error landscape.
- Mechanism: When multiple models are fine-tuned from the same pre-trained initialization, they tend to settle in nearby local minima of the loss landscape. Averaging their weights moves the solution to a point that is still within this favorable region, improving generalization.
- Core assumption: All models in the soup must share a similar optimization trajectory and converge to the same error landscape.
- Evidence anchors:
  - [abstract] "The study reveals that model soups work best when models converge to the same error landscape during fine-tuning"
  - [section] "the concept of soups works well for the fine-tuning of pre-trained models, but not for the trained-from-scratch models. In fact, the soups work well when the models have been tuned independently from the same initialization as they have the same error landscape."
  - [corpus] Weak evidence: no direct citations about error landscape in related papers; mentions of soups are mostly algorithmic.
- Break condition: If models converge to different local minima (e.g., due to different architectures or optimizers), weight averaging destroys generalization ability.

### Mechanism 2
- Claim: Pruned soups improve performance by iteratively removing poorly contributing models while preserving the best combination.
- Mechanism: Start with the uniform average of all models, then iteratively test removal of each model. If removal does not hurt validation accuracy, keep it out. This greedy elimination converges to a minimal set of high-contributing models.
- Core assumption: Some models in the initial soup are redundant or harmful; removing them can improve or maintain accuracy with fewer ingredients.
- Evidence anchors:
  - [section] "The pruned soup performed better than the uniform and greedy soups... while picking models randomly, and 52.1% when the models were sorted in decreasing accuracy."
  - [section] "an increase in the number of passes increases the accuracy of both random and sorted pruned soups."
  - [corpus] No direct evidence in related papers; method appears novel to this work.
- Break condition: If all models contribute positively, removal will degrade accuracy; the process stops when no further improvement is possible.

### Mechanism 3
- Claim: Sorted greedy soups outperform random greedy soups because models with higher individual accuracy are more likely to improve the ensemble.
- Mechanism: By sorting models in descending order of validation accuracy before adding them to the soup, the algorithm prioritizes high-performing models, increasing the chance that each addition improves the ensemble.
- Core assumption: Models with higher individual accuracy are more likely to have weights that, when averaged, improve ensemble performance.
- Evidence anchors:
  - [section] "Similar to what the paper mentioned, a sorted strategy gives a slightly better accuracy than a randomly ordered strategy."
  - [section] "a better accuracy is achieved with sorted soup models."
  - [corpus] No direct evidence in related papers; observation is empirical from this study.
- Break condition: If model accuracy does not correlate with contribution to the ensemble, sorting provides no benefit.

## Architecture Onboarding

- Component map:
  Model training module -> Evaluator module -> Soup construction module -> Experiment orchestration

- Critical path:
  1. Train individual models with varied hyperparameters.
  2. Evaluate each model on a held-out validation set.
  3. Construct soups using chosen recipe (uniform, greedy, pruned).
  4. Validate soup performance on a separate test set.

- Design tradeoffs:
  - Memory vs. performance: Storing multiple fine-tuned models increases memory use but enables soups.
  - Soup complexity vs. accuracy: More ingredients can improve accuracy up to a point, then hurt it.
  - Sorted vs. random selection: Sorted greedy soups are slightly more accurate but require sorting overhead.

- Failure signatures:
  - Uniform soup accuracy much lower than best individual model (models converged to different landscapes).
  - Pruned soup accuracy near random guessing (models not pre-trained or incompatible architectures).
  - Greedy soup stops improving after a few ingredients (diminishing returns or wrong ingredient selection).

- First 3 experiments:
  1. Train 36 ResNet models on CIFAR-100 with varied learning rates and weight decays; evaluate individual and uniform soup performance.
  2. Apply greedy soup (sorted) to the same ResNet models; compare accuracy to best individual model.
  3. Apply pruned soup (2 passes) to the ResNet models; observe ingredient count reduction and accuracy change.

## Open Questions the Paper Calls Out

### Open Question 1
- Question: What specific architectural characteristics determine whether model soups will successfully improve accuracy?
- Basis in paper: [explicit] The paper shows soups work well for ViT but fail for ResNet and EfficientNet, suggesting architecture-dependent behavior
- Why unresolved: The paper identifies that soups require models to converge to the same error landscape but doesn't explain why some architectures naturally satisfy this requirement while others don't
- What evidence would resolve it: Systematic experiments comparing different architectural families (CNNs, transformers, MLPs) while controlling for pre-training status and fine-tuning hyperparameters

### Open Question 2
- Question: Does batch normalization contribute to models converging to different error landscapes during fine-tuning?
- Basis in paper: [inferred] The paper suggests that different error landscapes are a key limitation but doesn't investigate specific architectural components
- Why unresolved: While batch normalization introduces stochasticity during training, the paper doesn't test whether removing or modifying batch normalization affects soup performance
- What evidence would resolve it: Comparative experiments using batch normalization-free architectures (like those using GroupNorm) versus standard batch normalization to measure differences in soup effectiveness

### Open Question 3
- Question: How does the choice of optimizer during fine-tuning influence whether models converge to the same error landscape?
- Basis in paper: [explicit] The paper mentions optimizer choice as part of hyperparameter tuning but doesn't analyze its impact on soup performance
- Why unresolved: Different optimizers (SGD, Adam, AdamW) have different convergence properties that could affect whether models settle in the same basin of the loss landscape
- What evidence would resolve it: Experiments comparing soup performance when using different optimizers with otherwise identical fine-tuning procedures across multiple model architectures

### Open Question 4
- Question: What is the minimum number of fine-tuned models needed to reliably construct effective soups across different architectures?
- Basis in paper: [inferred] The paper uses 36 hyperparameter combinations but doesn't analyze how performance scales with the number of models
- Why unresolved: While the paper shows soups outperform individual models in some cases, it doesn't establish the sample complexity requirements for reliable performance gains
- What evidence would resolve it: Systematic studies varying the number of fine-tuned models (5, 10, 20, 36) and measuring soup performance improvements to identify the point of diminishing returns

## Limitations

- Model soups only work for fine-tuning pre-trained models with similar optimization trajectories
- Technique fails completely for ResNet and EfficientNet architectures tested
- Requires storing multiple fine-tuned models, increasing memory usage

## Confidence

- High confidence: Model soups require models to converge to the same error landscape during fine-tuning
- Medium confidence: Pruned Soup algorithm's superiority, but implementation details unclear
- Low confidence: Generalizability beyond CIFAR-100 and specific architectures tested
