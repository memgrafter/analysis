# Experience in Engineering Complex Systems: Active Preference Learning with Multiple Outcomes and Certainty Levels

## Quick Facts
- arXiv ID: 2302.14630
- Source URL: https://arxiv.org/abs/2302.14630
- Reference count: 33
- Primary result: AmPL algorithm significantly improves worst-case and mean performance on benchmark functions compared to APL-RBF

## Executive Summary
This paper presents an Active multi-Preference Learning (AmPL) algorithm for black-box optimization where the objective function is unknown but human preferences can be queried. The key innovation is incorporating 5-point Likert scale outcomes and certainty levels (1-4) into the preference learning framework. Using radial basis functions with slack variables weighted by certainty levels, the algorithm constructs a surrogate function that satisfies acquired preferences while handling uncertain feedback. An acquisition function combining exploitation of the surrogate with exploration based on inverse distance weighting guides the search for new samples.

## Method Summary
The AmPL algorithm extends active preference learning by using a 5-point Likert scale for preference outcomes and certainty levels from 1 to 4. It constructs a surrogate function using radial basis functions with slack variables and certainty-weighted constraints to handle uncertain feedback. The algorithm iteratively selects new samples using an acquisition function that balances exploitation of the surrogate function with exploration based on inverse distance weighting. The method is validated on six-hump camel-back, Ackley, and 8-dimensional Rosenbrock functions, showing significant improvements over the state-of-the-art APL-RBF algorithm.

## Key Results
- AmPL significantly improves both worst-case and mean performance across all test functions compared to APL-RBF
- The algorithm effectively exploits richer preference information from multiple outcomes and certainty levels
- Performance gains are consistent across different benchmark functions with varying complexity

## Why This Works (Mechanism)

### Mechanism 1
- Claim: The algorithm improves performance by incorporating richer preference information through 5-point Likert scale outcomes and certainty levels.
- Mechanism: The preference-based surrogate function uses slack variables weighted by certainty levels to relax constraints, allowing the model to handle uncertain human feedback more effectively than binary preference approaches.
- Core assumption: Human certainty levels accurately reflect their confidence in preferences and can be meaningfully incorporated into the optimization framework.
- Evidence anchors:
  - [abstract] "The method uses radial basis functions to construct a surrogate function that satisfies acquired preferences, with slack variables and certainty-weighted constraints to handle uncertain feedback."
  - [section] "wh,t values are selected proportionally to the certainty level ch,t to emphasize the fact that ˆf(xi(h)) − ˆf(xj(h)) tends to stay inside a boundary where the certainty level is higher."
  - [corpus] Weak - the corpus papers focus on preference learning but don't specifically address certainty-weighted constraints.
- Break condition: If human certainty ratings are systematically biased or inconsistent, the weighted constraints could mislead the optimization rather than improve it.

### Mechanism 2
- Claim: The acquisition function balances exploitation of the surrogate function with exploration using inverse distance weighting.
- Mechanism: The acquisition function combines normalized surrogate function values with an exploration term that increases as distance from existing samples grows, preventing premature convergence to local optima.
- Core assumption: The exploration function effectively identifies unexplored regions of the decision space that may contain better solutions.
- Evidence anchors:
  - [abstract] "An acquisition function combining exploitation of the surrogate and exploration based on inverse distance weighting guides the search for new samples."
  - [section] "z(x) gets bigger as x being far away from all sampled points but assuring at the same time that z(x) is refrained from getting excessively large."
  - [corpus] Moderate - several corpus papers mention exploration strategies but not specifically the IDW-based approach used here.
- Break condition: If the exploration parameter tuning is incorrect, the algorithm might either over-explore (slowing convergence) or under-explore (getting stuck in local optima).

### Mechanism 3
- Claim: Allowing multiple outcomes per preference query captures uncertainty and improves information efficiency.
- Mechanism: When multiple preference outcomes are collected from a single query, the algorithm can encode more nuanced information about the decision maker's uncertainty, reducing the number of queries needed for effective optimization.
- Core assumption: Humans can meaningfully express uncertainty through multiple preference outcomes rather than just certainty levels.
- Evidence anchors:
  - [section] "multiple outcomes would be acquired from one single preference query" and "much more information could be harvested than in the case where only absolutely sure answers are allowed."
  - [section] "While the human decision maker may not be absolutely sure about individual outcomes, one of the outcomes needs to be the correct one."
  - [corpus] Moderate - the corpus papers mention preference learning but don't specifically address multiple outcomes per query.
- Break condition: If humans find it cognitively difficult to express multiple outcomes, the quality of feedback may degrade, negating the information efficiency benefits.

## Architecture Onboarding

- Component map:
  Preference acquisition module -> Surrogate function builder -> Slack variable manager -> Acquisition function generator -> Optimization engine -> Benchmark validator

- Critical path:
  1. Initialize samples using Latin hypercube sampling
  2. Collect preference feedback with multiple outcomes and certainty levels
  3. Build surrogate function with slack variables weighted by certainty
  4. Generate acquisition function combining exploitation and exploration
  5. Solve for next sample and repeat until convergence

- Design tradeoffs:
  - Complexity vs. information richness: More detailed preference scales capture more information but increase cognitive load on human evaluators
  - Exploration vs. exploitation: Aggressive exploration may slow convergence but prevents local optima; too little exploration risks missing better solutions
  - Certainty weighting: Accurate certainty assessment improves performance but requires reliable human self-awareness

- Failure signatures:
  - Slow convergence: May indicate poor exploration parameter tuning or insufficient preference information
  - Inconsistent results across runs: Could signal sensitivity to initialization or preference noise handling issues
  - Preference satisfaction failure: May indicate slack variable configuration problems or RBF function selection issues

- First 3 experiments:
  1. Validate basic RBF surrogate function construction on a simple 2D test function with synthetic preferences
  2. Test certainty-weighted slack variable handling by introducing controlled noise into preference feedback
  3. Verify exploration-exploitation balance by running on a multimodal function and analyzing sample distribution

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How does the performance of AmPL compare to APL-RBF when human decision makers provide preferences with varying levels of certainty and multiple outcomes?
- Basis in paper: [explicit] The paper states that AmPL significantly improves both worst-case and mean performance across all test functions compared to APL-RBF, but does not provide a direct comparison of how the algorithms perform when human decision makers provide preferences with varying certainty levels and multiple outcomes.
- Why unresolved: The paper validates AmPL using benchmark functions, where the "human decision maker" is replaced by these functions. It does not report results from actual human experiments with varying certainty levels and multiple outcomes.
- What evidence would resolve it: A study where both algorithms are tested with human subjects providing preferences with different certainty levels and multiple outcomes, comparing the performance of AmPL and APL-RBF in finding optimal solutions.

### Open Question 2
- Question: What is the optimal number of choices in a Likert-type scale for preference queries in black-box optimization problems?
- Basis in paper: [explicit] The paper mentions that the debate regarding the optimal number of choices in a Likert-type scale continues and uses a 5-point scale, but does not investigate the impact of different scale sizes on the algorithm's performance.
- Why unresolved: The paper uses a 5-point Likert scale based on existing literature, but does not experimentally determine if this is the optimal number of choices for the specific context of black-box optimization with preference learning.
- What evidence would resolve it: An empirical study comparing the performance of AmPL using different Likert scale sizes (e.g., 3-point, 5-point, 7-point) in various optimization problems, measuring convergence speed and solution quality.

### Open Question 3
- Question: How sensitive is AmPL to the choice of hyperparameters (σ1, σ2, αN) and can these be automatically tuned?
- Basis in paper: [explicit] The paper states that γ is tuned through K-fold cross validation, but does not discuss the tuning of σ1, σ2, and αN, which are also hyperparameters in the algorithm.
- Why unresolved: While the paper provides default values for these hyperparameters, it does not investigate their impact on the algorithm's performance or propose a method for automatic tuning.
- What evidence would resolve it: A sensitivity analysis of AmPL's performance to different values of σ1, σ2, and αN, and the development and validation of an automatic hyperparameter tuning method for these parameters.

## Limitations
- The algorithm's performance with real human decision makers has not been validated, only benchmark functions
- Several implementation details including exact slack variable handling and exploration parameter schedules are not fully specified
- The generalizability to complex engineering systems beyond synthetic benchmark functions remains unproven
