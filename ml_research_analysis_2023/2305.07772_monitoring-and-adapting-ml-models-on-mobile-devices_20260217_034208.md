# Monitoring and Adapting ML Models on Mobile Devices

## Quick Facts
- arXiv ID: 2305.07772
- Source URL: https://arxiv.org/abs/2305.07772
- Reference count: 40
- Key outcome: First end-to-end system for continuously monitoring and adapting ML models on mobile devices without user feedback, achieving up to 22% average accuracy improvement on all data and up to 50% on drifted data compared to baselines.

## Executive Summary
Nazar is the first end-to-end system for continuously monitoring and adapting ML models on mobile devices without requiring user feedback or labeled data. The system detects model degradation using a confidence threshold method, analyzes root causes through frequent itemset mining and counterfactual analysis, and adapts models by-cause using self-supervised entropy minimization techniques like TENT. Evaluated on cityscapes and animal datasets, Nazar achieves significant accuracy improvements while operating autonomously on resource-constrained mobile devices.

## Method Summary
Nazar operates through a three-phase pipeline: detection, analysis, and adaptation. During detection, it uses a confidence threshold method where model predictions with Maximum Softmax Probability (MSP) below a threshold are flagged as potentially drifted. For analysis, it logs drift events with device metadata and applies frequent itemset mining to identify root causes, using set reduction and counterfactual analysis to eliminate redundant causes. During adaptation, it selectively fine-tunes batch normalization layers using self-supervised entropy minimization techniques to adapt to specific drift causes without requiring labels.

## Key Results
- Achieves up to 22% average accuracy improvement on all data compared to baselines
- Achieves up to 50% accuracy improvement specifically on drifted data
- Operates autonomously without user feedback or labeled data requirements

## Why This Works (Mechanism)

### Mechanism 1
- Claim: Nazar detects data drift by comparing model confidence against a threshold.
- Mechanism: When the model's maximum softmax probability (MSP) falls below a configured threshold, the inference is flagged as potentially drifted.
- Core assumption: Data drift correlates with the model being less confident in its predictions.
- Break condition: If data drift does not reduce model confidence (e.g., label shift without feature shift), the detector may miss the drift.

### Mechanism 2
- Claim: Nazar identifies root causes by mining frequent itemsets from drift log metadata.
- Mechanism: Each drift detection is logged with device metadata (location, weather, device ID). Apriori algorithm finds sets of attributes that co-occur with drift flags. Set reduction and counterfactual analysis eliminate redundant or subsumed causes.
- Core assumption: Root causes of drift are correlated with recurring metadata patterns across multiple devices.
- Break condition: If drift is caused by attributes not captured in the log (e.g., sensor hardware differences), FIM may fail to identify true root causes.

### Mechanism 3
- Claim: Nazar adapts models by-cause using self-supervised entropy minimization.
- Mechanism: For each identified root cause, Nazar fine-tunes the batch normalization layer (and optionally other parameters) by minimizing entropy on the affected data distribution. This avoids catastrophic forgetting and preserves performance on clean data.
- Core assumption: The source of data drift for a specific cause can be isolated and used to adapt the model without harming performance on other data.
- Break condition: If multiple root causes overlap heavily or drift is too rapid, adapting by-cause may be insufficient or too slow.

## Foundational Learning

- Concept: Maximum Softmax Probability (MSP) drift detection
  - Why needed here: Provides a lightweight, unsupervised way to flag potentially drifted inputs on resource-constrained devices.
  - Quick check question: If MSP is 0.95 for a prediction, what does that say about model confidence?

- Concept: Frequent Itemset Mining (Apriori algorithm)
  - Why needed here: Enables discovery of attribute combinations that frequently coincide with drift flags, surfacing root causes without labeled data.
  - Quick check question: Why does apriori start by finding frequent single attributes before building larger sets?

- Concept: Entropy minimization for self-supervised adaptation
  - Why needed here: Allows the model to adapt to drifted data without requiring labels, using the objective that the model should be confident on its own inputs.
  - Quick check question: In TENT, what happens to the model's logits during adaptation?

## Architecture Onboarding

- Component map: Device inference -> MSP threshold detector -> drift log entry -> cloud Aurora database -> Lambda root cause analysis -> GPU adaptation instance -> S3 model store -> device model pull
- Critical path: Device inference → MSP check → log entry → cloud aggregation → FIM + reduction → adaptation → model push → device inference with adapted model
- Design tradeoffs:
  - Threshold vs batch methods: Threshold is simple but noisier; batch methods more accurate but need batching logic and storage.
  - FIM vs clustering: FIM scales linearly with log size and requires no K parameter; clustering may be more flexible but costlier.
  - BN-only vs full model adaptation: BN-only is lightweight and sufficient for accuracy gains; full model adaptation is more expressive but expensive.
- Failure signatures:
  - Drift detector over-alerting → high false positive rate in log
  - Root cause analysis producing many overlapping sets → set reduction/counterfactual logic broken
  - Adaptation not improving accuracy → wrong root cause identified or adaptation not reaching devices
- First 3 experiments:
  1. Run MSP detector on a held-out clean/validation set, sweep threshold, plot precision/recall.
  2. Simulate drift log entries with known ground truth root causes, run FIM + reduction, compare FMS score to ground truth.
  3. Apply TENT adaptation to a corrupted dataset by-cause, compare accuracy vs no-adapt and adapt-all baselines.

## Open Questions the Paper Calls Out

### Open Question 1
- Question: How well would Nazar's detection and adaptation methods perform in federated learning settings where models are trained on-device?
- Basis in paper: The paper mentions that Nazar's principles could be applied to federated learning, but focuses primarily on cloud-trained models.
- Why unresolved: The paper does not evaluate Nazar in a federated learning context, leaving uncertainty about its effectiveness when models are trained on user devices.
- What evidence would resolve it: Running Nazar on federated learning workloads and comparing its accuracy and resource usage to centralized training scenarios.

### Open Question 2
- Question: Can Nazar's root cause analysis identify subtle sources of drift that are not explicitly captured in the drift log metadata?
- Basis in paper: The paper acknowledges that Nazar may group devices by attributes that do not capture the "real" root cause, such as grouping by device model when the actual issue is a specific camera lens manufacturer.
- Why unresolved: The drift log relies on available metadata, which may not include all potential root causes of drift, leading to less precise root cause identification.
- What evidence would resolve it: Conducting experiments where known subtle root causes (e.g., specific hardware components) are intentionally introduced and measuring Nazar's ability to identify them versus grouping by more obvious attributes.

### Open Question 3
- Question: What is the impact of Nazar's model consolidation strategy on long-term accuracy in highly dynamic environments?
- Basis in paper: The paper describes a least recently updated (LRU) algorithm for consolidating model versions but does not evaluate its long-term effects.
- Why unresolved: While the consolidation strategy prevents unbounded model growth, it may evict models that are still relevant for certain devices, potentially degrading accuracy over time.
- What evidence would resolve it: Simulating highly dynamic environments with frequent device turnover and varying drift patterns, then measuring how Nazar's consolidation affects accuracy compared to alternative strategies.

## Limitations
- The confidence threshold method for drift detection may miss certain types of drift like label shift without feature shift
- Root cause analysis is limited to metadata captured in drift logs and may miss subtle hardware-related drift sources
- By-cause adaptation focuses on batch normalization layers which may be insufficient for complex drift patterns

## Confidence
- High confidence: The overall system architecture and end-to-end evaluation results (22% accuracy improvement on all data, 50% on drifted data) are well-documented and reproducible.
- Medium confidence: The confidence threshold method for drift detection and the FIM-based root cause analysis approach are sound but may have edge cases where they fail silently.
- Low confidence: The effectiveness of by-cause adaptation for complex, overlapping drift scenarios and the system's performance under rapid drift conditions need more validation.

## Next Checks
1. Conduct threshold sensitivity analysis by systematically varying the MSP threshold across different drift types and measuring precision/recall trade-offs.
2. Create synthetic drift scenarios with known causes (including those not in metadata) to measure the system's ability to correctly identify all relevant root causes.
3. Apply the system to datasets with multiple overlapping drift causes to measure whether by-cause adaptation maintains performance across all data subsets or degrades on certain combinations.
