# RMIT-ADM+S at the MMU-RAG NeurIPS 2025 Competition

## Quick Facts
- arXiv ID: 2602.20735  
- Source URL: https://arxiv.org/abs/2602.20735  
- Reference count: 38  
- Primary result: Won the NeurIPS 2025 MMU-RAG Competition's Best Dynamic Evaluation award (Open Source category) with a lightweight, dynamic RAG system.

## Executive Summary
The RMIT-ADM+S team introduced Routing-to-RAG (R2RAG), a dynamic retrieval-augmented generation system that adapts its retrieval strategy based on query complexity. Simple queries are processed via a single-pass Vanilla RAG pipeline, while complex queries are handled by an iterative Vanilla Agent that accumulates evidence across multiple retrieval rounds, guided by an LLM-based coverage estimation module. The system achieved top performance in the user-centric, real-time dynamic evaluation setting of the NeurIPS 2025 MMU-RAG Competition, demonstrating that resource-efficient designs using small reasoning-oriented models (Qwen3-4B) on a single consumer-grade GPU can excel at complex, research-oriented tasks. Qualitative user feedback was instrumental in identifying trade-offs between verbosity and depth, directly informing system refinements.

## Method Summary
R2RAG begins with an LLM-based classifier that routes queries as "simple" or "complex." Simple queries follow a Vanilla RAG pipeline: generate query variants, retrieve documents via the ClueWeb22-A API, rerank with a lightweight reranker (Qwen3-Reranker-0.6B), and synthesize an answer with citations. For complex queries, a Vanilla Agent enters an iterative loop: generate query variants, retrieve and rerank documents, then review accumulated documents with an LLM to estimate information coverage. The loop continues until coverage is complete (Cov=1), a token budget (~20,000) is exceeded, or five iterations are reached. All LLM components (classifier, reformulator, reviewer, generator) use the small Qwen3-4B model unquantized, enabling operation on a single consumer GPU. This design balances depth and efficiency, with iterative evidence gathering tailored to complex information needs.

## Key Results
- Won the NeurIPS 2025 MMU-RAG Competition’s Best Dynamic Evaluation award in the Open Source category.
- Achieved top performance using a small unquantized model (Qwen3-4B) on a single consumer-grade GPU, demonstrating resource-efficient excellence.
- Qualitative user feedback revealed a trade-off between verbosity and depth, leading to refinements in the iterative agent’s stopping criteria and presentation.

## Why This Works (Mechanism)

#### Dynamic Query Routing
The system improves efficiency and relevance by routing queries to a single-pass pipeline for simple questions and a multi-step agent for complex ones. An LLM-based classifier inspects the query’s semantic structure (e.g., ambiguity, multi-part nature) to assign it to “simple” or “complex.” Simple queries go to Vanilla RAG; complex queries go to Vanilla Agent. The core assumption is that query complexity, defined by the need for multi-step synthesis, reliably selects the appropriate retrieval depth and reasoning strategy. Evidence includes the classifier prompt in section 3.1 and the competition result validating the routing-based design.

#### Iterative Evidence Accumulation with Coverage Estimation
For complex queries, the Vanilla Agent iteratively searches with query variants and estimates information coverage using an LLM review module. The loop (generate variants → retrieve & rerank → review coverage) stops when coverage is complete (Cov=1), token budget (~20k) is exceeded, or after five iterations. The review module identifies gaps and proposes new queries. This prevents premature termination and improves answer comprehensiveness. Evidence: section 3.3 details the loop and stopping conditions; qualitative feedback indicates the agent handles complex queries effectively despite some verbosity.

#### Resource-Constrained Design with Small Unquantized Models
The system uses small reasoning-oriented LLMs (Qwen3-4B) without quantization to fit on a single consumer GPU while preserving reasoning fidelity. Model selection prioritized memory constraints and long-context reasoning; the 4B model was used unquantized despite reducing the context window to 25k tokens, balancing context capacity and memory use. The assumption is that for the specific tasks (routing, query generation, document review), a 4B model’s reasoning is sufficient and benefits more from being unquantized than a larger quantized model would. Evidence: the abstract and section 3 report that 4-bit quantized larger models yielded weaker performance than the unquantized 4B variant.

## Foundational Learning

#### Query Complexity Classification
**Why needed:** The routing strategy depends on accurately distinguishing simple (factual, single-answer) from complex (multi-perspective, decompositional) queries. Misclassification sends a complex query to a single-pass pipeline, leading to insufficient evidence.
**Quick check:** What are two linguistic or semantic features (beyond intuition) that might indicate a query is “complex” as per the system’s definition?

#### Information Coverage Estimation as a Stopping Criteria
**Why needed:** Unlike fixed-iteration loops, the system aims to halt retrieval when sufficient evidence is gathered, not after N steps. The LLM-based review module must judge completeness across sub-questions and perspectives, a non-trivial reasoning task.
**Quick check:** If a user asks “Compare the economic impacts of renewable vs. fossil fuel subsidies in Germany,” what would indicate Cov=1 in the review module’s judgment?

#### Resource-Performance Trade-offs in LLM Deployment
**Why needed:** The design explicitly targets a single consumer GPU, driving model size selection, context window tuning, and efficiency choices. Understanding this trade-off is key to reproducing the system’s cost-effective yet high-performing nature.
**Quick check:** Why might running a quantized 8B model be less effective for this specific RAG pipeline than an unquantized 4B model, even if the 8B has more parameters?

## Architecture Onboarding
**Component map:**  
Query -> Classifier -> Router -> (Vanilla RAG: Query Variant Generator -> Parallel Retrieval (ClueWeb22-A API) -> Reranker (Qwen3-Reranker-0.6B) -> Answer Generator) OR (Vanilla Agent: [Query Variant Generator -> Retrieval -> Reranker -> Document Review] loop with state (prev_questions, prev_docs_summaries) -> Answer Generator)

**Critical path:** The longest path is for complex queries: Classifier -> (Agent loop: VariantGen -> Retrieval -> Rerank -> Review) repeated -> Answer Generator. Latency is dominated by sequential LLM calls (review, variant generation) and API retrieval latency.

**Design tradeoffs:**  
- Simple vs. Complex Path: A single powerful agent for all queries was rejected due to unnecessary overhead for simple queries, hurting latency.  
- Model Size vs. Capability: Smaller models (4B) fit memory but may lack depth; no quantization preserves reasoning but increases memory footprint.  
- Retrieval Scope: Vanilla RAG limits to ~30 docs for speed; Vanilla Agent allows up to ~25k tokens for depth, risking noise.  
- Coverage Signal: Using an LLM for Cov is flexible but uncalibrated; may over/underestimate completeness.

**Failure signatures:**  
- Classifier error: Simple query routed to Agent ⇒ verbose, slow, over-complicated answer. Complex query to RAG ⇒ shallow, incomplete answer.  
- Review module failure: Cov=1 set too early ⇒ missing key aspects; never set ⇒ token budget exceeded with redundant info.  
- Retrieval failure: No relevant docs returned ⇒ agent must recover via reformulation (prompt-dependent).  
- Reranker misrank: Important document ranked low and truncated ⇒ never seen by generator.

**First 3 experiments:**  
1. Validate classifier routing: Run a held-out set of manually labeled simple/complex queries (e.g., Deep-Research Questions dataset). Measure routing accuracy and correlate with downstream answer quality (LLM-as-judge completeness score).  
2. Stress-test coverage estimation: For complex questions with known multi-aspect answers, run the Agent and manually audit the review module’s is-sufficient decisions and new-query generations at each step. Identify if the prompt consistently identifies gaps or hallucinates sufficiency.  
3. Resource benchmark: Profile end-to-end latency and GPU memory usage for both paths on a standard consumer GPU (e.g., RTX 4090). Measure distribution of iteration counts for complex queries to ensure the 5-iteration cap and 20k token limit are generally sufficient and not frequently hit.

## Open Questions the Paper Calls Out
1. **How accurate and reliable is the LLM-based document review module in estimating information coverage for complex research queries?**  
   *Basis:* The system relies on an LLM (Qwen3-4B) to judge sufficiency after each retrieval iteration, but no validation against human judgments or ground truth is provided.  
   *Why unresolved:* Without knowing the accuracy of this coverage signal, the stopping condition’s effectiveness is questionable; errors could lead to premature termination or wasted resources.  
   *Evidence needed:* A human evaluation study comparing the LLM’s sufficiency judgments to expert human assessments on diverse complex queries.

2. **What specific aspects of RAG system performance are captured by dynamic user-centric evaluations (like MMU-RAG Arena) but are missed by static automatic metrics?**  
   *Basis:* The authors state static metrics did not fully capture qualitative differences in reasoning depth, presentation, and user preference, and that qualitative feedback revealed verbosity-depth trade-offs not apparent in aggregate metrics.  
   *Why unresolved:* The exact qualitative dimensions poorly correlated with static metrics are not detailed, hindering design of better evaluation frameworks.  
   *Evidence needed:* Systematic analysis comparing a wide range of static metrics (ROUGE, BERTScore, faithfulness) with dynamic preference judgments across query types to identify mismatches.

3. **How robust is the LLM-based query classifier to out-of-distribution queries and variations in query phrasing across different domains?**  
   *Basis:* The authors chose an LLM-based classifier over logistic regression because it “can reason about query semantics, better handle out-of-distribution queries,” but no empirical evaluation on diverse or adversarial queries is presented.  
   *Why unresolved:* The classifier’s operational definition (“requires more than a single Google search”) is subjective and may not generalize; misclassification could degrade answer quality.  
   *Evidence needed:* Testing the classifier on a held-out set of queries from various domains (medical, legal, technical) with human annotations of complexity; measure accuracy, consistency, and impact of misrouting on final answer quality.

4. **What are the optimal stopping criteria for iterative RAG systems like the Vanilla Agent, balancing information sufficiency, computational cost, and response timeliness?**  
   *Basis:* The system uses heuristic thresholds: token count >20k OR coverage=1 OR iterations ≥5, with coverage signal from an LLM review. No analysis of threshold choice or effectiveness is provided.  
   *Why unresolved:* Thresholds may be suboptimal; e.g., 20k tokens might be insufficient for some topics, while 5 iterations might be excessive for others; coverage reliability affects this.  
   *Evidence needed:* Ablation study varying thresholds (token limit, iteration cap) and measuring answer quality, user satisfaction, resource usage; explore adaptive thresholds based on query characteristics.

## Limitations
- **Unvalidated internal signals:** The LLM-based classifier’s definition of “complex” and the coverage estimation signal lack empirical validation against ground truth or human judgment.
- **Narrow resource comparison:** The claimed advantage stems from comparing unquantized 4B vs. quantized 8B models; broader comparisons with other efficient architectures (e.g., distilled models, alternative quantization schemes) are absent.
- **Non-quantitative user feedback:** Qualitative feedback used for refinements is not quantified and may not generalize across user populations or query domains.

## Confidence
- **Dynamic Query Routing improves efficiency/relevance:** Medium  
- **Iterative coverage estimation ensures comprehensiveness:** Medium  
- **Small unquantized models enable top performance on consumer hardware:** High  

## Next Checks
1. **Classifier Audit:** Evaluate routing accuracy on a held-out, manually labeled benchmark of research queries (e.g., TREC Complex Answer Retrieval). Measure correlation between misrouting rate and downstream answer quality degradation.
2. **Coverage Signal Calibration:** For complex questions with known multi-facet answers, have human experts judge the LLM review module’s sufficiency decisions and new-query relevance at each iteration. Compute agreement metrics (e.g., Cohen’s κ).
3. **Efficiency Benchmark Replication:** Re-run the full pipeline on a standard consumer GPU (e.g., RTX 4090), reporting latency and memory footprint distributions for both paths. Compare against a quantized 8B variant using the same prompts to isolate quantization vs. size effect.
