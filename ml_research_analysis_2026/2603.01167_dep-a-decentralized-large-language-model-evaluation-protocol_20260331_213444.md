# DEP: A Decentralized Large Language Model Evaluation Protocol

## Quick Facts

- **arXiv ID**: 2603.01167
- **Source URL**: https://arxiv.org/abs/2603.01167
- **Reference count**: 40
- **Primary result**: DEP introduces a decentralized client-server protocol that isolates ground truth data to prevent contamination, enables plug-and-play benchmark reuse with near-zero integration effort, and has been adopted for over 60 benchmarks.

## Executive Summary

Large language model (LLM) evaluation suffers from benchmark fragmentation and test-set contamination, undermining reproducibility and fair comparison. This paper presents DEP (Decentralized Evaluation Protocol), a server-based architecture that separates benchmark owners (servers) from evaluation clients. Benchmark data and scoring logic remain exclusively on the server, while clients only send model outputs and receive scores, thereby preventing leakage at the architectural level. The DEP Toolkit implements the protocol with features like breakpoint resume, congestion control, and automatic discovery. A user study demonstrates drastic reductions in integration effort: reusing an existing DEP benchmark required 3 minutes and 0 lines of code versus 45 minutes and 109 lines for manual implementation. Large-scale evaluations across 12 LLMs and 10 benchmarks confirm DEP's practicality, uncovering scaling trends and safety-performance gaps without data contamination. As of February 2026, over 60 benchmarks have been adapted to DEP, indicating growing ecosystem adoption.

## Method Summary

DEP defines a standardized communication protocol between an evaluation client and a benchmark server. The client (installed via the `llmdep` CLI) orchestrates the evaluation: it invokes an LLM adapter to obtain model outputs for each test instance, then sends these outputs to the benchmark server’s evaluation endpoint. The server internally loads the original dataset files (e.g., Parquet, JSONL), formats prompts, computes metrics (accuracy, F1, LLM-as-a-judge, etc.), and returns only the scores, never exposing ground truth. The client handles lifecycle management, breakpoint resume, concurrency, and congestion control (e.g., token bucket algorithm). To use DEP, one installs the toolkit, obtains a DEP-compliant benchmark server (either by adapting a dataset following the protocol or downloading an existing one), and runs `dep-evaluate --benchmark <name> --model <model>`. The protocol’s decoupled design ensures that any compliant server can interoperate with any LLM adapter, solving fragmentation.

## Why This Works (Mechanism)

### Architectural Isolation for Contamination Prevention
- **Claim**: By confining benchmark data and evaluation logic to the server side, DEP prevents clients and LLMs from accessing answer keys, making test-set contamination architecturally impossible unless the server is compromised.
- **Mechanism**: The client submits only model-generated responses to the server. The server internally compares these against the ground truth and returns computed scores. No raw dataset or answer key ever leaves the server. This structural separation blocks reverse-engineering through score queries under the assumption that score patterns alone cannot reveal full answers.
- **Break condition**: The protection fails if a malicious server operator intentionally leaks ground truth, or if side-channel information (e.g., error messages) inadvertently reveals answers.

### Near-Zero Reuse via Server Standardization
- **Claim**: Once a benchmark is packaged as a DEP server, any user can evaluate on it without writing code, drastically reducing integration effort and encouraging standardization.
- **Mechanism**: Benchmark authors adapt their dataset into a server that implements the DEP interface (data loading, prompt formatting, scoring, Dataset Card). The client auto-discovers these servers and treats them uniformly. Users only need to specify the benchmark and model; the client handles all communication.
- **Break condition**: Protocol updates that break backward compatibility, or server deprecation without migration, could raise barriers again.

### Unified Protocol for Fragmentation Mitigation
- **Claim**: A fixed request/response schema allows heterogeneous benchmarks and LLMs to interoperate seamlessly, addressing fragmentation.
- **Mechanism**: The client and servers exchange standardized JSON messages with status codes (e.g., 200, 429). The client automatically retries on transient failures, respects rate limits, and selects appropriate adapters. This common interface decouples the specific benchmark implementation from the evaluation engine.
- **Break condition**: Non-compliant servers or adapters that violate the protocol specifications would break interoperability; ambiguous specifications could lead to divergent implementations.

## Architecture Onboarding

**Component map**:  
Client -> LLM Adapter -> Benchmark Server; Optional: Client <-> Matching Server Platform (for discovery)

**Critical path**:
1. User installs the `llmdep` toolkit.
2. User obtains a DEP-compliant benchmark server (local directory or remote URL).
3. Client auto-discovers servers via directory scan (Dataset Cards) or configuration.
4. Client invokes LLM Adapter to generate outputs for each input.
5. Client sends outputs to the Benchmark Server’s evaluation endpoint.
6. Server computes scores and returns structured results; client aggregates and displays.

**Design tradeoffs**:
- Decentralization vs. availability: Servers may be offline; users rely on server uptime but gain privacy and control.
- Flexibility vs. standardization: Servers can use any internal data format but must conform to the external DEP interface, balancing author freedom with client interoperability.
- Security vs. transparency: Remote servers hide ground truth but reduce auditability; local mounting offers transparency but risks leakage if misused.

**Failure signatures**:
- Server unreachable or timeout: Client logs an error, suggests retry or server status check.
- Protocol mismatch (invalid JSON, missing fields): Client rejects server during discovery; check Dataset Card compliance.
- Congestion control triggered (status 429): Client automatically reduces request rate; may indicate server overload or API limits.
- Benchmark server returns incorrect scores: Usually a server-side bug; requires debugging the evaluation logic, not the client.

**First 3 experiments**:
1. **Local Server Smoke Test**: Run an example server (e.g., IFEval) locally, use `llmdep` to evaluate a tiny model (e.g., Qwen3-0.6B) on 2 samples, verify scores appear and ground truth is not exposed.
2. **Remote Server Connection**: Deploy a server on another machine or use a hosted one, configure client with its URL, submit evaluations and confirm the client cannot access raw dataset files.
3. **Adapt a New Benchmark**: Take a simple JSONL benchmark (e.g., BoolQ subset), follow DEP docs to create a server with `data_loader` and `evaluator`, test with client, and measure time/LoC against manual implementation.

## Open Questions the Paper Calls Out

- **Question 1**: How can DEP be extended to evaluate LLM-based agents with complex external interactions (e.g., executing code within Docker environments)?  
  *Basis*: The paper explicitly states DEP cannot yet evaluate agents requiring such interactions. *Why unresolved*: The current protocol is designed for static input-output evaluations, not dynamic, multi-step agent-environment interactions. *Resolution evidence*: A protocol extension for standardized agent action spaces, environment APIs, and trajectory logging validated on benchmarks like WebArena.

- **Question 2**: What incentive structures or governance models can ensure sustainable community contributions to maintain and expand the ecosystem of DEP-compliant benchmark servers?  
  *Basis*: The paper acknowledges that DEP’s effectiveness depends on contributions from benchmark authors, which introduces extra integration workload. *Why unresolved*: Volunteer-driven ecosystems risk stagnation or uneven coverage. *Resolution evidence*: An analysis of contributor motivations in similar ecosystems and an implemented framework (e.g., credentialing, citation tracking, micro-grants) that demonstrably increases contribution rates and benchmark diversity.

- **Question 3**: Do heterogeneous custom evaluation modules within DEP benchmark servers introduce hidden variability that undermines cross-benchmark model comparability?  
  *Basis*: DEP permits custom-defined metrics and does not mandate standardized validation of server-side evaluation logic, allowing divergent implementations. *Why unresolved*: Identical model outputs might yield different scores across servers due to post-processing differences, confounding performance rankings. *Resolution evidence*: A systematic study scoring a fixed set of LLM outputs across multiple DEP servers for the same task, quantifying score variance attributable to implementation differences.

- **Question 4**: Are the significant reductions in time and code effort reported in the user study generalizable to a broader, more diverse population of LLM practitioners?  
  *Basis*: The study involved only 8 participants with undergraduate degrees and LLM research backgrounds, a small homogeneous sample. *Why unresolved*: Selection bias and limited statistical reliability raise doubts about real-world adoption across academia and industry. *Resolution evidence*: A large-scale, multi-site replication with a stratified sample of users (students, industry engineers, researchers) evaluating a wider array of benchmarks, using mixed methods to assess quantitative and qualitative usability.

## Limitations

- **Contamination prevention** remains a theoretical guarantee; the paper provides no adversarial security audit or side-channel analysis (confidence: Medium).
- **Fragmentation solution** lacks empirical metrics showing reduced benchmark diversity or increased reuse chains; simple count of adapted benchmarks does not prove the problem is solved (confidence: Low).
- **Long-term sustainability** of the decentralized ecosystem is uncertain; server deprecation, protocol drift, or malicious operators could undermine the system, yet these risks are unaddressed (confidence: Low).

## Confidence

- Data isolation via server confinement: Medium
- Near-zero reuse cost via pre-adapted benchmarks: High
- Unified protocol solving fragmentation: Low
