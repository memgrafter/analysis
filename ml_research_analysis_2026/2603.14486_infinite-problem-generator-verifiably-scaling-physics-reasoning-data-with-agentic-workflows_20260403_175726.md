# Infinite Problem Generator: Verifiably Scaling Physics Reasoning Data with Agentic Workflows

## Quick Facts
- **arXiv ID:** 2603.14486
- **Source URL:** https://arxiv.org/abs/2603.14486
- **Reference count:** 40
- **Primary result:** From 165 expert seeds, IPG generated 1,335 physics problems with 99.85% verification success and identified a linear complexity blueprint (R²≈0.95) enabling controllable difficulty.

## Executive Summary
The Infinite Problem Generator (IPG) addresses the scarcity of verifiable physics reasoning data by synthesizing problems with guaranteed solvability. It encodes physics formulas as executable Python functions (Formula-as-Code) and employs an agentic generate-then-verify workflow to produce problems whose solutions are verified by execution. From 165 seed problems, IPG generated ClassicalMechanicsV1: 1,335 problems spanning 102 unique formulas, with 99.85% verification success. It also discovers a Complexity Blueprint: a linear correlation (R²≈0.95) between formula count and solution code length, enabling controllable difficulty. Zero-shot evaluation with Qwen3-14B yields 34.96% accuracy on IPG vs. 47.97% on JEEBench, demonstrating its rigor as a physics reasoning benchmark.

## Method Summary
IPG uses a three-phase agentic pipeline. Phase I (Problem Analysis) processes each seed tuple to extract relevant chapters, variable ranges, and generate six alternate scenarios. Phase II (Constrained Generation) selects a scenario and a subset of 3–5 formulas from the chapter dictionary, designates one variable as unknown, and produces a problem JSON. Phase III (Code Verification) generates a `solve()` function that must use only the selected formulas, executes it in a sandbox, and checks for syntactic validity, numerical solvability, and physical sanity. Failures trigger retries with structured error traces. A signature hash (formula set + unknown variable) ensures uniqueness across generations. This closed-loop approach yields a large dataset with high verification success.

## Key Results
- **Generated dataset:** ClassicalMechanicsV1 contains 1,335 problems covering 102 unique formulas, averaging 3.05 formulas per problem, with 99.85% verification success.
- **Complexity Blueprint:** Strong linear correlation (R²≈0.95) between formula count (pre-set budget) and solution code length, enabling controllable difficulty.
- **Benchmark rigor:** Zero-shot Qwen3-14B accuracy is 34.96% on IPG, compared to 47.97% on JEEBench, indicating greater challenge.

## Why This Works (Mechanism)
### Mechanism 1: Formula-as-Code Guarantees
**Claim:** Representing physics axioms as executable Python functions ensures mathematical consistency and solvability.  
**Mechanism:** Physics formulas are pre-defined as Python functions (e.g., `kinematics.final_velocity(u, a, t)`). During generation, solutions must call only these verified functions. The resulting code is executed in a sandbox; only outputs that are finite and physically plausible (e.g., `t > 0`) are accepted. This imposes a hard constraint that the problem's logical structure must map to executable, numerically consistent mathematics.  
**Evidence:** [abstract], [section 3.1.2] describe the design; [section 3.4] lists the three verification criteria; corpus shows 99.85% verification success and only 2 NaN/∞ cases [section 5].  
**Break condition:** If higher-order constraints (e.g., conservation laws) are violated despite range checks, verification is insufficient—acknowledged for N≥5 formulas [section 6].

### Mechanism 2: Agentic Generate-then-Verify Workflow
**Claim:** An iterative generation loop with execution feedback mitigates hallucinations.  
**Mechanism:** The pipeline (Problem Analysis → Constrained Generation → Code Verification) is iterative. Failed attempts (execution errors, signature collisions) trigger structured reprompting with the specific error trace (Appendices C.4, C.6). This closed loop forces the agent to correct reasoning based on objective runtime feedback, rather than discarding failed generations silently.  
**Evidence:** [abstract] mentions Program-of-Thought verification; [section 2.3] describes integration into the generation loop; [section 4.1.2] details the internal retry loop; corpus shows 22–122 LLM calls per accepted problem [section 4.1.2].  
**Break condition:** If error traces are ambiguous or the model cannot reliably parse them, the retry loop becomes ineffective, leading to high rejection rates or superficial fixes.

### Mechanism 3: Complexity Blueprint
**Claim:** The Complexity Blueprint establishes code length as a proxy-free, controllable metric for problem difficulty, enabling curriculum generation.  
**Mechanism:** A strong linear correlation (R²≈0.95) exists between the number of required formulas (the *a priori* complexity knob) and the character length of the solution code. Because code length is derived from execution, it reflects actual logical steps, not just declared formula count. This allows setting a target code length to generate problems of desired difficulty without human labeling.  
**Evidence:** [abstract] states the correlation; [section 5.3] discusses the consistent "cost" per formula; [appendix F] clarifies that formula count is an input constraint; [corpus] Figure 2 shows the linear fit across 1,335 data points.  
**Break condition:** If in new domains (e.g., electromagnetism) code length scales non-linearly due to more complex dependencies (e.g., vector calculus), the blueprint fails as a universal proxy.

## Foundational Learning
### Concept: Program-of-Thought (PoT)
**Why needed here:** IPG relies on code execution to verify solvability; understanding that reasoning is offloaded to a Python interpreter (not just text generation) is key to grasping why hallucinations are reduced.  
**Quick check question:** Why might generating executable code, rather than a natural language reasoning chain, provide a stricter correctness test for a physics problem?

### Concept: Agentic Workflow
**Why needed here:** IPG is not a single-shot generator but a multi-stage pipeline with feedback loops. Recognizing the phases (analysis, generation, verification) and their handoffs is essential to understanding its robustness.  
**Quick check question:** What is the functional role of the "Problem Analysis" phase, and how does its output constrain the subsequent "Constrained Generation"?

### Concept: Formula Budgeting as Complexity Control
**Why needed here:** The complexity blueprint hinges on the idea that difficulty is set *before* generation by specifying how many formulas must be used. This contrasts with post-hoc difficulty estimation.  
**Quick check question:** How does instructing the model to "select 3-5 formulas" during generation differ from simply counting formulas after a problem is generated?

## Architecture Onboarding
The system comprises the following components: Seed Tuple Processor, Chapter Dictionary & Formula Library, Constrained Generator (LLM Agent), Code Generator & Sandbox, and Retry & Uniqueness Manager.  
**Critical path:** Seed → Analysis → Formula/Scenario Selection → Problem Generation → Code Generation → Execution → Accept. Failures trigger Error → Retry. Uniqueness signature check runs in parallel to generation.  
**Design tradeoffs:**  
- *Verification rigor vs. throughput:* The 22–122 calls per problem (section 4.1.2) show high computational cost for 99.85% validity.  
- *Formula library granularity:* Too coarse (few large formulas) limits mixing; too fine (many tiny functions) may force unnatural problem structures. The paper uses mid-level axioms.  
- *Controlled variability vs. creativity:* The round-robin scenario selection (section 3.3) ensures diversity but may cap narrative novelty.  
**Failure signatures:**  
- **Signature collision:** Duplicate `(formula set, unknown variable)` detected → regenerate.  
- **Execution failure:** `SyntaxError`, `NameError`, or `None` return from `solve()` → reprompt with error trace.  
- **Physical sanity failure:** Output violates `range` constraints (e.g., `mass < 0`) → reprompt.  
- **Low complexity (<2 formulas):** Pruned post-generation as "trivial" (section 5.6).  
**First 3 experiments:**  
1. **Smoke test:** Run a single seed (e.g., a kinematics problem) through the full pipeline. Verify that the output problem's signature matches the intended formula set and that the code executes to a plausible number.  
2. **Blueprint validation:** Sample 50 problems across 2–6 formula counts. Plot their code lengths. Confirm linear trend (`R² > 0.9` locally) to validate the blueprint on your domain expansion.  
3. **Uniqueness stress test:** Generate 10 variations from one seed. Check that all signatures are unique and that narratives differ lexically (TTR > 5%). If collisions occur, adjust scenario selection or formula subset size.

## Open Questions the Paper Calls Out
- **Integration of formal constraint solvers:** How can IPG integrate formal constraint solvers (e.g., Z3) to enforce conservation laws and eliminate semantic hallucinations in high-complexity problems? *Basis:* Limitations section; *Why unresolved:* Current execution checks miss physics-impossible solutions that are numerically valid, especially with ≥4 formulas. *Resolution evidence:* Add Z3 checks during verification, measure decrease in "physics impossibilities" errors from taxonomy on complex subset.  
- **Extension to continuous mathematics:** Can the Formula-as-Code paradigm be extended to physics domains requiring continuous mathematics (e.g., Electromagnetism) without sacrificing verification success rates? *Basis:* Future Work; *Why unresolved:* The current Python function interface handles discrete formulas; continuous domains need differential/integral operations, which may not be executable in the same framework. *Resolution evidence:* Prototype for a continuous subdomain (e.g., Coulomb’s Law with charge distributions), generate problems, and report execution success rate and formula count distribution.  
- **Cross-LLM robustness:** Is the IPG framework equally effective when powered by different LLMs, or does the Complexity Blueprint depend on Gemini-specific behaviors? *Basis:* Appendix J; *Why unresolved:* Different LLMs may vary in following formula budgets, affecting code length correlation and verification rates. *Resolution evidence:* Replicate generation with 3+ LLMs (e.g., GPT-4, Claude, Llama) on same seeds; compare verification success, average formulas, and R² of code-length vs. formula count.

## Limitations
- **Non-released resources:** The exact 165 seed problems, complete Formula-as-Code library, and chapter dictionary are not published, hindering exact replication.  
- **Domain-specific blueprint:** The Complexity Blueprint's linear correlation is validated only on classical mechanics; it may fail in domains with vector calculus or coupled differential equations.  
- **Incomplete verification:** The current execution checks (syntax, solvability, physical sanity) may miss higher-order constraints (e.g., conservation laws) for problems with ≥5 formulas.

## Confidence
- **Guaranteed Solvability:** High (99.85% pass rate, only 2 NaN/∞ cases).  
- **Agentic Workflow Efficacy:** Medium (robust but costly; retry logic depends on LLM's error parsing).  
- **Complexity Blueprint Validity:** Medium (strong R²≈0.95 in one domain; lacks cross-domain evidence).  
- **Benchmark Rigor:** Medium (lower model accuracy suggests difficulty; but no human baseline or multi-model evaluation).

## Next Checks

2. **Conservation Law Stress Test:** For all problems with ≥5 formulas, augment execution checks with energy/momentum conservation. Report violation rate; accept only if ≤0.5%.
