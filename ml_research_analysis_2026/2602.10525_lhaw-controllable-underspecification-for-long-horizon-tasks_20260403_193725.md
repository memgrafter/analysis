# LHAW: Controllable Underspecification for Long-Horizon Tasks

## Quick Facts
- arXiv ID: 2602.10525
- Source URL: https://arxiv.org/abs/2602.10525
- Reference count: 40
- Primary result: Generates 285 controllably underspecified task variants; underspecification causes up to 60% drop in pass@3 on outcome-critical variants; an ask_user tool partially recovers performance; introduces Gain/Q metric for cost‑sensitive clarification evaluation.

## Executive Summary
LHAW addresses the challenge of studying how missing information (underspecification) impacts long‑horizon agent workflows. The core contribution is a synthetic pipeline that transforms well‑specified tasks into underspecified variants by systematically removing information across four dimensions: Goals, Constraints, Inputs, and Context. The pipeline uses an LLM to segment the original prompt, scores segments by criticality and guessability, and applies removal strategies (DELETE, VAGUIFY, GENERICIZE). Each candidate variant is then validated through multiple independent agent trials; based on terminal state divergence, it is classified as outcome‑critical (no success), divergent (successes but varied outcomes), or benign (consistent success). Applying this to three benchmarks (THEAGENTCOMPANY, SWE‑Bench Pro, MCP‑Atlas) yields 285 variants.

Evaluation with frontier models shows underspecification severely degrades performance, with outcome‑critical variants nearly always failing. Adding an ask_user tool allows agents to recover a substantial fraction of the lost performance, demonstrating that clarification helps but is not always sufficient. Analysis of clarification behavior via the Gain/Q metric (performance gain per question) reveals divergent model strategies: GPT‑5.2 asks many questions with low efficiency, while Gemini models achieve higher efficiency but under‑clarify. LHAW thus provides the first systematic, cost‑sensitive framework for evaluating agent clarification in long‑horizon settings.

## Method Summary
The pipeline begins by filtering benchmark tasks using baseline competence: for each task, pass@3 is measured with a set of reference models (e.g., Sonnet‑4.5, GPT‑5.2, Gemini‑3‑Flash for THEAGENTCOMPANY; two or three models for others). Tasks that are too hard or too easy are discarded. For retained tasks, an LLM (Gemini‑3‑Flash) extracts atomic removable segments from the fully‑specified prompt, optionally using grounding data such as golden trajectories or checkpoint specifications. Each segment is labeled with a dimension (Goals, Constraints, Inputs, Context), a criticality score (failure if the segment is wrong) and a guessability score (how inferable it is from context). The priority score is criticality × (1–guessability). Candidate underspecified variants are generated by selecting one or two high‑priority segments and applying a removal strategy—DELETE (complete omission), VAGUIFY (replace with ambiguous reference), or GENERICIZE (replace with a generic placeholder)—while preserving grammaticality.

Each candidate undergoes empirical validation: the variant prompt is executed n=3 times with a frontier model (ask_user tool disabled). The agent’s terminal state, encoded as a tuple of checkpoint success/failure outcomes, is recorded. Classification follows Definition 3.1: outcome‑critical (0 successes), divergent (>0 successes and >1 distinct terminal state), benign (>0 successes and exactly 1 distinct terminal state), or new task (0 successes and exactly 1 distinct terminal state; filtered out by an LLM judge). The final benchmark is sampled to balance classes, dimensions, and datasets, resulting in 285 variants. This empirical classification ensures underspecification severity is measured by actual agent behavior rather than LLM‑based ambiguity prediction.

## Key Results
- Underspecification leads to severe performance drops; outcome‑critical variants reduce pass@3 by up to 60% relative to the fully‑specified baseline.
- The ask_user tool restores a substantial portion of the lost performance, but full recovery is rare, indicating limits of single‑turn clarification.
- Frontier models exhibit distinct clarification strategies: GPT‑5.2 asks the most questions but yields low Gain/Q (inefficient), while Gemini models achieve higher Gain/Q yet ask fewer questions, suggesting under‑clarification.
- The Gain/Q metric successfully captures cost‑sensitive clarification efficiency and varies with simulated user cost personas (Supervisor, Standard, Executive).

## Why This Works (Mechanism)

### Mechanism 1: Systematic Removal for Controllable Underspecification
LHAW generates underspecified variants by removing information across four dimensions (Goals, Constraints, Inputs, Context). The three‑phase pipeline is: (1) Segment Extraction – an LLM identifies atomic removable segments, scoring each for criticality (failure if the segment is wrong) and guessability (how inferable from context); priority = criticality × (1–guessability). (2) Candidate Generation – for high‑priority segments, the system applies DELETE, VAGUIFY, or GENERICIZE while preserving grammaticality. (3) Empirical Validation – candidate variants run through multiple agent trials; terminal state divergence determines classification. The core assumption is that removable segments exist in well‑specified prompts and their removal yields ambiguous tasks without altering the fundamental intent. Evidence includes the detailed pipeline description (Sec 3.3) and validation showing predictable difficulty curves from severity. Break condition: if segment extraction fails to identify truly atomic segments or if removal inadvertently creates a valid alternative task (mitigated by the new‑task filter).

### Mechanism 2: Empirical Classification Based on Terminal State Divergence
The impact of underspecification is measured by executing agents rather than by LLM prediction. For each candidate, n independent trials are run, collecting the set S of distinct terminal states (checkpoint success tuples). Definition 3.1 classifies: outcome‑critical (c=0 successes), divergent (c>0 and |S|>1), benign (c>0 and |S|=1). Variants with c=0 and |S|=1 are “new tasks” and filtered out. This assumes that divergent terminal states among runs reliably indicate underspecification severity: agents take different (often wrong) paths due to missing information. Evidence: The classification rule is explicitly defined and used throughout; experiments show different removal strategies produce consistent outcome‑critical/divergent rates (Sec 3.4). Break condition: high agent stochasticity or unreliable terminal‐state equivalence could misclassify variants.

### Mechanism 3: Cost‑Sensitive Clarification via Gain/Q
LHAW evaluates clarification by equipping agents with an ask_user tool and computing Gain/Q = (Pass@3 improvement %) / (average questions per trajectory). This metric isolates efficiency: models asking many questions with little gain have low Gain/Q; those asking few highly informative questions have high Gain/Q. The simulator’s answers are grounded in the originally removed information to ensure factual correctness. Core assumption: the value of a clarification question is proportional to its marginal contribution to task success. Evidence: Table 3 and Figure 4 show GPT‑5.2 has high Ask% but low Gain/Q, while Gemini models achieve higher Gain/Q; persona‑based cost experiments further modulate Ask% and Gain/Q (Sec 4.2–4.3). Break condition: simulator hallucinations or non‑actionable questions would make Gain/Q a noisy proxy.

## Architecture Onboarding

### Component Map
Core pipeline: Segment Extraction → Candidate Generation → Empirical Validation → Benchmark Release  
Supporting systems: User Simulator (ask_user MCP tool), Agent Harness (OpenHands for THEAGENTCOMPANY, SWE‑agent for SWE‑Bench Pro, MCP client for MCP‑Atlas)  
Data flow: Original Task → Segment Extraction → Variant Prompt → Agent Trials (via Harness) → Terminal State Logs → Classification (Def 3.1) → Benchmark Release

### Critical Path
1. Task selection based on baseline competence filters (e.g., TAC tasks need average checkpoint accuracy ≥50% across reference models).
2. Segment extraction with grounding data (golden trajectories or checkpoints) to produce segments with criticality and guessability scores.
3. Candidate generation using one or two high‑priority segments and a chosen removal strategy (DELETE/VAGUIFY/GENERICIZE); preserve grammar and formatting.
4. Run n=3 independent agent trials per variant (ask_user disabled); collect terminal state tuples.
5. Apply Definition 3.1 classification; filter out “new tasks” using an LLM judge.
6. Sample final benchmark with balanced distribution across classes, dimensions, and datasets, yielding 285 variants.

### Design Tradeoffs
- Removal strategy: DELETE makes missing info obvious (agents may ask); VAGUIFY creates ambiguous references that may lead to confident wrong assumptions; GENERICIZE replaces with generic placeholders.
- Severity: Single‑segment removal yields clearer ambiguity with lower risk of creating a new valid task; multi‑segment increases difficulty but raises the chance of inadvertently defining a solvable alternative task.
- Empirical validation cost: More trials improve classification reliability (reducing misclassification due to agent stochasticity) but increase compute budget; the paper uses n=3 as a pragmatic balance.

### Failure Signatures
- New task leak: A variant where all trials converge on a non‑successful but consistent state, indicating the removal created a valid albeit different task (should be filtered by the new task judge).
- User simulator hallucination: The ask_user simulator provides answers that include information not present in the original task, artificially boosting performance.
- Agent stochasticity: High variance in terminal states for a truly outcome‑critical variant, potentially misclassifying it as divergent; may require more trials or a more deterministic agent.
- Prompt overfitting: The agent’s system prompt is modified to overly encourage using ask_user, distorting natural clarification behavior and invalidating cost‑sensitive analysis.

### First 3 Experiments
1. Segment extraction sanity check: Run extraction on a single TAC task (e.g., ds‑format‑excel‑sheets); manually inspect extracted segments for correct dimension labeling and plausible criticality/guessability scores. Removing a top‑priority segment and running a few trials should cause near‑zero pass@3.
2. Strategy comparison: Generate 1‑segment variants for the same base task using DELETE, VAGUIFY, and GENERICIZE; run 3 trials with a fixed model (e.g., Gemini‑3‑Flash) and compare pass@3. Expect VAGUIFY to yield the lowest success due to ambiguity without explicit omission.
3. Gain/Q measurement: On a subset of MCP‑Atlas outcome‑critical variants, run GPT‑5.2 with ask_user enabled; compute average questions per trajectory and pass@3 improvement. Verify Gain/Q is low (<0.1) as reported.

## Open Questions the Paper Calls Out

1. **How can LHAW be extended to generate underspecification at the environment level?**  
   *Basis*: Future work includes “creating more types of ambiguity, including at the environment level.”  
   *Why unresolved*: The current pipeline only manipulates the prompt; real‑world agents often face ambiguous sensory input.  
   *Resolving evidence*: Implement components that insert ambiguity into observation streams (e.g., partial tool outputs) and measure agent behavior.

2. **What is an appropriate quantitative model for user interruption cost in long‑horizon workflows, and how can it be integrated into a decision‑theoretic framework for clarification?**  
   *Basis*: The authors state they “do not explicitly quantify the cost of user interaction” and call for incorporating calibrated user‑time costs.  
   *Why unresolved*: Without calibrated costs, agents cannot make rational trade‑offs between clarification and execution.  
   *Resolving evidence*: Experimental studies measuring real user interruption costs and implementing agents that optimize expected value of information minus cost.

3. **Why do frontier models exhibit divergent clarification strategies (e.g., GPT‑5.2 over‑clarifying vs. Gemini under‑clarifying), and what factors predict efficient clarification?**  
   *Basis*: Table 3 and Figure 4 show GPT‑5.2 has highest Ask% but lowest Gain/Q, while Gemini‑3‑Pro has highest Gain/Q on TAC; the paper notes this pattern but does not explain it.  
   *Why unresolved*: Understanding root causes could inform model design or prompting to achieve optimal clarification efficiency.  
   *Resolving evidence*: Ablation studies varying model architecture, size, or training; analyzing internal representations of uncertainty.

4. **How can we systematically generate and evaluate long‑horizon tasks with semantic ambiguity (multiple valid interpretations) as opposed to underspecification?**  
   *Basis*: The authors state that “our work focuses entirely on underspecification rather than semantic ambiguity.”  
   *Why unresolved*: Semantic ambiguity is common in real‑world tasks and requires different handling.  
   *Resolving evidence*: Extend the taxonomy to include ambiguity types, create synthetic generators for semantic variants (e.g., ambiguous verbs, cultural references), and measure agent disambiguation.

5. **How realistic is the ask_user tool simulation, and would agent clarification performance hold with real human users who may provide incomplete or incorrect answers?**  
   *Basis*: The user simulator is an LLM constrained to removed segments; real users may not cooperate perfectly—a known limitation not fully addressed.  
   *Why unresolved*: If agents are tuned to an idealized user, performance may degrade with humans.  
   *Resolving evidence*: Conduct a human study where real users answer agent questions on underspecified tasks, comparing to simulator results.

## Limitations
- Implementation details (model versions, extraction prompts, harness configurations) are incompletely specified, risking reproducibility drift.
- Empirical classification relies on terminal state equivalence, which may be brittle if checkpoints are unstable or agents exhibit high stochasticity.
- The ask_user simulator may not perfectly restore removed information; hallucinations or off‑target answers could bias the Gain/Q metric.
