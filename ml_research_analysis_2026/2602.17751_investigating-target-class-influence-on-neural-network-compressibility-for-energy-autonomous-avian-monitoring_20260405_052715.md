# Investigating Target Class Influence on Neural Network Compressibility for Energy-Autonomous Avian Monitoring

## Quick Facts
- **arXiv ID:** 2602.17751
- **Source URL:** https://arxiv.org/abs/2602.17751
- **Reference count:** 32
- **Primary result:** High compression rates (82–88% in FLOPs, ROM, RAM) with minimal accuracy loss across 2–501 bird species classes; deployment feasible on Cortex-M7 and Raspberry Pi 4 for energy-autonomous operation, but not on Cortex-M4.

## Executive Summary
This paper explores compressing neural networks for real-time, energy-autonomous bird sound classification on microcontrollers. Using the MCUNet framework, models were trained and compressed for 2 to 501 target bird species (plus a non-avian class) and benchmarked on ARM Cortex-M4, Cortex-M7, and Raspberry Pi 4 hardware. The study finds that compression rates remain high (82–88%) across all class counts with little accuracy loss. However, inference latency and energy consumption increase with more classes, making the Cortex-M4 infeasible for most cases while the Cortex-M7 and Raspberry Pi 4 can operate autonomously with modest solar power (e.g., ~0.07 m² panel for a 31-class model in December).

## Method Summary
The authors assembled a dataset from Xeno-Canto and ESC-50, preprocessing audio into 2-second mel-spectrograms (64 bands, FFT 512, hop 384) with augmentations. A modified MobileNetV2 (`mcunet-in4`) was trained as a baseline for each class count. Edge models were compressed using an internal Fraunhofer tool that interleaves pruning with quantization-aware training (50 trials per class count). Pareto-optimal models were selected via a ranking function balancing memory and accuracy (`rank = mem + acc`). These models were converted to C code, flashed onto the target hardware, and benchmarked for latency and energy. Finally, measured power figures (active/sleep) and a 10% duty cycle were used to estimate battery and solar panel requirements for 48-hour autonomy.

## Key Results
- Compression rates of 82–88% in FLOPs, ROM, and RAM were sustained across all class counts with negligible accuracy drop.
- Latency and energy per inference increased with the number of target classes, though a slight compressibility improvement beyond 151 classes partially mitigated this.
- The Cortex-M4 was too slow for all models; Cortex-M7 and Raspberry Pi 4 were feasible, with a 31-class model requiring a 6.6 Wh battery and a 0.07 m² solar panel in December.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Increasing target bird species classes initially reduces compressibility (compression rate) but may improve it for very large class counts (>151).
- **Mechanism:** More classes increase the final classification layer's complexity and demand more discriminative features, potentially yielding a larger, less compressible network. However, with many classes, the model might learn more generic, shared features, which could be more efficiently compressed.
- **Evidence:** Section 3 notes a slight decline in compressibility with increasing classes, reversing from 201 classes onward, though the overall variation is minor (82–88% range).
- **Break condition:** The non-monotonic trend is subtle and based on a single architecture (`mcunet-in4`); a different architecture, dataset, or compression method may show a different relationship.

### Mechanism 2
- **Claim:** Hardware deployment feasibility (latency, energy) is primarily determined by total inference FLOPs, which scale with model size and class count, but is moderated by achieved compression.
- **Mechanism:** More classes increase parameter count (especially in the final layer) and computational graph size, raising FLOPs. Compression reduces these FLOPs. The resulting FLOP count directly dictates inference time and dynamic energy draw on a fixed MCU.
- **Evidence:** Section 2 states latency and energy are largely determined by FLOPs; Figure 6 shows upward trends in energy and latency as classes increase, with local reversals matching compressibility changes.
- **Break condition:** This linear FLOP-to-cost assumption may break if compiler optimizations, memory access patterns, or hardware accelerators dominate cost for certain layers.

### Mechanism 3
- **Claim:** The black-box, multi-objective compression process (interleaved training/pruning/quantization) is the primary driver of final model efficiency, finding Pareto-optimal solutions that maintain accuracy despite high compression.
- **Mechanism:** The compression tool runs 50 trials per class count, exploring trade-offs between accuracy, ROM, RAM, and FLOPs. It selects models that are Pareto-optimal (no better in one metric without a worse trade-off in another), enabling high compression with minimal accuracy loss.
- **Evidence:** Section 2 describes the 50-trial process and Pareto selection; Section 3 reports almost no accuracy loss due to compression and consistently high compression rates (82–88%) across class counts.
- **Break condition:** The 50-trial budget may be insufficient for the search space complexity at high class counts (501), potentially missing better Pareto points. Results are also constrained to the `mcunet-in4` architecture.

## Foundational Learning

- **Concept: MCUNet (TinyNAS + TinyEngine)**
  - **Why needed:** It is the specific framework used for training and deploying compressed models on MCUs. TinyNAS performs neural architecture search for tiny models; TinyEngine is an inference engine for low-memory devices.
  - **Quick check:** What fundamental design trade-off does TinyNAS search for, and how does TinyEngine enable deployment on memory-constrained devices?

- **Concept: Structured Pruning & Quantization-Aware Training (QAT)**
  - **Why needed:** These are the core compression techniques applied. Pruning removes redundant filters/connections; QAT trains models to be robust to low-precision (e.g., int8) weights/activations, reducing memory and compute.
  - **Quick check:** How does interleaving training and pruning differ from train-then-prune, and why might this lead to better Pareto-optimal models under tight memory constraints?

- **Concept: Edge AI Deployment Trade-offs (Accuracy vs. Latency vs. Energy)**
  - **Why needed:** The study explicitly balances these trade-offs for real-world deployment. The ranking function (`rank = mem + acc`) combines a normalized accuracy metric with a normalized memory metric.
  - **Quick check:** Given the power measurements (Cortex-M7: 83 mJ inference, 116 mW sleep) and a 10% active duty cycle, how would you calculate the average daily power draw and required battery Wh for a 48-hour autonomy goal?

## Architecture Onboarding

**Component map:**
Dataset Ingestion (Xeno-Canto + ESC-50) -> Preprocessing (chunking, mel-spectrogram) -> Model Definition (mcunet-in4 modified) -> Baseline Training (SGD, 30 epochs) -> Compression Search (50 trials of interleaved pruning + QAT) -> Pareto Selection (rank = mem + acc) -> Binary Generation (C code) -> Hardware Benchmarking (Cortex-M4/M7, Pi4) -> Feasibility Analysis (energy model)

**Critical path:** Data Preprocessing → mcunet-in4 (Base) → Compression Search (50 trials) → Pareto Selection → Binary Generation → Hardware Benchmarking → Energy Model Calculation

**Design tradeoffs:**
- Accuracy vs. Resource: Explicitly balanced in the ranking function; more classes inherently hurt accuracy.
- Compression Trials vs. Search Cost: 50 trials per class count is computationally expensive but explores the Pareto front.
- Model Architecture vs. Comparability: Using a single base architecture isolates class-count effects but may not be optimal for all class counts.
- Dataset Fidelity vs. Realism: Heterogeneous Xeno-Canto data with augmentations increases noise robustness but likely limits peak accuracy.

**Failure signatures:**
- Cortex-M4 latency > 2 s (audio chunk length) across class counts → model too large/slow.
- High accuracy drop: if `acc(edge) << acc(baseline)`, compression failed to find a viable trade-off.
- Low compression rate: `cr < 0.7` indicates ineffective compression for that class count/architecture.
- Non-Pareto solutions: if the "best ranked" model is dominated, the selection function is flawed.

**First 3 experiments:**
1. **Class Count Sweep:** Train/compress models for 2, 31, 51, 101, 151, 201, 301, 501 classes. Measure accuracy, FLOPs, ROM, RAM. Verify the non-monotonic compressibility trend.
2. **Hardware Benchmarking:** Flash each Pareto-optimal model to Cortex-M4, Cortex-M7, and Raspberry Pi 4. Measure inference latency and energy per sample. Confirm hardware-specific feasibility thresholds.
3. **Energy-Autonomy Estimation:** Using the 31-class model on Cortex-M7, measure active (inference+spectrogram) and sleep power. Apply the 10% duty cycle to compute average power, then required 48 h battery capacity (Wh) and December solar panel area (m²). Validate against reported 6.6 Wh / 0.07 m².

## Open Questions the Paper Calls Out
- What explains the non-monotonic relationship between number of target classes and neural network compressibility?
- How would a curated, high-quality dataset affect model accuracy and compressibility compared to the current heterogeneous dataset?
- How do alternative neural network compression frameworks compare to MCUNet's internal tool in terms of accuracy-compression trade-offs for avian monitoring on MCUs?
- Can model architectures or compression strategies be adapted to enable feasible deployment on the ARM Cortex-M4, or is the hardware fundamentally unsuitable?
- How accurate are the energy-autonomy assumptions (e.g., 10% inference time, solar irradiance) under real-world deployment conditions?

## Limitations
- The proprietary compression pipeline (Fraunhofer internal tool) details are unknown, preventing exact replication of Pareto-optimal models and observed trends.
- The exact spatial dimensions of the input mel-spectrogram required by `mcunet-in4` are unspecified, affecting model architecture and resource metrics.
- Findings are limited to a single base architecture (`mcunet-in4`), one dataset pipeline, and specific hardware; generalizability is uncertain.
