# Conversational Demand Response: Bidirectional Aggregator-Prosumer Coordination through Agentic AI

## Quick Facts
- **arXiv ID:** 2603.06217  
- **Source URL:** https://arxiv.org/abs/2603.06217  
- **Reference count:** 25  
- **Primary result:** End-to-end interactions complete in under 12 s (upstream ≤2 s, downstream ≤10 s) with token usage under 34 k, demonstrating a scalable transparent DR system.

## Executive Summary
Residential demand response (DR) suffers from low prosumer participation because traditional coordination is opaque and one-way. This paper introduces Conversational Demand Response (CDR), a two-tier multi-agent architecture where an aggregator agent and a prosumer home energy management system (HEMS) agent negotiate via natural language. The HEMS grounds its decisions in a mixed-integer linear programming (MILP) optimization tool to assess feasibility of proposed DR actions. A proof-of-concept implementation shows end-to-end interactions finishing within 12 seconds, with subcomponents meeting tighter bounds (upstream ≤2 s, downstream ≤10 s) and consuming fewer than 34 k tokens per benchmark. The full system is released as open source, bridging scalability and transparency in DR.

The evaluation uses six scripted scenarios—three downstream (acceptance, rejection, high‑target) and three upstream (availability, preference, new asset)—on a single synthetic household with battery and appliance parameters from Table IV. Inference runs at zero temperature via the Cerebras API (GPT‑OSS‑120B) at up to 2 500 tokens/sec. Results indicate that the combination of LLM‑driven negotiation and exact optimization can yield responsive, explainable DR coordination.

## Method Summary
CDR consists of two primary agents: an aggregator representing the grid/market operator and a prosumer’s HEMS. They communicate using natural language in a ReAct (reasoning + acting) pattern. When the aggregator issues a DR request, the HEMS enters a loop of thought and tool calls, ultimately invoking a MILP optimizer to evaluate feasibility. The optimizer performs a dual‑solve procedure comparing a baseline schedule with one that includes the requested DR adjustment, returning either full, partial, or infeasible verdicts. The HEMS then formulates a human‑readable response with justification. Upstream scenarios work similarly but are initiated by the HEMS (e.g., reporting availability or adding assets). All interactions are orchestrated by lightweight Python code; the LLM is queried via Cerebras’ inference endpoint. Latency and token count are measured from message dispatch to final aggregator update.

## Key Results
- **Latency:** Mean end‑to‑end ≤12 s; upstream exchanges ≤2 s; downstream dispatches ≤10 s.
- **Token usage:** ≤34 k tokens across all benchmark dialogues.
- **Transparency:** Full dialogue logs and implementation (code, prompts, orchestration) are publicly available.

## Why This Works (Mechanism)
The ReAct pattern gives agents structured reasoning steps that produce interpretable dialogues and precise tool invocations. The MILP solver guarantees that feasibility assessments respect all physical and operational constraints (battery capacity, household demand, degradation costs). By offloading the home‑level optimization to the HEMS, the aggregator avoids heavy computation and only coordinates high‑level dispatch. Zero‑temperature inference ensures deterministic outputs, which is essential for reproducible coordination. Finally, the Cerebras API’s high throughput (2 500 tok/s) keeps LLM latency within the sub‑10 s window for typical dialogue lengths.

## Foundational Learning
- **Multi‑agent systems** – *Why needed:* Separates grid‑level and home‑level concerns, allowing independent development and scaling. *Quick check:* Agents operate and communicate without a single point of failure.
- **ReAct reasoning** – *Why needed:* Enables LLMs to interleave thought and action, making tool use reliable. *Quick check:* Agent outputs contain explicit `Thought:` and `Action:` sections.
- **Mixed‑integer linear programming** – *Why needed:* Provides provably optimal or infeasible decisions under linear constraints. *Quick check:* Solver returns a schedule that satisfies all constraints (e.g., battery SoC bounds, power limits).
- **Demand response** – *Why needed:* The core grid service that adjusts load to balance supply. *Quick check:* Prosumer agrees to shift or curtail consumption in exchange for remuneration.
- **Natural language interface** – *Why needed:* Builds trust and allows flexible negotiation. *Quick check:* Messages are understandable to humans (e.g., “Can you reduce load at 6 pm?”).
- **Zero‑temperature inference** – *Why needed:* Eliminates randomness for consistent coordination. *Quick check:* Same prompt yields identical response across repeated runs.

## Architecture Onboarding
**Component Map**  
Aggregator Agent ↔ HEMS Agent (via natural language) → MILP Optimizer (PuLP)

**Critical Path**  
*Downstream:* Aggregator sends DR request → HEMS ReAct loop → MILP feasibility check → HEMS response → Aggregator update.  
*Upstream:* HEMS detects change (availability/preference/new asset) → ReAct loop → MILP if needed → Update to aggregator.  
LLM inference time dominates; MILP solves typically within seconds.

**Design Tradeoffs**  
- LLM negotiation offers flexibility and transparency but adds latency and token costs versus fixed protocols.  
- MILP ensures exact feasibility at the expense of model linearity and solve time for very complex assets.  
- Two‑tier design reduces aggregator computational load but introduces dependency on HEMS availability and network reliability.

**Failure Signatures**  
- Latency >15 s: LLM API slowdown or network congestion.  
- MILP infeasibility or solver errors: aborted dialogues; detect via error codes or “infeasible” verdict.  
- Malformed tool calls (JSON parse errors): break ReAct cycle; check API logs.  
- Token count approaching context window: risk of truncation; monitor cumulative tokens.

## Open Questions the Paper Calls Out
1. **Scalability to multi‑household portfolios:** The proof‑of‑concept evaluates only isolated single‑household interactions; concurrent coordination of hundreds or thousands of prosumers may introduce context‑window, network, and orchestrator bottlenecks that could violate the sub‑12‑second requirement.  
2. **Impact on prosumer engagement:** While transparency is claimed to improve participation, trust, and satisfaction, no empirical user study exists. Controlled field trials comparing CDR to conventional DR interfaces are needed to validate these human‑centered benefits.  
3. **Generalization to complex assets:** The current MILP and sub‑agent design target a single battery and simple appliances. Extending to heterogeneous, non‑linear assets (e.g., multi‑zone HVAC, pools, multiple batteries with different chemistries) may require different optimization formulations (MINLP, RL) and could break latency guarantees.  
4. **Economic and operational limits under high‑frequency requests:** The MILP tool’s behavior under extreme market signals (price spikes, negative prices), very short‑notice DR events, or multi‑event days is unknown. Sensitivity of feasibility verdicts and prosumer economics to parameters (degradation cost, horizon length) remains unexplored.

## Limitations
- **Proprietary inference service:** Performance claims rely on the Cerebras API and GPT‑OSS‑120B; other models or local inference will likely yield different latency and token usage.
- **Undocumented prompts/orchestration:** Exact system prompts, JSON tool schemas, and conversation flow are not detailed in the paper, making exact replication sensitive to minor variations.
- **Single‑household simulation:** Evaluation uses one synthetic home with fixed parameters; generalizability to diverse real‑world prosumer populations and actual data is uncertain.
