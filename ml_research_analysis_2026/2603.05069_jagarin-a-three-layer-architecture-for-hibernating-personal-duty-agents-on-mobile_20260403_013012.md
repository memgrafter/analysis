# Jagarin: A Three-Layer Architecture for Hibernating Personal Duty Agents on Mobile

## Quick Facts
- **arXiv ID:** 2603.05069
- **Source URL:** https://arxiv.org/abs/2603.05069
- **Reference count:** 14
- **Primary result:** Three-layer architecture enabling hibernating personal duty agents on mobile without violating OS policies or draining battery.

## Executive Summary
Jagarin introduces a novel three-layer architecture that solves the mobile personal agent deployment paradox: persistent background execution is prohibited by mobile OS policies and drains battery, while reactive agents fail to handle time-sensitive duties. The system comprises ARIA (email parser), DAWN (on-device urgency engine), and ACE (machine-readable institutional communication protocol). DAWN computes a composite urgency score from four signals—duty-typed optimal windows, user engagement prediction, opportunity cost, and cross-duty resonance—to decide when to nudge or escalate. The Android prototype demonstrates feasibility, with sub-50ms inference, compliance with WorkManager/BGTaskScheduler constraints, and full on-device privacy. Adaptive thresholds personalize wake behavior based on user response patterns, avoiding persistent cloud state.

## Method Summary
The paper does not provide explicit reproduction notes. However, the method is described as a three-layer architecture: ARIA automatically parses commercial emails into structured duty records, eliminating cold-start; DAWN computes a composite urgency score from duty-specific optimal times, predicted user engagement, opportunity cost, and cross-duty resonance; and ACE defines a protocol for direct machine-readable institutional communication. The system operates entirely on-device, using OS-provided periodic wake mechanisms (Android WorkManager, iOS BGTaskScheduler) to run DAWN inference in under 50ms. No persistent cloud state is maintained, ensuring privacy. Adaptive thresholds adjust nudge behavior based on historical user responses.

## Key Results
- The three-layer architecture resolves the mobile personal agent deployment paradox by keeping agents hibernating except for brief, OS-compliant wake periods.
- DAWN’s composite urgency heuristic runs in under 50ms and fits within 15-minute periodic constraints, preserving battery.
- ARIA eliminates cold-start by parsing commercial email into duty records; ACE provides an alternative direct institutional channel.
- The prototype maintains privacy via on-device processing and personalizes wake behavior through adaptive thresholds.

## Why This Works (Mechanism)
Jagarin’s mechanism hinges on shifting from continuous background execution to opportunistic, urgency-driven nudges. ARIA (and ACE) convert unstructured communications into structured duty records, providing the raw material for DAWN. DAWN evaluates each duty using four signals: (1) duty-typed optimal windows (e.g., paying a bill before due date), (2) predicted user engagement (likelihood of response at current time), (3) opportunity cost (interruption cost), and (4) cross-duty resonance (synergies/conflicts with other duties). This composite score is compared against an adaptive threshold that personalizes to the user’s response history. When the score exceeds the threshold, the system triggers a brief, targeted nudge via standard notification mechanisms, then returns to hibernation. By basing wake decisions on predicted urgency rather than fixed schedules, the system avoids unnecessary awakenings, respects OS battery policies, and reduces missed obligations. The entire pipeline runs on-device, eliminating cloud dependencies and privacy risks.

## Foundational Learning
- **Composite urgency score:** Combines four signals into a single metric to decide when to intervene. *Why needed:* Provides a holistic, interpretable measure of duty priority without machine learning. *Quick check:* Correlate score with user satisfaction or duty completion rates across varying thresholds.
- **Duty-typed optimal windows:** Each duty type (e.g., financial, social) has a best time for handling. *Why needed:* Aligns nudges with when the user is most effective, reducing opportunity cost. *Quick check:* Compare completion latency for duties nudged inside vs. outside their optimal windows.
- **User engagement prediction:** Estimates the probability the user will respond at a given moment. *Why needed:* Avoids nudging during low-engagement periods (e.g., meetings), saving battery and annoyance. *Quick check:* Measure prediction accuracy against observed response times.
- **On-device heuristic processing:** All computation occurs locally, with no persistent cloud state. *Why needed:* Ensures privacy, reduces latency, and avoids network dependency. *Quick check:* Verify no network calls are made during duty evaluation or nudge generation.
- **Adaptive thresholds:** Thresholds for triggering nudges adjust based on user’s historical response patterns. *Why needed:* Personalizes the system to individual behavior, balancing promptness and interruption tolerance. *Quick check:* Track threshold drift over time and its correlation with user satisfaction metrics.
- **OS-compliant periodic wake:** Leverages WorkManager (Android) and BGTaskScheduler (iOS) for bounded execution. *Why needed:* Respects mobile OS policies that restrict background activity, preventing battery drain and policy violations. *Quick check:* Confirm that all background tasks complete within the permitted execution window.

## Architecture Onboarding
**Component map:** ARIA -> DAWN <- ACE; DAWN -> Nudger; User Response Tracker -> DAWN

**Critical path:** Duty acquisition (ARIA parses email or ACE receives institutional message) generates a duty record → DAWN computes composite urgency score using current context and duty signals → if score exceeds adaptive threshold, Nudger dispatches a notification → user interacts or ignores → response logged by User Response Tracker → adaptive thresholds updated for future decisions. DAWN re-evaluates periodically during OS-scheduled wakes.

**Design tradeoffs:** 
- Privacy vs. accuracy: On-device heuristics avoid cloud privacy risks but may be less accurate than centralized ML. 
- Battery vs. timeliness: Periodic wakes (max 15 min) limit how urgently duties can be addressed; some may be delayed. 
- Simplicity vs. adaptability: Rule-based signals are transparent but may not capture complex user preferences; adaptive thresholds partially address this. 
- OS constraints vs. flexibility: Must use platform schedulers, restricting execution frequency and duration. 
- Cold-start vs. integration: ARIA relies on email parsing, which may fail for non-commercial formats; ACE requires institutions to adopt a new protocol.

**Failure signatures:** 
- Missed duties: Urgency score consistently below threshold or OS wake missed. 
- Excessive nudges: Overly sensitive signals or low threshold leading to user annoyance. 
- Parsing failures: ARIA cannot extract duty details from email, causing duty loss. 
- Battery drain: Too frequent wakes or long-running DAWN inference. 
- Stale adaptation: Thresholds not adjusting to changing user behavior. 
- Institutional incompatibility: ACE messages ignored or unsupported by institutions.
