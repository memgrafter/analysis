# Stepwise: Neuro-Symbolic Proof Search for Automated Systems Verification

## Quick Facts

- **arXiv ID:** 2603.19715
- **Source URL:** https://arxiv.org/abs/2603.19715
- **Reference count:** 40
- **Primary result:** On the FVEL seL4 benchmark, the system achieves a 77.6% proof success rate, covers 36.2% of proof lines, and reduces expert effort by 71.1% in AI-human collaboration.

## Executive Summary

The construction of proof scripts in interactive theorem proving for system verification remains a manual, time‑consuming process. This paper introduces *Stepwise*, a neuro‑symbolic framework that automates proof search by combining a fine‑tuned large language model (LLM) with symbolic tools. The system performs best‑first tree search over Isabelle/HOL proof states, repeatedly querying a small LLM (fine‑tuned on 181,887 state‑step pairs from the seL4 microkernel proofs) to propose the next tactic. Rejected steps are repaired using heuristic recombination of tactics and premise substitution, while state filtering via QuickCheck, Nitpick, and SolveDirect prunes invalid or duplicate branches. On the FVEL seL4 benchmark, Stepwise with a Mistral‑7B model achieves 77.6% proof success, far exceeding prior neural approaches (<10%) and standalone Sledgehammer (40.3%). It also automatically covers 36.2% of all proof lines and reduces expert effort by 71.1% in an AI‑human collaboration study, with promising generalization to additional AFP and program verification benchmarks.

## Method Summary

The framework targets automated theorem proving in Isabelle/HOL for systems verification, using the FVEL dataset extracted from the seL4 microkernel. The dataset comprises 29,125 theorems split into training, validation, test, and test‑hard sets, yielding 181,887 proof state–step pairs. A small language model (Mistral‑7B or Qwen3‑1.7B) is fine‑tuned via full‑parameter supervised fine‑tuning (learning rate 1e‑5, 3 epochs) to predict the next tactic conditioned on the current proof state.

Search proceeds in a best‑first manner: from a given state, up to 128 candidate steps are sampled from the LLM and executed in Isabelle. Steps that fail undergo symbolic repair: either tactic repair (recombining premises with 12 frequent tactics) or premise repair (substituting similar premises). All resulting states—from successful original steps and repaired steps—are filtered using QuickCheck (random testing), Nitpick (finite model finding), and SolveDirect (duplicate removal). States are ranked by normalized cumulative log‑probability of the steps that generated them. The top‑*k* unexplored states are selected for further expansion. If a state with no subgoals is reached, the proof is returned; otherwise the loop repeats until a 120‑minute budget is exhausted. At that point, Sledgehammer is invoked (60‑second timeout, 2048 premises via MeSh) on the 16 highest‑ranked states as a final backstop.

## Why This Works (Mechanism)

**Mechanism 1: Fine‑tuned LLM for step prediction.** The system collects 181,887 state‑step pairs from seL4 proofs and fine‑tunes a small LLM (e.g., Mistral‑7B) to predict the next tactic given the current proof state (Section 3.1.1). The underlying assumption is that the procedural reasoning involved in system verification can be captured by learning from these step‑by‑step traces, and that a domain‑adapted model will generalize to new theorems.

**Mechanism 2: Symbolic repair of rejected steps.** When a proposed step fails in Isabelle (e.g., due to an undefined fact), the system applies symbolic repair: either tactic repair (recombining premises with a curated set of 12 frequent tactics) or premise repair (substituting a similar premise via edit distance) (Algorithm 2). This approach assumes that LLM‑generated steps often contain minor, locally fixable errors, and that rule‑based transformations can salvage many otherwise invalid candidates without retraining.

**Mechanism 3: Counterexample‑based filtering and LLM‑guided ranking.** After executing candidate steps, the system uses QuickCheck and Nitpick to detect counterexamples in the resulting states, discarding those that admit falsifying tests; duplicates are removed via SolveDirect. Remaining states are scored by normalized cumulative log‑probability of the generating steps, and the top‑*k* are expanded. The method assumes that counterexamples reliably indicate dead ends and that the LLM’s confidence provides a useful utility heuristic for guiding the best‑first search (Section 3.2).

## Architecture Onboarding

### Component Map
Root Proof State → LLM Step Generator (candidate steps) → Proof Executor (Isabelle/HOL). Failed steps → Symbolic Step Repair (tactic/premise revision) → back to Proof Executor. All resulting states → State Filter (QuickCheck, Nitpick, SolveDirect) → State Ranker (normalized cumulative log‑prob) → top‑k states → next iteration. If budget exhausted without proof: → Sledgehammer Backstop (top‑16 states).

### Critical Path
1. Start with root state (theorem statement).
2. Pick highest‑score unexplored node.
3. Generate up to 128 candidate steps via LLM.
4. Execute each step in Isabelle; separate successes and failures.
5. Apply repair to failures (Algorithm 2) and re‑execute.
6. For all new states, run filter (counterexamples/duplicates).
7. Score remaining states and add to search tree.
8. If any new state has no subgoals, return proof; else repeat until max iterations.
9. If max iterations reached, invoke Sledgehammer on top‑k states.

### Design Tradeoffs
- **Search budget vs. completeness:** More iterations and candidates increase success probability but linearly increase runtime; the paper uses a 120‑minute limit.
- **LLM size vs. latency:** Smaller models (1.7B, 7B) are used for fast generation despite lower accuracy; fine‑tuning bridges the gap.
- **Repair granularity vs. explosion:** Repair can multiply candidates; the system limits the tactic set (12 most frequent) and premise set (128 via MePo).
- **Filtering aggressiveness:** Counterexample detection prunes many states but may discard provable ones if the test is incomplete.

### Failure Signatures
- **Zero valid steps from LLM:** Model fails to produce any step accepted by Isabelle even after repair; indicates out‑of‑distribution state.
- **High counterexample rate:** Many filtered states contain counterexamples; suggests LLM proposes steps leading to false subgoals.
- **Search stagnation:** Tree grows but no state reaches proof; may require adjusting scoring or increasing repair aggressiveness.
- **Runtime explosion:** Excessive branching (128 candidates × 5 states) overwhelms resources; reduce candidate count or tighten filtering.

### First Three Experiments
1. **End‑to‑end smoke test:** Run the framework on 5–10 simple theorems from the training split to verify the pipeline (LLM, repair, filter) produces correct proofs within minutes.
2. **Component ablation:** Disable repair and/or filtering individually and measure success rate and time on a sample of 50 theorems to quantify each component’s contribution.
3. **Hyperparameter sensitivity:** Vary top‑k (expanded states) and candidate count to find a Pareto front of success rate vs. runtime on a medium‑sized subset.

## Open Questions the Paper Calls Out

1. **Computational efficiency:** How can the overhead of tree search be reduced without sacrificing success rates? The paper identifies cost as a key limitation but does not evaluate proposed mitigations such as caching or parallel expansion.
2. **Long‑proof performance:** Why does performance degrade for multi‑step proofs (>10 lines), and what modifications (e.g., hierarchical planning, reinforcement learning) are needed to maintain high success on long chains? No empirical evaluation of suggested directions is provided.
3. **Revision module limitations:** Can the heuristic repair (tactic recombination, premise substitution) be replaced or augmented with learned relevance models to improve the quality of revised steps? No comparison with supervised rankers exists.
4. **Fine‑tuning vs. RAG:** Why does fine‑tuning a small LLM on domain data outperform retrieval‑augmented generation with large off‑the‑shelf models? The paper does not analyze factors like retrieval quality, context window limits, or model utilization, leaving this trade‑off unexplained.

## Limitations

- Missing critical implementation details (tactic list, premise thresholds, prompt formatting) hinders faithful replication.
- The false positive rate of the counterexample filters (QuickCheck/Nitpick) is unreported; over‑pruning may occur.
- Search budget parameters (number of expanded states per iteration, exact top‑*k*) are vague, making results sensitive to unrecorded choices.
