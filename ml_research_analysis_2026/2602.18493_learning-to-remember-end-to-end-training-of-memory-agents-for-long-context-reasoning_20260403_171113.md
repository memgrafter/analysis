# Learning to Remember: End-to-End Training of Memory Agents for Long-Context Reasoning

## Quick Facts
- **arXiv ID:** 2602.18493  
- **Source URL:** https://arxiv.org/abs/2602.18493  
- **Reference count:** 40  
- **Primary result:** UMA achieves 53.33% accuracy at 50 sessions on Ledger-QA (baselines <25%) and 76.46% average accuracy across 13 datasets, with large gains on dynamic reasoning tasks (e.g., 87% on Banking77, 91% on Clinic).

## Executive Summary
Long-context LLMs and RAG systems often fail when faced with ultra-long streaming data that requires continuous state tracking and evidence aggregation, because they defer reasoning to query time. This paper introduces the Unified Memory Agent (UMA), an end‑to‑end reinforcement learning framework that unifies memory operations (CRUD) and question answering within a single policy. UMA maintains a dual‑memory structure—a compact core summary and a structured Memory Bank—that is proactively updated during the stream. Training uses Task‑Stratified Group Relative Policy Optimization (GRPO) to jointly optimize memory maintenance and QA. On the new Ledger‑QA benchmark, which demands cumulative state updates, UMA retains robust performance (53.33% at 50 sessions) while all baselines drop below 25%. Across 13 datasets, UMA averages 76.46% accuracy, substantially outperforming on dynamic tasks and remaining competitive on standard retrieval benchmarks, demonstrating the value of learned, proactive memory management.

## Method Summary
UMA is a memory agent that processes an incoming stream of text chunks. Its state consists of a core summary (`m_core`), a structured Memory Bank (`B`), and a short interaction history (`ht`). A single policy LLM (Qwen3‑4B‑Instruct) selects actions from separate tool sets depending on the phase: during stream processing (Phase I) it can add, update, delete, retrieve, list entries, or update the core summary; during question answering (Phase II) it uses retrieval tools and finally answers. The training loop follows a nested rollout design: for each context, sample `N` memory trajectories, then for each resulting memory state sample `M` queries and generate QA rollouts. Rewards combine tool‑success (`r_tool`) and answer correctness (`r_outcome`). Task‑Stratified GRPO computes advantages separately for memory actions (normalized globally across trajectories) and QA actions (normalized per query group), avoiding scale mismatches. Two agents are trained: a Generalist (on HotpotQA + MemAlpha, 2 epochs) and a Specialist (on Ledger‑QA, 6 epochs). Inference proceeds by first consuming all chunks via Phase I actions, then answering queries via Phase II.

## Key Results
- On Ledger‑QA, UMA’s accuracy declines slowly with session count, reaching **53.33% at 50 sessions**; all baselines fall below **25%**.
- Across 13 datasets spanning Test‑Time Learning and Accurate Retrieval, UMA averages **76.46%** accuracy.
- UMA achieves **87% on Banking77** and **91% on Clinic**, major improvements over prior work, while remaining competitive on standard retrieval benchmarks.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** UMA addresses the failure of passive long‑context LLM/RAG systems by unifying memory operations (CRUD) and question answering within a single, end‑to‑end trained policy, enabling proactive state consolidation during streaming.
- **Mechanism:** Instead of deferring state tracking to query time, the agent incrementally updates a structured Memory Bank (key‑value store) and a core summary as each chunk arrives. This creates a persistent, query‑aware belief state separate from the raw context, decoupling maintenance from sequence length.
- **Core assumption:** The optimal policy for answering future queries can be shaped by reinforcement learning signals from those queries, even when memory updates happen earlier in the stream.
- **Evidence anchors:**
  - [abstract] “unifies memory operations (CRUD) and question answering within a single policy… enabling proactive consolidation during streaming.”
  - [section 2.1] Formal MDP where memory state `Mt` is updated during chunk processing (`xt` = chunk) and later queried (`xt` = question).
  - [section 4.3] On Ledger‑QA (which requires state aggregation), UMA’s accuracy remains robust (53.33% at 50 sessions) while RAG collapses (<20%), demonstrating the value of proactive updates.
- **Break condition:** If the reward function (`Ri,j` in Eq. 3) fails to provide meaningful gradients for memory actions (e.g., if `rtool` is too sparse or `r_outcome` is delayed/shaped poorly), the policy may not learn to perform timely CRUD operations, reverting to passive retrieval.

### Mechanism 2
- **Claim:** Task‑Stratified Group Relative Policy Optimization (GRPO) enables effective credit assignment in the hierarchical two‑phase process by normalizing advantages within semantically homogeneous groups (memory‑trajectory utility vs. per‑question QA performance).
- **Mechanism:** For memory actions, the return is the average QA reward across multiple questions (`Gmem_i`), normalized against all memory trajectories (global baseline). For QA actions, reward is normalized only among trajectories answering the same question. This prevents mixing heterogeneous reward scales (aggregated memory utility vs. binary QA scores) and ensures fair comparison within each phase.
- **Core assumption:** Memory quality can be estimated by the expected utility across a distribution of future queries, and this estimate is stable enough for policy gradient updates when averaged over sampled questions.
- **Evidence anchors:**
  - [section 2.3] Explicit equations for stratified advantage calculation: Eq. 4‑5 for memory, Eq. 6 for QA.
  - [section 4.4] “Global Group” variant (mixed normalization) underperforms stratified (73.58% vs 76.46%), confirming the necessity of separate baselines.
  - [corpus] Neighbors like “Dynamic Long Context Reasoning…” also use RL for memory, implying credit assignment is a known challenge.
- **Break condition:** If the number of sampled queries per memory trajectory (`M`) is too low, `Gmem_i` becomes a high‑variance estimator, leading to noisy gradients for memory updates. The paper uses `M` unspecified; insufficient sampling would destabilize training.

### Mechanism 3
- **Claim:** The dual‑memory architecture (core summary + structured Memory Bank) provides a scalable representation that balances global context compression with precise, verifiable state tracking.
- **Mechanism:** The `m_core` (summary) captures high‑level trends and is updated via `UpdateCore` after each chunk, while the Memory Bank `B` stores discrete, updatable facts via CRUD operations. During QA, the agent can retrieve from both: `B` for exact state values (e.g., current balance) and raw chunks for unsummarized details.
- **Core assumption:** A compressed core summary is sufficient to guide memory operations and retrieval decisions, while the bank holds the ground‑truth values needed for accurate aggregation (e.g., summing transactions).
- **Evidence anchors:**
  - [section 2.2] “dual memory representation: a compact core summary… and a structured Memory Bank that supports explicit CRUD.”
  - [section 4.2] UMA outperforms on Ledger‑QA (state tracking) and remains competitive on AR benchmarks (retrieval), suggesting the dual structure handles both update‑heavy and retrieval‑heavy tasks.
  - [section 4.4] Ablation “w/o Phase I” (no sequential maintenance) drops significantly on Ledger‑QA and average (63.81% vs 76.46%), confirming the need for the proactive bank.
- **Break condition:** If `UpdateCore` compression is lossy or fails to capture relevant details for future queries, the core may misguide subsequent memory operations. The paper does not specify compression method; poor summarization could create a misleading global context.

## Foundational Learning
- **Concept: Markov Decision Process (MDP) formulation for sequential reasoning.**  
  *Why needed here:* UMA frames long‑context reasoning as a sequential decision problem where actions (CRUD, retrieval) affect future state (memory) and rewards (QA accuracy). Understanding states, actions, transitions, and rewards is essential to grasp how the policy learns.  
  *Quick check question:* Why must the transition dynamics include an “UpdateCore” terminal action that advances the chunk and resets history? What would happen if the agent could never commit memory updates?

- **Concept: Reinforcement Learning credit assignment across time horizons.**  
  *Why needed here:* Memory actions early in the stream only receive reward much later during QA. The stratified GRPO mechanism specifically addresses this delayed, sparse credit assignment problem. Without understanding RL’s challenge with long‑term credit, the training design seems arbitrary.  
  *Quick check question:* In the nested rollout (Section 2.3.1), why sample `M` questions per memory trajectory instead of using a single question? How does this reduce variance in the memory advantage estimate?

- **Concept: Dual memory systems (working vs. long‑term) in cognitive architectures.**  
  *Why needed here:* UMA’s `m_core` and Memory Bank `B` loosely mirror cognitive distinctions: a summary (global context) vs. explicit storage (episodic/semantic). This design is key to handling both aggregation (summing transactions) and retrieval (finding specific facts).  
  *Quick check question:* If the Memory Bank is a simple key‑value store, how does it support “reorganize” operations (mentioned in abstract)? What would a reorganization action practically do?

## Architecture Onboarding
- **Component map:**  
  Policy LLM (`π_θ`) → Memory Bank (`B`) & Core Summary (`m_core`) → Interaction History (`ht`) → Environment → Reward Calculator → GRPO Module → Policy update.  
  1. Policy LLM (`π_θ`): Qwen3‑4B‑Instruct, takes concatenated `[Isys, m_core, xt, ht]` and outputs tool calls.  
  2. Memory Bank (`B`): External key‑value store, mutable via `Add/Update/Delete/Retrieve/List`.  
  3. Core Summary (`m_core`): Compressed text summary, updated via `UpdateCore` action.  
  4. Interaction History (`ht`): Short‑term buffer of recent tool executions, reset per chunk.  
  5. Environment: Simulates chunk stream and query sampling; executes tool actions and returns results.  
  6. Reward Calculator: Computes `rtool` (tool success rate) and `r_outcome` (LLM judge on final answer).  
  7. GRPO Module: Computes stratified advantages and updates policy (uses `π_ref` for KL penalty).

- **Critical path:**  
  - Training: For each context `C`, sample `N` memory trajectories (Phase I loops) → for each final memory state, sample `M` queries → generate `N×M` QA rollouts → compute stratified advantages → policy update via Eq. 7‑9.  
  - Inference: Process each chunk: `xt = chunk`, `ht = ∅`; loop until `UpdateCore` → after last chunk, `xt = query`, `ht = ∅`; loop until `Answer`.

- **Design tradeoffs:**  
  - Dual memory vs. single store: Bank provides precise updates/aggregation but requires explicit keys; summary compresses but may lose details. Tradeoff: more bank entries → higher retrieval cost but better accuracy on state tracking.  
  - End‑to‑end RL vs. two‑stage: Unified training allows QA outcomes to shape memory decisions but requires complex nested rollouts. Two‑stage is simpler but suffers from train‑test mismatch (ablation shows 10% drop).  
  - Hard context window (16k): Paper admits truncation is a limitation; UMA mitigates but doesn’t eliminate context limits. Infinite horizon remains open.

- **Failure signatures:**  
  - Memory bank corruption: Frequent `Update` to non‑existent keys or `Delete` of critical entries → plummeting Ledger‑QA scores while AR tasks might be unaffected.  
  - Credit assignment collapse: If `M` (queries per memory) or `G` (group size) is too small, variance in `Gmem_i` increases → policy oscillates or learns to ignore memory actions.  
  - Tool misuse: High `rtool` penalty but no improvement in QA → agent may be learning to call tools correctly but not informatively (e.g., `List` repeatedly without `Add`).  
  - Core summary drift: If `UpdateCore` overwrites rather than integrates, `m_core` may become stale or contradictory, harming subsequent memory operations.

- **First 3 experiments:**  
  1. Replicate Ledger‑QA trend: Train UMA on 10‑session Ledger‑QA, test on 2/5/10/20/30/40/50 sessions. Expect accuracy drop but slower than baselines; verify >50% at 50 sessions.  
  2. Ablation: w/o Phase I: Remove `Add/Update/Delete` from Phase I, rely only on retrieval during QA. Expect catastrophic drop on Ledger‑QA at high sessions (similar to `MemAgent‑woq` in Fig 4).  
  3. Stratified vs. Global Group: Train two policies with same data, only difference being advantage normalization (Eq. 5 vs. single group). Expect stratified to achieve higher average accuracy, especially on TTL tasks (Banking77, Clinic).

## Open Questions the Paper Calls Out
1. Can UMA scale to infinite‑horizon streams (millions of tokens) without raw context fallback?  
   *Basis:* “an infinite‑horizon setting where the agent must manage memory over millions of tokens without any raw context fallback remains an open challenge.”
2. Does UMA generalize from synthetic Ledger‑QA data to real‑world state‑tracking scenarios with higher noise and ambiguity?  
   *Basis:* “Real‑world bookkeeping or state‑tracking scenarios may involve more unstructured noise and ambiguity than our current simulation covers.”
3. Can the unified RL framework be extended to multi‑modal memory (images, audio) and richer tool‑use while preserving end‑to‑end trainability?  
   *Basis:* “extending this framework to support multi‑modal memory (e.g., images, audio) or more complex tool‑use patterns requires further investigation.”

## Limitations
- Hyperparameters `N`, `M`, `λ`, and PPO `ϵ` are not reported, affecting training stability and gradient variance.
- Data split and phase allocation details are missing; epoch boundaries under multi‑trajectory RL are ambiguous.
- Baseline implementations (e.g., MemAlpha) rely on undocumented settings (16k truncation, retrieval top‑k); comparison fairness is uncertain.
- Evaluator model version (Qwen3‑30B‑A3B‑Instruct‑2507) is not pinned, risking score reproducibility.
