# VisPhyWorld: Probing Physical Reasoning via Code-Driven Video Reconstruction

## Quick Facts
- **arXiv ID:** 2602.13294  
- **Source URL:** https://arxiv.org/abs/2602.13294  
- **Reference count:** 40  
- **Primary result:** A code-driven evaluation pipeline that produces valid videos in 97.7% of cases, revealing state-of-the-art MLLMs' strength in semantic understanding but weakness in inferring accurate physical parameters and dynamics.

## Executive Summary
VisPhyWorld introduces a paradigm shift for evaluating physical reasoning in multimodal large language models (MLLMs). Instead of black-box image or video generation, it requires models to produce executable simulator code from two initial frames, generating a testable physical hypothesis. The accompanying VisPhyBench suite, with 209 scenes across 108 templates, measures both visual reconstruction and motion plausibility. Results show that even advanced models like GPT-5 demonstrate a significant gap between semantic comprehension (high DINO and CLIP scores) and accurate physical dynamics prediction. The code-centric approach provides diagnostic insights into model reasoning that pixel-level outputs cannot.

## Method Summary
The pipeline accepts two video frames depicting a scene with initial object states. The MLLM generates code for a physics engine (default Three.js) that simulates the scene. This code executes to produce a full video, which is then evaluated. Evaluation uses both visual similarity metrics (DINO, CLIP-Image) to check if object identities/positions match ground truth, and a motion plausibility score to assess whether dynamics adhere to physical laws. The entire process is deterministic and inspectable, turning model output into a falsifiable hypothesis.

## Key Results
- The pipeline achieves a 97.7% success rate in generating executable code that produces valid output videos.
- GPT-5 excels at semantic understanding (DINO: 0.8556, CLIP-Img: 0.8930) but performs poorly on accurate physical parameter inference and consistent dynamics.
- Physics-enabled backends (Three.js) significantly outperform non-physics and no-backend baselines in generating plausible motion.

## Why This Works (Mechanism)
The code-driven paradigm forces models to externalize explicit, executable hypotheses about physical laws. Unlike end-to-end video generation, which can rely on spurious correlations, generating simulator code requires specifying forces, masses, friction, and initial conditions. The resulting video is a direct consequence of these parameters, making it straightforward to diagnose *why* a prediction fails (e.g., incorrect gravity value, missing collision logic). The use of a standard engine like Three.js grounds evaluation in well-understood Newtonian mechanics, providing a common, inspectable substrate for all models.

## Foundational Learning
- **Executable Physical Simulations**: Code that can be run in a physics engine to generate outcomes. *Why needed*: Transforms abstract reasoning into testable predictions. *Quick check*: Does the generated code run without errors and produce a coherent animation?
- **Physical Parameter Inference**: Deduction of quantities like mass, friction, or elasticity from observed states. *Why needed*: Core to genuine physical reasoning beyond mere recognition. *Quick check*: Do inferred parameters produce motion consistent with Newton's laws when varied slightly?
- **Diagnostic Code Analysis**: Inspecting the structure and content of generated code to understand model reasoning. *Why needed*: Black-box outputs offer no insight into the reasoning process. *Quick check*: Can one identify logical errors or assumptions by reading the code (e.g., "object.mass = 1" for all objects)?
- **Falsifiable Hypothesis Generation**: Producing outputs that can be directly verified against ground-truth physics. *Why needed*: Moves evaluation beyond pattern matching. *Quick check*: Does the model's prediction contradict observable physical constraints in the scene?

## Architecture Onboarding
**Component Map:**  
Input Video Frames -> MLLM (Code Generation) -> Three.js Backend (Execution) -> Generated Video -> Evaluation Module (Visual + Motion Metrics)

**Critical Path:** Code Generation -> Backend Execution -> Video Output. Failures in code generation (syntax errors, incoherent logic) immediately halt the pipeline.

**Design Tradeoffs:**  
- **Engine Choice (Three.js)**: Provides rich features and web compatibility but may bias results toward models trained on web-related code. Other engines (e.g., PyBullet) were unexplored.
- **Template Curation**: 108 curated templates ensure coverage but risk overfitting to MLLMs' training distributions; diverse, natural scenes could reveal different weaknesses.
- **Metric Selection**: DINO/CLIP are accessible proxies for visual fidelity but are not direct measures of physical accuracy (e.g., they may accept visually plausible but dynamically incorrect motion).

**Failure Signatures:**  
1. **Code Generation Errors**: Syntax mistakes, undefined variables, or API misuse leading to execution failure.
2. **Semantic-Dynamic Decoupling**: High visual similarity scores (DINO/CLIP) paired with low motion plausibility, indicating correct object recognition but flawed dynamics.
3. **Parameter Insensitivity**: Generated video remains unchanged when key physical parameters (gravity, restitution) are altered, suggesting hardcoded or default values.

**First Three Experiments:**  
1. Replace Three.js with PyBullet or MuJoCo in the backend and re-run VisPhyBench to test for engine-specific performance differences.
2. Recruit human participants to write simulator code for a subset of scenes and compare video plausibility and parameter error against MLLM outputs.
3. Introduce templates featuring fluids (water) and deformable objects (cloth) to test the framework's scalability beyond rigid-body physics.

## Limitations
- Benchmark is restricted to rigid-body scenes; excludes fluids, soft bodies, and multi-agent interactions.
- Heavy reliance on Three.js may bias results; other physics engines remain untested.
- Template set is curated, potentially allowing overfitting to MLLM training data distributions.
- Metrics (DINO, CLIP) serve as proxies for physical accuracy rather than direct measurement of parameter error.
- 97.7% valid video rate depends on a controlled execution environment; performance may degrade with noisier, real-world code.

## Confidence
- **Code-driven evaluation feasibility**: Medium (promising but requires cross-domain and cross-engine validation)
- **GPT-5’s semantic/physical reasoning gap**: Medium (based on a single model; other architectures may differ)
- **Physics backend advantage**: Medium (only Three.js tested; other engines might yield smaller gains)
- **Diagnostic value of generated code**: Medium (necessitates systematic human evaluation of code quality)

## Next Checks
1. **Cross-engine validation**: Re-run VisPhyBench using alternative physics engines (PyBullet, MuJoCo) to confirm whether the observed backend superiority is engine-specific.
2. **Human baseline comparison**: Collect simulator code from human experts for 20 scenes and compare the resulting videos' motion plausibility and physical parameter accuracy against MLLM outputs.
3. **Domain expansion**: Add 50 new templates covering fluid dynamics and deformable materials to probe the framework's generalizability beyond rigid bodies.
