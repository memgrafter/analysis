# Progressive Searching for Retrieval in RAG

## Quick Facts
*   **arXiv ID:** 2602.07297
*   **Source URL:** https://arxiv.org/abs/2602.07297
*   **Reference count:** 16
*   **Primary result:** A progressive multi-stage KNN algorithm reduces 1M-document RAG query time by up to 5x while matching the top-1 accuracy of single-stage truncated searches.

## Executive Summary
The paper addresses the inherent trade-off in Retrieval-Augmented Generation (RAG) systems between retrieval accuracy and query latency caused by high-dimensional vector embeddings. It proposes a progressive searching algorithm that incrementally refines a candidate set of documents through a multi-stage process. This begins with a low-dimensional KNN search over the full corpus to generate an initial candidate pool, followed by successive higher-dimensional KNN searches on this shrinking pool. Evaluated on a 1M-document corpus, the method achieves significant speedups (e.g., 5x) compared to a single-stage search at the target high dimension, while preserving accuracy equivalent to that high-dimensional baseline.

## Method Summary
The proposed method is a multi-stage KNN retrieval process. Given a query embedding of full dimension `D_full`, the system is configured with a starting dimension `D_s`, a maximum dimension `D_m` (typically `D_full`), and an initial candidate count `K`. The algorithm first truncates the query and all document embeddings to `D_s` and performs an exact KNN search for the top `K` documents over the entire corpus. This `K`-document set becomes the candidate pool. It then enters a loop: the current search dimension is doubled (e.g., from `D_s` to `2*D_s`), the candidate count `K` is halved (minimum 1), and an exact KNN search for the new top `K` is run *only within the current candidate pool* using the higher-dimensional truncated vectors. This loop repeats until the current dimension reaches or exceeds `D_m`. A final exact 1-NN search is performed at full dimension `D_m` on the remaining candidate pool to retrieve the single best document. Baselines consist of single-stage exact KNN searches at fixed, truncated dimensions (e.g., 256D, 512D, up to full dimension).

## Key Results
*   On a 1M-document DBpedia corpus using Alibaba `gte-Qwen2` (3584D) embeddings, progressive search achieves a top-1 accuracy of 95.02% in 20.63 seconds, matching the accuracy of a single-stage full-dimension (3584D) search but completing in 99.36 seconds—a **5x speedup**.
*   The speedup increases with the target maximum dimension `D_m`, demonstrating better scalability for higher-dimensional embedding models.
*   Progressive retrieval accuracy consistently meets or slightly exceeds the accuracy of a single-stage truncated search at the same `D_m`, but never surpasses the theoretical upper bound of a full-corpus search at that `D_m`.

## Why This Works (Mechanism)
### Mechanism 1
Progressive search maintains accuracy by ensuring the true nearest neighbor survives filtering in early, low-dimensional stages. A coarse, low-dimensional KNN search over the full corpus identifies a broad candidate pool. The mechanism relies on the "distance concentration" phenomenon in high dimensions, where low-dimensional distance rankings approximate high-dimensional rankings for top candidates. The core assumption is that the rank of the true nearest neighbor is preserved or only slightly perturbed by truncation to `D_s`. The break condition is a failure to include the true neighbor in the initial pool, which would cause final accuracy to drop below the truncated full-dimension baseline.

### Mechanism 2
The method achieves speedup because the computational cost of high-dimensional search is amortized over a rapidly shrinking candidate set. The first stage (low-dim, full dataset) dominates total time. Each subsequent stage operates on a candidate pool orders of magnitude smaller than the full corpus. Therefore, even though dimensionality increases, the per-query cost grows sub-linearly or decreases because the `O(nd)` cost (n = pool size, d = dimension) is heavily dominated by the reduction in `n`. The break condition is an `initial K` that is too large, causing the candidate pool to remain too big in later stages and eroding the time benefit.

### Mechanism 3
Progressive search accuracy is bounded by the maximum target dimensionality `D_m`. The final stage performs an exact 1-NN search on the remaining candidate set using the vectors at `D_m`. Since no further refinement occurs beyond this dimension, the ranking cannot surpass what a full-dataset, exact search at `D_m` would produce. The accuracy is thus sandwiched between a lower bound (single-stage search at `D_s`) and an upper bound (single-stage search at `D_m`). The break condition is the candidate pool at the final stage missing the true nearest neighbor, which would cause accuracy to fall below the `D_m` truncated baseline.

## Foundational Learning
*   **Concept: K-Nearest Neighbors (KNN) search complexity.** The brute-force KNN search has a complexity of O(nd) per query (n = dataset size, d = dimensionality). This fundamental cost explains why searching a tiny pool at high dimension is cheap and why the first stage (low-dim, full n) dominates total query time in the progressive method.
    *   *Quick check:* Why does the first stage dominate total query time even though later stages use higher dimensions?
*   **Concept: Dimensionality vs. Retrieval Accuracy Trade-off.** Using fewer embedding dimensions reduces computational cost but harms retrieval accuracy. The progressive method's core premise is that this trade-off is non-linear for top-ranked items; low dimensions are sufficient for coarse filtering while high dimensions are needed for precise final re-ranking.
    *   *Quick check:* What property of high-dimensional spaces makes distance rankings less stable when dimensionality is reduced?
*   **Concept: Candidate Pool Filtering and Set Intersection.** Progressive search is a cascade of set reductions. The initial `K` and `D_s` control the size of the pool entering subsequent stages. Understanding this pool size decay is critical for predicting overall latency.
    *   *Quick check:* If `initial K` is doubled while keeping other parameters fixed, what happens to the final candidate pool size and expected query time?
*   **Concept: Distance Concentration.** In high-dimensional spaces, the contrast between nearest and farthest neighbor distances diminishes, making Euclidean distance less discriminative. This phenomenon justifies using lower dimensions for an initial, stable approximation of the nearest neighbor ranking.
    *   *Why needed:* Provides the theoretical basis for trusting low-dimensional rankings to retain true top candidates.
    *   *Quick check:* Does distance concentration mean all points become equidistant in high dimensions? What is the practical implication for vector search?

## Architecture Onboarding
*   **Component map:**
    Vector Database (stores 1M full-dim embeddings) -> Progressive Searcher (orchestrates multi-stage KNN) -> Evaluator (measures accuracy/time). Also, Embedding Model (generates query vector).
*   **Critical path:**
    Query -> Truncate to `D_s` -> Brute-force KNN(`K`) on full DB (1M) -> Candidate Pool (size ≤ K) -> Loop: `dim *=2`, `K = K/2` (min 1) -> Brute-force KNN(`K`) on Candidate Pool at new `dim` -> Update Candidate Pool -> Final: Exact 1-NN on Candidate Pool at `D_m`.
*   **Design tradeoffs:**
    *   `D_s` (starting dimension): Lower = faster first stage but higher risk of missing true neighbor (accuracy drop). Higher = slower first stage but better initial candidate quality.
    *   `K` (initial K): Larger = higher recall of true neighbor in pool but larger pool for later stages (slower). Must be large enough to ensure true neighbor survives.
    *   `D_m` (max dimension): Must be ≤ full model dim. Higher `D_m` can recover accuracy but adds final-stage cost. Setting `D_m` equal to full dim is typical to match truncated full-dim accuracy.
*   **Failure signatures:**
    *   **Accuracy collapse:** Progressive accuracy << truncated at `D_m`. Cause: `D_s` too low or `K` too small → true neighbor filtered out early.
    *   **No speedup:** Progressive runtime ≈ or > truncated at `D_m`. Cause: `K` too large → candidate pool remains large in high-dim stages; or `D_s` too high → first-stage cost dominates.
    *   **Non-determinism:** Runtime varies widely across runs. Cause: Running on shared cloud (Google Colab) with network jitter; need median over 10+ runs (as done in paper).
*   **First 3 experiments:**
    1.  **Vary `D_s` while fixing `K` and `D_m`:** Expect a U-shaped accuracy curve (low at very low `D_s`, plateau at adequate `D_s`) and monotonically decreasing runtime as `D_s` ↓. Identify minimal `D_s` that achieves >99% of full `D_m` accuracy.
    2.  **Vary `K` (initial) while fixing `D_s` and `D_m`:** Expect accuracy ↑ with `K` (recall) but runtime ↑ (pool size). Find `K` where accuracy plateaus.
    3.  **Fixed accuracy target sweep:** For a target accuracy (e.g., 94.5%), compare progressive runtime vs. single-stage truncated runtime across `D_m`. Demonstrate progressive shifts the entire accuracy-runtime curve leftward.

## Open Questions the Paper Calls Out
### Open Question 1
How can progressive search be integrated with approximate nearest neighbor (ANN) algorithms (e.g., HNSW, ANNOY) to further reduce query latency while maintaining accuracy?
*Basis:* The conclusion states future work will explore "integration with Approximate Nearest Neighbor Search methods [13], [16]". The current study uses exact KNN (brute-force). The trade-offs in combining progressive filtering with ANN indexing are unknown.
*What evidence would resolve:* Implement progressive search where each stage uses an ANN index on the candidate subset, measure accuracy/time vs. exact KNN baseline.

### Open Question 2
What systematic guidelines can be derived for configuring progressive search parameters (`D_s`, `K`, `D_m`) to achieve specific accuracy-speed trade-offs in RAG systems?
*Basis:* The introduction identifies a lack of "guidelines with respect to how to balance dimensionality, retrieval accuracy, and system efficiency". The paper explores parameter ranges but does not provide a model or heuristic.
*What evidence would resolve:* A large-scale parametric study varying corpus size, embedding model, and target accuracy, then deriving a predictive model or decision rules.

### Open Question 3
Does the choice of distance metric (Euclidean vs. cosine similarity) significantly impact the effectiveness of progressive search, and could metric selection be adaptive across stages?
*Basis:* The paper exclusively uses Euclidean distance, noting it's common for KNN, but embeddings often use cosine similarity. The methodology does not justify this choice or test alternatives.
*What evidence would resolve:* Replicate key experiments with cosine similarity and compare accuracy/time. Test mixed-metric strategies.

## Limitations
*   **Hyperparameter sensitivity:** Optimal `D_s`, `K`, `D_m` may vary significantly across different corpora and embedding models; the paper does not provide a full sweep or universal tuning rules.
*   **Assumption of rank preservation:** The mechanism relies on low-dimensional distances approximating high-dimensional rankings for the top candidate. This is inferred but not directly validated; it may fail on datasets where the true nearest neighbor is highly sensitive to minor dimensionality changes.
*   **Environment & generalizability:** Runtime experiments were conducted on Google Colab, which may not reflect production hardware. Evaluation is limited to a single corpus (DBpedia) and two specific embedding models.

## Confidence
*   **Accuracy preservation (M1):** *Medium*. Results show progressive accuracy matches truncated full-dim baselines, but the core assumption of rank preservation in low dimensions is not explicitly proven and may be dataset-dependent.
*   **Speedup (M2):** *High*. The mechanism is clearly demonstrated via candidate pool size reduction and runtime measurements across configurations.
*   **Bounded accuracy (M3):** *High*. Experimental results consistently show progressive accuracy never exceeding the `D_m` truncated baseline, confirming the theoretical upper bound.

## Next Checks
1.  **Ablation on initial `K`:** Systematically vary `K` while holding `D_s` and `D_m` constant. Measure (a) the recall rate of the true nearest neighbor in the initial candidate pool and (b) the final top-1 accuracy. This directly tests Mechanism 1's core assumption.
2.  **Cross-dataset validation:** Replicate the main experiments on at least two new, diverse corpora (e.g., a scientific paper corpus, a product review corpus) with different embedding models (e.g., `all-MiniLM-L6-v2`, `text-embedding-ada-002`). Test the robustness of the `D_s` and `K` heuristics.
3.  **Stage-wise profiling & hardware replication:** Decompose total query time per stage on a fixed, bare-metal server (not Colab) to confirm the first stage's dominance and sub-linear scaling. Repeat the core timing experiments with median of 50+ runs to reduce variance.
