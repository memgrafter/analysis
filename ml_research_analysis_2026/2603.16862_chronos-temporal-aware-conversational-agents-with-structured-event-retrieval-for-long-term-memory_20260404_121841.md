# Chronos: Temporal-Aware Conversational Agents with Structured Event Retrieval for Long-Term Memory

## Quick Facts
- **arXiv ID:** 2603.16862
- **Source URL:** https://arxiv.org/abs/2603.16862
- **Reference count:** 5
- **Primary result:** Chronos achieves 92.60% (GPT-4o) and 95.60% (Claude Opus 4.6) accuracy on LongMemEvalS, a 7.67% relative improvement over prior best.

## Executive Summary
Chronos addresses the key limitation of existing conversational memory systems: their inability to accurately reason about time across long interaction histories. It introduces a dual-calendar framework that separately indexes structured event tuples (with normalized datetime ranges) and raw dialogue turns. At query time, dynamic prompting generates tailored retrieval guidance, and an agentic tool-calling loop iteratively searches both calendars to gather evidence for complex temporal and multi-session questions.

Evaluated on the LongMemEvalS benchmark, Chronos attains state-of-the-art accuracy—92.60% with GPT-4o and 95.60% with Claude Opus 4.6—improving over the previous best by 7.67% relative. Ablation studies show the event calendar component alone contributes a 58.9% gain over a turn-only baseline, underscoring the importance of explicit temporal structuring.

## Method Summary
Chronos processes multi-session dialogues in two phases. In the offline ingestion phase, it uses an LLM to extract subject-verb-object event tuples with normalized ISO 8601 datetime ranges from 25-turn chunks (5-turn overlap), along with lexical aliases. These events are vector-indexed in an event calendar, while raw turns are indexed separately in a turn calendar.

At query time, a dynamic prompt generator (Gemini 3 Flash) analyzes the question to produce 1–5 bullet points of retrieval guidance. The agent then performs initial turn retrieval: dense vector search (top‑100), reranking with Cohere Rerank v3, and context expansion to a top‑15 set. A ReAct‑style agent, equipped with tools for vector search and grep on both calendars, iteratively gathers additional evidence based on the dynamic prompt. The final answer is synthesized from the collected context.

## Key Results
- **State of the art:** Chronos Low (GPT‑4o) 92.60%, Chronos High (Claude Opus 4.6) 95.60% accuracy on LongMemEvalS.
- **Relative gain:** 7.67% improvement over prior best.
- **Component impact:** Event calendar alone yields a 58.9% gain over turn‑only baseline.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Selective extraction of temporally‑grounded events into a structured calendar, separate from raw turns, improves retrieval precision for time‑sensitive queries without sacrificing semantic context.
- **Mechanism:** An LLM‑powered pipeline decomposes dialogue turns into (subject, verb, object) tuples with normalized ISO 8601 datetime ranges (handling explicit, relative, and ambiguous expressions) and generates lexical aliases. This structured event index enables efficient, precise temporal filtering (e.g., "events within May 2024") during retrieval, while the parallel turn index preserves full conversational context for semantic understanding and reference resolution.
- **Core assumption:** Query time is the optimal moment to determine what information to structure, avoiding the context entropy of pre‑computed, query‑independent knowledge graphs.
- **Evidence anchors:** [abstract] "decomposes raw dialogue into subject‑verb‑object event tuples with resolved datetime ranges… indexing them in a structured event calendar alongside a turn calendar." [section 3.1] "The event extraction pipeline identifies temporally‑grounded occurrences… multi‑resolution temporal normalization to convert natural language time references into precise ISO 8601 datetime ranges."

### Mechanism 2
- **Claim:** Dynamic prompting—generating query‑specific retrieval guidance—adapts the agent's reasoning strategy to the diverse demands of long‑term memory questions (temporal filtering, preference recall, multi‑hop aggregation) more effectively than static prompts.
- **Mechanism:** A lightweight LLM (Gemini 3 Flash) analyzes each user query to output 1‑5 concrete bullets directing the agent's attention (e.g., "Pay close attention to… the most recent purchase"). This preamble is integrated into the agent's system prompt, conditioning its tool‑calling and reasoning pattern without requiring separate models or classifiers per question type.
- **Core assumption:** The retrieval strategy (what to search for, how to filter by time, whether to aggregate) must be query‑conditioned; a one‑size‑fits‑all prompt cannot optimally handle the six LongMemEvalS categories.
- **Evidence anchors:** [abstract] "dynamic prompting generates tailored retrieval guidance for each question, directing the agent on what to retrieve, how to filter across time ranges, and how to approach multi‑hop reasoning." [section 3.2] "Rather than reformulating the search query itself, dynamic prompting analyzes each question to generate retrieval guidance tailored to the agent’s reasoning process."

### Mechanism 3
- **Claim:** An agentic tool‑calling loop that iteratively searches both calendars (event and turn) with vector and grep tools, guided by dynamic prompting and initialized with pre‑retrieved turn context, enables robust multi‑hop reasoning over long histories.
- **Mechanism:** The agent starts with top‑15 semantically relevant turns (dense search + rerank + context expansion). It then uses ReAct‑style reasoning to decide when to invoke `search_events`, `grep_events`, `search_turns`, or `grep_turns`, constraining searches by datetime ranges derived from the dynamic guidance. This allows it to cross‑validate events with source dialogue, refine temporal constraints, and gather missing evidence across multiple retrieval steps.
- **Core assumption:** Complex memory queries require interactive retrieval; a single‑shot retrieval pass cannot gather sufficient, correctly filtered evidence from a dual‑index system spanning months of conversation.
- **Evidence anchors:** [abstract] "an agentic tool‑calling loop iterates over both calendars." [section 3.4] "The Chronos Agent is an LLM agent with native tool‑calling capabilities for iterative memory retrieval… Tool calls execute asynchronously… Retrieved results… are appended to the agent’s message history, progressively building up contextual information." [section 4.3] "Chronos’s agentic design allows it to proactively retrieve additional context when initial evidence is insufficient."

## Foundational Learning

### Concept: Hybrid Dense-Sparse Retrieval
- **Why needed here:** Chronos's initial retrieval uses dense vector search (cosine similarity) for semantic matching, then applies a cross‑encoder reranker (Cohere Rerank v3) to improve precision. Understanding this pipeline is key to grasping how the system narrows thousands of turns to a relevant initial context batch.
- **Quick check question:** Why might dense retrieval alone be insufficient for long‑term memory queries, and how does reranking address this gap?

### Concept: Temporal Normalization in NLP
- **Why needed here:** The event extractor converts expressions like "last month" or "the week after my vacation" into precise datetime ranges relative to the conversation turn's timestamp. This transforms fuzzy temporal language into machine‑interpretable constraints for filtering.
- **Quick check question:** How would you represent the temporal scope of the phrase "recently" from a turn dated 2024‑03‑15 as an ISO 8601 datetime range?

### Concept: Agentic RAG (ReAct Pattern)
- **Why needed here:** The Chronos Agent uses a thought‑action‑observation loop to decide when to retrieve more information. This is core to its ability to handle multi‑hop queries that require evidence gathering from both calendars.
- **Quick check question:** In a ReAct loop, what triggers the agent to stop retrieving and produce a final answer, and what risks arise if it stops too early or too late?

## Architecture Onboarding

**Component map:**  
Ingestion Pipeline: Raw dialogue → Event Extractor (LLM) → Structured Event Tuples (with datetime ranges, aliases) + Raw Turns.  
Indexing: Events → Event Calendar (vector index); Turns → Turn Calendar (vector index).  
Query Processing: User Query → Dynamic Prompt Generator → Tailored System Prompt + Pre‑retrieved Turn Context (from initial dense+rerank+expansion).  
Agent Execution: Chronos Agent (LLM with tools) iteratively calls `search_events`, `grep_events`, `search_turns`, or `grep_turns` using the dynamic prompt, then synthesizes answer.

**Critical path:** The dual‑index creation (Step 1‑2) is offline prerequisite. At query time, the critical path is: Dynamic Prompt → Initial Turn Retrieval → Agent Tool‑Calling Loop → Answer.

**Design tradeoffs:**  
- Storage vs. Precision: Dual calendars increase storage but enable precise temporal filtering; tradeoff justified by gains on temporal/MS/KU categories.  
- Inference Cost vs. Accuracy: Agentic tool‑calling adds latency/cost per query versus single‑shot retrieval, but is necessary for multi‑hop reasoning; ablation shows ~14‑16 pt drop without it.  
- Extraction Overhead vs. Relevance: LLM‑based event extraction adds offline compute, but selective extraction (only temporal events) keeps event index compact vs. full knowledge graphs.

**Failure signatures:**  
- High errors in MS/KU/TR categories: Event extraction failed (missing/inaccurate datetime) or agent failed to use event calendar/grep tools.  
- High errors in SSP category: Dynamic prompting misdirected agent on preference queries, or turn retrieval missed relevant preference statements.  
- Consistently low retrieval recall: Initial turn retrieval (dense+rerank) is poor, seeding agent with bad context; check embedding model quality and reranker performance.  
- Agent loops excessively or fabricates: Tool descriptions unclear or model lacks capability to abstain when evidence insufficient.

**First 3 experiments:**  
1. Event Extraction Sanity Check: Process a small, hand‑annotated dialogue session; manually verify that each extracted event has a correct, granular datetime range and that aliases capture paraphrases; measure precision/recall against gold event tuples.  
2. Initial Retrieval Recall@k: For a held‑out set of questions, compute if the gold answer turns are within the top‑15 pre‑retrieved turns after reranking; low recall would cripple the agent.  
3. Tool Call Audit: Run the agent on 20 diverse questions, logging every tool call and its arguments; audit whether the agent correctly invoked the event calendar for temporal queries, used datetime filters, and cross‑referenced events with source turns; look for patterns of missing tool calls or incorrect filters.

## Open Questions the Paper Calls Out

1. **What level of explicit temporal representation optimizes cross‑session reasoning accuracy?**  
   *Basis in paper:* Section 2.1 states that benchmarks leave open the question of how much explicit temporal representation is needed.  
   *Why unresolved:* Existing works do not vary temporal structuring in memory systems to find the optimal balance.  
   *What evidence would resolve it:* Controlled experiments manipulating temporal detail in event extraction and measuring accuracy on isolated cross‑session tasks.

2. **How can storage overhead from dual indexing be minimized while preserving retrieval performance?**  
   *Basis in paper:* Section 5 identifies increased storage from separate turn and event indexes as a limitation.  
   *Why unresolved:* Dual indexing doubles storage compared to turn‑only approaches, limiting scalability.  
   *What evidence would resolve it:* New indexing schemes that unify or compress event and turn data, evaluated on storage‑accuracy trade‑offs.

3. **Can event traces be utilized to update model weights for enhanced long‑term memory?**  
   *Basis in paper:* Section 6 proposes learning from retrieved events as future work.  
   *Why unresolved:* Current systems retrieve events but do not integrate them into model training for continuous improvement.  
   *What evidence would resolve it:* Frameworks where event sequences fine‑tune the model, with experiments showing improved memory retention.

4. **How can retrieval failures over large histories be reduced in agentic memory systems?**  
   *Basis in paper:* Section 4.3 reports retrieval failures as the top error, even with guidance.  
   *Why unresolved:* LLMs fail to retrieve from large indexes, leading to incomplete context.  
   *What evidence would resolve it:* Scalable retrieval algorithms tested on dialogues with thousands of turns, measuring recall and reasoning accuracy.

## Limitations
- Event extraction details (LLM, prompt, normalization logic) and datetime accuracy are unspecified, hindering reproducibility.
- Dynamic prompting and agent tool‑calling specifics (retry logic, top‑k selection) are opaque, limiting understanding of failure modes.
- LongMemEvalS judge model and category‑specific prompts are undocumented, and known benchmark inconsistencies affect score reliability.

## Confidence
- Selective event extraction + dual calendar: Medium  
- Dynamic prompting: Medium  
- Agentic tool‑calling loop: High  
- Overall SOTA performance: Medium‑High
