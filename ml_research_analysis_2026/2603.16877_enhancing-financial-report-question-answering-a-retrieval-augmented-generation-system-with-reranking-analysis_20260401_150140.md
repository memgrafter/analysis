# Enhancing Financial Report Question-Answering: A Retrieval-Augmented Generation System with Reranking Analysis

## Quick Facts
- **arXiv ID**: 2603.16877  
- **Source URL**: https://arxiv.org/abs/2603.16877  
- **Reference count**: 16  
- **Primary result**: Neural reranking improves answer correctness (score ≥8) from 33.5% to 49.0% (+15.5 pp) and reduces completely incorrect answers (score=1) from 35.3% to 22.5% (-12.8 pp) on the FinDER benchmark.

## Executive Summary
The paper addresses the challenge of extracting information from lengthy 10‑K financial reports by proposing a Retrieval‑Augmented Generation (RAG) system. The core approach combines hybrid retrieval (full‑text and semantic) using Reciprocal Rank Fusion with neural reranking via a cross‑encoder model. Evaluated on 1,500 queries from the FinDER benchmark, the reranker yields a 15.5 percentage point increase in basically correct answers (score ≥8) and a 12.8 percentage point decrease in completely incorrect answers (score =1), with consistent gains across five independent test groups.

## Method Summary
The pipeline first preprocesses 10‑K reports: HTML is rendered to PDF with Playwright, text extracted via PyMuPDF, then chunked into 2,500‑character segments with 50% overlap. Chunks are indexed for full‑text search (SQLite FTS5) and semantic search (FAISS with `text-embedding-3-small`). At query time, GPT‑4.1 rewrites the user question into a clarified semantic query and a set of keywords. Full‑text search retrieves the top‑20 candidates based on keywords; semantic search retrieves the top‑30 by embedding similarity. These lists are fused through Reciprocal Rank Fusion (k=60) to produce a candidate set. A neural reranker (Jina Reranker v2) re‑scores up to 30 candidates, and adaptive cutoff heuristics (cumulative probability threshold 0.45, score cliff 0.15) select the final context passages. Finally, GPT‑4.1 (temperature=0) generates an answer grounded in the selected context.

## Key Results
- Basically correct answers (score ≥8) increased from 33.5% (without reranking) to 49.0% (with reranking), a 15.5 percentage point improvement.  
- Completely incorrect answers (score =1) decreased from 35.3% to 22.5%, a 12.8 percentage point reduction.  
- Improvements were consistent across all five independent test groups from FinDER.

## Why This Works (Mechanism)
### Hybrid Search with Reciprocal Rank Fusion (RRF)
**Claim**: Combining full‑text and semantic retrieval yields more comprehensive candidate recall for financial queries than either method alone.  
**Mechanism**: Full‑text search excels at exact matches for domain‑specific terminology and named entities, while semantic search captures conceptual similarity for ambiguous phrasing. RRF fuses their rankings without training, leveraging complementary strengths.  
**Core assumption**: Financial queries contain both precise terms (benefiting FTS) and nuanced concepts (benefiting semantic search); hybrid retrieval increases the chance that relevant chunks appear in the candidate set.  
**Evidence**: The paper highlights hybrid search in the abstract and details RRF in section III.B.2; neighboring works on metadata‑driven RAG support hybrid strategies.  
**Break condition**: If one retrieval mode consistently dominates (e.g., semantic search captures all relevant chunks), hybrid search’s overhead may not be justified.

### Neural Reranking with Cross‑Encoder
**Claim**: A cross‑encoder reranker significantly improves precision by filtering out superficially relevant but substantively poor chunks from hybrid results.  
**Mechanism**: Jina Reranker v2 jointly encodes query‑chunk pairs, modeling fine‑grained interactions missed by bi‑encoder semantic search. It re‑scores the top ~30 candidates, promoting truly relevant passages and suppressing false positives.  
**Core assumption**: First‑stage retrieval (FTS+semantic+RRF) includes many chunks that score well on superficial metrics but lack substantive relevance for accurate answer generation.  
**Evidence**: The abstract reports the 15.5 pp correctness gain; section V.B.1 states the cross‑encoder identifies genuine semantic relevance and that RRF may include superficially matching chunks.  
**Break condition**: If the first‑stage retrieval already has near‑perfect precision (very few irrelevant chunks in top‑K), reranking’s incremental benefit may not outweigh its computational cost.

### Adaptive Cutoff Strategies
**Claim**: Dynamic cutoff during reranking prevents low‑quality context from diluting the generator’s input, directly contributing to reduced error rates.  
**Mechanism**: Instead of a fixed top‑K, two heuristics are applied: (1) cumulative probability threshold (0.45) stops when remaining probability mass is low; (2) score cliff detection (0.15 drop) stops if scores fall sharply. Both aim to include only high‑confidence passages.  
**Core assumption**: A smaller, high‑signal context leads to better generation than a larger context contaminated by marginally relevant or irrelevant passages.  
**Evidence**: The paper states these strategies prevent dilution (section III.B.3); the error rate (Score=1) drops by 12.8 pp with reranking.  
**Break condition**: If the reranker’s score distribution is flat (no clear cliffs) and cumulative probability declines slowly, a fixed top‑K might perform similarly with less complexity.

## Foundational Learning
- **Hybrid Search & Reciprocal Rank Fusion (RRF)**  
  *Why needed*: Financial queries mix precise terms (e.g., “EBITDA”) and conceptual questions (“growth strategy”). Single‑method retrieval fails on one aspect.  
  *Quick check*: Why use RRF instead of learning‑to‑rank for fusing FTS and semantic results in a financial RAG system?

- **Cross‑Encoder Reranking**  
  *Why needed*: Bi‑encoder semantic search (used in first stage) approximates similarity but cannot model deep query‑document interactions. Cross‑encoders provide finer‑grained relevance scoring critical for noisy financial text.  
  *Quick check*: What architectural difference allows a cross‑encoder to capture relevance signals a bi‑encoder misses, and why is this important for 10‑K reports?

- **Adaptive Context Pruning**  
  *Why needed*: Passing too many retrieved chunks risks introducing noise. Adaptive cutoffs aim to provide the generator with a concise, high‑signal context.  
  *Quick check*: How does “score cliff detection” cutoff differ from simply taking the top‑5 reranked chunks, and what risk does it mitigate?

## Architecture Onboarding
**Component map**  
Offline: HTML → PDF (Playwright) → Text (PyMuPDF) → Chunking (2.5k chars, 50% overlap) → Store in SQLite FTS5 and FAISS (`text-embedding-3-small`).  
Online: User query → Rewriting (GPT‑4.1) → Split into clarified semantic query + keywords → Hybrid retrieval (FTS top‑20, semantic top‑30) → RRF (k=60) → Neural reranking (Jina v2, up to 30) → Adaptive cutoff → Context assembly → Answer generation (GPT‑4.1, temp=0).

**Critical path**: Query rewriting → Hybrid retrieval → Reranking → Generation. The reranker is the pivotal performance lever.

**Design tradeoffs**  
- Chunk size/overlap: Larger chunks preserve context but reduce retrieval granularity; 50% overlap mitigates boundary loss.  
- Reranker cost vs. gain: Jina v2 adds latency/API cost but delivers ~15.5 pp correctness gain; deployment must weigh this against error tolerance.  
- Adaptive cutoff heuristics: More complex than fixed‑K but optimize context quality; parameters (0.45 cumulative, 0.15 cliff) are tuned on validation data (details not provided).

**Failure signatures**  
- High `Score=1` rate (>25%) despite reranking → likely retrieval failure (relevant chunk not in top‑30 hybrid) or query ambiguity.  
- Low variance across reranker scores → adaptive cutoffs may not filter effectively; consider fixed top‑K.  
- Reranker API timeouts/failures → fallback to RRF top‑10 (as in “No Reranking” config) to maintain availability.

**First 3 experiments**  
1. Baseline retrieval sanity check: For 50 FinDER queries, manually inspect top‑5 RRF‑fused chunks to confirm they contain relevant information using ground truth evidence.  
2. Reranker ablation: Run full pipeline on 100 queries with and without reranking (same hybrid candidates). Measure delta in LLM‑as‑judge scores.  
3. Cutoff strategy evaluation: Compare (a) reranker top‑5 fixed, (b) adaptive cutoff as implemented, (c) reranker top‑10 fixed on answer quality.

## Open Questions the Paper Calls Out
### 1. Graph‑based retrieval for multi‑hop queries  
The authors identify multi‑hop reasoning as a key failure pattern and propose graph‑based retrieval to better model relationships between document sections. Current chunk‑based hybrid retrieval struggles with evidence scattered across non‑adjacent sections. A controlled A/B test of a graph‑based retriever on multi‑hop FinDER queries would provide evidence.

### 2. LLM‑as‑judge evaluation bias  
The paper acknowledges that LLM‑as‑judge may prefer verbose answers or penalize valid alternative phrasings. Without human assessment, it’s unclear whether the reported 15.5 pp gain reflects true semantic accuracy or judge artifacts. A blinded human evaluation on a significant sample (e.g., 500 queries) using the same rubric is needed.

### 3. Cost‑performance trade‑off of neural reranking  
The paper cites computational cost as a limitation and suggests more efficient rerankers but provides no empirical analysis. The point of diminishing returns—whether smaller/cheaper rerankers lose disproportionate accuracy or if fewer candidates suffice—is unexplored. Systematic variation of reranker size, quantization, and candidate pool size to measure performance vs. cost would resolve this.

### 4. Multi‑modal integration of tables and figures  
10‑K reports contain critical data in tables and strategic insights in charts. The text‑only system discards this information. The potential magnitude of improvement from multi‑modal retrieval—and the technical challenges of aligning visual/numerical data with textual queries—remains open. A prototype that extracts and encodes tables and figures, then evaluates on FinDER queries referencing such content, would provide evidence.

## Limitations
- FinDER dataset source/access method is unspecified; sample definitions (1,500 queries) are not provided, hindering reproducibility.  
- Playwright HTML→PDF conversion parameters are undocumented, risking inconsistent text extraction and chunk content.  
- Adaptive cutoff thresholds (0.45 cumulative, 0.15 cliff) lack validation details; their impact and tuning set size are unclear.
