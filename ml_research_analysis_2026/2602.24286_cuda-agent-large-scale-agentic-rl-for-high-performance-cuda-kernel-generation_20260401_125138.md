# CUDA Agent: Large-Scale Agentic RL for High-Performance CUDA Kernel Generation

## Quick Facts
- **ArXiv ID**: 2602.24286
- **Source URL**: https://arxiv.org/abs/2602.24286
- **Reference count**: 40
- **Primary result**: CUDA Agent achieves up to 100% faster rate than `torch.compile` on KernelBench Level-1/2 tasks, 92% on Level-3, and outperforms Claude Opus 4.5 and Gemini 3 Pro by ~40% on hardest Level-3 tasks.

## Executive Summary
Generating high-performance CUDA kernels for deep learning is a complex optimization challenge. This paper introduces CUDA Agent, a large-scale agentic reinforcement learning system that automates CUDA kernel generation and optimization. The solution integrates three core components: a scalable data synthesis pipeline that produces diverse optimization tasks; a skill-augmented agent environment with automated verification and profiling to ensure reliable reward signals; and a multi-stage RL training regimen that stabilizes learning over long horizons. Evaluated on the KernelBench benchmark, CUDA Agent dramatically outperforms the production compiler `torch.compile`, achieving perfect or near-perfect faster rates on Level-1, -2, and -3 splits (100%, 100%, 92%). Moreover, it surpasses state-of-the-art proprietary models by approximately 40% on the most difficult Level-3 tasks. Ablations confirm the necessity of each proposed component, demonstrating a viable path toward fully automated high-performance GPU code generation.

## Method Summary
The method centers on three interconnected subsystems. First, the data synthesis pipeline mines seed operators from stable libraries (PyTorch, Transformers) and uses an LLM to combinatorially fuse up to five operators into new tasks, expanding the optimization landscape. An execution-based filter removes stochastic, trivial, or non-executable samples, yielding a high-quality training set of 6,000 operator samples (CUDA-Agent-Ops-6K). Second, the agent operates within an OpenHands-style tool sandbox, where a fixed `SKILL.md` specification enforces a four-step iterative process: profile native code, implement custom kernels, compile and test, and iterate toward a 5% speedup. Verification and profiling scripts are permission-locked to prevent reward hacking, and correctness is enforced via five random inputs. Third, the training pipeline employs a multi-stage warm-up to stabilize PPO over up to 150 steps and a 128k token context: single-turn PPO adapts the base model to direct CUDA generation; Rejection Fine-Tuning (RFT) on high-reward trajectories initializes the actor with a strong behavioral prior; and Value Pretraining pre-trains the critic on collected trajectories to produce accurate advantage estimates from the start. The base model is Seed1.6, a 23B active parameter mixture-of-experts model. During evaluation, the agent receives a KernelBench task and may use up to 200 turns to produce a kernel that passes correctness tests and achieves speedup over `torch.compile`.

## Key Results
- Faster Rate over `torch.compile`: 100% (Level-1), 100% (Level-2), 92% (Level-3).
- Relative performance: ~40% better than Claude Opus 4.5 and Gemini 3 Pro on Level-3 tasks.
- Ablation evidence: Removing any of the three core components (data pipeline, agent loop, warm-up stages) leads to significant degradation in correctness and speedup.

## Why This Works (Mechanism)

### Mechanism 1: Scalable, Non-Random Data Synthesis
Claim: A scalable, non-random data synthesis pipeline produces a diverse training distribution of CUDA optimization problems that mirrors real-world kernel task complexity, enabling the model to learn generalizable strategies rather than overfit to specific patterns.

Mechanism: The pipeline crawls seed operators from stable libraries (torch, transformers), then uses an LLM to combinatorially fuse up to 5 operators into new tasks. Fusion reshapes the optimization landscape (e.g., avoiding intermediate memory materialization). Execution-based filters remove stochastic, trivial, or non-executable tasks, ensuring each sample is a valid, deterministic optimization challenge with a reasonable workload (1–100ms eager runtime).

Core assumption: The space of useful CUDA optimization problems can be systematically expanded through controlled fusion of known primitives, and execution-based filtering reliably proxies for "interesting" optimization potential.

Evidence anchors: [abstract] mentions the scalable data synthesis pipeline; [section 3.1] details the three-stage pipeline and CUDA-Agent-Ops-6K composition; related works (e.g., CudaForge, ASTRA) lack comparable pipeline details, suggesting it is differentiating but causal evidence depends on ablations.

Break condition: If combinatorial synthesis produces tasks where the fused operator’s optimal kernel is trivially the sum of individually optimal kernels, fusion fails to create a genuinely new challenge. Filtering criteria might also incorrectly discard tasks with subtle optimization opportunities.

### Mechanism 2: Skill-Augmented Agent Environment
Claim: Embedding CUDA development knowledge into a structured "Agent Skill" (SKILL.md) and a sandboxed, tool-rich environment provides a consistent, correct, and hack-resistant workflow that transforms the base model into an active, iterative optimizer capable of learning from execution feedback.

Mechanism: The agent loop (based on OpenHands/ReAct) supplies shell tools (Bash, Edit, Glob) and enforces a fixed 4-step process via SKILL.md: profile native code, implement custom kernels, compile/test, and iterate toward a 5%+ speedup. The sandbox’s verification and profiling scripts are permission-locked to prevent reward hacking; correctness is checked with 5 random inputs, and timing includes warm-up and averaging.

Core assumption: Standardizing the developer workflow into a machine-readable skill specification, combined with a secure execution sandbox, suffices to teach a minimally pretrained base model the iterative process of kernel writing, debugging, and optimization.

Evidence anchors: [abstract] highlights the skill-augmented environment; [section 3.2] presents full SKILL.md content, tool list, and anti-hacking measures (file permissions,禁止 fallbacks, 5-input correctness); [section 4.3.1] shows that removing the agent loop (single-turn only) drastically reduces both correctness and optimization quality.

Break condition: If the skill specification omits critical patterns (e.g., tensor cores) or sandbox isolation fails (allowing modification of verification scripts), the agent cannot learn correct behaviors or receives misleading rewards, leading to collapse or hacking.

### Mechanism 3: Stabilized RL via Multi-Stage Warm-Up
Claim: A multi-stage warm-up strategy (Single-Turn RL → RFT → Value Pretraining) mitigates the severe distribution mismatch between the base model’s pretraining (web code) and the CUDA agentic task, stabilizing PPO training over 150+ steps and preventing reward collapse.

Mechanism: Single-turn PPO first adapts the base model to direct CUDA kernel generation. Rejection Fine-Tuning (RFT) on high-reward multi-turn trajectories initializes the actor with a strong behavioral prior, controlling entropy growth. Value Pretraining uses those trajectories to pre-train the critic, providing accurate advantage estimates from step one and preventing pathological long-horizon exploration.

Core assumption: Instability in agentic RL for specialized domains stems from actor output distribution collapse and critic inability to estimate value in the new action space—both addressable by priming on successful multi-turn trajectories before online PPO.

Evidence anchors: [section 3.3] describes the root cause ("<0.01% of pretraining data is CUDA") and details RFT and Value Pretraining; [section 4.3.3] presents ablations: without RFT, training reward collapses with entropy surge; without Value Pretraining, explained variance is low and response lengths explode; [figure 4 & 5] empirically validate entropy and value stability.

Break condition: If the single-turn RL stage yields no positive-reward trajectories, RFT receives no viable data and actor initialization remains poor. If trajectory diversity for Value Pretraining is limited (e.g., all short, successful paths), the critic may not generalize to longer, exploratory trajectories during PPO.

## Foundational Learning

- **Proximal Policy Optimization (PPO)**: PPO with clipped objectives and Generalized Advantage Estimation (GAE) is the core RL algorithm used throughout. Why needed: Understanding the clipped surrogate objective and GAE is necessary to grasp training stabilization and interpret ablations on critic initialization. Quick check: How does clipping the importance sampling ratio (ρ) in PPO prevent destructive policy updates, and what problem does a poorly initialized critic cause for GAE estimates in long-horizon agentic tasks?

- **CUDA kernel optimization fundamentals**: Concepts like memory coalescing, shared memory, kernel fusion, and occupancy underpin the agent’s actions and reward signals. Why needed: To interpret why fusing a matmul with a ReLU is beneficial and to analyze case studies (e.g., Appendix D). Quick check: Why does fusing a sequence of element-wise ops and a GEMM into a single kernel typically yield a speedup beyond just reducing kernel launch overhead?

- **Agent frameworks (ReAct, OpenHands)**: The agent loop is built on ReAct (reasoning + acting) and OpenHands tool abstractions (Bash, Edit, Glob). Why needed: This paradigm defines the structure of states, actions, and observations. Quick check: In a ReAct-style agent loop, what is the role of the "observation" after an action (e.g., running `python verification.py`), and how does it differ from the initial "thought"?

## Architecture Onboarding

- **Component Map**: Data Pipeline → Agent Environment → RL Training → Evaluation. More specifically: (Seed1.6 base model + CUDA-Agent-Ops-6K dataset) → Agent loop (OpenHands tools + SKILL.md + sandbox with locked scripts) → Single-turn PPO → Trajectory collection → RFT (actor init) + Value Pretraining (critic init) → Multi-turn PPO (≤150 steps, 128k context, ≤200 turns) → KernelBench evaluation.

- **Critical Path**: The core development sequence: construct the synthetic dataset → design the agent loop with tools and skill specification → perform single-turn PPO adaptation → collect multi-turn trajectories → initialize actor and critic via RFT and Value Pretraining → run full PPO → evaluate on KernelBench.

- **Design Tradeoffs**:
  - Context length (128k) vs. stability: Longer contexts allow complex debugging but increase memory and risk degenerate trajectories; mitigated by warm-up stages.
  - Reward sparsity: Using a discrete reward (-1,1,2,3) based on correctness and speedup milestones offers cleaner learning than continuous speedup ratio but may lose granularity.
  - Sandbox isolation: Process-level separation with dedicated GPU pools (128 H20s) ensures clean timing and prevents interference, but incurs massive computational cost and limits accessibility.

- **Failure Signatures**:
  - Training collapse: rapid reward drop concurrent with actor entropy spike → indicates failed RFT (no good trajectories for rejection sampling).
  - Exploding response lengths: critic fails to assign low value to futile long trajectories → indicates failed Value Pretraining.
  - High pass rate but low speedup: model generates correct but naive kernels (e.g., no fusion) → suggests reward shaping issue or insufficient exposure to optimization patterns.

- **First 3 Experiments**:
  1. **Data pipeline validation**: Apply the three-stage synthesis to a small seed set (e.g., 10 torch ops). Verify >80% of fused tasks pass all four filters (executable, deterministic, non-trivial, time-bounded). Check AST similarity against KernelBench is below the decontamination threshold.
  2. **Agent loop unit test**: Freeze the base model and run 5 trajectories on a Level-1 KernelBench task. Ensure the agent can execute all required tool calls (profiling.py, editing kernels, compile.sh, verification.py) and that at least one trajectory achieves >5% speedup.
  3. **Warm-up stage ablation**: Train single-turn PPO for 10 steps. Compare: (a) full RFT + Value Pretraining versus (b) RFT only or no warm-up. Monitor actor entropy and 10-step PPO reward curve. Expect entropy spike and collapse without both RFT and Value Pretraining.

## Open Questions the Paper Calls Out

1. **Comparison with TVM**: How does CUDA Agent perform when evaluated against TVM or integrated with it? The authors note in Section E that they did not compare due to integration challenges. TVM may offer a stronger baseline, making this comparison essential to understand the relative merits of learned kernel generation versus traditional compiler tuning. Resolution would require direct evaluation of CUDA Agent-generated kernels via TVM’s tuning stack or engineering a hybrid integration.
2. **Reducing GPU resource requirements**: Training relied on 128 H20 GPUs, creating a barrier to adoption and limiting scalability experiments. Evidence to resolve this would be methods that achieve similar performance with far fewer GPUs, such as sample-efficient RL, simulation-based reward models, or curriculum learning strategies.
3. **Alternative reward designs**: The discrete reward outperformed raw speedup, but other designs (continuous gradients, potential-based shaping, multi-objective rewards) might improve stability and final speedup. Systematic ablation of various reward formulations under identical training conditions, measuring both convergence and final performance, would provide evidence.
4. **Generalization to other base models**: All experiments used Seed1.6; it is unclear whether the full pipeline transfers to other architectures (e.g., open-source models). Replicating the entire training pipeline (data, environment, RL) on at least one additional base model (e.g., CodeLlama-34b) and reporting KernelBench results would resolve this.

## Limitations
- The synthetic data pipeline may not capture the full diversity of real-world CUDA optimizations; fused operator tasks might yield trivial solutions that escape filtering.
- The fixed `SKILL.md` specification might omit critical optimization patterns (e.g., tensor cores), and sandbox isolation could fail in unexamined edge cases, permitting reward hacking.
- Training stability and final performance appear tightly coupled to the proprietary Seed1.6 model and undisclosed hyperparameters, raising concerns about generalizability to other base models.

## Confidence
- Data pipeline efficacy: Medium
- Agent environment design: High
- RL stability via warm-up: Medium-High
