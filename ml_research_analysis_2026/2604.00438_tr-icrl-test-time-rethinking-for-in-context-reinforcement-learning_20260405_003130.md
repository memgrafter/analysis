# TR-ICRL: Test-Time Rethinking for In-Context Reinforcement Learning

## Quick Facts
- **arXiv ID:** 2604.00438  
- **Source URL:** https://arxiv.org/abs/2604.00438  
- **Reference count:** 21  
- **Primary result:** TR-ICRL yields large absolute gains on reasoning and medical benchmarks (e.g., Qwen2.5-7B +58.91% on AMC, +137.59% on AIME2024; Llama3.1-8B +21.22% on MedQA) in a fully unsupervised test-time setting.

## Executive Summary
TR-ICRL enhances LLM reasoning at test time by synthesizing supervision from unlabeled data. It retrieves relevant examples, generates multiple candidate answers, derives pseudo-labels via majority voting, assigns binary rewards, and produces formative feedback—all within an iterative loop that refines the model’s context before a final majority vote. Evaluations on AMC, AIME2024, and MedQA show substantial improvements, scaling across model architectures and domains without any label access during inference.

## Method Summary
The method comprises two stages. First, a retriever (embedding model + cosine similarity) selects the top‑N semantically similar instances from an unlabeled set. Second, for each retrieved instance, the model generates K candidate answers in parallel. A pseudo‑label is formed by majority vote; each candidate then receives a binary reward (correct if equal to the pseudo‑label, else wrong) and the model generates formative feedback conditioned on the reward and its answer. These tuples (question, answer, reward, feedback) are appended to K parallel context buffers. After N iterations, the original query is added to each buffer, K final answers are sampled, and the majority vote yields the output. Key hyperparameters: N=10, K=8, temperature=0.6, top_p=0.8, max new tokens=8192.

## Key Results
- For Qwen2.5-7B: +58.91% on AMC, +137.59% on AIME2024.  
- For Llama3.1-8B on MedQA: +21.22%.  
- Performance scales consistently across model families and both reasoning and medical tasks, using only unsupervised test‑time computation.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Pseudo‑labels derived via majority voting from multiple parallel rollouts provide a sufficiently accurate proxy for ground‑truth rewards during test‑time ICRL.  
- **Mechanism:** For each retrieved instance, K candidate answers are generated. The most frequent answer becomes the pseudo‑label y*. Binary rewards are assigned to each candidate based on equality with y*.  
- **Core assumption:** The majority answer among model samples correlates with the true answer more often than random chance, especially when the model can produce some correct reasoning paths.  
- **Evidence anchors:**  
  - [abstract] Deriving “pseudo‑label via majority voting” and using it “to give reward messages.”  
  - [section 3.2] Formal definition of y* = arg max_c ∑ 1{y_i = c} and reward R_i = R_correct if y_i = y* else R_wrong.  
  - [section 5.2] “Lucky reward” accuracy remains high (e.g., 71.71% on AIME2024) even when raw label accuracy is low (16.56%).  
- **Break condition:** If the model’s distribution is so poor that the majority answer is almost always wrong *and* that wrong answer matches the model’s consistent mistake, the reward signal becomes useless (no negative reward). The “lucky reward” buffer diminishes as base capability drops further.

### Mechanism 2
- **Claim:** The iterative “rethinking” loop, where the model generates feedback conditioned on reward messages, emulates gradient‑based policy improvement within the context window.  
- **Mechanism:** After receiving a reward r_i, the model produces formative feedback f_i = π_θ(m_i ⊕ q_i ⊕ a_i ⊕ r_i). This feedback is appended to the context buffer, allowing subsequent rollouts to reason based on the reinforced or penalized pattern. The process repeats for each retrieved instance.  
- **Core assumption:** The model can interpret and act upon a natural language reward/feedback message to adjust its subsequent internal reasoning trajectory, effectively simulating a policy update.  
- **Evidence anchors:**  
  - [abstract] Describes processing a reward message to generate formative feedback.  
  - [section 3.2] Explicit feedback generation formula.  
  - [section 5.3] Spurious reward ablation: replacing real majority‑vote rewards with random ones harms performance, proving the *content* of the reward is critical.  
- **Break condition:** If the model is not instruction‑following enough to generate meaningful feedback, or if context length becomes excessive (observed degradation in section 4.2), the loop introduces noise instead of signal.

### Mechanism 3
- **Claim:** Retrieval of semantically relevant, in‑domain instances from an unlabeled set provides a high‑quality, task‑aligned context that bootstraps the ICRL process.  
- **Mechanism:** An embedding model encodes the target query and all unlabeled instances. The top‑N by cosine similarity are retrieved and used as initial q_i for rethinking iterations, offering concrete, relevant practice problems before answering the main query.  
- **Core assumption:** Problems sharing surface or semantic features have overlapping solution strategies; solving a retrieved problem transfers to the original query.  
- **Evidence anchors:**  
  - [abstract] States TR‑ICRL “retrieves the most relevant instances from an unlabeled evaluation set.”  
  - [section 3.1] Formalizes the retrieval step.  
  - [section 4.3 & Appendix B] Ablations show “Min‑Similarity” and “Cross‑Domain” underperform standard high‑similarity retrieval.  
  - [section 5.1] “Increasing similarity” ordering (most relevant last, closest to query) yields best results.  
- **Break condition:** If the unlabeled set is small, lacks diversity, or crosses domains, retrieval fails to provide useful demonstrations, leading to performance collapse.

## Foundational Learning

### In‑Context Learning (ICL)
- **Why needed here:** TR‑ICRL is a specialized form of ICL where demonstrations are not static (input, output) pairs but are dynamically generated, evaluated, and refined via an internal reinforcement loop. Understanding the base paradigm—learning from examples in the context window—is prerequisite.  
- **Quick check question:** How does the format of an ICL example differ from the format of a “rethinking” iteration step in TR‑ICRL?

### Self‑Consistency (Majority Voting)
- **Why needed here:** The core signal—the pseudo‑label and the final answer—is derived from multiple sampled reasoning paths via majority vote. This relies on the empirical finding that correct answers are more likely to be consistent across rollouts.  
- **Quick check question:** Why is majority voting used for pseudo‑label generation instead of just taking the first sample? What does this trade‑off?

### Reinforcement Learning (RL) Basics (Policy, Reward)
- **Why needed here:** TR‑ICRL frames test‑time refinement as an RL process: the LLM’s next‑token prediction is the policy, the pseudo‑label comparison provides the reward, and the feedback step is analogous to a policy update. Grasping this analogy is key to understanding the “rethinking” stage’s purpose.  
- **Quick check question:** In the equation R_i = R_correct if y* = y_i else R_wrong, what is the “policy” (π_θ) being reinforced or penalized?

## Architecture Onboarding

### Component Map
Retriever (embedding model + cosine search) → Retrieves N instances → For each instance: Rollout Sampler (K parallel generations) → Pseudo‑label Engine (majority vote) → Reward Assigner (binary reward) → Feedback Generator (prompted LLM) → Context Aggregator (appends (q_i, a_i, r_i, f_i) to K parallel buffers m₁…m_K) → After N iterations, original query x_test appended to each m_k → Final Rollouts (K candidates A_k*) → Final Aggregation & Voting (majority vote → A*).

### Critical Path
Query → Retrieve top‑N similar unlabeled instances → For each i=1..N: generate K answers → compute pseudo‑label y_i* → assign rewards → generate feedbacks → update K buffers → After all N, add original query to each buffer → generate K final answers → majority vote final output.

### Design Tradeoffs
- **Context Length vs. Relevance:** More steps (N) or rollouts (K) provide more data but increase context length, risking informational interference (performance degradation observed for large N/K).  
- **Binary vs. Granular Rewards:** Simple correct/incorrect rewards lack nuance for complex reasoning; richer signals (e.g., process reward models) could help but add complexity.  
- **Computational Cost:** O(N·K) LLM calls per query; linear scaling with N and K, though fixed‑token cost can still be efficient vs. scaling model parameters.

### Failure Signatures
1. **Contextual Interference:** Accuracy declines after too many iterations (N or K too high) as the buffer accumulates noisy or contradictory data (e.g., Qwen3‑8B on AMC).  
2. **Poor Retrieval Quality:** Performance equals or falls below zero‑shot baseline if retrieved instances are irrelevant (e.g., due to embedding mismatch or cross‑domain retrieval).  
3. **Majority Voting Instability:** High tie frequency among K candidates, especially for small K, leads to variance in results and unstable pseudo‑labels.  
4. **Spurious Reward Propagation:** Incorrect feedback can reinforce wrong reasoning; noticeable when spurious reward yields significantly lower performance than real reward (section 5.3).

### First 3 Experiments
1. **Pseudo‑label Sanity Check:** On a held‑out slice of the unlabeled set, compute majority‑vote pseudo‑label accuracy versus ground truth. Expect modest accuracy (e.g., 40–70% on hard benchmarks) to quantify the “lucky reward” buffer.  
2. **Retrieval Quality Ablation:** Run TR‑ICRL with three retrieval settings: (a) default high similarity, (b) random selection, (c) lowest similarity. Replicate the performance gap (high > random > low) from Fig 4/Appendix B.  
3. **Spurious Reward Baseline:** Replace real majority‑vote rewards with random binary labels (as in section 5.3). Performance should drop significantly (>10% absolute), confirming that the reward *content* drives improvement.

## Open Questions the Paper Calls Out

**Open Question 1:** How can reward estimation be made more robust and nuanced than simple majority voting in tasks with very low base model accuracy, where pseudo‑labels are frequently incorrect?  
- *Basis in paper:* [explicit] The authors identify reliance on simple majority vote as a limitation and explore the “lucky reward” phenomenon where inaccurate pseudo‑labels can still yield correct negative rewards by differing from the model’s incorrect prediction.  
- *Why unresolved:* The “lucky reward” mechanism is not theoretically guaranteed across all task distributions and model capabilities; the tension between pseudo‑label fidelity and reward utility remains unaddressed.  
- *What evidence would resolve it:* Systematic experiments across a wider range of model scales and task difficulties, correlating pseudo‑label accuracy, reward accuracy (signal correctness), and final task performance. Theoretical analysis bounding performance gain as a function of the divergence between pseudo‑label and true label distributions.

**Open Question 2:** What architectural or algorithmic modifications can mitigate the performance degradation caused by “informational interference” from accumulating long context histories during iterative rethinking?  
- *Basis in paper:* [explicit] The authors observe: “As this sequence length expands, the model becomes increasingly susceptible to informational interference… leading to a breakdown in the model’s ability to internalize the optimal reasoning path.”  
- *Why unresolved:* The problem is identified as a key bottleneck, particularly for larger models, but no concrete solution beyond identifying the trade‑off is proposed.  
- *What evidence would resolve it:* Ablations with context compression (summarization, memory networks), attention masking, or iterative pruning of low‑value historical traces. Measuring correlation between context length, attention entropy, and performance decay on diverse benchmarks.

**Open Question 3:** To what extent are the reasoning patterns and corrective feedback learned via TR‑ICRL transferable across domains (e.g., from mathematics to medicine), and what conditions facilitate such cross‑domain generalization?  
- *Basis in paper:* [inferred] Cross‑domain ablations show clear limitation and less effective guidance, implying strong in‑domain dependency, but the underlying reason is not analyzed.  
- *Why unresolved:* The severe drop in cross‑domain settings is presented as a limitation without investigating whether disparate vocabularies, reasoning patterns, or feedback utility are responsible. The potential for learning general “reasoning refinement” versus task‑specific heuristics is unknown.  
- *What evidence would resolve it:* Analysis of feedback content (via LLM‑as‑judge or human evaluation) to categorize corrections (factual error, logical flaw, procedural mistake) across domains. Controlled experiments with “domain‑adjacent” retrieval sets to map the boundary of effective generalization.

**Open Question 4:** How does the quality and diversity of the retrieved unlabeled instances quantitatively affect the stability and convergence of the ICRL process, and is there an optimal retrieval strategy beyond semantic similarity?  
- *Basis in paper:* [explicit] The ablation compares retrieval strategies (Random, Min‑Similarity, Cross‑Domain) against standard similarity‑based retrieval; similarity is critical. Only one embedding model and fixed N are tested.  
- *Why unresolved:* The optimal *profile* of retrieved instances—such as mix of difficulty levels, solution diversity, or presence of common pitfalls—is unexplored. Relationship between retrieval set composition and variance/robustness of majority vote is unstudied.  
- *What evidence would resolve it:* Sensitivity analysis varying the number of retrieved instances (N) and similarity thresholds. Experiments with curated retrieval sets (e.g., only high‑confidence instances, or diverse error types) to deconstruct which properties drive performance.

**Open Question 5:** Can the reward signal be densified and made more informative than the current binary (correct/incorrect) format derived from majority vote, and would this improve performance, especially on complex, multi‑step reasoning tasks?  
- *Basis in paper:* [explicit] The “Limitations” section states binary reward “lacks the nuance required for complex reasoning tasks” and suggests incorporating uncertainty metrics or rubric‑based rewards.  
- *Why unresolved:* The spurious reward experiment shows that even random, incorrect feedback can sometimes help by prompting reconsideration, suggesting the *act of generating feedback* may be as important as its precise correctness. The optimal granularity and structure of the reward/feedback message is an open design question.  
- *What evidence would resolve it:* Controlled comparison between binary rewards and finer‑grained rewards (e.g., step‑level process rewards from a learned PRM, or natural language critiques rated on a rubric). Analysis of correlation between reward confidence (vote margin) and utility of subsequent feedback.

## Limitations
- Exact retrieval backbone (e.g., huggingface ID of Qwen3‑8B‑Embedding) is unspecified, risking mismatch in retrieval quality.  
- Prompt engineering details (system prompt, wording of reward/feedback templates) are incomplete, potentially altering learning dynamics.  
- Criteria for discarding “abnormal responses” (refusals, non‑CoT formats) are not detailed, which may skew majority votes.

## Confidence
- Core mechanism clarity and empirical support (majority‑vote pseudo‑label → binary reward → feedback loop): **High**  
- Claims of broad scalability (performance degrades with longer contexts; gains may not transfer without careful retrieval): **Medium**  
- Long‑term reliability beyond test‑time and dependence on base model competence (“lucky reward” buffer): **Low**
