# Designing Production-Scale OCR for India: Multilingual and Domain-Specific Systems

## Quick Facts
- **arXiv ID:** 2602.16430
- **Source URL:** https://arxiv.org/abs/2602.16430
- **Reference count:** 25
- **Primary result:** Fine-tuning an OCR‑specialized backbone (Chitrapathak‑2) achieves 3–6× speedup and state‑of‑the‑art character ANLS for Telugu (6.69); Parichay‑2 attains 89.8% Exact Match with 4× lower latency than its predecessor.

## Executive Summary
This paper addresses the challenge of building efficient OCR systems for India’s multilingual and heterogeneous documents under production constraints. It compares two training strategies for vision‑language models: (1) end‑to‑end multimodal training (Chitrapathak‑1) and (2) fine‑tuning an existing OCR‑specialized model (Chitrapathak‑2). The second strategy consistently yields superior accuracy‑latency trade‑offs. Chitrapathak‑2 obtains a 3–6× speedup over Chitrapathak‑1, achieving state‑of‑the‑art character ANLS for Telugu (6.69) and ranking second‑best for other Indic scripts. For domain‑specific extraction from Indian government documents, Parichay‑2 (using the same fine‑tuning approach) achieves 89.8% Exact Match with 4× lower latency than its predecessor. The core finding is that initializing from an OCR‑optimized backbone and adapting via fine‑tuning yields more deployable systems than training a general multimodal model from scratch.

## Method Summary
The study focuses on two OCR systems: Chitrapathak for general multilingual text recognition, and Parichay for structured field extraction from Indian government forms. For Chitrapathak, the authors compare an end‑to‑end LLaVA‑style VLM (Chitrapathak‑1) that uses a CLIP vision encoder, aspect‑ratio‑aware dynamic tiling, and a multilingual decoder (Krutrim‑1 7B) trained via a two‑stage procedure (multimodal pretraining then supervised fine‑tuning); against a fine‑tuning approach (Chitrapathak‑2) that starts from an OCR‑specialized backbone (Nanonets‑OCR2‑3B, based on Qwen2.5‑VL) and directly fine‑tunes on a 1.1 M multilingual subset without tiling. For Parichay, they investigate both a Phi‑3.5‑Vision‑based model (Parichay‑1) with dynamic cropping and LoRA/full fine‑tuning, and a version based on the same OCR‑specialized backbone (Parichay‑2) with an optional rotation pre‑processor, using schema‑conditioned instruction fine‑tuning to generate structured JSON output.

Training details include using noisy OCR labels from Google Cloud OCR as supervision. Chitrapathak‑2 is fine‑tuned with LR = 1e‑5 for 1 epoch; Parichay uses full fine‑tuning for best results. Evaluation uses IndicVisionBench‑OCR (character/word ANLS) for Chitrapathak and a proprietary 5‑sample set for Parichay, with latency measured on H100 GPUs. vLLM is employed for models with fixed‑sequence‑length vision encoders (Chitrapathak‑2, Parichay‑2), enabling efficient continuous batching; others use Hugging Face `generate`.

## Key Results
- Chitrapathak‑2 achieves a 3–6× speedup over Chitrapathak‑1 and sets state‑of‑the‑art character ANLS for Telugu (6.69), ranking second‑best among all evaluated systems for other Indic scripts.
- Parichay‑2 reaches 89.8% Exact Match on domain‑specific extraction tasks while cutting latency by 4× compared to Parichay‑1.
- Fine‑tuning an OCR‑specialized backbone consistently outperforms end‑to‑end multimodal training, even with a smaller (1.1 M) training set versus >7 M samples for the end‑to‑end variant.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** The dynamic tiling strategy required by Chitrapathak‑1 to handle high‑resolution documents creates variable‑length inputs that are incompatible with optimized inference engines like vLLM, resulting in high latency and memory overhead.
- **Mechanism:** Tiling splits a page into a global view and multiple local crops, each resized and encoded independently. The number of crops varies per image, producing irregular sequence lengths. This prevents efficient continuous batching and memory pooling in vLLM, which relies on uniform tensor shapes for throughput.
- **Core assumption:** Production OCR systems depend on frameworks such as vLLM for scalable serving, and these frameworks require fixed‑shape attention patterns to achieve low latency.
- **Evidence anchors:**
  - [abstract] "lack of compatibility with optimized inference stacks like vLLM results in high latency and memory overhead."
  - [section 3.1] Describes the aspect‑ratio‑aware tiling and its cost; notes that "dynamic image cropping strategy improves high‑resolution OCR quality, lack of compatibility with optimized inference stacks like vLLM results in high latency and memory overhead."
  - [corpus] The corpus (e.g., Surya OCR) highlights efficiency as a design goal but does not isolate tiling as the root cause; evidence is indirect.
- **Break condition:** If tiling were redesigned to produce a fixed number of crops per image (e.g., via padding) or integrated into a custom inference engine that supports variable‑length vision sequences, the latency penalty might be reduced.

### Mechanism 2
- **Claim:** Fine‑tuning an OCR‑specialized model (Chitrapathak‑2) with a native‑resolution vision encoder eliminates tiling, enabling direct processing at full resolution and full compatibility with vLLM, which yields a 3–6× speedup.
- **Mechanism:** The base model (Nanonets‑OCR2‑3B) uses a Qwen2.5‑VL‑style encoder with 2D‑RoPE and windowed attention. This architecture can ingest the entire high‑resolution image as a single visual token sequence within a fixed budget, avoiding crops. The resulting uniform sequence length allows vLLM to batch requests efficiently and manage memory via PagedAttention.
- **Core assumption:** Windowed attention can model both local character details and global layout across the whole page without tiling, and the maximum token budget covers typical document resolutions.
- **Evidence anchors:**
  - [abstract] "Chitrapathak‑2 achieves 3‑6× speedup over its predecessor."
  - [section 3.2] "This backbone uses a native‑resolution‑capable vision encoder with 2D‑RoPE and windowed attention, eliminating the need for dynamic tiling and allowing direct processing of document images in native resolution within the visual token budget. ... This architecture is fully compatible with vLLM."
  - [corpus] The corpus includes the Qwen2.5‑VL technical report (Bai et al., 2025) that describes the architecture, but does not directly measure the latency impact in this specific setup.
- **Break condition:** If document images exceed the encoder’s token budget (e.g., very large posters), tiling would become necessary again, re‑introducing latency overhead.

### Mechanism 3
- **Claim:** Initializing from an OCR‑specialized model provides strong visual‑text alignment priors, so fine‑tuning on a small multilingual dataset (1.1 M pairs) yields higher accuracy than end‑to‑end training on a much larger corpus (7 M+ pairs).
- **Mechanism:** The base OCR model has already learned to detect text regions, recognize character shapes, and handle layout variations from its pretraining on English documents. Fine‑tuning only needs to adapt the projection layer and the multilingual LLM decoder (already competent in Indic languages) to the new script‑specific visual patterns. In contrast, Chitrapathak‑1 must learn visual features for text from scratch while also learning to generate Indic characters, requiring more data and a two‑stage training pipeline.
- **Core assumption:** Visual features for text (strokes, ligatures, spatial arrangements) are largely transferable across scripts, and the decoder’s multilingual knowledge can be quickly aligned with the visual backbone via limited fine‑tuning.
- **Evidence anchors:**
  - [abstract] "the core finding is that initializing from an OCR‑optimized backbone and adapting via fine‑tuning yields more deployable systems than training a general multimodal model from scratch."
  - [section 6] "Initializing from an OCR‑specialized model significantly improves data efficiency: Chitrapathak‑2, trained on a subset outperformed Chitrapathak‑1, indicating that structural priors for document text reduce adaptation cost as long as the LLM decoder supports the target languages."
  - [corpus] The corpus includes Krutrim LLM (Kallappa et al., 2025) demonstrating strong multilingual decoders, supporting the availability of multilingual LLMs; however, it does not directly measure transfer efficiency for OCR.
- **Break condition:** If target scripts are fundamentally different (e.g., logographic vs. alphabetic) or the base OCR model’s visual features are poorly suited, more data and end‑to‑end training might become necessary.

## Architecture Onboarding

**Component map:**
- Chitrapathak‑1: Document image -> Dynamic tiling -> CLIP‑ViT‑L/14‑336 -> MLP projection -> Krutrim‑1 7B -> Plain text (Hugging Face `generate`)
- Chitrapathak‑2 & Parichay‑2: Document image (native resolution) -> Qwen2.5‑VL encoder (Nanonets‑OCR2‑3B) -> MLP projection -> Qwen2.5‑3B -> Output (plain text for Chitrapathak, JSON for Parichay) (vLLM)
- Parichay‑1: Document image -> Rotation module (Phi‑3.5 Vision) -> Dynamic cropping -> Phi‑3.5 Vision -> Phi‑3.5 Vision Instruct -> JSON (Hugging Face `generate`)

**Critical path (Chitrapathak‑2):**
1. Load image, resize to native resolution (within token budget).
2. Forward through vision encoder → visual tokens.
3. Project tokens via MLP.
4. Autoregressive decoding with LLM until EOS.
5. Return raw text.

**Design tradeoffs:**
- Tiling vs. native resolution: Tiling handles arbitrary resolutions but breaks efficient batching; native resolution requires a long‑context encoder but enables vLLM.
- End‑to‑end training vs. fine‑tuning: End‑to‑end may learn tighter integration but is data‑hungry and slow; fine‑tuning leverages pretrained priors for speed and data efficiency.
- LoRA vs. full fine‑tuning (Parichay): LoRA saves memory but underfits complex domain shifts; full fine‑tuning gives higher accuracy at higher resource cost.
- Structured vs. free‑form OCR: Schema‑constrained JSON output improves accuracy and reduces decoding steps for known document types but sacrifices generality.

**Failure signatures:**
- High latency (>10 s/page) or OOM: likely tiling with vLLM or batch size too large.
- Low accuracy on specific languages: check decoder tokenizer coverage and fine‑tuning data diversity.
- Low EM on Parichay: rotation module failure (mis‑oriented input) or insufficient LoRA rank.
- Layout errors (missing lines, wrong order): common on dense index pages; may require layout‑aware fine‑tuning or post‑processing.

**First 3 experiments:**
1. **Latency benchmarking:** Run Chitrapathak‑1 and Chitrapathak‑2 on a fixed set of high‑resolution images (e.g., 20 per language) on a single H100 GPU. Measure average end‑to‑end latency and peak memory. Expect 3–6× speedup for Chitrapathak‑2.
2. **Accuracy on IndicVisionBench‑OCR:** Evaluate both models across all 10 Indic languages. Compute word/char ANLS. Expect Chitrapathak‑2 to achieve SOTA on Telugu (char ANLS ≤ 6.69) and be within 2–3 ANLS of Gemini‑2.5 Flash on others.
3. **Rotation module ablation (Parichay):** Test Parichay‑2 with and without the rotation module on a held‑out set of documents with varied orientations (90°, 180°, etc.). Measure EM drop; expect significant degradation without rotation, confirming its robustness benefit.

## Open Questions the Paper Calls Out
- **Why does fine‑tuning an OCR‑specialized model yield better accuracy‑latency trade‑offs than end‑to‑end multimodal training for Indic OCR?** The paper shows Chitrapathak‑2 outperforms Chitrapathak‑1 but attributes gains only to data efficiency and structural priors without deeper analysis. Isolation of factors like vision encoder resolution, decoder pretraining effects, or inference stack compatibility is missing.
- **How can tokenizer inefficiency for Indic scripts with high token‑to‑word ratios (e.g., Malayalam, Telugu) be mitigated to reduce OCR decoding latency?** The paper identifies the issue but does not explore tokenizer redesign, script‑specific adaptations, or integration with model training.
- **What data or model modifications can overcome degradation on rare Indic scripts and complex layouts (e.g., index pages) in current OCR systems?** Limitations are listed without proposed solutions or empirical evaluation of remedies.

## Limitations
- Data provenance: Exact sources and sampling for the 7M+ web archives and the 1.1 M subset are unspecified, hindering replication.
- Proprietary components: Parichay’s 21 K annotated dataset and rotation module details are not public, blocking external validation.
- Generalization boundaries: Transferability to under‑represented scripts (e.g., Meitei‑Mayek, Sindhi) and extreme layouts (e.g., historical manuscripts, dense tables) is untested; tokenization overhead for high token‑to‑word ratios may offset latency gains.
