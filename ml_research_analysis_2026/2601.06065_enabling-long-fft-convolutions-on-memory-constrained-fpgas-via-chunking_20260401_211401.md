# Enabling Long FFT Convolutions on Memory-Constrained FPGAs via Chunking

## Quick Facts
- **arXiv ID:** 2601.06065
- **Source URL:** https://arxiv.org/abs/2601.06065
- **Reference count:** 5
- **Primary result:** Chunked FFT convolution with overlap‑add enables 450K‑point convolutions on an Alveo U200 FPGA with 2.8 MB BRAM; throughput scales with chunk size and compute dominates >97% of runtime.

## Executive Summary
Long one‑dimensional convolutions are essential for state‑space models like Hyena, but their FFT‑based implementation demands memory that exceeds the limited on‑chip BRAM of modern FPGAs (typically 2–3 MB). This paper introduces a chunked FFT convolution scheme that splits input and filter into small segments that fit within BRAM, computes each segment pair via on‑chip FFT, and reconstructs the full result with overlap‑add. The approach achieves scalable performance: for sequence lengths up to 450 K on a Xilinx Alveo U200 (2.8 MB BRAM) the throughput drop compared to a 32 K baseline is only ~7%, and kernel computation accounts for more than 97% of the total execution time. The work demonstrates that memory‑constrained FPGAs can efficiently handle very long convolutions without sacrificing the algorithmic advantages of FFT.

## Method Summary
The authors design a radix‑2 decimation‑in‑time FFT kernel in Vitis HLS that processes chunks of up to 8 192 points entirely within BRAM, including buffers and twiddle factors. The host software partitions the input sequence *x* and filter *h* into overlapping chunks of size *C* (≤8192). For every pair of input and filter chunks, the host transfers the data to the FPGA, the kernel performs forward FFTs on both chunks, multiplies them pointwise in the frequency domain, applies an inverse FFT, and returns the partial result. The host then accumulates each partial result into an output buffer at the correct offset using overlap‑add, with zero‑padding to avoid circular convolution artifacts. The system is evaluated on the Alveo U200 platform for sequence lengths 32 K, 160 K, and 450 K with chunk sizes 8192, 4096, and 2048. Execution time is broken down into data transfer (PCIe ~0.8 GB/s) and kernel compute, showing compute dominance (>97%) and throughput increasing with larger chunk sizes.

## Key Results
- Enabled linear convolutions of length 450 K on an FPGA with only 2.8 MB BRAM, a regime previously infeasible due to memory constraints.
- Throughput scales monotonically with chunk size; moving from 32 K to 450 K sequence length incurs only a ~7% performance drop.
- Compute time consistently exceeds 97% of total runtime, indicating that data movement overheads are negligible under the chosen chunking strategy.

## Why This Works (Mechanism)
The solution rests on three key mechanisms. First, **chunking** reduces peak memory usage by ensuring that all intermediate data (chunk buffers, FFT workspace, twiddle factors) stay within the limited BRAM; the maximum chunk size (8192 points) was determined experimentally to fit the 2.8 MB budget. Second, **overlap‑add reconstruction** guarantees an exact linear convolution from the chunked FFT results. Each chunk pair is zero‑padded to length *L* ≥ *C* + *filter_chunk* – 1, so its circular convolution equals the desired linear segment; the overlapping outputs are summed with proper offsets to produce the full result. Third, **compute domination** makes the overhead of chunking negligible. Larger chunks increase arithmetic intensity, so kernel execution (which uses the FPGA’s DSPs efficiently) occupies >97% of runtime; fixed host‑side and PCIe costs become insignificant, yielding near‑linear throughput scaling with *C*. The design therefore transforms a memory‑bound problem into a compute‑bound one that modern FPGAs can handle.

## Foundational Learning
- **FFT‑based convolution** – Why needed: Converts an O(N²) direct convolution into O(N log N) by transforming to frequency domain, making long convolutions feasible. Quick check: What is the minimum zero‑padding length required for linear convolution of input length *Nₓ* and filter length *Nₕ*?  
- **Overlap‑add (block convolution)** – Why needed: Allows exact reconstruction of a long linear convolution from shorter FFT‑based blocks, avoiding aliasing. Quick check: With FFT size *L* and chunk size *C*, what is the stride between successive output blocks?  
- **FPGA BRAM constraints** – Why needed: On‑chip BRAM is fast but small; the FFT kernel must fit its workspace (buffers, twiddles) in BRAM to achieve high throughput. Quick check: Why are FFT butterfly computations placed in fast on‑chip BRAM despite its limited capacity relative to DRAM?

## Architecture Onboarding
Host CPU partitions input and filter into chunks of size *C*; these are transferred via PCIe (~0.8 GB/s) to the FPGA kernel, which performs FFT, pointwise multiplication, and IFFT entirely in BRAM. The partial results return to the host, which accumulates them with overlap‑add into the final output stored in host RAM.

- **Component map:** Host CPU -> PCIe -> FPGA kernel (Alveo U200) -> PCIe -> Host CPU; Host RAM holds full data; FPGA BRAM holds working sets.
- **Critical path:** 1. Partition data into chunks. 2. For each input chunk *i* and filter chunk *j*: transfer both to FPGA, compute convolution via FFT, transfer result back. 3. Accumulate output at offset *iC + jC* with overlap handling.
- **Design tradeoffs:** Chunk size *C*: larger *C* reduces number of pairs but needs more BRAM. FFT size *L*: usually power‑of‑two ≥ *C* + *filter_chunk* – 1; larger *L* improves FFT efficiency but costs BRAM. Filter reuse: Precomputing filter FFTs saves compute if they fit in BRAM; otherwise recomputation is cheaper. Parallel kernels: Multiple engines could hide transfer latency but increase resource use, possibly lowering feasible *C*.
- **Failure signatures:** BRAM overflow (synthesis failure or runtime crash), output mismatch (bugs in overlap‑add or scaling), low throughput (transfer time >30%), resource overuse (DSP/LUT >100%).
- **First 3 experiments:** 1. Correctness test: compare FPGA output against CPU reference for small N (e.g., 1024) to validate numerical accuracy. 2. Throughput scaling: measure execution time for N=450 K with *C*=2K, 4K, 8K; expect monotonic gain and compute >95%. 3. Memory capacity: synthesize with increasing *C* until BRAM overflow; verify maximum practical *C* ≈8192.

## Open Questions the Paper Calls Out
- **Sparse causal 1D‑convolution operator for FPGAs** – The authors propose designing a sparse convolution kernel to further reduce compute and memory, but no existing FPGA implementation addresses this for causal 1‑D convolutions. Evidence needed: a working sparse convolution design with empirical reductions in FLOPs, on‑chip memory, and latency compared to the dense approach.
- **Integration of URAM with BRAM in FFT kernels** – URAM offers larger capacity than BRAM but may have higher latency. The paper suggests exploring this combination to increase feasible chunk sizes. Evidence needed: an FFT kernel that uses both memory types, analyzed for impact on maximum *C*, throughput, and resource utilization.
- **Parallel FFT kernels for simultaneous chunk‑pair processing** – Deploying multiple FFT engines could improve throughput, but introduces data dependencies and bandwidth challenges. Evidence needed: a multi‑kernel architecture with measured scaling efficiency relative to the single‑kernel baseline.

## Limitations
- Exact FFT kernel configuration (fixed‑ vs floating‑point, bit‑widths, scaling, data layout) is unspecified, hindering precise reproducibility and accuracy modeling.
- Filter reuse strategy (precompute vs recompute) is not clarified, significantly affecting operation count and reported throughput.
- Evaluation is confined to a single device (Alveo U200) and sequence lengths up to 450 K; results may not generalize to other FPGAs or much longer sequences.

## Confidence
- Memory reduction via chunking: **High**
- Exactness of overlap‑add reconstruction: **High**
- Throughput scaling with chunk size: **High**
- Compute domination (>97% of runtime): **High**
