# VeRO: An Evaluation Harness for Agents to Optimize Agents

## Quick Facts
- **arXiv ID:** 2602.22480
- **Source URL:** https://arxiv.org/abs/2602.22480
- **Reference count:** 40
- **Primary result:** Using the full VERO harness yields up to 8% absolute accuracy gain versus non-VERO baselines, with focused improvements (7–9% points) on tool-use tasks.

## Executive Summary
VERO addresses the lack of systematic evaluation infrastructure for agent optimization—the task of iteratively improving an LLM agent’s own code. It provides a harness with versioned agent snapshots, budget-controlled evaluation, and structured traces, alongside a benchmark suite of target agents and tasks. Experiments comparing five optimizer configurations across five tasks show that VERO is essential for meaningful gains, particularly on tool-use benchmarks (GAIA, TAU-Bench, SimpleQA). Optimizer instructions significantly affect stability and generalization, and modifications are overwhelmingly prompt-focused. A case study indicates simpler agents have greater optimization headroom than sophisticated ones.

## Method Summary
VERO formalizes agent optimization as a loop where a coding agent (the optimizer) proposes edits to a target agent’s codebase. The harness enforces a fixed evaluation budget B via an ExperimentRunner, which executes the target agent on validation splits and returns scores. All changes are automatically committed via Git worktrees, providing versioning and rollback capability. The optimizer receives structured feedback through ExperimentViewer (past results) and DatasetViewer (sample inputs/outputs). Target agents are uv-locked Python packages with controlled tool access. The process continues until the budget is exhausted, with all traces stored in an ExperimentDatabase for reproducibility.

## Key Results
- Full VERO harness yields up to 8% absolute accuracy gain versus baselines without versioning and budget control.
- Tool-use tasks (GAIA, TAU-Bench, SimpleQA) see mean lifts of 7–9% points; reasoning tasks (GPQA, MATH) show negligible change.
- Optimizer instructions strongly affect stability: verbose guidance gives highest lift but also higher variance.
- Over 50% of modifications across all runs target prompts, indicating limited structural diversity.
- Simpler agents show greater headroom (GAIA lift up to 11.5%) than sophisticated agents (peak 6.9%).

## Why This Works (Mechanism)
VERO works because it imposes disciplined iteration on a fundamentally uncontrolled process. Budget gating forces optimizers to make every evaluation count, while automatic versioning captures every hypothesis as a reproducible snapshot. Structured traces (experiment logs, diffs, scores) turn a black-box code-editing process into an analyzable trajectory, enabling detection of overfitting, prompt-only tweaks, and instruction sensitivity. Without these constraints, optimization devolves into ad-hoc tinkering with no reliable progress measurement.

## Foundational Learning
- **Versioned worktrees:** Isolate each experiment in a Git worktree with auto-commit hooks. *Why needed:* Enables rollback, diff analysis, and reproducibility. *Quick check:* Verify that each edit creates a new commit with a clean baseline.
- **Budget enforcement:** A fixed number of evaluation calls (B) via ExperimentRunner. *Why needed:* Prevents unlimited probing and forces efficient search. *Quick check:* Confirm that evaluations stop exactly at B and that each call decrements a counter.
- **Structured feedback:** ExperimentViewer shows past scores and diffs; DatasetViewer provides input-output samples. *Why needed:* Gives the optimizer evidence to guide edits beyond guesswork. *Quick check:* Ensure the optimizer can query validation scores and inspect failed cases.
- **Dependency locking:** uv lockfiles for target agent environments. *Why needed:* Guarantees that evaluation results are comparable across iterations. *Quick check:* Check that the environment is identical before and after edits (except code changes).
- **Tool sandboxing:** Controlled access to filesystem, Bash, and external APIs. *Why needed:* Prevents runaway edits and security risks; isolates optimization to intended modifications. *Quick check:* Audit which tools are available to the optimizer and target agent.
- **Dataset split management:** Training/validation/test splits with access controls. *Why needed:* Avoids accidental overfitting to test data. *Quick check:* Verify that optimizer can only see training/validation splits during optimization.

## Architecture Onboarding
**Component map:** Optimizer Agent -> VERO Tools (ExperimentRunner, DatasetViewer, ExperimentViewer) -> GitWorktree (auto-commit) -> Target Agent (with tools) -> Evaluator -> Score stored in ExperimentDatabase

**Critical path:** 1) Optimizer inspects current state via viewers. 2) Proposes code edit. 3) Write operation triggers auto-commit to new worktree. 4) ExperimentRunner executes target agent on validation set within budget. 5) Score and traces returned; loop repeats.

**Design tradeoffs:** 
- Simple evaluation count budget vs. multi-dimensional metrics (tokens, cost, time). Current choice favors clarity but risks unfair efficiency comparisons.
- Verbose optimizer instructions vs. minimal scaffolding. Verbose yields higher lifts but also higher variance, suggesting instability.
- Open tool access (e.g., FileWrite) vs. restricted. More tools enable deeper changes but increase risk of irrelevant edits.

**Failure signatures:** 
- >50% of edits are prompt-only, indicating optimizer lacks incentive or ability to modify code structure.
- Validation score improves but test score degrades, signaling overfitting.
- High run-to-run variance (e.g., >10% absolute) under same budget, often due to stochastic optimizer (temp=1.0) or non-deterministic tools.

**First three experiments:**
1. **Baseline harness integrity:** Run a single optimization with a trivial optimizer (e.g., random edits) to confirm budget enforcement, versioning, and reproducibility.
2. **Instruction sensitivity:** Compare Minimal vs. Cookbook+Reasoning instruction templates on a single task (e.g., GAIA) to observe lift-variance tradeoff.
3. **Modification diversity:** Analyze diff statistics (prompt vs. code vs. config edits) across a full run to quantify structural change ratio; if <30% non-prompt, consider adding explicit diversity incentives.

## Open Questions the Paper Calls Out
1. What multi-dimensional budget metric should replace the simple evaluation count?
2. How does optimization performance vary with budget size and allocation strategy?
3. What human-level performance can be achieved on agent optimization under VERO’s constraints?
4. Why do optimizers fail to improve reasoning tasks (GPQA, MATH) while excelling at tool-use tasks?
5. How can we encourage optimizers to make diverse structural changes rather than over-relying on prompt edits?

## Limitations
- The core VERO harness implementation is not released; reproduction requires reconstructing from high-level descriptions, risking inconsistencies.
- Target agent initializations (Pawn/Knight) and exact tool configurations for each benchmark are unspecified.
- Optimizer instruction templates are described but full prompts and cookbook content are omitted.
- Experimental details (random seeds, statistical tests, exact budget values) are missing, preventing precise verification.
- Claims rely on Claude Sonnet 4.5; generalizability to other LLMs (especially open-source) is untested.

## Confidence
- **Main efficacy claim (VERO essential, up to 8% gain):** Medium. Quantitative but unverifiable without code/logs.
- **Task-specific impact (tool-use lift 7–9%, reasoning negligible):** Medium. Aggregated numbers lack per-task confidence intervals.
- **Instruction sensitivity (verbose vs. minimal tradeoff):** Medium-Low. Trade-off claim lacks variance details and statistical significance.
- **Modification pattern (>50% prompt-only):** Medium. Analysis plausible but raw diffs not inspectable.
- **Case study (simpler agents have more headroom):** Low. Single example, not generalizable.
