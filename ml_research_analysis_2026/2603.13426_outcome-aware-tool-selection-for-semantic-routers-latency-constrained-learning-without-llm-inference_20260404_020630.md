# Outcome-Aware Tool Selection for Semantic Routers: Latency-Constrained Learning Without LLM Inference

## Quick Facts
- **arXiv ID:** 2603.13426
- **Source URL:** https://arxiv.org/abs/2603.13426
- **Reference Count:** 37
- **Primary Result:** Outcome-aware embedding refinement (OATS-S1) improves tool selection accuracy (NDCG@5) by 7.1–8.2 points on two benchmarks while maintaining sub-10ms CPU latency and adding zero parameters or serving cost.

## Executive Summary
Semantic routers in LLM gateways must select relevant tools within strict latency budgets (single-digit milliseconds), but static embedding similarity cannot learn from historical outcome feedback (e.g., which tools succeeded for past queries). This paper proposes Outcome-Aware Tool Selection (OATS), a framework that refines tool embeddings offline by moving them toward the centroid of queries where they historically succeeded and away from queries where they failed. This zero-cost refinement stage provides large gains without altering the online inference path. Two optional, lightweight learned components—a feature-based MLP re-ranker and a contrastive adapter—can yield further improvements but only under sufficient outcome data density. The core insight is that outcome logs contain geometric signal to correct static description embeddings, enabling high-accuracy retrieval with no serving overhead.

## Method Summary
OATS comprises three modular stages. Stage 1 (OATS-S1) is the core zero-cost method: for each tool, it computes the centroid of positive queries (where the tool succeeded) and negative queries (where it was retrieved but failed) from historical logs. The tool’s stored embedding is interpolated toward the positive centroid and away from the negative centroid, with momentum and a validation gate to accept only improvements. Stages 2 and 3 add learned components if data permits: Stage 2 trains a tiny MLP (2.6K params) on outcome-derived features to re-rank the top-C candidates from Stage 1; Stage 3 trains a contrastive adapter (197K params) with hard-negative triplets to reshape the embedding space itself. All stages are designed to preserve the sub-10ms CPU latency constraint: Stage 1 updates the static tool database offline; Stage 2 adds one extra scoring pass over a small candidate set; Stage 3 replaces the base embedder with a minimally larger model.

## Key Results
- On MetaTool (199 tools), OATS-S1 improves NDCG@5 from 0.869 to 0.940.
- On ToolBench (2,413 APIs), OATS-S1 improves NDCG@5 from 0.834 to 0.848.
- All variants maintain single-digit millisecond CPU latency; the zero-cost S1 adds no parameters or serving delay.
- Ablations show the MLP re-ranker (S2) harms performance on sparse data (ToolBench: 0.823 vs. 0.834 baseline), while the contrastive adapter (S3) achieves 0.931 NDCG@5 on MetaTool—comparable to S1.

## Why This Works (Mechanism)

### Mechanism 1: Outcome-guided centroid interpolation
- **Claim:** Offline interpolation of tool embeddings toward positive query centroids and away from negative ones improves ranking accuracy with zero serving cost.
- **Mechanism:** For each tool `ti`, collect positive (`Q+_i`) and negative (`Q-_i`) query embeddings from outcome logs. Compute centroids `¯e+` and `¯e-`. Update: `ˆe_i = (1-α)*e(di) + α*¯e+ - β*¯e-` (α=0.3, β=0.1), with momentum (µ=0.5) over `N=3` iterations. Accept only if validation Recall@K improves.
- **Evidence:** [abstract] NDCG@5 gains on MetaTool (0.869→0.940) and ToolBench (0.834→0.848) without latency increase. [section 4.1] Algorithm 1 and geometric example.
- **Break condition:** Noisy/bad outcome labels cause drift if validation gate fails.

### Mechanism 2: Feature-based MLP re-ranker (data-dependent)
- **Claim:** A lightweight MLP re-ranker improves selection only when outcome density per tool is high (∼10+ examples).
- **Mechanism:** Train a 2.6K-parameter MLP on features: similarity scores, gaps, tool category, historical success rate, frequency, query length. Re-rank top-C from initial search.
- **Evidence:** [abstract] MLP "hurts or matches baseline when outcome data is sparse." [section 6.2] ToolBench (<0.15 examples/tool) NDCG@5 drops to 0.823.
- **Break condition:** Data-to-tool ratio below ~10:1 leads to overfitting.

### Mechanism 3: Contrastive adapter with hard negatives
- **Claim:** A contrastive adapter reshaping the embedding space via hard-negative learning provides consistent gains for large tool sets with minimal overhead.
- **Mechanism:** Mine triplets (query, positive tool, hard-negative tool) from logs. Train a small adapter head with InfoNCE loss to pull positives closer and push hard negatives away.
- **Evidence:** [abstract] Adapter achieves NDCG@5 0.931 on MetaTool, comparable to S1. [section 4.3] Triplet mining and deployment as drop-in embedder.
- **Break condition:** Inadequate hard-negative mining or base model capacity limits adaptation.

## Foundational Learning

- **Centroid interpolation in embedding space**
  - *Why needed:* Corrects tool embeddings by moving them toward clusters of successful queries and away from failure clusters—a directional update in geometry.
  - *Quick check:* If a tool’s positive and negative query centroids are nearly aligned, the interpolation update becomes negligible or noisy, likely yielding no improvement.

- **Hard-negative contrastive learning**
  - *Why needed:* Static embeddings confuse functionally distinct tools with superficial similarity; hard negatives (retrieved but incorrect tools) teach precise decision boundaries.
  - *Quick check:* Random negatives are insufficient because they don’t reflect the model’s current confusion; hard negatives mined from retrieval outcomes target the specific errors the model makes.

- **Outcome-derived feature engineering**
  - *Why needed:* The MLP re-ranker relies on context beyond raw similarity (e.g., historical success rate, similarity gaps) to capture nuanced patterns.
  - *Quick check:* Historical success rate per tool becomes statistically unreliable when outcome data is very sparse (e.g., <5 examples/tool), as estimates become high-variance.

## Architecture Onboarding

**Component map:** Query → embed(query) → similarity search against refined tool DB → (optional: MLP re-rank on top-C) → top-K selected tools. Offline: outcome logs → centroid updates → validation gate → swap tool DB; or contrastive adapter training → deploy new embedder.

**Critical path:** Online inference must complete in 3–7ms CPU. All offline learning must produce outputs that plug into this path without adding steps: Stage 1 updates the tool DB; Stage 2 adds a re-scoring call; Stage 3 replaces the embedder.

**Design tradeoffs:**
- Start with Stage 1 (zero-cost). Add Stage 2 only if data-to-tool ratio > 10:1. Add Stage 3 if tool set > 500 and logs > 10K.
- Stage 2 adds a second pass over candidates; Stage 3 changes the first-pass embedding distribution.
- Lexical signals (e.g., BM25) may still be needed separately; Stage 1 does not integrate them.

**Failure signatures:**
- MLP re-ranker degrades NDCG@5 on large/sparse datasets (observed on ToolBench).
- Contrastive adapter overfits if validation NDCG drops during training; requires early-stopping.
- Centroid interpolation causes tool embedding drift if validation gate is omitted or outcome labels are corrupted.

**First 3 experiments:**
1. Validate Stage 1 against random and static baselines on a held-out set; ensure Recall@K improves and latency unchanged.
2. Test Stage 2 with varying data density: simulate reduced logs per tool (e.g., 1, 5, 10, 20) to identify the breakpoint where NDCG@5 drops.
3. Compare Stage 3 adapter vs. Stage 1 on MetaTool-sized tool set; check if adapter matches refinement gains and test on out-of-distribution queries.

## Open Questions the Paper Calls Out

- **What is the precise data-to-tool ratio threshold below which the MLP re-ranker consistently degrades performance?** The paper notes it hurts on ToolBench (<0.15 examples/tool) but gives no gain on MetaTool (~13 examples/tool). A systematic threshold across tool set sizes is needed for practitioners.
- **How do richer, multi-dimensional outcome signals (e.g., task success, latency, cost) affect embedding refinement compared to binary relevance?** The framework is agnostic to signal source, but experiments only use a binary proxy. Multi-faceted signals could yield more nuanced updates.
- **Can the cold-start problem for newly added tools (no outcome history) be mitigated without serving latency?** New tools fall back to static similarity until data accumulates, potentially causing systematic under-selection. Warm-up strategies (e.g., interpolating toward similar tools) are unexplored.
- **Does improved tool selection accuracy translate into higher end-to-end task completion rates or lower hallucination in downstream LLM responses?** The paper measures selection quality, not agent performance; the correlation between NDCG@5 and final task success remains open.

## Limitations
- Unspecified top‑K for constructing positive/negative query sets in Algorithm 1 may affect centroid stability.
- Validation split details (size, metric) are missing, risking overfitting to a particular split.
- Outcome logs may contain noisy relevance labels; robustness is unknown.
- Zero‑shot generalisation to tools without outcome data is untested.

## Confidence
- **Core zero‑cost refinement (S1):** High – gains are consistent across two benchmarks but rely on an unspecified top‑K.
- **MLP re‑ranker (S2):** Medium – improves only when outcome density exceeds ≈10 examples/tool; can degrade on sparse data.
- **Contrastive adapter (S3):** Medium – matches S1 on MetaTool but not evaluated on ToolBench; risk of overfitting without careful early‑stopping.

## Next Checks
1. **Top‑K sensitivity:** Train S1 with K ∈ {1,5,10,20} and evaluate NDCG@5 to identify a stable configuration.
2. **Noise robustness:** Introduce synthetic label noise (5%, 10%, 20% flip rates); verify the validation gate prevents degraded embeddings and quantify performance drop.
3. **Adapter scalability:** Train the contrastive adapter on the full ToolBench (2,413 APIs) and compare NDCG@5 to S1; test on a held‑out subset of tools with no outcome data.
