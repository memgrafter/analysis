# OpenRad: a Curated Repository of Open-access AI models for Radiology

## Quick Facts
*   **arXiv ID:** 2603.02062
*   **Source URL:** https://arxiv.org/abs/2603.02062
*   **Reference count:** 0
*   **Primary result:** A curated repository of 1,694 verified open-access radiology AI models, created by automatically extracting standardized records from 5,239 papers using an LLM guided by the RSNA AI Roadmap schema, followed by expert review.

## Executive Summary
The literature for radiology AI is highly fragmented, with models reported in non-standard ways across thousands of papers, hindering discovery and reproducibility. OpenRad addresses this by creating a centralized, curated repository. It uses a locally hosted large language model (LLM) to automatically extract structured metadata from papers according to the RSNA AI Roadmap schema, then employs ten expert reviewers to verify and correct the records. The final repository contains 1,694 models with accessible code or weights, offering a searchable web portal with faceted filtering by modality, subspecialty, and resource availability.

## Method Summary
The authors built OpenRad through a multi-stage pipeline. First, they queried PubMed, arXiv, and Scopus to collect 5,239 paper records. For each paper, a locally hosted 120B parameter LLM (`gpt-oss:120b`) was prompted to extract key information and populate fields of the RSNA AI Roadmap JSON schema, processing full-text PDFs where possible. An automated script then checked identified GitHub URLs for the presence of pretrained weights or demos. Ten domain experts manually reviewed every LLM-generated record, correcting inaccuracies and classifying edits as minor or major. The validated records power a public web interface that supports keyword search and faceted filtering.

## Key Results
*   Automated extraction using the LLM demonstrated high stability for structured fields (Levenshtein ratio >90%), while expert review found 78.5% of required edits to be minor.
*   Analysis of the final repository shows Convolutional Neural Networks (CNNs) and transformers as the dominant architectures, with MRI being the most common modality, particularly in neuroradiology (621 models).
*   Geospatial analysis reveals a heavy concentration of research output in China and the United States.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** Automated LLM extraction guided by a standardized schema overcomes the bottleneck of dispersed, non-standardized model reporting.
*   **Mechanism:** A locally-hosted LLM (`gpt-oss:120b`) processes full-text PDFs (or abstracts) with structured prompts to populate fields from the RSNA AI Roadmap JSON schema (e.g., modality, architecture, performance metrics). This converts heterogeneous paper content into a uniform, machine-readable format.
*   **Core assumption:** The LLM can accurately identify and map key concepts from scientific text to predefined schema fields with sufficient consistency.
*   **Evidence anchors:** Use of the `instructor` library for structured output (`section 2.1`); stability metrics for structured fields (`section 3.2`).
*   **Break condition:** LLM extraction stability for structured fields drops below a functional threshold (e.g., <85%) for a significant subset of papers.

### Mechanism 2
*   **Claim:** Expert verification of LLM outputs corrects extraction errors and ensures repository trustworthiness, balancing scalability with accuracy.
*   **Mechanism:** Ten domain experts manually review each LLM-generated record, correcting inaccuracies and classifying edits as minor or major.
*   **Core assumption:** A small team of experts can efficiently review a large volume of records, and their corrections represent a gold standard.
*   **Evidence anchors:** "Manually verified by ten expert reviewers" (`abstract`); "78.5% of record edits being characterized as minor" (`abstract`).
*   **Break condition:** The ratio of major edits exceeds a critical limit (e.g., >15%), or expert review time per record grows non-linearly.

### Mechanism 3
*   **Claim:** Community-driven contribution and flagging, coupled with automated repository monitoring, sustains long-term repository relevance and accuracy.
*   **Mechanism:** A portal allows users to submit new models and suggest edits; flagged entries are re-reviewed. An automated pipeline periodically re-checks GitHub links for weights/demos.
*   **Core assumption:** The research community will actively participate in submitting and correcting entries.
*   **Evidence anchors:** "The community can contribute new models through a dedicated portal" (`abstract`); description of flagging and link re-checking (`section 3.1.3`).
*   **Break condition:** Submission and correction rates fall below the level needed to offset model obsolescence.

## Foundational Learning
*   **Concept: Structured Data Extraction with LLMs**
    *   *Why needed here:* The core innovation is converting unstructured text (papers) into structured JSON. Understanding prompt engineering, schema adherence, and LLM consistency limitations is critical.
    *   *Quick check question:* What specific design choice (e.g., using the `instructor` library, providing full PDF vs. abstract) likely reduces schema-breaking hallucinations?
*   **Concept: Ontology-Based Metadata Standardization (RSNA Roadmap)**
    *   *Why needed here:* Repository value depends on consistent, interoperable metadata (e.g., RadLex codes). This explains why a predefined JSON schema is used over free-text extraction.
    *   *Quick check question:* How would using a non-standardized, ad-hoc metadata schema specifically harm the "faceted filtering" feature?
*   **Concept: Expert-in-the-Loop Validation Metrics**
    *   *Why needed here:* Quality is quantified via "minor/major edit" classification and lexical stability scores. Understanding what these measure (semantic fidelity vs. exact match) is key to evaluating reliability.
    *   *Quick check question:* Why might a high Levenshtein ratio for the "Architecture" field be less concerning than a low ratio for the "Repository link" field?

## Architecture Onboarding
*   **Component map:**
    Paper Ingestor -> LLM Extraction Engine -> Repository Inspector -> Expert Review Interface -> Stability Assessment Module -> Web Portal (OpenRad) <- Community Moderation
*   **Critical path:** Paper Metadata -> LLM JSON Generation -> Automated Repo Check -> Expert Review (Flagging loop) -> Validated JSON -> Web Portal Index.
*   **Design tradeoffs:**
    *   Automation Scale vs. Precision: Using a 120B LLM locally improves control but may have lower fidelity than a proprietary model. Manual review mitigates this but caps throughput.
    *   Schema Completeness vs. Extraction Feasibility: The comprehensive RSNA schema had some fields omitted initially due to computational constraints, prioritizing core indexing.
    *   Static Analysis vs. Dynamic Integrity: The analysis is a snapshot; live stats and link checking attempt dynamic maintenance but require ongoing resources.
*   **Failure signatures:**
    *   High major-edit rate (>20%) in expert review, indicating systemic LLM failure on certain paper types.
    *   Rapid decay in "resource availability" filter as GitHub repos are deleted, exceeding periodic re-check capacity.
    *   Low community submission/flagging volume, causing repository to become a static archive.
*   **First 3 experiments:**
    1.  **LLM Stability Stress Test:** Process the same 225-paper subset with different temperature settings or a different open-source LLM (e.g., Llama 3 70B). Quantify changes in minor/major edit rate and lexical similarity.
    2.  **Expert Review Throughput Benchmark:** Time an expert reviewing 50 randomly selected records. Calculate total person-hours for the full set and model a sustainable review rate.
    3.  **Link Rot & Resource Availability Audit:** Programmatically re-check all 1,694 repository URLs 3 months post-initial scrape. Measure percentage of broken links and lost weights/demos.

## Open Questions the Paper Calls Out
### Open Question 1
*   **Question:** How can the accuracy of LLM-based extraction be improved for complex, free-text fields (e.g., model architecture, limitations, regulatory details) that exhibited lower lexical stability?
*   **Basis in paper:** The stability analysis reported low Levenshtein/Jaccard scores for "Architecture" (~66-70%), "Limitations" (~46-50%), and "Regulatory" (~61-79%), with the authors noting semantic consistency remained high despite lexical variance.
*   **Why unresolved:** High lexical variance can hinder standardized indexing and fair comparison. The root causes and robust mitigation strategies are not explored.
*   **What evidence would resolve it:** A controlled study comparing different prompting strategies or fine-tuning on a manually annotated subset, measuring both lexical stability and semantic equivalence.

### Open Question 2
*   **Question:** What are the underlying barriers (e.g., infrastructure, funding, cultural) causing the heavy geographic concentration of open-access radiology AI research in China and the US, and how can they be addressed to foster more equitable global contribution?
*   **Basis in paper:** The geospatial analysis found "research output was mostly concentrated in China and the United States," with most other countries contributing only a handful of studies.
*   **Why unresolved:** The paper identifies the concentration as a finding but does not investigate its causes or propose solutions.
*   **What evidence would resolve it:** Mixed-methods research combining surveys/interviews with researchers from low-contribution regions, analysis of funding and compute resource distribution.

### Open Question 3
*   **Question:** What is the long-term viability of the community-driven curation model for OpenRad, specifically regarding sustained contributor engagement and the effective moderation of user-submitted models/edits?
*   **Basis in paper:** The paper describes a system for community submissions and a "Verify & Edit" mode for curators, with all submissions and edits requiring expert verification.
*   **Why unresolved:** The paper does not analyze incentives, workload, or retention rates for volunteer curators. Scalability of expert verification and risk of low-quality submissions are unaddressed.
*   **What evidence would resolve it:** Longitudinal analysis of submission volumes, contributor demographics/retention, and verification throughput. Implementation and evaluation of gamification or recognition systems.

### Open Question 4
*   **Question:** To what extent does the literature search strategy (PubMed, arXiv, Scopus with defined queries) miss eligible open-access radiology AI models, and how can search comprehensiveness be improved without prohibitive manual effort?
*   **Basis in paper:** The authors state the queries "may not have captured every available model" and encourage community submissions to enrich the repository.
*   **Why unresolved:** The potential magnitude of missed models is unknown. The trade-off between query precision/recall and the burden of expanding coverage is not quantified.
*   **What evidence would resolve it:** A manual audit or "capture-recapture" analysis using alternative data sources (e.g., conference proceedings, institutional repositories) to estimate the fraction of missed models.

### Open Question 5
*   **Question:** What is the cost-accuracy trade-off of populating all RSNA AI Roadmap fields versus the selected subset used in OpenRad, and which additional fields would provide the highest marginal utility for users?
*   **Basis in paper:** The paper notes that "due to computational constraints the initial extraction did not populate every field mandated by the RSNA Roadmap, focusing more on correct indexing and access."
*   **Why unresolved:** The decision to omit fields was pragmatic but not data-driven. The value of specific missing fields for end-user tasks is unclear.
*   **What evidence would resolve it:** A user study asking researchers/clinicians to rate the importance of each RSNA field for common workflows, coupled with experiments measuring incremental computational cost and LLM accuracy for each field.

## Limitations
*   Key implementation details (exact LLM prompts/temperature, GitHub verification heuristics) are unreported, hindering full replication.
*   Quality metrics (stability scores, minor/major edit rates) are self-reported without external benchmarks or a gold-standard test set.
*   Long-term sustainability depends on unproven community participation and the scalability of the expert verification loop.

## Confidence
*   **Automated extraction scalability:** Medium (internal stability metrics reported, but prompt/parameter opacity prevents full replication).
*   **Repository accuracy via expert review:** Medium (78.5% minor edits suggest viability, but review criteria/thoroughness are not externally audited).
*   **Community-driven upkeep:** Low (mechanism described but no adoption data; neighboring corpus shows no similar dynamic systems).
*   **Current snapshot findings** (e.g., CNN/transformer dominance, geographic concentration): High (directly observable from the published repository).

## Next Checks
1.  **LLM extraction stress test:** Re-run the 225-paper stability subset with varied LLM temperatures (e.g., 0.1 vs 0.7) and an alternative open-source model (e.g., Llama 3 70B) to quantify robustness to hyperparameters.

3.  **Link rot longitudinal audit:** Re-scrape all 1,694 GitHub URLs at 3- and 6-month intervals to measure resource decay rate (broken links, removed weights/demos) and validate periodic re-check efficacy.
