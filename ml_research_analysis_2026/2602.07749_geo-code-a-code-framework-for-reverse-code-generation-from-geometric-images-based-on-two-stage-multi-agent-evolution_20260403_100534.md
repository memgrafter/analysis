# Geo-Code: A Code Framework for Reverse Code Generation from Geometric Images Based on Two-Stage Multi-Agent Evolution

## Quick Facts
- **arXiv ID:** 2602.07749  
- **Source URL:** https://arxiv.org/abs/2602.07749  
- **Reference count:** 7  
- **Primary result:** Geo-Code achieves state-of-the-art geometric fidelity on four benchmarks (Layout Score 98.04, SSIM 0.8456, Hausdorff Distance 95.90, Chamfer Distance 13.06) and improves multimodal reasoning accuracy by 4% on MathVerse.

## Executive Summary
Geo-Code introduces a two-stage multi-agent framework to address inverse graphics failures in geometric reconstruction. Stage 1 uses pixel-wise anchoring, combining classical vision operators with LLM-based semantic parsing to extract precise coordinates and topological constraints. Stage 2 employs a synthesis-rendering-validation loop with visual error projection to iteratively refine executable code. This decoupling ensures a correct skeleton before parameter optimization. Evaluations on four benchmarks show superior fidelity and downstream reasoning performance. The release includes a curated dataset of 1,510 image-code pairs and a fine-tuned GeoCodeLM model.

## Method Summary
Geo-Code processes an input image–text pair \((I_{\text{obs}}, T)\) in two phases. **Stage 1 (Anchoring)** fuses classical vision operators (edge/junction detectors) with an LLM's semantic parsing to extract a precise geometric skeleton \(S_{\text{geo}} = \{P^*, R^*\}\). The Geometric Extraction Agent proposes candidate points via vision operators and infers topological constraints via the LLM; the Visual Verification Agent then filters candidates against the image and constraints to produce the grounded skeleton.

**Stage 2 (Evolution)** starts from \(S_{\text{geo}}\) and uses a Code Generation Agent to create initial executable code \(C^{(0)}\). A closed loop then iterates: the renderer executes \(C^{(t)}\) to produce \(I_{\text{rec}}^{(t)}\); the Hybrid Inspection Agent computes Chamfer and Hausdorff distances and projects them into a Visual Difference Map \(M_{\text{err}}^{(t)}\); the Reflective Correction Agent interprets \(M_{\text{err}}^{(t)}\) and updates the code to \(C^{(t+1)}\). The loop terminates when geometric metrics stabilize, yielding final code \(C^*\). The approach is supported by the released Geo-Code dataset (1,510 image–code pairs) and the fine-tuned GeoCodeLM backbone.

## Key Results
- Achieves SOTA geometric fidelity: Layout Score 98.04, SSIM 0.8456, Hausdorff Distance 95.90, Chamfer Distance 13.06.  
- Reconstructed images preserve or enhance multimodal reasoning accuracy, with a 4% improvement on MathVerse.  
- Provides a high-quality dataset (1,510 image-code pairs) and a specialized GeoCodeLM model for the task.

## Why This Works (Mechanism)
Geo-Code's effectiveness relies on three core mechanisms: pixel-wise anchoring, visual error projection, and decoupled modeling.

### Pixel-wise Anchoring
Pixel-wise anchoring binds noisy raster pixels to precise geometric primitives, reducing topological hallucinations. Stage 1 synergizes classical vision operators (e.g., gradient/junction detectors) that excel at local edge detection with an LLM's semantic parsing that provides global topology. The vision operators propose high-frequency candidate points, while the LLM—guided by text constraints—filters them into a grounded skeleton. Evidence includes the abstract’s claim of “precise capture of pixel coordinates and visual attributes” and section 4.2.1’s parallel extraction paths. Break condition: vision operators may miss weak edges, or the LLM may mis-prioritize constraints, leading to an incomplete skeleton.

### Visual Error Projection (VEP)
VEP enables intuitive, gradient-free code refinement by converting abstract metrics into spatial difference maps. In Stage 2, the Hybrid Inspection Agent computes Chamfer/Hausdorff distances and projects them into a pixel-space error map \(M_{\text{err}}\). The Reflective Correction Agent interprets this map to diagnose issues (e.g., missing lines, drift) and directly adjust code parameters, avoiding non-convex numeric optimization. The assumption is that agents reason more effectively from a spatial “visual diff” than scalar loss values. Evidence: the abstract mentions a “synthesis-rendering-validation closed loop,” and section 4.2.2 defines VEP explicitly. Break condition: if \(M_{\text{err}}\) is too noisy or the agent misinterprets it, the loop may converge to an incorrect structure.

### Decoupled Modeling and Evolution
Decoupling into a modeling stage (skeleton) and an evolution stage (refinement) isolates topological correctness from pixel-level precision. Stage 1 establishes a globally consistent geometric skeleton; Stage 2 then performs local parameter optimization around this fixed topology. This prevents early topological errors from being “baked in” and later “corrected” by pixel losses that are poor proxies for topology. Evidence: the abstract states “decouples the process into geometric modeling via pixel-wise anchoring and metric-driven code evolution,” and section 6.3 ablations show Phase 1 improves structural scores while Phase 2 improves pixel metrics. Break condition: a subtle topological flaw in Stage 1 will propagate to Stage 2, yielding high pixel fidelity around an incorrect structure.

## Foundational Learning
### Neuro-Symbolic Integration
- **Why needed:** Geo-Code merges continuous vision operators (sub-symbolic) with discrete LLM reasoning (symbolic). Engineers must design interfaces (e.g., \(P_{\text{raw}} \rightarrow P^*\)) that translate between representations without information loss.  
- **Quick check:** How does the \(\pi_{\text{ver}}\) agent convert a set of candidate points into a symbolically grounded set \(P^*\)? What causes it to reject a valid point?

### Metric-to-Visual Feedback Translation
- **Why needed:** VEP’s core innovation is projecting numeric distances into a visual map. Engineers must grasp how to construct \(M_{\text{err}}\) to highlight actionable discrepancies (missing primitives, misalignment) rather than pixel noise.  
- **Quick check:** Why is a Visual Difference Map more useful to an LLM-based \(\pi_{\text{ref}}\) than a scalar Chamfer Distance? What are the risks of a poorly constructed map?

### Multi-Agent Closed-Loop Systems
- **Why needed:** The framework orchestrates six specialized agents. Engineers need to model handoffs, state dependencies, and termination conditions to avoid deadlocks or infinite loops.  
- **Quick check:** What triggers the transition from Stage I to Stage II? What terminates the Stage II iteration loop? What happens if \(\pi_{\text{ref}}\) repeatedly makes the same error?

## Architecture Onboarding
### Component Map
Stage I: Geometric Extraction Agent (\(\pi_{\text{ext}}\)) with parallel modules \(\pi_{\text{logic\_ext}}\) (LLM for topology \(R\)) and \(\pi_{\text{vision\_ext}}\) (CV operators for points \(P_{\text{raw}}\)) → Visual Verification Agent (\(\pi_{\text{ver}}\)) filters to produce cleaned skeleton \(S_{\text{geo}} = \{P^*, R^*\}\).  
Stage II: Code Generation Agent (\(\pi_{\text{gen}}\)) creates \(C^{(0)}\) → Code Execution Agent (\(\pi_{\text{exec}}\), renderer) produces \(I_{\text{rec}}^{(t)}\) → Hybrid Inspection Agent (\(\pi_{\text{insp}}\)) computes metrics and Visual Difference Map \(M_{\text{err}}^{(t)}\) → Reflective Correction Agent (\(\pi_{\text{ref}}\)) updates code to \(C^{(t+1)}\). Loop repeats until convergence.  
External components: Renderer, Metrics (CD/HD on edges), LLM/MLLM backends.

### Critical Path
\(I_{\text{obs}}, T\) → \(\pi_{\text{ext}}\) → \(\pi_{\text{ver}}\) → \(S_{\text{geo}}\) → \(\pi_{\text{gen}}\) → \(C^{(0)}\) → \(\pi_{\text{exec}}\) → \(I_{\text{rec}}^{(0)}\) → \(\pi_{\text{insp}}\) → \(M_{\text{err}}^{(0)}\) → \(\pi_{\text{ref}}\) → \(C^{(1)}\) → … → \(\pi_{\text{exec}}\) → \(I_{\text{rec}}^{(t)}\) → (convergence) → final \(C^*\).

### Design Tradeoffs
- **Precision vs. Speed:** Pixel-wise anchoring and VEP iterations increase latency; fewer iterations risk residual error.  
- **LLM-specific vs. General:** \(\pi_{\text{gen}}\) and \(\pi_{\text{ref}}\) are LLM-dependent; using smaller fine-tuned models (e.g., GeoCodeLM) reduces cost but may lose diagnostic reasoning.  
- **Closed-loop stability:** Over-aggressive \(\pi_{\text{ref}}\) corrections can oscillate; requires careful prompt engineering and possibly a backtrack mechanism.

### Failure Signatures
- **Topological collapse:** Layout Score plummets; \(M_{\text{err}}\) shows large missing regions (Stage 1 failure).  
- **Coordinate drift:** High Hausdorff Distance but moderate Layout Score; \(M_{\text{err}}\) shows consistent offset patterns (Stage 2 calibration failure).  
- **Style mismatch:** SSIM low but CD/HD moderate; \(M_{\text{err}}\) highlights line thickness or label placement errors.  
- **Infinite loop:** \(\pi_{\text{ref}}\) cycles through same corrections; monitor iteration count and CD stagnation.

### First 3 Experiments
1. **Module isolation test:** Run only Stage I on a dataset. Its skeleton \(S_{\text{geo}}\), when manually coded, should reconstruct >95% Layout Score, validating anchoring works.  
2. **VEP ablation:** Replace \(M_{\text{err}}\) with raw CD/HD values as text for \(\pi_{\text{ref}}\). Expect significant drop in pixel metrics and more iterations, confirming VEP’s utility.  
3. **Agent swap stress test:** Replace \(\pi_{\text{ref}}\) with a non-agentic single-prompt LLM call. Expect failure on complex cases requiring multi-step correction, highlighting the need for iterative refinement.

## Open Questions the Paper Calls Out
1. **Generalization to exotic geometries:** Evaluations cover common planar/solid geometries only. It remains unknown how Geo-Code handles irregular polygons, higher-dimensional projections, or non-Euclidean geometries. Resolution: test on a diverse new benchmark.
2. **Computational overhead and iteration efficiency:** The paper reports final accuracy but not convergence rates or resource usage. The iterative nature may be slow for complex images, but this is not analyzed. Needed evidence: average iteration counts, time per iteration, and experiments on early stopping.
3. **Dataset size limitations:** Geo-Code uses a small curated dataset (1,510 samples). It is unclear whether scaling with similarly high-quality annotations would improve GeoCodeLM’s generalization or cause saturation/noise. Resolution: train on progressively larger subsets or additional data and measure performance on out-of-distribution tasks.

## Limitations
- **Undisclosed implementation details:** Exact classical vision operators, their parameters, and fusion with LLM outputs are not specified, hindering precise replication.  
- **Missing agent prompts:** Prompting strategies for constructing the Visual Difference Map and for code editing are omitted, making the VEP loop’s behavior opaque.  
- **Limited scope:** The method is tailored to geometric code generation; generalization to other program synthesis domains (e.g., UI layouts, data processing) is unvalidated.

## Confidence
- **High:** Two-stage decoupling (topology first, refinement second) is well-supported by ablations and mechanistic description.  
- **Medium:** Pixel-wise anchoring improves precision; evidence is qualitative (baseline comparisons) but lacks controlled operator ablation.  
- **Low:** Visual Error Projection as a general principle for LLM-based refinement; success may be specific to geometric edge maps and untested in non-spatial code domains.

## Next Checks
1. **Operator Ablation Study:** Replace Stage 1’s vision operators with alternatives (e.g., Canny vs. deep edge detectors) and measure impact on structural scores (Layout Score) and pixel metrics (CD/HD). Validates whether claimed precision stems from specific operators.  
2. **VEP Utility Test:** Disable VEP (feed only scalar CD/HD to \(\pi_{\text{ref}}\)) and compare convergence speed and final CD/HD against the full loop. Determines if visual projection is necessary or merely accelerative.  
3. **Generalization Stress Test:** Apply Geo-Code to a non-geometric code dataset (e.g., Chart-to-Code). Measure failure rates in skeleton extraction and refinement stability. Tests scope limits of the geometric anchoring assumption.
