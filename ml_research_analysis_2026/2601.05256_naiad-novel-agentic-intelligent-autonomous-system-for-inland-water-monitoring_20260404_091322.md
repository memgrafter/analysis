# Naiad: Novel Agentic Intelligent Autonomous System for Inland Water Monitoring
## Quick Facts
- **ArXiv ID:** 2601.05256
- **Source URL:** https://arxiv.org/abs/2601.05256
- **Reference count:** 31
- **Primary result:** NAIAD achieves 82.98% correctness and 78.72% relevancy on a benchmark of inland water monitoring queries using Qwen2.5 (14B), balancing computational cost and reasoning performance.

## Executive Summary
NAIAD is an agentic AI system that translates natural language queries about inland water quality into automated, multi-step analytical workflows. It leverages a large language model (LLM) to dynamically construct and execute Directed Acyclic Graphs (DAGs) that orchestrate external tools for Earth Observation data retrieval (e.g., Sentinel-2), index calculation (NDCI), chlorophyll-a estimation, weather data, and bloom forecasting (CyFi). The system integrates Retrieval-Augmented Generation (RAG) to ground its reasoning in domain knowledge and applies a reflection mechanism to refine outputs. Evaluated on a curated benchmark across user expertise levels, NAIAD demonstrates high correctness (82.98%) and relevancy (78.72%) with the Qwen2.5 model, highlighting its potential for holistic inland water monitoring.

## Method Summary
The core method uses an LLM-driven agent to interpret user queries and generate a DAG-based execution plan. The pipeline starts with a query rewriter to clarify intent, followed by a RAG engine that retrieves relevant domain documents from a vector database (BAAI/bge-large-en-v1.5). The LLM then combines the original query, rewritten query, and retrieved context to produce a JSON DAG specifying tool nodes and data dependencies. A DAG executor validates and runs the workflow, invoking external tools sequentially or conditionally. After execution, a reflection module reviews outputs against the query, logging and correcting irrelevant or incorrect elements. Finally, a report generator synthesizes results into a tailored narrative. The system runs local LLMs (Qwen2.5, Gemma3) via Ollama to ensure data privacy and cost control.

## Key Results
- **Correctness:** 82.98% (Qwen2.5 and Gemma3) on benchmark queries.
- **Relevancy:** 78.72% with Qwen2.5, 68.09% with Gemma3.
- **Ablation outcome:** Qwen2.5 (14B) identified as optimal for balancing computational cost and reasoning performance.

## Why This Works (Mechanism)
### Mechanism 1: Dynamic DAG Construction from Natural Language
The LLM analyzes the query and retrieved context to instantiate a DAG at runtime. Nodes represent tool operations (e.g., fetch Sentinel-2, compute NDCI), and edges encode data dependencies inferred from tool metadata and query intent. The DAG is validated (acyclic, inputs satisfied) before execution. Evidence: Section 3.1 describes runtime DAG instantiation and edge inference. Break condition: Misinterpretation of tool I/O or dependency chains leads to invalid graphs and execution failure.

### Mechanism 2: RAG Grounding for Domain-Specific Tool Selection
A vector database stores curated documents on water quality indices, Sentinel-2 usage, CyFi, etc. For each query, top-10 relevant documents are retrieved and injected into the LLM prompt. This context guides appropriate tool invocation (e.g., choosing NDCI for chlorophyll estimation) and tailors report language to user expertise. Evidence: Abstract and Section 3.1 detail the RAG integration. Break condition: Queries outside the knowledge base scope yield irrelevant retrieval, leading to poor tool selection or irrelevant content.

### Mechanism 3: Agentic Reflection for Output Refinement
After DAG execution, a reflection phase (another LLM call) reviews aggregated outputs against the original query. It identifies and logs irrelevant or incorrect elements, prompting corrections or re-weighting. This creates a self-correcting loop before final report generation. Evidence: Abstract and Section 3.1 describe the reflection and correction mechanism. Break condition: Poorly calibrated reflection or fundamentally flawed initial outputs may lead to insufficient corrections or new errors.

## Foundational Learning
- **LLM Tool Calling & Function Schema Adherence:** The LLM must output structured calls that exactly match external tool JSON schemas. Mis-schema calls cause execution failures. Quick check: If a tool requires `{ "lat": number, "lon": number }` but the LLM outputs `{ "coordinates": [lat, lon] }`, execution fails.
- **Retrieval-Augmented Generation (RAG):** Grounds LLM decisions in domain knowledge to prevent hallucinations about tool usage. Quick check: If the vector database only contains ocean chlorophyll documents, a query about freshwater lakes may yield irrelevant tool selections.
- **Directed Acyclic Graphs (DAGs) for Workflow Orchestration:** DAGs encode the precise sequence and dependencies of analysis steps. Understanding DAGs is key to debugging. Quick check: If tool B depends on tool A's output but the DAG lacks an edge from A to B, runtime errors (missing inputs) occur.

## Architecture Onboarding
**Component map:** User Prompt → Query Rewriter → RAG (context retrieval) → DAG Planner (JSON graph) → DAG Executor (run tools) → Reflection (refine) → Report Generator → User Output

**Critical path:** The main processing flow follows the component map above.

**Design tradeoffs:**
- Single-agent vs. multi-agent: Simpler coordination but higher cognitive load per LLM call vs. specialized sub-agents.
- Local LLM (Ollama) vs. cloud API: Better privacy/cost control but limited model scale/performance.
- Dynamic DAG vs. pre-defined templates: Flexible for novel queries but risks invalid plans vs. robust but inflexible templates.

**Failure signatures:**
- Incorrect tool sequence: DAG edge order mismatches true dependency (e.g., report generation before data fetch). Check: Inspect generated DAG JSON node order.
- Missing tool invocation: Required tool (e.g., weather) absent from DAG. Likely cause: poor RAG retrieval or LLM oversight.
- Reflection failure: Output contains factual errors that reflection misses; logs show no correction flags.
- Tool API timeout/failure: Executor halts; check for fallback nodes or conditional branches.

**First 3 experiments:**
1. Basic single-tool query: "Get latest NDCI for Lake Mornos." Verify DAG has 1-2 nodes and output format matches expected Zonal Statistics.
2. Multi-step query: "Compare chlorophyll trends in Lake Trichonida last summer and predict cyanobacteria risk for next month." Verify DAG includes fetch, indices, chlorophyll calc, CyFi, weather, and synthesis with correct data dependencies.
3. Ambiguous location: "How is the water quality?" (no location). Verify system asks for clarification rather than guessing or failing silently.

## Open Questions the Paper Calls Out
### Open Question 1
How does NAIAD's performance generalize to geographically and ecologically diverse inland water bodies beyond the three Greek lakes studied? The evaluation was limited to three specific Greek lakes; its ability to handle varied hydrological regimes, satellite data availability, and regional semantic nuances remains untested. A multi-regional benchmark study is needed.

### Open Question 2
What is the impact on NAIAD's holistic monitoring capability and user utility when integrating additional sensor modalities (e.g., Landsat time-series, real-time IoT in-situ sensors) and advanced analytic tools (e.g., nutrient load modeling, shoreline change detection)? The current toolset is limited, and the effect of increased tool complexity on DAG construction, LLM reasoning, and report coherence is unknown.

### Open Question 3
Does a multi-agent architecture, where separate agents handle distinct sub-domains, offer measurable advantages over NAIAD's single-agent DAG orchestration for complex, long-horizon queries? The paper cites GeoLLM-Squad showing a 17% increase in correctness with multi-agent, but a direct comparison for inland water monitoring is missing.

## Limitations
- **Geographic scope:** Evaluation only on three Greek lakes; generalization to other regions unproven.
- **Toolset limitations:** Currently limited to Sentinel-2 and basic indices; lacks integration of other modalities (Landsat, IoT) and advanced analytics.
- **Architecture not compared:** Single-agent design not benchmarked against multi-agent alternatives; trade-offs in correctness, efficiency, and robustness uncertain.

3. **Reflection ablation with seeded errors:** Execute correct DAGs but inject subtle factual errors into intermediate outputs. Quantify reflection's detection/correction rate and any introduced hallucinations.
