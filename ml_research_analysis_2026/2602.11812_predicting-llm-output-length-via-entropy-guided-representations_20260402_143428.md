# Predicting LLM Output Length via Entropy-Guided Representations

## Quick Facts
- **arXiv ID:** 2602.11812  
- **Source URL:** https://arxiv.org/abs/2602.11812  
- **Reference count:** 40  
- **Primary result:** Entropy‑Guided Token Pooling (EGTP) reduces length prediction MAE by 29.16% over the best baseline, and when combined with a length‑aware scheduler, it improves end‑to‑end inference throughput and reduces padding ratio.

## Executive Summary
Batched LLM inference suffers from computational waste due to variable output lengths forcing excessive padding. This paper introduces a lightweight framework that reuses the main model’s internal activations to predict output length, avoiding extra model overhead. It proposes Entropy‑Guided Token Pooling (EGTP) for accurate static prediction and Progressive Length Prediction (PLP) for dynamic stochastic generation. Evaluated on the newly curated ForeLen benchmark, EGTP achieves a 29.16% reduction in Mean Absolute Error. Integrated with a length‑aware scheduler, the predictor significantly boosts throughput and cuts padding, addressing the inefficiency of existing methods.

## Method Summary
The framework leverages the hidden states produced during the prefill phase of the main LLM. For each prompt token, the next‑token probability distribution is extracted from the model’s logits to compute entropy. Entropies are softmax‑normalized into weights, and a weighted sum of the corresponding last‑layer hidden states yields a pooled representation. A single linear prediction head maps this vector to a distribution over discretized length bins (soft labels), with the expected value as the length estimate. For stochastic generation (e.g., RL sampling), PLP updates the remaining‑length prediction at every decoding step by concatenating the pre‑computed prompt feature with the hidden states of tokens generated so far and feeding the combined vector through the same head. The predictor is trained while freezing the LLM, using a joint loss combining cross‑entropy on the soft label distribution and MSE on the continuous length.

## Key Results
- EGTP reduces MAE by 29.16% compared to the strongest baseline (SSJF‑Reg).  
- When plugged into a shortest‑job‑first scheduler, the over‑length rate drops by 18.53%, improving overall throughput.  
- In RL sampling scenarios, PLP lowers MAE by 19.22% relative to static EGTP, enabling more effective scheduling for stochastic generation.

## Why This Works (Mechanism)

### Mechanism 1: Entropy‑Guided Token Pooling (EGTP)
EGTP improves static length prediction by weighting each token’s hidden state with its entropy: less certain tokens (higher entropy) contribute more to the pooled representation. The weighted sum creates an informative input to the regression head. Evidence shows a positive correlation (r=0.451) between token entropy and feature importance, and the reuse of the main model’s activations eliminates auxiliary overhead.  
*Break condition:* EGTP assumes a fixed generation length for a given prompt; it fails under highly stochastic “one‑to‑many” generation where the length varies with sampling.

### Mechanism 2: Progressive Length Prediction (PLP)
PLP addresses stochasticity by refining the remaining‑length estimate after each newly generated token. The prompt‑level pooled feature is combined with the hidden states of the tokens already produced, and the same prediction head outputs an updated remaining length. This autoregressive refinement matches the LLM’s own decoding process.  
*Break condition:* PLP introduces a small per‑step computational cost and requires access to hidden states during decode, which may be unavailable in some serving setups.

### Mechanism 3: Internal Activation Reuse
Both EGTP and PLP use the main LLM’s internal activations directly, avoiding separate models. This design minimizes inference overhead, simplifies deployment, and leverages representations already tuned for the generation task. The approach is incompatible with black‑box APIs and depends on the base model’s representation quality.

## Foundational Learning
- **Token Entropy:** Measures uncertainty of the next‑token distribution. *Why needed:* EGTP uses entropy to weight tokens; more uncertain tokens carry more signal about eventual length. *Quick check:* Higher entropy means the model is less certain about the next token.  
- **Autoregressive Decoding:** LLMs generate tokens sequentially. *Why needed:* PLP exploits this by updating length forecasts as each token appears. *Quick check:* At step *t*, PLP combines the prompt pooled feature with the first *t* generated tokens’ hidden states to predict remaining length.  
- **Padding Overhead in Batched Inference:** Requests with variable lengths force padding to the longest sequence in a batch, wasting compute. *Why needed:* Accurate length prediction enables grouping similar‑length requests, reducing padding. *Quick check:* If predicted lengths in a batch are similar, the padding ratio decreases.

## Architecture Onboarding

**Component map**  
Prefill LLM → Last‑layer hidden states H<sub>prompt</sub> → EGTP (entropy calculation + weighted pooling) → pooled feature *h* → Regression head → predicted length  
During decode (PLP): New token hidden state *h′<sub>t</sub>* → concatenate with *h* → same regression head → remaining length

**Critical path**  
1. Run prefill for all prompts; collect hidden states and logits.  
2. For static prediction: compute entropies, weight, pool → *h*, apply head → *ŷ*.  
3. For dynamic decoding: at each step *t*, fetch *h′<sub>t</sub>*, form *z<sub>t</sub>* = concat(*h*, {*h′<sub>1</sub>…*h′<sub>t</sub>*}), pass through head → *ŷ<sub>rem</sub>*, adjust scheduling.  
4. Length‑aware scheduler groups requests by predicted length.

**Design tradeoffs**  
- **EGTP vs. PLP:** EGTP is cheaper (one prediction) but static; PLP adapts to stochastic paths but adds per‑step cost.  
- **Soft‑label vs. classification:** Soft labels preserve ordinal relationships, yielding lower MAE.  
- **Temperature α:** Controls weighting sharpness; needs tuning.

**Failure signatures**  
- High MAE despite training: check entropy‑importance correlation or loss weighting (λ).  
- Throughput not improved: scheduling integration issue or predictions not actionable for grouping.  
- PLP slowdown: prediction head too large; reduce width or depth.

## Open Questions the Paper Calls Out
1. **Entropy as universal pooling metric?** Correlation validated only on one model/dataset; other attribution methods (SHAP, gradients) may work better across architectures and tasks.  
2. **PLP’s real‑world overhead:** Latency not isolated; per‑step cost may erode throughput under extreme batch sizes or fast decode models.  
3. **ForeLen benchmark coverage:** Built from text‑only datasets; may not reflect emerging workloads (agentic planning, multimodal outputs).  
4. **Extension to MoE architectures:** Sparse activations and routing complicate pooling; entropy may need adaptation to router probabilities.  
5. **Interaction with other schedulers:** Benefits demonstrated with SJF; sensitivity to prediction error for fairness‑aware or deadline‑aware policies is unknown.

## Limitations
- Token entropy correlation (r=0.451) might not generalize, weakening EGTP.  
- PLP’s per‑step latency is unquantified and could negate system‑level gains.  
- Requires access to model internals; unsuitable for black‑box APIs.  
- Soft‑label binning details (range, edges) omitted, hampering exact reproduction.  
- ForeLen’s diversity may not capture all production length distributions.

## Confidence
- **EGTP**: High – Strong MAE reduction (29.16%) on multiple models.  
- **PLP**: Medium – Demonstrated dynamic improvement; overhead and scalability unclear.  
- **Activation reuse**: High – Conceptual simplicity and clear savings vs. auxiliary models.

## Next Checks
