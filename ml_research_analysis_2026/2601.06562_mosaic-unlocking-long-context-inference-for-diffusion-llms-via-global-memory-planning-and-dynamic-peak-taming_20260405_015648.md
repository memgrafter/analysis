# Mosaic: Unlocking Long-Context Inference for Diffusion LLMs via Global Memory Planning and Dynamic Peak Taming

## Quick Facts
- **arXiv ID:** 2601.06562
- **Source URL:** https://arxiv.org/abs/2601.06562
- **Reference count:** 9
- **Primary result:** Reduces memory peak-to-average ratio by 2.71× and extends maximum supportable context length on fixed hardware by 15.89–32.98×, while lowering end-to-end inference latency by 4.12%–23.26% without accuracy loss.

## Executive Summary
Long-context inference with diffusion-based large language models (dLLMs) is hindered by prohibitive memory usage from transient activation recomputation and dynamic memory peaks—problems that autoregression-optimized systems mishandle. Mosaic resolves this with three integrated innovations: (1) a mask-only logits kernel that computes outputs solely for masked tokens, eliminating redundant memory and computation; (2) a lazy chunking optimizer that performs online heuristic search to adaptively split only the current memory-intensive operator when a peak occurs; and (3) a global virtual memory manager that issues a single contiguous memory request and binds physical pages on-demand to eradicate fragmentation. Together, these enable substantially longer contexts, lower memory pressure, and faster inference on existing hardware.

## Method Summary
Mosaic augments a dLLM inference stack (built on vLLM) with four coordinated components. First, a **graph registrar** defines a symbolic computation graph template with chunking barriers and in-place aliasing for whole-program visibility. Second, a **lazy chunking optimizer** runs an online bottleneck-driven search at each diffusion step: when projected memory exceeds capacity, it incrementally chunks the operator (logits or FFN) constituting the current peak until the fit is achieved. Third, a **global memory manager** uses a first-fit planner on the configured graph to assign reuse offsets for all transient tensors, then reserves a large contiguous virtual workspace via CUDA VMM and maps physical pages only up to the planned peak. Fourth, a custom **mask-only logits kernel** fuses gather and GEMM operations to produce logits exclusively for masked token positions, avoiding intermediate buffers. This end-to-end integration replaces standard operators with in-place variants that write into the pre-assigned virtual offsets.

## Key Results
- Memory peak-to-average ratio reduced by 2.71×.
- Maximum supportable context length extended by 15.89–32.98× on fixed hardware (RTX 309O 24GB, A100 40GB).
- End-to-end inference latency lowered by 4.12%–23.26% across varying mask ratios, with no accuracy compromise.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Computing logits only for masked tokens eliminates redundant memory allocation and computation for unmasked tokens.
- **Mechanism:** A fused gather-GEMM kernel directly processes scattered masked token hidden states via indirect addressing and tiled computation, avoiding an intermediate contiguous buffer. Logits are produced solely for masked positions.
- **Core assumption:** Only masked tokens require logits in each diffusion step for sampling; logits for already-sampled (unmasked) tokens are never used.
- **Evidence anchors:**
  - [abstract] "mask-only logits kernel to eliminate redundancy"
  - [section 4.2] "compute logits only for masked tokens... gather-GEMM fused kernel to directly process scattered inputs... eliminating intermediate buffers"
  - [corpus] Weak: neighboring papers (e.g., Sparse-dLLM, Focus-dLLM) address dLLM acceleration via caching or context focusing, not mask-only logits.
- **Break condition:** If the mask ratio (`rm`) becomes extremely low (~0), the kernel's overhead may outweigh its benefit, but the paper shows consistent gains across `rp` values (0.1, 0.5, 0.9).

### Mechanism 2
- **Claim:** An online bottleneck-driven search adaptively chunks only the current memory-intensive operator (logits or FFN) when necessary, minimizing peak memory with negligible latency overhead.
- **Mechanism:** At runtime, when physical memory is insufficient for the target context, the optimizer incrementally increases chunk counts (`K_logits`, `K_FFN`) for the operator constituting the current peak. It re-simulates the memory plan via the graph template and halts once the peak fits, avoiding over-chunking.
- **Core assumption:** Memory peaks are dynamic (toggle between logits and FFN based on `rm`) and the peak memory dictates the maximum supportable context; reducing non-dominant components yields no gain.
- **Evidence anchors:**
  - [abstract] "lazy chunking optimizer driven by an online heuristic search to adaptively mitigate dynamic peaks"
  - [section 3] "memory peak toggles between Logits (at high rm) and FFN (at low rm)"
  - [section 4.4] "search targets the current bottleneck... halts immediately when the peak fits... with negligible overhead"
  - [corpus] Weak: Streaming-dLLM uses suffix pruning; no direct evidence for online heuristic search.
- **Break condition:** If the relationship between `rm` and which operator is dominant is non-monotonic or highly nonlinear across models, the heuristic might misidentify the bottleneck, leading to suboptimal chunking.

### Mechanism 3
- **Claim:** A global virtual memory manager that issues a single contiguous memory request and binds physical pages on-demand eliminates external fragmentation from myopic, multi-request allocation.
- **Mechanism:** A graph registrar provides whole-computation-graph visibility. A first-fit planner derives a single reuse plan (offsets/sizes) for all transient tensors. A VMM-based allocator reserves a large virtual workspace upfront and lazily binds physical pages only up to the planned peak memory.
- **Core assumption:** Myopic planning (as in `torch.compile`) causes fragmentation by failing to globally reuse buffers; a single virtual workspace with a pre-calculated plan prevents this.
- **Evidence anchors:**
  - [abstract] "global memory manager to resolve fragmentation via virtual addressing"
  - [section 3] "myopic memory planning... results in significant fragmentation and inflated reserved memory"
  - [section 4.5] "eliminate this issue by generating a single global memory request... map physical pages to the planned addresses"
  - [corpus] Weak: PagedAttention (vLLM) addresses KV-cache fragmentation, not transient activation fragmentation.
- **Break condition:** If the reuse plan's first-fit heuristic fails to pack tensors efficiently under very complex liveness patterns (though the paper shows it matches ILP for their workloads), or if the OS/VMM cannot provide truly contiguous virtual addresses on some systems.

## Foundational Learning
- **Concept: Transient Activations vs. Persistent KV-Cache**
  - **Why needed here:** The fundamental shift in dLLMs is that the memory bottleneck moves from a persistent, growing KV-cache (AR) to repeatedly recomputed transient activations (dLLM). All of Mosaic's optimizations target this new bottleneck.
  - **Quick check question:** Why does bidirectional attention in dLLMs make KV-caching ineffective compared to causal attention in AR models?
- **Concept: Graph-based Liveness Analysis & Memory Reuse**
  - **Why needed here:** Mosaic's global planner relies on whole-graph visibility of tensor lifetimes to create a reuse plan. Understanding how liveness analysis enables buffer reuse is key to grasping why myopic planning fails.
  - **Quick check question:** If Tensor A's last use is before Tensor B's creation, what does this imply about their memory allocation?
- **Concept: Virtual Memory Management (VMM) for Contiguity**
  - **Why needed here:** The global manager uses VMM to present a logically contiguous buffer to the computation while only committing physical memory for the actual peak. This decouples logical layout from physical allocation.
  - **Quick check question:** What is the difference between reserving virtual address space and committing physical memory in the context of Mosaic's allocator?

## Architecture Onboarding
- **Component map:** Graph Registrar → Lazy Chunking Optimizer → Global Memory Manager (Planner + VMM Allocator) → Mask-only Logits Kernel & In-place Operator Wraps
- **Critical path:** Graph registration (offline) → Request received → Lazy chunking search (online) → Memory plan generation → VMM physical binding → Execution with custom kernels & in-place ops.
- **Design tradeoffs:**
  - **Lazy vs. Static Chunking:** Lazy disables chunking for short contexts (saves overhead) but adds search latency. Static simplifies but pays overhead unnecessarily.
  - **First-fit vs. ILP Planning:** First-fit is near-instant (~ms) but heuristic; ILP is optimal but prohibitively slow (~seconds). Paper shows first-fit's efficacy due to chunking reducing the peak to a fixed size.
  - **Virtual vs. Physical Contiguity:** Virtual contiguity (via VMM) avoids wasted pre-allocation but depends on OS/VMM support and may introduce minor TLB pressure.
- **Failure signatures:**
  - **OOM despite planning:** Inaccurate bottleneck search (heuristic failure) or first-fit packing failure under extreme fragmentation from complex liveness.
  - **Unexpected latency spikes:** Over-chunking (too many small chunks) on short contexts if lazy strategy fails; under-chunking if search stops prematurely.
  - **Fragmentation persists:** If graph breaks still occur, leading to subgraphs that the global manager cannot see, preventing a single-request plan.
- **First 3 experiments:**
  1. **Isolate Mask-only Kernel:** Run with `torch.compile` but replace only the logits projection with the fused kernel. Measure memory for logits tensor and per-step latency across `rm` values. *Expected: Logits memory eliminated for unmasked tokens; latency reduced.*
  2. **Add Lazy Chunking (No Global Manager):** Integrate the online search and chunking into the graph (using `add_barrier`). Use standard `torch` allocator. Test long contexts (e.g., 128k). *Expected: Peak-to-average ratio reduced, enabling longer context than baseline, but reserved memory still inflated due to fragmentation.*
  3. **Add Global Memory Manager:** Combine all components. Measure `Lmax` and peak-to-average ratio vs. Mosaic-Torch. *Expected: `Lmax` increases 15-33×, peak-to-average ratio drops 2.71×, reserved memory aligns with theoretical peak.*

## Open Questions the Paper Calls Out
- **Open Question 1:** How effectively does Mosaic generalize to non-Transformer-based diffusion language models (e.g., recurrent or convolutional architectures) and to future dLLM designs with different computational patterns?
- **Open Question 2:** Does Mosaic maintain its memory and latency advantages when evaluated on real long-context generative tasks (e.g., code synthesis, novel writing) rather than synthetic dummy inputs, and does the mask-only computation affect output quality for low mask-ratio scenarios?
- **Open Question 3:** Can the lazy chunking optimizer’s bottleneck-driven heuristic search find globally optimal chunk configurations for all memory-bound scenarios, or are there complex memory patterns (e.g., from intermediate reuse across non-adjacent operators) where the heuristic fails?
- **Open Question 4:** How does the global virtual memory manager’s single-request planning scale to extremely large context lengths (e.g., millions of tokens) in terms of planning latency and the feasibility of maintaining a contiguous virtual address space?
- **Open Question 5:** Does the mask-only logits kernel’s efficiency hold for highly sparse mask patterns (e.g., widely scattered masked tokens) and for models with very large vocabulary sizes, where the gather-GEMM fusion might underutilize GPU units?

## Limitations
- Generalization limits: The mask-only kernel's efficacy assumes a moderate mask ratio; overhead may negate benefits at extreme ratios, though paper tests `rm`∈{0.1,0.5,0.9}.
- Heuristic robustness: The lazy chunking's bottleneck-driven search may misidentify the dominant operator if the `rm`-operator relationship is non-monotonic or model-specific.
- Planner scalability: The first-fit reuse planner is near-instant but heuristic; its packing efficiency for extremely complex liveness patterns beyond evaluated dLLMs is unproven.

## Confidence
- **Memory reduction claims (PAR↓2.71×, Lmax↑15-33×):** High. Strong ablation evidence with clear baselines and hardware measurements.
- **Mask-only kernel logic & latency:** Medium. Internal benchmarks show gains, but external verification of kernel correctness/efficiency is absent.
- **Lazy chunking optimality:** Medium. Paper shows it matches/beats static chunking, but no exhaustive search confirms global optimality.
- **Fragmentation elimination via VMM:** Medium. Measured reserved memory aligns with theoretical peak, but long-term system-level fragmentation and TLB impact unevaluated.

## Next Checks
1. **Isolate mask-only kernel correctness & overhead:** Implement a minimal fused gather-GEMM kernel (e.g., using `torch.scatter` + `matmul` as baseline) and measure memory/latency across `rm`=0.01–0.99 on a single transformer layer. Validate output parity and identify `rm` threshold where overhead dominates.
2. **Stress-test lazy bottleneck search under non-monotonic `rm`:** Artificially design a synthetic computation graph where the dominant operator switches multiple times per generation step (e.g., alternating high/low `rm`). Compare Mosaic's chunk counts against a brute-force optimal search to quantify heuristic deviation.
3. **Challenge first-fit planner with adversarial liveness:** Generate a synthetic graph with highly irregular tensor lifetimes (e.g., many small, overlapping short-lived tensors) to force fragmentation. Compare first-fit's planned peak and reserved memory against an ILP solver's optimum to measure worst-case packing inefficiency.
