# DynamicGTR: Leveraging Graph Topology Representation Preferences to Boost VLM Capabilities on Graph QAs

## Quick Facts
- **arXiv ID:** 2602.21864
- **Source URL:** https://arxiv.org/abs/2602.21864
- **Reference Count:** 40
- **Primary Result:** DynamicGTR dynamically selects the optimal graph topology representation (GTR) per query, improving average accuracy by +6.3% and reducing average token consumption by -276.8 on GPT-4o for in-domain tasks.

## Executive Summary
Vision-Language Models (VLMs) struggle with graph question answering (QA) because they rely on a single, fixed graph topology representation (GTR). This one-size-fits-all approach often yields inaccurate or verbose responses. DynamicGTR introduces a framework that dynamically selects the best GTR for each query during inference, balancing accuracy and brevity. It builds a diverse, model-agnostic GTR pool and trains a lightweight router on a probe dataset to learn query-to-GTR preferences, guided by a Graph Response Efficiency (GRE) metric. Experiments across seven algorithmic tasks and two real-world applications (link prediction, node classification) show consistent improvements in both accuracy and token efficiency over strong baselines, with strong transferability across tasks, domains, and different VLMs.

## Method Summary
DynamicGTR operates in two phases. First, a **probe phase** constructs a GTR Preference dataset (GTRP). A diverse pool of eight model-agnostic GTRs (five visual layouts via Graphviz, three textual formats) is evaluated on a synthetic dataset of canonical graph algorithm questions (e.g., connectivity, shortest path) using a target VLM. For each query, the Graph Response Efficiency (GRE) score—combining accuracy and token efficiency via a tunable parameter α—is computed for every GTR. The GTR(s) with the highest GRE become the preferred labels for that query. Second, a lightweight router (DeBERTaV3-base) is trained on GTRP as a multi-label classifier to predict the preferred GTR(s) from the query text. At inference, the router selects a GTR for a new query, and the VLM generates an answer using that representation. The framework is model-agnostic, transferable across VLMs, and lets users tune the accuracy-brevity trade-off via α.

## Key Results
- **Pareto Improvement:** DynamicGTR achieves higher average GRE than any single fixed GTR across seven in-domain algorithmic tasks (+6.3% accuracy, -276.8 tokens on GPT-4o).
- **Cross-Model Transfer:** A router trained on probe data from one VLM (e.g., GPT-4o) benefits other VLMs (e.g., Gemini-2.5 Pro) without retraining.
- **Real-World Applicability:** Gains transfer to link prediction and node classification tasks on real-world graphs, albeit with smaller margins.

## Why This Works (Mechanism)
### Mechanism 1
Different graph topology representations (GTRs) exhibit task-specific performance preferences in accuracy and token efficiency. The framework constructs a GTR Preference dataset (GTRP) by probing a diverse GTR pool on synthetic graph algorithmic tasks. For each query, it computes the Graph Response Efficiency (GRE) score (balancing accuracy and token consumption) across all GTRs and selects the top-performing ones as labels. The core assumption is that task type and query features predictably correlate with optimal GTR choice, and these preferences are stable enough across instances of the same task to learn from a probe dataset. Evidence includes the abstract's claim of dynamic selection for balancing accuracy and brevity, and Section 4.4 describing GTRP construction. A break condition would be if query-level preferences are highly stochastic or do not generalize beyond the specific probe graphs.

### Mechanism 2
A lightweight router can learn the mapping from query semantics to optimal GTRs using the GTRP dataset, enabling dynamic selection at inference without model-specific tuning. Treating GTR selection as a multi-label classification problem, a DeBERTaV3-base model is trained on GTRP to predict which GTR(s) will maximize GRE for a given query. The core assumption is that the textual/visual features of the question and graph description contain sufficient signal to predict the GRE-optimal GTR, and this mapping is consistent enough across graph samples within a task to be learned. Evidence includes Section 4.5's router specification and Section 5.5's cross-model transfer results. A break condition would be if the optimal GTR depends on subtle, inaccessible details of the VLM's internal processing rather than query semantics.

### Mechanism 3
Dynamic GTR selection yields a Pareto improvement over any single fixed GTR by adaptively applying the right representation for each query, thereby enhancing both accuracy and efficiency. At inference, the router selects a GTR for the query; the VLM then processes the graph using that GTR. By choosing the GTR with the highest expected GRE for that query type, the system avoids the systematic suboptimality of a one-size-fits-all approach. The core assumption is that the GRE metric effectively captures a meaningful, user-tunable trade-off between answer correctness and response brevity, and maximizing it per-query leads to overall system improvement. Evidence includes the abstract's customizable trade-off claim, Section 4.3's GRE definition, and Table 5 showing no single GTR dominates all tasks. A break condition would be if the GRE metric mis-specifies the utility function (e.g., log transforms distort true costs, or α cannot capture user priorities).

## Foundational Learning
- **Graph Topology Representations (GTRs):** Distinct ways to encode a graph for a VLM, such as visual layouts (e.g., Graphviz `neato`) or textual formats (e.g., edge list). *Why needed:* Understanding GTR characteristics explains why a single fixed representation is insufficient and what the router chooses between. *Quick check:* For cycle detection, why might a visual GTR like `Vneato` be preferred over `Tset` (edge list)?
- **Graph Response Efficiency (GRE) Score:** Scalarized objective: GRE = log(1+100·accuracy) + α·(−log(tokens)). *Why needed:* GRE defines "optimal" for the router, quantifying the accuracy-brevity trade-off and underpinning GTRP construction. *Quick check:* How would changing α from 0.5 to 1.0 alter preferred GTRs for a shortest path task? Why?
- **GTR Preference Dataset (GTRP):** Dataset of queries labeled with their GRE-optimal GTR(s), built by probing. *Why needed:* This dataset trains the router to map queries to preferred GTRs, enabling dynamic selection. *Quick check:* Why is it necessary to run *k* independent trials per (query, GTR) pair when constructing GTRP, and what does this robustness help capture?

## Architecture Onboarding
- **Component map:**
  GTR Pool (R_ZS) -> Probe Executor -> GRE Calculator -> GTRP Constructor -> GTR Router (φ) -> VLM Reasoner
  (Also: Trade-off Tuner for α, which influences GRE Calculator and GTRP Constructor.)

- **Critical path:**
  1. Generate probe dataset of graph algorithm QAs.
  2. Probe Executor runs all GTRs on probe dataset with target VLM, records accuracy and tokens.
  3. GRE Calculator and GTRP Constructor build labeled dataset (query, preferred GTRs).
  4. Router φ trained on GTRP.
  5. For new query q, router φ outputs selected GTR r_q.
  6. VLM Reasoner processes q + r_q to produce answer.

- **Design tradeoffs:**
  - Model-Agnostic vs. Specialized GTRs: Using only generation methods independent of VLM parameters ensures broad compatibility but may miss model-specific optimizations.
  - Static Pool vs. Dynamic Routing: A fixed, curated pool (R_ZS) limits expressiveness but makes the router's search space manageable and training feasible.
  - Accuracy vs. Brevity: Controlled by α. Higher α prefers concise GTRs (often visual), risking accuracy; lower α favors verbose GTRs (often textual).

- **Failure signatures:**
  - Poor Transfer: Router trained on synthetic small-graph tasks fails on large real-world graphs or different task types. *Mitigation: Expand probe dataset diversity.*
  - Router Overfitting: High training accuracy but no improvement or degradation on actual VLM inference. *Mitigation: Ensure diverse probe graphs/questions; use multiple VLM seeds for probing.*
  - High Latency: GTR generation (complex visual layouts) or router inference adds unacceptable overhead. *Mitigation: Pre-generate all GTRs for a given graph; use smaller/faster router model.*

- **First 3 experiments:**
  1. **Task-Level Preference Analysis:** Compute top-3 GTRs per task from GTRP (Table 2). Validate preferences align with task characteristics (e.g., perceptual tasks prefer visual GTRs).
  2. **Router vs. Single GTR Ablation:** For each task, compare DynamicGTR (router) against every single GTR in R_ZS on accuracy and token consumption (Table 5). Confirm router's Avg.GRE exceeds all individual GTRs.
  3. **Cross-Model Transfer Test:** Train router on probe data from VLM A (e.g., GPT-4o). Apply it to VLM B (e.g., Gemini-2.5 Pro) without retraining. Measure performance against router trained natively on VLM B and best single-GTR baseline (Table 8).

## Open Questions the Paper Calls Out
- **Question 1:** Can the preferences for graph topology representations (GTRs) be systematically leveraged to improve both accuracy and efficiency in VLM-based graph QA?  
  *Basis:* The paper explicitly questions whether these preferences can make graph QA "accurate and inexpensive." Unresolved because generalizability across diverse VLMs, graph domains, and user-defined trade-offs remains underexplored. Resolution would require comprehensive benchmarking across a wider array of VLMs, graph types, and real-world applications under varied α preferences.

- **Question 2:** To what extent do GTR preferences learned from synthetic graph algorithmic tasks transfer to complex, large-scale, or semantically rich real-world graph applications?  
  *Basis:* The paper asks how and to what extent GTRs enhance VLM capabilities, showing transfer from synthetic tasks to link prediction and node classification. Unresolved because transfer boundaries (e.g., extremely large graphs, attributed graphs, molecular graphs) are not investigated. Resolution would involve evaluating on diverse out-of-domain tasks with varying graph scales, densities, and semantic complexities.

- **Question 3:** What are the limitations of the current fixed GTR pool (R_ZS) and could expanding it with additional representation types (e.g., 3D visualizations, hybrid textual-visual formats) yield further performance gains?  
  *Basis:* Inferred; the pool is constructed from eight representations following model-agnostic, variety, and effectiveness principles, but not claimed exhaustive. Unresolved because the pool may not capture all useful representations, especially for graphs with specific characteristics. Resolution would require systematic evaluation of candidate new GTRs and measuring improvements in GRE.

- **Question 4:** How can the trade-off parameter α in the GRE metric be automatically adapted to user preferences or task requirements without manual tuning?  
  *Basis:* Inferred; α is left to users, with no guidance on selection for specific scenarios. Unresolved because manual tuning may be cumbersome and suboptimal. Resolution would involve developing methods to infer α from natural language user specs or task characteristics, validated via user studies or automated alignment.

- **Question 5:** How stable are the learned GTR preferences (as captured in GTRP) over time as VLMs are updated or new architectures emerge?  
  *Basis:* Inferred; GTRP is constructed for specific VLMs and transfer shows some robustness, but long-term stability is unaddressed. Unresolved because VLMs rapidly advance; preferences learned today may become obsolete. Resolution would require longitudinal studies across successive VLM versions and methods to update routers efficiently.

## Limitations
- **Reproduction Ambiguities:** Router input format (textual graph encoding), exact probe parameters (k trials, temperature), and graph validity rules (e.g., DAGs for topological sort) are unspecified, risking inconsistent implementations.
- **GRE Metric Alignment:** Logarithmic scaling and α choice may not reflect actual user satisfaction on complex queries; the metric's utility function might misalign with true downstream task success.
- **Transfer Boundaries:** Gains on real-world tasks are modest (e.g., small margin on ogbl-ppa); the router's effectiveness may degrade on extremely large, dense, or semantically rich graphs beyond the probe distribution.
