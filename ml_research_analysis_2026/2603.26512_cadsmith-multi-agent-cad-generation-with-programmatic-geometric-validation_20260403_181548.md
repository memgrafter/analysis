# CADSmith: Multi-Agent CAD Generation with Programmatic Geometric Validation

## Quick Facts
- **arXiv ID:** 2603.26512
- **Source URL:** https://arxiv.org/abs/2603.26512
- **Reference count:** 34
- **Primary result:** On a 100-prompt benchmark, CADSmith achieves 100% execution rate (vs. 95% zero-shot) and significantly improves geometric accuracy: median F1 from 0.9707 to 0.9846, median IoU from 0.8085 to 0.9629, and mean Chamfer Distance from 28.37 to 0.74.

## Executive Summary
CADSmith is a multi-agent pipeline for text-to-CAD generation that systematically addresses both execution errors and geometric inaccuracies through two nested correction loops. An inner loop resolves code-level failures using retrieval-augmented generation over error patterns, while an outer loop combines exact OpenCASCADE kernel metrics with a vision-language model Judge to refine shape fidelity. The system uses RAG over curated CadQuery API documentation instead of fine-tuning, enabling it to stay current with library evolution. Evaluated on a custom 100-prompt benchmark (T1–T3), it achieves perfect execution and substantial gains in dimensional accuracy, demonstrating the effectiveness of closed-loop refinement with independent validation.

## Method Summary
The pipeline comprises five agents: (1) Planner converts the natural language prompt into a JSON design specification; (2) Coder generates a CadQuery script using retrieval over a knowledge base of API methods (KB1); (3) Executor runs the script in a sandbox, returning either a success (mesh + OpenCASCADE metrics) or a failure (traceback); (4) if execution fails, an Error Refiner (with retrieval over common error patterns, KB2) corrects the code (inner loop, up to 3 attempts); (5) on execution success, a Validator Judge (a strong VLM plus kernel metrics) assesses geometric correctness; if validation fails, a geometric Refiner revises the code (outer loop, up to 5 attempts). The dual loops separate concerns: inner loop for syntax/API errors, outer loop for shape/design errors. All agents are LLM-based; the Judge uses Claude Opus, while the Coder/Refiner use Claude Sonnet.

## Key Results
- Execution rate: 100% (vs. 95% for zero‑shot generation).
- Median F1 improved from 0.9707 to 0.9846; median IoU from 0.8085 to 0.9629.
- Mean Chamfer Distance reduced from 28.37 to 0.74, indicating a drastic increase in point‑cloud similarity to reference meshes.

## Why This Works (Mechanism)
1. **Dual nested correction loops** systematically eliminate error classes: the inner loop fixes execution failures via RAG over error patterns, while the outer loop uses kernel metrics plus a VLM to catch geometric defects. This separation prevents conflation of feedback signals and creates a closed refinement cycle. The design is supported by ablations showing that disabling either loop harms performance (Section IV.B).

2. **Independent VLM Judge** avoids self‑confirmation bias. The Judge cross‑references exact OpenCASCADE metrics (volume, bounding box, validity) with three‑view renders, enabling detection of “false convergence” (e.g., correct volume but wrong feature count). Ablations removing vision cause catastrophic drops on complex T3 prompts, proving that visual holistic assessment is indispensable for structural correctness.

3. **Retrieval‑augmented generation** over up‑to‑date API documentation (KB1) and error patterns (KB2) injects precise procedural knowledge without fine‑training. This keeps the system adaptable to CadQuery changes and leverages the base LLM’s coding ability. The approach contrasts with fine‑tuning (e.g., Text‑to‑CadQuery) and aligns with recent trends in code generation.

## Foundational Learning
- **Concept: CadQuery/OpenCASCADE Geometry Kernel**  
  *Why needed here:* The system relies on kernel metrics (volume, bbox, validity) to quantify geometric fidelity; understanding how CadQuery scripts translate to kernel operations is key to interpreting these metrics.  
  *Quick check question:* If a `cylinder()` call produces a valid solid but with the wrong radius, which kernel metric would definitely detect this error?

- **Concept: LLM Self‑Correction & Iterative Refinement**  
  *Why needed here:* The entire pipeline assumes LLMs can improve given structured feedback. Knowing the limitations of self‑correction (oscillation, bias) explains the need for an independent Judge and history tracking in the outer loop.  
  *Quick check question:* Why might using the same LLM as both Coder and Validator lead to failure even with feedback?

- **Concept: Multi‑Agent System Design**  
  *Why needed here:* Decomposing the task into Planner, Coder, Executor, Validator, and Refiner defines clear responsibilities and message passing, enabling modular extension and debugging.  
  *Quick check question:* What specific role does the Planner play that prevents the Coder from directly interpreting the raw prompt?

## Architecture Onboarding
- **Component map:**  
  Planner → Coder → Executor → (if fail: Error Refiner → Executor, inner loop ≤3) → (if success: Validator → if fail: Refiner → Executor, outer loop ≤5)  
- **Critical path:** The pipeline diverges based on execution success; iterative refinement proceeds only if the preceding agent signals failure.
- **Design tradeoffs:**  
  *RAG vs. fine‑tuning:* RAG stays current with API changes but depends on doc quality; fine‑tuning risks staleness.  
  *Vision inclusion:* Fixed three‑view renders are cheap but may miss small gaps (e.g., T3 019); adaptive views would cost more.  
  *Model selection:* Using a stronger Judge (Claude Opus) avoids self‑bias but increases cost/latency; a weaker Judge might miss subtle errors.
- **Failure signatures:**  
  *Execution failure:* Traceback indicates API misuse/syntax error (inner loop active).  
  *Validation failure:* Judge feedback cites missing features, wrong dimensions, or structural issues (outer loop active).  
  *False positive:* Metrics (F1/IoU) are high but geometry is unmanufacturable (e.g., small gaps) and evades both loops.  
  *Oscillation:* Refiner cycles between two incorrect states; mitigated by history in feedback.
- **First 3 experiments:**  
  1. *Baseline replication:* Run zero‑shot configuration (no Planner, no loops) on 10 T1 prompts; expect ~90% execution but poor dimensional accuracy (high CD).  
  2. *Vision ablation test:* Run full pipeline with vision removed on 5 T3 prompts; predict drastic degradation in F1/IoU and spike in CD (as in Table II).  
  3. *Error pattern analysis:* On 3 prompts with outer‑loop iterations, log Judge feedback and Refiner changes; identify whether corrections are parameter tweaks vs. strategy changes (e.g., switching boolean operation).

## Open Questions the Paper Calls Out
1. How can the Validator's three‑view rendering be enhanced to reliably detect subtle geometric discontinuities such as small gaps or incomplete boolean unions? The paper identifies a failure (T3 019) where gaps escaped detection and suggests adaptive view selection or higher‑resolution crops (Section V).  
2. Can CADSmith’s multi‑agent pipeline be extended to generate valid multi‑part assemblies, and what architectural modifications are required? The discussion lists support for assemblies as a natural extension, implying current limitation to single solids.  
3. What is the relative contribution of programmatic kernel metrics versus vision‑language judgment in driving effective refinement across varying geometric complexities? Ablations show vision is critical for T3 but not for T1/T2, but per‑iteration or per‑error‑type contributions remain unquantified.  
4. How does the strength and architecture of the VLM Judge affect validation accuracy and the risk of self‑confirmation bias? The system uses a stronger judge (Claude Opus) than the generator (Sonnet), but no systematic comparison of VLM choices or required strength gap exists.

## Limitations
- Knowledge bases (KB1: 155 CadQuery methods; KB2: 25 error patterns) and keyword‑matching retrieval rules are unreported, making exact replication and coverage assessment difficult.
- Full Validator Judge prompt, metric thresholds, and escalation heuristics are omitted, hindering independent calibration and reproducibility.
- The fixed three‑view rendering scheme can miss small geometric discontinuities (e.g., T3 019), limiting reliability for precision engineering applications.

## Confidence
- **Dual correction loops:** Medium – strong internal evidence (ablations, detailed specs) but no independent replication or testing on other CAD kernels.
- **VLM + kernel validation:** Medium – ablation proves vision necessity for complex shapes, yet the specific VLM (Claude Opus) and three‑view design lack comparative baselines.
- **RAG over documentation:** Low – paper asserts adaptability over fine‑tuning but provides no head‑to‑head experiment; KB coverage and retrieval quality are unmeasured externally.
