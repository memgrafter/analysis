# Training LLMs for Multi-Step Tool Orchestration with Constrained Data Synthesis and Graduated Rewards

## Quick Facts
- **arXiv ID**: 2603.24709  
- **Source URL**: https://arxiv.org/abs/2603.24709  
- **Reference count**: 31  
- **Primary result**: +14.6% turn accuracy (Qwen3-8B, oracle) and +13.7% (Qwen2.5-7B, generalization) on ComplexFuncBench via constrained data synthesis and graduated rewards.

## Executive Summary
Multi-step tool orchestration—chaining dependent API calls—remains a key challenge for LLMs due to parameter errors and credit assignment in long horizons. This work introduces a reinforcement learning framework that combines a deterministic, cache-based environment built from 100k+ real API responses with a constrained data synthesis pipeline using workflow templates to generate valid, dependency-consistent traces. The reward design decomposes correctness into Ratomic (individual call validity at syntactic and semantic levels) and Rorch (correct sequencing and dependency propagation), providing dense learning signals. Evaluated on ComplexFuncBench, the method yields substantial turn accuracy improvements (e.g., +14.6% for Qwen3‑8B in an oracle setting, +13.7% for Qwen2.5‑7B in generalization). Ablation studies confirm both reward components are essential: the combined approach achieves 52.1% turn accuracy versus 32.2% with Ratomic only and 37.5% with Rorch only. Performance plateaus with minimal synthetic data (~67 samples), indicating high data efficiency.

## Method Summary
The framework constructs a deterministic execution environment by caching 100k+ real API responses from Booking.com across 40 functions. Workflow templates—curated sequences of function calls with explicit dependency edges—guide training data generation. The constrained synthesis pipeline builds a reverse index over the cache and samples entries step-by-step while respecting dependencies, guaranteeing internally consistent traces; an LLM then produces a natural language query matching the sampled parameters. During training, Group Relative Policy Optimization (GRPO) uses a graduated reward: Ratomic validates each call via AST matching and execution success; Rorch evaluates sequence-wide alignment with the ground‑truth dependency graph, rewarding correct ordering and propagation. The two signals (combined with λ=0.5) yield dense gradients that mitigate credit assignment, and the synthesis process achieves high data efficiency, saturating after only ~67 synthetic examples.

## Key Results
- Turn accuracy gains: +14.6% (Qwen3‑8B, oracle) and +13.7% (Qwen2.5‑7B, generalization) over baseline on ComplexFuncBench.  
- Ablation: combined reward yields 52.1% turn accuracy vs 32.2% (Ratomic only) and 37.5% (Rorch only), demonstrating necessity of both components.  
- Data efficiency: performance plateaus with ~67 synthetic samples; increasing samples per template (up to 7) shows no consistent improvement.

## Why This Works (Mechanism)
### Mechanism 1: Deterministic Environment and Constrained Synthesis
- **Claim**: A deterministic, cache‑based environment built from 100k+ real API responses, combined with workflow‑template‑guided constrained synthesis, ensures dependency‑consistent multi‑step traces with high generation efficiency.  
- **Mechanism**: Workflow templates define valid function sequences and dependencies. The synthesis pipeline builds a reverse index over the cache and samples traces step‑by‑step, guaranteeing that each trace satisfies dependencies. An LLM then generates a query matched to the exact parameters.  
- **Core assumption**: Sampling within template skeletons preserves dependency consistency; random sampling often yields invalid bindings.  
- **Evidence anchors**: Abstract and Section 2.2 describe the template‑guided synthesis and reverse‑index sampling; trace generation fails when the reverse‑index intersection is empty, indicating coverage gaps.  
- **Break condition**: Empty reverse‑index intersection aborts trace generation, signaling insufficient cache or template coverage.

### Mechanism 2: Graduated Reward Design
- **Claim**: Decomposing correctness into Ratomic and Rorch provides dense learning signals, mitigating sparse‑reward credit assignment in long‑horizon workflows.  
- **Mechanism**: Ratomic scores each call via AST validation (function name, parameters, values) and semantic validation (execution success). Rorch evaluates sequence‑wide alignment with the dependency graph, ensuring correct ordering and propagation. Total reward \(R_{\text{total}} = \lambda R_{\text{atomic}} + (1-\lambda)R_{\text{orch}}\) yields orthogonal gradients.  
- **Core assumption**: Separating atomic and orchestration aspects yields clearer gradients than a binary success/failure signal.  
- **Evidence anchors**: Ablation studies (Section 3.4) show collapse when either component is omitted; Figure 2 displays diverging Ratomic/Rorch curves in single‑component training.  
- **Break condition**: Omitting one component leads to either atomic collapse (high Ratomic, low Rorch) or orchestration collapse (high Rorch, low Ratomic).

### Mechanism 3: High Data Efficiency
- **Claim**: Constrained synthesis achieves high data efficiency—performance plateaus with minimal synthetic data (~67 samples)—because templates capture essential structural patterns, reducing need for large sample counts per template.  
- **Mechanism**: The pipeline uses a small set of validated workflow templates as skeletons. By sampling from a cache that already satisfies dependencies, each trace is guaranteed valid. The model learns template patterns rather than memorizing specific values, enabling quick convergence.  
- **Core assumption**: Diversity of dependency structures (not sample density) is the primary bottleneck; templates represent compositional primitives that generalize.  
- **Evidence anchors**: Abstract notes plateau at ~67 samples; Section 3.5 scaling analysis shows no consistent improvement from 1 to 7 samples per template, and suggests expanding template diversity may be more valuable.  
- **Break condition**: Insufficient template coverage—i.e., test dependency patterns absent from the template set—degrades performance regardless of sample count.

## Foundational Learning
- **Reinforcement Learning for LLMs (e.g., GRPO/PPO)**  
  *Why needed*: The paper uses Group Relative Policy Optimization (GRPO) to fine‑tune the LLM policy using the graduated rewards. Understanding how RL adapts LLM outputs (discrete tokens) via reward signals is key.  
  *Quick check*: "Why is policy gradient methods like GRPO suitable for LLM tool orchestration compared to supervised fine‑tuning alone?"

- **Multi‑step Tool Orchestration & Dependency Graphs**  
  *Why needed*: The core task is chaining API calls where later parameters depend on earlier outputs. Grasping directed acyclic graph (DAG) structures and propagation logic is essential.  
  *Quick check*: "Given a workflow of 3 steps where step 2 uses output from step 1, what happens if step 1's parameter is slightly wrong? How does this differ from independent steps?"

- **Reward Shaping & Sparse vs. Dense Signals**  
  *Why needed*: The graduated reward design directly addresses the sparse binary reward problem. Understanding why intermediate feedback (partial correctness) matters for credit assignment in long sequences is fundamental.  
  *Quick check*: "What is the 'credit assignment problem' in multi‑step tool use, and how does decomposing rewards into atomic and orchestration components help?"

## Architecture Onboarding
**Component map:** Workflow Templates -> Constrained Synthesis Pipeline -> RL Training Loop -> Cache & Environment (execution)  
**Critical path:** Real API collection → template curation → cache indexing → constrained trace sampling → query generation → environment rollouts → reward computation (Ratomic + Rorch) → policy gradient update.  
**Design tradeoffs:**  
- Real APIs vs. synthetic simulation: Real responses ensure consistency but require caching; simulation risks invalid dependency chains.  
- Template diversity vs. generation efficiency: More templates cover more patterns but require validation; fewer templates yield high sample efficiency but may bottleneck generalization.  
- Ratomic vs. Rorch weighting (λ): Equal weighting (0.5) used; tuning may be needed for domain‑specific error profiles.  
**Failure signatures:**  
- Sampling failure: reverse‑index intersection empty → trace abandoned (indicates cache/template coverage gaps).  
- Atomic collapse: high Ratomic, low Rorch → valid calls but wrong order/missing steps.  
- Orchestration collapse: high Rorch, low Ratomic → correct sequence but invalid parameters.  
- SFT overfitting: degraded cross‑domain performance, increased function‑selection errors.  
**First 3 experiments:**  
1. Oracle setting: Train and evaluate on same queries; expect >10% turn accuracy gain vs zero‑shot.  
2. Reward ablation: Train with Ratomic‑only, Rorch‑only, and combined; expect combined to significantly outperform; monitor collapse via reward component curves.  
3. Data scaling: Vary samples per template (1,3,5,7); expect performance to plateau early (~67 samples) and not improve monotonically.

## Open Questions the Paper Calls Out
### Open Question 1
**Question**: How can workflow templates be automatically generated to increase diversity, given manual curation is limiting and diversity seems more valuable than sample density?  
**Basis in paper**: [inferred] In Section 3.5, the authors note that performance plateaus with increased sample density and suggest that "expanding template diversity (the 40 templates that failed validation) may be more valuable than generating more samples per existing template."  
**Why unresolved**: Manual template curation is labor‑intensive and may not cover the full spectrum of real‑world workflows; the existence of 40 failed templates indicates gaps.  
**What evidence would resolve it**: Developing an automated method for template induction from API specifications or usage logs, and evaluating whether automatically discovered templates improve generalization on ComplexFuncBench.

### Open Question 2
**Question**: Does the graduated reward design effectively handle workflows with conditional or optional steps, where multiple valid execution sequences exist?  
**Basis in paper**: [explicit] The reward Rorch (Section 2.3) requires exact matching to a fixed ground truth sequence. The paper evaluates patterns like "alternative options" (Section 3.6, Table 6), but the reward does not explicitly account for conditional correctness.  
**Why unresolved**: For conditional workflows, an agent might correctly execute a subset of steps based on runtime conditions, but the current reward would penalize missing steps that were not needed, misguiding learning.  
**What evidence would resolve it**: Constructing a benchmark with truly conditional workflows and comparing the existing Rorch against alternative rewards that allow flexible step matching or outcome‑based evaluation.

### Open Question 3
**Question**: How can the framework be adapted to non‑deterministic or time‑varying APIs, given its reliance on a static cache of responses?  
**Basis in paper**: [inferred] The deterministic environment is built from a cache of 100k+ real API responses (Section 2.2). The cache ensures dependency consistency only if API responses remain stable; real APIs change over time.  
**Why unresolved**: A policy trained on a static cache may fail when deployed on live APIs with broken dependency chains due to data staleness or non‑determinism.  
**What evidence would resolve it**: Testing trained models on live APIs or a dynamic test set to measure degradation, then exploring techniques like freshness‑aware caching, mixing live data during training, or robust RL.

### Open Question 4
**Question**: Why do query parameter extraction errors remain higher than dependency propagation errors even after RL training, and how can they be reduced?  
**Basis in paper**: [explicit] Table 5 shows that after GRPO training, Query Param Err is 12.7% while Dependency Param Err is 5.6%, despite the graduated reward including parameter value matching.  
**Why unresolved**: This gap suggests the model struggles more with interpreting natural language queries than with propagating values; the current training does not specifically address this asymmetry.  
**What evidence would resolve it**: Analyzing failure modes in query parameter extraction (e.g., date parsing, entity recognition), then designing targeted interventions like query‑focused data augmentation or auxiliary losses for parameter prediction.

## Limitations
- **Template curation**: Exact methodology (manual/LLM‑assisted/log‑mining) and coverage of the 100+ workflow templates are unspecified, limiting reproducibility and generalization claims.  
- **Validator implementations**: The eight specialized validators (e.g., date/coordinate checks) are described but not detailed; their fidelity to real API error behavior is unknown.  
- **Benchmark scope**: Evaluation is restricted to ComplexFuncBench; performance on other multi‑step orchestration benchmarks (e.g., ToolBench, API‑Bank) is not reported, raising questions about broad applicability.

## Confidence
- Graduated reward design: **High** confidence.  
- Deterministic environment & constrained synthesis: **High** confidence.  
- Data efficiency (plateau at ~67 samples): **Medium** confidence (impact of template diversity inferred, not directly measured).  
- Generalization to unseen domains: **Low** confidence (cross‑domain tests limited).
