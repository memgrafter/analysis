# Task Scarcity and Label Leakage in Relational Transfer Learning

## Quick Facts
- **arXiv ID:** 2603.29914  
- **Source URL:** https://arxiv.org/abs/2603.29914  
- **Reference count:** 26  
- **Primary result:** Gradient projection against an adversarial label predictor mitigates label leakage from task scarcity, boosting within-dataset transfer AUROC by +0.145 on average, but harms cross-dataset transfer.

## Executive Summary
Task scarcity—limited supervision from few prediction targets—in relational deep learning causes shared representations to encode task‑specific shortcuts that degrade transfer performance even within the same database schema, a phenomenon the authors call *label leakage*. They introduce a sample‑wise gradient projection method applied to the learnable relational backbone of the K‑Space architecture. The intervention removes label‑predictive components from representation updates by projecting out gradients aligned with those of an adversarial label predictor. On the RelBench benchmark, this yields large gains for within‑dataset transfer (+0.145 AUROC) and often recovers near single‑task performance. However, the same method fails to improve—and may slightly hurt—cross‑dataset transfer, indicating that the failure mechanisms in these two settings are fundamentally distinct. The work underscores the need to address task‑induced leakage in multi‑task relational learning and provides a targeted, modular approach for its suppression.

## Method Summary
The study uses the K‑Space architecture, which comprises a frozen TabICL tabular encoder that converts raw table rows into initial node embeddings, a learnable relational convolutional core (stacked SMPNN‑based heterogeneous blocks performing directed message passing), and a frozen in‑context learning (ICL) predictor head that consumes the core’s outputs and a support set to make predictions. To mitigate label leakage, a trainable adversarial head is added to predict the task label directly from the core’s intermediate representation \(z\). During training, for each sample the gradient of the main ICL loss \(\nabla_z \ell_{\text{ICL}}\) and the adversarial loss \(\nabla_z \ell_{\text{adv}}\) are computed. When the two gradients are positively aligned, the component of \(\nabla_z \ell_{\text{ICL}}\) along \(\nabla_z \ell_{\text{adv}}\) is subtracted (sample‑wise projection). The transformed gradients are averaged and backpropagated through only the backbone, while the adversarial head updates normally. This projection removes directions in the representation that are useful for predicting the current task’s label, thereby suppressing the encoding of task‑specific shortcuts and encouraging more transferable relational features. The method is evaluated across single‑task (ST), within‑dataset (WD), cross‑dataset (CD), and all‑task (ALL) settings on RelBench.

## Key Results
- Within‑dataset transfer improves dramatically with gradient projection: average AUROC rises by +0.145 over the baseline, often matching single‑task performance.  
- Cross‑dataset transfer shows no benefit and a slight performance drop (average AUROC change –0.067), suggesting different failure modes.  
- The baseline model (without projection) exhibits strong single‑task accuracy but severe within‑dataset transfer collapse (near chance), confirming the presence of label leakage due to task scarcity.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Task scarcity (few distinct prediction targets) enables representations to encode task‑specific shortcuts (label leakage), which degrade transfer performance even within the same database schema.  
- **Mechanism:** During training on a single or small set of tasks, the shared relational representation backbone optimizes for the immediate loss without conflicting objectives. This allows it to learn features that are spuriously predictive of the training labels (e.g., database‑specific artifacts or statistical noise) but are not causally or relationally meaningful for other tasks.  
- **Core assumption:** The frozen pretrained encoder and ICL head isolate the relational message‑passing core as the sole locus where leakage can be learned and encoded.  
- **Evidence anchors:**
  - [abstract] Explicitly states: “This task scarcity causes learned representations to encode task‑specific shortcuts that degrade transfer even within the same schema, a problem we call label leakage.”
  - [section 1] “When supervision comes from a single task, learned representations are free to encode any feature that predicts the label, including task‑specific shortcuts that do not generalize… With abundant task diversity, conflicting gradients from different objectives would suppress such shortcuts.”
  - [corpus] Weak direct evidence. Corpus neighbors discuss label leakage (e.g., in split learning) and label scarcity, but not the specific mechanism of *task* scarcity causing *relational* shortcut learning.  
- **Break condition:** If task diversity during training is sufficiently high (many distinct, conflicting objectives), the mechanism of leakage via shortcut learning should be suppressed, reducing the performance gap between base and adversarial models in within‑dataset transfer.

### Mechanism 2
- **Claim:** Sample‑wise gradient projection against an adversarial label‑prediction gradient removes label‑predictive components from the shared representation’s update, suppressing leakage.  
- **Mechanism:** For each sample, the gradient of the main ICL loss (\(\nabla \ell_{\text{ICL}}\)) with respect to the shared representation \(h\) is projected. Any component aligned with the gradient of an adversarial head (\(\nabla \ell_{\text{adv}}\)) trained to predict the label from \(h\) is subtracted. This operation is intended to remove directions in \(h\) that are useful for predicting the *current* task’s label, forcing the backbone to learn features less contaminated by task‑specific signals.  
- **Core assumption:** The adversarial head’s gradient accurately identifies directions in the representation space that are purely label‑predictive for the training task (i.e., the leakage). The projection is sample‑wise to handle per‑instance variations.  
- **Evidence anchors:**
  - [section 3] “We introduce a gradient projection method that removes label‑predictive directions from representation updates… we compute per‑query gradients w.r.t. z and remove components of \(\nabla_z \ell_{\text{main}}\) that align with \(\nabla_z \ell_{\text{adv}}\) via sample‑wise projection.”
  - [figure 2] Geometrically illustrates the projection: \(\tilde{\nabla}_h \ell_{\text{ICL}}(x_i) = \nabla_h \ell_{\text{ICL}}(x_i) - \alpha \nabla_h \ell_{\text{adv}}(x_i)\) where \(\alpha\) is the projection coefficient.
  - [corpus] Weak direct evidence. The method is inspired by adversarial training (e.g., DANN) and Muon optimizer, but the specific sample‑wise projection against a label‑predictive adversary for leakage suppression is novel to this work.  
- **Break condition:** If the adversarial head fails to learn a gradient that cleanly isolates label‑predictive directions (e.g., if it also learns general relational features, or if leakage is entangled with useful signals), the projection could remove useful information, harming performance even in within‑dataset transfer.

### Mechanism 3
- **Claim:** The failure mechanisms in within‑dataset transfer (leakage‑dominated) and cross‑dataset transfer (schema/domain mismatch‑dominated) are distinct; thus, a method targeting label leakage benefits the former but not the latter.  
- **Mechanism:** Within‑dataset transfer failure is primarily due to the backbone encoding non‑transferable, task‑specific shortcuts from the source task. Removing these via projection recovers performance. Cross‑dataset transfer failure involves more fundamental mismatches: different entity types, relation schemas, and data distributions. Projection may remove features that, while predictive of the source label, are coincidentally useful for cross‑schema generalization, or it may simply reduce the overall optimization signal without addressing the core domain shift problem.  
- **Core assumption:** The K‑Space architecture (frozen encoder/core) can learn *some* cross‑schema transferable features in the base case, but these are insufficient; leakage suppression does not enhance them and may prune them.  
- **Evidence anchors:**
  - [section 5] Table 1: Avg. AUROC for WD: Base (0.486) → Adv. (0.631, +0.145). Avg. CD: Base (0.611) → Adv. (0.544, –0.067).
  - [section 6] “Within‑dataset and cross‑dataset transfer fail differently. The former is dominated by task‑specific leakage, while the latter likely involves schema and domain mismatch that our method does not address.”
  - [corpus] No direct evidence; this is an inferred distinction from the paper’s experimental analysis.  
- **Break condition:** If cross‑dataset transfer failure were *also* primarily due to label leakage (e.g., if schemas were identical and only tasks differed), then gradient projection should improve CD performance similarly to WD. The observed harm suggests other factors dominate.

## Foundational Learning
### Relational Deep Learning (RDL)
**Why needed:** The entire study operates within the RDL paradigm, which transforms multi‑table relational databases into heterogeneous graphs. This structural representation is the substrate for message passing and the source of the “relational” in relational transfer learning. Understanding RDL is necessary to grasp why task scarcity occurs (few prediction targets per graph schema) and how K‑Space processes this structure.  
**Quick check:** How does converting a multi‑table database into a heterogeneous graph create a “task scarcity” problem distinct from standard graph node classification?

### Frozen Pretrained Components & Modularity
**Why needed:** The K‑Space architecture deliberately freezes the tabular encoder (TabICL) and the ICL predictor head. This design choice isolates the relational convolution core as the only trainable component, making it the exclusive potential source of label leakage. It also imposes constraints that explain K‑Space’s lower single‑task performance vs. RelGT.  
**Quick check:** If the encoder and predictor are frozen, what specific component is responsible for learning the shared representation, and why does this design help isolate the phenomenon of label leakage?

### Gradient Projection for Representation Purification
**Why needed:** This is the core intervention. It’s a specific technique to manipulate learning dynamics in the representation space of the backbone. Understanding it requires knowing that we compute two gradients at the representation layer: one for the main task, one for an adversarial label predictor. Their alignment dictates the intervention.  
**Quick check:** In the per‑sample gradient projection formula \(\tilde{\nabla} = \nabla_{\text{main}} - \alpha \nabla_{\text{adv}}\), what does a positive \(\alpha\) indicate about the relationship between the two gradient vectors, and why would subtracting it remove “label‑predictive” information?

## Architecture Onboarding

**Component Map:**
1. Frozen Tabular Encoder (TabICL): Takes raw table rows (with metadata), outputs initial node embeddings. Input: row features + time + RWPE. Output: fixed‑dimensional vector per row.  
2. Input Projection & RoPE: Projects concatenated features (encoder output + time + RWPE) to model width. Injects table‑type information via Rotary Position Embeddings.  
3. Relational Convolutional Core (Stack of N Hetero Blocks): The learnable backbone. Implements directed, relation‑type‑aware message passing (SMPNN‑based). Each block aggregates incoming/outgoing messages per relation type with shared weights and applies a residual update. Key: linear edge complexity.  
4. Output Projection: Processes the final node representations from the core.  
5. Dual Heads (per mini‑batch):  
   - ICL Predictor Head (Frozen): Consumes a set of (support embedding, label) pairs and query embeddings from the core’s output to make in‑context predictions.  
   - Adversarial Head (Trainable, optional): Simple MLP that takes the *same* core output representation \(z\) and tries to predict the label directly. Used only to compute \(\nabla_z \ell_{\text{adv}}\) for gradient projection.

**Critical Path:**  
Raw Row Data → TabICL Encoder → [Time Features + RWPE] → Input Proj + RoPE → [Hetero Block x N] → Output Proj → Split into (z_adv, z_icl) → Adversarial Head (ℓ_adv) & ICL Head (ℓ_ICL).

**Design Tradeoffs:**
- *Frozen encoder/predictor vs. performance:* Sacrifices peak single‑task accuracy (vs. end‑to‑end trainable models like RelGT) for isolation and modular analysis of the backbone.
- *Sample‑wise projection vs. batch‑wise:* More precise per‑instance leakage removal but computationally more expensive than a single batch‑level projection. Requires careful implementation to avoid distributed training issues.
- *Simple convolutional core vs. transformers:* K‑Space uses linear‑complexity SMPNN blocks instead of full attention. This makes training on large relational graphs feasible but may limit capacity for complex long‑range relational reasoning, potentially interacting with leakage effects.

**Failure Signatures:**
- **Within‑dataset (WD) collapse (Base model):** AUROC near 0.5 (chance) despite good ST performance. Primary signature of task‑scarcity‑induced label leakage.
- **Cross‑dataset (CD) degradation (Adv. model):** Performance drop compared to Base model when using gradient projection. Signature that projected‑out directions included features useful for cross‑schema generalization, or that the method harms optimization in low‑signal transfer settings.
- **ALL‑task interference:** Varying per‑task performance under multi‑task training, indicating negative transfer; not a direct failure of the projection method but of the multi‑task regime itself.

**First 3 Experiments:**
1. **Establish baseline leakage:** Train and evaluate K‑Space *Base* (no adversarial head) in ST and WD settings on RelBench. Expect strong ST, weak WD (near‑chance). This confirms the label leakage phenomenon.
2. **Test intervention:** Replicate experiment 1 with K‑Space *Adv.* (with gradient projection). Expect similar ST (slightly lower) and *significantly improved* WD. This tests if projection suppresses leakage.
3. **Test transfer boundary:** Evaluate both model variants in the CD setting. Expect Base > Adv. (or Adv. no better). This tests if the failure mechanisms differ and if projection is specifically beneficial for within‑schema transfer.

## Open Questions the Paper Calls Out
1. **What combination of task count, task diversity, and dataset size determines when task scarcity causes harmful label leakage?**  
   Basis: “understanding when task scarcity harms relational representations remains open.” (Discussion).  
   Why unresolved: The paper shows leakage occurs under scarcity but does not map the boundary conditions; e.g., how many tasks are needed to avoid leakage, or how task similarity interacts with scarcity is unknown.  
   Evidence needed: Systematic experiments on RelBench (or similar) varying these factors, measuring the AUROC drop in within‑dataset transfer relative to single‑task performance to identify thresholds.

2. **Why does gradient projection not improve cross‑dataset transfer, and can it be modified to do so?**  
   Basis: “cross‑dataset transfer remains weak (requiring methods beyond gradient projection)” (Discussion).  
   Why unresolved: The distinct failure mechanisms between within‑ and cross‑dataset transfer are hypothesized but not identified; it is unclear whether projection discards useful cross‑domain features or if other factors dominate.  
   Evidence needed: Analyze the gradient directions removed by projection (e.g., via linear probing) to test if they contain domain‑invariant information; develop alternative projection objectives that preserve cross‑dataset utility and evaluate on CD tasks.

3. **Does the leakage suppression approach work for regression tasks, not just binary classification?**  
   Basis: “results are classification‑only (a regression head such as TabPFN Hollmann et al. (2022) could be substituted)” (Discussion).  
   Why unresolved: Regression losses differ from classification losses, potentially altering gradient geometry and the effect of projection; its effectiveness for regression is unknown.  
   Evidence needed: Replace the ICL predictor with a regression head (e.g., TabPFN) and replicate the experiments on regression tasks from RelBench, comparing ST, WD, and CD performance with and without projection.

4. **Are the findings on task scarcity and gradient projection generalizable beyond RelBench to other relational databases?**  
   Basis: “we only evaluate on RelBench” (Discussion).  
   Why unresolved: RelBench’s limited set of schemas and domains may not represent all relational settings; external validity is not established.  
   Evidence needed: Apply the same experimental protocol to additional relational benchmarks or real‑world databases, checking whether label leakage occurs under task scarcity and whether gradient projection consistently improves within‑dataset transfer.

## Limitations
- Pretrained TabICL encoder and ICL predictor specifics (architecture, checkpoints, preprocessing) are not publicly specified, blocking exact replication.  
- Critical training hyperparameters (learning rate, batch size, projection coefficient \(\alpha\)) are missing; optimal values may significantly affect results.  
- RelBench data splits, temporal handling, and graph construction details (edge directions, sampling) are assumed but unreported, risking evaluation mismatches.

## Next Checks
1. **Task diversity ablation:** Train Base model on varying numbers of tasks (1, 2, 4, 8) within a single dataset. A monotonic rise in within‑dataset AUROC would confirm leakage scales with scarcity.  
2. **Gradient alignment analysis:** Compute per‑sample cosine similarity between \(\nabla_{\text{main}}\) and \(\nabla_{\text{adv}}\) before projection. A positive correlation between high alignment and larger gains from projection would validate that projection targets leakage directions.  
3. **Schema‑matched cross‑dataset test:** Construct a cross‑dataset setting with identical schemas but distinct data distributions (e.g., temporal splits). If gradient projection still harms performance, schema mismatch is not the sole failure factor; if it helps, leakage may also hinder cross‑dataset transfer.
