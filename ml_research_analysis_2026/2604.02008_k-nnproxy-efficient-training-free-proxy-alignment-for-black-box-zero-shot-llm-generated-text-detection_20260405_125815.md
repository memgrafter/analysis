# $k$NNProxy: Efficient Training-Free Proxy Alignment for Black-Box Zero-Shot LLM-Generated Text Detection

## Quick Facts
- **arXiv ID:** 2604.02008  
- **Source URL:** https://arxiv.org/abs/2604.02008  
- **Reference count:** 40  
- **Primary result:** Achieves average AUROC 0.99 on Mix8 (8 proprietary LLMs), a 6.45% gain over prior SOTA alignment methods.

## Executive Summary
kNNProxy tackles zero‑shot detection of LLM‑generated text in a black‑box setting, where a fixed proxy LLM often misaligns with the unknown source distribution. It repurposes kNN language model retrieval as a training‑free domain adapter: a lightweight datastore built from a source‑reflective corpus provides nearest‑neighbor token evidence that is interpolated with the proxy’s own next‑token distribution, aligning them without fine‑tuning or repeated API calls. For domain shift, MoP adds a topic router to select domain‑specific datastores. Theoretical analysis yields a corpus‑size error bound and motivates token‑adaptive hyperparameters. The method attains near‑perfect detection (average AUROC 0.99 on Mix8, 0.999 AUROC in‑domain on DetectRL) and substantially outperforms existing alignment techniques. These results demonstrate that non‑parametric retrieval can effectively bridge the gap between proxy and source LLMs.

## Method Summary
kNNProxy operates in two phases. Offline, it constructs a datastore by sliding a context window over a corpus of LLM‑generated texts; each context is encoded with the proxy LLM’s hidden state (key) and the succeeding token is stored (value). The datastore is indexed for fast nearest‑neighbor search (e.g., FAISS). During inference, for each token position the proxy produces a next‑token distribution. The current context is encoded to a query and the *k* nearest neighbors are retrieved. From these, a distance‑weighted distribution over next tokens (temperature‑scaled) is computed. This retrieval distribution is linearly interpolated with the proxy distribution using a token‑adaptive interpolation weight *λ*. The resulting aligned distribution is used by a zero‑shot detector (e.g., Binoculars) after per‑token log‑likelihood clipping and aggregation. MoP extends this by maintaining multiple domain‑specific datastores and a router based on sentence embeddings; the router selects the appropriate expert datastore per input to improve out‑of‑domain robustness.

## Key Results
- Average AUROC **0.99** on Mix8 (8 proprietary LLMs), a **6.45%** improvement over prior SOTA alignment methods.
- On DetectRL, Binoculars+kNNProxy achieves **0.999 AUROC** in‑domain and improves OOD F1 by **17–23%**; MoP further lifts OOD F1 to **0.911**.
- Closed‑set source attribution accuracy reaches **0.84**.

## Why This Works (Mechanism)

### Mechanism 1: Retrieval‑based Proxy Alignment
- **Claim:** kNNProxy aligns a fixed proxy LLM’s output distribution to the unknown source LLM by interpolating with a kNN‑induced distribution from a source‑reflective datastore, eliminating the need for fine‑tuning or repeated API calls.
- **Mechanism:** Offline, construct a datastore from a corpus generated by (or reflective of) the source LLM: slide a window over texts, encode each context with the proxy’s hidden state to get a key, and store the next token as the value. During inference, for each token position, retrieve the *k* nearest neighbors (by L₂ distance in representation space) to the current query context, compute a distance‑weighted distribution over next tokens (using temperature *τ*), and linearly interpolate this kNN distribution with the proxy’s own next‑token distribution using interpolation weight *λ*. The interpolation can be token‑adaptive based on local retrieval quality.
- **Core assumption:** The source LLM’s next‑token distribution is locally smooth in the proxy’s representation space (i.e., nearby contexts yield similar distributions), and the datastore provides accurate samples from the source distribution for contexts similar to the query. Additionally, the proxy’s representation space is semantically meaningful for retrieval.
- **Evidence anchors:** [abstract] states the approach; [Sec. III.A] details datastore construction, retrieval‑induced distribution, and alignment; corpus includes related works but no direct validation.
- **Break condition:** If the query context is extremely far from all datastore entries (large effective radius *r*<sub>eff</sub>) or the retrieved neighbors are highly concentrated (small *k*<sub>eff</sub>), the error bound grows and alignment may fail. Also, if the source distribution is not locally smooth, the bias term *L·r*<sub>eff</sub> becomes large.

### Mechanism 2: Domain‑Specific Routing (MoP)
- **Claim:** MoP improves out‑of‑domain robustness by routing each input to a domain‑specific kNNProxy expert, ensuring retrieval from a topically consistent datastore and avoiding misleading evidence from mismatched domains.
- **Mechanism:** Build multiple domain‑specific datastores from corpora partitioned by topic (or source LLM family). Create a separate routing datastore: for each training sentence, store its sentence embedding (from a pre‑trained encoder) and its domain label. At inference, compute the input’s sentence embedding, retrieve its *k*<sub>r</sub> nearest neighbors from the routing datastore, and take a majority vote to assign a domain. Then use the expert datastore of that domain for the usual kNNProxy alignment.
- **Core assumption:** Domain boundaries correlate with distinct shifts in the source LLM’s token preferences, and sentence embeddings can reliably predict the relevant domain based on topical similarity. The router’s kNN vote approximates the true domain distribution.
- **Evidence anchors:** [abstract] mentions MoP; [Sec. III.B] details routing datastore and expert selection.
- **Break condition:** If the sentence embedding model fails to capture topical features, or if a test sample belongs to a domain not represented in any expert, the router may select an inappropriate expert, harming detection.

### Mechanism 3: Token‑Adaptive Hyperparameters
- **Claim:** Token‑wise adaptive selection of neighbor size *k*, temperature *τ*, and interpolation weight *λ* reduces the theoretical approximation error of kNNProxy and improves reliability without costly global hyperparameter sweeps.
- **Mechanism:** For each token query, compute surrogates for the bias‑variance terms from Thm. 1: effective radius *r*<sub>eff</sub> and effective neighborhood size *k*<sub>eff</sub>. Form a combined objective *U(k,τ) = c·r*<sub>eff</sub> + 1/√*k*<sub>eff</sub> (with calibration *c*). Choose (*k*,*τ*) minimizing *U* over a candidate set. Then set *λ = σ(U* – median{U* over all tokens in the text})*, where σ is sigmoid. Tokens with below‑median error receive smaller *λ* (more trust in retrieval), others rely more on the proxy.
- **Core assumption:** The theoretical error bound (Thm. 1) accurately reflects the true discrepancy between source and kNN distributions, and the computed *r*<sub>eff</sub> and *k*<sub>eff</sub> are reliable estimates of bias and variance. The median normalization provides a stable within‑text reference.
- **Evidence anchors:** [Sec. IV.A] derives the L₁ error bound; [Sec. IV.B] defines *U* and adaptive selection.
- **Break condition:** If the Lipschitz constant *L* is large or vocabulary size *V* huge, bound terms may dominate; if datastore too small, *k*<sub>eff</sub> near 1 or *r*<sub>eff</sub> large; incorrect *r*<sub>eff</sub> estimation leads to poor choices.

## Architecture Onboarding

- **Component map:**  
  Offline: Datastore builder → FAISS index; Domain partitioner; Router datastore builder → routing index.  
  Online: Input → (MoP router?) → expert datastore selection → (per token: Proxy → query encoding → kNN retrieval → adaptive selector → interpolation) → aggregation (clipping, mean) → final score.

- **Critical path:**  
  1. Input text → prepend BOS.  
  2. If MoP: compute sentence embedding, query routing datastore, get domain label.  
  3. For *i* = 1 to *T*:  
     a. Get proxy next‑token distribution π<sub>prx</sub><sup>(i)</sup>.  
     b. Encode prefix to query *q*<sub>i</sub>.  
     c. Retrieve *k*<sub>max</sub> nearest neighbors from expert datastore.  
     d. If adaptive: for candidate (*k*,*τ*) pairs, compute *U* on truncated neighbor list; pick (*k*<sup>*</sup>,*τ*<sup>*</sup>); compute *U*<sup>*</sup> and *λ*<sup>*</sup> via sigmoid vs. median.  
     e. Compute π<sub>knn</sub><sup>(i)</sup> from retrieved neighbors (distance weights with *τ*<sup>*</sup>).  
     f. Align: ˆπ<sup>(i)</sup> = *λ*<sup>*</sup> π<sub>prx</sub><sup>(i)</sup> + (1 – *λ*<sup>*</sup>) π<sub>knn</sub><sup>(i)</sup>.  
  4. Aggregate: ˜ℓ<sub>i</sub> = max(log ˆπ<sup>(i)</sup>(x<sub>i</sub>), *γ*); mean of ˜ℓ<sub>i</sub> gives final score.  
  5. Threshold decision.

- **Design tradeoffs:**  
  - **Datastore size vs. latency:** Larger corpora improve coverage but increase memory and search time; fixed‑budget querying balances cost.  
  - **Neighbor count *k*:** Larger *k* reduces variance but may include distant, irrelevant contexts (higher bias). Adaptive *k* mitigates.  
  - **Temperature *τ*:** Low *τ* focuses on nearest neighbors (high variance, low bias); high *τ* smooths more (lower variance, higher bias).  
  - **Interpolation *λ*:** Small *λ* leans on retrieval (good if datastore high‑quality), large *λ* on proxy (robust if retrieval noisy). Adaptive per‑token is superior.  
  - **MoP vs. single:** MoP enhances OOD robustness at the cost of multiple datastores and a router; router accuracy is critical.  
  - **Representation dimensionality:** Lower‑dimensional hidden states reduce memory but may lose semantic information.

- **Failure signatures:**  
  - **High OOD error:** Sudden AUROC/F1 drop on topics or LLMs not well‑represented in the datastore(s).  
  - **Extreme token log‑likelihoods:** Many tokens with very low (or very high) aligned log‑likelihoods after clipping indicate severe misalignment.  
  - **Router confusion (MoP):** Router often selects wrong expert; expected accuracy >0.9 in‑domain but may drop OOD.  
  - **Sparse retrieval:** Effective radius *r*<sub>eff</sub> consistently large, or effective *k*<sub>eff</sub> ≈ 1; suggests datastore too small or poor representation space.  
  - **Memory pressure:** FAISS index too large for GPU memory; need to reduce dimensions or use CPU search.

- **First 3 experiments:**  
  1. **Mix8 benchmark:** Compare kNNProxy (with Falcon‑7B‑Instruct) against fixed‑proxy detectors (Fast‑DetectGPT, Binoculars) and alignment methods (DALD, Glimpse) on 8 proprietary LLMs across 4 topics. Measure AUROC; expect average 0.990, ~6.45% gain over prior SOTA.  
  2. **DetectRL benchmark:** Evaluate in‑domain (train/test same topic/LLM) and out‑of‑domain (cross‑topic, cross‑LLM, including attacks) with three zero‑shot detectors (Likelihood, Fast‑DetectGPT, Binoculars) + kNNProxy and + MoP. Report AUROC/F1; expect near‑ceiling in‑domain (0.999 AUROC) and significant OOD F1 gains (17–23% over baselines).  
  3. **Ablation studies:** Vary key hyperparameters (*τ*, *k*, *λ*, clip value *γ*, corpus size *N*) with and without adaptive schemes. Show adaptive strategies consistently match or beat best fixed settings; also ablate corpus source LLM, prompt template, and base proxy LLM choices.

## Open Questions the Paper Calls Out
1. **Lipschitz smoothness assumption:** The theoretical analysis assumes the source next‑token distribution is L1‑Lipschitz in the proxy representation; its validity across diverse black‑box LLMs and domains is unknown and directly impacts the error bound.
2. **Source‑reflective corpus construction:** In a black‑box setting, obtaining a datastore that accurately reflects the unknown source distribution is challenging; mismatches can severely degrade detection.
3. **Adversarial robustness:** The kNN retrieval mechanism may be vulnerable to targeted attacks that manipulate inputs to retrieve irrelevant neighbors; the paper does not analyze this threat model.
4. **Unsupervised routing:** MoP currently requires labeled topic data and a fixed sentence embedding model; an unsupervised, embedding‑agnostic router would increase practicality.

## Limitations
- The offline datastore must be source‑reflective; constructing it for an unknown black‑box LLM is non‑trivial and misalignment harms performance.
- Token‑adaptive hyperparameter selection lacks concrete implementation details (candidate sets, calibration constant), hindering reproducibility.
- Theoretical error bound relies on strong smoothness assumptions that may not hold for real LLMs; empirical validation of the bound is absent.
