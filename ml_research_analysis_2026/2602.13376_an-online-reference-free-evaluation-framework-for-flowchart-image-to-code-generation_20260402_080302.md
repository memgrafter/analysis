# An Online Reference-Free Evaluation Framework for Flowchart Image-to-Code Generation

## Quick Facts
- **arXiv ID:** 2602.13376  
- **Source URL:** https://arxiv.org/abs/2602.13376  
- **Reference count:** 21  
- **Primary result:** A reference-free framework using OCR-based recall and visual entailment precision to evaluate flowchart-to-code generation without ground-truth code, showing strong correlation (r > 0.91) with ground-truth metrics on FlowVQA.

## Executive Summary
This paper tackles the challenge of automatically evaluating the quality of flowchart image-to-code generation in production environments where reference (ground-truth) code is unavailable. The proposed solution is a fully automated, reference-free evaluation framework that computes two complementary metrics: **Recall_OCR**, which measures how much text content from the flowchart image is covered in the generated code using OCR and string matching; and **Precision_VE**, which uses a Visual Entailment (VE) model to verify that each code-declared element is visually present in the image, detecting hallucinations. Their harmonic mean yields an F1 score (F1_OCR-VE). Validated on the FlowVQA dataset, all metrics exhibit very high Pearson correlation (r ≥ 0.91) with ground-truth quality metrics, demonstrating the framework's potential as a reliable proxy for human or reference-based evaluation. The approach is model-agnostic, operates at inference time, and provides interpretable error signals.

## Method Summary
The framework operates in two parallel branches on a given flowchart image *I* and generated code *C*. The **Recall_OCR** branch uses an OCR engine to extract all text strings from *I*. These strings are matched (with fuzzy string matching) against text identifiers present in *C* (e.g., node labels, condition texts). The ratio of matched to total extracted text provides a recall estimate of content coverage. The **Precision_VE** branch iterates over each element (node, edge label) declared in *C* and queries a Visual Entailment (VE) model with a prompt asking whether the specific element's text/label is visible in *I*. The proportion of elements answered "yes" yields a precision estimate, penalizing hallucinations. The final **F1_OCR-VE** is the harmonic mean of Recall_OCR and Precision_VE. The system is designed to be plug-and-play: any OCR engine and any VE-capable vision-language model (VLM) can be substituted.

## Key Results
- Recall_OCR (with Gemini 1.5 Pro) achieves Pearson correlation *r* = 0.967 with ground-truth recall on FlowVQA.
- Precision_VE (with Gemini 2.5 Pro) achieves *r* = 0.910 with ground-truth precision.
- The composite F1_OCR-VE score achieves *r* = 0.939 with ground-truth F1.
- The framework produces instance-level diagnostics (e.g., which text was missed, which code element was hallucinated).

## Why This Works (Mechanism)
The framework decouples evaluation into two orthogonal error modes: **omission** (missing elements) and **hallucination** (spurious elements). Recall_OCR directly approximates omission errors by checking if visible text in the image appears in the code. This is effective because flowcharts are text-centric; node and edge labels are primary carriers of meaning. Precision_VE directly approximates hallucination errors by verifying each code-declared element against the visual input, catching cases where the generator invents nodes/edges not in the image. The harmonic mean balances these two failure modes, analogous to the standard F1 metric in retrieval. High correlation with ground-truth suggests that in flowcharts, these surface-level textmatches are strong proxies for structural and functional correctness, likely because correct code generation fundamentally requires accurate transcription of the diagram's labeled components.

## Foundational Learning
- **Optical Character Recognition (OCR):** Extracts raw text from the image. *Why needed:* Provides the set of "true" text elements to compare against code. *Quick check:* Test OCR accuracy on a sample of flowchart images; if character error rate > 5%, Recall_OCR will be noisy.
- **Visual Entailment (VE):** A VLM task determining if a textual hypothesis is entailed by an image. *Why needed:* Serves as a binary verifier for presence of code-declared elements in the image. *Quick check:* Manually review VE predictions on a validation set; if false positive rate > 20%, Precision_VE will be inflated.
- **Harmonic Mean (F1):** Aggregates recall and precision. *Why needed:* Provides a single, balanced score that penalizes extreme imbalance between omission and hallucination. *Quick check:* Compare with arithmetic mean; large discrepancies indicate one metric dominates the score.
- **Pearson Correlation:** Measures linear agreement with ground-truth metrics. *Why needed:* Validates that the reference-free scores track what a reference-based metric would output. *Quick check:* Ensure correlation is statistically significant (p < 0.05) on the validation set.
- **Fuzzy String Matching:** Allows for minor OCR errors (e.g., "node1" vs "nodeI"). *Why needed:* OCR output is imperfect; exact matching would undercount recall. *Quick check:* Tune matching threshold (e.g., edit distance) on a held-out set to maximize correlation.
- **Model-Agnostic Design:** The framework defines interfaces (text extraction, element verification) rather than fixing models. *Why needed:* Allows adaptation to future, better OCR/VE models without redesigning the metric. *Quick check:* Swap one component (e.g., use Tesseract instead of Google Cloud OCR) and re-run correlation; degradation should be minimal if the new model is competent.

## Architecture Onboarding
**Component Map**  
Input Flowchart Image -> [OCR Engine -> Extracted Text Set] -> Recall_OCR Calculator  
Input Flowchart Image + Generated Code -> [Code Parser -> Element List] -> [VE Model (per element)] -> Precision_VE Calculator  
Recall_OCR + Precision_VE -> Harmonic Mean -> F1_OCR-VE Score + Diagnostics (missing text, hallucinated elements)

**Critical Path**  
1. Image ingestion and OCR (serial dependency for Recall_OCR).  
2. Code parsing to extract target elements (serial dependency for Precision_VE).  
3. Parallel invocation of VE model for each element (can be batched).  
4. Final score aggregation.

**Design Tradeoffs**  
- *OCR vs. VE cost:* OCR is a one-time cost; VE scales with number of code elements (more nodes/edges = more VE calls).  
- *VE model selection:* Larger VLMs (Gemini 2.5 Pro) reduce false negatives but increase latency/cost; smaller models may increase false positives.  
- *Prompt design for VE:* More detailed prompts (asking about shape/color) could improve robustness but may confuse the VLM or increase cost.

**Failure Signatures**  
- *Recall_OCR unexpectedly low:* Likely OCR failure on low-contrast, handwritten, or stylized text; or code uses synonyms not captured by fuzzy matching.  
- *Precision_VE unusually high:* VE model likely answering "yes" indiscriminately (high false positive rate); prompt may be too lenient.  
- *Large gap between Recall_OCR and Precision_VE:* Indicates asymmetric error mode (e.g., code misses many labels but does not hallucinate extra nodes, or vice versa).

**First Experiments**  
1. **OCR Robustness Stress Test:** Apply synthetic degradations (blur, rotation, noise) to FlowVQA images and measure variance in Recall_OCR and F1_OCR-VE.  
2. **VE Model Swap:** Replace Gemini 2.5 Pro with open-source VLMs (e.g., LLaVA, CogVLM) and compare Precision_VE correlation with ground-truth and false positive rates.  
3. **Weight Sensitivity:** Replace harmonic mean with weighted Fβ (e.g., F2 favoring recall) and re-calculate correlation with ground-truth; test if optimizing β on a held-out set yields better alignment.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the Recall_OCR metric be extended to reliably capture unlabeled edges and their connections, given that current methods for edge detection are not yet scalable or robust?
- **Basis in paper:** [explicit] The authors state that "Recall_OCR effectively captures text-labeled nodes but cannot handle unlabeled edges, leaving edge recall unaddressed" and note that "reasoning over edges, arrows, and connections remains an open problem in computer vision and vision-language model research." They cite preliminary heuristics from Omasa et al. (2025) but note lack of large-scale validation.
- **Why unresolved:** Edge detection is fundamentally more challenging than text extraction, requiring spatial reasoning about shapes, arrows, and node relationships without clear textual anchors.
- **What evidence would resolve it:** A validated, scalable edge detection component (e.g., via object detection or graph parsing) that can be integrated into the framework and shown to correlate with ground-truth edge-level metrics on diverse flowchart datasets.

### Open Question 2
- **Question:** Does the framework maintain strong correlation with ground-truth metrics when evaluated on diverse flowchart datasets beyond FlowVQA, such as FlowLearn, which may have different styles, noise levels, or domain conventions?
- **Basis in paper:** [explicit] The authors explicitly identify this as a limitation: "Moreover, the framework can be further validated against ground-truth in other flowchart datasets, such as FlowLearn (Pan et al., 2024)."
- **Why unresolved:** Validation was performed on a single dataset (FlowVQA), which may not capture the full diversity of production inputs (e.g., hand-drawn sketches, scanned documents, varied diagramming languages).
- **What evidence would resolve it:** Replication of the validation protocol (Pearson/Kendall correlation, RMSE/MAE) on multiple benchmark datasets, showing consistently high agreement across varied data distributions.

### Open Question 3
- **Question:** Would a weighted or learned combination of Recall_OCR and Precision_VE (instead of the fixed harmonic mean) better align with human judgment or ground-truth F1, especially for flowcharts where node and edge importance varies?
- **Basis in paper:** [inferred] The paper uses the harmonic mean (F1_OCR-VE) without exploring alternative aggregations. This equal-weighting assumes node coverage and hallucination detection are equally critical, which may not hold for all use cases (e.g., some applications prioritize precision over recall).
- **Why unresolved:** The harmonic mean is a standard F1 formulation but may not optimally reflect user-perceived quality if the cost of missing vs. hallucinated elements is asymmetric.
- **What evidence would resolve it:** Comparative studies measuring correlation with human evaluations or task-specific success metrics under different weighting schemes (e.g., β-F1, learned meta-metrics).

### Open Question 4
- **Question:** Can the Visual Entailment (VE) component be made more robust to subtle visual variations (e.g., iconography, color, layout) and less reliant on exact textual matching, to handle flowcharts with non-standard node representations or stylized text?
- **Basis in paper:** [inferred] The VE prompt emphasizes textual matching (e.g., "Check if the specific node text/label is visible") and tolerates minor string errors (tilde/quote confusion). Error analysis shows model-specific false positive/negative rates, suggesting sensitivity to visual nuances not fully captured by the current prompt design.
- **Why unresolved:** Current VE models may fail when nodes use symbols, abbreviations, or custom visuals not explicitly mentioned in the generated code, or when image quality degrades.
- **What evidence would resolve it:** Ablation studies with modified VE prompts (e.g., incorporating visual features, icon recognition) or fine-tuned VE models that show reduced error rates on heterogeneous flowchart images while maintaining correlation with ground-truth.

### Open Question 5
- **Question:** Is there a universal VE model (or model class) that consistently yields low false positive rates across different VLM generators (Qwen, Gemini, Claude, GPT), or does the optimal VE model depend on the generator's error profile?
- **Basis in paper:** [explicit] The authors find that "selecting a VE model with low FPR is particularly important" and that Gemini 2.5 Pro performed best. However, they test only commercial VLMs as VE models and note that "the worst-performing VE model (Gemini 1.5 Pro) suffers from both high false positive and false negative rates."
- **Why unresolved:** The interaction between the code-generating VLM and the VE model is not deeply analyzed. A VE model that works well for one generator's outputs might be suboptimal for another due to differing hallucination patterns.
- **What evidence would resolve it:** Cross-evaluation matrix showing which VE model pairs minimize FPR for each code-generating VLM, potentially revealing a need for generator-specific calibration or a more robust, architecture-agnostic VE approach.

## Limitations
- **Dataset specificity:** Validation solely on FlowVQA, which may not capture diverse real-world flowchart styles, complexity, or noise. Generalizability beyond this curated dataset is unproven.
- **OCR dependency:** Recall_OCR’s fidelity is bottlenecked by OCR accuracy. Performance on low-quality, complex layout, or handwritten flowcharts is unknown and likely degraded.
- **Metric alignment:** High correlation exists with synthetic ground-truth metrics on FlowVQA. Alignment with human judgment of "code quality" or functional correctness in production remains speculative.

## Confidence
- **Claim:** Metrics correlate strongly with ground-truth quality on FlowVQA. **Confidence:** High (empirical result reported).
- **Claim:** Framework is model-agnostic. **Confidence:** Medium (tested on multiple LLMs, but not exhaustive; VE/OCR backbones are fixed).
- **Claim:** Provides interpretable diagnostics. **Confidence:** Low (diagnostics are derived from component scores, but no user study confirms practical interpretability).
- **Claim:** Framework handles diverse flowchart types (hand-drawn, scanned, varied domains). **Confidence:** Low (only tested on one dataset).
- **Claim:** VE component is robust to visual variations and non-standard representations. **Confidence:** Low (prompt design is simple; error analysis shows sensitivity).

## Next Checks
