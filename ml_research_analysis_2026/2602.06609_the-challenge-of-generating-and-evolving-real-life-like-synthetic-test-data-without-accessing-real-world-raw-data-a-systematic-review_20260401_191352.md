# The challenge of generating and evolving real-life like synthetic test data without accessing real-world raw data -- a Systematic Review

## Quick Facts
- **arXiv ID:** 2602.06609
- **Source URL:** https://arxiv.org/abs/2602.06609
- **Reference count:** 30
- **Primary result:** From 1,013 publications, 37 relevant studies were identified; 9 partially satisfy generation (mostly rule-based), only 2 incorporate evolution, highlighting a significant research gap.

## Executive Summary
This systematic review addresses the challenge of generating realistic synthetic test data for decentralized e-Government systems without accessing sensitive real-world data, a constraint driven by privacy regulations like GDPR. A structured literature search across three databases identified 37 relevant studies after strict filtering. No single approach fully meets all criteria, particularly the ability to evolve data over time while preserving cross-entity relationships. While nine approaches partially support generation (primarily rule-based), only two publications—both from the same research group—incorporate evolution, using recurrent neural networks or a retrained domain-specific language. The findings reveal a substantial gap in methods for evolving synthetic test data without any real-data input.

## Method Summary
The review followed a systematic literature search protocol across three databases, initially retrieving 1,013 publications. Inclusion criteria required approaches that generate synthetic test data for e-Government contexts without using any real-world raw data and that consider decentralized system interoperability. After screening and full-text review, 37 studies were selected for synthesis. The analysis categorized approaches by generation technique (rule-based, ML-based, etc.) and evolution capability, assessing their adherence to the core constraints of no real-data access and support for temporal evolution in a multi-entity setting.

## Key Results
- Only 9 of 37 studies partially fulfilled the generation requirement, with the majority relying on rule-based methods using specifications like WSDL or UML/OCL.
- Merely 2 publications (from the same research group) addressed evolution, using RNNs or a DSL retrained on periodic production data samples.
- No approach simultaneously achieved generation without real data, evolution over time, and guaranteed cross-entity consistency for decentralized systems.

## Why This Works (Mechanism)
### Mechanism 1: Rule-Based Generation
Claim: Rule-based generation produces realistic synthetic test data without real-world data input by encoding domain knowledge and constraints.
Mechanism: Formal specifications (WSDL, UML/OCL, contracts) define valid data structures, relationships, and value distributions; a constraint solver or rule engine generates compliant instances.
Core assumption: Essential data characteristics and invariants can be fully captured and formalized by domain experts without observing actual distributions.
Evidence: 9 identified rule-based approaches; section 5.4.1 categorizes 13 rule-based studies using specification inputs.
Break condition: Rule set becomes too large/complex to maintain as domain logic evolves, or fails to capture subtle, undocumented statistical realities.

### Mechanism 2: Evolution via Retraining
Claim: Synthetic data evolution is simulated by periodically retraining a generative model on newly available production data.
Mechanism: Initial synthetic dataset generated; generative model (RNN or DSL) retrained at intervals on fresh production snapshots; entire corpus regenerated to incorporate latest patterns.
Core assumption: Periodic access to small, recent production samples is permissible for retraining only, structured to avoid raw data storage, thus navigating privacy rules.
Evidence: Only two publications (P66: RNNs trained on synthetic history; P43: DSL retrained quarterly on 100 days of production data).
Break condition: Legal/policy prohibits any production data access, or retraining frequency cannot keep pace with real-world change.

### Mechanism 3: Multi-Source Consistency via Centralized Specification
Claim: Decentralized system compatibility is achieved by generating all entity-specific datasets from a single shared model enforcing global identifiers.
Mechanism: Central specification (schema, constraints, shared seed) defines consistent identifiers (person IDs, case numbers) and relationships; generation for each entity is a constrained sub-task referencing the master.
Core assumption: All interoperability requirements and shared identifiers can be completely specified a priori in an authoritative model.
Evidence: Section 2 notes need for preserved identifiers; section 4.1 includes "relationships between data subject instances" in evolution definition; section 3 states other domains' solutions don't transfer.
Break condition: Shared identifiers/business rules are incomplete, unknown, or change non-coordinately across the network.

## Architecture Onboarding
- **Component map**: Domain Knowledge Encoder -> Constraint Solver/Generator Core -> Evolution Controller -> Consistency Manager -> Validation & metric module
- **Critical path**: Requirements -> Select/Encode Domain Model -> Generate Initial Corpus -> (Optional) Configure Evolution Rules/Retraining Schedule -> Generate/Update Datasets -> Validate Consistency & Realism -> Deploy to Test Environments
- **Design tradeoffs**:
  - Rule-based vs. ML-based: Rules offer transparency and no real-data need but struggle with complexity/realism; ML (GANs, LLMs) offers higher realism but typically requires real data for training.
  - Centralized vs. Distributed Generation: Centralized generator ensures consistency but conflicts with decentralized principles; distributed generators need a shared immutable specification source.
  - Evolution via Retraining vs. Simulation: Retraining on production data yields high fidelity but needs data access; simulation (e.g., RNNs of life events) avoids data access but may drift without calibration.
- **Failure signatures**:
  - Inconsistent identifiers: A person exists in health system data but not tax data, or with conflicting attributes.
  - Static decay: Test suites fail as business rules change and synthetic data isn't updated.
  - Unrealistic distributions: Generated data has uniform/random values where real data has Zipfian distributions, misleading performance tests.
- **First 3 experiments**:
  1. Constraint Coverage Test: For a rule-based approach (e.g., P28's UML/OCL solver), measure percentage of defined constraints satisfied in a generated sample; identify unsolved constraints.
  2. Cross-Entity Integrity Simulation: Generate datasets for two mock government entities using a shared identifier rule; attempt joins on shared key; quantify unmatched records and attribute mismatches.
  3. Evolution Drift Analysis: Using RNN from P66, generate a 10-year synthetic timeline for a cohort; compare annual statistics (age pyramid, marriage rate) against known demographic trends; observe divergence without recalibration.

## Limitations
- **Validation gap:** Almost no independent empirical validation of output quality ("real-life-like") or evolution fidelity against real-world benchmarks; success is largely self-reported.
- **Evolution scarcity:** Finding only 2 evolution studies (same group) creates a severe evidence gap; generalizability and alternative mechanisms are unknown.
- **Formalization assumption:** Rule-based generation assumes all critical data characteristics and cross-entity relationships can be completely specified a priori, a high-risk assumption in complex systems.

## Confidence
- Rule-Based Generation Feasibility (No Real Data): High
- Evolution as a Missing Capability: High
- Consistency via Centralized Specification: Medium

## Next Checks
- Constraint Solver Benchmark: Implement a representative rule-based generator (e.g., from UML/OCL); measure provable constraint satisfaction rate in large sample; document unsolved constraints.
- Cross-Entity Integrity Stress Test: Generate datasets for 3+ mock entities using shared identifier specification; programmatically attempt all possible relational joins; quantify and categorize mismatches.
- Evolution Calibration Drift Test: For P66's RNN model, generate a 20-year timeline; quarterly compare key distributions (e.g., age, event rates) against stable public statistics; track divergence to establish recalibration threshold.
