# Precomputing Multi-Agent Path Replanning using Temporal Flexibility: A Case Study on the Dutch Railway Network

## Quick Facts
- **ArXiv ID:** 2601.04884  
- **Source URL:** https://arxiv.org/abs/2601.04884  
- **Reference count:** 5  
- **Primary result:** FlexSIPP leverages temporal flexibility of other agents to generate vastly more valid replanning paths for delayed trains in the Dutch railway network compared to prior methods.

## Executive Summary
This paper tackles the challenge of quickly replanning a single delayed agent (e.g., a train) in a multi-agent system without causing cascading delays. The proposed method, FlexSIPP, precomputes all feasible replanning paths by exploiting the temporal flexibility of non-delayed agents—the maximum delay each can absorb without disrupting the overall schedule. In a real-world case study on the Dutch railway network, FlexSIPP dramatically outperformed prior approaches that forbade altering other agents, identifying orders of magnitude more valid paths (e.g., 5,487 vs. 279). Although precomputation times were longer (up to ~1,190 seconds), they remained acceptable for offline use, and the method automatically generated “tipping points” where swapping agent order becomes optimal, offering practical utility for disruption management.

## Method Summary
FlexSIPP operates in two phases: offline precomputation and online querying. During precomputation, it first computes a conflict-free Safe Interval Path Planning (SIPP) graph for the delayed agent, treating other agents as moving obstacles. For each non-delayed agent, it then calculates temporal flexibility at every configuration—the maximum allowable delay without changing interaction order or causing further delays. These flexibility values are embedded into the SIPP graph by modifying Arrival Time Functions (ATFs): for edges where the delayed agent would otherwise follow a conflicting agent, the ATF is extended to allow the delayed agent to start later and still pass before the conflicting agent’s new, delayed time. This enhanced graph is searched using the RePEAT algorithm (repeated A* over any-start-time plans) to compute all optimal plans parametric on departure time. The β parameter of the resulting path ATFs that use flexibility indicates the “tipping point”—the latest departure time where swapping order remains beneficial. At runtime, given a concrete delay, the precomputed plan is retrieved instantly.

## Key Results
- FlexSIPP identified vastly more valid replanning paths than prior methods (@MAEDeR and rSIPP), which forbade altering other agents (e.g., 5,487 vs. 279 in one scenario), by strategically incorporating small delays for other trains.
- Precomputation/search times were significantly longer (up to ~1,190 seconds) but remained within reasonable limits for offline preparation.
- The algorithm automatically generated tipping points for the congested Dutch network, demonstrating practical utility for railway disruption management.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Precomputing per-agent temporal flexibility enables safe, non-cascading delay absorption by other agents.
- **Mechanism:** For each non-delayed agent *a*, Algorithm 1 computes its flexibility *f_a(x_j, t_j)* at each configuration *x_j* and time *t_j* along its planned trajectory. This value represents the maximum delay *a* can incur at that point without changing the order of agent interactions or further delaying any other agent. It is computed by summing local slack (difference between actual and minimum traversal time) and propagated future flexibility, then capping it by the time until the next agent visits the same configuration. This scalar flexibility is attached to the agent’s future safe intervals.
- **Core assumption:** The original plan is conflict-free and agents adhere to their trajectories except for introduced delays. Delaying an agent within its flexibility does not create new conflicts because it only uses idle time (buffer) that was already present in the schedule.
- **Evidence anchors:**
  - [abstract] “tracking and using the temporal flexibility of other agents… the maximum delay an agent can take without changing the order of or further delaying more agents.”
  - [section “Problem Description”] Definition 1 and Algorithm 1 formally define and compute flexibility.
  - [corpus] Corpus shows related work on “Introducing Delays” (paper 226706) and “Real-Time Rescheduling” (132973), but does not detail the specific polynomial-time flexibility computation method; evidence for this precise algorithm is primarily internal.
- **Break condition:** If an agent’s plan has no slack (τ = 0) and its future flexibility is 0, *f_a(x_j, t_j) = 0*. The mechanism fails if the summed local slack and future flexibility are insufficient to absorb a required delay, or if another agent occupies the same configuration immediately after, capping flexibility to near-zero.

### Mechanism 2
- **Claim:** Embedding flexibility as modified Arrival Time Functions (ATFs) in the @SIPP graph allows the replanning search to automatically consider viable “swap” orders with other agents.
- **Mechanism:** For each edge *e* in the @SIPP graph of the delayed agent *a_d*, a standard ATF *A[e] = ⟨ζ, α, β, Δ⟩* defines when *a_d* can traverse it. A flexible ATF *A_F[e] = ⟨ζ, β, β + f_aF(x, t), Δ⟩* is created, where *a_F* is the first other agent that occupies the destination configuration *x* after *a_d* would. The new β parameter extends the latest safe departure time from *a_d*’s start state by *a_F*’s flexibility, permitting *a_d* to start later and still arrive before *a_F*’s new, delayed time. This encodes the “tipping point” trade-off: use *a_F*’s slack to let *a_d* go first, up to the limit.
- **Core assumption:** The only relevant other agent for a given edge is the first one that would conflict (*a_F*). Delaying *a_F* by *f_aF* does not affect the safety intervals for *a_d* on that edge, as *a_F*’s new occupation window is shifted but still non-overlapping with *a_d*’s new window.
- **Evidence anchors:**
  - [section “Method”] Equation (6) and surrounding text define *A_F[e]*.
  - [section “Search”] Explains that using a flexible ATF tracks flexibility used and updates subsequent safe intervals for *a_F*.
  - [corpus] Corpus includes “WinkTPG” (47406) using temporal reasoning and “Bidirectional Temporal Plan Graph” (255579) for switchable orders, but the specific ATF modification technique is unique to this paper; corpus provides context but not direct evidence for this formulation.
- **Break condition:** If *f_aF(x, t) = 0* for the critical agent *a_F*, the flexible ATF collapses to the original (β, β), offering no new departure window. The mechanism also breaks if delaying *a_F* by its full flexibility would cause it to conflict with a *third* agent not originally considered in *a_d*’s @SIPP graph, violating the no-cascade guarantee.

### Mechanism 3
- **Claim:** The search over the enhanced @SIPP graph with flexible ATFs, using RePEAT, efficiently computes all optimal any-start-time plans for *a_d*, implicitly revealing tipping points as the β parameter of path ATFs that use flexibility.
- **Mechanism:** RePEAT performs repeated A* searches over the @SIPP state space for monotonically increasing departure times. The presence of flexible ATFs (*A_F[e]*) creates additional edges and safe intervals that represent plans where other agents are delayed. When the search selects a path using such an edge, the cumulative delay imposed on *a_F* is tracked. The path’s final ATF *A_F[p]* has a β parameter that is the maximum departure time for *a_d* that still uses *a_F*’s flexibility. This β is the “tipping point”: before it, *a_d* can depart and use *a_F*’s slack; after it, *a_d* must wait for *a_F* to pass first (the original order).
- **Core assumption:** The optimal solution for *a_d* given the flexibility constraints will be found by a standard shortest-path search (A*) over the modified graph, as the flexible ATFs correctly encode the cost-neutral delay transfers. The heuristic (shortest distance to goal) remains admissible and consistent in this graph.
- **Evidence anchors:**
  - [abstract] “identifying ‘tipping points’ where swapping agent order becomes optimal.”
  - [section “Tipping points”] “the tipping point is then the β parameter.”
  - [section “Search”] Describes tracking flexibility used during RePEAT search.
  - [corpus] Corpus shows “Any-Start-Time Planning” (Thomas et al. 2023, cited) as foundational, but the integration of flexibility into ATFs and tipping point extraction is a novel contribution of this paper; corpus evidence for this specific combination is absent.
- **Break condition:** The search may not terminate if the flexible ATFs introduce cycles with negative cost (unlikely here as delays only increase time). More critically, if the graph becomes too large (many flexible edges), the polynomial time guarantee (Proposition 2) relies on the number of configurations and agents; if each configuration gains O(|A|) new intervals, search time degrades.

## Foundational Learning
- **Concept: Safe Interval Path Planning (SIPP)**  
  **Why needed here:** FlexSIPP is built on the SIPP state space, where each state is a (location, safe time interval) pair. Understanding how dynamic obstacles (other agents) carve safe intervals from continuous time is fundamental to seeing how conflicts are represented and avoided.  
  **Quick check:** Given a moving obstacle occupying location *x* from time 10 to 15, what are the safe intervals for *x* for an agent with minimum traversal time 2?

- **Concept: Any-Start-Time Planning (@SIPP) and Arrival Time Functions (ATFs)**  
  **Why needed here:** FlexSIPP’s precomputation phase relies on @SIPP to compute a plan for *all* possible start times at once. ATFs (⟨ζ, α, β, Δ⟩) are the core data structure that compactly represents a family of paths parametric on departure time. Modifying ATFs is how flexibility is injected.  
  **Quick check:** What does the parameter β in an ATF represent, and how does it constrain the agent’s possible departure times?

- **Concept: Temporal Flexibility (Definition 1)**  
  **Why needed here:** This is the central resource FlexSIPP exploits. It must be understood as a *local*, *non-propagating* slack: the delay an agent can take *at a specific configuration* without impacting the order of *any* subsequent interactions. It is not global schedule slack.  
  **Quick check:** In the corridor example, if agent *a2* has flexibility 4 at configuration *w*, what exactly does that mean for agent *a1*’s ability to use *w* before *a2*?

## Architecture Onboarding
- **Component map:** Domain Preprocessor → Graph Enhancer → Search Engine → Query Interface
- **Critical path:** Timetable/Infrastructure → (1) Compute original @SIPP for *a_d* → (1) Compute flexibilities for all *a ≠ a_d* → (2) Build flexible @SIPP graph → (3) Run RePEAT search → (4) Query result for specific delay.
- **Design tradeoffs:**
  - **Precomputation time vs. Query speed:** FlexSIPP shifts cost to offline precomputation (graph building + search), enabling near-instantaneous query responses at runtime, crucial for disruption management. @MAEDeR makes the same trade-off but without flexibility.
  - **Graph size vs. Solution quality:** Adding flexible ATFs increases the number of safe intervals and edges in the @SIPP graph (O(|N|·|A|²) as stated). This exponentially increases search space, explaining longer runtimes (Table 3), but yields dramatically more valid paths (Table 2).
  - **Flexibility fidelity vs. Cascading risk:** The algorithm assumes flexibility can be consumed in integer amounts without causing secondary conflicts. The guarantee (Definition 1, Algorithm 1) prevents cascading by limiting *f_a* to the time until the *next* agent’s visit. This is a conservative, safe assumption.
- **Failure signatures:**
  - **No path found in query:** The delayed *a_d* cannot be replanned even with all available flexibility. Indicates the network is critically congested for *a_d*’s route, or the required delay exceeds all relevant agents’ combined flexibility. Output: failure.
  - **Excessive precomputation/search time:** Graph enhancement and RePEAT search time grows with number of agents *|A|* and network size *|N|*. If runtime exceeds limits, the scenario may be too large for current hardware. Symptom: memory pressure, long search times (e.g., 1190s in Table 3).
  - **Unexpectedly low path count:** If FlexSIPP’s path count is close to @MAEDeR’s (e.g., Scenario 4: 525 vs 150), it suggests most flexibility values *f_a* are near zero, meaning the original schedule has minimal buffer time on critical conflicts.

## Limitations
- **Scalability of precomputation:** Search time grows with network/agent count (up to ~1190s). Unclear how it scales to full Dutch network (~400 trains/day) or other domains.
- **Flexibility consumption assumption:** The guarantee that using *f_a* causes no cascading conflicts relies on agents strictly adhering to delayed trajectories. Real-world adherence (e.g., stochastic delays) may violate this.
- **Original schedule dependency:** FlexSIPP assumes an optimal, conflict-free base plan. Performance degrades if the original schedule has minimal slack (Scenario 4 showed only 3.5× improvement over @MAEDeR).

## Next Checks
1. **Stress-test scalability:** Run FlexSIPP on a full-day Dutch timetable (~400 agents). Measure precomputation time/memory vs. scenario size to verify polynomial behavior claim (Proposition 2) and identify practical limits.
2. **Cascading conflict stress-test:** Introduce stochastic perturbations (e.g., small random delays to non-delayed agents) during query execution. Monitor if consumed flexibility *f_a* leads to secondary conflicts, violating the no-cascade guarantee.
3. **Comparative dynamic replanning:** Implement a lightweight dynamic variant of FlexSIPP (without precomputation) and compare query-time performance against the precomputed version under varying delay magnitudes. This tests whether the offline cost is justified for real-time use.
