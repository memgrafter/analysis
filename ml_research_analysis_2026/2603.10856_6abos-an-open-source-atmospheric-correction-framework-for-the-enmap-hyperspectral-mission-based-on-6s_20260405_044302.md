# 6ABOS: An Open-Source Atmospheric Correction Framework for the EnMAP Hyperspectral Mission Based on 6S

## Quick Facts
- **ArXiv ID:** 2603.10856
- **Source URL:** https://arxiv.org/abs/2603.10856
- **Reference count:** 29
- **Primary result:** Validated high spectral similarity (SAM < 10°) for inland water atmospheric correction using EnMAP hyperspectral imagery.

## Executive Summary
6ABOS is an open-source framework for atmospheric correction of EnMAP hyperspectral imagery, specifically targeting optically complex inland waters. It automates a physical inversion of the 6S radiative transfer model, dynamically parameterizing it per scene and per band using parsed metadata and optional Google Earth Engine (GEE) atmospheric retrievals. Validation against in situ spectroscopy at two Mediterranean reservoirs (oligotrophic Benagéber and hypertrophic Bellús) demonstrated high accuracy, with Spectral Angle Mapper (SAM) values consistently below 10°. The framework is distributed via conda-forge to ensure accessibility.

## Method Summary
6ABOS processes EnMAP Level-1C (L1C) products to retrieve bottom-of-atmosphere (BOA) reflectance. The workflow ingests the radiance cube and XML metadata, extracting acquisition geometry, sensor spectral response functions (SRFs), and atmospheric state variables (total column water vapour, O₃, AOD). Atmospheric parameters can be taken directly from the metadata or retrieved dynamically from global GEE catalogues (e.g., MODIS MAIAC for AOD). Using these inputs, the framework configures the 6S model via Py6S and performs parallelized per-band radiative transfer simulations to compute atmospheric terms (path radiance, gaseous transmittance, etc.). It then applies the inverted radiative transfer equation on a per-pixel basis to convert top-of-atmosphere radiance to BOA reflectance. Finally, it applies a mask based on total transmittance (default threshold 0.85) and writes the output as a GeoTIFF.

## Key Results
- High spectral similarity validated at two contrasting inland water sites (Benagéber, Bellús).
- Consistently low SAM values (< 10°) between corrected EnMAP spectra and in situ measurements.
- Open-source distribution via conda-forge for community adoption.

## Why This Works (Mechanism)

### Mechanism 1: Dynamic 6S Inversion
- **Claim:** 6ABOS retrieves surface reflectance (ρ_w) by dynamically inverting the 6S radiative transfer equation per spectral band, avoiding interpolation errors from static lookup tables.
- **Mechanism:** For each EnMAP channel, the framework uses Py6S to parameterize the 6S model with scene-specific geometry, SRFs, and atmospheric state (O₃, WV, AOD). It explicitly computes atmospheric path radiance (L_path), gaseous transmittance (T_g), and other terms to solve the inverted radiative transfer equation, transforming TOA radiance to BOA reflectance.
- **Core assumption:** The atmospheric state variables (parsed from metadata or GEE) are sufficiently accurate and representative of the scene-average conditions. The 6S model’s vectorial treatment and per-band simulation adequately capture atmospheric effects.
- **Evidence anchors:** [abstract] "automate the atmospheric correction (AC) of EnMAP hyperspectral imagery. By leveraging the Second Simulation of the Satellite Signal in the Solar Spectrum (6S) radiative transfer model, 6ABOS implements a physically-based inversion scheme..." [section 2.1] "In contrast, the proposed 6ABOS framework does not rely on static forward LUT inversion. Instead, it employs 6S as a physically-based radiative transfer engine to dynamically simulate the atmospheric state for each acquisition geometry and spectral channel." [section 3.2] "Dynamic parameterisation of the 6S model using the Py6S interface..."
- **Break condition:** Severely inaccurate or temporally mismatched atmospheric state inputs propagate errors. High-gradient atmospheric conditions or extreme aerosol events may exceed the model’s parametric capacity, leading to residual errors.

### Mechanism 2: GEE Integration for Atmospheric Parameters
- **Claim:** Integration with Google Earth Engine (GEE) provides a flexible, dynamic source for atmospheric parameters (AOD, O₃, WV), reducing dependency on potentially sparse or low-quality EnMAP L1C metadata.
- **Mechanism:** The `atmospheric.py` module uses the GEE API to query global atmospheric datasets (e.g., MODIS MAIAC for AOD, TOMS/SBUV for O₃, NCEP RE for WV) based on the acquisition date and footprint. These retrieved values parameterize the 6S model, offering an alternative or cross-validation to the metadata.
- **Core assumption:** The GEE datasets are available, have sufficient spatial/temporal resolution, and are representative of the actual atmospheric conditions over the scene at acquisition time.
- **Evidence anchors:** [abstract] "integrates automated EnMAP metadata parsing with dynamic atmospheric parameter retrieval via the Google Earth Engine (GEE) Application Programming Interface (API)." [section 3.2] "A key advantage of 6ABOS is its operational flexibility regarding atmospheric characterisation. While the framework can automatically parse the atmospheric state variables provided in the EnMAP L1C metadata, it also offers the capability to retrieve these parameters from global catalogues via the Google Earth Engine (GEE) API."
- **Break condition:** GEE service outages, dataset discontinuation, or poor spatial/temporal collocation between the GEE product and the EnMAP scene yield unrepresentative parameters.

### Mechanism 3: Modular Parallelized Architecture
- **Claim:** The modular, parallelized architecture enables efficient processing of large hyperspectral cubes by decoupling I/O, atmospheric modeling, and pixel-wise inversion.
- **Mechanism:** The workflow orchestrates five stages: 1) Metadata/SRF ingestion (`utils.py`), 2) 6S configuration, 3) parallelized per-band RTM simulation (using `ProcessPoolExecutor`), 4) pixel-wise application of the inverted equation (`core.py`), 5) compliant export. This separation allows independent scaling of the computationally intensive RTM simulations across CPU cores.
- **Core assumption:** The per-scene, scene-average atmospheric parameters are valid for all pixels. Parallelization does not introduce race conditions or memory issues. The SRF convolution correctly maps the 6S 2.5 nm output to EnMAP’s ~6.5 nm bands.
- **Evidence anchors:** [section 3.3] "The 6ABOS workflow implements a modular five-stage architecture designed to ensure physical consistency and computational efficiency: 1. Metadata and SRF Ingestion... 3. Parallelised RTM Simulation: The RTM simulations are executed in parallel across multiple CPU cores." [section 3.4] "The architecture is organised into well-defined modules... core.py (Physics Engine)... atmospheric.py (Atmospheric Data Interface)... utils.py (I/O & Metadata)."
- **Break condition:** Extremely large scenes may exhaust memory during parallel RTM accumulation. Strong spatial atmospheric gradients cause localized failures due to single atmospheric state.

## Architecture Onboarding

- **Component map:** `sixabos-run (CLI) -> Orchestrator -> [core.py (Physics Engine), atmospheric.py (Atmospheric Data Interface), utils.py (I/O & Metadata)] -> External (Py6S, GEE API, rasterio/numpy)`
- **Critical path:** Metadata/SRF ingestion (utils.py) → Atmospheric parameter fetch (atmospheric.py) → Per-band 6S simulation (parallel in core.py) → Pixel-wise inversion (core.py) → Mask application → Output writing (utils.py). The RTM simulation is the heaviest computational step.
- **Design tradeoffs:**
  1. Dynamic vs. LUT: Dynamic per-scene/per-band 6S calls increase compute time vs. pre-computed LUTs but avoid interpolation errors in non-linear regimes.
  2. GEE dependency vs. self-containment: GEE integration adds flexibility but introduces external API dependency, network requirements, and potential data latency/collocation issues.
  3. Scene-average vs. per-pixel atmosphere: Using a single atmospheric state for the whole scene is efficient but fails over strong spatial gradients (e.g., aerosol plumes, broken cloud shadows).
- **Failure signatures:**
  - High SAM error (>10°): Likely cause: Mismatched atmospheric state (O₃, WV, AOD). Check metadata vs. GEE values.
  - Striking or banding in output: Parallelization race condition or memory overflow. Reduce `--jobs` in CLI.
  - Discontinuous spectra or excessive masking: `T_g` threshold too aggressive, or strong gaseous absorption bands mis-modelled. Review 6S spectral sampling vs. EnMAP SRF convolution.
  - `Py6S` import error: 6S binary not found in PATH or conda environment not activated correctly.
- **First 3 experiments:**
  1. **Installation & CLI Check:** `conda install -c conda-forge sixabos`; `sixabos-run -h`. Confirm `import sixabos` in Python prints system hook message.
  2. **Single-Band Smoke Test:** Run 6ABOS on a tiny subset (e.g., 100x100 pixels) of a known EnMAP L1C scene with `--aerosol Continental`. Inspect output `.tif` band 10 (blue) for reasonable land/water contrast. Check `metadata.json` for atmospheric parameters used.
  3. **Validation Replication:** Process the Benagéber or Bellús scene from the paper (if available). Extract a water pixel spectrum and compute SAM against the paper’s *in situ* spectrum (provided in Fig 5). Expect SAM < 10° if parameters match.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How does the limited intrinsic spectral resolution of the 6S radiative transfer model (2.5 nm sampling) affect the accuracy of atmospheric correction in the strongest gaseous absorption bands (e.g., deep water vapor features) for EnMAP data, and can integrating higher-resolution absorption files mitigate this without compromising computational stability?
- **Basis in paper:** [explicit] The paper acknowledges that 6S's spectral resolution may not fully resolve narrow absorption structures, particularly in strong gaseous bands, and states that "a future development would be to integrate absorption files with higher spectral resolution" (Page 6). This is presented as a known structural limitation.
- **Why unresolved:** The current framework uses the standard 6S resolution and applies a transmittance mask to avoid noise in these bands, but the quantitative impact of this approximation on downstream water-leaving reflectance retrieval—especially in the critical NIR/SWIR regions used for glint correction or turbid water algorithms—has not been quantified. The proposed solution (higher-res files) has not been implemented or tested.
- **What evidence would resolve it:** A rigorous sensitivity analysis comparing 6ABOS outputs using standard 6S absorption data versus proposed higher-resolution alternatives over scenes with strong, variable water vapor/oxygen absorption. Validation would require coincident high-resolution ground-based atmospheric spectroscopy (e.g., from AERONET or dedicated field campaigns) to benchmark the simulated atmospheric transmittance in these problematic spectral regions.

### Open Question 2
- **Question:** To what extent can the 6ABOS framework, validated only over two semi-arid Mediterranean reservoirs, reliably correct EnMAP imagery over inland waters experiencing extreme but common atmospheric conditions such as severe aerosol loading from dust storms, biomass burning plumes, or high humidity events?
- **Basis in paper:** [explicit] The conclusions explicitly state that "AC remains an evolving challenge... particularly regarding the characterisation of extreme aerosol events" (Page 17). The validation was limited to two sites with "contrasting trophic states" but similar regional climates.
- **Why unresolved:** The study's validation sites represent specific, relatively stable atmospheric and optical conditions (oligotrophic vs. hypertrophic). The framework's performance under dynamically complex aerosol models (e.g., heavy dust, smoke) or very high water vapor columns—which significantly alter scattering and absorption—was not tested. The reliance on GEE products like MODIS MAIAC for AOD retrieval may also introduce uncertainties during such events due to potential saturation or retrieval failures.
- **What evidence would resolve it:** Systematic application of 6ABOS to a global set of EnMAP scenes acquired during known extreme atmospheric events, with validation using coincident AERONET aerosol and precipitable water data, and in-water radiometry if available. Performance should be evaluated against other processors (e.g., ACOLITE, PACO/WASI) under these same conditions.

### Open Question 3
- **Question:** How effective is the adjacency effect correction implicitly handled by 6ABOS's physical inversion (using scene-averaged atmospheric parameters from metadata) in landscapes with highly heterogeneous terrestrial surroundings (e.g., small, fragmented water bodies interspersed with dense vegetation or bright urban areas), and does it require an explicit, dedicated adjacency correction module?
- **Basis in paper:** [inferred] The paper identifies adjacency effects as a key complication for inland waters (Page 2) and notes that 6ABOS uses "scene-average characterisation" of atmospheric state variables from metadata (Page 8). However, the methodology description does not include a specific, algorithmic adjacency correction step beyond the core 6S inversion, which is typically designed for homogeneous surfaces.
- **Why unresolved:** While 6S can theoretically model adjacency if provided with detailed surrounding reflectance, 6ABOS's automated pipeline uses averaged atmospheric parameters. It is unclear if the inversion adequately accounts for spatially variable environmental radiance in complex riparian zones. The validation was conducted on large reservoirs with open water-dominated surroundings, not on small or fragmented water bodies where adjacency is a dominant error source.
- **What evidence would resolve it:** Controlled experiments using synthetic EnMAP data (e.g., generated by WASI or RTMs) with known, spatially heterogeneous adjacency contributions. Compare 6ABOS outputs with and without an external adjacency correction module (like that in EnMAP L2A) against the known "true" water-leaving reflectance. Additionally, field validation in complex landscapes with detailed mapping of adjacent land cover is needed.

### Open Question 4
- **Question:** What are the comparative advantages and trade-offs of using dynamic GEE-retrieved atmospheric parameters (e.g., MODIS MAIAC AOD, NCEP WV) versus the native EnMAP L1C metadata parameters for 6S inversion in terms of final Rrs accuracy, especially in regions with sparse ground truth or during rapid atmospheric changes?
- **Basis in paper:** [explicit] The framework explicitly integrates "dynamic atmospheric parameter retrieval via the Google Earth Engine (GEE) Application Programming Interface (API)" as a "dual-source approach" to allow "cross-validation" or substitution for missing metadata (Page 8-9). However, no comparative assessment between the two parameter sources is provided in the validation.
- **Why unresolved:** The validation results (SAM values) are presented without specifying which atmospheric parameter source (metadata vs. GEE) was used for the final correction, or if both were tested. The potential for increased accuracy (or introduced error) from using potentially higher-resolution but collocated-in-time GEE products versus the potentially sensor-specific but temporally mismatched L1C metadata is an open methodological question.
- **What evidence would resolve it:** A dedicated processing experiment over the validation sites (and others) where 6ABOS is run with (a) only L1C metadata, (b) only GEE-retrieved parameters, and (c) a hybrid approach. The resulting Rrs products should be compared against in situ spectra using SAM, RMSE, and band-by-band bias. The stability of each source's parameters (e.g., AOD) should also be compared to local AERONET measurements to assess representativeness.

## Limitations
- **Atmospheric state source dependency:** Accuracy hinges on the quality and collocation of inputs (AOD, O₃, WV); GEE products may be temporally/spatially mismatched or unavailable.
- **Scene-average atmosphere assumption:** A single atmospheric state fails over large areas with heterogeneous aerosols, cloud shadows, or complex terrain.
- **6S model limitations for water:** 6S is a general atmospheric RTM, not specialized for aquatic optics; validity for high chlorophyll or CDOM cases is not deeply examined; validation limited to two reservoirs.

## Confidence
- **Claim 1:** Dynamic 6S inversion produces accurate BOA reflectance. **Confidence: Medium-High** (supported by in situ validation but limited site diversity and no comparative methods).
- **Claim 2:** GEE integration provides a robust alternative to metadata. **Confidence: Medium** (mechanism described but no empirical comparison of parameter sources).
- **Claim 3:** Open-source conda-forge distribution ensures accessibility. **Confidence: High** (package exists and installs reliably).
