# Domain-Independent Dynamic Programming with Constraint Propagation

## Quick Facts
- arXiv ID: 2603.16648
- Source URL: https://arxiv.org/abs/2603.16648
- Reference count: 39
- Primary result: Integrating constraint propagation into DIDP prunes infeasible states and strengthens dual bounds, solving more instances of scheduling and RCPSP problems; improvements on TSPTW appear only under tight constraints.

## Executive Summary
The paper presents a generic method to embed constraint propagation from constraint programming into the Domain‑Independent Dynamic Programming (DIDP) framework. By calling a general‑purpose CP solver during heuristic search (A* or CABS), the approach filters successors and tightens dual bounds. Experiments on three combinatorial optimisation problems show increased solved instances and fewer state expansions for Single Machine Scheduling with Time Windows (1|r_i, δ_i|∑w_iT_i) and Resource Constrained Project Scheduling Problem (RCPSP). For Travelling Salesperson Problem with Time Windows (TSPTW), gains are limited to tightly constrained cases. The work demonstrates a model‑based, problem‑independent integration of DP dominance detection with CP inference.

## Method Summary
The DIDP solver (RPID) operates on a state‑transition representation. The authors replace the standard successor generator with a CP wrapper. For each state, the wrapper builds a CP model from the partial assignment, applies propagation (via Pumpkin) to tighten variable domains, and uses the results to (i) discard infeasible states, (ii) filter infeasible successors, and (iii) compute a problem‑specific dual bound that supplements the original DP bound. The interface is generic: users implement `CPModel(S)` to map a state to a CP model and define `IsInfeasible`, `DualCP`, and `IsSuccInfeasible`. The integrated solver is compared against baseline RPID (with A* or CABS) on standard benchmarks under a 30‑minute timeout, measuring solved instances, state expansions, and optimality gaps.

## Key Results
- The CP‑integrated solver solves more instances than the DP baseline for 1|r_i, δ_i|∑w_iT_i and RCPSP, with significantly fewer state expansions.
- For TSPTW, improvements occur only on tightly constrained instances (low time‑window slack, high density); on loosely constrained instances the overhead negates benefits.
- Propagation overhead is offset by pruning gains on constrained instances, but further optimisation is needed for broader efficiency.

## Why This Works (Mechanism)
### Mechanism 1
**Claim:** Constraint propagation prunes infeasible successor states during DP state expansion, reducing the number of states explored.  
**Mechanism:** For a state `S`, the DP solver constructs a CP model of its partial assignment. Generic CP propagation tightens variable domains. A successor state `Sⱼτ` is infeasible if its decision variable falls outside the propagated domain (e.g., `t'(t, τ) ∉ D'(s_τ)`).  
**Core assumption:** The CP model accurately captures the constraints of `S` and its feasible extensions.  
**Evidence anchors:** [abstract] "enabling a DP solver to prune states and transitions using constraint propagation." [section 4.1] `IsSuccInfeasible(Sⱼτ, D')` uses propagated domains to prune.  
**Break condition:** Propagation overhead exceeds the cost of generating/evaluating pruned successors, typically on loosely constrained instances.

### Mechanism 2
**Claim:** Propagated domain bounds (`D'`) yield a stronger dual bound (`DualCP(S, D')`) than the generic DP bound, improving heuristic guidance.  
**Mechanism:** After propagation, reduced domains (e.g., earliest start times) compute a tighter lower bound on remaining cost. The DP heuristic becomes `f(S) = g(S) + max{Dual(S), DualCP(S, D')}`.  
**Core assumption:** The CP‑derived bound is admissible and tighter than the original DP bound.  
**Evidence anchors:** [section 4.1] `Dual(Sⱼτ)` replaced with `max{Dual(Sⱼτ), DualCP(Sⱼτ, D')}`. [sections 4.2–4.4] Problem‑specific `DualCP` formulations.  
**Break condition:** Computing `DualCP` costs more than the heuristic improvement justifies.

### Mechanism 3
**Claim:** The generic CP‑DP interface enables model‑based, problem‑independent integration without modifying the core DP solver.  
**Mechanism:** The `GenSuccPropagation` wrapper (Algorithm 2) centralises CP interaction. The user provides `CPModel(S)` to map a state to a CP model `(X, C, D)`. Propagation results are interpreted via `IsInfeasible`, `DualCP`, and `IsSuccInfeasible`, decoupling DP logic from CP inference.  
**Core assumption:** The user‑provided `CPModel` translation is correct and complete.  
**Evidence anchors:** [abstract] "providing a generic model‑based way of integrating heuristic search with constraint propagation." [section 4.1] Interface definition and Algorithm 2.  
**Break condition:** `CPModel(S)` is too costly or the available propagators do not effectively prune the state space.

## Foundational Learning
- **State‑Based Dynamic Programming (DP) Representation**  
  *Why needed:* DIDP represents solutions as sequences of state transitions; understanding `(State, Transition, Successor)` and concepts like dominance and dual bounds is prerequisite to seeing where CP propagation is injected.  
  *Quick check:* If state `S_a` has the same set of scheduled tasks as `S_b` but an earlier current time `t_a < t_b`, what dominance relationship holds according to Inequality (5) in Section 2.1?

- **Constraint Propagation & Filtering Algorithms**  
  *Why needed:* The core pruning mechanism comes from CP. Knowing how propagators (e.g., edge‑finding for `Disjunctive`, timetable filtering for `Cumulative`) tighten variable domains is essential to understand what information is fed back to the DP solver.  
  *Quick check:* For a `Cumulative` constraint with capacity `C_r`, what does the propagation algorithm infer if the sum of guaranteed resource usage of tasks `Ω` exceeds `C_r` at some time point?

- **Heuristic Search (A* and CABS) in DP**  
  *Why needed:* The DP solver uses heuristic search (`f = g + h`) to order state expansions; the dual bound is the heuristic `h(S)`. Understanding this function is critical to see how `DualCP` improves guidance.  
  *Quick check:* In CABS, how does the beam width `b` affect memory usage and the likelihood of proving optimality compared to A*?

## Architecture Onboarding
**Component map:**  
DP Solver (RPID) -> CP Wrapper (GenSuccPropagation) -> Generic CP Solver (Pumpkin), with User‑Defined Problem Modules providing implementations of `DP‑TargetState`, `IsBaseState`, `GenSucc`, `Dominates`, `Dual`, and CP hooks (`CPModel`, `IsInfeasible`, `DualCP`, `IsSuccInfeasible`).

**Critical path:** The performance‑critical loop is `DP Solver` → `GenSuccPropagation` → `CP Solver` → `Propagate` → `IsSuccInfeasible` during state expansion; overhead here directly impacts runtime per node.

**Design tradeoffs:**  
- *Propagation depth:* One propagation per state vs. fixed‑point propagation (tried, too costly). Limited propagation reduces overhead but may miss deeper inferences.  
- *CP model scope:* Using a relaxation (e.g., TSPTW with `Disjunctive` on all unvisited nodes) vs. tighter representation. Relaxations propagate faster but yield weaker bounds.  
- *Interface richness:* Current simple interface (`Propagate` → `D'`) vs. a richer "lazy clause generation" style that could incrementally add constraints. Simplicity aids engineering; richness may improve pruning.

**Failure signatures:**  
- **High overhead, low pruning:** On loosely constrained instances (e.g., TSPTW with large `α`, scheduling with large `ϕ`). Symptoms: `CABS+CP` solves fewer instances than `CABS` within timeout, runtime per node higher, state expansions similar or slightly lower.  
- **Incorrect/incomplete CP model:** `CPModel(S)` omits an active constraint. Symptoms: `IsSuccInfeasible` fails to detect truly infeasible transitions or `DualCP` is weaker than expected.  
- **Propagation not cost‑effective:** On medium‑constrained instances where pruning does not offset CP call cost. Symptoms: `CABS+CP` expands fewer states but uses more total time than `CABS`.

**First 3 experiments:**  
1. **Baseline comparison on 1|r_i, δ_i|∑w_iT_i:** Run `CABS` vs. `CABS+CP` on 900 instances (varying `τ, ρ, ϕ`). Verify `CABS+CP` solves more total instances, especially for `ϕ ≤ 1.05`. Check that state expansions are significantly lower (Figure 2a).  
2. **Overhead analysis on RCPSP:** Measure average time per state expansion for `CABS` and `CABS+CP` on J90 instances. Confirm `CABS+CP` has higher per‑node cost but lower *cost per solved instance* (Figure 4b). Inspect optimality gap curves (Figure 10) to see if gap reduction justifies overhead.  
3. **Constrainedness sensitivity on TSPTW:** Run `CABS` and `CABS+CP` on Rifki & Solnon (2025) parameterised instances with varying `α` (density) and `β` (time window tightness). Confirm `CABS+CP` only outperforms `CABS` when `α < 1.2` and `β` is low (tight windows); for `α ≥ 1.2` overhead dominates (Figures 6, 8).

## Open Questions the Paper Calls Out
**Open Question 1:** To what extent can the DIDP framework incorporate inference techniques from other paradigms (e.g., linear programming relaxations, Boolean satisfiability) while preserving its generic model‑based integration?  
*Basis:* The authors state: “Our interface is generic, allowing future work to investigate the integration of DP solvers with other techniques besides CP.”  
*Why unresolved:* The current implementation exclusively uses a CP solver; alternative inference engines have not been explored within the same heuristic‑search loop.  
*What evidence would resolve it:* Implement hybridizers that plug LP or SAT engines into the DIDP generation function, then evaluate the impact on state expansions and runtime across the three benchmark problems.

**Open Question 2:** Does enriching the DP‑CP interface with richer information exchange (e.g., sharing partial state data, custom propagators) yield measurable performance gains over the minimal current design?  
*Basis:* The authors note: “the interface could be enriched to investigate the impact of additional information on the DP solver.”  
*Why unresolved:* The existing interface only returns infeasibility flags and a dual bound; bidirectional or more elaborate communication remains unexamined.  
*What evidence would resolve it:* Design an extended API that allows the CP solver to feed back domain reductions or learned constraints, and empirically compare the enriched version against the baseline on standard benchmarks.

**Open Question 3:** Which algorithmic strategies can effectively reduce the overhead of constraint propagation in DIDP, particularly redundant work from state‑to‑state jumps and the timing of propagation calls?  
*Basis:* The authors identify: “future work could look into reducing propagation overhead, e.g., by reducing redundant work introduced by jumping between states, or by determining when to propagate.”  
*Why unresolved:* Propagation is invoked at every state expansion without caching or adaptivity; for many instances the cost outweighs pruning gains, especially when constraints are loose.  
*What evidence would resolve it:* Propose techniques like memoization of propagation results for state clusters, lazy propagation, or threshold‑based invocation, then measure runtime and state reduction across instances of varying constrainedness.

**Open Question 4:** How do problem‑specific characteristics (e.g., time‑window tightness, resource capacity ratios, precedence density) influence the effectiveness of constraint propagation in DIDP?  
*Basis:* Experiments reveal sharply different outcomes: propagation dramatically improves results for 1|r_i,δ_i|∑w_iT_i and RCPSP, but helps TSPTW only under tight constraints. The authors observe that propagation “performs exceptionally well when instances are highly constrained” but do not explain why.  
*Why unresolved:* No systematic diagnostic study links propagation strength to quantifiable instance features; the observed variation is only qualitatively attributed to constrainedness.  
*What evidence would resolve it:* Perform a large‑scale correlation analysis between propagation impact (e.g., reduction in state expansions) and metrics such as time‑window slack, resource utilization, or graph density; alternatively, run controlled parameter‑varying experiments to isolate causal factors.

## Limitations
- Exact CABS parameters (beam width, layer definition) are not fully specified, risking reproducibility.
- Propagation overhead can dominate runtime on loosely constrained instances, negating pruning benefits.
- User‑defined `CPModel` translation errors may cause false infeasibility or missed pruning.

## Confidence
- Pruning via propagation: Medium
- Stronger dual bounds: Medium
- Generic model‑based integration: Medium

## Next Checks
1. **Overhead break‑even analysis:** On TSPTW, measure propagation time vs. constrainedness (α, β). Confirm CABS+CP underperforms baseline when α ≥ 1.2 or time windows are loose.
2. **CP model fidelity test:** For each problem, generate partial states with known infeasible transitions. Verify `IsSuccInfeasible` correctly detects them and `DualCP` remains admissible.
3. **Propagation depth trade‑off:** Implement a fixed‑point propagation variant and compare against once‑per‑state on 50 random instances per problem. Expect more pruning but higher overhead, justifying the design choice.
