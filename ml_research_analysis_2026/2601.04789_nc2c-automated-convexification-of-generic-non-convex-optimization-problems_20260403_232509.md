# NC2C: Automated Convexification of Generic Non-Convex Optimization Problems
## Quick Facts
- **ArXiv ID:** 2601.04789
- **Source URL:** https://arxiv.org/abs/2601.04789
- **Reference count:** 40
- **Primary result:** An LLM-based framework automatically transforms generic non-convex optimization problems into convex forms, achieving 89.3% execution rate and 76% success rate on 100 diverse problems.

## Executive Summary
Non-convex optimization problems are widespread but pose significant difficulties for standard solvers, traditionally requiring expert manual intervention to convexify them. The NC2C framework proposes an automated approach using large language models (LLMs) to detect non-convex components within a mathematically formulated problem, select appropriate convexification strategies (e.g., successive convex approximation), and generate an equivalent convex problem. The system incorporates iterative error correction and feasibility domain correction loops to recover from execution failures and infeasible solutions. Evaluated on 100 diverse problems from multiple benchmarks, NC2C demonstrates high execution and success rates, generalizes across problem domains and LLM models, and operates with competitive running times, thereby reducing expert dependency and enabling efficient deployment of convex solvers.

## Method Summary
NC2C implements a multi-stage pipeline: First, a problem parser uses named entity recognition to extract variables, parameters, objective, and constraints from natural language descriptions, constructing a formal optimization model. Next, an analyzer identifies non-convex components (e.g., bilinear terms, fractional expressions). A strategy selector then maps each non-convex element to a convexification technique from a predefined set (e.g., linearization via first-order Taylor expansion). The convexifier applies these transformations to produce a convex counterpart. A code generator translates the convex model into executable Python using CVXPY, Gurobi, or SciPy. The generated code is executed; if it fails (error), an error correction loop (ECL) iteratively revises the code. If a solution is found but is infeasible for the original problem, a feasibility domain correction (FDC) loop adjusts initial points or re-convexifies over multiple iterations. The final output is a feasible solution to the original problem derived from its convex surrogate.

## Key Results
- Achieved an **89.3% execution rate** (code runs without error) and a **76% success rate** (solution satisfies original constraints) on 100 diverse non-convex problems using GPT-5.1.
- Significantly outperformed baseline methods in success rate, demonstrating the effectiveness of the automated convexification approach.
- Generalizes across multiple optimization domains (NL4Opt, NLP4LP, ComplexOR, WireOpt) and scales to different LLM backbones (GPT-5.1, Qwen3-235B-A22B).
- Maintains competitive average running times (~20–30 seconds per problem), with the majority of time spent on convex transformation and model generation.

## Why This Works (Mechanism)
### Mechanism 1: Non-convex component detection
- **Claim:** NC2C uses LLMs to detect non-convex components in mathematically formulated problems.
- **Mechanism:** The framework employs named entity recognition and symbolic reasoning to parse the mathematical model, identifying terms like bilinear products, fractional expressions, or integer constraints that violate convexity.
- **Core assumption:** LLMs possess sufficient mathematical parsing capability to correctly classify function and constraint terms as convex or non-convex based on standard definitions.
- **Evidence anchors:** Abstract mentions autonomous detection; Section 3.1 details `ExtractVariables` and variable type inference.
- **Break condition:** Misidentification of non-convex terms leads to incorrect or omitted convexification, causing downstream solver failure or infeasible solutions.

### Mechanism 2: Strategy selection and application
- **Claim:** NC2C selects and applies appropriate convexification strategies tailored to each detected non-convex component.
- **Mechanism:** For each identified non-convex element `n_l`, the system invokes `SelectStrategy(n_l, P)` to choose from a strategy set Σ. For instance, SCA linearizes functions via first-order Taylor expansion around a reference point.
- **Core assumption:** A predefined, limited set of heuristic convexification rules is sufficient to transform most generic non-convex components into convex equivalents without significant optimality loss.
- **Evidence anchors:** Abstract mentions selecting optimal strategies; Section 3.2 formalizes strategy selection and SCA derivation.
- **Break condition:** An inappropriate strategy is selected (e.g., using SCA on a non-differentiable term), yielding a convex problem whose solution is infeasible or suboptimal for the original problem.

### Mechanism 3: Iterative correction loops
- **Claim:** Error correction (ECL) and feasibility domain correction (FDC) loops recover from execution failures and infeasible solutions, respectively.
- **Mechanism:** After code execution, ECL analyzes error reports to iteratively correct code. If a solution is infeasible, FDC either adjusts the initial point (Stage 1) or re-convexifies with alternative strategies (Stage 2), both bounded by iteration limits.
- **Core assumption:** Most initial convexification and code generation errors are systematic and correctable via LLM-driven analysis of solver feedback and constraint violations.
- **Evidence anchors:** Abstract describes both mechanisms; Section 5.2 ablation shows o-ECL drops execution rate by ~27-31%, o-FDC drops success rate by ~79-84%.
- **Break condition:** Errors exceed correction capacity within iteration limits, or FDC cannot find a feasible region due to over-relaxation.

## Foundational Learning
- **Convexity Conditions:** (e.g., Hessian positive semidefinite for twice-differentiable functions, Jensen’s inequality). **Why needed:** To understand what makes a component non-convex and why specific transformations yield convex approximations. **Quick check:** Given `f(x) = x^T Q x + c^T x`, what property must `Q` have for `f` to be convex?
- **Successive Convex Approximation (SCA) and convex relaxations:** (e.g., for bilinear terms, binary variable relaxation). **Why needed:** These are the primary strategies NC2C is expected to select and apply. Knowing their mathematical form and limitations explains the framework’s power and potential suboptimality. **Quick check:** How does one convexify a constraint `x * y <= 1` with `x, y >= 0` using a first-order Taylor approximation around `(x0, y0)`?
- **Solver-based validation and feasibility checking:** (CVXPY/Gurobi constraints). **Why needed:** NC2C’s success metric relies on executable code that produces feasible solutions. Understanding how solvers interpret constraints and declare infeasibility is key to interpreting `I_e` and `I_f` metrics. **Quick check:** If a convexified problem returns a solution that violates an original non-convex constraint, what does that imply about the relaxation?

## Architecture Onboarding
- **Component map:** Problem Parser -> Mathematical Model Builder -> Non-Convex Analyzer -> Strategy Selector -> Convexifier -> Code Generator -> Executor & Validator. [ECL Module] and [FDC Module] are triggered conditionally after Executor & Validator based on error (`I_e=0`) or infeasibility (`I_f=0`).
- **Critical path:** Input → Parser → Model Builder → Analyzer → Selector → Convexifier → Code Gen → Executor → (if `I_f=0`) FDC → Output. ECL runs in parallel after Code Gen/Executor on errors.
- **Design tradeoffs:**
  - Generality vs. Optimality: Generic LLM-driven transformations yield high generality but may produce suboptimal relaxations compared to domain-specific hand-crafted convexifications.
  - Robustness vs. Speed: ECL/FDC improve success rates but add computational overhead; iteration hyperparameters `K` and `L` directly trade runtime for robustness.
  - LLM Capability Dependency: Performance scales with model reasoning ability; transparent strategy selection is limited (“black-box” LLM choice).
- **Failure signatures:**
  - Low Execution Rate indicates persistent code generation/solver integration issues (likely Code Generator or incorrect `P_c`).
  - High Execution Rate but low Success Rate indicates feasible `x*` for `P_c` but infeasible for original `P`—failure of FDC or overly aggressive relaxation.
  - Ablation `o-convex` shows catastrophic drop, confirming convexification as the single most critical component.
- **First 3 experiments:**
  1. **Ablation Study:** Systematically remove `-convex`, `-ECL`, `-FDC` to quantify each component’s contribution to success/execution rates.
  2. **Iteration Analysis:** Vary `K` (ECL max iterations) and `L` (FDC max iterations) to find efficiency/robustness sweet spots.
  3. **Cross-Dataset & Model Generalization:** Test on NL4Opt, NLP4LP, ComplexOR, WireOpt with two models to assess robustness to problem type and LLM capability.

## Open Questions the Paper Calls Out
- **Open Question 1:** How does NC2C’s performance scale with the mathematical reasoning capabilities and architectural differences of various underlying LLMs, especially in domains requiring specialized terminology?
- **Open Question 2:** What is the theoretical or empirical optimality gap introduced by NC2C’s convexification and relaxation steps, and can this gap be bounded or minimized?
- **Open Question 3:** Can the NC2C framework’s selection of convexification strategies be made more transparent and interpretable, and does a more principled, theoretically-guided strategy selection improve success rates on complex problems?
- **Open Question 4:** What are the formal convergence properties and limitations of the Feasibility Domain Correction mechanism, particularly its two-stage iterative process?
- **Open Question 5:** Can the multi-stage processing pipeline be optimized or streamlined to reduce computational overhead while maintaining high success and execution rates, making it viable for real-time or interactive applications?

## Limitations
- Prompt engineering details (system prompts, temperature, few-shot examples) are incompletely described, hampering exact replication.
- The exact composition of the 100-problem test set and the filtering criteria from source datasets are not disclosed, preventing independent dataset reconstruction.
- The fixed convexification strategy set may not cover all non-convex forms; LLM-driven selection lacks interpretability and could fail on out-of-distribution structures.
- Performance claims rely on only two LLMs (GPT-5.1, Qwen3); results may not generalize to newer or differently architectures.
- No theoretical correctness guarantees; the pipeline inherits the LLM’s imperfect mathematical reasoning.

## Confidence

- Strategy selection and application: **Medium**
- Error correction (ECL) & feasibility correction (FDC): **High**
- Overall success rate (76% on 100 problems): **Medium**
