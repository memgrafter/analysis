# SPARTA: Scalable and Principled Benchmark of Tree-Structured Multi-hop QA over Text and Tables

## Quick Facts
- **arXiv ID:** 2602.23286  
- **Source URL:** https://arxiv.org/abs/2602.23286  
- **Reference count:** 40  
- **Primary result:** SPARTA introduces an automated pipeline to build a large-scale, error-free Table-Text QA benchmark; state-of-the-art models drop by >30 F1 points, revealing fundamental weaknesses in cross-modal reasoning.

## Executive Summary
SPARTA addresses limitations of existing Table-Text QA benchmarks—small scale, manual annotation errors, and shallow questions—by introducing a fully automated pipeline. It constructs a unified reference fact database from source tables and text-derived grounding tables, then synthesizes executable, nested SQL queries with controlled hop counts using LLMs guided by provenance-based refinement and post-order traversal. Natural-language questions are generated via SQL-to-text models with lightweight human validation. The resulting benchmark features large tables (up to ~10k rows), supports aggregation/grouping, and achieves a 0% annotation error rate versus 21–30% in prior benchmarks. State-of-the-art models (ODYSSEY, HProPro) drop by more than 30 F1 points on SPARTA compared to HybridQA/OTT-QA, highlighting the difficulty of deep cross-modal reasoning. Annotation time is reduced to one-quarter of HybridQA’s.

## Method Summary
SPARTA builds a benchmark through a three-stage pipeline. First, it constructs a *reference fact database* by merging structured source tables with grounding tables derived from atomic facts extracted from unstructured text. Second, it generates executable SQL queries with the desired multi-hop structure: non-nested queries are built clause-by-clause with execution-guided feedback, while nested queries use post-order traversal combined with provenance-based refinement to ensure non-empty results. Third, each valid SQL query is verbalized into natural language using an LLM guided by the SQL’s abstract syntax tree (AST-ICL); the resulting questions undergo lightweight human validation to ensure clarity and correctness without full manual annotation. This fully automated approach scales to tens of thousands of queries while maintaining high quality.

## Key Results
- **Scale & expressiveness:** Supports large tables (~10k rows) and complex analytical operations (aggregation, grouping, tree-structured multi-hop).
- **Annotation quality:** 0% error rate, compared to 21–30% in prior benchmarks.
- **Model performance:** State-of-the-art models (ODYSSEY, HProPro) drop by >30 F1 points on SPARTA versus HybridQA/OTT-QA, exposing weaknesses in cross-modal reasoning.
- **Efficiency:** Annotation time reduced to one-quarter of HybridQA’s (1,493 minutes for 3,300 queries).

## Why This Works (Mechanism)

**Mechanism 1: Executable Nested SQL via Post-Order Traversal and Provenance Refinement**  
The query generator constructs nested SQL in post-order: leaf subqueries are built and validated first, then wrapped by outer predicates. If a new predicate yields an empty result, why-not provenance identifies the minimal blocking condition, and the LLM rewrites only that clause. This prevents the explosion of empty-query generations and aligns join orders with natural analyst styles. The approach reduces empty-result queries and LLM calls by over 40%.

**Mechanism 2: Unified Reference Fact Database**  
Unstructured passages are decomposed into atomic tuples stored in grounding tables, which are merged with original structured tables into a single relational store. All facts become uniformly addressable via standard SQL joins, eliminating the need for cross-modal retrieval. This simplifies the QA task to pure query execution. The unified representation is shown to be the primary cause of the >30 F1 point drop for SOTA models, as it introduces reasoning complexity absent in prior benchmarks.

**Mechanism 3: LLM-Based SQL-to-Text with Lightweight Validation**  
For each executable SQL, an LLM rewrites it into natural language using the AST as in-context exemplar (AST-ICL). The resulting question is validated by CS graduate students who check fluency and correctness without re-performing full multi-hop reasoning. This replaces full manual annotation and reduces effort by 4× compared to HybridQA while achieving high naturalness scores.

## Architecture Onboarding
- **Component map:**  
  Data Ingestion Module -> Fact Extraction Module -> Reference Fact Database -> Query Generator (Non-nested & Nested) -> SQL-to-Text Module -> Human Validation Interface -> Benchmark Packager

- **Critical path:**  
  1. Prepare source data; construct source tables (ST) and grounding tables (GT); build unified database D.  
  2. For each target query shape and depth, invoke query generator on D to produce candidate SQL.  
  3. Execute candidate SQL; if empty, trigger provenance refinement loop until non-empty.  
  4. Pass successful SQL to SQL-to-text module to generate NL question.  
  5. Human validation of (question, answer) pairs.  
  6. Deduplicate and package final benchmark.

- **Design tradeoffs:**  
  – *Scalability vs. Naturalness:* Full automation enables large scale but may yield some unnatural questions; mitigated by human validation on a random sample.  
  – *Generality vs. Domain Effort:* The framework is domain-agnostic, but each new domain requires careful schema design and fact extraction templates.  
  – *Execution Guarantee vs. Diversity:* Enforcing executability via post-order and provenance limits some query shapes but ensures all questions are answerable, trading off coverage of edge-case logical forms.

- **Failure signatures:**  
  – High empty-result rate during generation → check value diversity and join path identification.  
  – Low naturalness scores in human eval → adjust SQL-to-text prompts or model.  
  – Duplicate queries → implement result-based or structural deduplication.  
  – Unanswerable questions after validation → audit grounding tables for extraction errors.

- **First 3 experiments:**  
  1. **End-to-end smoke test:** Run full pipeline on a tiny domain (2 tables, 50 passages) to verify database construction, query generation, and verbalization.  
  2. **Provenance repair test:** Craft an impossible predicate (e.g., `salary > 100,000,000`) and confirm refinement relaxes it to return a valid, non-empty query.  
  3. **Human validation cost estimate:** Time 3 annotators validating 100 random pairs; compare to reported 1,493 minutes for 3,300 queries.

## Open Questions the Paper Calls Out
1. **Extending to images and videos** – How can multi-modal QA systems incorporate additional modalities? The paper proposes using vision–language models to summarize visuals into atomic statements but leaves the integration pipeline unexplored.  
2. **Artifacts in synthetic questions** – To what extent do automatically generated questions exhibit unnatural phrasing or template bias? Without comparative studies of human vs. synthetic distributions, model failures may reflect dataset artifacts rather than reasoning limits.  
3. **Architectural changes for analytical operations** – What modifications enable robust aggregation, grouping, and deep tree-structured reasoning? The severe performance drop indicates fundamental weaknesses but no ablations pinpoint the cause (representation, depth, numerical computation).  
4. **Retrieval-reasoning gap** – Why does performance plummet when retrieval is imperfect? The large oracle vs. retrieval gap suggests brittleness, but the paper does not dissect whether failures stem from missed tables/paragraphs or reasoning errors.  
5. **Scaling LLMs alone sufficient?** – Will next-generation LLMs close the gap, or are architectural innovations necessary? The improvement from GPT-3.5 to GPT-5 is insufficient, hinting that scaling may not resolve inherent challenges.

## Limitations
- Exact LLM prompts, temperature, and sampling parameters are undisclosed; reproduction relies on code release.  
- Generalization to domains without validated text-to-fact corpora may be limited by schema design and fact extraction noise.  
- Provenance-based refinement assumes why-not tools can identify minimal blocking predicates; it may fail on correlated subqueries or complex operators.
