# FedPS: Federated data Preprocessing via aggregated Statistics
## Quick Facts
- arXiv ID: 2602.10870
- Source URL: https://arxiv.org/abs/2602.10870
- Reference count: 35
- Primary result: Federated preprocessing improves test accuracy by up to 14 percentage points (88% vs 74%) on non-IID tabular data, with communication costs ranging from ~0.6 KB to ~61 KB per client depending on method.

## Executive Summary
FedPS tackles the overlooked problem of consistent data preprocessing in federated learning, where privacy constraints prevent data centralization and local preprocessing distorts the global distribution under non-IID data. The framework uses aggregated statistics and data‑sketching to enable communication‑efficient, consistent preprocessing across clients for common tasks like scaling, encoding, discretization, and imputation. Evaluations on tabular datasets show substantial accuracy gains—e.g., 88% vs. 78% (local) and 74% (none) on Cover with an MLP—while maintaining modest communication overhead. By decoupling preprocessing from model training, FedPS allows existing FL pipelines to incorporate reliable data preparation without sharing raw data.

## Method Summary
FedPS operates in a standard federated setting: clients compute local sufficient statistics (sums, counts, or compact sketches for quantiles/categories), the server aggregates them (summing or merging sketches), derives global parameters (e.g., means, quantile boundaries, imputation models), and broadcasts these back for uniform application. For operations that naturally require iterative refinement—such as k‑means discretization or Bayesian linear regression imputation—the process repeats for multiple rounds, with careful reformulations (e.g., aggregating XX⊤ instead of X⊤X in vertical FL) to avoid cross‑client feature sharing. The design is modular, associating each preprocessor with its required statistics and aggregation logic, and leverages data sketches to keep communication sub‑linear in data size. Empirical results confirm that consistent preprocessing significantly boosts downstream model accuracy, especially under strong heterogeneity, while communication costs scale with sketch parameters rather than raw data volume.

## Key Results
- On the Cover dataset with an MLP, federated preprocessing achieves 88% test accuracy versus 78% for local preprocessing and 74% for no preprocessing.
- Communication costs vary by method: StandardScaler ~0.6 KB/client, KBinsDiscretizer (k‑means) ~61 KB/client, matching theoretical predictions.
- Consistent preprocessing under non‑IID distributions yields large accuracy improvements across multiple tabular datasets (Adult, Bank, Cover).

## Why This Works (Mechanism)
### Mechanism 1: Consistent preprocessing via global statistics aggregation
- **Claim:** Consistent preprocessing across clients is achieved by aggregating local statistics into global parameters, preventing distribution distortion from local transformations (e.g., standardization) under non‑IID data.
- **Mechanism:** Clients compute sufficient statistics (e.g., sums, counts, sketches) locally. The server aggregates these via summation or sketch merging to compute global parameters (e.g., global mean, quantiles). These parameters are broadcasted back, ensuring all clients apply identical transformations.
- **Core assumption:** Global parameters derived from aggregated statistics accurately represent the combined data distribution, even when local distributions differ. This holds for additive statistics (mean, variance) and sketch‑based estimators with theoretical guarantees.
- **Evidence anchors:**
  - [abstract] "FedPS leverages data‑sketching techniques to efficiently summarize local datasets while preserving essential statistical information... ensure consistency... under non‑IID data distributions."
  - [section 1] "Option 4: Local preprocessing... can distort the global data distribution... Option 5: Federated preprocessing... ensures consistency."
  - [corpus] Neighbors focus on feature augmentation/adaptation, not preprocessing consistency; direct evidence is weak.
- **Break condition:** If local data distributions are extremely skewed (e.g., some clients hold outlier‑heavy subsets), aggregated statistics may not reflect the true global distribution, leading to biased preprocessing. Sketches with loose error bounds could amplify this.

### Mechanism 2: Communication efficiency via data sketches
- **Claim:** Communication efficiency is maintained by using data sketches (e.g., KLL, frequent‑item) to summarize complex statistics (quantiles, categories) instead of raw data exchange.
- **Mechanism:** For statistics that normally require full data (e.g., quantiles), clients compute compact sketches with bounded error. These sketches are merged centrally to approximate global values, drastically reducing message size.
- **Core assumption:** Sketch accuracy guarantees (e.g., additive error for KLL) hold under aggregation across heterogeneous clients, and the resulting approximation error is tolerable for downstream tasks.
- **Evidence anchors:**
  - [section 2.3] "Approximate quantile algorithms based on data sketches are therefore preferred... KLL sketch... provides additive error guarantees... both are designed to operate efficiently in distributed environments."
  - [section 3.2] Table 2 shows communication costs scale with sketch parameters (ε, δ), not data size.
  - [corpus] Neighbors discuss feature statistics but not sketching for preprocessing; evidence is paper‑specific.
- **Break condition:** For extremely high‑cardinality categorical data or very fine‑grained quantiles, sketch size may still become large, or error bounds may be insufficient for sensitive preprocessing (e.g., median imputation in skewed data).

### Mechanism 3: Federated model‑based preprocessing (Bayesian linear regression)
- **Claim:** Model‑based preprocessing (e.g., iterative imputation) is enabled via federated Bayesian linear regression, which avoids cross‑client feature interactions by reformulating sufficient statistics.
- **Mechanism:** For vertical FL, instead of aggregating X⊤X (which requires cross‑client feature products), the server aggregates XX⊤. Using the Woodbury identity, the posterior mean is computed from this aggregated matrix and broadcasted partial results, allowing clients to compute local coefficients without sharing raw features.
- **Core assumption:** The Woodbury‑based reformulation yields an exact posterior mean equivalent to centralized BLR, and the iterative refinement converges under the same conditions as centralized BLR.
- **Evidence anchors:**
  - [section 4.2] "We reformulate the posterior mean computation using an equivalent expression based on XX⊤... eliminates all cross‑client feature products."
  - [Theorem 4.2] Proof shows equivalence of the two formulations.
  - [section 5] IterativeImputer uses this variant; empirical results show improvement over no/local preprocessing.
- **Break condition:** If the XX⊤ matrix is ill‑conditioned (e.g., due to redundant features across clients), numerical instability in eigen‑decomposition could disrupt convergence. Privacy leakage risks may also arise from iterative broadcasts of derived quantities (ˆω(c)).

## Foundational Learning
- **Concept: Federated Averaging (FedAvg) workflow**
  - *Why needed here:* FedPS assumes a standard FL communication pattern (server broadcast, client upload) but applies it to preprocessing statistics instead of model gradients. Understanding FedAvg clarifies the "rounds" and "aggregation" steps.
  - *Quick check question:* In FedAvg, what is aggregated at the server? How does this differ from what FedPS aggregates?
- **Concept: Data sketching (e.g., KLL, Count‑Min)**
  - *Why needed here:* Sketches are core to FedPS's communication‑efficient quantile/frequent‑item estimation. Without them, many preprocessors would require O(n) communication.
  - *Quick check question:* What is the trade‑off between sketch size and error guarantee? How does aggregation affect these guarantees?
- **Concept: Sufficient statistics for common preprocessors**
  - *Why needed here:* FedPS's design revolves around identifying the minimal statistics (e.g., sum, sum of squares, set union) needed for each transformation. Missing this breaks the workflow.
  - *Quick check question:* What statistics does StandardScaler need? Why does KBinsDiscretizer (quantile) need a sketch instead of raw data?

## Architecture Onboarding
- **Component map:**
  1. **Client-side:** Local data loader → Statistic composer (computes sums, sketches, etc.) → Communicator (uploads stats, downloads parameters) → Local applicator (applies transformation).
  2. **Server-side:** Statistic aggregator (sums, merges sketches) → Parameter solver (computes global parameters, e.g., quantiles from merged sketch) → Broadcaster → (For iterative methods) Convergence monitor.
  3. **Shared:** Preprocessor definitions (Table 1) linking each method to its required statistics and aggregation logic.
- **Critical path:** Statistic identification → Local computation → Aggregation → Parameter derivation → Broadcast → Local application. For iterative methods (k‑Means, BLR), this loop repeats.
- **Design tradeoffs:**
  - **Accuracy vs. communication:** Sketches reduce cost but introduce approximation error (e.g., quantile error ε affects bin edges).
  - **One‑shot vs. iterative:** Simple scalers (StandardScaler) need one round; k‑Means/BLR need multiple rounds, increasing latency.
  - **Horizontal vs. vertical:** Vertical requires careful reformulation (e.g., BLR's XX⊤) to avoid cross‑client feature sharing. This adds complexity but enables feature‑partitioned FL.
- **Failure signatures:**
  - **Sketch overflow:** If distinct categories/quantiles exceed sketch capacity, accuracy degrades silently.
  - **Non‑convergence in iterative methods:** If local data is too heterogeneous, federated k‑Means or BLR may not converge within t iterations.
  - **Mismatched statistics:** If a client computes wrong statistics (e.g., forgets to count missing values), global parameters become invalid.
- **First 3 experiments:**
  1. **StandardScaler:** Run on a synthetic horizontal dataset with known global mean/variance. Verify aggregated parameters match centralized version. Check communication cost matches O(m).
  2. **OrdinalEncoder:** Run on a dataset with categorical features. Verify global category mapping is identical across clients. Test with a frequent‑item sketch to ignore rare categories.
  3. **KNNImputer (horizontal):** Introduce missing values. Verify that the global nearest neighbors used for imputation are consistent across clients. Measure how communication cost scales with test set size n′ and k.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can FedPS incorporate rigorous privacy‑preserving techniques (e.g., secure multi‑party computation, differential privacy) for complex statistics like quantiles and iterative model‑based imputation without sacrificing accuracy or incurring prohibitive communication overhead?
- **Basis in paper:** [explicit] The authors explicitly state in Section 6 that "designing private protocols for complex statistics like quantiles requires careful consideration of trade‑offs between latency, privacy, accuracy, and communication cost" and that "due to these complexities, we leave privacy‑preserving preprocessing for future work."
- **Why unresolved:** Current FedPS implementation does not address privacy beyond aggregation; complex statistics (e.g., quantile sketches, Bayesian linear regression iterations) may leak sensitive information, and existing secure methods for such operations are not integrated or evaluated.
- **What evidence would resolve it:** Implement and benchmark privacy‑preserving variants of quantile sketches (e.g., with differential privacy) and federated Bayesian linear regression within FedPS, measuring privacy‑accuracy‑communication trade‑offs on realistic non‑IID datasets.

### Open Question 2
- **Question:** To what extent do data sketching techniques (e.g., KLL for quantiles) maintain their theoretical error guarantees under extreme non‑IID data distributions (e.g., Dirichlet α → 0) or with a very small number of clients (e.g., < 5)?
- **Basis in paper:** [inferred] The paper asserts in Section 3.1 that "quantile and frequent‑item sketches maintain theoretical guarantees regardless of local distribution differences," but empirical evaluation uses α = 0.5 and a fixed number of clients (20 in simulation), leaving more extreme scenarios untested.
- **Why unresolved:** Sketches like KLL assume sufficient data samples for accurate merge; under severe skew or few clients, sketch errors could compound, leading to inconsistent preprocessing parameters that degrade model performance, as hinted by the non‑IID results where local preprocessing harmed accuracy.
- **What evidence would resolve it:** Conduct controlled experiments varying Dirichlet α and number of clients, measuring the error in aggregated quantiles versus centralized baselines, and correlating this with downstream task accuracy (e.g., using KBinsDiscretizer).

### Open Question 3
- **Question:** Can the FedPS framework be extended beyond tabular data to support preprocessing operations for other data modalities (e.g., image whitening, text n‑gram extraction, time‑series windowing) without fundamental changes to its aggregated statistics paradigm?
- **Basis in paper:** [inferred] The paper exclusively focuses on tabular data and column‑wise operations (e.g., scaling per feature, encoding categories). All examples and evaluations are on tabular datasets (Adult, Bank, Cover), and preprocessing methods are feature‑agnostic, assuming independence across columns—an assumption that may not hold for images or text.
- **Why unresolved:** Operations like image normalization across pixels or sequence‑based transformations require cross‑feature dependencies or spatial considerations that do not decompose into simple per‑feature statistics; FedPS’s current design does not address such cases.
- **What evidence would resolve it:** Adapt FedPS to a non‑tabular domain (e.g., federated preprocessing of image datasets using PCA or ZCA whitening), define appropriate sufficient statistics that can be aggregated, and evaluate consistency and communication costs against local preprocessing baselines.

### Open Question 4
- **Question:** What communication‑efficient algorithms or approximations can reduce the high overhead of iterative preprocessing methods like `IterativeImputer` (which incurs O(t m² min(n, m)) per client in horizontal FL) while preserving imputation quality?
- **Basis in paper:** [inferred] Table 2 and Table 5 highlight that iterative methods such as `KBinsDiscretizer` with k‑means and `IterativeImputer` have substantially higher communication costs (e.g., ~61 KB and ~25 KB per client respectively) compared to simple scalers (~0.6 KB). The analysis shows costs scale with iterations t and feature count m, posing scalability issues.
- **Why unresolved:** The current implementation relies on exact federated Bayesian linear regression per iteration, which aggregates dense matrices (X⊤X or XX⊤). In high‑dimensional settings (large m), this becomes a bottleneck, and no compression or early‑stopping strategies are explored.
- **What evidence would resolve it:** Propose and test variants such as randomized sketching of sufficient statistics, early termination of BLR iterations, or approximate iterative schemes; evaluate imputation accuracy versus communication savings on larger feature datasets.

## Limitations
- Evaluation restricted to tabular datasets; generalizability to images, text, or high‑dimensional data is unknown.
- Impact of sketch approximation error on downstream model accuracy is not quantified, especially for high‑cardinality categories or fine‑grained quantiles.
- Privacy risks of sharing aggregated statistics and sketches remain unanalyzed (e.g., membership inference).
