# Learning to Repair Lean Proofs from Compiler Feedback
## Quick Facts
- **arXiv ID:** 2602.02990
- **Source URL:** https://arxiv.org/abs/2602.02990
- **Reference count:** 11
- **Primary result:** Finetuning a 4B-parameter model on a synthetically generated repair dataset yields a 25× improvement in single-shot proof repair accuracy (27.4%) over its base version and slightly exceeds a 32B baseline.

## Executive Summary
This paper introduces a method to learn automated repair of Lean 4 proofs from compiler feedback. It addresses the scarcity of supervised error-repair data by constructing the APRIL dataset, which contains over 260k failing proof variants generated via systematic mutations of correct proofs. Each example pairs an erroneous proof with Lean's diagnostic output and a human-readable explanation. Models finetuned on this data learn to perform single-shot proof repair conditioned on the error. A 4B-parameter model finetuned on APRIL achieves 27.4% repair accuracy, a 25× gain over its base version and a modest win over a 32B model, demonstrating the value of targeted, feedback-conditioned training. Performance varies significantly by error type, with tactic-based errors being easiest to fix and line-insertion errors hardest. An ablation reveals a trade-off: training without explanation generation improves pure repair accuracy to 31.2%, suggesting explanations provide utility but compete with the primary repair objective.

## Method Summary
The core method is a pipeline for synthetic supervised data generation and model finetuning. First, a large corpus of verified correct Lean proofs is collected from existing sources (Herald, Workbook, NuminaMath–Lean). Four mutation operators are applied to produce failing variants: theorem substitution, tactic replacement, line mutation, and multi-line mutation. Each mutated proof is compiled to capture the exact error message and local goal state from Lean. A separate LLM (DeepSeek-V3) is then prompted to generate a natural-language explanation of the error and a suggested fix, resulting in a structured (input: erroneous proof + diagnostics; target: corrected proof + explanation) tuple. This corpus, APRIL, is used to finetune instruction-tuned base LLMs (e.g., Qwen3-4B-Instruct) via LoRA. The model is trained in a chat format to generate either just the corrected proof or a diagnosis followed by the corrected proof. Evaluation is performed in a single-shot, no-search setting: the model receives the error and failing proof and must output a proof that compiles successfully under Lean 4.22.0-rc4.

## Key Results
- A Qwen3-4B-Instruct model finetuned on APRIL achieves **27.4%** repair accuracy, a **25× improvement** over its base version (1.1%) and **slightly exceeding** the 32B Goedel-Prover-V2 baseline (26.8%).
- Repair performance is highly error-type dependent: tactic mutations (~40%), theorem substitutions (~27%), and line/multi-line mutations (~13-16%) show a clear difficulty gradient.
- An ablation shows that training **without explanation generation increases pure repair accuracy** to 31.2%, confirming a trade-off between autonomous repair performance and the generation of human-interpretable diagnoses.

## Why This Works (Mechanism)
### Mechanism 1
Systematic mutation of correct proofs creates a large-scale supervised corpus for learning feedback-conditioned repair, addressing the scarcity of real error trajectories. Begin with verified correct proofs, apply controlled perturbations to generate failing variants, and pair each with the original correct version, the Lean compiler's diagnostic output, and an LLM-generated natural-language explanation. This transforms an unsupervised failure into a supervised (input: error+feedback, target: repair+diagnosis) tuple. The core assumption is that errors generated by these precise, localized mutations are sufficiently similar in nature to errors arising during human proof development. Evidence: The APRIL dataset construction is explicitly described in the abstract and Section 3.1. Break condition: If the synthetic error distribution diverges significantly from natural errors (e.g., being systematically easier or requiring different reasoning), the learned repair policy may not transfer to real-world interactive proof construction.

### Mechanism 2
Jointly training on both proof repair and natural-language explanation generation yields a model that improves at feedback-conditioned reasoning; the explanation objective provides a regularizing signal that enhances the model's internal representation of the error's cause. The supervised target concatenates a natural-language diagnosis with the corrected Lean code, forcing the model to first interpret the compiler feedback and contrast it with the failing proof to generate a coherent explanation, which may scaffold subsequent code generation. The core assumption is that generating a human-interpretable diagnosis forces the model to build an explicit, grounded model of *why* the proof failed, which is a prerequisite for generating a targeted correction. Evidence: Section 5.3 ablation shows removing explanation training increases pure repair accuracy (27.4% → 31.2%), indicating a trade-off. However, the explanation-trained model's outputs can be used to augment another model's input (DeepSeek's success rate jumps from 4% to 29% with better explanations), proving the explanations are grounded and useful. Break condition: If the explanatory signal distracts from the primary repair objective or if the LLM-generated explanations are low-quality, joint training could degrade repair performance without providing downstream utility.

### Mechanism 3
Repair performance is highly sensitive to the *type* and *locality* of the error; models learn distinct repair heuristics for different mutation-induced failure modes, with more local, syntactic errors (tactics) being easier to fix than semantic, structural errors (line insertions). The mutation pipeline creates error categories with varying "repair distance" and required reasoning depth. Tactic swaps are local within a known tactic class. Theorem substitutions create semantic mismatches that may manifest later. Line/multi-line mutations require generating missing or incorrect code from context, demanding broader state understanding. A model trained on all types must develop mechanisms to identify the error category from the diagnostic and apply the appropriate repair strategy. The core assumption is that the model can implicitly classify the error type from the compiler message and local proof state. Evidence: Section 5.2 reports tactic mutations yield the highest repair rates (~40%), theorem mutations intermediate (~27%), and line mutations most challenging (~13-16%). Models trained jointly on the full dataset maintain strong performance across individual categories. Break condition: If error types are not cleanly separable by the model (e.g., a complex theorem substitution produces a diagnostic indistinguishable from a multi-line hallucination), the model's strategy may fail catastrophically on ambiguous cases.

## Foundational Learning
- **Concept: Formal Verification & Proof State (Lean 4)**
  - **Why needed:** The entire task operates within Lean's elaboration model. The "local proof state" (goals, hypotheses) is a primary input. A learner must understand what a "goal" is, how tactics transform it, and how Lean reports errors.
  - **Quick check:** Given the goal `n : Nat ⊢ n + 0 = n` and the tactic `rw [add_comm]`, what is the new goal? What error would `rw [mul_comm]` produce?
- **Concept: Compiler Diagnostics as Structured Signals**
  - **Why needed:** The model's input includes Lean's raw error message and Infoview state. A learner must parse that "unknown identifier 'foo'" implies a missing definition, while "type mismatch at ..." implies a term of wrong type was provided.
  - **Quick check:** For the failing line `apply h` with error "failed to apply, is not an append? ...", what is the most likely mismatch between the goal and `h`'s type?
- **Concept: Mutation-Based Synthetic Data Generation**
  - **Why needed:** The paper's core method is to *create* the training signal. A learner must grasp why real error data is absent, and how systematic, deterministic mutations (with compiler validation) can produce plausible, integrable failure cases at scale.
  - **Quick check:** If you randomly replace `linarith` with `ring` in a goal involving inequalities, will the error be a syntax error or a failure to prove? Why is this a "plausible" error?
- **Concept: Low-Rank Adaptation (LoRA) for Efficient Finetuning**
  - **Why needed:** Finetuning 4B-parameter models on a large dataset is computationally intensive. LoRA allows efficient adaptation by training low-rank matrices on top of frozen weights, making the experiment accessible with moderate hardware.
  - **Quick check:** Why might applying LoRA only to attention and MLP projection layers be sufficient for learning the repair task, rather than all parameter types?
- **Concept: Single-Shot vs. Search-Based Evaluation**
  - **Why needed:** The paper evaluates in a strict single-shot setting (no iterative compiler feedback). This isolates the model's inherent repair capability from the gains provided by search or multiple attempts, which are orthogonal.
  - **Quick check:** How would the reported accuracy likely change if the model were allowed 5 generation attempts per example (pass@5) instead of 1 (pass@1)?

## Architecture Onboarding
**Component map:** Correct Proof Sources -> Mutation Scripts -> Lean Compiler (Lean-Interact) -> Error Filtering -> LLM Explanation Generation -> APRIL Dataset -> Base LLM -> LoRA Finetuning -> Finetuned Model -> Evaluation Harness (Lean Compiler)

**Critical path:** Mutation -> Compilation -> Explanation -> Finetuning -> Evaluation. The most fragile step is **mutation**, as it must produce *valid*, *failing* Lean code that is also *structurally similar* to the original. A broken mutation script yields meaningless data.

**Design tradeoffs:**
- **Synthetic vs. Natural Errors:** Mutations guarantee scale and control but may lack the complexity and diversity of human-introduced bugs.
- **Joint vs. Separate Objectives:** Joint training (repair+explanation) yields interpretable outputs but slightly lower raw repair accuracy (27.4% vs 31.2%).
- **Model Size:** A 4B model finetuned on APRIL outperforms a 32B base model (26.8%), suggesting data quality and task-specific training outweigh raw parameter count.

**Failure signatures:**
- **Data-level:** Low mutation yield rate (many mutations still compile). Poorly generated explanations (non-JSON, empty fields).
- **Training-level:** No improvement over baseline (<10% gain). Overfitting (val loss rises while train loss falls).
- **Evaluation-level:** Disparity between error types; especially low line/multi-line repair (<15%) indicates a gap in the model's generative capability for missing code.

**First 3 experiments:**
1. **Replicate mutation yield:** Run the mutation code on a small subset (e.g., 100 correct proofs). Verify you get ~5-10x failing variants and that the error type distribution roughly matches the paper's (Theorem~60%, Tactic~24%, etc.).
2. **Smoke-test finetuning:** Finetune a small model (e.g., Kimina-1.7B) on a 1,000-sample subset for 100 steps. Confirm validation loss decreases and the model begins to output syntactically valid Lean (even if incorrect).
3. **Error-type sanity check:** Evaluate your finetuned model on a held-out set of *only* tactic mutations. Expect >30% accuracy (per Table 2). If it's <10%, your training data or format is likely flawed.

## Open Questions the Paper Calls Out
### Open Question 1
Why does joint supervision with natural-language explanations reduce pure repair accuracy (from 31.2% to 27.4%) compared to training repair alone? The paper does not investigate whether explanations introduce conflicting objectives, distraction, or greater sample complexity, leaving the cause of the performance drop unclear.

### Open Question 2
How well do models trained on synthetically generated mutation errors generalize to naturally occurring proof failures encountered by human mathematicians? The paper does not evaluate on any held-out set of genuine human proof errors, so it is unknown whether the repair skills transfer beyond the curated mutation types.

### Open Question 3
What specific factors make line mutation errors substantially harder to repair (max 13.5% accuracy) compared to tactic or theorem mutations (up to 42.5%)? The paper shows the performance gap but does not analyze whether the difficulty stems from lack of local context, goal-state complexity, or the nature of the generated faulty lines.

### Open Question 4
Can incorporating iterative search or feedback loops at inference time improve repair accuracy beyond the current single-shot evaluation setting? The paper does not test whether the trained repair models can leverage multiple attempts or compiler feedback in a loop, leaving open whether single-shot performance is a lower bound.

## Limitations
- **Synthetic error fidelity:** Mutated proofs may not match the complexity and diversity of natural human errors, risking limited transfer to real-world interactive repair.
- **Explanation quality:** LLM-generated diagnoses are unvalidated; they could be plausible yet incorrect, potentially misleading the repair model.
- **Prompt/template sensitivity:** Undocumented formatting choices create replication fragility; minor deviations may degrade performance.

## Confidence
- **Cluster A (APRIL dataset enables large repair gain):** **High** – Direct evidence: 25× improvement over base model (1.1% → 27.4%) and surpassing a 32B baseline.
- **Cluster B (Joint training trade-off):** **High** – Ablation shows repair accuracy drops from 31.2% (repair-only) to 27.4% (with explanations).
- **Cluster C (Error-type sensitivity):** **High** – Reported per-category accuracies (tactic ~40%, theorem ~27%, line ~13-16%) are consistent across models.
- **Cluster D (Synthetic errors generalize to natural errors):** **Low** – No validation that repair performance on mutated proofs transfers to genuinely user-introduced errors.
- **Cluster E (Generated explanations are useful):** **Medium** – Downstream experiment (DeepSeek success rate jump) suggests utility, but lacks human evaluation or error analysis.

## Next Checks
1. **Distribution alignment study:** Compile a corpus of real Lean proof errors (e.g., from mathlib CI or student submissions) and compare diagnostic distributions (error types, message n-grams) to APRIL’s synthetic errors using statistical divergences.
2. **Explanation fidelity audit:** Manually evaluate a random sample of generated explanations for correctness and grounding relative to the code change; correlate explanation quality with repair success on a held-out set.
3. **Interactive repair benchmark:** Deploy the finetuned model in a Lean IDE plugin and measure repair accuracy on naturally failing proofs from active developers, comparing results to the synthetic test set to quantify generalization gap.
