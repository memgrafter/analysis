# Cost Trade-offs in Matrix Inversion Updates for Streaming Outlier Detection

## Quick Facts

- **arXiv ID:** 2603.16697  
- **Source URL:** https://arxiv.org/abs/2603.16697  
- **Reference count:** 18  
- **Primary result:** A practical rule for Python implementations: use ISM for rank‑1 updates (*k*=1), WMI for small updates (*k* ≤ *s*/3, where *s* is matrix dimension), and DI for large updates (*k* > *s*/3); ISM suffers numerical instability for large *k*.

## Executive Summary

This paper studies the problem of efficiently updating the inverse of a symmetric positive definite matrix after a rank‑*k* update, a core operation in streaming outlier detection based on the Christoffel function. The authors compare three methods—Direct Inversion (DI), Iterative Sherman‑Morrison (ISM), and Woodbury Matrix Identity (WMI)—both theoretically (floating‑point operation counts) and empirically (Python CPU simulations). Key findings reveal that implementation‑specific factors (memory access patterns, BLAS optimizations) cause substantial deviations from theoretical predictions. A practical selection rule emerges: for *k*=1, use ISM; for *k* ≤ *s*/3, use WMI; for *k* > *s*/3, use DI. Additionally, ISM suffers from numerical instability for large *k*, while WMI and DI remain stable. These results provide actionable guidance for matrix inversion updates in streaming applications.

## Method Summary

The paper evaluates three algorithms for updating the inverse of a symmetric positive definite moment matrix *M* (size *s* × *s*) after a rank‑*k* update, as required in online Christoffel‑function‑based outlier detection. The algorithms are: Direct Inversion (DI), which recomputes the inverse from scratch; Iterative Sherman‑Morrison (ISM), which applies the Sherman‑Morrison rank‑one update formula *k* times; and Woodbury Matrix Identity (WMI), which uses a single matrix identity to incorporate all *k* updates at once. Theoretical floating‑point operation (flop) counts are derived for each method. Empirical validation uses synthetic data (ambient dimension *d*=8, polynomial degree *n*=5, feature dimension *s*=1287, total samples *S*=2000) with Python’s NumPy/SciPy on an Intel CPU. The update’s correctness is assessed via Frobenius norm error against a ground‑truth inverse recomputed via full inversion. The primary outcome is a practical method selection rule based on the update rank *k* relative to the matrix dimension *s*, with the observation that implementation efficiencies significantly alter performance relative to pure flop predictions.

## Key Results

- A practical selection rule: ISM for *k*=1, WMI for *k* ≤ *s*/3, DI for *k* > *s*/3.
- Implementation factors (memory access, BLAS) cause WMI to outperform ISM for small *k* > 1 despite higher theoretical flop count.
- ISM accumulates floating‑point errors for large *k*; WMI and DI maintain machine‑precision stability.

## Why This Works (Mechanism)

The discrepancy between theoretical flop counts and actual runtime in Python arises because flop counts consider only arithmetic operations, while actual performance is dominated by memory access patterns and BLAS library optimizations. ISM’s iterative vector operations incur Python‑level loop overhead and poor cache utilization, whereas WMI’s dense matrix operations leverage highly optimized BLAS kernels. This explains why WMI, though theoretically more expensive for small *k*, often runs faster in practice; the crossover thresholds derived from flop counts are far off (e.g., ISM threshold overestimated 535 vs. 10–20). Different programming languages or hardware (C++, GPU) would shift these thresholds due to changed overhead profiles.

The relative size of the update rank *k* to the matrix dimension *s* determines the optimal method. WMI’s cost includes a cubic term *O*(*k*³) from inverting a *k*×*k* matrix; once *k* exceeds roughly *s*/3, DI’s fixed *O*(*s*³) cost becomes lower. Theoretical flop formulas yield an inequality that solves to *k* ≈ *s*/3.7506, which the authors round to *s*/3. However, for very small *s* (e.g., *s*=10) DI may dominate even at *k*=1 due to constant factors, showing that the rule’s boundaries depend on parameter regime.

ISM’s numerical instability stems from cumulative rounding errors. Each Sherman‑Morrison update introduces small inaccuracies in division and subtraction; after *k* iterations, these errors compound. By contrast, WMI and DI perform a single inversion step, avoiding accumulation. Empirical results confirm ISM’s error grows dramatically (e.g., ~5.9 × 10¹⁰ for *k*=750) while DI/WMI stay near machine epsilon (~10⁻¹³). Ill‑conditioning of *M* exacerbates ISM’s errors, potentially making it unusable for moderate *k*.

## Foundational Learning

**Symmetric Positive Definite (SPD) matrices and Cholesky decomposition**  
*Why needed:* The moment matrix *M* is SPD, guaranteeing invertibility and enabling efficient Cholesky‑based inversion (cost *O*(*s*³/5) vs. *O*(2*s*³) for LU). DI and WMI both rely on inverting SPD submatrices.  
*Quick check:* If *M* were not SPD, would the Woodbury identity still apply? (Answer: Yes, but inversion costs might increase if special structure is lost.)

**Floating‑point operation (flop) counting**  
*Why needed:* The theoretical comparison (Table 1) uses flop counts to predict computational cost. Flops provide a hardware‑agnostic metric for arithmetic intensity.  
*Quick check:* Why do flop counts diverge from actual runtime in Python? (Answer: Because flops count only arithmetic operations, while runtime is heavily influenced by memory access patterns and BLAS library optimizations.)

**Streaming data and rank‑*k* updates**  
*Why needed:* In online outlier detection, new data points arrive in batches of size *k*, leading to a rank‑*k* update: *M*<sub>new</sub> = *M* + ∑<sub>*i*=1</sub><sup>*k*</sup>*v*(*x*<sub>*i*</sub>)*v*(*x*<sub>*i*</sub>)<sup>⊤</sup>. Efficiently updating *M*<sup>−1</sup> avoids full recomputation, reducing latency.  
*Quick check:* Why not just recompute *M*<sup>−1</sup> from scratch after each batch? (Answer: Full inversion is *O*(*s*³), while updates can be cheaper for small *k*, e.g., ISM is *O*(*k**s*²).)

## Architecture Onboarding

**Component map**: Data stream → batch of *k* new points {*x*<sub>*i*</sub>} → compute feature vectors *v*<sub>*n*</sub>(*x*<sub>*i*</sub>) → design matrix *X* (*k*×*s*) with rows *v*<sub>*n*</sub>(*x*<sub>*i*</sub>)<sup>⊤</sup> → update inverse using DI/ISM/WMI → Christoffel scoring (*v*<sub>*n*</sub>(*x*)<sup>⊤</sup>*M*<sup>−1</sup>*v*<sub>*n*</sub>(*x*)) → outlier decision (score ≥ threshold).  
**Critical path**: The inverse update step (fourth component) is the computational bottleneck; optimizing it directly impacts streaming latency.  
**Design tradeoffs**:  
- Theoretical flop vs empirical runtime: WMI may have higher flops than ISM for small *k* but runs faster due to vectorized BLAS operations.  
- Stability vs speed: ISM is fastest for *k*=1 but unstable for large *k*; DI is stable but slower for small *k*.  
- Memory vs computation: WMI needs to store *X* (*k*×*s*) and invert a *k*×*k* matrix; for large *k* memory may become limiting.  
**Failure signatures**:  
- ISM: Sudden increase in Frobenius norm error ‖*I* − *M*<sub>updated</sub> * *M*<sub>updated</sub><sup>−1</sup>‖<sub>*F*</sub> as *k* grows; condition number of *M* spikes.  
- WMI: Runtime curve crosses DI around *k* = *s*/3; beyond that WMI becomes slower.  
- DI: Consistently stable but may be suboptimal for small *k*; high memory usage for large *s*.  
**First experiments**:  
1. Timing benchmark: For a fixed *s* (e.g., 1287), measure execution time of each method across *k* ∈ {1,2,3,4,5,10,20,30,40,50,100,200,300,400,500,750,1000}. Expect ISM fastest at *k*=1, WMI fastest for 2≤*k*≤*s*/3, DI fastest for *k*>*s*/3.  
2. Stability test: For increasing *k*, compute error ‖*I* − *M*<sub>updated</sub> * *M*<sub>true</sub><sup>−1</sup>‖<sub>*F*</sub> where *M*<sub>true</sub><sup>−1</sup> is from a full recomputation. Observe ISM error grows rapidly while DI/WMI stay near 10<sup>‑13</sup>.  
3. Threshold validation: Vary *s* (e.g., 50, 100, 500, 1000) and find the empirical *k* where DI overtakes WMI. Confirm the crossover scales approximately linearly with *s* (*k* ≈ *s*/3) across tested *s*.

## Open Questions the Paper Calls Out

1. **Platform generalizability:** How do the relative performance and numerical stability of DI, ISM, and WMI change when implemented on different computational platforms (e.g., C++ with optimized BLAS, GPU‑accelerated libraries) compared to Python CPU? The authors explicitly suggest extending the empirical comparison to other languages and environments.  
2. **Dimensionality reduction:** What techniques can be applied to the moment matrix in Christoffel‑function‑based outlier detection to maintain accuracy while reducing computational cost in high‑dimensional data streams? The combinatorial growth of *s* = *C*(*d*+*n*,*n*) with ambient dimension *d* makes this a fundamental limitation.  
3. **Stabilizing ISM:** Can the Iterative Sherman‑Morrison algorithm be modified to prevent error accumulation during large rank updates (*k* > 50) while retaining reasonable computational efficiency? The paper shows ISM becomes highly unstable for *k* > 1 but offers no stabilization.  
4. **WMI vs. ISM empirical behavior:** Why does Woodbury Matrix Identity empirically outperform Iterative Sherman‑Morrison for rank updates *k* > 1 despite a higher theoretical flop count? The paper attributes this to memory access and library optimizations but lacks a detailed analysis.

## Limitations

- **Hardware/software specifics:** Experiments used a single Intel CPU with unspecified NumPy/BLAS defaults; thresholds may shift with different BLAS implementations, threading, or GPU acceleration.  
- **Parameter regime:** Only one matrix size (*s*=1287) was studied systematically; for very small *s* (<100) DI may outperform ISM even at *k*=1, and for very large *s* memory‑bandwidth effects could alter the *s*/3 rule.  
- **Stability envelope:** ISM instability was shown on synthetic data with moderate condition numbers; real‑world streaming matrices may be far more ill‑conditioned, causing earlier failure; the safe *k* as a function of condition number remains unknown.
