# ESAA: Event Sourcing for Autonomous Agents in LLM-Based Software Engineering

## Quick Facts
- arXiv ID: 2602.23193
- Source URL: https://arxiv.org/abs/2602.23193
- Reference count: 21
- Primary result: Event sourcing enables auditability and deterministic replay for LLM agents, yielding zero rejects and successful verification in case studies with both single and concurrent multi-agent setups.

## Executive Summary
ESAA introduces an event-sourcing framework to address critical vulnerabilities in LLM-based autonomous software engineering agents: lack of native state, context degradation, and probabilistic-deterministic gaps. Agents emit structured JSON intentions under contracts; a deterministic orchestrator validates these, appends events to an append-only log (`activity.jsonl`), applies file effects, and projects a read-model (`roadmap.json`) with SHA-256 hashing for replay verification. Case studies demonstrate successful runs with zero rejections and verifiable state reconstruction, even under concurrent multi-agent orchestration.

## Method Summary
Reproducing ESAA requires implementing the orchestrator and associated contracts. The core workflow: initialize an event log with a `run.init` event; iteratively process task claims by having agents produce JSON outputs compliant with the provided schema; validate each output against boundary contracts; upon validity, append the event to `activity.jsonl`, apply associated file patches, and update the task state in `roadmap.json`. Verification is performed by replaying all events, recomputing the projection hash via a deterministic canonicalization function, and comparing to the stored hash. Key missing artifacts include the exact boundary contracts (`AGENT_CONTRACT.yaml`, `ORCHESTRATOR_CONTRACT.yaml`) and PARCER metaprompting profiles, which are central to enforcement but not provided in the paper.

## Key Results
- Single-agent landing page: 9 tasks, 49 events, run.success, verify.ok, zero rejects.
- Multi-agent clinical dashboard: 50 tasks, 86 events, 4 concurrent agents over 8 phases, run.success, verify.ok (31/50 done), zero rejects.
- Scalability evidenced by 6 concurrent claims recorded within one minute, demonstrating effective coordination via the append-only log.

## Why This Works (Mechanism)
ESAA’s effectiveness rests on three interconnected mechanisms:

1. **Immutable event log provides audit trail and deterministic replay**  
   Agent intentions are converted into events and appended to `activity.jsonl` before any irreversible file effects. The current state (`roadmap.json`) is derived by applying a deterministic projection function over the entire event sequence, enabling complete reconstruction from the log. Core assumption: the projection function is pure and deterministic. Evidence: abstract and Section 3.2 describe the trace-first model; Section 3.3 uses SHA-256 to detect divergence. Break condition: missing or reordered events cause incorrect replay.

2. **Constrained JSON output with boundary contracts**  
   Agents operate under contracts (`AGENT_CONTRACT.yaml`) and metaprompting profiles (`PARCER`) that enforce a strict JSON envelope with only `agent.result` or `issue.report`. The orchestrator validates each payload against the JSON Schema; invalid outputs are rejected as `output.rejected`, preventing malformed intentions from entering the log. Core assumption: LLMs can reliably produce syntactically correct JSON under explicit constraints. Evidence: abstract and Section 3.1; Section 6.1 reports zero rejects. Break condition: repeated contract violations halt progress.

3. **Append-only event store coordinates concurrent workflows**  
   Multiple agents work in parallel; the orchestrator serializes acceptance by appending events sequentially to `activity.jsonl`. Total ordering determines effect application order and records responsible agents, enabling conflict detection. Core assumption: conflicts are rare enough that sequential appends are not a bottleneck. Evidence: abstract; Section 3.4 and 5.2.3 note six claims in one minute. Break condition: high contention leads to bottlenecks or indefinite blocking.

## Foundational Learning
- **Concept: Event Sourcing**  
  *Why needed*: Makes the event log the single source of truth, enabling replay, audit, and reconstruction without agent-side memory.  
  *Quick check*: In event sourcing, what is the difference between an event (a fact that has happened) and a command (an intention to change state)?

- **Concept: JSON Schema Validation / Structured Output**  
  *Why needed*: Ensures agent outputs are valid before entering the event store, preventing invalid state transitions and enabling deterministic processing.  
  *Quick check*: Which fields are required in the agent output contract JSON according to the schema in Appendix A?

- **Concept: CQRS / Deterministic Projection**  
  *Why needed*: Separates write model (events) from read model (`roadmap.json`), ensuring replay produces identical state, critical for verification.  
  *Quick check*: How does the `projection_hash_sha256` field help detect divergence between the current read model and a replayed state?

## Architecture Onboarding
- **Component map**  
  .roadmap/activity.jsonl (append-only event log) → orchestrator → .roadmap/roadmap.json (materialized view with projection hash)  
  Orchestrator ← AGENT_CONTRACT.yaml, ORCHESTRATOR_CONTRACT.yaml, PARCER_PROFILE.*.yaml (enforcement)  
  Orchestrator → file system (src/, .roadmap/specs/) for patch application  
  Event vocabulary defines allowed event types (claim, complete, promote, etc.)

- **Critical path** (run start to verification):  
  run.init → task.create → promote → claim → orchestrator.dispatch → agent result validation → event append → orchestrator.file.write → task.update → phase.complete → esaa verify (replay, hash compare) → run.end.

- **Design tradeoffs**  
  Overhead vs benefit: added 200–500 tokens/sub-second validation is marginal vs LLM cost.  
  Log granularity: simplified vocabulary reduces verbosity but omits low-level details; full vocabulary increases traceability.  
  Concurrency: serialized appends simplify conflict detection but limit throughput under high contention; conflicts resolved post-hoc.  
  Security: agent sandboxing reduces blast radius, but orchestrator becomes privileged and must remain deterministic.  
  Replay determinism: relies on canonical JSON and stable projection; algorithm changes invalidate historical hashes.

- **Failure signatures**  
  output.rejected events indicate contract/schema violations.  
  attempt.timeout signals agent unresponsiveness.  
  verify.fail or projection_hash_sha256 mismatch shows divergence/log corruption.  
  Gaps/duplicates in event_seq suggest log integrity issues.  
  Tasks lingering in in_progress indicate agent failure/deadlock.  
  Conflicting file modifications during replay reveal concurrency issues.  
  Orchestrator exceptions during validation or file writing.

- **First 3 experiments**  
  1. Initialize and verify baseline: run `esaa init`; ensure activity.jsonl has only run.init; check roadmap.json status and hash; run `esaa verify` for verify.ok.  
  2. Single-task completion: select a simple task; observe claim→complete sequence; inspect file changes and roadmap update; confirm fresh verify is ok.  
  3. Induce verification failure: tamper with a source file or alter stored hash; run `esaa verify` to see verify.fail; restore state via replay.

## Open Questions the Paper Calls Out
- **Open Question 1**: How does ESAA scale to large, complex enterprise repositories and benchmarks like SWE-bench? Future work calls for systematic evaluation; current case studies are limited.
- **Open Question 2**: What conflict detection and resolution mechanisms are needed for concurrent agents modifying the same resources? Serialization defers resolution; a formal policy and validation under contention are required.
- **Open Question 3**: Does ESAA improve end-to-end software quality metrics (test pass rate, maintainability, security) compared to conventional agent workflows? Evaluation focuses on orchestration success, not quality; a controlled study is needed.
- **Open Question 4**: Can orchestrator invariants be formally verified? Only empirical replay verification is used; model checking or theorem proving is proposed.
- **Open Question 5**: To what extent does the "purified view" mitigate context degradation for long-horizon tasks? Claim asserted without comparative experimentation; an ablation study is required.

## Limitations
- Missing boundary contracts and PARCER profiles, central to enforcement but not provided.
- No raw event logs for case studies; only aggregated metrics prevent independent replay verification.
- Scalability claims based on minimal concurrent activity; no stress tests with high contention.

## Confidence
- Mechanism 1 (immutable audit trail): Medium. Supported by architecture and zero rejects, but lacks independent replication.
- Mechanism 2 (JSON contracts): Medium. Zero rejects suggest efficacy, but LLM compliance under diverse prompts is not robustly evidenced.
- Mechanism 3 (concurrency coordination): Low. Anecdotal evidence; no quantitative throughput or conflict data.
- Overall: Major uncertainties remain due to missing enforcement artifacts and limited scalability validation.
