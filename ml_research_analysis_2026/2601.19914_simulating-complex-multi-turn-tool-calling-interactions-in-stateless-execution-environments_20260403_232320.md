# Simulating Complex Multi-Turn Tool Calling Interactions in Stateless Execution Environments

## Quick Facts
- **arXiv ID**: 2601.19914  
- **Source URL**: https://arxiv.org/abs/2601.19914  
- **Reference count**: 40  
- **One-line primary result**: DiGiT-TC generates synthetic multi-turn tool calling data without stateful execution; a Llama3.1‑8B model trained on it achieves 27.0% on BFCL‑v3 multi‑turn, surpassing prior open‑model approaches.

## Executive Summary
DiGiT-TC is a framework for generating synthetic multi‑turn tool‑calling conversations in stateless environments. It constructs tool call sequences as dependency graphs, hides a subset of calls as implicit, and uses back‑translation to ensure the user request implies the full plan. The resulting data trains an 8‑billion parameter model to strong performance on challenging multi‑turn benchmarks, demonstrating that carefully designed synthetic data can substitute for real multi‑turn interactions and stateful execution.

## Method Summary
The pipeline iteratively builds conversations. For each turn, it samples tools and a persona, then has an LLM generate a raw tool sequence. This sequence is converted to a directed acyclic graph (DAG); only the largest connected component is kept. The sequence is split into explicit and implicit sets, constrained so implicit calls are leaf nodes with parents. A user request is generated that mentions only explicit calls. A Kendall τb filter discards requests too similar to the plan’s argument ordering. Back‑translation checks that all original leaves appear in the plan predicted from the request. Accepted turns accumulate. After several turns, the assistant’s tool calls are simulated with an LLM, observations and a summary are inserted, and synthetic errors (clarification or tool misuse) are added. Finally, conversations are concatenated and random function/parameter names are masked before instruction fine‑tuning (LoRA) of Llama3.1‑8B‑Instruct.

## Key Results
- Llama3.1‑8B trained on DiGiT‑TC data scores 27.0% overall on BFCL‑v3 multi‑turn, outperforming prior open‑model methods and approaching frontier models.  
- Ablation study: removing implicit tool calls causes a 9% drop; removing back translation causes an 8% drop.  
- The model also achieves competitive τ²‑bench reward.

## Why This Works (Mechanism)
**Implicit tool call synthesis forces inference of hidden preparatory steps.** The pipeline first generates a full tool call sequence S (as a DAG of data dependencies). It then randomly partitions S into explicit (E) and implicit (I) sets, with I constrained to leaf nodes that have parents. The user request is written to mention only the calls in E, leaving I as implicit. Real‑world user requests often omit obvious dependencies; by embedding such implicit calls in training data, the model learns to complement user intent with necessary intermediate actions. Evidence: Section 3.2.2 (Algorithm 1) details the split; the Neighbor OrchDAG work (arxiv:2510.24663) models similar dependencies. The process fails for incoherent E or violated constraints.

**Back translation acts as a fidelity check for alignment between request and plan.** After producing a user request r, a separate LLM predicts a tool call sequence S′. The condition `leaves(S) ⊆ leaves(S′)` verifies that all terminal calls of the original sequence appear in S′. Failures discard the example; otherwise S′ is used. A valid user request should yield a complete tool plan that includes all data‑producing steps; leaf coverage is a lightweight proxy for completeness. Evidence: abstract mentions the check; Section 3.2.3 formalizes it; ablation shows an 8% drop when removed. The check fails if the request is ambiguous, the implicit calls are too complex, or the back‑translation model is weak.

**Distilling the initial sequence to its largest DAG component removes spurious calls.** The raw sequence S from the planning LLM is converted into a DAG where edges represent data dependencies. The method extracts all connected components and retains only the largest, discarding isolated or small fragments. A meaningful tool chain for a single goal should form a single connected graph; disconnected calls are likely noise. Evidence: Section 3.2.1 describes the distillation; Figure 4 shows an example. The heuristic may arbitrarily drop valid sub‑plans if multiple equal‑sized components exist.

## Foundational Learning
- **Tool Calling (Function Calling)**  
  *Why needed*: The framework generates assistant messages that are structured tool invocations. Understanding tool specifications, arguments, and inter‑tool references (e.g., `$1.output`) is essential.  
  *Quick check*: “How does an LLM indicate a dependency on a previous tool’s output in a multi‑turn conversation?”

- **Directed Acyclic Graph (DAG) Representation**  
  *Why needed*: DiGiT‑TC uses DAGs to model dependencies, perform plan distillation, and select implicit calls. Without grasping roots, leaves, and connected components, the technical description is opaque.  
  *Quick check*: “In a tool‑call DAG, what defines a leaf node, and why are leaves critical for the back‑translation check?”

- **Synthetic Data Generation with Verification Loops**  
  *Why needed*: The method is a multi‑stage pipeline where each stage adds noise or filters it. Appreciating the need for quality control (back translation, Kendall τ filter) and the trade‑offs of a stateless approach is key.  
  *Quick check*: “What problem does the Kendall τb correlation filter address in the request‑generation stage?”

## Architecture Onboarding
- **Component map**:  
  1. Initialization (sample tools & persona) →  
  2. Planning (LLM generates raw sequence S) →  
  3. Plan Distillation (largest DAG component) →  
  4. Implicit/Explicit Split (Algorithm 1) →  
  5. Request Generation (LLM writes r) →  
  6. Triviality Filter (Kendall τb) →  
  7. Back Translation (leaf check) →  
  8. Conversation Assembly (append r, S′) →  
  9. Tool Execution Simulator (LLM simulates O) →  
  10. Summarization (LLM creates s) →  
  11. Error Augmentation (clarification & tool errors) →  
  12. Pre/Post filters (judge filter, name masking) →  
  13. Concatenation (merge multiple conversations).

- **Critical path**: For each turn: Planning → Distillation → Split → Request Gen → τb filter → Back Translation → if passed, add to message history. After N turns, steps 9‑11 are applied sequentially. Any filter failure skips the current turn but does not abort the whole conversation.

- **Design tradeoffs**:  
  *Random split* increases diversity but may yield unbalanced implicit/explicit ratios; leaf‑parent constraint mitigates inconsistency.  
  *Leaf‑only back‑translation* is cheap but may miss missing non‑leaf calls; full DAG isomorphism would be more thorough but costly.  
  *LLM‑based tool simulation* is stateless and cheap but may not match real semantics; acceptable for training data with some noise.  
  *Open‑source teacher* (`gpt‑oss‑120b`) lowers cost versus frontier models but likely caps data quality.

- **Failure signatures**:  
  High turn rejection rate (>50%) suggests prompts need tuning or teacher model is too weak.  
  Poor performance on `Miss Func`/`Miss Param` categories indicates error‑augmentation or handling of incomplete information is insufficient.  
  Inconsistent summaries (e.g., referencing tool outputs not produced) break coherence; could be caught by a post‑hoc consistency checker.  
  Over‑fitting to specific tool identifiers is mitigated by masking; failure would show sharp drop on held‑out tool name distributions.

- **First 3 experiments**:  
  1. Train on data with all‑explicit calls vs. mixed implicit/explicit; expect significant gain from implicit inclusion (reported 9% drop when removed).  
  2. Train with/without back‑translation filter; expect ≈8% performance drop without it.  
  3. Reproduce prior methods (APIGen‑MT, ToolACE‑MT) using identical teacher and base LLM; compare on BFCL‑v3 and τ²‑bench to confirm DiGiT‑TC superiority.

## Open Questions the Paper Calls Out
- **Optimal implicit ratio**: The paper randomly partitions tool calls into implicit/explicit; ablations removing implicit calls drop 9%, but the optimal ratio is unexplored.
- **Error handling improvement**: Current error augmentation (clarification & tool‑call hints) is simplistic; performance lags on Miss Func/Miss Param categories. Strengthening this is a clear future direction.
- **Teacher model cost‑quality trade‑off**: Authors used `gpt‑oss‑120b` and speculated stronger teachers (e.g., `gpt‑4o`) would help, but no empirical comparison across teachers exists.

## Limitations
- Exact LLM generation hyperparameters and complete prompt templates are omitted, hindering faithful replication.  
- Back‑translation only checks leaf inclusion, not full plan correctness, potentially allowing misaligned examples.  
- The stateless tool execution simulator cannot model real stateful tool semantics, limiting realism for complex dependencies.  
- The training data size (~5k conversations) and reliance on a single teacher LLM may cap achievable performance.

## Confidence
- **Overall effectiveness (BFCL‑v3/τ²‑bench gains)**: High (empirically validated with ablations)  
- **Implicit call mechanism**: Medium (9% drop without it supports contribution but causal inference is indirect)  
- **Back‑translation fidelity**: Medium (8% drop when removed, but leaf‑only check is a coarse proxy)  
- **Generalization beyond presented benchmarks**: Low (only two multi‑turn benchmarks used)

## Next Checks
1. **Reproduce filter acceptance rates**: Implement the pipeline with best‑guess settings; report fractions of turns passing Kendall τb and leaf‑inclusion checks to validate undisclosed parameters.
2. **Full‑plan back‑translation comparison**: Replace leaf check with DAG isomorphism between original and back‑translated sequences; quantify dataset overlap and final model performance to assess fidelity trade‑offs.
3. **Cross‑benchmark generalization**: Fine‑tune the same base model on DiGiT‑TC data and evaluate on a stateful tool‑calling benchmark (e.g., ToolBE‑v1); a significant drop would confirm the stateless simulator’s limitation.
