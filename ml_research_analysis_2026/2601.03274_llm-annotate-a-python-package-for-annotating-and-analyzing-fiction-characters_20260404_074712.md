# LLM_annotate: A Python package for annotating and analyzing fiction characters

## Quick Facts
- **arXiv ID:** 2601.03274  
- **Source URL:** https://arxiv.org/abs/2601.03274  
- **Reference count:** 29  
- **Primary result:** Automated character trait annotation with 95% human-validated accuracy on a full-length animated film script.

## Executive Summary
This paper introduces *LLM_annotate*, a Python package that automates the annotation of fictional character behaviors and traits using large language models (LLMs). The package provides a standardized pipeline: it chunks text into manageable sections, prompts an LLM with structured trait definitions to label observed actions, automatically disambiguates character names across chunks, and includes a human-in-the-loop GUI for quality scoring. Evaluated on *The Simpsons Movie* and *Pride and Prejudice*, the method achieved high human-validated accuracy (95% on Simpsons) and reproduced known psychological correlations. By making the workflow reproducible and scalable, *LLM_annotate* lowers the barrier to quantitative literary analysis.

## Method Summary
The core method consists of five sequential steps. First, `chunk_text` splits the full narrative into overlapping text chunks to respect LLM context limits. Second, `annotate` sends each chunk to an LLM along with user-defined trait specifications (including explanations and positive/negative examples) to generate action–trait labels per character. Third, `disambiguate` scans all annotations to detect and merge character name aliases (e.g., “Homer” vs. “Homer Simpson”) using cross-chunk consistency, proposing merges for user confirmation. Fourth, `score_annotations` launches a GUI where human reviewers judge a random sample of LLM-generated labels, producing an accuracy estimate. Finally, `compute_annotation_statistics` aggregates trait scores per character and visualizes results. The package supports any LLM and emphasizes the importance of structured trait definitions for reliable inference.

## Key Results
- Human reviewers validated 95% (89%–98% credible interval) of *LLM_annotate*’s trait annotations on *The Simpsons Movie*.
- For *Pride and Prejudice*, the default chunk size (500 tokens) yielded 1,981 annotations compared to 578 from chapter-wise chunking, while maintaining comparable validation accuracy.
- The pipeline successfully reproduced the expected negative correlation between social dominance orientation and agreeableness in *Pride and Prejudice* (r = –0.742, p = .014).

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Structuring trait definitions with explicit examples and explanations improves the reliability of LLM-based behavioral annotations for fictional characters.
- **Mechanism:** The `annotate` function requires users to provide a `traits` dictionary containing a `trait_explanation` and positive/negative `examples`. This structures the prompt sent to the LLM, moving beyond vague trait labels (e.g., "agreeable") to concrete, contextualized behavioral indicators. The LLM uses this guidance to map text actions to the specified rating scale.
- **Core assumption:** Clear, example-backed definitions reduce ambiguity and align the LLM's inference process with the researcher's conceptualization of the trait.
- **Evidence anchors:** 
  - [abstract] "It standardizes workflows for annotating character behaviors... and inferring character traits."
  - [section, PAGE 3] "To induce deliberate instructions and explicitness, the LLM_annotate package requires users to define the traits... and provide examples of positive and negative indicators."
  - [corpus] Weak direct evidence; corpus shows related work on character portrayal but not this specific prompt-structuring mechanism.
- **Break condition:** If the provided trait explanations are themselves ambiguous, internally contradictory, or the examples are irrelevant/poor, the mechanism fails, leading to inconsistent or invalid annotations.

### Mechanism 2
- **Claim:** An iterative, cross-chunk name review process mitigates character name disambiguation errors (e.g., pseudonyms, nicknames) that arise from chunked text processing.
- **Mechanism:** The `disambiguate` function automatically scans all annotation chunks for potential character name aliases (e.g., "Homer" vs. "Homer Simpson"). It evaluates consistency by reviewing character actions across multiple chunks and larger text sections. It proposes merges to the user, who can accept, reject, or manually specify merges.
- **Core assumption:** A character's core actions and traits are relatively consistent across a narrative, allowing algorithmic detection of name variants based on overlapping behavioral patterns in different chunks.
- **Evidence anchors:**
  - [section, PAGE 3] "LLM_annotate addresses this challenge in two ways. First, it automatically reviews the full list of characters for pseudonyms across varying section lengths and with cross-section memory... Second, the human expert is prompted to review and, if necessary, correct the names..."
  - [section, PAGE 10] Describes a case where "Jane Bennet" and "Miss Bennet" were correctly merged after manual review.
- **Break condition:** Fails when a single name string (e.g., "Miss Bennet") legitimately refers to multiple characters in different contexts, and the disambiguation logic incorrectly merges them. Also fails if character behaviors are highly inconsistent or if chunks are too short to contain sufficient identifying context.

### Mechanism 3
- **Claim:** A human-in-the-loop GUI for quality scoring quantifies annotation accuracy and filters egregious errors, creating a trust metric for the automated output.
- **Mechanism:** The `score_annotations` function presents human reviewers with randomly selected LLM-generated annotations (action + trait label) alongside the source text chunk. The reviewer judges correctness on a defined scale. The resulting agreement statistics (e.g., 95% [89%-98%] correct) serve as a validation benchmark for the entire annotation set and identify systematic failure modes.
- **Core assumption:** A sample of human judgments on the LLM's output is a valid proxy for the overall accuracy of the full, unlabeled annotation set. High agreement indicates the LLM's inferences are generally sound for the given task definitions.
- **Evidence anchors:**
  - [abstract] "...validating annotation/inference quality via a human-in-the-loop GUI."
  - [section, PAGE 7] Describes the GUI and reports the Simpsons example accuracy (95% [89%-98%]).
  - [section, PAGE 11] Shows the accuracy comparison between chunking methods for *Pride and Prejudice*.
- **Break condition:** If human reviewers are poorly trained, inconsistent, or biased, the quality scores are invalid. Also, sampling may miss rare but critical error types (e.g., systematic misattribution for a minor character).

## Foundational Learning
- **Concept: Text Chunking & Context Windows**  
  **Why needed here:** LLMs have fixed maximum context lengths. Full novels or scripts exceed this limit. Chunking is the prerequisite step to make the text processable, but it introduces fragmentation that complicates character continuity and narrative coherence.  
  **Quick check:** If you halve the default chunk size (500 tokens), what is the most likely impact on (a) number of annotations collected and (b) the difficulty of name disambiguation?

- **Concept: Operationalization of Psychological Constructs**  
  **Why needed here:** Traits like "social dominance orientation" or "agreeableness" are abstract psychological constructs. The package does not infer them magically; it requires the user to *operationalize* them into specific, observable textual behaviors via `trait_explanation` and `examples`.  
  **Quick check:** Why is it insufficient to simply provide the LLM with a dictionary definition of "authoritarianism" for annotation? What additional element is required by the package's design?

- **Concept: Interrater Reliability as a Validation Metric**  
  **Why needed here:** Since there is no absolute "ground truth" for a character's personality, the package substitutes *human-LLM agreement* as the primary validation metric. Understanding that this measures *consistency with a human standard* (not objective truth) is crucial for interpreting results.  
  **Quick check:** The paper reports 95% annotation accuracy for *The Simpsons Movie*. Does this mean 95% of the LLM's trait labels are universally "true"? What is the more precise interpretation of this statistic?

## Architecture Onboarding
The pipeline comprises five components executed in sequence:

- `chunk_text` → `annotate` → `disambiguate` → `score_annotations` → `compute_annotation_statistics`

**Critical path:** The steps must be followed in this exact order; skipping or reordering (e.g., disambiguating before annotating) breaks the pipeline.

**Design tradeoffs:**
- **Chunk size:** Smaller chunks increase total annotations and sensitivity to local context but worsen name disambiguation due to less contextual information per chunk. Larger chunks risk missing behaviors and hitting LLM context limits.
- **Automation vs. Control:** Full automation (`disambiguate` auto-merge) is efficient but risky. Manual specification (`list_of_pseudonym_lists`) is safer for complex texts but requires expert knowledge and time.
- **Default LLM (GPT-4o) vs. Custom:** Using defaults is easiest, but a custom model might be needed for domain-specific texts or to avoid API costs. This trades reproducibility and benchmarking for cost/domain fit.

**Failure signatures:**
- **Low human accuracy (<80% "Correct") in `score_annotations`:** Indicates fundamental problem with trait definitions, LLM capability, or text complexity. Halt analysis; revise `traits` or model.
- **Excessive proposed merges in `disambiguate` (e.g., merging distinct protagonists):** Suggests chunks are too short or characters' behaviors are not distinctive enough for the algorithm. Manually correct and consider increasing chunk size.
- **Very few annotations for a known major character in `annotations.json`:** Likely cause: The character's name is consistently misspelled or referred to by an unhandled alias, failing disambiguation. Check raw annotations.

**First 3 experiments:**
1. **Sanity Check with Simple Text:** Run the full pipeline on a short, well-known script (e.g., a 10-page movie scene) with 2–3 obvious traits (e.g., "friendly", "aggressive") and simple examples. Verify the GUI shows >90% accuracy and character lists are correct. Confirms installation and basic logic.
2. **Chunk Size Sensitivity:** For a given text (e.g., one Austen novel chapter), run `chunk_text` with default (500 tokens) and a larger custom size (e.g., 2000 tokens). Run `annotate` and `disambiguate` on both. Compare: (a) total annotation count, (b) number of unique character names, (c) proposed merges. Validates the tradeoff described in the paper.
3. **Trait Definition Stress Test:** Define a notoriously difficult-to-code trait (e.g., "irony", "narrative unreliability") with only a dictionary definition, no examples. Run annotation and scoring on a text where the trait is central. Expect very low human accuracy. Then, add clear, text-specific positive/negative examples and re-run. Confirms the mechanism of structured definitions.

## Open Questions the Paper Calls Out
1. **Sample size for validation:** What sample size of human-validated annotations yields a stable accuracy estimate? The paper scores 100 (Simpsons) or 50 (Pride) annotations without statistical justification.
2. **LLM comparison:** How do different LLMs compare in accuracy, bias, and cost for character annotation? The package supports any LLM, but only GPT-4o and a custom LLM were tested; no comparative results are provided.
3. **Optimal chunking parameters:** What chunking parameters (size, overlap) maximize annotation coverage and accuracy for varying text genres? The paper compared default vs. chapter-wise for one novel; other parameters untested.
4. **False negative estimation:** How can LLM_annotate estimate the number of omitted character behaviors (false negatives)? The GUI does not score omissions, which require manual review or sensitivity analysis.

## Limitations
- **Generalizability limited:** Evaluation on only two texts (screenplay, novel) with specific traits; unknown performance on diverse genres/eras.
- **Human validation bias:** Accuracy scores depend on reviewer consistency; sampling may miss systematic errors (e.g., misattribution for minor characters).
- **Mechanism fragility:** Break conditions (ambiguous trait definitions, extreme name ambiguity, inconsistent character behavior) are identified but not quantitatively stress-tested.

## Confidence
- **Accuracy Claims (95% Simpsons, P&P correlation):** Medium (strong empirical results but narrow scope; confidence intervals reflect sample uncertainty, not text/trait diversity).
- **Mechanism Validity (structured prompts, disambiguation, human-in-the-loop):** Low to Medium (core assumptions lack broad empirical validation beyond presented cases; break conditions indicate known failure modes).
- **Pipeline Reproducibility & Integration:** High (the package operationalizes a standardized, validated workflow, but outcomes remain sensitive to user-defined traits and LLM choice).

## Next Checks
1. **Cross-Text Generalizability:** Replicate the full pipeline on at least three additional fictional works (e.g., epic poetry, modern drama) with consistent trait definitions to measure stability of accuracy metrics.
2. **Disambiguation Stress Test:** Use texts with deliberate name ambiguity (e.g., multiple "Miss [Surname]" characters) to quantify false-merger rates and manual correction burden.
3. **Trait Definition Sensitivity:** Systematically degrade trait specifications (remove examples, add contradictions) and measure impact on `score_annotations` human accuracy.
