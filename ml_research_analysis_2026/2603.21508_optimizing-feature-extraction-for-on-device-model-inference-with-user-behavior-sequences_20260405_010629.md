# Optimizing Feature Extraction for On-device Model Inference with User Behavior Sequences

## Quick Facts
- **arXiv ID**: 2603.21508
- **Source URL**: https://arxiv.org/abs/2603.21508
- **Reference count**: 40
- **Primary result**: AutoFeature reduced end-to-end on-device feature extraction latency by 1.33–4.53× across five ByteDance mobile services, bringing average latency below 20ms.

## Executive Summary
Feature extraction from raw app logs consumes 61–86% of on-device ML inference latency, representing a critical bottleneck. AutoFeature addresses this by introducing an automated engine that (1) models extraction as a directed acyclic graph (FE-graph) with four atomic operations—Retrieve, Decode, Filter, Compute—(2) fuses redundant nodes across features via hierarchical filtering, and (3) caches behavior-level intermediate results using a greedy knapsack policy to maximize redundancy elimination within memory limits. Deployed in five ByteDance services, AutoFeature achieved 1.33–4.53× end-to-end speedup (daytime 1.33–3.93×, nighttime 1.43–4.53×), with average latency under 20ms. Inter-feature fusion cut Retrieve/Decode latency by over 4×, and caching reused 50% of redundant operations while storing only 23% of data. Compared to cloud offloading, it was up to 77.7% faster with ≤100KB overhead and <3.5ms offline cost.

## Method Summary
AutoFeature consists of an offline optimization pipeline and an online executor. Offline, it parses the model’s feature specification into an FE-graph where each feature is a chain of four atomic operations: Retrieve (query logs by event names and time range), Decode (parse compressed attributes), Filter (select needed attributes), Compute (apply aggregation function). The engine first performs intra-feature partition: each Retrieve node is split into sub-nodes per distinct event name to expose finer-grained overlaps. Then inter-feature fusion merges Retrieve/Decode sub-nodes sharing identical event names and time ranges, postponing branching until just before Compute. A hierarchical filtering algorithm replaces the individual Filter nodes: it precomputes a reverse mapping from time ranges to the required attributes, then processes events chronologically, checking the nearest matching time range to extract attributes for all fused features in one pass, reducing complexity. For cross-execution caching, the system formulates a 0/1 knapsack: select behavior types to cache under a memory budget to maximize utility \(U(E) = \text{Num\_Overlap} \times \text{Cost\_opt}\), where cost \(C(E) = \text{Num\_events} \times \text{Size\_event}\). A greedy policy sorts by \(U/C\) ratio, decomposing it into a dynamic term (time overlap over time range) and a static term (cost per event), enabling constant-time evaluation. Online, the executor checks the cache for each behavior type, executes missing parts of the optimized graph, and updates the cache eviction set according to the greedy policy.

## Key Results
- End-to-end latency reduced by 1.33–4.53× (daytime 1.33–3.93×, nighttime 1.43–4.53×); average latency brought below 20ms.
- Inter-feature fusion cut Retrieve/Decode latency by over 4×.
- Greedy caching reused 50% of redundant operations while storing only 23% of data.
- Compared to cloud offloading, achieved up to 77.7% faster extraction with ≤100KB memory overhead and <3.5ms offline optimization cost.

## Why This Works (Mechanism)
### Mechanism 1: Graph Abstraction
- **Claim**: Modeling feature extraction as a directed acyclic graph (FE-graph) with four atomic operations systematically exposes redundancy across features.
- **Mechanism**: User features are defined by four orthogonal conditions: `<event_names, time_range, attr_names, comp_func>`. Extraction follows a chain: **Retrieve** (query logs by `event_names`/`time_range`) → **Decode** (parse compressed attributes) → **Filter** (select `attr_names`) → **Compute** (apply `comp_func`). The union of all feature chains forms an FE-graph where nodes are operations and edges are data dependencies. Redundancy is identified by computing set intersections of conditions across nodes of the same operation type.
- **Core assumption**: All user features in industrial on-device models can be expressed through these four operations, which sufficiently cover transformations from raw app logs to model inputs.
- **Evidence anchors**:
  - [abstract] "graph abstraction to formulate the extraction workflows of different input features as one directed acyclic graph"
  - [section 3.2] "characterize feature extraction as an information filtering process... four orthogonal conditions... four atomic operations"
  - [corpus] Related work such as *Optimizing Storage Overhead of User Behavior Log for ML-embedded Mobile Apps* also targets user behavior logs for on-device ML, confirming the problem domain. FMR scores (0.45–0.58) indicate moderate alignment with this research direction.
- **Break condition**: If a feature requires external data (e.g., cloud lookups) or non-deterministic transformations, the FE-graph abstraction fails because such steps cannot be represented as deterministic filters on local logs.

### Mechanism 2: Inter-Feature Optimization
- **Claim**: Fusing redundant operation nodes across features eliminates repeated data retrieval and decoding, reducing latency by up to 4× for the most expensive stages.
- **Mechanism**: Two-step process:  
  1. **Intra-feature partition**: Decompose each feature’s `Retrieve` node into sub-nodes per distinct `event_name`, ensuring fusion only occurs between sub-chains with identical event types and avoiding irrelevant data expansion.  
  2. **Inter-feature fusion**: Merge identical `Retrieve`/`Decode` sub-nodes and postpone branching until immediately before `Compute`. A **hierarchical filtering** algorithm replaces individual per-feature branches: it precomputes a reverse mapping from time ranges to required attributes, processes input events in chronological order, and checks the nearest matching time range, reducing `Filter` complexity from \(O(\text{len(inputs)} \times \text{num(features)})\) to \(O(\text{len(inputs)} + \text{num(time\_ranges)})\).
- **Core assumption**: The majority of extraction latency resides in `Retrieve` and `Decode` (empirically 15× and 300× slower than `Filter`/`Compute`), and many features share overlapping behavior types (e.g., >80% in some models).
- **Evidence anchors**:
  - [abstract] "graph optimization to identify and fuse redundant operation nodes... hierarchical filtering"
  - [section 3.3] "branch postposition... hierarchical filtering algorithm" and Figure 10 showing Retrieve/Decode dominance.
  - [corpus] *ENCODE: Breaking the Trade-Off Between Performance and Efficiency in Long-Term User Behavior Modeling* addresses long-term user behavior sequences, implying complex feature sets that benefit from efficient extraction.
- **Break condition**: If features have highly disjoint `event_names` (low overlap), fusion adds partitioning and branch overhead without meaningful redundancy elimination.

### Mechanism 3: Cross-Execution Caching
- **Claim**: Caching behavior-level intermediate results (decoded attributes) across consecutive inferences reduces redundant operations by 50% while storing only 23% of data, using a greedy knapsack policy.
- **Mechanism**: Caching is formulated as a 0/1 knapsack problem: select behavior types \(E_i\) to maximize utility \(U(E_i) = \text{Num\_Overlap} \times \text{Cost\_opt}\) under memory budget \(M\), where cost \(C(E_i) = \text{Num\_events} \times \text{Size\_event}\). A greedy policy prioritizes by utility‑to‑cost ratio \(U/C\), which decomposes into a dynamic term \(\text{Time\_overlap}/\text{Time\_range}\) (depends on inference frequency) and a static term \(\text{Cost\_opt}/\text{Size}\) (profiled offline), enabling constant‑time evaluation.
- **Core assumption**: Device memory per app is limited but non‑trivial; caching at behavior granularity amortizes storage across multiple features that share the same behavior type, maximizing reuse.
- **Evidence anchors**:
  - [abstract] "efficient caching to minimize operations on overlapping raw data between consecutive model inferences"
  - [section 3.4] Knapsack formulation, greedy policy with 2‑approximation guarantee, and term decomposition.
  - [corpus] *Speech Understanding on Tiny Devices with A Learning Cache* leverages temporal locality to cache spoken language understanding results, supporting cross‑inference reuse in resource‑constrained settings.
- **Break condition**: If inference intervals exceed the maximum `time_range` of features (e.g., hourly features invoked daily), overlap vanishes; also if memory budget is extremely tight (e.g., < 1 behavior), caching yields negligible savings.

## Foundational Learning
- **Concept**: Directed Acyclic Graph (DAG)
  - **Why needed**: The FE‑graph is a DAG; acyclicity ensures a topological execution order and enables safe fusion of nodes without cycles.
  - **Quick check**: What would happen if the graph contained a cycle? Could a cycle arise from real‑world feature definitions? (Hint: features depend only on past logs, never on future outputs.)
- **Concept**: Knapsack Problem (0/1)
  - **Why needed**: Caching selection is a knapsack: maximize computational savings (utility) within memory limit. The greedy approximation offers efficient, theoretically bounded decisions.
  - **Quick check**: What is the approximation ratio of the greedy algorithm for the 0/1 knapsack? How does this differ from the fractional knapsack, which can be solved optimally?
- **Concept**: Information Filtering
  - **Why needed**: The four atomic operations act as filters on an information stream; understanding this helps reason about condition intersections and redundancy.
  - **Quick check**: If two features share `event_names` but have disjoint `time_range`, at which operations do they still overlap? (Answer: `Retrieve` only on the intersecting time portion; `Decode` on retrieved rows; `Filter` and `Compute` diverge.)

## Architecture Onboarding
### Component map
Offline: Graph Generator → Intra-Feature Partition → Inter-Feature Fusion → Event Evaluator. Online: Cache Manager and Executor.

### Critical path
Inference request → cache lookup → for missing events: Retrieve (I/O) → Decode (CPU) → fused Filter (memory bound) → Compute (lightweight). Retrieve and Decode are primary latency contributors.

### Design tradeoffs
- *Partition granularity*: Per-event_name splits balance overhead vs. fusion precision.
- *Cache selection*: Greedy runs in O(N log N) vs. DP's O(NM); accepts small optimality loss for speed.
- *Hierarchical Filter*: Requires a small reverse mapping (one per distinct time range) but drastically reduces runtime filtering complexity when many features are fused.

### Failure signatures
- No speedup: Very low feature overlap; inspect FE-graph for disjoint `event_names`/`time_range`.
- Memory pressure: Cache misses/evictions spike if greedy underestimates size or budget is too small.
- Incorrect outputs: Mis-grouped time ranges in hierarchical filter cause wrong extraction; validate with synthetic tests.

## Open Questions the Paper Calls Out
1. **What accuracy loss results from deliberately using stale feature values in on‑device predictions?** The paper mentions co‑design could trade minor accuracy for major latency by reusing stale features, but this remains unexplored.
2. **How much latency does the greedy cache policy lose versus optimal, and can a lightweight predictor narrow the gap?** The caching uses a greedy approximation; the optimality gap is unmeasured, and dynamic workloads may benefit from prediction.
3. **Are the four atomic operations (Retrieve, Decode, Filter, Compute) sufficient to express all feature extraction tasks, especially stateful ones?** The FE‑graph assumes these four operations, validated only on ByteDance apps; complex or cross‑model features may require additional operations.

## Limitations
- Exact log schema and compression format are unspecified, hindering precise implementation of `Decode()` and memory sizing.
- Atomic operation cost model is not provided; per-event latencies needed for accurate knapsack utility are unknown.
- Branch postposition mechanism (hierarchical filter) is underspecified; potential overhead or edge-case bugs are not addressed.
