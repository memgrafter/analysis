# Arabic Morphosyntactic Tagging and Dependency Parsing with Large Language Models

## Quick Facts
- **arXiv ID**: 2603.16718
- **Source URL**: https://arxiv.org/abs/2603.16718
- **Reference count**: 34
- **Primary result**: Retrieval-based in-context learning with high surface similarity (chrF++) enables instruction-tuned LLMs to approach or exceed supervised Arabic parsing performance on gold tokenization, but tokenization remains a bottleneck for open-weight models in raw-text parsing.

## Executive Summary
We evaluate instruction-tuned large language models (LLMs) on two core Arabic NLP tasks: morphosyntactic tagging (14 features) and labeled dependency parsing (CATiB). Through zero-shot and retrieval-based in‑context learning (ICL), we find that demonstration selection via surface similarity (chrF++) substantially boosts performance. Proprietary models (Gemini 3, GPT‑5.2) achieve near-supervised tagging accuracy and surpass the state-of-the‑art CamelParser on gold-tokenized dependency parsing (LAS 88.2% vs. 87.5%). For open-weight models, tokenization is the main obstacle in raw-text parsing, but best‑ICL narrows the gap. Retrieval quality is paramount; high‑chrF++ examples yield consistent gains over random or low-similarity selections. However, exact full‑bundle tagging and raw-text parsing remain below supervised baselines, highlighting limits of current LLMs for fine‑grained structured prediction.

## Method Summary
We conduct experiments on Penn Arabic Treebank (PATB) for tagging and CAMeL Treebank (CAMeLTB) for parsing. For each test sentence, we retrieve *k* demonstrations from the training set using either random selection or similarity based on chrF++ (surface) or CAMeLBERT embeddings (semantic). These demonstrations are prepended to a fixed prompt instructing the LLM to output JSON with morphosyntactic features or dependency relations. We evaluate under gold tokenization (exact tokens given) and raw-text (end‑to‑end) settings. Model outputs are parsed and compared to gold using All Tags, Tag F1, LAS, UAS, and Token F1. The best configuration (*k*=10, highest chrF++) is chosen on dev and applied to all LLMs on test. Supervised baselines (CAMeL Tools, CamelParser) are computed for reference.

## Key Results
- Proprietary LLMs (Gemini 3, GPT‑5.2) achieve Tag F1 > 98.5% and LAS 88.2% (Gemini 3) on gold-tokenized parsing, surpassing CamelParser (87.5% LAS).
- For open-weight models (e.g., Qwen3), best‑ICL with high‑chrF++ demonstrations yields dramatic raw-text improvements: Token F1 + 33.7 points and LAS + 44.7 points.
- Retrieval quality is critical: high chrF++ selection outperforms random or low-similarity retrieval by large margins (e.g., All Tags for Qwen3: 78.0 vs. 65.9 for random).

## Why This Works (Mechanism)

### Mechanism 1: Surface similarity retrieval drives ICL gains
- **Claim**: Retrieval quality, measured by chrF++, is a primary driver of ICL performance. High-similarity demonstrations yield substantial gains over random or low-similarity selection.
- **Mechanism**: chrF++ captures substring-level morphological and orthographic similarity, retrieving examples with analogous cliticization patterns and inflectional morphology. This calibrates the LLM to produce structured outputs adhering to the task's linguistic constraints.
- **Core assumption**: Surface similarity correlates with shared linguistic structure.
- **Evidence**: [section 4] "retrieval quality (high chrF++) consistently outperforms random or low-similarity selection." Table 4: Qwen3 All Tags 78.0 (high chrF++) vs. 65.9 (random).
- **Break condition**: Fails when retrieved examples are too dissimilar or when task requires semantic generalizations not captured by surface form.

### Mechanism 2: Proprietary LLM scale and instruction tuning
- **Claim**: Proprietary models approach or exceed supervised baselines due to superior instruction following and scaled pretraining.
- **Mechanism**: Larger pretraining corpora and instruction tuning enable accurate mapping to 14‑dimensional feature bundles and generation of valid CATiB trees under strict output formats.
- **Core assumption**: Model scale improves internalization of task specifications.
- **Evidence**: [abstract] Tag F1 > 98.5% (near CAMeL Tools 99.6%); LAS 88.2% > CamelParser 87.5% (Tables 5, 8).
- **Break condition**: Underperformance in raw-text parsing; All Tags gap ~ 10% indicates limits in modeling fine‑grained feature interactions.

### Mechanism 3: Tokenization bottleneck relieved by ICL
- **Claim**: Tokenization is the primary bottleneck in raw-text parsing for open-weight LLMs, but retrieval‑based ICL with high‑quality demonstrations significantly improves both tokenization and downstream LAS.
- **Mechanism**: Arabic’s orthographic ambiguity requires explicit tokenization rules. Demonstrations that include correct tokenization implicitly teach the segmentation policy (e.g., separating proclitics). Better tokenization yields cleaner inputs for dependency labeling.
- **Core assumption**: ICL conveys domain‑specific tokenization rules through example outputs.
- **Evidence**: [abstract] Qwen3 Tok F1 + 33.7 points; LAS + 44.7 points. Table 9: raw-text improvements. Error analysis: Gemini3 tokenization errors 56% hallucinations.
- **Break condition**: When input contains highly irregular, dialectal, or out‑of‑domain forms absent from retrieved demonstrations.

## Architecture Onboarding

### Component map
LLM inference layer -> Retrieval module -> Prompt templates -> Data loaders -> Evaluation suite. Configuration orchestrator coordinates all components.

### Critical path
1. **Data preparation**: Load PATB and CAMeLTB splits, ensure consistent tokenization (CATiB) and feature representation.
2. **Dev‑set model selection**: Run zero‑shot evaluation; choose strongest open‑weight model (Qwen3) for ICL exploration.
3. **ICL configuration search**: For Qwen3 on dev, iterate over *k* and selection methods; record All Tags/LAS to identify best (*k* = 10, highest chrF++).
4. **Test‑set evaluation**: Apply (*k*<sup>*</sup>, *m*<sup>*</sup>) to all LLMs on test; compute supervised baselines.
5. **Analysis**: Break down results by genre, feature, and error type; compute cost/time.

### Design tradeoffs
- **chrF++ vs. semantic similarity**: chrF++ cheap and morphology‑sensitive; semantic similarity expensive but may capture meaning. chrF++ empirically worked best.
- **Shot count**: More shots improve performance but increase cost; sweet spot often 10.
- **Retrieval diversity vs. relevance**: Highest‑similarity maximizes relevance but may reduce diversity; low‑similarity used diagnostically.
- **Open‑weight vs. proprietary**: Open‑weight reproducible but lag in zero‑shot/raw‑text; proprietary higher accuracy but costly and less transparent.

### Failure signatures
- **Formatting drift**: Invalid JSON, missing fields, extra commentary.
- **All Tags collapse**: High Tag F1 but low All Tags indicates clustered multi‑feature errors.
- **Tokenization mismatch (raw text)**: Low Tok F1 persists after ICL; retrieval may not provide relevant tokenization examples or model hallucinates.
- **Zero‑shot collapse**: Open‑weight All Tags < 15%.
- **Retrieval bottleneck**: Large training sets cause latency; pre‑computed indexes needed.

### First 3 experiments
1. **Zero‑shot baseline**: Run all LLMs on dev/test with no demonstrations; measure gaps; select Qwen3 as strongest open‑weight.
2. **ICL configuration sweep**: Using Qwen3 on dev, vary *k* and selection method; identify best‑ICL (*k*=10, highest chrF++). Validates retrieval importance.
3. **Cross‑model best‑ICL transfer**: Apply chosen config to all LLMs on test; compare to supervised baselines; analyze per‑model gains.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question**: How can LLMs be effectively adapted to Arabic dialects beyond Standard Arabic for morphosyntactic tagging and dependency parsing?
- **Basis**: Paper restricts evaluation to Standard Arabic; dialects differ and lack large treebanks.
- **Why unresolved**: Need dialectal treebanks and cross‑dialect transfer studies.

### Open Question 2
- **Question**: What retrieval methods can more effectively select in‑context examples for Arabic structured prediction tasks than current surface (chrF++) and semantic similarity metrics?
- **Basis**: Future work suggested to explore improved retrieval.
- **Why unresolved**: Current metrics may not capture linguistic features critical for tagging/parsing (e.g., morphological patterns, syntactic structures).

### Open Question 3
- **Question**: How can constrained decoding be incorporated into LLMs to enforce valid morphosyntactic bundles and dependency trees for Arabic?
- **Basis**: Future work: explore constrained decoding.
- **Why unresolved**: LLMs generate without structural guarantees; need integration of finite‑state automata/tree constraints.

### Open Question 4
- **Question**: Why do LLMs exhibit different tokenization error profiles compared to supervised tokenizers, and how can raw‑text Arabic parsing be made more robust to tokenization?
- **Basis**: Tokenization is a major bottleneck; error analysis shows LLMs hallucinate tokens while supervised systems have superficial errors.
- **Why unresolved**: Tokenization errors cascade; need to understand root cause and develop tokenization‑aware methods.

## Limitations
- Exact model versions, API endpoints, and generation hyperparameters are undisclosed, hindering precise reproduction.
- Retrieval implementation details (chrF++ parameters, semantic similarity specifics) are omitted.
- The approach relies on large, high‑quality Arabic treebanks for demonstrations, limiting applicability to low‑resource settings.
- ICL incurs high computational and monetary costs.

## Confidence
- **Retrieval quality (chrF++) drives ICL gains**: Medium.
- **Proprietary LLMs match/surpass supervised baselines**: Medium.
- **Tokenization bottleneck in raw‑text parsing**: High.

## Next Checks
1. Reproduce best‑ICL with explicit chrF++ parameters (e.g., 6‑gram, smoothing) and compare against semantic similarity to confirm surface similarity’s advantage.
2. Decouple tokenization from parsing by feeding gold‑tokenized input (using CAMeL Tools) to the LLM, isolating pure dependency labeling performance.
3. Evaluate retrieval‑based ICL on multiple Arabic dialects (Egyptian, Levantine) to test cross‑dialect generalization and robustness of chrF++ retrieval.
