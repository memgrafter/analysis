# Puda: Private User Dataset Agent for User-Sovereign and Privacy-Preserving Personalized AI

## Quick Facts
- **ArXiv ID:** 2602.08268
- **Source URL:** https://arxiv.org/abs/2602.08268
- **Reference count:** 40
- **Primary result:** Predefined Category Subsets achieve 97.2% of the personalization performance of sharing Detailed Browsing History in a travel planning task, while providing deterministic privacy guarantees and lower operational cost.

## Executive Summary
Puda addresses the tension between personalization and privacy in user data for LLM-based agents, where personal data is typically siloed within platforms. It introduces a user-sovereign, browser-based agent that aggregates cross-service browsing history and manages it at three granular privacy levels: Detailed Browsing History, Extracted Keywords, and Predefined Category Subsets. In an evaluation using LLM-as-a-Judge for a travel planning task, the highest-privacy tier (Categories) retained 97.2% of the personalization performance compared to sharing full detailed history, while offering significantly stronger deterministic privacy protection and reduced latency and token consumption. This demonstrates that structured, taxonomy-constrained data provisioning can effectively mitigate the privacy-personalization trade-off for many agent tasks.

## Method Summary
The paper evaluates Puda using synthetic browsing histories for 20 Japanese personas. A Dataset Agent processes raw browser logs (captured by a Content Recorder extension) through a two-stage pipeline: per-page summarization/keyword extraction via a Small Language Model (SLM), followed by per-user aggregation into three artifacts—Detailed History, Keywords, and Categories (mapped to a predefined 810-category taxonomy). An external Travel Planner Agent (Gemini 2.5 Flash) generates JSON travel plans using user context (a static Profile plus one of the three data granularities). Personalization performance is measured via LLM-as-a-Judge across three criteria (Abstracted Preference Match, Serendipity, Groundedness) against a reference using full Detailed History. Operational costs (latency, token count) are logged for each condition.

## Key Results
- Predefined Category Subsets achieve 97.2% of the average personalization performance score of Detailed Browsing History.
- Categories offer deterministic privacy: the closed taxonomy eliminates risk of leaking unexpected sensitive proper nouns.
- Lower-granularity data (Categories, Keywords) results in significantly lower token consumption and latency compared to Detailed History.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Deterministic category-based data provision (Predefined Category Subsets) can achieve near-optimal personalization performance while offering strong, predictable privacy guarantees.
- **Mechanism:** The Dataset Agent maps aggregated browsing data onto a fixed, predefined taxonomy (e.g., 810 third-tier categories). This closed-set representation eliminates the risk of leaking unexpected sensitive proper nouns (e.g., specific medical conditions) that could appear in less structured formats.
- **Core assumption:** For many personalization tasks (like travel planning), user preferences can be effectively captured through high-level conceptual categories without needing granular raw history.
- **Evidence anchors:** Abstract states Categories achieve 97.2% performance of Detailed History with "significantly stronger deterministic privacy protection." Section 3.3 notes the risk of leaking proper nouns is "deterministically eliminated" with Categories.
- **Break condition:** Fails for tasks requiring time-series behavioral data (e.g., "repeat last week's schedule") or specific named entities (e.g., "book the same hotel").

### Mechanism 2
- **Claim:** Multi-granular user-controlled data provisioning enables explicit trade-offs between personalization, cost, and privacy on a per-task basis.
- **Mechanism:** The architecture produces three distinct data artifacts from the same raw history: verbose summaries (Detailed History), scored keywords (Keywords), and category subsets. Each has a different token footprint. The user selects which artifact to share via the Access Control Agent.
- **Core assumption:** The relationship between granularity, utility, and cost is approximately monotonic and task-dependent; users can make rational choices with clear trade-off understanding.
- **Evidence anchors:** Section 6.2 (Figure 5) shows lower privacy risk (Categories) correlates with lower token consumption and latency. Section 7.1 states Categories demonstrated "superiority in cost efficiency."
- **Break condition:** Breaks if users misunderstand trade-offs (e.g., always select Detailed History) or if task utility is non-linear for intermediate granularities.

### Mechanism 3
- **Claim:** Browser-based content recording is a practical, user-side point of collection for cross-service personal data, enabling user sovereignty without platform adoption of new standards.
- **Mechanism:** A browser extension (Content Recorder) captures URLs, titles, and HTML bodies for all visited pages, sending them to a user-controlled server hosting the Dataset Agent. This aggregates a user's footprint across siloed platforms (e.g., Google, Amazon) into one repository.
- **Core assumption:** A significant portion of important personal data is generated via browser interactions, and users will install a trusted extension.
- **Evidence anchors:** Section 3.2 states the browser is a "pivotal interface" enabling "comprehensive collection." Section 1 contrasts platform-enclosed data with Puda's cross-service aggregation.
- **Break condition:** Fails for data from native mobile apps, desktop applications, or offline contexts; also fails if browsing history is a poor proxy for preferences (e.g., shared computer).

## Foundational Learning
- **Concept: User Sovereignty vs. Platform Silos**
  - **Why needed:** Puda's premise is that users should control their cross-service data, counter to current platform-centric models where data is enclosed. Understanding why control is lost (e.g., notice-and-control failures) is key to designing reclamation mechanisms.
  - **Quick check:** How does the "notice-and-control" mechanism fail users in a multi-agent, AI-driven web?
- **Concept: Multi-Granularity Privacy Design**
  - **Why needed:** The core innovation is the three-tier pipeline. Engineers must grasp transforming raw, high-sensitivity data into representations with *deterministically* lower sensitivity (Categories) and *probabilistically* lower sensitivity (Keywords).
  - **Quick check:** What is the key technical difference in privacy assurance between "Extracted Keywords" and "Predefined Category Subsets"?
- **Concept: LLM-as-a-Judge for Personalization Evaluation**
  - **Why needed:** The 97.2% result depends on this methodology. Engineers must understand its strengths (flexible criteria-based scoring) and weaknesses (moderate human correlation, potential bias) to interpret results correctly.
  - **Quick check:** Why is traditional automated metric evaluation (e.g., BLEU) insufficient for a personalized travel planning task?

## Architecture Onboarding
- **Component map:** Content Recorder -> Dataset Agent -> Access Control Agent -> External AI Agent
- **Critical path:** User browses → Content Recorder logs → Dataset Agent processes → User authorizes granularity for agent/task → Access Control Agent issues token → External Agent requests data → Dataset Agent serves authorized dataset.
- **Design tradeoffs:** Browser-only vs. Native Apps (misses app/offline data); Cloud LLM for Categories vs. Strict User-Side Processing (pragmatic compromise vs. sovereignty ideal); Taxonomy Rigidity (deterministic privacy but cannot represent novel interests).
- **Failure signatures:** Data Freshness Lag (processing delays); Token Scope Mismatch (enforcement failure); Category Mapping Failure (LLM fails to map preferences to taxonomy).
- **First 3 experiments:**
  1. Granularity Verification Test: For fixed test histories, verify Dataset Agent outputs at each level correctly reflect source data and that Categories contain only list items.
  2. Cost Baseline Profiling: Measure token consumption and latency for the Dataset Agent's own processing pipeline per granularity level.
  3. Taxonomy Coverage Audit: Sample real browsing histories; manually annotate key preferences; measure percentage mappable to the 810-category list.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can Puda be extended to collect and manage personal data from non-browser sources (native mobile apps, OS-level operations) while maintaining user sovereignty and privacy?
  - **Basis:** Section 3.2 states the Content Recorder focuses exclusively on browser-based activities; non-browser behaviors are out of scope.
  - **Why unresolved:** Significant gap in capturing comprehensive cross-service behavior for personalized AI.
  - **Resolution evidence:** Develop extensions for non-browser sources, integrate with Dataset Agent, evaluate impact on performance and privacy.
- **Open Question 2:** Can Puda be fully deployed on user-controlled devices without cloud-based models, and what are the performance trade-offs?
  - **Basis:** Section 4.1 admits cloud-based models violate the user-side processing ideal; GPT-5 nano simulates future SLMs.
  - **Why unresolved:** Feasibility with current on-device SLMs is unexplored; contradicts sovereignty goal.
  - **Resolution evidence:** Implement with state-of-the-art on-device SLMs, benchmark against cloud version.
- **Open Question 3:** Does multi-granularity management generalize beyond travel planning (e.g., healthcare, finance)?
  - **Basis:** Evaluation limited to travel planning; section 7.2 discusses task-dependent granularity needs.
  - **Why unresolved:** Unclear if 97.2% retention holds for other domains with different privacy sensitivities.
  - **Resolution evidence:** Replicate LLM-as-a-Judge evaluation across multiple personalization tasks.
- **Open Question 4:** How can access control be made context-aware and adaptive to dynamic preferences or task requirements?
  - **Basis:** Section 7.2 states users must selectively utilize granularities based on intent; current design uses static OAuth scopes.
  - **Why unresolved:** Static authorizations may not handle real-time changes in context or preference.
  - **Resolution evidence:** Design adaptive access control, evaluate impact via user studies or simulations.

## Limitations
- **Reproducibility gaps:** Undisclosed predefined taxonomy (810 categories), LLM prompt templates, and synthetic browsing history datasets hinder faithful replication.
- **Evaluation validity:** LLM-as-a-Judge scores for "personalization" lack human validation; criteria may not align with user-perceived utility.
- **Scope limitation:** Browser-only collection misses native app/offline data; category-based approach breaks for niche interests or entity-specific requests.

## Confidence
- **97.2% performance retention (Categories vs. Full History):** High (direct experimental result, though dependent on LLM-as-a-Judge).
- **Deterministic privacy via fixed taxonomy:** Medium (theoretically sound but untested against adversarial extraction).
- **Cost-efficiency trend (lower granularity → lower latency/tokens):** High (empirically measured).
- **Browser-based aggregation enables user sovereignty:** Medium (architecturally plausible but lacks real-world adoption evidence).
