# SAGE-5GC: Security-Aware Guidelines for Evaluating Anomaly Detection in the 5G Core Network

## Quick Facts
- **arXiv ID:** 2602.03596
- **Source URL:** https://arxiv.org/abs/2602.03596
- **Reference count:** 28
- **Primary result:** Proposes SAGE-5GC guidelines that reveal 98–100% evasion rates for state-of-the-art 5G Core anomaly detectors under adversarial attacks, demonstrating a severe robustness mismatch with standard evaluation.

## Executive Summary
Anomaly detection systems for 5G Core (5GC) networks are typically evaluated under unrealistic assumptions—independent and identically distributed (IID) data and non-adaptive attackers—leading to inflated security claims. To address this, the authors introduce SAGE-5GC, a security-aware evaluation framework that mandates testing under adversarial, protocol-compliant conditions using functionality-preserving traffic manipulations. The guidelines specify four training constraints (GT1–GT4) and three evaluation criteria (GE1–GE3), with GT4 requiring anomaly-agnostic training (benign-only data) and GE3 requiring adversarial testing that respects attacker-controllable features.

The experimental evaluation on a realistic PFCP-based 5G dataset shows that while ensemble detectors achieve near-perfect detection performance (AUC/F1 > 0.99) on unmodified attack traffic, they suffer nearly complete evasion (98–100%) under a model-agnostic genetic algorithm attack that perturbs only feasible features. Even with RobustScaler, evasion rates remain high (up to 48.7% for the best model). The stark mismatch between static and adversarial results proves that standard metrics are insufficient and that adversarial evaluation is indispensable for trustworthy 5G security deployment. SAGE-5GC thus establishes a new benchmark for rigorous, realistic assessment of anomaly detection in 5G Core networks.

## Method Summary
The reproducibility plan follows the paper's description of the dataset, preprocessing, training, and evaluation. The "5G-Attacks" dataset provides raw packet captures of benign and PFCP-based malicious traffic. Preprocessing strictly adheres to SAGE-5GC guidelines: filter UDP packets, extract features from IP, UDP, and PFCP headers; remove constant/empty features; impute missing values (categorical with most frequent, numerical with IterativeImputer using Random Forest); and scale numerical features with RobustScaler. Data splits are defined as: Train (benign from Dataset1 + all benign from Dataset2), Validation (benign from Dataset2), and Test (all malicious from Dataset2 + all of Dataset3). Models are trained exclusively on benign data (GT4), with hyperparameter tuning via grid search on the validation set. Twelve one-class detectors (e.g., HBOS, IForest, kNN, PCA) and four ensembles (combining base detector scores) are evaluated.

Evaluation uses both standard metrics (AUC, Precision, Recall, F1) on clean test data (GE1) and adversarial evasion rates under a model-agnostic genetic algorithm (GA) attack (GE3). The GA perturbs only a manually selected set of attacker-controllable features J while preserving protocol compliance and attack functionality, using a query budget of 100. A random search (RS) baseline is also applied. Several details are essential but not fully specified in the paper, including the exact composition of J, GA hyperparameters (mutation rate, selection), and the inverse mapping F⁻¹ to reconstruct valid packets from perturbed feature vectors. The provided reproduction notes highlight these unknowns, which must be resolved via educated guesses or access to the authors' code to achieve faithful replication.

## Key Results
- Static evaluation yields near-perfect detection (AUC/F1 > 0.99) for ensemble detectors on unmodified attack traffic.
- Under optimized adversarial attacks (model-agnostic GA), evasion rates reach 98–100% for most models, even with RobustScaler.
- The gap reveals a severe robustness mismatch, proving that standard metrics are insufficient and adversarial evaluation is mandatory.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** The SAGE-5GC evaluation guidelines mitigate overestimated security claims by enforcing evaluation under adversarial, protocol-compliant conditions that reflect real 5G Core deployments.
- **Mechanism:** The guidelines mandate four training constraints (GT1–GT4) and three evaluation criteria (GE1–GE3). GT4 requires anomaly-agnostic training (using only benign data). GE3 explicitly requires testing against adversarial traffic that manipulates only attacker-controllable features while preserving attack functionality. This forces evaluation to account for adaptive attackers and non-IID traffic, unlike standard practices.
- **Core assumption:** Real-world 5G Core operation involves non-IID traffic and adaptive attackers who can craft subtle, protocol-compliant manipulations to evade detection.
- **Evidence anchors:** 
  - [abstract] “proposes SAGE-5GC, a set of security-aware guidelines mandating evaluation under adversarial conditions with protocol-compliant, functionality-preserving traffic manipulations.”
  - [section 2.3] Details GT1–GT4 (e.g., GT2: “traffic unrelated to this control-plane interaction… should be excluded”).
  - [corpus] Weak evidence; neighbor papers discuss realistic adversarial NID but not 5G-specific guidelines.
- **Break condition:** If the attacker cannot feasibly manipulate any features without breaking protocol compliance (i.e., set *J* is empty) or if evaluation ignores GE3 and reverts to static test sets.

### Mechanism 2
- **Claim:** A model-agnostic genetic algorithm (GA) can generate effective adversarial evasion samples by optimizing perturbations solely on attacker-controllable features, without needing the detector’s internal parameters.
- **Mechanism:** The GA evolves a population of feature vectors where genes corresponding to indices in *J* (controllable features) are sampled from empirical distributions *µ_j*, while other features are fixed. Fitness is defined as `[D(F(p’)) – τ]₊`. Crossover and mutation operate only on *J*, and decoding `F⁻¹(x’)` ensures feasibility. The search continues until an individual achieves zero fitness (successful evasion) or a query budget is exhausted.
- **Core assumption:** The attacker has access to the feature extractor *F* and can observe the detector’s score *D* and threshold *τ*, but not the model’s internal parameters.
- **Evidence anchors:** 
  - [abstract] “introduce a practical optimization strategy based on genetic algorithms that operates exclusively on attacker-controllable features and does not require prior knowledge of the underlying detection model.”
  - [section 3.2] Describes GA initialization, fitness, selection, crossover, and mutation, all constrained to *J*.
  - [corpus] Neighbors like “SoK: Realistic Adversarial Attacks…” discuss model-agnostic attacks but not GA for 5G packet features.
- **Break condition:** If the feature space is too constrained (e.g., *J* is very small) or the detector’s decision boundary is inherently robust to such localized perturbations.

### Mechanism 3
- **Claim:** High detection performance under static evaluation (AUC/F1 >0.99) is a poor predictor of robustness because ensemble detectors exhibit 98–100% evasion rates under optimized adversarial attacks, revealing a severe robustness mismatch.
- **Mechanism:** Baseline evaluation (Table 3) uses standard metrics on unmodified attack traffic. Adversarial evaluation (Table 4) applies GA-based attacks. The mismatch arises because detectors rely on fragile correlations in the feature space that are disrupted by small, feasible perturbations, even when scaling is applied.
- **Core assumption:** Static evaluation on unmodified attack samples does not capture performance under adaptive, functionality-preserving manipulations.
- **Evidence anchors:** 
  - [abstract] “ensemble detectors achieve near-perfect AUC/F1-scores (>0.99) against static attacks, adversarial evasion rates reach 98–100% for most models under optimized attacks.”
  - [section 4.2] Shows high F1-scores (e.g., Ens-HKLIP 0.998 without scaler).
  - [section 4.3] Table 4: Ens-HKLIP has 98.4% evasion under GA DE without scaler, 48.7% with scaler.
  - [corpus] Neighbors highlight fragility of ML-based NIDS to adversarial attacks but do not quantify the mismatch for 5G-specific ensembles.
- **Break condition:** If the detector is inherently robust to feature-space perturbations (e.g., via adversarial training) or if the attack manipulations are not functionality-preserving (violating the threat model).

## Foundational Learning
- **Concept:** One-class novelty detection (unsupervised anomaly detection).  
  **Why needed here:** The entire evaluation assumes detectors are trained only on benign 5G traffic (GT4), learning a model of “normal” to detect deviations. Including malicious samples in training would invalidate the novelty premise and overestimate performance.  
  **Quick check:** Why would including attack samples in the training set lead to unrealistic performance estimates in a 5G Core deployment scenario?

- **Concept:** Protocol-compliant feature manipulation.  
  **Why needed here:** Attackers must preserve the semantics and effectiveness of malicious PFCP traffic; otherwise, the attack fails regardless of detector evasion. This constrains the adversarial search to a feasible subset *J* of features.  
  **Quick check:** How does the definition of “feasible” (Definition 1) differ from “compliant” (Definition 2) in the context of PFCP attacks?

- **Concept:** Model-agnostic adversarial evaluation.  
  **Why needed here:** The threat model assumes the attacker does not know the detector’s internals (section 3.1). Evaluation must thus use optimization methods (like GA) that rely only on observed scores, making robustness claims more general and conservative.  
  **Quick check:** Why is a model-agnostic attacker considered a more conservative assessment than a white-box attacker for 5G Core anomaly detection?

## Architecture Onboarding
- **Component map:** Data Ingestion → Feature Extraction → Preprocessing → Detector Training → Evaluation Pipeline.
- **Critical path:** Preprocessing → Detector training → Static evaluation → Adversarial sample generation (GA) → Robustness assessment.
- **Design tradeoffs:**
  - Model-agnostic vs white-box attacks: GA is conservative but may be less efficient than gradient-based methods; however, gradients are infeasible for protocol features (section 3.1).
  - Feature scaling: RobustScaler can improve robustness against GA (Table 4) but may distort some categorical feature distributions; impact must be explicitly evaluated (GT3).
- **Failure signatures:**
  - High evasion rates (>90%) for a model under GA attacks, especially with unscaled features (Table 4).
  - Discrepancy between high static F1-score (Table 3) and low robust F1 under attack.
  - Certain attack categories consistently missed even in static evaluation (e.g., LODA 0% for Restoration-TEID in Figure 2).
- **First 3 experiments:**
  1. Baseline static evaluation: Train detectors on benign traffic, test on unmodified attack samples; report AUC, F1, per‑attack detection rates (Tables 3, Figure 2).
  2. Random perturbation sensitivity: For each model, apply random feasible perturbations (RS attack) to attack samples; compute evasion rate (Table 4, “RS” columns).
  3. Optimized adversarial evasion: Run GA (DE or ES) with query budget 100 on attack samples; report evasion rates and compare to random (Table 4, “GA DE/ES” columns).

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the set of attacker‑controllable features (J) be automatically inferred for 5G Core networks in multi‑vendor environments?
- **Basis in paper:** [inferred] The authors manually define J based on domain knowledge and note this as a limitation, stating that "in complex, multi‑vendor environments, identifying these constraints may require automated inference."
- **Why unresolved:** Manual definition does not scale and may overlook vendor-specific protocol implementations or subtle feature interdependencies, potentially leading to incomplete threat models.
- **What evidence would resolve it:** An automated framework that extracts feasible manipulation constraints by analyzing protocol specifications, packet traces, and network function behavior across diverse 5G deployments.

### Open Question 2
- **Question:** To what extent do the SAGE-5GC findings (e.g., high adversarial evasion rates) generalize to other 5G Core protocols beyond PFCP?
- **Basis in paper:** [explicit] The study focuses exclusively on the PFCP protocol, and the authors explicitly state: "our analysis focuses exclusively on the PFCP protocol, leaving vulnerabilities related to other protocols unexplored."
- **Why unresolved:** Other protocols (e.g., NAS, GTP-U) have different structures, header fields, and operational constraints, which may yield different robustness profiles for anomaly detectors.
- **What evidence would resolve it:** A systematic adversarial evaluation applying the same SAGE-5GC guidelines to datasets representing other 5G control‑ and user‑plane protocols, measuring evasion rates and identifying protocol‑specific vulnerabilities.

### Open Question 3
- **Question:** Can adversarially manipulated feature vectors be reliably transformed into fully valid, replayable network traffic that preserves both protocol compliance and attack functionality in real 5G testbeds?
- **Basis in paper:** [explicit] The authors acknowledge that their adversarial samples are "feasible and compliant" at the feature level but are not reconstructed into "replayable and fully‑valid network traffic," calling this a limitation and future work.
- **Why unresolved:** Without packet-level reconstruction and validation, it remains unclear whether adversarial examples would actually be accepted by 5G network functions and maintain attack effectiveness in realistic deployments.
- **What evidence would resolve it:** Implementing a pipeline that maps feature-space perturbations back to byte‑level packets (e.g., using protocol‑aware encoders), then deploying and evaluating them on a physical or emulated 5G Core testbed to measure detection evasion and functional impact.

## Limitations
- Exact definition of the attacker‑controllable feature set `J` is missing, hindering precise replication of adversarial attacks.
- GA hyperparameters (mutation rate, selection) and packet reconstruction method (`F⁻¹`) are unspecified, risking implementation drift.
- Preprocessing pipeline details (categorical encoding, scaling inverse) are ambiguous, potentially misaligning training and attack spaces.
