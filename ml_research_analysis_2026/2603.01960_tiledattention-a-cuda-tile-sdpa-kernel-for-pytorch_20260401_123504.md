# TiledAttention: a CUDA Tile SDPA Kernel for PyTorch

## Quick Facts
- **arXiv ID:** 2603.01960
- **Source URL:** https://arxiv.org/abs/2603.01960
- **Reference count:** 19
- **Primary result:** Achieves 63.2% of fused PyTorch SDPA mean throughput across 80 regimes, with 4 wins; outperforms unfused baselines by up to 28.15×.

## Executive Summary
TiledAttention addresses the scaled dot‑product attention (SDPA) bottleneck in foundation models by providing a modifiable CUDA tile kernel via cuTile Python. It uses online softmax and tiled K,V streaming to avoid full matrix materialization, enabling easy schedule changes. Benchmarking on NVIDIA DGX GB10 shows it achieves 63.2% of fused PyTorch SDPA’s mean throughput across 80 regimes, with 4 wins, and outperforms unfused baselines by 28.15× (PyTorch math SDPA) and 14.36× (eager attention). Performance is strongest at head dimension 128 (94.7% of fused) and sensitive to tiling parameters, supporting rapid research with reproducible profiling.

## Method Summary
TiledAttention implements the forward pass of scaled dot‑product attention by partitioning the sequence dimension into query tiles and streaming key‑value tiles through shared memory. It maintains running softmax statistics (max and normalizer) online to avoid materializing the full attention matrix, thereby reducing HBM traffic. The kernel is expressed as a Python tile program using cuTile, exposing schedule parameters (tile sizes, staging, layout) for easy modification. Evaluation uses a standardized benchmark harness that performs warmup runs, times with CUDA events (median/p95), validates correctness against a high‑precision reference, and isolates the GPU. The study covers a grid of sequence lengths (512–8192), head dimensions (64–160), and precisions (FP16/BF16) on NVIDIA DGX GB10.

## Key Results
- Mean throughput: 63.2% of fused PyTorch SDPA across 80 regimes, with 4 regime wins.
- Speedups: 28.15× over PyTorch math SDPA and 14.36× over eager attention.
- Best case: 94.7% of fused at head dimension 128; performance sensitive to tiling parameters.

## Why This Works (Mechanism)

### Mechanism 1: Streaming KV and Online Softmax
The kernel partitions the sequence dimension into tiles. For each query tile, it streams key‑value tiles, computes partial score blocks, and updates running softmax statistics (max and normalizer) on the fly. This avoids materializing the full S×S attention matrix, reducing HBM traffic. The core assumption is that memory savings outweigh recomputation and update overhead for long sequences. Evidence: [abstract] mentions online softmax and streaming; section 2.2 describes streaming; section 4.1 shows performance degrades at S=8192, supporting the overhead tradeoff.

### Mechanism 2: cuTile Python Abstraction
TiledAttention is expressed as a Python tile program using cuTile, which abstracts CUDA tile IR. Schedule knobs (TM, TN, staging, layout) are exposed as arguments, enabling easy modification from Python without editing low‑level CUDA. This allows rapid schedule experimentation while generating realistic machine code. The performance gap versus hand‑tuned fused kernels is acceptable for research. Evidence: [abstract] highlights modifiability; section 3.2 lists tunable parameters; section 5 emphasizes fast iteration and reproducible profiling. Break condition: abstraction overhead may limit peak performance (0.632× fused throughput reported).

### Mechanism 3: Reproducible Benchmarking
A standardized harness enforces warmup, median/p95 timing with CUDA events, correctness checks, and isolation. Results are collected across a comprehensive grid of configuration parameters on NVIDIA DGX GB10. This methodology ensures meaningful comparisons and validates performance trends. Evidence: [abstract] mentions DGX‑ready reproducibility; section 3.2 details harness policies; sections 4.1–4.5 present results relying on controlled measurement.

## Architecture Onboarding

**Component map:** Python API layer → cuTile compiler → Kernel runtime → Benchmark harness  
- Python API: validates inputs, triggers JIT.  
- cuTile compiler: generates CUDA kernel from tile program + schedule; caches by hash.  
- Kernel runtime: launches CTAs, performs tile streaming, updates accumulators, writes output.  
- Benchmark harness: warmup, timed runs (CUDA events), optional NSight, correctness validation.

**Critical path:**  
1. First call with new schedule parameters → cuTile JIT compiles kernel (high latency).  
2. Subsequent calls use cached binary; harness disables autotuning.  
3. Kernel launch: CTA assignment → shared memory allocation → tile streaming loop (KV load, GEMM, mask, online softmax update) → write‑back.

**Design tradeoffs:**  
- Tiling parameters: Larger TM improves query reuse but reduces occupancy; larger TN improves KV streaming efficiency but increases shared memory. Optimal = TM=64, TN=128 for D=128.  
- Staging/prefetch depth: More stages hide latency but consume shared memory/registers.  
- Online softmax vs fused epilogue: separation may reduce overlap compared to fused kernels.

**Failure signatures:**  
- Low occupancy (<30%): tile sizes too large → reduce TM/TN.  
- High global memory traffic: KV re‑streaming due to misaligned tiles → check `ncu --metrics gpu__dram__read_transactions`.  
- Poor scaling with S: online softmax overhead dominates → try larger TN or vectorized loads.

**First 3 experiments:**  
1. **Reproduce baseline:** Run harness on S=4096, D=128, FP16, non‑causal with default (TM=64, TN=128). Expect TiledAttention ≈63% of fused SDPA throughput.  
2. **Tile sweep:** For S=8192, D=128, sweep TN ∈ {64,128,256} with TM=64. Plot throughput; peak near TN=128.  
3. **Short‑S regime:** Run S=512, D=128. TiledAttention should be >90% of fused; if not, increase TM to 128.

## Open Questions the Paper Calls Out

- **Backward pass and fused operations**  
  The paper evaluates only the forward pass; backward and fused variants are future work. Unresolved because training requires backward passes and often fused kernels for efficiency. Evidence needed: implement and benchmark backward/fused variants within cuTile, comparing throughput and memory usage against existing baselines on training tasks.

- **Portability to non‑Blackwell GPUs**  
  The target is Grace–Blackwell / Blackwell‑class GPUs; portability to other architectures may require additional schedules. Unresolved because evaluation is confined to DGX GB10; architectural differences (memory bandwidth, warp size) may affect tiling efficiency. Evidence needed: port the kernel to diverse architectures (e.g., Ampere, Hopper, AMD GPUs), run the same harness, and analyze required schedule tweaks and performance deltas.

- **Expanded tiling parameter search and automated tuning**  
  The paper studies a deliberately small tuning space; extending to larger search spaces is an important next step. Unresolved because broader searches may improve performance but incur higher tuning cost. Evidence needed: conduct systematic search over broader parameters (TM, TN, staging depths) using methods like Bayesian optimization, report gains across all grid points, and evaluate tuning overhead versus benefits.

## Limitations
- Tuning space incompleteness: Optimal TM/TN values are provided only for a few shapes; full 80‑regime sweep logs are missing, making exact peak reproduction uncertain.
- Architecture lock‑in: Performance is benchmarked solely on NVIDIA DGX GB10; transferability to other GPU architectures (e.g., Ampere, Hopper) is unknown and may require significant re‑tuning.
- Gap etiology: The ~37% throughput deficit versus fused PyTorch SDPA is attributed to abstraction overhead, but the precise breakdown (occupancy, instruction mix, traffic) lacks microbenchmark evidence.

## Confidence
- **Avoids full matrix materialization + online softmax:** High – core mechanism clearly described, analytically sound, and supported by performance trends (degradation at large S).
- **cuTile modifiability:** Medium – schedule knobs are exposed, but magnitude of tunable performance gain vs. hand‑rolled CUDA is inferred, not exhaustively benchmarked.
- **Reproducible benchmarking:** High – rigorous harness policies documented; baseline numbers specific enough for replication on compatible hardware.
