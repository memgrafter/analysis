# EPOCH: An Agentic Protocol for Multi-Round System Optimization

## Quick Facts
- **arXiv ID:** 2603.09049
- **Source URL:** https://arxiv.org/abs/2603.09049
- **Reference count:** 20
- **Primary result:** A two-phase protocol with strict role separation and round-level artifact tracking yields stable, traceable optimization across heterogeneous tasks (code, hyperparameters, prompts, rules), achieving significant gains and autonomous termination.

## Executive Summary
EPOCH is a protocol designed to coordinate multi-round optimization of complex systems in a reproducible and integrity-preserving manner. It addresses the lack of standardized methods for iteratively improving diverse components like prompts, code, and hyperparameters. The core innovation is a two-phase structure: first, it establishes an executable baseline from a specification; second, it runs iterative loops where hypothesis generation (Investigator) is strictly separated from evaluation (Reviewer). Each round produces a structured artifact, and evaluation uses a canonical command interface. Empirical evaluation on four small-scale tasks demonstrates consistent improvement, explicit state transitions, and self-termination upon metric saturation, suggesting the protocol's robustness across different optimization domains.

## Method Summary
The protocol defines a reproducible process with two phases. Phase I uses a Seed Planner to design a baseline system and evaluation interface, and a Baseline Executor to implement and validate it, producing an initial accepted state. Phase II begins a multi-round loop orchestrated by an Orchestrator. In each round, an Investigator analyzes training-side signals to propose a change (a "delta"), an Executor applies it within constrained action spaces, and a Reviewer runs a fixed canonical evaluation command to issue an accept/reject/terminate verdict based on task-defined metrics and constraints (e.g., minimum improvement, overfitting guards). Every round’s artifacts—investigation report, proposed delta, evaluation results—are recorded, creating an auditable chain of states and decisions that separates the logic of proposing changes from validating them.

## Key Results
- **Fibonacci (code improvement):** Achieved a 99.9% runtime reduction from the baseline and self-terminated when further Python-level gains were negligible.
- **MNIST (hyperparameter tuning):** Improved held-out accuracy by 12.7 percentage points; explicitly rejected an overfitting change (aggressive learning rate) and successfully retried with a different strategy.
- **SST-2 (prompt tuning):** Reached perfect held-out accuracy in three rounds while enforcing strict train/evaluation separation to prevent data leakage.
- **Iris (rule-based optimization):** Attained 100% evaluation accuracy and rejected refinements that would have overfitted to the training data.

## Why This Works (Mechanism)

### Mechanism 1: Role Separation Preserves Evaluation Integrity
- **Claim:** Separating hypothesis generation (Investigator) from evaluation (Reviewer) prevents data leakage and overfitting in iterative optimization.
- **Mechanism:** The Investigator only accesses training-side signals or visible tests, while the Reviewer assesses candidate changes on a held-out evaluation interface or committed artifacts. This logical and often physical separation prevents the loop from inadvertently optimizing for the evaluation metric itself.
- **Core assumption:** Optimization pressure will corrupt evaluation if the same evidence used to generate changes is also used to accept them.
- **Evidence anchors:** [abstract] "separating hypothesis generation from evaluation to ensure integrity." [section 2.4] "To preserve the integrity of the evaluation. The roles that generate or implement hypotheses are distinct from the role that evaluates them."
- **Break condition:** If Investigator and Reviewer collapse into a single component or LLM call, feedback loops can directly optimize the metric, bypassing the integrity guard.

### Mechanism 2: Round-Level Artifacts Ensure Reproducible Trajectories
- **Claim:** Recording each round as a structured unit with a canonical evaluation command creates a traceable, auditable optimization history.
- **Mechanism:** Each round produces artifacts (investigation report, delta, metrics) and uses a fixed `eval_cmd` derived from the task spec. This standardizes measurement across all candidate states, turning the optimization trajectory into a chain of comparable states and decisions.
- **Core assumption:** Without explicit per-round state capture and standardized evaluation, iterative optimization becomes a black box where changes and effects cannot be reliably compared or repeated.
- **Evidence anchors:** [abstract] "round-level artifact tracking." [section 2.4] "EPOCH records each optimization round as a structured unit of experimentation... This round-level structure allows us to reconstruct how and why the system evolved over time." [section A.2] Example directory structure with per-round files.
- **Break condition:** If evaluation commands vary per round or artifacts are not consistently recorded, traceability and reproducibility are lost.

### Mechanism 3: Two-Phase Structure Handles Unstable Initial States
- **Claim:** Isolating baseline construction from iterative refinement ensures Phase II always starts from a valid, evaluated state.
- **Mechanism:** Phase I (Seed Planner + Baseline Executor) transforms a problem spec into an accepted executable baseline with initial metrics. Only after this state is established does Phase II begin its iterative loop. This prevents refinement from chasing objectives on an invalid or unevaluated initial system.
- **Core assumption:** Many problems lack a pre-existing, validated baseline; starting iterative loops on unstable states causes failure modes like chasing incorrect objectives.
- **Evidence anchors:** [abstract] "first establishing an executable baseline, then conducting iterative self-improvement." [section 2.2] "Phase I transforms a problem specification into an accepted executable baseline... EPOCH therefore treats baseline construction as part of the protocol rather than as an external prerequisite." [section 2.3] "Once an accepted baseline has been established, EPOCH enters Phase II..."
- **Break condition:** Skipping Phase I or using an unvalidated initial state in Phase II risks optimizing a mis-specified or broken system.

## Foundational Learning
- **OODA Loop (Observe-Orient-Decide-Act):** EPOCH protocolizes this strategic cycle. Understanding it clarifies why each round is structured: observe current state + training signals, orient via Investigator analysis, decide via Reviewer verdict, act via Executor implementation. *Quick check:* If "Orient" (analysis) and "Decide" (review) are performed by the same agent without separation, how does that compromise evaluation integrity and loop stability?
- **Train/Evaluation Separation & Data Leakage:** A core ML principle enforced by the protocol. Investigator is confined to training data; Reviewer uses a held-out set. This prevents the optimization from inadvertently tuning to the test metric. *Quick check:* In SST-2 prompt tuning, why must the Investigator be barred from seeing the 12 held-out evaluation examples when proposing few-shot additions?
- **Canonical Command Interface:** A fixed evaluation command (e.g., `python evaluate.py`) derived from the task spec and used identically in every round. This technical detail ensures all candidate states are measured consistently, making improvements comparable. *Quick check:* If the eval command for a code task changed in Round 3 to include an additional hidden test, how would that invalidate comparisons to Round 2's metrics?

## Architecture Onboarding
- **Component map:**
  Phase I: Seed Planner -> Baseline Executor
  Phase II Loop: Orchestrator -> Investigator -> Executor -> Reviewer -> ( verdict: Accept? Update Accepted State; Reject? Retry; Terminate? Stop )
- **Critical path:** Task Specification (`task_spec.yaml`) → Phase I (Planner designs, Executor implements) → **Accepted Baseline Artifacts** → Phase II Loop (Orchestrator schedules, Investigator proposes, Executor applies, Reviewer evaluates) → Termination (metric saturation or round limit).
- **Design tradeoffs:**
  - Rigidity vs Safety: Strict role separation and command standardization reduce failure modes (leakage, drift) but add overhead and may be overly bureaucratic for simple, single-artifact tuning.
  - Overhead vs Traceability: Per-round artifact creation and fixed evaluation commands incur computational/logistical costs but are necessary for auditability and reproducibility in production settings.
  - Generality vs Performance: EPOCH is a coordination protocol, not a task-specific optimizer. It may not reach state-of-the-art on any single benchmark compared to a specialized algorithm, but provides a stable, consistent process across heterogeneous tasks.
- **Failure signatures:**
  - Protocol violation: Investigator accesses evaluation data; Reviewer accepts a change without running the canonical `eval_cmd`.
  - State corruption: Executor modifies protected files (e.g., eval dataset, fixed model architecture) marked immutable in `task_spec.yaml`.
  - Stuck loop: Investigator repeatedly proposes changes that fail to meet `min_delta`, or Reviewer rejects changes due to an overly strict `acceptance_rule` (e.g., train-eval gap threshold).
  - Baseline failure: Phase I cannot produce a runnable baseline from the spec, preventing Phase II from starting.
- **First 3 experiments:**
  1. **Fibonacci (Code Improvement):** Tests staged optimization (correctness then performance), uses visible tests for Investigator, and demonstrates self-termination when gains cease.
  2. **MNIST (Hyperparameter Fine-Tuning):** Tests strict train/eval separation, shows explicit rejection of an overfitting change (high learning rate), and recovery via a retry with a different strategy (SGD).
  3. **SST-2 (Prompt Tuning):** Tests leakage prevention (Investigator builds few-shot examples from training data only), handles non-deterministic LLM evaluation, and terminates early upon metric saturation.

## Open Questions the Paper Calls Out
- **Multi-agent coordination:** How can EPOCH be extended beyond a single agent per role to coordinate multiple, interacting agents over complex systems?
- **Large-scale, long-horizon optimization:** How does the protocol scale to problems requiring many more rounds, larger datasets, or high-dimensional search spaces? Current experiments use small subsets and ≤5 rounds.
- **LLM sensitivity:** How sensitive is EPOCH's performance to the choice of underlying LLM? The paper only tests GPT-4.1-nano; model-agnostic design suggests other models could be used, but their impact on acceptance rates, round count, and final metrics is unknown.

## Limitations
- **Implementation gap:** The full codebase and detailed logs are not publicly available, preventing direct inspection and independent replication.
- **Experimental underspecification:** Key details like exact LLM prompts, model versions, hyperparameter search spaces, and data splits are omitted, hindering faithful reproduction.
- **Scalability untested:** The protocol's behavior on large-scale, high-dimensional, or long-horizon tasks (e.g., full ImageNet training) remains an open question.
- **Overhead unquantified:** The computational and logistical costs of artifact tracking, canonical evaluations, and role separation are not measured.

## Confidence
- Role separation ensures evaluation integrity: **Medium** (plausible design principle, supported by description but not independently validated).
- Round-level artifacts guarantee reproducibility: **Medium** (supported by protocol description and example structures, but no code to verify enforcement).
- Two-phase baseline construction enables stable iteration: **Medium** (empirically supported on four small tasks, but generalization to complex problems is uncertain).
- Overall protocol achieves stable cross-task optimization: **Medium** (results are promising across diverse task types, but limited to small-scale experiments).

## Next Checks
1. **Release and replicate:** The authors must release the full codebase, including task specs, role implementations, and orchestration logic. Independent replication of all four experiments should verify reported metrics and artifact structures.
2. **Ablation on role separation:** Conduct an experiment where Investigator and Reviewer roles are merged into a single LLM call. Measure overfitting on held-out sets (e.g., train-eval gap) to empirically test the necessity of the integrity mechanism.
3. **Scale-up trial:** Apply EPOCH to a larger benchmark (e.g., fine-tuning a transformer on a standard dataset like full ImageNet or GLUE) with a higher round budget to assess protocol stability, overhead, and final performance relative to scaled baselines.
