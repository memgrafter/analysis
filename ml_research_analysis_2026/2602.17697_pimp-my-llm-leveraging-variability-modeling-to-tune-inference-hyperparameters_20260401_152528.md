# Pimp My LLM: Leveraging Variability Modeling to Tune Inference Hyperparameters

## Quick Facts
- **arXiv ID:** 2602.17697
- **Source URL:** https://arxiv.org/abs/2602.17697
- **Reference count:** 40
- **Primary result:** A feature model encoding 96 Hugging Face Transformers inference hyperparameters enables systematic optimization; Random Forest predictors trained on sampled configurations achieve R² >0.94 for energy, latency, and accuracy.

## Executive Summary
This paper addresses the combinatorial explosion of LLM inference hyperparameter configurations, which hinders systematic optimization for energy, latency, and accuracy. It proposes a feature-based variability model for Hugging Face Transformers, encoding 96 features and their constraints. Using this model, configurations are sampled via 2-wise and random strategies, measured on three metrics, and used to train predictive models. The approach enables analysis of individual and interacting hyperparameter effects, and Pareto analysis reveals distinct trade-off classes: low-energy configurations favor dynamic caching and greedy decoding, while high-accuracy setups require more beams and higher energy consumption.

## Method Summary
The core pipeline consists of four steps: (1) Model the variability of Hugging Face Transformers generation hyperparameters as a feature model with propositional constraints, yielding ~9.37×10¹² valid configurations. (2) Sample a manageable subset using 2-wise interaction-aware samplers (YASA, ICPL) and random sampling. (3) Execute each configuration on three open-source models (<8B parameters) using the HumanEval+ benchmark, measuring energy (via RAPL and nvidia-smi), latency, and pass@1 accuracy after a calibration and warm-up phase. (4) Train Random Forest regressors on the collected data to predict metrics for unseen configurations, achieving high R² scores.

## Key Results
- The feature model captures 96 features and constraints, defining a valid configuration space of approximately 9.37×10¹².
- Predictive models trained on the combined sampler (`ALL`) achieve high accuracy: R² = 0.95 (energy), 0.94 (latency), 0.99 (accuracy).
- Pareto analysis identifies two dominant trade-off classes: low-energy configurations use dynamic caching and greedy decoding; high-accuracy configurations employ more beams and higher energy consumption.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** A feature model explicitly encodes inference hyperparameters and their constraints, making the vast configuration space analyzable and preventing invalid configurations.
- **Mechanism:** The hyperparameters (e.g., `temperature`, `num_beams`, `cache_implementation`) and their allowed values are represented as hierarchical features with cross-tree constraints (requires, excludes). This propositional logic model allows automated generation of only valid configurations for systematic exploration.
- **Core Assumption:** The model accurately captures all mandatory and optional dependencies between hyperparameters as defined in the Hugging Face Transformers library.
- **Evidence Anchors:**
  - [abstract] "We encode the variability of the Hugging Face Transformers library in a publicly available feature model... resulting in approximately 9.37 × 10¹² valid configurations."
  - [section 3.2] "Dependencies and constraints between features were extracted from official documentation, source code inspection, and empirical testing, ensuring that all configurations generated from the model are valid and executable."
  - [corpus] Corpus neighbors focus on LLM efficiency and configuration but do not directly discuss feature model construction for LLMs, indicating this is a novel application.
- **Break Condition:** If key constraints are missing or incorrectly modeled, the generated configuration set will contain invalid or failing configurations, as hinted by the ~3% failure rate reported in Section 6.2.

### Mechanism 2
- **Claim:** Sampling strategies (t-wise and random) can efficiently select a small, representative subset of valid configurations from the intractable space, enabling meaningful empirical analysis and model training.
- **Mechanism:** Instead of exhaustive evaluation, algorithms like YASA and ICPL perform t-wise sampling to guarantee coverage of all individual parameters and their pairwise (t=2) interactions. Random sampling provides a baseline. The sampled set is used for measurement and learning.
- **Core Assumption:** A limited set of configurations that covers parameter interactions (t-wise) or is randomly distributed is sufficient to learn accurate performance/energy/accuracy predictors and identify dominant effects.
- **Evidence Anchors:**
  - [abstract] "Sampling representative configurations, measuring their energy consumption, latency, accuracy, and learning predictive models from the collected data."
  - [section 3.3] "We adopted three complementary sampling strategies: two interaction-aware strategies based on 2-wise coverage... and one random strategy... ensuring that combinations of up to 𝑡 features are covered at least once."
  - [section 5, RQ3] Models trained on the combined `ALL` sampler (all strategies) achieve the best prediction accuracy (R²: 0.95 energy, 0.94 latency, 0.99 accuracy).
- **Break Condition:** If the configuration space contains high-order interactions (t>2) that critically affect metrics, 2-wise sampling may miss them, potentially degrading model accuracy for certain regions of the space.

### Mechanism 3
- **Claim:** Machine learning models (Random Forest) can be trained on measured data from a small set of sampled configurations to accurately predict energy, latency, and accuracy for unseen, valid configurations.
- **Mechanism:** Measurements from the sampled configurations form a dataset (features=hyperparameters, targets=metrics). A Random Forest Regressor is trained via grid search and k-fold CV to learn the mapping from configuration to metric. The model generalizes to predict outcomes for new configurations without measurement.
- **Core Assumption:** The relationship between hyperparameters and the target metrics (energy, latency, accuracy) is learnable from a finite, representative sample and is stable enough for prediction within the modeled configuration space.
- **Evidence Anchors:**
  - [section 3.5] "We rely on Random Forest Regression... to assess whether models trained on a limited yet representative set of configurations can accurately predict..."
  - [section 5, RQ3 & Table 5] The `ALL` sampler model achieves R² = 0.95 (energy), 0.94 (latency), 0.99 (accuracy), with low MAE/MAPE, demonstrating high predictive accuracy.
  - [section 6.2] Acknowledges limitations: performance depends on the target metric and sampling strategy; external validity is limited to code generation and specific models.
- **Break Condition:** Prediction accuracy would drop significantly (low R², high MAE) if the training sample is not representative of the target configuration's region (e.g., due to undersampled interactions) or if metrics are highly stochastic or dependent on external factors (dataset, model) not captured in the feature model.

## Foundational Learning
- **Concept: Feature Modeling (Feature Models)**
  - Why needed here: It is the foundational technique to manage the combinatorial explosion. It transforms an informal, vast set of hyperparameters into a formal, analyzable model of valid configurations.
  - Quick check question: What is the difference between a "mandatory" feature and an "optional" feature in a feature model, and how would you represent `do_sample` (sampling on/off) and `num_beams` (integer >0)?
- **Concept: t-wise Sampling (Interaction-aware Sampling)**
  - Why needed here: Exhaustive measurement is impossible; t-wise sampling provides a theoretical guarantee to cover parameter interactions up to strength *t*, which is critical since hyperparameters often interact non-additively.
  - Quick check question: Why might 2-wise sampling still miss important effects if all significant interactions involve 3 or more specific hyperparameters simultaneously?
- **Concept: Sampling-Measuring-Learning Pipeline for Configurable Systems**
  - Why needed here: This established pattern from software variability engineering allows learning system behavior (energy, latency) from a small sample, avoiding exhaustive evaluation. It bridges SE and ML.
  - Quick check question: What are the key risks in the "measuring" step that could corrupt the training data for the predictive model (e.g., hardware noise, warm-up effects)?

## Architecture Onboarding
- **Component map:** Feature Model -> Sampler -> Executor/Measurer -> Data Processor -> Predictor Trainer -> Analyzer
- **Critical path:** Feature Model -> Sampler -> Executor/Measurer -> Data Processor -> Predictor Trainer -> Analyzer.
- **Design tradeoffs:**
  - FM Granularity: Finer discretization of numerical parameters increases model expressiveness but explodes the valid configuration count exponentially.
  - Sampling Strategy: 2-wise (YASA/ICPL) ensures interaction coverage but may produce less diverse samples than random. Combining (`ALL`) mitigates this but requires more measurements.
  - Model Complexity: Random Forest offers good accuracy and interpretability but may not capture very high-order interactions as well as other models; chosen for consistency with prior SPL literature.
  - Measurement Fidelity: Software-based power measurement (RAPL, nvidia-smi) is accessible but less precise than external power meters; absolute values include system noise, though relative comparisons are valid.
- **Failure signatures:**
  - FM/Sampler: >3% of generated configurations fail to execute, indicating missing/incorrect constraints in the FM.
  - Executor: High variance in energy measurements across repeats suggests unstable warm-up calibration or external system load.
  - Predictor: Low R² (<0.7) or high MAE on test set indicates the sample is not representative or critical interactions are unmodeled.
  - Analyzer: Feature-wise analysis shows a parameter has both very high positive and very high negative impact, suggesting a strong interaction is present and not captured by main effects alone.
- **First 3 experiments:**
  1. FM Validation Experiment: Generate 1000 configurations from the FM using the sampler. Execute each with a trivial prompt (e.g., "Hello") and a fast, small model (e.g., Qwen-3B). Goal: Verify <1% failure rate, confirming constraint completeness. Report invalid configs for FM debugging.
  2. Sampling Strategy Comparison: Using a fixed, small LLM (e.g., Qwen-3B) and 20 HumanEval+ problems, generate 50 configurations from each sampler (YASA, ICPL, RANDOM). Measure energy and latency. Goal: Compare the distribution (range, mean) of metrics across samplers. Check if 2-wise samplers cover more extreme values than random.
  3. Prediction Sanity Check: Train a Random Forest on the `ALL` sampler data for a single LLM (e.g., Qwen-7B) using only a subset of features (e.g., cache, num_beams, temperature, top_p). Evaluate on a held-out test set. Goal: Achieve R² > 0.9 for energy/latency. If not, inspect feature importances and residual plots for signs of missing key features or non-linearities not captured.

## Open Questions the Paper Calls Out
- **Open Question 1:** How do hyperparameter effects and trade-offs differ in other inference servers (e.g., vLLM, TGI)?
  - Basis in paper: [explicit] Future work cites extending the methodology to other inference servers.
  - Why unresolved: The study only evaluated Hugging Face Transformers; other servers may expose different configuration options and implement parameters differently, potentially altering observed impacts.
  - What evidence would resolve it: Construct feature models for alternative servers, replicate the sampling-measurement-learning pipeline, and compare the relative importance of hyperparameters and Pareto fronts.
- **Open Question 2:** Are the identified hyperparameter influences and accuracy-energy-latency trade-offs generalizable to other NLP tasks beyond code generation?
  - Basis in paper: [explicit] Future work mentions extending to other datasets, and external validity threats note the exclusive use of HumanEval+ for code generation.
  - Why unresolved: Task-specific generation behaviors and accuracy metrics (e.g., BLEU for translation) may shift which hyperparameters are most impactful and how trade-offs manifest.
  - What evidence would resolve it: Conduct the same variability-driven exploration on datasets for summarization, translation, or dialogue, and analyze whether the same features dominate and similar trade-off classes emerge.
- **Open Question 3:** How can hardware configurations (e.g., GPU type, CPU DVFS) and deployment options (e.g., batching, parallelism) be modeled as variability, and what is their combined effect with inference hyperparameters on energy, latency, and accuracy?
  - Basis in paper: [explicit] Future work proposes enriching the variability model with hardware configurations and deployment options.
  - Why unresolved: The current feature model solely covers generation hyperparameters; hardware and deployment factors are fixed, so their interactions and potential for new trade-offs remain unknown.
  - What evidence would resolve it: Extend the feature model to include hardware/deployment features, sample configurations across all variability levels, measure metrics, and perform feature-wise/pairwise analysis to quantify their contributions.
- **Open Question 4:** Can the variability model enable adaptive reconfiguration during inference to dynamically optimize trade-offs in response to real-time constraints or user preferences?
  - Basis in paper: [explicit] Future work aims to leverage the approach for adaptive reconfiguration during inference, enabling runtime trade-off management.
  - Why unresolved: The presented approach is offline and static; runtime adaptation introduces challenges such as reconfiguration overhead, prediction latency, and handling dynamic workloads.
  - What evidence would resolve it: Implement a runtime system that uses the feature model and learned predictors to switch configurations on-the-fly based on monitored metrics, then evaluate its effectiveness in reducing energy or improving accuracy under varying loads.

## Limitations
- Feature model completeness: The reported ~3% configuration failure rate suggests potential missing or incorrect constraints; exact specification depends on the Zenodo artifact.
- Discretization details: Value sets for continuous hyperparameters (e.g., `temperature`, `top_p`) are not documented, affecting configuration space size and sampling.
- Generalizability: Findings are limited to code generation with <8B open-source models on HumanEval+; other tasks, model sizes, or datasets may behave differently.
- Measurement fidelity: Energy/latency results rely on software-based tools (RAPL, nvidia-smi) and specific warm-up/calibration; hardware or setup deviations may skew values.

## Confidence
- FM-based valid configuration generation: Medium-High (explicit constraints from docs/code, but 3% failures suggest gaps).
- 2-wise sampling sufficiency: Medium (combined `ALL` sampler yields best predictors, but high-order interactions could be missed).
- Random Forest prediction accuracy (R² >0.94): High (strong empirical results on test sets, but dependent on sample representativeness and FM coverage).
