# M2F: Automated Formalization of Mathematical Literature at Scale

**ArXiv ID:** 2602.17016  
**Source URL:** https://arxiv.org/abs/2602.17016  
**Reference count:** 40  
**Primary result:** In ~3 weeks, M2F produced a fully buildable Lean library of 153,853 lines from 479 pages of textbooks and achieved 96% proof success on the FATE‑H benchmark, outperforming a strong baseline (80%).

## Executive Summary

Automating the formalization of large mathematical texts requires handling cross-file dependencies, import resolution, and end-to-end project compilation. M2F addresses this with a two‑stage agentic framework for Lean. The first stage (statement compilation) decomposes documents into atomic blocks, orders them by inferred dependencies, and iteratively repairs declaration skeletons—allowing `sorry` placeholders—until the entire project compiles. The second stage (proof repair) closes the holes under fixed signatures using goal‑conditioned local edits. Throughout both stages, edits are committed only when Lean’s toolchain feedback confirms improvement (VeriRefine). In about three weeks, M2F generated a buildable Lean library of 153,853 lines from 479 pages of real and convex analysis textbooks. On the FATE‑H benchmark, it achieved 96% proof success versus 80% for a strong baseline, and under matched statements it closed all 875 proof holes (100%). The results demonstrate that large‑scale automated formalization is practically achievable.

## Method Summary

The pipeline begins with a preprocessor that converts LaTeX/PDF sources into an ordered dataset of JSON items, each representing a mathematical declaration (definition, lemma, theorem) with provenance spans and fields for statement and proof. Stage 1 processes statements sequentially: for each item, a Lean skeleton is generated (with `sorry` in the proof body) and inserted into a target file based on section numbering. Forward references are temporarily satisfied by emitting typed stubs (e.g., `theorem n_b : T_b := by sorry`). A verifier‑certified refinement loop (VeriRefine) then attempts up to \(K\) repairs: the file is snapshotted, a patch is applied within a scoped region, Lean verifies the file, and the patch is accepted only if the stage objective (total error count, then local error reduction) strictly improves; otherwise the edit is reverted. After all statements, the project must build with zero errors (though `sorry` is allowed). Stage 2 freezes signatures and iterates over proof holes: for each hole, it optionally splits large files, fixes any compile errors, obtains the current goal state (via LSP/MCP), plans a proof, and proposes up to \(R\) attempts per plan across up to \(C\) plans, using the same accept/revert rule with the objective of hole removal. All operations run under a pinned Lean environment (specific version and mathlib commit) to ensure deterministic verifier feedback. Outputs include the final Lean project and a provenance map linking each declaration to its source spans.

## Key Results

- Generated a fully buildable Lean library of 153,853 lines from 479 pages of textbooks, with 100% statement coverage (SCC) and 100% proof closure on the audited set (875 holes).
- Achieved 96% proof success on the FATE‑H benchmark under matched statements, exceeding a strong baseline by 16 percentage points.
- Showed efficient repair: average repair rounds for statement blocks ranged from 0.08 to 0.42, indicating rapid stabilization without oscillation.

## Why This Works (Mechanism)

**Mechanism 1: Verifier‑certified refinement loop (VeriRefine)**  
Claim: The verifier‑certified refinement loop guarantees monotonic progress toward end‑to‑end buildability and prevents error accumulation over long runs.  
Mechanism: For each candidate edit confined to a scope \(S\), the system snapshots the file, applies the patch within \(S\), reruns file verification, and commits only if the stage objective strictly improves. Stage 1’s objective is \((\operatorname{err}(\Delta), \operatorname{err}_S(\Delta,S))\); Stage 2 replaces the secondary term with remaining sorry count. Otherwise the edit is reverted. The verifier’s diagnostics are the sole acceptance signal.  
Core assumption: Under a pinned environment \(E\) (Lean version + library commit), elaboration is deterministic and the number of errors reliably reflects proximity to a buildable state.  
Evidence: Abstract states “committing edits only when toolchain feedback confirms improvement”; Section 4.2 proves monotonicity of accepted patches; Table 3 shows average repair rounds below 0.5, indicating quick stabilization without oscillation.  
Break condition: Non‑deterministic elaboration (e.g., hash‑seeded name resolution) or a decoupled objective could cause deadlock or regression.

**Mechanism 2: Separation of statement stabilization and proof completion**  
Claim: Separating statement compilation (with proof placeholders) from proof repair isolates the dominant source of project‑scale failures—imports, namespaces, and type mismatches—making the problem tractable.  
Mechanism: Stage 1 processes ordered statement items, injecting skeletons that may contain `sorry` in proof bodies. It iterates, proposing small repairs guided by diagnostics, until the file elaborates with zero errors. Only after the entire project elaborates (allowing `sorry`) does Stage 2 begin, freezing statement signatures and editing only proofs.  
Core assumption: Most build failures arise at the declaration level (missing definitions, incorrect imports, type errors), not inside proof terms. Once these are fixed, proof repair becomes a well‑posed problem.  
Evidence: Abstract and Section 3.2 describe the separation; Table 3 shows ARR as low as 0.08–0.42, meaning most statement blocks required zero repair after insertion; Table 2 shows final project buildability for all textbooks.  
Break condition: If the source contains many implicit assumptions that cannot be captured in typed stubs, generated statements may be semantically incorrect yet still compile. Conversely, if many blocks exhaust the per‑item budget \(K\) without elaborating, Stage 1 coverage drops.

**Mechanism 3: Atomic decomposition with typed stubs**  
Claim: Atomic decomposition of the source into JSON items with dependency‑aware ordering, supplemented by typed stubs for forward references, yields a linearizable compilation schedule that respects Lean’s elaboration constraints while keeping verification scopes small.  
Mechanism: The preprocessor extracts an ordered sequence of items. For each item, its skeleton is inserted into a target file. If a required name is not yet defined, the system emits a typed stub to satisfy the reference, deferring the actual body until later.  
Core assumption: Mathematical exposition has an underlying DAG structure; forward references are rare and can be temporarily satisfied by stubs without creating irreparable type conflicts.  
Evidence: Section 4.5 describes stub usage; total blocks across long‑form corpora are 1043, with PB=✓ and SCC=100%, indicating successful decomposition and stubbing.  
Break condition: Cyclic dependencies that cannot be broken by stubs (e.g., mutually recursive definitions in each other’s types) cause elaboration failures that the repair loop cannot resolve.

## Foundational Learning

### Verifier-in-the-loop refinement (VeriRefine)
Why needed here: This control pattern turns noisy LLM proposals into a converging build process; without it, errors would accumulate and the project would never compile.  
Quick check: In Stage 1, the primary objective is total error count. If a patch reduces localized errors within the current scope but increases total errors, will it be accepted? What if it reduces both total and localized errors?

### Pinned dependency environment
Why needed here: Deterministic tool feedback is essential for the accept/revert rule to be meaningful. Pinning the Lean version and mathlib revision ensures that repeated verifier calls on the same file yield identical diagnostics, enabling reliable progress tracking and reproducible compute accounting.  
Quick check: If you run M2F with a newer, unpinned mathlib commit, name two specific ways the pipeline could break (e.g., renamed theorems, changed typeclass instances).

### Matched statement evaluation
Why needed here: To isolate proof‑search capability from statement‑generation quality. Stage 2 freezes statement signatures; only proof terms may change. This allows fair comparison of provers and prevents “cheating” by altering the goal.  
Quick check: On FATE‑H, M2F Stage 2 achieves 96% PSR while Seed‑Prover 1.5 achieves 80%. Is this comparison fair? What does “matched statements” mean, and why is it important?

## Architecture Onboarding

### Component map
Preprocessor → Stage 1 Controller (GenSkeleton, RepairPatch) → Stage 2 Controller (Plan, ProposeProofPatch) → Lean Tool Interface; supporting components: Verifier Certification Layer (TryPatch1/TryPatch2), Budget & Checkpoint Manager, Logging Infrastructure, and Output (Lean project + provenance map).

### Critical path
1. Load pinned environment \(E\), initialize empty project.  
2. Preprocess source → ordered JSON items.  
3. Stage 1: For each statement item, determine target file, generate skeleton, insert, define scope, and loop (verify → repair → accept/revert) up to \(K\) attempts.  
4. After all statements, verify full project builds (PB; `sorry` allowed).  
5. Stage 2: For each proof item, locate hole; if file too large, split; loop: verify → if errors, fix → obtain goal state → plan → for \(c=1..C\): for \(r=1..R\): propose proof patch and try; accept if hole removed and file ok; else replan.  
6. Optional final cleanup.  
7. Write final project and provenance.

### Design tradeoffs
- **File‑local verification**: Fast but may miss cross‑file errors; mitigated by final PB check.  
- **Scope‑limited patches**: Keeps edits small but sometimes requires expansion fallback.  
- **Fixed budgets (\(K,R,C\))**: Ensures predictable compute but may cutoff legitimate solutions.  
- **Statement‑first decomposition**: Guarantees buildability even if statements are sub‑optimal for proof search.  
- **Lean as sole oracle**: Guarantees absolute correctness at the cost of many verifier calls.

### Failure signatures
1. **Stage 1 revert**: Block exceeds \(K\) attempts, leading to missing declaration; SCC < 100%.  
2. **Stage 2 unsolved**: Hole remains after \(C·R\) attempts; exit condition `t≥T`.  
3. **Non‑deterministic verifier**: Same file yields different error counts across runs; breaks monotonic logic.  
4. **Scope‑expansion blowup**: Diagnostics consistently lie outside current scope, forcing large edits.  
5. **File‑split failure**: `SplitIfLargeAndResolve` cannot produce compilable part files.  
6. **GoalState unavailable**: Planner degrades to diagnostics‑only mode, reducing performance.  
7. **Provenance mismatch**: Human audit discovers statement divergence from source.

### First 3 experiments
1. **Hello World**: Convert a two‑line source (`def foo := 1`, `theorem bar : foo = 1 := rfl`). Run full pipeline; expect PB=✓ and PSR=100%.  
2. **Stub generation test**: Create source where Lemma B uses Lemma A appearing after B. Run Stage 1 only; verify that when B is processed, a stub for A appears before B, and later the stub is replaced by the actual skeleton.  
3. **Budget‑exhaustion failure**: Take a simple provable theorem (e.g., `0 < 1`). Set tight Stage 2 budgets (\(R=1, C=1\)) and ensure first‑attempt failure. Confirm sorry remains and run records a timeout; then increase budgets and observe success.

## Open Questions the Paper Calls Out
1. How can natural‑language grounding and library navigation be improved to reduce the remaining bottleneck in large‑scale automated formalization?  
2. Can we automate the statement faithfulness audit that currently requires manual expert review?  
3. How accurate is the inferred dependency ordering among mathematical statements, and does inaccuracy increase repair effort?  
4. What are the fundamental limitations causing the two unsolved FATE‑H instances, and can extended planning or compute overcome them?

## Limitations
- **Undisclosed LLM setup**: Exact Codex CLI parameters, prompts, and temperature schedules are unreleased, preventing exact replication of Stage 2 results.  
- **Closed preprocessing**: The PDF/LaTeX → JSON pipeline used for long‑form corpora is not open‑sourced; only pre‑processed artifacts are available.  
- **Missing audit data**: The set of audited statements and provenance mappings are not published, so the claim of 100% statement fidelity cannot be independently verified.

## Confidence
- **End‑to‑end buildability on provided corpora**: High (artifact builds successfully).  
- **Proof repair success on FATE‑H (96% PSR)**: Medium (depends on unreleased LLM configuration and specific mathlib commit).  
- **Mechanism claims (VeriRefine, separation, atomic decomposition)**: Medium (supported by metrics but core assumptions lack independent validation).
