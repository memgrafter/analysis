# Code-A1: Adversarial Evolving of Code LLM and Test LLM via Reinforcement Learning
## Quick Facts
- arXiv ID: 2603.15611
- Source URL: https://arxiv.org/abs/2603.15611
- Reference count: 40
- Primary result: Code-A1 achieves state-of-the-art code generation, surpassing Golden Tests and Self-Play baselines, and dramatically improves test generation efficiency.

## Executive Summary
Code-A1 introduces an adversarial co-evolution framework that jointly optimizes a Code LLM and a Test LLM with opposing objectives. The Code LLM aims to produce solutions that pass generated tests, while the Test LLM attempts to expose defects in the Code LLM's outputs. This overcomes limitations of static test suites and self‑play, where a single model risks self‑collusion or generic testing. Key innovations include architectural separation enabling safe white‑box test generation, a Mistake Book for experience replay, and a composite reward balancing test validity with adversarial difficulty. Evaluations on Qwen2.5‑Coder models (1.5B, 3B, 7B) demonstrate superior code generation performance and significantly more effective test generation compared to baselines.

## Method Summary
Code-A1 employs two separate language models initialized from the same checkpoint: a Code LLM (π_C) that generates candidate solutions for programming problems, and a Test LLM (π_T) that generates test cases (in assertion format) conditioned on the candidate code. The training loop proceeds in iterations. For each sampled question, the Code LLM produces multiple (M=8) candidate solutions. For each solution, the Test LLM generates multiple (N=8) test suites, with white‑box access to the candidate code to craft targeted tests. Generated tests are validated against ground truth solutions to correct wrong predictions and discard invalid ones. Each candidate code is executed against a combined set of validated new tests and historical failing tests from the Mistake Book (B), which stores failures per question. The Code LLM receives a reward equal to the average pass rate across these tests. The Test LLM receives a composite reward: α·R_val + (1−α)·R_adv, where R_val is the fraction of valid tests, and R_adv measures adversarial difficulty (tests that fail code previously passing historical tests). The Mistake Book is updated by adding new failures and removing tests that are persistently passed. Training uses Group Relative Policy Optimization (GRPO) with asynchronous updates. Asymmetric sampling selects only the top‑ℓ (ℓ=1) test suite groups (by reward variance) to update the Test LLM, reducing compute while preserving learning signal.

## Key Results
- On the 3B model, average code generation score (Avg) reaches 66.15% vs. 65.14% for the Golden Tests baseline.
- Test generation Mul score (pass@5 × mut@5) for the 3B model is 15.29, exceeding the 7B base model's 14.72 and far ahead of SFT's 8.53.
- Ablations confirm that white‑box access, the composite reward, and the Mistake Book are all critical for performance.

## Why This Works (Mechanism)
Code-A1's effectiveness arises from three interrelated mechanisms:

**Mechanism 1: Architectural separation eliminates self‑collusion while enabling white‑box testing.** By decoupling code generation and test generation into two separate policies with opposing objectives, the Test LLM has no incentive to generate trivial tests even when it can inspect the Code LLM's candidate code. This avoids the dilemma in self‑play where a single model either produces generic tests (black‑box) or colludes to produce easy tests (white‑box).

**Mechanism 2: Composite reward balances test validity and adversarial difficulty.** The Test LLM's reward combines a validity component (ensuring tests are executable, correct, and unique) with an adversarial component that incentivizes tests which fail candidate code that historically passed. This prevents the generation of either invalid garbage or overly trivial tests.

**Mechanism 3: Mistake Book stabilizes co‑evolution via per‑question experience replay.** It stores historically failing tests for each question, ensuring the Code LLM does not forget previously fixed bugs and giving the Test LLM a curriculum of increasing difficulty. The Mistake Book is dynamically updated by adding new failures and removing passed tests, maintaining a frontier of current challenges.

Ablation studies provide direct evidence: removing the white‑box access, the composite reward, or the Mistake Book each leads to significant performance drops.

## Architecture Onboarding
- **Component map**: Questions -> Code LLM (π_C) -> candidate solutions -> Test LLM (π_T) (with white‑box access) -> test suites -> Sandbox Service -> execution results (pass/fail) -> Reward Manager -> Mistake Book (B) (stores historical failing tests, updates after each step) -> rewards for π_C and π_T -> asynchronous GRPO updates for both models.
- **Critical path**:
  1. Sample batch of questions.
  2. Code LLM generates M=8 candidate solutions per question.
  3. For each candidate, Test LLM generates N=8 test suites (white‑box: sees candidate code).
  4. Validate each test suite against ground truth solution; correct wrong predictions, discard invalid tests.
  5. Execute each candidate code against all validated new tests plus Mistake Book tests for that question.
  6. Compute Code LLM reward = average pass rate on the combined tests.
  7. Compute Test LLM reward per test suite: α·valid_fraction + (1−α)·adversarial_term (using historical vs new pass rates).
  8. Select top‑ℓ=1 test suite groups (by reward variance) for Test LLM gradient update (asymmetric sampling).
  9. Update Mistake Book: add new failing tests (frequency=1), decrement/remove passed historical tests.
  10. Perform GRPO updates for Code LLM and Test LLM.
- **Design tradeoffs**:
  - Asymmetric sampling (ℓ vs N): reduces computational load but discards potentially useful low‑variance groups.
  - Composite reward weight α: balances validity and adversarial difficulty; α=0.5 found optimal, mis‑tuning yields invalid or trivial tests.
  - White‑box access: enabled by architectural separation; tradeoff is increased system complexity.
  - Mistake Book size: per‑question buffer must be bounded; pruning via frequency decay prevents memory bloat.
- **Failure signatures**:
  - Test LLM reward collapse (constant high/low) indicates reward imbalance; inspect validity and adversarial components separately.
  - Code LLM forgetting: pass rate on historical Mistake Book tests drops while new‑test pass rate stays high; suggests Mistake Book under‑utilized or too small.
  - Self‑collusion: tests always pass Code LLM's current solutions or are trivial (e.g., assert f(x)==f(x)); monitor test diversity and hardness.
  - Training instability: large variance in Code LLM pass rates across steps; may indicate Test LLM generating tests with inappropriate difficulty; adjust α or Mistake Book update frequency.
- **First 3 experiments**:
  1. Main results comparison: Run Code-A1 against Golden Tests (human‑annotated) and Self‑Play (unified model, black‑box test generation) on code generation benchmarks (HumanEval+, MBPP+, BigCodeBench) and test generation benchmark (UnLeakedTestBench). Expect Code-A1 to outperform both.
  2. Ablation study: Remove key components one at a time: (a) no predicted answer in tests (only function calls), (b) no candidate code access for Test LLM (black‑box), (c) no Mistake Book. Measure degradation on code (Avg) and test (Mul) performance.
  3. Generated tests as static golden tests: Use Code-A1's Test LLM to produce test suites, then fix them as golden tests and train a Code LLM via standard GRPO. Compare against using human‑annotated tests to demonstrate generated test quality.

## Limitations
- Exact prompt templates, test validation logic, and Mistake Book update thresholds are underspecified, hindering exact replication.
- Details of the Golden Tests baseline and Test LLM SFT data are missing, affecting direct comparison.
- Evaluation is restricted to Qwen2.5‑Coder models on KodCode‑V1; generalizability to other architectures and datasets remains unknown.

## Confidence
- Performance superiority (Avg/Mul > baselines): Medium
- Architectural separation prevents self‑collusion: Medium
- Composite reward yields valid and adversarial tests: Medium
- Mistake Book stabilizes training: High
