# See, Plan, Snap: Evaluating Multimodal GUI Agents in Scratch

## Quick Facts
- **arXiv ID:** 2602.10814
- **Source URL:** https://arxiv.org/abs/2602.10814
- **Reference count:** 40
- **Primary result:** Introduces ScratchWorld benchmark and reveals a substantial reasoning-acting gap (78.31% vs 14.46% success) in multimodal GUI agents, with endpoint localization in drag-and-drop as the primary bottleneck.

## Executive Summary
This paper addresses the underexplored problem of evaluating multimodal GUI agents on program-by-construction tasks in block-based environments like Scratch. It introduces ScratchWorld, a benchmark of 83 tasks across four categories (Create, Debug, Extend, Compute), using two interaction modes to separate logical reasoning (composite mode with high-level APIs) from fine-grained GUI execution (primitive mode with drag-and-drop). Evaluation is execution-based via runtime tests. Key results reveal a substantial reasoning-acting gap: state-of-the-art models achieve 78.31% success in composite mode but only 14.46% in primitive mode. Diagnostics show the primary bottleneck is endpoint localization in drag-and-drop operations, with single-step success around 23–32%, even though static visual perception accuracy is high (up to 90.5%). This demonstrates that current agents struggle with precise GUI manipulation despite strong planning capabilities.

## Method Summary
ScratchWorld comprises 83 curated Scratch tasks spanning four categories. In **primitive mode**, agents receive a hybrid observation: a screenshot plus an indexed list of UI elements (derived from DOM and OCR) and must output low-level actions (e.g., `click`, `drag_androp`, `type`). In **composite mode**, agents receive structured pseudocode describing block layouts and variable scopes and output high-level API calls (e.g., `add_block`, `connect_blocks`). A unified backend server interfaces with the Scratch VM via Playwright, executing agent actions and exposing VM state. After task completion, the final project is evaluated by running task-specific JavaScript unit tests to compute Success Rate (SR) and Partial Success Rate (PSR). The paper evaluates existing SOTA models (GPT-5, Claude-Sonnet-4.5, Gemini-2.5-Pro, etc.) and agentic frameworks (AWM, Agent-S2) in zero-shot settings.

## Key Results
- State-of-the-art models achieve 78.31% success in composite mode but only 14.46% in primitive mode, revealing a large reasoning-acting gap.
- Single-step drag benchmark shows endpoint localization accuracy of 23–32% even with correct start positions; start component accuracy is nearly 100%.
- Static visual perception accuracy on the 200-element QA set reaches up to 90.5%, indicating the bottleneck lies in action execution, not perception.

## Why This Works (Mechanism)
The dual-mode design isolates reasoning from execution. Composite mode bypasses GUI manipulation via high-level APIs, allowing agents to demonstrate planning capabilities without motor challenges. Primitive mode forces precise spatial control through drag-and-drop. The execution-based evaluation (runtime tests) ensures functional correctness rather than superficial similarity. The large performance gap underscores that current multimodal agents lack fine-grained motor skills despite strong planning. The hybrid observation (screenshot + element list) provides semantic grounding but introduces trade-offs: index-based targeting often misses snapping zones, leading to endpoint localization failures.

## Foundational Learning
- **Multimodal GUI Agents**: Agents that process both visual and textual information to interact with graphical interfaces. *Why needed*: To perform tasks requiring visual understanding and action. *Quick check*: Can the agent correctly identify UI elements from a screenshot?
- **Block-based Programming**: Visual paradigm where code is built by snapping together blocks. *Why needed*: ScratchWorld targets this domain. *Quick check*: Does the agent understand block connectivity and shape semantics?
- **Execution-based Evaluation**: Running the generated program and checking behavior against unit tests. *Why needed*: Provides functional correctness beyond syntactic similarity. *Quick check*: Does the agent's output pass the same tests as a human-written program?
- **Reasoning-Acting Gap**: Discrepancy between high-level planning and low-level execution. *Why needed*: Highlights a key weakness in current agents. *Quick check*: Compare performance on composite vs. primitive modes.
- **Endpoint Localization**: Precisely targeting the correct connection point during drag-and-drop. *Why needed*: Critical for successful block snapping. *Quick check*: Measure accuracy in single-step drag tasks with ground-truth start points.
- **Element List Representation**: Indexed list of UI elements from DOM and OCR fusion. *Why needed*: Provides semantic grounding for primitive actions. *Quick check*: Does the element list correctly identify and index all relevant blocks?

## Architecture Onboarding
**Component map**:  
Agent (model) -> Backend Server (Playwright + Scratch VM) -> Scratch GUI  
**Critical path**: Agent observes (screenshot + element list or pseudocode) -> decides action -> backend executes -> updates state -> repeat until task done -> evaluation via JavaScript tests.  
**Design tradeoffs**: Composite mode simplifies action space but may not reflect real GUI interaction; primitive mode is realistic but harder. The hybrid observation balances semantics and pixels but causes index-based center targeting that misses snapping zones.  
**Failure signatures**: In primitive mode, failures often due to incorrect drop coordinates; in composite mode, failures due to incorrect block structure.  
**First experiments**:  
1. Run a baseline agent (e.g., GPT-5) in both modes to reproduce the reasoning-acting gap.
2. Run the single-step drag benchmark to isolate endpoint localization.
3. Test the element list ablation (without element list) to measure its impact.

## Open Questions the Paper Calls Out
- **Open Question 1**: What underlying factors make endpoint localization substantially more difficult than start point identification in drag-and-drop operations within block-based programming? The paper identifies this as the primary bottleneck but does not investigate why models struggle so severely with endpoint prediction; potential causes such as insufficient spatial training data, lack of action-conditioned perception, or limited resolution in the observation space are not explored.
- **Open Question 2**: Can learning-based approaches automatically acquire the spatial heuristics required for reliable block snapping, or will they always depend on manually engineered rules? The reliance on hand-crafted heuristics indicates a gap between high-level reasoning and low-level execution; it remains open whether models can learn these constraints from data or interaction without explicit rule injection.
- **Open Question 3**: How should the observation space for GUI agents be designed to balance semantic indexing (which aids understanding) with precise spatial grounding (which is needed for accurate drag-and-drop)? The paper highlights this tension but does not propose or evaluate alternative representations (e.g., snapping zone markers, pixel-level segmentation) that might mitigate the issue.
- **Open Question 4**: Do the reasoning-acting gap and the endpoint localization bottleneck generalize beyond Scratch to other block-based (e.g., Blockly, App Inventor) and low-code environments? The study is limited to Scratch; although Scratch is a representative platform, its specific GUI mechanics and snapping rules may differ elsewhere. The authors suggest implications for "Scratch-style program-by-construction," but this extrapolation is untested.

## Limitations
- The backend server and element list construction pipeline are not open-sourced, hindering full replication and potentially affecting reported performance.
- Evaluation is limited to Scratch; generalizability to other block-based or low-code environments is uncertain.
- The paper does not investigate why endpoint localization is so difficult, nor does it evaluate alternative observation representations to address the trade-off.

## Confidence
- **Reasoning-acting gap**: High (robust across 6 models, supported by clear metric splits and execution-based eval)
- **Endpoint localization as primary bottleneck**: Medium (strongly implied by single-step drag benchmarks and ablations, but depends on unreleased backend spatial handling details)
- **Element list utility**: Medium (ablations show benefit, but full impact unclear without reproducing exact list generation)
- **Generalization beyond block-based environments**: Low (single-environment evaluation)

## Next Checks
