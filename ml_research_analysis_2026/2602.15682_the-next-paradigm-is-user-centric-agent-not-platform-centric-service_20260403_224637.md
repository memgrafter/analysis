# The Next Paradigm Is User-Centric Agent, Not Platform-Centric Service

## Quick Facts
- **arXiv ID**: 2602.15682
- **Source URL**: https://arxiv.org/abs/2602.15682
- **Reference count**: 40
- **Primary result**: Proposes a shift from platform-centric services to user-centric on-device agents, using an edge-cloud pipeline to align AI systems with user welfare via privacy-preserving context synthesis, cross-boundary execution, and constraint enforcement.

## Executive Summary
The paper identifies a fundamental misalignment: platform-centric AI services optimize for engagement and revenue, often at odds with user welfare. To resolve this, it advocates for a paradigm shift to user-centric agents—autonomous AI systems residing on the user’s device. These agents synthesize holistic local context from cross-app signals, plan and execute end-to-end intents across multiple platforms, and enforce user-defined constraints. The architecture employs an edge-cloud collaboration: the on-device agent handles perception, planning, and final decision-making with privacy, while the cloud provides external inventory and explainable outputs. This design overcomes three key bottlenecks of platform models: fragmented context, limited cross-boundary execution, and incentive misalignment. However, realizing this vision requires governance structures that ensure user sovereignty and equitable value-sharing with platforms.

## Method Summary
The proposed method is an edge-cloud pipeline centered on an on-device agent. The agent operates in three stages: (1) Perception & Memory aggregates cross-app signals (notifications, calendar, location) via OS-level instrumentation into a compact situational state; (2) Intent Decomposition & Planning uses a lightweight on-device LLM to break user goals into steps, deciding which actions require cloud delegation; (3) Execution & Evolution enforces user constraints, makes final selections, and updates memory. The cloud layer receives structured requests, performs context-aware reasoning, retrieves or ranks candidates with task-aware modulation, and returns explainable, constraint-tagged outputs. Communication relies on standardized intent schemas, with the device agent preserving privacy by minimizing disclosed context and retaining ultimate control. The objective is to maximize user utility rather than platform engagement, while maintaining explainability and agency.

## Key Results
- Platform-centric services are structurally misaligned with user welfare due to optimization for engagement and revenue.
- User-centric agents, enabled by modern LLMs and on-device intelligence, can resolve this by synthesizing holistic context, executing cross-platform workflows, and enforcing user constraints.
- The edge-cloud architecture addresses three bottlenecks: fragmented context, limited cross-boundary execution, and incentive misalignment; adoption depends on governance for user sovereignty and value-sharing.

## Why This Works (Mechanism)
### Mechanism 1: Holistic Context Synthesis
- **Claim**: Holistic context synthesis on the user’s device overcomes the fragmentation of platform logs, enabling situation-aware decisions.
- **Mechanism**: The on-device agent aggregates cross-app signals (e.g., notifications, calendar, location) via OS-level instrumentation into a compact situational state. This avoids reliance on any single platform’s limited, siloed behavioral data.
- **Core assumption**: The device is the natural convergence point for a user’s activities across apps and modalities; local processing can maintain privacy while capturing richer context.
- **Evidence anchors**:
  - [abstract] "the device agent synthesizes holistic local context (cross-app signals, constraints) to perceive, plan, and enforce decisions"
  - [section] §4.1: "Unlike cloud systems that rely on fragmented platform logs, an on-device agent can access user-centric signals through OS-level instrumentation"
  - [corpus] Emerging work on user-centric privacy and multimedia streaming suggests interest in user-controlled context, but no direct evidence for this specific mechanism.
- **Break condition**: If OS restrictions block cross-app data access or on-device compute cannot handle context synthesis in real time.

### Mechanism 2: Cross-Boundary Execution
- **Claim**: Cross-boundary execution planning shifts success metrics from platform engagement to user utility by treating intents as end-to-end workflows.
- **Mechanism**: The agent decomposes abstract goals into multi-step plans using local context, delegates cloud calls for external inventories, but enforces user constraints and makes final decisions locally. This extends beyond any single platform’s candidate pool.
- **Core assumption**: Many real-world intents (e.g., coordinating an event) naturally require actions across multiple services; platform-limited systems cannot fulfill them effectively.
- **Evidence anchors**:
  - [abstract] "the cloud provides external inventory and execution with explainable, constraint-aware outputs"
  - [section] §3.2: "A user-centric agent extends execution beyond any single platform boundary. It treats an intent as an end-to-end plan to be completed under user constraints"
  - [corpus] Neighbor papers focus on platform-centric recommenders or single-service agents, not cross-boundary orchestration.
- **Break condition**: If platforms refuse to expose execution APIs or if standardization for agent–platform negotiation collapses.

### Mechanism 3: Incentive Realignment via User Control
- **Claim**: Placing decision authority in a user-controlled agent aligns outcomes with user-defined goals, counteracting platform-centric incentive misalignment.
- **Mechanism**: The agent enforces constraints at execution (e.g., budget, calendar), re-ranks candidates using private preferences, and allows user overrides. Platforms become mere service providers rather than decision brokers.
- **Core assumption**: Trust and alignment require the entity governing constraints and final choices to be the user, not the platform.
- **Evidence anchors**:
  - [abstract] "user-centric agents prioritize privacy, align with user-defined goals, and grant users control"
  - [section] §3.3: "A user-centric agent makes this separation explicit: the user defines objectives and constraints, and the agent enforces them"
  - [corpus] Some neighbors address user agency but do not directly validate the governance split; evidence is indirect.
- **Break condition**: If the agent itself becomes a proprietary gatekeeper (e.g., controlled by a platform) or users cannot specify constraints meaningfully.

## Architecture Onboarding
**Component map**: On-device agent: perception/memory module (consolidates cross-app signals), planner (decomposes intents, decides delegation), executor (constraint checks, final decision, feedback loop). Cloud service layer: context-aware reasoner (interprets compact context), adaptive strategy modulator (tunes retrieval/ranking to intent mode), explainable generator (outputs structured candidates with rationales). External platforms: provide inventory and execution endpoints via standardized APIs.

**Critical path**: User intent → device perception (aggregate local context) → planning (decompose, decide cloud vs. local) → cloud request (structured query with constraints) → cloud response (candidates with metadata) → device constraint enforcement & final selection → execution & memory update.

**Design tradeoffs**:
- On-device compute vs. latency: richer local context improves decisions but may exceed device capability; trade off between context depth and responsiveness.
- Privacy vs. precision: minimal disclosure protects privacy but may cloud’s reasoning; balance via compact constraint summaries.
- Standardization vs. flexibility: strict intent schemas enable interoperability but may limit expressiveness across diverse platforms.

**Failure signatures**:
- High rate of user overrides during execution indicates poor alignment of agent decisions with user preferences.
- Frequent cloud rejections or malformed responses suggest weak adherence to standardized API contracts.
- Memory growth and consolidation failures lead to stale context and irrelevant plans.

**First 3 experiments**:
1. **Context synthesis benchmark**: Measure accuracy of situational state construction from cross-app signals against manually labeled ground truth.
2. **Cross-boundary intent success rate**: Evaluate completion of multi-service workflows (e.g., booking a dinner and ride) compared to platform-specific baselines.
3. **Constraint enforcement correctness**: Inject conflicting constraints (e.g., budget limit) and verify agent respects them before finalizing actions.

## Open Questions the Paper Calls Out
### Open Question 1: Governance of User-Centric Agents
- **Question**: How can we design enforceable mechanisms to ensure the on-device agent remains a user fiduciary, with transparent governance, portability, and insulation from vendor incentives?
- **Basis**: Section 5.1 identifies control as an economic vantage point, requiring user-governed agents with inspectable preferences, override capabilities, and provider-switching without state loss.
- **Why unresolved**: The paper recognizes this as the harder institutional barrier but does not propose concrete governance models; without enforceable safeguards, the agent risks becoming a new gatekeeper.
- **Resolution evidence**: Deployable governance frameworks (e.g., open-source agents with audit trails), legal analyses defining user rights to agent control, and real-world case studies demonstrating vendor-neutral agent operation.

### Open Question 2: Ecosystem Primitives for Agent-Platform Coordination
- **Question**: What interoperable ecosystem primitives—standardized intent schemas, verifiable compliance audits, and economic settlement mechanisms—are necessary to align incentives and enable reliable coordination between user agents and platforms?
- **Basis**: Section 5.2 lists three required shared primitives: standardized intent and constraint schemas, auditability and verifiable compliance, economic settlement for attribution and revenue sharing.
- **Why unresolved**: These are presented as essential but their design and implementation are left open; without them, platforms lack incentive to expose execution interfaces, and cross-platform workflows cannot scale.
- **Resolution evidence**: Published open standards for agent-platform communication, prototypes demonstrating constraint satisfaction verification, and empirical models of revenue-sharing that maintain user utility.

### Open Question 3: On-Device Context Aggregation
- **Question**: How can on-device agents reliably aggregate fragmented cross-app signals into a compact, actionable situational state—respecting privacy, latency, and resource constraints—to enable effective planning?
- **Basis**: Section 4.1 identifies context construction as core challenge; Section 3.1 contrasts platform systems' structural confinement to fragmented logs.
- **Why unresolved**: The vision assumes feasibility with modern on-device intelligence but provides no specifics on algorithms, data structures, or privacy-preserving techniques to achieve robust, real-time context awareness at scale.
- **Resolution evidence**: Implementations of cross-app context aggregation pipelines, benchmark results on accuracy/energy/latency, and user studies showing improved intent understanding in multi-app scenarios.

## Limitations
- The exact standardized intent and constraint schemas for device-cloud communication are not defined.
- Technical details for on-device constraint enforcement and local re-ranking are unspecified.
- Governance mechanisms to ensure the agent remains a user-controlled fiduciary are not proposed.
