# Graph-Based Self-Healing Tool Routing for Cost-Efficient LLM Agents

## Quick Facts
*   **arXiv ID:** 2603.01548
*   **Source URL:** https://arxiv.org/abs/2603.01548
*   **Reference count:** 3
*   **Primary result:** Matches ReAct's 19/19 correctness while reducing control-plane LLM calls by 93% (9 vs 123) and eliminates silent failures.

## Executive Summary
Tool-using LLM agents face a key trade-off: using an LLM for every decision ensures correctness but is costly and slow, while static pre-defined workflows are brittle under unanticipated compound tool failures. This paper introduces the Self-Healing Router, a system that replaces routine LLM inference with a deterministic, cost-weighted tool graph. Parallel lightweight monitors detect issues and trigger automatic path recomputation via Dijkstra's algorithm. The LLM is invoked only as a last resort when no valid tool path exists. Across 19 test scenarios and three topologies, this approach achieves identical task correctness to the ReAct baseline but with a 93% reduction in LLM calls and zero silent failures, demonstrating a viable path to more efficient and reliable agent orchestration.

## Method Summary
The core method constructs a directed graph where nodes are tools and edges represent functional transitions with associated cost weights. On each user request, the system first runs parallel health monitors (e.g., tool health, risk detection). The monitor with the highest priority score dictates the next action. If a tool failure is detected, the orchestrator sets all edges connected to the failed tool node to infinite cost and instantly recomputes the shortest path from the current execution point using Dijkstra's algorithm. This yields an immediate recovery path without LLM involvement. Only if the graph becomes disconnected (no finite-cost path exists) does the system escalate to the LLM for high-level goal demotion or replanning.

## Key Results
*   **Correctness:** Maintains ReAct-level performance, successfully completing all 19 benchmark scenarios (19/19).
*   **Efficiency:** Reduces control-plane LLM calls by 93% (9 calls vs. ReAct's 123 calls).
*   **Reliability:** Eliminates the 3 silent failures observed in a well-engineered static workflow baseline.

## Why This Works (Mechanism)

### Mechanism 1
*   **Claim:** Parallel health monitors replace LLM inference for routine attention allocation.
*   **Mechanism:** Multiple lightweight modules (intent classifier, risk detector, tool health monitor) run in parallel on each request, each emitting a priority-scored signal. The system selects the highest-priority signal via a simple `max()` operation; the winning signal dictates the next action without LLM involvement.
*   **Core assumption:** Most agent decisions are structurally routine (e.g., "find a working payment provider") rather than novel reasoning problems, and can be resolved by deterministic priority competition.
*   **Evidence anchors:**
    *   [abstract] "Parallel health monitors that assign priority scores... The winning signal is broadcast to the orchestrator."
    *   [section 2.1] "Parallel health monitors compete: a risk detector's 0.95-priority signal outbids an intent classifier's 0.5 signal... This replaces the LLM's role as attention allocator."
*   **Break condition:** If a critical failure signal (e.g., tool outage) is not emitted by any monitor due to misclassification or detector failure, the system may route through a broken tool.

### Mechanism 2
*   **Claim:** A cost-weighted tool graph with Dijkstra routing handles routine substitution decisions without LLM calls.
*   **Mechanism:** Tools are graph nodes; functional alternatives are connected by edges with numeric cost weights. On each request, Dijkstra's algorithm finds the cheapest path from start to goal. When conditions change (e.g., a tool becomes slow), its edge weights increase; when a tool fails, weights are set to infinity, causing automatic rerouting.
*   **Core assumption:** Tool substitution is an optimization problem (minimize cost) solvable by deterministic graph algorithms, not an LLM reasoning step.
*   **Evidence anchors:**
    *   [abstract] "Cost-weighted tool graph where Dijkstra's algorithm performs deterministic shortest-path routing."
    *   [section 2.2] "Given a goal and the current system state... Dijkstra's algorithm finds the cheapest valid path. When a tool fails... its edges get infinite weight, and Dijkstra naturally avoids them."
*   **Break condition:** If the graph is disconnected (no finite-cost path exists) after reweighting, Dijkstra returns `null`, requiring LLM escalation.

### Mechanism 3
*   **Claim:** Automatic recovery from tool failures is achieved by reweighting failed edges to infinity and recomputing paths, avoiding LLM calls entirely.
*   **Mechanism:** Upon tool failure detection (Step 1), the orchestrator sets all edges touching the failed node to infinite weight (Step 2), then re-runs Dijkstra from the current execution point (Step 3). If a new path exists, execution resumes; if no path exists (Step 4), the LLM is invoked for goal demotion.
*   **Core assumption:** Failures are detectable in real-time and can be modeled as binary edge removals (infinite cost), with recovery complexity independent of the number of simultaneous failures.
*   **Evidence anchors:**
    *   [abstract] "When a tool fails mid-execution, its edges are reweighted to infinity and the path is recomputed — yielding automatic recovery without invoking the LLM."
    *   [section 2.3] Outlines the four-step sequence: Failure Detection → Graph Update → Dijkstra Re-run → Execution Continues. Notes: "The same four-step sequence handles any failure combination... The time complexity does not change with the number of simultaneous failures."
*   **Break condition:** If failure detection is delayed or the graph update step fails to set weights correctly, the system may continue using a broken tool or incorrectly block healthy alternatives.

## Foundational Learning
*   **Concept:** Dijkstra's shortest-path algorithm
    *   *Why needed here:* It is the core routing engine that deterministically finds the cheapest tool sequence given dynamic edge weights.
    *   *Quick check question:* "What does Dijkstra return when all outgoing edges from the current node have infinite weight?"
*   **Concept:** Circuit breaker pattern (binary health states: CLOSED/OPEN/HALF-OPEN)
    *   *Why needed here:* Health monitors implement circuit-breaking logic to translate tool liveness into graph edge weights (1.0 vs. ∞). Understanding this prevents flapping and ensures graceful recovery.
    *   *Quick check question:* "How does the HALF-OPEN state allow a recently recovered tool to re-enter service without overwhelming it?"
*   **Concept:** Exponential state explosion in static workflow graphs
    *   *Why needed here:* It explains why pre-coded fallback edges (e.g., in LangGraph) fail under compound failures, motivating the graph-routing approach.
    *   *Quick check question:* "For N tools with 2 failure modes each, how many distinct compound-failure states must a static workflow explicitly handle?"

## Architecture Onboarding
*   **Component map:**
    Parallel Health Monitors (intent, risk, tool health) -> Orchestrator (receives winning signal, updates graph, runs Dijkstra) -> Tool Graph (directed weighted graph of tools) -> Execution Engine (runs selected tool). LLM is a fallback invoked by the Orchestrator when Dijkstra returns `null`.
*   **Critical path:** Request arrives -> parallel monitors emit priority-scored signals -> `max()` selects winning signal -> if signal indicates tool failure, orchestrator sets adjacent edges to ∞ -> orchestrator runs Dijkstra from current node -> if path exists, execute next tool in sequence; if `null`, call LLM for demotion -> repeat until task completion or final LLM replan.
*   **Design tradeoffs:**
    *   *Static vs. dynamic weights:* Benchmarks use static backup weights (primary=1, backup=2); production uses live telemetry (latency, error rate, rate limits) for continuous calibration.
    *   *Manual graph construction:* Domain-specific tool graphs must be hand-specified; automatic graph generation from tool docs is future work.
    *   *Deterministic vs. probabilistic routing:* Dijkstra guarantees optimal path given weights; no stochasticity means no exploration of suboptimal paths unless weights change.
*   **Failure signatures:**
    *   *Reroute:* Logged when Dijkstra returns a new path after edge reweighting (health monitor fired). Expected in scenarios like Stripe down → Razorpay path selected.
    *   *Escalation:* Logged when Dijkstra returns `null`; LLM is called. Expected when all payment providers are down (e.g., Scenario S3).
    *   *Silent failure:* Structurally impossible by design; if a tool fails and no alternative exists, the system escalates, not proceeds with missing steps.
*   **First 3 experiments:**
    1.  **Single tool failure:** Mock Stripe API to timeout during a refund. Observe: Tool Health Monitor fires (high priority), Stripe edges set to ∞, Dijkstra finds Razorpay path, execution resumes without LLM call.
    2.  **Simultaneous failures:** Mock both Stripe and Email to fail in a single task. Observe: Both sets of edges set to ∞ in one update, Dijkstra runs once, finds backup path (Razorpay + SMS), zero LLM calls.
    3.  **All alternatives exhausted:** Mock all payment providers (Stripe, Razorpay) and notification channels (Email, SMS) to be down. Observe: After last failure, Dijkstra returns `null`, orchestrator calls LLM for goal demotion (e.g., "refund impossible, issue store credit").

## Open Questions the Paper Calls Out
### Open Question 1
*   **Question:** How does the Self-Healing Router's performance (recovery time, correctness, LLM call reduction) generalize to real-world API environments with variable latency, error distributions, and partial failures?
*   **Basis in paper:** [explicit] The paper states its evaluation uses a "mock environment" with "deterministic mock LLM" and does not validate "real-world API latency, error distributions, or LLM accuracy under production conditions."
*   **Why unresolved:** The claimed sub-millisecond deterministic recovery and 93% LLM reduction rely on idealized tool failure signals (binary health checks). Real APIs may exhibit partial failures (e.g., timeout vs. malformed data), transient errors, or latency spikes that affect weight calibration and recovery paths.
*   **What evidence would resolve it:** A production-grade benchmark with real API integrations (e.g., Stripe, SendGrid) and fault injection across diverse failure modes (latency degradation, HTTP 5xx vs. 4xx, data corruption), comparing recovery latency, task integrity, and escalation rates against the mock results.

### Open Question 2
*   **Question:** Can the manual effort of specifying tool graphs be automated, and what is the accuracy/completeness of automatically generated graphs from tool documentation or usage logs?
*   **Basis in paper:** [explicit] The paper notes "the tool graph must be manually specified for each domain" and identifies the "cold-start problem of automatically constructing the graph" as a limitation for future work.
*   **Why unresolved:** Manual graph construction is a significant barrier to adoption; without automation, the approach does not scale to new domains or rapidly evolving tool ecosystems. An automatically generated graph might miss subtle functional equivalences (e.g., Razorpay as a Stripe fallback) or dependency edges.
*   **What evidence would resolve it:** A system that ingests tool APIs/SDK documentation or historical agent-tool interaction logs to propose graph structures (nodes, edges, base costs), evaluated on its ability to match manually curated gold-standard graphs from the paper’s three domains and on end-to-end agent correctness when using the auto-generated graph.

### Open Question 3
*   **Question:** How robust is the architecture to errors in the parallel health monitors (e.g., false positives/negatives in tool health detection or risk classification)?
*   **Basis in paper:** [explicit] The paper acknowledges it "assumes perfect module accuracy" for intent classifiers and risk detectors, which "overstates the architecture's reliability," and calls for "systematic evaluation of module error propagation."
*   **Why unresolved:** The priority competition mechanism could misprioritize signals (e.g., a false-negative tool health monitor might not reweight edges, causing silent failures; a false-positive risk signal could cause unnecessary LLM escalations). The impact on correctness and LLM call rates is unknown.
*   **What evidence would resolve it:** A sensitivity analysis injecting controlled error rates (e.g., 1–10% false-negative rate in tool health monitors) into the benchmark scenarios, measuring degradation in failure recovery rates, silent failure incidence, and escalation frequency compared to the perfect-monitor baseline.

### Open Question 4
*   **Question:** Does the Self-Healing Router handle partial tool failures (e.g., tools returning incorrect or incomplete data) as effectively as hard outages?
*   **Basis in paper:** [explicit] The paper limits failure testing to "tool outages and cascading failures" and explicitly states it does not test "partial failures (tool returns incorrect data)" or "adversarial inputs."
*   **Why unresolved:** The current design only reweights edges upon hard failure detection (timeout, error response). Partial failures (e.g., a payment API returning a successful status but not actually processing a refund) would not trigger edge reweighting, potentially leading to silent data corruption or incorrect task completion.
*   **What evidence would resolve it:** Extending the scenario suite to include partial failure cases (e.g., tools that succeed syntactically but produce semantically invalid outputs), and measuring whether the architecture detects such failures (via output validation monitors) and correctly reroutes or escalates, or if new failure modes emerge.

## Limitations
*   **Unspecified failure coordination:** The pseudocode handles single-failure reweighting; the protocol for aggregating *simultaneous* health signals before a single Dijkstra recompute is unverified and could introduce race conditions.
*   **Unevaluated dynamic weights:** The proposed production design for live telemetry-driven weight calibration is unevaluated; its impact on cost optimality and recovery under real-world flaky conditions remains unknown.
*   **Manual graph bottleneck:** The requirement to manually specify tool graphs and edge costs for each domain is a major scalability barrier not addressed by the paper.

## Confidence
*   **Mechanism 1 (priority competition):** Medium. Evidence is internal; no external validation that deterministic `max()` reliably allocates attention across diverse scenarios.
*   **Mechanism 2 (Dijkstra routing):** Medium. Graph routing is sound, but the assumption that all necessary substitution edges are pre-wired is not stress-tested for complex topologies.
*   **Mechanism 3 (automatic recovery):** Low. Claims of handling “any failure combination” rely on an unverified aggregation protocol; silent failures might still occur if monitors miss compound failures.
*   **Overall correctness claim (19/19):** High. Reported results are clear, but depend on the above mechanisms working as designed in unseen scenarios.

## Next Checks
1.  **Simultaneous failure protocol:** Instrument the orchestrator to log all health signals and graph update operations during induced multi-tool failures. Verify that *all* failed edges are set to ∞ before Dijkstra recomputation, and that no stale edges remain.
2.  **Dynamic weight calibration impact:** Replace static edge weights with a telemetry-driven estimator (e.g., moving average of latency + error rate). Measure changes in (a) path optimality (cost vs. static-gold) and (b) recovery time under gradual degradation (e.g., increasing tool latency).
3.  **Graph completeness stress test:** For a given domain, systematically remove random edges from the tool graph (simulating missing fallbacks) and run the 19 scenarios. Quantify the failure rate increase and identify which missing edge types cause the most Dijkstra `null` escalations.
