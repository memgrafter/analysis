# A Multi-Agent Framework for Code-Guided, Modular, and Verifiable Automated Machine Learning

## Quick Facts
- arXiv ID: 2602.13937
- Source URL: https://arxiv.org/abs/2602.13937
- Reference count: 26
- Primary result: iML achieves 85% valid submission rate, 45% medal rate, and APS 0.77 on MLE-BENCH; outperforms SOTA by 38%–163% on iML-BENCH; retains 70% success with stripped task descriptions.

## Executive Summary
iML is a multi-agent framework that automates machine learning pipeline generation while addressing key limitations of traditional AutoML and LLM-based code generation. It introduces three pillars: Code-Guided Planning uses autonomous empirical profiling to create a strategic blueprint anchored in physical data properties; Code-Modular Implementation decomposes the pipeline into specialized, contract-bound components; and Code-Verifiable Integration enforces dynamic execution and iterative debugging to guarantee feasibility. Evaluated on MLE-BENCH and a new iML-BENCH (Kaggle competitions), iML achieves 85% valid submissions and 45% medal rate on MLE-BENCH, and outperforms state-of-the-art agents by 38%–163% in average standardized performance on iML-BENCH. The framework demonstrates strong robustness, maintaining 70% success even with minimal task descriptions.

## Method Summary
The iML pipeline executes three phases. In Code-Guided Planning, a Profiling Agent runs verified tools (e.g., ydata-profiling) on raw data to produce empirical meta-features, and a Guideline Agent synthesizes a Strategic Blueprint that defines interface contracts and component strategies, optionally incorporating retrieved resources. In Code-Modular Implementation, independent Preprocessing and Modeling Coder agents generate code for their modules, strictly adhering to the blueprint’s contracts and performing self-verification (e.g., validating preprocessing output against post-conditions). In Code-Verifiable Integration, an Assembler combines modules into a unified script, which is executed; if errors occur, an Error Analyzer localizes the fault and a Debugging Agent iteratively repairs the offending module using web search, up to a fixed budget. After integration or budget exhaustion, a Comparison/Evaluation Agent selects the best-performing pipeline, optionally ensembling top candidates. The system uses Gemini-2.5-Flash by default, a 5-hour time budget per dataset, and a single NVIDIA P100 GPU.

## Key Results
- 85% valid submission rate and 45% medal rate on MLE-BENCH, with average standardized performance score (APS) of 0.77.
- Outperforms state-of-the-art agents by 38%–163% in APS on the new iML-BENCH (Kaggle competitions).
- Maintains 70% success rate even with stripped task descriptions, demonstrating robustness via empirical grounding.

## Why This Works (Mechanism)

### Mechanism 1: Code-Guided Planning
**Claim:** Eliminates strategic hallucination by grounding the blueprint in empirical data profiling rather than textual inference.  
**Mechanism:** The Profiling Agent executes verified profiling tools on dataset D to produce empirical meta-features Fmeta (schema, quality, distribution). The Guideline Agent then synthesizes a Strategic Blueprint B from the task summary and Fmeta, defining interface contracts IC_T and component strategies (Bprep, Bmodel, etc.). This constrains the code generation search space from infinite syntactically valid scripts to a subspace S_B aligned with physical data properties.  
**Evidence:** The abstract states the blueprint is "grounded in autonomous empirical profiling to eliminate hallucination." Section 3.2.1 emphasizes that profiling ensures planning is based on "physical reality rather than the probabilistic inference of LLMs." Comparative framing against baselines like MLZero and AutoML-Agent, which rely on simulation-first or pseudo-analysis without execution, supports the contrast.  
**Break condition:** If profiling fails or yields corrupted/incomplete Fmeta, the blueprint lacks a reliable anchor, potentially reintroducing hallucination and causing downstream failures.

### Mechanism 2: Code-Modular Implementation
**Claim:** Prevents logic entanglement and catastrophic error propagation by isolating preprocessing and modeling into independent, contract-bound components.  
**Mechanism:** The pipeline is decomposed into a Preprocessing Coder (generating S_prep) and a Modeling Coder (generating S_model). Development is independent but governed by a strict Interface Contract IC_T defined in the blueprint, which specifies exact input/output types (e.g., DataFrame shapes, tensor types) as a formal post-condition Q_post for S_prep and pre-condition R_pre for S_model. This decoupling allows the Assembler to bind variables semantically and the Debugging Agent to localize faults to a specific module’s scope.  
**Evidence:** The abstract mentions "decomposes the pipeline into specialized components governed by strict interface contracts." Section 3.3.1 describes enforcing a post-condition that the preprocessing output satisfies exact schema constraints required by modeling. Ablation evidence: the iML_mono variant (monolithic code) shows reduced valid submission rate (80% vs 85%) and APS (0.69 vs 0.77), indicating entanglement harms reliability.  
**Break condition:** If IC_T is poorly defined (e.g., incorrect tensor shape specifications), both coders may generate technically valid but incompatible code, causing assembly failure and debugging loops that correct for a flawed contract rather than a code bug.

### Mechanism 3: Code-Verifiable Integration
**Claim:** Guarantees physical feasibility and recovers from runtime errors by enforcing dynamic execution and iterative debugging on intermediate artifacts.  
**Mechanism:** The Assembler integrates S_prep and S_model into a unified script S. Crucially, the system executes S_prep on an actual data sample to produce D’ and validates its runtime properties (shape, dtype) against IC_T before full integration. If validation fails, an Error Analyzer classifies the fault (contract fulfillment vs. usage violation) and a Debugging Agent iteratively repairs the offending module (typically Preprocessing Coder) using web-retrieved syntax fixes, up to a budget K.  
**Evidence:** The abstract states it "enforces physical feasibility through dynamic contract verification and iterative self-correction." Section 3.4.2 details the intermediate execution and debugging loop with web search. Ablation evidence: iML_static variant (no intermediate execution) shows lower APS (0.67) and valid rate (80%) vs full iML (0.77, 85%), directly linking dynamic verification to success.  
**Break condition:** If debugging budget K=0 or if runtime errors are unrecoverable due to fundamental logical flaws, the pipeline fails verification.

## Architecture Onboarding
**Component map (simplified flow):**  
Task Analyzer + Profiling Agent → Guideline Agent (with Resource Retrieval: Pretrained Model Retriever, Custom Architecture Retriever) → Preprocessing Coder → Modeling Coder → Assembler → Execute S → (if error → Error Analyzer → Debugging Agent ↔ affected coder) → Comparison/Evaluation Agent → (optional) Modular Ensembler

**Critical path:** Task & Data Analysis → Guideline Agent (Blueprint) → Preprocessing Coder (S_prep, verify Q_post) → Modeling Coder (S_model, check R_pre) → Assembler (bind, create S) → Execute S → Debug (if fail) → Loop until pass or budget exhausted → Evaluate & Select.

**Design tradeoffs:**
- Modularity vs. Overhead: Isolating coders increases LLM calls and execution time but drastically improves fault isolation and valid submission rate.
- Verification Cost vs. Success: Higher debugging budget K improves medal rate but increases token/time cost; performance plateaus at K=10.
- Single-Track vs. Multi-Track Strategy: Restricting to one modeling track reduces search cost but risks total failure on unsuitable tasks; full iML’s parallel tracks are costlier but adaptively select the best-performing track.

**Failure signatures:**
- Contract Fulfillment Failure (Preprocessing): S_prep runs but outputs D’ with wrong shape/dtype/NaNs. Debugging focuses on S_prep.
- Contract Usage Violation (Modeling): S_model fails because its input expectations don’t match D’ (e.g., layer dimensions). Debugging focuses on S_model.
- Guideline Failure: Profiling meta-features Fmeta or task summary Sum_T are wrong, leading to a fundamentally flawed blueprint; success rate plummets even with perfect debugging.

**First 3 experiments:**
1. Ablation Study: Run full iML vs. iML w/o guideline (no Guideline Agent), iML_mono (single monolithic agent), and iML_static (no intermediate execution). Compare APS and valid submission rate to quantify each pillar’s contribution.
2. Model Selection Strategy: Compare full iML (all three tracks: Traditional ML, Pretrained, Custom NN) against single-track variants. Measure APS and medal rate to prove the value of dynamic, empirical selection.
3. Sensitivity to Task Description: Compare performance with full Kaggle description vs. stripped description (“Predict the target column”). Measure drop in APS and valid rate to demonstrate robustness via empirical grounding.

## Open Questions the Paper Calls Out
### Open Question 1
**Question:** How can iML’s performance on multimodal tasks be significantly improved given its current degradation (APS 0.56) compared to unimodal tasks?  
**Basis:** Section 5.3.2 states the Multimodal category presented the greatest challenge (APS 0.56) and identifies “cross-modal feature orchestration” as a frontier for future optimization.  
**Why unresolved:** The current modular architecture successfully isolates preprocessing and modeling but struggles with the strategic overhead of orchestrating cross-modal feature engineering.  
**Resolving evidence:** An enhanced blueprint synthesis mechanism in the Guideline Agent that explicitly generates contracts for cross-modal data alignment (e.g., fusion layers, attention mechanisms) or a new specialized Coding Agent for multimodal integration, validated on a new multimodal benchmark.

### Open Question 2
**Question:** To what extent can iML’s “semantic autonomy” be generalized beyond stripped descriptions to handle tasks with inherently ambiguous or conflicting objectives?  
**Basis:** Section 5.3.1 evaluates performance on stripped prompts and concludes iML maintains a robust 70% success rate by relying on empirical meta-features. It also notes a failure case where the task description provided insufficient clarity.  
**Why unresolved:** The experiment uses a standardized, minimally descriptive prompt; it does not test more realistic ambiguity forms (e.g., conflicting metrics, vague success criteria) where empirical profiling alone may be insufficient to infer correct semantics.  
**Resolving evidence:** A new evaluation suite with graded ambiguity levels (e.g., missing evaluation metric, contradictory instructions) measuring iML’s ability to infer the correct optimization target, possibly through iterative hypothesis validation via small-scale execution.

### Open Question 3
**Question:** What specific capabilities in backbone LLMs (beyond general reasoning scores) are most critical for each agent role (Guideline, Coder, Debugger) in the iML framework?  
**Basis:** Figure 6 shows dramatic performance variation across LLMs (e.g., GPT-5 mini matches Gemini’s valid rate but lags in “competitive quality”). The paper speculates that “high-level thinking… are critical for… agents to synthesize the complex architectural invariants,” but does not isolate which skills drive the difference.  
**Why unresolved:** The ablation uses different monolithic LLMs for the entire pipeline; the differential contribution of LLM capability to the distinct phases (Code-Guided Planning vs. Code-Verifiable Integration) is not measured.  
**Resolving evidence:** An ablation study swapping different LLMs for specific agents only (e.g., using a strong coding model for Coding Agents but a weaker one for Guideline Agent) on a held-out set of tasks, measuring impact on blueprint quality, valid submission rate, and final APS.

### Open Question 4
**Question:** Can the self-correction budget (K) be dynamically adapted per task or per failure type to improve efficiency without sacrificing the 45% relative gain from K=10?  
**Basis:** Section 5.2.3 shows a clear plateau in performance gains between K=10 and K=20 while “average execution time increases 13%.” The paper concludes K=10 is optimal but suggests this is a static, one-size-fits-all setting.  
**Why unresolved:** The optimal debugging effort likely depends on task complexity (e.g., multimodal tasks may need more rounds) and error type (contract fulfillment vs. usage violation). A static budget wastes resources on simple tasks and may under-allocate for complex ones.  
**Resolving evidence:** A failure-type classifier integrated with the Error Analyzer that predicts required debugging depth (e.g., based on error trace complexity, blueprint size), allowing early termination or extended budgets, and evaluating this adaptive policy against the static K=10 baseline on efficiency metrics (time, tokens) and success rate.

## Limitations
- Exact configuration of the Profiling Agent (e.g., ydata-profiling version/parameters) and the web search tool’s query/validation logic are unspecified, hindering exact replication.
- Generalizability may be limited to the provided benchmarks (MLE-BENCH Lite, iML-BENCH) and the Gemini-2.5-Flash model within a 5-hour budget.

- Mechanism 1 (Code-Guided Planning): Medium
- Mechanism 2 (Modular Implementation): High
