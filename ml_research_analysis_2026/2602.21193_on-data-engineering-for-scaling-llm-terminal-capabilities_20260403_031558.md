# On Data Engineering for Scaling LLM Terminal Capabilities
## Quick Facts
- **arXiv ID:** 2602.21193
- **Source URL:** https://arxiv.org/abs/2602.21193
- **Reference count:** 40
- **Primary result:** A scalable data pipeline (Terminal-Task-Gen) producing Terminal-Corpus enables small Qwen3-based models (8B–32B) to outperform a 480B model on Terminal-Bench 2.0, with the 32B variant achieving 27.4% vs. Qwen3-Coder's 23.9%.

## Executive Summary
This paper tackles the data scarcity problem for training capable LLM terminal agents. It introduces **Terminal-Task-Gen**, a two-stage pipeline that combines dataset adaptation (reformatting existing math/code/SWE prompts into terminal tasks) with skill-based synthetic task generation (using a primitive skill taxonomy and pre-built domain Docker images). This creates **Terminal-Corpus**, a large-scale trajectory dataset. After supervised fine-tuning Qwen3 models (8B, 14B, 32B) on this data—including unsuccessful trajectories—the resulting **Nemotron-Terminal** models show dramatic improvements on Terminal-Bench 2.0. The 32B model's 27.4% pass@1 surpasses the much larger 480B Qwen3-Coder, demonstrating that high-quality, diverse trajectory data can significantly close the gap with giant models.

## Method Summary
The core method is a scalable synthetic data generation pipeline. **Stage 1 (Dataset Adaptation)** converts existing high-quality prompts from mathematical, coding, and software engineering datasets into terminal-format tasks by wrapping them in a shell context. **Stage 2 (Synthetic Generation)** uses a taxonomy of 9 primitive skill domains (e.g., System Ops, Data Science) and pre-built Docker images (one per domain) to generate novel tasks. A teacher agent (DeepSeek-V3.2 running Terminus 2) rolls out multi-turn trajectories for each task. The pipeline emphasizes scalability by using fixed environments instead of per-task Dockerfiles, allowing single-pass generation. The resulting trajectories are filtered minimally (decontamination, Chinese text removal) and used for SFT on Qwen3 base models.

## Key Results
- Nemotron-Terminal-32B achieves **27.4%** on Terminal-Bench 2.0, exceeding the 480B Qwen3-Coder (23.9%) and showing a massive gain from its 3.4% base.
- The 8B model improves from 2.5% to 13.0%; the 14B from 4.0% to 20.2%.
- Including all trajectories (successful and unsuccessful) yields the best results; success-only filtering severely harms performance.
- Combining dataset adapters with skill-based synthetic data is synergistic, outperforming either source alone.

## Why This Works (Mechanism)
### Mechanism 1: Complementary Data Scaling & Depth
Dataset adaptation provides broad coverage by converting existing high-quality reasoning prompts into terminal format, rapidly scaling data volume. Synthetic task generation, guided by a primitive skill taxonomy and stable domain environments, creates novel, verifiable tasks that target specific terminal operations. This decouples problem specification from environment validation, making data generation efficient. The combined corpus gives models exposure to both general reasoning patterns and targeted operational skills.

### Mechanism 2: Pre-built Docker Environments
Using a fixed set of pre-installed, domain-specific Docker images (e.g., with pandas pre-loaded for data science) eliminates the expensive per-task Dockerfile validation and repair cycle. This drastically reduces resource overhead and accelerates generation. The environment stability allows the pipeline to focus on task variation while retaining flexibility for agents to install additional runtime-specific packages during execution.

### Mechanism 3: Training on All Trajectories
Retaining unsuccessful trajectories provides supervision on error states, debugging, and recovery patterns that are intrinsic to terminal interaction. Discarding them removes this "negative knowledge" and creates a distribution shift, as evaluation naturally includes failures. Learning from a mix of outcomes builds robustness and improves generalization to the stochastic nature of agent execution.

## Foundational Learning
- **Concept: Agentic Scaffolding vs. Base Model Training**
  - **Why needed:** The paper improves the base model via SFT, contrasting with work that uses complex, model-specific scaffolding. This highlights the hypothesis that data quality can reduce reliance on sophisticated inference-time scaffolds.
  - **Quick check:** What are the trade-offs between a complex, hand-crafted scaffold and a more capable base model with a simple scaffold?
- **Concept: Trajectory Generation for SFT**
  - **Why needed:** The entire pipeline creates (state, action) trajectories. Understanding how the Terminus 2 agent structures its responses (analysis, plan, commands) defines the action space for training data.
  - **Quick check:** How does the JSON response format of Terminus 2 translate into the supervised learning signal?
- **Concept: Docker-Based Environment Isolation & Reproducibility**
  - **Why needed:** Containerization is non-negotiable for generating large-scale, consistent, and reproducible agent interaction data. All design choices (pre-built images, orchestration) depend on it.
  - **Quick check:** Why are virtual machines or bare-metal setups insufficient for this scale of trajectory collection?

## Architecture Onboarding
- **Component map:**
  Source Data (Existing Prompts + Seeds) -> Terminal-Task-Gen (Adapters + Skill-based Generator) -> Task Validator -> Environment Manager (Pre-built Docker + Harbor) -> Trajectory Rollout (DeepSeek-V3.2 + Terminus 2) -> Raw Trajectories -> Filtering (Decontamination, Cleaning) -> Terminal-Corpus -> SFT Trainer (veRL) -> Nemotron-Terminal (Qwen3 variants) -> Evaluator (Terminus 2 + Daytona on TB2.0) -> Pass@1 Score
- **Critical path:** Seed/Prompt Data → Task Generation → Validation → (Fixed Environments + Teacher Model) → Raw Trajectories → Filtering → SFT → Evaluation.
- **Design tradeoffs:**
  - Pre-built Docker vs. Per-Task Docker: Chose scalability/stability over maximum per-task customization.
  - No Filtering vs. Success-Only: Chose diversity/robustness over data purity.
  - Mixed SFT vs. Curriculum: Chose simplicity over staged learning.
- **Failure signatures:**
  - Trajectory truncation due to 32k token limit.
  - Environment drift if Docker images become outdated.
  - Test leakage via inadequate 14-gram decontamination.
  - Bias inheritance from teacher model (DeepSeek-V3.2).
- **First 3 experiments:**
  1. Ablate dataset components (adapters vs. synthetic seed vs. synthetic skill) to measure individual and combined contributions on Qwen3-8B.
  2. Compare filtering strategies (no filter, complete-only, success-only) to assess the impact of including unsuccessful trajectories.
  3. Test long-context training extensions (65k context, YaRN2) to see if handling longer trajectories improves performance.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can reinforcement learning with verifiable execution feedback be integrated to enable self-correction and optimal planning for long-horizon terminal tasks?
- **Open Question 2:** What specific error recovery patterns do unsuccessful trajectories provide that improve robustness, and how should they be optimally weighted or filtered?
- **Open Question 3:** What is the mechanism behind the synergistic gains when combining multiple domain adapters, and what is the optimal mixing ratio?
- **Open Question 4:** How do seed-based and skill-based synthetic generation methods complement each other in coverage, and can their outputs be optimally weighted?
- **Open Question 5:** Why do long-tail trajectories exceed standard context windows, and how should they be handled optimally (e.g., hierarchical modeling, compression)?

## Limitations
- Exact specifications of the 9 pre-built Docker images and the full primitive skill taxonomy are not released, hindering precise replication.
- Dataset composition and filtering rules for adapter trajectories are ambiguous (e.g., "no filtering" for tasks without test cases).
- Decontamination via 14-gram overlap may be insufficient; evaluation is limited to Terminal-Bench 2.0.
- Potential bias from the teacher model (DeepSeek-V3.2) propagating to student models.

## Confidence
- **Terminal-Task-Gen scalability:** Medium (design plausible, lacking direct ablation vs. alternatives).
- **Nemotron-Terminal SOTA on TB2.0:** High (consistent gains across model sizes).
- **Pre-built Docker critical for scalability:** Medium (cost savings plausible but not quantitatively isolated).
- **Including unsuccessful trajectories improves robustness:** High (strong ablation evidence).
- **Complementarity of adapted and synthetic data:** Medium (additive gains shown, real-world transfer unproven).

## Next Checks
1. **Docker environment replication:** Rebuild the 9 domain Docker images from descriptions, run released tasks, and measure success rate/resource use versus a per-task Dockerfile baseline.
2. **Contamination stress test:** Compute sub-14-gram overlaps between training tasks and an external holdout of real terminal command sequences to assess overfitting risk beyond TB2.0.
3. **Error trajectory classification:** Manually annotate unsuccessful teacher rollouts to categorize failure modes (syntax, environment, infinite loops) and correlate with student model performance on similar tasks.
