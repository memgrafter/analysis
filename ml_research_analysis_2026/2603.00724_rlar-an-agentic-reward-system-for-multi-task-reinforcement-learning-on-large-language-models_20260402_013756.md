# RLAR: An Agentic Reward System for Multi-task Reinforcement Learning on Large Language Models

## Quick Facts
- arXiv ID: 2603.00724
- Source URL: https://arxiv.org/abs/2603.00724
- Reference count: 40
- Primary result: RLAR dynamically assigns tailored reward functions to individual queries, yielding 10‑60% performance gains across math, coding, translation, and dialogue tasks and reducing token consumption by ~80% compared to GPT‑5-as-a-judge.

## Executive Summary
RLAR introduces an agentic reward system to overcome the limitations of static reward models in reinforcement learning for large language models. Instead of relying on a single, fixed reward model, RLAR employs a policy router to either select the most suitable existing reward tool from a library or synthesize a new one on demand via specialized agents (WrapLLM for retrieving HuggingFace reward models and CodeVerify for generating Python verifiers). This self‑evolving framework adapts to shifting data distributions and task varieties. Experiments on Llama‑3.1‑8B and Qwen3‑8B across four domains show consistent improvements of 10‑60%, high tool selection accuracy (90.44% on RewardBench‑V2), and an ~80% reduction in token usage relative to GPT‑5-as-a-judge, while remaining robust to common reward hacking behaviors.

## Method Summary
RLAR replaces the conventional static reward model with a dynamic library of reward tools. For each training query `(q, r, ˆr)`, a Policy Router decides whether an existing tool suffices or a new one must be synthesized. If a suitable tool exists, a Tool Selector retrieves the best‑matching function from the library. Otherwise, the Synthesis Module activates: WrapLLM searches HuggingFace for task‑specific reward models and wraps them as callables; CodeVerify generates rule‑based Python verifiers for objective tasks. Before integration, a Verification step (EvalTool) validates the new tool to ensure correctness and executability. The selected tool produces a scalar reward that feeds into a Group Relative Policy Optimization (GRPO) trainer, updating the policy. This loop allows the reward system to grow and specialize over time, handling diverse tasks without manual intervention.

## Key Results
- Consistent performance gains of 10%–60% across mathematics, coding, translation, and dialogue tasks on Llama‑3.1‑8B and Qwen3‑8B.
- On RewardBench‑V2, RLAR significantly outperforms static baselines and approaches the performance upper bound, with the reward tool selector achieving 90.44% accuracy.
- Reduces API token consumption by approximately 80% relative to GPT‑5-as-a-judge and exhibits robustness against format and verbosity reward hacking.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: RLAR dynamically matches queries to the most suitable reward tool from a growing library, avoiding the generalization ceiling of a single static reward model.
- **Mechanism**: A Policy Router (`π_agent`) classifies whether an existing tool in the library `F` can accurately evaluate a given `(q, r, ˆr)` triplet (completeness assessment). If complete, a Tool Selector (`ϕ_select`) picks the optimal tool `f_t ∈ F` by matching task metadata to tool descriptions.
- **Core assumption**: Different tasks (math, code, translation) have fundamentally different optimal reward functions; a one‑size‑fits‑all model cannot capture all these objectives simultaneously.
- **Evidence anchors**: Abstract mentions “dynamically assigns tailored reward functions” and “self‑evolve with the shifting data distributions”; section 3.2 formalizes the router’s decision and the selection process; neighboring papers offer weak evidence on agentic RL and tool‑use but do not specifically validate dynamic reward routing.
- **Break condition**: If the router consistently fails to select the appropriate tool (low accuracy on RewardBench‑V2), the system reverts to a generic, potentially suboptimal reward, negating the dynamic advantage.

### Mechanism 2
- **Claim**: RLAR synthesizes missing reward tools on‑demand via two specialized agents (WrapLLM and CodeVerify), expanding the library `F` to cover new or unseen task distributions.
- **Mechanism**:
  - **WrapLLM**: An LLM agent searches HuggingFace for lightweight (<10B) task‑specific reward models, then wraps the checkpoint into a callable Python function.
  - **CodeVerify**: An agent plans and generates Python verifiers (e.g., unit test executors for code, exact numeric match for math) for tasks with objective correctness criteria.
- **Core assumption**: High‑quality, pre‑trained reward models exist for niche tasks (WrapLLM) and deterministic verifiers can be reliably code‑generated (CodeVerify) for certain domains.
- **Evidence anchors**: Section 3.3 describes the iterative retrieval for WrapLLM and the “Plan‑and‑Execute” strategy for CodeVerify; section 4.5 ablations show that removing either component causes significant drops in math/coding (w/o CodeVerify) or chat/translation (w/o WrapLLM) performance.
- **Break condition**: If the code‑generation fails to produce executable scripts (low `EvalTool` pass rate) or the web search returns irrelevant/non‑executable models, the synthesis pipeline breaks, leaving a gap in the library.

### Mechanism 3
- **Claim**: A verification module (`EvalTool`) and library update loop ensure only reliable, functional tools are added to `F`, maintaining system integrity as it self‑evolves.
- **Mechanism**: Before committing `f_new`, `EvalTool` validates WrapLLM tools (checking model docs consistency) and CodeVerify tools (code analysis + execution checks). Only passing tools are added: `F ← F ∪ {f_new}`.
- **Core assumption**: Automated validation can effectively screen out broken or misaligned reward tools without human intervention.
- **Evidence anchors**: Section 3.4 defines the validation steps and update rule; Appendix G.2 reports a 94.9% executability rate for code‑agent tools and a 47.6% successful deployment rate for web‑agent tools, indicating effective (though imperfect) filtering.
- **Break condition**: If validation is too lenient, buggy tools corrupt the library and harm RL training; if too strict, the library fails to grow, causing the router to default to generic models.

## Architecture Onboarding
**Component map**:
Policy Router (π_agent) --> Tool Selector (ϕ_select) --> Reward Tool Library (F) --> RL Trainer (GRPO)
Policy Router (π_agent) --> Synthesis Module (ϕ_gen) --> Verification (EvalTool) --> Reward Tool Library (F) --> Tool Selector (ϕ_select) --> RL Trainer (GRPO)

**Critical path**:
1. Input `(q, r, ˆr)` arrives.
2. Router decides `Select` or `Synthesize`.
3. If `Select`: Selector picks `f_t` from `F`.
4. If `Synthesize`: Agents generate `f_new`; `EvalTool` validates; valid `f_new` added to `F`; Selector picks from updated `F`.
5. `f_t` computes reward `s`.
6. GRPO updates policy using `s`.

**Design tradeoffs**:
- Cost vs. Generality: Web retrieval and code synthesis add latency but broaden coverage.
- Automation vs. Reliability: Fully automated synthesis risks buggy tools; verification mitigates but does not eliminate this (e.g., 5.1% code‑agent failure rate).
- Specialization vs. Universality: Relying on existing HuggingFace reward models limits coverage; CodeVerify fills gaps but only for objective, verifiable tasks.

**Failure signatures**:
- Router failure: Low accuracy on RewardBench‑V2 (<80%) leads to suboptimal reward selection.
- Synthesis failure: High rejection rate from `EvalTool` (e.g., >20% for web‑agent) indicates inability to find/wrap viable tools.
- Hacking persistence: If verbosity/length bias persists in trained models, it signals over‑reliance on LLM‑based tools without sufficient rule‑based constraints.

**First 3 experiments**:
1. **Ablation: Disable CodeVerify** – Train RLAR without code‑based verifier generation. Expect significant drop in math/coding benchmarks (GSM8K, LeetCode) as deterministic rewards are lost.
2. **Ablation: Disable WrapLLM** – Train without web‑retrieved LLM‑based reward models. Expect drop in chat/translation tasks that benefit from semantic understanding.
3. **Random Tool Selection** – Replace selector with random choice from library. Expect overall performance degradation, confirming importance of intelligent routing.

## Limitations
- The exact prompt for the Policy Router’s completeness assessment is undisclosed, hindering precise replication of the selection logic.
- WrapLLM’s Serper search queries, rate limits, and filtering heuristics are unspecified, leading to variability in retrieved tools.
- EvalTool’s validation procedures (e.g., consistency checks for LLM tools, execution tests for code) lack full implementation details, risking deployment of faulty tools.
