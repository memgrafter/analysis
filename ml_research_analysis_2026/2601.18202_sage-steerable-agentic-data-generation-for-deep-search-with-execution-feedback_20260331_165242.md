# SAGE: Steerable Agentic Data Generation for Deep Search with Execution Feedback

## Quick Facts
- **arXiv ID:** 2601.18202
- **Source URL:** https://arxiv.org/abs/2601.18202
- **Reference count:** 23
- **Primary result:** An agentic pipeline that automatically generates difficulty-controlled QA pairs with execution feedback, yielding up to 87% pass@4 and enabling significant gains in downstream search agent performance.

## Executive Summary
SAGE addresses the scarcity of high-quality training data for deep search agents by introducing an automated, agentic pipeline for generating question-answer pairs with controlled difficulty. The system uses a data generator to propose QA pairs and a search agent to test them, using execution traces as feedback to iteratively refine the generator’s output. Intrinsically, this process produces more correct and harder questions; extrinsically, training search agents on the resulting 20K synthetic dataset leads to substantial accuracy improvements on in-domain and out-of-domain multi-hop benchmarks, even when transferring to a different retrieval tool like Google Search.

## Method Summary
SAGE’s core is an iterative loop between a data generator agent and a search agent. Given a document and a target number of search steps \(S\), the generator produces an initial QA pair. The search agent then attempts to solve the question via multiple independent execution traces (queries, reasoning steps). These traces are used to verify correctness (pass@K) and difficulty (minimal steps among correct traces). If the pair fails either check, the execution traces are fed back to the generator in a structured prompt to produce a revised QA pair. This cycle repeats for up to \(R\) rounds. The final dataset consists of pairs with at least one correct trace, ensuring both validity and targeted difficulty.

## Key Results
- Intrinsically, SAGE achieves up to **87% pass@4** (vs. 18% baseline) and increases average search steps from 3.2 to **4.9**, with more diverse reasoning strategies.
- Extrinsically, training Qwen-7B on 20K SAGE examples improves average accuracy on 3-7 hop in-domain tasks by **29% relative** (38.1% vs. 29.6% with Musique).
- On out-of-domain benchmarks, it achieves **up to 23% relative improvement on FRAMES** and **50% on GAIA** when transferring to Google Search at inference, without further training.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Iterative refinement using the search agent’s execution traces improves correctness and difficulty by reconciling the generator’s planning with actual search behavior.
- **Mechanism:** The generator creates an initial QA pair. The search agent produces multiple traces; these are fed back to the generator to update the QA. The loop repeats until the pair meets correctness and difficulty criteria.
- **Evidence anchors:** Abstract mentions “execution feedback for iterative refinement”; Section 3.3 details using traces as feedback; Table 2 shows improvement from 18% to 50% correct/difficult data after three feedback rounds, with average steps rising from 3.3 to 4.9.
- **Break condition:** Generator may fail to improve after feedback due to context limits or inability to interpret traces; correlated errors between agents could prevent convergence.

### Mechanism 2
- **Claim:** Specifying a target number of search steps \(S\) in the generator’s prompt increases the difficulty of the resulting QA pairs.
- **Mechanism:** The prompt includes \(S\) (e.g., 4–7) and instructs the generator to plan a question requiring exactly \(S\) steps, biasing toward multi-hop reasoning. Feedback later helps adjust to meet \(S\).
- **Evidence anchors:** Section 3.1 describes including \(S\) in the prompt; Table 2 shows with \(S\), average steps rise modestly (3.3 vs 3.2) but correctness drops (71% vs 84%), a trade-off feedback mitigates.
- **Break condition:** If \(S\) exceeds generator capability or corpus information density, yield of correct, sufficiently difficult pairs remains low even with feedback.

### Mechanism 3
- **Claim:** SAGE produces questions with a broader spectrum of reasoning strategies than prior datasets, leading to better generalization of trained search agents.
- **Mechanism:** Grounding generation in a diverse corpus (Wikipedia) and verifying with a capable search agent leads to emergent complexity; the generator is unconstrained by templates.
- **Evidence anchors:** Section 5.2/Figure 3: SAGE data covers more reasoning types (e.g., calculation 35% vs 5% in Musique, temporal 32% vs 8%); Tables 3–4 show correlated downstream gains on FRAMES and GAIA.
- **Break condition:** Generated strategies may not align with specific downstream tasks; overfitting to certain patterns could reduce diversity over time.

## Foundational Learning
- **Search-augmented LLM agents (ReAct style):** Needed because SAGE’s verification relies on an agent that interleaves reasoning and search queries to produce execution traces. Quick check: What are the two main types of output tokens in a ReAct trace, and how do they interact?
- **Difficulty measurement via search step count:** Central to SAGE’s control; the target \(S\) operationalizes difficulty and drives generation/verification. Quick check: How does SAGE define the number of search steps for a given QA pair, and why is it a proxy for difficulty?
- **Outcome-based reinforcement learning for search agents:** Synthetic data from SAGE trains agents via PPO using answer correctness as reward. Quick check: In the Search-R1 framework, what is the reward signal for PPO training, and what trajectories are required?

## Architecture Onboarding
- **Component map:** Data Generator Agent (A_gen) -> Search Agent (A_search) with Retrieval Model (T) and Corpus (D) -> Verification Module (computes pass@K, minimal steps) -> Feedback Loop Controller (manages rounds, accumulates traces, filters pairs).
- **Critical path:** 1) Sample document \(d\) from corpus. 2) A_gen(\(d, S\)) → (\(q, a, t_{\text{gen}}\)). 3) RunSearchAgent(\(q, a, S, K\)) → (\(a^*, S^*, t_{\text{search}}\), is_correct, is_difficult). 4) If not (correct ∧ difficult) and round < \(R\), prompt A_gen with traces to get updated QA; repeat from step 3. 5) After \(R\) rounds or success, return only if correct; else discard.
- **Design tradeoffs:** Same LLM for generator and search agent reduces cost and ensures compatibility vs. different models for independent verification; fixed corpus (Wikipedia) ensures reproducibility vs. dynamic web search for realism; feedback rounds \(R\) improve quality with diminishing returns; filtering pass@K=1 maximizes yield but admits noise; higher target \(S\) yields harder questions but lower success rates.
- **Failure signatures:** Low yield (few pairs meet criteria); homogeneous reasoning (superficial patterns); search agent errors dominating (>50% failures due to retrieval); stalled feedback loop (no improvement); divergence (updated QA unrelated to document).
- **First 3 experiments:** 1) **Intrinsic evaluation:** Generate QA with varying \(S\) and feedback rounds; compute % pass@K, avg. steps; compare against baselines (no \(S\), no feedback). 2) **Downstream training:** Train a search agent (Qwen-7B) with PPO on 20K SAGE examples; evaluate on in-domain multi-hop and out-of-domain benchmarks (Musique, FRAMES); compare against NQ+HotpotQA and Musique-trained agents. 3) **Transfer test:** Evaluate SAGE-trained agent on GAIA/Browsecomp/HLE-Search by swapping retriever to Google Search at inference; compare to baseline-trained agents.

## Open Questions the Paper Calls Out
1. How to implement iterative co-evolution of the data generator and search agent? The authors suggest alternating training cycles; evidence would compare data quality and final agent performance against static baselines.
2. What robust verification methods can identify correct (q,a) pairs that current search agents fail (pass@K=0)? The paper notes this discards potentially valid but challenging pairs; evidence would use stronger verifiers (e.g., human annotation) and measure impact on data diversity and downstream performance.
3. Does SAGE generalize to domain-specific corpora (e.g., legal, scientific)? The authors only experiment with Wikipedia; evidence would apply SAGE to such domains, evaluate intrinsic quality, and train/test on domain-specific benchmarks.

## Limitations
- Proprietary Gemini models used; performance with open-source alternatives (e.g., Qwen) is inferred but not verified.
- Retriever specifics (E5 variant, passage chunking) and decoding settings (e.g., “disable thinking”) lack precise documentation, hindering exact replication.
- PPO hyperparameters are borrowed from prior work; optimal settings for SAGE’s synthetic data may differ.

## Confidence
- **Intrinsic correctness/difficulty gains:** High (Table 2 shows clear improvement with feedback rounds; ablations isolate effects).
- **Difficulty control via target step \(S\):** Medium (Table 2 shows trade-off without feedback; feedback mitigates but yield drops for \(S \geq 6\), per Figure 2).
- **Reasoning diversity → OOD transfer:** High (Tables 3–4 show correlated gains; Figure 3 diversity analysis supports mechanism).
- **Google Search transferability:** Medium (GAIA results positive but single benchmark; no cross-validation on other web-search tasks).

## Next Checks
1. **Open-source replication:** Implement SAGE using Qwen-2.5-7B for both generator and search agent, with Contriever retriever. Measure pass@4 and average steps against paper’s numbers (87% pass@4, 4.9 steps) to quantify gap from proprietary models.
2. **Feedback round ablation:** Fix \(S=5\) and vary feedback rounds \(R\) (0–4) on 1K samples. Plot yield (valid pairs) and difficulty (minimal steps) to identify point of diminishing returns and optimal compute-quality trade-off.
3. **Diversity isolation test:** Train two search agents on SAGE-filtered data: one with only calculation/temporal questions, another with random subset. Evaluate on FRAMES and GAIA to quantify marginal gain from each reasoning type and test if diversity is necessary for OOD transfer.
