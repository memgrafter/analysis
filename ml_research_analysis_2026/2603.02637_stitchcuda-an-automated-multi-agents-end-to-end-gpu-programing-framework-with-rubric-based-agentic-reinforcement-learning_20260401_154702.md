# StitchCUDA: An Automated Multi-Agents End-to-End GPU Programing Framework with Rubric-based Agentic Reinforcement Learning
## Quick Facts
- arXiv ID: 2603.02637
- Source URL: https://arxiv.org/abs/2603.02637
- Reference count: 40
- Primary result: On KernelBench Level 3 (the hardest end-to-end tasks), StitchCUDA achieves nearly 100% success rate and average speedup of 1.72× over multi-agent baseline and 2.73× over RL model baselines, even outperforming the stronger GPT-5.2 baseline.

## Executive Summary
StitchCUDA tackles the challenge of automated end-to-end GPU programming, which prior LLM-based methods failed to achieve due to their single-kernel focus. It introduces a multi-agent system comprising a Planner, Coder, and Verifier that collaboratively generate, test, and optimize complete GPU programs. The Coder is further enhanced via rubric-based agentic reinforcement learning (RL), which decomposes the complex multi-turn process into two atomic skills: generating code from high-level tasks and refining based on structured feedback. A combined reward—incorporating expert-aligned rubrics and execution-based metrics—prevents reward hacking and encourages advanced optimizations such as kernel fusion and tensor core usage. Evaluated on KernelBench Level 3, the hardest tasks in the suite, StitchCUDA attains near-perfect functional correctness and significant speedups over both multi-agent and RL baselines, while surpassing the stronger GPT-5.2 model.

## Method Summary
StitchCUDA’s workflow is an iterative coding‑feedback loop. The Planner first analyzes a PyTorch reference implementation and initial Nsys profiling to produce a structured decomposition—identifying kernel fusion boundaries, tensor shapes, and host‑side constraints. For each subtask, the Coder generates CUDA kernel and host code, compiles with `nvcc`, and runs local tests. If compilation or testing fails, the Verifier returns an error and the Coder retries; if tests pass, the Verifier profiles performance with Nsys/NCU and returns structured feedback for optimization. The Coder refines the code accordingly, repeating until a speedup goal is reached or iteration limits expire. After a subtask succeeds, the loop proceeds to the next, and finally runs an integration test that may trigger a full re‑plan if performance regresses.

The Coder’s policy is improved offline via rubric‑based agentic RL. Instead of costly full‑trajectory rollouts, training samples single‑turn examples for two atomic skills: (1) generating initial code from a Planner specification and reference, and (2) refining code given Verifier feedback. The reward function combines a rule‑based term (correctness, speedup) with a shaping term from an expert‑aligned rubric that scores Anti‑Hacking, CUDA Engineering (e.g., use of tensor cores, custom fusion), Operator Coverage, and Skill Compliance. This design prevents degenerate solutions like copying PyTorch code and encourages meaningful optimizations. The RL uses Group Relative Policy Optimization (GRPO) to update a backbone LLM (e.g., Qwen3‑32B), yielding a Coder that excels at both initial implementation and iterative optimization.

## Key Results
- Nearly 100% success rate on KernelBench Level 3 (the hardest end‑to‑end tasks).
- Average end‑to‑end speedup of 1.72× over the multi‑agent baseline and 2.73× over RL model baselines.
- Outperforms the stronger GPT-5.2 baseline on the same benchmark.

## Why This Works (Mechanism)
### Multi-Agent Orchestration
StitchCUDA employs a three‑agent system (Planner, Coder, Verifier) to tackle end‑to‑end GPU programming. The Planner examines a PyTorch reference and initial profiling to produce a structured plan: fusion boundaries, tensor shapes, and host constraints. The Coder implements the CUDA kernels and host code for each subtask, compiles, and tests locally. Upon passing tests, the Verifier profiles performance with Nsys/NCU and returns structured feedback for optimization. This “plan–code–profile–refine” cycle repeats per subtask, with the Verifier routing decisions (retry, advance, or re‑plan) based on outcomes. The core assumption is that end‑to‑end performance depends on both kernel efficiency and host orchestration, requiring global program‑level reasoning beyond single‑kernel approaches. Evidence from the paper’s experiments and comparisons to single‑kernel frameworks support this. The loop fails if the Planner’s decomposition is infeasible, the Coder cannot improve despite feedback, or the Verifier’s profiling misguides optimization, exhausting the iteration budget.

### Rubric‑Based Agentic Reinforcement Learning
The Coder’s policy is enhanced through reinforcement learning that uses a combined reward signal to avoid hacking and promote advanced optimizations. Training decomposes the multi‑turn process into two atomic skills: (1) generating CUDA code from a Planner’s subtask specification and reference, and (2) refining an existing implementation based on Verifier feedback. Standard single‑turn GRPO is applied to these skills, avoiding the cost of full multi‑turn rollouts. The reward combines a rule‑based term (correctness, speedup) with an expert‑aligned rubric scoring four dimensions: Anti‑Hacking, CUDA Engineering (e.g., tensor cores, fusion), Operator Coverage, and Skill Compliance. The rubric provides a rich training signal that discourages degenerate behaviors like copying PyTorch code and encourages sophisticated techniques. Ablation studies in the paper confirm the rubric’s contribution: the full system significantly outperforms a variant trained without it. Potential break conditions include misaligned rubric criteria or failure to capture subtle hacking.

### Atomic Skill Decomposition for Efficiency
Collecting full multi‑turn trajectories for agentic RL would be prohibitively slow (≈60–75 minutes per trajectory in a CUDA environment). StitchCUDA instead gathers single‑turn examples for each atomic skill directly from real workflow executions: for Skill 1, Planner specifications plus reference; for Skill 2, Verifier feedback paired with the preceding code. These examples train the Coder with GRPO in a standard single‑turn setup, reducing computational cost dramatically. The authors report a reduction from thousands of H200‑hours to a few hundred. The core assumption is that these two skills encapsulate the main challenges of end‑to‑GPU programming and can be learned independently. However, if long‑range dependencies exist (early decisions affecting later subtasks), the atomic approach might miss them, though the paper argues this risk is minimal in practice.

## Architecture Onboarding
### Component Map
- **Planner**: Parses PyTorch reference, runs initial Nsys profiling, emits a structured to‑do list (fusion opportunities, kernel specs, host‑side constraints).
- **Coder**: Backbone LLM (e.g., Qwen3‑32B) that produces CUDA source files, invokes `nvcc`, and iteratively refines code based on Verifier feedback.
- **Verifier**: Compiles code, runs unit tests, performs Nsys/NCU profiling, produces JSON feedback with routing decision (coding/next_task/final_test).
- **Shared State**: Typed object containing generated code, build artifacts, profiling results, and routing metadata; accessible to all agents.
- **RAG Module**: Vector database of latest NVIDIA documentation (cuBLAS, CUTLASS, architecture whitepapers) to retrieve accurate API details for Planner and Verifier.
- **RL Training Loop**: Offline data collection from previous workflow runs; rubric reward assessment via expert LLM; updates Coder with GRPO.

### Critical Path
1. Planner creates subtask list from the reference implementation.
2. For each subtask:
   - Coder generates code → compile.
   - If compilation fails, Verifier returns error and Coder retries.
   - If tests pass, Verifier profiles with Nsys/NCU → returns optimization feedback.
   - Coder refines code; repeat until speedup goal or max iterations.
3. After a subtask succeeds, advance to the next subtask.
4. After all subtasks, run final integration test; if performance regresses, trigger replanning.
5. RL training separately samples from successful and failed trajectories to update the Coder model.

### Design Tradeoffs
- **Multi‑agent decomposition**: Reduces single‑agent complexity but introduces communication overhead and potential state drift; mitigated by strict State schema and routing logic.
- **Atomic RL**: Avoids expensive multi‑turn rollouts but may miss higher‑order dependencies; authors argue the two skills cover most needed behaviors.
- **Rubric reward**: Adds computational cost (LLM calls) and design effort but effectively prevents reward hacking; trade‑off is slower per‑step reward yet better final performance.
- **RAG**: Improves API accuracy yet adds retrieval latency; agents invoke it only when necessary to balance correctness and efficiency.

### Failure Signatures
- Planner emits infeasible fusion boundaries or incorrect tensor shapes, causing Coder to produce mismatched kernels.
- Coder repeatedly ignores Verifier feedback (e.g., continues generating PyTorch‑only code), indicating insufficient RL training or rubric mis‑specification.
- Verifier misclassifies bottlenecks (e.g., labeling memory‑bound kernels as compute‑bound), leading to ineffective optimizations.
- Reward hacking persists despite rubric (e.g., subtle hard‑coding of outputs), suggesting rubric criteria require refinement.
- Iteration budget exhausted due to slow convergence or repeated compilation errors.

## Open Questions the Paper Calls Out
1. Can StitchCUDA’s multi‑agent design scale to more complex end‑to‑end GPU programs (e.g., KernelBench Level 4 or large models like BERT/ResNet‑152)? The paper only evaluates up to Level 3, leaving the behavior on richer structures unknown.
2. Does the rubric‑based reward generalize beyond NVIDIA GPUs and CUDA? The rubric is tailored to CUDA‑specific optimizations and NVIDIA tools; its validity on AMD GPUs or ROCm remains an open question.
3. How essential is the RAG module to StitchCUDA’s performance and feedback quality? The framework uses RAG, but no ablation isolates its contribution, making it unclear whether it is critical or auxiliary.

## Limitations
- Rubric design and scoring thresholds are not public, hampering exact replication.
- Dataset splits and manual task fixes are incompletely documented, risking data leakage.
- RAG retrieval details are underspecified, limiting reproducibility.
