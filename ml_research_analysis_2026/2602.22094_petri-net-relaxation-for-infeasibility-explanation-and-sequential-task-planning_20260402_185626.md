# Petri Net Relaxation for Infeasibility Explanation and Sequential Task Planning

## Quick Facts
- **arXiv ID:** 2602.22094  
- **Source URL:** https://arxiv.org/abs/2602.22094  
- **Reference count:** 40  
- **Primary result:** A Petri net relaxation method transforms planning into LP feasibility, enabling efficient infeasibility detection, explanations, and incremental handling of dynamic updates, with empirical gains in detection rate and sequential planning speed.

## Executive Summary
This paper addresses sequential task planning in dynamic environments where goals or constraints change over time—a scenario often overlooked by one-shot planners. The core method converts grounded PDDL problems into Petri nets and relaxes reachability to a linear program (LP). This LP serves as a polynomial-time necessary condition for feasibility, enabling invariant synthesis and goal-unreachability detection. Infeasibility is explained via conflicting LP constraints. Incremental constraint solving supports updates efficiently. Empirically, the approach detects up to 2× more infeasible cases (48/50) faster than baselines and reduces cumulative runtime for sequential planning with updates, while maintaining competitive one-shot planning performance.

## Method Summary
The process starts by grounding a PDDL domain into propositional variables and actions, then constructing a Petri net: places represent state variables, transitions represent actions, and arcs encode preconditions/effects with numeric bounds inferred from effects. A relaxed linear system (the marking equation) is formed by summing all transition firings across planning steps and adding slack variables for Boolean rebindings, yielding an LP whose feasibility is necessary for reachability. This LP synthesizes mutex invariants via pairwise infeasibility checks and detects unreachable goals. Explanations are found by minimizing disabled goal clauses via an MILP. For dynamic updates (goal changes or added constraints), the constraint model is updated incrementally with warm starts or assumption-based solving, while forward/backward reachability propagation prunes variables and bounds the horizon.

## Key Results
- Detects up to 2× more infeasible cases (48 out of 50 tested) with lower detection times compared to baselines (FF, ENHSP, FD, Mp).
- Outperforms baselines in cumulative runtime for sequential planning with 30 updates, leveraging incremental solving and warm starts.
- Generates a comparable number of invariants to Madagascar and Fast Downward in classical domains; one-shot planning performance is domain‑dependent.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Polynomial-time LP feasibility of the relaxed PN marking equation is a necessary condition for planning feasibility.
- **Mechanism:** Transform grounded PDDL into a PN; derive the marking equation (token flow conservation). Relax by summing all transition firings across steps, adding non‑negative slack variables for Boolean "rebinding" effects, and treating all variables as continuous. This yields a linear system (Eq. 10) whose feasibility implies possibility of a reachable marking.
- **Core assumption:** Token conservation holds when aggregating flows over all steps; intermediate state constraints (non‑negativity, bounds) are ignored by the relaxation.
- **Evidence anchors:** [abstract]: "relaxing PN reachability to a linear program (LP)" and "efficient goal-unreachability detection". [section 5.3]: Derivation of Eq. (10) and Proposition 1 (infeasible LP ⇒ unreachable marking). [corpus]: Limited direct evidence; neighboring papers focus on PN modeling but not this specific LP relaxation.
- **Break condition:** Floating‑point rounding errors may cause false infeasibility (Sec. 6.4).

### Mechanism 2
- **Claim:** Pairwise LP infeasibility for two places' final token counts identifies mutex invariants.
- **Mechanism:** For each place pair, freeze other variables, project Eq. (10) onto the two places' rows (Eq. 12). Infeasibility of this subsystem means both places cannot be true simultaneously in any reachable state.
- **Core assumption:** Pairwise checks scale to larger mutex groups via greedy combination (Eq. 13).
- **Evidence anchors:** [section 5.4]: Derivation of Eq. (12) and mutex group construction. [section 6.1]: Empirical invariant count comparison against baselines.
- **Break condition:** The relaxation may deem a mutex pair feasible if intermediate token counts could go negative, though this did not occur in tested domains.

### Mechanism 3
- **Claim:** Incremental constraint solving with warm starts reduces cumulative runtime for sequential planning updates.
- **Mechanism:** Maintain the constraint model across updates; modify only goal clauses or add global constraints; reuse solver state (assertion stack or assumptions). Previous solution provides a warm start for MILP solvers.
- **Core assumption:** Updates are restricted to goal changes or added constraints; underlying PN and relaxed LP structure remain valid.
- **Evidence anchors:** [abstract]: "incremental constraint solving to support goal and constraint updates" and "outperforms in sequential plan updates". [section 5.8]: Formal update definitions and incremental solving procedure. [section 6.3]: Cumulative time plots showing advantage over baselines.
- **Break condition:** General structural updates (e.g., new actions, modified preconditions) require rebuilding PN and LP, losing incremental benefits.

## Architecture Onboarding
### Component map
PDDL Grounder → PN Constructor → Reachability Propagator → LP Relaxation Generator → {Invariant Synthesizer, Infeasibility Explainer, Sequential Planner}

### Critical path
Ground PDDL → Build PN → Propagate reachability (fix constants & bound h) → Synthesize invariants → For each update: modify goals/constraints → check LP feasibility → if feasible, solve planning LP with incremental horizon extension → output plan or explanation.

### Design tradeoffs
- *Relaxation completeness:* LP feasibility is necessary but not sufficient; tradeoff: polynomial‑time test vs. potential false positives.
- *Invariant granularity:* Pairwise checks are embarrassingly parallel but may miss larger mutex groups; greedy grouping reduces solver constraints but is suboptimal.
- *Solver choice:* SMT handles logical structure natively; MILP benefits from warm starts but requires CNF translation. Uses both (Z3, Gurobi) for robustness.

### Failure signatures
- Spurious infeasibility due to floating‑point tolerance; check with rational arithmetic or tightened tolerances.
- Poor scaling: large grounded state space leads to huge PN → large LP → slow solve; look for high grounding factor.
- Missing mutexes: if invariant count is low, propagation may be insufficient; consider stronger propagation.
- Incremental solving not providing speedup; verify warm start reuse and pruning efficiency.
- Inability to handle added global constraints; ensure they are correctly injected as per‑step or final‑step constraints.

### First 3 experiments
1. **Invariant generation benchmark:** Compare mutex counts on classical IPC domains against Madagascar and Fast Downward; validate counts are comparable and inspect pairwise runtime.
2. **Infeasibility detection:** Run on Unsolvability IPC 2016 + numeric domains; measure detection count/time vs. FF, ENHSP, FD, Mp; validate system finds ≥48/50 infeasibilities.
3. **Sequential planning:** Generate update sequences in Block Grouping/Counters; measure cumulative time for goal updates and constraint additions; validate improvement over one‑shot replanning baselines.

## Open Questions the Paper Calls Out
- **Open Question 1:** Can the Petri net relaxation approach be extended to handle arbitrary updates to the planning domain, such as changes to action preconditions or effects? *Basis:* Section 5.8 notes only goal changes and constraint additions are efficiently supported; general updates would require dynamic restructuring.
- **Open Question 2:** Under what conditions does the LP relaxation's feasibility guarantee an actual feasible plan, and how does this gap vary across domain characteristics? *Basis:* Proposition 1 gives only necessity; the converse is not proven and false positive rate is unquantified.
- **Open Question 3:** How does the constraint‑based approach scale compared to heuristic methods as problem size increases, and what are the practical limits? *Basis:* Section 6.4 acknowledges performance challenges; experiments use only small IPC instances.
- **Open Question 4:** To what extent does the choice between SMT and MILP solvers affect performance, and are there domain characteristics that favor one? *Basis:* Both Z3 and Gurobi are used but no comparative analysis is provided.
- **Open Question 5:** Can invariant synthesis capture more complex invariants beyond pairwise mutexes without polynomial blowup? *Basis:* The method checks candidates independently and uses greedy grouping; Madagascar generates more invariants via iterative regression.

## Limitations
- Specific problem instances for auto‑generated domains (Delivery, Counter) are not provided, hindering exact replication.
- Greedy mutex group construction details (order, tie‑breaking) are unspecified, affecting invariant counts and performance.
- Floating‑point tolerance in LP solvers may cause spurious infeasibility; rational arithmetic is suggested but not used in benchmarks.

## Confidence
- Polynomial‑time LP feasibility as necessary condition: High (formally derived, but numerical issues possible)
- Pairwise mutex detection via LP: Medium (empirically comparable, but relaxation may miss larger mutexes)
- Incremental solving advantage: High (empirical cumulative runtime improvements shown)
