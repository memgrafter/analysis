# Tracking Equivalent Mechanistic Interpretations Across Neural Networks
## Quick Facts
*   **arXiv ID:** 2603.30002
*   **Source URL:** https://arxiv.org/abs/2603.30002
*   **Reference Count:** 40
*   **Primary Result:** Defines interpretive equivalence via overlapping implementation sets and introduces Congruity, an algorithm using linear representation similarity from causal interventions to determine if models share the same high-level algorithm without needing explicit descriptions.

## Executive Summary
The paper addresses a fundamental gap in mechanistic interpretability (MI): the lack of a rigorous definition for when two interpretations of a model are equivalent. It proposes that interpretations are equivalent if the sets of all neural network implementations realizing them overlap. To operationalize this, the authors develop Congruity, an algorithm that samples diverse implementations of a model via causal interventions on unimportant components and measures the linear similarity of their hidden representations. Theoretical results prove this similarity is necessary and sufficient for interpretive equivalence under the linear representation hypothesis. Experiments on synthetic tasks and real models (GPT-2, Pythia) demonstrate that Congruity effectively distinguishes between different high-level algorithms (e.g., sorting vs. counting) and shows that smaller models often implement the same interpretation as larger ones on tasks like Indirect Object Identification, providing a formal foundation for scaling MI.

## Method Summary
Congruity determines if two model families (A and B) share an interpretation by comparing the geometry of their sets of implementations. First, for each model, it identifies components causally unrelated to the task (the circuit's complement). It then generates multiple implementations per model by applying random interventions (e.g., patching) to these unimportant components, preserving the core algorithm. For each implementation, it extracts a fixed set of hidden representations (e.g., final-layer residual streams) on a evaluation dataset. Pairwise similarity between implementations is measured by `ReprDist`: given two implementations (h₁, h₂) and a reference from h₁'s family (h₁*), it fits bidirectional linear regressions to map between their representation matrices and checks if h₁ is closer to h₁* than h₂ is. The probability `p` that a random (A, A*, B) triple satisfies this condition is computed in both directions, and Congruity is `1 - |p + π - 1|`, where π is the symmetric probability. High Congruity indicates the implementation sets overlap, implying interpretive equivalence.

## Key Results
*   On a synthetic n-permutation detection task with six RASP-based interpretations (four sorting, two counting), Congruity achieved average within-family congruence of 0.43 for sorting-based models versus 0.01 across families, cleanly separating distinct algorithmic interpretations.
*   For the Indirect Object Identification (IOI) task applied to GPT-2 and Pythia (85M–2.9B), within-family Congruity scores ranged from 0.73 to 0.92, while cross-family scores dropped to approximately 0.13, supporting the hypothesis that larger models reduce to simpler ones' implementations.
*   Comparing GPT-2's next-token prediction to a syntactic parts-of-speech circuit revealed high Congruity for syntactic tokens (e.g., terminal punctuation) but not for semantic ones (e.g., articles), demonstrating interpretive alignment between tasks varies by token type.

## Why This Works (Mechanism)
### Mechanism 1: Interpretive Equivalence via Overlapping Implementation Sets
*   **Claim:** Two models share the same high-level interpretation iff the sets of all possible implementations (neural networks realizing that interpretation) intersect, without requiring an explicit algorithm description.
*   **Mechanism:** For a fixed interpretation, many implementations exist due to neural network redundancy. Interventions on causally irrelevant components produce new implementations while preserving the interpretation. Equivalence is determined by whether these implementation sets have non-empty intersection.
*   **Core Assumption:** The interpretation is invariant to modifications of components outside the core circuit, and these components can be reliably identified.
*   **Evidence Anchors:** The principle is formalized in the paper's framework. Section 2 notes that interventions on causally unrelated components yield equivalent implementations. The synthetic task experiment confirms that implementations within an interpretation family are mutually congruent while those across families are not.

### Mechanism 2: Linear Representation Similarity as a Proxy for Implementation Overlap
*   **Claim:** If two implementations stem from the same interpretation, their hidden representations across layers should be linearly aligned; this alignment is captured by the `ReprDist` metric.
*   **Mechanism:** Congruity samples three implementations: two from model A (same interpretation) and one from model B. Using multi-target linear regression, it computes the bidirectional linear approximation error (`drepr`) between pairs. If the two A-implementations are more linearly similar to each other than either is to the B-implementation, the families likely share an interpretation.
*   **Core Assumption:** The linear representation hypothesis holds sufficiently; algorithmic features are linearly decodable from the chosen hidden states.
*   **Evidence Anchors:** The theoretical framework (Definition 6.1, Theorem 6.2) establishes necessity and sufficiency of representation similarity for equivalence under linearity. Empirically, the synthetic task shows clear separation in `drepr` values within vs. across interpretation families.

### Mechanism 3: Intervention-Implementation Duality Enables Scalable Sampling
*   **Claim:** Causal interventions on unimportant components generate a diverse set of implementations, allowing estimation of the implementation set's "diameter" (compression) without enumeration.
*   **Mechanism:** Instead of enumerating all implementations (infeasible), the algorithm defines an alignment class Π via which interventions preserve the interpretation. Sampling interventions from this class yields implementations that cover the set's geometry. Congruity uses these samples to estimate equivalence via the Hausdorff-like distance `dinterp`.
*   **Core Assumption:** The intervention distribution adequately covers the true implementation set; unimportant components are truly independent of the core algorithm.
*   **Evidence Anchors:** Algorithm 1 (`GetImpl`) explicitly constructs implementations via interventions. Appendix H.2 formalizes the duality. IOI experiments use ablations of previously identified "unused" components to generate implementations, demonstrating practical applicability.

## Foundational Learning
*   **Mechanistic Interpretability (MI):** The bottom-up reverse-engineering of neural networks into human-understandable circuits and algorithms. **Why needed:** The paper operates within MI's two-stage paradigm (circuit discovery → interpretation) and seeks to formalize the second stage's validation problem. **Quick check:** What distinguishes bottom-up circuit discovery from top-down hypothesis testing in MI, and how does interpretive equivalence bridge them?
*   **Causal Abstraction:** A framework for relating a low-level system (a neural circuit) to a high-level causal model (an interpretation) via an alignment map that preserves interventions. **Why needed:** Interpretive equivalence is defined using causal abstraction; the theoretical guarantees rely on intervention consistency. **Quick check:** How does an alignment map `π` ensure that an intervention on the high-level model corresponds to a compatible intervention on the circuit (Equation D.2)?
*   **Circuit Discovery:** The process of identifying a minimal subnetwork (circuit) responsible for a behavior, often via patching or ablation. **Why needed:** Congruity requires knowing which components are causally unimportant (the circuit's complement) to sample valid implementations; it relies on prior circuit analyses for real models. **Quick check:** What is the conceptual difference between a *circuit* (a specific subnetwork) and an *implementation* (a full model instantiation), and why doesn't Congruity need a minimal circuit?

## Architecture Onboarding
### Component map
Congruity (Algorithm 1) -> GetImpl (samples implementations via interventions) & GetReprs (extracts hidden states) -> ReprDist (computes linear similarity via multi-target regression) -> drepr metric -> Congruity score (aggregates ReprDist probabilities)

### Critical path
1.  Acquire base models that solve the same task and identify causally unimportant components (e.g., via prior patching analysis).
2.  For each model, generate N implementations by applying random interventions (e.g., patching, noise) to the unimportant components, verifying each still solves the task with high accuracy.
3.  For every implementation, run a fixed evaluation dataset (e.g., 200 sentences) through the model and extract the chosen hidden representation vectors (e.g., final residual stream at a specific token).
4.  For all pairs of implementations within a family and across families, compute `drepr` using bidirectional linear regression on their representation matrices.
5.  Use `drepr` values within `ReprDist` to estimate probabilities p and π that an implementation is closer to a same-family sibling than to a cross-family member.
6.  Calculate final Congruity as `1 - |p + π - 1|`.

### Design tradeoffs
*   **Linear vs. nonlinear similarity:** Linear regression is fast and theoretically grounded but may fail if representations are nonlinear. Nonlinear methods (CCA, kernels) could improve sensitivity but break formal guarantees.
*   **Layer and representation choice:** Using final layers captures output-level equivalence but may mix irrelevant information; earlier layers might reveal algorithmic steps but be noisier. The paper does not specify layer selection criteria, leaving it task-dependent.
*   **Intervention design:** Interventions must preserve the interpretation. Using components from prior circuit work is safe but limits generalizability; random interventions risk altering the core algorithm.
*   **Number of implementations:** More samples better approximate the implementation set but linearly increase computation. The paper uses 10–100; the tradeoff is between variance reduction and runtime.

### Failure signatures
*   **Low within-family Congruity (<0.3):** Indicates either misidentification of unimportant components (circuit complement) or that the linear similarity metric is too weak for the chosen representations/layer.
*   **Cross-family Congruity > within-family:** Suggests the task is solved by a trivial, shared heuristic or that interventions failed to distinguish the models' core computations.
*   **High variance in `drepr` estimates:** Representations may be unstable across seeds or inputs; increase sample size (inputs, implementations) or check regression quality (R²).
*   **Task accuracy drops post-intervention:** If implementations no longer solve the task, the intervention altered the interpretation; revise the definition of unimportant components or intervention strength.

### First 3 experiments
1.  **Synthetic validation task:** Implement the six RASP-based programs for n-permutation detection (four sorting, two counting) as Transformers. For each, generate 100 implementations via weight perturbation and unimportant-component ablation. Run Congruity and confirm within-group scores >0.4 and cross-group scores <0.05.
2.  **IOI across model scales:** For GPT-2 small/medium and Pythia 85M/160M/410M/2.9B, generate 10 implementations each by ablating heads identified as outside the IOI circuit (from prior work). Compute pairwise Congruity and verify within-family high (0.7–0.9) vs. cross-family low (~0.1), with the noted exception of Pythia-160M/410M vs. GPT-2 small/medium.
3.  **POS circuit and token type analysis:** Extract a "POS circuit" from GPT-2 using the method of Todd et al. (function vectors). For GPT-2 next-token prediction, evaluate Congruity between the model's representations and the POS circuit for different token groups (e.g., articles, terminal punctuation). Expect high Congruity for syntactic tokens (punctuation) and low for semantic tokens (articles).

## Open Questions the Paper Calls Out
1.  Why do Pythia-160M and 410M show increased congruence with GPT2-medium and small respectively on the IOI task, despite overall low cross-family congruence? The authors suggest subtle similarities in name-mover head representations but find it unclear.
2.  How can representation similarity metrics be broadened beyond linear transformations to capture non-linear representational similarities while maintaining computational tractability? The paper notes the tension and leaves implications for future work.
3.  Once interpretive equivalence is established, how can the actual shared interpretation be extracted or reverse-engineered? The paper states equivalence alone is insufficient to identify interpretations and leaves formal exploration for future work.
4.  How robust is Congruity to different choices of alignment classes Π and intervention strategies in `GetImpl`? The sensitivity of empirical results to these theoretical choices is not explored.
5.  Under what conditions does the linear representation hypothesis hold sufficiently for Congruity to reliably detect interpretive equivalence on complex, realistic tasks? Mixed results (high for IOI, moderate for POS/token types) suggest the boundary is unclear.

## Limitations
*   The definition of equivalence via overlapping implementation sets is theoretically elegant but may not capture all intuitive notions of algorithmic sameness (e.g., functionally equivalent but structurally different circuits).
*   Congruity's empirical reliability hinges on the linear representation hypothesis; if features are not linearly decodable in the chosen layer, the necessary/sufficient guarantees may not hold in practice.
*   Sampling implementations requires accurate prior identification of causally unimportant components, which itself depends on task-specific mechanistic analyses that may be incomplete or incorrect.

## Confidence
*   **Interpretive equivalence via overlapping implementations:** Medium (formalism is sound but alignment with intuitive algorithmic equivalence is uncertain).
*   **Linear similarity ⇔ equivalence (theoretical):** High under stated assumptions; Medium if assumptions are relaxed for real-world representations.
*   **Intervention-implementation duality (practical coverage):** Low-Medium (theoretically valid, but empirical coverage of the implementation space is untested).
*   **Empirical validation (synthetic task):** Medium (controlled conditions).
*   **Empirical validation (real models: IOI, POS):** Medium (results depend on prior circuit definitions which may not be unique or complete).
*   **General applicability to new tasks/models:** Low (many open hyperparameter and architecture questions remain).

## Next Checks
1.  **Circuit Identification Sensitivity:** Replicate IOI experiments using alternative sets of "unimportant" components (e.g., from gradient attribution or random head ablation) and measure stability of within-family and cross-family Congruity scores.
2.  **Nonlinear Comparison Baseline:** Compute a non-linear Congruity analogue using kernel CCA or centered kernel alignment on the same implementations and compare to linear results to assess sensitivity to the linearity assumption.
3.  **Sample Complexity Analysis:** Systematically vary the number of implementations sampled per model (e.g., 5, 10, 20, 50, 100) and plot Congruity as a function of sample size to determine stable sampling budgets and confirm reported scores are not due to undersampling.
