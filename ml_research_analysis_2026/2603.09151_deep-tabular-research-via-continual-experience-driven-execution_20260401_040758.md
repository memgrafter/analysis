# Deep Tabular Research via Continual Experience-Driven Execution

## Quick Facts
- **arXiv ID:** 2603.09151
- **Source URL:** https://arxiv.org/abs/2603.09151
- **Reference count:** 40
- **Primary result:** State‑of‑the‑art on DTR‑Bench (37.5% accuracy) and RealHitBench (up to 70.90% LLM‑EVAL data analysis, 100% execution correctness) with only 4.78 average LLM calls.

## Executive Summary
Large language models struggle with complex, long‑horizon analytical reasoning over unstructured tables featuring hierarchical and bidirectional headers. This paper formalizes the problem as Deep Tabular Research (DTR) and proposes an agentic framework that decouples strategic planning from low‑level execution. The core innovations include a hierarchical meta graph to capture table semantics, an expectation‑aware selection policy (p‑UCB) to navigate operation paths, and a siamese structured memory that integrates parameterized feedback and abstracted experience for continual refinement. Evaluations on DTR‑Bench and RealHitBench show significant gains in accuracy, analysis depth, and efficiency, using far fewer LLM calls than prior approaches.

## Method Summary
The method begins by constructing a hierarchical meta graph from the input table, which explicitly models bidirectional header relationships and latent structural dependencies. This graph, along with the natural language query, is used to generate a set of candidate operation paths (e.g., sequences of CLEAN, FILTER, GROUP, AGG, etc.) via a predefined operation bank. An expectation‑aware selection policy, inspired by the UCB bandit algorithm, scores each path based on historical rewards, a structural prior, and an exploration bonus. The highest‑scoring path is executed using a prompting strategy that separates reasoning ([THINK]) from code generation ([CODE]). After execution, a siamese memory updates: a parameterized store records success, time, and type consistency to refine path statistics; an abstracted store captures high‑level strategic observations (e.g., “filter before aggregate”) for generalization. The loop repeats, refining paths until a valid answer is produced; final results are aggregated via majority vote across multiple execution attempts.

## Key Results
- On DTR‑Bench: 37.5% accuracy, ranking first in analysis depth, feasibility, and aesthetics.
- On RealHitBench (with DeepSeek‑V3): exact match scores – 58.22% (fact checking), 55.51% (numerical reasoning), 56.57% (structure comprehension), 70.90% (data analysis, LLM‑EVAL), 52.69% (chart generation, PASS@1); execution correctness 100%.
- Efficiency: average 4.78 LLM calls per query vs. 8.8 for the Code Loop baseline.

## Why This Works (Mechanism)
### Mechanism 1: Hierarchical Meta Graph
- **Claim:** A hierarchical meta graph explicitly models bidirectional header semantics and latent structural dependencies in unstructured tables, enabling correct navigation across overlapping row/column spans.
- **Mechanism:** The framework extracts explicit headers and implicit metadata (units, aggregations), then constructs an overlapping tree‑like graph `G_T = (V_T, E_T)` where nodes represent header elements and edges encode containment/hierarchy. This graph linearizes table semantics into relational triples for LLM consumption, resolving ambiguous cell contexts via resolved header scopes.
- **Core assumption:** The true semantic structure of an unstructured table is latent but can be inferred through interaction and graph‑based modeling.
- **Evidence anchors:** Abstract states “constructs a hierarchical meta graph to capture bidirectional semantics, mapping natural language queries into an operation‑level search space.” Section 3.1 explains bidirectional headers form an overlapping tree‑like structure. Neighbors like HiMAC use hierarchical representations but for different domains.
- **Break condition:** If header hierarchies are excessively ambiguous or deeply nested beyond typical spreadsheet conventions, graph construction fails to isolate unique data cell contexts, leading to erroneous operation scoping.

### Mechanism 2: Expectation‑Aware Selection Policy
- **Claim:** An expectation‑aware selection policy (p‑UCB style) efficiently navigates the massive operation path space by balancing exploitation of historically successful paths with exploration of structurally plausible but under‑tried alternatives.
- **Mechanism:** For each candidate path `π`, the score `E(π) = ˆR(π) + α·P(π) / √(log ΣN(π')/(1+N(π)))` combines empirical reward `ˆR(π)` (from executed outcomes) with a structural prior `P(π)` and an exploration bonus inversely proportional to execution count `N(π)`. This avoids exhaustive simulation while adapting to table‑specific ambiguities.
- **Core assumption:** Rewards are path‑level and non‑decomposable; early operation errors propagate, so holistic path evaluation is necessary.
- **Evidence anchors:** Abstract mentions “expectation‑aware selection policy that prioritizes high‑utility execution paths.” Section 3.3 gives the UCB equation and iterative selection. Conceptually aligned with HiMAC’s hierarchical macro‑micro learning and Jenius Agent’s experience‑driven accuracy optimization.
- **Break condition:** If the search space is too vast relative to the execution budget (e.g., >1000 valid paths for a simple query), exploration may not sample enough paths to identify a high‑reward strategy before budget exhaustion, causing premature convergence to suboptimal paths.

### Mechanism 3: Siamese Structured Memory
- **Claim:** A siamese structured memory—with parameterized execution feedback (success/time/format) and abstracted experience (semantic patterns)—enables continual refinement of planning policies across queries and tables, mitigating error propagation.
- **Mechanism:** After execution, concrete signals `f(π) = (fexec, ftime, ftype)` update path‑level statistics (`ˆR(π)`). Concurrently, a text‑based channel distills strategic observations (e.g., “AGG before validation causes failure”) that inform broader path modifications (insert/remove operations). The two streams operate in parallel: parameterized feedback refines the current query’s path, while abstraction generalizes to future instances.
- **Core assumption:** Execution outcomes contain transferable strategic knowledge beyond the immediate table instance.
- **Evidence anchors:** Abstract notes “siamese structured memory, i.e., parameterized updates and abstracted texts, enabling continual refinement.” Section 3.4 details the two feedback streams. Analogous to “Learning on the Job” and S1‑NexusAgent, but the exact split is novel.
- **Break condition:** If abstracted experiences overfit to domain‑specific quirks of early benchmark tables (e.g., specific Excel formatting patterns in RealHitBench), they may misguide planning on tables with different structural conventions, causing negative transfer.

## Foundational Learning
- **Hierarchical Data Representation & Graph Modeling:** Unstructured tables have merged cells and bidirectional headers; flat serialization loses structural relationships. The meta‑graph is the core representation enabling coherent operation scoping.  
  *Quick check:* How would you represent a table with a merged header spanning two columns and two sub‑rows in a graph without losing the “belongs‑to” relationships for each data cell?
- **Multi‑Armed Bandit Exploration‑Exploitation:** The operation path space is combinatorially large; p‑UCB provides a theoretically bounded way to allocate limited execution trials across candidate strategies.  
  *Quick check:* If you observed a path with 2 executions (one success, one failure) and a novel path with 0 executions, how does the UCB bonus affect their relative selection probability?
- **Experience Replay & Abstractive Memory:** Raw execution traces are instance‑specific; extracting strategic rules (e.g., “clean before aggregate”) allows knowledge transfer across tables and queries, preventing repeated errors.  
  *Quick check:* Given two failed executions: one due to a missing column, another due to a type mismatch, how might you abstract a rule that applies to both?

## Architecture Onboarding
- **Component map:** Tabular Comprehension → Operation Bank & Map → Path Planner ↔ Execution Engine ↔ Siamese Memory → Closed‑Loop Refinement (replan on failure, aggregate final answers).  
- **Critical path:** Query → Build meta‑graph & candidate operations → Generate initial candidate paths → Iterative [Select via p‑UCB → Execute with [THINK]/[CODE] → Reflect & update (parameterized & abstracted)] → Final answer via majority vote.  
- **Design tradeoffs:** Decoupling planning and execution isolates semantic reasoning from code bugs but adds coordination overhead; path‑level rewards avoid credit assignment but require full execution to judge; siamese memory balances specificity and generalization but risks conflicting updates if abstractions are noisy.  
- **Failure signatures:** (1) Meta‑graph construction fails → misaligned cell contexts → systematic operation errors; (2) Path selection stagnates (entropy too low/high) → adjust exploration term α; (3) Memory corruption (abstract rules contradict statistics) → check consistency during reflection.  
- **First 3 experiments:**  
  1. **Ablation (Table 3):** Incrementally add components (Meta Info → QDO → Expectation → Abstraction) to quantify marginal gains (+0.4‑1.4% accuracy each).  
  2. **Prompting Strategy (Table 4):** Compare `[THINK]+[CODE]` vs. direct code vs. multi‑stage reflection; separated reasoning reduces errors (28.4% vs 42.3%) and calls (4.78 vs 5.8).  
  3. **LLM Call Budget (Figure 3):** Vary max calls; DTR plateaus ~6 calls while Code Loop degrades beyond 8.8 calls, showing DTR’s selection avoids over‑exploration.

## Open Questions the Paper Calls Out
- **OQ1:** Can DTR automatically expand or discover new operations beyond the predefined seed bank to handle unseen analytical tasks? (The paper uses a fixed set of operations, limiting adaptation to novel reasoning patterns.)
- **OQ2:** Does reliance on path‑level, undecomposable rewards hinder efficient learning in long‑horizon tabular reasoning? (No credit assignment to intermediate steps may cause wasted exploration.)
- **OQ3:** How does DTR’s hierarchical meta graph construction scale with extremely large or highly irregular tables? (Graph may exceed context limits or become noisy.)
- **OQ4:** Is the expectation‑aware path selection policy robust to distribution shifts in table domains or query styles? (The structural prior may overfit to benchmark patterns.)

## Limitations
- Exact operation bank and code generation details for merged/bidirectional headers are unspecified.
- Mechanism for applying abstracted experience to new paths lacks procedural details.
- Generalization to tables with structures unlike DTR‑Bench/RealHitBench remains uncertain.
- Performance depends heavily on LLM quality and prompt engineering.
- Scalability of combinatorial path search to very large tables is untested.

## Confidence
- **Meta‑graph modeling:** Medium (internal evidence strong but break condition shows fragility on deep nesting).
- **Expectation‑aware selection:** Medium‑High (empirical support and bandit theory; budget limits a risk).
- **Siamese structured memory:** Medium (analogous agents exist, but specific dual‑stream architecture lacks independent validation).

## Next Checks
1. **Meta‑graph ablation:** Replace hierarchical meta‑graph with flat serialization on a subset of DTR‑Bench containing bidirectional headers; a major accuracy drop would confirm its necessity.
2. **Scalability stress test:** Generate synthetic tables with increasing header hierarchy depth and measure whether p‑UCB maintains performance as the operation space grows beyond realistic execution budgets.
3. **Cross‑distribution transfer:** Train the memory using only DTR‑Bench, then evaluate on a new benchmark with different structural conventions (e.g., financial reports); assess performance degradation and identify negative transfer from abstracted rules.
