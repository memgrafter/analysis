# Governed Memory: A Production Architecture for Multi-Agent Workflows
## Quick Facts
- arXiv ID: 2603.17787
- Source URL: https://arxiv.org/abs/2603.17787
- Reference count: 40
- Primary result: Production system achieving 99.6% fact recall, 92% governance routing precision, 50% token reduction via progressive delivery, zero cross-entity leakage across 500 adversarial queries, 100% adversarial governance compliance, and 74.8% LoCoMo accuracy.

## Executive Summary
Enterprise AI agents acting on shared entities suffer from memory silos, governance fragmentation, and unstructured data unusable by downstream systems. Governed Memory introduces a shared infrastructure layer that unifies four mechanisms: a dual memory model (atomic facts + schema-enforced properties), tiered governance routing with progressive context delivery, reflection-bounded retrieval with entity-scoped isolation, and a closed-loop schema lifecycle. Validated in production with 250 entities across five content types, the system achieves 99.6% fact recall with complementary coverage, 92% governance routing precision, 50% token reduction, zero cross-entity leakage, and 74.8% overall LoCoMo accuracy. These results demonstrate that rigorous memory governance can coexist with high retrieval quality and efficiency.

The architecture ensures autonomous agents operate on a unified, governed memory store, eliminating inconsistencies and enabling downstream automation such as CRM synchronization, compliance checks, and analytics. By combining open-set recall with structured property extraction, progressive governance context injection, and strict entity isolation, Governed Memory provides a production-ready solution for scalable multi-agent workflows.

## Method Summary
The Governed Memory system comprises four integrated layers. The Dual Memory Store ingests content via a single-pass LLM extraction that produces both open-set atomic facts and schema-enforced typed properties, ensuring complementary coverage. Governance Routing selects relevant compliance variables using a tiered approach (fast embedding+keyword vs. full LLM analysis) and employs progressive delivery to avoid token redundancy across agent sessions. Governed Retrieval performs entity-scoped vector searches (CRM key pre-filter) and optionally runs a reflection loop (≤2 rounds) to improve completeness while guaranteeing no cross-entity leakage. The Schema Lifecycle manages property definitions through AI-assisted authoring, rubric-based evaluation, and automated refinement. These layers expose a shared MCP/SDK interface, partitioned by orgId and CRM key, allowing agents to query governed memories efficiently and reliably.

## Key Results
- 99.6% fact recall with complementary coverage (38% open-set only, 12% schema only); 92% governance routing precision; 50% token reduction via progressive delivery.
- Zero cross-entity leakage across 500 adversarial queries and 100% adversarial governance compliance.
- Output quality saturates at ~7 governed memories per entity; LoCoMo overall accuracy reaches 74.8%.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** The dual memory model (atomic facts + schema-enforced properties) prevents information loss and provides complementary coverage for both unstructured insights and structured downstream queryability.
- **Mechanism:** A single LLM extraction pass co-produces two output types: (1) open-set atomic facts (self-contained, coreference-resolved) and (2) typed property values governed by organizational schemas. This ensures the same source content is processed once for both modalities, with schema properties selected via embedding similarity and validated against type definitions.
- **Core assumption:** Agents require both free-form recall (for context) and structured signals (for CRM sync, filtering, analytics). Storing both from the same extraction pass avoids modality-induced loss.
- **Evidence anchors:**
  - [abstract] "dual memory model combining open-set atomic facts with schema-enforced typed properties"
  - [section 4] "The 38% captured exclusively by open-set memory... would be permanently lost in a schema-only system. The 12% captured exclusively by schema enforcement would lack type enforcement in an open-set-only system."
  - [corpus] Related papers (e.g., SimpleMem, Mem0) focus on memory primitives; none combine dual modalities with governance (Section 2.4). *Assumption:* This complementary coverage pattern generalizes beyond the studied content types.
- **Break condition:** If schema definitions are too restrictive or poorly-authored, the schema-enforced branch may under-extract, shifting balance toward open-set-only coverage and losing structural actionability. Quality gates (Section 4.2) and schema refinement (Section 7) are intended mitigations.

### Mechanism 2
- **Claim:** Tiered governance routing with progressive context delivery ensures organizational policies reach relevant agent tasks while reducing token waste in autonomous multi-step executions.
- **Mechanism:** Governance context (variables) is selected via two paths: a fast, embedding+keyword-based path (~850ms) and a full LLM-analysis path (2–5s). A session layer tracks delivered variables/sections, injecting only deltas on subsequent steps within a session, preventing re-injection of identical context.
- **Core assumption:** Agents operating in autonomous loops repeatedly invoke governance; re-injecting identical context consumes tokens without improving output and can degrade attention [4].
- **Evidence anchors:**
  - [abstract] "tiered governance routing with progressive context delivery" and "50% token reduction via progressive delivery"
  - [section 5] "Progressive delivery addresses this by maintaining a session state record... only new or newly relevant content is resolved and injected."
  - [section F] Table showing 50.3% token savings across a 5-step mixed-domain workflow.
  - [corpus] [4] (Liu et al.) demonstrates model under-use of long-context middles, motivating delta injection. *Assumption:* The specific 50% reduction figure depends on workflow recurrence patterns and session TTL (24h).
- **Break condition:** Progressive delivery assumes previously delivered context remains relevant. If session context expires or task scope shifts radically, excluding delivered items could omit still-relevant guidelines. The 24-hour TTL is a heuristic limit.

### Mechanism 3
- **Claim:** Reflection-bounded retrieval with entity-scoped isolation enables thorough evidence gathering for complex queries without cross-entity data leakage.
- **Mechanism:** Retrieval starts with a single vector search scoped to an entity (via CRM key filter). An optional bounded reflection loop (default ≤2 rounds) uses an LLM to judge evidence completeness and generate targeted follow-up queries. Entity scoping is enforced as a pre-search filter at the storage layer.
- **Core assumption:** Complex queries often require multiple retrieval passes, but unbounded loops are costly and error-prone. Entity scoping via deterministic CRM keys is more reliable than relying on embedding separation for isolation.
- **Evidence anchors:**
  - [abstract] "reflection-bounded retrieval with entity-scoped isolation" and "zero cross-entity leakage across 500 adversarial queries"
  - [section 6] "Entity isolation is enforced by the CRM key pre-filtering mechanism, not embedding distinctiveness."
  - [section 8.7] "Zero true cross-entity leakage" across 3,800 results; 2.74% flag rate all false positives from shared name tokens.
  - [section 8.6] +25.7pp completeness gain with 2 rounds on hard multi-hop queries.
  - [corpus] Self-RAG [3] and iterative retrieval works exist but lack entity-scoping guarantees. *Assumption:* The completeness gains depend on query generation quality; API-managed reflection showed modest gains vs. manual multi-hop, indicating query strategy is the primary lever.
- **Break condition:** If the CRM key resolver fails to map a query to the correct entity, isolation breaks. Also, if relevant facts across an entity's history are too scattered even with 2 rounds, completeness will plateau below 100%.

## Foundational Learning
- **Concept: Multi-Agent Workflow Memory Silos**
  - Why needed here: The paper's core problem statement assumes dozens of autonomous agents act on shared entities (customers, deals) without a common memory layer. Understanding this distributed-agent scope is prerequisite to valuing a shared infrastructure.
  - Quick check question: "Why would a sales enrichment agent's discovery not automatically inform an outbound agent's next action in a typical stack?"
- **Concept: RAG as a Retrieval Primitive vs. Infrastructure Layer**
  - Why needed here: The paper positions Governed Memory as the layer RAG leaves vacant (governance, schema, session awareness). Distinguishing *retrieval capability* from *memory governance* is key to understanding the contribution.
  - Quick check question: "What three governance concerns does a standard RAG system NOT address according to Section 1.2?"
- **Concept: Schema Enforcement for Downstream Actionability**
  - Why needed here: A central thesis is that unstructured memories are a "downstream dead end." Understanding why typed, validated properties are necessary for CRM sync, filtering, and conditional logic explains the dual model's purpose.
  - Quick check question: "Why can't a free-text memory about 'deal value: $450k' drive a 'deal_size > $100k' workflow filter as reliably as a schema-enforced number property?"

## Architecture Onboarding
- **Component map:** Dual Memory Store → Governance Routing → Governed Retrieval; Schema Lifecycle ↔ Dual Memory Store (schema definitions and refinements). All layers expose a shared MCP/SDK interface partitioned by orgId and CRM key.
- **Critical path:** Data flow for a new agent task: (a) Agent submits query + session ID → (b) Governance router (fast/full) returns critical + supplementary context (using session state to exclude delivered items) → (c) Retrieval layer performs entity-scoped vector search, optionally runs reflection loop → (d) Results merged and returned to agent. Separately, ingested content → dual extraction pipeline → writes to unified store.
- **Design tradeoffs:** 
  - *Dual memory vs. single-modality:* Accepts overlap/duplication to ensure no information is lost; schema layer requires more authoring/maintenance overhead.
  - *Fast vs. full routing:* Speed (850ms vs. 2–5s) vs. precision; auto-mode selects based on library characteristics.
  - *Reflection rounds:* Cost/latency vs. completeness; 2 rounds shown as practical ceiling for most gains.
- **Failure signatures:** 
  - High defect rate in retrieved memories → quality gates (Section 4.2) failing or outdated schemas.
  - Low governance routing precision → poorly-authored variables (Section 8.5) or embedding misalignment.
  - Cross-entity leakage → CRM key filter misconfiguration or missing at query time.
  - Token savings < expected → session state not maintained across agent steps or TTL too short.
- **First 3 experiments:**
  1. **Extraction Quality (E1/E9):** Run the dual extraction pipeline on 50 samples per content type (calls, docs, emails, transcripts, chats). Verify >99% fact recall and that quality gates reduce output defect rate by ~25% relative.
  2. **Governance Routing Precision (E3):** With a known set of 25 governance variables, run 20 diverse tasks through the router. Measure precision (target 92%) and recall (target 88%). Test progressive delivery by simulating a 3-step session and verifying delta tokens injected on step 2+.
  3. **Entity Isolation (E11):** Prepare 100 entities with high name/role overlap. Execute 500 adversarial queries targeting cross-entity leakage. Verify zero true leakage in results, all flags being false positives from shared tokens.

## Open Questions the Paper Calls Out
- **Open Question 1**
  - Question: Does the governed memory architecture generalize across organizations with varied content domains, schema maturity, and multi-agent write concurrency?
  - Basis in paper: [explicit] "cross-organization validation measuring whether patterns hold across varying content and schema maturity, including multi-agent write compatibility and contradiction detection"
  - Why unresolved: The current evaluation uses a single organization with synthetic data; it is unknown if results hold for other enterprises with different data characteristics, compliance regimes, or agent densities.
  - What evidence would resolve it: A multi-organization study (5–10 enterprises) executing the same controlled experiments (fact recall, routing precision, entity isolation, schema accuracy) on both synthetic and real workloads, comparing performance across schema maturity levels and multi-agent write loads.
- **Open Question 2**
  - Question: Can automated schema expansion from unextracted content patterns effectively propose new typed properties and improve downstream data usability?
  - Basis in paper: [explicit] "automated schema expansion proposing new properties from unextracted content patterns"
  - Why unresolved: The current schema lifecycle requires manual property definition; latent needs may be missed, limiting the actionable structured data available to downstream systems.
  - What evidence would resolve it: Deploy a prototype that analyzes unused memory content to suggest new properties, then measure property adoption by human operators, recall increase of relevant facts, and downstream impact (e.g., CRM field completeness) against a baseline of no expansion.
- **Open Question 3**
  - Question: Does hybrid retrieval (semantic vector search combined with keyword-based lanes using reciprocal rank fusion) improve accuracy and robustness for governed memory queries?
  - Basis in paper: [explicit] "hybrid retrieval combining semantic search with keyword lanes and reciprocal rank fusion"
  - Why unresolved: The existing retrieval relies solely on vector similarity; queries that target exact schema properties or rare terms may suffer from limited precision or recall.
  - What evidence would resolve it: Conduct an A/B test on a benchmark dataset comparing pure vector search against hybrid fusion variants, evaluating recall@k, precision@k, and end-to-end task success rates for both open-set and schema-enforced queries.
- **Open Question 4**
  - Question: Can transformer-based NER augment regex redaction to detect non-standard PII patterns without increasing false positives?
  - Basis in paper: [explicit] "ML-augmented redaction supplementing regex patterns with transformer-based NER for non-standard PII"
  - Why unresolved: The current redaction pipeline uses regex patterns that may miss obfuscated or context-dependent PII, leaving residual privacy risks; ML methods could fill gaps but might over-redact.
  - What evidence would resolve it: Evaluate regex-only vs. regex+ML redaction on a corpus containing diverse PII obfuscations, measuring detection coverage (against human-labeled PII) and false positive rates, and assessing any impact on extraction quality downstream.

## Limitations
- LLM model details and prompts not disclosed, hindering exact replication.
- CRM pre-filter integration with vector search (e.g., pre- vs. post-filter, index parameters) underspecified, affecting isolation guarantees.
- Evaluation limited to a single synthetic dataset (N=250, five content types), limiting external validity.
