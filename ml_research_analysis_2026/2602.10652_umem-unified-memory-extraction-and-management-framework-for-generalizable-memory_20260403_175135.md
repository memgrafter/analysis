# UMEM: Unified Memory Extraction and Management Framework for Generalizable Memory

## Quick Facts
- arXiv ID: 2602.10652
- Source URL: https://arxiv.org/abs/2602.10652
- Reference count: 40
- Primary result: UMEM jointly optimizes memory extraction and management, achieving up to 10.67% improvement in multi-turn interactive tasks (ALFWorld) with GPT-5.1 and maintaining monotonic performance growth during continuous evolution.

## Executive Summary
Existing self-evolving agents suffer from poor memory generalization due to decoupled extraction and management, leading to instance-specific noise accumulation. UMEM addresses this by jointly optimizing a learned Mem-Optimizer for simultaneous memory extraction and management via Group Relative Policy Optimization (GRPO). It introduces Semantic Neighborhood Modeling to cluster related queries and evaluate memory utility at the neighborhood level using a marginal utility reward that combines success gain and efficiency regularization. On five benchmarks, UMEM consistently outperforms competitive baselines (e.g., ReMem, Memp) and demonstrates robust cross-model transfer, with higher success rates accompanied by reduced execution steps.

## Method Summary
UMEM treats the memory bank as evolvable non-parametric parameters, separate from a frozen executor LLM. A trainable Mem-Optimizer (e.g., Llama-1B/4B) takes a query, its execution trajectory, and top-k retrieved memories, then outputs both a memory extraction and a management operation. Training uses GRPO: for each query, the optimizer samples multiple candidate memory actions; each candidate is applied to the memory bank and evaluated over a semantic neighborhood (top-3 similar queries) by re-running the executor. The neighborhood-level marginal utility reward measures success gain (correcting failures) and efficiency regularization (token reduction only if correctness preserved). A format reward ensures valid outputs. The best action is committed to the memory bank, enabling online evolution.

## Key Results
- UMEM achieves up to 10.67% improvement in success rate on ALFWorld (multi-turn) with GPT-5.1.
- Performance grows monotonically during continuous evolution, unlike baselines that degrade.
- Cross-model transfer is robust: training with Qwen3-4B yields gains when evaluated with GPT-5.1 and Gemini.
- Ablations show that removing joint optimization or neighborhood reward degrades performance significantly (e.g., 4.7 point average drop without extraction optimization).

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Joint optimization of memory extraction and management prevents decoupled degradation and noise accumulation.
- **Mechanism:** The Mem-Optimizer is trained end-to-end via GRPO to output both extracted memory content (`value`) and management operations (`operation`), aligning extraction decisions with their long-term management impact. This contrasts with prior works that optimize management while treating extraction as static prompting.
- **Core assumption:** The quality of memory bank evolution is jointly bounded by extraction granularity and management strategy; optimizing one in isolation leaves residual noise that degrades future reuse.
- **Evidence anchors:** [abstract] "UMEM addresses this by jointly optimizing a learned Mem-Optimizer for simultaneous memory extraction and management via GRPO."; [section 3] "The bottleneck of the self-evolving agent lies in the capability of this memory optimizer... we propose the UMEM framework to jointly optimize its extraction and management policies."; Corpus neighbors like "MemSkill" and "Agentic Memory" highlight coupled management, but UMEM uniquely unifies extraction via policy learning.
- **Break condition:** Constraining the Mem-Optimizer to output only extraction templates (fixed management) or only operations (fixed extraction) degrades performance; ablation (Table 2, w/o Extraction Opt. drops 4.7 points avg).

### Mechanism 2
- **Claim:** Semantic Neighborhood Modeling mitigates instance-specific overfitting by evaluating memory utility across related query clusters.
- **Mechanism:** Queries are embedded (e.g., BGE-M3) and clustered into neighborhoods (Top-N similar queries). Candidate memory updates are validated on the entire neighborhood via marginal utility, forcing extraction of principles that generalize beyond the source instance.
- **Core assumption:** Cosine proximity correlates with shared reasoning patterns; similar queries will retrieve overlapping memories and thus benefit from shared memory updates.
- **Evidence anchors:** [abstract] "To mitigate overfitting to specific instances, we introduce Semantic Neighborhood Modeling... evaluates memory utility across clusters of semantically related queries."; [section 4.1] "Our core insight is to treat the local cluster of similar queries as a proxy to approximate cross-task variations."; Corpus: "Generalizable Self-Evolving Memory for Automatic Prompt Optimization" also uses group-based evaluation, but UMEM applies it to memory evolution specifically.
- **Break condition:** Neighborhood construction fails (e.g., N=1 too narrow, N=5 too broad) – both underperform N=3 (Table 2).

### Mechanism 3
- **Claim:** The neighborhood-level marginal utility reward enforces cross-task generalization by balancing success gain and efficiency regularization.
- **Mechanism:** For each candidate memory update, reward Δu(q') = G_succ(q') + R_eff(q') is averaged over neighborhood queries q'. G_succ measures correctness correction; R_eff rewards token reduction only when correctness is preserved. GRPO then optimizes the policy to maximize this group-relative reward.
- **Core assumption:** Generalizable memories should improve both accuracy and efficiency for a distribution of related tasks, not just the immediate instance.
- **Evidence anchors:** [section 4.2] "The marginal utility reward... quantifies the correction of execution failures" and "efficiency regularization... rewards token reduction, but only when correctness is preserved."; [section 5.2] UMEM reduces average steps while increasing success rate (Figure 5); Corpus: "Evo-Memory" uses success-based rewards but lacks explicit efficiency regularization and neighborhood aggregation.
- **Break condition:** Mis-specified reward weighting (e.g., R_eff without G_succ gating) leads to brevity over accuracy; format reward prevents malformed outputs but not semantic errors.

## Foundational Learning
- **Concept:** Group Relative Policy Optimization (GRPO)
  - *Why needed:* UMEM uses GRPO (Shao et al., 2024) to train the Mem-Optimizer without a value critic, using group-relative advantages from sampled rollouts. This is critical for stable optimization in a space where absolute reward scales are unstable due to varying task difficulty.
  - *Quick check:* How does GRPO's group-relative advantage stabilize training compared to standard PPO when the reward signal (marginal utility) has high variance across semantic neighborhoods?
- **Concept:** Semantic Neighborhood Construction via Dense Retrieval
  - *Why needed:* The neighborhood NN(q) approximates the distribution of future queries that will retrieve the same memory. This requires a robust embedding model (BGE-M3) to cluster by reasoning pattern rather than surface form.
  - *Quick check:* Why cosine similarity on L2-normalized embeddings (Appendix C) provides a stable proxy for retrieval overlap, and how does neighborhood size N trade off noise vs. task coverage?
- **Concept:** Memory as Evolvable Non-Parametric Parameters
  - *Why needed:* UMEM treats the memory bank B as the agent's trainable parameters, separate from frozen executor Θ₀. This shifts learning from model weights to external knowledge, enabling lifelong updates without catastrophic forgetting.
  - *Quick check:* How does this paradigm differ from fine-tuning or working memory RL (e.g., MemAgent), and why is it more suitable for open-ended, continual interaction?

## Architecture Onboarding
- **Component map:** Frozen Agent Executor (E) -> Memory Bank (B) <- Mem-Optimizer (π_ϕ) -> Semantic Neighbor Builder (precomputed NN(q))
- **Critical path:** 
  1. Given query q, retrieve B_topk from B.
  2. Executor E generates trajectory τ_q.
  3. Mem-Optimizer samples G candidate memory actions {a_q^{(g)}}.
  4. For each candidate, apply to B → B̃^{(g)}, then evaluate marginal utility over NN(q) by re-running E on neighbors with B̃^{(g)} vs. B.
  5. Compute reward r_g = r_fmt + r_g, update π_ϕ via GRPO.
  6. Apply best action a_q^{(g*)} to update B (online evolution).
- **Design tradeoffs:**
  - Joint optimization vs. computational cost: end-to-end training requires multiple rollouts per query (G=8) but yields monotonic improvement; decoupled methods are cheaper but accumulate noise.
  - Neighborhood size N: Small N risks missing generalizable patterns; large N dilutes reward with dissimilar queries. Paper finds N=3 optimal.
  - Memory granularity: UMEM distills entire trajectories into single memory entries; finer granularity might help but increases noise.
- **Failure signatures:**
  - Performance degradation over time: If π_ϕ extracts instance-specific noise, cumulative success rate drops (observed in ReMem baseline, Figure 3).
  - Overfitting to narrow neighborhoods: When N=1, gains on ALFWorld shrink (Table 2), indicating poor cross-task transfer.
  - Reward hacking: If R_eff dominates, memories may promote brevity over accuracy; format reward r_fmt prevents malformed outputs but not semantic errors.
- **First 3 experiments:**
  1. **Ablation: Joint Optimization** (Table 2) – Disable gradient for extraction or management tokens. Expected: Removing extraction optimization causes largest drop (~4.7 avg points), confirming extraction as primary bottleneck.
  2. **Ablation: Neighborhood Size Sensitivity** (Table 2) – Vary N∈{1,3,5}. Expected: N=3 best; N=1 fails to generalize; N=5 introduces noise.
  3. **Cross-Model Transfer** (Table 1, Figure 5) – Train Mem-Optimizer with Qwen3-4B, evaluate with GPT-5.1/Gemini. Expected: UMEM shows consistent gains across executors, proving memory generalizability is model-agnostic.

## Limitations
- Major uncertainties block exact reproduction: (1) Mem-Optimizer prompt template and retrieval integration are unspecified; (2) Executor’s generation parameters and retrieval logic lack detail; (3) GRPO hyperparameters (optimization steps, KL schedule) are inherant from `verl` but not documented.
- Baselines may be limited to contemporaneous methods; newer memory architectures (e.g., HMAS, Retro*) are not evaluated.
- Scalability to larger memory banks or longer horizons is untested.

## Confidence
- **Joint optimization necessity:** High (supported by ablation drops >4 pts).
- **Neighborhood modeling benefit:** Medium (optimal N=3 shown, but embedding model choice’s impact unclear).
- **Cross-model transfer robustness:** Medium (evaluated on 3 models but limited to specific executor sizes).
- **Monotonic growth claim:** Medium (observed in experiments, but long-term stability beyond presented epochs unknown).

## Next Checks
1. **Neighborhood similarity threshold sweep:** Vary cosine similarity cutoffs (0.5–0.9) for neighbor inclusion to test robustness of marginal utility reward against noisy clusters.
2. **Executor gradient leakage test:** Run control where executor is *unfrozen* during training to measure if observed gains stem solely from memory vs. combined model-memory adaptation.
3. **Memory bank saturation study:** Track memory entry growth and performance over 10× more evolution steps to identify potential degradation from memory bloat or overwriting of high-value entries.
