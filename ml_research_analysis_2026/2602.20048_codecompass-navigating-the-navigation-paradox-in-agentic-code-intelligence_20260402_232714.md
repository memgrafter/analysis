# CodeCompass: Navigating the Navigation Paradox in Agentic Code Intelligence

## Quick Facts
- arXiv ID: 2602.20048
- Source URL: https://arxiv.org/abs/2602.20048
- Reference count: 0
- Primary result: Graph navigation achieves 99.4% Architectural Coverage Score on hidden-dependency tasks, a 23.2 percentage-point improvement over vanilla agents.

## Executive Summary
The Navigation Paradox identifies that agentic coding failures stem not from context limits but from inability to navigate architecturally hidden dependencies. CodeCompass addresses this by providing graph-based structural navigation via an MCP server, exposing AST-derived dependency graphs (IMPORTS, INHERITS, INSTANTIATES). On hidden-dependency tasks (G3), it achieves 99.4% Architectural Coverage Score (ACS), a 23.2 percentage-point improvement over vanilla agents (76.2%) and BM25 retrieval (78.2%). However, 58% of trials with graph access ignored the tool, revealing the primary bottleneck is agent tool-adoption behavior rather than tool capability. Improved prompt engineering raised adoption on G3 tasks to 100%, increasing ACS from 96.6% to 99.4%.

## Method Summary
The study evaluates CodeCompass on the FastAPI RealWorld example app (~40 Python files) with 30 benchmark tasks (10 G1 semantic, 10 G2 structural, 10 G3 hidden). Three conditions are compared using Claude Code: A) Vanilla (no augmentation), B) BM25 retrieval results prepended, C) CodeCompass MCP server exposing `get_architectural_context` returning 1-hop neighborhood via IMPORTS/INHERITS/INSTANTIATES. Primary metric is Architectural Coverage Score (ACS), fraction of required files accessed. Graph built via Python AST, stored in Neo4j. For each condition × task × 3 runs, transcripts are parsed to compute ACS and tool usage.

## Key Results
- On G3 hidden-dependency tasks, CodeCompass (Condition C) achieves 99.4% ACS, a 23.2 percentage-point improvement over vanilla (76.2%) and BM25 (78.2%).
- 58% of Condition C trials made zero MCP calls; when used, ACS was 99.5%, when ignored, 80.2%.
- Improved prompt engineering (checklist-at-END) raised adoption on G3 tasks to 100% and increased ACS from 96.6% to 99.4%.

## Why This Works (Mechanism)

### Mechanism 1
Graph navigation surfaces architecturally hidden dependencies that lexical retrieval cannot, because structural connections (IMPORTS, INHERITS, INSTANTIATES) are orthogonal to semantic similarity. A static AST analysis builds a dependency graph. When an agent queries a file, the tool returns its 1-hop structural neighborhood. Files like `app/api/dependencies/database.py` (hidden dependency for "logger parameter to BaseRepository") are returned because they import or instantiate the queried file, despite zero lexical overlap with the task description. The core assumption is that the agent will invoke the graph tool and act on its results. Evidence: On G3 tasks, graph achieves 99.4% ACS vs 76–78% for baseline methods. Break condition: If the agent ignores the tool (58% failure rate), the mechanism fails; also fails on semantic (G1) tasks where retrieval is sufficient.

### Mechanism 2
The primary bottleneck is not graph capability but consistent agent tool-adoption behavior; models skip the graph tool unless prompted in a way that overcomes their default heuristic (glob+read). Agents evaluate tool use via a cost-benefit heuristic. On G1/G2 tasks, glob+read already achieves ~80% ACS, so the overhead of calling the graph seems unjustified. On G3 tasks, the same heuristic fails silently, and the agent never self-corrects. Only prompt engineering that positions instructions prominently (checklist-at-END to mitigate Lost-in-the-Middle) forces adoption. Evidence: 58% of Condition C trials made zero MCP calls; 0% adoption on G2 structural tasks, 100% on G3 after improved prompting. Break condition: If prompt engineering cannot consistently mandate the first-tool-call, adoption will remain inconsistent, especially on G2 tasks.

### Mechanism 3
The Navigation Paradox is that expanded context windows shift failure from retrieval capacity to navigational salience; having all files in context does not ensure the model attends to architecturally critical, semantically distant files. With large contexts, the failure mode changes. The model's attention (and tool-use strategy) is guided by semantic heuristics derived from the task description. Architecturally connected files with low lexical overlap are systematically excluded from the model's effective search space, regardless of context window size. Evidence: Claude Code with full codebase achieves 80% ACS—not because the relevant file exceeds the context window, but because it never enters the model’s navigational attention. BM25 provides no benefit on G3 tasks (78.2% vs 76.2% Vanilla), showing lexical retrieval is ineffective for hidden dependencies even with full context. Break condition: If the task's required files all have high lexical overlap with the prompt (G1), the paradox does not manifest, and retrieval/glob suffices.

## Foundational Learning
- **Concept: Dependency Taxonomies (G1/G2/G3)**  
  Why needed: To design experiments and interpret results, one must distinguish between tasks solvable by semantic search (G1), structural import chains (G2), and hidden architectural links (G3). The taxonomy predicts when graph navigation will help.  
  Quick check: For a task "Fix the import error in `models/user.py`", is it G1, G2, or G3? (Answer: Likely G2, solution requires following imports, not just keyword search.)

- **Concept: MCP (Model Context Protocol) Server**  
  Why needed: CodeCompass is implemented as an MCP server. Understanding MCP is key to seeing how new tools are integrated into agent environments (like Claude Code) as standardized, callable functions.  
  Quick check: What does an MCP server *do* vs. a pre-computed context? (Answer: It exposes live, queryable tools during agent execution, not static context injection.)

- **Concept: Architectural Coverage Score (ACS)**  
  Why needed: The primary metric. It measures navigational completeness: fraction of gold-standard required files actually accessed (read/edited). It does **not** measure correctness of edits.  
  Quick check: If an agent reads all required files but introduces a bug, what is its ACS? (Answer: 100%. ACS only measures discovery, not edit quality.)

## Architecture Onboarding
- **Component map:**  
  AST Parser (Python ast) → Graph DB (Neo4j) → MCP Server (FastMCP) → Agent (Claude Code) → Harness (experiment orchestrator)

- **Critical path:** Task prompt → Agent decides to call `get_architectural_context(primary_file)` → MCP server queries Neo4j → Returns neighbor file paths → Agent reads neighbors → Makes edits. *Breakdown:* If agent never calls the tool (58% failure rate), the path reverts to vanilla glob+read.

- **Design tradeoffs:**  
  - Graph completeness vs. automation: Fully automated AST graph is reproducible but may include irrelevant edges (e.g., test imports). Human curation could improve precision but adds maintenance cost.  
  - Tool adoption vs. overhead: Forcing an initial graph call adds one step but guarantees discovery on hidden-dependency tasks. Not forcing it preserves speed on simple tasks but fails on complex ones.  
  - Single-hop vs. multi-hop: This system uses 1-hop for simplicity and speed. Multi-hop could find deeper dependencies but increases noise and token usage.

- **Failure signatures:**  
  - Zero MCP calls in Condition C: Indicates prompt/instruction failure or rational heuristic override.  
  - G2 regression: Condition C underperforms BM25/Vanilla on structural tasks because tool is ignored + prompt overhead.  
  - High FCTC but high ACS (Condition C on G3): Slow start (2.23 steps to first required file) but eventual high coverage, showing the tool works when used but is called later than optimal.  
  - Low ACS on G3 in A/B: Files like `database.py` never accessed—classic Veto Protocol event.

- **First 3 experiments:**  
  1. Baseline replication: Run Condition A (Vanilla) on all 30 tasks. Expect ~82% overall ACS, ~76% on G3. Confirm the Navigation Paradox: failure despite full context.  
  2. Tool efficacy test: Run Condition C (Graph) on G3 tasks only, with the original prompt. Expect ~85-96% adoption? Measure ACS when tool used vs. ignored—should see ~99.5% vs ~80%.  
  3. Adoption engineering: Run Condition C on G3 tasks with improved "checklist-at-END" prompt. Expect 100% adoption and ACS increase from 96.6% to 99.4%. Isolate the prompt effect from tool capability.

## Open Questions the Paper Calls Out

### Open Question 1
**Question:** How can agent systems be architecturally designed to enforce consistent invocation of graph-based navigation tools, rather than relying on prompt-based encouragement?  
**Basis in paper:** Section 6.3 identifies the core bottleneck as "consistent agent adoption" and suggests "structural workflow enforcement (via tool_choice or multi-agent pipelines)" as a necessary intervention, noting that "even strongly-worded prompts are insufficient."  
**Why unresolved:** The study only tested prompt engineering variations (e.g., checklist-at-END) which improved adoption on G3 tasks but failed entirely on G2 tasks. No experiments enforced tool usage via system-level constraints.  
**What evidence would resolve it:** A follow-up study comparing adoption rates and ACS across conditions where the first tool call is mandated (e.g., via API-level `tool_choice` constraints) versus optional, across all task groups (G1–G3). Metrics would include adoption rate, ACS, FCTC, and task completion time.

### Open Question 2
**Question:** What minimal human validation effort is required to produce dependency graphs that reliably capture architecturally meaningful dependencies, and can this process be partially automated?  
**Basis in paper:** Section 6.4 states that "graph quality requires domain expert input" and that "an SME familiar with the codebase’s architectural intent must review and approve the edges." The automated AST graph is treated as a "reproducible lower bound."  
**Why unresolved:** The paper provides no empirical comparison between automated and human-validated graphs. It assumes validation is necessary but does not quantify the performance gap or explore hybrid (semi-automated) curation methods.  
**What evidence would resolve it:** An ablation study on a subset of tasks comparing ACS using: (1) fully automated AST graphs, (2) graphs augmented with SME-validated edges, and (3) graphs filtered by automated heuristics (e.g., edge centrality, ownership metadata). Success would be measured by reduction in ACS variance and closure of the ~3.5% gap on G3 tasks.

### Open Question 3
**Question:** Why do agents categorically reject graph navigation on structurally-dependent (G2) tasks despite the tool’s design purpose, and what intervention strategies (beyond difficulty-sensing) could activate its use?  
**Basis in paper:** Section 5.3 reports 0% MCP adoption on G2 tasks (0/30 trials), and Section 6.5 hypothesizes that agents apply a "rational heuristic: on tasks where Glob+Read achieves ~80% ACS, the overhead of calling the graph tool is not justified."  
**Why unresolved:** The paper does not test whether G2 tasks genuinely require the graph tool or if the agent’s heuristic is correct. No interventions (e.g., adaptive triggers based on search recall, explicit G2 task labeling) were evaluated for this group.  
**What evidence would resolve it:** Analyze G2 tool-ignored trials to determine if the missed files were truly unreachable via Glob/Grep (i.e., architecturally hidden) or merely suboptimal. Then, run a targeted experiment with G2 tasks where agents are either (a) given a "difficulty signal" (e.g., after first Glob returns zero required files) to invoke the graph, or (b) instructed that G2 tasks mandate graph use, measuring ACS change.

### Open Question 4
**Question:** Does the Navigation Paradox and the efficacy of graph navigation generalize to codebases with different architectural patterns (e.g., microservices, event-driven) or programming languages (e.g., TypeScript, Java)?  
**Basis in paper:** Section 6.5 lists "Single codebase" as a key limitation: "All 30 tasks are drawn from one Python web application. Generalizability to other codebases, languages, or architectural patterns is untested."  
**Why unresolved:** All experiments used the FastAPI RealWorld app (Python, repository pattern with DI). The AST extraction logic (IMPORTS, INHERITS, INSTANTIATES) may not capture equivalent architectural dependencies in other paradigms (e.g., message-passing in microservices, component hierarchies in React).  
**What evidence would resolve it:** Replicate the benchmark construction (G1/G2/G3 tasks) on 2–3 additional codebases with distinct architectures/languages. Measure whether (a) the G3 hidden-dependency tasks remain unsolvable by BM25, (b) the graph tool provides similar ACS improvements, and (c) the same tool-adoption patterns (58% ignore rate) persist.

## Limitations
- **Artifact gaps:** Exact system prompts (especially improved G3 prompt), precise FastAPI RealWorld commit, and exact Claude model identifier are unspecified, hindering exact replication.
- **Generalizability:** Evidence is based on a single ~40-file Python codebase; the graph navigation mechanism’s effectiveness on larger/multi-language repos is unknown.
- **Metric scope:** Architectural Coverage Score (ACS) measures file access only, not edit correctness; high ACS ≠ task success.

## Confidence
- **Mechanism 1 (Graph navigation surfaces hidden links):** Medium. Strong internal evidence on G3 tasks, but assumes agents will use the tool and that structural edges generalize beyond this codebase.
- **Mechanism 2 (Tool adoption is primary bottleneck):** High. Directly supported by 58% zero-call rate in Condition C and 100% adoption after prompt engineering on G3.
- **Mechanism 3 (Navigation Paradox: salience > capacity):** Medium. Well-supported in this setup, but may not manifest if all relevant files have high lexical overlap (G1 tasks).

## Next Checks

2. **Cross-codebase test:** Apply CodeCompass to a second, larger Python repo (e.g., Django or Kombu) with architecturally hidden dependencies; measure whether 1-hop graph navigation still yields >20 percentage-point ACS gain over retrieval on G3-like tasks.
3. **Prompt ablation:** Isolate the effect of the "checklist-at-END" instruction by running Condition C on G3 tasks with (a) original prompt, (b) checklist-at-BEGINNING, (c) checklist-at-END; compare adoption rates and ACS to confirm the optimal positioning.
