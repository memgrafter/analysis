# Executable Archaeology: Reanimating the Logic Theorist from its IPL-V Source

## Quick Facts
- **arXiv ID:** 2603.13514  
- **Source URL:** https://arxiv.org/abs/2603.13514  
- **Reference count:** 26  
- **Primary result:** Reanimated the 1956 Logic Theorist by constructing a new IPL-V interpreter, executing original transcribed source code, and proving 16 of 23 *Principia Mathematica* theorems within a 20,000-cycle limit, matching historically reported performance.

## Executive Summary
This paper presents the first faithful reanimation of the 1956 Logic Theorist (LT)—the pioneering AI program—by building a new IPL-V abstract machine interpreter in Common Lisp and executing original IPL-V source code transcribed from a 1963 RAND report. The system successfully proves 16 of 23 targeted theorems from *Principia Mathematica*, reproducing historically cited performance within a constrained cycle budget. The work demonstrates "executable archaeology" as a methodology for empirically studying historic AI systems through reconstruction, revealing subtle semantic ambiguities in the IPL-V specification and showcasing a hybrid human-LLM debugging process to resolve them.

## Method Summary
The author constructed a complete IPL-V interpreter that emulates the abstract machine (cell table, control/working registers, J-functions) in Common Lisp. Original IPL-V code for LT was meticulously transcribed from a scanned RAND report into a data format (.liplv) using specialized tools. This code was loaded into the interpreter and executed against a set of 23 theorems with a 20,000-cycle limit per theorem. Performance and proof outcomes were compared against historical accounts. Debugging involved initial solo crash resolution followed by collaborative LLM-assisted trace analysis to fix non-crashing heuristic misbehaviors, culminating in verification against an original 1962 J-function reference deck ("Simon’s J’s").

## Key Results
- Proved 16 of 23 attempted *Principia Mathematica* theorems, matching the historically reported success rate within the cycle limit.
- Executed approximately 574,000 IPL machine cycles, generating over 576,000 symbols in seconds on modern hardware—a task likely requiring hours on the original 1950s JOHNNIAC.
- Identified and fixed subtle semantic bugs in the interpreter’s J-function implementations (e.g., J74 list copying) by cross-referencing multiple archival artifacts, including a preserved original punched-card deck.

## Why This Works (Mechanism)

### Mechanism 1: Faithful Emulation of Abstract Machine Semantics
- **Claim:** A faithful reanimation is possible by building a standards-compliant interpreter for a defunct abstract machine and supplying it with correctly transcribed original source code.
- **Mechanism:** The interpreter implements the IPL-V abstract machine specification (cell table, control registers H0–H5, working cells W0–W9, J-functions) in Common Lisp. Original IPL-V code from a 1963 RAND report is transcribed and loaded as data. The interpreter executes this code as if on the original machine, producing historically consistent behavior.
- **Core assumption:** The original system's behavior is fully determined by its code and the IPL-V machine semantics; hardware idiosyncrasies of the 1950s JOHNNIAC are not critical for logical correctness.
- **Evidence anchors:** [abstract] "constructed a new IPL-V interpreter... executing original code transcribed from a 1963 RAND report... successfully proves 16 of 23 attempted theorems... historically consistent." [section IV] "I implemented a complete IPL-V interpreter... implements the complete IPL-V abstract machine as described in the 1964 manual... The LT code... is the original code from that report."
- **Break condition:** If the original code utilized undocumented hardware-specific behaviors or machine-level IPL primitives not described in the manual, the interpreter might fail to replicate certain edge cases.

### Mechanism 2: Hybrid Human-LLM Debugging for Heuristic Misbehaviors
- **Claim:** Debugging non-crashing heuristic misbehaviors in reconstructed vintage AI requires a hybrid approach combining human conceptual oversight with LLM-assisted exhaustive state tracing.
- **Mechanism:** After initial crash debugging (solo), persistent anomalous behavior (e.g., runaway recursion, missed proofs) creates a cognitive bottleneck. An LLM is engaged to meticulously analyze thousands of lines of execution trace, insert diagnostic instrumentation, and track state across machine cycles, while the human maintains the methodological frame and validates hypotheses.
- **Core assumption:** The misbehavior stems from subtle semantic errors in the interpreter's implementation of J-functions (e.g., J74 list copying), not in the original LT code; LLMs can process trace data at scale but require human guidance to avoid propagating interpreter bugs.
- **Evidence anchors:** [section VI.B] "The character of the bugs changed... LT was proving trivial theorems but not simple ones... the cognitive load... exceeded what I could sustain. This is where I turned to large language models." [section VI.D] "Claude isolated the second problem in J74... 'Simon’s J’s'... original 1962 IPL-V J-function card deck... provided the ground truth."
- **Break condition:** If the LLM's training data on dead languages is too sparse, it may consistently misinterpret the interpreter's (possibly buggy) behavior, leading to circular debugging.

### Mechanism 3: Cross-Referencing Archival Artifacts to Resolve Specification Ambiguities
- **Claim:** Ambiguities in historical language specifications can be resolved by cross-referencing multiple archival artifacts (manuals, code listings, original implementation decks) rather than relying on prose descriptions alone.
- **Mechanism:** The IPL-V manual's textual descriptions of J-functions were found to be "vague in subtle ways." The definitive resolution came from comparing the interpreter's Lisp implementation against the original 1962 punched-card code ("Simon’s J’s") preserved at the Computer History Museum. The discrepancy in J74's list-copying logic was identified and fixed.
- **Core assumption:** Original source code artifacts (even if from a slightly later version) represent the ground truth for language semantics, superseding second-hand manual descriptions.
- **Evidence anchors:** [section VI.D] "We had access to 'Simon’s J’s'... original 1962 IPL-V J-function card deck... They differed in exactly the way I had hypothesized, and a one-line patch... made LT run completely correctly." [section III] "Both documents proved to be exceptionally well-written. There were, however, occasional ambiguities—places where the specification assumed familiarity with conventions of 1960s computing."
- **Break condition:** If the original implementation deck is lost, damaged, or corresponds to a different IPL-V variant than the code being run, the cross-reference may be invalid or misleading.

## Foundational Learning
- **Concept: IPL-V Abstract Machine Model (Cells, Registers, J-functions)**  
  Why needed here: The entire interpreter is a direct implementation of this model. Understanding the cell-table structure, H1 as a combined program counter/call stack, and the semantics of J-functions (e.g., J74 for list copying) is essential to build and debug the system.  
  Quick check question: If H1 (the program counter) is implemented as a push-down list, how does a J-function that performs a subroutine call (like J100) manipulate H1 versus a data stack?

- **Concept: Heuristic Search & Proof Strategies in LT (Substitution, Detachment, Forward/Backward Chaining)**  
  Why needed here: To interpret LT's outputs and trace anomalies (e.g., why it proves 2.01 but not 2.14), one must understand its control flow: how it generates subgoals, applies axioms, and decides when a proof is found. This distinguishes correct heuristic behavior from bugs.  
  Quick check question: In the trace for Theorem 2.01, why does LT first apply *1.2 (A v A) → A) and then use sublevel replacement with 2.01? What heuristic goal is it satisfying?

- **Concept: Software Archaeology Methodology (Source Transcription, Emulation vs. Reimplementation)**  
  Why needed here: The paper's core contribution is *faithful reanimation*, not rewriting. This requires meticulous transcription from scanned documents (using tools like Gridlock) and a choice to emulate the abstract machine rather than the specific 1950s hardware (JOHNNIAC). Understanding this methodology is key to evaluating the work's claims.  
  Quick check question: What is the crucial difference between "reimplementing LT's algorithms in Lisp" (a known exercise) and "constructing a faithful emulator of the IPL-V abstract machine to run the original code" (this paper's approach)?

## Architecture Onboarding
- **Component map:** Transcriber (Google Sheets + Gridlock) -> Loader (.liplv generation) -> Interpreter Core (iplv.lisp: cell table, H0–H5, W0–W9, J-dispatch) -> J-function Library (~50 implemented, e.g., J2, J17, J74, J100) -> LT Program (transcribed .liplv files) -> Runner/Controller (effort limits, metrics collection).
- **Critical path:** Source transcription from PDF -> Loader conversion -> Interpreter instantiation -> LT program load -> Execution loop (H1-driven) -> Proof attempt -> Metrics/output.
- **Design tradeoffs:** 
  - Emulated abstract machine vs. vintage hardware: Chose abstract machine for portability and because Stefferud's code is IPL-V standard, not JOHNNIAC-specific. 
  - Lisp implementation: Leverages Lisp's list processing for IPL's linked cells and recursion, but risks semantic drift if GC/immutability affects state. 
  - Partial J-function set: Implemented only functions used by LT (~50 of ~150), increasing risk of missing indirect calls.
- **Failure signatures:** 
  - Crash: Stack underflow/overflow, null cell reference, unimplemented J-function. 
  - Non-termination/infinite recursion: LT stuck in subproblem generation, likely generator (J17–J19) logic error. 
  - Proof failure on simple theorems: J-function semantic bug (e.g., J74 list copy) or incorrect H-register save/restore. 
  - Metrics mismatch: Actual cycles/subproblems far outside historical range suggests inefficient interpreter or incorrect primitive emulation.
- **First 3 experiments:** 
  1. Run IPL-V "Hello World" (e.g., `(J2 W0 'HELLO)`) to verify basic cell allocation, J2, and output. 
  2. Execute a single LT substitution on a known input (e.g., applying axiom *1.2 to goal `(P → P)`) to validate key proof step logic. 
  3. Run LT on Theorem 2.01 with `effort_limit=20000` and instrumented J74; compare trace against reference output to confirm bug fix.

## Open Questions the Paper Calls Out
1. Can the IPL-V interpreter successfully execute other landmark early AI programs (GPS, EPAM)? The author is currently transcribing and debugging these but results are not yet available.
2. How does the 1963 Stefferud IPL-V version of LT differ behaviorally from the lost 1957 IPL-II JOHNNIAC version? Without the original source, algorithmic differences remain speculative.
3. What are effective methodologies and risks of using LLMs in "executable archaeology" regarding the "epistemological bootstrapping" problem where the LLM learns incorrect semantics from a buggy reference interpreter?
4. Does emulating the abstract IPL-V machine (rather than the full JOHNNIAC/CTSS environment) introduce subtle behavioral or performance biases that compromise "faithful reconstruction"?

## Limitations
- **Transcription integrity:** Subtle errors may persist in the transcribed IPL-V code from the 1963 RAND report PDF despite tooling and reviews.
- **Incomplete J-function semantics:** The interpreter implements only the ~50 J-functions used by LT; indirect jumps to unimplemented functions could cause silent failures.
- **Ground truth dependency:** Resolution of key bugs relied on access to the original 1962 "Simon's J's" card deck; if this artifact is lost or mismatched, fixes may be invalid.

## Confidence
- **Core claim (faithful reanimation matching 16/23 theorems):** High (direct execution, manual conformance, independent validation).
- **Methodological soundness ("executable archaeology"):** High (hybrid debugging, multi-artifact cross-referencing).
- **Generality beyond LT:** Low (validated only for this specific program/artifact set).
