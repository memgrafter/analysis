# Synthesis and Verification of Transformer Programs

## Quick Facts
- arXiv ID: 2602.16473  
- Source URL: https://arxiv.org/abs/2602.16473  
- Reference count: 40  
- Primary result: The paper introduces the first automated verification and synthesis methods for C‑RASP, achieving 100% accuracy on most benchmark languages within 300 seconds and enabling program minimization and constrained learning from partial specifications.

## Executive Summary
C‑RASP is a formal model capturing transformer computation, but prior to this work it lacked automated verification and synthesis. This paper bridges that gap by translating C‑RASP to Lustre for verification via model checking and by using simulated annealing for synthesis from examples. Evaluated on standard formal language benchmarks, the synthesizer attains perfect accuracy on most tasks within minutes, far outpacing direct transformer training. The verifier checks inclusion and equivalence properties in up to ~90 seconds. An integrated framework supports two applications: program minimization through iterative refinement and constrained learning from partial specifications. Failures on languages outside C‑RASP (e.g., Parity, PT‑5) confirm the method’s soundness and the expressiveness boundary of the formalism.

## Method Summary
The method comprises two integrated components. Verification translates a C‑RASP program into a synchronous dataflow program in Lustre, encoding properties (language inclusion or equivalence) as Lustre `check` statements. The Lustre code is validated by the Kind2 model checker with SMT solvers (CVC5, Z3), which either proves the property or returns a counterexample trace. Synthesis searches for a C‑RASP program consistent with provided positive/negative string examples. It operates on a fixed program shape (`N_b`, `N_c`, `K`) and explores the space via simulated annealing. Mutations locally modify rule right‑hand sides; an objective function `E(P)=λ_mis·mis(P)+λ_U·unreach(P)+λ_S·size(P)` balances correctness and simplicity, while an annealing schedule controls exploration. The two components are combined in an iterative loop: synthesis proposes candidates, verification checks against a reference (original or specification), and counterexamples from failed checks are fed back as additional training data, enabling minimization and constrained learning.

## Key Results
- Synthesis accuracy: 100% on most benchmark languages (Dyck‑1, Majority, Tomita 1/2/4/7) within a 300‑second budget; training transformers for the same tasks takes days.
- Verification efficiency: inclusion and equivalence checks complete in up to ~90 seconds using the Lustre/Kind2 pipeline.
- Applications: program minimization and constrained learning from partial specifications succeed with few rounds; languages outside C‑RASP (Parity, PT‑5) time out as expected, confirming the correctness and expressiveness limits.

## Why This Works (Mechanism)

### Mechanism 1: Verification via Lustre Reduction
- **Claim:** C‑RASP program verification is automated by translating to Lustre and leveraging mature model checkers.  
- **Mechanism:** A polynomial‑time translation (for unary‑bounded local counts) from a C‑RASP program to a synchronous dataflow program in Lustre. Verification properties (inclusion, equivalence) are encoded as Lustre `check` statements. Kind2 uses SMT solvers (e.g., CVC5, Z3) to prove the property or produce a counterexample trace.  
- **Core assumption:** The Lustre model checker is sound and sufficiently complete for the translated fragment; the translation faithfully preserves C‑RASP semantics over finite words via the `ι` encoding and stream markers.  
- **Evidence anchors:** [abstract] “we establish a connection to the verification of synchronous dataflow programs in Lustre…”; [section 3.2] details translation and Proposition 3.2 for inclusion.  
- **Break condition:** Translation becomes exponential if `#rs,re` bounds are binary; verification fails for properties/programs outside the decidable Lustre fragment or for languages not expressible in C‑RASP (e.g., Parity).

### Mechanism 2: Synthesis via Local Search
- **Claim:** C‑RASP synthesis from examples is feasible via local search over a restricted syntactic space, avoiding the cost and non‑guarantees of transformer training.  
- **Mechanism:** Simulated annealing explores a finite space `Pσ` of programs with a fixed shape (`N_b`, `N_c`, `K`). Mutations (resampling or micro‑mutations of rule right‑hand sides) propose neighbors. Objective function `E(P)=λ_mis·mis(P)+λ_U·unreach(P)+λ_S·size(P)` prioritizes zero misclassification then simplicity. The annealing schedule (`T₀`, `α`, reheating) balances exploration/exploitation.  
- **Core assumption:** The search space `Pσ` contains a fitting program; the mutation neighborhood connects all programs of the shape; the temperature schedule allows escape from local minima while eventually converging.  
- **Evidence anchors:** [abstract] “synthesis from examples uses local search via simulated annealing…” ; [section 4] defines state space, mutation operator, objective, and Algorithm 1.  
- **Break condition:** No correct program exists in the specified shape; mutation operator too restrictive; annealing schedule poorly tuned; budget exhausted.

### Mechanism 3: Verify‑Guided Iteration
- **Claim:** Iterative interplay between synthesis and verification enables program minimization and constrained learning from partial specifications.  
- **Mechanism:**  
  1. *Minimization*: Start with a correct (possibly large) C‑RASP. Synthesize simpler variants; verify equivalence against original using the Lustre checker. A counterexample from a failed equivalence check is added as a negative example to steer synthesis. Repeat until equivalence holds.  
  2. *Constrained learning*: Start with labeled examples and a partial‑spec C‑RASP `P_spec`. Synthesize candidates consistent with examples; verify inclusion `L(P) ⊆ L(P_spec)`. Failed inclusion yields a counterexample added as a negative example.  
- **Core assumption:** Verification is fast enough to guide many synthesis rounds; counterexamples from failed checks are valid and informative; the original/spec program correctly describes the target property.  
- **Evidence anchors:** [abstract] “The integrated framework enables two applications…” ; [section 5] describes the applications and shows refinement rounds in Table 1.  
- **Break condition:** Verification times dominate; generated counterexamples insufficient; partial specification inconsistent.

## Architecture Onboarding
- **Component map:** Front-end parser -> Shape validator -> Mutation engine -> C‑RASP evaluator -> Lustre translator -> Verification back‑end -> Annealing controller -> Application orchestrator  
- **Critical path:**  
  - Synthesis‑only: Parse -> Initialize program -> Loop: mutate -> evaluate -> annealing accept/repeat until `mis(P)=0` or budget.  
  - Verification‑guided: Add after synthesis: translate -> call Kind2 -> if check fails: parse counterexample -> add to `D⁻` -> re‑synthesize.  
- **Design tradeoffs:**  
  - Mutation expressiveness vs. simplicity: Shallow fragments bias toward interpretable programs but may require more rounds.  
  - Verification cost vs. guidance frequency: Full equivalence checks are expensive but give strong guarantees; inclusion checks may be cheaper but less informative for minimization.  
  - Temperature schedule: Higher `T₀` and reheating increase exploration but slow convergence; `α` close to 1 extends cooling, risking stagnation.  
  - Shape selection (`σ`): Too restrictive makes problem unsolvable; too large increases search space and verification complexity.  
- **Failure signatures:**  
  - Synthesis timeouts on Parity/PT‑5 → hypothesis class limitation (expected).  
  - Verification timeouts on D3/D4 minimization → model checker overwhelmed.  
  - Repeated counterexamples → mutation operator or shape inadequate; stuck in local minima.  
  - Kind2 “unknown” – SMT solver inconclusive; may need tactic adjustments.  
- **First 3 experiments:**  
  1. Single‑language sanity check: Synthesize Dyck‑1 from 1000 examples. Expect 100% accuracy within seconds.  
  2. Equivalence check: Take two known C‑RASPs for Majority, run inclusion checks both ways. Expect Kind2 validation within ~20 s.  
  3. Minimization trial: Provide an over‑complicated C‑RASP for Tomita‑2; run minimization. Should converge to canonical program in ~20 rounds.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can verification methods for C‑RASP be extended to handle robustness properties (e.g., string perturbations like Hamming or edit distance) for sequential models?  
- **Basis in paper:** [explicit] The “Future Work” section explicitly mentions extending verification to properties such as “robustness” and notes that the right formulation for sequential models is unexplored.  
- **Why unresolved:** Robustness is well‑studied for neural networks but lacks a natural definition for string‑based models like C‑RASP; metrics on strings and their integration with the Lustre translation are non‑trivial.  
- **What evidence would resolve it:** A formal definition of robustness for C‑RASP (e.g., small input changes preserve acceptance) and an implemented verification procedure (e.g., via modified Lustre encoding) tested on benchmark examples.

### Open Question 2
- **Question:** Can C‑RASP be extended to express languages it currently cannot (e.g., Parity, PT‑5) while still capturing the class of length‑generalizable transformer languages?  
- **Basis in paper:** [inferred] The paper notes timeouts on Parity and PT‑5, attributing them to fundamental expressiveness limits of C‑RASP, and references the “RASP conjecture” that C‑RASP captures all such transformer languages.  
- **Why unresolved:** The conjecture remains unproven; extending C‑RASP might break its alignment with real transformers or require new primitives whose transformer implementation is unknown.  
- **What evidence would resolve it:** Either a proof that no C‑RASP extension can express these languages without violating transformer capabilities, or a concrete extended C‑RASP formalism that includes such languages and is shown to be implementable by transformers.

### Open Question 3
- **Question:** Do the syntactic depth restrictions in the synthesis algorithm (e.g., shallow counting expressions, no nested Boolean connectives) prevent finding smaller or more efficient C‑RASP programs?  
- **Basis in paper:** [inferred] The synthesis uses a restricted fragment to bias search toward simplicity; the paper does not analyze whether this limits optimality or completeness.  
- **Why unresolved:** The fragment is chosen heuristically for interpretability; it may exclude minimal programs or those requiring deeper nesting.  
- **What evidence would resolve it:** Empirical comparison of synthesis results with and without depth restrictions on benchmarks, or a theoretical characterization of the fragment’s completeness relative to unrestricted C‑RASP.

### Open Question 4
- **Question:** Can the exponential translation blowup for `#(rs,re)` under binary encoding be avoided while preserving polynomial‑time verification?  
- **Basis in paper:** [explicit] Proposition 3.3 states the translation is polynomial only if `rs` and `re` are unary; otherwise it is exponential.  
- **Why unresolved:** The paper assumes unary encoding as a workaround but does not explore optimizing the translation for binary parameters, which are more compact and realistic.  
- **What evidence would resolve it:** A new encoding of `#(rs,re)` in Lustre that is polynomial in the size of the C‑RASP program even when `rs` and `re` are binary, or a proof that such an encoding is impossible without losing verification soundness.

### Open Question 5
- **Question:** Is the RASP conjecture true—does C‑RASP precisely capture all length‑generalizable transformer languages?  
- **Basis in paper:** [explicit] The paper mentions the “RASP conjecture” from [12] that C‑RASP captures all such languages and positions this work as a step toward investigating it via synthesis/verification.  
- **Why unresolved:** The conjecture is stated as an open problem; this work provides tools to test it but does not prove it.  
- **What evidence would resolve it:** A formal proof that any transformer exhibiting length generalization can be simulated by a C‑RASP program, or a counterexample of a length‑generalizable transformer task not expressible in C‑RASP.

## Limitations
- Hyperparameter values (λ coefficients, annealing schedule, mutation probabilities) are not disclosed, potentially affecting reproducibility.  
- Dataset generation details (positive/negative sampling, length distribution) are missing, which may influence synthesis difficulty.  
- Shape parameters for some languages (D2, D3, D4) are not provided, preventing faithful replication of all benchmarks.

## Confidence
- Verification via Lustre reduction: High  
- Synthesis accuracy (100% on most languages, ≤300 s): Medium  
- Expressiveness boundary (Parity/PT‑5 time out): High  
- Integrated applications (minimization, constrained learning): Medium  

## Next Checks

- Translation fidelity: Generate a diverse benchmark of small C‑RASP programs (≤5 rules, bounds ≤3). For each, compare the language produced by the original C‑RASP interpreter (exhaustively over strings ≤ length 10) with the Lustre model checker’s decision on the same set.  
- Verification scalability: Construct C‑RASP programs where a counting rule uses `#rs,re` with bound *b* increasing from 1 to 20. Measure Kind2’s wall‑clock time for the inclusion check; plot time vs. *b* to confirm polynomial growth and identify the practicality threshold.
