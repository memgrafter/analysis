# Stan: An LLM-based thermodynamics course assistant

## Quick Facts
- **arXiv ID:** 2603.04657
- **Source URL:** https://arxiv.org/abs/2603.04657
- **Reference count:** 0
- **Primary result:** Locally deployed dual-role LLM system for thermodynamics education using Whisper large-v3 and Llama 3.1 8B achieves 49× transcription speed, 0.02% hallucination loops, and instructor analysis in ~15 minutes on RTX 4090.

## Executive Summary
Stan is a locally deployed dual-role LLM system for thermodynamics education built on open-weight models (Whisper large‑v3, Llama 3.1 8B). For students, it uses retrieval‑augmented generation (RAG) that extracts technical terms from queries, matches them against a structured textbook index, and synthesizes page‑referenced responses. For instructors, it analyzes lecture transcripts to generate summaries, identify questions and confusion points, and catalog anecdotes/analogies. The pipeline transcribed 39 lectures (35.7 hours) in 43.7 minutes (49× realtime) with hallucination loops reduced to 0.02%. Instructor analyses completed in ~15 minutes on an RTX 4090. Key failure modes (context truncation, bimodal output) were resolved by explicit context sizing and a two‑pass extraction architecture.

## Method Summary
The system processes lecture audio via `faster-whisper` (Whisper large‑v3) with domain‑specific vocabulary prompting, VAD, and post‑processing to filter hallucinated loops. Student queries undergo dual‑path term extraction (regex + Llama 3.1 8B) that matches terms against a pre‑extracted textbook index JSON; top matching pages are retrieved and synthesized into grounded responses. Instructor analysis feeds full transcripts (with `num_ctx=16,384`) to Llama 3.1 8B in JSON mode to extract summaries, questions, confusion points, and anecdotes, using a two‑pass architecture for question identification to avoid bimodal output. All components run locally: batch transcription and analysis on an RTX 4090 workstation; interactive querying on a laptop with quantized models via Ollama.

## Key Results
- Transcribed 39 lectures (35.7 hours) in 43.7 minutes (49× realtime) with hallucination loops reduced to 0.02%
- Instructor analyses completed in ~15 minutes on RTX 4090
- Resolved key failure modes: context truncation via explicit `num_ctx=16,384`; bimodal output via two‑pass extraction architecture

## Why This Works (Mechanism)

### Dual‑Path Term Extraction for Robust Index Matching
The system runs two parallel extractors on student queries: a regex matcher for deterministic phrase matching and an LLM for semantic expansions. Scores per index entry are merged by taking the maximum, preserving matches from either path. This assumes a professionally curated textbook index is a high‑quality retrieval target and that term overlap scoring reliably surfaces relevant pages. Evidence comes from the paper’s description of the dual‑path design addressing local LLM fragility. Break condition: if the index lacks coverage for a query’s concepts, retrieval fails.

### Structured LLM Analysis of Long Transcripts
Full timestamped transcripts are passed to an LLM with a JSON‑mode system prompt specifying a schema (summaries, questions, confusion points, anecdotes). Explicit context window sizing (`num_ctx=16,384`) prevents truncation. The core assumption is that an 8B parameter local model can extract conversational teaching elements from long academic speech. Evidence is the instructor analysis pipeline producing structured JSON. A break condition is schema drift or bimodal output (e.g., exactly 8 questions per lecture), mitigated by a two‑pass decomposition for complex tasks.

### Local Deployment on Consumer Hardware
Batch processing (transcription, index building) runs on a high‑VRAM GPU workstation; interactive querying runs on a laptop with quantized models via Ollama. No cloud APIs are used, ensuring data privacy, predictable costs, and reproducibility. The assumption is that 7–8B models suffice for structured extraction and consumer hardware can handle interactive load. Evidence includes the described hardware split and performance metrics. Break condition: sub‑minimum hardware (no GPU, low RAM) makes latency unusable or quantization degrades quality.

## Foundational Learning
- **Retrieval‑Augmented Generation (RAG)**: Why needed: grounds LLM outputs in specific textbook pages to prevent hallucination of thermodynamic principles. Quick check: Why is it insufficient to rely on the LLM’s parametric knowledge for precise thermodynamics explanations?
- **Structured Indexing vs. Vector Search**: Why needed: the textbook’s back‑of‑book index is a pre‑curated, hierarchical map offering transparent, deterministic matching without embedding tuning. Quick check: What are the trade‑offs of using a human‑edited index versus embedding‑based search over raw textbook text?
- **Context Window Management**: Why needed: lecture transcripts (~13K tokens) exceed default LLM context windows; explicit sizing prevents silent truncation and loss of extraction fidelity. Quick check: How does setting `num_ctx=16,384` prevent a failure mode in the lecture analysis pipeline?

## Architecture Onboarding
- **Component map:** Audio Recordings -> [Batch: Whisper Transcription -> Hallucination Filter] -> Transcripts JSON -> [Student: Query -> Dual‑Path Extraction -> Index Search -> Context Assembly -> LLM Synthesis -> Response] and [Instructor: Transcript -> Two‑Pass Analysis (e.g., candidate extraction -> filtering) -> Structured JSON]. Data assets (textbook index JSON, TOC navigation tree JSON) feed into student pipeline.
- **Critical path:** For student queries, LLM synthesis is slowest (~1–3 s on laptop). For course setup, transcription of all lectures is the bottleneck.
- **Design tradeoffs:** Dual‑path extraction adds complexity but guarantees baseline if LLM inference fails; max‑score merge preserves matches but risks higher noise; local deployment eliminates API costs but transfers maintenance burden.
- **Failure signatures:** Exactly 8 items extracted from every lecture → bimodal output; timestamps show `H:MM:SS` → placeholder echoing in prompt; transcription time anomalously fast (~2 s/lecture) → context truncation.
- **First 3 experiments:**
  1. **Term extraction sanity check:** Query “fugacity coefficient” and verify both regex and LLM extractors return relevant index entries with page numbers. Confirm max‑score merge does not penalize regex‑only matches.
  2. **Lecture analysis end‑to‑end:** Process a 60‑min transcript with the confusion detection pipeline. Check output JSON schema conformity (topic, severity, timestamp) and timestamp alignment.
  3. **Hallucination loop detection:** Run transcription on a lecture with known silent segments. Verify post‑processing removes identical consecutive segments and logs loop metadata; aim for <0.1% segment removal rate.

## Open Questions the Paper Calls Out
- **How does deployment of instructor‑facing tools like Stan’s lecture analytics impact teaching practices and course improvement?** The paper states systematic evaluation is essential and future work includes defining measurable outcomes, but presents no empirical study on effectiveness. Without evidence, claimed benefits for course evolution remain anecdotal. Resolution requires a longitudinal study tracking instructors’ use of analytics and correlating with teaching adjustments or student outcomes.
- **To what extent can the RAG‑based student‑facing tool be scaled to higher cognitive capability levels (e.g., Concept Explainer, Guided Problem Solver) while maintaining factual grounding?** The authors limit current goals to Levels 1–2 (Resource Pointer, Content Summarizer) and note higher levels involve deeper reasoning and open‑ended problems, which are prone to hallucination even with RAG. Scaling requires evaluation of whether grounding constraints suffice for complex queries. Resolution requires controlled experiments where higher‑level queries are expert‑evaluated for accuracy against gold standards.
- **Are the failure‑mode mitigations (e.g., two‑pass extraction for question identification) generalizable to other structured extraction tasks (confusion detection, anecdote cataloging) when using small local models over long transcripts?** The paper details a bimodal output failure in question extraction resolved by two‑pass decomposition, but applies single‑pass to other modules, where over‑classification persists. The pattern’s generalizability is untested. Resolution requires replicating two‑pass for confusion/anecdote extraction and comparing output distributions against human annotations.
- **How can domain vocabulary prompting be automated or semi‑automated to scale across multiple courses or evolving curriculum without manual instructor intervention?** The paper uses a static prompt that “does not scale well” and suggests strategies (textbook index extraction, syllabus‑driven prompting) but implements none. Scaling requires a systematic solution. Resolution requires developing and testing an automated pipeline that generates per‑lecture prompts from textbook index and syllabus, measuring transcription accuracy against manual baselines.

## Limitations
- Textbook index and TOC extraction method is unspecified, blocking faithful reproduction.
- No empirical evidence that instructor analytics lead to tangible teaching improvements or better student outcomes.
- RAG system’s utility is strictly bounded by textbook index coverage; queries outside the index yield no useful response.
- Instructor analysis outputs lack human validation; bimodal output necessitated a two‑pass fix, indicating model fragility.
- Performance claims assume high‑end hardware (RTX 4090); accessibility for users with lower‑spec devices is unclear.

## Confidence
- **Student RAG pipeline (dual‑path extraction):** Medium – internal metrics show low hallucination, but no user study confirms answer accuracy or pedagogical value.
- **Instructor analysis pipeline (structured transcript analysis):** Low – two‑pass architecture was needed to avoid bimodal output, and no evaluation of artifact extraction quality is reported.
- **Local deployment readiness (hardware/software setup):** High – transcription speed (49× realtime) and interactive latency are clearly documented on specified hardware.
