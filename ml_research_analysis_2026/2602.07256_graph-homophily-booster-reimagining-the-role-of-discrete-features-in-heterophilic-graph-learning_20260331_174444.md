# Graph homophily booster: Reimagining the role of discrete features in heterophilic graph learning

## Quick Facts
- **arXiv ID**: 2602.07256
- **Source URL**: https://arxiv.org/abs/2602.07256
- **Reference count**: 40
- **Primary result**: GRAPHITE directly boosts graph homophily via a graph transformation that adds feature nodes, enabling homophilic message passing and achieving significant performance gains on heterophilic benchmarks while adding only O(|V|) nodes and O(|E|) edges.

## Executive Summary
Graph neural networks often underperform on heterophilic graphs, where connected nodes tend to have dissimilar features. This paper introduces GRAPHITE, a novel paradigm that transforms the input graph to increase homophily without altering the GNN architecture. By creating a feature node for each discrete feature and connecting all nodes sharing that feature to it, GRAPHITE establishes two‑hop homophilic pathways. Theoretically, the transformation increases the homophily ratio while adding only linear overhead. Empirically, GRAPHITE dramatically improves homophily metrics (up to +179% on Actor) and outperforms 27 state‑of‑the‑art methods across multiple heterophilic datasets, with gains up to 5.4%. It remains competitive on homophilic graphs and can enhance existing GNNs with minimal runtime overhead.

## Method Summary
GRAPHITE transforms a graph with discrete node features into an augmented bipartite graph. For each feature in the original matrix, a new feature node is created and connected to all original nodes possessing that feature. Feature node features are set to the average of their connected nodes’ features. The resulting graph consists of original nodes and feature nodes, with edges of two types: original graph edges and feature edges. This transformed graph is fed into a GNN equipped with a self‑gating mechanism: for each edge, a gating score α = tanh((aᵀ[h_u ∥ h_v] + b)/τ) modulates the contribution. Edge weights (w_E for original, w_X for feature, w_0 for self‑loops) and degree normalization are applied in the aggregation. The model also incorporates an MLP with residual connections after each GNN layer. Training uses Adam (lr=3e‑5) for 1000 steps on node classification tasks. The transformation adds at most O(|V|) nodes and O(|E|) edges under sparsity assumptions, ensuring scalability.

## Key Results
- GRAPHITE improves feature homophily by +179% and adjusted homophily by +2767% on the Actor dataset.
- It surpasses 27 SOTA methods on heterophilic benchmarks: +4.2% on Actor, +5.2% on Squirrel‑F, +5.4% on Chameleon‑F, +3.5% on Minesweeper.
- The approach remains competitive on homophilic graphs (e.g., CORA, CiteSeer) and can boost existing homophilic GNNs with little extra cost.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: GRAPHITE creates two‑hop homophilic pathways between nodes sharing any discrete feature, enabling effective homophilic message passing even in heterophilic graphs.
- **Mechanism**: For each discrete feature, a “feature node” is created and connected to all graph nodes possessing that feature. Any two graph nodes with a common feature become length‑2 neighbors via the shared feature node. This indirect connection pattern allows similar nodes to exchange information homophilically despite lacking direct edges.
- **Core assumption**: The graph’s node features are discrete (binary/multi‑valued) and sparse, such that node pairs sharing features exist but are rarely directly connected in the original heterophilic graph.
- **Evidence anchors**:
  - [abstract] “creates discrete feature nodes as hubs, connecting original nodes with shared features via two‑hop paths”
  - [section] Observation 2: “For each pair of nodes u, v ∈ V, if they share at least a feature … then v_i and v_j are two‑hop neighbors on the transformed graph G*.”
  - [corpus] Neighbor papers (e.g., [31996] on graph rewiring for homophily) confirm that structural modifications can address heterophily, but GRAPHITE uniquely leverages feature‑based hubs.
- **Break condition**: If the original graph already exhibits high homophily, two‑hop pathways may be redundant, potentially adding noise without benefit. Also fails for purely continuous features without discretization.

### Mechanism 2
- **Claim**: Adding homophilic feature edges (graph node ↔ feature node) provably increases the overall graph homophily ratio under realistic sparsity assumptions.
- **Mechanism**: Every added feature edge connects a graph node to a feature node where the feature node’s representation (average of connected nodes’ features) shows perfect alignment with that node on the shared feature. Since these edges always have feature similarity = 1 (by construction), and the original graph has heterophily (hom(G)<1), inserting even a few such edges tilts the overall average homophily upward.
- **Core assumption**: (1) Original graph is heterophilic (hom(G) < 1). (2) Feature matrix is sparse (∥X∥₀ ≤ O(|E|)) and the number of features |X| ≤ O(|V|). (3) At least one feature is shared by multiple nodes but those nodes are not all directly connected.
- **Evidence anchors**:
  - [section] Theorem 3: “Under mild and realistic assumptions … hom(G*)>hom(G)” with formal proof using feature edge similarity = 1 and Lemma 4 on multiset averages.
  - [abstract] “Theoretically, GRAPHITE increases homophily while only adding O(|V|) nodes and O(|E|) edges.”
  - [corpus] Corpus shows many heterophily‑focused methods (e.g., [254618] H2GCN, FAGCN) but none explicitly transform graph structure to increase homophily metric; our theoretical guarantee is distinctive.
- **Break condition**: If all original edges already have feature similarity = 1 (perfect homophily), then adding edges with similarity = 1 doesn’t change the average. Also, if feature nodes are poorly defined (e.g., continuous features binned inconsistently), the similarity assumption may not hold.

### Mechanism 3
- **Claim**: GRAPHITE efficiently represents feature sharing relationships using only O(|V|) added nodes and O(|E|) added edges, avoiding the O(|V|²) blowup of naive “shortcut” edge addition.
- **Mechanism**: Instead of connecting every pair of nodes that share a feature (requiring O(|V|²) edges), GRAPHITE uses feature nodes as hubs. Each feature node connects to *all* nodes having that feature. The total added edges = ∑ₖ degₖ (sum over features of number of nodes with feature k), which is exactly ∥X∥₁ = ∥X∥₀ under sparsity assumptions, yielding O(|E|) growth.
- **Core assumption**: The sparsity pattern of the feature matrix matches graph edge density: ∥X∥₀ ≤ O(|E|) and |X| ≤ O(|V|). Real‑world discrete feature matrices are typically sparse (each node has few features).
- **Evidence anchors**:
  - [section] Theorem 3: “|V*| ≤ O(|V|), |E*| ≤ O(|E|)” and comparison to naive homophily booster (NHB) which adds O(|V|²) edges (Eq. 2).
  - [section] Page 3: “To reduce the number of shortcut edges, we propose to connect such node pairs indirectly instead.”
  - [corpus] Corpus includes efficiency‑sensitive GNN methods (e.g., NodeFormer, SGFormer) but GRAPHITE’s transformation complexity is theoretically bounded, making it scalable to large graphs.
- **Break condition**: If features are extremely dense (each node has nearly all features) or the number of features |X| is Ω(|V|²), the O(|E|) bound may not hold. Also, if feature nodes become super‑hubs with millions of connections, message passing could become unbalanced without careful weighting.

## Foundational Learning
- **Concept**: Graph Homophily/Heterophily  
  - **Why needed here**: The core problem is graph heterophily, where connected nodes tend to have dissimilar features. Understanding edge homophily, feature homophily, and adjusted homophily is essential to interpret the theory and results.  
  - **Quick check question**: What is the difference between edge homophily (H_edge) and feature homophily (H_feature), and why might they diverge on heterophilic graphs?

- **Concept**: Message Passing in Graph Neural Networks  
  - **Why needed here**: GRAPHITE’s goal is to facilitate “homophilic message passing.” Standard GNN layers aggregate neighbor features; in heterophilic graphs this aggregates dissimilar information, harming performance. The transformed graph alters the neighborhood structure to enable aggregation from similar nodes via two‑hop paths.  
  - **Quick check question**: In a 2‑layer GNN on the original heterophilic graph, what information does a node aggregate from its 2‑hop neighborhood? How does GRAPHITE change this aggregation pattern?

- **Concept**: Graph Transformation and Computational Complexity  
  - **Why needed here**: GRAPHITE is a preprocessing transformation that modifies the graph structure. The paper emphasizes theoretical guarantees on size increase (O(|V|) nodes, O(|E|) edges). Assessing scalability requires understanding graph complexity metrics and worst‑case edge addition scenarios.  
  - **Quick check question**: Why does connecting nodes via feature hubs reduce the worst‑case edge addition from O(|V|²) to O(|E|)? What assumptions about the feature matrix make this possible?

## Architecture Onboarding
- **Component map**: Data loader → GraphTransformer → GNN model → Trainer
- **Critical path**:
  1. Load raw graph
  2. Transform graph (add nodes/edges, compute feature node features)
  3. Initialize GNN with appropriate edge weights and self‑gating
  4. Train on labeled nodes (masking feature nodes from loss)
  5. Evaluate on test set (original graph nodes only)
- **Design tradeoffs**:
  - *Preprocessing vs. end‑to‑end*: Transformation is fixed, simplifying training but missing task‑specific adaptation of feature nodes.
  - *Feature node aggregation*: Averaging is simple and effective; learned embeddings gave negligible gains but add parameters.
  - *Edge weighting*: Hyperparameters w_X and τ control influence of feature edges; tuning needed per dataset.
  - *Backbone flexibility*: Transformation is GNN‑agnostic, but custom self‑gating GNN works best.
- **Failure signatures**:
  - No gain on high‑homophily datasets (e.g., CORA).
  - Memory blowup if |X| is huge (feature nodes dominate).
  - Feature node feature collapse when many nodes share a feature, making averaged representation uninformative.
  - Self‑gating saturation if τ is too small (vanishing gradients) or too large (linear behavior).
- **First 3 experiments**:
  1. **Homophily boost validation**: Compute H_feature and H_adjusted on Actor before/after transformation; expect +179% and +2767% (Table 3).
  2. **Baseline comparison**: Replicate Table 2 on heterophilic datasets (Actor, Squirrel‑F, Chameleon‑F, Minesweeper) with 10 random splits; confirm GRAPHITE outperforms 27 baselines with statistical significance.
  3. **Transformation‑only ablation**: Take a standard homophilic GNN (e.g., GCN) and run on original vs. transformed graph (without custom self‑gating); expect improvement (GCN on Actor: 30.21% → 34.83% in Table 4), isolating the effect of graph transformation.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: Can GRAPHITE be extended to graphs with continuous node features, and what discretization strategies (e.g., clustering, binning) best preserve discriminative information while controlling the number of added feature nodes?
- **Basis in paper**: [explicit] “An interesting future direction would be extending the proposed graph transformation to general graphs with continuous node features; possible approaches include clustering the continuous features into a few clusters and binning the continuous features into discrete buckets.”
- **Why unresolved**: The current method is designed for discrete binary features; continuous features require preprocessing that may introduce information loss or create an impractically large number of feature nodes, undermining efficiency.
- **What evidence would resolve it**: Empirical evaluation across continuous‑feature heterophilic benchmarks comparing clustering‑based vs. uniform binning approaches, measuring accuracy, runtime, and homophily boost. Theoretical analysis of reconstruction guarantees for different discretization schemes.

### Open Question 2
- **Question**: How does the graph transformation in GRAPHITE affect other global graph properties (e.g., spectral gap, clustering coefficient, effective resistance) beyond homophily, and could these side‑effects explain performance variations on certain datasets?
- **Basis in paper**: [explicit] “Other future directions include (i) studying how our graph transformation affects graph properties...”
- **Why unresolved**: The paper focuses solely on homophily metrics; the transformation may alter other topological characteristics that influence GNN expressivity or oversquashing, potentially beneficial on some graphs but harmful on others.
- **What evidence would resolve it**: Comprehensive measurement of standard graph metrics before/after transformation on diverse datasets, correlated with performance gains. Controlled experiments where homophily is held constant but other properties vary to isolate their effects.

### Open Question 3
- **Question**: Does GRAPHITE’s homophily boosting have a theoretical connection to the node distinguishability principle (Luan et al., 2023), and can this link predict when GRAPHITE will be most effective?
- **Basis in paper**: [explicit] “…(ii) connecting to the node distinguishability principle (Luan et al., 2023)...”
- **Why unresolved**: Node distinguishability (based on multi‑hop neighborhoods) is proposed as a fundamental predictor of GNN success, but its relationship to the explicit local homophily increase from GRAPHITE is unclear.
- **What evidence would resolve it**: Formal proof relating feature node augmentation to changes in node distinguishability scores. Empirical validation showing correlation between pre‑transformation distinguishability measures and GRAPHITE’s improvement magnitude across many graphs.

### Open Question 4
- **Question**: Does using all discrete features to create feature nodes introduce noise or redundancy, and can we automatically select an optimal feature subset to maximize performance while minimizing computational overhead?
- **Basis in paper**: [explicit] “…(iii) identifying an optimal subset of features (Zheng et al., 2025).”
- **Why unresolved**: The current simple approach uses every non‑zero feature as a hub, but irrelevant or rare features may add unnecessary edges and nodes, potentially degrading efficiency or accuracy.
- **What evidence would resolve it**: Feature selection methods (e.g., based on frequency, mutual information with labels) evaluated on heterophilic datasets, tracking accuracy vs. graph size. Theoretical bounds relating feature utility to expected homophily increase per added feature node.

## Limitations
- **Reproduction variability**: Exact train/test splits and some architecture details (MLP size, dropout placement) are not fully specified, leading to potential mismatches in reported numbers.
- **Assumption sensitivity**: The theoretical guarantees rely on sparse discrete features and a heterophilic original graph; dense or continuous features may invalidate the homophily boost or increase overhead.
- **Scalability constraints**: If the number of distinct features is Ω(|V|²) or features are extremely dense, the O(|V|) node and O(|E|) edge bounds may not hold, risking memory blowup and message‑passing imbalance.
