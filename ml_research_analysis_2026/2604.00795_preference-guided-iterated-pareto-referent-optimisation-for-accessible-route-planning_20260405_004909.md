# Preference Guided Iterated Pareto Referent Optimisation for Accessible Route Planning
## Quick Facts
*   **arXiv ID:** 2604.00795
*   **Source URL:** https://arxiv.org/abs/2604.00795
*   **Reference count:** 22
*   **Primary result:** PG-IPRO achieves higher user utility in early interaction rounds and reduces average route generation time from 70s to 4.7s by generating one Pareto-optimal solution at a time instead of precomputing the full front.

## Executive Summary
This paper tackles accessible urban route planning as a multi-objective problem where trade-offs exist between factors like distance and the number of crossings. Traditional approaches that precompute the entire Pareto front are computationally expensive, leading to slow response times unsuitable for interactive use. The authors propose Preference Guided Iterated Pareto Referent Optimisation (PG-IPRO), an interactive algorithm that avoids full front enumeration. After presenting an initial route, the user specifies which objective to improve. The system then iteratively identifies a new Pareto-optimal route in that preferred direction using a guided search oracle. This user-in-the-loop approach focuses computation on relevant regions of the objective space, delivering high-utility solutions quickly and significantly reducing waiting times compared to Bayesian baselines.

## Method Summary
PG-IPRO is an interactive multi-objective optimisation algorithm designed for time-sensitive applications like route planning. It builds on the Iterated Pareto Referent Optimisation (IPRO) framework, which partitions the objective space into regions (dominated, infeasible, unexplored). Instead of computing the complete Pareto front, PG-IPRO operates in a loop: (1) it presents a current best route; (2) the user provides directional feedback by selecting a single objective to improve; (3) the algorithm selects a referent point from unexplored regions that guarantees improvement in that objective; (4) a specialised oracle (Multi-Objective Depth-First Search) is invoked to find any Pareto-optimal route that strictly dominates the referent within its target region; (5) the new route is presented and compared. This process repeats, generating exactly one new solution per interaction. The oracle is accelerated by precomputed lower bounds (via Dijkstra), Pareto-dominance pruning at graph nodes, and scalarised heuristics (e.g., Chebyshev) to prioritise promising search branches.

## Key Results
*   PG-IPRO achieves higher user utility than the Bayesian GPPE baseline within the first few interaction rounds, which is critical given users' limited patience.
*   On a real Amsterdam instance (7 Pareto routes), PG-IPRO's average single-route generation time is 4.7 seconds, while GPPE's full front pre-computation requires 70 seconds.
*   The algorithm remains effective on synthetic fronts and demonstrates robustness through its referent-steering mechanism, which focuses computational effort on user-relevant slices of the objective space.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** PG-IPRO rapidly increases user utility by steering the multi-objective search toward regions preferred by the user after only a few interactions.
*   **Mechanism:** The algorithm replaces exhaustive Pareto front enumeration with a user-in-the-loop cycle. After an initial solution, the user specifies a single objective to improve. The system then selects a referent point from its internal partitioning (IPRO's unexplored regions) that guarantees improvement in that objective and invokes a single-objective constrained search (the Oracle) to find a new Pareto-optimal solution in that direction. This focuses computational effort on a narrow, user-relevant slice of the objective space.
*   **Core assumption:** User feedback on "which objective to improve" provides sufficient directional guidance to find high-utility solutions faster than algorithms that explore the full front (e.g., GPPE) or use information-gain queries.
*   **Evidence anchors:**
    *   [abstract]: "interactive algorithm that avoids full front computation... user can interact... by giving feedback on a route, i.e., the user can say which objective should be further minimized... especially effective during early iterations."
    *   [section 3.1]: Describes the interactive loop where user-selected objective `i` filters the improving set `R_improve` from available referents.
    *   [corpus]: Neighbors (e.g., "Preference-Guided Multi-Objective UI Adaptation", "PreferRec") show the broader trend of using preferences to guide MOO, but the specific referent-steering mechanism per IPRO is unique to this paper. Direct corpus evidence for the *early-query advantage* is weak; it is primarily anchored in the paper's own synthetic experiments (Figure 3).
*   **Break condition:** The `R_improve` set becomes empty, indicating no referent exists that can strictly improve the chosen objective while remaining Pareto-optimal.

### Mechanism 2
*   **Claim:** Computational efficiency is achieved by decomposing the multi-objective search into a sequence of bounded single-objective pathfinding subproblems solved by an Oracle with pruning.
*   **Mechanism:** PG-IPRO inherits IPRO's divide-and-conquer approach. The objective space is partitioned into a bounding box of dominated, infeasible, and unexplored target regions. For a selected referent, the Oracle performs a Multi-Objective Depth-First Search (MO-DFS) constrained to the target region. It uses node-wise lower bounds (precomputed via Dijkstra), Pareto-dominance pruning at each node, and scalarized distance-to-target heuristics (Chebyshev/Manhattan) to prioritize exploration, returning a single Pareto-optimal route or reporting failure for that region.
*   **Core assumption:** Solving these constrained single-objective subproblems (with dominance pruning) is significantly cheaper than enumerating the entire Pareto front, and the scalarized heuristic efficiently guides the search to a feasible, strictly dominating solution if one exists.
*   **Evidence anchors:**
    *   [section 2.3]: Explains IPRO's partitioning and Oracle call pattern.
    *   [section 3.3]: Details the MO-DFS Oracle, its lower-bound preprocessing, pruning conditions, and scalarized prioritization.
    *   [corpus]: The neighbor "Divide and Conquer: Provably Unveiling the Pareto Front..." (paper_id 122768) is the source of IPRO. It provides the theoretical guarantee and algorithmic framework that PG-IPRO builds upon, but does not include the interactive preference guidance.
*   **Break condition:** The Oracle exhausts the search space within the target region without finding a solution that strictly dominates the referent and falls within the region's upper bounds.

### Mechanism 3
*   **Claim:** The iterative, single-solution generation model reduces average user waiting time compared to front-first methods.
*   **Mechanism:** Unlike GPPE, which requires pre-computing the entire discrete Pareto front before elicitation can begin (costly for large graphs), PG-IPRO generates exactly one new route per user interaction. The time cost is amortized across interactions; the user sees a first candidate after only the initial Oracle call, and subsequent solutions are produced on-demand in the interactive loop.
*   **Core assumption:** In time-sensitive applications like route planning, the latency of presenting the first few satisfactory solutions is more critical than the total time to compute all possible options. Users have limited patience for multiple interactions.
*   **Evidence anchors:**
    *   [abstract]: "due to PG-IPRO’s iterative nature, the full set... is never computed, leading to higher computational efficiency and shorter waiting times."
    *   [section 4.4]: Empirical result: "GPPE requires pre-computation... which took 70s. On the other hand, PG-IPRO generates solutions iteratively, which took 4.7s on average."
    *   [corpus]: No direct evidence; this is an empirical claim from the paper's real-world instance experiment. Corpus neighbors discuss preference-guided MOO generally but not latency profiles.
*   **Break condition:** Not applicable as a mechanism failure; it's a performance characteristic. The trade-off is that if the user requires seeing many alternatives to decide, a pre-computed front (GPPE) might eventually offer more options, but at a high initial cost.

## Foundational Learning
*   **Concept:** Pareto Dominance & Pareto Front
    *   **Why needed here:** The entire problem is formulated as finding a path whose objective vector is non-dominated by any other feasible path. Understanding dominance is required to grasp what an "optimal" solution means in a multi-objective context and why a set of trade-offs (the front) exists instead of a single best route.
    *   **Quick check question:** Given two routes, A ([500m, 4 crossings]) and B ([550m, 3 crossings]), is either Pareto-dominating the other? What would a Pareto-optimal route look like relative to these two?
*   **Concept:** Interactive Preference Elicitation
    *   **Why needed here:** PG-IPRO is fundamentally an interactive preference elicitation method. It assumes a user has a latent utility function over objective vectors and learns it through a specific query type ("improve objective i"). This contrasts with eliciting pairwise comparisons between full solutions (as in GPPE).
    *   **Quick check question:** How does asking "which objective should be improved?" differ information-theoretically from asking "do you prefer route A or route B?" in guiding the search?
*   **Concept:** Oracle-based Constrained Search
    *   **Why needed here:** PG-IPRO's efficiency hinges on the Oracle subroutine. The Oracle takes a referent and a target region and must efficiently find *any* Pareto-optimal solution within that region, or report none exists. This is a specialised constrained shortest-path problem.
    *   **Quick check question:** Why is it insufficient to simply run a standard multi-objective shortest path algorithm with a constraint on one objective? What specific pruning techniques (from section 3.3) make this Oracle fast?

## Architecture Onboarding
*   **Component map:**
    User Interface (UI) -> Referent Selector -> IPRO Core Manager -> Oracle (MO-DFS)
    UI <- Oracle (returns solution)
    IPRO Core Manager <- Oracle (updates partition)
    Preprocessing Module -> Oracle (provides lower bounds)
*   **Critical path:** `Init_Phase()` → `Propose Initial Solution` → **User Feedback ("improve obj i")** → `Select Referent r_next` → `Call Oracle(r_next)` → `Oracle Returns Solution?` → (Yes) `Update IPRO Partition` → `Present New Solution` → **User Comparison** → `Update Best Solution` → Loop.
*   **Design tradeoffs:**
    *   **Heuristic choice:** Closest-distance (exploitative, small steps) vs. Middle-distance (exploratory, balanced moves). This trades off rapid local gain against potentially missing a better global trade-off.
    *   **Oracle scalarization:** Manhattan (closeness to ideal) vs. Chebyshev Achievement Scalarizing Function (balance). Affects which type of Pareto solution is found first in a region.
    *   **Nadir approximation:** Exact Nadir is NP-hard to compute; using an approximation risks an initial bounding box that is too large (more search) or too small (may miss parts of the front).
*   **Failure signatures:**
    *   **Stalled improvement:** User selects an objective `i`, but `R_improve` is empty or Oracle repeatedly fails. Indicates the current best solution is already optimal for that objective direction within the explored space.
    *   **High variance in solution time:** Oracle's DFS runtime is path-dependent; certain target regions may contain many near-dominating partial paths causing deep stack exploration. Monitor per-query generation time.
    *   **Partition inconsistency:** After an Oracle success, the update of `D`, `I`, and unexplored regions must correctly carve out the new solution's dominated volume. A bug here could leave referents in `R_improve` that cannot actually lead to improvement.
*   **First 3 experiments:**
    1.  **Oracle Correctness Validation:** On a small, known graph with 2 objectives, manually compute the exact Pareto front. Run PG-IPRO with exhaustive referent sampling and verify every solution returned is truly Pareto-optimal and strictly dominates its referent.
    2.  **Heuristic Benchmarking:** Fix the user model and problem instance. Run PG-IPRO with Closest vs. Middle-distance referent selection and Manhattan vs. Chebyshev Oracle scalarization. Measure average utility after 3 interactions and average Oracle runtime. Identify the most robust combination.
    3.  **Latency Stress Test:** Replicate the Amsterdam Osdorp-Midden instance (7 routes). Measure distribution (mean, std dev) of single-route generation time for PG-IPRO's Oracle against the total pre-computation time for GPPE. Verify the 4.7s vs 70s claim holds under different hardware/resource constraints.

## Open Questions the Paper Calls Out
*   **Open Question 1: How does PG‑IPRO perform in real‑user studies compared to simulated trials?** Current evaluations use synthetic linear utilities and simulated users, which may not reflect real preference complexity and limited interaction patience. A field deployment with human participants measuring utility gain, number of interactions, satisfaction, and response times against baseline algorithms would resolve this.
*   **Open Question 2: Does incorporating prior assumptions about utility distributions improve PG‑IPRO’s sample efficiency and scalability to higher dimensions?** The present algorithm uses no prior information; its behaviour on many‑objective problems is unknown. Comparing standard PG‑IPRO with a Bayesian variant that encodes utility priors on synthetic tasks of increasing objective count would provide evidence.
*   **Open Question 3: Can PG‑IPRO effectively handle more than two objectives, and how do the referent selection and oracle heuristics scale?** All experiments are bi‑objective; the curse of dimensionality may degrade IPRO’s partitioning and oracle performance. Implementing PG‑IPRO for m ≥ 3 objectives and evaluating on fronts of varying dimensionality would test scalability.

## Limitations
*   **Generalizability:** Results are demonstrated on a single real-world instance (Amsterdam Osdorp-Midden, 2 objectives). Performance on larger graphs, more objectives, or different urban fabrics is unknown.
*   **User Model Fidelity:** The simulated user utility function (weighted sigmoids + small noise) is a proxy. Real user preferences may be more complex or expressed through different feedback types, potentially breaking the core assumption that "improve objective *i*" is sufficiently informative.
*   **Baseline Specificity:** The comparison is against a specific Bayesian GPPE implementation. Performance relative to other interactive MOO frameworks is not established, and exact heuristic parameters (Nadir approximation, scalarization) may be sensitive.

## Confidence
*   **Algorithmic Mechanism (IPRO + Preference Loop):** High. The mechanism is precisely defined and inherits theoretical guarantees from the base IPRO algorithm.
*   **Empirical Performance vs. GPPE (Utility & Time):** Medium. Claims are backed by the paper's own experiments, but independent reproduction is needed to rule out implementation details or parameter tuning.
*   **Core Assumption (Directional Feedback Sufficiency):** Low-Medium. This central innovation is validated primarily against a baseline with a different feedback type (probabilistic updates). There is no ablation study isolating the contribution of preference guidance.

## Next Checks

2.  **Sensitivity to Heuristic Parameters:** For the Amsterdam instance, run PG-IPRO across all combinations of referent selection heuristics (Closest, Middle) and Oracle scalarizations (Manhattan, Chebyshev). Record the area under the utility curve over 6 queries to identify the most robust combination.
3.  **Baseline Replication & Latency Isolation:** Re-run the Osdorp-Midden experiment comparing PG-IPRO's average generation time to GPPE's full front pre-computation time on identical hardware. Instrument GPPE to report incremental solution generation time to understand if the 70s vs 4.7s gap is due to front-computation overhead or per-solution complexity.
