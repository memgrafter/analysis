# An Ontology-driven Dynamic Knowledge Base for Uninhabited Ground Vehicles

## Quick Facts
- **arXiv ID:** 2602.10555
- **Source URL:** https://arxiv.org/abs/2602.10555
- **Reference count:** 6
- **Primary result:** An ontology-driven Dynamic Contextual Mission Data (DCMD) system enables real-time knowledge base updates and sharing across a team of UGVs, improving situation awareness and supporting autonomous hazard-driven decision-making in dynamic environments.

## Executive Summary
Uninhabited Ground Vehicles (UGVs) typically rely on static, pre-mission data, which creates identification ambiguities when operating in dynamic environments. This paper introduces Dynamic Contextual Mission Data (DCMD), an ontology-driven knowledge base that allows for real-time updates. The system integrates the Basic Formal Ontology (BFO) and Common Core Ontologies (CCO) for semantic representation, uses Bayesian Networks for probabilistic hazard identification, and employs TypeDB for on-board storage and querying. Implemented on four TurtleBot3 UGVs in a lab-based surveillance mission, the system successfully detected and represented known objects and hazards, dynamically shared updates across the team, and triggered coordinated verification actions, leading to successful mission completion.

## Method Summary
The proposed pipeline consists of five stages: (1) **Acquisition**: UGV sensors (RealSense D435i) capture images and depth; YOLOv11 performs object detection. (2) **Assessment**: Detected objects are matched against the a priori knowledge base; a Bayesian Network (using Variable Elimination) infers identity and hazard probabilities. (3) **Representation**: Inferred data is structured using an ontology (BFO/CCO/RO Core), mapped to an Entity-Relationship model, and stored in TypeDB. (4) **Updates**: New DCMD records, containing spatial, temporal, and attribute information, are inserted via TypeQL and shared across agents over WLAN. (5) **Mission**: Explorer UGVs traverse waypoints to generate updates; if a hazard probability exceeds a threshold, verifier UGVs are dispatched to confirm.

## Key Results
- Accurate detection and representation of known objects (e.g., a rigid hulled inflatable boat) and hazards (e.g., an armoured humvee identified as a hazard with 0.98 probability).
- DCMD updates were dynamically integrated into the shared knowledge base, enabling cross-agent situational awareness.
- Shared updates triggered coordinated hazard verification actions, leading to successful mission completion.

## Why This Works (Mechanism)
DCMD works by closing the loop between perception and knowledge. Real-time sensor detections are not merely logged but are assessed against a structured, probabilistic model (Bayesian Network) and an ontology-backed knowledge base. This allows the system to quantify uncertainty (e.g., hazard probability) and maintain semantic consistency. Updates are propagated instantly across the UGV team via ROS 2, enabling collective adaptation. The use of established ontologies (BFO/CCO) ensures that representations are interoperable and formally grounded, while TypeDB's graph model efficiently handles complex queries for identity matching and relation traversal.

## Foundational Learning
- **Ontologies (BFO, CCO, RO Core):** Provide a formal, shared semantics for representing entities (e.g., material entities, objects) and their relations. *Why needed:* To ensure interoperable, consistent knowledge representation across heterogeneous sensors and agents. *Quick check:* Validate the TypeDB schema against upper-level ontology constraints (e.g., all `object` types must subclass `material entity` from BFO).
- **Bayesian Networks:** A probabilistic graphical model for reasoning under uncertainty. *Why needed:* To fuse noisy sensor evidence (e.g., visual shape, movement) and infer identity/hazard status with quantified confidence. *Quick check:* Test inference on a known scenario (e.g., stationary object matching a `humvee` visual profile should yield high `hazard` probability).
- **TypeDB (Graph Database):** Stores and queries the ontology-driven knowledge base using TypeQL. *Why needed:* To support complex, relation-heavy queries (e.g., "find all hazards near waypoint X with confidence >0.9") required for dynamic mission planning. *Quick check:* Execute a sample query that joins an object with its spatial context and inferred hazard probability.
- **ROS 2 (Robot Operating System):** Middleware for robot software communication. *Why needed:* To facilitate reliable, decentralized data sharing (DCMD updates) among multiple UGVs over WLAN. *Quick check:* Verify that custom messages/types for DCMD updates are published/subscribed correctly across four nodes.
- **YOLOv11 (Object Detection):** A deep learning model for real-time detection. *Why needed:* To provide the initial perceptual evidence (bounding boxes, class labels) from camera imagery. *Quick check:* Run inference on test images from the lab environment to confirm detection of target objects (boat, humvee) with sufficient accuracy.
- **Entity-Relationship (ER) Modeling:** Conceptual data modeling technique. *Why needed:* To bridge the formal ontology and the implementation-specific database schema in TypeDB. *Quick check:* Map a sample ontology class (e.g., `armoured_vehicle`) to its corresponding entity type and attributes in the ER diagram.

## Architecture Onboarding
The system follows a perception-to-action loop distributed across multiple agents.

**Component Map:**  
Sensors (RealSense D435i) -> YOLOv11 Detection -> Depth Localization -> Identity Matching (TypeDB Query) -> Bayesian Network Inference -> DCMD Update Creation (TypeDB Insert) -> ROS 2 Publication -> Team-wide Update Integration -> Mission Behavior (Explorer/Verifier)

**Critical Path:** The end-to-end latency from raw sensor capture to a shared DCMD update that triggers a verifier's action. Delays in any step (detection, inference, database write, network publish) degrade real-time coordination.

**Design Tradeoffs:**
- **TypeDB vs. Faster Key-Value Store:** TypeDB's rich graph queries enable semantic matching but introduce overhead versus a simpler store. Tradeoff: expressiveness for speed; chosen because identity matching requires complex relational queries.
- **Discrete Bayesian Network vs. Deep Learning Classifier:** The BN explicitly models uncertainty and allows incorporation of domain knowledge (CPTs) but requires hand-crafted structure and parameters. Tradeoff: interpretability and data efficiency for ease of training; chosen for explainable hazard reasoning.
- **Centralized Knowledge Base (TypeDB on each UGV) vs. Truly Distributed:** Each UGV hosts its own copy, synchronized via ROS 2. Tradeoff: resilience to network partition vs. consistency overhead; chosen for reliable local querying with eventual consistency.

**Failure Signatures:**
- **Ontology Schema Rejection:** TypeDB startup fails due to invalid constraints or misaligned BFO subclassing. *Diagnostic:* Validate schema with a minimal `*.tl` file; check error logs for constraint violations.
- **BN Inference Nonsense:** Hazard probabilities are uniform or NaN. *Diagnostic:* Verify all evidence nodes have valid discrete states; ensure all Conditional Probability Tables (CPTs) are complete and normalized.
- **Update Desynchronization:** Agents act on outdated hazard information. *Diagnostic:* Add sequence timestamps to DCMD updates; monitor ROS 2 message delivery latency and backlog.

**First Three Experiments:**
1.  **Schema Validation:** Load the complete TypeDB schema and a minimal a priori knowledge base (e.g., definitions for `boat`, `humvee`). Execute a query that retrieves all `hazard` objects. Success = valid schema and correct results.
2.  **BN Sanity Check:** With the Bayesian Network initialized, feed evidence corresponding to a clear `armoured_humvee` detection (high visual match, stationary). Expect `hazard` probability >0.95. Success = inference yields plausible, deterministic-like result for unambiguous evidence.
3.  **End-to-End Update Flow:** Run a single explorer UGV through one waypoint, detect a target, and generate an update. Verify the update appears in its local TypeDB and is published on the ROS 2 topic, then received and integrated by a verifier UGV's knowledge base. Success = verifier's KB reflects the new hazard record within 5 seconds.

## Limitations
- **Unreported Bayesian Network Parameters:** The Conditional Probability Tables (CPTs) and prior probabilities are not provided, making exact replication of hazard inference impossible without heuristic definition.
- **Incomplete TypeDB Schema Specification:** The full ontology-driven schema (all entity types, relations, constraints) and the exact "class documents" for a priori objects are not detailed, requiring significant reconstruction.
- **Limited Evaluation Scope:** Tests were conducted in a controlled laboratory with 1:18 plastic targets and four pre-scripted agents. Performance in unstructured, large-scale, or adversarial environments is unknown.

## Confidence
- **Claim:** DCMD enables real-time knowledge base updates and sharing. **Confidence:** Medium. Supported by described architecture and lab demo, but lacks details on latency, scalability, and conflict resolution.
- **Claim:** Hazard detection accuracy (e.g., armoured humvee at 0.98). **Confidence:** Low. This result is contingent on unreported BN parameters; the number is not independently verifiable.
- **Claim:** Ontology-driven representation (BFO/CCO) ensures semantic consistency. **Confidence:** High. The use of established upper-level ontologies is sound theoretically; the limitation is in incomplete specification, not the approach.
