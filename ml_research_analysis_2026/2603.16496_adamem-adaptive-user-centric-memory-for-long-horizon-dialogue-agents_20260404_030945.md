# AdaMem: Adaptive User-Centric Memory for Long-Horizon Dialogue Agents

## Quick Facts
- arXiv ID: 2603.16496
- Source URL: https://arxiv.org/abs/2603.16496
- Reference count: 29
- Primary result: Achieves SOTA on LoCoMo (44.65% F1) and PERSONAMEM (63.25% accuracy) with adaptive memory structures and retrieval.

## Executive Summary
AdaMem tackles key challenges in long-horizon dialogue agents by introducing an adaptive user-centric memory framework. It structures memory per participant into four types—working, episodic, persona, and graph—to preserve context, experiences, traits, and relations. At inference, it resolves the target participant, plans question-conditioned retrieval that combines semantic search with relation-aware graph expansion only when needed, and uses a specialized multi-agent pipeline (Memory, Research, Working) for evidence synthesis and response generation. Experiments on LoCoMo and PERSONAMEM show significant improvements over prior SOTA, with notable gains in temporal reasoning and generalization.

## Method Summary
AdaMem implements a multi-stage pipeline. First, the Memory Agent processes each utterance via a normalization prompt, updating participant-specific working memories (FIFO buffers). When working memory fills, older segments are consolidated into episodic memory (structured events, facts, attributes) and persona memory (compact user profiles). A heterogeneous graph memory links messages, topics, facts, and persona snapshots via typed edges. For question answering, the Target Resolver identifies the participant of interest. The Route Planner uses rule-based cues (temporal, relational, attribute patterns) to generate a retrieval plan specifying whether to use graph expansion, hop depth, and fusion weights; an optional LLM refiner adjusts within bounds. The Research Agent then iteratively retrieves evidence via a unified API that combines baseline semantic search (over persona/episodic/topic caches) with conditional graph expansion, integrates findings, and decides if further retrieval is needed. Finally, the Working Agent synthesizes a concise answer conditioned on the research summary. The system uses an all-MiniLM-L6-v2 embedding model, Faiss for similarity search, and NetworkX for graph operations; hyperparameters include working capacity Cw=20, consolidation segment r=5, graph hop-decay λ=0.85, and up to Li=2 research iterations.

## Key Results
- LoCoMo: 44.65% F1 (+4.4% relative improvement over prior SOTA) with GPT-4.1-mini; temporal reasoning improves by +23.4% F1.
- PERSONAMEM: 63.25% accuracy (+5.9% relative), with a 27.3% gain in generalizing to new scenarios.
- Ablations confirm each component's contribution; disabling graph memory causes the largest performance drop.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Organizing dialogue history into four participant-specific memory structures (working, episodic, persona, graph) combats evidence fragmentation by preserving information at appropriate abstraction levels.
- **Mechanism:**  
  - *Working Memory*: Bounded FIFO buffer retains recent conversational context.  
  - *Episodic Memory*: Structured long-term records (events, facts, attributes) formed by consolidating older working segments.  
  - *Persona Memory*: Compact user profiles distilled from aggregated episodic evidence to capture stable traits.  
  - *Graph Memory*: Heterogeneous graph linking messages, topics, facts, and persona snapshots via typed edges (e.g., `mentions`, `supports`, `temporal_next`), enabling relation-aware navigation.
- **Core assumption:** Different question types require evidence at different granularities and relations; a monolithic memory cannot efficiently serve all.
- **Evidence anchors:**  
  - [abstract] "organizes dialogue history into working, episodic, persona, and graph memories... preserve recent context, structured long-term experiences, stable user traits, and relation-aware connections"  
  - [section 3.1] Describes each memory's purpose and participant-specific bundling.  
  - [corpus] Weak direct evidence; neighboring papers (e.g., MAGMA, MemWeaver) also pursue multi-structure memory, suggesting this is an emerging consensus, but AdaMem's specific quartet is novel.
- **Break condition:** If any memory structure is disabled, performance degrades (Table 3 ablation). Graph removal causes largest drop, confirming its role in linking fragments.

### Mechanism 2
- **Claim:** Question-conditioned retrieval planning adapts memory access to query needs, avoiding the pitfalls of static retrieval strategies (e.g., fixed chunking or pure semantic search).
- **Mechanism:**  
  - *Target resolution*: Determines if question refers to user, assistant, both, or ambiguous participant.  
  - *Route planning*: Rule-based cue detection (temporal, relational, attribute patterns) initializes a plan specifying whether to use graph expansion, hop depth, seed count, and fusion weights. Optional LLM refinement adjusts within bounded ranges.  
  - *Hybrid retrieval*: Baseline semantic search over persona/episodic/topic caches combined with bounded multi-hop graph expansion only when the plan activates it.
- **Core assumption:** Retrieval strategy should be dynamically matched to question demands; overusing graph expansion adds noise for simple factoid queries.
- **Evidence anchors:**  
  - [section 3.3] Details the plan construction and conditional graph activation.  
  - [section 4.4] Ablation shows removing fusion (which combines baseline and graph signals) hurts performance.  
  - [corpus] Neighbors like "Choosing How to Remember" also stress adaptive retrieval, supporting the premise.
- **Break condition:** If graph expansion is forced for all questions, performance may drop due to noise; if never used, temporal reasoning suffers (as seen in ablation and case studies).

### Mechanism 3
- **Claim:** A role-specialized multi-agent pipeline (Memory, Research, Working Agents) decomposes memory maintenance, evidence synthesis, and answer generation, reducing interference and improving evidence grounding.
- **Mechanism:**  
  - *Memory Agent*: Handles normalized write, working-to-episodic consolidation, topic clustering, persona refresh, and graph synchronization.  
  - *Research Agent*: Iterative `Planning → Search → Integrate → Reflection` loop; decomposes information needs, issues retrieval requests, integrates evidence, and decides if more search is needed.  
  - *Working Agent*: Converts the consolidated research summary into a concise final answer, conditioning on speaker identity.
- **Core assumption:** Separating concerns allows each stage to be optimized; e.g., retrieval planning doesn't conflate with response drafting.
- **Evidence anchors:**  
  - [section 3.4] Explicitly defines each agent's role and collaboration order.  
  - [section 4.4] Ablating multi-agent (replacing with single-agent) reduces F1 (43.24 vs. 44.65), showing marginal but consistent benefit.  
  - [corpus] MIRIX also uses specialized agents but without AdaMem's consistency guarantees; the ablation suggests the decomposition itself is beneficial.
- **Break condition:** If any agent fails (e.g., Research Agent's integration misses contradictions, or Working Agent over-summarizes), final answer quality degrades. Case studies show failure when temporal normalization is missing (Figure 5).

## Foundational Learning
- **Concept: Participant-specific memory bundling**  
  - *Why needed here:* Many dialogue questions implicitly target one speaker; bundling memories per participant enables target-aware retrieval and avoids cross-participant noise.  
  - *Quick check question:* Why might storing all utterances in a single memory store fail for a question like "What does *Alice* prefer?"  
- **Concept: Graph memory as a relation-aware retrieval scaffold**  
  - *Why needed here:* Pure semantic retrieval misses links across turns (e.g., an event mentioned early and its consequence later); the graph's typed edges (`temporal_next`, `supports`) provide lightweight structure to traverse such connections.  
  - *Quick check question:* How would a `temporal_next` edge help answer "What happened *after* X?" compared to semantic search alone?  
- **Concept: Question-conditioned route planning**  
  - *Why needed here:* Not all questions need graph expansion; simple factoids can be answered from episodic/persona caches. Planning conserves compute and reduces irrelevant evidence.  
  - *Quick check question:* For "When did Y occur?" what retrieval plan does the rule-based planner likely select, and why?

## Architecture Onboarding
### Component Map
Input (Dialogue history D, question q) → Memory Agent (writes normalized records, updates memories) → Target Resolver (identifies participant) → Route Planner (generates retrieval plan π(q)) → Research Agent (iterative retrieval and integration) → Working Agent (answer synthesis) → Output (answer a).

### Critical Path
Utterance → Normalized write → Memory consolidation → Target resolution → Route planning → Baseline + optional graph retrieval → Research iteration → Answer generation.

### Design Tradeoffs
- *Latency vs. accuracy*: Graph expansion and multiple research iterations increase token usage and latency but improve F1.
- *Complexity vs. robustness*: Four memory structures and multi-agent pipeline increase implementation complexity but reduce interference between write and read phases.
- *Conservatism vs. coverage*: Route planner uses narrow LLM refinement ranges to avoid over-expansion; this may miss some needed graph paths but keeps precision high for simple questions.

### Failure Signatures
- *Target resolution error*: Ambiguous referent leads to retrieving from wrong participant bundle; symptoms: answer attributes wrong speaker.
- *Temporal grounding failure*: Relative time expressions ("last year") not canonically stored; answer defaults to "No evidence".
- *Graph over/under-expansion*: Too many hops → noise; too few → missing links; monitored via `hop_k` and `graph_topn` in plan.

### First 3 Experiments
1. **Ablation - Graph memory off**: Measure drop in temporal/F1; expected largest degradation.
2. **Ablation - Force graph for all questions**: Compare to adaptive planning; expect noise hurting simpler categories (Open Domain).
3. **Research Agent iterations `Li` sweep**: Vary `Li`∈{1,2,3}; expect peak at `Li=2`, drop at `Li=3` due to redundant evidence.
