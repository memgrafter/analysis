# SciVisAgentBench: A Benchmark for Evaluating Scientific Data Analysis and Visualization Agents

## Quick Facts
- arXiv ID: 2603.29139
- Source URL: https://arxiv.org/abs/2603.29139
- Reference count: 40
- Primary result: General-purpose coding agents (e.g., Claude-Code) achieve up to 97.92% task completion and superior image similarity metrics, outperforming specialized SciVis agents.

## Executive Summary
SciVisAgentBench introduces the first reproducible benchmark for evaluating large language model (LLM) based scientific visualization agents in multi-step, real-world analysis settings. It provides a structured taxonomy and 108 expert-crafted cases covering diverse scientific visualization domains, along with a multimodal evaluation pipeline that combines LLM-based judging with deterministic evaluators such as image metrics and code checkers. Validation with 12 domain experts shows strong alignment between the LLM judge (Claude-Opus-4.6) and human scores (Pearson r=0.806). Baseline evaluations demonstrate that general-purpose coding agents significantly outperform specialized SciVis agents in task completion rates (up to 97.92%) and outcome quality, while also achieving superior image similarity metrics. The benchmark is designed as a living, extensible framework to support ongoing community-driven advancement.

## Method Summary
SciVisAgentBench defines a set of 108 evaluation tasks, each specifying a scientific dataset (covering scalar, vector, tensor, multivariate, and time-varying fields), a target visualization tool (ParaView, napari, VMD, or TTK), a ground-truth artifact (image, script, or state), and a rubric. Agents must implement a `run_task` method to ingest the specification, operate the tool, and produce the required output. The benchmark’s evaluation engine orchestrates execution, optionally re-renders outputs under controlled conditions, and computes scores through a hybrid pipeline: deterministic evaluators (e.g., PSNR, SSIM, code linting) assess measurable properties, while a multimodal LLM judge, prompted with the task rubric, scores semantic alignment on a 0–10 scale. Final metrics include completion rate, pass@k, weighted rubric scores, and efficiency (tokens, time). The minimum viable reproduction involves obtaining the repository (Hugging Face), setting up the required visualization environments, implementing an agent, and running the provided evaluation script.

## Key Results
- SciVisAgentBench provides a structured taxonomy and 108 expert-crafted cases across diverse SciVis domains.
- The multimodal evaluation pipeline (LLM judge + deterministic evaluators) achieves strong human-LLM alignment (r=0.806).
- Baseline evaluations show general-purpose coding agents (e.g., Claude-Code) achieve up to 97.92% task completion and superior image similarity metrics, outperforming specialized SciVis agents.

## Why This Works (Mechanism)

**Mechanism 1: Structured Taxonomy for Representative Coverage**  
*Claim:* The structured, expert-curated taxonomy across application domain, data type, complexity level, and visualization operation enables representative coverage of SciVis while ensuring tasks are reproducible.  
*Mechanism:* The four-dimensional taxonomy serves as a multi-dimensional sampling frame. Experts author cases within this frame, guaranteeing that tasks reflect real-world SciVis workflows and admit a single, explicit outcome. This design supports both breadth (diverse scenarios) and targeted evaluation.

**Mechanism 2: Multimodal Outcome-Centric Evaluation Pipeline**  
*Claim:* The pipeline provides reliable, scalable assessment for subjective SciVis tasks by combining deterministic checks with a validated LLM judge.  
*Mechanism:* Each task specifies a mandatory ground-truth artifact (e.g., an image). Evaluation employs deterministic evaluators (image metrics like PSNR/SSIM, code checkers, rule verifiers) for objective components. An MLLM judge, guided by expert rubrics, scores semantic alignment. Human-LLM alignment studies (Pearson r=0.806 with Claude-Opus-4.6) and stability checks validate the judge’s reliability.

**Mechanism 3: Living, Extensible Benchmark Design**  
*Claim:* The framework’s modular architecture and community contribution pipeline sustain long-term relevance and growth.  
*Mechanism:* Clear interfaces for agents, tasks, and evaluators, combined with public contribution templates, allow experts to add new cases, datasets, and evaluators without restructuring the core. This addresses the risk of a benchmark becoming overly general and ensures it can track progress as the field evolves.

## Architecture Onboarding
- **Component map:**  
  1. **Task Suites:** YAML-specified cases (description, dataset, ground-truth artifacts, rubrics) organized by toolchain (ParaView, napari, VMD, TTK).  
  2. **Agent Interface:** A Python base class with a single `run_task(task_spec)` method. Agent returns recorded outcomes (images, scripts, states) to predefined paths.  
  3. **Evaluation Engine:** Orchestrator that loads tasks, invokes agent, triggers post-processing (standardized re-rendering), and calls evaluators.  
  4. **Evaluators:** Modular plugins: `LLMJudge` (rubric scoring), `ImageMetric` (PSNR/SSIM/LPIPS), `CodeChecker`, `RuleVerifier`, `CustomScript`.  
  5. **Aggregator:** Computes pass@k, pass@k, overall score (weighted rubric sum), and efficiency stats (tokens, time).
- **Critical path:** Task specification → Agent execution → Outcome recording → Deterministic evaluation (if applicable) → LLM judging (if applicable) → Score aggregation → Leaderboard update.
- **Design tradeoffs:**  
  - Outcome determinism vs. agent flexibility: Tasks are constrained to single outcomes to ensure fair comparison, which penalizes exploratory agents that might produce alternative valid insights.  
  - Evaluation fidelity vs. scalability: Using a powerful MLLM as judge is costly and may have remaining biases, but rule-based evaluators alone are insufficient for semantic tasks.  
  - Tool-specific vs. generalist evaluation: Current suites are tool-specific (ParaView vs. napari), making cross-domain agent comparison indirect.
- **Failure signatures:**  
  - Agent fails to produce required output artifact: `completion_rate` low, but `pass@1` also low. Check agent's `run_task` implementation.  
  - LLM judge gives high variance scores: Check prompt stability; may need to shuffle rubric order as implemented.  
  - High token usage with low score: Indicates inefficient exploration (common in generalist coding agents). Profile agent's tool call pattern.
- **First 3 experiments:**  
  1. Baseline replication: Evaluate `Claude-Code+Claude-Sonnet-4.5` on the *ParaView Visualization* suite using the provided Docker/conda environment. Verify you reproduce Table 4's ~62.6 score and 97.9% completion.  
  2. Evaluator sanity check: Run the `LLMJudge` on a single case with the agent output replaced by the ground-truth image. Expect near-perfect rubric scores (~10/10). Then, flip the image order in the prompt to test for positional bias (should be minimal due to shuffling).  
  3. Custom case integration: Follow the contribution template to add a simple new task (e.g., a new scalar field isosurface case). Validate that your task's YAML, dataset, and ground-truth image are correctly loaded and that the `ImageMetric` and `LLMJudge` produce non-zero scores for a deliberately flawed agent output.

## Open Questions the Paper Calls Out
**Open Question 1**  
- **Question:** How can we establish reliable ground-truth action trajectories for process-based evaluation of SciVis agents, given the inherent variability in multi-step workflows and the lack of a single "correct" action sequence?  
- **Basis in paper:** Section 5.1 states that process-based evaluation is not fully realized because "the main challenge is establishing reliable ground-truth action trajectories for complex tasks." The paper further explains that multiple valid sequences exist and trajectories are unstable when agents fail.  
- **Why unresolved:** Current evaluation relies solely on outcomes; diagnosing failures, assessing reasoning, and distinguishing systematic approaches require process metrics, but no robust method exists for SciVis workflows.  
- **What evidence would resolve it:** Development of techniques to generate reference trajectories (e.g., from expert demonstrations, constrained executions, or LLM-based trajectory judges) that remain valid across different but correct action sequences, and validation that these metrics correlate with expert assessments of agent behavior.

**Open Question 2**  
- **Question:** How can benchmark evaluation be extended to tasks with multiple equally valid visualization outcomes without sacrificing reproducibility and fairness?  
- **Basis in paper:** The paper admits in Section 5.2 that it deliberately restricts tasks to a single explicit output to avoid the difficulty of multiple valid solutions, acknowledging this as a limitation of the current design.  
- **Why unresolved:** Real SciVis tasks often admit many acceptable visual encodings or rendering choices; forcing a single outcome may not reflect true agent capability and may penalize creative but correct variations.  
- **What evidence would resolve it:** Introduction of evaluation frameworks that measure semantic or feature-level similarity rather than pixel-perfect matches (e.g., using vision-language models or expert rubrics that tolerate variation), along with studies showing these metrics align with human judgment across diverse valid outputs.

**Open Question 3**  
- **Question:** Can LLM-based agents complete long-horizon, end-to-end scientific visualization workflows (including setup, iterative analysis, and reporting) at a level comparable to human experts in contests like IEEE VIS?  
- **Basis in paper:** Section 8 explicitly poses the question: "whether LLM agents can complete end-to-end workflows comparable to an IEEE VIS contest designed for human participants," identifying it as a key direction for deeper complexity levels.  
- **Why unresolved:** SciVisAgentBench currently focuses on task-level evaluations; workflows that span multiple stages, involve external data processing, or require sustained reasoning remain unevaluated.  
- **What evidence would resolve it:** Extension of the benchmark with workflow-level cases that mimic contest-style challenges, followed by systematic testing of existing agents to quantify performance gaps and identify architectural improvements for long-horizon autonomy.

**Open Question 4**  
- **Question:** What is the optimal balance between specialized tool integration and general-purpose reasoning in SciVis agent architectures? Can modular domain-specific skills be added to flexible coding agents to achieve both high performance and efficiency?  
- **Basis in paper:** Baseline results show general-purpose coding agents (e.g., Claude Code) outperform specialized SciVis agents in completion and scores, while specialized agents are more token-efficient. Section 7.4 demonstrates that augmenting Claude Code with a napari skill improves both score and token usage.  
- **Why unresolved:** The trade-offs between adaptability, efficiency, and reliability are not fully understood; it remains unclear whether skill-augmented coding agents can universally match or surpass specialized agents across domains, or if hybrid designs introduce new failure modes.  
- **What evidence would resolve it:** Comprehensive experiments comparing hybrid architectures (coding agents with varying skill sets) against specialized agents across all SciVisAgentBench suites, measuring not only outcome quality but also resource consumption, robustness, and ease of deployment.

## Limitations
- External validity: No evidence that benchmark scores correlate with success on real SciVis research projects.
- LLM judge robustness: Alignment validation used only Claude-Opus-4.6; other MLLMs or new task distributions may yield lower expert agreement.
- Extensibility sustainability: The "living benchmark" depends on volunteer contributions; no data yet on submission volume, quality, or long-term maintenance.

## Confidence
- **Taxonomy-driven coverage**: Medium  
- **Multimodal evaluation**: High  
- **Extensibility & longevity**: Low
