# Team of Thoughts: Efficient Test-time Scaling of Agentic Systems through Orchestrated Tool Calling

## Quick Facts
- arXiv ID: 2602.16485
- Source URL: https://arxiv.org/abs/2602.16485
- Reference count: 29
- Primary result: Team-of-Thoughts achieves state-of-the-art performance on four benchmarks, notably 96.00% on AIME24 (up from 80.00% baseline) and 77.91% on LiveCodeBench (up from 65.93%).

## Executive Summary
Team-of-Thoughts (ToT) is a heterogeneous multi-agent framework that orchestrates diverse LLMs as specialized tools via a central coordinator. The method employs orchestrator calibration to select a model best suited for synthesis and agent self-assessment for each tool to profile its domain strengths. During inference, the orchestrator dynamically selects the most compatible tools based on these profiles and aggregates only their final answers, excluding intermediate reasoning traces. Evaluated on five mathematical and coding benchmarks, ToT consistently sets new state-of-the-art, demonstrating substantial gains over baselines and existing multi-agent systems.

## Method Summary
ToT operates in two offline phases and one inference phase. Offline, it conducts orchestrator calibration: candidate orchestrator models are evaluated on a domain-specific calibration set by aggregating outputs from a fixed tool pool under a cost budget; the highest-scoring model is selected as the orchestrator per domain. Additionally, each tool agent undergoes self-assessment: given its own performance data and reasoning traces on the calibration set, it generates a natural language capability profile summarizing strengths, weaknesses, and failure modes. During inference, the orchestrator reads these profiles and, for each query, selects a small subset of compatible tool agents (typically k=2), invokes them, receives only their final answers (not reasoning traces), and synthesizes a final answer. The approach treats different model families (e.g., Claude, GPT, DeepSeek) as heterogeneous tools with complementary priors.

## Key Results
- Achieves 96.00% on AIME24, improving from 80.00% baseline; and 77.91% on LiveCodeBench, improving from 65.93%.
- Outperforms individual models and homogeneous multi-agent systems by leveraging complementary strengths through dynamic, capability-aware tool calling.
- Shows that limiting tool responses to final answers (excluding reasoning traces) maximizes orchestrator synthesis accuracy, with experiments confirming that including traces degrades performance.

## Why This Works (Mechanism)
### Mechanism 1: Orchestrator Calibration
- **Claim:** A specialized orchestrator model, selected via calibration, can effectively synthesize outputs from heterogeneous tool agents by leveraging its superior coordination and aggregation capabilities.
- **Mechanism:** The system evaluates candidate orchestrator models on a domain-specific calibration set, measuring their accuracy when tasked with aggregating responses from a fixed set of tool agents under a computational budget. The highest-scoring model is designated as the orchestrator. This model then manages the reasoning process: selecting compatible tool agents based on their self-assessed profiles, invoking them, and synthesizing their final outputs into a final answer.
- **Core assumption:** Orchestration proficiency—the ability to integrate diverse external outputs—is a distinct skill not perfectly correlated with a model's standalone problem-solving ability or its scale.
- **Evidence anchors:** [abstract]: "Orchestrator Calibration, which identifies models with superior coordination and synthesis capabilities." [section 3.2] details calibration and shows DeepSeek for math, GPT-5 Mini for code. [section 4.2] empirical results confirm best orchestrator differs by task and is not the overall strongest solver.
- **Break condition:** Calibration fails if the validation set is too small or unrepresentative, leading to suboptimal orchestrator selection. Performance decays when the orchestrator is overwhelmed by context from too many tool agents.

### Mechanism 2: Agent Self-Assessment
- **Claim:** Tool agents can accurately and usefully self-profile their domain-specific strengths and failure modes, enabling the orchestrator to make targeted, efficient invocations.
- **Mechanism:** Each tool agent is prompted with its own performance data (correct/incorrect labels) on a calibration set, its reasoning traces for those tasks, and the ground truths. It generates a natural language "capability profile" summarizing its core competencies, blind spots, and reliability for specific problem categories. This profile is provided to the orchestrator's context during inference to guide agent selection.
- **Core assumption:** LLMs possess sufficient meta-cognitive capacity to critique their own reasoning patterns on a set of examples and produce a stable, generalizable summary of their expertise.
- **Evidence anchors:** [abstract]: "Agent Self-Assessment, a protocol where tool agents profile their own domain-specific strengths to guide selection." [section 3.3] outlines the three-stage self-assessment process. [section 4.3] direct comparison shows "Agent Self-Assessment" policy achieves highest Pass@1 accuracy over "Orchestrator-Led Assessment" and "Random Invocation".
- **Break condition:** Self-assessment fails if the calibration set is too small for the model to identify robust patterns, or if the model's self-critique is systematically inaccurate or overconfident.

### Mechanism 3: Final-Answer-Only Synthesis
- **Claim:** Limiting tool agent responses to final answers only (excluding intermediate reasoning traces) maximizes the orchestrator's synthesis accuracy by reducing contextual noise from fallible intermediate steps.
- **Mechanism:** During a tool call, an activated agent generates a full reasoning trajectory but returns only its final prediction to the orchestrator, not its intermediate steps. The orchestrator then aggregates these discrete answers. This filtering prevents the orchestrator's own reasoning from being derailed by incorrect logical steps or irrelevant details.
- **Core assumption:** The primary value of a specialized tool agent lies in its final answer distribution, not its reasoning process. Intermediate reasoning from a potentially misaligned or error-prone agent introduces harmful variance and noise.
- **Evidence anchors:** [section 4.4] explicit experiments showing configurations that "Include traces" underperform "No traces" across AIME2025 and MBPP+ metrics. Analysis: "Verbose trajectories introduce significant contextual noise, which can distract or mislead the orchestrator."
- **Break condition:** This mechanism breaks for tasks where reasoning process itself is critical for verification or debugging.

## Foundational Learning
- **Concept: Test-Time Scaling (TTS)**
  - **Why needed:** The paper operates within the TTS paradigm, where performance is improved by allocating more inference-time compute (e.g., calling multiple agents) rather than scaling model parameters during training. Understanding TTS is key to seeing why ToT is a test-time scaling method.
  - **Quick check:** How does Team-of-Thoughts achieve test-time scaling differently from single-model methods like Tree of Thoughts?

- **Concept: Homogeneous vs. Heterogeneous Multi-Agent Systems (MAS)**
  - **Why needed:** The core innovation is exploiting heterogeneity. Foundational knowledge of traditional MAS (often using the same model with different prompts/personas) is necessary to contrast with the proposed framework that treats different model architectures as distinct "tools."
  - **Quick check:** Why might a homogeneous MAS (multiple instances of GPT-4) fail to cover as much of the solution space as a heterogeneous one (e.g., GPT-4 + Claude + DeepSeek)?

- **Concept: Tool-Calling / Function-Calling Paradigm**
  - **Why needed:** The orchestrator uses native LLM tool-calling capabilities to "invoke" other LLMs as tools. This architectural pattern is the engine of the system.
  - **Quick check:** In this system, what is the "tool" being called? Is it a calculator API or another LLM? What changes in the prompt structure to implement this?

- **Concept: Orchestration Calibration**
  - **Why needed:** Ensures the orchestrator model is chosen for its synthesis ability rather than its standalone problem-solving skill, which is central to the ToT design.
  - **Quick check:** How does orchestrator calibration differ from simply selecting the strongest model as the coordinator?

- **Concept: Agent Self-Assessment**
  - **Why needed:** Enables the orchestrator to make informed decisions about which tools to invoke based on each tool's self-perceived strengths, reducing reliance on external evaluations.
  - **Quick check:** What are the risks of using self-assessment profiles generated by the tool agents themselves?

- **Concept: Final-Answer Aggregation**
  - **Why needed:** The system's output synthesis step relies on aggregating final answers only, which is a design choice to minimize noise.
  - **Quick check:** What tasks might benefit from including reasoning traces in the aggregation? What tasks might suffer?

## Architecture Onboarding
- **Component map:**  
Calibration Module → (Orchestrator selection, Tool performance)  
Self-Assessment Module → (Tool profiles)  
Profile Store ← (from Calibration & Self-Assessment)  
Orchestrator Agent ↔ Profile Store  
Orchestrator Agent → Tool Agent Pool (invocations)  
Tool Agent Pool → Orchestrator Agent (final answers)
- **Critical path:**
  1. Offline Pre-Inference: For each target domain (math, code), run Orchestration Calibration to pick best `orch_model`. For every tool agent in the pool, run Agent Self-Assessment to generate its `profile_i`.
  2. Inference - Per Query: Given a new problem D, the orchestrator (`orch_model`) reads stored `profile_i` for all available tools. It selects a subset of k most compatible tools. It invokes each selected tool agent with D (receiving only final answers `ˆXi`). It synthesizes `{D, ˆX1..k}` to produce the final answer.
- **Design tradeoffs:**
  - Activation Density (k): More tools increase chance of a correct solver but introduce noise, hurting Pass@1; optimal k is small (2).
  - Ensemble Breadth (|E|): Larger pool offers more candidates but causes "selection logic overload" for the orchestrator; optimal pool size ~25 tools.
  - Profile Objectivity: Self-assessment profiles decouple from orchestrator bias but depend on model self-insight; orchestrator-led assessment is cheaper but may reflect orchestrator's blind spots.
  - Information Flow: Excluding full traces boosts robustness but loses process-level information for verification.
- **Failure signatures:**
  - Orchestrator Bottleneck: Performance plateaus/drops when increasing k or |E| beyond small numbers.
  - Selection Degradation: Sharp drop in "Agreement" between small-k and large-k selections as |E| grows, indicating random/poor tool choices.
  - Calibration Mismatch: If calibration data distribution diverges from online queries, agent profiles become misleading.
  - Context Overload: Noisy or excessively long tool output formats could saturate orchestrator's effective reasoning capacity.
- **First 3 experiments:**
  1. **Orchestrator Calibration Validation:** For a fixed budget, run all candidate orchestrators aggregating outputs from a fixed tool set on a domain validation set. Verify that the top-selected orchestrator genuinely achieves the highest score and is not simply the strongest standalone solver.
  2. **Self-Assessment vs. Baseline Selection:** On a held-out test set, compare three conditions: (a) Random tool invocation, (b) Orchestrator-led assessment, (c) Agent Self-Assessment. Expect (c) to yield highest Pass@1.
  3. **Scaling Laws & Activation Saturation:** With a fixed large pool (e.g., 25 popular models), vary the number of tools activated per call (k). Plot Pass@1, Pass@3, Pass@5. Expect Pass@1 to peak at low k (e.g., 2) and degrade for k>=8, while Pass@5 may remain stable or increase slightly.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the centralized orchestrator bottleneck be mitigated when scaling Team-of-Thoughts to very large agent ensembles (e.g., >50 tools)?
- **Basis in paper:** [explicit] The limitations state that the orchestrator becomes overwhelmed by excessive options, leading to selection overload and performance decay.
- **Why unresolved:** Current work shows sharp drops in selection agreement and pass@1 accuracy beyond 25-50 tools, limiting scalability.
- **What evidence would resolve it:** Experiments with hierarchical or distributed orchestration, or enhanced selection algorithms, tested on ensembles of 100+ tools.

### Open Question 2
- **Question:** What principles should guide the construction of calibration datasets to balance bias toward strong models and exploration diversity in tool selection?
- **Basis in paper:** [explicit] Appendix B identifies a trade-off where categorized calibration improves pass@1 but reduces selection diversity and pass@5.
- **Why unresolved:** No systematic study exists on calibration set design; the current approach is ad-hoc and domain-specific.
- **What evidence would resolve it:** Comparative analysis of calibration strategies (e.g., stratified sampling, difficulty-weighted) across multiple benchmarks, measuring both accuracy and diversity metrics.

### Open Question 3
- **Question:** How reliable are agent self-assessments in profiling domain expertise, and do they consistently correlate with actual performance on unseen tasks?
- **Basis in paper:** [inferred] The framework relies on self-assessment for tool selection but does not validate whether self-reported strengths/weaknesses match empirical results.
- **Why unresolved:** Self-assessment could be biased (overconfident or modest), leading to suboptimal orchestrator decisions; no ablations test this assumption.
- **What evidence would resolve it:** Correlate self-assessment scores with held-out task performance across diverse models and domains; compare against third-party assessments.

### Open Question 4
- **Question:** Should the number of tool agents activated per query (k) be static or dynamically adapted based on task complexity or ensemble size?
- **Basis in paper:** [inferred] Experiments show that increasing k beyond 2 degrades pass@1, but this is tested with fixed k; dynamic adjustment might optimize for stability vs. exploration.
- **Why unresolved:** The paper uses k=2 universally, but different tasks may benefit from different activation densities; the orchestrator's synthesis capacity might vary with context.
- **What evidence would resolve it:** Per-query k selection strategies (e.g., based on task difficulty estimation or ensemble agreement) evaluated on scaling curves and robustness metrics.

## Limitations
- Orchestrator selection overload occurs when ensemble size exceeds ~25 tools or activation density k > 2, limiting scalability.
- Calibration and self-assessment rely on representative domain-specific validation sets; performance degrades with distribution shift between calibration and test data.
- Agent self-assessment profiles may be biased or inaccurate if calibration data is insufficient, leading to suboptimal tool selection.
