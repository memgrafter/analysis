# Em-Garde: A Propose-Match Framework for Proactive Streaming Video Understanding

## Quick Facts
- arXiv ID: 2603.19054
- Source URL: https://arxiv.org/abs/2603.19054
- Reference count: 40
- Primary result: Improves proactive response accuracy by over 3% and F1 score by over 10% compared to prior models, while achieving 10-15 fps on A100 GPUs.

## Executive Summary
Em-Garde is a propose-match framework for proactive streaming video understanding that addresses the efficiency-accuracy trade-off by decoupling semantic parsing from streaming perception. At query time, an Instruction-Guided Proposal Parser transforms user queries into structured visual proposals grounded in perceptual features. A Lightweight Proposal Matching Module then continuously compares incoming video frames against these proposals via cosine similarity in an embedding space, enabling efficient triggering without repeated semantic reasoning. Evaluated on StreamingBench and OVO-Bench, Em-Garde yields over 3% absolute gains in accuracy and over 10% in F1 relative to prior methods, while maintaining 10-15 fps processing on A100 GPUs and competitive online video QA performance.

## Method Summary
The framework consists of two main components: (1) an Instruction-Guided Proposal Parser that processes a natural language query to generate a set of perceptually-grounded visual proposals (e.g., object locations, actions) at query time, and (2) a Lightweight Proposal Matching Module that runs continuously on the streaming video, computing embeddings for each frame and matching them against stored proposal embeddings using cosine similarity. Matching scores trigger the execution of more expensive downstream reasoning only when a proposal is matched above a threshold. This design avoids the need to perform full semantic reasoning on every frame, drastically reducing computational overhead. The proposal parser leverages a large language or vision-language model to interpret the query and produce proposals grounded in visual features extracted by a pre-trained vision encoder. The matching module uses a lightweight network to embed frames and proposals into a shared space.

## Key Results
- Outperforms prior models by >3% accuracy and >10% F1 on StreamingBench and OVO-Bench.
- Achieves real-time processing speeds of 10-15 fps on A100 GPUs.
- Maintains competitive performance on online video QA tasks.

## Why This Works (Mechanism)
Em-Garde works by separating the computationally expensive semantic reasoning from the continuous video stream. The proposal parser runs only once per query, transforming the query into concrete visual concepts that can be matched with low-cost embeddings. The lightweight matching module operates on every frame but only computes simple cosine similarities, which are much faster than running a full perception pipeline repeatedly. This decoupling ensures that the system scales efficiently with frame rate and query complexity, as the matching cost is independent of the number of proposals (only their embeddings). Moreover, the use of a shared embedding space learned for matching preserves discriminative power, allowing accurate triggering despite the simplicity of the similarity metric.

## Architecture Onboarding
**Component Map** (plain text flow):  
User Query -> Instruction-Guided Proposal Parser -> Set of Proposal Embeddings -> Stored in Memory  
Video Stream -> Frame Encoder -> Frame Embeddings -> [Cosine Similarity Computation] -> Matching Scores -> Trigger Decision  

**Critical Path**: The end-to-end latency is dominated by (a) proposal parsing time (only at query time) and (b) per-frame embedding and matching time. The matching must be faster than the frame interval to maintain real-time operation; otherwise frames are dropped.

**Design Tradeoffs**:
- Accuracy vs. Speed: The matching module prioritizes speed by using a shallow network and cosine similarity; this may sacrifice fine-grained discrimination compared to more complex models.
- Proposal expressiveness vs. Parsing complexity: More detailed proposals improve matching but increase parser burden and embedding dimensionality.
- Memory vs. Performance: Storing many proposal embeddings can improve coverage but increases memory footprint and matching time.

**Failure Signatures**:
- High false negatives: Proposal embeddings do not align with frame embeddings; may indicate poor training of the embedding space or inadequate proposal coverage.
- High false positives: Matching threshold too low or ambiguous proposals; monitor precision-recall tradeoff on validation stream.
- Dropped frames: Matching latency exceeds frame interval; check CPU/GPU utilization and model optimization.

**First 3 Experiments**:
1. **Baseline Comparison**: Run Em-Garde against a full-frame-per-trigger baseline (e.g., applying a video QA model on every frame) on a held-out streaming dataset; measure accuracy and fps.
2. **Ablation of Proposal Parser**: Replace the parser with random proposals or a simpler heuristic to quantify its contribution to overall accuracy.
3. **Matching Module Sensitivity**: Vary the matching threshold and embedding dimensions to plot accuracy-fps curves; identify operating points that meet real-time constraints.

## Limitations
- ⚠️ **Benchmark Scope**: Results are only on StreamingBench and OVO-Bench; unknown how well Em-Garde generalizes to other datasets or real-world streaming conditions.
- ⚠️ **Component Analysis Missing**: No ablation studies isolate the Proposal Parser vs. Matching Module, limiting understanding of each part’s contribution.
- ⚠️ **Deployment Constraints**: Efficiency claims rely on high-end A100 GPUs; edge deployment feasibility and robustness to ambiguous queries remain untested.
