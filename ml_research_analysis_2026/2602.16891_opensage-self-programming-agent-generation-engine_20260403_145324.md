# OpenSage: Self-programming Agent Generation Engine

## Quick Facts
- **arXiv ID:** 2602.16891  
- **Source URL:** https://arxiv.org/abs/2602.16891  
- **Reference count:** 38  
- **Primary result:** First AI‑centered ADK enabling autonomous agent construction achieves state‑of‑the‑art on CyberGym (60.2%), Terminal‑Bench 2.0 (78.4%), SWE‑Bench Pro (59.0%), and DevOps‑Gym (46.8%).

## Executive Summary
OpenSage addresses the limitation of existing Agent Development Kits (ADKs) that require manual design of agent topology, tools, and memory. It introduces the first AI‑centered ADK, allowing LLMs to autonomously construct agents with self‑generated topologies (dynamic sub‑agent creation supporting vertical/horizontal patterns and ensembles), dynamic tool synthesis (hierarchical organization, container isolation, async execution, plus a software‑engineering toolkit), and hierarchical graph‑based memory managed by a dedicated memory agent. Evaluated on CyberGym, Terminal‑Bench 2.0, SWE‑Bench Pro, and DevOps‑Gym, SageAgent outperforms prior SOTA agents. Ablations confirm the necessity of each component, demonstrating the viability of AI‑driven agent construction.

## Method Summary
OpenSage is built around three integrated capabilities.  
1. **Self‑generating agent topology**: a parent agent uses the `create_agent` tool to spawn sub‑agents at runtime, supporting vertical decomposition (sequential sub‑tasks) and horizontal parallelism (agent ensembles). Sub‑agents are managed in a unified pool with `run_agent`, `search_agent`, and `resume_agent` tools.  
2. **Dynamic tool synthesis**: meta‑tools like `create_tool` let agents write new tool modules, which are stored in a hierarchical file‑system registry. Tools declare environment requirements, triggering Docker container provisioning; long‑running tools execute asynchronously with background handles. A domain‑specific toolkit (e.g., Joern, AFL++) is included for software‑engineering tasks.  
3. **Hierarchical graph‑based memory**: short‑term memory is an execution graph (AgentRun, Event, RawToolResponse nodes) per agent; long‑term memory is a Neo4j graph with predefined node/edge types (e.g., `code_understanding`, `DEFINED_IN`). A specialized `memory_agent` mediates storage and retrieval via `save_memory` and `search_memory` tools. Together these components enable an LLM to autonomously build and execute complex agent workflows.

## Why This Works (Mechanism)

### Mechanism 1: Self‑Generating Agent Topologies
- **Claim:** AI‑generated agent topologies (vertical/horizontal) improve task decomposition and contextual isolation, enhancing adaptability and performance on complex, multi‑stage tasks.  
- **Mechanism:** A parent agent dynamically spawns sub‑agents via a `create_agent` tool, specifying their role, tools, and instructions. Sub‑agents execute in isolated memory contexts (graph nodes). A built‑in `agent_ensemble` tool enables parallel execution of multiple sub‑agents on the same task, with results aggregated.  
- **Core assumption:** LLMs can reliably self‑specify effective sub‑agent configurations (role, tools, instructions) for sub‑task decomposition.  
- **Evidence:** Abstract and Section 3.2; ablation in Figure 3 (left) shows performance drop when disabling vertical creation.  
- **Break condition:** LLM creates sub‑agents with mismatched toolsets or hallucinates non‑functional agents, leading to context overflow and performance drops (Appendix C.3).

### Mechanism 2: Dynamic Tool Synthesis
- **Claim:** Dynamic tool synthesis with hierarchical organization, container isolation, and async execution expands the agent’s actionable scope and handles conflicting dependencies, which static toolkits cannot.  
- **Mechanism:** Meta‑tools (e.g., `write_python_script`) let the agent create new tool modules. Tools are organized in a file‑system hierarchy for discovery. Each toolset declares environment requirements, triggering Docker container provisioning. Long‑running tools execute asynchronously, returning handles for polling.  
- **Core assumption:** LLMs can generate syntactically correct, functionally appropriate tool code and correctly specify its metadata (description, dependencies).  
- **Evidence:** Abstract and Section 3.3; ablation in Figure 3 (right) shows loss of performance without tool creation.  
- **Break condition:** Generated tools are buggy, have incorrect metadata, or require dependencies the system cannot provision, causing execution failures.

### Mechanism 3: Hierarchical Graph‑Based Memory
- **Claim:** A hierarchical, graph‑based memory system managed by a dedicated memory agent reduces redundancy, enables precise retrieval over long horizons, and supports structured knowledge persistence for coding tasks.  
- **Mechanism:** Short‑term memory is a graph of execution events per agent. Long‑term memory is a separate Neo4j graph with predefined node/edge types (e.g., `code_understanding`, `DEFINED_IN`). A `memory_agent` tool accepts natural language queries, decides target memory, and invokes graph‑based or embedding‑based retrieval tools.  
- **Core assumption:** An LLM given a constrained schema can correctly map findings to appropriate node/edge types and formulate effective retrieval queries.  
- **Evidence:** Abstract and Section 3.4; ablation vs. Mem0g (Figure 5) and LOCOMO (Table 4).  
- **Break condition:** Memory agent misclassifies findings, fails to create useful edges, or cannot formulate precise queries, causing relevant knowledge to be inaccessible.

## Architecture Onboarding
- **Component map:**  
  Parent Agent ↔ Sub‑Agent Pool; Parent Agent ↔ Tool Registry; Parent Agent ↔ Container Manager; Parent Agent ↔ Async Task Tracker; Parent Agent ↔ Memory Graphs; Parent Agent ↔ Memory Agent; Sub‑Agent ↔ Tool Registry; Sub‑Agent ↔ Container Manager; Memory Agent ↔ Memory Graphs; All agents and containers access Shared Workspace (Docker volume).  
- **Critical path:** User query → Parent Agent decides to decompose → `create_agent` spawns sub‑agent → Sub‑agent runs in its container with its toolset → Interactions and tool results logged in its short‑term graph → High‑signal findings proposed to `memory_agent` → `memory_agent` stores/updates long‑term graph → Later, parent/sub‑agent uses `search_memory` to retrieve relevant past findings.  
- **Design tradeoffs:**  
  - Flexibility vs. Overhead: Dynamic sub‑agent/tool creation adds orchestration latency but enables adaptation; container isolation adds startup cost but prevents dependency conflicts.  
  - Schema Rigidity vs. Generalization: Predefined memory node/edge types improve structure for coding tasks but may constrain other domains; system allows new types but lacks governance.  
  - Memory Agent Intelligence: Delegating memory ops to a separate LLM agent adds a reasoning hop but prevents direct manipulation of the complex graph schema by task agents.  
- **Failure signatures:**  
  - Topology misuse: frequent `create_agent` calls with generic instructions or tool lists; agent ensemble used unnecessarily.  
  - Tooling failure: meta‑tools produce syntactically invalid modules; container spin‑up failures; async tasks never terminate.  
  - Memory failure: `memory_agent` queries return empty/noise; long‑term graph filled with uncategorized nodes; short‑term graphs lack cross‑agent edges.  
- **First 3 experiments:**  
  1. **CyberGym subset (300 tasks):** Disable `create_agent` (NoVertical). Expect increase in summarization events and context overflow errors vs. full system; performance drop per Figure 3 (left).  
  2. **SWE‑Bench Pro:** Disable long‑term memory (NoMem). Measure ability to recall similar code patterns/errors across a long trajectory. Expect performance drop vs. full system (Figure 5).  
  3. **Tool creation probe:** On a task requiring a custom parser, inspect tool registry hierarchy. Verify agent uses meta‑tool to create new parsing tool, registers under logical category, and subsequent calls succeed in container.

## Open Questions the Paper Calls Out
- **AI‑generated workflows:** Extend OpenSage to support AI‑generated workflows with explicit dependencies and communication protocols across agents. Currently lacks primitives for coordinating complex multi‑agent workflows.  
- **Integration with reinforcement learning and post‑training:** Provide rollout interfaces for frameworks (AReaL, verl, LlamaFactory) and a Kubernetes‑based sandbox backend for large‑scale data collection and training on real‑world tasks.  
- **Consistent utilization of advanced features:** Even SOTA models do not consistently or correctly use advanced features (dynamic tool creation, agent ensemble, hierarchical memory) without hallucination or misuse. Need training/dataset to improve.  
- **Domain adaptation:** Automatically adapt domain‑specific toolkits and memory schemas to non‑software‑engineering domains (e.g., scientific computing) without manual redesign; automatic induction process remains unevaluated.

## Limitations
- No code release; key implementation details (tool registration, memory schema) missing.  
- Evaluation transparency low: baselines, time/compute limits, prompts unreported.  
- Memory schema appears domain‑specific (fixed node types for coding), limiting generalization.  
- Hallucination risks: sub‑agent tool mismatches, non‑existent tool calls.  
- Reliance on proprietary frontier models hinders replication.

## Confidence
- Self‑generating topologies: **Medium** (ablation supports but no independent replication).  
- Dynamic tool synthesis: **Medium** (ablation gain, but tool generation correctness unverified).  
- Hierarchical memory: **Medium** (ablation vs. Mem0g/LOCOMO positive, but memory agent errors possible).  
- Overall SOTA claims: **Medium** (results strong but reproducibility compromised).
