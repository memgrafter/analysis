# EvoSkill: Automated Skill Discovery for Multi-Agent Systems

## Quick Facts
- arXiv ID: 2603.02766
- Source URL: https://arxiv.org/abs/2603.02766
- Reference count: 40
- Primary result: Improves exact-match accuracy by 7.3 percentage points on OfficeQA (60.6→67.9%) and by 12.1 points on SealQA (26.6→38.7%), with zero-shot transfer to BrowseComp (+5.3%).

## Executive Summary
EvoSkill tackles the challenge of hand-crafted, non-transferable agent skills by introducing an automated, iterative loop that discovers and refines reusable capabilities through failure analysis. The system uses a Proposer agent to diagnose execution failures and generate skill proposals, a Skill-Builder to materialize them into structured modules, and a Pareto frontier to retain only those programs that improve held-out validation performance while the base model remains frozen. Empirical results on two question-answering benchmarks show substantial absolute gains (OfficeQA +7.3%, SealQA +12.1%), and skills evolved on SealQA transfer zero-shot to BrowseComp, demonstrating the emergence of generalizable skill-level optimization.

## Method Summary
EvoSkill splits task data into a small stratified training batch (5-15%) and a fixed validation set. It maintains a frontier of top-k programs, each comprising the frozen base model plus a set of evolved skills. Each iteration selects a parent from the frontier (round-robin), executes the training batch with the Executor agent, and collects failures (examples where the fuzzy-scored output falls below a threshold). The Proposer examines these failures and the feedback history to propose a new or edited skill. The Skill-Builder then writes the proposal into a standardized skill folder (including SKILL.md and scripts). The candidate program (parent plus new skill) is evaluated on the full validation set. If its score exceeds the lowest frontier member, it replaces that member; otherwise it is discarded. The loop runs for a predetermined number of iterations (1.5 epochs) or until convergence.

## Key Results
- OfficeQA: +7.3% absolute exact-match (60.6% → 67.9%).
- SealQA: +12.1% absolute exact-match (26.6% → 38.7%).
- Zero-shot transfer: SealQA-evolved skills improve BrowseComp by +5.3% without modification.

## Why This Works (Mechanism)
### Mechanism 1: Failure-Driven Skill Induction
The Proposer diagnoses execution failures to generate targeted skill modifications. By converting error analysis into an automated mutation operator, the system focuses improvement on systematic capability gaps. Core assumption: failures on a held-out validation set reveal reproducible weaknesses addressable by modular skill edits. Evidence: abstract and section 2.2 describe the failure analysis loop; break condition if proposals become irrelevant.

### Mechanism 2: Pareto-Guided Skill Retention
A Pareto frontier selects only those candidate programs that achieve higher validation scores than the current weakest member. This prevents skill bloat and regressions, ensuring that the model remains frozen while only validated improvements are kept. Core assumption: validation performance is a sufficient proxy for generalizable gains. Evidence: abstract and Algorithm 1 lines 11-15; break condition if frontier saturates with minimally distinct skills.

### Mechanism 3: Skill Abstraction Enables Transfer
Skills are encapsulated as portable modules (folders with metadata, instructions, scripts) that follow a standardized specification. This structure decouples skills from specific prompts/models, allowing them to be invoked unchanged in new tasks. The observed zero-shot transfer from SealQA to BrowseComp demonstrates this. Core assumption: skills encode domain-agnostic workflows. Break condition: if skills are overly tied to training artifacts, they fail to trigger on new tasks.

## Foundational Learning
### Textual Feedback Descent
Textual feedback from the Proposer acts as a mutation operator, distinct from gradient-based optimization. It provides sparse but interpretable signals. Quick check: How does textual feedback differ from scalar rewards in terms of sparsity and interpretability?

### Pareto Frontier Maintenance
The frontier balances exploration and exploitation; only a fixed number of top programs are retained. Quick check: Why use a Pareto frontier (top-k) instead of always accepting any improvement on the validation set?

## Architecture Onboarding
### Component Map
Executor (A) -> Proposer (P) -> Skill-Builder (S) -> Frontier Manager; Feedback History (H) and Validation Set (V) are shared resources.

### Critical Path
Parent selection (from frontier) -> Execute training batch (A) -> Collect failures -> Proposer generates proposal (P) -> Skill-builder builds skill (S) -> Evaluate candidate on V -> Frontier manager updates frontier if improved. All changes are validated against V before adoption.

### Design Tradeoffs
- Frozen model vs. skill expressiveness: keeping model weights fixed limits adaptation breadth but ensures stability and portability.
- Frontier size (k): small k speeds convergence but risks premature convergence; large k increases diversity and compute cost.
- Training data size: small splits (5-15%) reduce risk of overfitting skills to a specific task distribution.

### Failure Signatures
- Frontier stagnation: multiple iterations without improvement; proposer may be generating redundant skills.
- Skill explosion without gain: frontier fills with many skills but scores do not increase; skills may be irrelevant or conflicting.
- Overfitting on training failures: skills fix training examples but degrade validation performance.

### First 3 Experiments
1. Baseline: Run Executor without skills on the held-out test set to establish reference scores.
2. Single-iteration trace: Execute one full evolution iteration; inspect the proposed skill and its validation score delta to verify proposer/skill-builder functionality.
3. Ablation: Vary frontier size (k=1,3,5) to observe impact on diversity and convergence; expect diminishing returns beyond k=3.

## Open Questions the Paper Calls Out
1. **Cross-domain generalizability:** To what extent do discovered skills generalize across diverse domains (e.g., financial, medical, legal)? Evidence needed: run EvoSkill on multiple new benchmarks, cluster skills by applicability, and measure cross-domain transfer.
2. **Multi-modal extension:** Can EvoSkill discover skills that integrate vision, language, and code for heterogeneous inputs? Evidence: implement a multi-modal variant on benchmarks like VQA with figures/tables and demonstrate cross-modal workflows.
3. **Shared skill repositories:** How can skills be shared, composed, and reused across agents/users? Evidence: build a public skill registry API, allow upload/import, and measure performance gains from skill composition on unseen tasks.
4. **Transfer success factors:** Under which conditions do skills transfer zero-shot across tasks, models, or harnesses? Evidence: systematic experiments transferring skills across varied task pairs, base LLMs, and agent frameworks, with analysis of skill attributes predicting transfer success.

## Limitations
- Full agent prompts (Proposer, Skill-Builder) are undisclosed, hindering exact replication.
- Scorer implementation (fuzzy matching) is underspecified; tolerances and unit handling unclear.
- Key hyperparameters, randomness controls, and validation set sizes are not reported.
- Risk of overfitting to training failures and frontier saturation without diagnostics.

## Confidence
- Failure-driven skill induction: Medium
- Pareto-guided skill retention: Medium
- Skill abstraction enables transfer: Low
