# VehicleMemBench: An Executable Benchmark for Multi-User Long-Term Memory in In-Vehicle Agents

## Quick Facts
- arXiv ID: 2603.23840
- Source URL: https://arxiv.org/abs/2603.23840
- Reference count: 40
- Primary result: Top models achieve 90.60 Exact State Match with gold memory but drop to 64.80 with autonomous memory; Memory Error accounts for 63.9% of failures.

## Executive Summary
VehicleMemBench introduces the first executable benchmark for assessing multi-user long-term memory in in-vehicle agents. It combines temporally interleaved event chains (average 81.78 events per sample) spanning five preference evolution types with a rich vehicle simulation (23 modules, 111 APIs). Agents must ingest dialogue histories (~92k tokens), retrieve relevant memories, and manipulate the simulated vehicle via tool calls to reach a target state, which is compared against a reference state via Exact State Match (ESM). Findings reveal that while oracle (gold) memory enables near-perfect performance (up to 90.60 ESM), autonomous memory systems suffer a significant drop to 64.80 for the best model, with memory retrieval errors responsible for nearly two-thirds of failures. General-purpose memory systems underperform simple baselines, and queries involving conditional constraints prove universally challenging. The benchmark thus highlights memory construction and retrieval as the primary bottleneck in real-world in-vehicle agent deployment.

## Method Summary
The benchmark evaluates agents through a two-stage loop. First, the agent ingests a lengthy dialogue history into its chosen memory system. Then, it engages in up to 10 interaction rounds: retrieving memories, generating tool calls (APIs) to modify the vehicle state, and observing the resulting state. The task is to derive the correct final state from a user query that often requires integrating evolving multi-user preferences. The dataset comprises 500 queries across 50 scenarios, each containing ~30 interleaved event chains covering five types of preference evolution. The simulation includes 23 vehicle modules and 111 executable APIs. Performance is measured primarily by Exact State Match (ESM) between the agent-produced and reference states, with secondary metrics (Field-F1, Value-F1) and MemoryScore (autonomous vs. gold memory ratio) providing finer-grained insights.

## Key Results
- State-of-the-art LLM (Gemini-3-Pro-Preview) attains 90.60 ESM with gold memory but only 64.80 ESM using its own memory, with Memory Error causing 63.9% of failures.
- General-purpose memory systems (e.g., MemOS, Mem0) underperform even simple baselines (Recursive Summarization, Key Value Store), indicating domain-specific memory design matters.
- Conditional Constraint queries—where preferences apply only under specific contexts (e.g., time, location, activity)—are the hardest across all models; without any memory, all agents score below 20 ESM, confirming the benchmark’s demand for long-term memory.

## Why This Works (Mechanism)
VehicleMemBench effectively isolates long-term memory challenges by decoupling memory construction from execution in a grounded, executable environment. The use of temporally interleaved event chains forces agents to resolve conflicting preferences across users and time, mirroring real in-vehicle multi-user scenarios. The simulation’s deterministic state transitions and comprehensive API suite provide an objective, checkable outcome (the final state), unlike open-ended text generation. Moreover, the benchmark includes a gold memory condition to separate memory errors from execution deficiencies, and its design yields fine-grained failure categories (memory, execution, conditional constraints) that pinpoint exactly where current systems falter.

## Foundational Learning
**Temporal Event Chains** – Why needed: They capture how user preferences evolve over time and interleave across users, requiring agents to track and reconcile changes. – Quick check: Does the memory contain the most recent preference for each attribute in the correct temporal order?

**Multi-User Preference Distinction** – Why needed: Agents must correctly attribute preferences to the right user and apply them only when that user is active or when preferences overlap. – Quick check: Can the agent retrieve a preference specific to user A while ignoring conflicting preferences from user B?

**State-Based Grounded Evaluation** – Why needed: An exact state match provides an unambiguous correctness signal, avoiding the ambiguities of free-form language evaluation. – Quick check: Does the final simulated environment exactly match the reference state on all fields?

**Tool-Augmented Agent Capability** – Why needed: In-vehicle tasks require invoking precise APIs with valid parameters; memory alone is insufficient. – Quick check: Are all generated tool calls syntactically correct, semantically valid, and within parameter constraints?

**Conditional Preference Application** – Why needed: Many preferences depend on context (time, location, activity); misapplying them leads to silent errors. – Quick check: Does the agent apply a preference only when all its stated conditions are satisfied?

## Architecture Onboarding
Component map (plain text): Event Chain Generator -> Dialogue Simulator -> Memory Ingestor -> Agent (Retriever + Planner) -> Vehicle Simulation Engine -> State Evaluator. The Memory Ingestor writes to a unified search interface that the Agent’s Retriever queries during interaction.

Critical path: (1) Generate scenario (event chains + dialogue). (2) Ingest dialogue into memory system. (3) Given a query, retrieve relevant memories. (4) Plan a sequence of tool calls to achieve the target state. (5) Execute calls via Vehicle Simulation. (6) Compare produced state to reference via ESM.

Design tradeoffs: 
- Temporal interleaving increases cognitive load but better reflects real-world usage. 
- High dialogue token count stresses memory capacity and LLM context limits; using summarization vs. raw storage trades detail for efficiency. 
- Simulation fidelity (23 modules, 111 APIs) improves realism but raises hardware costs and integration complexity. 
- Gold memory vs. autonomous memory gap exposes difficulty of automatic memory construction; designs could prioritize robustness over compression.

Failure signatures:
- Memory Error: Retrieved content does not reflect the latest or contextually appropriate preferences; often due to outdated or noisy memory.
- Execution Error: Invalid API calls, parameter mismatches, or premature termination; indicates planner or tool interface issues.
- Conditional Constraint Failure: Preference applied outside its required context (e.g., temperature setting at wrong time).
- Field-Value Mismatch: Correct field/device selected but wrong value assigned; signals granularity loss in memory or planning.

First experiments:
1. Run the baseline Recursive Summarization memory on a small (5-scenario) subset and verify the pipeline end-to-end, logging ESM and memory/token counts.
2. Execute the same subset with gold memory (oracle) to isolate execution capability; expect near-perfect ESM. This confirms simulation and evaluation correctness.
3. Focus exclusively on Conditional Constraint queries (choose a subset) to diagnose failure patterns; compare retrieval content against ground truth conditional rules.

## Limitations
- Incomplete specification of API schemas, state representation, and prompt templates hinders exact replication.
- Simulation hardware requirements and execution speed are undocumented, making local deployment uncertain.
- Very long dialogues (~92k tokens) and reliance on proprietary LLMs limit accessibility and large-scale validation.

## Confidence
- Benchmark Construction (temporal interleaving, preference types, simulation scale): Medium
- Evaluation Protocol (two-phase loop, state-based metrics): Medium
- Quantitative Results (ESM scores, failure breakdown): Low
- Qualitative Findings (memory bottleneck, conditional constraints hardest): Medium
