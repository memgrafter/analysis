# Bandwidth-adaptive Cloud-Assisted 360-Degree 3D Perception for Autonomous Vehicles

## Quick Facts
- **arXiv ID:** 2602.23871  
- **Source URL:** https://arxiv.org/abs/2602.23871  
- **Reference count:** 40  
- **Primary result:** Achieves a 72% reduction in end-to-end latency versus onboard-only processing and improves accuracy by up to 20% over static configurations while meeting a 100 ms latency bound.

## Executive Summary
This paper tackles the latency-accuracy trade-off in autonomous driving perception by proposing a bandwidth-adaptive cloud-assisted hybrid computing framework that dynamically partitions computation of the BEVFormer model between the vehicle and the cloud. The system uses real-time bandwidth estimation to choose the optimal split layer and feature quantization level, applying post-training quantization, percentile clipping, and lossless compression to minimize transmission overhead while preserving detection accuracy. A constrained optimization algorithm selects the configuration that maximizes the nuScenes Detection Score (NDS) under a strict 100 ms end-to-end latency bound. Real-world V2X experiments with a prototype implementation on a Jetson Orin and a cloud GPU server show a 72% reduction in end-to-end latency compared to processing everything onboard. Trace-based evaluations under realistic 5G bandwidth variability reveal that the adaptive strategy improves accuracy by up to 20% over static split configurations while maintaining the latency constraint, demonstrating robustness to network fluctuations.

## Method Summary
The proposed system leverages BEVFormer, a state-of-the-art 3D object detector that fuses multi-camera images into a bird's-eye-view representation. The model is partitioned at an adjustable layer: early layers run on the vehicle, producing intermediate features. These features undergo post-training quantization (FP32/FP16/FP8), percentile-based clipping (removing values below the 10th and above the 90th percentiles), and zlib compression to drastically reduce size (up to 97% reduction). The compressed payload is transmitted over C-V2X to a cloud server, which executes the remaining layers and the detection head. The cloud then sends back detection results (e.g., CPM messages) to the vehicle. A profiling phase measures for each (split layer, quantization) combination the local processing time, cloud processing time, feature size, and resulting NDS on the nuScenes validation set. This data is sorted in descending NDS order. At runtime, a dynamic optimizer estimates the current uplink bandwidth and computes total latency for each configuration as local + transmission (based on feature size and bandwidth) + cloud + downlink. Starting from the highest-NDS configuration, it selects the first tuple that meets the latency bound; if none satisfy, it chooses the one with minimal total latency. This approach ensures maximal accuracy given the network condition while guaranteeing real-time performance.

## Key Results
- 72% reduction in end-to-end latency compared to onboard-only processing (from 194 ms to 61.9 ms in optimal configuration).
- Up to 20% improvement in NDS over static configurations under varying bandwidth while adhering to a 100 ms latency constraint.
- The adaptive system maintains robustness to realistic 5G bandwidth fluctuations, avoiding latency violations that plague static setups.

## Why This Works (Mechanism)

### Dynamic Parameter Selection for Accuracy-Latency Optimization
The system maximizes detection accuracy (NDS) under a strict end-to-end latency bound by adaptively selecting the split layer and quantization level based on real-time bandwidth estimates. A pre‑sorted array of (split, quantization) tuples ordered by NDS is maintained. For each perception cycle, estimated uplink/downlink bandwidths are used to compute total latency (local processing + transmission + cloud processing) for each tuple. The first tuple satisfying the latency constraint is chosen; if none satisfy, the tuple with minimum latency is selected. This ensures the highest possible accuracy given current network conditions. The core assumptions are that latency components can be accurately profiled offline and that bandwidth estimation reliably predicts transmission latency. Evidence includes the formal problem formulation, the correctness theorem for the selection algorithm, and trace‑based simulations showing consistent gains over static baselines. Break condition: Inaccurate bandwidth estimates or profiled latencies that do not generalize to new conditions may cause latency violations or suboptimal accuracy.

### Lightweight Feature Offloading via Quantization, Clipping, and Compression
Applying post‑training quantization, percentile‑based clipping, and lossless compression to intermediate feature tensors dramatically reduces their size, enabling feasible transmission over bandwidth‑limited V2X links. After extracting features at the split point onboard, the tensor is quantized (FP32/FP16/FP8), clipped by removing values below the 10th and above the 90th percentiles, and compressed with zlib. This reduces entropy and size; experiments show up to 97% reduction for FP32. The compressed payload is transmitted via C‑V2X. The core assumption is that feature tensors contain statistical redundancy such that clipping and lossless compression yield significant size reduction, and the information loss from quantization and clipping does not catastrophically degrade detection accuracy, especially for shallower splits. Evidence includes the algorithm details, measured size reductions, and acceptable NDS preservation for viable configurations. Break condition: If feature tensors are already low‑entropy, compression ratios drop; aggressive clipping may remove salient features, particularly for deeper splits, leading to accuracy cliffs under very limited bandwidth.

### Hybrid Computing to Leverage Cloud Resources
Partitioning the BEVFormer model so that early layers run onboard and remaining layers run on a cloud server reduces overall end‑to‑end latency by utilizing the cloud's superior compute while minimizing onboard processing. The vehicle performs lightweight feature extraction (up to a split layer) using its GPU; the extracted feature tensor is transmitted to the cloud, which runs the rest of the model and the detection head. The cloud's powerful GPUs process the features much faster than the onboard hardware could process the full model, and transmission latency is mitigated by compression. The core assumptions are that the cloud has readily available compute resources and that the network latency (including transmission and cloud queuing) is low enough that the sum of local processing and transmission is less than full onboard inference. Evidence includes hardware specs (Jetson Orin vs. Tesla V100), profiling results showing end‑to‑end delays as low as 61.9 ms vs. 194 ms onboard, and trade‑off analyses. Break condition: If the cloud is heavily loaded or network latency is high, transmission plus cloud processing may exceed the latency bound, making offloading worse than onboard; packet loss could break real‑time guarantees.

## Architecture Onboarding

**Component Map**  
6 Cameras -> Onboard Jetson Orin (feature extraction, quantization, clipping, compression) -> C‑V2X Uplink -> Cloud Server (decompression, remaining BEVFormer layers, detection) -> CPM Message -> ITS‑G5 Broadcast -> Receiving Vehicles.

**Critical Path**  
1. Capture multi‑camera images.  
2. Onboard feature extraction (layers 1 .. split).  
3. Clip and compress feature tensor.  
4. Transmit compressed tensor to cloud (V2C).  
5. Cloud decompresses and runs layers (split+1 .. n) plus BEVFormer remainder.  
6. Cloud encodes detection results into CPM.  
7. Cloud broadcasts CPM to vehicles (C2V) via V2X.  
8. Total time must be ≤ latency bound (e.g., 100 ms).

**Design Tradeoffs**  
- *Split depth:* Shallower splits reduce onboard compute but increase transmission size/latency; deeper splits increase onboard compute but reduce transmission. Optimal split depends on relative compute speeds and network bandwidth.  
- *Quantization precision:* Lower precision (FP8) reduces compute and transmission size but may degrade accuracy; higher precision (FP32) preserves accuracy but increases latency.  
- *Clipping aggressiveness:* Wider clipping ranges reduce size more but risk losing important features. Fixed 10th/90th percentiles used as tradeoff.  
- *Adaptive vs static:* Adaptive requires profiling and bandwidth estimation overhead but yields higher accuracy under variable networks; static is simpler but may violate latency or underutilize bandwidth.

**Failure Signatures**  
- *Latency violations:* End‑to‑end delay exceeds bound. Causes: high transmission latencies, cloud overload, mis‑estimated bandwidth leading to infeasible configuration.  
- *Degraded accuracy (NDS drop):* Possibly due to too deep split or too low quantization under low bandwidth forcing low‑accuracy modes.  
- *High packet loss:* V2X communication fails, causing missing frames.  
- *Profiling mismatch:* Actual latency components deviate from profiled values (e.g., hardware changes), causing suboptimal configuration selection.

**First 3 Experiments**  
1. **Onboard baseline profiling:** Run BEVFormer on Jetson Orin with different quantizations (FP32, FP16, FP8) on nuScenes to measure inference time and NDS. Establishes need for offloading.  
2. **Hybrid static configuration validation:** Choose fixed split and quantization, run full pipeline with real/emulated V2X over a short route. Measure end‑to‑end latency and NDS to validate pipeline and communication overhead.  
3. **Dynamic selection simulation:** Use recorded bandwidth trace (e.g., Porto dataset) and simulate the dynamic algorithm offline. Compare achieved accuracy and latency violations against best static configuration for average bandwidth. Verifies adaptive logic without moving vehicle.

## Open Questions the Paper Calls Out
1. **Multi‑vehicle cooperative perception under interference:** How does the dynamic selection perform in real‑world multi‑vehicle scenarios with high interference, contention, and rapid topology changes? Current evaluation is trace‑based and does not account for multi‑vehicle interactions.  
2. **5G network slicing integration:** To what extent can URLLC slices improve robustness and predictability of the hybrid perception system under dynamic network conditions? The paper suggests combining with 5G slicing but does not evaluate it.  
3. **Generalizability to other BEV detectors:** How effectively can the dynamic selection framework be applied to alternative BEV detectors or backbone architectures without extensive re‑profiling? The optimizer is claimed architecture‑agnostic but only BEVFormer‑ResNet101 is evaluated.  
4. **Sensitivity to bandwidth estimation errors:** How sensitive is the algorithm to inaccuracies in real‑time bandwidth estimation? The algorithm assumes a reliable estimator but provides no analysis of error impact.

## Limitations
- **Trace availability & generalization:** Evaluation relies on a specific 5G uplink trace from Porto; its representativeness of other urban/highway environments is unclear.  
- **Feature compression assumptions:** The clipping/compression pipeline is tuned on nuScenes; may not generalize to other datasets or extreme scenes, potentially causing accuracy cliffs when forced into lower‑bandwidth modes.  
- **Cloud & network model simplifications:** The latency model ignores real‑world cloud queueing, server load fluctuations, and V2X protocol overhead, which could violate the 100 ms bound in practice.

## Confidence
- **Dynamic Parameter Selection:** High Confidence (formally defined algorithm, correctness theorem, trace‑based gains).  
- **Lightweight Feature Offloading:** Medium Confidence (strong evidence of size reduction and manageable NDS degradation, but break conditions under aggressive clipping not fully stress‑tested).  
- **Hybrid Computing Latency Reduction:** Medium Confidence (testbed results show significant reduction, but lacks real‑world cloud load testing and sensitivity to packet loss).

## Next Checks
1. **Compression Generality Test:** Re‑implement the clipping/compression pipeline and measure compression ratio and NDS degradation on a different multi‑camera dataset (e.g., KITTI‑360, Waymo Open) to assess generalization.  
2. **Optimizer Robustness to Noisy Bandwidth:** Run the dynamic selection with synthetically corrupted bandwidth traces (Gaussian noise, delayed estimates, sudden 50% drops) to quantify latency bound violations and NDS drops.  
3. **Cloud Queueing Impact Measurement:** In a controlled testbed, inject artificial load on the cloud server, measure tail latency (p99) for cloud processing, and compare to profiled constant values to evaluate impact on feasibility.
