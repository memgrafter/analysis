# A Self-Evolving Defect Detection Framework for Industrial Photovoltaic Systems

## Quick Facts
- **arXiv ID:** 2603.14869
- **Source URL:** https://arxiv.org/abs/2603.14869
- **Reference count:** 29
- **Primary result:** SEPDD achieves 91.4% mAP50 on public PVEL-AD (+4.7% over human experts) and 49.5% mAP50 on a private industrial dataset (+2.5% over human experts, +4.9% over AIDE).

## Executive Summary
This paper tackles robust automated defect detection in industrial photovoltaic (PV) systems, where real-world challenges include long-tailed defect distributions, imaging condition shifts, and the emergence of new defect categories. The authors propose SEPDD, a self-evolving framework that combines automated model optimization with a continual adaptation loop triggered by performance degradation or label evolution. SEPDD integrates large language model (LLM) powered operators within a graph-based search to iteratively generate, validate, and refine detection models. It sets new state-of-the-art results on a public PV defect benchmark and a private industrial dataset, significantly outperforming human experts and prior autonomous systems, while demonstrating enhanced resilience to newly emerging rare defects.

## Method Summary
SEPDD addresses PV defect detection in electroluminescence (EL) images using two datasets: public PVEL-AD (4,050 train, 450 test) and private EF Industrial (814 train, 90 test). Both exhibit severe class imbalance and domain shift. The framework operates via trigger-driven evolution: monitors detect conditions like validation mAP50 drop or changes in label sets, activating a graph-based search. Each search node employs an LLM-powered pipeline—Idea Generator, Code Creator, Analyzer, Code Refiner—in a validate→execute→refine loop. Parent models are selected from a top-k journal of past nodes; a merge operator periodically synthesizes a new candidate by prompting an LLM with summaries of top parents' strengths/weaknesses. Base models are from the YOLO family (v8m/v11l), with LLMs Qwen3-coder-plus for code and Qwen3.5-plus for analysis. Invalid code terminates nodes; successful candidates update the journal.

## Key Results
- On public PVEL-AD, SEPDD achieves **91.4% mAP50**, exceeding human expert performance by **+4.7%**.
- On private EF Industrial, SEPDD reaches **49.5% mAP50**, leading by **+2.5%** over human experts and **+4.9%** over the autonomous AIDE baseline.
- In simulated scenarios with newly emerging rare defects, SEPDD shows **superior resilience** compared to static and periodically retrained models.

## Why This Works (Mechanism)
SEPDD’s effectiveness stems from its closed-loop adaptation to non-stationary industrial conditions. The trigger system ensures evolution is activated precisely when the current model degrades or the defect taxonomy evolves, avoiding unnecessary retraining. The graph-based search with LLM operators automates the exploration of model architectures, training schedules, and augmentation strategies tailored to long-tailed PV data. Knowledge-based prompts inject domain constraints (e.g., typical defect morphologies, sensor limitations), guiding the LLM toward feasible and relevant modifications. The merge operator enables synergistic combination of complementary parent models, accelerating convergence on robust solutions. This design balances automation with domain awareness, allowing SEPDD to autonomously correct for data shift and incorporate new defect categories without manual intervention.

## Foundational Learning
- **Long-tailed data distribution:** Real-world PV defect datasets have extreme class imbalance (e.g., cracks vs. inactive modules). *Why needed:* Rare defects are often safety-critical but underrepresented. *Quick check:* Class frequency histogram shows a heavy tail; baseline models have low recall on tail classes.
- **Domain shift:** EL image characteristics vary across production lines, cameras, and environmental conditions. *Why needed:* Models trained on one factory fail on another. *Quick check:* Performance drops significantly when testing on data from a different source.
- **Continual/lifelong learning:** New defect types (e.g., from panel aging) appear over time. *Why needed:* Static models become obsolete. *Quick check:* Cumulative error on newly introduced classes increases without adaptation.
- **LLM-based code generation:** LLMs propose and generate training scripts, augmentation pipelines, and model modifications. *Why needed:* Automates the search for optimal configurations in a vast space. *Quick check:* Generated code executes without syntax errors and yields valid training runs.
- **Knowledge-based AI:** Domain expertise (e.g., physical defect characteristics, operational constraints) is encoded in prompts. *Why needed:* Constrains LLM search to plausible PV-specific solutions, improving sample efficiency. *Quick check:* LLM suggestions respect PV defect semantics (e.g., crack continuity, cell-level patterns).
- **Graph-based evolutionary search:** Models are nodes; edges represent merge or mutation operations. *Why needed:* Enables systematic exploration and combination of promising solutions. *Quick check:* Search graph shows multiple nodes improving validation mAP before converging.

## Architecture Onboarding
- **Component map:** Triggers (performance drop, label change) → Journal (stores node metadata) → Graph Search (selects top-k parents) → Merge Operator (LLM synthesizes new candidate) → LLM Operators (Idea Generator → Code Creator → Validation → Analyzer → Code Refiner) → New Node (trained model) → Evaluation → Journal update. Base model (YOLO) is initialized from parent or scratch.
- **Critical path:** 1) Monitor validation metrics and label set. 2) On trigger, select top-k parents from journal. 3) Merge operator generates candidate via LLM with parent summaries. 4) Code Creator produces training script; validation executes training and evaluation. 5) Analyzer interprets results; Code Refiner iterates if needed. 6) If candidate outperforms thresholds, add as new node.
- **Design tradeoffs:** 
  - *LLM autonomy vs. control:* High autonomy increases innovation risk (invalid code); domain prompts mitigate but require crafting.
  - *Search breadth vs. compute:* More nodes and deeper validation improve solutions but increase token/GPU cost; SEPDD limits per-node validation and uses top-k selection.
  - *Knowledge injection vs. over-constraint:* Rich domain knowledge speeds convergence but may blind search to novel patterns.
- **Failure signatures:** 
  - High node termination rate due to syntactically invalid or runtime-error code.
  - Degenerate pipelines that overfit head classes and ignore tail/rare defects (per-class recall plateaus).
  - Trigger sensitivity issues: frequent false positives (wasted compute) or false negatives (missed adaptation).
- **First experiments:**
  1. **Baseline replication:** Run AIDE on PVEL-AD; confirm ~76.6% mAP50 to establish reference.
  2. **SEPDI integration:** Add trigger monitors and journal to AIDE; run for 10 evolution cycles; measure node acceptance rate and validation mAP trajectory.
  3. **Knowledge ablation:** Disable domain-specific prompts in Idea Generator; compare convergence speed and tail-class recall on PVEL-AD.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can SEPDD be extended to multimodal PV inspection data (e.g., combining EL with infrared or visible-light imagery) while maintaining its self-evolving adaptation capabilities? *Basis:* Conclusion explicitly states future work on multimodal inspection. *Why unresolved:* Current framework is designed for single-modality EL; multimodal integration introduces feature alignment and new trigger design challenges. *What evidence would resolve:* Evaluate a multimodal SEPDD variant on paired datasets, measuring detection of cross-modal ambiguous defects.
- **Open Question 2:** What are the precise algorithmic definitions and empirical thresholds for the trigger conditions (e.g., performance degradation, label evolution)? *Basis:* Section III.A lists triggers but provides no quantitative criteria. *Why unresolved:* Lack of thresholds hinders deployment; sensitivity unknown. *What evidence would resolve:* Ablation studies varying trigger parameters (mAP drop percentage, new label count) on industrial dataset, reporting performance vs. computational cost.
- **Open Question 3:** How is external domain knowledge formally encoded into SEPDD's knowledge base and how does its quality/quantity affect adaptation to rare or new defects? *Basis:* Framework described as "knowledge-based"; prompts include "Domain specific code" and "Task Knowledge" (Fig. 1) but no structural analysis. *Why unresolved:* Contribution of knowledge vs. automated search is unclear; limits transferability. *What evidence would resolve:* Controlled experiments varying knowledge base content (full rules vs. minimal vs. none) on label-evolution simulations, measuring recall on rare defects and search convergence.
- **Open Question 4:** What is the computational cost-benefit trade-off of SEPDD's self-evolving loop compared to simpler periodic retraining, and under what operational conditions does its overhead become justified? *Basis:* Token usage reported (~50% more than AIDE) but no cost-benefit analysis vs. naive strategies. *Why unresolved:* Practitioners need to know if complexity is worthwhile. *What evidence would resolve:* Simulate long-term deployment with shifts; compare SEPDD against fixed-interval full retraining and degradation-triggered static retraining, plotting average mAP vs. cumulative compute.

## Limitations
- **Major unknowns:** Exact LLM prompt templates and system rules are undisclosed; per-dataset hyperparameter schedules (specific YOLO version, learning rates, augmentation mixes) for final models are missing.
- **Reproducibility risk:** Results depend on specific, potentially gated LLMs (Qwen3-coder-plus, Qwen3.5-plus); search stability and convergence properties not fully characterized; private dataset composition and human expert baseline protocol are opaque.
- **Operational clarity:** Trigger thresholds undefined, risking sensitivity issues (too sensitive or too slow) in real-world deployment.
