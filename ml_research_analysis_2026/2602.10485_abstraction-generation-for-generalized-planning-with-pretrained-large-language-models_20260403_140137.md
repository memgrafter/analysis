# Abstraction Generation for Generalized Planning with Pretrained Large Language Models

## Quick Facts
- **arXiv ID**: 2602.10485
- **Source URL**: https://arxiv.org/abs/2602.10485
- **Reference count**: 8
- **Primary result**: With automated debugging, GPT-5.2 achieves 100% coverage on Delivery, Heavy, Ferry; 85% on Gripper; 40% on Miconic; 0% on Spanner and Forest. Debugging significantly improves coverage over direct generation.

## Executive Summary
This paper explores whether pretrained large language models (LLMs) can generate Qualitative Numerical Planning (QNP) abstractions for generalized planning (GP). The authors propose a structured prompt protocol that decomposes the task into generating abstract features (boolean existential and numerical counting formulas) and projecting domain elements onto those features to form a QNP problem. To ensure the abstractions are approximately sound on a finite training set, they introduce an automated debugging cycle that leverages the DSET solver and a series of checks—Abstraction Solvability Check (ASC), HL Instance Check (HLISC), HL Plan Refinement Check (HLPRC), and LL Goal Reachability Check (LLGRC)—to detect and localize errors, then prompt the LLM to repair them. Evaluated across seven GP domains using four LLMs (including GPT-5.2 and Gemini-3), the approach yields near-perfect coverage on three domains and substantial improvements when debugging is enabled, demonstrating that LLMs can produce useful abstractions with appropriate guidance. Failures on Spanner and Forest highlight limitations of the QNP formalism and current templates.

## Method Summary
The method takes a PDDL domain file and a set of training problem instances. In the first stage, the LLM is prompted to generate QNP abstract features: boolean features of the form `p ≜ ∃⃗x. ϕ(⃗x)` and numerical features `n ≜ #⃗x. δ(⃗x)`, where ϕ and δ are first-order formulas over domain predicates. In the second stage, the LLM abstracts the initial states, actions, and goal conditions into a QNP problem `⟨S0, SG, A_h⟩` and defines a refinement mapping `m` that interprets abstract variables and actions in terms of concrete predicates and actions. The generated QNP is then solved by the DSET solver to obtain a policy `π`. To verify that this abstraction is approximately sound on the training instances, the system performs a sequence of automated checks: ASC ensures the QNP is syntactically valid and solvable; HLISC confirms that each training instance has a corresponding abstract state under `m`; HLPRC builds an `m`‑simulation tree from `π` and checks that every abstract action step can be refined to concrete actions that respect preconditions and effects; LLGRC uses a classical planner (Fast Downward) to verify that the refined concrete states can still reach the goal. If any check fails, a structured error report is fed back to the LLM, which is prompted to regenerate or revise the QNP. This loop runs up to ten iterations or until the abstraction passes all checks on the training set. Finally, the QNP policy's plan is refined and evaluated on a separate test set of instances to measure coverage.

## Key Results
- Coverage with automated debugging: GPT-5.2 achieved 100% on Delivery, Heavy, Ferry; 85% on Gripper; 40% on Miconic; 0% on Spanner and Forest.
- Without debugging, coverage dropped substantially (e.g., Delivery from 100% to 70%, Heavy from 100% to 75%).
- Error analysis shows ASC and HLPRC were the dominant failure modes fixed during debugging; LLGRC never triggered on any domain.

## Why This Works (Mechanism)

### Mechanism 1: Prompt Protocol for Valid QNP Generation
A structured prompt protocol decomposes abstraction generation into two sequential tasks: (1) generating abstract features from domain predicates using prescribed templates (existential FOL for booleans, counting for numerics), and (2) projecting initial states, goals, and actions onto these features to form QNP components `⟨S0, SG, A_h⟩` and the refinement mapping `m`. The core assumption is that LLMs have sufficient procedural knowledge of PDDL and the QNP formalism to follow the templates correctly. Evidence: Section 3.1 gives full input-output specifications; ASC failures indicate when the protocol breaks down. Break condition: The generated QNP is rejected by DSET due to syntactic or semantic errors.

### Mechanism 2: Iterative Debugging via Solvability Checks
The debugging orchestrator runs the QNP through four automated checks to localize errors and guide repair. ASC verifies solvability; HLISC tests whether abstract states can represent all training instances; HLPRC constructs an `m`‑simulation tree to ensure each abstract action step refines to concrete actions; LLGRC diagnoses if the refined concrete plan fails to reach the goal. Each check provides specific feedback to the LLM, enabling targeted fixes. The underlying assumption is that these checks cover the primary failure modes for an abstraction that is approximately sound on the provided finite instances. Evidence: Table 2 shows ASC and HLPRC fixes dominate; LLGRC never fires. Break condition: The LLM exhausts the iteration budget (N=10) without achieving a passing abstraction.

### Mechanism 3: Approximate Soundness Guarantees Solution Transfer
If the generated QNP abstraction is *approximately sound*—i.e., it is a sound abstraction for every training instance under the refinement mapping `m`—then any abstract plan solving the QNP can be refined into a concrete plan that solves all corresponding training problems. This is formalized in Theorem 1 and Corollary 1, which rely on an `m`‑simulation relation between concrete and abstract transitions. The debugging checks explicitly test for violations of this property on the training set, ensuring the final abstraction satisfies approximate soundness. Evidence: Section 2.3 defines `m`‑simulation; Section 3.2 implements HLPRC and LLGRC to verify it. Break condition: HLPRC or LLGRC detect a refinement failure, indicating a violation of approximate soundness.

## Foundational Learning
- **Qualitative Numerical Planning (QNP) Abstraction**  
  *Why needed:* QNP is the target output format; it compresses concrete states into a compact representation using only boolean flags (`p`) and qualitative counts (`n > 0`, `n = 0`). The LLM must learn to distill essential planning knowledge into this restricted language.  
  *Quick check:* Given a concrete state with `at(ball1, roomA)` and `at(ball2, roomB)`, can you define `N = #b. (¬at(b, target_room))` and `A = ∃b. at(b, source_room)` as valid QNP features?

- **Refinement Mapping (`m`)**  
  *Why needed:* `m` provides the semantic bridge linking abstract QNP variables/actions to concrete predicates and actions. An incorrect `m` breaks the solution transfer guarantee.  
  *Quick check:* If a QNP action `Pick` has precondition `¬H`, what must `m(Pick)`'s precondition imply about the concrete state (e.g., regarding `free(g)` and `at(ball, room)`)?

- **Approximate Soundness (Definition 4 & Corollary 1)**  
  *Why needed:* It is the operational correctness criterion tested during debugging. An abstraction need not be globally sound; it only needs to work for the provided finite training set. The iterative checks aim to achieve this.  
  *Quick check:* If a QNP abstraction solves all 4 training instances after refinement, does Corollary 1 guarantee it will solve an unseen 5th instance from the same distribution? (Answer: No, only approximate soundness for the training set is claimed.)

## Architecture Onboarding
- **Component map**:  
  LLM Generator → Debugging Orchestrator → QNP Solver (DSET) → Refinement Engine → Goal Checker (Fast Downward) → Feedback Composer → (back to LLM Generator)

- **Critical path (success flow)**:  
  `PDDL Input → LLM (Gen QNP) → DSET (Solve QNP) → Get π → Refinement Engine (Build Tree w/ m) → Tree reaches concrete goal → SUCCESS (Abstraction is approx. sound for training set).`

- **Design tradeoffs**:
  - *Feature expressivity vs. noise*: Templates restrict features to single-count/existential FOC, limiting expressiveness (e.g., cannot encode Euclidean distances) but reducing hallucination of invalid QNP features.
  - *Debugging granularity vs. prompt complexity*: Four distinct checks provide fine-grained signals but require complex prompt engineering to convey precise failure context.
  - *Training data size*: Initial generation uses 2 instances, debugging uses 2 additional for validation; more instances may improve quality but increase LLM context length and cost.

- **Failure signatures**:
  - *Consistent ASC failures*: LLM produces syntactically invalid QNP (e.g., numerical effects without `inc/dec`, malformed preconditions).
  - *HLISC failures on all instances*: Generated features cannot represent given initial states/goals (e.g., missing critical count).
  - *HLPRC failures early in tree*: Refinement mapping `m` is broken—abstract actions do not refine to any concrete actions or violate preconditions.
  - *Persistent LLGRC failures*: Abstract plan is executable but leads to dead-end concrete states, indicating a semantic error in state updates.
  - *Domain-specific breakdown*: Spanner requires multi-step refinements; Forest needs metric distances—both unsupported by current formalism.

- **First 3 experiments**:
  1. **Baseline (No Debugging)**: Run LLM once with 4 training instances. Measure coverage on 10 held-out evaluation instances. Establishes raw generation capability.
  2. **With Automated Debugging**: Run the iterative loop (max 10 iterations) starting from 2 training instances, using the other 2 for validation during debugging. Measure final coverage. Tests if debugging recovers or improves abstractions.
  3. **Error Distribution Analysis**: For failed runs, log which check (ASC, HLISC, HLPRC, LLGRC) triggered the final failure and at which iteration. Validates whether debugging gets stuck on a particular error type.

## Open Questions the Paper Calls Out
1. **LLGRC necessity**: Is the LLGRC check fundamentally unnecessary for the tested GP domains, or does its absence indicate a limitation in the error detection pipeline? (Basis: zero LLGRC errors observed; unresolved because no analysis of why it never triggered; evidence to resolve: test LLGRC on a broader set of domains or analyze abstract plans.)
2. **Precise debugging feedback**: How can the automated debugging feedback be made more precise to improve the efficiency and accuracy of QNP abstraction revision? (Basis: current error reports are coarse-grained; unresolved; evidence to resolve: implement more granular error localization and measure impact.)
3. **Extending feature templates**: Can the feature template expressiveness be extended to support QNP abstractions for domains requiring non-FOC features (e.g., Euclidean distances), and would this enable success on domains like Forest? (Basis: failure in Forest due to inability to express distance; unresolved; evidence to resolve: design extended templates with difference/comparison operators and test.)
4. **Generalizing refinement mapping**: Can the refinement mapping be generalized to allow HL actions to refine into sequences of LL actions rather than single LL actions, and would this address failures in domains like Spanner? (Basis: Spanner failure due to abstract action `walk-to-spanner` requiring multi-step refinement; unresolved; evidence to resolve: allow HL actions to map to action sequences and evaluate on Spanner.)

## Limitations
- Prompt templates and DSET integration details are underspecified, impeding exact replication.
- Evaluation limited to 7 domains; two (Spanner, Forest) remain unsolved, indicating QNP expressivity gaps.
- LLGRC never fired in experiments, questioning its diagnostic utility.

## Confidence
- Prompt protocol yields syntactically valid QNP: **Medium**
- Debugging checks effectively fix errors: **Medium**
- Approximate soundness holds for training set: **High**
