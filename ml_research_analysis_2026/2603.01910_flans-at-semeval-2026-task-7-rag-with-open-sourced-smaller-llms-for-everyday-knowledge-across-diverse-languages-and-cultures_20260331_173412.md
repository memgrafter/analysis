# FLANS at SemEval-2026 Task 7: RAG with Open-Sourced Smaller LLMs for Everyday Knowledge Across Diverse Languages and Cultures

## Quick Facts
- arXiv ID: 2603.01910
- Source URL: https://arxiv.org/abs/2603.01910
- Reference count: 15
- Primary result: RAG with small open-source LLMs and culturally-aware local KBs, combined with strict prompt engineering (RP-v1) and language-specific model routing, significantly improves accuracy on multilingual everyday knowledge QA compared to minimal prompting.

## Executive Summary
This paper tackles the poor performance of smaller, open-source Large Language Models (LLMs) on culturally specific everyday knowledge questions, a key gap in practical multilingual QA. The proposed FLANS system uses a Retrieval-Augmented Generation (RAG) pipeline with a locally-deployed, culturally-aware knowledge base (CulKBs) built from Wikipedia and optional live web search. A cascaded retrieval strategy and deterministic language-based model routing (e.g., using a larger DeepSeek-LLM for Chinese) are employed. The central innovation is in prompt design: a persona-driven, strictly formatted prompt (RP-v1) dramatically stabilized outputs. Evaluated on the BLEnD benchmark across English, Spanish, and Chinese, the system achieved competitive results, demonstrating that sustainable, CPU-friendly RAG with smaller models can address parametric knowledge gaps in cultural QA.

## Method Summary
The system is a RAG pipeline without model fine-tuning. It builds a multilingual, culturally-aware knowledge base (CulKBs) from Wikipedia extracts and manually curated facts, stored in Chroma vector stores per country/language. At inference, a router parses the question's language/country code to select a model (default Gemma-3.4B; variants use Mistral-7B or DeepSeek-67B) and a retrieval strategy. The RAG-BASE variant uses only the local KB. The RAG-WEB variant uses a cascaded approach: first attempts DuckDuckGo web search; if confident, uses those snippets; otherwise falls back to the local country-specific KB summary; and finally, if no evidence, generates a parametric answer with an abstention token. Retrieved context is injected into one of three prompt templates (Minimal Prompt, RP-v1, RP-v2). The final chosen prompt, RP-v1, enforces a "factual multilingual assistant" persona with strict output rules (one concise answer, same language, no explanations).

## Key Results
- Prompt ablation showed RP-v1 (with explicit formatting/persona) improved three-language average SAQ accuracy from 16.15% (minimal prompt) to 33.57%, while RP-v2's added reasoning helped SAQ more (44.40%) but harmed MCQ performance (73.81% vs. RP-v1's 83.57%).
- Language-specific routing to DeepSeek-67B in the RAG-WEB variant boosted Chinese MCQ accuracy to 91.67%, compared to 82.86% with Gemma-3.4B in RAG-BASE.
- The final competition submission used the RP-v1 prompt across three systems, achieving competitive results in the SemEval task.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** RAG mitigates parametric knowledge gaps in smaller LLMs for culturally specific questions by grounding generation in external, curated sources.
- **Mechanism:** The system retrieves relevant text snippets from a local, culturally-aware knowledge base (CulKBs) or via live web search. These snippets are injected into the prompt, providing the small LLM with concrete evidence to base its answer on, rather than relying solely on its limited internal weights which lack fine-grained cultural facts.
- **Core assumption:** The retrieved context contains the correct answer and is sufficiently salient for the small LLM to correctly extract and format it.
- **Evidence anchors:** [abstract] "core method uses retrieval-augmented generation (RAG) with open-sourced small LLMs... and a locally-deployed, culturally-aware knowledge base (CulKBs)"; [section 3] Describes the RAG pipeline: "retrieved context is then combined with the original question and inserted into a structured prompt template... to generate the final answer."
- **Break condition:** If retrieval fails to return relevant passages (e.g., "NULL" output), the small LLM defaults to its parametric knowledge, likely leading to incorrect or hallucinated answers.

### Mechanism 2
- **Claim:** Strict, persona-driven prompt engineering with explicit formatting instructions significantly stabilizes and improves small LLM output for multilingual factual QA.
- **Mechanism:** RP-v1's persona ("factual multilingual assistant") and rigid rules ("one concise answer," "SAME language," "no explanations") constrain the model's decoding behavior. This reduces common failure modes in small models like verbosity, language switching, and off-topic generation, forcing a direct, formatted extraction from the provided context.
- **Core assumption:** The small LLM can follow complex formatting constraints and that adherence to them correlates with factual accuracy.
- **Evidence anchors:** [abstract] "explicit formatting and persona instructions (RP-v1) were most effective, improving three-language average SAQ accuracy from 16.15% (minimal prompt) to 33.57%"; [section 4.2] "performance consistently improved from MP to RP-v2... suggesting that both explicit formatting instruction and perspective-aware prompting are beneficial" (though MCQ peaked at RP-v1).
- **Break condition:** If the question's correct answer format requires explanation, RP-v1's constraints may force an incorrect or incomplete response.

### Mechanism 3
- **Claim:** Deterministic language and model routing based on question metadata improves performance for linguistically or culturally hard languages by dynamically allocating more capable models.
- **Mechanism:** The system parses the language/country code in the question ID. For non-Chinese variants, it uses a fast, balanced model (Mistral-7B). For Chinese variants, it routes to a larger model (DeepSeek-67B) which has superior factual recall and NER for Chinese, as empirically determined during development.
- **Core assumption:** Model performance on this task is strongly language-dependent and a larger parameter count is necessary for Chinese factual accuracy within their hardware constraints.
- **Evidence anchors:** [section 3.1] "For Chinese variants... the system switches to using the deepseek-llm:67b model. This is because it is much larger but performs better for Chinese factual reasoning and named entity recognition."; [section 4.2] Table 2: Chinese MCQ score jumps to 91.67% in RAG-WEB (DeepSeek-67B) vs. 82.86% in RAG-BASE (Gemma-3.4B).
- **Break condition:** If the "Chinese variant" metadata is incorrect or missing, routing fails. The heavy DeepSeek model's slower inference may violate efficiency goals if overused.

## Foundational Learning
- **Concept: Retrieval-Augmented Generation (RAG)**
  - Why needed: The entire system is a RAG implementation. Understanding the retrieve-read-generate loop is fundamental to diagnosing whether failures are due to poor retrieval, ineffective context injection, or weak generation.
  - Quick check: If the retrieved context contains the gold answer verbatim but the LLM output is wrong, is this primarily a retrieval or a generation problem?
- **Concept: Prompt Engineering for Constrained Decoding**
  - Why needed: The paper's main result is the dramatic effect of prompt design (RP-v1). Grasping how personas, output format rules, and CoT steps influence small LLM behavior is key to reproducing and extending their work.
  - Quick check: Why might adding a "Chain-of-Thought" reasoning step (RP-v2) harm performance on multiple-choice questions but help on short-answer questions?
- **Concept: Multilingual Model Routing & Cascading Retrieval**
  - Why needed: The RAG-WEB variant uses a non-uniform strategy (model choice, KB usage, fallback to web search) triggered by language/country codes. Understanding this logic is essential to predict system behavior on a new language variant.
  - Quick check: What are the ordered fallback steps if DuckDuckGo search returns no relevant snippets for a Spanish (es-AR) question?

## Architecture Onboarding
Input Parser -> Router -> Retriever -> Prompt Builder -> LLM -> Output Formatter
Critical path: Question ID → Router → Retriever → Prompt Builder → LLM → Answer.
- Branching: The "whether evidence is needed" decision is implicit; RAG-WEB has a more explicit conditional flow.
Design tradeoffs:
- Local DB vs. Web Search: Local KB ensures stability/reproducibility but may miss recent/nuanced facts; web search is broader but introduces non-determinism/API dependency.
- Model Size vs. Speed/Cost: DeepSeek-67B boosts Chinese accuracy but is slower and more memory-intensive than Gemma-3.4B.
- Prompt Complexity vs. Reliability: RP-v2's reasoning step helps SAQ but harms MCQ, showing task-specific optimal prompt structure.
Failure signatures:
- Retrieval failure: LLM outputs "NULL" or generic/incorrect answer.
- Routing failure: Model generates answer in wrong language (e.g., English for Chinese question).
- Prompt failure: Verbose output, multiple candidates, or reasoning included when only a short answer is expected.
First 3 experiments:
1. **Baseline sanity check:** Run MP prompt on a known QA pair from CulKBs with retrieval disabled. Expect poor, inconsistent answers, confirming small LLM's parametric gap.
2. **Prompt validation:** Run RP-v1 vs. RP-v2 on a set of 20 SAQ and 20 MCQ items from a held-out dev set. Verify RP-v1's superior MCQ score and RP-v2's SAQ gain, replicating Table 1 pattern.
3. **Routing test:** Submit a Chinese BLEnD question and an English question with identical cultural content. Verify system uses DeepSeek for zh-* and Mistral for en-*, and that DeepSeek's answer is more accurate. Check logs for router code parsing.

## Open Questions the Paper Calls Out
### Open Question 1
Why does perspective-aware prompting (RP-v2) degrade multiple-choice question (MCQ) accuracy while improving short-answer question (SAQ) performance?
- **Basis:** Prompt ablation (Table 1) shows RP-v2 increases SAQ average (33.57% → 44.40%) but decreases MCQ (83.57% → 73.81%).
- **Why unresolved:** Authors attribute this to "unnecessary cognitive overhead" for constrained answer spaces but provide no empirical analysis of the interference mechanism.
- **What evidence would resolve it:** Controlled experiments isolating reasoning steps in MCQ prompts, measuring option-space match rates; analyzing model attention or logits to see if internal reflection distracts from option selection.

### Open Question 2
What specific factors in the local knowledge base construction cause performance degradation for Spanish SAQ in the RAG-WEB system?
- **Basis:** Table 2 shows Spanish SAQ score drops from 33.33% (no local DB) to 0% (with local DB) under RP-v1 in RAG-WEB.
- **Why unresolved:** Authors suggest the local DB "might have introduced noise" but do not investigate the source or nature of this noise.
- **What evidence would resolve it:** Error analysis comparing retrieved Spanish KB chunks for correct vs. incorrect responses; auditing KB entries for cultural inaccuracies; quantifying retrieval precision/recall per language variant.

### Open Question 3
Is the superior performance of DeepSeek-67B for Chinese queries primarily due to its larger parameter count, or does it reflect better training data coverage of Chinese cultural nuances?
- **Basis:** The language/model router switches to DeepSeek-67B for Chinese variants, achieving 91.67% MCQ accuracy (Table 2), while Mistral-7B underperforms.
- **Why unresolved:** The authors assume size is the key factor, but model training data is a confounding variable not disentangled.
- **What evidence would resolve it:** Compare DeepSeek-67B with other 7B-scale models trained on similar data; probe model outputs for cultural consistency; analyze training data composition if accessible.

## Limitations
- Incomplete description of KB construction (keywords, page lists) prevents faithful recreation of CulKBs.
- Cascaded retrieval logic in RAG-WEB (confidence threshold, `<NO_ANSWER>` handling) is underspecified, obscuring fallback behavior.
- Best performance (RAG-WEB Chinese) confounds larger model (DeepSeek-67B) with expanded retrieval (web search), making it hard to attribute gains.
- Deterministic language/country code parsing may fail for edge variants (e.g., `zh-SG`), risking misrouting and degraded accuracy.

## Confidence
- RAG mitigates parametric gaps: **Medium**
- RP-v1 prompt engineering: **High**
- Language/model routing: **Medium**

## Next Checks
1. **RAG isolation test:** Run Gemma-3.4B with retrieval (local KB) and without (parametric only) on a held-out dev set; a significant difference confirms RAG’s benefit.
2. **Routing ablation:** For Chinese QA, keep retrieval constant (local KB) and compare Gemma-3.4B vs. DeepSeek-67B; isolates model-size contribution and tests routing necessity.
3. **KB coverage audit:** Randomly sample 100 gold answer entities; query local KB (top-5 chunks) and compute recall. Low recall would indicate systematic knowledge gaps.
