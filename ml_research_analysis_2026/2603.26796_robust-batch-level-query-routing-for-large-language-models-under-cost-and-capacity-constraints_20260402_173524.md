# Robust Batch-Level Query Routing for Large Language Models under Cost and Capacity Constraints

## Quick Facts
- arXiv ID: 2603.26796
- Source URL: https://arxiv.org/abs/2603.26796
- Reference count: 40
- Primary result: Batch-level ILP routing strictly enforces cost and GPU constraints and outperforms per-query routing by up to 24% under adversarial batching.

## Executive Summary

This paper tackles the challenge of routing queries to large language models (LLMs) in a serving system where monetary cost and GPU capacity must be respected at the batch level. While per-query routing methods fail to control spending under adversarial batching, the authors formulate batch-level routing as an Integer Linear Programming (ILP) problem that jointly assigns each query in a batch to a model while respecting average cost limits and per-model instance capacities. A robust variant uses lower prediction bounds to handle uncertainty in performance estimates. Additionally, an offline ILP optimizes the allocation of fixed GPU instances to open-source models. Experiments on two multi-task benchmarks show that robust routing improves accuracy by 1–14% over non-robust versions, batch-level optimization yields up to 24% gains over per-query routing under adversarial batches, and optimized instance allocation provides up to 3% extra improvement. The approach enforces constraints rigorously but assumes stationary query distributions and moderate batch sizes (≤400) for real-time ILP solving.

## Method Summary

The core method is an online batch-level routing algorithm that, for each batch of queries, solves an ILP to maximize the average predicted performance (e.g., accuracy) subject to: (i) the batch's average per-query cost not exceeding a budget C, and (ii) the number of queries assigned to each model j not exceeding its total capacity, defined as the product of assigned GPU instances I_j and the per-instance concurrency limit l_j. The performance predictions a_{i,j} are obtained from a learned estimator (e.g., XGBoost, kNN) trained on query-model pairs. To handle uncertainty, a robust variant replaces a_{i,j} with a lower bound derived from bootstrap prediction intervals. An offline stage solves a larger ILP over historical batches to determine the optimal fixed allocation I_j across models given a total GPU budget, which is then used in the online phase. The ILP is solved with SCIP; for batch sizes up to 400 the solve time is under 0.4 seconds, making it feasible for real-time deployment.

## Key Results

- Robust routing (using lower prediction bounds) improves average test performance by 1–14% relative to non-robust routing across two benchmarks.
- Batch-level ILP optimization outperforms per-query routing by up to 24% when evaluated on adversarially constructed batches that stress cost overspending.
- Offline optimization of model instance allocation yields up to 3% additional performance gains compared to a naive uniform allocation under the same GPU budget.

## Why This Works (Mechanism)

### Mechanism 1: Joint batch-level optimization via ILP
- **Claim:** Joint batch-level optimization via Integer Linear Programming (ILP) strictly enforces cost and capacity constraints, which per-query routing fails to control under adversarial batching.
- **Mechanism:** For a batch of N queries and M models, the ILP (Problem 2) assigns each query to exactly one model (binary variables x_{i,j}) to maximize average estimated performance, subject to: (i) average batch cost ≤ C, and (ii) per-model capacity limits based on instance count I_j and concurrency l_j. This global coupling prevents cost spikes and oversubscription.
- **Core assumption:** The ILP can be solved within the batch arrival interval (milliseconds per [section 2.2] using SCIP) and that per-query cost c_j is a reasonable model for batch cost aggregation.
- **Evidence anchors:**
  - [abstract] "jointly optimizes model assignment for each batch while respecting cost and model capacity limits."
  - [section 2.2] Full ILP formulation (2) and runtime analysis showing SCIP solves in <0.4s for B=400.
  - [corpus] Neighbor papers like "Near-Optimal Online Deployment and Routing for Streaming LLMs" also explore coupled deployment-routing, suggesting related challenges, but evidence for this specific ILP mechanism's superiority is primarily from authors' experiments.
- **Break condition:** If batch size B grows so large that ILP solve time exceeds the batch formation/window deadline, the mechanism fails in real-time. The paper assumes B is moderate (up to 400) and solve time is acceptable.

### Mechanism 2: Robust optimization with lower prediction bounds
- **Claim:** Robust routing, which optimizes against worst-case performance estimates (lower bounds of prediction intervals), improves accuracy by 1–14% over non-robust versions under uncertainty.
- **Mechanism:** For each query-model pair, instead of a point estimate a_{i,j}, a prediction interval [\underline{a}_{i,j}, \overline{a}_{i,j}] is constructed (e.g., via bootstrap or conformal). The ILP objective uses the lower bound \underline{a}_{i,j}, thus guarding against overestimation. This is equivalent to maximizing the worst-case average performance over the uncertainty set.
- **Core assumption:** The prediction intervals capture the true distribution of performance estimates with high probability; specifically, that the true a_{i,j} lies within [\underline{a}_{i,j}, \overline{a}_{i,j}]. The robustness improvement depends on the quality of these intervals.
- **Evidence anchors:**
  - [abstract] "robust variant uses lower prediction bounds to handle performance estimate uncertainty... improves accuracy by 1–14%."
  - [section 2.4] Formal robust formulation (3) and equivalence to using lower bounds. Bootstrap procedure described for interval estimation.
  - [section 3.1] Empirical results showing robust XGBoost/kNN outperform non-robust counterparts in cost-performance curves and PI length analysis (Table 1).
- **Break condition:** If the uncertainty quantification (e.g., bootstrap quantile Q) is severely miscalibrated—either too conservative (hurt performance on certain queries) or too narrow (fails to protect against worst-case)—the robust variant may underperform. The paper shows some sensitivity to Q but overall stability.

### Mechanism 3: Offline model instance allocation
- **Claim:** An offline optimization for allocating fixed GPU instances (I_j) across models, before inference, yields up to 3% additional performance gains over a uniform fixed allocation under cost and GPU constraints.
- **Mechanism:** Using B held-out calibration batches, a larger ILP (Problem 4) simultaneously optimizes binary routing variables x_{i,j}^b for each batch and integer instance variables I_j. It maximizes average performance over all calibration batches, subject to total GPU budget (∑_j g_j I_j ≤ G) and per-batch capacity constraints (for each model j in each batch b: ∑_i x_{i,j}^b ≤ l_j I_j). The optimal I_j is then fixed for online routing.
- **Core assumption:** The calibration batches are representative of the future query distribution. The offline optimization assumes static instance counts during online phase, not adapting to traffic spikes.
- **Evidence anchors:**
  - [abstract] "offline procedure optimizes model instance allocation... optimized instance allocation yields up to 3% additional gains."
  - [section 2.5] Complete ILP formulation (4), simulation of online performance during offline phase.
  - [section 3.3] Figure 5 showing optimized allocation outperforms fixed uniform allocation across GPU budgets.
- **Break condition:** If the future query distribution shifts significantly from the calibration batches, the static allocation I_j becomes suboptimal. The paper's limitation section explicitly notes static evaluation and distribution shift as concerns.

## Foundational Learning

- **Concept: Integer Linear Programming (ILP) for combinatorial assignment**
  - *Why needed here:* The batch-level routing and offline allocation problems are inherently discrete (binary query-model assignments, integer model instance counts) and constrained. ILP provides a mathematically sound framework to maximize a linear objective (average performance) under linear constraints (cost, capacity, assignment). Without this, one might resort to heuristics that violate constraints or are suboptimal.
  - *Quick check question:* In Problem (2), what does the constraint ∑_i x_{i,j} ≤ l_j I_j represent, and why is it linear in the variables?

- **Concept: Robust optimization with prediction intervals**
  - *Why needed here:* Performance estimates a_{i,j} are noisy. Using point estimates in the ILP objective can lead to fragile routing decisions if estimates are over-optimistic. By optimizing the lower bound of a prediction interval, the router inherently prefers models with more certain (lower variance) performance predictions, as shown in Table 1.
  - *Quick check question:* How does the robust routing objective (3) simplify when the prediction intervals are known, and what practical method (e.g., bootstrap) is used to obtain the intervals?

- **Concept: Offline resource allocation as a two-stage stochastic/batch optimization**
  - *Why needed here:* Deciding how many GPU instances I_j to dedicate to each open-source model is a high-stakes, slow-changing decision. Doing this poorly (e.g., uniform allocation) wastes GPU budget or forces over-reliance on costly closed-source models. The offline ILP (4) leverages historical batch data to find a near-optimal fixed allocation that balances quality and capacity ahead of time.
  - *Quick check question:* In Problem (4), what role do the calibration batches play, and why can't the online ILP (2) directly optimize I_j during inference?

## Architecture Onboarding

- **Component map:**
  Performance Estimator -> Batch Accumulator -> Router Controller -> ILP Solver Interface; Router Controller also fetches I_j from Offline Allocation Module and uses Constraint Calculator; Offline Allocation Module runs once before deployment.

  More precisely: The offline process uses calibration data with Offline Allocation Module to produce I_j. Online: Batch Accumulator gathers queries; Router Controller invokes Performance Estimator for all (query, model) pairs; then Constraint Calculator determines C and retrieves I_j, l_j; then ILP Solver Interface solves Problem (2); Router Controller dispatches queries accordingly.

- **Critical path:** 
  Online: Batch ready -> Estimate a_{i,j} for all i,j -> Compute constraints (C, I_j, l_j) -> Solve ILP (2) -> Assign and dispatch.
  Offline: Load calibration batches -> Solve ILP (4) for I_j -> Deploy configuration.

- **Design tradeoffs:**
  - Solver choice: SCIP is powerful but heavy; for smaller B/M, commercial solvers may be faster but have licensing issues. Trade-off: optimality vs. latency.
  - Uncertainty quantification: Bootstrap gives good intervals but requires refitting estimator many times (100×). Conformal is cheaper but may be less precise if estimator is unstable.
  - Fixed vs. dynamic I_j: Static offline allocation ensures stability; dynamic reallocation could adapt to traffic shifts but incurs model load/unload overhead and may cause capacity violations during transition.

- **Failure signatures:**
  - ILP infeasibility: Constraints too tight (C too low or capacity insufficient). Fallback: relax constraints or use heuristic.
  - Solver timeout: For large B or M, solve time exceeds batch window. Mitigation: set time limit, fallback to per-query routing.
  - Degenerate assignment: all queries assigned to one model. Indicates either identical estimates or overly restrictive constraints; check estimator output distribution and constraint tightness.

- **First 3 experiments:**
  1. Replicate Section 3.2: Implement per-query routing (baseline) and batch-level ILP routing. Generate random and adversarial batches (size 100). Adversarial batches built by sorting queries by per-query router's selected model cost and grouping. Verify batch-level outperforms per-query by up to 24%.
  2. Test robust quantile sensitivity (Section 3.1/A.2): For XGBoost and kNN, compute bootstrap prediction intervals. Vary quantile Q ∈ {5,10,20,30}. Plot performance vs. cost curves. Confirm stability across Q, justifying default Q=10.
  3. Validate offline allocation gain (Section 3.3): For a fixed GPU budget (e.g., 100 GPUs on Dataset 2), compare optimized I_j from Problem (4) against uniform I_j=n for n∈{1,2,3}. Run online routing with these I_j for B=100 batches. Expect ~2-3% gain from optimized allocation, more evident at tighter cost budgets.

## Open Questions the Paper Calls Out

1. **Scalability of ILP to large batches and model pools** – The paper tests up to 400 queries and ~20 models; scalability beyond that is open, with potential need for approximation algorithms.
2. **Efficient uncertainty quantification for robust routing** – Bootstrap is computationally heavy; the paper mentions conformal prediction as an alternative but does not implement or compare it.
3. **Impact of conversational context switching** – The work assumes independent single-turn queries; routing across models in a conversation incurs KV-cache invalidation overhead, which is not modeled.
4. **Adaptive model instance allocation under non-stationarity** – Offline allocation assumes stationary query distribution; adapting to distribution shifts without high reconfiguration costs remains open.
5. **Theoretical relationship between uncertainty conservatism and constraint violations under shift** – The robust approach uses fixed quantiles; how the choice of Q affects the probability of cost overruns or capacity breaches under distribution shift is not analyzed.

## Limitations

- **Scalability untested** – The ILP solve times are reported only up to batch size 400; performance with larger batches or hundreds of models is unknown.
- **Stationary distribution assumption** – Both the offline allocation and robust intervals are calibrated on a fixed dataset; real-world query distributions may drift, degrading performance.
- **Dependence on interval calibration** – Robust gains rely on well-specified prediction intervals; miscalibrated intervals (e.g., due to bootstrap errors) could harm performance.

## Confidence

- Batch-level ILP outperforms per-query routing: **High** (consistent gains up to 24% across benchmarks).
- Robust routing improves accuracy over non-robust: **Medium** (gains 1–14% but sensitive to quantile Q and interval quality).
- Offline instance allocation yields additional gains: **Medium** (small gain on static calibration, may degrade under shift).

## Next Checks

1. **Solve time scaling benchmark** – Measure SCIP runtime as batch size increases from 200 to 1000 queries and model counts from 20 to 100; identify thresholds where solve time becomes unacceptable and test fallback heuristics.
2. **Compare bootstrap with conformal prediction** – Replace bootstrap intervals with conformal intervals for robust routing; evaluate coverage and resulting cost-accuracy trade-offs to assess computational vs. robustness trade-off.
3. **Stress test under distribution shift** – Partition calibration and test data by task, time, or topic to simulate non-stationarity; run offline allocation on one partition and evaluate on another to quantify performance degradation and re-allocation frequency needed.
