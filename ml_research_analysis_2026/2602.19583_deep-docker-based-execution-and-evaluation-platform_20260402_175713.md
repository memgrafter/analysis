# DEEP: Docker-based Execution and Evaluation Platform

## Quick Facts
- **arXiv ID:** 2602.19583
- **Source URL:** https://arxiv.org/abs/2602.19583
- **Reference count:** 4
- **Primary result:** DEEP enables reproducible, resource-aware, and statistically rigorous benchmarking by automating Dockerized model execution, multi-metric evaluation, and significance-based clustering.

## Executive Summary
DEEP is a platform designed to automate the comparative evaluation of machine learning systems, addressing common shortcomings in competitions and research such as lack of standardization, absence of resource monitoring, and reliance on simple metric rankings without statistical validation. It requires participants to package their models as Docker containers, which are then executed on a shared test set under controlled conditions while measuring inference time. Post-execution, it computes standard metrics (e.g., BLEU, TER, chrF for machine translation; WER for OCR) and clusters systems based on statistically indistinguishable performance using Approximate Randomization Testing (ART). A Streamlit-based visualization dashboard allows users to explore trade-offs between accuracy, significance clusters, and computational cost. A demonstration on eight machine translation models from WMT20 produced ranked performance tables, identified non-significant pairwise differences (e.g., Seed and MADLAD-400 on TER), and visualized score-time correlations, illustrating a holistic evaluation pipeline.

## Method Summary
DEEP implements a three-phase pipeline. First, the **Docker Orchestrator** builds participant-submitted Docker images, mounts the test dataset into a standardized `/data` directory, runs the container, and records wall-clock execution time, collecting predictions from `/predictions`. Second, the **Metric Engine** loads hypotheses and references, computes overall and per-sample scores for registered metrics (e.g., BLEU, TER, chrF, WER). The **Significance Engine** then sorts systems by a primary metric and applies pairwise Approximate Randomization Testing (with 10,000 trials, p=0.05) between adjacent systems, greedily merging those without significant difference into clusters. Finally, a **Results Serializer** outputs a structured file containing scores, sample-level data, execution times, and cluster assignments. A separate **Streamlit Visualization** app reads this file to render interactive charts: ranked bar plots, execution time arcs, score-vs-time scatter plots, and cluster-average comparisons.

## Key Results
- In the WMT20 English–German demo, DEEP produced a ranked table of eight MT systems; Seed achieved BLEU 38.84 and chrF 65.45.
- Clustering via ART revealed that some adjacent systems (e.g., Seed and MADLAD-400 on TER) shared a cluster, indicating no statistically significant performance difference.
- The integrated visualization enabled exploration of trade-offs between metric scores and execution time, providing a more holistic view than score-only rankings.

## Why This Works (Mechanism)
### Mechanism 1: Dockerized Execution for Controlled, Resource-Aware Inference
DEEP automates model execution and captures resource usage by requiring systems to be packaged as Docker containers. The orchestrator builds the image, mounts the test dataset to `/data`, executes the container, and collects predictions from `/predictions`, while measuring wall-clock time. This ensures environment isolation for fair inference time comparison, contingent on participants adhering to the I/O contract. Evidence is drawn from the abstract and Section 3.1; corpus neighbors discuss Docker generally but not for this specific evaluation context. If containerization fails or the I/O contract is violated, execution halts.

### Mechanism 2: Significance-Based Clustering via Approximate Randomization Testing (ART)
DEEP clusters systems by applying metric-agnostic ART to pairwise comparisons of adjacent systems in a list sorted by the primary metric's overall score. With 10,000 trials and p=0.05, a p-value > 0.05 merges the lower-ranked system into the higher-ranked one's cluster, creating tiers where differences are not statistically meaningful. This moves beyond simple ranking. Evidence is from the abstract and Section 3.2.2 (Algorithm 1). The approach assumes ART's validity for sample-level metric scores and that the greedy order based on the main metric is appropriate. Clustering fails if sample scores are unavailable or test instances are too few.

### Mechanism 3: Integrated Visualization for Multi-Dimensional Trade-off Analysis
DEEP embeds a Streamlit web app that reads the structured results file (scores, times, clusters) and renders interactive charts: a ranked bar chart, a time arc chart, a score-vs-time scatter plot, and a cluster-average bar chart. Users can select metrics and filter systems, enabling holistic exploration of accuracy, statistical significance, and efficiency trade-offs. Evidence is from the abstract and Section 3.3. The visualization depends on the results file schema; mismatches cause crashes.

## Foundational Learning
- **Docker Containerization:** Needed because the entire execution and resource monitoring relies on participants' models being encapsulated in Docker images that follow DEEP's I/O contract (read from `/data`, write to `/predictions`). Quick check: What must a Dockerfile's `CMD` or `ENTRYPOINT` do to comply?
- **Approximate Randomization Test (ART):** Needed to determine if observed differences between two systems' metric scores are statistically significant, using permutations of sample-level scores rather than parametric tests. Quick check: Given two lists of sentence-level BLEU scores, what does p=0.03 from ART indicate under the null hypothesis of equal performance?
- **Metric Modularity & Interface Contract:** Needed to extend DEEP to new tasks or metrics; developers must implement a function taking `(hypotheses, references)` and returning a `float`. Quick check: To add ROUGE-L for summarization, what is the function signature and where is it registered?
- **Resource-Aware Benchmarking:** Needed to understand why measuring execution time alongside accuracy is valuable for practical deployment decisions. Quick check: Why might a system with a slightly lower BLEU but significantly faster inference be preferred in production?
- **Statistical Clustering vs. Ranking:** Needed to grasp why grouping systems into significance-based clusters is more informative than a strict sorted list. Quick check: If System A and B are in the same cluster on the primary metric, can we confidently say A is better than B?
- **Streamlit Rapid Prototyping:** Needed to appreciate how DEEP's visualization is built and customized. Quick check: How does Streamlit's reactive programming model allow charts to update when a user changes the metric selector?

## Architecture Onboarding
Docker Orchestrator -> Data Manager -> Metric Engine -> Significance Engine -> Results Serializer -> (Separate Process) Streamlit App
**Critical path:** Docker Build -> System Execution -> Hypothesis Collection -> Metric Computation (Sample & Overall) -> ART & Clustering -> Results File Write -> Streamlit App Launch -> Chart Rendering.
**Design tradeoffs:** Rigor vs. Speed (10k ART trials are heavy); Reproducibility vs. Overhead (Docker adds build/run cost); Task Specificity vs. Generality (I/O contract is currently text/image-specific, limiting easy extension to new modalities).
**Failure signatures:** Docker stage: build failures, container non-zero exit, missing `/predictions`. Evaluation stage: metric crashes, sample score length mismatches for ART. Visualization stage: results file schema changes break the app parser.

## Open Questions the Paper Calls Out
- **Open Question 1:** To what extent can DEEP's modular architecture be seamlessly extended to support non-textual tasks (e.g., image generation, audio synthesis) without significant redesign of its core pipeline? The paper only demonstrates extension to OCR; challenges for fundamentally different tasks are unaddressed.
- **Open Question 2:** How sensitive are DEEP's statistically significant cluster formations (via ART) to chosen hyperparameters (e.g., 10,000 trials, p=0.05), and could alternative significance tests yield different system groupings? The paper uses fixed ART parameters without comparison to other tests (e.g., bootstrap, Williams test).
- **Open Question 3:** Does the mandatory Docker-based execution model create a practical barrier for systems that cannot be containerized (e.g., proprietary APIs, hardware-tied models), and can DEEP's "hypotheses-only" mode provide equivalent holistic evaluation? The trade-off between reproducibility/standardization and accessibility is not analyzed.
- **Open Question 4:** Can the integration of more ambiguous, model-based metrics (e.g., COMET, BERTScore) into DEEP's clustering pipeline produce statistically reliable system rankings, given their known distributional properties and correlation with human judgment? DEEP currently uses only classical metrics; applying ART to neural metrics may violate assumptions.

## Limitations
- **Docker I/O contract specifics**: The exact file naming, directory structure within `/data`, and aggregation logic for multi-file datasets (e.g., XML for MT) are not detailed, creating replication ambiguity.
- **ART clustering implementation**: The algorithm's handling of ties after sorting, the precise definition of "adjacent" systems, and its computational scaling with many systems (>50) are not explored.
- **Generalizability beyond MT/OCR**: The mechanism for adapting the Data Manager to new tasks (e.g., image segmentation) is unclear, limiting claims of broad applicability.

## Confidence
- **Dockerized Execution (Mechanism 1): Medium.** The core concept is clear and standard, but evidence for its *novelty in benchmarking* is weak; neighbors discuss Docker generally, not specifically for resource-aware evaluation.
- **Significance Clustering (Mechanism 2): Medium.** ART is established, but the paper provides no validation that the greedy, metric-sorted application is sound for multi-metric evaluation or that 10k trials are sufficient across varied sample sizes.
- **Integrated Visualization (Mechanism 3): High.** The Streamlit implementation is explicitly described; confidence is high in *existence*, but lower in *proven utility* for decision-making (no user study).
