# The Wikidata Query Logs Dataset

## Quick Facts
- arXiv ID: 2602.14594
- Source URL: https://arxiv.org/abs/2602.14594
- Reference count: 24
- This paper presents the Wikidata Query Logs (WDQL) dataset, containing 200k question-query pairs derived from real-world SPARQL queries submitted to Wikidata Query Service

## Executive Summary
This paper introduces the Wikidata Query Logs (WDQL) dataset, a collection of 200,000 question-query pairs derived from real-world SPARQL queries submitted to the Wikidata Query Service. The authors address the challenge of generating natural language questions from anonymized query logs by developing an agent-based method that iteratively de-anonymizes, cleans, and verifies queries while generating corresponding questions. WDQL is over 6x larger than existing Wikidata datasets and contains more diverse query patterns. Experiments with GRISP question answering models demonstrate significant improvements when trained on WDQL, with F1-scores increasing from 6.8 to 57.6 on the WDQL test set and outperforming previous datasets on several benchmarks.

## Method Summary
The authors developed an agent-based method to transform anonymized SPARQL query logs into question-query pairs. The process involves iteratively de-anonymizing variables, cleaning queries by removing noise, and generating natural language questions. Human verification ensures quality by selecting "interesting" queries. The resulting WDQL dataset contains 200k pairs and is over 6x larger than existing Wikidata datasets, with claims of greater diversity in query patterns.

## Key Results
- WDQL contains 200k question-query pairs, over 6x larger than existing Wikidata datasets
- GRISP models trained on WDQL show F1-score improvement from 6.8 to 57.6 on WDQL test set
- WDQL-trained models outperform previous datasets on several Wikidata benchmarks

## Why This Works (Mechanism)
The iterative agent-based approach successfully transforms anonymized SPARQL logs into usable training data by systematically addressing the core challenge of variable de-anonymization and query cleaning. The human verification step ensures quality by selecting queries that represent meaningful patterns, while the iterative refinement process allows for progressive improvement of both queries and their natural language counterparts.

## Foundational Learning
- SPARQL query structure: Understanding how variables, triples, and patterns compose queries - needed to de-anonymize and clean queries effectively
- Natural language generation: Mapping formal query patterns to intuitive questions - needed to create training pairs that models can learn from
- Semantic parsing: Converting natural language to structured queries - needed to evaluate model performance on the dataset
- Query diversity metrics: Measuring variety in query patterns, entities, and topics - needed to claim WDQL is more diverse than alternatives
- Data cleaning pipelines: Systematic approaches to remove noise and standardize formats - needed to transform raw logs into usable training data

## Architecture Onboarding

Component map: Query logs -> De-anonymization agent -> Cleaning agent -> Question generation agent -> Human verification -> WDQL dataset

Critical path: The iterative pipeline where each agent processes queries, with human verification serving as the quality gate that determines which queries progress to the final dataset

Design tradeoffs: The paper balances dataset size against quality through human verification, accepting a more labor-intensive process to ensure only "interesting" queries are included. This introduces potential bias but aims for higher-quality training data.

Failure signatures: Poor variable de-anonymization leads to nonsensical questions, incomplete cleaning leaves noise that confuses models, and human verification may exclude valid but less intuitive query patterns.

First experiments: 
1. Test de-anonymization agent on a sample of anonymized queries to verify variable recovery accuracy
2. Evaluate cleaning agent's ability to remove noise while preserving query semantics
3. Measure human verification consistency by having multiple annotators rate query "interestingness"

## Limitations
- The human verification step introduces subjective bias in selecting which queries are "interesting" enough to include
- Claims of greater diversity lack rigorous quantitative validation across multiple metrics
- Evaluation focuses primarily on GRISP models, leaving uncertainty about performance with other semantic parsing approaches

## Confidence

Confidence labels:
- Dataset creation methodology: Medium - systematic but subjective
- Size and diversity claims: Medium - lacks rigorous comparative metrics  
- Performance improvements: High - clearly demonstrated on tested models
- Generalizability to other systems: Low - limited evaluation scope

## Next Checks
