# WebTrap Park: An Automated Platform for Systematic Security Evaluation of Web Agents

## Quick Facts
- arXiv ID: 2601.08406
- Source URL: https://arxiv.org/abs/2601.08406
- Reference count: 27
- Primary result: WebTrap Park introduces an action-based security evaluation platform; with GPT-4o, Agent-E (77.41%) and SeeAct (76.02%) outperform Browser Use (text) (72.26%) and Skyvern-AI (61.67%) on the security score (1 - Attack Success Rate), and proprietary models generally exceed open-source models.

## Executive Summary
WebTrap Park addresses the lack of standardized, reliable security evaluation for Web Agents by introducing an automated platform that assesses agents through direct observation of their concrete actions in live web environments, rather than relying on error-prone internal logs. It instantiates three major security risk sources (Malicious User Prompts, Malicious Prompt Injection, Deceptive Website Design) into 1,226 executable tasks and uses web instrumentation to monitor agent behavior without requiring code modifications. Results across 20 agent-model pairings reveal that agent architecture significantly impacts security, independent of the underlying model. Under the same GPT-4o model, Agent-E and SeeAct achieved the highest security scores, while proprietary models (GPT-4o, Claude-4-Sonnet) generally outperformed open-source models. The platform’s design enables fair, architecture-agnostic comparisons and provides a foundation for future web agent security research.

## Method Summary
WebTrap Park evaluates web agents by instrumenting web pages to intercept and log low-level user interactions (clicks, typed inputs) as they occur in a real browser. The platform hosts a suite of 1,226 tasks, each representing a specific security risk from three categories. Each task runs in an isolated Docker container managed by Kubernetes, with the agent connecting via a standard remote browser control endpoint. The instrumentation captures the agent’s actions and sends them to a backend server, which compares them against task-specific ground truth to determine success or failure, computing the Attack Success Rate (ASR) and a security score (1-ASR). This design allows assessment without modifying the agent’s code and enables standardized, reproducible testing across diverse agent architectures.

## Key Results
- Agent architecture significantly impacts security performance, independent of the underlying model.
- With GPT-4o, Agent-E (77.41%) and SeeAct (76.02%) achieve higher security scores (1-ASR) than Browser Use (text) (72.26%) and Skyvern-AI (61.67%).
- Proprietary models (GPT-4o, Claude-4-Sonnet) generally achieve higher average security scores than evaluated open-source models (Qwen2.5-72B-Instruct, Llama-3.3-70B-Instruct).

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Evaluating agents via direct observation of concrete actions in live web environments reduces misinterpretation risks compared to analysis of internal logs.
- **Mechanism:** The platform instruments web pages to intercept and log low-level user interactions (clicks, typed inputs) as they occur in a real browser. These action logs are sent to a backend server and compared against task-specific ground truth to determine success or failure.
- **Core assumption:** An agent's observable DOM-modifying actions are a reliable, architecture-agnostic proxy for its security-relevant behavior.
- **Evidence anchors:** [abstract] "...through direct observation of their concrete interactions with live web pages" and "shifting from inference based on internal logs to verification based on concrete actions." [section 2.1] "Our instrumentation focuses on capturing critical actions... We intercept the click or input events to extract the execution detail." [corpus] Neighbor papers (WASP, MUZZLE) also rely on action monitoring for prompt injection, providing indirect corroboration for the action-based paradigm, though WebTrap Park's scope is broader.
- **Break condition:** If an attack succeeds via non-DOM channels (e.g., JavaScript console execution, browser API abuse) that the instrumentation does not capture, the evaluation would produce false negatives.

### Mechanism 2
- **Claim:** Instantiating abstract security risk sources into a large, granular dataset of executable tasks enables comprehensive and standardized assessment.
- **Mechanism:** A taxonomy (Malicious User Prompts, Malicious Prompt Injection, Deceptive Website Design) guides the curation and creation of 1,226 specific, actionable tasks. Each task has a defined goal and clear success/failure criteria based on the agent's observed actions.
- **Core assumption:** Granular subtypes (e.g., "Invisible Form Aria," "Social-Proof") effectively capture the diversity of real-world attack vectors agents face.
- **Evidence anchors:** [abstract] "instantiates three major sources of security risk into 1,226 executable evaluation tasks." [section 2.1] Table 1 presents the full taxonomy and the "Task Construction" paragraph describes preserving and enriching existing benchmarks. [corpus] Limited direct corroboration; neighbor work like WASP focuses narrowly on prompt injection tasks, suggesting WebTrap Park's multi-risk dataset fills a gap.
- **Break condition:** Emergence of novel attack strategies (e.g., multi-turn contextual attacks) not represented in the current taxonomy would lead to underrepresentation of certain risk classes.

### Mechanism 3
- **Claim:** A containerized, model-agnostic service design allows seamless integration and fair comparison across diverse agent architectures without requiring code modification.
- **Mechanism:** Each task runs in an isolated Docker container managed by Kubernetes. The agent connects to a provided web environment via a standard interface (likely a remote browser control endpoint like a WebSocket). The platform's instrumentation is external to the agent, acting as a "man-in-the-middle" for the browser session.
- **Core assumption:** The external instrumentation approach is universally compatible with any agent that can drive a standard browser (e.g., via Selenium, Playwright, or remote debugging protocol).
- **Evidence anchors:** [abstract] "enables action based assessment without requiring agent modification" and "seamless integration." [section 3.2] Describes a three-stage workflow (Application, Provisioning, Testing) where the developer "runs the Web Agent locally to interact with web pages" and the platform "automatically monitors and records." [section 2.2] Details Docker encapsulation and Kubernetes Pod management for isolation.
- **Break condition:** Agents that bundle a custom, non-standard browser binary or rely on specialized browser extensions that bypass standard automation protocols may fail to connect or be fully observable.

## Foundational Learning
- **Web Agent Architecture Patterns** (e.g., SeeAct's vision-language-act loop vs. Browser Use's text/vision decision making). *Why needed:* Interpreting security score differences requires understanding how architectural choices (like planning depth, memory management, or input modality processing) influence susceptibility to deception or injection. *Quick check:* What is a plausible reason an architecture with a separate "planning" step might be more vulnerable to a "Urgency" deceptive pattern than a reactive architecture?
- **Prompt Injection & Deceptive Design Taxonomies**. *Why needed:* The 1,226 tasks are meaningless without understanding what "Invisible Form Aria" or "Trusted-Entity" deceptive design entails. This knowledge is prerequisite to validating the platform's coverage and interpreting results per risk type. *Quick check:* How does a "Malicious Prompt Injection" (MPI) task differ in goal from a "Deceptive Website Design" (DWD) task? Give an example of each.
- **Outcome-Based vs. Process-Based Security Evaluation**. *Why needed:* The paper's central argument is that outcome (final action) is a more reliable measure than process (internal logs). This concept challenges default assumptions about how to assess AI safety. *Quick check:* Why might an agent's "safe" textual reasoning trace coincide with a final "unsafe" click action on a webpage?

## Architecture Onboarding
**Component map:** Task Suite & Metadata DB -> Orchestration & API (Kubernetes) -> Isolated Execution Environment (browser + Web Instrumentation Layer) -> Evaluation Backend -> Leaderboard

**Critical path:** Developer Registration -> Platform Approval -> Received Task List & Connection Endpoint -> Launch Agent -> Agent connects to endpoint -> Agent navigates/interacts -> Instrumentation logs actions -> Backend evaluates -> Email with final score

**Design tradeoffs:**
- *Live Web vs. Sandbox:* Realism (captures real DNS, JS, ads) vs. reproducibility (external site changes can break tasks). The platform uses static, pre-seeded pages to mitigate this.
- *Isolation vs. Overhead:* One container per task ensures zero interference but increases resource cost. This is accepted for evaluation integrity.
- *Action-Based vs. Full State:* Logging only clicks/types is lightweight but may miss contextual state corruption (e.g., a hidden DOM change). Assumption: critical security actions involve explicit user-like interactions.

**Failure signatures:**
- **Agent-Side:** Connection timeout to the provided endpoint; inability to render or interact with the page (e.g., due to CSP); excessive latency causing task timeout.
- **Platform-Side:** Pod crash/restart; instrumentation failing to inject (malformed page); evaluation backend missing ground truth data for a task.
- **Result Discrepancy:** Low success rate on "Malicious User Prompt" tasks but high on "Deceptive Design" might indicate the agent is prompt-aligned but visually gullible.

**First 3 experiments:**
1. **Baseline Sanity Check:** Run the full 1,226-task suite with a known, simple agent (e.g., a scripted clicker) to verify the instrumentation and evaluation pipeline correctly identifies trivial failures and baseline vulnerability.
2. **Architecture Isolation Test:** Using the *same model* (e.g., GPT-4o), run Browser Use (text), Agent-E, SeeAct, and Skyvern-AI. Confirm the performance tiering (Agent-E/SeeAct > Browser Use > Skyvern-AI) from the paper holds, isolating architecture effect.
3. **Risk-Specific Stress Test:** Isolate the 300+ "Malicious Prompt Injection" tasks and run a single agent (e.g., Browser Use with GPT-4o). Manually inspect a sample of failure cases to verify the failure mode is indeed an *injection* (agent acting on injected text) vs. a simple navigation failure. This tests the dataset's precision and the evaluation rule's correctness.

## Open Questions the Paper Calls Out
### Open Question 1
**Question:** What specific architectural components or decision-making processes in Agent-E and SeeAct enable their superior security performance compared to Browser Use and Skyvern-AI when using the same GPT-4o model?
**Basis in paper:** [inferred] Results show clear security tiering across frameworks under identical model conditions (Figure 1), with Agent-E (77.41%) and SeeAct (76.02%) outperforming Browser Use (text) (72.26%) and Skyvern-AI (61.67%). The paper attributes differences to agent architecture but does not analyze the underlying mechanisms.
**Why unresolved:** The study identifies architecture as a key factor but does not dissect which specific design choices (e.g., prompting strategies, tool-use policies, feedback loops) contribute to resilience against the evaluated threats.
**What evidence would resolve it:** Controlled ablation studies that systematically vary individual architectural elements (e.g., input sanitization, action verification steps) within a single agent framework to measure their isolated impact on security scores across the WebTrap Park task suite.

### Open Question 2
**Question:** Do the observed security advantages of proprietary models (GPT-4o, Claude-4-Sonnet) over open-source models (Qwen2.5-72B-Instruct, Llama-3.3-70B-Instruct) hold across a wider variety of agent architectures beyond Browser Use (text)?
**Basis in paper:** [inferred] Figure 2 shows proprietary models achieve higher average security scores (72.26%, 65.01%) than open-source models (55.83%, 54.90%) when standardized to the Browser Use (text) framework. The paper speculates this may be due to "more sophisticated safety alignment."
**Why unresolved:** The comparison is confined to a single agent framework. It remains unclear whether the model-driven security gap generalizes to architectures with different interaction logics, as the framework itself may mediate model capabilities.
**What evidence would resolve it:** Repeating the evaluation with multiple agent frameworks (e.g., Agent-E, SeeAct) paired with both proprietary and open-source models to isolate the effect of the model from the framework and determine if the security disparity persists.

### Open Question 3
**Question:** How does the diversity and comprehensiveness of the WebTrap Park task suite (1,226 tasks across three risk dimensions) influence the validity and generalizability of its comparative security rankings for web agents?
**Basis in paper:** [explicit] The paper instantiates "three major sources of security risk" into 1,226 tasks and states the dataset is "comprehensive and extensible." However, it also notes future work to "broaden the scope" and incorporate more attack surfaces.
**Why unresolved:** While the taxonomy covers known risk categories, the distribution of tasks within each category and the inclusion of emerging or nuanced attack patterns are not detailed. Rankings could shift if task sampling bias exists or if new threat types are added.
**What evidence would resolve it:** A sensitivity analysis where the security scores of each agent are recomputed on stratified subsets of the current tasks (e.g., by subtype) and on candidate expanded tasks (e.g., new injection styles, deceptive designs) to measure ranking stability and identify potential coverage gaps.

### Open Question 4
**Question:** What critical security-relevant agent behaviors or vulnerabilities are not captured by WebTrap Park's instrumentation, which is limited to monitoring "click and type" actions in the web environment?
**Basis in paper:** [explicit] The instrumentation "focuses on capturing critical actions capable of modifying the web environment, namely click and type actions." The evaluation is "outcome-oriented" based on these intercepted actions.
**Why unresolved:** Web agents may engage in other actions (e.g., script execution, navigation, file downloads, API calls, handling pop-ups) that could indicate security failures or successes but are not systematically tracked. This could lead to incomplete or misleading assessments, especially for attacks that manipulate these other channels.
**What evidence would resolve it:** Extending the instrumentation to log a broader set of browser events (e.g., `executeScript`, `navigate`, `download`) and re-running the evaluation to analyze whether additional captured behaviors correlate with security outcomes not reflected in the current click/type-based metrics.

## Limitations
- Exact instrumentation details (e.g., element selection, event interception API) are undisclosed, creating reproducibility risk.
- Task composition specifics (website sources, ground truth rules) are opaque, hindering audit of coverage biases.
- Long-term viability depends on static task pages; real-world website evolution may degrade benchmark relevance.

## Confidence
- Action-based evaluation superiority: Medium
- Taxonomy coverage (1,226 tasks): Medium
- Architecture-agnostic integration: Low

## Next Checks
1. Instrumentation Fidelity Check: Run a scripted agent that uses both standard clicks and direct JavaScript execution (e.g., `eval()`) to confirm whether non-DOM actions are captured or produce false negatives.
2. Architecture Isolation Replication: Re-run the core comparison (Agent-E, SeeAct, Browser Use, Skyvern-AI) under identical GPT-4o and identical hardware/network conditions to verify the reported performance tiering.
3. Taxonomy Stress Test: Manually analyze 50 random failure cases from the "Malicious Prompt Injection" subset to validate that failures correspond to *injection* (agent following injected text) versus generic task completion errors.
