# Power and Limitations of Aggregation in Compound AI Systems

## Quick Facts
- **arXiv ID:** 2602.21556
- **Source URL:** https://arxiv.org/abs/2602.21556
- **Reference count:** 40
- **Primary result:** Aggregating multiple homogeneous LLM outputs can expand the set of elicitable outputs via three mechanisms—feasibility expansion, support expansion, and binding set contraction—demonstrated on a reference-generation task.

## Executive Summary
The paper investigates whether aggregating responses from multiple copies of an LLM using the same prompt can produce outputs unattainable by any single prompt. Framed as a principal‑agent problem, the system designer specifies reward functions while homogeneous agents generate outputs constrained to a conic feasibility set. The authors formally define *elicitability‑expansion* and prove that any aggregation that yields such expansion must implement at least one of three mechanisms: feasibility expansion (producing outputs outside individual cones), support expansion (combining lower‑support outputs into a higher‑support one), and binding set contraction (relaxing binding constraints). Strengthened versions provide necessary and sufficient conditions. Empirical validation with GPT‑4o‑mini on a paper‑title reference‑generation task confirms non‑zero expansion across all mechanisms, with ℓ1 gaps ranging from 0.03 to 0.94.

## Method Summary
The authors designed a controlled experiment to quantify expansion. The task: generate lists of ten paper titles representing a target topic distribution (output as a non‑negative M‑dimensional proportion vector). They used GPT‑4o‑mini with temperature 0 for deterministic generation. For each mechanism, they crafted specific prompt specifications that control inclusion/exclusion of topics and logical operators (and/or). Agent outputs (title lists) were converted to topic proportion vectors using an LLM‑as‑judge prompted to label each title with relevant topics from a fixed set. Aggregation was performed via two prompt styles: *addition* (union of themes) and *intersection* (common themes). The aggregated vector was compared to the best possible single‑prompt vector obtained by brute‑force search over all feasible prompt specifications (non‑empty topic subsets and connector choices). The ℓ1 distance between these vectors served as the expansion metric. The procedure was repeated 30 times per mechanism to compute average gaps and confidence intervals.

## Key Results
- Formal definition of *elicitability‑expansion* and proof that any power‑expanding aggregation must realize at least one of the three mechanisms; strengthened versions yield necessary and sufficient conditions.
- Empirical measurements on GPT‑4o‑mini show significant ℓ1 gaps for each mechanism: support expansion 0.58–0.94, binding set contraction 0.21–0.35, feasibility expansion 0.03–0.15, all statistically non‑zero.

## Why This Works (Mechanism)
Aggregation expands the elicitability set through three distinct pathways:
1. **Feasibility expansion:** The aggregated output may lie outside the feasible cone of any individual agent, thus unattainable by a single prompt.
2. **Support expansion:** Individual agents may produce outputs with limited topic coverage (small support); aggregation merges these to yield an output covering a broader set of topics (higher support).
3. **Binding set contraction:** Agents can have binding constraints that restrict certain combinations; aggregation can relax these constraints, producing outputs that would violate an individual agent’s binding set.

Each mechanism relaxes a different limitation of single‑agent elicitation, collectively enabling outputs beyond the original feasible region.

## Foundational Learning
1. **Principal‑Agent Framework**  
   *Why needed:* Models the designer (principal) setting rewards and agents (LLMs) acting under constraints, enabling formal analysis of incentives and capabilities.  
   *Quick check:* Can you describe how a reward function influences an agent’s feasible output set?

2. **Conic Feasibility Constraints**  
   *Why needed:* Assumes agents’ outputs lie in a convex cone, a mathematical structure that ensures closure under addition and non‑negative scaling, which simplifies aggregation analysis.  
   *Quick check:* If an agent’s feasible set is a cone, what does that imply about scaling any feasible output?

3. **Elicitability**  
   *Why needed:* Defines the set of outputs achievable by a single agent via any prompt; serves as the baseline for measuring expansion.  
   *Quick check:* Given a fixed reward, what does it mean for an output to be elicitable?

4. **Aggregation Operator**  
   *Why needed:* Determines how multiple agent outputs are combined; its properties directly affect whether and which expansion mechanisms occur.  
   *Quick check:* How would an intersection‑style aggregation differ from an addition‑style one in terms of support expansion?

## Architecture Onboarding
**Component map:**  
PromptSpec → LLM Agent (gpt‑4o‑mini) → Title List → Feature Extraction (LLM‑as‑Judge) → Topic Vector → Aggregation Operator → Aggregated Vector  
*Evaluation branch:* Brute‑Force Search over PromptSpecs → Best Single‑Prompt Vector

**Critical path:**  
1. Define task and reward (target topic distribution).  
2. Construct prompt specifications for individual agents (per mechanism).  
3. Generate raw title lists from agents.  
4. Convert titles to topic proportion vectors via LLM‑as‑judge.  
5. Apply aggregation prompt to obtain final list and vector.  
6. Compute ℓ1 distance between aggregated vector and best single‑prompt vector from exhaustive search.  
7. Repeat across trials for statistical confidence.

**Design tradeoffs:**
- *Homogeneity:* Using identical agents reduces variability but may limit the diversity needed for expansion.
- *Aggregation style:* Addition promotes support expansion; intersection may induce binding set contraction but risks empty outputs.
- *Determinism vs. randomness:* Fixed temperature ensures reproducibility but may under‑represent natural LLM variability.
- *Prompt space completeness:* Exhaustive search is infeasible for large topic sets; the paper restricts to small N, risking sub‑optimal baselines.
- *Judge automation:* LLM‑as‑judge scales but introduces potential labeling noise.

**Failure signatures:**
- Zero or negative ℓ1 gap (aggregated vector closer to best single than himself) indicates no expansion or benchmark error.
- Parsing failures from the judge (non‑yes/no responses) corrupt vectors.
- Aggregated title list length mismatch (≠10) requires truncation/padding, affecting fairness.
- Brute‑force search times out or returns a vector not truly optimal due to incomplete spec space.
- API rate limits or authentication errors interrupt data collection.

**Three first experiments:**
1. **Support expansion replication:** Use two agents with disjoint topic sets, generate titles, aggregate with addition‑style prompt, expect large ℓ1 gap (~0.7).
2. **Binding set contraction replication:** Construct agents whose individual binding constraints conflict, aggregate with intersection‑style prompt, expect moderate gap (~0.3).
3. **Feasibility expansion replication:** Design agents whose cones exclude a central target vector; aggregate to obtain a vector inside the combined cone, expect small but positive gap (~0.1).

## Open Questions the Paper Calls Out
1. **What empirical phenomena support binding set contraction?**  
   *Basis:* The authors leave this to future work. *Why unresolved:* The mechanism is theoretical; without concrete examples, designers cannot exploit it. *What would resolve it:* Identify real tasks where aggregation yields outputs with fewer binding constraint violations than any individual agent.

2. **Do real aggregation methods (e.g., debate, prompt ensembling) exhibit the three mechanisms?**  
   *Basis:* The authors call for testing practical methods. *Why unresolved:* Current experiments use contrived aggregation rules; it is unknown if standard techniques realize the mechanisms. *What would resolve it:* Evaluate existing aggregation protocols on problems with known feasibility/feature structures, checking for the mechanisms.

3. **How do nonlinear output constraints or feature mappings affect the characterization of elicitability‑expansion?**  
   *Basis:* The authors suggest extending to nonlinearities. *Why unresolved:* The theory relies on linear (conic) assumptions; nonlinearities may cause non‑convex sets and alter conditions. *What would resolve it:* Develop generalized theory for specific nonlinear classes (e.g., convex constraints) and validate on synthetic tasks.

4. **How does introducing stochasticity in agent outputs (e.g., temperature) change the aggregation power?**  
   *Basis:* The authors note the need to model randomness. *Why unresolved:* Determinism simplifies analysis; real LLMs are stochastic, potentially enabling new expansion forms. *What would resolve it:* Extend the model to handle distributions, analyze resulting elicitability sets, and run experiments at varying temperatures.

## Limitations
- **Model/task specificity:** Experiments limited to reference‑generation with GPT‑4o‑mini; findings may not generalize to other models or task types.
- **Prompt space completeness:** Brute‑force search over all prompt specifications is exponential; the paper’s restriction to small topic sets may miss the true best single‑prompt output, understating expansion.
- **Judge reliability:** LLM‑as‑judge labeling is automated and may produce parsing errors or biases; lack of human verification threatens metric accuracy.

## Confidence
- **Claim:** Three mechanisms are necessary for power‑expanding aggregation. **Confidence:** Medium (sound under framework assumptions, but assumptions may be restrictive).
- **Claim:** Empirical ℓ1 gaps for each mechanism are non‑zero. **Confidence:** Medium (gaps reported but statistical robustness and judge noise not fully addressed).
- **Claim:** Aggregation unlocks a strictly larger set of outputs than any single prompt. **Confidence:** Low–Medium (supported by limited experiments; needs broader validation).

## Next Checks
1. **Cross‑model replication:** Repeat the three mechanism experiments with GPT‑4, Claude, or other LLM families to test consistency.
2. **Expand task and aggregation diversity:** Include additional tasks (e.g., code generation, summarization) and aggregation methods (voting, weighted averages) to probe generalizability.
3. **Human‑based evaluation:** Have human annotators label topic proportions for a sample of outputs to verify LLM‑as‑judge accuracy and confirm that measured expansion corresponds to meaningful output diversity.
