# Multi-Field Tool Retrieval
## Quick Facts
- **arXiv ID**: 2602.05366
- **Source URL**: https://arxiv.org/abs/2602.05366
- **Reference count**: 40
- **Primary result**: Proposed Multi-Field Tool Retrieval (MFTR) achieves state-of-the-art performance on five tool retrieval datasets, improving Recall@10 by ~48% over the strongest baseline on the Gorilla dataset.

## Executive Summary
Tool retrieval for LLMs is hindered by three key limitations of treating tool documentation as flat text: incomplete/inconsistent documentation, semantic/granularity mismatch with user queries, and the multi-aspect nature of tool utility. This paper introduces the Multi-Field Tool Retrieval (MFTR) framework to address these issues. MFTR standardizes tool documentation into four canonical fields (description, parameters, response, examples), rewrites user queries into structured intents aligned with these fields, and computes adaptive field-specific relevance scores with a missing-parameter penalty. The method is retriever-agnostic and trained via pairwise ranking loss. Evaluated on five datasets and a mixed benchmark, MFTR significantly outperforms baselines in NDCG@10 and Recall@10 across both sparse and dense retrievers, demonstrating superior robustness and generalization in large-scale, heterogeneous settings.

## Method Summary
MFTR operates in three stages. First, it standardizes raw tool documentation using an LLM (gpt-4o-mini) to extract and reformat content into four consistent fields: description, parameters, response, and examples. Second, user queries are rewritten using an LLM prompted with top-20 BM25 pseudo-relevance feedback to produce a structured intent (task description) and explicit arguments, aligning query semantics with the field schema. Third, for retrieval, it computes separate similarity scores between the query and each field of a tool document (semantic matching for description/response/examples, exact/partial matching for parameters with a learnable missing-parameter penalty). A final relevance score is a weighted sum of these field scores, where the weights are learned end-to-end via a pairwise ranking loss (using negatives sampled from BM25 errors) in a 5-fold cross-validation setup. The training process uses Adam (lr=0.1, batch=256, 5 epochs) and is applicable with any underlying retriever (BM25, dense models).

## Key Results
- MFTR sets new state-of-the-art on five tool retrieval datasets (ToolBench, APIGen, APIBank, Gorilla HF, Toolink) and a mixed benchmark, significantly surpassing prior best methods in NDCG@10 and Recall@10.
- Using the MiniLM-L6 dense retriever on the Gorilla dataset, MFTR improves Recall@10 by approximately 48% compared to the strongest baseline.
- The framework shows consistent gains across diverse retrievers (BM25, Sentence-BERT, Contriever) and demonstrates greater robustness in heterogeneous, large-scale tool pools.

## Why This Works (Mechanism)
MFTR works because it directly counteracts the three core limitations of flat-document retrieval. The four-field schema introduces fine-grained structure, enabling the system to treat different aspects of a tool (what it does, how to call it, what it returns, usage examples) separately. This resolves the semantic/granularity mismatch: a query about "convert currency" can precisely match a tool's "response" field mentioning exchange rates, even if the "description" is vague. Query rewriting aligns user intent with the field terminology, reducing vocabulary gap. The adaptive weighting allows the system to learn which fields are most discriminative for a given dataset or query type (e.g., parameters might be critical for API lookup, while examples matter for conceptual tools). The missing-parameter penalty explicitly discourages retrieving tools whose required parameters are not satisfied by the query arguments, directly addressing the multi-aspect utility problem where a tool must be usable as a whole. By making these aspects explicit and learnable, MFTR produces a more nuanced and accurate relevance signal than a single holistic similarity score.

## Foundational Learning
- **Field-centric Documentation Schema**: Standardizing docs into fixed fields (description, parameters, response, examples) provides a consistent structure for matching. *Why needed*: Raw docs are messy, incomplete, and inconsistent; fields isolate different utility dimensions. *Quick check*: Verify that >90% of tools in a dataset can be cleanly mapped to all four fields after standardization.
- **Query Decomposition & Alignment**: Rewriting natural language queries into structured intents and arguments bridges the user's mental model and the tool's technical specification. *Why needed*: Users ask ("weather in Paris") while tools require parameters (city="Paris"); alignment is necessary for precise parameter matching. *Quick check*: For 50 random queries, confirm that the extracted arguments match the key constraints in the ground-truth tool's parameters.
- **Adaptive Field Weighting**: Learning a weight for each field's similarity score allows the model to emphasize the most informative aspects per dataset. *Why needed*: The importance of description vs. parameters varies by domain (e.g., data processing APIs vs. creative tools); uniform weighting is suboptimal. *Quick check*: After training, inspect learned weights—they should differ significantly across datasets (as shown in Table 5).
- **Missing-Parameter Penalty**: A learnable penalty term is subtracted when a tool's required parameters are not satisfied by the query's provided arguments. *Why needed*: A tool is useless if the user cannot provide a mandatory parameter; this penalizes partial matches that are functionally invalid. *Quick check*: Simulate a query lacking a required parameter; the tool's score should drop substantially compared to a tool with that parameter optional.
- **Retriever-Agnostic Scoring**: The field scoring and weighting operate on top of any base retriever's similarity scores. *Why needed*: Allows plug-and-play improvement for existing IR systems (BM25, dense models) without retraining the entire retriever. *Quick check*: Swap the base retriever (e.g., from BM25 to Contriever) and confirm MFTR's relative gains remain stable.
- **Pseudo-Relevance Feedback for Rewriting**: Using BM25 top-20 results as context for the LLM during query rewriting grounds the intent in actual tool terminology. *Why needed*: Prevents the LLM from generating overly generic or hallucinated intents that don't match the vocabulary of available tools. *Quick check*: Compare rewritten intents with and without BM25 context; the latter should show less overlap with actual tool descriptions.

## Architecture Onboarding
**Component Map**  
Raw Tool Docs -> LLM Standardization -> Four-Field Docs (Description, Parameters, Response, Examples)  
User Query -> BM25 Feedback -> LLM Query Rewriter -> Structured Query (Intent, Arguments)  
Four-Field Docs + Structured Query -> Field Scorers (Semantic/Param Match) -> Field Scores -> Adaptive Weighting (w_f, b) + Missing Penalty (τ) -> Final Score -> Ranking

**Critical Path**  
1. Standardization (ensures all tools have comparable fields)  
2. Query Rewriting (ensures query is expressed in the same "language" as the fields)  
3. Parameter Matching & Penalty (ensures functional usability constraint is met)  

**Design Tradeoffs**  
- *Schema Granularity*: More fields capture more nuance but increase LLM hallucination risk and complexity. The four-field choice balances coverage and stability.  
- *Weight Model*: Linear weighting is simple and trainable with few samples; a neural aggregator could model field interactions but would require more data and risk overfitting.  
- *LLM Dependence*: Using gpt-4o-mini for standardization/rewriting leverages strong NLP capabilities but introduces cost, latency, and potential inconsistency; a local model could reduce this but may sacrifice quality.  

**Failure Signatures**  
- *Standardization failures*: Inconsistent field extraction (e.g., parameters appearing in description), hallucinated examples.  
- *Query rewriting failures*: Extracted arguments don't match any tool's parameter names; intent is too vague ("help with data").  
- *Training failures*: Validation loss diverges, indicating unstable weight updates (common on small datasets like APIBank).  
- *Retrieval failures*: High-scoring tools have missing required parameters despite the penalty, suggesting τ is not learned properly.  

**First Three Experiments**  
1. **Baseline Replication**: Reproduce the Full-Doc (raw docs, no rewriting) baseline results for all retrievers on Gorilla to establish a correct evaluation pipeline.  
2. **Prompt Audit**: Manually inspect 50 standardized documents and 30 rewritten queries from the MFTR pipeline to quantify hallucination rates and alignment accuracy.  
3. **BM25 Sensitivity**: Re-run MFTR with varied BM25 configurations (different tokenizers, k1/b values) on APIGen to measure robustness to pseudo-relevance feedback quality.

## Open Questions the Paper Calls Out
### Open Question 1
How can we improve the robustness of tool documentation standardization when source documents are extremely incomplete or inconsistent, without relying on LLM hallucination?

### Open Question 2
Is the four-field schema (description, parameters, response, examples) optimal for capturing tool utility, or could alternative field sets or granularities yield better retrieval performance?

### Open Question 3
Can we model field interactions more effectively than the current linear weighting scheme—e.g., through neural or non-linear aggregation—to better combine multi-field relevance signals?

### Open Question 4
Does the improvement in retrieval metrics from MFTR translate into higher success rates for LLM agents in real tool-using tasks?

## Limitations
- **Implementation Underspecification**: Critical details like exact LLM prompts, BM25 hyperparameters (k1, b, tokenizer), dataset split generation, and adaptive weight initialization/regularization are not reported, hindering precise reproduction.
- **Hallucination Risk**: The LLM-based standardization may invent or distort content when source docs are sparse, potentially injecting semantic noise that harms retrieval.
- **Linear Aggregation**: The final scoring is a linear combination of field similarities, which may underutilize complex cross-field dependencies that affect tool utility.
