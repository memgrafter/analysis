# Dimensional Peeking for Low-Variance Gradients in Zeroth-Order Discrete Optimization via Simulation

## Quick Facts
- **arXiv ID:** 2602.00075
- **Source URL:** https://arxiv.org/abs/2602.00075
- **Reference count:** 39
- **Primary result:** Dimensional peeking reduces gradient variance (up to 7.9×) and accelerates convergence on discrete simulation problems, with a runtime overhead of 9–28%.

## Executive Summary
Zeroth-order gradient estimation is essential for optimizing black-box simulations where gradients are unavailable, but high variance in the estimates often impedes convergence, especially in discrete, non‑convex settings. This paper introduces *dimensional peeking*, a technique that groups perturbations by control‑flow equivalence, allowing all relevant alternatives per dimension to be evaluated in a single simulation run. Rooted in Polyak’s Gradient Oracle, the estimator remains unbiased while substantially lowering variance. Empirical evaluation on three simulation benchmarks—CityFlow (144 variables), Hotel (56), and DynamNews (1000)—shows variance reductions of up to 7.9× and convergence speedups of up to 4.1× compared to both standard gradient methods and meta‑heuristics, albeit with a modest 9–28% increase in simulation time. The approach thus enhances the practicality of zeroth‑order optimization for challenging discrete simulation problems.

## Method Summary
Dimensional peeking reimagines standard zeroth‑order perturbation by exploiting control‑flow equivalence. Instead of performing separate simulations for each perturbation, the method intelligently combines them so that all necessary alternatives for a given dimension are evaluated in a single simulation execution. This is achieved through a custom `pfloat` data type in C++ that overloads arithmetic and comparison operators to record boolean masks indicating which branch decisions were taken during the simulation. After the run, these masks are analyzed to disentangle the effects of each perturbation, reconstructing the gradient components for all dimensions. The estimator is derived from Polyak’s Gradient Oracle, guaranteeing unbiasedness. Implementation leverages vectorization for efficiency, though the custom type and mask tracking introduce some overhead.

## Key Results
- Variance reductions: 2.6× on CityFlow (144 variables), 7.9× on Hotel (56), and 1.5× on DynamNews (1000) at coverage radius c=3σ.
- Convergence speed: PGO‑DP significantly outperformed PGO and meta‑heuristics (GA, PSO, CMA‑ES) on Hotel and DynamNews (up to 4.1× faster); on CityFlow both gradient methods beat meta‑heuristics but were similar to each other.
- Overhead: Execution time increased by 9–28% relative to standard zeroth‑order estimation due to the custom `pfloat` and equivalence tracking.

## Why This Works (Mechanism)
The core of dimensional peeking lies in grouping perturbations that lead to identical control‑flow paths within the simulation. By reusing a single simulation run to estimate multiple gradient components, the random noise inherent to the simulation is shared across those estimates, dramatically reducing variance. The derivation from Polyak’s Gradient Oracle ensures that the grouping does not introduce bias, preserving the estimator’s correctness. The custom `pfloat` type and boolean mask tracking enable the detection of equivalence without requiring additional simulation repetitions, making the variance reduction cost‑effective despite the modest overhead.

## Foundational Learning
**Zeroth‑Order Optimization** – Optimizes using only function evaluations; needed when gradients are unavailable (e.g., black‑box simulations). *Quick check:* Verify that a finite‑difference gradient estimate approximates the true gradient on a smooth test function.

**Polyak’s Gradient Oracle** – A theoretical construct for unbiased gradient estimation via two‑point or multi‑point finite differences; underlies methods like SPSA. *Why needed:* Provides a formal basis for unbiasedness. *Quick check:* Confirm estimator expectation equals the true gradient on a linear function.

**Control‑Flow Equivalence** – When different input perturbations cause identical branching outcomes in code; allows reuse of a single simulation for multiple gradient component estimates. *Why needed:* Reduces the number of required simulation runs. *Quick check:* Instrument code to log branch decisions and compare masks for different perturbations.

**Variance Reduction** – Techniques to lower the variability of stochastic estimators; crucial for faster convergence. *Why needed:* High variance leads to many evaluations to obtain accurate gradients. *Quick check:* Compare empirical variance of estimates against a baseline over repeated trials.

**Vectorization (SIMD)** – Processing multiple data elements in parallel using CPU vector units; speeds up elementwise operations like those in `pfloat`. *Why needed:* Offsets overhead introduced by custom data types. *Quick check:* Benchmark a vectorized loop against its scalar counterpart to measure speedup.

## Architecture Onboarding
**Component map**  
Input → pfloat Generation → Simulation with Masked Operations → Control Flow Mask Extraction → Gradient Reconstruction → Output

**Critical path**  
The dominant cost is the single simulation run that executes with instrumented `pfloat` operations. After completion, mask extraction and gradient reconstruction are performed; these steps are comparatively lightweight but contribute to the overall overhead.

**Design tradeoffs**  
- *Correctness vs overhead*: Custom `pfloat` ensures precise control‑flow tracking but adds syntactic complexity and may inhibit compiler optimizations.  
- *Generality vs implementation effort*: The approach requires that all potentially branching operations be wrapped; integrating with closed‑source or highly complex simulators can be difficult.  
- *Variance reduction vs memory*: Storing boolean masks for many dimensions consumes memory; trade‑offs exist between mask granularity and memory footprint.

**Failure signatures**  
- *Bias*: If estimated gradients show non‑zero mean on a symmetric test function (e.g., sum of sines) or mismatch known gradients on simple cases, equivalence grouping likely failed.  
- *Excessive overhead*: Runtime increase beyond 30% suggests that instrumentation is too heavy or prevents vectorization.  
- *Mask collisions*: When the number of distinct control‑flow paths exceeds the bits allocated for masks, collisions cause misgrouping, leading to increased variance or bias.

**First experiments**  
1. *Unbiasedness validation*: Apply the estimator to a linear function f(x)=a·x; over many trials, the mean gradient estimate should equal a.  
2. *Variance comparison*: On a smooth quadratic function, compare the variance of the proposed estimator against standard SPSA while keeping the total number of function evaluations constant.  
3. *End‑to‑end overhead benchmark*: Instrument a simple discrete‑event simulator and measure the per‑run time increase relative to the uninstrumented version.

## Limitations
- **Generalizability**: Experiments on only three simulation problems; findings may not extend to other discrete settings.  
- **Radius dependency**: Variance reduction evaluated at a single coverage radius (c=3σ); behavior for other radii remains unknown.  
- **Overhead**: 9–28% execution time increase could be prohibitive in large‑scale deployments; hardware and scaling details are sparse.
