# PASCAL: A Phase-Aware Scheduling Algorithm for Serving Reasoning-based Large Language Models

## Quick Facts
- **arXiv ID:** 2602.11530
- **Source URL:** https://arxiv.org/abs/2602.11530
- **Reference count:** 40
- **Primary result:** PASCAL reduces tail Time-To-First-Token (TTFT) by up to 72% while maintaining answering-phase SLO attainment (>0.95) and keeping throughput within 3% of baseline schedulers.

## Executive Summary
PASCAL is a phase-aware scheduling algorithm designed to serve reasoning-based large language models (LLMs) that generate output in two distinct phases: a hidden reasoning phase (Chain-of-Thought) and a user-visible answering phase. By distinguishing these phases, PASCAL applies different scheduling policies: it prioritizes reasoning requests to minimize the Time-To-First-Token (TTFT), and during the answering phase it uses controlled preemption with token pacing to preserve quality-of-experience (QoE). The system employs a two-level hierarchical scheduler that makes instance-level placement decisions based on phase-specific load and intra-instance priority queues, with dynamic request migration at phase boundaries. Evaluations on DeepSeek-R1-Distill-Qwen-32B using AlpacaEval2.0 and Arena-Hard datasets show tail TTFT reductions of up to 72% relative to first-come-first-served (FCFS) scheduling, while meeting answering-phase SLO targets and maintaining throughput within 3% of baselines.

## Method Summary
PASCAL modifies the vLLM serving framework without retraining the model. It detects phase boundaries using the special token `<think>`. At the instance level, reasoning requests are routed to SLO-compliant instances with smallest KV cache footprint (Algorithm 1). When a request transitions to answering, it is migrated to the instance with the fewest reasoning requests (Algorithm 2), with an adaptive check that skips migration if the current instance has sufficient memory. Intra-instance scheduling uses two priority queues: a high-priority queue for reasoning requests scheduled round-robin, and a low-priority queue for answering requests also round-robin but with a token pacer that smooths output to a target Time-Per-Output-Token (TPOT ≤ 100 ms). Reasoning requests with KV cache exceeding 5 000 tokens are demoted to the low-priority queue to avoid starvation of answering requests. The token quantum is set to 500 tokens. The system is evaluated using a profile-based simulator validated with less than 13% MAPE error against real measurements, under synthetic Poisson workloads at three arrival rates that saturate GPU memory when constrained to 50% of oracle capacity.

## Key Results
- Tail TTFT reduced by up to 72% vs. FCFS and 29% vs. RR baselines.
- Answering-phase QoE maintained above the 0.95 threshold, with SLO violation rates comparable to or lower than baselines.
- Throughput remains within 3% of FCFS and RR schedulers across load levels.

## Why This Works (Mechanism)
PASCAL’s effectiveness stems from its phase-aware prioritization and controlled migration. Reasoning requests receive immediate access to GPU resources through a high-priority queue, reducing the latency until the first user-visible token (TTFT). Once reasoning completes, requests migrate to less loaded instances for answering, preventing interference with subsequent reasoning workloads. The token pacer in the answering phase ensures a steady output rate, satisfying TPOT targets and preserving QoE. Adaptive migration avoids unnecessary overhead when memory is adequate. The two-level hierarchy balances global load distribution with local scheduling efficiency, while demotion of long-running reasoning requests protects answering-phase SLOs.

## Foundational Learning
- **Phase-aware scheduling:** Separates work into logically distinct stages (reasoning vs. answering) to apply different policies. Why needed: Different latency sensitivities; answering requires steady output while reasoning is pre-generative. Quick check: Can you identify the phase transition token in the model's output?
- **Time‑To‑First‑Token (TTFT):** Latency from request arrival to emission of the first user‑visible token. Why needed: Primary metric for responsiveness in interactive LLM services. Quick check: Does reducing TTFT always improve user satisfaction? (Consider quality trade‑offs.)
- **Token pacing / preemption:** Mechanism to smooth output inter‑token intervals, often via a token bucket or similar. Why needed: Maintains QoE by meeting TPOT targets during answering. Quick check: How would a naive round‑robin scheduler affect TPOT variability?
- **KV cache management:** Shared memory storing key‑value states for autoregressive generation. Why needed: Memory footprint grows with sequence length, influencing instance placement and migration decisions. Quick check: What happens when KV cache exceeds GPU memory?
- **Priority queues with demotion:** Scheduler structure that can lower priority of long‑running requests. Why needed: Prevents starvation of short, latency‑sensitive answering requests. Quick check: Under what condition does PASCAL demote a reasoning request?
- **Adaptive migration:** Conditional request transfer between instances based on memory availability. Why needed: Reduces unnecessary migration overhead while balancing load. Quick check: Why might skipping migration be beneficial even if the target has fewer reasoning requests?

## Architecture Onboarding
Component map (plain text):
Client -> Dispatcher (Router) -> Instance Selector -> GPU Instances (each with Scheduler: High‑priority Q, Low‑priority Q + Token Pacer) -> Model Execution -> Output. Additionally: KV Cache Migrator (between instances) and Phase Monitor (detects `<think>`).

Critical path:
1. Request arrives.
2. Dispatcher invokes Instance Selector (Algorithm 1) to choose an instance for reasoning.
3. Reasoning phase executes on chosen instance, tokens placed in high‑priority queue.
4. Phase Monitor detects `<think>` token, triggers migration decision (Algorithm 2).
5. If needed, KV cache is copied to target instance; request enters low‑priority queue there.
6. Token Pacer regulates token emission, producing first answering token (TTFT measured) and subsequent tokens at target TPOT.

Design tradeoffs:
- Prioritizing reasoning reduces TTFT but risks answering‑phase SLO violations if not migrated; PASCAL mitigates with migration and token pacing.
- Migration overhead (network + queueing) vs. load balancing benefits; adaptive migration reduces overhead when memory permits.
- Token pacer adds buffering latency to answer, but necessary for smooth output; quantum size (500 tokens) balances fairness and overhead.

Failure signatures:
- High tail TTFT: reasoning requests starved or migration too slow.
- Low QoE (SLO violations): token pacer misconfigured or answering requests blocked by long reasoning tails.
- Throughput drop >3%: excessive migrations or suboptimal instance selection.
- Priority inversion: demotion threshold too low, causing many reasoning requests to be treated as answering.

First three onboarding experiments:
1. Validate phase detection by feeding a trace with known `<think>` positions and confirming that the trigger fires correctly.
2. Compare TTFT under low load for PASCAL vs. FCFS and RR to quantify reduction.
3. Toggle adaptive migration off and measure impact on throughput and TTFT to verify its benefit.

## Limitations
- Token pacer implementation details (buffer size, release algorithm) are underspecified, which could affect answering‑phase QoE measurements.
- SLO compliance detection (measurement window, TPOT calculation during pacing) is not fully described, leading to ambiguity in evaluation.
- Generalizability is limited: evaluation uses only one model (DeepSeek‑R1‑Distill‑Qwen‑32B) and two datasets; performance on other architectures or tasks is unknown.

## Confidence
- Tail TTFT reduction (up to 72%): Medium (algorithm well‑specified but sensitive to unspecified parameters).
- Answering‑phase SLO attainment (≥0.95): Medium (depends on token pacer and SLO detection details).
- Throughput within 3% of baselines: Medium (overheads described but migration models could introduce variance).
