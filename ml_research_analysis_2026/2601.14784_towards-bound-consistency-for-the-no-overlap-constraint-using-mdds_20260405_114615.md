# Towards Bound Consistency for the No-Overlap Constraint Using MDDs

## Quick Facts
- **arXiv ID:** 2601.14784
- **Source URL:** https://arxiv.org/abs/2601.14784
- **Reference count:** 9
- **Primary result:** Introduces the first bound-consistent algorithm for no-overlap via MDDs, with exact O(|E|) and relaxed O(n²W) variants; relaxed filtering reduces search more than precedence extraction and is complementary to classical propagation.

## Executive Summary
This paper addresses the NP-complete problem of achieving bound consistency for the no-overlap constraint in scheduling. It introduces the first bound-consistent algorithm by leveraging the no-overlap MDD, computing exact earliest start and latest end times in time linear in the MDD’s edges. For scalability, a polynomial-time relaxed variant bounds the MDD width to W, running in O(n²W). Experiments on just-in-time scheduling show the relaxed BC filtering, even with a width limit, reduces search tree nodes more effectively than the prior precedence-detection MDD method. On smaller instances, the relaxed approach achieves search tree expansion within 5% of the exact bound-consistent method when W=32, while the exact method incurs exponential runtime overhead. The filtering is also complementary to classical propagation, substantially lowering nodes and solving time on multiple benchmarks.

## Method Summary
The approach constructs a Multi-valued Decision Diagram (MDD) representing all feasible job sequences. For exact bound-consistency, it scans each edge of the exact no-overlap MDD to extract the minimum earliest-start coordinate for each job, yielding O(|E|) time. To handle larger instances, a relaxed MDD limits layer width to W via bucketing of state values, with compilation time O(n²W). An incremental refinement procedure updates the MDD during search as domains shrink: invalid edges are removed, dead-end nodes pruned, and layers re-expanded when width permits. The resulting bounds are applied redundantly alongside classical propagation to tighten time windows.

## Key Results
- Exact BC algorithm runs in O(|E|) time on exact NO-MDD but suffers exponential blowup (e.g., ~9000s for n=16).
- Relaxed BC with width bound W runs in O(n²W) and reduces search tree nodes more effectively than precedence-detection MDD; at W=32, within 5% of exact BC on smaller instances.
- MDD-based filtering is complementary to classical propagation, significantly lowering nodes and solving time on multiple benchmarks.

## Why This Works (Mechanism)

### Mechanism 1
**Claim:** An exact bound-consistent (BC) filter for start/end times can be computed by scanning all edges of the exact No-Overlap MDD.  
**Mechanism:** For each job *i*, the earliest feasible start time *sᵢ* is set to the minimum `E↓` (earliest start state) among all edges labeled *i* in the MDD. This captures the earliest *i* can appear in any valid full sequence because every root-to-sink path encodes a feasible schedule.  
**Core assumption:** The exact MDD contains *all* feasible sequences (permutations respecting release times and deadlines). Thus, the minimum over its edges gives the true earliest start.  
**Evidence anchors:**  
  - [abstract]: "extract bounds of the time window of the jobs... in time linear in the MDD’s edges (O(|E|))"  
  - [section 2.2]: Describes formula (1) `sᵢ ← max(sᵢ, min_{e:ϕₑ=i} E↓_{e.orig})` and states "These filtering rules ensure bound-consistency."  
**Break condition:** If the exact MDD construction inadvertently prunes feasible sequences (e.g., due to implementation error or horizon *H* too small), the computed bounds may be incorrect (too loose or inconsistent).

### Mechanism 2
**Claim:** Relaxing the MDD by bounding layer width to *W* yields a polynomial-time (O(n²W)) filtering that still reduces search more than precedence extraction.  
**Mechanism:** During top-down MDD compilation, nodes are merged within layers by bucketing their `E↓` values into *W* intervals (operator ⊕). The resulting "relaxed" MDD represents a superset of sequences. The same edge-scanning rule (Mechanism 1) is applied, but now on this superset, giving "relaxed BC" bounds.  
**Core assumption:** Merging nodes based on similar `E↓` creates a manageable MDD while preserving enough sequential information to tighten time windows meaningfully.  
**Evidence anchors:**  
  - [abstract]: "limit the width of the MDD to a threshold... running in O(n²W)... reduces search tree nodes more effectively than the prior precedence-detection MDD method."  
  - [section 3.1]: Defines relaxed state `⟨A↓, S↓, E↓, K⟩` and merge operator ⊕ based on `E↓` bucketing.  
  - [section 3.3]: "Applying our BC filtering or extracting the precedences on a relaxed NO-MDD follows the same formulas as in the exact ones."  
**Break condition:** If bucketing merges states with genuinely different sequencing implications (e.g., one state enables a job *i* earlier than another), the computed `min E↓` for *i* may be artificially high (loose), weakening filtering.

### Mechanism 3
**Claim:** Incremental MDD refinement during search maintains filtering strength without full recomputation.  
**Mechanism:** As domains shrink, `λ′` may invalidate some transitions. The MDD is updated: remove invalid edges, prune orphan/dead-end nodes, then if a layer’s width falls below *W*, re-expand nodes from previous layers using `τ′` and re-merge via ⊕. This dynamically tightens the MDD.  
**Core assumption:** Search progresses by tightening variable domains, so the MDD can be *refined* (transitions removed) rather than rebuilt; occasional re-expansion captures newly feasible partial sequences.  
**Evidence anchors:**  
  - [section 3.2]: Describes the "refinement procedure" including edge extraction, node removal, and re-expansion when width allows.  
  - [example 5]: Shows stepwise refinement where extracting edges gradually tightens `s₄` to 8.  
**Break condition:** If domain shrinkages frequently invalidate many transitions, the refinement cycle (update → prune → re-expand) could become costly, approaching full rebuild cost, or may create oscillations if re-expansion reintroduces previously pruned infeasible paths.

## Foundational Learning
- **MDD (Multi-valued Decision Diagram)**  
  **Why needed here:** The entire approach relies on the No-Overlap MDD structure to represent all feasible job sequences compactly (exact) or approximately (relaxed). Understanding nodes (states), edges (labeled jobs), and compilation (top-down with node merging) is essential.  
  **Quick check:** How does the state `⟨A↓, E↓⟩` in the exact MDD differ from `⟨A↓, S↓, E↓, K⟩` in the relaxed MDD, and why is `S↓` needed for precedence extraction?

- **Bound Consistency (BC)**  
  **Why needed here:** BC is the target filtering strength for the no-overlap constraint. It requires that for every start/end variable, the current bound is contained in some solution. The paper’s core contribution is achieving BC (exact) or approximating it (relaxed).  
  **Quick check:** Why is achieving BC for no-overlap NP-complete, yet the exact MDD-based algorithm runs in O(|E|)? What does this imply about the relationship between problem complexity and representation size?

- **Disjunctive Scheduling & Classical Propagation**  
  **Why needed here:** The no-overlap constraint enforces disjunctive scheduling (jobs cannot overlap). The paper contrasts MDD-based filtering with classical polynomial-time techniques (edge finding, not-first-not-last). Understanding the baseline is key to appreciating the complementarity benefit.  
  **Quick check:** What does "detectable precedence" mean in the context of no-overlap, and why might it fail to detect a precedence like `1 ≺ 4` in Example 1?

## Architecture Onboarding
- **Component map:**  
  MDD Builder -> MDD Refiner -> Propagator -> Scheduler Core  
  (optional: Precedence Extractor for comparison)

- **Critical path:** On constraint activation or after domain events, the MDD is built or refined → Propagator scans edges → Updates variable bounds → Fixpoint with other propagators.

- **Design tradeoffs:**  
  - **Width *W*:** Larger *W* → tighter bounds (closer to BC) but more memory and compilation time; smaller *W* → faster but looser.  
  - **Exact vs. Relaxed:** Exact BC is only feasible for very small *n* (exponential blowup). Relaxed is practical but not guaranteed BC; empirical evaluation shows `W=32` gets within 5% of BC on tested instances.  
  - **Redundancy:** MDD-based filtering is used *redundantly* alongside classical propagation, blending benefits without replacing core algorithms.

- **Failure signatures:**  
  - **Memory explosion:** Exact MDD width grows combinatorially (observed ~20k nodes for *n*=12). Monitor node count per layer; abort if exceeding limit.  
  - **Poor filtering:** Relaxed MDD with very small *W* (e.g., 4) may not tighten bounds beyond classical methods. Check if new bounds differ from baseline after propagation.  
  - **Stagnant refinement:** If MDD refinement rarely triggers re-expansion, the MDD may be too relaxed (large buckets) or domains not shrinking enough. Monitor frequency of layer re-expansions.

- **First 3 experiments:**  
  1. **Validation against exact BC:** For small *n* (12–16), replay search trees comparing relaxed BC (vary *W*) and precedence extraction against exact BC. Measure search tree expansion `g = (Z - Z')/Z'`. Expected: relaxed BC with `W=32` has `g < 5%`.  
  2. **Scalability & complexity:** Time the MDD operations (build/refine + scan) per search node for varying *n* and *W*. Expected: relaxed BC ~ O(n²W), precedence extraction ~ O(n³W). Confirm quadratic vs. cubic growth experimentally.  
  3. **Complementarity test:** Run four models: (i) classical only, (ii) classical + relaxed BC, (iii) classical + precedence extraction, (iv) classical + both MDD-based. Measure nodes/time on medium instances (*n*=40). Expected: (ii) and (iii) both reduce nodes vs. (i); (ii) reduces more than (iii); combining both may yield further reduction on some instances.

## Open Questions the Paper Calls Out
1. **How can the exponential runtime of exact bound-consistent filtering be mitigated for larger no-overlap instances?**  
   **Basis in paper:** [explicit] The paper states the exact BC method incurs exponential runtime (e.g., ~9000s for n=16) due to MDD size explosion, limiting scalability.  
   **Why unresolved:** The method is only evaluated on small instances (n ≤ 16); no algorithmic improvements are proposed to handle larger problems.  
   **What evidence would resolve it:** An exact BC algorithm with provably better worst-case complexity or empirical results showing feasibility on instances with n > 20.

2. **What is the theoretical relationship between relaxed MDD width W and the gap to exact bound-consistency?**  
   **Basis in paper:** [inferred] The paper empirically shows that larger W reduces search tree expansion (e.g., W=32 gives <5% gap), but provides no theoretical analysis of how W affects filtering quality.  
   **Why unresolved:** The choice of W is heuristic (e.g., W=16 as compromise); the gap as a function of W and instance properties remains uncharacterized.  
   **What evidence would resolve it:** A theoretical bound on the difference between relaxed and exact BC bounds in terms of W, job time window characteristics, and experimental validation across diverse instances.

3. **Why does precedence extraction fail to achieve bound-consistency even on exact MDDs, and can it be enhanced?**  
   **Basis in paper:** [explicit] Example 6 demonstrates precedence extraction does not tighten the window for job t4, while BC does, even on the exact MDD.  
   **Why unresolved:** The paper identifies this limitation but does not analyze the structural reasons or propose enhancements.  
   **What evidence would resolve it:** A formal characterization of when precedence extraction suffices for BC, and an extension that extracts additional implied constraints (e.g., higher-order precedences) efficiently within the MDD.

4. **What is the optimal integration strategy for MDD-based filtering with classical propagation in solvers?**  
   **Basis in paper:** [explicit] The paper notes the new filtering is complementary to classical methods and, when used redundantly, reduces nodes and time, but does not explore integration tactics.  
   **Why unresolved:** They apply MDD filtering as a static redundant constraint without investigating propagation ordering, activation frequency, or dynamic toggling.  
   **What evidence would resolve it:** A systematic study comparing integration schemes (e.g., always-on, conflict-driven activation) on diverse benchmarks to identify performance patterns and guidelines.

## Limitations
- Exact BC algorithm scales exponentially (e.g., ~9000s for n=16), restricting use to trivial instances.
- Relaxed BC’s bucketing heuristic (⊕) lacks theoretical guarantees on approximation error; worst-case looseness unknown.
- Experiments solely on JIT scheduling benchmarks; generalizability to other disjunctive/constraint types untested.

## Confidence
- **Exact BC via MDD edge scanning:** Medium (theoretically sound but computationally infeasible beyond n≈12).
- **Relaxed BC via width-bounded MDD:** Low-Medium (empirical gains on JIT, but heuristic nature and narrow evaluation scope).
- **Empirical superiority over precedence extraction:** Medium (consistent on JIT, but compared only to one prior MDD method).
