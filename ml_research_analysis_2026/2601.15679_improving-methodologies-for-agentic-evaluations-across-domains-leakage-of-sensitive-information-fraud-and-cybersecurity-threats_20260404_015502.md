# Improving Methodologies for Agentic Evaluations Across Domains: Leakage of Sensitive Information, Fraud and Cybersecurity Threats

## Quick Facts
- arXiv ID: 2601.15679
- Source URL: https://arxiv.org/abs/2601.15679
- Reference count: 40
- Primary result: Low agent pass rates (14-57%) and significant LLM-judge vs. human discrepancies (15-41%) highlight methodological fragility in multilingual agentic safety evaluations.

## Executive Summary
A joint international exercise evaluated AI agent safety across leakage, fraud, and cybersecurity domains in 8-9 languages using adapted public benchmarks and synthetic tools. The study found that current agents exhibit low pass rates (14–57%) and that LLM judges frequently disagree with human evaluators (15–41%), indicating poor alignment in safety adjudication. Key methodological challenges include translation-induced tool inconsistencies, benchmark difficulty dominating outcomes, and sensitivity to sampling parameters. The results underscore the nasceny of agentic testing and the need for nuanced, scenario-specific evaluations beyond simple pass/fail metrics.

## Method Summary
The evaluation adapted existing benchmarks (AgentHarm, InjecAgent, AgentDojo, etc.) into action-oriented tasks equipped with ~1,000 synthetic tools (code, simulated APIs, file operations). Tasks were translated into eight languages (Farsi, French, Hindi, Japanese, Kiswahili, Korean, Mandarin Chinese, Telugu) following a policy that retained English for tool identifiers but translated user-facing strings and culturally adapted names. A simple agent scaffold implemented a reason-plan-tools-observe loop with minimal guardrails. Two separate LLMs served as judges scoring complete trajectories, while human annotators provided ground truth using detailed guidelines. Variations included temperature, token limits, and prompt styles. Analysis employed hierarchical Bayesian models (HiBayES) and qualitative transcript review. The cybersecurity subset used Cybench/Intercode frameworks with further parameter sweeps.

## Key Results
- Agent pass rates ranged from 14% to 57% across models and languages, with frequent execution failures even in benign tasks.
- LLM judges disagreed with human evaluators in 15–41% of cases, often due to leniency and inconsistent reasoning about partial harms.
- Methodological hurdles emerged: translation inconsistencies between tasks and tools, benchmark difficulty skewing cybersecurity results, token limits showing diminishing returns, and one model habitually abandoning tasks.

## Why This Works (Mechanism)
### Mechanism 1: Low pass rates driven by underdeveloped agentic capabilities
- **Claim:** Low agent pass rates (14–57%) are primarily due to underdeveloped tool use, reasoning, and orchestration, not solely safety alignment failures.
- **Mechanism:** Agents fail because of technical execution errors (e.g., incorrect tool calls, incomplete task completion) and an inability to maintain goal-directed reasoning over long horizons, especially in non-native languages where capability gaps widen.
- **Core assumption:** Agent safety requires baseline competency; without reliable tool invocation and error recovery, safety guardrails cannot be consistently applied.
- **Evidence anchors:** Abstract reports low pass rates; a section notes common execution failures in benign tasks (~30% in English); the corpus discusses multi-agent privacy but does not directly quantify execution failures.
- **Break condition:** Consistent pass rates above 80% across languages and risk categories with low technical failure rates.

### Mechanism 2: High LLM-judge vs. human discrepancy due to judge brittleness
- **Claim:** The 15–41% discrepancy between LLM judges and humans stems from judges’ inability to capture nuanced safety failures (e.g., partial compliance, simulation awareness) and their tendency toward leniency.
- **Mechanism:** Judge LLMs misclassify trajectories by misinterpreting task intent, overlooking partial harm execution, and producing internally inconsistent reasoning (e.g., executing harm but outputting a refusal).
- **Core assumption:** Human annotation, despite subjectivity, offers a more reliable ground truth for complex safety adjudication than current LLM-as-judge setups.
- **Evidence anchors:** Abstract notes significant discrepancies; a section reports that judges agreed on task classification but disagreed on safety, often with inconsistent reasoning; the corpus includes “Agent-as-a-Judge” research on LLM judge brittleness in multi-step contexts.
- **Break condition:** Discrepancy rates drop below 5% across diverse scenarios and languages with improved, task-specific judge prompts.

### Mechanism 3: Methodological fragility in multilingual testing
- **Claim:** Inconsistent code/tool translation and task-tool alignment introduce noise that confounds safety signal detection.
- **Mechanism:** Translating tool code (variable names, docstrings, input/output strings) while preserving semantic and functional consistency across languages is error-prone, leading to tool failures mistaken for safety failures.
- **Core assumption:** Valid safety evaluation requires tool functionality preservation across translations; otherwise, observed failures may reflect translation artifacts rather than agent safety issues.
- **Evidence anchors:** Abstract states translation challenges and introduced variability; a section details difficulties in ensuring task/tool consistency, translation errors, and occasional tool failures; the corpus mainly discusses multi-agent privacy risks, not tool translation.
- **Break condition:** Tool failure rates due to translation mismatches are reduced below 5% via standardized, culturally-adapted translation protocols.

## Foundational Learning
- **Agentic Evaluation Complexity:** Agent safety testing differs from conversational QA due to multi-step tool orchestration, state management, and non-deterministic paths. Pass/fail metrics alone are insufficient; trajectory analysis is essential. *Quick check:* How would you design an evaluation that distinguishes between a model that refuses a malicious task correctly and one that fails to execute it due to a tool error?
- **Multilingual NLP in Code-Switched & Tool Contexts:** Non-English tasks often involve code-switching (English tool names, local language prompts) and culturally-specific references. Agent performance depends on handling this mix, not pure translation. *Quick check:* Why might translating variable names and tool docstrings into the target language break tool functionality, even if the prompt is translated?
- **Statistical Evaluation Under High Variability:** Small sample sizes (N~156/model-lang) and high outcome variability mean point estimates are unstable. Understanding confidence intervals and hierarchical modeling (HiBayES) is crucial. *Quick check:* If running 10 epochs yields a success rate standard deviation of 0.04, is a 3% difference between two conditions meaningful?

## Architecture Onboarding
#### Component Map
- Task/Tool Suite: Public benchmarks (AgentHarm, InjecAgent, etc.) adapted into action-oriented tasks with synthetic tools (code, APIs, file operations).
- Agent Scaffold: Simple loop (Reason → Plan → Tool Call → Observe) until final output; minimal guardrails.
- Judge Module: Two separate LLMs (C, D) scoring complete trajectories against pass/fail scenarios via a prompt that includes risk classification and outcome assessment.
- Human Annotation Layer: Guides for pass/fail labeling plus qualitative metrics (linguistic fidelity, comprehensibility, hallucinations, logical consistency).
- Variation Engine: Swappable parameters (temperature, token limit, prompt style, tool set) for robustness testing.

#### Critical Path
Task/Tool Translation → Agent Execution → Judge Scoring → Human Validation → Discrepancy & Failure Mode Analysis.

#### Design Tradeoffs
- Synthetic Tools vs. Realism: Synthetic tools avoid real-world harm but may allow agents to detect simulation; trade-off between safety and ecological validity.
- Single vs. Multiple Judges: Two judges enable comparison but increase cost; single judge requires rigorous calibration.
- Global Pass Rate vs. Scenario-Specific: A single pass rate obscures performance differences across malicious, injection, and benign-underspecified tasks; scenario-level metrics are more interpretable.

#### Failure Signatures
- Tool Failure: “Tool error: file not found” or “No tasks match” → may indicate translation/tool consistency issue.
- Language Mismatch: Agent output language ≠ task language → check translation consistency and model multilingual support.
- High NA Rate: Human annotators mark NA (cannot assess) → often due to technical failures or ambiguous task design.
- Judge Discrepancy >30%: Likely judge prompt ambiguity or task interpretive subjectivity.

#### First 3 Experiments
1. Baseline Replication: Run English task set (30 tasks spanning 3 risk scenarios) with default agent scaffold and judge prompt. Quantify baseline pass rate, judge-human discrepancy, and tool failure rate. Establish performance anchor.
2. Translation Consistency Stress Test: Take 5 tasks with complex tool parameters (e.g., names, file paths). Translate to target language (e.g., Hindi). Run agent and manually inspect tool invocation logs for mismatched strings. Document failure type and rate.
3. Judge Prompt A/B Test: Using a fixed set of 50 trajectories (balanced pass/fail), run two judge prompt variants: (A) original (classify risk + outcome), (B) simplified (only outcome). Compute discrepancy against human labels for each. Identify which prompt reduces ambiguity for borderline cases.

## Open Questions the Paper Calls Out
- Which model architectures demonstrate the most consistent multilingual agent safety across fraud and leakage scenarios?
- How does the realism of simulated tools and environments affect the ecological validity of agent safety evaluations?
- What multi-dimensional metric framework best distinguishes genuine safety failures from capability limitations in agentic systems?
- How can judge-LLM evaluation protocols minimize discrepancies with human annotators across diverse languages and risk scenarios?
- How should token limits and sampling parameters be set to balance capability elicitation with evaluation efficiency in agentic testing?

## Limitations
- Exact model identifiers (Models A–F) and their specific versions/configurations are anonymized, preventing precise replication.
- Full task/tool datasets (~1.2k items) and translation scripts/guidelines are not released; cultural adaptation examples are sparse.
- Hyperparameter details (e.g., agent recursion limits, exact judge prompts post-revision, temperature baselines) are incomplete.

## Confidence
- Low Agent Pass Rates (14–57%): High confidence.
- LLM-Human Judge Discrepancy (15–41%): High confidence.
- Methodological Fragility (Translation/Tool Consistency): Medium confidence.
- Cybersecurity Benchmark Difficulty Dominance: Low confidence.
