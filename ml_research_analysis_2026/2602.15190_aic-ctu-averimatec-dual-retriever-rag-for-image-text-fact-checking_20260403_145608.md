# AIC CTU@AVerImaTeC: dual-retriever RAG for image-text fact checking

## Quick Facts
- **arXiv ID:** 2602.15190  
- **Source URL:** https://arxiv.org/abs/2602.15190  
- **Reference count:** 2  
- **Primary result:** A dual-retriever RAG system achieved 3rd place in the AVerImaTeC shared task with a question score of 0.81, evidence score of 0.35, verdict accuracy of 0.35, and justification score of 0.30.

## Executive Summary
This paper presents a RAG-based system for the AVerImaTeC image-text fact-checking shared task. The system uses two parallel retrievers: a text-based FAISS vector store with MMR reranking, and a reverse image search (RIS) via Google Lens API with Firecrawl scraping. Retrieved sources are fed to a multimodal LLM (GPT-5.1) to generate evidence and a verdict. The approach achieved 3rd place, with strong performance on question answering but lower evidence and justification scores due to evidence format mismatches and RIS reliability issues.

## Method Summary
The system employs a three-module RAG pipeline. First, a text retriever embeds claim text using *mxbai-embed-large-v1*, searches a pre-chunked knowledge store via FAISS (k=20), and reranks with MMR (λ=0.8) to 7 text sources (IDs 1–9). Second, an image retriever uses Google Lens (Serper API) to find visually similar webpages, scrapes them with Firecrawl, filters by date (Htmldate), and keeps up to 9 results per image (IDs 11–19, etc.). Third, a multimodal LLM call (GPT-5.1) receives the claim, its images (base64), and the numbered sources in a system prompt with few-shot examples. The LLM outputs JSON containing QA pairs (later concatenated into evidence text), Likert scores for four verdicts, and a justification. Output formatting appends `[IMG_i]` tags if image sources are cited.

## Key Results
- Achieved 3rd place in the AVerImaTeC shared task.
- High question score (0.81) but lower evidence (0.35), verdict accuracy (0.35), and justification (0.30) scores.
- Operational cost averaged $0.013 per claim using OpenAI Batch API.
- Ablation showed a declarative evidence prompt improved evidence score by 2%, highlighting format mismatch impact.

## Why This Works (Mechanism)

### Mechanism 1: Text Retrieval via FAISS + MMR
Offline text retrieval using vector similarity and MMR reranking provides relevant textual evidence for claim verification. Claim text is embedded, a FAISS index retrieves top-k=20 chunks from a knowledge store, and MMR (λ=0.8) reranks to l=7 diversified results. Core assumption: semantically similar text chunks contain factual evidence. Break condition: if the store lacks domain/time coverage, retrieval yields irrelevant or absent evidence. Evidence score drop despite high question score suggests retrieved text may support meta-questions but not valid evidence texts.

### Mechanism 2: Reverse Image Search (RIS)
RIS contextualizes claim images by finding webpages with visually similar images. Google Lens (Serper API) returns up to 30 results per image; Firecrawl scrapes URLs, filtered by publication date, keeping first 9 valid results. Core assumption: webpages with similar images likely contain relevant textual context. Break condition: RIS returns zero results (e.g., for old or explicit images) or scraping fails (social media blocks), leading to missing image-related sources.

### Mechanism 3: Multimodal LLM Synthesis
A single multimodal LLM call, fed retrieved text and image-related sources plus few-shot examples, generates QA-pair evidence and a verdict. The prompt instructs the model to use only numbered sources. Output QA pairs are concatenated into evidence text, with `[IMG_i]` tags appended if image sources are cited. Core assumption: the LLM can synthesize answers from multiple sources to produce verifiable evidence and correct verdicts. Break condition: evidence format mismatch (QA vs. declarative) and occasional source-ignoring or mis-tagging lower evidence/verdict scores.

## Architecture Onboarding

- **Component map:** Text Retriever (Embedding → FAISS → MMR) → 7 text sources (IDs 1–9)  
  Image Retriever (RIS API → Scraper → Date filter) → up to 9 image sources per image (IDs 11–19, etc.)  
  Generator (Prompt builder + few-shot → Multimodal LLM → JSON parser → Output formatter)

- **Critical path:** Text retrieval and image retrieval can run in parallel; prompt assembly follows; LLM call is the most costly and time-consuming step.

- **Design tradeoffs:**  
  Simplicity vs. RIS reliability: single RIS API call per image is simple but failure-prone; no fallback.  
  Cost vs. coverage: capping at 9 RIS results limits prompt budget but may discard relevant results.  
  Modularity vs. format fidelity: decoupled modules ease debugging but evidence concatenation hack causes format mismatch.

- **Failure signatures:**  
  High question score + low evidence score indicates evidence format mismatch.  
  Empty image-related source lists signal RIS failure (scraping blocks or zero results).  
  Variable costs if many RIS results survive filtering; LLM ignores source constraints or mis-applies tags.

- **First 3 experiments:**  
  1. Measure RIS coverage: run RIS on dev set claims, log % with ≥1 valid scrape, correlate with evidence score.  
  2. Test declarative prompt: replace QA→concat with direct declarative evidence generation, evaluate on dev set.  
  3. Swap scraper: replace Firecrawl with Trafilatura on a subset; compare evidence quality (LLM judge) and cost; verify markdown parsing.

## Open Questions the Paper Calls Out

- **Open Question 1:** How can RIS be improved for older claims and explicit graphical content, which often yield zero results?  
  Basis: Paper acknowledges Google Lens pitfalls (zero hits for 2022 claims, explicit content).  
  Why unresolved: RIS failures limit image-contextual evidence.  
  Resolving evidence: Compare alternative RIS engines (TinEye, Bing) or novel methods on diverse claim types.

- **Open Question 2:** What is the isolated contribution of RIS to overall performance, given its cost and lack of ablation?  
  Basis: Paper admits no text-only vs. text+RIS ablation.  
  Why unresolved: Unclear if RIS complexity meaningfully improves accuracy or if text-only suffices.  
  Resolving evidence: Controlled ablation study comparing full system against text-only variant, with per-claim analysis.

- **Open Question 3:** How should image-text evidence be formatted to align with AVerImaTeC evaluator expectations?  
  Basis: Mismatch between system's QA concatenation and expected declarative sentences with image pointers; ablation shows declarative prompt improves evidence score.  
  Why unresolved: Format mismatch lowers scores even when evidence is correct.  
  Resolving evidence: Human evaluation of evidence formats; derive optimal template from gold data; reimplement and test.

- **Open Question 4:** Can an agentic system with an LLM controller dynamically select between text retrieval, RIS, or both per claim?  
  Basis: Paper suggests an LLM router to predict RIS utility, saving resources.  
  Why unresolved: Current pipeline always invokes both retrievers, wasting resources and possibly adding noise.  
  Resolving evidence: Implement a classifier/LLM router predicting RIS utility based on claim metadata; evaluate cost savings and performance.

- **Open Question 5:** Does severe class imbalance in AVerImaTeC (95% Refuted in train, 78% in text-claims) bias models and render accuracy-based metrics unreliable?  
  Basis: Paper notes overrepresentation of Refuted makes accuracy a problematic metric for real-world use.  
  Why unresolved: Imbalance may cause default Refuted predictions, inflating accuracy but harming minority-class utility.  
  Resolving evidence: Per-class performance analysis on balanced test subset; develop alternative metrics; test dataset rebalancing.

## Limitations
- RIS reliability is low: scraping blocks and zero hits, especially for older or social media images.
- Evidence format mismatch: QA-pair output conflicts with AVerImaTeC's declarative requirement, penalizing scores.
- Model dependency: GPT-5.1 API access is uncertain; substitutes may alter performance.

## Confidence
- **Text retrieval (FAISS+MMR):** High. Standard RAG; strong question score indicates coverage.
- **Reverse image search:** Medium. External API variability and scraping issues reduce reliability.
- **LLM generation (single-call QA→evidence):** Low. Format mismatch and hallucinations limit effectiveness; declarative prompt improves score.
