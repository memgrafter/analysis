# ArgLLM-App: An Interactive System for Argumentative Reasoning with Large Language Models

## Quick Facts
 - **arXiv ID**: 2602.24172
 - **Source URL**: https://arxiv.org/abs/2602.24172
 - **Reference count**: 10
 - **Primary result**: ArgLLM-App is a publicly deployed interactive system using Quantitative Bipolar Argumentation Frameworks to enable real-time revision of LLM decisions through contested modifications, achieving performance competitive with chain-of-thought on claim verification.

## Executive Summary
Large language models (LLMs) often produce decisions that lack transparent explanations and cannot be easily contested by users. ArgLLM-App addresses this by representing LLM reasoning as Quantitative Bipolar Argumentation Frameworks (QBAFs), which structure arguments into graphs with explicit attack and support relations. Users can interactively adjust argument confidences and modify the graph to explore counterfactual reasoning. The system supports depth-1 or 2 trees with breadth ≤4 and offers multiple gradual semantics for computing final claim confidences. It also incorporates user-uploaded PDFs via RAG to ground arguments in trusted documents. Deployed at argllm.app, the system demonstrates that ArgLLMs can achieve performance competitive with chain-of-thought on claim verification tasks, while providing a faithful and contestable explanation interface.

## Method Summary
ArgLLM-App implements ArgLLMs, a method that uses Quantitative Bipolar Argumentation Frameworks (QBAFs) to explain and contest LLM decisions on binary tasks. The system configures the QBAF structure (depth up to 2, breadth up to 4) and selects a gradual semantics (DF-QuAD, Euler-based, Quadratic Energy). Inputs include a binary query and optional PDFs; the system parses PDFs to Markdown and injects them into the LLM prompt to generate a tree-structured QBAF. The backend computes the final claim confidence via the chosen semantics and returns an interactive graph visualization and chat summary. Users can adjust base confidences with sliders and add nodes, triggering immediate recomputation. Reproduction involves setting up a Python backend with OpenAI API access; the live demo is available at argllm.app.

## Key Results
 - Public deployment at argllm.app with interactive graph visualization.
 - Enables users to contest LLM decisions by adjusting argument confidences and adding nodes in real time.
 - ArgLLMs achieve performance competitive with chain-of-thought on claim verification tasks.

## Why This Works (Mechanism)
### Mechanism 1
 **Claim:** Representing LLM decisions as QBAFs enables faithful explainability because reasoning becomes graphically structured with explicit attack/support relations rather than opaque neural activations.
 **Mechanism:** The system prompts an LLM to generate a tree-structured argument graph where each node has a base confidence score; gradual semantics algorithms then propagate these scores through attack/support edges to compute a final confidence for the root claim. Humans can trace the reasoning by following the visible graph.
 **Core assumption:** People can comprehend and debug reasoning chains when presented as a modular graph of arguments with quantified influences, as opposed to free-text chains of thought.
 **Evidence anchors:**
  - [abstract] "The interpretable nature of these argumentation frameworks and formal reasoning means that any decision made by ArgLLMs may be faithfully explained to, and contested by, humans."
  - [section 2] "QBAFs can be seen as graphs with arguments as nodes and elements of the attack and support relations as edges."
  - [corpus] Neighbor papers (e.g., Freedman et al. [3], Gorur et al. [4]) also explore ArgLLMs for explainable reasoning, suggesting this is an active research direction, though direct evidence for ArgLLM-App's explainability comes from its visual design rather than user studies in this paper.
 **Break condition:** If the generated QBAF contains cycles (violating the tree constraint), some gradual semantics may fail to converge, breaking the reasoning traceability.

### Mechanism 2
 **Claim:** Interactive manipulation of QBAF parameters (base confidences, structure) allows humans to contest and iteratively improve decisions by exploring counterfactual reasoning states.
 **Mechanism:** Users adjust base confidence sliders or add attacker/supporter nodes via the UI; these changes trigger immediate recomputation of the final claim confidence using the selected gradual semantics, enabling real-time "what-if" exploration of how evidence weights affect outcomes.
 **Core assumption:** Users can identify errors in the LLM's initial argument assessment or detect missing evidence when presented with a structured summary of the reasoning, and know how to correct them.
 **Evidence anchors:**
  - [abstract] "It supports visualisation of the produced explanations and interaction with human users, allowing them to identify and contest any mistakes in the system's reasoning."
  - [section 3] "Users can modify the generated outputs by using the base confidence slider to express what they deem to be the correct confidence in evidence... Users can add additional supporters or attackers by using the Add buttons associated with arguments."
  - [corpus] Interactive argumentation systems like IntelliProof and VISAR (neighbors) also allow structural editing, but ArgLLM-App's specific slider-based confidence tuning for contestation appears novel.
 **Break condition:** If users add arguments that create dependencies requiring deeper recursion than the configured depth allows, the system may fail to propagate effects to the claim, leading to incomplete revision.

### Mechanism 3
 **Claim:** Incorporating user-uploaded PDFs via RAG grounds argument generation in trusted document content rather than LLM parametric memory, increasing reliability for domain-specific tasks.
 **Mechanism:** Uploaded PDFs are parsed to Markdown and injected into the LLM prompt when generating the QBAF; the LLM is instructed to derive arguments explicitly from the document text, constraining its output to the provided source.
 **Core assumption:** User-provided documents are more trustworthy for the task than the LLM's training data, especially for recent or specialized information.
 **Evidence anchors:**
  - [abstract] "It is highly modular and enables drawing information from trusted external sources."
  - [section 3] "Users can augment the internal LLM knowledge through document-based QBAF generation with documents specified in a PDF format. These PDFs are parsed to MarkDown format and incorporated into the LLM prompts."
  - [corpus] Standard RAG techniques [5] are cited, supporting the general approach; however, the neighbors do not specifically examine PDF-to-argument integration with QBAFs.
 **Break condition:** If PDF parsing loses critical formatting (tables, citations) or the LLM fails to extract relevant arguments from the text, the RAG-enhanced QBAF may degrade rather than improve.

## Foundational Learning
 - **Concept:** Quantitative Bipolar Argumentation Frameworks (QBAFs)
   **Why needed here:** QBAFs are the core representational structure; all system operations—generation, visualization, revision—depend on understanding arguments as nodes with attack/support edges and base scores.
   **Quick check question:** "Given a QBAF with a claim node having two supporters and one attacker, sketch the graph and label the edge types."
 - **Concept:** Gradual Semantics
   **Why needed here:** These algorithms (DF-QuAD, Euler-based, Quadratic Energy) compute final confidence scores from base confidences and relations; different semantics yield different outcomes, affecting explainability and revision behavior.
   **Quick check question:** "How would DF-QuAD semantics handle a strongly supported argument that is also attacked? Would the attack completely cancel the support?"
 - **Concept:** Retrieval-Augmented Generation (RAG)
   **Why needed here:** The PDF upload feature is a form of RAG; understanding why raw documents are parsed and injected into prompts is key to predicting when argument generation will be document-grounded.
   **Quick check question:** "Why convert PDFs to Markdown before including them in an LLM prompt, rather than sending the raw text?"

## Architecture Onboarding
 **Component map**  
 Frontend (React) → Backend (Python) → QBAF Engine → Backend → Frontend (with PDF Processor and LLM Gateway integrated in Backend)

 **Critical path**
 1. User submits claim → frontend POSTs to backend.
 2. Backend loads optional PDF context → constructs LLM prompt → calls OpenAI API → receives QBAF (arguments, relations, base scores).
 3. Backend applies selected gradual semantics → computes final claim confidence.
 4. Backend returns JSON (graph data, final confidence) → frontend renders interactive graph and chat summary.
 5. User adjusts slider or adds node → frontend sends delta → backend updates QBAF → re-runs semantics → pushes updated confidence and graph.

 **Design tradeoffs**
 - Tree-only structure: Enables simple visualization and guarantees no cycles (important for some semantics) but cannot represent shared evidence (same sub-argument used in multiple branches).
 - Depth ≤2: Prevents cognitive overload in graph display but limits reasoning depth; deeper frameworks may require progressive disclosure UI.
 - Breadth ≤4: Caps visual complexity but may truncate rich argument sets; dynamic layout algorithms needed for >4 children.
 - Single LLM: Ensures consistent style but loses multi-model diversity; multi-agent extensions (cited future work) would need cross-model alignment.

 **Failure signatures**
 - Visualizer freezes or cluster-implies when node count >30 (layout algorithm performance).
 - Slider changes don't update final confidence (likely backend not recomputing semantics or caching stale state).
 - PDF upload has no effect on QBAF generation (parser failure or prompt injection error).
 - QBAF generation includes cycles despite tree constraint (LLM not adhering to tree structure; may need post-hoc validation/repair).
 - Euler-based semantics diverges with strong attacks (known property; should fallback or warn).

 **First 3 experiments**
 1. Sanity check: Claim "Paris is the capital of France" → verify QBAF has claim at root, at least one supporter, final confidence >0.9, graph renders without crashes.
 2. Depth toggle: Same claim with depth=1 vs depth=2 → confirm depth=2 introduces exactly one additional layer of arguments (attackers/supporters of first-layer arguments).
 3. Slider impact: Identify a key pro-argument, reduce its base confidence from 0.9 to 0.1 → verify final claim confidence drops significantly (>0.3 change) for DF-QuAD semantics.

## Open Questions the Paper Calls Out
### Open Question 1
 - Question: Can ArgLLM-App support QBAF depths beyond 2 without cognitive overload?
 - Basis in paper: [explicit] "The system could be adjusted to support QBAF depths higher than 2 while avoiding cognitive overload of users."
 - Why unresolved: Depth is capped at 2; deeper argument trees could capture richer reasoning but risk exceeding user comprehension and interaction capacity.
 - What evidence would resolve it: Conduct user studies with adaptive UI (e.g., progressive disclosure) measuring understanding, trust, and decision quality across increasing depth levels.

### Open Question 2
 - Question: How can ArgLLM-App fully integrate RAG to autonomously retrieve and incorporate external arguments?
 - Basis in paper: [explicit] "Further, it would be interesting to fully integrate RAG [5] into ArgLLM-App, allowing our agents to find relevant sources autonomously and extract relevant arguments therefrom."
 - Why unresolved: Users must manually upload PDFs; autonomous retrieval would improve scalability and knowledge freshness but requires solving relevance filtering and argument extraction.
 - What evidence would resolve it: Build a RAG pipeline that queries a corpus (e.g., Wikipedia), extracts candidate arguments, and integrates them into QBAFs; evaluate via relevance, correctness, and impact on verification accuracy.

### Open Question 3
 - Question: Does supporting multiple LLMs and multi-agent configurations improve robustness and explanation quality in ArgLLM-App?
 - Basis in paper: [explicit] "The current realisation allows the use of only base LLMs from OpenAI, and only single LLMs. We envisage the support of LLMs from other providers, and multi-agent variants where different agents rely upon different LLMs."
 - Why unresolved: Dependency on a single provider limits flexibility and may introduce bias; multi-agent setups could enhance diversity and fault tolerance but pose aggregation challenges.
 - What evidence would resolve it: Integrate at least one additional LLM (e.g., Anthropic Claude), design aggregation methods (e.g., voting), and compare performance, consistency, and error rates against the single-LLM baseline.

## Limitations
 - Lack of user validation: explainability and contestability claims rely on structural assumptions without empirical user studies.
 - Representation constraints: Tree-only, shallow (depth ≤2, breadth ≤4) structures may oversimplify complex arguments.
 - Generation and RAG risks: LLM-generated QBAFs may contain cycles or low-quality edges; PDF-RAG grounding quality and parsing robustness remain unevaluated.

## Confidence
 - Faithful explainability via QBAFs: Medium
 - Effective contestation via interactive sliders and node addition: Low
 - Reliable grounding of arguments via PDF-RAG: Low

## Next Checks
 1. User comprehension study: Compare QBAF visualization vs. chain-of-thought text for error detection on 20 claim verification tasks with 25 participants; measure accuracy and perceived explainability.
 2. Robustness stress test: Generate QBAFs for 200 diverse claims; report cycle/invalid-edge rate; implement and evaluate a post-hoc repair algorithm (e.g., cycle removal) on a subset.
