# A System for Name and Address Parsing with Large Language Models

## Quick Facts
- **arXiv ID:** 2601.18014  
- **Source URL:** https://arxiv.org/abs/2601.18014  
- **Reference count:** 34  
- **Primary result:** 99.8% exact-row accuracy on a 17-field schema, reducing error by 23% vs baseline.

## Executive Summary
This research introduces a prompt-driven framework for parsing unstructured person and address text into structured data without model fine-tuning. The system handles noisy, multilingual inputs via a four-stage pipeline: deterministic normalization, structured prompt assembly, constrained LLM inference, and strict validation. Evaluated on a heterogeneous real-world dataset, it achieves near-perfect exact-row accuracy while automatically handling most exceptions.

## Method Summary
Processing begins with deterministic input normalization—applying Unicode NFKC, removing zero-width characters, collapsing whitespace, expanding abbreviations (e.g., “Ave” → “Avenue”), mapping directionals (“N.E.” → “NE”), unifying unit symbols (“#” → “Unit”), and de-duplication. Next, a fixed prompt scaffold (role, task, schema order, rules, two examples) is assembled in pipe-delimited format. For inference, Claude 4.0 Sonnet via AWS Bedrock processes records in fixed batches (size 16) with temperature=0.30, top_p=0.90, top_k=50, max_tokens=1500, and stop sequences at batch boundaries; a single retry occurs on structural failure. Finally, strict validation enforces schema compliance, type checks (digits for numbers, two-letter states, 5/9-digit ZIPs), canonical maps (states, street types), and cross-field rules (e.g., ZIP-state consistency). No fine-tuning is used; all hyperparameters are fixed.

## Key Results
- Exact-row accuracy reaches 99.8% (0.2% error) on a 1,500-record evaluation set, cutting error rate by 23% compared to a 99.34% baseline.
- Field-level accuracies exceed 99% for critical components (street name, city, etc.), and the validation layer auto-handles 94% of exception cases.
- Confidence scores are well-calibrated: high-confidence predictions (78% of records) achieve 99.9% accuracy, with confidence strongly correlated to correctness.

## Why This Works (Mechanism)
Reliability emerges from layered safeguards. Normalization reduces input variability and noise, giving the LLM a cleaner, consistent textual signal. Structured prompting explicitly defines the output schema, field order, and formatting rules via a fixed scaffold, guiding the model without fine-tuning. Constrained decoding—with stop sequences, batch delimiting, and a retry on structural failure—prevents merged or truncated outputs. Finally, strict validation acts as a post-hoc corrector, enforcing domain constraints (type checks, canonical mappings) and cross-field consistency to catch residual LLM errors. This combination compensates for the absence of fine-tuning by merging deterministic preprocessing with rule-based correction.

## Foundational Learning
- **Input Normalization**  
  *Why needed:* To handle noisy, multilingual text with inconsistent formatting, abbreviations, and Unicode artifacts.  
  *Quick check:* Apply NFKC, remove zero-width spaces, collapse whitespace, expand common abbreviations (e.g., “Ave” → “Avenue”), map directions (e.g., “N.E.” → “NE”), unify unit symbols.
  
- **Structured Prompting**  
  *Why needed:* To clearly communicate the parsing task, schema, and output format to the LLM without fine-tuning.  
  *Quick check:* Use a fixed scaffold specifying role, task, field order, formatting rules, and two illustrative examples, all pipe-delimited.
  
- **Constrained Decoding**  
  *Why needed:* To enforce strict output structure and prevent malformed responses in batch processing.  
  *Quick check:* Set stop sequences at record boundaries and field limits, retry once on structural failure, and cap tokens (max 1500).
  
- **Validation Rules**  
  *Why needed:* To ensure parsed data complies with domain-specific constraints and catch LLM hallucinations.  
  *Quick check:* Implement type checks (digits for numeric fields), canonical mappings (states, street types), and cross-field consistency (e.g., ZIP matches state).

## Architecture Onboarding
Component map: Raw Input -> Normalization -> Prompt Assembly -> LLM Inference -> Validation -> Structured Output  
Critical path: LLM Inference is the central, latency-determining step; all other stages support or correct its output.  
Design tradeoffs: Fixed hyperparameters favor reproducibility over adaptability; batch size 16 balances throughput and error risk; avoiding fine-tuning reduces development cost but may limit domain-specific performance.  
Failure signatures: Validation failures (schema mismatch, type errors), abnormal field counts in LLM output, low-confidence scores, and spikes in exception rates.  
First experiments: 1) Vary batch size (e.g., 8, 16, 32) to measure impact on exact-row accuracy and throughput. 2) Evaluate on a non-English address corpus to test multilingual robustness. 3) Compare against a fine-tuned smaller model (e.g., T5) on the same task to assess cost-performance tradeoffs.

## Limitations
- Incomplete public specification of normalization dictionaries (abbreviations, street types, directionals) and exhaustive validation rules prevents exact replication.
- Evaluation dataset (1,500 heterogeneous records) is not released, blocking independent verification of results.
- Results are tied to Claude 4.0 Sonnet with fixed settings; generalizability to other LLMs or dynamic configurations is unknown.
