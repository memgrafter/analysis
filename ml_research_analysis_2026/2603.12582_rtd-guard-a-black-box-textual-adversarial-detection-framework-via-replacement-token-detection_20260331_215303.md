# RTD-Guard: A Black-Box Textual Adversarial Detection Framework via Replacement Token Detection

## Quick Facts
- **arXiv ID:** 2603.12582
- **Source URL:** https://arxiv.org/abs/2603.12582
- **Reference count:** 22
- **Primary result:** A training-free, strictly black-box detector using a frozen RTD model for token localization and a two-query confidence shift test, achieving SOTA detection metrics with minimal overhead.

## Executive Summary
RTD-Guard tackles the real-world problem of detecting word-substitution adversarial attacks on NLP models under strict practical constraints: no access to adversarial examples, no white-box model internals, and minimal query overhead. It repurposes a pre-trained Replaced Token Detection (RTD) discriminator—without any fine-tuning—to identify tokens that are contextually inconsistent, a hallmark of adversarial substitutions. These suspicious tokens are masked, and the victim model's prediction confidence for its originally predicted class is compared between the original and masked inputs. A significant confidence drop signals an adversarial example. This approach requires exactly two black-box queries and no training, making it highly efficient and deployable. Across multiple datasets and four state-of-the-art attack methods, RTD-Guard consistently achieves the best detection performance in TPR at 10% FPR, F1-score, and AUC, while incurring the lowest computational cost among compared defenses.

## Method Summary
RTD-Guard is a two-stage pipeline. First, a frozen pre-trained ELECTRA discriminator (the RTD model) processes the input text and outputs a token-level probability score indicating how likely each token is a "replaced" token. The top-*k* non-special tokens with highest scores are selected as localized perturbation candidates. Second, these tokens are replaced with `[MASK]` to create a modified input. The victim model (a black-box API) is queried on both the original and masked inputs. The detector computes the squared difference in confidence between the two outputs for the class originally predicted by the victim model. If this score exceeds a threshold *τ* (e.g., 0.09), the input is classified as adversarial. The entire process involves one forward pass through the RTD model (run locally) and exactly two queries to the victim model, with no fine-tuning or dependence on the victim's architecture.

## Key Results
- **SOTA detection performance:** Ranks highest in TPR@10%FPR, F1-Score, and AUC across AG-News, IMDB, and Yelp datasets against TextFooler, PWWS, BAE, and TF-adj attacks.
- **Minimal overhead:** Runtime is marginally above pure victim model inference; significantly faster than query-intensive baselines like MLE or GradMask.
- **Strict efficiency:** Requires only two black-box queries and zero model fine-tuning or adversarial data.

## Why This Works (Mechanism)

### Mechanism 1: RTD as Contextual Inconsistency Detector
- **Claim:** Adversarial word substitutions introduce contextual inconsistencies that a pre-trained Replaced Token Detection (RTD) discriminator can identify without fine-tuning.
- **Mechanism:** The RTD discriminator, trained to distinguish original tokens from generator-produced replacements, learns a general sense of contextual naturalness. Adversarial tokens, being optimized substitutes that are semantically similar but contextually jarring, score high as "replaced" by this discriminator.
- **Core assumption:** The contextual unnaturalness of adversarially substituted tokens is structurally similar to the unnaturalness of randomly replaced tokens in RTD pre-training.
- **Evidence anchors:**
  - [abstract] "...word-substitution perturbations in adversarial attacks closely resemble the 'replaced tokens' that a Replaced Token Detection (RTD) discriminator is pre-trained to identify."
  - [section 5.2] "A clear structural symmetry exists... The RTD generator substitutes random tokens... Both processes share the core operation of token substitution. Consequently, a discriminator excelling at RTD becomes inherently attuned to detecting 'out-of-place' tokens... the hallmark of adversarial perturbations."
- **Break condition:** Fails if adversarial substitutions are crafted to be maximally contextually coherent (e.g., using a powerful MLM to select synonyms that perfectly fit the local context).

### Mechanism 2: Confidence Shift as Fragility Signal
- **Claim:** Adversarial examples are fragile with respect to interventions at their perturbed tokens, causing a significant confidence shift in the victim model when those tokens are masked, whereas clean examples are robust.
- **Mechanism:** The attack optimization concentrates predictive influence onto the substituted tokens. Masking these key tokens (localized by RTD) disrupts the adversarial signal, causing the model's confidence in the attacker-chosen label to drop sharply. For clean inputs, masking RTD-identified tokens (often peripheral or low-salience) causes minimal confidence change.
- **Core assumption:** A successful adversarial example resides close to the decision boundary and depends critically on a small set of optimized tokens.
- **Evidence anchors:**
  - [abstract] "...by observing the prediction confidence shift of the victim model before and after intervention."
  - [section 5.2] "Adversarial examples are highly sensitive to intervention at their optimized tokens, whereas clean examples remain stable. This differential sensitivity underpins our detection strategy."
  - [section 7.3] Qualitative examples show confidence in the adversarial class drops from e.g., 0.54 to near 0.0 after masking, while clean original confidence remains high.
- **Break condition:** Fails if the victim model is inherently non-robust and highly sensitive to random masking of any tokens (high false positives), or if the perturbation is distributed across many tokens not captured by top-*k* localization.

### Mechanism 3: Decoupled Design for Strict Black-Box Efficiency
- **Claim:** The framework achieves strict black-box, data-free, and minimal-query operation by decoupling perturbation localization (using a frozen RTD model) from decision-making (using two victim model queries).
- **Mechanism:** The RTD discriminator runs locally as a separate, static module, requiring no victim model access. Detection depends solely on comparing two black-box outputs (original and masked input). This isolates the defense from victim model architecture, training data, and attack strategy.
- **Core assumption:** A general-purpose, pre-trained RTD model's contextual inconsistency signal is transferable to the task of adversarial perturbation detection across different victim models and datasets without adaptation.
- **Evidence anchors:**
  - [abstract] "requires only two black-box queries... no adversarial data, model tuning, or internal model access."
  - [section 5.3] "RTD-Guard... requires no modification to the deployed NLP system... (1) zero-shot and training-free... (2) strictly black-box... (3) computationally lean—exactly two model queries..."
  - [section 7.2] Runtime comparisons show RTD-Guard's overhead is marginally above pure victim model inference.
- **Break condition:** Breaks if the RTD discriminator itself is very large, making the single forward pass prohibitively slow, or if the deployed environment restricts even auxiliary model execution.

  - **Quick check:** "What are the three key practical constraints that an 'ideal' black-box detector must satisfy, and why do they rule out methods like GradMask or MLE?"

- **Concept: Confidence Shift as Anomaly Signal**
  - **Why needed here:** The detection logic is not based on the RTD score alone, but on the *change* in victim model confidence after a targeted intervention.
  - **Quick check:** "Why is measuring the difference in confidence for the *original predicted class* before and after masking critical, rather than just looking at the RTD's token probabilities or the final masked input's prediction?"

## Architecture Onboarding
- **Component map:** Input Text -> RTD Discriminator (Frozen) -> TokenSelector (Top-K) -> Masking Module -> Victim Model API (Black-Box) -> Confidence Comparator -> Decision Threshold (τ) -> Output Label
- **Critical path:**
  1.  Run input `x` through `D_RTD` to get per-token replacement probabilities `p_i`.
  2.  Apply `TopK(p_i, k)` to get index set `I` (excluding special tokens).
  3.  Construct `x_m` by replacing positions in `I` with `[MASK]`.
  4.  Query victim model: `pred_orig = f(x)`, `pred_mask = f(x_m)`.
  5.  Let `c = argmax(pred_orig)`.
  6.  Compute score `S = (pred_orig[c] - pred_mask[c])²`.
  7.  Output `D(x)=1` (adversarial) if `S > τ`; else `0` (clean).
- **Design tradeoffs:**
  - **`k` (masking budget):** Larger *k* captures more adversarial edits but risks masking important clean tokens, increasing false positives. Paper finds `k=5` effective.
  - **RTD Model Size:** Larger models (Large vs. Base) improve accuracy but increase latency.
  - **Intervention Strategy:** `[MASK]` is simplest and sufficient; `[UNK]` or deletion are alternatives. MLM-based filling adds cost without benefit.
- **Failure signatures:**
  - **High False Positive Rate:** `S` is large for many clean examples. Likely `k` too large or RTD flagging semantically important tokens. Validate on clean set.
  - **High False Negative Rate:** `S` is small for many adversarial examples. Likely RTD failed to localize perturbed tokens or attack was contextually smooth. Check if `τ` is too high.
  - **Runtime Overrun:** Total time >> 2x victim query time. Profile RTD forward pass; consider a smaller RTD variant.
- **First 3 experiments:**
  1.  **Localization Sanity Check:** For a known adversarial example (e.g., from TextFooler), run RTD and print token-level probabilities. Visually confirm highest-probability tokens correspond to actual attack changes.
  2.  **`k` Sweep:** Run detection on a fixed validation set for `k` in [1, 2, 3, 5, 7, 10]. Plot F1-score vs. `k`. Expect rise then fall-off; identify optimal `k`.
  3.  **Intervention Strategy Comparison:** Implement variants (RTD-UNK, RTD-DEL, RTD-MLM) alongside `[MASK]`. Run on one dataset/attack. Verify similar F1/AUC, confirming localization is key.

## Open Questions the Paper Calls Out
- **Multilingual/Cross-lingual Generalization:** How to extend RTD-Guard to settings where input language may not match the RTD discriminator's training language? The current framework relies on monolingual RTD models and may fail on code-switched or foreign-language texts.
- **Prompt Injection/Jailbreak Detection:** Can the principle be generalized to detect hidden malicious instructions in LLM prompts under black-box constraints? This requires adapting from classification tasks with simple substitutions to generative scenarios with complex semantic manipulations.
- **Hallucination Detection:** Are RTD-based inconsistency signals effective for detecting factual errors in generative outputs? This involves extending from single-classification inputs to long, generated texts and designing an efficient confidence shift test for factual claims.
- **Adaptive Attacks:** How robust is RTD-Guard against an attacker who explicitly minimizes the RTD discriminator's replacement scores for substituted tokens? The threat model assumes an attack unaware of the defense; a adaptive adversary could evade localization.

## Limitations
- **Tokenizer mismatch:** Misalignment between ELECTRA and victim model tokenizers can cause incorrect token localization, degrading detection.
- **Threshold ambiguity:** The published threshold *τ* = 0.09 lacks details on per-dataset tuning or validation set composition, making exact replication of results uncertain.
- **Context-fluent attacks:** Mechanism relies on adversarial tokens being contextually jarring. Attacks using context-optimized substitutions (e.g., MLM-based) may produce tokens that score well on RTD, reducing detection efficacy.

## Next Checks
1.  **Tokenizer consistency:** Tokenize sample sentences with both ELECTRA and victim BERT tokenizers; compare token boundaries. If mismatched, use a single shared tokenizer (e.g., BERT's) for both models to ensure masking aligns with actual tokens.
2.  **Threshold calibration:** For each dataset/attack combination, tune *τ* on a held-out validation split (e.g., 20% of clean data). Plot TPR@10%FPR vs. *τ* to assess sensitivity and verify if 0.09 is near-optimal.
3.  **Context-fluent attack evaluation:** Generate adversarial examples using an attack that selects substitutions via a masked language model (e.g., BERT-MLM) for maximal contextual fit. Evaluate RTD-Guard's TPR10 on this set to directly probe the break condition for Mechanism 1.
