# Accelerating Local LLMs on Resource-Constrained Edge Devices via Distributed Prompt Caching
## Quick Facts
- **arXiv**: 2602.22812
- **URL**: https://arxiv.org/abs/2602.22812
- **References**: 11
- **Key result**: Average TTFT reduction of 93.12% and TTLT reduction of 50.07% on Raspberry Pi Zero 2W.

## Executive Summary
Running large language models locally on edge devices like the Raspberry Pi Zero 2W is often prohibitively slow due to limited computational resources. This paper introduces a distributed prompt caching system that offloads intermediate key‑value (KV) states from prompt decoding to a remote cache server, allowing multiple devices to reuse them. Each client maintains a Bloom‑filter‑based local catalog to quickly check whether a prompt prefix is cached, thereby avoiding unnecessary network requests and supporting partial matching to maximize reuse. Evaluated on a Raspberry Pi Zero 2W with the Gemma‑3 270M model and MMLU dataset, the approach reduces Time to First Token (TTFT) by 93.12% and Time to Last Token (TTLT) by 50.07% on average, demonstrating substantial latency improvements for resource‑constrained edge platforms.

## Method Summary
The proposed system employs a distributed caching architecture where the intermediate KV states generated during prompt decoding are stored on a remote cache server and shared across edge devices. Before decoding a new prompt, a client consults its local Bloom filter catalog to determine if any prefix of the prompt already exists in the remote cache. If a hit is detected, the client retrieves the cached KV states and resumes generation from the cached point, bypassing redundant computation. The Bloom filter provides a memory‑efficient membership test with controllable false positive rates, and the system supports partial prefix matching to increase cache hit probability. By shifting the burden of prompt processing to a shared server, the method dramatically reduces the local computation required, especially for repeated or similar prompts across devices.

## Key Results
- TTFT decreased by 93.12% on average.
- TTLT decreased by 50.07% on average.
- The Bloom‑filter catalog effectively limits network overhead while maintaining high cache reuse.

## Why This Works (Mechanism)
The mechanism works because the majority of latency in local LLM inference on edge devices stems from the autoregressive decoding of the prompt, which is often repeated across requests (e.g., common system prompts or user queries with shared prefixes). By caching the KV states of these prefixes remotely, devices can skip the entire prompt encoding phase for cached prefixes, jumping directly to token generation. The local Bloom filter catalog prevents unnecessary network round‑trips for non‑cached prompts by quickly rejecting them with a small memory footprint. Partial matching ensures that even if the full prompt is not cached, longer cached prefixes still yield partial savings. Together, these elements reduce both time to first token (by avoiding initial decoding) and overall generation time (by reducing total computation), with the greatest benefits seen on devices with slow CPUs.

## Foundational Learning
**KV Cache**: In transformer decoding, each token’s attention keys and values are stored to avoid recomputation for subsequent tokens. *Why needed*: Caching these states allows the system to resume generation from any point without reprocessing earlier tokens. *Quick check*: Given a sequence length L and model dimension d, the KV cache size is approximately 2 * L * d * num_layers * bytes_per_param; can you compute it for a 6‑layer, 768‑dim model?

**Bloom Filter**: A space‑efficient probabilistic data structure for set membership queries with no false negatives but possible false positives. *Why needed*: Provides a compact local catalog to quickly test whether a prompt prefix might be cached, reducing unnecessary network calls. *Quick check*: For a filter of m bits and k hash functions, the false positive rate is approximately (1 - e^{-kn/m})^k. Can you estimate it for m=1024, k=7, n=100?

**Partial Prefix Matching**: Instead of requiring an exact full‑prompt match, the system considers any cached prefix that matches the beginning of the prompt. *Why needed*: In many scenarios, prompts share common leading tokens (e.g., system prompts), so caching longer prefixes yields higher reuse even if the full prompt varies. *Quick check*: If prefix length L is cached and the full prompt length is N, what fraction of computation is saved? (Approximately L/N of the prompt processing.)

**Distributed Caching**: Storing shared data on a remote server accessible by multiple clients. *Why needed*: Enables multiple edge devices to benefit from the same computed KV states, amplifying the CPU savings across a fleet. *Quick check*: What are the trade‑offs between cache coherence and network latency in this context?

## Architecture Onboarding
**Component map**: Edge Device (LLM inference engine + Bloom filter catalog) <--network--> Remote Cache Server (KV storage + retrieval API). The client sends a prefix hash to the catalog; if the Bloom filter indicates possible presence, it queries the server for the KV states. The server responds with the cached KV tensors, which the client uses to resume generation.

**Critical path**: For a given prompt, (1) check Bloom filter for the full prompt or longest prefix; (2) if hit, request KV from server; (3) upon receipt, continue generation from the cached point; (4) if miss, decode the entire prompt locally and optionally store resulting KV in the cache for future use (not detailed). The network round‑trip in step 2 dominates latency for hits.

**Design tradeoffs**:
- Bloom filter size vs. false positive rate: larger filters reduce false positives but consume more local memory.
- Network latency vs. local computation: if the server is far or congested, even a cache hit may be slower than local decoding; the system assumes network is sufficiently fast.
- Cache eviction policy: limited server storage requires eviction; poor eviction can reduce hit rates.
- Partial matching threshold: allowing shorter prefixes increases hit rate but may yield smaller savings per hit.

**Failure signatures**:
- High network latency or packet loss: TTFT for cached prompts degrades, potentially exceeding local decoding time.
- Bloom filter false positives: extra network requests for uncached prompts, adding latency.
- Cache server outage: all requests fall back to local decoding, but the Bloom filter may still cause unnecessary retries.
- Inefficient eviction: frequent eviction of popular prefixes reduces hit rate over time.

**First experiments**:
1. Baseline measurement: Run local LLM inference without caching on the target edge device, record TTFT and TTLT for a set of prompts.
2. Full cache hit scenario: Pre‑populate the remote cache with all prompt prefixes and measure latency under ideal network conditions to quantify maximum possible speedup.
3. Bloom filter tuning: Vary the filter size (bits per item) and measure the trade‑off between catalog memory usage, false positive rate, and overall latency to identify a sweet spot.

## Limitations
- Experiments were conducted only on a Raspberry Pi Zero 2W using Gemma‑3 270M and MMLU, limiting generalizability.
- Network effects (latency, bandwidth) are not thoroughly characterized; performance under varied connectivity remains unknown.
- Bloom filter configuration (size, hash functions) and cache server management (eviction, consistency) are not explored.

## Confidence
- Latency reduction (TTFT ↓93%, TTLT ↓50%): Medium (single‑config experiment, no statistical analysis).
- Catalog minimizing overhead: Low (no direct network traffic measurements).
- General benefit for edge platforms: Low (only one low‑end device evaluated).

## Next Checks
