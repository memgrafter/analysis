# SMES: Towards Scalable Multi-Task Recommendation via Expert Sparsity
## Quick Facts
- **arXiv**: 2602.09386  
- **Source**: https://arxiv.org/abs/2602.09386  
- **References**: 36  
- **Result**: Deployed at Kuaishou (400M+ DAU); +0.29% GAUC, +0.31% watch time lift with low latency.
## Executive Summary
SMES tackles a critical inefficiency in multi-task recommendation: naive sparse Mixture-of-Experts (MoE) routing leads to exploded per-instance expert activation and severe expert load skew across tasks. It introduces two core mechanisms: (1) progressive expert routing, which decomposes activation into a jointly selected task-shared expert subset plus small task-adaptive private sets, explicitly bounding distinct expert executions per instance; and (2) a global multi-gate load-balancing regularizer that coordinates routers across tasks to stabilize training. System-level optimizations—deduplicated expert execution and a reindexed grouped GEMM kernel—enable low-latency inference at scale. Industrial A/B tests confirm robust gains across tasks.
## Method Summary
SMES employs a shared encoder and a large pool of experts. Instead of each task independently selecting its top-K experts (causing union explosion), it uses a two-stage progressive router: first, a global score aggregates all task gate probabilities to pick a shared set of \(K_s\) experts. Then, each task selects \(K_a\) additional experts from the remaining pool as its adaptive set. The final activated set for task \(t\) is the union of shared and adaptive experts. This guarantees at most \(K_s + T \cdot K_a\) distinct experts per instance, far below the worst-case \(T \cdot K\). To prevent cross-task hotspots, a multi-task load-balancing regularizer \(L_{lb} = \frac{E}{K} \sum_e \bar{f}_e \bar{p}_e\) is minimized, where \(\bar{f}_e\) and \(\bar{p}_e\) are expert \(e\)'s average selection frequency and probability averaged over all tasks and batches. During inference, expert outputs are computed only once for each expert in the deduplicated union set and reused.
## Key Results
- Online A/B test at Kuaishou (400M+ DAU): GAUC gain +0.29%, user watch time uplift +0.31%.
- Maintains stable performance gains across a diverse set of 21 recommendation tasks.
- Achieves low inference latency via deduplication and optimized kernels, suitable for large-scale production.
## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** SMES bounds per-instance expert activation via progressive routing with task-shared and task-adaptive sets.
- **Mechanism:** For each instance, first compute global scores \(s_e = \sum_t w_t p_{t,e}\) and select top \(K_s\) experts as shared set \(S\). Then for each task \(t\), select top \(K_a\) experts from the remaining pool as \(A_t\). Final activated set for task \(t\) is \(K_t = S \cup A_t\). The union across tasks \(U = \bigcup_t K_t\) has size at most \(K_s + T K_a\), which is strictly less than \(T K\) when \(K_s < K\) and \(K_a < K\), preventing the union explosion from naive independent top-\(K\) routing.
- **Core assumption:** There exists a subset of experts that are generally useful across all tasks (shared patterns), while residual task-specific patterns can be captured by a small adaptive set.
- **Evidence anchors:**
  - [abstract] "decomposes activation into a task-shared expert subset ... explicitly bounding per-instance expert execution"
  - [section] Section 3.2.1, Equations (10)-(14) define the two-stage selection and union bound.
- **Break condition:** If tasks have no shared patterns (\(S\) meaningless) or \(K_s\) is set too small, \(|U|\) may approach \(T K_a\), undermining sparsity.

### Mechanism 2
- **Claim:** A global multi-task load-balancing regularizer mitigates expert load skew by balancing aggregated expert utilization across tasks.
- **Mechanism:** For each expert \(e\), compute average selection frequency \(\bar{f}_e\) and average routing probability \(\bar{p}_e\) across all tasks and batch instances (Eq. 16). Minimize \(L_{lb} = \frac{E}{K} \sum_e \bar{f}_e \bar{p}_e\) (Eq. 17). This penalizes experts that are both frequently selected and assigned high probability mass, encouraging balanced traffic across the expert pool.
- **Core assumption:** Expert load skew arises from independent task routers accumulating on hotspots; coordinating via cross-task statistics can distribute utilization.
- **Evidence anchors:**
  - [abstract] "global multi-gate load-balancing regularizer stabilizes training by regulating aggregated expert utilization"
  - [section] Section 3.2.2 defines \(\bar{f}_e\), \(\bar{p}_e\), and \(L_{lb}\).
- **Break condition:** If tasks have fundamentally incompatible optimal experts, forcing balance may degrade some tasks; \(\beta\) must be tuned to trade off balance vs. specialization.

### Mechanism 3
- **Claim:** Deduplicated expert execution and optimized kernels enable low-latency inference despite dynamic sparse activation.
- **Mechanism:** After determining union \(U\), compute expert outputs only for unique experts in \(U\), reusing results for all tasks that selected them. Use a reindexed grouped GEMM kernel to pack variable-sized inputs into contiguous tensors, avoiding irregular computation overhead. A profiling-guided workspace allocator pre-allocates memory pools based on expected load distribution, reducing allocation latency.
- **Core assumption:** The reduction in FLOPs from deduplication outweighs overhead of dynamic memory management and kernel dispatch, and profiling can accurately anticipate runtime requirements.
- **Evidence anchors:**
  - [abstract] "optimized matrix computation and memory-efficient execution, supporting large-scale low-latency production serving"
  - [section] Section 3.3 describes Reindexed Grouped GEMM and Profiling-Guided Workspace Allocation.
- **Break condition:** If \(|U|\) grows large (near \(T K\)), deduplication gains vanish; profiling mismatches can cause memory waste or contention.

## Architecture Onboarding
- **Component map:**  
  Input \(x\) → Shared encoder \(F(x)=h\) → Expert pool \(\{f_e\}_{e=1}^E\) → For each task \(t\): router \(g_t(h) → z_t → p_t = \text{softmax}(z_t)\) → Progressive routing: \(S = \text{TopK}(\sum_t w_t p_t, K_s)\); \(A_t = \text{TopK}(z_t \text{ excluding } S, K_a)\); \(K_t = S ∪ A_t\) → Deduplication: \(U = \bigcup_t K_t\) → Execute \(f_e\) only for \(e∈U\) → For each task: aggregate \(h_t = ∑_{e∈K_t} p_{t,e} o_e\) → Task head \(\phi_t → \hat{y}_t\) → Loss \(\mathcal{L}=∑_t λ_t \mathcal{L}_t + β \mathcal{L}_{lb}\) → System: Reindexed Grouped GEMM, Profiling-Guided Workspace Allocation.
- **Critical path:** \(F(x) →\) routers \(→\) progressive selection \(→\) deduplication \(→\) expert computation \(→\) task aggregation \(→\) heads \(→\) loss (with regularization).
- **Design tradeoffs:**  
  - \(K_s\) vs. \(K_a\): Larger \(K_s\) improves bound stability but reduces per-task capacity; larger \(K_a\) increases capacity but risks larger \(|U|\).  
  - Regularization weight \(\beta\): higher \(\beta\) encourages balance but may constrain task-specific routing.  
  - System overhead: Dynamic workspace management adds complexity; profiling must reflect production traffic distributions.
- **Failure signatures:**  
  - High \(|U|\) close to \(T K\): shared set \(S\) too small or tasks too diverse → increase \(K_s\) or revisit expert initialization.  
  - Skewed expert utilization (high variance in \(\bar{f}_e\)): load-balancing ineffective → increase \(\beta\) or adjust expert initialization.  
  - Increased p99 latency: workspace allocation inefficiency → check memory pool size, fragmentation, and kernel launch overhead.
- **First 3 experiments:**  
  1. Offline comparison against dense and sparse baselines (MMoE, PLE, RankMixer) on public and industrial datasets to validate GAUC gains.  
  2. Ablation study: remove Task-SHA, Task-ADA, and Reg components to quantify individual contributions.  
  3. Scalability analysis: vary expert count and hidden dimension, measure performance (GAUC) and inference latency to confirm bounded compute and stable scaling.
## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Does SMES maintain consistent performance improvements when applied to recommendation domains with fundamentally different user engagement patterns (e.g., e-commerce, news feeds) compared to short-video platforms?
- **Basis in paper:** [explicit] The conclusion explicitly states "extending to other recommendation scenarios" as future work.
- **Why unresolved:** The experiments are exclusively conducted on KuaiRand (short-video benchmark) and Kuaishou's short-video service; no evaluation on domains with different interaction semantics or data distributions.
- **What evidence would resolve it:** Large-scale offline studies and A/B tests on diverse datasets (e.g., Amazon Reviews for e-commerce, MIND for news) measuring GAUC and business metrics like watch time versus conversion.

### Open Question 2
- **Question:** Can the progressive expert routing mechanism dynamically adjust the shared (K_s) and adaptive (K_a) expert budget per instance based on instance-specific characteristics (e.g., task sparsity, feature density)?
- **Basis in paper:** [inferred] SMES uses fixed hyperparameters K_s and K_a (Eqs. 10–12) despite emphasizing heterogeneous task demands; the paper does not explore per-instance budget adaptation.
- **Why unresolved:** Static budgets may under-utilize capacity for instances with rich supervision or over-activate for sparse ones, limiting optimal capacity allocation.
- **What evidence would resolve it:** Implement a lightweight instance-adaptive router predicting K_s and K_a per instance, then compare GAUC and expert utilization variance against fixed budgets across tasks of varying sparsity.

### Open Question 3
- **Question:** Would alternative multi-task load-balancing regularizers (e.g., minimizing activation entropy or incorporating task-specific importance weights) further improve training stability and final performance compared to the product-based L_lb?
- **Basis in paper:** [inferred] The proposed L_lb (Eq. 17) uses a simple product of aggregated selection frequency and probability mass; no comparative analysis of other imbalance metrics is provided.
- **Why unresolved:** The paper does not justify why this particular regularizer is optimal or explore whether more nuanced measures (e.g., entropy over expert load) could better prevent cross-task hotspots.
- **What evidence would resolve it:** Ablation studies replacing L_lb with entropy-based, variance-based, or task-weighted formulations, tracking convergence speed, expert load distribution (Gini index), and final GAUC.

### Open Question 4
- **Question:** How do SMES's system-level optimizations (Reindexed Grouped GEMM) compare in latency and memory efficiency against standard sparse MoE execution frameworks (e.g., MegaBlocks, TensorRT MoE) under varying sparsity ratios and hardware architectures?
- **Basis in paper:** [inferred] Section 3.3 introduces custom kernel optimizations but provides no comparative benchmarks; efficiency claims rely on internal deployment without baselines.
- **Why unresolved:** Without direct comparisons, it is unclear whether the optimizations are generally superior or merely tailored to Kuaishou's specific serving stack.
- **What evidence would resolve it:** Benchmark SMES's kernel against state-of-the-art MoE execution engines on standardized hardware (e.g., NVIDIA GPUs), measuring per-instance latency, memory bandwidth usage, and throughput across sparsity levels (e.g., 5%, 10%, 20%).

### Open Question 5
- **Question:** Does SMES scale effectively to an extremely large number of tasks (e.g., T > 100) without causing expert utilization collapse or prohibitive union size |U|?
- **Basis in paper:** [inferred] The method targets multi-task scenarios and introduces global load-balancing to mitigate "accumulation effect," but experiments use at most 21 tasks (Kuaishou dataset); scalability to hundreds of tasks remains untested.
- **Why unresolved:** The theoretical bound \(|U| ≤ K_s + T·K_a\) (Eq. 14) suggests linear growth with T if \(K_a > 0\), potentially violating latency budgets; load-balancing may fail under extreme task counts.
- **What evidence would resolve it:** Simulations or controlled experiments with synthetic task sets (e.g., 50, 100, 200 tasks), measuring \(|U|\) distribution, expert load skew (e.g., coefficient of variation), and GAUC relative to task count, while monitoring latency.
## Limitations
- Feature preprocessing and hyperparameter choices (\(K_s, K_a, β, E\), dimensions) are not fully specified or analyzed for sensitivity.
- No head-to-head comparison with recent multi-task scaling methods (e.g., RankMixer) in the related work corpus.
- System-level overheads (memory fragmentation, kernel launch cost) not quantified; may limit scalability to extreme E/T.
- Load-balancing may degrade task-specific performance under high inter-task conflict; trade-off not explored.
- Generalization to datasets with more diverse tasks or different domains (beyond recommendation) uncertain.
## Confidence
- **Progressive Routing**: High (bound proof and per-instance expert count confirm activation control).
- **Load-Balancing**: Medium (regularizer reduces skew but sensitivity to β and task conflict not fully characterized).
- **Efficiency**: Low (claims lack detailed benchmarks; custom kernel dependency raises reproducibility concerns).
- **Online Gains**: Medium (A/B test on 400M users shows lifts, but long-term effects and cross-domain transfer unknown).
