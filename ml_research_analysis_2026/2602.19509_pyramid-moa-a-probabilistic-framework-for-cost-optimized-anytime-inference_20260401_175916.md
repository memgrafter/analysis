# Pyramid MoA: A Probabilistic Framework for Cost-Optimized Anytime Inference
## Quick Facts
- **arXiv ID:** 2602.19509
- **Source URL:** https://arxiv.org/abs/2602.19509
- **Reference count:** 11
- **Primary result:** A two-tier hierarchical router dynamically escalates queries from small models (8B/7B/9B) to a large Oracle (70B), achieving significant compute savings (up to 18.4%) while matching Oracle accuracy across multiple benchmarks by formalizing inference as a probabilistic anytime computation problem.

## Executive Summary
The paper tackles the inherent cost-accuracy trade-off in LLM deployment, where large models are effective but expensive, and small models are efficient but limited. It introduces Pyramid MoA, a hierarchical Mixture-of-Agents system that uses a lightweight, decision-theoretic router to selectively escalate queries from an ensemble of small models to a large Oracle model. The work formally maps multi-model routing to a probabilistic anytime computation problem, proving that expected solution quality is monotonically non-decreasing with computational depth under identifiable router precision conditions. Empirically, on code (MBPP) and math (GSM8K/MMLU) benchmarks, the system intercepts a high proportion of errors and matches the Oracle's accuracy with substantial compute savings. The approach demonstrates robust zero-shot transfer to held-out tasks (HumanEval, MATH 500), confirming the practical validity of the anytime property.

## Method Summary
The method specifies a two-tier architecture: Layer 1 is a parallel ensemble of small models (Llama-3.1-8B, Qwen2.5-7B, Gemma-2-9B); Layer 2 is a large Oracle (Llama-3.3-70B). A lightweight XGBoost router, trained on domain-specific features (e.g., semantic agreement for code, token log-prob for math), predicts the probability `P_fail` that the Layer 1 ensemble is incorrect. For a given threshold `t`, the router returns Layer 1's majority vote if `P_fail ≤ t`; otherwise, it invokes the Oracle. The objective is to match Oracle accuracy while minimizing compute cost, formalized via a Value of Computation escalation rule that accounts for imperfect oracles and escalation cost. Minimum viable reproduction involves: (1) generating Layer 1 outputs on training data, (2) extracting features and training routers to predict correctness, (3) sweeping thresholds on validation to profile accuracy vs. savings, and (4) evaluating on test sets and zero-shot benchmarks. Critical unknowns blocking faithful replication include exact XGBoost hyperparameters, precise feature engineering (e.g., semantic agreement metric), and the absolute cost model (hardware, per-token pricing) used to compute savings percentages.

## Key Results
- On MBPP code generation, the trained router intercepts 81.6% of bugs; zero-shot on HumanEval, it achieves Oracle-level accuracy (81.1%) with 62.7% compute savings.
- On GSM8K/MMLU math, the system matches the Oracle's 68.1% accuracy with up to 18.4% compute savings at a balanced operating point.
- The Probabilistic Anytime Property (expected accuracy non-decreasing with escalation rate) empirically holds across all four benchmarks (MBPP, GSM8K/MMLU, HumanEval, MATH 500), enabling dynamic adaptation to task difficulty.

## Why This Works (Mechanism)
### Mechanism 1: Formalizing LLM Routing as Probabilistic Anytime Computation
- **Claim:** Multi-model LLM routing can be formalized as a probabilistic anytime computation problem.
- **Mechanism:** The system maps classical anytime concepts to the LLM setting: Layer 1 ensemble provides an initial solution; escalation to the Oracle provides extended computation. The router acts as a monitor deciding when to stop (use Layer 1) and when to escalate.
- **Core assumption:** The Oracle yields higher expected accuracy than the ensemble on the subset of queries escalated by the router.
- **Evidence anchors:** [abstract] "We observe that the emerging practice of LLM cascading and routing implicitly solves an anytime computation problem..."; [section 2.1] "We bridge this gap by recasting multi-model LLM inference as a probabilistic anytime computation problem."
- **Break condition:** If the Oracle does not improve accuracy on the escalated subset (i.e., αL2(R) < αL1(R)), then adding computation can decrease expected quality, violating the anytime premise.

### Mechanism 2: Probabilistic Anytime Property via Router Precision
- **Claim:** Expected solution quality is monotonically non-decreasing with computational depth (escalation rate) under a condition on router precision.
- **Mechanism:** Theorem 1 shows accuracy improvement over Layer 1 equals `pR·(αL2(R) - αL1(R))`. Thus, expected quality increases iff `αL2(R) ≥ αL1(R)`. This condition depends on the router's ability to identify queries where the ensemble underperforms the Oracle.
- **Core assumption:** The router's escalation set R satisfies that the Oracle's accuracy on R is at least that of Layer 1 on R.
- **Evidence anchors:** [abstract] "We establish a Probabilistic Anytime Property, proving that expected solution quality is monotonically non-decreasing with computational depth under identifiable conditions on router precision."; [section 2.3] Theorem 1 and Equation (3).
- **Break condition:** The property fails if on the escalated subset, the Oracle's accuracy is lower than the ensemble's (`αL2(R) < αL1(R)`), which can occur due to router errors or domain shift.

### Mechanism 3: Generalized Decision-Theoretic Escalation Rule
- **Claim:** The paper derives an optimal escalation rule from Value of Computation theory, accounting for imperfect oracles and extending the classical monitoring framework to stochastic LLM inference.
- **Mechanism:** The router compares expected utility of stopping (`E[Ustop] = (1-Pfail)·Ucorrect`) versus escalating (`E[Uesc] = Poracle·Ucorrect - Cesc`). Escalation is optimal when `Pfail > Cesc/Ucorrect + (1-Poracle)`, introducing a cost barrier and an imperfection barrier.
- **Core assumption:** Utility of correctness (`Ucorrect`) and escalation cost (`Cesc`) are known or estimable, and `Pfail` is well-calibrated. The decision is myopic (single-step), valid for the two-tier architecture.
- **Evidence anchors:** [abstract] "We derive a generalized escalation rule from Value of Computation theory that accounts for imperfect oracles..."; [section 2.4] Equation (5) and discussion of the two barriers.
- **Break condition:** The rule is optimal only if parameters (`Ucorrect`, `Cesc`, `Poracle`) are correctly specified and `Pfail` is accurate. Heterogeneous `Poracle` across queries or a deeper pyramid would require a non-myopic approach.

## Architecture Onboarding
- **Component map:** Layer 1 (ensemble of small models) -> Router (XGBoost classifier) -> Layer 2 (Oracle model)
- **Critical path:**
  1. Receive user query.
  2. Dispatch query to all Layer 1 models; collect responses in parallel.
  3. Extract features from ensemble outputs (semantic similarity, length variance, log-prob statistics).
  4. Router computes `P_fail`; compare to threshold `t`.
  5. If `P_fail ≤ t`, aggregate Layer 1 responses (majority vote) and return.
  6. If `P_fail > t`, send query (and optionally Layer 1 context) to Oracle; return Oracle response.
- **Design tradeoffs:**
  - Router feature complexity vs. latency: More features improve accuracy but increase preprocessing time.
  - Threshold tuning: Lower `t` increases escalation (higher accuracy, higher cost); higher `t` saves cost but risks more errors.
  - Ensemble diversity vs. base cost: Heterogeneous models yield richer agreement signals but increase parallel inference cost.
  - Router training data: Requires labeled examples (queries with known correctness) to train `P_fail` predictor; domain-specific routers may be needed.
- **Failure signatures:**
  - Escalation rate significantly deviates from validation: suggests router miscalibration or distribution shift.
  - Accuracy on non-escalated queries drops far below Layer 1 baseline: router failing to detect errors.
  - Oracle accuracy on escalated queries is not higher than Layer 1 on those queries: violation of Theorem 1 condition.
  - Compute savings vary wildly across similar datasets: router not generalizing.
- **First 3 experiments:**
  1. MBPP code generation: Train Consensus Router (XGBoost) on semantic agreement features. Achieves 81.6% bug recall. Zero-shot transfers to HumanEval, matching Oracle accuracy (81.1%) with 62.7% savings.
  2. GSM8K/MMLU math: Train Anytime Router on token log-prob features. Matches Oracle 68.1% accuracy with up to 18.4% compute savings at balanced threshold.
  3. Zero-shot transfer to MATH 500: Apply GSM8K/MMLU router to out-of-distribution calculus. System preserves Oracle ceiling (58.0%) and achieves 63.4% savings, demonstrating robustness to severe domain shift.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How does extending Pyramid MoA to a generative architecture—where the Oracle refines Layer 1 outputs as context—affect accuracy, cost trade-offs, and the theoretical anytime guarantees?
- **Basis in paper:** [explicit] The authors identify this as a natural extension in the Limitations & Future Work section (Page 10), noting it would strengthen the anytime analogy and may improve Oracle accuracy on escalated queries.
- **Why unresolved:** The current framework uses independent generation; incorporating refinement could break the monotonicity condition (Theorem 1) if refinement degrades quality for certain queries. The theoretical analysis assumes independent outputs.
- **What evidence would resolve it:** Empirical evaluation of a generative variant on the same benchmarks, measuring changes in the accuracy gap αL2(R) − αL1(R) and the concave shape of the performance profile. Theoretical proof extending Theorem 1 to dependent refinement steps.

### Open Question 2
- **Question:** What specific measurable conditions on the router's precision are necessary and sufficient to guarantee the Probabilistic Anytime Property in practice, and how can they be monitored or enforced during deployment?
- **Basis in paper:** [explicit] Theorem 1 states the property holds "under identifiable conditions on router precision" but does not specify quantifiable metrics beyond αL2(R) ≥ αL1(R) (Page 4). The "router quality" remark (Remark 1) is qualitative.
- **Why unresolved:** The condition is defined in terms of unknown subset accuracies (αL1(R), αL2(R)), which are not directly observable at inference time for a new query. This limits the router's ability to self-monitor its own adherence to the anytime guarantee per-instance.
- **What evidence would resolve it:** Derivation of a sufficient condition using only observable router outputs (e.g., confidence Pfail, ensemble agreement). A calibration study showing that a proxy metric (e.g., precision-recall on a validation set) correlates with maintaining the monotonicity condition on test distributions.

### Open Question 3
- **Question:** Why does the Consensus Router (trained on MBPP) transfer zero-shot effectively to HumanEval but the Anytime Router (trained on GSM8K/MMLU) shows reduced efficacy on the out-of-distribution MATH 500 benchmark, despite both being code vs. math tasks?
- **Basis in paper:** [inferred] Results (Page 6-8, Figures 3 & 6) show the Consensus Router achieves the Oracle ceiling on HumanEval with high savings, while the Anytime Router on MATH 500 only preserves the Oracle ceiling at very high thresholds (low savings). The paper notes the MATH 500 results are "predicted by the generalized decision rule" due to low Oracle accuracy but does not analyze the differential transfer.
- **Why unresolved:** The routers use different primary signals (semantic agreement vs. token log-prob). The paper does not investigate whether the discrepancy in transfer robustness is due to the signal's inherent generalizability across domains or the relative difficulty of the target distributions.
- **What evidence would resolve it:** An ablation study training both router types on both domains and evaluating cross-transfer. Analysis of which features (e.g., semantic agreement, token uncertainty) remain predictive under severe domain shift, possibly measuring the distributional distance between training and test feature manifolds.

### Open Question 4
- **Question:** Can the optimal escalation rule (Equation 5) be practically implemented with accurate estimates for Poracle (Oracle success probability) and Ucorrect (utility of correctness) in real-world deployments where ground-truth correctness is unknown?
- **Basis in paper:** [explicit] Equation 5 derives the optimal rule using Poracle and Ucorrect (Page 4). The implementation uses a classifier (XGBoost) trained to estimate Pfail, implicitly absorbing these parameters into the threshold t. The paper does not validate whether the learned t approximates the theoretically optimal threshold derived from (Cesc/Ucorrect) + (1-Poracle).
- **Why unresolved:** In practice, Poracle and Ucorrect are unknown and dataset-dependent. The trained classifier's threshold t is a monolithic parameter that may not adapt to varying query-specific costs (Cesc) or utilities. The paper uses a single threshold per domain.
- **What evidence would resolve it:** Comparing the empirical performance profile against the theoretically optimal profile computed using held-out estimates of Poracle and a fixed Ucorrect. An experiment with query-specific cost models (e.g., varying Cesc by prompt length) to see if a static threshold remains optimal.

### Open Question 5
- **Question:** How does the system's behavior scale with more than two tiers (e.g., 7B → 70B → 405B), and does the full sequential monitoring formulation from Hansen & Zilberstein yield non-myopic improvements over the current single-step router?
- **Basis in paper:** [explicit] The authors mention extending to deeper pyramids would require the "full sequential monitoring formulation" (Page 10). The current system is a two-tier reduction.
- **Why unresolved:** The decision rule in Equation 5 is myopic (one-step lookahead). A multi-tier system faces a sequential decision problem where escalating now vs. later has different costs and each tier's accuracy is stochastic. The theoretical guarantees (Theorem 1) are for the two-tier case and may not extend.
- **What evidence would resolve it:** Simulation or empirical implementation with three tiers, using a dynamic programming or reinforcement learning router that considers future options. Measurement of whether the expected accuracy under a budget improves over a greedy router, and verification of a multi-step probabilistic anytime property.

## Limitations
- Router hyperparameters (XGBoost settings, train/validation splits) and feature engineering details (e.g., exact semantic agreement computation) are unreported, hindering replication.
- Compute savings percentages depend on unspecified hardware (GPU type) and per-token/per-request costs, limiting real-world applicability and cross-study comparison.
- Zero-shot transfer claims (e.g., to HumanEval, MATH 500) lack diagnostic analysis of feature distribution shifts, weakening evidence of robustness and generalizability.

## Confidence
- **Theoretical framework (anytime formalization, Theorem 1):** High – proofs are explicit and grounded in established Hansen & Zilberstein monitoring problem.
- **In-distribution empirical results (MBPP, GSM8K/MMLU):** Medium – results are detailed but reproducibility is blocked by missing implementation specifics (e.g., threshold tuning procedure).
- **Zero-shot transfer and "Probabilistic Anytime Property" across benchmarks:** Low – claims rely on aggregate metrics without per-benchmark verification of the monotonicity condition (αL2(R) ≥ αL1(R)) for all thresholds or analysis of feature shift.

2. **Cost-savings sensitivity analysis:** Recalculate savings using varied hardware cost models (e.g., A100 vs. H100, batch sizes 1–4). Identify thresholds where savings drop below reported values and assess stability under plausible cost perturbations.
3. **Feature shift diagnostics:** Compare distributions of key router features (semantic agreement, log-prob stats) between in-distribution (GSM8K) and OOD (MATH 500) test sets using Kolmogorov–Smirnov tests. If significant shifts exist, the zero-shot transfer claim requires stronger evidence.
