# Comparing Classifiers: A Case Study Using PyCM
## Quick Facts
- **arXiv ID**: 2602.13482
- **Source URL**: https://arxiv.org/abs/2602.13482
- **Reference count**: 5
- **Primary result**: Weighted composite metrics can reverse classifier rankings compared to accuracy or macro-F1, demonstrating context-sensitive model selection.

## Executive Summary
The paper presents PyCM, a Python library offering over 150 classification evaluation metrics and a Compare class that aggregates multiple overall and class-based benchmarks into weighted composite scores. In a case study using the Covertype dataset and two decision tree models, the authors show that while accuracy and macro F1 are nearly identical, applying domain-specific weights (flammability vs. riparian) flips the preferred classifier. This highlights the risk of relying on simple metrics and illustrates PyCM's utility for task-appropriate model evaluation.

## Method Summary
The study employs the Covertype dataset to train two decision tree classifiers. Using PyCM, confusion matrices are generated and a suite of metrics is computed. The Compare class then combines seven overall benchmarks (e.g., Landis-Koch, Matthews Correlation) and six class-based benchmarks, with optional per-class importance weights. Two weighting scenarios—flammability and riparian—are applied to produce composite scores and class-level scores, which are compared to determine the superior model under each weighting scheme.

## Key Results
- Macro F1 scores are nearly identical (0.8827 vs 0.8829) and overall scores without weighting are identical (0.9238).
- With flammability weights, Classifier 2 ranks higher (class-score 0.8845 vs 0.8814).
- With riparian weights, Classifier 1 ranks higher (0.8622 vs 0.7930).
- The ranking flip demonstrates that weighting based on domain relevance can change model selection decisions.

## Why This Works (Mechanism)
PyCM’s Compare class aggregates multiple evaluation metrics into a single composite score while allowing class-specific weights. This mechanism ensures that model evaluation reflects task-specific costs or importance, rather than treating all errors equally. The case study confirms that such weighting can reverse model rankings, thereby surfacing trade-offs that simple metrics like accuracy conceal.

## Foundational Learning
- **Confusion Matrix**: Foundation for most classification metrics; tabulates true vs. predicted classes. *Why needed*: All derived metrics rely on correct counts of TP, TN, FP, FN. *Quick check*: Does the sum of the matrix equal the number of samples? Are diagonal entries correct?
- **Evaluation Metrics (Precision, Recall, F1)**: Measure per-class or aggregate performance. *Why needed*: Capture different error types (false positives vs. false negatives). *Quick check*: For binary case, does F1 = 2 * (precision*recall)/(precision+recall)?
- **Macro vs. Micro Averaging**: Strategies to aggregate per-class metrics across multiple classes. *Why needed*: Macro treats all classes equally, micro reflects overall class distribution. *Quick check*: Does macro-average equal the simple average of class-wise scores?
- **Class Imbalance**: Skewed class frequencies that can bias accuracy. *Why needed*: Imbalanced data renders accuracy misleading; metrics like balanced accuracy or weighted F1 are needed. *Quick check*: If 90% of samples belong to one class, a naïve classifier can achieve 90% accuracy but may fail on minority classes.
- **Composite Scoring**: Combining multiple metrics into one number (e.g., averaging overall benchmarks). *Why needed*: Simplifies model comparison across several criteria. *Quick check*: Are all included metrics normalized to comparable scales (e.g., 0-1) before aggregation?
- **Importance Weighting**: Assigning higher weight to certain classes based on domain cost. *Why needed*: Errors in critical classes (e.g., safety-critical) should penalize more heavily. *Quick check*: Do weights sum to 1 (or another consistent total) before applying?

## Architecture Onboarding
**Component Map**:  
Input (true labels, predictions) -> ConfusionMatrix -> Metric Calculator (individual metrics) -> Compare Class (aggregates benchmarks + weights) -> Composite Score Output

**Critical Path**:  
1. Compute confusion matrices for each classifier.  
2. Calculate required metrics (overall and per-class).  
3. Instantiate Compare with chosen benchmarks and weights.  
4. Invoke Compare to obtain overall and class-based scores.  
5. Compare scores across classifiers to decide ranking.

**Design Tradeoffs**:  
- *Breadth vs. Usability*: Offering 150+ metrics gives flexibility but can overwhelm users; the Compare class abstracts this by pre-selecting a subset.  
- *Static vs. Adaptive Weights*: Fixed domain weights are simple but may not adapt to dataset-specific characteristics; dynamic weighting would add complexity.  
- *Transparency*: Composite scores are easy to compare but obscure which underlying metrics drive differences; detailed reports are needed to avoid black‑box evaluation.

**Failure Signatures**:  
- Mismatched class labels between true and predicted arrays cause incorrect confusion matrix.  
- Using inappropriate weights (e.g., negative, non‑normalized) yields unintuitive rankings.  
- For datasets with missing classes in predictions, some per-class metrics become undefined (division by zero).  
- Overlooking metric normalization before aggregation can bias the composite toward larger‑scale metrics.

**First Three Experiments**:  
1. Validate a subset of PyCM’s metric implementations against scikit‑learn on a toy dataset (e.g., Iris) to ensure correctness.  
2. Compare rankings of two simple classifiers on a binary imbalanced dataset using accuracy, macro F1, and a weighted composite score; observe which metric aligns with domain cost.  
3. Benchmark PyCM’s runtime and memory usage on a large multiclass dataset (e.g., Covertype) to assess scalability.

## Limitations
- Experiments are limited to one dataset (Covertype) and two decision tree models; broader validation is needed.  
- The weighting schemes (flammability, riparian) are domain‑specific and lack general justification; their practical utility beyond the case study is unclear.  
- No statistical significance testing is performed on the composite score differences, leaving open the possibility that observed ranking flips are due to chance.
