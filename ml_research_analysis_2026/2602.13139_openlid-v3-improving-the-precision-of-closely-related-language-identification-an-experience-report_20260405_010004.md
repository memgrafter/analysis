# OpenLID-v3: Improving the Precision of Closely Related Language Identification -- An Experience Report

## Quick Facts
- **arXiv ID:** 2602.13139
- **Source URL:** https://arxiv.org/abs/2602.13139
- **Reference count:** 40
- **Primary result:** Extended OpenLID with merged macrolanguages, a dedicated noise class (`zxx_Zxxx`), and augmented training data to improve precision on closely related languages and noisy web text, achieving state-of-the-art results on standard and targeted benchmarks while trading recall for precision via ensemble methods.

## Executive Summary
This paper presents OpenLID-v3, an evolution of the OpenLID language identification system designed to address precision failures on closely related languages and noisy web data. Key modifications include merging mutually intelligible language variants into macrolanguages (e.g., Arabic dialects), introducing a dedicated `zxx_Zxxx` class for non-language content, and augmenting training data for under-represented scripts. The authors also created new, targeted evaluation benchmarks for groups like BCMS, Romance, and Scandinavian languages, where existing tests were inadequate. OpenLID-v3 matches or exceeds prior systems (OpenLID-v2, GlotLID) on standard benchmarks and shows specific precision gains on language-targeted tests. For high-precision applications like the HPLT 4.0 data curation pipeline, an ensemble with GlotLID (top-1 agreement) is adopted, which drastically reduces false positives but at a significant cost to recall for low-resource languages.

## Method Summary
OpenLID-v3 is a fastText-based supervised classifier trained on an extended corpus combining filtered GlotLID data, Wikipedia dumps, UDHR, FLORES+, and synthetic noise. The training process incorporates three main changes: (1) merging problematic language variant clusters (e.g., 8 Arabic dialects into `ara_Arab`, Persian varieties into `fas_Arab`) to reduce within-group confusion, (2) adding a `zxx_Zxxx` class trained on GlotLID's noise tags (`und_*`, `zxx_*`) to capture non-linguistic content, and (3) augmenting data for specific languages/scripts (e.g., `srp_Latn`, Latin) to address recall gaps. The model outputs softmax scores over ~195 labels; a threshold of 0.5 is applied to predictions to improve precision. Evaluation uses a suite of benchmarks: clean parallel corpora (FLORES+, UDHR), web-like noisy sets (FastSpell, re-annotated HPLT-LID), and new fine-grained, language-group-specific tests (BCMS Twitter, ParlaSent, ITDI, SLIDE, Nordic DSL). An ensemble strategy requiring top-1 agreement between thresholded OpenLID-v3 and unthresholded GlotLID is used for maximum precision in production.

## Key Results
- On standard multilingual benchmarks (FLORES+, UDHR), OpenLID-v3 achieves competitive F1-scores (e.g., 97.7% on FLORES+), matching or slightly trailing GlotLID (98.3%), but with improved precision for closely related language groups.
- On targeted benchmarks for confusable groups, OpenLID-v3 shows clear gains, such as higher precision for Serbian Latin in BCMS Twitter data compared to OpenLID-v2, demonstrating the benefit of script-specific data augmentation.
- The top-1 agreement ensemble with GlotLID substantially reduces false positive rates, a trade-off adopted for HPLT 4.0 curation, but this comes with a severe recall drop for low-resource languages.

## Why This Works (Mechanism)
### Mechanism 1: Merging Variants into Macrolanguages
- **Claim:** Merging mutually intelligible language variants into macrolanguages reduces within-group confusion and improves precision for those groups.
- **Mechanism:** By collapsing clusters of highly similar dialects (e.g., Arabic dialects into `ara_Arab`, Persian varieties into `fas_Arab`) into single macrolabels, the classifier avoids overfitting to minor orthographic or lexical variations that are inconsistent across web data. This simplifies the decision boundary and prevents the model from learning spurious correlations tied to specific variant-level training examples.
- **Core assumption:** For mutually intelligible varieties with overlapping features, discriminative classification is fundamentally noisy given typical web text lengths; grouping them yields more robust predictions for the linguistic community.
- **Evidence anchors:** The paper merges 8 Arabic dialects and two Persian varieties; this is reported in the abstract and detailed in section 3.

### Mechanism 2: Dedicated Noise Class (`zxx_Zxxx`)
- **Claim:** Introducing a dedicated `zxx_Zxxx` (not-a-language) class explicitly captures non-linguistic noise and out-of-vocabulary content, preventing it from being misclassified as a valid language and contaminating language-specific subsets.
- **Mechanism:** The model learns a representation for "non-language" patterns (e.g., code, garbled text, repetitive strings) from curated noise datasets (GlotLID's `und_*` and `zxx_*`). During inference, such inputs are funneled to this class instead of the nearest linguistic class, which acts as a "trash bin" in its absence.
- **Core assumption:** Web crawls contain substantial non-linguistic content that is not randomly distributed but exhibits regular patterns distinguishable from natural language.
- **Evidence anchors:** The class is introduced in the abstract and section 3, trained using GlotLID's noise-labeled data.

### Mechanism 3: Targeted Data Augmentation
- **Claim:** Targeted data augmentation for specific under-represented script variants (notably Serbian Latin, Latin language) directly addresses recall/coverage gaps for those realizations in web text.
- **Mechanism:** By supplementing the training corpus with clean, high-quality sources (e.g., recent Wikipedia dumps, validated GlotLID subsets) for languages that were previously missing or had insufficient data, the model acquires robust feature representations for those variants. This reduces both false negatives (missed instances) and false positives (confusion with related languages).
- **Core assumption:** Performance deficits for certain languages/scripts are primarily due to *training data deficiency*, not inherent linguistic difficulty.
- **Evidence anchors:** Section 3 and Table 10 list specific languages with added data sources (e.g., `srp_Latn` from UD, SETimes, Tatoeba).

## Foundational Learning
- **Concept: fastText classification**
  - **Why needed here:** OpenLID-v3 is built on fastText, which uses word and character n-gram features. This is crucial for handling morphologically rich languages, code-switching, and misspellings common in web text.
  - **Quick check:** How does the summation of word/character n-gram embeddings in fastText provide robustness to OOV words and morphological variants?
- **Concept: Macrolanguage (in linguistic resource coordination)**
  - **Why needed here:** The paper's merges (Arabic, Persian, Bambara/Dyula) follow a macrolanguage strategy. Understanding that this is a *pragmatic grouping for engineering purposes*, not a claim about linguistic unity, is key.
  - **Quick check:** What are the trade-offs between modeling a macrolanguage vs. separate languages in terms of data efficiency, precision, and downstream usability?
- **Concept: Evaluation metrics under extreme class imbalance**
  - **Why needed here:** The paper explicitly argues that precision/F1 are misleading on web-scale data where true language distribution is heavily skewed. FPR and recall are prioritized.
  - **Quick check:** Why does a model with 98% F1 on a balanced benchmark like FLORES+ potentially have near-0% precision on real web crawls? How do FPR and recall avoid this pitfall?

## Architecture Onboarding
- **Component map:** Training Data Pipeline (GlotLID-corpus, Wikipedia, UDHR, FLORES+, synthetic noise) -> Model (fastText supervised classifier, ~195 labels + `zxx_Zxxx`) -> Post-processing Options (softmax thresholding, ensemble with GlotLID) -> Evaluation Suite (FLORES+, UDHR, FastSpell, BCMS/Romance/Scandinavian benchmarks)
- **Critical path:** 1. Data curation: Identify problematic clusters → decide merges/data augmentation → fetch/extract sources → integrate into training corpus. 2. Model training: Standard fastText `supervised` (5 epochs, lr 0.1, word n-grams 2). 3. Threshold calibration: Validate on held-out set (FLORES+ dev); use 0.5 for v3. 4. Ensemble decision: For HPLT 4.0, use top-1 agreement between thresholded OpenLID-v3 and unthresholded GlotLID, accepting recall drop. 5. Targeted evaluation: Run language-group-specific tests (BCMS, Scandinavian) to catch hidden confusions.
- **Design tradeoffs:** Thresholding: Higher threshold increases precision but lowers recall, especially for low-resource/noisy languages. Ensembling (top-1): Maximizes precision but acts as a "coverage killer" for languages where models disagree (often low-resource). Macrolanguage merges: Improves group precision but eliminates fine-grained distinction (e.g., cannot separate Bosnian/Croatian/Serbian after merge).
- **Failure signatures:** Symptom: Very high FPR on a specific low-resource language in web data. Likely cause: That language is a "trash bin" for noise or confusable content; check if `zxx_Zxxx` captures noise or if a related higher-resource language overshadows it. Symptom: Systematic confusion between two specific languages in a group (e.g., Bosnian ↔ Serbian Latin on Twitter). Likely cause: Insufficient discriminative features in short texts; script/lexical overlap; requires multilabel data or extra features. Symptom: Ensemble drastically reduces recall for a language. Likely cause: Disagreement between GlotLID and OpenLID-v3; check if one model is more conservative or if training distributions differ.
- **First 3 experiments:** 1. **Baseline replication:** Train OpenLID-v3 exactly as described and evaluate on FLORES+ devtest. Expect F1 ~97.7%. 2. **Threshold sweep:** Run inference with thresholds [0.3, 0.5, 0.7] on FLORES+ and a noisy subset (e.g., FastSpell). Plot FPR vs. recall to visualize trade-off. 3. **BCMS sanity check:** Evaluate on re-annotated HPLT-LID subset for Bosnian/Croatian/Serbian Latin. Confirm improved Serbian Latin recall over v2 and persistent Bosnian confusion.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can multilabel language identification benchmarks be effectively created for web data to address code-switching and texts valid in multiple languages? *Basis:* The authors state a need for more multilabel training data and benchmarks, as existing ones (FLORES+, UDHR) are single-label and clean. *Why unresolved:* Lack of large-scale, diverse multilabel LID datasets from web sources with systematic multi-language annotation.
- **Open Question 2:** What architectural or training modifications can mitigate the precision-recall trade-off in ensemble LID models for low-resource languages? *Basis:* Ensembling improves precision but substantially reduces coverage for low-resource languages; the paper does not explore beyond top-1/top-3. *Why unresolved:* No alternative ensemble strategies (e.g., weighted, meta-classifiers) are evaluated for preserving low-resource recall.
- **Open Question 3:** Why do hierarchical coarse-to-fine LID models fail to improve performance for closely related language groups, and under what conditions might they succeed? *Basis:* Appendix F reports negative results on hierarchical models for Scandinavian, BCMS, Arabic, Persian; hypothesis is unsaturated model capacity. *Why unresolved:* Not rigorously tested; factors like training data quality, similarity metrics, or hierarchical depth are not analyzed.
- **Open Question 4:** How can LID models better detect and handle non-language content and out-of-vocabulary languages to reduce contamination in target language classes? *Basis:* Introduction of `zxx_Zxxx` addresses the "trash bin phenomenon" (e.g., Ligurian in v2), but noise detection is not comprehensively evaluated. *Why unresolved:* The `zxx_Zxxx` class may not capture all noise types; thresholds are heuristic; no comparison to alternative dynamic class handling methods.
- **Open Question 5:** What evaluation methodologies are most reliable for assessing LID performance on closely related languages, given the inadequacy of standard multilingual benchmarks? *Basis:* The authors created new benchmarks for BCMS, Romance, Scandinavian because existing ones are inadequate; FLORES+ hides poor precision. *Why unresolved:* The paper lacks a general framework for benchmark design; factors like text length, domain, label ambiguity are not systematically analyzed for correlation with real-world performance.

## Limitations
- **Training data specifics:** Exact preprocessing (deduplication, filtering) and complete, versioned composition beyond Table 10 are undocumented, hindering replication and edge-case analysis.
- **Hyperparameter transparency:** FastText training settings (n-gram range, learning rate, epochs, dimensionality) are not explicitly stated; assumptions rely on OpenLID-v2 defaults without verification.
- **Benchmark construction details:** New language-targeted benchmarks (BCMS Twitter subsets, ParlaSent, SLIDE, Nordic DSL, ITDI) lack documentation on sampling, labeling, and domain match, raising questions about generalizability.

## Confidence
- **Macrolanguage merges improve precision for confusable groups:** Medium-High. Supported by reduced Arabic confusion and improved Serbian Latin precision, but without full ablation isolating merges from other changes; trade-offs in losing fine distinctions are under-explored.
- **Dedicated `zxx_Zxxx` noise class reduces false positives:** Medium. Logically sound and incorporated, but no controlled experiment quantifies isolated impact; residual noise misclassification may persist.
- **Targeted data augmentation addresses recall gaps:** Medium. Specific gains (e.g., `srp_Latn`) are shown, but overall contribution vs. other modifications is not ablated; quality/domain match of added sources assumed but not verified.

## Next Checks
1. **Ablation study:** Retrain OpenLID-v3 variants by systematically removing (a) macrolanguage merges, (b) the `zxx_Zxxx` class, and (c) targeted data augmentations. Evaluate each on BCMS, Romance, and Scandinavian benchmarks to isolate individual effects on precision, recall, and confusion matrices.
2. **Real-world web crawl validation:** Apply OpenLID-v3 (and the ensemble) to a large, unfiltered web crawl (e.g., Common Crawl snapshot). Manually validate a stratified sample—especially for low-resource languages and noisy documents—to measure true false positive rate and recall under natural distribution shifts.
3. **Per-language threshold optimization:** Replace the fixed 0.5 softmax threshold with thresholds tuned per language (or language group) on a held-out validation set. Assess whether this improves the precision-recall trade-off, particularly for low-resource languages that suffer under the global threshold.
