# Luna-2: Scalable Single-Token Evaluation with Small Language Models

## Quick Facts
- **arXiv ID**: 2602.18583  
- **Source URL**: https://arxiv.org/abs/2602.18583  
- **Reference count**: 11  
- **Primary result**: Replaces multi-token LLM-as-judge evaluation with single-token classification using fine‑tuned small language models, reducing inference cost by 80× and latency by 20× while matching GPT‑4.1 accuracy.

## Executive Summary
Luna-2 reimagines automated evaluation by converting small language models (SLMs) into single‑token classifiers. Instead of generating lengthy chain‑of‑thought responses, a Luna metric produces exactly one token (e.g., “true” or “false”) whose logits yield a confidence score. A shared frozen backbone supports hundreds of lightweight LoRA adapters—one per metric—enabling massive concurrency. The system attains accuracy comparable to frontier models like GPT‑4.1 on key benchmarks (prompt injection, context adherence, tool selection) while cutting costs by 80× and latency by 20×. In production, Luna-2 processes over 100 B tokens monthly, saving an estimated $30 M annually.

## Method Summary
Luna-2 repurposes decoder‑only small language models (e.g., LLaMA 3.2‑3B) as discriminative classifiers. Each metric is defined by a prompt template with placeholders (e.g., `{input}`, `{output}`) and a set of target class tokens. The base SLM remains frozen; a LoRA adapter is trained on metric‑specific data—blending human annotations, synthetic examples, and LLM consensus labels (30k–100k samples). Training minimizes cross‑entropy over the logits of the class tokens at the final position, forcing a single‑token output. During inference, the appropriate adapter is activated, the prompt is tokenized, and one forward pass extracts and normalizes those logits into a confidence score. This design eliminates multi‑token generation, drastically reducing latency and cost while maintaining high accuracy.

## Key Results
- **Accuracy**: Luna‑2 (3B) achieves F1 scores of ~0.95 on prompt injection, context adherence, and tool selection, matching or exceeding ChainPoll GPT‑4.1 (e.g., 0.95 vs 0.96 on context adherence).  
- **Efficiency**: Inference cost reduced by ~80× (≈$0.01 vs $2.00 per 1K evaluations) and latency by ~20× (≈150 ms vs 3000 ms) compared to GPT‑4.1‑based judges.  
- **Scalability**: Hundreds of metrics run concurrently on a single GPU; in production, Luna‑2 processes >100 B tokens monthly with an estimated annual saving of $30 M.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Luna‑2 achieves orders‑of‑magnitude reductions in latency and cost by replacing multi‑token LLM‑as‑judge generation with single‑token classification.  
- **Mechanism**: The system fine‑tunes a decoder‑only small language model (SLM) on metric‑specific data so that, given a prompt describing the evaluation task, it produces exactly one output token (e.g., “true” or “false”). The logits for the predefined class tokens are normalized to yield a confidence score, avoiding the need for chain‑of‑thought or repeated sampling.  
- **Core assumption**: Decoder‑based SLMs retain sufficient reasoning capability after fine‑tuning to perform accurate discriminative evaluations without generating intermediate tokens.  
- **Evidence anchors**:  
  - [abstract] “…single‑token classification using fine‑tuned small language models… reducing inference cost by over 80× and latency by over 20×.”  
  - [section 3.1] “Luna‑2 uses decoder‑only transformer backbones… enforces exactly one output token… extract logits at the final unmasked position and normalize over the class‑token set.”  
  - [corpus] Neighboring papers such as “Towards Small Language Models for Security Query Generation” and “LLavaCode” explore efficient, specialized uses of SLMs, suggesting a broader feasibility of lightweight models for production tasks.  
- **Break condition**: If the evaluation rubric requires multi‑step logical decomposition that cannot be compressed into a single token, the approach fails (as seen in Table 2 where prompting the base SLM without fine‑tuning collapses to near‑random accuracy).

### Mechanism 2
- **Claim**: Hundreds of metrics can run concurrently on a single GPU by sharing a common SLM backbone and attaching lightweight LoRA adapters, one per metric.  
- **Mechanism**: The base SLM weights are frozen; each metric is equipped with a small LoRA adapter (typically ~3% of base model size) trained on its own data. At inference, the appropriate adapter is activated alongside the shared backbone, so the same forward pass serves many metrics without duplicating the full model.  
- **Core assumption**: The cumulative memory of many adapters is negligible compared to multiple full models, and the backbone can process inputs for different metrics in a single pass (or efficiently batched).  
- **Evidence anchors**:  
  - [abstract] “Each metric is implemented as a lightweight LoRA/PEFT head on top of a shared SLM backbone, enabling hundreds of specialized metrics to run concurrently on a single GPU…”  
  - [section 3.1] “All Luna metrics share the same base SLM weights. Each metric m has its own lightweight adapter (LoRA) parameters… Memory and compute cost grow only modestly per metric, unlike duplicating entire models.”  
  - [corpus] Works like “Guard Vector” use parameter‑efficient task vectors for safety, supporting the viability of adapter‑based specialization.  
- **Break condition**: If the number of loaded adapters exceeds GPU memory or adapter switching overhead becomes prohibitive, concurrency degrades.

### Mechanism 3
- **Claim**: High accuracy matching LLM‑as‑judge is achieved by training each SLM head on a diverse, high‑quality dataset that blends human annotations, synthetic examples, and LLM consensus labels.  
- **Mechanism**: For every metric, training data is curated from three sources: real production traces (human‑labeled), synthetically generated or adversarially perturbed samples, and large‑scale pseudo‑labels from an ensemble of frontier LLMs. This mix provides both coverage of edge cases and reliable ground truth while keeping dataset sizes moderate (~30k–100k examples).  
- **Core assumption**: A small, diverse, and well‑labeled dataset is sufficient to distill the evaluation skill of large generalist LLMs into a narrow‑domain SLM, especially when the model retains pre‑trained linguistic knowledge.  
- **Evidence anchors**:  
  - [section 3.2] “We utilize a multi‑faceted approach… Human‑Annotated Production Data… Synthetic Generation and Adaptation… LLM Consensus Labeling… dataset size varies by task complexity, ranging from ∼30k examples to ∼100k examples.”  
  - [section 4.1] Table 2 shows Luna‑2 (3B) matching or exceeding ChainPoll GPT‑4.1 (e.g., 0.95 vs 0.96 F1 on context adherence), while the same base model without fine‑tuning performs poorly.  
  - [corpus] Studies such as “TrueTeacher” and “MiniCheck” similarly demonstrate that small models can rival large judges when trained on targeted data.  
- **Break condition**: Significant distribution shifts (e.g., novel attack vectors, new domains) uncovered in training data will cause accuracy to decay faster than for a generalist LLM‑as‑judge.

## Foundational Learning
### LoRA (Low‑Rank Adaptation)
- **Why needed**: Enables many lightweight metric heads without retraining the entire backbone, drastically reducing memory/compute overhead while allowing independent updates per metric.

- **Why needed**: Converts a generative decoder into a deterministic classifier via constrained output, eliminating multi‑step generation latency and making scoring stable and repeatable.

## Architecture Onboarding
### Component map
Shared frozen SLM backbone (e.g., LLaMA 3.2‑3B) → Metric‑specific LoRA adapters → Prompt template system (placeholders filled with trace data) → Inference engine (Triton + TensorRT‑LLM) → Score normalizer (logits over class tokens normalized to confidence).

### Critical path
1. Receive evaluation request (metric ID, trace data).  
2. Retrieve appropriate LoRA adapter (load into GPU if not cached).  
3. Fill metric’s prompt template with trace data.  
4. Tokenize prompt and run forward pass through shared backbone with adapter.  
5. At final position, gather logits for the metric’s class tokens.  
6. Normalize to produce probability(s) and confidence score.  
7. Return score to caller.

### Design tradeoffs
- **Single‑token vs. multi‑token reasoning**: Speed vs. expressiveness; fine‑tuning mitigates accuracy loss.  
- **Shared backbone vs. separate models**: Memory/concurrency vs. potential metric interference; LoRA isolates but backbone capacity is shared.  
- **Adapter rank (r)**: Higher rank improves metric accuracy but increases memory; Luna‑2 uses r=16, α=16 as a practical sweet spot.  
- **Backbone size (3B vs 8B)**: Larger models may generalize better but cost more; 3B already matches GPT‑4.1 on chosen metrics, so smaller is preferred.  
- **Training data mix**: Human labels ensure quality; synthetic data increases coverage but may introduce artifacts; LLM consensus scales labeling but can propagate judge biases.

### Failure signatures
- **Adapter mismatch**: Model outputs irrelevant tokens or uniform distribution; verify adapter ID and checksum.  
- **Token mapping error**: Class words not found as single tokens in vocabulary; pre‑flight check should catch during adapter setup.  
- **Data drift**: Accuracy drops on new domains; continuous monitoring and periodic re‑training needed.  
- **Memory pressure**: Loading too many adapters saturates GPU; implement LRU eviction or dynamic loading.  
- **Prompt corruption**: Placeholders not substituted correctly; validate template rendering before tokenization.

## Open Questions the Paper Calls Out
1. **Multi‑headed vs. per‑metric heads**: Can a single multi‑headed Luna model achieve comparable accuracy to separate metric‑specific heads while evaluating multiple metrics in one forward pass? (Future Work proposes multi‑task adaptation.)  
2. **Robustness to domain shift**: How robust are Luna‑2 heads to domain shift and concept drift, and what is the minimum viable data needed to effectively re‑tune a metric head via automated continual adaptation? (Future Work describes automated continual adaptation but not data efficiency.)  
3. **Adapter interference**: Does the shared SLM backbone approach with independent LoRA adapters cause measurable interference or “crosstalk” between semantically related metrics, and does this impact calibration? (Adapters are assumed independent but interactions not studied.)  
4. **Data source impact**: To what extent does the quality and source diversity of training data (human vs. synthetic vs. LLM‑consensus) determine the upper‑bound accuracy and robustness, particularly for nuanced tasks like context adherence? (Paper details data strategy but no ablation on source contributions.)  
5. **Scalability limits**: What is the scalability limit of the multi‑tenant LoRA serving approach in terms of number of concurrent metrics per GPU before hardware memory or scheduling overhead negates the throughput benefits? (Paper claims “hundreds” but does not provide detailed profiling at scale.)

## Limitations
- Exact training hyperparameters (LR schedule, epochs, batch size) are unspecified, hindering exact replication.  
- Full prompt templates for all metrics are not public; minor variations could affect performance.  
- Key datasets (RAGBench, BFCL v4) may not be publicly available, requiring proxy datasets for open replication.

## Confidence
- **Accuracy matching GPT‑4.1**: Medium (results are strong but rely on undisclosed data/tuning details, reducing certainty for external replication).  
- **80× cost reduction / 20× latency reduction**: High (methodology is clear and cost modeling transparent; easily verifiable).  
- **Concurrency of hundreds of metrics on one GPU**: Medium (LoRA efficiency proven, but real‑world overhead may limit practical concurrency).
