# Agentic Multi-Source Grounding for Enhanced Query Intent Understanding: A DoorDash Case Study

## Quick Facts
- arXiv ID: 2603.01486  
- Source URL: https://arxiv.org/abs/2603.01486  
- Reference count: 21  
- Primary result: The system improves intent accuracy by +10.9 percentage points over an ungrounded LLM baseline and +4.6pp over a legacy system, achieving 90.7% accuracy on long-tail queries. Deployed in production, it serves >95% of daily search impressions.

## Executive Summary
The paper addresses a critical challenge in multi‑category marketplaces: intent ambiguity arising from short, context‑sparse user queries (e.g., “Wildflower”), which can map to multiple product categories. Standard large language models without grounding often hallucinate items not present in the catalog, leading to poor user experiences. To solve this, the authors develop an Agentic Multi‑Source Grounded system that tightly integrates a staged catalog retrieval pipeline, an autonomous web‑search tool for cold‑start queries, and a configurable disambiguation layer that resolves an ordered dual‑intent prediction. The system is deployed on DoorDash’s food delivery and grocery platform. In A/B tests, it achieves a +10.9 percentage point lift in intent accuracy over an ungrounded LLM baseline and a +4.6pp improvement over the previous rule‑based system, with long‑tail query accuracy reaching 90.7%. The architecture now underpins more than 95% of daily search impressions, demonstrating the practical viability of tool‑augmented LLMs for real‑world intent understanding.

## Method Summary
The pipeline begins with an offline batch process that prunes the catalog to category subsets and indexes items for fast retrieval. At inference time, a query first hits a cache; if missed, it proceeds to a two‑stage catalog retrieval: a lightweight category filter narrows potential categories, followed by a learned ranker that scores individual items. If the catalog returns no viable results, an autonomous web‑search tool is invoked to gather external signals. The collected context—both catalog items and web snippets—is fed to a large language model, which is prompted to output an ordered pair of possible category intents. A separate disambiguation layer then selects the final intent using configurable business rules (e.g., global win‑rate statistics, inventory availability). The system is designed to be modular, allowing each component to be updated independently.

## Key Results
- Overall accuracy: +10.9 percentage points vs. ungrounded LLM baseline; +4.6pp vs. legacy system.  
- Long‑tail performance: 90.7% accuracy, a +13.0pp improvement over baseline.  
- Deployment impact: The system handles >95% of daily search impressions through an offline batch‑and‑cache mechanism, with the remaining ~4% routed to an online fallback.

## Why This Works (Mechanism)
The effectiveness stems from three synergistic factors. First, catalog grounding provides a strong signal by restricting LLM predictions to items that actually exist, eliminating hallucination and yielding an +8.3pp gain. Second, the autonomous web‑search tool extends the system’s reach to cold‑start or trending queries not yet reflected in the catalog, contributing an additional +3.2pp. Third, the configurable disambiguation layer resolves the dual‑intent predictions using business‑friendly rules, adding +1.5pp and allowing non‑ML experts to adjust behavior. The dual‑intent schema itself acts as a safety net: even if the first guess is wrong, the second may be correct, improving robustness on ambiguous queries.

## Foundational Learning
- **Multi‑Source Grounding**  
  Why needed: Prevent LLM hallucination by grounding in external, authoritative data.  
  Quick check: Randomly sample 100 queries; for each, verify that both predicted intents are supported by at least one retrieved item from the catalog or web.

- **Staged Catalog Retrieval**  
  Why needed: Efficiently narrow large catalogs to a manageable candidate set while preserving recall.  
  Quick check: Measure recall of true category after Stage 1 filter; ensure >95% and that Stage 2 ranker improves precision without significant recall loss.

- **Autonomous Web‑Search Tool**  
  Why needed: Provide up‑to‑date signals for queries with no catalog matches, extending coverage.  
  Quick check: For cold‑start queries, check that >80% of web results are relevant to the query intent and that the LLM cites them.

- **Dual‑Intent Prediction**  
  Why needed: Capture inherent ambiguity by allowing two plausible categories, increasing chance of correct final resolution.  
  Quick check: For a set of ambiguous queries, ensure the two intents are semantically distinct yet plausible (e.g., evaluated by human raters).

- **Configurable Disambiguation**  
  Why needed: Decouple business logic from the LLM, enabling rapid adjustments without retraining.  
  Quick check: Change a rule (e.g., favor category with higher inventory) and confirm that the disambiguation outcome flips on a held‑out set as expected.

- **Offline Batch‑and‑Cache**  
  Why needed: Meet strict latency SLAs for the majority of queries by precomputing intents.  
  Quick check: Monitor cache hit rate; confirm that cached queries serve in <5 ms and that batch runs cover >95% of expected daily impressions.

## Architecture Onboarding
### Component Map
Query → Cache Lookup → (cache hit) → Final Intent  
Cache miss → Catalog Retrieval (Stage1: Category Filter → Stage2: Item Ranker) → [if empty result] → Web Search → LLM (Dual‑Intent) → Disambiguation → Final Intent (and async cache write)

### Critical Path
For 95% of impressions (cached queries), the critical path is a single cache lookup (~sub‑millisecond). For the remaining ~4% of daily queries (cold or uncached), the path includes catalog retrieval (Stage1 + Stage2, ~10 ms), optional web search (~50 ms), LLM inference (~50 ms), and disambiguation (~1 ms). The total online latency must stay within the end‑to‑end budget (e.g., <100 ms) to meet product requirements. The most variable components are the web search and LLM call; thus, these are optimized via parallelization and model quantization.

### Design Tradeoffs
- **Coverage vs. Latency**: The offline batch‑and‑cache ensures low latency for frequent queries but creates a coverage hole for novel queries, which must be handled by a slower online path.  
- **Accuracy vs. Cost**: Using an LLM for final prediction is effective but expensive; the dual‑intent design reduces the number of LLM calls (only one per query) while still providing a fallback.  
- **Modularity vs. Performance**: Keeping components independent (retrieval, search, LLM, disambiguation) allows independent updates but adds integration overhead and potential handoff latency.  
- **Simplicity vs. Expressiveness**: The configurable disambiguation layer uses coarse global statistics, which are easy to understand but cannot model personalized user preferences.

### Failure Signatures
- Cache miss rate spikes (e.g., >10%) indicate a shift in query distribution or insufficient batch processing frequency.  
- Catalog retrieval recall drops suggest catalog data quality issues or retrieval pipeline corruption.  
- Web search returns low‑relevance hits can be detected by monitoring click‑through rates on returned URLs; a sharp decline would precede intent accuracy drops.  
- Disambiguation misconfigurations (e.g., outdated win‑rate rules) manifest as a sudden change in the selection ratio between the two intents, often caught by monitoring the “first‑intent win‑rate” metric.  
- Latency degradation on the online fallback path, particularly in the LLM or web‑search stages, can be identified through percentiles of end‑to‑end response times.

### First Experiments
1. **Coverage & Latency Profiling**: Run the batch‑and‑cache on a week of production queries; report cache hit rate, average/95th‑percentile latency for cached vs. uncached paths, and identify bottlenecks in the online pipeline.  
2. **Ablation Validation**: On the long‑tail test set, run the full system and three ablations (no catalog grounding, no web search, no disambiguation). Compare accuracy to the reported incremental gains (+8.3pp, +3.2pp, +1.5pp) and verify interactions.  
3. **Cold‑Start Quality Audit**: Randomly sample 200 cold‑start queries (no catalog hits). For each, manually inspect web‑search results and LLM‑generated dual‑intents. Compute relevance of web results and plausibility of intents; correlate with final accuracy to isolate failure modes.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: Can the teacher's dual‑intent reasoning be distilled into a smaller student model for real‑time inference without accuracy loss on ambiguous tail queries?
- Basis in paper: [explicit] The authors plan to curate high‑quality teacher labels into a silver‑standard dataset to distill capabilities into smaller, cost‑effective student models for real‑time online inference.
- Why unresolved: Distilling multi‑source grounded, tool‑augmented reasoning and preserving dual‑intent fidelity in a compact model is unproven and could degrade accuracy.
- What evidence would resolve it: Train student models of varying sizes on the silver dataset, evaluate on the Tail benchmark, and measure accuracy, latency, and cost; compare dual‑intent consistency with the teacher.

### Open Question 2
- Question: How can the pluggable disambiguation layer be extended to incorporate personalization signals (e.g., user location, order history) while maintaining modularity and low latency?
- Basis in paper: [explicit] The dual‑intent schema and disambiguation layer pave the way for fully personalized intent resolution using such signals.
- Why unresolved: The current layer uses static global win‑rate rules; no concrete method exists to integrate dynamic user features without breaking the architecture or adding overhead.
- What evidence would resolve it: Implement a personalized disambiguation module that consumes user features, run an A/B test on production traffic, and report changes in relevance metrics and system latency.

### Open Question 3
- Question: For the ~4% of daily queries not covered by the offline batch‑and‑cache, what online fallback can deliver real‑time multi‑source grounding and disambiguation within production latency budgets?
- Basis in paper: [explicit] The offline batch‑and‑cache system covers 95.9% of daily search impressions, implying a coverage gap for previously unseen queries.
- Why unresolved: Real‑time execution of the full pipeline (staged retrieval, agentic search, LLM reasoning) may exceed latency constraints; the paper does not describe an online mechanism.
- What evidence would resolve it: Build an online fallback service that executes the pipeline on‑demand, optimize with caching and parallelization, and measure coverage increase and tail latency on a stream of novel queries.

## Limitations
- Ablation gains sum (+13.0pp) exceeds total improvement (+10.9pp), indicating possible overlap or non‑linear interactions.  
- Evaluation is limited to a single marketplace (DoorDash), so generalizability to other domains is uncertain.  
- The definition and sampling of “long‑tail queries” are not fully specified, casting doubt on the robustness of the 90.7% claim.

## Confidence
- Production deployment claim: High (system serves >95% of daily impressions).  
- Overall performance improvement: Medium (supported by internal A/B test; lacks external replication).  
- Ablation attribution breakdown: Low (numerical inconsistencies undermine confidence in isolated contributions).
