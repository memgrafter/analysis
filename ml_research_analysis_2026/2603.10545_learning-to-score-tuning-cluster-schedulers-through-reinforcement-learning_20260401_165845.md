# Learning to Score: Tuning Cluster Schedulers through Reinforcement Learning

## Quick Facts
- **arXiv ID:** 2603.10545  
- **Source URL:** https://arxiv.org/abs/2603.10545  
- **Reference count:** 40  
- **Primary result:** The method delivers an average 33% improvement in a composite performance score over fixed-weight schedulers and a 12% improvement over the best baseline (random search, Bayesian Optimization, TPE), while generalizing robustly to unseen cluster configurations and workloads.

## Executive Summary
The paper addresses the inefficiency of manually tuning scoring function weights in cluster schedulers, which often leads to suboptimal deployments for diverse workloads. The core method uses reinforcement learning with three key innovations: a percentage improvement reward to optimize multi-step parameter tuning, frame-stacking to retain historical action-reward context, and limiting domain information to prevent overfitting and enhance generalization. Trained on heterogeneous FaaS workloads and cluster setups, the approach achieves an average 33% improvement in a composite performance score (combining execution time, queue time, and success rate) over fixed weights and a 12% improvement over the best baseline in lab experiments. It demonstrates robust generalization to unseen cluster configurations and workloads.

## Method Summary
The problem is formulated as reinforcement learning where an agent sequentially proposes weight vectors for the scheduler’s scoring functions. The environment is a FaaS simulator (faas-sim) implementing the Skippy scheduler, wrapped as an OpenAI Gym interface. The state includes static descriptors of the cluster and workload (with domain details deliberately limited to avoid overfitting) and a history of past actions and rewards encoded via frame-stacking. The action is a continuous vector of weights for eight scoring functions. The reward is the percentage improvement of the final composite score (average of normalized execution time, queue time, and success rate) relative to an initial fixed-weight baseline, provided only at the end of an episode after a fixed number of samples. The agent uses Soft Actor-Critic (SAC) with a 512×512×512 MLP and is trained in parallel across three cluster setups (cloud CPU, cloud GPU, edge cloudlet) and multiple workloads. Performance is evaluated against fixed weights, random search, Bayesian optimization, and TPE on both training and held‑out cluster/workload combinations.

## Key Results
- Average 33% improvement in composite performance score over fixed‑weight schedulers.  
- 12% improvement over the best baseline (random search, Bayesian Optimization, or TPE).  
- Strong generalization to unseen cluster configurations and workloads, maintaining performance gains.

## Why This Works (Mechanism)

### Mechanism 1: Percentage Improvement Reward
- **Claim:** Using a *percentage improvement reward* successfully frames multi‑step parameter tuning as a reinforcement learning problem by normalizing the optimization objective.  
- **Mechanism:** The reward \( r_i = (max(r_1,...,r_n) - r_0) / r_0 \) (when \( i = n \)) is given only at the end of an experiment (\( n \) samples). It incentivizes the agent to maximize the *relative improvement* over the baseline fixed‑weight score \( r_0 \) across all allowed weight samples, rather than optimizing absolute scores per step.  
- **Core assumption:** The baseline fixed‑weight score \( r_0 \) is a meaningful reference point for normalization, and maximizing the *rate* of improvement is a suitable proxy for finding high‑performing weights in a limited sample budget.  
- **Evidence anchors:** Abstract explicitly states "percentage improvement reward to address the objective of multi‑step parameter tuning." Section III.A.1 defines the reward function Equation (1) and explains its normalization benefit.  
- **Break condition:** If the baseline fixed‑weight configuration is already near‑optimal for a given cluster/workload, the percentage improvement signal may vanish, providing no learning gradient.

### Mechanism 2: Frame‑Stacking
- **Claim:** *Frame‑stacking* (or recurrent policies) enables the RL agent to retain memory of past exploration (action‑reward pairs), improving sample efficiency in a sequential decision‑making process.  
- **Mechanism:** The state space includes a history of previous weight samples and their rewards, either by stacking these as additional input "frames" to a feedforward network or by using an RNN/LSTM whose hidden state encodes the history. This allows the policy to condition future actions on what has already been tried.  
- **Core assumption:** Past samples provide actionable information about the reward landscape (e.g., regions to avoid or promising directions) that is predictive of future outcomes.  
- **Evidence anchors:** Abstract mentions "frame‑stacking to retain historical action‑reward context." Section III.A.2 describes encoding action‑reward pairs via "frame‑stacking where the number of stacks is equal to the number of maximum samples" or using "a recurrent policy." Section IV.B notes they "use SAC with frame stacking."  
- **Break condition:** If the reward landscape is extremely noisy or non‑smooth such that past samples have zero predictive value for unseen configurations, maintaining this history may introduce harmful bias or simply waste capacity.

### Mechanism 3: Limiting Domain Information
- **Claim:** *Limiting domain information* (e.g., providing only coarse cluster/workload descriptors) prevents the policy from overfitting to specific training setups, enhancing generalization to unseen clusters and workloads.  
- **Mechanism:** During training, the state representation deliberately excludes fine‑grained details about the cluster (e.g., exact device counts) or workload (e.g., specific function mixes), providing only abstracted features. This forces the learned policy to focus on generalizable patterns in how scoring weights affect performance, rather than memorizing idiosyncrasies of training environments.  
- **Core assumption:** The underlying relationship between scoring function weights and performance metrics contains transferable principles across heterogeneous clusters; over‑specific domain features act as noise that distracts from learning these principles.  
- **Evidence anchors:** Abstract states "limiting domain information prevents overfitting and improves performance in unseen clusters and workloads." Section III.A.3 explicitly proposes this as a technique. Section IV.D.2 presents results showing improved performance on *novel* cluster setups and workloads, attributing this to generalization.  
- **Break condition:** If critical, non‑linear interactions between weight choices and *specific* cluster details (e.g., a rare hardware feature) are the primary driver of performance, then omitting those details will cripple the policy's effectiveness on any cluster possessing that feature.

## Foundational Learning

### Reinforcement Learning (Markov Decision Process, Policy, Reward Shaping)
- **Why needed here:** The core method formulates weight tuning as an RL problem. An engineer must understand states (cluster/workload info + history), actions (continuous weight vectors), and the custom reward to modify or debug the agent.  
- **Quick check question:** Given the percentage improvement reward, what is the agent's objective during an episode of 5 samples if the fixed‑weight baseline score is 0.6 and after 3 samples the best observed score is 0.9? What reward will it receive at the end?

### Black‑box Parameter Optimization (Random Search, Bayesian Optimization)
- **Why needed here:** These are the primary baselines (RS, BO, TPE) against which the RL approach is compared. Understanding their limitations (computational cost, poor handling of high dimensionality, lack of sequential memory) explains the motivation for RL.  
- **Quick check question:** Why might standard Bayesian Optimization struggle with the scoring weight tuning problem as described in Section II.C, even with a good kernel?

### Cluster Scheduling (Filtering, Scoring Functions, Bin Packing vs. Spreading)
- **Why needed here:** The entire problem exists within the domain of cluster schedulers. An engineer needs to know what scoring functions (e.g., `MostAllocated`, `ImageLocality`) do and the trade‑offs they embody to interpret which weights the RL agent learns to prioritize.  
- **Quick check question:** In a heterogeneous cluster with edge and cloud nodes, why might `ImageLocality` weight become more important during optimization than in a homogeneous cloud cluster?

## Architecture Onboarding

### Component Map
1. **FaaS Benchmark (faas‑sim):** Simulates function execution, network delays, and heterogeneous hardware. Outputs metrics (exec/queue time, success rate).  
2. **Gym Wrapper:** Encapsulates the benchmark as an OpenAI Gym‑compatible environment. Defines `observation_space` (state), `action_space` (weights), and `reward` function. Handles normalization and domain info limitation.  
3. **RL Agent (SAC/RecurrentPPO):** Neural network policy that takes the state (including stacked frames) and outputs weight vectors. Trained via gradient updates to maximize cumulative (episodic) reward.  
4. **Baseline Optimizers (RS, BO, TPE):** External modules that sequentially propose weight samples to the Gym environment for evaluation.

### Critical Path
State (cluster/workload + history) → Agent Policy → Action (weight vector) → Scheduler (in sim) → Job Allocation → Metrics → Reward → Updated State/History. The loop repeats for `n` samples per episode.

### Design Tradeoffs
- **Reward design vs. convergence:** Percentage improvement encourages final‑best exploration but provides no intermediate reward signal, potentially slowing learning compared to a step‑wise reward.  
- **Frame length vs. generalization:** Longer frame stacks (more history) may help in complex landscapes but risk overfitting to specific sequences in training environments.  
- **Domain abstraction vs. performance:** Greater limitation of domain info improves generalization (as claimed) but may discard signals that are actually highly predictive in certain common scenarios, hurting peak performance.

### Failure Signatures
- **Agent fails to improve over fixed weights:** Likely reward signal is too sparse/noisy, or network capacity is insufficient. Check reward calculation and scale.  
- **Agent performs well on training clusters but poorly on novel ones:** Classic overfitting. Verify domain info is sufficiently limited in the state representation.  
- **Agent's weight selections show high variance across similar experiments:** Indicates poor exploration (entropy too low) or insufficient training steps. Check SAC entropy coefficient or PPO clip range.

### First 3 Experiments
1. **Sanity check with fixed weights:** Run the Gym environment with no agent (just fixed weights) to establish baseline `r0` and verify the reward pipeline. Confirm that `r0` is reasonable and the environment is stable.  
2. **Test frame‑stacking ablation:** Train two agents: one with frame‑stacking (history included) and one with state = only current static info. Compare sample efficiency and final best score on a held‑out training cluster. Expect stacked version to converge faster and/or to a better score.  
3. **Probe domain information limitation:** Train an agent with full domain info (exact cluster/workload specs) and one with limited info (coarse descriptors). Evaluate both on a *novel* cluster configuration from the test set. Expect the limited‑info agent to generalize better, even if it scores slightly lower on training clusters.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How transferable is the learned reinforcement learning policy to different cluster scheduling systems beyond Skippy?  
- **Basis in paper:** The authors state in the conclusions: "In future work, we will be exploring the transferability of learned policy between different scheduling systems."  
- **Why unresolved:** The evaluation is confined to the Skippy scheduler in a FaaS environment. The policy's effectiveness on other schedulers (e.g., Kubernetes, Borg) with varying scoring mechanisms, constraints, and workload types remains unknown due to differences in architecture and optimization goals.  
- **What evidence would resolve it:** Test the policy trained on Skippy directly on other schedulers, possibly with minor adaptations, across diverse cluster setups and workloads. Measure performance gains using the composite score and compare against baselines.

### Open Question 2
- **Question:** How does expanding the set of scoring functions impact the RL agent's tuning performance and generalization capabilities?  
- **Basis in paper:** Future work includes "expanding the set of scoring functions."  
- **Why unresolved:** The study uses a fixed set of eight scoring functions from Skippy. Adding more functions (e.g., from other schedulers) could increase dimensionality, introduce correlations, and challenge the agent's ability to learn effective weight combinations without overfitting or poor convergence.  
- **What evidence would resolve it:** Incrementally increase the number of scoring functions in experiments, train the agent on mixed sets, and evaluate on both similar and novel configurations. Analyze performance trends, weight distributions, and sample efficiency.

### Open Question 3
- **Question:** Can incorporating additional optimization metrics (beyond execution time, queue time, and success rate) enhance the agent's ability to optimize for diverse workload objectives?  
- **Basis in paper:** The authors mention "using additional metrics for improved optimization" as future work.  
- **Why unresolved:** The current composite score weights three metrics equally. Other critical metrics like cost, energy efficiency, SLA compliance, or network usage are ignored, which may limit applicability in scenarios with different priorities (e.g., cost‑sensitive clouds, green computing).  
- **What evidence would resolve it:** Integrate new metrics into the reward function (e.g., weighted sums or multi‑objective formulations), retrain the agent, and test on workloads tailored to those metrics. Compare the composite score and metric‑specific improvements against the baseline.

## Limitations
- The `faas-sim` simulator and Skippy scheduler code are not publicly available, hindering exact replication.  
- Experiments are reported without multi‑seed variance or statistical significance tests.  
- Generalization evaluation uses only a small set of held‑out clusters; scalability to larger or more heterogeneous clusters remains unknown.  
- Key design choices—sparse end‑of‑episode reward, frame‑stack length—are not explored via sensitivity analysis.  
- Inconsistency in the number of scoring functions (8 vs 9) raises questions about the exact action space.

## Confidence
- **RL tuning outperforms baselines:** Medium  
- **Generalization to unseen clusters/workloads:** Medium  
- **Critical role of the three mechanisms:** Low‑Medium  

## Next Checks
1. **Statistical re‑run:** Execute RL and all baselines with ≥10 random seeds on the same 8 cluster–workload pairs; report mean ± std for the composite score and compute p‑values (e.g., paired t‑test) to verify significance of gains.  
2. **Targeted ablation:** Train three variants: (a) without frame‑stacking, (b) using a step‑wise absolute reward, (c) with full domain information. Compare each to the full method on both training clusters and ≥5 unseen clusters to isolate each innovation’s impact.  
3. **Extended generalization:** Generate 10+ novel cluster configurations (varying node counts, hardware mixes, network latencies) and function compositions not seen during training; evaluate the policy’s composite score distribution to assess robustness and potential failure points.
