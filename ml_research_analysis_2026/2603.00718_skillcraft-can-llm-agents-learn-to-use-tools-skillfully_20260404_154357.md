# SkillCraft: Can LLM Agents Learn to Use Tools Skillfully?
## Quick Facts
- **arXiv ID**: 2603.00718
- **Source URL**: https://arxiv.org/abs/2603.00718
- **Reference count**: 38
- **Primary result**: Skill Mode reduces token usage by up to 79% and transferred skills maintain >95% execution success across tasks and models.

## Executive Summary
SkillCraft introduces a novel benchmark and protocol for evaluating LLM agents' ability to learn and reuse higher-level tool compositions, called Skills. The benchmark consists of 126 long-horizon tasks across six domains, scaled by entity count and complexity. The Skill Mode protocol allows agents to automatically compose atomic tool calls into parameterized Python skills, validate them, and cache them for reuse within and across tasks. Experiments with state-of-the-art models show that skill reuse leads to substantial efficiency gains, reducing token consumption by up to 79%, and that skill execution rate strongly correlates with overall task success (r=0.65). Moreover, skills demonstrate robust cross-task and cross-model transferability, with >95% execution success when transferred.

## Method Summary
The SkillCraft benchmark comprises 126 tasks organized into 21 families across six domains (e.g., web APIs, code execution). Tasks are systematically scaled by the number of entities (3–5) and the number of tool calls per entity (3–5), creating long-horizon challenges that require composing multiple atomic tools. The paper introduces a Skill Mode protocol that extends the agent's action space with four MCP primitives: `save_skill`, `execute_skill`, `list_skills`, and `get_skill`. During task execution, agents can encode successful multi-step tool sequences as reusable Python skills, which are validated by a Coding Verifier (syntax, runtime, quality checks) and stored in a persistent Skill Library. Once saved, skills can be invoked with different parameters, allowing agents to amortize planning overhead across repeated subtasks. The evaluation measures success rate (task score ≥90%), token usage, cost, turns, and skill execution rate, and includes cross-task and cross-model transfer experiments.

## Key Results
- Token usage reduced by up to 79% (GPT-5.2) and 71% (Claude-4.5-Sonnet) via skill reuse.
- Success rate strongly correlates with skill execution rate (r=0.65).
- Transferred skills maintain >95% execution success across tasks and models.

## Why This Works (Mechanism)
**Mechanism 1: Token Compression via Skill Abstraction**  
Skill Mode reduces token consumption by compressing repeated multi-step tool sequences into single parameterized skill calls, eliminating redundant serialization of intermediate results. Atomic tool calls force the agent to pass full context (including large outputs) between steps, bloating the conversation. Skills encapsulate verified workflows, allowing internal data chaining without repeated context injection. This amortizes planning overhead across multiple executions. Evidence: token usage reduced by up to 79% (GPT-5.2) and 71% (Claude-4.5-Sonnet); raw tool outputs are repeatedly injected but Skill Mode extracts only minimal task-relevant fields. Break condition: if repetition count is low (N<3), skill overhead may exceed savings.

**Mechanism 2: Success Rate Improvement via Pre-verified Procedural Modules**  
Skill reuse improves success rates by replacing on-the-fly planning with pre-verified procedural modules, reducing reasoning errors in long-horizon tasks. When a skill executes, the agent bypasses multi-step planning for that subtask. Since skills pass a verifier (syntax, runtime, quality checks), their execution is more reliable than generating new tool chains. Evidence: success rate correlates with skill execution rate (r=0.65); cross-task transfer maintains or improves success (Claude: 95%→100%; Gemini: 76%→90%). Break condition: if skills contain edge-case bugs or are overfitted, reuse may propagate errors.

**Mechanism 3: Universal Cross-Model Transfer via Code-Based Skills**  
Well-designed skills achieve universal cross-model transferability because they encode procedural logic independent of the executor's reasoning style. Skills are stored as executable code with clear parameter interfaces; any model capable of executing the code can run it, regardless of how the skill was created. Evidence: transferred skills maintain >95% execution success across tasks and models; Claude-created skills achieve 100% success when executed by Gemini, GLM, and Minimax. Break condition: poorly designed skills (e.g., missing null checks) fail regardless of executor capability.

## Architecture Onboarding
**Component map**:  
`save_skill` → Coding Verifier → Skill Library  
`execute_skill` → Skill Library → (script execution) → Agent  
`list_skills` / `get_skill` → Skill Library → Agent  
Atomic tool calls → MCP Primitives → Environment  
Task Runner orchestrates Agent and Environment.

**Critical path**:  
1. Agent checks available skills via `list_skills`.  
2. If a relevant skill exists, it calls `execute_skill` with task-specific parameters.  
3. If the skill fails or no suitable skill is found, the agent resorts to atomic tool calls to solve the subtask.  
4. Upon successful completion using atomic tools, the agent may generate a new skill from the tool sequence and call `save_skill`.  
5. The Coding Verifier validates the skill; if it passes, the skill is added to the Skill Library for reuse in later tasks.

**Design tradeoffs**:  
- **Flat vs hierarchical skills**: Flat (single-level) skills are robust; hierarchical (nested) skills risk compounding failures, reducing success rates (e.g., GPT-5.2 drops from 90% to 79% in Hierarchical mode).  
- **Creation timing**: The agent must decide when a tool sequence is worth abstracting. Creating a skill for low repetition (N<3) adds overhead without sufficient reuse benefits; missing opportunities for high repetition also wastes potential savings.  
- **Parameterization overhead**: Direct execution (hardcoded values) yields immediate token savings but loses cross-task generalization, while parameterized skills incur abstraction cost but enable reuse across instances.

**Failure signatures**:  
- **Skill creation**: Syntax errors, missing parameters, non-deterministic outputs (rejected by verifier).  
- **Skill execution**: Runtime exceptions (missing fields, API changes), low-quality outputs (e.g., >50% None).  
- **Hierarchical cascades**: Error in a nested skill propagates to all dependents.

**First 3 experiments**:  
1. **Baseline**: Run agent with only atomic tools. Record success rates, token usage, tool calls.  
2. **Skill Mode**: Enable skill tools. Compare metrics; measure `exec_rate` and `reuse_factor`.  
3. **Cross-task transfer**: Pre-compute skills on Easy tasks → run on Hard tasks. Evaluate if transferred skills maintain high `exec_rate` and improve efficiency without new skill creation.

## Open Questions the Paper Calls Out
1. **Error propagation in hierarchical skills** – How can error propagation in hierarchical skill composition be mitigated to enable reliable, nested skill reuse without sacrificing success rates? (Section 5.1; requires systematic error handling and compositional verification to achieve success rates within 2% of flat skills.)
2. **Cross-domain generalization** – To what extent do learned skills generalize across fundamentally different domains or tool types, beyond the within-family transfers evaluated? (Sections 5.2/5.3; cross-domain transfer not tested.)
3. **Sample efficiency** – Can skill acquisition be made significantly more sample-efficient, reducing the number of tasks required to build a useful skill library? (Appendix D.2; Direct Exec Mode shows high efficiency but lacks generalization; need to show few-shot seeding.)
4. **Robust skill creation** – What architectural or training improvements can make LLM skill creation consistently robust, achieving high first-attempt success without repeated repairs? (Appendix D.3; current models have high failure rates on syntax and parameterization.)

## Limitations
- **Reproducibility**: Exact model versions/API names and MCP server implementation are not fully specified, hindering exact replication.
- **Task repetitiveness requirement**: Token and success gains rely on substructure repetition (N≥3); sparse tasks see diminished or negative returns.
- **Skill creation robustness**: Skill quality depends on the generating model; weaker models produce brittle skills, and hierarchical nesting amplifies failures.

## Confidence
- **Skill execution rate ↔ success correlation** (High): Strong statistical evidence (r=0.65) across models and tasks.
- **Token reduction magnitude** (Medium): Empirical results up to 79% reduction, but dependent on task structure, model capability, and reuse frequency.
- **Universal cross-model transfer** (Low): >95% success only for skills created by top models (e.g., Claude); poor-quality skills fail regardless of executor.

## Next Checks

2. **Break-condition stress test**: Systematically vary entity count (N=2,3,4,5) and hierarchy depth; confirm the N≥3 threshold and quantify failure rates in nested skill cascades.
3. **Out-of-distribution generalization**: Test transferred skills on held-out tool domains (e.g., financial APIs) not in the 6 benchmark domains; measure if >95% execution success holds for truly novel procedural contexts.
