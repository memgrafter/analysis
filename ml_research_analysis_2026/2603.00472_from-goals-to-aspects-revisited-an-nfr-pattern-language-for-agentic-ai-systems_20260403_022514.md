# From Goals to Aspects, Revisited: An NFR Pattern Language for Agentic AI Systems

## Quick Facts
- **arXiv ID**: 2603.00472
- **Source URL**: https://arxiv.org/abs/2603.00472
- **Reference count**: 27
- **Primary result**: A pattern language of 12 reusable aspects, including four novel agent-specific patterns, reduces crosscutting non-functional concern scattering in agentic AI codebases by up to 96% in a proof-of-concept refactoring.

## Executive Summary
Agentic AI systems suffer from scattered, crosscutting non-functional requirements (NFRs) like security, cost, and reliability, which contribute to high production failure rates. This paper revisits the 2004 goals-to-aspects methodology, extending its V-graph analysis to model agent-specific NFRs where single tasks exhibit high crosscutting density. The authors present a pattern language of 12 reusable aspects implemented in Rust (ASPECT-RS), introducing four novel patterns for agentic systems: tool-scope sandboxing, prompt injection detection, token budget management, and action audit trails. Validation via a case study of the ZeroClaw framework empirically quantifies severe scattering (e.g., rate limiting in 29 files, path validation in 68 files) and demonstrates a 96% LOC reduction for rate limiting after refactoring. The methodology provides a traceable chain from i* softgoals to concrete aspect implementations, enabling proactive modularization of agent NFRs.

## Method Summary
The research extends the classic goals-to-aspects approach, which maps high-level NFR softgoals (e.g., "Ensure Security") to crosscutting aspects in code. It adapts this for agentic architectures by using V-graph analysis on i* models to identify dense crosscutting (δ≥4) even in simple tasks like "Call LLM Provider." A catalog of 12 patterns was developed, with four targeting agent-specific concerns (e.g., managing token budgets across tool calls). The ASPECT-RS Rust implementation demonstrates feasibility. Validation uses a mixed-methods case study: (1) static analysis of the ZeroClaw framework (200 files, 135K LOC) to measure scattering metrics; (2) a proof-of-concept refactoring applying the patterns; and (3) longitudinal analysis across four versions to examine scattering stability under growth.

## Key Results
- **Extreme scattering quantified**: Rate limiting appears in 3 implementations across 29 files, path validation in 3 divergent forms across 68 files, and error handling in 81% of files.
- **Efficacy via refactoring**: A proof-of-concept applying the pattern language reduced rate-limiting concern-specific LOC from ~195 to 8 (96% reduction) and eliminated implementation inconsistencies.
- **Scattering is structurally stable**: Longitudinal analysis across four versions (120% growth) shows scattering ratios remain constant, indicating crosscutting compounds without modularization.
- **Novel patterns introduced**: Four agent-specific aspects address unique challenges: tool-scope sandboxing, prompt injection detection, token budget management, and action audit trails.

## Why This Works (Mechanism)
Agentic AI systems orchestrate multiple tools, LLM calls, and data flows, creating dense crosscutting even for elementary tasks (e.g., a single LLM call touches cost, reliability, security, and audit concerns). Traditional modularization (classes, functions) cannot encapsulate these concerns, leading to scattering. Goals-to-aspects works by:
1.  **Early identification**: i* softgoal models make NFR trade-offs explicit among stakeholders *before* coding.
2.  **Structured mapping**: The V-graph traceability forces a deliberate link from high-level softgoals (e.g., "Prevent Data Leakage") to specific join points in the agent execution flow (e.g., before tool execution).
3.  **Density flagging**: The δ metric highlights where single tasks have ≥4 crosscutting concerns, signaling a prime candidate for aspectization.
4.  **Pattern reuse**: The catalog provides concrete, tested solutions (e.g., a token budget manager aspect that wraps multiple tool invocations) that replace ad-hoc, scattered implementations.

## Foundational Learning
*   **Crosscutting Concerns (NFRs)**: Non-functional requirements (security, cost, reliability) that span multiple functional modules. **Why needed**: They are the root cause of scattering and instability in agentic workflows. **Quick check**: Can you modify a cost-control policy by changing code in only one place?
*   **Aspect-Oriented Programming (AOP)**: A paradigm for modularizing crosscutting concerns via "aspects" that inject behavior at defined "join points." **Why needed**: Provides the technical mechanism to implement the patterns. **Quick check**: Does your language/framework support method interception or decorators for generic concerns?
*   **i* Modeling**: A goal modeling framework with softgoals (non-functional qualities) and actors. **Why needed**: Captures NFRs and their trade-offs in early design, feeding the V-graph. **Quick check**: Can you model a "Trustworthy AI" softgoal and its contributing factors (e.g., auditability, fairness)?
*   **V-Graph Traceability**: A mapping technique linking model elements (softgoals) to code artifacts (aspects). **Why needed**: Ensures NFRs are not lost from requirements to implementation. **Quick check**: For a "Prevent Infinite Loops" softgoal, can you point to the specific aspect and join point that enforces it?
*   **Join Points in Agentic Flows**: Specific points in the agent's execution (e.g., before LLM call, after tool result). **Why needed**: Define *where* crosscutting logic (e.g., token counting) is applied. **Quick check**: Identify 5 distinct phases in your agent's "think-act" cycle.
*   **Crosscutting Density (δ)**: Number of distinct NFRs impacting a single functional unit (e.g., a tool call). **Why needed**: Quantifies coupling severity; δ≥4 signals a high candidate for aspectization. **Quick check**: Count how many separate concerns (cost, security, log, timeout) your primary agent loop handles.

## Architecture Onboarding
**Component Map**: Agent Execution Engine -> (Tool Invocation, LLM Call, Memory Access) -> Crosscutting Aspects (Rate Limit, Audit, Sandbox, Token Budget) -> External Services (LLM Provider, Tools, DB)

**Critical Path**: A user request enters the Agent Execution Engine. Before each Tool Invocation, the Tool-scope Sandboxing and Audit Trail aspects run. Before each LLM Call, Prompt Injection Detection and Token Budget Management aspects run. After each step, Reliability (retries) and Cost Tracking aspects run. Error Handling aspects catch exceptions globally.

**Design Tradeoffs**:
*   **Performance vs. Safety**: Aspects add overhead (context switching, logging). Tradeoff: depth of audit trail vs. latency.
*   **Flexibility vs. Complexity**: Dynamic token budgets are powerful but increase aspect interaction complexity.
*   **Tool Autonomy vs. Sandboxing**: Strict sandboxing may break tools needing system access; requires per-tool policy configuration.

**Failure Signatures**:
*   **Unbounded Cost**: Missing/ineffective Token Budget aspect leads to runaway LLM expenses.
*   **Security Breach**: Prompt Injection Detection false negatives or missing sandboxing allows tool misuse.
*   **Inconsistent Behavior**: Scattered error handling causes non-deterministic retries and state corruption.
*   **Audit Gaps**: Missing action audit trails hinder forensic analysis after incidents.

**First 3 Experiments**:
1.  **Scatter Audit**: Use a script to count occurrences of rate-limiting logic (e.g., `if token_count > limit`) across your agent codebase. Map findings to the "Resource Consumption" softgoal.
2.  **Aspect Prototype**: Implement the Token Budget Management pattern from ASPECT-RS as a decorator around your primary `agent.step()` function. Measure LOC before/after for budget-related code.
3.  **Traceability Drill**: Create an i* model for your agent's "Safe Execution" softgoal. Manually trace it to at least three concrete join points in your code where security aspects should be applied.

## Limitations
- Generalizability limited to a single case study (ZeroClaw); other agentic architectures remain unevaluated.
- Claims about "high production failure rates" lack empirical industry data; correlation between scattering and failure is inferred, not measured.
- Pattern validation focuses on code metrics, omitting runtime performance, security efficacy, or developer productivity impacts.
