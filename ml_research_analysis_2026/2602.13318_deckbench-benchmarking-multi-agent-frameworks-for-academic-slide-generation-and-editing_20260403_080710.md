# DECKBench: Benchmarking Multi-Agent Frameworks for Academic Slide Generation and Editing

## Quick Facts
- **arXiv ID:** 2602.13318  
- **Source URL:** https://arxiv.org/abs/2602.13318  
- **Reference count:** 40  
- **Primary result:** Introduces a benchmark with a 294-pair dataset and multi-turn evaluation protocol; a modular baseline achieves perfect layout, zero failure rate, and progressive multi-turn improvement.

## Executive Summary
DECKBench proposes the first standardized benchmark for multi-agent academic slide generation and editing. It addresses a gap in evaluation by providing a curated dataset of 294 paper-slide pairs with simulated user editing instructions across three personas (granular, balanced, executive). The benchmark defines a comprehensive metric suite spanning slide-level fidelity, deck-level coherence, layout quality, and multi-turn iterative improvement. A modular baseline decomposes the task into paper parsing, slide planning, HTML creation, and iterative editing. Experiments show the baseline attains competitive faithfulness, perfect layout, and zero failure in initial generation, with GPT-based agents demonstrating clear gains in multi-turn editing convergence. This establishes a reproducible foundation for future research in slide automation.

## Method Summary
The task is to generate an academic slide deck from a PDF paper and iteratively edit it over multiple turns based on user instructions. Inputs include the paper PDF, a reference human-created slide deck (HTML), and a persona-driven simulated user instruction sequence. Evaluation uses a hierarchical metric suite: slide-level (perplexity, faithfulness, text/figure similarity, layout quality), deck-level (perplexity, fidelity, DTW, transition similarity), and multi-turn Δ metrics tracking convergence. The proposed modular baseline consists of an Outline Agent (parses paper via MinerU and creates a structured outline), a Code Agent (maps outline to HTML slides using a coding LLM), and an Editor Agent (applies single-step edits from user instructions). Agents are coordinated in a pipeline: PDF → outline → HTML deck → iterative editing cycles. Reference-based metrics require Hungarian matching to align generated and reference slides before computing similarity.

## Key Results
- Baseline achieves competitive faithfulness (0.538), perfect layout (1.000), and zero failure rate on initial generation.
- In multi-turn editing, it shows progressive structural alignment gains (ΔDTW up to 0.0228) and transition similarity improvements (ΔTransSim up to 0.0323) over five turns.
- GPT-based agents consistently outperform other LLMs across editing personas and metrics.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Simulated user agents enable scalable, reproducible multi-turn editing evaluation by generating varied instruction sequences that approximate real user behavior.
- **Mechanism:** The user simulator compares current intermediate slide decks against ground-truth final decks to derive editing instructions, with three personas (granular, balanced, executive) controlling verbosity and specificity. This creates a controlled interaction loop for measuring iterative improvement via metrics like ΔDTW and ΔTransSim.
- **Core assumption:** Simulated instructions reflect genuine revision patterns and the metrics capture meaningful progress toward target decks.
- **Evidence anchors:**  
  - [abstract] States "simulated user editing instructions" and "multi-turn instruction following" as core contributions.  
  - [section 3.3] Details the simulator's design, persona prompts, and 5-turn generation process.  
  - [corpus] Weak direct evidence; neighbor papers (e.g., "Talk to Your Slides") explore editing agents but not user simulation for multi-turn benchmarks.
- **Break condition:** If persona variations fail to produce instruction diversity or if Δ metrics do not correlate with human-perceived edit quality.

### Mechanism 2
- **Claim:** Decomposing the workflow into specialized agents (Outline, Code, Editor) isolates failure modes and supports robustness in complex slide generation and editing tasks.
- **Mechanism:** The Outline Agent parses papers using MinerU and structures content; the Code Agent maps outlines to HTML templates; the Editor Agent applies single-step edits from user instructions. Modular separation allows independent optimization and fallback strategies.
- **Core assumption:** Task decomposition reduces cognitive load per agent and minimizes cascading errors compared to monolithic systems.
- **Evidence anchors:**  
  - [abstract] Mentions "modular multi-agent baseline" and decomposition into "paper parsing, slide planning, HTML creation, and iterative editing."  
  - [section 5] Describes each agent’s role, implementation choices (e.g., LRMs for planning, coding LLMs for HTML), and fallback mechanisms.  
  - [corpus] Related multi-agent systems (e.g., SlideGen, Auto-Slides) use similar decomposition, but DECKBench formalizes it for benchmarking.
- **Break condition:** If inter-agent communication fails or if decomposition prevents holistic adjustments (e.g., layout reflow across slides).

### Mechanism 3
- **Claim:** A hierarchical metric suite (slide-, deck-, multi-turn-level) provides comprehensive, multi-faceted evaluation that captures both static quality and dynamic editing efficacy.
- **Mechanism:** Reference-based metrics (e.g., DTW, transition similarity) measure alignment to human decks post-Hungarian matching; reference-free metrics (e.g., faithfulness via paper grounding, perplexity) assess intrinsic quality. Multi-turn Δ metrics track iterative convergence.
- **Core assumption:** No single metric suffices; combining linguistic, visual, structural, and temporal measures yields a robust benchmark.
- **Evidence anchors:**  
  - [abstract] Lists metrics: "slide- and deck-level fidelity, coherence, layout quality, and multi-turn improvement."  
  - [section 4] Defines all metrics, including alignment procedures and LLM-as-judge components.  
  - [corpus] Weak direct evidence; benchmarks like PPTC focus on atomic tasks, while DECKBench integrates these dimensions uniquely.
- **Break condition:** If metrics are noisy, redundant, or fail to predict user satisfaction in real editing scenarios.

## Foundational Learning
- **Concept: Multi-agent coordination**  
  - *Why needed here:* The baseline relies on agents passing structured data (outlines, HTML) and handling asynchronous edits; understanding coordination patterns is key to diagnosing failures.  
  - *Quick check:* How does the Editor Agent’s unified edit step differ from separate content and layout editing modules?
- **Concept: Reference-based vs. reference-free evaluation**  
  - *Why needed here:* DECKBench uses both to balance human-deck similarity (reference-based) with inherent quality (reference-free); misinterpretation could skew results.  
  - *Quick check:* Why is Hungarian matching necessary before computing slide-level similarity?
- **Concept: User simulation for interactive systems**  
  - *Why needed here:* Simulated personas drive the multi-turn evaluation; grasping their design (e.g., granularity levels) is essential for interpreting editing results.  
  - *Quick check:* What specific linguistic features distinguish the three personas in the generated prompts?

## Architecture Onboarding
- **Component map:** Outline Agent -> Code Agent -> Editor Agent; User Simulator interacts with Editor Agent each turn.
- **Critical path:** Paper PDF -> Outline Agent (parse/summarize) -> structured outline -> Code Agent (HTML generation) -> initial HTML deck -> Editor Agent cycles (apply edits from User Simulator) -> final deck. Metrics computed after each turn.
- **Design tradeoffs:** HTML format ensures editability but may limit layout sophistication; modularity aids debugging but introduces coordination latency; simulated users enable scalability but may not capture all human editing heuristics.
- **Failure signatures:** Layout overflow (elements off-slide), incorrect figure placement or caption mismatches, hallucinated content (low faithfulness), editing inconsistencies (e.g., slide reordering errors), parsing failures on dense math.
- **First 3 experiments:**  
  1. **Baseline generation validation:** Run the full pipeline on 10 diverse papers, compute slide/deck metrics, verify zero failure rate and layout perfection as reported.  
  2. **Persona impact test:** Execute 5-turn editing for one paper under all three personas with GPT-based agents, track ΔDTW and ΔTransSim to confirm persona impact.  
  3. **Editor Agent ablation:** Disable the Editor Agent’s unified edit (force two-step: content then layout), compare convergence speed and error rates against the proposed design.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can multi-agent slide generation systems be improved to handle complex mathematical expressions and figures while maintaining robust layout quality across diverse academic papers?
- **Basis in paper:** [explicit] Section 8 (Future Work): "improving multi-agent pipelines... handling complex mathematical expressions and equations... optimizing slide layout"
- **Why unresolved:** The baseline system uses template-based HTML/CSS layout and struggles with figure scaling/placement and math rendering, as noted in qualitative failures; DECKBench includes math-dense papers (avg. math density 62.8±74.2), highlighting this gap.
- **What evidence would resolve it:** Integrating specialized vision-language or math-aware modules for figure/equation extraction and layout optimization, with ablation studies on DECKBench measuring layout overflow reduction and faithfulness in math-heavy subsets.

### Open Question 2
- **Question:** How should slide editing systems be evaluated beyond similarity metrics to assess real-world usability, comprehension, and accessibility for diverse audiences?
- **Basis in paper:** [explicit] Section 8 (Future Work): "more rigorous, user-centered evaluation, including systematic usability studies, assessment of audience comprehension, and evaluation of accessibility"
- **Why unresolved:** DECKBench focuses on automated reference-based metrics (DTW, Transition Similarity) and simulated user edits; it does not incorporate human evaluations of slide clarity, learning outcomes, or accessibility (e.g., color contrast, screen reader compatibility).
- **What evidence would resolve it:** Conducting controlled user studies with presenters and audiences, measuring comprehension scores, time-to-prepare, and accessibility compliance, correlated with DECKBench metrics to identify which automated metrics predict real-world effectiveness.

### Open Question 3
- **Question:** Can the DECKBench evaluation framework be extended to assess multi-modal presentation generation, including synchronized audio narration and video slides, and how should iterative editing be evaluated in such settings?
- **Basis in paper:** [explicit] Section 8 (Future Work): "extending the current benchmark to encompass full video generation, including synchronized speaker audio, video, and subtitles, or interactive slide decks"
- **Why unresolved:** DECKBench targets static HTML slide decks; real presentations involve temporal dynamics (transitions, animations, spoken content) that are not captured, and multi-turn editing would need to coordinate across modalities.
- **What evidence would resolve it:** Developing a video/speech extension of DECKBench with ground-truth narrated presentations, defining new metrics for audio-visual synchronization and temporal coherence, and evaluating multi-agent systems that generate/edit multi-modal outputs over turns.

### Open Question 4
- **Question:** What mechanisms are needed to support collaborative, version-controlled slide editing in multi-agent frameworks, and how can iterative improvement be measured in team-based scenarios?
- **Basis in paper:** [explicit] Section 8 (Future Work): "supporting edit history, collaborative editing, and version control would facilitate iterative refinement and team workflows"
- **Why unresolved:** The current benchmark simulates a single user agent; real-world slide preparation often involves multiple authors with overlapping edits, requiring conflict resolution and history tracking—aspects not evaluated by ΔDTW or ΔTransSim.
- **What evidence would resolve it:** Implementing a collaborative editing module in the baseline (e.g., using operational transformation or CRDTs), generating synthetic multi-user edit trails, and defining metrics for edit conflict rates, convergence speed, and version consistency across simulated team personas.

## Limitations
- **Simulated user validity:** Persona-driven instructions may not capture full human editing diversity; ΔDTW/ΔTransSim correlation with real user satisfaction is unverified.
- **Metric robustness:** Reference-based alignment (Hungarian matching) and LLM-as-judge components lack human validation; risk of metric noise or redundancy.
- **Generalizability:** Benchmark built on 294 paper-slide pairs (mostly CS/ML?) limits cross-domain applicability; low neighbor citations suggest nascent adoption.

## Confidence
- **Mechanism 1 (Simulated users):** Low – Evidence is largely conceptual; weak direct validation from corpus.
- **Mechanism 2 (Modular decomposition):** Medium – Supported by related work and baseline success, but coordination failure modes underexplored.
- **Mechanism 3 (Hierarchical metrics):** Medium-Low – Comprehensive by design, but predictive validity for real-world editing quality is unestablished.

## Next Checks

2. **Persona impact test:** Execute 5-turn editing for identical papers under all three personas; verify ΔDTW/ΔTransSim trends and analyze instruction diversity (e.g., token length, action types).
