# The Provenance Paradox in Multi-Agent LLM Routing: Delegation Contracts and Attested Identity in LDP

## Quick Facts
- **ArXiv ID**: 2603.18043  
- **Source URL**: https://arxiv.org/abs/2603.18043  
- **Reference count**: 2  
- **Primary result**: Multi-agent LLM systems suffer a provenance paradox where routing by self-claimed quality scores selects the worst delegates; extending LDP with delegation contracts, attested identity, and typed failures restores performance to near-optimal levels.

## Executive Summary
The paper identifies a critical flaw in multi-agent LLM routing: when delegates dishonestly inflate self-claimed quality scores, routers that select based on these scores perform *worse* than random selection—a "provenance paradox." The proposed solution enhances the LLM Delegate Protocol (LDP) with three mechanisms: (1) delegation contracts that explicitly define objectives, budgets, and failure policies; (2) a claimed-vs-attested identity model that distinguishes verified quality scores from self-reports; and (3) typed failure semantics for automated recovery. In simulations and real-model tests, attested routing achieves near-optimal quality (e.g., 0.95 on a 0–1 scale) while self-claimed routing significantly underperforms random. The extensions add negligible overhead and remain backward-compatible.

## Method Summary
The authors evaluate the paradox and solution through two primary methods: (1) a simulated routing environment with 10 delegates where some inflate self-claimed scores, comparing random, self-claimed, and attested selection; and (2) real-model validation using Claude variants performing reasoning tasks. The LDP extensions are implemented and tested across 36 sensitivity configurations with dishonest delegates, measuring task quality, cost, and failure rates. Overhead is assessed in isolation via microbenchmarks.

## Key Results
- Self-claimed routing in 10-delegate simulations achieved mean quality 0.55 versus random 0.68, while attested routing reached 0.95 (near-optimal, d=9.51, p<0.001).
- Real-model validation with Claude: self-claimed scored 8.90 versus random 9.30; attested matched optimal 9.30.
- The attested routing advantage persists across 36 sensitivity configurations involving dishonest delegates.
- All LDP extensions introduce negligible processing overhead (<5 µs) and are backward-compatible.

## Why This Works (Mechanism)
**Delegation Contracts** bound delegation authority by attaching explicit objectives, success criteria, budgets (max tokens/cost), deadlines, and failure policies (`fail_closed`/`fail_open`) to task submissions. The delegator validates received results against these terms; violations yield typed `LdpError` with `partial_output`. This makes resource usage auditable and prevents runaway costs, assuming delegates report violations truthfully or client-side validation can detect non-compliance. Break conditions include delegates ignoring constraints and client validation failing to detect covert violations like token underreporting.

**Attested Identity** extends identity cards with a `claim_type` field (`self_claimed`, `runtime_observed`, `issuer_attested`, `externally_benchmarked`). Routers preferentially select delegates with attested claims, ignoring potentially inflated self-reports. This eliminates the provenance paradox by ensuring quality scores reflect verified performance. It assumes attested scores are accurate and issuers trustworthy; if attestation infrastructure is compromised, stale, or not adopted, the paradox may persist.

**Typed Failure Semantics** replace free-form error strings with structured `LdpError` objects containing `category` (e.g., `runtime`, `policy`, `capability`), `severity`, `retryable`, and optional `partial_output`. Routers apply predefined policies per category to automate recovery (retry, reroute, escalate). This relies on delegates emitting accurate, well-formed errors; misclassification can cause inappropriate retries and degrade reliability.

## Architecture Onboarding
- **Component map**: Delegate Identity Card -> TASK_SUBMIT (with optional contract) -> Router (selects based on attested identity) -> Delegate -> Result/Provenance or LdpError -> Client Validation (checks contract) -> Lineage update.  
- **Critical path**: 1) Delegator constructs task + contract; 2) Router selects delegate using attested quality; 3) Delegate executes; 4) On success, returns result + provenance; on failure/violation, returns `LdpError`; 5) Delegator validates against contract; 6) Update verification status and lineage.  
- **Design tradeoffs**: Backward compatibility vs. expressiveness (new fields optional); contract expressiveness vs. enforcement (client-side only, no cryptographic receipts); attestation accuracy vs. overhead (no signatures in base spec).  
- **Failure signatures**: Budget overflow -> `LdpError(category=policy, code=CONTRACT_VIOLATED)`; runtime crash -> `category=runtime, retryable=true`; quality inflation -> router picks low-true-quality delegates with high `self_claimed` scores.  
- **First 3 experiments**: 1) Simulated routing: compare random, self-claimed, and attested selection to observe quality drop in self-claimed. 2) Contract enforcement: set `max_tokens` too low; verify client detects overuse and returns `LdpError`. 3) Typed error recovery: force delegate to return errors of different categories; confirm router retries only `retryable=true` cases.

## Open Questions the Paper Calls Out
1. How can a standardized attestation infrastructure be designed and evaluated for issuer-attested and externally-benchmarked quality claims in LDP, including issuer identity models, cryptographic signatures, claim expiry semantics, and skill-specific scoping?  
2. Can delegation contracts be endowed with machine-checkable success criteria (e.g., formal predicates for word count, output schema, required fields) to replace free-form strings and enable automated contract validation without delegator intervention?  
3. Can runtime enforcement mechanisms (e.g., cryptographic resource-consumption receipts, platform-level billing integration) prevent delegates from violating contract constraints like token budgets or deadlines, moving beyond best-effort client-side validation?  
4. Does the provenance paradox persist at scale across diverse, real-world task families (e.g., creative writing, code generation, data analysis) and non-stationary delegate populations, or is it confined to the controlled experimental settings?  
5. How can delegation depth limits (max_delegation_depth) be reliably enforced at runtime in multi-hop scenarios using the lineage chain, preventing infinite or excessive sub-delegation?

## Limitations
- **Generalizability**: Paradox and solution validated primarily with Claude and simulated delegates; unknown across diverse model families or real-world heterogeneous agent populations.
- **Attestation Ecosystem**: Assumes trustworthy, non-coordinated issuers and timely score updates; no evidence on scalability or resilience against coordinated false attestation or issuer compromise.
- **Enforcement Depth**: Delegation contracts rely on client-side validation only; no cryptographic receipts or on-ledger verification, leaving gaps for covert violations like token underreporting.

## Confidence
- **Provenance Paradox Existence**: High (strong statistical evidence, p<0.001, consistent effect size)
- **Attested Routing Efficacy**: Medium (near-optimal in tests, but limited to controlled settings; long-term trust dynamics unevaluated)
- **Solution Components (Contracts/Identity/Errors)**: Medium (design logic sound, backward-compatible, but real-world adoption, interoperability, and adversarial resistance unproven)
- **Generalizability & Security Assumptions**: Low (core assumptions like trusted issuers and honest error reporting lack adversarial validation)

## Next Checks
1. **Cross-Model Replication**: Re-run simulations and real-model validation using at least three additional model families (e.g., GPT-4, Llama 3, Mistral) to test parity of the paradox and attested routing gains.
2. **Compromised Attestation Test**: Introduce a coordinated attacker issuing false high `issuer_attested` scores for low-quality delegates; measure degradation in attested routing performance.
3. **Scalable Contract Overhead**: Benchmark `TASK_SUBMIT` validation (including complex budget/deadline checks) under load with 1000+ concurrent tasks and network latency; report median/99th percentile latency increase relative to bare LDP.
