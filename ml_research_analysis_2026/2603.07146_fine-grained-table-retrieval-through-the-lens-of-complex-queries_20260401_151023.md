# Fine-Grained Table Retrieval Through the Lens of Complex Queries

## Quick Facts
- arXiv ID: 2603.07146
- Source URL: https://arxiv.org/abs/2603.07146
- Reference count: 15
- Primary result: DCTR improves capped recall@25 by up to +23.3% and downstream text-to-SQL execution accuracy by up to +5% on industry benchmarks (BEA VER, FIBEN, BIRD).

## Executive Summary
Fine-grained table retrieval for complex analytical queries over large relational databases remains challenging due to multi-constraint queries and dense schemas that single-vector dense retrieval cannot adequately handle. This paper introduces DCTR, a system that decomposes natural language queries into typed semantic components—schema, value, and aggregator—and performs multi-vector retrieval aligned with these components. Additionally, DCTR leverages a foreign-key graph to expand candidate tables beyond direct semantic matches, capturing necessary join contexts. Evaluations on three industry-aligned benchmarks (BEA VER, FIBEN, BIRD) show substantial improvements in capped recall@25 (up to +23.3%) and downstream text-to-SQL execution accuracy (up to +5%). The method proves especially robust for longer queries and those involving densely connected tables.

## Method Summary
DCTR operates as a pipeline: first, an LLM decomposes the query into schema, value, and aggregator components using a fixed prompt. Each component is embedded and independently retrieved against two dense vector indices—one for tables and one for columns—built offline with a pretrained embedding model. Retrieved columns are mapped to their parent tables. Then, for each database, a schema graph is constructed from the candidate tables using foreign-key relationships; each connected component forms a table group. Groups are scored by summing the top-k similarities per query component (group coverage), optionally expanding each group to all FK-adjacent tables. Finally, the top n groups are selected, and within each, the top k tables are returned as the retrieved set. No model training is involved; the approach relies on pretrained embeddings and a fixed LLM.

## Key Results
- DCTR achieves capped recall@25 gains of +7.9% on BEA VER (0.350 → 0.429 with bge-small) and +23.3% on FIBEN (0.281 → 0.516 with e5-small) over dense baselines.
- Downstream text-to-SQL execution accuracy improves by +3% on BEA VER and +5% on FIBEN.
- The method maintains performance on longer queries (≥40 tokens) and queries with more components, while baseline recall degrades.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Typed query decomposition into schema, value, and aggregator components improves fine-grained alignment between query constraints and schema elements for complex, multi-constraint queries.
- **Mechanism:** A language model segments the natural language query into atomic semantic units. Only schema and value components are embedded and retrieved independently against separate table/column indices, avoiding the dilution of constrained signals in a single full-query embedding.
- **Core assumption:** Complex queries contain multiple, separable semantic constraints (tables/columns vs. filter values) that should be matched at different granularities to schema elements.
- **Evidence anchors:** [abstract] "...decomposes queries into semantic units of distinct types to enable fine-grained query-schema alignment using multi-vector embeddings..." ; [section 4.1] "First Pass Retrieval: each query component is processed independently... This initial retrieval produces unranked lists..." ; [section 6.2] "The baseline’s recall degrades steadily as the number of components increases while DCTR remains stable."
- **Break condition:** Fails if query decomposition is inaccurate (e.g., misclassifies a value as a schema component) or if the database contains highly ambiguous terminology where multiple schema elements plausibly match a single component.

### Mechanism 2
- **Claim:** Global connectivity-awareness via foreign-key (FK) graph expansion recovers relevant tables that lack direct semantic similarity to the query but are logically required via joins.
- **Mechanism:** Candidate tables from first-pass retrieval form nodes in an FK graph. Each connected component (table group) is expanded to include all FK-adjacent tables, even if not initially retrieved by semantic matching. This surfaces multi-hop join contexts.
- **Core assumption:** Relevant tables for an analytical query are often connected via FK joins in a normalized schema, and some necessary tables may not contain terms directly resembling the query text.
- **Evidence anchors:** [abstract] "...global connectivity-awareness via foreign-key graph expansion to recover relevant tables beyond semantic similarity." ; [section 4.1] "By global FK-expansion, we expand each table group by including all tables that are connected through FKs... recovering multi-hop join context." ; [section 6.1] Group expansion improves recall on BIRD (+3–5%) but degrades on FIBEN/BEA VER (up to -30%), indicating dataset-dependent utility.
- **Break condition:** Breaks on extremely large, sparsely connected schemas where FK expansion introduces massive noise, overwhelming the candidate set (as seen on FIBEN/BEA VER). Also fails if the FK graph is incomplete or inaccurate.

### Mechanism 3
- **Claim:** Group scoring via component-wise top-k voting within a table group balances recall of diverse query components with precision, mitigating over-retrieval from expansion.
- **Mechanism:** For each query component, compute its similarity to all tables in a group. The group's score sums the top vote_k similarities per component. This favors groups where multiple tables collectively cover different query aspects.
- **Core assumption:** A set of joinable tables (a group) is relevant if different tables within it match different query components, rather than a single table matching all.
- **Evidence anchors:** [section 4.1] "We introduce a parameter vote_k to cap the number of tables included in the scoring... group coverage score = Σ top_vote_k({sim(t, C_j)})" ; [section 6.2] "DCTR achieves stronger performance on queries involving densely connected tables, indicating that connectivity-aware grouping improves retrieval of joinable table sets."
- **Break condition:** Ineffective if query components are all semantically tied to the same table (monolithic query), where group scoring may penalize groups containing that single high-scoring table plus irrelevant neighbors. Also sensitive to vote_k and n_groups hyperparameters.

## Foundational Learning
### Dense vector retrieval single-vector limitations
- **Why needed here:** The baseline represents a query and a table as single vectors. Understanding this limitation (inability to represent multi-constraint relevance) explains DCTR's multi-vector decomposition.
- **Quick check question:** Why might a single embedding for the query "average sale of Luka Dončić jerseys in 2025" fail to match both a `sales` table and a `players` table, even if both are relevant?

### Schema linking in text-to-SQL
- **Why needed here:** DCTR's decomposition is a form of schema linking. Knowing prior work (e.g., RESDSQL, RASL) clarifies that DCTR operates in open-domain retrieval, not within a fixed database context.
- **Quick check question:** How does open-domain table retrieval differ from schema linking within a single, known database schema?

### Graph-based reasoning over database schemas
- **Why needed here:** DCTR's FK graph expansion relies on understanding tables as nodes and FKs as edges. This connects retrieval to the relational structure.
- **Quick check question:** What is the risk of adding all FK-adjacent tables to a candidate group without a scoring heuristic?

## Architecture Onboarding
- **Component map:**  
  1. Query Decomposer: LLM (gpt-4.1-mini) with fixed prompt → outputs typed components (schema/value/aggregator).  
  2. Dense Indices: Two Qdrant collections (table embeddings, column embeddings). Built offline from schema text.  
  3. First-Pass Retriever: For each schema/value component, independently search table & column indices → merge results to parent tables.  
  4. Schema Graph Builder: Per-database, build undirected graph from candidate tables using FK relationships.  
  5. Group Scorer: For each connected component (group), compute group coverage score using top-vote_k per component.  
  6. Final Selector: Pick top n_groups groups per DB, then top vote_k tables within each.  

  Flow: Query Decomposer → Dense Indices → First-Pass Retriever → Schema Graph Builder → Group Scorer → Final Selector.

- **Critical path:** Decompose query → retrieve tables/columns per component → map columns to tables → build per-DB FK graph on candidates → find connected components → score & expand groups → select final tables.

- **Design tradeoffs:**  
  *Precision vs. Recall:* Higher vote_k and n_groups increase recall but add noise. Expansion (expand groups=True) boosts recall on small, dense schemas (BIRD) but harms on large ones (FIBEN).  
  *Cost:* Multi-vector retrieval & graph construction add latency vs. single-vector baseline.  
  *Generality:* Decomposition relies on LLM consistency; graph expansion assumes reliable FK metadata.

- **Failure signatures:**  
  - Low recall on short, simple queries (over-decomposition noise).  
  - Dramatic recall drop on large schemas when expand groups=True.  
  - High variance across runs if LLM decomposition is stochastic (mitigated by fixed prompt/config).

- **First 3 experiments:**  
  1. Decomposition sanity check: Run decomposer on 50 random queries; verify >90% of schema components are exact table/column name matches (using schema dump).  
  2. Index sanity check: Embed 100 known table-column pairs; confirm top-1 retrieval accuracy >95% when querying with the exact name.  
  3. Group expansion isolate: On BIRD, set expand groups=False → measure recall@25. Then enable expansion → expect +3–5% gain. On FIBEN, expect drop. Validates connectivity-awareness effect.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** What additional complexity dimensions beyond query and data complexity impact open-domain table retrieval performance?
- **Basis:** [explicit] The authors state that "deeper insights are lacking regarding such complex retrieval characteristics" while only formalizing complexity along query- and data-dimensions.
- **Why unresolved:** Their binary framework likely omits factors such as schema naming consistency, join path length, or query ambiguity that affect retrieval.
- **What evidence would resolve it:** Large-scale correlation studies across diverse databases linking retrieval metrics to granular schema and query properties.

### Open Question 2
- **Question:** How can group expansion parameters be adaptively set to avoid dataset-specific performance degradation?
- **Basis:** [explicit] They observe expansion helps on BIRD but harms larger schemas, suggesting "a dynamic value for k would be viable in practice."
- **Why unresolved:** Current DCTR uses fixed hyperparameters; no mechanism adapts to database size or connectivity density.
- **What evidence would resolve it:** An adaptive algorithm scaling n_groups and vote_k with database statistics (e.g., tables per DB, average FK degree).

### Open Question 3
- **Question:** Which architectural modifications enable effective retrieval for queries requiring many (≥10) gold tables?
- **Basis:** [explicit] Results show "both methods exhibit a degradation... The proposed method behaves similarly to the baseline, indicating limited advantage when there is a lot of relevant tables to retrieve."
- **Why unresolved:** DCTR’s grouping and voting approach saturates; extensive join contexts remain poorly retrieved.
- **What evidence would resolve it:** New methods explicitly evaluated on high-cardinality table sets with many join-connected gold tables.

### Open Question 4
- **Question:** What is the reliability and error profile of LLM-based query decomposition used in DCTR?
- **Basis:** [inferred] The pipeline fully depends on LLM decomposition, yet the paper provides no analysis of decomposition quality or its impact on retrieval.
- **Why unresolved:** Decomposition errors likely cascade; unknown consistency across query types or models.
- **What evidence would resolve it:** Human-annotated gold decompositions, error analysis of LLM outputs, and correlation between decomposition quality and retrieval accuracy.

### Open Question 5
- **Question:** Should different query component types (schema, value, aggregator) be weighted differently in table group scoring?
- **Basis:** [inferred] DCTR scores groups by summing component similarities with equal weighting, though component types may have varying discriminative power.
- **Why unresolved:** Schema components likely more critical than value literals; aggregators might indicate structural needs.
- **What evidence would resolve it:** Ablation with learned per-component weights, or human judgments on component importance for table relevance.

## Limitations
- Decomposition reproducibility: exact LLM prompt details (few-shot examples, decoding parameters) are unspecified, risking variance in component extraction across runs.
- Hyperparameter tuning: the process for selecting vote_k, n_groups, and expand_groups is opaque; optimal settings may be dataset-specific and not fully reported.
- Generalizability: strong gains on three benchmarks are clear, but the corpus shows no cited follow-up work, limiting confidence in broader adoption or robustness to unseen schemas.
