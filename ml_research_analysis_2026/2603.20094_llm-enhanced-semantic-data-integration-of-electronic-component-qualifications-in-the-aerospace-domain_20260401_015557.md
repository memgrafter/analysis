# LLM-Enhanced Semantic Data Integration of Electronic Component Qualifications in the Aerospace Domain
## Quick Facts
- **arXiv ID**: 2603.20094
- **Source URL**: https://arxiv.org/abs/2603.20094
- **Reference count**: 34
- **Primary result**: Deployed VKG+LLM system reduces qualification retrieval effort to ~5 person-minutes per component (>70% reduction vs manual) with high accuracy (F1 >92%) for direct and similarity qualifications.

## Executive Summary
Electronic component qualification data in aerospace manufacturing is typically siloed across Product Lifecycle Management (PLM) and qualification databases, forcing designers into time-consuming manual searches prone to errors. This paper presents a hybrid system combining Virtual Knowledge Graphs (VKG) for semantic integration and SPARQL querying with Large Language Models (LLMs) for semi-automated data cleansing and vector-based similarity search. The VKG, built using Ontop, provides a unified query interface over relational sources without data duplication. LLMs (GPT-OSS-120B) extract structured part numbers from free-text notes and normalize manufacturer names, reducing manual effort. Retrieval is hybrid: SPARQL handles exact and near-exact matches (direct and similarity qualifications), while vector similarity (using multilingual-e5-large-instruct embeddings) addresses alternative qualifications requiring flexible criteria. The system is deployed at Thales Alenia Space.

Evaluation shows high F1-scores for direct (92.1%) and similarity (93.7%) qualifications, though alternative qualification retrieval lags (F1 61.9%). A cost-benefit analysis demonstrates that after an initial setup of 60 person-days, the VKG+LLM pipeline reduces per-component retrieval effort to approximately 5 person-minutes, compared to 15 minutes for a RAG-based alternative and 40 minutes for manual search, achieving over 70% reduction beyond 5,000 components. The system is actively used in production.

## Method Summary
The methodology centers on constructing a Virtual Knowledge Graph (VKG) that semantically integrates two heterogeneous relational databases: a PLM database and a qualification database. An ontology (TASI) defines domain concepts and relationships; Ontop generates R2RML mappings and rewrites SPARQL queries into source-specific SQL at runtime, enabling a virtual, unified view. Data cleansing—critical due to inconsistencies in manufacturer names and unparsed part numbers in qualification notes—is performed by prompting GPT-OSS-120B in a few-shot, semi-automated manner. The LLM extracts part numbers from free text and proposes normalization rules for manufacturer variants, which domain experts validate or refine. For qualification retrieval, the system first executes SPARQL queries targeting direct (exact match on component identifier) and similarity (relaxed attribute matches) qualifications. When these fail, it falls back to a vector search: component and qualification records are serialized to JSON, embedded using multilingual-e5-large-instruct, and ranked by cosine similarity to surface alternative qualifications that meet complex, multi-attribute criteria.

## Key Results
- Retrieval performance: F1-scores of 92.1% for direct qualifications, 93.7% for similarity qualifications, and 61.9% for alternative qualifications (the latter using vector search).
- Efficiency gains: Per-component effort reduced from ~40 minutes (manual) to ~5 minutes (VKG+LLM) and ~15 minutes (RAG), yielding >70% reduction beyond 5,000 components despite higher initial setup (60 vs 10 person-days).
- Deployment: The system is successfully deployed and actively used by designers at Thales Alenia Space.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Virtual Knowledge Graphs (VKGs) enable integrated, queryable access to siloed relational databases without materializing a new physical database.
- **Mechanism**: A curated ontology defines a semantic model (classes, properties). Ontop framework generates R2RML mappings that translate SPARQL queries into source-specific SQL at runtime, executing them across the PLM-DB and QC via a virtual lens that also applies LLM-generated normalization rules for manufacturer names.
- **Core assumption**: A stable, well-defined ontology and correct mappings can abstract away source heterogeneity sufficiently for exact and similarity-based qualification matching.
- **Evidence anchors**: [abstract] "combines Virtual Knowledge Graphs (VKGs) for semantic integration and structured querying via SPARQL"; [section 4] Description of Ontop, mappings, and the *Lens* for virtual manufacturer normalization.
- **Break condition**: Frequent schema changes in source databases or a need to query highly dynamic, unstructured data not captured in the relational schema would undermine the VKG's utility, requiring frequent remapping.

### Mechanism 2
- **Claim**: LLMs (specifically, GPT-OSS-120B) significantly reduce human effort in data cleansing—extracting Part Numbers from free-text and normalizing manufacturer names—through a semi-automated, few-shot prompting workflow with human validation.
- **Mechanism**: LLMs process raw text columns (e.g., QC "Notes") to extract structured Part Numbers and generate normalization rules for manufacturer variants. Outputs are cross-validated against known databases (PLM-DB) or reviewed by domain experts, creating clean, structured columns usable by the VKG.
- **Core assumption**: The LLM can reliably extract/normalize the target entities with few-shot prompts and domain expert oversight, and the resulting cleaned data is accurate enough for downstream matching.
- **Evidence anchors**: [section 4] Detailed Figure 2 and text on PN extraction; "GPT-OSS-120B generated 50 normalization rules. Of these, 9 (approximately 18%) required further refinement."; [section 6] "data cleaning proved to be as crucial and even more time-consuming than data modeling... Leveraging LLMs significantly streamlined this process."
- **Break condition**: LLM extraction/normalization error rate becomes too high, overwhelming the human-in-the-loop and negating efficiency gains. Data formats (e.g., notes) become too noisy or convention changes dramatically.

### Mechanism 3
- **Claim**: A hybrid retrieval strategy (symbolic SPARQL + vector similarity search) effectively addresses the three qualification types (direct, similarity, alternative) by leveraging the strengths of each method.
- **Mechanism**: 1) SPARQL queries over the VKG perform exact or near-exact attribute matching for direct and similarity qualifications. 2) When these fail, a vector-based search (using `multilingual-e5-large-instruct` embeddings of component/qualification JSON) ranks alternative candidates by semantic similarity of combined attributes (e.g., assembly process, dimensions), which is then reviewed by an expert.
- **Core assumption**: Structured attribute matching is deterministic and sufficient for the first two types, while vector similarity can approximate the complex, expert-judgment-based criteria for alternative qualifications.
- **Evidence anchors**: [abstract] "retrieval of qualifications is then performed through an Ontology-based Data Access approach for structured queries and a vector search mechanism for retrieving qualifications based on similar textual properties."; [section 4] SPARQL query in Listing 2 for direct qualification; description of vectorization and cosine similarity for alternatives.; [section 5] RAG comparison showing high F1 for direct/similarity (>92%) but lower for alternative (61.9%), confirming the hybrid split.
- **Break condition**: Vector similarity fails to surface relevant alternative candidates (low recall/precision), forcing a fallback to full manual review, or the criteria for "alternative" become too complex for embedding-based ranking.

## Architecture Onboarding
### Component Map

                                                                                |
                                                                                v
                                                                      JSON serializer → multilingual-e5-large-instruct embeddings → Vector index
                                                                                |
                                                                                v
                                                                        Web UI (issues SPARQL or vector queries)

### Critical Path
1) LLM data cleansing (manufacturer rules, PN extraction) → 2) Ontology & mapping design (one-time) → 3) VKG/Onboarding setup (Ontop configuration) → 4) Vector index build → 5) Query execution (SPARQL first, fallback to vector).

### Design Tradeoffs
- VKG+LLM vs. RAG: VKG has high upfront cost (60 vs. 10 person-days) but low per-query cost (5 vs. 15 min/component) and guaranteed precision for exact/similarity matches. RAG is fast to deploy but requires expert validation for all outputs and has lower performance on alternative qualifications.
- Symbolic vs. Vector: Symbolic (SPARQL) offers explainability and precision for rule-based matches. Vector provides recall for fuzzy, unstructured-criteria matches but is less interpretable and needs expert review.

### Failure Signatures
- LLM extraction failure: PN not found in notes or extracted incorrectly → component shows "no qualification" or wrong match.
- Ontology/mapping misalignment: Valid qualification not returned by SPARQL → likely a mapping error or missing data property.
- Vector search misses: Relevant alternative qualification not in top-K results → embedding model may not capture key attribute similarity for that component family.

### First 3 Experiments
1. Validate LLM PN extraction: Take 50 QC entries, run extraction pipeline, measure accuracy against manual baseline. Target >98% correct extractions after human review of LLM failures.
2. Test SPARQL query fidelity: For a known set of 100 components with direct qualifications, run the Listing 2 query. Measure recall (should be ~100% if data is clean) and investigate false negatives (likely data issues).
3. Benchmark vector retrieval: For 50 components with no direct/similarity match, run vector search for alternatives. Have domain experts judge if the top-5 results contain valid suggestions. Target >80% inclusion rate.

## Limitations
- VKG relies on stable source schemas; frequent schema changes require remapping, threatening maintenance.
- LLM data cleansing incurs 18% rule refinement and may degrade with noisier input; alternative qualification recall is low (F1 61.9%).
- Evaluation is single-site (Thales Alenia Space); generalizability to other aerospace contexts and the high upfront cost (60 person-days) pose adoption barriers.

## Confidence
- VKG integration: Medium (supported by design but corpus weak; depends on ontology stability).
- LLM data cleansing: Medium-High (quantified refinement, but human-in-loop critical for accuracy).
- Hybrid retrieval: High for direct/similarity (F1 >92%), Low for alternative (F1 61.9% indicates recall issues).
