# MobileDreamer: Generative Sketch World Model for GUI Agent

## Quick Facts

- **arXiv ID**: 2601.04035  
- **Source URL**: https://arxiv.org/abs/2601.04035  
- **Reference count**: 20  
- **Primary result**: MobileDreamer improves task success rate by 5.25% over strong baselines, achieving state-of-the-art performance on mobile GUI tasks.

## Executive Summary

MobileDreamer is a framework that introduces a world model for mobile GUI agents to overcome the limitation of reactive planning in long-horizon tasks. Its core is a textual sketch world model that converts screenshots into structured text (label, text, position) and uses an order-invariant loss to forecast post-action states robustly. A rollout imagination strategy recursively builds a prediction tree from candidate actions, allowing the agent to evaluate multi-step outcomes before acting.

On the Android World benchmark, MobileDreamer achieves a state-of-the-art success rate, improving by 5.25% over strong baselines. The world model itself demonstrates high forecasting accuracy (mIoU 0.8564, F1-score 0.7608) and ablations confirm the contributions of its sketch representation, order-invariant learning, and tree-based rollout.

## Method Summary

MobileDreamer consists of two components: a textual sketch world model (TSWM) and a rollout imagination engine. First, the system extracts a structured representation of the current GUI state using OCR (PaddleOCR-VL), producing a set of UI elements with label, text, and bounding box. This sketch, along with an action string, is fed to a fine-tuned Qwen3-8B model (via LoRA) to predict the next-state sketch. Training uses a combined loss: an order-invariant optimal transport matching loss (with costs based on IoU, label similarity, and text similarity) and a token cross-entropy loss, ensuring robustness to element ordering and small spatial shifts.

During deployment, the agent (an LLM like Claude) receives the current screenshot and task goal. It generates a sub-task and proposes M candidate actions. For each candidate, TSWM predicts the resulting sketch; optionally, the process recurses to a specified depth d, building a tree of imagined trajectories. A reasoner then selects the root action whose predicted subtree best aligns with the goal. The chosen action is executed, and the loop repeats.

## Key Results

- Achieves state-of-the-art success rate on Android World, improving by 5.25% over strong baselines.
- World model forecasting accuracy: mIoU = 0.8564, F1-score = 0.7608, significantly outperforming other LLM-based predictors.
- Ablation studies confirm that all three components (textual sketch, order-invariant loss, tree rollout) contribute to performance; removing any degrades results.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** A textual sketch representation combined with order-invariant learning enables robust, spatially-aware prediction of post-action GUI states from raw screenshots, which is more efficient and effective than pixel-level or pure text-based approaches.
- **Mechanism:** The world model converts screenshots into a structured set of UI elements (label, text, bounding box). Instead of token-level cross-entropy loss (sensitive to element order and minor bounding box shifts), it uses an optimal transport matching loss that pairs predicted and ground-truth elements based on a combined IoU and text similarity cost. This forces the model to learn the geometric and semantic transition dynamics of the GUI state, not the exact textual serialization.
- **Core assumption:** A minimal structural representation (label, text, position) is sufficient for planning, and element-level matching is a more appropriate training objective than sequential token prediction for a set-based state representation.
- **Evidence anchors:**
  - [abstract]: "Textual sketch world model forecasts post-action states... designs a novel order-invariant learning strategy to preserve the spatial information of GUI elements."
  - [section 3.1]: Detailed formulation of the element set representation and the order-invariant matching loss (Eq. 2-5). Ablation in Table 4 shows order-invariant learning improves forecasting metrics.
  - [corpus]: Neighbors like ViMo use generative image modeling (computationally expensive, includes irrelevant details), while text-based methods (e.g., MobileWorld) lose spatial info. MobileDreamer's sketch+order-invariant learning is a novel middle ground.
- **Break condition:** If the OCR-based extraction fails catastrophically on a screen (e.g., no recognizable text/labels in an icon-heavy layout), the input representation becomes invalid, and world model prediction collapses. The paper's "Limitations" section acknowledges this.

### Mechanism 2
- **Claim:** A recursive "tree-of-prediction" rollout imagination strategy allows a GUI agent to perform implicit multi-step lookahead planning by evaluating candidate action sequences, overcoming the short-sightedness of single-step greedy selection.
- **Mechanism:** For a candidate action, the world model predicts the next state. This predicted state (as a textual sketch) is fed back to the agent, which proposes *new* candidate actions for that hypothetical state. This recurses to a specified depth, building a branching tree of predicted trajectories. The agent then selects the root action whose predicted trajectory best aligns with the task goal.
- **Core assumption:** The world model's short-horizon predictions are accurate enough that their recursive use provides a useful, approximately correct signal for evaluating long-term action consequences.
- **Evidence anchors:**
  - [abstract]: "Rollout imagination strategy for GUI agent optimizes the action-selection process by leveraging the prediction capability of world model."
  - [section 3.2]: Describes the recursive process and the prompt templates (Table 6) used to get follow-up actions from a predicted state. Ablation in Table 3 shows adding tree-of-prediction (✓✓✓) gives the best SR (65.78%).
  - [section 4.3]: Table 5 shows depth=2 and M=3 provide the best trade-off; deeper/more branches add noise, confirming the mechanism's sensitivity to prediction quality.
- **Break condition:** If the world model's per-step error accumulates or diverges quickly (especially beyond depth=2 as per Table 5), the imagined trajectories become misleading, guiding the agent into incorrect long-term plans. The diminishing returns in Table 5 are evidence of this break condition in practice.

### Mechanism 3
- **Claim:** The integration of a robust, efficient textual sketch world model with a recursive rollout imagination creates a synergistic framework where high-fidelity, structured predictions enable effective multi-step evaluation, leading to superior performance on long-horizon mobile GUI tasks.
- **Mechanism:** The order-invariant world model (Mechanism 1) provides reliable, noise-robust state forecasts. The rollout strategy (Mechanism 2) uses these forecasts to construct and evaluate multiple short futures. The agent's final action selection is thus informed by a comparison of anticipated multi-step outcomes, not just immediate next-state utility.
- **Core assumption:** The benefits of multi-step evaluation (better long-horizon decisions) outweigh the computational cost and potential error propagation from recursive world model calls.
- **Evidence anchors:**
  - [abstract]: Overall claim that MobileDreamer "addresses the limitation of reactive mobile GUI agents" via a "world-model-based lookahead framework."
  - [section 4.2]: Table 2 shows consistent gains (e.g., +5.25% for Claude-Sonnet-4.5) over reactive baselines and prior world-model methods (ViMo, MobileWorld).
  - [section 4.3]: The full ablation (Table 3) demonstrates that each component (Sketch, Match, Tree) contributes incrementally to the final performance, proving their combined necessity.
  - [corpus]: Common neighbor theme is improving GUI agents (V-Droid, ReInAgent, UI-TARS). MobileDreamer's unique differentiator is the explicit world-model-based lookahead, which these neighbors lack.
- **Break condition:** For tasks where the optimal path requires a non-obvious single action with no immediately beneficial intermediate state (i.e., a "strategic" move that looks bad initially), even a perfect 2-step lookahead might not suffice if the world model's planning horizon is too short. The task success rate plateau in Table 5 (depth 3 vs. 2) suggests such limits.

## Foundational Learning

- **Concept: World Models (Predictive Dynamics)**
  - *Why needed here:* The entire framework hinges on learning a model `p(s_{t+1} | s_t, a_t)`. Without understanding this transition dynamics, the "lookahead" is impossible.
  - *Quick check question:* What is the key difference between training a world model via next-state prediction vs. training a policy via reward maximization?

- **Concept: Structured Representations for GUI States**
  - *Why needed here:* Moving from raw pixels to a set of annotated UI elements is the core innovation. It compresses state and focuses on task-relevant affordances.
  - *Quick check question:* Why might a bounding box (position) be a more critical feature for a GUI world model than for a world model in a robotic navigation domain?

- **Concept: Order-Invariant Set Matching (Optimal Transport)**
  - *Why needed here:* The state is a set, but the output is a sequence. Standard SFT penalizes reordering. This loss matches elements by content/spatial similarity, not sequence position.
  - *Quick check question:* In the matching loss `C(ˆe_k, e_n)`, what would happen if the `λ_text` term were set to zero? What if `λ_bbox` were set to zero?

## Architecture Onboarding

- **Component map:**
  1. **Input Processor:** PaddleOCR-VL extracts `(label, text, bbox)` from current screenshot `s_t`.
  2. **Textual Sketch World Model (TSWM):** A fine-tuned LLM (Qwen3-8B) that, given `s_t` (as text) and action `a_t`, predicts the next state sketch `ŝ_{t+1}`. Uses order-invariant loss.
  3. **Rollout Engine:** Recursive controller:
     - Takes current real state `s_t`, task goal, and candidate actions `A_t` from the Agent.
     - For each `a_t^{(m)}`, calls TSWM to get `ŝ_{t+1}^{(m)}`.
     - If depth > 1, feeds `(ŝ_{t+1}^{(m)}, goal)` to the Agent to get new candidate actions `A_{t+1}^{(m)}`, and recurses.
     - Compiles all `(a_t^{(m)}, predicted_trajectory)` into a tree summary.
  4. **GUI Agent (Planner/Actor):** An LLM (e.g., Claude). At rollout step 0, it receives `(real s_t, tree_summary)` and selects the best root action `a_t`. At rollout steps >0 (inside tree), it receives a *predicted* state sketch and generates candidate follow-up actions.

- **Critical path:** Screenshot -> OCR -> Textual Sketch -> TSWM prediction -> (if depth>1) Agent proposes follow-ups on *prediction* -> Repeat -> Summary -> Agent selects best initial action.

- **Design tradeoffs:**
  - *Sketch Fidelity vs. Efficiency:* Sketches are lightweight but lose visual details (icons, colors). This is a trade-off for speed and robustness to irrelevant pixels.
  - *Tree Depth (d) vs. Noise:* Deeper trees evaluate longer-term outcomes but amplify world model error (Table 5). d=2 is optimal.
  - *Branching Factor (M) vs. Computation:* More candidates explore more paths but increase TSWM calls (cost) and can include irrelevant actions.

- **Failure signatures:**
  - **TSWM:** High matching loss `L_match` during training, low mIoU/F1 on test set (Table 1). Indicates poor element transition learning.
  - **Rollout:** Tree collapse where all predicted trajectories are identical/chaotic. Agent defaults to greedy selection (effectively ignoring the tree).
  - **Overall:** Success rate not improving over reactive baseline, or degrading with increased depth (Table 5, depth=3).

- **First 3 experiments:**
  1. **Unit Test TSWM Forecasting:** On a held-out set of `(s_t, a_t, s_{t+1})` pairs, compute mIoU and F1-score (as in Table 1). Verify >0.85 mIoU and >0.76 F1.
  2. **Sanity Check Tree Construction:** For a simple, deterministic task (e.g., "open settings"), run rollout with `d=2, M=2`. Manually inspect the tree summary. Do the predicted states show logical progression (e.g., clicking "Settings" leads to a sketch with "Wi-Fi", "Apps")?
  3. **Baseline Comparison:** Run the task suite with `(Agent only)` vs. `(Agent + MobileDreamer)`. Expect ~5% absolute SR gain on average (per Table 2). If gain is near zero, inspect TSWM quality and tree summary prompts for misalignment.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How can MobileDreamer's textual sketch extraction be made more robust to visual noise, uncommon fonts, and icon-dominated layouts where OCR and UI parsing fail?
- **Basis in paper:** [explicit] The Limitations section (Page 8) states: "Prediction quality may be less stable on screens with heavy visual noise, uncommon fonts, or icon-dominant layouts where reliable text cues are limited."
- **Why unresolved:** The current approach relies entirely on OCR and UI element parsing, which may degrade or fail in such scenarios, limiting the framework's applicability to diverse real-world apps with non-standard visual designs.
- **What evidence would resolve it:** Evaluate MobileDreamer on a benchmark dataset with synthetically added noise or naturally icon-heavy screens (e.g., gaming apps), measure performance drops, and test enhancements like incorporating low-level visual features or robust parsing backbones.

### Open Question 2
- **Question:** Does the set-based textual sketch representation discard sequential or hierarchical layout information that could be crucial for certain GUI navigation tasks?
- **Basis in paper:** [inferred] The paper represents GUI states as unordered sets of elements (E(s_t) = {e_n}), preserving only label, text, and position. While spatial layout is captured, implicit ordering or grouping (e.g., form fields, list items) is not explicitly modeled, though the authors do not discuss potential losses.
- **Why unresolved:** If tasks require understanding of reading order, tab sequences, or grouped controls, the set representation may lose necessary cues, leading to suboptimal planning or inaccurate predictions.
- **What evidence would resolve it:** Design controlled experiments comparing the current set representation against ordered or hierarchical representations on tasks with known sequential dependencies, measuring impacts on prediction accuracy and task success rates.

### Open Question 3
- **Question:** How does MobileDreamer's performance scale with prediction tree depth and branching factor for longer-horizon tasks beyond those in Android World?
- **Basis in paper:** [inferred] Main experiments use tree depth d=2 and branching M=3, with ablations (Table 5) showing diminishing returns beyond these values. However, Android World tasks may not be sufficiently long to test deeper trees, and the paper does not explore depth >3 or varying M on complex, multi-step workflows.
- **Why unresolved:** For truly long-horizon tasks (e.g., multi-app workflows), deeper trees might capture longer dependencies but could introduce noise and computational overhead. Optimal parameters likely depend on task complexity and remain uncharacterized.
- **What evidence would resolve it:** Conduct experiments on synthetic or benchmark tasks with varying horizon lengths (e.g., 5, 10, 20 steps), systematically vary depth and M, and analyze success rates, prediction stability, and latency to identify scaling trends and breakpoints.

### Open Question 4
- **Question:** Is MobileDreamer's world model robust to distribution shifts caused by novel apps, UI designs, or action types not encountered during training?
- **Basis in paper:** [inferred] The world model is trained on trajectories from Android Control and manually annotated data covering specific apps. Testing on Android World involves 20 apps, but the paper does not evaluate generalization to unseen apps or UI paradigms, nor discuss potential overfitting.
- **Why unresolved:** Real-world deployment may encounter new apps with unconventional layouts, components, or actions. Lack of robustness to such distribution shifts could severely limit practical utility.
- **What evidence would resolve it:** Perform cross-app generalization tests by holding out entire app categories during training, then evaluating on those apps. Measure performance degradation and investigate techniques like domain-adversarial training or data augmentation to improve robustness.

### Open Question 5
- **Question:** How sensitive is the overall framework to the quality of candidate actions proposed by the GUI agent in the initial step?
- **Basis in paper:** [inferred] The rollout imagination strategy relies on candidate actions generated by the GUI agent (At = {a_t^(1), ..., a_t^(M)}). The paper assumes these are reasonable but does not analyze how their quality affects the final action selection, especially when proposals are suboptimal or incomplete.
- **Why unresolved:** If the agent's initial proposals are poor, the tree-of-prediction may not provide meaningful improvements, as the planning horizon is built from these seeds. The framework's benefit might be contingent on candidate quality.
- **What evidence would resolve it:** Correlate human-annotated or automatic metrics of candidate relevance with final success rates. Artificially degrade candidate sets (e.g., random actions, irrelevant actions) and measure the drop in performance compared to a reactive baseline, assessing the framework's tolerance to poor proposals.

## Limitations

- OCR extraction failures on icon-heavy or low-text screens may invalidate the textual sketch input.
- Error accumulation limits effective planning horizon; depth >2 degrades performance.
- Reproduction gaps (e.g., exact OCR settings, loss hyperparameters) hinder faithful replication.

## Confidence

- **Forecasting metrics (mIoU 0.8564, F1 0.7608)**: High confidence—directly reported and validated on test set.
- **Sketch + order‑invariant design**: High confidence—ablation (Table 4) shows clear benefit.
- **Tree‑based rollout**: Medium‑High confidence—improves SR at d = 2 but plateaus/deteriorates at d = 3, indicating sensitivity to prediction quality.
- **Overall SR gain (+5.25 %)**: High confidence—consistent improvements across strong baselines and prior world‑model methods (Table 2, 3).
