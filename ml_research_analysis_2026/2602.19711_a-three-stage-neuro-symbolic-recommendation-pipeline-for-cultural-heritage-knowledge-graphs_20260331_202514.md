# A Three-stage Neuro-symbolic Recommendation Pipeline for Cultural Heritage Knowledge Graphs
## Quick Facts
*   **arXiv ID:** 2602.19711
*   **Source URL:** https://arxiv.org/abs/2602.19711
*   **Reference count:** 36
*   **Primary result:** A neuro-symbolic pipeline using ComplEx embeddings, HNSW search, and SPARQL filtering provides explainable recommendations in sparse cultural heritage knowledge graphs, achieving an MRR of 0.1393 on the full JUHMP dataset (≈3.2M triples).

## Executive Summary
This paper tackles the problem of providing recommendations within cultural heritage knowledge graphs (KGs) that are characterized by sparse, heterogeneous metadata and a complete absence of user interaction history. The authors propose a three-stage neuro-symbolic pipeline to overcome these challenges. First, knowledge graph embeddings are generated using the ComplEx model, selected after hyperparameter tuning. Second, these embeddings are indexed for efficient approximate nearest-neighbor search using HNSW. Third, the initial candidate set is filtered and explained via SPARQL queries that enforce domain-specific constraints from the CIDOC-CRM ontology. The system is evaluated on the JUHMP graph (≈3.2M RDF triples). While quantitative link prediction metrics are modest (MRR 0.1393 on the full graph), expert evaluation confirms that the top-10 recommendations for historical persons represent valid close connections, demonstrating the approach's utility and explainability despite data sparsity.

## Method Summary
The proposed recommendation pipeline integrates neural embedding-based similarity search with symbolic, ontology-aware reasoning to ensure explainable outputs. The process begins by transforming the RDF-based JUHMP knowledge graph (using the CIDOC-CRM ontology) into a set of (head, relation, tail) triples. A ComplEx embedding model is trained on this data using PyKEEN, with hyperparameters (learning rate 0.01, dimension 200) selected via validation. The resulting entity embeddings are indexed with the HNSW algorithm for fast vector similarity search. For a query entity, the system retrieves a large set of nearest neighbors from the HNSW index. This raw candidate list is then filtered using a series of SPARQL queries that check for explicit, meaningful connections between the query and candidate entities—such as shared participation in an event or co-location—and restrict results to relevant types (e.g., `crm:E39_Actor`). The surviving candidates are ranked by their embedding similarity and returned with SPARQL-derived evidence explaining the connection.

## Key Results
*   The ComplEx model achieved a Mean Reciprocal Rank (MRR) of 0.1393 on the full JUHMP graph (≈3.2M triples), with Hits@10 up to 0.3288.
*   Expert evaluation of top-10 recommendations for nine historical persons confirmed the presence of "close connections" (rating ≥2), with a higher count of valid connections found in the denser full graph compared to the prototype.
*   The HNSW index with `efSearch=50` achieved a recall of 0.4600 at `efSearch=150` while maintaining a query latency of 6.2 seconds, demonstrating a feasible efficiency-quality trade-off.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** ComplEx embeddings can capture semantic relationships in sparse, heterogeneous cultural heritage knowledge graphs despite limited metadata.
*   **Mechanism:** ComplEx uses complex-valued embeddings to model relational patterns both symmetrically and anti-symmetrically. This allows it to represent the diverse relation types in CIDOC-CRM (e.g., `crm:P11i_participated_in`, `crm:P12i_was_present_at`) without requiring large amounts of training data, which is crucial for sparse historical records.
*   **Core assumption:** Entities that are historically or contextually related (e.g., two people in the same event) will have vector-space proximity in the ComplEx embedding space.
*   **Evidence anchors:**
    *   [abstract] "ComplEx model selected via hyperparameter tuning"
    *   [section 3.4] Table 1 shows ComplEx outperformed TransE, DistMult, and RotatE on the prototype graph (MRR 0.3515) with moderate resource use.
*   **Break condition:** If graph sparsity is extreme (entities sharing fewer than ~2-3 common relations), embedding quality degrades. Evidence: MRR dropped from 0.2207 (prototype) to 0.1393 (full graph) as scale and sparsity increased.

### Mechanism 2
*   **Claim:** HNSW approximate nearest-neighbor search efficiently retrieves candidate entities from high-dimensional embedding spaces with a controllable recall-latency trade-off.
*   **Mechanism:** HNSW builds a multi-layer graph index where each layer is a navigable small-world network. Search proceeds greedily from the top (sparse) layer to lower (dense) layers, achieving logarithmic query time complexity.
*   **Core assumption:** A recall of ~0.4–0.5 at `efSearch=50` provides a sufficiently large and high-quality candidate set for the subsequent precise SPARQL filter without causing excessive computational overhead.
*   **Evidence anchors:**
    *   [abstract] "HNSW approximate nearest-neighbor search"
    *   [section 3.5] Grid search selected `M=16, efConstruction=400, efSearch=50` based on a balance of recall (0.4600 at `efSearch=150`) and query latency (6.2s).
*   **Break condition:** If `efSearch` is too low (<20), recall drops below 0.2 and meaningful candidates are lost before filtering. If too high (>100), query latency increases linearly with diminishing returns in candidate quality.

### Mechanism 3
*   **Claim:** SPARQL-driven semantic filtering transforms approximate vector-space neighbors into explainable, contextually valid recommendations by enforcing domain-specific constraints from the CIDOC-CRM ontology.
*   **Mechanism:** For each candidate from HNSW, SPARQL queries verify the existence of at least one explicit, shared graph connection with the target entity—such as participation in the same event (`crm:P11i_participated_in`) or location (`crm:P12i_was_present_at`)—and that the candidate is of a relevant type (e.g., `crm:E39_Actor`). Only candidates satisfying these conditions are retained, and the shared property/object (`?prop`, `?value`) forms the explanation.
*   **Core assumption:** Historical relevance in cultural heritage is often signaled by explicit, structured links in the KG (shared events, dates, places) rather than by latent embedding similarities alone.
*   **Evidence anchors:**
    *   [abstract] "SPARQL-driven semantic filtering for explainable results"
    *   [section 3.6] Listing 1.1 provides a SPARQL query pattern for finding candidates sharing a property value with the target.
    *   [section 4.2] Expert evaluation validated the filtered results, confirming "close connections" for the top-10 lists.
*   **Break condition:** If the KG lacks structured links for a target entity (e.g., no triples using the filtered properties), the SPARQL stage yields zero results, causing a failure for that specific query regardless of embedding/HNSW quality.

## Foundational Learning
*   **Concept:** Knowledge Graph Embeddings (e.g., ComplEx)
    *   **Why needed here:** To encode heterogeneous RDF triples (entities/relations) into dense, comparable vectors for similarity search when user-item interaction history is unavailable.
    *   **Quick check question:** Why might ComplEx outperform TransE on a graph with many symmetric relations like `sameBirthPlace`?
*   **Concept:** Approximate Nearest Neighbor (ANN) Search (HNSW)
    *   **Why needed here:** To scale candidate retrieval to millions of entities without performing exhaustive pairwise comparisons in the high-dimensional embedding space, which would be computationally intractable.
    *   **Quick check question:** How does increasing `efConstruction` affect index build time versus the maximum achievable recall at query time?
*   **Concept:** Ontology-Aware Filtering (CIDOC-CRM, SPARQL)
    *   **Why needed here:** To ensure recommendations respect cultural heritage semantics (e.g., only suggesting actors, not objects) and to provide traceable, human-understandable justifications (e.g., "shared event X") rather than opaque vector distances.
    *   **Quick check question:** Why is it necessary to filter for `crm:E39_Actor` if the embedding space supposedly already encodes type information?

## Architecture Onboarding
*   **Component map:** RDF Graph (JUHMP) -> PyKEEN (ComplEx Trainer) -> Entity Embeddings -> HNSWLib (Index Builder) -> HNSW Index -> Query Engine (Load Target Embedding -> HNSW knn_query -> SPARQL Filter Loop -> Ranked Output)
*   **Critical path:** For a new query entity: (1) load its pre-trained embedding vector, (2) query the HNSW index (`knn_query`) for the top-K (e.g., 100) candidate entity IDs, (3) for each candidate, execute a batch of SPARQL queries against the original RDF graph to test for shared properties/values and type conformance, (4) retain only candidates with ≥1 matching connection, (5) sort the surviving candidates by their HNSW-similarity score and return them with the matching `(prop, value)` pairs as explanations.
*   **Design tradeoffs:**
    *   **Embedding dimension vs. quality/memory:** Higher dimensions (e.g., 200 vs. 100) can improve MRR but increase HNSW index size and memory footprint (~2× for 200 vs. 100 dims).
    *   **HNSW `efSearch` vs. latency:** A higher `efSearch` (e.g., 150 vs. 50) improves recall from the ANN index but increases query latency linearly. The chosen `efSearch=50` balances speed (6.2s) with sufficient recall for the subsequent precise filter.
    *   **SPARQL filter strictness vs. coverage:** Stricter filters (e.g., requiring shared exact event participation) increase precision but reduce recall, especially on sparse graph regions. Looser filters (e.g., "same place of birth") increase coverage but may yield less relevant or explainable results.
*   **Failure signatures:**
    *   **Embedding training failure:** Validation MRR remains below 0.1 or loss does not decrease, indicating issues with hyperparameters, data formatting, or model configuration.
    *   **HNSW recall failure:** Recall@10 on a validation query set drops below 0.3, suggesting index parameters (`M`, `efConstruction`) are too low for the dataset's dimensionality and size.
    *   **SPARQL filtering failure:** Over 80% of HNSW candidates are filtered out for most queries, pointing to either an overly strict filter definition or a fundamental lack of structured connections in the KG for the queried entities.
*   **First 3 experiments:**
    1.  **Baseline model comparison:** Train ComplEx, TransE, DistMult, and RotatE on the prototype graph for 10 epochs. Compare validation MRR, Hits@k, and training time to justify ComplEx selection.
    2.  **ComplEx hyperparameter tuning:** Perform a sweep over learning rate (0.001, 0.01) and embedding dimension (100, 200) on the prototype graph. Select the configuration that provides the best MRR/RAM trade-off.
    3.  **HNSW parameter optimization:** Conduct a grid search over `M` (e.g., 8, 16, 32) and `efConstruction` (e.g., 200, 400) on the full graph's embeddings. For each index, query a validation set with varying `efSearch` and measure Recall@k and mean query latency to select the final parameters (`M=16`, `efConstruction=400`, `efSearch=50`).

## Open Questions the Paper Calls Out
*   **Open Question 1:** How should the user interface for the pipeline integrate unambiguous identifiers (e.g., CAC IDs) and generate clear, user-friendly explanations from SPARQL evidence to address expert feedback on ambiguity?
*   **Open Question 2:** What specific modifications to the SPARQL-driven filtering stage will emerge from the planned expert workshop, and how will they quantitatively improve recommendation relevance for diverse historical scenarios?
*   **Open Question 3:** How does the performance (accuracy, explainability, latency) of the proposed three-stage pipeline compare to an LLM-assisted, RAG-style relational search over the same curated JUHMP subgraphs?
*   **Open Question 4:** To what extent does the pipeline's effectiveness degrade when applied to cultural heritage knowledge graphs using ontologies other than CIDOC-CRM or with fundamentally different metadata granularity (e.g., sparse event/place data)?
*   **Open Question 5:** How robust is the pipeline to extreme metadata sparsity at the individual entity level (e.g., persons with fewer than three linked triples), and can the semantic filtering stage be made more resilient without sacrificing precision?

## Limitations
*   **Reproduction details are missing:** The train/validation/test split methodology for the link prediction task is not described, preventing faithful replication of the reported MRR and Hits@k scores.
*   **Filter logic is underspecified:** The complete set of CIDOC-CRM properties and any value-based constraints (e.g., date proximity thresholds) used in the SPARQL filtering stage are not enumerated, relying on an external notebook.
*   **Evaluation is narrow:** Expert validation was conducted on only nine historical persons, limiting statistical significance. The URIs of these persons and the precise reference connections are not provided.
