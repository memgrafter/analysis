# Agentic Uncertainty Reveals Agentic Overconfidence

## Quick Facts
- **arXiv ID:** 2602.06948
- **Source URL:** https://arxiv.org/abs/2602.06948
- **Reference Count:** 10
- **Primary Result:** Frontier AI agents exhibit severe overconfidence on coding tasks, with post-execution success predictions (e.g., 77%) far exceeding true success rates (e.g., 22%), and adversarial framing significantly improves calibration.

## Executive Summary
This paper investigates whether AI agents can accurately estimate their own likelihood of success when performing coding tasks. Using three frontier models on 100 SWE-bench Pro problems, the study elicits probability estimates at three stages: before execution, after generating a patch, and after an adversarial review that prompts the agent to find faults. All models show severe overconfidence, predicting success rates 2–3 times higher than actual performance. Notably, the simplest pre-execution assessments, made with less information, demonstrate better discrimination between successful and failed attempts than standard post-execution assessments. Reframing the review phase as a bug-finding (adversarial) task yields the best calibration, reducing expected calibration error by up to 35%. The findings highlight a fundamental gap in agentic self-awareness and suggest that elicitation framing is a practical lever for improving reliability.

## Method Summary
The study deploys agentic coding systems built around large language models (Gemini, GPT-4, Claude) to solve instances from the SWE-bench Pro benchmark. For each task, the agent produces a code patch after repository traversal and editing. Probability estimates of success are elicited via zero-shot prompting at three points: (1) pre-execution, given only the issue description; (2) standard post-execution, after patch generation; and (3) adversarial post-execution, where the agent is prompted to critique its own patch for bugs. True success is determined by the benchmark’s test suite. Evaluations use discrimination (AUROC) and calibration (Expected Calibration Error, ECE) metrics to assess whether confidence estimates align with outcomes.

## Key Results
- All models exhibit extreme overconfidence; e.g., Gemini’s 22% true success rate contrasts with 77% mean predicted post-execution success.
- Pre-execution confidence provides better discrimination (higher AUROC) than standard post-execution for all models, despite having less task information.
- Adversarial framing (prompting to find bugs) improves calibration substantially, reducing ECE by up to 35% compared to standard post-execution review.
- Simple ensemble strategies (e.g., taking the minimum of pre- and adversarial post-estimates) further enhance calibration.

## Why This Works (Mechanism)
The paper does not identify a definitive underlying mechanism for the observed overconfidence. However, it demonstrates that the *framing* of the self-assessment query drastically changes outcomes. Standard post-execution prompts likely elicit a celebratory or completion-oriented response, inflating confidence. Adversarial framing activates a more critical, search-oriented mental set, leading to more conservative and better-calibrated estimates. Pre-execution assessments avoid both the optimism of completion and the potential complacency after effort, instead prompting a more abstract, prospective evaluation that happens to discriminate well. The results suggest overconfidence stems partly from poor calibration in the self-assessment process rather than an absolute inability to reason about uncertainty.

## Foundational Learning
- **Agentic Task Execution:** The paradigm where LLMs perform multi-step, tool-augmented workflows (e.g., code editing). *Why needed:* Defines the operational context where uncertainty is elicited. *Quick check:* Can the agent complete a given software issue autonomously?
- **Uncertainty Elicitation:** The process of obtaining confidence estimates from a model via prompting. *Why needed:* Core method for measuring agentic self-awareness. *Quick check:* Does the model output a well-formed probability when asked "How likely are you to succeed?"
- **Calibration (ECE):** A metric measuring alignment between confidence scores and empirical accuracy (lower is better). *Why needed:* Quantifies over/under-confidence. *Quick check:* Are 80% confidence predictions correct ~80% of the time?
- **Discrimination (AUROC):** A metric assessing the ability to separate successful from failed attempts (higher is better). *Why needed:* Evaluates if confidence scores carry signal about outcome. *Quick check:* Do higher confidence estimates correlate with higher success rates?
- **SWE-bench Pro:** A benchmark of real-world software engineering issues requiring repository traversal and patching. *Why needed:* Provides objective, test-based success labels for calibration studies. *Quick check:* Does a generated patch pass the repository’s unit tests?
- **Prompting-Based Self-Assessment:** Using natural language prompts to query a model’s own success probability without training a separate verifier. *Why needed:* The paper’s entire methodology relies on this low-cost approach. *Quick check:* Does rephrasing the prompt ("find bugs" vs "are you done") change the probability output?

## Architecture Onboarding
The system is a prompting-based pipeline with no persistent components or training.

**Component Map:**
Task Description -> Pre-Assessment Agent (prompted) -> Executor Agent (traversal + editing) -> Patch -> Standard Post-Assessment Agent (prompted) -> Adversarial Reviewer Agent (prompted) -> Metrics (AUROC, ECE)

**Critical Path:**
1. Receive GitHub issue and repository.
2. Pre-Assessment Agent outputs initial success probability.
3. Executor Agent interacts with repository (read, edit) to produce a patch.
4. Standard Post-Assessment Agent reviews the patch and outputs a probability.
5. Adversarial Reviewer Agent is prompted to critique the patch for bugs and outputs a probability.
6. True success determined by applying patch and running test suite.
7. Compare all probabilities against binary outcome to compute AUROC and ECE.

**Design Tradeoffs:**
- **Latency vs. Information:** Pre-execution is fast but uninformed; adversarial review is slower but yields better calibration.
- **Prompting Cost vs. Reliability:** More elaborate prompts (e.g., chain-of-thought for adversarial review) may improve estimates but increase token cost and risk of prompt hacking.
- **Generality vs. Optimization:** The zero-shot approach works across models and tasks but likely underperforms a custom-trained verifier on a specific domain.

**Failure Signatures:**
- **Systemic Overconfidence:** Mean predicted probabilities >> true success rates across all models and conditions.
- **Calibration Gap:** Standard post-execution probabilities show high ECE; confidence does not match accuracy.
- **Discrepancy Between Assessments:** Large disagreement between pre-execution and adversarial post-execution estimates for the same task, indicating instability in self-assessment.

**First Three Experiments:**
1. **Reproduce Core Findings:** Run the exact protocol (three assessment stages, same 100 SWE-bench Pro tasks) on at least two other frontier models (e.g., Llama-3.1-405B, Mistral-Large) to confirm overconfidence and framing effects.
2. **Framing Ablation:** Systematically vary the adversarial prompt (e.g., "List all possible bugs", "Rate severity 1-5", "What would a critic say?") to identify which linguistic features most improve calibration.
3. **Pre-Execution Feature Analysis:** Correlate pre-execution confidence with static features of the issue (description length, number of files changed in reference solution, repository size) to understand what information the model uses for its surprisingly good discrimination.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Does agentic overconfidence persist in tasks with subjective or ambiguous success criteria?
- **Basis in paper:** [explicit] "Beyond software engineering... Understanding how overconfidence varies across this spectrum... would inform domain-specific deployment guidelines."
- **Why unresolved:** The study exclusively uses SWE-bench Pro, which has objective, test-based success criteria; domains like web navigation, scientific workflows, or creative tasks lack clear ground truth and may exhibit different uncertainty behaviors.
- **What evidence would resolve it:** Replicate the uncertainty elicitation protocol across diverse task types (e.g., web navigation with partial observability, scientific hypothesis generation without absolute answers, creative writing judged by humans), and compare calibration/discrimination metrics using domain-appropriate success definitions.

### Open Question 2
- **Question:** Can explicitly trained verifiers significantly improve agentic uncertainty estimation compared to prompting-based approaches?
- **Basis in paper:** [explicit] "Trained verifiers for self-assessment... The key challenge is obtaining training signal: while SWE-bench provides binary success labels, scaling to diverse agentic tasks requires either expensive human annotation or proxy metrics..."
- **Why unresolved:** All uncertainty agents in this work use zero-shot prompting; training on execution traces (e.g., process reward models) might capture failure patterns more reliably, but scalable training data collection remains unsolved.
- **What evidence would resolve it:** Train verifiers on large datasets of agent trajectories with success labels (from SWE-bench or similar), then compare their AUROC and ECE against prompted agents on held-out tasks; also explore semi-supervised methods or synthetic failure injection to reduce annotation needs.

### Open Question 3
- **Question:** What is the optimal hybrid strategy combining pre-execution and adversarial post-execution assessments for efficient and safe agent deployment?
- **Basis in paper:** [explicit] "Our results suggest complementary strengths: pre-execution achieves better discrimination while adversarial post-execution achieves better calibration... A practical deployment strategy might combine both... Investigating the optimal combination, including when to escalate to human review based on estimate disagreement, remains an open question."
- **Why unresolved:** The paper shows simple ensembles (e.g., conservative min) improve calibration but do not optimize for operational trade-offs like cost, latency, or human review burden; the best routing policy is unknown.
- **What evidence would resolve it:** Conduct simulation studies where tasks are first assessed pre-execution (to filter out likely failures) and then adversarially post-reviewed (for borderline cases), varying thresholds and cost parameters; measure outcomes like total success rate, human hours saved, and catastrophic failure incidence.

## Limitations
- **Domain Specificity:** Findings are confined to the SWE-bench Pro coding benchmark; generalizability to other agentic domains (navigation, reasoning, creative tasks) is unknown.
- **Model Scope:** Evaluated only on three frontier models; behavior in open-weight or smaller models may differ.
- **Lack of Mechanistic Insight:** The paper demonstrates *that* framing affects calibration but does not explain *why* (e.g., training objective misalignment, lack of introspection capabilities in LLMs).

## Confidence
- **Overconfidence Finding:** High. Consistent, large-effect results across multiple models and elicitation conditions with robust metrics.
- **Pre-Execution Discrimination Advantage:** High. Clear AUROC superiority over standard post-execution for all models, despite less information.
- **Adversarial Framing Calibration Improvement:** Medium. Strong ECE reductions reported, but limited to three models and one benchmark; may not generalize broadly.
- **Generalizability of Results:** Low. No cross-benchmark or cross-domain evidence provided.

## Next Checks
1. **Cross-Benchmark Replication:** Re-run the exact experimental protocol on at least two other agentic coding benchmarks (e.g., SWE-bench Lite, AgentBench) to test generality of overconfidence and framing effects.
2. **Error Pattern Analysis:** Categorize failure modes (e.g., logic errors, API misuse, test misalignment) and analyze whether overconfidence correlates with specific error types or task complexities (e.g., number of files modified).
3. **Mechanistic Probing:** Use representational analysis (e.g., linear probes on hidden states, activation patching) during pre- and post-execution phases to identify internal correlates of accurate versus overconfident predictions.
