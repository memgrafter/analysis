# KohakuRAG: A simple RAG framework with hierarchical document indexing

## Quick Facts
- **arXiv ID**: 2603.07612
- **Source URL**: https://arxiv.org/abs/2603.07612
- **Reference count**: 40
- **Primary result**: First place on WattBot 2025 Challenge (final score 0.861), the only team to maintain top rank on both public and private leaderboards.

## Executive Summary
KohakuRAG is a retrieval-augmented generation framework designed to overcome common RAG limitations—structure loss from flat chunking, vocabulary mismatch in queries, and answer instability. It introduces a four-level hierarchical document index (document→section→paragraph→sentence) with bottom-up embedding aggregation, an LLM-powered multi-query planner with cross-query reranking, and ensemble inference with abstention-aware voting. The system achieved state-of-the-art performance on the WattBot 2025 Challenge, a technical QA benchmark requiring precise numeric answers and exact citations. Ablations confirm the importance of prompt ordering (+80% relative), retry mechanisms (+69%), and ensemble voting (+1.2 pp). Hierarchical dense retrieval performs nearly as well as a BM25 hybrid, suggesting the structure-aware approach is highly effective.

## Method Summary
KohakuRAG operates in three stages. First, documents are parsed into a four-level tree (document, section, paragraph, sentence). Sentence embeddings are computed directly, and parent node embeddings are length-weighted averages of their children’s vectors, preserving compositional semantics and structural boundaries. The tree and embeddings are stored in a sqlite-vec vector database. Second, for a user question, an LLM query planner generates multiple diverse queries (rephrasings, expansions). Each query retrieves top-k nodes via dense similarity; results are aggregated by retrieval frequency and cumulative similarity, then reranked and deduplicated hierarchically. Retrieved snippets are expanded to include parent nodes for context. Third, the generator LLM produces answers in JSON format with an `is_blank` flag. An ensemble of independent runs (with temperature >0) is aggregated: blanks are filtered if non-blank answers exist, and majority voting on normalized values selects the final answer. A retry mechanism re-retrieves with increased k on abstention.

## Key Results
- First place on WattBot 2025 Challenge (final score 0.861), only team top on both public and private leaderboards.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Hierarchical tree indexing with bottom‑up embedding aggregation preserves document structure and enables precise citation tracking.
- **Mechanism**: Documents are parsed into a four‑level tree (document → section → paragraph → sentence). Sentence embeddings are computed directly via a text encoder; internal node embeddings are length‑weighted averages of their children’s embeddings. This bottom‑up propagation captures compositional semantics while maintaining structural boundaries for clean citation.
- **Core assumption**: Natural document hierarchy encodes meaningful semantic units; preserving it during indexing aids retrieval precision and attribution.
- **Evidence anchors**: [abstract]: “preserves document structure through a four‑level tree representation (document→section→paragraph→sentence) with bottom‑up embedding aggregation”; [section 4.1]: Details parsing heuristics, Algorithm 2 for embedding propagation, and storage in sqlite‑vec; [section 7]: Break condition—rule‑based parsing fails on irregular layouts.
- **Break condition**: Rule‑based parsing fails on irregular layouts (multi‑column, non‑standard sections), producing incorrect hierarchy and degraded retrieval.

### Mechanism 2
- **Claim**: LLM‑powered query planning with cross‑query reranking bridges vocabulary mismatch between questions and source documents.
- **Mechanism**: The query planner (LLM) generates *n* diverse queries (rephrasings, expansions, decompositions). Each retrieves top‑*k* nodes via dense similarity. Results are aggregated: nodes are scored by retrieval frequency (how many queries retrieved them) and cumulative similarity; combined ranking prioritizes consensus. This leverages multiple query formulations to surface passages missed by any single query.
- **Core assumption**: Single queries often use terminology different from documents; multiple complementary queries increase coverage.
- **Evidence anchors**: [abstract]: “LLM‑powered query planner with cross‑query reranking”; [section 4.2]: Describes planner prompt, reranking strategies (Frequency, Score, Combined), and deduplication; [section 5.2]: Ablation shows increasing planner queries from 2 to 6 improves performance substantially (e.g., +40% relative at *k*=4); Combined reranking is most consistent; Frequency‑only underperforms drastically.
- **Break condition**: Planner generates off‑topic queries or fails to cover the information need, reducing retrieval quality.

### Mechanism 3
- **Claim**: Ensemble inference with abstention‑aware voting stabilizes answers and reduces unnecessary abstentions.
- **Mechanism**: The generator LLM runs *m* independent times (temperature > 0). If any run outputs “blank” (insufficient evidence) and `ignore_blank` is true, those are filtered out provided at least one non‑blank exists. Majority voting on normalized answer values selects the final answer; reference aggregation (e.g., AnswerPriority) aligns citations with the winning answer.
- **Core assumption**: LLM outputs are stochastic; aggregating multiple runs yields more robust predictions. Filtering blanks prevents conservative abstentions from dominating when evidence exists.
- **Evidence anchors**: [abstract]: “ensemble inference with abstention‑aware voting”; [section 4.4]: Details voting strategies and blank handling; [section 5.4]: Ensemble scales logarithmically, plateauing at *n*=9–11; `ignore_blank` improves by ~+1.2 pp at *n*=9; AnswerPriority voting ranks best; [section 5.5]: Error analysis: unnecessary abstention was 26.8% of failures; retry mechanism (re‑retrieving on blank) gave +69% relative improvement at *k*=4.
- **Break condition**: Ensemble size too small leaves variance high; `ignore_blank` may incorrectly filter valid answers if normalization fails.

## Architecture Onboarding
- **Component map**:  
  Document Parser -> Embedding Engine -> Vector Store (sqlite-vec) -> Query Planner -> Retriever -> Cross-Query Reranker -> Context Expander -> Generator LLM -> Retry Controller -> Ensemble Aggregator

- **Critical path**:  
  1. **Indexing**: parse documents → build tree → compute embeddings → store in vector DB.  
  2. **Query**: user question → query planner → multiple queries → retrieve per query → rerank → expand context → generate *m* times (with possible retry) → ensemble vote → output.

- **Design tradeoffs**:  
  - Hierarchical vs. flat chunking: structure improves citation precision but requires complex parsing; may fail on messy layouts.  
  - Number of planner queries: more queries improve coverage but increase retrieval latency linearly; paper found 4–6 optimal.  
  - Ensemble size: larger ensembles reduce variance but linearly increase cost; plateau at *n*=9–11. `ignore_blank` adds ~+1 pp.  
  - Prompt ordering: context‑before‑question yields +80% relative improvement due to attention sink and lost‑in‑the‑middle effects.  
  - BM25 hybrid: adds only +3.1 pp; may be omitted if hierarchical dense retrieval suffices.

- **Failure signatures**:  
  - High abstention rate: may indicate insufficient retrieval depth or poor query planning; check retry usage.  
  - Reference mismatch: LLM cites wrong doc despite correct answer; consider reference‑constrained decoding.  
  - Degraded performance on irregular documents: parsing errors propagate; visualize tree structure.  
  - Model‑dependent performance: smaller LLMs (e.g., GPT‑5‑nano) show much higher error rates; ensure adequate capacity.  
  - Context window overflow: retrieved snippets exceed limit; monitor length and adjust `top‑k_final`.

- **First 3 experiments**:  
  1. Verify hierarchical indexing: Retrieve a known sentence; check that its parent paragraph and section are correctly linked; measure recall at different granularities.  
  2. Test query planner: For a sample question, compare planner outputs with manual diverse queries; measure retrieval coverage (unique relevant docs) with varying *n*.  
  3. Measure ensemble effect: Run same question multiple times with temperature > 0; compute answer variance. Compare single‑run vs. ensemble (*n*=5, 9) on a small dev set to confirm stability gains.

## Open Questions the Paper Calls Out
- Can learned document parsers (LayoutLM/DocFormer) replace rule-based heuristics to improve robustness across diverse document layouts?
- How can citation mismatch errors (23.6% of failures) be reduced where LLMs cite secondary sources over primary documents?
- Can ensemble robustness be maintained with sub-linear computational cost via confidence-based selective ensembling or knowledge distillation?
- Does deeper multimodal integration (cross-modal attention, structured table/chart extraction) significantly improve performance beyond caption-based retrieval?

## Limitations
- Parsing heuristics: exact thresholds for section/paragraph segmentation (font size, spacing) are unreported, limiting reproduction on irregular layouts.
- Query planner details: the LLM used for query expansion, its prompt phrasing, and temperature are unspecified, hindering exact replication of the multi-query strategy.
- Vector index parameters: `sqlite-vec` IVF-PQ settings (e.g., `nlist`, `m`) are not provided, affecting retrieval recall/latency trade-offs.

## Confidence
- **Hierarchical indexing**: Medium – Mechanism clearly described, but break conditions depend on undocumented parsing thresholds.
- **LLM query planning**: Medium – Ablations support efficacy, but the planner’s design space (model, prompts) remains opaque.
- **Ensemble voting**: High – Strong ablations (+1.2 pp with `ignore_blank`) and error analysis (26.8% unnecessary abstention) robustly support this component.
