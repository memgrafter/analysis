# Quantifying the Accuracy and Cost Impact of Design Decisions in Budget-Constrained Agentic LLM Search

## Quick Facts
- arXiv ID: 2603.08877
- Source URL: https://arxiv.org/abs/2603.08877
- Reference count: 0
- Primary result: Budget-aware agentic search (BCAS) shows diminishing returns after ~3 searches, hybrid+re-ranking yields largest gains, and token budget impact varies by dataset.

## Executive Summary
This paper introduces Budget-Constrained Agentic Search (BCAS), a framework for quantifying how design decisions in agentic retrieval-augmented generation affect accuracy under explicit search and token budgets. The authors evaluate six LLMs across three multi-hop QA datasets, systematically varying search depth, retrieval strategies (BM25, hybrid, re-ranking), and completion token limits. Key findings include: accuracy improves with up to approximately three searches before diminishing returns set in; hybrid search combined with re-ranking yields the largest accuracy gains; and the benefit of a larger token budget is most pronounced for synthesis-intensive tasks like HotpotQA, while being minimal for factoid or retrieval-constrained datasets. The study provides an ablation analysis revealing a component hierarchy (re-ranking > hybrid search > planning/reflection) and highlights the importance of aligning budget allocation with dataset-specific bottlenecks.

## Method Summary
The study employs the BCAS harness, which enforces explicit `max_searches` and `max_total_tokens` constraints within a ReAct-style agent loop. The agent uses a fixed prompt template that includes remaining budget values at each turn. Retrieval is configurable: base retriever (BM25 or hybrid BM25+vector using BGE-M3), optional re-ranker (bge-reranker-v2-m3 over top 100 chunks returning top 5), and optional reasoning scaffolds (pre-planning, reflection). Experiments are run on six LLMs (including API-based and open-weight models) and three QA benchmarks (TriviaQA, HotpotQA, 2WikiMultihopQA). Accuracy is measured via binary correctness judged by GPT-4o-mini, with token usage and search counts logged. The primary evaluation consists of an ablation on HotpotQA to isolate component contributions and scaling studies varying search depth and token budgets across datasets.

## Key Results
- Accuracy improves with additional searches up to a small cap (~3), then diminishing returns.
- Hybrid search with re-ranking (HS+RR) provides the largest average accuracy gains (+9.29 points on HotpotQA).
- The effect of a larger completion token budget is dataset-dependent: significant for synthesis-heavy tasks (HotpotQA) but minimal for factoid (TriviaQA) or retrieval-constrained (2WikiMultihopQA).

## Why This Works (Mechanism)

**Mechanism 1: Diminishing Returns from Iterative Search**  
Accuracy improves with additional iterative searches up to a small cap (typically ~3), after which gains plateau. Each search retrieves new evidence chunks, progressively building a factual foundation; the BCAS loop surfaces remaining budget, encouraging deliberate query sequencing. Gains plateau when searches become redundant or the retrieved corpus is exhausted. Evidence: abstract and Section 4.1/Figure 2 show consistent lifts from 1→2→3 searches across models/datasets, flattening thereafter; corroborated by related work on over-search.

**Mechanism 2: Hybrid Search + Re-ranking Efficacy**  
Hybrid lexical+dense retrieval followed by lightweight re-ranking (HS+RR) produces the largest average accuracy gains. Hybrid search (BM25 + vector) broadens recall by capturing both keyword matches and semantic similarity. The subsequent re-ranking (cross-encoder) rescoring a larger candidate pool (100 chunks) improves precision, returning only the top 5 most relevant chunks to the agent context, balancing exploration and exploitation within a fixed context window. Evidence: Section 3.5 describes the pipeline; Table 2 shows HS+RR with +9.29 points over BM25 baseline on HotpotQA; EcoRank study supports re-ranking under cost constraints.

**Mechanism 3: Dataset-Dependent Token Budget Scaling**  
The impact of a larger completion token budget is task-dependent: it provides the most significant gains on synthesis-heavy multi-hop QA (HotpotQA) and minimal gains on factoid (TriviaQA) or retrieval-constrained tasks (2WikiMultihopQA). A larger token budget allows the LLM's generation to include more intermediate reasoning, explicit citation of multiple evidence snippets, and complex synthesis. For datasets where the bottleneck is retrieval (2WikiMultihopQA), extra tokens cannot compensate for missing evidence; for factoid questions (TriviaQA), answers are short and synthesis minimal; for HotpotQA, combining multiple facts requires explicit reasoning space. Evidence: Section 5.1 explains dataset differences; Figure 2 shows HotpotQA accuracy lifts from 4K to 16K tokens, while TriviaQA and 2WikiMultihopQA show much flatter curves.

## Foundational Learning

**Budget-Aware Agent Loop**  
Why needed: BCAS's core innovation is making search and token budgets explicit state variables in the LLM's reasoning loop, transforming the agent from one that "uses tools until done" to one that "manages a fixed allowance."  
Quick check: How does surfacing `remaining_searches` and `remaining_tokens` as part of the prompt at each turn change the agent's decision-making policy compared to a standard ReAct loop without budget signals?

**Retrieval Component Hierarchy**  
Why needed: The paper identifies a clear hierarchy of component effectiveness (Re-ranking > Hybrid Search > Planning/Reflection for most models). Understanding this hierarchy is key to cost-effective configuration.  
Quick check: Given a fixed budget, should you first improve the retriever (e.g., add re-ranking) or add a reasoning component (e.g., pre-planning)? What does the paper's ablation data suggest?

**Dataset-Specific Scaling Laws**  
Why needed: The accuracy-budget trade-off is not universal; it is conditioned on the dataset's primary bottleneck (retrieval vs. synthesis). Deployment decisions must be grounded in the target task's characteristics.  
Quick check: For a new multi-hop QA dataset, how would you diagnose whether to invest budget in more searches or in a larger completion token limit?

## Architecture Onboarding

**Component map**:  
LLM Agent <-> Budget Tracker  
LLM Agent -> IR Pipeline (search query) -> LLM Agent (retrieved chunks)  
Optional Reasoners (Pre-planning, Reflection) -> LLM Agent (prompt injection)  
Judge & Ledger (post-execution evaluation)

**Critical path**:  
1. Initialize `remaining_searches`, `cumulative_tokens=0`.  
2. Agent turn: generate `thought` and select `action`; if `search`, Budget Tracker decrements `remaining_searches` and blocks if zero.  
3. IR Pipeline executes search based on configuration, returns top 5 chunks.  
4. Update `cumulative_tokens`; if `>= max_total_tokens`, terminate loop.  
5. Repeat until `ready_to_answer` or budget exhaustion; grade answer with Judge.

**Design tradeoffs**:  
- **Search Depth vs. Token Budget**: More searches consume tokens in context and calls; a tight token budget can force succinctness, potentially enabling more searches within the same token cap (paradox noted in Section 5.1).  
- **Retrieval Cost vs. Precision**: Hybrid+RR is computationally heavier (100 candidates × re-ranker) but yields largest accuracy gains; BM25 is cheaper but may have lower recall/precision.  
- **Scaffolding Overhead**: Pre-planning and reflection add tokens to system/intermediate prompts, reducing budget for actual searches/answers; their benefit is model-dependent (smaller models gain more).

**Failure signatures**:  
- **Premature termination**: Agent calls `ready_to_answer` with high `remaining_searches` and low `cumulative_tokens`, indicating under-confidence or poor search policy.  
- **Redundant searches**: High `searches_used` but low accuracy; queries are paraphrases of previous ones, suggesting ineffective planning or poor retrieval diversity.  
- **Token starvation**: `cumulative_tokens` approaches `max_total_tokens` before answer generation, causing truncated answers or never reaching `ready_to_answer`.  
- **Re-ranking inversion**: HS+RR performs worse than HS alone, possibly due to mismatched re-ranker domain or already optimal top-5 from hybrid search.

**First 3 experiments**:  
1. **Baseline establishment**: Run BCAS with unlimited searches, 16K token budget, BM25 retriever, no planning/reflection on all 6 models × 3 datasets. Establish upper bounds and baseline convergence.  
2. **Component ablation (RQ2)**: On HotpotQA, systematically toggle: Pre-planning, Reflection, Hybrid Search, Hybrid+Re-ranking. Measure net accuracy shift from baseline to identify highest-leverage component.  
3. **Search scaling (RQ3)**: Fix token budget 16K, BM25, no planning/reflection. Vary `max_searches` in {1,2,3,unlimited}. Plot accuracy vs. search count to identify diminishing-returns cap. Repeat with `+Planning` and `+Plan+RF` to see if planning shifts the cap.

## Open Questions the Paper Calls Out
1. **What is the accuracy-cost benefit of multi-turn agentic search over single-pass retrieve-then-read under identical budgets?**  
   Basis: The study omits a non-agentic baseline (Section 7). Unresolved because without this baseline, incremental value of agency per unit cost is unknown. Evidence needed: implement single-pass retrieve-then-read with same retrieval backends and budget constraints, compare on all datasets.

2. **Does the ranking of component gains generalize beyond HotpotQA?**  
   Basis: Full component ablation reported only on HotpotQA (Section 7). Unresolved because dataset-specific characteristics may change relative effectiveness. Evidence needed: same ablation on TriviaQA and 2WikiMultihopQA, compare ordering.

3. **How do RL-trained open-web search agents compare to BCAS's policy-based agents in budget-constrained settings?**  
   Basis: No head-to-head results against RL-trained agents (Section 7). Unresolved because RL agents have different training paradigms and cost-accuracy profiles. Evidence needed: adapt RL agents to use BCAS's tools and budget enforcement, evaluate alongside BCAS with identical cost accounting.

## Limitations
- Prompt and document chunking parameters, as well as the exact test split, are repository-dependent but not fully specified, risking reproduction drift.
- The GPT-4o-mini correctness evaluator prompt is unspecified, which could affect accuracy labels.
- Token accounting details (e.g., inclusion of retrieval overhead) are ambiguous, potentially leading to budget adherence discrepancies.

## Confidence
- Diminishing returns from iterative search: High confidence.
- Hybrid search + re-ranking efficacy: Medium confidence.
- Dataset-dependent token budget scaling: Low confidence.
