# MOSAIC: A Unified Platform for Cross-Paradigm Comparison and Evaluation of Homogeneous and Heterogeneous Multi-Agent RL, LLM, VLM, and Human Decision-Makers

## Quick Facts
- **arXiv ID:** 2603.01260  
- **Source URL:** https://arxiv.org/abs/2603.01260  
- **Reference count:** 40  
- **Primary result:** Open-source platform enabling reproducible cross-paradigm multi-agent research via IPC-based worker protocol, operator abstraction, and deterministic evaluation across 26 environment families and 8 worker types.

## Executive Summary
MOSAIC bridges gaps in multi-agent research by allowing reinforcement learning (RL) policies, large language models (LLMs), vision‑language models (VLMs), and humans to interact in shared environments under reproducible conditions. Its three core contributions—an IPC‑based worker protocol that isolates third‑party frameworks, an operator abstraction that maps workers to agents through a minimal interface, and a deterministic evaluation framework with both manual GUI and scripted modes—enable systematic, fair comparisons. The platform supports 26 environment families and integrates eight worker types (e.g., CleanRL, XuanCe, RLlib, BALROG), facilitating studies such as adversarial RL vs. LLM matchups and cooperative teams mixing solo‑trained RL agents with LLM/VLM partners. Released under the MIT license with extensive documentation, CI tests, and telemetry, MOSAIC aims to standardize cross‑paradigm multi‑agent evaluation.

## Method Summary
The method centers on three pillars. First, the **IPC‑based worker protocol** wraps external frameworks (e.g., CleanRL, XuanCe, RLlib, BALROG) as subprocesses communicating via stdin/stdout JSON, eliminating the need for source modifications. Second, the **operator abstraction** provides a unified `OperatorController` interface (`select_action`/`select_actions`) that translates between the environment’s observations and each worker’s expected input format while normalizing actions. Third, **deterministic evaluation** is achieved through shared random seeds across the environment and all agents, with two execution modes: a lock‑step GUI for manual human interaction and a scripted mode for automated runs. RL agents are typically pre‑trained solo (N=1) and then frozen; LLM/VLM agents are queried on demand. Declarative `OperatorConfig` files (JSON/Python) specify agent‑to‑worker assignments. The platform includes wrappers for 26 environment families to maintain consistent observation and action spaces.

## Key Results
- Enables direct, reproducible interaction between RL, LLM, VLM, and human agents across 26 environment families.
- Integrates 8 worker types (including CleanRL, XuanCe, RLlib, BALROG, human, random) without requiring modifications to third‑party code.
- Facilitates systematic studies such as adversarial RL vs. LLM matchups and cooperative teams mixing solo‑trained RL policies with LLM/VLM agents.

## Why This Works (Mechanism)
The approach succeeds because it isolates each agent in its own subprocess via a simple IPC protocol, preventing interference and allowing any framework with a CLI to participate without source changes. The operator abstraction acts as a universal adapter, translating between the environment’s observations and each worker’s expected input format while normalizing actions. Deterministic lock‑step execution with shared seeds synchronizes all stochastic sources (environment, RL policy, LLM sampling), ensuring fair comparisons. Together, these mechanisms provide both flexibility (supporting diverse agents) and rigor (reproducibility), which are essential for cross‑paradigm evaluation.

## Foundational Learning
**Inter‑Process Communication (IPC) via JSON streams**: Needed to decouple agent implementations from the core platform, allowing any framework that can be launched as a subprocess and read/write JSON to participate without modifications.  
*Quick check*: Verify that a dummy worker can send/receive JSON messages to/from the platform using stdin/stdout.

**Operator abstraction pattern**: Provides a single interface (`select_action(s)`) that hides heterogeneity of different agent types (RL, LLM, human) and handles observation preprocessing and action postprocessing uniformly.  
*Quick check*: Implement a minimal operator wrapping a random policy; ensure it correctly maps environment observations to actions.

**Deterministic lock‑step execution**: Guarantees reproducibility across runs and paradigms by synchronizing all sources of randomness (environment, RL policy, LLM sampling) through a shared seed.  
*Quick check*: Run two episodes with the same seed and verify identical telemetry (rewards, actions) byte‑for‑byte.

**Subprocess isolation**: Prevents crashes or state leaks from one agent affecting others and allows different dependency versions per worker.  
*Quick check*: Force a worker to exit prematurely; confirm the platform detects the crash and shuts down gracefully.

**Declarative configuration**: Specifies agent assignments and environment settings in a data‑driven way, enabling easy experiment replication and sharing.  
*Quick check*: Write a minimal JSON config with two random workers; load and validate it programmatically.

**Telemetry collection**: Logs standardized metrics (per‑step rewards, actions) for all agents, enabling quantitative comparison across paradigms.  
*Quick check*: Run a short episode and verify that a JSONL log file is generated with entries for every step.

## Architecture Onboarding
**Component map**: `OperatorConfig → OperatorController → {WorkerIPCClient_i → Worker_subprocess_i}`; `OperatorController ↔ Environment`.  
**Critical path**: (1) Load config → instantiate operator; (2) Launch worker subprocesses & establish IPC; (3) Reset env → get observations; (4) Per step: send obs to workers, receive actions, step env, log telemetry; (5) On episode end, optionally reset; (6) On shutdown, terminate workers.  
**Design tradeoffs**:  
- *Isolation vs. Performance*: Subprocess IPC adds overhead but ensures safety and compatibility.  
- *Determinism vs. Flexibility*: Shared seeds enforce reproducibility but may restrict stochastic behaviors (e.g., LLM temperature must be fixed).  
- *Generality vs. Efficiency*: Operator abstraction adds a layer but supports any agent type; may limit framework‑specific optimizations.  
**Failure signatures**: Worker subprocess crash (logs show exit code), misaligned observation/action spaces (JSON parsing errors, shape mismatches), IPC deadlock (no messages), environment wrapper incompatibility (unexpected observation format).  
**First experiments**:  
1. Install MOSAIC and run a simple 1‑agent MiniGrid task with a random worker to verify basic functionality.  
2. Configure a 2‑agent heterogeneous matchup: one CleanRL‑trained PPO agent vs. one LLM agent (e.g., GPT‑4o) in a Soccer environment; observe interaction via GUI or script.  
3. Execute a deterministic reproducibility test: run the scripted evaluation of the same heterogeneous matchup twice with the same seed and compare telemetry logs for exact identity.
