# MobilityBench: A Benchmark for Evaluating Route-Planning Agents in Real-World Mobility Scenarios

## Quick Facts
- arXiv ID: 2602.22638  
- Source URL: https://arxiv.org/abs/2602.22638  
- Reference count: 38  
- Primary result: State-of-the-art LLM-based route-planning agents achieve up to 97.23% Delivery Rate and 69.09% Final Pass Rate on basic tasks, but struggle significantly on Preference-Constrained Route Planning.

## Executive Summary
MobilityBench introduces a reproducible benchmark for evaluating LLM-based route-planning agents in realistic mobility scenarios. It leverages 100,000 anonymized Amap queries across 350+ cities and a deterministic API-replay sandbox to eliminate environmental variance. The benchmark uses a multi-dimensional protocol to assess instruction understanding, planning, tool use, decision making, and efficiency. Results show high performance on basic tasks (up to 97.23% Delivery Rate, 69.09% Final Pass Rate) but a sharp drop on Preference-Constrained Route Planning, exposing a key weakness in handling personalized constraints. The open-source toolkit enables standardized comparisons; Plan-and-Execute allows open-source models to approach closed-source performance with lower token usage, while ReAct offers greater robustness at higher computational cost.

## Method Summary
The benchmark is built from 100,000 anonymized Amap user queries covering 11 task families, from simple point-to-point to preference-constrained routing. Each query is paired with a scenario-specific standard operating procedure (SOP) that defines the correct sequence of API calls and parameters. A deterministic sandbox replays cached API responses, ensuring identical observations across runs for the same agent actions. Agent systems use ReAct or Plan-and-Execute frameworks with various LLM backbones (e.g., Qwen series) and interact with the sandbox via structured tool calls obeying JSON schemas. The harness logs trajectories and computes metrics across five dimensions: Instruction Understanding (Intent Detection, Information Extraction), Planning (Task Decomposition), Tool Use (Tool Selection, Schema Compliance), Decision Making (Delivery Rate, Final Pass Rate), and Efficiency (input/output token counts). The test set comprises 7,098 episodes.

## Key Results
- On basic route planning tasks, state-of-the-art models achieve Delivery Rates up to 97.23% and Final Pass Rates up to 69.09%.
- Performance on Preference-Constrained Route Planning (e.g., avoiding highways, adding waypoints) declines sharply, exposing a key weakness in handling personalized constraints.
- Plan-and-Execute enables open-source models to approach closed-source performance with lower token usage; ReAct yields higher success rates but consumes ~35% more input tokens.

## Why This Works (Mechanism)
The benchmark’s effectiveness stems from three design choices. First, the deterministic API-replay sandbox freezes the environment, removing variance from live network conditions, API updates, and dynamic traffic, ensuring fair, reproducible comparisons. Second, the multi-dimensional evaluation protocol dissects agent capabilities beyond end-task success, isolating strengths and weaknesses in understanding, planning, and tool usage. Third, grounding the benchmark in a massive corpus of real user queries captures the diversity of genuine mobility intents, enhancing ecological validity. Together, these elements pinpoint exact failure modes (e.g., on constrained preferences) and enable systematic improvement.

## Foundational Learning
1. **Deterministic Replay Sandbox**  
   *Why needed:* To eliminate environmental variance from live APIs for reproducible evaluations.  
   *Quick check:* Run the same agent episode twice; the sandbox should produce identical observations and final outcome.

2. **Multi-Dimensional Evaluation Metrics**  
   *Why needed:* To diagnose specific failure modes beyond end-task success.  
   *Quick check:* Correlate metrics (e.g., Schema Compliance) with known agent modifications (e.g., inserting malformed tool calls).

3. **Real-World User Queries**  
   *Why needed:* To reflect natural language diversity and authentic mobility constraints.  
   *Quick check:* Sample queries and verify they contain typical elements (origins, destinations, preferences like “avoid highways”).

4. **Standard Operating Procedures (SOPs)**  
   *Why needed:* To programmatically define the correct tool call sequence and parameters, enabling automated evaluation.  
   *Quick check:* Execute an SOP against the sandbox and confirm it yields a correct route with near-perfect Delivery Rate.

5. **Tool Use and Schema Compliance**  
   *Why needed:* Successful route planning depends on correct API invocation; schema violations cause immediate failures.  
   *Quick check:* Audit agent outputs; any deviation from the provided JSON schema should be flagged.

6. **Agent Frameworks (ReAct vs Plan-and-Execute)**  
   *Why needed:* To explore two paradigms for tool-augmented LLMs: reactive iteration vs. upfront planning.  
   *Quick check:* Measure token usage and Final Pass Rate for both on a constrained task; ReAct should show higher success but higher token consumption.

## Architecture Onboarding
**Component map:**  
User Query -> Agent (LLM + ReAct/Plan-and-Execute) -> Tool Call Generator -> Sandbox (cached API responses) -> Observation Formatter -> Agent context update -> (loop) -> Final Route Output

**Critical Path:**  
(1) Agent receives user query. (2) It either produces a full plan (Plan-and-Execute) or starts a think-act-observe loop (ReAct). (3) Each tool call is schema-validated and executed by the sandbox, returning a deterministic observation. (4) The agent updates its context and repeats until termination (max steps or route completion). (5) The final route is compared against the SOP ground truth.

**Design Tradeoffs:**  
- Deterministic sandbox vs. live APIs: reproducibility & fairness vs. realism (real-time traffic, errors).  
- ReAct vs. Plan-and-Execute: robustness through correction vs. efficiency via static planning.  
- Granular metrics: richer diagnostics vs. increased evaluation complexity.

**Failure Signatures:**  
- Excessive input tokens in ReAct indicate verbose loops or redundant observations.  
- Low Tool Selection or Schema Compliance scores point to poor API usage.  
- Sharp Final Pass Rate drop on Preference-Constrained tasks shows inability to incorporate multiple constraints.

**Three First Experiments:**  
1. **Baseline Replication:** Run the official script for Qwen-4B with both frameworks; verify Delivery Rate and Final Pass Rate align with reported values (within 1%).  
2. **Single-City Validation:** Evaluate on queries from one major city (e.g., Beijing) to check for geographic bias and sandbox coverage.  
3. **Constrained Task Error Analysis:** Run the top model on Preference-Constrained tasks; manually inspect 50 failures to quantify planning vs. tool-use errors.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** What specific architectural or reasoning enhancements are needed for LLM-based agents to reliably handle Preference-Constrained Route Planning tasks, given the stark performance drop compared to basic planning?
- **Basis in paper:** [explicit] The authors explicitly state that "current models perform competently on Basic information retrieval and Route Planning tasks, yet struggle considerably with Preference-Constrained Route Planning, underscoring significant room for improvement in personalized mobility applications."
- **Why unresolved:** The paper identifies this as a key weakness but does not investigate the underlying causes or propose architectural solutions.
- **What evidence would resolve it:** Ablation studies isolating components like planning depth, tool selection accuracy, or constraint handling; development and evaluation of novel agent architectures or prompting strategies designed for multi-constraint optimization.

### Open Question 2
- **Question:** What is the fundamental trade-off between the ReAct and Plan-and-Execute frameworks in production mobility settings, and can hybrid approaches mitigate ReAct's high token cost while preserving its robustness?
- **Basis in paper:** [explicit] The paper finds that "ReAct's superior robustness comes at a non-trivial computational cost... ReAct’s average IT is approximately 35.38% higher than Plan-and-Execute’s" and notes the static planning of Plan-and-Execute "shows a significant lack of robustness when facing dynamic feedback."
- **Why unresolved:** The paper presents the trade-off but does not explore hybrid approaches or evaluate cost-per-success in a realistic deployment scenario.
- **What evidence would resolve it:** Comparative experiments with hybrid agents that combine initial planning with lightweight reactive correction; analysis of token efficiency vs. success rate curves to identify optimal operating points for different latency/cost budgets.

### Open Question 3
- **Question:** To what extent does the deterministic API-replay sandbox introduce distribution shift compared to live mapping services, and how does this affect the real-world generalizability of agent performance?
- **Basis in paper:** [inferred] The sandbox uses cached responses to "eliminate environmental variance," which is necessary for reproducibility. However, real-world traffic, POI availability, and service errors are dynamic. The paper does not measure the performance delta between sandbox evaluation and live API calls.
- **Why unresolved:** The sandbox is a core contribution for reproducibility, but its impact on ecological validity is not assessed. Performance gains might partly reflect overfitting to static, ideal conditions.
- **What evidence would resolve it:** A holdout evaluation on a subset of episodes using live APIs (with statistical controls for time variance) to compare success rates and failure modes against the sandbox results; analysis of error types unique to live services (e.g., rate limiting, stale POI data).

### Open Question 4
- **Question:** What are the precise failure modes within the tool-use and planning dimensions that most critically limit success on Preference-Constrained tasks, and are they primarily due to incorrect tool selection, parameter errors, or flawed intermediate planning?
- **Paper basis:** [inferred] Table 2 shows significant drops in metrics like DEC-P/R and SC for Preference-Constrained tasks (implied by Figure 3's "significant increase in task logic complexity"). The multi-dimensional protocol diagnoses capabilities but the paper does not drill into the error breakdown for the hardest task family.
- **Why unresolved:** The paper presents aggregate scores but does not provide a per-task-family error analysis; without this, targeted improvements are speculative.
- **What evidence would resolve it:** Fine-grained error annotation on failed Preference-Constrained episodes, categorizing failures by stage (intent extraction, tool choice, parameter correctness, planning coherence) and correlating with specific constraint types (e.g., avoid_highways vs. via_points).

### Open Question 5
- **Question:** Can the evaluation protocol be extended to assess robustness under *partial observability* and *ambiguity* in user queries, which are common in real-world mobility interactions but are excluded by the "no-clarification" assumption?
- **Basis in paper:** [explicit] The benchmark assumes "all episodes are designed to be fully solvable based solely on the initial user query" and agents "are not permitted to ask users for clarification." This is a major simplification of real-world dialogues.
- **Why unresolved:** The paper acknowledges this constraint but does not explore how agents would perform if allowed clarification, nor does it quantify the prevalence of underspecified queries in the raw data that were filtered out. This limits understanding of agent readiness for interactive deployment.
- **What evidence would resolve it:** Creation of a complementary test set with ambiguous or underspecified queries; evaluation of agents with a clarification turn budget; measurement of success rate improvements when agents can request missing constraints, and analysis of common clarification strategies.

## Limitations
- Hardware requirements are unspecified, hindering resource planning for full-scale reproduction with large models.
- Sandbox construction pipeline details are incomplete, limiting adaptation to other mapping services.
- Data is restricted to Amap (China), potentially reducing geographic generalizability due to cultural and infrastructural differences.
