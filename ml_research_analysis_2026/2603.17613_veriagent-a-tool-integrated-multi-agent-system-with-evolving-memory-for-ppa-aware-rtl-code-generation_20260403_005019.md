# VeriAgent: A Tool-Integrated Multi-Agent System with Evolving Memory for PPA-Aware RTL Code Generation

## Quick Facts
- **arXiv ID**: 2603.17613
- **Source URL**: https://arxiv.org/abs/2603.17613
- **Reference count**: 8
- **Primary result**: VeriAgent (Gemini-3) achieves 8.539× relative PPA improvement on RTLLM v2.0 and 100% pass@5 on RTLLM v1.1.

## Executive Summary
VeriAgent addresses the gap in LLM-based RTL generation by jointly optimizing for functional correctness and PPA (Power, Performance, Area) through a closed-loop, tool-integrated multi-agent framework. It uses a Programmer Agent for code generation, a Correctness Agent for simulation-based verification, and a PPA Agent for synthesis-driven metric extraction. Central to its performance is an Evolved Memory Mechanism that accumulates and reuses optimization experience across tasks. On standard benchmarks, it significantly outperforms prior work in PPA while maintaining high functional correctness.

## Method Summary
VeriAgent is a training-free framework where three specialized agents orchestrate an iterative refinement process. The Programmer Agent generates or updates RTL based on natural language specs and retrieved memory guidance. The Correctness Agent runs simulation testbenches and returns pass/fail signals. Only functionally correct designs proceed to the PPA Agent, which invokes synthesis tools to extract timing, area, and power metrics. An Evolved Memory Manager maintains a pool of structured nodes (Rule, Structure, EDA Signal) extracted from execution trajectories. After each task, it uses LLM-based semantic matching to retrieve relevant nodes and an LLM-based decision step to insert, refine, or discard memory, enabling cross-task learning.

## Key Results
- On RTLLM v2.0, VeriAgent (Gemini-3) achieves an 8.539× relative PPA score improvement over the original design.
- It achieves 100% pass@5 on RTLLM v1.1, matching high functional correctness standards.
- Against ChipSeek-R1 on overlapping tasks, VeriAgent wins >80% of comparisons on PPA metrics.

## Why This Works (Mechanism)
The system works because it transforms RTL generation from a one-shot task into a continual optimization loop with external feedback. The closed-loop integration of EDA tools grounds the LLM’s coding in real physical constraints. The Evolved Memory Mechanism prevents repeating mistakes and propagates successful patterns (e.g., pipelining strategies, common structural fixes) across designs, effectively building a reusable knowledge base. Semantic memory retrieval ensures guidance is context-aware, while the three-agent separation isolates concerns: correctness is enforced before costly PPA evaluation, and each agent’s output is structured for reliable downstream consumption.

## Foundational Learning
- **Tool-integrated multi-agent systems**: Why needed: LLMs lack inherent access to external verification and synthesis tools; integration provides ground truth for PPA and correctness. Quick check: Can each agent’s output be parsed unambiguously by the next stage?
- **Evolved memory mechanisms**: Why needed: Static prompts cannot capture the diversity of optimization insights across designs; memory enables cumulative learning. Quick check: Does memory insertion/refinement increase the diversity and relevance of stored nodes over time?
- **PPA-aware RTL generation**: Why needed: Traditional code generation ignores physical design costs; PPA metrics require synthesis feedback. Quick check: Are PPA metrics consistently extracted from synthesis reports with the same process library?
- **LLM-based semantic matching**: Why needed: Memory retrieval must generalize beyond keyword matches to surface relevant guidance. Quick check: Does retrieval consistently surface nodes that later prove useful in refinement?
- **EDA tool automation**: Why needed: Manual metric extraction is infeasible for iterative loops; scripts must reliably parse tool outputs. Quick check: Can the pipeline run end-to-end on a known-good RTL example without human intervention?

## Architecture Onboarding
Component map: Natural Language Spec → Programmer Agent → RTL Code → Correctness Agent → [Pass?] → PPA Agent → PPA Metrics; Memory Manager ↔ All Agents (retrieval before generation, evolution after full trajectory).

Critical path: The iterative loop (Programmer → Correctness → PPA) is gated by functional correctness; memory retrieval precedes each Programmer step; memory evolution occurs after a task’s final attempt.

Design tradeoffs: Training-free design enables rapid deployment but relies heavily on prompt engineering and LLM capability. Memory evolution adds computational overhead but improves long-term performance. Proprietary LLMs (Gemini-3) yield best results but limit reproducibility; open-source alternatives may underperform.

Failure signatures: Low functional pass rate despite simple specs (tool integration or parsing errors). Memory nodes that never trigger or frequently trigger but degrade PPA (overfitting or irrelevant retrieval). Many N/A PPA results due to synthesis failures (missing libraries or malformed RTL).

First experiments:
1. Set up Yosys synthesis, a simulator (Icarus Verilog), and NanGate45 library; verify a sample RTL file produces expected delay/area/power numbers.
2. Implement the orchestrator with hard-coded agent prompts for a single benchmark task; confirm the loop runs without tool errors and produces a final RTL file.
3. Run an ablation without memory on 5 RTLLM v2.0 tasks; establish a baseline PPA improvement and functional pass rate.

## Limitations
- **Prompt and integration specs missing**: Exact agent prompts and EDA command sequences are not provided, requiring reverse-engineering.
- **Proprietary LLM dependency**: Core results depend on Gemini-3; performance with open-source models is unclear.
- **PPA metric nuance**: Relative PPA score formula and normalization details are incompletely standardized, risking inconsistent computation.

## Confidence
- **Functional correctness (100% pass@5 on RTLLM v1.1)**: High. Standard benchmark, clear metric.
- **PPA improvement (8.539× on RTLLM v2.0)**: Medium. Depends on correct implementation of unspecified memory and tool integration.
- **Baseline win rate (>80% vs ChipSeek-R1)**: Low. Overlapping task definition and baseline replication conditions are underspecified.

## Next Checks
1. **Memory Mechanism Audit**: Inspect a sample of stored memory nodes (Rule/Structure/EDA Signal) from a reproduced run to verify relevance and actionability of guidance.
2. **Toolchain Isolation Test**: Manually execute the reported EDA commands (simulation, synthesis with NanGate45) on a known-good RTL example to validate metric extraction logic and avoid false negatives.
3. **Cross-LLM Replication**: Run the framework on 5–10 RTLLM v2.0 tasks using a strong open-source LLM (e.g., Llama-3.1-70B) to measure performance variance and test robustness beyond proprietary models.
