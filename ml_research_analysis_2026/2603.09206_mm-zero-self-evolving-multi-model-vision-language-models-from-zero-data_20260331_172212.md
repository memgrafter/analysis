# MM-Zero: Self-Evolving Multi-Model Vision Language Models From Zero Data

## Quick Facts
- **arXiv ID:** 2603.09206
- **Source URL:** https://arxiv.org/abs/2603.09206
- **Reference count:** 0
- **Primary result:** Self-evolving VLMs from zero data via a tri-role RL framework; Qwen3-VL-8B improves average accuracy by +3.4% (3 iterations) and Mimo-VL-7B by +5.1% (3 iterations).

## Executive Summary
MM-Zero presents a novel approach to training vision-language models without any external data by leveraging a tri-agent reinforcement learning loop. The three agents—Proposer, Coder, and Solver—are all initialized from the same base model and trained sequentially using Group Relative Policy Optimization (GRPO). The Proposer designs abstract visual concepts and easy/hard question-answer pairs; the Coder translates these concepts into executable SVG code, which is rendered into images; and the Solver answers questions on the rendered images, with test-time RL providing synthetic labels for hard questions. Rewards are carefully crafted to incorporate execution feedback, solvability monitoring, difficulty balancing, and diversity incentives to prevent reward hacking and maintain a challenging yet solvable task distribution. Experiments on Qwen3-VL-8B and Mimo-VL-7B demonstrate consistent gains across nine multimodal benchmarks: +3.4% absolute (50.7% → 54.1%) for Qwen3-VL-8B after three iterations and +5.1% (50.9% → 56.0%) for Mimo-VL-7B, with further improvement to 54.5% for Qwen3-VL-8B after five iterations. This work opens a path toward self-improving VLMs that can bootstrap their reasoning capabilities from scratch.

## Method Summary
MM-Zero’s training proceeds in iterative cycles, each consisting of three sequential stages with the other agents frozen. First, the Proposer is trained using GRPO to generate tuples (caption, easy question/answer, hard question/answer). Its reward combines binary execution feedback (did the Coder successfully render an image?), a solvability score (fraction of Solver correct on easy questions) capped at 0.5, a difficulty reward based on Solver’s self-consistency on hard questions (peaking when consistency ≈0.5), and penalties/rewards for content diversity. Next, the Coder is trained on data produced by the latest Proposer; it receives rewards for successful SVG rendering, solvability of the easy question, appropriate difficulty, and low syntax errors. Finally, the Solver is trained on images from Proposer+Coder that pass filtering (render success rate between 0.25–0.75, easy accuracy >0.5, hard accuracy 0.27–0.75). The Solver’s reward uses test-time RL: multiple rollouts produce answers, a majority vote serves as a silver label, and the reward mixes accuracy against this label and a format bonus. All roles use GRPO with group-relative advantages, avoiding a learned value network. The process is repeated for multiple iterations, with each stage using the most recent checkpoints for rollouts. Final performance is evaluated via an LLM-as-a-judge (Qwen2.5-14B-Instruct) across nine multimodal reasoning benchmarks.

## Key Results
- **Qwen3-VL-8B:** average accuracy across 9 benchmarks increased from 50.7% to 54.1% after 3 iterations (+3.4% absolute).
- **Mimo-VL-7B:** average accuracy rose from 50.9% to 56.0% after 3 iterations (+5.1% absolute).
- **Extended training:** Qwen3-VL-8B reached 54.5% after 5 iterations, indicating ongoing improvement potential.

## Why This Works (Mechanism)

### Mechanism 1: Tri-role Closed-loop Enables Zero-Data Self-Evolution
- **Claim:** The tri-role closed-loop (Proposer → Coder → Solver) enables zero-data self-evolution by generating its own training distribution from a single base model.
- **Mechanism:** The Proposer creates captions and paired easy/hard questions. The Coder translates these into executable SVG code to render images. The Solver answers questions on these images, providing execution feedback (via rendering success) and reasoning signals (via TTRL) back to the Proposer. This loop creates a synthetic data pipeline where each role's output becomes the next role's training data, all initialized from the same model checkpoint.
- **Core assumption:** A single base model possesses latent capabilities for semantic description (Proposer), code generation (Coder), and visual reasoning (Solver) that can be disentangled and specialized via role-specific RL fine-tuning.
- **Evidence anchors:** [abstract] "All three roles are initialized from the same base model and trained using Group Relative Policy Optimization (GRPO)"; [section 2.2] "MM-Zero contains three distinct model agents evolved from the same base model... During each role’s training phase, the other two roles remain frozen."; [corpus] Prior work (e.g., VisPlay, Agent0-VL) uses dual-role proposer-solver loops but still rely on seed images; MM-Zero’s tri-role with code-based rendering is a key differentiator.
- **Break condition:** If the Coder’s rendering success rate collapses (e.g., below the 25% filtering threshold), the loop fails to produce valid training images for the Solver, halting progression.

### Mechanism 2: Multi-component Reward Prevents Hacking and Maintains Goldilocks Difficulty
- **Claim:** The multi-component reward function, particularly the capped solvability (`min(Rsolv, 0.5)`) and dynamic difficulty (`Rdiff = min(ci, 1-ci)`), prevents reward hacking and maintains task difficulty in the "Goldilocks zone."
- **Mechanism:** The Proposer reward combines binary execution feedback, a solvability score (fraction of solver correct on easy questions) capped at 0.5, and a difficulty score peaking at 0.5 when solver self-consistency is 0.5. This forces the Proposer to create tasks where the easy question is just solvable (to get solvability reward) while the hard question induces maximum solver uncertainty (to get difficulty reward), preventing trivial answer-in-image shortcuts.
- **Core assumption:** Solver self-consistency on hard questions (via TTRL majority vote) is a reliable proxy for task difficulty when ground truth is unavailable.
- **Evidence anchors:** [section 2.4] "This cap prevents the Proposer from being overly rewarded for generating easy, trivially solvable instances... Without the cap, solvability can reach a maximum of 1.0 while the difficulty optimum remains at 0.5, creating an imbalanced reward signal."; [section 4 (ablation)] "Removing solvability capping leads to reward hacking by the coder... the model increasingly embeds answers directly as text within the generated code."; [corpus] The concept of 'Goldilocks' difficulty [14] is cited, but the specific reward formulation is novel to MM-Zero.
- **Break condition:** If solver consistency (`ci`) systematically drifts toward 0 or 1 on hard questions, the difficulty reward (`Rdiff`) collapses to 0, removing the incentive to create appropriately challenging tasks and causing training stagnation.

### Mechanism 3: Progressive Complexity Scaling via Dynamic Difficulty Distribution
- **Claim:** Progressive complexity scaling emerges from the interaction of the difficulty reward and data filtering, where the Solver's improving capabilities shift the Proposer's task distribution toward harder, more compositional problems.
- **Mechanism:** The Coder’s rendering success rate filter (0.25–0.75) and Solver’s difficulty filter (hard accuracy 0.27–0.75) ensure only tasks of intermediate difficulty enter training. As the Solver improves via TTRL on these tasks, questions that were previously "hard" become "easy," altering the solver’s self-consistency distribution. The Proposer, rewarded for maximizing `Rdiff`, then generates new questions that re-induce solver uncertainty at the new capability frontier, creating a moving target of complexity.
- **Core assumption:** The Solver’s performance improvement is monotonic within an iteration, allowing the difficulty distribution to shift forward.
- **Evidence anchors:** [section 3.1/Fig. 2] "Throughout training, the coder’s image rendering success rate steadily improves... image solvability also increases."; [section 3.3/Fig. 3] Case studies show evolution from cluttered layouts with embedded answers to polished diagrams requiring multi-step extraction and derived value computation.; [section 2.2 (training data filtering)] Filters explicitly maintain a "just right" difficulty band for both Coder and Solver training data.
- **Break condition:** If the Solver’s improvement saturates or regresses between iterations, the `Rdiff` signal can no longer push complexity forward, leading to a distributional collapse where the Proposer recycles previously successful templates.

## Foundational Learning
- **Concept: Reinforcement Learning with Verifiable Rewards (RLVR)**
  - Why needed: Replaces human preference labels or ground-truth answers with rule-based, differentiable rewards (e.g., execution success, answer consistency), enabling training without external supervision.
  - Quick check: How does the binary execution indicator `1_exec(Ci)` for the Coder differ from the continuous solvability score `Rsolv` for the Proposer, and why are both necessary?

- **Concept: Test-Time Reinforcement Learning (TTRL)**
  - Why needed: Generates synthetic "silver labels" for hard questions via majority vote of multiple solver rollouts, providing a training signal when ground truth is absent.
  - Quick check: Why is the difficulty reward `Rdiff = min(ci, 1-ci)` symmetric around `ci=0.5`, and what would happen if it were simply `1 - ci`?

- **Concept: Group Relative Policy Optimization (GRPO)**
  - Why needed: Enables policy updates using relative advantages within a rollout group, avoiding the need for a learned value function and stabilizing training in sparse-reward settings.

## Architecture Onboarding
**Component map:**  
Base Model → Proposer, Coder, Solver (roles initialized from the same VLM). Proposer generates (caption, easy_q/a, hard_q/a) → Coder generates SVG code → Rasterized images → Solver answers questions. Feedback loops: Solver’s TTRL yields silver labels and consistency scores used in Proposer reward; Coder’s render success used in Proposer reward.

**Critical path (per iteration):**  
1. Train Proposer with frozen Coder and Solver using GRPO and reward `Rp`.  
2. Collect ~4k samples from the trained Proposer.  
3. Train Coder (initialized from the same base model) on the collected data, using reward `RD`.  
4. Collect solver training data by running Proposer+Coder (latest checkpoints), filter by render success and difficulty filters.  
5. Train Solver (initialized from base) on filtered data using TTRL reward `RS`.  
6. Repeat from step 1 for the next iteration, loading latest checkpoints.

**Design tradeoffs:**  
- GRPO vs. PPO: GRPO removes the value network, reducing memory/compute but relies on group-based relative rewards; may be less stable if group diversity is low.  
- SVG-only rendering: Ensures deterministic, executable synthesis but limits visual diversity (no photorealistic or 3D scenes).  
- Single-model initialization: Parameter-efficient and promotes shared knowledge, but may hinder role specialization if the base model lacks certain capabilities (e.g., 4B model’s lower render success).

**Failure signatures:**  
- **Coder collapse:** Render success rate drops below 25% filter threshold → no valid images for Solver.  
- **Proposer reward hacking:** Solvability (`Rsolv`) near 1.0 while difficulty (`Rdiff`) near 0 → answers embedded in code/text.  
- **Solver overfit:** Hard accuracy declines across iterations → Proposer converges to narrow visual types.  
- **Diversity penalty failure:** Caption/question cluster shares remain high → repetitive generation.

**First three experiments to run:**  
1. Role isolation sanity check: Freeze all but one role and verify its expected reward component moves in the right direction (e.g., training only Proposer should increase `Rdiff`).  
2. Solvability cap ablation: Remove `min(Rsolv,0.5)` and monitor for solvability inflation and later performance drop.  
3. Render success tracking: Log Coder’s SVG compilation rate every 5 steps; confirm monotonic improvement as a leading health indicator.

## Open Questions the Paper Calls Out
1. **How does self-evolution performance scale with base VLM size?**  
   Basis: The limitation section notes inability to validate scaling on larger models (e.g., 38B) due to compute cost.  
   Why unresolved: Training extremely large models is expensive, so the scaling curve (linear, logarithmic, saturating) is unknown.  
   Evidence needed: Train MM-Zero on progressively larger base models (8B, 13B, 34B, 70B) with matched compute, measuring intermediate metrics and final scores.

2. **What is the ultimate ceiling of self-evolution from zero external data?**  
   Basis: Section 3.2 asks how far a model can self-evolve before reaching its ceiling without human supervision; experiments stopped at 5 iterations due to resources.  
   Why unresolved: It is unclear whether gains will plateau, reverse, or continue indefinitely.  
   Evidence needed: Very long-horizon runs (tens/hundreds of iterations) tracking performance, diversity, and reward behavior.

3. **Can extending the Coder’s toolset render richer multimodal data and further improve reasoning?**  
   Basis: Conclusion suggests extending beyond code generation to 3D renderers, diagram libraries.  
   Why unresolved: Currently Coder only produces SVG/simple plots; many tasks require 3D/spatial reasoning. Unknown if diversifying output modalities yields gains.  
   Evidence needed: Integrate additional backends (e.g., Blender for 3D, Graphviz) and compare Solver performance on a 3D/spatial benchmark suite.

4. **Do additional specialized agent roles improve stability, diversity, or convergence?**  
   Basis: Conclusion mentions exploring roles beyond the current three.  
   Why unresolved: Roles like Critic, meta-optimizer, or Refiner might mitigate reward hacking or diversity collapse but their coordination is unexplored.  
   Evidence needed: Design and train supplementary roles while keeping conditions fixed; compare curves, final performance, and robustness.

## Limitations
- **Implementation details missing:** GRPO/TTRL hyperparameters (ε, β, K) and vLLM orchestration specifics are not provided, hindering exact reproduction.
- **Evaluation via LLM judge:** Reliance on Qwen2.5-14B-Instruct as a judge without human verification may introduce bias and questions about result reliability.
- **Compute and rendering constraints:** Training requires 8×96GB GPUs, limiting accessibility; SVG-only rendering restricts scene complexity and may not generalize to photorealistic or 3D tasks.
