# vla-eval: A Unified Evaluation Harness for Vision-Language-Action Models

## Quick Facts
- **arXiv ID**: 2603.13966
- **Source URL**: https://arxiv.org/abs/2603.13966
- **Reference count**: 23
- **Primary result**: A unified harness eliminates evaluation duplication and dependency conflicts, achieves up to 47× parallel speedup on LIBERO, but reveals hidden benchmark requirements that distort reproducibility.

## Executive Summary
Vision-Language-Action (VLA) model evaluation is highly fragmented, with each benchmark requiring custom scripts, leading to code duplication, dependency conflicts, and poorly specified protocols. vla-eval introduces a unified harness that standardizes integration through a single `predict()` interface for models and a four-method protocol for benchmarks. It uses Docker isolation and WebSocket+msgpack communication to manage environment conflicts, and supports parallel evaluation via episode sharding and batch inference. The harness covers 13 benchmarks and 6 models, delivering a 47× wall-clock speedup on LIBERO. A reproducibility audit confirms close alignment with published scores but uncovers critical undocumented requirements (e.g., CALVIN’s normalization, SimplerEnv’s termination logic) that can invalidate results. A public leaderboard aggregates 657 results across 17 benchmarks.

## Method Summary
vla-eval employs a two-command workflow: `vla-eval serve` launches a model server within an isolated environment (using Docker or `uv`), exposing a WebSocket endpoint; `vla-eval run` executes a benchmark by connecting to the server, resetting environments, and iterating steps until termination. Models are integrated by implementing a `predict(images, states, task_description)` function. Benchmarks are wrapped to provide `reset()`, `step(action)`, `render()`, and `close()` methods. Parallelism is achieved by distributing episodes across multiple workers (`num_episode_workers`) and processing observations in batches (`max_batch_size`). Configuration is managed via YAML files specifying model paths, benchmark Docker images, and parallelism parameters.

## Key Results
- Unified harness integrates 6 models and 13 benchmarks, eliminating custom scripts and dependency conflicts.
- Parallel evaluation (episode sharding + batch inference) yields a 47× speedup, reducing 2000 LIBERO episodes from ~14 hours (sequential) to ~18 minutes on an H100.
- Reproducibility audit on DB-CogACT closely matched published scores on three benchmarks but identified critical undocumented requirements: ambiguous termination semantics in SimplerEnv and hidden normalization statistics in CALVIN that significantly distort results if mishandled.
- Leaderboard aggregates 657 published results across 17 benchmarks, promoting centralized comparison.

## Why This Works (Mechanism)
The harness succeeds by enforcing a strict separation of concerns: models and benchmarks are decoupled through a minimal, well-defined interface. Docker containers isolate benchmark-specific dependencies (e.g., physics engines, vision libraries), preventing version conflicts. WebSocket+msgpack provides a lightweight, language-agnostic communication layer between the host and containers. Parallelism scales by sharding episodes across CPU workers and batching observations for GPU inference, maximizing hardware utilization. The design accepts that underlying benchmarks may be ambiguous—it standardizes the integration points but cannot resolve inherent protocol flaws, which the audit exposes.

## Foundational Learning
- **Dependency Isolation**: Docker containers encapsulate each benchmark’s environment. *Why needed*: Benchmarks rely on incompatible libraries (e.g., MuJoCo vs. PyBullet). *Quick check*: `docker pull` succeeds for all benchmark images; container starts without missing library errors.
- **Parallel Episode Sharding**: Distributes independent episodes across multiple processes. *Why needed*: Most benchmarks are embarrassingly parallel; sequential evaluation wastes CPU cycles. *Quick check*: CPU utilization scales with `num_episode_workers` until saturation.
- **Batch Inference**: Aggregates multiple observations into a single model forward pass. *Why needed*: GPU throughput is optimized for large tensors; small batches underutilize compute. *Quick check*: Increase `max_batch_size` and measure steps/second; should increase until GPU memory limits.
- **Standardized Model Interface**: All models expose `predict(images, states, task_description)`. *Why needed*: Allows any model to run on any benchmark without modification. *Quick check*: Swap model config files; same benchmark driver runs unchanged.
- **WebSocket Communication**: Host and containers exchange serialized messages. *Why needed*: Enables real-time, bidirectional control flow across process/language boundaries. *Quick check*: Monitor WebSocket traffic for dropped packets or high latency during long runs.
- **Benchmark Protocol Abstraction**: Four-method interface (`reset`, `step`, `render`, `close`). *Why needed*: Uniform control loop across diverse simulators (e.g., LIBERO vs. CALVIN). *Quick check*: Each benchmark’s Docker image implements all methods without requiring custom host-side logic.

## Architecture Onboarding
Component map: Model Server -> WebSocket -> Benchmark Environment (Docker) -> vla-eval run CLI  
Critical path: `vla-eval serve` starts model server (loading model weights); `vla-eval run` loads benchmark YAML, connects via WebSocket, resets N environments, then repeatedly calls `step()` until all episodes terminate or truncate.  
Design tradeoffs: Docker isolation adds startup overhead but guarantees reproducibility; parallelism limited by GPU memory (batch size) and CPU cores (episode workers); batching improves throughput but requires handling variable-length episode padding.  
Failure signatures: Score deviation >5% indicates possible normalization/termination mismatch; container crashes show Docker logs; dependency conflicts resolved by using `uv run` for model server.  
First experiments: 1) Run 1 episode with OpenVLA on LIBERO to validate basic connectivity. 2) Scale `num_episode_workers` from 1 to 16 on H100; measure speedup and monitor GPU/CPU utilization to find saturation point. 3) Reproduce DB-CogACT’s LIBERO success rate from Table II; if off by >2%, inspect CALVIN normalization and SimplerEnv termination handling.

## Limitations
- Hidden benchmark requirements (CALVIN’s normalization statistics, SimplerEnv’s termination flags) are not documented by original authors; using defaults leads to score distortion.
- The 47× speedup claim is hardware-specific (H100); optimal shard/batch sizes vary with GPU memory, CPU cores, and network latency, limiting generalizability.
- vla-eval standardizes integration but cannot fix fundamental ambiguities in benchmark protocols (e.g., what constitutes episode termination), leaving reproducibility contingent on external resolution.

## Confidence
- Unified harness eliminates duplication/conflicts: Medium (design is sound, but benchmark ambiguities undermine full reproducibility gains).
- 47× parallel speedup: Medium (plausible given architecture; not broadly validated across hardware).
- Reproducibility audit (close match + documented pitfalls): High (direct empirical evidence with clear root-cause analysis).
- Leaderboard aggregation (657 results): Medium (straightforward collation, but sourcing transparency unverified).
