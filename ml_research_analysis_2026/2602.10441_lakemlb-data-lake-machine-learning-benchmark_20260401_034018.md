# LakeMLB: Data Lake Machine Learning Benchmark

## Quick Facts
- **arXiv ID**: 2602.10441
- **Source URL**: https://arxiv.org/abs/2602.10441
- **Reference count**: 40
- **Primary result**: Pre-training (PT) yields 83.3% win rate in Union scenarios; feature augmentation (FA) yields 91.7% win rate in Join scenarios.

## Executive Summary
LakeMLB is a novel benchmark designed to evaluate machine learning methods in data lake environments, where multiple tables from diverse sources must be integrated for predictive tasks. It introduces six real-world datasets—three for Union (vertical integration of tables with overlapping label spaces) and three for Join (horizontal enrichment via entity linking)—each with fixed train/validation/test splits. The benchmark assesses three integration strategies: pre-training-based (PT), data augmentation-based (DA), and feature augmentation-based (FA), across a broad suite of tabular learning methods, from gradient boosting to deep transformers and transfer learning models. Key findings indicate that PT strategies excel in Union settings, while FA dominates in Join settings. Transfer learning models such as CARTE and TransTab demonstrate robust performance across both scenarios, highlighting their adaptability to data lake challenges.

## Method Summary
The benchmark addresses multi-table classification under two data lake scenarios. **Union** tasks combine target and auxiliary tables that share a common label space but originate from different sources (e.g., Maryland and Seattle traffic data). **Join** tasks link tables via entity matching to enrich the target with auxiliary features (e.g., stock lists with Wikipedia articles). Each dataset provides predefined splits (70/10/20) and balanced classification targets.

Three integration strategies are formalized:
- **Pre-training-based (PT)**: Models are pretrained on the full auxiliary table (using either supervised or self-supervised objectives per method) and then fine-tuned on the target training set.
- **Data Augmentation-based (DA)**: Schema alignment (normalized column names) and label alignment are performed; for Union, BERT-based 1-NN maps labels between domains; for Join, matched auxiliary rows inherit target labels. A fraction (up to 30%) of aligned auxiliary samples is appended to the target training data.
- **Feature Augmentation-based (FA)**: For each target row, the nearest neighbor in the auxiliary table is retrieved using BERT embeddings of entity names (Join) or row text (Union). The auxiliary features of the neighbor are concatenated to the target features, and the model is trained on this augmented dataset.

The benchmark evaluates a diverse set of baselines: XGBoost, LightGBM, CatBoost; TabTransformer, FT-Transformer, SAINT, TromptNet, ExcelFormer; TransTab, CARTE; TabPFNv2, TabICL. Hyperparameters are tuned via grid search on the validation set using search spaces from Appendix C, with early stopping. Test accuracy is the primary metric.

## Key Results
- **Union**: Pre-training-based (PT) methods achieve the highest win rate (83.3%) and a positive average gain over baselines.
- **Join**: Feature augmentation-based (FA) methods dominate with a 91.7% win rate and an average gain of +2.97%.
- Transfer learning models (CARTE, TransTab) exhibit consistent robustness across both Union and Join scenarios, often ranking among the top performers.

## Why This Works (Mechanism)
The effectiveness of the integration strategies can be attributed to the structural differences between Union and Join scenarios. In Union, the auxiliary table shares the same feature space as the target but comes from a different distribution; pre-training allows a model to learn generalizable representations that transfer effectively to the target domain. In Join, the auxiliary table provides complementary features that are not present in the target; feature augmentation directly injects this additional information, making it essential to have accurate row matching. Transfer learning models like CARTE and TransTab are specifically designed to handle multi-table data by learning entity embeddings that capture cross-table semantics, hence they perform robustly irrespective of the integration scenario.

- **Data Augmentation** – Adding aligned auxiliary samples to the target training set. *Why needed*: Increases training data size and diversity, especially useful when target data is scarce. *Quick check*: Ensure label alignment is correctly implemented (e.g., BERT 1-NN mapping).

- **Multi-table Classification** – Predictive tasks that span multiple tables. *Why needed*: Real-world data lakes often consist of numerous related tables. *Quick check*: Validate that each dataset’s target and auxiliary tables are correctly identified and that label spaces are compatible.

## Architecture Onboarding
**Component Map** (plain text):
Raw Data -> Preprocessing -> Alignment (for DA/FA) -> Model Training -> Evaluation -> Metrics

**Critical Path**: A successful run requires: (1) downloading and verifying dataset files; (2) applying fixed splits; (3) computing alignments (label mapping for DA, nearest neighbors for FA) if needed; (4) training the chosen model with hyperparameter search on the validation set; (5) evaluating on the test set and reporting accuracy.

**Design Tradeoffs**:
- *Simplicity vs Generality*: The benchmark restricts to a single auxiliary table to keep the setup tractable, but this limits applicability to more complex relational data lakes.
- *BERT Embedding Cost*: Using BERT for matching yields semantic richness but introduces significant compute and memory overhead, especially for large tables.
- *Fixed Splits*: Fixed splits enhance reproducibility but do not cover temporal or distributional variations that occur in real deployments.

**Failure Signatures**:
- Missing or corrupted dataset files leading to `FileNotFoundError`.
- Schema mismatches between target and auxiliary tables causing alignment failures (e.g., mismatched column names or types).
- Memory exhaustion during BERT embedding generation; mitigated by batching.
- Hyperparameter search not converging due to inappropriate search ranges or insufficient early stopping patience.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: How can machine learning models effectively integrate information from multiple auxiliary tables with complex relational structures in data lakes?
- **Basis in paper**: [explicit] The authors state that future work should extend the benchmark to "larger collections of highly heterogeneous tables" and "richer relational structures" beyond the current single-auxiliary-table setting.
- **Why unresolved**: Current research and benchmarks, including LakeMLB, are limited to scenarios with at most one auxiliary table, which does not reflect the complexity of real-world data lakes where multiple related tables exist.
- **What evidence would resolve it**: Development and evaluation of new models on extended benchmarks featuring multiple auxiliary tables with varied relationships (e.g., chains, stars), demonstrating improved performance over naive extensions of existing single-auxiliary methods.

### Open Question 2
- **Question**: How can models adapt to evolving schemas over time in data lake environments?
- **Basis in paper**: [explicit] The authors identify "evolving schemas" as a key aspect of more realistic data lake scenarios that the current benchmark does not address.
- **Why unresolved**: Existing methods assume static feature spaces and label taxonomies, but in practice, data lakes ingest new sources with schema changes, causing feature drift and label shifts that degrade model performance.
- **What evidence would resolve it**: Models that maintain performance on temporally split data with schema changes, or that can dynamically adjust feature representations when new columns appear or old ones disappear, validated on synthetic or real datasets with controlled schema evolution.

### Open Question 3
- **Question**: What are the fundamental reasons behind the scenario-dependent effectiveness of integration strategies, where pre-training-based methods excel in Union settings and feature augmentation-based methods dominate in Join settings?
- **Basis in paper**: [inferred] The paper reports empirical results showing PT win rate 83.3% in Union and FA win rate 91.7% in Join, but does not provide a theoretical or in-depth analysis of why this discrepancy occurs.
- **Why unresolved**: Understanding the underlying mechanisms could inform the design of more robust and adaptive integration strategies that perform well across both scenarios, but the paper only offers high-level intuitions (e.g., semantic alignment in PT, feature complementarity in FA).
- **What evidence would resolve it**: Controlled experiments isolating factors like distribution shift, semantic similarity, and feature redundancy; or qualitative analysis of learned representations showing how PT and FA capture different types of cross-table information.

### Open Question 4
- **Question**: How can row-matching for joinable tables be made more accurate and robust in noisy data lakes with semantic gaps and schema heterogeneity?
- **Basis in paper**: [inferred] The paper uses a simple BERT-based 1-NN matching and shows that performance degrades with poorer matches (Figure 4), and identifies data quality and semantic gaps as key challenges.
- **Why unresolved**: The current matching approach is simplistic and likely error-prone, especially with noisy entity names and cross-domain tables; improving matching is critical for feature augmentation but not deeply explored.
- **What evidence would resolve it**: New matching techniques (e.g., using richer metadata, cross-modal embeddings, or learning to match) that achieve higher precision/recall on joinable table pairs, leading to improved performance in the Join setting when used with FA.

## Limitations
- **Dataset acquisition ambiguity**: The paper references external sources but does not specify whether the repository provides preprocessed splits or raw data, risking schema mismatches and inconsistent preprocessing.
- **Incomplete implementation details**: Exact procedures for BERT-based fuzzy matching (tokenization, pooling, thresholds) and label alignment are not documented, hindering faithful reproduction.
- **Baseline adaptation vagueness**: It is unclear how tree-based models (e.g., XGBoost) incorporate pre-training or augmentation, and how the 30% sample cap for DA is applied when auxiliary sizes vary.
