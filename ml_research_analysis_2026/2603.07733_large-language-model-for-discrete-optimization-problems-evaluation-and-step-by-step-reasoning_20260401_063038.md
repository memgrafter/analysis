# Large Language Model for Discrete Optimization Problems: Evaluation and Step-by-step Reasoning
## Quick Facts
- **arXiv ID:** 2603.07733
- **Source URL:** https://arxiv.org/abs/2603.07733
- **Reference count:** 40
- **Primary result:** Stronger LLMs (GPT-4o-mini, DeepSeek-R1) outperform weaker ones (Llama-3-8B, ORLM); CoT improves performance for strong models but harms weak ones; disordered datasets increase accuracy for strong models on easy problems but raise timeout rates and variance.

## Executive Summary
This paper evaluates large language models on discrete optimization tasks from the OR Library and Vehicle Routing Problem (VRP) using a newly created natural language dataset. The dataset includes original, expanded, and disordered (sentence‑randomized) versions of problem descriptions. The authors test Program‑of‑Thought (PoT) and Chain‑of‑Thought (CoT) prompting, measuring pass rate, accuracy rate, MAPE, and timeout rate across four models: GPT-4o-mini, DeepSeek-R1, Llama-3-8B, and ORLM. Results show that stronger models consistently achieve higher scores. Contrary to common belief, CoT benefits strong models but degrades performance of weak ones. Disordered descriptions improve accuracy for strong models on easier problems but also increase timeout and variability. Error analysis reveals model‑specific failure patterns (e.g., frequent ValueError for weak models, IndexError for strong models). The study concludes that optimal prompting strategy depends on model capability and problem difficulty.

## Method Summary
The dataset comprises discrete optimization instances converted into natural language prompts. Each instance is accompanied by a separate numeric data file, an optimal reference value, and optimization sense (min/max). Three dataset variants are used: original (ordered sentences), disordered (randomized sentence order), and expanded (background‑swapped). Four LLMs are evaluated with two prompting techniques: (1) PoT, which directly generates executable Python code; (2) PoT+CoT, which first produces step‑by‑step reasoning before code. For each run, the model’s output is extracted as a Python script and executed in a sandbox with PuLP or OR‑Tools, under a 300‑second timeout. If the script fails, the error is fed back to the model for correction up to six times. Success metrics include Pass Rate (code runs without error), Accuracy Rate (solution beats known optimum), Mean Absolute Percentage Error (MAPE), and Timeout Rate (execution exceeds 300 s among passes). Errors are logged and classified to analyze failure modes.

## Key Results
- **Model strength:** Stronger LLMs (GPT-4o-mini, DeepSeek-R1) significantly outperformed weaker ones (Llama-3-8B, ORLM) on all metrics.
- **CoT effect:** Chain‑of‑Thought reasoning improved performance for strong models but harmed weak models, contradicting the assumption that step‑by‑step guidance universally helps.
- **Disorder effect:** Randomizing sentence order boosted accuracy for strong models on easy problems but increased timeout rates and output variance.
- **Error patterns:** Weak models often produced format‑related errors (ValueError, SyntaxError), while strong models exhibited more logical errors (IndexError, KeyError).
- **Strategic implication:** Prompting should be tailored to model strength and problem difficulty—strong models benefit from CoT and disorder on easy tasks, while weak models perform best with no‑CoT on original datasets.

## Why This Works (Mechanism)
### Mechanism 1: CoT benefits stronger models but harms weaker ones.
Chain‑of‑Thought prompting decomposes optimization problems into a sequence of reasoning steps, which the model must follow to produce a final solution. Stronger models, with superior coherence and reasoning capacity, can maintain correctness across multiple steps, increasing the likelihood of a valid outcome. In contrast, weaker models are prone to error propagation: an early mistake cascades through subsequent steps, causing complete failure. The underlying assumption is that multi‑step reasoning amplifies the model’s innate quality; if per‑step accuracy falls below a critical threshold, CoT introduces more failure points than guidance. Evidence includes the abstract’s claim and results from Section 4.A showing that for pass rate, stronger models benefit while weaker ones do not.

### Mechanism 2: Disordered datasets aid stronger models on easier problems but increase instability.
Randomizing the order of sentences in problem descriptions disrupts stereotypical phrasing and forces models to extract the optimization objective early (often moved to the front). This encourages deeper processing rather than shallow pattern matching. For easy problems—where the objective is recoverable despite scrambling—strong models leverage this to produce more accurate solutions. However, the added cognitive load leads to longer solution times and less stable outputs, raising timeout and variance rates. The effect is problem‑dependent: “easier” tasks improve with disorder, while “more difficult” ones do not. Evidence is reported in the abstract and RQ3, with data showing GPT‑4o‑mini’s accuracy rise on disordered easy tasks accompanied by higher timeout rates.

### Mechanism 3: Stronger models produce fewer format compliance errors and more viable code.
Superior pretraining data (including high‑quality code and instructions) enables stronger models to correctly use APIs (e.g., PuLP), handle variable dimensions, and output properly formatted results. They generate syntactically correct Python, correctly parse input data, and call solver functions appropriately. Weaker models suffer from hallucination, mismatched data types, and poor reading of provided files, leading to frequent SyntaxErrors, ValueErrors, and other runtime failures. This pattern is evident in error analysis tables (A.12–A.24), where Llama‑3‑8B and ORLM are dominated by format errors, while GPT‑4o‑mini and DeepSeek‑R1 exhibit rarer, more diverse issues. The break condition is simple: sufficient exposure to high‑quality code during training correlates with lower error rates.

## Architecture Onboarding
**Component Map:**  
Dataset Module → Prompting Module → LLM Inference Module → Code Execution Sandbox → Evaluation Module → Analysis Module

**Critical Path:**  
Problem instance → Prompt → LLM response → Code extraction → Execution → Metric calculation. Any break (e.g., invalid code) stops progress and is logged as failure.

**Design Tradeoffs:**  
- *Explicit vs. Implicit Representation:* Explicit mathematical models are verbose and prone to hallucination; the paper uses implicit natural language, which is cheaper but relies on model inference.  
- *Disorder:* Adding sentence randomization tests robustness and can improve deep processing, but increases variance and timeout risk.  
- *CoT:* Provides stepwise guidance, extending sequence length; beneficial only for strong models.  
- *Timeout Limit:* 300 seconds balances thoroughness with practicality; shorter limits may penalize exact solvers.

**Failure Signatures:**  
- **Execution Errors:** IndexError (out‑of‑range), ValueError (data conversion), SyntaxError (malformed Python), TypeError (API misuse), PulpError (infeasibility).  
- **Timeout:** Exceeding 300 s during solver run.  
- **Incorrect Solution:** Accuracy Rate = 0 or MAPE ≥ 500% (treated as null).  
- **Model‑specific patterns:** ORLM – format compliance; Llama‑3‑8B – high SyntaxError on VRP; GPT‑4o‑mini – more KeyError.

**First 3 Experiments:**  
1. Baseline comparison across all models on original dataset with and without CoT, recording pass rate, accuracy rate, MAPE, and timeout rate.  
2. Disorder impact analysis: for each model, compare metrics between original and disordered versions, focusing on accuracy variance and timeout rate.  
3. Error analysis: tally and categorize errors (e.g., IndexError, ValueError) for each problem type and model/technique combination to identify common failure modes.

## Limitations
- **Implementation gaps:** Dataset file structure and reference metadata are not sufficiently described, hindering exact replication.  
- **Prompt/setting ambiguity:** CoT instruction wording and inference parameters (e.g., max tokens, retry feedback) are omitted.  
- **Generalizability:** Evaluation is limited to four models on a static set of OR problems; findings may not extend to other LLMs or domains.

## Confidence
- **CoT effect (benefits strong, harms weak):** Medium  
- **Disorder effect (improves accuracy on easy problems for strong models, increases timeout/variance):** Medium  
- **Error pattern differences (strong models have fewer format errors):** High  
- **Strategic recommendations (tailor prompting to model strength and problem difficulty):** Medium  

## Next Checks
1. Full replication: Obtain the Figshare dataset, clarify file conventions, and rerun the PoT/PoT+CoT pipeline for all four models to verify reported metrics.  
2. CoT prompt sensitivity: Reconstruct or retrieve the per‑problem‑type CoT templates and test alternative formulations to confirm the strength‑dependent effect.  
3. Generalizability test: Evaluate at least two newer LLMs (e.g., GPT‑4o, Claude‑3) on the same dataset with finer‑grained difficulty metrics to assess whether disorder and CoT findings hold beyond the original models.
