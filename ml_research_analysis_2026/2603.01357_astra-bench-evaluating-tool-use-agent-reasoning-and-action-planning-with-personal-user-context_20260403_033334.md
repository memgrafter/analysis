# ASTRA-bench: Evaluating Tool-Use Agent Reasoning and Action Planning with Personal User Context

## Quick Facts
- **arXiv ID**: 2603.01357
- **Source URL**: https://arxiv.org/abs/2603.01357
- **Reference count**: 25
- **Primary result**: ASTRA-bench reveals that state-of-the-art tool-use agents suffer significant performance degradation under high referential, functional, and informational complexity, with argument/payload generation identified as the primary bottleneck and stress conditions (insufficient context, misinformation) causing large task completion drops.

## Executive Summary
ASTRA-bench introduces a comprehensive benchmark for evaluating context-aware personal assistant agents. It combines time-evolving synthetic personal data (contacts, calendar, email, SMS, WhatsApp, phone logs) from five protagonists, an interactive tool sandbox with 25+ tools, and 2,413 human-authored scenarios spanning multiple complexity dimensions. The evaluation methodology centers on event-driven data generation from longitudinal storylines and verifiable milestones represented as a directed acyclic graph. Results show that even top-tier models like Claude-4.5-Opus and DeepSeek-V3.2 experience substantial performance declines as complexity increases. The primary bottleneck lies in generating correct tool arguments and payloads rather than retrieving relevant information. Stress tests that introduce insufficient context or misinformation further degrade performance, highlighting critical gaps in personal-context grounding and robust multi-step planning.

## Method Summary
ASTRA-bench assesses tool-use agents operating on a personal user context. The input consists of a longitudinal synthetic dataset generated through an event-driven pipeline: starting from a protagonist profile (bio, social graph, pattern-of-life grammar), a sequence of events is created; for each event, specialized LLM agents (Draft, Critique, Revise, Verify) produce cross-application artifacts (emails, messages, calendar entries, etc.) that maintain referential and temporal consistency. Human annotators then author 2,413 user goal scenarios, each annotated with complexity tiers (referential, functional, informational) and explicit success conditions encoded as milestone tasks (a DAG). During evaluation, the target agent receives a user query and must orchestrate tool calls within the ToolSandbox to achieve the goal. The agent's trajectory is evaluated automatically via milestone similarity (completion of required steps) and by an LLM judge that scores five axes (Task Completion, Tool Usage, Information Retrieval, Conversation Effectiveness, No Hallucination) on a 0–2 scale. Robustness is measured by additional stress scenarios with insufficient context or embedded misinformation.

## Key Results
- Macro task completion: Claude-4.5-Opus 0.9112, DeepSeek-V3.2 0.9050; scores drop significantly under high complexity dimensions.
- Step-level analysis shows the main bottleneck is argument/payload generation (~0.84) compared to retrieval (~0.95).
- Stress conditions cause large performance deteriorations (e.g., DeepSeek macro score decreases by 0.244).

## Why This Works (Mechanism)
The benchmark’s strength lies in its tight integration of longitudinal personal data with a rich toolset and multi-step evaluation. Event-driven generation ensures that artifacts naturally evolve over time and remain consistent across applications, mirroring real user environments. The use of verifiable milestone DAGs provides an objective grounding for success, while the LLM judge captures nuanced aspects like conversational effectiveness and hallucination. By varyingly combining referential (entity count), functional (tool chain depth), and informational (context length) complexity, the benchmark isolates specific failure modes. The controlled introduction of stress factors (missing context, misinformation) further tests robustness. This multifaceted design yields a reliable, reproducible diagnosis of agent capabilities and limitations in personal-context scenarios.

## Foundational Learning
- **Tool-use agents**: Agents that can call external functions/tools to act on behalf of a user. *Why needed*: The benchmark evaluates exactly this capability. *Quick check*: Can the agent correctly select and sequence tools to achieve a multi-step goal?
- **Personal context grounding**: Linking user data (contacts, messages, calendar) to the agent’s decisions. *Why needed*: Core of the benchmark; agents must reason over evolving personal information. *Quick check*: Does the agent retrieve and use correct personal details (e.g., a meeting time) when relevant?
- **Multi-step planning**: Decomposing a user request into a sequence of tool invocations. *Why needed*: Scenarios often require multiple dependent actions. *Quick check*: Does the agent produce a coherent plan and execute it in the right order?
- **Longitudinal synthetic data generation**: Automatically creating time-ordered user artifacts that reflect a realistic life pattern. *Why needed*: Provides the personal context backbone. *Quick check*: Are generated emails, events, etc., temporally consistent and entity-consistent?
- **LLM-as-judge evaluation**: Using large language models to score agent behavior along multiple dimensions. *Why needed*: Enables scalable, fine-grained assessment where automated metrics are insufficient. *Quick check*: Does the judge assign low scores to obviously flawed trajectories (e.g., hallucinated facts) and high scores to perfect ones?
- **Complexity dimensions (referential, functional, informational)**: Taxonomic axes to measure scenario difficulty. *Why needed*: Allows diagnosing which aspects challenge agents the most. *Quick check*: Do agents’ scores systematically decrease as the number of entities (referential), tool depth (functional), or context length (informational) increases?

## Architecture Onboarding
**Component map**: Protagonist generator (bio, social graph, PoL) -> Event generator -> Cross-app artifact agents (Draft -> Critique -> Revise -> Verify) -> Synthetic data store -> Scenario authoring (human) -> Evaluation runner -> Agent under test -> ToolSandbox -> Milestone scorer & LLM judge -> Results.

**Critical path**: For a given scenario, the agent must interpret the user query, retrieve relevant context from the synthetic store, plan a sequence of tool calls, correctly execute each tool with accurate arguments (payload), and finally achieve the milestones defined in the DAG. The most fragile steps are argument generation and maintaining referential integrity across tools.

**Design tradeoffs**: 
- Synthetic vs. real data: Synthetic data provides controlled, scalable, privacy-safe context but may lack noise and edge cases of real user data. 
- Automated (LLM judge) vs. human evaluation: Automated scoring allows large-scale testing but risks misalignment with true quality; LLM judge is cheaper but requires careful prompt engineering. 
- Milestone DAG provides objective metrics but may not capture all aspects of a successful interaction (e.g., conversational nuance).

**Failure signatures**: 
- Artifact incoherence: mismatched entities (e.g., an email refers to a contact that does not exist). 
- Milestone DAG mismatch: agent’s trajectory does not cover required steps or includes extra incorrect steps. 
- LLM judge inconsistency: same trajectory yields divergent scores across runs. 
- Time resolution bugs: relative time expressions (e.g., “next Friday”) incorrectly canonicalized.

**First three experiments**:
1. Validate the synthetic data generation pipeline by comparing artifact counts per domain (e.g., number of contacts, emails) against Table S1 from the paper.
2. Measure inter-annotator agreement on scenario complexity labeling to confirm the distribution matches Table 2.
3. Run a baseline model (e.g., GPT-4) on a small set of scenarios and verify that its macro task completion score lies in the expected range (around 0.95) before proceeding to full evaluation.

## Limitations
- The benchmark code, data, and generation scripts are not publicly released, preventing independent replication.
- Critical implementation details (LLM prompts, temperatures for generation and judging, complexity thresholds, annotation protocols) are omitted.
- The evaluation relies on self-reported metrics without external validation; the LLM judge’s alignment with human judgment is not quantified.

## Confidence
- Model degradation under high complexity: Medium confidence (supported by reported scores but metrics lack transparency).
- Argument/payload generation bottleneck: Medium confidence (step-level scores provided, but similarity metric unspecified).
- Stress test performance drops: Medium confidence (specific deltas given, but scenario construction not auditable).
