# LLM-Guided Lifecycle-Aware Clustering of Multi-Turn Customer Support Conversations

## Quick Facts
- **arXiv ID:** 2601.04388
- **Source URL:** https://arxiv.org/abs/2601.04388
- **Reference count:** 27
- **Primary result:** Deployed on 90k+ chats, improves Silhouette Score by over 100% and reduces Davies-Bouldin Index by 65.6% compared to baselines, enabling stable, real-time analytics that handles 500+ new concerns daily.

## Executive Summary
This paper tackles a critical limitation of static clustering methods for multi-turn cloud support conversations: their inability to handle overlapping, evolving user concerns, which leads to degraded cluster quality and disruptive full re-clustering. The proposed solution introduces a lifecycle-aware system that uses LLMs to segment chats into distinct, service-specific concerns, applies contrastive filtering to remove intra-chat duplicates, and performs localized clustering within service groups. New concerns are incrementally assigned via a hybrid embedding+LLM matching scheme. A continuous monitoring loop detects cluster drift using internal metrics and triggers targeted, LLM-guided splits without global re-clustering, preserving longitudinal stability. Deployed on over 90,000 real chats, the system demonstrates substantial improvements in clustering validity and operational scalability.

## Method Summary
The pipeline begins by processing multi-turn chats with an LLM to extract non-overlapping "themes" and then granular "concerns." Within each chat, near-duplicate concerns are removed using a high cosine similarity threshold (0.95) on sentence embeddings to prevent overweighting repetitive phrasing. Each concern is classified into one of seven predefined service groups (e.g., Billing, Compute) via few-shot LLM prompting. Clustering is then performed *locally* within each service group: embeddings are reduced via UMAP and clustered with HDBSCAN. For daily incremental updates, new concerns are matched to existing clusters through a two-stage process: first, a centroid-based cosine similarity shortlist (top-5), then LLM confirmation for precise assignment. A lifecycle manager periodically recomputes cluster-level metrics (DBI, Silhouette, cohesion Z-score). Clusters exhibiting degradation (e.g., Z-score ≥ 2) are split by an LLM; candidate merges are identified by high centroid similarity (>0.92) and validated by an LLM; stale clusters are pruned. This adaptive loop maintains cluster coherence and identity over time without full re-clustering.

## Key Results
- Clustering quality metrics improved substantially: Silhouette Score increased by over 100% and Davies-Bouldin Index decreased by 65.6% compared to non-adaptive baselines (KMeans+BERT, HDBSCAN-only).
- The system processes 500+ new concerns daily with high assignment accuracy, demonstrating operational scalability.
- Over 90 days, the lifecycle manager triggered 61 cluster splits, successfully correcting topic drift while preserving stable cluster identities for longitudinal analytics.

## Why This Works (Mechanism)

### Mechanism 1
**Claim:** Segmenting multi-turn chats into discrete, service-specific concerns via LLMs and removing intra-chat duplicates with contrastive filtering produces cleaner, more semantically coherent inputs for clustering than using raw chat logs or whole-session embeddings.
- **Mechanism:** An LLM detects topic shifts to extract "themes," then extracts granular "concerns" from each theme. A high-threshold (0.95) cosine similarity filter on `nli-roberta-base-v2` embeddings removes near-duplicate concerns *within the same chat session*, preventing a single user's repetitive phrasing from overweighting a cluster. Distinct concerns across different chats are preserved.
- **Core assumption:** The semantic similarity threshold effectively separates true duplicate expressions from distinct but related issues within a session, and the embedding model captures necessary nuance.
- **Evidence anchors:**
  - [abstract] "segments chats into distinct, service-specific concerns using LLMs, applies contrastive filtering to remove duplicates"
  - [Section 3.1, P3] Threshold = 0.95; filtering applied within each multi-turn chat to prevent overweighting paraphrased repetitions; identical concerns across chats are preserved.
  - [ablation] Quality degrades when filtering is removed.
- **Break condition:** Threshold too low merges distinct concerns; too high leaves redundant paraphrases, distorting cluster density.

### Mechanism 2
**Claim:** A hybrid two-stage incremental assignment (embedding similarity shortlist + LLM semantic confirmation) allows new concerns to be integrated into existing clusters accurately and efficiently without full re-clustering, preserving cluster identity and stability.
- **Mechanism:** For a new concern, its embedding is compared to precomputed cluster centroids within its service group; the top-5 most similar clusters are shortlisted. An LLM then selects the best match from this shortlist based on natural language understanding. Unmatched concerns accumulate for potential new cluster formation.
- **Core assumption:** The embedding model provides sufficient recall to include the correct cluster in the top-5, and the LLM can precisely disambiguate between shortlisted clusters, handling nuanced or emerging topics.
- **Evidence anchors:**
  - [abstract] "New concerns are incrementally assigned via hybrid embedding+LLM matching."
  - [Section 3.2, P4-5] Hybrid approach improves precision for edge cases, emerging topics, and ambiguous inputs.
  - [Appendix N.3 / Table 18] Ablation: replacing LLM confirmation with embedding-only matching degrades Silhouette (0.72 → 0.53) and DBI (0.46 → 0.81).
- **Break condition:** Embedding recall fails (correct cluster not in top-5) or LLM makes erroneous selections on ambiguous shortlists, causing misassignment and drift.

### Mechanism 3
**Claim:** Continuous monitoring of cluster-level internal metrics (DBI, Silhouette, Cohesion Z-score) enables targeted, LLM-guided splitting of only degraded clusters, correcting topic drift while minimizing disruption and preserving longitudinal continuity of stable clusters.
- **Mechanism:** After each incremental batch, service-group DBI and Silhouette are computed. A cluster is flagged if its group's DBI > 0.5 or Silhouette < 0.5. For flagged clusters, a Centroid-Based Cohesion Score (average distance to centroid) is computed and its Z-score against historical values is calculated. A Z-score ≥ 2 triggers an LLM-based split, reassigning concerns into new, semantically coherent sub-clusters.
- **Core assumption:** The defined thresholds reliably detect "drift" correlating with human-judged loss of coherence, and an LLM can perform semantic splitting effectively.
- **Evidence anchors:**
  - [abstract] "Cluster quality is continuously monitored; degraded clusters... are split using LLMs without full re-clustering."
  - [Section 3.4, P5] Thresholds: DBI > 0.5 or Silhouette < 0.5 for service group; Z ≥ 2 for cluster split.
  - [Section 4.4 & 4.7] 61 splits over 90 days; qualitative examples show improved coherence (e.g., splitting broad "billing" into specific sub-issues).
- **Break condition:** Thresholds too sensitive cause unnecessary splits; too insensitive allow significant drift. LLM splitting might create incoherent sub-clusters if prompt or model capability is insufficient.

## Foundational Learning

- **Concept: Clustering Validity Metrics (Davies-Bouldin Index, Silhouette Score)**
  - **Why needed here:** The adaptive system relies on these metrics to quantitatively detect cluster degradation (drift). DBI measures compactness and separation (lower is better); Silhouette measures how similar an object is to its own cluster vs. others (higher is better). Operational thresholds (DBI>0.5, Silhouette<0.5) trigger corrective actions.
  - **Quick check:** If a cluster's Silhouette drops from 0.75 to 0.45 and DBI rises from 0.3 to 0.6 after incremental updates, this indicates significant loss of coherence and separation; the system would flag it for potential split if its service-group metrics cross thresholds and its cohesion Z-score ≥ 2.

- **Concept: Density-Based Clustering (HDBSCAN) and Dimensionality Reduction (UMAP)**
  - **Why needed here:** These form the core unsupervised techniques for initial "base clusters" and incremental updates within service groups. HDBSCAN discovers clusters of varying density without pre-specifying *k*. UMAP reduces embedding dimensions while preserving semantic structure, which is crucial for HDBSCAN's performance in high-dimensional spaces.
  - **Quick check:** Applying HDBSCAN directly to 768-dimensional embeddings may lead to poorer quality due to the "curse of dimensionality" where distance metrics become less meaningful. UMAP first projects embeddings into a lower-dimensional manifold (e.g., 10-50 dimensions) that better captures semantic neighborhoods, improving HDBSCAN's density estimation and cluster separation.

- **Concept: Few-Shot LLM Prompting for Classification and Generation**
  - **Why needed here:** LLMs are used for deterministic tasks: segmenting chats, extracting concerns, classifying into service groups, labeling clusters, splitting/merging clusters, and generating narratives. Few-shot prompts provide examples to steer the model toward consistent, domain-aware outputs.
  - **Quick check:** Risks for the service group assignment task include inconsistency due to ambiguous phrasing, hallucination of non-existent groups, or bias from few-shot examples. The paper mitigates these by using a fixed set of 7 groups, providing clear definitions in the prompt, and validating assignments against metadata (e.g., if a concern mentions "VM" it should not go to "Billing").

## Architecture Onboarding

- **Component map:**
  Multi-turn Chat -> Preprocessing & Segmentation (LLM themes, LLM concerns, Contrastive Filter) -> Service Group Classifier (LLM) -> Base Clustering (Embedding Generator, UMAP, HDBSCAN, LLM Labeling) -> Cluster Centroids & Metadata Storage.
  New Chat -> Preprocessing & Segmentation -> Service Group Classifier -> Hybrid Assigner (Embedding shortlist + LLM confirmation) -> Update Affected Clusters.
  Periodic: Metric Monitor (DBI, Silhouette, Cohesion Z-score) -> Lifecycle Manager (LLM Split/Merge/Prune/Role Assign) -> Drift Narrative Gen (LLM).

- **Critical path:** The most frequent operational path is the **Incremental Pipeline**. A new chat enters, is segmented/filtered/classified, and its concerns are matched to existing clusters via the hybrid method. This path must be fast (seconds per chat) and stable to support real-time analytics.

- **Design tradeoffs:**
  - **Granularity vs. Stability:** Finer-grained extraction and lower similarity thresholds increase cluster count and potential Silhouette but raise fragmentation risk and merge/split frequency. System balances with service-group boundaries and merge/prune logic.
  - **Cost vs. Accuracy:** LLM-based semantic confirmation (Stage 2 assignment) and splitting add API cost/latency but are necessary for accuracy over pure embeddings (Table 5). The hybrid approach (LLM only on top-5) is a key efficiency tradeoff.
  - **Local vs. Global:** Clustering is performed *within* service groups (localized). This improves purity and interpretability but creates silos; a cross-service issue appears in multiple groups. Accepted tradeoff for domain-specific analytics.

- **Failure signatures:**
  - Sudden DBI spike / Silhouette drop in a single service group without change in others → likely topic drift in a major cluster within that group.
  - High "Others" service group classification error rate → extractor or classifier failing to resolve ambiguous queries (Appendix D shows "Others" has highest error).
  - Proliferation of very small clusters (<10 concerns) that persist → prune logic too conservative or merge thresholds too strict.
  - LLM split narratives becoming repetitive or vague → prompt degradation or model fatigue; may need prompt refresh.

- **First 3 experiments:**
  1. **Validate Base Clustering Quality:** Run Phase 1 pipeline on a held-out, manually labeled ~1,000 chats. Compute Silhouette/DBI. Manually inspect 20 random clusters/service group for coherence. Compare against baseline of clustering raw chat embeddings.
  2. **Test Incremental Assignment Accuracy:** Take a day's new concerns (e.g., 500). Simulate assignment via (a) pure cosine similarity to centroids, (b) proposed hybrid method. Have domain experts judge correctness for a random 100-sample. Calculate precision/recall; expect hybrid superior.
  3. **Simulate Drift and Trigger Split:** Identify a broad cluster (e.g., "Billing" from Appendix G). Artificially inject 50-100 new, divergent concerns. Monitor cohesion Z-score. Verify system triggers LLM split and resulting sub-clusters are more coherent (measured by intra-cluster similarity and manual review).

## Open Questions the Paper Calls Out

- **Question 1:** How can classification accuracy for ambiguous, compound, or cross-service concerns be improved, given "Others" and "Data Services" groups show highest misclassification rates (2.17% and 2.33%) due to vague language?
  - **Basis:** Limitations section: "Ambiguous or compound concerns spanning multiple services can still challenge classification." Appendix D shows 60% of misclassifications in these two groups.
  - **Why unresolved:** Current few-shot LLM classifier relies on semantic cues insufficient for under-specified queries. No proposed mechanisms for disambiguation (e.g., multi-label classification, extended dialogue analysis).
  - **What evidence would resolve:** Targeted study on misclassified samples to identify linguistic patterns. Experiments with enhanced prompts (e.g., probing for multi-service relevance) or auxiliary models. Business impact metrics (e.g., ticket escalation rates).

- **Question 2:** Do the fixed quality thresholds for triggering cluster refinement (DBI > 0.5, Silhouette < 0.5, Z-score ≥ 2) generalize across different service groups and temporal patterns, or are they overfitted to the 90-day enterprise dataset?
  - **Basis:** Algorithm 1 and Section 3.4 define thresholds. Paper reports 61 splits over 90 days but no cross-validation or sensitivity analysis.
  - **Why unresolved:** Thresholds are static heuristics. No investigation whether service groups with different semantic densities require different thresholds, or whether seasonal trends cause false positives/negatives. Role assignment also uses static criteria (e.g., 30-day inactivity).
  - **What evidence would resolve:** Retrospective analysis across multiple time windows or different datasets to measure false positive/negative rates of split/merge triggers. Ablation varying thresholds per service group. Longitudinal tracking of cluster stability under different regimes.

- **Question 3:** How faithfully does the released synthetic dataset capture linguistic diversity, noise, and edge cases of real-world conversations, given evaluation limited to macro clustering metrics (DBI, Silhouette)?
  - **Basis:** Section 5: synthetic data is "distributionally aligned"; macro metrics similar (Avg DBI: 0.48 vs. 0.46; Silhouette: 0.70 vs. 0.72). No fine-grained linguistic or error analysis.
  - **Why unresolved:** Macro metric similarity does not guarantee replication of critical failure modes (ambiguous phrasing, compound concerns, conversational phenomena like corrections). If synthetic data lacks these, it may not be a reliable testbed for evaluating improvements on core challenges.
  - **What evidence would resolve:** Detailed comparative analysis of error distributions (misclassification rates per service group, failed extraction types) on real vs. synthetic data. Human evaluation of synthetic conversation quality (fluency, multi-service coherence). Benchmarking full pipeline on synthetic vs. real data for split/merge events.

- **Question 4:** What are the practical scalability limits of the LLM-guided components (segmentation, extraction, splitting) in terms of cost and latency as chat volume grows by orders of magnitude, given cost estimates are for ~90k chats?
  - **Basis:** Appendix O: Base phase ~$61 for 90k chats; incremental ~$1.44/day for 500 chats; lifecycle ~$0.39/90 days. Presented as feasible but no stress-testing.
  - **Why unresolved:** Cost model assumes constant API pricing and linear scaling. Does not consider exponential cost growth, rate limits, or impact of longer chats on token counts. Real-time requirement for incremental updates not benchmarked under load.
  - **What evidence would resolve:** Benchmarking end-to-end latency at scale (e.g., 10k, 100k new chats/day). Cost projections under tiered API pricing or if local/open-source LLMs become necessary. Analysis of failure modes (timeouts, dropped updates) under high load.

- **Question 5:** Can the lifecycle management heuristics (merge threshold cos>0.92, prune after 30 days/10 concerns) be learned or adapted from data, rather than set empirically, to better balance cluster granularity and stability?
  - **Basis:** Sections 3.6 and 4.4: thresholds are empirical choices (e.g., "cosine similarity above a threshold (empirically set at 0.92)"). Merge example shows LLM validation, but candidate selection is rule-based.
  - **Why unresolved:** No exploration whether these thresholds optimally trade off fragmentation vs. coherence across domains. Static 30-day prune window might prematurely retire seasonal clusters or retain obsolete ones. Role assignment uses fixed criteria without learning from historical transitions.
  - **What evidence would resolve:** Analysis of merge/prune outcomes to find correlation between threshold values and post-operation metric improvements (∆Silhouette, ∆DBI). Using reinforcement learning or Bayesian optimization to learn per-group thresholds. Tracking role transition sequences against business outcomes (e.g., issue resolution time).

## Limitations
- Exact LLM prompts (Appendix Q) and clustering hyperparameters (UMAP/HDBSCAN settings) are unreported, blocking faithful replication and potentially explaining performance variance.
- Static quality thresholds (DBI>0.5, Silhouette<0.5, Z≥2) and lifecycle criteria (30-day prune) are empirically set without validation of generalizability across service groups or temporal patterns.
- The system's reliance on LLMs for core tasks introduces sensitivity to prompt design, model version, and cost/latency, with no discussion of fallback strategies if API performance degrades.

## Confidence
- **High:** Hybrid incremental assignment efficacy (backed by ablation and deployed metrics).
- **Medium:** Lifecycle monitoring & split triggers (logic described, but threshold justification and long-term stability depend on unstated parameters).
- **Low:** Base clustering quality from segmentation + contrastive filtering (core steps lack reproducibility details; performance may be dataset/prompt-sensitive).
