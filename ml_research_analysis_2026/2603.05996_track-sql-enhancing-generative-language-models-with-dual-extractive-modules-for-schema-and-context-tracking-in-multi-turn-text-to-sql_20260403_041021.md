# Track-SQL: Enhancing Generative Language Models with Dual-Extractive Modules for Schema and Context Tracking in Multi-turn Text-to-SQL

## Quick Facts
- **arXiv ID:** 2603.05996  
- **Source URL:** https://arxiv.org/abs/2603.05996  
- **Reference count:** 35  
- **Primary result:** Achieves state-of-the-art multi-turn Text-to-SQL, improving interaction match execution accuracy by 7.1% on SparC and 9.55% on CoSQL.

## Executive Summary
Track-SQL addresses multi-turn Text-to-SQL by decoupling schema linking and context filtering from SQL generation via two specialized extractors. The Semantic-enhanced Schema Extractor (SESE) resolves ambiguities in schema references using LLM‑generated semantic annotations and a gating mechanism. The Schema-aware Context Extractor (SACE) selects the most relevant historical SQL queries based on semantic similarity and schema distribution overlap. The cleaned inputs are then fed to a fine‑tuned generative language model, which produces the target SQL. Evaluated on SparC and CoSQL, Track-SQL achieves state-of-the-art performance; ablation studies confirm that both extractors are essential, delivering improvements of 7.1% in interaction-match execution accuracy on SparC and 9.55% on CoSQL. The framework notably reduces error propagation in long dialogues and handles coreference/ellipsis more robustly than prior work.

## Method Summary
Track-SQL processes a multi-turn dialogue as follows: For each turn, SESE scores all tables and columns in the database schema using a RoBERTa encoder. Schema items are semantically annotated by an LLM (GPT-3.5-turbo) offline; at runtime, a gating mechanism combines the original embedding with the annotated description embedding, weighted by learned attention. Scores are thresholded (s=0.1) to produce the extracted schema E(S). SESE also detects when the user intends to select all columns (ACID). In parallel, SACE retrieves the most relevant historical SQL by combining question-level semantic similarity (SentenceBERT) with a Jensen‑Shannon divergence between the schema probability distributions of past and current turns. The top‑k historical SQL is designated SQL_base.

The final prompt for the SQL generator concatenates the full multi‑turn questions (joined by “&”), the textual representation of E(S), and SQL_base. A generative LLM (e.g., DeepSeek‑7B) is fine‑tuned with LoRA to minimize the standard language modeling loss on these prompts. During inference, the generated SQL is stored in history stores for subsequent turns, and a fixed‑length sliding window (size 5) prunes older entries to control context length. This design offloads the burden of schema selection and context filtering from the LLM, enabling it to focus on synthesizing correct SQL.

## Key Results
- Track-SQL achieves state-of-the-art interaction match (IM) execution accuracy on SparC and CoSQL benchmarks.
- Reported gains: +7.1% IM-EX on SparC, +9.55% IM-EX on CoSQL over prior baselines.
- Ablation studies reveal that removing either SESE or SACE degrades performance significantly, confirming their complementary roles.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Track-SQL improves multi-turn Text-to-SQL by dynamically linking database schemas specific to each turn, reducing ambiguity from reused or vague column/table names.
- **Mechanism:** The Semantic-enhanced Schema Extractor (SESE) uses LLM-generated semantic annotations for schemas and a gating mechanism to weigh original schema names against their augmented descriptions. This resolves naming ambiguities (e.g., `continent` in `Countries` vs. `Continents`). It also tags previously extracted schemas from earlier turns (`[SN]`) to maintain dialogue continuity.
- **Core assumption:** Semantic augmentation from an LLM can align user question intent with database element meanings more accurately than raw schema names alone, especially for abbreviations or overloaded terms.
- **Evidence anchors:**
  - [abstract] "Semantic-enhanced Schema Extractor (SESE) dynamically links database schemas using semantic augmentation from LLM-generated annotations to resolve ambiguities."
  - [section 2.2] Details the annotation generation via GPT-3.5-turbo and the attention gating mechanism (Eq 1-4) for combining original and annotated embeddings.
  - [corpus] Neighbor papers (e.g., "Rethinking Schema Linking") also identify schema linking as critical, but Track-SQL specifically targets *dynamic* linking in multi-turn settings with semantic enrichment.
- **Break condition:** If LLM-generated annotations are inconsistent or irrelevant for the domain, the gating mechanism may fail to resolve ambiguity, leading to incorrect schema extraction.

### Mechanism 2
- **Claim:** Track-SQL selects the most relevant historical SQL queries to guide current generation, mitigating error propagation and irrelevant context in long dialogues.
- **Mechanism:** The Schema-aware Context Extractor (SACE) scores past turns (`Q_h`) against the current question (`Q_m`) using two signals: 1) semantic similarity of questions (`S_sim_h` via SentenceBERT) and 2) overlap in extracted schema item probability distributions (`P_sim_h` via Jensen-Shannon divergence). The top-ranked historical SQL (`SQL_base`) is provided as a prompt to the generator.
- **Core assumption:** Questions with similar wording or referencing similar database entities (schema distributions) are likely to have related SQL structures, and providing a correct `SQL_base` simplifies the current generation task.
- **Evidence anchors:**
  - [abstract] "Schema-aware Context Extractor (SACE) selects relevant historical SQL queries based on semantic similarity and schema distribution overlap to guide current generation."
  - [section 2.3] Formally defines the combined relevance score `R_h = S_sim_h + (1 - P_sim_h)` and the retrieval process.
  - [corpus] Neighbor work (e.g., "QURG: Question Rewriting...") also uses context rewriting, but Track-SQL uses direct SQL retrieval with schema-aware scoring rather than question reformulation.
- **Break condition:** If the highest-scoring historical SQL is structurally erroneous (e.g., missing joins), it will mislead the generator. The paper notes this risk and implies mitigation via the schema extractor's filtering, but doesn't fully eliminate it (see ablation where SACE removal hurts performance, but "Extra" difficulty samples show degradation).

### Mechanism 3
- **Claim:** By offloading schema linking and context filtering to specialized extractors, Track-SQL reduces the input complexity for the core SQL generator, allowing it to focus on core SQL synthesis.
- **Mechanism:** The framework transforms the multi-turn input (`Q_≤m`, full schema `S`) into a compact, filtered representation: `E(S)` (relevant schemas) + `SQL_base` (relevant history) + `Q_≤m` (concatenated questions). The generator (fine-tuned LLM) sees less noise and more precise constraints.
- **Core assumption:** Generative LLMs struggle with raw, untamed multi-turn inputs due to their length and irrelevance; pre-filtering key information is more effective than expecting the LLM to learn these filtering skills implicitly during generation.
- **Evidence anchors:**
  - [section 2.1] "To reduce the difficulty for the generative language model to learn schema linking and context information filtering."
  - [section 2.4] The training loss `L(M^*(ε(Q_≤m, E(S), SQL_base, s_m)))` explicitly uses the extracted inputs.
  - [ablation Tables 2,3] Removing either extractor degrades multi-turn metrics (IM-EX/TS), confirming the utility of pre-processing.
- **Break condition:** If either extractor makes a critical error (false negative on a needed schema, or selecting a misleading `SQL_base`), the generator is constrained with incorrect information, and the error is baked into the output.

## Foundational Learning

### Multi-turn Text-to-SQL Challenges
- **Why needed here:** Track-SQL explicitly targets the drop in performance when moving from single-turn to multi-turn dialogues. Understanding why this drop occurs (context drift, schema ambiguity over turns) is prerequisite to evaluating the solution.
- **Quick check question:** In a dialogue "List students. / And their pets?", why might a single-turn model fail on turn 2 without context?

### Schema Linking as a Dedicated Sub-Task
- **Why needed here:** Track-SQL's core innovation is decoupling schema selection from SQL generation. An engineer must understand that "linking" means identifying which tables/columns in a large DB are relevant to the current question.
- **Quick check question:** For "Show continent names" on a DB with `Countries(continent)` and `Continents(continent)`, what is the linking ambiguity?

### Semantic Similarity Metrics for Retrieval (SentenceBERT, JSD)
- **Why needed here:** SACE's functionality depends on these metrics to score historical context. An engineer needs to know their purpose (dense vs. distributional similarity) and limitations (e.g., SentenceBERT may miss structural SQL similarity).
- **Quick check question:** Why might two questions with different wording ("Which countries have cats?" vs. "List nations with felines as pets.") have high `S_sim_h` but require different `SQL_base` if the DB schema changed between turns?

### Supervised Fine-Tuning (SFT) of LLMs with Structured Prompts
- **Why needed here:** The final SQL generator is a fine‑tuned 7B LLM (CodeLlama/DeepSeek/Mistral). Onboarding requires understanding how the extracted information (`E(S)`, `SQL_base`) is formatted into the LLM's input and how LoRA enables efficient adaptation.
- **Quick check question:** How does concatenating multi‑turn questions with `&` differ from simple space‑separation, and why might it matter for an LLM's attention?

## Architecture Onboarding

**Component Map:**
Input (multi-turn questions Q₁..Qₘ, full database schema S, history stores) → SESE → extracted schema E(S) → SACE → selected historical SQL_base → SQL Generator (SFT LLM) → output SQL sₘ. History stores are updated with sₘ after each turn and provide both extracted schemas and past question‑SQL pairs to SESE and SACE.

SESE: consumes Q_≤m, S, and tags from History Schema Store → outputs E(S) (top‑m schema items with probability > s=0.1). Sub‑components: offline LLM annotation generator, RoBERTa encoder with pooling, semantic enhancement gating, all‑column intent detector.

SACE: consumes E(S), History Schema Store (past ÌYₕ), and History Question&SQL Store (past Qₕ, SQLₕ) → computes question semantic similarity (SentenceBERT) and schema distribution similarity (JSD), combines them into Rₕ, and retrieves top‑k SQL_base.

SQL Generator: fine‑tuned LLM (e.g., DeepSeek‑7B) receives formatted prompt (Q_≤m concatenated with “&”, E(S) in text, SQL_base) → generates normalized sₘ. Trained via standard language modeling loss with LoRA.

History Management: after generation, sₘ is appended to the respective stores; a fixed sliding window (size 5) discards oldest entries.

**Critical Path:**  
For turn m: (Qₘ, S, History) → **SESE** → E(S) → **SACE** → SQL_base → **SQL Generator** → sₘ → Update History.

**Design Tradeoffs:**
- **RoBERTa window limit (512 tokens):** Forces column‑level schema segmentation for large DBs, adding complexity. Using a decoder‑only model (longer context) was attempted but failed (Limitations section), trading off capacity for manageable context.
- **LLM annotation dependency:** SESE's semantic boost relies on GPT‑3.5‑turbo quality. This introduces cost, latency, and potential annotation errors propagating to extraction.
- **Fixed threshold `s=0.1`:** A single threshold for all samples balances precision/recall but may not be optimal for all DBs or question types.
- **SACE's error propagation risk:** Selecting a bad `SQL_base` (from a previous generation error) can hurt current turn. The paper uses syntactic validation but doesn't fully eliminate it.

**Failure Signatures:**
- **SESE failure:** High Table/Column Redundancy Scores (`TRS@s`, `CRS@s`) indicate extraction noise. Symptoms: generated SQL references wrong tables/columns or misses critical ones.
- **SACE failure:** Low improvement in IM metrics when SACE is removed, especially on longer dialogues (>4 turns). Symptoms: generated SQL ignores coreference ("those", "it") or repeats past errors.
- **ACID failure:** Incorrect handling of `*` (all‑columns) intents, seen in case studies. Symptom: SQL selects specific columns when `SELECT *` is intended, or vice‑versa.

**First 3 Experiments:**
1. **Reproduce main results (Table 1):** For a given base LLM (e.g., DeepSeek‑7B), run full Track‑SQL pipeline on SparC/CoSQL dev sets. Verify IM‑EX/TS improvements over baseline (~+7% on SparC, +9.5% on CoSQL).
2. **Ablation - SESE component:** Disable semantic enhancement (remove LLM annotations and gating) and/or all‑column intent detection. Measure degradation in schema extraction metrics (`TRS@0.5`, `CRS@0.5` from Table 4) and downstream SQL generation metrics (IM‑TS from Tables 2,3). Expect significant drop, confirming SESE's role.
3. **Ablation - SACE component:** Disable SACE (set `SQL_base` empty). Compare performance on turns with high coreference/ellipsis (e.g., turn >2). Expect larger drop on IM metrics vs QM (Tables 2,3), showing SACE's value for context. Also, inspect case studies like Table 12, Case#1 to see missing foreign‑key joins.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** Does Track‑SQL's reliance on RoBERTa for schema extraction, with its 512‑token limit, fundamentally limit its scalability to large schemas or long dialogue histories, and can decoder‑only models with longer contexts be effectively adapted for this classification task?
- **Basis in paper:** [explicit] The Limitations section (Page 10) states: "using RoBERTa as the base model limits the maximum window length to 512, which increases the training time for handling large volumes of text data; even with an A800 (80G) GPU‑equipped machine, training on the SparC dataset takes two days. We attempted to replace RoBERTa with a decoder‑only model that supports a larger window size for classifier training, but the results were unsatisfactory."
- **Why unresolved:** The authors identify this as a key limitation but do not explore *why* the decoder‑only model attempt failed or propose concrete solutions, leaving the path to scalability unclear.
- **What evidence would resolve it:** A systematic study comparing various encoder/decoder architectures (e.g., Longformer, BigBird, modern LLMs) for the schema extraction classification task, analyzing performance vs. context length trade‑offs. Successfully training an effective long‑context extractor and measuring its impact on overall SQL generation accuracy on datasets with larger schemas or longer dialogues would resolve this.

### Open Question 2
- **Question:** How robust is the Schema‑aware Context Extractor (SACE) to error propagation when the historical "base SQL" it retrieves is syntactically valid but semantically incorrect, and can the SQL validation step be enhanced to detect more than just syntactic errors?
- **Basis in paper:** [explicit] Page 4, Section 2.3: "This strategy of employing historical SQL as prompt generation exhibits inherent limitations: when structural errors exist in historically generated statements, erroneous prompts may trigger cascading error propagation... To mitigate this, SACE incorporates syntactic error detection in historical SQL generation to reduce error transmission." Page 8, Ablation studies: "removing SACE module resulted in performance degradation... This phenomenon indicates that under relatively high model accuracy conditions, the SACE module significantly enhances the completeness of multi‑turn SQL generation. Notably, the marginal effects revealed in Appendix A.1.1 demonstrate that when query difficulty escalates to EXTRA levels, SACE inadvertently induces error propagation."
- **Why unresolved:** The paper acknowledges error propagation as a limitation and notes it worsens on extra‑hard queries, but the syntactic validation is likely insufficient for semantic errors. The exact failure modes and a more robust verification mechanism (e.g., lightweight execution on sample data, logical form checking) are not explored.
- **What evidence would resolve it:** A detailed error analysis categorizing the types of errors in retrieved base SQL (syntax vs. logic vs. wrong tables/columns) and correlating them with failures in subsequent turns. Implementing and testing a more sophisticated validation (e.g., checking for empty result sets, constraint violations) and measuring its impact on reducing error propagation, especially for complex queries, would provide evidence.

### Open Question 3
- **Question:** To what extent does the performance of Track‑SQL depend on the quality and style of the LLM‑generated (GPT‑3.5‑turbo) schema annotations, and can the framework be made less dependent on a specific, external LLM?
- **Basis in paper:** [inferred] The Semantic‑enhanced Schema Extractor (SESE) relies on "open‑domain semantic knowledge, combining database content with large language models (LLMs) to enrich the semantic information of column names" (Page 3). The prompts for annotation are in Appendix B.2. However, the cost, variability, and potential biases of using a proprietary LLM like GPT‑3.5 are not discussed as a limitation. The "Implementation Details" (Page 5) states they "utilized the GPT‑3.5‑turbo model" but does not analyze sensitivity to the choice of annotator model.
- **Why unresolved:** This is an unstated assumption. The framework's semantic enhancement is critical for reducing ambiguity, but its effectiveness is tied to the annotation quality. If a different LLM or a cheaper/faster model produced inferior annotations, Track‑SQL's gains might diminish. The paper does not evaluate this sensitivity.
- **What evidence would resolve it:** An ablation where the LLM used for annotation is varied (e.g., GPT‑4, Claude, open‑source LLMs like Llama, or even rule‑based methods), measuring the change in SESE's schema extraction accuracy and the final SQL generation performance on the same datasets. This would show if the gains are robust to annotation source or tied to GPT‑3.5's specific capabilities.

### Open Question 4
- **Question:** Does the fixed, small context window (Lw = 5 turns) in the context expansion management strategy become a bottleneck for very long, coherent dialogues, and would a more sophisticated, content‑aware history pruning mechanism (e.g., based on relevance decay or coreference chains) improve performance?
- **Basis in paper:** [explicit] Page 5, Implementation Details: "For context expansion management, we designed: • A fixed‑length sliding window (Lw = 5) • A queue‑based update rule..." The paper does not justify the choice of 5 or test other window sizes.
- **Why unresolved:** The ablation by turn (Tables 8 & 9) shows that SACE's benefit continues for more turns (e.g., >4 turns in CoSQL), suggesting that longer contexts can be helpful. However, the fixed window might arbitrarily discard earlier but still relevant context. The queue‑based rule is simple and may not respect discourse coherence.
- **What evidence would resolve it:** Experiments varying the window size (e.g., 3, 5, 10, 15) on datasets with longer dialogues. More importantly, implementing and comparing against a dynamic pruning strategy (e.g., using the SACE relevance score Rh to keep only the most relevant historical turns, regardless of recency) and measuring the impact on multi‑turn accuracy for dialogues exceeding 5 turns.

### Open Question 5
- **Question:** How does the "all‑column intent detection" (ACID) module's limited performance gains (as noted in ablation studies) relate to the actual frequency and nature of such intents in the benchmarks, and could a more nuanced modeling of implicit user intent (beyond the wildcard '*') yield larger improvements?
- **Basis in paper:** [explicit] Page 8, ACID ablation: "removing this module resulted in decreases of 0.89% and 0.34% in QM‑TS and IM‑TS respectively... This phenomenon suggests that the EX evaluation metrics contain a higher proportion of false positive samples... the optimization effect of this strategy on the overall performance... demonstrates metric sensitivity characteristics. Final experimental data confirm that this module yields only limited performance gains in real‑world application scenarios." Page 9, case study: ACID examples are simple "SELECT * FROM table".
- **Why unresolved:** The authors attribute limited gains to metric sensitivity and perhaps low prevalence of true "all‑column" intents. However, user intent is often more complex—e.g., "show me everything about X" might semantically require all columns but could be expressed in many ways not captured by a simple '*' prediction. The module's binary classification for '*' per table seems simplistic.
- **What evidence would resolve it:** An error analysis specifically quantifying how often users intend to retrieve all columns from a table in the datasets (via manual annotation or analyzing gold SQLs). Then, developing a more sophisticated intent detector (e.g., using the LLM's own decoding probabilities or a separate classifier trained on diverse paraphrases of "show all") and measuring if it leads to significant gains, especially in EM/EX metrics.

## Limitations
- RoBERTa's 512‑token window forces column‑level segmentation and hinders scalability; attempts with decoder‑only models failed.
- Dependency on GPT‑3.5‑turbo for schema annotations introduces external cost, latency, and potential error propagation.
- SACE can propagate errors when the selected historical SQL is syntactically correct but semantically wrong, especially on Extra‑hard queries.

## Confidence
- Main outcome (SOTA gains): **High**
- Mechanism 1 (SESE disambiguation): **Medium**
- Mechanism 2 (SACE context selection): **Medium**
- ACID all‑column intent detection: **Low**
