# MAS-on-the-Fly: Dynamic Adaptation of LLM-based Multi-Agent Systems at Test Time
## Quick Facts
*   **arXiv ID:** 2602.13671
*   **Source URL:** https://arxiv.org/abs/2602.13671
*   **Reference Count:** 19
*   **Primary Result:** MASFly achieves a 61.7% final pass rate on TravelPlanner, substantially outperforming prior methods (~32%) and demonstrating robust test-time adaptation across multiple benchmarks.

## Executive Summary
LLM-based multi-agent systems (MAS) are typically static after deployment, limiting their ability to handle novel or erroneous test-time queries. This paper introduces MASFly, a framework that enables dynamic, on-the-fly adaptation without parameter training. It constructs a query-specific agent system by retrieving and instantiating past successful collaboration patterns (SOPs) from a repository. During execution, a dedicated Watcher agent monitors the system using a personalized pool of past failure experiences, enabling real-time interventions like corrective feedback or agent replacement. A post-execution reflection loop continuously distills new successes into the SOP repository and updates the failure pool. Evaluations on TravelPlanner, GAIA, and coding benchmarks show significant improvements over baselines and robustness to adversarial prompts.

## Method Summary
MASFly operates in three stages at test time. First, for a new query, it analyzes the task needs, retrieves relevant Standard Operating Procedure (SOP) templates from a repository via a hybrid similarity score (combining query and need-analysis embeddings), and uses an LLM to instantiate these into a task-specific Operational Procedure (OP) defining agent roles, tools, and communication. Second, this MAS executes while a global Watcher agent continuously monitors inter-agent messages and tool interactions against the OP and a Personalized Experience Pool (PEP) of past failure modes; the Watcher can send corrective feedback or replace underperforming agents. Third, after execution (with ground truth access on training data), an LLM reflects: successful runs generalize the OP into a new SOP for the repository, while failures diagnose root causes and update the PEP. This creates a closed-loop system that improves over time without gradient-based training.

## Key Results
*   On the TravelPlanner benchmark, MASFly achieves a **61.7% final pass rate**, significantly surpassing prior state-of-the-art methods (~32%) and several strong ablations.
*   It demonstrates strong generalization, achieving competitive results on GAIA (Levels 1-3), HumanEval, and MBPP Pro, while maintaining near-original accuracy under adversarial prompt attacks that cripple static MAS.
*   Ablation studies confirm the critical contributions of both the SOP-guided generation (removing it causes major drops) and the Watcher supervision (removing it harms robustness and final performance).

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** MASFly dynamically adapts the multi-agent system structure (agent roles, tools, communication topology) to each query at test time without training.
*   **Mechanism:** A retrieval-augmented SOP instantiation process selects relevant past successful collaboration patterns (SOPs) from a repository. An LLM then "expresses" these retrieved templates into a new, query-specific operational procedure (OP) that defines the agent team and their workflow.
*   **Core assumption:** Successful past solutions contain reusable structural knowledge (agent roles, tool assignments, interaction patterns) that can be adapted to novel but related queries.
*   **Evidence anchors:**
    *   [abstract] "retrieval-augmented SOP instantiation mechanism that leverages a self-constructed repository of successful collaboration patterns, enabling the LLM to assemble customized MASs for new queries."
    *   [section 3.2] Details the SOP Repository structure (Query, Need Analysis, SOP) and the hybrid retrieval process (Equation 1) that combines query similarity and need-analysis similarity.
*   **Break condition:** If the SOP repository lacks sufficiently similar past cases for a novel query type, the retrieval may yield low-quality or irrelevant templates, leading to a poorly instantiated OP and reduced performance. The system depends on repository coverage.

### Mechanism 2
*   **Claim:** MASFly adapts system behavior during execution to correct anomalies (e.g., agent failure, tool misuse) and maintain task progress.
*   **Mechanism:** A global Watcher agent continuously monitors the execution against the operational procedure (OP) and a personalized experience pool (PEP) of past failure modes and remedies. Upon detecting an anomaly, it intervenes via experience-augmented guidance (sending corrective feedback) or dynamic agent replacement.
*   **Core assumption:** A dedicated monitoring agent, armed with distilled failure experiences, can identify execution deviations (in communication or tool use) in real-time and take effective corrective actions that a static system cannot.
*   **Evidence anchors:**
    *   [abstract] "experience-guided process supervision mechanism, where a dedicated Watcher agent monitors system behaviors with reference to a personalized experience pool and provides real-time interventions."
    *   [section 3.3] Defines the PEP as `<Query, Failure Cause, Agent-Wise Experience>` and describes dual-level supervision (Inter-Agent Communication, Agent–Environment Interaction) and two intervention actions.
*   **Break condition:** If the PEP lacks relevant failure patterns for the current anomaly, the Watcher's interventions may be misdirected or ineffective. Overly aggressive intervention frequency can disrupt natural agent coordination and harm stability.

### Mechanism 3
*   **Claim:** MASFly continuously improves its generation and supervision capabilities over time by distilling experiences from each task execution.
*   **Mechanism:** After task completion (with ground truth access on training data), an LLM reflects on the outcome. For successes, it generalizes the task-specific OP into a new reusable SOP for the repository. For failures, it diagnoses root causes, attributes errors to specific agents, and updates the PEP with new `Agent-Wise Experience` entries.
*   **Core assumption:** Post-hoc reflection on execution trajectories and evaluation outcomes can reliably extract generalizable procedural knowledge (for the SOP repo) and precise failure diagnostics (for the PEP), creating a closed-loop learning cycle without parameter updates.
*   **Evidence anchors:**
    *   [section 3.4] Explicitly describes "Reflective Experience Distillation" where successful executions distill SOPs for the repository and failures update the PEP.
    *   [section 3.1] Positions this as the third stage in the closed-loop process.
*   **Break condition:** If the LLM's reflection is inaccurate (e.g., misdiagnosing failure causes or over-generalizing a one-off success), it could poison the SOP repository or PEP with low-quality entries, degrading future performance. The process relies on training data with ground-truth evaluations.

## Foundational Learning
*   **Concept: Standard Operating Procedure (SOP) as a reusable pattern**
    *   **Why needed:** The SOP is the core "genetic unit" in MASFly's repository. It encodes a proven collaboration pattern (agent specs + communication graph) that can be retrieved and instantiated.
    *   **Quick check:** What are the two mandatory parts of an SOP in MASFly's repository, and how do they differ from a single-agent prompt?
*   **Concept: Hybrid Retrieval (Query + Need Analysis)**
    *   **Why needed:** The quality of SOP instantiation depends on retrieving the *right* past pattern. The hybrid score balances surface-level query similarity with deeper task-structure similarity (via LLM-generated Need Analysis).
    *   **Quick check:** Why might retrieving SOPs based solely on user query string similarity be insufficient for complex multi-agent task decomposition?
*   **Concept: Process Supervision with a Global Watcher**
    *   **Why needed:** This enables closed-loop execution. It's not just monitoring; it's *experience-guided* intervention. The engineer must understand the Watcher's dual role (monitor + actor) and its reference to the PEP.
    *   **Quick check:** What are the two levels of execution anomalies the Watcher monitors, and what are the two possible intervention actions it can take?

## Architecture Onboarding
*   **Component map:** SOP Repository -> Hybrid Retriever -> SOP Agent/LLM (Generator) -> Operational Procedure (OP) -> MAS Execution <- Watcher Agent (reads OP, accesses PEP) -> PEP. Reflective Distiller updates both Repository and PEP post-execution.
*   **Critical path:** Query -> Need Analysis -> Hybrid Retrieval -> SOPs -> SOP Agent -> OP -> MAS Execution (with Watcher monitoring & PEP lookup) -> (if failure) Reflection -> PEP update / (if success) SOP distillation -> Repository/PEP update.
*   **Design tradeoffs:**
    *   **Intervention Frequency vs. Stability:** High frequency catches errors early but may disrupt coordination; low frequency is efficient but risks error propagation.
    *   **Repository Size vs. Retrieval Relevance:** A large repository improves match chances but increases cost and noise risk; MASFly uses a small, distilled repository.
    *   **Generality vs. Specificity in SOPs:** Overly general SOPs are hard to instantiate; overly specific ones limit adaptability. Distillation aims for a middle ground.
*   **Failure signatures:**
    *   **System Generation:** Low retrieval relevance or LLM outputting an OP that doesn't structurally follow any SOP.
    *   **Execution:** Watcher repeatedly replacing the same agent role (PEP entry ineffective), or no interventions on clearly failing runs (PEP missing patterns).
    *   **Reflection:** Rapid performance decay on a query type after updates (indicating corrupted SOP/PEP from bad reflections).
*   **First 3 experiments:**
    1.  **Ablation: Remove SOP guidance (w/o SOP-RAG / w/o SOP-Inst).** Isolates the contribution of retrieval-augmented generation.
    2.  **Ablation: Remove Watcher (w/o Watcher) or Remove PEP (w/o PEP).** Isolates the contribution of experience-guided supervision.
    3.  **Retriever Ablation: Compare Hybrid vs. QuerySim vs. NeedSim.** Validates the hybrid retrieval score design.

## Open Questions the Paper Calls Out
*   Can the process supervision triggering mechanism be fully automated to dynamically determine optimal intervention timing across diverse task types, rather than relying on fixed heuristic rules (e.g., intervention every M rounds)?
*   Does the Personalized Experience Pool (PEP), built from historical failure cases, introduce biases that lead to incorrect or suboptimal interventions when facing novel failure modes or out-of-distribution queries?
*   What is the computational overhead of real-time process supervision, and how does it trade off with performance gains across tasks of varying complexity? Can the supervision mechanism be made more efficient without sacrificing robustness?
*   How well does MASFly generalize to LLM architectures beyond the Qwen3 family (e.g., GPT, Claude, or open-source models of different scales), and does its adaptive generation mechanism depend on specific model capabilities?

## Limitations
*   **Repository dependency:** SOP instantiation fails if stored patterns lack relevance to novel queries; coverage and quality of the training-derived repository are critical but not stress-tested on out-of-distribution tasks.
*   **Reflection reliability:** The closed-loop learning assumes LLM self-diagnosis is accurate; misattributed failures or over-generalized successes could corrupt both SOP and PEP resources over time.
*   **PEP intervention logic:** Anomaly detection thresholds and replacement strategies are heuristic; over-intervention harms coordination, while under-intervention misses recoverable errors—optimal tuning appears dataset-specific.

## Confidence
*   **High:** Performance gains on TravelPlanner/GAIA/HumanEval (clear empirical results, ablations).
*   **Medium:** Core mechanisms (SOP instantiation, Watcher supervision) are well-described theoretically but lack external replication or ablation of subcomponents (e.g., hybrid retrieval weighting).
*   **Low:** Generalizability beyond tested benchmarks; robustness claims depend heavily on the quality of the initial distilled repository and PEP.

## Next Checks
1.  **Repository stress test:** Systematically reduce SOP repository size/diversity and measure degradation curve on TravelPlanner; identify minimum viable coverage.
2.  **Reflection accuracy audit:** Manually analyze 100 failure/success distillations to quantify misdiagnosis rates and correlate with downstream performance drops.
3.  **PEP intervention ablation with confidence filtering:** Replace Watcher's heuristic decisions with a learned confidence threshold on PEP matches; compare to original Watcher to isolate effective vs. harmful interventions.
