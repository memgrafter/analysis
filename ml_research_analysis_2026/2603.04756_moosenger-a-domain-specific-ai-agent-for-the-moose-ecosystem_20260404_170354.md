# MOOSEnger -- a Domain-Specific AI Agent for the MOOSE Ecosystem

## Quick Facts
- **ArXiv ID**: 2603.04756
- **Source URL**: https://arxiv.org/abs/2603.04756
- **Reference count**: 40
- **Primary result**: MOOSEnger achieves a 0.90 execution pass rate vs 0.06 for LLM-only generation (15× improvement) on a 175-prompt benchmark across seven physics families.

## Executive Summary
MOOSEnger is a domain-specific AI agent for the MOOSE (Multiphysics Object Oriented Simulation Environment) ecosystem that automates the generation of executable input files from natural language specifications. It combines retrieval-augmented generation (RAG) over curated documentation and examples, a deterministic input precheck pipeline that repairs HIT syntax and corrects object types, and an iterative runtime verification loop. In a rigorous evaluation with 175 prompts spanning seven major physics families, MOOSEnger achieves a 90% pass rate compared to 6% for raw LLM generation—a 15-fold reliability gain. This work demonstrates the viability of tightly coupling LLM-based generation with deterministic domain tools for complex scientific simulation authoring.

## Method Summary
The task is to convert natural-language requests into valid MOOSE `.i` input files and ensure successful execution. The benchmark consists of 175 prompts across Diffusion, Transient Heat Conduction, Solid Mechanics, Porous Flow, Navier–Stokes, Phase Field, and Plasticity physics. The primary metric is end-to-end execution success (exit code 0). MOOSEnger operates as a tool-augmented agent: it first retrieves relevant documentation and examples using RAG, then applies a precheck pipeline that sanitizes formatting, repairs HIT syntax via grammar-constrained loops, and corrects object types via similarity search against a syntax registry. Finally, it places the MOOSE runtime in the loop, executing the input and iteratively refining based on solver diagnostics until success or an iteration limit. The baseline uses a standard LLM (ChatGPT 5.2) prompted to output a single code block without additional tools.

## Key Results
- 90% (0.90) execution pass rate on the 175-prompt benchmark.
- LLM-only baseline: 6% (0.06) pass rate; MOOSEnger yields a 15× improvement.
- High pass rates achieved across all seven physics families (detailed in Table 2 of the paper).

## Why This Works (Mechanism)
### Mechanism 1: Retrieval-Augmented Generation (RAG)
- **Claim**: RAG over curated documentation/examples grounds the LLM in MOOSE-specific knowledge, reducing hallucinations and improving factual accuracy.
- **Mechanism**: During offline ingestion, MOOSE documentation and example `.i` files are parsed with `pyhit` to preserve HIT block boundaries, embedded, and stored in a vector store. At runtime, the agent retrieves relevant chunks based on the user query and injects them into the LLM prompt, steering generation toward valid patterns.
- **Core assumption**: The retrieval corpus sufficiently covers the domain and the embedding model accurately matches queries to relevant snippets.
- **Evidence anchors**: [abstract]; Section 3.1.1 details MOOSE-aware ingestion and retrieval; related work (AutoSAM, MooseAgent) also uses RAG for simulation input, indicating a common pattern.
- **Break condition**: If the query addresses a newly introduced MOOSE feature not present in the corpus, or if retrieval fails to fetch the correct snippet, the LLM may hallucinate.

### Mechanism 2: Deterministic Precheck Pipeline
- **Claim**: A deterministic input-precheck pipeline transforms raw LLM output into syntactically valid and semantically consistent MOOSE input files by normalizing formatting, repairing structure, and correcting object types before execution.
- **Mechanism**: The pipeline sequentially applies: (1) sanitation (normalize Unicode, remove control characters), (2) a grammar-constrained repair loop that uses `pyhit` parsing to fix HIT structure while preserving block boundaries, (3) type correction via similarity search against a syntax registry (using block context, lexical and semantic similarity), and (4) optional lightweight MOOSE validation (`--check-input`).
- **Core assumption**: The HIT grammar is well-defined and amenable to bounded local repairs; the syntax registry is comprehensive; and similarity search can resolve common typos and naming confusions.
- **Evidence anchors**: [abstract]; Section 3.1.2 fully describes the composite precheck workflow and its stages; corpus evidence is limited for this specific combination of techniques.
- **Break condition**: If the input is severely malformed beyond the repair budget (e.g., missing critical blocks) or if object types are completely absent from the registry, precheck fails.

### Mechanism 3: Runtime Integration and Iterative Correction
- **Claim**: Placing the MOOSE runtime in the loop provides ground-truth feedback, enabling iterative verification-and-correction that bridges the gap between static correctness and successful execution.
- **Mechanism**: After precheck, the input is executed via an MCP-backed backend (or local fallback). Solver diagnostics (errors, warnings, convergence signals) are captured as structured tool outputs and fed back to the agent, which then attempts targeted fixes (e.g., adjusting parameters, correcting file paths). This loop repeats until the input runs successfully or an iteration limit is reached.
- **Core assumption**: MOOSE diagnostics are sufficiently clear and actionable; the agent can parse them and map them to specific code modifications.
- **Evidence anchors**: [abstract]; Section 3.1.3 explains the MCP abstraction, execution tools, and feedback loop; AutoSAM and MooseAgent have related but distinct integration patterns, making MOOSEnger's tight runtime loop distinctive.
- **Break condition**: Ambiguous or misleading diagnostics (e.g., cascading errors) can misguide the agent; fundamental physics mis-specifications may require human intervention.

## Foundational Learning
- **MOOSE HIT input structure**  
  *Why needed*: MOOSEnger parses, repairs, and generates `.i` files; understanding block semantics (e.g., `[Mesh]`, `[Kernels]`, parameter assignments) is essential to interpret errors and produce valid configurations.  
  *Quick check*: What information is typically specified inside a `[BCs]` block? (Answer: Boundary condition definitions, including type, boundary IDs, and parameters.)

- **Retrieval-Augmented Generation (RAG)**  
  *Why needed*: The agent’s generation is conditioned on retrieved documentation snippets; grasping how vector search works and why chunking matters explains retrieval quality’s impact on correctness.  
  *Quick check*: In a RAG pipeline, what is the purpose of embedding documents and queries into the same vector space? (Answer: To enable similarity-based retrieval of relevant documents for a given query.)

- **Tool-augmented agent loops**  
  *Why needed*: MOOSEnger is not a pure text generator; it calls deterministic tools (sanitizer, parser, executor) to modify the filesystem and simulation environment. This tool-use pattern is central to its reliability.  
  *Quick check*: What does an agent typically receive as input from a tool call, and how does it use that information? (Answer: The tool returns structured output (e.g., diagnostics, success/failure) that the agent parses to decide subsequent actions.)

## Architecture Onboarding
**Component map**
- Core: PluginLoader (discovers domain plugins), Registries (prompts, tools, skills), PromptManager (resolves prompts), ToolRuntime (executes tool calls), RAGManager (handles embedding/retrieval), WorkspaceManager (guarded filesystem), SessionState (traceability).
- MOOSE Plugin: HitParser (pyhit-based), InputPrecheckTool (sanitize, repair, type correction), MCPExecutionTool (with local fallback), domain-specific prompt packs and skills.
- Interfaces: CLI (user entry point), optional A2A server (remote/multi-agent).

**Critical path**
1. User submits natural-language request via CLI.
2. Runtime assembles MOOSE domain profile, binds tools, and constructs context (workspace, memory).
3. Agent iterates: retrieve relevant docs, draft/edit `.i` file.
4. Run `moose.input_precheck` (sanitize → repair → validate → optional smoke test).
5. If execution requested and fails, parse diagnostics and loop back to step 3.
6. Return final runnable input file and summary.

**Design tradeoffs**
- Core‑plus‑domain: Reusable core reduces duplication across domains, but adds abstraction overhead. Plugins must adhere to registration contracts.
- Fixed precheck vs. agent autonomy: Mandatory sequence ensures essential steps run but limits the agent’s ability to skip or reorder checks; tradeoff is improved reliability.
- MCP vs. local execution: MCP enables remote/cluster execution but introduces network dependency; local fallback guarantees offline use.
- Block‑aligned chunking: Preserving HIT boundaries improves retrieval precision but increases index size and may miss cross‑block context.

**Failure signatures**
- Retrieval failure: Low context precision/recall in evaluation reports; agent frequently invents parameters not in docs.
- Parse failure: Precheck reports repeated “parse error” messages; likely malformed brackets or missing `[]` delimiters.
- Type correction failure: Many “unknown type” warnings; may indicate incomplete syntax registry or out‑of‑date object list.
- Execution failure: Non-zero exit code; inspect logs for solver divergence, missing files, or incompatible solver settings.

**First 3 experiments**
1. **Happy path**: Run a known‑good prompt (e.g., Appendix D1 “Create a minimal 2D transient diffusion input…”) and inspect `workspace/inputs/current.i` and the precheck report in the session logs to see a successful flow.
2. **Trigger repair**: Intentionally corrupt an input (e.g., delete a closing `]`), run the precheck tool standalone, and observe the grammar‑constrained repair loop iterations.
3. **Break retrieval**: Clear the vector store or provide a query about a very niche MOOSE feature, then generate an input; note the increase in hallucinations and type errors, demonstrating retrieval’s role.

## Open Questions the Paper Calls Out
1. **How can MOOSEnger move beyond exit‑code success to evaluate scientific correctness via intent‑aware constraints and physics‑informed validation?**  
   *Basis in paper*: Sec 5.1 and 6.2 state the need for “intent‑aware checks” and “richer post‑run checks” to align “pass” with scientific validity.  
   *Why unresolved*: An input may run successfully yet deviate from the user’s intent (e.g., wrong material, oversimplified BCs), limiting trust.  
   *What evidence would resolve it*: A framework that automatically verifies key physical invariants, conserved quantities, or expected trends against solver output, coupled with a human‑evaluated benchmark showing correlation with expert assessment.

2. **Can MOOSEnger autonomously mine diagnostics from its precheck/repair loop to identify knowledge gaps and update its retrieval corpus or prompts?**  
   *Basis in paper*: Sec 6.2: “We plan to mine structured diagnostics from the precheck/repair loop to identify knowledge gaps and automatically propose updates to retrieval content and prompt/tool guidance.”  
   *Why unresolved*: The knowledge base is static; new physics syntax or common errors are not incorporated without manual effort, leading to repeated failures.  
   *What evidence would resolve it*: A closed‑loop pipeline that clusters frequent error patterns, maps them to missing documentation or prompt modifications, and demonstrates reduced errror rates after automated updates.

3. **How should the core‑plus‑domain architecture be extended to enable coordinated multi‑agent workflows for complex multiphysics studies?**  
   *Basis in paper*: Sec 6.2: “We will extend the core–plugin architecture to simplify authoring of application‑specific agents and to support coordinated multi‑agent workflows for complex multiphysics studies.”  
   *Why unresolved*: MOOSEnger is a single‑agent system; coupling multiple physics (e.g., thermal‑fluid‑structural) may benefit from specialized sub‑agents that collaborate, but no coordination mechanism exists.  
   *What evidence would resolve it*: A prototype where distinct domain agents (e.g., heat, flow, mechanics) communicate via the A2A protocol to jointly generate a coupled input, benchmarked against current single‑agent performance on multiphysics prompts.

## Limitations
- **RAG corpus opacity**: The exact composition (which MOOSE docs/examples) and chunking strategy are undisclosed, risking retrieval bias and limiting reproducibility.
- **Environment specificity**: Unstated MOOSE app versions, enabled modules, and solver settings may cause execution differences outside the tested setup.
- **Benchmark scope**: The 175 prompts across seven families may not capture rare edge cases; pass rate could drop on novel physics combinations.
