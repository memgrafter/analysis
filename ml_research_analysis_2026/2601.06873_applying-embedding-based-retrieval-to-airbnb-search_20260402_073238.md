# Applying Embedding-Based Retrieval to Airbnb Search
## Quick Facts
- **arXiv ID**: 2601.06873
- **Source URL**: https://arxiv.org/abs/2601.06873
- **Reference count**: 22
- **Primary result**: Airbnb's embedding-based retrieval system achieved a 0.31% relative increase in booking conversion while reducing compute resources by 16%.

## Executive Summary
Airbnb faced scalability challenges with its legacy search system due to large, dynamic inventories and flexible date features. To address this, they developed an Embedding-Based Retrieval (EBR) system using a two‑tower model trained via trip‑based sampling to capture multi‑stage user journeys and harder negatives. For serving, they selected an Inverted File Index (IVF) over HNSW to support real‑time updates and geographic filters. Online A/B testing demonstrated a 0.31% relative lift in booking conversion, a 16% reduction in compute, and notable gains for new listings and email campaigns, confirming improved relevance across the user journey.

## Method Summary
The authors replace a query‑independent scoring model with a two‑tower neural network. The query tower ingests sparse features like placeId embeddings, guest count, and geo size, while the listing tower uses pre‑computed aggregates of engagement (views, wishlists, reviews), amenities, and static S2CellIDs. Training employs contrastive learning: positives are booked listings within a "trip" (grouped by canonical location, guest count, and bucketed stay length); negatives are harder listings sampled from intentful actions (viewed, wishlisted) with auxiliary labels. The loss evolves from pointwise to pairwise Euclidean distance. At serving time, listing embeddings are computed offline daily and indexed via IVF clustering. At query time, the query embedding is computed, top‑k IVF clusters are retrieved, and candidates are re‑ranked after geographic and availability filtering.

## Key Results
- **Booking conversion**: 0.31% relative increase.
- **Compute efficiency**: 16% reduction in resources.
- **Ecosystem impact**: +2.3% bookings from email campaigns; increased bookings for new and wishlisted listings.

## Why This Works (Mechanism)
The two‑tower architecture decouples query and listing computation, enabling pre‑computation of listing embeddings for low‑latency retrieval. Trip‑based sampling creates semantically coherent positive pairs and exposes the model to harder negatives that reflect true user intent, improving embedding discrimination. IVF provides an approximate nearest neighbor index that supports efficient updates and integrates seamlessly with geographic constraints, which is critical for Airbnb’s spatial queries. Together, these design choices yield a system that scales to millions of listings while maintaining relevance and freshness.

## Foundational Learning
- **Two‑Tower Model**: Separate query and item networks produce embeddings; allows pre‑computation of item vectors. *Why needed*: low‑latency serving at scale. *Quick check*: confirm that listing embeddings are stable across daily retrains and can be stored offline.
- **Trip‑Based Sampling**: Groups searches by location, guest count, and stay length to define positive (booked) and hard negative (viewed/wishlisted) pairs. *Why needed*: captures multi‑stage journey and supplies challenging negatives that mimic online distribution. *Quick check*: compute average similarity (e.g., cosine) between booked listing and sampled negatives; should be lower than random negatives.
- **Inverted File Index (IVF)**: Clusters embeddings into Voronoi cells; at query time only a few clusters are searched. *Why needed*: balances recall and latency for large catalogs, supports real‑time updates and filter integration. *Quick check*: measure recall@10 as cluster count and nprobes vary; identify knee point.
- **Contrastive Loss with Euclidean Distance**: Optimizes embedding similarity for matching pairs and dissimilarity for non‑matches. *Why needed*: directly optimizes retrieval objective. *Quick check*: monitor training loss and validate that identical‑item queries return self as nearest neighbor.
- **Geographic Filtering via S2CellIDs**: Encodes location using hierarchical cells; filtering applied after IVF retrieval. *Why needed*: enforces spatial constraints critical for accommodation search. *Quick check*: ensure all returned listings fall within query’s S2Cell hierarchy; test edge cases across cell boundaries.

## Architecture Onboarding
Component map: Data Pipeline → Training Service → Listing Embedding Store → Query Service → IVF Index → Lucene Filters → Ranking Model. The data pipeline collects logs and features; training service produces listing embeddings; listing store updates daily; query service computes query embedding on‑the‑fly, probes IVF, then Lucene applies geographic/availability filters before final re‑ranking.

Critical path: (1) User issues search query; (2) Query features extracted and embedded; (3) IVF selects top clusters; (4) Candidate listings retrieved from those clusters; (5) Lucene filters by geography and availability; (6) Ranking model scores survivors; (7) Results returned.

Design tradeoffs: IVF vs. HNSW – IVF chosen for easier real‑time updates and filter pushdown; HNSW offers higher recall for static data but complicates updates. Two‑tower vs. single tower – two‑tower enables pre‑computation; single tower might capture deeper interactions but incurs higher latency. Hard negative sampling – trip‑based intentful negatives improve relevance but require careful logging and may introduce bias if logs are incomplete.

Failure signatures: 
- Low recall despite training: check cluster imbalance or incorrect distance metric (dot vs Euclidean).
- High update latency: inspect batch update pipeline; IVF cluster assignments may cause full index rebuild.
- Degraded performance for new listings: verify that cold‑start features (amenities, location) are sufficiently informative; consider fallback strategies.

Three first experiments:
1. **Traffic replay validation**: Replay historic queries using the first‑stage model as ground truth and compute recall@10/50 for the IVF configuration; correlate with expected online lift.
2. **Ablation study on negatives and loss**: Replace trip‑based hard negatives with random negatives and switch between pointwise/pairwise losses; measure offline recall and convergence speed.
3. **IVF vs. HNSW benchmark**: Under identical latency budgets and with geographic filters, compare recall‑latency curves; confirm IVF’s advantage in update throughput.

## Limitations
- Exact feature engineering (aggregation windows, embedding dimensions) and hyperparameters (learning rate, batch size, IVF cluster count) are not disclosed, making exact replication difficult.
- Online A/B results (e.g., 0.31% conversion lift) are presented without statistical significance values or discussion of potential confounding factors.
- Confidence in claims about compute reduction and IVF superiority is medium due to missing infrastructure and experimental details.

- IVF chosen over HNSW: **Medium**
- Gains for new listings and email campaigns: **Medium**
