# LongAudio-RAG: Event-Grounded Question Answering over Multi-Hour Long Audio
## Quick Facts
- **arXiv ID**: 2602.14612
- **Source URL**: https://arxiv.org/abs/2602.14612
- **Reference count**: 21
- **Primary result**: LA-RAG achieves up to 76.93% counting accuracy, 90.67% detection accuracy, and 0.56s end-to-end latency on a synthetic Home IoT benchmark, outperforming AGM+RAG (48.95% overall) and Text2SQL (41.77%).

## Executive Summary
LongAudio-RAG (LA-RAG) tackles multi-hour audio question answering, a challenging scenario where large context windows and risk of hallucination hinder existing methods. It introduces an event-grounded retrieval-augmented generation (RAG) framework: long audio is processed by an Audio Grounding Model (AGM) to produce timestamped acoustic event records stored in a SQL database. At query time, natural-language time expressions are resolved, intent is classified, only relevant events are retrieved, and an LLM generates answers strictly constrained by the retrieved evidence. Evaluated on a synthetic benchmark built from concatenated labeled audio clips, LA-RAG substantially surpasses baselines, achieving over 90% detection accuracy and 56% summary accuracy while maintaining low latency (0.56s). The hybrid edge-cloud deployment places the AGM on IoT hardware for fast event extraction and offloads LLM reasoning to the cloud, balancing responsiveness and computational cost.

## Method Summary
LA-RAG comprises two phases: offline audio grounding and online query processing. For audio grounding, an open-vocabulary sound event detection (SED) model processes multi-hour audio in shifted windows (e.g., 4s with overlap) and outputs events (label, start, end, confidence, loudness) stored in a SQLite database. During query processing, the system first rephrases the user query for clarity using an LLM. It then resolves any temporal expressions via regex patterns (explicit times, durations, relative references) with an LLM fallback that converts natural language to start/end seconds. Next, intent classification determines whether the query is about detection, counting, summarization, or anomaly detection, using a hybrid of keyword matching and embedding similarity. Relevant events are retrieved by filtering the database on the resolved time interval; for event-specific queries, a top-k reranking by cosine similarity between the query and event labels (using all-MiniLM-L6-v2) is applied. Finally, an LLM (e.g., Phi‑4‑mini‑instruct) generates a concise answer conditioned on the retrieved events and the user intent, with prompts engineered to minimize hallucination. The entire pipeline is designed for hybrid deployment: the AGM runs on a Qualcomm IQ‑9075 edge device, while embedding and LLM services run on a GPU server, achieving low end-to-end latency.

## Key Results
- On the Home IoT synthetic dataset, LA-RAG achieves **90.67% detection accuracy**, **76.93% counting accuracy**, and **56.10% summary accuracy**.
- The system attains **0.56 seconds** end-to-end latency, making it suitable for interactive use.
- It significantly outperforms baseline approaches: AGM+RAG (48.95% overall) and Text2SQL (41.77%).

## Why This Works (Mechanism)
LA-RAG’s design directly addresses the two core challenges of long-audio QA: **temporal grounding** and **hallucination control**. By converting raw audio into a structured database of timestamped events, the system restricts LLM attention to a concise, relevant subset of the original content, avoiding the context window limits of direct audio-to-text models. The retrieval step ensures the answer is based on actual detected events rather than on the model’s internal (and often inaccurate) knowledge of audio content. Time resolution explicitly maps vague natural-language time references to precise intervals, enabling accurate filtering. The use of an intent-specific prompt guides the LLM to produce the required output format (yes/no, count, summary) while strictly conditioning on the retrieved evidence. The hybrid edge-cloud deployment keeps the computationally intensive AGM close to the data source, reducing bandwidth and latency, while leveraging powerful cloud LLMs for complex reasoning. Together, these components create a scalable, low-latency pipeline that minimizes hallucinations and respects temporal constraints.

## Architecture Onboarding
**Component map (plain text):**  
Audio stream -> Audio Grounding Model (AGM) -> SQLite Events Database -> Query Processor (Rephrase -> Resolve Time -> Classify Intent -> Retrieve) -> LLM Generator -> Answer

**Critical path:**  
1. AGM processes audio in sliding windows, outputs events.  
2. User query arrives: LLM rephrases it.  
3. Time resolver converts temporal expressions to [start, end] seconds.  
4. Intent classifier routes to detection/counting/summary.  
5. Retriever filters events by time and optionally reranks by embedding similarity.  
6. LLM generates answer using the retrieved event list and intent-specific prompt.

**Design tradeoffs:**  
- **Event extraction**: High confidence threshold reduces false positives but may miss faint events (lower recall).  
- **Time resolution**: Purely regex-based is fast but brittle; adding LLM fallback increases coverage at latency cost.  
- **Retrieval**: Simple time filter is fast; embedding rerank improves precision for specific queries but adds embedding computation.  
- **Deployment**: Edge AGM reduces bandwidth and latency; cloud LLM ensures quality but requires network and may raise privacy concerns.

**Failure signatures:**  
- *Missing events in database* → answers show low detection/count; check AGM precision/recall on a sample clip.  
- *Incorrect time interval* → retrieved events are off by minutes/hours; validate time resolution on a set of expressions.  
- *Intent misrouting* → answer format mismatches expectation; examine confusion matrix on labeled queries.  
- *LLM ignores evidence* → generates unsupported details; inspect prompts and consider adding “use only the provided events”.

**Exactly 3 first experiments:**  
1. **AGM validation**: Run the AGM on a short (e.g., 1-minute) audio with known events; compute event-level F1 to verify the reported ~74.8 score.  
2. **Time resolution test**: Assemble 100 diverse temporal queries (explicit, relative, duration); measure exact-match accuracy of resolved intervals against ground truth.  
3. **End-to-end baseline**: Use the minimum viable reproduction plan to build the full pipeline on synthetic audio; evaluate accuracy on the 800 QA pairs and measure latency.

## Open Questions the Paper Calls Out
1. **Generalization to real-world audio**: While the synthetic benchmark enables controlled evaluation, it does not fully capture the acoustic complexity, overlapping events, and ambiguous queries present in real multi-hour recordings. Testing on large, annotated real-world datasets is needed to assess robustness.
2. **Improving time resolution for hard queries**: The current regex+LLM approach achieves only 30% accuracy on hard temporal expressions (e.g., “late afternoon”, “during the second hour”). More sophisticated temporal reasoning, possibly via a dedicated model fine-tuned on diverse expressions, is required.
3. **Fully on-device deployment**: The hybrid edge-cloud architecture offloads LLM inference to the cloud. Achieving end-to-end on-device execution with both AGM and compact LLMs on edge hardware (e.g., Qualcomm IQ‑9075) while maintaining accuracy and latency remains future work.
4. **Extending to multi-modal and agentic capabilities**: Incorporating additional sensors (video, temperature, vibration) and supporting interactive dialogue or code generation would broaden the system’s applicability but demands architectural modifications and new benchmarks.

## Limitations
- **Synthetic benchmark**: Results are obtained from auto‑generated QA pairs on concatenated clean clips, which may not reflect real-world noise, overlaps, or linguistic ambiguity; confidence in real‑world performance is **Low**.
- **Implementation gaps**: Exact AGM training details (architecture, splits, hyperparameters) and LLM prompts are undisclosed, making faithful replication of the reported numbers difficult; confidence in exact event extraction is **Medium**.
- **Prompt sensitivity**: The system’s performance likely depends on careful prompt engineering, which is not fully documented; confidence in modular reproducibility is **Medium**.
