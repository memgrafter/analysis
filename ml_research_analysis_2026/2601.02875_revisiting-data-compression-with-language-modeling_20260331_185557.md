# Revisiting Data Compression with Language Modeling

## Quick Facts
- arXiv ID: 2601.02875
- Source URL: https://arxiv.org/abs/2601.02875
- Reference count: 7
- Primary result: Achieved a new SOTA adjusted compression rate of ~18% on enwik9 using a 3-bit HQQ-quantized 360M-parameter model, significantly reducing model size while maintaining competitive raw compression.

## Executive Summary
This paper revisits lossless compression using large language models (LLMs), aiming to make LLM-based compressors competitive with traditional methods by minimizing the adjusted compression rate that accounts for model size. The core methods are: extending the model’s context length to capture longer dependencies, applying post‑training quantization (especially 3‑bit HQQ) to shrink the model footprint without severely degrading prediction quality, and tailoring tokenization strategies to the data type (e.g., integer‑token mapping for raw byte streams). Key results include a ~18% adjusted compression rate on enwik9 with a 3‑bit HQQ‑quantized 360M‑parameter model, demonstrating that quantization to 3‑bit preserves performance while drastically cutting storage. For non‑English text, compression effectiveness aligns with the model’s pre‑training language exposure, and for raw byte streams (e.g., PDFs), mapping bytes to integer tokens yields far better compression than treating them as UTF‑8 text. Code data compresses well due to its prevalence in training corpora.

## Method Summary
The approach leverages pretrained LLMs combined with arithmetic coding. To reduce the adjusted compression rate (compressed size plus model size divided by original size), the authors employ three main techniques: (1) extending the context length up to the model’s maximum (e.g., 128k for Llama‑3.2‑1B) to improve raw compression by capturing longer‑range dependencies; (2) applying post‑training quantization—specifically 3‑bit HQQ, a calibration‑free method that preserves probability distributions better than GPTQ at ultra‑low bit‑widths—to shrink the model file; and (3) adapting tokenization: for text data using the model’s standard tokenizer, for raw byte streams mapping each byte (0–255) to a dedicated integer token, and for non‑Latin scripts relying on models with relevant language exposure. The compression pipeline: preprocess the input into token IDs, run the quantized LLM to predict token probabilities, feed these to an arithmetic encoder to emit bits, and finally output the compressed stream. Decompression reverses this process with the same model and tokenizer.

## Key Results
- Adjusted compression rate of ~18% on enwik9 (1GB) using a 3‑bit HQQ‑quantized 360M‑parameter model, establishing a new SOTA.
- Quantization to 3‑bit preserves raw compression rates near the full‑precision baseline, while 2‑bit degrades performance; HQQ outperforms GPTQ at 3‑bit.
- For raw byte streams (PDFs), mapping bytes to integer tokens (0–255) achieves the lowest compression; UTF‑8 text tokenization performs similarly to Gzip.
- Compression quality on non‑English text correlates with the model’s pre‑training language coverage: Llama‑3.2‑1B excels on its trained languages, Qwen2‑0.5B on Chinese/Japanese, while smaller models like SmolLM degrade on non‑Latin scripts.
- Code datasets compress effectively due to abundant code in training data.

## Why This Works (Mechanism)

### Mechanism 1: Extending context length
- **Claim:** Extending the context length of an LLM can improve raw compression rates by enabling the model to capture longer‑range dependencies in the data.
- **Mechanism:** Arithmetic coding compresses sequences based on predicted token probabilities. A longer context provides more preceding tokens, allowing the autoregressive LLM to produce more accurate probability distributions for subsequent tokens, thereby reducing the encoded bitlength toward the entropy limit.
- **Core assumption:** The data contains exploitable sequential dependencies beyond the model’s original context window.
- **Evidence anchors:**  
  - [abstract] identifies “extending model context length” as a core method to achieve lower adjusted compression.  
  - [section 5.2.1] reports “the longer the context length, the more the reduction in the compression rate γ” on enwik9 for models supporting ≥128k tokens.  
  - [corpus] Weak: neighboring papers (e.g., In‑Context Former) explore context compression but do not directly evaluate data compression gains.
- **Break condition:** If the data is statistically independent or the context window exceeds the model’s effective positional encoding range, further extension yields no benefit or degrades performance (as seen with SmolLM beyond 2048 tokens).

### Mechanism 2: Post‑training quantization (HQQ)
- **Claim:** Post‑training quantization (especially HQQ at 3‑bit) drastically reduces the model file size with only a modest increase in raw compression rate, thereby lowering the adjusted compression rate.
- **Mechanism:** Quantization replaces high‑precision weights (e.g., BF16) with lower‑bit integers, shrinking the model footprint. HQQ, a calibration‑free method, optimizes weight clustering without requiring representative data, preserving the original weight distribution better than calibration‑based GPTQ at ultra‑low bits (3‑bit vs. 2‑bit). This maintains the LLM’s predictive accuracy for arithmetic coding while cutting storage cost.
- **Core assumption:** The quantized model’s token probability distributions remain sufficiently close to the full‑precision model’s distributions.
- **Evidence anchors:**  
  - [abstract] states “Quantization to 3‑bit preserves performance better than 2‑bit, with HQQ outperforming GPTQ” and highlights the 18% adjusted SOTA on enwik9 using a 3‑bit HQQ‑quantized 360M model.  
  - [section 5.2.2] and Table 2 show that HQQ 3‑bit yields raw compression rates (γr) near the unquantized baseline (e.g., 0.107 vs. 0.100 for SmolLM‑360M) while reducing model size by >5×, whereas 2‑bit degrades γr substantially.  
  - [section 4.2] details HQQ’s calibration‑free optimization and its advantage over GPTQ’s column‑wise error propagation.
- **Break condition:** At extremely low bits (≤2‑bit), quantization error overwhelms the probability estimates, causing raw compression rates to rise sharply and negating adjusted gains.

### Mechanism 3: Byte tokenization strategy
- **Claim:** For raw byte‑stream data (e.g., PDFs), mapping each byte to a dedicated integer token (0–255) in the tokenizer yields far better compression than treating the stream as UTF‑8 text.
- **Mechanism:** UTF‑8 text tokenization fragments byte values into multi‑token subwords and invalid sequences, distorting the underlying byte distribution. Integer‑token mapping preserves a one‑to‑one correspondence between byte values and tokens, allowing the LLM to model the true empirical distribution of bytes (including non‑printable and high‑ASCII values) without encoding artifacts.
- **Core assumption:** The LLM’s tokenizer can be reconfigured to include exactly 256 tokens representing byte values 0–255, and the model’s pre‑training has exposed it to similar byte‑level sequences (or the mapping is applied consistently during compression and decompression).
- **Evidence anchors:**  
  - [abstract] summarizes: “For raw byte streams (PDFs), mapping bytes to integer tokens in the tokenizer yields the best compression, whereas treating bytes as UTF‑8 text performs similarly to Gzip.”  
  - [section 5.4] and Figure 7/8 demonstrate that integer‑token mapping achieves the lowest raw and adjusted compression rates on PDF data, while UTF‑8 text tokenization offers no advantage over Gzip.  
  - [section 4.3] explains the three tokenization strategies and the process of deriving byte‑token mappings from BPE‑based tokenizers.
- **Break condition:** If the tokenizer cannot be coerced into a 256‑token byte vocabulary or the model has never seen such token IDs during pre‑training, the integer mapping may yield undefined behavior or poor probabilities.

## Foundational Learning

### Arithmetic coding
- **Why needed:** It is the entropy encoder that transforms LLM‑predicted token probabilities into a compressed bitstream; understanding its interval‑narrowing mechanism is essential to grasp how compression efficiency relates to model accuracy.
- **Quick check:** “Why does arithmetic coding achieve compression rates close to the entropy limit of a source?”

### Tokenization (Byte‑Pair Encoding)
- **Why needed:** The choice of how raw data is split into tokens directly impacts the LLM’s ability to model the distribution; different tokenization strategies (text vs. integer vs. raw bytes) lead to vastly different compression outcomes.
- **Quick check:** “How does mapping bytes to integer tokens differ from UTF‑8 text tokenization in terms of vocabulary coverage and sequence fragmentation?”

### Post‑training quantization (GPTQ, HQQ)
- **Why needed:** These techniques reduce model size for adjusted compression; knowing the trade‑offs between calibration‑based and calibration‑free methods explains why HQQ outperforms GPTQ at 3‑bit.
- **Quick check:** “What is the fundamental difference between GPTQ’s activation‑matching objective and HQQ’s weight‑matching objective?”

## Architecture Onboarding
- **Component map:** Input preprocessor -> Tokenizer -> LLM core -> Probability sampler -> Arithmetic encoder/decoder  
  Supporting storage: Model storage (holds quantized weights and tokenizer configuration).
- **Critical path:**  
  1. Load quantized model and tokenizer (verify context length support).  
  2. Preprocess input stream into token IDs via chosen mapping.  
  3. For each token within the context window: fetch probability vector from LLM, feed to arithmetic encoder to emit bits for the current token.  
  4. Finalize bitstream and write to disk; for decompression, reverse the process with the same model and tokenizer.
- **Design tradeoffs:**  
  - Context length vs. memory: Longer contexts improve compression but increase quadratic attention memory; choose the maximum supported by GPU (e.g., 128k) if data has long dependencies.  
  - Quantization bit‑width vs. fidelity: 3‑bit HQQ offers near‑baseline raw compression with ~5× size reduction; 2‑bit often degrades performance unacceptably.  
  - Tokenization strategy: integer mapping maximizes byte‑stream compression but requires a tokenizer with 256 tokens; UTF‑8 mapping is universal but typically matches only Gzip‑level performance.
- **Failure signatures:**  
  - Compression rate >1.0: model probabilities are ineffective (e.g., tokenizer mismatch, model not suited to data domain).  
  - Disproportionately poor performance on non‑Latin scripts: model’s pre‑training lacked those languages.  
  - Out‑of‑memory errors during inference: context length exceeds GPU capacity or RoPE scaling is misconfigured.
- **First 3 experiments:**  
  1. Baseline verification: compress enwik9 with unquantized Llama‑3.2‑1B at 2048‑token context; confirm γr ≈ 0.085 and γa >1 due to large model.  
  2. Quantization sweep: compare GPTQ vs. HQQ at 8/4/3/2‑bit on enwik9; record raw and adjusted rates; expect HQQ‑3bit to yield γa ≈ 0.18.  
  3. Byte tokenization test: compress a PDF dataset using UTF‑8, integer, and byte‑token mappings; expect integer mapping to achieve the lowest γa and validate the break‑even point vs. Gzip.

## Open Questions the Paper Calls Out

### Applicability to arbitrary binary file formats
The paper only evaluates text, code, and PDF byte streams, leaving many other binary formats untested. The authors mention this as future work. To resolve, one would need to systematically apply the LLM compression pipeline to various binary formats (e.g., PNG, MP3, ELF) and compare against traditional compressors like Zstandard or Brotli, measuring compression ratios and potential domain‑specific adaptations.

### Compressing neural network weights
The authors suggest exploring compression of deep neural network model weights. It is unknown whether LLMs can capture the structured patterns in weight tensors better than existing quantization methods (e.g., GPTQ, HQQ). Validation would involve compressing weight files from different architectures and comparing not only compression ratio but also downstream task performance after decompression and recovery.

### Theoretical explanation for integer token mapping superiority
While the paper empirically shows that mapping bytes to integer tokens (0‑255) yields better compression for raw byte streams than UTF‑8 text tokenization, the reason is not analyzed. Understanding whether this stems from entropy reduction, model inductive biases, or tokenizer design could guide future binary compression systems. Ablation studies measuring LLM perplexity, entropy estimates, and attention patterns on identical byte sequences under different tokenizations would provide needed evidence.

### Scaling adjusted compression for small datasets
The paper achieves good adjusted rates on enwik9 (1GB) with a quantized model, but the break‑even point for very small datasets is unclear. For tiny datasets, even a 3‑bit 360M‑parameter model may be too large. Deriving scaling laws would require evaluating quantized LLMs of varying sizes (e.g., 100M to 1B parameters) on datasets from kilobytes to gigabytes, plotting adjusted compression rate curves, and identifying minimal viable model sizes for cost‑effective compression at different scales.

## Limitations
- The precise arithmetic coding implementation (e.g., precision, restart intervals) is not fully specified, hindering exact reproduction and potentially causing small rate discrepancies.
- The byte‑to‑integer token mapping procedure is manual and error‑prone; it is not packaged as a reusable function and may not generalize across all tokenizers.
- Compression quality on non‑Latin scripts heavily depends on the model’s pre‑training language coverage; smaller models exhibit poor performance on such texts, limiting universality.

## Confidence
- Extending context length improves raw compression: **High** (direct experimental evidence on enwik9).
- 3‑bit HQQ quantization yields best adjusted compression: **High** (consistently superior raw/ adjusted trade‑off across models).
- Integer token mapping for byte streams outperforms UTF‑8: **Medium** (strong on PDFs but limited to one dataset; generalizability to other binaries unproven).
- Overall SOTA adjusted rate of ~18% on enwik9: **High** (combines two high‑confidence mechanisms).
