# Pruning as a Cooperative Game: Surrogate-Assisted Layer Contribution Estimation for Large Language Models
## Quick Facts
- **arXiv ID**: 2602.07804
- **Source URL**: https://arxiv.org/abs/2602.07804
- **Reference count**: 40
- **Primary result**: Cooperative game-based layer pruning with a surrogate network consistently reduces perplexity and improves zero-shot accuracy across Transformer and non-Transformer LLMs, while offering favorable speed‑memory trade‑offs.

## Executive Summary
Large language models (LLMs) have high inference costs, and existing static pruning heuristics fail to account for inter‑layer dependencies. This paper reformulates depth pruning as a cooperative game where each layer is a player and the model's performance is the utility. Exact Shapley values, which fairly allocate contributions, are infeasible to compute; instead, the authors train a lightweight surrogate network on scores from binary pruning masks generated via stratified Monte Carlo sampling. The surrogate predicts model performance for any mask, enabling efficient Shapley approximation across layers. Experiments on LLaMA, Vicuna, RWKV, and Mamba models demonstrate lower perplexity on WikiText2, PTB, and C4 datasets, and higher zero‑shot accuracy on eight tasks compared to traditional depth/width pruning baselines, especially under aggressive pruning. The approach also yields beneficial speed‑throughput‑memory trade‑offs and integrates with quantization for additional memory savings.

## Method Summary
The proposed pruning pipeline consists of two stages. **Stage 1** generates binary pruning masks with a fixed number of retained layers (Hamming weight) using stratified Monte Carlo sampling. For each mask, a pruned model is built by selecting the corresponding layers in order, and its performance is evaluated on a small calibration set (10 samples from BookCorpus). The score is defined as the ratio of the original model's perplexity to the pruned model's perplexity. **Stage 2** trains a two‑layer MLP surrogate (input dimension = number of layers, hidden size = 2×, CELU activation, sigmoid output) on the collected (mask, score) pairs using mean‑squared error loss. To approximate Shapley values, for each layer the method samples many masks (from the same Hamming‑weight distribution) that do not include the layer, queries the surrogate for the score of the mask and of the mask with the layer added, and averages the differences. Layers are then ranked by their estimated Shapley values and the lowest‑scoring layers are pruned.

## Key Results
- Consistently lower perplexity on WikiText2, PTB, and C4 compared to depth/width pruning baselines.
- Higher zero‑shot accuracy across eight tasks (PIQA, HellaSwag, ARC, OpenbookQA, RACE, WSC273, LAMBADA, MMLU), particularly when pruning aggressively.
- Favorable speed‑throughput‑memory trade‑offs; compatible with quantization for further memory reduction.

## Why This Works (Mechanism)
The cooperative game formulation ensures that each layer's contribution is measured in the context of all possible layer subsets, capturing complex inter‑layer dependencies that static heuristics miss. Shapley values provide a theoretically sound allocation that respects marginal contributions and symmetry. By training a surrogate on a diverse set of binary masks, the method bypasses the exponential cost of evaluating all subsets; the surrogate generalizes to unseen combinations, enabling fast estimation of marginal contributions via Monte Carlo sampling. Stratified sampling over different Hamming weights ensures coverage across pruning strengths, leading to robust rankings. Consequently, the identified least‑contributory layers can be removed with minimal degradation to model performance.

## Architecture Onboarding
**Component Map**: Calibration Data → Mask Generator → Pruned Model Constructor → Evaluator → Surrogate Trainer → Shapley Estimator → Layer Ranker → Pruner → Final Pruned Model  
**Critical Path**: Generate masks → Evaluate pruned models → Train surrogate → Approximate Shapley values for each layer → Rank and prune.  
**Design Tradeoffs**:  
- *Number of masks (N)*: More masks improve surrogate accuracy but increase Stage 1 compute.  
- *Surrogate capacity*: Larger networks fit better but are slower for Shapley estimation; a two‑layer MLP balances speed and expressiveness.  
- *Sampling budget (Q)*: More samples in Shapley estimation reduce variance at the cost of longer runtime.  
- *Hamming weight set (K)*: Choice of retained‑layer counts affects coverage of pruning strengths; a wider range yields more robust rankings but may require more masks.  
- *Calibration data size*: More samples give reliable scores but slow down Stage 1 evaluation.  
**Failure Signatures**:  
- Surrogate underfitting: low R² (<0.85) on held‑out masks → noisy Shapley estimates.  
- Poor post‑pruning perplexity (>30% degradation) → likely incorrect layer removal or bad ranking.  
- High variance in Shapley values across random seeds → insufficient sampling (N or Q too low).  
**First Experiments**:  
1. *Surrogate validation*: Train surrogate on 8k masks; compute R² on 200 held‑out masks. If <0.9, increase N or hidden size.  
2. *Sanity check on known important layers*: Manually prune the final layer only; expect large perplexity increase. Confirm Shapley ranks it highly.  
3. *Stability of Shapley estimates*: Run Shapley estimation with Q=10k and Q=80k; compute rank correlation (e.g., Spearman) between resulting layer orderings. Low correlation indicates need for larger Q.

## Limitations
- The handling of residual connections and layer norms after manual layer removal is unspecified, risking implementation errors.
- The stratified Monte Carlo sampling distribution (exact Hamming weight set and allocation) is not fully detailed, which may affect Shapley estimation stability.
- It is ambiguous whether the base mask in the Shapley formula is always forced to exclude the target layer; if not, contribution estimates could be biased.

## Confidence
- **Performance superiority** (lower perplexity, higher zero‑shot accuracy): Medium  
- **Efficiency trade‑offs** (speed, throughput, memory): Medium  
- **Generalizability** across Transformer and non‑Transformer architectures: Low
