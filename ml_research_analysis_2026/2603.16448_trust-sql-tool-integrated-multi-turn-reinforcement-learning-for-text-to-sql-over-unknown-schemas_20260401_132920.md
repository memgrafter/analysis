# TRUST-SQL: Tool-Integrated Multi-Turn Reinforcement Learning for Text-to-SQL over Unknown Schemas

## Quick Facts
- **ArXiv ID**: 2603.16448
- **Source URL**: https://arxiv.org/abs/2603.16448
- **Reference Count**: 30
- **Primary Result**: BIRD-Dev execution accuracy of 64.9% (4B) and 65.8% (8B) without schema prefilling, matching or surpassing prefilled baselines.

## Executive Summary
TRUST-SQL tackles the Unknown Schema scenario in Text-to-SQL, where an agent must actively explore a massive, noisy database instead of relying on full schema prefilling. It introduces a four-phase protocol—Explore, Propose, Generate, Confirm—that enforces verified schema grounding and prevents hallucinations. Dual-Track Group Relative Policy Optimization (GRPO) isolates exploration and execution rewards using token‑level masked advantages, resolving credit assignment. Across five benchmarks, TRUST-SQL yields average absolute improvements of 30.6% (4B) and 16.6% (8B) over base models, and a 9.9% relative gain over standard GRPO on BIRD‑Dev. Without any schema prefilling, it matches or exceeds prefilled baselines.

## Method Summary
The method comprises a four‑phase interaction loop: (1) **Explore** agent uses database tools to iteratively discover schema details; (2) **Propose** generates candidate schema grounding from the exploration history; (3) **Generate** produces a SQL query conditioned on the proposed schema; (4) **Confirm** validates execution and feeds back for refinement if needed. Reinforcement learning is trained with Dual‑Track GRPO, which applies token‑level masked advantages to separate rewards for exploration actions (e.g., useful `DESCRIBE` queries) and final execution correctness. This isolation mitigates credit assignment conflicts in multi‑turn settings.

## Key Results
- BIRD‑Dev execution accuracy: 64.9% (4B) and 65.8% (8B) with greedy decoding, no schema prefilling.
- Average absolute gains of 30.6% (4B) and 16.6% (8B) over base models across five benchmarks.
- Relative improvement of 9.9% over standard GRPO on BIRD‑Dev.

## Why This Works (Mechanism)
The four‑phase protocol ensures that schema exploration completes before query generation, so the model never generates SQL based on unverified or hallucinated schema elements. Dual‑Track GRPO assigns credit at the token level, masking tokens belonging to exploration actions when computing execution advantages (and vice versa). This prevents exploration policy from being penalized by a poor final execution caused by generation issues, and avoids polluting generation learning with intermediate exploration noise. The result is a stable multi‑turn policy that learns to gather just enough schema information to produce correct SQL.

## Foundational Learning
- **Tool‑Integrated Reasoning**: Agents must learn to call external tools (e.g., database introspection) to acquire missing information. *Why needed*: The unknown schema setting forbids prefilling; without tools the agent cannot access the database structure. *Quick check*: Verify Explore agent issues syntactically valid SQL introspection queries and incorporates results.
- **Reinforcement Learning for Text‑to‑SQL**: RL optimizes for final execution accuracy with sparse rewards. *Why needed*: Direct supervision (correct SQL) is unavailable; RL guides the policy through intermediate rewards. *Quick check*: Ensure reward shaping provides meaningful signal for both exploration utility and execution success.
- **Schema Grounding**: Mapping natural language references to actual tables/columns. *Why needed*: Prevents generation from referring to non‑existent schema elements. *Quick check*: Check that the proposed schema contains only columns returned by exploration steps.
- **Multi‑Turn Interaction**: Sequential decision making across phases. *Why needed*: Unknown schemas require progressive information gathering; one‑shot generation is insufficient. *Quick check*: Analyze average number of turns per successful query; ensure a clear termination condition.
- **Reward Isolation**: Separating exploration and execution reward streams. *Why needed*: Avoids credit assignment conflicts that could destabilize learning. *Quick check*: Inspect advantage masks to confirm that only tokens belonging to a given track receive its reward gradient.
- **Unknown Schema Scenario**: The core problem definition. *Why needed*: Reflects real‑world deployment where database schemas are large, dynamic, and not pre‑documented. *Quick check*: Assess whether evaluation benchmarks truly hide the schema until exploration begins.

## Architecture Onboarding
**Component Map**  
User Query -> Explore Agent -> Database Tool -> Schema History -> Propose Agent -> Proposed Schema -> Generate Agent -> SQL Query -> Database Execution -> Confirm Agent -> Rewards & Feedback -> (back to Explore if needed)

**Critical Path**  
1. User issues a natural language question.  
2. Explore Agent selects an introspection action (e.g., `SHOW TABLES`, `DESCRIBE`).  
3. Database Tool returns results; Schema History is updated.  
4. Propose Agent analyzes the History and emits a concrete grounding (relevant tables/columns).  
5. Generate Agent produces a SQL query conditioned on the grounding.  
6. SQL is executed; result (success/failure, intermediate data) is captured.  
7. Confirm Agent checks correctness; if correct, terminate; otherwise, loop back with feedback.

**Design Tradeoffs**  
- *Exploration depth vs. latency*: More turns yield better schema coverage but increase response time.  
- *Tool reliability*: The pipeline assumes the database tool behaves correctly; malformed exploration queries can derail learning.  
- *Separate policies*: Dual‑Track GRPO may maintain distinct policy networks for explore and generate, raising complexity but allowing specialization.  
- *Decoding strategy*: Results are reported with greedy decoding; sampling could improve robustness at the cost of determinism.

**Failure Signatures**  
- Infinite exploration loops (Explore agent asks irrelevant or repetitive questions).  
- Proposed schema contains columns never seen in exploration (hallucination).  
- Generated SQL fails syntax/semantics without recovery.  
- Misaligned reward masking leads to degenerate policies (e.g., explore agent ceases exploration).  

**First Three Experiments**  
1. Evaluate TRUST‑SQL on BIRD‑Dev with greedy decoding to establish the reported 64.9% (4B) / 65.8% (8B) accuracy.  
2. Ablate the Explore phase: provide no schema and observe the degradation in execution accuracy.  
3. Compare Dual‑Track GRPO against standard GRPO on BIRD‑Dev to measure the 9.9% relative gain.

## Open Questions the Paper Calls Out
The paper highlights several open questions and future research directions:
- How does TRUST-SQL scale to larger model sizes (e.g., 70B parameters) and different architectural families (e.g., encoder‑decoder)?
- Can the system generalize across diverse SQL dialects (T‑SQL, PL/pgSQL) and domain‑specific schema designs (healthcare, finance)?
- What are the computational costs and latency implications of multi‑turn exploration in real‑world deployments?
- How robust is the approach to schema noise (e.g., column name corruption) and dynamic schema changes?
- Can the exploration efficiency be improved to reduce the number of turns required?

## Limitations
- **Scalability**: Claims are based on 4B/8B models; performance on larger architectures (e.g., 70B+) or different families (e.g., encoder‑decoder) is unknown.
- **Generalization**: Benchmarks may not capture full variability of real‑world SQL dialects (T‑SQL, PL/pgSQL) or domain‑specific schema designs (healthcare, finance).
- **Real‑world practicality**: No evidence on computational cost of multi‑turn exploration, latency in production, or user interaction design for non‑experts.

## Confidence
- Four‑phase protocol & Dual‑Track GRPO design: High
- Performance gains on benchmarks: Medium
- Unknown schema scenario definition: High
- Real‑world applicability: Low

## Next Checks
1. Test on a held‑out, high‑diversity industrial dataset with zero overlap with training benchmarks to measure true generalization.
2. Ablate the exploration phase under controlled schema noise (10%/30%/50% column name corruption) to quantify failure modes and recovery rates.
3. Scale evaluation to models >13B parameters (e.g., Llama‑3.1 70B, GPT‑4o‑mini) using identical protocols to verify if gains are architecture‑agnostic.
