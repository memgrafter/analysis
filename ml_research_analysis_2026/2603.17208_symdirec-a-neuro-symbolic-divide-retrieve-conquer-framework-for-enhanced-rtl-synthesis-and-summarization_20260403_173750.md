# SYMDIREC: A Neuro-Symbolic Divide-Retrieve-Conquer Framework for Enhanced RTL Synthesis and Summarization

## Quick Facts
- **arXiv ID**: 2603.17208
- **Source URL**: https://arxiv.org/abs/2603.17208
- **Reference count**: 14
- **Primary result**: ~20% higher Pass@1 for RTL synthesis and 15-20% ROUGE-L improvement for summarization over baselines, supporting both Verilog and VHDL without LLM fine‑tuning.

## Executive Summary
SYMDIREC is a neuro-symbolic framework designed to improve large language model (LLM) performance on RTL synthesis (natural language to HDL) and summarization (HDL to natural language). It addresses the challenges posed by rigid HDL syntax and poor natural language alignment by dividing tasks into symbolic subgoals, retrieving relevant code with a fine-tuned symbolic retriever, and conquering via LLM-guided verification and assembly. Experiments on Verilog-Eval and VHDL-Eval benchmarks demonstrate significant gains: approximately 20% higher Pass@1 for synthesis and 15-20% ROUGE-L improvement for summarization compared to prompting and retrieval-augmented generation baselines. The approach supports both Verilog and VHDL without requiring fine-tuning of the LLM itself, highlighting the effectiveness of symbolic guidance.

## Method Summary
The SYMDIREC pipeline comprises three stages. In the Divide stage, an LLM (e.g., GPT‑4o) parses the input—either a natural language specification or RTL code—into a set of subcomponents. For synthesis, each subcomponent yields a textual description and a symbolic logic expression (Boolean/dataflow); for summarization, the RTL is segmented into AST blocks, each abstracted into a symbolic representation. Next, in the Retrieve stage, a fine‑tuned dual‑encoder retriever (based on CodeT5+) encodes both the natural language description and the symbolic expression to form a joint query. This query searches a Milvus vector database storing the RTL‑IR knowledge base (∼50.5k aligned triplets) and returns the top‑k relevant entries. The retriever is trained using a multiple‑negatives ranking loss on the RTL‑IR dataset. Finally, in the Conquer stage, an LLM scores each retrieved candidate against the subcomponent’s description and symbolic logic, selects the best match, and assembles all selected subcomponents into a coherent final output (RTL module or summary). Orchestration is managed via LangChain. No LLM fine‑tuning is required; only the retriever is domain‑adapted.

## Key Results
- ~20% higher Pass@1 on Verilog-Eval and VHDL-Eval for RTL synthesis.
- 15-20% ROUGE‑L improvement for RTL summarization.
- Outperforms prompting and RAG baselines; works for both Verilog and VHDL without LLM fine‑tuning.

## Why This Works (Mechanism)
### Symbolic Decomposition
The framework decomposes RTL tasks into smaller subcomponents, each paired with a symbolic logic expression (Boolean/dataflow). This structured intermediate representation improves retrieval precision and generation correctness by capturing functional intent more precisely than natural language alone. The LLM generates both a textual description and a symbolic expression for each subcomponent. Evidence: the abstract and Section 3.2 describe decomposition prompts and dual outputs. A break condition arises when symbolic expressions are incomplete or inconsistent (~8–10% of subcomponents), degrading retrieval and final performance.

### Fine-Tuned Symbolic Retriever
A dual-encoder retriever encodes natural language descriptions and symbolic logic separately, concatenates them, and projects to a joint query vector. It retrieves candidates from a vector database (Milvus) by cosine similarity. The retriever is fine‑tuned on the RTL‑IR dataset of aligned triplets using multiple‑negative ranking loss. The combination of textual and symbolic cues yields richer query representations, leading to better semantic alignment with code snippets. Evidence: abstract and Section 3.3 detail architecture and training. Potential breakdown: poor fine‑tuning data or overly fragmented symbolic expressions cause mismatches.

### LLM-Guided Verification and Assembly
For each subcomponent, the LLM scores retrieved candidates' alignment with the description and symbolic logic, selects the best, and then assembles all verified subcomponents into final output. This ensures functional correctness and structural coherence. The LLM's self‑scoring leverages its reasoning abilities; assembly ensures naming consistency and correct connectivity. Evidence: abstract and Section 3.4 outline verification and assembly prompting. Failure occurs when retrieved candidates include distractors or when the LLM integrates incorrectly (~6‑8% of subcomponents), especially in hierarchical designs.

## Architecture Onboarding
### Component Map
Input specification → LLM decomposition (Divide) → joint query (NL + symbolic) → Milvus vector search (Retrieve) → candidate retrieval → LLM verification and assembly (Conquer) → final output.

### Critical Path
The pipeline follows a linear sequence: input → symbolic decomposition into N subcomponents → parallel retrieval of k candidates per subcomponent → LLM verification scoring → selection of top candidate per subcomponent → LLM assembly → final output. Retrieval and verification are parallelized across subcomponents.

### Design Tradeoffs
- **Decomposition granularity (N)**: Too small (N=2) may miss modularity; too large (N>6) fragments semantics. Empirically, N≈4 is optimal; adjust for task complexity.
- **Retrieval depth (k)**: Larger k increases chance of correct snippet but adds noise. Performance peaks at k≈5; beyond that gains diminish.
- **LLM choice**: GPT‑4o yields higher accuracy but is costly/closed; Llama‑3 (70B) is open but weaker. Trade off between performance and accessibility.
- **Retriever model**: Code‑specific models (CodeT5+) outperform general text embeddings (Stella‑400m) despite smaller embedding size, due to pre‑training on code.

### Failure Signatures
- **Decomposition errors**: Symbolic expressions malformed, incomplete, or inconsistent (~8-10% of subcomponents). Manually inspect symbolic outputs for complex specs.
- **Retrieval mismatches**: Top‑k candidates lack functional correctness or contain distractors (~12-15%). Monitor NDCG@1 on validation set; if below 0.65, consider more fine‑tuning data.
- **Assembly failures**: LLM integrates verified snippets incorrectly (signal mismatches, missing connections). Common in hierarchical designs; check for cross‑module signal errors.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: How can SYMDIREC's symbolic decomposition be made robust when using smaller or less capable LLMs that may generate incomplete or inconsistent symbolic expressions, which currently degrades performance?
- **Basis in paper**: Limitations state: "Symbolic decomposition depends on the LLM’s ability to generate well‑formed symbolic expressions. Smaller or less capable models may produce incomplete or inconsistent decompositions, diminishing the symbolic scaffolding benefits..."
- **Why unresolved**: The framework's effectiveness hinges on high‑quality symbolic decomposition; weaker models lead to performance similar to NL‑only queries, limiting accessibility.
- **What evidence would resolve it**: Empirical studies testing decomposition robustness across LLM sizes, or development of alternative decomposition methods (e.g., fine‑tuned smaller models, rule‑based extraction) that maintain symbolic quality with limited resources.

### Open Question 2
- **Question**: What improvements to the LLM‑guided verification and assembly stage can reduce failures when retrieved candidate sets contain distractors or partially matching snippets, which currently cause a 6‑8% error rate in sub‑components?
- **Basis in paper**: Error Analysis reports: "LLM Assembly & Verification Failures: When retrieved candidates are correct, the LLM occasionally fails to integrate them properly... observed in roughly 6‑8% of sub‑components." Limitations also note failures with distractors.
- **Why unresolved**: Even with correct retrieval (SYMDIREC‑GT), assembly errors persist, indicating a gap in the LLM's ability to filter and integrate candidates under noise.
- **What evidence would resolve it**: Ablation experiments with enhanced verification prompts, symbolic consistency checks during assembly, or candidate re‑ranking based on multiple criteria, demonstrating reduced error rates in standardized benchmarks.

### Open Question 3
- **Question**: How can SYMDIREC be extended to handle hierarchical, multi‑file RTL designs with cross‑module dependencies, given its current restriction to single‑file projects?
- **Basis in paper**: Limitations state: "The current pipeline is restricted to single‑file RTL designs and does not support hierarchical or multi‑file projects... Scaling to such designs may require advanced AST processing, block‑ and function‑level chunking, and multi‑level summarization strategies."
- **Why unresolved**: Real‑world hardware designs are modular and span multiple files; without support for inter‑module dependencies, SYMDIREC cannot be applied to complex industrial designs.
- **What evidence would resolve it**: Development of a multi‑level decomposition and retrieval mechanism that tracks symbolic dependencies across modules, evaluated on multi‑file RTL benchmarks with measured impact on synthesis and summarization quality.

## Limitations
- Symbolic decomposition may produce invalid expressions in ~8–10% of cases, limiting gains on complex modules.
- Retriever training details and dataset construction are not fully disclosed, hindering reproducibility.
- The framework relies on proprietary LLMs (GPT‑4o) for core stages; performance with open models may differ.

## Confidence
