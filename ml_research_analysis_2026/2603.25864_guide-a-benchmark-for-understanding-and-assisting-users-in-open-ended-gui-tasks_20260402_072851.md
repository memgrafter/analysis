# GUIDE: A Benchmark for Understanding and Assisting Users in Open-Ended GUI Tasks
## Quick Facts
- **arXiv ID:** 2603.25864
- **Source URL:** https://arxiv.org/abs/2603.25864
- **Reference count:** 40
- **Primary result:** AI models struggle on open-ended GUI assistance tasks; providing structured user context (behavior state, intent) can boost help prediction accuracy by up to 50.2 percentage points.

## Executive Summary
GUIDE is a benchmark designed to evaluate AI models on understanding user intention and providing assistance in open-ended graphical user interface (GUI) workflows. It defines three sequential tasks: Behavior State Detection (classifying the user's cognitive phase), Intent Prediction (identifying the short-term goal), and Help Prediction (detecting need and suggesting content). The dataset comprises 67.5 hours of screen recordings from novice users interacting with 10 different software applications, with annotations at fine-grained temporal segments.

State-of-the-art multimodal models performed poorly on the baseline (video-only) setting, achieving only 44.6% accuracy on Behavior State Detection and 55.0% on Help Content Prediction. However, augmenting the models with oracle structured user context—specifically the correct behavior state and intent—led to dramatic improvements, raising Help Prediction accuracy by up to 50.2 percentage points. These results underscore that effective assistance in complex software requires deeper, temporally-aware user modeling beyond simple action recognition.

## Method Summary
The GUIDE benchmark collects screen recordings of novice users performing self-directed tasks across ten common desktop applications (e.g., spreadsheet, image editor). The recordings are segmented and annotated with three labels: (1) behavior state (9 categories like Frustration, Exploration), (2) short-term intent (4 multiple-choice options), and (3) help need (binary) plus appropriate help content (4 categories). Eight multimodal models are evaluated on these tasks under varying context conditions: using only video frames, or additionally providing oracle behavior state, or both behavior state and intent as textual prompts. An online simulation protocol progressively reveals more of the video to study the effect of temporal context accumulation. The experimental design isolates the impact of structured user understanding on assistance quality.

## Key Results
- Baseline model accuracies are modest: 44.6% for Behavior State Detection and 55.0% for Help Content Prediction.
- Adding oracle behavior state and intent improves Help Prediction accuracy by up to 50.2 percentage points, with the largest gains for InternVideo2.5-8B (50.19 pp).
- Models struggle most with subtle states like Frustration (0.07 accuracy) and Debugging (0.04), often misclassifying them as Performing Actions or Exploration.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Providing an explicit **behavior state label** (e.g., *Frustration*, *Exploration*) disambiguates raw visual action patterns, allowing the model to infer user needs more accurately than from motion alone.
- **Mechanism:** The model receives a structured semantic tag that summarizes the user's cognitive phase (Planning, Execution, etc.). This tag acts as a high-level prior that constrains the interpretation of subsequent visual and temporal cues, bridging the gap between low-level pixel changes and high-level assistance decisions.
- **Core assumption:** Behavior states are **meaningfully distinguishable from visual features alone** (without narration) and provide information orthogonal to the raw action sequence.
- **Evidence anchors:**
  - [abstract] "...providing structured user context—such as inferred behavior state and intent—substantially improved performance, raising Help Prediction accuracy by up to 50.2 percentage points."
  - [section 4.3.3] "Providing the user’s behavior state led to consistent and significant improvements in Help Need Detection across all models..."
  - [corpus] Weak direct corpus evidence; neighboring papers (e.g., ScreenLLM, YETI) focus on action prediction or proactive intervention but not on explicit behavior-state conditioning for help.
- **Break condition:** If behavior state labels themselves are highly noisy or uninterpretable by the model (e.g., the taxonomy is not visually grounded), the conditional performance gain would disappear.

### Mechanism 2
- **Claim:** **Intent prediction** serves as a necessary intermediate representation that translates a generalized behavior state into a specific, actionable user goal, which is critical for determining the correct help content.
- **Mechanism:** Behavior state provides *mode* (e.g., "debugging"), but intent provides *object* (e.g., "align text boxes"). The model uses the intent to filter the space of possible assistance types (e.g., "explain feature" vs. "suggest alternative") from a large pool, making the help content prediction tractable.
- **Core assumption:** Short-term user goals (intent) are **recoverable from short video segments** and are a deterministic or highly probable function of the current behavior state and visual context.
- **Evidence anchors:**
  - [abstract] "...providing structured user context—such as inferred behavior state and intent—substantially improved performance..."
  - [section 4.3.3] "Incorporating user intent led to substantial improvements across models, with the largest gain in InternVideo2.5-8B [43] at 50.19 percentage points, highlighting the importance of understanding both user state and intent for providing targeted support."
  - [corpus] Neighbors (e.g., ProactiveVA, EARL) investigate intent recognition but GUIDE uniquely shows the *marginal value* of intent *on top of* behavior state for assistance.
- **Break condition:** If intents are too fine-grained or ambiguous (low inter-annotator agreement), the provided intent context would introduce noise rather than signal, harming performance.

### Mechanism 3
- **Claim:** **Temporal context accumulation** (seeing more of the ongoing segment) progressively improves all tasks, indicating that user state and intent are **non-stationary and require evidence integration over time**.
- **Mechanism:** Early frames may show only initiation of an action (e.g., a click), while later frames reveal the outcome (e.g., an error dialog). Models benefit from longer context windows to resolve ambiguities in initial actions and detect patterns (e.g., repeated undos) signaling frustration.
- **Core assumption:** User behavior in open-ended GUI workflows is a **temporal process** where later observations causally depend on or are influenced by earlier ones, and the *precise moment* of need is often only clear in hindsight.
- **Evidence anchors:**
  - [section 4.3.4] "In our online simulation experiment... we observe consistent performance gains across all four tasks... with larger and more consistent gains across all tasks, compared to the smaller open-source models, indicating a strong ability to integrate growing context into more accurate predictions."
  - [section 3.1] "The average video duration is 33 minutes and 44 seconds... This extended duration ensures that the dataset captures the full evolution of user tasks, including periods of exploration, struggle, and error recovery."
  - [corpus] Neighbors (e.g., VideoWebArena, WorldGUI) evaluate long-horizon tasks but GUIDE explicitly isolates the *temporal completeness* variable in an online protocol.
- **Break condition:** If key signals (like a frustrated sigh or external help switch) occur only at the very end of a segment, and models are not evaluated with the full segment, the benefit of temporal accumulation would plateau or reverse.

## Foundational Learning
### Hierarchical Intent Modeling
- **Why needed here:** The benchmark decomposes assistance into three linked stages (State → Intent → Help). A learner must understand that *what* the user is doing (state) informs *what* they want (intent), which then determines *what* help is appropriate. This is a causal chain, not independent predictions.
- **Quick check question:** If a user is in the *Debugging* state and their intent is "fix audio sync issue," what type of help is most likely needed (e.g., "explain a setting," "suggest a tool," "diagnose an error")?

### Open-Ended vs. Closed-Task Semantics
- **Why needed here:** GUIDE focuses on **novice users in open-ended tasks**, where goals evolve and multiple valid solutions exist. This contrasts with prior benchmarks that evaluate step-by-step replication of a fixed expert trajectory. The learner must handle ambiguity and exploration, not just recognize a canonical action sequence.
- **Quick check question:** How might the visual signature of "Exploration and Decision-Making" differ between a user trying to format a chart and a user trying to design a poster, even if both involve clicking different font menus?

### Multimodal Temporal Reasoning from Pixels
- **Why needed here:** The input is **screen-recorded video without narration** at test time. The model must infer cognitive states from visual dynamics: cursor hesitations, repeated undos, UI state changes, and Switch-to-browser events. This requires learning mappings from low-level motion patterns to high-level mental states.
- **Quick check question:** What sequence of visual cues (e.g., mouse movements, UI updates) might indicate *Frustration* versus *Performing Actions*?

## Architecture Onboarding
### Component Map
1. **Visual Encoder:** Processes sampled video frames (e.g., ViT, CLIP-ViT) into spatial features.
2. **Temporal Aggregator:** Models frame-to-frame dynamics (e.g., VideoMAE, TimeSformer, or simple MLP over frame features) to capture action sequences.
3. **Context Injector:** A module to condition the temporal representation on auxiliary context (previous behavior state, predicted intent). This could be cross-attention, feature concatenation, or prompt-based conditioning for LLMs.
4. **Task-Specific Heads:** Separate classifiers/regressors for (a) 9-way behavior state, (b) 4-way intent MCQ, (c) binary help-need + 4-way help-content.

### Critical Path
The baseline pipeline: [Sampled Frames] → Visual Encoder → Temporal Aggregator → Task Heads → Predictions.  
The improved pipeline introduces conditional context: [Sampled Frames] → Visual Encoder → Temporal Aggregator → [Conditional Context (State/Intent)] → Context Injector → Task Heads → Predictions.

### Design Tradeoffs
- **Context Injection Timing:** Early injection (fuse with visual features) vs. late injection (fuse with temporal sequence). Late injection is simpler and matches the prompt-based evaluation in the paper.
- **Temporal Window Size:** Longer windows capture more context but increase compute and risk dilution of key signals. GUIDE uses uniform sampling of 32 frames from a segment; the segment length varies by task (~14s for state, ~25s for intent/help).
- **Context Source:** True user context is latent. The system must infer it *or* be provided oracle context. The tradeoff is between training a single model to do all three tasks (cascade errors) vs. assuming gold context for help prediction (oracle setting).

### Failure Signatures
- **High confusion matrix errors:** Model consistently misclassifies *Frustration* and *Debugging* as *Performing Actions* or *Exploration*. Indicates failure to recognize "struggle" visual patterns (repeated clicks, long pauses, undo sequences).
- **Low recall in Help Need Detection:** Model predicts "no help" for segments labeled "help needed." Shows insensitivity to implicit cues (narration of confusion) or overt external help-seeking (browser open).
- **Minimal gain from added context:** If adding behavior state or intent does not improve help prediction, the context injection mechanism is broken, or the context labels are not visually grounded.

### First 3 Experiments
1. **Reproduce Baseline:** Train/evaluate a single multimodal model (e.g., Qwen3-VL) on all three tasks *without* any external context (video only). Record accuracies to establish the strong baseline (expect ~44% state, ~55% help-content as per paper).
2. **Evaluate Oracle Context Benefit:** For the *same* model checkpoints, run evaluation with **oracle context** provided as text prompts (as in paper's `+ Behavior State` and `+ Behavior State + Intent` settings). Measure the delta to quantify the maximum potential value of structured user understanding.
3. **Train a Cascaded System:** Train a dedicated model for Behavior State Detection. Use its *predicted* state (not oracle) as context for a second model trained for Help Prediction (with or without predicted intent). Compare performance to the single-model-with-oracle-context baseline to measure **pipeline error propagation**.

## Open Questions the Paper Calls Out
1. **Question:** How can multimodal models be improved to accurately detect subtle user behavior states like *Frustration* and *Debugging*, which are frequently misclassified as *Performing Actions* or *Exploration and Decision-Making*?
   - **Basis in paper:** The confusion matrix (Figure C4) and analysis (Section 4.3.1) show models achieve near-zero accuracy (0.07 and 0.04) on *Frustration* and *Debugging*, often misinterpreting struggle signals as deliberate progress.
   - **Why unresolved:** Current models lack the temporal reasoning and nuanced visual cue integration needed to distinguish between trial-and-error and confident execution, limiting their ability to recognize when users are stuck.
   - **What evidence would resolve it:** Higher accuracy on *Frustration* and *Debugging* in the Behavior State Detection task, especially when models incorporate longer temporal context or auxiliary cues (e.g., hesitations in audio, though evaluation is vision-only).

2. **Question:** What specific structured user context (behavior state, intent, temporal history) is most effective for accurate *Help Prediction*, and how should models integrate these cues to avoid over-reliance on any single signal?
   - **Basis in paper:** Providing behavior state and intent context improved Help Prediction accuracy by up to 50.2 percentage points (Abstract; Section 4.3.3), but the optimal combination and fusion mechanism remain unclear.
   - **Why unresolved:** While context helps, behavior context alone gave only modest gains for *Intent Prediction* but larger improvements for *Help Need Detection*, suggesting task-specific context utility that is not well understood.
   - **What evidence would resolve it:** Systematic ablation studies varying context types (e.g., only behavior state vs. only intent vs. both) across models, with analysis of which context most reduces specific error types in help-related tasks.

3. **Question:** Why do current models exhibit very low recall in *Help Need Detection* (often <37% except Gemini-2.5-Pro), missing many genuine help-seeking moments, and how can recall be improved without sacrificing precision?
   - **Basis in paper:** Section 4.3.3 reports recall scores well below 37% for most models on Help Need Detection, despite some achieving moderate precision.
   - **Why unresolved:** Low recall indicates models fail to identify situations where users actually need help, potentially due to implicit cues (e.g., confusion, external help-seeking) not being captured by visual-only input or model biases toward predicting “no help.”
   - **What evidence would resolve it:** Error analysis categorizing missed help cases (e.g., *Frustration* without explicit narration, subtle external help cues) and development of models that better link behavior states to help needs, perhaps by improving detection of negative states.

4. **Question:** How can models better leverage temporal context across video segments to perform *real-time proactive assistance*, given that online evaluation showed performance gains but absolute accuracy remains low even with full context?
   - **Basis in paper:** In the online setting (progressively more video), all tasks showed consistent improvement (Figure 4), but starting accuracies were poor (e.g., <30% on Behavior State Detection at 25% video).
   - **Why unresolved:** Proactive agents must anticipate needs from incomplete, evolving information. Current models’ limited gains suggest inadequate temporal reasoning and memory mechanisms for tracking user states over time.
   - **What evidence would resolve it:** Implementation of memory-augmented architectures (e.g., recurrent or transformer-based history) that maintain evolving user state representations, evaluated in streaming scenarios with low latency, showing significantly higher early-segment accuracy.

## Limitations
- Generalizability is limited to novice users and ten specific desktop applications; it is unclear whether findings transfer to experts or vastly different software domains.
- The assumption that behavior states are visually distinguishable without strong narration lacks direct validation; human annotation studies are needed to confirm the visual grounding of the taxonomy.
- Performance improvements reported with oracle context may not be achievable in practice due to error propagation in cascaded systems that rely on predicted context.

## Confidence
- **Structured user context improves Help Prediction accuracy (up to 50.2 pp):** High.
- **Behavior states provide information orthogonal to raw action sequences:** Medium.
- **Temporal context accumulation yields consistent gains across workflows and software:** Low.

## Next Checks
1. **Validate Taxonomy Visual Grounding:** Conduct a human study where annotators, given only short GUI video clips, assign behavior state labels from the GUIDE taxonomy; measure inter-annotator agreement against the paper's original labels.
2. **Measure Cascaded System Degradation:** Implement a pipeline: (a) train a model for Behavior State Detection, (b) use its predicted state (and a separate intent predictor) as context for a Help Prediction model; compare final accuracy to the oracle-context baseline.
3. **Cross-Domain Generalization Test:** Apply a trained GUIDE model (video-only and oracle-context versions) to a new, held-out software application from a different category (e.g., a video editor or IDE) to measure the drop in performance and identify domain-specific failure modes.
