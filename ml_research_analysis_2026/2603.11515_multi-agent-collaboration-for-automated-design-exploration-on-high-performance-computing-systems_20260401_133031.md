# Multi-Agent Collaboration for Automated Design Exploration on High Performance Computing Systems

## Quick Facts
- **arXiv ID:** 2603.11515
- **Source URL:** https://arxiv.org/abs/2603.11515
- **Reference count:** 40
- **Primary result:** Automated multi-agent system (MADA) improved the quality-of-interest metric by 10% over 40 designs in ~40 minutes on HPC and found the global optimum in under 40 evaluations with a surrogate model.

## Executive Summary
The paper presents MADA, a multi-agent framework powered by large language models (LLMs) to automate scientific design exploration on high-performance computing (HPC) systems. Using Richtmyer–Meshkov Instability (RMI) suppression as a case study, MADA decomposes the workflow into specialized agents: a Job Management Agent (JMA) for HPC scheduling, a Geometry Agent (GA) for mesh generation, and an Inverse Design Agent (IDA) for exploration. Agents are coordinated via AutoGen and integrate tools through the Model Context Protocol (MCP). Results demonstrate a 10% improvement in the quality-of-interest metric over 40 designs in ~40 minutes with HPC simulations, and with a surrogate model, the IDA located the global optimum in under 40 evaluations, matching gradient-based methods while providing interpretable reasoning. The system reduces manual workflow setup and enables scalable, automated exploration for high-dimensional parameter spaces.

## Method Summary
MADA automates iterative design loops where designs are proposed, simulated, and refined based on a quality-of-interest (QoI) metric. The task targets RMI suppression with parameters defining energy profiles or spline points. Inputs include parameter bounds, simulation outputs from the Laghos hydrodynamics code, or a pre-trained surrogate model. The objective is to minimize a QoI combining jet length and velocity terms. The method uses three LLM-driven agents: JMA schedules HPC jobs via Flux, GA generates meshes via Cubit/PMesh, and IDA proposes designs and analyzes results. Agents communicate through AutoGen’s chat framework and access tool functionality via MCP servers, which wrap each tool (Flux, Cubit, Laghos, Surrogate) with a standardized JSON-RPC interface. The iterative loop: GA creates a mesh template, IDA samples initial designs, JMA submits an ensemble to HPC, JMA polls until completion, IDA extracts QoI, and the cycle repeats with refined proposals.

## Key Results
- With HPC simulations (Laghos), MADA improved the QoI by 10% (from 4.1 to 3.7) over 40 designs in approximately 40 minutes.
- Using a surrogate model, the IDA found the global optimum (objective value 9) for minimization in under 40 evaluations, matching gradient-based optimization but with interpretable reasoning.
- The framework reduces manual workflow setup and enables scalable, automated design exploration for high-dimensional parameter spaces.

## Why This Works (Mechanism)
1. **Modular Specialization via Agent Decomposition**
   - **Claim:** Decomposing the scientific design loop into specialized agents (JMA, GA, IDA) reduces orchestration overhead and manages LLM context limits.
   - **Mechanism:** Each agent handles a distinct, bounded sub-task, confining the LLM's reasoning to domain-relevant information and enabling parallel, focused execution. State is passed via structured messages rather than a monolithic prompt.
   - **Core assumption:** Scientific workflows can be partitioned into logically independent stages with well-defined state transitions.
   - **Evidence anchors:** Paper states agents "modularizes the scientific design workflow" and each "focuses on its area of expertise" [abstract, III.A]. Neighbor papers use similar decomposition but no direct evidence for this partitioning's causal effect.

2. **Standardized Tool Access via Model Context Protocol (MCP)**
   - **Claim:** MCP provides a uniform interface for LLM-based agents to discover, invoke, and interpret results from diverse HPC tools without custom per-tool logic.
   - **Mechanism:** MCP servers wrap domain-specific tools, exposing tools, resources, and prompts via JSON-RPC. Agents use a single client library to call functions, decoupling reasoning from tool-specific APIs.
   - **Core assumption:** Tool functionality can be captured by discrete, stateless function calls with well-defined inputs/outputs.
   - **Evidence anchors:** Section II.C describes MCP architecture; Section III.C states that wrapping tools in MCP servers means agents written for one tool work with any other. No external validation from neighbor papers.

3. **LLM-Driven Adaptive Workflow Orchestration**
   - **Claim:** An LLM-based planner (via AutoGen) dynamically determines the next agent action based on conversation history, enabling adaptation to unexpected results without pre-defined graphs.
   - **Mechanism:** A "context analyzer" synthesizes chat history, a "selector" chooses the next agent, creating a reactive loop that replans based on new data (e.g., mesh failure triggers retry).
   - **Core assumption:** The LLM can reliably identify the correct next subtask in a complex scientific loop.
   - **Evidence anchors:** Section III describes LLM-based reasoning to decompose tasks, allocate work, and adapt execution. Moderate support from neighbor papers on multi-agent reasoning, but MADA's selector is not directly evidenced elsewhere.

## Foundational Learning
- **Multi-Agent System Design (Specialization & Coordination)**
  - **Why needed:** MADA replaces manual/single-agent workflows with coordinated specialists. Engineers must understand why to split roles (JMA/GA/IDA) and how they communicate (message passing, shared state) vs. monolithic agents.
  - **Quick check:** If the Geometry Agent fails to generate a valid mesh, what should the system's next action be, and which component decides?
- **Tool Integration Patterns (MCP Client-Server)**
  - **Why needed:** All agent capabilities depend on external tools. Engineers must grasp the MCP pattern to wrap new simulation codes or schedulers correctly.
  - **Quick check:** What are the three MCP primitive types, and which one exposes a function that runs a simulation and returns a file path?
- **HPC Job Scheduling for Ensembles (Flux Concepts)**
  - **Why needed:** The JMA manages large, asynchronous job ensembles. Engineers need to understand dependency handling, resource specification, and status polling in HPC.
  - **Quick check:** What is the key difference between `submit_job()` and `submit_jobs_async()` in the Flux MCP server, and when should each be used?

## Architecture Onboarding
- **Component map:** Agents (JMA, GA, IDA) -> MCP Servers (Flux, Cubit, Laghos, Surrogate) -> Coordination Layer (AutoGen Selector/ContextAnalyzer). Knowledge: RAG vector DBs for Cubit/PMesh docs; geometric graph serializer. UIs: CLI/GUI.
- **Critical path (iterative design loop)**:
  1. User provides objective, parameters, bounds.
  2. GA generates initial mesh template via Cubit/PMesh MCP.
  3. IDA proposes initial design batch (e.g., Latin hypercube).
  4. JMA submits batch: calls Laghos MCP `generate_runs()` then Flux MCP `submit_jobs_async()`.
  5. JMA polls Flux MCP `check_job_status()` until complete.
  6. JMA collects outputs; IDA calls Laghos MCP `get_qoi()` or Surrogate MCP `get_objective()`.
  7. IDA reasons, ranks, proposes next batch; repeat from step 4.
- **Design tradeoffs**:
  - Modularity vs. Integration Cost: Adding a new simulation code requires a new MCP server (low agent change) but development effort. Deep tool customization may leak into GA prompts.
  - LLM Reasoning vs. Predictability: Adaptive orchestration handles surprises but introduces non-determinism and "agent drift" risk.
  - Context Management: RAG and graphs mitigate context limits, but long histories risk overflow; system truncates/summarizes.
- **Failure signatures**:
  - Agent deadlock: Selector cycles between agents without progress (e.g., GA↔IDA) with no tool calls to JMA.
  - Tool invocation failure: MCP server errors (e.g., invalid mesh from Cubit) with stack traces in agent messages.
  - LLM hallucination in code generation: GA produces invalid Cubit DSL; Cubit MCP parse error.
  - QoI extraction failure: `get_qoi()` returns NaN/error; IDA may request re-run or heuristic fallback.
- **First 3 experiments**:
  1. **Unit Test: Agent-Tool Connectivity.** For each MCP server, craft minimal agent prompt to invoke primary tool (e.g., `submit_job` with trivial command, `create vertex` in Cubit). Verify successful JSON-RPC exchange and side-effects.
  2. **Integration Test: Single Design Cycle.** Use trivial 2–3 parameter space. Run full loop: GA generates mesh, JMA submits 1-job Laghos run (short test case), IDA extracts QoI. Confirm data flows and final QoI logged.
  3. **Regression Test: Known Optimum Recovery.** For surrogate-based RMI problem, run with fixed random seed. Verify discovery of global optimum within ~40 evaluations. Monitor trace for expected reasoning pattern (e.g., "sign alternation matters").

## Open Questions the Paper Calls Out
1. Does MADA's sampling-based design exploration reliably find global optima in complex, multimodal design spaces, or does it risk converging to local optima? The paper acknowledges no guarantee and evaluates only one RMI case study.
2. How does the stochastic nature of LLMs impact the reproducibility and consistency of MADA's design exploration outcomes across multiple independent runs? The paper notes variations may occur but provides no statistical analysis.
3. What is the practical development overhead and scalability limitations when integrating new simulation codes into MADA via MCP servers? The paper mentions initial effort but no quantification across diverse codes.
4. To what extent can MADA's multi-agent architecture and tool integration pattern be successfully applied to scientific design problems outside fluid dynamics? The framework is described as general-purpose but validated only on RMI suppression.

## Limitations
- Proprietary tool dependencies (Cubit, Flux on Tuolumne, specific Laghos build) block exact replication without access to these restricted systems.
- MCP server implementation details are not fully disclosed; inferred functionality may diverge from actual code.
- Generalizability is unclear; results are limited to one RMI case study with no evaluation in other domains.
- LLM non-determinism could affect reproducibility; fixed seeds not reported for HPC experiments.

## Confidence
- **Core method (agent decomposition + MCP):** Medium. Logical design is coherent and supported internally, but lacks external validation or ablation studies isolating each mechanism's contribution.
- **HPC results (10% QoI improvement):** Medium. Outcome is specific to their infrastructure/tools; surrogate-free HPC loop cannot be independently verified without identical resources.
- **Surrogate-based optimization (global optimum):** Medium-High. The optimization trace and known optimum provide a clear reproducibility target, though LLM reasoning steps remain opaque.
