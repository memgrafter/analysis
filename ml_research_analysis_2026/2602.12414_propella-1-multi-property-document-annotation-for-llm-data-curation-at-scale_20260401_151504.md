# propella-1: Multi-Property Document Annotation for LLM Data Curation at Scale

## Quick Facts
- **arXiv ID:** 2602.12414
- **Source URL:** https://arxiv.org/abs/2602.12414
- **Reference count:** 36
- **Primary result:** A 4B-parameter model annotates documents across 18 structured properties with higher agreement (0.779) against a frontier LLM than much larger general-purpose models, enabling billion-document-scale curation.

## Executive Summary
This paper introduces a paradigm shift from single-score to multi-property document annotation for LLM data curation. The core contribution is propella-1, a family of compact multilingual LLMs (0.6B–4B parameters) that output 18 structured properties per document. This system was deployed to annotate over three billion documents from major pretraining corpora, revealing nuanced quality differences previously masked by scalar scores. The approach demonstrates that small, specialized models can achieve superior agreement with frontier LLMs on structured tasks, making large-scale, interpretable annotation feasible.

## Method Summary
The method involves fine-tuning decoder-only LLMs (Qwen-3 base) to produce JSON annotations conforming to a predefined 18-property schema. Training data is generated by a frontier LLM (Gemini-3-Pro) annotating a diverse multilingual sample using a detailed rubric. Models are trained with a compact system prompt (~800 tokens) that lists properties and enumerated values, internalizing the guidelines. For scalable deployment, inference uses SGLang with llguidance to enforce strict JSON schema conformance and no whitespace, eliminating post-processing. The annotation process is input-heavy (long documents) and output-light (compact JSON), making throughput dominated by prefill speed.

## Key Results
- The 4B propella-1 model achieves a higher overall agreement score (0.779, weighted QWK/F1/IoU) with Gemini-3-Pro than larger open-weight baselines (e.g., Qwen3-30B-A3B-Instruct at 0.700) and Gemini-3-Flash.
- The system successfully annotated over 3 billion documents from corpora like FineWeb-2 and HPLT 3.0, demonstrating operational viability at web scale.
- Multi-property analysis uncovered substantial, previously hidden variations in dataset quality, reasoning depth, and content composition across sources and languages.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Structured multi-property annotation resolves the conflation and interpretability limitations of single scalar quality scores.
- **Mechanism:** The system defines 18 complementary properties across 6 categories (core content, classification, quality & value, audience & purpose, safety & compliance, geographic relevance). A small LLM is fine-tuned to output a JSON document containing a value for each property, enabling flexible, composable filtering predicates (e.g., high reasoning AND low commercial bias).
- **Core assumption:** Data quality is inherently multi-dimensional, and preserving these dimensions yields more actionable curation insights than aggregating them.
- **Evidence anchors:** [abstract] Introduction of 18 properties organized into six categories to replace single scores. [section 3.1] Design philosophy requiring each property to enable a concrete filtering use case and be complementary. [corpus] Neighbors like "Oasis" and "FineWeb" show single-score dominance; propella's multi-dimensional release is novel at billion-document scale.
- **Break condition:** If downstream training experiments (not yet reported) show that multi-property filtering offers no advantage over optimal single-score baselines for key model capabilities.

### Mechanism 2
- **Claim:** Small, specialized models (0.6B–4B) can achieve higher agreement with frontier LLM judges on structured annotation than much larger general-purpose models, making large-scale annotation efficient.
- **Mechanism:** The propella-1 models are decoder-only LLMs (Qwen-3 base) fine-tuned on a dataset of documents annotated by frontier LLMs (Gemini-3-Pro) using the full rubric. A compact system prompt (~800 tokens) suffices because the fine-tuning internalizes the detailed guidelines.
- **Core assumption:** Distilling frontier LLM annotations into a small model preserves annotation quality while drastically reducing cost, and the structured JSON format provides a well-defined learning target.
- **Evidence anchors:** [section 4.1] Choice of decoder-only architecture for native long-document handling and unified JSON output. [section 5.4] The 4B model (0.779 overall agreement) exceeds Gemini-3-Flash and all larger open-weight baselines (e.g., Qwen3-30B-A3B-Instruct at 0.700). [section 6.2] Throughput of 27 docs/sec on H100 (fp8) enables billion-document scaling.
- **Break condition:** Agreement collapses on low-resource languages or niche content types not sufficiently represented in the frontier-LLM-generated training data.

### Mechanism 3
- **Claim:** Web-scale multi-property annotation is feasible via purpose-built serving infrastructure that enforces strict schema conformance, eliminating post-processing.
- **Mechanism:** Inference is served with SGLang using the llguidance backend, which constrains generation to a predefined JSON schema with no whitespace. This guarantees every output is a valid annotation object, removing the need for validation or retries. The input/output asymmetry (long document in, compact JSON out) makes throughput dominated by prefill speed.
- **Core assumption:** Structured output constraints can be efficiently enforced at the decoding level without significant throughput penalty, and schema guarantees eliminate operational complexity at scale.
- **Evidence anchors:** [section 6.1] Use of SGLang + llguidance for strict JSON schema conformance. [section 6.1] Throughput measurements showing prefill-dominated performance (50.1K prompt TPS vs. 3.9K output TPS for 4B fp8). [section 6.2] Successful annotation of ~500M FineWeb-2 documents in 3.5 hours across 3,936 A100 GPUs.
- **Break condition:** Schema enforcement causes exponential latency increases for complex or ambiguous documents, or the serving stack cannot maintain throughput at multi-thousand GPU scale due to coordination overhead.

## Foundational Learning
- **Concept: Scalar vs. Multi-Dimensional Quality Assessment**
  - **Why needed here:** The paper's central premise is that a single score (like FineWeb-Edu's "educational value") discards crucial information (e.g., a document can be educational but commercially biased). Understanding this limitation is key to appreciating propella's design.
  - **Quick check question:** What curation scenarios are impossible with a single quality score but trivial with 18 structured properties?
- **Concept: LLM-as-Judge Distillation**
  - **Why needed here:** propella-1's training data comes from frontier LLM (Gemini-3-Pro) annotations. Understanding the risks of using LLMs as reference annotators (e.g., shared biases, overestimation of agreement) is critical for interpreting the evaluation.
  - **Quick check question:** Why is agreement with a frontier LLM an imperfect proxy for "true" annotation quality, and what specific biases might propagate from Gemini to propella?
- **Concept: Structured Output Generation for Scalability**
  - **Why needed here:** The system's efficiency hinges on generating strict JSON without validation loops. Knowing how tools like llguidance enforce schemas at the sampling level explains the operational viability.
  - **Quick check question:** How does enforcing a JSON schema during decoding (vs. post-hoc validation) impact fault tolerance and throughput in a billion-document pipeline?

## Architecture Onboarding
- **Component map:**
  - Annotation Schema -> Model Family (0.6B, 1.7B, 4B) -> Training Pipeline (Frontier LLM labeling -> Fine-tuning) -> Serving Stack (SGLang + llguidance) -> annotation Dataset (3B+ records)
- **Critical path:** Rubric finalization -> frontier annotation of training sample -> model fine-tuning -> serving stack integration -> large-scale deployment on inference-hive cluster -> dataset publication.
- **Design tradeoffs:**
  - Model size vs. annotation cost: 4B offers best agreement but 0.6B might be sufficient for less critical properties; throughput scales inversely with size.
  - Property coverage vs. complexity: 18 properties are comprehensive but may introduce noise if some are ambiguous for a given document. Adding more properties increases output dimensionality without proportional curation benefit.
  - Multilingual breadth vs. per-language quality: Support for 57 languages risks lower agreement on low-resource languages not well-represented in the frontier-LLM training data.
- **Failure signatures:**
  - Schema violations: Even with llguidance, occasional malformed JSON may occur on extremely corrupted inputs—monitor for parse errors.
  - Property-specific degradation: Sudden drop in agreement for specific properties (e.g., `regional_relevance` on ambiguous documents) indicates rubric ambiguity or training data gaps.
  - Throughput collapse: If prefill TPS plateaus or output TPS dominates, batch sizing or KV cache strategy needs adjustment.
- **First 3 experiments:**
  1. Schema Conformance Stress Test: Feed 10K synthetically corrupted documents (garbled encoding, mixed languages, extreme length) to verify `llguidance` never emits invalid JSON and produces sensible `content_integrity`/`one_sentence_description` fallbacks.
  2. Cross-Language Agreement Audit: Sample 500 documents per language from low-resource families (e.g., Turkic, Austronesian) and measure per-property QWK/F1 against Gemini-3-Pro. Identify languages where `audience_level` or `technical_content` agreement falls <0.6.
  3. Throughput Scaling Curve: Run the 4B model on a single H100 with batch sizes {1, 4, 16, 64, 256} and measure docs/sec, prefill TPS, and memory usage. Find the batch size that maximizes throughput before Attention KV cache swapping degrades prefill speed.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Does filtering training data based on combinations of propella-1's multi-property annotations (e.g., high educational value + high reasoning depth + low commercial bias) improve downstream model performance on reasoning-intensive benchmarks compared to filtering on any single property or a scalar quality score?
- **Basis in paper:** [explicit] "The most important next step is evaluating the downstream training impact of multi-property filtering." (Section 8, Discussion and Future Work).
- **Why unresolved:** The paper demonstrates analytical insights from the annotations but provides no empirical results from actual LLM training experiments using different filtering strategies.
- **What evidence would resolve it:** Ablation studies training models on subsets of a large corpus (e.g., FineWeb-2) filtered by different propella-1 property combinations, with performance comparisons on reasoning, knowledge, and safety benchmarks.

### Open Question 2
- **Question:** To what extent do the propella-1 models inherit and amplify systematic biases present in the frontier LLMs (Gemini-3-Pro) used to generate their training labels, particularly for underrepresented languages and content types?
- **Basis in paper:** [inferred] The paper acknowledges: "the propella-1 models inherit biases from the frontier LLMs used to generate training labels" and notes "LLM-based judges are also known to vary in reliability across languages" (Section 8, Limitations). The evaluation uses Gemini-3-Pro as the sole reference.
- **Why unresolved:** High agreement with a single frontier model does not guarantee correctness; shared biases could lead to consistent but incorrect annotations for certain content or languages.
- **What evidence would resolve it:** Human evaluations on diverse, stratified samples across languages and content categories to measure where propella-1 annotations diverge from human judgment and correlate with known biases in the training LLMs.

### Open Question 3
- **Question:** How transferable are the propella-1 annotation rubrics and model performance across the full 57 supported languages, given that the public annotation release only covers English and 14 European languages?
- **Basis in paper:** [inferred] The paper states models support 57 languages and training data included European, Arabic, Chinese, etc. (Section 4.2, Training Data), but the propella-annotations dataset release is limited: "covers English and 14 European languages" (Section 6.3, The propella-annotations Dataset).
- **Why unresolved:** Performance and rubric validity for non-European languages (e.g., Arabic, Chinese, Thai) are not evaluated in the released dataset or evaluation results, leaving a significant gap in understanding multilingual applicability.
- **What evidence would resolve it:** Evaluation of propella-1 models on a held-out test set of documents for a representative sample of the 43 non-released languages, using human or robust multilingual LLM-as-judge evaluation to measure annotation quality.

### Open Question 4
- **Question:** What are the practical cost-benefit trade-offs of using propella-1 for large-scale annotation versus alternative strategies (e.g., heuristic filtering, single-score classifiers, or different multi-property systems) when considering total annotation cost, hardware requirements, and downstream training efficiency gains?
- **Basis in paper:** [inferred] The paper provides throughput benchmarks (Section 6.1) and scaling stories (Section 6.2) but does not analyze the economic impact of using these annotations for data curation in a full training pipeline. The "Value of the release" focuses on analytical insights, not cost-effectiveness (Section 8).
- **Why unresolved:** While annotation speed is reported, the paper does not connect annotation cost to potential savings in downstream training compute (e.g., tokens needed for target quality) or compare against other curation methods' total cost of ownership.
- **What evidence would resolve it:** A controlled study comparing total resources (annotation compute + downstream training compute) required to reach a target model performance level when using propella-1 multi-property filtering versus single-score distillation or heuristic baselines.

### Open Question 5
- **Question:** Do the specific property definitions and enumerated values in the propella-1 rubric comprehensively cover the quality dimensions most critical for modern LLM pretraining (e.g., for code generation, mathematical reasoning, multilingual alignment), or are there missing dimensions?
- **Basis in paper:** [inferred] The rubric was developed iteratively over two weeks from candidate properties (Section 3.3, Rubric Development). It includes properties like "Technical Content" and "Reasoning Indicators," but the selection process and justification for omitting potential dimensions (e.g., creativity, factual consistency, toxicity granularity) are not exhaustively documented or validated with downstream training stakeholders.
- **Why unresolved:** The design choices are team-internal; there is no user study or correlation analysis showing that the chosen properties are the most predictive of downstream task performance across diverse model types.
- **What evidence would resolve it:** Feature importance analysis from training models on data selected using different subsets of propella-1 properties, coupled with practitioner surveys to assess whether the property set aligns with curation needs for specialized models (e.g., coding assistants, scientific LLMs).

## Limitations
- Training corpus composition and exact hyperparameters are unreleased, blocking full reproducibility.
- Gold-standard reliance on a single frontier LLM (Gemini-3-Pro) risks propagating its biases; no human validation is reported.
- Per-property failure modes on edge-case documents (e.g., malformed input, niche domains) are not characterized.

## Confidence
- **Multi-dimensional annotation value:** Medium. Novel design addresses single-score flaws, but downstream curation efficacy (e.g., model training) is unvalidated; break condition not tested.
- **Small model agreement superiority:** High for the evaluated setting (4B vs. baselines on sampled data). Medium for broad generalization, as low-resource language/content gaps are noted.
- **Billion-document scalability:** Medium. Operational details and throughput are demonstrated, but long-term stability and cost metrics at multi-thousand GPU scale are unreported.
