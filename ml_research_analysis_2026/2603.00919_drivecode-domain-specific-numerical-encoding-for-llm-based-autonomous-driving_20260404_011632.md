# DriveCode: Domain Specific Numerical Encoding for LLM-Based Autonomous Driving

## Quick Facts
- **arXiv ID:** 2603.00919
- **Source URL:** https://arxiv.org/abs/2603.00919
- **Reference count:** 40
- **Primary result:** DriveCode improves numerical reasoning in LLM-based autonomous driving, achieving lower trajectory prediction and control signal errors compared to baselines like DriveGPT4 and xVal, while also reducing inference latency.

## Executive Summary
DriveCode addresses a key limitation in large language models (LLMs) for autonomous driving: discrete tokenization of numbers fragments numerical values into digit subtokens (e.g., "3.14" → ["3", ".", "14"]), which hinders precise arithmetic reasoning for control signals and sensor data. The solution introduces a number projector—a two-layer MLP that maps raw scalars directly into the LLM’s hidden space as continuous embeddings—and a dedicated number head that regresses numerical outputs in a single step. This avoids token‑by‑token generation errors and aligns numeric representations bidirectionally via a shared projector. Evaluated on OmniDrive, DriveGPT4, and DriveGPT4‑V2, DriveCode consistently outperforms baselines in metrics such as speed RMSE, turning angle error, and theta accuracy, while also lowering inference latency. Ablation studies confirm that joint numeric input‑output conditioning is critical for performance.

## Method Summary
DriveCode replaces each number in the input text with a special `<number_token>` placeholder while storing the actual numeric value in an ordered list. During embedding, a number projector (a two‑layer MLP) maps each raw number into a continuous vector in the LLM’s hidden dimension and injects it at the corresponding placeholder position. The LLM processes this unified sequence (which also includes visual tokens from a SigLIP vision encoder). At generation, when the language model head predicts a `<number_token>`, a parallel number head (linear → LayerNorm → GELU → linear) regresses a scalar from the previous hidden state. That number is re‑embedded via the same projector and fed as the next input. Training combines cross‑entropy loss for text tokens with L1/L2 loss for numeric regressions (weight λ=1). This design preserves magnitude semantics, enables single‑step number generation, and ties input and output numeric representations together through a shared projector.

## Key Results
- On DriveGPT4: speed RMSE 1.08 (vs. 1.13 in DriveGPT4, 1.17 in xVal), turning angle error 7.71° (vs. 8.78° in DriveGPT4, 9.12° in xVal).
- On DriveGPT4‑V2: theta error 0.07377 vs. 0.07409 in xVal (higher accuracy).
- Inference latency reduction by generating numbers in a single decoding step instead of multiple token‑level steps.

## Why This Works (Mechanism)
### Mechanism 1: Continuous embeddings preserve magnitude relationships
- **Claim:** Continuous number embeddings maintain numerical magnitude relationships, enabling precise arithmetic reasoning absent in discrete tokenization.
- **Mechanism:** A two‑layer MLP number projector maps each raw scalar \(x_k\) to an embedding \(e_{num} = g_\phi(x_k)\) that replaces the `<number_token>` placeholder in the input sequence. This avoids fragmenting numbers into digit subtokens.
- **Core assumption:** The LLM’s pre‑trained hidden space can accommodate these novel continuous numeric embeddings without destabilizing existing text/vision alignments, and the model can learn to interpret them as quantities.
- **Evidence anchors:** Abstract states “numbers as dedicated embeddings rather than discrete text tokens”; Section III‑D describes the number projector; related works (FoNE, xVal) explore continuous number encoding, indicating this direction addresses known LLM numerical weaknesses.
- **Break condition:** If number distributions exceed the training range (e.g., extreme magnitudes) or the projector fails to learn a scaling that preserves linear relationships, magnitude errors will persist.

### Mechanism 2: Direct regression via number head
- **Claim:** A dedicated number head generates complete numeric values in one step, eliminating token‑by‑token generation errors and reducing inference latency.
- **Mechanism:** When the LM head predicts a `<number_token>`, the number head (linear → LayerNorm → GELU → linear) regresses a scalar \(x̂_m\) from the preceding hidden state \(h_{i_m-1}\). The regressed number is re‑embedded via the same number projector and fed as the next input token.
- **Core assumption:** The hidden state at positions preceding `<number_token>` contains sufficient information to regress the target number, and the ℓ₁/ℓ₂ loss can train this mapping effectively.
- **Evidence anchors:** Abstract mentions “a dedicated number head then directly regresses numerical outputs”; Section III‑D details the number head’s operation; Section F shows latency reduction from single‑step number prediction.
- **Break condition:** If the number head capacity is insufficient or the text loss dominates training (λ too small), regressed numbers become noisy or biased.

### Mechanism 3: Joint input‑output conditioning with shared projector
- **Claim:** Using a shared number projector for both input embedding and output re‑embedding aligns numeric representations bidirectionally, enabling the LLM to ground numbers in perception and action.
- **Mechanism:** The same projector \(g_φ\) embeds input numbers and re‑embeds output numbers (from the number head). This creates a closed loop: input numbers → LLM → number head → regressed number → \(g_φ\) → next input.
- **Core assumption:** Shared parameters force consistency between how numbers are interpreted (input) and produced (output), acting as a regularizer that ties the two tasks.
- **Evidence anchors:** Section III‑D describes the re‑embedding process; Section E ablation shows joint conditioning (numeric input *and* output) yields best performance; xVal uses scaled embeddings but lacks an output regression head, highlighting DriveCode’s shared loop as key.
- **Break condition:** If input and output number distributions differ significantly (e.g., sensor values vs. control commands), a single projector may become a bottleneck.

## Architecture Onboarding
**Component map (data flow):**  
Vision Tower (SigLIP) → Vision Projector (MLP) → LLM Backbone (LLaVA‑NeXT)  
Tokenized text with `<number_token>` → Number Projector (MLP) → LLM Backbone (injected at placeholder positions)  
LLM Backbone hidden states → Parallel heads: LM Head (text logits) and Number Head (regression)  
Number Head output → Number Projector → next input embedding

**Critical path:**
1. Preprocessing: Extract numbers from dialogue text via regex, replace each with `<number_token>`, store numbers in an ordered list.
2. Input embedding: For each token in the sequence, if `<image>` insert projected visual tokens; if `<number_token>` take next number from list, pass through number projector; else use standard token embedding. Concatenate all.
3. LLM forward: Process the unified sequence through the causal transformer to obtain hidden states.
4. Generation loop:
   - Compute logits from LM head and hidden state.
   - If predicted token is `<number_token>`: run number head on previous hidden state to regress a number, project it, and append as next embedding.
   - Else: append the embedding of the predicted token from the embedding table.
   - Repeat until EOS or max length.

**Design tradeoffs:**
- Shared projector (same for input and output) enforces consistency but may be a bottleneck if input/output number distributions differ.
- Number head simplicity (shallow MLP) is efficient but may lack capacity for complex relationships; deeper heads increase latency.
- Strict alignment between `<number_token>` count and number list is essential; misalignment corrupts training/inference.

**Failure signatures:**
- Extraction errors: regex fails to capture numbers (e.g., scientific notation, commas) leading to empty/misaligned number list.
- Projector norm explosion: embeddings with large norms destabilize LLM attention.
- Number head saturation: regression loss under‑weighted (λ too small) leads to constant outputs (e.g., 0).
- Modality interference: gradients from vision/text overwhelm number projector, causing numeric embeddings to collapse to text‑like vectors.

**First 3 experiments:**
1. **Unit test number extraction:** For synthetic sentences with numbers, verify that the extracted list matches the `<number_token>` count and order.
2. **Projector sanity check:** Input a linearly spaced set of numbers (0.0 to 100.0 step 10.0) through the number projector. Check that embedding norms are finite and stable, pairwise cosine similarity decreases with numeric difference, and PCA shows a dominant linear direction.
3. **Toy regression test:** Train on a trivial dataset where input `"Value: <number_token>"` should output `x*2+1`. Freeze LLM, train only number head, verify it learns the transformation accurately across a range.

## Limitations
- AnyRes vision integration details (dynamic resolution, newline token handling) for SigLIP with LLaVA‑NeXT are unspecified, critical for correct visual token sequence construction.
- Preprocessing ambiguity: no rule provided for identifying “meaningful physical quantities” to convert to `<number_token>`, risking misalignment in real‑world data.
- Missing training hyperparameters: exact learning rate, global batch size, weight decay, and number of epochs for each dataset are not reported.
- No number normalization: raw values may have large ranges (e.g., global coordinates), potentially destabilizing training without scaling.
- LLM backbone specifics (e.g., Vicuna‑7b/13b) and hidden dimension \(d\) are not stated.

## Confidence
- **Mechanism 1 (Continuous embeddings preserve magnitude):** High Confidence. Strongly supported by design choice and comparative results vs. discrete‑token baselines, though exact scaling properties are not fully detailed.
- **Mechanism 2 (Direct regression via number head):** High Confidence. Clear architectural specification and latency reduction claim are validated by inference experiments and ablation.
- **Mechanism 3 (Joint input‑output conditioning with shared projector):** Medium Confidence. Ablation confirms importance of joint conditioning, but the specific contribution of the shared projector vs. separate projectors is not isolated; risk of distribution mismatch remains untested.
