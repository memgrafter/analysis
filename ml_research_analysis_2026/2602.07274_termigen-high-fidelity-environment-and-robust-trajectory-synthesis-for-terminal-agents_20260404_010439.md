# TermiGen: High-Fidelity Environment and Robust Trajectory Synthesis for Terminal Agents

## Quick Facts
- **ArXiv ID:** 2602.07274  
- **Source URL:** https://arxiv.org/abs/2602.07274  
- **Reference count:** 24  
- **Primary result:** TermiGen-Qwen2.5-Coder-32B achieves 31.3% pass@1 on TerminalBench 1.0, establishing a new open-weight SOTA and surpassing o4-mini (20.0%).

## Executive Summary
TermiGen is a framework for training open-weight large language models (LLMs) to act as robust terminal agents. It tackles two main challenges: the scarcity of diverse, executable terminal environments and the mismatch between expert demonstration data and the failure modes of smaller models. The pipeline synthesizes thousands of verifiable Docker-based tasks via a multi-agent iterative refinement process, then collects interaction trajectories with a Generator-Critic protocol that actively injects errors to produce error→diagnosis→recovery cycles. Even trajectories that do not reach successful completion are retained for their local repair supervision. Fine-tuning Qwen2.5-Coder-32B on this data yields 31.3% pass@1 on TerminalBench 1.0, a new record for open-weight models and surpassing proprietary o4-mini (20.0%). Ablations confirm that physical execution (real Docker) outperforms simulation, and that including unresolved trajectories (τ=0%) maximizes performance, highlighting the value of diverse failure exposure for building resilience.

## Method Summary
TermiGen's pipeline has two phases. Phase I (Environment Synthesis) starts from a hierarchical taxonomy of 11 task categories. A Task Seeder generates high-level seeds, which a Proposer-Evaluator loop expands into concrete task specifications (objective, I/O, success criteria) with a feasibility threshold >4. A Structured Environment Builder then sequentially employs File Planner, Construct Agent, and Env Agent to generate the required files and a Dockerfile. Each candidate environment undergoes an iterative Docker build loop (max 5 retries) that captures build errors and feeds them back to the Env Agent until the image builds successfully. Finally, a Unit Test Generator produces tests, and a Judge Agent validates solvability via a Generator-Judge framework. Phase II (Trajectory Collection) uses a BashAgent (ReAct-style) to interact with verified environments. A Critic Agent validates each step's alignment with the task. A stochastic intent sampler (ϵ=0.2) decides whether the next step should be correct or an error. For error intents, the generator produces a plausible mistake from five predefined failure modes; the critic ensures the error generates informative feedback. When the next intent returns to correct, the generator is conditioned to diagnose the preceding error and synthesize a recovery action. All trajectories—including those that ultimately fail—are stored. The Data Curator then applies an inclusion threshold τ (the paper uses τ=0% to keep all). Finally, a base LLM (Qwen2.5-Coder-32B) is fine-tuned with full-parameter SFT on the full dataset using standard hyperparameters (AdamW, 5 epochs, lr=5e-6, seq_len=20k, BF16, DeepSpeed ZeRO-3, grad accumulation 8).

## Key Results
- TermiGen-Qwen2.5-Coder-32B achieves **31.3% pass@1** on TerminalBench 1.0, a new open-weight SOTA and surpassing o4-mini (20.0%).
- Using physically verifiable Docker environments improves over simulation: **25.0% vs. 22.5%** pass@1.
- Including unresolved trajectories (**τ=0%**) yields the best performance (31.3%), whereas stricter filtering degrades results.

## Why This Works (Mechanism)

### Mechanism 1: Physical Verification via Docker
**Claim:** Using physically verifiable Docker-based environments reduces hallucination in training data compared to simulated execution, leading to better downstream performance.  
**Mechanism:** A multi-agent iterative refinement loop generates task specifications, files, and Dockerfiles. An automated Docker build loop executes until success (max 5 iterations), filtering non-executable configurations. A Generator-Judge framework then validates task solvability via unit tests.  
**Core assumption:** Grounded execution signals (stdout/stderr) from real containers provide more accurate state transitions and failure modes than a simulator's hypothetical outputs.  
**Evidence:** The abstract and Section 3.2 describe the interactive execution loop and build feedback; neighboring papers similarly emphasize executability but TermiGen's specific validation loop is novel.  
**Break condition:** If the Docker build loop exceeds maximum iterations (N=5) without success, the environment is discarded.

### Mechanism 2: Error Injection via Generator-Critic
**Claim:** Actively injecting controlled errors during trajectory collection creates data rich in explicit error→diagnosis→recovery cycles, which teaches models resilience against their own runtime failures.  
**Mechanism:** At each step, an intent signal (correct vs. error) is sampled stochastically (ϵ=0.2). If error, the generator produces a plausible, domain-specific mistake from a taxonomy of 5 failure modes. A Critic Agent validates the step to ensure it triggers informative feedback. On subsequent correct intents, the generator is conditioned to diagnose the preceding error and synthesize a corrective action.  
**Core assumption:** Standard expert trajectories (from strong teacher models) lack the distribution of simple, common errors that smaller student models make, creating a mismatch. Explicit exposure to and recovery from these errors during training bridges this gap.  
**Evidence:** The abstract and Section 3.3 detail the error injection and recovery conditioning; neighboring works explore trajectory synthesis but not explicit error injection for recovery learning.  
**Break condition:** If the Critic Agent consistently fails to validate injected errors as "syntactically plausible and triggering informative feedback," the error injection process fails to generate usable training data for failure modes.

### Mechanism 3: Inclusion of Unresolved Trajectories
**Claim:** Including trajectories that ultimately fail to complete the task (unresolved errors) improves model performance, contrary to standard SFT practices that filter for 100% success.  
**Mechanism:** Training data is not strictly filtered by final task success (τ=0% inclusion). Even failed trajectories contain high-quality local repair segments for injected errors. This exposes the model to complex, high-difficulty scenarios and supervision on the mechanics of diagnosis/correction independent of global outcome.  
**Core assumption:** The value of a trajectory for learning resilience lies in its local error-correction sequences, not just its global success. Discarding imperfect runs removes supervision for recovery from cascading or complex failures.  
**Evidence:** The abstract and Section 4.3 present ablation results showing τ=0% achieves the highest performance; the paper attributes this to task complexity coverage and local recovery supervision.  
**Break condition:** If a trajectory contains no recoverable error-correction segments (i.e., all errors are terminal and uncorrected within the trajectory), its inclusion may add noise without recovery supervision.

## Foundational Learning

#### Docker Containerization
**Why needed:** All training and evaluation environments are isolated, reproducible Docker containers. Understanding Dockerfile syntax, image building, and container runtime is essential to grasp how environment executability is verified and how agents interact with a persistent filesystem and state.  
**Quick check:** How does the iterative Docker build loop (Section 3.2) ensure that a synthesized environment is functionally valid before trajectory collection?

#### ReAct-style Agent Frameworks
**Why needed:** The BashAgent in TermiGen generates "a reasoning trace followed by a bash command" at each turn. This action-observation loop is the fundamental interaction pattern for which trajectories are collected and upon which the model is fine-tuned.  
**Quick check:** In the Generator-Critic protocol (Section 3.3), what is the role of the "intent signal" (I_correct vs. I_error) in shaping the action at step *t*?

#### Supervised Fine-Tuning (SFT) for Agentic Tasks
**Why needed:** The final model is trained via full-parameter SFT on the synthesized trajectories. Prerequisite understanding includes how long-horizon, multi-turn interaction histories are formatted as training sequences and the pitfalls of exposure bias when training on only optimal demonstrations.  
**Quick check:** According to the paper, why is standard SFT on "expert trajectories" (from a strong teacher) insufficient for training robust terminal agents, and how does TermiGen's data address this?

## Architecture Onboarding

### Component Map
Task Seeder → Proposer-Evaluator Loop → Structured Environment Builder (File Planner → Construct Agent → Env Agent) → Validation Loop (Docker Build → Unit Test) → Trajectory Collector (Generator-Critic) → Data Curator → Fine-Tuning Engine

### Critical Path
Task Seed → Proposer-Evaluator → Environment Builder → Docker Build Success? → Unit Test Validation? → Generator-Critic Trajectory Collection → Data Curation (τ) → SFT → Evaluation on TerminalBench.

### Design Tradeoffs
- **Physical Execution vs. Simulation:** TermiGen chooses costly, slow real Docker builds/executions to eliminate hallucinations, sacrificing scale for fidelity (RQ1 ablation).
- **Error Injection Rate (ϵ):** Fixed at 0.2. Higher rates might increase failure diversity but risk generating unrecoverable trajectories or non-plausible errors; lower rates reduce exposure to failure modes.
- **Inclusion Threshold (τ):** 0% (include all) vs. 100% (only perfect). Lower τ includes diverse failure scenarios and complex tasks but adds noise from ultimately failed trajectories.

### Failure Signatures
- **Environment Synthesis Failure:** Docker build loop exceeds max iterations (N=5). Unit test generator/validator cannot achieve approval after max refinement rounds.
- **Trajectory Collection Failure:** Critic Agent repeatedly rejects candidate error steps as "not triggering informative feedback," causing a regeneration loop timeout.
- **Training Failure:** Model trained on τ=100% data shows a significant performance drop (>5% abs) on TerminalBench compared to τ=0%, indicating sensitivity to data distribution.

### First 3 Experiments
1. **Environment executability sanity check:** Run the Phase I pipeline on 10 random seeds. Measure % that succeed within N=5 Docker build iterations. Target: >90% success.
2. **Error injection quality audit:** For 50 sampled trajectories with ϵ=0.2, use a validator (e.g., Claude) to check: (a) Are injected errors plausible and domain-specific? (b) Do they trigger non-trivial stderr? (c) Is recovery behavior correctly conditioned? Target: >85% plausibility.
3. **τ ablation replication:** Replicate Table 4 with a smaller dataset (N=500 trajectories). Train three models (τ=100%, τ=50%, τ=0%). Expect performance rank: τ=0% > τ=50% > τ=100%. Confirm the "value of negative trajectories" hypothesis holds at smaller scale.

## Open Questions the Paper Calls Out

### Open Question 1: Reinforcement Learning for Terminal Agents
**Question:** Does incorporating reinforcement learning (RL) improve performance beyond supervised fine-tuning (SFT) for terminal agents trained on TermiGen data?  
**Basis:** The conclusion states that "a natural next step is to apply reinforcement learning" since the environment provides deterministic verification signals.  
**Why unresolved:** The paper only evaluates SFT; RL could potentially enable exploration beyond the fixed training distribution and better utilize the verifiable environments.  
**Evidence needed:** An RL fine-tuning experiment (e.g., using PPO or GRPO) on the TermiGen dataset, with pass rate comparison on TerminalBench and analysis of sample efficiency.

### Open Question 2: Memory for Error Recovery
**Question:** How does adding a memory component (e.g., conversation history or state tracking) affect error-correction capabilities in long-horizon terminal tasks?  
**Basis:** The limitations note they "implement a simple agent without a memory component" and suggest future work should design agents with memory.  
**Why unresolved:** Memory might help maintain diagnostic coherence across cascading failures, but its trade-offs (e.g., context length, distraction) are unknown.  
**Evidence needed:** Replicate the TermiGen pipeline with an agent that maintains a structured memory (e.g., vector store or recurrent summary), then compare error recovery rates and pass rates on complex tasks.

### Open Question 3: Real-World Transfer
**Question:** To what extent do models trained on synthetic TermiGen environments transfer to real-world, open-ended terminal scenarios (e.g., production clusters)?  
**Basis:** The limitations acknowledge that synthetic environments "cannot fully replicate the stochasticity and scale" of real systems and call for investigation of transfer.  
**Why unresolved:** TermiGen environments are isolated and deterministic; real systems involve concurrency, partial failures, and external dependencies that may break learned behaviors.  
**Evidence needed:** Evaluate TermiGen-trained models on a real-world deployment benchmark (e.g., a set of authentic DevOps tickets or a live staging cluster) and measure performance drop versus synthetic tasks.

### Open Question 4: Optimal Error Injection Rate
**Question:** What is the optimal error injection probability (ϵ) in the Generator-Critic protocol for maximizing resilience without degrading baseline performance?  
**Basis:** The paper fixes ϵ = 0.2 without systematic exploration, stating only that this value is used.  
**Why unresolved:** A higher ϵ might expose models to more failure modes but could also overwhelm learning with noise; a lower ϵ might under-expose. The trade-off is untested.  
**Evidence needed:** Ablate ϵ across a range (e.g., 0.05, 0.1, 0.2, 0.3, 0.5) while controlling for data size, then measure pass rates and error recovery metrics on TerminalBench.

### Open Question 5: Error Taxonomy Contribution
**Question:** Which specific failure modes in the five-category error taxonomy (Analysis, Command, Hallucination, Requirement, Verification) contribute most to improved error-correction capabilities?  
**Basis:** The paper taxonomizes errors and shows overall benefit from error injection, but does not analyze per-category impact despite noting baseline errors are skewed (e.g., 50% Verification Failures).  
**Why unresolved:** It is unknown whether all error types are equally valuable for training resilience, or if some (e.g., Hallucinations) are more instructive than others.  
**Evidence needed:** Generate trajectories with controlled injection of only one error type at a time (keeping other conditions constant), then fine-tune separate models and compare their error recovery performance on held-out tasks.

## Limitations
- Prompt templates for all agents are not public, hindering exact replication of multi-agent interactions.
- Critic Agent's validation heuristics (e.g., "informative feedback") are unspecified and remain opaque.
- Error injection parameters (ϵ=0.2, taxonomy) and the scalability of physical verification are not systematically analyzed.

## Confidence
- Physical verification via Docker environments: **High**  
- Error injection via Generator-Critic protocol: **Medium**  
- Inclusion of unresolved trajectories: **High**
