# LOGIGEN: Logic-Driven Generation of Verifiable Agentic Tasks

## Quick Facts
*   **arXiv ID:** 2603.00540
*   **Source URL:** https://arxiv.org/abs/2603.00540
*   **Reference Count:** 25
*   **Primary Result:** LOGIGEN-32B(RL) achieves 79.5% success on τ²-Bench, a 38.8-point absolute gain over its base model (40.7%).

## Executive Summary
LOGIGEN addresses the scarcity of high-quality, stateful training data for LLM agents by introducing a logic-driven synthesis framework. It replaces tool-centric reverse-synthesis with forward generation grounded in strictly enforced business policies. The method compiles natural-language rules into database-level constraints, seeds boundary-adjacent initial states to provoke critical decisions, and uses a Triple-Agent Orchestration (Architect, Set Designer, Explorer) to discover causally valid trajectories. This pipeline produces 20,000 verifiable tasks across 8 domains. Training on this data yields an agent that performs on par with proprietary systems on the complex τ²-Bench benchmark.

## Method Summary
LOGIGEN’s pipeline generates verifiable agent tasks in three automated phases. The **Architect** translates a domain's natural-language policy into a hard-compiled SQLite environment (schema + triggers) that enforces rules transactionally. The **Set Designer** initializes the database to a "boundary-adjacent" state (e.g., one action away from a constraint violation) to embed immediate trade-offs. The **Explorer** then runs a collaborative Client-Consultant simulation within this environment to discover a valid trajectory from the initial state to a user goal, producing a spoiler-free task description and a target state snapshot. Verified trajectories are used for Supervised Fine-Tuning (SFT), followed by Reinforcement Learning (RL) with Turn-aware Group Relative Policy Optimization (TA-GRPO) and dense, deterministic state-based rewards.

## Key Results
*   LOGIGEN-32B(RL) achieves a 79.5% pass@1 on τ²-Bench.
*   This represents a 38.8-point absolute improvement over the base Qwen3-32B model (40.7%).
*   The generated dataset comprises 20,000 verifiable tasks across 8 distinct domains.

## Why This Works (Mechanism)
### Mechanism 1: Hard-Compiled Policy Enforcement
*   **Claim:** Hard-compiled database constraints enforce deterministic policy compliance, eliminating ambiguous rule violations.
*   **Mechanism:** Natural-language business rules are translated into SQL triggers that intercept every write transaction, physically rejecting invalid operations and auto-computing side effects (e.g., quotas).
*   **Core Assumption:** Business logic can be expressed as declarative constraints bound to data models at the transactional level.
*   **Evidence:** [abstract] "compiles natural-language policy into database constraints"; [section 3.3] "enforce policy logic at the database level... the database engine enforces them at the transactional level".
*   **Break Condition:** Policies requiring subjective judgment (e.g., "reasonable effort") cannot be encoded as deterministic triggers.

### Mechanism 2: Boundary-Adjacent State Initialization
*   **Claim:** Seeding states exactly at policy boundaries maximizes logical friction from the first agent step, forcing engagement with critical conflicts.
*   **Mechanism:** The Set Designer initializes data at critical thresholds (e.g., `flight_count = 2` for a `max=3` quota) and injects user archetypes (Rookie, Edge, Mismatch) to guarantee immediate trade-offs.
*   **Core Assumption:** Complex decision density is more educative than smooth execution; early constraints yield stronger learning signals.
*   **Evidence:** [abstract] "initializes boundary-adjacent states to trigger critical policy conflicts"; [section 3.4] "initialize the database at the critical boundary N−1".
*   **Break Condition:** Boundary states are unreachable under policy or produce unsolvable tasks.

### Mechanism 3: Deterministic State-Diff Verification
*   **Claim:** Exact state equivalence between final and target snapshots provides path-independent reward supervision, preventing reward hacking.
*   **Mechanism:** Success is defined by `DIFF(s_final, s_target) = 0`. Dense incremental rewards are derived from state proximity, guaranteeing a noise-free signal.
*   **Core Assumption:** Task completion is a well-defined state transition; the final state uniquely determines success.
*   **Evidence:** [abstract] "validity is strictly guaranteed by checking exact state equivalence"; [section 4.2] "starget is obtained via execution rather than prediction, it is guaranteed to be free of ground-truth drift".
*   **Break Condition:** Tasks have multiple equally valid final states or require procedural correctness (specific sequence).

## Foundational Learning
*   **Stateful vs. Stateless Interaction**
    *   **Why Needed:** LOGIGEN trains agents where every action changes a persistent system state (e.g., booking reduces quota), unlike single-turn tasks.
    *   **Quick Check:** If an agent books a flight, how does that affect whether it can book another flight later?
*   **Hard vs. Soft Policy Enforcement**
    *   **Why Needed:** Policies are physically enforced by database triggers; the agent must comply or fail, rather than remembering rules.
    *   **Quick Check:** What happens if an agent tries to book a $1200 flight when policy says flights >$1000 require approval but the agent forgets to set approval_status?
*   **Deterministic State-Based Rewards**
    *   **Why Needed:** Exact database comparison avoids noisy LLM-as-judge signals, enabling reliable RL optimization.
    *   **Quick Check:** If two agent trajectories produce the same final database state but use different intermediate steps, should they receive the same reward? Why?

## Architecture Onboarding
**Component Map:**  
Architect (Policy → SQL) -> Set Designer (Constraint & Boundary Logic → `s_origin`) -> Explorer (Simulated Dialogue → `I`, `s_target`) -> [Verifier (Embedded in each phase)]

**Critical Path:**
1.  **Architect:** Generates Wiki Policy (P) and Hard-Compiled Environment (E) via Analyze→Policy Codification→Tables→Triggers. Iterates through a Check–Fix–Verify loop.
2.  **Set Designer:** Constructs `s_origin` using boundary-adjacent seeding (numerical thresholds at N−1) and injects contextual diversity (trade-offs, distractors, user archetypes).
3.  **Explorer:** Runs a dual-role Client–Consultant simulation. Consultant proposes feasible actions from current state; Client selects goals. Successful path yields task description `I` (spoiler-free) and `s_target`.
4.  **Training:** Verified Explorer trajectories feed Cold-Start SFT. RL uses TA-GRPO with fine-grained state-diff rewards (`r_t = P_t - P_{t-1}`).

**Design Tradeoffs:**
*   **Atomic tools vs. high-level APIs:** Exposes per-table CRUD tools to preserve planning freedom but increases reasoning burden.
*   **Boundary seeding vs. random initialization:** Boundary states increase early friction and difficulty; may yield unsolvable instances if constraints are too tight.
*   **Hard-compiled vs. programmatic enforcement:** Triggers guarantee invariants but limit flexibility for special-case overrides.
*   **Spoiler-free projection:** Task description `I` hides procedural details (tool names, IDs); risks under-specification.

**Failure Signatures:**
*   **Architect fails:** Verifier reports SQL compilation errors or semantic drift between policy and triggers.
*   **Set Designer fails:** Initial state has no feasible path to any target (all actions immediately violate constraints).
*   **Explorer fails:** Low success rate (<95%) in discovering executable trajectories; Consultant proposes no feasible options early.
*   **Training fails:** RL reward doesn't improve; Pass@k high but Passˆk low (capability-consistency gap); simulator hacking (performance drops with diverse user simulator).

**First 3 Experiments:**
1.  **Architect validation:** Feed a simple seed policy (e.g., "Bookings must have departure > booking + 3 steps"). Verify the generated `validate_flight_booking_insert` trigger compiles and correctly aborts invalid inserts. Check that the tool schema documents the precondition.
2.  **Set Designer check:** For a domain with a max-quota constraint (e.g., max 3 flights), confirm `s_origin` has exactly 2 active flight bookings. Verify that adding one more booking succeeds but a third violates the quota trigger.
3.  **Explorer smoke test:** With a minimal task (e.g., "book an economy flight under $1000"), run the Client–Consultant loop and assert (a) final state matches the documented booking, (b) task description `I` never mentions table names or IDs, (c) trajectory length is ≥2 turns (includes clarification).

## Open Questions the Paper Calls Out
1.  **Non-Relational Extension:** Can LOGIGEN's hard-compiled policy grounding be extended to non-relational environments (e.g., hybrid simulators, multi-service backends) while preserving deterministic verification?
2.  **Exploration Efficiency:** How can exploration efficiency be improved to guarantee coverage of logically critical boundary states as policy complexity scales?
3.  **Simulator Robustness:** What robust methods can prevent agent overfitting to user simulator artifacts during RL, ensuring generalization across diverse user behaviors and evaluators?
4.  **Scalability to Complex Policies:** Can the hard-compiled approach scale to extremely complex real-world policies (e.g., thousands of interdependent rules) without intractable overhead or loss of verifiability?

## Limitations
*   **Reproducibility gaps:** Exact agent prompts, reward shaping coefficient (λ_err), and Verifier checklist are undisclosed.
*   **Generalizability:** Claims are restricted to 8 domains; unknown if logic-driven synthesis scales to highly subjective policies or procedural correctness requirements.
*   **Simulator dependence:** Explorer relies on an internal Client–Consultant loop; performance may overfit to this synthetic pattern versus real user variability.

## Confidence
*   **Hard-compiled constraint enforcement:** High. Well-specified via SQL triggers with transactional guarantees.
*   **Boundary-adjacent seeding:** Medium. Principle detailed, but "break condition" (unsolvable edges) lacks empirical validation across all 20k tasks.
*   **Deterministic state-diff rewards:** High. Metric is mathematically precise and reproducible.
*   **79.5% τ²-Bench success:** Medium. Depends on undisclosed RL hyperparameters and benchmark version.

## Next Checks
1.  **Boundary-solvability audit:** For all 20k tasks, compute `DIFF(s_origin → s_target)` and measure the percentage where the initial boundary-adjacent state has ≥1 feasible action sequence to target. Flag domains with >5% unsolvable seeds.
2.  **Zero-shot domain transfer:** Evaluate LOGIGEN-32B(RL) on 2 held-out domains (e.g., Healthcare Scheduling, Academic Committee) without any in-domain SFT/RL. Report absolute pass@1 drop versus in-domain performance.
3.  **Trigger coverage verification:** For a stratified sample of 100 policy rules per domain, use differential testing: (a) manually craft a violating transaction, (b) confirm trigger aborts with correct error code, (c) verify non-violating transaction succeeds. Compute rule coverage rate.
