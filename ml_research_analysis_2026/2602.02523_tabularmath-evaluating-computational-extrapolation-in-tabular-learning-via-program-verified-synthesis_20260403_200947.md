# TabularMath: Evaluating Computational Extrapolation in Tabular Learning via Program-Verified Synthesis

## Quick Facts
- **ArXiv ID:** 2602.02523
- **Source URL:** https://arxiv.org/abs/2602.02523
- **Reference count:** 40
- **Primary result:** Tabular models (TabPFN v2.5) achieve near-perfect in-distribution R² but fail at exact integer match under output extrapolation, while ICL (GPT-OSS-120B) sustains ~40% OOD consistency, exposing a gap between function approximation and exact computation.

## Executive Summary
TabularMath is a benchmark designed to evaluate whether tabular models can perform computational extrapolation—recovering deterministic computational rules from examples and generalizing to out-of-distribution outputs—rather than merely interpolating statistically. Using a program-verified synthesis pipeline, the authors create 114 deterministic math problems (233,472 rows) with guaranteed correct labels and output-based OOD splits. Key findings: TabPFN v2.5 yields near-perfect in-distribution R² (0.998) and retains positive R² under OOD, yet its exact integer match plummets below 10% under OOD. In contrast, in-context learning with a 120B-parameter model (GPT-OSS-120B) maintains ~40% OOD consistency despite lower R², demonstrating robust exact computation from few examples. This exposes a fundamental limitation: tabular models learn smooth function approximations but fail to recover precise outputs under extrapolation, while ICL shows promise in rule induction. The paradigms are complementary, with ICL excelling at low-shot rule induction and TabPFN at scaling with data.

## Method Summary
TabularMath converts natural-language math problems (from GSM8K and AIME) into deterministic computational templates using an LLM-assisted compiler. For each problem, a generator produces input feature vectors and a verifier computes exact integer outputs, guaranteeing label correctness. Each problem yields 2,048 tabular rows with engineered features (raw values, logs, signs, modular arithmetic, text statistics). Two splits are defined: a random 80/20 i.i.d. split and an output-based OOD split (train on the 80% smallest target values, test on the 20% largest). Models are trained or prompted on context sets of sizes {32, 64, 128, 256, 512, 1024, 2048} and evaluated using R² and rounded consistency (exact match after rounding). The evaluation covers tree ensembles (XGBoost, CatBoost, LightGBM, Random Forest), TabPFN v2/v2.5, deep tabular architectures (RealMLP-TD-S, TabM, xRFM), and ICL with GPT-OSS-120B.

## Key Results
- TabPFN v2.5 achieves near-perfect in-distribution R² (0.998) but its OOD exact-match accuracy drops below 10%, despite maintaining positive R² (~0.75).
- In-context learning (GPT-OSS-120B) sustains ~40% OOD consistency, demonstrating robust exact computation even with few examples.
- TabPFN’s exact-match scales with data (62% in-distribution at 2,048 rows) while ICL is sample-efficient (55% at 32 rows) but does not scale within the few-shot regime; under OOD ICL consistently outperforms.

## Why This Works (Mechanism)
### Mechanism 1: Tabular models learn smooth function approximations
- **Claim:** Tabular models (e.g., TabPFN v2.5) learn smooth function approximations that capture general trends but fail to recover precise integer outputs under output extrapolation, creating an R²–consistency gap.
- **Mechanism:** Models trained via statistical interpolation optimize for mean-squared error, which rewards predictions close to the true value on average but does not enforce exact computation. Under OOD splits where test outputs exceed training maxima, the learned smooth function extrapolates to a continuous estimate rather than snapping to the discrete, deterministic target.
- **Core assumption:** Deterministic computational tasks require exact rule recovery, not function approximation.
- **Evidence anchors:** [abstract] "TabPFN v2.5 achieves near-perfect in-distribution R² (0.998) and maintains positive R² under OOD, but its rounded consistency (exact integer match) plummets below 10% under OOD."; [section 5.2] "TabPFN v2.5 achieves strong R² (0.75) under OOD evaluation but only 7.8% exact-match accuracy."; [section 6.2] "Tree-based models make piece-wise constant predictions... High R² (good capture of general trends), Low rounded consistency (failing to hit exact integer values)."
- **Break condition:** When the task requires exact integer outputs and test targets lie outside the training support (output extrapolation), rounded consistency will collapse even if R² remains reasonable.

### Mechanism 2: ICL performs program induction
- **Claim:** In-context learning (ICL) with large pretrained transformers performs program induction—identifying the underlying computational template from a few (x, y) pairs—and can systematically extrapolate exact outputs.
- **Mechanism:** ICL leverages priors from massive pretraining to map a small set of examples to a latent algorithm (e.g., “compute 20% more then add tax”). The model then executes this induced program on new inputs, enabling accurate OOD predictions without additional training.
- **Core assumption:** LLMs encode reusable computational patterns that can be activated by few-shot demonstrations.
- **Evidence anchors:** [abstract] "ICL (GPT-OSS-120B) sustains ~40% OOD consistency despite lower R², showing robust exact computation from few examples."; [section 6.4] "ICL rapidly saturates and its performance is primarily based upon whether it recognizes the underlying computation from a small number of demonstrations."; [section 6.4] "ICL exhibits ~39% consistency despite many problems being completely unresolved. The robustness... is due to a subset of problems on which ICL is able to attain nearly perfect accuracy under OOD output extrapolation."
- **Break condition:** Problems requiring complex, multi-step chaining or unfamiliar computational templates exceed the model’s in-context induction capacity; performance then drops (as seen on AIME).

### Mechanism 3: Complementarity of paradigms
- **Claim:** The two paradigms (TabPFN and ICL) are complementary: TabPFN scales efficiently with more data to improve interpolation accuracy, while ICL achieves high exact-match accuracy from very few examples but does not scale within the few-shot regime.
- **Mechanism:** TabPFN’s prior-fitted architecture is optimized for smooth function generalization from synthetic training distributions; given sufficient in-distribution samples, it approximates the deterministic function well. ICL’s strength comes from pretrained algorithmic knowledge, not from the provided examples, so adding more context examples yields diminishing returns.
- **Core assumption:** Inductive biases differ: TabPFN favors continuous functional smoothing; ICL favors discrete rule induction.
- **Evidence anchors:** [abstract] "The paradigms are complementary, with ICL excelling at rule induction and TabPFN at functional scaling."; [section 5.1] "TabPFN v2.5 scales from 16.0% at 32 rows to 62.0% at 2,048 rows... ICL achieves 50–57% across row caps 32–128, showing strong sample efficiency but limited scaling."; [section 6.1] "TabPFN v2.5 gains ~7.7 points per data doubling; ICL shows near-flat scaling."
- **Break condition:** In high-data regimes (≥1024 rows), TabPFN surpasses ICL on in-distribution exact-match; in low-data regimes (≤32 rows), ICL outperforms. Under OOD, ICL’s advantage persists regardless of data size.

## Foundational Learning
### Deterministic computation vs. statistical interpolation
**Why needed:** TabularMath treats each math problem as a deterministic function V: X → Y with zero irreducible error. This contrasts with standard tabular benchmarks where Y is stochastic. The distinction is critical because it changes the learning objective from estimating P(Y|X) to inferring and executing a program.
**Quick check:** If you double the training set size on a noisy real-world prediction task, what happens to expected error? What happens on a deterministic computational task like those in TabularMath?

### Output-based OOD split
**Why needed:** The OOD split sorts rows by target y and trains on the smallest 80%, testing on the largest 20%. This isolates *output extrapolation*—the model must predict values beyond any training target seen. It is a stricter test of computational generalization than input extrapolation alone.
**Quick check:** Why would a model that achieves R² = 0.98 on an i.i.d. test set fail completely on an output-based OOD test set?

### Latent program hypothesis
**Why needed:** This hypothesis frames each math problem as having an underlying Turing-complete program that generates y from x. The learning task is then *program induction from examples*. This theoretical lens explains why ICL (which can implement programs in-context) succeeds under OOD while traditional tabular models (which approximate functions) fail.
**Quick check:** Under the latent program hypothesis, what would it mean for a model to achieve 100% exact-match accuracy on an OOD test set?

## Architecture Onboarding
**Component map:** Seed Lifting -> Verification -> Tabular Projection -> Evaluation

**Critical path:** The verification step (Phase 2) is non-negotiable; without it, labels may be incorrect, invalidating the diagnostic. The OOD split construction must be based on sorted y values to ensure test outputs are outside training support.

**Design tradeoffs:**
- Synthetic vs. real data: TabularMath uses program-generated data with zero noise, isolating computational reasoning. Real-world tabular tasks often contain noise, where interpolation-friendly models (tree ensembles) excel. Do not apply OOD conclusions to noisy domains.
- Deterministic targets: The benchmark uses exact integers. Models trained with MSE loss are mismatched to this objective; post-processing (e.g., rounding to nearest plausible integer) may help.
- Feature engineering: The provided feature set (logs, mod k, signs) is designed to be informative but generic. Do not tune features per problem; that would leak computational structure.

**Failure signatures:**
- High in-distribution R² (~1.0) but low exact-match accuracy (<70%) indicates the model is learning a smooth approximation, not the discrete function.
- OOD R² positive but OOD exact-match ≈0% confirms extrapolation failure for deterministic rules.
- ICL showing high OOD consistency on some problems and 0% on others indicates template-matching success/failure, not gradual scaling.

**First 3 experiments:**
1. **Verification sanity check:** For one GSM8K problem, run the generator to produce 10 rows, pass each through the verifier, and assert all returned y are integers and match the problem’s logic when recomputed manually.
2. **Baseline i.i.d. vs OOD:** Train TabPFN v2.5 on 512 random rows (80/20 split) and compute R² and consistency. Repeat with OOD split. Observe the R²–consistency divergence under OOD.
3. **ICL sample efficiency:** For a single problem, evaluate ICL at row caps {32, 64, 128} on both splits. Expect flat scaling on random split and stable ~40% on OOD split. Contrast with TabPFN’s increasing random-split performance but collapsing OOD performance.

## Open Questions the Paper Calls Out
1. **Can training objectives or post-processing be designed to encourage exact integer outputs under output extrapolation?**  
   **Basis in paper:** [explicit] "Future work might explore objectives or post-processing that favor discrete outputs when appropriate."  
   **Why unresolved:** Current tabular models optimize regression losses (e.g., MSE) that prioritize smooth approximations, leading to a gap between high R² and low exact-match accuracy on OOD data.  
   **What evidence would resolve it:** Introduce rounding-aware losses, discrete output constraints, or curriculum learning; evaluate whether exact-match consistency improves on TabularMath without sacrificing R².

2. **What causes the non-monotonic performance of ICL with increasing context size on AIME, and how can it be stabilized?**  
   **Basis in paper:** [explicit] "additional context examples can create spurious correlations that compete with the underlying computation, leading to non-monotonic behavior."  
   **Why unresolved:** The mechanism behind context-induced spurious correlations in complex reasoning remains unclear, limiting reliable ICL deployment.  
   **What evidence would resolve it:** Controlled ablations varying context diversity and correctness; mechanistic analysis of attention patterns to identify and suppress spurious feature learning.

3. **Can neuro-symbolic methods that induce executable programs from tabular examples achieve high exact-match accuracy under OOD extrapolation?**  
   **Basis in paper:** [explicit] "A direct path toward closing the extrapolation gap is to merge neural pattern recognition with explicit program induction."  
   **Why unresolved:** No concrete implementation of such a hybrid system has been evaluated on TabularMath; it is unknown whether program synthesis can robustly extrapolate.  
   **What evidence would resolve it:** Build a system that generates candidate programs (e.g., via DSL search) from the context set, verifies on a held-out validation split, and executes on queries; demonstrate substantially improved OOD consistency compared to pure neural models.

## Limitations
- The benchmark uses noise-free, deterministic math problems; findings may not generalize to stochastic real-world tabular tasks.
- Access to GPT-OSS-120B and TabPFN v2.5 is limited; reproduction relies heavily on cached predictions.
- ICL’s OOD success is binary per problem (either near-perfect or zero), suggesting limited induction beyond pretraining templates rather than continuous scaling.

## Confidence
- **Tabular models fail exact extrapolation:** High
- **ICL performs program induction:** Medium
- **Complementarity:** High
