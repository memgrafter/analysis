# LLMStructBench: Benchmarkmarking Large Language Model Structured Data Extraction

## Quick Facts
- arXiv ID: 2602.14743
- Source URL: https://arxiv.org/abs/2602.14743
- Reference count: 20
- Primary result: Benchmark shows prompting strategy is more critical than model size for structural validity in JSON extraction; P offers best accuracy/validity balance, PJ+ guarantees parseability but with semantic errors.

## Executive Summary
LLMStructBench introduces a comprehensive benchmark for evaluating large language models on the task of extracting structured data from natural language text into JSON format. The benchmark comprises 995 manually verified samples across five diverse use cases (e.g., support tickets, sick leave requests), and evaluates 22 models using five prompting strategies. Two primary metrics are used: F1micro, a token-level accuracy measure with partial credit for near matches, and DOCmicro, a document-level validity measure that penalizes any parsing failure. Results demonstrate that the choice of prompting strategy is more important than model size for achieving structurally valid outputs. The P strategy (schema in prompt) provides the best balance of accuracy and validity for well-aligned models, while PJ+ (schema in prompt and API) guarantees parseable outputs at the cost of increased semantic errors. Notably, smaller models like Gemma3-12B can outperform larger ones, and GPT-4o matches the best open-source systems.

## Method Summary
The evaluation uses the LLMStructBench dataset, which provides 995 test cases. Each case includes a natural-language input message, a JSON schema, and an example input-output pair. For each of 22 models (from families Qwen3, Phi, Gemma3, Deepseek-R1, Llama3, plus GPT-4o) and five prompting strategies (J, P, PJ, J+, PJ+), the model generates a JSON response based on the input. The output is parsed and compared to the ground truth via a recursive algorithm that assigns partial credit for approximate value matches (using Levenshtein distance and type compatibility). This yields F1micro (with key/value weighting α=0.25) and DOCmicro. Errors are classified into Missing Key (MK), Missing Value (MV), and Wrong Value (WV). The combined score equally weights both metrics (λ=0.5). The pipeline proceeds from data generation and manual verification through inference, parsing, error classification, metric aggregation, and analysis.

## Key Results
- Prompting strategy choice outweighs model parameter count in determining structural validity (parseable JSON).
- P strategy offers the best trade-off between accuracy and validity; PJ+ eliminates parsing failures for weaker models but shifts errors toward Wrong Value (semantic inaccuracies).
- No strict correlation between model size and performance; Gemma3-12B exceeds many larger models, and GPT-4o is competitive with top open-source systems.

## Why This Works (Mechanism)
### Mechanism 1: Prompting strategy outweighs model size for structural validity
Claim: Choosing the right prompting strategy is more important than model size for achieving parseable JSON outputs.  
Mechanism: Explicit schema provision (via system prompt and/or API `format` parameter) constrains the model's decoding toward JSON syntax. The P and PJ+ strategies provide different enforcement layers to guide output structure.  
Core assumption: Models possess latent knowledge of JSON but require sufficient structural cues at inference to activate it consistently.  
Evidence: P ranked best for most models; PJ+ eliminated parsing failures for weaker families (e.g., Phi).  
Break condition: When instruction-following capability is too limited to interpret schema guidance, or schema complexity exceeds the model’s capacity.

### Mechanism 2: PJ+ shifts errors from Missing Key/Value to Wrong Value
Claim: Enforcing structural validity via PJ+ trades "absent data" errors for "incorrect data" errors.  
Mechanism: The API-level JSON-schema constraint forces compliance with required keys and types, so failures manifest as incorrect value fills rather than omissions.  
Core assumption: The bottleneck under PJ+ is semantic extraction fidelity, not structural reasoning.  
Evidence: Under PJ+, MK errors drop to near 0% for Deepseek-R1, while WV errors rise to ~100% of error cases; Venn diagrams show near-complete overlap into WV-only region.  
Break condition: When downstream applications cannot tolerate any value error (e.g., financial figures), PJ+ becomes detrimental.

### Mechanism 3: Model scale is not the sole determinant; architectural tuning matters
Claim: Parameter count alone does not guarantee superior performance; efficient architectures and targeted instruction tuning enable smaller models to match or exceed larger ones.  
Mechanism: Architectures like Gemma3 and SFT for structured tasks improve schema adherence and value extraction consistency. F1micro correlates with size, but DOCmicro is prompt-strategy sensitive.  
Core assumption: Pre-training data diversity and task-specific tuning matter more than raw capacity for JSON generation.  
Evidence: Gemma3-12B scores 0.72, exceeding Deepseek-R1-32B (0.63) and LLaMA3.1-70B (0.73); Qwen3-1.7B outperforms several 14B+ models.  
Break condition: For extremely deep or rare schema features, larger models may recover due to broader coverage.

## Foundational Learning
### Micro-averaged F1 (F1_micro) with partial credit
Why needed: It is the primary token-level accuracy metric, measuring correctness of each extracted key-value pair. Its design (α=0.25 weighting keys vs. values) reflects real-world priority: correct values matter more than extra/missing keys. The graded scoring (Levenshtein for strings, type coercion credit) explains why models score non-zero even with imperfect outputs.  
Quick check: If a model outputs `"amount": "42"` vs. GT `"amount": 42`, does F1_micro give full, partial, or zero credit for this field, and why?  
*Answer: Partial credit. The string vs. integer mismatch is type-coercible and within the allowed threshold (β=0.2), so partial credit is awarded.*

### Document Overall Correctness (DOC_micro)
Why needed: It captures brittleness hidden by F1_micro: a single parsing failure (invalid JSON) ruins the whole document. This metric separates "mostly correct" from "fully valid" outputs, crucial for ETL pipelines requiring 100% valid JSON.  
Quick check: Can a model achieve a high F1_micro but a low DOC_micro? Provide a plausible test-case scenario causing this.  
*Answer: Yes. If a model produces nearly perfect JSON in most cases but occasionally emits unparsable text (e.g., markdown wrapper, incomplete braces), F1_micro on parsed cases may be high while DOC_micro (fraction of fully valid documents) is low.*

### Prompting strategy taxonomy (P, PJ+, etc.)
Why needed: The paper’s core comparison hinges on these configurations. P = prompt includes schema/example; PJ+ = also sets API `format` to JSON-schema. Knowing which combination enforces syntax vs. semantics is key to selecting a strategy for a given model.  
Quick check: Which strategy (P or PJ+) is theoretically more likely to produce a JSON object with all required keys but incorrect string values? Explain the mechanism.  
*Answer: PJ+. The API-level JSON-schema constraint forces the model to include all required keys and correct types. If semantic extraction fails, the model must still populate the fields, leading to wrong values. P lacks this hard constraint, so omissions (Missing Key/Value) are more common.*

## Architecture Onboarding
**Component map:**  
Datasets -> Models -> Prompting strategies -> Evaluation engine -> Analysis modules

**Critical path:**  
Data generation (GPT-4o → emails) → Manual verification → Inference (model × strategy × test) → Parse output → Error classification → Metric aggregation → Strategy-ranking → Size/family analysis → Failure analysis (Venn) → Summary tables.

**Design tradeoffs:**  
- Metric weights (α=0.25, λ=0.5): Chosen to prioritize value correctness and balance token vs. document validity; applications needing more key presence or zero parse failures may reweight.  
- Prompt selection: P optimizes accuracy/validity balance for well-aligned models; PJ+ maximizes parseability for unreliable models at semantic cost.  
- Model selection: Larger models generally improve F1micro but not DOCmicro; family-specific prompt compatibility can outweigh size (e.g., Gemma3-12B > Deepseek-32B).

**Failure signatures:**  
- High MK + low WV under P: Model ignores schema guidance; outputs free text or partial JSON.  
- Near-zero MK but high WV under PJ+: Structural constraint working, but semantic extraction failing (hallucination or misreading).  
- Size-performance non-monotonicity: e.g., Deepseek-R1-32B underperforms 14B/70B; indicates prompt incompatibility or architectural quirks.  
- High F1micro but low DOCmicro: Model often returns almost-correct JSON but occasionally emits unparsable output.

**First 3 experiments:**  
1. Strategy baseline test: Run all 5 prompting strategies on 1 small model (e.g., Gemma3-1B) and 1 large model (e.g., Llama3.1-70B) across 100 random test cases. Plot parse success (DOCmicro proxy) and perfect-match count. Expect PJ+ eliminates failures for small model; P may work for large model.  
2. Error type profiling: For a single model/strategy (e.g., Deepseek-R1-14B + P), compute per-test error types (MK, MV, WV). Generate Venn diagram as in Fig 10. Expect MK dominant in smallest models, WV dominant in larger ones.  
3. Size trend validation: For one family with >2 sizes (e.g., Qwen3: 0.6B, 1.7B, 4B, 8B, 14B, 32B), run P and PJ+ separately. Plot F1micro and DOCmicro vs. log(size). Expect F1micro roughly log-linear; DOCmicro variance increase with size under P, decrease under PJ+.

## Limitations
- Dataset and prompt details are not fully specified (download URL, exact prompt wording, model inference settings), risking reproduction variance.
- Benchmark is limited to five email-like use cases; findings may not generalize to highly complex schemas or non-text modalities.
- Metrics use fixed weights (α, λ) that might not align with all application requirements.

## Confidence
- Prompting strategy outweighs model size for structural validity: **High**
- PJ+ shifts errors from Missing Key/Value to Wrong Value: **High**
- No strict scale-performance correlation; smaller models can excel: **Medium**
