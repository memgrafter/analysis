# X-SYS: A Reference Architecture for Interactive Explanation Systems

## Quick Facts
- **arXiv ID**: 2602.12748  
- **Source URL**: https://arxiv.org/abs/2602.12748  
- **Reference count**: 40  
- **Primary result**: X-SYS provides a decoupled five-component reference architecture (XUI, Explanation, Model, Data Services, Orchestration/Governance) with explicit contracts and offline/online separation to achieve scalability, traceability, responsiveness, and adaptability, demonstrated via SemanticLens.

## Executive Summary
Interactive explanation (XAI) systems face deployment challenges in scalability, traceability, responsiveness, and adaptability as models, stakeholder needs, and governance constraints evolve. X-SYS addresses these by defining a reference architecture that strictly decouples user interfaces from backend computation through five core components and explicit interface contracts, guided by the STAR quality attributes. The architecture is instantiated in SemanticLens, a system for semantic search and activation steering of vision-language models, validating contract-based service boundaries, offline/online separation for sub-second responsiveness, and persistent state management for traceability. This demonstrates a viable approach for end-to-end interactive explanation system design.

## Method Summary
X-SYS organizes an interactive XAI system into five components:
- **XUI Services**: handles user interactions and presentation logic.
- **Explanation Services**: computes explanation outputs (e.g., semantic search, activation steering).
- **Model Services**: provides model inference and access to model internals.
- **Data Services**: stores datasets, precomputed assets (embeddings, attributions), and session state.
- **Orchestration/Governance**: routes requests, enforces policies, manages versioning and lifecycle.

Components communicate via Data Transfer Objects (DTOs) that define stable contracts. The architecture enforces an offline/online separation: expensive computations (embedding generation, attribution, visualization rendering) are performed asynchronously before user interaction; online queries rely on cached assets to guarantee responsiveness. Persistent state management across sessions supports traceability and auditability. The design is evaluated through SemanticLens, which precomputes component embeddings from MobileCLIP, computes Concept Relevance Propagation attributions, and serves interactive search and steering within the X-SYS framework.

## Key Results
- Contract-based decoupling allows components to evolve independently without system-wide downtime.
- Offline/online separation yields sub-second response times for interactive queries.
- Persistent state with versioned artifacts ensures full traceability of explanations for audits.

## Why This Works (Mechanism)
X-SYS’s effectiveness stems from its rigorous separation of concerns and explicit contracts. By isolating the XUI from backend computation, user interactions are unaffected by changes in explanation algorithms or model versions. The offline phase amortizes heavy preprocessing, storing results in Data Services; online queries then perform only lightweight operations (similarity search, arithmetic modifications) on cached data, meeting responsiveness requirements. Governance enforces data-model version alignment and logs all accesses, enabling reproducibility. Activation steering demonstrates how the architecture supports dynamic interventions without recomputing embeddings, by applying a multiplicative factor `a' = a * (1 + m)` to component activations. The combination of these patterns yields a system that scales horizontally (components can be replicated), adapts to new XAI methods (plug in new services conforming to DTOs), and maintains traceability through immutable version tags and audit trails.

## Foundational Learning
- **Decoupled architecture**  
  *Why needed*: Enables independent development, scaling, and evolution of components.  
  *Quick check*: Replace one service with a mock; system continues to operate via contract compliance.
- **Data Transfer Objects (DTOs)**  
  *Why needed*: Provide stable, versioned interfaces that prevent cascading changes.  
  *Quick check*: Serialize/deserialize a DTO (e.g., `SearchRequest`) with multiple language bindings.
- **Offline/online separation**  
  *Why needed*: Moves expensive work out of the critical path for interactive use.  
  *Quick check*: Measure online query latency; it should be orders of magnitude lower than offline preprocessing time.
- **Persistent state with versioning**  
  *Why needed*: Guarantees traceability and reproducibility of explanations.  
  *Quick check*: Given an audit log entry, fetch the exact model and data versions and reconstruct the explanation.
- **STAR quality attributes**  
  *Why needed*: Guide design tradeoffs (Scalability, Traceability, Adaptability, Responsiveness).  
  *Quick check*: Define metrics for each attribute (e.g., 95th-percentile latency, audit completeness) and benchmark the system.
- **Activation steering**  
  *Why needed*: Allows interactive modification of model behavior without altering weights.  
  *Quick check*: Apply a steering factor to a component and verify changed prediction while response time remains <1s.

## Architecture Onboarding
- **Component map**:  
  User → XUI Services → Orchestration/Governance → {Explanation Services, Model Services, Data Services} → Orchestration/Governance → XUI Services → User  
  (Data Services also store precomputed assets consumed by Explanation Services.)

- **Critical path**:  
  1. User issues query (e.g., semantic search).  
  2. XUI builds `SearchRequest` DTO and sends to Orchestration.  
  3. Orchestration forwards to Explanation Service.  
  4. Explanation Service retrieves cached component embeddings from Data Services, embeds the query, computes cosine similarities, and returns a `SearchResponse` DTO.  
  5. Orchestration returns response to XUI, which visualizes results.  
  For activation steering: similar flow with `SteeringRequest` and `SteeringResponse`.

- **Design tradeoffs**:  
  - *Offline computation cost*: Requires upfront resources but pays off in low online latency.  
  - *Contract rigidity*: Strict DTOs prevent ad-hoc extensions; evolving contracts requires versioning strategy.  
  - *Centralized governance*: Simplifies policy enforcement but can become a bottleneck; may need distributed enforcement for large scale.

- **Failure signatures**:  
  - High online latency (>1s) → possible cache miss or missing precomputed asset.  
  - Inconsistent results across sessions → version mismatch between model and data artifacts.  
  - Unable to reconstruct an explanation during audit → missing linkage between log event and artifact versions.  
  - Inability to integrate new XAI method → contract not expressive enough; requires DTO modification.

- **Exactly 3 first experiments**:  
  1. **Hello-world pipeline**: Implement all five components as separate FastAPI services; define minimal DTOs for search and steering; verify orchestration routing with mock responses.  
  2. **Offline asset generation**: For a small vision-language model (e.g., CLIP-ViT-B/32), precompute component embeddings on 100 images and store them in Data Services; measure generation time and storage size.  
  3. **Interactive query test**: Load precomputed assets; issue a semantic search query and measure end-to-end latency; then perform activation steering on a sample and verify prediction change; assert latency <1s and that session state can restore previous results.

## Open Questions the Paper Calls Out
1. **Generalizability across domains**  
   *Basis*: The architecture is demonstrated through a single implementation.  
   *Why unresolved*: It may not hold for tabular, time-series, or streaming data, or for different stakeholder workflows.  
   *Resolving evidence*: Multiple instantiations in distinct domains (healthcare, finance, IoT) with documented deviations and STAR trade-off analyses.

2. **Systematic derivation from existing XAI systems**  
   *Basis*: X-SYS was derived from prior work and design reasoning rather than a systematic literature review.  
   *Why unresolved*: Risks missing common patterns or overfitting to SemanticLens constraints.  
   *Resolving evidence*: Systematic meta-analysis of a large corpus of operational XAI systems to extract recurring service boundaries, interaction patterns, and STAR implementations.

3. **Operational definitions and benchmarks for STAR attributes**  
   *Basis*: Systematic measurements for the four quality attributes under realistic load have not been proposed.  
   *Why unresolved*: Without standardized metrics and workloads, claims remain qualitative and incomparable.  
   *Resolving evidence*: A benchmark suite with defined metrics (e.g., 95th-percentile response time, audit trail completeness) and synthetic/realistic workload generators for XAI systems, validated across reference architectures.

4. **Minimal stable interface contracts**  
   *Basis*: Standardizing contracts to enable composable capabilities without locking implementations remains open.  
   *Why unresolved*: The necessary generality for diverse XAI methods (counterfactuals, saliency) and XUI patterns (dialogue, dashboard) is unknown; too rigid stifles innovation, too loose breaks decoupling.  
   *Resolving evidence*: A catalog of interaction primitives mapped to minimal contract specifications, with empirical studies on contract evolution cost and success rates of plug-and-play swaps.

5. **Governance component design for regulations**  
   *Basis*: Tighter integration with governance (access control, audit logging, lifecycle alignment) is needed for deployable guidance.  
   *Why unresolved*: Implementation details (policy language, logging granularity, synchronization) are abstract; real-world deployment requires specific, low-overhead patterns.  
   *Resolving evidence*: Prototyped governance modules for common regulatory scenarios (e.g., reconstructing any explanation’s provenance) with performance benchmarks showing overhead trade-offs and design patterns (e.g., sidecar proxies).

## Limitations
- **Incomplete DTO specifications**: The paper does not define full interface schemas for all interaction types, hindering integration of new XAI methods.
- **Underspecified caching and state management**: Details on cache invalidation, session persistence, and asset versioning are lacking, risking consistency and traceability.
- **Limited empirical validation**: Evaluation relies solely on SemanticLens in one domain; scalability thresholds and cross-domain applicability are not established.

## Confidence
- **High**: Decoupled service architecture and offline/online separation are concretely instantiated and demonstrated in SemanticLens.
- **Medium**: STAR attributes (Scalability, Traceability, Responsiveness, Adaptability) are partially validated through the single implementation; lack of systematic benchmarks.
- **Low**: Claims about broad adaptability to evolving models, governance constraints, and cross-domain generality are not stress-tested.
