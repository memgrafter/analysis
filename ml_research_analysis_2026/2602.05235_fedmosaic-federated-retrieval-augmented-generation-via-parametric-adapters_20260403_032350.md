# FedMosaic: Federated Retrieval-Augmented Generation via Parametric Adapters

## Quick Facts
- **ArXiv ID**: 2602.05235  
- **Source URL**: https://arxiv.org/abs/2602.05235  
- **Reference count**: 40  
- **Primary result**: Achieves +10.9% F1 over baselines while reducing storage by 78.8–86.3% and communication by 91.4% under strict locality constraints.

## Executive Summary
FedMosaic tackles federated retrieval-augmented generation (FedRAG) under data locality constraints, where distributed silos cannot share raw documents. It integrates knowledge across silos using parametric adapters paired with document-specific binary masks. The core innovations are (1) clustering related documents into multi-document adapters to dramatically cut storage and communication, and (2) a selective aggregation mechanism that picks adapters based on relevance scores and mask overlap, avoiding destructive parameter merging. Evaluations on four QA datasets show significant gains in answer accuracy (average +10.9% F1) and efficiency, while preserving locality and offering stronger privacy than prior FedRAG methods.

## Method Summary
The method operates in offline and online phases. **Offline**: Each silo clusters its documents via constrained k-means on embeddings (maximum cluster size 5–10). For every cluster, a LoRA adapter is trained on augmented data (rewrites and QA pairs generated by an LLM). Simultaneously, a binary mask per document is learned over the rows of the adapter’s frozen *B* matrix, using next-token loss plus an ℓ1 sparsity regularizer; after training, the mask is binarized. **Online**: Upon a query, silos retrieve top‑k local documents, re‑rank with a shared cross‑encoder to obtain relevance scores and retrieve the stored masks. They upload the scores and masks to the server. The server selects a subset of documents by maximizing total relevance minus a penalty for mask overlap (greedy selection with threshold). It then requests the corresponding adapters, aggregates them via a weighted sum of masked *B* matrices times *A*, merges the result with the frozen base LLM, and generates the answer.

## Key Results
- **+10.9%** average F1 improvement over state-of-the-art baselines on four QA datasets.
- **78.8–86.3%** storage reduction compared to naive per‑document adapters.
- **91.4%** communication reduction per query.
- Enforces strict **data locality** and provides **stronger privacy** than in‑context FedRAG.

## Why This Works (Mechanism)
FedMosaic succeeds by solving two key challenges: parameter overhead and destructive interference. Multi‑document adapters share parameters across related documents, reducing the total number of adapters while maintaining expressiveness through masks that isolate document‑specific contributions. Selective aggregation ensures that only adapters with high relevance and minimal overlapping masked rows are merged, preventing conflicting updates and preserving the integrity of the combined knowledge. Because only adapters—never raw documents—are transmitted, locality is respected, and the masks act as a form of on‑demand parameter routing that mitigates interference.

## Architecture Onboarding
- **Component Map**  
  Silos → (relevance scores, masks) → Server → (adapter requests) → Silos → (adapters) → Server → (merged adapter) → Base LLM → Answer

- **Critical Path**  
  1. Query broadcast to silos.  
  2. Each silo retrieves and re‑ranks local documents, computes relevance scores and retrieves stored masks.  
  3. Silos upload scores and masks to server.  
  4. Server selects top documents using a greedy algorithm that balances relevance and mask overlap.  
  5. Server requests adapters for selected documents.  
  6. Silos send the corresponding adapters.  
  7. Server aggregates adapters into a merged weight update via weighted and masked combination.  
  8. Server applies the update to the base LLM and generates the answer.

- **Design Tradeoffs**  
  - Cluster size: Larger clusters reduce adapter count but risk more interference; smaller clusters increase adapter count but simplify masking.  
  - Mask sparsity: Higher sparsity saves storage and overlap but may discard important features; lower sparsity risks destructive merging.  
  - Selection penalty (λ<sub>ol</sub>): Higher values aggressively avoid overlap but may drop relevant documents; lower values risk including conflicting adapters.  
  - Number of selected documents (k’): More documents improve coverage but increase computation and potential interference; fewer documents streamline but may omit key info.

- **Failure Signatures**  
  - Average mask sparsity < 20% indicates insufficient regularization (target ≥ 50%).  
  - Pairwise mask overlap among selected documents > 30% suggests poor selection and likely F1 drop.  
  - Greedy selector consistently picks ≤ 1 document when k’ > 1, signaling overlap penalty too high or scores too low.  
  - Re‑ranker scores poorly correlated with true relevance degrade selection quality.

- **First Three Experiments**  
  1. **Clustering and adapter training**: Simulate two silos via Dirichlet partition of a QA dataset; perform constrained k‑means per silo; train LoRA adapters per cluster; validate loss convergence.  
  2. **Mask learning and sparsity control**: For documents in a cluster, train binary masks with a sweep over λ<sub>l1</sub>; measure resulting sparsity and overlap; select hyperparameters achieving ≥ 50% sparsity and ≤ 20% overlap.  
  3. **End‑to‑end pipeline evaluation**: Implement the online phase; run on test queries; compute F1, storage per document, and communication per query; compare against a per‑document adapter baseline to verify reported reductions.

## Limitations
- Missing implementation details for the shared re‑ranker (model architecture, training data) hinder exact replication.
- Undisclosed hyperparameters for mask training (λ<sub>l1</sub>, α) and selective aggregation (λ<sub>ol</sub>, τ) create uncertainty in performance and efficiency trade‑offs.
- Recognized failure modes (dense masks, high overlap) require careful tuning; absent guidance increases risk of degraded F1.

## Confidence
- **High**: Locality enforcement and privacy (no raw document transfer) are robustly addressed.
- **Medium**: Storage reduction via masked multi‑document adapters is plausible but depends on achieving sufficient mask sparsity and low overlap; requires tuning.
- **Low**: Overall F1 gains and communication reductions rely on undisclosed hyperparameters and re‑ranker design; exact replication of reported improvements is uncertain.
