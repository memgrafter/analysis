# KernelSkill: A Multi-Agent Framework for GPU Kernel Optimization
## Quick Facts
- **arXiv**: 2603.10085
- **Source URL**: https://arxiv.org/abs/2603.10085
- **Reference count**: 17
- **Primary result**: 100% success on KernelBench Levels 1–3 with average speedups up to 5.44× over Torch Eager.

## Executive Summary
KernelSkill tackles inefficient and opaque GPU kernel optimization by replacing implicit LLM heuristics with a knowledge-driven, trajectory-aware multi-agent framework. Its dual-level memory—long-term for reusable expert optimization skills and short-term for per-task repair history—enables traceable method selection and prevents backtracking. On KernelBench Levels 1–3, it achieves a 100% success rate with average speedups of 5.44×, 2.82×, and 1.92× over Torch Eager, outperforming all prior baselines. Ablation confirms both memory components are essential, with long-term memory critical for the highest speedups.

## Method Summary
KernelSkill orchestrates a pipeline of specialized agents. It starts with a Generator that produces initial CUDA kernels from PyTorch reference code. A Reviewer (incorporating compiler, verifier, and profiler) evaluates these seeds and selects the best base kernel. The system then enters an iterative refinement loop (up to N rounds). In each round, the Reviewer runs on the current base kernel. If errors are found, a Diagnoser consults short-term repair memory to propose fixes, and a Repairer applies them. Otherwise, a Feature Extractor analyzes the kernel’s static and dynamic characteristics; this triggers retrieval from Long-term Memory (a curated library of expert optimization skills). A Planner then uses the retrieved methods along with short-term optimization memory to devise an optimization plan, which an Optimizer executes. After each step, both short-term memories are updated. Speedup thresholds determine whether the new kernel becomes the new base or best kernel. This closed-loop, memory-driven coordination yields robust and explainable optimization.

## Key Results

- Average speedups: 5.44× (Level 1), 2.82× (Level 2), 1.92× (Level 3) over Torch Eager.

## Why This Works (Mechanism)
### Mechanism 1: Explicit, traceable expert knowledge for method selection
- **Claim**: KernelSkill replaces implicit LLM heuristics with explicit, traceable expert optimization skills.
- **Mechanism**: Long-term memory stores a structured library of optimization skills (bottleneck patterns, decision rules, implementation cues). The Feature Extractor produces code features; a deterministic retrieval policy matches these and profiling signals to select candidate methods, which the Planner then executes.
- **Core assumption**: Expert optimization knowledge can be captured in a rule‑based, retrievable format that generalizes across kernels.
- **Evidence**: The long-term memory integrates a library of targeted kernel‑optimization skills distilled from prior GPU optimization literature; the retrieval is deterministic and traceable, contrasting with implicit LLM heuristics. (Sec. 4.2.1)
- **Break condition**: If no matching case is retrieved, the system falls back to LLM‑only selection, reducing reliability and speedup gains.

### Mechanism 2: Short‑term memory for preventing backtracking
- **Claim**: Short‑term memory records per‑task repair and optimization history, preventing oscillations and enabling coupled multi‑step improvements.
- **Mechanism**: After each round, the system logs the plan, edits, and outcomes (compilation, correctness, profiling). This history is injected into Diagnoser and Planner prompts, conditioning subsequent plans on past attempts and avoiding repeated ineffective edits.
- **Core assumption**: Optimization and repair are sequential processes where past outcomes strongly predict future success; recording these reduces cycles.
- **Evidence**: Short‑term memory maintains an explicit per‑task refinement trace that is used to prompt the Diagnoser and Planner, explicitly conditioning on prior attempts. (Sec. 4.2.2)
- **Break condition**: Unbounded growth may exceed LLM context windows, requiring pruning or summarization; otherwise, history loss reintroduces cycles.

### Mechanism 3: Multi‑agent closed‑loop orchestration
- **Claim**: A multi‑agent architecture with specialized roles, guided by memory, yields robust iterative kernel refinement.
- **Mechanism**: The pipeline consists of Generator, Reviewer, Feature Extractor, Retrieval, Diagnoser, Planner, Optimizer/Repairer, and the two memory systems. Agents interact in a closed loop: each round produces a new kernel, and memories are updated. This decomposition allows targeted prompting and clear error handling.
- **Core assumption**: Decomposing the optimization process into distinct agents improves robustness and allows targeted prompting; memory provides continuity across rounds.
- **Evidence**: The full pipeline is described in Sec. 4.1 and Algorithm 1, detailing each agent’s responsibilities and the iteration logic. Multi‑agent designs are common in recent systems, but KernelSkill’s integration of dual‑level memory is novel.
- **Break condition**: Agent misinterpretation of tools or prompts can derail the loop; robust error handling and memory consistency are necessary to recover.

## Architecture Onboarding
### Component Map
Generator → Reviewer → [loop: if errors: Diagnoser → Repairer; else: Feature Extractor → Long‑term Memory (Retrieval) → Planner → Optimizer] → new kernel. All agents read/write Short‑term Memory; Reviewer provides profiling feedback used by Feature Extractor and Retrieval. Long‑term Memory consists of a Deterministic Decision Policy and a Method Knowledge library.

### Critical Path
1. Generate seed kernels and pick the best Reviewer‑validated seed.
2. For each round up to N:
   - Run Reviewer on the current base kernel.
   - If errors: Diagnoser (using short‑term repair memory) → Repairer → new kernel.
   - Else: Feature extraction → Retrieval from long‑term memory → Planner (using short‑term optimization memory) → Optimizer → new kernel.
   - Update short‑term memory with this round’s trajectory.
   - If the new kernel achieves a speedup beyond thresholds, update the base kernel and/or best kernel.
3. Return the best kernel found.

### Design Tradeoffs
- Rule‑based vs. LLM‑based feature extraction: rules offer determinism but lower recall; LLMs cover variability but may be inconsistent.
- Long‑term memory breadth vs. retrieval speed: larger knowledge base improves coverage but may increase decision latency.
- Short‑term memory window size: longer history aids context but risks exceeding LLM context limits, necessitating summarization.
- Agent decoupling: specialization improves prompt design but adds coordination overhead.

### Failure Signatures
- Repeated compilation errors with no success: Diagnoser stuck; inspect repair memory content or failure patterns.
- Speedup plateau despite many rounds: likely lack of relevant methods in long‑term memory; fallback heuristics insufficient.
- Prompt context overflow: short‑term memory too large; apply truncation or summarization strategies.
- Inconsistent method selection (e.g., applying tensor cores when precision incompatible): bug in decision policy or feature extraction; verify feature values.

### First 3 Experiments (for Validation)
1. **Short‑term repair memory efficacy**: Compare success rate on multi‑step repair tasks with and without short‑term memory; expect lower success when memory disabled due to cycling.
2. **Long‑term memory impact**: Disable long‑term retrieval (use LLM‑only method selection) on Level 1 tasks; measure drop in average speedup, confirming knowledge contribution.
3. **Decision policy sanity check**: Manually compute features for a kernel, invoke the deterministic policy, and verify that retrieved methods align with known bottleneck patterns; refine rules for mismatches.

## Limitations
- Evaluation is confined to KernelBench Levels 1–3; generalization to other kernel families or large‑scale applications remains unknown.
- Long‑term memory depends on manually curated expert skills; coverage gaps force fallback to LLM, potentially reducing performance.
- Short‑term memory may grow unbounded, requiring pruning to avoid context window overflow; pruning strategies are not yet validated.

## Confidence
- Success rates and speedups on KernelBench: **High**
- Dual‑level memory is essential: **High**
- Knowledge‑driven selection outperforms LLM heuristics: **Medium**
- Multi‑agent orchestration prevents backtracking: **Medium**
