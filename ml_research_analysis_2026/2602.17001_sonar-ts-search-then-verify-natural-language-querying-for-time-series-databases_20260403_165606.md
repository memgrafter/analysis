# Sonar-TS: Search-Then-Verify Natural Language Querying for Time Series Databases
## Quick Facts
- arXiv ID: 2602.17001
- Source URL: https://arxiv.org/abs/2602.17001
- Reference count: 40
- Primary result: Sonar-TS achieves an average score of 0.6168 on NLQTSBench, substantially outperforming Text-to-SQL (0.1562) and time series models.

## Executive Summary
Sonar-TS is a system for natural language querying of massive time series databases, specifically targeting morphological pattern retrieval (e.g., shapes, anomalies) in ultra-long histories. It introduces a neuro-symbolic Search-Then-Verify pipeline: offline multi-scale feature tables (SAX strings and statistics) enable efficient candidate retrieval via SQL; thereafter, Python-based verification uses domain-specific operators on raw signals for precise validation. Evaluated on NLQTSBench (831 queries), Sonar-TS achieves an average score of 0.6168, far surpassing existing approaches. Ablations confirm the critical roles of the feature index (morphology), verification (algorithmic reasoning), and an Experience loop that distills heuristics from execution trajectories.

## Method Summary
Sonar-TS preprocesses time series into multi-resolution feature tables (yearly, monthly, daily). Each table stores symbolic SAX representations (alphabet size 5) and statistical primitives (min, max, avg, std, slope). At query time, an LLM-based Task Planner decides between direct access (fixed range) or Search-Then-Verify mode. For the latter, a Code Generator produces SQL that queries the feature tables using regex on SAX and statistics to yield candidate window IDs. Then Python code, leveraging a library of atomic operators (e.g., detect_period, find_best_match), verifies candidates against the raw signal. Errors trigger up to three self-correction retries. A post-execution Experience loop automatically summarizes execution insights and updates a bounded knowledge pool (<20 items) to improve subsequent queries. The final answer is formatted appropriately.

## Key Results
- Average score 0.6168 on NLQTSBench (831 queries, ~170k-point histories), dwarfing best Text-to-SQL baseline (0.1562) and TS model performance on short-context subsets.
- Ablation: removing Feature Table causes severe drop in morphology tasks (e.g., CT from 0.30 to 0.04); removing Verification reduces overall average from 0.62 to 0.25, especially on algorithmic tasks.
- Experience mechanism improves robustness on domain-specific reasoning tasks like Contextual Anomaly detection.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Multi-scale feature tables (SAX + statistics) enable efficient, approximate candidate retrieval over ultra-long histories by transforming continuous morphology into discrete, queryable tokens.
- **Mechanism:** Offline preprocessing discretizes windows into symbolic SAX strings and computes summary statistics. At query time, SQL filters (e.g., regex on SAX) rapidly prune irrelevant windows using these precomputed descriptors, avoiding full raw-data scans.
- **Core assumption:** Abstract morphological concepts (e.g., "V-shape") can be coarsely approximated by piecewise symbolic representations (SAX) without losing essential discriminative power.
- **Evidence anchors:** [abstract] "offline multi-scale feature tables (using SAX strings and statistics) enable efficient candidate retrieval via SQL"; [section 4.2] Feature Tables as a "Queryable Semantic Index" with "Morphological Tokens" and "Statistical Primitives"; [section 5.3 ablation] "removing the Feature Table severely impacts morphology-driven tasks (e.g., CT drops 0.30→0.04)".
- **Break condition:** If the SAX alphabet size or window granularity mismatches the target pattern's scale, the symbolic approximation may miss subtle nuances or yield no candidates.

### Mechanism 2
- **Claim:** Python-based verification against raw signals provides necessary computational precision for tasks requiring algorithmic reasoning (e.g., period detection, change-point analysis) that are inexpressible in SQL.
- **Mechanism:** After SQL narrows candidates, generated Python code executes domain-specific operators (e.g., PELT for changepoints, DTW for matching) on the exact raw signal slices to validate constraints and compute precise answers.
- **Core assumption:** Certain morphological or logical queries require non-linear, stateful computations that cannot be encoded as static SQL predicates, especially over variable-length patterns.
- **Evidence anchors:** [abstract] "followed by Python-based verification against raw signals"; [section 4.3.1] "Operator-based Verification: For the localized candidates, the system synthesizes executable programs to perform execution-grounded validation."; [section 5.3 ablation] "removing the Verification stage causes the most severe collapse (Avg. 0.62→0.25), especially on algorithmic tasks like PD and IS."
- **Break condition:** If the verification operator library is incomplete or the generated code misapplies operators, precise grounding fails.

### Mechanism 3
- **Claim:** The closed-loop "Experiences" mechanism (reward-summarize-update) distills domain heuristics from execution trajectories, improving robustness without model fine-tuning by adaptively guiding the LLM's planning and code generation.
- **Mechanism:** After each query execution, a deterministic reward scores the result. An LLM summarizer extracts a generalizable insight from the full trajectory (plan, code, errors). An updater merges this insight into a bounded global set (<20 items), which is injected into subsequent prompts to guide future decisions.
- **Core assumption:** LLM solvers for complex, knowledge-intensive domains benefit more from dynamic, trajectory-derived few-shot guidelines than from static templates.
- **Evidence anchors:** [section 4.3.2] details the "Reward-Summarize-Update process" and states it "progressively accumulates domain know-how, improving robustness without expensive model fine-tuning."; [section 5.3 ablation] "removing Experiences leads to broad degradation, particularly on tasks requiring domain-specific reasoning, such as Contextual Anomaly."; [section B.2.2] shows example Experiences like "For structural trend reporting, do not calculate a global slope. Instead, use a divide-and-conquer approach..."
- **Break condition:** If the summarizer produces low-quality or overly specific insights, or the updater allows redundancy/inflation, the knowledge base becomes noisy, diluting guidance.

## Foundational Learning
- **SAX (Symbolic Aggregation Approximation):** Transforms raw numeric sequences into discrete strings, enabling efficient similarity search and regex matching in SQL. *Why needed here:* The entire search mechanism relies on matching morphological patterns via SAX regex. *Quick check:* How does the choice of SAX alphabet size and PAA segment length affect the trade-off between pattern distinguishability and index size?
- **Neuro-Symbolic Pipeline Decomposition:** Separates the problem into a scalable, recall-oriented search (symbolic SQL on features) and a precise, resource-intensive verify (Python on raw data). *Why needed:* Addresses the dual challenges of scale (ultra-long histories) and morphology (expressivity). *Quick check:* Why is a single end-to-end LLM call insufficient compared to the search-then-verify split?
- **Deterministic Reward Design for Complex Output Types:** Provides executable, type-aware feedback (IoU, relative accuracy, F1, composite score) to guide experience learning. *Why needed:* Queries produce diverse answer types; metrics must be computable to score results. *Quick check:* How does the composite report score for Level 4 tasks avoid pitfalls of free-text metrics by enforcing structured schema and controlled vocabulary?

## Architecture Onboarding
- **Component map:** Offline Data Processing (multi-scale feature tables) → Online Querying (Task Planner → Code Generator → Executor → Experience Manager) → Post-processing (formatting and visualization).
- **Critical path:** Natural Language Query → Task Plan (mode selection) → SQL on Feature Tables → Candidate window IDs → Python `sonar_ops` verification on raw slices → `final_answer` variable → Post-processing output.
- **Design tradeoffs:** 
  - Indexing vs. Storage: Feature tables add storage but enable sub-linear search; trade-off: materialization cost vs. query latency.
  - SAX Expressivity vs. Precision: Coarse SAX supports SQL regex but discards fine details; may miss exact patterns.
  - LLM Autonomy vs. Control: High-level planning/codegen is flexible but error-prone; mitigated by atomic operators and self-correction.
- **Failure signatures:**
  - Planning failure: Misclassifies mode, leading to empty/inaccurate results.
  - Search failure: SQL returns no candidates (SAX regex too strict); fallback to full raw scan needed.
  - Verification failure: Python code errors or misapplied operators; self-correction may exhaust retries.
  - Experience poisoning: Redundant/incorrect experiences accumulate, degrading prompts over time.
- **First 3 experiments:**
  1. Benchmark Sanity Check: Run Sonar-TS on NLQTSBench-Lite to verify baseline competency on short-context pattern tasks.
  2. Ablation - Feature Tables: Disable Feature Table usage to confirm indexing necessity on morphology-heavy tasks.
  3. Case Study - Longest Plateau: Inspect generated SQL and Python for a Level 2 query to validate search-verify coupling.

## Open Questions the Paper Calls Out
### Open Question 1: Enhancing Symbolic Shape Representations
- **Question:** How can symbolic shape representations (like SAX) be enhanced to preserve fine-grained morphological details necessary for short-context pattern recognition without sacrificing query efficiency?
- **Basis:** The authors observe that Sonar-TS’s accuracy on morphology tasks drops in the short-context NLQTSBench‑Lite setting due to information loss from SAX compression (Section 5.2).
- **Why unresolved:** The SAX‑based index is central to scalability yet discards local details, potentially failing on subtle patterns. The trade‑off remains unaddressed.
- **Evidence needed:** Systematic comparison of alternative discretization schemes (larger alphabets, adaptive PAA, learned embeddings) with recall‑precision curves across window lengths on morphology‑heavy benchmarks.

### Open Question 2: Generalization and Optimization of Experience Learning
- **Question:** To what extent does the Experience mechanism generalize beyond NLQTSBench, and how can its dynamic update policy be optimized to maximize learning efficiency while avoiding redundancy or forgetting?
- **Basis:** Section 4.3.2 describes a closed‑loop Reward‑Summarize‑Update loop that maintains a compact set (<20) of insights. Performance gains are shown, but long‑term behavior, scalability, and transferability are unexplored.
- **Why unresolved:** Experiences are distilled automatically via LLMs; the interplay between update frequency, merging heuristics, and accuracy is unclear. Cross‑domain transfer is unknown.
- **Evidence needed:** Longitudinal runs tracking experience pool size and content over hundreds of queries, measuring incremental gains against static baselines. Cross‑domain transfer tests (synthetic to real‑world).

### Open Question 3: Extending the Verification Operator Library
- **Question:** How can the verification operator library be systematically extended to cover a broader range of algorithmic reasoning tasks while preserving atomicity and composability for LLM code generation?
- **Basis:** The framework relies on a fixed set of domain‑specific operators (detect period, find best match, detect changepoints, calc trend slope, calc correlation) (Table 4). The paper does not explore selection or expansion.
- **Why unresolved:** More complex Level‑4 tasks or specialized domains may require additional primitives (e.g., seasonality decomposition, causal tests). Determining which operators yield the greatest coverage, how to design them for robust LLM usage, and how composition affects answer quality remain open.
- **Evidence needed:** Incremental ablation studies adding new operators (e.g., STL, Granger causality) and measuring impact on a diverse query suite. Expert elicitation to identify missing primitives for real‑world use cases.

### Open Question 4: Scaling to Ultra‑Long Histories
- **Question:** Does the Search‑Then‑Verify paradigm scale to truly ultra‑long histories (multi‑year, high‑frequency data) in terms of index size, query latency, and retrieval accuracy, and what are the trade‑offs between multi‑scale feature granularity and recall?
- **Basis:** Evaluations use histories of ~170 k points with three fixed granularities (Year/Month/Day). Scaling beyond this and granularity trade‑offs are not analyzed.
- **Why unresolved:** Industrial TSDBs may store billions of points. Precomputed feature tables could become massive, and SQL search latency might degrade. The optimal balance of resolution and efficiency is unknown; adaptive indexing may be needed.
- **Evidence needed:** Scaling experiments with synthetic datasets of 10 M–100 M points, measuring index build time, storage overhead, query latency, and answer quality for different granularity settings. Theoretical analysis linking SAX parameters and window sizes to expected recall.

### Open Question 5: Robustness to Real‑World Data Issues
- **Question:** How robust is Sonar‑TS to real‑world data issues such as noise, missing values, and irregular sampling, and what preprocessing extensions are necessary to maintain performance under such conditions?
- **Basis:** The Experiences mention pitfalls like irregular sampling gaps (Section 4.3.2) and the pipeline assumes regular intervals for SAX. Evaluation uses curated synthetic injections on clean data, leaving robustness unquantified.
- **Why unresolved:** Real‑world TSDBs frequently contain gaps, outliers, and non‑uniform timestamps. These could distort the feature index and break verification operators. Deployment risks remain high.
- **Evidence needed:** Controlled degradation studies injecting missingness, irregular timestamps, and varying noise levels into the benchmark, tracking performance decay. Development and evaluation of integrated resampling/imputation operators within the workflow.

## Limitations
- SAX parameterization (alphabet breakpoints, window sizes) is not fully specified, affecting index quality and reproducibility.
- The set of atomic verification operators is described but their complete implementations and coverage boundaries are undocumented; missing operators could limit task support.
- NLQTSBench generation details (query templates, injection parameters) are opaque, hindering independent extension and replication.
