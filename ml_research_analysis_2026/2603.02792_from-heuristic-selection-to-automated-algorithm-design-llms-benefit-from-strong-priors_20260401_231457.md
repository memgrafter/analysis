# From Heuristic Selection to Automated Algorithm Design: LLMs Benefit from Strong Priors

## Quick Facts
*   **arXiv ID:** 2603.02792
*   **Source URL:** https://arxiv.org/abs/2603.02792
*   **Reference count:** 40
*   **Primary result:** BAG, a benchmark-guided approach that periodically injects top benchmark algorithm codes into LLM prompts, achieves state-of-the-art normalized AUC on pbo (23 problems) and bbob (24 problems), improving average AUC by 14% over the best baseline on bbob.

## Executive Summary
This paper investigates uncontrolled search dynamics in Large Language Model (LLM)-driven black-box optimization for automated algorithm design. Using AttnLRP, a token attribution method, the authors demonstrate that the provided example code in the prompt is the dominant influence on the LLM's generated output, outweighing linguistic task descriptions and fitness values. Motivated by this finding, they propose BAG (Benchmark-guided Algorithm Generation), which periodically injects codes from a set of high-quality human-designed benchmark algorithms into the refinement loop. This mechanism steers the LLM's search across multiple high-performance neighborhoods in algorithm space. Evaluated on the pbo and bbob suites with three LLMs, BAG consistently achieves top-2 rankings and significant performance gains, demonstrating that integrating strong, diverse priors from benchmark algorithms enhances both efficiency and robustness in LLM-based automated algorithm design.

## Method Summary
BAG operates within a (1+1) elitist evolutionary loop where an LLM acts as a variation operator. The process is initialized with the best algorithm from a predefined benchmark set `A_bench` (top-5 human-designed algorithms for the problem suite). For each of up to 100 LLM queries, the system constructs a prompt containing a reference algorithm code and a strategy instruction ("refine" or "create"). With 50% probability, it refines the current best algorithm; otherwise, it creates a novel algorithm guided by the current best. Crucially, every 10 iterations, the reference is randomly switched to a different algorithm from `A_bench`, injecting strong prior knowledge and resetting the search trajectory. The generated algorithm is evaluated on a set of problem instances, and its normalized AUC (area under the ECDF curve) determines if it replaces the current parent. This periodic reintroduction of benchmark codes allows the search to escape local basins associated with any single starting algorithm.

## Key Results
*   On the bbob suite (24 problems), BAG improves average normalized AUC by 14% over the best prior baseline (e.g., Gemini: BAG 0.934 vs. EoH 0.878).
*   On the pbo suite (23 problems), BAG achieves consistently top-2 performance across three LLMs, with an average rank between 2.17 and 2.38.
*   BAG demonstrates strong generalization to unseen test instances and reduces failure rates compared to baseline methods, indicating improved robustness.

## Why This Works (Mechanism)
### Mechanism 1: Code Examples Dominate Token Attribution
*   **Claim:** In LLM-driven algorithm generation, code-related prompt tokens (the reference algorithm's code and the "refine"/"create" strategy) receive the highest token-wise attribution scores (via AttnLRP), making them the primary drivers of the generated code.
*   **Mechanism:** AttnLRP relevance propagation indicates the LLM attends most strongly to the syntactic and semantic patterns in the provided example code, rather than to linguistic task descriptions or numerical fitness values. This makes the reference code the strongest prior shaping the output distribution at each generation step.
*   **Evidence:** [section V] Table I shows code description relevance scores are 3–6× higher than task description or fitness value scores. [abstract] directly states AttnLRP reveals code examples most strongly influence generated algorithms.
*   **Break condition:** If AttnLRP's propagation rules are invalid for decoder-only models in code synthesis, or if subsequent work finds linguistic priors dominate for certain problem classes.

### Mechanism 2: Benchmark Codes Steer Search Neighborhoods
*   **Claim:** Starting the LLM-driven refinement with a specific high-quality benchmark algorithm constrains the search to a local neighborhood of structurally similar algorithms. Different initial benchmarks lead to divergent performance outcomes.
*   **Mechanism:** In the (1+1) elitist scheme, the prompt's reference code defines a manifold of solutions the LLM is likely to generate via in-context learning. Each iteration's "refine" operation produces variations that inherit the reference's structure, performing a local search within that region. The initial benchmark thus determines the starting basin.
*   **Evidence:** [section VI] Figure 3 shows five Refine:Ai runs with different initial benchmark algorithms produce clearly different AUC convergence curves on OneMax, with some significantly outperforming baselines. [section VI]notes refinement-only parallels LHNS, supporting the neighborhood search interpretation.
*   **Break condition:** If LLMs fail to maintain structural similarity during refinement (generate arbitrarily different code), or if the benchmark codes themselves are not locally optimizable.

### Mechanism 3: Periodic Benchmark Reintroduction Escapes Local Optima
*   **Claim:** Injecting benchmark algorithms at fixed intervals (q=10) rejuvenates the search by reintroducing high-quality genetic material from diverse basins, leading to better final performance.
*   **Mechanism:** Every q iterations, the current parent is replaced by a randomly selected benchmark algorithm for refinement. This resets the search trajectory, allowing the LLM to explore regions around different strong priors. CodeBLEU similarity scores drop sharply after injection, confirming the introduction of new structural patterns.
*   **Evidence:** [section VII] Algorithm 1 lines 8–9 defines periodic injection. [section VII] Figure 5 shows star markers (injections) often correspond to AUC improvements. [section VII] Figure 6 shows CodeBLEU similarity drops at injections (iterations 41, 51), then new clusters form. [appendix D] finds q=10 optimal.
*   **Break condition:** If the benchmark set is too homogeneous or injected algorithms are low-quality, the mechanism may degrade performance.

## Foundational Learning
*   **Concept: Token-wise attribution (AttnLRP)**
    *   Why needed: Provides empirical evidence about which prompt elements actually influence LLM output, moving beyond anecdotal prompt engineering to a mechanistic understanding.
    *   Quick check: What does a high AttnLRP relevance score for a prompt token imply about its role in generation?
*   **Concept: Black-box optimization (BBO) and anytime performance (AUC)**
    *   Why needed: The task is to generate algorithms that solve unseen BBO problems. AUC captures performance across the entire optimization trajectory, not just final best, which is essential for robust algorithm design.
    *   Quick check: Why is normalized AUC preferred over best-found fitness for comparing BBO algorithms?
*   **Concept: LLM-driven evolutionary loop**
    *   Why needed: The framework treats the LLM as a variation operator within an evolutionary algorithm. Understanding the loop (initialization, variation, evaluation, adaptation) is crucial to grasp how search proceeds and where prompt design matters.
    *   Quick check: How does the 'refine' strategy differ from 'create' in the BAG prompt template?

## Architecture Onboarding
*   **Component map:**
    Prompt Template -> LLM Query Engine -> Fitness Evaluator -> Selection Controller -> (back to Prompt Template with new reference) & (periodic trigger to Benchmark Set)
*   **Critical path:**
    1.  Initialize: select best algorithm from `A_bench` -> prompt -> generate `A` -> evaluate -> set `A* = A`.
    2.  Loop (t = 1 to B-1):
        *   If `t mod q == 0`: randomly pick `A'` from `A_bench` -> prompt (refine `A'`) -> generate `A`.
        *   Else: with 0.5 probability prompt (refine `A*`) -> `A`; else prompt (create novel with `A*`) -> `A`.
        *   Evaluate `A` -> if better than `A*`, update `A*`.
    3.  Return `A*`.
*   **Design tradeoffs:**
    *   **Search strategy:** (1+1) focuses on code refinement; population-based variants (EoH, LLaMEA) could be integrated but complicate prompt management and attribution analysis.
    *   **Benchmark size:** |`A_bench`|=5 balances diversity and signal strength. Larger sets risk diluting strong priors; smaller sets may not cover enough basins.
    *   **Injection frequency `q`:** `q=10` optimizes between exploitation (refining current best) and exploration (reintroducing benchmarks). Smaller `q` may cause premature convergence; larger `q` may miss timely exploration.
    *   **LLM selection:** Code-specialized models (Qwen Coder) produce more executable code; general instruction models (Gemma) may explore more creatively. Tradeoff between reliability and diversity.
*   **Failure signatures:**
    *   **High code failure rate** (~30% of queries): LLM outputs syntactically invalid or logically broken code. Mitigate by improving prompt clarity, reducing temperature, or adding error feedback.
    *   **Performance stagnation:** No AUC improvement for ~20 iterations. May indicate overfitting to current neighborhood; consider increasing `q` or enriching `A_bench`.
    *   **Benchmark overfitting:** Final algorithm excels on training instances but fails on unseen test instances. Suggests `A_bench` lacks generalization; need more diverse benchmarks.
*   **First 3 experiments:**
    1.  **Token attribution validation:** Run AttnLRP on 100 prompt-code pairs from early BBO runs. Confirm code-related tokens consistently score highest across LLMs and problems.
    2.  **Refinement-only neighborhood check:** For a single pbo problem, run Refine:Ai for each top-5 benchmark algorithm. Plot AUC trajectories; verify they diverge and some surpass standard LHNS/LLaMEA baselines.
    3.  **Full BAG benchmark:** Execute BAG with all three LLMs on full pbo (23) and bbob (24) suites. Compare normalized AUC, average rank, and statistical significance against EoH, LHNS, LLaMEA, MCTS-AHD, ReEvo. Validate `q=10` vs other frequencies.

## Open Questions the Paper Calls Out
*   **Open Question 1:** How can we automatically identify the most suitable benchmark algorithm(s) to initialize and guide LLM-driven optimization for a new problem domain? The paper manually selected top 5 algorithms per problem without a principled mechanism.
*   **Open Question 2:** How can benchmark-guided techniques be effectively integrated into population-based LLM-driven AAD frameworks while maintaining diversity and avoiding premature convergence? BAG uses a (1+1) elitist strategy; population-based dynamics present different challenges.
*   **Open Question 3:** What are the underlying mechanistic reasons why code examples dominate token attribution in LLM code generation for optimization tasks? AttnLRP analysis shows this consistently, but the causal explanation is unknown.
*   **Open Question 4:** How does the effectiveness of benchmark-guided LLM optimization scale with the diversity and size of the benchmark algorithm set across different problem domains? BAG used a fixed size-5 set and `q=10` with no systematic study.

## Limitations
*   **Attribution validity:** The core mechanistic claim relies on AttnLRP, which lacks thorough validation for decoder-only code models and may misrepresent token influence.
*   **Benchmark dependence:** BAG's performance hinges on a manually curated, high-quality benchmark set (`A_bench`). Its success for new domains is uncertain if suitable benchmarks are unavailable or lack diversity.
*   **Evaluation scope:** Results are restricted to two suites (pbo, bbob). Cross-domain generalizability to other combinatorial or real-world problems remains untested.

## Confidence
*   **High:** BAG's overall performance improvement (14% on bbob, top-2 on pbo) is consistent, statistically significant, and replicated across three LLMs.
*   **Medium:** Mechanistic claims (code dominance, neighborhood steering) are supported by AttnLRP and behavioral analyses but rest on assumptions about attribution validity and search manifold structure.
*   **Low:** Generality of benchmark priors and robustness to out-of-distribution problems, given limited testing across domains and fixed hyperparameters (`|A_bench|=5`, `q=10`).

## Next Checks
1.  **Attribution robustness:** Replicate AttnLRP across ≥5 decoder-only code LLMs (e.g., StarCoder, CodeLlama) on pbo/bbob; compare with alternative methods (integrated gradients, SHAP) to confirm code token dominance.
2.  **Basin coverage quantification:** Compute structural (CodeBLEU) and behavioral similarity among `A_bench` algorithms; cluster by performance on diverse BBO functions; verify the set spans multiple basins and that injection events align with basin transitions.
3.  **Cross-domain test:** Apply BAG to a new domain (e.g., TSP, job-shop scheduling) with a fresh human-designed benchmark suite; evaluate whether injection retains advantage and whether the attribution pattern holds.
