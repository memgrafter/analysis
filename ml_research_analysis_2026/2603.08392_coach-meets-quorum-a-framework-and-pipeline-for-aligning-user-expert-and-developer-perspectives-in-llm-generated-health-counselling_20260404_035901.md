# COACH meets QUORUM: A Framework and Pipeline for Aligning User, Expert and Developer Perspectives in LLM-generated Health Counselling

## Quick Facts
- **arXiv ID**: 2603.08392  
- **Source URL**: https://arxiv.org/abs/2603.08392  
- **Reference count**: 0  
- **Primary result**: The COACH RAG pipeline evaluated with the QUORUM framework demonstrates high user relevance (3.90–4.32/5), expert quality (3.73–4.02/5), and developer reliability (faithfulness 79%, completeness 97%, hallucination 22%), showing stakeholder convergence but divergence in tone preferences and tolerance for non‑harmful hallucinations.

## Executive Summary
Fragmented evaluation of LLM‑generated health counselling systems impedes reliable deployment. This paper presents QUORUM, a unified framework that assesses developer reliability, expert clinical quality, and user relevance simultaneously. COACH, an implementation of QUORUM, is a RAG pipeline that produces personalised lifestyle advice for cancer patients/survivors by combining their diary data with a vetted knowledge base (kanker.nl). Evaluation via QUORUM yields largely positive scores across all three perspectives, yet highlights divergence in tone preferences, sensitivity to data extraction errors, and tolerance for certain hallucinations. The work underscores the necessity of multi‑faceted evaluation for health‑related LLM applications.

## Method Summary
COACH uses a RAG architecture built with LangChain. The system takes structured diary data (sleep, mood, activities, goals over ≤21 days) and a user question. It embeds the query with `text‑embedding‑3‑small`, retrieves the top‑4 chunks from a vector store containing kanker.nl pages, and constructs a prompt that includes the table schema, in‑context examples for common topics (fatigue, activities), and formatting rules to separate claims about user data from contextualisation statements derived from the knowledge base. GPT‑4o generates the response. QUORUM evaluation combines developer metrics (faithfulness, completeness, hallucination via binary annotation on sampled outputs) with human surveys: 19 users and 6 experts rate outputs on 5‑point Likert scales across multiple dimensions. A minimum viable reproduction plan is provided, though key corpus and prompt specifics remain undisclosed.

## Key Results
- **User relevance** (5‑point scales): alignment 3.90, follow‑up 3.90, tone 4.32, length 4.16.  
- **Expert quality** (5‑point scales): correctness 4.02, tone 3.73, length 4.00.  
- **Developer reliability**: faithfulness 79%, completeness 97%, hallucination 22%.

## Why This Works (Mechanism)
COACH’s success stems from grounding through RAG: retrieval of authoritative kanker.nl content ensures contextualisation is evidence‑based. The prompt’s explicit separation of user‑derived claims and knowledge‑derived contextualisation enables reliable automated metrics and prevents mixing personal data with general advice. GPT‑4o’s strong instruction‑following adheres to the required structure. The multi‑perspective QUORUM evaluation not only confirms overall quality (high scores on correctness, relevance, completeness) but also reveals divergence (tone, hallucination tolerance), guiding targeted improvements.

## Foundational Learning
- **Retrieval‑Augmented Generation (RAG)**: *Why needed*: Provides external knowledge without retraining, crucial for factual accuracy in medical domains. *Quick check*: Does the system perform retrieval before generation and incorporate it into the prompt?  
- **Multi‑perspective evaluation (QUORUM)**: *Why needed*: Different stakeholders prioritise different quality aspects (reliability, clinical correctness, user satisfaction). *Quick check*: Are metrics defined for developer, expert, and user viewpoints?  
- **Prompt engineering for health domains**: *Why needed*: Ensures safe, empathetic, and properly bounded responses. *Quick check*: Does the prompt include explicit tone guidelines and structural constraints?  
- **Vector databases and embeddings**: *Why needed*: Enable efficient semantic search over large knowledge bases. *Quick check*: Is a vector store (e.g., Chroma, FAISS) used with a text embedding model?  
- **Faithfulness and hallucination metrics**: *Why needed*: Quantify grounding in provided data, essential for trust. *Quick check*: Are claims checked against the user table and contextualisation against retrieved chunks?

## Architecture Onboarding
**Component map**:  
User Diary Data + Query → Query Embedding → Retriever → kanker.nl Vector Store → Retrieved Chunks → Prompt Builder (schema, examples, formatting) → GPT‑4o → Structured Output (Claims, Contextualisation) → Evaluation (Developer metrics, User/Expert surveys)

**Critical path**:  
1. Parse diary into structured table.  
2. Embed query and retrieve top‑4 chunks.  
3. Assemble prompt with schemas, examples, and formatting instructions.  
4. Invoke GPT‑4o.  
5. Parse output into labelled sections.  
6. Compute developer metrics and distribute human surveys.

**Design tradeoffs**:  
- Retrieval top‑k = 4 balances relevance and context window; larger k risks noise, smaller k may miss key info.  
- Prompt length: in‑context examples improve topic coverage but increase token cost; limited to two common topics.  
- Output structure: strict separation aids metric computation but may reduce textual fluidity.  
- Vector store: embedding model (text‑embedding‑3‑small) favours speed over potential accuracy gains.

**Failure signatures**:  
- Low faithfulness: claims referencing diary entries not present.  
- Hallucination in contextualisation: statements unsupported by retrieved chunks.  
- Poor user alignment: low Likert scores (≤2) on alignment/follow‑up.  
- Tone mismatch: experts score tone ≤3 while users score high.  
- Structural non‑compliance: output missing required sections or containing medical advice beyond contextualisation.

**First experiments**:  
1. **Retrieval recall test**: On 50 held‑out queries, verify top‑4 chunks contain necessary information; target >80% recall.  
2. **Prompt compliance check**: Generate 20 outputs and programmatically validate presence of both claims and contextualisation sections; target 100% structural compliance.  
3. **Pilot metric reliability**: Three annotators independently score 20 outputs using developer binary metrics; compute Cohen’s κ to assess agreement (>0.8 desirable).
