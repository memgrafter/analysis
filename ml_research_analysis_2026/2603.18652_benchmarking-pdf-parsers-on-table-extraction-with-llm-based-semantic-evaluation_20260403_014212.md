# Benchmarking PDF Parsers on Table Extraction with LLM-based Semantic Evaluation
## Quick Facts
- **arXiv ID:** 2603.18652
- **Source URL:** https://arxiv.org/abs/2603.18652
- **Reference Count:** 40
- **Primary Result:** An LLM-as-judge evaluation (Gemini-3-Flash) achieves Pearson r=0.93 correlation with human judgment for table extraction quality, substantially outperforming rule-based metrics (TEDS r=0.68, GriTS r=0.70).

## Executive Summary
This paper tackles the inadequacy of rule-based metrics like TEDS and GriTS for evaluating PDF table extraction, which fail to capture semantic equivalence. The authors introduce a benchmarking framework built from synthetic PDFs generated from real arXiv LaTeX tables, providing perfect ground truth. Their core contribution is an LLM-based evaluation pipeline that uses Gemini-3-Flash to score parser outputs against ground truth on semantic accuracy. Human validation on over 1,500 ratings confirms the LLM judge's high correlation with human perception. Evaluating 21 parsers reveals significant performance gaps, with top models (e.g., Gemini 3 Pro) scoring near 9.55/10, offering practical guidance for parser selection in scientific documents.

## Method Summary
The methodology centers on a synthetic benchmarking pipeline. First, a corpus of 451 real LaTeX tables from arXiv is collected, classified by complexity, and programmatically embedded into randomly generated PDF pages using `pdflatex`, creating a test set with exact, unambiguous ground truth. Next, 21 diverse PDF parsers process these synthetic PDFs, producing heterogeneous outputs (HTML, Markdown, LaTeX, plain text). A critical matching step uses an LLM (Gemini-3-Flash) with rule-based validation to align each parser's fragmented or reordered table output to its corresponding ground truth table. Finally, the same LLM acts as a judge, scoring each matched table pair on a 0–10 scale for semantic fidelity (content accuracy and structural preservation). The validity of this LLM-as-judge approach is established through a large-scale human study.

## Key Results
- The LLM-based evaluation score correlates strongly with human judgment (Pearson r=0.93), while TEDS (r=0.68) and GriTS (r=0.70) show moderate correlation.
- Evaluated parser performance spans a wide range (2.10 to 9.55 on a 10-point scale), with proprietary LLM-based parsers (Gemini 3 Pro, Claude 3.5 Sonnet) achieving the highest semantic accuracy.
- Rule-based metrics fail to align with human perception because they penalize harmless surface variations (e.g., "85%" vs. "85.0%") but underweight critical semantic errors like a lost decimal or sign flip.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** LLM-as-a-judge evaluation captures semantic table equivalence where rule-based metrics fail.
- **Mechanism:** An LLM is prompted to score a parsed table against LaTeX ground truth on a 0–10 scale, jointly assessing content accuracy and structural preservation (correct header-cell associations). This replaces character-level edit distance with human-like semantic judgment.
- **Core assumption:** Modern LLMs possess sufficient world knowledge to judge whether tabular information is preserved, even with surface-form differences.
- **Evidence anchors:** The abstract reports Pearson r=0.93 vs. human judgment, versus r=0.68/0.70 for TEDS/GriTS. Section 4.1 details how string metrics mispenalize equivalent values and underweight critical errors.
- **Break condition:** Correlation would drop if the LLM exhibits format bias or fails on highly complex, domain-specific tables outside its training distribution.

### Mechanism 2
- **Claim:** The LLM-based matching pipeline reliably aligns each parser's output table to its exact ground truth despite heterogeneous outputs and parser inconsistencies.
- **Mechanism:** For a parser's full-page output, an LLM is given all ground truth tables on that page and extracts the corresponding representation for each. A rule-based post-validation step then verifies the extracted text against the original parser output to prevent hallucination.
- **Core assumption:** The matching LLM can identify semantic table correspondence across structural variations (splits, merges, reordering), and post-validation ensures fidelity.
- **Evidence anchors:** Section 3.2 states the pipeline is "necessary" because parsers "may split or merge tables, reorder content... or fail to recognize tables entirely." Successful meta-evaluation (n=518) in section 4.4 implies accurate matching.
- **Break condition:** Matching recall would fail if a parser's output is extremely fragmented or if the LLM cannot disambiguate multiple similar tables on a page.

### Mechanism 3
- **Claim:** Synthetic PDFs generated from arXiv LaTeX tables provide scalable, perfectly annotated ground truth.
- **Mechanism:** Real LaTeX tables are extracted from arXiv, classified, and embedded into randomly generated PDF pages with varied layouts and filler text via `pdflatex`. The original LaTeX serves as exact ground truth.
- **Core assumption:** Synthetic PDFs capture the structural diversity of real scientific tables sufficiently for benchmarking.
- **Evidence anchors:** Section 3.1 claims this "ensures realistic complexity and diversity" and eliminates "manual annotation." Section 6 acknowledges a limitation: "Synthetic PDFs do not capture the full diversity of real-world tables... leaving domains such as financial reports or medical records unrepresented."
- **Break condition:** If synthetic generation introduces artifacts (e.g., perfectly clean text, no compression noise), performance may not generalize to real scanned PDFs.

## Foundational Learning
- **Concept:** LLM-as-a-Judge Paradigm
  - **Why needed:** To move evaluation beyond syntactic similarity (edit distance) toward semantic judgment of information fidelity, which is the actual goal of data extraction.
  - **Quick check:** What are two examples of surface-level differences that TEDS would penalize but a human would consider semantically equivalent? (e.g., "85%" vs. "85.0%", unit symbol encoding differences).
- **Concept:** Rule-Based vs. Semantic Metrics Trade-off
  - **Why needed:** Understanding why TEDS/GriTS cluster within a narrow correlation band (r=0.56–0.70) despite parser performance spanning 2.10–9.55 LLM scores is key to interpreting benchmark results.
  - **Quick check:** If two parser outputs both have a TEDS of 0.85, what range of human-perceived quality might they actually represent? (Potentially from mediocre to excellent, if one has critical semantic errors TEDS misses).
- **Concept:** PDF Parsing Pipeline Variability
  - **Why needed:** Parsers output wildly different formats (HTML, Markdown, LaTeX, plain text) and may detect, split, or merge tables differently. This necessitates the matching pipeline and explains low scores for parsers like GROBID that don't produce tabular structure.
  - **Quick check:** Why would a rule-based metric like TEDS be inapplicable to GROBID's output in this study? (Because GROBID outputs plain text without table markup, making structural comparison impossible; the LLM judge must infer structure from text alignment or context).

## Architecture Onboarding
- **Component map:**
  synthetic_pdf_generator -> parser_executor -> table_matcher -> llm_judge -> leaderboard
  human_annotation_interface (parallel validation side-path)
- **Critical path:** Generate synthetic PDFs with ground truth -> run all parsers -> match parser outputs to ground truth tables using LLM + rules -> score each match with LLM judge -> aggregate scores for leaderboard.
- **Design tradeoffs:** 
  - **LLM judge cost vs. fidelity:** Gemini-3-Flash chosen for near-ceiling correlation (r=0.927) at lower cost than Claude Opus (r=0.939). Using a weaker LLM saves money but loses nuance.
  - **Synthetic vs. real data:** Synthetic data gives perfect, cheap ground truth and control over complexity, but may not generalize to scanned docs or non-academic layouts.
  - **Matching automation vs. accuracy:** Fully automated matching scales but errors cascade; human matching was used only for the validation subset.
- **Failure signatures:**
  - **LLM judge bias:** The judge model may favor certain formats; if it was used to generate "error hints" for humans (as with Claude Opus), human scores could be artificially inflated.
  - **Matching pipeline failure:** A parser that splits one table into multiple fragments or merges two tables may not match correctly, leading to false low scores.
  - **Format mismatch:** Parsers outputting plain text without table markup (e.g., PyMuPDF4LLM) have extremely low TEDS (inapplicable) and rely entirely on the LLM judge's ability to infer structure.
- **First 3 experiments:**
  1. **Human validation replication:** On a fixed subset of 518 table pairs, reproduce the correlation numbers (r=0.93 for Gemini-3-Flash) to confirm the evaluation pipeline's reliability before scaling.
  2. **Matching recall test:** Manually verify on 50 random tables that the matcher correctly identified the parser's output table corresponding to each ground truth table; expected recall >95%.
  3. **Parser smoke test:** Run all 21 parsers on 5 synthetic pages and check that each produces output and that the matcher returns a non-zero number of matched tables per parser; catch integration issues early.

## Open Questions the Paper Calls Out
1. **How can the benchmark incorporate more diverse document formats (e.g., scanned documents, financial or medical reports) to assess parser generalizability beyond scientific arXiv tables?** The current benchmark uses synthetic PDFs generated from arXiv LaTeX sources only, which may not capture the variability of scans, non-scientific layouts, or domain-specific structures.
2. **Can PDF parsers reliably extract tabular data when tables are embedded within figures or images, and how should such extractions be semantically evaluated?** The benchmark assumes tables are in the text layer; figure-embedded tables require vision-based extraction and lack clear ground truth alignment.
3. **Does the LLM-as-a-judge semantic evaluation generalize to domains beyond scientific arXiv tables, such as financial or medical tables with specialized notations?** The LLM judge was validated primarily on arXiv tables; other domains may have different semantic expectations affecting judgment reliability.
4. **How can the benchmarking framework be extended to evaluate holistic document parsing that jointly extracts tables, formulas, and text?** Current evaluation isolates table extraction; real-world parsing requires coherent integration where errors in one component affect others.

## Limitations
- **Synthetic Data Generalization:** arXiv-based synthetic tables may not represent real-world complexity (scans, non-academic layouts), leading to low confidence in performance transfer.
- **LLM Judge Bias:** Gemini-3-Flash may harbor format preferences; human validation mitigates but doesn’t eliminate this risk, yielding medium confidence in bias-free evaluation.
- **Matching Pipeline Fragility:** LLM-based matching could fail on highly fragmented/merged outputs, systematically penalizing certain parsers; confidence in robust matching across all 21 parsers is medium.

## Confidence
- **LLM-as-Judge Validity** (r=0.93 with humans): **High** (direct human validation provided).
- **Matching Pipeline Accuracy**: **Medium** (validated indirectly via meta-evaluation; no standalone recall test).
- **Synthetic Benchmark Utility** (generalization to real-world): **Low** (acknowledged domain limitation; no real-world correlation test).

## Next Checks
