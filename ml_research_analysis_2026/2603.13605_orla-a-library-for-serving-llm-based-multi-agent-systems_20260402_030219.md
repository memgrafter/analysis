# Orla: A Library for Serving LLM-Based Multi-Agent Systems

## Quick Facts
- arXiv ID: 2603.13605  
- Source URL: https://arxiv.org/abs/2603.13605  
- Reference count: 24  
- Primary result: Orla reduces wall-clock time by 38%, mean completion time by 60%, and inference cost by 35% on SWE-bench Lite via dynamic stage mapping, and improves time-to-first-token (TTFT) distribution on DAG-MATH via workflow-level cache management.

## Executive Summary
Orla is a serving library for LLM-based multi-agent systems that separates request execution from workflow-level policy. It introduces three core components: a Stage Mapper that dynamically assigns stages to optimal models/backends, a Workflow Orchestrator that schedules stages and propagates context, and a Memory Manager that controls KV cache lifecycle across workflow boundaries. Evaluated on SWE-bench Lite (2,294 requests) and DAG-MATH (2,894 requests), Orla achieves significant reductions in end-to-end latency and inference cost compared to a single-model baseline. The architecture enables heterogeneous model usage, workflow-aware scheduling, and cross-stage cache reuse, addressing key inefficiencies in serving multi-stage agentic workflows.

## Method Summary
Orla models agent workflows as directed acyclic graphs (DAGs) of stages. At submission, a Stage Mapper translates the workflow DAG into an execution plan, assigning each stage to a specific backend (e.g., Qwen3-4B vs. Qwen3-8B) using strategies such as the lightweight OneBitStageMapper classifier. The Workflow Orchestrator then manages execution: a two-level scheduler first picks a stage queue, then a request within it, optionally using dynamic priority hints from upstream stages; a Context Manager builds downstream prompts from upstream outputs. The Memory Manager observes workflow-level signals (stage completion, backend continuity, memory pressure) to decide whether to preserve or flush the KV cache between stages, avoiding redundant prefill computation. All components communicate with heterogeneous LLM backends (vLLM, SGLang, etc.) via a uniform API.

## Key Results
- Dynamic stage mapping via OneBitStageMapper on SWE-bench Lite routed 956 of 2,294 requests to a smaller Qwen3-4B model and the remainder to Qwen3-8B, reducing wall-clock time by 38%, mean completion time by 60%, and inference cost by 35% compared to a single-model Qwen3-8B vLLM baseline.
- Workflow-level KV cache management on DAG-MATH preserved cache across stages on the same backend, decreasing time-to-first-token (TTFT) relative to per-request flushing and improving the overall latency distribution.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Dynamic stage mapping based on request complexity reduces inference cost and end-to-end latency by routing simpler requests to smaller, cheaper models.
- **Mechanism:** A lightweight classifier (e.g., `OneBitStageMapper`) evaluates each incoming request's perceived complexity and assigns the request's stage to either a "light" or "heavy" model backend. This creates heterogeneous execution within a single workflow definition.
- **Core assumption:** A simple, fast LLM call can reliably distinguish between requests that require sufficient capability from a small model versus those requiring a large model. The overhead of this classification is outweighed by the cost/latency savings of correct routing.
- **Evidence anchors:**  
  [abstract]: "...dynamic stage mapping via OneBitStageMapper routed 956 requests to Qwen3-4B and the rest to Qwen3-8B, reducing wall-clock time by 38%, mean completion time by 60%, and inference cost by 35%..."  
  [section 2.2]: "The second strategy is dynamic routing through the StageMapper interface. Orla includes a OneBitStageMapper that uses a lightweight LLM call to classify each request as 'simple' or 'complex' and routes it to a light or heavy model accordingly."  
  [corpus]: Neighbor papers discuss multi-stage pipelines and resource disaggregation but do not directly evaluate or detail a complexity-based dynamic routing mechanism like Orla's.

### Mechanism 2
- **Claim:** Workflow-aware, two-level scheduling (stage-level then request-level) with dynamic priority hints improves resource utilization and reduces latency for multi-workload environments.
- **Mechanism:** The orchestrator's scheduler first selects which stage's queue to serve next (e.g., based on FCFS or priority). Then, a request scheduler picks the next request within that stage's queue. Priority hints can be dynamically attached to stage requests based on upstream stage outputs, allowing latency-sensitive tasks to jump queues on a shared backend.
- **Core assumption:** The output of an upstream stage (like a classifier) provides a reliable signal for prioritizing downstream stages. The benefit of dynamically prioritizing high-value or urgent workflows outweighs the potential for starvation of lower-priority requests.
- **Evidence anchors:**  
  [abstract]: "...workflow-level cache management, which preserves KV cache across stages on the same backend, decreased time-to-first-token..."  
  [section 2.2]: "Scheduling proceeds in two steps. First, a stage scheduler selects which stage’s queue to serve next... Second, a request scheduler selects the next request within the chosen stage queue... Alternatively, the scheduler may use priority scheduling... These priorities are propagated through scheduling hints attached to downstream stage requests."  
  [section B.2]: Demonstrates setting dynamic priority based on the `classify` stage's output.

### Mechanism 3
- **Claim:** Managing the KV cache lifecycle at the workflow level (across stage boundaries) reduces time-to-first-token (TTFT) by enabling cache reuse for consecutive stages on the same backend, compared to per-request flushing.
- **Mechanism:** The memory manager observes workflow-level signals (stage completion, workflow termination, backend switches). It applies policies (e.g., `preserve on small increments`, `flush at workflow boundaries`) to decide whether to retain the KV cache for a workflow's future stage or evict it to free memory for other workflows. This avoids expensive redundant prefill computation.
- **Core assumption:** Consecutive stages within a workflow frequently share a large, common context prefix. The performance gain from reusing this cached state exceeds the memory pressure cost of retaining it, except under high contention.
- **Evidence anchors:**  
  [abstract]: "...workflow-level cache management, which preserves KV cache across stages on the same backend, decreased time-to-first-token relative to per-request flushing, improving overall latency distribution."  
  [section 2.2]: "Preserving the KV cache across these stages can therefore avoid redundant prefilling and significantly reduce latency... The memory manager coordinates the life-cycle of inference state across workflow boundaries... These decisions rely on workflow-level signals... that are invisible to a request-level backend."  
  [section 4 / Figure 3]: Empirical CDF showing TTFT reduction with workflow-level vs. request-level flushing.

## Foundational Learning
- **Concept: LLM Serving Primitives (Prefill/Decode, KV Cache)**  
  - **Why needed here:** Understanding Orla's optimizations requires knowing the baseline cost model of LLM inference. The "prefill" phase computes the KV cache for the prompt (expensive, latency-sensitive). The "decode" phase generates tokens autoregressively by reusing the KV cache. Orla's memory manager directly manipulates the KV cache to avoid redundant prefills.  
  - **Quick check question:** What is the primary computational difference between processing the initial prompt and generating the first new token in a standard LLM call?
- **Concept: Directed Acyclic Graph (DAG) for Workflow Definition**  
  - **Why needed here:** Orla models agent workflows as DAGs of stages. This formalism defines dependencies (edges) and concurrency. The orchestrator's scheduling and the memory manager's policies depend on this graph structure to know when stages are ready and which share context/backend.  
  - **Quick check question:** In Orla's DAG model, if Stage C depends on both Stage A and Stage B, what must be true before Stage C can be scheduled?
- **Concept: Multi-Model/Multi-Backend Heterogeneity Trade-offs**  
  - **Why needed here:** Orla's core value is managing heterogeneity. An engineer must understand why one might use different models (cost/capability) or backends (SGLang/vLLM/Ollama, GPU/CPU) for different stages, and the coordination complexity this introduces (network, serialization, cache incompatibility).  
  - **Quick check question:** What is a key reason a developer would assign the `classify` stage to a 4B parameter model and the `reply` stage to an 8B model within the same workflow?

## Architecture Onboarding
- **Component map:** Stage Mapper -> Workflow Orchestrator -> Memory Manager -> Backend Interface  
- **Critical path:**  
  1. Developer defines a Workflow DAG and configures Stage properties (backend hint, tools, builder).  
  2. StageMapper produces an ExecutionPlan.  
  3. Orchestrator monitors stage dependencies. When a stage is ready, its request is placed in the specific stage's queue on the assigned backend.  
  4. Scheduler picks a stage queue, then a request from it. The request is dispatched to the Backend.  
  5. Memory Manager intercepts cache-related signals. Before dispatch, it may ensure cache is preserved from a prior stage on the same backend. After completion/workflow end, it may flush.
- **Design tradeoffs:**  
  - Heterogeneity vs. Complexity: Dynamic mapping adds a lightweight inference call and potential misrouting risk versus simplicity of explicit mapping.  
  - Cache Preservation vs. Memory Pressure: Aggressive reuse reduces TTFT but increases memory footprint, risking OOM under high concurrency.  
  - Scheduling Policy Generality vs. Optimality: Simple FCFS/priority is easy but may not minimize makespan or tail latency for complex dynamics.
- **Failure signatures:**  
  - Misrouting: Sudden drop in task accuracy for a subset of requests; check mapper logic and classifier prompts.  
  - Priority Inversion: High-priority workflows not executing while low-priority ones do; inspect scheduler logs and hint propagation.  
  - Cache Thrashing/OOM: Increased TTFT variance or backend OOM errors under load; monitor memory manager's flush decisions and KV hit rates.  
  - Context Propagation Error: Downstream stage prompts missing expected upstream data; debug builder functions.
- **First 3 experiments:**  
  1. Validate Stage Mapping: Run OneBitStageMapper on SWE-bench Lite. Log classification rationale and backend assignments for a mix of requests. Manually verify a sample of "simple" vs. "complex" assignments.  
  2. Test Priority Scheduling: In a multi-workload scenario, configure two workflows with different priority hints. Measure dispatch order and completion times (tail latency) for high vs. low-priority workflows.  
  3. Compare Cache Policies: On SGLang with Qwen3-8B, run DAG-MATH workflows. Compare TTFT CDF for "flush per request" vs. Orla's "preserve across stages + flush at workflow boundary" policy.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How does Orla’s OneBitStageMapper, which classifies requests into two complexity bins, perform when scaling to a larger, more diverse set of models and backends with nuanced capability differences?
- **Basis in paper:** [inferred] The evaluation uses a simple two-model, two-bin router on SWE-bench Lite. The paper notes developers can implement custom mappers but provides no study on routing efficacy beyond this binary case.
- **Why unresolved:** A binary classifier may not capture the continuous spectrum of task difficulty or model capabilities, potentially leading to suboptimal routing in real-world multi-model deployments.
- **What evidence would resolve it:** An empirical study with 5+ models spanning different sizes/architectures on a diverse benchmark (e.g., varying coding, reasoning, tool-use tasks), measuring routing accuracy’s impact on cost-latency trade-offs.

### Open Question 2
- **Question:** What is the comparative effectiveness of different workflow-level KV cache policies (beyond the three implemented) across varying workflow DAG topologies, context reuse patterns, and memory pressure?
- **Basis in paper:** [inferred] The memory manager implements three basic policies (preserve on small increments, flush at boundaries, flush under pressure) and is evaluated only on a linear CoT math dataset. The paper acknowledges cache decisions depend on workflow signals but does not explore policy design space.
- **Why unresolved:** Agentic workflows can have complex branching, loops, and shared subgraphs. Simple heuristics may fail to optimize cache reuse in such structures, especially under multi-workload contention.
- **What evidence would resolve it:** A systematic evaluation of synthetic and real-world workflows with varying DAG complexity, measuring TTFT and throughput under different policy configurations (e.g., predictive reuse based on stage similarity, weighted eviction scores).

### Open Question 3
- **Question:** How does Orla’s separation of request execution from workflow-level policy interact with, or conflict with, optimizations within underlying LLM serving backends (e.g., vLLM’s continuous batching, SGLang’s RadixAttention)?
- **Basis in paper:** [explicit] Orla is designed as a serving layer above existing engines. The paper states these backends optimize request-level execution but lack cross-stage coordination. However, the evaluation runs both Orla and the baseline on the same backend hardware/configuration, isolating Orla’s contributions but not deeply analyzing backend interaction.
- **Why unresolved:** The memory manager’s cache preservation decisions might interfere with backend-level eviction policies (e.g., LRU), and the two-level scheduler could create suboptimal batching if backend schedulers are unaware of workflow priorities.
- **What evidence would resolve it:** Experiments measuring end-to-end throughput/latency with backend-specific optimizations enabled/disabled under Orla’s control, and profiling cache hit rates at both the backend and Orla memory manager levels.

### Open Question 4
- **Question:** To what extent can Orla’s abstractions and backend-agnostic design support emerging agentic patterns beyond DAGs, such as dynamic graph modification, recursive agent loops, or real-time human-in-the-loop interventions?
- **Basis in paper:** [inferred] Orla models workflows as static DAGs (Section 2.1) and assumes stage dependencies are known upfront. The demo and evaluation use fixed DAGs. The paper mentions agent loops but within a predefined stage (via tool calls), not at the DAG structure level.
- **Why unresolved:** Advanced agentic systems may require dynamic re-planning, adding/removing stages, or interruptible workflows. Orla’s current orchestrator and memory manager are built for static DAGs and may not handle dynamic structural changes without restarting workflows or losing context.
- **What evidence would resolve it:** Extending Orla with APIs for dynamic DAG mutation and evaluating on benchmarks requiring adaptive planning (e.g., long-horizon tasks with uncertainty), measuring overhead and correctness of context propagation across structural changes.

## Limitations
- Evaluation restricted to SWE-bench Lite and DAG-MATH with Qwen3-4B/8B; unclear if results generalize to other model families, longer contexts, or diverse agent workflows.
- The `OneBitStageMapper`'s classification logic (prompt design, threshold) is not specified, requiring inference from examples; this obscures reproducibility and limits trust in routing decisions.
- No independent citations or replications found, indicating the work is early-stage with minimal external validation.
