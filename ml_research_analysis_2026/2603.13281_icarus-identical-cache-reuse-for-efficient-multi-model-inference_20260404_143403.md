# ICaRus: Identical Cache Reuse for Efficient Multi Model Inference
## Quick Facts
- arXiv ID: 2603.13281
- Source URL: https://arxiv.org/abs/2603.13281
- Reference count: 40
- Primary result: ICaRus enables exact KV cache sharing across multiple decoder-only models by freezing a shared logical encoder and fine-tuning only task-specific logical decoders, achieving comparable accuracy to conventional fine-tuning while reducing P95 latency by up to 11.1× and improving throughput by up to 3.8× in multi-agent workflows.

## Executive Summary
ICaRus tackles the memory explosion and redundant computation in multi-model inference by decomposing a decoder-only Transformer into a shared logical encoder (frozen) that generates the key-value cache and task-specific logical decoders (fine-tuned) that predict tokens. This design ensures identical KV caches for the same prompt across all models, eliminating redundant storage and prefill recomputation. Lightweight adapters (e.g., LoRA) enable parallel execution of the encoder and decoder during decoding, minimizing latency by batching attention operations over the shared cache. Evaluations on LLaMA and Qwen models across math, coding, and instruction tasks show accuracy on par with conventional fine-tuning. In multi-agent workflows with up to eight models, ICaRus reduces P95 latency by up to 11.1× and improves throughput by up to 3.8×, while preventing memory explosion and cache evictions.

## Method Summary
ICaRus builds on the conceptual split of a decoder-only Transformer: a logical encoder (frozen) that produces KV caches and a logical decoder (fine-tuned) that performs token prediction. During training, only the decoder is adapted (e.g., via LoRA), ensuring that for any input the encoder generates identical KV states across tasks. At inference, a single shared KV cache pool is maintained. For each decoding step, the current token is duplicated: one copy passes through the frozen encoder to generate a new KV pair appended to the cache; the other passes through the encoder plus the task-specific adapter to produce queries. These queries are concatenated, and a single batched attention operation over the shared KV cache yields the decoder's output for token sampling, while the encoder's output is discarded. This parallelization avoids redundant memory accesses, keeping latency comparable to a single model. The approach integrates with serving systems like vLLM and supports cross-model prefix caching, where the first model's prefill populates the cache for subsequent models.

## Key Results
- Achieves accuracy comparable to conventional task-specific fine-tuning across mathematics, coding, and instruction-following tasks on LLaMA and Qwen models.
- In multi-agent workflows with up to eight models, reduces P95 latency by up to 11.1× and improves throughput by up to 3.8× relative to a conventional multi-model system.
- Eliminates redundant KV storage and recomputation, preventing memory explosion and cache evictions.

## Why This Works (Mechanism)
### Mechanism 1: Exact KV Cache Sharing
ICaRus decomposes a decoder-only Transformer into a logical encoder (frozen) that generates KV caches and a logical decoder (fine-tuned) that predicts tokens. By freezing the encoder across all tasks, the KV cache for a given prompt becomes byte-for-byte identical, enabling direct sharing. The core assumption is that the encoder's parameter space suffices for a universally valid KV representation, with task specialization captured by decoder modifications. Evidence: The abstract and Section 3.1 formally define the decomposition (K1:i, V1:i = E(x1:i); xi+1 = D(xi, K1:i, V1:i)). Section 3.2 keeps the encoder frozen during training and shows loss curves overlapping with conventional fine-tuning. Break condition: If a task requires encoder modifications (e.g., fundamental input representation shifts), the decomposition fails.

### Mechanism 2: Parallel Encoder-Decoder Execution
To avoid the 2× latency overhead of sequential encoder-decoder passes, ICaRus uses lightweight adapters (e.g., LoRA) in the decoder, allowing shared parameters to be loaded once. The current token is duplicated: one copy goes to the frozen encoder to generate a new KV pair; the other goes to the decoder (base + adapter) to produce queries. These queries are concatenated along the head dimension, enabling a single batched attention operation over the shared KV cache. This parallelizes the two logical streams, hiding memory access costs. Core assumption: Adapter overhead is negligible and hardware can handle concurrent memory transactions. Evidence: Section 3.3 describes parallelization and concatenated queries; Table 1 shows decode complexity O(2M+2Lt) but claims memory access dominates, achieving latency comparable to baseline O(M+Lt). Break condition: Large adapters or hardware lacking parallel memory streams erodes benefits.

### Mechanism 3: Shared KV Cache for Memory and Prefill Savings
Conventional multi-model systems allocate separate KV caches, leading to O(N·Lt) memory and redundant prefill computation for identical prompts. ICaRus uses a single shared pool of size O(Lt), preventing memory explosion and evictions. In agentic workflows, the first model's prefill populates the cache; subsequent models skip prefill entirely, loading the existing cache. The improvement scales with number of models (N) and prefix overlap. Evidence: Abstract and Section 2 motivate the problem; Section 4.3 shows P95 latency reductions (e.g., 5.1× for 4 models, up to 7.4×) and prevents KV explosion. Break condition: If tasks require different KV representations for the same input, sharing fails; minimal prefix overlap reduces benefits.

## Architecture Onboarding
Component map:  
Input Token -> Duplicate -> {Base Model (Frozen) -> Update Shared KV Cache} & {Base Model (Frozen) + Task-Specific Adapter -> Generate Queries} -> Concatenated Queries -> Batched Attention over Shared KV Cache -> Output Token

Critical path (Decode Step):
1. Orchestrator sends a decoding request (with current token) to a specific task-adapter.
2. System duplicates the current token tensor.
3. Path A (Encoder): First copy passed through frozen base model -> produces new KV pair, appends to shared cache.
4. Path B (Decoder): Second copy passed through base model + task adapter -> produces queries for next token.
5. Batched Attention: Queries from both paths are concatenated, attending to the entire shared KV cache in a single operation.
6. Output from Path B is used for token sampling; Path A's output is discarded.

Design tradeoffs:
- Frozen Encoder vs. Capacity: Maximizes cache sharing and minimizes memory, but restricts all models to a single input representation. May limit performance on tasks requiring drastic input transformation.
- Adapter Placement: Adapters are placed in the decoder path (query/output projections). This enables parameter sharing for the bulk of the model (FFN, key/value projections) but means the adapter must work with the frozen encoder's representations.
- Parallelism vs. Complexity: The concatenated query trick is elegant but requires careful tensor reshaping in the attention kernel. It trades implementation complexity for latency reduction.

Failure signatures:
- Accuracy drop: Per-task performance significantly worse than full fine-tuning suggests the frozen encoder's representations are incompatible with the target task's decoder needs.
- Cache Coherence Error: If the system ever loads a KV cache generated by a different base model (e.g., due to a bug in the cache key), the decoder will make nonsensical predictions.
- No Latency Improvement: If the adapter size is too large or the hardware cannot parallelize the two logical streams, P95 latency will be worse than baseline.

First 3 experiments:
1. Loss Convergence Validation: Train both a baseline (full fine-tuning) and ICaRus (encoder-frozen) on a small dataset (e.g., MetaMathQA). Plot training loss curves to verify ICaRus converges to a comparable loss.
2. Single-Task Accuracy Benchmark: Evaluate the ICaRus-tuned model for a single task (e.g., math) against the base model and a conventionally fine-tuned model on the task's test set (e.g., GSM8K).
3. Multi-Memory Stress Test: Set up a serving environment with vLLM, run a workflow that invokes 2+ task-specific adapters on the same prompt in quick succession. Monitor GPU memory usage of the KV cache pool; it should grow by one sequence length, not by N. Also measure the time for the second model's prefill—it should be near-zero if prefix caching works.

## Open Questions the Paper Calls Out
- Does ICaRus maintain its efficiency gains when scaling to agent systems with more than eight models?
- Can ICaRus be applied to tasks requiring encoder-side updates (e.g., retrieval-augmented generation) without harming performance?
- Can ICaRus share KV caches across heterogeneous base models (e.g., LLaMA and Qwen) while preserving efficiency?
- How does storing many LoRA adapters affect memory consumption and maximum sustainable agent count in large multi-agent deployments?

## Limitations
- Generalization scope unclear: The frozen encoder assumption holds for math/coding/instruction tasks, but may fail for domains requiring fundamental input representation shifts (e.g., multimodal or structured data).
- Hardware dependency: Latency gains assume GPU memory systems can hide two logical streams' bandwidth; this may not hold on memory-constrained or non-NVIDIA hardware.
- Adapter configuration underspecified: Optimal LoRA rank, target modules, and placement within the decoder path are not detailed, leaving a critical design space unexplored.

## Confidence
- Accuracy parity with full fine-tuning: Medium
- Memory reduction via KV sharing: High
- Latency/throughput gains in multi-model settings: Medium
