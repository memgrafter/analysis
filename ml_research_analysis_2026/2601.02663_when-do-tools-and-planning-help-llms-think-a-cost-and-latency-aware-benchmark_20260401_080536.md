# When Do Tools and Planning Help LLMs Think? A Cost- and Latency-Aware Benchmark

## Quick Facts
- **arXiv ID**: 2601.02663  
- **Source URL**: https://arxiv.org/abs/2601.02663  
- **Reference Count**: 37  
- **Primary Result**: Tool augmentation improves accuracy on structured QA (Event-QA) by ~20% but increases latency ~40×; one-shot prompting with a smaller model (GPT-4o-mini) achieves the best accuracy-latency trade-off on persuasion (CMV) without planning.

## Executive Summary
This study evaluates the practical utility of inference-time planning and tool use in large language models (LLMs) under realistic cost and latency constraints. It compares a plan-execute-replan agent (implemented via LangGraph) against a one-shot baseline on two diverse tasks: Event-QA (structured question answering over graph knowledge) and CMV (persuasive response generation). Results show that tools significantly boost accuracy on Event-QA but incur massive latency overhead. On CMV, simpler one-shot prompting with a smaller model yields superior performance at minimal cost. The work emphasizes that the benefits of tool orchestration are highly task-dependent and must be weighed against operational constraints.

## Method Summary
The authors implement two pipelines using LangChain/LangGraph: a NoPlanning agent (single LLM call) and a 3‑stage planning agent (Planner → Executor → Replanner/Answerer). Evaluation uses 60 examples per dataset, split into three groups for sequential tuning and holdout testing. Tools include DBpedia SPARQL, entity lookup, schema explorer, Wikipedia search (Event-QA), and Tavily web search (CMV). Models tested are GPT‑4o and GPT‑4o‑mini. Metrics are accuracy (exact match for Event-QA; ROUGE‑1 ≥0.27 for CMV) and average end‑to‑end latency, with token counts used to estimate cost. Final results are averaged over the tuned development split and the holdout test split.

## Key Results
- On Event‑QA, tool augmentation raises GPT‑4o accuracy from 47.5% to 67.5% but increases average latency from ~8 s to ~317 s.
- On CMV, one‑shot prompting with GPT‑4o‑mini achieves 75% accuracy at ~6 s latency; planning with GPT‑4o increases latency without consistent accuracy gains.
- Complex tool orchestration leads to failure modes (e.g., malformed queries, excessive replanning), especially for smaller models like GPT‑4o‑mini.

## Why This Works (Mechanism)
Tool use benefits tasks that require precise, up‑to‑date, or structured external knowledge (e.g., graph QA) by offloading retrieval to specialized APIs. Planning adds value only when multi‑step reasoning is genuinely needed; otherwise, it introduces unnecessary overhead and failure points. For tasks like persuasive writing, the model’s internal knowledge suffices, making one‑shot prompting more efficient. The stark latency differences arise because each planning iteration triggers additional LLM calls and tool invocations, compounding cost and delay.

## Foundational Learning
- **Tool‑augmented LLMs**: Why needed: To access dynamic or domain‑specific data beyond training. Quick check: Does the task require factual lookups or structured queries?  
- **Planning agents**: Why needed: For decomposing complex problems into executable steps. Quick check: Can the task be solved in a single reasoning pass?  
- **Cost‑latency trade‑offs**: Why needed: Real‑world deployments must balance performance with operational budget. Quick check: Is low‑latency response critical?  
- **Graph‑based QA**: Why needed: Event‑QA relies on DBpedia’s graph structure. Quick check: Is the knowledge inherently relational?  
- **Persuasion generation**: Why needed: CMV tests argumentative writing, not factual accuracy. Quick check: Is the task focused on style/coherence over exact facts?  
- **Sequential tuning**: Why needed: Adapting prompts and tool parameters per split mimics real‑world iterative development. Quick check: Does the benchmark allow incremental optimization?

## Architecture Onboarding
Component map: Planner → Executor → Replanner/Answerer (or one‑shot baseline).  
Critical path: Plan generation → tool execution → sufficiency evaluation → possible replanning → final answer.  
Design tradeoffs: More tool calls increase accuracy potential but also latency, cost, and failure surface. Simpler prompts reduce overhead but may lack precision.  
Failure signatures: Malformed SPARQL queries, API timeouts, infinite replanning loops, redundant evidence retrieval—especially prevalent with smaller models.  
First three experiments:  
1. Run Event‑QA with no tools vs. full toolset to isolate knowledge‑access impact.  
2. Compare GPT‑4o vs. GPT‑4o‑mini on both tasks to gauge model‑size sensitivity.  
3. Measure distribution of replanning iterations and total tool calls per example to diagnose latency spikes.

## Limitations
- Missing final tuned prompt templates and system messages for all stages prevents exact reproduction.  
- Tool configuration details (search snippet count, SPARQL timeouts, retry logic, caching) are undisclosed, affecting latency and accuracy measurements.  
- Failure mode analysis is anecdotal; no systematic breakdown of error types or their correlation with model size is provided.

## Confidence
- Tool utility on Event‑QA (accuracy gain): **Medium** (benchmark clear but tuning opaque).  
- Planning inefficiency on CMV (high latency, minimal gain): **Medium** (latency reliable, but prompt/config dependence unquantified).  
- Smaller models’ tool orchestration breakdowns: **Low** (observational, no statistical error analysis).

## Next Checks
1. Request authors’ final prompts, system messages, and exact tool parameters (e.g., Tavily snippet limit, SPARQL timeout).  
2. Audit provided tool call logs to compute error rates (malformed queries, API failures) and replanning iteration distributions.
