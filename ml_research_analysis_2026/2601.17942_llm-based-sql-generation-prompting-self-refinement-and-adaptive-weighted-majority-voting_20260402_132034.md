# LLM-Based SQL Generation: Prompting, Self-Refinement, and Adaptive Weighted Majority Voting

## Quick Facts
- **arXiv ID:** 2601.17942
- **Source URL:** https://arxiv.org/abs/2601.17942
- **Reference count:** 40
- **Primary result:** SSEV achieves 85.5% (Spider 1.0-Dev), 86.4% (Spider 1.0-Test), and 66.3% (BIRD-Dev) execution accuracy; ReCAPAgent-SQL reaches 31% on Spider 2.0-lite with GPT-4.1 (25% absolute gain).

## Executive Summary
This paper tackles the challenge of generating accurate SQL from natural language queries using large language models (LLMs). The authors propose a two-phase approach: first, a Single-Agent Self-Refinement with Ensemble Voting (SSEV) pipeline that integrates two-round prompting, execution-guided self-refinement, and adaptive Weighted Majority Voting (WMA/RWMA) without ground‑truth data. Second, building on SSEV insights, they introduce the multi‑agent ReCAPAgent‑SQL framework, which decomposes the task into specialized agents (Planner, Critic, SchemaLinker, SelfRefiner, Validator) for iterative plan‑execute‑critique‑refine cycles. Evaluations on standard benchmarks show that SSEV attains strong execution accuracy on Spider 1.0 and BIRD, while ReCAPAgent‑SQL on Spider 2.0‑lite yields a 25% absolute improvement over the baseline. Core innovations include schema pruning via PreSQL, error‑driven self‑refinement, and an adaptive voting mechanism that dynamically weights LLM experts.

## Method Summary
The SSEV pipeline processes each query through several stages. Initially, multiple LLMs generate preliminary SQL (PreSQL) using the full database schema. The PreSQL outputs are parsed to extract referenced tables and columns, producing a pruned schema that removes irrelevant elements. A second‑round generation (PostSQL) uses this reduced context. All resulting candidates (PreSQL and PostSQL) are executed; those that fail due to syntax errors or empty results are refined iteratively (up to M times) by re‑prompting with the original query and the execution error. Finally, the Weighted Majority Algorithm (WMA) or its randomized variant (RWMA) aggregates the valid outputs. Each LLM starts with weight 1.0; after a mistake, its weight is multiplied by (1−ε), enabling adaptive selection of more reliable experts without ground truth.

ReCAPAgent‑SQL extends these ideas into a multi‑agent architecture. It begins with external retrieval for knowledge and syntax, then a Planner creates a JSON‑formatted plan. A Critic reviews the plan, and an Action agent executes predicted steps (SQL or Bash). Upon failure, the system invokes a SelfRefinerAgent or SchemaLinkerAgent to correct errors. A Validator checks whether the final result satisfies the query. The loop repeats until termination or a step limit. Final SQL selection again uses WMA/RWMA over multiple runs. Both systems emphasize robustness through execution‑driven feedback and adaptive ensembling.

## Key Results
- SSEV achieves 85.5% execution accuracy on Spider 1.0‑Dev, 86.4% on Spider 1.0‑Test, and 66.3% on BIRD‑Dev.
- ReCAPAgent‑SQL with GPT‑4.1 reaches 31% execution accuracy on Spider 2.0‑lite, a 25% absolute improvement over the 6% baseline.
- WMA consistently outperforms naïve voting and RWMA, securing the highest overall accuracy (31%) in the ReCAPAgent‑SQL evaluation.

## Why This Works (Mechanism)

### Mechanism 1: Schema Linking via PreSQL Pruning
- **Claim:** Schema linking via PreSQL output pruning reduces noise and focuses generation on relevant database entities.
- **Mechanism:** The system first generates preliminary SQL (PreSQL) with the full schema. It then parses this output to extract referenced tables and columns (e.g., via regex), constructing a pruned schema for the second‑round (PostSQL) prompt. This reduces token noise and guides the LLM to the minimal relevant context.
- **Core assumption:** The initial PreSQL generation, even if imperfect, captures enough correct schema references to identify the core relevant subset.
- **Evidence anchors:**
  - [Section 3.1.1] details the PreSQL‑based schema linking process.
  - [Table 6] shows modest but consistent gains from adding schema linking (Stage 2 vs. Stage 1) across models.
  - [corpus] indicates related schema‑linking work (e.g., Solid‑SQL, X‑SQL), confirming its recognized importance.
- **Break condition:** PreSQL may completely miss critical tables/columns due to initial errors, leading to an over‑pruned schema and incomplete reasoning.

### Mechanism 2: Execution‑Guided Self‑Refinement
- **Claim:** Execution‑guided self‑refinement iteratively corrects SQL errors using runtime feedback, improving robustness without external supervision.
- **Mechanism:** When a generated SQL fails (syntax error or empty result), the system re‑prompts the LLM with the original query, error message, and schema context for up to *N* iterations. Failed queries are retained for final voting.
- **Core assumption:** The LLM can correctly interpret database error messages and apply appropriate targeted fixes (e.g., type mismatches, missing joins).
- **Evidence anchors:**
  - [Section 3.1.3] defines the loop structure and termination criteria.
  - [Table 7] shows particularly strong gains on BIRD Dev (e.g., +2.28% for Qwen2.5‑coder‑32B), indicating effectiveness in complex, real‑world scenarios.
  - [corpus] lists ReFoRCE as a related self‑refinement agent, supporting the mechanism’s validity.
- **Break condition:** Persistent or opaque errors (e.g., "No matching signature") that the LLM cannot diagnose may cause refinement loops to terminate without success, wasting iterations.

### Mechanism 3: Adaptive Weighted Majority Voting
- **Claim:** The Weighted Majority Algorithm (WMA) dynamically prioritizes more reliable LLM experts, achieving near‑best‑expert ensemble performance without ground‑truth data at inference.
- **Mechanism:** Each expert *i* starts with weight *wᵢ*=1.0. After each query, experts whose SQL fails execution (or is incorrect) have their weight multiplied by (1−ε). The final SQL is selected by summing weights of supporting experts (WMA) or by sampling proportionally (RWMA). Updates are constant‑time, enabling practical deployment.
- **Core assumption:** An expert's historical accuracy is predictive of its future performance on similar queries (stationarity assumption).
- **Evidence anchors:**
  - [Section 3.1.2] formally defines WMA/RWMA and mistake bounds.
  - [Figures 15–20] show rapid weight convergence toward stronger models (Gemini‑2.5‑Pro, GPT‑4o) and lower regret compared to RWMA/Naïve.
  - [Table 9] confirms Stage 6 (voting+refinement+linking) yields net gains over Stage 1.
- **Break condition:** Rapid concept drift (e.g., query difficulty distribution shifts) or highly correlated expert failures can cause weight updates to misrepresent true expertise, leading to suboptimal selection.

## Foundational Learning
- **In‑context learning (few‑shot prompting):** Forms the basis of PreSQL generation; the system retrieves similar question‑SQL pairs to condition the LLM without fine‑tuning. *Quick check:* How does the similarity‑based retrieval of few‑shot examples affect the diversity and correctness of the initial PreSQL?
- **Schema linking in Text‑to‑SQL:** Bridges natural language tokens to database tables/columns; the dynamic pruning based on PreSQL is central to reducing context length and noise. *Quick check:* What are the failure modes when schema linking incorrectly excludes a table that is actually required?
- **Online ensemble learning (Weighted Majority Algorithm):** Provides a theoretically grounded, adaptive mechanism to combine multiple LLM outputs without requiring ground truth during inference; updates weights based on execution feedback. *Quick check:* How does the choice of the penalty factor ε affect the trade‑off between responsiveness and stability in weight updates?
- **Multi‑agent reasoning (ReAct pattern):** ReCAPAgent‑SQL decomposes the complex Text‑to‑SQL task into specialized roles (Planner, Critic, Validator, etc.) enabling iterative refinement and robust error handling for enterprise workflows. *Quick check:* How does agent specialization impact overall latency compared to a single‑agent approach?

## Architecture Onboarding
- **Component map:**  
  SSEV Pipeline: Input → PreSQL Generation (multiple LLMs) → Schema Linking (parse & prune) → PostSQL Generation (same LLMs) → Execution‑Guided Self‑Refinement (iterative) → Voting (WMA/RWMA) → Output.  
  ReCAPAgent‑SQL: Input → External Knowledge/Syntax Retrievers → PlannerAgent (plan generation) → Plan Critique → Action Agent (predict/execute SQL/Bash) → Upon failure: SelfRefinerAgent or SchemaLinkerAgent → ValidatorAgent → Loop until termination. Final SQL selected via WMA/RWMA across multiple probable outputs.
- **Critical path:** The shortest successful execution path: PlannerAgent plan → ActionAgent SQL prediction → Database execution → ValidatorAgent confirmation → Terminate.
- **Design tradeoffs:**  
  *Multi‑agent overhead vs. robustness:* ReCAPAgent‑SQL adds prompt engineering and loop management compared to SSEV but gains in handling ambiguous schemas and complex enterprise queries.  
  *Voting determinism vs. exploration:* WMA converges faster to top experts; RWMA maintains diversity, which can help on hard queries.  
  *Refinement iterations vs. cost:* More self‑refinement steps improve robustness but increase LLM calls and latency.
- **Failure signatures:**  
  Repeated execution errors (syntax or "TableNotFound") after several refinements; SchemaLinkerAgent returning minimal/irrelevant schema; PlanCritiqueAgent oscillating without convergence; WMA weights collapsing to a single expert early.
- **First 3 experiments:**  
  1. **Baseline LLM performance:** Evaluate each individual LLM (e.g., GPT‑4o, Gemini‑2.5) on the target benchmark with 9‑shot prompting to establish expert strength hierarchy.  
  2. **SSEV ablation study:** Run six incremental stages (Base → +SL → +SR → +SL+SR → +Vote+SR → +Vote+SR+SL+SR+Vote) to isolate contributions of schema linking, self‑refinement, and voting. Compare Stage 6.1 (WMA) vs. Stage 1.  
  3. **ReCAPAgent‑SQL vs. baseline agent:** On Spider 2.0‑lite, compare (a) official Spider‑Agent with Grok‑3‑beta, (b) ReCAPAgent‑SQL with Grok‑3‑beta, (c) ReCAPAgent‑SQL with GPT‑4.1 (with/without WMA). Measure absolute gain and analyze failure modes.

## Limitations
- **Unspecified details:** Exact few‑shot selection, prompt templates, hyperparameters (N, M, ε), and ReCAPAgent‑SQL agent prompts/termination conditions are not fully described, blocking faithful reproduction.
- **Environment access:** Spider 2.0‑lite requires cloud setup (BigQuery/Snowflake) whose configuration is not provided.
- **Potential break conditions:** Schema linking may over‑prune if PreSQL misses key tables; self‑refinement may degrade if errors are opaque; WMA may collapse diversity under rapid distribution shifts.
