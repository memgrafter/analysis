# Resolving the Robustness-Precision Trade-off in Financial RAG through Hybrid Document-Routed Retrieval

## Quick Facts
- **arXiv ID**: 2603.26815
- **Source URL**: https://arxiv.org/abs/2603.26815
- **Reference count**: 6
- **Primary result**: HDRR achieves top performance on FinFinder (avg score 7.54, failure rate 6.4%, correctness 67.7%, perfect answer 20.1%) by combining document routing with scoped chunk retrieval.

## Executive Summary
Financial question-answering over homogeneous regulatory filings (e.g., 10-Ks) faces a robustness-precision trade-off: chunk-based retrieval (CBR) is precise but prone to cross-document confusion, while semantic file routing (SFR) avoids this but dilutes context by using entire documents. This paper proposes Hybrid Document-Routed Retrieval (HDRR), which first uses an LLM to extract company ticker and year metadata to route to the correct document, then performs targeted chunk retrieval only within that document. A fallback to full-corpus CBR ensures robustness if routing fails. On the FinFinder benchmark of 1,500 queries over S&P 500 10-Ks, HDRR significantly outperforms both CBR and SFR across all metrics, effectively resolving the trade-off for single-entity financial queries.

## Method Summary
The study compares three retrieval-augmented generation (RAG) pipelines on the FinFinder dataset of financial queries over S&P 500 10-K filings. **Chunk-Based Retrieval (CBR)** splits documents into overlapping chunks, dual-indexes them with FAISS (embeddings) and FTS5 (keyword), fuses results, reranks, and generates answers. **Semantic File Routing (SFR)** uses an LLM with structured output to extract ticker/year from the query, maps these to a specific filing, and passes the entire document as context to the generator. **Hybrid Document-Routed Retrieval (HDRR)** combines both: it first performs SFR-style document routing, then executes scoped CBR (chunk retrieval restricted to the routed document(s)), and only falls back to unrestricted CBR if no documents are resolved. Evaluation uses a GPT-4.1 judge scoring answers 1–10, computing average score, failure rate (score=1), correctness (score≥8), and perfect answer (score=10) rates.

## Key Results
- Average score: 7.54 (+25.2% over CBR, +16.9% over SFR)
- Failure rate: 6.4% (-71.6% relative to CBR)
- Correctness rate: 67.7% (+18.7 pp over CBR)
- Perfect answer rate: 20.1% (+6.3 pp over CBR, +11.6 pp over SFR)
- Consistent improvement across all five experimental query groups.

## Why This Works (Mechanism)
### Mechanism 1: Eliminates Cross-Document Chunk Confusion
- **Claim**: HDRR avoids catastrophic retrieval of chunks from wrong companies by ensuring all retrieved chunks originate from the correctly routed document.
- **Mechanism**: Stage 1 uses an LLM to extract ticker/year metadata from the query, mapping it deterministically to a file path. Stage 2's chunk retrieval is scoped exclusively to chunks from that document.
- **Core assumption**: The corpus exhibits *naming regularity*—a deterministic, extractable mapping (ticker+year → file path) exists and can be reliably extracted.
- **Evidence anchors**: Abstract states HDRR "eliminates cross-document confusion"; Section 7.1.1 attributes CBR's high failure (22.5%) to such confusion; FinFinder's S&P 500 10-Ks have standardized naming.
- **Break condition**: If routing fails (e.g., ticker mismatch due to rebranding) and fallback to full-corpus CBR occurs, cross-document confusion can reappear.

### Mechanism 2: Preserves Precision via Scoped Retrieval
- **Claim**: HDRR achieves higher precision than SFR by avoiding context dilution from full-document input.
- **Mechanism**: After routing, HDRR retrieves only the top 5–10 relevant chunks *within* the routed document, rather than passing the entire 50K–200K token filing to the generator.
- **Core assumption**: The answer-relevant information for a query is contained within a small, retrievable subset of the target document.
- **Evidence anchors**: Abstract notes SFR "sacrifices the precision of targeted chunk retrieval"; Section 7.1.2 links SFR's context dilution to reduced precision; Section 4.3 confirms HDRR sends only reranked chunks; FinFinder evidence is often scattered, necessitating scoped retrieval.
- **Break condition**: If relevant information is highly fragmented across many low-scoring fragments, even scoped retrieval may miss key context.

### Mechanism 3: Fallback Ensures Robustness
- **Claim**: HDRR's fallback to full-corpus CBR when routing fails provides robustness, ensuring it never underperforms CBR.
- **Mechanism**: If document resolution yields no valid files (e.g., ticker/year not found), HDRR degrades gracefully to standard chunk-based retrieval over the entire corpus.
- **Core assumption**: Routing succeeds frequently enough that fallback is rarely needed, but when triggered it prevents total failure.
- **Evidence anchors**: Section 3.2.3 defines the fallback; Section 7.3.1 shows HDRR's lower failure rate (6.4% vs. SFR's 10.3%) partly due to fallback mitigating ticker mismatches; FinFinder includes ambiguous queries testing fallback.
- **Break condition**: If routing failures become frequent (e.g., poor naming regularity), HDRR will often fall back to CBR, losing its precision advantage and converging to CBR's higher failure rate.

## Foundational Learning
- **Concept: Chunk-Based Retrieval (CBR)**  
  - *Why needed here*: Baseline paradigm whose failure mode (cross-document confusion) HDRR solves. Understanding chunking, embedding similarity, and retrieval fusion is key.
  - *Quick check*: Why does splitting homogeneous 10-Ks into chunks cause "cross-document chunk confusion"?

- **Concept: LLM Structured Output for Routing**  
  - *Why needed here*: Engine of first-stage document filter. Converts unstructured query into structured metadata (ticker/year) deterministically.
  - *Quick check*: How does forcing JSON output from an LLM enable reliable document routing compared to free-text parsing?

- **Concept: Retrieval-Precision vs. Robustness Trade-off**  
  - *Why needed here*: The core problem HDRR solves. Precision = getting *right* chunks; Robustness = avoiding *catastrophic* failures (wrong document). CBR optimizes precision but fails robustly; SFR optimizes robustness but dilutes precision.
  - *Quick check*: Why does providing a full document (SFR) increase robustness but decrease precision compared to providing a few relevant chunks (CBR)?

## Architecture Onboarding
- **Component map**:
  Routing LLM (GPT-4.1) -> File Resolver -> [if success: Scoped Retriever -> Reranker (Jina v2) -> Generator LLM] / [if fail: Unscoped CBR (Retriever -> Reranker -> Generator)]

- **Critical path**: Query -> Routing LLM (extract tickers/years) -> File Resolver (map to doc_ids) -> Conditional branch: Scoped retrieval (if doc_ids found) or Unscoped CBR (if none) -> Reranker -> Generator -> Answer.

- **Design tradeoffs**:
  - Cost: Adds 1 LLM routing call vs. CBR; saves 50K–200K tokens/gen vs. SFR. Net ~CBR cost, ~SFR precision.
  - Complexity: Requires corpus with predictable file organization (naming regularity). No extra indexing cost beyond CBR.
  - Latency: Routing call adds ~200–500ms; scoped searches are faster due to smaller search space.

- **Failure signatures**:
  1. Ticker/year mismatch: LLM extracts wrong ticker (e.g., post-rebranding). Fallback triggers (HDRR) or complete failure (SFR).
  2. Inherent unanswerability: No document contains answer (e.g., future projections). All systems fail.
  3. Routed doc but poor chunk relevance: Relevant info fragmented; top-k chunks miss key passages.

- **First 3 experiments**:
  1. Routing Accuracy Test: On held-out set, measure % queries where extracted (ticker,year) exactly matches ground-truth document. Target >95%.
  2. Scoped vs. Unscoped Retrieval: For correctly routed queries, compare HDRR's top-k chunk relevance (F1 vs. gold evidence) against CBR's. Expect >90% of gold evidence in HDRR's pool vs. ~60% for CBR.
  3. Fallback Stress Test: Inject ambiguous/missing company references. Verify HDRR's failure rate ≤ CBR's, confirming graceful degradation.

## Open Questions the Paper Calls Out
1. **How can document routing be made robust to ticker symbol mismatches?**  
   *Basis*: Paper identifies ticker mismatches as residual failure and suggests lookup tables or knowledge bases (Section 8.3).  
   *Why unresolved*: Current routing relies on exact ticker-year extraction; fails when queries reference non-canonical names.  
   *What evidence*: Systematic error analysis on corpus with known ticker changes, comparing HDRR with enhanced routing (lookup/fuzzy matching).

2. **How does HDRR perform on comparative multi-company queries?**  
   *Basis*: Paper proposes evaluating on "comparative and multi-document queries" as future work (Section 8.3).  
   *Why unresolved*: FinFinder is predominantly single-entity; multi-entity queries may route to multiple documents, altering dynamics.  
   *What evidence*: New evaluation suite of multi-company financial queries, measuring HDRR's multi-document routing vs. CBR/SFR.

3. **To what extent do benefits generalize beyond finance?**  
   *Basis*: Paper discusses generalizability to legal, medical, technical docs (Section 7.6) but notes "unique routing challenges."  
   *Why unresolved*: Core assumptions (naming regularity, structural homogeneity) may differ; domain-specific metadata schemas needed.  
   *What evidence*: Replication studies in 2+ non-financial domains with standardized corpora, measuring the same trade-off.

4. **Can adaptive routing confidence thresholds reduce residual failures?**  
   *Basis*: Inferred—HDRR falls back only when routing yields zero documents (Algorithm 2), ignoring low-confidence routes that may be wrong.  
   *Why unresolved*: Binary success/failure may be too coarse; low-confidence routing could cause scoped retrieval in wrong doc.  
   *What evidence*: Implement confidence scoring (LLM certainty or logprobs) and evaluate hysteresis strategies (fallback if confidence low) on error subset.

5. **What is minimal architectural overhead—can routing and query rewriting be merged?**  
   *Basis*: Paper notes HDRR adds one API call vs. CBR and suggests combining routing with query rewriting for cost optimization (Section 8.3).  
   *Why unresolved*: Separating structured (routing) and free-text (rewriting) outputs ensures reliability; merging risks degradation.  
   *What evidence*: Prompt engineering study with single LLM call outputting both, measuring routing accuracy, rewrite quality, and end-to-end performance vs. two-call baseline.

## Limitations
- **Reproduction blocked**: Exact LLM prompts (query rewriting, structured routing) and FinFinder group splits are undisclosed, preventing faithful replication.
- **Corpus dependence**: Claims hinge on "naming regularity" (Def. 1); performance may drop on corpora without deterministic file naming.
- **Reranker ambiguity**: Jina v2 implementation details (batch size, sequence length, scoring normalization) are unspecified, potentially affecting chunk selection.

## Confidence
- **High**: Performance on FinFinder; Mechanism 1 (eliminating cross-document confusion) for this corpus; Mechanism 3 (fallback robustness) due to direct failure rate analysis.
- **Medium**: Mechanism 2 (precision via scoped retrieval)—assumes answer-relevant chunks are retrievable within top-k, not verified for all query types.
- **Low**: Generalizability beyond standardized financial filings (not tested).

## Next Checks
1. **Naming regularity stress test**: Apply HDRR to a non-standardized financial corpus (e.g., foreign filings, mixed report types). Expect performance drop if deterministic mapping fails.
2. **Information scatter audit**: On FinFinder gold evidence, compute fraction of answer spans covered by a single chunk vs. distributed across >3 chunks. Validates scoped retrieval necessity.
3. **Fallback isolation experiment**: Run HDRR with routing artificially disabled (forced CBR fallback) versus original. Measure change in failure rate to quantify fallback's actual contribution.
