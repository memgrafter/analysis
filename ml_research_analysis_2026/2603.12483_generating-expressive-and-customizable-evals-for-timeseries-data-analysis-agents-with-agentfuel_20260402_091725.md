# Generating Expressive and Customizable Evals for Timeseries Data Analysis Agents with AgentFuel

## Quick Facts
- arXiv ID: 2603.12483
- Source URL: https://arxiv.org/abs/2603.12483
- Reference count: 40
- Primary result: AgentFuel exposes a severe performance gap in time-series analysis agents: stateful queries (34%) and incident-specific (10%) lag far behind stateless (73%) across six agents.

## Executive Summary
Current benchmarks fail to evaluate conversational data analysis agents in time-series domains because they lack domain-specific datasets and stateful, incident-aware query types. AgentFuel addresses this gap with an AI‑assisted framework that lets domain experts generate synthetic time‑series data and aligned query‑answer pairs covering stateless, stateful, and incident‑specific analytics. Evaluations on e‑commerce, IoT, and telecom benchmarks with six agents (e.g., Databricks Genie, PandasAI) reveal dramatic performance drops: stateful accuracy falls from 73% to 34%, and incident‑specific to just 10%. The telecom benchmark, featuring multi‑table and incident queries, is the hardest (21% average). Preliminary experiments show that AgentFuel evals can drive prompt optimization (GEPA), boosting incident query accuracy by 17%. The benchmarks are publicly released, providing a tool to measure and improve agent capabilities in operational settings.

## Method Summary
AgentFuel is a modular, AI‑assisted framework for generating time‑series benchmarks tailored to specific domains. Domain experts provide high‑level descriptions of data schemas, entities, and typical incident patterns. An LLM assistant converts these inputs into structured specifications: entity models, state‑transition diagrams (with dwell times), and per‑state measurement models. The system then selects and blends exemplar behavioral patterns from a library, partitioning a global timeline into epochs and combining exemplars with configurable weights. A pattern‑injection library introduces domain‑relevant incidents—such as KPI degradation or cascading failures—into the synthetic timeline. Queries are generated programmatically via a template engine that maps structured query definitions (entity filters, event filters, aggregation functions) to natural language variants. The dataset and QA pairs are exported to the target agent’s backend for evaluation, with responses graded manually or via an LLM‑as‑judge. This pipeline ensures tight alignment between data content and query semantics, so ground‑truth answers depend uniquely on the injected patterns, preventing false positives from generic heuristics.

## Key Results
- Stateless query accuracy: 73%; stateful: 34%; incident‑specific: 10%.
- Telecom domain benchmark (multi‑table, incident queries) average accuracy: 21%.
- GEPA prompt optimization based on AgentFuel evaluations improves incident query accuracy by 17%.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim**: AgentFuel exposes a previously hidden performance gap in time‑series data agents by generating benchmarks aligned with domain‑specific stateful and incident‑aware query patterns.
- **Mechanism**: The framework creates synthetic datasets via controlled pattern injection (e.g., KPI degradation, cascading failures) and couples them with corresponding query templates that require temporal reasoning and anomaly detection. This forces agents to move beyond simple aggregations to tasks involving state tracking and incident‑specific analysis.
- **Core assumption**: Existing generic benchmarks (Spider2‑Snow, BIRD, Beaver) primarily contain stateless queries (92–96%), failing to test capabilities needed in operational domains like IoT, telecom, and observability.
- **Evidence anchors**:
  - [abstract] "existing benchmarks lack domain‑specific datasets and stateful, incident‑aware query types."
  - [section 2.3] Classification of benchmark queries showing >92% stateless, and identification of "dataset expressivity" and "analytic queries gap."
  - [corpus] Evidence is indirect; neighboring papers focus on general LLM evaluation or time‑series retrieval, not domain‑specific agent eval gaps. *Assumption: The gap is real and impactful based on the paper's own evaluation results.*
- **Break condition**: If future general benchmarks integrate stateful and incident patterns effectively, the unique value of AgentFuel's customizable generation would diminish.

### Mechanism 2
- **Claim**: The AI‑assisted, modular pipeline lowers the barrier for domain experts to create expressive, reproducible evals without requiring deep technical data synthesis expertise.
- **Mechanism**: AgentFuel uses an LLM assistant to translate high‑level domain descriptions (schemas, sample data) into structured entity specifications, state transition diagrams, and measurement models. A pattern injection library then injects domain‑relevant incidents. This abstracts complex time‑series simulation into declarative components.
- **Core assumption**: Domain experts (e.g., SREs, product analysts) can effectively describe their data semantics and incident patterns but lack tools to synthesize corresponding test data at scale.
- **Evidence anchors**:
  - [section 3.3] "We use an LLM assistant to infer domain‑specific schemas and entity specifications from the expert’s input."
  - [section 4] Implementation details of the Python SDK and pattern library for controllable generation.
  - [corpus] Weak direct support; neighboring work like "AQuilt" focuses on data synthesis for specialist LLMs but not tailored eval generation for agents.
- **Break condition**: If the LLM assistant's translations prove unreliable or the pattern library fails to capture key domain incidents, expert effort would remain high, negating the "lower barrier" claim.

### Mechanism 3
- **Claim**: Data‑query alignment in AgentFuel prevents false‑positive agent performance assessments by ensuring ground‑truth answers are derivable only from the specific patterns in the generated dataset.
- **Mechanism**: Queries are generated programmatically based on the same specifications used for data creation (e.g., incident time windows, state trajectories). The evaluation harness checks agent responses against deterministic answers computed from the ground‑truth data, avoiding ambiguity.
- **Core assumption**: Misaligned benchmarks (where queries don't match dataset contents) can incorrectly reward agents for generic or lucky guesses, masking true capability gaps.
- **Evidence anchors**:
  - [section 3.4] "We argue for explicitly ensuring data and query alignment... If we have a naïve agent that always responds that there are no spikes. Now, if the eval data does not actually contain such incidents, we would incorrectly conclude that the agent was working correctly."
  - [section 5.3] Failure cases show agents applying global thresholds or ignoring incident windows, highlighting the need for aligned queries.
  - [corpus] Not directly covered; related to general eval reliability concerns in papers like "Why do multi‑agent LLM systems fail?" but not the alignment mechanism.
- **Break condition**: If the query generation logic diverges from the data generation logic (e.g., incident windows in queries don't match injected patterns), evaluations become invalid.

## Foundational Learning

- **Concept: Time‑Series State Machine Modeling**
  - *Why needed here*: AgentFuel's data generation and stateful queries rely on modeling entity behavior as semi‑Markov processes with discrete states (e.g., normal, degraded, failure). Understanding state transitions and dwell times is essential to grasp how synthetic data encodes temporal patterns and how queries reconstruct occupancy records.
  - *Quick check question*: If an IoT sensor's state machine has states `operational -> warning -> critical -> maintenance`, what would the `OCC(e, 'critical', W)` function return for a given window `W`?

- **Concept: Query Template Taxonomy (Stateless vs. Stateful vs. Incident‑Specific)**
  - *Why needed here*: The paper's core argument hinges on distinguishing query types. Stateless queries treat events as unordered aggregates; stateful queries require sequence and timing; incident‑specific queries condition analysis on anomalous regimes. This taxonomy defines what agents must be tested on.
  - *Quick check question*: Is "What is the average CPU load?" stateless? Is "What is the average CPU load *while the service was in a degraded state*?" stateful? Is "What was the average CPU load *during the outage on Jan 2*?" incident‑specific?

- **Concept: Text‑to‑SQL/Code Agent Evaluation Pitfalls**
  - *Why needed here*: The paper evaluates agents that generate SQL or Python code to answer natural language questions over time‑series data. Understanding classic failure modes (schema confusion, incorrect time intervals, global vs. entity‑specific thresholds) is key to interpreting the results.
  - *Quick check question*: Why might an agent fail on "How many product views occurred while users had an item in their cart?" even if it can write correct SQL for "How many product views total?"

## Architecture Onboarding

- **Component map**: Domain Input -> LLM Assistant -> Exemplar Library -> Blending Engine -> Pattern Injection -> Query Template Engine -> Test Harness
- **Critical path**: Domain description → LLM‑assisted spec generation → Exemplar selection/blending → Pattern injection → Query generation (structured → NL) → Dataset/QA export → Agent test run → Scoring.
- **Design tradeoffs**:
  - *Realism vs. Control*: Pattern injection adds domain realism but risks overfitting to synthetic patterns; the library must balance common incidents with flexibility.
  - *Automation vs. Expert Override*: LLM assistant speeds setup but may misinterpret domain nuances; experts must be able to manually adjust specs.
  - *Coverage vs. Size*: Many query templates increase test comprehensiveness but blow up benchmark size; selection must prioritize high‑impact query types (stateful/incident).
- **Failure signatures**:
  - *Data Generation*: Generated time‑series don't exhibit intended patterns (e.g., no clear incident spikes); check via `data quality checkers` (section 4).
  - *Query Alignment*: Ground‑truth answers don't uniquely depend on injected patterns; agent can guess correctly without understanding.
  - *Agent Evaluation*: High inconsistency (`self‑consistency` low) or random failures (`pass@2` similar to `accuracy`) indicate non‑deterministic agent flaws, not benchmark issues.
- **First 3 experiments**:
  1. **Validate Dataset Realism**: For a generated IoT dataset, manually inspect a sample time‑series to confirm state transitions (e.g., `operational -> warning -> critical`) and injected incidents (e.g., sudden temperature spikes) match specs.
  2. **Test Query‑Dataset Alignment**: Pick an incident‑specific query (e.g., "average latency during the outage"). Compute ground‑truth answer from `D_global`. Then, modify `D_global` to remove the incident (e.g., set all latency to baseline). Re‑run query—answer should change significantly, proving alignment.
  3. **Reproduce Performance Gap**: Run a baseline agent (e.g., PandasAI with O4Mini) on the e‑commerce benchmark. Confirm stateless accuracy >70%, stateful <40%, and incident (if present) ~10%. If gap is absent, benchmark generation likely flawed.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question**: What specific architectural or training limitations in current data analysis agents cause their consistent failure on stateful trajectory‑dependent queries, and are these failures primarily due to reasoning limitations, tool‑use deficiencies, or training data gaps?
- **Basis in paper**: [inferred] The paper shows stateful query accuracy drops from 73% (stateless) to 34%, with failure modes including "no state tracking" and inconsistent answers (Section 5.2, 5.3). However, the black‑box evaluation design prevents isolating whether failures stem from LLM reasoning chains, lack of specialized tools, or inadequate training examples.
- **Why unresolved**: The study uses one‑shot query‑response without tracing intermediate steps (tool calls, SQL generation, reasoning traces), so the exact failure point in the agent pipeline remains unknown. Different agent architectures (ReAct, direct SQL generation, code execution) could exhibit different failure modes.
- **What evidence would resolve it**: Controlled experiments with agent tracing frameworks to compare reasoning patterns across query types; ablation studies removing/adding state‑tracking tools; analyzing failure correlations with underlying LLM capabilities (context length, reasoning benchmarks).

### Open Question 2
- **Question**: How can AgentFuel's pattern injection library be systematically validated and extended to ensure it covers the full spectrum of anomalous and incident patterns encountered in real‑world time‑series systems across diverse domains?
- **Basis in paper**: [explicit] The paper describes an "extensible and controllable 'pattern injection' library that covers many common patterns (e.g., KPI degradation, data outages, sudden flash crowds)" (Page 4) but provides no inventory of patterns, validation methodology, or discussion of potential gaps. The evaluation uses only three domains with a limited set of injected incidents.
- **Why unresolved**: Without a taxonomy of real‑world incident patterns or quantitative metrics for pattern realism, it's unclear whether AgentFuel's pattern library is sufficiently comprehensive or whether its synthetic incidents match the complexity of production anomalies.
- **What evidence would resolve it**: A cross‑domain survey cataloging incident patterns from production systems (telecom, IoT, observability); measuring whether agents fail similarly on AgentFuel vs. production incidents; expert assessment of synthetic incident realism; systematic coverage testing against the incident taxonomy.

### Open Question 3
- **Question**: Do AgentFuel‑generated benchmarks reliably predict real‑world agent deployment failures, or do they introduce synthetic biases that make them either too easy or unrealistically difficult compared to production workloads?
- **Basis in paper**: [inferred] The paper demonstrates poor agent performance on AgentFuel benchmarks but provides no validation that these failures correlate with failures on real production data or that benchmark difficulty matches deployment risk. The motivating examples are illustrative, not statistically validated against production failure cases.
- **Why unresolved**: Synthetic data generation may introduce distribution shifts (e.g., oversimplified temporal dynamics, unrealistic correlations) or omit subtle patterns that cause real failures. Without external validation, AgentFuel benchmarks might optimize for the wrong capabilities.
- **What evidence would resolve it**: Multi‑organization study measuring agent accuracy on both AgentFuel benchmarks and production deployments; correlation analysis between benchmark scores and incident detection rates in live systems; sensitivity analysis varying synthetic data parameters to identify when benchmark performance diverges from production performance.

### Open Question 4
- **Question**: What evaluation design principles should guide the creation of time‑series agent benchmarks to balance domain‑specific expressivity with generalizability across organizations, and how can we measure the "transferability" of evaluation insights?
- **Basis in paper**: [inferred] The paper advocates "customized evals" but offers no methodology for determining the appropriate level of customization. The three domain benchmarks vary in difficulty (telecom hardest), but the paper doesn't analyze which aspects (schema complexity, incident logic, multi‑table joins) drive this or whether lessons transfer across domains.
- **Why unresolved**: Organizations have heterogeneous data schemas, query patterns, and incident types. Over‑customization might yield evaluations that fail to generalize even within a domain, while under‑customization might miss critical failure modes. The paper provides no framework for this trade‑off.
- **What evidence would resolve it**: Experimental study systematically varying benchmark customization (schema complexity, query mix, pattern diversity) and measuring cross‑domain predictiveness; developing a metric for evaluation portability based on feature overlap between source and target domains; case studies from multiple organizations using AgentFuel to identify common vs. domain‑specific failure patterns.

### Open Question 5
- **Question**: Can AgentFuel evaluations be automated end‑to‑end without manual grading, and what are the accuracy and reliability trade‑offs of using LLM‑as‑a‑judge versus execution‑based verification for time‑series query answering?
- **Basis in paper**: [explicit] The paper states: "for the accuracy evaluation we currently manually code all agent responses" (Page 7). It mentions using LLM‑as‑a‑judge for GEPA experiments but explicitly notes this was a change for compatibility, implying concerns about main evaluation validity.
- **Why unresolved**: Manual grading doesn't scale and may introduce subjectivity. LLM‑as‑judge may struggle with nuanced numerical answers, temporal reasoning, or multi‑table results. Execution‑based verification (running generated code/SQL) might fail when agents produce incorrect but plausible answers. The paper doesn't compare these approaches.
- **What evidence would resolve it**: Benchmarking agreement between manual grading, LLM‑as‑judge, and execution verification on a diverse query set; measuring cost vs. accuracy trade‑offs; identifying query types where automated methods fail; developing hybrid scoring protocols that combine multiple verification signals.

## Limitations
- **Domain Generalizability**: Benchmarks only cover e‑commerce, IoT, and telecom; it's uncertain whether the identified gaps persist in finance or healthcare with different state dynamics and regulatory constraints.
- **LLM Assistant Reliability**: No quantitative error analysis of the spec translation step; the burden and frequency of expert overrides remain unknown.
- **Benchmark Obsolescence Risk**: Rapid advances in agent architectures could close the stateful/incident gap, and the pattern library may not keep up with evolving real‑world anomaly complexity.
