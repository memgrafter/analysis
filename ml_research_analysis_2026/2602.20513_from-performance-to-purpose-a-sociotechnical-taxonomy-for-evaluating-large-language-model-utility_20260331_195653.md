# From Performance to Purpose: A Sociotechnical Taxonomy for Evaluating Large Language Model Utility

## Quick Facts
- **arXiv ID:** 2602.20513  
- **Source URL:** https://arxiv.org/abs/2602.20513  
- **Reference count:** 40  
- **Primary result:** LUX introduces a four-domain hierarchical framework for LLM utility evaluation, linking each component to quantifiable metrics via a dynamic web tool.

## Executive Summary
Large language models (LLMs) are increasingly deployed in real-world settings, yet their evaluation remains narrow, focusing on task performance while ignoring sociotechnical factors that determine actual utility. This paper presents the Language Model Utility Taxonomy (LUX), a comprehensive framework that structures utility evaluation across four domains—Performance, Interaction, Operations, and Governance—each decomposed into thematically aligned dimensions and components. Every component is anchored to specific, measurable metrics, and a companion dynamic web tool offers a curated repository linking each component to relevant metrics, descriptions, and literature. The taxonomy thereby shifts LLM assessment from correctness-centric benchmarks toward a holistic, context-aware approach that can guide model selection and deployment decisions.

## Method Summary
The paper does not describe a training or evaluation procedure but instead proposes a conceptual taxonomy and an associated web-based resource. LUX is built as a four-level hierarchy: Domains (high-level themes), Dimensions (thematic groupings within domains), Components (specific, measurable factors), and Metrics (quantitative or validated qualitative measures). The authors accompany the taxonomy with a dynamic web tool (https://chart-lab.github.io/LUX-Framework/) that maps every component to a repository of metrics, each with definitions, usage notes, and citations.

To apply LUX, practitioners first identify the LLM use case and relevant stakeholder needs, then use the web tool to select appropriate domains, dimensions, and components. For each chosen component, they locate corresponding metrics (e.g., F1 score for accuracy, TTFT for latency) and implement measurement—either by leveraging existing benchmarks or by designing custom tests. Finally, results across components are synthesized into a multi-dimensional utility profile that reveals strengths, weaknesses, and trade-offs, informing model selection and deployment planning.

## Key Results
- LUX organizes LLM utility into four non-overlapping domains: Performance (accuracy, stability), Interaction (workflow integration, traceability), Operations (cost, efficiency), and Governance (policy enforcement, security).
- The framework is hierarchical: each domain is decomposed into dimensions and components, with each component anchored to specific, quantifiable metrics.
- A dynamic web tool provides an updatable interface to explore components and access the associated metric repository.

## Why This Works (Mechanism)

### Mechanism 1: Structuring fragmented sociotechnical factors
**Claim:** LUX structures a previously fragmented set of sociotechnical factors into a coherent, hierarchical framework, enabling systematic evaluation.  
**Mechanism:** The framework organizes utility into four high-level domains, each decomposed into thematic dimensions and concrete components. This hierarchy translates broad utility concerns into specific, comparable criteria.  
**Core assumption:** The selected domains and their decomposition comprehensively capture the determinants of real-world LLM utility for diverse use cases.  
**Evidence anchors:** [abstract] "LUX, a comprehensive framework that structures utility evaluation across four domains..." [section] "Within each domain, LUX is organized hierarchically into thematically aligned dimensions and components."  
**Break condition:** The framework fails if critical utility determinants are omitted or if the hierarchical decomposition creates artificial silos that misrepresent interdependent factors.

### Mechanism 2: Anchoring components to quantifiable metrics
**Claim:** Each component within LUX is anchored to specific, quantifiable metrics, transforming abstract constructs into measurable criteria.  
**Mechanism:** For every component (e.g., "robustness"), the framework connects to a repository of defined metrics (e.g., performance drop under paraphrased queries). This grounds evaluation in operational definitions.  
**Core assumption:** A valid, reliable metric exists (or can be developed) for every defined component.  
**Evidence anchors:** [abstract] "each grounded in metrics that enable quantitative comparison." [section] "Ultimately, components are defined by specific metrics, which are designed to offer quantitative evaluation of a model." Appendix B provides a catalog of metrics (e.g., F1 score, TTFT). Neighboring papers develop metrics for safety, supporting feasibility.  
**Break condition:** The mechanism breaks if a component lacks any viable metric or if metrics are contested or sparse.

### Mechanism 3: Companion web tool operationalizes the taxonomy
**Claim:** The dynamic web tool operationalizes the taxonomy, providing a persistent, updatable interface linking theoretical components to practical metrics and literature.  
**Mechanism:** The tool maps each LUX component to a curated repository of metrics, descriptions, and references, externalizing the framework from the static paper and allowing community contributions.  
**Core assumption:** Practitioners will actively use the tool and it will be maintained.  
**Evidence anchors:** [abstract] "an external dynamic web tool is provided to support exploration..." [section] footnote 1 URL: https://chart-lab.github.io/LUX-Framework/.  
**Break condition:** The tool becomes obsolete, loses links, or is not maintained, decoupling the living framework from its publication.

## Foundational Learning

**Concept 1: Sociotechnical Systems Thinking**  
*Why needed:* LUX evaluates LLMs as embedded within human, organizational, and regulatory systems, not as isolated technical artifacts. Grasping this perspective is prerequisite to understanding why domains like Governance and Interaction are co-equal with Performance.  
*Quick check:* Identify one factor from the Governance domain and explain how it reflects a sociotechnical (not purely technical) risk of an LLM deployment.

**Concept 2: Hierarchical Taxonomy Design**  
*Why needed:* LUX’s structure is a multi-level hierarchy (Domains → Dimensions → Components → Metrics). Understanding how to navigate and apply this hierarchy is essential for using the framework beyond memorizing its four domains.  
*Quick check:* For the goal "evaluate an LLM for a legal document review tool," walk down the hierarchy: which Domain, Dimension, and Component would be most critical for the "workflow integration" aspect?

**Concept 3: Operationalizable Metrics**  
*Why needed:* The framework’s utility hinges on moving from abstract principles (e.g., "the model should be fair") to actionable measures (e.g., "disparate impact score"). Learning to identify and critique the operational definition of a metric is key to applying LUX.  
*Quick check:* For the "Cost" component in Operations, what are two distinct metrics one could use, and what trade-off might exist between them?

## Architecture Onboarding

**Component map:** Domains → Dimensions → Components → Metrics (the hierarchy), with the dynamic web tool serving as the navigational engine and metric repository.

**Critical path:**  
1. Define use case & stakeholder needs.  
2. Domain scoping: identify relevant LUX domains.  
3. Component drill-down: select specific dimensions and components.  
4. Metric selection & sourcing: use web tool to find metrics.  
5. Evaluation design & execution: integrate metrics into testing (benchmarks, user studies, cost analysis).  
6. Synthesis & trade-off analysis: aggregate results into a multi-dimensional utility profile.

**Design tradeoffs:**  
- **Comprehensiveness vs. Pragmatism:** LUX is exhaustive; applying all components for every evaluation is impractical. Selection of a subset risks overlooking silent but critical factors.  
- **Standardization vs. Context-Specificity:** The taxonomy provides standard components, but metric choice must be context-sensitive. A "timeliness" metric for medical diagnosis (seconds) differs from one for literary analysis (days).  
- **Static Framework vs. Dynamic Tool:** The paper’s hierarchy is fixed, but utility depends on the tool’s metric repository being current. Relying solely on the paper becomes outdated; reliance on the tool introduces a single point of failure.

**Failure signatures:**  
- **Domain Blind Spot:** Strong results in Performance and Operations but omitted Governance leads to compliance failures.  
- **Metric Misapplication:** Using an invalid metric (e.g., BLEU for text fluency) for a component, generating misleading results.  
- **Tool Disconnect:** Practitioners use the static diagram without consulting the web tool, missing newer metrics or nuanced definitions.  
- **Goal Displacement:** Focusing on maximizing scores across metrics rather than answering the original purpose-driven question.

**First 3 experiments:**  
1. **Domain Coverage Audit:** For a given LLM use case (e.g., "customer service chatbot"), list all 4 LUX domains. For each, state 1-2 components most critical and 1-2 least relevant. Justify rankings based on use case purpose and constraints.  
2. **Metric Hunt & Critique:** Select one component (e.g., "attribution" under Traceability). Use the web tool to find 3 proposed metrics. For each, write one sentence on its strengths and one on a potential weakness or context where it would fail.  
3. **Comparative Utility Profile:** Choose two LLMs (Model A and Model B). For a specific purpose (e.g., "real-time data analysis for financial reports"), construct a LUX-style table with 5-6 key components from different domains. Populate with estimated scores/assessments. Write a 3-sentence recommendation stating which model is preferable for this purpose and why, referencing trade-offs revealed by the table.

## Open Questions the Paper Calls Out

**Open Question 1**  
- **Question:** How can the LUX framework be systematically updated and adapted to incorporate newly emergent sociotechnical factors and metrics as LLM applications and contexts evolve?  
- **Basis in paper:** (inferred) The conclusion states LUX is designed as a "flexible framework, not a metric" to allow for "emerging considerations," but provides no specific methodology or governance structure for its maintenance, curation, or evolution.  
- **Why unresolved:** Without a defined process for community input, validation, and versioning, the framework risks becoming static and misaligned with the rapidly changing LLM landscape and research priorities it aims to capture.  
- **What evidence would resolve it:** A documented, participatory protocol for proposing, reviewing, and integrating new components/metrics, supported by a case study demonstrating the update process for a novel domain (e.g., environmental impact quantification).

**Open Question 2**  
- **Question:** What is the empirical evidence that the specific metrics associated with each LUX component are predictive of real-world utility and successful deployment outcomes in specific high-stakes domains (e.g., healthcare, legal)?  
- **Basis in paper:** (inferred) The paper links components to existing "metrics" and provides a repository, but does not validate whether these metrics correlate with or causally influence downstream measures of utility like user adoption, task success, risk mitigation, or return on investment.  
- **Why unresolved:** The taxonomy organizes factors but does not establish the validity or weight of its constituent metrics. A metric's presence does not confirm its importance or predictive power for practical utility.  
- **What evidence would resolve it:** Large-scale field studies or meta-analyses correlating LUX metric scores (e.g., on stability, cost, governance) with deployed system performance metrics across diverse, real-world applications.

**Open Question 3**  
- **Question:** How can LUX be used to identify and quantify critical trade-offs between domains (e.g., between performance accuracy and cost efficiency, or between interaction fluidity and governance security) for a given use case?  
- **Basis in paper:** (inferred) The framework organizes domains hierarchically but treats them as largely independent collections of components. The conclusion notes evaluation must happen "in context," implying trade-offs exist, but the taxonomy does not provide a method for comparative weighting or multi-criteria decision analysis across domains.  
- **Why unresolved:** Practitioners need to make resource allocation and model selection decisions that inherently involve trade-offs. LUX currently lists factors but does not offer a structured approach to navigate these compromises.  
- **What evidence would resolve it:** Development and validation of a formal decision-support model (e.g., a scoring rubric, utility function, or Pareto analysis method) that can be applied to LUX component scores to reveal and quantify key trade-offs for specific operational scenarios.

**Open Question 4**  
- **Question:** How can the sociotechnical concept of "bias," noted as permeating all LUX domains, be operationalized and measured consistently and meaningfully across the disparate components (e.g., from training data provenance in performance to policy enforcement in governance)?  
- **Basis in paper:** (explicit) The conclusion states: "Reflecting on evaluation more broadly, the importance of information and impact of bias permeates all domains and factors." However, bias is not established as a distinct dimension or component with its own metrics.  
- **Why unresolved:** Bias is a cross-cutting, fundamental risk. Without a unified approach to measuring it across LUX's sociotechnical spectrum, evaluations may miss systemic or context-specific biases that undermine utility.  
- **What evidence would resolve it:** A set of validated, domain-agnostic bias audit protocols or metrics that can be mapped onto relevant LUX components (e.g., data audits for performance, fairness audits for interaction, equity audits for governance) and demonstrated in a cross-domain case study.

**Open Question 5**  
- **Question:** To what extent do the governance and security components in LUX (e.g., policy enforcement, jailbreak resistance, statefulness) provide robust safeguards in adversarial or evolving threat environments, and how should their evaluation adapt to novel attack vectors?  
- **Basis in paper:** (explicit) The Governance domain explicitly mentions vulnerability to "jailbreaking" and the need for "risk assessment." The paper cites tools like JailBreakV and PII-Scope as current metrics.  
- **Why unresolved:** LLM security is a moving target; current jailbreak and PII leakage metrics are snapshots against known attacks. The taxonomy does not address how to evaluate a model's *adaptive* resilience or the dynamic nature of policy enforcement against unforeseen threats.  
- **What evidence would resolve it:** A proposed framework for "adversarial robustness evaluation" within LUX's governance domain, tested via red-teaming exercises that generate novel attack strategies, with metrics that measure not just static compliance but adaptive defense capabilities.

## Limitations
- **Metric Repository Completeness:** The web tool’s linked metrics lack verification for accessibility, implementation status, and validity across contexts.  
- **Aggregation Framework:** No prescribed method exists to synthesize heterogeneous metrics (e.g., cost vs. accuracy), risking subjective or inconsistent utility scoring.  
- **External Validation:** The corpus shows zero citations, indicating LUX is untested by independent research and may overlap with existing fragmented efforts.

## Confidence
- Framework Comprehensiveness: Medium  
- Metric Operationalization: Medium  
- Tool Adoption & Maintenance: Low
