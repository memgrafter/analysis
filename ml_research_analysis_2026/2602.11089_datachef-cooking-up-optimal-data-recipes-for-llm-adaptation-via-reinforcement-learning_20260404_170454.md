# DataChef: Cooking Up Optimal Data Recipes for LLM Adaptation via Reinforcement Learning

## Quick Facts
- arXiv ID: 2602.11089
- Source URL: https://arxiv.org/abs/2602.11089
- Reference count: 40
- Primary result: DataChef-32B generates data recipes that match human expert and Gemini-3-Pro performance on six held-out tasks; a math adaptation recipe doubles Qwen3-1.7B-Base's AIME’25 score from 33.3 to 66.7.

## Executive Summary
DataChef introduces an automated system for generating data processing pipelines (“data recipes”) to adapt large language models (LLMs) to new tasks. The core innovation is an LLM-based policy (DataChef-32B) trained via online reinforcement learning (GRPO) guided by a proxy reward computed by a Data Verifier. The verifier, an LLM-as-judge with a fine-grained rubric, evaluates a small subset of the generated dataset and correlates strongly with downstream LLM performance (Pearson r=0.83 on one task). This avoids costly full-model training during RL. Across six held-out benchmarks, DataChef produces recipes comparable to those crafted by human experts and to those from Gemini-3-Pro. Most impressively, a recipe for math adaptation boosts Qwen3-1.7B-Base’s AIME’25 score from 33.3 to 66.7, a 100% relative improvement. The work demonstrates the feasibility of using RL with learned rewards to automate data-centric LLM adaptation.

## Method Summary
DataChef employs a two-phase training pipeline. First, a cold-start supervised fine-tuning (SFT) phase initializes the policy model (Qwen3-32B) with high-quality demonstrations. These demonstrations are created by decoupling reasoning and coding: a strong reasoning LLM generates a natural-language processing plan, and a coding-focused LLM implements it as executable Python code. Only successful, high-quality rollouts are retained, forming a dataset of 5,000 examples. The policy is SFT on this data for two epochs, equipping it with basic code generation skills and complex pipeline patterns.

Second, an online reinforcement learning phase uses the GRPO algorithm. For each sampled task (from a pool of 31 benchmarks across 19 domains, augmented to 5,000 unique instances), the policy generates G=8 candidate recipes (Python scripts). Each script is executed on the available raw data sources to produce a candidate training dataset. A Data Verifier (gpt-oss-120b) scores a random 100-sample subset using a five-category rubric (Invalid, Format Error, Incorrect, Task Mismatch, Pass). The average score, penalized for execution failures or format violations, serves as the reward. The policy is updated to maximize this proxy reward. This loop avoids the computational expense of repeatedly fine-tuning and evaluating an LLM for each candidate recipe.

## Key Results
- Across six held-out tasks, DataChef’s generated recipes achieve performance comparable to human experts and Gemini-3-Pro.
- A recipe adapting Qwen3-1.7B-Base to mathematics yields an AIME’25 score of 66.7, doubling the official checkpoint’s 33.3.
- The Data Verifier exhibits a high Pearson correlation (r=0.83) with downstream performance on one task, and an average correlation of 0.59 across all six evaluated domains.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: DataChef leverages a learned proxy reward (Data Verifier) that correlates strongly with downstream LLM performance, enabling efficient online reinforcement learning without costly model training in the loop.
- **Mechanism**: The Data Verifier, a powerful LLM-as-judge, evaluates a randomly sampled subset of the generated dataset using a fine-grained rubric (invalid, format error, incorrect, task mismatch, pass). The average score, possibly penalized for execution failures, serves as the reward signal for GRPO. This avoids the computational burden of repeatedly fine-tuning and evaluating an LLM for each candidate recipe.
- **Core assumption**: The quality assessment of a small, random subset of data is a statistically reliable predictor of the full dataset’s utility for training an LLM on the target task.
- **Evidence anchors**:
  - [abstract] "The verifier uses fine-grained LLM-as-judge scoring and correlates highly (Pearson r=0.83) with downstream performance."
  - [section 3.3] "We define the final recipe reward R(r) by incorporating penalties for execution failures... The Data Verifier exhibits superior capability compared to existing metrics, achieving the highest average Pearson correlation of 0.59 across all six domains."
  - [corpus] The provided corpus evidence focuses on cooking recipes and robotics, not LLM data evaluation; thus direct relevance is weak.
- **Break condition**: If the Data Verifier’s correlation degrades on unseen data distributions or if the sampling strategy for the subset becomes biased (e.g., consistently missing critical flaws), the proxy reward may become uninformative or misleading, causing RL to optimize for the wrong objective.

### Mechanism 2
- **Claim**: Cold-start supervised fine-tuning (SFT) with decoupled planning and coding yields more complex and effective data pipelines than training the policy from scratch via RL, mitigating reward hacking.
- **Mechanism**: Before RL, the policy is SFT on demonstrations generated by two specialized models: a strong reasoning LLM produces natural-language processing plans, and a coding-focused LLM implements them as executable code. Only high-quality, executable rollouts are retained. This warm-up equips the policy with basic code-generation skills and non-trivial pipeline patterns, enabling RL to explore richer operation spaces rather than defaulting to simplistic, safe scripts that avoid execution penalties.
- **Core assumption**: A policy initialized with high-quality demonstrations will maintain diversity and complexity during RL exploration, rather than collapsing to trivial solutions that maximize short-term reward.
- **Evidence anchors**:
  - [section 3.3] "Cold-start Initialization: ... decoupling reasoning and coding yields superior inference-time performance ... Initializing πϕ on this curated dataset equips the policy with a foundational capability for code generation, significantly stabilizing the subsequent RL phase."
  - [section 4.4] "Omission of cold start leads to significant performance degradation ... direct RL model tends to generate simplistic data pipelines ... reward hacking."
  - [corpus] Not directly relevant; corpus relates to cooking recipe generation, not LLM data pipeline design.
- **Break condition**: If the demonstration generation process (using separate models for planning and coding) produces low-quality or non-executable examples, the SFT initialization may teach the policy poor patterns, hindering RL convergence or leading to suboptimal pipelines.

### Mechanism 3
- **Claim**: A large, diverse task pool with probabilistic augmentation enables the policy to generalize across domains and learn robust data recipe selection and orchestration.
- **Mechanism**: The authors curate 31 benchmarks spanning 19 domains, each paired with 8–15 raw data sources. These 25 seed tasks are augmented by randomly subsampling subsets of available data sources, creating 5,000 unique task instances. This exposes the policy to a vast combinatorial space of data source combinations and task specifications, forcing it to learn principles of data selection and processing rather than memorizing task-specific heuristics.
- **Core assumption**: Exposure to a wide variety of task configurations during training is necessary for the policy to generalize to held-out tasks, including out-of-domain benchmarks, by capturing transferable patterns in data recipe construction.
- **Evidence anchors**:
  - [section 3.2] "We construct a comprehensive task pool comprising 31 widely used benchmarks across 19 distinct domains. ... We expand the 25 seed tasks into a large-scale training set T_train. ... yields 5K unique task instances."
  - [section 4.2] Results show strong performance on both in-domain and out-of-domain held-out tasks (e.g., matching Gemini-3-Pro), indicating effective generalization.
  - [corpus] Not directly relevant; corpus centers on cooking recipe systems, not LLM adaptation data recipes.
- **Break condition**: If the task pool lacks coverage of certain domain characteristics (e.g., long-context, specialized knowledge) or if augmentation introduces tasks that are too noisy or ill-defined, the policy may fail to learn transferable strategies and perform poorly on novel tasks.

## Foundational Learning
- **Concept: Reinforcement Learning with Learned Rewards**
  - **Why needed here**: DataChef’s core training loop uses GRPO, an RL algorithm, with a learned proxy reward instead of a ground-truth reward (downstream LLM performance). Understanding RL basics (policy, reward, advantage) and the challenges of reward shaping is essential.
  - **Quick check question**: What are the risks of using a learned reward model in RL, and how might it diverge from the true objective of maximizing downstream task performance?

- **Concept: Data Processing Pipelines for LLM Training**
  - **Why needed here**: The paper automates the creation of “data recipes” — sequences of operations (filtering, synthesis, mixing, deduplication, formatting) applied to raw datasets to produce training data. Knowing common operations and their purposes (e.g., improving quality, diversity, task relevance) is key to interpreting generated recipes.
  - **Quick check question**: Why might a data recipe include both filtering (removing outliers) and synthesis (generating new samples)? What trade-offs does this involve?

- **Concept: LLM-as-a-Judge and Reward Modeling**
  - **Why needed here**: The Data Verifier is an LLM prompted with a rubric to score data samples. This paradigm (LLM-as-a-judge) is widely used for evaluation and reward modeling but has known limitations (bias, inconsistency). Understanding its application here is critical.
  - **Quick check question**: How does the paper’s use of a rubric with five categories attempt to make LLM-as-a-judge more objective, and what residual risks remain?

- **Concept: Supervised Fine-Tuning (SFT) for Code Generation**
  - **Why needed here**: The cold-start phase uses SFT on code-generation demonstrations. The policy must output valid Python scripts that manipulate datasets. Familiarity with SFT and code generation challenges (executability, library usage) is necessary.
  - **Quick check question**: What makes generating executable data-processing code particularly difficult compared to generating natural language, and how does the paper’s decoupled planning/coding approach address this?

## Architecture Onboarding
- **Component map**:
  1. Task Input Parser: Extracts task description, benchmark details, and available dataset metadata.
  2. Policy LLM (DataChef-32B): Generates a natural-language plan and corresponding executable Python code (data recipe).
  3. Execution Engine: Runs the code on the raw data sources, producing a training dataset (and possibly intermediate artifacts).
  4. Data Verifier: LLM-as-judge that scores a random subset of the generated dataset using the rubric, returning a scalar reward.
  5. RL Trainer (GRPO): Computes group-relative advantages and updates policy weights.
  6. Cold-start SFT Module: (Offline) Generates demonstrations using separate planning and coding models, filters for quality, and performs initial SFT.

- **Critical path**: Task specification → Policy proposes recipe → Execution produces dataset → Verifier scores → RL updates policy. Cold-start runs once before RL.
- **Design tradeoffs**:
  - **Proxy reward fidelity vs. cost**: A more accurate but slower verifier would improve signal but reduce RL throughput; the paper uses a fast MoE model (gpt-oss-120B) to balance.
  - **End-to-end vs. modular policy**: Training a single model to do both planning and coding (end-to-end) vs. using specialized modules at inference (decoupled). The paper finds end-to-end training yields better performance but decoupling helps in cold-start.
  - **Task pool diversity vs. training stability**: More tasks improve generalization but may introduce噪声 or ill-defined instances that destabilize RL.
  - **Reward granularity**: Fine-grained rubric (5 categories) provides richer signal than binary success but requires careful prompt design and may still be noisy.

- **Failure signatures**:
  - **High execution failure rate** (many `d=∅` or format violations): Policy generates syntactically invalid or logically broken code. Check code generation capabilities, prompt clarity, and execution environment consistency.
  - **Low Data Verifier score despite execution**: Generated dataset is low quality (e.g., irrelevant, incorrect, mismatched). Investigate source selection, processing operations, and verifier prompt alignment.
  - **High variance in reward across rollouts**: Policy not converged, reward signal too noisy, or group size (`G`) too small. Monitor reward distribution and adjust KL penalty or learning rate.
  - **Poor generalization to held-out tasks**: Task pool lacks diversity or overfits to training distribution. Augment with more varied tasks or improve prompt generalization.

- **First 3 experiments**:
  1. Validate Data Verifier correlation independently: On a small set of manually crafted datasets (e.g., high-quality vs. corrupted versions), verify that verifier scores correlate with known quality and with downstream performance on a simple fine-tuning run.
  2. Ablate cold-start: Train a model from random initialization with RL only, compare the complexity of generated pipelines (e.g., number of operations, use of LLM calls) and DVS to the full method.
  3. Test robustness to data source scarcity: Create tasks with very few available raw datasets (e.g., 1–2) and see if the policy can still generate valid recipes, and how performance scales with source count.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: Can AI systems automatically generate high-quality data recipes for LLM adaptation in a cost-efficient manner compared to human experts, considering both computational resources and human labor?
- **Basis in paper**: [explicit] The Introduction explicitly asks: "can AI systems automatically generate a data recipe for training LLMs... in a cost-efficient way?" The paper proposes DataChef as a step toward this but does not provide a full cost-benefit analysis against manual curation.
- **Why unresolved**: The study uses a proxy reward to avoid expensive downstream training, but the total cost of RL training, verifier inference, and recipe execution is not compared to the person-hours and compute needed for human-designed recipes. Generalization to arbitrary tasks and data sources also remains untested at scale.
- **What evidence would resolve it**: A comprehensive study measuring total computational cost (GPU hours), time, and human oversight for DataChef versus expert-led pipeline design across a diverse set of tasks, including iterations needed for convergence.

### Open Question 2
- **Question**: To what extent do specialized data evaluators (domain-specific verifiers) outperform the generalist LLM-as-judge approach in generating optimal data recipes for highly specialized or safety-critical domains?
- **Basis in paper**: [explicit] The Limitations state: "Our reliance on an LLM-as-a-Judge for proxy rewards prioritizes generalizability but may sacrifice precision in niche tasks. Developing specialized evaluators to offer higher-resolution reward signals remains a valuable direction for future research."
- **Why unresolved**: The Data Verifier uses a single generalist model (gpt-oss-120b) across all 6 evaluated tasks, which are relatively broad. No experiments compare it to domain-specific evaluators (e.g., biomedical, legal) where nuanced quality criteria may differ. The correlation analysis shows variable significance (Table 5), hinting at domain sensitivity.
- **What evidence would resolve it**: Construct domain-specific verifiers for niche fields (e.g., clinical text, legal documents) using tailored rubrics and expert annotations. Compare recipe performance (DBS) when using generalist vs. specialist verifiers as rewards in RL, measuring downstream task accuracy and verifier-downstream correlation.

### Open Question 3
- **Question**: How does the cold-start SFT phase affect the diversity and novelty of generated data pipelines, and can alternative initialization strategies (e.g., diverse demonstrations, unsupervised pretraining) mitigate potential reward hacking while preserving exploration?
- **Basis in paper**: [inferred] The paper shows that without cold-start, RL generates simpler pipelines with fewer complex operations (Fig 5), suggesting reward hacking (avoiding penalties by producing trivial scripts). The cold-start uses a decoupled planner-coder approach, but its impact on pipeline diversity (e.g., operation variety, novel combinations) is not analyzed.
- **Why unresolved**: The evaluation focuses on downstream performance (DBS/DVS) but not on metrics of pipeline creativity or exploration breadth. It is unclear whether cold-start biases the policy toward patterns from the demonstration set, limiting discovery of unconventional but effective pipelines.
- **What evidence would resolve it**: Define diversity metrics (e.g., entropy of operation types, syntactic variance in generated code). Compare these metrics across policies trained with: (a) no cold-start, (b) proposed cold-start, (c) alternative initializations (e.g., random code, diverse synthetic plans). Correlate diversity with downstream gains, especially on out-of-domain tasks.

### Open Question 4
- **Question**: Does the Data Verifier's sample-based reward estimation remain reliable when scaling to larger data budgets or more complex data recipes involving heterogeneous sources and multi-step transformations?
- **Basis in paper**: [inferred] The framework evaluates recipes using a fixed small sample (100 instances) for the verifier, while downstream training uses up to 10K samples. The proxy reward assumes this sample sufficiently estimates dataset quality, but this may not hold for larger or more diverse recipes where quality variance is higher.
- **Why unresolved**: All experiments use the same small sample size for DVS regardless of recipe complexity or data budget. No analysis tests whether verifier scores on 100 samples correlate with scores on the full 10K dataset or with downstream performance as budget increases. Complex recipes (e.g., heavy synthesis) might exhibit higher variance.
- **What evidence would resolve it**: For a subset of generated recipes, compute verifier scores on increasing sample sizes (100, 1K, 10K) and measure correlation with downstream performance at each budget. Evaluate if prediction error grows with recipe complexity (e.g., number of operations, source diversity).

### Open Question 5
- **Question**: Why does the Data Verifier achieve strong but statistically inconsistent correlation with downstream performance across domains (e.g., p > 0.1 for PHYSICS), and can its rubric be refined to improve robustness without sacrificing generalizability?
- **Basis in paper**: [explicit] Table 5 reports Pearson correlations and p-values: for PHYSICS, r=0.63 but p=0.07; for LiveCodeBench, r=0.63, p=0.07; for CHID, r=0.83, p=0.01. The paper notes "4 out of 6 tasks satisfying p < 0.1", indicating variable statistical significance despite positive correlations.
- **Why unresolved**: The verifier uses a fixed five-category rubric (Invalid to Pass) applied uniformly. Domain-specific nuances (e.g., code correctness vs. mathematical reasoning) may not be captured equally, leading to noisier signals in some tasks. The paper does not investigate error cases or adjust the rubric per domain.
- **What evidence would resolve it**: Perform error analysis on low-significance tasks: examine instances where verifier score disagrees with downstream outcome. Refine the rubric with domain-specific criteria (e.g., code executability for coding tasks, formal proof structure for math) and test if correlation and significance improve across all tasks while maintaining cross-domain applicability.

## Limitations
- Data Verifier’s correlation (r=0.83 abstract; avg 0.59 in 6 domains) may not generalize to new data distributions.
- Cold-start demonstrations are unreproducible without the original planner/coder models and prompts.
- Key hyperparameters (GRPO clipping ϵ, KL coefficient β, failure penalties λ) are omitted, blocking exact replication.

## Confidence
- Proxy reward validity: Medium
- Cold-start benefit: High
- Generalization to new tasks: Medium

## Next Checks
1. *Verifier generalizability*: Compute verifier scores on 50 novel datasets (5+ domains), correlate with downstream scores of a fine-tuned 1.7B model; expect r ≥ 0.7.
2. *Cold-start ablation*: Train policy with RL only (same compute) and compare pipeline complexity (operation count, LLM calls) and success rate; RL-only should yield simpler, failure-prone recipes.
3. *Cross-domain robustness*: Evaluate on two unseen domains (e.g., biomedical QA, legal reasoning). If average DBS drop <5 points vs. in-domain, the generalization claim gains support.
