# Hydra: Unifying Document Retrieval and Generation in a Single Vision-Language Model

## Quick Facts
- **arXiv ID:** 2603.28554
- **Source URL:** https://arxiv.org/abs/2603.28554
- **Reference count:** 7
- **Primary result:** Hydra unifies visual document retrieval and generation in one VLM using a single LoRA adapter, achieves byte-identical generation to the base model, and reduces peak GPU memory by 41%.

## Executive Summary
Hydra introduces a unified vision-language model that perform both visual document retrieval and autoregressive text generation. By training a single LoRA adapter exclusively for retrieval and toggling it—along with attention masks—at inference, the model switches between multi-vector retrieval and generation. Three engineering fixes—attention-mode restoration, `lm_head` preservation, and KV-cache-aware decoding—ensure generation quality exactly matches the base VLM. Evaluations on ViDoRe and VQA benchmarks show competitive retrieval performance (nDCG@5 within 1 pp of a baseline), perfect generation equivalence, and a 41% memory reduction versus separate models. The approach extends to zero-shot audio/video retrieval and speech generation in Qwen2.5-Omni-3B.

## Method Summary
Hydra builds on a frozen vision encoder and a language model backbone (Qwen3.5-4B). It adds a `custom_text_proj` head for retrieval and applies a LoRA adapter (rank 16) to the LM’s projections (q/k/v/o/gate/up/down) and the `custom_text_proj`. The adapter is trained only with a ColBERT retrieval loss on document-image and query pairs. At inference, enabling the adapter and using bidirectional attention on full-attention layers produces multi-vector embeddings for retrieval. Disabling the adapter restores the base weights; full-attention layers revert to causal masks and the original `lm_head` is used with KV-cache for efficient generation. This design ensures the base model’s generation remains untouched, yielding identical outputs. Training uses 1 epoch, lr 5e-5, batch 112 (DDP), and bf16.

## Key Results
- Generation outputs are byte-identical to the base model across 10,500 samples, with maximum ΔANLS=0.0044 over 15,301 VQA samples.
- On ViDoRe V1 (9 tasks), Hydra achieves nDCG@5=0.8842, within 1 percentage point of a single-head baseline.
- Peak GPU memory reduced by 41% (10.5GB vs 17.9GB) compared to separate retrieval and generation models.

## Why This Works (Mechanism)
1. **LoRA Toggling and Attention Mask Switching**: The retrieval LoRA adapter is trained with bidirectional attention on full-attention layers. Enabling the adapter and using bidirectional masks at inference enables token interactions for retrieval. Disabling the adapter and restoring causal masks recovers the base model’s autoregressive generation, preventing future token leakage.
2. **Preservation of the Original `lm_head`**: During retrieval training, gradients from tied input embeddings or DDP synchronization can modify the `lm_head`. Loading the `lm_head` from a separate, frozen instance and excluding it from optimizer/DDP groups keeps its weights identical to the base model, guaranteeing generation equivalence.
3. **KV-Cache-Aware Decoding**: The vision encoder is processed only once at the start of generation; subsequent steps reuse cached key-value pairs from the language model. This avoids ~38× slower recomputation, making the unified model practical.

## Foundational Learning
- **LoRA Mechanics**: LoRA updates are additive (W = W_base + BA). Disabling the adapter reverts exactly to base weights, enabling Hydra’s toggle.
  - Quick check: With W_base and BA, what are effective weights when the LoRA adapter is enabled vs. disabled?
- **Attention Patterns**: Bidirectional attention allows all-to-all token interactions for retrieval; causal attention prevents future access for generation. Switching masks is essential.
  - Quick check: Why can’t a bidirectionally trained model generate autoregressively without modifying the attention mask?
- **KV-Cache in Transformers**: Past key-value tensors are cached and reused during autoregressive decoding to avoid recomputation, drastically speeding up generation.
  - Quick check: In a decoder with `use_cache=True`, what happens to past key/value tensors in the next forward pass?

## Architecture Onboarding
Component map:
Frozen Vision Encoder -> Text Model Backbone (with LoRA adapter on q/k/v/o/gate/up/down projections + custom_text_proj) -> [Retrieval Path: custom_text_proj (320-dim) OR Generation Path: lm_head (vocab)]

Critical path:
- Retrieval: Image -> Vision Encoder -> LM (LoRA ON, bidirectional attention on full-attention layers) -> custom_text_proj -> L2-normalized multi-vector embeddings.
- Generation: Image + Prompt -> Vision Encoder (once) -> LM (LoRA OFF, causal attention on full-attention layers, KV-cache ON) -> lm_head -> autoregressive text.

Design tradeoffs:
- Memory vs. Throughput: Single model reduces peak VRAM by 41% but cannot serve retrieval and generation concurrently on one GPU.
- Simplicity vs. Control: One adapter simplifies deployment but couples capabilities; toggle bugs break both.
- Performance ceiling: Joint training offers no benefit over retrieval-only LoRA (ablation), but may not hold for higher ranks or other architectures.

Failure signatures:
1. Generation mismatch (ANLS drop or non-identical outputs): likely `lm_head` corruption or incorrect attention mask.
2. Excessive memory: using two separate models instead of toggling.
3. Slow generation (>100s per sample): KV-cache not implemented.
4. Retrieval failure in generation mode: causal mask not restored.

First 3 experiments:
1. **Generation equivalence sanity check**: Run greedy decode on a fixed VQA subset with base model and Hydra (LoRA off). Assert 100% byte-identical outputs.
2. **Memory measurement benchmark**: Profile peak VRAM for embed-then-generate cycle with separate models vs. single Hydra model. Expect ~41% reduction.
3. **Mode-switch overhead test**: Time alternating retrieval and generation calls (50 iterations). Expect negligible overhead (<2% of generation time).

## Open Questions the Paper Calls Out
1. Do the gains on ViDoRe V2 and V3 persist across multiple training seeds? The paper reports a single run (seed 42), so statistical reliability is unknown.
2. Does Hydra's dual-head design work with non-Qwen VLMs (e.g., InternVL, LLaVA)? The paper acknowledges this as future work.
3. How does Hydra perform in a full RAG pipeline under concurrent user requests? The paper notes adapter switching serializes requests but provides no quantitative serving benchmarks.

## Limitations
- Unclear specification of which layers in Qwen3.5-4B are full-attention versus sliding-window, risking incorrect mask application.
- Incomplete recipe for preventing `lm_head` corruption during distributed training (e.g., DDP parameter group filtering).
- Undefined initialization and LoRA application details for `custom_text_proj`, affecting training reproducibility.

## Confidence
- LoRA/attention toggling mechanism: Medium
- Separate `lm_head` preservation requirement: Medium
- KV-cache-aware decoding necessity: High
- Reported retrieval and generation metrics: Medium-High
