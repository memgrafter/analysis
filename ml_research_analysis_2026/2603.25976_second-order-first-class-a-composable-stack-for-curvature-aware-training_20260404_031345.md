# Second-Order, First-Class: A Composable Stack for Curvature-Aware Training

## Quick Facts
- **arXiv ID**: 2603.25976
- **Source URL**: https://arxiv.org/abs/2603.25976
- **Reference count**: 40
- **Primary result**: Somax delivers a composable, Optax-native stack that treats curvature-aware training as a single JIT-compiled step, enabling systematic recombination and reducing per-step overhead via static planning.

## Executive Summary
Second-order optimization methods are underused due to implementation brittleness and a lack of modular APIs. Somax addresses this by offering a composable stack built on JAX and Optax, where curvature operators, solvers, damping policies, and preconditioners are first-class modules. A static planning phase analyzes module requirements to produce a lane‑specialized, JIT‑compiled step function that reuses intermediate computations, eliminating redundant work. System‑oriented evaluations reveal that the execution lane (parameter‑space vs. row‑space) fundamentally changes scaling with model and batch size; solver performance is tightly coupled to damping and preconditioning choices; and the modular design enables new optimizers such as Sophia‑N, which achieves competitive accuracy on CIFAR‑10/ResNet‑20. Microbenchmarks confirm that cadence‑gated telemetry can increase per‑step time by over 50 % when computed every step.

## Method Summary
Somax is a JAX/Optax library that assembles second‑order optimizers from explicit component specifications: `CurvatureSpec`, `SolverSpec`, `DampingSpec`, `PrecondSpec`, and optional `EstimatorSpec`. The assembler validates compatibility and resolves defaults. The planner then derives a static execution plan: it selects an execution lane (diagonal, parameter‑space, or row‑space) based on the curvature operator’s exposed primitives, determines which intermediate values (e.g., curvature snapshot) must be computed, and schedules any cadence‑gated probes (e.g., gain‑ratio). This plan yields a lane‑specialized step function that is JIT‑compiled as a single pure function. At runtime, the step computes the curvature once, reuses it for solving, damping updates, and optional telemetry, and finally applies the direction via Optax. The entire process decouples algorithm design from performance engineering and avoids redundant recomputation.

## Key Results
- The choice of execution lane (parameter‑space vs row‑space) fundamentally changes the asymptotic cost scaling with model size and batch size, as demonstrated through synthetic regression experiments.
- Solver performance is strongly coupled to damping and preconditioning; incompatible module interactions cause failure (e.g., certain damping‑preconditioner combinations on Fashion‑MNIST).
- The modular composition enables straightforward creation of new optimizers; Sophia‑N (combining Sophia‑G damping with Sophia‑H curvature) reaches 91.83 % test accuracy on CIFAR‑10/ResNet‑20, comparable to Sophia‑G (91.99 %) and better than Sophia‑H (90.74 %).
- Cadence‑gated telemetry (e.g., gain‑ratio every step) incurs a measurable overhead (>50 % increase in step time), highlighting a key trade‑off.

## Why This Works (Mechanism)

### Mechanism 1: Static Planning Eliminates Redundant Recomputation
The planner produces a fixed execution plan from module requirements, ensuring that expensive intermediates (e.g., curvature snapshot) are computed once per step and reused across all dependent modules (solver, damping updates, telemetry). This eliminates the redundant recomputation typical in ad‑hoc compositions. The resulting step function contains no runtime branching on lane or module choice, allowing JAX’s compiler to fully optimize it. Evidence includes the design description in Sections 3.1–3.2 and microbenchmarks (Section 3.4) showing reduced overhead versus unplanned composition. Break condition: if a module needs dynamic, data‑dependent cadence or statistics not expressible in the static schema, the planner must omit them or incur extra recomputation, raising overhead.

### Mechanism 2: First‑Class Modules Enable Systematic Recombination
All components are encapsulated behind explicit contracts that declare inputs and outputs (e.g., a curvature operator must provide matrix‑free primitives and may expose row operators). The assembler validates compatibility and resolves defaults, turning second‑order optimizer design into an auditable, swappable configuration. This modularity supports controlled ablations and easy recombination into new regimes (e.g., Sophia‑N). Evidence: Table 6 lists contracts; Section 4.4 demonstrates Sophia‑N. Break condition: Incompatible contracts (e.g., row‑space solver paired with curvature lacking row primitives) cause assembly failure; forcing such combinations would lead to missing functionality or incorrect solves.

### Mechanism 3: Execution Lane as a First‑Class Design Knob
For a given curvature family (e.g., GGN), Somax can solve the damped subproblem either in full parameter space (matrix‑free matvecs) or in row space (using Jacobian structure). The planner determines feasibility from the curvature operator’s primitives and generates a lane‑specialized compiled path. This choice fixes the dominant linear‑algebra operations and thus the scaling behavior with model and batch size. Evidence: Abstract and Section 2.3 define lanes; Figure 2 (Section 4.2) empirically shows lane‑dependent scaling. Break condition: Using an unsupported lane (e.g., Exact Hessian without row primitives with a row‑space solver) fails assembly; forcing the wrong lane would produce incorrect mathematics or excessive overhead.

## Architecture Onboarding
**Component map**: CurvatureSpec, SolverSpec, DampingSpec, PrecondSpec, EstimatorSpec → Assembler → Planner → (Lane, StepInfo plan) → Executor (JIT‑compiled step) → integrates with Optax transformations.

**Critical path**:  
1. Create component specs (or use `somax.make` preset).  
2. Call `somax.assemble(specs)` to run assembler and planner; receive a `SecondOrderMethod` with compiled step.  
3. Initialize once: `state = method.init(params)`.  
4. Train: repeatedly call `params_next, state_next, info = method.step(params, batch, state, rng)`.

**Design tradeoffs**:  
- *Lane selection*: diagonal lane cheap but crude; parameter‑space scales with parameter count \(d\); row‑space scales with batch size \(b\) and needs row primitives. Optimal lane depends on model size and batch regime.  
- *Planning overhead*: One‑time compilation cost is amortized; over‑specialization may reduce code reuse across configurations.  
- *Telemetry cadence*: Computing probes (e.g., gain‑ratio) every step increases step time by >50 % (Section 3.4); sparse cadence reduces overhead but delays control signals.

**Failure signatures**:  
- *Assembly error*: Incompatible specs (e.g., row solver with curvature lacking row primitives) raise immediate validation exception.  
- *Numerical divergence*: Bad damping/preconditioner combination (e.g., square‑gradient preconditioner + trust‑region) leads to stagnation or instability (Table 4).  
- *Performance regression*: Lane mismatched to model/batch regime drastically increases step time (Section 4.2).  
- *Probe overhead*: Expensive post‑update probes (every step) dominate step time; cadence gates mitigate but do not eliminate cost.

**First 3 experiments**:  
1. Probe overhead measurement (Section 3.4, Table 3): Sweep `rho_every_k` for `NewtonCG` in parameter‑space lane; report median/p90 step time.  
2. Lane scaling analysis (Section 4.2, Figure 2): Synthetic regression with MLP; vary hidden width (fixed batch) or batch size (fixed width); compare parameter‑space (SGN) vs row‑space (EGN) step times.  
3. Module interactions ablation (Section 4.3, Table 4): Train on Fashion‑MNIST with SGN base; vary damping (constant/trust‑region), CG budget, and diagonal preconditioning; measure time to 85 % test accuracy and final accuracy.

## Open Questions the Paper Calls Out
- **Multi-device distributed training**: The paper identifies this as the main systems extension. It remains unresolved because the single‑accelerator design does not address parameter/optimizer‑state sharding, communication‑aware lane placement, or collective operations for curvature statistics. Evidence needed: a distributed implementation demonstrating weak/strong scaling.
- **Structured preconditioners**: Integrating Kronecker‑factored or tensor‑axis methods into the modular API without performance loss is open. Their complex memory layouts and update schedules may conflict with static planning. Evidence needed: implementations of K‑FAC and Shampoo as Somax modules evaluated on large models, showing no overhead relative to specialized versions.
- **Quasi‑Newton methods**: Mapping quasi‑Newton updates (e.g., L‑BFGS) to Somax’s preconditioner contracts while preserving planning guarantees is unclear. Time‑dependent low‑rank corrections may break static plans or cadence‑gated telemetry. Evidence needed: an L‑BFGS module in the diagonal lane that respects cadence limits and matches convergence/wall‑clock performance of a monolithic L‑BFGS implementation on non‑convex deep learning tasks.

## Limitations
- Missing exact hyperparameters (learning rates for ablation studies) and random seeds hinders precise replication.
- Assumption that module requirements are static; dynamic cadence or data‑dependent statistics would break the static planning model.
- Lack of guidance on which execution lane to choose for new model architectures.
- Cadence‑gated probes still incur significant overhead (>50 % when computed every step), limiting practical use.

## Confidence
- Static planning reduces per‑step overhead by eliminating redundant recomputation: **High**
- First‑class modular design enables systematic recombination and controlled ablation: **Medium**
- Execution lane fundamentally changes scaling behavior: **High**
- Solver performance is strongly coupled to damping and preconditioning choices: **Medium**
