# Formal Semantics for Agentic Tool Protocols: A Process Calculus Approach

## Quick Facts
*   **arXiv ID:** 2603.24747
*   **Source URL:** https://arxiv.org/abs/2603.24747
*   **Reference Count:** 5
*   **Primary Result:** Establishes a formal foundation for LLM agent tool protocol safety by proving structural bisimulation between SGD and MCP under a mapping Φ, identifying five necessary/sufficient schema design principles (formalized as MCP+), and proving that security properties like capability confinement are process invariants.

## Executive Summary
This paper provides the first rigorous formal semantics for two dominant LLM agent tool protocols, Schema-Guided Dialogue (SGD) and the Model Context Protocol (MCP), using the π-calculus. It proves that SGD and the base MCP are forward-structurally bisimilar via a syntactic mapping Φ, meaning any observable agent execution in one protocol has a matching execution in the other. However, the reverse mapping is partial and lossy due to MCP's missing expressivity. The authors identify five precise schema design principles (semantic completeness, explicit action boundaries, etc.) that are both necessary and sufficient to close these gaps. By extending MCP with metadata enforcing these principles (creating MCP+), they prove full behavioral equivalence (isomorphism) with SGD. Finally, they encode key security constraints directly into the process calculus, demonstrating that properties like capability confinement and approval ordering can be formally verified as invariants.

## Method Summary
The authors construct labeled transition systems (LTSs) for SGD and MCP using π-calculus syntax and operational semantics. They define a forward mapping Φ from SGD processes (Intent, Slot, Execute) to MCP processes (Tool, JSON Schema, ToolCall) and prove SGD ∼ MCP by constructing a symmetric bisimulation relation R. They then define a reverse mapping Φ⁻¹ and demonstrate its partiality through counterexamples (e.g., MCP's `Resource` and `Prompt` primitives, missing `is_transactional` flag). To achieve full equivalence, they formalize five schema design principles as typing rules (P1–P5) that extend MCP with metadata fields (MCP+), proving that with these extensions, the combined mapping Φ⁺ becomes a bijection (MCP+ ∼= SGD). Security properties are encoded by structuring processes to enforce specific channel usage and sequencing, then proved as invariants via type-based reasoning.

## Key Results
*   **Forward Bisimulation:** SGD and MCP are structurally bisimilar (SGD ∼ MCP) under the mapping Φ, aligning core actions (invoke/call, execute, result/error) despite MCP's silent validation step.
*   **Five Design Principles:** The principles (semantic completeness, explicit action boundaries, failure documentation, progressive disclosure, inter-tool relationships) are formally necessary and sufficient to achieve full behavioral equivalence between MCP+ and SGD.
*   **Provable Safety:** Key security properties—capability confinement, tool-poisoning prevention, approval ordering, and dependency ordering—are formalized as process invariants within the π-calculus semantics of MCP+.

## Why This Works (Mechanism)
**Mechanism 1: Forward Bisimulation via Silent Alignment**
The paper defines operational semantics for both protocols and constructs a relation R = {(S, Φ(S))}. It proves R is a bisimulation by structural induction, showing that for every SGD transition (e.g., `collect`), there is a corresponding MCP sequence (e.g., silent `validate` τ-action followed by `call`). The core assumption is that MCP's JSON validation subsumes SGD's explicit slot-checking as a silent step. The proof holds because the observable actions are aligned (Def 4.2). It would break if SGD required explicit multi-turn slot collection with no single-validation MCP counterpart.

**Mechanism 2: Full Equivalence via Metadata Gaps**
Bidirectional analysis shows Φ⁻¹ is partial and lossy, identifying gaps like missing `is_transactional` and MCP's `Resource`/`Prompt`. The five principles are formalized as type-system rules (P1–P5) that add metadata (e.g., `requires_approval` for P2, `dependencies` for P5). The isomorphism proof (Thm 7.1) shows Φ⁺ becomes a bijection when these fields are present. Removing any principle breaks the bijection by leaving a semantic gap unrecoverable in the reverse direction.

**Mechanism 3: Security as Process Invariants**
Security constraints are encoded directly into process structure. For example, a write-capable tool must receive an `approval` message on a restricted channel before executing. Invariants are proved by tracing all possible transitions from the initial state, leveraging π-calculus scoping (ν) and the type system to enforce ordering and confinement. The proofs depend on the invariant properties being syntactically manifest in the process definition.

## Foundational Learning
*   **π-calculus structural operational semantics:** Needed to define how processes (Intent, Tool) evolve via labeled transitions and to state/prove bisimulation. Quick check: In MCP's `Validate` step, the τ (silent) action absorbs slot-checking; the observable label is the subsequent `call`.
*   **Schema-guided dialogue vs. MCP primitives:** Needed to understand the mapping Φ. SGD uses `Intent` with slots; MCP uses `Tool` with JSON schema plus extra `Resource`/`Prompt`. Quick check: MCP's `Resource⟨uri,content⟩` has no SGD equivalent—this is a gap Φ⁻¹ cannot handle.
*   **Type systems for protocol safety:** Needed to see how "schema quality" (Principle 1) and "action boundaries" (Principle 2) become mechanically enforceable. Quick check: The rule `meta.side_effects ∈ {write,delete} → meta.requires_approval = true` enforces Principle 2 (Explicit Action Boundaries).

## Architecture Onboarding
**Component Map:**
SGD Intent → Φ → MCP Tool → Type Checker (P1–P5) → MCP+ Tool → Φ⁺→ (Φ⁺)⁻¹ → Bisimilar SGD Intent; Security Invariants extracted from MCP+ process structure.

**Critical Path:** To add a verified tool: (a) Define SGD intent with slots and `is_transactional`; (b) Map to MCP+ Tool with full metadata; (c) Type-check metadata; (d) The resulting process is bisimilar to the SGD intent and satisfies security invariants.

**Design Tradeoffs:**
*   *Expressivity vs. Simplicity:* Base MCP chose simplicity (no `is_transactional`) at cost of safety; MCP+ restores safety via richer metadata.
*   *Token Efficiency:* Principle 4 trades richer descriptions for token cost, formalized as a scaling bound but not a type-level invariant.
*   *Static vs. Dynamic:* The calculus assumes static schemas; dynamic evolution is out-of-scope.

**Failure Signatures:**
*   `Φ⁻¹` undefined: Tool uses `Resource`, `Prompt`, or `Initialize`.
*   Type violation: `sem_density(desc) < τ` (P1), or write tool lacks `requires_approval=true` (P2).
*   Bisimulation break: A tool dependency (P5) is not encoded as a channel handoff, violating dependency ordering.

**First 3 Experiments:**
1.  **Forward Bisimulation Test:** Formalize a `transfer_funds` SGD intent (slots: `from`, `to`, `amount`; `is_transactional=true`). Map to MCP Tool. Verify that an `invoke` with missing `amount` yields an error in both LTSs (MCP via `validate` τ-failure).
2.  **Reverse Mapping Gap:** Take an MCP Tool without `requires_approval`. Show `Φ⁻¹` produces `Intent⟨·,·,·,·,?⟩` (lost transactionality). Add `requires_approval=true` and re-map—now `Φ⁺` is bijective.
3.  **Dependency Ordering:** Create `create_order` and `process_payment` tools with `process_payment.dependencies = [("create_order", Requires)]`. Encode `create_order` sending a `done` signal on a `requires` channel; `process_payment` blocks on receive before `execute`. Trace all valid executions to confirm `create_order` always precedes `process_payment`.

## Open Questions the Paper Calls Out
*   **Open Question 1:** Can the bisimulation proofs be fully mechanized in a proof assistant to eliminate human error?
*   **Open Question 2:** How can the framework be extended to reason about probabilistic tool selection, given LLMs' stochastic outputs?
*   **Open Question 3:** Can global safety properties (deadlock freedom, resource exclusivity) be verified compositionally from locally type-checked agents in multi-agent choreographies?
*   **Open Question 4:** Can token-efficiency constraints (Principle 4) be enforced as type-level invariants rather than informal guidelines?
*   **Open Question 5:** Does schema evolution (versioning, deprecation) preserve behavioral equivalence between SGD and MCP+?

## Limitations
*   **Expressivity Assumption:** The claim that five principles are *sufficient* assumes they capture *all* semantic gaps; other subtle differences might exist.
*   **Token Efficiency:** Principle 4 is a coarse token bound, not a compositional type invariant; violations remain undetectable at type-checking time.
*   **Static Schemas:** The model treats tool schemas as immutable; dynamic updates could break bisimulation and invariants.

## Confidence
*   **Forward Bisimulation (SGD ∼ MCP): High Confidence.** The proof uses a well-defined symmetric relation R and accounts for silent steps; the break condition is clearly identified and addressed.
*   **Five Principles are Necessary & Sufficient (MCP+ ∼= SGD): Medium Confidence.** The reverse mapping analysis rigorously identifies gaps filled by the principles, but sufficiency depends on the exhaustive identification of all expressivity differences.
*   **Security Invariants as Provable Properties: Medium Confidence.** The encoding of constraints into process structure is sound within the calculus, but these are novel formalizations of informal safety concepts; real-world adequacy requires empirical validation.
