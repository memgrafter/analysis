# TharuChat: Bootstrapping Large Language Models for a Low-Resource Language via Synthetic Data and Human Validation

## Quick Facts
- **arXiv ID:** 2603.17220
- **Source URL:** https://arxiv.org/abs/2603.17220
- **Reference count:** 13
- **Primary result:** Fine-tuning a 3B-parameter model on 3,116 synthetically generated, human-validated Tharu samples reduces validation perplexity from >88 (base) to 2.88, demonstrating effective override of Hindi bias on consumer-grade hardware.

## Executive Summary
This paper addresses the exclusion of Tharu, a low-resource Indo-Aryan language with multiple dialects and no existing digital corpus, from LLM advancements. The authors introduce the TharuChat dataset, built via an "LLM-to-Human" bootstrapping pipeline: Gemini models generate synthetic instruction-response pairs using prompt-engineered grammar and folklore, followed by native speaker validation to correct Hindi-fication and dialect mixing. A LLaMA-3.2-3B model fine-tuned with LoRA on this dataset achieves a dramatic perplexity reduction (from >88 to 2.88) as training data scales, proving that small volumes of verified synthetic data can override high-resource language biases. The entire pipeline is designed to run on a single NVIDIA T4 GPU, offering a practical path for linguistic inclusion of low-resource languages.

## Method Summary
The task is to fine-tune a small LLM for Tharu using a synthetically generated dataset. The TharuChat dataset comprises 3,116 training and 390 validation instruction-response pairs. The base model is Meta-Llama-3.2-3B-Instruct. Fine-tuning employs LoRA with rank r=16, alpha α=32 (scale 2), applied to all linear layers (`q_proj`, `k_proj`, `v_proj`, `o_proj`, `gate_proj`, `up_proj`, `down_proj`). Training runs for 3 epochs with an effective batch size of 16 (batch size 2, gradient accumulation 8), fp16 precision, AdamW optimizer, learning rate 2e-4 with linear decay and 3% warmup, and dropout 0.05. Hardware is a single NVIDIA T4 GPU (16GB VRAM). Evaluation uses validation perplexity and qualitative inference with deterministic sampling (temperature=0.3, top_k=15, top_p=0.3, repetition_penalty=1.2, max 100 new tokens).

## Key Results
- Validation perplexity decreases linearly with training data: 6.42 (25%, 779 samples), intermediate values at 50% and 75%, to 2.88 (100%, 3,116 samples), down from base perplexity >88.
- Qualitative examples show the fine-tuned model correctly uses Tharu morphosyntactic features (e.g., "-lehi" conditional marker, "nikalat haen" plural form).
- The complete pipeline (synthetic data generation, human validation, LoRA fine-tuning) is achievable on a single consumer-grade NVIDIA T4 GPU.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** A human-in-the-loop synthetic data pipeline can generate functionally useful training data for a low-resource language with no existing digital corpus.
- **Mechanism:** A high-capacity multilingual model (Gemini) is prompt-engineered with grammatical rules and folklore to generate dialect-mixed instruction-response pairs. Native speakers then validate and correct the output, converting raw model bias ("Hindi-fication") into a "silver-standard" corpus that reflects real-world linguistic heterogeneity.
- **Core assumption:** The teacher model possesses latent knowledge of related linguistic structures (via shared Indo-Aryan roots and Devanagari script) that can be elicited and corrected through targeted prompting and human filtering, bypassing the need for native-scale pre-training.
- **Evidence anchors:**
  - [abstract]: "constructed via an 'LLM-to-Human' bootstrapping pipeline using prompt-engineered Gemini models to generate synthetic, mixed-dialect instruction-response pairs, followed by human validation."
  - [section III.A]: Details the three-phase pipeline (Grammar Injection, Domain Elicitation, Human Validation) and lists specific corrections (Hindi-fication, dialect confusion).
  - [corpus]: Neighbor papers like "NagaNLP" and "Bootstrapping Embeddings for Low Resource Languages" validate the broader methodological trend of using LLMs as elicitors, but the specific validation loop and dialect-mixing strategy are novel to *TharuChat*.
- **Break condition:** If the teacher model's linguistic priors are too distant from the target language (e.g., non-Indo-Aryan, non-Devanagari), the context-loading phase would fail to produce coherent seed structures, making correction intractable.

### Mechanism 2
- **Claim:** A small volume of verified, syntactically dense examples can override a base model's strong high-resource language biases and achieve functional fluency.
- **Mechanism:** Parameter-Efficient Fine-Tuning (LoRA) with a high adapter rank (r=16) and scaling (α/r=2) aggressively updates the model's feed-forward and attention layers. This forces the model to reassign probability mass from dominant Hindi token sequences to the Tharu-specific morphology and syntax present in the small, curated dataset.
- **Core assumption:** The base model (LLaMA-3.2-3B) already contains the necessary tokens and conceptual primitives (via its multilingual pre-training) but has incorrect conditional probabilities for Tharu sequences; fine-tuning acts as a "re-alignment" rather than a full knowledge acquisition.
- **Evidence anchors:**
  - [abstract]: "small volumes of verified synthetic data can effectively override high-resource language biases."
  - [section V.B & Figure 1]: The linear reduction in validation perplexity from >88 to 2.88 as data scales from 0% to 100% demonstrates a strong dose-response relationship between Tharu example density and model fluency.
  - [section IV.B]: The choice of "all linear layers" and high α/r explicitly targets the model's internal syntax-processing pathways to combat Hindi priors.
- **Break condition:** If the base model had zero exposure to Tharu vocabulary or script (e.g., a monolingual English model), perplexity would not drop linearly; it would plateau at a high value regardless of data volume, as the token space itself would be missing.

### Mechanism 3
- **Claim:** A 3B-parameter model fine-tuned with LoRA is sufficient to capture the core morphosyntactic complexity of Tharu and can be deployed on consumer-grade hardware (NVIDIA T4).
- **Mechanism:** The 3B scale provides a minimal sufficient capacity for modeling Tharu's verbal morphology and honorific systems. LoRA reduces the trainable parameter count to ~0.1% (for r=16), drastically lowering memory (VRAM) and compute requirements, enabling training on a single 16GB GPU via gradient accumulation.
- **Core assumption:** Tharu's grammatical complexity, while distinct from Hindi, does not require the vast parameter count of a 70B model for basic instruction-following; the inductive biases of the pre-trained LLaMA-3.2 architecture are adaptable with targeted updates.
- **Evidence anchors:**
  - [abstract]: "achievable on consumer-grade hardware."
  - [section IV.A]: Explicitly states the 3B class was chosen as a "sweet spot" for deployment on T4 GPUs, and section IV.B details the fp16, batch size 2, grad accumulation 8 configuration that makes it fit.
  - [section VI.B]: Qualitative examples (e.g., correct use of "-lehi" conditional marker, "nikalat haen" plural form) show the 3B model captures key morphological features.
- **Break condition:** If Tharu required modeling exceptionally long-range dependencies or a vastly larger vocabulary than present in LLaMA's tokenizer, the 3B model would underfit even with 100% data, and validation loss would not decrease below a higher threshold (e.g., >4.0).

## Foundational Learning

- **Concept:** **Parameter-Efficient Fine-Tuning (PEFT) / LoRA**
  - Why needed here: The entire hardware accessibility claim rests on using LoRA to avoid full fine-tuning. An engineer must understand that only low-rank matrices (A, B) are trained, while W0 is frozen, to grasp the memory savings.
  - Quick check question: If you double the LoRA rank `r` while keeping `α` constant, what happens to the number of trainable parameters and the potential influence of the new task?

- **Concept:** **Perplexity as a Primary Evaluation Metric for Language Models**
  - Why needed here: The paper's core quantitative result is a perplexity reduction. An engineer must know that perplexity is the exponential of cross-entropy loss and measures how well the model's predicted probability distribution matches the true next-token distribution.
  - Quick check question: Why is a validation perplexity of 2.88 considered good for this context, even though it is higher than typical perplexities for English on large models?

- **Concept:** **The "Curse of Multilinguality" in Multilingual Pre-training**
  - Why needed here: The mechanism for failure (base model >88 PPL) is explained by the dilution of Tharu representation in a model trained on predominantly Hindi/English data. An engineer needs this context to understand why fine-tuning is necessary.
  - Quick check question: In a model like XLM-R, what happens to the representation quality for a low-resource language as you add more high-resource languages to the pre-training corpus?

## Architecture Onboarding

- **Component map:**  
  Data Synthesis Engine (Gemini 2.5 Pro) -> Human Validation Loop (native speakers) -> Fine-Tuning Engine (LLaMA-3.2-3B with LoRA) -> Hardware/Orchestration (single NVIDIA T4) -> Evaluation Harness (validation perplexity, qualitative inference)

- **Critical path:**  
  Grammar/Folklore Docs -> Prompt Engineered Gemini Generation -> Human Validation & Cleaning -> TharuChat Dataset -> LoRA Fine-Tuning (Config: r=16, α=32) -> Tharu-LLaMA -> Perplexity Evaluation & Qualitative Testing

- **Design tradeoffs:**
  - **Dialect Purity vs. Generalization:** Mixed-dialect (70% Rana) corpus maximizes coverage, trading off pure-dialect performance for broader "Pan-Tharu" utility.
  - **Model Size vs. Accessibility:** 3B selected over 8B/70B to meet T4 constraint, accepting potentially lower reasoning capacity for deployability.
  - **Synthetic "Silver" vs. "Gold" Standard:** Accepted residual noise (code-mixing, Awadhi traces) as the cost of creating any sizable dataset at all, prioritizing existence over perfection.

- **Failure signatures:**
  - **High Perplexity (>5.0) on 100% data run:** Indicates fundamental mismatch—likely LoRA configuration too weak (r too low, α too low), dataset not cleaned sufficiently, or base model incompatible.
  - **Training Loss ↓ but Validation Loss ↑:** Classic overfitting to the small synthetic set; need to increase dropout (currently 0.05) or reduce LoRA rank/alpha.
  - **Persistent Hindi-fication in outputs:** Human validation was insufficient; the model hasn't learned Tharu-specific syntax. Requires more aggressive LoRA targeting or more/different data.
  - **CUDA Out-of-Memory on T4:** Check precision (`fp16`), effective batch size (2*8=16), and that all optimizer states are using 16-bit. Might require gradient checkpointing.

- **First 3 experiments:**
  1. **Replicate Ablation Study:** Train the exact LoRA config (r=16, α=32) on 25%, 50%, 75%, 100% of the provided `prajwal-panth/tharu-chat` dataset. Verify the linear perplexity drop matches Table I. This validates the core scaling law claim and your setup.
  2. **Dialect Robustness Probe:** Take a prompt in Dangaura Tharu (e.g., from the 20% dataset subset) and evaluate if the model's response uses Dangaura or Rana morphology. Quantify the switch rate. This tests the "Pan-Tharu" generalization claim and identifies dialect inconsistency.
  3. **Hardware Constraint Stress Test:** Intentionally try to train the 8B LLaMA variant with the same LoRA config on the T4. Document the exact failure point (OOM during optimizer step, during forward pass?). This concretely demonstrates why the 3B choice was mandatory for the stated hardware constraint.

## Open Questions the Paper Calls Out

1. **How can dialectal inconsistency in mixed-dialect training be mitigated while preserving broad linguistic coverage for low-resource languages?**  
   Basis: Inferred from Section VII.A, which identifies dialectal noise and inconsistency as a key limitation due to mixing Rana, Dangaura, and Kochila dialects.  
   Why unresolved: Authors accept inconsistency as a trade-off for coverage but propose no concrete mitigation strategies.  
   What evidence would resolve: Comparative experiments with separate dialect adapters, hierarchical dialect modeling, or controlled mixing ratios evaluated through dialect-specific perplexity and human intelligibility tests.

2. **To what extent does residual high-resource language bias (Hindi/Awadhi) persist in synthetically generated low-resource language data after human validation, and what training modifications can reduce it?**  
   Basis: Explicit in Section VII.B: residual Awadhi/Hindi influence remains due to teacher model's priors.  
   Why unresolved: Paper acknowledges issue but does not investigate methods to further purify data or adjust training.  
   What evidence would resolve: Bias-detection metrics (grammatical structure analysis, code-switching rates) before and after interventions like adversarial training or alternative prompts.

3. **Can a model fine-tuned on a small, domain-specific low-resource dataset generalize to unseen domains without large-scale additional data?**  
   Basis: Explicit in Section VII.C: model limited to trained domains (agriculture, civics, culture) and fails on out-of-distribution topics.  
   Why unresolved: Paper does not explore domain expansion techniques.  
   What evidence would resolve: Zero-shot/few-shot evaluations on diverse domains, possibly with synthetic data augmentation, measuring hallucination rates and semantic coherence.

4. **Does a "pan-dialect" model trained on mixed data provide greater practical utility for linguistically diverse low-resource languages compared to separate dialect-specific models?**  
   Basis: Inferred from Section VIII.A hypothesis that mixed dialects create an intelligible koine, but no comparative evaluation.  
   Why unresolved: Mixed-dialect training suggested as viable but not tested against dialect-specific models or speaker preferences.  
   What evidence would resolve: User studies with speakers of different dialects comparing mixed vs. dialect-specific models for comprehension, acceptability, cultural authenticity, alongside objective metrics like dialect-specific perplexity.

5. **How does model parameter size interact with data scaling laws for extremely low-resource languages, and what is the minimum capacity needed to capture complex morphology?**  
   Basis: Inferred: paper uses 3B for hardware accessibility and demonstrates data scaling but does not vary model size.  
   Why unresolved: 3B choice pragmatic, not optimized; unclear if smaller/larger models achieve similar perplexity.  
   What evidence would resolve: Ablation training models of different sizes (1B, 3B, 8B) on identical TharuChat subsets, measuring perplexity, morphological accuracy, hardware requirements to define scaling laws.

## Limitations
- Synthetic data generation prompt templates and detailed human validation protocol (annotator expertise, guidelines, inter-annotator agreement) are unreported, hindering full reproducibility.
- The TharuChat dataset is small (3,116 samples) and uses a mixed-dialect approach, containing residual noise (Hindi-fication, code-mixing) and limiting dialect-specific performance.
- Evaluation is restricted to validation perplexity and a few qualitative examples; no downstream tasks or comparison to human-produced text; no ablation on model size.
