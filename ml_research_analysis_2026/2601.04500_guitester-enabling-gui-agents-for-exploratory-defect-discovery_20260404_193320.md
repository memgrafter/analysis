# GUITester: Enabling GUI Agents for Exploratory Defect Discovery

## Quick Facts
- **arXiv ID:** 2601.04500
- **Source URL:** https://arxiv.org/abs/2601.04500
- **Reference count:** 40
- **Primary result:** GUITester (UI‑TARS‑1.5‑7B) achieves 48.90% F1‑score (Pass@3) on GUITestBench, outperforming the best baseline (33.35% F1).

## Executive Summary
Exploratory GUI testing is hindered by two key limitations in current agents: goal‑oriented masking (agents prioritize task completion over defect reporting) and execution‑bias attribution (agents misclassify system defects as their own errors). To address these, the authors introduce GUITestBench, a benchmark with 143 tasks covering 26 real‑world defects, and propose GUITester, a multi‑agent framework that decouples navigation from verification. The Planning‑Execution Module (PEM) proactively embeds test intents to probe boundary behaviors, while the Hierarchical Reflection Module (HRM) uses full interaction history to accurately attribute anomalies. Evaluated on GUITestBench with UI‑TARS‑1.5‑7B, GUITester achieves a 48.90% F1‑score (Pass@3), a substantial improvement over the baseline (33.35% F1). The approach shows consistent gains in both defect‑oriented and exploration‑oriented tasks, with notable improvements on single‑action defects.

## Method Summary
GUITester is a modular multi‑agent framework comprising four roles: Planner, Executor, Monitor, and Reflector. The Planner (Qwen3‑VL‑Plus) receives the user goal and, using the interaction history, generates a sequence of subtasks that interleave navigation actions with defect‑probing test intents (e.g., alternative paths, boundary inputs, state validation). The Executor (UI‑TARS or GUI‑Owl) executes the current subtask’s actions. After each action, the Monitor (GPT‑4o) compares the expected post‑action state with the actual observation to classify the outcome as DONE (subtask complete), FAIL (anomaly detected), or CONTINUE. Upon FAIL, the Reflector (Qwen3‑VL‑Plus) performs a hierarchical analysis of the entire trajectory, using visual overlays of executed actions to distinguish whether the anomaly stems from a genuine GUI defect or an agent execution error. The Reflector’s attribution then triggers either a retry (if agent error) or a plan revision (if defect), closing the loop. No task‑specific fine‑tuning is applied; the framework relies on prompting pretrained models. Evaluation is conducted on the newly released GUITestBench benchmark, which includes 143 tasks across 12 Android applications with 26 real‑world defects. Tasks are split into defect‑oriented (explicit defect hints) and exploration‑oriented (pure navigation) settings. Performance metrics are F1‑score, Recall, and Precision, measured via Pass@1 and Pass@3. For multi‑action defects, a Claude‑4‑Sonnet judge compares reported defect traces against ground truth.

## Key Results
- Overall F1‑score (Pass@3): **48.90%** (UI‑TARS‑1.5‑7B), compared to best baseline **33.35%**.
- Consistent gains in both defect‑oriented and exploration‑oriented settings; baselines degrade sharply in exploration.
- Substantial improvements on single‑action defects (ONR, UTR, NLE), highlighting the benefit of embedded test intents.

## Why This Works (Mechanism)
### Mechanism 1: Proactive Defect Probing via Embedded Test Intents
- **Claim:** Decoupling navigation from verification allows agents to probe for defects without being masked by goal‑oriented behavior.
- **Mechanism:** The Planner interleaves navigation subtasks with test intents targeting boundary behaviors (alternative paths, edge‑case inputs, state validation), forcing exploration beyond the shortest completion path.
- **Core assumption:** Traditional MLLM agents follow success‑optimized paths that bypass defects; embedding testing intents increases defect exposure during navigation.
- **Evidence anchors:**
  - [abstract] "Planning‑Execution Module (PEM) that proactively probes for defects via embedded testing intents"
  - [section 4.1.1] "To increase the defect exposure, the Planner embeds test intents that guide the agent to explore boundary behaviors"
  - [section 5.2] "GUITester maintains relatively consistent performance across both settings" (Defect‑Oriented vs Exploration‑Oriented) while "baseline agents exhibit some detection capability in the Defect‑Oriented setting, their performance drops substantially in the Exploration‑Oriented setting"
  - [corpus] Weak direct evidence; neighboring papers focus on GUI testing benchmarks rather than defect probing mechanisms.
- **Break condition:** If defects are predominantly located on primary navigation paths rather than boundary conditions, or if agents already exhibit sufficient exploration without explicit prompting.

### Mechanism 2: Hierarchical Anomaly Attribution via Separate Monitor and Reflector
- **Claim:** Separating anomaly capture from attribution prevents both defect bypassing (via immediate termination) and misattribution (via full‑trajectory analysis).
- **Mechanism:** Monitor evaluates post‑action state to issue FAIL on anomalies without cause analysis; Reflector subsequently analyzes full interaction history with visual overlays to distinguish GUI defects from agent errors.
- **Core assumption:** Real‑time attribution causes bias toward self‑blame; hierarchical analysis with complete trajectory context enables accurate root‑cause identification.
- **Evidence anchors:**
  - [abstract] "Hierarchical Reflection Module (HRM) that resolves attribution ambiguity through interaction history analysis"
  - [section 4.2] "the Monitor observes...determines the execution state: ct ∈ {DONE,FAIL,CONTINUE}"; "the Reflector is responsible for attributing anomalies captured by the Monitor"
  - [section 4.2.2] "Visual Attribution: we visualize the Executor's actions on corresponding screenshots by marking interaction points...allows the Reflector to clearly identify whether the anomaly stems from ineffective operations or genuine defects"
  - [section 5.2] "agents either passively accept defective states or misattribute anomalies to their own execution errors"
- **Break condition:** If defects manifest as immediate, unambiguous states requiring no complex attribution, or if visual overlay proves insufficient for distinguishing subtle UX defects.

### Mechanism 3: Multi‑Agent Specialization for Defect‑Oriented Reasoning
- **Claim:** Differentiating responsibilities across Planner, Executor, Monitor, and Reflector enables each component to optimize for defect discovery rather than navigation success.
- **Mechanism:** Planner focuses on defect‑exposure strategies; Executor implements stable action policies; Monitor performs immediate state verification; Reflector conducts retrospective logical analysis—each with tailored prompting and objectives.
- **Core assumption:** Single‑agent systems trained for navigation success inherit biases that conflict with testing objectives; role separation constrains each agent to testing‑specific reasoning.
- **Evidence anchors:**
  - [section 4] "GUITester comprises two core modules... (i) a Planning‑Execution Module (PEM)... (ii) a Hierarchical Reflection Module (HRM)" and "The system consists of four agents: Planner, Executor, Monitor, Reflector"
  - [Table 1] GUITester with UI‑TARS‑72B achieves 43.70% F1 vs base 19.55%; GUITester with UI‑TARS‑1.5‑7B achieves 48.90% vs base 33.35%—improvements hold across different Executor backbones
  - [section 5.2] "current agents fail to meet this requirement due to task‑success bias inherited from their training objectives"
- **Break condition:** If a unified agent can be fine‑tuned or prompted to simultaneously achieve navigation and defect discovery without role conflict, eliminating coordination overhead.

## Architecture Onboarding
**Component map:**  
Planner (Qwen3‑VL‑Plus): Inputs: goal g, current observation o, history h, reflection feedback r. Outputs: decomposed subtasks {s1,...,sn} with embedded test intents.  
Executor (UI‑TARS/GUI‑Owl base): Inputs: current subtask s, current observation o, trajectory τ. Outputs: action a.  
Monitor (GPT‑4o): Inputs: subtask s, pre‑action state o_t, action a_t, post‑action state o_{t+1}. Outputs: state c_t ∈ {DONE,FAIL,CONTINUE}.  
Reflector (Qwen3‑VL‑Plus): Inputs: subtask s, full trajectory τ, history h. Outputs: attribution r (GUI_DEFECT or AGENT_ERROR) and plan revision feedback.  
Data flow: Planner → Executor → Monitor → (if FAIL) Reflector → Planner (with feedback). Shared observation sync at each loop.

**Critical path:**  
1. Planner decomposes user goal into navigation + test‑intent subtasks.  
2. Executor performs action for current subtask.  
3. Environment returns new state; Monitor classifies as DONE (subtask complete), FAIL (anomaly), or CONTINUE (proceed in subtask).  
4. On FAIL: Reflector analyzes full trajectory to attribute cause.  
5. If AGENT_ERROR and retries remain: Executor retries same subtask; else: Planner generates new plan (alternative path or next subtask).  
6. Loop until all subtasks complete or max steps reached.

**Design tradeoffs:**  
- Modularity vs. latency: Four specialized agents introduce coordination overhead but allow independent optimization; single‑agent alternatives would reduce latency but likely inherit navigation bias.  
- Prompt‑based vs. trained components: Uses off‑the‑shelf models with prompting rather than fine‑tuning, enabling flexibility but limiting domain adaptation.  
- Conservative vs. aggressive monitoring: Monitor issues FAIL on any mismatch; this increases recall but may cause false positives on slow‑loading states (Figure 13).  
- Test intent density: More test intents increase defect exposure but reduce navigation efficiency; paper does not specify optimal interleaving ratio.

**Failure signatures:**  
- Premature timeout: Slow network response triggers FAIL as ONR defect (Figure 13).  
- Domain ignorance: Monitor mispredicts expected states due to missing application‑specific knowledge (Figure 14: UFC→MMA navigation misjudged).  
- Action space limitation: Missing gestures (e.g., chart zoom) leave certain defects unexplored (section 7 limitation 3).  
- UX defect under‑detection: Subtle interaction flaws may not produce clear state mismatches; current Monitor relies on binary state comparison.

**First 3 experiments:**  
1. Baseline characterization: Evaluate raw UI‑TARS, GUI‑Owl, MAI‑UI on GUITestBench to establish their poor defect discovery (F1 <25%, Recall <20%) and confirm Goal‑Oriented Masking and Execution‑Bias Attribution in practice.  
2. Full system validation: Run GUITester with UI‑TARS‑72B and UI‑TARS‑1.5‑7B backbones to demonstrate significant improvement (F1 43.70% → 48.90%) and consistent gains across both defect‑oriented and exploration‑oriented tasks.  
3. Component isolation (implied): Ablate PEM or HRM to show their individual contributions; case studies (Appendix G) demonstrate PEM's boundary testing and HRM's accurate attribution in real‑world apps.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can exploratory GUI testing agents robustly distinguish environmental delays (e.g., network lag, page timeouts) from genuine GUI defects to minimize false positives and false negatives?
- **Basis in paper:** [explicit] The Limitation “The Wait‑or‑Miss Dilemma” (Section 7) states: “Distinguishing environmental delays from true anomalies remains an open challenge… The naive fix of ‘just wait longer’ creates its own problems.”
- **Why unresolved:** The current Monitor uses fixed timeouts (e.g., 3 seconds), leading to misclassification of slow‑loading states as defects, while also risking missed defects that manifest as fleeting glitches.
- **What evidence would resolve it:** An adaptive waiting mechanism that learns per‑action response distributions, detects loading indicators, or uses probabilistic modeling to differentiate delays from true non‑responsiveness.

### Open Question 2
- **Question:** How can the Hierarchical Reflection Module (HRM) be enhanced with domain‑specific knowledge to accurately attribute anomalies in applications with complex, non‑obvious navigation logic (e.g., subsidiaries like UFC under MMA)?
- **Basis in paper:** [explicit] Limitation “Monitor Capability Boundaries” (Section 7) notes: “The Monitor’s effectiveness is bounded by its domain knowledge… Integrating application‑specific knowledge or more capable vision‑language models could improve precision.”
- **Why unresolved:** The Monitor relies on general assumptions about expected UI states; lacking context about app‑specific relationships, it misjudges correct but unfamiliar navigations as defects.
- **What evidence would resolve it:** A knowledge‑augmented Monitor that retrieves from an app‑specific knowledge graph, fine‑tunes on the target app’s data, or consults documentation via retrieval‑augmented generation.

### Open Question 3
- **Question:** How can GUI agents be equipped with richer action primitives (e.g., multi‑touch gestures, zooming, pointer control) to explore a wider range of defect scenarios, especially in applications requiring advanced interactions?
- **Basis in paper:** [explicit] Limitation “Small Action Space, Narrow Testing Scope” (Section 7) explains: “Current GUI agents are equipped with action spaces designed for autonomous navigation… real‑world testing demands richer interactions… such capability gaps leave some defects unexplored.”
- **Why unresolved:** Standard GUI agent action spaces (click, type, swipe) omit gestures like zooming on charts or precise drags, preventing detection of layout or interaction bugs that require such inputs.
- **What evidence would resolve it:** Extended action space definitions, gesture macro libraries, or integration of vision‑language models that generate low‑level touch sequences from high‑level intents.

### Open Question 4
- **Question:** How can exploratory GUI testing be extended to detect visual and layout defects (e.g., overlapping elements, misaligned text, truncated labels) that do not involve functional anomalies?
- **Basis in paper:** [explicit] Limitation “Broader Defect Coverage” (Section 7) states: “GUIs can fail in other ways: overlapping elements, misaligned text, truncated labels. Expanding defect coverage to include such layout issues would enable more comprehensive quality assurance.”
- **Why unresolved:** GUITester focuses on interactive defects (ONR, UTR, NLE); layout problems require comparing rendered UI against design specifications or detecting rendering errors, which is outside its current scope.
- **What evidence would resolve it:** Vision‑based layout verifiers that compare UI screenshots to reference designs, pixel‑difference metrics for element consistency, or learning‑based models trained to flag visual distortions.

## Limitations
- **Major unknowns:** Exact APK versions, emulator configuration, and full system prompts for Planner/Monitor are unreported; Monitor’s expected‑state prediction logic and Judge settings are underspecified.
- **Evidence weakness:** Corpus shows weak direct evidence for the proposed mechanisms; neighboring work focuses on benchmarks rather than probing or attribution.
- **Reproducibility:** Unreleased code and logs hinder independent verification.
