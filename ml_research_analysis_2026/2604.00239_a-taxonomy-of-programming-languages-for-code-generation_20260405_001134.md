# A Taxonomy of Programming Languages for Code Generation

## Quick Facts
- **arXiv ID**: 2604.00239
- **Source URL**: https://arxiv.org/abs/2604.00239
- **Reference count**: 40
- **Primary result**: A four-tier taxonomy (High/Medium/Low/Scarce) of 646 programming languages based on 7.63 trillion tokens, revealing extreme resource imbalance where 12 High-resource languages (1.9%) account for 74.6% of tokens.

## Executive Summary
We introduce a systematic resource‑tier taxonomy for programming languages, addressing the lack of structured data on code availability. By merging and deduplicating seven major code corpora, we amass 7.63 trillion tokens across 646 languages. Using the StarCoder tokenizer, we classify languages into four tiers based on token counts: High (≥100B), Medium (10–100B), Low (1–10B), and Scarce (<1B). The results show a severe skew: only 12 languages (1.9%) fall in the High tier yet hold 74.6% of all tokens, while 463 languages (71.7%) are Scarce, contributing just 1.0%. Statistical analyses confirm the imbalance is systematic both across and within tiers, providing a principled foundation for dataset curation and multilingual code model evaluation.

## Method Summary
The taxonomy was built from seven permissively licensed code corpora: The Stack v2, RefineCode, StarCoder Data, The Heap, Project CodeNet, GitHub Code, and CodeSearchNet. First, all files were globally deduplicated using SHA‑256 hashes to remove exact duplicates. Each remaining file was then tagged with a programming language via GitHub Linguist, using a refined mapping to handle edge cases. The StarCoder tokenizer tokenized every file, and token counts were aggregated per language. Finally, the four tier thresholds were applied to these counts to produce the final classification.

## Key Results
- **Extreme concentration**: 12 High‑resource languages (1.9% of 646) hold 74.6% of tokens; 463 Scarce‑resource languages (71.7%) hold only 1.0%.
- **Systematic inequality**: Gini coefficients per tier (High=0.43, Scarce=0.66) and coefficient of variation for Scarce (1.37) show persistent skew within tiers.
- **Python dominance**: Python alone accounts for 1,543B tokens (20.2% of the corpus), exemplifying the “Python default” bias.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Merging and deduplicating seven major code corpora yields a unified, non‑redundant resource count that mitigates corpus‑specific biases.
- **Mechanism**: Exact deduplication via SHA‑256 hashes ensures each unique source file is counted once, preventing overrepresentation from overlapping datasets. This creates a consolidated baseline for token accounting.
- **Core assumption**: Unique file hashes adequately capture distinct code samples; duplicate removal does not discard semantically unique variants (e.g., minor formatting changes).
- **Evidence anchors**: [abstract] "merge and deduplicated seven major code corpora covering 646 languages"; [section 3.2] "S1 Merge and Deduplicate... dropping exact duplicates by comparing SHA‑256 hashes"; [corpus] Table 1 lists the seven corpora; post‑deduplication token total is 7.63T.
- **Break condition**: If significant near‑duplicate content (e.g., forked repositories) remains, token counts will be inflated, distorting tier boundaries.

### Mechanism 2
- **Claim**: Token counts from a code‑specific tokenizer provide a model‑aligned metric for resource availability, reflecting actual exposure during training.
- **Mechanism**: Uniform tokenization using the StarCoder tokenizer (trained on code) converts all files into tokens, producing counts proportional to the data a competitive Code LLM would encounter.
- **Core assumption**: The StarCoder tokenizer’s vocabulary and segmentation strategies are representative of mainstream Code LLM tokenizers; token volume correlates with learning signal strength.
- **Evidence anchors**: [abstract] "Using token counts from a code‑specific tokenizer"; [section 3.2] "S3 Token Accounting... with the StarCoder tokenizer... these counts serve as a faithful proxy for model exposure."; [corpus] Full taxonomy in Appendix A shows token counts per language; Python leads with 1,543B tokens.
- **Break condition**: If target models use substantially different tokenizers (e.g., byte‑level BPE), the proxy misaligns, potentially misranking languages.

### Mechanism 3
- **Claim**: Statistical dispersion metrics (Gini, CV) within tiers confirm that resource skew is systematic and persistent, not an artifact of tier thresholds.
- **Mechanism**: Calculating inequality measures per tier quantifies concentration; high Gini (e.g., 0.66 in Scarce) shows a few languages dominate even within low‑resource groups, while high CV indicates heterogeneous token distributions.
- **Core assumption**: Within‑tier statistical patterns reflect intrinsic data‑collection biases (e.g., popularity, tooling support) rather than random noise.
- **Evidence anchors**: [abstract] "Statistical analyses (Gini coefficients: High=0.43, Scarce=0.66; coefficient of variation: Scarce=1.37) confirm the skew is systematic"; [section 5] Figure 2a–c and accompanying analysis show right‑skew and dispersion in every tier; [corpus] Tier‑wise token distributions: Scarce tier (463 languages) hold only 1.0% of tokens but exhibit CV=1.37.
- **Break condition**: If tier definitions are drastically altered (e.g., different thresholds), within‑tier inequality may dissipate, suggesting thresholds rather than data drive the pattern.

## Foundational Learning
### Code‑specific tokenization
- **Why needed**: Token counts are the foundation of the taxonomy; understanding how code tokenizers differ from NLP tokenizers (e.g., handling symbols, whitespace) is crucial to interpreting resource metrics.
- **Quick check**: Why might a tokenizer trained on multilingual code (like StarCoder’s) produce different token counts per language compared to a generic text tokenizer, and how could that affect tier assignments?

### Resource tier adaptation from NLP
- **Why needed**: The taxonomy directly adapts Joshi et al.’s NLP framework; understanding its original categories (labeled/unlabeled data) clarifies why token volume alone is used for PLs and what nuances might be missing.
- **Quick check**: What are the limitations of using token counts as the sole criterion for resource tiers, compared to Joshi et al.’s multi‑dimensional (labeled/unlabeled) classification for natural languages?

### Inequality metrics (Gini, CV)
- **Why needed**: These metrics diagnose whether imbalance is concentrated in a few languages or pervasive; they guide whether interventions should target top‑heavy or long‑tail distributions.
- **Quick check**: How would you interpret a tier with a Gini coefficient of 0.43 versus 0.66 in terms of data collection strategies for underrepresented languages?

## Architecture Onboarding
### Component map
- corpus_loader: Fetches raw files from seven sources (Table 1).
- deduplicator: Computes SHA‑256 hashes, removes exact duplicates.
- pl_tagger: Maps file extensions to language IDs via GitHub Linguist rules.
- tokenizer_interface: Wraps StarCoder tokenizer for batch token counting.
- tier_assigner: Applies thresholds (≥100B, 10–100B, 1–10B, <1B) to aggregated counts.
- stats_analyzer: Computes Gini, CV, Lorenz curves, ECDFs per tier.
- taxonomy_exporter: Outputs ranked table (Appendix A) and tier summaries.

### Critical path
corpus_loader → deduplicator → pl_tagger → tokenizer_interface → tier_assigner → stats_analyzer

### Design tradeoffs
- *PL detection*: Extension‑based tagging is fast but error‑prone (e.g., `.h` files for C/C++/Objective‑C). Trade accuracy for scalability.
- *Tokenizer*: StarCoder aligns with current LLMs but may not match future tokenizers. Fixed thresholds are transparent but arbitrary; adaptive thresholds (e.g., percentiles) could reduce boundary sensitivity.
- *Corpus selection*: Permissive‑licensed corpora ensure reproducibility but exclude proprietary code, potentially underrepresenting enterprise languages.

### Failure signatures
- Unexpected spikes in token counts for a language (e.g., due to mis‑tagged configuration files).
- Tier assignments that place well‑known languages (e.g., Rust) in Low instead of Medium, indicating tokenization or deduplication bugs.
- Gini CV values near zero within tiers, suggesting overly homogeneous distributions—likely a processing error.

### First 3 experiments
1. **Deduplication validation**: Compare token counts before/after deduplication on a subset (e.g., The Stack v2). Expect ~5–10% reduction; larger reduction indicates high corpus overlap.
2. **Tokenizer sensitivity test**: Re‑run tokenization with two alternative code tokenizers (e.g., CodeLlama’s, GPT‑4’s). Measure rank correlation (Spearman’s ρ) of language token counts; ρ < 0.9 suggests tier instability.
3. **Tier boundary stress test**: Perturb thresholds by ±10% (e.g., Scarce < 1.1B) and record changes in language tier assignments. Languages near boundaries (e.g., Tier 1/2 cutoff at 10B) will flip; document which ones to assess robustness.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: How do different tokenization methods (beyond the StarCoder tokenizer used) affect the stability and thresholds of the proposed four‑tier taxonomy?
- **Basis in paper**: [inferred] The authors acknowledge in Limitations that their choice of a single tokenizer is a controlled methodological knob that may influence absolute token counts, though they argue it does not disturb the overall skew. They release raw counts to allow others to “swap tokenizers” and refine the taxonomy.
- **Why unresolved**: The paper does not empirically test how sensitive tier assignments are to tokenizer variations. Different code tokenizers (e.g., CodeBERT, GPT‑2) have varying vocabularies and subword strategies, which could shift languages across tier boundaries, especially near the 1B and 10B thresholds.
- **What evidence would resolve it**: Re‑tokenizing the entire deduplicated corpus with multiple state‑of‑the‑art code tokenizers, then computing the overlap and divergence in tier assignments. A high overlap would validate robustness; significant shifts would indicate the need for tier definitions that account for tokenizer choice.

### Open Question 2
- **Question**: To what extent does the inclusion of non‑permissively licensed, proprietary, or heavily filtered code data (e.g., removing boilerplate) alter the long‑tail distribution and tier boundaries?
- **Basis in paper**: [inferred] The authors use only permissively licensed data to respect licenses and privacy, noting in Ethical Considerations that this minimizes risks. Limitations also mention that design points like “heuristic tier cutoffs” are intentional for reproducibility but could be refined.
- **Why unresolved**: The current taxonomy is based on a specific, ethically constrained subset of public code. Incorporating broader, potentially non‑permissive or differently filtered corpora (e.g., internal enterprise code, more aggressive de‑duplication) might reveal a different resource landscape, possibly reducing or exacerbating the observed imbalance.
- **What evidence would resolve it**: Augmenting the merged corpus with additional datasets that have different licensing and filtering policies (e.g., a corpus of proprietary code with anonymized tokens, or a corpus with aggressive boilerplate removal), then recomputing the tier distribution and statistical measures (Gini, CV) to compare with the original.

### Open Question 3
- **Question**: Does constructing multilingual code benchmarks by systematically sampling languages across all four tiers (rather than selecting ad hoc popular languages) lead to more accurate and fair evaluations of Code LLMs' multilingual capabilities?
- **Basis in paper**: [explicit] The authors state that existing benchmarks (e.g., MultiPL‑E, HumanEval‑X) evaluate beyond Python but “select languages without accounting for training‑data availability.” Their taxonomy is presented as “the first framework to not only identify under‑resourced PLs but quantify the magnitude of that scarcity” to guide benchmark design.
- **Why unresolved**: The paper proposes the taxonomy as a tool for tier‑aware evaluation but does not validate whether using it to create balanced benchmarks changes model rankings or exposes weaknesses not captured by current evaluations. It remains an untested hypothesis that tier‑stratified selection improves assessment.
- **What evidence would resolve it**: Designing at least two benchmark versions: one using languages selected via the tier taxonomy (ensuring proportional representation from each tier) and one using languages from existing popular benchmarks. Evaluating a suite of Code LLMs on both and analyzing correlations between performance and tier resource levels, as well as assessor agreement on model quality across tiers.

### Open Question 4
- **Question**: Can targeted data balancing techniques (e.g., down‑sampling high‑resource languages, synthetic data generation for scarce ones) during Code LLM pre‑training mitigate the “Python default” bias without catastrophically degrading overall performance?
- **Basis in paper**: [explicit] The authors quantify the “Python default” phenomenon, noting Python holds 1,543B tokens (20.2% of corpus), and link training‑data composition to generation bias. They suggest the taxonomy “transforms ‘Python default’ from an anecdote into a measurable, tier‑level phenomenon.”
- **Why unresolved**: While the taxonomy identifies the cause (extreme token concentration), it does not explore remedies. The paper stops at providing a diagnostic framework, leaving open whether and how intervention in the data distribution can alter model behavior in a principled way.
- **What evidence would resolve it**: Conducting ablation studies in pre‑training: (a) a baseline model with original data distribution, (b) models with modified distributions (e.g., uniform token sampling across tiers, or up‑sampling Scarce‑tier data via augmentation), and (c) models with tier‑specific learning rates. Evaluate on: (i) bias metrics (e.g., default language rate under neutral prompts), (ii) performance on tier‑stratified benchmarks, and (iii) catastrophic forgetting on high‑resource tasks.

### Open Question 5
- **Question**: What specific data augmentation or synthetic generation techniques are most effective at improving Code LLM performance on Scarce‑tier programming languages, given their extremely limited natural code samples (<1B tokens)?
- **Basis in paper**: [inferred] The taxonomy reveals 71.7% of languages (Scarce tier) contribute only 1.0% of tokens. The authors note these “niche formats and DSLs are vital for real‑world tooling” and suggest “targeted scraping, augmentation, or synthetic generation could disproportionately benefit the most under‑served languages” based on the Scarce tier’s high coefficient of variation (1.37).
- **Why unresolved**: The paper identifies Scarce‑tier languages as critically under‑served but does not investigate which augmentation strategies (e.g., back‑translation, code morphing, few‑shot prompting with high‑resource languages) are viable or effective when starting from such a low base. It leaves a practical gap for researchers aiming to support these languages.
- **What evidence would resolve it**: A systematic study applying a range of augmentation techniques (e.g., translating high‑resource code to Scarce languages via LLMs, generating code from specifications, using code completion to expand snippets) to a sample of Scarce‑tier languages. Pre‑train or fine‑tune models on augmented data and evaluate on held‑out, authentic Scarce‑language code tasks to measure improvements in functional correctness and syntax compliance.

## Limitations
- **Corpus transparency**: Exact versions, download sources, and preprocessing states of the seven corpora are unreported, hindering exact replication.
- **Tokenizer dependency**: Tier thresholds are derived from StarCoder tokenizer counts; alternative tokenizers could reassign languages across tiers.
- **Tagging ambiguity**: Language identification relies on an undisclosed refined mapping of GitHub Linguist, risking misclassification of files with ambiguous extensions.
