# LLM-Driven Heuristic Synthesis for Industrial Process Control: Lessons from Hot Steel Rolling
## Quick Facts
- arXiv ID: 2603.20537
- Source URL: https://arxiv.org/abs/2603.20537
- Reference count: 32
- Primary result: The best synthesized heuristic achieves a 30% improvement in mean reward over the hand-coded baseline (55.5 vs 41.0) on eight search scenarios, while passing a comprehensive audit pipeline.

## Executive Summary
The paper tackles the challenge of developing interpretable and auditable control policies for industrial process control, using hot steel rolling as a demanding case study where black-box neural networks are undesirable. It presents an LLM-driven heuristic synthesis framework that automatically generates human-readable Python controllers, iteratively refining them through interaction with a physics-based simulator.

The core method employs a structured four-phase search loop (ideation, selection, implementation, evaluation) that provides rich per-component reward feedback to the LLM. A Luby-style universal restart strategy efficiently allocates the search budget across multiple independent runs. The best synthesized controller improves mean reward by 30% relative to a simple baseline (55.5 vs. 41.0) and successfully passes a 65-point automated audit, with Z3 formally verifying key safety and monotonicity properties. The work demonstrates that LLM-based synthesis can produce high-performance, verifiable policies for complex industrial tasks.

## Method Summary
The framework searches for a control policy in the space of readable Python functions. The environment is a physics-based simulator (PyRoll) wrapped as a Gymnasium interface; it exposes a state vector (thicknesses, grain size, temperature, force, torque, HR limit, step count) and an action mask. The search proceeds in outer iterations, each consisting of four phases: (1) Ideation – the LLM proposes three high-level strategy descriptions; (2) Selection – the most promising description is chosen; (3) Implementation – the LLM writes executable Python code via tool calling, with up to three repair attempts; (4) Evaluation – the code is run on eight predefined scenarios, returning a mean total reward and a detailed breakdown per reward component. The system adapts between refinement and radical exploration based on stagnation metrics. Between iterations, conversation memory can be compacted or synthesized. After completing a campaign (potentially using Luby’s restart schedule), candidate heuristics undergo a five-layer audit pipeline (AST checks, interval analysis, domain specs, Z3 SMT verification, and property-based testing). Finally, a portfolio builder selects the highest-performing auditable heuristic for deployment.

## Key Results
- Best heuristic improves mean reward by 30% over the hand-coded baseline (55.5 vs 41.0).
- A single 160-iteration Luby campaign (unit=5) approaches the hindsight-optimal reward distribution obtained from 730 iterations across 52 ad‑hoc runs, confirming the theoretical efficiency of universal restarts.
- The audit pipeline passes all 65 automated checks with zero errors; Z3 formally verifies safety and monotonicity for all valid inputs.

## Why This Works (Mechanism)
### Mechanism 1: Structured Four‑Phase Search Loop
The structured loop (ideation, selection, implementation, evaluation) with rich per-­component feedback enables rapid convergence to competent policies. The LLM first reasons in natural language, decoupling strategy from implementation. The chosen strategy is then encoded in Python. Evaluation returns a multi-dimensional reward breakdown across eight scenarios, allowing the LLM to diagnose weak components (e.g., “every scenario loses ∼2.0 points on temperature”) and target refinements. Adaptive modes (refinement, radical exploration) steer the search based on stagnation, and conversation management (compaction or synthesis) preserves context while controlling memory.

Core assumption: The LLM can correctly interpret the feedback and translate it into code changes.

Evidence: The abstract highlights “rich behavioral feedback” and the “structured four-phase search loop”. Section 2.2 details the phases and mode selection. Section 4.6 shows the evolution of LLM‑stated strategies.

Break condition: Misinterpretation of feedback or inability to propose viable fixes leads to stagnation. Observed issues include “radical departures… crashed with deeply negative rewards” and “conversation compaction causes amnesia” causing rediscovery of discarded strategies.

### Mechanism 2: Luby‑Style Universal Restarts
Luby‑style restarts automate near-optimal budget allocation without prior knowledge of run‑length distributions. A Luby schedule (e.g., 1,1,2,1,1,2,4,… scaled by unit u=5) defines a sequence of sub‑runs; each sub‑run starts with a fresh LLM conversation. The schedule is theoretically optimal for maximizing the best result when the distribution of first‑iteration rewards is unknown, balancing breadth (many fresh starts) and depth (longer sub‑runs). The value of a restart is the first‑iteration reward; additional iterations improve upon it.

Core assumption: The distribution of best‑so‑far rewards across independent runs is stable enough that a universal schedule approximates the optimal mixed allocation.

Evidence: The abstract states the Luby approach “approaches the hindsight‑optimal budget allocation”. Section 4.4 (Table 2, Figure 5) compares a 160‑iteration Luby campaign to an ad‑hoc optimal mix using 730 iterations. Figure 4 illustrates the first‑iteration vs. later‑iteration reward gains. Section 4.3 presents the optimal mixed‑allocation analysis.

Break condition: Highly skewed or heavy‑tailed reward distributions may render the constant‑factor guarantee far from the true optimum for a small fixed budget. The paper notes that the best ad‑hoc outlier (55.5) was not reached by the 160‑iteration Luby run.

### Mechanism 3: Five‑Layer Automated Audit Pipeline
The five‑layer pipeline ensures deployment assurance by combining static checks, interval analysis, domain specifications, Z3 SMT verification, and property‑based testing. It bridges human‑readable code with formal guarantees: (1) AST checks for structure and security; (2) interval analysis for output bounds; (3) domain‑spec compliance; (4) Z3 SMT for ∀‑quantified safety and monotonicity properties (using a two‑translation technique); (5) property‑based testing for complex numeric specs. This layered approach scales to realistic heuristics while providing strong evidence.

Core assumption: Heuristic code uses a restricted Python subset that permits translation to Z3 or exhaustive testing.

Evidence: The abstract mentions the “five‑layer automated audit pipeline… zero errors”. Section 4.8 describes all five layers, Table 4 reports 65 checks with 0 errors, and Figure 7 shows audit evolution. Appendix B details the Z3 translation and monotonicity proof.

Break condition: Heuristics that employ untranslatable constructs (e.g., np.argmin, array indexing) in core logic cause Z3 translation failures, deferring those specifications to property‑based testing, which is not exhaustive. Example: SPEC‑006 produced a Z3 counterexample at a degenerate boundary, though testing confirmed realistic validity.

## Foundational Learning
- **LLM‑driven iterative code synthesis**: The paradigm of treating the LLM as an iterative optimizer that refines code based on multi‑faceted feedback. *Why needed*: The entire framework hinges on the LLM’s ability to update a controller from reward decompositions and diagnostics. *Quick check*: How would you design the evaluation feedback to enable the LLM to fix a heuristic that performs poorly on grain size management but well on temperature?
- **Hot rolling metallurgy and process constraints**: Physical principles governing the rolling process (e.g., HR ≤ thickness−target, grain growth during interpass times). *Why needed*: The reward function, action space, and domain specs are grounded in metallurgy; generated policies must respect these to be viable. *Quick check*: Why is it metallurgically problematic if a heuristic chooses a very short interpass time when the grain size is below target?
- **Formal verification and property‑based testing for code**: Techniques for proving ∀‑properties (e.g., safety) with SMT solvers and testing ∃‑properties (e.g., responsiveness). *Why needed*: The audit pipeline relies on both to provide deployment assurance; understanding their trade‑offs is crucial. *Quick check*: What is the difference between proving SPEC‑004 (monotonicity) with the two‑translation technique and verifying SPEC‑007 (responsiveness) with property‑based testing?

## Architecture Onboarding
Component map (plain text):
FlatRollingEnv -> SearchLoop -> AuditPipeline -> PortfolioBuilder
LubyRunner manages multiple SearchLoop runs; HeuristicZ3Translator is used within AuditPipeline.

Critical path: For a new job specification, the entire pool of previously found heuristics is evaluated on the job, filtered by the audit pipeline, and the best (via portfolio selection) is deployed. The search/audit loop runs offline; deployment uses a lightweight simulation per job.

Design tradeoffs:
- Search depth vs. breadth: Long single runs risk mode collapse; many short runs explore more strategies. Luby’s schedule automates a balanced mix.
- Memory strategy: Compaction is cheap but can lose key insights (amnesia); synthesis (resetting with summaries) improves early convergence but may introduce sequential confounds.
- Audit thoroughness vs. cost: Z3 verification is fast but supports only a restricted Python subset; property‑based testing covers more specs but is not exhaustive. The pipeline defers some specs to testing.
- Seeding across Luby sub‑runs: Experiments show unseeded runs (best reward 51.6) outperformed seeded runs (48.3), suggesting seeding may reinforce local optima.

Failure signatures:
- Mode collapse: All strategies in a run converge to similar TMCP‑style architectures, failing to discover unconventional but effective mappings (e.g., decoupled controller).
- Radical exploration crashes: “Radical” prompts generate heuristics with catastrophically negative rewards (−79 to −88), indicating insufficient guidance for safe exploration.
- Audit warnings correlate weakly with reward: Even high‑reward heuristics may trigger division safety or domain‑spec warnings, showing audit is an orthogonal signal.
- Z3 translation failures: Occur when heuristics use np.argmin, array indexing, or complex NumPy operations in return logic, forcing reliance on property‑based testing for those specs.

First 3 experiments:
1. **Baseline reproduction**: Implement and evaluate the hand‑coded baseline controller; confirm it yields a mean reward of ~41.0 on the eight search scenarios.
2. **Single‑run search**: Execute a 10‑iteration search with compaction memory; track the best‑so‑far reward trajectory and verify early convergence (median ~40 by iteration 5); inspect a few heuristics for readability.
3. **Luby vs. uniform**: For a fixed budget of 100 iterations, compare (a) one continuous 100‑iter run, (b) ten independent 10‑iter runs, and (c) one Luby campaign (unit = 5). Plot cumulative best‑so‑far to demonstrate Luby’s near‑optimal mixing effect.

## Open Questions the Paper Calls Out
1. **What mutation operators can systematically explore alternative controller architectures to counteract mode collapse to TMCP paradigms?** The paper notes that radical exploration prompts often crash and no method exists to encourage viable but unconventional mappings (e.g., decoupled controller). Evidence to resolve: Implement candidate mutation operators (e.g., randomizing control variable assignments) and evaluate their impact on architectural diversity and best reward across runs.
2. **How can persistent cross‑run memory mitigate conversation amnesia and rediscovery of effective micro‑modifications?** The paper proposes persistent cross‑run memory; current compaction loses insights and synthesis memory (per‑iteration summaries) improved early convergence but sequential confounding remains. Evidence to resolve: Build a cross‑run knowledge store (e.g., embedding similar successful code snippets) and compare convergence speed and final reward between runs with and without persistent memory.
3. **Can the Z3 verifier be extended to formally prove array‑dependent specifications (e.g., responsiveness, continuity) currently deferred to property testing?** The audit pipeline defers four specs due to NumPy operations (np.where, np.argmin); future work calls for extending Z3 verification. Evidence to resolve: Enhance the AST‑to‑Z3 translation to handle array operations and successfully prove all 11 specifications on the best heuristic without falling back to testing.

## Limitations
- Missing implementation details: The exact `FlatRollingEnv` code and reward coefficients (step penalty, terminal bonuses) are not provided; reproduction must rely on reconstruction from the cited repository.
- LLM API specifics: Gemini 2.5 Pro tool‑calling interface, temperature, rate limits, and any proprietary optimizations are not open‑sourced, risking configuration drift.
- Audit scope limits: Z3 translation is limited to a restricted Python subset; heuristics using advanced NumPy operations defer specifications to property‑based testing, which is not exhaustive.
