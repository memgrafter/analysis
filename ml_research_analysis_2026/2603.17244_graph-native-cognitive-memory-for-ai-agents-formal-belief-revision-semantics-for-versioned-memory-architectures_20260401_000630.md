# Graph-Native Cognitive Memory for AI Agents: Formal Belief Revision Semantics for Versioned Memory Architectures

## Quick Facts
- **arXiv ID**: 2603.17244
- **Source URL**: https://arxiv.org/abs/2603.17244
- **Reference count**: 21
- **Primary result**: Graph-native cognitive memory with AGM belief revision mapping achieves state-of-the-art on LoCoMo (0.447 token F1, 97.5% adversarial refusal) and LoCoMo-Plus (93.3% judge accuracy), with 100% AGM compliance.

## Executive Summary
AI agents require persistent, structured memory for long-term reasoning, yet existing solutions lack unified architecture and formal grounding. Kumiho addresses this gap with a graph-native cognitive memory where primitives—immutable revisions, mutable tags, typed dependency edges, URI addressing—simultaneously serve asset tracking and map AGM belief revision to graph operations. It uses a dual-store design (Redis working memory, Neo4j long-term graph) and combines full-text and vector retrieval, enhanced by prospective indexing, event extraction, and client-side LLM reranking. A safety-hardened Dream State consolidates episodic memories.

On the LoCoMo benchmark, Kumiho achieves 0.447 four-category token F1 (highest reported) and 97.5% adversarial refusal accuracy. On LoCoMo-Plus, it attains 93.3% judge accuracy (98.5% recall) with GPT-4o-mini at ~$14 cost, beating Gemini 2.5 Pro by 47.6 points. The system demonstrates 100% AGM compliance across 49 scenarios and a model-decoupled architecture that allows swapping the answer model without pipeline changes.

## Method Summary
Kumiho ingests conversations via a memory_ingest tool, which creates graph items, revisions, tags, and typed dependency edges (e.g., Supersedes) in Neo4j. Redis holds working memory for low-latency access. Retrieval uses hybrid BM25 (full-text) and vector similarity (with text-embedding-3-small) via max fusion (β = 0.85) and graph-augmented traversal. Retrieved sibling revisions are filtered by embedding cosine similarity (threshold 0.30) and then presented to the answer model (GPT-4o or GPT-4o-mini), which selects the most relevant sibling and generates the final response. The Dream State runs asynchronously to extract events and generate prospective implications using an LLM, enriching revisions. Safety is maintained by a circuit breaker (max deprecation ratio 0.5) and protection of published items. Evaluation uses token-level F1 with Porter stemming on LoCoMo and an LLM judge on LoCoMo-Plus, with AGM compliance checked via a deterministic test suite.

## Key Results
- **LoCoMo**: 0.447 four-category token F1 (highest reported), 97.5% adversarial refusal accuracy, overall F1 0.565.
- **LoCoMo-Plus**: 93.3% judge accuracy (98.5% recall) with GPT-4o-mini at ~$14 cost, outperforming Gemini 2.5 Pro by 47.6 points.
- **Compliance & Decoupling**: 100% AGM compliance (49/49 scenarios); architecture is model-decoupled, allowing answer model swaps to improve end-to-end accuracy without pipeline changes.

## Why This Works (Mechanism)
The graph-native representation with immutable revisions and typed edges naturally encodes belief states and their dependencies, enabling AGM belief revision through graph operations (e.g., Supersedes edges for belief updates). The dual-store optimizes performance: Redis provides low-latency access to recent working memories, while Neo4j supports complex graph queries for long-term reasoning. Hybrid retrieval (BM25 + vector) captures both lexical and semantic matches, and graph traversal ensures contextual relevance. Client-side LLM reranking further refines results by comparing embedding similarities among sibling revisions. The Dream State consolidation enriches the memory graph with prospective implications (future scenarios) and extracted events, providing anticipatory and causal reasoning capabilities. Safety features like the circuit breaker and published-item protection maintain integrity during high-velocity updates.

## Foundational Learning

- **Graph-Native Memory**: Representing knowledge as a property graph with nodes (items, revisions), edges (typed dependencies), and properties (tags, timestamps). *Why needed*: Enables flexible modeling of versioned beliefs, their relationships, and metadata, supporting complex queries and audits. *Quick check*: Trace a revision’s history via Supersedes edges and explain how tags indicate mutability.
- **Hybrid Retrieval (BM25 + Vector)**: Combining lexical (BM25) and semantic (embedding similarity) search with max fusion. *Why needed*: Captures both exact keyword matches and conceptual similarity, improving recall and precision for diverse queries. *Quick check*: Explain the role of β (0.85) in weighting the two retrieval branches and how results are merged.
- **Dream State Consolidation**: Asynchronous process that extracts events and generates prospective implications using an LLM, updating the memory graph. *Why needed*: Enriches memory with causal and forward-looking knowledge, enabling reasoning about past events and future possibilities. *Quick check*: Describe the trigger for Dream State and how its outputs (events, implications) are stored in revisions.

## Architecture Onboarding
**Component Map**: User query → memory_recall → (Redis, Neo4j) → Hybrid Fusion → Sibling Filter (embedding ≥0.30) → Answer Model (GPT) → Response. Ingestion: Conversation → memory_ingest → Neo4j (items, revisions, tags, edges) → Dream State (async) → Enriched Revisions. Safety: Circuit breaker + published-item protection.

**Critical Path**: (1) memory_recall retrieves candidates and fuses results; (2) sibling filtering by embedding; (3) answer model selects sibling and generates response. Failure in any step breaks the pipeline.

**Design Tradeoffs**:
- Dual-store: Redis for speed vs. Neo4j for persistence; adds synchronization complexity.
- Hybrid retrieval: Doubles retrieval cost but improves coverage; β=0.85 favors precision.
- Client-side reranking: Adds latency but refines relevance.
- Graph-native: Flexible schema but may degrade with large graphs; requires indexing.
- Prospective indexing: LLM-generated scenarios enhance anticipation but incur cost and potential noise.

**Failure Signatures**:
- Missing prospective implications: Dream State errors or deprecation ratio >0.5 halts consolidation; check audit reports.
- Deprecated items retrieved: Verify queries exclude deprecated revisions (WHERE NOT item.deprecated).
- Sibling reranking anomalies: Log counts; zero or excess siblings may indicate threshold misconfiguration.
- Circuit breaker activation: Logs show >50% deprecation; may require tuning or manual review.

**First Experiments**:
1. Ingest a short known conversation via memory_ingest and inspect Neo4j to confirm items, revisions, tags, and edges.
2. Run memory_recall for a fact from the ingested conversation; verify hybrid returns both full-text and vector matches; check sibling filtering.
3. Manually trigger Dream State consolidation; confirm revisions gain prospective_implications and extracted_events; review audit report.

## Open Questions the Paper Calls Out
The paper does not explicitly dedicate a section to open questions or future work. However, based on the limitations and suggested next checks, the following questions arise for further investigation:
- How can the community overcome data accessibility barriers for LoCoMo and LoCoMo-Plus to ensure reproducible research?
- What are the exact prompts, parameters, and schemas for Dream State's prospective indexing and event extraction, and how sensitive is performance to these configurations?
- How does the choice of judge model and judging prompt affect LoCoMo-Plus accuracy, and can a standardized evaluation protocol be established?
- How does Kumiho scale with increasing graph size and conversation length, and what are the performance bottlenecks of the dual-store architecture?
- To what extent can the answer model be swapped across diverse LLMs without loss of performance, and what model characteristics are most compatible?

## Limitations
- **Data accessibility**: Official LoCoMo and LoCoMo-Plus datasets are not publicly available; reproduction requires direct request to the benchmark authors.
- **Dream State configuration**: The prompts, parameters, and schemas for prospective indexing and event extraction are unreleased, making it hard to match the reported enrichment quality.
- **Evaluation specifics**: The judge model and judging prompt used for LoCoMo-Plus are unspecified, so reported accuracy may not be directly comparable without these details.

## Confidence
- **LoCoMo benchmark (0.447 token F1, 97.5% adversarial refusal)**: **High** — The high token F1 and robust adversarial refusal are strongly supported by the reported numbers and align with the formal AGM compliance verification.
- **LoCoMo-Plus judge accuracy (93.3%)**: **Medium** — The judge model and judging prompt are unspecified (see Limitations), introducing uncertainty in comparability and reproducibility.
