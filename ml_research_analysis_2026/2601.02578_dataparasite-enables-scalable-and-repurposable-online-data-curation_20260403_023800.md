# DataParasite Enables Scalable and Repurposable Online Data Curation

## Quick Facts
- **arXiv ID:** 2601.02578
- **Source URL:** https://arxiv.org/abs/2601.02578
- **Reference count:** 0
- **Primary result:** DataParasite reduces online data curation cost to ~$0.09 per record (10x cheaper than human RAs) while achieving high accuracy and perfect repurposability on tested tasks.

## Executive Summary
DataParasite tackles the expensive and irreproducible manual curation of online data for computational social science. By introducing a modular pipeline defined by lightweight YAML configurations and a shared task-agnostic Python executor, the system allows new data collection tasks to be specified with minimal effort. Furthermore, repurposing is enabled through natural-language instructions to a coding agent, eliminating the need for predefined entity lists. Evaluations on faculty hiring records, Nobel death events, and US senator election trajectories show high accuracy, perfect performance on repurposed tasks, and a drastic cost reduction to approximately $0.09 per record. An ablation test disabling web search confirms that results rely on active retrieval, not model memorization.

## Method Summary
No reproduction notes were provided in the source summary. The method is described in the key outcome: DataParasite implements a modular pipeline where tasks are defined via YAML configurations and executed by a single task-agnostic Python script. Repurposing for new tasks is achieved by providing natural-language instructions to a coding agent, which adapts the pipeline without manual coding. The system actively retrieves current information via web search to ensure up-to-date and comprehensive data collection.

## Key Results
- Cost reduction: ~$0.09 per record vs. $0.66 for a human research assistant (an order of magnitude cheaper).
- High accuracy: perfect accuracy on both repurposed tasks (two examples) and strong performance on original tasks (faculty hiring, Nobel deaths, senator trajectories).
- Reliance on active retrieval: Disabling web search significantly degraded performance, confirming the system does not rely on memorized data.

## Why This Works (Mechanism)
DataParasite’s cost and accuracy stem from its modular, configuration-driven architecture. Tasks are specified in YAML, decoupling task definition from execution logic. A single Python script runs all tasks, reducing code duplication and maintenance overhead. The coding agent interprets natural-language instructions to modify or extend the pipeline on the fly, enabling rapid repurposing even for tasks without predefined entity lists. Finally, the integration of live web search ensures the system retrieves current information rather than depending on static training data, as validated by the ablation study. This combination of modularity, automation via an LLM agent, and active retrieval yields both scalability and adaptability.

## Foundational Learning
- **Modular pipeline design**  
  *Why needed:* Separates task specification from execution, allowing new tasks to be added without rewriting core code.  
  *Quick check:* Can a new task be incorporated by only editing the YAML config?

- **YAML configuration**  
  *Why needed:* Provides a lightweight, human-readable format for defining data fields, sources, and extraction rules.  
  *Quick check:* Is the config syntax easy to validate and modify by non-programmers?

- **Task-agnostic executor**  
  *Why needed:* A single Python script processes all YAML-defined tasks, reducing code complexity and ensuring consistency.  
  *Quick check:* Does the executor handle varying schemas and extraction logics transparently?

- **Coding agent (LLM-based)**  
  *Why needed:* Translates natural-language instructions into executable code or config adjustments, lowering the barrier for repurposing.  
  *Quick check:* Does the agent produce syntactically correct and semantically appropriate modifications?

- **Active web retrieval**  
  *Why needed:* Guarantees access to up-to-date information and avoids reliance on potentially stale model knowledge.  
  *Quick check:* Does disabling web search lead to a measurable drop in accuracy or coverage?

## Architecture Onboarding
**Component map:** User → YAML config + natural-language instruction → Coding Agent → Python script → Web Search → Output storage

**Critical path:**  
1. User defines a task in a YAML configuration file (specifying target entities, attributes, and sources).  
2. Optionally, user provides natural-language instruction to the coding agent to adapt the pipeline for the new task.  
3. The coding agent generates or modifies code/config as needed.  
4. The task-agnostic Python script parses the YAML, orchestrates web searches, extracts data, and stores results.  
5. Results are validated and output.

**Design tradeoffs:**  
- *Modularity vs. overhead:* YAML and a generic executor add abstraction layers, which may increase debugging complexity but greatly simplify adding new tasks.  
- *LLM reliance vs. cost/control:* The coding agent introduces dependence on external LLM APIs (cost, latency, error rates) but enables flexible repurposing.  
- *Active web retrieval vs. reliability:* Web search yields current data but introduces network failures, rate limits, and variable result quality.

**Failure signatures:**  
- Invalid YAML syntax or missing required fields.  
- Coding agent produces syntactically invalid or logically incorrect code.  
- Web search returns no results, times out, or provides irrelevant content.  
- Parsing stage fails to extract structured data from fetched pages.

**First three experiments:**  
1. **Baseline execution:** Run a simple extraction task with a provided YAML config (e.g., collect faculty names from university directories) to verify end-to-end functionality and accuracy.  
2. **Repurposing test:** Provide a natural-language instruction for a new task (e.g., “Extract dates of birth for these individuals”) and measure success rate in generating a working configuration/script.  
3. **Retrieval ablation:** Disable web search (use cached or static data) on the same tasks to quantify the performance drop, confirming reliance on active retrieval.

## Limitations
- Evaluations covered only three relatively small-scale tasks (faculty hiring, Nobel deaths, senator trajectories); generalizability to broader, noisier domains remains unproven.  
- The claim of “perfect accuracy on repurposed tasks” rests on just two repurposing examples, limiting confidence in robustness across diverse instructions and entity types.  
- Cost analysis assumes a fixed human RA rate and does not account for training, supervision, or error-correction overheads, possibly oversimplifying the economic comparison.

## Confidence
- **Scalability & Cost Reduction (~$0.09/record):** Medium – straightforward API cost calculation, but hidden expenses (prompt engineering, failure handling) may affect real-world cost.  
- **Repurposability via Natural Language:** Low – demonstration is preliminary; success likely depends on instruction clarity and task similarity to original pipeline.  
- **Reliance on Active Web Retrieval:** Medium – ablation test supports the claim but only tests memorization of named entities, not other memorization aspects.

## Next Checks
1. **Broad Task Generalizability:** Replicate DataParasite on 5–10 diverse, unseen curation tasks from computational social science (e.g., event extraction, sentiment aggregation across domains) to measure accuracy drop-off.  
2. **Comparison with Alternative Tools:** benchmark against existing semi-automated curation frameworks (e.g., Cura, custom scrapers) using the same tasks and cost model to contextualize the claimed order-of-magnitude savings.  
3. **Longitudinal Repurposing Study:** Track a team of social scientists using DataParasite for 4 weeks to self-assign new curation tasks via natural language; record success rate, number of instruction iterations, and final accuracy compared to manual baseline.
