# OrgForge: A Multi-Agent Simulation Framework for Verifiable Synthetic Corporate Corpora

## Quick Facts
- **arXiv ID:** 2603.14997
- **Source URL:** https://arxiv.org/abs/2603.14997
- **Reference count:** 3
- **Primary result:** A 22-day simulation produced a verifiable corporate corpus; BM25 retrieval (MRR@10 0.28) outperformed dense embeddings (0.20) on most question types, with a total cost of ~$285 for 953 LLM calls.

## Executive Summary
OrgForge introduces a deterministic simulation framework to generate multi-artifact corporate corpora with verifiable, causally consistent ground truth for RAG evaluation. It enforces a strict physics-cognition boundary: a deterministic Python engine maintains an immutable `SimEvent` log of all facts, while LLMs generate only prose constrained by validated proposals. This architecture prevents cross-document contradictions and ensures timestamp consistency across Slack, JIRA, email, and other artifacts. Baseline evaluations on a generated 22-day corpus (1,079 documents, 83 questions) show BM25 retrieval surpassing dense embeddings on most question categories, establishing a new benchmark for controlled corporate simulation.

## Method Summary
The framework simulates an organization by running a deterministic engine (`flow.py`) that updates a social graph and state machine. Each day, department planners (LLMs) propose structured events, which a validator checks against current state (actor existence, capacity, cooldowns). Approved proposals trigger artifact generators, which use actor-local clock primitives (`sync_and_tick`, `advance_actor`) to produce causally consistent timestamps. The entire process emits an immutable `SimEvent` log. An evaluation harness extracts causal threads from this log to generate typed questions (e.g., TEMPORAL, CAUSAL, RETRIEVAL), exports datasets, and runs retrieval baselines. Reproduction requires configuring a minimal `config.yaml`, running the simulation, and executing the harness.

## Key Results
- BM25 retrieval achieved an overall MRR@10 of 0.28 vs. 0.20 for dense embeddings (Stella 1.5B), leading on most question types.
- Dense retrieval narrowly outperformed on RETRIEVAL questions (0.39 vs. 0.35).
- The 22-day simulation cost approximately $285 for 953 LLM calls using `openai.gpt-oss-120b-1`.

## Why This Works (Mechanism)
### Mechanism 1: Physics-Cognition Boundary Prevents Contradictions
- **Claim:** The strict separation between deterministic state management and LLM prose generation prevents cross-document factual contradictions.
- **Mechanism:** A deterministic Python engine (`S`, `E`) maintains all ground truth via an immutable `SimEvent` log. LLM planners (`P`) generate only structured proposals. A validator (`V`) checks these proposals against the current state before any prose is written. LLMs never directly modify `E`.
- **Core assumption:** The validator (`V`) correctly enforces all logical constraints derived from `S` and `E`.
- **Evidence anchors:**
  - Abstract: "enforces a strict physics-cognition boundary... large language models generate only surface prose, constrained by validated proposals."
  - Section 3.1: Formal system definition `M = (S, P, V, E)` and description of `V`'s five checks.
- **Break condition:** A flawed validator implementation (e.g., missing a state plausibility rule) or a prompt injection causing an LLM to emit a proposal that incorrectly passes validation.

### Mechanism 2: Graph-Dynamic Stress Propagation Creates Capacity Noise
- **Claim:** Stress propagation via betweenness centrality models causally consistent organizational capacity noise.
- **Mechanism:** Each day, nodes with above-median betweenness centrality (`K_t`) exceeding a burnout threshold (`B`) distribute excess stress proportionally to neighbors' edge weights. This deterministically updates engineer capacity (`C_i`).
- **Core assumption:** Betweenness centrality in the social graph is a valid proxy for an individual's stress diffusion influence.
- **Evidence anchors:**
  - Section 3.4.1: Specification of Equation (3) and `K_t` threshold.
  - Section 3.6: Capacity formula (`C_i`) consuming stress-derived values.
  - Section 4.4: "ground-truth capacity variance: the SimEvent log records the time consumed by interruptions."
- **Break condition:** Lazy betweenness recomputation could use stale values if edge weight updates are frequent, misidentifying key players temporarily.

### Mechanism 3: Actor-Local Clock Enforces Causal Timestamps
- **Claim:** An actor-local clock guarantees causal timestamp consistency across all artifacts.
- **Mechanism:** Each actor has an independent time cursor. `sync_and_tick(A, Δ)` synchronizes participants in set `A` to the maximum cursor before advancing a shared cursor. `advance_actor(i, Δ)` models parallel work. This ensures dependent artifacts (e.g., a reply) cannot precede their trigger.
- **Core assumption:** Organizational work can be modeled as parallel independent tasks (`advance_actor`) and synchronized collaborative chains (`sync_and_tick`).
- **Evidence anchors:**
  - Section 4.3: "Timestamp are no longer sampled independently... guaranteeing that no response artifact can receive a timestamp earlier than its trigger."
  - Section 3.9: Causal chains rely on this ordering.
  - Corpus: "causal timestamp correctness" property; evaluation questions like `TEMPORAL` and `CAUSAL` depend on it.
- **Break condition:** Incomplete coverage of new artifact types by the clock primitives would reintroduce timestamp inversions.

## Foundational Learning
- **Concept: Deterministic Simulation Engines**
  - **Why needed:** The verifiability guarantee rests on `S` and `E` being fully deterministic and separate from stochastic LLM output. Any hidden randomness corrupts ground truth.
  - **Quick check:** If you changed the random seed but kept the config identical, would the `SimEvent` sequence be byte-for-byte identical?

- **Concept: Graph Dynamics for Social Modeling**
  - **Why needed:** Stress propagation, edge decay, and escalation routing are defined as updates on the weighted social graph `G`. Understanding these as deterministic functions is key to predicting behavior.
  - **Quick check:** How does an `incident` collaboration between two engineers (`β_inc`) affect both their direct edge weight and future stress propagation risk?

- **Concept: Proposal-Validation Loop as a Guarded Interface**
  - **Why needed:** This embodies the physics-cognition boundary. The planner (`P`) is unconstrained, but its influence is channeled through the validator (`V`), a stateful, rule-based gatekeeper.
  - **Quick check:** What happens to a planner's "team celebration" proposal if current system health `H` is 35? Trace the path through `V`.

## Architecture Onboarding
- **Component map:**
  Config & Genesis -> Daily Loop (DayPlannerOrchestrator -> Department Planners -> PlanValidator -> NormalDayHandler) -> Graph Dynamics -> Causal Infrastructure -> Clock -> Persistence (MongoDB, filesystem) -> Evaluation (EvalHarness -> CausalThreadBuilder -> EvalQuestionGenerator -> OrgForgeScorer -> HFExporter)

- **Critical path:** GraphDynamics updates `S` -> Validator checks proposals against `S`/`E` -> Approved proposals trigger artifact generators -> Generators use `sim_clock` for timestamps -> All artifacts reference `SimEvent` IDs -> CausalChainHandler links chains -> EvalHarness queries `SimEvent` log for ground truth.

- **Design tradeoffs:**
  - Validation strictness vs. narrative richness: Tight rules prevent contradictions but may cause high rejection rates, leading to repetitive artifacts.
  - Graph computation cost vs. realism: Lazy betweenness recomputation (`O(n*m)`) trades immediate accuracy for performance; for `n>50`, transient inaccuracies in `K_t` are possible.
  - Actor-local clock complexity vs. correctness: Simple model but requires discipline; new generators must correctly use synchronization primitives.

- **Failure signatures:**
  - High validator rejection rate: Indicates planner prompts or `KNOWN EVENT TYPES` mismatch with `S` state.
  - Timestamp inversion in logs: A Slack reply with an earlier timestamp than its parent indicates clock primitive misuse.
  - Stress saturation: All `S_i,t` hitting 100 suggests `δ` too low or `β_inc` too high relative to `α`.
  - Zero escalation chains: `find_escalation_target()` may fail if the graph is too fragmented.

- **First 3 experiments:**
  1. Trace a single incident end-to-end: Run a 5-day simulation with `random_seed=42`. Find an `incident_opened` `SimEvent`. Use its `incident_id` to collect all subsequent artifacts and verify timestamps are monotonically non-decreasing. Inspect the `EscalationChain` `SimEvent` to see if the `escalation_path` matches the `Dijkstra` calculation on `G`.
  2. Validate the physics-cognition boundary: Temporarily modify `PlanValidator.actor_integrity` to allow a non-existent actor name. Rerun one day. Check if a `SimEvent` with that ghost actor appears. It should not.
  3. Probe graph dynamics sensitivity: Record edge weight `w_uv` after a `β_inc` event. Simulate 10 days with no interactions between those actors. Verify `w_uv` decays toward `ω_min` (0.5) by a factor of `γ^10` (~0.74), confirming Equation (4).

## Open Questions the Paper Calls Out
- **Question 1:** What is the performance of a full retrieval-augmented generation pipeline on OrgForge’s eight question categories, and how does it vary with difficulty and reasoning complexity?
- **Question 2:** Does an unconstrained LLM-generated corpus (without SimEvent grounding) exhibit non-zero contradiction rates on incident-referencing fields (timestamp, actor, status), and how does that compare to OrgForge’s zero contradiction guarantee?
- **Question 3:** Does incorporating SimEvent metadata as retrieval context improve correctness on TEMPORAL and GAP DETECTION questions, and what recall does a retrieval agent achieve on identifying probabilistically dropped emails?
- **Question 4:** Can OrgForge be extended to simulate multiple interacting organizations (e.g., vendor and customer) with independent state machines and planning loops, thereby enabling evaluation of cross-organizational knowledge handoffs?

## Limitations
- Baseline corpus generation used undocumented random seeds and a specific `novel event logging` setting, blocking identical replication.
- LLM endpoint details for `openai.gpt-oss-120b-1` are unspecified, requiring equivalent access for faithful reproduction.
- High validator rejection rates may reduce narrative diversity, a trade-off not quantified.

## Confidence
- **Physics-cognition boundary claim:** Medium confidence. Mechanism is formally specified and architecturally enforced, but an implementation flaw in `V`'s checks would break guarantees.
- **Graph-dynamic stress propagation:** Medium confidence. Equations are deterministic, but lazy centrality updates introduce a known window where `K_t` may be stale.
- **Actor-local clock causal consistency:** High confidence. Primitives are well-defined and enforced; failures would stem from new generators not using them.
