# An Intelligent AI glasses System with Multi-Agent Architecture for Real-Time Voice Processing and Task Execution

## Quick Facts
- arXiv ID: 2601.06235
- Source URL: https://arxiv.org/abs/2601.06235
- Reference count: 12
- Primary result: A dual-agent AI glasses system enables real-time multilingual voice command processing, distributed task execution, and resilient cross-network operation for enterprise deployment.

## Executive Summary
Current AI glasses lack integrated real-time voice processing, intelligent task execution, and robust cross-network communication needed for enterprise use. This paper presents a dual-agent architecture: Agent 01 performs streaming automatic speech recognition (ASR) using Whisper.cpp, while Agent 02 handles intent processing via local large language models (LLMs) enhanced with Model Context Protocol (MCP) tools and retrieval-augmented generation (RAG). Multi-modal data (audio, video, eye tracking) is streamed via RTSP, and RabbitMQ messaging distributes tasks across networked execution hosts. The implemented system validates functional multilingual (English/Chinese) command recognition, cross-platform task execution (e.g., robotic arm troubleshooting, navigation), and resilient operation across LAN, WAN, and VPN configurations.

## Method Summary
The system comprises two cooperating agents. Agent 01 ingests an RTSP audio stream from the glasses, applies voice activity detection and a sliding-window buffer, and uses Whisper.cpp to produce a continuous text transcript. This transcript is passed to Agent 02, which uses a locally running LLM (via Ollama) to interpret user intent. The LLM query is augmented with context retrieved from a RAG store (ChromaDB with sentence-transformers embeddings) containing domain-specific documentation. Based on the intent and retrieved context, the LLM invokes appropriate MCP tools to formulate an executable command, which is published to a RabbitMQ topic exchange. A network manager dynamically selects the optimal RTSP transport method (direct LAN, port-forwarded WAN, or VPN) and adapts streaming bitrates to maintain quality. Task executor applications on various hosts consume messages from RabbitMQ queues and perform actions such as opening a browser, controlling a robotic arm, or displaying navigation information.

## Key Results
- Dual-agent separation reduces end-to-end latency and modularizes maintenance: Agent 01’s streaming ASR runs independently of Agent 02’s LLM inference.
- The system accurately processes English and Chinese voice commands and executes tasks across heterogeneous platforms (e.g., robotic arm troubleshooting, navigation).
- Network resilience is achieved via RTSP streaming and RabbitMQ task queuing, with automatic fallback across LAN, WAN, and VPN connections.

## Why This Works (Mechanism)

### Mechanism 1: Separating streaming ASR from LLM-based intent processing
- **Claim:** Separating streaming ASR from LLM-based intent processing reduces end-to-end latency and modularizes system maintenance.
- **Mechanism:** Agent 01 uses Whisper.cpp to convert continuous audio streams (via RTSP) into text in near real-time. This text is passed to Agent 02, which uses a local LLM with MCP tools and RAG to parse intent and execute tasks. The decoupling prevents LLM inference from blocking audio processing.
- **Core assumption:** The sequential pipeline's latency is acceptable for the target use cases (e.g., industrial troubleshooting) and the overhead of inter-agent messaging is lower than combined processing.
- **Evidence anchors:** [abstract] "dual-agent architecture where Agent 01 handles Automatic Speech Recognition (ASR) and Agent 02 manages AI processing through local Large Language Models (LLMs), Model Context Protocol (MCP) tools, and Retrieval-Augmented Generation (RAG)."; [section 3.2 & 3.3] Details the independent pipelines: Agent 01's sliding window audio processing and Agent 02's intent recognition/RAG pipeline.
- **Break condition:** Cumulative latency from the two-stage processing exceeds interaction-time requirements (<200ms as noted in limitations), or Agent 01's ASR accuracy degrades in novel acoustic environments, propagating errors downstream.

### Mechanism 2: Integrating local LLMs with MCP tools and RAG memory
- **Claim:** Integrating local LLMs with MCP tools and RAG memory enables context-aware, executable task planning without cloud dependency.
- **Mechanism:** Agent 02's framework first uses the LLM to interpret user intent from the ASR transcript. The RAG system (ChromaDB + sentence-transformers) retrieves relevant past interactions or documentation. The MCP protocol then allows the LLM to call specific, defined tools (e.g., "open_browser", "query_robot_arm_docs") to formulate a concrete, executable command.
- **Core assumption:** The local LLM's reasoning capability is sufficient for the constrained domain (enterprise troubleshooting/navigation) and the retrieved context from RAG is semantically relevant.
- **Evidence anchors:** [abstract] "Agent 02 manages AI processing through local Large Language Models (LLMs), Model Context Protocol (MCP) tools, and Retrieval-Augmented Generation (RAG)."; [section 3.3] Explicitly describes the "multi-stage analysis pipeline" combining pattern matching, LLM processing, RAG document retrieval, and MCP tool use.
- **Break condition:** RAG retrieval returns irrelevant documents (low cosine similarity), leading to incorrect tool selection or command formulation by the LLM, or the MCP toolset lacks a required function for a novel query.

### Mechanism 3: Using RTSP for multi-modal data streaming and RabbitMQ for task messaging
- **Claim:** Using RTSP for multi-modal data streaming and RabbitMQ for task messaging creates a resilient, cross-network backbone for distributed execution.
- **Mechanism:** RTSP streams audio/video from glasses and eye-tracking data to processing agents. RabbitMQ queues decouple command generation (Agent 02) from execution (remote hosts). The Network Manager automatically selects the optimal connection method (direct LAN, port-forwarded WAN, VPN) and adapts streaming bitrates. Message persistence in RabbitMQ ensures tasks are not lost during network blips.
- **Core assumption:** RabbitMQ's topic-based routing can correctly map diverse task types (robotics, navigation) to appropriate execution hosts, and the network manager's criteria (latency, bandwidth, reliability) are valid proxies for connection quality.
- **Evidence anchors:** [abstract] "system supports real-time RTSP streaming for voice and video data transmission... and remote task execution through RabbitMQ messaging."; [section 3.4 & 3.5] Details the RTSP streaming setup, Network Manager's method selection, adaptive streaming, and RabbitMQ's task scheduling with priority queuing.
- **Break condition:** Network manager selects a suboptimal method (e.g., VPN with high latency), failing real-time requirements, or RabbitMQ queue backlog grows unbounded if execution hosts are unavailable, violating task timeliness.

## Foundational Learning

- **Concept: Streaming ASR with Sliding Windows**
  - *Why needed here:* To convert continuous audio from glasses into low-latency text without waiting for sentence boundaries, as required for real-time interaction.
  - *Quick check question:* What is the purpose of overlap between consecutive audio buffers in a sliding window ASR pipeline?

- **Concept: Model Context Protocol (MCP)**
  - *Why needed here:* To provide a standardized, secure way for the local LLM (Agent 02) to invoke external tools and data sources (e.g., robotic arm APIs, map services) beyond its native capabilities.
  - *Quick check question:* In this system, what is the role of the MCP server relative to the LLM and the external tools?

- **Concept: Retrieval-Augmented Generation (RAG)**
  - *Why needed here:* To ground the LLM's intent interpretation in specific, enterprise-specific knowledge (e.g., equipment manuals) without fine-tuning the model, improving accuracy for domain-specific commands.
  - *Quick check question:* How does the RAG system in Agent 02 select which documents to provide as context to the LLM for a given voice query?

## Architecture Onboarding

- **Component map:** AI Glasses -> RTSP Stream -> Agent 01 (Whisper.cpp) -> Text -> Agent 02 (LLM + RAG + MCP) -> Task Intent -> RabbitMQ (topic exchange) -> Task Executor (platform-specific host) -> Action/Display
- **Critical path:** Glasses Audio -> Agent 01 ASR -> Agent 02 Intent/RAG/MCP -> RabbitMQ Message -> Task Executor -> Action/Display.
- **Design tradeoffs:**
  - Latency vs. Accuracy: Larger Whisper.cpp buffer sizes improve ASR accuracy but increase first-word latency.
  - Local vs. Cloud: Local LLMs (Ollama) ensure privacy/offline use but have smaller context windows/knowledge than cloud models.
  - Generality vs. Performance: The RabbitMQ topic scheme is flexible but requires careful routing key design to prevent misrouting.
- **Failure signatures:**
  - ASR Failure: Incoherent text output from Agent 01 (check Whisper.cpp logs, audio input gain).
  - Intent Failure: LLM generates plausible text but wrong tool call (check RAG retrieval scores, MCP tool availability).
  - Network Failure: RabbitMQ message backlog increases, RTSP stream disconnects (check Network Manager logs, firewall/VPN status).
  - Execution Failure: Task Executor logs show "unknown command" (check RabbitMQ message payload format vs. executor parser).
- **First 3 experiments:**
  1. Benchmark Agent 01: Stream a fixed audio file via RTSP, measure Whisper.cpp's word error rate (WER) and latency per second of audio with different buffer sizes.
  2. Validate Agent 02's RAG: Inject a known document into ChromaDB, craft a query that should retrieve it, and verify the top-k result's cosine similarity score meets a threshold (e.g., >0.7).
  3. Test end-to-end network resilience: Run a simple "open browser" command while deliberately switching the network from LAN to WAN (port-forwarded) and observe RabbitMQ message delivery time and success rate.

## Open Questions the Paper Calls Out

1. **Edge computing integration:** How can edge computing integration be practically implemented to reduce network dependency while maintaining low-latency task execution in distributed AI glasses systems?  
   *Basis:* Future work should focus on edge computing integration to reduce network dependency and improve privacy protection.  
   *Why unresolved:* The current system relies on centralized or WAN-based task execution, introducing latency and vulnerability to network disruptions, which hinders real-time industrial applications.  
   *Evidence needed:* Comparative performance benchmarks deploying edge nodes proximate to AI glasses, measuring task completion latency, RabbitMQ message throughput, and resilience to network partitions against the baseline cloud-centric design.

2. **Privacy-preserving voice data processing:** What on-device or federated learning approaches can effectively protect voice data privacy during transmission and processing without compromising multilingual intent recognition accuracy?  
   *Basis:* Privacy considerations arise from voice data transmission... necessitating enhanced encryption and on-device processing capabilities. Implementation of federated learning approaches could enable model improvement while maintaining data locality.  
   *Why unresolved:* Voice commands may contain sensitive information, and current network-dependent transmission poses risks in secure enterprise environments, yet privacy hardening methods are unimplemented.  
   *Evidence needed:* Security analysis quantifying data leakage risks under encryption schemes, and empirical accuracy comparisons of federated versus centralized LLM fine-tuning for multilingual command interpretation.

3. **Sub-200ms end-to-end latency:** Can the sequential ASR-to-LLM processing pipeline be architecturally reconfigured to achieve sub-200ms end-to-end latency for time-critical voice commands?  
   *Basis:* Sequential processing architecture introduces cumulative latency that may limit real-time interaction scenarios requiring sub-200ms response times.  
   *Why unresolved:* Cumulative delays from audio streaming, Whisper.cpp processing, LLM inference, and task dispatching may exceed thresholds for interactive industrial assistance, as the paper does not measure component-wise latencies against this target.  
   *Evidence needed:* Detailed latency profiling of each pipeline stage under load, followed by experimental modifications (e.g., model quantization, parallelization) validated with time-sensitive tasks like emergency stop commands.

4. **Scalability under multi-user load:** How does the RabbitMQ-based distributed task execution framework scale and maintain performance under concurrent multi-user enterprise deployments with dozens of simultaneous AI glasses sessions?  
   *Basis:* The paper validates single-user functionality and claims enterprise suitability, but provides no stress-testing or resource allocation analysis for multiple concurrent glasses users sharing execution hosts.  
   *Why unresolved:* Enterprise deployment implies multi-user scenarios; without scalability data, system viability for large-scale operational settings remains speculative due to potential RabbitMQ queue congestion, host resource exhaustion, or message routing bottlenecks.  
   *Evidence needed:* Systematic load testing with increasing concurrent simulated glasses clients, measuring RabbitMQ throughput, task execution latency, and host resource utilization to identify breaking points and required infrastructure scaling.

## Limitations
- Lacks quantitative performance metrics (latency, accuracy) and omits critical implementation parameters (e.g., Whisper.cpp buffer sizes, VAD thresholds, LLM model details, MCP tool schemas, RAG corpus, RabbitMQ topology).
- Network adaptation algorithm thresholds and decay constants are unspecified, hindering reproducibility.
- No empirical validation of tool-calling accuracy, RAG retrieval relevance, or multi-user scalability.
