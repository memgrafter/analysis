# Learning to Ideate for Machine Learning Engineering Agents

## Quick Facts
- **arXiv ID:** 2601.17596
- **Source URL:** https://arxiv.org/abs/2601.17596
- **Reference count:** 11
- **Primary result:** MLE-Ideator, a dual-agent framework with a separate Ideator, outperforms implementation-only baselines; RL-trained Ideator yields 11.5% relative improvement and achieves 63.1 Best@3 on 51 held-out tasks.

## Executive Summary
Existing MLE agents fail to iteratively optimize solutions beyond an initial baseline. This paper introduces MLE-Ideator, a dual-agent framework where an Implementer (code agent) can request strategic ideas from a separate Ideator via a `<seek_help>` action. The Ideator produces high-level, actionable suggestions in a structured format (ANALYSIS, ACTION, RATIONALE), while the Implementer executes a single-step code change to realize the idea. This decoupling allows a smaller model to guide a more capable implementer.

The training-free dual-agent system already surpasses implementation-only baselines on MLE-Bench. To further boost performance, the Ideator is trained with reinforcement learning (GRPO) using execution-based rewards: each suggested idea is executed in one step by a frozen Implementer, and the immediate performance change yields a reward of +1/0/-1. With only 1,000 samples from 10 tasks, RL-trained Qwen3-8B achieves an 11.5% relative improvement over its untrained version, surpasses Claude Sonnet 3.5, and reaches a Best@3 score of 63.1 across 51 held-out tasks. RL also shifts the idea distribution toward more effective categories such as feature engineering.

## Method Summary
The framework comprises two agents: the Implementer (based on CodeAct) and the Ideator (LLM). The Implementer interacts with the MLE-Bench environment by executing Python or Bash commands. When it detects a performance plateau, it issues a `<seek_help>` query containing the problem statement, past attempts, and current goal. The Ideator receives this structured query and returns a suggestion (ANALYSIS, ACTION, RATIONALE). The Implementer then integrates the suggestion into a single code action, producing a new solution state and performance score.

For RL training, the authors collect an offline buffer of states from prior runs where `<seek_help>` was invoked. They then train the Ideator with GRPO using LoRA. Each training step samples a state, generates G candidate ideas, and uses a frozen Implementer to execute each idea in one step. The reward is based on the immediate performance delta. The policy is updated to maximize this reward, avoiding costly multi-step rollouts and requiring only a small number of training tasks (10 tasks, 1,000 samples).

## Key Results
- The training-free dual-agent system outperforms strong implementation-only baselines (e.g., CodeAct) on MLE-Bench.
- RL-trained Ideator (Qwen3-8B) with 1K samples from 10 tasks achieves an 11.5% relative improvement over its untrained version, surpasses Claude Sonnet 3.5, and obtains a Best@3 score of 63.1 across 51 held-out tasks.
- RL shifts the Ideator’s idea distribution toward categories with higher effectiveness: Feature Engineering (+7.5%), Data Preparation (+3.1%), while reducing less effective categories like Model Training (-4.9%) and Architecture (-3.2%).

## Why This Works (Mechanism)
### Mechanism 1: Decoupling Strategic Ideation from Code Implementation
- **Claim:** Separating ideation from implementation allows a small, trainable model to guide a more capable implementer, improving iterative MLE performance.
- **Mechanism:** The Implementer, upon plateauing, emits a structured `<seek_help>` query (problem, attempts, goal). The Ideator generates a high-level suggestion (ANALYSIS, ACTION, RATIONALE). The Implementer then executes a single-step code change to realize the idea. The Ideator only needs to produce textual guidance, not syntactically correct code, lowering the barrier for small models.
- **Core assumption:** The Implementer can reliably execute a one-step refinement based on the suggestion, and the immediate performance delta is a reasonable proxy for the idea’s quality.
- **Evidence:** The framework design (Section 3.1) and ablations showing that NULLIDEA or VAGUEIDEA yield minimal gains confirm the quality of ideation matters.
- **Break condition:** If the Implementer fails to detect plateaus or cannot execute suggestions in one step, the loop breaks down.

### Mechanism 2: RL with Execution-Based Rewards for Ideator Training
- **Claim:** Reinforcement learning with one-step execution rewards can train the Ideator to generate more effective ideas, shifting its distribution toward empirically successful categories without costly multi-step rollouts.
- **Mechanism:** For each offline state, the Ideator generates G candidate ideas. A frozen Implementer executes each in one step, and the performance change yields a discrete reward (+1/0/-1). The Ideator’s policy is updated via GRPO to maximize this reward, aligning idea generation with outcomes that improve the ML solution.
- **Core assumption:** The one-step reward correlates with the long-term value of an idea; foundational ideas that lack immediate impact may be undervalued.
- **Evidence:** RL training shifts idea distribution (Section 4.2, Table 3): Feature Engineering +7.5%, Data Preparation +3.1%, while Model Training and Architecture decrease.
- **Break condition:** If single-step reward is a poor predictor of ultimate contribution (e.g., groundwork ideas), the RL signal misaligns and may suppress valuable ideas.

### Mechanism 3: Ideation-Driven Exploration Escapes Local Optima
- **Claim:** The external strategic injection from the Ideator enables agents to escape local optima and achieve higher peak performance than implementation-only agents.
- **Mechanism:** After establishing a baseline, the Implementer plateaus and seeks help. The Ideator’s context-aware suggestion provides a new direction (e.g., feature engineering) that breaks the agent out of repetitive local loops (e.g., hyperparameter tweaks).
- **Core assumption:** Single-agent implementers lack intrinsic high-level re-planning once a baseline is found; they exploit local gradients rather than exploring novel strategy spaces.
- **Evidence:** Performance curves (Figure 2) show a sharp gain after the plateau phase coinciding with increased `<seek_help>` calls. Ablations with NULLIDEA/VAGUEIDEA show minimal gains.
- **Break condition:** If the Ideator’s suggestions are consistently ineffective, the implementer may waste steps or degrade performance.

## Foundational Learning
### Concept: Machine Learning Engineering (MLE) Workflow Iteration
- **Why needed:** The Ideator must understand standard MLE cycles (data preparation, feature engineering, model selection/training, hyperparameter tuning, evaluation) to propose actions that fit naturally into an ongoing trajectory and target high-leverage improvements.
- **Quick check:** Given an agent's current model (e.g., Random Forest) and performance metric (e.g., AUC), what are the three highest-leverage stages to modify for potential improvement?

### Concept: Code Execution Semantics & Single-Step Boundaries
- **Why needed:** The RL reward is based on a *single-step* execution of the suggested idea. The Ideator must generate concrete, bounded suggestions so the Implementer can translate them into one executable code change.
- **Quick check:** Would "try a different model" be executable in one step by a typical coding agent? Why or why not? What makes a suggestion "single-step executable"?

### Concept: Trajectory State Representation & Context Window
- **Why needed:** The Ideator's state includes the full trajectory (history of actions, code, scores). It must distill this long context to identify the blocking issue and avoid repeating failed approaches.
- **Quick check:** If the trajectory shows three failed attempts at adjusting learning rate, what should the Ideator infer about the bottleneck, and what category of idea might be more promising?

## Architecture Onboarding
### Component Map
Implementer Agent (CodeAct) ↔ Ideator Agent (LLM) via `<seek_help>` and suggestion.
Implementer Agent ↔ MLE-Bench Environment via code execution and score feedback.
State Buffer stores (D, τ, p_t, C_t) when `<seek_help>` is invoked.
RL Pipeline (VeRL) samples from State Buffer, generates G ideas per state, runs frozen Implementer to execute each, computes rewards, and updates Ideator via GRPO.

### Critical Path
1. Task Start: Implementer initialized with no code.
2. Baseline Phase: Implementer explores to produce a valid ML solution and record performance.
3. Plateau Detection & Query: After stagnation (e.g., no improvement for N steps), Implementer emits `<seek_help>` with structured query summarizing problem, attempts, and goal.
4. Ideation: Ideator receives full state and generates suggestion.
5. Execution & Evaluation: Implementer integrates suggestion into a single code action, runs it in the environment, and obtains new score.
6. Reward & Loop: Reward computed based on score delta. If positive, trajectory continues; repeat from step 3 until step limit.

### Design Tradeoffs
- **Separation vs. Cost:** Dual-agent design yields performance gains but increases inference cost (~1.4×) and longer context for Ideator.
- **Single-Step Reward vs. Fidelity:** Using one-step execution reward makes RL sample-efficient but may undervalue foundational ideas (e.g., data cleaning) that lack immediate impact.
- **Offline Buffer vs. Online Adaptation:** Training on static offline buffer is efficient but prevents Ideator from adapting to its own evolving suggestions; state distribution remains fixed.

### Failure Signatures
- Low `<seek_help>` frequency (<5% of steps): Implementer may not detect plateaus.
- High rate of `R_t(α)=0` or `-1`: Ideator generates unexecutable or ineffective ideas.
- Idea distribution heavily skewed to "Model Training" or "Hyperparameter Tuning" (effectiveness ~51%, 48%): RL should shift toward "Feature Engineering" (~65%) and "Data Preparation" (~57%).
- No performance gap between `Qwen3-8B` and `Qwen3-8B-RL`: RL training likely failed; check reward clarity, GRPO hyperparameters, buffer quality.

### First 3 Experiments
1. **Framework Sanity Check:** Run training-free MLE-Ideator (untrained Ideator) against CodeAct baseline on 5 held-out tasks. Compare Avg@3 and Best@3 scores; log `<seek_help>` frequency.
2. **RL Training Validation:** Train Ideator on the 10-task buffer (1K samples, 1 epoch). Evaluate Qwen3-8B-RL vs. untrained Qwen3-8B on a fixed validation set of states. Expect higher mean reward and a shifted idea distribution toward Feature Engineering/Data Preparation.
3. **Idea Effectiveness Analysis:** Sample 100 (state, idea, reward) tuples from RL validation set. Manually classify or use provided classifier (Prompt E) to categorize ideas. Plot proportion of effective ideas per category to confirm RL exploits category effectiveness.

## Open Questions the Paper Calls Out
1. Can a learned proxy reward model replace full ML solution execution during RL training, maintaining the Ideator's effectiveness while drastically reducing computational cost?
2. Does scaling test-time compute via Best-of-N sampling of Ideator suggestions lead to further performance gains in MLE tasks beyond the current single-suggestion-per-step framework?
3. How would co-training the Implementer and Ideator in a joint RL framework compare to the current decoupled approach where the Implementer is frozen during Ideator training?
4. To what extent can the RL-trained Ideator generalize its learned ideation strategies to novel machine learning tasks or entirely different scientific domains beyond the MLE-Bench Kaggle tasks used for training and evaluation?

## Limitations
- Incomplete implementation specs (plateau detection logic, full Implementer prompt, RL hyperparameters, frozen Implementer identity) hinder faithful reproduction.
- Single-step reward assumption may undervalue foundational ideas that lack immediate performance gains.
- Lack of human performance bounds and exact held-out task list prevents exact normalized score replication.

## Confidence
- Dual-agent framework improvement over baselines: **High**
- RL-driven idea distribution shift toward effective categories: **Medium**
- Escaping local optima via ideation: **Medium**

## Next Checks
1. **Plateau detection sensitivity:** Systematically vary stagnation thresholds and measure changes in `<seek_help>` frequency, state distribution, and final Best@3.
2. **Reward signal fidelity audit:** Manually classify 100 (idea, execution, reward) samples to quantify executability rate and correlation between immediate reward and long-term trajectory improvement.
3. **Single-step vs. multi-step reward ablation:** Compute an oracle reward based on full-trajectory peak improvement for a held-out subset and compare its alignment with the proposed single-step reward.
