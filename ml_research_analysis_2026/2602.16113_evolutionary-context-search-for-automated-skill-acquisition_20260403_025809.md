# Evolutionary Context Search for Automated Skill Acquisition

## Quick Facts
- **ArXiv ID:** 2602.16113
- **Source URL:** https://arxiv.org/abs/2602.16113
- **Reference count:** 30
- **Primary result:** ECS improves BackendBench by 27% relative (0.461 vs 0.363 best RAG) and τ²-bench airline Pass1 by 7% (0.767 vs 0.717).

## Executive Summary
Large language models (LLMs) cannot incorporate new knowledge after deployment, and retrieval-augmented generation (RAG) retrieves semantically similar but often task-ineffective context. Evolutionary Context Search (ECS) addresses this by framing context selection as an optimization problem: it uses a genetic algorithm to evolve combinations of atomic context units, with fitness defined by accuracy on a small development set. ECS constructs units at varying abstraction levels (source texts, insights, skills) and applies selection, crossover, mutation, and LLM refinement. It yields substantial gains on code generation (BackendBench) and multi-turn assistance (τ²-bench) and transfers across model families, enabling effective post-deployment skill acquisition.

## Method Summary
ECS takes raw text resources (e.g., documentation, demonstration trajectories) and preprocesses them into a pool of atomic context units across granularities. It initializes a population of candidate contexts by sampling units. Each generation, every candidate is evaluated on a small development set using the target LLM; the success rate becomes its fitness. The top 60% of candidates are selected as elites to produce offspring: parents are combined via crossover (concatenation and truncation to a length budget), mutated (each unit has a 0.1 probability to be added or replaced), then refined by an LLM to resolve contradictory information. This loop runs for 5–10 generations, after which the best context is returned. The approach requires only inference calls and works within the model’s context window.

## Key Results
- BackendBench: relative improvement of 27% (0.461 vs. 0.363, best RAG).
- τ²-bench (airline): Pass@1 gain of 7% (0.767 vs. 0.717).
- Cross-model transfer: contexts evolved with Gemini-3-Flash transfer to Claude-4.5-Sonnet and DeepSeek-V3.2; DeepSeek’s gain over RAG is 7×.

## Why This Works (Mechanism)
**Mechanism 1: Fitness-guided optimization.** Instead of retrieving based on semantic similarity, ECS directly optimizes context combinations for task performance using a genetic algorithm. Fitness is measured as accuracy on a small development set (section 3.1), providing a training signal that discovers non-obvious pairings. Evidence: The formalization `C* = argmax f(C; M, T)` and the GA loop (Algorithm 1) show the process; ablations confirm the advantage over retrieval.

**Mechanism 2: Multi-granularity context units.** ECS builds units ranging from verbatim source texts to distilled insights and modular skills, matching the knowledge granularity required by different tasks (section 3.3). This flexibility lets the GA select the appropriate level, e.g., exact syntax for DSL generation or abstract rules for policy tasks. Evidence: Qualitative analysis (section 5.1) reveals contexts that span kernel code to FFI interfaces; the Full Context ablation (section 4.2) shows ECS beats brute-force inclusion, demonstrating the value of selective curation.

**Mechanism 3: Model-agnostic pattern transfer.** Evolved contexts encode domain-specific structural patterns (e.g., API usage conventions) rather than model-specific quirks; as static text, any competent model can interpret them. Evidence: Experiments show contexts evolved on Gemini-Flash transfer to Claude and DeepSeek (section 4.2). A concrete case (section 5.2) shows a context containing `cute.math.exp2` taught the pattern `cute.math.*`, which DeepSeek generalized to `cute.math.atan`, while RAG retrieved irrelevant code.

## Architecture Onboarding
**Component map:** Text Resources (D) -> Context Unit Builder (g(D)) -> Unit Pool (U) -> Population Initializer -> Evolution Loop: Fitness Evaluator -> Selector -> Crossover Operator -> Mutation Operator -> Refinement Module (LLM) -> (repeat generations) -> Best Context

**Critical path:** D is converted to U. An initial population P⁰ is sampled. For each generation: each candidate in Pᵗ is evaluated on the dev set; elites are selected; offspring are created via crossover, mutation, and refinement to form Pᵗ⁺¹. After the final generation T, the highest‑fitness context is returned. Fitness evaluation is the bottleneck.

**Design tradeoffs:**
- Upfront search cost (many model calls during evolution) vs. deployment efficiency (static cached context).
- Exploration vs. exploitation (higher mutation explores more; higher elite fraction converges faster but risks local optima).
- Unit abstraction vs. coherence (abstract insights are compact but may lose nuance; verbatim source texts preserve detail but may contain noise).
- Dev set size vs. fitness noise (larger set gives a more reliable signal but increases search time).

**Failure signatures:**
- Stagnant fitness across generations → exhausted search space or poor U.
- High contradiction rate in offspring → unit combinations are incompatible; if refinement fails, performance drops.
- No transfer gain → evolved context only benefits the evolution model, possibly encoding model‑specific patterns.
- Dev set overfitting → excellent dev scores but poor test performance, indicating an unrepresentative dev set.

**First 3 experiments:**
1. **Baseline replication:** Implement RAG baselines (AST/BM25, dense retrieval, hybrid) on a small BackendBench subset; reproduce the ordering (AST-based > chunk‑based) and verify random/plain baselines are lower.
2. **Minimal ECS smoke test:** Run ECS for 1 generation with population size 4 using only source‑text units. Verify fitness improves from generation 0 to 1 and the best context is not simply the concatenation of all units.
3. **Unit type ablation:** On a single τ²‑bench task, run ECS with U containing only (a) source texts, (b) insights, (c) skills. Compare final fitness; expect insights to perform best on policy‑heavy tasks.

## Limitations
- The development set must be representative; otherwise the fitness signal misguides evolution, causing overfitting or suboptimal contexts.
- Unit construction `g(D)` must produce coherent atomic units at appropriate granularities; failure here dooms the search regardless of the algorithm.
- Transferability assumes domain patterns are model‑agnostic; if the task is highly stochastic or reliant on memorizing arbitrary facts, evolved contexts may not generalize.

## Confidence
- **Primary empirical gains (BackendBench, τ²‑bench):** High (specific numbers, supported by ablations).
- **Cross‑model transferability:** Medium (transfer experiments are concrete, but rely on the assumption that contexts encode domain patterns rather than model quirks).
- **Mechanistic explanations (multi‑granularity units, fitness‑guided search):** Medium (qualitative examples and ablations provided, but disentangling GA vs. unit construction effects is incomplete).

## Next Checks
1. **Dev Set Audit:** Re‑run ECS with varying dev set sizes (e.g., 5 vs. 10 samples) and shuffled splits to assess fitness variance and plateau risk.
2. **Refinement Prompt Sensitivity:** Ablate the LLM refinement step using several prompt variations to test robustness of the gains.
3. **Unit Builder Sanity Check:** Compare ECS performance using the proposed unit builder against naive chunking (e.g., fixed‑size windows) and random unit sampling on a single task.
