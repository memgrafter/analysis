# GEAKG: Generative Executable Algorithm Knowledge Graphs

## Quick Facts
- **arXiv ID**: 2603.27922
- **Source URL**: https://arxiv.org/abs/2603.27922
- **Reference count**: 40
- **Primary result**: GEAKG captures procedural algorithmic knowledge as executable graphs, enabling zero-shot cross-domain transfer with zero-LLM-token deployment.

## Executive Summary
Procedural algorithmic knowledge is often implicit, lost between runs, and must be re-engineered for each new domain. GEAKG introduces a knowledge graph framework that makes this knowledge explicit, learnable, and transferable. It uses a three-layer architecture: L0 topology defines abstract roles and transitions; L1 binds executable operators to roles; L2 learns composition preferences via ant colony optimization. The framework is domain-agnostic, requiring only a pluggable RoleSchema ontology. Evaluated on combinatorial optimization and neural architecture search, GEAKG achieves zero-shot transfer: from TSP to JSSP and QAP (maintaining performance on large QAP instances) and across 70 NAS cross-dataset transfers (100% win rate over random search, matching evolutionary methods in seconds). The online phase requires no LLM tokens, demonstrating that procedural knowledge can be commoditized as executable graphs.

## Method Summary
GEAKG operates in two phases. Offline, an LLM generates a graph of abstract roles (L0) and executable operators (L1) according to a human-designed RoleSchema. The operators are validated for syntax, correctness, and safety. An ant colony optimization (ACO) engine then traverses the graph on training instances, learning transition preferences (pheromones) and symbolic rules (L2). The result is a snapshot—a serialized JSON containing L0, L1, and L2. Online, a symbolic executor loads the snapshot and a domain-specific binding (which defines solution representation, evaluation, etc.). It selects operator sequences based on learned pheromones and applies them to solutions, all without LLM calls. For transfer to a new domain, only the domain binding is changed; the snapshot remains identical.

## Key Results
- Zero-shot transfer from TSP to JSSP and QAP; on large QAP instances (n=256) GEAKG maintains performance where generic search degrades.
- In neural architecture search, across 70 cross-dataset transfers, GEAKG achieves a 100% win rate over random search (89% statistically significant) with zero deployment tokens, matching evolutionary methods while completing in seconds.
- The three-layer architecture and ACO-based learning engine are domain-agnostic, successfully instantiated across optimization and NAS with different RoleSchemas.

## Why This Works (Mechanism)
### Mechanism 1: Separation of Layers
Separating algorithmic structure (L0 topology), implementations (L1 operators), and empirical preferences (L2 pheromones/rules) enables cross-domain transfer without retraining. The three-layer design enforces a clean abstraction: L0 defines a typed graph of abstract roles (e.g., `CONST_GREEDY`, `LS_INTENSIFY_SMALL`); L1 binds runnable code; L2 learns transition preferences via ACO. During transfer, only the domain binding changes (fitness evaluation); L0/L1/L2 persist. The core assumption is that domain-agnostic search strategies (e.g., "intensify while improving, perturb when stuck") transcend problem semantics when roles are abstract enough. Evidence: The same architecture handles NAS (18 roles) and optimization (11 roles); Table 1 shows identical engine. Break condition: if L2 rules overfit source-domain instance distributions, transfer performance degrades (e.g., larger gaps on target for small QAP).

### Mechanism 2: RoleSchema as Transfer Interface
The `RoleSchema` ontology acts as a transfer interface, allowing the same ACO engine to traverse semantically different graphs without code changes. `RoleSchema` defines abstract roles, categories, valid transitions, entry points, and revisitability flags. The engine's traversal logic interprets this schema universally—ACO samples paths according to L2 pheromones but only considers edges permitted by the schema. Changing the schema reconfigures the search space; engine code remains identical. Core assumption: human-designed role semantics abstract away domain details while preserving essential algorithmic intent. Evidence: Section 3.1 states engine parameterized by protocol; Section 4.3 says same ACO engine traverses both graphs; Figure 2 shows identical engine applied to NAS and optimization. Break condition: poor schema design (missing roles, invalid transitions) leads to unreachable solutions or degenerate search.

### Mechanism 3: Offline Validation for Zero-Token Deployment
Offline validation of L1 operators ensures the online Symbolic Executor never encounters invalid code, enabling zero-LLM-token deployment. L1 operators are generated by an LLM but validated offline (syntax check, timeout, result verification). Only validated operators enter the pool. The online executor is a pure symbolic interpreter: it loads the snapshot and applies pheromones/rules to select pre-validated operators—no synthesis, no API calls. Core assumption: the space of valid operators is discoverable offline and small enough to enumerate with bounded tokens. Evidence: Section 3.4 says all L1 operators validated before online; Section 9.2 reports pool converges to 100% validated within 2–3 cycles; Table 18 shows offline cost ∼15k tokens, online 0. Break condition: validation might miss subtle semantic errors (e.g., operators that run but produce invalid solution representations), causing silent failures.

## Foundational Learning
### Procedural vs. Declarative Knowledge Graphs
**Why needed**: GEAKG captures *how-to* knowledge (operator sequences) rather than *what-is* facts. Misunderstanding this leads to expecting SPARQL-like queries instead of executable search policies.
**Quick check**: What's the difference between storing "swap is an LS operator" (declarative) and storing "after `CONST_GREEDY` prefer `LS_INTENSIFY_SMALL` with pheromone 0.92" (procedural)?

### RoleSchema as Ontology
**Why needed**: The `RoleSchema` is the *only* domain-specific artifact. Its quality determines transferability. It is not a data schema but an *algorithmic ontology* defining atomic search behaviors.
**Quick check**: When designing a `RoleSchema` for robotic task planning, what would you include: roles, categories, transition rules?

### ACO as Graph Refinement
**Why needed**: ACO isn't just a search algorithm—it's a *knowledge acquisition* process that converts LLM priors (L0 weights) into empirical transition preferences (L2). Without it, L0 remains static and brittle.
**Quick check**: How does the pheromone update rule (`τ_ij ← (1-ρ)τ_ij + Δτ_best`) differ from gradient-based reinforcement in neural networks?

## Architecture Onboarding
**Component map**: RoleSchema -> Offline Pipeline (LLM generates L0 topology & L1 operators; validation; ACO learns L2 pheromones & rules) -> Snapshot (JSON) -> Online: Symbolic Executor + DomainBinding -> Solutions. Data flow: Snapshot is the transfer unit; only DomainBinding changes per target.

**Critical path**: 1. Design RoleSchema (hours of domain expertise). 2. Run offline pipeline (LLM tokens + ACO compute). 3. Serialize snapshot (∼1–3 KB). 4. Deploy by plugging in new DomainBinding.

**Design tradeoffs**:
- **Schema generality vs. expressivity**: Abstract roles transfer broadly but lose domain nuances; concrete roles specialize faster but don't transfer.
- **Token budget allocation**: More tokens for L1 operator quality vs. L0 topology exploration (coverage). Paper allocates 15k to one embedded LLaMEA operator, 35k to rest.
- **Validation strictness**: Tight validation ensures reliability but may reject creative operators. Paper uses syntax + timeout + result checks.

**Failure signatures**:
- **L1 validation failures >30%**: LLM generating operators outside role semantics or with syntax errors. Fix: tighten prompts or use smaller design axes.
- **Pheromone entropy near uniform**: ACO failed to learn; either operators are all equal or search budget too low. Fix: increase ACO iterations or improve operator diversity.
- **Transfer gap degrades sharply on target**: RoleSchema mismatches or L2 rules overfit source instances. Fix: review category transitions, ensure `Revisitability` flags correct.

**First 3 experiments**:
1. **Toy example (Section 3.12)**: Run the 5-city TSP end-to-end. Verify `greedy_nn → 2opt` pheromone converges > `greedy_nn → swap`. Confirm snapshot transfers by swapping `ctx.evaluate()` only.
2. **Pure mode validation (Section 6.2.1)**: Deploy a TSP-learned snapshot on JSSP using only generic permutation operators. Expect moderate gaps on small JSSP (≤20×5), larger on bigger—this establishes baseline transfer.
3. **Cross-dataset ablation (Section 7.2.3)**: On NAS-Bench-Graph, pick one source (e.g., Cora) and one target (e.g., Photo). Compare Symbolic Executor vs. Random Search (same operator pool). Expect 100% win rate—isolates value of learned sequencing.

## Open Questions the Paper Calls Out
1. **Can RoleSchema ontologies be automatically generated from domain descriptions?**  
   *Basis*: Future work includes LLM-assisted schema derivation.  
   *Why unresolved*: Manual design requires domain expertise and hours of modeling.  
   *Resolving evidence*: An LLM-based system that, given a problem statement or operator implementations, outputs a valid RoleSchema (roles, categories, transition rules) that yields performance comparable to manual schemas.

2. **Can the Symbolic Executor perform lightweight runtime adaptation?**  
   *Basis*: All learning is offline; online adaptation is future work.  
   *Why unresolved*: Fixed rules may not generalize across heterogeneous instance distributions.  
   *Resolving evidence*: A mechanism that modifies pheromone evaporation rates or applies minor rule adjustments based on instance-specific stagnation metrics, validated by improved performance on diverse benchmarks without LLM calls.

3. **Does the engine support transfer across domains with different solution representations?**  
   *Basis*: "Transfer beyond permutations: Extend to binary vector and partition representations" is future work.  
   *Why unresolved*: All experiments use permutation representation; domain-agnosticism untested beyond this family.  
   *Resolving evidence*: Successful instantiation for continuous (e.g., neural weight tuning) and binary (e.g., knapsack) problems using appropriate RoleSchemas, then zero-shot transfer between them or to/from permutation domains.

4. **Can procedural knowledge transfer between orthogonal application domains (e.g., optimization ↔ NAS)?**  
   *Basis*: "Direct cross-family snapshot transfer (optimization↔NAS) remains future work."  
   *Why unresolved*: Current transfers are within-family; cross-family would test truly general algorithmic patterns.  
   *Resolving evidence*: Train on TSP and deploy on NAS-Bench-Graph with only binding changes; if the search policy consistently outperforms random ordering of the same operator pool, it indicates cross-domain transfer of meta-level procedural knowledge.

## Limitations
- **Manual RoleSchema design**: The only domain-specific artifact requires hours of expert modeling, limiting scalability and introducing designer bias.
- **Missing implementation details**: Exact LLM prompts, ACO hyperparameters, and validation procedures are undisclosed, hindering exact replication.
- **Validation gaps**: Offline validation may miss subtle semantic errors in operators, potentially causing silent failures on target domains.

## Confidence
- **Cross-domain transfer**: High (strong zero-shot results on optimization and NAS).
- **RoleSchema interface**: Medium (engine works across domains but schema quality is manual and unquantified).
- **Zero-token deployment**: High (validated operators run safely; edge-case bugs possible but unlikely).

## Next Checks
1. **Reproduce TSP toy (Sec 3.12)**: Confirm pheromone convergence (e.g., `greedy_nn → 2opt` > `greedy_nn → swap`) and transfer by changing only `DomainContext`.
2. **Ablate RoleSchema**: For TSP, create alternative schemas (e.g., more granular roles) and test zero-shot on JSSP/QAP to measure sensitivity to schema design.
