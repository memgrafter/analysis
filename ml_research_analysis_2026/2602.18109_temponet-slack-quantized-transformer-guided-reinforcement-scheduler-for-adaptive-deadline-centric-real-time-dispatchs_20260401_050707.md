# TempoNet: Slack-Quantized Transformer-Guided Reinforcement Scheduler for Adaptive Deadline-Centric Real-Time Dispatchs

## Quick Facts
- arXiv ID: 2602.18109
- Source URL: https://arxiv.org/abs/2602.18109
- Reference count: 40
- Primary result: Achieved up to 79% deadline compliance (+7.57% over DQN, +67.33% over conventional schedulers) on a standard task configuration.

## Executive Summary
TempoNet is a reinforcement learning-based scheduler designed to meet tight deadlines in real-time systems while respecting strict compute constraints. Its core innovation lies in a permutation-invariant Transformer architecture that processes task sets via a slack-quantized tokenizer and a latency-aware sparse attention stack. This design enables efficient global reasoning with near-linear computational complexity and sub-millisecond inference, even for large task sets. A dedicated multicore mapping layer then translates contextualized Q-values into processor assignments.

Extensive evaluations on industrial mixed-criticality traces and various multiprocessor configurations demonstrate substantial gains over conventional schedulers and neural baselines. On a standard task configuration, TempoNet achieved 79% deadline compliance, representing a 7.57% absolute improvement over feedforward DQN and a 67.33% improvement over conventional schedulers. Over 200 random task sets with utilizations between 0.6 and 1.0, the mean compliance was 85% (σ=0.27), a 14.86% relative improvement over DQN. Success rates for 100 and 600 tasks were 98.2% and 90.1%, respectively. In industrial scenarios, PITMD reached 89.15% (+1.87% over DIOS) and average response time decreased by 25.7%.

## Method Summary
TempoNet employs a reinforcement learning framework where the scheduler is modeled as a policy network that maps a set of tasks to processor assignments. The input task set is first transformed by a slack-quantized tokenizer, which discretizes each task’s temporal slack into a finite set of learned embeddings. These embeddings are fed into a permutation-invariant Transformer encoder that uses a sparse attention mechanism. The sparse attention combines blockwise top-k selection and locality-sensitive chunking to reduce the quadratic complexity of standard attention to near-linear scaling while still capturing long-range dependencies. The encoder produces contextualized representations, from which a multicore mapping layer derives Q-values for assigning tasks to cores. During training, the policy is optimized to maximize deadline compliance under given compute constraints using appropriate RL algorithms.

The design emphasizes global reasoning (via Transformer) and computational efficiency (via sparse attention and quantization), enabling the scheduler to operate with sub-millisecond inference latency even for hundreds of tasks. This makes TempoNet suitable for online dispatching in large-scale real-time systems.

## Why This Works (Mechanism)
The slack-quantized tokenizer transforms continuous slack into discrete, learnable embeddings, allowing the Transformer to efficiently capture temporal urgency. Permutation invariance ensures robustness to arbitrary task ordering, essential for scheduling. Sparse attention with blockwise top-k and locality-sensitive chunking reduces computational complexity while preserving global context, enabling sub-millisecond inference even for large task sets. The multicore mapping layer effectively translates Q-values into processor assignments, balancing load. RL training optimizes directly for deadline fulfillment, adapting to diverse workloads.

## Foundational Learning
1. **Permutation-Invariant Transformer**
   - Why needed: Task sets have no inherent order; the scheduler must treat tasks as unordered to avoid bias.
   - Quick check: Shuffle tasks in a test set; verify identical scheduling decisions.

2. **Slack Quantization**
   - Why needed: Raw slack values are continuous and may be sparse; quantization yields dense embeddings and improves learning efficiency.
   - Quick check: Compare performance using raw slack vs quantized embeddings.

3. **Sparse Attention (Blockwise Top-k & Locality-Sensitive Chunking)**
   - Why needed: Full attention scales quadratically; sparse patterns enable near-linear complexity while maintaining long-range dependencies.
   - Quick check: Plot inference time vs number of tasks; expect O(N^1.1) scaling rather than O(N^2).

4. **Reinforcement Learning for Scheduling**
   - Why needed: Analytic schedulers rely on heuristics; RL can learn complex, data-driven policies that maximize deadline compliance.
   - Quick check: Compare RL policy against classical algorithms (e.g., EDF) on unseen task sets.

## Architecture Onboarding
**Component map:** Task Set -> Slack-Quantized Tokenizer -> Permutation-Invariant Transformer (Sparse Attention) -> Multicore Mapping Layer -> Processor Assignments

**Critical path:** The input task set flows through the tokenizer, where each task's slack is quantized into an embedding. These embeddings are processed by the Transformer encoder with sparse attention to capture global context. The resulting representations are fed to the multicore mapping layer, which produces Q-scores for each task-core pair and outputs final assignments. Inference latency is dominated by the Transformer's attention layers.

**Design tradeoffs:**
- Slack quantization granularity: Finer buckets improve expressiveness but increase embedding size and computation; coarser buckets reduce cost but may lose nuance.
- Sparse attention accuracy vs speed: More aggressive sparsity yields better scaling but may omit important cross-task dependencies, risking deadline misses.
- Permutation invariance discards ordering information that might be useful (e.g., task release order); using positional encodings could break invariance and add sensitivity.
- RL training stability: High-dimensional action space and sparse rewards make training challenging; requires careful hyperparameter tuning.

**Failure signatures:**
- Degradation in deadline compliance when task utilization approaches or exceeds 1.0, indicating the policy may not respect hard constraints.
- Inconsistent outputs when task order changed, suggesting permutation invariance is not properly enforced.
- Inference latency exceeding sub-millisecond threshold for large N, indicating sparse attention overhead is higher than expected.
- Multicore mapping producing unbalanced core loads, leading to localized bottlenecks.

**First experiments:**
1. Permutation invariance test: Randomly shuffle task order in a fixed set and compute output difference (e.g., assignment distribution). Expect near-zero difference.
2. Scaling benchmark: Run inference on task sets of varying sizes (N=50 to 1000) and plot latency; fit complexity exponent; confirm it is close to 1.1.
3. Baseline comparison: Evaluate TempoNet against EDF and a DQN baseline on a standard benchmark (e.g., synthetic task sets with 30% utilization margin) and report deadline compliance.
