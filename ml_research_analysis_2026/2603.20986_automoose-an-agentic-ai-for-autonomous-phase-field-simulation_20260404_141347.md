# AutoMOOSE: An Agentic AI for Autonomous Phase-Field Simulation

## Quick Facts
- **arXiv ID:** 2603.20986  
- **Source URL:** https://arxiv.org/abs/2603.20986  
- **Reference count:** 40  
- **Primary result:** AutoMOOSE automates MOOSE phase‑field simulation from natural language, achieving near‑expert input fidelity (6/12 structural blocks exact), accurate grain coarsening (R²=0.90–0.95), activation energy (0.296 eV) comparable to human runs, and autonomous recovery from three failure classes on a copper grain growth benchmark.

## Executive Summary
Phase‑field simulations in MOOSE are powerful for studying microstructural evolution but demand deep expertise to configure inputs, execute runs, and diagnose failures. AutoMOOSE lowers this barrier by deploying an agentic AI pipeline that transforms a natural‑language prompt into a full simulation workflow. The system orchestrates five specialized agents (Architect, Input Writer, Runner, Reviewer, Visualization), supported by a plugin architecture for different physics models. Validation on a four‑temperature copper grain growth benchmark (300–750 K) shows that the generated input files match an expert reference in 6 of 12 required structural blocks and are functionally equivalent in another 4. The recovered grain coarsening kinetics agree with theory (R² = 0.90–0.95 at T ≥ 600 K), and the activation energy extracted from an Arrhenius fit (Q_fit = 0.296 eV) is consistent with a human‑written run (Q_fit = 0.267 eV). The Reviewer autonomously resolves three common runtime failure classes (duplicate objects, duplicate keys, unused parameters), enabling uninterrupted execution. Parallel sweeps across temperatures achieve a 1.8× speedup over serial execution, and every run produces FAIR‑compliant provenance records.

## Method Summary
AutoMOOSE is a full‑stack system that translates natural‑language requests into executable MOOSE simulations. Its core is a five‑agent pipeline:
1. **Architect** parses the user prompt into a structured simulation plan *P* (JSON).
2. **Input Writer** coordinates six sub‑agents in dependency order (Mesh, Variables, Kernels, Materials, Postprocessors, Executioner) to generate the MOOSE input file. A key sub‑agent implements a physics‑parameter bridge that converts user‑provided, experimentally accessible quantities (grain boundary energy σ, width *w*<sub>GB</sub>, mobility *M*<sub>0</sub>, activation energy *Q*) into the phase‑field coefficients (*L*, µ, κ) required by the Allen‑Cahn GBEvolution model using deterministic equations from Moelans et al.
3. **Runner** launches the simulation, optionally in parallel across multiple temperatures, using a compiled `phase_field-opt` binary.
4. **Reviewer** examines non‑zero exit codes, parses the log, and, for known failure patterns, applies targeted corrections (e.g., halving the timestep, increasing mesh resolution, removing duplicate blocks) before re‑routing the plan to the Input Writer.
5. **Visualization** extracts time‑series data (e.g., grain count from `GrainTracker`), fits the coarsening law *1/N(t) – 1/N₀ = k̃(T) t*, performs an Arrhenius analysis to extract *Q*<sub>fit</sub>, and generates a narrated summary.
The system is modular: physics plugins implement `generate_input(**params)` and `parse_results(csv)`, allowing new models to be added without altering the core. The LLM backbone is `claude‑sonnet‑4‑20250514`.

## Key Results
- **Input fidelity:** 6 of 12 structural blocks exactly matched an expert reference; 4 were functionally equivalent.
- **Kinetic & thermodynamic accuracy:** Grain coarsening kinetics followed the expected law with R² = 0.90–0.95 at T ≥ 600 K; extracted activation energy *Q*<sub>fit</sub> = 0.296 eV, comparable to the human baseline of 0.267 eV.
- **Autonomy & performance:** The Reviewer resolved three runtime failure classes without human intervention; parallel execution yielded a 1.8× speedup; all runs produced FAIR‑compliant provenance metadata.

## Why This Works (Mechanism)

**Mechanism 1: Specialized agent decomposition.** The workflow is divided into five sequential agents (Architect, Input Writer, Runner, Reviewer, Visualization), each with a narrow scope and a concise system prompt (~100–300 tokens). The simulation plan *P* serves as the sole state passed between agents, enforcing clean separation of concerns and making data flow explicit. This modular architecture, inspired by prior agent systems for MOOSE, prevents cognitive overload and allows independent optimization of each stage. A break condition arises if an early agent corrupts *P* (e.g., malformed JSON), propagating errors downstream.

**Mechanism 2: Physics‑parameter bridge.** The Input Writer’s Materials sub‑agent converts user‑specified, measurable grain boundary properties (σ, *w*<sub>GB</sub>, *M*<sub>0</sub>, *Q*) into the phase‑field coefficients (*L*, µ, κ) required by the Allen‑Cahn GBEvolution model. This transformation relies on a deterministic algebraic mapping (Eq. 4) from Moelans et al., explicitly encoded in the sub‑agent’s prompt. By eliminating LLM recall for these calculations, the system avoids coefficient hallucinations and ensures physical consistency. If input values are physically unrealistic (e.g., negative σ), the subsequent solver divergence is handled by the Reviewer.

**Mechanism 3: Closed‑loop failure recovery.** When the Runner returns a non‑zero exit code, the Reviewer parses the error log, matches patterns against a taxonomy of common MOOSE failures (e.g., TIMESTEP_TOO_LARGE, MESH_RESOLUTION, DUPLICATE_OBJECT), and proposes a specific corrective action. The plan is then sent back to the Input Writer via a “retry arc” to regenerate the input with the fix. This loop enables autonomous resolution without human intervention for the three documented failure classes; unknown or ambiguous failures trigger a user confirmation step, preventing infinite retries.

## Foundational Learning
**Concept 1: Multiphysics Simulation Block Structure (MOOSE “blocks”)**  
*Why needed?* The Input Writer must produce 12 ordered blocks (Mesh, GlobalParams, Kernels, etc.) with correct cross‑references (e.g., `op_num` must be declared before Variables). Misunderstanding the DAG dependency leads to invalid inputs.  
*Quick check:* If you change the number of order parameters (`op_num`), which downstream blocks must be regenerated and why?

**Concept 2: Phase‑Field Parameter Bridging**  
*Why needed?* Users reason in terms of measurable grain boundary properties (σ, *w*<sub>GB</sub>, *M*<sub>0</sub>), but the solver requires coefficients (*L*, µ, κ). The automated bridge (Eq. 4) is the essential translation layer; misunderstanding it yields physically nonsensical simulations.  
*Quick check:* Given σ = 0.5 J/m² and *w*<sub>GB</sub> = 10 nm, calculate κ. Show your unit conversions.

**Concept 3: Convergence Failure Diagnostics (Nonlinear vs. Linear)**  
*Why needed?* The Reviewer classifies failures based on whether the nonlinear residual or the linear Krylov residual is problematic, which determines the fix (timestep cutback vs. solver tolerance adjustment).  
*Quick check:* A MOOSE log shows “Solver failures at timestep 50: |F|₂ = 1.2e‑2, initial residual = 1.2e‑2” with `nl_rel_tol = 1e‑8`. What is the most likely failure class and corrective action?

## Architecture Onboarding

**Component map**  
User → Browser UI → MCP server (port 8001) → FastAPI backend (server.py, port 8000) → Agent pipeline: f1(Architect) → f2(Input Writer + 6 sub‑agents) → f3(Runner) → (on success) f5(Visualization). On failure: f3 non‑zero exit → f4(Reviewer) ↺ f2. Plugin Registry loads physics modules from `plugins/`; MOOSE Engine executes the generated `.i` file; Data stored as simulation plan *P* (JSON) and run artifacts (`*.i`, `*.csv`, `metadata.json`, `record.json`).

**Critical path**  
*Happy path:* prompt → f1 generates *P* → f2 produces MOOSE input → f3 runs simulation (parallel if sweep) → on exit 0, f5 parses results, fits kinetics/Arrhenius, outputs narrative.  
*Failure path:* f3 exit ≠ 0 → f4 parses log, classifies failure, proposes corrected parameters → f2 regenerates input with corrections → resubmit via f3; loop repeats until success or unknown failure escalates.

**Design tradeoffs**  
- *Modular plugins vs. shared knowledge:* Plugin contract is minimal (2 functions), but Architect/Input Writer prompts must be specialized per plugin via `PLUGIN['system_prompt']`; adding new physics requires prompt engineering.  
- *Pre‑trained knowledge vs. RAG:* The system relies on the LLM’s internal MOOSE knowledge, which suffices for common blocks but risks hallucinations on rare ones; no retrieval from MOOSE documentation.  
- *Autonomous recovery vs. safety:* Reviewer auto‑corrects only three known failure classes with high confidence; unknown failures are escalated to the user to avoid infinite correction loops.

**Failure signatures**  
The Reviewer recognizes pattern‑matched error messages:  
- Duplicate UserObject (“A <type> ‘<name>’ already exists”) → remove duplicate block.  
- Duplicate parameter key (“duplicate key ‘<param>’”) → deduplicate.  
- Unused parameter (“unused parameter ‘Outputs/<subblock>/<param>’”) → strip.  
- Nonlinear divergence (residual stalls) → halve `dt_max` and/or increase `nl_max_its`.  
- Insufficient mesh (*h* > *w*<sub>GB</sub>/4) → increase `nx/ny`.  
- NaN values → validate positivity of physical parameters.  
- MPI deadlock → reduce MPI ranks to 1.

**First 3 experiments**  
1. **Smoke test:** Run the benchmark prompt from the paper; verify that *Q*<sub>fit</sub> ≈ 0.3 eV and R² ≥ 0.90 at T≥600 K.  
2. **Failure recovery test:** Intentionally set an excessively large timestep to trigger `TIMESTEP_TOO_LARGE`; confirm that Reviewer detects and corrects it on the first retry.  
3. **Plugin isolation test:** Create a stub plugin (e.g., spinodal decomposition), register it, prompt for that physics, and ensure the core system correctly invokes the plugin’s `generate_input` and `parse_results` without changes to the core code.

## Open Questions the Paper Calls Out
1. **RAG integration** – *Question:* Does adding retrieval‑augmented generation over MOOSE docs improve first‑attempt success and fidelity for less‑common physics? *Basis:* Authors cite RAG as the most impactful near‑term extension. *Unresolved:* Current system lacks RAG; its effect on coverage and accuracy is unknown. *Evidence needed:* Benchmark no‑RAG vs. RAG across diverse MOOSE modules, measuring first‑attempt success and block‑by‑block fidelity.
2. **Multi‑tier Reviewer** – *Question:* Would a multi‑tier retry policy (e.g., timestep cutback → mesh refinement → solver fallback) increase autonomous recovery across a broader error spectrum? *Basis:* Proposed as future work; present Reviewer solves only three documented classes. *Unresolved:* Recovery for novel/composite failures is unclear. *Evidence needed:* Test suite of MOOSE errors comparing single‑cycle vs. multi‑tier reviewers, quantifying recovered vs. remaining failures.
3. **Grain count scaling** – *Question:* How does increasing the number of initial grains reduce the discrepancy between the input activation energy *Q* and the fitted *Q*<sub>fit</sub>? *Basis:* The observed error (0.296 eV vs. 0.23 eV) is attributed to finite‑size effects in the 15‑grain system. *Unresolved:* No systematic scaling study. *Evidence needed:* Runs with varying initial grain counts (e.g., 15, 30, 60, 120) while keeping other parameters fixed, extracting *Q*<sub>fit</sub> for each to quantify convergence.
4. **Agent decomposition benefit** – *Question:* Does the five‑agent pipeline yield higher reliability and lower error rates than a monolithic single‑agent approach? *Basis:* Authors argue specialization improves reliability but provide no comparison. *Unresolved:* Relative benefit of decomposition is unknown. *Evidence needed:* Implement a single‑agent variant that performs all tasks, benchmark both systems on the grain‑growth task, and compare input fidelity, failure recovery, and end‑to‑end success.

## Limitations
- **Build configuration:** The exact MOOSE version, PETSc/Trilinos variants, compiler flags, and optimization settings are unreported, which may affect reproducibility, convergence behavior, and Reviewer intervention frequency.
- **LLM inference parameters:** Temperature, top‑p, and max‑token limits are not disclosed, introducing potential variability in generated content.
- **Limited failure coverage:** The Reviewer handles only three specific runtime error classes; novel or composite failures still require human input.
- **Performance claims:** Speedup measurements were performed on a single MacBook Pro; scalability to HPC clusters or different architectures is unverified.

## Next Checks
1. **Cross‑platform reproducibility:** Replicate the copper grain growth benchmark on at least two distinct systems (different MOOSE/PETSc builds, operating systems), measuring the frequency of Reviewer interventions and consistency of the 1.8× speedup.
2. **Parameter bridge ablation:** Disable the analytical parameter bridge and allow the LLM to generate phase‑field coefficients directly; compare resulting kinetic fidelity (R²) and failure rates against the standard pipeline.
3. **Plugin generalizability test:** Implement a new physics plugin (e.g., Cahn‑Hilliard), register it, and run a natural‑language prompt for that model; assess whether the generated simulation is physically plausible without manual tuning.
