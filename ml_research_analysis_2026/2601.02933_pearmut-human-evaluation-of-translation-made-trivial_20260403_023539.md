# Pearmut: Human Evaluation of Translation Made Trivial

## Quick Facts
- arXiv ID: 2601.02933
- Source URL: https://arxiv.org/abs/2601.02933
- Reference count: 40
- Primary result: Pearmut reduces researcher setup time (11 minutes vs. 19–25 minutes), achieves highest ease-of-use (9.0/10), and scales to 2000 concurrent users, making reliable human evaluation practical for routine model development.

## Executive Summary
Human evaluation is crucial for multilingual NLP but rarely used due to complex setup and operational overhead of existing tools. Pearmut is a lightweight, pip-installable platform that simplifies running end-to-end human evaluation for translation and multilingual tasks. It provides pre-configured support for standard protocols (DA, ESA, MQM) with features like document-level context and contrastive evaluation. User studies show Pearmut has the fastest researcher setup time (11 minutes vs. 19–25 minutes) and highest ease-of-use score (9.0/10). Annotators complete tasks faster (124s vs. 145s per item) and report higher satisfaction. Server benchmarks demonstrate at least 3× faster response times than Appraise and support for up to 2000 concurrent users on modest hardware, making reliable human evaluation practical for routine model development.

## Method Summary
Pearmut is a lightweight platform for human evaluation of translation, distributed as a pip package to minimize setup and operational overhead. Users define an evaluation campaign via a JSON configuration file specifying the protocol (DA, ESA, MQM), assignment strategy, and data. The FastAPI server serves static files and provides API endpoints; a TypeScript/jQuery frontend handles annotation collection. Data is stored in-memory for fast reads, with an append-only log on disk for durability. The system includes document-level context, contrastive evaluation, AI pre-annotations (ESAAI), and dynamic assignment to optimize annotation effort.

## Key Results
- Pearmut reduces researcher setup time (11 minutes vs. 19–25 minutes) and achieves the highest ease-of-use score (9.0/10).
- Annotators complete tasks faster (124s vs. 145s per item) and report higher satisfaction (8.3 vs. 6.3 speed score).
- Server benchmarks show at least 3× faster response times than Appraise and support up to 2000 concurrent users on modest hardware.

## Why This Works (Mechanism)
### Mechanism 1: Simplified setup and deployment
- **Claim:** Pearmut reduces the time and effort required to set up a human evaluation campaign by providing a simple installation process and pre-configured protocols.
- **Mechanism:** Pearmut is distributed as a pip package, and setting up a campaign requires only three commands: `pip install`, `pearmut add` (with a JSON configuration file), and `pearmut run`. The tool provides reasonable defaults for common translation evaluation protocols (DA, ESA, MQM) so that researchers do not need to build these from scratch.
- **Core assumption:** The primary barrier to running human evaluation is the engineering and operational overhead of existing tools; by minimizing these, researchers are more likely to incorporate human evaluation into their workflow.
- **Evidence anchors:**
  - [abstract]: "lightweight yet feature-rich platform that makes end-to-end human evaluation as easy to run as automatic evaluation."
  - [section 4]: "Pearmut has the fastest researcher setup time (11 minutes vs. 19–25 minutes)" and "highest ease-of-use score (9.0/10)".
  - [corpus]: Corpus evidence is weak; neighboring papers are about multilingual MT benchmarks, not evaluation tools.
- **Break condition:** If a researcher needs a highly customized protocol that is not achievable via the JSON configuration, they may still need to modify the codebase, reducing the simplicity benefit.

### Mechanism 2: Domain-specialized interface and protocol support for translation
- **Claim:** Pearmut's focus on translation evaluation with built-in support for standard protocols and features like document-level context and contrastive evaluation leads to more efficient and higher-quality annotations.
- **Mechanism:** Pearmut implements interfaces specifically designed for translation tasks, such as showing source and reference alongside translations, supporting error span annotations, and allowing contrastive (side-by-side) evaluation. It also supports AI pre-annotations (ESAAI) and dynamic assignment to optimize annotation effort.
- **Core assumption:** General-purpose annotation tools do not cater to the specific needs of translation evaluation (e.g., span-level error marking, document context), leading to inefficiencies and lower-quality data. By specializing, Pearmut reduces cognitive load and streamlines the annotation process.
- **Evidence anchors:**
  - [abstract]: "engineered specifically for multilingual and translation evaluation", "implements standard evaluation protocols, including DA, ESA, or MQM", "features document-level context, absolute and contrastive evaluation".
  - [section 5]: Annotators complete tasks faster (124s vs 145s per item) and report higher satisfaction (8.3 vs 6.3 speed score) compared to Appraise.
  - [section 2]: Contrast with general-purpose tools like Label Studio, which "lack the specific logic required for modern translation evaluations".
- **Break condition:** For non-translation multilingual tasks (e.g., summarization, dialogue), the specialized features might not be as beneficial, and the tool may not be the best choice.

### Mechanism 3: Efficient server architecture enabling low latency and high concurrency
- **Claim:** Pearmut's lightweight server architecture (static file serving, client-side logic, in-memory storage with append-only log) provides fast response times and scales to thousands of concurrent users on modest hardware.
- **Mechanism:** The server serves static files and the frontend makes API calls for data, avoiding server-side template rendering. Data is stored in-memory for fast reads, with writes logged to disk for durability. This reduces overhead and improves responsiveness.
- **Core assumption:** Existing tools like Appraise use server-rendered templates and databases, which introduce latency and resource consumption, limiting scalability. A more streamlined architecture can handle more concurrent users with less hardware.
- **Evidence anchors:**
  - [appendix A.1]: Detailed architecture description: "does not use server-rendered templates", "frontend queries the server", "in-memory for low-latency read access", "append-only log file".
  - [section E]: Server benchmarks show "at least 3× faster response times than Appraise" and "supporting up to 2000 concurrent users on modest hardware".
  - [corpus]: No direct evidence; corpus neighbors are about MT models, not evaluation tools.
- **Break condition:** The in-memory storage may become a bottleneck for extremely large campaigns (millions of annotations) or if the server crashes without a backup (though the log helps). Also, the single-threaded design might limit scaling on multi-core systems without modifications.

## Foundational Learning
- **Translation evaluation protocols (DA, ESA, MQM)**: Why needed: Pearmut implements these protocols; the user must understand their differences to select the appropriate one for their study and interpret results correctly. Quick check: What is the key difference between ESA and MQM? (Answer: MQM includes error categories, while ESA only uses severity.)
- **Assignment strategies (task-based, single-stream, dynamic)**: Why needed: The assignment strategy affects the efficiency of annotation collection and potential biases. Quick check: In the JSON config, what does the `"assignment"` field control, and what are the possible values? ## Architecture Onboarding
**Component map**:
- CLI tool (`pearmut`): for installing, adding campaigns, running server.
- Server (FastAPI): serves static files and API endpoints.
- Frontend (TypeScript/jQuery): annotation interface and dashboard.
- Data storage: in-memory dictionary with append-only log file on disk.
- Campaign definition: JSON file specifying protocol, assignment, data.

**Critical path**:
1. `pip install pearmut`
2. Create a JSON campaign config (see Appendix F for examples).
3. `pearmut add campaign.json` to register.
4. `pearmut run` to start server; generate magic links.
5. Annotators use links to access interface; annotations are saved.
6. Researcher uses dashboard to monitor and export results.

**Design tradeoffs**:
- Speed vs. features: Pearmut prioritizes low latency by avoiding server-side rendering and using in-memory storage, at the cost of immediate durability (mitigated by log) and potential memory limits.
- Specialization vs. generality: By focusing on translation evaluation, Pearmut provides optimized workflows but may not suit other NLP tasks without modification.
- Simplicity vs. control: The JSON config and defaults reduce setup complexity but may limit fine-grained control for advanced users.

**Failure signatures**:
- Server fails to start: Check for port conflicts, invalid JSON config, missing dependencies.
- Annotators see blank page or errors: Static files not served, frontend build issue, network issues.
- Annotations not saving: In-memory storage full? Log write permission? Server crash?
- Slow response: Too many concurrent users, server resource bottlenecks, network latency.
- Dashboard not showing data: Campaign not properly added, data not loaded, or browser cache.

**First 3 experiments**:
1. Run the example campaign from the README to verify installation and see the basic annotation flow.
2. Modify the example JSON to change the protocol (e.g., from ESA to MQM) and observe the interface changes (additional category selection).
3. Set up a campaign with two different assignment strategies (e.g., task-based vs single-stream) and examine how items are distributed in the dashboard.

## Limitations
- External validity of user study: sample size, annotator backgrounds, and statistical significance are unspecified.
- Long-term reliability: in-memory storage with append-only log may face corruption or memory limits in very large campaigns.
- Generalization beyond translation: claims for non-translation tasks are unsupported; specialized features may be irrelevant.

- **Medium**: Scalability claim for routine model development.
