# Ontology-to-tools compilation for executable semantic constraint enforcement in LLM agents

## Quick Facts
- arXiv ID: 2602.03439
- Source URL: https://arxiv.org/abs/2602.03439
- Reference count: 40
- Primary result: The system achieved micro-F1 0.826 and macro-F1 0.785 on a benchmark of 30 metal–organic polyhedra synthesis papers; constraint feedback improved synthesis step F1 from 0.843 to 0.572 when removed.

## Executive Summary
This work solves the challenge of extracting structured data from scientific literature while guaranteeing adherence to formal ontological constraints. Traditional pipelines rely on error‑prone post‑hoc validation or manual engineering. The proposed solution, ontology‑to‑tools compilation, automatically transforms a domain T‑Box into a set of MCP‑compatible tool interfaces. An LLM agent must invoke these tools to modify a shared knowledge graph, causing every change to be validated against the ontology and providing structured feedback on violations. On a benchmark of 30 metal–organic polyhedra synthesis papers, the approach yields strong graph‑recoverable performance: micro‑F1 0.826, macro‑F1 0.785 across categories. Crucially, removing constraint feedback reduces synthesis step F1 from 0.843 to 0.572, highlighting the importance of runtime enforcement.

## Method Summary
The pipeline consists of two main stages. In the preparation stage, a meta‑prompted LLM agent reads a domain ontology (T‑Box) and compiles it into executable artifacts: (i) a static JSON task plan defining the sequence of extraction actions, (ii) a domain‑specific MCP server whose tools encode hard constraints (e.g., unit checks, cardinalities) as runtime validators, and (iii) ontology‑aware instantiation prompts. In the instantiation stage, another LLM agent processes each paper following the JSON plan. It reads document snippets, decides which MCP tool to call, and invokes the tool to create or update individuals in a persistent Turtle‑based knowledge graph. Tool calls are validated immediately; on constraint violation the tool returns a detailed error message, prompting the agent to retry with corrected arguments. After all steps, an optional grounding stage aligns extracted chemical entity IRIs to canonical identifiers via a fuzzy lookup against a cached label index from the reference knowledge graph. This end‑to‑end flow embeds semantic constraints directly into the extraction process, preventing invalid states and guiding the agent through interactive repair.

## Key Results
- Micro‑aggregate F1: 0.826; macro‑F1: 0.785 (CBU 0.771, characterisation 0.788, synthesis steps 0.843, chemicals 0.736).
- Ablation: disabling constraint feedback reduces synthesis steps F1 from 0.843 to 0.572, demonstrating its critical role in completeness and structural integrity.
- Chemical entities: perfect precision (1.000) but recall limited to 0.582, indicating challenges in chemical grounding.

## Why This Works (Mechanism)

### Mechanism 1: Compile‑Time Translation of Ontology Constraints into Tool Validation
The preparation agent converts T‑Box axioms and annotations into Python tool functions that perform upfront validation on inputs. Each tool call checks class/property typing, datatype restrictions, and cardinalities; violations produce structured feedback for the agent to revise. This enforces hard constraints at runtime, preventing invalid graph states. The core assumption is that constraints are faithfully encoded and the agent can interpret feedback. Evidence includes the abstract’s description of “executable tool interfaces” and Section 3’s treatment of the T‑Box as a “machine‑readable contract”. The mechanism fails if the agent repeatedly violates constraints and cannot recover, leading to stalled instantiation.

### Mechanism 2: Stateful, Iterative Construction via Persistent Memory
All tool operations read from and write to a shared Turtle file, acting as persistent cross‑step memory. This allows incremental construction of complex, linked instances; previously created individuals remain available for reuse, ensuring global consistency. The core assumption is that the store remains accessible and IRI minting/lookup functions correctly identify reuse opportunities. Evidence: abstract mentions “iteratively applies them” and Section 6.2 describes the Turtle‑based memory. Failures include file corruption, IRI collisions, or missed reuse leading to duplicates or orphans.

### Mechanism 3: Domain‑Agnostic Compilation via Meta‑Prompts
Generic meta‑prompts guide the preparation agent to decompose the extraction task, generate Python scripts, and produce instantiation instructions for any T‑Box. This separates domain‑independent orchestration from domain‑specific knowledge, reducing manual re‑engineering when schemas change. Core assumption: meta‑prompts are expressive enough to cover diverse ontology constructs. Evidence: abstract’s claim of reducing manual schema engineering and Section 6.1’s description of domain‑agnostic meta‑prompts. Break condition arises when the ontology contains unsupported patterns (e.g., unusual cardinalities), requiring manual intervention.

## Foundational Learning

### Ontology T‑Box vs A‑Box
- **Why needed here**: The T‑Box (schema) is compiled into tools that enforce constraints; the A‑Box (instances) is built by the agent during instantiation. This separation clarifies how constraints are applied at creation time.
- **Quick check**: What is the functional difference between a T‑Box and an A‑Box in a knowledge graph?

### Model Context Protocol (MCP)
- **Why needed here**: MCP standardizes the interface between LLM agents and external tools. The ontology‑compiled tools are exposed as MCP servers, which the agent calls with structured arguments. Without MCP, integration would be ad‑hoc.
- **Quick check**: How does MCP enable tool use by LLM agents, and what are its key components?

### ReAct‑Style Reasoning Loop
- **Why needed here**: The instantiation agent follows a reasoning‑and‑acting cycle: it reads document snippets, decides which tool to call, observes the result (including validation feedback), and iterates. This loop is essential for handling constraint‑driven repairs.
- **Quick check**: Describe the ReAct pattern and explain why it suits interactive knowledge‑graph construction.

## Architecture Onboarding

**Component map**  
Preparation agent (LLM) → generates: JSON task plan, ontology‑specific MCP server (tool functions), instantiation prompts.  
Instantiation agent (LLM) → executes plan: reads document, calls MCP tools, updates Turtle store, processes feedback.  
MCP servers: Instantiation server (custom tools), PubChem server, CCDC server (external grounding).  
Persistent store: Turtle file (cross‑step memory).  
Grounding agent (LLM) → aligns instance IRIs to canonical KG IRIs using label index.

**Critical path**  
For a new synthesis paper: load MCP tools → instantiation agent runs JSON plan step‑by‑step. Each step: read paper → extract evidence → decide tool calls → invoke tool → on constraint violation receive feedback → retry with corrected arguments → on success update Turtle store. After all steps, optionally run grounding stage to map chemical IRIs to canonical species.

**Design tradeoffs**  
- **Feedback vs speed**: Constraint feedback improves completeness but adds interaction rounds; disabling it speeds up runs but harms recall.  
- **Tool granularity**: Fine‑grained tools enable precise enforcement but increase planning complexity; coarser tools reduce LLM decisions but risk complex error handling.  
- **Meta‑prompt generality**: Generic meta‑prompts maximize reuse across domains but may miss domain‑specific subtleties; domain‑tuned prompts improve extraction but reduce portability.  
- **Hard vs soft constraints**: Hard constraints (T‑Box axioms) strictly enforced; soft constraints (rdfs:comment heuristics) encoded in prompts, less reliable.

**Failure signatures**  
- Missing chemical entities: lower recall for reaction chemicals (precision 1.0, recall 0.582) due to naming variability.  
- Constraint feedback removal: increased step‑number inconsistencies, extra redundant steps, regression to placeholder values.  
- Error concentration: a few fields dominate failures (e.g., `addedChemical.amts`, `atmosphere`, `duration`). Precision‑limited vs. recall‑limited fields differ.  
- Persistent validation errors: tool returns same error repeatedly, indicating agent inability to satisfy constraints.  
- High per‑paper error variance: a minority of papers account for majority of errors, suggesting problematic document characteristics.

**First 3 experiments**  
1. **Preparation validation**: Run preparation on a minimal test ontology; inspect generated Python tools to confirm hard constraints (e.g., unit checks) are encoded; verify JSON plan sequencing.  
2. **End‑to‑end single‑paper run**: Process one benchmark paper with full pipeline; use evaluation scripts to reconstruct JSON from Turtle output and compare against ground truth; observe constraint feedback traces.  
3. **Ablation of constraint feedback**: Modify instantiation MCP server to disable feedback; re‑run same paper; measure synthesis‑step F1 drop; inspect Turtle for step‑number integrity issues and placeholder values.

## Open Questions the Paper Calls Out

1. **Question**: How does performance change when the underlying T‑Box is modified (e.g., adding/removing classes or constraints)? **Basis**: Section 5.2 (Future work) explicitly states the need to evaluate robustness under ontology change. **Why unresolved**: Only a fixed ontology was used in the current evaluation; adaptive capacity of the compilation is untested. **What would resolve it**: Deliberately alter the ontology (add new constraints, new class, change cardinalities), re‑run the full compilation, and quantify the success rate of automatic tool/prompt regeneration and any need for manual intervention, while monitoring extraction performance stability.

2. **Question**: To what extent are the observed performance characteristics and error modes specific to the MOP synthesis domain, versus fundamental to the ontology‑to‑tools approach? **Basis**: Section 5.1 acknowledges the evaluation covers only one ontology and one document collection. **Why unresolved**: No cross‑domain validation has been performed; error patterns may stem from idiosyncrasies of MOP reporting styles. **What would resolve it**: Replicate the pipeline in another scientific domain (e.g., organic synthesis or battery materials) with a suitable curated benchmark; compare error signatures (e.g., unit normalization, entity grounding) to identify which are universal versus domain‑specific.

3. **Question**: What are the computational and temporal trade‑offs of enforcing constraints at generation time versus a post‑hoc validation pipeline, especially as ontology complexity and document length grow? **Basis**: Inferred from the interactive ReAct loop with constraint feedback; the ablation shows efficacy but not efficiency. **Why unresolved**: The paper does not compare token usage, number of LLM calls, or latency against a “single‑pass extraction + batch validation” alternative. The scalability of iterative repair for long documents or large ontologies is unknown. **What would resolve it**: Measure average number of tool calls, interaction turns, and total processing time per document for the full system versus a no‑feedback ablation and a simulated post‑hoc validator; correlate these metrics with ontology size (number of constraints, classes) and document features (length, number of steps).

4. **Question**: How dependent is the system on the capability of the LLM used for instantiation, and are the benefits of constraint feedback equally pronounced across models of varying size and cost? **Basis**: Section 6.7 lists model assignments (e.g., `gpt-4.1`, `gpt-4o`), but all results use high‑end OpenAI models. **Why unresolved**: The framework may require a sufficiently capable model to interpret feedback; cheaper or open‑source models might not utilize the constraint messages effectively. **What would resolve it**: Conduct controlled experiments varying the instantiation agent model (e.g., `gpt‑4o`, `gpt‑4o‑mini`, Claude Sonnet 3.5, Llama 3.1 70B) while keeping tools constant. For each model, compare performance with and without feedback to assess whether feedback gains are universal or model‑size dependent.

5. **Question**: Can the lexical grounding stage’s deterministic fuzzy‑lookup scale to handle polysemy and contextual variation in chemical nomenclature beyond the MOP domain, without prohibitive label‑index growth or false positives? **Basis**: Section 6.3 describes grounding via a locally cached label index and deterministic selection; the paper reports perfect precision but lower chemical recall (0.582). **Why unresolved**: The method assumes a finite set of labels; in broader chemistry, synonymy and abbreviation ambiguity are severe. It is unclear whether recall limitations stem from the fuzzy lookup algorithm, label‑index coverage, or extraction errors. **What would resolve it**: Perform an error analysis on the false‑negative chemical entities from the benchmark, categorizing failures as extraction failure, grounding failure, or wrong selection. Additionally, measure label‑index size and lookup latency as more reference data (e.g., larger PubChem subsets) is added to test scalability and the potential for false positives.

## Limitations
- Exact model assignments (e.g., GPT versions, temperatures) and inference settings for preparation and instantiation are unspecified, hindering reproducibility.
- The MCP helper library and server configuration details are not provided, which could lead to implementation discrepancies or subtle bugs.
- Evaluation is restricted to a single domain (metal‑organic polyhedra synthesis); cross‑domain generalizability remains unverified.

## Confidence
- Constraint feedback improves completeness: Medium.
- Domain‑agnostic compilation: Low‑Medium.
- Stateful memory ensures global consistency: Medium.
- End‑to‑end graph‑recoverable performance: Medium‑High.

## Next Checks
1. **Tool validation inspection**: Compile a minimal ontology and verify that the generated Python functions correctly encode constraints (e.g., unit checks, cardinalities).
2. **Cross‑domain generalization**: Run the pipeline on a distinct scientific domain (e.g., organic synthesis) using an appropriate ontology to test compilation robustness and error pattern consistency.
3. **Systematic feedback ablation**: Disable constraint feedback per tool and measure per‑field F1 changes to isolate which constraints contribute most to performance gains.
