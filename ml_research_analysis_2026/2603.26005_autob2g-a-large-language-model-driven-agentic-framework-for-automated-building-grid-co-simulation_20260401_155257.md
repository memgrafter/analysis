# AutoB2G: A Large Language Model-Driven Agentic Framework For Automated Building-Grid Co-Simulation

## Quick Facts
- **ArXiv ID:** 2603.26005
- **Source URL:** https://arxiv.org/abs/2603.26005
- **Reference count:** 33
- **Primary result:** Success rate up to 0.83 on complex tasks; code score 0.88; RL control reduced voltage deviation spread from ±0.4 p.u. to near nominal.

## Executive Summary
AutoB2G is an agentic framework that automates the entire building-grid (B2G) co-simulation workflow from natural-language task descriptions. It integrates CityLearn V2 for building control with Pandapower for power flow analysis, coupling them bidirectionally so that building load influences grid states and grid conditions affect building observations. The framework employs a DAG-structured codebase to guide an LLM-based retrieval process, ensuring a valid sequence of simulation modules, and uses the SOCIA multi-agent system with Textual Gradient Descent to generate and iteratively repair simulator code. Evaluated on tasks of varying complexity, SOCIA+AR achieved a success rate of up to 0.83 on complex tasks and a code score of 0.88, significantly outperforming baselines. The resulting RL-based control strategies improved grid-side metrics, notably reducing voltage deviation spread.

## Method Summary
AutoB2G constructs a DAG where nodes are functional modules (e.g., data generation, co-simulation setup, grid analysis) and edges encode dependencies. Given a natural-language task, a retriever agent proposes a candidate module sequence; a validator checks topological ordering and provides feedback until a valid path is found. This sequence templates the code generation. The SOCIA framework then iteratively produces simulator code via a Code Generator, executes it, evaluates results (e.g., compilation, metric accuracy), and if violations occur, a Feedback Generator formulates a textual gradient describing the error. The Code Generator patches the code based on this gradient, and a self-repair projection ensures basic feasibility before the next iteration. The generated simulator runs CityLearn V2 to produce building loads and receives grid states from Pandapower, enabling RL control that can be evaluated on grid metrics such as voltage deviation, N-1 resilience, and thermal loading.

## Key Results
- On complex tasks, SOCIA+AR achieved a success rate of 0.83 and a code score of 0.88, outperforming baselines (LLM, SOCIA, LLM+AR).
- RL-based control policies learned within the automated co-simulation reduced voltage deviation spread from approximately ±0.4 p.u. to a narrower distribution centered near the nominal voltage.
- The DAG retrieval mechanism was crucial for handling complex workflows; removing it (SOCIA without retrieval) led to lower success rates and inclusion of irrelevant modules.

## Why This Works (Mechanism)
### Mechanism 1: DAG-Guided Retrieval
- **Claim:** Structuring the codebase as a DAG enables an LLM agent to reliably retrieve a complete, executable sequence of functional modules for building-grid co-simulation workflows.
- **Mechanism:** The DAG explicitly encodes module dependencies and execution order. The agent receives the DAG structure as a planning problem, proposes candidate function sets, and a validator checks these sets against the DAG edges, returning structured feedback on missing prerequisites. The agent iteratively repairs its proposal until a topologically valid sequence is obtained, which then templates code generation.
- **Core assumption:** LLMs can follow structural constraints and incorporate dependency feedback when the problem is framed with explicit graph rules.
- **Evidence anchors:** Abstract and Section 3.1 describe the DAG retrieval process; validation through experiments shows improved success rates with retrieval.
- **Break condition:** Inaccurate DAG edges or LLM inability to consistently satisfy topological constraints will cause retrieval failure.

### Mechanism 2: Textual Gradient Descent (TGD) for Code Repair
- **Claim:** The TGD feedback loop within SOCIA can iteratively repair a non-executable simulator implementation into a feasible one.
- **Mechanism:** After execution, the Result Evaluator identifies constraint violations (e.g., compilation errors) and formulates them as constraint functions. The Feedback Generator converts these into a textual gradient—natural-language repair directives pinpointing the failed module and suggesting corrections. The Code Generator patches the code based on this gradient, with a self-repair projection step before the next iteration.
- **Core assumption:** LLM agents can accurately diagnose program failures from logs and generate minimal, correct patching instructions that move the code toward feasibility without new errors.
- **Evidence anchors:** Section 4.3 describes the TGD process; Section 5.3.1 provides concrete logs showing error identification and repair.
- **Break condition:** Ambiguous or incorrect textual gradients, interdependent errors, or LLM misdiagnosis can prevent convergence.

### Mechanism 3: B2G Coupling Enables Grid Evaluation
- **Claim:** Integrating CityLearn V2 with Pandapower in an automated pipeline allows RL actions to influence grid-level metrics and enables systematic grid-side evaluation.
- **Mechanism:** At each simulation step, CityLearn generates aggregated building loads from control actions, mapped to buses in a Pandapower network. Power flow computes grid states (voltages, line loadings), which are fed back into CityLearn’s observation space. Grid-specific metrics (voltage admissibility, N-1 resilience, etc.) are computed post-simulation from recorded trajectories.
- **Core assumption:** Building control policies exposed to grid state feedback and evaluated on grid metrics will learn co-optimizing strategies.
- **Evidence anchors:** Abstract and Section 2.2 detail the coupling; Section 5.4.2 shows voltage distribution narrowing under RL control.
- **Break condition:** Grid improvement depends on RL learning capacity, reward design, and grid topology; limited building control flexibility may yield no measurable grid-side benefit.

## Foundational Learning
- **Directed Acyclic Graph (DAG) for Workflow Encoding:**  
  *Why needed:* The retrieval mechanism depends on modeling simulation workflows as nodes (functions) and edges (dependencies); topological sorting ensures executability.  
  *Quick check:* If Function B requires output from A, and C requires both A and B, a valid order is [A, B, C]; [B, A, C] fails because B precedes A.
- **Textual Gradient Descent (Program-Space Optimization):**  
  *Why needed:* This is the core error-repair engine; instead of tuning numerical parameters, it edits source code based on natural-language feedback from execution failures.  
  *Quick check:* How does textual gradient differ from numerical gradient (e.g., ∂L/∂w)? The textual gradient explicitly contains a natural-language description of the violation and suggested repair, not a directional derivative in parameter space.
- **Building-to-Grid (B2G) Co-Simulation Coupling:**  
  *Why needed:* To extend or debug the framework, one must understand the bidirectional loop: building loads → grid power flow → grid states → building observations.  
  *Quick check:* In the described coupling, which grid state variable is fed back into CityLearn’s observation space, and which grid-side metric is penalized in Eq. (1)? (Answer: bus voltages; voltage deviation spread.)

## Architecture Onboarding
- **Component map:** DAG-Structured Codebase (modules with dependencies), Retriever Agent (LLM that proposes module sequences validated by DAG), SOCIA Multi-Agent Framework (Workflow Manager, Code Generator, Simulation Executor, Result Evaluator, Feedback Generator), Simulation Engines (CityLearn V2, Pandapower), Validator (checks topological order).
- **Critical path:** Natural Language Task → DAG retrieval loop (Retriever + Validator) → Validated Function Set S* → Template Θ(S*) → SOCIA TGD loop (Generate → Execute → Evaluate → Feedback → Repair) → Executable Simulator Code x*.
- **Design tradeoffs:**  
  - *Generality vs. Platform Specificity:* DAG and SOCIA are general, but current codebase is hardcoded for CityLearn+Pandapower; extending requires rebuilding DAG and adjusting prompts.  
  - *Automation vs. Debuggability:* Full automation reduces manual effort but yields black-box code; DAG template and TGD logs are primary debugging artifacts.  
  - *LLM Capability Dependency:* Success rates are tied to GPT-5; performance with other models is an open variable.
- **Failure signatures:**  
  - *DAG retrieval failure:* Agent repeatedly returns sets missing core functions (e.g., no power flow setup); validator feedback loops without convergence.  
  - *SOCIA non-convergence:* TGD iterations stall (loss stays >0) due to ambiguous feedback, interdependent errors, or LLM failing to apply patches.  
  - *Semantic misalignment:* Generated code runs but produces wrong grid metrics due to misrepresented module behavior or misinterpreted grid evaluation requirements.
- **First 3 experiments:**  
  1. Reproduce Table 3 & 4: Run SOCIA+AR and baselines on simple/medium/complex tasks; verify success rate and code score trends.  
  2. Isolate DAG impact: On a medium task, compare SOCIA+AR vs. SOCIA (no retrieval); audit code for irrelevant modules and measure success rate difference.  
  3. Grid metric sanity check: For a successful complex run, manually inspect final code to confirm Pandapower `runpp()` call, bus voltages fed into CityLearn observations, and post-simulation computation of N-1/voltage metrics.

## Open Questions the Paper Calls Out
- **Open Question 1:** How does AutoB2G's performance generalize when integrated with alternative building energy simulation engines (e.g., EnergyPlus directly, Modelica) and power system analyzers beyond Pandapower? The framework’s DAG and retrieval are tailored to CityLearn V2 and Pandapower; other tools may have different interfaces and break the pipeline.
- **Open Question 2:** To what extent can SOCIA with DAG-based retrieval accurately interpret and execute underspecified natural language task descriptions? Ambiguous requests may yield invalid workflows that TGD cannot repair without clarification, limiting real-world usability.
- **Open Question 3:** What is the computational overhead and convergence behavior of TGD as DAG complexity increases? TGD reliance on iterative textual feedback may cause more repair cycles, non-convergence, or error compounding with larger DAGs, yet scalability limits are not quantified.
- **Open Question 4:** Does AutoB2G maintain effective grid-side optimization on larger-scale distribution networks (e.g., IEEE 123-bus) with higher building-to-bus ratios? Grid dynamics and RL learning may scale nonlinearly; larger networks could introduce new constraints that challenge both simulation generation and controller effectiveness.

## Limitations
- **Generalizability:** Results are tied to GPT-5 and the IEEE 33-bus test case; performance with other LLMs or grid topologies is unknown.
- **Implementation Gaps:** Exact DAG schema, validator logic, and SOCIA prompt templates are not disclosed, requiring reconstruction.
- **LLM Dependency:** Both DAG retrieval and TGD convergence critically depend on the LLM’s ability to interpret structured feedback and diagnose failures, which may not hold for all models or complex tasks.
