# GroupGPT: A Token-efficient and Privacy-preserving Agentic Framework for Multi-User Chat Assistant

## Quick Facts
- **arXiv ID:** 2603.01059  
- **Source URL:** https://arxiv.org/abs/2603.01059  
- **Reference count:** 40  
- **Primary result:** Token-efficient multi-user chat assistant with privacy-preserving components, reducing token consumption by up to 3× and achieving 4.72/5.0 response quality.

## Executive Summary
GroupGPT addresses the dual challenges of token inefficiency and privacy risks in multi-user chat assistants by introducing a collaborative small-large model architecture. A lightweight **Intervention Judge** dynamically decides when the large language model (LLM) should generate a response, avoiding unnecessary computations. Parallel **Privacy Transcriber** and **Multimodal Processor** components handle PII sanitization and non-text input conversion, respectively. The system is evaluated on **MUIR**, a novel 2,500-segment benchmark for multi-user intervention reasoning, and demonstrates strong judge performance, significant token savings, high user-perceived privacy, and low latency in real-world studies.

## Method Summary
The framework processes multi-user chat streams through a pipeline: Multimodal Processor first converts images, memes, videos, and voice to text. The Privacy Transcriber then sanitizes PII from all text inputs. The Intervention Judge—a small, efficient model—analyzes the sanitized context to determine both *whether* and *when* the LLM should intervene. Only on positive intervention does the LLM generate a response, which may be further processed (e.g., sanitized) before delivery. This selective invocation reduces token usage versus always-on LLM baselines. Evaluation uses the custom MUIR benchmark (for judge accuracy) and user studies (for quality, privacy perception, latency).

## Key Results
- **Token efficiency:** Up to 3× reduction in token consumption vs. LLM-only baselines.
- **Judge performance:** Intervention Judge (Qwen-2.5-Instruct 3B) achieves 86.3% accuracy on intervention reason classification; timing judge (Qwen-3 4B) reaches 83.4% accuracy and 88.7% F1.
- **User satisfaction:** Average LLM-as-a-judge response quality score of 4.72/5.0; 84% of users perceived effective privacy sanitization with preserved meaning.

## Why This Works (Mechanism)
The mechanism hinges on **selective intervention** and **specialized preprocessing**. The Intervention Judge acts as a gatekeeper, avoiding costly LLM calls for routine or low-value messages (e.g., quick acknowledgments, off-topic banter), which are common in multi-user chats. This drastically cuts token usage. Privacy is maintained by sanitizing PII before any processing, preventing leakage through the LLM or logs. The Multimodal Processor ensures all input modalities are textually represented, enabling uniform processing by the judge and LLM. The small-large split balances speed (judge) and capability (LLM), while the modular design allows independent optimization of each component.

   *Why needed:* To gate LLM invocation, avoiding unnecessary computation on trivial messages.  
   *Quick check:* Evaluate its false negative rate on MUIR—missed interventions could degrade usefulness.

2. **Privacy Transcriber**  
   *Why needed:* To remove PII from chat streams before LLM processing, upholding privacy.  
   *Quick check:* Measure PII recall on a held-out dataset of synthetic PII-laden messages.

3. **Multimodal Processor**  
   *Why needed:* To unify diverse input types (images, voice, video) into text for downstream components.  
   *Quick check:* Assess transcription accuracy on a multimodal benchmark (e.g., How2 for video, VoxCeleb for voice).

4. **MUIR Benchmark**  
   *Why needed:* First dedicated dataset for multi-user intervention reasoning, addressing a gap in existing eval.  
   *Quick check:* Verify inter-annotator agreement on its labels and cross-check with human judgments on fresh chat logs.

5. **Small-Large Collaborative Architecture**  
   *Why needed:* To trade off between the efficiency of small models and the expressivity of large LLMs.  
   *Quick check:* Vary judge model size and measure token savings vs. quality drop on out-of-distribution chats.

## Architecture Onboarding
**Component Map**  
Input (multimodal) -> Multimodal Processor -> Privacy Transcriber -> Intervention Judge -> (if intervene) -> LLM -> Response

**Critical Path**  
1. Receive multi-user message.  
2. Multimodal Processor converts to text.  
3. Privacy Transcriber sanitizes text.  
4. Intervention Judge decides: intervene (call LLM) or not.  
5. If intervene, LLM generates response; response may be sanitized again.  
6. Send response to chat.

**Design Tradeoffs**  
- *Efficiency vs. Responsiveness:* Smaller judge reduces latency but may misclassify, requiring fallback strategies.  
- *Privacy vs. Utility:* Aggressive PII removal may strip context; conservative risks leakage.  
- *Generality vs. Cost:* Supporting more modalities increases processor complexity and inference time.

**Failure Signatures**  
- Judge false negatives: LLM never called → irrelevant/absent responses.  
- Judge false positives: Wasted LLM calls → token budget overruns.  
- Privacy Transcriber errors: PII leakage (recall failure) or nonsensical output (precision failure).  
- Multimodal Processor failures: Unsupported media types → pipeline stall.

**First 3 Experiments**  
1. **Judge calibration sweep:** Vary Intervention Judge model size (1B–7B) and threshold on MUIR to map accuracy-latency frontier.  
2. **Token accounting drill:** Run the full pipeline on a held-out multi-user corpus (e.g., public Discord logs) and compare token counts against a “always-call-LLM” baseline.  
3. **Privacy stress test:** Inject known PII strings (names, phones, emails) into synthetic chat streams and measure Privacy Transcriber’s recall/precision against a gold label set.

## Limitations
- Small-scale user validation; results may not generalize across demographics or conversation dynamics.  
- Reliance on “LLM-as-a-judge” for quality assessment introduces potential bias without human expert annotation.  
- Novel MUIR benchmark may not capture full real-world complexity or generalize across cultures/languages.

## Next Checks
1. **Reproduce token savings** on an independent large-scale multi-user chat corpus (e.g., public WhatsApp/Telegram datasets) using the same full-context LLM baseline.
2. **Adversarial privacy testing:** Inject benchmark PII (e.g., from HIPAA/PCN logs) into chat streams and measure Privacy Transcriber’s recall/precision against a held-out entity set.
3. **Cross-validate MUIR:** Train/evaluate the Intervention Judge on a different multi-user intervention dataset (if available) or via fresh human annotations on held-out chat logs to test for overfitting and domain shift.
