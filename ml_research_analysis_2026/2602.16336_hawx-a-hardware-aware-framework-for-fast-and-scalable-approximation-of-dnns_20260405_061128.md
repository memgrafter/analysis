# HAWX: A Hardware-Aware FrameWork for Fast and Scalable ApproXimation of DNNs

## Quick Facts
- **ArXiv ID:** 2602.16336
- **Source URL:** https://arxiv.org/abs/2602.16336
- **Reference count:** 17
- **Primary result:** Up to 23× speedup for layer-level and over 3×10⁶× speedup for filter-level search on LeNet-5 vs. exhaustive search, maintaining comparable accuracy.

## Executive Summary
HAWX provides a scalable framework for hardware-aware design space exploration of approximate DNNs. It uses a single profiling pass to compute multi-level sensitivity scores that hierarchically prune the search space, enabling efficient identification of Pareto-optimal configurations across diverse accelerator architectures. Evaluations on CNNs show exponential efficiency gains with model size and significant power/area reductions on both spatial and temporal platforms while meeting user-defined accuracy thresholds.

## Method Summary
Given a pretrained DNN, a dataset, a library of approximate hardware blocks (e.g., 8‑bit multipliers), an accelerator specification, and an accuracy threshold, HAWX proceeds in four steps. First, it selects K representative inputs using k‑means clustering on first‑layer activation statistics (mean, standard deviation) and performs a single GPU inference pass to extract the computation graph, operation types, and loss gradients. Second, for each operation‑input pair, it computes a hawx score as the product of gradient magnitude (`|∂L/∂o|`) and output deviation (`|Δout|`) when using an approximate block, then aggregates these scores to the operator, filter, layer, and model levels using mean absolute error. Third, it determines per‑layer hawx boundaries by evaluating full networks built with minimum, median, and maximum score blocks; if needed, binary search refines thresholds to satisfy the accuracy constraint while minimizing hardware cost. Finally, it maps the selected approximate blocks to the target accelerator (spatial or temporal) and estimates power/area from pre‑characterized block costs.

## Key Results
- **Scalability:** Achieves up to 23× speedup for layer‑level and over 3×10⁶× speedup for filter‑level search on LeNet‑5 compared to exhaustive search.
- **Efficiency scaling:** Benefits grow exponentially with network size; evaluated on VGG‑11, ResNet‑18, EfficientNetLite.
- **Hardware gains:** Delivers significant power and area reductions on both spatial (dataflow) and temporal (PERUN) accelerators while meeting accuracy thresholds.

## Why This Works (Mechanism)

#### Mechanism 1: Multi‑level sensitivity scoring
- **Claim:** Multi‑level sensitivity scoring (operator, filter, layer, model) enables efficient design space pruning by identifying approximation‑tolerant regions.
- **Mechanism:** HAWX computes a `hawx(o,i)` score per operation‑input pair using gradient magnitude (`|∂L/∂o|`) and output deviation (`|Δout|`). These are aggregated (MAE) to `hawx(o)`, then hierarchically to filter/layer/model scores. Boundary `hawx` values for layers are found via binary search on min/median/max score configurations, pruning all blocks below the threshold for that layer.
- **Core assumption:** The `hawx` score, combining gradient sensitivity and numerical deviation, is a reliable predictor of accuracy impact when scaling from individual operations to full layers.
- **Evidence anchors:** 
  - Abstract: "multi‑level sensitivity scoring at different DNN abstraction levels (operator, filter, layer, and model) to guide selective integration"
  - Section II.A: Definition of `hawx(o,i)` and aggregation to `hawx(f)`, `hawx(l)`, `hawx(model)`.
  - Corpus: Weak direct corpus evidence; hierarchical aggregation's predictive power is assumed.
- **Break condition:** If the relationship between layer‑level `hawx` scores and end‑to‑end accuracy is non‑monotonic or inconsistent across model architectures, the boundary search may prune valid configurations or miss optimal ones.

#### Mechanism 2: Single‑pass profiling with representative inputs
- **Claim:** A single network profiling pass with representative inputs provides sufficient data to compute all multi‑level `hawx` scores, avoiding repeated evaluations.
- **Mechanism:** HAWX selects K representative inputs via k‑means on first‑layer activation statistics (µ, σ). It then executes one full inference pass on these inputs on a GPU, extracting operation types, inputs, and gradients. All `hawx(o,i)` and subsequent aggregations are derived from this single pass.
- **Core assumption:** The k‑means selected inputs capture the diversity of the full dataset's activation distribution, making the sensitivity scores robust.
- **Evidence anchors:**
  - Section II.A: "A small subset of input samples is first selected as representative samples by a k‑means algorithm... The pretrained model is then executed... during which HAWX automatically identifies the types and number of all operations... computes the gradient."
  - Section III.B, Fig 2: Alignment between full dataset and representative sample activation distributions for LeNet‑5.
- **Break condition:** If the first‑layer activations are not a sufficient proxy for downstream layer sensitivity (e.g., in networks with highly nonlinear early layers), the representative set may not generalize, causing inaccurate `hawx` scores.

#### Mechanism 3: Hardware‑aware mapping and cost estimation
- **Claim:** Hardware‑specific mapping and cost estimation, guided by the pruned `hawx` boundaries, yields Pareto‑optimal accuracy‑power‑area trade‑offs for both spatial and temporal accelerators.
- **Mechanism:** After determining layer‑level `hawx` boundaries that meet the accuracy threshold, HAWX maps approximate blocks to hardware granularities (op/filter/layer). For spatial architectures, it accounts for PE/SIMD folding parameters; for temporal (e.g., PERUN), it groups layers by Compute Vectors (CVs). Power/area are estimated by summing base block costs scaled by instance count.
- **Core assumption:** The predictive models for power/area (based on instance counts of base approximate blocks) and the hardware mapping rules (folding, CV grouping) accurately reflect the true hardware costs and constraints.
- **Evidence anchors:**
  - Section II.C: "Power and area are estimated by extracting the count of each approximate block in the configuration and combining this with the base power and area metrics."
  - Section III.B, Fig 5: Reports normalized power/area reductions for synthesized dataflow and PERUN configurations.
  - Corpus: Neighbors like DeepAxe and HASS provide context, but HAWX's cross‑architecture estimation is not directly validated.
- **Break condition:** If the base block cost models do not scale linearly with instance count, or if architectural constraints (memory bandwidth, routing) are not captured, the estimated Pareto front will be inaccurate.

## Foundational Learning

- **Concept: Approximate Computing (AxC)**
  - *Why needed here:* HAWX applies AxC by substituting exact arithmetic (multipliers/adders) with approximate blocks. Understanding AxC's error resilience principle in DNNs explains why the search space exists and how `hawx` scores approximate error impact.
  - *Quick check question:* Why are DNNs inherently tolerant to errors in intermediate computations, and how does this enable hardware‑level approximation?

- **Concept: Sensitivity Analysis in DNNs**
  - *Why needed here:* The `hawx` score is a sensitivity metric; gradient‑based saliency (e.g., `|∂L/∂o|`) is a component. Prerequisite knowledge of how gradients indicate operation importance is necessary.
  - *Quick check question:* How does the gradient of the loss with respect to an intermediate activation indicate that operation's importance to final accuracy?

- **Concept: Design Space Exploration (DSE) for Hardware**
  - *Why needed here:* HAWX is a DSE framework. Understanding the curse of dimensionality in exhaustive search and common pruning strategies (hierarchical search, predictive modeling) is key to appreciating its novelty.
  - *Quick check question:* Why does exhaustive search for per‑filter approximation become intractable even for moderately sized CNNs?

- **Concept: Hardware Accelerator Architectures (Spatial vs. Temporal)**
  - *Why needed here:* The mapping and cost estimation differ fundamentally for spatial (massively parallel, dataflow) and temporal (time‑multiplexed) architectures. Knowing these paradigms is required to understand the algorithm's branching logic.
  - *Quick check question:* What is the key difference in how a layer's computations are mapped onto a spatial array of PEs versus a temporal multi‑threaded soft processor?

## Architecture Onboarding

**Component map:**
Profiler & Input Selector -> Multi-level Score Engine -> Boundary Search & Pruner -> Hardware Mapper & Estimator

**Critical path:** 
Profiling (GPU inference) → Score computation → Boundary search (few full evaluations) → Mapping & estimation. Profiling and scoring must complete before boundary search can begin.

**Design tradeoffs:**
- **Granularity:** Finer (filter/op-level) yields better accuracy‑efficiency trade‑offs but increases score storage and mapping complexity. Coarser (layer/model-level) is faster but less optimal.
- **Representative inputs (K):** Larger K improves robustness but increases profiling time; K is fixed (paper does not specify value).
- **Hardware modeling:** Using pre‑characterized block base costs is fast but may not capture interconnect, memory, or control overheads, especially for complex spatial arrays.

**Failure signatures:**
- **Accuracy miss:** End‑to‑end accuracy below threshold. Likely cause: `hawx` score did not predict true error (unrepresentative inputs or poor gradient correlation).
- **Hardware mismatch:** Estimated power/area differs significantly from synthesis. Cause: base block cost model invalid for the specific architecture.
- **Scalability collapse:** Speedup over exhaustive search diminishes for very deep models. Check: boundary search iterations may increase if accuracy thresholds are very tight.

**First 3 experiments:**
1. **Validate representative inputs:** For a test network, compare the distribution (mean, variance) of first‑layer activations from the k‑means selected K samples against a larger random subset (e.g., 1000 samples) using KL‑divergence or histogram overlap.
2. **Correlate `hawx(model)` with true accuracy:** For each approximate block, replace all operations in a model, compute `hawx(model)` and measure actual top‑1 accuracy on a validation set. Plot normalized `hawx(model)` vs. accuracy to verify monotonicity.
3. **Measure search cost breakdown:** Implement HAWX for a small network (LeNet‑5) with 2 AxC blocks. Time: (a) profiling pass `t_prof`, (b) score computation for all blocks `B·t_score`, (c) number of full evaluations `N_HAWX_eval`. Compare `T_HAWX` to `N_exh · t_eval`.

## Open Questions the Paper Calls Out

#### Open Question 1
- **Question:** To what extent can HAWX's multi‑level sensitivity scoring and design space pruning generalize to approximate computing primitives beyond 8‑bit multipliers (e.g., adders, higher‑precision units, or non‑arithmetic approximations like approximated activation functions)?
- **Basis in paper:** The framework is validated exclusively using eight 8‑bit approximate multipliers from EvoApproxLib. While the authors state the methodology is "directly extendable" to other primitives (Section III.A), no experiments or analysis are provided for adders, different bit‑widths, or other approximation types.
- **Why unresolved:** The scoring metric (`hawx`) is defined around output deviation from replacing an exact block with an approximate one (Equation 2). The error characteristics of different primitive types (adders vs. multipliers) or precision levels may differ fundamentally, potentially invalidating the sensitivity hierarchy and pruning efficacy.
- **What evidence would resolve it:** Systematic experiments applying HAWX to a diverse library of approximate components (e.g., adders, dividers, various bit‑widths) across multiple DNNs. Comparative analysis would show whether the same multi‑level scoring reliably identifies Pareto‑optimal configurations for different primitive types without loss of accuracy or hardware gains.

#### Open Question 2
- **Question:** How robust is HAWX's k‑means‑based selection of representative inputs (based on first‑layer activation statistics) to variations in dataset distribution, model architecture, or training artifacts such as outliers or adversarial samples?
- **Basis in paper:** The framework profiles the first layer to derive Gaussian features (mean, std) for k‑means clustering (Section II.A). This is justified by the first layer's proximity to inputs, but no validation is provided on whether this consistently captures "typical" data diversity across different datasets (e.g., ImageNet vs. GTSRB), model depths, or presence of atypical inputs.
- **Why unresolved:** The assumption that first‑layer activations are a sufficient proxy for whole‑network input sensitivity is critical for scalable profiling. If key features affecting later layers are not captured by early activations (e.g., in networks with complex early preprocessing or high‑level semantic shifts), the computed `hawx` scores may not reflect true resilience.
- **What evidence would resolve it:** Comparative studies using alternative input selection strategies (e.g., layer‑wise clustering, gradient‑based selection, farthest‑point sampling) on a diverse set of models and datasets. Metrics would include correlation between `hawx` scores derived from full vs. sampled inputs and the final accuracy of pruned configurations.

#### Open Question 3
- **Question:** Do the multi‑level `hawx` scores (operation → filter → layer → model) exhibit consistent, non‑conflicting sensitivity rankings across different network architectures, or are there cases where high sensitivity at one level (e.g., filter) contradicts low sensitivity at another (e.g., layer), undermining the hierarchical aggregation approach?
- **Basis in paper:** The framework aggregates scores via MAE within each level (Equations 3, 6). This implicitly assumes that sensitivity is additive or representative within a container (filter/layer). The paper shows aggregated values (Table I) but does not analyze intra‑level variance or inter‑level consistency (e.g., whether a layer with low average `hawx(l)` could contain highly sensitive filters that are masked by robust ones).
- **Why unresolved:** Hierarchical pruning relies on the premise that a layer's score appropriately guides approximation decisions for its constituent filters/operations. If significant sensitivity conflicts exist, applying uniform approximation at the layer level could degrade accuracy beyond thresholds, while the binary‑search boundary method may not detect such localized vulnerabilities without exhaustive per‑filter evaluation.
- **What evidence would resolve it:** Statistical analysis of score distributions within layers/filters across multiple networks (e.g., coefficient of variation). Controlled experiments where approximation is applied based on different level scores (operation vs. layer) and comparing accuracy impacts, especially in networks with residual connections or grouped convolutions.

#### Open Question 4
- **Question:** How does HAWX's hardware‑aware mapping and cost estimation perform on emerging DNN architectures (e.g., transformers, state‑space models) and accelerator paradigms (e.g., in‑memory computing, neuromorphic systems) beyond the evaluated spatial (dataflow) and temporal (PERUN) architectures?
- **Basis in paper:** Evaluation is limited to four CNN models and two specific accelerator templates (dataflow, PERUN). The methodology claims support for "both spatial and temporal accelerator architectures" (Abstract) but does not define how mapping rules or cost models adapt to fundamentally different compute models (e.g., attention mechanisms in transformers require different dataflow patterns; in‑memory systems have non‑von Neumann cost metrics).
- **Why unresolved:** The hardware mapping step (Algorithm 1) uses parameters like PEs, SIMD width, or CV grouping, which are tailored to classical systolic/temporal arrays. Transformers have dynamic attention patterns and layer‑norm operations, potentially breaking the assumed operation granularity and reuse patterns. Cost models for power/area are based on block counts, which may not hold for architectures with analog compute or memory‑centric operations.
- **What evidence would resolve it:** Case studies applying HAWX to transformer‑based models (e.g., BERT, ViT) on in‑memory or analog accelerator platforms. This would require extending the hardware abstraction to capture new parameters (e.g., memory bandwidth, analog noise) and validating that `hawx` scoring remains predictive when approximation is applied to attention or feed‑forward sub‑layers.

## Limitations
- **Unspecified block details:** Exact error profiles and implementations of the EvoApproxLib approximate blocks are not provided, preventing precise Δout calculation and hardware cost scaling.
- **Missing cost metrics:** Base power/area figures per block are omitted; only normalized reductions are reported, making reconstruction of quantitative Pareto fronts impossible.
- **Assumption gaps:** Hierarchical `hawx` aggregation's generalizability across architectures is unproven; first‑layer activation representativeness may fail for deeper or non‑linear networks.

## Confidence
- **High:** Scalability (speedup over exhaustive search) – clear exponential pruning results and timing comparisons are presented.
- **Medium:** Accuracy maintenance – accuracies reported for three models, but hierarchical sensitivity's generalizability lacks rigorous proof.
- **Low:** Hardware‑aware cost estimation – base block costs and scaling assumptions lack empirical grounding; cross‑architecture synthesis validation is absent.

## Next Checks
1. **Input representativeness test:** For a deep network (e.g., ResNet‑50), compute KL‑divergence between first‑layer activation distributions of the k‑means selected K samples and a large random subset (≥1000) of the full dataset.
2. **Hawx–accuracy correlation:** For each candidate block, replace all operations in a model, compute `hawx(model)`, and measure top‑1 accuracy on a validation set; fit a monotonic regression and report R² across models.
3. **Cost model accuracy:** Synthesize a small spatial accelerator (e.g., 4 PEs) with selected approximate blocks; compare estimated power/area (using base block metrics) against actual post‑synthesis numbers.
