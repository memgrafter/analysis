# The Token Games: Evaluating Language Model Reasoning with Puzzle Duels
## Quick Facts
* **arXiv ID:** 2602.17831
* **Source URL:** https://arxiv.org/abs/2602.17831
* **Reference Count:** 15
* **Primary Result:** A fully automated, scalable duel-based framework where models propose and solve coding puzzles, yielding Elo ratings that correlate strongly with expert benchmarks while measuring distinct creative and evaluative skills.

## Executive Summary
The paper introduces The Token Games (TTG), an automated evaluation framework where language models duel by alternately proposing and solving Python boolean function puzzles. This addresses the scarcity and potential saturation of human-curated reasoning benchmarks. By verifying solutions via code execution and computing Elo ratings from pairwise outcomes, TTG provides a scalable alternative. Evaluations on ten frontier models show that solver rankings correlate well with established benchmarks (e.g., Humanity’s Last Exam, ρ=0.75), but proposer performance reveals a separate, less-measured capability set marked by low success rates. The framework also captures models’ increasing puzzle difficulty across duel turns, demonstrating dynamic reasoning assessment.

## Method Summary
TTG structures each “duel” as a series of alternating rounds between two models. One model (the proposer) generates a programming puzzle: a Python function signature along with a specification and an incorrect sample solution. The other model (the solver) must produce a correct implementation. Both outputs are automatically validated by executing test cases in a sandbox. The proposer wins if the solver fails, and the solver wins by passing all tests. Elo ratings are updated from these pairwise outcomes across many matches, creating a skill-based leaderboard. The entire pipeline is automated, requiring no human intervention beyond initial configuration.

## Key Results
* **Solver skill correlates with benchmarks:** Solver Win Rate from TTG shows a strong positive correlation (ρ=0.75) with scores on Humanity’s Last Exam, indicating TTG effectively measures conventional reasoning prowess.
* **Proposing is much harder than solving:** The best model as a proposer achieved only a 43.3% win rate, while all models achieved near 100% solve rates as solvers, highlighting a major difficulty asymmetry.
* **Models ramp up difficulty:** Analysis of puzzle complexity metrics (e.g., code length, control flow) shows proposers, particularly advanced models like GPT-5.2, increase difficulty by ~2.5% per turn within a duel.

## Why This Works (Mechanism)
TTG works because it replaces static, human-written benchmarks with a dynamic, adversarial generation-and-solving loop. The use of executable code provides unambiguous, automated verification, eliminating scoring ambiguity. The Elo system aggregates many noisy pairwise outcomes into stable skill estimates. Critically, the dual roles (proposer/solver) separate the ability to solve problems from the ability to create valid, challenging ones—the latter requiring creativity, self-evaluation, and meta-reasoning. This bifurcation exposes capabilities that single-role benchmarks miss, while the automated nature allows indefinite scaling as models improve.

## Foundational Learning
* **Adversarial evaluation:** Why needed: Moves beyond static test sets to dynamically generate challenges, reducing contamination and saturation. Quick check: Does the adversary’s strategy adapt to the opponent’s known weaknesses?
* **Automated code verification:** Why needed: Provides objective, pass/fail outcomes without human grading. Quick check: Are all edge cases and execution environments (e.g., timeouts, memory) consistently handled?
* **Elo rating system:** Why needed: Converts many pairwise duel results into a continuous skill scale. Quick check: Is the rating stable given the number of matches per model, and does it converge?
* **Role differentiation (proposer vs. solver):** Why needed: Isolates distinct cognitive skills—problem creation versus problem solving. Quick check: Do individual models show large rank discrepancies between their proposer and solver Elos?
* **Puzzle difficulty scaling:** Why needed: Ensures the benchmark remains challenging as models improve, preventing ceiling effects. Quick check: Are objective difficulty metrics (e.g., cyclomatic complexity) reliably increasing across turns?
* **Self-evaluation in generation:** Why needed: Proposers must judge whether their puzzle is both valid and non-trivial, a form of meta-cognition. Quick check: Do proposers explicitly test their own sample solutions before submission?

## Architecture Onboarding
**Component Map (Plain Text):**
User Configuration -> Duel Scheduler -> Proposer Model -> Puzzle Output -> Solver Model -> Solution Code -> Code Execution Sandbox -> Verification (Pass/Fail) -> Outcome Recorder -> Elo Rating Updater -> Leaderboard

**Critical Path:** The central loop is Proposal → Solve → Verify → Record → Update Elo. The scheduler orchestrates match pairings and role assignments. The verifier is the source of ground truth.

**Design Tradeoffs:**
* **Domain restriction vs. control:** Limiting puzzles to Python boolean functions ensures verifiability and a clear API but may exclude other reasoning forms (e.g., natural language deduction, mathematical proofs).
* **Simplicity vs. expressiveness:** The function signature format is simple to validate but may not capture complex stateful or multi-step reasoning tasks.
* **Open vs. closed models:** The evaluation assumes access to model APIs; results for truly closed models (black-box only) would require different logistics.

**Failure Signatures:**
* High proposer invalid rate (>80%) indicates models struggle with self-consistency or understanding the task constraints.
* Low correlation between proposer Elo and existing benchmarks suggests the metric is noisy or measuring an unrelated skill.
* Elo instability across different random seeds or opponent pools points to insufficient match volume.

**First Three Experiments:**
1. **Prompting ablation for proposers:** Test variations (e.g., “include self-verification step,” “generate harder puzzles”) to measure impact on validity and win rates.
2. **Cross-domain validation:** Run identical models on a variant of TTG using JavaScript functions or formal logic puzzles to test generalizability of rankings.
3. **Duel length sensitivity:** Vary the number of rounds per duel (e.g., 5, 10, 20) and compute Elo variance to determine optimal match volume for stable ratings.

## Open Questions the Paper Calls Out
### Open Question 1
* **Question:** What causes LLMs to frequently propose invalid or trivially solvable puzzles, and can techniques like self-consistency or iterative refinement improve proposer success?
* **Basis in paper:** Proposers failed in 87.7% of rounds; e.g., GPT-5.2 had >97% penalties for incorrect sample solutions, indicating overconfidence or poor self-evaluation.
* **Why unresolved:** The paper does not investigate the root causes or test mitigation strategies.
* **What evidence would resolve it:** Ablation studies varying prompting (e.g., request verification steps) and measuring changes in validity and proposer win rates.

### Open Question 2
* **Question:** Does performance as a proposer in TTG predict real‑world creative skills such as generating educational problems or competitive programming challenges?
* **Basis in paper:** The paper shows proposer win rates correlate weakly with benchmarks like HLE (ρ ≤ 0.67), suggesting distinct, unmeasured capabilities.
* **Why unresolved:** No external validation of proposer skill beyond TTG is provided; it is unclear whether these abilities transfer.
* **What evidence would resolve it:** Correlate TTG proposer metrics with independent human evaluations or performance on separate creative generation tasks (e.g., math problem design contests).

### Open Question 3
* **Question:** How does puzzle difficulty evolve over the course of a duel across a broader spectrum of models, and does increasing the number of rounds improve rating discrimination?
* **Basis in paper:** The paper reports a decrease in solve rates by ~2.5% per turn for GPT-5.2 and ~1% for GPT-5 mini, indicating proposers ramp up difficulty.
* **Why unresolved:** It is unknown whether this pattern holds for all models and whether the fixed 10‑round duel is optimal for separating model abilities.
* **What evidence would resolve it:** Large‑scale experiments varying turn counts and opponent strengths, measuring Elo variance and stability.

### Open Question 4
* **Question:** To what extent are TTG results generalizable beyond the evaluated frontier models and the Python boolean function representation?
* **Basis in paper:** The study included only 10 models and a single puzzle format; the authors note potential future divergence from human benchmarks as models advance.
* **Why unresolved:** Robustness of TTG as a universal benchmark remains unproven; format biases or model‑specific effects could skew rankings.
* **What evidence would resolve it:** Replicate TTG with alternative encodings (e.g., natural language, formal logic) and include a diverse set of model sizes, architectures, and training regimes.

## Limitations
* Domain restricted to Python boolean functions, which may not generalize to other reasoning modalities (e.g., math proofs, commonsense QA).
* Model selection limited to 10 frontier (likely proprietary) models; performance on smaller or open-source models is unknown.
* Proposer win rate very low (43.3% vs 100% solver), indicating generation difficulty that may be task-specific rather than capability-limited.
* Elo rating stability and sensitivity to duel count not examined, leaving uncertainty about metric robustness.

## Confidence
* **Scalability/automation of TTG:** High – The pipeline demonstrably runs without human curation.
* **Correlation with expert benchmarks:** Medium – Strong correlation with Humanity’s Last Exam but limited cross-benchmark validation and possible contamination concerns.
* **TTG measuring distinct skills:** Medium – Proposer/solver discrepancy suggests novelty, but requires convergent evidence (e.g., factor analysis with other creativity benchmarks).
* **Increasing puzzle difficulty across turns:** Medium – Based on heuristic metrics; needs direct validation of intended difficulty increase.

## Next Checks
1. **Broad model and benchmark replication:** Evaluate TTG across diverse model families (e.g., Llama, Mistral) and compute correlations with multiple established benchmarks (MMLU, GSM8K), providing confidence intervals.
2. **Domain transfer test:** Extend puzzles to other programming languages (JavaScript) or non-programming reasoning tasks (logical deduction, math) to assess generalizability of rankings.
3. **Proposer capability ablation:** Systematically vary prompting (e.g., self-evaluation instructions) and validity checking mechanisms to determine bottlenecks in generating valid, challenging puzzles; measure impact on proposer win rate.
