# MaxCode: A Max-Reward Reinforcement Learning Framework for Automated Code Optimization

## Quick Facts
- **arXiv ID**: 2601.05475
- **Source URL**: https://arxiv.org/abs/2601.05475
- **Reference count**: 26
- **Primary result**: MaxCode, when combined with CUDA-LLM, achieves relative speedup improvements of 27.3% (KernelBench L1), 11.0% (KernelBench L2), and 22.5% (PIE), with 20.3% higher absolute speedup and 10.1% better ranking on average across baselines.

## Executive Summary
Automated code optimization for high-performance kernels (e.g., CUDA, C++) remains challenging for LLMs due to the need for deep systems expertise and the difficulty of interpreting raw performance metrics. MaxCode addresses this by reformulating the task as a max-reward reinforcement learning problem, where the agent’s objective is to find the single best-performing solution rather than maximizing cumulative reward. It enriches the agent’s observation with two critical elements: the best-discounted reward achieved so far and natural language critiques from a separate critic model that transform execution feedback into diagnostic insights and actionable suggestions. A max-reward inference operator adapts existing search methods (e.g., Effi-Learner, CUDA-LLM) and optionally uses a learned generative reward-to-go model to rerank candidates, improving sample efficiency under limited evaluation budgets. Experiments on KernelBench (CUDA) and PIE (C++) show substantial performance gains.

## Method Summary
MaxCode defines an MDP where the state comprises the initial problem, the current code candidate, the full trajectory of past attempts (code, execution feedback, critiques), the best-performing solution discovered so far, and a scalar best-discounted reward `u` (the maximum speedup seen, with discount γ=1). At each depth step up to T=8, the policy (Claude-3.7-Sonnet) generates k=8 new candidates from this augmented observation. Each candidate is executed for correctness and speedup, and a separate critic model generates a natural language critique diagnosing issues and suggesting improvements. The best-discounted reward `u` is updated to the maximum of its current value and the candidate’s speedup (if correct). After evaluating all candidates, if any are correct, the one with the highest speedup becomes the sole continuation state; otherwise, one refinement round per candidate is performed, and the best correct refinement (if any) is selected. An optional generative reward-to-go model (Qwen2.5-7B-Instruct) is trained on past search trajectories to predict future maximum speedup and rerank candidates during search.

## Key Results
- On KernelBench Level 1 (CUDA), MaxCode + CUDA-LLM yields a 27.3% relative speedup improvement over the baseline.
- On KernelBench Level 2, the improvement is 11.0% relative speedup.
- On PIE (C++), the improvement is 22.5% relative speedup.
- Across all baseline integrations, MaxCode delivers 20.3% higher absolute speedup and 10.1% better average ranking.

## Why This Works (Mechanism)
The max-reward RL formulation aligns the agent’s objective with the ultimate goal of code optimization: finding the single best kernel. By maintaining the best-discounted reward in the observation, the policy is explicitly conditioned on the current benchmark to beat, directing exploration toward surpassing known performance. The critic-generated natural language critiques convert raw execution feedback (compile errors, test failures, timing) into human-readable diagnostics and actionable suggestions, which are more effective for an LLM policy than raw numerical feedback. This enriched observation space allows the agent to learn from both successes (the best solution) and failures (critiques of incorrect/slow candidates), avoiding repeated mistakes and focusing search on promising regions. The generative reward-to-go model further improves sample efficiency by anticipating which candidates are likely to lead to higher final speedups, enabling better prioritization under a fixed evaluation budget.

## Foundational Learning
- **Max-reward Reinforcement Learning**: Objective is to maximize the best single reward encountered, not cumulative reward. *Why needed*: Matches the code optimization goal of finding the top-performing kernel. *Quick check*: Verify `u_t = max(u_{t-1}, r(candidate))` updates correctly and that final metric is the maximum speedup per problem.
- **Observation Augmentation with Critiques**: State includes natural language analysis of execution feedback. *Why needed*: Raw metrics are hard for LLMs to interpret; critiques provide actionable insights. *Quick check*: Sample 20 critiques; ensure each contains (a) specific diagnosis (e.g., “uncoalesced memory access”) and (b) concrete suggestion (e.g., “use shared memory for tile”).
- **Generative Reward-to-Go Model**: Learns to predict final max speedup from intermediate states. *Why needed*: Reranks candidates to focus search on promising branches. *Quick check*: Compute correlation between predicted and actual max speedup on a validation set of search trajectories.
- **Search Method Adaptation (e.g., CUDA-LLM)**: Integrating max-reward operator into existing beam search. *Why needed*: Leverages proven search infrastructure while improving objective. *Quick check*: Confirm beam selection logic picks the best correct candidate after each step, and that best-reward `u` is carried forward.
- **Correctness-Verify-Optimize Loop**: Each candidate is executed to verify correctness before measuring speedup. *Why needed*: Guarantees optimized kernels are functionally valid. *Quick check*: Ensure all reported speedups are computed only over solutions that pass all test cases.
- **Separate Critic Model**: Uses a different LLM call to generate critiques. *Why needed*: Dedicated role improves diagnostic quality over a single multitasking model. *Quick check*: Compare critique depth when using the same model for generation vs. a separate critic in a pilot.

## Architecture Onboarding
**Component Map**  
Problem Description + Baseline Code -> State (includes Trajectory, Best Perf, u) -> Policy (Claude) -> k Candidates -> Execution (Correctness, Speedup) -> Critic (Claude) -> Critique -> State Update (new u) -> Selection (best correct or refinement) -> Next Depth. Optional: Reward-to-go model reranks candidates before execution.

**Critical Path**  
1. Initialize state with problem, baseline code, `u=1.0` (or baseline speedup).  
2. For depth t=1 to T:  
   a. Construct prompt with trajectory, best solution, and `u`.  
   b. Generate k code candidates.  
   c. Execute each candidate; if correct, record speedup.  
   d. Generate critique for each candidate’s execution feedback.  
   e. Update `u` to max(current `u`, candidate speedup if correct).  
   f. Select continuation state: best correct candidate; if none, refine each once and pick best correct refinement; else terminate.  
3. After T steps, collect all correct solutions and record max speedup per problem.

**Design Tradeoffs**  
- **LLM Cost vs. Critique Quality**: Using a large closed-source model (Claude) for critique ensures high-quality diagnostics but increases API cost and latency. A smaller open-source critic might reduce cost but risk generic feedback.  
- **Beam Width vs. Budget**: Wider beams (k=8) explore more but consume more execution and LLM calls. Deeper search (T=8) finds better solutions but linearly increases cost.  
- **Reward-to-go Model Overhead**: Training and running the reranking model adds complexity; its benefit must outweigh the extra inference cost.

**Failure Signatures**  
- **Vague critiques**: Critiques lack specific failure causes or suggestions (“try to optimize”). Indicates poor critic prompt.  
- **Early termination**: Many problems yield no correct solutions within T steps. Could be due to misleading critiques, insufficient beam, or hard problems.  
- **Ignoring best-reward**: Generated code does not attempt to surpass the known best speedup, suggesting `u` is not salient in the prompt.  
- **High variance across PIE runs**: Large swings in speedup when changing the 68-problem subset indicate dataset sensitivity.

**First Three Experiments**  
1. **Prompt sanity check**: Run a pilot on 5 KernelBench problems; manually inspect 20–30 critic outputs. If >30% are vague (no specific diagnosis or actionable step), revise the critic prompt template (e.g., enforce structure: “Issue: … Suggestion: …”).  
2. **PIE subset reconciliation**: For the PIE results, run two evaluations: (a) the exact 100-solution instances described (41 problems), and (b) a random sample of 68 problems from the full PIE test set. Compare median max speedup; report the difference to gauge subset sensitivity.  
3. **Initial `u` sensitivity test**: Ablate the initial best-reward value: run MaxCode with `u0 = 1.0` (baseline speedup) vs. `u0 = 0` (no prior best). Measure change in median max speedup on KernelBench Level 1. A significant drop (>2% absolute) confirms the importance of a correct initialization.

## Open Questions the Paper Calls Out
- **Can we learn a coarse verification signal as the V model to improve search performance?** Mixed results; no effective solution provided. Reward models with higher correlation to max speedup across search methods were explored but inconclusive.
- **Can a smaller open-source model replace Claude for critique generation without losing effectiveness?** No cost-quality trade-off analysis was conducted. Fine-tuning a medium LLM as a critic and comparing speedup gains remains open.
- **Is the max-reward RL formulation essential, or could cumulative reward work similarly?** The contribution of the max-reward operator was not isolated against a cumulative reward baseline.
- **Can MaxCode generalize to other languages (e.g., Python) and metrics (e.g., memory)?** Evaluation was limited to CUDA/C++; effectiveness on Python optimization or memory-constrained benchmarks is untested.

## Limitations
- **Unspecified critic prompt**: Appendix C.2 is empty; the exact natural language prompt for the critic model is missing, risking variability in critique quality during reproduction.
- **Ambiguous PIE problem selection**: The paper reports results on “68 problems” but describes sampling 100 solutions from 41 problems; the exact list of 68 problems is unclear, potentially affecting C++ speedup reproducibility.
- **Edge case handling**: The number of refinement rounds when no candidate is correct is vaguely described as “iteratively refine until at least one is correct.” The reproduction plan assumes one extra round, but the true procedure may differ.
- **Baseline prompt fidelity**: The “Base” prompt in the appendix may not exactly match the original CUDA-LLM prompt, making direct comparison potentially noisy.

## Confidence
- **Max-reward formulation & search integration**: **Medium**. Algorithmic description is clear but depends on unverified prompt engineering and edge-case handling.
- **CUDA (KernelBench) performance gains**: **Medium**. KernelBench setup is better specified, but results hinge on critic quality and exact hyperparameters (temperature, beam width).
- **C++ (PIE) performance gains**: **Low**. High uncertainty from ambiguous problem subset and critic prompt; results may vary significantly with a different 68-problem slice.
- **Reproducibility of implementation details**: **High** for search procedure (depth, beam width given), **Low** for prompt templates and critic design.
