# An end-to-end agentic pipeline for smart contract translation and quality evaluation

## Quick Facts
- arXiv ID: 2602.13808
- Source URL: https://arxiv.org/abs/2602.13808
- Reference count: 18
- Primary result: Average composite quality score 81.54 (B grade) with 86.54% compilation success; security refinement reduced critical vulnerabilities by 88.2% and medium+ by 70.9%.

## Executive Summary
Smart contract development suffers from human error and security flaws. This paper presents an end-to-end agentic pipeline that translates natural language specifications into Solidity code, iteratively audits and refines it for security, and evaluates quality against formal Finite State Machine (FSM) semantics. Using a CrewAI-style multi-agent architecture, the system processes 9,000 contracts, achieving an 86.54% compilation rate and a composite quality score of 81.54. Strengthened by an automated security loop, critical vulnerabilities drop by 88.2% and medium+ issues by 70.9%. Generated contracts even surpass expert implementations by 8.29 points due to literal specification adherence.

## Method Summary
The pipeline comprises seven sequential phases orchestrated by `IBMAgenticContractTranslator`. A Parser Agent converts the natural language spec into a structured `UniversalContractSchema`. A Generator Agent produces Solidity code adhering to 12 critical rules. An Auditor Agent scans for vulnerabilities across eight categories; if medium+ severity issues are found, a Refiner Agent rewrites the code (up to two iterations). After compilation, a Quality Evaluator Agent scores the contract on five weighted dimensions (Functional Completeness, Variable Fidelity, State Machine Correctness, Business Logic Fidelity, Code Quality) by comparing it to the FSM spec and a ground-truth implementation. The system uses GPT-4o-mini for all agents, relies on prompt engineering and schema validation, and supports both batch and interactive modes. Evaluation on the FSM-SCG dataset demonstrates the approach's effectiveness.

## Key Results
- Composite quality score: 81.54 (B grade) on average across 9,000 contracts.
- Compilation success: 86.54%.
- Security impact: critical vulnerabilities reduced by 88.2%, medium+ issues by 70.9%.
- Compared to ground-truth expert code, generated contracts score +8.29 points higher, largely due to better literal adherence to the specification.

## Why This Works (Mechanism)
### Mechanism 1: CrewAI-Style Specialized Agent Orchestration
Decomposing translation into distinct phases (parsing, generation, auditing, refinement) with dedicated agents reduces contextual load and improves per-task accuracy. Each agent operates under a strict system prompt and produces structured outputs that serve as inputs for the next agent. This modularity prevents a single model from handling the full complexity and limits error propagation. Evidence: paper details seven phases (Section 3) and provides agent prompts in Appendix I.

### Mechanism 2: FSM-Grounded Paired Evaluation
The five-dimensional rubric, anchored in the specification's Finite State Machine, enables objective measurement of semantic correctness. Crucially, the evaluator applies the same rubric to both generated and ground-truth contracts, isolating the generator's performance and revealing systematic error modes (e.g., literal adherence vs. architectural optimization). Evidence: evaluation methodology (Section 4.2) and the reported +8.29 point delta attributed to "literal adherence" (Section 5.4).

### Mechanism 3: Iterative Security Reinforcement Loop
An Auditor–Refiner feedback loop automatically addresses medium+ severity vulnerabilities. The Auditor emits a structured report; if criteria are met, the Refiner rewrites the contract applying secure patterns (e.g., Checks-Effects-Interactions). The loop runs up to two times, significantly reducing security issues. Evidence: critical vulnerabilities drop by 88.2% and medium+ by 70.9% (Section 5.6), with the loop's design described in Section 3.4 and Listing 1.

## Foundational Learning
- **Finite State Machines (FSMs) for Semantic Specification**  
  *Why needed:* The quality rubric requires comparing contract behavior to an FSM definition (states, transitions, guards) to score State Machine Correctness.  
  *Quick check:* For a staking contract transitioning from `FarmingOngoing` to `FarmingEnded` based on a timestamp, what guard condition would the FSM include? (e.g., `block.timestamp >= endTime`).

- **Multi-Agent System Design (CrewAI/Orchestration)**  
  *Why needed:* The pipeline's novelty lies in orchestrating specialized agents; understanding role separation, handoffs (structured schemas), and the breakdown of tasks is essential for extending or troubleshooting the system.  
  *Quick check:* Why might splitting parsing, generation, and auditing across agents reduce "optimistic bias" compared to a single agent performing all steps? (Answer: Each agent focuses on a narrow sub-problem, reducing overgeneralization and self-assessment errors.)

- **Smart Contract Security Vulnerability Taxonomies**  
  *Why needed:* The Auditor Agent classifies issues into categories (reentrancy, access control, arithmetic, etc.); practitioners must know these to interpret audit reports and guide refinements.  
  *Quick check:* What distinguishes a reentrancy vulnerability from an ether handling vulnerability in a withdrawal function? (Answer: Reentrancy arises when external calls are made before state updates, allowing recursive withdrawals; ether handling issues involve incorrect balance management or insufficient checks for `msg.value`.)

## Architecture Onboarding
### Component Map
Orchestrator (`IBMAgenticContractTranslator`) -> Parser Agent -> UniversalContractSchema -> Generator Agent -> Solidity code -> Auditor Agent -> Audit report -> [Refiner Agent loop] -> Compiled code + Final audit -> Quality Evaluator Agent -> Paired scores vs. ground truth.  
Supporting components: agents (defined in `agents.py` with system prompts in `task_builders.py`), schemas (`pydantic` models in `schemas.py`), tools (`solcx` compiler wrapper; Slither/Mythril integration implied), demo interface (`launch_demo.py`).

### Critical Path
Specification text -> Parser -> Schema -> Generator -> Solidity -> Auditor -> Refine? (if medium+ issues, up to 2 iterations) -> Compile -> Quality Evaluator -> Output scores and artifacts.

### Design Tradeoffs
- *Speed vs. Security:* Allowing up to two refinement iterations improves security but increases processing time (~110 seconds/contract). `max_refinement_iterations` is configurable.
- *Generality vs. Fidelity:* The generator follows a "literal adherence" rule, boosting variable/function name matching (Variable Fidelity 84.62%) but potentially sacrificing architectural elegance. This trade-off explains the +8.29 point gain over ground truth.
- *Batch vs. Interactive:* Batch processing uses parallel workers for throughput; interactive mode streams events for debugging. The former favors volume, the latter observability.

### Failure Signatures
- **Parsing failure:** Parser returns incomplete `UniversalContractSchema` (missing parties/conditions). Check parser logs and prompt adherence.
- **Compilation failure:** ~13.46% overall, higher in complex contracts (73.2% success for high-complexity vs. 94.1% for low). Inspect `solcx` error logs and Solidity version alignment.
- **Evaluation skew:** Ground-truth bugs or FSM spec ambiguity can invalidate paired scores. Verify dataset integrity.
- **Refinement loop stall:** After 2 iterations, if severity remains medium+ and `approved` is false, the contract is released unrefined. Monitor `refinement_count` and final audit.

### First 3 Experiments
1. **Schema parsing unit test:** Feed a simple spec (e.g., "A vault with deposits and withdrawals") and verify that `UniversalContractSchema` captures all parties, functions, states, and conditions.
2. **Metric isolation test:** Generate a contract with a known state transition bug, run the Quality Evaluator on both the buggy and ground-truth versions, and confirm that the State Machine Correctness score drops appropriately.
3. **Refinement loop validation:** Take a contract with a reentrancy flaw (e.g., external call before state update), run with `enable_reinforcement=True` and `max_refinement_iterations=1`, and check whether the Refiner successfully applies a reentrancy guard.

## Open Questions the Paper Calls Out
- **Property-based testing integration:** How can tools like Echidna and Foundry fuzzers be integrated into the refinement loop to automatically generate test suites and verify invariants? The paper's Future Work proposes this but does not implement it.
- **Domain-specific compliance:** What architectural patterns and regulatory repositories are needed for a Compliance Agent to enforce legal requirements (e.g., securities transfer restrictions, sanctions screening) across generated contracts? Without such checks, contracts may be technically correct but legally non-deployable.
- **Gas optimization:** What gas-saving strategies (storage packing, loop unrolling, visibility adjustments) can a Gas Optimizer Agent apply while preserving functional equivalence, and how much reduction can be achieved? The current pipeline lacks any gas metric.

## Limitations
- **Dataset integrity:** The FSM-SCG ground truth may contain bugs or spec deviations, risking the validity of paired evaluation.
- **Reproducibility factors:** Undisclosed API rate limits, hardware specifications, and exact environment (e.g., `solcx` version) could affect runtime and success rates.
- **Evaluation scope:** The rubric weights are subjective, and FSM correctness assumes unambiguous specifications; edge cases may yield noisy scores.

## Confidence
- **High:** Security refinement loop efficacy (empirically observed 88.2% critical reduction).
- **Medium:** Specialized agent orchestration improves accuracy (inferred from modular design, not directly ablated).
- **Medium:** FSM-grounded evaluation validity (depends on dataset quality; not independently verified).

## Next Checks
1. **Dataset audit:** Manually inspect 50 random FSM-SCG entries for spec–code alignment; annotate any discrepancies.
2. **Parser stress test:** Feed intentionally ambiguous specifications (e.g., "handle transfers") to quantify parsing failure modes and error recovery.
3. **Refinement ablation:** Compare pipeline runs with `max_refinements=0` versus `=2` on a vulnerability-prone subset to isolate the loop's impact on security metrics.
