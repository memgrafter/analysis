# Engineering FAIR Privacy-preserving Applications that Learn Histories of Disease
## Quick Facts
- arXiv ID: 2603.00181
- Source URL: https://arxiv.org/abs/2603.00181
- Reference count: 0
- Primary result: Demonstrated a functional proof-of-concept web application that performs client-side inference of the Delphi 2M model using ONNX and WebAssembly, eliminating server communication and preserving privacy.

## Executive Summary
This paper presents an architecture for privacy-preserving generative AI in medicine by deploying the Delphi 2M disease trajectory prediction model entirely on the client side. The authors convert the original PyTorch model to ONNX, build a custom JavaScript SDK that handles preprocessing, iterative inference with time-to-event sampling, and postprocessing, and run it in the browser via ONNX Runtime Web compiled to WebAssembly. The resulting web application keeps all sensitive health data on the user's device, thereby mitigating privacy risks. The implementation serves as a blueprint for FAIR-compliant, high-performance medical AI.

## Method Summary
The core method involves converting the Delphi 2M transformer model from PyTorch to the open ONNX format. A custom JavaScript SDK, `delphi-onnx`, is developed to manage the end-to-end inference pipeline: tokenizing ICD-10 codes and ages into tensors, running iterative generation by sampling next events and times until a death token or maximum age, and postprocessing results to human-readable form. The SDK uses ONNX Runtime Web, which executes the ONNX model in the browser via WebAssembly (or WebGPU when available). This ensures all computation occurs locally without any network transmission of patient data. The authors provide a static web application that integrates the SDK, demonstrating the feasibility.

## Key Results
- Functional in-browser inference of the Delphi 2M model without server communication.
- Successful conversion of a PyTorch model to ONNX and execution via WebAssembly, achieving near-native speeds.
- Public release of the SDK and code, enabling reusability and interoperability per FAIR principles.

## Why This Works (Mechanism)
The privacy guarantee stems from executing the entire machine learning pipeline locally in the browser: input data never leaves the device, and no server is involved. This is achieved by converting the PyTorch model to ONNX, an open standard that allows the same model file to be loaded by ONNX Runtime Web, which is compiled to WebAssembly and runs efficiently in JavaScript environments. The custom SDK abstracts the complexity, implementing the original model's tokenization, age encoding, iterative generation loop (using `t_next = -log(u)/lambda` for time-to-event sampling), and postprocessing. The browser's sandbox isolates the computation, and the static deployment avoids any backend infrastructure.

## Architecture Onboarding
Component map:
User Input (ICD-10 codes + ages) -> Web UI (ObservableHQ) -> JavaScript SDK (`delphi-onnx`) -> ONNX Runtime Web (WebAssembly) -> ONNX Model (Delphi 2M) -> Generated Trajectory -> UI Display

Critical path:
1. Convert Delphi 2M PyTorch model to ONNX.
2. Implement SDK: preprocessing (tokenization, age encoding), inference loop with sampling, postprocessing.
3. Integrate SDK into a web page and serve via static host.
4. Test and optimize across browsers.

Design tradeoffs:
- WebGPU vs. WebAssembly: WebGPU offers GPU acceleration but with limited browser support; fallback to WebAssembly ensures compatibility.
- Model size: Larger models improve accuracy but increase load time and memory usage; the prototype uses a small synthetic model.
- Accuracy vs. privacy: Full real-world data would boost performance but handling sensitive data requires privacy safeguards; synthetic data used for prototype.
- Updatability: Client-side models are static; future updates via federated learning are challenging.

Failure signatures:
- ONNX model fails to load (CORS/MIME errors) → SDK initialization fails.
- Preprocessing mismatch → invalid token IDs or shape errors → nonsense outputs.
- Performance bottleneck → UI freeze; measured via browser dev tools.
- Memory exhaustion → browser tab crash.
- Termination logic bug → infinite loop or premature stop.

First 3 experiments:
1. **Preprocessing correctness**: Compare SDK tensor outputs against original Python for a known trajectory.
2. **End-to-end parity**: Run full generation in both environments and compare event sequences.
3. **Browser performance baseline**: Measure inference time, memory, and WebGPU availability across browsers and devices.

## Open Questions the Paper Calls Out
1. **Accuracy on full real-world data**: The prototype was trained on a small synthetic subset; how does the full model (trained on 400k real trajectories) perform when deployed client-side?
2. **Integration of fine-tuning and federated learning**: How can the SDK support continuous model improvement while preserving privacy?
3. **Performance profiling across devices**: What are the actual latency, memory consumption, and battery impact on various user devices? The paper claims high performance but provides no benchmarks.

## Limitations
- Implementation fidelity not quantitatively validated: the SDK's preprocessing and sampling may deviate from the original without verification.
- Model conversion integrity: potential loss of functionality if PyTorch-specific operations are unsupported in ONNX.
- Performance claims unsubstantiated: no empirical benchmarks provided for load times, inference speed, or resource usage on real hardware.
