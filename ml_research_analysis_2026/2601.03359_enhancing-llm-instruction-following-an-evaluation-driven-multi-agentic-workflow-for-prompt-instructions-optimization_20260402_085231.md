# Enhancing LLM Instruction Following: An Evaluation-Driven Multi-Agentic Workflow for Prompt Instructions Optimization

## Quick Facts
- **arXiv ID:** 2601.03359
- **Source URL:** https://arxiv.org/abs/2601.03359
- **Reference count:** 16
- **Primary result:** The multi-agentic workflow improves constraint compliance by decoupling constraint optimization, achieving average score deltas of 0.0536 (Mixtral) and 0.0456 (Llama) on InfoBench.

## Executive Summary
Large language models often fail to adhere to explicit output constraints even when generating relevant content. This paper introduces a multi-agentic workflow that specifically targets constraint compliance by decoupling the optimization of a prompt's primary task description from its explicit list of constraints. The system uses an LLM-as-a-judge to produce constraint-specific compliance scores, which serve as direct feedback for a planner agent to iteratively rewrite constraints via actions such as rephrase, split, merge, and reorder. The workflow operates on the InfoBench dataset, which decomposes complex instructions into fine-grained constraints.

Experiments with Llama 3.1 8B and Mixtral-8x7B show that merely adding explicit constraints raises baseline compliance from ~82% to ~91.6%. The full iterative workflow further increases compliance, yielding average score deltas of 0.0536 (Mixtral) and 0.0456 (Llama). An ablation study demonstrates that removing quantitative feedback reduces improvement rates by approximately 3%, underscoring the importance of precise, score-driven guidance. The "rephrase" action is most frequently linked to successful improvements, indicating that clarity in constraint wording is key. This approach offers a promising direction for enhancing instruction following without altering the core task intent.

## Method Summary
The work addresses the problem of improving LLM adherence to explicit response constraints. The dataset used is InfoBench, which provides 500 samples each containing a user input, a primary instruction, and a set of decomposed questions representing fine-grained constraints. These questions are translated into affirmative constraint statements to form the initial constraint list. The objective is to maximize the average constraint-specific compliance score, normalized to [0,1], as assessed by an LLM judge.

The proposed solution is a multi-agentic iterative workflow orchestrated by a state machine (LangGraph). It comprises five agent components: (1) a **Generator** (using Llama 3.1 8B or Mixtral-8x7B) that produces three responses given the instruction, user input, and current constraints; (2) an **Evaluator** (LLM-as-a-judge) that scores each constraint for each response on a 0-10 scale, normalized to 0-1; (3) a **Translator** that converts the current and previous scores and edit history into a textual summary of changes; (4) a **Planner** (Llama 3.3 70B) that, given the summary and current constraints, selects a target constraint and an editing action (rephrase, split, merge, reorder); and (5) a **Constraint Editing Agent** that executes the planned edit to produce a new constraint list. The cycle repeats until termination conditions are met: maximum of 5 iterations, 2 consecutive iterations without improvement, or perfect score.

## Key Results
- Adding explicit constraints raised baseline compliance from ~82% to ~91.6% for both Llama 3.1 8B and Mixtral-8x7B; the full workflow further increased compliance by average deltas of 0.0536 (Mixtral) and 0.0456 (Llama).
- Ablation study: removing quantitative feedback from the Planner reduced improvement rates by ~3%, proving its critical role.
- The "rephrase" editing action was most frequently associated with successful increases in compliance.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Decoupling a prompt's primary task description from its explicit list of constraints allows for targeted optimization of compliance without altering the core task intent.
- **Mechanism:** The system isolates constraints into a modular list. The Planner and Constraint Editing Agents operate exclusively on this list, iteratively rewriting constraints (via rephrase, split, merge, reorder) while the primary task description remains unchanged. This focuses the optimization effort on the granular acceptance criteria that directly govern response format and procedural correctness.
- **Core assumption:** The primary task description is already sufficient for generating conceptually relevant content; failures stem primarily from the constraints' poor formulation or placement, not from a flawed task description.
- **Evidence anchors:**
  - [abstract] "Traditional prompt refinement approaches focus on rephrasing the description of the primary task... neglecting the granular constraints... We propose a novel multi-agentic workflow that decouples optimization of the primary task description from its constraints."
  - [section 3.1] Describes constructing prompts where `{Instruction}` (primary task) and `{Translated Constraints}` are separate slots in a template.
  - [corpus] Evidence is weak; neighboring papers discuss instruction following broadly but not this specific decoupling architecture.
- **Break condition:** If the initial constraint set is fundamentally incomplete or mis-specified (missing a critical acceptance criterion), optimizing a flawed set will not yield perfect compliance. The system has no mechanism to generate new constraint types.

### Mechanism 2
- **Claim:** Using constraint-specific quantitative compliance scores (0-1) as direct, iterative feedback is critical for effective constraint rewriting.
- **Mechanism:** After each generation, the Evaluator Agent produces a normalized score (0-1) for every individual constraint. The Translator Agent converts these scores and their delta from the previous iteration into a textual summary. The Planner Agent uses this quantitative feedback to decide *which* constraint needs editing and *what* edit action (rephrase, etc.) to apply, creating a closed feedback loop where edits are guided by measurable performance changes.
- **Core assumption:** The LLM-as-a-judge used for scoring provides a reliable, consistent, and discriminative signal that correlates with the true compliance objective. The Planner can correctly interpret score deltas to make strategic decisions.
- **Evidence anchors:**
  - [abstract] "using quantitative scores as feedback to iteratively rewrite and improve them."
  - [section 3.2] "Second, we use constraint-specific evaluation metrics as a direct feedback signal to guide the refinement process."
  - [section 4] Ablation study: "When we remove them [quantitative scores] and force the Planner Agent to rely on just the raw response... the rate of positive improvements drops... This highlights that direct, quantitative constraint-level feedback is crucial."
  - [corpus] Evidence is weak; neighboring papers use LLM-as-judge but not as an iterative, constraint-specific feedback signal for prompt rewriting.
- **Break condition:** If the judge model is biased, inconsistent, or fails to capture subtle constraint meanings, the feedback loop will optimize for the judge's preferences rather than true compliance. The 81-96% human agreement (section 3.2) suggests reliability but is not proof for all constraints.

### Mechanism 3
- **Claim:** A planner-executor multi-agent architecture, where a strategic "Planner" selects editing actions based on history and a separate "Editing" agent executes them, enables more robust and interpretable constraint optimization than a single-agent approach.
- **Mechanism:** The Planner acts as a reasoning layer over the editing history (past constraints, scores, edits). It selects a target constraint and an action (rephrase, split, merge, reorder) based on the Translator's summary of score changes. The Constraint Editing Agent then performs the rewrite. This separation of concerns allows the Planner to focus on strategy ("*what* to change and *why*") while the Editor focuses on execution ("*how* to rewrite it").
- **Core assumption:** The Planner's decision-making, prompted with the editing history and tool descriptions, leads to better action selection than if the Editor agent were asked to both decide and perform the edit in one step. The predefined action space (rephrase, etc.) is expressive enough for most compliance failures.
- **Evidence anchors:**
  - [abstract] "multi-agentic workflow... guided by a planner agent."
  - [section 3.2] Outlines the Planner's role: "decides which constraint to edit and what action to take... The Agent provides three strategies... and we evaluate them in parallel." The Editor "performs the actual modification."
  - [section 4, Table 6] Shows the Planner's action distribution, indicating it actively selects from the toolset.
  - [corpus] Evidence is weak; "multi-agentic" appears in neighbor titles but not necessarily with this planner-executor separation for prompt optimization.
- **Break condition:** The fixed action space is a limitation. The "merge" action was never selected (Table 6), suggesting the tool definitions or the dataset's constraint structure did not present opportunities it could handle. More complex failures (e.g., needing to delete a constraint or add a new one) are outside this architecture's capability.

## Foundational Learning
- **Concept: LLM-as-a-Judge Evaluation**
  *Why needed here:* The entire feedback loop depends on the Evaluator Agent's scores. Understanding its strengths (scalability) and weaknesses (bias, inconsistency) is crucial for interpreting why a constraint's score changed and trusting the Planner's decisions.
  *Quick check question:* If a constraint's score drops after an edit, what are the two most likely causes: (A) the rewrite made the constraint worse, or (B) the judge model's scoring became inconsistent?

- **Concept: Modular Prompt Design**
  *Why needed here:* The system's core innovation is the explicit separation of `{Instruction}` and `{Translated Constraints}` in the prompt template. This requires understanding that a prompt is a structured object, not just a monologue, and that different slots serve different functions (task definition vs. acceptance criteria).
  *Quick check question:* In the template `System: You are a writing assistant. {Instruction} Ensure your draft complies with all of the following requirements: {Translated Constraints}`, what is the primary purpose of the `{Translated Constraints}` slot?

- **Concept: Closed-Loop Optimization**
  *Why needed here:* The workflow is a stateful graph (LangGraph) that runs cycles of Generate -> Evaluate -> Plan -> Edit. This is a control theory-inspired loop where output performance (scores) directly controls the next input (rewritten constraints). Understanding state persistence and termination conditions (`Nmax`, `Pmax`, perfect score) is key.
  *Quick check question:* What happens if the Planner selects the same "rephrase" action on the same low-scoring constraint for three consecutive cycles without score improvement? What does this suggest about the constraint or the action's suitability?

## Architecture Onboarding
- **Component map:**
  1.  **Generator Agent:** Takes `(Instruction, User Input, Current Constraints)` → produces `Response`. Model: Llama 3.1 8B or Mixtral.
  2.  **Evaluator Agent:** Takes `(Task Description, User Input, Response, Decomposed Question)` → produces `Constraint Score (0-10)`. Model: Llama 3.3 70B. Uses JSON output.
  3.  **Translator Agent:** Takes `(Current & Previous Scores, Responses, Edit History)` → produces `Text Summary` of score deltas and history.
  4.  **Planner Agent:** Takes `(Summary, Current Constraints, Tool Descriptions)` → produces `(Selected Tool, Edit Instruction)` as JSON. Model: Llama 3.3 70B.
  5.  **Constraint Editing Agent:** Takes `(Edit Instruction, Current Constraints)` → produces `New Constraints List`.
  6.  **Orchestrator (LangGraph):** Manages state (`constraints`, `history`, `best_score`), executes the cycle, applies termination logic.

- **Critical path:** `Initial Constraints` → **Generator** → `Response` → **Evaluator** → `Scores` → **Translator** → `Summary` → **Planner** → `Action Plan` → **Editor** → `New Constraints` → back to Generator (unless termination).

- **Design tradeoffs:**
  - *Performance vs. Cost:* Using a 70B model for Planner/Evaluator improves decision quality but adds high latency/cost. Ablation shows quantitative feedback is critical, but maybe a smaller judge could suffice?
  - *Exploration vs. Exploitation:* Planner evaluates K parallel strategies (K=3 in main experiment). Higher K increases chance of finding an improvement (Table 4) but multiplies computational cost.
  - *Generality vs. Specificity:* The workflow relies on an initial, valid constraint decomposition (from InfoBench's questions). A poor initial set may lead the loop into a local optimum. The system cannot discover *new* constraints.

- **Failure signatures:**
  - **Stuck in local optimum:** Workflow terminates with `Unchanged Compliance` after `Pmax` iterations. History shows repeated similar edits to the same constraint(s) with no score gain.
  - **Action space exhaustion:** "merge" action is never selected, and "split"/"reorder" are rare. If "rephrase" fails repeatedly, the system may have no effective tool left for a particular constraint type.
  - **Judge-model inconsistency:** A single constraint's score fluctuates wildly across identical or near-identical responses, indicating the Evaluator is not a stable feedback source.

- **First 3 experiments:**
  1.  **Baseline Comparison:** Run the Generator with (a) no explicit constraints, (b) original InfoBench constraints, and (c) manually refined "perfect" constraints. Quantify the compliance gap your workflow is trying to close. *Expected: (a) ~82%, (b) ~91.6%, (c) ~100%.*
  2.  **Ablation of Quantitative Feedback:** Replace the Planner's quantitative summary with only the raw previous responses. Measure the drop in `Increased Compliance` percentage. *Expected: ~3% drop, as shown in Table 2.*
  3.  **Action Impact Analysis:** Log every Planner decision. For constraints that saw a score increase, what percentage of those increases were immediately preceded by a "rephrase" action vs. "split" or "reorder"? *Expected: "rephrase" dominates, especially in successful cases (Table 6).*

## Open Questions the Paper Calls Out
1. **How well does the proposed multi-agentic workflow generalize to other instruction-following datasets beyond InfoBench?**  
   **Basis:** Explicit (future work).  
   **Why unresolved:** The paper only evaluates on InfoBench; generalization to other benchmarks or domains is unknown.  
   **What would resolve:** Running the same workflow on a diverse set of instruction-following datasets (e.g., those with different constraint types) and reporting compliance improvements.

2. **How does the choice of model (e.g., size, architecture) for each agent impact the performance and cost of the workflow?**  
   **Basis:** Explicit (future work).  
   **Why unresolved:** All agents except Generator used Llama 3.3 70B; the effect of using smaller or different models is unexplored.  
   **What would resolve:** Systematic experiments varying agent models, measuring compliance gains, iteration counts, and computational overhead.

3. **To what extent does the quality of the initial constraint decomposition affect the maximum achievable compliance improvement?**  
   **Basis:** Inferred (limitations).  
   **Why unresolved:** The workflow's sensitivity to initial decomposition quality was not quantified; suboptimal decompositions may limit gains or cause failure.  
   **What would resolve:** Controlled experiments with varying initial constraint quality (e.g., artificially perturbed decompositions) measuring final compliance and iteration dynamics.

4. **How reliable is LLM-as-a-judge for evaluating constraint compliance compared to human judgments?**  
   **Basis:** Inferred (limitations).  
   **Why unresolved:** While inter-annotator agreement between LLM judge and humans was reported (81-79%), deeper analysis across constraint categories is missing; biases could misguide the Planner.  
   **What would resolve:** Comprehensive study of LLM judge bias across constraint types, perhaps with multiple human annotators and calibration to human gold standards; also explore ensemble or human-in-the-loop evaluation.

5. **Can expanding the Planner's action space (e.g., adding, deleting, or modifying constraints) further improve compliance rates in cases where the current actions fail?**  
   **Basis:** Inferred (limitations).  
   **Why unresolved:** The fixed set (rephrase, split, merge, reorder) may not address all failure modes; the merge action was never used, indicating gaps.  
   **What would resolve:** Ablation studies adding new actions (e.g., add, delete, replace) to the Planner's toolkit and measuring impact on compliance, particularly on prompts that resisted improvement with original actions.

## Limitations
- The specific LLM used as the Evaluator (judge) is not disclosed, undermining exact replication.
- The fixed action space (rephrase, split, merge, reorder) is restrictive; “merge” was never chosen and the system cannot add or remove constraints, likely causing local optima.
- The workflow assumes an initially valid constraint decomposition; poor initial sets may lead to futile optimization.

## Confidence

- **Quantitative feedback as a critical signal**: High
