# MoEEdit: Efficient and Routing-Stable Knowledge Editing for Mixture-of-Experts LLMs

## Quick Facts
- **arXiv ID:** 2602.10965
- **Source URL:** https://arxiv.org/abs/2602.10965
- **Reference count:** 38
- **Primary result:** MoEEdit achieves state-of-the-art editing performance (e.g., 99.30% efficacy on COUNTERFACT) while preserving routing stability (>88% similarity) and computational efficiency.

## Executive Summary
MoEEdit introduces the first framework for knowledge editing in Mixture-of-Experts (MoE) large language models that maintains routing stability. Existing editing methods for dense models struggle with MoE due to expert coupling and the sensitivity of the router's distribution to weight changes. MoEEdit addresses these challenges through two core innovations: (1) per-expert null-space projections that force expert updates to be orthogonal to preservation features, thereby keeping router inputs invariant; (2) a randomized block coordinate descent (BCD) solver that efficiently handles the coupled optimization by updating only active experts, scaling with expert hidden size rather than total experts. Extensive experiments on Qwen3-30B-A3B and GPT-OSS-20B using COUNTERFACT and ZsRE benchmarks show that MoEEdit achieves near-perfect efficacy and generalization while preserving routing distributions (similarity >88%) and offering superior efficiency, establishing a robust foundation for precise knowledge editing in sparse LLMs.

## Method Summary
MoEEdit operates in three phases. First, a large preservation set (e.g., 100k unlabeled prompts) is used to compute per-expert projection matrices \(P_n\) that span the approximate left-null space of the preservation keys for each expert. This projection guarantees that any update \(\Delta_n = \hat{\Delta}_n P_n\) will not alter the expert's output on preservation examples, thus stabilizing routing. Second, for a batch of edit requests, target output vectors \(v_i\) are obtained by optimizing a perturbation of the original MLP output to maximize likelihood of the new fact while preserving the model's behavior on related contexts. Third, the method solves a strictly convex quadratic objective in the projected update variables \(\{\hat{\Delta}_n\}\) using randomized block coordinate descent. Each BCD pass iterates over active experts (those with gate weight \(g_{i,n} > \varepsilon\) for any edit example), computes a residual that accounts for contributions from other experts, accumulates a small ridge regression system (\(M_n, B_n\)), and updates \(\hat{\Delta}_n = B_n M_n^{-1}\). Updates are applied only to the down-projection matrices. The overall cost per pass scales with the number of active experts and their hidden dimension \(d_k\), not the total number of experts, enabling efficient editing.

## Key Results
- State-of-the-art editing efficacy: 99.30% on COUNTERFACT (Qwen3-30B-A3B) with utility 91.46; 84.47% on ZsRE.
- Maintains routing stability: RS >88% across layers, far surpassing baselines (<55%).
- Efficient scaling: BCD runtime nearly constant as expert count increases up to 128 experts.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Per-expert null-space projection reparameterization decouples expert updates from preservation features, thereby suppressing routing distribution shift.
- **Mechanism:** For each expert `n`, the method computes a projector `P_n` from the eigendecomposition of the covariance matrix `K0_n K0_n^T` of preservation-set keys. The update `Δ_n` is constrained as `Δ_n = Δ̂_n P_n`, where `P_n` zeros out any component aligned with preservation keys. Because `P_n k_i,n = 0` for preservation examples, the expert's output on those examples remains unchanged, which by linearization of the router's softmax prevents changes to the router's input `u` in subsequent layers and thus stabilizes routing distributions.
- **Core assumption:** Routing drift is primarily caused by updates that alter expert outputs on preservation prompts, which then perturb the input `u` to downstream routers. By construction eliminating this alteration, routing stability is achieved.
- **Evidence anchors:**
  - [abstract] "...per-expert null-space projections that force expert updates to be orthogonal to preservation features, thereby keeping router inputs invariant and suppressing routing drift."
  - [section 4.1] Analytical derivation of `δg_ℓ ≈ J_sm(s_ℓ) E_ℓ^T δu_ℓ` and the insight that suppressing `δu_ℓ` on preservation sets controls routing shift.
  - [section 4.2] Formal definition of `P_n` and the proof that `P_n k_i,n = 0` for `i ∈ P`.
  - [corpus] Weak. Corpus neighbors discuss MoE adaptors for editing (MEMoE, LEMoE) but do not address the routing-stability mechanism via null-space projection.
- **Break condition:** If the preservation set `P` is not representative of the distribution whose routing must be preserved, the null-space computed from `K0_n` may not span all harmful directions. The projection could fail to filter out all components that cause `δu_ℓ ≠ 0`, leading to residual routing drift. Numerical thresholds (`τ` for eigenvalue cutoff) also introduce approximation error.

### Mechanism 2
- **Claim:** Randomized block coordinate descent (BCD) solves the coupled expert optimization efficiently by updating a single expert block at a time, making the computational cost scale with expert hidden size `d_k` rather than total experts `N`.
- **Mechanism:** The global objective (Eqn. 8) is a strictly convex quadratic in `{Δ̂_n}`. BCD iteratively minimizes the objective with respect to one expert's `Δ̂_n` while holding others fixed. The subproblem (Eqn. 12–14) reduces to a small ridge regression with normal equations `Δ̂_n M_n = B_n`, where `M_n ∈ R^{d_k × d_k}` and `B_n ∈ R^{d_m × d_k}`. These are accumulated per active expert in a minibatch. The cost per expert is dominated by forming/inverting `M_n` (`O(|E| d_k^2 + d_k^3)`), independent of `N`. Only experts active in the current batch are updated.
- **Core assumption:** The block separable structure of the objective (sum of losses) and the convexity of each subproblem ensure that randomized BCD converges to the global optimum under standard conditions (Tseng, 2001).
- **Evidence anchors:**
  - [abstract] "...block-structured optimization is solved efficiently with a block coordinate descent (BCD) solver."
  - [section 4.3] Derivation of the single-expert subproblem and closed-form update `Δ̂_n = B_n M_n^{-1}`. Analysis of complexity showing dependence on `d_k`, not `N`.
  - [section 5.4] Figure 3b empirically demonstrates near-constant runtime up to 128 experts, while the global closed-form solver becomes infeasible.
  - [corpus] Weak. Neighbors discuss MoE training systems (FSMoE) or parameter-efficient tuning (TT-LoRA MoE) but not BCD for editing.
- **Break condition:** If the preservation loss term were absent or decoupled, the objective might not be strictly convex or block-separable. Pathological conditioning (e.g., `M_n` near-singular even with `λ>0` due to degenerate `{g_i,n}` or `{k̃_i,n}`) could cause numerical instability in the inversion step. The assumption that only `K` experts are active per example limits the sparsity benefit; with very high `K`, more blocks need updating per pass.

### Mechanism 3
- **Claim:** The combination of per-expert projection and BCD achieves a favorable tripartite resolution: (i) projection maintains routing stability, (ii) BCD limits computational cost, (iii) the block structure naturally handles expert coupling via the residual `r_i^{(-n)}`.
- **Mechanism:** Projection ensures each expert's update does not affect preservation outputs, making routing inputs `u` invariant on `P` and preventing cascade shifts. BCD makes the overall optimization tractable by never constructing the giant `(N d_k) × (N d_k)` system. The residual `r_i^{(-n)}` in the subproblem (Eqn. 11) accounts for the contributions of other experts' updates, properly disentangling the coupling—the solution for expert `n` is computed given the current state of all others, iteratively converging to a solution where all experts jointly satisfy the edit targets.
- **Core assumption:** Inter-expert coupling is fully captured by the linear additive model of the MoE output (`v = Σ_n g_n E_n(u)`). The residual formulation correctly isolates expert `n`'s contribution. The routing stability from projection is sufficient; no other hidden coupling paths (e.g., through non-linearities or attention interactions) significantly destabilize routing.
- **Evidence anchors:**
  - [abstract] "...addresses the tripartite challenges of computational cost, expert coupling, and routing distribution shifts."
  - [section 1] Explicitly lists the three challenges and states the method's design addresses them.
  - [section 4.2] Substitution of `Δ_n = Δ̂_n P_n` into the objective yields Eqn. 8, where coupling remains via `g_i,n` but preservation is handled by projection.
  - [section 5.2] Table 1 shows MoEEdit achieves high efficacy/generalization (addressing coupling/accuracy) while Table 2 shows >88% RS (addressing routing shift), and Section 5.4 demonstrates BCD scalability.
  - [corpus] Weak. No direct evidence; neighbors focus on either editing (MEMoE, LEMoE) or MoE efficiency, not their joint resolution.
- **Break condition:** If the MoE architecture had non-linear expert interaction (e.g., experts applied sequentially, not summed), the residual formulation would be invalid. If the projection subspace is poorly estimated (e.g., insufficient preservation samples), the method might trade off too much efficacy for stability, or residual coupling might require many BCD passes to resolve.

## Foundational Learning
- **Concept: Mixture-of-Experts (MoE) Routing**  
  Why needed here: Understanding the source of challenges. The router's Top-K selection and gate-weighted summation create the expert coupling and make naive editing (update all experts) costly. The routing distribution (`g`) is a differentiable function of the input `u`, which is affected by edits in previous layers.  
  Quick check question: *If you increase the output of expert 1 for a specific input, what happens to the router's input `u` in the next layer, and how could that change which experts are activated there?*

- **Concept: Null-Space Projection for Locality**  
  Why needed here: The core technique to guarantee preservation set invariance without needing an explicit penalty term in the objective. It converts a constrained optimization into an unconstrained one in a lower-dimensional subspace.  
  Quick check question: *What matrix property must `P_n` satisfy to ensure `Δ_n k_i,n = 0` for all preservation keys `k_i,n`?*

- **Concept: Block Coordinate Descent (BCD)**  
  Why needed here: The only scalable way to solve the coupled expert optimization. It decomposes a high-dimensional problem into many small, independent ridge regressions.  
  Quick check question: *Why does updating one expert at a time (BCD) still converge to the global optimum for the objective in Eqn. 8?*

## Architecture Onboarding
- **Component map:** Preservation Feature Collector -> Per-Expert Projector -> Projected Key Cache -> BCD Solver -> Edit Request Handler
- **Critical path:**
  1. **Pre-edit analysis:** Run preservation prompts through model, collect `k_i,n` at target editing layers for all experts.
  2. **Projector computation:** For each target expert at each target layer, compute `P_n`. (Can be parallelized across experts/layers).
  3. **Edit execution:** For a batch of edit requests:
     a. Compute current `g_i,n` and `k_i,n` for edit prompts.
     b. Compute `k̃_i,n = P_n k_i,n`.
     c. Initialize `{Δ̂_ℓ = 0}` for all experts.
     d. Run BCD passes: for each expert `n` (active in batch), compute residual `r_i^{(-n)}`, accumulate `B_n, M_n`, solve for `Δ̂_n`, set `Δ_n`.
     e. Apply `Δ_n` to `W_n`.
  4. **Post-edit validation:** Check edit success, generalization, and routing similarity on sample prompts.
- **Design tradeoffs:**
  - **Projection threshold `τ`:** Low `τ` (more aggressive null-space) preserves more features but reduces the degrees of freedom for the edit, potentially harming efficacy. High `τ` risks including preservation directions in the update space.
  - **BCD passes vs. time:** Fewer passes reduce runtime but may not fully resolve coupling; more passes improve convergence but with diminishing returns. A pass over all active experts is cheap; one full pass over all experts is more costly if many are inactive.
  - **Active-expert filtering:** Only updating experts with `g_i,n > ε` for any edit example reduces cost. Too high `ε` might miss experts that contribute to the edit; too low `ε` updates many experts with tiny `g_i,n`, wasting effort.
- **Failure signatures:**
  - **Routing drift persists (RS << 90%):** Check if `P_n` is correctly computed. Likely cause: preservation set `P` does not cover key routing inputs, or `τ` is too high. Verify `P_n k_i,n ≈ 0` numerically for `i∈P`.
  - **Low efficacy (<80% on COUNTERFACT):** Projection may be too restrictive (`τ` too low) or BCD did not converge (too few passes). Check if `M_n` is well-conditioned (`λ` might be too high). Also verify edit targets `v_i` are correctly obtained.
  - **High memory/time:** BCD implementation may not be caching `k̃_i,n` or may be updating all experts per pass instead of only active ones. Ensure minibatch processing and streaming accumulation of `B_n, M_n`.
  - **Generalization poor but efficacy high:** Edit may be overfit to the specific prompt; check if the located layer `l*` is appropriate for the fact type. MoEEdit assumes editing occurs at a layer where the fact is stored; mis-localization will fail regardless of method.
- **First 3 experiments:**
  1. **Projection ablation:** Run MoEEdit with `w/o Proj` on a small batch (e.g., 50 edits) and measure RS. Expect drastic drop (~15 points). This confirms the projection's role in stability.
  2. **BCD convergence curve:** For a fixed batch, plot reconstruction error `||Ψ - R||_F^2` vs. BCD passes. Should drop quickly in first few passes and plateau. If error increases or oscillates, check residual calculation `r_i^{(-n)}` and update order.
  3. **Per-expert update magnitude:** After editing, compute `||Δ_n||_F / ||W_n||_F` for all experts. Expect a few experts (the active ones for the batch) to have non-zero updates, others near zero. If many experts show significant updates, the active-expert filtering may be broken, or `g_i,n` values are not sparse.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How sensitive is MoEEdit's routing stability and editing performance to the size and domain coverage of the preservation set used for null-space projection?
- **Basis in paper:** [inferred] The method computes per-expert projections from a preservation set (Section 4.2) and uses 100,000 samples in experiments, but no analysis of preservation set size or diversity is provided.
- **Why unresolved:** A too small or narrow preservation set may fail to capture all features that must remain invariant, leading to unintended interference or insufficient routing stability. The paper does not explore this trade-off.
- **What evidence would resolve it:** Systematic experiments varying preservation set size (e.g., 1k, 10k, 100k) and source (in-distribution, out-of-distribution) on routing similarity, specificity, and edit efficacy; perhaps theoretical bounds on projection error.

### Open Question 2
- **Question:** Does MoEEdit's guarantee of suppressed routing drift hold for very deep MoE architectures (e.g., >60 layers) where perturbations might accumulate across many subsequent routers?
- **Basis in paper:** [inferred] Experiments are limited to top editing layers (3–7) in Qwen3-30B-A3B (40 layers) and layer 5 in GPT-OSS-20B; routing shift is measured only within 10-layer windows (Table 2, Figure 2).
- **Why unresolved:** The linearized analysis (Eqn. 7) is local; deeper networks could see compounded shifts that degrade stability in later layers, which remain untested.
- **What evidence would resolve it:** Evaluate MoEEdit on a deep MoE model (64+ layers), measure routing similarity throughout the entire depth after editing, and correlate with downstream performance; develop a multi-layer propagation model to predict shift accumulation.

### Open Question 3
- **Question:** Can MoEEdit successfully edit multi-hop or compositional factual knowledge without harming locality, given its per-expert decoupling assumption?
- **Basis in paper:** [inferred] Evaluation uses single-hop benchmarks (COUNTERFACT, ZsRE); no multi-hop or compositional edit scenarios are considered.
- **Why unresolved:** Multi-hop facts may require simultaneous updates across several experts or layers, increasing inter-expert coupling beyond what the independent block updates and projection can safely handle.
- **What evidence would resolve it:** Introduce a multi-hop editing benchmark, apply MoEEdit to such cases, and analyze edit success, generalization, and routing changes compared to single-hop edits; assess BCD convergence when dependencies exist.

### Open Question 4
- **Question:** Would combining MoEEdit's parameter-modifying edits with a parameter-preserving external memory (e.g., SERAC-style) improve reversibility and reduce catastrophic forgetting in long sequential editing regimes?
- **Basis in paper:** [inferred] The introduction contrasts parameter-modifying vs. preserving methods and suggests MoEEdit as a foundation; no hybrid approach is explored.
- **Why unresolved:** MoEEdit permanently alters base weights; an external mechanism could provide undo capabilities or conflict resolution for thousands of sequential edits, enhancing trustworthiness.
- **What evidence would resolve it:** Build a system that stores original parameters or diffs in an external module, uses MoEEdit for edit application, and compare against standalone MoEEdit on long edit sequences (e.g., 10k edits) measuring retention, forgetting, and computational overhead.

### Open Question 5
- **Question:** What is the computational overhead of computing the per-expert null-space projection matrices at scale, and can this cost be amortized or approximated?
- **Basis in paper:** [inferred] Section 4.2 describes eigen-decomposition of per-expert covariance matrices from 100k activation samples but provides no timing or memory analysis of this preprocessing step.
- **Why unresolved:** For models with many experts (e.g., 128 per layer), this step could be expensive and offset MoEEdit's efficiency gains during editing; scalability of this step remains unknown.
- **What evidence would resolve it:** Measure runtime and memory usage of projection construction across model sizes; explore approximations (random projection, streaming PCA) or reuse of projections across multiple edits; report impact on end-to-end editing throughput.

## Limitations
- **vᵢ construction details missing:** The procedure for computing target output vectors (optimizer, steps, regularization weight) is not fully described, which may affect reproducibility and the trade-offs between edit strength and preservation.
- **Editing layers ambiguous:** It is unclear whether the main results (Table 1) use a single editing layer or multiple layers (e.g., {3,4,5,6,7}), impacting reported efficacy and computational cost.
- **Preservation set sensitivity:** The guarantee of routing stability relies on the preservation set adequately covering routing-relevant features; a mismatch may cause residual routing drift.

## Next Checks
1. **Projection ablation replication:** On a fresh 100-edit sample, run MoEEdit without projection. Expect routing similarity to drop below 70% (vs. >88% with projection). Replicating this drop verifies the projection's central role.
2. **BCD convergence monitoring:** For a fixed batch, track objective residual per pass; it should decrease quickly (≤4 passes) then plateau. A rising residual indicates errors in residual computation or update order.
3. **Active-expert update sparsity:** After editing, compute the relative Frobenius norm change \(||\Delta_n||_F / ||W_n||_F\) for all experts. Only experts with non-zero gate weights for the batch should show significant updates. Widespread changes suggest active-expert filtering is broken.
