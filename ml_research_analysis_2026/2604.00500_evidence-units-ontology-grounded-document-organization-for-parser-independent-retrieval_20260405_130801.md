# Evidence Units: Ontology-Grounded Document Organization for Parser-Independent Retrieval

## Quick Facts
- **arXiv ID:** 2604.00500
- **Source URL:** https://arxiv.org/abs/2604.00500
- **Reference count:** 36
- **Primary result:** Parser-independent Evidence Unit chunking improves document retrieval, raising LCS from 0.50 to 0.81 and Recall@1 by 3.4× on OmniDocBench.

## Executive Summary
Semantically coupled document elements (e.g., tables with captions) are often fragmented during indexing, impairing retrieval accuracy. This work introduces **Evidence Units (EUs)**: parser-independent, semantically complete chunks that group visual assets with their contextual text. The pipeline employs an ontology-grounded role normalization to unify parser outputs, a global semantic assignment algorithm to allocate paragraphs to visual cores, and graph-based rule validation. Evaluated on OmniDocBench (1,340 pages, 1,551 QA pairs), EU-based chunking substantially improves retrieval metrics (LCS +0.31, Recall@1 +3.4×) and demonstrates robustness across different parsers (MinerU, Docling).

## Method Summary
The method is a deterministic, non-training post-processing pipeline applied to outputs from existing document parsers. It consists of three stages: (1) **Normalization** maps heterogeneous parser element labels to a canonical semantic role vocabulary (DSO ontology, extending DoCO) via a three-priority cascade: regex pattern matching, a parser-specific `TYPE_MAP` using ontology aliases, and embedding-based fallback. (2) **EU Construction** occurs in three phases: Phase A forms visual-core seeds and merges adjacent visual elements; Phase B globally assigns all remaining paragraphs to EUs using a full-page similarity matrix and a threshold (τ=0.40); Phase C applies residual heuristics (section grouping, proximity reattachment, clustering). (3) **Graph Validation** encodes construction rules and invariants (anchoring, type consistency) in a Neo4j schema for potential runtime checks. The pipeline outputs EUs as final, semantically coherent chunks for indexing.

## Key Results
- Retrieval LCS improved by +0.31 (0.50 → 0.81) and Recall@1 improved by 3.4× (0.15 → 0.51) on OmniDocBench.
- Cross-parser consistency confirmed: gains hold for both MinerU and Docling (ΔLCS +0.23–+0.31).
- Text-only queries benefit most, with Recall@1 rising from 0.08 to 0.47.

## Why This Works (Mechanism)
Parser independence is achieved by abstracting parser-specific labels into a unified semantic schema via the DSO ontology and a three-priority normalization cascade (pattern matching, `TYPE_MAP` aliases, embedding fallback). Semantic completeness for visual elements (e.g., tables) is enforced by a global assignment algorithm that computes a full similarity matrix between all paragraphs and all EUs, allocating each paragraph to the EU with maximum similarity above a threshold (τ=0.40), rather than relying on local spatial proximity. Robustness to parser bbox variance is gained because the final EU spatial footprint is dominated by consistently detected non-visual anchors (captions, headers) whose bounding boxes converge across parsers; these stable elements absorb variance from less consistent visual element detections.

## Foundational Learning
- **Concept: Document Components Ontology (DoCO) / Semantic Roles.**  
  *Why needed:* Provides the fixed canonical vocabulary (`table_panel`, `caption`, `section_header`) that all parser outputs are mapped to, enabling parser-independent rule application.  
  *Quick check:* If MinerU labels a table as "TableBlock" and Docling as "table", which component resolves this to a single canonical role?
- **Concept: Embedding-based Semantic Similarity.**  
  *Why needed:* Drives Phase B's global paragraph assignment; the quality of cosine similarity between paragraph and EU member embeddings determines correct contextual linking.  
  *Quick check:* Why is the similarity threshold for Phase B (τ=0.40) lower than typical semantic chunking thresholds (~0.70)?
- **Concept: Graph-Based Rule Specification (Neo4j).**  
  *Why needed:* Separates the *definition* of EU construction rules (merging, assignment) from executable code, allowing dynamic updates and future runtime enforcement via schemas.  
  *Quick check:* What is the purpose of encoding D2/D3 as schemas rather than executable pipeline steps?

## Architecture Onboarding
**Component map:**  
Normalizer → EU Builder (Phase A → Phase B → Phase C) → Graph Validator

**Critical path:**  
Normalization produces DSO-grounded nodes → Phase A forms visual-core EUs → Phase B globally assigns paragraphs → Phase C applies residuals → (optional) Graph validation checks invariants. Phase B depends on Phase A's EUs.

**Design tradeoffs:**  
- *Global vs. Local Assignment:* Phase B's full similarity matrix is computationally heavier (O(P×E)) but captures longer-range semantics versus faster local matching.  
- *Threshold τ:* A low τ (0.40) increases recall but risks noise; the paper's value is corpus-specific.  
- *Footprint convergence reliance:* Assumes non-visual anchors (captions, headers) are detected consistently; missing anchors can break convergence.

**Failure signatures:**  
- Many `plain_text` nodes after normalization → `TYPE_MAP`/fallback failing for parser labels.  
- Low Recall@1 despite EUs → Phase B τ too high, embeddings poor, or global assignment ineffective.  
- High `MinK` → EU grouping remains incomplete (invariant violation).  
- Cross-parser ΔLCS inconsistency → Footprint convergence broken (missing anchors, bbox errors).

**First 3 experiments:**  
1. **Normalization Sanity Check:** Process a sample page; verify `section_header` from Docling's "heading" maps correctly via `TYPE_MAP` and all `hasBbox` are normalized [0,1].  
2. **Phase A Visual Core:** For a table split across multiple bboxes (e.g., Docling), confirm adjacent `table` EUs merge (Y-gap <0.22) and `euKind` is `table_panel`.  
3. **Footprint Convergence:** Run MinerU and Docling on the same page; compute IoU of final EU footprints for a visual element pair. Expected: IoU ≥0.88 (worst-case from paper).

## Open Questions the Paper Calls Out
**Open Question 1:** How can the EU pipeline be extended to handle cross-page references (currently single-page only)?  
*Basis:* Limitations state "Single-page EU: cross-page references are not resolved."  
*Why unresolved:* Multi-page elements (continued tables/figures) are common; resolving them could improve retrieval completeness.  
*What evidence would resolve it:* An extension grouping elements across page boundaries, evaluated on a dataset with cross-page annotations to measure LCS/Recall@K changes.

**Open Question 2:** What is the impact of embedding dilution in long EU chunks on short-query retrieval, and what mitigations (adaptive chunking, embedding aggregation) exist?  
*Basis:* Limitations mention "Embedding dilution: long EU chunks may reduce similarity with short queries."  
*Why unresolved:* EU chunks average 4.7× larger than baselines, potentially misaligning with concise queries.  
*What evidence would resolve it:* Controlled experiments varying EU length (splitting) on short vs. long queries, with embedding similarity analysis.

**Open Question 3:** How can D2/D3 invariants (Anchoring, Type Consistency) be enforced at runtime in production, given they are only schematically defined?  
*Basis:* Limitations state "D2/D3 runtime: Restoration and Validation invariants are defined in Neo4j but not yet executed at runtime."  
*Why unresolved:* Without enforcement, edge cases may produce invalid EUs, harming retrieval.  
*What evidence would resolve it:* Implementation of invariants as inline pipeline checks, with latency/performance benchmarks and violation rate metrics on large corpora.

**Open Question 4:** Why do text-only queries show larger absolute gains in LCS/Recall@1 with EU chunking versus visual queries?  
*Basis:* Inferred from Table 8; text queries' LCS gain (+0.33) and Recall@1 improvement (0.08→0.47) exceed table/figure gains.  
*Why unresolved:* Understanding the cause could tailor EU construction for query types and clarify if gains stem from fragmentation patterns or embedding properties.  
*What evidence would resolve it:* Error analysis comparing text vs. visual retrieval results, examining evidence distribution, EU composition, and embedding similarity; ablation isolating EU component effects per query type.

## Limitations
- **Incomplete type mapping:** `TYPE_MAP` and regex patterns for canonical role assignment are not fully enumerated; unseen parser labels may default to `plain_text`, missing semantic grouping cues.
- **Graph validation opacity:** Neo4j invariant schemas (I1, I2) lack concrete Cypher definitions and enforcement details, limiting reproducibility and runtime deployment.
- **Phase B ambiguity:** Unclear whether similarity uses all EU member embeddings or only visual cores; fixed τ=0.40 may be corpus-sensitive and not generalize.

## Next Checks
1. **Mapping coverage stress test:** Process 100 diverse PDFs with ≥5 parsers; quantify the proportion of elements falling back to `plain_text` due to missing `TYPE_MAP` entries or failed pattern matches.
2. **Phase B ablation and threshold sweep:** Run with Phase B disabled (local assignment only) and with τ varied from 0.2 to 0.6; measure changes in Recall@1 and `MinK` to isolate global assignment's marginal benefit and identify a robust τ range.
3. **Cross-domain footprint convergence:** Apply MinerU and Docling to a new corpus (e.g., 50 financial forms); compute EU footprint IoU for visual elements to test whether convergence generalizes beyond OmniDocBench layouts.
