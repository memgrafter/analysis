# Verified Multi-Agent Orchestration: A Plan-Execute-Verify-Replan Framework for Complex Query Resolution

## Quick Facts
- arXiv ID: 2603.11445
- Source URL: https://arxiv.org/abs/2603.11445
- Reference count: 8
- Primary result: VMAO improves answer completeness from 3.1 to 4.2 and source quality from 2.6 to 4.1 on expert-curated market research queries.

## Executive Summary
VMAO (Verified Multi-Agent Orchestration) addresses the challenge of coordinating multiple specialized LLM agents to resolve complex queries reliably, without constant human oversight. The framework decomposes queries into a dependency-aware DAG of sub-questions, executes them in parallel with context propagation, and uses an LLM-based verifier to evaluate result completeness. Incomplete results trigger adaptive replanning, while configurable stop conditions balance quality and resource usage. Evaluated on 25 expert-curated market research queries, VMAO significantly improves answer completeness (3.1 → 4.2) and source quality (2.6 → 4.1) compared to single-agent baselines, demonstrating the effectiveness of verification-driven orchestration.

## Method Summary
The method follows a Plan-Execute-Verify-Replan cycle. The QueryPlanner translates a complex query into a DAG of atomic sub-questions, each assigned to a specialized agent with tool access. The DAGExecutor schedules nodes whose dependencies are satisfied for parallel execution, propagating parent results as context to children. After each execution wave, a ResultVerifier (LLM) scores completeness and identifies gaps. The AdaptiveReplanner then decides whether to retry incomplete sub-questions or generate new ones to fill gaps. A StopConditionChecker monitors termination criteria (completeness threshold, diminishing returns, token budget, max iterations). The final Synthesizer merges all results into a structured answer with citations. The implementation uses LangGraph, Strands Agents, and AWS Bedrock (Claude Sonnet 4.5, Haiku 4.5, Opus 4.5). The evaluation used an expert-curated dataset of 25 market research queries and LLM-judge scoring.

## Key Results
- Answer completeness improved from 3.1 to 4.2 on a 1–5 scale.
- Source quality improved from 2.6 to 4.1 on a 1–5 scale.
- The framework effectively coordinates multiple agents for complex tasks without requiring constant human intervention.

## Why This Works (Mechanism)
The paper identifies three key mechanisms:

**Mechanism 1: Dependency-aware parallel execution via a DAG**  
The QueryPlanner decomposes the query into sub-questions with explicit dependencies, forming a DAG. The DAGExecutor schedules all ready nodes for concurrent execution and propagates results from parents to children, maximizing parallelism where possible while respecting data dependencies.  
*Core assumption:* The initial decomposition correctly identifies all necessary sub-questions and their dependencies.  
*Break condition:* If replanning frequently needs to add new dependency edges, the initial DAG is systematically flawed, undermining efficiency.

**Mechanism 2: Verification-driven adaptive replanning**  
After each execution wave, the ResultVerifier evaluates every sub-question result, producing a completeness score and listing missing aspects or contradictions. The AdaptiveReplanner uses this aggregated signal to retry incomplete sub-questions or propose entirely new ones, creating a feedback loop that focuses effort on specific gaps.  
*Core assumption:* The verifier reliably distinguishes complete from incomplete answers at the sub-question level, in a way that aligns with the original complex query’s needs.  
*Break condition:* If most replanning iterations simply retry the same sub-questions without introducing new ones, the verifier fails to detect novel gaps, leading to redundant work.

**Mechanism 3: Configurable multi-condition stop criteria**  
Termination is triggered by any of several conditions: a completeness threshold (e.g., 80%), high confidence with partial coverage, diminishing returns (<5% improvement), a token budget (e.g., 1M), or a maximum number of iterations (e.g., 3). These levers let deployments trade thoroughness for efficiency.  
*Core assumption:* The chosen thresholds meaningfully correlate with user-perceived answer adequacy for the target domain.  
*Break condition:* If outputs meeting the completeness threshold are consistently rated unsatisfactory, the metric or threshold is misaligned.

## Foundational Learning
- **Directed Acyclic Graph (DAG) for Task Decomposition**  
  *Why needed:* Enables parallel execution while respecting information flow constraints; the entire parallelism strategy hinges on a correct DAG representation.  
  *Quick check:* For "Analyze Q3 revenue decline by region and propose solutions," identify 3–4 sub-questions and their dependency ordering.

- **LLM-as-a-Verifier for Orchestration (vs. Agent Self-Evaluation)**  
  *Why needed:* The core innovation is using an LLM to judge the *collective* output of multiple agents against the original information needs, not just individual agent outputs.  
  *Quick check:* How would the verification prompt differ when an agent self-critiques its own response versus when an orchestrator assesses a sub-question result?

- **Stop Condition Design as a Resource-Quality Tradeoff**  
  *Why needed:* The framework does not have a single correct stopping point; thresholds must be set based on operational constraints (budget, latency) and the qualitative meaning of each condition.  
  *Quick check:* For a latency-sensitive application, which two stop conditions would you prioritize tightening, and what would be the likely impact on answer completeness?

## Architecture Onboarding
The system comprises seven main components:

**Component map (plain text flow):**  
QueryPlanner → DAGExecutor → AgentPool → ResultVerifier → (if gaps) AdaptiveReplanner → DAGExecutor (next wave) → … → StopConditionChecker (termination) → Synthesizer → Final Answer

**Critical path:** Original query → Plan (DAG) → Execute (Wave 1) → Verify → If gaps and not stopped → Replan (modify DAG) → Execute (Wave N) → … → Verify → If stopped → Synthesize → Final answer.

**Design tradeoffs:**  
- *Parallelism vs. Overhead:* Higher concurrency reduces latency but increases simultaneous tool calls and memory pressure.  
- *Verification cost vs. quality:* Using a more powerful model (e.g., Claude Opus) improves signal quality but consumes many tokens; cheaper models risk poor replanning decisions.  
- *DAG fidelity vs. flexibility:* A static, pre-planned DAG is interpretable but brittle; dynamic replanning adds flexibility but can produce complex, hard-to-debug graphs.

**Failure signatures:**  
- *Infinite replanning loop:* Without a max-iteration limit, a persistent gap could cause endless retries.  
- *Stalled execution:* A single sub-question with unsatisfied dependencies or agent timeout blocks downstream nodes; monitor the size of the ready set.  
- *Verification blindness:* Consistently high completeness scores from the verifier followed by poor human evaluation indicate misalignment of the verifier’s criteria.

**First 3 experiments:**  
1. **Baseline DAG execution:** Run a simple 3-node linear query (A→B→C). Observe execution waves and context propagation. Confirm that C’s prompt contains A and B’s results when `context_from_deps=true`.  
2. **Stop condition threshold sweep:** On a medium-complexity query, vary `ready_threshold` (e.g., 0.6 vs. 0.9). Measure final completeness score versus total tokens and iterations to understand the quality-cost curve.  
3. **Verifier robustness test:** For a sub-question with a deliberately incomplete answer (missing a key data point), confirm the verifier returns `status: incomplete` and lists the specific missing aspect. Then add that missing aspect in a retry and verify the verifier marks the result `complete`.

## Open Questions the Paper Calls Out
**Open Question 1**  
*Question:* What is the isolated contribution of each VMAO component (DAG execution, verification, replanning) to the observed quality improvements?  
*Basis:* Section 6 lists component-level ablation as future work; Section 5.3 notes the static pipeline baseline tests verification and replanning jointly without isolation.  
*Why unresolved:* Current evaluations compare full VMAO against baselines lacking some components but do not systematically disable individual components to measure marginal effects.  
*Resolution:* Conduct ablation experiments where each component is independently removed while holding others constant, measuring changes in completeness and source quality on the same 25-query dataset.

**Open Question 2**  
*Question:* Does VMAO's performance generalize across different LLM families (e.g., GPT, Gemini) beyond the Claude models tested?  
*Basis:* Section 6 states the framework’s effectiveness with other LLM families remains untested; all experiments use Claude Sonnet 4.5 and Opus 4.5.  
*Why unresolved:* The framework is model-agnostic, but effectiveness may vary due to differences in model capabilities, tool-use proficiency, or biases.  
*Resolution:* Replicate the market research evaluation using at least two other major LLM families (e.g., GPT-4o, Gemini 1.5) as both execution and verification models, comparing metrics.

**Open Question 3**  
*Question:* Can VMAO's stop conditions be automatically optimized via learning rather than manually configured thresholds?  
*Basis:* Section 6 proposes learning-based stop conditions trained on execution traces; Section 3.3 defines five fixed thresholds.  
*Why unresolved:* Manual thresholds may not optimally balance quality and cost across diverse query complexities; no data-driven method exists for setting them.  
*Resolution:* Collect execution traces with varying settings, train a model (e.g., reinforcement learning) to predict optimal stopping based on query features and intermediate results, then evaluate against manual thresholds.

**Open Question 4**  
*Question:* When is human-in-the-loop verification necessary in VMAO, and how does it affect the verification-replanning loop?  
*Basis:* Section 6 mentions human-in-the-loop verification for high-stakes queries as a future direction; current verification is fully automated.  
*Why unresolved:* The automated verifier may miss critical errors in high-stakes domains; it is unclear which query types or verification outcomes would benefit from human review and how that integrates with the iterative loop.  
*Resolution:* For a subset of high-stakes market research queries, have domain experts review verification outputs at each iteration, measuring quality improvements, cost increases, and the types of errors corrected by humans versus the automated verifier.

## Limitations
- Exact LLM prompts, verification thresholds, and the private 25-query dataset are undisclosed, hindering direct replication.
- The verifier’s alignment with human judgment regarding answer completeness is not empirically validated.
- Evaluation is restricted to Claude models; generalizability to other LLM families remains untested.

## Confidence
- **High confidence:** The reported metric improvements (completeness +1.1, source quality +1.5) are based on the paper's own controlled evaluation.
- **Medium confidence:** The DAG parallel execution mechanism is clearly specified but not extensively tested on a wide variety of dependency graphs.
- **Low confidence:** The efficacy of verification-driven replanning; neighboring work shows similar paradigms but provides no direct evidence for VMAO’s specific loop.

## Next Checks
1. **Reproduce DAG scheduling:** Implement Algorithm 1; run a 5-node query with a diamond dependency (A→B, A→C, B→D, C→D). Verify D executes only after both B and C complete and receives both contexts.

3. **Stop condition threshold sweep:** On 5 medium queries, vary `completeness_threshold` (0.7 vs. 0.9) and `max_iterations` (2 vs. 4). Measure impact on final human-rated completeness versus total token cost.
