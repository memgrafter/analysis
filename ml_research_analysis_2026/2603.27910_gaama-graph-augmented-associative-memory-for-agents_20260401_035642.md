# GAAMA: Graph Augmented Associative Memory for Agents
## Quick Facts
- arXiv ID: 2603.27910
- Source URL: https://arxiv.org/abs/2603.27910
- Reference count: 25
- Primary result: GAAMA achieves 78.9% mean reward on LoCoMo-10, outperforming tuned RAG (75.0%), HippoRAG (69.9%), A-Mem (47.2%), and Nemori (52.1%).

## Executive Summary
GAAMA introduces a persistent, structured long-term memory for multi-session AI agents. It constructs a hierarchical knowledge graph with four node types (episode, fact, reflection, concept) via a three-step pipeline: verbatim episode storage, LLM-based extraction of atomic facts and topic concepts, and synthesis of cross-session reflections. Retrieval combines semantic similarity search with edge-type-aware Personalized PageRank (PPR), using a low PPR weight (0.1) to augment rather than override embedding results. On the LoCoMo-10 benchmark (1,540 questions), GAAMA achieves a mean reward of 78.9%, surpassing strong baselines. Ablation studies confirm that adding mild PPR augmentation to semantic search over the constructed memory yields a consistent +1.0 percentage point improvement.

## Method Summary
The construction pipeline is applied incrementally as new conversations arrive. First, each conversation turn is stored as a verbatim `episode` node, linked temporally within a session via `NEXT` edges. Second, LLM (GPT-4o-mini) processes episode chunks to extract atomic `fact` nodes (linked to source episodes via `DERIVED_FROM`) and topic `concept` nodes (connected via `HAS_CONCEPT`/`ABOUT_CONCEPT`). The prompts provide explicit rules and JSON output. Third, `reflection` nodes are synthesized from groups of facts using an LLM prompt, linked by `DERIVED_FROM_FACT` edges. The resulting graph contains four node types and five edge types with base weights.

For retrieval, a query is embedded with `text-embedding-3-small`. A candidate pool of size `2B` (where `B` is the sum of per-type budgets) is gathered via cosine similarity. The top `k=40` seeds are weighted by `sim²` and used to initiate PPR on the local subgraph expanded to depth `d=2`. Edge-type weights (from Table 2) and hub dampening (threshold `θ=50`) are applied. PPR scores are max-normalized and combined additively with the original similarity: `final_score = 0.1 * ppr + 1.0 * sim`. Retrieved nodes are bucketed by type, respecting per-type caps (`max_facts=60`, `max_reflections=20`, `max_episodes=80`), sorted chronologically (episodes), and trimmed to a total word budget of 1000. The memory context is fed to an answer generation LLM (GPT-4o-mini, temperature 0). Performance is measured by an LLM-as-judge reward based on fractional coverage of reference facts.

## Key Results
- GAAMA achieves 78.9% mean reward on LoCoMo-10, exceeding tuned RAG (75.0%), HippoRAG (69.9%), A-Mem (47.2%), and Nemori (52.1%).
- Ablation: Adding PPR augmentation (`w_ppr=0.1`) to semantic search over the GAAMA memory yields a consistent +1.0 percentage point improvement.
- The hybrid retrieval approach mitigates hub-dominated retrieval that plagues prior graph-based methods.

## Why This Works (Mechanism)
The hierarchical graph structure prevents single-node hubs from monopolizing retrieval by distributing importance across diverse node types (episodes, facts, reflections, concepts). Edge-type-aware PPR propagates relevance through semantically meaningful relationships (e.g., `ABOUT_CONCEPT`, `DERIVED_FROM_FACT`) rather than uniform edges, allowing cross-session connections without overwhelming the signal. The low PPR weight (0.1) ensures that semantic similarity remains the primary ranking signal, while PPR provides a gentle correction for multi-hop needs. Per-type retrieval budgets force content diversity, preventing episodes from crowding out concise facts and reflections. Together, these design choices balance precision (via embedding similarity) and recall (via graph traversal), leading to robust performance across question types.

## Foundational Learning
**1. Hierarchical Knowledge Graph**
- *Why needed*: To organize memory at multiple granularities (raw episodes, atomic facts, high-level concepts, synthesized reflections) and avoid hub dominance.
- *Quick check*: Does the graph contain exactly four node types and five edge types as described?

**2. Edge-type-aware Personalized PageRank**
- *Why needed*: To perform graph traversal that respects relationship semantics and prevents high-degree hubs from diffusing mass indiscriminately.
- *Quick check*: Are edge weights assigned per type (e.g., `ABOUT_CONCEPT` weight 1.0) and is hub dampening applied when node degree exceeds 50?

**3. Hybrid Semantic-Graph Retrieval**
- *Why needed*: To combine the precision of embedding-based similarity with the recall of graph-based multi-hop, while keeping graph influence bounded.
- *Quick check*: Is the final score computed as `0.1*ppr + 1.0*sim` after max-normalizing PPR scores?

**4. Incremental Graph Construction**
- *Why needed*: To support continuous agent operation without re-building memory from scratch.
- *Quick check*: Are new episodes added verbatim, then facts/concepts extracted from recent chunks, and reflections synthesized periodically?

**5. Per-type Retrieval Budgets**
- *Why needed*: To maintain a balanced mix of node types in the retrieved context, ensuring facts and reflections are not overshadowed by numerous episodes.
- *Quick check*: Are the caps `max_facts=60`, `max_reflections=20`, `max_episodes=80` enforced before word-trimming?

**6. LLM-guided Extraction**
- *Why needed*: To convert raw conversation into structured, atomic knowledge with minimal supervision.
- *Quick check*: Do the extraction prompts (Appendices A, B) produce JSON with `fact`, `concept`, and `reflection` nodes and appropriate edges?

## Architecture Onboarding
**Component Map**
Query -> Embedding -> KNN Candidate Pool (size 2B) -> PPR Seed Selection (top k=40 by sim²) -> PPR Expansion (depth d=2) -> Edge-type-aware PPR Scoring -> Additive Combination with Similarity -> Type Bucketing & Budget Enforcement -> Word Budget Trimming -> Answer Generation

**Critical Path**
1. Receive query.
2. Compute embedding and retrieve initial candidate pool via cosine similarity.
3. Select PPR seeds and expand graph to include 2-hop neighbors.
4. Run PPR on the subgraph with configured weights and hub dampening.
5. Combine scores, enforce per-type budgets, and apply word limit.
6. Construct context from selected nodes (episodes sorted chronologically).
7. Generate answer using LLM prompt.

**Design Tradeoffs**
- *Graph size vs. latency*: Expanding to depth 2 captures useful neighbors but increases PPR computation; depth is fixed to control cost.
- *PPR weight*: A low weight (0.1) preserves semantic ranking while adding mild graph augmentation; too high would let noisy edges dominate.
- *Budgets*: Fixed numeric caps simplify implementation but may not adapt to varying query needs; however they guarantee predictable context size.
- *LLM calls*: Construction and retrieval rely on LLMs; the system trades off accuracy for inference cost. Use of smaller models (GPT-4o-mini) keeps cost manageable but may limit quality.

**Failure Signatures**
- **Concept fragmentation**: Many near-duplicate or overlapping concept nodes (e.g., singular/plural variants) leading to PPR mass splitting. Detect by counting concept nodes with high string similarity or embedding similarity.
- **Hub-dominated concepts**: Concepts with degree >30 (e.g., `personal_growth`) that cause PPR diffusion to spread too widely. Monitor node degree distribution.
- **Budget bypass**: If episodes dominate retrieval despite budgets, the bucketing logic may be buggy or budgets mis-set. Verify type counts in final context.

**First Experiments**
- *Construction sanity check*: Process a small set of conversations and verify expected numbers of episodes, facts, concepts, reflections, and edge types.
- *Retrieval sanity check*: Run a few known queries and compare retrieval results with and without PPR; ensure PPR scores are non-zero and edges are weighted correctly.
- *Budget enforcement test*: Intentionally create a graph with many episodes and query to see if fact count respects `max_facts=60`.

## Open Questions the Paper Calls Out
**Open Question 1**: Concept Canonicalization  
How effective is merging near-duplicate or overlapping concepts at improving retrieval and reducing fragmentation? The paper identifies this as a key future direction and notes existing issues (e.g., 15+ duplicate pairs, broad concepts like `personal_growth` with 44 edges).

**Open Question 2**: Adaptive PPR Gating  
Can a lightweight neural classifier predict per-query whether PPR augmentation helps, thereby improving robustness? The per-category ablation shows high variance for Open Domain questions, suggesting conditional gating could yield gains.

**Open Question 3**: Hyperparameter Generalization  
Do the hand-tuned per-type budgets and fixed `w_ppr=0.1` generalize to other conversation datasets? No sensitivity analysis is provided; optimal settings may vary with dataset characteristics.

**Open Question 4**: Graph Quality vs. Retrieval Limitations  
What portion of failures is due to poor graph construction (missing/incorrect nodes) versus suboptimal ranking? Error analysis points to graph quality as the main bottleneck, but quantitative blame is lacking.

**Open Question 5**: Scalability  
How do construction cost, graph size, and retrieval latency scale with increasing sessions? The paper evaluates only 10 conversations; practical deployment for years of interaction is unclear.

## Limitations
- The trigger frequency for reflection synthesis is unspecified, potentially affecting memory growth and cross-session linking.
- The value of `k` for retrieving related context during node extraction is not given, leaving a gap in the construction procedure.
- Evaluation is limited to LoCoMo-10 with a single LLM (GPT-4o-mini); generalization to other benchmarks, domains, or models is unknown.
- Concept node fragmentation and hub-dominated concepts are observed but not mitigated, which may degrade PPR performance.
