# All-Mem: Agentic Lifelong Memory via Dynamic Topology Evolution

## Quick Facts
- arXiv ID: 2603.19595
- Source URL: https://arxiv.org/abs/2603.19595
- Reference count: 40
- Primary result: All-Mem achieves state-of-the-art performance on LOCOMO and LONGMEMEVAL-S with significantly lower query-time token counts (918 vs >1700) compared to Mem0.

## Executive Summary
All-Mem presents a lifelong memory system for agents that integrates online retrieval from a bounded visible surface with offline non-destructive topology consolidation. The consolidation uses LLM-proposed edits (SPLIT, MERGE, UPDATE) to dynamically reorganize memory. On LOCOMO and LONGMEMEVAL-S benchmarks, it outperforms baselines like Mem0 across multiple metrics while reducing query-time token usage and maintaining lower latency as history grows.

## Method Summary
The method combines two phases: (1) online retrieval limited to a bounded visible memory surface for efficient query answering, and (2) offline consolidation where an LLM suggests topological edits (SPLIT, MERGE, UPDATE) to the memory graph without destroying existing data. The visible surface restricts the number of memories considered at query time, reducing computational cost. The consolidation runs asynchronously, using the LLM's semantic understanding to reorganize the memory topology for improved coherence and relevance over time.

## Key Results
- On LOCOMO: All-Mem attains 4o-J 54.63, F1 52.18, R@5 46.63, N@5 41.02, all above Mem0 (48.91/43.08/38.74/32.13).
- On LONGMEMEVAL-S: 4o-J 60.20, F1 45.19, R@5 94.68, N@5 93.27, vs Mem0 (55.80/36.10/90.20/87.10).
- Query-time injected tokens reduced to 918, compared to over 1700 for other methods, with latency benefits scaling with history.

## Why This Works (Mechanism)
The bounded visible surface limits the memory search space during queries, reducing token usage and latency while avoiding interference from irrelevant memories. The offline LLM-driven consolidation adapts the memory topology through edits (SPLIT, MERGE, UPDATE) to maintain coherence and relevance as new interactions accumulate. This two-phase design balances efficiency with long-term memory quality, mitigating degradation that typically occurs in lifelong settings.

## Foundational Learning
- **Dynamic Topology Evolution**: Why needed? To adapt memory structure to accumulating data without catastrophic forgetting. Quick check: Monitor graph metrics (e.g., connectivity, cluster coherence) over consolidation cycles.
- **Bounded Visible Surface**: Why needed? To ensure predictable query-time efficiency. Quick check: Measure retrieval latency and accuracy across varying surface sizes.
- **LLM-Proposed Edits**: Why needed? To leverage semantic understanding for intelligent memory reorganization. Quick check: Evaluate edit proposal accuracy against human annotations or synthetic ground truth.
- **Lifelong Memory**: Why needed? Agents must retain information across extended, multi-session interactions. Quick check: Test performance on progressively longer dialogue histories.
- **Non-Destructive Consolidation**: Why needed? To maintain memory integrity during reorganization. Quick check: Audit memory preservation rates after edits (e.g., via replay accuracy).

## Architecture Onboarding
- **Component map**: Query -> Visible Surface Search -> Retrieved Responses; Memory Store -> Offline Consolidation (LLM Edit Suggestion) -> Apply Edits -> Updated Memory Store.
- **Critical path**: For queries, the critical path is the search on the visible surface; for maintenance, it is the LLM edit cycle running asynchronously offline.
- **Design tradeoffs**: Visible surface size vs. retrieval coverage; consolidation frequency vs. computational overhead; edit aggressiveness vs. memory stability.
- **Failure signatures**: Declining performance on recent events; token usage spikes; edit operations causing information loss, duplication, or topology drift.
- **First experiments**: 1. Systematically vary visible surface size and measure retrieval metrics (e.g., R@5, latency). 2. Compare edit quality using different LLM backbones (e.g., GPT-4 vs. Llama). 3. Adjust consolidation intervals to balance performance gains against computational cost.

## Open Questions the Paper Calls Out
The paper implicitly suggests several open questions for future research. These include: (1) how the choice of LLM backbone affects the quality of memory edits and overall performance; (2) the impact of consolidation frequency on the trade-off between memory coherence and computational cost; (3) the scalability of the approach to extremely long interaction histories; and (4) the generalizability of results beyond the LOCOMO and LONGMEMEVAL-S benchmarks to other domains and datasets.

## Limitations
- Benchmarks LOCOMO and LONGMEMEVAL-S are newly introduced with no external citations, so their validity and generalizability are unproven.
- Baseline comparisons are limited to Mem0; other state-of-the-art lifelong memory methods (e.g., RAG-based, transformer memory) are not evaluated.
- The LLM-driven consolidation process lacks error analysis, with potential for topology drift or information loss not quantified.

## Confidence
- Performance superiority on LOCOMO and LONGMEMEVAL-S: **Medium** (benchmarks not externally validated).
- Query-time token and latency reductions: **Medium** (token counts plausible but total system cost including offline LLM calls unknown).
- Correctness of topology evolution mechanism: **Low** (theoretical design not empirically dissected; LLM edit reliability unverified).
