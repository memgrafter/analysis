# STEM Agent: A Self-Adapting, Tool-Enabled, Extensible Architecture for Multi-Protocol AI Agent Systems

## Quick Facts
- **arXiv ID:** 2603.22359  
- **Source URL:** https://arxiv.org/abs/2603.22359  
- **Reference count:** 5  
- **Primary result:** STEM Agent unifies five interoperability protocols behind a single gateway, continuously profiles callers via EMA, crystallizes skills from recurring patterns, and achieves 100% pass on a 413-test suite (2.92s runtime).

## Executive Summary
STEM Agent presents a modular, pluripotent architecture for AI agent systems that eliminates lock-in by unifying five interoperability protocols (A2A, AG-UI, A2UI, UCP, AP2) behind a single gateway. The system continuously learns user preferences across more than twenty behavioral dimensions using exponential moving averages (α=0.1) via a Caller Profiler, externalizes all domain capabilities through the Model Context Protocol (MCP), and acquires reusable skills through a biologically-inspired maturation lifecycle. Independent validation via a comprehensive 413-test suite resulted in a 100% pass rate with a total runtime of 2.92 seconds, confirming protocol handler behavior and cross-layer integration. Compared to existing frameworks, STEM uniquely combines multi-protocol support, per-caller adaptation, four memory types, emergent skills, and commerce protocols.

## Method Summary
STEM Agent is implemented as a TypeScript monorepo comprising six packages (shared, agent-core, standard-interface, mcp-integration, memory-system, caller-layer). The core cognitive pipeline processes requests through eight phases: Perceive, Adapt, Skill Match, Reason, Plan, Execute, Learn, and Respond. Domain capabilities are externalized via the Model Context Protocol (MCP), and all interactions are unified through a gateway that mounts protocol-specific handlers (A2A, AG-UI, A2UI, UCP, AP2) as Express.js routers. The Caller Profiler maintains per-caller profiles across twenty-plus behavioral dimensions, updating each dimension using an exponential moving average with α=0.1; confidence grows with interaction count. Skills emerge from recurring interaction patterns: episodes are grouped by action patterns, and when sufficient frequency and topic overlap are detected, a skill crystallizes and matures through a lifecycle with success thresholds and apoptosis rules. The system employs four memory types (episodic, semantic, procedural, user context) with consolidation mechanisms. Validation consists of 413 tests covering protocol integration, handler correctness, and cross-layer behavior, achieving 100% pass in 2.92 seconds.

## Key Results
- Unifies five interoperability protocols (A2A, AG-UI, A2UI, UCP, AP2) behind a single, pluggable gateway.
- Implements a continuously learning Caller Profiler (EMA α=0.1 across 20+ dimensions) and a skill crystallization lifecycle that turns recurrent patterns into reusable capabilities.
- Achieves 100% pass rate on a comprehensive 413-test suite with total runtime of 2.92 seconds, validating protocol handler behavior and cross-layer integration.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** The unified gateway with pluggable protocol handlers eliminates architectural lock-in by allowing multiple interaction protocols to coexist.
- **Mechanism:** Each protocol (A2A, AG-UI, etc.) implements a `createRouter()` method returning an Express.js router, mounted with shared middleware (auth, rate-limiting). All protocols route to the same Agent Core cognitive pipeline.
- **Core assumption:** Protocol-specific transformations (serialization, state management) are confined to thin handler layers; the core logic remains protocol-agnostic.
- **Evidence anchors:**
  - [abstract] "unifies five interoperability protocols (A2A, AG-UI, A2UI, UCP, and AP2) behind a single gateway"
  - [section 4] "Each protocol handler implements a `createRouter(): Router` method... Adding a new protocol requires only implementing the handler and mounting its router."
  - [corpus] Weak neighbor relevance; no direct evidence in retrieved corpus.
- **Break condition:** If a protocol handler incorrectly transforms or fails to route requests, downstream core pipeline receives malformed input, violating the protocol agnosticism assumption.

### Mechanism 2
- **Claim:** The Caller Profiler’s exponential moving average (EMA) enables continuous, stable adaptation to user preferences without manual retraining.
- **Mechanism:** For each of 20+ dimensions, the profile value `vₜ` is updated per interaction: `vₜ₊₁ = (1−α)·vₜ + α·sₜ`, with α=0.1. Confidence increases with interaction count via `conf(n)=n/(n+κ)`, blending learned and current signals.
- **Core assumption:** User preferences evolve slowly enough for EMA smoothing, and signals `sₜ` extracted from interactions are meaningful proxies for underlying preferences.
- **Evidence anchors:**
  - [abstract] "continuously learns user preferences across more than twenty behavioral dimensions using exponential moving averages (α=0.1)"
  - [section 5.1] Full EMA equation, α=0.1 justification, confidence gating.
  - [corpus] No direct corpus evidence; adjacent work on adaptation (Alomrani et al., 2025) discusses adaptive compute but not EMA profiling.
- **Break condition:** Rapid preference shifts (non-stationarity) or noisy signal extraction would cause the EMA to lag or oscillate, degrading adaptation quality.

### Mechanism 3
- **Claim:** Biologically-inspired skill crystallization converts recurring interaction patterns into reusable procedures, reducing future compute.
- **Mechanism:** The `Learn` phase groups episodes by action patterns; when ≥3 episodes share an action key and ≥50% share topic keywords, a progenitor skill forms. Skills mature (committed after 3 successes, mature after 10) or undergo apoptosis (failure rate <0.3 after 10 activations).
- **Core assumption:** Frequent successful patterns represent generalizable strategies, and success thresholds reliably separate robust skills from noise.
- **Evidence anchors:**
  - [abstract] "recurring interaction patterns crystallize into reusable agent skills through a maturation lifecycle analogous to cell differentiation"
  - [section 5.5] Full crystallization rules (episode grouping, keyword threshold) and maturation/apoptosis thresholds.
  - [corpus] Neighbors discuss memory (Ai et al., 2025) and multi-agent patterns but not this specific crystallization lifecycle.
- **Break condition:** If pattern grouping is too strict, true recurring strategies fail to crystallize; if too lenient, spurious skills proliferate and waste resources.

## Foundational Learning
- **Concept:** Protocol plurality via a unified gateway  
  - *Why needed here:* Prevents commitment to a single interaction standard; allows callers to use A2A, AG-UI, etc., interchangeably.  
  - *Quick check question:* If you add a new protocol handler, what must you ensure about its `createRouter()` output and middleware usage?

- **Concept:** EMA-based caller profiling  
  - *Why needed here:* Provides smooth, computationally cheap per-user adaptation without batch retraining.  
  - *Quick check question:* How would changing `α` from 0.1 to 0.3 affect profile responsiveness vs. stability?

- **Concept:** Skills maturation lifecycle  
  - *Why needed here:* Turns observed successful patterns into first-class reusable capabilities, emerging from interaction history.  
  - *Quick check question:* What triggers apoptosis of a crystallized skill, and why is this biologically analogous?

## Architecture Onboarding
- **Component map:**  
  - Five layers (Caller, Standard Interface, Agent Core, Memory, MCP Integration) implemented as a TypeScript monorepo with six packages (`shared`, `agent-core`, `standard-interface`, `mcp-integration`, `memory-system`, `caller-layer`).  
  - Key engines: Perception, Reasoning (with Strategy Selector), Planning, Execution, Skill Manager.  
  - Gateway: Express.js app mounting five protocol routers and four framework adapters.  
  - Memory: Episodic (PostgreSQL+pgvector), Semantic, Procedural, User Context.

- **Critical path:**  
  A request enters via any protocol handler → Gateway middleware → Agent Core’s 8-phase pipeline (Perceive→Adapt→Skill Match→Reason→Plan→Execute→Learn→Respond) → MCP tool calls if needed → Memory updates → Response routed back via same protocol.

- **Design tradeoffs:**  
  - Pluggable handlers vs. slight overhead: Each protocol adds serialization/middleware cost but preserves core simplicity.  
  - In-memory caches (profiles, idempotency) vs. scalability: Simplicity now; distributed locking needed for horizontal scaling.  
  - Simple rule-based strategy selection vs. learned adaptation: Deterministic and explainable but may miss nuanced task-strategy mappings.

- **Failure signatures:**  
  - Protocol handler tests fail: Check router mounting, schema validation, error propagation.  
  - Caller profile not updating: Verify signal extraction logic in `PERCEIVE`, EMA update in `UPDATEPROFILE`.  
  - Skills not crystallizing: Inspect episode grouping thresholds (min 3 episodes, 50% keyword overlap).  
  - MCP tool failures: Check transport connectivity, schema matching, retry circuit breaker.

- **First 3 experiments:**  
  1. Run full test suite (`npm test`); confirm 413 tests pass in <3s, especially protocol integration tests for A2A JSON-RPC, AG-UI event sequencing, UCP idempotency.  
  2. Send identical payloads via two protocols (e.g., REST `/api/v1/chat` and A2A `tasks/send`); verify identical `AgentResponse` structure and core pipeline execution.  
  3. Simulate 20+ interactions with a fixed caller; inspect `callerProfile` in DB to confirm EMA updates across dimensions and confidence growth toward saturation.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How can the Strategy Selector's deterministic rules be replaced with a learned, adaptive model for reasoning strategy selection that responds to real-time task characteristics and caller profiles?  
- **Basis in paper:** [explicit] The authors state as future work: "learned strategy selection via adaptive test-time compute." The current implementation uses fixed rules (Section 5.4).  
- **Why unresolved:** The fixed rule-based approach may not capture complex interactions between task features, caller preferences, and strategy effectiveness across diverse domains.  
- **What evidence would resolve it:** A comparative benchmark showing a learned selector (e.g., via reinforcement learning) outperforms the rule-based system on accuracy, efficiency, or user satisfaction across MAFBench or similar suites.

### Open Question 2
- **Question:** What are the scalability limits and failure modes of the in-memory stores for caller profiles and idempotency caches under high-concurrency, distributed deployments?  
- **Basis in paper:** [inferred] The Limitations section (7) identifies: "In-memory stores for profiles and idempotency caches require distributed locking under high concurrency."  
- **Why unresolved:** The paper's validation used a test suite, not a load test. The design choice for in-memory storage conflicts with stated scalability needs, but the exact breaking point and required distributed coordination mechanisms are undefined.  
- **What evidence would resolve it:** A formal scalability analysis and stress test reporting throughput/latency degradation curves, lock contention metrics, and a proposed distributed cache or database migration strategy with performance comparisons.

### Open Question 3
- **Question:** Can skills be effectively transferred or shared across different caller sessions and user contexts, and what mechanisms prevent inappropriate skill application?  
- **Basis in paper:** [explicit] Future work includes: "embedding-based skill matching and cross-session skill transfer." The current skill maturation is per-agent (Section 5.5).  
- **Why unresolved:** Skills crystallize from patterns within a single agent's interaction history. It is unknown if semantic similarity (via embeddings) can safely generalize skills across users with differing profiles or if cross-session transfer introduces harmful biases or errors.  
- **What evidence would resolve it:** An experiment measuring skill transfer success rates (skill reuse leading to correct outcomes) across a diverse set of simulated caller profiles, with analysis of failure cases to define safe transfer constraints.

### Open Question 4
- **Question:** What is the security posture and attack surface of the novel UCP and AP2 commerce protocols, and how do they compare to established financial transaction standards?  
- **Basis in paper:** [inferred] The Limitations state: "Commerce protocol maturity: UCP and AP2 lack external adoption and formal threat modeling." The protocols are described (Section 4) but without security analysis.  
- **Why unresolved:** The protocols handle checkout sessions and payments. Without formal threat models, audits, or penetration testing, vulnerabilities (e.g., audit trail tampering, mandate spoofing, idempotency bypass) remain undetected, hindering real-world deployment.  
- **What evidence would resolve it:** A published formal security analysis (e.g., using a framework like STRIDE) and a red team exercise report against a reference implementation, comparing findings to standards like PCI-DSS or Open Banking.

## Limitations
- **External Dependency Opacity:** The exact configuration of MCP servers and LLM inference used in the test suite is unspecified, hindering full reproducibility.
- **Limited External Validation:** Evidence is primarily internal; the corpus shows weak neighbor relevance and no independent corroboration of mechanisms.
- **Scalability Assumptions:** In-memory stores for profiles and idempotency caches and rule-based strategy selection are validated only in a monorepo test environment, not under distributed high-concurrency conditions.

## Confidence

- **EMA-based Per-Caller Adaptation:** Medium
- **Biologically-Inspired Skill Crystallization:** Medium
