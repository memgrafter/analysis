# AgentLTV: An Agent-Based Unified Search-and-Evolution Framework for Automated Lifetime Value Prediction
## Quick Facts
*   **arXiv ID:** 2602.21634
*   **Source URL:** https://arxiv.org/abs/2602.21634
*   **Reference count:** 40
*   **Primary result:** On a large-scale industrial dataset, AgentLTV reduced error rate by 41.26% and improved normalized Gini by 15.44% versus the strongest baseline.

## Executive Summary
AgentLTV tackles the manual, scenario-specific effort required to build accurate Lifetime Value (LTV) prediction pipelines. It introduces a fully automated framework that searches over executable pipeline programs by combining a Monte Carlo Tree Search (MCTS) stage for broad, budget-aware exploration with a subsequent Evolutionary Algorithm (EA) stage for focused refinement. Both stages are orchestrated by LLM-driven agents that generate, execute, validate, and repair code. Evaluated on a major industrial dataset, AgentLTV substantially outperformed existing methods in offline metrics and demonstrated superior online ranking consistency and value calibration, confirming its practical utility for automated, robust LTV modeling.

## Method Summary
AgentLTV treats an LTV pipeline as an executable program and automates its design via a two-stage search. First, an MCTS stage explores a broad space of modeling choices under a fixed computational budget. It builds a tree of pipeline programs, using the PUCT criterion and a Pareto-aware multi-metric reward to select nodes for expansion. LLM agents (Adviser, Expert Optimizer, Code Generator, Code Fixer) propose edits, generate code, execute it, and repair failures. Second, an EA stage refines the best program from MCTS. It initializes multiple "islands" with mutated variants of that program and evolves them over generations via selection, crossover, and mutation, again guided by LLM agents. Periodic migration between islands shares high-fitness individuals. The globally best program after evolution is deployed.

## Key Results
*   Reduced error rate by 41.26% and improved normalized Gini by 15.44% on a large-scale industrial dataset compared to the strongest baseline.
*   Online A/B testing showed superior ranking consistency (Same Interval Ratio) and value calibration, with pronounced gains for high-value and negative-LTV user segments.
*   Ablation studies confirmed the complementary roles of MCTS (critical for ranking metrics) and EA (important for error reduction).

## Why This Works (Mechanism)
The framework succeeds through three synergistic mechanisms. First, the MCTS stage enables structured, wide-reaching exploration of the vast, non-differentiable space of LTV pipeline architectures. Guided by the PUCT selection rule and a Pareto-aware reward that balances multiple metrics (error, rank correlation, complexity), it efficiently identifies promising model families within a limited evaluation budget. Second, the EA stage performs population-based refinement on the best MCTS-discovered program. Island-based evolution with crossover, mutation, and migration allows for deep local optimization and prevents premature convergence, improving final performance and stability. Third, LLM-driven multi-agent collaboration grounds the entire search in executable, domain-aware code. The Code Generator produces interface-compliant programs, the Code Fixer handles execution errors, and the Adviser/Expert Optimizer inject LTV-specific knowledge to propose edits. This creates a closed loop where abstract ideas are turned into runnable, evaluated pipelines, enabling end-to-end automation.

## Foundational Learning
*   **Concept: Monte Carlo Tree Search (MCTS) with PUCT**
    *   **Why needed here:** MCTS explores a discrete space of program edits where each evaluation (training a model) is expensive. PUCT balances exploring untried modifications with exploiting known high-reward nodes.
    *   **Quick check:** What does the `c_puct` parameter control in the PUCT formula (Eq. 2), and why is it combined with a Pareto-aware reward?
*   **Concept: Island-Based Evolutionary Algorithms**
    *   **Why needed here:** Island evolution prevents premature convergence by maintaining parallel populations that evolve independently and occasionally exchange individuals (migration), helping to explore diverse architectures.
    *   **Quick check:** How does periodic migration (`𝜏` generations) in Algorithm 2 help avoid local optima compared to a single-population EA?
*   **Concept: LLM-as-Code-Generator with Execution Feedback**
    *   **Why needed here:** The search space consists of full, executable Python pipelines. LLMs must generate syntactically correct, interface-compliant code. Execution feedback grounds iterations in reality, moving beyond hypothetical code.
    *   **Quick check:** Why is a "unified pipeline interface" (data loading, training, evaluation, logging) necessary for comparing candidate programs generated by different LLM prompts?
*   **Concept: Pareto-Aware Multi-Metric Optimization**
    *   **Why needed here:** LTV model quality is multi-faceted (e.g., error, rank correlation, calibration). A single scalar reward can obscure trade-offs. The Pareto-aware function identifies solutions on the multi-objective frontier, promoting diverse, balanced candidates.
    *   **Quick check:** How does combining normalized metrics, frontier membership (`I_Pareto`), and crowding distance (`d_crowd`) in Eq. 3 guide MCTS toward structurally diverse, high-performing regions?

## Architecture Onboarding
*   **Component map:**
    Configuration Module -> MCTS Module (MCTS Agent, Adviser, Expert Optimizer, Code Generator, Code Fixer)
    Configuration Module -> EA Module (EA Agent, Adviser, Expert Optimizer, Code Generator, Code Fixer)
    MCTS/EA Modules -> Shared Interface (for fair program evaluation)
    Configuration Module -> Dataset `D`
    MCTS Module -> `c_MCTS` -> EA Module -> `c*` (final deployed model)
*   **Critical path:** 1. Configuration initializes agents and loads data. 2. MCTS runs: multi-root init -> PUCT-guided expansion/backpropagation -> outputs best `c_MCTS`. 3. EA runs: seeds islands with `c_MCTS` variants -> evolves with migration -> outputs global best `c*`. 4. Deploy `c*`.
*   **Design tradeoffs:** MCTS explores broadly but shallowly; EA refines deeply but depends on `c_MCTS` quality. Using multiple LLM APIs improves diversity but increases cost/latency. A rigid unified interface ensures fair comparison but may creatively constrain architectures.
*   **Failure signatures:** MCTS failure: shallow best node (<2 depth) or low tree diversity. EA failure: rapid island convergence or no improvement over `c_MCTS`. Code generation failure: high repair rate in Code Fixer or frequent assertion failures.
*   **First 3 experiments:**
    1.  Validate MCTS root diversity: After initialization, inspect the `K` root programs' architectures and scores; they should span diverse families (e.g., GBDT, DNN, TCN).
    2.  Test EA migration impact: Run EA with `𝜏 = ∞` (no migration) vs. `𝜏 = periodic`. Compare final best fitness and population diversity; migration should improve the global best and maintain diversity.
    3.  Compare single-stage vs. two-stage: Run pure MCTS (with total budget `B + B_EA`) and pure EA (seeded randomly) vs. AgentLTV's MCTS→EA pipeline. The two-stage approach should dominate, confirming complementary roles.

## Open Questions the Paper Calls Out
*   **Question 1:** How can an automated data profiling agent be integrated into AgentLTV's search loop to dynamically adapt root program initialization based on dataset characteristics?
*   **Question 2:** Is the two-stage division of labor between MCTS (broad exploration) and EA (refinement) universally optimal, or do their relative contributions shift with different data regimes (e.g., high vs. low sparsity, static vs. temporal feature dominance)?
*   **Question 3:** Does AgentLTV discover genuinely novel LTV architectures, or does it primarily converge to rediscovering established patterns (e.g., ZILN-like components) due to biases in its initial method library?
*   **Question 4:** How sensitive is AgentLTV's search efficacy and reproducibility to the choice of LLM backend, prompt engineering, and the inherent non-determinism in code generation?

## Limitations
*   Core hyperparameters (`c_puct`, reward weights, island parameters) and exact LLM prompts are not fully disclosed, hindering exact replication.
*   The domain knowledge base (27 method hints) and suggestion taxonomy are only partially described; Pareto frontier computation details are lacking.
*   Evaluation is limited to one industrial dataset and one public benchmark without full cross-dataset validation; neighboring literature provides weak context for MCTS-driven pipeline search.

## Confidence
*   **Performance improvement** (error rate −41.26%, normalized Gini +15.44%): *Medium*. Strong numbers from a single dataset; no independent replication yet.
*   **MCTS broad exploration**: *Medium*. Ablation shows benefit, but tree is wide–shallow; PUCT reward design not thoroughly validated.
*   **EA refinement**: *Medium*. Contribution appears secondary to MCTS; island-based evolution effect size unclear.
*   **LLM-driven code generation/repair**: *Low*. Success rates unreported; prompts and fixer logic opaque; heavy reliance on unquantified LLM capability.

## Next Checks

2.  **LLM necessity ablation:** Replace LLM agents with a random edit operator within the MCTS/EA framework; measure performance drop to isolate the LLM contribution.
