# Visual Model Checking: Graph-Based Inference of Visual Routines for Image Retrieval

## Quick Facts
- **arXiv ID**: 2602.17386
- **Source URL**: https://arxiv.org/abs/2602.17386
- **Reference count**: 24
- **Primary result**: A model-checking framework that re-ranks embedding-based retrieval and significantly improves performance on complex compositional queries (e.g., CLIP zero-shot Recall@10 on COCO-All increases from 0.579 to 0.621).

## Executive Summary
This paper tackles a key limitation of modern embedding-based image retrieval: the inability to reliably satisfy complex, compositional queries that involve counting, spatial relationships, or text. The authors propose a framework that integrates formal model checking. Natural language queries are decomposed into subject-predicate-object triplets. For each triplet, a large language model (LLM) generates an executable Python visual routine that verifies a specific constraint using an open-vocabulary object detector. Candidate images are then ranked by the fraction of satisfied routines. The method not only works as a standalone retriever but also consistently boosts the performance of existing embedding systems when used for re-ranking. Evaluations on MS-COCO show particular strength on hard, compositionally complex queries, while also delivering zero-shot Recall@K improvements across standard splits. The approach yields a verifiable and interpretable retrieval process.

## Method Summary
The framework begins by parsing a natural language query into a set of subject-predicate-object triplets. Each triplet is sent to an LLM, which produces a Python visual routine—a small program that operates on an image using an open-vocabulary detector and performs a logical check (e.g., “count of objects”, “spatial relationship”, “text presence”). These routines are executed on candidate images, producing a binary satisfaction verdict per routine. The final score for an image is the proportion of routines it satisfies, enabling ranking. For retrieval, the system can either generate routines for a query and score a large corpus, or more efficiently re-rank a shortlist provided by an embedding-based retriever (e.g., CLIP). This decomposition into independently verified logical units allows precise constraint handling and interpretable results.

## Key Results
- On MS-COCO, the standalone method is competitive on standard splits and shows clear advantages on hard compositional queries involving text, counting, and spatial reasoning.
- When used to re-rank CLIP and ALIGN outputs, it consistently improves zero-shot Recall@K across splits; e.g., CLIP Rec@10 on COCO-All jumps from 0.579 to 0.621.
- The verification process is interpretable: each satisfied routine corresponds to a verifiable constraint.

## Why This Works (Mechanism)
The core idea is to treat image retrieval as a model checking problem: a query specifies a set of logical properties that a satisfying image must exhibit. By decomposing a complex query into simple triplets, the system isolates each constraint and verifies it independently using a visual routine. This avoids the entanglement problem of monolithic embedding approaches, where a single vector must implicitly capture all query nuances. The use of LLM-generated routines provides flexibility: the same detector can be reused in many ways, and routines can express rich logical conditions (counts, relations, text). Open-vocabulary detection allows the system to handle any object category without retraining. The fraction of satisfied routines offers a robust, explainable ranking signal, and the modular design makes it easy to re-rank outputs from any base retriever, combining the broad coverage of embeddings with precise verification.

## Foundational Learning
- **Model checking**: Formal verification technique to check if a system satisfies logical specifications. *Why needed*: Provides a rigorous framework for decomposing and verifying complex queries. *Quick check*: Simulate on a small set of hand‑crafted queries and verify each constraint with ground‑truth image annotations.
- **Triplet decomposition**: Breaking a query into subject‑predicate‑object units. *Why needed*: Simplifies reasoning and maps naturally to visual routines. *Quick check*: Parse 50 natural language queries and ensure each yields at least one meaningful triplet.
- **Open‑vocabulary detection**: Detecting objects beyond a fixed set using vision‑language models. *Why needed*: Enables routines to reference arbitrary categories mentioned in the query. *Quick check*: Run detector on a few images and verify presence of rare classes (e.g., “stopsign”, “umbrella”).
- **LLM code generation**: Using an LLM to produce executable Python code. *Why needed*: Allows flexible specification of visual constraints without hand‑designed logic. *Quick check*: Generate routines for a set of triplets and check syntactic correctness and relevance.
- **Compositional query reasoning**: Handling queries that combine multiple constraints. *Why needed*: Real‑world queries often require counting, spatial relations, or text. *Quick check*: Construct compound queries (e.g., “two dogs left of a bike”) and test if routines can verify all parts.
- **Re‑ranking**: Adjusting an initial ranking with a secondary scoring model. *Why needed*: Leverages strengths of both embedding‑based retrieval and verification. *Quick check*: Apply re‑ranking to top‑K results from a baseline retriever and measure overlap change.

## Architecture Onboarding
**Component map**:  
Natural Language Query -> Parser -> Triplets -> LLM -> Visual Routines -> Open‑Vocabulary Detector -> Image Features -> Verifier (satisfaction checks) -> Fraction Score -> Ranker -> Ranked List.  
For re‑ranking: Candidate Images (from embedding retriever) -> Visual Routines -> Verifier -> Score -> Re‑ranker.

**Critical path**: The main data flow from query to ranking: parsing, routine generation, detection, verification, scoring. In re‑ranking, the candidate images come from a precomputed embedding list; the routines are still generated per query.

**Design tradeoffs**:  
- *Flexibility vs reliability*: LLM‑generated code can express many constraints but may be buggy or semantically off.  
- *Detector accuracy*: The verifier depends entirely on the detector’s open‑vocabulary performance; errors propagate.  
- *Computational cost*: Generating and executing multiple routines per image is expensive compared to embedding similarity, but acceptable for re‑ranking a shortlist.  
- *Interpretability*: Routines provide explainable decisions but at the cost of simplicity (e.g., a single routine may combine several checks).

**Failure signatures**:  
- Routine generation failure (non‑executable code, infinite loops).  
- Detector misses relevant objects or hallucinates, leading to false negatives/positives.  
- Triplet parser produces incomplete or incorrect decomposition (e.g., missing an attribute).  
- Re‑ranking degrades when the initial candidate set is poor (few positives in top‑K).

**First experiments**:  
1. *Routine correctness audit*: Sample 100 queries, collect generated routines, and have domain experts rate executability and semantic fidelity.  
2. *Detector sensitivity analysis*: Vary detector confidence thresholds and measure impact on retrieval metrics to understand robustness.  
3. *Cross‑retriever compatibility*: Test re‑ranking with different embedding models (CLIP, ALIGN, BLIP) on COCO to confirm generalizability.

## Open Questions the Paper Calls Out
The paper does not explicitly list open questions. However, based on the identified limitations and the approach, several natural open questions arise for future work:
- How can we improve the reliability of LLM‑generated visual routines to minimize errors and ensure semantic alignment?
- What are the limits of the current open‑vocabulary detector, and how can we build more robust detectors for verification?
- Does the method generalize to other datasets beyond MS‑COCO, such as those with more diverse scenes or query types?
- Can the computational overhead be reduced to make the approach feasible for large‑scale retrieval without re‑ranking?
- How does the re‑ranking performance vary with the quality of the initial embedding‑based candidate set, and can we adaptively choose when to re‑rank?

## Limitations
- LLM‑generated routines may be erroneous or misaligned with query semantics; error rates are unreported.
- Overall performance is heavily dependent on the open‑vocabulary detector; its limitations directly constrain the verifier.
- Evaluation is restricted to MS‑COCO; generalization to other datasets or more diverse, real‑world queries is unknown.
- Efficiency concerns are ignored; the computational overhead of routine generation and execution may hinder scalability.
- Re‑ranking gains might rely on high‑quality initial candidate sets; performance could drop with weaker embeddings.

## Confidence
- *Handling complex compositional queries*: **Medium** – decomposition is sound in theory, but robustness to LLM/detector errors is unverified.
- *Standalone competitiveness on COCO*: **Medium** – reported advantages on hard queries lack statistical detail and full metric breakdowns.
- *Re‑ranking improvement*: **Medium‑High** – the zero‑shot Recall@10 boost (0.579→0.621) is notable but requires replication across seeds and datasets.

## Next Checks
1. **Decomposition ablation**: Compare the full triplet‑based method against a single monolithic routine per query to isolate the benefit of logical decomposition.
2. **Human routine audit**: Sample 100 queries and involve experts to assess correctness, executability, and semantic fidelity of generated Python routines.
3. **Cross‑dataset generalization**: Evaluate on an established compositional benchmark (e.g., Flickr30k Entities or Visual Genome) and compare against state‑of‑the‑art methods.
