# DataFactory: Collaborative Multi-Agent Framework for Advanced Table Question Answering

## Quick Facts
- arXiv ID: 2603.09152
- Source URL: https://arxiv.org/abs/2603.09152
- Reference count: 7
- Primary result: DataFactory achieves +20.2% accuracy on TabFact and +23.9% on WikiTQ over baseline methods.

## Executive Summary
DataFactory tackles three core TableQA challenges—context length limits, hallucinations, and complex reasoning—by introducing a multi-agent framework centered on a ReAct-coordinated Data Leader. This orchestrator dynamically decomposes user queries and delegates tasks to two specialized teams: the Database Team (SQL) and the Knowledge Graph Team (Cypher). The framework features an automated data-to-knowledge graph transformation (T:D×S×R→G) to enable multi-hop reasoning and context engineering (RAG) to ground LLM outputs in verified schemas and historical examples.

Evaluated on TabFact, WikiTQ, and FeTaQA using eight LLMs, DataFactory substantially outperforms baselines, gaining +20.2% on TabFact and +23.9% on WikiTQ. Collaboration between teams yields 5.5%–17.1% ROUGE-2 improvements over single-team setups. Performance peaks with 1–3 tool calls; excessive coordination (>6 calls) degrades accuracy, highlighting the need for balanced multi-agent interaction.

## Method Summary
DataFactory is a multi-agent framework where a Data Leader uses the ReAct paradigm to iteratively decompose queries and coordinate two teams. The Database Team generates and executes SQL queries; the Knowledge Graph Team performs Cypher traversals on an automatically constructed knowledge graph. The transformation T:D×S×R→G converts raw tables, schemas, and relational hints into a semantic graph. Both teams employ retrieval-augmented generation (RAG) to incorporate historical QA pairs, schema information, and domain rules, reducing hallucinations. The system is evaluated on three standard benchmarks with eight LLMs, demonstrating significant accuracy gains and the importance of optimal tool-call frequency.

## Key Results
- Achieves +20.2% accuracy on TabFact and +23.9% on WikiTQ compared to state-of-the-art baselines.
- Multi-team collaboration outperforms single-team configurations by 5.5%–17.1% (ROUGE-2).
- Optimal performance occurs with 1–3 tool calls; exceeding six calls leads to accuracy degradation.

## Why This Works (Mechanism)
### Mechanism 1: ReAct-coordinated Data Leader
- **Claim:** The Data Leader uses the ReAct paradigm to dynamically decompose user queries and coordinate between Database and Knowledge Graph teams, enabling adaptive multi-step reasoning.
- **Mechanism:** It follows a three-stage principle—data discovery, evidence-based query planning, and comprehensive analysis—through iterative thought-action-observation cycles. The Data Leader first explores available data resources, then formulates and dispatches SQL or Cypher queries based on verified evidence, and finally synthesizes results from both teams, resolving conflicts via data provenance analysis.
- **Core assumption:** Complex TableQA requires both structured (SQL) and relational (Cypher) reasoning modalities; a centralized orchestrator with meta-reasoning can optimize task delegation and synthesis better than fixed workflows or single agents.
- **Evidence anchors:** Abstract mentions "Data Leader employing the ReAct paradigm for reasoning orchestration"; Section 4.4.1 details the three-stage principle and Section 4.4.2 describes dynamic team dispatch and conflict arbitration; neighbor paper DeALOG provides contrast with decentralized coordination.
- **Break condition:** If reasoning cycles exceed optimal frequency (e.g., >6 tool calls), performance degrades due to decision confusion and error accumulation, as shown by RQ5's inverted U-shaped curve.

### Mechanism 2: Automated Data-to-Knowledge Graph Transformation
- **Claim:** Automated data-to-knowledge graph transformation via the mapping function T:D×S×R→G enables multi-hop reasoning by capturing semantic relationships absent in pure SQL queries.
- **Mechanism:** The Knowledge Graph Information Processing Agent executes a three-stage workflow: LLM-based strategy generation to define entity and relationship patterns, configuration validation for consistency, and parallel graph construction using split-based entity extraction and rule-based relationship discovery (intra-row co-occurrence and cross-row grouping).
- **Core assumption:** Tabular data embeds implicit semantic networks that can be algorithmically extracted into graph structures, facilitating relational queries beyond tabular aggregations.
- **Evidence anchors:** Abstract states "We formalize automated data-to-knowledge graph transformation via the mapping function T:D x S x R -> G"; Section 4.3.1 presents theoretical frameworks (equations 1-8) and the three-stage implementation; corpus evidence is weak but neighbor papers like "Augment before You Try" focus on table expansion rather than automated KG construction.
- **Break condition:** Inaccurate LLM-generated patterns or noisy data lead to flawed entity/relationship extraction, producing knowledge graphs that misrepresent semantics and degrade query accuracy.

### Mechanism 3: Context Engineering for Hallucination Reduction
- **Claim:** Context engineering that integrates historical QA pairs, schema information, and domain knowledge into prompts mitigates hallucinations in SQL and Cypher generation.
- **Mechanism:** Database and Knowledge Graph Retrieval Agents use retrieval-augmented generation (RAG) to fetch vector-similarity-matched few-shot examples, DDL/graph schemas, and domain rules, constructing prompts that ground LLM outputs in verified patterns and structures.
- **Core assumption:** Rich, relevant context reduces LLM hallucinations by leveraging in-context learning to align generated code with actual data schemas and successful historical executions.
- **Evidence anchors:** Abstract mentions "context engineering strategies that integrate historical patterns and domain knowledge to reduce hallucinations"; Sections 4.2.2 and 4.3.2 show prompt templates with history examples, schema, and additional context for both teams; corpus evidence is indirect; neighbor "Table-CoT" uses chain-of-thought but lacks integrated RAG for hallucination reduction.
- **Break condition:** If retrieved historical examples are irrelevant or schema information is outdated, context fails to prevent hallucinations, particularly for novel query types or evolving data schemas.

## Architecture Onboarding
- **Component map:** Data Leader (ReAct agent) -> Database Team (Information Processing Agent, Retrieval Agent, Analysis Agent, Visualization Agent) -> SQL Database; Data Leader -> Knowledge Graph Team (Information Processing Agent, Retrieval Agent, Analysis Agent, Visualization Agent) -> Neo4j Graph Database; Vector Database (historical QA) supports both teams.
- **Critical path:** User query → Data Leader data discovery (explore schemas, sample values) → evidence-based planning → dispatch to teams → execute SQL/Cypher → return results → Data Leader synthesis (integrate, arbitrate conflicts) → final answer. The three-stage workflow (explore-verify-analyze) is core.
- **Design tradeoffs:**
  - Natural language consultation vs. rigid workflows: Flexibility for adaptive strategies but risks miscommunication; requires clear role boundaries.
  - Multi-agent collaboration vs. single-agent: Higher accuracy on complex tasks but increased token cost (~3,464-4,982 tokens) and coordination overhead.
  - Automated KG construction: Enables scalability but introduces transformation errors if rules are misconfigured.
  - Context engineering: Reduces hallucinations but depends on quality of retrieved historical examples and schema accuracy.
- **Failure signatures:**
  - Performance collapse when tool calls exceed 6 (RQ5), indicating over-collaboration.
  - MAST failure modes: Coordination problems (e.g., conflicting results), specification violations (e.g., ambiguous task delegation), inadequate verification (e.g., missing cross-source consistency checks).
  - Practical: LLM hallucinations in query generation, incorrect KG relationship extraction, Data Leader infinite loops without proper stopping criteria.
- **First 3 experiments:**
  1. Baseline validation: Replicate RQ1 by running DataFactory on TabFact and WikiTQ with GPT-4o mini, comparing against End-to-End, Few-Shot, and ReAcTable baselines to confirm +20% accuracy gains.
  2. Ablation study: Disable Knowledge Graph Team (SQL-only) and measure performance drop on WikiTQ and FeTaQA, expecting 14.4% and 17.1% decreases respectively, to quantify KG team necessity.
  3. Interaction frequency tuning: Enforce maximum tool call limits (1, 3, 5, unlimited) and plot accuracy vs. calls, identifying the 1-3 call optimum to prevent degradation from excessive coordination.

## Limitations
- External validity: Gains demonstrated on three benchmarks; generalizability to real-world or proprietary datasets remains uncertain.
- KG construction robustness: Automated transformation depends on LLM-generated patterns and rule-based extraction; errors in this pipeline can degrade QA accuracy.
- Coordination overhead & scaling: High token cost (~4k tokens/query) and multi-agent orchestration may limit scalability for large-scale deployments.

## Confidence
- Multi-Agent Coordination Efficacy: Medium-High
- Automated KG Transformation Utility: Medium
- Context Engineering for Hallucination Reduction: Medium

Manually validate a sample of extracted entities and relationships to estimate precision/recall of the T:D×S×R→G pipeline and correlate errors with final QA accuracy drops.

Systematically remove (a) historical QA examples, (b) schema information, and (c) domain rules to measure the isolated impact of each context component on hallucination rates (e.g., invalid SQL/Cypher syntax) and final answer accuracy.
