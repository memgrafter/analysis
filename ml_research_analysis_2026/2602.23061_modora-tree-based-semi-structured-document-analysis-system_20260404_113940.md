# MoDora: Tree-Based Semi-Structured Document Analysis System

## Quick Facts
- **arXiv ID**: 2602.23061
- **Source URL**: https://arxiv.org/abs/2602.23061
- **Reference count**: 36
- **Primary result**: MoDora outperforms state-of-the-art baselines by 5.97%–61.07% on four document QA benchmarks and achieves 73.33% AIC-Acc on the new MMDA suite for complex layouts.

## Executive Summary
MoDora is a system for question answering over semi-structured documents containing interleaved text, tables, charts, and supplements. Existing methods struggle with fragmented OCR outputs, lack hierarchical modeling, and cannot align scattered evidence. MoDora addresses these via three core innovations: (1) a local-alignment strategy that aggregates OCR elements into layout-aware components; (2) a Component-Correlation Tree (CCTree) that explicitly organizes components hierarchically with bottom-up summarization; and (3) a question-type-aware retrieval mechanism combining spatial grid mapping, LLM-guided semantic pruning, embedding fallback, and MLLM verification. Evaluated on DUDE, M3DocVQA, MP-DocVQA, and the new MMDA benchmark, MoDora achieves substantial gains across all question types and demonstrates robust handling of complex multi-modal layouts.

## Method Summary
MoDora processes documents in three stages. First, **preprocessing** applies a local-alignment aggregation to OCR-parsed elements (text, tables, charts, images, supplements) to form coherent components using heuristic rules based on reading order and element types. A vision-language model (Qwen2.5-VL) enriches non-text components with titles and semantic triples, and infers title levels for hierarchy detection. Second, **tree construction** builds a CCTree: a main body branch is created by linking components via title levels using a stack algorithm, while supplements form a separate branch; bottom-up summarization propagates metadata upward with an attenuation formula to control node size. Third, **analysis** parses the question type, then performs type-aware retrieval: location-based queries map spatial cues to a page grid; semantic queries use an iterative forward search where an LLM selects children from indices/metadata, with embedding search as fallback for unselected subtrees, followed by backward verification with an MLLM. Confirmed evidence nodes are aggregated and passed to an MLLM for final answer generation.

## Key Results
- MoDora achieves absolute accuracy gains of 5.97%–61.07% over eight baselines on DUDE, M3DocVQA, MP-DocVQA, and MMDA.
- It ranks highest across all four question types (text, hybrid, hierarchy, location) on the MMDA benchmark.
- On the new MMDA dataset, MoDora reaches 73.33% AIC-Acc, demonstrating strong capability on complex layouts and multi-modal elements.
- Ablation studies show each component (textual/locational evidence, forward search, tree structure) contributes significantly, with removals causing drops up to ~37%.

## Why This Works (Mechanism)

### 1. Local-alignment aggregation
- **Claim**: Transforms fragmented OCR outputs into coherent, layout-aware document components, preserving semantic context.
- **Mechanism**: Applies heuristic rules on reading-ordered element sequences: textual aggregation groups a title and following paragraphs until the next title; table/chart aggregation attaches a nearby title or assigns a default; supplement aggregation isolates headers/footers per page.
- **Core assumption**: Reading order and element type cues reliably indicate semantic grouping boundaries; title detection accuracy is sufficient.
- **Evidence anchors**: [abstract] describes the strategy; [section 4.1] details the three rules; indirect support from similar works like "LLM Based Multi-Agent Generation of Semi-structured Documents".
- **Break condition**: OCR misclassifies a hierarchical title as plain text, causing incorrect paragraph grouping; intervening supplements disrupt adjacency detection for tables/charts.

### 2. Component-Correlation Tree (CCTree)
- **Claim**: Explicitly models hierarchical structure and layout distinctions, enabling multi-level abstraction and efficient context propagation.
- **Mechanism**: Constructs a tree where nodes represent components; edges encode three relationships: title-based parent-child (text-to-text), adjacency-based (text-to-other), and independent supplements. Bottom-up summarization generates metadata for each node, with the number of keywords attenuated upward to control size.
- **Core assumption**: Title levels correctly infer nesting relationships; spatial adjacency implies semantic complementarity; summarization retains essential signals for retrieval.
- **Evidence anchors**: [abstract] introduces CCTree; [section 5] formalizes node/edge types and provides algorithms (Algorithms 1–3) and summarization formula; tangential support from "ReTreever: Tree-based Coarse-to-Fine Representations for Retrieval".
- **Break condition**: LLM-determined title levels are wrong, leading to mis-parented nodes; summarization attenuates critical details, causing loss of fine-grained evidence.

### 3. Question-type-aware retrieval
- **Claim**: Balances recall and precision by combining location-based grid partitioning, LLM-guided node selection, embedding fallback, and MLLM verification.
- **Mechanism**: For location questions, map spatial cues to page grids and select overlapping nodes. For semantic questions, iteratively forward-search: LLM selects child nodes using index/metadata, then embedding search on unselected subtrees; backward verification evaluates node content+location with an MLLM to confirm evidence.
- **Core assumption**: LLM can effectively prune using sparse node index/metadata; embedding search recovers missed evidence; MLLM verifier accurately distinguishes relevance.
- **Evidence anchors**: [abstract] mentions the dual-path strategy; [section 6] details forward search, embedding fallback, backward verification, and evidence aggregation; moderate corroboration from "Zero-Shot Document Understanding using Pseudo Table of Contents-Guided Retrieval-Augmented Generation".
- **Break condition**: LLM selection over-relies on metadata, pruning relevant subtrees; embedding fallback retrieves off-topic chunks; MLLM verifier discards necessary nodes or accepts irrelevant ones.

## Foundational Learning
- **Concept**: Semi-structured document elements and components  
  **Why needed**: MoDora’s input comprises interleaved text, tables, charts, images, and supplements. Understanding these categories and the aggregation into components is fundamental to the system’s representation.  
  **Quick check**: List the five element types MoDora defines. Which component type aggregates a title with multiple paragraphs?  
  *(Answer: Textual aggregation produces a title+paragraphs component.)*
- **Concept**: Hierarchical structure and title levels  
  **Why needed**: CCTree construction depends on correctly inferring title levels to establish parent-child relationships. Mis-leveling breaks the tree.  
  **Quick check**: If a sequence of titles has levels [1, 2, 2, 3], describe the parent-child links after processing the fourth title using the stack-based algorithm.  
  *(Answer: The title level 3 becomes a child of the most recent level 2; previous level 2 may have multiple children.)*
- **Concept**: Semantic vs. location-based retrieval  
  **Why needed**: MoDora adapts its retrieval strategy to question type; distinguishing these modes explains the dual-path design.  
  **Quick check**: For the question "What tables appear on the right half of page 5?", which retrieval path is used and what spatial mapping is applied?  
  *(Answer: Location-based; query mapped to right-column grids of page 5.)*

## Architecture Onboarding
- **Component map**:  
  OCR → Local Alignment → Components → CCTree (main body branch + supplement branch, bottom-up summarization) → Question Parsing → Type-aware Retrieval (location: grid mapping; semantics: forward LLM selection → embedding fallback → backward MLLM verification) → Evidence Aggregation → MLLM Answer Generation
- **Critical path**: OCR elements → component list → CCTree (with summarized metadata) → retrieval iteration (candidate list → forward search/fallback → backward verification) → selected evidence → final answer.
- **Design tradeoffs**:  
  - OCR generality vs. noise: OCR handles scanned docs but introduces misclassifications affecting component grouping and hierarchy.  
  - LLM cost vs. accuracy: Using GPT-5 improves performance but increases API cost; Qwen2.5-VL reduces cost but may reduce accuracy.  
  - Tree robustness: Heuristic construction is lightweight but brittle on unusual layouts; more robust ML models would add complexity and training needs.
- **Failure signatures**:  
  - Component construction fails: Adjacent paragraphs not merged if missing title; tables detached from titles.  
  - CCTree misstructure: Wrong title levels cause misparenting; supplement components incorrectly linked to main body.  
  - Retrieval errors: LLM selector discards relevant subtrees; embedding fallback retrieves irrelevant chunks; MLLM verifier allows false positives or blocks true evidence.
- **First 3 experiments**:  
  1. **Performance comparison** (Section 8.2, Figure 8): MoDora significantly outperforms eight baselines across four benchmarks and four question types.  
  2. **Ablation study** (Section 8.5, Table 6): Removing textual evidence, locational evidence, forward search, or tree structure each causes large drops (up to ~37%).  
  3. **Case study** (Section 8.6, Figure 9): MoDora retrieves correct evidence nodes for hybrid queries while baselines like GPT-5, TextRAG, and ZenDB fail due to missing hierarchy or non-text handling.

## Open Questions the Paper Calls Out
1. How to integrate native PDF structure and typographic cues, lost in OCR, to enhance MoDora's component detection and information extraction?
2. How can CCTree be extended to a cross-document forest to enable multi-document QA?
3. What dynamic retrieval strategies (e.g., backtracking, query-driven skipping) can improve MoDora's handling of complex queries?

## Limitations
- Critical implementation details (exact LLM/MLLM prompts, key hyperparameters like attenuation coefficient, embedding model, top-k) are undisclosed, hindering exact replication.
- Robustness of heuristic components (local alignment, title-level inference) under real-world OCR noise remains unevaluated.
- Reliance on closed-source models (GPT-5, Qwen2.5-VL) raises reproducibility and cost concerns.

## Confidence
- **Overall effectiveness**: High – large gains across four benchmarks and strong ablations.
- **Local-alignment aggregation**: Medium – heuristic rules are intuitive but may fail with OCR errors or missed titles.
- **CCTree construction**: Medium – tree benefits shown by ablation, but correctness of LLM-inferred title levels is not verified.
- **Retrieval strategy**: Medium – subcomponents contribute positively per ablation; however, lack of prompt details hinders verification of LLM/MLLM selection accuracy.

## Next Checks
1. Manually assess component grouping accuracy on a diverse document set, correlating with OCR quality and title detection correctness.
2. Replace the CCTree with a flat component list and measure performance drop on hierarchical questions to isolate the tree’s contribution.
3. Systematically disable each retrieval submechanism (LLM selection, embedding fallback, MLLM verification) and report type-specific recall/precision to validate design.
