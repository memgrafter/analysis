# Bypassing Document Ingestion: An MCP Approach to Financial Q&A

## Quick Facts
- **arXiv ID:** 2603.20316
- **Source URL:** https://arxiv.org/abs/2603.20316
- **Reference count:** 40
- **Primary result:** An MCP-based system querying LSEG APIs directly achieves 69.7% answer accuracy on quantitative financial questions, with 90.4% response groundedness, bypassing traditional document ingestion pipelines.

## Executive Summary
This paper evaluates whether the Model Context Protocol (MCP) can serve as a lightweight alternative to retrieval-augmented generation (RAG) for financial question answering. Instead of ingesting and chunking documents, the authors implement an MCP server that exposes curated vendor data (LSEG Workspace APIs) as tools for an LLM agent to query directly. Tested on the FinDER benchmark, the system excels on quantitative, numerically-dense questions derived from financial statements, achieving up to 80.4% accuracy on multi-step reasoning tasks and high groundedness scores. However, it fails on qualitative or document-specific queries that require textual analysis. The work demonstrates that for data-rich domains with reliable APIs, direct tool invocation via MCP can avoid the complexity and errors of document parsing while maintaining high accuracy on structured reasoning tasks.

## Method Summary
The study involves no model training. It constructs a custom MCP server that wraps 11 LSEG API endpoints (e.g., `get_income_statement`, `get_operating_metrics`) as tools. An LLM (GPT-4o mini) acts as an agent, selecting and invoking these tools to retrieve structured JSON data in response to user questions from the FinDER benchmark. The system's performance is evaluated using RAGAS metrics—Answer Accuracy, Context Relevance, and Response Groundedness—computed via an LLM-as-a-judge paradigm. The "Financials" subset of FinDER (990 questions) is the primary focus, with analysis stratified by reasoning type (e.g., numerical, compositional) and question characteristics (numeric density, forward-looking language).

## Key Results
- Achieves 69.7% Answer Accuracy on the quantitative *Financials* subset of FinDER.
- Reaches 80.4% accuracy on high-context-relevance multi-step numerical ("Compositional") questions.
- Records 90.4% Response Groundedness and 72.5% Context Relevance for the *Financials* category, far exceeding other categories.
- System fails on qualitative or document-intensive tasks not covered by vendor APIs, exposing a key limitation.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** MCP bypasses the error-prone document ingestion and chunk retrieval steps of traditional RAG by allowing the LLM to query structured, curated vendor APIs directly.
- **Mechanism:** Instead of parsing document pages into chunks and retrieving them via vector similarity, an MCP server exposes specific API endpoints (e.g., `get_income_statement`) as tools. The LLM agent selects and invokes these tools with parameters (company, period), receives structured JSON responses, and uses that data as context for generation. This eliminates OCR, table parsing, and chunk embedding errors.
- **Core assumption:** Curated vendor data (LSEG) is already normalized, accurate, and accessible via stable APIs, making direct querying more reliable than reconstructing it from raw filings.
- **Evidence anchors:** The abstract states the goal is "bypassing document ingestion... by allowing large language models (LLMs) to interact directly with data." Section 3.1 explains the server "exposes LSEG APIs as tools... entirely removes the necessity to set up an infrastructure that ingests and processes documents."
- **Break condition:** If the required data point is not available in the vendor's schema or an API requires parameters the LLM cannot infer, the tool fails and the system reverts to parametric knowledge or fails.

### Mechanism 2
- **Claim:** The approach excels on quantitative financial questions because those answers are predominantly derived from structured financial statements (tables), which vendor APIs natively return in machine-readable form.
- **Mechanism:** Questions in the *Financials* subset have high "numeric density" and low forward-looking language, indicating they require extracting figures from balance sheets, income statements, etc. MCP tools directly return these tables, enabling precise numerical extraction without parsing errors.
- **Core assumption:** Financial statement data is universally available and standardized across vendors like LSEG, and the benchmark questions map to these standard data fields.
- **Evidence anchors:** Section 3.2 notes the *Financials* pool has the highest numeric occurrences and lacks forward-looking terms. Figures 2 & 3 visualize this distribution. The corpus (e.g., *TAT-QA*, *FinQA*) also focuses on tabular reasoning, supporting the importance of such questions.
- **Break condition:** Questions requiring aggregation across non-standard segments, qualitative interpretation of numbers, or data beyond the vendor's coverage will perform poorly.

### Mechanism 3
- **Claim:** Performance is gated by the LLM's ability to select the correct tool and parameters, and by the vendor API's coverage of the specific data point asked.
- **Mechanism:** Accuracy depends on the agent retrieving the right table via the right tool call. If tool selection is wrong (e.g., calls `get_business_segments` for a profitability ratio needing `get_income_statement`), context is irrelevant and accuracy drops.
- **Core assumption:** The LLM can correctly interpret the question's intent and map it to the appropriate financial data domain (income statement vs. segments) and period.
- **Evidence anchors:** Section 4 links high Response Groundedness to effective tool use and low scores to poor context. Figure 5 shows metric drops for low-quality context. The "Compositional" task group, which benefits from sequential tool calls, peaks at 80.4% accuracy.
- **Break condition:** Ambiguous temporal references (e.g., "last quarter"), questions spanning multiple companies/years requiring complex joins, or malformed LLM tool arguments lead to low-quality context.

## Architecture Onboarding
- **Component map:** User Interface (Plotly Dash) -> Agent Orchestrator (LLM with MCP client) -> MCP Server (custom server exposing LSEG APIs) -> Data Vendor (LSEG Workspace APIs) -> Evaluation Module (RAGAS metrics via LLM-as-a-Judge)
- **Critical path:** User prompt arrives -> Agent selects and executes MCP tool calls -> MCP server calls LSEG API and returns JSON -> Agent formulates answer -> Evaluation module computes metrics against FinDER ground truth.
- **Design tradeoffs:**
  - Vendor dependency vs. maintenance: Leveraging LSEG APIs offloads data quality/scalability but creates lock-in and requires license management.
  - Tool granularity: Fine-grained tools (one per statement) vs. composite tools (e.g., `calculate_ratio`). Paper uses fine-grained; composite could reduce LLM planning steps but increase tool design complexity.
  - Evaluation cost: Using LLM-as-a-Judge for three metrics per answer is computationally expensive vs. exact string match.
- **Failure signatures:**
  - Low Context Relevance (<0.5) indicates wrong tool/parameters selected.
  - Low Response Groundedness with high Context Relevance indicates LLM ignored retrieved data (parametric guess).
  - 0 Answer Accuracy on Financials when question requires data beyond vendor's 5-period lookback or non-standard segment.
- **First 3 experiments:**
  1. Baseline replication: Run the published MCP server on the Financials subset. Expect ~70% Answer Accuracy and >90% Response Groundedness.
  2. Ablation - tool access: Disable all tools, rerun. Expect near 0% accuracy on Financials, confirming reliance on contextual data.
  3. Context quality conditioning: Compute metrics only for questions where Context Relevance ≥0.75. Expect Answer Accuracy to rise to ~80% for Compositional tasks, verifying retrieval quality gates performance.

## Open Questions the Paper Calls Out
- **Question 1:** How do variations in evaluation prompt phrasing and LLM judge selection systematically affect the reported performance metrics (Answer Accuracy, Context Relevance, Response Groundedness) in MCP-based financial QA?
  - *Basis:* The authors identify the choice and tweaking of evaluation prompts as a "relevant constraint" and call for research to "conclude what methods work best" for specific dataset types (Section 5).
  - *Why unresolved:* The study relies on a fixed set of RAGAS prompts and a single evaluator model (GPT-4o mini) without robustness checks.
  - *Resolving evidence:* Systematic experiments varying prompt wording, judge model families, and aggregation strategies to quantify impact on metric stability and correlation with human judgment.
- **Question 2:** To what extent do the choices of generator and evaluator LLMs, as well as core inference parameters (temperature, max tokens), impact the overall effectiveness, hallucination rates, and efficiency of MCP-based financial QA systems?
  - *Basis:* Authors list "Assessing robustness of the system to the choice of the generator and evaluator models" and "a robustness analysis on the impact... of model parameters" as future work (Section 5).
  - *Why unresolved:* Baseline uses a single model (GPT-4o mini) and fixed parameters; no comparative analysis or parameter sweep is performed.
  - *Resolving evidence:* Multi-model benchmarking across diverse LLM families with controlled parameter variations, measuring accuracy, context relevance, response groundedness, latency, and token consumption.
- **Question 3:** How can we design and validate benchmark datasets that specifically test MCP-based tool selection and execution capabilities, rather than document-based retrieval, for financial QA?
  - *Basis:* Authors highlight the "lack of suitable datasets for further work" and need for "human-curated benchmarks specifically designed for MCP-based solutions," noting FinDER is shaped for document retrieval (Section 5).
  - *Why unresolved:* FinDER's questions are tailored to document chunk contexts; its use may advantage MCP by coincidence rather than testing true tool orchestration skills.
  - *Resolving evidence:* Develop new benchmarks where correct answers require dynamic, multi-step API calls (e.g., chaining tools for ratio computation), and validate by contrasting MCP vs. RAG performance.
- **Question 4:** What optimal tool orchestration strategies (sequential, parallel, chained with intermediate computation) maximize retrieval accuracy and minimize latency for complex, multi-step quantitative financial queries using MCP?
  - *Basis:* Authors propose "creating a set of tools that reliably compute more complex financial ratios and that are chained to tools retrieving the necessary data points" as a development direction (Section 5).
  - *Why unresolved:* Current MCP server exposes single-data-point tools without higher-level composites; LLM must manually orchestrate multi-tool calls, which may be suboptimal.
  - *Resolving evidence:* Implement and compare orchestration patterns (single-tool, parallel calls, chained with a ratio calculator) on FinDER's Compositional tasks, measuring context relevance, answer accuracy, and tool calls.
- **Question 5:** How resilient is the MCP approach to changes or inconsistencies in underlying curated data provider APIs (e.g., LSEG) in terms of long-term answer accuracy, system maintenance overhead, and portability across vendors?
  - *Basis:* Authors suggest "testing how the system performs as data providers within and outside the commercial landscape change" as a robustness test (Section 5).
  - *Why unresolved:* Evaluation uses a single provider (LSEG) with a stable API; sensitivity to schema changes, deprecated endpoints, or different vendors' coverage is unknown.
  - *Resolving evidence:* Longitudinal study tracking accuracy over API version updates; cross-provider portability tests using alternative financial data APIs (e.g., Bloomberg, Refinitiv).

## Limitations
- **Implementation opacity:** Tool logic (error handling, parameter mapping) and LSEG schema coverage are undocumented, hindering exact replication and generalizability assessments.
- **Benchmark bias:** FinDER’s heavy quantitative skew means claims do not extend to qualitative/document-heavy tasks; performance on such tasks is explicitly poor.
- **Evaluation sensitivity:** Answer Accuracy relies on an unverified LLM-as-judge prompt; minor formatting/rounding variations may cause false negatives.
- **Vendor lock-in:** Success assumes access to curated, normalized vendor APIs (LSEG), introducing cost/license barriers and potential schema drift.

## Confidence
- **MCP bypasses ingestion errors:** High confidence. Architecture clearly replaces document parsing/retrieval with direct API calls; evidence is structural.
- **Excels on quantitative questions:** High confidence. Strong metrics (Financials accuracy 69.7%, Groundedness 90.4%) align with numeric-density analysis and tool design for structured statements.
- **Gated by tool selection/coverage:** Medium confidence. Correlations between Context Relevance and Accuracy support this, but LLM planning ability and edge-case coverage are not stress-tested.
