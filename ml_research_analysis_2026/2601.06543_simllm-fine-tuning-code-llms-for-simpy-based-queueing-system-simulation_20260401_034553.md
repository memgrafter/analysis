# SimLLM: Fine-Tuning Code LLMs for SimPy-Based Queueing System Simulation

## Quick Facts
- **arXiv ID:** 2601.06543  
- **Source URL:** https://arxiv.org/abs/2601.06543  
- **Reference count:** 4  
- **Primary result:** Multi-stage fine-tuning transforms Qwen2.5-Coder-7B and DeepSeek-Coder-6.7B into reliable SimPy code generators, achieving up to 76.8% instruction-code consistency and 86.0% executability on a 600-task benchmark.

## Executive Summary
Closed-source large language models (LLMs) like GPT-4o are effective for generating SimPy queueing simulation code but incur high costs and raise privacy concerns. This paper introduces SimLLM, a framework that fine‑tunes open‑source code LLMs (Qwen2.5‑Coder‑7B and DeepSeek‑Coder‑6.7B) for reliable SimPy code generation. The approach uses a curated dataset built via a Category‑Template Framework covering 12 queueing categories, followed by a multi‑stage training pipeline: supervised fine‑tuning (SFT) on diverse instruction‑code pairs, masked‑completion SFT to strengthen understanding of code structure, and Direct Preference Optimization (DPO) for alignment using error‑derived preference pairs. On a comprehensive 600‑task benchmark, both models show substantial improvements: Qwen’s instruction‑code consistency rises from 0% to 76.8% and executability from 80.4% to 86.0%; DeepSeek’s consistency jumps from 0% to 62.3% and executability from 26.2% to 75.0%. The results demonstrate that domain‑specific fine‑tuning can turn compact open‑source models into dependable SimPy code generators.

## Method Summary
The framework builds a multi‑stage dataset and training procedure.

**Stage I – Supervised Fine‑Tuning (SFT):** A Category‑Template Framework (CTF) generates 7,200 instruction‑code pairs. CTF defines 12 queueing categories (e.g., single‑server, networks) and for each creates at least three instruction templates and three code templates (procedural, object‑oriented, functional). Parameters are sampled within stable ranges (e.g., service rates) and instantiated into the templates; executability and output format are automatically verified.

**Stage II – Masked‑Completion SFT:** For each code template, functional segments (e.g., arrival logic, service handling) are masked. Using the Stage I dataset, 20,000 masked‑completion samples are created by masking one segment per sample and mixing them with the original data. Training continues from the Stage I checkpoint for two epochs with a lower learning rate, forcing the model to infer missing code and deepen its grasp of SimPy’s process‑interaction semantics.

**Stage III – Direct Preference Optimization (DPO):** A held‑out query set (50 tasks per category) is used to generate outputs from the Stage II model. Each output is evaluated for executability, format compliance, and instruction‑code consistency (the latter via a DeepSeek‑based evaluator). Failed samples become “rejected” responses; for each, corrected code is obtained from GPT‑4o and manually validated to serve as “chosen” responses. DPO trains the model to favor high‑quality outputs, using the Stage II checkpoint as initialization and a β parameter of 0.2.

**Evaluation:** The final model is tested on a 600‑task benchmark (same categories) and assessed on three metrics: executability (runs without error), format compliance (exact output match), and instruction‑code consistency (binary label from the DeepSeek evaluator).

## Key Results
- Qwen2.5‑Coder‑7B: instruction‑code consistency 76.8% (from 0%), executability 86.0% (from 80.4%).
- DeepSeek‑Coder‑6.7B: consistency 62.3% (from 0%), executability 75.0% (from 26.2%).
- Both models dramatically surpass zero‑shot baselines and the paper’s reported results show that even the smaller 7B parameter model becomes a reliable SimPy code generator after domain‑specific fine‑tuning.

## Why This Works (Mechanism)
The multi‑stage pipeline progressively hones the model’s capabilities. The CTF dataset provides broad coverage of queueing scenarios, establishing a solid pattern foundation. Masked‑completion fine‑tuning compels the model to reconstruct missing functional segments, which deepens its understanding of SimPy’s process‑interaction mechanics (e.g., environment coordination, resource management). DPO then directly optimizes for the target metrics by leveraging preference pairs derived from real execution failures corrected by a stronger teacher model. This curriculum shifts learning from surface‑level imitation (SFT) to structural comprehension (masked) to metric‑driven alignment (DPO), addressing both syntax and semantic correctness while mitigating instruction‑code mismatch and logical errors.

## Foundational Learning
### SimPy Process‑Interaction Paradigm
- **Why needed:** SimPy uses cooperative multitasking via processes (`env.process`) to model concurrent entities; understanding this paradigm is essential for generating correct simulation logic.
- **Quick check:** Can the model generate a valid `with resource.request()` block that yields control and resumes after release?

### Queueing Network Categories
- **Why needed:** Queueing systems vary widely (single‑server, networks, breakdowns); each category imposes distinct modeling constraints.
- **Quick check:** Does the dataset include at least 12 categories with distinct Kendall‑Lee notation?

### Category‑Template Framework (CTF)
- **Why needed:** CTF systematically produces diverse, executable training instances by combining instruction and code templates with parameter instantiations.
- **Quick check:** Are there ≥3 instruction templates and ≥3 code templates per category? Does auto‑checking filter non‑executable code?

### Masked Language Modeling for Code
- **Why needed:** Masking functional segments forces the model to learn dependencies and fill in missing logic, reinforcing its grasp of code structure.
- **Quick check:** After Stage II, does the model correctly complete masked segments that implement specific behaviors (e.g., routing, interruption)?

### Direct Preference Optimization (DPO)
- **Why needed:** DPO aligns model outputs with desired outcomes (executability, format, consistency) without requiring reinforcement learning.
- **Quick check:** Are preference pairs constructed from errors corrected by a trusted source (GPT‑4o) and manual validation?

### LLM‑Based Code Evaluation
- **Why needed:** Automatic assessment of instruction‑code consistency at scale replaces human annotation; a strong evaluator (DeepSeek) provides binary labels.
- **Quick check:** Does the evaluator produce the same label as a human expert on a random sample of 50 cases?

## Architecture Onboarding
**Component Map:**  
CTF Data Generation → Stage I SFT → Stage II Masked Completion SFT → Stage III DPO → Evaluation

**Critical Path:**  
The pipeline is strictly sequential: Stage I must finish before Stage II, which must finish before DPO; DPO depends on preference pairs built from Stage II outputs. Evaluation requires the final model.

**Design Tradeoffs:**  
- *Coverage vs. depth:* CTF ensures broad scenario variety but may lead to shallow pattern learning; masked completion adds depth but can initially degrade generation metrics (observed in DeepSeek).  
- *Automation vs. quality:* Fully automated data generation scales easily but requires careful parameter bounds to guarantee executability; DPO needs costly manual validation of corrected code.  
- *Model sensitivity:* Different base models react differently to the masked objective; DeepSeek’s performance dropped during Stage II, indicating an objective mismatch that may require adaptive mixing ratios or learning rates.

**Failure Signatures:**  
- Incorrect network routing (customers created instead of transferred between nodes).  
- Broken remaining service time after server breakdown (elapsed time not subtracted).  
- Output format deviations (missing lines, wrong decimal precision).  
- Executability failures (syntax errors, undefined variables, missing imports).

**First Experiments:**  
1. **Reproduce Stage I SFT** on a single category (e.g., `single_server`) with a small subset of CTF data to verify the data pipeline and obtain a baseline improvement.  
2. **Test masked‑completion impact** on 500 samples: train a model with masking for one epoch and evaluate its ability to correctly complete masked functional segments using unit tests.  
3. **Run a tiny DPO**: construct 10–20 preference pairs from Stage II errors, train for one epoch, and measure change in instruction‑code consistency on a held‑out set.

## Open Questions the Paper Calls Out
#### Open Question 1
**Question:** How can the multi‑stage fine‑tuning framework be modified to eliminate the persistent error patterns in network routing semantics and interrupt‑driven service logic, as identified in the error analysis?  
**Basis in paper:** [explicit] The error analysis section explicitly identifies two recurrent failure modes: (1) incorrect custom movement of customers across nodes in open networks, and (2) flawed handling of remaining service time after server breakdowns. The authors state these reveal "weaknesses in several queueing‑system simulation tasks" and suggest routing semantics and interruption‑resumption mechanics remain challenging.  
**Why unresolved:** The current training pipeline, including DPO alignment, does not fully resolve these logical errors, indicating gaps in the model’s conceptual understanding of state‑dependent updates and multi‑node coordination. The paper does not investigate targeted data augmentation or architectural changes to address these specific failure modes.  
**What evidence would resolve it:** A controlled experiment introducing specialized datasets or auxiliary losses focused on these mechanisms, followed by re‑evaluation on held‑out tests for `breakdown_maintenance` and `open_network` categories, would show whether performance can be improved without trade‑offs in other metrics.

#### Open Question 2
**Question:** Why do different base models (Qwen2.5‑Coder‑7B vs. DeepSeek‑Coder‑6.7B) exhibit such disparate sensitivity to the masked‑completion training stage, with DeepSeek showing a sharp drop in executability and format compliance that later recovers?  
**Basis in paper:** [explicit] The ablation study explicitly shows DeepSeek‑Coder‑6.7B’s executability and format compliance decrease during Stage II (from 74.7% to 67.2% and 74.2% to 66.8%, respectively), while Qwen’s metrics steadily improve. The authors note this is due to an "objective mismatch" where masked‑completion optimization may shift focus away from generation‑oriented metrics, and DeepSeek appears "more sensitive to this objective mismatch."  
**Why unresolved:** The paper does not analyze the underlying reasons for this sensitivity—whether it stems from differences in pre‑training data, model architecture, or initial code‑generation proficiency. Without this analysis, it is unclear how to adapt the framework for broader model compatibility.  
**What evidence would resolve it:** Comparative probing of the models’ internal representations during Stage II training (e.g., analyzing attention patterns on functional code segments) or a study correlating pre‑training code corpus diversity with Stage II stability could identify the source of sensitivity and inform adaptive training strategies.

#### Open Question 3
**Question:** To what extent does the proposed Category‑Template Framework (CTF) and multi‑stage fine‑tuning pipeline generalize to other discrete‑event simulation paradigms beyond SimPy (e.g., event‑scheduling libraries like SimJulia or process‑interaction frameworks in other languages)?  
**Basis in paper:** [inferred] The paper focuses exclusively on SimPy in Python, motivated by its popularity and alignment with process‑interaction paradigms. However, the introduction notes that other simulation platforms exist (Arena, AnyLogic), and the literature review mentions general DES methodologies. The framework’s reliance on SimPy‑specific primitives (e.g., `Environment`, `Resource`, `request`) suggests limited direct transferability.  
**Why unresolved:** The authors do not evaluate cross‑paradigm generalization. The CTF’s code templates and evaluation metrics are tightly coupled with SimPy’s API and output format. Questions remain about whether the learned queueing logic transfers to different simulation abstractions or if the framework must be redesigned for other tools.  
**What evidence would resolve it:** Applying the same fine‑tuning pipeline to a comparable dataset constructed for another DES library (e.g., SimJulia in Julia) and measuring performance on equivalent queueing tasks would test generalizability. Success would require adapting templates and validators but preserving the multi‑stage training logic.

#### Open Question 4
**Question:** How does the performance of fine‑tuned models scale with increased dataset size and diversity in the CTF framework, particularly for complex networked categories that showed limited gains (e.g., `breakdown_maintenance`, `open_network`)?  
**Basis in paper:** [explicit] The paper constructs 7,200 Stage I samples (600 per category‑template combination) and notes that even after fine‑tuning, some complex categories see only modest improvements (e.g., `breakdown_maintenance` consistency from 0% to ~32–82% depending on model). The authors speculate that "further targeted data would be needed" for these cases.  
**Why unresolved:** The current experiments fix the dataset size and template variety. It is unknown whether scaling up the number of parameter instantiations, adding more instruction templates, or introducing more complex multi‑mechanism combinations would yield diminishing returns or breakthrough improvements in the hardest categories.  
**What evidence would resolve it:** An ablation study varying dataset size (e.g., 1×, 5×, 10× the current CTF samples) and template diversity, with performance tracked per category, would reveal scaling laws and saturation points, especially for the complex group. This would guide future data collection efforts.

## Limitations
- **Reproduction gaps:** Exact parameter ranges, full instruction/code templates, and the masking strategy are not fully specified, making faithful recreation difficult.
- **Evaluation uncertainty:** The DeepSeek‑based consistency evaluator’s version and any post‑processing are unknown; human validation of DPO preference pairs is not thoroughly described.
- **Residual logical errors:** Even after DPO, common failure modes (e.g., incorrect routing, broken interrupt handling) persist, suggesting executability alone does not guarantee semantic correctness.

## Confidence
- **Multi‑stage fine‑tuning improves SimPy code generation:** Medium  
- **Benchmark comprehensiveness (600 tasks across 12 categories):** Medium  
- **Metrics (executability, consistency) truly reflect usable SimPy code:** Low
