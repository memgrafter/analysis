# RealMem: Benchmarking LLMs in Real-World Memory-Driven Interaction

## Quick Facts
- arXiv ID: 2601.06966  
- Source URL: https://arxiv.org/abs/2601.06966  
- Reference count: 14  
- Primary result: Current memory systems score poorly on dynamic queries (<0.6) while Oracle yields ~0.99, revealing a critical deficiency in maintaining project coherence.

## Executive Summary
RealMem addresses the lack of benchmarks for long-term, project-oriented LLM agent interactions. It introduces a benchmark of over 2,000 cross-session dialogues across eleven realistic scenarios, generated via a three-stage synthesis pipeline. Evaluation on four query types reveals that state-of-the-art memory systems (MemoryOS, Graph Memory, Mem0, A-mem) perform substantially below an Oracle upper bound, with particularly low scores in technical domains like Code Architecture. These results highlight a major gap in agents’ ability to maintain evolving project states over fragmented sessions.

## Method Summary
RealMem constructs its dataset in three stages: (1) Project Foundation Construction creates hierarchical project skeletons including goals, participants, and schedules; (2) Multi-Agent Dialogue Generation simulates conversations among agents that evolve the project across multiple sessions; (3) Memory and Schedule Management annotates dialogue turns with memory points and updates a dynamic schedule. The benchmark comprises dialogues and associated memory annotations. Evaluation compares memory systems on four query types (Static Retrieval, Dynamic Updating, Proactive Alignment, Temporal Reasoning) using metrics such as QA Score, Mem Recall, and NDCG@k. Experiments use GPT-4o‑mini/GPT‑4o as both backbone and judge, under two context settings: memory‑only (Top‑20 retrieved) and session‑based (Top‑5 sessions).

## Key Results
- Proactive Alignment QA ~0.571; Temporal Reasoning Recall ~0.559.  
- Oracle Recall ~0.993.  
- Code Architecture QA scores below 0.4 for all memory systems.

## Why This Works (Mechanism)
RealMem effectively stress-tests memory systems by mimicking the complexity of real-world projects. The three-stage synthesis pipeline produces dialogues with fragmented sessions, evolving goals, and dynamic schedules, forcing memory to track changes and infer implicit intents. The four query types probe distinct memory capabilities: factual recall (Static), handling updates (Dynamic), anticipating needs (Proactive Alignment), and ordering events (Temporal). By providing an Oracle with perfect context, the benchmark quantifies the gap between current retrieval-based approaches and ideal performance. The design reveals that existing systems, which rely on fuzzy vector/graph retrieval, struggle with precise constraints and proactive reasoning, especially in technical domains.

## Foundational Learning
- **Cross‑Session Dialogue**: Interactions split across multiple sessions requiring continuity. *Needed* to simulate projects where users return to ongoing work. *Quick check*: Dialogues have timestamps and recurring topics across sessions.  
- **Dynamic Memory Updates**: Memory must be revised as project state changes (e.g., task completion). *Needed* to evaluate systems’ ability to maintain consistent, up‑to‑date knowledge. *Quick check*: Memory entries include timestamps and version indicators.  
- **Four Query Types**: Static, Dynamic, Proactive, Temporal. *Needed* to isolate specific memory skills. *Quick check*: Queries are classified and metrics vary across types in results.  
- **Oracle Upper Bound**: Perfect memory system that sees all past context. *Needed* to gauge how far current systems are from ideal. *Quick check*: Oracle achieves scores >0.99 on most metrics.  
- **Project Scenario Synthesis**: Synthetic generation of realistic project skeletons (goals, schedules, participants) that drive dialogues. *Needed* to create diverse, controlled test cases. *Quick check*: Inspect a scenario for hierarchical tasks and participant roles.

## Architecture Onboarding
Component map:  
Project Foundation Builder -> Multi‑Agent Dialogue Generator -> Memory & Schedule Annotator -> Query Processor -> Evaluation Runner -> Metrics  

Critical path: The pipeline starts with a project configuration, generates dialogues and associated memory updates, creates test queries, then the evaluation runner interacts with the memory system to retrieve relevant memories and produce answers. The judge LLM scores answers, and metrics are aggregated.

Design tradeoffs: Using synthetic data offers scalability and control but may not capture all nuances of real human interactions. Relying on GPT judges enables flexible scoring but introduces variability and cost. The benchmark covers 11 scenarios, balancing diversity and evaluation time. The two context settings (memory‑only vs. session‑based) allow assessment of retrieval vs. raw context recall but require careful equivalence in comparison.

Failure signatures: A memory system exhibits (1) low QA scores (<0.4) on Proactive Alignment and Temporal queries, indicating poor inference and ordering; (2) high variance across runs, suggesting instability in retrieval; (3) inability to improve with more memory (saturation), implying fundamental architectural limits; (4) frequent retrieval of outdated information when updates occur.

First experiments:
1. **Schema Validation**: Load a sample dialogue, memory, and schedule to confirm JSON structures match expected schemas.  
2. **Baseline Smoke Test**: Run Mem0 on the Travel Planning scenario with 5 dialogues to ensure the end‑to‑end pipeline executes and yields non‑zero metrics.  
3. **Oracle Consistency Check**: Execute the Oracle on the same subset; verify QA scores exceed 0.95 and Recall exceeds 0.98, confirming judge reliability and metric computation.

## Open Questions the Paper Calls Out
#### Open Question 1
- **Question**: How can memory benchmarks be extended to evaluate tool‑use capabilities in long‑term project‑oriented interactions?  
- **Basis in paper**: [explicit] The authors state: “RealMem currently focuses specifically on memory‑centric challenges… does not yet involve the assessment of tool use capabilities, which we plan to incorporate in future work.”  
- **Why unresolved**: Real‑world agents frequently use external tools (e.g., booking systems, code execution), and memory must seamlessly integrate with tool outputs and states. Excluding tool use limits the benchmark’s ability to assess holistic agent performance in realistic scenarios.  
- **What evidence would resolve it**: An extended benchmark version where queries require invoking tools (e.g., “book a flight based on itinerary”), with metrics measuring correct tool selection, parameter extraction from memory, and handling tool feedback.

#### Open Question 2
- **Question**: Why do existing memory systems struggle with technical domains like Code Architecture, and what architectural modifications are needed to handle hard constraints?  
- **Basis in paper**: [inferred] Performance tables (Table 4, Figure 4) show Code Architecture has the lowest QA scores across all systems (e.g., MemoryOS QA 0.363), indicating a consistent, severe deficiency in domains requiring strict logical consistency.  
- **Why unresolved**: Technical tasks involve precise dependencies and non‑negotiable constraints (e.g., API compatibility), which may not be well‑represented by current retrieval mechanisms (vector/graph) that favor fuzzy matching. This gap suggests memory systems lack mechanisms for constraint satisfaction and version control.  
- **What evidence would resolve it**: Ablation studies isolating constraint types, or development of hybrid memory architectures that combine symbolic constraint solvers with neural retrieval, evaluated on code‑specific consistency metrics.

#### Open Question 3
- **Question**: How can agents improve Proactive Alignment to better infer and act on implicit user intents from long‑term memory?  
- **Basis in paper**: [inferred] MemoryOS achieves a QA score of 0.571 on Proactive Alignment queries, well below the Oracle (0.993), revealing difficulty in leveraging memory to anticipate goals without explicit user direction.  
- **Why unresolved**: Proactive Alignment requires identifying latent priorities from fragmented history and projecting next steps, which may exceed current retrieval’s ability to surface relevant but non‑obvious memories. This limits agents in open‑ended, collaborative projects.  
- **What evidence would resolve it**: Introduce memory indexing that weights historical priority signals (e.g., repeated mentions, emotional valence) or train models on synthetic dialogues with ambiguous queries, measuring success in predicting user‑approved next actions.

## Limitations
- Synthesis pipeline details are underspecified (Gemini 2.5 prompts/checkpoints, deduplication), hindering full dataset reproduction.  
- Baseline hyperparameters (e.g., memory chunk size, retrieval top‑k) are not enumerated, risking non‑equivalent implementations.  
- Judge prompts and model versions are unclear, leading to potential variability in QA scoring.
