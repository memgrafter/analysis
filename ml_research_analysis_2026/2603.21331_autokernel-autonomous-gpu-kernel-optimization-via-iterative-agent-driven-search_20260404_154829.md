# AutoKernel: Autonomous GPU Kernel Optimization via Iterative Agent-Driven Search

## Quick Facts
- **arXiv ID:** 2603.21331
- **Source URL:** https://arxiv.org/abs/2603.21331
- **Reference count:** 2
- **Primary result:** AutoKernel automates GPU kernel optimization for PyTorch models via an iterative agent loop, achieving up to 5.29× speedup on H100 over eager execution and 2.83× over `torch.compile` for RMSNorm.

## Executive Summary
AutoKernel is a system that autonomously optimizes GPU kernels for PyTorch models. It profiles the entire model to identify computational bottlenecks, ranks them by their potential end-to-end impact using Amdahl's law, and then iteratively refines Triton or CUDA C++ kernel implementations through an agent-driven search. Each candidate modification is validated by a comprehensive correctness harness before performance is measured. On an H100, the system yields substantial speedups on key kernels (RMSNorm, softmax, cross-entropy) and has been successfully deployed in community benchmarks, achieving first-place rankings and surpassing optimized libraries like CUTLASS.

## Method Summary
AutoKernel takes a PyTorch model (local file, HuggingFace ID, or custom class) and first profiles it with `torch.profiler` to measure per-kernel GPU time. It classifies kernels into nine types (e.g., matmul, softmax, layernorm) and ranks them by fractional runtime contribution. Using Amdahl's law, it projects end-to-end speedup for hypothetical kernel speedups and prioritizes kernels where improvement yields the largest gain. For each kernel, an LLM agent iteratively edits a single kernel file. A fixed five-stage correctness harness (smoke test, shape sweep, stability, determinism, edge cases) validates every candidate. If correct and >1% faster, the change is kept; otherwise it is reverted. The loop terminates per kernel based on move-on criteria (e.g., 5 consecutive reverts, 2× speedup, 90% peak utilization, or 2-hour timeout). Starter implementations in Triton (for rapid iteration) and CUDA C++ (for maximum control) are provided for each kernel type.

## Key Results
- RMSNorm: 5.29× vs eager, 2.83× vs `torch.compile` (H100)
- Softmax: 2.82× vs eager, 3.44× vs `torch.compile`
- Cross-entropy: 2.21× vs eager, 2.94× vs `torch.compile`
- Community deployments: first place on B200 leaderboard; FP4 matmul kernel 1.63–2.15× faster than CUTLASS.

## Why This Works (Mechanism)
### Mechanism 1
**Claim:** AutoKernel achieves speedups by prioritizing optimization effort on kernels with the highest potential end-to-end impact, using model-level profiling and Amdahl's law.
**Mechanism:** The system profiles an entire PyTorch model to measure per-kernel GPU time, then ranks candidate kernels by their fractional contribution to total runtime (f). The orchestrator applies Amdahl's law (S = 1/(1-f) + f/s) to project end-to-end speedup from a hypothetical kernel speedup (s), directing the agent's loop toward kernels where a given improvement yields the largest overall gain.
**Core assumption:** Model performance is dominated by a small set of kernels; improving those yields compounded end-to-end benefits.
**Evidence anchors:**
- [abstract] "profiles it to identify computational bottlenecks, ranks them by Amdahl's law impact"
- [section 3.2] "It computes an optimization plan ranked by Amdahl’s law impact (Equation 1), with what-if projections at 1.5×, 2×, 3×, and 5× speedup."
- [section 3.3] "Key insight: optimize what matters... A 1.5× speedup on a kernel that accounts for 60% of total runtime yields 1.25× end-to-end."
**Break condition:** The orchestrator moves to the next kernel when it reaches a move-on criterion (e.g., 5 consecutive reverts, 2× speedup, 90% peak utilization, or 2-hour timeout).

### Mechanism 2
**Claim:** The iterative agent loop (edit, verify, benchmark, keep/revert) reliably discovers performance improvements through automated, correctness-gated experimentation.
**Mechanism:** A single LLM agent modifies a single kernel file per iteration. A fixed, five-stage correctness harness validates every candidate before any performance measurement. If the candidate passes and shows a >1% speedup, it is kept; otherwise, the change is reverted via `git reset`. This creates a linear, reproducible experiment history where only improvements persist.
**Core assumption:** A simple keep/revert loop with a robust, static correctness oracle is more reliable and transparent than complex multi-agent coordination or learned policies for this search space.
**Evidence anchors:**
- [abstract] "iteratively refines Triton or CUDA C++ kernel implementations through hundreds of experiments without human intervention"
- [section 3.3] "An LLM agent modifies a single kernel file, a fixed benchmark harness verifies correctness and measures throughput, and the result determines whether the change persists."
- [section 3.4] Algorithm 1 explicitly defines the loop with `keep` and `revert` decisions.
- [section 10] "Simplicity over sophistication... A single agent in a tight loop produces a linear experiment history."
**Break condition:** The loop terminates per kernel based on the orchestrator's move-on criteria; for the entire model, it completes when all prioritized kernels have been processed.

### Mechanism 3
**Claim:** Supporting both Triton (for rapid iteration) and CUDA C++ (for maximum hardware control) backends under a unified interface allows the agent to apply the appropriate level of abstraction per kernel type, balancing development speed and performance ceiling.
**Mechanism:** The system provides 9 starter kernels in each backend. Triton offers JIT compilation (1-5s) and hardware-agnostic code, enabling quick exploration of tiling strategies. CUDA C++ provides direct access to warp-level primitives (WMMA, `__shfl_xor_sync`), shared memory bank-conflict layouts, and explicit register control for final-stage tuning. The agent chooses which backend file to edit based on the kernel's needs and the optimization playbook's advice.
**Core assumption:** Different kernels and optimization stages benefit from different abstraction levels; a one-size-fits-all backend would either be too slow to iterate (CUDA) or too limited (Triton) for peak performance.
**Evidence anchors:**
- [abstract] "iteratively refines Triton or CUDA C++ kernel implementations"
- [section 2.3] "AutoKernel differs... it supports both Triton and CUDA C++ backends within a single framework, letting the agent choose the right abstraction level per kernel."
- [section 5] "Both backends expose the same `kernel_fn()` interface."
**Break condition:** This is an architectural feature, not a conditional break. The mechanism persists throughout the optimization process.

## Foundational Learning
- **GPU Roofline Model & Amdahl's Law**: To reason about whether a kernel is compute- or memory-bound (guiding tier selection) and to quantify the end-to-end impact of optimizing a specific kernel. The system actively reports "% of peak" utilization and uses Amdahl's law for prioritization.
  - *Quick check:* If a kernel uses 40% of total model time and you achieve a 2× speedup on it, what is the theoretical maximum end-to-end speedup? (Answer: 1/(1-0.4) + 0.4/2 = 1.25×)
- **GPU Kernel Optimization Primitives**: The agent's six-tier playbook (block size tuning, memory coalescing, compute fusion, etc.) assumes familiarity with techniques like tiling, warp shuffle, bank conflicts, and online softmax. Understanding these is necessary to interpret the agent's actions and benchmark results.
  - *Quick check:* Why might vectorized memory loads (e.g., `tl.load` with `BLOCK_SIZE` alignment) improve performance for a memory-bound kernel like RMSNorm?
- **Agent-Based Search Loops**: The entire system is an autonomous loop. Grasping the paradigm—mutable code, fixed oracle, keep/revert decisions—is key to understanding the design's simplicity and effectiveness, and how to debug it (e.g., by examining the git history of experiments).
  - *Quick check:* What is the primary risk of allowing the agent to modify both the candidate code *and* the benchmark harness? How does AutoKernel mitigate it? (Answer: Risk of the agent cheating the harness; mitigation: harness is fixed and separate from the kernel file.)

## Architecture Onboarding
### Component map
profile.py -> extract.py -> orchestrate.py -> [agent loop with bench.py]

### Critical path
1. Profile entire model to get per-kernel GPU time and classify kernels.
2. Extract bottleneck kernels, generate standalone `kernel.py` files with shapes and reference.
3. Orchestrator ranks kernels by Amdahl's impact and iterates per kernel:
   - Agent edits kernel file.
   - `bench.py` runs five-stage correctness harness and benchmarks.
   - If correct and >1% speedup, keep; else revert.
   - Terminate per kernel based on move-on criteria.
4. Repeat for next kernel until all done.

### Design tradeoffs
- **Single agent vs multi-agent:** Simplicity and linear experiment history vs potential for parallel, diverse exploration.
- **Correctness gating:** Fixed, static harness ensures reliability but may miss some nondeterministic bugs.
- **Triton vs CUDA C++:** Rapid iteration (Triton) vs maximum hardware control (CUDA); agent chooses based on kernel needs.

### Failure signatures
- **Correctness harness rejection** (especially Stage 2 shape sweep or Stage 4 determinism): likely race conditions in reductions, incorrect masking for non-power-of-two dimensions, or dtype-specific overflow.
- **Performance regression after edit:** often due to block size changes causing shared memory bank conflicts or excessive register pressure.
- **Premature move-on** (5 consecutive reverts): agent stuck in local optimum or insufficient exploration of higher optimization tiers.

### First experiments
1. Install dependencies (PyTorch 2.x with CUDA 12.8+, Triton, LLM API access) and clone the repository.
2. Profile a model: `python profile.py --model <model_identifier>`.
3. Start optimization: `python orchestrate.py --kernel <kernel_type>` and monitor logs (TSV format).

## Open Questions the Paper Calls Out
- **Population-based multi-GPU search:** Could improve efficiency by parallel exploration, but single-agent may not explore optimally.
- **Learned search policies:** Could reduce iteration count by adapting to kernel types, but fixed playbook may be suboptimal.
- **Profiling-guided mutations:** Could target optimizations more precisely with low-level feedback (SASS, memory counters), but current loop uses only high-level metrics.
- **Cross-kernel fusion:** Could cut memory traffic by merging adjacent kernels, but not currently supported due to isolation.

## Limitations
- LLM configuration (model, temperature, top-p) not disclosed, affecting reproducibility and search diversity.
- Orchestrator thresholds (e.g., "90% peak utilization", "2× speedup" baseline) are unclear, hindering precise replication.
- Speedups reported only on H100; performance on other architectures (A100, consumer GPUs) is unknown due to potential roofline model mismatches.

## Next Checks
1. **LLM ablation:** Run AutoKernel with at least two different LLM backends (e.g., GPT-4 vs Claude 3.5 Sonnet) on the same kernels, keeping all else equal, and compare convergence rate and final throughput.
2. **Threshold sensitivity:** Systematically vary the move-on criteria (e.g., 3 vs 5 consecutive reverts, 80% vs 95% peak utilization) and measure impact on final speedup and total wall-clock time.
3. **Cross-architecture replication:** Execute the optimized kernels on at least two additional GPUs (e.g., A100 and RTX 4090) and report achieved TFLOPS/GB/s relative to the respective roofline and PyTorch baselines.
