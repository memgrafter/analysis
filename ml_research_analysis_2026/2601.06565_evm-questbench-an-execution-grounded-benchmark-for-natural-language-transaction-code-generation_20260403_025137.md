# EVM-QuestBench: An Execution-Grounded Benchmark for Natural-Language Transaction Code Generation

## Quick Facts
- **ArXiv ID**: 2601.06565
- **Source URL**: https://arxiv.org/abs/2601.06565
- **Reference count**: 40
- **Primary result**: A modular, execution-grounded benchmark for evaluating LLM-generated blockchain transaction scripts, revealing large performance gaps and persistent asymmetry between atomic and composite tasks.

## Executive Summary
EVM-QuestBench introduces a benchmark for evaluating large language models (LLMs) on generating EVM transaction scripts from natural language instructions. It addresses the critical need for execution-grounded evaluation, where errors cause irreversible financial loss. The benchmark comprises 107 tasks (62 atomic, 45 composite) that dynamically instantiate numeric parameters and validate outcomes on a forked EVM chain via snapshot isolation. Evaluating 20 models shows substantial performance differences and a split capability: some models excel at precise single actions but fail at multi-step workflows, while others show the opposite pattern. The top model, Claude-Sonnet-4.5, achieved 8,236 out of 10,700 total points with low variance. The design enables low-cost evaluation (as little as \$0.06 and 334K tokens per run) and provides split reporting to diagnose workflow orchestration failures.

## Method Summary
The benchmark defines tasks as JSON specifications containing natural language templates, parameter ranges, and validator configurations. For each evaluation round, the runner selects a template, samples numeric values uniformly from the specified intervals, and generates a prompt. The LLM must output a TypeScript module that constructs and submits EVM transactions using ethers.js. The runner executes this module in a Node/Bun sandbox against a forked BSC mainnet snapshot, ensuring identical preconditions for every task. Validators then compare the post-execution state (balances, allowances, etc.) against the instantiated parameters, using tolerance thresholds where appropriate. Scores are weighted sums of binary checks (success, address correctness, function signature, state change), with composite tasks also penalizing inefficiency via a step‑count decay. No model training is involved; the benchmark evaluates pretrained LLMs through on‑chain execution.

## Key Results
- 107 tasks covering atomic and composite DeFi operations (62 atomic, 45 composite).
- Dynamic instantiation prevents memorization, forcing generalization to unseen numeric values and unit conversions.
- Top model Claude-Sonnet-4.5 scored 8,236/10,700 with coefficient of variance <9%.
- Composite pass rates across models range from 41/45 to 0/45, revealing a persistent capability asymmetry.
- Low‑cost execution: a full run can cost as little as \$0.06 and consume 334K tokens.

## Why This Works (Mechanism)

### Mechanism 1: Dynamic Parameter Instantiation
**Claim**: Randomly sampling numeric parameters from predefined intervals for each evaluation round prevents trivial memorization and forces models to generalize across arbitrary values and unit conversions.  
**How it works**: The runner chooses a natural language template from a pool, samples numbers (e.g., percentages, amounts) uniformly, injects them into the template, and passes them to both the prompt and the validator. The validator expects the state change to match these instantiated values (e.g., `amount = balance × percentage`). The model must compute the correct integers, respecting token decimals, rather than recall fixed values.  
**Core assumption**: Generalization to unseen parameter combinations is separable from syntactic code recall; execution against fresh values is a valid proxy for real‑world robustness.  
**Evidence**: The paper reports low variance across rounds (CV < 9%) for most models, indicating that performance is stable despite different numbers. Section 3.5 states that dynamic sampling "forces models to generalize across arbitrary values and unit conversions."  
**Break condition**: If models learn the underlying mathematical transformations independent of specific numbers, the diagnostic value diminishes. Observed round‑to‑round variance suggests this has not occurred.

### Mechanism 2: Snapshot Isolation of Forked Chain State
**Claim**: Creating a snapshot of the initialized forked EVM environment and restoring it before each task guarantees identical preconditions, eliminating cross‑task interference from residual state changes.  
**How it works**: After funding accounts and deploying contracts on an Anvil fork, the runner captures a snapshot. Prior to each task, the chain state is rolled back to this snapshot, ensuring that balances, allowances, and contract storage are exactly the same regardless of previous task outcomes.  
**Core assumption**: Transaction scripts are pure functions of the initial state and instruction; side effects must not accumulate to confound scoring.  
**Evidence**: The abstract mentions "snapshot isolation"; Section 4.3 details the snapshot‑restore process. The low variance across rounds also indirectly supports effective isolation—state leakage would increase noise.  
**Break condition**: Imperfect snapshot restoration (e.g., non‑deterministic contract storage, time‑dependent variables) would introduce scoring noise. The observed stability suggests robustness.

### Mechanism 3: Validator‑Based Scoring Against Post‑Execution State
**Claim**: Scoring by comparing the actual on‑chain state changes to the expected changes (grounded in the instantiated parameters) directly reflects the irreversible financial impact of a transaction script, rather than relying on code similarity.  
**How it works**: Each task family defines a validator that checks: transaction success, correctness of target contract address, function signature, and quantitative state deltas (e.g., recipient balance increase ≈ amount). Tolerance thresholds are calibrated per family. For composite tasks, a step‑efficiency decay multiplies the base score based on the ratio of actual to optimal steps.  
**Core assumption**: The correctness of a transaction script is defined by its observable effects on the blockchain, not by structural resemblance to a reference.  
**Evidence**: Section 3.6 describes the validator checks and weighting. Section G (tolerance sensitivity) shows that validators produce bimodal outcomes (exact match or zero) and that changing tolerances does not affect scores, confirming reliability.  
**Break condition**: Bugs or incomplete coverage in validators (e.g., missing side effects) could yield scores that do not reflect true correctness. The bimodality and sensitivity analysis mitigate this concern.

## Foundational Learning
- **Concept: EVM Transaction Execution Model**  
  **Why needed**: Understanding how transactions interact with the EVM (gas, signing, receipt status, state transitions) is essential to interpret failure modes such as reverts versus incorrect value transfers.  
  **Quick check**: What is the difference between a transaction’s `value` field and an ERC‑20 `transfer` calldata amount, and why must both be correct for a successful BNB transfer?
- **Concept: DeFi Protocol Prerequisites**  
  **Why needed**: Composite tasks require chaining atomic actions (e.g., `approve` before a swap). Missing a prerequisite causes a revert, so models must infer and sequence dependencies from natural language.  
  **Quick check**: For swapping an ERC‑20 token on PancakeSwap, what are the prerequisite transactions and in what order must they appear in a composite workflow?
- **Concept: Units and Decimals in EVM**  
  **Why needed**: Token amounts are represented as integers in the token’s native unit (e.g., 10¹⁸ for 18 decimals). A model that forgets to scale will fail the state‑change validator. This is a common atomic failure.  
  **Quick check**: If a task says “swap 0.5 BNB” and BNB has 18 decimals, what integer value should the `value` field of the transaction contain?

## Architecture Onboarding
**Component map**: Task Definition → Dynamic Instantiation → Runner Interface → Fork Environment → Validators → Scoring Engine  
**Critical path**: Task JSON provides templates and ranges → instantiation builds prompt with sampled numbers → LLM outputs TypeScript module → Runner executes module in sandbox → transactions submitted to forked BSC → receipts and state changes collected → validators compare against instantiated parameters → score computed (including decay for composites).  
**Design tradeoffs**:  
- *Modularity vs. realism*: Adding tasks is simple (JSON + validator), but the fixed `ethers.js` interface and pre‑deployed contracts may not capture real‑world complexities like MEV or gas price volatility.  
- *Cost vs. coverage*: Dynamic instantiation keeps token cost low (~334 K tokens/run), but only 107 tasks may not cover every DeFi protocol or edge case.  
- *Single‑chain focus*: The benchmark runs on BSC; porting to other EVM or non‑EVM chains requires adapting the runner and validators.  
**Failure signatures**:  
- `schema_invalid`: Missing `executeSkill` export, incorrect return type, malformed TypeScript.  
- Transaction reverts: Receipt status = 0, often due to wrong calldata, insufficient allowance, or slippage.  
- State mismatch: Receipt success but validator’s delta check fails (e.g., amount off by >tolerance), commonly from unit/decimals errors.  
- Composite multi‑step decay: Final state correct but score reduced by `K_act / K_opt` overhead.  
**First 3 experiments**:  
1. Run a single atomic task (e.g., `bnb_transfer_percentage`) with Claude‑Haiku; verify a score of 100/100 and observe the full pipeline.  
2. Run a composite task (e.g., `composite_approve_and_swap`) with a valid solution, then intentionally remove the `approve` step; confirm the composite score drops to zero due to a revert on swap.  
3. Modify a validator’s tolerance (e.g., 0.1% → 5%) and re‑score a successful run; verify the score remains unchanged (supports bimodality claim).

## Open Questions the Paper Calls Out
1. Can LLMs autonomously generate valid and diverse benchmark tasks for EVM‑QuestBench? The current tasks are manually curated; autonomous generation would require LLMs to produce executable, varied JSON specs without human input.  
2. What security checks beyond post‑state validation can detect transaction intent violations or side effects? Existing validators only compare final state; they may miss intermediate attacks (e.g., reentrancy) that do not change end balances.  
3. How can task coverage be expanded across protocols, chains, and operation types to ensure comprehensive evaluation? The current focus on BSC and common DeFi ops may not expose weaknesses in other domains (e.g., lending, multi‑chain).  
4. What factors cause the persistent performance asymmetry between atomic and composite tasks in LLMs? The paper identifies the asymmetry but not its root causes; suspected factors include planning, parameter propagation, or interface handling.

## Limitations
- **External state dependency**: Forking BSC at the latest block may cause run‑to‑run variation unless a specific block height is pinned.
- **Model inference variability**: Unreported decoding parameters (e.g., top‑p, presence penalty) beyond temperature = 0.7 can affect output consistency.
- **Benchmark scope**: Only 107 tasks on BSC may not generalize to other EVM chains or non‑EVM ecosystems.

## Confidence
- **Dynamic instantiation prevents memorization**: Medium (strong round‑variance evidence, but long‑term learning of transformation rules could degrade diagnostic value).
- **Snapshot isolation ensures score comparability**: High (low variance and explicit restoration logic; imperfect restoration would increase noise, which is not observed).
- **Validator‑based scoring reflects real‑world correctness**: High (bimodal pass/fail outcomes and tolerance‑insensitivity tests indicate reliable capture of correct state changes).

## Next Checks

2. **Test composite workflow failure**: For `composite_approve_and_swap`, remove the `approve` step from a valid solution; verify the composite score drops to zero and the validator reports a revert on the swap transaction.
