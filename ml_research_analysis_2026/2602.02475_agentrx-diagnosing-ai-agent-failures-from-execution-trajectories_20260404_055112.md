# AgentRx: Diagnosing AI Agent Failures from Execution Trajectories

## Quick Facts
- **arXiv ID**: 2602.02475  
- **Source URL**: https://arxiv.org/abs/2602.02475  
- **Reference count**: 40  
- **Primary result**: AGENTRX achieves absolute improvements of 23.6% in step localization and 22.9% in failure category attribution over existing baselines.

## Executive Summary
AGENTRX is an automated framework for diagnosing failures in AI agent executions. It addresses the challenge of localizing the first unrecoverable failure step and attributing a root-cause category from a cross-domain taxonomy. The system normalizes execution trajectories into a common intermediate representation, synthesizes constraints from tool schemas, domain policies, and the trajectory prefix, and evaluates these constraints step-wise to generate an auditable violation log. An LLM judge then uses this log—along with the full trajectory and a taxonomy checklist—to pinpoint the critical failure step and its cause. Experiments on a benchmark of 115 failed trajectories across three domains (τ-bench, Flash, Magentic-One) show significant gains over prior methods.

## Method Summary
AGENTRX operates in four stages: (1) **Normalization** converts heterogeneous domain logs into a unified intermediate representation (IR) of steps and substeps; (2) **Constraint synthesis** generates two types of checks—global constraints (from tool schemas and domain policies) and dynamic constraints (from the trajectory prefix up to each step)—using LLM prompts; (3) **Evaluation** runs all applicable constraints at each step, recording violations as `(step_index, assertion_name, evidence)` with a short context window; (4) **Judgment** passes the full trajectory, violation log, and a taxonomy checklist to an LLM to predict the first unrecoverable failure step and its root-cause category. The framework is designed to be auditable, with every failure prediction tied to specific constraint violations.

## Key Results
- **Step localization**: AGENTRX improves exact-match accuracy by 23.6% absolute over baselines.
- **Failure category**: Improves critical-category accuracy by 22.9% absolute.
- **Cross-domain gains**: Shows per-domain improvements on τ-bench, Flash, and Magentic-One.

## Why This Works (Mechanism)
AGENTRX succeeds by transforming the ambiguous problem of failure diagnosis into a structured inference task guided by explicit constraints. The violation log acts as a grounded audit trail that filters out irrelevant steps and highlights contradictions between agent actions and domain rules. This reduces the LLM judge’s reliance on brittle chain-of-thought reasoning and focuses attention on evidence-backed anomalies. The taxonomy checklist further standardizes category selection, while dynamic constraints adapt to each trajectory’s prefix, capturing inconsistencies that static rules miss. Together, these components address the core challenges of probabilistic, long-horizon agent executions: noise in tool outputs, partial observability, and the need for interpretable root-cause analysis.

## Foundational Learning
- **Constraint synthesis**: Why needed? Converts domain knowledge (schemas, policies) into machine-checkable assertions that surface agent violations.  
  *Quick check*: Verify that a generated constraint correctly flags an invalid tool call (e.g., missing required field).
- **Violation log**: Why needed? Provides an auditable, step-indexed record of constraint failures to guide the judge.  
  *Quick check*: Ensure a log entry includes `step_index`, `assertion_name`, and a one-sentence `evidence` snippet.
- **Taxonomy checklist**: Why needed? Disambiguates failure categories (e.g., “tool misuse” vs. “planning error”) across domains.  
  *Quick check*: Confirm that the judge prompt lists all taxonomy categories and requires selection of one.
- **Intermediate representation (IR)**: Why needed? Normalizes diverse agent logs (single- vs. multi-agent) into a uniform format for constraint evaluation.  
  *Quick check*: Convert a sample Magentic-One trace into IR steps with `role`, `content`, `tool_name`.
- **LLM-as-judge**: Why needed? Leverages reasoning to integrate constraint evidence with trajectory context for final attribution.  
  *Quick check*: Test judge consistency on a trajectory with a clear, single violation.
- **Recovery reasoning**: Why needed? Distinguishes recoverable errors (e.g., retryable tool failure) from unrecoverable ones.  
  *Quick check*? Identify whether a later step compensates for an earlier mistake.

## Architecture Onboarding
**Component map**:
Trajectory + Tool schemas + Domain policy → Normalizer → IR → Constraint synthesizer → Constraints (global + dynamic) → Evaluator → Violation log → LLM judge → (Critical step, Category)

**Critical path**:
1. Normalization (IR creation) → 2. Constraint generation (per step) → 3. Violation log assembly → 4. Single judge call (all-at-once) → 5. Output.

**Design tradeoffs**:
- **One-shot vs. stepwise constraint generation**: One-shot is cheaper but risks missing early violations in long trajectories; stepwise is precise but costlier.
- **Programmatic vs. semantic constraints**: Programmatic (schema checks) are reliable but narrow; semantic (LLM-generated) are flexible but noisy.
- **All-at-once vs. step-then-category judging**: All-at-once avoids error propagation; step-then-category can improve clarity but harms performance on some domains.

**Failure signatures**:
- Overgeneration of low-quality constraints → noisy violation log → judge misled.
- Context window overflow in one-shot generation → early-step violations truncated.
- Judge prompt ambiguity → inconsistent category selection (especially with Step-then-Category).
- Domain mismatch (e.g., τ-bench constraints on Magentic) → irrelevant violations.
- Ambiguous “first unrecoverable” annotation → ground-truth tolerance issues (±3 steps acceptable).

**First 3 experiments**:
1. **Baseline constraint set**: Implement only global programmatic constraints (e.g., schema validation) and measure step localization accuracy vs. reported numbers.
2. **Judge prompt ablation**: Compare All-at-Once vs. Step-then-Category prompts on 10 Flash trajectories to replicate the performance drop noted in the paper.
3. **IR normalization validation**: Process 5 Magentic-One multi-agent traces into IR and verify that substep aggregation matches examples in Appendix E.2.

## Limitations
- **Reproducibility risk**: Exact LLM prompts for constraint synthesis and judging are not disclosed, hindering precise replication.
- **Generalization scope**: Benchmark covers only three domains; constraint transfer to out-of-distribution agent systems (e.g., WebArena) is unproven.
- **Annotation subjectivity**: Defining “first unrecoverable failure” is cognitively intense, leading to inherent ambiguity in step localization metrics.

## Next Checks
1. **Constraint generation fidelity**: Reimplement the synthesizer using only paper-described inputs (schemas, policy, prefix) and compare produced constraints against those in the released benchmark for 20 trajectories.
2. **Judge robustness**: Run AGENTRX with multiple LLM backbones (GPT-4o, Claude 3.5 Sonnet) at fixed temperature to quantify variance in step/category accuracy.
3. **Zero-shot transfer**: Apply AGENTRx trained solely on τ-bench data to a held-out domain (e.g., AgentBench) to measure out-of-distribution performance without fine-tuning.
