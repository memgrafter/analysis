# FactorSmith: Agentic Simulation Generation via Markov Decision Process Decomposition with Planner-Designer-Critic Refinement

## Quick Facts
- **arXiv ID:** 2603.20270
- **Source URL:** https://arxiv.org/abs/2603.20270
- **Reference count:** 22
- **Primary result:** FactorSmith achieves higher system test pass rates than all baselines on the PyGame Learning Environment, improving upon the strongest non-agentic factored baseline by 3–8 percentage points across eight games.

## Executive Summary
FactorSmith addresses the challenge of generating executable 2D game simulations from natural language by overcoming LLM limitations with large, interconnected code contexts. The method combines factored POMDP decomposition, which reduces per-step context to relevant state variables, with an embedded planner–designer–critic agentic workflow that iteratively refines each generated code component through structured scoring and checkpoint rollback. Evaluated on the PyGame Learning Environment benchmark, FactorSmith consistently outperforms prior approaches, achieving higher compilation and runtime success rates, with a token overhead of approximately 1.7× over the non-agentic factored baseline.

## Method Summary
FactorSmith first decomposes a natural language game specification into modular steps using chain-of-thought, each constrained to at most one input-handling, state-transition, and rendering function. For each step, it selects a minimal subset of state variables relevant to that step (factored POMDP) to shrink the context window. The step is then broken into MVC sub‑functions. Each sub‑function undergoes an iterative refinement loop: a designer proposes code, a critic evaluates it against structured rubrics (correctness, completeness, state usage, code quality), and a planner decides to accept, request revision, or rollback if scores regress. After all steps, the generated artifacts are assembled and validated for compilation and a 300‑frame runtime. The implementation uses the OpenAI Agents SDK and a SQLite‑backed session store for state persistence and rollback.

## Key Results
- System test pass rates improve over FactorSim by 3–8 pp across eight PLE games, with top gains of +8pp on Catcher and Waterworld.
- Ablations show both factorization (−12pp) and the critic (−7pp) are essential; removing either causes significant performance drops.
- Token overhead is ~1.7× relative to FactorSim, reflecting the cost of iterative refinement but delivering consistent quality improvements.

## Why This Works (Mechanism)

### Factored POMDP Decomposition
- **Claim:** Reducing per‑step context to only relevant state variables prevents LLM hallucination and irrelevant modifications.
- **Mechanism:** Each step operates on a scoped subset `S[Z_k]` selected via `CtxSelect`, shrinking the context window size `|C[Z_k]|` relative to full context.
- **Core assumption:** LLM performance degrades with large interconnected contexts; limiting to causally relevant components improves correctness.
- **Evidence:** Formal definition in section 3.1; predecessor FactorSim’s success; ablation removing factorization causes the largest single drop (−12pp).
- **Break condition:** If a step inherently requires many state variables (high connectivity), context reduction may be insufficient.

### Planner–Designer–Critic Refinement Loop
- **Claim:** Iterative refinement with structured evaluation catches local errors missed by single‑shot generation.
- **Mechanism:** Designer proposes code `x_r`, critic assigns scores `σ_r` across rubrics (correctness, completeness, state usage, code quality), and planner decides to accept, revise, or rollback if total score drops.
- **Core assumption:** An independent critic using structured rubrics reliably identifies subtle errors; rollback prevents degradation.
- **Evidence:** Algorithm 1 and Equation 8; ablation removing critic reduces pass rate by 7 pp.
- **Break condition:** Critic miscalibration (inflated scores) or designer inability to improve can lead to premature termination.

### Complementary Synergy
- **Claim:** Factorization and agentic refinement tackle orthogonal failure modes: context overwhelm vs. local errors.
- **Mechanism:** Factored decomposition provides a manageable scope; the agentic trio polishes each factored step’s output with exploration/backtracking. The scoped context is shared among agents for focused critique.
- **Core assumption:** Both mechanisms are required for high‑quality generation.
- **Evidence:** Abstract and section 8 discussion; ablations demonstrate substantial individual contributions.
- **Break condition:** Incorrect scoping (missing a dependency) cannot be fixed by the agentic trio operating within limited context.

## Foundational Learning

- **Factored POMDP Representation**  
  *Why needed:* Mathematical foundation for context selection, defining scopes `Z_k`, state projection `S[Z]`, and transition/reward decomposition.  
  *Quick check:* If state factors into `S = S_agent × S_environment` and a step updates only agent position, which variables and functions belong in the context?

- **Planner–Designer–Critic Deliberation Loop**  
  *Why needed:* Core refinement engine; understanding roles, structured rubrics, and planner’s rollback policy is essential.  
  *Quick check:* Given designer code that compiles but misreads a state variable, which critic scoring category catches it and what planner action follows a low score?

- **Structured vs. Free‑Form LLM Outputs**  
  *Why needed:* FactorSmith relies on structured critic scores for reliable delta computation and decisions, avoiding ambiguity.  
  *Quick check:* Why is a numerical correctness score delta (e.g., 6→8) more reliable for the planner than a natural‑language critique saying “the code is better now”?

## Architecture Onboarding

### Component map
SessionStore (SQLite) → Agents (Stateful*Agent) → Planner Tools → Pipeline (run_step)

Agents inherit BaseSimAgent, fetch scoped context from SessionStore, and internally orchestrate designer‑critic‑planner loops. Planner Tools include `request_initial_design`, `request_critique`, `request_design_change`, `reset_to_previous_checkpoint`. Pipeline (`run_step`) orchestrates: snapshot → state change → decompose → input logic → state transition → UI rendering → clean → validate.

### Critical path
1. Decompose the specification into steps `(q1,…,qK)` via Chain‑of‑Thought.
2. For each step, execute the agent sequence: StateChangeAgent → DecomposeAgent → (optional) InputLogicAgent → LogicAgent → UIAgent.
3. Each agent call triggers an internal trio loop (Designer→Critic→Planner) until score threshold `τ` or max rounds `N_max`, rolling back if total score drops.
4. After all steps, combine artifacts and run sanity checks (compilation, 300‑frame runtime).

### Design tradeoffs
- **Token overhead (~1.7× FactorSim):** Cost of multi‑round critique vs. single‑shot; trade‑off: higher quality vs. latency/cost.
- **Rollback safety vs. stagnation:** Rollback prevents regression but may loop if designer cannot improve; `N_max` and `τ` guard against this.
- **Structured scoring vs. flexibility:** Rubrics enable comparable scores but may miss errors outside defined categories (e.g., inefficiency).

### Failure signatures
- Persistent low critic scores in a category across rounds → likely incorrect scoping or flawed prompt.
- Frequent rollbacks → planner’s acceptance policy too lenient or critic inconsistent.
- Compilation failure after a step → state change or decomposition introduced breaking dependency; context omitted a required variable.
- Critic giving high scores to buggy code → rubric miscalibration; need to refine critic’s system prompt.

### First 3 experiments
1. Ablate on target game: run `w/o Factorization` (full context + agentic) and `w/o Critic` (designer‑only) to quantify each mechanism’s contribution.
2. Token audit: measure input/output tokens per step for FactorSim vs. FactorSmith; identify which agent type consumes most tokens.
3. Critic calibration: inject subtle bugs into 10 designer outputs; verify critic’s `Correctness` score drops by ≥2 points; adjust rubrics if necessary.

## Open Questions the Paper Calls Out
1. **Accuracy of critic scores:** The critic may inflate scores for subtly incorrect code. No analysis comparing scores to actual behavior. Resolution requires large‑scale study with execution‑based tests or human evaluation.
2. **Execution‑based feedback:** Incorporating runtime observations could catch dynamic errors but adds complexity. Need to integrate a sandboxed execution module into the critic and evaluate its impact.
3. **Parallel generation:** The factored structure might allow parallel generation of independent branches, but could introduce race conditions. Implement a parallel executor, measure generation time, token usage, and success rates.
4. **Specialized smaller models:** Fine‑tuning open‑source models (e.g., CodeLlama, Phi‑3) for designer/critic roles could reduce cost. Evaluate whether such models maintain FactorSmith’s quality improvements.

## Limitations
- Critic rubrics, weights, and detailed system prompts are not fully disclosed, hindering exact reproduction.
- Context selection algorithm (`CtxSelect`) and dependency graph computation remain vague.
- Model version (e.g., GPT‑4‑turbo) and sampling parameters (temperature, top_p) are unreported.
- Planner stopping thresholds (`τ`, `N_max`) are undisclosed, making refinement behavior hard to replicate.
