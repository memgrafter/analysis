# FedRot-LoRA: Mitigating Rotational Misalignment in Federated LoRA

## Quick Facts
- **arXiv ID:** 2602.23638  
- **Source URL:** https://arxiv.org/abs/2602.23638  
- **Reference count:** 40  
- **Primary result:** FedRot-LoRA mitigates rotational misalignment in federated LoRA via orthogonal alignment, achieving state-of-the-art accuracy on GLUE (e.g., 0.8932 with 3 clients) and generative tasks (44.37% on GSM8K) while reducing aggregation error by an order of magnitude.

## Executive Summary
Federated fine-tuning of large language models with Low-Rank Adaptation (LoRA) suffers from rotational misalignment: because the low-rank factorization is invariant to orthogonal rotations, different clients’ updates occupy different latent subspaces. Naively averaging these misaligned factors introduces destructive cross‑client interference. FedRot-LoRA solves this by having each client apply a client‑specific orthogonal rotation to one LoRA factor (alternating between A and B) before upload, aligning it with a reference (previous global model). This preserves the semantic update while reducing subspace mismatch. A soft rotation parameter λ provides robustness. Theoretically, alignment yields a tighter bound on the aggregation error in nonconvex FL convergence. Empirically, FedRot-LoRA outperforms baselines on GLUE and code/math benchmarks, with stable performance across ranks and heterogeneity levels.

## Method Summary
FedRot-LoRA runs the standard federated averaging loop with LoRA adapters. In each communication round, the server broadcasts the current global LoRA matrices (¯B, ¯A). Each client locally trains these factors on its private data via SGD. Before uploading, the client performs alignment: depending on round parity, it aligns either A or B to the corresponding matrix from the previous global model. Alignment solves an orthogonal Procrustes problem: given the reference matrix, the client computes the optimal rotation R that best aligns its local factor to the reference via SVD of their correlation matrix. To avoid over‑correction, a soft rotation is formed by interpolating between the identity and the optimal rotation using λ ∈ [0,1]. The rotated factor is updated (e.g., A_i ← Rᵀ A_i for A‑alignment, and correspondingly B_i ← B_i R). The client uploads the aligned factors. The server averages all clients’ aligned factors to form the new global LoRA. This alternating alignment progressively brings all clients into a common subspace without extra communication.

## Key Results
- On GLUE with RoBERTa‑Large, FedRot-LoRA achieves average accuracy 0.8932 (N=3) and 0.8818 (N=10), beating FedIT, FFA‑LoRA, and RoLoRA.
- On Llama 3‑8B, it reaches 44.37% on GSM8K and 40.88% on HumanEval.
- Aggregation error (measured as Frobenius norm discrepancy) is reduced by an order of magnitude compared to naive factor‑wise averaging.

## Why This Works (Mechanism)

### Mechanism 1: Rotational invariance causes destructive cross‑term noise
Due to low‑rank factorization, for any orthogonal R, (B R)(Rᵀ A) = B A. Thus, semantically equivalent updates can be represented by different (B, A) pairs across clients, spanning different latent subspaces. Direct averaging of these misaligned factors yields cross‑terms B_i A_j (i≠j) that introduce aggregation noise, degrading the global update.

### Mechanism 2: Orthogonal alignment aligns subspaces while preserving updates
Clients rotate one factor to align with a reference (previous global) via the orthogonal Procrustes solution. The rotation R* is derived from SVD of the correlation matrix between local and reference factors. Soft rotation (interpolation with λ) gradually applies alignment, preventing over‑correction when the reference is noisy (e.g., early rounds). The update B_i (Rᵀ A_i) remains mathematically equivalent to B_i A_i but now shares a common basis with other clients.

### Mechanism 3: Tighter theoretical convergence bound
In the nonconvex FL convergence analysis, the error term E_t = (average B)(average A) − average(BA) appears in the bound. Alignment reduces the dispersion of factors, yielding a positive gain Γ(λ) that strictly tightens the upper bound on E[‖E_t‖²] under standard assumptions (smoothness, bounded gradients, bounded LoRA norms, linear lower envelope, non‑IID, bounded dispersion).

## Architecture Onboarding
**Component map:** Server broadcasts global (¯B_t, ¯A_t) → Client receives, runs local SGD → Client computes alignment rotation R_i (based on round parity and previous global) → Client applies soft rotation to factors → Client uploads aligned (˜A_i, ˜B_i) → Server averages received factors → updates global (¯B_{t+1}, ¯A_{t+1}) → repeat.

**Critical path:** Server broadcast → client local training → alignment computation → upload → server aggregation → next round.

**Design tradeoffs:**
- λ (soft rotation): lower (e.g., 0.2) stabilizes early rounds; higher (e.g., 1.0) improves alignment but risks over‑correction; tune to heterogeneity.
- Alternating alignment vs single‑factor: Alternating between A and B yields best performance; aligning only B is especially harmful.
- Reference choice: previous global model is communication‑free and effective; random client local may be fresher but adds variance; older global (t−2) underperforms.
- LoRA rank r: higher rank increases expressivity but also misalignment degrees of freedom; FedRot‑LoRA remains robust but may need λ adjustment.

**Failure signatures:**
- λ set to 1.0 under high non‑IID → unstable training and accuracy drop.
- Aligning only B → significant accuracy decrease.
- Random rotation (no reference) → performance collapse.
- Round 1: reference undefined → skip alignment (implement guard).

## Open Questions the Paper Calls Out
- Are the standard smoothness, bounded gradient, and bounded LoRA norm assumptions practically valid in heterogeneous FL?
- Can the soft rotation strength λ be chosen automatically (e.g., based on alignment error) rather than via manual grid search?
- Does FedRot‑LoRA scale to larger foundation models (e.g., >10B parameters) and multimodal architectures?
- Could aligning both LoRA factors jointly (instead of alternating) further reduce cross‑client subspace mismatch?

## Limitations
- No official code; reimplementation may diverge in subtle details (LoRA init, optimizer, weight decay).
