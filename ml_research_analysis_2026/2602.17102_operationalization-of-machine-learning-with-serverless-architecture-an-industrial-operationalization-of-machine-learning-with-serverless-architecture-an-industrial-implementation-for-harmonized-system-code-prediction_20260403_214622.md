# Operationalization of Machine Learning with Serverless Architecture: An Industrial Implementation for Harmonized System Code Prediction

## Quick Facts
- **arXiv ID**: 2602.17102
- **Source URL**: https://arxiv.org/abs/2602.17102
- **Reference count**: 40
- **Primary result**: A serverless MLOps framework on AWS achieves 98% accuracy for HS code prediction using custom text embeddings and automated pipelines, ensuring scalability, reproducibility, and cost-efficiency.

## Executive Summary
This paper details an industrial deployment of machine learning for Harmonized System (HS) code classification in customs compliance, where errors cause significant shipment delays and financial losses. The authors implement a serverless MLOps framework on AWS that automates the ML lifecycle via event-driven pipelines. Key innovations include domain-specific custom text embeddings, multiple neural architectures (Text-CNN, LSTM, DNN) with Bayesian hyperparameter tuning, and stratified up-sampling to handle severe class imbalance. Automated A/B testing dynamically selects optimal models. Text-CNN achieves 98% accuracy on ground truth data, while the serverless infrastructure provides auto-scaling for SLA adherence and cost savings by avoiding expensive transformer models.

## Method Summary
The system employs a serverless AWS architecture (EventBridge, Step Functions, SageMaker) to orchestrate end-to-end ML workflows. Data preprocessing uses custom word embeddings trained directly on the customs corpus, outperforming generic pre-trained embeddings (GloVe). Models undergo Bayesian hyperparameter optimization within defined ranges. To address class imbalance, minority HS codes are up-sampled via stratified duplication. For production, event triggers initiate inference or retraining pipelines. Retraining includes k-fold cross-validation and ANOVA-based A/B testing to statistically validate model improvements before promotion, ensuring reproducibility and operational reliability.

## Key Results
- Text-CNN achieves 98% accuracy on ground truth data, outperforming LSTM and DNN.
- The serverless framework delivers auto-scaling, SLA compliance, and cost-efficiency by favoring simpler, less expensive models over transformers.
- Custom embeddings and stratified up-sampling are essential for capturing domain semantics and mitigating class imbalance.

## Why This Works (Mechanism)
### Mechanism 1: Domain-specific custom text embeddings
- **Claim**: Custom embeddings significantly improve classification accuracy by capturing specialized product description semantics.
- **Mechanism**: Embedding vectors are learned directly from the training corpus during model training, rather than using generic pre-trained embeddings (e.g., GloVe). This encodes domain-specific terminology and relationships in customs declarations.
- **Core assumption**: General-purpose embeddings lack coverage of engineering and trade-specific vocabulary; domain-adapted embeddings produce more discriminative features.
- **Evidence anchors**: 
  - [abstract] states custom embeddings yield 98% accuracy.
  - [section III-E] reports pre-trained embeddings failed; custom embeddings succeeded.
- **Break condition**: If domain vocabulary aligns with general corpora or training data is very limited, pre-trained embeddings may suffice without overfitting.

### Mechanism 2: Bayesian hyperparameter tuning
- **Claim**: Bayesian optimization efficiently navigates large neural network configuration spaces, finding high-performing models with fewer experiments than grid/random search.
- **Mechanism**: A Bayesian optimizer models the performance surface from prior runs and selects promising hyperparameter sets (e.g., dropout, layer sizes) for subsequent training, reducing compute cost.
- **Core assumption**: Model performance is highly sensitive to hyperparameters; intelligent search yields near-optimal configurations with fewer trials.
- **Evidence anchors**: 
  - [abstract] mentions Bayesian tuning.
  - [section IV-F] describes hyperparameter ranges passed to the optimizer; Tables II and V show tuned values.
- **Break condition**: In extremely high-dimensional or non-stationary spaces, Bayesian optimization may lose sample efficiency; simpler heuristics may be preferred under tight time constraints.

### Mechanism 3: Serverless MLOps with event-driven automation
- **Claim**: Serverless orchestration with event-driven pipelines and automated A/B testing ensures scalable, cost-efficient, reliable deployment in a compliance-critical environment.
- **Mechanism**: AWS services (EventBridge, Step Functions, SageMaker) automate the ML lifecycle. Event triggers start state machines for preprocessing, training, or inference. Auto-scaling handles variable loads. A/B testing compares candidate models via k-fold cross-validation and ANOVA, promoting the best performer based on metrics and cost.
- **Core assumption**: Manual MLOps cannot reliably meet SLAs under fluctuating volumes; serverless auto-scaling and event-driven automation reduce overhead while ensuring auditability.
- **Evidence anchors**: 
  - [abstract] describes serverless MLOps, auto-scaling, and cost-efficiency.
  - [section VII] details infrastructure, CI/CD, and pipelines; [section V-C] covers A/B testing.
  - Corpus evidence from serverless ML studies supports scalability.
- **Break condition**: Extremely low latency requirements (e.g., sub-10ms) may violate SLAs due to cold starts; very large models may exceed serverless memory limits, necessitating traditional deployment.

## Architecture Onboarding
- **Component map**:
  GitHub -> AWS CodeBuild -> Amazon ECR -> Amazon S3 -> Amazon EventBridge -> AWS Step Functions -> Amazon SageMaker

- **Critical path**:
  - *Inference*: User uploads data to S3 -> EventBridge triggers Step Functions state machine -> preprocessing -> SageMaker endpoint inference -> postprocessing -> results written to S3.
  - *Retraining*: New labeled data arrives or scheduled trigger -> EventBridge starts Step Functions -> data validation/preprocessing -> SageMaker training job -> evaluation -> A/B testing via k-fold/ANOVA -> if new model wins, update ECR; else discard.

- **Design tradeoffs**:
  - Serverless orchestration vs. compute: SageMaker handles heavy lifting; serverless services provide auto-scaling and glue. Tradeoff: complexity vs. infrastructure management elimination.
  - Custom embeddings vs. pre-trained: Custom embeddings required training from scratch but achieved 98% accuracy; pre-trained failed due to domain specificity.
  - Up-sampling: Stratified up-sampling preserves original data and avoids synthetic noise; SMOTE rejected due to overfitting risk.
  - Model choice: Text-CNN selected for accuracy and low latency; transformers avoided due to higher inference cost and opacity.
  - A/B testing overhead: Running multiple models adds compute but ensures safe, data-driven promotion.

- **Failure signatures**:
  - Step Functions execution failures (check CloudWatch logs).
  - SageMaker job failures (out-of-memory, high error rates, data issues).
  - Model performance decay: post-deployment monitoring shows precision/recall drop below threshold.
  - EventBridge triggers not firing: misconfigured event pattern or permissions.
  - Cost overruns: unexpected scaling of SageMaker instances; monitor AWS Cost Explorer.
  - Data drift: significant shift in input distribution; detect via statistical tests (e.g., KL divergence).

- **First 3 experiments**:
  1. **End-to-End Inference Test**: Upload a small CSV (10 product descriptions) to the inference input S3 bucket. Verify EventBridge triggers the state machine. Confirm output S3 contains predictions with HS codes. Check latency and logs.
  2. **Retraining Pipeline with Subset**: Prepare a minimal training dataset (1,000 samples) and place it in the retraining input location. Trigger the retraining state machine manually. Validate SageMaker training job launches, completes, and produces a model artifact. Ensure A/B testing step compares and logs metrics.
  3. **A/B Testing Validation**: Deploy two model versions (e.g., Text-CNN and LSTM) by updating Docker image tags in ECR. Run inference on a fixed test set. Inspect A/B testing results to confirm system correctly identifies the better model based on criteria (e.g., F1 score). Then promote the winner and verify it becomes default.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: Does advanced up-sampling (SMOTE/borderline SMOTE) improve class-balanced performance metrics over stratified up-sampling for minority HS codes in this dataset?
- **Basis in paper**: [explicit] The future scope states: "Implement alternate up-sampling techniques such as SMOTE."
- **Why unresolved**: The authors chose stratified up-sampling due to concerns about overfitting from synthetic samples but did not conduct a rigorous empirical comparison with SMOTE variants.
- **What evidence would resolve it**: Controlled experiments training models with each up-sampling method on identical train-test splits, comparing per-class F1 scores (especially for minority classes) and overfitting indicators (e.g., train-test gap).

### Open Question 2
- **Question**: Under what conditions can generative AI models (e.g., transformer-based) be integrated into this serverless MLOps framework without compromising explainability and cost targets?
- **Basis in paper**: [explicit] The future scope mentions: "Future work will also include the potential integration of generative AI approaches... once... transparency... policies allow."
- **Why unresolved**: Current design excludes them due to opacity and cost, but specific thresholds for explainability metrics and cost ceilings are undefined.
- **What evidence would resolve it**: Pilot integration of a distilled transformer model, measuring accuracy, inference latency, cost per prediction, and explanation quality (e.g., via SHAP consistency with feature importance from current model).

### Open Question 3
- **Question**: Does incorporating KL Divergence for monitoring prediction distribution drift reduce false positive/negative rates compared to current threshold-based monitoring?
- **Basis in paper**: [explicit] Future scope lists: "Include model monitoring strategies like KL Divergence can help to overcome data drift."
- **Why unresolved**: The paper indicates drift monitoring is implemented but does not specify the method; KL Divergence is proposed but untested.
- **What evidence would resolve it**: Backtesting on historical data: simulate drift events, compare KL Divergence-triggered retraining against existing accuracy-drop thresholds, measuring time-to-detection and post-retraining improvement in precision/recall.

### Open Question 4
- **Question**: What is the quantitative difference in total operational cost between transformer models and the selected Text-CNN when deployed in this serverless architecture?
- **Basis in paper**: [inferred] The abstract states: "Cost-efficiency drives model choice; while transformers may achieve similar accuracy, their long-term operational costs are significantly higher" without presenting cost data.
- **Why unresolved**: The cost argument is qualitative and central to model selection but lacks empirical validation in the serverless context.
- **What evidence would resolve it**: Benchmark deployment of accuracy-matched transformer variants and Text-CNN on AWS, logging all costs (training, inference, storage, retraining) over a realistic period, and analyzing SLA adherence under variable loads.

## Limitations
- **Data**: Proprietary Schneider Electric dataset; no public dataset described, hindering external validation of class distribution and text characteristics.
- **Up-sampling**: Exact stratified up-sampling algorithm ("mean and median ratios") is ambiguous; precise duplication strategy and target balance are unknown.
- **A/B testing**: ANOVA procedure (transformations, alpha) and 37-fold cross-validation logic are unspecified, limiting reproducibility of model selection.

## Confidence
- **Custom embeddings effectiveness**: Medium confidence. Internal results are strong, but lacks external validation; may not generalize if customs terminology overlaps common corpora.
- **Bayesian tuning efficiency**: Medium confidence. Standard method, but implementation details (library, iterations) are unspecified; efficiency gains not quantitatively benchmarked against alternatives.
- **Serverless MLOps scalability**: High confidence. Architecture thoroughly described with AWS services; analogous studies support claims, though cold-start mitigation details are sparse.
