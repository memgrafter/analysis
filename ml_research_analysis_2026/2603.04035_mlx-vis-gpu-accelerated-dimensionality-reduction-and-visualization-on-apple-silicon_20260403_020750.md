# mlx-vis: GPU-Accelerated Dimensionality Reduction and Visualization on Apple Silicon

## Quick Facts
- **arXiv ID:** 2603.04035  
- **Source URL:** https://arxiv.org/abs/2603.04035  
- **Reference count:** 10  
- **Primary result:** A unified, pure-MLX library that runs full dimensionality reduction (8 methods + NNDescent) and rendering on Apple Silicon GPUs, achieving up to 12.6× speedup over CPU baselines on Fashion-MNIST (70k points).

## Executive Summary
The paper introduces **mlx-vis**, a library that reimplements eight popular dimensionality reduction (DR) methods and the NNDescent algorithm entirely in MLX, enabling end‑to‑end execution on Apple Silicon GPUs via Metal. Existing DR tools are fragmented and CPU‑bound, ignoring the powerful integrated GPUs in Apple’s ecosystem. By leveraging MLX’s lazy evaluation and JIT compilation, mlx‑vis accelerates graph construction, optimization, and GPU‑based rendering. On a M3 Ultra, seven methods embed Fashion‑MNIST in 2.0–4.7 s, and an 800‑frame animation renders in 1.4 s. The library depends only on MLX and NumPy, simplifying deployment on macOS.

## Method Summary
mlx‑vis reimplements UMAP, t‑SNE, PaCMAP, LocalMAP, TriMap, DREAMS, CNE, and MMAE (plus NNDescent for approximate nearest neighbors) using exclusively MLX operations. The pipeline proceeds as: (1) standardized input data (z‑score per feature) is loaded as an MLX array; (2) k‑NN graphs are built via NNDescent entirely on GPU; (3) the chosen DR method minimizes its objective over the graph for a fixed number of epochs (default 500), with all tensor operations JIT‑compiled via `@mx.compile`; (4) final embeddings can be animated by capturing intermediate states and rendering frames with circle‑splatting and alpha blending, optionally encoding to H.264 via ffmpeg. The design eschews external C/C++/CUDA kernels, keeping dependencies minimal while exploiting Metal GPU acceleration.

## Key Results
- Embedding times on M3 Ultra for Fashion‑MNIST (70k × 784): 2.0–4.7 seconds across seven methods.  
- Animation of 800 frames at 1000×1000 resolution: 1.4 seconds.  
- Speedups vs. CPU baselines: up to 12.6× for t‑SNE and 7.2× for TriMap.

## Why This Works (Mechanism)
The speedup stems from **three core MLX‑enabled properties**: (1) **GPU‑first computation** – every operation from NNDescent to gradient updates runs on Metal, avoiding host‑CPU bottlenecks; (2) **JIT compilation** – `@mx.compile` fuses operations and optimizes memory layout for the GPU; (3) **lazy evaluation** – MLX defers execution until results are needed, reducing unnecessary intermediate transfers. Combined, these eliminate the CPU‑GPU data movement and sparse‑operation overhead that plague CPU‑based libraries. The pure‑MLX implementation also avoids complex build dependencies, ensuring the pipeline stays entirely within Apple’s unified memory architecture.

## Architecture Onboarding
**Component map:**  
Data (NumPy) → MLX array → NNDescent (GPU) → DR optimizer (GPU, JIT) → Embeddings list → animate_gpu (GPU render) → H.264 encode (GPU‑assisted via ffmpeg)

**Critical path:** The DR optimization loop (epoch iterations) dominates runtime; NNDescent can be reused across epochs, so the per‑epoch compute is the performance hotspot.

**Design tradeoffs:**  
- *Pure MLX* simplifies deployment and ensures GPU residency but may restrict use of highly optimized CPU‑only subroutines (e.g., sparse matrix libraries).  
- *Lazy evaluation* reduces memory pressure but can obscure performance bottlenecks during development.  
- *Circle‑splatting* trades geometric precision for speed and smoothness in animations.

**Failure signatures:**  
- `mx.default_device()` shows `cpu` → MLX fell back to CPU; update macOS/metal drivers.  
- `mx.get_peak_memory()` spikes → reduce rendering resolution or point radius; clear cache between frames.  
- ffmpeg errors → install ffmpeg with VideoToolbox support (`brew install ffmpeg --with-videotoolbox`).

**First experiments:**  
1. Verify GPU: `import mlx as mx; mx.set_default_device(mx.gpu); print(mx.default_device())` → should print `gpu`.  
2. Run a single DR method (e.g., UMAP) on a small subset (e.g., 5,000 points) to confirm no CPU fallback; time it.  
3. Render a 2‑second animation (e.g., 100 frames) to test the full pipeline; check output file size and visual smoothness.

## Open Questions the Paper Calls Out
**Open Question 1:** Do the mlx‑vis implementations produce embeddings quantitatively equivalent to their reference CPU counterparts?  
*Basis:* The paper states embedding quality should match but only shows visual results without numerical metrics like trustworthiness or continuity.  
*Why unresolved:* No empirical comparison across benchmark datasets using standard metrics; MLX‑specific adaptations may alter properties.

**Open Question 2:** How does performance scale with dataset size and vary across Apple Silicon hardware generations?  
*Basis:* All benchmarks use Fashion‑MNIST (70k points) on a single M3 Ultra; no results on smaller datasets or less‑memory‑constrained devices (e.g., MacBook Air).  
*Why unresolved:* Metal GPU capabilities (core count, memory bandwidth) differ across chips; scaling laws and minimum viable configurations are unknown.

**Open Question 3:** What algorithmic characteristics determine whether a DR method can be efficiently implemented in pure MLX without compromising the “pure MLX design”?  
*Basis:* The authors excluded PHATE and StarMAP due to architectural complexity; ANE is unsuitable due to reliance on external libraries.  
*Why unresolved:* Clarifying these characteristics would guide future extensions and help users select GPU‑friendly methods; requires implementing a diverse set of DR algorithms in MLX and documenting challenges.

## Limitations
- **Hardware lock‑in:** All claims and features are restricted to Apple Silicon; no cross‑platform validation.  
- **Algorithmic fidelity:** MLX implementations may diverge from reference libraries (e.g., NNDescent δ threshold, t‑SNE FFT parameters), potentially affecting embedding quality and speed comparisons.  
- **Baseline ambiguity:** CPU baselines lack pinned versions, thread counts, and preprocessing details (e.g., PCA), undermining reproducibility of speedup numbers.  
- **Power measurement:** Unclear if `macmon` reports whole‑system or isolated GPU power; methodology not standardized.

## Confidence
- **GPU‑accelerated pipeline (graph → optimization → rendering):** *Medium* – Paper states all steps run on Metal, but hidden CPU fallbacks (e.g., sparse ops) are possible without full code audit.  
- **Speedups vs. CPU (12.6× t‑SNE, 7.2× TriMap):** *Medium* – Dependent on unspecified baselines and hyperparameters; algorithmic differences may confound pure hardware gains.  
- **Method coverage (8 DR methods + NNDescent):** *High* – Library API explicitly lists these; algorithmic equivalence not verified but presence is certain.  
- **Dependency simplicity (MLX + NumPy only):** *High* – Clear from `requirements.txt` and implementation described.
