# CounselReflect: A Toolkit for Auditing Mental-Health Dialogues

## Quick Facts
- **arXiv ID:** 2603.29429  
- **Source URL:** https://arxiv.org/abs/2603.29429  
- **Reference count:** 40  
- **Primary result:** CounselReflect integrates 12 model-based and 69 rubric metrics via configurable LLM judges to generate multi-dimensional audit reports with evidence-linked excerpts, demonstrating high usability (SUS 75.2–78.8) and trust (TIA 5.1–5.7/7) in human evaluation.

## Executive Summary
CounselReflect is a toolkit designed to address the lack of structured auditing for mental-health dialogues. It combines two families of evaluation signals—12 task-specific model-based metrics and 69 literature-derived rubric metrics operationalized by configurable LLM judges—to produce comprehensive reports including session summaries, turn-level scores, and evidence-linked excerpts. A human evaluation with 20 users and 6 mental-health experts confirmed the system's high usability (System Usability Scale scores of 75.2–78.8) and trust (Trust in Automation scores of 5.1–5.7/7), indicating that the tool is understandable and trustworthy for auditing conversations.

## Method Summary
The system ingests conversation transcripts and allows users to select from a library of model-based predictors (e.g., for empathy, reflection, toxicity) and rubric-based metrics (covering constructs like therapeutic alliance and cultural humility). Model-based metrics are produced by specialized, pre-trained or fine-tuned machine learning models. Rubric metrics are scored by a configurable LLM-as-judge that interprets literature-derived rubrics. The audit results are synthesized into a multi-dimensional report with session-level summaries, interactive turn-level visualizations, and highlighted evidence excerpts. The toolkit is available as a web application, browser extension, and CLI, supporting local execution for privacy. Human evaluation used synthetic transcripts generated via GPT-4o and measured usability and trust.

## Key Results
- High usability: System Usability Scale scores of 75.2–78.8.
- High trust: Trust in Automation scores of 5.1–5.7 on a 7-point scale.
- Reports validated as understandable and trustworthy for auditing mental-health dialogues.

## Why This Works (Mechanism)

### Mechanism 1: Integrated Multi-Signal Evaluation
**Claim:** Combining model-based and rubric-based metrics provides more comprehensive coverage than any single signal.  
**Mechanism:** Model-based predictors offer consistent, scalable scoring for well-defined constructs; rubric-based LLM judges cover nuanced or less-frequent constructs. The system synthesizes both, allowing users to triangulate findings.  
**Core assumption:** No single automated metric captures all clinically relevant dimensions.  
**Evidence anchors:** Integration of 12 model-based and 69 rubric metrics; design rationale to extend coverage beyond fixed sets.  
**Break condition:** Failure of either component degrades comprehensiveness; outputs are decision support, not a replacement for expert judgment.

### Mechanism 2: Evidence-Linked, Drill-Down Reporting
**Claim:** Interactive inspection from summary to turn-level evidence builds trust and understandability.  
**Mechanism:** Session summary provides high-level digest; users drill down to turn-level scores and see highlighted excerpts that justify each score. This transparency lets users verify system reasoning.  
**Core assumption:** Users will trust audit results if they can inspect the basis for assessments.  
**Evidence anchors:** Abstract and section 3.3 describe two-level drill-down; user study qualitative feedback highlights helpfulness of evidence-linked feedback.  
**Break condition:** Poor evidence-linking or cumbersome UI reduces transparency and trust.

### Mechanism 3: Configurable Deployment Modes
**Claim:** Multiple deployment options (web, extension, CLI) and local execution lower adoption barriers across use cases and privacy contexts.  
**Mechanism:** Decouples engine from presentation; web for interactive analysis, extension for in-context auditing, CLI for batch processing, local via Ollama for privacy. Configurable LLM judges allow model choice based on budget, latency, privacy.  
**Core assumption:** Utility depends on fitting user workflows and data governance.  
**Evidence anchors:** Abstract and section 2 list modes and use cases; expert reviewers suggest use cases.  
**Break condition:** Brittle configuration or slow local deployment hinders adoption.

   **Why needed:** The 69 rubric metrics lack dedicated models, so the system uses an LLM to interpret rubrics. This requires understanding the LLM-as-judge paradigm and its pitfalls (sensitivity, bias, calibration).

## Architecture Onboarding

**Component Map:**  
Input Layer (transcript ingestion, API/model config) -> Metric Engine (Model-Based Subsystem: task-specific predictors; Rubric-Based Subsystem: LLM judge with configured backend) -> Report Generator (aggregates scores, computes session trends, selects evidence excerpts) -> Presentation Layer (Web/Extension UI: interactive visualizations, drill-down, chat; CLI: structured output). Local execution supported via Ollama.

**Critical Path:**  
Upload transcript -> Select/configure metrics -> Metric Engine runs parallel evaluations -> Report Generator aggregates -> User explores via UI/CLI, tracing from summary to metric graph to turn-level details.

**Design Tradeoffs:**  
- Coverage vs Reliability: 69 rubric metrics increase coverage but rely on less reliable LLM scoring versus specialized model-based predictors.  
- Flexibility vs Integration: Configurable LLM judges offer flexibility but create integration complexity and score incomparability.  
- Interpretability vs Automation: Evidence-linking enhances interpretability but requires additional logic for excerpt selection.

**Failure Signatures:**  
- Partial failure: A specific model-based predictor fails; system skips that metric and reports error.  
- LLM Judge failure: LLM endpoint rate-limits, returns malformed output, or refuses scoring; system should have timeout/retry and clear error reporting.  
- Data size failure: Long transcripts exceed context windows; system needs chunking/segmentation strategy and graceful truncation handling.  
- Privacy breach attempt: User configures untrusted API endpoint; system should validate endpoints or warn, with local deployment as mitigation.

**First 3 Experiments:**  
1. **Model-Based Metric Sanity Check:** Run the 12 model-based predictors on a human-annotated benchmark (e.g., AnnoMI, ESConv) to verify performance against documented metrics.  
2. **Rubric Scoring Consistency:** For 5 core rubric metrics, score 50 dialogue turns with expert consensus using different LLM backends; measure intra- and inter-judge reliability.  
3. **Usability of Evidence-Linking:** Recruit domain-naïve users to identify specific turn-level scores using CounselReflect reports with true vs. shuffled evidence excerpts; measure accuracy and time.

## Open Questions the Paper Calls Out
1. How can the sensitivity of rubric-based metrics to LLM model choice, versioning, and prompting be mitigated to ensure consistent evaluations across backends?
2. Does CounselReflect's multi-dimensional auditing lead to improved conversation quality or user outcomes in real-world mental-health support contexts?
3. How can CounselReflect be deployed while ensuring compliance with mental health data privacy regulations (e.g., HIPAA, GDPR) and maintaining user trust?

## Limitations
- LLM-as-judge reliability and operational rubrics are unspecified; stability and bias across backends unknown.  
- Evidence-linking algorithm is not detailed; its precision and recall unmeasured, impacting transparency claims.  
- Human evaluation used synthetic transcripts and a small, specific sample; generalizability to real clinical data and broader populations unproven.
