# Using a Human-AI Teaming Approach to Create and Curate Scientific Datasets with the SCILIRE System

## Quick Facts
- arXiv ID: 2603.12638
- Source URL: https://arxiv.org/abs/2603.12638
- Reference count: 29
- Primary result: SCILIRE's dynamic few-shot learning (n=100) increases record-level F1 from 16.28 to 28.42 and outperforms Elicit (2.09) and SciSpace (1.58) by over 10x.

## Executive Summary
SCILIRE is a system for extracting structured data from scientific literature using a Human-AI Teaming approach. It combines an AI extraction pipeline with iterative human curation, where user corrections dynamically provide few-shot examples for subsequent LLM inference. This workflow, supported by provenance checking and explanations, significantly improves extraction fidelity. Evaluated on 18 datasets, SCILIRE raises record-level F1 from 16.28 (zero-shot) to 28.42 with 100 curated examples and outperforms commercial tools by an order of magnitude. Case studies demonstrate reduced curation effort and enable dataset creation at previously infeasible scales.

## Method Summary
SCILIRE implements a Human-AI Teaming workflow with three main phases: preprocessing, record generation, and verification support. Preprocessing parses PDFs using GROBID/Tika, extracts tables/figures with custom models (Cascade R-CNN, UniTable), and chunks text. In the pilot phase, users define a schema and correct zero-shot generated records, storing corrections in a pool. For batch processing, the system retrieves a document-specific example from the pool via BM25 and includes it as a 1-shot prompt to the LLM. Generated records undergo provenance checking (fuzzy match) and explanation (BM25 retrieval of supporting paragraphs) to aid user verification. The feedback loop updates the pool, iteratively improving extraction fidelity.

## Key Results
- Dynamic few-shot learning (n=100) increased average record-level F1 from 16.28 (zero-shot) to 28.42 on 18 datasets (GPT-5).
- SCILIRE achieved average F1 of 22.76 on 10 PDFs per dataset compared to Elicit (2.09) and SciSpace (1.58).
- Case studies showed statistically significant decreasing trend in human workload (p<0.025) and users reported 2× efficiency improvement.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Dynamic sampling of human-corrected records for in-context learning (ICL) improves LLM extraction fidelity over time.
- **Mechanism:** The system uses BM25 to retrieve the most similar previously human-verified record from a growing pool and includes it as a 1-shot example in the LLM prompt for subsequent inference. This tailors the few-shot exemplar to be document-specific.
- **Core assumption:** Human corrections represent high-quality, gold-standard patterns that an LLM can successfully mimic when presented in a prompt, and that similarity (via BM25) is a valid proxy for selecting the most helpful exemplar for a new document.
- **Evidence anchors:**
  - [abstract] "users define a schema, review and correct AI-generated records, and these corrections dynamically sample few-shot examples for subsequent LLM inference, improving extraction fidelity."
  - [section 4.2] "SCILIRE retrieves a document-specific ICL example using BM25 from the pool of previously human-corrected documents. The closest match record is used as a 1-shot prototype... This dynamic ICL selection ensures that the LLM receives the most relevant example, improving extraction fidelity."
  - [corpus] Neighbors indicate active research in HAT for scientific IE (e.g., "Human-artificial intelligence teaming for scientific information extraction..."), supporting the relevance of the mechanism, though specific evidence for BM25's efficacy over other retrievers is not directly cited from corpus.
- **Break condition:** If the pool of human-corrected records contains only irrelevant or low-quality corrections, dynamic sampling will degrade performance. Performance gains also plateau if the pool becomes too large and redundant, as noted: "increasing pool size tends to introduce redundancy rather than informative diversity."

### Mechanism 2
- **Claim:** Integrated provenance checking and on-demand explanations build user trust and enable efficient verification of AI-generated records.
- **Mechanism:** The system computes fuzzy string match scores between LLM output and source text chunks to grade alignment (provenance). It also retrieves top-3 supporting paragraphs via BM25 and highlights aligned words. Users can request LLM-generated justifications.
- **Core assumption:** Graded provenance signals and retrieved evidence reduce the cognitive load of verification compared to manually searching source PDFs, making human-in-the-loop curation feasible at scale.
- **Evidence anchors:**
  - [abstract] "The system includes provenance checking and on-demand explanations to aid verification."
  - [section 4.3] "The system visualises match strength as a graded signal, enabling users to build trust... by identifying aligned and unaligned answers." and "SCILIRE provides justifications of AI answers by aligning generated text to the source material... Aligned words are shown highlighted in bold to the user to assist data verification."
  - [section 7] User feedback confirms: "interviews... indicated that they were not prepared to trust AI-generated results... They wanted to inspect and review the content, with the ability to correct the results... how the user performed this review was idiosyncratic: some preferred to check the source PDFs, while others preferred the supporting paragraphs. This validates our design decision to include tools to facilitate the curation."
- **Break condition:** If the fuzzy matching or BM25 retrieval fails to locate the correct source span for a correct value (false negative provenance), or locates a span for a hallucinated value (false positive), user trust will erode. The mechanism depends on the quality of the underlying text extraction and embedding/retrieval.

### Mechanism 3
- **Claim:** A modular preprocessing pipeline (parsing, table/figure extraction, chunking) creates a consistent, machine-readable text base from heterogeneous PDFs, which is foundational for reliable LLM extraction.
- **Mechanism:** The system uses a dual-parser strategy (GROBID preferred, Tika fallback) for text, a custom Cascade R-CNN model for detecting tables/figures/captions, and a fine-tuned UniTable for table structure recognition, outputting markdown. Long documents are chunked with overlap.
- **Core assumption:** The quality and consistency of the input text fed to the LLM is a primary bottleneck; improving this preprocessing directly improves the ceiling for extraction performance, regardless of LLM capability.
- **Evidence anchors:**
  - [section 4.1] Details the full pipeline: "The GROBID is the preferred pipeline... Tika pipeline provides an alternative... we develop a custom table and figure extraction module."
  - [section 4.1, B] Reports quantitative results: "Cascade R-CNN" achieves mAP 97.12 on detection; fine-tuned UniTable achieves TEDS 97.98 on table structure recognition, indicating high-quality extraction.
  - [abstract] "SCILIRE addresses the challenge of extracting structured data from the growing scientific literature" – the premise is that raw PDFs are insufficient; preprocessing is the first essential step.
- **Break condition:** Failure in any module (e.g., GROBID failure on a specific publisher format not covered by Tika, table detection miss) propagates poor text to the LLM, causing record generation failures. The system lacks a unified fallback for entire document failure modes beyond the two text parsers.

## Foundational Learning
- **Concept: Few-Shot In-Context Learning (ICL)**
  - *Why needed here:* The entire dynamic sampling mechanism relies on the principle that an LLM's performance on a task can be improved by including a well-chosen exemplar in its prompt. The system's core innovation is making the exemplar selection dynamic and user-curated.
  - *Quick check question:* If a user corrects 10 records in the pilot phase, how does SCILIRE decide which *single* corrected record to use as the exemplar for a new, uncorrected document in the next batch?
- **Concept: Human-AI Teaming (HAT) Workflow Patterns**
  - *Why needed here:* The paper's thesis is that a single-pass AI tool is insufficient. The HAT-DC pattern (pilot -> iterative correction -> batch) is the system's organizing principle. Understanding the asymmetry of tasks (human verifies/edits, AI generates) is key.
  - *Quick check question:* What is the primary purpose of the "pilot phase" in the SCILIRE workflow, and how does its output differ from the "batch phase" output?
- **Concept: Information Extraction Evaluation (Record-Level F1)**
  - *Why needed here:* The paper's primary results use a strict record-level F1 metric. This is non-standard compared to cell-level or token-level metrics. A learner must understand why full-record exact match is the chosen signal and its implications (e.g., a single error nullifies a record).
  - *Quick check question:* If a tool extracts 9 out of 10 fields correctly for a given paper's record but hallucinates the 10th, what is the record-level Precision, Recall, and F1 for that record?

## Architecture Onboarding
### Component Map
1. **Document Preprocessing:** Takes PDFs -> [GROBID/Tika] -> Text + [Custom Table/Figure Detection & UniTable TSR] -> Markdown tables/figures -> Chunked text. (Fig 1, Sec 4.1)
2. **Record Generation:** Takes Schema, Chunked Text, + (Optional: Dynamic ICL Example from Curated Pool) -> Constructs Prompt -> LLM (e.g., GPT-4o) -> Raw JSON records. (Sec 4.2)
3. **Verification Support:** Takes Raw Records + Source Chunks -> [Provenance Checker (fuzzy match)] & [Explanation Engine (BM25 retrieval + highlight)] -> UI for User Curation. (Sec 4.3)
4. **Feedback Loop:** User Curation (Edits/Accepts/Rejects) -> Updates Curated Pool -> Informs future Dynamic ICL. (Workflow in Fig 1)

### Critical Path
PDF Upload -> Preprocessing (text + tables) -> **Pilot Phase** (User selects small sample -> Zero-shot Generation -> User Curation -> Pool Update) -> **Batch Phase** (Dynamic ICL from Pool -> Generation on remaining docs -> Optional further curation -> Export). The pilot phase is the essential loop that bootstraps system improvement.

### Design Tradeoffs
- *Context Window vs. Example Quality:* Using a dynamic 1-shot example preserves context for the schema/record but limits the number of fields that can be extracted in one prompt. More examples (n-shot) would consume valuable context.
- *Parser Coverage vs. Complexity:* Relying on GROBID/Tika is pragmatic but introduces a dependency. The custom table extractor adds maintenance overhead for potentially niche gains.
- *Evaluation Metric:* Choosing strict record-level F1 penalizes partial correctness severely but aligns with scientist need for trustworthy, complete records.

### Failure Signatures
- *Preprocessing:* High rate of "No machine-readable text" OCR failures; low table detection mAP (<90) on specific PDF styles; chunking breaks sentences across fields.
- *Generation:* Low F1 persists even after 100 curated examples (pool redundancy). LLM consistently outputs non-JSON or missing required fields.
- *Provenance:* Low fuzzy match scores (>70% of cells) on a document the user believes is correct, indicating poor text alignment or LLM paraphrasing beyond fuzzy matching.

### First 3 Experiments
1. **Baseline Replication:** Run the benchmark protocol on a single small dataset (e.g., `YSHEAY`) with GPT-5 using 0-shot, ICL-10, ICL-50, ICL-100. Verify the F1 improvement trend matches the paper's average (Sec 5.1, Table 2).
2. **Tool Comparison Spot-Check:** Run `SCILIRE` (with dynamic ICL, n=all) against `Elicit` (static ICL) and `SciSpace` (zero-shot) on 10 PDFs from one dataset (e.g., `PPE`). Verify the magnitude of difference (Table 3).
3. **Pilot Phase Simulation:** Implement Algorithm 1 for one dataset. Artificially "seed" the curated pool with first 10 papers' ground truth as "user corrections." Run generation on the 11th paper with vs. without the dynamic sample. Measure per-record F1 change. This isolates the dynamic sampling effect.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can SCILIRE be extended to automatically analyze curated datasets to uncover scientific trends and patterns, as proposed for future work?
- **Basis in paper:** [explicit] The Conclusion states: "As future work, we plan to extend SCILIRE with additional analysis capabilities, allowing users to transform curated datasets into actionable insights by facilitating the discovery of trends and patterns."
- **Why unresolved:** The current system focuses solely on extraction and curation; no integrated analysis features are implemented or evaluated.
- **What evidence would resolve it:** Development and user evaluation of a module that ingests SCILIRE's output tables and performs statistical or machine learning-based trend detection, measuring utility against manual analysis.

### Open Question 2
- **Question:** What causes the performance plateau or degradation in dynamic sampling when the human-corrected pool exceeds ~100 records, and how can the sampling strategy be optimized for larger document collections?
- **Basis in paper:** [inferred] RQ1 results (Table 2) show F1 gains diminish or reverse beyond n=100, with the authors speculating "redundancy rather than informative diversity" but providing no deeper analysis.
- **Why unresolved:** The relationship between pool size, example similarity, and domain heterogeneity is unexplored; optimal sizing may vary by schema complexity or document similarity.
- **What evidence would resolve it:** An ablation study measuring example diversity (e.g., via embedding entropy) across pool sizes and domains, correlated with F1 changes, to derive a principled pool-size selection heuristic.

### Open Question 3
- **Question:** How reliable is the fuzzy string matching-based provenance checker at identifying hallucinations or misalignments in LLM-generated records across diverse scientific jargon and paraphrasing styles?
- **Basis in paper:** [inferred] The Verification Support module uses `fuzzywuzzy` for cell-level alignment, but user feedback (Section 7) indicates users still frequently check original PDFs, suggesting limited trust in automated provenance signals.
- **Why unresolved:** No quantitative evaluation of the provenance checker's precision/recall against ground-truth alignment; its effectiveness across domains (e.g., chemistry vs. medicine) is unknown.
- **What evidence would resolve it:** A human evaluation study where experts judge whether provenance flags (match scores) correctly indicate unsupported content, per domain, to calibrate thresholds and identify failure modes.

### Open Question 4
- **Question:** Does the quality of user corrections in the HAT-DC loop significantly impact the effectiveness of dynamic few-shot learning, and what mechanisms can mitigate error propagation from incorrect human edits?
- **Basis in paper:** [inferred] The HAT-DC workflow assumes user-corrected records are gold standards for dynamic sampling, but the paper does not address sensitivity to user errors or strategies for correction validation.
- **Why unresolved:** Real-world curation may introduce mistakes; erroneous few-shot examples could degrade LLM performance over iterations, a risk unexamined.
- **What evidence would resolve it:** Simulation experiments injecting controlled noise (e.g., random or systematic errors) into user corrections, measuring F1 decay across iterations, and testing consensus-based or self-consistency filtering to detect low-quality corrections.

### Open Question 5
- **Question:** To what extent can SCILIRE maintain extraction fidelity and curation efficiency when scaling to very large corpora (e.g., thousands of documents) as claimed by users, and what are the bottlenecks?
- **Basis in paper:** [inferred] Case studies processed up to ~200 documents, with one user noting a need for 6,000; however, benchmarking only evaluated up to 372 documents (SciREX), and scalability claims lack empirical validation at that magnitude.
- **Why unresolved:** Computational costs, dynamic sampling latency, and human curation burden at scale are not measured; performance may degrade due to pool management or document heterogeneity.
- **What evidence would resolve it:** A scalability experiment processing 1,000+ documents from one or more datasets, tracking F1, per-document processing time, curation time trends, and system resource usage, to identify practical limits and optimization needs.

## Limitations
- BM25 dynamic sampling parameters (k1, b), indexed text scope, and query formulation are unspecified, hindering exact replication.
- Record alignment threshold for merging GROBID/Tika outputs and for evaluation is unreported, creating ambiguity in F1 calculation.
- Reliance on proprietary LLMs (GPT-5/4o) limits reproducibility and the effect of dynamic ICL with smaller, open models is unverified.

## Confidence
- Dynamic ICL Improves Fidelity: Medium
- Provenance & Explanations Build Trust: Medium
- Preprocessing is Foundational: High

## Next Checks
