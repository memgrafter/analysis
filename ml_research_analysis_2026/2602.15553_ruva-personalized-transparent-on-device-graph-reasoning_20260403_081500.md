# RUVA: Personalized Transparent On-Device Graph Reasoning

## Quick Facts
*   **arXiv ID:** 2602.15553
*   **Source URL:** https://arxiv.org/abs/2602.15553
*   **Reference count:** 2
*   **Primary result:** An on-device neuro-symbolic GraphRAG system using a Personal Knowledge Graph (PKG) achieves transparent, deterministic fact deletion and multi-hop reasoning, with 61% positive answer ratings on a 52-question benchmark.

## Executive Summary
RUVA is a system designed to bring accountability and privacy to Retrieval-Augmented Generation (RAG) by replacing opaque vector stores with a user-inspectable Personal Knowledge Graph (PKG) stored on the device. It uses a small vision-language model to convert multimodal personal data (text, images) into a deterministic graph of facts. This "Glass Box" approach allows users to see the exact reasoning paths and perform precise, cascade deletions of facts via SQL, operationalizing a "Right to be Forgotten." Evaluated on a Google Pixel 8 Pro, it reports interactive ingestion (~2.4s) and retrieval (~38ms) latencies, with 61% of complex answers rated positively by multiple LLM judges.

## Method Summary
The paper's reproduction notes are not provided. Based on the key outcome and mechanism description, the method involves: 1) On-device ingestion of multimodal data using a Small Vision Language Model (SVLM) to extract structured subject-predicate-object triples. 2) Construction of a Personal Knowledge Graph (PKG) from these triples, using entity resolution and Leiden community detection to merge related facts. 3) Multi-hop reasoning performed by translating natural language questions into SQL queries executed on the graph database (SQLite). 4) Deterministic deletion of facts using SQL's `DELETE CASCADE`, ensuring all related edges are removed.

## Key Results
*   Achieves 2.4s average ingestion latency and 38ms retrieval latency on a Google Pixel 8 Pro.
*   On a benchmark of 52 complex questions, 61% of answers are rated "Positive" by multiple LLM judges, with strong inter-rater reliability (ρ=0.82, α=0.81).
*   Deletion tests confirm that removing a fact from the PKG causes subsequent questions relying on that fact to fail, demonstrating deterministic "forgetting."

## Why This Works (Mechanism)
RUVA's core value proposition—transparency, user control, and privacy—is enabled by replacing a probabilistic vector index with a deterministic graph. This shift allows for exact, inspectable reasoning paths (via SQL queries) and mathematically precise deletion (via SQL `CASCADE`). The use of a local, small VLM (Gemma-3n-E2b) makes on-device processing feasible, while the graph structure inherently supports multi-hop reasoning without the semantic drift common in embedding-based retrieval. The system's design directly addresses the "black box" and deletion-inaccuracy problems of standard RAG by making the knowledge store and its manipulation explicit and user-owned.

## Foundational Learning
*   **Personal Knowledge Graph (PKG):** A user-owned graph database of personal facts. *Why needed:* Replaces a vendor-controlled, opaque vector store with an inspectable, deletable knowledge base. *Quick check:* Can the user list all stored facts about a specific entity?
*   **Neuro-Symbolic Integration:** Combining neural models (VLM for extraction) with symbolic structures (SQL graph). *Why needed:* Leverages VLM perception for ingestion but uses deterministic logic for reliable reasoning and deletion. *Quick check:* Is the ingestion pipeline fully deterministic given the same input?
*   **On-Device Processing:** All computation occurs locally on the user's smartphone. *Why needed:* Ensures privacy (data never leaves) and enables direct, unfettered access to the knowledge store for inspection/deletion. *Quick check:* Does the system function without an internet connection after initial setup?
*   **Entity Resolution & Graph Cleaning:** Merging duplicate entities and detecting communities. *Why needed:* Prevents graph fragmentation from noisy data (e.g., "J. Smith" vs "John Smith"), which would break reasoning. *Quick check:* Does ingesting two documents about the same person/event result in one merged node or two separate ones?
*   **SQL as a Reasoning Engine:** Using SQL queries over the graph for multi-hop QA. *Why needed:* Provides a transparent, auditable, and deterministic query language that natively supports graph traversal. *Quick check:* Can a complex question like "Who attended the meeting with Alice on Tuesday?" be expressed as a single, human-readable SQL query?
*   **Deterministic Deletion (DELETE CASCADE):** Using SQL's referential integrity to remove a fact and all its dependent edges. *Why needed:* Guarantees precise "forgetting" without leaving indirect traces, fulfilling a key privacy requirement. *Quick check:* After deleting a node, do all queries mentioning its relationships fail or return no results?

## Architecture Onboarding
**Component Map:**
Raw Multimodal Data (Text/Images) -> Small Vision-Language Model (Gemma-3n-E2b) -> Triple Extraction -> Entity Resolution & Leiden Clustering -> Personal Knowledge Graph (SQLite) -> SQL Query Engine -> Natural Language Answer
User Inspection/Deletion Interface -> Direct SQL Operations on PKG

**Critical Path:** The primary user flow is: 1) On-device VLM ingests new data into triples. 2) Triples are cleaned and merged into the PKG. 3) User asks a question, which is translated to an SQL query over the PKG. 4) Query results are formatted into an answer. 5) User can select any node/edge to delete, triggering a `DELETE CASCADE`.

**Design Tradeoffs:**
*   *Graph vs. Vector Store:* Gains in transparency, exact deletion, and interpretability at the potential cost of recall for semantic similarity searches and scalability with dense connections.
*   *Small VLM (Gemma-3n-E2b):* Enables on-dev operation but may limit extraction accuracy for complex or ambiguous documents compared to larger cloud models.
*   *SQL Reasoning:* Guarantees determinism but requires careful schema design and may be less flexible than learned graph neural networks for certain inference tasks.

**Failure Signatures:**
*   **Ingestion Failure:** VLM produces malformed triples or fails to extract key entities, leading to graph gaps.
*   **Entity Resolution Failure:** Incorrectly merges distinct entities or fails to merge identical ones, corrupting graph topology and causing query errors or wrong answers.
*   **Query Failure:** Complex multi-hop questions generate invalid or inefficient SQL, timing out or returning incomplete results.
*   **Deletion Incompleteness:** A deleted fact remains inferable through an alternative, non-cascaded path in a densely connected graph, violating the "forgotten" guarantee.

**First Three Experiments:**
1.  **Baseline Ingestion Test:** Ingest a simple, known document (e.g., a short bio with 5 facts). Verify the PKG contains exactly those 5 triples and no extra spurious ones. Inspect the generated SQL schema.
2.  **Simple Multi-Hop Query:** With a PKG containing `<Alice>` ` knows ` `<Bob>` and `<Bob>` ` works_at ` `<Company>`, execute the query "Where does Alice's friend work?" as SQL. Confirm it returns `<Company>`.
3.  **Cascade Deletion Test:** From the graph above, delete the edge `<Alice>` ` knows ` `<Bob>`. Re-run the query. Confirm it returns no result, demonstrating the dependent inference path is broken.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: How does RUVA's graph reasoning performance (accuracy, latency) scale as the Personal Knowledge Graph grows to millions of nodes and edges, which is typical for long-term, multi-year personal data aggregation?
- Basis in paper: [inferred] The paper benchmarks on a single device (Pixel 8 Pro) with a limited dataset (71 objects, 52 questions) and reports interactive latencies (2.4s ingestion, 38ms retrieval). It does not evaluate performance under realistic, long-term scaling conditions.
- Why unresolved: The "spiderweb" graph topology and N-hop traversal mechanism may face combinatorial explosion or SQLite performance degradation with large, dense graphs. The claimed interactive latencies are demonstrated only on a small, controlled benchmark.
- What evidence would resolve it: A benchmarking suite with synthetically generated PKGs of increasing scale (e.g., 10K, 100K, 1M nodes) measuring retrieval latency, memory footprint, and accuracy on a held-out set of complex multi-hop questions.

### Open Question 2
- Question: What is the quantitative impact and failure modes of the Entity Resolution and community detection (Leiden algorithm) on the integrity of the PKG when processing noisy, real-world multimodal data (e.g., ambiguous names, OCR errors, VLM hallucinations)?
- Basis in paper: [explicit] The paper states RUVA employs "an Entity Resolution strategy along with community detection" to prevent graph fragmentation. However, it provides no quantitative evaluation of this module's precision/recall or its error propagation into downstream reasoning.
- Why unresolved: Incorrect entity merging or splitting would corrupt the graph's topological structure, directly undermining the "Glass Box" reasoning guarantee. The paper treats this as a solved engineering detail without validation.
- What evidence would resolve it: A dedicated error analysis study on the entity resolution module, using a gold-standard, manually curated subset of ingested data to measure merge/split accuracy and its correlation with final answer correctness.

### Open Question 3
- Question: To what extent do the design choices of the specific Neural Component (Gemma-3n-E2b SVLM) limit the complexity and modality of information RUVA can reliably ingest and reason over, compared to more powerful but potentially larger models?
- Basis in paper: [explicit] The architecture explicitly uses a "Small Vision Language Model (SVLM, i.e., Gemma-3n-E2b)" for perceptual tasks, citing mobile constraints.
- Why unresolved: The paper does not ablate the choice of SVLM. A more accurate (but larger) model might improve triple extraction quality, especially for complex documents or images, potentially boosting overall reasoning performance. The trade-off between model capability and on-device feasibility is unexplored.
- What evidence would resolve it: An experimental comparison replacing Gemma-3n-E2b with models of varying sizes/capabilities (e.g., a larger VLMs), measuring changes in triple extraction F1-score, subsequent graph quality, and final Q&A accuracy, all while monitoring on-device resource usage.

### Open Question 4
- Question: How reliable and unbiased is the evaluation framework using multiple LLMs-as-judges (Prometheus-style) for assessing the "positive" rating (61%) of RUVA's answers, particularly for subjective or ambiguous personal queries?
- Basis in paper: [explicit] The paper uses four LLM judges (GPT, Kimi, Llama, Qwen) to score answers on a 5-point scale, mapping to Positive/Neutral/Negative. It reports strong inter-rater reliability (ρ=0.82, α=0.81).
- Why unresolved: LLM-as-a-judge frameworks are known to exhibit systematic biases (e.g., verbosity, self-preference) that may not align with human judgment of "correct" or "helpful" answers for personal, context-dependent queries. The high inter-LLM agreement could reflect shared biases rather than true answer quality.
- What evidence would resolve it: A human evaluation study where human raters (ideally the users themselves, in a user study) score the same benchmark questions. Correlation between human scores and the LLM-judge scores would validate the methodology. Discrepancies would require analyzing bias patterns in the LLM judges.

### Open Question 5
- Question: Does the deterministic SQL DELETE CASCADE deletion mechanism guarantee complete removal of a "fact" from all potential reasoning paths in a densely connected PKG, especially when the deleted node is only an indirect intermediary in a multi-hop inference chain?
- Basis in paper: [explicit] The paper claims deletion is "deterministic" and "mathematically" exact via SQL cascade, operationalizing the "Right to be Forgotten." The deletion test in Scenario 3 is a simple direct query.
- Why unresolved: The demonstration shows a direct query failing post-deletion. However, in a complex graph, a sensitive fact might be indirectly inferable from the remaining topology (e.g., via alternative paths or inferred properties). The guarantee of "forgetting" may only hold for explicitly stored triples, not for latent knowledge encoded in the graph structure itself.
- What evidence would resolve it: A formal analysis or empirical stress test of the deletion mechanism. Construct PKGs where a sensitive fact is an intermediate node in a necessary multi-hop path (e.g., A-[rel]->B-[rel]->C). Delete B, then query for the relationship between A and C. If the system can still infer it, true "forgetting" is compromised.

## Limitations
*   **Benchmark Opacity:** The 52-question benchmark's composition, source, and required reasoning depth (e.g., hop count) are undisclosed, preventing assessment of its difficulty and generalizability.
*   **Missing Baseline:** No direct comparison against a standard black-box vector-store RAG system on identical tasks, leaving the magnitude of RUVA's claimed advantages (accountability, privacy) unquantified.
*   **Scalability Unknown:** Performance metrics are reported for a limited dataset on one device. Behavior under realistic long-term scaling (thousands/millions of nodes, concurrent queries) is not evaluated.

## Confidence
*   **On-Device Graph Ingestion & Retrieval Performance (High):** Specific, device-named (Pixel 8 Pro) latency measurements (2.4s, 38ms) are concrete empirical results.
*   **Operational "Right to be Forgotten" via Deletion (High):** The described SQL `CASCADE` mechanism and its validation test (questions failing post-redaction) provide a clear, testable, and deterministic procedure.
*   **Benchmark Answer Quality (Medium):** The 61% "Positive" rating is supported by strong inter-rater reliability metrics (ρ=0.82, α=0.81), but confidence is reduced by the undisclosed benchmark and reliance on LLM judges for subjective personal queries.
*   **Graph Integrity via Entity Resolution (Low):** The critical entity resolution step is mentioned but quantitatively unevaluated; its impact on overall system correctness is a major unknown.

## Next Checks
1.  **Benchmark Audit:** Obtain and analyze the full 52-question set to verify complexity (e.g., multi-hop necessity), assess potential data leakage, and judge question appropriateness for personal context.
2.  **Controlled Comparative Baseline:** Re-implement a standard vector-store RAG using the same VLM for ingestion and the same LLM judge for evaluation. Compare answer quality, reasoning traceability, and deletion precision directly with RUVA.
3.  **Scalability Stress Test:** On the Pixel 8 Pro, ingest synthetic PKGs of increasing scale (e.g., 10K, 100K nodes). Measure ingestion throughput, multi-hop query latency distribution, and confirm `DELETE CASCADE` remains functionally correct and efficient at scale.
