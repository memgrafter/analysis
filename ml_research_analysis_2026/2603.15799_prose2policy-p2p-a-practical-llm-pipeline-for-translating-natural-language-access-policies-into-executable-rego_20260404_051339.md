# Prose2Policy (P2P): A Practical LLM Pipeline for Translating Natural-Language Access Policies into Executable Rego

## Quick Facts
- **arXiv ID:** 2603.15799
- **Source URL:** https://arxiv.org/abs/2603.15799
- **Reference Count:** 33
- **Primary Result:** Achieved a 95.3% compile rate for accepted policies on the ACRE dataset, with 82.2% positive-test and 98.9% negative-test pass rates, demonstrating syntactic robustness and behavioral consistency for Zero Trust environments.

## Executive Summary
Prose2Policy (P2P) addresses the critical gap between informal, natural-language access control policies and enforceable, version-controlled "policy-as-code" for Open Policy Agent (OPA). It introduces a modular LLM-based pipeline that translates plain-text policies into executable Rego. The system processes input through discrete stages: policy detection, structured component extraction (decision, subject, action, resource, condition, purpose), validation against organization-specific schemas, linting, Rego synthesis, and comprehensive unit testing. Evaluated on the ACRE benchmark, P2P demonstrated high syntactic success (95.3% compile rate) and strong behavioral validation, particularly in enforcing deny-by-default semantics (98.9% negative-test pass rate). The work provides a practical blueprint for automating policy code generation in Zero Trust and other fine-grained access control contexts.

## Method Summary
The pipeline operates as a sequential, validation-guarded workflow. It begins with preprocessing to identify and segment policy statements. An LLM then extracts the core DSARCP (Decision, Subject, Action, Resource, Condition, Purpose) components from each policy using constrained prompts. These extracted elements are validated against predefined JSON schemas containing an organization's valid entity values. Failed validation halts the process. Valid components feed into a Rego synthesis module, followed by linting with Regal and compilation via `opa build`. Finally, the system automatically generates both positive and negative unit test cases derived from the DSARCP elements and executes them with `opa test`. Failures at validation, lint, compile, or test stages break the flow, providing clear audit trails for administrator intervention.

## Key Results
- 95.3% compile rate for accepted policies on the ACRE dataset.
- 82.2% positive-test pass rate, indicating policies correctly permit intended actions.
- 98.9% negative-test pass rate, demonstrating strong denial of unintended accesses (deny-by-default).

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Modular prompt chaining with validation feedback reduces LLM hallucination and enforces structural validity for policy extraction and code generation.
- **Mechanism:** The pipeline decomposes translation into discrete stages (policy detection, element extraction, Rego synthesis), each guided by constrained prompts. Outputs from earlier stages feed into later ones, with failures halting the flow. Intermediate validation against schemas, linters, and compilers provides guardrails and audit trails.
- **Core assumption:** Unconstrained LLM outputs for complex policy translation are error-prone; intermediate validation and deterministic normalization improve reliability and interpretability.
- **Evidence anchors:** Abstract describes the modular pipeline; Section 3.1 details prompt chaining for intent identification, element extraction, and synthesis with schema constraints; related work shows multi-stage pipelines are common, but P2P uniquely integrates continuous validation.

### Mechanism 2
- **Claim:** Schema-governed component extraction anchors extracted DSARCP elements to organization-specific valid values, improving domain accuracy.
- **Mechanism:** After extracting policy components, the system validates them against predefined JSON schemas listing allowable values for each component (e.g., list of valid subjects, actions). Invalid or missing core components (subject, action, resource) stop the pipeline for admin review.
- **Core assumption:** LLMs lack inherent knowledge of an organization's specific entity taxonomies; external schemas are necessary to ground extracted elements in real-world valid sets.
- **Evidence anchors:** Section 4.3 formalizes the schema validation module and its role in stopping flow for missing/invalid crucial components; Section 2.2 cites prior work where LLMs extracted invalid entities, motivating this guardrail.

### Mechanism 3
- **Claim:** Automated unit test generation and execution verifies behavioral consistency (not just syntax) of generated Rego policies before deployment.
- **Mechanism:** The system auto-generates positive and negative test cases derived from the DSARCP components (e.g., a policy allowing "nurses read prescriptions" yields a positive test with nurse/read/prescription and a negative test with a different subject). Tests are executed via `opa test`, and failures indicate semantic gaps.
- **Core assumption:** Compilation success is insufficient; testing against intended allow/deny semantics is required for trustworthy enforcement.
- **Evidence anchors:** Section 5.3 describes the test generation and execution process; Section 6 reports the high negative-test pass rate (98.9%), demonstrating effective deny-by-default behavior.

## Foundational Learning
- **Concept: Attribute-Based Access Control (ABAC)**
  - *Why needed here:* P2P extracts DSARCP components, which map directly to ABAC's core model (subject, action, resource, condition). Understanding ABAC is necessary to interpret extracted elements and validate their logical relationships in Rego.
  - *Quick check:* In an ABAC policy "Managers can edit financial reports only during business hours," what is the condition attribute and what is the action?
- **Concept: Policy-as-Code (PaC)**
  - *Why needed here:* The paper's goal is to produce executable policy code (Rego) for OPA. PaC requires treating policies as versionable, testable software artifacts rather than static documents.
  - *Quick check:* Why is storing policies as code (PaC) preferable to embedding auth logic directly in application code for distributed systems?
- **Concept: LLM Prompt Engineering for Structured Output**
  - *Why needed here:* The pipeline relies on few-shot and program-of-thought prompting to extract structured JSON (DSARCP) from unstructured text. Prompt design directly impacts extraction reliability.
  - *Quick check:* How might a "chain-of-thought" or "few-shot" prompt improve the reliability of extracting multiple policy statements from a paragraph compared to a simple "extract the policy" prompt?

## Architecture Onboarding
- **Component map:** Pre-processor (policy detector, co-reference resolver, segmenter) -> Extractor (LLM-based DSARCP extractor) -> Validator (Schema validation, Regal linter) -> Generator/Tester (Rego synthesizer, OPA compiler, Test generator, Test executor)
- **Critical path:** Input text -> Pre-processing -> Extraction -> Schema Validation -> Rego Generation -> Linting -> Compilation -> Test Generation -> Test Execution. Failures at validation, lint, compile, or test stages break the flow.
- **Design tradeoffs:**
  - *Schema rigidity vs. coverage:* Strict schemas prevent invalid entities but require maintaining exhaustive value lists; wildcard/pattern support trades precision for scalability.
  - *LLM variability vs. determinism:* The pipeline accepts non-deterministic LLM outputs but uses validation guardrails; fully deterministic outputs would require canonical templates, reducing flexibility.
  - *Test generation mode:* LLM-based testing handles complex conditions better but is less predictable; rule-based is consistent but brittle for nested logic.
- **Failure signatures:**
  - *Pre-processing:* Over-aggressive segmentation splits compound policies.
  - *Extraction:* Missing purpose/condition; hallucinated resources/actions.
  - *Validation:* Component value not in schema; missing subject/action/resource.
  - *Rego generation:* Syntax errors not caught by linter; incorrect semantics (e.g., wrong default rule).
  - *Testing:* Positive-test failures indicate policy too permissive/restrictive; negative-test failures indicate policy too permissive (violates deny-by-default).
- **First 3 experiments:**
  1. **Baseline extraction:** Input "Admins can delete all user files." Verify DSARCP extraction yields `{decision: allow, subject: admins, action: delete, resource: user files}` and schema validation passes.
  2. **Schema rejection:** Change subject to "super-admins" (not in schema). Confirm processing stops at validation with a missing-entity error.
  3. **Test generation behavior:** Use "Users can view records during business hours." Compare LLM-based (may generate `input.time = "10:00"`) vs. rule-based (may only test `input.time` nil vs. non-nil) test generation for condition complexity.

## Open Questions the Paper Calls Out
- How does the pipeline generalize to diverse real-world policy corpora beyond the ACRE dataset?
- What is the operational cost of maintaining exhaustive, organization-specific JSON schemas for entity validation in dynamic environments?
- What is the coverage and robustness of the auto-generated unit test suite for policies with complex, nested conditional logic?
- How do specific prompt designs and few-shot examples impact extraction accuracy and consistency?
- What are the integration overhead and administrator feedback loop requirements for live Zero Trust deployment?

## Limitations
- Evaluation is confined to the ACRE dataset; generalization to diverse, ambiguous, or organization-specific policies is unproven.
- Reliance on predefined, exhaustive JSON schemas for entity values creates a significant operational and maintenance burden not addressed.
- The completeness and coverage of auto-generated unit tests for complex conditional logic remain an open question despite strong metrics.
- Prompt engineering details (exact prompts, few-shot examples, refinement process) are not fully disclosed, limiting reproducibility.

## Confidence
- **Pipeline Design & Syntactic Robustness (Compile Rate):** High (95.3% compile rate with staged validation).
- **Schema-Governed Extraction Accuracy:** Medium (logically sound but efficacy hinges on schema quality/completeness, which is variable).
- **Behavioral Validation via Unit Tests:** High (concrete metrics: 82.2% positive, 98.9% negative pass rates).
- **Generalization to Unseen Domains/Organizations:** Low (success heavily dependent on schema availability and accuracy, untested).

## Next Checks
1. **Cross-Dataset Generalization:** Re-run evaluation on at least two other established policy-to-code datasets to measure performance decay and identify specific failure modes outside the ACRE distribution.
2. **Schema Evolution Stress Test:** Simulate a dynamic environment by incrementally adding, renaming, and deprecating values in the JSON schemas. Measure the pipeline's failure rate and manual admin intervention required.
3. **Ablation Study on Test Generation:** Isolate and compare the "LLM-based" vs. "rule-based" test generation modes on a holdout set with nested conditions and temporal logic. Quantify differences in test suite coverage (e.g., Rego branch/condition coverage) and correlated pass rates.
