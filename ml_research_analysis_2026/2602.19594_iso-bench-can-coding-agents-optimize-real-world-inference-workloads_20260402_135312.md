# ISO-Bench: Can Coding Agents Optimize Real-World Inference Workloads?

## Quick Facts
- **arXiv ID:** 2602.19594
- **Source URL:** https://arxiv.org/abs/2602.19594
- **Reference Count:** 40
- **Primary Result:** Coding agents frequently identify correct bottlenecks but fail to implement working solutions, revealing an understanding-execution gap; hard metrics alone overestimate success by 10–20% due to lucky wins, and agent scaffolding significantly impacts performance.

## Executive Summary
ISO-Bench evaluates coding agents on 54 real-world inference optimization tasks from vLLM and SGLang. The benchmark uses a dual-metric approach: hard metrics (TTFT, throughput) measure performance gains, while soft metrics (LLM-as-a-judge) assess whether patches target the intended bottleneck. Results show agents often comprehend the optimization goal but cannot implement a correct solution, a phenomenon termed the "understanding-execution gap." Relying solely on hard metrics is misleading, as accidental speedups (lucky wins) inflate success rates. Moreover, agent scaffolding—the structured workflow and tool use—exerts a stronger influence on performance than the underlying model, as identical models achieve divergent success rates across codebases. No single agent dominates both vLLM and SGLang, highlighting poor generalization.

## Method Summary
The benchmark constructs tasks from merged pull requests in vLLM (39 tasks) and SGLang (15 tasks). Each task provides a repository snapshot at the pre-optimization commit, a natural-language bottleneck description, and benchmark commands. Agents (Claude Code, Codex CLI, TRAE-Agent with Claude Sonnet 4.5 or GPT-5) run in isolated Docker containers with an H100 GPU and a 120-minute time limit. Evaluation first measures hard metrics by rerunning benchmarks to compute TTFT and throughput deltas. Then, an LLM judge (Gemini-3-Flash-Preview) evaluates the agent's patch against the human reference patch, classifying bottleneck targeting (same/related/different) and implementation approach (similar/valid/partial/ineffective). Hard and soft scores are cross-tabulated into four quadrants: Q1 (True Success), Q2 (Good Intent, Bad Execution), Q3 (Lucky Win), Q4 (Missed Target). Functional correctness is verified via LM Eval Harness for hard-success cases.

## Key Results
- Agents exhibit a consistent "understanding-execution gap," with Q2 (correct bottleneck, failed implementation) as the most frequent outcome on vLLM for three of four agents.
- Hard metrics overestimate true optimization capability by 10–20% by counting lucky wins (Q3), where speedups arise from unrelated code changes.
- Agent scaffolding profoundly shapes performance; identical models (Claude Sonnet 4.5) in TRAE-Agent and Claude Code show inverted rankings between vLLM (46.2% vs 28.2%) and SGLang (26.7% vs 80.0%), and adopt divergent strategies.

## Why This Works (Mechanism)
### Mechanism 1
The quadrant framework isolates an understanding-execution gap by disentangling *what* the agent targets (soft metric) from *how well* it performs (hard metric). Each task pairs with a human-intended bottleneck; LLM judges approximate whether the agent's patch aligns with that intent. The cross-tabulation yields four outcomes. A high frequency of Q2 indicates agents grasp the goal but fail to implement a working solution. Core assumption: the task prompt and human commit define ground-truth intent. Evidence: Q2 dominates on vLLM across agents; the framework explicitly defines Q2 in section 3.3.3.

### Mechanism 2
Hard metrics alone systematically overestimate capability because they cannot distinguish lucky wins (Q3) from true successes (Q1). An agent may achieve a speedup by modifying code regions unrelated to the stated bottleneck (e.g., altering model behavior or caching), which incidentally improves benchmark performance. Soft metrics detect this misalignment by comparing the agent's target to the human's. Core assumption: incidental speedups do not reflect the ability to solve the stated optimization problem. Evidence: abstract and section 5.2 quantify a 10–20% gap between Hard Success and True Success.

### Mechanism 3
Agent scaffolding—the structured workflow, tools, and iterative loop—is a primary determinant of performance, explaining why identical models diverge across codebases. Comparing Claude Code vs. TRAE-Agent (both using Claude Sonnet 4.5) shows starkly different True Success rates and approach distributions (e.g., TRAE mimics human solutions, Claude Code uses alternatives). Scaffolding dictates how an agent explores, decomposes tasks, tests hypotheses, and interprets errors, thus shaping its problem-solving trajectory. Core assumption: model capability is necessary but insufficient; the agent's execution policy is crucial. Evidence: abstract and section 5.5 directly attribute performance differences to scaffolding choices.

## Foundational Learning
- **Concept: Repository-Level Optimization vs. Function-Level Code Generation**  
  *Why needed:* ISO-Bench tasks require navigating multi-file codebases to locate and patch specific bottlenecks, unlike single-function benchmarks (e.g., HumanEval). This adds complexity in code comprehension, localization, and multi-file coordination.  
  *Quick check:* Name three challenges when optimizing `vllm/attention/backends/flash_attn.py` absent in HumanEval.

- **Concept: Dual-Metric Evaluation (Hard vs. Soft)**  
  *Why needed:* Relying solely on execution metrics (throughput) is gameable. Understanding the distinction between *performance change* and *targeted optimization* is core to interpreting the quadrant framework and the understanding-execution gap.  
  *Quick check:* Provide an example of a "Lucky Win" (Q3) in ISO-Bench and explain why it is not a true optimization.

- **Concept: Agent Scaffolding and Workflow**  
  *Why needed:* The paper's key conclusion is that *how* an agent works (tools, loop, stopping condition) matters as much as the model. An "agent" is an orchestrated system, not just an LLM.  
  *Quick check:* Describe a specific behavioral difference between Claude Code and TRAE (Sonnet) that explains their opposite rankings on vLLM vs. SGLang.

- **Concept: Contamination Risk in Code Benchmarks**  
  *Why needed:* Agents may have seen similar optimization patterns during pre-training, inflating performance. Recognizing this risk is essential for interpreting results and designing robust probes.  
  *Quick check:* How could paraphrasing the bottleneck description help detect memorization?

## Architecture Onboarding
Task Source -> Agent Interface -> Evaluation Pipeline -> Quadrant Classifier -> Analysis Module

**Critical path:** Tasks are extracted from merged PRs, manually curated with bottleneck descriptions, run through agents in Docker with 120-minute budgets, evaluated via hard metrics (benchmarks) and soft metrics (LLM judge), classified into quadrants, and aggregated.

**Design tradeoffs:**  
- Hard vs. Soft Metrics: Hard metrics are objective but incomplete; soft metrics add intent detection but introduce LLM-judge bias and cost.  
- Single vs. Multi-Codebase: Two repositories reveal generalization issues but limit statistical power; more repos increase curation cost.  
- Localized vs. Systemic Tasks: Filtering to <10 files ensures patch-sized tasks but excludes large-scale architectural optimizations.

**Failure signatures:**  
- Q2 Dominance: Correct targeting but buggy/non-functional patches—weak code generation/debugging.  
- Q4 Prevalence: Missed target—failure in code comprehension/search.  
- Scaffolding Sensitivity: Same model, different agent → opposite rankings—mismatched exploration/exploitation strategy.  
- OSS Failure Modes (Appendix D.5–D.7): Infinite planning loop, environment confusion (reimplementing deps), task completion failure.

**First 3 experiments:**  
1. Replicate Quadrant Analysis: Implement the full pipeline on 5 tasks (2 vLLM, 2 SGLang, 1 new repo). Verify that TRAE produces similar Q1/Q2 distributions as in the paper (anchor: Section 3.3.3 & Table 5).  
2. Scaffolding Swap Experiment: Take Claude Code's successful vLLM Q1 trajectories. Replay them using TRAE-Agent scaffolding with the same Claude Sonnet 4.5 model. Does success rate drop to TRAE's level? Tests trajectory-dependence vs. model-dependence.  
3. Contamination Probe: For a sample of tasks, paraphrase the bottleneck description (preserving meaning) and re-run one agent. Does True Success rate drop significantly? Tests for memorization of task descriptions from training data (anchor: Limitations).

## Open Questions the Paper Calls Out
- **Why do coding agents correctly identify bottlenecks but fail to implement working solutions?** The paper shows many Q2 cases but does not analyze specific error types or agent reasoning steps leading to failed patches. A detailed error taxonomy with trace inspection is needed.
- **Why does agent performance and strategy vary dramatically across vLLM and SGLang?** Rankings invert (e.g., TRAE excels on SGLang but not vLLM) and approach distributions differ, but the paper offers no explanation. Correlating outcomes with codebase attributes or controlled transfer experiments could resolve this.
- **How reliable are the LLM-as-judge soft metrics, and do they align with human expert assessments?** Soft metrics rely on a single LLM judge and lack validation against human annotators, posing potential bias. Human annotation of patches with agreement metrics (e.g., Cohen’s kappa) would quantify reliability.

## Limitations
- Proprietary agent black boxes (Claude Code, Codex CLI) prevent precise replication due to unreleased system prompts and tool definitions.
- Environmental variance (CUDA/driver versions, Docker layers) introduces performance measurement noise not fully specified.
- Dataset scale is limited: 54 manually curated tasks from only two repositories (vLLM, SGLang), restricting generalizability.
- LLM-as-judge reliability is unvalidated; contamination risks from pre-training data are acknowledged but not quantified.

## Confidence
- Understanding-Execution Gap Exists: **High** (quadrant analysis directly and consistently shows Q2 dominance across agents on vLLM).
- Hard Metrics Overestimate Success: **Medium-High** (10–20% gap is compelling but may be sensitive to thresholds and LLM-judge classification).
- Scaffolding is Primary Determinant: **Medium** (divergence for identical models is strong evidence, but confounding variables (stochastic variance, subtle prompt differences) may contribute).
- No Agent Dominates Cross-Codebase: **High** (ranking shifts are clearly demonstrated in results tables).

## Next Checks
1. **Cross-Repo Replication:** Run the full pipeline on a new inference codebase (e.g., HuggingFace Transformers or TensorRT-LLM) to test whether Q2 dominance and scaffolding sensitivity generalize beyond vLLM/SGLang.
2. **Controlled Scaffolding Ablation:** Implement an open-source agent framework (e.g., based on OpenHands) and vary one scaffolding component at a time (tool set, planning frequency, error recovery) while holding the model constant to isolate drivers of performance differences.
3. **LLM-Judge Calibration Study:** Conduct human evaluation on a stratified patch sample and compute agreement metrics (e.g., Cohen’s kappa) with Gemini-3-Flash-Preview scores to quantify soft metric reliability and identify biases.
