# Polaris: A Gödel Agent Framework for Small Language Models through Experience-Abstracted Policy Repair

## Quick Facts
- arXiv ID: 2603.23129
- Source URL: https://arxiv.org/abs/2603.23129
- Reference count: 40
- Primary result: Polaris with Qwen2.5-7B consistently outperforms base policy and chain-of-thought self-consistency, achieving gains of +3.6-5.7% on arithmetic/compositional tasks and up to +9.0% on graduate-level QA and creative writing.

## Executive Summary
Polaris introduces a framework for recursive self-improvement in small language models (7B–8B parameters) by addressing the memory‑intensive nature of Gödel agents. Its core innovation is experience abstraction: failures are distilled into compact, reusable strategies that generate minimal code patches, integrated with conservative checks. The agent cycles through failure analysis, strategy synthesis, patch generation, and policy update, keeping context small by retaining only a few failed examples and reduced tool history. Evaluations on MGSM, DROP, GPQA, and LitBench show consistent improvements over base policies and chain-of‑thought self-consistency, with gains up to +9.0%. The updates are small, auditable, and reusable, enabling traceable post‑deployment improvement without full retraining.

## Method Summary
Polaris implements a Gödel Agent that repeatedly evaluates its current policy (a Python `solver` function) on a validation set, identifies failures, and repairs the policy via a four‑step cycle. First, each failure is analyzed to produce a structured reflection (diagnosis, revision, prevention). Second, reflections are abstracted across multiple failures into 1–2 generalizable repair strategies. Third, each strategy is rendered as a minimal code patch. Fourth, patches are integrated into the policy via runtime code mutation with syntax validation and retry limits. Memory is constrained: only a small number of failed instances (N=3 or 5) and a limited tool‑call history (six messages) are retained to prevent context explosion. This allows recursive self‑improvement even under tight compute constraints of small models.

## Key Results
- On MGSM, DROP, GPQA, and LitBench, Polaris with Qwen2.5-7B achieves gains of +3.6-5.7% on arithmetic and compositional tasks, and up to +9.0% on graduate‑level QA and creative writing, outperforming the base policy and chain‑of‑thought self‑consistency.
- With Qwen3-8B, Polaris maintains high success rates across datasets, demonstrating scalability to slightly larger models.
- Policy updates are minimal (line‑level changes), auditable, and reusable, enabling traceable improvements without full retraining.

## Why This Works (Mechanism)
Polaris succeeds through three interconnected mechanisms:

1. **Cumulative policy refinement via experience abstraction**: Failures are transformed into transferable strategies. The cyclical process—failure analysis, strategy synthesis, patch generation, and integration—converts instance‑specific errors into persistent, auditable updates. Core assumption: SLMs can meta‑reason to abstract general principles and generate syntactically correct patches when guided by structured prompts and constrained context. Break condition: If strategies become redundant or patches fail syntactic/execution checks beyond retries, the cycle aborts.

2. **Controlled memory management**: By limiting the number of failed instances (N=3 or 5) and retaining only six tool‑call messages, context growth is bounded, preventing out‑of‑memory errors that plagued the original Gödel Agent. Core assumption: A small, high‑quality set of failures suffices for synthesizing reusable strategies. Break condition: Setting N too low yields overfitted strategies; too high risks OOM; verbose logs can still saturate context.

3. **Minimal, auditable code patches**: Patches modify only necessary lines, excluding explanatory text, and are validated for syntax before integration. This locality preserves interpretability and reduces risk of catastrophic edits. Core assumption: Small surgical edits are sufficient for measurable gains and conservative validation prevents policy corruption. Break condition: Patches with subtle logic bugs may degrade performance if they pass syntax checks but fail later.

## Architecture Onboarding
**Component map**: 
Memory -> SELF_INSPECT -> EVALUATE -> REPAIR_POLICY -> (AnalyzeFailure -> StrategySynthesis -> PatchGeneration -> IntegratePatch) -> UpdatePolicy -> Memory -> solver -> EVALUATE

**Critical path**:
1. Agent executes `solver` on validation set, collects failed tasks `T`.
2. `REPAIR_POLICY` invoked: for each τ in `T`, call `AnalyzeFailure` → store reflection `A_i`.
3. `StrategySynthesis` abstracts `{A_i}` into 1–2 novel strategies `δ`.
4. `PatchGeneration` creates minimal code patch `p` from `δ`.
5. `IntegratePatch` applies `p` to current policy `π_t` via `UpdatePolicy` with retries.
6. Loop returns to step 1 with updated policy `π_{t+1}`.

**Design tradeoffs**:
- Reflection depth (`N`) vs. memory/performance: Larger `N` yields robust abstractions but increases OOM risk; `N=5` generally outperforms `N=3` but with higher failure rate.
- Patch minimality vs. expressivity: Small patches are auditable but may require multiple cycles to encode complex logic.
- Conservative integration vs. exploration: Retry limits and syntax checks prevent corruption but may discard beneficial patches that fail early validation.

**Failure signatures**:
- Out-of-memory (OOM) errors due to context growth.
- Malformed tool calls (invalid JSON, missing fields).
- Patch integration errors (syntax/runtime) after retries.
- Non‑progressive repairs (no validation improvement).
- Agent hallucinates non‑existent tools.

**First 3 experiments**:
1. **Baseline replication**: Run Gödel Agent (Yin et al., 2024) with Qwen2.5‑7B under same memory constraints (`N=3`, `N=5`). Expect near‑total failure due to OOM.
2. **Polaris `N=3` vs. `N=5`**: For each dataset, run 10 independent cycles with `N=3` and `N=5`. Track success rate, maximum improvement over COT‑SC, and iteration count. Expect `N=5` higher gains but more unsuccessful runs.
3. **Model scaling test**: Run Polaris with `N=3` on Qwen3‑8B. Expect higher success rate and steady gains but fewer iterations due to longer token generation.

## Open Questions the Paper Calls Out
1. **Eliminating prompt template dependency**: Can automated prompt template generation replace handcrafted ones? Unresolved because handcrafted templates limit scalability; evidence would be an automated component matching handcrafted performance.
2. **Stabilizers for failure reduction**: Can rollbacks, stronger validation, and memory management reduce OOM and hallucinations? Unresolved because current runs often fail; evidence would be a suite of stabilizers significantly lowering failure rates.
3. **Escaping performance plateaus**: Can richer mutation operators, diverse abstraction schemes, or longer runs sustain improvement? Unresolved because plateaus observed; evidence would be extended experiments showing continued gains beyond plateaus.
4. **Open‑ended learning applicability**: Can Polaris adapt to dynamic environments with evolving tools/tasks? Unresolved because evaluations are on static benchmarks; evidence would be deployment in a non‑stationary environment with sustained self‑improvement.

## Limitations
- Initial `solver` code and base performance are unspecified, making replication and comparison uncertain.
- Tool‑call interface format (JSON structure) is ambiguous; mismatches can cause execution failures.
- DROP evaluation details (exact span matching) are not provided; approximations may misreport scores.
