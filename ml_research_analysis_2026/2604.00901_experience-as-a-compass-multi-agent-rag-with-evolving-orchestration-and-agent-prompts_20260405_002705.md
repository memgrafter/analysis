# Experience as a Compass: Multi-agent RAG with Evolving Orchestration and Agent Prompts
## Quick Facts
- **arXiv ID**: 2604.00901
- **Source URL**: https://arxiv.org/abs/2604.00901
- **Reference count**: 40
- **Primary result**: HERA achieves an average F1 improvement of 38.69% over state-of-the-art baselines, reaching up to 67.81% F1 on AmbigQA while using only 4.7k–6.6k tokens per query.

## Executive Summary
HERA is a hierarchical multi-agent RAG framework that evolves both global orchestration (agent topologies) and individual agent prompts without gradient-based updates. It addresses brittleness in static multi-agent pipelines by using an experience library to store semantic insights from successful and failed trajectories, guiding future topology sampling and prompt refinement. Evaluations on six knowledge-intensive QA benchmarks show substantial gains (average F1 +38.69% over baselines) with low token usage, and strong out-of-distribution generalization.

The system comprises an orchestrator that retrieves insights from an experience library to sample agent topologies, a pool of specialized agents with role-specific prompts, and a Role-aware Prompt Evolution (RoPE) module that refines underperforming agents’ prompts by extracting operational rules and behavioral principles from failure analysis. The experience library is managed via consolidation operations (ADD/MERGE/PRUNE/KEEP) to maintain utility and diversity. Token usage declines after an initial exploration phase as efficient topologies emerge, and topology analyses reveal compact, high-utility networks with strategic cycles.

## Method Summary
HERA introduces a hierarchical framework for multi-agent retrieval-augmented generation that evolves both the global coordination structure (agent topologies) and individual agent prompts without gradient-based training. For each query, an orchestrator consults an experience library containing curated semantic insights from past trajectories to sample an effective agent topology (e.g., ordering of specialized roles like decomposer, retriever, generator). Agents execute the topology, and the orchestrator performs group-based comparison of multiple candidate topologies to extract new insights, which are added to the library. Agents flagged as underperforming undergo Role-aware Prompt Evolution (RoPE), which generates prompt variants along axes like thoroughness, re-executes trajectories, and isolates operational rules (immediate fixes) and behavioral principles (long-term strategies) to refine prompts. The experience library is managed via consolidation operations (ADD/MERGE/PRUNE/KEEP) to control growth and maintain generalizability. This design enables continuous adaptation with frozen LLMs, achieving strong performance gains and token efficiency.

## Key Results
- Average F1 improvement of 38.69% over state-of-the-art baselines across six benchmarks; peak 67.81% F1 on AmbigQA.
- Token-efficient operation: only 4.7k–6.6k tokens per query, with consumption declining after initial exploration.
- Strong out-of-distribution generalization: ranks first on HoVer with +64.95% over CORAG.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** HERA evolves effective global agent coordination topologies without gradient-based updates by distilling comparative semantic insights from groups of successful and failed trajectories.
- **Mechanism:** For a given query, the orchestrator samples a group of candidate agent topologies. After execution, trajectories are ranked by task performance (e.g., F1) and token efficiency. The orchestrator performs a reflective analysis on groups containing both successes and failures to extract natural language "semantic advantages"—insights about what specific agent selections, orders, or dependencies led to success. These curated insights are stored in the experience library and retrieved to condition future topology sampling, biasing the orchestrator toward high-performing, efficient structures.
- **Core assumption:** Semantic, natural-language comparisons between trajectories of varying quality can distill generalizable, actionable strategies for agent coordination that are more interpretable and stable than scalar reward gradients.
- **Evidence anchors:**
  - [abstract] "its hierarchical framework simultaneously evolves (1) global agent topologies via reward-guided experience retrieval without gradient-based updates"
  - [section 3.1] "We adopt a hierarchical comparison: trajectories are first ranked by downstream task performance... These semantic advantages encode structured knowledge about effective reasoning strategies... effectively replacing numerical gradients with interpretable and compositional signals."
  - [corpus] Weak direct evidence; neighboring papers discuss other orchestrators but not the specific gradient-free semantic distillation mechanism.
- **Break condition:** The mechanism degrades if reward signals (F1/token counts) are too noisy or sparse to form clear success/failure dichotomies for group comparison, or if the set of candidate topologies in a group lacks sufficient diversity to reveal strategic differences.

### Mechanism 2
- **Claim:** RoPE (Role-aware Prompt Evolution) improves individual agent performance by systematically extracting and integrating two complementary types of behavioral corrections: short-term operational rules from recent failures and long-term behavioral principles from cross-trajectory patterns.
- **Mechanism:** For an agent flagged as underperforming by the orchestrator, RoPE retrieves its recent failed trajectories. It generates prompt variants along behavioral axes (e.g., thoroughness, risk sensitivity), re-executes the original trajectory with each variant, and performs a contrastive analysis between successful and failed variant executions. This analysis isolates (i) `∆ρ_op` (concrete, immediate corrective instructions) and (ii) `∆ρ_bp` (general strategic principles). These are projected onto the agent's prompt under length/coherence constraints, inducing a policy shift `π_new(y|x) ∝ π_base(y|x) * exp(f_ρ(x,y))` for the frozen LLM.
- **Core assumption:** Failure attribution to a specific agent by the orchestrator is sufficiently accurate, and the contrastive re-execution of prompt variants can isolate the specific role-specific behaviors that causally contributed to the failure.
- **Evidence anchors:**
  - [abstract] "Role-aware Prompt Evolution (RoPE). RoPE identifies underperforming agents and refines their prompts by extracting operational rules (short-term corrections) and behavioral principles (long-term strategies) from failed trajectories."
  - [section 3.4.1] "RoPE addresses this by targeting agents identified as underperforming by the orchestrator... perform contrastive analysis to extract actionable improvements along two complementary dimensions: (i) operational rules... (ii) behavioral principles."
  - [section 3.4.1] "Formally, the prompt update can be decomposed as: ∆ρ_i = ∆ρ_op_i + ∆ρ_bp_i"
- **Break condition:** The mechanism fails if the orchestrator consistently misattributes failures (e.g., blaming a correct agent due to complex inter-agent dependencies), or if the behavioral axes for variant generation do not cover the actual failure mode, leading to ineffective or contradictory prompt updates.

### Mechanism 3
- **Claim:** Topology mutation provides a structural fallback to escape persistent failure modes by replacing or augmenting agents in a failing topology, which is then optimized via the same GRPO loop.
- **Mechanism:** When the orchestrator identifies trajectories with catastrophic failure (e.g., F1=0), it triggers topology mutation. For each failed agent, it explores two structural modifications: (1) replacing the agent with an alternative from the pool, or (2) inserting a new specialized agent into the dependency chain. These candidate topologies are fed back into the GRPO-style sampling and evaluation loop, allowing the system to discover fundamentally different coordination patterns.
- **Core assumption:** A subset of persistent failures is attributable to a suboptimal or missing agent role in the current topology, rather than solely to the quality of the existing agents' prompts or the orchestrator's selection.
- **Evidence anchors:**
  - [section 3.5] "To address this, HERA performs topology mutation when trajectories consistently fail (e.g., F1 = 0)... These candidates are then incorporated into the same gradient-free GRPO optimization loop. This process enables the co-evolution of coordination structure and agent behaviors."
  - [section 2, problem formalization] The system tuple includes a set of agents N, implying a fixed pool from which replacements can be drawn.
  - [corpus] No direct anchor; this is a specific design choice of HERA not widely mirrored in neighboring papers.
- **Break condition:** The mechanism is ineffective if the agent pool N lacks a suitable specialist for the required role, or if the mutation space (replace/augment) is too limited to discover a viable alternative topology. It also risks infinite exploration if not coupled with the experience library's consolidation.

## Foundational Learning
### Concept: Multi-Agent RAG Pipelines
- **Why needed here:** HERA builds upon the paradigm of decomposing complex QA into specialized agent roles (Query Decomposer, Retriever, Answer Generator, etc.). Understanding the static, sequential baselines (e.g., IRCoT, SELF-RAG) is prerequisite to appreciating HERA's dynamic evolution.
- **Quick check question:** In a standard multi-hop RAG pipeline, what is the typical flaw that causes error propagation, and how does HERA's dual-level evolution aim to mitigate it?

### Concept: Gradient-Free Policy Optimization (GRPO-inspired)
- **Why needed here:** HERA's orchestrator does not update LLM weights. It relies on group-based comparison of topology candidates and extracting semantic insights instead of numerical policy gradients. This is a core shift from training-based multi-agent RL.
- **Quick check question:** How does the "hierarchical comparison" (ranking by F1 then tokens) and subsequent natural language insight extraction serve as a substitute for policy gradients in the orchestrator's learning loop?

### Concept: Experience Replay and Consolidation
- **Why needed here:** The experience library (`E`) is the persistent memory that enables generalization across queries. Its operations (ADD/MERGE/PRUNE/KEEP) are critical for managing insight growth and utility. Understanding non-parametric memory as a learning medium is key.
- **Quick check question:** Why is the PRUNE operation necessary for maintaining the generalizability of the experience library, and what triggers it (e.g., conflicting insights)?

## Architecture Onboarding
- **Component map:** 
  - **Top Layer:** Orchestrator (LLM) – queries experience library, samples agent topology Γ.
  - **Middle Layer:** Experience Library (`E`) – stores `(profile c, insight z, utility u)` entries. Managed via consolidation operations. Retrieved based on query profile similarity and diversity/utility balance.
  - **Bottom Layer:** Agent Pool (`N`) – each agent `N_i = (π_i, ρ_i, T_i)`. `π_i` (LLM) and `T_i` (tools) fixed. `ρ_i` (prompt) evolves via RoPE.
  - **Process Loop:** (1) `ORCHESTRATE(q, E, N)` → Γ. (2) `EXECUTE(Γ, q, D)` → τ. (3) `ORCHESTRATORUPDATE()` – group rollouts, extract insights `I`. (4) `EXPERIENCELIBRARYUPDATE(E, I)`. (5) `IDENTIFYFAILEDAGENTS(τ)` → trigger `ROPE(N_i)` for each. (6) Persistent failures → `TOPOLOGYMUTATION()`.

- **Critical path:** A query's lifecycle: `Characterize Query → Retrieve Insights from E → Orchestrator generates Γ → Agents execute sequentially/parallel per Γ → Trajectory evaluated → If mixed outcomes in group, extract new insights → Update E → If specific agents fail, run RoPE → If catastrophic failure, mutate topology`. The experience library is the central repository updated after every group evaluation and consulted before every orchestration.

- **Design tradeoffs:**
  - **Gradient-free vs. Sample Efficiency:** Explicit topology sampling and re-execution are computationally heavy per query but avoid costly offline RL training. The token usage analysis shows an initial exploration spike that declines as useful topologies are consolidated in `E`.
  - **Centralized Orchestrator vs. Distributed Control:** A single orchestrator enables holistic topology design but creates a bottleneck and single point of attribution failure. RoPE relies on the orchestrator's correct identification of underperforming agents.
  - **Prompt Evolution vs. Model Fine-tuning:** Prompt evolution is cheap and continuous but is limited by the base LLM's capabilities and may introduce prompt length/coherence constraints. It cannot fundamentally change the agent's knowledge.

- **Failure signatures:**
  - **Token Explosion (Figure 3):** Sustained high token consumption without later decline suggests the experience library is not accumulating high-utility insights or the orchestrator is not converging on efficient topologies.
  - **Low Node Efficiency (Figure 6):** Flat or declining `F1(τ)/|V|` during refinement phase indicates agents are being added without improving per-agent contribution, or prompts are not improving role-specific utility.
  - **High Transition Entropy without Plateau (Figure 5):** Entropy remains high or volatile, suggesting the system is not consolidating stable coordination patterns; the experience library may be too volatile or not discriminative enough.
  - **Ablation Sensitivity:** Large performance drop when removing `RoPE` on multi-hop datasets (Figure 2) indicates prompt evolution is critical for procedural correctness; drop when removing `E` suggests poor cross-instance generalization.

- **First 3 experiments:**
  1. **Single Query Debugging:** Run HERA on one carefully chosen query from the training set. Log the retrieved insights from `E`, the sampled topology Γ, the full trajectory τ, and the orchestrator's generated semantic advantages. Manually verify if the insight correctly explains the topology's success/failure. This validates the insight extraction pipeline.
  2. **Group Rollout Analysis:** For a batch of queries, deliberately sample a group of topologies with intentionally mixed quality (e.g., force a bad topology). Confirm that the `ORCHESTRATORUPDATE` step only proceeds when the group has explicit success/failure pairs, and inspect the `I` produced. Check if `I` is specific (mentions agents/order) and generalizable (query-type agnostic where possible).
  3. **RoPE Trigger Simulation:** Take a known failing trajectory from the log. Force the orchestrator to tag a specific agent as underperforming. Run the `ROPE` procedure: retrieve its failure buffer, generate and re-execute variants. Analyze the `operational_rules` vs. `behavioral_principles` extracted. Did the rules directly address the observed error? Did principles suggest a broader strategy? Verify the `updated_prompt` is coherent and shorter than the sum of parts due to `Π_C` projection.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Can HERA autonomously discover novel agent roles, and what is the performance impact?
- **Basis in paper:** [explicit] Future work identifies "meta-optimization of agent roles".
- **Why unresolved:** The current framework uses predefined roles; automatic discovery mechanisms are absent.
- **What evidence would resolve it:** Evaluate HERA on multi-hop QA with a role discovery module (e.g., clustering agent behaviors) and measure accuracy changes versus fixed roles.

### Open Question 2
- **Question:** How can HERA incorporate online adaptation of agent topologies across multiple turns?
- **Basis in paper:** [explicit] Conclusion suggests "adaptive multi-turn orchestration".
- **Why unresolved:** Orchestrator produces a single static topology per query; dynamic re-planning may be needed for interactive tasks.
- **What evidence would resolve it:** Implement a re-planning trigger in HERA and test on tasks requiring iterative feedback, comparing success rates and token usage.

### Open Question 3
- **Question:** Can token usage be directly constrained in HERA's experience-guided sampling and prompt evolution?
- **Basis in paper:** [inferred] HERA shows emergent token reduction but lacks explicit budget enforcement.
- **Why unresolved:** Missing hard constraints limit deployment in resource-sensitive applications.
- **What evidence would resolve it:** Add a token penalty or budget cap to the reward; evaluate accuracy vs. token consumption trade-offs under strict budgets.

### Open Question 4
- **Question:** How does temporal decay of experience entries affect HERA under non-stationary query distributions?
- **Basis in paper:** [inferred] The experience library accumulates insights without considering staleness.
- **Why unresolved:** Without decay, outdated insights may harm performance when data evolves.
- **What evidence would resolve it:** Simulate distribution shift (e.g., time-split data) and compare HERA with/without utility decay and pruning strategies over adaptation speed.

## Limitations
- Hyperparameters for GRPO sampling (group size, temperature) and experience library operations (similarity metric, utility update rule, diversity criterion) are underspecified, risking reproduction variance.
- Orchestrator’s accuracy in identifying underperforming agents is critical for RoPE; misattribution due to complex inter-agent dependencies could cause ineffective or harmful prompt updates.
- Token efficiency convergence relies on effective experience consolidation; if semantic insights become noisy or contradictory, exploration may not decline.
