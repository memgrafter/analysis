# Any Model, Any Place, Any Time: Get Remote Sensing Foundation Model Embeddings On Demand

## Quick Facts
- arXiv ID: 2602.23678  
- Source URL: https://arxiv.org/abs/2602.23678  
- Reference count: 17  
- Primary result: rs-embed provides a unified library for on-demand retrieval of embeddings from any remote sensing foundation model, enabling cross-model comparison and large-scale batch processing.

## Executive Summary
The rs-embed library addresses the fragmentation in remote sensing foundation models (RSFMs) by offering a single, region-of-interest-centric interface. With one line of code, users can obtain embeddings from any supported model for any location and time, abstracting away data acquisition and model inference complexities. This unification facilitates fair comparison of diverse RSFMs and supports efficient batch generation for large-scale studies. The authors demonstrate the system's capability through a maize yield regression across 16 models and a spatial embedding visualization, revealing both the predictive power and the representational diversity of existing RSFMs.

## Method Summary
rs-embed introduces two abstraction layers: the Provider Layer normalizes access to satellite data sources (e.g., Google Earth Engine) into consistent `(C, H, W)` tensors, while the Embedder Layer wraps heterogeneous model architectures behind a common interface. Users specify a spatial region, time range, and model identifier; the library then handles data fetching, preprocessing, inference, and output formatting (pooled or grid). A parallel pipeline (orchestration, prefetch, inference, export) maximizes resource utilization. Validation occurs via two experiments: (1) pooled embeddings for 991 Illinois fields (2019 growing season) predict maize yield with a Random Forest, comparing R² across 16 RSFMs; (2) grid embeddings for a fixed region are visualized via PCA to reveal variations in spatial feature representations.

## Key Results
- Agrifm achieved the highest R² in the maize yield regression but showed limited accuracy for extreme yield values.
- Grid embeddings from all models captured major land-cover structures such as rivers, yet their spatial representations varied substantially due to differing training objectives and datasets.
- The library enabled seamless comparison of 16 RSFMs under identical spatiotemporal constraints, demonstrating its “any model, any place, any time” capability.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** The `rs-embed` library reduces the cost of accessing and comparing diverse Remote Sensing Foundation Models (RSFMs) by providing a unified, Region of Interest (ROI)-centric API.
- **Mechanism:** An abstraction layer (the **Provider Layer**) standardizes access to heterogeneous data sources (e.g., Google Earth Engine) into consistent `(C, H, W)` tensors, while another layer (the **Embedder Layer**) wraps disparate model architectures and release formats behind a common base class interface (`get_embedding`, `get_embeddings_batch`). This decoupling means the user specifies only *what* (model ID), *where* (spatial spec), and *when* (temporal spec), not *how* to fetch data or run inference for each model.
- **Core assumption:** Heterogeneity in data access and model inference is the primary barrier to adoption and fair comparison; a standardized wrapper can sufficiently normalize these differences for common use cases (pooled/grid output).
- **Evidence anchors:**
  - [abstract]: "unified, region of interest (ROI) centric interface: with a single line of code, users can retrieve embeddings from any supported model for any location and any time range."
  - [section 2.2 & 2.3]: Describes the Provider Layer handling "projection and resampling, sensor-spec–guided spatiotemporal filtering" and the Embedder Layer's "standardized foundation-model base class."
  - [corpus]: Weak direct evidence. Neighbors discuss RSFM diversity ("Genealogy of Foundation Models") and cross-band generalization challenges, indirectly supporting the heterogeneity problem but not the solution mechanism.
- **Break condition:** A new model's required preprocessing or output format cannot be normalized by the existing `Embedder` base class or `OutputSpec` (e.g., a model requiring unique, non-tensor intermediate steps). The abstraction would leak, forcing custom user code.

### Mechanism 2
- **Claim:** `rs-embed` enables efficient, large-scale embedding generation through a parallel pipeline that decouples network I/O, computation, and disk writes.
- **Mechanism:** The **Orchestration** system splits batched requests into chunks. The **Prefetch** stage uses a thread pool to download and cache input patches from the provider (e.g., GEE) in parallel, deduplicating requests for the same spatial-sensor combination. **Inference** reuses loaded model instances and uses batch APIs where available. **Export** writes results asynchronously, overlapping disk I/O with ongoing computation. This maximizes resource utilization and minimizes idle time.
- **Core assumption:** The dominant bottlenecks for large-scale jobs are network latency for data fetching and disk write throughput; a staged, parallel pipeline with caching significantly mitigates these.
- **Evidence anchors:**
  - [abstract]: "efficient batch processing to enable large-scale embedding generation and evaluation."
  - [section 2.4.1]: Details the "4 stages: Orchestration, Prefetch, Inference, Export" and goals like "maximize utilization of network and computing resources" and "reduce costs caused by redundant downloads."
  - [corpus]: No direct evidence. Neighbors focus on model architecture or datasets, not systems engineering for embedding serving.
- **Break condition:** The provider's API has severe rate limits or lacks parallel access support, making the Prefetch stage ineffective. Batch inference APIs are absent for a model, increasing per-sample Python overhead and negating compute gains.

### Mechanism 3
- **Claim:** `rs-embed` facilitates fair comparison and reproducibility of RSFMs by enforcing strict specification validation and capability matching before execution.
- **Mechanism:** **Policy Enforcement** validates spatial/temporal specs (e.g., valid CRS, non-reversed date ranges). **Capability Matching** uses each model's `describe()` method to check if the requested `OutputSpec` (pooled/grid) and temporal settings are supported, rejecting mismatches with clear errors *before* expensive data fetching or inference begins. This ensures all models are evaluated under identical, valid spatiotemporal constraints.
- **Core assumption:** Fair comparison requires that all models are invoked with inputs and outputs that are both *valid* for that model and *identical* across models; catching mismatches early prevents silent failures or invalid results that would skew benchmarks.
- **Evidence anchors:**
  - [abstract]: Challenges include "heterogeneity in model release formats... and input data specifications" that hinder "fair comparison."
  - [section 2.4.2]: "Two-stage control flow: Policy Enforcement and Capability Matching... rejects mismatches with interpretable errors."
  - [section 3]: The maize yield experiment and grid visualization explicitly compare 16 models "under identical spatiotemporal settings."
  - [corpus]: Weak. Neighbors on RSFM genealogy imply a need for comparison frameworks but do not address the specific validation mechanism.
- **Break condition:** A model's `describe()` method is inaccurate or incomplete, leading the system to incorrectly permit an invalid configuration (e.g., grid size mismatch) that causes a runtime failure or corrupted output, invalidating the comparison.

## Foundational Learning
### Concept: ROI-Centric Geospatial Abstraction
- **Why needed here:** The entire library API is built around specifying a spatial region (BBox/PointBuffer) and time range, not file paths or individual tiles. Understanding this abstraction is key to using `rs-embed` correctly and to seeing why it simplifies cross-model comparison.
- **Quick check question:** If you want embeddings for a farm in Iowa from June to August 2023, what three `rs-embed` objects would you instantiate?

### Concept: Foundation Model Embedding Spaces
- **Why needed here:** The output (`Embedding.data`) is a high-dimensional vector (pooled) or tensor (grid) representing learned features. Different RSFMs produce embeddings of different dimensionalities (`d`) and spatial resolutions (`h x w`), as shown in Figure 6. Users must understand these are *not* directly comparable pixel values but latent representations.
- **Quick check question:** Agrifm's pooled embedding is 1024-D, while Galileo's grid output is `(128, 8, 8)`. What does the difference in shape imply about their underlying architectures and intended use?

### Concept: Batched Asynchronous Pipeline Pattern
- **Why needed here:** The performance benefits come from the 4-stage orchestration. An engineer extending or debugging the system needs to understand data flow: Spec -> Chunking -> Prefetch (parallel I/O) -> Inference (batch CPU/GPU) -> Async Export.
- **Quick check question:** In the pipeline (Figure 3), what is the primary purpose of the "Prefetch" stage relative to "Inference"?

## Architecture Onboarding
Component map: Spec Layer → Provider Layer → Embedder Layer → Export Layer, with the Orchestration Layer managing the overall workflow and pipeline stages (Prefetch, Inference, Export).

- **Critical path:** For a single `get_embedding` call: `SpatialSpec` + `TemporalSpec` -> `Provider.fetch()` -> (if on-the-fly) `Embedder.forward()` -> reshape to `OutputSpec` -> return `Embedding`. For a batch `export_batch`: Validate all specs -> for each chunk: deduplicate `(spatial, sensor)` -> `Provider.prefetch_parallel()` -> `Embedder.batch_inference()` -> async `Export.write()`.

- **Design tradeoffs:**
  - Flexibility vs. Performance: The generic `Provider` and `Embedder` interfaces add overhead vs. hand-coded per-model pipelines but enable the "Any Model" goal.
  - On-the-fly vs. Precomputed: On-the-fly offers temporal flexibility but incurs compute cost. Precomputed is fast but limited to available spatiotemporal coverage and fixed model versions.
  - Memory vs. I/O: Caching prefetched inputs (`inputs cache`) reduces download repeats but increases memory pressure. The `chunk_size` parameter balances peak memory vs. I/O efficiency.
  - Batch API Fallback: Auto-detection of `get_embeddings_batch` improves throughput but requires a fallback to a for-loop for incompatible models, which is slower.

- **Failure signatures:**
  - Provider Failure: GEE quota exceeded, invalid asset ID, cloud cover too high. Manifest `fail_stage: "provider_fetch"`.
  - Inference Failure: Model weights missing, CUDA OOM, input tensor shape mismatch after `SensorSpec` processing. Manifest `fail_stage: "inference"`.
  - Export Failure: Disk full, permission denied. Manifest `fail_stage: "export"`.
  - Policy Failure: Spec validation error (e.g., `buffer_m < 0`). Exception raised *before* pipeline start.
  - Capability Mismatch: Model does not support `OutputSpec.grid()`. Exception raised during capability matching.

- **First 3 experiments:**
  1.  **Maize Yield Regression (Section 3.1):** Validates the core use case. Uses `OutputSpec.pool()` to get 1D vectors for 991 points, feeds them to a Random Forest, and compares R² across 16 models. Demonstrates actionable insight: Agrifm best overall but poor on extremes.
  2.  **Grid-Mode Embedding Visualization (Section 3.2):** Validates spatial output. Uses `OutputSpec.grid()` on a fixed `PointBuffer` for all models, applies PCA for pseudo-RGB. Shows that while all capture coarse structures (rivers), spatial representations vary substantially due to training objectives.
  3.  **Tile Mode Visualization (Appendix B):** Explores an advanced output option. Uses `input_prep='tile'` to crop inputs to model's native resolution instead of resizing, producing finer-grained grids for models that support it. Demonstrates library flexibility for detailed spatial analysis.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** What factors contribute to AgriFM's reduced accuracy in predicting extreme maize yield values despite achieving the highest overall R² in the regression task?
- **Basis in paper:** [explicit] Section 3.1 states: "Agrifm achieves the highest R². However, its ability to fit samples with extremely high or low yields remains limited, and it struggles to accurately capture these outliers."
- **Why unresolved:** The paper presents the performance metric but does not investigate whether the cause lies in AgriFM's training data distribution (e.g., underrepresentation of extreme yields), model architecture limitations, temporal mismatch between embedding extraction and label period, or inherent challenges in representing outlier agricultural conditions.
- **What evidence would resolve it:** A detailed error analysis decomposing residuals by yield quantile, comparing AgriFM's training data yield distribution to the test set, probing the embedding space for outlier samples (e.g., via t-SNE of extreme vs. normal yields), and testing alternative downstream models (e.g., gradient boosting) to isolate whether the issue is in the embedding representation or the Random Forest regressor.

### Open Question 2
- **Question:** Which specific aspects of RSFM training objectives and datasets (e.g., sensor modalities, spatial resolution, pretraining tasks) most strongly influence the observed variations in spatial feature representation, particularly for fine-grained structures like rivers?
- **Basis in paper:** [inferred] Section 3.2 notes that "due to differences in training objectives and datasets, these models emphasize different aspects of spatial representation... their embeddings are generally able to capture key land-cover structures to some extent, such as prominent features like rivers," but the visualization shows substantial variation in how these structures are rendered (e.g., channel, height, width differences in Fig. 6).
- **Why unresolved:** The paper demonstrates the variation qualitatively but does not correlate it with model-specific metadata (e.g., training sensor bands, resolution, loss functions). Without such analysis, it remains unclear whether, for example, models trained on higher resolution data better preserve river morphology or if multimodal training enhances certain textures.
- **What evidence would resolve it:** A quantitative study measuring spatial fidelity of known land-cover features (e.g., river networks) across embeddings using metrics like structure tensor similarity or edge detection precision, combined with a regression analysis linking these metrics to model characteristics (training data sources, resolution, pretraining objectives) from the referenced papers. Ablation studies using `rs-embed` to extract embeddings from the same model under varied synthetic inputs could also isolate factors.

### Open Question 3
- **Question:** What technical approaches can effectively align or fuse heterogeneous RSFM embeddings (differing in dimension, resolution, and semantic space) to improve downstream task performance while preserving model-specific strengths and avoiding information loss?
- **Basis in paper:** [explicit] The Conclusion states: "It also supports cross-model embedding collaboration via alignment and fusion, fostering a more open and composable ecosystem," but the paper does not implement or evaluate any alignment/fusion techniques.
- **Why unresolved:** `rs-embed` provides a unified interface to obtain embeddings but leaves the challenge of combining them to future work. Given the demonstrated variability in representations, downstream users may benefit from complementary signals, but naive concatenation or averaging may be ineffective due to mismatched scales and semantics.
- **What evidence would resolve it:** Benchmark experiments on multiple downstream tasks (e.g., yield regression, land-cover classification) comparing strategies like: (1) learned projection layers (e.g., linear or MLP mappings to a common space), (2) contrastive alignment on paired samples, (3) attention-based fusion, and (4) model-specific averaging. Evaluation should measure performance gains, computational overhead, and sensitivity to hyperparameters, using `rs-embed` to generate the heterogeneous embeddings under fixed spatiotemporal specs.

## Limitations
- Exact sample coordinates for the maize yield regression are undisclosed, preventing exact metric replication.
- Model identifiers, default sensor configurations, and regression experimental details (train/test split, hyperparameters) are unspecified, introducing uncertainty in reproduction.
- Efficiency claims and robustness to non-standard models lack external benchmarks; the library's performance under provider rate limits is untested.
