# HotelQuEST: Balancing Quality and Efficiency in Agentic Search

## Quick Facts
- **arXiv ID**: 2602.23949
- **Source URL**: https://arxiv.org/abs/2602.23949
- **Reference count**: 36
- **Primary result**: HotelQuEST introduces a 214-query hotel benchmark with clarifications, showing LLM agents achieve highest accuracy (4.22/5) but at high cost ($96.03) and latency (P50 364s), while traditional retrievers are cheap but less accurate, with oracles indicating large inefficiency and potential for cost‑aware optimization.

## Executive Summary
HotelQuEST addresses the lack of joint quality‑efficiency evaluation in agentic search by proposing a benchmark of 214 diverse hotel queries, each with clarifications for underspecified preferences. The study evaluates retrieval models and LLM agents, revealing a stark trade‑off: agents like Claude Sonnet 3.7 deliver the best answer quality but incur substantial monetary and time costs, whereas traditional methods like BM25 are economical but inaccurate. Oracle analyses demonstrate that optimal stopping could achieve near‑perfect quality at a fraction of the cost, and even a \$1 budget oracle outperforms all agents. The findings highlight persistent inefficiencies in agent tool usage and underscore the need for cost‑aware agent design.

## Method Summary
The authors constructed HotelQuEST, a benchmark comprising 214 hotel search queries that include clarification questions to resolve ambiguous user preferences. They assessed a range of retrieval models (e.g., BM25) and LLM agents (notably Claude Sonnet 3.7) using two dimensions: answer quality (accuracy, factuality) and operational efficiency (monetary cost, latency). To probe inefficiency, they introduced two oracles: one that knows the exact amount of evidence needed for perfect quality, and another constrained to a \$1 budget. The evaluation involved running each system on the benchmark and aggregating results, supplemented by analyses of tool call patterns and query complexity effects.

## Key Results
- Claude Sonnet 3.7 achieved the highest accuracy (4.22/5) but incurred high cost (\$96.03) and latency (P50 364s, P90 938s).
- Traditional BM25 retriever was extremely cheap but lagged in accuracy (2.64).
- Oracle analyses revealed substantial inefficiency: a \$1 budget oracle outperformed all agents at 96× lower cost, and agents frequently over‑queried after sufficient evidence.

## Why This Works (Mechanism)
HotelQuEST’s effectiveness stems from its dual focus on quality and efficiency, which exposes the inherent trade‑offs in agentic search. The inclusion of clarifications for underspecified preferences ensures that queries reflect real‑world ambiguity, forcing systems to gather additional context. By measuring both accuracy and cost/latency, the benchmark highlights where agents waste resources. Oracle analyses provide a theoretical upper bound, showing that better stopping strategies could dramatically reduce expenses while maintaining quality. The observed over‑querying pattern directly points to a lack of cost‑aware decision‑making in current agents, offering a clear target for improvement.

## Foundational Learning
- **Agentic Search**: Iterative use of LLMs with external tools (e.g., retrievers) to answer complex queries. *Why needed*: Enables handling multi‑step information needs beyond single‑shot retrieval. *Quick check*: Does the agent decide when to stop retrieving?
- **Benchmarking**: Standardized test suite for systematic comparison. *Why needed*: Provides objective, reproducible evaluation across systems. *Quick check*: Are queries diverse and representative of target use cases?
- **Quality Metrics**: Accuracy and factuality measures of answer correctness. *Why needed*: Ensures reliability and trustworthiness of system outputs. *Quick check*: Do answers align with ground truth and avoid hallucinations?
- **Efficiency Metrics**: Cost (monetary) and latency (time) of processing. *Why needed*: Reflects real‑world constraints like budget and responsiveness. *Quick check*: How much does each query cost and how long does it take?
- **Oracle Analysis**: Use of idealized models to bound performance. *Why needed*: Identifies headroom for improvement and inefficiencies. *Quick check*: Could a perfect stopping rule achieve similar quality cheaper?
- **Stopping Decision**: Mechanism to determine when sufficient evidence has been collected. *Why needed*: Prevents unnecessary tool calls, saving cost and latency. *Quick check*: Does the agent cease retrieval once confidence is high?

## Architecture Onboarding
**Component map**: Query → LLM Agent → Retriever → Evidence Store → LLM Agent → Stopping Controller → (Answer or back to Retriever).

**Critical path**: A user query is processed by an LLM agent, which may call the retriever tool multiple times; each retrieval adds to the evidence store. The agent reassesses after every call and either returns an answer or repeats retrieval. The loop continues until the stopping controller signals completion.

**Design tradeoffs**:  
- *Quality vs. efficiency*: More retrieval calls improve accuracy but increase cost and latency.  
- *Stopping sensitivity*: Early stopping yields low latency but risks incomplete answers; late stopping improves quality but wastes resources.  
- *Retriever choice*: Sparse (BM25) is fast/cheap but less expressive; dense retrievers are more accurate but slower/costlier.

**Failure signatures**:  
- Over‑retrieval: Agent continues calling the retriever after sufficient evidence, causing high cost and latency.  
- Under‑retrieval: Agent stops too early, producing inaccurate or incomplete answers.  
- Cost‑quality mismatch: High spending does not translate to proportional accuracy gains.  
- Latency spikes: P90 latency much higher than median, indicating occasional excessive loops.

**First experiments**:  
1. Single‑query budget test: Run an agent on a fixed budget (e.g., \$0.10) and record whether it stops within budget and the resulting accuracy.  
2. Retriever comparison: Evaluate BM25 vs. a dense retriever on a 10‑query subset, measuring both accuracy and cost.  
3. Complexity correlation: For a sample of queries, compute a complexity score (e.g., number of constraints) and correlate with the number of tool calls made by the agent.

## Limitations
- Benchmark scope limited to the hotel domain; findings may not generalize to other verticals or query types.
- Reported cost and latency figures depend on specific LLM agents (Claude Sonnet 3.7), tool implementations, and 2024‑era pricing; changes could alter trade‑offs.
- Oracle analyses assume perfect evidence aggregation and stopping; implementing such oracles in real systems is non‑trivial and may not translate directly.

## Confidence
- Benchmark framework and joint quality‑efficiency methodology: **High**
- Performance rankings (e.g., Claude highest accuracy, BM25 lowest) and over‑querying observations: **Medium**
- Practical impact of oracle findings (e.g., 96× cost reduction) and feasibility of \$1 budget agents: **Low**

## Next Checks
1. Cross‑domain replication: Apply HotelQuEST to a distinct vertical (e.g., real estate or flight bookings) to test generalizability and quality‑efficiency trade‑offs.
2. Modern agent re‑evaluation: Repeat core experiments with current LLM agents (e.g., GPT‑4o, Claude 3.5 Sonnet) to verify if the accuracy‑cost gap persists under updated pricing and capabilities.
3. Oracle implementation: Construct a simplified \$1 budget agent using the oracle’s stopping heuristic (e.g., confidence threshold) and measure its quality‑efficiency on a subset of HotelQuEST queries.
