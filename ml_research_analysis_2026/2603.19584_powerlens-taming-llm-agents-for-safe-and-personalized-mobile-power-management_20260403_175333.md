# PowerLens: Taming LLM Agents for Safe and Personalized Mobile Power Management

## Quick Facts
- arXiv ID: 2603.19584
- Source URL: https://arxiv.org/abs/2603.19584
- Reference count: 40
- Primary result: Achieves 81.7% action accuracy, 38.8% energy saving over stock Android, 0.6% safety violation rate, and user satisfaction 4.3/5.0.

## Executive Summary
PowerLens is a multi‑agent system that leverages large language models (LLMs) to deliver context‑aware, personalized power management on Android devices. It infers user activities from UI semantics, synthesizes policies for 18 hardware/OS parameters, enforces safety via PDL (policy definition language) constraints, and continuously learns individual preferences from implicit user overrides without any explicit configuration. Evaluated on real phones, it significantly outperforms baselines in accuracy, energy efficiency, safety, and user satisfaction while maintaining low overhead.

## Method Summary
The system comprises four specialized agents orchestrated around a two‑tier memory. The Activity Agent ($M_a$) transforms UI tree data and device state into a discrete context signature. The Policy Agent ($M_p$) retrieves relevant preference rules from the long‑term preference memory (LPM) and volatile short‑term memory (STM), then generates a JSON‑structured policy via LLM prompting. The Execution Agent ($M_e$) verifies each action against a set of PDL constraints (hard and contextual) and translates approved actions into shell commands executed with root privileges. The Feedback Agent ($M_f$) performs state differencing to detect manual user overrides, logging them as STRONG signals. An asynchronous Extractor distills these signals into candidate LPM rules using confidence decay/reward; rules that exceed a threshold ($\tau_c=0.8$) are promoted to stable preferences. The cycle is triggered by app foreground changes or periodic timers, and memory updates occur after each execution.

## Key Results
- **Action accuracy:** 81.7%
- **Energy saving vs. stock Android:** 38.8%
- **Safety violation rate:** 0.6%
- **User satisfaction:** 4.3/5.0
- **Preference convergence:** 3–5 days
- **System overhead:** 0.5% daily battery consumption

## Why This Works (Mechanism)
### Mechanism 1: Multi‑agent decomposition for context‑aware policy generation
- **Claim:** Separating activity recognition from policy synthesis enables reliable context inference and personalized action selection.
- **Mechanism:** $M_a$ produces a context signature (category, sub‑activity, battery bucket, time period). $M_p$ uses this signature to query the LPM and STM, then arbitrates between candidate rules with an LLM that outputs structured actions.
- **Core assumption:** UI trees contain sufficient semantic information to infer high‑level activities (e.g., Navigation vs. Reading) and finer sub‑activities (e.g., actively watching vs. browsing).
- **Evidence anchors:** [abstract] “multi‑agent architecture that recognizes user context from UI semantics”; [section 3.1.1] details Activity Agent functions; [section 6.4] reports 83.0% activity‑type accuracy.
- **Break condition:** If $M_a$ accuracy drops significantly (e.g., <70% on key categories), the context signature becomes unreliable, causing $M_p$ to retrieve mismatched rules and degrade overall performance.

### Mechanism 2: Two‑tier memory with confidence‑based distillation learns preferences implicitly
- **Claim:** Implicit user overrides are captured via state differencing and distilled into stable, personalized rules without explicit user training.
- **Mechanism:** $M_f$ compares current device state to the STM’s last state; any manual change logs a STRONG signal. The Extractor runs asynchronously, prompting an LLM to infer the user’s intended rule from each STRONG event. Candidate rules accumulate confidence using $c_{new} = c_{old} \cdot \lambda^{\Delta t} + r$ (λ=0.93, rewards for strong/weak/conflict signals). When confidence crosses $\tau_c=0.8$ and passes conflict checks, the rule is promoted to the LPM.
- **Core assumption:** Manual overrides reflect dissatisfaction with the preceding automated decision, and repeated similar overrides reveal a stable preference.
- **Evidence anchors:** [abstract] “two‑tier memory system learns individualized preferences from implicit user overrides … converging within 3–5 days”; [section 3.2.3] describes distillation stages; [section 6.3] shows 23% UES improvement from memory.
- **Break condition:** If users rarely override settings, the system cannot gather STRONG signals, leaving the LPM empty and forcing reliance on generic profiles, which reduces personalization.

### Mechanism 3: PDL‑based constraint verification ensures execution safety
- **Claim:** A formal constraint layer deterministically blocks LLM‑generated actions that violate safety invariants, drastically reducing harmful outcomes.
- **Mechanism:** $M_e$ first submits each proposed action to a verification LLM call that checks against a PDL constraint set $\Phi$ (e.g., “during navigation, location_mode must be high”). Actions violating hard constraints are rejected or corrected. The second LLM call then translates only verified actions into precise shell commands.
- **Core assumption:** The PDL constraint set comprehensively covers all safety‑critical invariants for the supported app categories and parameters.
- **Evidence anchors:** [abstract] “PDL‑based constraint framework verifies every action before execution… with 0.6% safety violation rate”; [section 3.3.1] defines PDL constraints and provides an example; [section 6.5] shows raw LLM violation rate of 17.0% drops to 0.59% after PDL.
- **Break condition:** Gaps in $\Phi$ for novel app categories or unforeseen parameter combinations lead to residual violations (reported <1.2% in evaluation), as the checker cannot evaluate unspecified invariants.

## Foundational Learning
- **Concept: LLM prompt engineering for structured output**  
  *Why needed:* All agents rely on LLMs to produce valid JSON actions, constraints, or commands. Incorrect formatting breaks the pipeline.  
  *Quick check:* How would you design a system prompt to guarantee the Policy Agent outputs the exact JSON schema in Fig. 5 (`target`, `action`, `value`, `priority`, `reason`) without extra fields?

- **Concept: Android system‑level parameter control**  
  *Why needed:* PowerLens adjusts 18 hardware/OS parameters via root shell commands (`su -c settings put…`). Mapping logical actions to physical sysfs/Settings APIs is essential.  
  *Quick check:* For the `cpu_governor` parameter, what are the valid values, which sysfs file must be written, and what permission is required?

- **Concept: Implicit feedback via state differencing**  
  *Why needed:* The personalization loop depends on detecting manual overrides by comparing current state ($\sigma_{t1}$) to the last known state ($\sigma_{t0}$).  
  *Quick check:* If the system sets `screenBrightness` from 1600 to 1200, but the user later changes it to 2000, how does $M_f$ classify this event and where is it logged?

## Architecture Onboarding
- **Component map:** Device Profiler -> Accessibility UI Dumper -> Four Agents ($M_a$, $M_p$, $M_e$, $M_f$) -> Two‑tier Memory (STM & LPM) -> Extractor -> PDL constraint files  
- **Critical path:** App foreground change → Accessibility triggers → $M_f$.StateDiff → $M_a$.Recognize (LLM#1) → LPM lookup → $M_p$.Generate (LLM#2) → $M_e$.Verify (LLM#3) → $M_e$.GenCommands (LLM#4) → `su` execution → state readback → STM update.  
- **Design tradeoffs:**  
  • *Latency vs. safety:* Two LLM calls for verification and command generation add latency (~4.4 s) but prevent reasoning contamination.  
  • *Memory cost vs. convergence:* STM is volatile; LPM persistence enables long‑term learning but consumes storage (few KB/app). Extractor runs asynchronously to avoid active‑use overhead.  
  • *LLM cost vs. quality:* Cloud LLMs (Gemini‑2.5‑Flash) provide high quality ($0.005/cycle) but raise privacy concerns; on‑device SLMs could reduce cost/latency but may sacrifice accuracy.  
- **Failure signatures:**  
  – High violation rate (>2%): Missing PDL constraints or $M_e$ misapplying them.  
  – Low accuracy (<70%): $M_a$ misclassification or $M_p$ retrieving wrong LPM rules.  
  – Slow convergence (>10 days): Weak/contradictory override signals or reward mis‑calibration.  
  – High overhead (>2% daily battery): Over‑frequent cycles or excessive LLM calls during active use.  
- **First 3 experiments:**  
  1. *Unit test Activity Agent:* Feed captured UI trees from 7 categories with ground truth; measure sub‑activity accuracy (>78%).  
  2. *Stress test PDL checker:* Inject adversarial outputs (e.g., “disable all radios”); verify 100% hard constraint rejection.  
  3. *Measure memory convergence:* Simulate a known preference (brightness >800 during video); track candidate confidence in LPM buffer; expect promotion to stable rule by Day 5 ($\tau_c=0.8$).

## Open Questions the Paper Calls Out
- **Open Question 1:** How can PowerLens capture preferences for parameters with delayed or invisible effects, given its reliance on immediate override detection?  
  *Basis:* State differencing only sees immediate reversals; delayed feedback remains blind.  
  *What evidence would resolve it:* Alternative feedback mechanisms (e.g., explicit ratings or indirect signals) evaluated for those parameters.

- **Open Question 2:** Can PowerLens migrate to on‑device small language models without sacrificing accuracy, safety, or energy?  
  *Basis:* Cloud inference raises privacy/latency; SLMs may be less capable.  
  *What evidence would resolve it:* Implement with quantized SLMs on real hardware and compare all metrics to cloud baseline.

- **Open Question 3:** Does the design scale to non‑smartphone devices (wearables, EVs) with different hardware and usage patterns?  
  *Basis:* Current parameter set and constraints are smartphone‑specific.  
  *What evidence would resolve it:* Build prototypes for at least one new category, create a representative benchmark, and evaluate effectiveness.

- **Open Question 4:** How do real users’ long‑term preferences compare to synthetic profiles, and how does personalization perform in practice?  
  *Basis:* Evaluation used GPT‑generated personas and a short 14‑day study with 10 participants.  
  *What evidence would resolve it:* Longitudinal field study with 100+ users over months, comparing learned rules to self‑reported preferences.

## Limitations
- Incomplete public disclosure: The full PDL constraint set for all 7 app categories is not released, hindering exact replication of safety guarantees.
- Undisclosed benchmark: PowerLensBench (25 apps, 48 tasks, GPT‑generated ground truth) remains private, preventing independent verification of reported accuracy and energy‑saving numbers.
- Insufficient prompt details: System prompts for each agent are not fully specified, introducing uncertainty in reproducing structured outputs and safety reasoning.

## Confidence
- Multi‑agent decomposition for context awareness: Medium (activity accuracy 83% supports but UI semantics may not generalize).
- Two‑tier memory learning from implicit overrides: High (mechanism clearly defined, empirically validated with convergence and UES improvement).
- PDL constraint safety guarantee: Medium (96.5% violation reduction is strong; but claim depends on unreleased constraint completeness).
- Overall performance metrics (accuracy, energy, satisfaction): Low (high numbers reported without public benchmark or raw data; replication confidence minimal).
