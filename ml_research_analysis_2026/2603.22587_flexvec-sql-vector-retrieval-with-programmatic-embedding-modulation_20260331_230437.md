# flexvec: SQL Vector Retrieval with Programmatic Embedding Modulation

## Quick Facts
- arXiv ID: 2603.22587
- Source URL: https://arxiv.org/abs/2603.22587
- Reference count: 23
- Primary result: flexvec exposes the embedding matrix and score array as a programmable surface for Programmatic Embedding Modulation (PEM), enabling SQL-integrated, composable retrieval operations with verified correctness and millisecond-scale performance on million-chunk corpora.

## Executive Summary
Flexvec addresses the rigidity of conventional retrieval APIs for AI agents by introducing Programmatic Embedding Modulation (PEM). The system treats the embedding matrix and similarity scores as a programmable surface, allowing arithmetic operations such as suppression, decay, centroid, trajectory, and diversity to be composed before final selection. Integration into SQL is achieved via a query materializer that intercepts custom pseudo-functions and materializes modulated scores within the database engine.

Empirical validation demonstrates that three composed modulations execute in 19 ms on a 240 000‑chunk corpus and 82 ms on a 1 000 000‑chunk corpus using a desktop CPU, without approximate indexing. Algebraic correctness is confirmed with zero mismatches in 1 840 score comparisons (tolerance 1e-3). Behavioral experiments on BEIR datasets show intended ranking changes, notably a 10–40% reduction in intra‑list similarity for the diverse operation. The system has been in production since February 2026, serving approximately 6 500 agent queries.

## Method Summary
The authors evaluate flexvec through a dual approach: algebraic verification and behavioral experimentation. Algebraic correctness is tested by comparing computed modulated scores against theoretical formulas across 1 840 cases using four BEIR datasets (SciFact, NFCorpus, SCIDOCS, FiQA) with 128‑dimensional Nomic Embed v1.5 vectors (Matryoshka truncation). Behavioral impact is measured via ranking metrics—Rank‑Biased Overlap (RBO), Intra‑List Similarity (ILS), and nDCG@10—assessing how each PEM operation shifts rankings relative to an unmodulated baseline.

The experimental pipeline is automated: a Python script downloads the BEIR data, generates per‑dataset SQLite databases with precomputed embeddings, and inserts synthetic timestamps for decay tests. Two pytest suites then execute: `test_tokens_beir.py` (52 behavioral tests) and `test_algebraic.py` (score formula checks). Token grammar defaults are fixed for each operation (e.g., `suppress:w=0.5`, `diverse:λ=0.7, pool=3×K`). Reproduction requires a pinned environment (numpy, onnxruntime, tokenizers), the ONNX int8 model for Nomic Embed v1.5, and about one hour for dataset preparation plus 20 seconds for test execution.

## Key Results
- **Performance**: Three composed PEM operations run in 19 ms on a 240 000‑chunk corpus and 82 ms on a 1 000 000‑chunk corpus (desktop CPU, no approximate indexing).
- **Correctness**: Algebraic verification yields zero score mismatches across 1 840 comparisons (floating‑point tolerance 1e-3).
- **Impact & Deployment**: Behavioral validation shows intended ranking changes (e.g., 10–40% intra‑list similarity reduction for diverse); the system has been in production since February 2026, handling approximately 6 500 queries.

## Why This Works (Mechanism)
Flexvec reimagines the retrieval pipeline by making dense document embeddings and their precomputed similarity scores directly accessible and modifiable within the query processing stage. Instead of treating vector search as a black‑box nearest‑neighbor lookup, the embedding matrix and score array become operands in a programmable surface. PEM operations—expressed as pseudo‑functions in SQL—capture common adjustments (e.g., suppressing a concept, blending toward a centroid, enforcing diversity) as simple arithmetic transformations on scores or vectors. A query materializer intercepts these pseudo‑functions, rewrites the query to compute new scores on the fly, and then proceeds with standard ranking and selection. This design enables exact scoring, seamless SQL integration, and composition of multiple modulations without requiring specialized indexes or approximations.

## Foundational Learning
- **Embedding Modulation**  
  *Why needed*: Standard vector search returns a static ranking; PEM allows dynamic, application‑specific adjustments.  
  *Quick check*: Does the modulation produce the expected directional shift (e.g., suppressed documents drop in rank)?

- **Query Materializer**  
  *Why needed*: To embed custom operations within vanilla SQL without modifying the underlying engine.  
  *Quick check*: Does the materializer generate modulated scores that match a reference implementation?

- **Algebraic Correctness Verification**  
  *Why needed*: Guarantees precise implementation of PEM formulas, preventing subtle ranking errors.  
  *Quick check*: Are all score comparisons within the specified tolerance (1e-3)?

- **Composable Operations**  
  *Why needed*: Real‑world retrieval often requires multiple overlapping adjustments (e.g., suppress + diversity).  
  *Quick check*: Does chaining PEM functions yield results equivalent to applying them sequentially in the correct order?

## Architecture Onboarding
- **Component Map** (plain text):  
  Client → SQL Engine (with custom pseudo‑function intercept) → Query Materializer → Loads Embedding Matrix & Score Array from DB → PEM Modulation Engine → Modulated Scores → Top‑K Selection → Response

- **Critical Path**:  
  1. Parse incoming SQL query and detect PEM pseudo‑functions.  
  2. Load required embedding vectors and precomputed scores into memory.  
  3. Apply specified PEM arithmetic (vector ops, blending, etc.).  
  4. Compute final ranking and extract top‑K results.  
  The most computationally intensive steps are fetching the embedding matrix (if not cached) and performing vector arithmetic across many candidates.

- **Design Tradeoffs**:  
  - *Exact vs. Approximate*: Flexvec chooses exact materialization to guarantee correctness, sacrificing the scalability of approximate nearest‑neighbor indexes.  
  - *In‑memory vs. Disk*: Modulations operate in memory after loading embeddings, trading RAM for speed.  
  - *Simplicity of Arithmetic*: PEM operations are limited to linear combinations to maintain both performance and algebraic verifiability.

- **Failure Signatures**:  
  - Shape mismatches when embedding dimensions are incorrect.  
  - SQL errors indicating missing database tables or columns.  
  - Tolerance breaches in algebraic tests suggest implementation bugs or floating‑point drift.  
  - Linear latency growth with corpus size signals lack of indexing or vectorization.

- **First Three Experiments**:  
  1. Run `pytest tests/test_algebraic.py` to confirm all score formulas meet the 1e‑3 tolerance.  
  2. Issue a query with `suppress` on a single term and verify that the top result is no longer the most similar to the suppressed concept.  
  3. Benchmark composition latency for increasing candidate set sizes (e.g., 10, 100, 1000) to observe scaling behavior.

## Limitations
- BEIR evaluation uses the first 30 queries by insertion order rather than standard splits, which may affect generalizability of reported nDCG scores.  
- The exact ONNX int8 quantization method for Nomic Embed v1.5 is unspecified, potentially leading to embedding differences that impact reproduction.  
- Performance and deployment claims are based on a single desktop CPU; broader hardware evaluation is required.
