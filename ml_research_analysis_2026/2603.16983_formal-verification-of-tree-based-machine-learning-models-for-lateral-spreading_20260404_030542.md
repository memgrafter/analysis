# Formal verification of tree-based machine learning models for lateral spreading

## Quick Facts
- **arXiv ID:** 2603.16983
- **Source URL:** https://arxiv.org/abs/2603.16983
- **Reference count:** 33
- **Primary result:** Formal verification of tree ensembles (XGBoost, EBM) against geotechnical specifications reveals a fundamental trade-off: no model achieves both >80% accuracy and full physical compliance.

## Executive Summary
This paper introduces formal verification via SMT solvers to exhaustively check physical consistency in tree-based machine learning models for geotechnical lateral spreading prediction. By encoding trained ensembles as logical formulas, the authors verify four domain-specific specifications (e.g., groundwater depth monotonicity). Unconstrained models violate all specs; constrained models improve compliance but incur significant accuracy penalties (10–15 percentage points). A systematic Pareto analysis confirms no model escapes this trade-off. The work demonstrates a verify-fix-verify engineering loop and shows that post-hoc explanations (SHAP) cannot substitute for formal guarantees, as violating features may rank last in local importance.

## Method Summary
The study uses the 2011 Christchurch earthquake dataset (7,291 sites, 4 features: groundwater depth, distance to free face, slope, PGA; binary label for spreading ≥0.3 m). Tree ensembles (XGBoost, EBM) are trained with an 80/20 split. Each ensemble is translated into a quantifier-free If-Then-Else (ITE) expression over real-valued features. Physical specifications are formalized as universally quantified logical formulas (e.g., "∀x: groundwater deep ⇒ no spreading"). Their negations become existential queries combined with the model's ITE, yielding decidable QF_LRA formulas solved by Z3. Verification returns `unsat` (spec proven) or `sat` with a counterexample. Monotonicity constraints are applied during training; compound specs are checked post-training.

## Key Results
- Unconstrained XGBoost (82.5% accuracy) violates all four specifications; monotone-constrained XGBoost (69.3%) satisfies only PGA monotonicity.
- Unconstrained EBM (80.1%) violates all; PGA-monotone EBM (70.5%) satisfies only monotonicity; fully constrained EBM (67.2%) satisfies three specs but fails on groundwater depth threshold.
- Pareto analysis of 33 model variants shows no combination achieves >80% accuracy and full specification compliance, confirming a persistent accuracy–consistency trade-off.
- SHAP analysis of counterexamples reveals the offending feature can rank last in contribution, disproving the reliability of post-hoc explanations for universal guarantees.

## Why This Works (Mechanism)

### Mechanism 1: SMT encoding enables exhaustive verification
- **Claim:** Encoding tree ensembles as logical formulas allows universal, domain-wide checking of physical specifications.
- **Mechanism:** Each tree is recursively converted to an ITE expression over feature thresholds. The ensemble logit is a sum of ITEs, partitioning input space into hyperrectangles. Negating a universal specification (e.g., ∀x: g>5 ⇒ f(x)≤0) yields an existential query (∃x: g>5 ∧ f(x)>0). Inlining the model's ITE produces a decidable QF_LRA formula; an SMT solver (Z3) decides satisfiability, returning `sat` with a counterexample or `unsat` (proof over the bounded domain).
- **Core assumption:** Tree ensembles produce piecewise-constant predictions definable by nested comparisons and summations, admitting exact symbolic encoding.
- **Evidence anchors:** [abstract] "We encode trained tree ensembles as logical formulas in a Satisfiability Modulo Theories (SMT) solver..." [section 3.3] details the recursive ITE translation and reduction to QF_LRA.

### Mechanism 2: Verify-fix-verify loop iteratively enforces consistency
- **Claim:** Counterexamples from formal verification guide targeted corrections (e.g., monotone constraints), enabling provable improvement in physical consistency.
- **Mechanism:** Verification identifies precise input regions violating a spec. Engineers apply corrective measures (monotonicity, shape edits) and retrain. Re-verification confirms specification satisfaction or reveals residual violations, transforming correctness from empirical to proven.
- **Core assumption:** Counterexamples are valid and actionable; corrective mechanisms (e.g., single-feature monotonicity) can eliminate the violation pattern without introducing new ones.
- **Evidence anchors:** [abstract] "Establish a verify-fix-verify engineering loop..." [section 5.2] demonstrates the loop: unconstrained → monotone-constrained XGBoost fixes only monotonicity.

### Mechanism 3: Formal verification provides universal guarantees unattainable by SHAP
- **Claim:** SHAP's local feature attributions cannot certify universal compliance with logical specifications, whereas verification exhaustively proves or disproves them.
- **Mechanism:** SHAP decomposes a single prediction but does not reason globally. A violation can occur even if the offending feature has a small SHAP value, as SHAP reflects marginal contribution, not absolute threshold adherence. Formal verification, by exhaustively checking the symbolic model structure, yields a binary, universal guarantee or a concrete counterexample.
- **Core assumption:** The specification is expressible as a decidable logical formula over the input space; SHAP's additive attribution is insufficient for such universal properties.
- **Evidence anchors:** [abstract] "SHAP analysis of counterexamples reveals that the offending feature can rank last..." [section 5.4] shows a counterexample where the violating feature (GWD) ranks last in SHAP waterfall.

## Foundational Learning
- **Concept:** Tree Ensemble Partitioning  
  **Why needed:** Understanding that gradient-boosted trees partition the feature space into axis-aligned hyperrectangles (each leaf a constant score) explains why SMT encoding is finite and decidable.  
  **Quick check:** If a depth-3 binary tree splits on two features, what is the maximum number of distinct regions (leaf nodes) it can define?  
  *Answer: Up to 2³ = 8 regions.*

- **Concept:** SMT Solvers for QF_LRA  
  **Why needed:** Verification queries reduce to deciding satisfiability of formulas with real arithmetic and ITE terms. QF_LRA is decidable, and tools like Z3 implement this procedure, ensuring termination with a definitive answer.  
  **Quick check:** What does the solver return when it proves a specification holds for all inputs? What when it finds a violation?  
  *Answer: `unsat` for universal proof; `sat` with a counterexample for violation.*

- **Concept:** Formal Specification as Universal Quantification  
  **Why needed:** Physical geotechnical rules must be translated into ∀-formulas over bounded input domains. Verification hinges on negating these to existential queries for the solver.  
  **Quick check:** Write the logical negation of "∀x in X: (condition) ⇒ (model output ≤ 0)" as an existential query.  
  *Answer: ∃x in X: (condition) ∧ (model output > 0).*

## Architecture Onboarding
- **Component map:** Data → Training Pipeline → Unconstrained Model → SMT Encoder → Verifier (Z3) → Counterexample Analysis → Constraint Applicator → Constrained Model → Re-verification Loop
- **Critical path:** Train initial model → verify specs A–D → analyze counterexamples → apply constraints (monotonicity, shape edits) → retrain → re-verify until all `unsat` or no further constraints.
- **Design tradeoffs:**  
  - Accuracy vs. Consistency: Imposing constraints (e.g., monotonicity) reduces model capacity and test accuracy (e.g., 82.5% → 67.2% for full EBM constraints).  
  - Constraint Expressiveness: Single-feature monotone constraints enforce only monotonicity (Spec B); they cannot guarantee thresholds (Spec A) or compound conjunctions (Specs C/D).  
  - Verification Cost: Per-tree monotonicity checks are cheap (<1 s/tree); dual-ensemble checks for compound specs are slower (seconds to minutes for EBM).
- **Failure signatures:**  
  - Specification violation: Solver returns `sat` with concrete input (e.g., GWD=5.001 m, positive logit).  
  - Encoding mismatch: Counterexample does not reproduce model prediction; indicates precision error (float32 vs. exact arithmetic).  
  - Stalled loop: After full monotone constraints, Spec A still violated → need for non-monotone strategies (output clamping, data augmentation).
- **First 3 experiments:**  
  1. **Baseline Verification:** Train unconstrained XGBoost (depth 5, 100 trees). Verify all four specs. Expect `sat` for all, with counterexamples in data-sparse boundary regions (e.g., high distance, low PGA).  
  2. **Monotone Constraint Test:** Retrain XGBoost with monotone constraints on GWD(−), L(−), PGA(+). Verify again. Expect Spec B to be `unsat` (proven), but Specs A, C, D remain `sat`.  
  3. **Compound Constraint Exploration:** Train EBM with monotone constraints on all four features. Verify. Expect Specs B, C, D to be `unsat`, but Spec A likely still `sat` (thin margin), showing monotonicity alone cannot enforce absolute thresholds.

## Open Questions the Paper Calls Out
- **Open Question 1:** How to integrate formal verification (hard constraints) with probabilistic calibration (e.g., conformal prediction) for physical consistency and uncertainty quantification?  
  *Basis:* Authors propose this as a natural extension. Unresolved due to lack of unified framework combining deterministic guarantees with probabilistic coverage.
- **Open Question 2:** Can SMT verification be generalized to regression models predicting continuous displacement, and how to formalize continuous-output specifications?  
  *Basis:* Paper focuses on binary classification; extension to regression is conceptually straightforward but requires reformulating specs over continuous outputs.
- **Open Question 3:** What causes the persistent 10–15% accuracy penalty when enforcing physical consistency, and can it be reduced?  
  *Basis:* Pareto analysis shows no model achieves >80% accuracy and full compliance; cause may be inherent to constraint mechanisms or data sparsity.
- **Open Question 4:** How can a complete specification library for geotechnical ML be systematically derived and validated?  
  *Basis:* Current four specs encode necessary but not sufficient conditions; a methodology for eliciting, formalizing, and testing completeness of richer specs is absent.

## Limitations
- **Reproducibility gaps:** Exact hyperparameters (XGBoost learning rate, EBM binning) and low-level SMT encoding details (float32 casting, solver settings) are unspecified, risking drift in results.
- **Corpus maturity:** Neighboring work shows near-zero citations; the specific application to geotechnical lateral spreading is novel but not yet widely validated or benchmarked.
- **Specification expressiveness:** Evaluation uses four binary rules; the persistent trade-off may be exacerbated by limited specs—richer or multi-objective specifications could change the Pareto frontier.

## Next Checks
1. **Counterexample validity audit:** For every `sat` result, programmatically feed the solver's counterexample into the exact trained model (identical float32 arithmetic) to confirm the violation is real and not an encoding artifact.
2. **Hyperparameter sensitivity sweep:** Retrain a grid of XGBoost/EBM models across learning rates, depths, and regularization strengths. Re-run verification to test robustness of the accuracy–compliance trade-off.
3. **Constraint-generalization test:** Apply the verify-fix loop using non-monotone corrective strategies (e.g., output clamping, targeted data augmentation in violation regions) for Spec A. Measure if compliance improves without the steep accuracy drop seen with full monotone EBM.
