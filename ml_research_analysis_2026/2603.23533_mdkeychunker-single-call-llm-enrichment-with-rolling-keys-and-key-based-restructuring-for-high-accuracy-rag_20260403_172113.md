# MDKeyChunker: Single-Call LLM Enrichment with Rolling Keys and Key-Based Restructuring for High-Accuracy RAG

## Quick Facts
- **arXiv ID:** 2603.23533
- **Source URL:** https://arxiv.org/abs/2603.23533
- **Reference count:** 2
- **Primary result:** Achieves perfect Recall@5=1.000 on a 30-query evaluation using BM25 over structure-aware chunks, coupled with a 9.3% chunk reduction via LLM-driven key-based merging.

## Executive Summary
Fixed-size chunking in RAG systems fragments document structure and requires costly multi-call metadata extraction. MDKeyChunker introduces a three-stage pipeline that first splits Markdown into structurally atomic units, then enriches each chunk with seven coherent metadata fields via a single LLM call that propagates a rolling key dictionary to reduce synonym proliferation, and finally restructures chunks by merging those sharing a semantic key using bin-packing. On an 18-document corpus, the pipeline reduces chunk count by 9.3% while achieving perfect Recall@5 with sparse retrieval and strong results with dense retrieval, all with 100% metadata fill rate and high cross-reference utilization.

## Method Summary
The pipeline begins with structure-aware Markdown splitting, identifying atomic blocks (headers, code, tables, lists, blockquotes, paragraphs) and grouping them into initial chunks without breaking delimiters like fenced code fences, respecting size thresholds (τmin=100, τmax=1500 chars). Each structural chunk then undergoes single-call LLM enrichment, extracting title, summary, keywords, entities, questions, a specific subtopic `key`, and `related_keys`. A rolling dictionary `K` (capacity Kmax=40, LRU eviction) of prior chunk keys is injected into each prompt to encourage key reuse. Finally, enriched chunks are grouped by their `key`; within each group, a first-fit bin-packing algorithm merges chunks up to τmerge=3000 characters. Orphan chunks are minimally augmented. This process merges non-adjacent but thematically related content, creating larger, coherent retrieval units.

## Key Results
- Structure-only chunking with BM25 (Config D) yields perfect Recall@5=1.000 and MRR=0.911.
- Full pipeline with dense retrieval (Config C) achieves Recall@5=0.867.
- Chunk count reduced by 9.3% (269 → 244) with 100% metadata fill rate and 89.8% cross-reference utilization from rolling keys, using only one LLM invocation per chunk.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Structure-aware Markdown splitting prevents semantic fragmentation by treating headers, code blocks, tables, and lists as indissoluble units.
- **Mechanism:** A block parser identifies six atomic block types. A header stack tracks section hierarchy. Blocks are grouped into chunks respecting atomicity constraints (e.g., no splitting fenced code blocks) and size thresholds (τmin, τmax).
- **Core assumption:** Markdown’s semantic delimiters reliably indicate topical and functional boundaries that align with human-perceived document structure.
- **Evidence anchors:**
  - [abstract] “structure-aware chunking treating headers, code blocks, tables, and lists as atomic units”
  - [section 3.1] “Atomicity constraints. The following elements are never split across chunks: fenced code blocks… tables… list items”
  - [section 5.1] “zero code-block or table splits were observed”
- **Break condition:** For non-Markdown formats without a conversion step, semantic boundaries may not map to syntactic delimiters, causing fragmentation. Malformed Markdown could break the header stack logic.

### Mechanism 2
- **Claim:** Single-call LLM enrichment with rolling keys produces coherent metadata while reducing invocation cost and synonym proliferation across chunks.
- **Mechanism:** Each chunk is processed in one LLM call extracting seven fields. The prompt includes a rolling dictionary K of keys from prior chunks, enabling the LLM to reuse existing keys instead of generating synonyms.
- **Core assumption:** A single, well-structured prompt allows an LLM to generate internally consistent metadata fields; inter-chunk context via K is sufficient to canonicalize topic labels without explicit scoring functions.
- **Evidence anchors:**
  - [abstract] “single LLM call extracting seven coherent metadata fields per chunk while propagating a rolling key dictionary to reduce synonym proliferation”
  - [section 3.2] “The single-call design extracts all seven metadata fields in one LLM invocation, eliminating the need for separate per-field extraction passes.”
  - [section 5.2] “89.8% cross-reference utilization from rolling keys”
- **Break condition:** If the LLM ignores the JSON schema or key constraints, the rolling mechanism fails, leading to synonym proliferation. LRU eviction (Kmax=40) may evict relevant keys if the document is very long, reducing reuse.

### Mechanism 3
- **Claim:** Key-based bin-packing restructuring merges chunks sharing a semantic key, co-locating non-adjacent but thematically related content into larger, coherent retrieval units.
- **Mechanism:** After enrichment, chunks are grouped by their `key`. Within each group, chunks are merged using a first-fit bin-packing algorithm subject to τmerge (3000 chars). Orphan chunks undergo minor augmentation if small.
- **Core assumption:** The LLM-generated `key` is a stable, specific subtopic label such that all chunks with the same key form a single coherent semantic unit.
- **Evidence anchors:**
  - [abstract] “restructures chunks by merging those sharing the same semantic key via bin-packing, co-locating related content for retrieval”
  - [section 3.3] “A key-based chunk restructuring algorithm that merges semantically related chunks globally via bin-packing”
  - [section 5.2] Example: two non-adjacent fragments with key “model types” merged into one 2,503-char chunk
- **Break condition:** If keys are too broad, over-merging occurs, combining heterogeneous content. The bin-packing heuristic is greedy and not globally optimal; order-dependent groupings might leave suboptimal bins.

## Foundational Learning
- **Concept: Markdown block parsing and atomicity**
  - *Why needed here:* The entire pipeline’s correctness depends on Stage 1 never splitting semantic units (code, tables). Misparsing corrupts all downstream stages.
  - *Quick check question:* Given a Markdown document with a fenced code block spanning 50 lines, does the chunker ever split it? If not, what parameter prevents it?

- **Concept: Prompt engineering for constrained JSON generation**
  - *Why needed here:* Stage 2’s single-call enrichment requires the LLM to output exactly seven fields in a specific schema. Prompt design enforces this (e.g., “Return ONLY valid JSON”).
  - *Quick check question:* How does the prompt prevent the LLM from inventing a `related_keys` entry not present in the rolling keys dictionary?

- **Concept: Bin-packing for merge optimization**
  - *Why needed here:* Stage 3 uses a first-fit bin-packing algorithm to merge chunks by key while respecting τmerge. Understanding its greedy nature is key to predicting merge outcomes.
  - *Quick check question:* If three chunks with the same key have sizes 1200, 900, and 1100 characters (τmerge=3000), how many final merged chunks will result? Why?

## Architecture Onboarding
- **Component map:**  
  StructuralChunker -> LLMEnricher -> KeyRestructurer
- **Critical path:** Document -> structural chunks -> enriched chunks with rolling K -> merged chunks. The rolling K dictionary is the only state carried between Stage 2 invocations; its size is bounded to keep prompts small.
- **Design tradeoffs:**  
  - *Sequential enrichment vs. parallelism*: Rolling keys require processing chunks in document order, preventing naive batch parallelism.  
  - *Key specificity vs. merge yield*: Strict keys reduce over-merging but may leave many orphans; broad keys increase merges but risk incoherence.  
  - *Dense vs. sparse retrieval*: Config D (BM25 on structural chunks) unexpectedly outperforms dense on full pipeline (C), suggesting structure alone may be stronger than enriched restructured chunks for this corpus.
- **Failure signatures:**  
  - LLM returns malformed JSON → `result=∅` (graceful degradation: chunk keeps only parser fields).  
  - Rolling K evicts a key that reappears later → reduced `related_keys` reuse (below 89.8%?).  
  - Key granularity too broad → merged chunks exceed τmerge or mix distinct subtopics (check merged chunk `summary` for coherence).  
  - Non-Markdown input → structural parser may misidentify boundaries, causing fragmentation.
- **First 3 experiments:**  
  1. **Atomicity validation test:** Feed a Markdown document containing a multi-line fenced code block and a multi-row table. Assert no chunk splits these blocks (inspect chunk boundaries line numbers).  
  2. **Rolling key reuse test:** For a document with a recurring subtopic across sections, run the pipeline and check that the later chunk’s `related_keys` contains the earlier `key`. Measure reuse rate expected ~89.8%.  
  3. **Merge bin-packing sanity check:** Create a synthetic enricher output with three chunks same key, sizes 1000, 1000, 1000 (τmerge=3000). Assert final count=1 merged chunk of ~3000 chars, not three.

## Open Questions the Paper Calls Out
- **Question:** How does MDKeyChunker's retrieval performance generalize to larger, diverse corpora and established benchmarks (e.g., BEIR, TREC) beyond the small, homogeneous 18-document Markdown corpus?
  - *Basis in paper:* The evaluation is confined to "30 queries over an 18-document Markdown corpus (354KB)" (§4.2). The conclusion explicitly states that "comprehensive empirical evaluation on established benchmarks such as BEIR and TREC" is reserved for future work (§7).
  - *Why unresolved:* The reported perfect Recall@5 (Config D) and strong MRR may be corpus-specific, given the narrow domain (project documentation) and tiny scale. Performance on out-of-domain or large-scale corpora remains unknown.
  - *What evidence would resolve it:* Running the full pipeline on standardized public benchmarks (BEIR/TREC) with diverse document types and query distributions, reporting standard metrics (nDCG@10, Recall@100) for comparison with state-of-the-art chunking methods.

- **Question:** Can the rolling key propagation mechanism be extended to maintain semantic coherence across multiple documents in a corpus, rather than resetting per document?
  - *Basis in paper:* Listed as limitation (4): "Rolling keys reset between documents; cross-document key harmonization is left to future work" (§6.2). Future work also mentions "cross-document key vocabularies for corpus-level RAG" (§7).
  - *Why unresolved:* The current design isolates key dictionaries per document, preventing global topic linking. For multi-document RAG (e.g., a company's entire knowledge base), synonym proliferation may recur across documents, undermining the core benefit of key canonicalization.
  - *What evidence would resolve it:* Implementing a global key store with document-scoped namespaces, evaluating on a multi-document corpus where queries span multiple sources, and measuring reduction in duplicate keys/related_keys usage versus per-document rolling.

- **Question:** To what extent does the quality and granularity of the generated "semantic key" field influence the efficacy of the key-based restructuring, and can this be controlled adaptively?
  - *Basis in paper:* The paper notes "key quality sensitivity" as a limitation: "Less capable models may produce overly broad keys, causing over-merging" (§6.2). The default τmerge (3000 chars) is a blunt instrument to mitigate this. Future work proposes "adaptive key granularity" (§7).
  - *Why unresolved:* The key is the sole merging criterion; if keys are too broad (e.g., "machine learning" for an entire document), unrelated chunks merge, harming precision. If too narrow, merging fails. The paper provides no analysis of key distribution quality or τmerge sensitivity beyond a single default.
  - *What evidence would resolve it:* Ablation study A3 (broad vs. specific keys) as mentioned in §4.4, plus systematic variation of key generation prompts or post-processing to regulate specificity, measuring impact on chunk count reduction and retrieval metrics.

- **Question:** Can the sequential dependency in Stage 2 (rolling key propagation) be parallelized without significant loss of key coherence, and does speculative key prediction maintain the 89.8% cross-reference utilization rate?
  - *Basis in paper:* Identified as limitation (5): "Sequential enrichment... prevents naive batch parallelism. Speculative key prediction may partially address this" (§6.2). The 89.8% cross-reference rate (§5.2) depends on sequential propagation.
  - *Why unresolved:* The sequential loop (Algorithm 1) is a bottleneck for large corpora. Speculative prediction (guessing keys from prior context without full LLM pass) might introduce errors, breaking the rolling dictionary's utility and increasing synonym proliferation.
  - *What evidence would resolve it:* Implement a speculative pre-fetch system (e.g., using a smaller model or heuristic to guess keys), run parallel enrichment, and compare cross-reference rates, key reuse statistics, and retrieval performance against the fully sequential baseline.

- **Question:** What are the individual contributions of rolling keys versus key-based restructuring to the observed 9.3% chunk reduction and retrieval improvements, relative to structure-only chunking?
  - *Basis in paper:* Section 4.4 lists planned ablations: (A1) rolling keys disabled; (A2) restructuring disabled. Results are "reserved for a full evaluation in future work" (§4.4). The current analysis conflates both components in Config C.
  - *Why unresolved:* Without ablations, it is unclear whether gains come primarily from metadata coherence (rolling keys improving dense retrieval) or from merging related fragments (restructuring improving context). This hinders understanding of the core mechanism driving performance.
  - *What evidence would resolve it:* Running the ablation experiments A1 and A2: (A1) keep restructuring but use independent key generation per chunk; (A2) keep rolling keys but disable merging. Compare retrieval metrics (R@k, MRR) and chunk statistics (count, merge rate) against Config C and Config B.

## Limitations
- Prompt template, JSON validation logic, and retry parameters are unspecified, hindering exact replication.
- The evaluation corpus (18 Markdown documents, 30 queries) is proprietary; performance on diverse or non-Markdown formats is unknown.
- Rolling key update semantics with multi-key outputs and bin-packing ordering within key groups are ambiguous, affecting merge determinism and reuse rates.
- The paper provides no analysis of merged chunk semantic coherence or sensitivity of key granularity to prompt design.

## Confidence
- Structure-aware chunking prevents fragmentation: **High**
- Single-call enrichment + rolling keys reduces synonym proliferation: **Medium**
- Key-based merging yields coherent, retrieval-optimized chunks: **Low**
