# LMEB: Long-horizon Memory Embedding Benchmark
## Quick Facts
- **ArXiv ID:** 2603.12572
- **Source URL:** https://arxiv.org/abs/2603.12572
- **Reference count:** 40
- **Primary result:** LMEB introduces 22 datasets and 193 zero-shot tasks for long-horizon memory retrieval; evaluation shows orthogonality to passage retrieval (MTEB), top score 61.41, and no consistent scaling benefit.

## Executive Summary
The Long-horizon Memory Embedding Benchmark (LMEB) is a new evaluation framework designed to test embedding models on memory-intensive retrieval tasks involving fragmented, context-dependent, and temporally distant information. It comprises 22 datasets spanning four memory types (episodic, dialogue, semantic, procedural) with 193 zero-shot tasks, using both AI-generated and human-annotated data. Evaluation of 15 models (300M–10B parameters) using NDCG@10 and Recall@10 reveals that LMEB is a challenging benchmark (best score 61.41), that larger models do not consistently outperform smaller ones, and that performance on LMEB is largely independent of performance on passage retrieval benchmarks like MTEB. These findings indicate that long-horizon memory retrieval requires distinct capabilities not captured by existing benchmarks, making LMEB a valuable tool for advancing memory-augmented systems.

## Method Summary
LMEB adapts the MTEB v2 framework to evaluate text embedding models on long-horizon memory retrieval. It unifies 22 diverse datasets into a standard information retrieval format with queries, corpus, relevance judgments (qrels), and optional candidate pools. Models are evaluated zero-shot in two conditions: without task instructions (encoding only the query) and with instructions (prepending a task-specific instruction). Each dataset corresponds to one of four memory types—episodic, dialogue, semantic, or procedural—and includes tasks that require retrieving information fragmented across long contexts, temporally distant events, or dependent on dialogue history. The primary evaluation metric is NDCG@10, with Recall@10 also reported. Inputs are truncated to a maximum length of 1024 tokens (or 512 for some models), and some datasets employ specialized chunking strategies (e.g., semchunk) to handle long documents.

## Key Results
- Top model achieves 61.41 NDCG@10, indicating substantial room for improvement.
- Model performance does not consistently scale with parameter count; smaller models sometimes outperform larger ones on specific memory types.
- LMEB scores are nearly uncorrelated with MTEB passage retrieval scores (Pearson/Spearman ~0), demonstrating orthogonality of the two capabilities.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** LMEB and MTEB evaluate orthogonal capabilities; strong passage retrieval does not imply strong long-horizon memory retrieval.
- **Mechanism:** LMEB isolates memory-specific challenges (fragmentation, temporal dependence, context-dependency) through its dataset taxonomy and task design, whereas MTEB focuses on well-structured passage retrieval. The orthogonality is measured by near-zero Pearson/Spearman correlation between benchmark scores.
- **Core assumption:** Memory retrieval requires distinct representational and reasoning skills not captured by traditional IR tasks.
- **Evidence anchors:** [abstract] "...LMEB and MTEB are orthogonal (Pearson/Spearman ~0), indicating that passage retrieval skills do not transfer to memory-intensive tasks." [section] "5 Correlation Analysis" - presents correlation coefficients near zero between LMEB and MTEB (eng, v2) retrieval subset. [corpus] Corpus evidence for orthogonality is absent; the claim is derived from model evaluation scores, not corpus content.
- **Break condition:** Future models achieving high scores on both benchmarks with strong correlation would suggest capability convergence.

### Mechanism 2
- **Claim:** Larger model scale does not guarantee better performance on long-horizon memory tasks; architecture and training are critical.
- **Mechanism:** LMEB's diverse tasks expose limitations of scaling alone. Some smaller models (e.g., EmbeddingGemma-300M, bge-m3) outperform larger ones on specific memory types, indicating that task-specific optimization and data matter more.
- **Core assumption:** Memory retrieval benefits from architectural innovations (e.g., context handling, temporal modeling) beyond parameter count.
- **Evidence anchors:** [abstract] "Larger models do not always perform better." [section] "4 Main Results" - Tables 2 and 3 show instances where smaller models (e.g., EmbeddingGemma-300M) beat larger ones (e.g., KaLM-Embedding-Gemma3 12B) on NDCG@10. [corpus] Corpus evidence is not directly relevant; the mechanism is inferred from model performance rankings.
- **Break condition:** Consistently monotonic improvement with scale across all LMEB memory types and tasks.

### Mechanism 3
- **Claim:** LMEB's difficulty is appropriate because it challenges state-of-the-art models without being intractable.
- **Mechanism:** The benchmark combines varied granularities, corpus sizes, and query dependencies, yielding a top mean score of ~61.4 (NDCG@10), indicating room for progress but not collapse.
- **Core assumption:** A useful benchmark should separate current capability from theoretical limits.
- **Evidence anchors:** [abstract] "LMEB provides a reasonable level of difficulty; top score 61.41." [section] "4 Main Results" - states the best model achieved Mean (Dataset) score of 61.41 on N@10. [corpus] Corpus diversity metrics (weighted Jaccard) in "2.2 Dataset and Diversity Analysis" support that tasks are distinct, contributing to controlled difficulty.
- **Break condition:** Top models achieving near-perfect scores (>95) would indicate insufficient challenge.

## Foundational Learning
- **Concept:** Retrieval evaluation metrics (NDCG@k, Recall@k).  
  **Why needed here:** LMEB reports NDCG@10 as main metric; understanding graded relevance vs. binary hit-rate is key to interpreting scores.  
  **Quick check question:** Why does LMEB use NDCG@10 instead of simple accuracy for memory retrieval tasks?

- **Concept:** Memory taxonomies from cognitive science (episodic, semantic, procedural, dialogue).  
  **Why needed here:** LMEB's structure explicitly maps datasets to these types, each with different abstraction and temporal dependency.  
  **Quick check question:** How does "procedural memory" differ from "episodic memory" in terms of temporal dependency and abstraction level?

- **Concept:** Zero-shot evaluation protocol.  
  **Why needed here:** LMEB requires models to perform without task-specific fine-tuning, testing generalization of embedding capabilities.  
  **Quick check question:** What is the risk of evaluating memory retrieval in a few-shot or fine-tuned setting instead of zero-shot?

## Architecture Onboarding
- **Component map:**  
  Data loader → unified IR format (queries, corpus, qrels, candidates) → Model wrapper (encodes texts) → Retriever (computes similarity, ranks) → Evaluator (computes NDCG@10, Recall@10, aggregates).
- **Critical path:**  
  1. Wrap a new embedding model to output fixed-dimension vectors for a batch of texts.  
  2. For each dataset, load queries and corpus, encode them, compute similarity matrix.  
  3. Apply candidate pool restrictions if `candidates.jsonl` exists (e.g., dialogue history only).  
  4. Evaluate against qrels, collect metrics.
- **Design tradeoffs:**  
  - Uniform input length (1024 tokens) vs. dataset-specific needs (some require longer context). Truncation may hurt performance on long documents.  
  - Using instruction-tuned queries (`w/ inst.`) vs. bare queries (`w/o inst.`). Models vary in instruction sensitivity; LMEB reports both.  
  - Corpus chunking strategy (e.g., `semchunk` for long docs) affects granularity and recall; not all datasets use same chunking.
- **Failure signatures:**  
  - Extremely low scores (<10 NDCG@10) on all memory types: model wrapper likely broken or embedding dimension mismatch.  
  - High scores on semantic tasks but near-zero on episodic/dialogue: model may be overfitted to passage retrieval, lacks temporal reasoning.  
  - Large variance across datasets of same memory type: model sensitive to domain shift within a memory category.
- **First 3 experiments:**  
  1. Run evaluation with a known model (e.g., `bge-m3`) on a single small dataset (e.g., `SciFact`) to verify pipeline correctness; expect ~50-80 NDCG@10.  
  2. Compare `w/o inst.` vs `w/ inst.` scores on `LoCoMo`; instruction-sensitive models should show meaningful difference.  
  3. Compute correlation between LMEB-Procedural and MTEB scores for a set of models; expect near-zero or weakly positive (Pearson ~0.3), confirming orthogonality.

## Limitations
- The orthogonality between LMEB and MTEB is inferred from model score correlations without direct corpus-level analysis, leaving open the possibility that the relationship might differ with new models.
- The appropriateness of the benchmark's difficulty is not rigorously established; the top score of 61.41 suggests room for improvement but does not confirm optimal challenge level.
- Full reproducibility is hindered by unspecified details such as exact code version, preprocessing steps (e.g., chunking strategies), and dataset access restrictions.
