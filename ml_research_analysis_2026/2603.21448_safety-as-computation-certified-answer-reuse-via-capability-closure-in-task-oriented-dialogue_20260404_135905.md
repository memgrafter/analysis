# Safety as Computation: Certified Answer Reuse via Capability Closure in Task-Oriented Dialogue

## Quick Facts
- **arXiv ID:** 2603.21448  
- **Source URL:** https://arxiv.org/abs/2603.21448  
- **Reference count:** 24  
- **Primary result:** Reduces mean RAG calls from 13.7 to 1.31 and latency from 18.8 s to 340 ms on MultiWOZ 2.2 while eliminating all unsafe cache hits via formal containment checks.

## Executive Summary
Task-oriented dialogue systems repeatedly recompute answers each turn, ignoring content derivable from prior state. This paper reframes safety certification as a computation: it derives a fixed‑point closure of capabilities that implicitly contains every reachable answer under the current session configuration. By materializing all derivable follow‑up answers together with minimal provenance witnesses at each certified turn—stored in a Certified Answer Store (CAS) as Pre‑Answer Blocks (PAB)—subsequent queries are answered in sub‑millisecond time via exact mathematical containment checks. On MultiWOZ 2.2 this approach reduces redundant retrieval by over 90%, matches the theoretical prediction that RAG calls equal the number of distinct ontological classes visited (K = 1.31), and proves safe in multi‑tenant settings by preventing all cross‑tenant capability violations observed with embedding‑based caches.

## Method Summary
The system implements a six‑stage pipeline. First, a capability hypergraph **H** is extracted from dialogue data using co‑occurrence thresholds (Algorithm 1). For each turn, a belief‑state‑derived capability set **Aₜ** is assembled. A safety gate computes the monotone closure **Cₜ = cl(Aₜ)** via worklist iteration over hyperarc firings. At certified turns, a Pre‑Answer Block **PABₜ** is constructed: for every capability **v ∈ Cₜ \ Aₜ** with a template in **TemplateDB**, an answer is rendered and its minimal provenance witness **Wᵥ** (the smallest subset of **Aₜ** from which **v** derives) is computed. The **CAS** stores tuples **(ans, W, PABₜ, Fₛₙₐₚ, cert)**. For a new query, Stage 0 first checks the session **PABₜ**; if the primary capability **v\*** is present and **W ⊆ Cₜ** while the forbidden set **F** matches, the cached answer is returned. Otherwise, a fallback CAS lookup uses an embedding prefilter then the exact containment test; on failure, the full pipeline (Stages 1–4) runs, producing an answer and triggering **PAB** generation (Stage 5).

## Key Results
- Mean RAG calls drop from 13.7 to 1.31 per session, matching the distinct ontological classes visited (K).  
- End‑to‑end latency falls from 18.8 s to 340 ms.  
- Zero unsafe cache hits across 143 multi‑tenant violations seen with embedding‑based caching.

## Why This Works (Mechanism)

### Mechanism 1: Fixed‑Point Closure Precomputes All Reachable Answers
The safety certification step computes **cl(Aₜ)**, the smallest superset of the currently activated capabilities **Aₜ** that is closed under all hyperarc firings in the capability hypergraph. Because the closure operator is monotonic (capabilities once derived persist within a planning horizon), **cl(Aₜ)** is mathematically equivalent to the set of all answers derivable from the session state. This precomputation occurs once per certified turn and implicitly contains every follow‑up answer that could ever be produced without additional information.

### Mechanism 2: Pre‑Answer Blocks Materialize Derivable Follow‑Ups
From **cl(Aₜ) \ Aₜ**, the system materializes a **PAB** entry for each capability **v** that has a natural language template. The answer **ansᵥ** is rendered using current closure facts, and a minimal why‑provenance witness **Wᵥ** is computed—the smallest subset of **Aₜ** sufficient to derive **v**. Storing **(v, ansᵥ, Wᵥ, certᵥ)** certifies that **ansᵥ** is safely reusable whenever **Wᵥ** is contained in a future closure and the forbidden set **F** is unchanged.

### Mechanism 3: Formal Containment Guarantees Safe Reuse
During lookup, a cached answer is returned iff (1) its witness **W** is a subset of the current closure **Cₜ** and (2) the forbidden set snapshot **Fₛₙₐₚ** matches the current **F**. This exact mathematical check—*not* an embedding similarity—prevents unsafe cross‑tenant capability violations. The subset test is a fast set‑membership operation; combined with the **PAB**’s precomputation, it yields sub‑millisecond response times.

## Foundational Learning
- **Capability Hypergraph and Closure**  
  *Why needed:* Models how capabilities combine to derive new answers; the closure operator computes all reachable answers from a given set.  
  *Quick check:* What property makes **cl(·)** suitable for incremental maintenance in a dialogue session? (Answer: monotonicity.)

- **Provenance Witness**  
  *Why needed:* Provides a minimal certificate explaining *why* an answer is derivable, enabling safe reuse without full re‑computation.  
  *Quick check:* How does **MinWitness** find the smallest **A′ ⊆ Aₜ** such that **v ∈ cl(A′)**? (Answer: via why‑provenance in the hypergraph.)

- **Session Closure and Monotonicity**  
  *Why needed:* Explains why RAG calls scale with distinct ontological classes visited (K) rather than dialogue length.  
  *Quick check:* Under the Monotonicity Assumption, why are the incremental closures **Δₜ = Cₜ \ Cₜ₋₁** disjoint?

- **Containment Check vs. Semantic Similarity**  
  *Why needed:* Distinguishes CAS’s exact safety guarantee from unsafe embedding‑based caches in multi‑tenant settings.  
  *Quick check:* Why does a cosine‑similarity cache allow unsafe hits across tenants while a containment check does not?

## Architecture Onboarding
**Component map**  
Stage 0 → Stages 1–4 → Stage 5  
(Stage 0: PAB/CAS lookup; Stages 1–4: Beyond‑RAG understanding, capability assembly **φ**, safety gate closure, execution; Stage 5: PAB construction and CAS write)

**Critical path per turn**  
1. Compute **Aₜ** from belief state → **Cₜ = cl(Aₜ)**.  
2. Build **PABₜ** from **Cₜ \ Aₜ** using **TemplateDB**.  
3. On user query, extract primary capability **v\***.  
4. Try Tier 1 (session **PAB**) → Tier 2 (CAS with embedding prefilter → containment check).  
5. On hit, return cached answer; on miss, run full pipeline, then store result in CAS and update session **PAB**.

**Design tradeoffs**  
- *Storage vs. latency:* **PAB** stores all derivable follow‑ups (memory cost) but cuts RAG calls drastically.  
- *Coverage vs. completeness:* **TemplateDB** coverage **p** directly affects **PAB** hit rate; lower **p** increases RAG but not unsafety.  
- *Exactness vs. speed:* Containment checks are exact but require subset testing; optimized with bit‑vectors or hash indices.  
- *Safety vs. flexibility:* Multi‑tenant safety relies on explicit **F** comparison; any **F** change must propagate carefully.

**Failure signatures**  
- High RAG count → low **p** or frequent witness non‑containment.  
- Unsafe cache hits → broken **F** tracking or bypassed containment check.  
- False rejections → incomplete **φ** (underestimated **Cₜ**) or oversized witness frontier.  
- AND‑violations → hypergraph extraction errors (conjunctive arcs missing preconditions).

**First 3 experiments**  
1. **Hypergraph extraction sanity:** Run Algorithm 1 on a MultiWOZ subset; verify conjunctive arcs ≈ 73.5% and mean fan‑in ≈ 2.21.  
2. **PAB construction validation:** For fixed **Aₜ**, ensure every entry satisfies **Wᵥ ⊆ cl(Aₜ)** and **v ∈ cl(Wᵥ)**.  
3. **Containment check correctness:** Populate CAS, mutate **Cₜ** and **F**, confirm answers reuse iff **W ⊆ Cₜ** and **Fₛₙₐₚ = F**.

## Open Questions the Paper Calls Out
1. **Formal bound on safety vs. belief tracker recall**  
   What is the tight bound on violation probability as a function of tracker recall? Current guarantees assume perfect **φ**; real trackers have imperfect recall.

2. **Generalizing hypergraph extraction to tool‑calling schemas**  
   Can Algorithm 1 be adapted to arbitrary tool‑calling logs without belief‑state supervision? The noise model differs (failed invocations, no explicit slots).

3. **Tighter hit‑rate bound under empirical priors**  
   The (1 − 1/e) pre‑fetch guarantee assumes uniform priors; real conversation priors are non‑uniform. A weighted submodular analysis could yield tighter bounds.

4. **Cascade‑free invalidation for persistent sessions**  
   When forbidden set **F** expands between sessions, invalidating **PAB** entries whose witnesses overlap **F** may cascade. A method to contain such cascades while preserving soundness is open.

## Limitations
- Hypergraph extraction details (θ, slot‑subset iteration, cross‑domain patterns) are underspecified.  
- Primary capability mapping from user utterances (**CoarseIntent**) is opaque and likely requires an external NLU model.  
- **TemplateDB** content (28 templates) is not provided; generating accurate templates for all node types is non‑trivial.  
- **MinWitness** algorithm is not described; implementing efficient why‑provenance for hypergraph closures is complex.  
- Monotonicity Assumption may be violated by slot retractions, requiring recovery per Theorem 10.1.

## Confidence
- **Closure precomputation**: *Medium* (solid theory but depends on hypergraph extraction and monotonicity).  
- **Sub‑ms reuse**: *Medium* (achieved experimentally but hinges on **TemplateDB** coverage **p ≈ 100%** and witness efficiency).  
- **Safety via containment**: *High* (theorem‑backed and zero unsafe hits observed, assuming correct **MinWitness**).

## Next Checks
1. **Hypergraph extraction validation**: Re‑run Algorithm 1 with θ = 0.75; confirm graph statistics (conjunctive arcs ≈ 73.5%, mean fan‑in ≈ 2.21) match the paper.  
2. **PAB witness correctness**: For sampled turns, audit that every **PAB** entry’s witness is minimal and sound (**Wᵥ ⊆ cl(Aₜ)** and **v ∈ cl(Wᵥ)**).  
3. **Containment check robustness**: Test CAS lookup under controlled **Cₜ**/**F** mutations; ensure answers return *iff* **W ⊆ Cₜ** and **F** unchanged, and that closure shrinkage or **F** changes trigger misses.
