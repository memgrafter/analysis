# Linear-PAL: A Lightweight Ranker for Mitigating Shortcut Learning in Personalized, High-Bias Tabular Ranking

## Quick Facts
- arXiv ID: 2602.00013
- Source URL: https://arxiv.org/abs/2602.00013
- Reference count: 17
- Primary result: Achieves superior de-biased ranking quality (Relevance AUC 0.7626 vs. 0.6736) while reducing training latency by 43× (40s vs. 1762s), enabling frequent retraining for real-time personalization.

## Executive Summary
Deep ensemble rankers overfit to position bias in high-bias e-commerce settings, harming true relevance by learning spurious correlations between display rank and user clicks—a form of shortcut learning. Linear-PAL addresses this with a intentionally constrained linear model that enforces de-biasing through explicit feature conjunctions between item attributes and rank, aggressive ℓ₂ regularization, and a vectorized integer hashing trick for efficiency. On a large-scale e-commerce dataset, it substantially improves de-biased ranking quality (Relevance AUC +0.089) while being 43× faster to train than deep ensembles, making frequent retraining feasible for real-time personalization.

## Method Summary
Linear-PAL is a logistic regression ranker designed to predict intrinsic item relevance in the presence of severe position bias. Inputs are impression logs containing item features (e.g., price, ratings), user context (e.g., UCOEC), click labels, and historical display rank. The core innovation is a cross-product kernel that explicitly combines every quantized item feature bin with the one-hot rank vector via vectorized integer hashing (interaction ID = `bin(feature) * M + rank`), creating a sparse feature space of item⊗rank interactions. The model is trained with very strong ℓ₂ regularization (`C=1e-5`) to suppress noisy, high-variance interaction weights and avoid overfitting the position signal. At inference, the rank feature is forcibly set to the one-hot for rank 1, intervening on the causal graph to produce a de-biased score invariant to display position.

## Key Results
- **De-biased quality**: Relevance AUC of 0.7626, beating a deep ensemble baseline (0.6736) by +0.089.
- **Efficiency**: Training time of 40 seconds vs. 1762 seconds for the deep ensemble (43× speedup).
- **Regularization trade-off**: Relevance AUC peaks at `C=1e-5`, while Standard AUC (predictive accuracy on biased data) peaks near `C=0.01`, demonstrating the regularization-induced tension between fitting bias and learning relevance.

## Why This Works (Mechanism)
**Mechanism 1: Explicit Feature Conjunctions**
- **Claim**: Explicit item⊗rank conjunctions force the model to learn rank-specific relevance weights linearly, preventing it from overfitting to the rank signal.
- **Mechanism**: The Cartesian product between quantized item features Φ(x) and one-hot rank Ψ(k) yields a kernel K(x,k)=Φ(x)×Ψ(k). This makes the model’s sensitivity to any item feature explicitly rank-dependent (e.g., ∂Logit/∂Price = w_price + Σ w_price×rank·I(rank=k)). The known non-linear interaction structure is hard-coded, removing the need for non-convex optimization to discover it.
- **Core assumption**: All necessary de-biasing decision boundaries can be captured by pairwise interactions between item attributes and rank.
- **Evidence anchors**: Abstract cites “enforces de-biasing through structural constraints: explicit feature conjunctions”; Section 3.1 and 4.3 define the kernel expansion and rank-dependent derivative. Corpus lacks direct supporting evidence.
- **Break condition**: If higher-order interactions (e.g., item⊗user⊗rank) are necessary, this linear conjunction space will be insufficient.

**Mechanism 2: Vectorized Integer Hashing**
- **Claim**: Converting feature crossing to vectorized arithmetic replaces slow string operations with O(N) computation, enabling the 43× training speedup.
- **Mechanism**: Assigning a large multiplier M to feature bins, the interaction ID is computed as `(Bin(f) * M) + k`. This single arithmetic operation replaces concatenation and string hashing while remaining reversible for weight interpretation.
- **Core assumption**: The ID space is collision-free for the chosen M and feature sets.
- **Evidence anchors**: Abstract mentions “Vectorized Integer Hashing technique… replacing string-based operations with O(N) vectorized arithmetic”; Section 4.5 gives the reversible ID computation. No corpus evidence.
- **Break condition**: Very high-cardinality features or ranks could cause integer overflow or exceed sparse memory efficiency.

**Mechanism 3: Aggressive Regularization**
- **Claim**: ℓ₂ regularization with `C=1e-5` acts as a soft feature selector, inducing an information bottleneck that suppresses high-variance position interactions and forces reliance on dense content features.
- **Mechanism**: The heavy penalty drives coefficients for noisy, sparse feature×rank interactions to near zero. Minimization then primarily adjusts the `w_item` term (base relevance) and only a few robust interaction terms, avoiding the “shortcut” of memorizing the exact position bias curve.
- **Core assumption**: The signal for intrinsic relevance is carried by features with dense, lower-variance gradients compared to the position signal.
- **Evidence anchors**: Abstract notes “aggressive regularization (C=1e-5)” and “Shortcut Learning… overfitting to the rank signal”; Section 5.3–5.4 and 6.1 show ablation where Relevance AUC peaks at `C=1e-5` while Standard AUC peaks at `C=0.01`. No corpus evidence.
- **Break condition**: In very low-noise data or with perfectly separable position bias, such extreme regularization might underfit and discard useful interaction signals.

## Foundational Learning
**Concept: Position Bias as Confounding (Causal Inference)**
- Why needed here: To understand why modeling `P(click|item, position)` is flawed for ranking and why we need `P(click|do(position=1), item)`. The paper’s inference intervention is a do-calculus operation.
- Quick check: If you set all items to Rank 1 during inference, which term in Equation (2) becomes constant for all items, and why does this make ranking shift-invariant? The position bias term `f(k)` becomes constant, so differences in scores reflect only `f(x)` (intrinsic relevance).

**Concept: Feature Quantization for Linear Models**
- Why needed here: Continuous features must be binned into categorical bins that can participate in the cross-product kernel (Equation 6). Different binning strategies (Eq 7) preserve signal for different data types.
- Quick check: Why might a standard logarithm bin `⌊ln(1+v)⌋` be inappropriate for a similarity score in [-1,1], and what does the paper's adaptive function do instead? Log bins assume positive, heavy-tailed data; the adaptive piecewise function handles signed values by preserving symmetry and using linear bins near zero.

**Concept: Regularization as Inductive Bias / Feature Selection**
- Why needed here: The cross-product explosion creates ~12k features. Strong ℓ₂ (`C=1e-5`) is the primary mechanism to avoid overfitting and implement “soft” feature selection without manual search.
- Quick check: In the ablation curve (Fig 4), why does Relevance AUC increase as `C` decreases (regularization strengthens), while Standard AUC (Fig 5) peaked at much higher `C`? Stronger regularization suppresses fit to the position bias signal (improving de-biased relevance) but hurts raw predictive accuracy on the biased training distribution.

## Architecture Onboarding
Component map: Raw Logs -> COEC/UCOEC Calculation -> Adaptive Binning -> Vectorized Cross-Product -> Sparse Matrix -> L2-Regularized Logistic Regression -> Score with rank=1.

Critical path: Raw interaction logs are first used to compute propensity-normalized metrics (COEC, UCOEC). All numeric features are adaptively quantized. For each sample, base feature bins are crossed with the one-hot rank via vectorized integer hashing to generate a sparse binary vector. A logistic regression model with ℓ₂ penalty `C=1e-5` is trained on this matrix. At serving, the rank input is fixed to the one-hot for position 1 to produce de-biased scores.

Design tradeoffs:
- Interpretability vs. Capacity: Linear weights are fully inspectable (e.g., `PriceHigh×Rank1` weight) vs. DNN black boxes. Capacity is deliberately limited to prevent shortcut learning.
- Speed vs. Flexibility: 40s training enables hourly retraining vs. 30min+ for deep models. This trades potential long-tail pattern capture for real-time personalization agility.
- Explicit vs. Implicit Interactions: Requires domain knowledge to ensure key conjunctions are present in the feature set (via binning) vs. DNNs learning them implicitly (but often failing in high-bias regimes).

Failure signatures:
- Shortcut learning detected: High Standard AUC (>0.81) but very low Relevance AUC (<0.68) on validation. Model has perfectly fit the position bias.
- Underfitting: Both Standard and Relevance AUC are low (<0.75). Likely `C` is too small or key feature bins are missing.
- Concept drift: Sudden drop in Relevance AUC on new data despite stable Standard AUC. The position bias distribution has shifted, and the model’s interaction weights are mis-calibrated. Solution: increase retraining frequency (enabled by speed).

First 3 experiments:
1. Regularization Sweep: Train models across `C` in `[1e-6, 1e-5, 1e-4, ..., 1.0]`. Plot Standard AUC and Relevance AUC. Verify the divergence point where Relevance AUC peaks (`C≈1e-5`) while Standard AUC is still high.
2. Feature Ablation - Interaction Terms: Train a Linear-PAL variant without the cross-product features (only `w_pos` and `w_item`). Expect a severe drop in Relevance AUC, proving the interaction kernel's necessity.
3. Speed & Quality Benchmark: Replicate the evaluation in Table 2/Fig 3. Train the Deep MLP and Microsoft Ensemble on the same 4.2M sample, 8-core CPU setup. Confirm >40x speedup and higher Relevance AUC for Linear-PAL. This validates the core Pareto claim.

## Open Questions the Paper Calls Out
1. **Domain generalizability**: Does Linear-PAL maintain its de-biasing advantage across multiple e-commerce domains with varying degrees of position bias, or is its performance specific to the high-bias regime of Viator's FTTD pages? Basis: Evaluation only on a single dataset from Viator with extreme position bias (Propensity AUC ≈ 0.81). No multi-domain tests. Evidence needed: Multi-dataset study covering various e-commerce domains (e.g., product search, news recommendation) with a range of bias strengths.
2. **Regularization selection**: Is the aggressive regularization (`C=1e-5`) that enables Linear-PAL’s de-biasing robust across datasets, or does it require dataset-specific tuning? Can we develop a data-driven criterion for selecting the optimal strength? Basis: Ablation on one dataset; optimal `C` likely depends on data sparsity, bias magnitude, or feature set. Evidence needed: Systematic `C` variation across multiple datasets, measuring Relevance AUC and prediction-ranking gap; correlate optimal `C` with dataset properties.
3. **Sufficiency of linear conjunctions**: Are explicit linear feature conjunctions between item attributes and rank sufficient to model all relevant position-bias interactions, or would higher-order (e.g., `item⊗item × rank`) or non-linear interactions provide additional gains? Basis: Linear-PAL uses only pairwise `Φ(x)×Ψ(k)`; assumes necessary boundaries are known a priori. Evidence needed: Extend Linear-PAL to include higher-order interaction features and test for Relevance AUC improvements; or statistical tests on added features.
4. **Personalization effect**: Does Linear-PAL’s explicit interaction framework actually produce superior personalized ranking compared to non-personalized baselines or deep models that incorporate user context, and if so, which user segments benefit most? Basis: Personalization claim is speculative; only overall Relevance AUC reported, no per-user analysis. Evidence needed: Cohort analysis (e.g., high- vs. low-activity users) and comparison to personalized deep models; online A/B test measuring engagement per segment.

## Limitations
- Exact feature engineering protocol is unspecified: the final list of base features, quantization thresholds, and COEC/UCOEC calculation details are not fully enumerated.
- The source of ground-truth relevance for computing Relevance AUC is ambiguous; COEC is used as a feature, not a label, and the ultimate relevance signal is not clearly defined.
- Generalizability is limited: claims are validated on a single large-scale e-commerce dataset; performance in other high-bias domains (e.g., news, travel) is unknown.

## Confidence
- Speed & Pareto Efficiency: High (explicitly reported and reproducible)
- Mechanism 1 (Explicit Conjunctions): Medium (mathematics clear, but evidence relies on ablation/correlation, not causal proof of sufficiency)
- Mechanism 2 (Vectorized Hashing): Medium (arithmetic trick described and plausible, but collision risk and exact impact not stress-tested)
- Mechanism 3 (Aggressive Regularization): Medium (ablation curve compelling, but “information bottleneck” interpretation inferred)
- Relevance Metric Validity: Low (lack of clarity on gold-standard relevance signal limits confidence that AUC gains reflect true unbiased quality)
