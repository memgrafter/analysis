# Learning Query-Aware Budget-Tier Routing for Runtime Agent Memory

## Quick Facts
*   **arXiv ID:** 2602.06025
*   **Source URL:** https://arxiv.org/abs/2602.06025
*   **Reference count:** 40
*   **Primary result:** BudgetMem achieves superior accuracy-cost trade-offs for runtime memory extraction via a modular, query-aware router trained with RL.

## Executive Summary
Runtime memory extraction for LLM agents lacks explicit control over the performance-cost trade-off. This paper proposes BudgetMem, a system that structures memory processing into modular components, each offered at three quality tiers (LOW/MID/HIGH). A lightweight router, trained with reinforcement learning, selects a tier for each module at runtime based on the query. This enables fine-grained, query-aware allocation of compute. Evaluations on multiple datasets show BudgetMem consistently outperforms baselines, particularly under high-budget conditions, and generates superior accuracy-cost frontiers under constrained budgets, demonstrating effective controllable trade-offs.

## Method Summary
BudgetMem implements a fixed pipeline of memory modules (filter, entity, temporal, topic, summary). Each module is realized with three complementary tiering strategies: **Implementation** (heuristic → BERT → LLM), **Reasoning** (direct → CoT → reflection), or **Capacity** (small → medium → large LLM). A shared router ingests the query and intermediate state to select a tier per module. The router is trained via Proximal Policy Optimization (PPO) on a reward that combines task performance (e.g., F1-score) with a normalized cost penalty, scaled to align reward variances. This yields a single policy that can produce smooth performance-cost trade-off curves by adjusting a single λ parameter at test time.

## Key Results
*   BudgetMem variants (IMP, REA, CAP) significantly outperform strong baselines (e.g., single-tier full extraction, prior adaptive systems) in high-budget settings, with the Capacity strategy using LLaMA-3.3-70B achieving average F1 45.72 and Judge score 59.99 at a cost of $1.38.
*   Under constrained budgets, BudgetMem consistently yields superior accuracy-cost frontiers. Implementation and Capacity tiering cover wide cost ranges, while Reasoning tiering provides fine-grained tuning within a narrower band.
*   Ablation studies confirm the critical role of reward-scale alignment (α) in preventing the router from collapsing to a low-cost, low-quality policy.

## Why This Works (Mechanism)

### Mechanism 1
*   **Claim:** Modular budget-tier interfaces enable granular, module-level performance-cost control without altering pipeline structure.
*   **Mechanism:** Each memory module exposes three fixed-quality tiers (LOW/MID/HIGH) via a common input-output contract. The router selects tiers per module at runtime, allowing compute to be allocated selectively based on query needs rather than a single global budget.
*   **Core assumption:** Different modules contribute unevenly to overall task performance; routing allows high compute where it matters most.
*   **Evidence anchors:**
    *   [abstract] "BudgetMem structures memory processing as a set of memory modules, each offered in three budget tiers… A lightweight router performs budget-tier routing across modules."
    *   [section 4.1] "Each module M in the pipeline is exposed through a common budget-tier interface… enabling module-level budget control."
    *   [corpus] Weak direct support; related work (e.g., ShardMemo) uses tiered memory but not for runtime extraction routing.

### Mechanism 2
*   **Claim:** Reinforcement learning with reward-scale alignment trains a router to balance task reward against extraction cost under varying budget preferences.
*   **Mechanism:** The router policy πθ is optimized via PPO on objective r = r_task + λ·α·r_cost, where r_cost is normalized and α = std(rtask)/std(rcost) aligns reward variances. This yields a single policy generalizing across λ.
*   **Core assumption:** Task and cost rewards have disparate scales/variance; without α, optimization biases toward the higher-variance term, causing degenerate low-cost policies.
*   **Evidence anchors:**
    *   [abstract] "The router is trained with reinforcement learning (PPO) under a reward that balances task performance against extraction cost."
    *   [section 4.3] "We introduce a simple variance-based alignment factor: α = std(rtask) / (std(rcost) + ϵ)… Without reward-scale alignment… the router collapses to selecting the LOW tier."
    *   [section 6.3] Ablation shows reward-scale alignment prevents collapse to low-cost, low-quality policies.

### Mechanism 3
*   **Claim:** Complementary tiering strategies (implementation, reasoning, capacity) provide distinct, exploitable performance-cost characteristics across budget regimes.
*   **Mechanism:**
    *   *Implementation tiering* upgrades module algorithms (heuristics → BERT → LLM), yielding broad cost range and rapid gains at moderate budgets.
    *   *Reasoning tiering* varies inference behavior (direct → CoT → reflection) within a fixed model, offering fine-grained quality tuning at concentrated cost.
    *   *Capacity tiering* swaps model size (small → medium → large), extending the frontier at high budgets but with less granularity.
*   **Core assumption:** Different cost-quality trade-off dimensions are orthogonal; a unified framework can compare them meaningfully.
*   **Evidence anchors:**
    *   [abstract] "We study three complementary strategies for realizing budget tiers: implementation (method complexity), reasoning (inference behavior), and capacity (module model size)."
    *   [section 6.2] Figure 2 shows implementation/capacity span wider cost ranges; reasoning shows narrower cost spread but quality refinement.
    *   [section 4.2] Detailed tier definitions for each strategy per module.

## Foundational Learning

### Concept: Reinforcement Learning (PPO) for Sequential Decision-Making
*   **Why needed:** Routing is a sequential decision problem over modules with non-differentiable components; PPO optimizes the policy under cost-aware rewards.
*   **Quick check:** How does the PPO objective in Eq.13 handle multiple module decisions per episode, and why is entropy averaged instead of summed?

### Concept: Modular System Design with Fixed Interfaces
*   **Why needed:** Allows independent tiering of components and a shared router; decouples budget control from pipeline structure.
*   **Quick check:** What would break if modules had varying output formats across tiers instead of a fixed budget-tier interface?

### Concept: Reward Normalization and Scale Alignment
*   **Why needed:** Task reward (e.g., F1 ∈ [0,1]) and cost reward (raw token count) have disparate scales; improper scaling destabilizes policy updates.
*   **Quick check:** Why use sliding-window quantile normalization for cost (Eq.9) instead of min-max over the entire dataset?

### Concept: Budget-Tier Interface as an Abstraction
*   **Why needed:** Defines a uniform contract for quality levels, enabling the router to operate without knowing implementation details of any tier.
*   **Quick check:** If a module's HIGH tier output format differed from its LOW tier, how would the router's state representation need to change?

### Concept: Controller Generalization via Single-Policy Multi-Objective RL
*   **Why needed:** Training one policy that generalizes across λ values is more efficient than training Separate policies per budget; it enables smooth interpolation.
*   **Quick check:** What explicit mechanisms in the reward design encourage the policy to learn a spectrum of behaviors rather than a single optimal action per state?

### Concept: Cost Modeling and Normalization for RL Stability
*   **Why needed:** Raw cost (token count) has a heavy-tailed distribution; normalization with robust quantiles (Q5/Q95 on √raw_cost) prevents outliers from dominating the cost reward signal.
*   **Quick check:** Why transform raw cost with a square root before computing quantiles, as mentioned in section 4.3?

## Architecture Onboarding

### Component map
Contriever Retriever -> Router (shared actor-critic) -> [Filter Module] -> Parallel [Entity, Temporal, Topic Modules] -> [Summary Module] -> Answer Generator (LLaMA/Qwen)

### Critical path
1.  **Input:** User query q, agent history H → chunk store C.
2.  **Retrieve:** R(q,C) → C_q (top-K relevant chunks).
3.  **Route per module:** For each module in pipeline order:
    *   Router observes state s_k (q, previous module output, module ID).
    *   Selects tier a_k ∈ {LOW, MID, HIGH}.
    *   Module M_k executes at selected tier, produces output.
4.  **Answer:** Final extracted memory m → f_ans(q,m) → predicted answer ˆy.
5.  **Reward:** r_task from ˆy vs. ground truth; r_cost from sum of normalized costs per tier.
6.  **Update:** PPO batch update on router policy πθ.

### Design tradeoffs
*   **Granularity vs. Overhead:** Module-wise routing adds router calls but enables fine control; coarser (per-stage) routing would reduce decisions but limit adaptability.
*   **Strategy orthogonality:** IMP/REA/CAP are evaluated separately; combining them (e.g., capacity-tiered reasoning) would explode the router's action space.
*   **Prompt control:** To isolate tier effects, HIGH-tier prompt template is reused for all tiers within a strategy; this may understate LOW-tier potential if prompts are mismatched.
*   **Cost modeling:** Non-LLM tiers treated as negligible cost; if heuristics/BERT become expensive, normalization may misrepresent true relative costs.

### Failure signatures
*   **Router collapse:** All queries → LOW tier across modules (observed without reward-scale alignment). Indicates cost term dominated updates.
*   **Degenerate tier selection:** One tier (e.g., HIGH) selected for all modules regardless of λ. Suggests insufficient state conditioning or poor reward shaping.
*   **Performance-cost decoupling:** Cost varies but task performance constant; indicates tier quality gaps are negligible or router not learning utility signals.
*   **Transfer failure:** Router trained on LLaMA fails on Qwen if tier cost/quality distributions shift significantly; paper reports successful transfer, implying robustness.

### First 3 experiments
1.  **Vary λ to trace Pareto frontiers:** For each tiering strategy (IMP/REA/CAP), sweep λ and plot Judge vs. Cost. Verifies controllable trade-offs and relative strategy characteristics.
2.  **Ablate reward-scale alignment:** Train with/without α under capacity tiering. Confirms alignment prevents collapse to LOW-tier policies.
3.  **Compare tiering strategies:** Under fixed backbone (LLaMA), run all three strategies at multiple λ points; compare cost ranges and frontier shapes. Validates hypothesis: IMP/CAP widen budget coverage, REA refines within band.

## Limitations
*   Retrieval implementation details (Contriever specifics, chunk size, top-K) and key PPO hyperparameters (GAE, sliding window size) are unspecified, hindering exact replication.
*   Cost model treats heuristic and BERT tiers as having negligible cost; real-world compute may narrow effective cost gaps and alter frontier ordering.
*   All tiers reuse the HIGH-tier prompt template, potentially underrepresenting the potential of lower-tier strategies.
*   Evaluation is limited to three datasets (LoCoMo, LongMemEval, HotpotQA); domain robustness and generalizability remain unknown.

## Next Checks
1.  **Reproduce PPO stability:** Implement sliding-window normalization and α alignment. Sweep window size to ensure router does not collapse and the Pareto curve is stable across random seeds.
2.  **Measure actual non-LLM costs:** Time heuristic and BERT module executions under realistic conditions; recompute accuracy-cost frontiers using true compute costs to see if the relative advantage of IMP/CAP strategies changes.
3.  **Correlate tier choices with query features:** Log router selections per module for a validation set; compute correlation with query length, entity count, or topic complexity to validate query-awareness and identify which modules benefit most from high tiers.
