# EvoSkills: Self-Evolving Agent Skills via Co-Evolutionary Verification

## Quick Facts
*   **arXiv ID:** 2604.01687
*   **Source URL:** https://arxiv.org/abs/2604.01687
*   **Reference count:** 40
*   **Primary result:** A co-evolutionary framework achieves a 71.1% pass rate on SkillsBench, a 40.5 pp improvement over no-skill baselines and 17.6 pp over human-curated skills, with strong cross-model transfer.

## Executive Summary
EvoSkills addresses the challenge of autonomous skill generation for LLM agents on complex, multi-step professional tasks. Manually crafted skills are label-intensive and often misaligned with how LLM agents actually reason. This paper introduces a co-evolutionary framework where a Skill Generator iteratively refines multi-file skill packages, guided by a Surrogate Verifier that provides structured feedback using only execution outputs (without hidden ground-truth tests). On the SkillsBench benchmark, EvoSkills substantially outperforms no-skill, self-generated, and human-curated baselines. The evolved skills demonstrate strong portability, yielding consistent large gains when transferred to six different LLM families, indicating they encode reusable task structures rather than model-specific quirks.

## Method Summary
The core of EvoSkills is an iterative loop between two independent LLM components. A **Skill Generator** creates or refines a skill—a multi-file bundle containing documentation (`SKILL.md`) and executable scripts (`scripts/`). It executes the skill in a sandboxed environment and, based on feedback, updates its context to improve the skill. A separate **Surrogate Verifier** evaluates the skill's outputs with its own dynamically generated test suite. If the surrogate reward is low, it returns a structured diagnosis (failed tests, root cause, suggestions) to the Generator's context. If the surrogate passes but the hidden ground-truth oracle fails, only a pass/fail bit is returned, and the Verifier escalates its tests. This **generate–verify–refine** cycle repeats until the oracle passes or a fixed budget (5 oracle rounds, 15 surrogate retries) is exhausted. Information isolation between the Generator and Verifier is enforced to prevent biased, uninformative tests.

## Key Results
*   EvoSkills achieves a 71.1% pass rate on SkillsBench (Claude Code), a 40.5 pp absolute improvement over the no-skill baseline (30.6%) and 17.6 pp over human-curated skills (53.5%).
*   The framework outperforms five alternative baselines (including one-shot self-generation and Skill-Creator) on both Claude Code and Codex agents.
*   Skills evolved on Claude Opus 4.6 transfer effectively to six other LLMs (GPT-5.2, Claude Sonnet, Haiku, Qwen3-Coder, DeepSeek V3, Mistral Large), each showing 35–44 pp gains over their respective no-skill baselines.

## Why This Works (Mechanism)

### Mechanism 1: Co-evolutionary Verification Loop
*   **Claim:** Alternating refinement between the Skill Generator and Surrogate Verifier steadily improves skill quality by providing structured, actionable feedback without relying on opaque oracle signals.
*   **Mechanism:** The generator produces a skill bundle and executes it. The independent verifier evaluates outputs with a test suite, yielding a surrogate reward. On failure, it generates a diagnostic (failed tests, root-cause analysis, suggestions) appended to the generator’s context. On surrogate success but oracle failure, only a pass/fail bit is returned, prompting the verifier to escalate its tests. This generate–verify–refine cycle repeats.
*   **Core assumption:** An informationally isolated verifier can produce high-fidelity feedback the generator can act upon, even without access to the hidden ground-truth tests.
*   **Evidence anchors:** [Abstract] describes the co-evolutionary framework with a verifier that "co-evolves to provide informative and actionable feedback without access to ground-truth test content." [Section 3.3] formalizes the alternating optimization (Eq. 5–6) and Algorithm 1. [Section 4.3] Ablation: removing the surrogate verifier drops pass rate from 71.1% to 41.1% (–30.0 pp).
*   **Break condition:** If the verifier’s test suite diverges from hidden oracle criteria (e.g., precision, edge cases), the generator may optimize for surrogate performance while still failing the oracle—the "surrogate–GT gap" shown in the exoplanet case study (Appendix E).

### Mechanism 2: Human–Machine Cognitive Misalignment Correction
*   **Claim:** Self-evolved skills outperform human-curated ones because they capture the agent’s actual reasoning patterns, tool-use strategies, and decomposition preferences, rather than workflows designed by human experts that may misalign with the model’s context processing.
*   **Mechanism:** The agent iterates using its own execution traces and failure diagnostics. Each revision is guided by concrete errors observed during execution, allowing the skill to adapt to the model’s strengths (e.g., specific tool invocation patterns, reasoning step length) and avoid misalignments inherent in manually authored procedures.
*   **Core assumption:** Human-designed abstraction and workflow heuristics do not naturally match how LLM agents reason across long horizons; adaptation to the agent’s own behavior yields more effective procedural guidance.
*   **Evidence anchors:** [Abstract] notes manually crafted skills "may suffer from human–machine cognitive misalignment." [Section 4.5] Per-domain analysis (Fig. 6) shows human-curated skills degrade in Natural Science, while self-evolved skills yield large gains. [Takeaway 1, Section 4.2] states agents with self-evolved skills "outperform those guided by human-curated procedures… by encoding their own reasoning patterns."
*   **Break condition:** If the agent’s baseline behavior is biased or suboptimal (e.g., prone to certain errors), self-evolution could amplify those weaknesses. The framework assumes the oracle ultimately corrects this, but with limited oracle rounds, persistent misalignment may remain.

### Mechanism 3: Transferable Task Structure Encoding
*   **Claim:** Self-evolved skills generalize across diverse LLM families because they encode reusable task structures and procedural abstractions rather than model-specific artifacts.
*   **Mechanism:** The skill package bundles domain instructions, executable scripts, and references into a portable format. The evolution process optimizes for execution in a generic environment (not tied to a particular model’s quirks), so the resulting workflow abstracts away model-specific reasoning patterns and focuses on logical sequences, data transformations, and verification steps.
*   **Core assumption:** Procedural knowledge can be represented in a model-agnostic form that retains utility when used by different LLM agents.
*   **Evidence anchors:** [Abstract] highlights "strong generalization and the portability of the encoded task structures." [Section 4.4] Cross-model transfer results (Fig. 5, Tab. A3) show consistent gains of 35–44 pp for all six target models. [Takeaway 2, Section 4.4] states skills "encode reusable task structures rather than model-specific artifacts."
*   **Break condition:** If a task heavily relies on model-specific capabilities (e.g., proprietary tool use, nuanced chain-of-thought styles), a skill evolved on one model may lose critical nuances when transferred. The modest drop when using transferred vs. self-evolved skills (e.g., GPT-5.2: 69.8% self-evolved vs. 65.0% transferred) suggests some loss.

## Foundational Learning
*   **Concept:** Co‑evolutionary optimization  
    *Why needed:* The core is two coupled, asynchronous optimization processes (generator and verifier) that depend on each other’s outputs. Understanding incentives, feedback loops, and convergence is essential to grasp why the system improves.  
    *Quick check:* If the verifier were updated on every iteration while the generator updated only on oracle failures, how might that affect stability and progress?
*   **Concept:** Skill representation as multi‑file bundles  
    *Why needed:* Skills are not atomic tools but structured packages including instructions, scripts, and references. This enables modularity, reusability, and portability across tasks and models.  
    *Quick check:* What would break if skills were single-file functions instead of multi-file bundles? Consider maintainability and encapsulation of domain knowledge.
*   **Concept:** Surrogate verification without ground‑truth access  
    *Why needed:* Real-world professional tasks rarely expose test content; the oracle provides only a binary signal. The surrogate must approximate the hidden reward while remaining aligned enough to guide improvement.  
    *Quick check:* Why can’t the generator simply reuse the oracle’s pass/fail signal for refinement? What information is lost?
*   **Concept:** Information isolation between generator and verifier  
    *Why needed:* Prevents the verifier from inheriting the generator’s biases (confirmation bias) and ensures test diversity. The verifier must operate in a separate LLM session with no access to the generator’s code or reasoning.  
    *Quick check:* If the verifier could see the generator’s code, what kind of biased or uninformative tests might it produce?
*   **Concept:** Transferability of procedural knowledge  
    *Why needed:* The end goal is skills that work for many LLM agents. Understanding what makes a skill portable (e.g., abstraction level, code dependencies) is key to designing effective evolution and evaluation.  
    *Quick check:* Which skill attributes would most likely cause transfer failure: high algorithmic specificity vs. reliance on a particular tool invocation syntax?

## Architecture Onboarding
*   **Component map:**  
    Skill Generator (LLM agent) -> Executor (sandbox) -> outputs -> Surrogate Verifier (independent LLM) -> structured feedback -> Skill Generator (context update). Oracle (external deterministic verifier) -> binary signal -> Orchestrator (controls loop termination).
*   **Critical path:**  
    1. Generator produces initial skill from instruction and meta-skill.  
    2. Executor runs skill, collects outputs.  
    3. Verifier evaluates outputs with current test suite, returns surrogate reward.  
    4. If surrogate reward < 1: verifier emits diagnostic, appended to context; generator refines skill; verifier test suite locked.  
    5. If surrogate reward = 1: oracle re-executes skill in fresh environment, returns binary pass/fail. If pass, return skill; else append pass/fail bit to context and verifier escalates test suite.  
    6. Loop until max oracle rounds (5) or max surrogate retries (15) or context overflow.
*   **Design tradeoffs:**  
    *Isolation vs. feedback fidelity:* Verifier independence prevents bias but may produce tests misaligned with hidden criteria (surrogate–GT gap). Full access could yield more accurate feedback but risks confirmation bias.  
    *Evolution budget:* Fixed limits (K=5, M=15) keep runtime practical (~3000s/task) but may prematurely halt on very hard tasks.  
    *Multi‑file packaging:* Increases generation complexity but enables modular, reusable skills; failures in one file can cascade.  
    *Context management:* Accumulating feedback improves refinement but risks overflow; the β=0.7 cap forces early termination on long histories.
*   **Failure signatures:**  
    *Surrogate–GT gap:* Surrogate reward = 1 but oracle fails (e.g., precision mismatch, hidden edge cases).  
    *Verifier escalation loops:* Surrogate repeatedly fails after skill refinement, indicating generator not addressing core issues or verifier too aggressive.  
    *Transfer degradation:* Skills evolved on source model underperform on target models relative to self-evolved skills (e.g., GPT-5.2 transferred vs. self-evolved: –4.8 pp).  
    *Progress checklist stalls:* Case study shows Round 2 failed due to incomplete checklist, not skill quality, showing orchestrator’s procedural guardrails can delay oracle evaluation.
*   **First 3 experiments:**  
    1. Baseline comparison: Evaluate no‑skill, human‑curated, self‑generated, and EvoSkills on SkillsBench to establish absolute gains.  
    2. Ablation study: Remove surrogate verifier and/or evolution to quantify each component’s contribution.  
    3. Cross‑model transfer: Evolve skills on Opus 4.6, then deploy on six other LLMs to measure portability.

## Open Questions the Paper Calls Out
*   **Open Question 1:** How can EvoSkills be extended to evolve skills jointly across multiple LLM models in a single co‑evolutionary process, rather than transferring skills post‑hoc? The current framework evolves skills using a single backbone model and then evaluates transfer. Multi‑model evolution—where multiple models participate in the generation and verification loops—is not implemented, leaving open questions about coordination, conflict resolution, and whether such an approach yields more portable or higher‑quality skills.
*   **Open Question 2:** What specific design modifications to the Surrogate Verifier can reduce its frequency of false positives/negatives relative to the ground‑truth oracle, thereby decreasing the number of required oracle interventions? The case study illustrates surrogate–GT mismatches (e.g., passing due to insufficient precision, failing due to its own estimation error). The paper does not propose or evaluate techniques to improve surrogate fidelity.
*   **Open Question 3:** Why do self‑evolved skills provide diminishing returns in some professional domains (e.g., Energy, Robotics) compared to others (e.g., Finance, Cybersecurity), and what domain characteristics predict the magnitude of improvement over human‑curated skills? Fig. 6 shows small gains in Energy (+4pp) and Robotics (+6pp) versus large gains in Finance (+57pp) and Cybersecurity (+23pp). The paper attributes this to "human–machine cognitive misalignment" but does not analyze which domain features drive the variation.
*   **Open Question 4:** What specific properties of self‑evolved skill packages enable their strong cross‑model portability, and can these properties be explicitly encoded or optimized during evolution to further improve transferability? The paper observes strong transfer but does not dissect what constitutes the reusable structure—e.g., modular decomposition, algorithmic choices, abstraction level of instructions, or avoidance of model‑specific idioms.
*   **Open Question 5:** Can the number of evolution iterations required for convergence be predicted a priori from task characteristics, enabling adaptive budgets that reduce unnecessary computation on easy tasks while allocating more resources to hard ones? Fixed budgets (K=5, M=15) are used for all tasks, but Fig. C1 shows wide variation in required cycles. An adaptive controller could improve efficiency.

## Limitations
*   **Surrogate‑Oracle Alignment Gap:** The verifier’s test suite may diverge from hidden oracle criteria (e.g., precision, edge cases), leading to skills that pass surrogate tests but fail real evaluation. This gap’s prevalence is not quantified across the benchmark.
*   **Mechanism of Human Misalignment:** While self‑evolved skills beat human‑curated ones, the precise cognitive mismatch (e.g., abstraction level, tool sequencing, reasoning depth) is not systematically decomposed; evidence is primarily aggregate pass‑rate differences.
*   **Transferability Nuance:** Consistent cross‑model gains suggest portable structures, but performance drops when transferring vs. self‑evolving (e.g., –4.8 pp for GPT‑5.2) indicate some model‑specific encoding remains; the relative contribution of bundle format vs. procedural logic is unquantified.

## Confidence
*   **Co‑evolutionary loop efficacy:** High (strong ablation evidence, clear algorithm)
*   **Superiority over human‑curated skills:** Medium‑High (consistent cross‑domain wins, but cause is inferred)
*   **Cross‑model transferability:** Medium‑High (robust +35‑44 pp gains across 6 models, but transfer performance is uniformly lower than self‑evolved)
*   **Surrogate as effective guidance signal:** Medium (relies on verifier’s diagnostic quality; limited formal analysis of feedback informativeness)

## Next Checks
1.  **Quantify surrogate‑oracle divergence:** Manually analyze failure cases where the surrogate passed but the oracle failed. Categorize mismatch types (output format, numerical precision, missing edge case) to measure prevalence and nature of the "surrogate–GT gap."
2.  **Controlled skill ablation for misalignment:** For tasks where human skills underperform, have experts revise human‑curated skills *using the agent’s typical error patterns* (from failure logs). Test if these "misalignment‑aware" revisions close the performance gap with self‑evolved skills.
3.  **Portability stress test via component swapping:** Transfer evolved skills to a target model but swap out one component at a time (e.g., replace `scripts/` functions with model‑specific implementations, alter documentation style). Measure pass‑rate drop to isolate which bundle component is more critical for portability.
