# RefineRL: Advancing Competitive Programming with Self-Refinement Reinforcement Learning

## Quick Facts
- arXiv ID: 2604.00790
- Source: https://arxiv.org/abs/2604.00790
- Reference count: 40
- Primary result: After RL, the Skeptical-Agent with 16 queries enables 4B models to achieve 75.97% on LiveCodeBench v5 and 67.82% on v6, surpassing 32B baselines and approaching 235B model performance.

## Executive Summary
RefineRL addresses the limitation of single-attempt LLM solving in competitive programming, where reliance on sparse public test cases yields false positives. It introduces the Skeptical-Agent, an iterative refiner that uses local code execution to validate against public tests but maintains skepticism even after passing them, generating either failure-driven or skepticism-driven feedback. This capability is internalized via Self-Refinement RL, which trains the model on its own refinement trajectories using only problem-answer pairs, guided by a squared-incentive reward function that provides dense supervision. Experiments on Qwen3-4B and Qwen3-4B-2507 show that after RL training, the Skeptical-Agent (with 16 queries) enables these 4B models to achieve 75.97% and 67.82% on LiveCodeBench v5 and v6, respectively, surpassing 32B baselines and approaching 235B model performance. Ablation studies confirm the necessity of self-generated refinement trajectories and the squared reward; training also increases response length, indicating deeper reasoning.

## Method Summary
The method solves competitive programming problems given a problem statement `x` and public test cases `T_pub`. The **Skeptical-Agent** iteratively refines code for up to `N=16` turns. In each turn, it executes the generated code locally on `T_pub` using an **Execution Tool** and judges outputs with a **Judgment Function**. If any test fails, it generates **error-driven feedback** (PFail) detailing the failure; if all tests pass, it generates **skepticism-driven feedback** (PSkep) prompting self-critique for edge cases, shortcuts, and complexity issues. The agent includes a restart rule (`M1=4` consecutive passes) and a termination rule (`M2=8` consecutive passes). For **Self-Refinement RL**, the base model produces initial trajectories from `D_CP` (problem-answer pairs). From these, `D_Err` (solutions with at least one failing test) and `D_Skep` (solutions passing all public tests) are synthesized, yielding `D_RL = D_CP ∪ D_Err ∪ D_Skep`. The model is trained with GRPO (no KL regularization) on `D_RL`. The reward is a squared incentive: `R = (k*/|T|)^2`, where `k*` is the number of passed tests or the index of the first failing test minus one. Implementation uses the VeRL framework with Ray for distributed evaluation; code execution is sandboxed with 8-second timeout and 512MB memory limits. Experiments use Qwen3-4B and Qwen3-4B-2507 with rollout lengths up to 32,768 tokens and 65,536 tokens respectively, learning rate 1e-6, temperature 1.0, rollout number 8, and batch/mini-batch size 32. The entire pipeline requires only problem-answer pairs and no human‑annotated refinement traces.

## Key Results
- **SOTA for 4B models:** Skeptical@16 yields 75.97% on LiveCodeBench v5 and 67.82% on v6, surpassing 32B baselines and approaching 235B model numbers (79.08%, 72.50%).
- **Ablation validation:** Removing self‑generated trajectories (`D_Err`, `D_Skep`) or switching to binary reward degrades performance, confirming the necessity of both components.
- **Deeper reasoning:** RL training increases response length, suggesting the model engages in more extensive self‑refinement.

## Why This Works (Mechanism)

### Mechanism 1: Skeptical-Agent mitigates false positives
- **Claim:** The Skeptical-Agent mitigates false positives from sparse public test cases by enforcing self-refinement even after all public tests pass.
- **Mechanism:** The agent uses local execution to validate solutions against public tests. If any public test fails, it generates detailed error-driven feedback (Eq. 5). If all public tests pass, it generates skepticism-driven feedback (Eq. 6) that prompts the model to self-critique for edge cases, hard-coded shortcuts, and complexity issues, rather than accepting the solution.
- **Core assumption:** LLMs can generate meaningful self-critique and identify latent defects not exposed by public tests when explicitly prompted with a skepticism checklist.
- **Evidence anchors:**
  - [abstract] “maintains a skeptical attitude towards its own outputs and thereby enforces rigorous self-refinement even when validation suggests correctness.”
  - [section 4.2] Describes the feedback functions PFail and PSkep and the restart/termination rules that implement skepticism.
  - [corpus] Neighbors like “Evolving LLMs’ Self-Refinement Capability” and “LLM-ARC” explore self-critique but do not directly validate the skepticism mechanism; evidence is weak.
- **Break condition:** If the model consistently fails to produce useful self-critique even with skeptical prompts (e.g., cannot identify edge cases), the mechanism fails and may waste compute on unnecessary refinements.

### Mechanism 2: Self-Refinement RL internalizes skeptical self-refinement
- **Claim:** Self-Refinement RL internalizes the skeptical self-refinement capability by training on the model’s own refinement trajectories.
- **Mechanism:** From a base dataset D_CP, the model generates solution trajectories. For each problem, two feedback types are synthesized: error-driven (if solution fails any test in T) and skepticism-driven (regardless of pass/fail). These (problem, feedback, test set) tuples are combined with D_CP to form D_RL. The model is then trained via GRPO on this dataset, exposing it to the full iterative refinement process.
- **Core assumption:** The model’s own refinement attempts provide a relevant and scalable training signal for improving self-refinement, without requiring human-annotated correction traces.
- **Evidence anchors:**
  - [abstract] “internalized via Self-Refinement RL, which trains the model on its own refinement trajectories using only problem-answer pairs.”
  - [section 4.3] Details the synthesis of D_Err and D_Skep from the model’s initial generations and the union D_RL = D_CP ∪ D_Err ∪ D_Skep.
  - [corpus] “BanglaForge: LLM Collaboration with Self-Refinement” uses self-refinement but for code generation in a low-resource language; not directly comparable. Evidence is suggestive but not direct.
- **Break condition:** If the model’s initial generations are of uniformly low quality, the synthesized trajectories may be noisy or uninformative, leading to poor or unstable RL training.

### Mechanism 3: Squared-incentive reward provides dense supervision
- **Claim:** The squared-incentive reward function provides dense supervision that incentivizes full problem resolution and enables learning from difficult problems where the model initially fails.
- **Mechanism:** For a generated solution r_code on test set T, reward R = (k*/|T|)^2, where k* = |T| if all tests pass, else the index of the first failing test minus one. This gives non-zero reward for partial progress and squares the reward for later tests, amplifying the incentive to pass all.
- **Core assumption:** A dense, shaped reward that correlates with the number of passed tests is more effective for RL than binary pass/fail, especially on hard problems where correct solutions are rare.
- **Evidence anchors:**
  - [abstract] “squared-incentive reward function (R = (k*/|T|)^2) provides dense supervision and encourages full problem resolution.”
  - [section 4.3] Explains the motivation and form of the squared reward, contrasting it with binary pass-or-fail.
  - [corpus] “UpSkill: Mutual Information Skill Learning” addresses test-time scaling but uses different reward shaping; “ThinkTwice” optimizes for reasoning and refinement but not specifically this reward. No direct corpus anchor.
- **Break condition:** If the reward shaping misaligns with the true objective (e.g., encourages optimizing for partial matches that do not generalize to full solutions), it could lead to reward hacking without improving final pass@1 accuracy.

## Foundational Learning

#### Reinforcement Learning with Verifiable Rewards (RLVR)
- **Why needed here:** The entire Self-Refinement RL training uses GRPO, a policy gradient algorithm, with rewards derived from code execution on test cases. Understanding how verifiable rewards replace human feedback is key.
- **Quick check question:** How does GRPO use group-based advantages to stabilize training compared to standard PPO, and why might excluding KL regularization be beneficial here?

#### Chain-of-Thought (CoT) and Test-Time Scaling
- **Why needed here:** The Skeptical-Agent relies on long CoT generation for analysis and refinement. The paper shows increased response length after RL, indicating deeper reasoning.
- **Quick check question:** Why might longer CoT correlate with better problem-solving in competitive programming, and what are the risks (e.g., hallucination, inefficiency)?

#### Competitive Programming Evaluation (Public vs Private Tests)
- **Why needed here:** The core problem is false positives from public tests. Understanding the contest setting—public tests visible to contestants, private tests hidden—is essential to grasp the skepticism motivation.
- **Quick check question:** Why are public test cases insufficient as sole validation, and how does the Skeptical-Agent’s checklist attempt to cover private test distribution gaps?

## Architecture Onboarding

**Component map:**
- LLM (π_θ): Generates solution analysis, text solution, and code and refines based on feedback. Base models: Qwen3-4B, Qwen3-4B-2507.
- Execution Tool (f): Runs generated code on given input, returns output. Used locally during agent loop.
- Judgment Function (g): Compares execution output to expected output, returns status (AC, WA, TLE, etc.).
- Feedback Generators: PFail constructs error-driven feedback from a failing test; PSkep constructs skepticism-driven feedback when all public tests pass.
- RL Trainer (GRPO): Updates π_θ using trajectories from D_RL with squared-incentive reward. Implemented via VeRL framework with distributed code execution.
- Skeptical-Agent Loop: Orchestrates up to N iterations, applies restart (M1) and termination (M2) rules, selects final solution.

**Critical path:** Problem statement (x) + public tests (T_pub) → Initial solution (r_code) → Local test evaluation (f, g on T_pub) → Feedback (r_fed) → Refinement (next r_code) → Repeat until termination → Final solution (r*_code) → Evaluate on private tests (T_pri) for true performance.

**Design tradeoffs:**
- Skepticism vs Efficiency: Maintaining skepticism increases compute (more iterations, longer CoT) but may reduce false positives. The termination rule (M2 consecutive passes) balances this.
- Reward shaping: Squared reward provides dense signal but may overemphasize later tests; binary reward is sparse but aligned with final goal. Tradeoff between learning stability and objective matching.
- Trajectory source: Using self-generated trajectories is scalable but depends on base model quality. Human-curated refinements might be higher quality but expensive.

**Failure signatures:**
- Agent loops indefinitely without passing public tests (restart rule may help).
- Agent passes public tests but fails private tests despite skepticism (PSkep ineffective).
- RL training degenerates: reward does not increase, response length does not grow, or performance on private tests drops.
- High variance in pass@1 across random seeds, indicating unstable policy updates.

## Open Questions the Paper Calls Out
1. **False positive reduction quantification**  
   The paper identifies false positives from sparse public tests as a major risk, but does not directly measure how much the Skeptical-Agent reduces this rate relative to baselines like Reflexion. An ablation on a dataset with both public and private tests comparing the proportion of solutions passing public but failing private tests would be needed.

2. **Hyperparameter sensitivity**  
   The agent's hyperparameters (max iterations N=16, restart M1=4, termination M2=8) are fixed without sensitivity analysis. Optimal values likely depend on model capacity and problem difficulty; systematically varying them across model scales and problem difficulties would clarify trade-offs.

3. **Reward exponent choice**  
   The squared-incentive reward uses exponent α=2 without theoretical justification or comparison to alternatives. The effect of different α values on learning speed and stability is unknown. Comparative experiments with α ∈ {1, 1.5, 2, 2.5, 3} are needed.

4. **Training data scaling**  
   Performance is demonstrated on only 4.5K HardTest problems; it is unclear whether additional data would yield further improvements or if the current scale already saturates learning. Training on increasingly larger CP datasets (e.g., 10K, 20K, 50K) and evaluating on LiveCodeBench would reveal scaling trends.

## Limitations
- The approach depends heavily on the model's ability to generate useful self-critique; weaker models may produce low-quality skepticism feedback, leading to wasted computation or degradation.
- Evaluation is limited to LiveCodeBench; it remains uncertain whether gains generalize to other competitive programming benchmarks like Codeforces or APPS.
- Test-time cost is high due to up to 16 iterations and long chain-of-thought responses, which may be impractical for real-world deployment.
