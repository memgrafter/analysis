# Hierarchical Reward Design from Language: Enhancing Alignment of Agent Behavior with Human Specifications

## Quick Facts
- **arXiv ID**: 2602.18582  
- **Source URL**: https://arxiv.org/abs/2602.18582  
- **Reference count**: 40  
- **Primary result**: L2HR generates hierarchical rewards from language, significantly improving alignment of HRL agent behavior with human specifications across three domains.

## Executive Summary
The paper introduces Hierarchical Reward Design from Language (HRDL), a problem formulation that extends classical reward design to hierarchical reinforcement learning (HRL) agents. Unlike flat reward functions, HRDL separates rewards into high-level (for subtask selection) and low-level (for execution) components, enabling nuanced behavioral specifications. The proposed solution, Language to Hierarchical Rewards (L2HR), leverages large language models (LLMs) to generate these hierarchical rewards directly from natural language. Empirical evaluations in Rescue World, iTHOR, and Kitchen environments show that hierarchical rewards dramatically outperform flat reward baselines in alignment metrics. For instance, in Rescue World, hierarchical rewards achieved 76.92% expert-level high-level alignment compared to 12.5% for flat rewards, and in iTHOR, 87.5% versus 0%. Human evaluations corroborate these gains, with users rating hierarchical agents higher on specification adherence. Hierarchical rewards also exhibit lower syntax error rates during LLM generation and better preserve task feasibility.

## Method Summary
HRDL addresses the limitation of flat reward functions in capturing preferences about subtask sequencing and execution for long-horizon tasks. It formalizes the reward design problem for HRL by requiring two distinct reward functions: a high-level reward that guides the selection of subtasks (options), and low-level rewards that govern the execution of actions within each subtask. The authors propose L2HR, an approach that uses a single LLM to generate both reward components from a natural language specification. The LLM is prompted to produce code for the high-level and low-level rewards in a structured format. These rewards are then used to train a hierarchical agent consisting of a high-level policy that chooses subtasks and low-level policies that execute primitive actions. This decomposition allows the LLM to express complex constraints and ordering preferences that are otherwise inexpressible with a monolithic reward.

## Key Results
- In Rescue World, hierarchical rewards achieved 76.92% expert-level high-level alignment versus 12.5% for flat rewards.  
- In iTHOR, hierarchical rewards achieved 87.5% alignment versus 0% for flat rewards.

## Why This Works (Mechanism)
The hierarchical separation enables LLMs to capture two complementary aspects of a task: the high-level planning and ordering constraints, and the low-level execution details. Flat rewards conflate these aspects, overwhelming the LLM and leading to incomplete or incorrect specifications. By splitting the reward design problem, the LLM can focus each output on a specific level of abstraction, reducing cognitive load and improving the correctness and specificity of generated code. Additionally, the high-level reward directly influences subtask selection, allowing it to encode sequencing preferences that are naturally expressed in language (e.g., "first clean the table, then wash the dishes"). The low-level rewards then handle the precise control within each subtask. This division mirrors the structure of complex human tasks and aligns with the hierarchical nature of many HRL algorithms, resulting in better behavioral alignment.

## Architecture Onboarding
**Component map** (plain text):  
Natural Language Specification -> L2HR (Prompted LLM) -> High-Level Reward Function + Low-Level Reward Functions -> HRL Agent (High-Level Policy π_h selects subtasks, Low-Level Policies π_l execute actions) -> Agent Interaction with Environment  

**Critical path**:  
1. Receive natural language spec from user.  
2. L2HR sends a structured prompt to the LLM, which generates high-level and low-level reward code.  
3. Generate and validate reward functions (syntax check, feasibility).  
4. Train or evaluate the hierarchical agent using the two reward types: high-level reward guides subtask selection; low-level rewards guide action execution within subtasks.  
5. Agent performs in the target environment; alignment metrics are collected.  

**Design tradeoffs**:  
- LLM variability vs. reproducibility: LLMs can produce inconsistent outputs; prompts must be carefully engineered.  
- Separation of rewards adds modularity but risks misalignment between high- and low-level rewards.  
- Simplicity of using a single LLM versus potential need for model chaining or post‑processing.  

**Failure signatures**:  
- Syntax errors in generated reward code (immediate compilation failure).  
- High‑level reward that does not induce the intended subtask ordering (low alignment scores).  
- Low‑level rewards that are infeasible within the given subtask (agents stall or receive constant penalty).  
- Large variance in LLM outputs leading to unpredictable agent performance.  

**First experiments**:  
1. Run L2HR on a simple gridworld (e.g., MiniGrid) to verify that both reward types generate syntactically correct code and produce expected subgoal behaviors.  
2. Compare hierarchical vs. flat rewards on Rescue World: report high‑level and low‑level alignment metrics, statistical significance across multiple seeds.  
3. Perform an ablation on prompt design: vary prompt wording and structure to measure impact on reward syntax error rates and final alignment.

## Limitations
- Experimental details (hyperparameters, LLM prompts, random seeds) are not fully reported, hindering reproducibility.  
- No statistical significance testing on observed improvements; results may be due to variance.  
- Human evaluation is limited in scale and diversity, raising risks of selection bias.  
- L2HR’s reliance on fixed LLMs may not generalize across model families or languages; robustness analysis is absent.  
- Evaluation restricted to three domains, leaving external validity uncertain.
