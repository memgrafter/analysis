# Mechanic: Sorrifier-Driven Formal Decomposition Workflow for Automated Theorem Proving

## Quick Facts
- arXiv ID: 2603.24465
- Source URL: https://arxiv.org/abs/2603.24465
- Reference count: 40
- Primary result: Solves 11/12 Putnam 2025 and all 4 IMO 2025 problems with significantly lower time (114 min avg.), cost ($18.5), proof length (656 lines), and lemmas (14) compared to state‑of‑the‑art baselines.

## Executive Summary
Automated theorem proving for complex mathematics often discards entire proofs upon failure or suffers from context bloat when iteratively fixing errors. Mechanic introduces a sorrifier‑driven workflow that uses Lean’s `sorry` placeholder to surgically isolate erroneous subgoals while preserving correct surrounding structure. The system employs a recursive pipeline: generate an informal proof sketch, translate it into a formal Lean proof, decompose failures via iterative sorrification into self‑contained subproblems, and independently solve each subgoal before reassembly.

On Putnam 2025 (12 problems) Mechanic solves 11 problems with superior efficiency: average time 114 minutes (vs. 165–228 min for baselines), monetary cost $18.5 (vs. $37.9–$72.7), proof length 656 lines (vs. 667–1 161), and generated lemmas 14 (vs. 17–49). On IMO 2025 (4 problems) it solves all, producing wider, shallower proof trees that enable better parallelization and notably lower time on harder problems. Ablation studies confirm that the informal proof stage reduces errors and tree complexity, and the pipeline scales across multiple high‑end LLM backbones.

## Method Summary
Mechanic implements an automated theorem proving agent that decomposes failing proofs using Lean’s `sorry` placeholder. The agent interacts with a Lean compiler, theorem retrieval tools (LeanDex/Loogle), and three specialized LLM roles: Reasoner (informal sketch and subgoal synthesis), Verifier (evaluation and validation), and Prover (formal Lean code generation). The fixed pipeline consists of four stages:

1. **Informal Prove** – Reasoner produces a natural‑language solution sketch; Verifier evaluates correctness over up to 16 iterations with three verification passes per iteration.
2. **Formal Prove** – Prover transliterates the accepted informal sketch into Lean; Lean compiles; on errors, retrieved theorems inform up to four correction rounds with Verifier‑provided strategy comments.
3. **Subgoal Split** – If formal proof still fails, the Sorrifier algorithm iteratively replaces the innermost error with `sorry` until the code compiles. Each `sorry` is converted into a self‑contained subgoal: the Reasoner extracts the relevant local tactic state and formulates a lemma premise; the Verifier checks syntactic and semantic soundness.
4. **Subgoal Process** – Every extracted subgoal is recursively handled by the same pipeline (stages 1‑3), terminating when a subgoal repeats identically beyond a threshold or a recursion depth limit is reached.

The orchestrated interaction aims to preserve correct context, avoid bloat, and yield wide‑and‑shallow proof trees that support parallelization.

## Key Results
- **Putnam 2025**: Solves 11/12 problems; average time 114 min (vs. 165–228 min), cost $18.5 (vs. $37.9–$72.7), proof length 656 lines (vs. 667–1 161), lemmas 14 (vs. 17–49).
- **IMO 2025**: Solves all 4 problems; generates broader, shallower proof trees enabling parallelization; notably lower time on harder instances.
- **Ablation & scalability**: Removing the informal proof stage increases errors and tree size; the pipeline operates successfully with both Gemini‑3.1‑Pro‑Preview and Claude‑4.5‑Opus.

## Why This Works (Mechanism)

### Mechanism 1: Surgical Error Isolation via Iterative Sorrification
**Claim**: By iteratively replacing the innermost failing proof block with `sorry`, Mechanic preserves the surrounding correct proof structure and context, preventing cascading error inflation.  
**Mechanism**: The Sorrifier algorithm targets the innermost reported error. If the error lies inside a `have` block, it replaces only that block’s body with `sorry`; if the error is outside any block, it truncates the code at the error line and appends `sorry`. After each modification, Lean recompiles immediately, clearing downstream errors caused by the broken context. This yields a compilable but incomplete proof containing minimal `sorry` placeholders.  
**Core assumption**: Cascading errors in dependent type systems are primarily localized; repairing the root cause (innermost error) invalidates subsequent false errors, allowing precise isolation.  
**Evidence anchors**: [section 3.1] “the Sorrifier is designed to operate through a highly targeted, iterative pipeline… surgically targets the innermost reported error.” [section 3.2.3] “after a single modification is made, the Lean environment is immediately recompiled, instantly removing any downstream cascading errors.” Weak direct corpus support; related works like DeepSeek‑Prover and Seed‑Prover use iterative error fixing without structural decomposition, making Mechanic’s targeted approach distinctive.  
**Break condition**: When the error context is so corrupted that the innermost error is not the logical root, or when repeated sorrification yields identical failing contexts (termination heuristic triggers).

### Mechanism 2: Modular Subgoal Extraction and Reassembly
**Claim**: Extracting self‑contained subgoals from `sorry` states and solving them independently avoids context bloat and enables parallelizable, wide‑and‑shallow proof trees.  
**Mechanism**: For each `sorry`, the current tactic state is extracted. The Reasoner filters relevant hypotheses from the local context to formulate a self‑contained subgoal. The Verifier then evaluates the extracted subgoal for syntactic validity (well‑formed Lean) and logical soundness (e.g., missing hypotheses, false premises). Proven subgoals are reintegrated into the original proof using `apply` tactics at the `sorry` positions.  
**Core assumption**: The tactic state at a `sorry` location contains sufficient and necessary context to define a valid subgoal; irrelevant hypotheses can be discarded manually without losing essential dependencies.  
**Evidence anchors**: [section 3.2.3] “the Reasoner is then tasked with identifying which hypotheses… are relevant… Irrelevant hypotheses are discarded.” [section 3.2.3] “Subgoals that are incorrectly extracted deviate from the original proof context and are likely to fail to reassemble.” [section 4.1] “our proof trees are broader but shallower… proofs at the same level can be parallelized.”  
**Break condition**: Extracted subgoal is logically flawed (e.g., inequality reversal as in Appendix B.1) or missing critical hypotheses, making it unprovable or divergent from the original proof intent.

### Mechanism 3: Informal‑Guided Formal Decomposition with Recursion
**Claim**: Generating an informal proof sketch first provides a high‑level roadmap that reduces formal error complexity and tree size, while recursive subgoal processing ensures full decomposition.  
**Mechanism**: An informal solution is produced via generate‑and‑verify loops (Reasoner ↔ Verifier). This sketch guides the Prover’s formalization. If the formal proof fails after error‑correction rounds, sorrification decomposes it. Each subgoal recursively runs the same full pipeline (informal → formal → split if needed) until termination.  
**Core assumption**: Informal reasoning captures strategic essence better than pure formal search; decomposing at the formal level after an informal blueprint is more efficient than informal decomposition from scratch.  
**Evidence anchors**: [abstract] “faulty proofs are decomposed into clean, self‑contained subproblems solved independently via a recursive pipeline (informal proof → formal proof → sorrify → extract subgoals → reassemble).” [section 3.2.1] “natural language is often better suited to exploratory reasoning… generates an informal reasoning sketch, which then guides the construction of the formal proof.” [section 4.2] “a well‑structured informal proof significantly reduces errors in formal proofs… decreasing the size of the proof tree.”  
**Break condition**: Recursion depth limit reached; subgoal identical to parent (no progress); or informal proof is absent/incorrect for a subproblem, leading to repeated failure cycles.

## Foundational Learning

### Concept: Dependent Type Theory & Proof Irrelevance
**Why needed here**: Understanding Lean’s core logic (Calculus of Inductive Constructions) is essential to grasp why a single error corrupts context (cascading failures) and how `sorry` creates a provably incomplete but type‑correct state. Proof irrelevance notions explain why `sorry` is accepted locally without global consistency checks.  
**Quick check**: If a `have h : P := sorry` is used, why does Lean still accept the surrounding proof even if `P` is later used in a proof of `False`?

### Concept: Tactic‑Based Proof State Management
**Why needed here**: Mechanic’s extraction and assembly rely on manipulating Lean’s tactic state (goals, hypotheses). The engineer must understand how `have`, `apply`, and `exact` alter the context to predict the state at a `sorry` location and formulate valid subgoals.  
**Quick check**: Given a goal `⊢ a = b` with hypothesis `h : a = c` and `h' : c = b`, what is the tactic state after `have step1 : a = c := exact h`? What would be the subgoal if that `have` were replaced by `sorry`?

### Concept: Informal‑to‑Formal Translation & Proof Sketching
**Why needed here**: The pipeline’s efficiency hinges on the informal proof’s quality. The engineer must recognize how a high‑level informal sketch (e.g., “use induction on n”) translates into a structured formal sequence of `have` blocks and where formalization typically fails (e.g., missing type casts, library lemma mismatches).  
**Quick check**: How would you informally prove “For all natural numbers n, n + 0 = n” before formalizing it in Lean? What are the likely failure points when translating this into `by simp` vs. `by induction n`?

## Architecture Onboarding

### Component map
Orchestrator → Reasoner ↔ Verifier → Prover → Lean → (if failure) → Sorrifier → Subgoal Extractor → (back to Orchestrator for recursive processing)

### Critical path
1. **Informal Prove** – Reasoner generates an informal sketch; Verifier evaluates (3 passes); iterate up to 16 rounds.
2. **Formal Prove** – Prover translates the sketch to Lean; Lean compiles; if errors, retrieve theorems via LeanDex/Loogle; Verifier comments strategy; Prover revises (≤ 4 rounds).
3. **Subgoal Split** – Apply Algorithm 1 (Sorrifier) to iteratively replace innermost error with `sorry` until compilation. For each `sorry`, extract tactic state; Reasoner formulates self‑contained subgoal; Verifier validates (syntactic & semantic); reassemble by `apply`.
4. **Subgoal Process** – Recursively apply steps 1‑3 to each extracted subgoal; terminate when a subgoal repeats identically beyond a threshold or recursion depth limit is reached.

### Design tradeoffs
- **Fixed pipeline vs. adaptive**: Simplicity vs. efficiency on simple problems (overhead) or hard problems (insufficient iterations).
- **Sorification depth**: Aggressive sorrification yields many parallelizable subgoals but introduces coordination overhead; conservative may leave residual errors.
- **Verifier burden**: Three verification passes per informal iteration increase latency but reduce error propagation downstream.

### Failure signatures
- **Cascading error overwhelming**: Sorrifier loops endlessly because each sorrification reveals new innermost errors rooted in a fundamental misconception (e.g., wrong theorem choice).
- **Subgoal extraction flaw**: Extracted subgoal is false or missing critical hypotheses, causing reassembly failure or infinite recursion.
- **Informal proof misguidance**: Informal sketch is strategically wrong, leading the Prover down an unproductive formal path.
- **Incomplete/inaccurate Sorrifier replacements**: Replacement logic misidentifies the innermost error or truncates too much code, altering proof intent.
- **Context bloat persists**: Despite decomposition, the context passed to LLMs grows large, degrading performance.
- **Model capability mismatch**: Certain LLMs lack sufficient Lean reasoning proficiency, causing early‑stage failures.

### First 3 experiments
1. **Sorrification correctness test**: Feed a deliberately failing Lean proof with a single local error (e.g., type mismatch in one `have`). Verify Sorrifier replaces only that block and compiles successfully; check that subsequent `sorry` extraction yields the correct local goal.
2. **Proof tree topology validation**: Compare proof tree depth/breadth of Mechanic vs. baseline on IMO 2025 P4 (Figure 4). Confirm Mechanic’s tree is shallower; instrument to count parallelizable nodes at each depth.
3. **Ablation of informal stage**: Run Putnam A2–A4 with and without informal prove stage (Table 3a). Measure: (a) success rate, (b) final proof length, (c) number of subgoals generated. Expect higher failure/longer proofs without informal guidance.

## Open Questions the Paper Calls Out

### Open Question 1: Adaptive pipeline selection
**Question**: How can we construct an adaptive formal theorem proving agent that dynamically selects and sequences pipeline stages (e.g., informal reasoning, direct formal proof, subgoal decomposition) based on real‑time problem characteristics and intermediate feedback, rather than following a fixed workflow?  
**Basis in paper**: The authors explicitly state: “Mechanic employs a fixed pipeline that follows an iterative cycle of informal proof, formal proof, and subgoal split. However, an ideal agent may require the flexibility to adapt its steps based on context. For example, agent can omit the informal proof stage for simpler problems or perform additional error‑fix iterations for formal proof on harder ones.”  
**Why unresolved**: The current system’s rigidity may lead to inefficiencies on easy (unnecessary overhead) or extremely hard (insufficient iterations) problems; adaptivity could improve overall success rate and resource usage, but no mechanism is proposed.  
**What evidence would resolve it**: Develop a meta‑controller that predicts the need for each stage using features like problem length, initial proof attempt error count, or model confidence. Evaluate on a benchmark like Putnam/IMO with adaptive vs. fixed policies, measuring success rate, time, and cost.

### Open Question 2: Modular sorrifier
**Question**: How can the sorrifier—the core component that surgically replaces erroneous proof segments with `sorry`—be modularized as a standalone, reusable tool within a general‑purpose code agent, enabling on‑demand invocation without the full Mechanic pipeline?  
**Basis in paper**: The authors state: “In future work, we will modularize the sorrifier as a standalone component integrated into the code agent. This design preserves the efficacy of the sorrifier‑driven formal decomposition workflow while enabling the model to autonomously invoke the component as needed.”  
**Why unresolved**: The sorrifier is currently tightly coupled with the proof pipeline; its algorithm (iterative innermost error replacement) may need adaptation to work in diverse agent contexts (e.g., when multiple errors exist, when the agent wants to manually control decomposition). Integration challenges include error reporting, context management, and interaction with other tools.  
**What evidence would resolve it**: Define a standard interface (e.g., function that takes Lean code and returns sorried code with extraction of subgoals), implement as a library, integrate into an existing code agent framework (e.g., Numina or general SWE‑agent), and evaluate on formal proof tasks comparing selective vs. full pipeline.

### Open Question 3: Subgoal extraction errors
**Question**: What are the failure modes of LLM‑based subgoal extraction from `sorry` placeholders, and how can we improve the reliability of generating self‑contained, logically sound subgoals that correctly capture the local context?  
**Basis in paper**: The paper includes an example (Appendix B.1) where the verifier detects a logical error in an extracted subgoal: the subgoal was mathematically false due to missing hypotheses or flawed reasoning. The authors note the need for verification but do not analyze the prevalence or systematic causes.  
**Why unresolved**: Subgoal extraction is critical for decomposition but relies on LLM judgment; errors can lead to infinite loops or unprovable subgoals. The current two‑stage verification (syntactic and semantic) catches some errors, but the underlying extraction quality is not studied, nor are there alternatives like automated decomposition based on proof dependencies.  
**What evidence would resolve it**: Conduct a large‑scale error analysis on extracted subgoals across many problems, categorizing error types (e.g., hypothesis omission, incorrect generalization, logical inconsistency). Then design improved prompting, fine‑tuning, or tool‑assisted extraction (e.g., using Lean’s context API) and measure reduction in extraction errors and impact on overall proof success.

## Limitations
- **Data non‑disclosure**: The exact Lean statements for Putnam 2025 and IMO 2025 are not provided, preventing independent verification of the primary results.
- **Missing critical prompts**: Prompt templates for the subgoal extraction step (Reasoner’s conversion of `sorry` states into lemmas) are omitted, hindering faithful replication of the most error‑prone component.
- **Undisclosed heuristics**: Thresholds for identical subgoal retries, recursion depth limits, and the exact budget allocation per problem are not specified, complicating precise parameter tuning.
