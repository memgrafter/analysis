# LiveVectorLake: A Real-Time Versioned Knowledge Base Architecture for Streaming Vector Updates and Temporal Retrieval

## Quick Facts
- arXiv ID: 2601.05270
- Source URL: https://arxiv.org/abs/2601.05270
- Reference count: 28
- Primary result: Reduces content re-processing to 10–15% (vs. 100% full re-indexing), achieves sub-100 ms latency for current queries and sub-2 s for temporal queries, stores only active chunks in hot tier (10–20% of total), and maintains 100% change detection accuracy with ACID consistency.

## Executive Summary
LiveVectorLake tackles the core tension in retrieval-augmented generation (RAG) systems between low-latency vector search and continuous versioning of knowledge. It introduces a dual-tier architecture that separates a hot vector index (Milvus) for active chunks from a cold lakehouse (Delta Lake) for full version history. Change detection is performed via SHA-256 hashing of semantic chunks, enabling selective re-embedding of only modified content. Temporal queries are routed to the cold tier with validity filtering applied before similarity search, eliminating temporal leakage. Evaluated on a 100-document corpus across five versions, the system reduces re-processing overhead by 85–90%, maintains sub-100 ms latency for current queries and sub-2 s for historical queries, limits the hot tier to 10–20% of total chunks, and achieves perfect change detection accuracy with ACID guarantees across tiers.

## Method Summary
LiveVectorLake’s pipeline comprises three stages. First, incoming documents are split into semantic (paragraph-level) chunks, each normalized and hashed with SHA-256. An in-memory hash store compares these hashes to previously seen values, classifying chunks as new, modified, or deleted. Only changed chunks are embedded; unchanged ones are skipped. Second, writes follow a write-ahead log order: historical records are appended to a Delta Lake table (the cold tier) with validity intervals (valid_from, valid_to), and active (currently valid) chunks are upserted into a Milvus collection (the hot tier) with an HNSW index for fast approximate nearest neighbor search. The hash store is updated to reflect the new version. Third, queries are classified: current queries are sent to Milvus for sub-100 ms retrieval; temporal queries load the appropriate Delta Lake snapshot, filter chunks by validity at the target timestamp, then compute cosine similarity in-memory (≤2 s). The dual-tier design isolates low-latency access from comprehensive version history, while deterministic hashing ensures consistent change detection and ACID transactions maintain cross-tier consistency.

## Key Results
- Reduces content re-processing to 10–15% of full re-indexing and achieves 100% change detection accuracy with ACID consistency.
- Latency: sub-100 ms for current queries, sub-2 s for temporal queries.
- Storage efficiency: hot tier holds only 10–20% of total chunks.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Deterministic chunk-level change detection via SHA-256 hashing enables selective re-processing of only modified content.
- **Mechanism**: Each semantic chunk is normalized and hashed; comparing hashes against a lightweight in-memory store identifies new, modified, and deleted chunks without querying persistent storage.
- **Core assumption**: Semantic chunk boundaries (paragraph-level) align with meaningful content changes; identical hashes guarantee identical semantics for deduplication and change detection.
- **Evidence anchors**: [abstract] "SHA-256 based chunk-level change detection... reduces content re-processing to 10-15%"; [section III.A] details hashing, normalization, and in-memory hash store comparison logic; [corpus] weak evidence; neighbor papers discuss streaming/CDC but not content-addressable hashing for semantic chunks.
- **Break condition**: If semantic chunking fails to capture coherent units (e.g., multi-paragraph arguments) or if content changes semantically without textual change (e.g., paraphrasing), hashing will miss modifications.

### Mechanism 2
- **Claim**: Dual-tier storage (hot: Milvus for active chunks; cold: Delta Lake for full history) independently optimizes query latency and storage cost while maintaining version history.
- **Mechanism**: Active chunks (valid_to = NULL) reside only in Milvus with HNSW for sub-100 ms queries; all historical versions, including superseded/deleted chunks, append to Delta Lake with ACID guarantees. Hot tier size is minimized because only ~10–20% of total chunks are active.
- **Core assumption**: Active chunk set is a small fraction of total historical chunks; query workload is dominated by current-knowledge queries.
- **Evidence anchors**: [abstract] "dual-tier architecture separating hot (Milvus)... from cold (Delta Lake)... stores only active chunks in the hot tier (10-20% of total)"; [section III.C] explicit schema design and write operations for both tiers; cross-tier consistency protocol; [corpus] weak; neighbor papers address vector indexing or lakehouses separately, not combined temporal-vector dual-tier.
- **Break condition**: If active chunk set grows disproportionately (e.g., many micro-versions with many active chunks), hot tier costs and query latency degrade.

### Mechanism 3
- **Claim**: Temporal query routing with validity filtering before similarity search prevents temporal leakage for point-in-time retrieval.
- **Mechanism**: Query classifier routes temporal queries to cold tier; system loads Delta Lake snapshot at target timestamp, filters chunks by valid_from ≤ target_ts < valid_to, *then* computes cosine similarity. This ensures only historically valid chunks are considered.
- **Core assumption**: Naïve post-filtering (similarity first, filter later) risks returning superseded/deleted chunks that rank highly; validity must constrain the search space.
- **Evidence anchors**: [section III.D.3] "Temporal Leakage Prevention: Validity filtering precedes similarity ranking..."; [section V.B.3] "100% accuracy, 0% temporal leakage" on test queries; [corpus] weak; related temporal IR work focuses on recency ranking, not point-in-time reconstruction.
- **Break condition**: If classifier misroutes queries or validity filtering logic is buggy, historical queries may leak future information or miss valid chunks.

## Foundational Learning
### Content-Addressable Storage (CAS)
- **Why needed here**: Enables deterministic, state-free change detection via cryptographic hashing. Without CAS, CDC requires external state tracking (e.g., database triggers) which adds overhead and complexity.
- **Quick check**: How does SHA-256 hashing of normalized chunk content allow automatic deduplication across documents and reliable change detection?

### Delta Lake ACID & Time-Travel
- **Why needed here**: Provides immutable version history with snapshot isolation for temporal queries. Without ACID, cross-tier consistency (hot/cold) would be vulnerable to partial failures during updates.
- **Quick check**: What Delta Lake features enable loading a table state "as of" a past timestamp, and how do they support LiveVectorLake's cold tier?

### HNSW Approximate Nearest Neighbor Indexing
- **Why needed here**: Enables sub-100 ms vector search in Milvus hot tier. Without efficient ANN, current query latency would be unacceptable for interactive RAG.
- **Quick check**: Why is HNSW preferred over brute-force search in the hot tier, and what are its key parameters (M, efConstruction) affecting index build vs. query trade-off?

## Architecture Onboarding
### Component Map
- **Ingestion Layer**: Document loader → Semantic chunker (paragraph boundaries) → SHA-256 hasher → In-memory hash store comparison → Change detector.
- **Storage Layer**: 
  - *Hot tier*: Milvus collection (active chunks, HNSW index)
  - *Cold tier*: Delta Lake table (all versions, Parquet files, transaction log)
- **Query Layer**: Query classifier → Embedding model → Router (hot or cold path) → Result formatter with provenance.
- **Consistency Layer**: Write-ahead log (Delta Lake first, then Milvus) + compensating transactions.

### Critical Path
Update flow: Document update → chunk hashing → change detection → embed only changed chunks → write to Delta Lake (append historical records) → write to Milvus (upsert active set) → update hash store.  
Query flow: Current query: embed → Milvus search (≤100 ms). Temporal query: embed → load Delta snapshot → filter by validity → in-memory similarity (≤2 s).

### Design Tradeoffs
- *Update latency vs. query freshness*: CDC reduces embedding load (10–15% vs 100%) but adds ~1.2 s update latency due to dual-tier writes.
- *Storage cost vs. historical completeness*: Hot tier is fast but expensive; cold tier cheap but slower. Ratio depends on active chunk fraction (evaluated 10–20%).
- *Temporal precision vs. performance*: Validity filtering before search prevents leakage but requires loading full Parquet snapshot for cold queries.

### Failure Signatures
- **Hash store corruption**: CDC fails → either full re-embedding (performance hit) or missed changes (stale data). Mitigation: periodic full recomputation from Delta Lake.
- **Milvus outage**: Hot queries fail; fallback to cold tier possible but with ~2 s latency. Consistency: uncommitted Delta records may exist until reconciliation.
- **Delta Lake transaction log loss**: Time-travel queries impossible; hot tier remains functional but version history lost.

### First 3 Experiments
1. **CDC accuracy stress test**: Introduce 50 real document updates (minor edits, paragraph additions/deletions). Verify hash-based detection matches ground truth (100% expected).
2. **Hot/cold tier ratio measurement**: After simulating 6 months of versions, measure active chunk percentage. Should be 10–20% per evaluation; investigate deviations.
3. **Temporal leakage check**: Run 20 historical queries with known answers at specific timestamps. Ensure 0% leakage and 100% recall of historically valid chunks.

## Open Questions the Paper Calls Out
1. **Retrieval quality benchmarks**: How do LiveVectorLake's retrieval quality metrics (MRR, NDCG@k, recall@k) compare to established RAG frameworks (LangChain, LlamaIndex) and vector databases (Pinecone) on standard benchmarks like BEIR or MS MARCO? The current evaluation uses a synthetic 100-document corpus focused on update efficiency and latency, not on standard IR quality benchmarks. Resolution would require running on BEIR/MS MARCO and comparing metrics.
2. **Learned temporal-semantic embeddings**: Can a joint embedding model that incorporates temporal context achieve comparable or better temporal retrieval accuracy without explicit post-search validity filtering, and what are the trade-offs in semantic search quality for current queries? The current system relies on separate temporal metadata and filtering, which adds latency for historical queries. Resolution would involve training a temporal-aware embedding model (e.g., via contrastive learning), evaluating its accuracy on point-in-time queries vs. the current approach, and measuring any semantic degradation on current-query benchmarks.
3. **Temporal knowledge graph extension**: How can LiveVectorLake's versioning model be extended from semantic chunks to a temporal knowledge graph that tracks versioned entities and relationships, enabling queries about evolving entity connections? The current architecture versions text chunks but does not extract or maintain versioned structured knowledge. Resolution would involve prototyping an extension that extracts versioned triples from chunks, stores them in a temporal graph database, and evaluating query accuracy/latency for relationship evolution queries against a test corpus with annotated entity changes.
4. **Semantic change detection via embedding drift**: Can semantic change detection be achieved by analyzing embedding drift (e.g., cosine distance between old and new chunk embeddings) to identify meaning shifts even when content wording changes are minimal or paraphrased, and can this improve audit precision over exact-hash matching? The current CDC relies on SHA-256 hashes for exact content matching, which cannot detect semantic equivalence with different phrasing. Resolution would require collecting a dataset of paraphrased updates and semantic edits, computing drift metrics, defining a drift threshold against human judgments, and comparing audit precision with hash-based approach.
5. **Adaptive tiering policy**: Can an ML-based adaptive tiering policy that dynamically migrates chunks between hot and cold tiers based on query frequency, recency, and temporal query patterns reduce storage costs further while maintaining current query latency SLAs? The current static policy keeps only active chunks in the hot tier. Resolution would involve simulating or implementing a reinforcement learning policy that migrates chunks based on query logs, measuring storage cost reduction and query latency impact, and comparing against the static 10–20% hot tier occupancy.

## Limitations
- **Chunking boundary alignment**: The reliance on paragraph-level semantic chunks assumes that meaningful content changes align with these boundaries; multi-paragraph edits or paraphrasing may yield false negatives in change detection.
- **Active chunk ratio generality**: The 10–20% active chunk figure is based on a 100-document, 5-version corpus; it may not hold for large-scale, high-churn knowledge bases where the active set could grow, undermining the hot/cold cost model.
- **Classifier dependency**: The 100% temporal routing accuracy depends entirely on the query classifier; no details on training data or failure modes are provided, so misrouting could cause temporal leakage or missed results.
