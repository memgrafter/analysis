# Personalized Medication Planning via Direct Domain Modeling and LLM-Generated Heuristics

## Quick Facts
- **arXiv ID:** 2601.03687
- **Source URL:** https://arxiv.org/abs/2601.03687
- **Reference count:** 13
- **Primary result:** LLM-generated, instance-specific heuristics guided Greedy Best-First Search to solve up to 36 of 37 scaled medication planning instances (28 drugs) vs. 2 by prior best heuristic, with significantly reduced planning time.

## Executive Summary
Personalized medication planning (PMP) aims to automatically generate safe and effective drug dosing schedules for individual patients, but its computational complexity has limited prior methods to at most seven drugs. This paper replaces generic, domain-independent heuristics with automatically generated, problem-specific heuristics created by large language models (GPT-5.1, Claude Sonnet-4.5) from a programmatic domain description in Rust. The heuristics guide a Greedy Best-First Search (GBFS), enabling the system to scale to clinically relevant sizes (up to 28 drugs) and dramatically improve coverage on the hardest benchmarks—solving up to 36 of 37 instances compared to 2 previously—while also reducing planning time. The approach demonstrates the power of LLM-generated, instance-specific guidance in complex numeric planning.

## Method Summary
The authors propose a framework where the planning domain—state representation, successor generation (simulating pharmacokinetics/pharmacodynamics), goal test, and constraints—is implemented as a Rust library. Given a specific patient problem (converted to a JSON instance), an LLM is prompted with the Rust domain code and the problem description to generate a Rust heuristic function that estimates the minimum remaining time to achieve all therapeutic goals. This heuristic is compiled and linked with the domain, then used by GBFS to search for a solution. A meta-controller orchestrates up to 10 generation attempts, retrying on compilation failures or out-of-memory errors. Evaluations on scaled PMP benchmarks show that the LLM-generated heuristics provide high-quality guidance, making GBFS far more effective than state-of-the-art domain-independent heuristics.

## Key Results
- Coverage on hardest benchmarks (Tight Constraints, Time Stretching X4) scaled to 28 drugs jumped from ≤2 to up to 36 of 37 instances solved.
- Planning time was significantly reduced compared to baselines.
- The method scales to clinically relevant drug counts, overcoming previous limits of seven drugs.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** LLM-generated, problem-specific heuristics provide more accurate guidance for search than generic domain-independent heuristics in large-scale PMP.
- **Mechanism:** The LLM ingests a structured problem description (JSON) and the Rust-coded domain (successor function, goal test) to produce a Rust function that estimates the minimum time to achieve remaining goals from a given state. This heuristic encodes instance-specific knowledge about drug potency, safety margins, and clearance times that generic heuristics cannot capture.
- **Core assumption:** The LLM can correctly interpret the programmatic domain description and the patient-specific PK/PD parameters to synthesize a cost estimation function that aligns with the true search landscape.
- **Evidence anchors:**
  - Abstract: "replaces those [domain-independent heuristics] with automatically generated, problem-specific heuristics created by an LLM... guiding greedy best-first search (GBFS)."
  - Section "Generating Heuristics": Describes the three-part prompt and example heuristic combining `max goal time`, `clearance penalty`, and `safety penalty`.
- **Break condition:** The generated heuristic is syntactically invalid, panics at runtime, or consistently returns misleading estimates (e.g., always 0 or infinity), causing search to fail within resource limits.

### Mechanism 2
- **Claim:** Programmatic domain specification in Rust enables safe, efficient integration of generated heuristic code with the search engine.
- **Mechanism:** The domain—including state representation, successor generation (PK/PD simulation), and goal test—is implemented as Rust functions. Rust’s strong static typing and memory safety allow the system to trust that the LLM-generated heuristic (also in Rust) can be compiled and linked without undefined behavior and will interact correctly with the domain’s state structure.
- **Core assumption:** The Rust-based domain code is correct and faithfully implements the PMP definition; the LLM can produce syntactically and semantically valid Rust adhering to the expected function signature and data structures.
- **Evidence anchors:**
  - Abstract: "specify the domain programmatically (specifying an initial state and a successor generation procedure)"
  - Section "Searching with LLM-Generated Heuristics": "We employ Greedy Best-First Search (GBFS)... The Rust code is given to a LLM to generate a suitable heuristic in Rust. The heuristic is compiled and linked..."
  - Section "Medication Planning Problems Definition": Details the GMP tuple and `adm(m, d, t)` action.
- **Break condition:** The manually written Rust domain contains a bug in PK/PD simulation or constraint checking, or the generated heuristic compiles but violates logical invariants (e.g., assumes instantaneous drug effects).

### Mechanism 3
- **Claim:** GBFS with a high-quality, instance-specific heuristic efficiently navigates the enormous branching factor from many drugs and long time horizons.
- **Mechanism:** GBFS expands the most promising node (lowest heuristic value) first. The LLM-generated heuristic provides a tight, problem-aware estimate of remaining time-to-goal, drastically reducing the number of state expansions compared to uninformed search or weak heuristics. Its components (goal time, clearance, safety) directly address core challenges: long durations, drug elimination, and narrow safety margins.
- **Core assumption:** The heuristic is admissible or at least sufficiently informed to consistently rank nodes closer to a solution higher than those farther away, despite complex numeric fluents and time.
- **Evidence anchors:**
  - Abstract: coverage improved dramatically and planning time reduced.
  - Table 2: coverage jumps on scaled domains.
  - Section "Robust Usage of the Approach": Retry strategy compensates for non-admissible or misguiding heuristics.
- **Break condition:** The heuristic is consistently misinformative (e.g., overestimates), causing GBFS to follow poor paths and exhaust resources. The retry loop mitigates but does not eliminate this risk.

## Foundational Learning
- **Pharmacokinetic/Pharmacodynamic (PK/PD) Modeling:** Needed to understand the successor function and state updates, which simulate drug concentration and effect over time. The models use formulas like `b[m] := g(b,m,Δt)·d` for biodistribution and `b[p] += Emax·b[m]/(b[m]+EC50)` for effect, with Loewe-additivity for interactions. *Quick check:* How would the state trajectory change if a drug has a longer elimination half-life (`elim`) in the `MaxGoalTime` function?
- **Greedy Best-First Search (GBFS):** The fixed search algorithm that consumes the LLM-generated heuristic. Its performance depends entirely on heuristic quality. *Quick check:* If the heuristic for a state is 10 but the true minimum cost is 50, what is the risk for GBFS?
- **Programmatic Domain Specification vs. PDDL+:** Representing the domain as executable Rust code rather than declarative PDDL+ enables direct LLM generation of heuristics. *Quick check:* What is one advantage of a programmatic successor function over a PDDL+ `:effect` for modeling the non-linear PK trajectory?

## Architecture Onboarding
**Component map:** Problem Translator → Domain Implementation (Rust) → LLM Heuristic Generator → Compiler & Linker → GBFS Executor → Meta-Controller. The meta-controller loops back to the LLM Heuristic Generator on failure to retry.

**Critical path:** Instance JSON → LLM Prompt → Generated Heuristic Rust Code → Compile → Linked GBFS Binary → Search → Solution or Failure.

**Design tradeoffs:**  
- *LLM Choice (GPT-5.1 vs. Claude):* GPT-5.1 had higher individual success rate (57.3%) but higher OOM rate (34.2%) and longer generation time; Claude had lower success rate (29.5%) but lower OOM (12.8%) and faster generation.  
- *Retry Budget:* 100-second time-slice per generation batch balances opportunity vs. total runtime.  
- *Rust Safety vs. Expressivity:* Rust’s borrow checker prevents many errors but may constrain the LLM’s heuristic design space compared to dynamic languages.

**Failure signatures:**  
1. `Compilation error`: Invalid Rust syntax or type misuse.  
2. `Out of Memory (OOM)`: Heuristic or search state explosions.  
3. `Runtime panic/error`: Heuristic logic flawed (e.g., division by zero).  
4. `Timeout`: Search exhausts 600s budget.

**First 3 experiments:**  
1. Baseline Replication: Run ENHSP-20 with domain-independent heuristics on original 7-drug, 37-instance sets; confirm prior results.  
2. Scaling Test: Scale two hardest domains (`Tight`, `Stretching X4`) by 4× drugs; run LLM-generated heuristic method; measure coverage and runtime vs. baselines.  
3. LLM Comparison & Robustness: For a hard domain, generate 30 heuristics with each model; run Monte Carlo to measure variance in coverage.

## Open Questions the Paper Calls Out
- **Open Question 1:** Can prompt engineering or LLM fine-tuning systematically improve reliability and quality of generated heuristics, reducing compilation failures and OOM errors? The authors note the prompt is not optimized and report high failure rates, using a retry strategy instead. Evidence: systematic prompt variations would be needed.
- **Open Question 2:** What are the fundamental limits of the LLM-generated heuristic approach as problem size and complexity increase beyond 28 drugs? Scaling experiments beyond this are absent. Evidence: empirical tests with more drugs and constraint tightness.
- **Open Question 3:** How clinically valid and safe are generated plans when evaluated against pharmacological experts or in biological models, beyond simulated PK/PD? The paper admits lack of clinical validation. Evidence: prospective validation studies required.
- **Open Question 4:** To what extent can the problem-specific heuristic generation be fully automated from a standard problem representation (e.g., PDDL+), removing the manual JSON translation? The authors note this as future work. Evidence: development and evaluation of an automated translator.
- **Open Question 5:** How do the generated heuristics generalize across different patient problems within the same domain, and could a portfolio of heuristics be combined? The retry strategy shows variance; combining heuristics is left for future work. Evidence: experiments on heuristic transferability and portfolios.

## Limitations
- Exact LLM prompt and Rust API details are not fully disclosed, hindering precise replication.
- Method for scaling drug instances (4×) is unspecified, introducing variability in benchmark difficulty.
- Evaluation is limited to synthetic benchmarks; clinical feasibility and generalizability remain unproven.

## Confidence
- LLM-generated heuristics significantly improve coverage and runtime: **High**
- Rust-based programmatic domain enables safe, efficient integration: **Medium**
- The approach scales to clinically relevant problem sizes (up to 28 drugs): **High**
