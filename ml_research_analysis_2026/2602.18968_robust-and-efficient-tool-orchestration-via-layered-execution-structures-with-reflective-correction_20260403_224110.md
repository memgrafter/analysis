# Robust and Efficient Tool Orchestration via Layered Execution Structures with Reflective Correction

## Quick Facts
- arXiv ID: 2602.18968
- Source URL: https://arxiv.org/abs/2602.18968
- Reference count: 21
- Primary result: RETO achieves a 49.5% average solvable pass rate (SoPR) on StableToolBench with a non-tool-tuned Qwen2.5-7B backbone, matching tool-tuned baselines while reducing token consumption by 69.6–84.8% and inference steps by 40.5–69.6%.

## Executive Summary
Multi-tool orchestration often fails due to brittle execution order and error propagation, especially for small language models (SLMs). This paper introduces RETO, a framework that decouples global structure from local execution. RETO uses a lightweight layer predictor to infer a coarse-grained dependency structure (layered execution) and then executes tools layer by layer, constraining the context per step. A schema-aware reflective correction mechanism detects and repairs invalid tool calls locally under a tight budget, confining failures and avoiding global re-planning. On the StableToolBench benchmark, RETO with a 7B model achieves performance comparable to tool-tuned baselines while drastically reducing token usage and steps, and remains effective down to 1.5B models, demonstrating a robust and efficient approach for resource-constrained SLMs.

## Method Summary
RETO consists of three core components. First, a layer predictor trained via ordinal regression on DTA-Tool trajectories assigns each candidate tool to an ordered layer (0 to L-1) such that tools in layer k may depend only on outputs from earlier layers. This coarse structure reduces the combinatorial planning problem. Second, during execution, an engine iterates through layers; at each layer k, the executor SLM sees only the schemas of tools predicted for that layer and prior observations, producing tool calls. Third, a schema gate validates each call against the tool's JSON schema; invalid or failed calls trigger a repair loop (deterministic edits followed by LLM repair) with a fixed budget B. After all layers, a forced Finish step grounds the final answer in the execution summary. The method is trained offline on the layer predictor only; the executor is a frozen pretrained SLM, making the system efficient and adaptable.

## Key Results
- RETO (Qwen2.5-7B) achieves 49.5% average solvable pass rate (SoPR) on StableToolBench, significantly higher than DFSDT's 12.2% and matching tool-tuned baselines.
- Token consumption reduced by 69.6–84.8% and inference steps reduced by 40.5–69.6% compared to baselines.
- Performance remains robust down to 1.5B model sizes, demonstrating scalability to resource-constrained SLMs.

## Why This Works (Mechanism)
### Mechanism 1: Coarse-grained layering for global structure
**Claim:** Coarse-grained layering provides sufficient global structure to guide tool orchestration without requiring precise dependency graphs.
**Mechanism:** A lightweight layer predictor assigns tools to ordered layers where layer k tools may depend on outputs from layers < k. This transforms the combinatorial problem of predicting full dependency graphs into ordinal layer assignment, reducing planning complexity.
**Core assumption:** High-level tool dependencies can be captured by coarse layering rather than fine-grained pairwise edges.
**Evidence anchors:** Abstract and Section 3.2 describe the ordinal regression predictor; corpus focuses on agentic systems broadly.
**Break condition:** If tool dependencies are truly non-layered (e.g., cyclic), misassignments cause failures. Paper shows degradation only at 0.5B scale, suggesting layering works for typical workflows.

### Mechanism 2: Context-constrained invocation
**Claim:** Constraining the model's action space per layer reduces decision space and prevents out-of-turn calls, making execution tractable for SLMs.
**Mechanism:** At each layer, the LM sees only schemas of current-layer tools and prior outputs, breaking long-horizon reasoning into short, scoped decisions. This keeps context compact and prevents premature/delayed tool use.
**Core assumption:** SLMs can execute reliably when the action space is restricted to a small, relevant subset per step.
**Evidence anchors:** Abstract; Section 3.3; Section 4.2.1 notes separation of planning and execution.
**Break condition:** If layer assignments are too coarse or the LM ignores constraints, decision space remains large; the schema gate and prompt engineering enforce compliance.

### Mechanism 3: Schema-aware reflective correction
**Claim:** Local detection and repair of invalid tool calls confines failures without global re-planning.
**Mechanism:** A lightweight schema gate validates arguments pre-execution; rejected/failed calls go to a repair operator (deterministic edits then LLM-based) under a fixed budget B. Repairs are local, avoiding trajectory-wide retries.
**Core assumption:** Most execution failures are local argument/tool-selection errors repairable in isolation.
**Evidence anchors:** Abstract; Section 3.4 (Algorithm 1); Section 4.2.4 ablation shows necessity.
**Break condition:** If errors require global re-planning (e.g., earlier tool choice invalidates later steps), local repair fails. Paper acknowledges this limitation in Appendix A.2.

## Foundational Learning
### Ordinal Regression for Layer Assignment
**Why needed:** To assign tools to ordered execution layers efficiently, exploiting the inherent order among layers.
**Quick check:** Why use ordinal regression instead of multi-class classification for predicting execution layers? What would happen if layers were treated as independent classes?

### Context Window Management in SLMs
**Why needed:** RETO's efficiency relies on keeping per-step context small; SLMs degrade with long contexts. Layer-wise execution restricts the context to current-layer tools and prior outputs.
**Quick check:** How does the layer-wise execution protocol reduce effective context length compared to ReAct's full-history approach?

### Schema-Based Validation
**Why needed:** The schema gate performs lightweight pre-execution checks (required keys, types, enums) catching argument errors before they pollute the execution trace, which is cheaper than waiting for API failures.

## Architecture Onboarding
**Component map:** Layer Predictor -> Execution Engine (with Schema Gate and Repair Operator) -> Finish Step.

**Critical path:**  
1. **Training:** Extract layer annotations from DTA-Tool trajectories; train ordinal regression predictor (2-layer Transformer, 256 dim, 8 heads) for 10 epochs, lr=1e-3.  
2. **Inference prep:** Given query q and tool set T, encode with ToolBench IR BERT, predict layers ˆlᵢ. Apply schema-level constraint shifting if needed.  
3. **Execution loop:** For k = 0 to max(ˆlᵢ): prompt executor SLM with allowed tools Tₖ and prior observations; parse tool calls in JSON.  
4. **Per-call validation:** For each call (t, A), run Schema Gate. If rejected/API error, invoke Repair (deterministic then LLM) up to budget B.  
5. **Finalize:** After all layers, issue Finish prompt with execution summary to produce final answer.

**Design tradeoffs:**  
- **Max layers L:** Paper uses L=5; too few reduces guidance, too many adds overhead.  
- **Repair budget B:** Paper uses B=5; higher improves recovery but increases token cost, lower may cause premature failures.  
- **Predictor capacity:** Small projection (256 dim) sufficient, enabling use with tiny backbones (1.5B works).  
- **Schema strictness:** Gate rejects invalid calls but may also reject semantically valid minor mismatches; trade-off between safety and flexibility.

**Failure signatures:**  
- Layer predictor misassignment → wrong layer ordering.  
- Executor ignoring layer constraints → out-of-layer tool calls.  
- Repair budget exhaustion → incomplete trajectories.  
- Schema gate false negatives → valid calls rejected.  
- Final answer hallucination despite Finish instruction.

**First 3 experiments:**  
1. **Layer predictor accuracy:** Measure per-tool layer assignment and ranking consistency on held-out DTA-Tool annotations. Expected accuracy >80%.  
2. **Zero-shot generalization:** Test on StableToolBench Inst. splits with Qwen2.5-7B; expect SoPR ~50% on I1-Inst.  
3. **Repair budget sweep:** Vary B ∈ {1,3,5,10} on I2-Inst.; plot SoPR vs. token cost; expect diminishing returns after B=5.

## Open Questions the Paper Calls Out
1. **Improving layer predictor quality for complex dependencies:** How to handle deeply nested or cyclic tool dependencies? Error analysis and architectural changes (e.g., GNNs) could help.  
2. **Lower bound on backbone model size:** What is the minimal model size for RETO to remain effective? Could training/architectural modifications push this further? Requires systematic evaluation across sizes with controlled ablations.  
3. **Extending local repair to global re-planning:** Can RETO handle failures that require revisiting earlier decisions? Possibly via lightweight backtracking.  
4. **Adaptation to dynamic tool sets:** How to incorporate on-the-fly tool retrieval when new tools become relevant mid-execution?  
5. **Richer failure diagnosis signals:** Beyond JSON validation, what additional signals (e.g., semantic error types) could make repair more effective? Could be elicited from LLMs or tools cheaply.

## Limitations
- **Layer annotation derivation:** The mapping from DTA-Tool execution trees to integer layers is underspecified, risking mismatched training data in reproduction.  
- **Repair LLM identity:** Unclear whether the executor SLM or a separate model performs Tier-2 repair, affecting cost and performance.  
- **Schema-level constraint shifting:** Implementation details for matching output/input types and enforcing shifting during prediction are missing.
