# Supercharging Federated Intelligence Retrieval

## Quick Facts
*   **arXiv ID:** 2603.25374
*   **Source URL:** https://arxiv.org/abs/2603.25374
*   **Reference count:** 22
*   **Primary result:** Cascading inference improves accuracy by ~40-46% over standalone CPU inference, while a confidential GPU-backed mode achieves the highest accuracy and lowest latency with end-to-end data confidentiality.

## Executive Summary
This paper addresses a critical limitation of standard Retrieval-Augmented Generation (RAG): its assumption of centralized document access, which fails when knowledge is distributed across private data silos. The authors present a secure Federated RAG system built on the Flower framework. It performs local retrieval within each silo, aggregates results on a server within a hardware-enforced Trusted Execution Environment (TEE), and generates responses confidentially. A cascading inference variant incorporates a non-confidential third-party LLM as auxiliary context. Evaluations on medical QA benchmarks demonstrate that cascading inference yields substantial accuracy gains (~40% on PubMedQA, ~46% on MedQA) over a standalone CPU-based model, while the confidential inference mode using a large GPU-backed model within the TEE achieves the best accuracy and latency while maintaining strict data confidentiality.

## Method Summary
The system orchestrates a federated retrieval and generation pipeline using the Flower framework. Each client/silo hosts a local FAISS vector index over its private document corpus. Upon receiving a query, the server (running inside a TEE) broadcasts it to all verified clients. Each client performs a local top-*k* retrieval and returns only the retrieved snippets and scores to the server's TEE. Inside the TEE, results are aggregated (using Reciprocal Rank Fusion) and combined with a prompt. Three inference modes are supported: 1) **Standalone**, using a CPU-bound SmolLM 1.7B model; 2) **Cascading**, which first obtains an answer from an external AWS Nova Micro model using the *query alone* and appends it as context for SmolLM; and 3) **Confidential**, which uses a GPU-backed Qwen3 235B model executed within the TEE via Flower Confidential Remote Compute (CRC). The pipeline is evaluated on medical QA datasets (PubMedQA, BioASQ, MedQA) measuring accuracy and end-to-end query latency.

## Key Results
*   Cascading inference improves accuracy by approximately 40% on PubMedQA and 46% on MedQA compared to the standalone CPU-based SmolLM mode.
*   The confidential inference mode (Qwen3 235B in TEE) achieves the highest reported accuracy (e.g., 0.82 on BioASQ, 0.78 on MedQA) and the lowest mean latency (25 seconds per query).
*   The cascading and confidential modes maintain end-to-end data confidentiality, as raw documents never leave their silos and server-side processing occurs in an attested TEE.

## Why This Works (Mechanism)

### Mechanism 1
*   **Claim:** Federated retrieval preserves data locality by ensuring raw documents never leave their silo.
*   **Mechanism:** Each client/silo executes a local vector search (FAISS) over its private corpus, returning only the top-*k* retrieved document snippets and their scores to the server. The server never accesses any silo's raw data store.
*   **Core assumption:** Silos are honest-but-curious and will not share raw documents with each other or the server, following standard FL trust assumptions.
*   **Evidence anchors:** [abstract]: "performs local silo retrieval"; [section 3]: "Each client retrieves the top-*k* relevant documents from its local private document store and returns them to the server".
*   **Break condition:** Collusion between multiple malicious clients to reconstruct raw data from repeated queries or if retrieval scores themselves leak sensitive information.

### Mechanism 2
*   **Claim:** A hardware-enforced TEE on the server protects the aggregation of retrieved documents and the subsequent LLM generation from a compromised or honest-but-curious server operator.
*   **Mechanism:** The server's aggregation logic (merging, re-ranking) and the LLM inference run inside an attested TEE (Flower CRC). Plaintext documents and prompts are only exposed inside this isolated enclave, inaccessible to the host OS or infrastructure provider.
*   **Core assumption:** The TEE (e.g., Intel SGX, AWS Nitro) is secure against software attacks and remote attestation correctly verifies the enclave's integrity.
*   **Evidence anchors:** [abstract]: "server-side aggregation and text generation run inside an attested, confidential compute environment"; [section 3]: "the entire server-side workload... runs inside a TEE" and "documents only decrypted within Flower CRC’s hardened TEE".
*   **Break condition:** A successful side-channel attack on the TEE, a flawed enclave implementation, or a compromised attestation service.

### Mechanism 3
*   **Claim:** Cascading inference confidentially boosts accuracy by treating a non-confidential third-party LLM's output as an auxiliary context source, without exposing the original private documents.
*   **Mechanism:** The server's TEE first acquires an answer from a third-party model (e.g., AWS Nova) using only the *query* (not the retrieved private documents). This external answer is then concatenated with the securely aggregated retrieved documents as context for the server's own LLM (SmolLM or Qwen3 in CRC). The sensitive documents never leave the TEE.
*   **Core assumption:** The third-party provider is honest (or at least, its API does not log or misuse the plaintext query), and the query itself does not contain highly sensitive information.
*   **Evidence anchors:** [abstract]: "incorporates a non-confidential third-party model... as auxiliary context without weakening confidentiality"; [section 3]: Describes the three modes; [section 4]: "Cascading Inference... even with the lightweight Amazon Nova Micro model, the additional context... yields a ∼40% improvement".
*   **Break condition:** Malicious or logging third-party provider that records queries; or if the external model's answer is itself factually harmful.

## Foundational Learning
*   **Concept: Federated Learning (FL) Orchestration (Flower)**
    *   **Why needed here:** The entire system is built on the Flower framework for coordinating distributed clients. Understanding `ServerApp`, `ClientApp`, `SuperLink`/`SuperNode` roles is essential to trace the query lifecycle.
    *   **Quick check question:** In the Flower FL paradigm, what is the fundamental responsibility of the `ServerApp` versus a `ClientApp`?

*   **Concept: Trusted Execution Environments (TEEs) & Remote Attestation**
    *   **Why needed here:** The security guarantees for server-side aggregation and generation rely entirely on the TEE's isolation and the attestation process that verifies it to clients. This is the cornerstone of the "confidential" claim.
    *   **Quick check question:** What is the difference between the confidentiality goals of a TEE and those provided by standard TLS encryption at rest/in transit?

*   **Concept: Retrieval-Augmented Generation (RAG) Pipeline**
    *   **Why needed here:** This work modifies the standard RAG pattern (Retrieve -> Augment -> Generate) to be federated and confidential. One must understand the baseline to see where the federated and TEE steps are inserted.
    *   **Quick check question:** In a canonical RAG system, what are the two primary components, and what is the purpose of the "augment" step?

## Architecture Onboarding
*   **Component map:** Clients/Silos (with local FAISS index & document store) -> Flower SuperLink/SuperNode -> Server-Side TEE (Flower CRC) -> (Optional) Third-Party LLM API -> User
*   **Critical path (Confidential Inference Mode):** 1. User query → Flower SuperLink. 2. SuperLink (outside TEE) forwards query to attested Server TEE. 3. TEE broadcasts query to verified clients. 4. Clients perform local FAISS retrieval → return top-*k* snippets + scores to TEE. 5. TEE aggregates snippets (RRF), constructs prompt. 6. TEE sends prompt to `Qwen3 235B` model within same TEE (Flower CRC). 7. Generated answer sent from TEE to SuperLink → user.
*   **Design tradeoffs:** Security vs. Performance/Latency (TEE overhead); Trust vs. Utility (cascading trusts external provider with query); Cost (GPU TEE vs. CPU-bound models).
*   **Failure signatures:** High latency, low accuracy (Standalone mode indicates insufficient CPU model); Attestation failure (hardware/software mismatch); Cascading underperformance (poor external model response); Resource exhaustion in TEE (model too large for enclave memory).
*   **First 3 experiments:**
    1.  **Baseline retrieval sanity check:** With a single client, run a known query and verify returned snippets are relevant. Validate FAISS index building and L2 metric behavior.
    2.  **TEE overhead isolation:** Run the same query in "Standalone" mode with the LLM *inside* vs. *outside* a minimal TEE. Measure pure CPU TEE overhead on SmolLM.
    3.  **Cascading context ablation:** For a fixed query, compare: (a) SmolLM with only retrieved docs, (b) SmolLM with docs + Nova answer, (c) Nova answer alone. Quantify the added value and potential harm from the auxiliary context.

## Open Questions the Paper Calls Out
1.  How does scaling the third-party model capacity in cascading inference affect the accuracy-latency trade-offs in FedRAG? The authors note that more powerful Nova Pro/Premier models are a promising direction for further evaluation after showing gains with Nova Micro.
2.  What are the practical risks of side-channel attacks against the TEE in the confidential inference mode, despite being out-of-scope in the threat model? The system assumes TEE security, but real-world TEEs like Intel SGX have demonstrated side-channel leaks that could compromise confidentiality.
3.  Does the FedRAG system generalize to non-medical domains (e.g., legal or financial) with different document types and query structures? Evaluation is restricted to medical QA benchmarks with no cross-domain tests reported.
4.  How sensitive is the FedRAG performance to the reciprocal rank fusion parameter (kRRF) and top-k retrieval, especially regarding communication overhead in large-scale federations? Fixed values are used without analysis of their impact on communication costs or accuracy with more silos or larger corpora.

## Limitations
*   **TEE/CRC Deployment Specifics:** The exact hardware (SGX vs. SEV-SNP), cloud setup, Flower CRC configuration, and remote attestation implementation are unspecified, blocking direct replication of the confidential mode.
*   **Model & Prompt Details:** Precise model identifiers, quantization methods, and the full prompt template for SmolLM and Qwen3 are unknown. The AWS Nova Micro API contract and its prompt are also not detailed.
*   **Cascading Trust Boundary:** The security of the query sent to the third-party LLM is assumed but not formally modeled; a logging or malicious provider could compromise query privacy.

## Next Checks
1.  **Isolate TEE Overhead:** Run the *same* SmolLM inference in "Standalone" mode both inside and outside a minimal TEE (e.g., SGX/SEV) on identical hardware. Measure pure CPU/GPU latency delta to quantify the confidential compute tax.
2.  **Cascading Context Ablation:** For a fixed query set, compare: (a) SmolLM with only retrieved docs, (b) SmolLM with docs + Nova answer, (c) **Nova answer alone.** This isolates the net positive/negative contribution of the auxiliary context.
3.  **Reproduce Federated Retrieval Core:** Using public Flower docs, implement a minimal client-server with local FAISS indexes (`IndexFlatL2`, `top-k=8`). Validate that aggregation with `kRRF=60` on 4 clients yields the same document merge order/score distribution as the paper's setup for a known query.
