# A survey: Information search time optimization based on RAG (Retrieval Augmentation Generation) chatbot

## Quick Facts
- **arXiv ID**: 2601.07838
- **Source URL**: https://arxiv.org/abs/2601.07838
- **Reference count**: 20
- **Primary result**: A RAG-based chatbot achieved 80–95.5% reduction in average query time compared to manual search across simple, complex, and calculation-intensive corporate information retrieval tasks.

## Executive Summary
This study evaluates a Retrieval-Augmented Generation (RAG) chatbot for corporate information retrieval against traditional manual search. Implemented with LangChain, ADA‑002 embeddings, Milvus, and OpenAI’s API on 2,300 Confluence pages, the system was tested by 105 employees across five departments. Participants performed the same 10 queries—categorized as simple, multi‑page complex, or calculation‑intensive—using both methods. The chatbot reduced time per query by 80% for simple searches, 90% for complex multi‑page searches, and 95.5% for those requiring manual calculation. Moreover, manual search time grew polynomially with query complexity, while chatbot time remained nearly linear, indicating strong scalability benefits.

## Method Summary
The RAG pipeline ingested Confluence pages via LangChain loaders, split them into chunks, generated embeddings with ADA‑002, and stored them in Milvus. For a query, the system embedded the question, retrieved the top‑k most similar chunks using vector similarity, assembled these as context, and prompted an OpenAI LLM to generate an answer. Evaluation involved timing participants as they answered the fixed set of 10 queries with both manual Confluence search and the chatbot. Answer correctness was later verified against the source corpus. Mean times per query type were compared to compute percentage reductions.

## Key Results
- Simple queries: 80% time reduction.
- Multi‑page complex queries: 90% reduction.
- Calculation‑intensive queries: 95.5% reduction.
- Manual search time scaled polynomially with query complexity; chatbot time scaled nearly linearly.

## Why This Works (Mechanism)
Efficiency stems from three mechanisms:
1. **Parallel semantic retrieval**: The vector database performs a single similarity search over all embedded chunks, replacing sequential human document navigation.
2. **Near‑constant retrieval complexity**: Approximate nearest‑neighbor search scales sub‑linearly with corpus size, keeping retrieval time stable as documents grow.
3. **Automated synthesis and calculation**: The LLM directly aggregates and computes information from retrieved chunks, eliminating separate human comprehension and arithmetic steps.

## Foundational Learning
- **Vector Embeddings & Semantic Similarity Search**: Why needed here: Retrieval hinges on mapping text to vectors where proximity reflects meaning; this determines failure modes (e.g., jargon mismatch). Quick check: If a query uses a synonym not present in the corpus, will vector search still find relevant passages? Why?
- **Retrieval Augmented Generation (RAG) Pattern**: Why needed here: This pattern distinguishes the system from a pure LLM by grounding generation in retrieved private data, reducing hallucinations for corpus‑bound queries. Quick check: What is the functional role of the vector database? What would change if it were replaced by a keyword search engine?
- **Latency Budgeting in Interactive Systems**: Why needed here: The key metric is time per query; engineers must profile each pipeline stage (embedding, search, API, generation) to identify bottlenecks. Quick check: Given an OpenAI API call takes ~2 s for a 500‑token response and Milvus search on 1M vectors takes 50 ms, which stage dominates total latency?

## Architecture Onboarding
**Component map**  
Data Ingestion: Confluence API → LangChain loaders → Text chunker → ADA‑002 embedding → Milvus vector DB.  
Query Pipeline: Web UI → Query string → ADA‑002 embedding → Milvus top‑k similarity search → Context assembly → Prompt template → OpenAI API → Answer display.

**Critical path**: The OpenAI API call (seconds) dominates latency; embedding and Milvus search are much faster (milliseconds). Reducing k or context length can modestly lower latency but risks omitting key information.

**Design tradeoffs**  
- *Embedding model (ADA‑002)*: High performance but vendor lock‑in and per‑embedding cost vs. open‑source alternatives (e.g., all‑MiniLM‑L6‑v2).  
- *LLM backend (OpenAI API)*: State‑of‑the‑art quality vs. data‑privacy concerns, cost, and latency variance; trade‑off with local models (e.g., Llama 3) on privacy/latency vs. quality.  
- *Chunking strategy*: Smaller chunks improve retrieval precision but may lose cross‑chunk context; larger chunks risk including irrelevant text and exceeding the LLM’s context window.

**Failure signatures**  
- *Hallucination within corpus*: LLM generates facts not supported by retrieved context; user must verify.  
- *Time not improving for complex queries*: Chatbot latency approaches manual search; likely due to excessive k or overly long generation.  
- *Zero results for valid query*: Milvus returns no relevant vectors; may stem from embedding mismatch, poor chunking, or indexing errors.

**First 3 experiments**  
1. *Baseline time metric replication*: Run the exact 10‑query set (5 simple, 3 complex, 2 calculation) with ≥5 participants to replicate the reported 80–95.5% reductions.  
2. *Complexity scaling test*: Generate 20 queries of increasing complexity; measure and plot time vs. complexity for both methods to verify polynomial vs. near‑linear scaling.  
3. *Retrieval quality & k sensitivity*: For a fixed query set, vary k (1, 3, 5, 10); measure answer correctness and latency to find the optimal balance.

## Open Questions the Paper Calls Out
1. Does the significant time reduction generalize to larger organizations with more extensive and diverse document repositories?  
2. Can RAG chatbots achieve comparable benefits in non‑text domains (e.g., image analysis, medical report processing)?  
3. How does the scaling relationship change when query complexity is measured by semantic depth rather than length?  
4. What is the impact of alternative embedding models (e.g., BERT‑based) and vector databases (e.g., Pinecone) on the speed‑accuracy trade‑off?

## Limitations
- Unreproducible query set and ground truth answers block exact replication.  
- Critical configuration parameters (chunk size, retrieval k, OpenAI model version, prompt template) are unspecified.  
- Timing methodology and operational definition of “answer found” are ambiguous, risking measurement bias.  
- The hallucination rate is not quantified, potentially invalidating time savings if errors are frequent.

## Confidence
- Overall time reduction claim (80–95%): **Medium**  
- Mechanism 1 (Parallel semantic retrieval): **Medium**  
- Mechanism 2 (Polynomial vs. linear scaling): **Low**  
- Mechanism 3 (Automated calculation): **Low**

## Next Checks
1. Replicate the baseline timing experiment with a newly created comparable query set and ≥5 participants to confirm the reported reductions.  
2. Perform a sensitivity analysis varying retrieval k to assess its effect on answer correctness and query latency, testing the assumption that a small fixed k suffices.  
3. Conduct a factual accuracy audit of chatbot outputs (from original or replication study) and examine whether erroneous answers correlate with suspiciously fast response times.
