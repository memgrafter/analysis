# ToolGym: an Open-world Tool-using Environment for Scalable Agent Testing and Data Curation

## Quick Facts
- **arXiv ID:** 2601.06328  
- **Source URL:** https://arxiv.org/abs/2601.06328  
- **Reference count:** 13  
- **Primary result:** ToolGym provides a large-scale open-world environment with 5,571 unified tools and a state controller for robust agent testing; evaluations reveal a planning-execution misalignment and fine-tuning on just 1,170 curated trajectories yields superior performance.

## Executive Summary
ToolGym is a new benchmark environment designed to evaluate tool-using LLM agents in realistic, large-scale scenarios. It standardizes 5,571 tools from 204 applications into a common invocation format, synthesizes long-horizon workflows with complex constraints, and injects realistic failures via a state controller. Testing across frontier models uncovers a gap between planning and execution abilities, with constraint following as the dominant failure mode. DeepSeek-v3.2 shows the strongest robustness and recovery. Moreover, fine-tuning models on only 1,170 high-quality trajectories from ToolGym outperforms baselines trained on 119k samples, demonstrating its efficiency as a data engine for agent training.

## Method Summary
ToolGym’s core method involves three components: (1) a **Tool Universe** of 5,571 manually curated tools unified under the Model Context Protocol (MCP) schema, indexed with FAISS for retrieval; (2) a **Task Engine** that automatically generates long-horizon tasks by sampling coherent tool bundles and iteratively enriching them with “wild constraints” (e.g., diversity, order, trade-offs) via an LLM-based refinement loop; and (3) a **State Controller** that intercepts tool execution to simulate real-world failures (timeouts, rate limits, session expiry, evolving constraints). Agents follow a planner–actor architecture: the planner decomposes the task into a sub‑goal graph and provides feedback; the actor executes a ReAct loop of reasoning, tool retrieval, and invocation. Evaluation uses an LLM‑as‑judge protocol on 50 specialized scenarios, measuring answer quality, robustness, constraint adherence, and planning efficiency. High‑quality trajectories (1,170) are curated for fine‑tuning.

## Key Results
- ToolGym supplies 5,571 unified tools across 204 apps, a task engine generating long‑horizon workflows with wild constraints, and a state controller that injects failures to stress‑test robustness.
- All evaluated LLMs show a misalignment between strong planning (high Goal Decomposition scores) and weaker execution (low Success Rates), with constraint following as the primary failure mode; DeepSeek‑v3.2 achieves the best robustness (90.6% Recovery, 72.4% Flexibility).
- Fine‑tuning on only 1,170 ToolGym‑curated trajectories yields state‑of‑the‑art performance on external benchmarks, vastly outperforming models trained on 119k samples, highlighting the dataset’s quality and efficiency.

## Why This Works (Mechanism)
### Mechanism 1: Unified Tool Format (MCP) Enables Scalable Evaluation
**Claim:** Standardizing a large, diverse toolset into a unified invocation format (MCP) enables scalable, open‑world agent evaluation.  
**Mechanism:** Manual curation of 5,571 tools from 204 apps into a common schema abstracts away app‑specific implementation details, allowing an agent to reason over a single action space (“call tool X with args Y”) regardless of the underlying service.  
**Evidence anchors:** [abstract] “built on 5,571 format unified tools across 204 commonly used apps”; [section 2.1] details MCP‑based curation, validation, and retrieval index.  
**Break condition:** If the unified format cannot capture critical app‑specific semantics (e.g., stateful sessions, error codes), agent performance may degrade despite scale.

### Mechanism 2: Wild Constraints Reveal Planning‑Execution Misalignment
**Claim:** Synthesizing tasks with “wild constraints” and a reference sub‑goal graph forces agents into long‑horizon planning with meaningful dependencies, exposing the planning‑execution gap.  
**Mechanism:** The task engine samples semantically coherent tool candidates and uses an iterative LLM‑based prompt refinement loop to generate user queries with multiple interacting constraints (e.g., “use at least three services, verify output from two sources, prefer cheaper options”). The planner‑actor framework provides a gold sub‑goal graph for direct comparison.  
**Evidence anchors:** [abstract] “synthesizing long‑horizon, multi‑tool workflows with wild constraints” and “reveal the misalignment between tool planning and execution abilities”; [section 4.2] shows high Goal Decomposition but variable Success Rates.  
**Break condition:** If the constraint synthesis produces unsolvable or artificially convoluted tasks, the environment measures adversarial robustness rather than practical capability.

### Mechanism 3: Failure Injection Probes Real‑World Robustness
**Claim:** Injecting controlled, realistic failures via a state controller is necessary to measure and improve agent robustness in open‑world settings.  
**Mechanism:** The state controller acts as middleware intercepting tool execution to simulate API instabilities (timeouts, rate limits, session expiry) or evolving user constraints, requiring agents to detect failures, diagnose causes, and adapt plans.  
**Evidence anchors:** [abstract] “state controller that injects interruptions and failures to stress‑test robustness”; [section 2.4] categorizes interventions; [section 4.2] DeepSeek‑v3.2’s high Recovery (90.6%) and Flexibility (72.4%) show the controller successfully discriminates robustness.  
**Break condition:** If failures are too predictable or frequent, agents may over‑verify or loop, measuring cautiousness instead of adaptive robustness.

## Foundational Learning
- **Tool‑Using Agent Paradigm (ReAct)**  
  *Why needed:* The entire environment assumes an agent that interleaves reasoning (“thought”) with external action (“tool call”) in a loop. Understanding this cycle is prerequisite to interpreting trajectories and designing the planner‑actor separation.  
  *Quick check:* “Given an observation from a previous tool call, how would you generate the next ‘thought’ and ‘action’ to proceed toward a multi‑step goal?”

- **Long‑Horizon Task Decomposition**  
  *Why needed:* Tasks average 28.5 turns, requiring the planner to maintain and update a complex plan over many steps.  
  *Quick check:* “For a goal requiring data from three different apps, what intermediate sub‑goals would you create, and in what dependency order?”

- **Constraint Satisfaction in Open‑World Planning**  
  *Why needed:* The “wild constraints” (order, diversity, trade‑offs) are the primary differentiator from simpler benchmarks; constraint following is the dominant failure mode.  
  *Quick check:* “If a task requires ‘compare prices from two sites and buy the cheapest, but only use sites you haven’t used before,’ what logical constraints must your execution sequence satisfy?”

## Architecture Onboarding
**Component map:** Tool Universe (5,571 MCP‑standardized tools + FAISS index) -> Task Engine (synthesizes constrained tasks) -> State Controller (injects failures) -> Agent Framework (Planner decomposes into sub‑goal graph; Actor executes ReAct loop with tool retrieval) -> Evaluation Harness (LLM‑as‑judge scores trajectories).

**Critical path:** Tool retrieval from the universe → Planner initial task decomposition → Actor loop (Reason → Retrieve tools → Call tool → *State Controller interception* → Observation) → Planner verification feedback → Termination. The cycle repeats until all sub‑goals are marked complete.

**Design tradeoffs:**  
- *Scale vs. Realism:* 204 apps cover common workflows but miss niche enterprise systems; manual validation may not capture every edge case.  
- *Automated Synthesis vs. Ground Truth:* Fully automated task generation enables scale, but reference rationales are LLM‑generated approximations, not human‑verified gold plans.  
- *Failure Injection vs. Solvability:* The state controller adds realism but risks making tasks unsolvable if failures compound; the paper does not quantify failure‑induced unsolvability.

**Failure signatures:**  
- **High Tool Call Count + Low Completeness:** e.g., GPT‑4o‑mini (51.7 calls, 1.13 completeness) indicates looping or poor observation synthesis.  
- **Early Abandonment:** Model halts after few turns despite good initial planning, showing poor execution endurance.  
- **Constraint Violation:** Low scores on Order, Diversity, Format metrics even if final answer seems plausible.

**First 3 experiments:**  
1. **Tool Selection Accuracy:** For a given sub‑goal, measure if the Actor retrieves a tool from the true required set among top‑k results. Tests retrieval efficacy.  
2. **Constraint Violation Rate Under Stress:** Run tasks with State Controller active vs. control; compare constraint metrics (Order, Format). Isolates robustness impact.  
3. **Planner Intervention Frequency:** Log how often Planner feedback corrects the Actor’s sub‑goal or action choice. High frequency indicates Actor frequently off‑track, testing decomposition utility.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can we construct a large‑scale, diverse evaluation suite covering the full spectrum of ToolGym’s tools, apps, and constraints? The current 50‑scenario set is too small to cover all combinations, risking biased leaderboard results.  
- **Open Question 2:** How do sub‑10B language models perform in ToolGym, and does fine‑tuning on its trajectories yield similar data efficiency gains? The paper focuses on frontier/large models; smaller models’ capabilities and training response remain unknown.  
- **Open Question 3:** What modifications to agent design or training can close the planning‑execution performance gap? Without understanding the cause (e.g., weak grounding, insufficient interaction experience), systematic improvement is blocked.

## Limitations
- Task synthesis is fully automated with no human verification of solvability or constraint naturalness, risking artificial tasks.  
- State controller’s failure injection policies (triggers, probabilities, types) are undocumented, hindering replication and possibly biasing results.  
- MCP unification may discard app‑specific nuances (e.g., stateful sessions, error codes), limiting real‑world validity.

## Confidence
- **Claim:** Unified MCP format enables scalable evaluation. **Confidence: Medium** (scale shown, but causal necessity not isolated).  
- **Claim:** Wild constraints reveal planning‑execution misalignment. **Confidence: Medium–High** (consistent gap across models, but task naturalness untested).  
- **Claim:** State controller’s failure injection probes robustness. **Confidence: Medium** (DeepSeek’s high recovery suggests discrimination, but injection design may bias results).

## Next Checks
1. **Human task validation:** Sample 50–100 synthesized tasks; have humans rate solvability and constraint naturalness to certify benchmark realism.  
2. **Ablation of failure injections:** Run the same tasks varying injection categories (tool/state/constraint) and rates to measure each factor’s impact on recovery and flexibility.  
3. **Semantic coverage test:** For a subset of apps (e.g., 10), compare agent performance when using the native API spec directly vs. the MCP‑schema wrapper; any significant drop indicates loss of critical semantics.
