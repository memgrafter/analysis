# AILS-NTUA at SemEval-2026 Task 3: Efficient Dimensional Aspect-Based Sentiment Analysis

## Quick Facts
- **arXiv ID:** 2603.04933
- **Source URL:** https://arxiv.org/abs/2603.04933
- **Reference count:** 40
- **Primary result:** Parameter-efficient language-specific modeling (encoder fine-tuning, LoRA on ≤14B LLMs) consistently surpassed baselines in multilingual, multi-domain DimABSA, matching or exceeding 70B+ model performance.

## Executive Summary
AILS-NTUA tackled SemEval-2026 Task 3's multilingual, multi-domain Dimensional Aspect-Based Sentiment Analysis (DimABSA) with a specialized, parameter-efficient approach. For the regression subtask (DimASR), they fine-tuned language-appropriate transformer encoders per language-domain pair. For extraction subtasks (DimASTE/DimASQP), they employed LoRA-based instruction tuning of medium-sized LLMs (≤14B parameters) to generate structured JSON outputs. This design yielded strong improvements over baselines on all metrics—significant RMSE reduction in DimASR and higher continuous F1 (cF1) in extraction—while maintaining computational efficiency. The work underscores the value of per-language specialization and structured generation for precise, fine-grained sentiment analysis.

## Method Summary
The system separates the three subtasks into two pipelines. DimASR (valence-arousal regression) uses a language-specific encoder (e.g., DeBERTa for English, XLM-R for low-resource languages) fine-tuned on flattened (review, aspect) pairs. The pooled encoder output feeds two regression heads, trained with a combined loss of weighted MSE, Concordance Correlation Coefficient (CCC), and a V-A-guided triplet regularizer to shape the affect space. For DimASTE and DimASQP (triplet/quadruplet extraction), medium-sized instruction-tuned LLMs (Llama 3.1 8B or Qwen 2.5 7B/14B) are adapted via LoRA (rank 16, alpha 32). The task is cast as constrained JSON generation using language-specific prompts that include explicit formatting rules and domain-specific category lists (for ASQP). Training uses 4-bit quantization, 1 epoch, and a small effective batch size. Inference involves greedy decoding and parsing the JSON output.

## Key Results
- DimASR regression dramatically improved RMSE (e.g., English Restaurant: 0.92 vs. 2.15 baseline).
- DimASTE/DimASQP extraction achieved higher cF1 (e.g., English Restaurant: 0.77 vs. 0.45 baseline).
- Parameter-efficient ≤14B models competed effectively with fully fine-tuned 70B–120B variants.
- Performance was generally higher for valence than arousal; low-resource and NULL-heavy datasets showed instability and larger errors.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Language-specific transformer encoder fine-tuning achieves superior performance on DimASR compared to large LLMs and baselines.
- **Mechanism:** For each language, a monolingual pretrained encoder (e.g., DeBERTa, RoBERTa, XLM-R) is fine-tuned on flattened (review, aspect) pairs with input formatted as "Aspect: a. Sentence: x." The encoder's output is pooled via attention, then passed to two regression heads to predict valence and arousal. The loss combines MSE, CCC, and a triplet regularizer that minimizes the distance between representations of close VA pairs while pushing apart far ones within a minibatch. This per-language-domain training isolates domain-specific vocabulary and aspect distributions.
- **Core assumption:** Continuous VA scores are well modeled by the semantic representations of monolingual encoders when explicitly conditioned on the aspect, and the triplet loss improves metric learning of the affect space.
- **Evidence anchors:** 
  - [abstract] "fine-tuning of language-appropriate encoder backbones for continuous aspect-level sentiment prediction"
  - [section 4.1] Details of backbone selection, regression head, pooling, and loss functions.
  - [corpus] The QuadAI system (arxiv:2603.07766) also uses a RoBERTa encoder for regression, supporting encoder viability for this task.
- **Break condition:** Degrades if the pretrained encoder has insufficient language coverage (e.g., Tatar) or training data is extremely small. Arousal consistently shows lower PCC, indicating it is intrinsically harder to model from text.

### Mechanism 2
- **Claim:** LoRA-based instruction tuning of medium-sized LLMs (≤14B) on JSON generation yields structured extraction performance competitive with fully fine-tuned 70B+ LLMs.
- **Mechanism:** DimASTE/DimASQP is cast as constrained JSON generation. Language-specific prompt templates with explicit rules (exact span copying, NULL handling, numeric range) are used with the LLM's chat template. LoRA (r=16, α=32) adapts q/k/v/o_proj and gate/up/down_proj layers while keeping the base model frozen. Training is on the training JSON for 1 epoch. During inference, the JSON list is generated and parsed; V-A values are split into separate keys to simplify formatting.
- **Core assumption:** LLMs can be taught via instruction tuning to produce well-formed JSON that exactly matches aspect/opinion spans, and LoRA adapts them efficiently with few trainable parameters.
- **Evidence anchors:**
  - [abstract] "language-specific instruction tuning of large language models using LoRA for structured triplet and quadruplet extraction."
  - [section 4.2] Prompt templates, LoRA configuration, and quantization details.
  - [corpus] The nchellwig system (arxiv:2603.01788) also uses LoRA-adapted LLMs for DimABSA, corroborating parameter-efficient tuning.
- **Break condition:** Performance drops in low-resource languages due to limited pretraining. Exact-match evaluation penalizes any paraphrasing or formatting errors, which increase with task complexity (e.g., adding categories in DimASQP). NULL-heavy training sets can bias the model to overpredict NULL.

### Mechanism 3
- **Claim:** Training separate models (or LoRA adapters) per language-domain combination yields strong specialization and avoids cross-lingual noise, despite management overhead.
- **Mechanism:** For each (language, domain) pair, independently train a DimASR encoder or DimASTE/DimASQP LoRA adapter. No weight sharing across languages or domains. Isolates domain-specific vocabulary and aspect distributions. For languages without dedicated encoders, default to XLM-R; for those with strong pretrained models, use them. A translation experiment (translate to English, train, back-map) underperformed direct training, indicating cross-lingual transfer via translation introduces noise.
- **Core assumption:** Language and domain boundaries create distinct data distributions best captured by separate models; cross-lingual or cross-domain transfer would require careful adaptation and risks lexical/semantic gaps.
- **Evidence anchors:**
  - [abstract] "unified yet task-adaptive design emphasizes parameter-efficient specialization across languages and domains"
  - [section 5.4] Translation-based training leads to performance drop compared to direct training, and pre-trained English model underperforms on non-Chinese languages.
  - [corpus] Neighboring systems (e.g., LogSigma, QuadAI) also report per-language results, indirectly supporting specialization.
- **Break condition:** Not scalable to many languages/domains due to storage and maintenance. In extremely low-resource settings (e.g., Tatar), separate models may overfit; cross-lingual transfer could be beneficial if properly regularized.

## Foundational Learning
- **Concept:** Dimensional Sentiment Representation (Valence-Arousal)  
  - **Why needed here:** The task uses continuous VA scores (1.00–9.00) instead of discrete polarity, requiring regression models and evaluation via RMSE/PCC. Models must predict fine-grained affect intensities.  
  - **Quick check:** Valence ranges from negative to positive affect; arousal indicates intensity/activation. Why is arousal often harder to predict from text alone?

- **Concept:** Parameter-Efficient Fine-Tuning (LoRA)  
  - **Why needed here:** Fully fine-tuning large LLMs is computationally expensive; LoRA trains low-rank adapters, making per-language/domain adaptation feasible with limited resources.  
  - **Quick check:** LoRA decomposes weight updates into low-rank matrices. How does this reduce trainable parameters, and which layers are typically targeted?

- **Concept:** Structured Generation as JSON  
  - **Why needed here:** Extraction tasks require exact lists of tuples with spans and numeric values; prompting for JSON enforces schema and simplifies parsing.  
  - **Quick check:** Why is exact-match evaluation stringent, and how might minor formatting deviations or paraphrased spans cause penalization?

- **Concept:** Metric Learning with Triplet Loss  
  - **Why needed here:** The triplet regularizer in DimASR shapes the representation space so that samples with similar VA scores are closer, improving regression generalization.  
  - **Quick check:** In a triplet (anchor, positive, negative), what distance metric is typically used, and what does the margin control?

- **Concept:** Cross-Lingual Transfer vs. Specialization  
  - **Why needed here:** The paper compares separate per-language models against translation-based transfer, informing scalable multilingual system design.  
  - **Quick check:** What are common pitfalls of translation-based transfer for sentiment analysis (e.g., cultural nuances, aspect expressions)?

## Architecture Onboarding
- **Component map:**  
  DimASR: Input (Review, Aspect) → Language-specific Encoder → Attention Pooling → Two Regression Heads (Valence, Arousal)  
  DimASTE/DimASQP: Review + Prompt → LLM (with LoRA adapters) → JSON String → Parse → Structured Output (Triplet/Quadruplet)
- **Critical path for adding a new language-domain:**  
  1. Choose appropriate encoder (e.g., DeBERTa, RoBERTa, XLM-R) or LLM backbone (e.g., Qwen 2.5 14B for broad coverage).  
  2. Create language-specific prompt template (translate rules, include domain-specific category list for ASQP).  
  3. Fine-tune encoder (DimASR) or LLM with LoRA (DimASTE/DimASQP) on the training set.  
  4. Validate on development set; monitor RMSE (DimASR) or cF1 (extraction).  
  5. Diagnose issues: NULL bias, formatting errors, data size limitations.
- **Design tradeoffs:**  
  - Separate vs. unified models: Separate per language/domain gives specialization but multiplies checkpoints; a single multilingual model could exploit transfer but risks cross-lingual noise (as shown by translation experiments).  
  - Encoder vs. LLM: Encoders are efficient and robust for regression but cannot handle structured extraction; LLMs with LoRA cover both but require careful prompt engineering and have slower inference.  
  - Exact-match vs. fuzzy: cF1 demands exact substring matches; this encourages verbatim copying but penalizes semantically equivalent paraphrases or minor JSON format deviations.
- **Failure signatures:**  
  - DimASR: Very high RMSE (>2.0) on low-resource languages (Tatar, Ukrainian) correlates with small training size and weaker pretrained encoders. Arousal PCC significantly lower than valence suggests models struggle with intensity cues.  
  - Extraction: Large Dev-Test cF1 gap indicates distribution shift (review length, tuple density); high NULL rate in training (e.g., English Laptop) leads to overprediction of NULL. Formatting errors (invalid JSON) cause complete parsing failure.  
  - General: Strong performance on high-resource languages but poor on low-resource ones without transfer attempts suggests specialization alone is insufficient for data-scarce settings.
- **First 3 experiments:**  
  1. **Baseline reproduction:** Run the provided Kimi K2 Thinking and Qwen 3 14B baselines on a subset (e.g., English Restaurant) to establish reference performance and verify evaluation scripts.  
  2. **Loss component ablation for DimASR:** Remove the triplet regularizer (β=0) and compare RMSE/CCC to the full loss; this isolates the contribution of metric learning to regression accuracy.  
  3. **Prompt variation for extraction:** For DimASTE, compare prompts with and without explicit "Use 'NULL' only if..." instruction; measure impact on NULL overprediction and cF1, especially for NULL-heavy datasets like English Laptop.

## Open Questions the Paper Calls Out
- **Open Question 1:** Can a unified multilingual model match language-specific performance in DimABSA?  
  - **Basis in paper:** [explicit] The authors state in the Limitations: "we train separate models... does not directly exploit cross-lingual or cross-domain transfer."  
  - **Why unresolved:** The paper only evaluates language-specific fine-tuning; attempts at translation-based transfer led to performance degradation, leaving unified modeling uninvestigated.  
  - **What evidence would resolve it:** Train a single multilingual encoder (e.g., XLM-R) on all language-domain pairs, evaluate zero-shot and few-shot cross-lingual performance, and compare to the per-language baselines.

- **Open Question 2:** How can we eliminate format errors and paraphrased spans in LLM-generated outputs for structured DimABSA under exact-match evaluation?  
  - **Basis in paper:** [explicit] The Limitations note: "generation can still produce format errors and paraphrased spans, which are heavily penalized by cF1."  
  - **Why unresolved:** Prompt engineering reduced but did not remove these errors; alternative decoding constraints, loss functions, or training regimes were not explored.  
  - **What evidence would resolve it:** Compare constrained decoding (e.g., grammar-guided generation), reinforcement learning with span-matching rewards, or auxiliary losses enforcing exact substring copying, using the same evaluation.

- **Open Question 3:** What data augmentation or transfer learning strategies can improve stability and reduce variance for low-resource languages in DimABSA?  
  - **Basis in paper:** [explicit] The Results and Observations state: "performance is less stable in low-resource settings" and the Limitation cites small dev sets and distribution shifts.  
  - **Why unresolved:** The paper uses standard fine-tuning without augmentation techniques for low-resource languages; thus the potential for stability improvements remains unknown.  
  - **What evidence would resolve it:** Apply techniques like back-translation, synthetic data generation via LLMs, or meta-learning to low-resource language splits and measure changes in variance and cF1 on dev/test sets.

## Limitations
- **Triplet loss opacity:** Exact sampling strategy (distance metric, margin thresholds) for the V-A-guided triplet loss is unreported, limiting reproducibility and theoretical understanding.
- **Low-resource prompt fidelity:** Appendix prompt templates for Tatar/Ukrainian contain non-ASCII characters with potential rendering issues; domain-specific category lists for DimASQP are not provided, risking implementation drift.
- **Evaluation brittleness:** cF1's exact-match requirement may penalize semantically correct but lexically varied outputs; Dev-Test distribution shifts (e.g., review length) could inflate performance gaps.

## Confidence
- **Claim 1 (Encoder fine-tuning superiority):** Medium-High. Strong empirical gains vs. baselines are clear, but triplet loss's specific contribution is unknown.
- **Claim 2 (LoRA instruction-tuning efficacy):** Medium-High. Competitive with 70B+ models is supported, but prompt engineering for low-resource languages is a key risk.
- **Claim 3 (Specialization over transfer):** Medium. Translation experiment evidence is solid, but generalizability beyond tested languages is uncertain.

## Next Checks
1. **Triplet loss ablation:** Re-train a DimASR model with β=0 (no triplet regularization) on English Restaurant; report ΔRMSE/CCC to quantify its impact.
2. **Prompt/category verification:** For Tatar and Ukrainian, clean and normalize the prompt templates from Appendix F; extract and validate domain-specific category lists from training data for DimASQP.
3. **Dev-Test shift & NULL bias analysis:** Compute feature distribution PSI (length, tuple density) between Dev/Test; for NULL-heavy datasets (e.g., English Laptop), measure precision/recall for NULL vs. non-NULL tuples to diagnose overprediction.
