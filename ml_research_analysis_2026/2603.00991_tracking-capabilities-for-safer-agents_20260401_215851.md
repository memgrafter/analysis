# Tracking Capabilities for Safer Agents

## Quick Facts
- arXiv ID: 2603.00991
- Source URL: https://arxiv.org/abs/2603.00991
- Reference count: 40
- Primary result: A Scala 3-based safety harness with static capability tracking prevents 100% of tested information leakage and malicious side-effects while maintaining comparable utility across benchmarks.

## Executive Summary
AI agents that invoke tools risk leaking private data or causing unintended side effects, especially under prompt injection attacks. This paper introduces a "safety harness" that replaces direct tool calls with code generation in Scala 3. The harness leverages Scala 3's capture checker to statically track capabilities (e.g., file handles, network access) in types, ensuring that generated code can only use resources within its granted budget. Sensitive data is wrapped in a `Classified` type, which restricts processing to pure functions that cannot perform side effects, thereby preventing exfiltration. Capabilities are scoped to blocks to enforce lifetime safety and prevent smuggling. In evaluations on multiple models and benchmarks (τ²-bench, SWE-bench), the approach achieved 100% prevention of leakage and malicious side-effects in adversarial settings, while utility remained on par with conventional tool-calling baselines (e.g., 99.2% vs 83.3% for Claude Sonnet 4.6 under injection). The safety guarantees are compile-time and model-independent, offering a robust foundation for safer agent deployment.

## Method Summary
The authors build an MCP server dubbed "tacit" that mediates agent actions. Instead of calling tools directly, the agent generates Scala 3 code snippets using a provided typed API (the capability library). The server compiles each snippet with Scala 3's capture checker in safe mode (`language.experimental.safe`), which enforces that all effects requiring capabilities are declared in the type system. The capability library defines resource-specific capabilities (e.g., `FileSystem`, `Network`) and a `Classified[T]` wrapper that only accepts pure functions in its `map` operation. Access to real-world resources is granted within scoped blocks (e.g., `requestFileSystem`), guaranteeing that capabilities cannot escape. The compiled code runs in a REPL with the library preloaded; if compilation fails, the agent reads the errors and retries. This design shifts safety checks from runtime to compile time, providing static guarantees irrespective of the LLM's alignment.

## Key Results
- 100% of tested information leakage and malicious side-effect attacks were prevented, including sophisticated prompt injections.
- Task utility was comparable to conventional tool-calling baselines; e.g., Claude Sonnet 4.6 achieved 99.2% success under injection versus 83.3% for the baseline.
- The approach yields model-independent, compile-time safety guarantees through Scala 3's type system.

## Why This Works (Mechanism)
### Static Capability Tracking
Capabilities are ordinary objects extending `Capability`. Scala 3's capture checker records which capabilities a value can access (its capture set) and enforces that functions only use declared capabilities; this check occurs at compile time. The core assumption is that the type system correctly and completely tracks all effects requiring capabilities, and code is compiled in safe mode (disabling unsafe features). Evidence: the abstract emphasizes static tracking; Section 2 introduces capture checking and shows types like `FileEntry^{this}`; the corpus notes that prior solutions rely on runtime checks. A break condition would be if the agent uses reflection, casts, or if the capability library itself contains untracked side effects.

### Local Purity for Information Flow Control
Sensitive data is wrapped in `Classified[T]`. Its `map` method requires a pure function `T -> U`, which has an empty capture set and cannot perform I/O, network access, or any side effect. This forces all operations on classified data to be non-leaking. The core assumption is that the type system correctly identifies pure functions and the `Classified` wrapper is not bypassed. Evidence: the abstract mentions local purity; Section 3.1 defines `Classified` and its purity constraint; the corpus highlights that existing leakage mitigations use runtime monitoring, making static purity novel. A break condition could be covert channels (e.g., timing) or circumventing `Classified` via casts.

### Scoped Capabilities for Lifetime Control
Functions like `requestFileSystem` take a block that receives a capability. The type system ensures the block’s return type does not depend on the capability, preventing it from being returned or stored outside. Capture checking rejects any attempt to leak the capability, thereby preventing use after deallocation and capability smuggling. The core assumption is that capture inference works correctly and the scoping pattern is consistently applied. Evidence: the abstract notes fine-grained control; Section 2 and 3.4 demonstrate scoping; prior runtime approaches do not track lifetimes. A break condition would be a capability retained via a closure that evades capture checking or unsafe constructs in the library.

## Foundational Learning
- **Capability-based security**: In the object-capability model, a function gains authority to read a file only by being passed a file capability as a parameter or accessing a global capability object. This is needed because the safety harness mediates all resource access via unforgeable capability objects, preventing unauthorized access. Quick check: How does a function gain authority to read a file? (Answer: By receiving a file capability.)
- **Capture checking in Scala 3**: Capture checking is a type system feature that tracks which capabilities a value can access, enabling static enforcement of capability safety and local purity. It is essential to ensure that generated code only uses granted capabilities and remains pure when handling classified data. Quick check: What does the type `FileEntry^{this}` indicate? (Answer: The file entry captures the file system capability `this`.)
- **Local purity**: A function is locally pure if it has an empty capture set, meaning it performs no side effects. This property is required to guarantee that processing of `Classified` data cannot leak information via I/O or other effects. In Scala 3, pure function types (`T -> U`) are enforced by the `Classified.map` method. Quick check: What is the type of a pure function in Scala 3 with capture checking? (Answer: It has an empty capture set, e.g., `String -> Unit`.)

## Architecture Onboarding
### Component Map
Untrusted Agent -> MCP Server (tacit) -> Capability Library -> Real World Resources

### Critical Path
A typical file-read operation proceeds as follows: 1) The agent generates a Scala snippet such as `requestFileSystem("/data") { fs => access("file.txt").read() }`. 2) The snippet is sent to the MCP server via the `execute_scala` tool. 3) The Scala 3 compiler checks that `requestFileSystem` requires an implicit `IOCapability`, that the block returns a pure `String`, and that the `fs` capability does not escape. 4) If compilation succeeds, the REPL executes: `requestFileSystem` creates a `FileSystem` for `/data`; `access("file.txt")` yields a `FileEntry^{fs}`; `read()` returns the file content; the `FileSystem` and `FileEntry` are invalidated after the block. 5) The file content is returned to the agent.

### Design Tradeoffs
- **Safety vs Expressiveness**: The type system restricts code, but benchmarks show agents remain productive; tasks heavy in shell operations may be less natural.
- **Static vs Dynamic**: Compile-time checks provide zero runtime overhead and strong guarantees, but require the agent to generate well-typed Scala 3 code, which may need careful prompting.
- **Model Independence**: Safety does not rely on model alignment, only on the compiler; however, code-generation success still depends on the LLM's ability to produce compilable Scala.
- **Implementation Cost**: Building the capability library demands expertise in Scala 3 capture checking; it is a one-time investment per domain but reusable.

### Failure Signatures
- **Compilation errors**: Type mismatches (e.g., `FileEntry^{contextual$1} required: FileEntry`), capability leakage (e.g., “capability cannot flow into capture set {}”), or null-handling issues.
- **Runtime security exceptions**: `SecurityException` when attempting to access paths outside the allowed root or improperly using classified data.
- **Agent recovery**: The agent reads compiler error messages and automatically retries, as demonstrated in the experiments.

### First Experiments
1. **Safety benchmark**: Run the agent with prompt injections in both classified and unclassified modes. Expect 100% security in classified mode and high utility.
2. **τ²-bench**: Compare the capability-safe agent against a tool-calling baseline on customer service tasks. Anticipate comparable or slightly better utility.
3. **SWE-bench Lite**: Evaluate software bug-fixing performance. Expect results comparable to baselines, with possible minor drop due to shell operation limitations.

## Open Questions the Paper Calls Out
### Formal soundness of safe mode
The paper notes that, unlike RustBelt for Rust, no formal proof exists for Scala 3's safe mode. Without mechanized soundness, users must rely on informal confidence. Resolving this would require a proof (e.g., in Coq or Isabelle) that well-typed programs cannot leak capabilities or violate purity.

### Transfer to other mainstream languages
Scala 3 is currently the only production-ready language with static capability tracking. Extending this approach to more widely used languages (e.g., Java, Python, TypeScript) is nontrivial and unexplored. Evidence to resolve this would be a prototype in another language demonstrating that LLMs can generate safe code with minimal performance impact.

### Multi-agent scalability
The capability model conceptually extends to hierarchical delegation, but a thorough evaluation in multi-agent settings is missing. Outstanding issues include coordination overhead, expressiveness for delegation, and potential hierarchical leaks. A full evaluation would require an experimental framework with multiple agents generating capability-safe code and analyzing patterns.

### Side-channel vulnerabilities
The approach explicitly excludes covert channels such as timing or termination. These could leak classified information (e.g., by varying execution time based on secret data). Mitigating side channels would require additional mechanisms (e.g., constant-time checks, resource accounting), followed by empirical assessment of utility and security trade-offs.

## Limitations
- The full `tacit` MCP server and capability library source are not released, hindering assessment of implementation fidelity and possibly missing invariants.
- Evaluation relies on a limited set of adversarial prompts and benchmarks; robustness against a broader attack surface (covert channels, reflection) is unproven.
- Agents must generate syntactically and type-correct Scala 3 code, which may be brittle across models and tasks, and the exact safe mode boundary (allowed stdlib features) is unspecified, creating potential security gaps.
