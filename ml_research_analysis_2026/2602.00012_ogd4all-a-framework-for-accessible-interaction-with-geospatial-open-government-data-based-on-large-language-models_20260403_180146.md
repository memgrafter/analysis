# OGD4All: A Framework for Accessible Interaction with Geospatial Open Government Data Based on Large Language Models

## Quick Facts
- **arXiv ID:** 2602.00012  
- **Source URL:** https://arxiv.org/abs/2602.00012  
- **Reference Count:** 30  
- **Primary Result:** A two-stage pipeline combining semantic dataset retrieval with secure iterative code generation achieves 98% analytical correctness and 94% recall on a Zurich OGD benchmark while reliably rejecting unanswerable queries.

## Executive Summary
OGD4All is a framework designed to allow citizens to intuitively query complex geospatial Open Government Data using natural language. It addresses the dual challenges of accurately identifying relevant datasets from a large catalog and generating correct, executable analysis code to produce verifiable multimodal outputs (e.g., maps, plots). The system employs a semantic retrieval stage with LLM-driven query reformulation to match questions to dataset metadata, followed by an agentic coding loop that iteratively writes and executes Python in a secure sandbox. Evaluated on a curated 199-question benchmark across 430 Zurich datasets, the framework demonstrates high correctness and recall while minimizing hallucinations through a robust rejection mechanism for unsupported queries. Expert feedback highlights a key trade-off: the superior performance of proprietary LLMs conflicts with public sector data sovereignty imperatives.

## Method Summary
OGD4All implements a two-stage pipeline without model fine-tuning. **Stage 1: Dataset Retrieval** uses semantic vector search over dataset metadata (embedded with OpenAI’s `text-embedding-3-large`). An LLM reformulates user questions into up to three German subqueries (matching metadata language), performs nearest-neighbor search, and selects relevant datasets or rejects the query if none are found. **Stage 2: Dataset Analysis** loads selected datasets into a persistent Python notebook. A coding agent (orchestrated by LangGraph) follows a plan-generate-execute-observe cycle, running code in a sandboxed environment (HuggingFace `smolagents` or E2B microVMs) until a final answer is produced. The system is evaluated on a 199-question benchmark (169 answerable, 30 unanswerable) using LLM-as-a-judge correctness scoring, recall metrics, and operational logs.

## Key Results
- Achieves **98% analytical correctness** on answerable questions when using GPT-4.1, with high recall (**94%**) of relevant datasets.
- **Reliably rejects unanswerable questions**, minimizing hallucinations; retrieval stage prevents analysis on unsupported queries.
- **Trade-off identified**: Proprietary models (GPT-4.1) outperform open-weight models (60–69% correctness) but raise data sovereignty concerns for public deployment.

## Why This Works (Mechanism)

### Mechanism 1: Semantic Retrieval with Answerability Rejection
- **Claim:** OGD4All accurately retrieves relevant datasets for a citizen’s question while reliably rejecting questions with no supporting data, thereby preventing hallucinations.
- **Mechanism:** Semantic vector search over dataset metadata, augmented by LLM-driven query reformulation (up to three subqueries). The LLM interprets the question, generates reformulations in German (due to German metadata), issues nearest-neighbor searches, and outputs a structured list of datasets or a rejection.
- **Core assumption:** Questions and metadata embeddings share a semantic space where similarity indicates relevance, and the LLM can correctly determine answerability based on retrieval results.
- **Evidence anchors:**  
  - [abstract]: “combines semantic dataset retrieval with … reliably rejecting questions unsupported by available data, which minimizes hallucination risks.”  
  - [section III.A]: “A semantic retrieval strategy embeds both metadata and queries into a dense vector space… The system prompt… instructs the model to perform reformulated queries in German… The capability to integrate textual and visual cues…”  
  - [corpus]: Weak; neighboring works like GeoVisA11y focus on multimodal QA but do not describe explicit rejection mechanisms for unanswerable queries.
- **Break condition:** The mechanism fails when embeddings do not capture specialized terminology (e.g., local slang) or when the LLM misjudges answerability, leading to false positives (retrieving irrelevant datasets) or false negatives (rejecting answerable questions).

### Mechanism 2: Iterative Code Generation with Error Recovery
- **Claim:** OGD4All can generate correct Python code to process geospatial datasets and produce multimodal outputs, achieving high analytical correctness.
- **Mechanism:** An LLM acts as a coding agent in a persistent Python notebook. It iteratively plans, generates code, executes it in a sandbox, observes output, and recovers from errors by re-generation until a final answer tool is called or a step limit (20) is reached.
- **Core assumption:** LLMs can produce valid analysis code for data tasks when provided context and error feedback; the iterative loop compensates for initial mistakes.
- **Evidence anchors:**  
  - [abstract]: “agentic reasoning for iterative code generation… OGD4All reaches 98% analytical correctness.”  
  - [section III.B]: “The coding agent can recover from errors, as in such cases, the error message is provided to it, and it is instructed to generate a corrected code snippet… The cycle ends when the LLM agent decides to call the final answer tool.”  
  - [corpus]: Neighboring works (e.g., GeoGPT, UrbanLLM) explore code generation for geospatial tasks, but OGD4All emphasizes auditable traces and multimodal outputs; the corpus lacks direct evaluation of iterative error recovery.
- **Break condition:** The agent fails if it cannot fix code within the iteration limit or if a flawed plan propagates errors; limitations in LLM code generation for complex GIS operations can further reduce correctness.

### Mechanism 3: Secure Sandboxed Execution
- **Claim:** OGD4All executes untrusted LLM-generated code safely, preventing system compromise while producing verifiable multimodal results (maps, plots, tables).
- **Mechanism:** Integration of HuggingFace’s smolagents, a local Python interpreter that disables additional imports, caps elementary operations, and prevents undefined operations. For stronger security, remote microVM sandboxes (E2B) are supported. All code and outputs are logged for audit.
- **Core assumption:** Sandbox restrictions are sufficient to contain any malicious or erroneous code, and the operation cap prevents resource exhaustion.
- **Evidence anchors:**  
  - [abstract]: “secure sandboxed execution that produces verifiable multimodal outputs.”  
  - [section III.B]: “OGD4All relies on a custom secure-by-design execution layer, namely HuggingFace’s sandbox Python interpreter smolagents. This interpreter disables additional imports and access to submodules, caps the total count of elementary operations to prevent infinite loops and resource bloating, and prevents undefined operations.”  
  - [corpus]: Corpus indicates interest in accessible geospatial AI (e.g., PyGALAX, ChatGeoAI), but security via sandboxing is rarely highlighted; OGD4All explicitly addresses this for public deployment.
- **Break condition:** The sandbox could be breached if the LLM discovers an implementation flaw or circumvents the operation cap; overly restrictive settings might also block legitimate geospatial libraries, causing analysis failures.

## Architecture Onboarding
- **Component map:**  
  User Interface -> Retrieval Module (Metadata DB, Embedding Model, Vector Search, LLM) -> Analysis Agent (LangGraph, LLM, Persistent Notebook) -> Execution Sandbox (smolagents/E2B)  
  Logging & Audit (parallel to all stages) & Benchmarking Suite (external evaluator)

- **Critical path:**  
  1. Citizen submits a multimodal question.  
  2. Retrieval: LLM reformulates question, performs vector search, selects relevant datasets; if none, returns rejection and stops.  
  3. For each selected dataset, load into the analysis agent’s notebook context.  
  4. Analysis agent iterates: plan step → generate Python code → execute in sandbox → observe output → decide next step or finalize.  
  5. On final answer, system presents multimodal results (text, map, plot, table) and logs all steps.  
  6. Follow-up questions may trigger additional retrieval or direct analysis.

- **Design tradeoffs:**  
  - *Proprietary vs. open LLMs:* Frontier models (GPT-4.1) give higher correctness (98%) and recall but raise data sovereignty issues; open models (Mistral, Llama) cost less and preserve sovereignty but achieve 60–70% correctness.  
  - *Cost vs. performance:* GPT-4.1-mini offers 91.7% correctness at 15× lower cost; reasoning models (GPT-o1, GPT-5) incur higher latency and token consumption.  
  - *Security vs. functionality:* Stricter sandbox (capped ops, disabled imports) increases safety but may block needed geospatial libraries; smolagents whitelists common data science packages.  
  - *Retrieval recall vs. precision:* High recall (94%) ensures relevant datasets are found but may include false positives; LLM selection after search balances this.  
  - *Multimodal complexity:* Supporting images/PDFs increases token usage and latency but improves usability.

- **Failure signatures:**  
  - *Retrieval:* Recall below 90% on benchmark, high false rejection rate on answerable questions, or frequent LLM refusal due to misunderstood answerability.  
  - *Analysis:* Correctness below 90%, many code generation errors, failure to complete within 20 steps, or outputs that diverge from ground truth even when code runs.  
  - *Sandbox:* Errors indicating disallowed operations, resource exhaustion (timeouts, memory), or suspected security escapes.  
  - *Overall:* Expert concerns that incorrect information erodes trust; system must avoid hallucinations by grounding every output in executed, verified code.

- **First 3 experiments:**  
  1. Baseline retrieval test: Run the 169 answerable benchmark questions through retrieval only (with ground-truth datasets provided). Compute recall and precision; verify retrieval of all required datasets for ≥90% of questions with ≤5% false positives.  
  2. End-to-end correctness: For a random sample of 20 benchmark questions, execute the full pipeline (retrieval + analysis). Compare final answers to ground truth via LLM-as-a-judge; target ≥95% correctness with GPT-4.1.  
  3. Rejection validation: Submit the 30 unanswerable benchmark questions. Confirm system rejects all (answerability accuracy 100%) and does not attempt analysis; monitor for any hallucinated outputs.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the quality of multimodal outputs (maps, plots) generated by OGD4All be automatically evaluated alongside textual correctness?
- **Basis in paper:** [explicit] The benchmark only grades textual outputs, omitting quantitative assessment of visualizations, though experts noted their high value for citizens.
- **Why unresolved:** Current evaluation lacks metrics for geospatial visual accuracy and usability, limiting holistic performance assessment.
- **What evidence would resolve it:** Development of automated metrics (e.g., spatial accuracy, perceptual clarity) or large-scale user studies comparing generated visuals to ground-truth references.

### Open Question 2
- **Question:** How does OGD4All handle geographically ambiguous or underspecified user queries (e.g., “downtown areas”) without predetermined answers?
- **Basis in paper:** [explicit] Authors note the benchmark avoided ambiguous questions and cite Mai et al. on ambiguity as a common geospatial issue; system behavior for such queries remains unevaluated.
- **Why unresolved:** Real-world citizen queries often lack precision; robustness to ambiguity is critical for trust but untested.
- **What evidence would resolve it:** Systematic testing with ambiguous query datasets, measuring consistency, user clarification strategies, or multi-interpretation handling.

### Open Question 3
- **Question:** Can open-weight, sovereign LLMs achieve comparable analytical correctness to proprietary models like GPT-4.1 in geospatial OGD tasks?
- **Basis in paper:** [explicit] Municipal experts highlighted a dilemma: proprietary models perform best but conflict with public data sovereignty; authors call for developing sovereign models.
- **Why unresolved:** Current open-weight models (e.g., Llama 4 Maverick) show large correctness gaps (60–69% vs. 98%); closed models’ architectures/training are opaque.
- **What evidence would resolve it:** Benchmarking future open models on OGD4All’s suite; analyzing whether sovereignty-focused fine-tuning or architectures can close the gap.

### Open Question 4
- **Question:** Does augmenting the benchmark with domain-expert curated knowledge (e.g., local context, nuanced rules) improve its discriminability for frontier LLMs?
- **Basis in paper:** [explicit] Authors suggest increasing benchmark complexity by adding expert knowledge, as current 98% correctness indicates saturation for short tasks.
- **Why unresolved:** Saturation limits ability to distinguish model capabilities on harder, realistic citizen questions requiring deeper domain insight.
- **What evidence would resolve it:** Creating and integrating a supplementary set of expert-validated, complex questions; re-evaluating model performance spread.

### Open Question 5
- **Question:** How can OGD4All’s retrieval mechanism be optimized to reduce subquery count (e.g., from ~2.25 per question) without sacrificing recall or answerability?
- **Basis in paper:** [inferred] Results show GPT-4.1 uses more subqueries than others, implying a strategy trade-off; the default max of 3 is arbitrary and not tuned for efficiency.
- **Why unresolved:** More subqueries increase token cost and latency; optimal query reformulation for varied metadata structures is unexplored.
- **What evidence would resolve it:** Ablation studies varying subquery limits or strategies; analyzing correlation between query complexity, metadata characteristics, and retrieval success.

## Limitations
- Generalizability beyond Zurich’s 430 curated datasets and German/English metadata is unproven.
- Full audit trail transparency (exact system prompts, few-shot examples, sandbox config) is not publicly available.
- LLM-as-judge reliability for correctness; agreement with human experts is unreported.

## Confidence
- **Semantic retrieval & rejection (98% correctness, 94% recall):** Medium-High. Strong benchmark results, but evidence for robustness to out-of-distribution terminology is weak.
- **Iterative code generation (analytical correctness):** Medium. High scores rely on frontier LLMs; performance drop with open models is significant (60–70%). Error-recovery claims lack independent replication.
- **Secure sandboxing:** Medium. Design is well-specified, but real-world adversarial testing and sandbox escape attempts are not documented.
