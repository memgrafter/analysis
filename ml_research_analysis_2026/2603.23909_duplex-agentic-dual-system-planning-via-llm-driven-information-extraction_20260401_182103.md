# DUPLEX: Agentic Dual-System Planning via LLM-Driven Information Extraction

## Quick Facts
- **arXiv ID:** 2603.23909
- **Source URL:** https://arxiv.org/abs/2603.23909
- **Reference count:** 30
- **Primary result:** DUPLEX achieves 97.5% average success rate on IPC benchmarks (vs. LLM+P’s 71.9%) and 83.5% on household tasks (vs. LLM+P’s 20.0%).

## Executive Summary
DUPLEX introduces a dual-system neuro-symbolic architecture to overcome LLM unreliability in long-horizon robotic planning. It strictly confines LLMs to schema-guided information extraction from natural language, with a deterministic script mapping the extracted structured data to syntactically correct PDDL. A symbolic planner (Fast Downward) solves the problem; a high-capacity “Slow System” activates only on failure, using planner diagnostics to iteratively repair the problem PDDL. Evaluated on 12 classical and household domains, DUPLEX dramatically outperforms prior LLM-based planning approaches, demonstrating that isolating LLMs from logical synthesis while leveraging symbolic planners maximizes reliability.

## Method Summary
DUPLEX separates planning into a fast, low-cost pipeline and a slow, reflective loop. The Fast System uses a lightweight LLM (e.g., Qwen3-8B) to extract entities, relations, and states from a natural language task description, guided by a PDDL-derived schema. A deterministic mapper validates this JSON-like output and populates a PDDL problem template, guaranteeing syntactic correctness. A symbolic planner then attempts to solve the problem; success yields a plan. Upon failure (compilation error or unsolvable), the Slow System activates: a high-capacity LLM (e.g., GPT-4o) analyzes the planner’s diagnostic, the domain PDDL, and the failing problem file to propose targeted edits. These edits are applied and the planner reruns, iterating until success or a limit. This design leverages LLMs for robust semantic grounding while using symbolic methods for guaranteed search and syntax.

## Key Results
- DUPLEX achieves 97.5% average success rate on IPC benchmarks, compared to 71.9% for the LLM+P baseline.
- On household tasks, DUPLEX reaches 83.5% success, far exceeding LLM+P’s 20.0%.
- The dual-system architecture eliminates most LLM-induced hallucinations and syntax errors, with the Slow System contributing +13.7% (IPC) and +32.6% (Household) over the Fast System alone.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Confining the LLM to schema-guided information extraction (IE) improves reliability compared to end-to-end planning or code generation.
- **Mechanism:** The LLM is restricted to extracting structured entities, relations, and states from unstructured input, guided by a PDDL-derived schema. A deterministic script then maps this structured data to syntactically valid PDDL. This isolates the LLM from the combinatorial search and strict syntactic requirements of planning, leveraging its strength in semantic parsing while eliminating its weaknesses in logical synthesis and code generation.
- **Core assumption:** LLMs are generally more reliable at extracting structured information from text than at performing multi-step logical deduction or generating flawless code for complex specifications.
- **Evidence anchors:**
  - [abstract] "...strictly confines the LLM to schema-guided information extraction rather than end-to-end planning or code generation."
  - [section IV.A] "By relieving the language model of both complex logical search and strict syntactic generation, this architecture not only improves overall system robustness and success rates, but also enables the deployment of smaller, more efficient LLMs."
- **Break condition:** If the domain schema is incomplete or frequently changes, the guided IE may still produce critical omissions or hallucinations that the deterministic mapper cannot correct, leading to planner failure.

### Mechanism 2
- **Claim:** A dual-system architecture with failure-triggered, agentic reflection (the Slow System) substantially increases success rates on complex/underspecified tasks.
- **Mechanism:** The high-frequency, low-cost Fast System handles routine cases. Upon any planner failure (compilation error or unsolvable problem), diagnostics trigger the Slow System. A high-capacity LLM analyzes the error, references the domain PDDL and original task, and iteratively repairs the problem PDDL. This closed-loop repair specifically targets missing facts, semantic hallucinations, and implicit state omissions that caused the failure.
- **Core assumption:** Symbolic planner failure diagnostics provide a reliable, external grounding signal that allows a capable LLM to conduct effective root-cause analysis and targeted repair of the grounded representation.
- **Evidence anchors:**
  - [abstract] "A Slow System is activated exclusively upon planning failure, leveraging solver diagnostics to drive a high-capacity LLM in iterative reflection and repair."
  - [section V.B] "By parsing the failure diagnostics from the symbolic planner, the Slow System performs root-cause analysis and executes targeted repairs by modifying the Problem PDDL to reflect corrected states."
  - [section VII.B] Ablation shows full system (Fast+Slow) achieves +13.7% (IPC) and +32.6% (Household) over Fast System alone.
- **Break condition:** If the planner's diagnostic is ambiguous or points to a flaw in the domain PDDL itself (not the problem file), the Slow System's repair cycle may loop indefinitely or introduce new errors.

### Mechanism 3
- **Claim:** Deterministic, script-based mapping from structured extraction output to PDDL guarantees syntactic correctness, eliminating a major failure mode of LLM-generated code.
- **Mechanism:** The LLM outputs a constrained JSON or similar structure. A pre-programmed function populates a PDDL template with these values, performing rule-based validation (e.g., ensuring object types exist in the domain). This removes the LLM from the process of writing PDDL syntax (parentheses, keywords, format), ensuring 100% syntactic validity for the problem file.
- **Core assumption:** Template filling with validated data is a more reliable task for a deterministic script than for an LLM generating free-form code, especially for lightweight LLMs.
- **Evidence anchors:**
  - [section IV.B.2] "By completely isolating the LLM from PDDL syntax generation, our approach guarantees 100% syntactic correctness, even with lightweight LLMs."
  - [section IV.B.2] "This design eliminates the compilation failures—such as missing parentheses or type mismatches—that frequently plague direct LLM-to-PDDL generation methods."
- **Break condition:** If the extracted structured data is semantically invalid (e.g., contains a predicate not in the domain), the mapper may either fail or produce a PDDL file that compiles but is logically flawed, pushing the error to a later stage (planner failure).

## Foundational Learning
- **Concept: PDDL (Planning Domain Definition Language)**
  - *Why needed:* The entire system hinges on a correct domain PDDL file (defining actions, predicates, types) used to validate extracted information, guide the IE schema, and be solved by the symbolic planner. Understanding PDDL’s structure (domain vs. problem, :objects, :init, :goal, action :parameters, :precondition, :effect) is essential.
  - *Quick check:* In a blocksworld domain, what PDDL components are needed in a *problem* file to describe a state where block A is on block B, and the goal is to have block A on the table?
- **Concept: Information Extraction (IE)**
  - *Why needed:* DUPLEX reframes the LLM’s task from “plan” to “extract structured information.” Engineers must distinguish open-ended generation from constrained extraction to design effective schemas and prompts. The paper treats IE as a robust task for LLMs.
  - *Quick check:* How would you design a JSON schema to prompt an LLM to extract necessary objects and relations for a “make_sandwich” task from a domain that defines `on`, `held`, and `cut` predicates?
- **Concept: Symbolic Planning & Heuristic Search**
  - *Why needed:* The value proposition relies on the symbolic planner (Fast Downward) providing a *guaranteed feasible* plan given a correct PDDL problem. The planner is a deterministic solver; its failures (unsolvable) are diagnostic signals for the Slow System. Knowledge of common failure modes (e.g., unsolvable due to missing initial facts) is crucial.
  - *Quick check:* If a planner returns “unsolvable” for a problem where the goal is `(on apple plate)` and the initial state is `(on apple table)`, what implicit state fact is likely missing from the problem file?

## Architecture Onboarding
- **Component map (plain text):**  
  Fast System: Schema GUI -> LLM Extractor -> Mapper Script -> Symbolic Planner  
  Slow System (on failure): Diagnostic Parser -> LLM Diagnostician -> Edit Applier -> loop back to Symbolic Planner
- **Critical path:** Fast System’s single pass (Extract → Map → Plan) is the happy path. The critical failure recovery path is: Planner fails → Diagnostic parsed → LLM Diagnostician refines problem PDDL → Re-plan.
- **Design tradeoffs:**
  - *LLM Capacity vs. Cost/Latency:* Small LLM for frequent IE; large LLM only for rare failures. Tradeoff: potential lower extraction quality in Fast System.
  - *Generality vs. Domain Knowledge:* Requires hand-crafted domain PDDL for each new domain. Tradeoff: reduces LLM burden but adds upfront modeling cost.
  - *Open-loop vs. Closed-loop:* Fast System is open-loop; Slow System adds closed-loop with external validation. Tradeoff: added latency for failures but much higher reliability.
- **Failure signatures:**
  - *Fast System:* LLM extraction yields JSON with non-existent types/predicates → Mapper may reject or produce invalid PDDL → **Planner compilation failure** (syntax error, undefined predicate).
  - *Planner:* Valid PDDL but unsolvable → **Planner returns “unsolvable”** (caused by missing implicit facts in init/goal).
  - *Slow System:* LLM’s edit is invalid or introduces new error → **Planner fails again**, triggering another reflection cycle.
- **First 3 experiments:**
  1. **Baseline Establishment:** Run Fast System alone on a few tasks per domain. Verify non-zero success rate and identify common failure modes (e.g., missing object types, missing `clear` predicates).
  2. **Diagnostic Loop Verification:** Intentionally omit a critical initial fact (e.g., `(not (holding robot))`). Confirm planner returns “unsolvable” and Slow System successfully identifies and adds the missing fact within few iterations.
  3. **End-to-End Comparison:** Run full DUPLEX against LLM+P baseline on a small, diverse subset. Measure success rate and average number of Slow System invocations/iterations.

## Open Questions the Paper Calls Out
- **Automatic Domain Learning:** Can DUPLEX learn PDDL domain models from multimodal execution traces without manual authoring? The paper explicitly states this as future work; currently it requires hand-crafted domains, limiting scalability. Resolution would need an algorithm that induces PDDL from demonstrations and achieves comparable benchmark performance.
- **Reflection Latency:** Can the latency of the reflection cycle be reduced for real-time control while maintaining high success rates? The iterative loop with a large LLM introduces latency that may bottleneck real-time deployment. Evidence would be an optimized variant (e.g., faster model, early stopping) achieving similar success rates with sub-second latency.
- **Visual Perception Integration:** How can DUPLEX incorporate visual perception to resolve referential ambiguity? Relying solely on text leaves the system vulnerable in visually rich environments. A multimodal DUPLEX using vision-language models would be needed to demonstrate significantly higher success on ambiguous tasks.

## Limitations
- Reliance on hand-crafted, complete domain PDDL schemas; omissions or changes propagate as semantic errors that the mapper cannot correct.
- The Slow System’s repair loop may not converge if planner diagnostics are ambiguous or if the domain model itself is flawed.
- Deterministic mapping eliminates syntax errors but defers semantic validation to the planner, causing failures that must be repaired via the reflection loop.

## Confidence
- **Schema-Guided IE:** Medium confidence
- **Agentic Repair Loop:** Medium-High confidence
- **Deterministic Mapping:** High confidence

## Next Checks
1. **Fast System Failure Mode Audit:** Run Fast System on a small, diverse task set. Log and categorize all planner failures (compilation vs. unsolvable). Manually inspect extracted JSON to identify common patterns of omission/hallucination against the domain schema.
2. **Diagnostic-Signal Fidelity Test:** For a known-failing problem PDDL (e.g., missing `(not (holding robot))`), confirm the planner produces a clear diagnostic. Then run the Slow System repair loop and measure first-attempt repair success rate.
3. **Schema Completeness Stress Test:** Intentionally remove a non-trivial predicate (e.g., `clear`) from the domain schema given to the Fast System. Evaluate how often the LLM’s extractions omit facts referencing that predicate and whether this consistently leads to “unsolvable” failures that the Slow System can recover from.
