# ROSE: Reordered SparseGPT for More Accurate One-Shot Large Language Models Pruning

## Quick Facts
- **arXiv ID**: 2603.05878
- **Source URL**: https://arxiv.org/abs/2603.05878
- **Reference count**: 40
- **Primary result**: ROSE reduces reconstruction error and perplexity versus SparseGPT for one-shot LLM pruning, e.g., LLaMA3-8B at 80% sparsity (perplexity 172.14 vs 203.45), with minimal overhead.

## Executive Summary
ROSE is an enhancement to the SparseGPT one-shot pruning framework for large language models. It addresses a key limitation: the fixed, left-to-right pruning order in SparseGPT can be suboptimal for layers with columnar weight patterns, where important weights are concentrated in specific columns. ROSE introduces a two-level reordering strategy. Before pruning, it estimates the potential reconstruction loss for each column within a block and for each block globally, using a simple importance metric based on weight magnitude and activations. Layers exhibiting high variance in these block losses (identified by a relative range metric) are deemed "columnar" and undergo reordering: columns within blocks and blocks themselves are sorted so that those projected to cause higher loss are pruned earlier. This ensures weights likely to incur larger pruning errors are removed when more remaining weights are available for compensation under the Optimal Brain Surgeon framework. Evaluations on LLaMA2/3 and Mistral models show ROSE consistently lowers reconstruction error andWikiText perplexity compared to SparseGPT, especially at high sparsities (e.g., 80–90%), and also improves semi-structured sparsity patterns. The added pre-pruning analysis incurs only a small computational overhead (~5–8%).

## Method Summary
ROSE modifies the SparseGPT pipeline with a pre-pruning analysis and reordering phase. For each weight matrix, it splits the columns into fixed-size blocks along the input dimension. Using a calibration dataset, it computes an importance score per weight (product of absolute weight value and the ℓ₂ norm of its corresponding activation channel). For each block, it selects the smallest p% of these scores (where p is the target sparsity) to form a candidate pruning loss matrix. From this, it derives a per-column loss (summed over rows within the block) and a per-block loss (summed over all entries in the matrix). A layer is identified as columnar if the relative range of block losses, R_rel = (max - min) / mean, exceeds a threshold (η=0.5). For such layers, ROSE reorders columns within each block in descending order of column loss, then reorders all blocks globally in descending order of block loss. The reordered weight and activation matrices are then fed into the standard SparseGPT Hessian-based pruning procedure. After pruning, the inverse permutations are applied to restore the original matrix structure. Non-columnar layers skip reordering and use standard SparseGPT directly.

## Key Results
- ROSE reduces reconstruction error and WikiText perplexity versus SparseGPT across LLaMA2/3 and Mistral models at high sparsities (60–90%).
- Example: LLaMA3-8B at 80% sparsity, ROSE achieves perplexity 172.14 vs SparseGPT's 203.45.
- It also improves accuracy for 2:4 and 4:8 semi-structured sparsity and composes effectively with 4/8-bit quantization, adding minimal overhead (~5.15 min vs 4.76 min for LLaMA2-7B pruning).

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Pre-pruning based on initial weight magnitude and activations reliably identifies weights likely to be pruned, enabling estimation of column and block pruning losses before the actual SparseGPT process.
- **Mechanism**: Compute importance score S_ij = |W_ij| * ||X_j||₂. For each block of size B_s along input channels, select the smallest p% of scores to form a loss matrix L(k). Sum L(k) over columns to get column loss l_j(k), and over all entries to get block loss L(k). These losses prioritize which columns/blocks cause more error if pruned.
- **Core assumption**: The relative importance (and thus pruning eligibility) of most weights remains stable during SparseGPT's iterative pruning, supported by observation that >80% of weights change by <30% in magnitude (Figure 2).
- **Evidence anchors**: Abstract mentions "estimates column and block pruning losses via pre-pruning"; Section 4.2 details the Wanda-based metric; neighbor works (SparseGPT, Wanda) validate magnitude/activation importance.
- **Break condition**: If weight distributions shift drastically during pruning (e.g., at extreme sparsity), pre-pruning estimates become inaccurate, leading to poor reordering.

### Mechanism 2
- **Claim**: Two-level reordering (columns within blocks by descending column loss; blocks globally by descending block loss) ensures weights with larger potential pruning errors are pruned earlier, leveraging more remaining weights for effective error compensation.
- **Mechanism**: In SparseGPT's left-to-right pruning, earlier-pruned weights can be approximated using a larger set of remaining weights (via the inverse Hessian). By reordering so high-loss columns/blocks are first, ROSE minimizes the final reconstruction error.
- **Core assumption**: Pruning error correlates with the pre-pruning loss estimates; earlier compensation is more effective (motivated by Figure 1(c)).
- **Evidence anchors**: Abstract states "columns within each block are reordered in descending order of column loss, while blocks are reordered based on block loss"; Section 4.2 formalizes Equations 5 and 6; Section 5.4 ablation (Figure 4) shows both reorders help, with block reordering having larger impact, and inverse ordering worsens error.
- **Break condition**: If loss estimates poorly correlate with actual pruning error, reordering misplaces high-error weights, potentially increasing final error.

### Mechanism 3
- **Claim**: The relative range of block loss (R_rel) effectively identifies layers with columnar weight patterns, where reordering yields consistent reconstruction error reduction.
- **Mechanism**: Compute R_rel = (max L(k) - min L(k)) / mean(L(k)) from block loss estimates. If R_rel > η (default 0.5), classify as columnar and apply reordering; else use standard SparseGPT.
- **Core assumption**: Columnar layers have high variance in block-wise loss due to concentration of high-magnitude weights in specific columns; non-columnar layers show low variance (Appendix D Figures).
- **Evidence anchors**: Abstract cites "relative range of block loss as a metric to identify columnar layers"; Section 4.2 defines R_rel and η; Section D.4 shows o_proj layers have R_rel > 0.5 and benefit from reordering, while others do not.
- **Break condition**: If a non-columnar layer exhibits high R_rel due to noise, reordering adds overhead without gain. If a columnar layer has low R_rel, it is missed, forfeiting potential improvement.

## Foundational Learning
- **Concept: Second-Order Pruning (OBS/OBC Framework)**
  - *Why needed*: ROSE extends SparseGPT, which uses Optimal Brain Surgeon (OBS) to approximate the effect of pruning a weight on the loss by compensating via other weights using the Hessian. Understanding that the compensation set shrinks as pruning progresses explains why pruning order matters.
  - *Quick check*: Why does the OBS framework allow pruning without retraining, and how does the available "compensation set" shrink as pruning progresses?
- **Concept: Block-wise Iterative Pruning**
  - *Why needed*: SparseGPT and ROSE prune in blocks (sub-matrices along input channels) to manage the computational cost of Hessian inversion. The blocksize parameter affects both the Hessian approximation fidelity and the granularity of reordering.
  - *Quick check*: How does increasing blocksize affect the fidelity of the Hessian approximation and the potential impact of reordering?
- **Concept: Weight Stability Under Pruning**
  - *Why needed*: ROSE's pre-pruning relies on the observation that most weights' relative magnitudes remain stable during SparseGPT's iterative process, justifying the use of initial weight/activation statistics to predict future pruning masks.
  - *Quick check*: What might cause a weight's relative importance to change significantly during SparseGPT's iterative pruning, violating the stability assumption?
- **Concept: Semi-Structured Sparsity**
  - *Why needed*: The paper also evaluates ROSE on 2:4 and 4:8 sparsity patterns, which are hardware-friendly. ROSE's reordering logic can be adapted to such structured masks.
  - *Quick check*: How does the concept of fixed patterns (like 2:4) interact with ROSE's column and block reordering?
- **Concept: Activation Calibration**
  - *Why needed*: Both SparseGPT and ROSE rely on activation statistics (norms) from a calibration dataset to compute importance scores. The quality and size of this data directly impact loss estimation accuracy.
  - *Quick check*: Why is a small, representative calibration set sufficient for estimating activation norms, and what are the risks of using insufficient or non-representative data?

## Architecture Onboarding
- **Component map**: Input (Weight matrix W, Activation matrix X, blocksize B_s, sparsity p, threshold η) -> Pre-pruning (Compute importance S, form loss matrix L) -> Loss aggregation (Column loss l_j(k), Block loss L(k)) -> Columnar detection (Compute R_rel from L(k)) -> Conditional reordering (If R_rel > η: column permute within blocks, then block permute globally) -> SparseGPT pruning (Hessian-based mask selection & weight compensation) -> Inverse permutation (Restore original order) -> Output (Sparse weight matrix Ŵ).
- **Critical path**: 1) Split W and X into K blocks along input channels. 2) For each block, compute S_ij = |W_ij| * ||X_j||₂; extract smallest p% scores to form L(k). 3) Sum L(k) over columns to get l_j(k); sum all entries to get L(k). 4) Compute R_rel across L(k). 5) If R_rel > 0.5: (a) Permute columns in each block so l_j(k) descending. Apply same permutation to corresponding X block. (b) Permute blocks globally so L(k) descending. Apply same permutation to X. 6) Run SparseGPT on reordered W and X to generate sparse Ŵ. 7) Apply inverse permutations to Ŵ to return to original layout. If R_rel <= 0.5, skip steps 5a/5b and 7.
- **Design tradeoffs**: Overhead vs. accuracy: Pre-pruning adds O(N log N) sorting cost but can significantly reduce reconstruction error/perplexity, especially at high sparsity. Threshold η trades coverage (more layers reordered) against risk of misapplication (overhead without benefit). Blocksize B_s affects both SparseGPT's Hessian approximation and ROSE's ability to capture columnar patterns; larger blocks reduce Hessian cost but may blur columnar signals.
- **Failure signatures**: 1) No perplexity improvement vs. SparseGPT: likely R_rel <= η for most layers, so reordering not applied; verify R_rel values. 2) Pruning time much higher than reported ~8% overhead: could be due to applying reordering to too many large layers or inefficient sorting; profile pre-pruning time. 3) Reconstruction error decreases but perplexity increases: may indicate calibration data/sequence length insufficient for accurate Hessian/activation norms, as both methods are sensitive to these.
- **First 3 experiments**: 1) **Reconstruction Error Ablation**: On a single layer (e.g., LLaMA2-7B self_attn.o_proj), compare ROSE, column-reorder only, block-reorder only, inverse ordering, and SparseGPT across sparsities. Expect both reorders reduce error, block more so; inverse increases error. 2) **Columnar Layer Identification Validation**: For a model (LLaMA3-8B), compute R_rel for all layers. Correlate with weight magnitude visualizations (Appendix D) and measure reconstruction error after reordering vs. SparseGPT. Expect o_proj layers have high R_rel (>0.5) and consistent error reduction; others do not. 3) **End-to-End Pruning Utility**: Prune full models (LLaMA2/3, Mistral) at multiple sparsities (60–90%) with ROSE and SparseGPT. Evaluate WikiText perplexity and zero-shot accuracy on commonsense benchmarks. Expect consistent improvements, larger at higher sparsities.

## Open Questions the Paper Calls Out
- Is the fixed threshold of 0.5 for identifying columnar layers optimal across all LLM architectures and sizes? The paper sets it based on LLaMA3-8B analysis without systematic study across models.
- Does the assumption that most weights maintain stable relative importance during pruning hold universally? It is based on Figure 2 for LLaMA2-7B; not validated for higher sparsity or larger models.
- What causes columnar patterns to predominantly appear in self-attention output projection layers? The paper observes this pattern but provides no mechanistic explanation.
- Could alternative pre-pruning importance metrics improve ROSE's performance beyond Wanda's |W|·||X||2? The paper adopts this metric without comparison.

## Limitations
- **Weight stability assumption**: Pre-pruning relies on the observation that most weights' relative magnitudes change little during SparseGPT pruning. This may not hold at extreme sparsities (e.g., >90%) or for very large models, potentially degrading loss estimates.
- **Columnar detection heuristic**: The R_rel > 0.5 threshold is derived from analysis on LLaMA/Mistral models. Other architectures (e.g., encoder-decoder, MoE) may have different weight distributions, requiring threshold tuning or failing to exhibit clear columnar patterns.
- **Generalization scope**: Evaluations are limited to decoder-only LLMs. Applicability to other model families (e.g., T5, GPT, vision-language models) remains unverified.

## Confidence
- Pre-pruning loss estimation: *Medium* (stability observed on one model; not universally proven).
- Two-level reordering strategy: *High* (ablation studies confirm benefit for columnar layers).
- R_rel metric for columnar identification: *Medium* (empirically effective on tested models; threshold may not transfer).
- Overall reported gains (perplexity, accuracy): *High* for decoder-only LLMs at 60–90% sparsity; *Low* for other architectures/sparsities.
- Overhead claims: *High* (time measurements provided, small relative increase).

## Next Checks
1. **Cross-architecture validation**: Apply ROSE to non-decoder-only models (e.g., T5 encoder-decoder, a MoE model like Mixtral) and compare reconstruction error and zero-shot accuracy against SparseGPT.
2. **Calibration sensitivity analysis**: Vary calibration dataset size (32–1024 samples) and sequence length (512–4096 tokens) to measure impact on R_rel distribution, reconstruction error, and final perplexity.
3. **Dynamic reordering extension**: After pruning an initial fraction of weights (e.g., 25%), recompute the loss matrix on the remaining weights and reorder again. Assess if this adaptive approach improves over static pre-pruning reordering, especially at very high sparsities.
