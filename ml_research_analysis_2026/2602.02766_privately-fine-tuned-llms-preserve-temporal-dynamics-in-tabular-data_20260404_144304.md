# Privately Fine-Tuned LLMs Preserve Temporal Dynamics in Tabular Data

## Quick Facts
- **ArXiv ID:** 2602.02766  
- **Source URL:** https://arxiv.org/abs/2602.02766  
- **Reference count:** 40  
- **Primary result:** PATH reduces distributional distance by over 60% and state transition errors by nearly 50% compared to AIM at ε=2, while maintaining similar marginal fidelity.

## Executive Summary
Longitudinal tabular data, where each user contributes multiple sequential records, violates the row-independence assumption underlying many differentially private synthetic data generators. Flattening histories into fixed-width vectors destroys temporal coherence even when marginal distributions are preserved. This paper introduces PATH (Private Autoregressive Trajectory Histories), a framework that treats each user’s entire table as the unit of DP protection. PATH privately fine‑tunes a large language model (Gemma) to autoregressively generate rows conditioned on prior context, followed by a private selection step that refines the synthetic dataset. Evaluations on MIMIC‑IV vitals, NYC 311 service requests, and a synthetic HMM show that PATH captures long‑range dependencies far better than state‑of‑the‑art marginal mechanisms like AIM. At ε=2, PATH reduces the TDCR distributional divergence from 0.7359 to 0.2886 (over 60% reduction) and state transition Frobenius error from 0.7412 to 0.3867 (nearly 50% improvement), while preserving univariate marginals. On HMM log‑likelihood, PATH attains 57.97 vs AIM’s 319.43—a five‑fold improvement. For spatiotemporal NYC 311 data, where marginal methods fail to scale, PATH achieves MAUVE up to 0.634.

## Method Summary
PATH addresses longitudinal synthesis under user‑level differential privacy by redefining the privacy unit as an entire user table rather than individual rows. The first step is to serialize each user’s complete table into a fixed‑format token sequence that includes a schema header and delimited rows (e.g., “Columns: … [Row i]: col1 is val1, …”). For training, a pre‑trained Gemma model is fine‑tuned with DP‑SGD, where each training example consists of a randomly split user table: the first *k* rows serve as context, and the remaining rows are the target. This dynamic splitting teaches the model to generate from any prefix, enabling arbitrary‑length trajectories. After training, an large pool of synthetic tables is generated by autoregressively sampling row tokens, with a parsing cascade that discards malformed rows and propagates static identifiers (e.g., subject_id). Finally, a private selection procedure embeds both real and synthetic tables (using Gecko), lets each real table noisily vote for its ten nearest synthetics, and selects the highest‑scoring candidates to form the final dataset. The entire pipeline operates under a total privacy budget ε, divided between training (ε_train) and selection (ε_select).

## Key Results
- Distributional divergence (TDCR JSD) reduced by over 60% (0.7359 → 0.2886 at ε=2).  
- State transition errors nearly halved (Frobenius 0.7412 → 0.3867).  
- HMM log‑likelihood improved 5× (57.97 vs. AIM’s 319.43 at ε=2).

## Why This Works (Mechanism)

**Mechanism 1: User‑level privacy unit**  
- **Claim:** Treating the full user table as the unit of differential privacy protection preserves longitudinal coherence that row‑level DP cannot.  
- **Mechanism:** All rows belonging to a single user are treated as one indivisible record for adjacency (add/remove one user’s entire history). This ensures DP guarantees cover the whole trajectory, preventing reconstruction of partial histories.  
- **Core assumption:** Temporal dependencies span multiple rows and are meaningful for both privacy and utility.  
- **Evidence:** The paper’s abstract and Section 2 formalize this adjacency; related work (e.g., DP‑TBART) uses row‑level DP, highlighting the novelty. Empirically, ablations in the appendix show user‑level DP yields significant gains in temporal metrics.

**Mechanism 2: Autoregressive LLM generation**  
- **Claim:** Autoregressive generation via privately fine‑tuned LLMs captures long‑range temporal dependencies that marginal‑based methods miss.  
- **Mechanism:** A pre‑trained Gemma model is fine‑tuned with DP‑SGD on serialized user tables. At inference, rows are generated sequentially, conditioning on previously generated rows, thus directly modeling P(x_t | x_{<t}).  
- **Core assumption:** LLMs can learn high‑order sequential distributions; DP‑SGD noise does not entirely erase this ability.  
- **Evidence:** The abstract states PATH “leverages the autoregressive capabilities of privately fine‑tuned large language models.” Section 5 describes the conditional generation objective; Section 7 reports reductions in state transition errors (~50%) and a 5× HMM likelihood improvement over AIM.

**Mechanism 3: Private selection**  
- **Claim:** A private post‑hoc selection step draws from an over‑generated pool to correct model imperfections without additional DP budget beyond the allocated ε_select.  
- **Mechanism:** Many candidate synthetic tables are generated. Each real table casts DP‑noisy votes for its *k* nearest synthetic neighbors in an embedding space (Gecko). The highest‑voted candidates form the final dataset.  
- **Core assumption:** The over‑generation pool covers the data manifold; selecting a representative subset can mitigate mode collapse and invalid outputs from the DP‑fine‑tuned model.  
- **Evidence:** Abstract mentions “followed by a private selection step.” Section 5 details the voting mechanism; Appendix A allocates a separate ε_select (e.g., 0.5–1.0). Ablation in the appendix shows selection improves fidelity over raw generations.

## Foundational Learning

### Differential Privacy (ε, δ) and DP‑SGD
- **Why needed:** PATH relies on formal user‑level privacy guarantees; DP‑SGD is the training algorithm and requires careful budget allocation (ε_train vs ε_select).  
- **Quick check:** If you treat each user’s full table as one record, how does the sensitivity of the gradient computation change compared to per‑row DP?

### Autoregressive modeling and next‑token prediction
- **Why needed:** The core innovation is applying LLMs to sequential row generation; understanding conditioning on prior rows is essential to see why temporal coherence emerges.  
- **Quick check:** Why does generating a row conditioned on previous rows help preserve state transitions better than modeling flattened vectors with marginals?

### Serialization of structured data into text
- **Why needed:** LLMs process tokens; converting tables into deterministic strings (with a fixed schema and row delimiters) is the bridge that allows the model to learn the joint distribution.  
- **Quick check:** What are two pitfalls of the serialization format that could cause the model to generate syntactically invalid rows?

### Evaluation metrics for longitudinal synthetic data (TDCR, State Transition Frobenius, MAUVE)
- **Why needed:** Standard row‑wise metrics fail to capture whole‑table cohesion, temporal logic, and distributional coverage.  
- **Quick check:** How does TDCR use Dynamic Time Warping to compare tables of different lengths, and why is JSD used on the distance distributions?

## Architecture Onboarding
**Component map:** Data loader → DP fine‑tuning engine → Generation pipeline → Private selector → Evaluation suite.

**Critical path:** Raw data → serialization → DP fine‑tuning → over‑generation → private selection → final synthetic dataset → evaluation.

**Design tradeoffs:**
- Model size vs. privacy budget: Smaller models degrade faster at low ε; 4B retains coherence but costs more compute.
- Flattening vs. trajectory: Flattening enables marginal mechanisms but destroys temporal dependencies; PATH avoids flattening but requires an autoregressive architecture.
- Over‑generation amount: More candidates improve selection quality but consume compute; selection ε must be balanced against training ε.
- Serialization format: Deterministic “column is value” aids parsing but may waste tokens; row delimiters are crucial for temporal segmentation.

**Failure signatures:**
- High TDCR JSD (>0.6): Synthetic tables are far from the real manifold, likely due to excessive DP noise or failed learning.
- State Transition Frobenius much larger than real: Autoregressive generation is ignoring history; check context window and training formulation.
- Parsing failure rate >30%: DP‑fine‑tuned model emits malformed strings; tighten post‑processing or increase over‑generation.
- Classifier AUC ≈ 1.0: Synthetic data is too easily distinguishable; indicates memorization or severe mode collapse.

**First 3 experiments:**
1. **Synthetic HMM sanity check:** Train PATH on small HMM‑generated data (simple known dynamics). Verify that HMM log‑likelihood of synthetic sequences is close to that of held‑out real sequences.
2. **MIMIC marginal + temporal parity:** At ε=10.0, compare PATH’s univariate Wasserstein distances and state transition error against AIM. If PATH’s marginals are significantly worse, revisit clipping norm or LoRA rank.
3. **NYC 311 spatiotemporal sanity:** At ε=2.0, produce geospatial hexbin plots and hourly request distributions. If synthetic data clumps incorrectly, check whether Gecko embeddings capture location semantics or augment the schema with explicit geographic features.

## Open Questions the Paper Calls Out
1. **Heterogeneous schemas:** How can PATH be extended to handle users with different sets of columns? The authors note the framework could naturally accommodate heterogeneity but leave full exploration for future work.
2. **Optimal serialization:** What text format best preserves long‑range temporal dependencies under DP‑fine‑tuned LLMs? The paper uses a fixed schema prefix with row delimiters but does not compare alternatives.
3. **Budget allocation:** How does the split of the privacy budget between training (ε_train) and private selection (ε_select) affect temporal fidelity? The method uses a fixed ε_select but provides no analysis of its impact.
4. **Scaling laws:** What is the relationship between model size, privacy budget, and longitudinal synthesis performance? Results only compare Gemma 1B and 4B; broader scaling trends remain unknown.

## Limitations
- **Privacy unit assumption:** USER‑level DP protects full trajectories but may not match real‑world policies where individual rows have different sensitivity levels.
- **LLM capacity under DP noise:** The boundary at which DP‑fine‑tuned LLMs maintain autoregressive coherence for long sequences or tight budgets is not mapped.
- **Selection bias risk:** If the over‑generation pool suffers from mode collapse due to DP noise, the private selection step cannot recover missing temporal modes.

## Next Checks
1. **Ablation on privacy unit:** Implement a hybrid adjacency (e.g., user‑level for temporal columns, row‑level for non‑temporal ones) to quantify the specific benefit of protecting full histories.
2. **Controlled capacity test:** Train PATH on synthetic sequences of varying lengths (e.g., 5, 20, 50 rows) at fixed ε=2. Plot TDCR or HMM likelihood versus sequence length to locate the context‑length failure threshold of the DP‑fine‑tuned Gemma.
3. **Selection pool diversity analysis:** For a fixed training ε, vary the over‑generation factor (2×, 5×, 10×) and measure the marginal improvement from private selection. Saturation would indicate adequate coverage; no gain would signal irrecoverable mode collapse.
