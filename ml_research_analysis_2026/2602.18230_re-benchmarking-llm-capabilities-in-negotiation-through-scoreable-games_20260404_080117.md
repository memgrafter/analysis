# [Re] Benchmarking LLM Capabilities in Negotiation through Scoreable Games
## Quick Facts
- arXiv ID: 2602.18230
- Source URL: https://arxiv.org/abs/2602.18230
- Reference count: 20
- Primary result: High-capability models reach near 100% 5‑way agreement; 6‑way peaks at 55%. Code bug fixes lower leakage and improve small-model scores, but ablation choices cause up to 15% performance swings, challenging benchmark objectivity.

## Executive Summary
This work reproduces and critically extends the Scoreable Games benchmark for evaluating LLM negotiation. The authors fixed known implementation bugs (leakage detection, threshold handling, final deal validation), introduced additional social welfare metrics (USW, ESW, NSW), conducted extensive ablation studies, assessed game diversity, and validated behavioral claims. Their results show that correcting bugs substantially alters model rankings and reduces false leakage detection, especially benefiting smaller models. Performance is highly sensitive to prompt ablations (up to 15% variation), with optimal configurations differing across models, undermining the benchmark’s claim of objective comparison. Moreover, the benchmark’s games are overwhelmingly construction-themed, revealing a thematic bias that limits generalizability. Behavioral prompts (greedy/adversarial) confirmed the original findings. The study highlights the need for careful experimental design and standardized evaluation protocols.

## Method Summary
The reproduction used a corrected codebase across a wide range of models (GPT-4o mini, GPT-4o, Qwen2.5-7B/72B, DeepSeek variants, Llama, Phi, Ministral, Mixtral, etc.). Key fixes included robust parsing of `<ANSWER>` tags, proper threshold checks (≥, no p1 bonus), and accurate final deal validation. New metrics (USW, ESW, NSW) tracked fairness over negotiation rounds. Ablation experiments varied four prompt components (previous deals, others’ preferences, candidate generation, planning) in 16 configurations for two models. Game diversity was evaluated by generating 10 new games with the original prompt and 10 with a revised prompt, computing sparsity, IoU, and deal-space statistics. Behavioral tests implemented greedy and adversarial modifications to specific agent role descriptions. All experiments averaged results over 20 iterations.

## Key Results
- Bug fixes drastically reduced false leakage detection and boosted agreement rates for smaller models, altering original rankings.
- Ablation configurations caused up to 15% performance variation in 5/6‑way agreement; optimal prompt settings differed between models (e.g., GPT-4o mini vs. Qwen2.5-72B), making comparisons ambiguous.
- All 15 original and auto‑generated games shared a construction project theme; a revised prompt produced diverse scenarios (e.g., military budgeting, conference planning), highlighting thematic bias.
- Behavioral prompts (greedy/adversarial) shifted utilities as originally reported, confirming that claim.
- High‑capability models nearly solved 5‑way agreement (≈100%) but 6‑way remained difficult, with DeepSeek-R1‑Distill‑Qwen‑32B reaching 55%.

## Why This Works (Mechanism)
### Mechanism 1: Bug fixes align evaluation with intended design
- **Claim**: Fixing code bugs in leakage detection and threshold handling leads to fairer and more accurate model comparisons.
- **Mechanism**: The original implementation misinterpreted formatting deviations as leakage and had inconsistent threshold checks (≥ vs >, automatic p1 bonus). These disproportionately penalized smaller models that often deviate from strict formatting. Correcting parsing and threshold logic yields reliable scores.
- **Core assumption**: The bugs were unintentional and the fixes match the benchmark's intended design.
- **Evidence anchors**: Abstract notes code issues; Section 3.1.5 describes handling malformed responses and threshold corrections; neighboring work highlights leakage detection pitfalls.
- **Break condition**: Original behavior might be intentional, or fixes could introduce new biases.

### Mechanism 2: Ablation sensitivity undermines objectivity
- **Claim**: The benchmark's claim of objective model comparison is weakened because performance is highly sensitive to ablation configurations, with optimal settings varying across models.
- **Mechanism**: Ablations modify reasoning scaffolding (e.g., "consider previous deals", "generate candidates"). The paper shows up to 15% variation in 5/6‑way agreement across 16 configurations, and best config for GPT‑4o mini differs from Qwen2.5‑72B.
- **Core assumption**: Ablation configurations are meaningful experimental parameters and the original single config is not universal.
- **Evidence anchors**: Abstract states model comparisons ambiguous; Table 2 shows variance; Section 3.2.1 emphasizes need to account for ablations.
- **Break condition**: Future work identifies a canonical ablation or shows effects negligible.

### Mechanism 3: Thematic bias limits generalizability
- **Claim**: The benchmark lacks diversity in game settings, as all provided and auto‑generated games are construction‑themed, restricting applicability to real‑world negotiations.
- **Mechanism**: The prompt for generating new games contains words like "project" and "resources", biasing toward construction. Generating 10 games with original prompt yields all construction‑based; removing such terms yields diverse contexts.
- **Core assumption**: A negotiation benchmark should cover multiple domains.
- **Evidence anchors**: Abstract notes low diversity; Section 4.2 provides experimental evidence and alternative prompt.
- **Break condition**: Construction scenarios are considered representative or benchmark extended with diverse games.

## Foundational Learning
### Scoreable Games
- **Why needed here**: The entire benchmark is built on Scoreable Games (Susskind, 1985), defining structure (parties, issues, deals, utilities). Understanding this formalism is essential to grasp the game setup and evaluation metrics.
- **Quick check question**: What are the roles of p1 and p2 in a Scoreable Game, and what is the difference between 5‑way and 6‑way agreement?

### Leakage in LLM Negotiation Benchmarks
- **Why needed here**: Leakage (disclosing private utility information) is a key metric; the original detection method was buggy. Understanding leakage is crucial to interpret results and code fixes.
- **Quick check question**: How can formatting inconsistencies in model responses lead to false leakage detection, and how did the authors mitigate this?

### Social Welfare Metrics (USW, ESW, NSW)
- **Why needed here**: These metrics evaluate negotiation fairness beyond agreement rates, used to check if models unfairly advantage some agents.
- **Quick check question**: Why might Nash Social Welfare be a better measure of fairness than Utilitarian Social Welfare in multi‑party negotiations?

### Ablation Studies in Prompt‑Based Experiments
- **Why needed here**: The paper's second experiment varies prompt components to assess robustness. Ablations are common in NLP to understand model dependence on prompt engineering.
- **Quick check question**: What is the risk of using a single ablation configuration when comparing multiple LLMs?

## Architecture Onboarding
### Component Map
main.py → agent/ → game/ → evaluation/ → utils/
### Critical Path
1. Define game configuration (config.txt) with parties, issues, utilities.
2. Set model and ablation options via CLI arguments.
3. Run main.py which initializes agents, executes negotiation rounds, collects traces.
4. Post‑process logs to compute metrics (5/6‑way, leakage, social welfare).
### Design Tradeoffs
- Quantization: reduces memory and speeds inference but may affect performance; tradeoff between resource constraints and accuracy.
- API vs local: OpenAI API simplifies setup but costs and limits reproducibility; local models require GPU but are fully controllable.
- Leakage handling: strict parsing may discard valid malformed responses; lenient risks including actual leakage; authors chose a middle ground.
### Failure Signatures
- High leakage rates (>20%) in small models, indicating parsing issues.
- Low agreement rates (<10%) in base game for capable models, suggesting threshold or utility misconfiguration.
- Runtime errors from missing packages or insufficient GPU memory.
- Inconsistent metrics across runs with same seed (non‑determinism).
- High failure rates due to models not adhering to `<ANSWER>` format.
### First 3 Experiments
1. Reproduce base game results for a set of models (including GPT‑4o mini, Qwen2.5‑72B) using fixed code; run 20 iterations per model; collect 5/6‑way, Any, Wrong, Leakage.
2. Run full ablation matrix (16 configurations) on GPT‑4o mini and Qwen2.5‑72B; each config 20 iterations; measure performance sensitivity.
3. Generate new game settings using original prompt and modified prompt to assess diversity; compute sparsity, IoU, and deal space statistics for all games.

## Open Questions the Paper Calls Out
1. **Why does model comparison remain ambiguous?**  
   The benchmark introduces many comparison axes (games, ablations, metrics) without a principled aggregation method, making it unclear which configuration reflects true negotiation skill. Resolution requires identifying consistent predictors of performance and defining a standardized evaluation protocol.

2. **Does limited thematic diversity affect generalizability?**  
   All original and auto‑generated games are construction‑themed; it is unknown whether this theme favors certain model capabilities or correlates with performance in other domains. Testing on a diverse set of non‑construction games would reveal if rankings are stable.

3. **How should ablation studies be standardized?**  
   Single ablation configurations may arbitrarily advantage models; a factorial experiment mapping the impact of each prompt component across many models is needed to determine which variations are consistent versus model‑specific.

4. **What other hidden biases or bugs might exist?**  
   The codebase may contain additional subtle issues (e.g., in utility calculation, round termination) that systematically distort measurements, especially for weaker models. A comprehensive code review and unit testing could uncover them.

5. **What intrinsic game properties determine difficulty across models?**  
   Current static descriptors (sparsity, IoU) do not explain model‑specific difficulty variations (e.g., why DeepSeek excels in Game 3 but Mistral‑Small fails). Richer game features (e.g., Nash equilibrium properties, linguistic complexity) need to be correlated with performance to build a predictive model.

## Limitations
- Behavioral variant prompts and exact agent sets (P_const, P_benefit) are not detailed, blocking exact replication of behavioral experiments.
- The diversity claim relies on only 10 auto‑generated games; a larger sample is needed for statistical robustness.
- Baseline details (e.g., random priority generation) are missing, making it impossible to reproduce the original baseline results.
