# IF-GEO: Conflict-Aware Instruction Fusion for Multi-Query Generative Engine Optimization

## Quick Facts
- **arXiv ID**: 2601.13938
- **Source URL**: https://arxiv.org/abs/2601.13938
- **Reference count**: 20
- **Primary result**: IF-GEO achieves state-of-the-art multi-query GEO performance with superior stability (lowest downside risk, highest win-tie rate) by fusing conflicting edit requests into a coherent global revision blueprint.

## Executive Summary
IF-GEO tackles the constrained optimization problem in multi-query Generative Engine Optimization (GEO), where a single document revision must satisfy diverse user queries that impose conflicting content requirements under a limited budget. It introduces a **diverge-then-converge** framework: first, it mines a weighted set of representative latent queries and generates distinct, query-specific edit requests. Second, it synthesizes a global **Global Revision Blueprint** via conflict-aware instruction fusion that coordinates competing preferences while explicitly optimizing for risk-aware stability metrics (Worst-Case Performance, Win-Tie Rate, Downside Risk). On GEO-Bench using GPT-4o-mini, IF-GEO outperforms baselines in both average visibility gains and cross-query robustness, demonstrating that coordinated conflict resolution is critical for stable multi-query optimization.

## Method Summary
IF-GEO operates as an inference-time, multi-stage LLM pipeline without model training. Given a document and an initial query set, it first **diverges** by mining additional latent queries (via reverse retrieval) and generating structured edit requests (excerpt, suggestion, necessity score) for each. It then **converges** through an instruction fusion module: requests are prioritized by global weight (query popularity × necessity), semantically deduplicated, and subjected to LLM-arbitrated conflict resolution for mutually exclusive edits targeting the same content. The resolved instructions are mapped onto document sections to form a JSON `revision_blueprint`. Finally, a blueprint-guided revision step rewrites the document by strictly following this blueprint. The optimization objective balances expected visibility gain with penalties for negative gains (Downside Risk) and constraints on worst-case performance, ensuring robust improvements across all queries.

## Key Results
- **Highest mean visibility gains**: Objective impression mean 11.03 vs. Auto-GEO's 7.80; subjective average 5.87.
- **Superior stability**: Lowest downside risk (0.0023), highest win-tie rate (80.50%), and best worst-case performance (−0.0090).
- **Ablation confirmation**: Removing conflict resolution causes the largest drop in both mean and tail metrics, proving its critical role.

## Why This Works (Mechanism)

### Mechanism 1: Diverge Phase – Mining Latent Queries & Generating Distinct Edit Requests
- **Claim**: Mining a weighted set of representative latent queries and generating query-specific edit requests captures heterogeneous optimization preferences for diverse user intents.
- **Mechanism**: Reverse retrieval (LLM-generated plausible queries) produces a weighted query set `Q(D)`. For each query, the system diagnoses content gaps and outputs structured `(excerpt, suggestion, necessity)` tuples, creating a diverged pool of localized revision signals.
- **Core assumption**: A small, weighted set of synthetically mined queries approximates the latent intent distribution a document will face.
- **Evidence anchors**: [abstract] "mining representative latent queries..." ; [section 4.2] details Query Mining and Request Generation.
- **Break condition**: If query mining fails to cover the true intent distribution (e.g., all queries cluster around one aspect), the blueprint will misalign, hurting cross-query performance.

### Mechanism 2: Converge Phase – Conflict-Aware Instruction Fusion into a Global Revision Blueprint
- **Claim**: Consolidating diverged requests via prioritization, deduplication, and conflict resolution coordinates competing preferences into a coherent, executable plan that prevents inconsistent edits under a limited content budget.
- **Mechanism**: Requests are filtered by global priority `g = w * s`, semantically deduplicated, and resolved via LLM arbitration (selection or synthesis based on priority gaps). Fused instructions are mapped to document sections to form the `revision_blueprint`, which acts as a strict execution contract.
- **Core assumption**: An LLM can effectively arbitrate conflicts and synthesize compatible instructions when provided with priority scores and semantic context.
- **Evidence anchors**: [abstract] "synthesizing a global revision blueprint via conflict-aware instruction fusion" ; [section 4.3] steps: Prioritization/Deduplication, Conflict Resolution, Blueprint Construction.
- **Break condition**: If conflict resolution fails (e.g., always selects high-priority but contradictory edits), the blueprint contains irreconcilable directives, causing severe regressions on some queries (high DR, low WCP).

### Mechanism 3: Risk-Aware Optimization Objective – Explicit Stability Metrics
- **Claim**: Integrating Worst-Case Performance (WCP), Downside Risk (DR), and Win-Tie Rate (WTR) safeguards against tail degradations and ensures robust, Pareto-safe improvements across the query set.
- **Mechanism**: Beyond expected gain `E[∆v]`, the system penalizes squared negative gains (DR), sets a safety lower bound (WCP), and measures non-regressive coverage (WTR). The goal maximizes visibility gain while simultaneously maximizing WCP/WTR and minimizing DR.
- **Core assumption**: A robust GEO solution must minimize harmful failures on any query, not just maximize average improvement; these three metrics collectively characterize cross-query stability.
- **Evidence anchors**: [abstract] "explicitly optimizing for risk-aware stability metrics..." ; [section 4.4] formal definitions and integrated optimization goal.
- **Break condition**: If stability metrics are de-emphasized during fusion (e.g., priority weighting ignores downside potential), the optimized document may exhibit high variance, with some queries suffering large visibility drops despite high mean.

## Architecture Onboarding

### Component map
Query Miner -> Request Generator -> (Prioritizer/Deduplicator -> Conflict Arbiter -> Blueprint Constructor) -> Blueprint Executor -> Optimized Document

### Critical path
Linear flow with feedback only within the Fusion Module: Document → Query Miner → Request Generator → (Fusion: Prioritize → Deduplicate → Resolve Conflicts → Construct Blueprint) → Blueprint Executor → Optimized Document. The blueprint is the central artifact encoding the global strategy.

### Design tradeoffs
- **Token Cost vs. Stability**: Diverge-then-converge uses ~10k tokens/document vs. ~2.5k for single-pass heuristics; cost is traded for explicitly managed cross-query stability (lower DR, higher WTR).
- **Model Reliance vs. Rule-Based robustness**: Conflict resolution uses LLM semantic reasoning instead of hard-coded rules; adds flexibility but introduces variance based on model judgment.
- **Query Coverage vs. Efficiency**: Larger query expansion `N` improves performance/stability but increases latency linearly; `N=5` is chosen as Pareto frontier.

### Failure signatures
1.  **High Downside Risk (DR) & Negative WCP**: Indicates blueprint likely prioritized a query subset, causing regressions on others. Could be poor conflict resolution (always selecting) or unrepresentative query mining.
2.  **Low Win-Tie Rate (WTR)**: Signals many queries experienced negative gains. Suggests fusion/blueprint failed to accommodate even basic needs of some queries.
3.  **Blueprint-Execution Mismatch**: If executor ignores blueprint directives (e.g., adds unrequested content), stability degrades. Shows as high variance (`VAR`) and inconsistent performance across runs.
4.  **Ablation Impact**: Removing Conflict Resolution causes largest drop in mean and tail metrics. If removal doesn't hurt much, fusion logic may be ineffective.

### First 3 experiments
1.  **Ablate Conflict Resolution**: Disable the conflict arbiter (use deduplicated list without arbitration). Expect significant DR increase and WTR drop, confirming its safety guardrail role.
2.  **Vary Query Expansion Size (N)**: Re-run with `N ∈ {1,3,5,7,9}`. Expect mean and stability metrics (DR, WCP) to improve with `N` but plateau after `N=5`, validating coverage-stability tradeoff.
3.  **Cross-Model Generalization**: Evaluate IF-GEO and baselines on Gemini-2.0-Flash. IF-GEO should maintain stability advantage (lower DR, higher WTR) even if mean scores shift, proving model-agnostic robustness.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question**: How does the computational overhead of IF-GEO's multi-stage pipeline trade off against its stability gains, and can efficiency be improved without sacrificing cross-query robustness?
- **Basis in paper**: [explicit] "Inference Cost" cited as primary limitation due to multiple LLM calls consuming significantly more tokens than single-pass baselines.
- **Why unresolved**: Token consumption is reported, but no cost-performance Pareto analysis or architectural alternatives (e.g., distillation, caching) are explored.
- **What evidence would resolve it**: Systematic experiments varying mined query count (`N`) against stability metrics (WCP, DR) and token cost, or evaluating a compressed fusion stage (e.g., smaller model) for comparable stability.

### Open Question 2
- **Question**: To what extent do performance and stability gains from conflict-aware instruction fusion transfer from LLM-simulated generative engines to real commercial systems like Perplexity AI or You.com?
- **Basis in paper**: [explicit] "Simulation Gap" limitation acknowledges reliance on LLM-simulated environments (GPT-4o-mini) that may not mirror commercial GEs.
- **Why unresolved**: All evaluations use closed-loop simulation where the same model acts as optimizer and simulator, risking overfitting to its specific behaviors and citation patterns.
- **What evidence would resolve it**: Re-running IF-GEO and baselines on a real-world generative search API or on a diverse set of simulated engines with varied architectures, then comparing relative stability improvements (WTR, DR).

### Open Question 3
- **Question**: How robust is IF-GEO's Global Revision Blueprint when the initial query mining step fails to capture a substantial portion of the true latent intent distribution?
- **Basis in paper**: [explicit] "Dependency on Query Discovery" limitation states blueprint quality hinges on representativeness of mined queries; misalignment due to incomplete coverage is a key risk.
- **Why unresolved**: Query mining uses LLM-generated queries based on parametric knowledge without validation against real search logs or user behavior. No quantification of robustness to missing or biased query subsets.
- **What evidence would resolve it**: Controlled experiments using ground-truth latent intent clusters (if available) or adversarially selected query subsets, measuring degradation in stability metrics (WCP, DR) as coverage is systematically reduced/skewed.

### Open Question 4
- **Question**: Is the priority-based conflict resolution strategy (selection vs. synthesis based on LLM-judged priority gaps) optimal, or could formal multi-objective or Pareto-based approaches yield better cross-query stability?
- **Basis in paper**: [inferred] Conflict resolution delegates arbitration to LLM using informal priority comparisons (§4.3.2); no comparison to alternative mechanisms (e.g., weighted averaging, explicit multi-objective optimization).
- **Why unresolved**: Ablations remove conflict resolution entirely but do not isolate effectiveness of the specific synthesis-vs-selection heuristic. LLM arbitration flexibility is touted but its optimality versus more rigid methods is unknown.
- **What evidence would resolve it**: Ablation comparing different conflict resolution strategies (e.g., strict priority thresholding, pairwise synthesis for all conflicts, a learned arbitration model) on stability metrics (WTR, DR), possibly with human evaluation of blueprint coherence and balance.

## Limitations
- **Prompt/Implementation Details**: Core LLM prompts (especially conflict resolution thresholds) are not precisely specified, introducing non-determinism.
- **Dataset Access**: GEO-Bench/RAID dataset files are not released, making exact replication of query conflict dynamics impossible.
- **Metric Fidelity**: Exact implementation of visibility metrics (PAWC, G-EVAL) may vary, affecting numerical comparisons.

## Confidence
- **Core Mechanism (Diverge-then-Converge)**: High. Supported by clear architecture, ablation studies (Table 3), and failure signature analysis.
- **Stability Metrics (WCP/DR/WTR)**: Medium. Novel definitions; no external validation, but internal correlations with mean gains are consistent (Table 1).
- **SOTA Performance Claims**: High. Results on GPT-4o-mini are explicitly reported and ablation confirms contributions, but independent verification is pending.
