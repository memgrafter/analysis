# CUDABench: Benchmarking LLMs for Text-to-CUDA Generation

## Quick Facts
- arXiv ID: 2603.02236
- Source URL: https://arxiv.org/abs/2603.02236
- Reference count: 18
- Primary result: LLMs achieve >92% compilation rates but functional correctness as low as 42.6%, and performance scores plateau around 40% of the theoretical peak.

## Executive Summary
CUDABench introduces the first comprehensive benchmark for evaluating large language models (LLMs) on generating CUDA kernels from natural language specifications. It addresses the lack of standardized evaluation and the difficulty of assessing both correctness and performance. The benchmark comprises 500 tasks across six domains, each at three difficulty levels, and employs a generative verification pipeline that checks compilation, functional correctness via execution against reference outputs, and hardware-independent performance using a roofline model. Evaluation of state-of-the-art LLMs reveals a significant gap: while compilation rates exceed 92%, functional correctness drops to as low as 42.6%, and performance scores hover around 40% of the theoretical peak, indicating poor hardware utilization and insufficient domain-specific algorithmic knowledge.

## Method Summary
CUDABench’s core evaluation framework uses a dataset (CUDABench-Set) of 500 tasks spanning six application domains, each with three difficulty levels (Level 1: detailed algorithmic guidance; Level 3: only task name) and five input scales (Tiny to Huge), yielding 1,500 unique prompts. For each generated kernel, an automated pipeline compiles the code with NVCC, executes it on random test data generated by provided data generators, compares outputs to reference implementations for functional correctness, and profiles correct kernels with NVIDIA Nsight Compute to measure achieved GFLOPs/s and data movement. A roofline model based on the target GPU’s specifications computes the attainable performance, and the Performance-Score is the ratio of achieved to attainable GFLOPs/s. The final CUDABench-Score aggregates compilation success, functional Pass@k, and normalized performance.

## Key Results
- LLMs exhibit high compilation success (>92%) but significantly lower functional correctness (as low as 42.6% on some tasks), indicating syntactic proficiency but semantic flaws.
- Performance scores plateau around 40% of theoretical peak across models, demonstrating failure to implement hardware-aware optimizations.
- Task difficulty and domain greatly impact performance, with Level 3 (concept retrieval) tasks and scientific simulation/finance domains showing the largest correctness drops, highlighting a lack of domain-specific algorithmic knowledge.

## Why This Works (Mechanism)
### Mechanism 1: Syntax–Semantics Gap
LLMs master CUDA syntax and API patterns from training data but generate code with logical errors (e.g., incorrect thread synchronization, memory boundary violations) that compile but fail at runtime. Evidence: high compilation rates (>92%) alongside lower functional correctness (down to 42.6%) and analysis confirming functional errors as the primary failure source. Core assumption: training corpora lack exposure to subtle parallel programming pitfalls. Break condition: functional correctness surpassing compilation rates or a compilation drop >15% with increased prompt complexity.

### Mechanism 2: Missing Hardware‑Aware Optimizations
LLM‑generated kernels consistently perform at ~40% of theoretical peak because they lack optimizations for GPU architecture (e.g., memory coalescing, shared memory tiling, warp divergence avoidance). The roofline model shows kernels operate far below attainable performance. Core assumption: LLMs do not internalize the relationship between arithmetic intensity, memory bandwidth, and compute capacity. Evidence: uniformly low Performance‑Score across models and authors’ observation that LLMs cannot implement critical hardware‑aware optimizations. Break condition: a model achieving >70% Performance‑Score across diverse kernel types without explicit hardware parameters.

### Mechanism 3: Domain‑Algorithm Retrieval Deficit
On Level 3 tasks (only task name provided) and in specialized domains (scientific simulation, finance), performance degrades sharply. LLMs fail to retrieve appropriate domain‑specific algorithms and CUDA implementation patterns from their weights. Core assumption: niche GPU programming patterns are underrepresented in pre‑training data. Evidence: functional correctness drop from Level 1 to Level 3 and failure rates up to 85% in certain domains. Break condition: Level 3 functional correctness within 10% of Level 1 across all domains.

## Foundational Learning
- **Roofline Performance Model**: Needed to interpret CUDABench‑Score, which normalizes performance across hardware. The model defines attainable performance based on arithmetic intensity and hardware limits (memory bandwidth vs. compute peak). Quick check: For a kernel with 100 GFLOPs and 500 GB data movement, arithmetic intensity = 0.2 FLOP/byte. If GPU has 1 TB/s bandwidth and 10 TFLOPS peak, the roofline intensity is 10 FLOP/byte, so kernel is memory‑bound.
- **CUDA Execution Hierarchy**: Essential for understanding correctness and optimization; kernels must map computations to threads/blocks, use shared memory, and synchronize properly. Quick check: To maximize coalescing for a 4096‑element vector addition, use one‑dimensional grid/block with contiguous threads accessing contiguous global memory; block size multiple of 32.
- **Benchmark Design for Hardware‑Independent Metrics**: CUDABench abstracts away raw hardware differences by normalizing to a theoretical peak. Execution time alone is hardware‑dependent; roofline‑based metric enables fair comparison. Quick check: Why is raw execution time a poor primary metric? Faster GPUs would always win, regardless of kernel efficiency.

## Architecture Onboarding
### Component Map
CUDABench‑Set (500 tasks × 3 difficulties × 5 scales) → Prompt Generator → LLM API → CUDA Code → Generative Verification Pipeline: Compiler (NVCC) → Executor (with test data) → Reference Output Comparator → Profiler (Nsight Compute) → Performance‑Score Calculator → CUDABench‑Score Aggregator.

### Critical Path
Generate code via LLM → compile → if compilation fails, stop (compilation failure) → else run with test data → compare outputs → if mismatch, stop (functional failure) → else profile → compute arithmetic intensity and attainable performance from roofline → compute Performance‑Score.

### Design Tradeoffs
- Hardware‑independent roofline vs. realism: Roofline abstracts GPU differences but relies on accurate FLOP/data movement counting; inaccurate profiling skews scores.
- Multiple input scales for depth: Increases robustness but requires reference implementations and data generators per scale, expanding dataset size.
- Difficulty levels: Provides fine‑grained skill analysis but demands careful prompt engineering to isolate syntactic, algorithmic, and retrieval abilities.

### Failure Signatures
- Compilation failure: Syntax errors, API misuse, missing includes.
- Functional inconsistency: Logic flaws, race conditions, out‑of‑bounds accesses; kernel runs but outputs disagree with reference.
- Low Performance‑Score (<40%): Kernel runs correctly but ignores optimizations (e.g., no shared memory, uncoalesced accesses, poor occupancy).

### First 3 Experiments
1. Reference validation: Run all 500 reference kernels through the pipeline to ensure validators and profilers yield correct scores (expected >90% Performance‑Score).
2. Baseline LLM test: Generate Level 1 tasks for a single model; anticipate high compilation (≳90%), moderate functional correctness (˜60%), and low performance (˜35%).
3. Difficulty sweep: Compare Level 1 vs. Level 3 Pass@1 for the same model; expect a significant functional correctness drop (e.g., 20% absolute), confirming retrieval deficit.

## Open Questions the Paper Calls Out
1. **How can prompting, sampling, and domain‑specific training be optimized to improve functional correctness and performance?** The paper suggests headroom but does not test techniques. Resolution requires systematic experiments with prompt variants (few‑shot, chain‑of‑thought), sampling parameters, and fine‑tuning on CUDA code.
2. **What semantic error types primarily cause functional failures?** The paper notes errors like synchronization and boundary issues but provides no taxonomy. Evidence: manual/automated classification of invalid kernels into categories (race conditions, out‑of‑bounds, etc.) across difficulties and domains.
3. **Which domain‑specific algorithmic primitives are most deficient?** Decline on Level 3 and in scientific/finance tasks suggests missing patterns (e.g., spectral methods, Monte Carlo). Evidence: fine‑grained analysis of low‑success task types combined with training‑data coverage assessment.
4. **What hardware‑aware optimizations are missing?** Uniformly low performance indicates failures in coalescing, tiling, occupancy tuning. Evidence: profiling generated kernels (Nsight Compute) to identify specific optimization gaps vs. reference kernels.

## Limitations
- Prompt formatting and difficulty‑level encoding details are not fully specified; repository inspection required.
- Reference kernel implementations and data generators are not described in depth, risking validator inconsistencies.
- Hardware configuration (GPU model, driver, CUDA version, system load) for Performance‑Score calculation is undocumented, impeding cross‑study normalization.

## Confidence
- **High**: LLMs have high compilation but low functional correctness due to syntactic mastery vs. semantic flaws.
- **High**: Level 3 difficulty exposes critical domain‑algorithm retrieval deficits, especially in scientific simulation and finance.
- **Medium**: Performance gap (~40% of peak) stems from missing hardware‑aware optimizations; evidence primarily from paper’s roofline analysis.
