# Perspectives - Interactive Document Clustering in the Discourse Analysis Tool Suite

## Quick Facts
- **arXiv ID:** 2602.15540
- **Source URL:** https://arxiv.org/abs/2602.15540
- **Reference count:** 16
- **Primary result:** An interactive clustering pipeline using LLM-driven document rewriting and instruction-based embeddings significantly improves coherence for aspect-focused analysis, with further gains from human-in-the-loop refinement and few-shot fine-tuning.

## Executive Summary
Digital Humanities researchers缺乏有效的工具来探索和构建大型、非结构化文档语料库，超越基本搜索。Perspectives 通过一个交互式、面向方面的文档聚类流水线解决了这一需求。其核心创新包括：使用LLM驱动的文档重写来引导初始聚类，采用基于指令的嵌入，并支持人在回路细化（合并/拆分/重分配集群）以及少样本微调。在九个不同数据集上的评估使用KNN准确率作为聚类连贯性的代理指标显示，指令调优嵌入在8/9个数据集上一致优于非指令基线。添加文档重写（摘要或关键词）在6/9个数据集上提高了准确性，最大提升达24.46分（产品分类）和17.55分（姿态检测）。使用用户接受的集群分配进行模型微调带来了进一步但较小的持续2-3分增益。

## Method Summary
该流水线处理用户提供的文档语料库和任务特定指令（例如“识别情感”）。可选的LLM重写步骤根据提示（例如“总结情感”）将原始文档转换为面向方面的表示（摘要或关键词）。然后使用指令调优的嵌入模型（multilingual-e5-large-instruct）生成嵌入。嵌入向量通过UMAP降维至2D，并使用HDBSCAN进行聚类以生成初始主题集群。用户通过交互式操作（合并、拆分、更改集群）进行细化。当用户接受集群分配时，这些文档对用于通过SetFit构建对比数据集，对嵌入模型进行少样本微调（LoRA适配器，随后端到端训练），然后重新嵌入和重新聚类整个语料库。评估在九个多样化的数据集（如亚马逊评论、Spotify歌词、20个新闻组等）上进行，主要指标为5折交叉验证的KNN准确率。

## Key Results
- 指令调优嵌入在8/9个数据集上一致优于非指令嵌入。
- 文档重写在6/9个数据集上提升准确性，产品分类任务最大增益为+24.46分。
- 使用用户接受的集群进行少样本微调带来持续但较小的2-3分增益。

## Why This Works (Mechanism)

### Mechanism 1: Steering via LLM-Driven Document Rewriting
- **Claim:** Steering clustering via LLM-driven document rewriting can improve cluster coherence for aspect-focused analysis.
- **Mechanism:** User-provided prompts (e.g., "summarize sentiment") direct an LLM to rewrite raw documents into condensed, aspect-centric representations (summaries or keyphrases). These rewritten texts are then embedded, effectively filtering out irrelevant information and amplifying signals related to the user's analytical lens.
- **Core assumption:** Condensing documents to aspect-focused content reduces semantic noise and improves the quality of vector representations for the target clustering task.
- **Evidence anchors:**
  - [abstract] "steering initial clustering via LLM-driven document rewriting"
  - [section 4] "First, we employ alternative document representations, in which an LLM rewrites documents based on a prompt, thereby modifying the content for clustering."
  - [corpus] The experimental results show improvement in 6 of 9 datasets (e.g., +24.46 accuracy for product categorization), providing empirical support. However, corpus evidence is dataset-dependent and not universally positive.
- **Break condition:** If the LLM's rewriting prompt is poorly aligned with the true underlying task or distorts key information, the resulting embeddings may misrepresent documents, harming cluster quality.

### Mechanism 2: Instruction-Tuned Embeddings
- **Claim:** Using instruction-tuned embedding models consistently yields better aspect-oriented clustering than non-instruction models.
- **Mechanism:** An instruction-tuned model (e.g., "Identify the topic") receives both the document text and a task-specific instruction. This guides the embedding generation process to encode semantic properties relevant to the instruction, creating a representation space where documents answering the same instruction are closer together.
- **Core assumption:** Instruction tuning aligns the embedding model's internal representations with human-interpretable tasks, making the geometry of the embedding space more suitable for the user's analytical goal.
- **Evidence anchors:**
  - [abstract] "instruction-based embeddings"
  - [section 5.5] "embeddings generated with instructions (+inst) outperform those without in 8 out of 9 datasets."
  - [corpus] The tabulated results show clear, consistent improvements across diverse tasks (emotion, genre, product, etc.). The model chosen (multilingual-e5-large-instruct) was selected based on its strong MTEB benchmark performance.
- **Break condition:** If the provided instruction is ambiguous, contradictory, or outside the model's fine-tuning distribution, the instruction following may fail, producing embeddings no better than or worse than non-instruction baselines.

### Mechanism 3: Few-Shot Fine-Tuning with User Feedback
- **Claim:** Few-shot fine-tuning of the embedding model with user-accepted cluster assignments further aligns the embedding space with user intent, yielding modest but consistent gains.
- **Mechanism:** When users accept a cluster as correct (i.e., validate a set of documents belonging to the same intended category), these documents become positive pairs. A contrastive loss function (via SetFit) fine-tunes the embedding model to pull embeddings of accepted pairs closer and push others apart. This subtly reshapes the embedding space to reflect the user's validated categorizations.
- **Core assumption:** A small number of user-validated examples per cluster is sufficient to adjust the embedding model's parameters to better capture the specific semantic boundaries defined by the user.
- **Evidence anchors:**
  - [abstract] "fine-tuning... yielded further, though smaller, consistent gains of 2-3 points."
  - [section 4] "These labeled examples are used to create a contrastive dataset to fine-tune the embedding model... pulling similar documents closer and pushing dissimilar ones apart."
  - [section 5.5] The few-shot results table shows incremental, cross-dataset improvements (e.g., bias dataset: 52.53 -> 54.09 with 16-shot).
- **Break condition:** If the user's accepted examples are unrepresentative, noisy, or too few to capture cluster variance, fine-tuning may overfit or introduce bias, degrading performance on unseen documents.

## Foundational Learning
- **Concept: Instruction-Tuned Embeddings**
  - **Why needed here:** The system's core steerability relies on transforming a generic text embedding model into an aspect-oriented one via natural language instructions. Understanding how instructions modulate embedding space is key to predicting system behavior.
  - **Quick check question:** How would the embedding for the sentence "The movie was great" differ if the instruction was "Identify the sentiment" versus "Identify the movie genre," and why would this matter for clustering?
- **Concept: Human-in-the-Loop (HITL) Refinement Operations**
  - **Why needed here:** Clustering is a starting point; the tool's value lies in the interactive manipulation (merge/split/reassign) that translates user expertise into system updates. The ontology of these operations defines the user's control vocabulary.
  - **Quick check question:** What is the semantic difference between using "Split Cluster" versus "Add Cluster" on a set of documents you believe contain two subtopics, and how does each operation trigger different system recomputations?
- **Concept: Density-Based Clustering (HDBSCAN) for Topic Discovery**
  - **Why needed here:** The pipeline uses HDBSCAN, which discovers clusters of varying density and identifies outliers. This choice impacts how topics are initially formed and how operations like "Split Cluster" function on a sub-space of documents.
  - **Quick check question:** Why might HDBSCAN be preferred over k-means for an exploratory DH workflow where the number of topics is unknown and outlier/edge-case documents are common?

## Architecture Onboarding
- **Component map:** React Frontend (Plotly.js visualization) -> FastAPI Backend (corpus state, task queue) -> RQ GPU Workers (LLM rewriting, embedding, UMAP, HDBSCAN, SetFit fine-tuning) -> DATS Data Store (corpus storage, tagged outputs)
- **Critical path:** User uploads corpus -> Chooses instruction & optional rewrite prompt -> System: rewrites (if any) -> embeds with instruction -> reduces dims (UMAP) -> clusters (HDBSCAN) -> serves map. **User refinement loop:** User performs operation (e.g., merge) -> System recalculates cluster representations (keywords, centroids) on affected subset -> updates map. **Model update path:** User accepts clusters -> system creates contrastive pairs -> fine-tunes embedding model -> re-embeds entire corpus -> re-clusters -> updates map.
- **Design tradeoffs:**
  - **Local vs. Cloud Models:** Chose local, open-licensed models (Gemma 3, multilingual-e5) for privacy/deployability, trading off potential state-of-the-art accuracy of larger proprietary models.
  - **Response Time vs. Fidelity:** Initial document rewriting is slow (LLM batch inference) but one-time. Subsequent refinement operations are fast (operate on cluster centroids/representatives only). Fine-tuning requires full re-embedding, causing a disruptive "mental map reset" acknowledged as a limitation.
  - **Generality vs. Performance:** Mandatory instruction improves average performance but may constrain use cases where a generic "find similar documents" view is desired.
- **Failure signatures:**
  - **Visualization:** Map becomes a single large blob or hundreds of tiny isolated points → indicates embedding space has poor structure (bad instruction/rewrite) or HDBSCAN parameters are off.
  - **Refinement:** "Change Cluster" or "Merge" operations produce nonsensical new cluster names/keywords → indicates representative document selection (cosine similarity to centroid) failed, likely due to a degenerate embedding space.
  - **Fine-tuning:** Post-fine-tuning map looks completely different and user loses orientation → inherent to full re-embedding; the "refinement history" timeline is a mitigation in development.
- **First 3 experiments:**
  1. **Baseline sanity check:** Run a small test corpus (e.g., 100 docs from 20 Newsgroups) with `text` (no instruction, no rewrite) and `text+inst`. Verify the KNN accuracy difference matches expected ~5-10 point gain and that clusters on the map are visibly more coherent with instruction.
  2. **Document rewriting toggle:** For a dataset where rewriting helped (e.g., Amazon Reviews for product), run `text+inst` vs. `summary+inst`. Visually inspect the map: do summary-based clusters align better with known product categories? Check if LLM-generated summaries are actually aspect-focused (e.g., mention product features, not just sentiment).
  3. **HITL operation validation:** On the same map, perform a "Split Cluster" on a visually dense, heterogeneous cluster. Verify the system: (a) only reclusters the selected subset, (b) generates new meaningful keywords/names for sub-clusters, (c) updates the map without breaking other clusters.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can the disruption of users' spatial mental maps during model fine-tuning be effectively mitigated to maintain continuity in the interactive exploration workflow?
  - **Basis in paper:** The "Limitations" section states that the Refine Model operation requires re-embedding and re-clustering of the entire dataset, resulting in the loss of spatial understanding and disruption of the user’s mental map. A planned "refinement history component" is a proposed mitigation.
  - **Why unresolved:** The core issue—that a fundamental model update globally alters the embedding space and thus the 2D map—remains. The effectiveness of the history feature in preserving a coherent sense-making process is an open empirical question.
  - **What evidence would resolve it:** A user study comparing the current "reset" fine-tuning behavior against the new history feature, measuring task completion time, user-reported confusion, and ability to track conceptual changes across refinement steps.
- **Open Question 2:** To what extent does the KNN accuracy metric used in the evaluation serve as a valid proxy for the actual utility and coherence of clusters in real-world Digital Humanities research tasks?
  - **Basis in paper:** The paper acknowledges KNN accuracy is used as a "proxy for end-to-end evaluation" and "mimics user behavior," but it is not a direct evaluation of thematic quality or research utility.
  - **Why unresolved:** High KNN accuracy indicates documents of the same ground-truth label are nearby, but it does not guarantee clusters are thematically coherent, interpretable, or useful for a DH scholar's specific research question. The metric may favor easily separable label structures over meaningful topical divisions.
  - **What evidence would resolve it:** Correlational studies where KNN scores are compared against expert DH researcher ratings of cluster quality (coherence, novelty, utility) on the same system outputs, or a task-based evaluation measuring researcher success against KNN scores.
- **Open Question 3:** How robust and generalizable are the reported performance gains from document rewriting (summaries/keyphrases) across a wider range of LLMs, prompt engineering strategies, and document genres beyond the nine tested datasets?
  - **Basis in paper:** The evaluation is limited to one LLM (Gemma 3 27B) and two prompt types (summary/keyphrase). The "Limitations" note that experiments did not involve extensive prompt engineering and exploring other prompts could lead to further improvements. The dataset-dependent results (beneficial in 6/9 cases) suggest the strategy's efficacy is not universal.
  - **Why unresolved:** The interaction between LLM capability, prompt design, and document type is complex. The boundary conditions for when rewriting helps versus when it harms (e.g., by losing nuance) are unclear.
  - **What evidence would resolve it:** A systematic ablation study varying: multiple open-source and commercial LLMs of different sizes, a diverse set of rewriting prompts (e.g., "extract named entities," "paraphrase for topic"), and a broader, more diverse corpus of DH-relevant text types. Analysis would identify which (LLM, prompt, genre) combinations yield significant improvements vs. degradation.
- **Open Question 4:** Can the few-shot fine-tuning mechanism be made less sensitive to the specific selection of training examples and more sample-efficient, to reduce the user burden and increase reliability in low-data regimes common in DH?
  - **Basis in paper:** The paper notes the few-shot approach is "sensitive to the selection of training samples" and that "an optimal combination of training examples may not have been discovered." While 10 random runs were averaged, gains were modest (2-3 points). The "Limitations" also state that incorporating more labeled examples could further enhance performance, implying a sample-efficiency problem.
  - **Why unresolved:** Requiring users to provide a set of "accepted" cluster assignments that are representative and balanced enough to improve the embedding space is a high burden. The sensitivity suggests the model can be skewed by poor or unrepresentative seed examples, risking reinforcing user bias or creating brittle topic representations.
  - **What evidence would resolve it:** Experiments comparing the current SetFit+LoRA approach against other few-shot paradigms (e.g., prompt-tuning, clustering-based active learning to select informative examples, using refinement history's sequence of edits as a richer signal). Success measured by achieving comparable/better KNN gains with fewer, less carefully selected examples and lower variance across random training subsets.

## Limitations
- Ambiguity in selecting the "best zero-shot configuration" per dataset for fine-tuning, as inferred from Table 1 but not explicitly stated.
- Underspecified few-shot sampling strategy (stratification, seed, split) and missing details of the SetFit second-stage classification head architecture.
- No reported random seeds for stochastic UMAP and HDBSCAN, risking irreproducibility of cluster assignments and KNN scores.

## Confidence
- **Instruction-tuned embeddings:** High (consistent 8/9 dataset gains, strong baseline).
- **LLM rewriting:** Medium (improved 6/9, gains large but task-dependent; prompt alignment critical).
- **Few-shot fine-tuning:** Medium (small consistent 2-3 pt gains; robustness to sample variance unknown).

## Next Checks
1. **Zero-shot config clarity:** Cross-reference Table 1 results with fine-tuning choices to infer selection logic; if ambiguous, run ablation comparing candidate variants (e.g., summary+inst vs keyphrases+inst) on 2-3 datasets.
2. **Few-shot stability:** Replicate fine-tuning with stratified sampling (ensuring all classes per shot) across 20 random seeds; report mean/variance of accuracy gains vs. paper’s 10-run average.
3. **Stochasticity control:** Fix UMAP `random_state` and HDBSCAN seeds; measure variance in KNN accuracy across 5 runs for one dataset (e.g., Amazon). If variance >1 pt, adopt seeds in full replication.
