# QUIETT: Query-Independent Table Transformation for Robust Reasoning

## Quick Facts
- **arXiv ID:** 2602.20017  
- **Source URL:** https://arxiv.org/abs/2602.20017  
- **Reference count:** 36  
- **Primary result:** QUIETT consistently improves F1 scores across four benchmarks, peaking at 84.41 (Gemini 2.5 on HiTab) and gaining 4–8 points on a challenge set of structurally diverse unseen questions.

## Executive Summary
Real-world tables are often messy, with irregular schemas, heterogeneous formats, and implicit structure that undermine reliable reasoning by language models. Existing query-dependent solutions entangle cleanup with reasoning, limiting their ability to generalize to new questions or models. QUIETT introduces a query-independent transformation framework that preprocesses any raw table into a single lossless, SQL-ready canonical representation before any queries are observed. This canonical table is then reused for downstream question answering, disentangling structural cleanup from logical reasoning and enabling robust, model-agnostic performance.

## Method Summary
QUIETT operates in three pipeline stages applied once per raw table. First, an **Issue Prober** generates synthetic probe queries from the table’s markdown representation to surface intrinsic structural deficiencies. Second, a **Plan Generator** consumes the raw table and the identified issues to produce a JSON transformation plan—a fixed sequence of deterministic operations (e.g., `parse_date_text`, `extract_regex`) with declared inputs, outputs, and a target schema. Third, a **Code Executor** converts this plan into Python code (using a restricted operator vocabulary) and executes it on a pandas DataFrame, enforcing row count invariance and lossless preservation by adding auxiliary snapshot columns whenever necessary. The resulting canonical table is cached and fed to any fixed downstream QA model, which answers test queries without further modification.

## Key Results
- Peak F1 of 84.41 on HiTab using Gemini 2.5.  
- Consistent gains of 4–8 F1 points on a manually constructed challenge set of structurally diverse, unseen questions.  
- Positive table-level improvements on 57–60% of web and hierarchical tables, enabling smaller QA models to perform effectively.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Preprocessing tables into a canonical, SQL-ready representation before query time disentangles structural cleanup from reasoning, enabling generalization across unseen queries.  
- **Mechanism:** QUIETT applies a fixed sequence of deterministic transformations to a raw table `T_raw` to produce a single canonical table `T_C`. This `T_C` is reused unchanged for any downstream query `q`, rather than performing query-specific restructuring. The transformation is guided by synthetic probe queries that only expose table-intrinsic deficiencies, not anticipated user questions.  
- **Core assumption:** A lossless, regularized table representation reduces the semantic and structural burden on the downstream QA model, making its reasoning more robust and less dependent on the specific query wording or model scale.  
- **Evidence anchors:** [abstract]: "preprocesses raw tables into a single SQL-ready canonical representation before any queries are observed"; [section 2.1]: "The transformation function `f` is independent of any `q∈ Q`" and "Each table is transformed exactly once into a single canonical representation that can be reused"; corpus: neighbor papers (e.g., *Tree-of-Table*, *MMTBENCH*) also investigate table structure challenges, but QUIETT's explicit *query-independent* premise is a differentiating architectural claim.  
- **Break condition:** If downstream queries require information that was lost during the supposedly "lossless" transformation (e.g., over-aggressive normalization that discards original semi-structured context), the reuse benefit collapses for those queries.

### Mechanism 2
- **Claim:** Lossless preservation of raw information via auxiliary snapshot columns ensures that the canonical representation does not constrain the space of answerable queries.  
- **Mechanism:** During transformation, QUIETT retains original raw values in dedicated snapshot columns (e.g., `Name_raw`) whenever an operation would otherwise be destructive (e.g., splitting a compound value). This allows recovery of any original element while still presenting a clean, queryable surface.  
- **Core assumption:** Downstream QA models can effectively ignore or leverage snapshot columns as needed. The presence of raw snapshots does not themselves introduce confusion that degrades performance.  
- **Evidence anchors:** [section 3]: "preserving all original information through lossless raw snapshots" and "auxiliary snapshot columns are introduced only when necessary to ensure losslessness"; [section 5.1]: "QUIETT preserves information by construction. Auxiliary snapshot columns are introduced only when necessary... required for approximately 13% of WebTables"; corpus: *NormTab* (a direct baseline) performs normalization but does not explicitly guarantee losslessness via snapshots, which QUIETT cites as a key differentiator.  
- **Break condition:** If the snapshot policy is implemented incorrectly (e.g., snapshots not truly complete, or snapshot column names/ semantics confuse the QA model), the lossless guarantee fails, potentially harming performance on queries needing original format.

### Mechanism 3
- **Claim:** A fixed, deterministic transformation plan executed via code generation ensures reproducibility and auditability, separating symbolic planning from execution.  
- **Mechanism:** QUIETT generates a structured transformation plan `π` (a sequence of operator invocations with declared inputs/outputs). This plan is then converted into deterministic Python code that is executed on the raw table. The plan is not conditioned on the downstream query and is cached.  
- **Core assumption:** LLM-generated code, when constrained to a known operator vocabulary and executed in a controlled environment, will faithfully implement the plan's declared semantics without introducing unintended side effects or non-determinism.  
- **Evidence anchors:** [section 3]: "deterministically generates executable code in Python where each code block corresponds to a specific operation" and "executor enforces plan faithfulness by disallowing implicit control flow"; [section 3]: "inspired by design principle of separating symbolic planning from deterministic execution, as advocated in Weaver"; corpus: *DataMorpher* and *RelationalCoder* also use LLM-based code generation for transformation but are often query-coupled; QUIETT's plan-execute split is a specific architectural choice for query-independence.  
- **Break condition:** If the code generation step introduces bugs, diverges from the plan's declared semantics, or the executor environment is non-deterministic (e.g., unstable sorting), the canonical table `T_C` becomes unreliable, undermining all downstream QA.

## Foundational Learning
- **Concept: Canonical Schema Normalization**  
  *Why needed here:* Real-world tables have inconsistent column names, mixed data types in columns, and heterogeneous value formats (e.g., dates as "March 4, 1789" vs "1789-03-04"). QUIETT must resolve these to a uniform, SQL-typed schema (e.g., a single `date` column with ISO format) to enable reliable symbolic querying.  
  *Quick check:* Given a column with values `["5 km", "300 m", "1.2 miles"]`, what derived columns would QUIETT likely create to achieve a canonical representation, and what would happen to the original column?

- **Concept: Provenance-Preserving Transformation**  
  *Why needed here:* To satisfy the "lossless" constraint, QUIETT cannot discard original information. This requires understanding when to keep an original column versus derive a new one, and when to add a snapshot column to store the raw value without duplicating information.  
  *Quick check:* For a column `Name` containing `"John Smith (USA)"`, if QUIETT creates `first_name="John"` and `last_name="Smith"`, under what condition would it also keep the original `Name` column versus replacing it?

- **Concept: Query-Independent Planning**  
  *Why needed here:* The entire premise of QUIETT is that transformation must not peek at downstream queries. The planner must use only table-intrinsic signals (from synthetic probes) to decide *all* necessary normalizations and enrichments for general-purpose querying.  
  *Quick check:* If a table has two date columns (`Start` and `End`) but the actual table logic implies a single date range, what synthetic probe question might trigger QUIETT to create a derived `duration_days` column, even if no current downstream query asks for duration?

## Architecture Onboarding
- **Component map:**  
  1. Issue Prober – generates synthetic queries from the raw markdown table.  
  2. Plan Generator – takes raw table + issues → outputs a JSON plan of operations.  
  3. Code Executor – converts the JSON plan into Python code (Pandas operations), executes it, and produces the canonical table `T_C` with snapshot columns if needed.  
  4. QA Consumer – any fixed downstream model/prompt (e.g., CoT+SQL) that consumes `T_C` to answer test queries; this component is *not* modified by QUIETT.

- **Critical path:** Raw Table → (Issue Prober → Plan Generator) → Code Executor → Canonical Table `T_C` → (QA Consumer × N queries). The parentheses denote stages run once per table; `T_C` is cached and reused.

- **Design tradeoffs:**  
  1. **Determinism vs. Flexibility:** Enforcing a strict operator vocabulary and fixed row count ensures reproducibility but may limit handling of extremely exotic table structures, requiring a "custom" operator escape hatch.  
  2. **Losslessness vs. Redundancy:** The "smart lossless" principle tries to avoid keeping columns that are fully captured by derived ones. Overly conservative retention bloats `T_C`; overly aggressive dropping breaks losslessness.  
  3. **Single-Table Focus:** The pipeline processes one table at a time. Multi-table reasoning (joins) is left to the downstream QA model, which now operates on a set of individually clean tables.

- **Failure signatures:**  
  1. Row count mismatch in output `T_C` (violates "ROW COUNT MUST STAY THE SAME" rule).  
  2. Missing `_row_id` or unstable row ordering, breaking reproducibility for downstream querying.  
  3. Snapshot columns not added where required, leading to irreversible information loss.  
  4. Plan contains `explode_entities` (explicitly forbidden), indicating a planner failure to maintain row count.  
  5. Canonical table not SQL-ready (e.g., dates still as mixed strings, no primary key) despite transformation.  
  6. Column names in plan `reads` do not exist in current DataFrame.  
  7. Code generation produces non-executable Python or references undefined variables.

- **First 3 experiments:**  
  1. **Unit Transformation Test:** Take a single raw table with a known issue (e.g., a `Date` column with `"March 4, 1789"`). Run QUIETT and verify `T_C` has a `date_parsed` column with ISO format `1789-03-04` and the original column is either retained as a snapshot or dropped only if fully captured.  
  2. **Losslessness Audit:** For a table with complex cell values (e.g., `"John Smith (USA), PhD"`), after transformation, write a script to confirm that the concatenation of derived columns (`first_name`, `last_name`, `country`, `title`) can reconstruct the original value (or that the original `Name_raw` snapshot exists).  
  3. **Cross-Model Reuse Validation:** Use the *same* `T_C` from a WikiTQ table with two different QA models (e.g., Gemini 2.0 CoT and DeepSeek-V3.1 PoT). Verify that both models receive the identical `T_C` input and that performance gains (vs. raw table) are observable for both, confirming the "reuse" property.

## Limitations
- JSON schemas for issue and plan outputs are not fully defined; implementation must infer fields from examples.  
- QA stage details (e.g., whether generated SQL plans are executed) remain ambiguous, affecting reproduction fidelity.  
- Answer normalization rules are underspecified, potentially leading to F1 score discrepancies.

## Confidence
- Disentanglement: Medium  
- Losslessness: Medium  
- Deterministic execution: High  
- Empirical results: High
