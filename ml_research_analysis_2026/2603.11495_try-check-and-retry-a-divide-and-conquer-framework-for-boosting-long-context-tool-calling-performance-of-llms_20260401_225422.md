# Try, Check and Retry: A Divide-and-Conquer Framework for Boosting Long-context Tool-Calling Performance of LLMs

## Quick Facts
- **arXiv ID:** 2603.11495
- **Source URL:** https://arxiv.org/abs/2603.11495
- **Reference count:** 31
- **Primary result:** Tool-DC boosts tool-calling accuracy under noisy long-context conditions, with TF achieving up to +25.10% average gain and TB surpassing leading proprietary models on standard benchmarks.

## Executive Summary
Tool-calling performance in large language models degrades significantly when faced with many candidate tools, primarily due to increased noise and context length. This paper introduces Tool-DC, a divide-and-conquer framework that employs a "Try-Check-Retry" paradigm. The training-free variant (TF) splits tools into strategic groups, performs parallel local inference, validates outputs against schema constraints, and aggregates valid results for a final decision. The training-based variant (TB) fine-tunes models on synthesized chain-of-thought data to internalize this process. Evaluations on extended benchmarks show substantial improvements across multiple model families, with TB even exceeding the performance of models like OpenAI o3 and Claude-Haiku-4.5.

## Method Summary
Tool-DC addresses the long-context tool-calling problem by decomposing a large, noisy candidate set into smaller, manageable subspaces. The TF pipeline first retrieves a top-K set of tools and creates parallel groups around anchor tools, mixing them with distractors. Each group is processed independently (Try). A rule-based validator then checks each output for syntactic correctness against the tool schemas (Check). Finally, valid tool definitions are aggregated and presented to the model for a final re-evaluation (Retry). The TB variant generates chain-of-thought data using the TF pipeline and fine-tunes a model to perform the entire reasoning in a single forward pass, eliminating the need for explicit multi-stage inference at test time.

## Key Results
- TF yields up to +25.10% average accuracy gain on extended BFCL/ACEBench (e.g., Qwen2.5-1.5B improves from 29.48% to 54.58%).
- TB elevates Qwen2.5-7B to 83.16% on BFCL, surpassing OpenAI o3 (77.58%) and Claude-Haiku-4.5 (82.59%).
- Improvements are consistent across Qwen, Llama, and Gemma model families and remain robust as the number of candidate tools increases.

## Why This Works (Mechanism)

### Mechanism 1  
- **Claim:** Splitting the candidate tool set into smaller, strategically grouped subspaces reduces reasoning difficulty and mitigates noise interference.  
- **Mechanism:** The *Try* stage employs *Strategic Anchor Grouping*: retrieve top‑K tools (`T_top`) via BM25, keep them as a dedicated group (`S_0`), and create K additional groups by taking each anchor from `T_top` and adding disjoint distractors from the tail set (`T_tail`). This yields parallel subspaces `{S_0, S_1, ..., S_K}`. Each group is processed independently by the LLM for local inference, producing a tool invocation or `null`.  
- **Core assumption:** LLMs make more accurate decisions when presented with a small, semantically focused candidate set (around an anchor), even if some relevant tools are not in the same group; multiple groups ensure coverage of tools missed by retrieval.  
- **Evidence anchors:**  
  - [abstract]: “split into parallel groups for local inference”  
  - [section]: Section 3.2.1 details the grouping and parallel inference.  
  - [corpus]: Corpus contains related divide‑and‑conquer works for long contexts but none specifically target tool‑calling; indirect support only.  
- **Break condition:** If the golden tool is absent from all groups (neither in `T_top` nor included in any `T_tail` subset), no local inference can recover it. The design mitigates this by preserving `S_0 = T_top`.

### Mechanism 2  
- **Claim:** Rule-based schema validation effectively filters out invalid tool calls, improving candidate quality for subsequent refinement.  
- **Mechanism:** The *Check* stage applies a *Consistency Validator* `F(·)` that verifies each local output `o_j` against three constraints: (1) function name exists in the tool set, (2) argument keys match required parameters, (3) argument values adhere to defined data types. Valid outputs form set `V`.  
- **Core assumption:** LLM hallucinations in tool‑calling often manifest as syntactic/structural violations (e.g., wrong name, missing args, type mismatches) that deterministic rules can catch.  
- **Evidence anchors:**  
  - [abstract]: “outputs are validated via schema constraints”  
  - [section]: Section 3.2.2 defines the three validation dimensions.  
  - [corpus:** Not directly addressed; corpus focuses on long‑context reasoning, not tool validation.  
- **Break condition:** Overly strict or incomplete schemas may incorrectly filter valid calls; semantic errors (e.g., logically flawed arguments that satisfy schema) remain undetected.

### Mechanism 3  
- **Claim:** Aggregating validated candidates and prompting the LLM to re‑evaluate leverages self‑reflection to produce the final correct tool invocation.  
- **Mechanism:** The *Retry* stage constructs a refined candidate set `T_retry` from the tool definitions in the valid set `V`. The LLM then processes the original query with `T_retry` to generate the final call `y*`.  
- **Core assumption:** After filtering, the candidate set is cleaner and more relevant; the LLM can better focus and correct earlier mistakes when reconsidering only plausible tools.  
- **Evidence anchors:**  
  - [abstract]: “valid results are aggregated for a final decision”  
  - [section]: Section 3.2.3 describes the aggregation and final decision.  
  - [corpus:** Corpus contains self‑reflection works but not in this specific pipeline.  
- **Break condition:** If `V` excludes the golden tool (filtered out or never generated), Retry cannot recover it; weak self‑reflection may still pick a wrong valid candidate.

## Architecture Onboarding

- **Component map:**  
  - **Input:** User query `q`, tool library `T` (N candidates).  
  - **TF pipeline:** Strategic anchor grouping → parallel local inference via model `M` per group → outputs `o_j` → rule-based validator `F` filters `o_j` → valid set `V` → build `T_retry` from `V` → final invocation `y* = M(q, T_retry)`  
  - **TB pipeline:** CoT data generation (using TF) → fine-tune `M` on `D_CoT` → inference (single forward pass).

- **Critical path:**  
  - **TF:** Try (parallel groups) → Check → Retry (sequential).  
  - **TB:** CoT generation (using TF) → Fine‑tuning → Inference (single forward).

- **Design tradeoffs:**  
  - **TF vs TB:** TF is training‑free and flexible but incurs multiple forward passes (latency) and depends on a retriever. TB yields single‑pass efficiency but requires training data/compute and may overfit.  
  - **Group count `K`:** Smaller `K` reduces context per group but risks missing relevant tools; larger `K` increases overhead. Paper finds `K=5` optimal.  
  - **Retriever dependence:** TF uses BM25 by default; poor retrieval hurts, but grouping gives tail tools a second chance.

- **Failure signatures:**  
  - Large performance drop on Extended Setting (20 tools) → inability to handle noise.  
  - Removing *Check* causes significant accuracy loss (ablation Table 3: 52.24 % vs full 64.77 %).  
  - If `V` contains no golden tool, *Retry* fails catastrophically (Table 3: removal of *Retry* collapses to ~5 %).  
  - For TB: poor generalization on new tool sets suggests CoT data lacks diversity.

- **First 3 experiments:**  
  1. **Baseline replication:** Implement TF (BM25, `K=5`) for Qwen2.5‑1.5B on BFCL Extended; expect ~54.58 % vs All_Funs 29.48 %.  
  2. **Ablation:** Disable *Check* stage; expect accuracy drop to ~52 % (Table 3).  
  3. **Sensitivity analysis:** Vary `K` from 1 to 8 on Extended BFCL; expect peak around `K=5` (Figure 6).

## Open Questions the Paper Calls Out
- **Question 1:** How can we construct a more diverse and noisy training dataset for Tool-DC (TB) to better simulate real-world long-context tool-calling scenarios?  
  *Basis:* [explicit] "we only used xlam-function-calling-60k as the seed dataset... it lacks sufficient diversity and contains a limited number of tools in the context... construct a more diverse training set with massive and noisy context"  
  *Why unresolved:* Current training data may not prepare models for the scale and noise of real applications, limiting generalizability.

- **Question 2:** Can Tool-DC's divide-and-conquer approach be successfully applied to multi-step nested tool-calling where outputs of one tool feed into subsequent calls?  
  *Basis:* [explicit] "our current experiments are limited to single-step tool-calling tasks... future work could extend our method to more complex tool-calling settings."  
  *Why unresolved:* The "Try-Check-Retry" paradigm assumes a single invocation decision; multi-step introduces sequential dependencies and state management.

- **Question 3:** How robust is Tool-DC to failures in the initial tool retrieval step, and can we reduce reliance on a high-quality retriever?  
  *Basis:* [inferred] Tool-DC (TF) uses BM25 to retrieve Top-K tools for grouping. Appendix A.6 shows variation across retrievers, but the framework's sensitivity to retrieval accuracy is not fully analyzed.  
  *Why unresolved:* In real-world deployments, retrievers may be imperfect or unavailable; understanding performance under retrieval noise is critical.

- **Question 4:** Can the Check stage's rule-based schema validation be replaced or augmented with a learned validator to handle more complex or unseen tool schemas?  
  *Basis:* [inferred] The Check stage uses strict, predefined schema constraints (function name, argument keys, data types). This may not scale to schemas with nuanced constraints not easily expressible as rules.  
  *Why unresolved:* Real-world tools often have intricate parameter dependencies (e.g., mutual exclusivity, conditional requirements) that simple rules might miss or reject incorrectly.

- **Question 5:** Does Tool-DC (TF)'s inference overhead (multiple forward passes) become prohibitive for large-scale deployment, and can we achieve similar gains with a single-pass architecture?  
  *Basis:* [inferred] Tool-DC (TF) runs parallel inferences per group then a retry pass. The paper notes "inference latency" but doesn't provide a detailed cost-benefit analysis at scale.  
  *Why unresolved:* For production systems with strict latency budgets, the extra passes may offset accuracy gains; a more efficient single-pass method could be preferable.

## Limitations
- Generalization beyond benchmark tool sets to real-world applications remains untested.
- TF depends on BM25 retrieval quality; sensitivity to retrieval accuracy is not fully characterized.
- TF's parallel inference overhead may be prohibitive for latency-sensitive deployments; TB requires expensive fine-tuning and diverse training data.
