# Compiling Temporal Numeric Planning into Discrete PDDL+: Extended Version

## Quick Facts
- **arXiv ID:** 2603.12188
- **Source URL:** https://arxiv.org/abs/2603.12188
- **Reference count:** 6
- **Primary result:** A polynomial compilation from PDDL 2.1 durative actions to PDDL+ using lock predicates; ENHSP-WA solves 67/80 temporal numeric instances, outperforming ARIES, OPTIC, and TAMER.

## Executive Summary
The paper presents a practical polynomial compilation from temporal planning with durative actions (PDDL 2.1 Level 3) to PDDL+. The translation encodes each durative action into a start action, a process that increments a clock fluent, and an end mechanism (action or event). Auxiliary predicates (locks) enforce non-interference and non-self-overlapping semantics, mirroring PDDL 2.1's "no moving targets" rule. The compilation is proven sound and complete, preserving plan length up to a constant factor. Experiments on four domains with numeric fluents show that using the PDDL+ planner ENHSP with the compilation solves more instances and runs faster than state-of-the-art temporal planners, demonstrating its effectiveness for hard temporal numeric problems.

## Method Summary
The core method is a polynomial transformation that takes a PDDL 2.1 (Level 3) problem and produces an equivalent PDDL+ domain. For each durative action, the compiler generates a start action (`¯a⊢`), a process (`¯p_a`) that increments a clock fluent `c_a` each time step, and either an end action (`¯a⊣` for variable duration) or an end event (`¯e⊣_a` for fixed duration). Additional boolean fluents `lock_f` (split into `rl_f`, `al_f`, `il_f`) encode read/write/assign conflicts. A universal event `¯eE` resets all locks when time advances (via `gc>0`), ensuring that simultaneous happenings at a discrete time point are properly ordered. The compilation enforces non-self-overlap via a per-action flag `r_a` and checks invariants through an `ok` fluent; the goal becomes `G ∧ ok ∧ oc=0`. The resulting PDDL+ problem can be handed to any PDDL+ solver; the authors use ENHSP with WA* and LG configurations. Plan extraction from the PDDL+ solution maps compiled actions back to original durative actions, preserving semantics.

## Key Results
- ENHSP-WA solved 67 out of 80 temporal numeric instances across four domains, exceeding ARIES (59), OPTIC (36), and TAMER (42).
- The compilation is sound and complete, and preserves plan length up to a constant factor (at most doubling).
- Runtime analysis confirms ENHSP’s superiority on numeric-rich problems, demonstrating the practical effectiveness of the compilation.

## Why This Works (Mechanism)
### Mechanism 1
**Claim:** A polynomial translation can convert durative actions into PDDL+ actions, processes, and events.  
**Mechanism:** Each durative action `a` is compiled into a start action `¯a⊢`, an end action/event (`¯a⊣` for variable duration, `¯e⊣_a` for fixed), and a process `¯p_a` that increments a clock fluent `c_a`. The process models the passage of time while the action is active, and the end component triggers when `c_a` reaches the duration bounds. The precondition `¬r_a` on `¯a⊢` ensures non-self-overlapping (no two instances of the same action overlap).  
**Break condition:** Violates non-self-overlapping if the source allows concurrent instances of the same action.

### Mechanism 2
**Claim:** Lock predicates (`rl_f`, `al_f`, `il_f`) enforced by the event `¯eE` prevent temporal interference between simultaneous happenings at the same logical time point.  
**Mechanism:** For any instantaneous happening (action start/end/event), a lock precondition `λ_a` requires relevant lock predicates to be true. The happening's lock effects `L_a` set specific locks to false based on whether it reads (`V^r_a`), assigns (`V^:=_a`), or increments (`V^+=_a`) a fluent `f`. The event `¯eE` triggers when `gc>0` (indicating time progression) and resets all locks to true, thus separating happenings in different discrete time steps.  
**Break condition:** If a planner executes happenings in an order that violates lock preconditions within the same discrete step, the plan becomes invalid; soundness assumes `¯eE` resets locks before other happenings at a new time step.

### Mechanism 3
**Claim:** The compilation preserves plan length up to a constant factor and is sound and complete.  
**Mechanism:** Soundness: given a valid PDDL+ plan, a mapping `˜π` interprets `¯a⊢`/`¯a⊣` (or `¯e⊣_a`) as start/end of a durative action, reconstructing a temporal plan that satisfies the original constraints. Completeness: from any valid temporal plan, choose a sufficiently small discrete step `δ` and construct a PDDL+ plan where each original happening is placed at integer multiples of `δ`. The state sequence is defined to mimic the temporal states, using the clock `c_a` and `ok` to enforce invariants and duration bounds.  
**Break condition:** The completeness proof requires all original plan times to be integer multiples of the chosen `δ`; if the compiled plan yields non‑multiple times, the mapping fails.

## Foundational Learning
- **Concept: PDDL+ Discrete-Time Semantics**  
  **Why needed:** The compilation models time as discrete steps of size `δ`. Understanding the state transition (processes increment fluents per step), event firing, and superdense ordering within a timepoint is crucial to see why the lock mechanism and `gc` reset work.  
  **Quick check:** A process with `d/dt f = 1` active for 3 discrete steps changes `f` by `3 * δ` between the start state and the state three steps later.

- **Concept: Temporal Planning Semantics (PDDL 2.1 Level 3)**  
  **Why needed:** The source semantics (conditions like invariant `γ_a`, snap actions `a⊢`/`a⊣`, non-self-overlap) are what the compilation must capture. Each compiled component (`¯a⊢`, `¯a⊣`, `¯↔_a`, `r_a`) enforces one of these conditions.  
  **Quick check:** In a temporal plan, can the end effect of one durative action and the start effect of another occur at exactly the same instant? Yes, provided there is no mutual exclusion and preconditions are satisfied; the compilation uses locks to model such interactions.

- **Concept: Mutual Exclusion via Dynamic Predicates**  
  **Why needed:** The lock system (`rl_f`, `al_f`, `il_f`) is the novel core for encoding PDDL 2.1's non-interference. Learning how read/write/assign conflicts translate into specific lock requirements and effects, and reset via `gc`, is key to correctness.  
  **Quick check:** If action `a` increments fluent `f` and action `b` reads `f` in its precondition, `b` requires `rl_f` to be true at the discrete step; `a`'s effect will set `al_f` to false, but that does not block `b` unless `b` also assigns. The lock ordering within a step determines whether both can occur; the encoding ensures a valid ordering exists only if PDDL 2.1's non-interference rule holds.

## Architecture Onboarding
- **Component map:**  
  Source Parser -> Compilation Core -> Target Serializer -> Planner Interface. The Compilation Core internally generates fluents, actions, processes, events, and builds initial/goal conditions.

- **Critical path:**  
  Parse PDDL2.1 domain/problem → generate auxiliary fluents (`ok`, `oc`, `gc`, `r_a`, `c_a`, lock predicates) → for each durative action define start action, process, end mechanism → construct universal process `¯p_E` and lock-reset event `¯eE` → assemble initial state and goal → write PDDL+ file.

- **Design tradeoffs:**  
  - Polynomial blowup: new elements are linear in input size, but increases planner search space.  
  - Discrete vs continuous time: The encoding relies on discrete steps for lock separation; using continuous PDDL+ semantics could cause Zeno behavior.  
  - Lock granularity: Using one set of locks per fluent may be over‑conservative in lifted domains, potentially rejecting valid concurrent plans.

- **Failure signatures:**  
  - Plan invalidity after back‑mapping suggests bug in event `¯↔_a` or state mapping.  
  - Planner crash on simple instance indicates missing initialization (e.g., `ok=true`, locks) or syntax error in process.  
  - No solution for obviously solvable instance could be wrong termination condition for fixed‑duration actions or `oc` counter mismatch.

- **First 3 experiments:**  
  1. Compile a minimal domain with one durative action of duration [1,2] and verify the start action, process, and end event fire correctly with `c_a` reaching bounds and `r_a` toggling.  
  2. Test locking with two conflicting instantaneous actions (one sets `f:=true`, other needs `f=false`) to ensure they cannot both occur in the same discrete time step.  
  3. Solve a small instance (e.g., two‑action sequence from MatchCellar) with ARIES and ENHSP on the compiled domain; check that the back‑mapped temporal plan matches the structure and durations.

## Open Questions the Paper Calls Out
- **Open Question 1:** Can the compilation be extended to PDDL 2.1 level 4 (with continuous change, differential equations)? The paper suggests it as future work but does not address continuous dynamics.
- **Open Question 2:** How to adapt the encoding for PDDL+ continuous‑time semantics to avoid Zeno behavior while preserving the lock mechanism? The lock construction is discrete‑time specific; continuous time may allow infinite event firings.
- **Open Question 3:** What is the scalability of the approach beyond the four evaluated domains and 80 instances? The paper only tests on small‑to‑medium benchmarks; broader industrial or IPC‑scale domains are not considered.
- **Open Question 4:** Does the non‑self‑overlapping assumption limit applicability? Can the compilation be generalized to allow overlapping or concurrent instances of the same durative action? The current encoding forbids it via the `r_a` predicate.

## Limitations
- Exact translation command and ENHSP parameters are not fully specified in the paper, making reproduction dependent on inspecting UPL source.
- The discrete time quantum `δ` is not described; inappropriate defaults could cause state explosion or incorrect duration handling.
- Support for timed initial literals and delayed effects is only sketched; it is unclear whether the compiler fully handles them.

## Confidence
- **Compilation correctness (soundness/completeness, polynomial blowup):** High
- **Lock mechanism correctness (non‑interference, non‑self‑overlap):** High
