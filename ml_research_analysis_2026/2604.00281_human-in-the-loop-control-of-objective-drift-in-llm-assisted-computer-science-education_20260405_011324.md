# Human-in-the-Loop Control of Objective Drift in LLM-Assisted Computer Science Education

## Quick Facts
- **arXiv ID:** 2604.00281
- **Source URL:** https://arxiv.org/abs/2604.00281
- **Reference count:** 13
- **Primary result:** Sensitivity power analysis shows that under section-level clustering (ICC=0.10), achieving 80% power for a three-arm pilot requires large standardized effect sizes (d ≥ 1.05–1.45), corresponding to 10.5–14.5 point differences on a 100-point scale.

## Executive Summary
This paper proposes a human-in-the-loop (HITL) pedagogy to address objective drift—where LLM-generated code diverges from task specifications—in AI-assisted computer science education. The approach trains students to separate planning (defining acceptance criteria and architectural constraints) from AI-assisted execution, with an optional third arm that deliberately injects concept-aligned drift to practice diagnosis and recovery. The core contribution is a sensitivity power analysis for a planned three-arm pilot study. The analysis reveals that, given realistic section-level clustering (ICC = 0.10), the design requires very large effect sizes to achieve 80% power, raising important questions about the feasibility of detecting moderate but educationally meaningful improvements.

## Method Summary
The planned pilot is a three-arm randomized trial comparing: (1) unstructured AI use, (2) structured HITL planning (students create explicit objective and world-model specifications before execution), and (3) HITL with injected drift (pre-specified perturbations aligned with curricular concepts). Primary outcomes are rubric scores on an evaluation lab and a concept quiz. The power analysis accounts for clustering at the section level (ICC = 0.10) by computing an effective sample size per arm: n_eff = n / [1 + (n−1)×0.10]. For each per-arm sample size n ∈ {10, 15, 20} and assumed outcome standard deviation σ = 10 (on a 100-point scale), it solves for the minimum standardized difference d that yields 80% power in a one-sided contrast using the non-central t-distribution.

## Key Results
- Under ICC=0.10 and n=15, detecting Arm 2 > Arm 1 with 80% power requires d ≥ 1.25 (Δ = 12.5 points).
- For Arm 3 > Arm 2, detectable d ranges from 1.05 (n=20) to 1.45 (n=10), corresponding to 10.5–14.5 point differences.
- Clustering substantially reduces effective sample size (e.g., n_eff = 8.11 for n=15), inflating required effect sizes compared to an unclustered design.

## Why This Works (Mechanism)

### Mechanism 1: Specification-Before-Execution
**Claim:** Separating planning (specification) from execution reduces objective drift by establishing bounded goals before AI code generation begins.  
**Mechanism:** Students produce explicit objective specifications (acceptance criteria) and world-model constraints (architectural bounds) prior to substantial AI interaction. These artifacts constrain the AI's output space, preventing uncontrolled scope expansion and misalignment.  
**Break condition:** If planning artifacts are vague, incomplete, or internally inconsistent, they fail to meaningfully constrain the AI, and drift persists.

### Mechanism 2: Artifact-Based Control for Durability
**Claim:** Framing specifications and constraints as operational, inspectable artifacts cultivates durable control competencies that transfer across evolving AI tools.  
**Mechanism:** Students treat planning artifacts as tangible deliverables they actively refine and monitor against during execution. This externalizes self-regulation, making control explicit rather than implicit prompt engineering.  
**Break condition:** If students create artifacts but ignore them during execution, monitoring fails and drift goes uncorrected.

### Mechanism 3: Injected Drift for Diagnostic Practice
**Claim:** Deliberate, concept-aligned injection of objective drift improves diagnostic skill and conceptual learning by creating structured failure events.  
**Mechanism:** In Arm 3, the curriculum introduces pre-specified perturbations (e.g., off-by-one errors) at workflow landmarks. Students, aware errors may occur, use their specifications and conceptual knowledge to detect and repair misalignments, turning drift into a deliberate learning resource.  
**Break condition:** If injected drift is too subtle, too frequent, or misaligned with the targeted concept, the learning benefit diminishes or reverses.

## Foundational Learning
- **Concept: Objective Specification**  
  *Why needed:* Students must unambiguously define "correct" for a programming task (acceptance criteria, quality measures) before engaging the AI; otherwise, the AI optimizes for locally plausible but globally incorrect outputs.  
  *Quick check:* "List three concrete, testable acceptance criteria for a function that removes duplicates from a list."
  
- **Concept: World-Model Constraint Definition**  
  *Why needed:* Students must bound the AI’s option space (libraries, file structure, algorithmic approaches) to prevent uncontrolled scope expansion and architectural violations that constitute drift.  
  *Quick check:* "Specify three constraints that would prevent an AI from using a forbidden library (e.g., `collections`) in a sorting assignment."
  
- **Concept: Specification-Compliance Monitoring**  
  *Why needed:* During execution, students must continuously compare AI outputs against their own specifications to detect drift early, before errors compound autoregressively.  
  *Quick check:* "Given a specification requiring O(n log n) time complexity, what two signs in AI-generated code would indicate a potential violation?"

## Architecture Onboarding
**Component map:**  
Planning Module -> Execution Module  
Drift Injector (Arm 3 only) -> Execution Module  
Monitoring Interface (parallel to Execution)  
Assessment Layer (receives outputs from Planning, Execution, Monitoring)

**Critical path:**  
1. Student completes planning phase → produces instruction file.  
2. Student enters execution phase with AI access.  
3. (Arm 3) Drift injector activates at predefined landmark.  
4. Student monitors output, detects violation against spec.  
5. Student initiates recovery (revise prompt, tighten constraints).  
6. Final submission evaluated for compliance and concept understanding.

**Design tradeoffs:**  
- Durability vs. Immediate Efficacy: Tool-agnostic specifications (durable) may yield less immediate productivity than advanced prompt engineering (fragile).  
- Cognitive Load vs. Skill Transfer: Explicit planning adds upfront cost but aims to build transferable control skills.  
- Drift Frequency vs. Learning Benefit: Too many injected errors cause frustration; too few miss diagnostic practice opportunities.

**Failure signatures:**  
- **Planning failure:** Vague, incomplete, or inconsistent specifications.  
- **Execution failure:** High rate of constraint violations (e.g., unauthorized dependencies) in repository logs.  
- **Monitoring failure:** Students fail to detect injected drift in Arm 3 (no attempted corrections).  
- **Transfer failure:** No performance difference in evaluation lab or concept quiz between arms.

**First 3 experiments:**  
1. **Arm Contrast (RQ1):** Compare mean evaluation lab scores between Arm 1 and Arm 2 under per-arm n=15, ICC=0.10; test if d ≥ 1.25 is detectable.  
2. **Drift Effect (RQ2):** Compare mean concept quiz scores between Arm 2 and Arm 3; test if drift condition yields ≥1.25 SD improvement.  
3. **Mechanism Probe:** Correlate planning artifact quality scores with specification compliance rates during execution to validate that better specs reduce drift.

## Open Questions the Paper Calls Out
1. Does explicit HITL control training (separating planning from execution) significantly improve students' AI-assisted coding performance compared to unstructured AI use? The study only presents a sensitivity power analysis; the required effect sizes (d ≥ 1.05–1.45) are very large, so smaller but meaningful improvements might go undetected.  
2. Does deliberate injection of curriculum-aligned objective drift significantly enhance students' learning of specific CS concepts compared to HITL training without injected drift? Again, only a power analysis is provided; the magnitude of any learning benefit is unknown and may be smaller than the detectable thresholds.  
3. Is a three-arm pilot design with section-level clustering (ICC=0.10) and 10–20 students per arm feasible, or are the required effect sizes so large that the intervention's true impact is likely undetectable in typical undergraduate lab sections? The analysis suggests the study may be underpowered to detect anything but enormous effects; prior evidence to estimate plausible effect sizes is lacking.  
4. What specific characteristics of deliberately injected objective drift (error type, injection timing, conceptual alignment) are most effective at promoting diagnostic skills and conceptual learning without causing excessive frustration? The paper introduces injected drift but does not specify design principles or validate which perturbations are pedagogically effective; future work calls for "libraries of concept-aligned drift injections."  
5. To what extent does the debriefing process after students encounter injected drift mitigate potential negative effects (e.g., confusion, mistrust in AI) and reinforce learning, and could it inadvertently reduce the diagnostic practice opportunity? The Ethics section notes students are informed about intentional errors and receive a debrief, but this confound is unexamined; it may either support learning or weaken the diagnostic challenge.

## Limitations
- **Clustering parameter ambiguity:** The clustering adjustment assumes section size equals per-arm sample size (n), an atypical and unexplained choice; actual sectioning (number and size of sections) is unreported, risking misestimated statistical power.
- **Indirect mechanistic evidence:** The proposed HITL mechanisms are theoretically grounded but lack direct empirical validation in CS education; corpus evidence is correlational or from adjacent fields.
- **Assumed distributions:** Power analysis assumes normality and equal variance in outcome scores; the true distribution of lab rubric scores and quiz results is unreported.

## Confidence
- **Primary Result (Power Analysis):** Medium-High (transparent calculation but hinges on questionable clustering assumption).
- **Mechanistic Claims:** Low-Medium (plausible and well-articulated but lack direct empirical support in this context).
- **Durability & Transfer:** Low (aspirational goal; planned study does not directly measure transfer to novel AI tools).

## Next Checks
1. Replicate the power analysis using the actual section size (m) and number of sections; report how detectable effect sizes change if the assumed m = n is incorrect.
2. Conduct a small pilot (n=5 per arm) to score planning artifact quality and correlate these scores with objective measures of specification compliance (e.g., forbidden library use rate) during execution.
3. In Arm 3 pilot, log all injected drift events and measure student detection/correction rates; if key concept detection is <60%, recalibrate drift injection (subtlety, frequency, alignment).
