# 98$\times$ Faster LLM Routing Without a Dedicated GPU: Flash Attention, Prompt Compression, and Near-Streaming for the vLLM Semantic Router

## Quick Facts
- arXiv ID: 2603.12646  
- Source URL: https://arxiv.org/abs/2603.12646  
- Reference count: 40  
- Primary result: 98× speedup in LLM routing latency (from 4,918 ms to 50 ms at 8K tokens) without a dedicated GPU via CK Flash Attention, prompt compression, and near‑streaming.

## Executive Summary
System-level LLM routers require low latency and must often share a GPU with vLLM inference. Standard attention’s O(n²) memory prevents long‑context (8K‑32K) classification on a shared GPU, causing out‑of‑memory failures. This paper introduces three optimizations: (1) a custom CK Flash Attention operator for ONNX Runtime on ROCm that reduces attention memory to O(n), enabling long‑context processing; (2) neural‑inference‑free prompt compression using TextRank, position weighting, TF‑IDF, and novelty scoring, which shrinks all inputs to ~512 tokens; (3) near‑streaming body processing with adaptive chunking and zero‑copy JSON that eliminates serialization overhead. Together these yield a 98× speedup: end‑to‑end latency drops from 4,918 ms to 50 ms at 8K tokens, and 16K‑token routing takes 108 ms, while the GPU footprint stays under 800 MB. The approach allows the router to coexist with vLLM on a single AMD MI300X without a dedicated accelerator, offering a cost‑effective solution for high‑throughput deployments.

## Method Summary
The method integrates three stages. Stage 1 replaces standard scaled dot‑product attention (SDPA) subgraphs in an ONNX model (mmBERT‑32K) with a custom “CK Flash Attention” operator built on AMD’s Composable Kernels. The operator tiles computations to fit in shared memory and fuses QKᵀ, softmax, and AV, collapsing O(n²) memory to O(n) and making 8K‑32K token classification feasible on a shared GPU. Stage 2 applies extractive prompt compression: sentences are scored by combining TextRank centrality, a U‑shaped position weight (emphasizing boundaries), TF‑IDF information density, and novelty (inverse cosine similarity to document centroid). The top‑scoring sentences within a ~512‑token budget are selected; this step uses no neural inference and preserves accuracy for domain and PII tasks while capping memory and latency. Stage 3 implements near‑streaming within an Envoy ext proc filter: incoming HTTP bodies are processed in STREAMED mode; the first chunk is inspected with gjson to extract the `model` field. If a specific model is named, the router forwards chunks immediately (passthrough) with zero‑copy via sjson. For “auto” requests, the router accumulates chunks and incrementally performs sentence splitting and TF‑IDF during arrival, overlapping I/O with preprocessing, and compresses at EOF. Zero‑copy JSON edits avoid full Marshal/Unmarshal. The combined system runs on an AMD MI300X, sharing the GPU with vLLM while meeting sub‑50 ms latency at 8K tokens and staying under 800 MB.

## Key Results
- Latency reduced by 98×: from 4,918 ms to 50 ms for 8K tokens; 16K tokens routed in 108 ms.  
- GPU memory footprint under 800 MB, enabling co‑location with vLLM without a dedicated GPU.  
- Enables classification of long contexts (8K‑32K tokens) that would otherwise OOM with standard attention.

## Why This Works (Mechanism)
#### Mechanism 1: CK Flash Attention for ONNX Runtime
The custom CK Flash Attention operator replaces standard SDPA subgraphs in ONNX Runtime with tiled, fused kernels from AMD’s Composable Kernel library. By processing attention in blocks that fit in shared memory and fusing QKᵀ, softmax, and AV, it avoids materializing the full O(n²) attention matrix, reducing memory from O(n²) to O(n). This enables 8K–32K token classification on a shared GPU without OOM. The method assumes the model’s alternating local/global attention pattern maps to CK’s sliding window parameters (window_left/right) and that the graph rewrite correctly identifies and replaces SDPA nodes. Evidence includes the abstract’s claim, Section IV‑A’s description of the rewrite and HIP kernel dispatch, and the novelty of integrating FlashAttention into ONNX Runtime for ROCm. The approach fails for models with arbitrary attention masks or if the operator registration/rewriting is incorrect.

#### Mechanism 2: Neural‑Inference‑Free Prompt Compression
Extractive prompt compression combines four signals: TextRank (PageRank on sentence similarity), U‑shaped position weighting (sine curve emphasizing boundaries), TF‑IDF information density, and novelty (inverse cosine similarity to document centroid). Sentences are scored and greedily selected within a token budget (~512 tokens), then reordered to preserve discourse. This avoids neural inference, capping latency and memory. The core assumption is that classifier decisions rely on a small subset of sentences captured by these signals and that the U‑shaped weighting aligns with the classifier’s attention pattern. Evidence: abstract and Section IV‑B detail the composite scoring (α = (0.20,0.40,0.35,0.05)); Section V‑F shows accuracy gains for domain (53.1%→61.2%) and PII (78.5%→92.4%). Break conditions: critical middle‑sentence signals (e.g., jailbreak patterns) may be dropped; effectiveness depends on sentence segmentation quality.

#### Mechanism 3: Near‑Streaming Body Processing
The router runs as an Envoy ext proc filter in STREAMED mode. The first chunk is inspected with gjson to extract the `model` field. If a specific model is named, the router enters passthrough mode, forwarding subsequent chunks immediately using zero‑copy edits (sjson). If model is “auto”, the router accumulates chunks and incrementally performs sentence splitting and TF‑IDF computation during arrival, overlapping I/O with preprocessing. At EOF, the accumulated prompt is compressed. Zero‑copy JSON operations avoid full Marshal/Unmarshal overhead. The assumption is that the `model` field appears early (within ~1 KB) so that passthrough can be decided quickly. Evidence: abstract and Section IV‑C describe the state machine and gjson/sjson usage; the paper reports a ~19% latency reduction at 8K tokens (62 → 50 ms). Failure modes include malformed JSON or large initial headers that delay model detection, forcing a fallback to full buffering.

## Architecture Onboarding
**Component map:** Envoy proxy (v1.33) → Router service (Go) → ONNX Runtime (ROCm) with custom CK Flash Attention operator → AMD MI300X GPU (shared with vLLM). Router components: header inspector, near‑streaming body handler, prompt compressor (CPU), parallel classifier sessions (3× mmBERT‑32K), decision engine.

**Critical path (auto model request):**  
1. Envoy sends first chunk; router extracts `model` via gjson.  
2. If "auto", router enters accumulate mode, incrementally splitting sentences and computing TF‑IDF.  
3. At EOF, compressor selects ~512 tokens; classifiers run in parallel on GPU with FlashAttention.  
4. Decision engine aggregates signals; router mutates headers/body and responds.

**Design tradeoffs:**  
- Memory vs. accuracy: Compression caps GPU memory and latency but risks signal loss; weights tuned to preserve domain/PII at cost of jailbreak accuracy (mitigated by running jailbreak on full prompt in production).  
- Streaming complexity: State machine and incremental NLP add code complexity but avoid full buffering for ~majority of requests (specified model).  
- Hardware lock‑in: Stage 1 is AMD‑specific; Stages 2–3 are portable.

**Failure signatures:**  
- OOM: Router exceeds available HBM (e.g., without FA at 8K tokens, or without compression at 32K tokens under high concurrency).  
- Latency spike: Compression exceeding ~20 ms at 16K tokens, or streaming mode failing to detect model early (forcing buffering).  
- Accuracy regression: Compression removes critical jailbreak/PII context (observed 14% drop in jailbreak detection in offline tests).

**First 3 experiments:**  
1. Validate CK Flash Attention: Run a single 8K‑token classifier with and without the custom operator; verify memory reduction (O(n) vs. O(n²)) and that SDPA OOMs while FA succeeds.  
2. Measure compression pipeline: Feed a 16K‑token prompt; check output token count (~512) and latency (<20 ms). Validate that composite scores rank boundary sentences highly.  
3. Compare streaming vs. buffering: For an "auto" request with 8K tokens, measure E2E latency in BUFFERED (with compression) vs. STREAMED modes; expect ~20% reduction. Also verify passthrough latency for specified models matches raw streaming overhead (~17 ms).

## Open Questions the Paper Calls Out
#### Open Question 1
**Question:** How can the prompt compression pipeline be enhanced to use the actual tokenizer of the classification models for precise token budget control, and what impact does this have on classification accuracy and compression ratio?  
**Basis in paper:** The paper states in the limitations: "The current prompt compression uses approximate tokenization (character‑length heuristic) rather than the actual model tokenizer. While this is sufficient for the coarse‑grained compression ratios we target (32× reduction), future work should integrate the model‑specific tokenizer for precise budget control."  
**Why unresolved:** The current heuristic may lead to inaccuracies in token counting, potentially causing over‑compression or under‑compression, affecting the effectiveness of the fixed 512‑token budget and model performance.  
**What evidence would resolve:** Implementing the compression with the model's tokenizer (e.g., from Hugging Face tokenizers) and comparing token counts, compression ratios, and classification accuracy against the heuristic‑based approach on diverse datasets.

#### Open Question 2
**Question:** Can the near‑streaming body processing be modified to avoid buffering the entire request body in memory during the "accumulate" state, thereby reducing overall memory footprint for long‑context requests?  
**Basis in paper:** The paper notes in the limitations: "The streaming handler’s “accumulate” path buffers the entire body in memory before classification, so the memory savings are primarily in reduced JSON processing, not in total memory usage."  
**Why unresolved:** For extremely long prompts, even with compression, the original body accumulation could consume significant CPU memory, limiting scalability in memory‑constrained environments and potentially causing OOM errors at scale.  
**What evidence would resolve:** Designing an incremental compression scheme that processes chunks on the fly without full accumulation (e.g., streaming sentence segmentation and scoring) and measuring memory usage and latency for very long prompts (e.g., >32K tokens) under high concurrency.

#### Open Question 3
**Question:** What modifications to the prompt compression scoring function can preserve or improve safety‑related classification accuracy (jailbreak and PII detection) while maintaining the benefits of compression for domain routing?  
**Basis in paper:** The paper reports that compression improves domain classification and PII detection accuracy but decreases jailbreak detection accuracy (from 70.8% to 56.6%). They mitigate this by running safety signals on the full prompt in production, but this adds latency. An optimal solution would allow compression for all signals without accuracy loss.  
**Why unresolved:** The current weighting scheme prioritizes domain‑representative content, which may dilute outlier‑based safety signals. Finding a balance or alternative features is an open challenge, especially for real‑time routing where latency is critical.  
**What evidence would resolve:** Experimenting with different weight combinations, adding novel features for safety signals (e.g., anomaly detection), or developing signal‑specific compression strategies, and evaluating accuracy on safety‑classification benchmarks with compressed prompts, while measuring latency overhead.

## Limitations
- Hardware lock‑in: CK Flash Attention relies on AMD’s CK library and gfx942; other platforms remain unvalidated.  
- Compression generalization: α weights tuned on unreleased Wikipedia data may not generalize, especially for jailbreak detection (observed 14% drop).  
- Streaming fragility: Depends on early `model` extraction; malformed JSON or large initial headers force full buffering, eroding gains.
