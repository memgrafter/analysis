# Beyond Pixels: Vector-to-Graph Transformation for Reliable Schematic Auditing

## Quick Facts
- arXiv ID: 2602.11678
- Source URL: https://arxiv.org/abs/2602.11678
- Reference count: 0
- Primary result: Vector-to-Graph transformation raises schematic auditing accuracy from 12% (near chance) to 47% (+35% absolute gain) by enabling deterministic graph-based verification.

## Executive Summary
Multimodal large language models (MLLMs) struggle with engineering schematic auditing because they cannot reason about topology from pixel-based images—a limitation the authors call "structural blindness." This paper introduces the Vector-to-Graph (V2G) framework, which converts CAD schematics into explicit property graphs where components are nodes, connectivity is edges, and attributes capture labels. Compliance rules are then evaluated deterministically using Graph Signal Processing operators. On a diagnostic benchmark of ~900 real-world electrical schematics, baseline MLLMs achieved only 12% accuracy, while V2G-augmented models reached 47% (+35% absolute gain), with particularly large improvements in connection checks (+61%) and grounding checks (+27%). All six tested MLLMs benefited, demonstrating that explicit graph-based structure is essential for reliable multimodal reasoning in engineering domains.

## Method Summary
The V2G pipeline comprises three main stages: (1) parsing of CAD files (e.g., .dxf) using ezdxf into geometric primitives (lines, arcs, text, inserts), (2) construction of a property graph where nodes represent components and edges encode connectivity (guided by a language model), and (3) rule verification via a two-step process. An MLLM planner translates natural language compliance rules into structured queries that select subgraphs and invoke deterministic Graph Signal Processing (GSP) operators. A GSP verifier then executes these operators (e.g., Laplacian-based connected component detection, attribute consistency checks, spectral analysis) to produce binary compliance outcomes. No model training is performed; the approach leverages off-the-shelf LLMs and standard graph libraries. The diagnostic benchmark includes ~900 augmented electrical schematics covering ten compliance tasks, and evaluation focuses on accuracy.

## Key Results
- Baseline MLLMs average 12% accuracy on schematic auditing (near chance).
- V2G framework boosts overall accuracy to 47% (+35% absolute gain).
- Largest gains observed in connection checks (+61%) and grounding checks (+27%); all six MLLMs tested show significant improvement.

## Why This Works (Mechanism)

### Mechanism 1: Graph Representation Eliminates Structural Blindness
- **Claim:** Transforming pixel-based schematic images into explicit property graphs mitigates structural blindness by preserving topology and symbolic relations lost in rasterization.
- **Mechanism:** The V2G pipeline parses CAD vector primitives into nodes (components) and edges (connectivity), creating a machine-readable graph \(G=(V,E,X)\) where structural dependencies are first-class citizens. This contrasts with MLLMs that process pixels as unordered token sequences, discarding explicit relational information.
- **Core assumption:** Engineering compliance is fundamentally a graph-theoretic verification problem (connectivity, attribute consistency) rather than a pattern-matching task.
- **Evidence:** The abstract describes converting CAD diagrams into property graphs; Section 3 details V2G stages—node identification via block patterns, edge inference from geometric heuristics, attribute mapping—stating that the resulting graph preserves both symbolic semantics and explicit topology.
- **Break condition:** If the CAD source lacks clean vector data (e.g., scanned raster images), the V2G transformation fails at primitive extraction, collapsing the advantage.

### Mechanism 2: Deterministic GSP Verifiers Provide Reliable, Interpretable Outcomes
- **Claim:** Deterministic Graph Signal Processing (GSP) verifiers provide reliable, interpretable compliance outcomes by leveraging spectral graph properties, avoiding the probabilistic hallucinations of MLLMs.
- **Mechanism:** GSP operators (Laplacian \(L\), adjacency \(A\)) transform compliance rules into mathematically precise checks: connectivity via zero-eigenvalue multiplicity \(c=\text{mult}_{\lambda=0}(L)\), attribute consistency via pairwise edge constraints, and grounding via node-type counting. These yield binary, auditable results \(o_t \in \{0,1\}\).
- **Core assumption:** Engineering standards are rule-based and can be encoded as graph-level predicates; deterministic execution is preferable to LLM-based probabilistic inference for safety-critical auditing.
- **Evidence:** The abstract notes that compliance rules are verified deterministically using GSP operators. Section 3 explicitly defines verification functions: \(g(R_t)\) for grounding count, \(c_{\text{attr}}(R_t)\) for attribute matching, and spectral cycle detection via \(\beta = |E_t| - |V_t| + c\). Section 4.2 ablation "w/o GSP" reduces accuracy from 47% to ~28%, confirming the verifier's critical role.
- **Break condition:** If the graph construction is erroneous (missing nodes/edges), GSP verifies a corrupted structure, producing confidently incorrect results (garbage-in-garbage-out).

### Mechanism 3: MLLM Planner Bridges Natural Language to Executable Graph Queries
- **Claim:** An MLLM "planner" guides structured query generation over the graph, bridging natural language rules to executable GSP functions while constraining search space via subgraph selection.
- **Mechanism:** The planner interprets natural-language compliance rule \(\phi\) into a structured query \((R_t, f_t)\): it identifies relevant node/edge types for region selection \(R_t \subseteq G\) and retrieves the appropriate GSP function \(f_t \in \mathcal{F}\). This limits the MLLM's role to symbolic command generation rather than raw reasoning.
- **Core assumption:** MLLMs can reliably perform semantic parsing and keyword-to-schema alignment when relieved of direct numerical/topological reasoning.
- **Evidence:** Section 3 describes rule interpretation: the MLLM parses \(\phi\) into structured JSON commands; region selection aligns keywords with node types; function selection retrieves the appropriate verification operator. Section 4.2 ablation "w/o RegionSel" reduces overall accuracy to ~39%, with steepest drop in wiring checks due to "increased clutter," confirming the planner's localization necessity.
- **Break condition:** If the MLLM planner misinterprets the rule's semantic scope (e.g., selecting wrong subgraph) or maps to an incorrect GSP function, verification targets the wrong graph slice, causing false compliance/error reports.

## Foundational Learning
### Property Graphs
- **Why needed:** The entire V2G framework hinges on representing schematics as nodes (components), edges (connectivity), and attributes (terminal IDs, polarity). Without grasping this data model, one cannot understand the transformation or verification.
- **Quick check:** Given a graph with nodes `{CT, G1, G2}` and edges `{(CT,G1), (CT,G2)}`, how would a 'single-point grounding' rule be encoded as an attribute constraint on the `CT` node's incident edges?

### Graph Laplacian & Connectivity
- **Why needed:** The GSP verifier uses the combinatorial Laplacian \(L = D - A\) to compute connected components via \(\text{rank}(L) = |V| - c\). This is the mathematical core of topological checks (e.g., open circuit detection).
- **Quick check:** If a subgraph has 5 nodes and \(\text{rank}(L)=3\), how many connected components does it contain? What would this imply for a 'circuit continuity' check?

### Engineering Compliance Rules as Graph Predicates
- **Why needed:** Rules like "CT secondary must connect to exactly one ground" are not visual patterns but graph-level logical constraints (\(g(R_t) = \sum_{v\in V_t} \mathbf{1}[\text{type}(v)=\text{Ground}] == 1\)). Bridging domain semantics to graph logic is essential.
- **Quick check:** Translate 'no duplicate terminal IDs in a connected region' into a graph traversal and attribute comparison operation.

## Architecture Onboarding
### Component Map
CAD Parser (ezdxf) → V2G Builder (LLM-driven) → MLLM Planner → GSP Verifier → Report Generator

### Critical Path
The graph `G` is built once: CAD Parser → V2G Builder. For each compliance rule: MLLM Planner → GSP Verifier. Failures in V2G propagate universally to all downstream checks.

### Design Tradeoffs
- *Precision vs. Automation*: V2G uses an LLM for flexible rule interpretation but sacrifices pure determinism in graph construction. A fully rule-based parser would be more auditable but less adaptable to varied schematic styles.
- *Complexity vs. Scope*: The benchmark covers 10 specific checks; extending to arbitrary rules requires expanding the GSP verifier library `F` and ensuring the MLLM planner can map new semantics correctly.
- *Performance*: Graph construction is computationally light; MLLM planner calls are the bottleneck. Batching rule queries could reduce latency.

### Failure Signatures
- **V2G construction error**: Missing component nodes or spurious edges. Diagnose by manually inspecting `G` for expected degree distributions (e.g., a breaker should have ≥2 terminals).
- **Planner misalignment**: MLLM selects a subgraph `R_t` that either excludes violating nodes or includes irrelevant clutter. Check JSON query: are keywords correctly mapped to node attributes?
- **Verifier mismatch**: `f_t` does not match rule intent (e.g., using connectivity check for a labeling rule). Validate by unit-testing `f_t` on synthetic `R_t`.

### First 3 Experiments
1. **Unit test graph extraction**: Take a trivial schematic (e.g., battery + resistor + wire). Run V2G builder, assert `|V|=2` (battery, resistor), `|E|=1` connecting terminals, and `X` contains correct terminal labels.
2. **Verify simple connectivity**: Construct a graph with nodes `A-B-C` in a path and `D` isolated. Run `check_connectivity(R_t={A,B,C})` → should return `1` (true); `R_t={A,D}` → `0` (false).
3. **End-to-end rule test**: Use a schematic with intentional multi-point grounding violation. Confirm: (i) V2G produces graph with two `Ground` nodes connected to same `CT`, (ii) Planner outputs `{"region":"CT_secondary", "function":"check_grounding_uniqueness"}`, (iii) Verifier returns `0` and flags both grounds in report.

## Open Questions the Paper Calls Out
### Open Question 1: Benchmark Expansion
- **Basis:** Explicit "Future work will scale the benchmark to broader coverage." (Section 4.2)
- **Why unresolved:** Current benchmark has only 60 unique base cases, limiting diversity of circuit topologies, component types, and rule categories. Generalizability to the full spectrum of real-world schematics is unclear.
- **Resolution:** A larger, systematically sampled benchmark with varied complexity, multiple utility standards, and additional compliance categories, accompanied by evaluation showing consistent V2G improvements across the expanded set.

### Open Question 2: Comparison with Graph Neural Networks
- **Basis:** Explicit "Future work will extend the dataset and include comparisons with domain-specific Graph Neural Networks and rule-based auditors." (Section 4.2)
- **Why unresolved:** The paper only benchmarks generic MLLMs; GNNs are tailored for graph-structured data and may achieve higher accuracy or better sample efficiency, but this remains untested.
- **Resolution:** Implement state-of-the-art GNN architectures on the V2G-generated property graphs, train/fine-tune them on the benchmark, and compare accuracy, robustness, and computational cost to V2G+MLLM.

### Open Question 3: V2G Extraction Accuracy and Robustness
- **Basis:** Inferred from V2G pipeline description; no separate metrics for graph construction correctness.
- **Why unresolved:** Errors in node/edge identification or attribute assignment propagate to all downstream verification. No analysis of where/often extraction fails, nor robustness to different CAD standards.
- **Resolution:** Manually create ground-truth property graphs for a representative sample, then measure precision/recall of nodes, edges, attributes produced by V2G across multiple CAD sources; also test on schematics with non‑standard symbols.

### Open Question 4: Scalability to Large Schematics
- **Basis:** Inferred; benchmark contains modest-sized schematics (≤20 perturbations each); no discussion of graph size/complexity effects.
- **Why unresolved:** Real industrial schematics can be much larger, potentially causing information overload for the MLLM planner or computational bottlenecks for spectral GSP. Observed gains may diminish with scale.
- **Resolution:** Evaluate V2G on a suite of large schematics (e.g., substation protection systems) with known compliance, measuring accuracy, runtime, memory usage; analyze failure modes related to graph size and test hierarchical partitioning improvements.

## Limitations
- V2G relies on clean vector CAD data; scanned raster images or poorly structured files cause failure at primitive extraction.
- The pipeline uses LLMs for graph construction and rule interpretation, introducing non-determinism and potential errors that are not fully quantified.
- Evaluation is limited to electrical schematics (60 base cases); generalizability to other engineering domains or drawing conventions remains unknown.

## Next Checks
1. **Cross-domain test:** Run V2G on a held-out set of mechanical/plumbing schematics; a significant drop would indicate overfitting to electrical conventions.
2. **Geometric tolerance sensitivity analysis:** Systematically vary the edge inference tolerance τ and measure accuracy; report the threshold where performance degrades sharply to quantify robustness.
3. **Planner error audit:** Manually inspect 100 randomly sampled planner JSON outputs for correct region selection and function mapping; compute error rate and categorize failure modes (e.g., wrong node type, incorrect verifier).
