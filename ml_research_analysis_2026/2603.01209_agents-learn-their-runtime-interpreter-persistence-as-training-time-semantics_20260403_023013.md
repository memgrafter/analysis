# Agents Learn Their Runtime: Interpreter Persistence as Training-Time Semantics
## Quick Facts
- arXiv ID: 2603.01209
- Source URL: https://arxiv.org/abs/2603.01209
- Reference count: 40
- Primary result: Interpreter persistence (stateful vs. stateless) is a learned behavioral prior; misalignment between training trace persistence and deployment runtime causes brittle failures or large efficiency costs without affecting solution quality.

## Executive Summary
The paper examines whether interpreter persistence—a runtime’s decision to keep state across turns—is merely a scaffold or a semantic that agents internalize during training. Using Opaque Knapsack, a partially observable knapsack problem that forces multi‑turn information gathering, they generate two matched sets of trajectories that differ only in whether Python globals persist between steps. Fine‑tuning identical Qwen3‑8B models on these variants produces persistent‑trained and stateless‑trained adapters. A 2×2 evaluation (training semantics × runtime semantics) reveals that final solution quality (normalized optimality) is statistically indistinguishable across conditions, but stability and efficiency depend critically on alignment: persistent‑trained models in a stateless runtime produce missing‑variable errors in ~80% of episodes, while stateless‑trained models in a persistent runtime incur an “amnesia tax” of ~3.5× more tokens due to redundant state reconstruction. Thus, interpreter persistence is a learnable behavioral prior that must be matched between training and deployment.

## Method Summary
The authors designed Opaque Knapsack, a synthetic task where item attributes (weight, value, class) are initially hidden and must be inspected within a budget, compelling multi‑step interaction. A teacher agent (Gemini 3 Flash) was run in two modes: persistent (variables survive across turns) and stateless (globals reset each turn), producing paired trajectories for each instance. After filtering by score, error density, and repetition, the traces were converted to chat format (system, user, assistant, observations) and truncated to 16k tokens. Two QLoRA fine‑tunes on Qwen3‑8B (rank = 64, 3 epochs) were conducted, one per dataset. Evaluation under both runtime conditions on Easy and Hard test sets collected normalized optimality, token counts, step counts, and error diagnostics. The 2×2 cross‑evaluation isolates the effect of persistence alignment.

## Key Results
- Solution quality (normalized optimality) shows no statistically significant difference across any alignment condition (e.g., Persistent→Persistent 81.1% vs. Persistent→Stateless 82.2% on Easy).
- Severe instability arises when a persistent‑trained model runs in a stateless environment: ~80% of episodes contain at least one unresolved reference error (NameError/UnboundLocalError).
- Efficiency collapses when a stateless‑trained model runs in a persistent environment: token consumption increases by ~3.5× (the “amnesia tax”), with near‑zero state utilization and an import every step.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** The agent learns a state‑management strategy (persistent vs. stateless) as a behavioral prior during post‑training, not merely as an inference‑time scaffold.
- **Mechanism:** During fine‑tuning on execution traces, the model internalizes the contract regarding variable lifetime across turns. When trained on persistent traces, the policy learns to rely on cross‑turn executable bindings, planning future actions assuming previously defined variables will remain available. When trained on stateless traces, it learns to externalize all state into textual representations for reconstruction.
- **Core assumption:** The training trace distribution sufficiently represents the deployment runtime’s execution semantics, allowing the model to absorb them as part of its behavioral policy rather than reasoning about them per‑step from prompts.
- **Evidence anchors:**
  - [abstract] "Fine‑tuning identical Qwen3‑8B models on these variants yields two adapters: persistent‑trained and stateless‑trained. A 2×2 evaluation (training semantics × runtime semantics) shows that solution quality does not vary significantly, but efficiency and stability depend critically on alignment."
  - [section 4.3] "When the persistent‑trained model is evaluated under stateless runtime, state‑mismatch exceptions emerge at high frequency. On both Easy and Hard splits, approximately 80% of traces contain at least one unresolved reference error."
  - [corpus] Corpus neighbors like "CaveAgent: Transforming LLMs into Stateful Runtime Operators" and "What Do Agents Learn from Trajectory‑SFT: Semantics or Interfaces?" contextualize this finding within broader work on stateful agents and trajectory‑SFT semantics.
- **Break condition:** If the training trace distribution does not consistently encode a single, coherent execution contract (e.g., mixed persistence modes in the same dataset), this learned prior may become ambiguous, leading to unpredictable behavior at deployment.

### Mechanism 2
- **Claim:** The "amnesia tax" (redundant state reconstruction) is a learned behavioral prior that persists even when a persistent runtime is available, indicating the model has internalized *how* to manage state rather than *what* state to manage.
- **Mechanism:** In stateless training traces, every turn must re‑establish all necessary variables by deriving them from textual history. The model learns this pattern as the canonical way to operate. Upon deployment in a persistent runtime, instead of shifting to a reuse strategy, it continues the re‑import/re‑derive pattern because that behavior was reinforced during training.
- **Core assumption:** The model’s policy gradient update process (via SFT) shapes multi‑step decision patterns, not just per‑step action prediction. The habit of re‑establishing state becomes entrenched in the sequence of actions, resistant to change even when the runtime constraint disappears.
- **Evidence anchors:**
  - [section 5] "Importantly, the ‘amnesia tax’ is portable. When the stateless‑trained model is deployed in a persistent runtime (Stateless→Persistent; 54,665 tokens), it continues re‑importing and re‑deriving state the interpreter is fully capable of retaining—Imports/Step = 1.00, State Utilization = 0.00."
  - [table 10] Under Stateless→Persistent on Hard tasks: Imports/Step = 1.00, State Utilization = 0.00, Redefinitions/Step = 6.15—active rewrites of already‑available bindings.
  - [section 4.3] "The reverse—a stateless‑trained model in a persistent runtime—pays an ‘amnesia tax’: it redundantly re‑derives state that the interpreter could have retained, using roughly 3.5× more tokens than the aligned persistent condition."
- **Break condition:** If the model is provided with strong, consistent demonstrations (in the system prompt) showing state reuse, and the training distribution includes some examples of efficient reuse, it may adapt its strategy at inference time. The tax appears robust when the training distribution is exclusively stateless.

### Mechanism 3
- **Claim:** The execution semantic (persistence contract) shapes the *efficiency* and *stability* of agent deployment, but not the ceiling of *solution quality*, which remains reachable via multiple strategies.
- **Mechanism:** Both persistent and stateless strategies can reach optimal or near‑optimal knapsack selections because the task’s decision space remains accessible through either approach. However, the persistent strategy accesses a more compact computational path (reusing state), while the stateless strategy paths through a larger textual‑state space (reconstruction). Mismatch introduces error modes that consume resources without improving outcomes.
- **Core assumption:** Opaque Knapsack is designed to be "non‑collapsible" but not exclusively solvable by one execution mode. Its partially observable nature forces multi‑step interaction, but both strategies can gather sufficient information through either persistent variable tracking or textual bookkeeping.
- **Evidence anchors:**
  - [abstract] "A 2×2 cross‑evaluation shows that solution quality (normalized optimality) does not vary significantly, but efficiency and stability differ substantially."
  - [table 2] Easy: Persistent→Persistent 81.1%, Persistent→Stateless 82.2%, Stateless→Persistent 81.4%, Stateless→Stateless 82.0%. Hard: 75.4%, 68.2%, 72.5%, 67.7%. No statistically significant differences in optimality ( Appendix E).
  - [section 4.3] "Notably, these efficiency and stability costs are not accompanied by a statistically significant reduction in solution quality."
  - [section 3.1] Task design with "budgeted tool access, strict partial observability, and per‑step interaction limits" that "enforces iterative information acquisition and plan revision" without mandating execution mode.
- **Break condition:** If the task were engineered such that only one strategy could succeed (e.g., a task requiring stateful mutation beyond textual reconstruction’s capacity), then solution quality would diverge. The non‑collapsible design must be balanced to test efficiency, not feasibility.

## Foundational Learning
### Concept: Behavioral Cloning from Synthetic Trajectories
- **Why needed here:** The paper fine‑tunes models on teacher‑generated interleaved reasoning‑action trajectories. Understanding that the model learns the *pattern* of interaction, including implicit execution semantics, is key. The teacher’s strategy (persistent or stateless) becomes the demonstration that shapes the student’s policy.
- **Quick check question:** When a model is fine‑tuned on trajectories where the teacher reuses variables across turns without redefinition, what implicit assumption about the runtime does the model absorb?

### Concept: Execution Semantics as Part of the Training Distribution
- **Why needed here:** The core insight is that the runtime used during trace generation is not a neutral scaffold but part of the data distribution. This connects to generalization bounds in imitation learning—the policy will be brittle if the deployment environment (including its execution contract) differs from that of the training demonstrations.
- **Quick check question:** If a model is trained on Python traces where all variables reset after each code block, what deployment runtime change would trigger a cascade of NameErrors?

### Concept: State Representation in Tool‑Augmented Agents
- **Why needed here:** The experiments contrast two loci for state: (1) persistent interpreter bindings (compressive, low textual overhead) and (2) context‑window textual reconstruction (high overhead). Understanding this trade‑off is essential to interpreting the "amnesia tax" and "state utilization" metrics.
- **Quick check question:** In a CodeAct agent, when might storing intermediate results in a Python list (persistent) be more efficient than printing them as text for re‑parsing (stateless)?

## Architecture Onboarding
### Component Map
- Task Generator: Opaque Knapsack procedural generator (Appendix A) outputs instances with hidden item attributes, capacity, and inspection budget.
- Teacher Agent Loop: CodeAct‑style system (Section B) that alternates reflection and action, enforces one‑code‑block‑per‑turn, and appends structured observations with runtime_state metadata.
- Trace Variant Generator: Runs the teacher in two modes (persistent vs. stateless), producing matched trajectory pairs.
- Dataset Pipeline: Validation filters (score, error density, repetitive loops) → message extraction (system, user, assistant, observation) → context‑aware truncation (head‑tail skeleton + middle backfill).
- Fine‑Tuning Engine: QLoRA on Qwen3‑8B (r=64) with AdamW, cosine schedule, FlashAttention, gradient checkpointing.
- Evaluation Harness: vLLM server serving adapters under controlled runtime conditions (persistent/stateless interpreter semantics), collecting optimality, token counts, step counts, and trace‑level diagnostics.
- Diagnostics Module: Parses execution logs for NameError patterns, assigns failure categories (constraint violation, execution instability, silent suboptimality), computes behavioral metrics (State Utilization, Imports/Step, Context/Interpreter Lifespan).

### Critical Path
1. Define the task’s non‑collapsibility criteria (budgeted inspection, hidden constraints) to force multi‑turn dependence.
2. Implement the two runtime semantics (persistent vs. reset) with identical tool APIs and observation formats.
3. Generate matched teacher traces for both regimes using the same base teacher model.
4. Apply identical validation and message extraction to both trace sets.
5. Fine‑tune separate adapters on each trace set.
6. Evaluate each adapter under both runtimes, logging all executions for post‑hoc analysis.
7. Aggregate outcome metrics (optimality, tokens) and trace‑level behavioral metrics.

### Design Tradeoffs
- **Token‑matched vs. episode‑matched training sets:** The paper matches by episodes, making the stateless dataset ~3.5× larger in raw tokens. This choice reveals the "amnesia tax" in the teacher traces but confounds token volume with learning signal. A token‑matched ablation would isolate learning efficiency.
- **Observability of interpreter state:** The runtime_state header exposes active_globals and last_step_globals names (but not values). This equalizes *structural* state observability across runtimes, isolating the *execution* contract difference. Removing this header would compound the difficulty and might mask pure persistence effects.
- **Teacher quality control:** The persistent teacher achieved slightly lower optimality (67.1% vs 74.5%) but similar success rates. The choice of teacher model and its own alignment to the runtime contract could influence the quality of the prior being taught.
- **Single‑task domain:** Using Opaque Knapsack isolates the variable cleanly but limits generality. The mechanisms should be validated across diverse tool‑use domains (e.g., web navigation, data analysis).

### Failure Signatures
- **Persistent‑trained in stateless runtime:** High rate of NameError/UnboundLocalError (~80% episodes), cascading recovery loops, elevated context lifespan (symbols referenced across many steps), low state utilization (true reuse impossible), moderate import rate (<1.0, incomplete adaptation).
- **Stateless‑trained in persistent runtime:** Very high import rate (~1.0 per step), zero state utilization, high redefinitions per step, elevated token count (~3.5×), but clean execution (no missing‑variable errors).
- **Both misaligned conditions:** Normalized optimality remains comparable to aligned conditions, but with higher cost or instability. Silent suboptimality dominates in Stateless→Persistent; execution instability dominates in Persistent→Stateless.

### First 3 Experiments
1. **Baseline cross‑evaluation replication:** Generate 100 Opaque Knapsack Easy instances, produce persistent and stateless teacher traces using Gemini 3 Flash. Fine‑tune Qwen3‑8B with QLoRA (r=64, 3 epochs). Evaluate both adapters under both runtimes. Verify: Persistent→Stateless should show ~80% NameError rate; Stateless→Persistent should show ~3.5× token increase vs Persistent→Persistent.
2. **Token‑matched training ablation:** Down‑sample the stateless trace set to match the total token count of the persistent set (~4.6M tokens). Fine‑tune and evaluate. Hypothesis: if the "amnesia tax" is purely a data‑volume effect, token‑matching should equalize performance; if it’s a *semantic* effect, the token‑matched stateless model will still show high import rate and token inefficiency at deployment.
3. **Component isolation: runtime header ablation:** Remove the runtime_state.active_globals and last_step_globals fields from observations. Repeat the Persistent→Stateless condition. Expected: NameError rate increases further because the model has less visibility into the state mismatch, potentially exacerbating cascading failures. This tests whether the structured metadata partly reveals the runtime shift.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Does interpreter persistence as a training‑time semantic have a statistically significant effect on solution quality (normalized optimality) in tool‑augmented agents?
- **Basis in paper:** Section 5 (Limitations) states: "Evaluation power: While our sample size (n=100 tasks per split) cleanly isolates massive behavioral and efficiency shifts, it is underpowered to conclusively resolve differences in absolute solution optimality." The observed optimality differences between fine‑tuned models across the 2×2 conditions were not statistically significant at this sample size.
- **Why unresolved:** The current evaluation used only 100 tasks per split, which may lack statistical power to detect modest but meaningful differences in optimality. Directional trends (e.g., Persistent→Persistent slightly higher on Hard) remain inconclusive due to large confidence intervals.
- **What evidence would resolve it:** A larger‑scale evaluation with more task instances (e.g., thousands) could provide sufficient power to determine whether persistence training meaningfully improves, degrades, or leaves unchanged final solution quality, ideally yielding robust p‑values and confidence intervals.

### Open Question 2
- **Question:** To what extent are the "amnesia tax" (increased token consumption) and failure modes (missing‑variable errors) attributable to the total token volume of the training data rather than the persistence semantic itself?
- **Basis in paper:** Section 5 (Limitations): "Token‑budget confounds: Matching training sets by episode rather than total tokens exposed the stateless‑trained model to substantially more raw text (~3.5×)." The stateless traces are longer, confounding token quantity with execution semantic.
- **Why unresolved:** The current dataset comparison conflates two factors: the model in the stateless condition saw both a different persistence contract and more total training tokens. Without isolating token volume from semantic, we cannot conclude that the efficiency gap is primarily due to the learned persistence prior.
- **What evidence would resolve it:** Controlled training experiments where persistent and stateless datasets are matched for total token count (e.g., by subsampling stateless traces or extending persistent ones) while keeping the semantic constant. If the efficiency/stability differences persist after token matching, the semantic is causal; if they vanish, token volume may be the main driver.

### Open Question 3
- **Question:** Do the observed effects of interpreter persistence as a learnable semantic generalize to other LLM architectures and to other partially observable, multi‑step tool‑use tasks?
- **Basis in paper:** Section 5 (Limitations): "Scope of generalization: Our controlled design cleanly isolates the variable of interest using a single task family and base model. Validating these findings across varied models and tasks is an important next step." The study was conducted solely with Qwen3‑8B and the Opaque Knapsack task.
- **Why unresolved:** The results could be specific to this model size/pretraining or to the knapsack domain’s structure. Different architectures may have varying capacities to infer or adapt to runtime changes; other tasks might exhibit different sensitivities to state management.
- **What evidence would resolve it:** Replication of the 2×2 study across multiple base models (e.g., different sizes, families like Llama, GPT) and a diverse set of non‑collapsible benchmarks (e.g., InterCode, ToolSandbox). Consistent findings would establish generality; divergences would map the boundary conditions.

### Open Question 4
- **Question:** How does the inclusion of structured runtime‑state metadata (e.g., the JSON header exposing active_globals and last_step_globals) interact with the learning of interpreter persistence and deployment robustness?
- **Basis in paper:** Section 5 (Limitations): "Co‑occurring protocol cues: Our runtime provided structured metadata about prior‑step interpreter symbols to equalize observability. Factorizing these visibility signals from pure persistence mechanics will further clarify how agents learn to manage memory." The header was held constant across regimes but may serve as an alternative information source.
- **Why unresolved:** The header presents a potential signal that could help models compensate for missing persistence or reinforce reliance on textual state. Its role was not systematically varied, yet it might explain why some mismatched deployments partially succeeded (e.g., 20% of persistent→stateless episodes solved without errors).
- **What evidence would resolve it:** Ablation experiments removing or altering the state header while keeping persistence constant, measuring impacts on error rates, token efficiency, and state reuse patterns. Additionally, probing model attention to header fields could reveal whether models leverage it as a substitute for persistent state.

## Limitations
- Teacher model configuration (temperature, top‑p, token budget) and instance generation seeds are undocumented, hindering exact replication.
- Evaluation harness specifics (vLLM flags, LoRA loading, error detection heuristics) are underspecified, risking variability in metrics.
- Experiments are confined to a single synthetic task (Opaque Knapsack); transfer to diverse agent domains remains unverified.

## Confidence
- Learned state‑management prior: High
- Amnesia tax as entrenched behavior: Medium
- Solution quality invariance: High
