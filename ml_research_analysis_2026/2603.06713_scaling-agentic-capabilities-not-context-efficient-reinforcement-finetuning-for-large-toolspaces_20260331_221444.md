# Scaling Agentic Capabilities, Not Context: Efficient Reinforcement Finetuning for Large Toolspaces

## Quick Facts
- **arXiv ID:** 2603.06713  
- **Source URL:** https://arxiv.org/abs/2603.06713  
- **Reference count:** 40  
- **Primary result:** A 4B SLM with ITL+PTC and rubric-based RFT achieves a Task Fulfillment score of 4.15/10 on MCP benchmarks, approaching the frontier Kimi-K2 baseline (4.38).

## Executive Summary
This paper addresses the limitations of small language models (SLMs) in large-tool environments, where eager tool loading, compounding errors, and sparse rewards hinder performance. The authors propose ATLAS, a reinforcement finetuning framework that combines adaptive tool loading (ITL) to bound context growth, programmatic tool orchestration (PTC) to stabilize long-horizon execution, and rubric-based rewards to provide dense and consistent supervision. On MCP benchmarks, a 4B SLM equipped with ITL, PTC, and rubric-based RFT reaches a Task Fulfillment score of 4.15/10, approaching the frontier Kimi-K2 baseline (4.38) while using far fewer parameters and a tighter context window. The work demonstrates that scaling agentic capabilities via structured execution and reward design can be more effective than merely scaling model size or context.

## Method Summary
ATLAS transforms the interaction with tools described in the Model Context Protocol (MCP) by replacing turn-by-turn JSON calls with a Python-based orchestration layer. The agent uses adaptive tool loading (ITL) to selectively fetch detailed tool schemas only when needed, preventing context saturation. It generates Python programs that call normalized MCPServer methods, storing intermediate results in program state rather than in the prompt, which reduces token usage and stabilizes long-horizon execution. The policy is trained via reinforcement finetuning (RFT) using the GRPO algorithm, with rewards derived from a set of structured rubrics (Task Fulfillment, Tool Appropriateness, Tool Grounding, Parameter Accuracy) that are generated offline by a strong LLM and evaluated by a smaller judge model (Qwen3-30B). This rubric-based approach densifies the learning signal and enables consistent advantage estimation, leading to significant improvements in task completion.

## Key Results
- A 4B SLM with ITL+PTC and rubric-based RFT attains a Task Fulfillment score of 4.15/10 on MCP benchmarks, nearly matching the frontier Kimi-K2 (4.38).
- Rubric rewards with an SLM judge (Qwen3-30B) outperform generic rewards with a frontier judge (3.87 vs 3.43 TF) and generic rewards with an SLM judge (3.87 vs 3.25).
- Adaptive tool loading reduces token consumption significantly (e.g., Qwen3-4B: 11,142 → 9,045 tokens), while programmatic orchestration improves cold-start Task Fulfillment from 2.36 to 2.94.

## Why This Works (Mechanism)

### Mechanism 1: Adaptive Tool Loading Bounds Context Growth
- **Claim:** ITL reduces token consumption and prevents context saturation by deferring full tool schemas until needed.  
- **Mechanism:** The agent decides which MCP server to query and selectively materializes detailed tool signatures only when constructing a specific tool call, keeping verbose definitions out of the context until they are functionally required.  
- **Core assumption:** The model can learn to anticipate future tool needs and make cost-effective loading decisions.  
- **Evidence anchors:** [section 2.2] "ITL preserves context for execution-critical information while enabling scalable reasoning over large and heterogeneous tool collections."; [section 5.3] Under ITL, token usage drops significantly (e.g., Qwen3-4B: 11,142 → 9,045 tokens).; [corpus] Weak direct evidence; neighboring papers discuss dynamic tool selection but not ITL specifically.  
- **Break condition:** Under-loading causes missing capability; over-loading erodes context savings. Without learning, cold-start ITL yields minimal gains.

### Mechanism 2: Programmatic Orchestration Stabilizes Long-Horizon Execution
- **Claim:** PTC replaces turn-by-turn JSON calls with executable Python, keeping intermediate state out of the prompt and enabling explicit control flow.  
- **Mechanism:** A single Python program coordinates all tool interactions; variables store intermediate results, and control structures (loops, conditionals) are native to the code rather than re-derived each step.  
- **Core assumption:** The model can generate syntactically and semantically correct Python that correctly uses the MCPServer abstraction.  
- **Evidence anchors:** [section 2.3] "intermediate results are stored in program state rather than surfaced to model, enabling compact, stateful execution without context overhead."; [section 5.2] PTC improves cold-start TF from 2.36 to 2.94 (∼25% gain) even without learning.; [appendix A] Scaffolding details (schema normalization, error hints) reduce code-generation brittleness.  
- **Break condition:** Code errors (incorrect function names, argument formats, output access) derail execution; scaffolding mitigates but does not eliminate all failures.

### Mechanism 3: Rubric-Based Rewards Enable Stable RL under Weak Supervision
- **Claim:** Task-specific rubrics decompose success into structured criteria, providing consistent supervision for RL and allowing small judges to replace frontier models.  
- **Mechanism:** For each task, a fixed set of weighted rubrics (Task Fulfillment, Tool Appropriateness, Tool Grounding, Parameter Accuracy) guides an SLM judge to score rollouts. This enforces consistent relative judgments during advantage estimation (GRPO) and densifies the learning signal.  
- **Core assumption:** Rubrics can capture essential dimensions of task success and be reliably evaluated by an SLM when guided.  
- **Evidence anchors:** [section 3.1] "rubric-based rewards... enforce consistent relative judgments, reduces variance... and improves supervision quality."; [section 5.4] Rubric-based RFT with SLM judge outperforms generic rewards with frontier judge (Qwen3-4B: 3.87 vs 3.43 TF) and generic rewards with SLM judge (3.87 vs 3.25).; [corpus] Yu et al. discuss structured evaluation improving RL stability in non-verifiable domains.  
- **Break condition:** Poorly designed rubrics (overlapping, unobservable, or misweighted criteria) inject noise; SLM judge may still be less reliable than frontier models for very complex tasks.

## Foundational Learning

#### Adaptive context management
- **Why needed:** To balance the cost of schema loading against the risk of missing capabilities.
- **Quick check:** Given a multi-server task, should the agent load a new server immediately after the first tool call or only when a specific function is required?

#### Code-based tool orchestration
- **Why needed:** PTC’s benefits depend on generating executable programs without repeated context injection.
- **Quick check:** How does the model convert "find the average temperature from the last week's data" into code when the weather tool returns a list of daily readings?

#### Composite reward optimization
- **Why needed:** Rubric scores are sparse per criterion but composite reward requires balancing trade-offs.
- **Quick check:** If a tool call is appropriate but arguments are imprecise, how should the model adjust future behavior?

#### Scaffolding compliance
- **Why needed:** The MCPServer abstraction is out-of-distribution; error hints provide recovery without full retraining.
- **Quick check:** When a tool returns "invalid parameter: 'limit' must be int", what does the model infer?

## Architecture Onboarding

**Component map:** MCPServer (normalizes tools) -> get_tools_info (adaptive loading) -> Code Interpreter (executes Python) -> Rubric Generator (GPT-5) produces rubrics -> Judge (Qwen3-30B) evaluates rollouts -> Composite reward -> RL Trainer (verl) updates policy.

**Critical path:**
1. Agent decides to explore a server → calls get_tools_info() → receives Python-format signatures.
2. Agent writes a Python program that calls mcp.method() for needed tools; interpreter executes and stores results in variables.
3. Errors trigger hint-rich messages; agent corrects via code revision in next rollout (not real-time).
4. Final answer extracted after program completion.
5. During training, rollouts sent to judge → rubric scores → composite reward → policy update.

**Design tradeoffs:**
- ITL reduces tokens but adds sequential decision overhead; may slow convergence if agent mispredicts needs.
- PTC increases per-call token cost (code vs JSON) but reduces turn count and makes state explicit; net efficiency depends on task length.
- Rubric complexity: 12 criteria strike a balance; more rubrics risk judge inconsistency, fewer lose granularity.
- SLM judge vs. frontier: SLMs are cheaper and, with rubrics, can outperform frontier generic judges, but may struggle with highly complex tasks.

**Failure signatures:**
- Context overflow: Agent repeatedly calls fetch_tools without executing, filling context.
- Code brittleness: Frequent AttributeError or TypeError despite scaffolding; indicates poor schema understanding.
- Reward hacking: Policies that game the SLM judge without improving true task fulfillment; monitored via held-out evaluation with o4-mini.
- Distribution shift: Drop on ATLAS-Test (unseen servers) indicates overfitting to training tool patterns.

**First 3 experiments:**
1. Baseline ISL (no RFT): Confirm cold-start failure (TF ~2.3-2.7) even with context control.
2. Add PTC to ITL (no RFT): Show execution stabilization (TF ~2.9) but still limited.
3. Apply rubric-based RFT to ITL+PTC: Achieve TF 4.15, nearing frontier baseline; compare with generic rewards to isolate rubric benefit.

## Limitations
- ATLAS codebase and MCPBench dataset are not publicly available, requiring custom reimplementation and potential fidelity loss.
- Rubric generation depends on proprietary GPT-5 and reference solutions, with unspecified parameters that critically affect training stability.
- Key training hyperparameters (reward weights, optimization steps) and evaluation judges (o4-mini) are proprietary, hindering exact reproduction.

## Next Checks

2. **PTC error resilience:** Inject controlled tool/API failures (invalid params, timeouts) to quantify recovery rate via interpreter error hints; track TF degradation vs. ISL.
3. **Rubric/judge sensitivity:** Train with multiple rubric sets (varying criteria/weights) and judges (GPT-4o, Claude-3.5-Sonnet); measure TF variance to isolate judge-criteria alignment effects.
