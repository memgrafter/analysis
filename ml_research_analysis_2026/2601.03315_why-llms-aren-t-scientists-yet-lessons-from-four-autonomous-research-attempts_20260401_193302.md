# Why LLMs Aren't Scientists Yet: Lessons from Four Autonomous Research Attempts

## Quick Facts
*   **arXiv ID:** 2601.03315
*   **Source URL:** https://arxiv.org/abs/2601.03315
*   **Reference count:** 40
*   **Primary result:** A pipeline of six LLM agents achieved a 25% success rate (1/4 runs) in autonomously producing a complete ML research paper accepted to a peer-reviewed conference, with three runs failing due to six recurring modes.

## Executive Summary
This study investigates whether state-of-the-art LLMs can autonomously conduct machine learning research. Using a six-agent pipeline orchestrated around a shared file repository, the system attempted four end-to-end research projects. One attempt succeeded in producing a paper accepted to the Agents4Science 2025 conference with reviewer scores ranging from borderline accept to strong accept. The three failures revealed six core limitations of current LLMs in scientific roles: susceptibility to training data defaults, implementation drift during code generation, context degradation across long tasks, overexcitement in evaluation, gaps in domain-specific intelligence, and weak scientific taste. The work concludes that while LLMs can contribute to research, full autonomy in generating novel, valid science remains an unsolved challenge.

## Method Summary
The core method is a modular, six-stage agentic pipeline. It begins with an **Idea Generation Agent** (Gemini 2.5 Pro) that combines two seed papers from a curated corpus to produce a structured research idea. This feeds a **Hypotheses Generation Agent** (Gemini 2.5 Pro) that creates a suite of testable hypotheses. An **Experiment Planning Agent** (Gemini 2.5 Pro) then generates a detailed execution plan. Implementation and initial writing are handled by **Claude Code** (Claude Opus 4.1/Sonnet 4) on Modal infrastructure, using tools (`read file`, `write file`, `llm search`, `list files`) to interact with a shared repository. After execution, an **Output Evaluation Agent** (Gemini 2.5 Pro) assesses results for fidelity and validity; upon failure, a **Revision Agent** (Gemini 2.5 Pro) decides corrective actions. Finally, a **Paper Outlining Agent** (Gemini 2.5 Pro) creates an outline for Claude Code to expand into a full paper. State is persistently managed via the shared repository, and a "portfolio" approach to hypotheses was adopted to increase resilience.

## Key Results
*   **Success Rate:** 1 of 4 autonomous research attempts completed the full pipeline and was accepted to the Agents4Science 2025 conference.
*   **Review Scores:** The accepted paper received scores of 4-6/6 from AI reviewers and a score of 4 from the human reviewer.
*   **Failure Modes:** The three failed runs identified six recurring issues: bias toward training data defaults, implementation drift, memory/context degradation, overexcitement in evaluation, insufficient domain intelligence, and weak scientific taste.

## Why This Works (Mechanism)

### Mechanism 1: Repository-Based State Persistence
*   **Claim:** The shared repository-based file system enables state persistence and context propagation across long-horizon, multi-agent tasks.
*   **Mechanism:** Agents read from and write structured artifacts (e.g., `idea.md`, `hypotheses.md`) to a shared repository, which is included in their system prompt. This decouples state from the LLM's context window, allowing successive agents to retrieve prior decisions.
*   **Break condition:** As file count and content length grow, agents lose track of earlier decisions, leading to redundancy, inconsistency, or forgotten motivation.

### Mechanism 2: Staged Verification with Revision Loops
*   **Claim:** Dedicated output evaluation and revision agents prevent error propagation and allow course correction.
*   **Mechanism:** The Output Evaluation Agent reviews experiment outputs for fidelity and validity. If failures are found, the Revision Agent decides whether to revise the idea, hypotheses, or request external feedback, creating a feedback loop to isolate issues.
*   **Break condition:** When evaluation relies on LLM-generated summaries instead of raw logs, overexcitement may mask failures; context degradation can also lead to misinterpretation.

### Mechanism 3: Portfolio of Hypotheses
*   **Claim:** Generating a suite of hypotheses (rather than a single one) reduces project risk and allows incremental adaptation.
*   **Mechanism:** If one experiment fails, the Revision Agent can adjust or replace individual hypotheses while preserving the core idea, increasing the chance of at least one successful branch.
*   **Break condition:** If all hypotheses share a common bias or dependency (e.g., on an unavailable library), the portfolio provides no resilience; managing many hypotheses strains context.

## Foundational Learning
*   **Concept:** Multi-Agent Orchestration
    *   **Why needed here:** Pipeline performance depends on correct handoffs between six specialized roles; understanding each agent’s input/output is key to diagnosing bottlenecks.
    *   **Quick check:** What artifact does the Idea Generation Agent output, and which agent consumes it next?
*   **Concept:** Repository-Based Context Management
    *   **Why needed here:** The shared file system is the backbone of state persistence; its strengths/weaknesses explain both coordination and context degradation.
    *   **Quick check:** Which tools do agents use to interact with the repository, and what instruction ensures they read the correct files?
*   **Concept:** Verification-Driven Revision Loops
    *   **Why needed here:** The “Verify Everything” principle is the primary safeguard against error cascades; it shapes system response to failures.
    *   **Quick check:** What are the two main axes of verification described (process vs. outcome; correctness vs. contribution)?

## Architecture Onboarding
*   **Component map:**
    Idea Generation Agent -> Hypotheses Generation Agent -> Experiment Planning Agent -> Claude Code (execution) -> Output Evaluation Agent -> Revision Agent -> Paper Outlining Agent -> Claude Code (writing)
*   **Critical path:**
    1.  Idea Generation Agent outputs `idea.md`.
    2.  Hypotheses Generation Agent outputs `hypotheses.md`.
    3.  Experiment Planning Agent outputs `plan.md` & `agent.md`.
    4.  Claude Code executes plan on Modal, producing code files, logs, `output.py`.
    5.  Output Evaluation Agent assesses; on failure, triggers Revision Agent.
    6.  Paper Outlining Agent outputs `paper_outline.md`.
    7.  Claude Code writes full paper from outline for submission.
*   **Design tradeoffs:**
    *   Autonomy vs. oversight: Higher autonomy risks undetected errors; humans still review ideas and final sanity.
    *   Generality vs. domain specificity: Pipeline targets computational ML broadly, but success required simpler domains (AI Safety) over complex ones (World Models, MARL).
    *   Early abstraction vs. feasibility: Starting abstract reduces training bias but may yield infeasible plans; grounding later risks drift if unmanaged.
    *   Verification thoroughness vs. cost: Raw log inspection is reliable but time-consuming; initial reliance on LLM summaries caused overexcitement.
    *   Single- vs. multi-model: Using Gemini for most agents simplifies coordination but inherits its biases; mixing Claude adds complexity but may mitigate weaknesses.
*   **Failure signatures:**
    *   Bias on training data: Agents revert to deprecated libraries or standard dataset formats against instructions.
    *   Implementation drift: Code generation simplifies or abandons core innovations after errors/timeouts.
    *   Memory/degradation: Agents ignore earlier configs, redefine hyperparameters, duplicate code, forget original motivation.
    *   Overexcitement: Evaluation declares success despite clear failures (e.g., dummy rewards); writing inflates claims.
    *   Insufficient domain intelligence: Poor baseline choices, misunderstanding algorithmic requirements, inability to predict interactions.
    *   Weak scientific taste: Untestable hypotheses, irrelevant complexity, failure to notice low baseline performance.
*   **First 3 experiments:**
    1.  **Baseline end-to-end run:** Execute the pipeline on a minimal idea (e.g., “Test batch normalization on CIFAR-10”). Verify all agents produce expected artifacts and code runs within resource limits.
    2.  **Bias injection:** Provide an idea requiring a non-canonical library or dataset field (e.g., “Use HarmBench’s context field”). Check if Execution Agent follows instructions or reverts to a memorized default (e.g., using `prompt`/`response` columns).
    3.  **Verification loop stress test:** Design a hypothesis with an unrealistic claim (e.g., “>95% accuracy on MNIST with one epoch”). Ensure Output Evaluation Agent flags the result and Revision Agent triggers hypothesis revision rather than idea abandonment.

## Open Questions the Paper Calls Out
*   **Open Question 1:** What is the statistical prevalence and relative impact of the six failure modes (training data bias, implementation drift, memory issues, overexcitement, domain intelligence gaps, weak scientific taste) in autonomous ML research systems?
*   **Open Question 2:** Which architectural or procedural interventions most effectively prevent implementation drift during autonomous code generation while preserving research fidelity?
*   **Open Question 3:** How can we build comprehensive datasets capturing the full scientific workflow—including failed experiments, negative results, and tacit expert decisions—to train and evaluate autonomous research agents?
*   **Open Question 4:** What objective metrics can reliably assess the quality, reproducibility, and novelty of AI-generated research, reducing dependence on peer review?

## Limitations
*   The exact prompt templates and system messages for all six agents are not publicly disclosed, blocking precise replication of mitigations for failure modes.
*   Generalizability is limited; success was only achieved in the simpler AI Safety domain, not in more complex targets like World Models or MARL, indicating strong domain dependence.
*   The repository-based state management has a noted scalability break condition: context degradation as file volume grows, which was not stress-tested.

## Confidence
*   **Claim:** 25% success rate (1/4 attempts achieved conference acceptance). **Confidence:** High.
*   **Claim:** Six failure modes are the primary reasons for the three failures. **Confidence:** High.
*   **Claim:** The shared repository is the primary mechanism enabling state persistence across agents. **Confidence:** Medium.
*   **Claim:** The "portfolio of hypotheses" approach increased resilience. **Confidence:** Medium.
*   **Claim:** Findings generalize beyond the specific AI Safety domain used for the successful run. **Confidence:** Low.
