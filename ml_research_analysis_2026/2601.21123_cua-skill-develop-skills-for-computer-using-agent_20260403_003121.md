# CUA-Skill: Develop Skills for Computer Using Agent

## Quick Facts
- **arXiv ID:** 2601.21123
- **Source URL:** https://arxiv.org/abs/2601.21123
- **Reference count:** 25
- **Primary result:** CUA-Skill achieves 76.4% trajectory generation success and 57.5% best-of-three success on WindowsAgentArena with ≤30 steps while using fewer execution steps than prior methods.

## Executive Summary
Computer-using agents (CUAs) have long suffered from a lack of reusable, structured skill abstractions, limiting their scalability and reliability relative to human performance. This paper introduces CUA-Skill, a large-scale library of parameterized skills for Windows applications, where each skill is defined by an execution graph (encoding GUI/script actions) and a composition graph (enabling skill chaining). Built on this library, the CUA-Skill Agent dynamically retrieves appropriate skills, instantiates arguments, and employs memory-aware failure recovery to complete user instructions. Evaluations on the WindowsAgentArena benchmark show state-of-the-art results: a 57.5% best-of-three success rate while using at most 30 execution steps. The skill library itself yields a 76.4% success rate in trajectory generation, representing a 1.7×–3.6× improvement over prior approaches. This work demonstrates the power of structured, reusable procedural knowledge for building reliable computer automation agents.

## Method Summary
The CUA-Skill system consists of a curated skill library and a retrieval-augmented agent. The library contains 478 atomic skills across 17 Windows applications; each skill S is formally defined as {τ, I, A, G_e}, where τ is the target application, I a minimal natural language intent description, A an argument schema with feasible domains, and G_e a parameterized execution graph—a directed graph of base actions (e.g., clicks, keystrokes) with conditional edges guarded by UI predicates. The agent operates by repeatedly: taking the user instruction and interaction history, generating multiple retrieval queries with a planner (M_p), fetching candidate skills via a hybrid lexical/semantic retriever, re-ranking the candidates (including basic GUI primitives as fallback), configuring concrete argument values respecting domains, and executing the skill by traversing G_e with a GUI grounding model. After each step, a memory buffer stores a summary of the executed skill and its outcome to inform future planning and avoid repeating mistakes.

Reproducing the full system is hindered by the absence of a released skill library and key implementation details (e.g., retrieval hyperparameters K and L, exact LLM prompts, grounding model choice, and memory format). The WindowsAgentArena benchmark is also not publicly accessible in its evaluation configuration. A minimal reproduction would involve manually defining a small skill subset (e.g., for File Explorer and Calculator), implementing the retrieval-augmented loop with an LLM API, and testing in a Windows VM. However, large-scale replication and evaluation remain infeasible without the original assets and precise settings.

## Key Results
- CUA-Skill library attains a 76.4% success rate in trajectory generation, outperforming prior methods by 1.7×–3.6×.
- CUA-Skill Agent reaches a state-of-the-art 57.5% best-of-three success rate on the WindowsAgentArena benchmark while limiting execution to at most 30 steps.
- The library comprises 478 atomic skills covering 17 Windows applications, showing broad coverage and transferability.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Encoding human computer-use knowledge as reusable, parameterized skills with execution and composition graphs bridges the abstraction gap between high-level user intent and low-level GUI actions, enabling transferable procedural knowledge.
- **Mechanism:** The skill abstraction (`S := {τ, I, A, G_e}`) packages a minimal user intent (`I`), an application context (`τ`), an argument schema (`A`) with feasible domains, and a parameterized execution graph (`G_e`). The execution graph encodes multiple valid realization paths (GUI primitives or scripts) conditioned on arguments and guarded by UI predicates. This allows the same skill to be instantiated differently across UI states and tasks.
- **Core assumption:** Human computer interaction is compositional and can be decomposed into reusable, parameterized procedural units that generalize across contexts.
- **Evidence anchors:**
  - [abstract] Introduces "reusable and structured skill abstractions" with "parameterized execution and composition graphs."
  - [section 3] Formal skill definition `S := {τ, I, A, G_e}` and description of execution graphs as "parameterized structured space of valid interaction paths."
  - [corpus] Related work (SoK: Agentic Skills) discusses "reusable procedural capabilities, a.k.a., agentic skills" but does not provide direct evidence for the specific graph-based parameterization.
- **Break condition:** If argument instantiations frequently violate feasible domains (`D(A)`) during execution, the skill's parameterization fails to capture realizable interactions, causing downstream planning errors.

### Mechanism 2
- **Claim:** Dynamic skill retrieval, re-ranking, and argument instantiation conditioned on current UI state and memory allow the agent to select appropriate procedural building blocks without hard-coding workflows.
- **Mechanism:** At each step, the planner (`M_p`) generates multiple queries (`Q_t`), a hybrid retriever (lexical + semantic) fetches top-k candidate skills (`C_t`), a re-ranker selects the most promising skill considering context and memory, and a configurator instantiates arguments within feasible domains. This retrieval-augmented loop adapts to the immediate environment.
- **Core assumption:** A sufficiently expressive skill library (`S`) contains skills relevant to most user goals, and semantic/lexical retrieval can match natural language queries to skill descriptions (`I`).
- **Evidence anchors:**
  - [abstract] Agent supports "dynamic skill retrieval, argument instantiation, and memory-aware failure recovery."
  - [section 4] Algorithm 1 details the retrieve-augmented planning loop (lines 5-10) and components (query generator, retriever, reranker, configurator).
  - [corpus] Neighbors like "Agent Skills for Large Language Models" discuss modular skill architectures but do not validate the specific retrieval-augmented, state-conditioned selection process.
- **Break condition:** If retrieval consistently returns irrelevant skills for a given UI state and goal, or if argument instantiation produces values outside `D(A)`, the agent cannot progress, indicating skill library coverage or retrieval alignment issues.

### Mechanism 3
- **Claim:** Memory-aware failure recovery mitigates error compounding by recording executed skills and outcomes, enabling the planner to avoid repeating ineffective actions and explore alternative paths.
- **Mechanism:** After each skill execution, a summary of `(skill, outcome)` is appended to a memory buffer (`M`). The planner queries this memory during subsequent steps to reason about past mistakes and adapt its strategy, avoiding loops and incorrect skill selections.
- **Core assumption:** Failures are partially observable and can be diagnosed from execution outcomes; recording them in a persistent buffer provides a signal for future planning.
- **Evidence anchors:**
  - [abstract] Mentions "memory-aware failure recovery."
  - [section 4.5] Explicitly describes memory storing "summaries that captures both the skill’s intent and its resulting effect" and using it to "reason about prior mistakes, avoid repeatedly selecting ineffective actions."
  - [corpus] Neighbors (e.g., Mem0) address long-term memory for agents but do not provide evidence for the specific failure-recovery loop tied to skill execution graphs.
- **Break condition:** If the memory buffer becomes saturated with noisy or misdiagnosed failure summaries, or if the planner cannot effectively query memory to adjust its behavior, the recovery mechanism degrades and error cycles persist.

## Architecture Onboarding
#### Component Map
- Skill Library (`S`): 478 atomic skills across 17 apps; each with execution (`G_e`) and composition (`G_c`) graphs.
- Agent Loop: Planner (`M_p`) → Query Generator → Retriever (hybrid) → Reranker (+ basic skills) → Configurator → Executor (GUI grounding + script) → Memory.

#### Critical Path
User instruction → planner query generation → retrieval → reranking → argument configuration → execution → memory update → next step. Failure at any stage (retrieval, configuration, grounding) breaks the loop.

#### Design Tradeoffs
- Skill authoring effort vs. transferability: Carefully engineered graphs yield high reliability (76.4% success) but require manual effort; auto-generated graphs might reduce coverage.
- Retrieval budget (`K`, `L`) vs. computation: Smaller top-k speeds up planning but risks missing relevant skills.
- Basic skill fallback vs. high-level abstraction: Fallback ensures robustness but increases step count if overused.

#### Failure Signatures
- Retrieval returns off-domain skills → reranker picks irrelevant skill → execution fails.
- Configurator generates argument outside `D(A)` → executor cannot ground/execute.
- Memory contains false negatives (recorded failures for actually viable paths) → planner avoids correct skills.
- Grounding model errors on coordinates → primitive action fails despite correct skill.

#### First 3 Experiments
1. **Skill library validation:** Sample 1,000 parameterized tasks from composition graphs; measure execution success rate (expect ~76.4%). Isolate failures by application (e.g., VLC lower due to media UI complexity).
2. **Agent end-to-end on WAA:** Run CUA-Skill Agent with GPT-5; record best-of-three success rate (expect 57.5%) and steps (≤30). Compare against no-skill baseline (Table 5) to quantify skill integration gain.

## Limitations
- The full CUA-Skill library (478 skills with detailed execution/composition graphs) is unreleased, blocking direct replication and large-scale evaluation.
- Critical hyperparameters (retrieval `K`, `L`), LLM prompts, memory format, grounding model, and "low reasoning" settings are undocumented.
- WindowsAgentArena benchmark details (task split, environment setup, official evaluation protocol) are referenced but not provided.
