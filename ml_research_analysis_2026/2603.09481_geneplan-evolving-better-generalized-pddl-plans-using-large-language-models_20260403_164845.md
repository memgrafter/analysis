# GenePlan: Evolving Better Generalized PDDL Plans using Large Language Models

## Quick Facts
- **arXiv ID:** 2603.09481
- **Source URL:** https://arxiv.org/abs/2603.09481
- **Reference count:** 40
- **Primary result:** GenePlan achieved a mean SAT score of 0.91, comparable to state-of-the-art planners (0.93), and significantly outperformed chain-of-thought baselines (0.64).

## Executive Summary
GenePlan tackles generalized PDDL planning by evolving interpretable Python planners via an LLM-driven evolutionary algorithm. It optimizes average plan length across training instances, producing planners that quickly solve new problems (0.49 s/task) at low generation cost ($1.82/domain with GPT-4o). On eight domains, GenePlan reaches near state-of-the-art performance (SAT 0.91 vs. 0.93) and far surpasses chain-of-thought approaches (0.64). The method bridges large language model code generation with evolutionary search, offering a practical path to automated heuristic synthesis.

## Method Summary
GenePlan formalizes generalized planning as optimizing a parameterized Python function Φ over a distribution of PDDL tasks. It maintains a population of candidate planners and iterates for a fixed number of generations. In each generation, planners are selected with probability proportional to exp(−fitness/T), where fitness is the mean plan length on training tasks (with a large penalty F for failures). Selected planners are provided as few-shot examples in a prompt to an LLM, which generates new offspring via code crossover and mutation. Offspring are validated by an AST parser, then executed on training tasks to compute fitness. The population is updated via µ+λ elitist replacement (best µ from combined pool). Hyperparameters include population size µ=10, offspring λ_max=10, and a temperature schedule decaying hyperbolically from T_max=50 to T_min=10. After evolution, the best planner is deployed to solve test instances.

## Key Results
- **Near-optimal quality:** Mean SAT score 0.91 across eight domains, comparable to hand‑tuned state‑of‑the‑art planners (0.93) and well above chain‑of‑thought baselines (0.64).
- **Fast inference & low cost:** Solves new tasks in 0.49 s on average; generation cost $1.82 per domain with GPT‑4o.
- **Interpretable output:** Generated Python planners are human‑readable and can be inspected or debugged.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** GenePlan uses an evolutionary algorithm to iteratively improve Python planners by recombining and mutating code, guided by a fitness function based on plan length.
- **Mechanism:** A population of candidate planners is maintained. Each generation, planners are selected with probability inversely related to their fitness (shorter plans have higher chance). Selected planners' code is combined via an LLM prompt (crossover/mutation) to generate new offspring. The new planners are evaluated on training tasks, and the population is pruned to the best performers (µ+λ selection).
- **Core assumption:** The LLM can effectively perform "crossover" (merging logical segments from different planners) and "mutation" (introducing efficiency‑improving changes) when provided with code examples and their performance feedback.
- **Evidence anchors:**
  - [abstract]: "iteratively evolves interpretable Python planners that minimize plan length across diverse problem instances."
  - [section 4]: Detailed pseudocode (Algorithm 1) and description of selection (Eq. 3), prompt construction with `@@examples@@`, and µ+λ replacement strategy.
  - [corpus]: Related work on "Evolutionary LLMs" (Romera‑Paredes et al. 2024) supports the paradigm, but direct evidence for GenePlan's specific implementation is internal.
- **Break condition:** If the LLM consistently generates syntactically invalid or functionally broken code (caught by AST parser), or if selection probabilities become so skewed that genetic diversity is lost, halting improvement.

### Mechanism 2
- **Claim:** The LLM acts as a stochastic code generator and modifier, where its output is constrained and evaluated in a closed loop, turning natural language instructions into executable planning heuristics.
- **Mechanism:** The LLM is prompted with the PDDL domain, a few‑shot set of previous planners (code + success/failure feedback), and specific "evolutionary optimization instructions" to produce a new Python `get_plan` function. This function is then executed on real PDDL problems to measure its fitness.
- **Core assumption:** The LLM has sufficient procedural knowledge of Python, PDDL semantics, and planning heuristics to generate functionally correct code from the prompt pattern, and to improve upon examples when given clear fitness signals.
- **Evidence anchors:**
  - [section 4]: Prompt template (Listing 2) explicitly structures the input: domain, examples with system feedback (error messages or scores), and instructions to "perform crossover" and "apply mutations."
  - [section 4]: AST parser serves as a guardrail, ensuring only syntactically valid Python proceeds to execution and fitness evaluation.
  - [corpus]: Neighboring papers like "LLM+P" and "Generalized Planning with Pretrained LLMs" explore similar code‑generation‑from‑PDDL, indicating the approach's plausibility but not direct replication.
- **Break condition:** If the LLM fails to generate valid Python after multiple attempts (high rejection rate by AST parser), or if generated planners consistently fail validation on trivial instances despite correct syntax, indicating a semantic gap in the LLM's planning knowledge.

### Mechanism 3
- **Claim:** Fitness evaluation via plan length on a held‑out set of training tasks provides a gradient for optimization, steering the population toward planners that produce shorter, higher‑quality plans.
- **Mechanism:** For each candidate planner, it is executed on every training PDDL problem. The length of the resulting valid plan is recorded; unsolvable tasks incur a large failure penalty F. The fitness score is the mean plan length (or F‑adjusted) across all training tasks. This scalar score drives selection.
- **Core assumption:** Minimizing average plan length on the training set correlates with producing a generalized planner that will also generate short, high‑quality plans on unseen test instances from the same domain distribution.
- **Evidence anchors:**
  - [section 2.3]: Explicitly defines the generalized planning optimization problem (Equation 1) with plan length c(π)=|π| as the cost.
  - [section 4]: "fitness function simply computes the average plan length... ˆf(Φ) = 1/|Πtrain| Σ |Φ(Π)|" and uses a failure score F≫0.
  - [section 6]: Results show the evolved planners (evo) achieve SAT scores (relative to best‑known plans) comparable to optimal planners (0.91 vs 0.93), supporting that the fitness function effectively optimized for plan quality.
  - [corpus]: The use of SAT score from IPC as an evaluation metric is standard, but the specific link between training‑set length minimization and test‑set SAT is demonstrated in their experiments.
- **Break condition:** If the fitness landscape is deceptive—e.g., a planner that is short on training tasks fails catastrophically on test tasks due to overfitting or missing critical constraints—or if the failure penalty F is not sufficiently large, causing unsolvable instances to be treated as equivalent to very long plans.

## Foundational Learning

- **Concept: Evolutionary Algorithms (Population, Selection, Variation)**
  - **Why needed here:** GenePlan's core loop is an evolutionary algorithm. Understanding population (P(t)), fitness‑based selection (Boltzmann/rank‑based), µ+λ replacement, and the roles of variation (here, LLM‑driven) vs. selection is essential to grasp how code improves over generations.
  - **Quick check question:** What would happen to genetic diversity if the temperature T in the selection probability (Eq. 3) was set too low from the first generation?

- **Concept: PDDL (Planning Domain Definition Language) and Classical Planning**
  - **Why needed here:** The entire problem input is a PDDL domain and problem instances. The output planner must interpret objects, init, and goal tuples and generate valid PDDL action strings. Misunderstanding predicate semantics or action preconditions/effects would lead to invalid plans.
  - **Quick check question:** Why is the `deposit` action in the Trading domain's preconditions `(containsinventory ?i ?l)` and not just `(at ?i ?l)`? What state change does `(deposited ?r ?i)` represent?

- **Concept: Large Language Models as Code Generators & Few‑Shot Learning**
  - **Why needed here:** The LLM is the "variation operator." The engineer must understand that the LLM is not executing code but generating it based on a prompt pattern. The quality of the `@@examples@@` (code + feedback) directly determines the usefulness of offspring.
  - **Quick check question:** In the prompt template, what is the functional purpose of including `{planner.plan_failure_error}` and `{planner.score}` for poorly performing examples? How does this differ from just showing correct code?

## Architecture Onboarding

- **Component map:**
  1. **PlannerDB:** Stores all candidate `Planner` objects (code, fitness, feedback). Manages selection (`select_planners`), prompt construction (`generate_prompt`), and population replacement (`reset_planner_db`).
  2. **GenePlan (Orchestrator):** Runs the main `fit` loop. Calls `PlannerDB.get_prompt()`, queries the LLM, creates `Planner` objects, and calls `evaluate_fitness`.
  3. **Planner:** A wrapper for a string of Python code. Methods to `get_planner()` (compile/execute code to get `get_plan` function), `evaluate_fitness` (run on tasks), and `add_feedback` (generate system message).
  4. **LLM Interface:** External API (e.g., GPT‑4o). Called with the prompt, returns `samples_per_prompt` code strings.
  5. **PDDL validator:** External tool (Unified Planning Framework) to parse the generated plan string and validate it against the PDDL problem.
  6. **Task:** A simple container for a PDDL domain string and a problem file.

- **Critical path:** `GenePlan.fit()` → `PlannerDB.get_prompt()` → `LLM.draw_samples()` → `Planner` creation → `Planner.get_plan()` execution on tasks → `PlanValidator.validate()` → score computation → `PlannerDB.add_planner()` → population reset when `reset_period` reached.

- **Design tradeoffs:**
  - **Cost vs. Quality:** Using a more powerful/expensive LLM (GPT‑4o vs. mini) yields better planners but higher API cost. The paper shows a significant quality gap.
  - **Generality vs. Efficiency:** GenePlan produces a single, fast Python planner for a domain. This is efficient for many inferences but cannot adapt online to a single novel instance like a search‑based planner could.
  - **Interpretability vs. Automation:** Generated Python code is interpretable, but the evolutionary process is a black box. Debugging why a particular mutation failed requires examining code and prompts.
  - **Hyperparameter Sensitivity:** µ (pop size), λ_max (offspring per gen), T_max/T_min (selection pressure), and G (generations) control exploration/exploitation. The paper uses fixed values; tuning might be domain‑specific.

- **Failure signatures:**
  1. **High AST rejection rate:** Most LLM outputs are not valid Python. *Action:* Check prompt clarity, LLM temperature, or consider a simpler initial seed.
  2. **100% failure penalty (F) on training tasks:** Generated planners compile but never produce a valid plan. *Action:* Inspect generated code logic; PDDL predicate/object name handling may be flawed (see `evo_abl` failure).
  3. **No fitness improvement over generations:** Population stagnates. *Action:* Check temperature decay—if T drops too quickly, exploitation kills diversity. May need more generations or larger λ_max.
  4. **Planner solves training but fails test:** Overfitting to training instances. *Action:* Increase diversity of training tasks or adjust fitness to include a simplicity prior (not in current paper).

- **First 3 experiments:**
  1. **Single‑Generation Smoke Test:** Seed `PlannerDB` with one correct, simple planner (e.g., the `heavypack` initial planner from Appendix B). Call `GenePlan.fit()` for G=1 with `samples_per_prompt=1`. Verify you get one new offspring, its fitness is computed, and the population updates. Goal: Confirm the end‑to‑end loop works without LLM variability.
  2. **AST Validation & Execution Sandbox:** Manually take a code string from the paper's Appendix B (e.g., `heavypack - Initial Planner`). Pass it to `Planner.get_planner()`. Confirm it compiles. Then create a minimal `heavypack` PDDL problem and call `planner.get_plan()`. Goal: Isolate the code execution environment and verify it can produce a valid plan list.
  3. **Fidelity Check on a Known Domain:** Use the `trapnewspapers` domain. Seed with the provided initial planner. Run evolution for a few generations with GPT‑4o (or a mock LLM that returns slightly modified copies). Track the best fitness score per generation. Expect: Score should improve (mean plan length decrease) towards the optimal value reported in Table 1 (~1.0 SAT). Goal: Verify the optimization loop can actually improve a known‑good heuristic.

## Open Questions the Paper Calls Out

- **Open Question 1:** What early stopping criteria can effectively terminate GenePlan's evolutionary process before convergence without compromising plan quality, thereby reducing generation time and computational cost?
  - **Basis in paper:** [explicit] The conclusion explicitly states "The first involves developing early stopping criteria to reduce the computational cost of planner generation."
  - **Why unresolved:** The paper currently uses a fixed number of generations (G=10) and doesn't explore stopping criteria that could detect when further evolution yields diminishing returns.
  - **What evidence would resolve it:** Empirical studies comparing different early stopping heuristics (e.g., plateau detection, performance threshold, LLM‑based confidence estimation) across multiple domains, measuring both computational savings and final plan quality.

- **Open Question 2:** Beyond minimizing plan length, what additional optimization metrics (e.g., plan robustness to uncertainty, resource consumption, temporal constraints) can be incorporated into GenePlan's fitness function to produce more practically useful planners?
  - **Basis in paper:** [explicit] The conclusion states "new optimization metrics beyond plan length should be investigated."
  - **Why unresolved:** The current fitness function solely minimizes average plan length across training instances, which may not capture all relevant quality aspects in real‑world applications.
  - **What evidence would resolve it:** Case studies in specific domains where alternative metrics (e.g., minimizing peak resource usage, maximizing plan reliability under stochasticity) lead to demonstrably better outcomes, along with modified evolutionary frameworks that can optimize multi‑objective or constrained fitness functions.

- **Open Question 3:** For which classes of planning domains and problem structures does GenePlan's generalized planning approach provide advantages over traditional search‑based planners, and what characterizes domains where it fails (e.g., Sokoban)?
  - **Basis in paper:** [inferred] The paper notes GenePlan "tried to build a search algorithm" and failed on Sokoban, suggesting some domains lack "simple, generalizable strategies." Section 6 states: "In such domains, exhaustive or heuristic search remains necessary."
  - **Why unresolved:** The paper evaluates on 8 domains but doesn't systematically characterize which domain features predict success for the generalized planning paradigm versus search.
  - **What evidence would resolve it:** A comprehensive empirical study across a diverse set of PDDL domains, analyzing correlations between domain characteristics (e.g., presence of irreversible actions, state space topology, strategy simplicity) and GenePlan's relative performance compared to search planners.

- **Open Question 4:** How do state‑of‑the‑art open‑source LLMs (e.g., Deepseek‑V3, R1) compare to GPT‑4o in terms of cost, generation time, and final plan quality when used within GenePlan's evolutionary framework?
  - **Basis in paper:** [explicit] The paper acknowledges: "We would like to highlight that while our experimental analysis used proprietary models (GPT‑4o and GPT‑4o mini), newer, open source models such as Deepseek‑V3 and R1 are available and have shown superior performance on math and coding benchmarks."
  - **Why unresolved:** All experiments used GPT‑4o/mini; the potential advantages of newer models remain untested.
  - **What evidence would resolve it:** Direct comparative experiments using Deepseek‑V3, R1, and other recent models in identical GenePlan setups, measuring SAT scores, generation costs, and generation times across the same benchmark domains.

- **Open Question 5:** How sensitive is GenePlan's performance to the choice of evolutionary algorithm hyperparameters (population size µ, offspring count λ_max, temperature schedule), and can adaptive parameter schemes improve robustness across diverse domains?
  - **Basis in paper:** [inferred] The paper fixes µ=10, λ_max=10, and uses a hyperbolic temperature decay with T_max=50, T_min=10 without exploring alternatives. The evolutionary algorithm's design choices are taken from prior work but may not be optimal for PDDL planning.
  - **Why unresolved:** No ablation studies on these parameters; optimal settings could vary by domain complexity.
  - **What evidence would resolve it:** Systematic parameter sweeps and sensitivity analyses across multiple domains, potentially leading to adaptive schemes that adjust parameters based on intermediate performance signals.

## Limitations
- Incomplete specification of key hyperparameters (e.g., `planners_per_prompt`, LLM temperature schedule) and AST validation rules impedes faithful reproduction.
- Training/test instance generation protocols are not fully described, leading to potential variability in evaluation.
- Reliance on proprietary GPT‑4o raises questions about portability to open‑source models and the impact of LLM capabilities on results.

## Confidence
- **Effectiveness** (SAT 0.91 vs SOTA 0.93): Medium (lacks statistical tests and full problem details; reproduction may show variability).
- **Mechanism** (LLM‑driven evolution + length fitness): Medium (the described loop is plausible but not independently validated; break conditions not quantified).
- **Practicality** (runtime efficiency): High (simple Python execution). **Cost**: Medium (dependent on token usage and API pricing).
