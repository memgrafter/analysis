# Lost in Execution: On the Multilingual Robustness of Tool Calling in Large Language Models

## Quick Facts
- **arXiv ID**: 2601.05366
- **Source URL**: https://arxiv.org/abs/2601.05366
- **Reference count**: 33
- **Primary result**: Despite strong tool-calling performance in English, LLMs exhibit systematic failures on multilingual queries due to parameter value language mismatch.

## Executive Summary
This paper investigates the robustness of tool-calling large language models (LLMs) when user queries are in languages other than English. The authors find that, although LLMs can correctly identify the intended tool and understand the query's semantics, they often generate parameter values in the language of the query rather than the English-only strings required by the execution interface. This "language mismatch" leads to high error rates—up to 50% on some models—for fully translated queries in high-resource languages like Chinese and Hindi. By contrast, queries that retain English parameter strings (partial translation) nearly eliminate these errors, indicating that intent understanding remains intact. Simple inference-time mitigations (prompting, pre-translation, post-translation) reduce language mismatch but fail to match English-only performance, often introducing new errors via translation drift. For low-resource Igbo, the dominant failure mode shifts to semantic misunderstanding rather than language mismatch. The study highlights a fundamental alignment gap between the flexibility of natural language generation and the rigid, exact-match contracts of tool APIs.

## Method Summary
The authors introduce MLCL, a diagnostic benchmark that extends the Berkeley Function Calling Leaderboard. Queries are fully or partially translated into Chinese, Hindi, and Igbo, and may include semantic perturbations. Three evaluation settings are compared: **Full Translation (FT)** where both query and parameter values are in the target language, **Partial Translation (PAR)** where parameter values remain in English, and **No Translation (NT)** as the English baseline. Additionally, three inference-time mitigation strategies are tested: **Prompting (PT)** (explicitly instructing the model to use English), **Pre-translation (PRE)** (translating the entire query before tool call), and **Post-translation (POST)** (translating only the generated parameter values). Failures are analyzed using a fine-grained error taxonomy (syntax, function selection, language mismatch sub-types, wrong value sub-types) to distinguish between intent understanding and execution contract violations.

## Key Results
- Fully translated queries increase error rates substantially (up to 50%) due to parameter value language mismatch, where models output semantically correct but non-English strings.
- Partial translation (PAR) preserving English parameter strings nearly eliminates mismatch errors, demonstrating that tool selection and intent understanding are robust across languages.
- Inference-time mitigations (PT, PRE, POST) reduce mismatch but do not achieve NT-level performance; they often introduce semantic drift, and for low-resource Igbo, errors remain dominated by semantic misunderstanding.

## Why This Works (Mechanism)

### Mechanism 1: Parameter Value Language Mismatch
- **Claim**: Multilingual queries cause execution failures primarily because LLMs copy non-English tokens from the query into parameter values, violating the English-only execution interface.
- **Mechanism**: The model correctly understands intent and selects the right tool, but during parameter generation it mirrors the surface language of the input instead of adhering to the language-invariant conventions required by the tool's API.
- **Evidence**: In the FT setting, models frequently produce non-English parameter values that are semantically correct; PAR (preserving English strings) largely avoids these failures.

### Mechanism 2: Resource-Dependent Failure Mode Shift
- **Claim**: The dominant failure mode (language mismatch vs. semantic misunderstanding) is determined by the resource level of the query language, as models are more likely to copy tokens from high-resource languages.
- **Mechanism**: For high-resource languages (Chinese, Hindi), strong token-level associations lead the model to confidently copy query tokens into parameters. For low-resource languages (Igbo), weak token associations discourage copying, making semantic grounding errors more common.
- **Evidence**: Language mismatch is most prevalent for Chinese, less for Hindi, and least for Igbo; mitigation strategies offer little gain for Igbo, indicating its failures are mostly semantic.

### Mechanism 3: Limitations of Inference-Time Mitigation
- **Claim**: Simple inference-time strategies cannot fully restore English-level performance because they introduce new errors via semantic drift, exposing an alignment gap between natural language variability and exact execution contracts.
- **Mechanism**: Enforcing English output (e.g., via PRE) alters the query's surface form, causing non-exact matches with ground truth values (e.g., "king-size bed" vs. "queen-size bed"). Under strict exact-match evaluation, fixing one error class often trades it for another.
- **Evidence**: No strategy eliminates failures; PRE and POST reduce mismatch but increase wrong-value errors; case studies show how translation changes parameter values.

## Foundational Learning

### Execution Interface as a Rigid Contract
- **Why needed**: The core problem is the mismatch between flexible LLM output and the precise, syntactical requirements of an API. Understanding that a tool call must match an exact schema (function name, parameter keys, and exact string values) is key.
- **Quick check**: If a user asks for the weather in "NYC" and the model calls `get_weather(location="New York City")`, is this call executable? (Answer: It depends on the tool's schema; if it expects "NYC", the call fails despite correct meaning.)

### Multilingual Token Copying vs. Semantic Understanding
- **Why needed**: The paper disentangles intent understanding (correct tool selection) from parameter realization (generating correct strings). Engineers must separate these steps to classify errors correctly.
- **Quick check**: For the query "天气在纽约如何？", if the model outputs `get_weather(location="纽约")`, what type of error is this? (Answer: *Language Mismatch + Exactly Same Meaning*—intent and semantic value are correct, but the parameter language violates the English-only contract.)

### Error Taxonomy for Execution-Centric Evaluation
- **Why needed**: Standard accuracy metrics hide the distribution of failure modes. A fine-grained taxonomy (Syntax, Function-Level, Language Mismatch sub-types, Wrong Value sub-types) is necessary to attribute cause (language convention violation vs. semantic error) and measure mitigation efficacy.
- **Quick check**: Which error is more severe: `Language Mismatch + Relevant but Incorrect` or `Wrong Value`? (Answer: `Language Mismatch + Relevant but Incorrect` is more severe because it adds a violation of the language-invariant interface convention on top of semantic inaccuracy.)

## Architecture Onboarding

### Component Map
Multilingual User Query -> [Optional: PRE] -> Query Processor -> Tool Selector & Planner -> Parameter Generator -> [Optional: POST] -> Execution Interface
*(Note: PT wraps the Parameter Generator; PRE can be inserted before the Parameter Generator; POST after Parameter Generator but before Execution Interface.)*

### Critical Path
The critical path runs from the multilingual user query through to the execution interface. The key failure occurs at the handoff between the Parameter Generator and the Execution Interface: the Parameter Generator outputs parameter values in the query's language, violating the interface's language constraint. Tool selection (Tool Selector & Planner) remains robust.

### Design Tradeoffs
- **Strict Matching vs. Semantic Tolerance**: Exact surface-form matching is simple but penalizes semantically equivalent values (e.g., "NYC" vs "New York City"). A semantic-equivalence check would be more lenient but adds complexity and ambiguity.
- **Pre-translation vs. Post-translation**: PRE normalizes the entire input, giving the model more context but risking query semantic alteration. POST preserves the model's original reasoning but must translate only the generated parameters accurately—a harder, context-starved task.
- **Prompting vs. Architectural Change**: PT is simple but relies on the model's instruction-following fidelity. A deeper solution might involve training or data that explicitly pairs tool schemas with language-agnostic parameter representations.

### Failure Signatures
1. **Parameter Value Language Mismatch**: Generated parameter values are in the query's language (e.g., Chinese, Hindi) instead of English.
2. **Semantic Drift in Mitigation**: After PRE/POST, parameter values are in English but semantically incorrect due to imperfect translation.
3. **Resource-Dependent Shift**: High-resource languages exhibit signature (1); low-resource Igbo exhibits signature `Wrong Value` without language mismatch.
4. **Inconsistent PT Compliance**: Under PT, the model sometimes obeys the "use English" instruction and sometimes does not, leading to a mix of mismatch and drift errors.

### First 3 Experiments
1. **Replicate Baseline Mismatch**: Run the core FT vs. PAR vs. NT experiment on one high-resource (Chinese) and one low-resource (Igbo) language using a strong model like GPT-5. Confirm that FT increases errors dominated by `Language Mismatch + Same Meaning` for Chinese, but not for Igbo.
2. **Mitigation Stress Test**: Apply PT, PRE, and POST to the FT Chinese dataset. Quantify (a) reduction in `Language Mismatch` errors and (b) increase in `Wrong Value`/`Relevant but Incorrect` errors. Verify that the total error rate rarely reaches the NT baseline due to trade-offs.
3. **Taxonomy Validation**: Manually label 100 random failure cases from the FT setting using the paper's error taxonomy. Compute the proportion of failures that are *purely* `Language Mismatch + Exactly Same Meaning` (correct semantics, wrong language) versus those involving semantic error, to anchor the prevalence of boundary failures.

## Open Questions the Paper Calls Out
1. **How do multilingual tool-calling failures scale to multi-turn conversations with persistent context?**  
   *Basis*: The study is limited to single-turn queries.  
   *Why unresolved*: Multi-turn interactions add state and language mixing, potentially altering error patterns.  
   *What evidence would resolve*: Extend MLCL to multi-turn tasks and track errors across turns.

2. **Do failure patterns hold for languages beyond Chinese, Hindi, Igbo?**  
   *Basis*: Paper admits coverage of only three languages.  
   *Why unresolved*: Other language families may produce new mismatches or semantic errors.  
   *What evidence would resolve*: Test MLCL on additional languages from diverse families and compare.

3. **Why do high-resource languages show mismatch while low-resource Igbo shows semantic errors?**  
   *Basis*: Error breakdown shows this pattern but no explanation.  
   *Why unresolved*: Identifying cause would help design language-specific interventions.  
   *What evidence would resolve*: Analyze model-language correlations, training data, or run controlled fine-tuning experiments.

4. **Can training-time methods (fine-tuning or RL) eliminate the multilingual performance gap?**  
   *Basis*: Inference-time mitigations are insufficient; system-level change needed.  
   *Why unresolved*: Training might embed English conventions without translation drift.  
   *What evidence would resolve*: Fine-tune on multilingual tool-calls with fixed English parameters, use RL with execution rewards, and evaluate.

## Limitations
- **Language coverage**: Benchmark uses only Chinese, Hindi, Igbo; generalizability to other high-/low-resource languages is unclear.
- **Evaluation rigidity**: Strict exact-match criteria may conflate semantic equivalence with true execution failures, potentially overstating mismatch impact.
- **Model scope**: Experiments conducted on earlier LLMs; limited independent validation of findings on newer models.

## Confidence
- Core mismatch mechanism (high-resource languages): **High**
- Resource-dependent shift (high vs. low resource): **Medium**
- Mitigation limits via translation drift: **Medium**
- Execution interface rigidity as central concept: **High**

## Next Checks
1. **Expand linguistic diversity**: Replicate key FT/PAR experiments on at least 5 additional languages spanning different scripts and resource tiers (e.g., Arabic, Swahili, Finnish, Thai, Tamil) to test generalizability of the mismatch pattern.
2. **Relax evaluation metric**: Re-run failure analysis using semantic similarity metrics (e.g., BERTScore, embedding distance) to quantify how much “language mismatch” represents true non-executability versus acceptable paraphrasing.
3. **Frontier model test**: Evaluate latest proprietary and open-source LLMs (e.g., GPT-5, Claude 4, Llama 4) on MLCL to determine whether scale or architectural changes mitigate the identified mismatch or if the failure persists.
