# From Assistant to Double Agent: Formalizing and Benchmarking Attacks on OpenClaw for Personalized Local AI Agent

## Quick Facts
- **arXiv ID:** 2602.08412
- **Source URL:** https://arxiv.org/abs/2602.08412
- **Reference count:** 6
- **Primary result:** A new security benchmark (PASB) reveals critical vulnerabilities in a real-world personalized agent, with indirect prompt injection achieving up to 66.8% attack success rate and memory attacks succeeding over 60%, even with common prompt-layer defenses.

## Executive Summary
This paper addresses a gap in LLM agent security research by focusing on *personalized* agents—systems that operate persistently, accumulate private context, and wield high-privilege tools. The authors introduce the Personalized Agent Security Bench (PASB), an end-to-end framework for black-box security assessment that models realistic, long-horizon interactions and toolchains. Applying PASB to the OpenClaw agent uncovers severe vulnerabilities: adversarial content in external sources can propagate to trigger dangerous tool calls (up to 66.8% success), and attacks can persist via long-term memory poisoning (over 60% success) across sessions. Crucially, standard prompt-layer defenses provide only partial mitigation, leaving residual risks. The work demonstrates that security for such agents requires defenses that protect the full execution chain, not just the initial prompt.

## Method Summary
The study uses the PASB framework, a modular harness that drives a black-box agent (OpenClaw) through controlled scenarios. PASB injects malicious payloads at defined channels (user input, external fetched content `z_t`, tool returns `y_t`) and records observable traces `tr(τ)` of interactions. Success is adjudicated automatically via deterministic rules checking for three harms: leakage of private assets (`P_leak`), execution of policy-violating tool calls (`P_act`), and persistence of harm after injection stops (`P_persist`). Experiments evaluate four attack primitives (direct/indirect injection, tool-return deception, memory poisoning) across three LLM backbones (Llama-3.1-70B-Instruct, Qwen2.5-7B-Instruct, GPT-4o-mini) with and without three prompt-layer defenses (Delimiter, Sandwich, Instruction Prevention). The testbed includes a self-hosted web range for realistic content ingestion and a sandboxed tool environment simulating 131 high-privilege skills.

## Key Results
- Indirect prompt injection attacks (via external content or tool returns) achieve an Attack Success Rate (ASR) of 66.8% against Llama-3.1-70B-Instruct with no defense, while the agent maintains a high response rate (~96–99%), indicating successful propagation from observation to dangerous action.
- Long-term memory extraction and edit attacks succeed at rates exceeding 60% without defenses, demonstrating the feasibility of persistent data theft and corruption.
- Applied prompt-layer defenses (Delimiter, Sandwich) reduce immediate ASR but leave significant residual risk (e.g., 22.0% ASR under Sandwich) and do not prevent memory-based persistence, proving their insufficiency for end-to-end security.

## Why This Works (Mechanism)

### Mechanism 1: Propagation via Mixed-Trust Observations
- **Claim:** Adversarial content injected into untrusted external sources (e.g., web pages, tool outputs) manipulates the agent's observation `o_t`, causing it to override user intent and invoke high-privilege tools.
- **Mechanism:** The observation `o_t` aggregates user prompts, external content `z_t`, and prior tool outputs. An attacker poisons `z_t` (`z'_t = z_t ⊕ δ_ext_t`). Because the backbone LLM `L` lacks fine-grained trust boundaries, these instructions influence planning and tool selection, leading to a malicious tool call `a_t`.
- **Evidence anchors:** [abstract] "attack propagation mechanisms... require security evaluation to go beyond output-level analysis toward action-chain assessment." [section 2.4] Formalizes `z'_t = z_t ⊕ δ_ext_t` and `o'_t = Compose(o_t, z'_t)`. [section 3.2] High response rate (~96–99%) and ASR up to 66.8% confirm propagation.
- **Break condition:** Strict separation and demotion of untrusted content in observation composition (e.g., via sandboxing or attestation) would neutralize the influence of `z_t`.

### Mechanism 2: Persistence via Memory Poisoning
- **Claim:** Malicious instructions written into the long-term memory store `D` create a persistent threat, enabling attacks in later, benign interactions without further injection.
- **Mechanism:** An attacker induces the agent to write a harmful memory artifact `(k_adv, v_adv)` into `D`. In subsequent steps, retrieval module `R` fetches this artifact based on a benign query `q_t` and includes it in `o_t`, causing the agent to act on it (`P_persist`).
- **Evidence anchors:** [abstract] "attacks can propagate and persist across interactions." [section 2.1] Defines `P_persist` as harm occurring after adversary stops injecting. [section 2.4] Models memory poisoning: `D' = D ∪ {(k_adv, v_adv)}` and `m_t = Retrieve(q_t, D')`. [section 3.2] Tables 3 & 4 show >60% LTM-Extract/Edit success, with residual success under defenses.
- **Break condition:** Cryptographic signing of memory writes by user intent and safety-filtered reads would prevent poisoned artifacts from persisting or being used.

### Mechanism 3: Insufficiency of Prompt-Layer Defenses
- **Claim:** Defenses that only sanitize the user prompt (e.g., Delimiter, Sandwich) fail against end-to-end attacks because they do not protect downstream channels (tool outputs, memory).
- **Mechanism:** A successful injection via `z_t` or `y_t` can cause a malicious tool call `a_t` that writes poisoned data to memory or returns a manipulated `y_t`. This `y_t` or memory artifact then becomes part of `o_{t+1}`, bypassing the original prompt defense and enabling a new infection vector.
- **Evidence anchors:** [abstract] "prompt-layer defenses are insufficient and that attacks can propagate and persist." [section 3.2] Residual ASR remains (e.g., 22.0% under Sandwich). [section 2.4] Models tool-return deception: `y'_t = y_t ⊕ δ_tool_t`, `o'_{t+1} = Compose(o_{t+1}, y'_t)`.
- **Break condition:** Validating every tool argument pre-execution and every memory write against an allow-list of user-approved intentions would block propagation via `a_t` and `D`.

## Foundational Learning
- **Personalized Agent (Persistent, Context-Aware, High-Privilege Tool Use):** PASB evaluates agents that maintain long-term state, accumulate private data, and execute powerful tools. This differs from task-centric agents, making the attack surface and propagation risks fundamentally different. *Quick check:* How does a long-term memory store `D` change the impact of a single successful prompt injection compared to a stateless task agent?
- **Indirect Prompt Injection (IPI) via Mixed-Trust Observations:** The primary attack vector where malicious instructions originate from external content (`z_t`) or tool returns (`y_t`), not the direct user prompt. This exploits the agent's observation composition that treats untrusted sources with similar weight as the user's request. *Quick check:* In `o_t = Compose(x_t, z'_t, ...)`, why is the insertion of `z'_t` (e.g., a fetched web page) a critical vulnerability even if `x_t` is clean?
- **System-Level Harm Prediction (Leakage, Action, Persistence):** PASB defines success via measurable system harms: `P_leak` (private asset in output/tool call), `P_act` (policy-violating tool invocation), `P_persist` (harm after injection stops). This moves beyond output toxicity to tangible risks. *Quick check:* Why is measuring "tool-call event `κ_t`" a more realistic security metric for a personalized agent than parsing the agent's natural language `r_t`?

## Architecture Onboarding
- **Component map:** Input Aggregator -> Backbone LLM (L + p_sys) -> Tool Execution Engine -> Long-Term Memory (D) -> PASB Harness. The Input Aggregator composes `o_t` from user prompt `x_t`, external content `z_t`, prior tool returns `y_{t-1}`, and retrieved memory `m_t`. The Backbone LLM reasons to generate `a_t` (text or tool call). The Tool Engine executes skills `τ` and returns `y_t`. The Memory store `D` uses retrieval module `R`. The PASB Harness injects payloads and adjudicates success from `tr(τ)`.
- **Critical path:** Adversarial Input (`z_t` or `y_t`) -> Input Aggregator (into `o_t`) -> Backbone LLM (poisoned reasoning) -> Tool Execution Engine (malicious `a_t`) -> Long-Term Memory (may write poison) -> Next `o_{t+1}` (contains new poison from `y_t` or `m_t`) -> Repeat. The cycle from tool execution back into the next observation is the core propagation loop.
- **Design tradeoffs:** 
  - *Realism vs. Controllability:* PASB uses a self-hosted web testbed for realistic content but sacrifices full reproducibility of the live web. It prioritizes black-box end-to-end evaluation over white-box internals.
  - *Scope vs. Depth:* Models broad scenarios and attack primitives but does not instrument LLM hidden states; focuses on manifested harms over mechanistic interpretability.
  - *Automated Adjudication:* Uses deterministic rules on `tr(τ)` (e.g., "was tool 'Email Send' called?"). Scalable but may miss nuanced harms requiring semantic understanding.
- **Failure signatures:**
  1. High "Response Rate" + High "ASR" in Table 2: Classic sign of successful IPI—agent remains active but targets dangerous skills.
  2. High LTM-Extract/Edit Success (Tables 3,4) under defenses: Indicates memory poisoning is robust to prompt-layer fixes.
  3. `P_persist` triggering: Harm occurs in a turn `t > T_injection` with benign user input, confirming cross-session propagation.
  4. Tool call arguments contain canary secrets (`S_priv`): Evidence of `P_leak` via unsafe tool use.
- **First 3 experiments:**
  1. **Baseline IPI Susceptibility:** Run Combined Attack (Table 2) on OpenClaw with Llama-3.1-70B-Instruct, no defense. Measure ASR and Resp Rate to establish raw propagation vulnerability via external content.
  2. **Memory Poisoning Persistence Test:** For LTM-Edit, write a canary marker into memory via an injected task. In a subsequent, clean user session, issue a neutral query and measure if the poisoned marker is retrieved/extracted (Table 3) or if the agent self-modifies memory based on the stored artifact (Table 4).
  3. **Defense Efficacy & Breakage:** Apply Delimiter and Sandwich defenses (Table 2) and Instruction Prevention (Tables 3,4). Check not only ASR reduction but explicitly for `P_persist` by running a follow-up clean session after an injected one to confirm residual risks.

## Open Questions the Paper Calls Out
- What defense mechanisms can effectively mitigate security risks arising from tool execution and long-horizon propagation in personalized LLM agents? Current prompt-layer defenses show residual success (up to 22.0% ASR) and memory manipulation, indicating insufficiency. Future work aims to improve defenses accounting for tool execution and long-horizon propagation.
- How can PASB be extended to incorporate more diverse personalized scenarios and advanced attacker capabilities to better reflect real-world threats? The current PASB covers three scenarios but may miss emerging vectors like multimodal inputs or insider attacks. Attacker capabilities are limited to four primitives.
- To what extent do the vulnerabilities found in OpenClaw generalize to other personalized LLM agents with different architectures or toolchains? The paper evaluates only OpenClaw; different implementations may have varying memory management or security measures, so generalization is unknown.
- How do security risks propagate and accumulate across multiple interaction steps, and can we develop a formal model to quantify this propagation? The paper emphasizes long-horizon interactions and defines `P_persist` but lacks a quantitative model for risk evolution over time or across stages.

## Limitations
- Testbed implementation (self-hosted web range, tool mocks) is underspecified; automated adjudication logic is not released; OpenClaw black-box access assumptions are not fully documented.
- Success predicates (`P_leak`, `P_act`, `P_persist`) rely on deterministic trace parsing, which may miss nuanced harms requiring semantic interpretation.
- Evaluation relies on the GitHub repository providing ready-to-run configurations and mock skills—this is unverified and could block faithful reproduction.

## Confidence
- **Indirect injection propagation (Mechanism 1):** Medium. High ASR in Table 2 is compelling, but observation composition (`Compose`) is a black box; payload injection fidelity cannot be independently confirmed.
- **Memory persistence (Mechanism 2):** Medium. Tables 3–4 show strong LTM-Extract/Edit success, but memory write/retrieval mechanisms are opaque; persistence may be overestimated if adjudication is lenient.
- **Prompt-defense insufficiency (Mechanism 3):** Medium-High. Residual ASR across defenses is consistent, but defense implementations (e.g., exact delimiter strings) are vague; could be under-specified in reproduction.

## Next Checks
1. **Injection channel verification:** Host a webpage with a unique payload (e.g., `"TRIGGER_EMAIL_ATTACK"`). Run OpenClaw with PASB harness; confirm the payload appears verbatim in `o_t` and that the agent subsequently calls the `Email Send` tool with attacker-controlled arguments.
2. **Persistence test:** Execute a memory edit attack to write a canary string (e.g., `"CANARY_123"`) into `D`. Then run a clean session with neutral user input; query a related topic and check if the canary is retrieved in `m_t` and either leaked in `r_t` or used to modify memory (indicating `P_persist`).
3. **Defense replication fidelity:** Implement Delimiter/Sandwich/Instruction Prevention as described in Section 3.2. Run the Combined Attack on Llama-3.1-70B-Instruct. If ASR reduction is <50% of Table 2 values, log the agent’s raw observations `o_t` to diagnose whether injection occurred via tool returns (`y_t`) rather than the user prompt—bypassing prompt-layer defenses.
