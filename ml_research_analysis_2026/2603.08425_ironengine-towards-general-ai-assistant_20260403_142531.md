# IronEngine: Towards General AI Assistant

## Quick Facts
- **arXiv ID:** 2603.08425
- **Source URL:** https://arxiv.org/abs/2603.08425
- **Reference count:** 40
- **Primary result:** IronEngine achieves 100% task completion on file operation benchmarks with a mean total time of 1541 seconds and 100% tool routing accuracy, uniquely combining local-first deployment, broad tool coverage, persistent memory, and formal quality assurance.

## Executive Summary
IronEngine is a unified AI assistant platform designed to address fragmentation in existing assistants by introducing a three-phase orchestration pipeline: Discussion (Planner–Reviewer collaboration), Model Switch (VRAM-aware transition), and Execution (tool-augmented action loop). This separation ensures high planning quality before execution, while enabling heterogeneous multi-model collaboration on consumer hardware. The system features intelligent tool routing with 130+ alias normalization and auto-correction, hierarchical memory consolidation, and vectorized skill learning. Experimental evaluation on file operation benchmarks demonstrates perfect task completion and tool dispatch accuracy, outperforming or uniquely combining capabilities compared to systems like ChatGPT and OpenClaw.

## Method Summary
IronEngine implements a local-first AI assistant that orchestrates multiple specialized models (Planner, Reviewer, Executor) in a sequential pipeline. The Discussion phase generates and evaluates a textual plan using anti-hallucination checks (memory duplication, forbidden phrases, contradictions) until a quality threshold is met. The Model Switch phase unloads planning models and loads the Executor, dynamically budgeting context based on available VRAM to avoid out-of-memory errors. In Execution, the Executor emits tool calls that are routed through a dispatch layer normalizing aliases and applying auto-correction heuristics; a fallback chain provides layered execution strategies. Persistent hierarchical memory (MemoMap) stores four entry types and merges via fast deduplication or model summarization. Skills are learned from successful traces via vector similarity and stored in ChromaDB. The system supports 24 tool categories, integrates with MCP servers, and provides desktop UI, REST/WebSocket API, and Python client.

## Key Results
- Achieved 100% task completion across four heterogeneous file operation benchmark tasks, with a mean total execution time of 1541 seconds.
- Tool routing dispatch accuracy reached 100% after alias normalization and auto-correction (e.g., `cli`→`file_ops` corrected all 12 misrouted cases).
- Planner–Reviewer quality scores improved iteratively from 0.10 to 0.92, demonstrating effective plan refinement.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Separating planning (Planner) and evaluation (Reviewer) in a discussion loop improves plan reliability before execution.
- **Mechanism:** The Planner generates a textual plan with tool requirements. The Reviewer evaluates it against anti-hallucination rules (memory duplication detection, forbidden phrases, score-text contradiction, memory contradiction) and assigns a quality score. Plans below a threshold trigger iterative feedback.
- **Core assumption:** A dedicated evaluator role can systematically identify planning flaws that a single model might miss when also responsible for execution.
- **Evidence anchors:**
  - [abstract] "three-phase pipeline—Discussion (Planner–Reviewer collaboration)... that separates planning quality from execution capability."
  - [section 7.1] Details four anti-hallucination mechanisms operating during Discussion.
  - [corpus] Weak direct evidence; neighboring papers (e.g., *Gradientsys*) explore multi-agent scheduling but not formal quality gates.
- **Break condition:** If the Reviewer cannot correct plans after `max_rounds` (typically 3–5) or if quality thresholds are consistently unmet, indicating a fundamental mismatch between model capabilities and task complexity.

### Mechanism 2
- **Claim:** VRAM-aware model switching enables heterogeneous multi-model collaboration on single-GPU consumer hardware.
- **Mechanism:** After plan approval, the system unloads Planner/Reviewer models and loads the Executor. Context length is dynamically budgeted based on available VRAM (`ctxmem = (VRAMfree×0.85)−overhead / Ckv`), preventing OOM while maximizing context utilization.
- **Core assumption:** Cognitive functions (planning, evaluation, execution) have differing computational profiles, and sequential model loading can fit larger-than-VRAM models at the cost of switch latency.
- **Evidence anchors:**
  - [section 7.2] Describes the four-step model switch process and simple-plan reuse optimization.
  - [section 10.2] Presents the VRAM-aware context budgeting formula and KV-cache cost variations.
  - [table 6] Shows phase-specific VRAM usage, confirming non-simultaneous model residency.
- **Break condition:** When available VRAM is insufficient to load even the smallest quantized model for a required role, or if switch latency dominates task time, making the approach impractical for real-time needs.

### Mechanism 3
- **Claim:** Intelligent tool routing with alias normalization and auto-correction compensates for local models' imprecise tool-type specification.
- **Mechanism:** Model output is parsed, tool types normalized via 130+ aliases, and mismatches corrected using context heuristics (e.g., `cli` with file paths → `file_ops`). Fallback chains provide layered execution strategies.
- **Core assumption:** Local models (≤14B) systematically mis-specify tool types; system-level correction is more robust than relying on larger prompts for perfect syntax.
- **Evidence anchors:**
  - [section 8.2] Details alias normalization and bidirectional auto-correction.
  - [table 5] Shows 100% dispatch accuracy after corrections (e.g., `cli→file_ops` 12/12).
  - [corpus] Weak; *Surfer 2* addresses cross-platform agents but not tool-type misrouting.
- **Break condition:** If heuristic-based redirection frequently misclassifies novel tool patterns or if fallback chains exhaust without success, indicating the need for model capability upgrade.

## Architecture Onboarding
### Component Map
IronEngine employs a four-layer architecture:
1. **Interaction:** Desktop UI (PySide6), REST/WebSocket API, Python client.
2. **Orchestration:** Three-phase pipeline (`pipeline.py`) managing context, role-specific model loading, and callbacks.
3. **Capability:** Provider registry (Ollama/LM Studio), `MemoMap` (memory), `SkillStore` (ChromaDB), `tool_router.py`, scheduler.
4. **Environment:** MCP servers, file system, browsers (CDP), desktop (UIA), network, hardware.

### Critical Path
The end-to-end flow: Discussion (Planner→Reviewer) → Model Switch (unload→load) → Execution (Executor + Tool Router → result loop) → Memory update/Skill learning.

### Design Tradeoffs
- *Latency vs. Reliability:* Model switch (~27s) and multi-round review add overhead but prevent hallucination failures.
- *Prompt brevity vs. Guidance:* Tiered prompts sacrifice detail for small models (≤10B: ~44 tok SOUL) to fit context, risking planning degradation.
- *Depth vs. Breadth:* Focused desktop workbench (deep orchestration) vs. OpenClaw's multi-channel breadth.

### Failure Signatures
- Plan rejected repeatedly: Reviewer score persistently < threshold; check Planner model capability or SOUL configuration.
- Tool type errors: Persistent `cli` for file ops despite auto-correction; may need more training data or different Tools model.
- Memory contamination: Stale values not superseded; verify contradiction detector's numerical comparison logic.
- Web search failure: All four strategies fail; likely network/blocklist issue, not pipeline flaw.

### First 3 Experiments
1. **File Operation Benchmark:** Runs the four-task benchmark from Section 12.2. Validates end-to-end pipeline, tool routing, and basic correctness. Expect ~385s/task on RTX 3090 with 27B/20B/3.8B config.
2. **Tool Routing Stress Test:** Submit queries that deliberately confuse tool types (e.g., "list files" → plan with `shell` instead of `file_ops`). Confirm auto-correction logs in `tool_router.py` and 100% dispatch accuracy.
3. **VRAM Monitoring:** Use `nvidia-smi` during pipeline phases. Verify Planner/Reviewer models are not co-resident and Executor loads after switch. Check `model_session.py` logs for context budget calculations.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How to reduce IronEngine's pipeline latency for real-time use?
- **Basis in paper:** [explicit] Section 15.6 (Limitations) states: "Latency overhead: The three-phase pipeline’s model switching and multi-round discussion introduce significant latency, making it unsuitable for real-time interaction scenarios requiring sub-second responses."
- **Why unresolved:** The pipeline always performs model switching (∼27 s) and may iterate planning rounds; no adaptive mechanism skips phases for simple tasks.
- **What evidence would resolve it:** Implement an adaptive pipeline that skips the Reviewer or Model Switch based on task complexity and measure end-to-end latency on real-time benchmarks (e.g., sub‑second response targets).

### Open Question 2
- **Question:** How can IronEngine extend GUI automation to macOS/Linux?
- **Basis in paper:** [explicit] Section 15.6 notes: "Windows‑centric testing: GUI automation and application control have been primarily tested on Windows 10. Cross‑platform support (macOS, Linux) requires alternative UIA backends (AT‑SPI, AppleScript), which are not yet implemented."
- **Why unresolved:** The current implementation depends on Windows UI Automation; other platforms use different accessibility APIs, requiring new backends and comprehensive testing.
- **What evidence would resolve it:** Develop AT‑SPI (Linux) and AppleScript (macOS) backends, run cross‑platform benchmarks (e.g., OSWorld), and report success rates compared to Windows.

### Open Question 3
- **Question:** What architectural modifications are needed to support multi‑user operation?
- **Basis in paper:** [explicit] Section 15.6 indicates: "Single‑user design: The current architecture assumes a single concurrent user. Multi‑user support would require session isolation, resource scheduling, and access control mechanisms."
- **Why unresolved:** Memory, skills, and tasks are stored without user namespaces; concurrent sessions risk state interference and resource conflicts, demanding isolation and scheduling layers.
- **What evidence would resolve it:** Prototype per‑user memory/skill namespaces and a resource scheduler, then conduct concurrent‑session stress tests showing no data leakage and bounded resource sharing.

### Open Question 4
- **Question:** How can skill learning efficiency be improved to reduce dependence on user ratings?
- **Basis in paper:** [explicit] Section 15.6 states: "Skill coverage: The 26 innate skills cover common scenarios, but long‑tail tasks still require interactive user guidance. Skill learning efficiency is constrained by the frequency of user rating feedback."
- **Why unresolved:** Learning triggers require explicit high ratings (≥7) and cosine novelty checks; infrequent ratings stall skill acquisition, and extraction from traces may not generalize.
- **What evidence would resolve it:** Design unsupervised skill extraction (e.g., infer success from tool outcomes), then evaluate by reusing learned skills on similar future tasks and measuring success‑rate improvements without additional ratings.

## Limitations
- **Generalization concerns:** Claims are based on a limited file-operation benchmark (4 tasks) and self-reported tool routing tests; no evaluation on diverse domains or against cloud-native agents.
- **Local model dependency:** Heavy reliance on small local models (≤14B) may limit planning depth; scalability boundaries not fully quantified.
- **External system fragility:** Web-search fallback chain and UIA automation likely degrade with website changes or OS updates; real-world success rates unknown.

## Confidence
- Planner–Reviewer separation improves plan reliability: **Medium**
- VRAM-aware model switching enables heterogeneous multi-model collaboration on consumer hardware: **High**
- Intelligent tool routing compensates for local model imprecision: **Medium**
