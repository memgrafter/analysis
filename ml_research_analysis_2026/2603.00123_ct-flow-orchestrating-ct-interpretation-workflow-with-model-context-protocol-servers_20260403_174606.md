# CT-Flow: Orchestrating CT Interpretation Workflow with Model Context Protocol Servers

## Quick Facts
- **arXiv ID:** 2603.00123  
- **Source URL:** https://arxiv.org/abs/2603.00123  
- **Reference count:** 20  
- **Primary result:** CT-Flow bridges static LVLM and radiologist workflow via MCP, achieving 69.46% accuracy on 3D-RAD with 95% tool invocation success.

## Executive Summary
CT-Flow introduces an agentic framework for 3D CT interpretation that leverages the Model Context Protocol (MCP) to transform large vision-language models into clinical orchestrators. By adopting a ReAct reasoning loop, the system dynamically invokes specialized tools (navigation, measurement, segmentation, radiomics) to actively probe the raw CT volume, overcoming the information bottleneck of static 3D encoding. This iterative, tool-mediated approach yields transparent, clinically aligned reasoning trails. Evaluated on CT-FlowBench and 3D-RAD, CT-Flow-8B attains state-of-the-art accuracy (69.46% on 3D-RAD, 44.33% on CT-FlowBench) with high tool reliability, even improving general models like GPT-5.2 and surpassing medical VLMs.

## Method Summary
CT-Flow redefines 3D CT diagnosis as an active information-probing task rather than single-pass inference. The core is a fine-tuned LVLM orchestrator that generates thoughts and tool calls in a ReAct loop, interfacing with MCP servers that expose atomic medical tools. Training uses CT-FlowBench, a dataset of 2,000 executable trajectories synthesized by teacher models (e.g., GPT-5.2) with execution-in-the-loop verification to ensure every observation is retrievable from the raw volume. The model learns to decompose clinical queries into valid tool sequences, interpret outputs, and synthesize final answers. Deployment employs SGLang for efficient inference and medical libraries (MONAI, SimpleITK, PyRadiomics) for tool execution.

## Key Results
- CT-Flow-8B achieves **69.46% accuracy** on 3D-RAD, a **41% relative improvement** over baselines.
- Scores **44.33%** on CT-FlowBench with a **95% tool invocation success rate**.
- General models (e.g., GPT-5.2) gain **+8.33%** on 3D-RAD when using the CT-Flow tool framework.
- Outperforms specialized medical VLMs such as M3D-RAD (**58.00%**).

## Why This Works (Mechanism)

**Mechanism 1: Active tool-mediated probing overcomes the static encoding bottleneck.** The LLM orchestrator dynamically invokes tools (e.g., `view_slice`, `measure_hu`) to retrieve targeted, high-fidelity observations from the raw CT volume. This iterative refinement replaces a single-pass model’s fixed representation with a growing evidence chain, allowing fine-grained hypothesis testing. Core assumption: tools are accurate and reproducible. Evidence: Abstract and Section 1 contrast active, iterative clinical workflow with static LVLM inference; Section 3 defines trajectories as active information probing.

**Mechanism 2: Trajectory structure enables transparent, auditable reasoning.** Each step is recorded as (thought, action, observation), creating an executable audit trail where observations must be “execution‑retrievable” from the raw volume. Clinicians can verify whether actions were justified and observations support conclusions. Core assumption: deterministic tool outputs and faithful reconstruction. Evidence: Abstract cites transparent, clinically aligned reasoning; Section 4 describes CT‑FlowBench’s procedurally consistent trajectories; Section 3 formalizes validity conditions.

**Mechanism 3: Supervised fine‑training on CT‑FlowBench teaches tool‑use mapping.** The 2,000 training trajectories provide direct supervision for decomposing complex queries into valid tool sequences and interpreting outputs. This improves diagnostic accuracy and reduces tool errors (95% success). Core assumption: training trajectories are high‑quality and representative. Evidence: Abstract reports SOTA and tool success; Section 5 shows SFT superiority; Section 4 details teacher‑model synthesis with verification.

## Foundational Learning

- **Model Context Protocol (MCP):** Standardizes the interface between LLM and tools, decoupling orchestration from implementation. *Why needed:* MCP is the backbone of CT‑Flow’s tool integration, allowing plug‑and‑play medical servers. *Quick check:* How does MCP differ from traditional function‑calling APIs, and why is it particularly suited for clinical tool orchestration?
- **Information bottleneck in 3D medical VLMs:** Static processing of 3D volumes (e.g., via 2D slices or compressed embeddings) loses fine‑grained anatomical details. *Why needed:* The paper’s motivation rests on this bottleneck to justify active probing. *Quick check:* Why might processing a 3D CT volume as a single input or as a set of 2D slices lead to loss of clinically relevant information?

## Architecture Onboarding
**Component map:** LLM Orchestrator (Qwen2.5‑VL‑7B/8B) -> MCP Servers (Data Ingestion, Global Navigation, Detailed Observation, Advanced Analysis) -> FASTMCP Bridge -> Imaging Environment (raw CT volume + MONAI/SimpleITK/PyRadiomics backend). Also: CT‑FlowBench dataset, LLaMA‑Factory for SFT, SGLang for inference.

**Critical path:**  
1. Data preparation: Curate CT‑RATE subset, synthesize trajectories via teacher models with execution verification.  
2. Fine‑tune: Full‑parameter SFT on CT‑FlowBench trajectories using LLaMA‑Factory (LR = 1e‑5).  
3. Deployment: Load fine‑tuned model, connect to MCP servers via FASTMCP.  
4. Inference: Model generates thought + action; MCP executes tool; observation feeds back; iterate to final answer.  
5. Evaluation: Measure accuracy, tool success, etc.

**Design tradeoffs:**  
- Tool comprehensiveness vs. complexity: More tools increase control but raise action space and error risk; CT‑Flow uses four suites for balance.  
- Trajectory length vs. efficiency: Longer trajectories enable thorough investigation but increase latency; model must balance.  
- Domain‑specific fine‑tuning vs. generalization: Fine‑tuning boosts medical performance but may reduce general reasoning; general models still benefit but fine‑tuned are best.

**Failure signatures:**  
- High tool‑name error rate indicates poor tool selection.  
- High tool‑argument error rate suggests incorrect parameter formatting.  
- Large performance drop on CT‑FlowBench vs. 3D‑RAD signals multi‑step reasoning difficulty.  
- Invalid observations (non‑retrievable) break the reasoning chain.  
- JSON format errors cause execution failure; strict schema adherence required.

**First three experiments:**  
1. Benchmark comparison (Table 1): CT‑Flow fine‑tuned 7B/8B vs. baselines on 3D‑RAD and CT‑FlowBench; shows SOTA accuracy (69.46%) and high tool success.  
2. Tool ablation study (Figure 4): Removing each tool category reduces accuracy and increases errors; all four categories are essential.  
3. Tool‑use performance analysis (Table 2): Reports tool call counts, name/argument errors; CT‑Flow models achieve very low error rates (e.g., name error = 0.007, arg error = 0.033).

## Open Questions the Paper Calls Out
1. How can Reinforcement Learning from Clinical Feedback (RLCF) be integrated to optimize tool‑calling trajectories and reduce redundant actions without compromising diagnostic accuracy? The Limitations note reliance on SFT and no RL optimization.
2. What architectural modifications can reduce inference latency for time‑sensitive scenarios (e.g., acute stroke) while preserving multi‑step transparency? The paper cites higher latency than single‑pass models and suggests future work on parallel processing or trajectory pruning.
3. To what extent does CT‑Flow generalize beyond chest CT to other anatomies (abdomen, brain) and modalities (MRI, PET), and what adaptations are required? Current tools and CT‑FlowBench are chest‑specific; cross‑modality generalization is untested.
4. What specific failure modes and cognitive biases cause the performance drop on CT‑FlowBench (max 44.33%) vs. 3D‑RAD (69.46%), and how can they be mitigated? Aggregate metrics hide step‑level error propagation and reasoning flaws.

## Limitations
- CT‑FlowBench not publicly released; trajectory generation with teacher models introduces variability and potential bias.
- Underspecified conversation template and tool APIs risk implementation divergence during reproduction.
- Generalization to other CT datasets or modalities unproven; potential selection bias in CT‑RATE subset.
- Tool failures may cascade through the ReAct loop; error propagation not analyzed.
- Transparent reasoning claim lacks radiologist evaluation or clinical usability study.

## Confidence
- **Accuracy gains (69.46% on 3D‑RAD):** Medium (internal results, no independent replication).  
- **Active probing mitigates bottleneck:** Medium (supported by ablation but uses synthetic trajectories).  
- **95% tool success:** Medium (low reported errors, but real‑world robustness unclear).  
- **Transparent reasoning:** Low (conceptual framework, no clinical user study).  

## Next Checks
1. **Replication:** Train and evaluate CT‑Flow on the CT‑RATE test set with exactly reported hyperparameters; compare accuracy and tool error rates to paper values.
2. **Observations audit:** Sample 100 CT‑FlowBench trajectories; for each intermediate step, verify the observation matches a reconstruction from the raw volume using the invoked tool.
3. **Clinical usability:** Engage radiologists to rate CT‑Flow’s reasoning traces on a held‑out set for clarity, completeness, and diagnostic correctness versus standard LVLM outputs.
