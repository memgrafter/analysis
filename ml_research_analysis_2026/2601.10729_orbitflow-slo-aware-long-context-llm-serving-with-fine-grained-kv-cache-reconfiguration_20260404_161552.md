# ORBITFLOW: SLO-Aware Long-Context LLM Serving with Fine-Grained KV Cache Reconfiguration

## Quick Facts
- **arXiv ID:** 2601.10729
- **Source URL:** https://arxiv.org/abs/2601.10729
- **Reference count:** 40
- **Primary result:** ORBITFLOW improves SLO attainment for long-context LLM serving by up to 66% (TBT) and 62% (TPOT), reduces P95 latency by 38%, and increases throughput by 3.3× over existing offloading methods under strict latency constraints.

## Executive Summary
ORBITFLOW tackles the problem of serving long-context large language models (LLMs) under strict latency Service Level Objectives (SLOs). Static KV cache offloading methods fail to adapt to runtime memory fluctuations caused by varying request lengths and dynamic batch compositions, leading to excessive CPU-GPU data transfers and SLO violations. The core innovation is a fine-grained, per-request KV cache placement policy driven by a lightweight integer linear programming (ILP) solver. This solver decides which layers' KV caches to keep on the GPU for each individual request, optimizing memory usage within GPU capacity. The system continuously reconfigures these placements based on runtime feedback about memory and compute conditions. A fallback mechanism, combining token buffering and selective pausing, prevents system collapse under overload by deferring requests with large memory footprints. Evaluations show significant improvements in SLO attainment, latency, and throughput compared to state-of-the-art offloading systems.

## Method Summary
ORBITFLOW modifies a continuous batching serving stack (based on vLLM) with three key components. First, a **Placement Planner** runs a lightweight ILP solver in a separate thread to compute per-request offload distances (which layers to keep on GPU) for the next decode window, optimizing for minimal latency while respecting GPU memory limits. Second, an **Adaptive Controller** monitors runtime signals—such as discrepancies between predicted and actual layer compute/transfer times and changes in batch composition—to trigger reconfiguration when the current plan becomes suboptimal. Third, a **Token-Deposit buffer** decouples token generation from delivery, masking transient stalls by holding tokens and releasing them at the required SLO rate. Under severe memory pressure, a **Pause-Resume** fallback defers the in-flight request with the largest combined KV cache and deposited tokens, freeing memory via on-demand eviction; the request resumes when capacity allows. The system employs a flattened 1D KV layout for efficient per-request management and asynchronous data movement.

## Key Results
- Up to **66% improvement in TBT (Time-Between-Tokens) SLO attainment** and **62% in TPOT (Time-Per-Output-Token) SLO attainment**.
- **38% reduction in P95 latency** compared to prior offloading systems.
- Up to **3.3× higher throughput** under SLO constraints.
- Effective adaptation to dynamic workloads with varying sequence lengths, avoiding catastrophic stalls from static offloading.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Per-request, fine-grained KV placement decisions optimize GPU memory usage under fluctuating batch demands, avoiding stalls from uniform offloading.
- **Mechanism:** An ILP solver selects which layers' KV caches to retain on GPU for each request individually, respecting a total GPU block budget. It balances per-layer compute time against data-transfer stalls by scheduling prefetches greedily across active streams.
- **Core assumption:** Layer-wise compute times and transfer costs can be profiled accurately and remain stable between solver invocations; a single decode iteration's decisions remain valid for a solver-determined window.
- **Evidence anchors:**
  - [abstract] "employs a lightweight ILP solver to decide which layers’ KV caches to retain on the GPU for each request, within memory capacity constraints."
  - [section 3.3] Formulation of placement matrix, GPU capacity bound (Eq. 1), and Algorithm 1 for batch latency.
  - [corpus] Weak direct evidence; neighboring papers explore per-layer management but ORBITFLOW's specific ILP formulation and per-request granularity are unique.
- **Break condition:** Token-dimension drift (growing KV cache per request) or batch-dimension mismatch (request arrivals/completions) invalidates the placement before the solver's expiry window, triggering reconfiguration.

### Mechanism 2
- **Claim:** Continuous reconfiguration based on runtime feedback adapts to shifting memory-to-compute ratios and batch composition, maintaining optimal placement.
- **Mechanism:** The Adaptive Controller monitors profile deviations (actual vs. predicted latency) and batch changes (request join/leave). It triggers the Placement Planner to recompute placements when these signals exceed thresholds, running the solver ahead of execution on a separate thread.
- **Core assumption:** Solver overhead can be hidden by running it one decode step ahead; profile mismatches accurately indicate changed resource contention (e.g., PCIe bandwidth).
- **Evidence anchors:**
  - [abstract] "It continuously refines KV placements based on runtime feedback when the active plan becomes suboptimal during token generation."
  - [section 3.4] "Solver Invocations" describing profile-mismatch and batch-change triggers; solver launched one step ahead.
  - [corpus] No direct evidence; adjacent work mentions multi-SLO adaptation but not ORBITFLOW's specific feedback loop.
- **Break condition:** Solver latency exceeds the decode step window, causing stalls; or profiled metrics become stale under rapidly changing contention, leading to suboptimal placements.

### Mechanism 3
- **Claim:** Token-Deposit buffering and Pause-Resume fallback decouple token generation from delivery and proactively manage memory pressure, masking SLO violations and preventing system collapse under overload.
- **Mechanism:** Generated tokens are deposited in a CPU buffer and released at the SLO-mandated rate. When the solver reports infeasibility under memory/SLO constraints, the Controller pauses the request with largest KV+deposited tokens, freeing GPU memory on-demand via layer-wise eviction. Paused requests resume when capacity permits.
- **Core assumption:** Depositing tokens early builds a buffer that can mask transient stalls without user-perceived gaps; pausing high-memory requests yields net SLO benefit for the batch.
- **Evidence anchors:**
  - [abstract] "employs a fallback mechanism to temporarily defer in-flight requests with large memory footprints."
  - [section 3.2] Token-Deposit logic; [section 3.4] Pause-Resume victim selection and on-demand eviction.
  - [section 5.4] Fig 14c showing pausing longest request maximizes SLO attainment.
- **Break condition:** Deposit buffer empties during prolonged stalls, exposing SLO violations; or repeated pausing/resuming of a single request causes starvation, inflating tail latency.

## Foundational Learning
- **Concept: KV Cache Management**
  - *Why needed here:* ORBITFLOW's core optimization is per-request placement of KV cache blocks between GPU and CPU. Understanding the linear growth of KV cache with sequence length and its impact on memory is essential.
  - *Quick check question:* How does the KV cache size scale with sequence length in GQA models, and why does this create "token-dimension drift"?
- **Concept: Continuous Batching**
  - *Why needed here:* The batch dimension mismatch arises from serving multiple requests at different decoding stages under continuous batching. This dynamic batching model is the scenario where ORBITFLOW's adaptivity matters.
  - *Quick check question:* In continuous batching, what event triggers a new request's admission, and how does this affect the memory footprint of the active batch?
- **Concept: SLO Metrics (TBT vs. TPOT)**
  - *Why needed here:* ORBITFLOW optimizes for both TBT (per-token latency) and TPOT (average latency). The solver's feasibility constraint and Token-Deposit design specifically target TBT violations.
  - *Quick check question:* Why can a low TPOT mask high TBT violations, and how does Token-Deposit address this?

## Architecture Onboarding
- **Component map:** Runtime Executor -> Placement Planner -> Adaptive Controller -> KV Manager; Runtime Executor also interfaces with Token-Deposit and Pause-Resume logic. Solver thread runs parallel to decode loop.
- **Critical path:** Decode step → Executor executes layers with current placement → records latency → Controller checks triggers → (if needed) Planner solves for next step ahead → Executor pulls new placement *before* next decode step.
- **Design tradeoffs:**
  - *Solver granularity vs. overhead:* Distance-driven pruning reduces search space from 2^(|R|*L) to D(L)^|R|, trading optimality for tractability.
  - *Reconfiguration frequency:* Too frequent → solver overhead dominates; too sparse → stale placement causes stalls. Solver self-determines Δ to balance this.
  - *Pause-Resume impact:* Increases E2E latency for deferred requests but improves throughput and SLO attainment for the batch by freeing resources.
- **Failure signatures:**
  - High P99 TBT despite high average SLO attainment → Token-Deposit buffer exhausted, exposing tail stalls.
  - Solver thread lagging decode steps → Decode proceeds with stale placement, causing predictable stalls.
  - Frequent Pause-Resume on same request → Starvation risk; check victim selection heuristic.
- **First 3 experiments:**
  1. Run with and without Token-Deposit on a trace with variable sequence lengths to quantify its masking effect on TBT violations.
  2. Artificially inject batch changes (request arrival/completion) or profile noise (simulate bandwidth contention) and measure reconfiguration latency vs. placement optimality decay.
  3. Use a trace with high proportion of long requests to force Pause-Resume; compare victim selection strategies (longest vs. random) on batch SLO attainment and stalled request count.

## Open Questions the Paper Calls Out
- **Open Question 1:** Can we design an efficient ILP solver that explores non-uniform KV offload patterns (unevenly spaced offloaded layers) without prohibitive runtime overhead, to capture the small latency improvements identified in the full space? *Basis:* Section 3.3.2 and Figure 15 show 16.7% of placements from the full space are strictly better but require 7.74× more solver time.
- **Open Question 2:** How can ORBITFLOW be extended to support multi-node LLM serving with pipeline parallelism (PP) and data parallelism (DP), where inter-node communication and heterogeneous resources introduce new constraints? *Basis:* Section 3.5 explicitly states this is left as future work.
- **Open Question 3:** Is pausing the request with the largest combined KV cache and deposited token count the optimal strategy for the Pause-Resume fallback, or can a more sophisticated selection policy further reduce SLO violations? *Basis:* Section 3.4 and 5.4 compare longest, shortest, and random selections, showing longest is best among those.
- **Open Question 4:** Can the ILP solver be extended to simultaneously optimize for both TPOT and TBT SLOs, instead of relying on a single violation cap α, to achieve better overall SLO attainment? *Basis:* Section 3.3.1 uses a single constraint bounding token-level violations without distinguishing TPOT and TBT.

## Limitations
- **Implementation Details Missing:** Exact ILP formulation (variable domains, objective weights), solver invocation logic, and decode window Δ tuning are underspecified, hindering precise replication.
- **Robustness of Feedback Loop:** Methodology for online profiling (`compℓ`, `B`) and latency margin tracking for Token-Deposit is vague, raising questions about performance under dynamic resource contention.
- **Generalization Scope:** Evaluations limited to 8B/70B models on synthetic traces; applicability to emerging architectures (e.g., MoE) or diverse real-world workloads is unverified.

## Confidence
- **Fine-Grained ILP Placement (Mechanism 1):** Medium. Theoretical soundness is clear, but direct experimental ablation isolating per-request granularity vs. other optimizations is weak.
- **Continuous Reconfiguration (Mechanism 2):** Low. Relies on unverified assumptions about solver hiding and profile stability; no direct failure analysis under rapidly changing conditions.
- **Token-Deposit & Pause-Resume (Mechanism 3):** Medium. Figure 14c offers some support, but buffer sizing policy and interaction with SLO scaling lack thorough stress-testing.

## Next Checks
1. **Measure solver overhead vs. decode step latency across varying batch sizes and sequence lengths.** Log solver wall-time per invocation and decode latency; verify the solver consistently finishes within the Δ window and quantify stall events attributable to solver lag.
2. **Evaluate Token-Deposit buffer efficacy under high-variability trace with frequent SLO scaling changes.** Inject synthetic traces with abrupt context length spikes and measure deposit balance decay; correlate buffer exhaustion with P99 TBT violations to confirm masking limits.
3. **Stress-test Pause-Resume victim selection with targeted long-request traces.** Compare ORBITFLOW's heuristic (largest KV) against random and shortest-request pausing on SLO attainment and per-request E2E latency variance to expose potential starvation.
