# Mnemis: Dual-Route Retrieval on Hierarchical Graphs for Long-Term LLM Memory

## Quick Facts
- **arXiv ID:** 2602.15313  
- **Source URL:** https://arxiv.org/abs/2602.15313  
- **Reference count:** 40  
- **Primary result:** Achieves SOTA on LoCoMo (93.9) and LongMemEval-S (91.6) with GPT-4.1-mini, with significant gains on multi-hop and temporal reasoning.

## Executive Summary
Mnemis is a novel long‑term memory system for large language models that overcomes the limitations of existing RAG and Graph‑RAG approaches, which rely solely on fast, similarity‑based (System‑1) retrieval and fail on queries requiring global reasoning or comprehensive coverage. It introduces a dual‑route framework: System‑1 performs fast similarity search over a base graph of episodes, entities, and edges using embeddings and BM25; System‑2 executes a deliberate “Global Selection” mechanism that traverses a hierarchically organized semantic graph built from memory entities, enabling structured scanning over abstract categories. The two routes run in parallel and their outputs are fused by a re‑ranker before answer generation. Evaluated on LoCoMo and LongMemEval‑S benchmarks, Mnemis achieves state‑of‑the‑art performance (93.9 and 91.6 with GPT‑4.1‑mini) and shows substantial improvements on multi‑hop and temporal reasoning tasks.

## Method Summary
Mnemis ingests conversation histories into a **base graph**: each turn becomes an *Episode*; an LLM extracts *Entities* (with summary, tag, and associated episodes), *Edges* (relationships with facts and timestamps), and *Episodic Edges* linking episodes to entities. Deduplication uses name and embedding similarity. A separate **hierarchical graph** is built by clustering base Entities into *Categories* across multiple layers under three constraints: *Minimum Concept Abstraction*, *Many‑to‑Many Mapping*, and *Compression Efficiency* (ensuring balanced layer sizes and minimum children per category). At query time, **System‑1** retrieves relevant episodes, entities, and edges via embedding cosine similarity and BM25, merging results via Reciprocal Rank Fusion (RRF) with a top‑k budget. **System‑2** navigates the hierarchy from the top, using an LLM to select pertinent leaf Entities; all incident edges and episodes of those entities are then retrieved. The combined result set is re‑ranked using Qwen3‑Reranker‑8B, truncated to context limits, and fed to an answer LLM (GPT‑4.1‑mini) to produce the final response.

## Key Results
- SOTA performance: **93.9** on LoCoMo and **91.6** on LongMemEval‑S using GPT‑4.1‑mini.
- Dual‑route synergy: Ablation shows combined System‑1+System‑2 (93.3) significantly outperforms System‑1 alone (89.1) or System‑2 alone (87.7) on LoCoMo.
- Strong gains on challenging query types: multi‑hop, temporal reasoning, and enumerative tasks.

## Why This Works (Mechanism)
### Mechanism 1: System‑1 Route
**Claim:** Mnemis’s System‑1 route efficiently retrieves fine‑grained, semantically similar memory items (Episodes, Entities, Edges) using embedding and full‑text search.

**Mechanism:** New historical inputs are parsed into Episodes, Entities, and Edges stored in a base graph. For a query, the system computes cosine similarity (embeddings) and BM25 (text) over stored components, merges results via Reciprocal Rank Fusion (RRF), and truncates to a top‑k budget.

**Core assumption:** Items with surface‑level lexical or embedding similarity to the query are likely relevant, providing a fast heuristic that works well for focused, single‑session queries.

**Evidence anchors:**
- [section 2.1] Details the base graph components (Episodes, Entities, Edges, Episodic Edges) and the ingestion pipeline.
- [section 2.3] Describes System‑1’s dual search (embedding + BM25) and RRF re‑ranking.
- [corpus] Neighbor papers (e.g., GraphRAG, Nemori) confirm graph‑based RAG is a known paradigm; Mnemis refines extraction but the core similarity assumption is shared.

**Break condition:** When queries require aggregating evidence across multiple disconnected graph nodes or enumerating all members of a category (e.g., “list all cities visited”), System‑1’s top‑k truncation fails to achieve comprehensive coverage.

### Mechanism 2: System‑2 Route
**Claim:** Mnemis’s System‑2 route performs deliberate, top‑down traversal of a hierarchical semantic graph to achieve global, structured scanning of memory, addressing gaps in similarity‑based retrieval.

**Mechanism:** Entities from the base graph are clustered bottom‑up into multi‑level Categories following three principles: (1) Minimum Concept Abstraction (categories are specific enough to be informative), (2) Many‑to‑Many Mapping (an entity can belong to multiple categories), and (3) Compression Efficiency Constraint (balanced layer sizes). At query time, the LLM navigates this hierarchy layer‑by‑layer from the top, selecting relevant Categories and finally the underlying Entities, then retrieves all connected Edges and Episodes.

**Core assumption:** Human‑like semantic hierarchies exist in memory and can be automatically constructed; browsing such a hierarchy allows systematic coverage of a concept’s entire extension (e.g., all sub‑types of “Geographical Locations”).

**Evidence anchors:**
- [abstract] Explicitly states the System‑2 “Global Selection” mechanism enables “top‑down, deliberate traversal over semantic hierarchies.”
- [section 2.2] Defines the hierarchical graph components and the three construction principles in detail.
- [section 3.3.1] Win case (fig. 3) shows how Global Selection retrieves the root cause (“weight”) via the path “Physical Well‑Beings”→“Health”→“Physical Health”→“Health Factors”, which similarity search missed.
- [corpus] Neighbors (HiMem, MemTree) explore hierarchical memory, but Mnemis uniquely enforces many‑to‑many mapping and compression constraints for retrieval‑focused browsing.

**Break condition:** If the hierarchical graph is poorly constructed—e.g., too shallow (no useful abstractions), too deep (excessive layers causing navigation overhead), or unbalanced violating compression rules—the top‑down path may terminate prematurely or miss key branches.

### Mechanism 3: Dual‑Route Integration
**Claim:** The dual‑route integration (System‑1 + System‑2) yields complementary retrieval signals; re‑ranking their union improves performance over either alone by capturing both fine‑grained semantic similarity and coarse structural relevance.

**Mechanism:** Both routes execute in parallel. System‑1 returns a ranked list; System‑2 returns an unordered but structurally grounded set. A re‑ranker (or RRF for System‑1 items) combines and reorders the unified set of Episodes, Entities, and Edges before answer generation.

**Core assumption:** Semantic similarity (System‑1) and relational/structural relevance (System‑2) are orthogonal dimensions; their combination mitigates the weaknesses of each.

**Evidence anchors:**
- [section 2.3] Describes the parallel execution and re‑ranking step.
- [table 4] Ablation shows System‑1+System‑2 (93.3) significantly outperforms System‑1 alone (89.1) and System‑2 alone (87.7) on LoCoMo with GPT‑4.1‑mini.
- [section 3.3.1] Notes that System‑2 excels on enumerative problems while System‑1 handles temporal queries better; their combination improves all categories.
- [corpus] Neighbors generally use single‑route retrieval; Mnemis’s explicit dual‑route design is distinctive, though dual‑process theory (Kahneman) provides a conceptual anchor.

**Break condition:** If the re‑ranker is biased toward one route’s scoring pattern (e.g., heavily favors embedding similarity), the complementary benefit diminishes. Also, for very simple queries, the added complexity may not yield gains.

**Why needed here:** The entire framework maps cognitive theories to retrieval routes. System‑1 is fast, associative; System‑2 is slow, analytical. This mapping justifies why a single retrieval method is insufficient.

## Architecture Onboarding
### Component Map
- **Ingestion Pipeline** writes to **Base Graph Store** (Neo4j) and periodically updates **Hierarchical Graph Store** (Neo4j).
- **Retrieval Orchestrator** triggers **System‑1** (on Base Graph) and **System‑2** (on Hierarchical Graph) in parallel.
- **System‑1** returns a ranked list; **System‑2** returns a set of relevant leaf Entities.
- Both outputs are sent to the **Re‑ranker** (Qwen3‑Reranker‑8B).
- **Re‑ranker** produces a fused context for the **Answer Generator** (GPT‑4.1‑mini).
- **Answer Generator** produces the final response.

### Critical Path
1. New conversation turn arrives → formatted as Episode.
2. Base graph ingestion extracts Entities/Edges from new & recent Episodes.
3. (Periodic) Hierarchical graph rebuild: all base Entities clustered into Categories layer‑by‑layer under constraints.
4. Query arrives → System‑1: similarity search over base graph components → top‑k list.
5. Query arrives → System‑2: LLM traverses hierarchy top‑down, selects relevant leaf Entities → retrieves all connected Edges/Episodes.
6. Re‑ranker fuses both result sets → final context.
7. Answer LLM generates response.

### Design Tradeoffs
- **Latency vs. Coverage:** System‑1 fast (~embedding lookup), System‑2 slow (LLM calls per layer). System‑2 has no top‑k limit but risks retrieving excessive context.
- **Hierarchy Stability vs. Freshness:** Hierarchical graph rebuilt periodically; new Entities may be temporarily uncategorized until next rebuild.
- **Expressiveness vs. Complexity:** Many‑to‑many mapping increases expressiveness but complicates traversal and may create ambiguous paths.
- **Budgeting:** Top‑k applies only to System‑1 and final context; System‑2 retrieves all connected items for selected Entities, potentially exceeding budget if an Entity has many edges.

### Failure Signatures
- **System‑1 dominance:** If System‑2 route returns few/no items, check if query is too vague for hierarchical navigation or if hierarchy construction failed (e.g., all Entities in one top‑level Category).
- **System‑2 over‑generation:** If final context is huge (>1000 tokens), System‑2 likely selected high‑degree Entities; consider filtering or adding a lightweight ranking within System‑2.
- **Poor multi‑hop performance:** Could indicate System‑1 failed to retrieve all needed hops, or System‑2 path missed relevant intermediate Categories. Inspect hierarchy for adequate abstraction depth.
- **Re‑ranker confusion:** If scores are uniform across items, the re‑ranker may not distinguish between System‑1 and System‑2 outputs; consider calibrating re‑ranker prompts.

### First 3 Experiments
1. **Component Sanity Check:** Ingest a tiny, controlled memory (5 Episodes, 10 Entities) with known ground truth. Verify base graph stores correct Entities/Edges. Manually inspect the constructed 2‑layer hierarchy—do Categories make sense and follow many‑to‑many mapping?
2. **Route Isolation:** Run queries on LoCoMo using only System‑1 (RAG+Graph) and only System‑2. Confirm System‑2 improves on multi‑hop/enumerative queries per paper’s claim (table 4).
3. **Top‑k Sensitivity:** Vary System‑1 top‑k (5, 10, 30) while keeping System‑2 constant. Plot overall score—expect sharp rise from 5→10, then plateau (fig. 4). If not, check if base graph has sufficient coverage or if re‑ranker is underperforming.

## Open Questions the Paper Calls Out
### Open Question 1
**Question:** How can the hierarchical graph be updated incrementally in real‑time as new episodes are ingested, rather than through periodic full rebuilds, while maintaining the quality constraints (Minimum Concept Abstraction, Many‑to‑Many Mapping, Compression Efficiency)?
**Basis in paper:** [explicit] “When the base graph is updated, the hierarchical graph should be updated accordingly. Currently, we periodically rebuild the hierarchical graph for simplicity and leave optimization for future work.” (Section 2.2)
**Why unresolved:** Periodic rebuilding is computationally expensive and may not scale to high‑throughput, real‑time agent interactions. Incremental updates risk violating hierarchical constraints or degrading abstraction quality over time.
**What evidence would resolve it:** An algorithm or mechanism that can dynamically merge new entities/categories into the existing hierarchy without full recomputation, evaluated for stability, constraint adherence, and retrieval accuracy over long‑running deployments.

### Open Question 2
**Question:** To what extent can the System‑2 Global Selection mechanism be extended beyond simple top‑down category traversal—e.g., by incorporating learned planning, multi‑path exploration, or adaptive depth control—to better handle complex, temporally nuanced, or loosely structured queries that currently fall outside its optimal scope?
**Basis in paper:** [explicit] “In future work, we plan to … enhance global selection with more flexible graph traversal and planning mechanisms.” (Conclusion) Also, [inferred] from the observation that System‑2 is expected to perform well on enumerative problems but weakly on temporal ones, and that ~9.94% of queries in LoCoMo fail to produce System‑2 results due to termination conditions.
**Why unresolved:** The current top‑down, layer‑by‑layer selection is rigid and may not retrieve all relevant evidence for queries requiring reasoning over event sequences, temporal constraints, or multiple disconnected semantic paths. Flexible traversal could improve coverage but might increase cost and complexity.
**What evidence would resolve it:** An extended Global Selection protocol that dynamically branches, revisits layers, or integrates temporal reasoning, with systematic evaluation showing improved recall on temporal and multi‑hop questions without prohibitive overhead.

### Open Question 3
**Question:** What is the optimal routing strategy between System‑1 and System‑2 retrieval routes for different query types and memory states, and can a lightweight meta‑controller be learned to decide when to invoke each route (or both) to maximize accuracy‑cost trade‑offs?
**Basis in paper:** [inferred] From the complementary strengths noted: System‑1 provides fine‑grained semantic similarity, while System‑2 offers structural coverage. The paper combines both always but notes System‑2 is unsuitable for all queries (e.g., temporal). The cost breakdown (Table 3) shows System‑2 is significantly more expensive (~3.6k seconds runtime vs. ingestion costs). No analysis is provided on per‑query routing decisions.
**Why unresolved:** Always running both routes is costly. A dynamic router could skip System‑2 for simple similarity‑based queries, saving time and tokens, but misrouting could hurt accuracy. The conditions under which each route contributes uniquely are not formally modeled.
**What evidence would resolve it:** A study correlating query features (e.g., type, embedding distribution, graph connectivity) with the marginal benefit of System‑2, followed by a trained router (e.g., classifier) that predicts route usage, validated on held‑out data for accuracy and efficiency gains.

### Open Question 4
**Question:** How do the design parameters of the hierarchical graph (e.g., compression ratio *n*, node count reduction rule, maximum layer limit) affect the trade‑off between retrieval comprehensiveness (recall) and efficiency (latency, token usage) of System‑2 Global Selection?
**Basis in paper:** [explicit] The compression efficiency constraint uses *n* (minimum children per category) and a layer‑wise node count reduction rule, but no ablation or sensitivity analysis on these parameters is provided. The paper uses a fixed configuration without justification.
**Why unresolved:** These parameters directly control graph granularity and depth, which influence how many entities are selected at the lowest layer and thus the size of the retrieved context. Too aggressive compression may lose important distinctions; too loose may overwhelm the answer model with noise or increase traversal cost.
**What evidence would resolve it:** Systematic experiments varying *n* and layer limits, measuring recall of ground‑truth entities for diverse query types, and correlating with System‑2 retrieval time and final answer accuracy. This would yield guidelines for parameter tuning based on desired recall‑latency profiles.

### Open Question 5
**Question:** Can Mnemis’s dual‑route design and hierarchical graph construction be successfully transferred to non‑textual memories (e.g., images, audio, structured database records) without sacrificing the semantic coherence and abstraction quality of the hierarchy?
**Basis in paper:** [explicit] “In future work, we plan to support more data modalities.” (Conclusion) The current implementation and evaluation are purely text‑based (episodes, entities, edges from conversational text).
**Why unresolved:** The extraction, deduplication, and categorization principles (e.g., “Minimum Concept Abstraction”) are defined for textual entity names and summaries. Multimodal data introduces new challenges: how to create cross‑modal embeddings for similarity search, how to describe non‑textual items for hierarchical clustering, and whether the many‑to‑many mapping principle remains meaningful.
**What evidence would resolve it:** An extension of Mnemis that ingests multimodal memories (e.g., images with captions, audio transcripts), defines appropriate embedding and summarization methods, and demonstrates comparable or improved performance on multimodal memory benchmarks (e.g., tasks requiring recall of visual or auditory events).

## Limitations
- Hierarchical construction parameters (e.g., minimum children `n`, layer size limits) are not specified, requiring empirical tuning and potentially causing unstable hierarchies.
- Extraction pipeline details (LLM prompts, deduplication thresholds, reflection mechanisms) are omitted; implementations must approximate from similar systems, risking variability.
- Re‑ranker calibration (how it fuses System‑1 scores with System‑2’s unranked set) is unclear, which may diminish the complementary benefits.
