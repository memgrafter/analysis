# Sample Size Calculations for Developing Clinical Prediction Models: Overview and pmsims R package
## Quick Facts
- arXiv ID: 2602.23507
- Source URL: https://arxiv.org/abs/2602.23507
- Reference count: 0
- Primary result: A simulation‑based method integrating learning curves, Gaussian Process optimization, and assurance principles provides model‑agnostic sample size estimates for clinical prediction models, implemented in the `pmsims` R package.

## Executive Summary
Inadequate sample sizes for clinical prediction models risk overfitting and poor generalizability. This study introduces a novel simulation‑based approach that combines learning curves, Gaussian Process (GP) optimization, and assurance principles to estimate the minimum development sample size needed for a model to achieve a desired performance (e.g., AUC) with a specified probability (e.g., 80%). Implemented in the flexible R package `pmsims`, the method explicitly accounts for performance variability across development datasets. Case studies comparing eight methodologies show that sample size estimates vary substantially by method, metric, and model type. Machine learning models often require 5‑10× larger samples than logistic regression, sometimes exceeding 20,000 under misspecification. For logistic regression targeting a calibration slope >0.9 with 80% assurance, `pmsims` yields estimates of 3510, 4198, and 1439 across three scenarios, aligning with other simulation tools but offering greater flexibility and efficiency.

## Method Summary
The core approach is simulation‑based: for a user‑specified model, performance metric, and data‑generating process, the algorithm repeatedly simulates development datasets of varying sizes, fits the model, and evaluates performance on a large fixed test set. A Gaussian Process surrogate model approximates the learning curve (performance vs. sample size) and estimates the 20th percentile of performance across simulations (for 80% assurance). An optimization routine then identifies the smallest sample size where this percentile exceeds a threshold `M*`, derived from an ideal large‑sample performance `M_ideal` minus an acceptable deviation `d`. The method is model‑agnostic; users define custom data generation, model fitting, and evaluation functions. A tuning step adjusts generator parameters so that asymptotic performance (`n` → ∞) matches `M_ideal`. The GP‑based surrogate reduces computational burden by focusing simulations on informative sample sizes, making the process efficient.

## Key Results
- Machine learning models (XGBoost, random forest, SVM, neural network) required 5‑10× larger sample sizes than logistic regression for comparable target performance.
- For logistic regression targeting a calibration slope >0.9 with 80% assurance, sample size estimates were 3510, 4198, and 1439 across three distinct data scenarios.
- The `pmsims` approach yields estimates comparable to other simulation‑based tools but with greater flexibility and computational efficiency due to GP optimization.

## Why This Works (Mechanism)
The proposed simulation‑based sample size estimation method rests on three key mechanisms:

1. **Gaussian Process surrogate for efficient learning curve approximation** – Instead of exhaustively simulating many datasets across a wide range of sample sizes, a GP model interpolates performance from a limited set of simulated points. It models uncertainty around the learning curve, guiding subsequent simulations to sample sizes that most efficiently narrow the confidence interval for the assurance level (e.g., 20th percentile). This approach assumes the learning curve is smooth and monotonic; failure may occur if the true curve is highly non‑smooth (e.g., due to extreme model instability or discrete data artifacts).

2. **Assurance criterion to account for model variability** – The method solves for the smallest sample size *n* where the 20th percentile (for 80% assurance) of the performance distribution across simulated development datasets exceeds a target `M*`. This ensures that in 80% of plausible development scenarios, the model will meet the standard, directly addressing model instability. It assumes the distribution of performance metrics can be reliably estimated via simulation; too few replicates can lead to unstable quantile estimates.

3. **Model‑agnostic modular architecture** – The framework decouples data generation, model fitting, and evaluation. Users supply three functions: a data generator (`P_gen`), a model fitting function (`f̂`), and a metric function (`M`). This separation allows the method to be applied to any prediction algorithm (logistic regression, machine learning) and any performance metric. The validity of the estimate depends on correct implementation of these user‑defined components and a sufficiently large independent test set. Misspecification of the data generator or model function will produce invalid sample size estimates.

## Foundational Learning
Understanding the following concepts is essential for applying the `pmsims` approach:

- **Simulation‑based vs. closed‑form sample size estimation** – Closed‑form methods (e.g., `pmsampsize`) rely on strong asymptotic assumptions (e.g., correctly specified logistic regression) and are not readily extendable to machine learning or complex data structures. Simulation‑based methods like `pmsims` model the entire development process and can accommodate any algorithm. *Quick check: Why might a sample size formula for logistic regression fail when applied to a random forest model on the same data?*

- **Learning curves** – A learning curve describes how model performance changes with increasing sample size. The `pmsims` method estimates this curve to determine the sample size needed to reach a target performance. *Quick check: If a learning curve plateaus very slowly (shallow slope), what does that imply about the sample size needed to reach a target performance?*

- **Assurance criterion** – Assurance is the probability that the model’s performance (quantified by a percentile of the performance distribution across development samples) exceeds a predefined threshold. This is more stringent and practical than targeting the mean performance alone, as it explicitly accounts for variability across development datasets. *Quick check: For two models with the same mean performance at n=2000, but one has much higher variance across samples, which requires a larger sample size to achieve 80% assurance?*

## Architecture Onboarding
The `pmsims` package follows a modular pipeline:

**Component map**: Scenario Definer → Data Generator Tuner → Learning Curve Estimator → Sample Size Solver

**Critical path**: Input specification → Generator tuning → Iterative GP‑guided simulation → Curve fitting → n identification

**Design tradeoffs**:
- **Computation vs. Realism**: Simple parametric data generators are fast but may oversimplify real data; complex synthetic generators (e.g., `synthpop`) are more realistic but slower.
- **Model‑agnostic vs. Ease‑of‑use**: Full flexibility requires user coding for custom models/generators; built‑in options trade flexibility for plug‑and‑play convenience.
- **Assurance stringency**: Higher assurance (e.g., 90% vs. 80%) demands more simulation replicates per sample size to accurately estimate tail quantiles, increasing runtime.

**Failure signatures**:
- **Tuning failure**: The data generator cannot be tuned to achieve `M_ideal` even with very large `n`; indicates unrealistic target or generator constraints.
- **GP convergence failure**: The Gaussian Process model fails to stabilize, often due to insufficient simulations or extremely noisy performance estimates (e.g., from a highly stochastic ML model with too few repeats).
- **Non‑monotonic learning curve**: If performance decreases with more data (possible with some ML models due to regularization), the solver may fail or produce misleading results.

**First 3 experiments**:
1. **Baseline logistic regression** – Use built‑in logistic regression and binary data generator with 10 true predictors. Target AUC = 0.8, assurance = 80%. Verify output sample size is reasonable (e.g., ~1000‑5000) and runtime acceptable.
2. **Generator tuning stress test** – Set an unrealistically high `M_ideal` (e.g., AUC = 0.99) for a simple data generator. Confirm the tuning step fails gracefully with an informative error.
3. **Compare assurance vs. mean** – For the same scenario, compute both the default assurance‑based sample size and a mean‑based sample size (by solving the mean learning curve directly). Observe that assurance yields a larger `n` and quantify the difference.

## Open Questions the Paper Calls Out
- **How can sample size estimation methods be extended to hierarchical and multimodal data structures?** Current methods assume independent observations; hierarchical clustering and multimodal inputs introduce correlations and dimensionality that affect learning curves and effective sample size.
- **How should fairness and stability metrics be integrated into sample size calculations to ensure equitable and robust prediction models?** Existing focus on overall performance ignores subgroup fairness and model stability under perturbations.
- **What adjustments are needed for sample size planning when development data contain missing values?** Missing data is ubiquitous and can bias performance; current methods largely ignore it.
- **Can generative adversarial networks (GANs) or other deep generative models improve the realism of synthetic data for sample size simulations?** Standard parametric generators oversimplify real clinical data, potentially biasing estimates.

## Limitations
- The exact data generator parameters for the case studies are not publicly available (broken GitHub link), hindering exact replication of reported sample size numbers.
- The Gaussian Process surrogate relies on the assumption of a smooth, monotonic learning curve; it may produce biased estimates if the true curve is highly erratic or non‑monotonic.
- The method’s accuracy critically depends on the correctness of user‑provided data generation, model fitting, and metric functions; misspecification leads to invalid sample size estimates.

## Confidence
- **High confidence**: The `pmsims` package correctly implements the described Gaussian Process‑assurance methodology and its model‑agnostic design is well documented.
- **Medium confidence**: Claims of computational efficiency and that the assurance criterion yields more conservative (larger) sample sizes are plausible but not extensively benchmarked across a wide range of scenarios.
- **Low confidence**: The specific numeric results reported in the paper (e.g., 5‑10× larger sample sizes for machine learning, the exact values 3510/4198/1439) lack reproducible details and should be treated as tentative.
