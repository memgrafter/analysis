# PeopleSearchBench: A Multi-Dimensional Benchmark for Evaluating AI-Powered People Search Platforms
## Quick Facts
- **arXiv ID:** 2603.27476
- **Source URL:** https://arxiv.org/abs/2603.27476
- **Reference count:** 40
- **Primary result:** Introduces PeopleSearchBench, the first open-source benchmark for AI-powered people search; specialized agent Lessie achieves the highest overall score (65.2), 18.5% above the second-ranked system.

## Executive Summary
PeopleSearchBench establishes the first comprehensive, open-source evaluation framework for AI-powered people search platforms. It addresses the lack of standardized assessment by introducing a multi-dimensional scoring system across Relevance Precision, Effective Coverage, and Information Utility. The core innovation is Criteria-Grounded Verification, which replaces subjective LLM-as-judge scoring with factual verification against explicit query criteria using live web search. Evaluating four commercial and agent platforms on 119 real-world queries, the benchmark finds that the specialized agent Lessie significantly outperforms competitors, achieving perfect task completion. The benchmark, code, and query set are publicly available to standardize future development and comparison in this domain.

## Method Summary
The evaluation uses 119 multilingual, real-world queries spanning recruiting, B2B sales, expert search, and influencer discovery. For each query-platform pair, the system retrieves up to 15 person profiles. The core *Criteria-Grounded Verification* pipeline operates in two stages: first, an LLM extracts explicit, verifiable criteria from the query; second, for each returned person, the system performs live web searches (via Tavily) per criterion and uses an LLM judge (Gemini 3 Flash) to assign a binary or partial relevance score (met/partially_met/not_met). These per-criterion judgments aggregate into three dimension scores: (1) **Relevance Precision** (padded nDCG@10), (2) **Effective Coverage** (task completion rate + qualified yield), and (3) **Information Utility** (profile completeness/actionability via an LLM prompt). The final overall score is the equal-weight average of the three dimensions. Confidence intervals are derived via bootstrap resampling (1000 iterations).

## Key Results
- Lessie (specialized AI agent) scores 65.2 (±1.5), 18.5% higher than second-place Exa (55.0±1.8).
- Lessie is the only platform with 100% task completion across all queries.
- Lessie leads all three evaluated dimensions: Relevance Precision (70.2±2.1), Effective Coverage (69.1±2.4), and Information Utility (56.4±1.8).

## Why This Works (Mechanism)
The benchmark's design is driven by the need for objective, reproducible evaluation in a field previously lacking standards. Its mechanism replaces noisy, subjective LLM-based scoring with a verification loop grounded in dynamic, factual web search. By decomposing queries into explicit criteria and validating each profile against them with fresh data, the system minimizes judge bias and stale information. This creates a reliable signal for comparing platforms on their ability to retrieve *factually relevant* people who *fully satisfy* the query's implicit and explicit demands, not just rank plausible candidates.

## Foundational Learning
- **Concept:** Criteria-Grounded Verification  
  **Why needed:** Moves beyond static, judge-based scoring to fact-check candidate profiles against query intent using live data.  
  **Quick check:** Can your evaluation decompose a query like "Find a Python ML engineer in Berlin with open-source contributions" into discrete, verifiable facts (e.g., location, skill, public repos) and validate each via current web search?
- **Concept:** Multi-Dimensional Platform Evaluation  
  **Why needed:** People search utility depends on more than ranking; platforms must also cover all query needs and provide actionable profiles.  
  **Quick check:** Does your benchmark measure not just *precision* but also *completeness of task fulfillment* and *profile depth*?
- **Concept:** Live Web Search as Verification Oracle  
  **Why needed:** Static datasets become stale; people's details change. Grounding in real-time web data ensures judgments reflect current reality.  
  **Quick check:** Is your verification step using a search API (like Tavily) to fetch fresh information about a candidate before scoring, rather than relying on the platform's cached profile?
- **Concept:** Unified Result Schema Normalization  
  **Why needed:** Platforms output heterogenous formats; fair comparison requires a common representation.  
  **Quick check:** Do you have a deterministic mapping (e.g., regex, field matching) to convert diverse platform outputs (names, companies, URLs) into a single schema?
- **Concept:** Bootstrap Confidence Intervals  
  **Why needed:** With many platforms and queries, score distributions need statistical validation for meaningful comparisons.  
  **Quick check:** Are you resampling your query-platform result sets to compute uncertainty bounds on your final scores?

## Architecture Onboarding
**Component Map:**  
Query Set (119 queries) -> Platform Execution (4 APIs/Interfaces) -> Result Retrieval (top 15 profiles) -> Schema Normalization (Unified Format) -> Criteria Extraction (LLM) -> Per-Criterion Web Search (Tavily) -> LLM Judge (Gemini) -> Score Aggregation (nDCG, Coverage, Utility) -> Bootstrap Resampling -> Final Dimensions & Overall Score

**Critical Path:**  
1. Execute query on platform via specified API/web interface.  
2. Normalize output to unified schema.  
3. Extract criteria from query text.  
4. For each person and criterion: fetch web evidence, judge relevance.  
5. Compute nDCG@10 (Relevance), task completion/yield (Coverage), completeness score (Utility).  
6. Average dimensions for overall score; repeat via bootstrap.

**Design Tradeoffs:**  
- *Verification cost vs. fidelity:* Each criterion-person pair triggers a separate web search, exploding cost and latency but ensuring fresh, specific evidence.  
- *Judge stability vs. flexibility:* Using a single judge model (Gemini Flash) ensures consistency but may inherit model-specific biases; prompt engineering is critical.  
- *Platform fairness vs. access:* Evaluating diverse platforms (API vs. web UI) requires bespoke adapters; minor differences in how "top 15" are retrieved could skew comparisons.

**Failure Signatures:**  
- **Search API exhaustion/quota errors:** Indicates unbounded search calls; likely missing caching or misconfigured criteria extraction (too many criteria).  
- **Normalization schema mismatches:** High rate of "null" or missing fields in unified schema suggests platform output changed or mapping rules are incorrect.  
- **Judge inconsistency:** Low Cohen's κ in human validation spot-checks points to prompt ambiguity or judge model instability.  
- **Task completion = 0%:** Platform returned no results or all results were filtered out as duplicates during normalization.

**First Three Experiments:**  
1. **Smoke test verification pipeline:** Run on 3 queries across all platforms; manually audit each step (criteria extraction, search queries, judge output) for sanity.  
2. **Cost-latency profiling:** Instrument the pipeline to log number of web searches per query and total runtime; establish baseline for budgeting and timeout settings.  
3. **Normalization validation:** For each platform, sample 20 raw outputs vs. normalized records; verify correct field mapping and deduplication logic (e.g., same name+company merging distinct people).

## Limitations
- **Platform execution underspecification:** Exact API parameters, rate limits, and programmatic access methods for all four platforms (especially web-based ones) are not detailed, risking inconsistent result retrieval.  
- **Judge pipeline sensitivity:** Minor variations in the extraction or verification prompts, or the judge model version, could alter scores despite high human agreement on the pipeline.  
- **Novelty claim uncertainty:** While no direct people-search benchmark exists, overlap with adjacent search verification or multi-dimensional evaluation frameworks makes the "first" claim moderately uncertain without a deeper corpus analysis.

## Confidence
- **Benchmark design & reproducibility:** **High** — Public code, clear pipeline, and strong human validation (κ=0.84).  
- **Performance results (Lessie’s lead):** **Medium** — Relies on faithful platform execution and stable judge; high inter-annotator agreement supports reliability but not absolute cross-platform fairness.  
- **Scalability & cost claims:** **Low** — The verification pipeline's search cost is noted as a challenge but not quantitatively analyzed for large-scale use.

## Next Checks
1. **Audit platform query execution:** Log exact requests (endpoints, parameters, pagination) for each platform and compare retrieved result sets against the paper's expected top-15 outputs to ensure fidelity.  
2. **Judge prompt sensitivity analysis:** Re-run the verification pipeline on 20 sampled queries with plausible prompt variations (e.g., different few-shot examples) to measure score volatility and robustness.  
3. **Corpus novelty verification:** Systematically search proceedings from major AI/benchmarking conferences (e.g., NeurIPS, ACL, SIGIR) from 2023–2024 for any benchmark explicitly evaluating *people-search platforms* with multi-dimensional metrics to confirm or refute the "first" claim.
