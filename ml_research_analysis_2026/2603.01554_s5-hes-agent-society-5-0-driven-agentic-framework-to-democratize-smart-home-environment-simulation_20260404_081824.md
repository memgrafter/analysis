# S5-HES Agent: Society 5.0-driven Agentic Framework to Democratize Smart Home Environment Simulation

## Quick Facts
- **arXiv ID:** 2603.01554
- **Source URL:** https://arxiv.org/abs/2603.01554
- **Reference count:** 40
- **Primary result:** An agentic RAG framework enables natural-language-driven, end-to-end smart home simulation without programming, achieving high-fidelity threat modeling and realistic device behavior generation.

## Executive Summary
Smart home simulators traditionally require significant technical expertise, are often inflexible, and impede multidisciplinary research aligned with Society 5.0 goals. The S5-HES Agent addresses this by introducing an agentic framework that leverages a Retrieval-Augmented Generation (RAG) pipeline and interchangeable large language models (LLMs) to interpret natural language queries and automatically generate complete simulation configurations. The system orchestrates multiple specialized agents to build home layouts, manage devices, inject threats, and optimize scenarios, all validated by a multi-rule verification pipeline. Evaluations demonstrate near-optimal retrieval performance, strong alignment of simulated threats with real-world IoT attack patterns (MITRE ATT&CK), and high realism in generated device messages. The engine also scales predictably across residence templates and produces datasets with superior diversity and taxonomic depth compared to static benchmarks.

## Method Summary
The core task is to democratize smart home simulation by allowing users to describe a scenario in natural language and receive a ready-to-run simulation without any coding. The framework operates on a pre-built knowledge base (KB) of 20,306 document chunks from academic papers, specifications, and threat reports, embedded using GTE-Large (1024-dim) and indexed with BM25. A hybrid retrieval system uses Reciprocal Rank Fusion (RRF) to combine semantic (cosine similarity) and keyword (BM25) search. A multi-agent orchestrator directs four specialized agents—HomeBuilder, DeviceManager, ThreatInjector, and Optimization—which use configurable LLM backends (e.g., Ollama, OpenAI, Gemini) to construct the simulation. A verification pipeline with six validators (schema, physical, semantic, factual, security, business rules) applies a confidence gate (≥0.85 auto-approves). The deterministic simulation engine uses seeded random number generators for reproducible device placement, traffic timing, and attack sequencing, with configurations exportable for reproducibility.

## Key Results
- The RAG pipeline achieves near-optimal retrieval: MRR=1.000 and MAP=0.967, outperforming standalone BM25 and semantic search baselines.
- Simulated threat scenarios show high fidelity: 8 of 9 evaluated threats meet or exceed thresholds for Attack Behaviour Coverage (≥60%) and Attack Lifecycle Fidelity (≥50%) against real IoT datasets (Edge-IIoTset, IoT-23, Bot-IoT).
- Generated device behaviors exhibit high realism, with a composite Message Similarity (M.SIM) score between 88.4% and 90.0% when compared against real-world logs (SDHAR-HOME, Logging).

## Why This Works (Mechanism)
The system succeeds by decomposing the complex configuration problem into manageable subtasks handled by specialist agents, coordinated by an orchestrator. The hybrid RAG pipeline ensures precise, context-aware retrieval from a curated KB, which grounds the LLM-generated configurations in factual device specs and threat models. The verification pipeline acts as a safeguard, catching inconsistencies before simulation. Determinism via seeded RNGs ensures that scalability and reproducibility claims are empirically verifiable. The use of interchangeable LLMs allows adaptation to different cost, latency, or capability requirements without redesigning the agent logic.

## Foundational Learning
- **Retrieval-Augmented Generation (RAG):** Needed to ground LLM outputs in a specific, technical knowledge base without fine-tuning. *Quick check:* Does retrieval consistently surface relevant device specs or threat techniques for a given query?
- **Multi-Agent Orchestration:** Needed to partition the configuration workflow into parallelizable, specialized steps (layout, devices, threats). *Quick check:* Can agents work semi-independently on their sub-tasks while the orchestrator resolves conflicts?
- **Hybrid Search (RRF):** Needed to balance semantic understanding with precise keyword matching for technical terms and identifiers. *Quick check:* Does the RRF score (κ=60, weights 0.7/0.3) yield better results than either search alone on a validation query set?
- **Deterministic Simulation:** Needed for scientific reproducibility and fair scalability benchmarking. *Quick check:* Does running the same configuration with the same seed produce byte-for-byte identical simulation outputs?
- **Rule-Based Verification:** Needed to catch LLM hallucinations or physical impossibilities (e.g., a fridge in a bathroom). *Quick check:* Do the six validators collectively reject implausible configurations while accepting valid ones?
- **MITRE ATT&CK Mapping:** Needed to evaluate threat simulation fidelity against a standardized, real-world adversary model. *Quick check:* Are simulated attack techniques correctly mapped to specific MITRE tactic/technique IDs for coverage calculations?

## Architecture Onboarding
**Component Map:** User (Natural Language Query) -> Orchestrator -> [HomeBuilder Agent -> DeviceManager Agent -> ThreatInjector Agent -> Optimization Agent] -> Simulation Engine -> Verification Pipeline (6 Validators) -> Validated Configuration -> Deterministic Execution.

**Critical Path:** Query -> RAG Retrieval -> Orchestrator intent parsing -> Sequential/Speculative agent execution -> Configuration assembly -> Validation gate -> Simulation run.

**Design Tradeoffs:** Hybrid retrieval (RRF) improves accuracy at slight latency cost vs. single-modality search; interchangeable LLMs trade performance consistency for flexibility; deterministic design sacrifices some stochastic realism for reproducibility; validation confidence gate (≥0.85) balances automation with safety.

**Failure Signatures:** Retrieval MRR/MAP drop below 0.9 indicates KB coverage or RRF weight issues; ABC/ALF scores <50% suggest MITRE mapping or attack sequence logic errors; low M.SIM range overlap indicates unrealistic sensor value distributions; scaling curves non-linear imply template parameter mismatches.

**First Three Experiments:** 1) Run the RAG evaluation notebook with the provided 100-query subset and verify MRR=1.000, MAP=0.967. 2) Execute a "Family apartment" simulation with seed 42, generate 24h of compressed traffic, and compute ABC/ALF for the "credential theft" threat. 3) Extract 1,000 simulated device messages from a benign scenario and compute field coverage and type compatibility against the SDHAR-HOME baseline.

## Limitations
- The exact 100 RAG evaluation queries and their relevance judgments are not publicly disclosed, hindering independent replication of the reported retrieval scores.
- Formal definitions and implementation details for the four device message similarity sub-metrics (field coverage, type compatibility, range overlap, semantic similarity) are unspecified.
- The complete list of 22 threat types, their MITRE ATT&CK technique IDs, and the precise mapping logic to the baseline threat datasets (Edge-IIoTset, IoT-23, Bot-IoT) are not provided.
- Preprocessing and labeling conventions for the reference behavioral datasets (SDHAR-HOME, Logging) are undocumented, creating risk of misalignment during realism evaluation.
