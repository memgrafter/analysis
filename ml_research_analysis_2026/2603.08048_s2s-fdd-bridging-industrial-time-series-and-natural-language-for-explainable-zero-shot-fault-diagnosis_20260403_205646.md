# S2S-FDD: Bridging Industrial Time Series and Natural Language for Explainable Zero-shot Fault Diagnosis

## Quick Facts
- **arXiv ID:** 2603.08048
- **Source URL:** https://arxiv.org/abs/2603.08048
- **Reference count:** 23
- **Primary result:** Achieves 76.92% zero-shot fault diagnosis accuracy on a multiphase flow process using only 500 normal samples and DeepSeek-R1, with reasoning LLMs consistently outperforming non-reasoning ones.

## Executive Summary
S2S-FDD is a framework for explainable, zero-shot industrial fault diagnosis that bridges the gap between continuous sensor time-series data and natural language processing capabilities of large language models (LLMs). It introduces a Signal-to-Semantic operator to convert multivariate signals into textual summaries of trends and deviations, and a multi-turn, tree-structured LLM reasoning process that iteratively references historical maintenance documents and dynamically queries for additional sensor data when needed. Evaluated on a multiphase flow process with no fault data during training, it demonstrates high accuracy and supports a human-in-the-loop mechanism for continuous knowledge base refinement.

## Method Summary
The method operates in two core stages without any fault-specific training. First, a **Signal-to-Semantic (S2S) operator** processes a test sample: it reconstructs the signal from a dictionary of *n* clustered normal patterns via linear least squares, computes residuals to identify anomalous variables, and formats the selected faulty signals (measured, predicted, deviation) into a table. An LLM then summarizes this table into a natural language description (`Di`) of trends and deviations. Second, a **multi-turn tree-structured diagnosis** embeds this description and retrieves relevant historical fault records from a knowledge base via cosine similarity. The LLM is prompted with process context, retrieved knowledge, and the signal description. If the LLM deems information insufficient, it emits a structured `<tool>` call to request additional sensor data, triggering a recursive S2S operation on the new signals and appending results to the conversation. The final diagnosis is aggregated across multiple reasoning runs via majority voting. Verified expert feedback on diagnosis reports can be added to the knowledge base for future improvement.

## Key Results
- Achieves **76.92% accuracy** on 13 test cases across 5 fault types using the DeepSeek-R1 reasoning LLM.
- **Reasoning LLMs (DeepSeek-R1, o1-mini) consistently outperform non-reasoning models (Qwen2.5-7B)**, highlighting the importance of structured, multi-turn reasoning.
- The framework operates **zero-shot with only 500 normal training samples**, requiring no fault data for model training or fine-tuning.
- Supports **explainable outputs** through natural language summaries and a traceable reasoning chain with dynamic data queries.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** The Signal-to-Semantic operator converts continuous time-series signals into discrete, semantically rich natural language descriptions of trends and deviations, enabling LLMs to process industrial data.
- **Mechanism:** It reconstructs an input sample via linear combination of *n* representative normal pattern vectors (from K-means clustered normal data). Large reconstruction residuals trigger anomaly detection. Selected faulty variables are formatted into a table (measured, predicted, deviation) and summarized by an LLM into qualitative text (e.g., "decreasing trend, below ideal").
- **Core assumption:** Normal process behavior can be adequately represented by a small set of linear combination bases; significant reconstruction residuals correspond to meaningful faults; LLMs can generate accurate summaries from structured tables.
- **Evidence anchors:**
  - [abstract] "design a Signal-to-Semantic operator to convert abstract time-series signals into natural language summaries, capturing trends, periodicity, and deviations."
  - [section II.A] Details the reconstruction `W_out = Dω`, residual calculation, variable selection (anomaly score, earliest fault time, variance filter), and prompt construction with `[TABLE]`.
- **Break condition:** If normal patterns are non-linear or multimodal, linear reconstruction may produce high residuals for normal operation (false positives) or low residuals for subtle faults (false negatives). The LLM summary may also omit critical quantitative details.

### Mechanism 2
- **Claim:** A multi-turn, tree-structured LLM reasoning process performs zero-shot fault diagnosis by iteratively referencing historical maintenance documents and dynamically querying for missing critical signals.
- **Mechanism:** 1) Textual variable descriptions are embedded and compared (cosine similarity) to chunks of historical fault records to retrieve relevant knowledge (`K_target`). 2) The LLM is prompted with process info, sensor list, retrieved faults, and time-series descriptions. 3) If information is insufficient, it emits a tool call (`get_target_table`) for specific sensor data, which is appended to the context for continued reasoning. 4) The diagnosis result is voted across multiple reasoning runs.
- **Core assumption:** Relevant historical fault knowledge is encoded in the text corpus; the LLM can correctly identify missing critical information and request it; the reasoning chain remains coherent across turns with appended tool results.
- **Evidence anchors:**
  - [abstract] "multi-turn tree-structured diagnosis method that references historical documents and dynamically queries signals."
  - [section II.B] Explains embedding-based retrieval (`sim(Di, Kj)`), the diagnosis prompt template with `[FAULT_KNOWLEDGE]` and `[TIME_DESP]`, the `<tool>` call condition ("insufficient or critical variables missing"), and the voting mechanism.
- **Break condition:** If historical documents lack coverage of the current fault type, retrieval fails. If the LLM misidentifies "critical missing variables," it queries irrelevant sensors, leading to wasted turns or incorrect diagnosis. Deeply nested reasoning may exceed context limits.

### Mechanism 3
- **Claim:** A human-in-the-loop feedback loop enables continuous framework refinement by incorporating expert validation of diagnosis reports back into the knowledge base.
- **Mechanism:** After an LLM diagnosis, the generated report (including reasoning and answer) is reviewed by domain experts. Verified reports are incorporated into the historical knowledge base (`Kj`), enriching future retrieval for similar faults.
- **Core assumption:** Experts can reliably distinguish correct from incorrect diagnoses; the textual format of reports is suitable for storage and future retrieval; the added knowledge improves retrieval relevance over time without introducing noise.
- **Evidence anchors:**
  - [abstract] "supports human-in-the-loop feedback for continuous refinement."
  - [section II.B] "...the results of the model diagnosis can be further organized to output a fault diagnosis report, which can be incorporated into the knowledge base for future retrieval after dedicated expert verification. This constitutes a human-in-the-loop closure and knowledge iteration."
- **Break condition:** If expert validation is inconsistent or infrequent, the knowledge base may not improve. Poorly written or ambiguous reports may not be effectively retrievable. The system lacks an automated mechanism to detect or correct incorrectly added reports.

## Foundational Learning
- **Concept: Reconstruction-Based Anomaly Detection**
  - **Why needed here:** The S2S operator's core is reconstructing signals from normal bases; understanding residuals as anomaly scores is key to variable selection.
  - **Quick check question:** What does a large `RES = W_in - W_out` imply about the sample `W_in`?
- **Concept: Embedding-Based Semantic Retrieval**
  - **Why needed here:** The diagnosis relies on matching LLM-generated textual descriptions of deviations to historical textual fault records via vector similarity.
  - **Quick check question:** How is the similarity between a description `Di` and a fault record `Kj` computed?
- **Concept: Tree-Structured LLM Reasoning with Tool Calls**
  - **Why needed here:** The diagnosis is not a single prompt but an iterative tree where the LLM decides if it can answer or needs more data via a function call, affecting the conversation flow.
  - **Quick check question:** What specific output format triggers the system to query additional sensor data instead of providing a final answer?

## Architecture Onboarding
- **Component map:**
  Normal Pattern Repository -> S2S Operator -> Retriever -> Diagnosis Engine -> Voting & Output Aggregator
  (with Knowledge Base Store accessible by Retriever and Diagnosis Engine; Diagnosis Engine can call S2S Operator recursively via `get_target_table`; Human-in-the-Loop Interface feeds back to Knowledge Base Store)
- **Critical path:** Raw time-series → S2S Operator (select variables, generate `Di`) → Retriever (find `K_target`) → Diagnosis Engine (prompt LLM, possibly call `get_target_table` → recursive S2S on new sensor → append) → LLM outputs `<answer>` → Voting → Final diagnosis.
- **Design tradeoffs:**
  - *Reconstruction simplicity (linear) vs. fidelity:* Linear bases are computationally light and interpretable but may fail to capture complex normal dynamics, affecting residual meaningfulness.
  - *LLM reasoning depth vs. cost/time:* Deeper tree-structured reasoning (multiple tool calls) improves accuracy but increases API latency and cost. Stopping at first sufficient answer trades off thoroughness for efficiency.
  - *Knowledge base granularity:* Fine-grained chunking improves retrieval precision but may lose context; coarse chunks preserve context but reduce relevance of specific snippets.
- **Failure signatures:**
  - **Variable Selection Failure:** `S_filtered` contains irrelevant sensors or misses critical ones. Check: Are top anomaly scores and earliest fault times aligned with known fault physics? Is the variance filter threshold (`>2·var`) appropriate?
  - **Retrieval Failure:** `K_target` is empty or irrelevant. Check: Are historical document embeddings high-quality? Is the similarity threshold too high? Do historical records cover the fault type?
  - **Reasoning Failure:** LLM outputs `<uncertain>` or wrong answer despite sufficient data. Check: Is the prompt template clear? Does the LLM correctly exclude contradictory evidence (e.g., Table III shows DeepSeek-R1 correctly excludes Fault 1 based on FT305)?
  - **Tool Call Loop:** Infinite or excessive tool calls. Check: Is the "data sufficiency" logic in the prompt effective? Is `R_max` set appropriately?
- **First 3 Experiments:**
  1.  **S2S Operator Sanity Check:** Feed known normal and single-fault samples. Verify that the textual summary (`Di`) correctly describes the injected fault's trend (e.g., "decreasing pressure" for a blockage) and that `S_filtered` includes the truly faulty sensor.
  2.  **Retrieval Relevance Test:** For a known fault record, compute its embedding. For a set of generated descriptions `Di` (some from the same fault, some from others), measure retrieval recall@k. Ensure the correct fault record appears in top-3 for its own description.
  3.  **Reasoning vs. Non-Reasoning LLM Comparison:** Replicate Table II's case 4 (or another) with a non-reasoning model (Qwen2.5-7B) and a reasoning model (DeepSeek-R1). Audit the full trace: Does the reasoning model perform more exclusion steps? Does it correctly identify when to call a tool?

## Open Questions the Paper Calls Out
- **Open Question 1:** Can the S2S-FDD framework generalize to diverse industrial processes beyond the multiphase flow facility?
  - **Basis in paper:** [explicit] The experiments are conducted solely on the multiphase flow process, as stated in Section III.
  - **Why unresolved:** The framework's design, particularly the S2S operator trained on normal patterns, may be tailored to the specific dynamics of that process. Its applicability to discrete manufacturing, batch processes, or systems with fundamentally different temporal characteristics remains untested.
  - **What evidence would resolve it:** Evaluation on multiple standardized industrial benchmarks (e.g., Tennessee Eastman, semiconductor manufacturing) with varying process types, sensor densities, and fault modes, measuring accuracy and robustness.
- **Open Question 2:** What specific reasoning capabilities of LLMs like DeepSeek-R1 contribute to their superior performance in zero-shot fault diagnosis using S2S-FDD?
  - **Basis in paper:** [explicit] Results show reasoning LLMs achieve higher accuracy (e.g., DeepSeek-R1 at 76.92% vs. Qwen2.5-7B at 23.08%), but the paper does not dissect the reasons.
  - **Why unresolved:** The multi-turn tree-structured method leverages LLM reasoning, but it is unclear whether the gain comes from better interpretation of temporal descriptions, more effective tool-use decisions, or superior cross-referencing with fault knowledge. Without ablation, the key factor remains unknown.
  - **What evidence would resolve it:** Controlled studies comparing reasoning vs. non-reasoning LLMs on identical inputs, with interventions such as disabling tree-structured queries, altering reasoning Chain-of-Thought prompts, or analyzing internal attention patterns on temporal text.
- **Open Question 3:** How sensitive is S2S-FDD to the completeness and accuracy of the historical maintenance document knowledge base?
  - **Basis in paper:** [inferred] The method retrieves similar fault records for diagnosis, but the experiment uses a fixed, presumably complete knowledge base from [19]. No stress-testing of knowledge base limitations is reported.
  - **Why unresolved:** In practice, maintenance records may be incomplete, noisy, or lack coverage of rare faults. The framework's reliance on retrieval makes it vulnerable to knowledge gaps, but this dependence is not quantified.
  - **What evidence would resolve it:** Experiments with controlled degradation of the knowledge base—e.g., removing a percentage of fault records, introducing mislabeled entries, or simulating incomplete documentation—and measuring drop in diagnosis accuracy and recovery via human-in-the-loop updates.
- **Open Question 4:** Does the linear reconstruction model in the S2S operator fail to capture nonlinear normal operating patterns, thereby limiting fault detectability?
  - **Basis in paper:** [inferred] The operator uses linear least squares (Equation 1) to reconstruct signals from a dictionary of normal samples, assuming normal patterns lie in a linear subspace. Theorem 1's theoretical guarantee also assumes linearity.
  - **Why unresolved:** Industrial processes often exhibit nonlinearities (e.g., phase changes, control interactions). If normal behavior is inherently nonlinear, the linear model may produce high residuals even during normal operation (false positives) or fail to reconstruct faulty states accurately (false negatives).
  - **What evidence would resolve it:** Comparative evaluation using nonlinear reconstruction techniques (e.g., kernel-based, autoencoders) on processes with known nonlinear dynamics, assessing residual distributions under normal and faulty conditions, and testing detectability bounds beyond linear assumptions.

## Limitations
- The exact Cranfield multiphase flow dataset and its sampling details are inaccessible. Critical hyperparameters—number of clusters *n*, residual threshold multiplier *α*, and window length *W*—are unreported.
- LLM inference settings (temperature, max tokens) and prompt engineering specifics are missing, as are the structure and chunking strategy of historical maintenance documents.
- The paper provides no empirical evidence of improvement over time from the human-in-the-loop feedback loop or expert consistency.

## Confidence
- **S2S operator (time‑series → text):** Medium. The reconstruction‑based variable selection and LLM summarization are well‑described, but the linear basis assumption and threshold choices may not generalize without tuning.
- **Multi‑turn tree‑structured diagnosis:** Medium‑Low. The mechanism heavily depends on the LLM’s reasoning and tool‑calling reliability, which vary across models and are not extensively validated in the paper.
- **Human‑in‑the‑loop refinement:** Medium. The feedback loop is conceptually sound, but the paper provides no empirical evidence of improvement over time or expert consistency.

3.  **Cross‑model reasoning replication:** Run the full pipeline on the same test cases using (a) a non‑reasoning model (e.g., Llama‑3.1‑8B) and (b) a reasoning model (e.g., DeepSeek‑R1, o1‑mini). Compare accuracy, average number of tool calls, and rate of premature `<uncertain>` outputs to verify the claimed superiority of reasoning LLMs.
