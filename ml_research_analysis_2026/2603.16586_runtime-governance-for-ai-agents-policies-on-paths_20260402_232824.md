# Runtime Governance for AI Agents: Policies on Paths

## Quick Facts
- **ArXiv ID:** 2603.16586
- **Source URL:** https://arxiv.org/abs/2603.16586
- **Reference count:** 5
- **Primary result:** Runtime path evaluation is necessary for sequence-dependent policies; prompts and static access control are special cases that cannot enforce such constraints.

## Executive Summary
AI agents exhibit non-deterministic, multi-step behaviors where policy violations can depend on the sequence of actions taken. Traditional governance mechanisms like prompts and static access control lack the context of the execution path and thus cannot enforce such sequence-dependent constraints. This paper introduces a formal framework for runtime governance where compliance policies are expressed as deterministic functions that map the agent's identity, its partial execution path, the proposed action, and shared organizational state to a violation probability. A Policy Engine intercepts each proposed action, evaluates these policies, and intervenes (pass, steer, block) to ensure the expected aggregate violation across the agent fleet remains within a predefined risk budget. The authors prove that existing methods are special cases (non-enforcing or path-ignoring) of their framework, demonstrating the necessity of path-dependent evaluation. The framework is instantiated with examples inspired by the EU AI Act and a reference implementation, laying the groundwork for auditable and enforceable agent governance.

## Method Summary
The core method is a runtime Policy Engine that enforces path-dependent compliance policies for AI agents. At task deployment, the engine evaluates registration policies that depend only on agent identity. During execution, for each proposed action, the engine receives the agent's partial execution path, the proposed action, and shared organizational state. It updates a governance state vector (a compact summary of the path relevant to policies) and evaluates all active policy functions π_j, each outputting a violation probability. The per-step violation score v_i is computed as the probabilistic union: v_i = 1 - ∏(1-π_j). A decision function δ then determines whether to pass, steer, or block the action, calibrated to keep the expected sum of terminal violation scores across the fleet within a risk budget B. The framework formalizes the trade-off between utility and compliance as a constrained optimization problem.

## Key Results
- Existing governance approaches (prompts, access control) are proven to be special cases that cannot enforce sequence-dependent constraints, establishing the necessity of runtime path evaluation.
- The policy function formalism and probabilistic union composition enable auditable, enforceable governance with a clear trade-off between task utility and risk via a fleet-level budget.
- The framework is instantiated with EU AI Act-inspired examples and a reference implementation, demonstrating feasibility.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Governance of AI agents requires evaluating each proposed action against the full partial execution path to enforce sequence-dependent constraints.
- **Mechanism:** A deterministic policy function π_j maps (agent identity A, partial path P^i, proposed action s^*, shared state Σ) to a violation probability in [0,1]. This allows preemptive intervention before the action executes.
- **Core assumption:** Policy functions are deterministic and can be evaluated at runtime with sufficient context from P^i and Σ.
- **Evidence anchors:**
  - [abstract] "compliance policies as deterministic functions mapping agent identity, partial execution path, proposed action, and shared state to a violation probability"
  - [section 3.2] Formal definition of π_j and its inputs.
  - [corpus] Limited direct evidence; neighboring papers (e.g., "Governance-as-a-Service") propose runtime enforcement but focus on content-level, not path-dependent, checks.
- **Break condition:** If P^i does not capture governance-relevant steps (e.g., sub-step actions within generated code) or Σ is incomplete, path-dependent violations may be missed.

### Mechanism 2
- **Claim:** The step-level violation score v_i is computed as the probabilistic union of all policy outputs: v_i = 1 - ∏(1-π_j), not a sum.
- **Mechanism:** This composition rule correctly aggregates independent policy probabilities without double-counting, ensuring v_i ∈ [0,1] regardless of policy count.
- **Core assumption:** Policy violation events are conditionally independent given (A, P^i, s^*, Σ); the product gives the probability of at least one violation.
- **Evidence anchors:**
  - [section 3.3] "v_i = 1 - ∏_{j∈J}(1-π_j(...))"
  - [abstract] Mentions combining policy outputs but does not specify the formula.
  - [corpus] No explicit mention in neighbors; most frameworks aggregate via thresholds or voting, not probabilistic union.
- **Break condition:** If policies are correlated (e.g., two policies triggered by the same underlying risk), the product rule may under- or over-estimate the true violation probability.

### Mechanism 3
- **Claim:** The governance objective is a constrained optimization: maximize expected task utility across the fleet while bounding expected terminal violation score E[∑ v_T] ≤ B.
- **Mechanism:** This formalizes the trade-off between productivity and risk; δ (the decision function) calibrates interventions to keep aggregate violations within budget B.
- **Core assumption:** Organizations can quantify task utility u(P) and set a risk budget B meaningful for regulatory exposure.
- **Evidence anchors:**
  - [abstract] "striking the right balance between as high as possible successful task completion rate and the legal, data-breach, reputational and other costs"
  - [section 3.3] Full constrained optimization formulation with E[∑ v_T] ≤ B.
  - [corpus] Neighbors (e.g., "Policy Cards") mention compliance but not fleet-level risk budgeting; evidence is indirect.
- **Break condition:** If u(P) or v_T cannot be measured/calibrated in practice, the objective cannot be monitored or optimized.

## Foundational Learning
**Concept: Execution Path (P)**
- Why needed here: The sequence of agent steps is the central object governance evaluates; violations depend on prior steps, not just the current action.
- Quick check: "Can you determine if an email action violates policy without knowing what data the agent accessed earlier?"

**Concept: Policy Function (π_j)**
- Why needed here: Encodes organizational rules as a deterministic, auditable map from execution context to violation probability; differentiates enforcement from mere shaping (like prompting).
- Quick check: "What distinguishes a policy function from a system prompt in terms of enforceability?"

**Concept: Shared Governance State (Σ)**
- Why needed here: Captures cross-agent context (e.g., which agents accessed sensitive data) needed for organizational constraints like information barriers that cannot be judged from a single agent's path.
- Quick check: "Why can't an agent's individual path alone enforce a constraint that spans multiple agents?"

## Architecture Onboarding
### Component Map
The system consists of: Agents that generate execution paths; a Policy Engine that intercepts actions, evaluates policies, and decides pass/steer/block; a Shared State Store that holds the shared governance state Σ; an Audit Trail that logs all evaluations; and a Registration Module for pre-task agent checks. The Policy Engine interacts with all other components: it receives proposed actions from Agents, reads/writes Σ from/to the Shared State Store, writes logs to the Audit Trail, and uses the Registration Module at task start.

### Critical Path
Task start → Registration Module checks agent identity → For each step: agent proposes action → Policy Engine retrieves current Σ and partial path P^i → evaluates all π_j → computes violation score v_i → applies decision function δ (pass/steer/block) → if continue, agent executes step and updates Σ and P^i → repeats until terminal state.

### Design Tradeoffs
- **Prospective vs. retrospective:** Prospective interception (pre-execution) enables prevention but requires full control over the agent environment; retrospective (post-execution logs) only detects violations after the fact.
- **Step granularity:** Finer granularity (e.g., intercepting every LLM token) catches more violations but increases overhead; coarser granularity (e.g., only tool calls) reduces overhead but may miss sub-step violations.
- **Centralized vs. distributed Policy Engine:** Centralized ensures consistent Σ and global policies but adds latency; distributed reduces latency but risks inconsistency in Σ and policy application.

### Failure Signatures
- **Fail-open:** Policy Engine unavailable or misconfigured leads to unmonitored execution, bypassing all governance.
- **State race conditions:** Concurrent updates to Σ by multiple agents can lead to missed barrier violations or false positives under eventual consistency.
- **Policy interaction overload:** Many low-scoring policies may combine via the product rule to push v_i above threshold on benign actions, causing over-blocking.
- **Uncalibrated δ:** If decision thresholds are not tuned to the risk budget B, the system may either block too many useful actions (hurting utility) or allow too many violations (exceeding budget).

### First 3 Experiments
1. Deploy a single path-dependent policy (e.g., "require approval before external send after PII access") in flag-only mode across a sample of agents to measure baseline violation rate without blocking.
2. Benchmark per-step evaluation latency against LLM inference time to ensure overhead is negligible; test with policy sets of increasing size.
3. Stress-test Σ consistency by running two agents concurrently under an information barrier policy, inducing deliberate cross-barrier data accesses, and verify all violations are logged.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How to calibrate π_j outputs to true violation probabilities?
- **Basis in paper:** Sec 6.1: risk calibration open; outputs are severity, not probabilities.
- **Why unresolved:** Needs labeled traces and violation definitions, lacking.
- **What evidence would resolve it:** Dataset of annotated paths; show score-violation correlation; threshold methods for risk budget.

### Open Question 2
- **Question:** Can agents circumvent governance by planning low-score paths to prohibited outcomes?
- **Basis in paper:** Sec 6.1: strategic circumvention open; assumption agents don't model governance may fail.
- **Why unresolved:** π_j only evaluates immediate action, not future trajectory.
- **What evidence would resolve it:** Agents with score access incentivized to evade; circumvention success metrics; multi-step lookahead extension.

### Open Question 3
- **Question:** Does prospective interception hold when agents execute arbitrary code and bypass the Policy Engine?
- **Basis in paper:** Sec 6.1: completeness problem; code execution can bypass enforced compliance.
- **Why unresolved:** Architectural assumption may be broken; generated code actions invisible.
- **What evidence would resolve it:** Formal model proving interception under sandboxing; or runtime instrumentation of code execution.

## Limitations
- The governance state vector design is underspecified; how to derive a sufficient statistic from arbitrary execution paths for complex cross-agent policies remains unknown.
- Calibration of the decision function `δ` to achieve the fleet-level risk budget lacks operational details, including threshold mapping and utility measurement.
- The concurrency model and consistency guarantees for shared state `Σ` in multi-agent scenarios are not defined.

## Confidence
- **Path-dependent evaluation necessity (Mechanism 1): High**
- **Probabilistic union composition (Mechanism 2): Medium**
- **Fleet-level risk budgeting (Mechanism 3): Medium-Low**

## Next Checks
1. **Path-dependence proof:** Implement a minimal simulator with two policies (e.g., `PiiPredecessorPolicy`) and verify that blocking occurs only when the sequence condition in the path is met, not on isolated actions.
2. **State vector sufficiency test:** For a complex barrier policy, compare policy outputs when using the proposed `GovernanceStateVector` vs. the full raw `partial_path`. Any discrepancy indicates an underspecified vector.
3. **Concurrent `Σ` integrity stress test:** Run two agents under an information barrier policy with concurrent external send actions. Log all `Σ` reads/writes; check for missed violations due to race conditions. If violations are missed, a stronger consistency model is required.
