# Measuring AI Agents' Progress on Multi-Step Cyber Attack Scenarios

## Quick Facts
- **arXiv ID**: 2603.11214
- **Source URL**: https://arxiv.org/abs/2603.11214
- **Reference count**: 40
- **Primary result**: Frontier AI models show log-linear scaling in autonomous cyber-attack capabilities with inference-time compute, achieving up to 22/32 steps on a multi-step corporate compromise scenario.

## Executive Summary
This paper presents the first systematic evaluation of frontier AI models' autonomous cyber-attack capabilities on multi-step attack scenarios, moving beyond isolated CTF benchmarks. The authors construct two custom cyber ranges representing a 32-step corporate network compromise and a 7-step industrial control system disruption. Using a ReAct agent equipped with Kali Linux tools, they evaluate seven models (GPT-4o to GPT 5.3 Codex, Claude Opus 4.6) across token budgets from 10M to 100M. Findings reveal that performance scales log-linearly with increased inference-time compute, with newer models showing substantial improvements. The best run completed 22 of 32 steps (~6 of 14 human-expert hours) on the corporate range, while the industrial range remains difficult (max 3/7 steps). Performance drops sharply after steps requiring reverse engineering or cryptography, and runs exhibit high variance.

## Method Summary
The evaluation employs a ReAct agent scaffold that cycles through reasoning, action execution (Bash, Python, Mythic C2 commands), and observation within simulated Kali Linux environments. To handle long horizons, the agent uses context compaction: when token usage nears the model's context window limit, it summarizes key findings (credentials, network topology) and resets the context with the summary. Two proprietary cyber ranges—"The Last Ones" (32 steps) and "Cooling Tower" (7 steps)—simulate realistic attack chains with verifiable flags. Evaluations are run via the Inspect AI framework across seven frontier models and two token budgets (10M, 100M), with multiple attempts per configuration. The primary metric is the number of steps completed per attempt, supplemented by token efficiency and per-step success rates. No active defenders or detection penalties are present, focusing purely on autonomous progression.

## Key Results
- Performance scales log-linearly with inference-time compute: increasing tokens from 10M to 100M yields up to 59% improvement without observed plateau.
- Newer models significantly outperform older ones: average completed steps at 10M tokens rose from 1.7 (GPT-4o) to 9.8 (Claude Opus 4.6) on the corporate range.
- The best single run (Opus 4.6 at 100M tokens) completed 22/32 steps (~6 of 14 human-expert hours); the industrial range remains difficult (best average 1.4/7, max 3).

## Why This Works (Mechanism)
The ReAct agent's success stems from its iterative reasoning-action cycle, which allows dynamic adaptation to the environment. Context compaction mitigates the fixed context window limitation by preserving essential state across long sequences. The use of Kali Linux tools provides a comprehensive arsenal for common cyber tasks (reconnaissance, exploitation, lateral movement). Performance scaling with compute likely reflects improved reasoning and planning capabilities in larger models, enabling better long-horizon decision-making. However, sharp drops after steps requiring reverse engineering or cryptography indicate inherent limitations in current models' ability to perform complex code analysis or cryptographic operations without specialized tools or fine-tuning.

## Foundational Learning
- **ReAct Agent Framework**: Combines reasoning and acting in a loop to translate goals into commands. *Why needed*: Enables adaptive plan execution. *Quick check*: Does the agent adjust actions based on observations?
- **Context Compaction**: Summarizes history to stay within context limits. *Why needed*: Maintains coherence over millions of tokens. *Quick check*: Are critical details preserved after summarization?
- **Cyber Ranges**: Simulated networks with predefined vulnerabilities. *Why needed*: Provide reproducible, realistic attack scenarios. *Quick check*: Are attack chains sufficiently long and sequential?
- **Token Budgeting**: Allocates inference-time compute. *Why needed*: Probes scaling relationship between resources and performance. *Quick check*: Does increasing tokens consistently improve step completion?
- **Kali Linux Tool Integration**: Access to standard penetration testing tools. *Why needed*: Enables concrete execution of cyber actions. *Quick check*: Does the agent select appropriate tools for each sub-task?
- **Mythic C2**: Command-and-control framework for advanced post-exploitation. *Why needed*: Supports persistence and lateral movement in complex environments. *Quick check*: Can the agent use C2 effectively?

## Architecture Onboarding
**Component Map**  
Model -> ReAct Loop -> Tool Executor -> Cyber Range -> Observation -> Model (loop)  
(Plus: Context Compaction module triggered when token threshold reached)

**Critical Path**  
Initial foothold -> reconnaissance -> privilege escalation -> lateral movement -> data exfiltration/impact -> flag capture. The agent must sequence actions correctly, recover from errors, and manage context.

**Design Tradeoffs**  
- Token budget vs. performance: higher budgets allow deeper exploration but increase cost; scaling appears log-linear without plateau.
- Context management vs. information loss: compaction prevents overflow but may drop subtle details crucial for later steps.
- Generality vs. specialization: generic Kali tools cover many scenarios but lack specialized reverse engineering/cryptography capabilities.

**Failure Signatures**  
- Repetitive loops: agent repeats same failed commands without adaptation.
- Premature context compaction: summarization discards key information, causing loss of progress.
- Stalls after specific step types: consistent failure at reverse engineering or cryptography steps suggests skill gaps.
- High variance between runs: same model and budget yield widely different step counts, indicating sensitivity to initial decisions or randomness.

**First Three Experiments**  
1. Baseline replication: run the ReAct agent on the corporate range with 10M tokens for all seven models to confirm the reported step-completion hierarchy.
2. Scaling test: for the best model (Opus 4.6), vary token budgets (10M, 50M, 100M) to verify log-linear scaling and identify any plateau points.
3. Ablation of context compaction: disable summarization and run with a fixed context window to measure impact on long-horizon performance (expected drop due to overflow).

## Open Questions the Paper Calls Out
The paper does not explicitly identify open questions for future work. However, the authors note that the industrial control system range remains extremely challenging, suggesting a need for improved agent designs or specialized tools for that domain.

## Limitations
- Exact cyber range specifications (network topology, vulnerabilities, flag definitions) are proprietary, preventing exact replication.
- Agent implementation details (prompts, tool schemas, failure-recovery heuristics) are not disclosed, making it unclear how much performance depends on scaffold design vs. intrinsic model capability.
- The industrial range shows near-floor performance; it is uncertain whether this reflects a true capability ceiling or an improperly calibrated scenario.

## Confidence
- **Log-linear scaling with compute**: High (consistent trends across models and budgets).
- **Performance progression across model versions**: High (clear improvements at fixed token budgets).
- **"Human-equivalent hours" estimate**: Medium (plausible extrapolation but depends on unverified assumptions about human efficiency).
- **Reverse-engineering/cryptography as a hard barrier**: Low (based on aggregate data; not isolated via controlled ablations).

## Next Checks
1. Re-run the agent on public multi-step cyber benchmarks (e.g., Cobalt Strike red team exercises) to test generalizability of scaling laws.
2. Perform qualitative log analysis of high-variance runs to classify stall causes (reasoning dead-ends, context failure, environment blind spots).
3. Isolate reverse-engineering/cryptography steps: modify the corporate range to provide correct outputs for those sub-tasks and measure impact on overall completion.
