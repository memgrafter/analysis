# RECOVER: Robust Entity Correction via agentic Orchestration of hypothesis Variants for Evidence-based Recovery

## Quick Facts
- **arXiv ID**: 2603.16411
- **Source URL**: https://arxiv.org/abs/2603.16411
- **Reference count**: 0
- **Primary result**: RECOVER reduces entity-phrase word error rate (E-WER) by 8–46% relative and improves entity recall by up to +22 percentage points across five datasets, without degrading overall WER.

## Executive Summary
RECOVER is a post-ASR correction system designed to fix errors on rare or domain-specific entity phrases. It consumes multiple ASR hypotheses from Whisper (via temperature sampling), dynamically retrieves a list of candidate entity phrases using exact, fuzzy, and phonetic matching, and then orchestrates three tools: hypothesis fusion, constrained LLM-based edit proposal, and deterministic verification/application. The system operates without any training. Across five datasets, RECOVER achieves significant relative reductions in entity WER and large gains in entity recall. The LLM-Select fusion strategy consistently delivers the best trade‑off, improving entity F1 while preserving the overall WER, with most gains coming from eliminating substitution errors.

## Method Summary
For each audio segment, RECOVER first generates five transcript hypotheses using Whisper‑small with temperatures {0.0, 0.2, 0.4, 0.6, 0.8}. These hypotheses are concatenated and scored against a precompiled list of entity phrases using a weighted combination: exact word matches (n_exact), best fuzzy similarity (f_best), and a phonetic prefix hit (p_hit). The top‑K (200) candidate entities are retrieved. Next, one of four fusion strategies produces a base transcript: 1‑Best (T=0.0), Entity‑Aware Select (hypothesis with most exact entity matches), ROVER Ensemble (entity‑aware pivot alignment and majority vote), or LLM‑Select (LLM chooses the best hypothesis and proposes corrections in a single call). Tool 2 then prompts the LLM (GPT‑4o) to propose only find/replace edits where the replacement string exactly matches an entity phrase. The edits are passed to Tool 3, which applies deterministic guardrails: ensure replacements are in the entity list, avoid case‑only changes, correct offsets if needed, enforce high Levenshtein similarity between original and replacement, and apply edits left‑to‑right without overlap. The pipeline is orchestrated sequentially, yielding the final corrected transcript.

## Key Results
- 8–46% relative reduction in entity‑phrase WER (E‑WER)
- Up to +22 percentage points improvement in entity recall
- LLM‑Select is the most consistent strategy, improving entity F1 while preserving overall WER
- Substitution error reduction accounts for 63–93% of total E‑WER improvement

## Why This Works (Mechanism)
RECOVER’s effectiveness stems from exploiting complementary information across multiple ASR hypotheses. Single‑best ASR outputs often miss or corrupt rare entities; sampling diverse hypotheses increases the chance that some contain the correct entity spelling. Dynamic candidate retrieval efficiently narrows down the vast entity vocabulary to a manageable set of plausible matches per segment, using exact, fuzzy, and phonetic signals to cover common ASR error types. Constrained LLM editing focuses the language model on a limited, high‑precision correction task, preventing hallucination and ensuring all proposed changes are domain‑specific entities. The verification guardrails further enforce correctness and resolve offset ambiguities. By separating hypothesis fusion (which reduces insertion/deletion noise) from correction proposal (which targets substitutions), the system systematically addresses the dominant error types for entities. The orchestration ensures each step builds on evidence from the previous, leading to robust recovery even when the 1‑best output is severely corrupted.

## Foundational Learning

**Concept 1: ASR Hypothesis Diversity**  
*Why needed*: Different sampling temperatures or decoding strategies produce varied transcript errors; exploiting multiple hypotheses can recover correct terms missing in the 1‑best output.  
*Quick check*: For a set of audio segments, compute the oracle WER (best among N hypotheses) vs. 1‑best WER; a significant gap indicates potential benefit from multi‑hypothesis fusion.

**Concept 2: Entity‑Centric Candidate Retrieval**  
*Why needed*: Domain‑specific entity vocabularies can be large (thousands of phrases); exhaustive search is infeasible. Scoring with exact, fuzzy, and phonetic matching quickly identifies a small high‑probability set.  
*Quick check*: For a random segment, measure recall of the true entity phrase within top‑K candidates for varying K; choose K where recall plateaus.

**Concept 3: Constrained LLM Editing**  
*Why needed*: Free‑form LLM correction risks introducing errors or changing non‑entity text. Restricting the LLM to propose only replacements that exactly match the entity list keeps corrections grounded.  
*Quick check*: Run the LLM on a sample segment without guardrails and tally proposals that are not in the entity list; the constrained prompt should reduce this to near zero.

**Concept 4: Deterministic Verification Guardrails**  
*Why needed*: LLM outputs can contain offset errors or subtle mismatches; guardrails ensure only valid edits are applied, maintaining system integrity.  
*Quick check*: After verification, log the number and type of rejected edits (e.g., case‑only, similarity too low). A well‑tuned system should reject very few valid edits.

**Concept 5: Agentic Orchestration**  
*Why needed*: Complex pipelines require clear sequencing and state management; an agent framework (e.g., Agno) coordinates tools and handles failures gracefully.  
*Quick check*: Simulate a tool failure (e.g., empty candidate list) and verify the orchestration either aborts cleanly or falls back to a safe default (e.g., 1‑Best unchanged).

**Concept 6: ROVER Ensemble for Token Consensus**  
*Why needed*: Merging multiple hypothesis sequences can reduce random errors by majority vote, improving the base transcript quality before correction.  
*Quick check*: Compare the WER of ROVER output against individual hypotheses on a clean subset; expect ROVER to be equal or better.

## Architecture Onboarding

**Component Map**  
Audio -> Whisper (5 hypotheses) -> Candidate Retrieval -> [Fusion Tool] -> [LLM Propose] -> [Verify & Apply] -> Corrected Transcript

**Critical Path**
1. Generate five transcripts at varying temperatures.
2. Concatenate tokens and score all entity phrases; take top‑200.
3. Fuse hypotheses into a single base transcript using selected strategy.
4. Prompt LLM to propose entity‑only edits; output JSON.
5. Apply guardrails and sequentially apply valid edits to base.
6. Output final corrected transcript.

**Design Tradeoffs**
- *Number of hypotheses*: More hypotheses increase coverage but add computation and fusion complexity; 5 is a practical sweet spot.
- *LLM vs. deterministic*: Using an LLM introduces latency and cost but provides semantic understanding; constrained editing mitigates risks.
- *ROVER vs. selection*: ROVER can reduce noise but may introduce insertions/deletions; selection strategies (1‑Best, Entity‑Aware, LLM‑Select) preserve original word order and are safer for noisy data.
- *Candidate retrieval K*: Larger K increases recall of true entities at the cost of more LLM proposals (and possible rejections); tuning needed per dataset.

**Failure Signatures**
- High guardrail rejection rate (>30%): indicates LLM proposes too many invalid or low‑similarity edits; prompt needs tightening or candidate set too noisy.
- Overall WER increase with ROVER: likely due to insertion errors in non‑entity regions; analyze token‑level edit distance.
- Low entity coverage in top‑K candidates (<80%): retrieval scoring weights or phonetic matching may be misconfigured; adjust weights or K.
- LLM‑Select underperforms: may be due to ambiguous hypothesis presentation; ensure hypotheses are clearly separated and entity list is included.

**First Three Experiments**
1. **Baseline comparison**: Implement the pipeline with 1‑Best fusion and GPT‑4o as LLM. Report E‑WER and F1 against the baseline (no correction) to confirm improvement.
2. **Strategy evaluation**: Add Entity‑Aware Select, ROVER, and LLM‑Select. Compare their relative E‑WER reductions and overall WER impacts across datasets.
3. **Candidate retrieval sensitivity**: Vary K (100, 200, 500) and measure entity recall in top‑K and final E‑WER to find optimal trade‑off.

## Open Questions the Paper Calls Out

1. **Adaptive strategy selection per segment**  
   *Question*: Can we adaptively choose the best fusion strategy (1‑Best, Entity‑Aware Select, ROVER Ensemble, LLM‑Select) per segment using inter‑hypothesis agreement?  
   *Basis*: Future work will explore adaptive per‑segment strategy selection based on inter‑hypothesis agreement.  
   *Why unresolved*: All strategies are applied uniformly; no adaptation explored.  
   *What evidence would resolve*: Measure agreement (e.g., hypothesis pair edit distances) per segment, find correlation with strategy E‑WER, implement adaptive selector, evaluate improvement.

2. **Integration of ASR confidence scores**  
   *Question*: Does integrating word‑level ASR confidence scores into RECOVER improve entity correction, especially in low‑confidence regions?  
   *Basis*: Integration with word‑level ASR confidence scores is mentioned in Conclusions.  
   *Why unresolved*: The pipeline uses only transcript hypotheses and ignores ASR confidence.  
   *Evidence*: Add Whisper word confidence as features in candidate retrieval or verification; compare entity metrics with/without confidence on all datasets.

3. **Alternative LLM evaluations**  
   *Question*: How do alternative LLMs (open‑source or other commercial) compare to GPT‑4o in the constrained editing task?  
   *Basis*: Comparison with more LLMs is noted.  
   *Why unresolved*: Only GPT‑4o and GPT‑4o‑mini are evaluated.  
   *Evidence*: Replicate LLM‑Select with diverse LLMs (Llama 3.1, Claude 3.5, Gemini 1.5), measure entity F1, E‑WER reduction, and guardrail rejection rates.

4. **Multi‑agent architecture extension**  
   *Question*: Would a multi‑agent architecture, where each tool (fuse, propose, verify) is a separate agent, enhance robustness or flexibility?  
   *Basis*: Extension to multi‑agent architectures is mentioned.  
   *Why unresolved*: Current system uses a single agent orchestrating three deterministic tools; multi‑agent dynamics unstudied.  
   *Evidence*: Implement each tool as an independent agent with its own LLM, allow iterative refinement, compare correction performance and analyze failure cases.

## Limitations
- Exact LLM prompt templates and few‑shot examples for Tool 2 and LLM‑Select are not specified, risking non‑compliant edit proposals.
- ROVER implementation details (Needleman‑Wunsch parameters, tie‑breaking for insertions) are unclear, potentially affecting reproducibility.
- The orchestration in the Agno framework (state passing, error handling) is inferred but undocumented, which may lead to deviation from the intended system.

## Next Checks
1. **Entity coverage audit**: For each dataset, verify that reference entity phrases appear in at least one ASR hypothesis (exact/fuzzy/phonetic). If coverage <95%, consider increasing K or adjusting retrieval weights.
2. **LLM constraint adherence test**: Run Tool 2 on a fixed sample and log all proposed edits; compute the percentage of edits whose replacement phrase is not in the entity list. After guardrails, aim for <5% invalid proposals.
3. **ROVER insertion analysis**: Use SCLITE to measure token‑level insertion rates in non‑entity regions. If ROVER’s overall WER is higher than 1‑Best, confirm that insertions constitute >50% of the WER increase.
