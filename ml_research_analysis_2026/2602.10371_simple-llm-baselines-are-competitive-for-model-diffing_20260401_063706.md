# Simple LLM Baselines are Competitive for Model Diffing

## Quick Facts
- **arXiv ID:** 2602.10371
- **Source URL:** https://arxiv.org/abs/2602.10371
- **Reference count:** 40
- **Primary result:** Simple LLM-based diffing baselines match SAE-based methods in accuracy and interestingness while producing more abstract hypotheses.

## Executive Summary
Model diffing seeks to automatically reveal systematic behavioral differences between large language models. This paper tackles the lack of a systematic comparison for API‑only diffing methods (LLM‑based versus SAE‑based). The authors define three evaluation desiderata—generalization, interestingness, and abstraction—and operationalize them via judge‑verified accuracy/frequency on held‑out data and LLM autoratings. Across three experimental settings (two model organisms and one frontier model revision), an improved LLM‑based baseline matches the SAE‑based method in accuracy and interestingness, yet yields consistently more abstract hypotheses. Both methods achieve comparable hypothesis frequency, while a token‑level KL‑divergence analysis surfaces only low‑level formatting differences. The findings establish simple LLM baselines as a competitive approach and highlight complementary strengths: SAE for fine‑grained patterns, LLM for abstract behavioral shifts.

## Method Summary
The study compares two diffing pipelines using a common dataset of 1,000 WildChat prompts, with a held‑out test set of 500 prompts. The LLM‑based pipeline (adapted from Dunlap et al., 2025) processes each prompt–response triplet `(p, rA, rB)` by extracting difference objects with Gemini 2.5 Flash, embedding them using `llama-embed-nemotron-8b`, reducing dimensionality (PCA to 128, then UMAP to 30), clustering with HDBSCAN, and summarizing each cluster into a concise hypothesis with Gemini 2.5 Flash. Clusters with a dominant model share below 65% are discarded. The SAE‑based pipeline (adapted from Jiang et al., 2025) feeds full `(p, r)` pairs into Llama 3.3 70B equipped with a publicly available SAE trained on layer 50, max‑pools SAE activations over completion tokens, computes activation frequency differences between models, selects the top features (40 in the modified version), collects example activations, relabels features with Gemini, and generates hypotheses followed by a phrasing adjustment step. Evaluation uses a judge (Gemini 2.5 Flash) to produce `J(h, t_i) ∈ {-1,0,1}` on held‑out triplets, yielding frequency `f(h)` and accuracy `acc(h)`. Interestingness and abstraction are autorated by three frontier models (GPT‑5.2, Claude Opus 4.5, Grok‑4) on a 1–5 scale, with scores averaged per hypothesis.

## Key Results
- LLM‑based pipeline matches SAE‑based pipeline in judge‑verified accuracy and interestingness.
- LLM‑based pipeline generates significantly more abstract hypotheses according to autoratings.
- Both pipelines achieve comparable hypothesis frequency; KL‑divergence token analysis yields only low‑level formatting differences.

## Why This Works (Mechanism)
The LLM pipeline operates on semantic embeddings of entire response pairs, capturing high‑level behavioral patterns, while the SAE pipeline relies on fine‑grained internal feature activations. Both effectively cluster systematic differences, but the LLM’s summarization step leverages its innate capacity for abstraction, converting clusters into conceptual descriptions. In contrast, SAE features are often narrow (e.g., specific token usage), limiting abstraction. The comparable accuracy indicates that systematic differences manifest at both semantic and syntactic levels, and each method can detect them when properly aggregated. The KL‑based method, focused on per‑token divergence, fails to capture higher‑level shifts, explaining its lack of abstraction.

## Foundational Learning
- **Model Diffing**: The task of automatically identifying coherent behavioral differences between two LLMs. *Why needed*: To interpret model updates, diagnose failures, and ensure alignment. *Quick check*: What makes a difference “systematic” rather than random?
- **Sparse Autoencoders (SAE)**: A technique that learns a set of interpretable, sparse features from neural activations. *Why needed*: To disentangle internal representations into human‑understandable concepts without relying on model outputs. *Quick check*: How does the sparsity constraint affect the interpretability of SAE features?
- **Embedding‑based Clustering**: Using high‑dimensional vector embeddings of text to group similar instances. *Why needed*: To aggregate many low‑level differences into coherent behavioral clusters. *Quick check*: Why are PCA and UMAP applied before HDBSCAN? What would happen if we clustered raw embeddings directly?
- **LLM‑as‑Judge & Autorater**: Employing large language models to evaluate hypotheses or rate properties. *Why needed*: To scale evaluation without human annotators. *Quick check*: What are the risks of using a single LLM as a judge, and how does the paper attempt to mitigate them?

## Architecture Onboarding
**Component Map**
LLM‑based pipeline:  
Prompt Dataset → Generate responses (Model A & B) → Difference Extraction (Gemini 2.5 Flash) → Embedding (llama‑embed‑nemotron‑8b) → PCA (128) → UMAP (30) → HDBSCAN Clustering → Hypothesis Generation (Gemini) → Direction Assignment (>65% majority) → Hypotheses  

SAE‑based pipeline:  
Prompt Dataset → Generate responses per model → Reader Forward (Llama 3.3 70B + SAE at layer 50) → SAE Activation Extraction → Max‑pool (completion tokens) → Feature Vectors → Compute Activation Difference → Select Top Features (e.g., 40) → Collect Positive/Negative Examples → Feature Relabeling (Gemini) → Hypothesis Generation (Gemini) → Phrasing Adjustment (Gemini) → Hypotheses  

Evaluation (shared):  
Hypotheses + Held‑out Test Triplets → Judge Scoring (Gemini 2.5 Flash) → Frequency & Accuracy  
Hypotheses → Autorating (GPT‑5.2, Claude Opus 4.5, Grok‑4) → Interestingness & Abstraction scores  

**Critical Path**  
LLM pipeline: (1) collect prompts; (2) generate paired responses; (3) extract differences; (4) embed & reduce; (5) cluster; (6) summarize hypotheses; (7) assign direction.  
SAE pipeline: (1) collect prompts; (2) generate responses; (3) forward reader; (4) extract & pool SAE activations; (5) compute feature differences; (6) select top features; (7) gather examples & relabel; (8) generate hypotheses. The judge step is critical for metric computation.

**Design Tradeoffs**  
- Representation: LLM embeddings capture semantic similarity but may miss precise token patterns; SAE features capture exact activations but are often too fine‑grained for abstract hypotheses.  
- Clustering vs. selection: HDBSCAN yields coherent groups but depends on hyperparameters; SAE feature selection is deterministic but may produce many redundant hypotheses.  
- Evaluation: Using a single judge reduces cost but introduces bias; ensemble autorating improves reliability but is expensive.  
- API‑only constraint: Both pipelines lack weight‑level access, potentially missing hidden behaviors that require targeted prompting.

**Failure Signatures**  
- Low acceptance rate on hypothesis‑generation data (e.g., <20%) indicates poor clustering or weak differences.  
- High variance in autorated abstraction scores across frontier models suggests subjectivity.  
- Judge disagreement on symmetric or near‑identical inputs undermines metric validity.  
- SAE hypotheses about low‑level formatting (e.g., pipe characters) signal semantically uninterpretable features.

**First Experiments**  
1. *Smoke Test LLM Pipeline*: Run the LLM pipeline on 20 prompts for one model pair (e.g., Qwen‑2.5‑7B vs. fine‑tuned). Verify at least one hypothesis and judge acceptance rate >0.  
2. *Judge Consistency Check*: For 50 random hypothesis–test‑triplet pairs, run the judge twice (or with swapped responses) and compute agreement; expect >80%.  
3. *Metric Reproduction*: On the full held‑out set (500 prompts), compute average accuracy and frequency for both pipelines and compare to paper’s reported means (e.g., LLM accuracy ~0.78, SAE ~0.76) to validate implementation.

## Open Questions
### Open Question 1
- **Question:** How can prompt design and dataset curation be systematically optimized to increase the sensitivity of API‑only model diffing for detecting subtle, implicit behavioral differences (e.g., hidden assumptions) that may not consistently manifest in free‑form outputs?
- **Basis in paper:** [explicit] The failure to detect the Gemma model's hidden gender assumption, despite confirming the behavior exists via targeted examples (Appendix D). The authors state: "curating a prompt set specifically targeted at eliciting gender assumptions may still allow API‑only model diffing methods to detect this difference. This highlights both a limitation and an avenue for future work: prompt selection substantially affects what behaviors can be surfaced."
- **Why unresolved:** The paper demonstrates that generic, diverse prompt distributions (e.g., WildChat) may miss low‑frequency or context‑dependent behaviors. A principled methodology for generating or selecting prompts that maximize the probability of eliciting a specific latent behavior does not exist.
- **What evidence would resolve it:** Developing and validating a framework for "behavior‑targeted prompt generation" (e.g., using adversarial techniques, behavioral classifiers, or synthetic prompt generation guided by known trigger conditions). Success would be measured by a significant increase in detection rate for a known subtle behavior (like the gender assumption) compared to a random or diverse baseline, while maintaining a low false positive rate.

### Open Question 2
- **Question:** Why do token‑level divergence methods (like KL‑based fork token analysis) and SAE‑based feature detection consistently yield low‑abstraction, syntactic hypotheses, and what architectural or methodological modifications could elevate their output to more abstract, conceptual behavioral descriptions?
- **Basis in paper:** [explicit] The KL‑divergence experiment (Appendix E) and SAE examples (e.g., "pipe (|) and hyphen (-) characters") show results are "primarily low‑level formatting patterns." The authors conclude: "token‑level methods may inherently struggle to produce abstract hypotheses." This is a stated limitation and observation.
- **Why unresolved:** The paper establishes the empirical pattern but does not diagnose the root cause. It is unclear whether the limitation stems from the granularity of the representation (tokens/features), the clustering/summarization pipeline, or the intrinsic nature of the signals these methods capture. Without understanding the cause, improvements are guesswork.
- **What evidence would resolve it:** Ablation studies or theoretical analysis pinpointing whether (a) the signal is fundamentally low‑level (e.g., SAE features are monosemantic at the concept level of "pipe character usage"), (b) the summarization step fails to abstract, or (c) the method discards contextual information needed for abstraction. A successful modification would produce hypotheses with significantly higher abstraction scores (per the paper's autorater) on the same data without sacrificing accuracy/frequency.

### Open Question 3
- **Question:** Can hybrid diffing pipelines that combine SAE‑based feature detection with LLM‑based summarization and contextualization produce hypotheses that are both highly accurate/frequent *and* highly abstract, thereby overcoming the complementary weaknesses identified in each pure approach?
- **Basis in paper:** [explicit] The Outlook explicitly proposes: "Hybrid approaches that combine SAE‑based feature detection with LLM‑based summarization may capture both low‑level and abstract differences." This is a direct, suggested future direction based on the finding of complementary strengths.
- **Why unresolved:** The paper only compares pure methods. No implementation or evaluation of a hybrid exists. Key design questions are open: How to weight/select features? How to provide sufficient SAE activation context to the LLM? How to avoid the LLM overwriting precise feature‑level information?
- **What evidence would resolve it:** Implementing a pipeline where SAE‑extracted features (with their activation examples) are fed as input to the LLM summarization step. The hybrid's hypotheses would need to be evaluated on the paper's framework and show non‑inferiority on accuracy/frequency while exceeding pure SAE on abstraction, and non‑inferiority on abstraction while exceeding pure LLM on frequency/accuracy (addressing the trade‑offs noted in B.4).

### Open Question 4
- **Question:** How reliable are LLM‑based judges and autoraters for evaluating hypothesis quality in model diffing, and what methodologies (e.g., human‑in‑the‑loop calibration, model ensembles, adversarial validation) can mitigate their biases and inconsistencies to produce a more trustworthy evaluation framework?
- **Basis in paper:** [inferred] The paper relies heavily on LLM judges (for hypothesis verification, frequency/accuracy) and LLM autoraters (for interestingness/abstraction). The Limitations state: "Automatic evaluation has inherent limitations: LLM judges can be unreliable." Evidence of unreliability is seen in the gender assumption analysis (Appendix D), where judge models disagree on which model assumes female users, and a single judge model inconsistently classifies near‑identical phrases. This threatens the validity of all reported metrics.
- **Why unresolved:** The paper uses a single judge model (Gemini 2.5 Flash) for core metrics and ensembles three for autorating, but provides no analysis of judge consistency or calibration against ground truth. The observed disagreements (Figure 8, judge inconsistency example) suggest metric noise that could swamp real methodological differences, especially in subtle cases.
- **What evidence would resolve it:** A full meta‑evaluation of the judge/autorater system. This would include: (1) measuring inter‑judge and intra‑judge reliability on a large annotated dataset; (2) correlating LLM‑judge scores with human expert judgments on a subset; (3) testing if judgments are sensitive to prompt order or minor wording changes; (4) developing and validating a more robust evaluation protocol (e.g., majority vote over diverse judges, or a smaller human‑validated core set).

### Open Question 5
- **Question:** Can model diffing methods (both LLM‑ and SAE‑based) reliably surface systematic differences in *reasoning processes* (e.g., chain‑of‑thought strategies, error patterns, faithfulness of intermediate steps) rather than just final‑output stylistic or content differences, and how should such "reasoning diffing" be evaluated?
- **Basis in paper:** [explicit] The Outlook states: "Another promising application is comparing reasoning behavior across models: as chain‑of‑thought reasoning becomes standard in frontier models, diffing methods could surface systematic differences in reasoning strategies, failure modes, or faithfulness of intermediate steps, offering a new lens for evaluating reasoning capabilities beyond final‑answer accuracy." This is presented as a key future direction.
- **Why unresolved:** The current pipeline and evaluation framework are optimized for output‑level behavioral differences. Reasoning differences may manifest temporally within a response, involve logical structure, or require comparing internal states (not just final text). The existing metrics (accuracy on response pairs, abstraction levels rated on final output descriptions) may be ill‑suited. It's unclear if API‑only methods can access sufficient granular information from CoT outputs, or if new hypothesis generation and verification techniques are needed.
- **What evidence would resolve it:** Adapting the diffing pipeline to explicitly parse and compare reasoning traces (e.g., step‑by‑step CoT). Developing new evaluation dimensions: e.g., "reasoning strategy consistency," "step‑level error divergence." Validation would require either (a) model organisms with known reasoning flaws (e.g., systematically skipping a reasoning step) to test detection, or (b) human expert evaluation of whether surfaced hypotheses accurately describe reasoning differences in a diverse set of model comparisons.

## Limitations
- **Judge reliability:** The evaluation relies on a single LLM judge (Gemini 2.5 Flash) which exhibits inconsistency on symmetric inputs, threatening metric validity.
- **Hyperparameter ambiguity:** Critical parameters (e.g., HDBSCAN `min_cluster_size`, SAE top‑feature count, response sampling temperature) are not specified, making exact replication difficult and potentially affecting results.
- **Abstraction metric subjectivity:** The autorating scale for abstraction uses non‑reproducible proprietary models without published rubrics, raising concerns about the validity of the abstraction comparison.

## Confidence
- LLM baselines match SAE in accuracy and interestingness: Medium
- LLM baselines produce more abstract hypotheses: Low
- Token‑level KL methods lack abstraction: High

## Next Checks
1. **Judge calibration multi‑model**: Re‑run core evaluation with multiple independent judges (e.g., Claude, GPT, open‑source LLMs) on a shared subset; compute inter‑rater reliability (Cohen’s κ) to assess robustness.
2. **SAE feature selection sensitivity**: Systematically vary the number of top features (e.g., 10, 20, 40, 100) and recompute metrics to determine if the “comparable frequency” claim holds.
3. **Abstraction metric human validation**: Create a human‑annotated gold standard of hypotheses labeled for abstraction level; measure correlation with autorater scores; low correlation would invalidate the metric.
