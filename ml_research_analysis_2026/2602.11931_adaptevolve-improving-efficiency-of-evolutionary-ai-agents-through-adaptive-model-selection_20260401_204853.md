# AdaptEvolve: Improving Efficiency of Evolutionary AI Agents through Adaptive Model Selection

## Quick Facts
- **arXiv ID:** 2602.11931
- **Source URL:** https://arxiv.org/abs/2602.11931
- **Reference count:** 8
- **Primary result:** Reduces inference cost by 37.9% while retaining 97.5% of the accuracy of a static large-model-only baseline on coding benchmarks.

## Executive Summary
Evolutionary AI agents for code generation repeatedly invoke large language models, creating a significant trade-off between computational cost and reasoning capability. AdaptEvolve addresses this by dynamically selecting between a small (4B) and large (32B) model within an evolutionary framework. It uses intrinsic generation confidence—derived from token entropy metrics—to estimate in real-time whether the small model’s candidate is solvable, routing uncertain cases to the larger model. A lightweight decision tree router, bootstrapped from a minimal warm-up set, enables this selection. Evaluated on LiveCodeBench and MBPP, this approach reduces total compute cost by over one-third while preserving nearly all of the large model’s accuracy, establishing a superior efficiency-accuracy Pareto frontier compared to static or random routing.

## Method Summary
AdaptEvolve integrates a routing mechanism into the mutation operator of an evolutionary coding agent (OpenEvolve). For each candidate mutation, the small model (4B) first generates an output, and a confidence vector is computed from its token log-probabilities. This vector includes Mean Confidence (MC), Lowest Group Confidence (LGC), Tail Confidence (TC), and Bottom-K% Confidence (BWC). A decision tree router, trained on a small warm-up set (N=50) where labels are derived from whether the large model (32B) would solve the problem, maps this vector to a binary decision: retain the small model’s output or regenerate with the large model. An optional Adaptive Hoeffding Tree can be used to update the router online, handling distribution shifts as the evolutionary population converges to harder instances.

## Key Results
- Achieves 97.9% of the upper-bound (32B-only) accuracy on LiveCodeBench with 34.4% less compute.
- Achieves 97.1% of the upper-bound accuracy on MBPP with 41.5% cost reduction.
- Across both benchmarks, reduces total inference cost by an average of 37.9% while retaining 97.5% of the large-model-only accuracy.

## Why This Works (Mechanism)

### Mechanism 1: Uncertainty-Driven Routing via Intrinsic Confidence
Intrinsic generation confidence metrics (token entropy-based) reliably predict whether a small model's candidate solution will be correct, enabling safe escalation to a larger model. For each generation from the small model, a feature vector `C(x_i)` is computed from token-level log-probabilities, including MC, LGC, TC, and BWC. A lightweight decision tree router `Φ` maps this vector to a binary decision. The distribution of these metrics differs systematically between solvable and unsolvable instances, a separability learnable from a small calibration set. Evidence includes the paper's definition of the metrics and their cited correlation with model failure, plus warm-up data showing statistical gaps (Table 3). A break condition occurs if these metrics lose discriminative power as evolution progresses (concept drift), requiring online adaptation.

### Mechanism 2: Bootstrapped & Adaptive Decision Tree Router
A shallow decision tree (max-depth=5), initialized on a minimal warm-up set (N=50), effectively learns the non-linear decision boundary between confidence signatures of solvable/unsolvable generations. An Adaptive Hoeffding Tree variant incrementally updates its structure during deployment, pruning branches when error rates rise to adapt to evolving problem distributions. The paper contrasts static vs. adaptive trees, showing the latter improves accuracy by 2.4 points on LiveCodeBench. The core assumption is that the confidence-solvability relationship is non-linear and non-stationary; a linear threshold fails (pilot study, Table 4). A break condition is abrupt or fundamental feature-space changes causing lag in incremental updates.

### Mechanism 3: Integration into Evolutionary Mutation Operator
Conditioning the mutation operator on the router's decision transforms fixed-model evolution into a cost-aware process where expensive large-model calls are reserved for steps where the small model exhibits high uncertainty. The standard mutation `x'_i = M(x_i)` becomes `x'_i = MS(x_i)` if `Φ(C(x_i)) = 1`, else `x'_i = ML(x_i)`. This dynamically allocates computational resources per generation step. A break condition arises if the small model's single-step confidence does not predict the final selected solution's correctness due to population-level selection or later mutations.

## Architecture Onboarding
Confidence Calculator -> Router -> Warm-up Module -> Evolutionary Loop -> Online Adaptation

Critical path: During a mutation step for candidate `x_i`: (a) Generate with `MS`, log token probs. (b) Compute `C(x_i)`. (c) Query Router `Φ(C(x_i))`. (d) If route=1, keep `MS(x_i)`; if route=0, regenerate `x_i` with `ML`. (e) New candidate enters population. The warm-up path runs (a-d) on the calibration set to train `Φ`.

Design tradeoffs:
- Router Complexity vs. Inference Cost: A deeper tree may capture more non-linearities but adds negligible traversal cost; tradeoff is in training/update complexity.
- Warm-up Size (N=50) vs. Generalization: A tiny warm-up risks overfitting to a narrow distribution; assumes initial stability for search to begin.
- Static vs. Adaptive Router: Static tree is simpler and stable; Adaptive HAT adds complexity (monitoring, splitting) but handles long-run distribution shifts.

Failure signatures:
- **High cost, low accuracy gain:** Router over-escalates (frequently chooses L when S would solve). Check if confidence thresholds are too conservative.
- **Accuracy drop vs. upper-bound:** Router under-escalates (chooses S when L is needed). Likely due to concept drift; static tree obsolete. Switch to HAT.
- **Router instability (flapping):** HAT too sensitive to noise, constantly restructuring. Adjust drift detection parameters or increase minimum samples per leaf.

First 3 experiments:
1. Validate Confidence Separability: On the warm-up set (N=50), plot distributions of LGC, MC, etc., for solved vs. unsolved instances (as in Table 3). Confirm statistical gaps exist.
2. Router Ablation (Static): Run evolution with a *random* router (fixed S:L ratio) vs. the *trained* static decision tree router. Measure accuracy and cost; trained router must show superior Efficiency (Acc/Cost).
3. Adaptation Benefit: Run a long evolutionary process (e.g., 50+ generations) comparing static decision tree vs. Adaptive Hoeffding Tree. Track routing ratios over time; HAT should show stable or improving accuracy as static tree's performance decays.

## Open Questions the Paper Calls Out
- How can AdaptEvolve be extended to closed-source large language models that do not provide token-level log-probabilities? The limitations section explicitly states this restricts applicability to open-weight models or APIs exposing logprobs.
- What is the optimal size for the warm-up set used to bootstrap the decision tree router, and does it vary across problem domains? The methodology uses a fixed N=50 without analyzing sensitivity.
- Does confidence-driven model selection generalize effectively to non-coding reasoning tasks, such as mathematical problem-solving or natural language inference? Evaluation is limited to coding benchmarks (LiveCodeBench, MBPP).
- How do alternative intrinsic uncertainty signals (beyond token entropy) compare in effectiveness for routing decisions in evolutionary agents? The paper exclusively uses four token-based entropy metrics without evaluating other approaches.

## Limitations
- Warm-up sampling strategy (random vs. stratified, class balance) is unspecified; results may be sensitive to the 50-sample set's composition.
- Adaptive Hoeffding Tree hyperparameters (grace period, split confidence) are not disclosed, hindering exact replication of online adaptation behavior.
- The approach requires token-level log-probabilities, which are unavailable from many proprietary LLM APIs, limiting applicability.
