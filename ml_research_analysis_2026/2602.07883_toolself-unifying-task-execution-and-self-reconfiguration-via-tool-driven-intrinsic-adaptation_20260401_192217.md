# ToolSelf: Unifying Task Execution and Self-Reconfiguration via Tool-Driven Intrinsic Adaptation

## Quick Facts
- **arXiv ID**: 2602.07883  
- **Source URL**: https://arxiv.org/abs/2602.07883  
- **Reference count**: 40  
- **Primary result**: ToolSelf unifies task execution and self-reconfiguration by treating configuration updates as a callable tool, enabling autonomous adaptation. With Configuration-Aware Two-stage Training (CAT), it achieves a 24.1% average performance improvement on FRAMES, xbench, GAIA, and SWE-bench Lite, matching expert workflows.

## Executive Summary
Long-horizon tasks challenge static LLM agent configurations, leading to context overflow and strategy rigidity. ToolSelf addresses this by modeling configuration updates—sub-goals, strategy, toolbox, and context—as a first-class tool (`Treconfig`) within the agent's action space. This unifies execution and self-reconfiguration, allowing the agent to intrinsically decide when and how to adapt. The system employs an inference-reconfiguration loop that resets local context after each stage while distilling key knowledge into a global knowledge pool. Training uses a two-stage CAT pipeline: rejection sampling fine-tuning (RFT) from teacher trajectories, followed by trajectory-level Kahneman-Tversky Optimization (KTO) to align both the inference agent and reconfiguration engine. Across four benchmarks, ToolSelf demonstrates robust generalization and significant gains over strong baselines.

## Method Summary
ToolSelf introduces a unified action space where the agent invokes `Treconfig` to trigger a reconfiguration engine (`µ`) that updates the configuration `C_i = (q_i, σ_i, T_i, K_i)`. Execution proceeds in stages: the inference agent (`π_i`) acts under `C_i` with a local history, then upon calling `Treconfig`, it produces a summary `H_i` and request `r_i`. The engine archives `H_i` to a global pool `H_all`, generates `C_{i+1}` from `r_i` and `H_all`, and resets the local history. Training first uses RFT on successful teacher trajectories to initialize separate LoRA adapters for `π` and `µ` (shared frozen base). Then KTO refines both adapters with binary trajectory-level labels, bypassing step-level credit assignment. Inference caps tokens at 32k and cleans up when exceeding 80% usage by retaining only the 10 most recent iterations.

## Key Results
- ToolSelf improves average accuracy by **24.1%** over strong ReAct-based baselines across FRAMES, xbench, GAIA, and SWE-bench Lite.
- It matches expert workflows in reconfiguration frequency (~6.89 iterations after KTO) and generalizes to unseen tasks.
- Token usage scales sublinearly with steps due to staged context resets (e.g., 30 steps ≈ 10k tokens).

## Why This Works (Mechanism)
### Mechanism 1: Unified Action Space for Intrinsic Adaptation
Treating configuration updates as a callable tool (`Treconfig`/`Tterm`) merges meta-decision-making with primitive actions into a single policy. The agent’s LLM can learn to trigger and formulate updates within the same forward pass as task actions, enabled by shared parameters and prompt structure. Evidence: The paper states this unification enables "autonomous adaptation" and abstracts updates as a "callable tool" [page 2, section 2.2]. Break condition: Failure to invoke `Treconfig` when needed or to formulate coherent update requests would cripple adaptation.

### Mechanism 2: Inference-Reconfiguration Loop with Bounded Context
Each stage uses a local history `s_i,t-1` that is cleared upon reconfiguration, preventing unbounded growth. Critical knowledge is distilled into propagated context `K_i` from a global pool `H_all`. This bounds token usage while preserving essential state across stages. Evidence: Stage-local history is "cleared upon each update" and `K_i` is propagated from `H_all` [page 4, section 2.2]. Break condition: If `K_i` omits crucial information (e.g., previously identified entities), repeated exploration occurs.

### Mechanism 3: CAT with Trajectory-Level Credit Assignment
RFT provides cold-start priors from teacher trajectories. KTO then jointly optimizes `π_i` and `µ` using binary success/failure labels propagated across an entire trajectory, avoiding difficult step-level attribution. Evidence: Table 2 shows progressive gains from RFT to RFT+KTO; the authors argue trajectory-level feedback aligns with cross-stage meta-capabilities [page 5, section 2.3]. Break condition: If teacher demonstrations lack reconfiguration diversity or KTO hyperparameters mis-specified, the model may overfit to suboptimal stage transitions.

## Foundational Learning
- **ReAct-style tool-augmented LLM agents**: The base paradigm of thought-action-observation cycles. ToolSelf extends it by adding configuration management tools to the action space.  
  *Why needed*: Without tool integration, agents cannot externally reconfigure; ToolSelf makes reconfiguration intrinsic.  
  *Quick check*: In standard ReAct, what happens when the context window fills during a long task? How does ToolSelf differ?

- **Parameter-efficient fine-tuning (LoRA)**: Low-rank adaptation of a frozen base model. ToolSelf uses separate LoRA adapters for `π_i` and `µ` while sharing the base model.  
  *Why needed*: Enables compact, end-to-end training of the coupled system without full fine-tuning.  
  *Quick check*: Why use separate adapters instead of a unified one? What are the optimization trade-offs?

- **Offline RL from human feedback (KTO)**: Binary preference optimization method. ToolSelf uses KTO for trajectory-level refinement.  
  *Why needed*: Avoids reward modeling and handles cross-stage credit assignment via binary task outcomes.  
  *Quick check*: Why is step-level attribution impractical for self-reconfiguration? How does binary trajectory feedback circumvent this?

## Architecture Onboarding
Inference Agent (π_i) -> Treconfig tool call -> Reconfiguration Engine (µ) -> new Configuration (C_{i+1}) -> new Inference Agent (π_{i+1})

Critical path: (1) Initialize C_0 from µ on empty history. (2) π_i executes under C_i with local history s_i until Treconfig. (3) π_i outputs summary H_i and request r_i; Treconfig triggers µ. (4) µ archives H_i to H_all, generates C_{i+1} from r_i and H_all, starts π_{i+1} with fresh local history s_{i+1,0} but updated K_{i+1}. (5) Repeat until Tterm.

Design tradeoffs:
- **Complexity vs. Generality**: Unified action space increases action space complexity and prompt engineering burden but yields a single generalist agent.
- **Context Management**: Stage-local resets bound token usage but risk information loss if K_i summaries are poor; H_all can grow indefinitely.
- **Training Decoupling**: Independent LoRA adapters simplify optimization but may underfit the tight π-µ coupling; a shared adapter could align objectives but risk interference.

Failure signatures:
- Premature termination: Agent calls Tterm before task completion due to misjudged sub-goals.
- Reconfiguration loop: Excessive Treconfig calls without progress from vague r_i or ineffective C_{i+1}.
- Context starvation: K_i lacks key entities from H_all, causing repeated exploration.
- Toolset fragmentation: T_i omits necessary tools or retains irrelevant ones, increasing noise.

First 3 experiments:
1. **Baseline replication**: Run a Vanilla ReAct agent (no Treconfig) on a short FRAMES task to observe context overflow and failure patterns.
2. **Unified space ablation**: Compare full ToolSelf against "w/o ‘When’" (fixed-interval reconfiguration) and "w/o ‘How’" (ignoring agent’s r_i) on GAIA Level 2; measure steps, tokens, and accuracy.
3. **Training stage ablation**: On Qwen3-8B, evaluate: (a) zero-shot ToolSelf; (b) +RFT; (c) +RFT+KTO on FRAMES/xbench; track reconfigurations and accuracy.

## Open Questions the Paper Calls Out
- **How does ToolSelf handle tasks with hundreds of stages?** The system caps context at 32k tokens and deletes all but the 10 most recent iterations when exceeding 80% usage. Long tasks may still exceed memory and lose crucial details; compression heuristics need validation on extreme-length tasks.
- **Would jointly training π_i and µ improve performance?** Currently separate LoRA adapters are trained independently. Joint training could better align execution and reconfiguration representations but risks interference.
- **Is trajectory-level credit assignment sufficient?** KTO’s binary feedback might equally credit good and bad reconfigurations if later execution fails for unrelated reasons. Granular per-stage rewards could improve sample efficiency but are noisy.

## Limitations
- **Reproducibility gaps**: Teacher prompts and inference hyperparameters for Stage I trajectory generation are unspecified; SWE-bench Docker integration details are sparse.
- **Summarization reliability**: No validation that H_i/K_i preserve critical knowledge across stages; risk of context starvation in complex tasks.
- **Training brittleness**: KTO’s trajectory-level assignment may be sensitive to label noise and trajectory diversity; hyperparameter sensitivity analysis is lacking.

## Confidence
- **Unified action space**: Medium. Conceptual soundness and implicit ablations support it, but explicit ablation results are not provided in the excerpt.
- **Inference-reconfiguration loop**: Medium. Context bound statistics exist, but no direct analysis of knowledge propagation failures.
- **CAT training**: High. Table 2 shows clear progression from RFT to RFT+KTO, aligning with established KTO applications.
- **Overall performance gain (24.1%)**: Medium. Strong multi-benchmark results, but reliance on Qwen3 models and missing baseline details may affect generalizability.

## Next Checks
1. **Ablate unified decisions**: Compare full ToolSelf against fixed-interval reconfiguration and ignoring the agent’s r_i on GAIA Level 2; expect >10% drop if autonomy is critical.
2. **Stress-test context propagation**: Create tasks with increasing irrelevant context; measure failure threshold of K_i in preserving key entities.
3. **KTO hyperparameter sensitivity**: Sweep β (0.05–0.2) and LoRA rank (8–32) on FRAMES with 3 seeds; report success-rate variance and transfer to a 4B model.
