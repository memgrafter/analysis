# Beyond Monolithic Architectures: A Multi-Agent Search and Knowledge Optimization Framework for Agentic Search

## Quick Facts
- arXiv ID: 2601.04703
- Source URL: https://arxiv.org/abs/2601.04703
- Reference count: 40
- Primary result: M-ASK achieves an average F1 score of 50.09 on multi-hop QA benchmarks, outperforming the best baseline by 3.30 points, with 0% training collapse rate over 10 runs.

## Executive Summary
M-ASK tackles fundamental flaws in monolithic agentic search systems—unconstrained outputs, sparse rewards, and search noise—by introducing a multi-agent framework that decouples search behavior (planning, execution) from knowledge management (filtering, state updates). It employs turn-level dense rewards to supervise each agent, leading to state-of-the-art performance on multi-hop question answering benchmarks and dramatically improved training stability.

## Method Summary
M-ASK employs five specialized agents—Planning, Search, Answer, Summary, and Update—all sharing a single Qwen2.5-7B-Instruct backbone, differentiated only by role-specific system prompts. The knowledge state K_t is a structured record containing the original question, a thinking trajectory of `<q_sub, a_sub>` pairs, and the current predicted answer. During training, each turn provides dense rewards: the Planning agent receives the F1 score between the initial answer and gold; the Answer agent gets the F1 of its temporary answer each turn; Search, Summary, and Update share the incremental change in F1 (ΔF1 = F1_t - F1_{t-1}), with Search receiving zero if it terminates. Training uses independent PPO with a shared policy π_θ and critic V_ϕ, updating over mixed experiences from all agents using GAE. At inference, Planning initializes K_0, then the loop runs: Search decides to query or terminate; if query, Retriever returns top-k documents; Summary extracts evidence; Update modifies K_t via `<Update>` or `<Add>` tags; Answer produces a final prediction upon termination.

## Key Results
- State-of-the-art average F1 score of 50.09 on multi-hop QA benchmarks (HotpotQA, 2WikiMultiHopQA, Musique, Bamboogle), surpassing the best baseline by 3.30 points.
- Near-zero training collapse rate (0% over 10 runs) compared to 90% for the monolithic Search-r1 at 1000 steps.
- Ablation studies confirm that both role specialization and turn-level rewards are essential for the observed performance.

## Why This Works (Mechanism)
M-ASK’s effectiveness stems from two coordinated mechanisms: role specialization and turn-level reward shaping. By decomposing the complex search process into distinct agents with constrained output formats, the system reduces unconstrained outputs and search noise, as each agent operates within a well-defined behavioral niche. Turn-level dense rewards provide immediate feedback on the utility of each action, enabling precise credit assignment and mitigating the sparse-reward problem. Together, these innovations stabilize policy gradient updates and prevent training collapse, while the shared backbone ensures consistent representation learning across roles.

## Architecture Onboarding
**Component map**:
Question -> Planning Agent -> K0 -> [Search Agent -> Retriever -> Summary Agent -> Update Agent -> K_t] (repeat) -> Answer Agent (final) -> Output
During training: Answer Agent also produces temporary answers each turn for reward calculation; Reward Calculator feeds ΔF1 to Search/Summary/Update and F1 to Planning/Answer; Replay Buffer stores all transitions; PPO updates shared Policy and Critic.

**Critical path**: The essential sequence for each turn: Search generates a query or termination signal; if query, Retriever fetches documents; Summary extracts evidence; Update modifies K_t; Answer generates a temporary answer for reward. The loop continues until Search outputs `<end>` or a max step limit is reached, after which Answer produces the final response.

**Design tradeoffs**:
- Parameter sharing vs. separate models: Sharing reduces compute and ensures transfer, but may limit specialization; role prompts mitigate this at low cost.
- Turn-level vs. episode-level rewards: Turn-level offers dense feedback but risks short-term optimization; ΔF1 encourages progress without harming final performance.
- Structured K_t with manual update operations: Enables precise state control but relies on correct parsing; errors cause context bloat or loss of information.

**Failure signatures**:
- Collapse to near-zero F1: likely reward miscomputation or PPO instability.
- Unbounded trajectory growth: Update agent failing to apply `<Update>` correctly, leading to additive bloat.
- Uniform agent outputs: system prompts not being applied or ignored.
- Low retrieval recall: incorrect E5 variant or top-k settings.

**First three experiments**:
1. Retrieval sanity check: Implement E5-base dense retrieval with top-k=10; measure recall@5 on 100 validation queries; expect >60% recall.
2. Reward pipeline validation: On 10 fixed examples, manually run a full trajectory and compute turn-level ΔF1; verify that rewards match the specification and sum to final F1.
3. Component isolation test: For each agent, feed a fixed K_t and observe output format (e.g., Search emits query or `<end>`, Update emits `<Update>τi</Update>` or `<Add>τnew</Add>`); ensure compliance with prompts.

## Limitations
- The paper omits critical training hyperparameters (learning rate, batch size, PPO clip ϵ, GAE λ, KL penalty) and exact training schedule, hindering faithful replication.
- Retrieval configuration details (E5 model variant, document chunk size, k) are not fully specified, leaving ambiguity about evidence quality and its impact.
- Knowledge state serialization and Update agent parsing rules are insufficiently documented, risking implementation deviations that could affect performance.
