# ZorBA: Zeroth-order Federated Fine-tuning of LLMs with Heterogeneous Block Activation

## Quick Facts
*   **arXiv ID:** 2603.04436
*   **Source URL:** https://arxiv.org/abs/2603.04436
*   **Reference Count:** 40
*   **Primary Result:** ZorBA reduces total client VRAM by up to 62.41% and converges up to 23.76% faster than baselines in federated LLM fine-tuning.

## Executive Summary
ZorBA is a federated fine-tuning framework for large language models (LLMs) designed to overcome the memory and communication bottlenecks of standard gradient-based methods. It combines two key innovations: zeroth-order (ZO) optimization, which estimates gradients via forward passes only to eliminate gradient storage, and heterogeneous block activation, where the server strategically assigns different subsets of transformer blocks to different clients. An ϵ-constraint lexicographic algorithm solves a multi-objective problem to allocate blocks, balancing convergence rate against VRAM constraints. Theoretical analysis introduces a metric Λ(A) linking the allocation matrix A to convergence guarantees. Experiments on OPT models show significant VRAM reductions and faster convergence compared to existing federated ZO and communication-efficient baselines.

## Method Summary
ZorBA operates in a standard federated learning loop but replaces backpropagation with a zeroth-order gradient estimator. Before training, the server pre-computes a binary block activation matrix A* that assigns each client a specific subset of the M transformer blocks to update, respecting each client's VRAM budget. This allocation is found by solving a multi-objective problem: minimize Λ(A) (to accelerate convergence) while ensuring per-client total VRAM ψ_tot,n ≤ ψ_max,n. The server uses an ϵ-constraint method and a greedy post-processing step to generate a Pareto-optimal A*. During each round, the server shares a set of random seeds. Clients generate identical perturbation vectors from these seeds and, for each vector, compute the finite difference of the loss on their local data for only their assigned blocks. They send the resulting scalar ρ values to the server. The server aggregates these ρ values per block using weights derived from A, computes an aggregated gradient estimate for each block, and updates the global block parameters. It then broadcasts the aggregated ρ values back to clients, who apply the same updates identically, ensuring model consistency without transmitting high-dimensional gradients or model parameters.

## Key Results
*   ZorBA cuts total client VRAM usage by up to 62.41% compared to baselines like FedIT and FedZO.
*   It achieves up to 23.76% faster convergence (fewer rounds to target accuracy) than the communication-efficient baseline DeComFL.
*   Its communication overhead remains competitive, matching the most efficient baselines by exchanging only scalars (M·Q values) per round instead of full gradients.

## Why This Works (Mechanism)

### Mechanism 1
*   **Claim:** Zeroth-order optimization eliminates gradient storage, reducing VRAM usage by replacing backpropagation with forward-pass-only gradient estimation.
*   **Mechanism:** For each perturbation vector sampled from a shared Gaussian distribution, clients compute finite differences of the loss function: ρ = (F(w+μv) - F(w))/μ. The gradient estimate is the average of ρ·v over Q perturbations. This avoids storing intermediate gradients and their associated optimizer states.
*   **Core Assumption:** The finite-difference approximation error is bounded (Lemma 1), and the variance of the estimator scales with model dimension d but can be controlled via the effective condition number κ (Condition 1).
*   **Evidence Anchors:** Abstract states ZorBA "leverages zeroth-order optimization to eliminate the storage of gradients at the clients by forward passes." Section II details the finite-difference estimation. Neighboring work on zeroth-order federated pre-training corroborates the memory-saving mechanism.
*   **Break Condition:** If the smoothing parameter μ is too large, estimates become biased; if too small, numerical instability arises. High data heterogeneity (σ_G) or large d without low κ can cause slow convergence despite VRAM savings.

### Mechanism 2
*   **Claim:** Heterogeneous block activation reduces VRAM per client while maintaining convergence by strategically assigning different transformer blocks to different clients, guided by minimizing Λ(A).
*   **Mechanism:** The server solves Problem P1 to find binary matrix A (size M×N) where a_m,n=1 means client n updates block m. The objective Λ(A) = Σ_n 1/(c_n)^2, with c_n = min_{m:a_m,n=1} c_m (least popularity of client n's activated blocks). Minimizing Λ(A) flattens the least-popularity distribution (Theorem 3), accelerating convergence. VRAM usage is linear in the number of activated blocks per client.
*   **Core Assumption:** The convergence rate is monotonic in Λ(A) (Lemma 4). The VRAM model per block is accurate.
*   **Evidence Anchors:** Abstract mentions "heterogeneous block activation mechanism... to accelerate the convergence rate and reduce the VRAM usage." Section III uses Λ(A) to characterize the bias term. Section IV formulates the multi-objective optimization. Neighboring ParaBlock work supports block-wise update viability.
*   **Break Condition:** If block allocations are imbalanced (some blocks have very low popularity), Λ(A) increases and convergence degrades. Strict VRAM constraints may force clients to activate too few blocks, creating bottlenecks.

### Mechanism 3
*   **Claim:** Shared random seeds and finite-difference communication reduce overhead by avoiding high-dimensional gradient exchanges; clients send scalars (loss differences) instead of full estimated gradients.
*   **Mechanism:** The server initializes seed set S and shares it. In round t, server broadcasts a subset Q_t ⊆ S. Clients generate identical perturbation vectors v_q from these seeds. Each client computes ρ_{v_q,n} for its activated blocks only and sends {ρ_{v_q,n}} to server. Server aggregates ̄ρ_{v_q} = (1/|Q_t|) Σ_n (a_m,n / Σ_n' a_m,n') ρ_{v_q,n} per block and updates global model: ̄w_{m}^{t+1} = ̄w_m^t - η_t Σ_{v_q∈Q_t} ̄ρ_{v_q} v_{q,m}. Server broadcasts {̄ρ_{v_q}} and clients reconstruct ̄w^{t+1} without sending model parameters.
*   **Core Assumption:** Perturbation vectors v_q are identical at client and server because they share the same random seeds and the same global model at the start of the round.
*   **Evidence Anchors:** Abstract states ZorBA "utilizes shared random seeds and the finite differences of gradients in order to reduce the communication overhead." Section II discusses communication overhead and details the protocol. Neighboring work on communication-efficient distributed learning aligns with the goal.
*   **Break Condition:** Seed synchronization failure (e.g., lost packets) or client stragglers can cause mismatched perturbations, corrupting updates. Finite-difference approximation error accumulates if Q is too small.

## Foundational Learning
*   **Federated Learning (FL):** Needed as ZorBA is a federated framework; understanding client-server orchestration, local updates, and global aggregation is foundational.
    *   **Quick Check:** What are the two main phases in each FL round? (Answer: local training on clients, then server aggregation of updates.)
*   **Zeroth-Order Optimization (ZOO):** Needed because ZorBA's memory savings rely on replacing backpropagation with forward-pass gradient estimation.
    *   **Quick Check:** How does ZOO estimate the gradient without backpropagation? (Answer: via finite differences around the current parameters using random perturbations.)
*   **Transformer Block architecture:** Needed since ZorBA activates subsets of transformer blocks; understanding that LLMs are stacks of identical blocks (each with attention and FFN) is essential.
    *   **Quick Check:** What are the three components of VRAM usage per block in zeroth-order optimization? (Answer: hidden state activations, QKV projections, and FFN activations.)
*   **Non-convex convergence analysis:** Needed as the paper provides theoretical bounds; familiarity with L-smoothness, gradient variance σ², dissimilarity σ_G², and Taylor expansion is needed to interpret Theorems 1–2.
    *   **Quick Check:** What does L-smoothness imply about the function f? (Answer: Gradient differences are bounded by L times the parameter difference: ∥∇f(x)−∇f(y)∥ ≤ L∥x−y∥.)
*   **Multi-Objective Optimization:** Needed because ZorBA balances convergence (min Λ(A)) and VRAM (ψ_tot,n ≤ ψ_max,n). The ε-constraint method transforms this into a series of single-objective problems.
    *   **Quick Check:** In the ε-constraint method, how are multiple objectives handled? (Answer: One objective is minimized while the others are constrained to be below thresholds ε.)

## Architecture Onboarding
*   **Component map:**
    Central Server -> Pre-computes A* (solves P1) -> Broadcasts seeds & aggregated ρ -> Computes global update -> Sends aggregated ρ to Clients.
    Clients -> Receive A* -> Activate assigned blocks -> Generate perturbations -> Compute local ρ -> Send ρ to Server -> Apply global update from Server.
    Random Seed Set S -> Shared initially -> Used to generate identical v_q each round.
    Block Activation Matrix A* -> Guides which blocks each client updates.
*   **Critical path:**
    1.  **Pre-deployment:** Server runs Algorithm 2 (ε-constraint + greedy) to compute A* given VRAM capacities {ψ_max,n}.
    2.  **Round initialization:** Server shares seed set S and global model ̄w^1; clients set local model ̂w^1 by blending global blocks per A*.
    3.  **Per round:**
        *   Server selects Q_t ⊆ S and broadcasts seeds.
        *   Clients: generate v_q from seeds; for each, compute F(̂w_n) and F(̂w_n+μv_q) on a local batch; derive ρ_{v_q,n} **only** for parameters in their activated blocks; send all ρ_{v_q,n}.
        *   Server: for each block m, compute denominator d_m = Σ_n a_m,n; for each q, compute α_{q,m} = (1/(Q·d_m)) Σ_n a_m,n ρ_{v_q,n}; update ̄w_m ← ̄w_m - η Σ_q α_{q,m} v_{q,m}.
        *   Server broadcasts all α_{q,m} (M·Q scalars); clients apply the identical update to their local copies of the global blocks.
*   **Design tradeoffs:**
    *   **VRAM vs Convergence:** More activated blocks lowers Λ(A) (faster convergence) but increases per-client VRAM. The Pareto front (Fig. 4) illustrates this tradeoff; A* is chosen on the front based on system constraints.
    *   **Communication vs Accuracy:** Larger Q reduces gradient estimator variance but linearly increases communication (Q scalars sent). Q=10 in experiments is a chosen balance.
    *   **Allocation fairness:** The greedy Algorithm 1 maximizes the minimum popularity γ* to avoid bottleneck clients, but may leave some blocks underutilized if VRAM budgets are very unequal.
*   **Failure signatures:**
    *   **VRAM overflow:** Client crashes if Σ_m a_m,n exceeds its block budget λ_n^*. Verify A* satisfies (8b) and that the per-block VRAM model (ψ_block) is accurate.
    *   **Mismatched perturbations:** If seeds are not identically interpreted (different RNGs) or model drift occurs mid-round, clients and server compute different v_q or loss values, corrupting updates. Ensure seed sharing and synchronous rounds.
    *   **Divergence:** If learning rate η is too large (violates Theorem 2 condition), convergence fails. Use η=5e-5 as in experiments; monitor training loss stability.
    *   **Imbalanced allocation:** If many clients have c_n(A) = 1 (only one block activated), Λ(A) becomes large. Check post-allocation: compute c_m (block popularity) and c_n (client's least popular block); ensure they are reasonably balanced.
*   **First 3 experiments:**
    1.  **Convergence comparison:** Run ZorBA and baselines (FedIT, FedZO, DeComFL) on AG-News, SST-2, SNLI with OPT-125M/1.3B. Record rounds to target accuracy (0.8/0.8/0.72). Expect ZorBA to converge faster than DeComFL/FedZO by up to 23.76% (Table I).
    2.  **VRAM & communication:** For each dataset/model, compute total VRAM per round (Σ_n ψ_tot,n(A*)) and total communication (number of scalars sent: clients→server: N·Q; server→clients: M·Q). Expect ZorBA to reduce total VRAM by up to 62.41% vs FedIT and match DeComFL’s communication (Table II).
    3.  **Pareto tradeoff validation:** For OPT-125M/SST-2, vary τ over 1000 samples, compute (Λ(A_ε^⋆), total activated blocks). Plot Pareto front (Fig. 4a). Select 3 points (SC1, SC2, SC3) with same total activated blocks but different Λ. Show SC1 and SC2 have similar convergence despite different VRAM, while SC3 (same VRAM as SC2 but higher Λ) converges slower (Fig. 4b). This validates that Λ, not just total blocks, controls convergence.

## Open Questions the Paper Calls Out
*   **Open Question 1:** How does ZorBA scale to larger LLMs (7B+ parameters) in terms of VRAM savings and convergence rate? Basis: Experiments limited to OPT-125M/1.3B; theoretical bounds have residual d-dependence. Why unresolved: Scaling behavior at billions of parameters is untested. Resolution: Evaluate on Llama-7B/13B, report VRAM reduction, convergence speed, and communication.
*   **Open Question 2:** Is the ϵ-constraint lexicographic algorithm near-optimal for the block activation allocation problem? Basis: Paper acknowledges P1 is NP-hard and proposes a heuristic without optimality guarantees. Why unresolved: Greedy steps may not achieve true Pareto front. Resolution: For small instances (M=6, N=4), brute-force enumerate all feasible A to compute optimal Λ(A) and compare to Alg. 2's output.
*   **Open Question 3:** How robust is ZorBA to violations of key theoretical assumptions (L-smoothness, bounded gradient variance, bounded gradient dissimilarity)? Basis: Convergence analysis relies on Assumptions 1–3 and Condition 1; no robustness analysis. Why unresolved: Real federated LLM fine-tuning may violate these assumptions. Resolution: Systematically vary smoothness, variance (batch size), and heterogeneity (Dirichlet α); measure convergence vs. theory.
*   **Open Question 4:** Can the block activation mechanism be extended to finer-than-block granularity (e.g., layers or attention heads) to achieve additional VRAM savings? Basis: ZorBA activates entire blocks; no sub-block activation considered. Why unresolved: Finer granularity could save more memory but increases allocation complexity. Resolution: Design hierarchical activation (per-layer/head), extend Λ(A) metric, compare trade-offs against block-level ZorBA.

## Limitations
*   **Hidden hyperparameters:** Exact sequence length L, per-block VRAM constants (α, K, B, H), and the specific τ values used for reported results are undisclosed, making absolute reproduction of VRAM numbers approximate.
*   **Allocation algorithm optimality:** The proposed heuristic for solving P1 (max-min popularity + greedy) is not proven optimal; its distance from the true Pareto front is unknown and may depend on instance topology.
*   **Theoretical assumption dependence:** The convergence guarantee relies on L-smoothness, bounded gradient variance, and bounded gradient dissimilarity. Real-world LLM fine-tuning landscapes may violate these, and the paper does not analyze robustness to such violations.

## Confidence
*   **VRAM reduction (zeroth-order + block activation):** Medium. Mechanism is sound and theoretically supported, but exact savings depend on unreported hyperparameters and allocation choices.
*   **Convergence acceleration vs. baselines:** Medium. Experimental results are promising but sensitive to learning rate, μ, Q, and allocation; the Λ(A) metric is plausible but not exhaustively validated.
*   **Communication efficiency:** High. Protocol is well-defined; per-round payload is M·Q scalars (plus one-time overhead), matching the described minimal overhead.
*   **Allocation algorithm optimality:** Medium. The ϵ-constraint method is standard, but the greedy PII heuristic may not achieve the true Pareto front in all cases.
