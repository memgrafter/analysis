# Rashomon Sets and Model Multiplicity in Federated Learning

## Quick Facts
- **arXiv ID:** 2602.09520
- **Source URL:** https://arxiv.org/abs/2602.09520
- **Reference count:** 40
- **Primary result:** Defines and evaluates Rashomon sets and predictive multiplicity metrics for federated learning, demonstrating their utility for transparent, client-aligned model selection.

## Executive Summary
This paper addresses predictive multiplicity in federated learning (FL) by introducing Rashomon set definitions tailored to decentralized settings. Three set definitions are proposed: global (aggregated across clients), t‑agreement (intersection across a fraction t of clients), and individual (client‑specific). Multiplicity metrics (ambiguity, discrepancy, Rashomon capacity) are adapted to respect FL privacy and aggregation constraints. Empirical results on benchmark datasets show that global sets inflate multiplicity, t‑agreement sets shrink with stricter thresholds and can become empty under high heterogeneity, and individual sets expose substantial local variation hidden by aggregated views. A fairness application illustrates how clients can leverage the Rashomon set to balance accuracy and demographic parity according to local needs, highlighting the value of multiplicity‑aware FL for transparent, client‑aligned model selection.

## Method Summary
The authors generate a pool of candidate FL models by independently training hundreds of models (e.g., 400 per configuration) using FedAvg with varied hyperparameters and client sampling. Each model is evaluated on every client’s local validation data. For global and t‑agreement sets, clients compute metric differences (e.g., accuracy gaps) relative to a baseline model and transmit these to the server, which aggregates them (weighted average) or counts clients meeting constraints to determine set membership. Individual sets are computed locally without server involvement. Multiplicity metrics—both decision‑based (ambiguity, discrepancy) and score‑based (Rashomon Capacity, VPR)—are adapted to FL, with score‑based metrics requiring differential privacy to protect client data. The pipeline adds minimal communication overhead (up to two extra rounds) but is computationally intensive due to retraining. Validation is performed on three datasets (Dutch Census, ACS Income, MNIST) with non‑IID client partitions.

## Key Results
- Global Rashomon sets yield higher multiplicity metrics and Rashomon ratios compared to t‑agreement sets, which shrink as the agreement threshold t increases.
- Centralized evaluation (aggregated test set) masks client heterogeneity, while individual client sets reveal significant local variation in metrics like ambiguity and Rashomon Capacity.
- In a fairness case study, models within the same global Rashomon set allow clients to trade off accuracy and demographic parity according to local preferences, enabling personalized yet globally compliant model selection.

## Why This Works (Mechanism)
### Mechanism 1: Global Aggregation Masks Heterogeneity
- **Claim:** The global Rashomon set uses federated aggregation (e.g., FedAvg) to combine client‑level metric differences into a single federation‑wide measure, but this masks client heterogeneity.
- **Mechanism:** Each client c ∈ C_E computes metric differences δ_i(h₁, h₂)_c for all candidate model pairs. The server aggregates these using the FL aggregation function f_a (e.g., weighted average by client dataset size). Two models belong to the global set if f_a(δ_i(h₁, h₂)_{c ∈ C_E}) ≤ ε_i for all metrics (δ_i, ε_i) ∈ (Δ, E) (Equation 3).
- **Core assumption:** Aggregated statistics accurately represent the federation’s collective behavior, even though individual clients may experience divergent model performances.
- **Evidence anchors:**
  - [abstract]: "Global Rashomon set defined over aggregated statistics across all clients."
  - [section 4.1]: Formal definition (Equation 3) and statement that "models that satisfy the definition for the aggregated statistics... may still fail to meet them on individual... clients."
  - [corpus]: Neighbors focus on centralized Rashomon sets; FL aggregation effects are under‑explored. *Assumption: Standard FL aggregation logic applies to metric differences.*
- **Break condition:** When client data distributions are highly heterogeneous, aggregated metrics fail to capture local instabilities, creating a false sense of model uniformity and potentially silencing minority client concerns.

### Mechanism 2: t‑Agreement Threshold Reveals Incompatibility
- **Claim:** The t‑agreement Rashomon set requires a minimum fraction t of clients to individually satisfy performance constraints, ensuring broader agreement across the federation and highlighting incompatibilities.
- **Mechanism:** For each candidate model pair, count the number of clients c ∈ C_E for which δ_i(h₁, h₂)_c ≤ ε_i holds for all metrics. The pair belongs to the t‑agreement set if this count ≥ t · |C_E| (Equation 4). Varying t adjusts the strictness of client agreement.
- **Core assumption:** A threshold t balances inclusivity and representativeness, revealing whether a single model can satisfy a substantial portion of the federation.
- **Evidence anchors:**
  - [abstract]: "t‑agreement Rashomon set representing the intersection of local Rashomon sets across a fraction t of clients."
  - [section 4.2]: Definition and analysis showing that "choosing t > 0.5 ensures... majority of evaluating clients" and that high t can yield empty sets, proving "fundamental incompatibility among client data distributions."
  - [corpus]: Neighbors discuss Rashomon set intersections [87978, 268757] but not threshold‑based agreement in FL. *Assumption: Intersection logic with a fraction threshold generalizes.*
- **Break condition:** For stringent thresholds (e.g., t = 0.9) and tight ε, the set often becomes empty, indicating no single model can meet constraints for most clients—a sign of severe heterogeneity or overly strict performance bounds.

### Mechanism 3: Individual Sets Expose Local Variation
- **Claim:** Individual Rashomon sets are computed per client using local evaluation data, fully respecting client autonomy and exposing local heterogeneity hidden by global or t‑agreement definitions.
- **Mechanism:** Each client c independently evaluates candidate models on its local data D_c. Two models belong to client c’s individual set if δ_i(h₁, h₂)_c ≤ ε_i for all metrics, using either globally shared constraints (Δ, E) or client‑specific ones (Δ_c, E_c) (Equation 5).
- **Core assumption:** Client data distributions are sufficiently divergent that federation‑level metrics cannot capture individual model behavior variance, necessitating client‑level analysis.
- **Evidence anchors:**
  - [abstract]: "Individual Rashomon sets specific to each client’s local distribution."
  - [section 4.3]: Definition and statement that this "balances central oversight with client‑level customization."
  - [corpus]: Neighbors emphasize individual model differences [75638, 83333] but in centralized settings. *Assumption: Local evaluation reveals hidden variance in FL.*
- **Break condition:** If clients adopt radically different performance constraints (Δ_c, E_c), the federation may lack coherent model selection, requiring negotiation or higher‑level coordination to maintain shared objectives.

## Foundational Learning
### Concept: Federated Learning (FL) Architecture & Heterogeneity
- **Why needed:** FL’s core design—decentralized data, client‑specific training, server aggregation—introduces data heterogeneity (non‑IID) and communication constraints. Traditional Rashomon definitions assume centralized data and uniform evaluation, which fails in FL. Understanding FedAvg, client sampling, and aggregation is essential to see why model multiplicity behaves differently.
- **Quick check:** How might the FedAvg aggregation of model weights, rather than predictions, smooth out or exaggerate differences between models in the Rashomon set?

### Concept: Rashomon Effect & Predictive Multiplicity Metrics
- **Why needed:** The Rashomon set captures all models achieving near‑identical performance (e.g., accuracy ±ε). Multiplicity metrics (ambiguity, discrepancy, Rashomon Capacity) quantify how much these models disagree on individual predictions. Adapting these to FL requires rethinking how to aggregate or threshold across clients without violating privacy.
- **Quick check:** Why might the *discrepancy* metric be particularly sensitive to the choice of Rashomon set definition (global vs. individual) in FL?

### Concept: Differential Privacy (DP) for Multiplicity Metrics
- **Why needed:** FL already employs DP to protect client data. Score‑based multiplicity metrics (e.g., Rashomon Capacity, VPR) require distributions of model outputs, which could leak client data if shared raw. DP mechanisms (e.g., adding noise to histograms) are needed to estimate these metrics privately, but they introduce noise that can distort estimates.
- **Quick check:** What are the trade‑offs between using a small number of histogram buckets (for privacy) versus many buckets (for metric accuracy) when computing a DP VPR?

## Architecture Onboarding
### Component map:
Candidate Generation → Set Construction (Global/t‑agreement/Individual) → Multiplicity Analysis → Application Layer

Critical path:
1. **Training loop:** Run standard FL (e.g., FedAvg) for multiple independent runs to build candidate model pool. This is the most computationally expensive step.
2. **Evaluation phase:** All clients evaluate all candidates on local hold‑out sets. For global/t‑agreement, send per‑metric differences (or DP‑noisy histograms) to server.
3. **Aggregation & filtering:** Server computes aggregated metrics (global) or counts (t‑agreement) and broadcasts set membership. Individual clients filter locally.
4. **Metric computation:** Compute chosen multiplicity metrics on final set(s). If needed, aggregate metric values across clients (e.g., average ambiguity).
5. **Model selection:** Clients pick model(s) from their local or federated Rashomon set based on domain needs.

Design tradeoffs:
- **Computational cost vs. coverage:** Re‑training generates a diverse candidate pool but is prohibitively expensive for large models. Alternatives (dropout, RashomonGB) are model‑specific and may not capture the full space.
- **Global vs. local perspective:** Global aggregation is efficient but obscures heterogeneity; individual sets are informative but syndicate no shared insight. t‑agreement is a middle ground but can yield empty sets.
- **Privacy vs. metric fidelity:** DP is mandatory for score‑based metrics in privacy‑preserving FL, but DP noise (especially with sparse histograms) can severely distort metric estimates (Appendix F shows inconsistent results).
- **Constraint strictness:** Tight ε yields small, potentially useless Rashomon sets; loose ε yields large sets with high multiplicity but may include poor models.

Failure signatures:
- **Empty t‑agreement sets:** Especially for t = 0.9 or tight ε, indicating no model satisfies a majority of clients—a sign of severe heterogeneity or unrealistic performance bounds.
- **Discrepancy divergence:** Centralized evaluation shows much higher discrepancy than FL settings, suggesting aggregation reduces prediction volatility but may also hide local conflicts.
- **DP metric instability:** Score‑based metrics (VPR, RC) with DP show non‑monotonic or erratic behavior across ε (Figure 7), indicating histogram sparsity/noise overwhelms signal.
- **Individual deviation:** Clients’ individual metrics (e.g., ambiguity, RC) frequently fall outside the global/t‑agreement range (Figure 4), proving aggregated metrics are insufficient.

First 3 experiments:
1. **Vary t in t‑agreement sets:** Test t ∈ {0.6, 0.75, 0.9} on a fixed candidate pool. Expect Rashomon set size and multiplicity metrics to shrink as t increases; check for empty sets at high t.
2. **Compare definitions head‑to‑head:** For the same ε, compute global, t‑agreement (t = 0.75), and individual Rashomon sets. Plot multiplicity metrics (e.g., ambiguity, RC) for individual clients against global/t‑agreement aggregates to visualize deviation (like Figure 4).
3. **Fairness‑aware selection:** From a small‑ε global Rashomon set, let each client locally evaluate accuracy vs. Demographic Parity. Plot tradeoff curves per client (like Figure 6) to demonstrate how multiplicity enables personalized fairness choices without sacrificing global performance.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can Rashomon sets in federated learning be constructed more efficiently without relying on exhaustive re‑training?
- **Basis in paper:** [explicit] The authors identify re‑training as a computational bottleneck and propose exploiting FL inner workings (e.g., intermediate updates) as future work.
- **Why unresolved:** Current approach requires training hundreds of models from scratch, which is infeasible for complex models or large client pools.
- **What evidence would resolve it:** A novel algorithm that leverages FL communication rounds or aggregated updates to approximate Rashomon sets with fewer training cycles, validated by reduced runtime while preserving metric reliability.

### Open Question 2
- **Question:** Can the proposed federated Rashomon set definitions be extended to other secure multi‑party computation frameworks (e.g., CryptTen) with different communication structures?
- **Basis in paper:** [explicit] The paper notes that other frameworks like CryptTen introduce heterogeneity requiring extensions, calling it an interesting direction.
- **Why unresolved:** Different MPC frameworks have distinct communication patterns and client interactions that may invalidate current definitions.
- **What evidence would resolve it:** Theoretical adaptation of definitions to a specific MPC framework, supported by empirical evaluation showing meaningful Rashomon sets and multiplicity insights.

### Open Question 3
- **Question:** How can score‑based multiplicity metrics be robustly estimated under differential privacy in FL despite histogram sparsity?
- **Basis in paper:** [explicit] Appendix F states additional work is needed to make the private pipeline robust against difficulties with empty bins and noise.
- **Why unresolved:** Standard DP histograms add noise that degrades approximation when bins are sparse, leading to unreliable metric estimates.
- **What evidence would resolve it:** A DP aggregation method robust to sparsity (e.g., adaptive binning or secure MPC variants), demonstrated via experiments aligning closely with non‑private baselines.

## Limitations
- Exact hyperparameters (learning rates, batch sizes) and FedAvg configurations (client participation, rounds) for the 400 candidate models are undisclosed, hindering exact replication.
- Differential privacy implementation for score‑based metrics (e.g., VPR, Rashomon Capacity) lacks detail (noise mechanism, bucket handling), causing instability in private estimates (Appendix F).
- High computational cost of retraining numerous FL models may limit practical adoption and scalability studies.
