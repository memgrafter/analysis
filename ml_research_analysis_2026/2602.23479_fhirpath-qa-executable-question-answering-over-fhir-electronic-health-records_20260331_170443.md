# FHIRPath-QA: Executable Question Answering over FHIR Electronic Health Records

## Quick Facts
*   **arXiv ID:** 2602.23479
*   **Source URL:** https://arxiv.org/abs/2602.23479
*   **Reference count:** 0
*   **Primary result:** A query-first text-to-FHIRPath approach reduces token usage by 391× and, after supervised fine-tuning on a new dataset, improves query synthesis accuracy from 27% to 79% for patient-specific EHR QA.

## Executive Summary
This paper introduces a paradigm shift for question answering over electronic health records (EHRs) standardized in FHIR. Instead of relying on retrieval-augmented LLMs that ingest entire patient records (risking hallucinations and high token costs), the authors propose generating executable FHIRPath queries. This "query-first" architecture dramatically improves efficiency and reliability. The study is supported by the release of the new FHIRPath-QA dataset (14,295 samples) and benchmark, demonstrating that supervised fine-tuning (SFT) on this data substantially improves a base model's accuracy in synthesizing correct, executable queries. The work establishes a foundation for building safe, efficient, and verifiable patient-facing QA systems.

## Method Summary
The core method replaces a retrieval-first pipeline (full EHR ingestion -> LLM reasoning -> answer) with a query-first pipeline (question -> LLM generates FHIRPath query -> external executor runs query on full patient bundle -> formatted answer). To enable this, the authors constructed the FHIRPath-QA dataset by translating templated clinical questions into ground-truth FHIRPath expressions, then generating clinician and patient paraphrases. They evaluated baseline LLM performance and applied SFT to models like `4o-mini` using subsets of this training data. Performance was measured via execution accuracy (exact match between query result and ground-truth answer), token usage, and failure rate, comparing the two architectures directly.

## Key Results
*   The query-first approach with `gpt-4o-mini` used 391× fewer tokens (1,609 vs. 629,829) and lowered the failure rate from 0.36 to 0.09 compared to retrieval-first.
*   Supervised fine-tuning on the FHIRPath-QA Large set improved query synthesis accuracy for `4o-mini` from 27% (zero-shot) to 79%.
*   Fine-tuned models consistently achieved higher accuracy on clinician-oriented (precise) questions than on patient-oriented (ambiguous) ones, revealing a performance ceiling for lay language.

## Why This Works (Mechanism)

### Mechanism 1
*   **Claim:** A query-first Text-to-FHIRPath architecture drastically reduces token consumption and context window limitations.
*   **Mechanism:** The LLM's context is limited to the natural language question and system prompt, not the EHR. It generates a concise, executable FHIRPath query which is run externally against the patient's complete `$everything` bundle. The LLM is removed from the record ingestion loop.
*   **Evidence anchors:** The abstract reports a 391× token reduction for `gpt-4o-mini` and lower failure rates. Section 5.1 & Table 3 provide the statistics and note the query-first approach's stable, low token variance versus retrieval-first's scaling with record size.

### Mechanism 2
*   **Claim:** Supervised Fine-Tuning (SFT) on paired (question, FHIRPath query) data substantially improves a base LLM's ability to map natural language to executable FHIRPath logic.
*   **Mechanism:** SFT teaches the model the specific syntactic patterns, resource traversal logic, and filtering semantics of FHIRPath, moving beyond its general medical knowledge to learn the formal query grammar required for precise EHR interrogation.
*   **Evidence anchors:** The abstract states SFT improved `4o-mini` accuracy from 27% to 79%. Section 5.3 & Figure 3 show dramatic gains on test splits for novel paraphrases and query compositions, confirming SFT's effectiveness for generalization over known resource types.

### Mechanism 3
*   **Claim:** Patient-oriented phrasing (conversational, ambiguous) imposes a lower performance ceiling than clinician-oriented phrasing for single-turn query generation, even after SFT.
*   **Mechanism:** Layperson questions use vague terms, require disambiguation of clinical concepts, or omit constraints. The model must perform complex inference to map this intent to a precise query. SFT improves pattern recognition but cannot fully resolve inherent ambiguity without additional context.
*   **Evidence anchors:** The abstract notes fine-tuned models achieved higher accuracy on clinician-paraphrases. Section 5.3 & 5.4.2 discuss this reversal and identify "Semantic Misinterpretation" as a key error, especially for patient paraphrases (e.g., confusing `MedicationRequest` vs. `MedicationAdministration`).

## Foundational Learning
*   **Concept: FHIR Resource Structure & References**
    *   **Why needed here:** Generating correct FHIRPath requires understanding the graph of resources (Patient, Encounter, Observation) and how they link via references (e.g., `Encounter.subject`). Errors stem from missing this schema knowledge.
    *   **Quick check:** "Given a `MedicationAdministration` referencing a `Patient` via `subject` and a `Medication` via `medication`, write a FHIRPath snippet from a `Bundle` to find all administrations for a specific patient."
*   **Concept: FHIRPath Syntax & Operators**
    *   **Why needed here:** The output must be a syntactically correct expression using filters (`where`), traversal (`.`), aggregation (`distinct`, `count`), sorting, and date arithmetic.
    *   **Quick check:** "Write a FHIRPath expression that selects the most recent `Observation` with LOINC code '15074-8' from a bundle, based on `effectiveDateTime`."
*   **Concept: Clinical Context & Ambiguity Resolution**
    *   **Why needed here:** Interpreting patient language requires mapping colloquial terms ("heart racing", "took my meds") to precise clinical concepts and resources, understanding care pathways (e.g., administered vs. prescribed).
    *   **Quick check:** "A patient asks, 'What was the last thing they gave me for my infection?' What are two possible `Medication`-related resources, and what distinguishes them?"

## Architecture Onboarding
*   **Component map:** Input (Question + Patient ID) -> Query Generator (Fine-tuned LLM) -> Query Executor (FHIRPath Engine) -> Answer Formatter -> User. An alternative retrieval-first path exists: Input -> Resource Retriever (full bundle) -> LLM Reasoner (free-text answer) -> User.
*   **Critical path:** The safety and efficiency gains depend entirely on the Query Executor step being deterministic and run on trustworthy infrastructure. The LLM's role is reduced to synthesizing a formal query.
*   **Design tradeoffs:** Query-first wins on token efficiency and predictable failure modes (syntax error vs. hallucination) but may sacrifice some accuracy when the LLM can correctly reason over retrieved snippets. SFT data scope trades depth on known patterns for breadth of schema coverage.
*   **Failure signatures:**
    *   **Invalid Syntax:** Executor returns a parse error.
    *   **Resource Profile Error:** Empty list or property-not-found error from executor (e.g., wrong path on `Location`).
    *   **Semantic Misinterpretation:** Executed result matches ground-truth format but answers the wrong clinical intent (e.g., counts total instead of distinct).
    *   **Date Arithmetic Error:** Result off by a specified period due to incorrect relative date calculation.
*   **First 3 experiments:**
    1.  **Baseline Capability Test:** Run the zero-shot query-first pipeline on the Benchmark test split for a base model (e.g., `4o-mini`). Measure accuracy and failure rate to confirm the initial low ceiling (~25-38%) and low failure rate.
    2.  **Architecture Comparison:** Run the same test set with a retrieval-first implementation (ingesting full bundles). Measure token usage variance and accuracy *excluding failures* to reproduce the 391× token gap and the accuracy trade-off.
    3.  **SFT Validation:** Fine-tune a model (e.g., `4o-mini`) on the FHIRPath-QA Large training set. Evaluate on Test 1 (novel paraphrases) to verify the accuracy improvement (~27% to ~70-79%) and the shift in sensitivity to paraphrase perspective.

## Open Questions the Paper Calls Out
*   **Question:** How can LLMs be trained to accurately resolve the semantic ambiguity in patient-authored questions to match performance on clinician-paraphrased queries?
    *   **Basis in paper:** The conclusion states patient-perspective questions "impose a natural performance ceiling" and fine-tuned models consistently underperform on them.
    *   **Why unresolved:** Patient language is inherently vague and lexically diverse; single-turn query generation lacks disambiguation mechanisms.
    *   **What evidence would resolve it:** Implement and evaluate interactive clarification dialogs, measuring if accuracy approaches clinician-phrase levels.
*   **Question:** To what extent can text-to-FHIRPath models generalize to FHIR resource types not seen during training?
    *   **Basis in paper:** Test 3 (resource holdout) shows a performance drop on unseen resources (Location, MedicationAdministration).
    *   **Why unresolved:** Models appear to overfit to training resource schemas, losing base models' broader schema knowledge.
    *   **What evidence would resolve it:** Systematically vary training data diversity (number of resource types) and measure zero-shot accuracy on held-out resources; probe for transferable composable patterns.
*   **Question:** Does the MIMIC-IV on FHIR-based dataset limit generalizability to other clinical settings and real patient-authored questions?
    *   **Basis in paper:** Limitations note the dataset reflects a single institution's ICU data and uses synthetically generated (not real) questions.
    *   **Why unresolved:** Single-institution ICU data may not capture outpatient heterogeneity or true patient information needs.
    *   **What evidence would resolve it:** Curate a multi-institution benchmark with authentic patient questions and diverse resources; evaluate cross-institution performance.

## Limitations
*   Dataset derived from only 100 MIMIC-IV patients, limiting demographic and clinical diversity.
*   Underspecified paraphrasing and query validation procedures block full reproducibility.
*   Results are tied to specific LLM families (OpenAI) and a specific FHIRPath engine; generalizability is uncertain.

## Confidence
*   **Query-first token reduction:** High (concrete, stable measurements).
*   **SFT accuracy boost:** High for OpenAI models on this dataset; Medium for broader architectures.
*   **Patient vs clinician phrasing gap:** Medium (consistent but dataset-specific).
*   **Benchmark as foundation:** Medium (open release invites external validation).
