# CCTU: A Benchmark for Tool Use under Complex Constraints

## Quick Facts
- arXiv ID: 2603.15309
- Source URL: https://arxiv.org/abs/2603.15309
- Reference count: 40
- Primary result: Under strict adherence, perfect solve rate (PSR) < 20% for all models; best (GPT-5.2) at 24.5% overall.

## Executive Summary
CCTU introduces a benchmark to evaluate large language models (LLMs) on tool use under explicit, multi-faceted constraints. It comprises 200 challenging test cases, each with an average of seven constraint types drawn from a 12-category taxonomy spanning resource, behavior, toolset, and response dimensions. Prompts are long (over 4,700 tokens), and an executable constraint validation module enforces step-level compliance during multi-turn interactions, providing corrective feedback. Nine state-of-the-art LLMs were evaluated in both thinking and non-thinking modes. Results reveal severe limitations: the perfect solve rate (PSR) is below 20% for all models, with the best achieving only 24.5%. Over 50% of cases involve constraint violations, particularly in resource and response dimensions. Self-refinement after feedback is weak—the highest correction rate is 65.36% (Claude Opus 4.6), with most models below 60%. These findings highlight substantial gaps in LLMs’ ability to perform constrained tool-use reliably.

## Method Summary
CCTU construction begins with a data source (FTRL) to generate reference trajectories—valid solutions without constraints. A constraint injector then iteratively adds constraints (with 50% probability per step) while an LLM-based filter checks for conflicts, ensuring solvability. The pipeline outputs task context, tool schemas, and automatically generated constraint validation code, followed by human verification for quality assurance. The evaluation harness orchestrates multi-turn interactions: models produce structured outputs ([THOUGHT], [ACTION], [REFLECTION], [FINAL ANSWER]); after each turn, the validation module assesses compliance and returns feedback. Tools are executed locally, and metrics include Solve Rate (SR), Perfect Solve Rate (PSR), per-category violation rates, and self-correction rates. Nine LLMs are queried via API in thinking and non-thinking modes, with three independent runs per configuration to ensure robustness.

## Key Results
- Perfect solve rate (PSR) is below 20% for all evaluated models; the best model (GPT-5.2) achieves 24.5% overall under strict adherence.
- Constraint violations occur in more than 50% of test cases, with particularly high rates in the resource and response dimensions.
- Self-refinement after constraint feedback is limited: the highest correction rate is 65.36% (Claude Opus 4.6), and most models achieve below 60%.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Step-level constraint validation enables precise measurement of compliance during interactive tool use.
- **Mechanism**: An executable module checks every model output against predefined constraints, injecting corrective feedback when violations occur. This creates a closed-loop evaluation that captures adherence throughout execution, not just final task completion.
- **Core assumption**: Constraint violations are detectable via code-based checks at each interaction turn.
- **Evidence anchors**: Abstract mentions "executable constraint validation module that performs step-level validation"; Section 3.2 details the validation module operation; neighboring papers (AGENTIF, LR^2Bench) also emphasize fine-grained validation.
- **Break condition**: If validation code fails to capture all constraint types or introduces false positives, evaluation reliability collapses.

### Mechanism 2
- **Claim**: Controlled constraint expansion maintains solvability while injecting complexity.
- **Mechanism**: Using a reference trajectory from a capable LLM, the pipeline iteratively adds constraints with 50% probability, checking consistency via LLM-based filtering before finalization. This balances diversity and feasibility.
- **Core assumption**: A reference trajectory provides a feasibility anchor that prevents unsolvable constraint combinations.
- **Evidence anchors**: Section 3.2 describes "controlled constraint expansion... with probability of 50%... LLM-based filtering"; Appendix C Algorithm 1 shows the iterative loop; ToolACE-R uses iterative training for tool learning, suggesting similar benefits.
- **Break condition**: If reference trajectories contain errors or filtering fails to catch subtle conflicts, the dataset becomes noisy and potentially unsolvable.

### Mechanism 3
- **Claim**: The four-dimensional taxonomy (resource, behavior, toolset, response) with 12 categories enables comprehensive coverage of real-world constraints.
- **Mechanism**: Each test case averages seven constraint types, forcing models to juggle multiple simultaneous restrictions across planning, execution, and output phases.
- **Core assumption**: These 12 categories capture the most critical constraints encountered in production LLM deployments.
- **Evidence anchors**: Abstract states "grounded in a taxonomy of 12 constraint categories spanning four dimensions"; Section 3.1 enumerates all 12 constraints; neighboring benchmarks (ATLAS, LR^2Bench) align with multi-faceted constraint evaluation.
- **Break condition**: If important constraint types (e.g., security policies, temporal deadlines) are missing, benchmark validity erodes.

## Foundational Learning
- **Tool Calling APIs**: Models must correctly invoke functions with proper parameters to retrieve information. Why needed: The benchmark uses locally executable tools; API misuse directly leads to task failure. Quick check: What happens when a model omits a required parameter or calls a non-existent tool?
- **Multi-Turn Interaction Management**: Tasks span multiple rounds with stateful feedback; models must track constraints across the entire dialogue. Why needed: The evaluation harness runs over many turns, requiring the model to maintain context and decide when to stop. Quick check：How does a model know when to stop calling tools and produce a final answer?
- **Constraint Satisfaction in Sequential Decision-Making**: Models must plan trajectories that honor dependencies (e.g., sequential tool orders, parallel call limits) without explicit demonstrations for each combination. Why needed: Constraints define complex dependencies that the model must reason about implicitly. Quick check: What is the difference between a sequential dependency and a parallel dependency constraint?

## Architecture Onboarding
- **Component map**: Data source (FTRL) → reference trajectory generator → constraint injector → LLM filter → task context generator → constraint validation code generator → human verification loop.
- **Critical path**: Reference trajectory → constraint injection → validation code generation. Any break here yields unsolvable tasks or broken evaluators.
- **Design tradeoffs**:
  - Constraint diversity vs. solvability: More constraints increase difficulty but risk making tasks impossible.
  - Automated generation vs. manual verification: High automation enables scale; manual checks catch edge-case conflicts but are costly.
- **Failure signatures**:
  - Validation module returns false positives/negatives for obvious cases.
  - Models consistently violate the same constraint type across all test cases.
  - Task completion rates near zero even for strongest models, indicating over-constrained instances.
- **First 3 experiments**:
  1. Smoke test: Run a simple rule-based agent to ensure constraint validation code correctly flags known violations.
  2. Solvability sanity check: Execute reference trajectories against the validation module to confirm no false constraint breaches.
  3. Pilot evaluation: Test 2–3 models on a 10-case subset to estimate variance before full runs.

## Open Questions the Paper Calls Out
- **Missing constraint taxonomy coverage**: How to extend the constraint taxonomy to cover missing real-world constraints? Basis: Appendix A explicitly notes the taxonomy is incomplete.
- **Single-source construction limits**: Does single-source construction limit scenario coverage, and how to diversify CCTU? Basis: Appendix A notes reliance on a single data source (FTRL).
- **Sufficient scale of test cases**: Is 200 test cases sufficient for reliable evaluation, or what scale is needed? Basis: Appendix A mentions only 200 cases, raising statistical power concerns.
- **Improving self-refinement**: How to improve LLMs’ self-refinement after constraint violations? Basis: Inferred from results (Abstract, Section 5.3) showing limited self-refinement rates.
- **Inconsistent effects of thinking mode**: Why does thinking mode inconsistently affect performance, and how to optimize it? Basis: Inferred from Section 5.1 and Appendix E, which report exceptions and overthinking cases.

## Limitations
- **Citation void**: Despite strong neighboring benchmarks (FMR > 0.5), CCTU has zero citations, suggesting limited adoption or being too new for academic validation.
- **Construct validity gap**: The 12-category taxonomy completeness is assumed but not externally validated; critical constraint types (e.g., security policies, temporal deadlines) may be missing.
- **Reproducibility barriers**: Dependence on restricted/proprietary models (GPT-5.2, Claude Opus 4.6) and unclear “thinking mode” API specifications hinder exact replication by most researchers.

## Confidence
- **High confidence**: The step-level validation mechanism and empirical results (PSR < 20%, violation rates) are internally consistent and well-documented.
- **Medium confidence**: The taxonomy coverage and controlled constraint expansion’s role in maintaining solvability lack independent cross-benchmark verification.
- **Low confidence**: Long-term impact and adoption prospects due to near-zero citation count and restricted model access.

## Next Checks
- Constraint validator sanity test: Run a deterministic rule-based agent on 50 diverse cases to quantify false positive/negative rates in the validation module.
- Solvability audit: Re-execute all reference trajectories with the validation module to confirm zero violations; flag any cases where the “feasible” baseline fails.
- Thinking mode parity check: For at least two open-weight models (e.g., Llama 3.1 405B), compare outputs with/without explicit reasoning prompts to isolate the effect of the paper’s “thinking mode” toggles.
