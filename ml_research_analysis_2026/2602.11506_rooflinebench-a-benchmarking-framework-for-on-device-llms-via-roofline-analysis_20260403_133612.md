# RooflineBench: A Benchmarking Framework for On-Device LLMs via Roofline Analysis

## Quick Facts
- **arXiv ID:** 2602.11506
- **Source URL:** https://arxiv.org/abs/2602.11506
- **Reference count:** 40
- **Primary result:** Introduces RooflineBench, a framework that uses the Roofline model and the Relative Inference Potential (Φ) metric to characterize on-device LLM inference efficiency across heterogeneous hardware, revealing that sequence length and model depth critically affect operational intensity and that MLA improves OI.

## Executive Summary
RooflineBench provides a systematic approach to evaluate LLM inference performance on diverse hardware platforms by applying the Roofline model. The framework measures achieved performance and memory traffic to compute operational intensity (OI), placing each configuration on a hardware-defined performance envelope. It introduces the Relative Inference Potential (Φ) to quantify the gap between achieved performance and the theoretical ceiling. Empirical evaluation across multiple models, precisions, and edge devices shows that input/output sequence lengths strongly dictate whether inference is memory- or compute-bound, while increasing model depth beyond a few layers degrades OI due to weight streaming bandwidth pressure. Architectural improvements like Multi-head Latent Attention (MLA) consistently increase OI and reduce Φ across hardware. The work highlights the "efficiency trap" where differing hardware ridge points hinder uniform utilization, underscoring the need for hardware-aware model design.

## Method Summary
RooflineBench combines analytical modeling with empirical profiling. First, it characterizes target hardware by measuring peak compute (π) and peak memory bandwidth (β) via synthetic benchmarks. For a given LLM configuration (architecture, precision, sequence lengths), the framework analytically estimates total FLOPs (W) and memory traffic (Q) per token based on model hyperparameters and attention mechanism (with specific formulas). It then runs inference (e.g., via llama.cpp) to measure end-to-end latency (T). Performance is computed as P = W/T, and operational intensity as OI = W/Q. The hardware Roofline is defined by the ridge point OI_r = π/β. The Relative Inference Potential (Φ) is calculated as the Euclidean distance from the measured (OI, P) point to the ridge (or to the compute ceiling if OI ≥ OI_r). This enables cross-hardware comparison and identification of bottlenecks (memory-bound if OI < OI_r, compute-bound otherwise). The framework supports depth sweeps, precision variations, and different attention types to analyze their impact on OI and Φ.

## Key Results
- Inference bottleneck is highly sensitive to sequence pattern: Long-input/short-output (LISO) operates near compute-bound limits, while short-input/long-output (SILO) remains deeply memory-bound.
- Operational intensity peaks at shallow model depths (3–5 layers) and regresses as depth increases due to cumulative weight streaming bandwidth pressure.
- Multi-head Latent Attention (MLA) increases OI by compressing KV cache traffic, reducing Φ across all tested platforms and mitigating the heterogeneity trap.

## Why This Works (Mechanism)
The Roofline model provides a hardware-agnostic efficiency metric by defining a theoretical envelope where attainable performance is the minimum of peak compute (π) and OI × peak bandwidth (β). By calculating OI = FLOPs / memory traffic per token, an LLM's realized throughput can be plotted against this envelope. The Relative Inference Potential (Φ) quantifies the distance to the hardware ceiling, distinguishing whether the system is memory- or compute-bound. The core assumptions are stable hardware limits and accurate analytical FLOPs/memory models. Evidence includes the paper's formal derivation and empirical validation across multiple devices and models, consistent with prior Roofline applications to LLMs.

Sequence length critically determines OI because attention computation scales quadratically with context while weight loading is constant. Longer inputs increase FLOPs spent in attention, raising OI and moving the operating point toward compute-bound. Conversely, long outputs keep OI low, remaining memory-bound. This mechanism is supported by analytical scaling and empirical data showing LISO near the ridge and SILO deep in memory-bound regime.

Increasing model depth beyond a shallow optimum (3–5 layers) reduces OI due to cumulative memory bandwidth pressure from weight streaming. Each added layer requires its weights to be loaded per token during decoding; on bandwidth-limited devices, total data movement eventually outweighs the marginal FLOP gain. The mechanism assumes autoregressive decoding and fixed bandwidth. Evidence includes layer-wise profiling showing OI peaking at 3–5 layers and then declining, while performance may still rise due to amortization of fixed overheads.

## Foundational Learning
- **Roofline model and operational intensity:** The Roofline model defines a hardware's performance ceiling based on peak compute and bandwidth. Operational intensity (OI = FLOPs/Byte) determines whether a kernel is memory- or compute-bound. This concept is fundamental because the entire framework maps LLM execution onto the Roofline to compute Φ. Quick check: Given peak compute 5 TFLOPS, peak bandwidth 200 GB/s, ridge point OI = 5e12 / 200e9 = 25 FLOP/Byte. If decoding OI is 1 FLOP/Byte, attainable performance = min(5 TFLOPS, 1 * 200 GB/s = 200 GFLOPS) = 200 GFLOPS.

- **LLM decoding phases and KV cache:** During autoregressive decoding, each token generation requires loading model weights and reading/writing the KV cache of the current context. The KV cache size depends on sequence length, number of heads, and hidden dimensions, and it significantly impacts memory traffic. Understanding this is necessary to estimate OI and model the effect of attention variants like MLA that compress the KV cache. Quick check: Multi-head Latent Attention (MLA) reduces KV cache size by using a latent dimension instead of per-head keys/values, thus lowering per-token memory traffic and raising OI compared to MHA for the same sequence length.

- **Cross-hardware heterogeneity and "efficiency trap":** Different devices have different ridge points (π/β). A given OI may be compute-bound on a low-ridge device but memory-bound on a high-ridge one, making direct throughput comparisons misleading. Φ helps, but the trap is that no single model can be optimal for all hardware. Quick check: Why can’t we directly compare tokens/s of the same model on Apple M1 Pro (ridge ~25) and RTX 3090 (ridge ~38)? Because the same OI may be on the compute-bound side for M1 Pro but memory-bound for RTX 3090, so the bottleneck differs and the performance is limited by different resources.

## Architecture Onboarding
The framework consists of:
- **Model config module:** Parses architecture (layers, hidden size, heads, attention type, quantization) to compute per-layer FLOPs and KV cache size
- **Hardware profiler:** Measures π (peak compute) and β (peak bandwidth) via synthetic benchmarks
- **Inference telemetry:** Wraps LLM inference engine (llama.cpp) to capture latency and memory usage
- **Roofline engine:** Combines analytical FLOPs/memory with measurements to compute Performance, OI, and Φ; generates plots
- **Dataset aggregator:** Coordinates runs across sequence lengths, precisions, and layer counts

Critical path:
1. Input model definition and hardware specs
2. Profile hardware to get π and β
3. For each configuration (depth, precision, seq-len), run inference, measure latency T and memory Q
4. Compute FLOPs W analytically; then P = W/T, OI = W/Q
5. Compare to Roofline bounds and compute Φ
6. Aggregate and visualize results

Design tradeoffs:
- FLOPs estimation accuracy: Analytical formulas avoid hardware counter overhead but may miss fused kernel optimizations. Tradeoff: purity vs realism.
- Memory traffic approximation: Summing weight size + KV cache is simpler than precise cache/DMA tracking. Tradeoff: usability vs granularity.
- Empirical vs theoretical limits: Using measured π/β increases realism but reduces cross-device ideal comparability.

Failure signatures:
- Unexpected memory-bound regime for high-OI cases (e.g., LISO near ridge but actually far left) suggests inaccurate memory traffic estimate (e.g., missing KV cache) or throttling.
- Non-monotonic OI vs depth curve not appearing at expected depth could indicate caching effects or offloading thrashing.
- Quantization not shifting OI rightward as expected suggests flawed bytes-per-parameter accounting.

First 3 experiments:
1. **Baseline Roofline:** Run a fixed model (e.g., Qwen2.5-1.5B FP16) on Apple M1 Pro across four sequence patterns (SISO, SILO, LISO, LILO). Verify LISO is closest to ridge, SILO is deepest memory-bound, and compute Φ for each.
2. **Depth sweep:** Under a fixed scenario (e.g., LILO), vary layers from 2 to 64. Plot OI vs layers; confirm the arch shape with peak at 3–5 layers and subsequent regression. Also check if overall performance still increases despite OI drop due to amortization.
3. **Attention architecture comparison:** Compare GQA (Qwen2.5), MHA (SmolLM2), and MLA (PLM) at ~1.5B params in FP16 under LISO. Confirm MLA attains higher OI and lower Φ, demonstrating KV compression benefits across hardware.

## Open Questions the Paper Calls Out
- How do emerging attention mechanisms (e.g., linear attention, hybrid sparse-dense variants) beyond MHA, GQA, and MLA impact OI and hardware utilization equity across heterogeneous edge devices?
- Why do theoretical ridge points vary drastically across hardware, and can future edge hardware be co-designed to minimize the resulting "efficiency trap" for a wider range of model architectures?
- What are the precise microarchitectural or memory system reasons behind the non-monotonic OI trend with increasing model depth (peaking at 3–5 layers), and can this regression be mitigated through hardware-aware model scaling or software scheduling?
- How can the Roofline model and Φ be extended to enable fair, cross-regime efficiency comparisons between memory-bound and compute-bound points, which are currently "fundamentally incomparable"?
- How can the Roofline framework be adapted to characterize dynamic, sparse activation patterns of Mixture of Experts (MoE) models during inference, given their stochastic token routing?

## Limitations
- Hardware profiling details for π and β (matrix sizes, warm-ups, precision) are unspecified, risking inconsistent ridge points.
- Memory traffic model for KV cache, particularly for MLA, lacks precise per-token formulas, hindering exact OI computation.
- Memory measurement method per platform (process RSS, nvidia-smi, etc.) is ambiguous, which could cause cross-device comparability issues.
- Depth-sweep model construction method (truncation vs training) is unclear, possibly affecting OI regression observations.

## Confidence
- Roofline/Φ: Medium — theory is solid but depends on precise measurements with unknown methodology.
- Sequence-length bottleneck: High — strong analytical scaling and consistent empirical results.
- Depth OI regression: Medium — plausible but affected by caching and model origin.
- MLA OI boost: High — clear theoretical and empirical support.

## Next Checks
1. Re-profile hardware using standard benchmarks (e.g., STREAM for memory, GEMM for compute) with documented settings and publish multi-run statistics to ensure reproducible ridge points.
2. Measure actual memory traffic via hardware counters (e.g., Intel PCM, NVIDIA Nsight) during inference and compare to analytical Q to validate the memory model.
3. Construct depth-varying models from a single pretrained checkpoint (e.g., by truncating layers) and benchmark to confirm OI regression and rule out artifacts from training different depths.
