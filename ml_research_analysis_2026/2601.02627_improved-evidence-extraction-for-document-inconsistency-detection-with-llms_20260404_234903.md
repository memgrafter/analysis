# Improved Evidence Extraction for Document Inconsistency Detection with LLMs

## Quick Facts
- **arXiv ID:** 2601.02627
- **Source URL:** https://arxiv.org/abs/2601.02627
- **Reference count:** 27
- **Primary result:** The proposed RnR+CF method raises evidence hit rate when correct (EHRC) from 0.669 to 0.757 and evidence precision when correct (EPRC) from 0.319 to 0.383 on GPT-4o, while average evidence coverage ratio (AECR) remains low (0.054 vs. 0.051 for direct prompting), using only ~3 LLM calls on average.

## Executive Summary
This paper tackles the problem of extracting the exact set of contradictory sentences (evidence) from an inconsistent document using large language models. The authors introduce a redact-and-retry (RnR) framework that iteratively removes previously identified evidence and re-prompts the LLM, followed by a constrained filtering (CF) step to refine the final evidence set. Evaluated on the ContraDoc dataset with GPT-4o and LLaMA3.2-90B, the combined RnR+CF approach substantially improves evidence hit rate and precision compared to direct prompting, while keeping the evidence set concise (AECR near baseline). The method requires only a modest increase in LLM calls (about three per document), demonstrating an efficient way to enhance evidence extraction for document-level inconsistency detection.

## Method Summary
The task is to extract all sentences that constitute a contradiction within a document. The study compares three pipelines:
- **Direct Prompting (DP):** A single LLM call with a fixed JSON prompt requesting a binary classification and a list of evidence sentences.
- **Redact‑and‑Retry (RnR):** Begins with a DP call; if the classification is “Yes”, the identified evidence sentences are removed (via approximate TF‑IDF cosine similarity matching ≥0.8) while preserving sentence order. The LLM is re‑prompted on the redacted document, and this cycle repeats until the LLM answers “No”. The final classification is the initial “Yes”; evidence is the union of all rounds.
- **Filtering variants:** After RnR, an optional filter LLM call refines the aggregated evidence. *Constrained Filtering (CF)* must output at least one sentence, thus preserving the original classification. *Unconstrained Filtering (UF)* may return an empty list, flipping the classification to “No” if so. The constrained variant yields the best balance.
All steps use temperature 0 and JSON‑formatted outputs. Metrics (EHR, EHRC, EPR, EPRC, AECR) also rely on the same TF‑IDF similarity for matching predictions to ground truth.

## Key Results
- RnR+CF significantly improves evidence hit rate when correct (EHRC) and evidence precision when correct (EPRC) over direct prompting. For GPT‑4o, EHRC rises from 0.669 to 0.757 and EPRC from 0.319 to 0.383; similar relative gains hold for LLaMA3.2‑90B.
- Average evidence coverage ratio (AECR) stays near DP’s level (e.g., 0.054 vs. 0.051 on GPT‑4o), indicating the filtered evidence set remains concise.
- The approach incurs only a modest increase in LLM calls: about 2.92 retries on average for GPT‑4o, totaling roughly 3 calls per document.

## Why This Works (Mechanism)

### Mechanism 1: Iterative Redaction Improves Hit Rate
The redact‑and‑retry framework improves evidence hit rate by iteratively narrowing the LLM’s focus to remaining inconsistencies. Each retry removes sentences previously flagged as evidence, reducing contextual clutter and making residual contradictions easier to detect. The union of all evidence sets across retries increases the likelihood of capturing all true inconsistent sentences. The core assumption is that the LLM correctly identifies at least one new true evidence sentence per retry, and redaction does not destroy cues needed to detect other inconsistencies. Support appears in the abstract and Section 4; failure conditions include plateau (LLM returns same set) or degradation (redaction removes necessary context).

### Mechanism 2: Constrained Filtering Improves Precision
Constrained filtering increases evidence precision by pruning spurious sentences from the union set while preserving the original classification. The filter call re‑analyzes the candidate sentences and retains only those deemed truly inconsistent; the constraint (output ≥ 1 sentence) prevents the filter from emptying the set and flipping the classification to “No”. The mechanism assumes the LLM can accurately distinguish true from false evidence. Evidence includes abstract/Section 4 descriptions and Table 1’s EPRC improvement. Break conditions: discarding true evidence lowers EHRC; retaining obvious false positives lowers EPRC.

### Mechanism 3: Synergy Balances Metrics
The combination of redact‑and‑retry and constrained filtering yields a balanced improvement: RnR expands recall (but adds false positives, raising AECR) while CF contracts the set back toward precision. The net effect is a modest AECR increase (e.g., 0.051→0.054 for GPT‑4o) alongside significant gains in both hit rate and precision when correct. This synergy depends on the filter being able to prune the extra false positives introduced by RnR without discarding many true positives. Evidence: Section 5.2 and Table 1; failure if filtering is ineffective (high AECR) or over‑prunes (low EHRC).

## Foundational Learning
- **Concept: Document-level inconsistency detection**  
  - *Why needed:* The task differs from sentence‑pair NLI; contradictions can span non‑adjacent sentences in long documents, requiring holistic document reasoning.  
  - *Quick check:* How would you design a prompt to ask an LLM to find self‑contradictions in a multi‑paragraph document without specifying sentence pairs?

- **Concept: Evidence extraction metrics (EHR, EHRC, EPR, EPRC, AECR)**  
  - *Why needed:* These metrics separately evaluate coverage (hit rate) and conciseness (precision, coverage ratio) of extracted evidence, addressing dual goals of correctness and efficiency.  
  - *Quick check:* Why is AECR defined only over positive documents (D⁺) and not all documents?

- **Concept: Iterative LLM calling patterns (redact‑and‑retry)**  
  - *Why needed:* The framework uses multiple LLM calls in a loop, where each call’s output (redacted document) becomes the next input; a form of process supervision for extraction tasks.  
  - *Quick check:* What are the risks of iterative LLM calls (e.g., error propagation, cost) and how does the paper mitigate them?

## Architecture Onboarding

**Component map:**  
- Input processor: splits document into sentences (implicit in Redact).  
- LLM caller: executes prompts for DP, RnR, and filtering steps.  
- Redactor: removes sentences matching any evidence in the current set (TF‑IDF cosine ≥ 0.8) while preserving order.  
- Aggregator: unions all evidence sets from retries.  
- Filter (optional): applies constrained or unconstrained LLM call to the aggregated evidence.  
- Metrics calculator: computes EHR, EHRC, EPR, EPRC, AECR using the same TF‑IDF similarity.

**Critical path (for RnR+CF):**  
1. Initial LLM call on full document → (ŷ¹, bE¹).  
2. While ŷʲ = “Yes”: redact document using bEʲ to obtain xʲ⁺¹, call LLM → (ŷʲ⁺¹, bEʲ⁺¹).  
3. After loop, set ŷ = ŷ¹ and bE = ⋃ bEʲ.  
4. If ŷ = “Yes”, invoke constrained filter on bE to produce final bE.  
(For UF, an empty filter output flips ŷ to “No”.)

**Design tradeoffs:**  
- Cost vs. performance: each retry adds an LLM call; RnR+CF averages ~3 calls vs. 1 for DP.  
- Precision vs. recall: redact‑and‑retry raises recall but lowers precision; filtering restores precision at a slight recall cost.  
- Prompt simplicity: all steps reuse similar JSON prompts; CF differs only by requiring ≥ 1 sentence.

**Failure signatures:**  
- High RUF(+→−|flip) or RCF(+→−|flip) – filter flips true positives to false negatives.  
- Low RCF(Ekept|Efound) – filter discards true evidence found by redact‑and‑retry.  
- AECR rises significantly (e.g., RnR alone ~0.12) – ineffective filtering.  
- Few retries (e.g., LLaMA3‑70B avg 1.41) – LLM may give up early.

**First 3 experiments:**  
1. Main evaluation: compare DP, RnR, and RnR+CF on EHRC, EPRC, AECR across GPT‑4o, LLaMA3.2‑90B, and LLaMA3‑70B.  
2. Filter analysis: contrast constrained vs. unconstrained filter on classification accuracy/TPR and evidence metrics.  
3. Retry dynamics: analyze distribution of number of retries and total evidence sentences per approach/LLM.

## Open Questions the Paper Calls Out
1. **Multi‑contradiction evidence extraction** – ContraDoc contains exactly one inconsistent sentence per positive document, so the method’s ability to retrieve all contradictory sentences in a multi‑contradiction setting is unknown. A dataset with multiple contradictions and metrics like ERR/ERRC would be needed.
2. **Generalization to other datasets** – The study only uses ContraDoc; it is unclear whether gains hold for other document‑inconsistency corpora from different domains. Cross‑dataset validation is required.
3. **Refining the filter step** – Only two simple filter prompts (constrained/unconstrained) are compared. More sophisticated approaches (e.g., confidence scoring, chain‑of‑thought, multi‑agent consensus) might further improve the precision‑recall trade‑off.

## Limitations
- Dataset scope: ContraDoc’s single‑contradiction design limits generalizability to real‑world multi‑contradiction scenarios.
- Reproduction details missing: exact sentence tokenization, TF‑IDF vectorizer configuration (tokenization, n‑grams, stop‑words), and LLM generation parameters (max tokens, stop sequences) are unspecified, risking implementation variance.
- Filter trade‑off: Constrained filtering discards some true evidence (≈15% loss in kept rate), which could be sensitive to prompt wording or model choice.
