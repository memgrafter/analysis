# An LLM-Guided Query-Aware Inference System for GNN Models on Large Knowledge Graphs

## Quick Facts
- **arXiv ID:** 2603.04545
- **Source URL:** https://arxiv.org/abs/2603.04545
- **Reference count:** 40
- **Primary result:** KG-WISE achieves up to 28× faster inference and 98% lower memory usage compared to state-of-the-art accelerators while maintaining or improving accuracy on node classification and link prediction tasks, across both commercial and open-weight LLMs.

## Executive Summary
GNN inference on large knowledge graphs traditionally loads entire models and graphs, causing excessive memory and compute waste even for small, semantically focused queries. This paper introduces KG-WISE, a system that uses an LLM to generate reusable SPARQL query templates that extract compact, task-relevant subgraphs. It then decomposes the trained GNN model into fine-grained components—node embeddings chunked by type and relation-specific parameters—stored in a key-value store, enabling partial loading of only the subgraph-specific parts during inference. Evaluated on six KGs with up to 42 million nodes, KG-WISE delivers up to 28× speedup and 98% memory reduction while preserving or improving accuracy on node classification and link prediction tasks, across both commercial and open-weight LLMs.

## Method Summary
KG-WISE operates in two phases. Offline: Given a task description and KG schema statistics, an LLM generates a SPARQL query template that retrieves a semantically relevant subgraph for that task. A GNN (RGCN) is trained on this subgraph. Post-training, the model is decomposed: node embeddings are chunked by node type and stored in a Zarr key-value store, while relation-specific layer weights are stored separately. Online: For an inference query with a set of target nodes, the template is instantiated to fetch the corresponding subgraph from an RDF engine. Only the embedding chunks for node types present in this subgraph, along with the full weights, are loaded into sparse tensors. A query-specific compact model is instantiated and a forward pass is executed over the subgraph, yielding predictions with minimal memory and compute overhead.

## Key Results
- Inference speedup up to 28× compared to state-of-the-art GNN accelerators.
- Memory usage reduced by up to 98%.
- Accuracy on node classification and link prediction tasks is maintained or improved across six benchmark KGs, using both commercial and open-weight LLMs.

## Why This Works (Mechanism)
**Mechanism 1:** LLM-generated SPARQL templates extract task-relevant subgraphs, avoiding load of irrelevant nodes/edges. The system prompts an LLM with the task description and KG schema statistics to generate a constrained SPARQL template that retrieves only semantically relevant triples within K hops of target nodes. This template is reused at inference, producing a compact subgraph. Core assumption: An LLM can reliably map high-level task semantics to precise KG relations/predicates, producing a valid, reusable SPARQL template. Evidence: Abstract and Section III describe the LLM-guided procedure; related work supports LLM-to-SPARQL feasibility. Break condition: LLM hallucinates invalid relations or fails to cover all task-relevant schema elements, leading to incomplete subgraphs and accuracy loss.

**Mechanism 2:** Decomposing the GNN model into type-chunked embeddings stored in a KV store enables partial loading. Post-training, embeddings are separated by node type, chunked row-wise, and stored in a Zarr KV store. During inference, only chunks for node types present in the extracted subgraph are loaded. Core assumption: Non-target node embeddings dominate model size (>95%) and their access pattern is predictable by node type. Evidence: Abstract and Section IV describe decomposition; Table III shows embeddings account for ~99% of model size. Break condition: Subgraph contains many node types, causing many small chunk loads that erode gains.

**Mechanism 3:** Query-aware model instantiation using sparse tensors tailors computation to the subgraph structure. Given subgraph SG, the system loads only convolutional weights (full) and embeddings for nodes in SG. These are materialized into a sparse tensor where only positions for SG nodes are populated, feeding a forward pass that aggregates only over SG edges. Core assumption: SG is sufficiently smaller than full KG such that sparse ops and reduced data movement outweigh overheads. Evidence: Abstract and Section V describe sparse tensor construction; Equation 3 shows aggregation confined to SG. Break condition: For very dense queries, SG becomes large, making sparse tensor overhead negate benefits over dense pass.

## Foundational Learning
**Concept: Relational Data & SPARQL**  
Why needed here: The KG is stored in an RDF engine, and subgraphs are extracted via SPARQL queries. Understanding triple patterns, OPTIONAL, and UNION is key to interpreting the query templates.  
Quick check question: What does a SPARQL `UNION` of two basic graph patterns (BGPs) do, and why might an LLM use it to build a multi-relation template?

**Concept: GNN Message-Passing Complexity**  
Why needed here: The efficiency claim hinges on reducing the O(LN²F) cost of full-graph aggregation. One must understand how neighbor aggregation scales with nodes (N) and features (F).

**Concept: Sparse vs. Dense Tensor Operations**  
Why needed here: The system chooses aggregation based on subgraph sparsity and constructs sparse embedding tensors. Knowing the overhead crossover point between sparse and dense ops is crucial for the "dynamic selection" claim.

## Architecture Onboarding
Component map: LLM Query Generator (produces SPARQL template QT) -> RDF Engine (stores KG, executes SPARQL) -> GNN Training Manager (trains RGCN on subgraph) -> Decomposition Manager (splits model into weights and type-chunked embeddings in Zarr KV store) -> Subgraph Manager (instantiation of QT during inference) -> Instantiation Manager (loads relevant KV chunks and weights into sparse tensors) -> Prediction Manager (runs forward pass).

Critical path (inference): Inference query with target nodes TN -> Subgraph Manager instantiates QT and fetches subgraph SG from RDF Engine -> Instantiation Manager loads weights and embedding chunks for node types in SG -> builds sparse model fM -> Prediction Manager runs forward pass on fM with SG -> outputs predictions.

Design tradeoffs:
- LLM choice vs. subgraph quality: Larger proprietary LLMs may generate more accurate templates but add cost/API dependency; open-weight models are cheaper but may miss subtle relations.
- KV chunk size: Smaller chunks reduce wasted load but increase I/O calls; larger chunks reduce calls but load more unused data per request.
- Sparse vs. dense aggregation: Dynamic selection depends on hardware (GPU favors dense; CPU with limited RAM favors sparse) and subgraph density.

Failure signatures:
- Low accuracy: LLM template missing critical relations → incomplete subgraph → model lacks context.
- High memory/time despite KG-WISE: Subgraph unexpectedly large/dense → many KV chunks loaded → sparse overhead dominates.
- Slow template generation: LLM latency or validation loops during offline phase.
- Memory blow-up during instantiation: SG dense or chunk size too large → loads many irrelevant chunks.

First 3 experiments:
1. Validate subgraph extraction: For fixed tasks, compare size of KG-WISE subgraph (using different LLMs) vs. KG-TOSA baseline and oracle subgraph. Measure node/edge count overlap.
2. Measure KV loading efficiency: Instrument KV store to log chunk loads. Vary |TN| and plot total chunks loaded vs. total chunks existing to confirm sub-linear scaling.
3. Stress sparse tensor boundary: Construct artificial queries with very dense SG. Compare time/memory of sparse vs. forced-dense instantiation to identify population density where sparse becomes liability.

## Limitations
- Template generation reliability: LLM may hallucinate invalid relations or fail to cover all task-relevant schema elements, leading to incomplete subgraphs and accuracy loss.
- Storage and access overheads: For queries spanning many rare node types, I/O overhead from loading many small KV chunks could erode gains; optimal chunk size is not studied.
- Subgraph encoding fidelity: Process for mapping SPARQL results to embedding chunks (Algorithm 3 steps 5-7) is underspecified; mismatch could cause silent failures.

## Confidence
- Feasibility of type-based decomposition and sparse tensor usage: High.
- LLM template reliability for arbitrary KG schemas and tasks: Medium.
- Assumption that query subgraphs are consistently sparse enough for sparse ops to win: Medium.

## Next Checks
1. Template quality stress test: For 50 random target node sets across all six KGs, measure subgraph size distribution from LLM-generated templates. Identify if size distribution is right-skewed (some queries massive).
2. KV store I/O profiling: Instrument to log every chunk read during inference. For increasing query batch sizes, plot total chunks loaded vs. total unique node types in all subgraphs. Linear relationship indicates break condition; sub-linear validates clustering assumption.
3. Encoding consistency audit: Introduce a schema change (e.g., rename predicate URI) after training but before inference. Run a standard query; expect error when mapping relations to weight matrices. Silent incorrect loading would indicate flaw in ID mapping pipeline.
