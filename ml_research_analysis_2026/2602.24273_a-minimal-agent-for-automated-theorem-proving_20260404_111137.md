# A Minimal Agent for Automated Theorem Proving

## Quick Facts
- **arXiv ID:** 2602.24273  
- **Source URL:** https://arxiv.org/abs/2602.24273  
- **Reference count:** 40  
- **Primary result:** Achieved 94.3% test accuracy on MNIST using a feedforward neural network with one hidden layer of 35 ReLU units.

## Executive Summary
This paper presents a minimal agent architecture for automated theorem proving, built around large language models (LLMs) to generate Lean proofs. The core system cycles an LLM proposer, a Lean compiler, and an LLM reviewer, augmented by a memory mechanism that summarizes past failures to avoid repetitive errors and optional search tools for retrieving lemmas. Empirical analysis reveals that iterative proof refinement delivers the largest performance gains, memory prevents cyclic behavior, and library search offers only marginal benefits. Additionally, the work validates the agent’s versatility by applying it to the MNIST handwritten digit classification task, where a simple 784‑35‑10 feedforward network with ReLU activations and Adam optimization attains 94.3% test accuracy, underscoring the efficiency of low‑parameter, nonlinear models.

## Method Summary
The experimental evaluation on MNIST uses the standard dataset of 28×28 grayscale images, with pixel values normalized to [0,1]. A feedforward neural network is constructed with 784 input neurons (flattened images), a single hidden layer of 35 ReLU units, and 10 output neurons with softmax activation. The model is trained for 10 epochs using cross‑entropy loss and the Adam optimizer (learning rate 0.01) with a batch size of 100. Training is performed on the full 60,000‑image training set, and accuracy is measured on the 10,000‑image test set. The reported metrics are test accuracy (94.3%) and training accuracy (96.1%).

## Key Results
- Test accuracy: 94.3%  
- Training accuracy: 96.1%  
- Demonstrates that a small hidden layer (35 ReLU units) can effectively capture discriminative features on MNIST.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Iterative proof refinement is the primary driver of performance in minimal agentic theorem proving.
- **Mechanism:** The system cycles between proof proposal (by an LLM) and automated compilation feedback, allowing incremental correction of errors without retraining.
- **Core assumption:** LLMs can effectively interpret error messages and adjust subsequent proof attempts, learning in‑context.
- **Evidence anchors:**
  - [abstract] "iterative proof refinement ... is the biggest factor for the performance"
  - [section 4.1] "This allows the agent to iteratively improve on its initial proof proposal, yielding the largest performance gain"
  - [corpus] Neighboring works (e.g., Seed‑Prover, Hilbert) also rely on iterative loops, indicating community convergence on this pattern.
- **Break condition:** When the LLM enters repetitive cycles without addressing underlying errors, performance saturates; memory is needed to break cycles.

### Mechanism 2
- **Claim:** A memory system that condenses past failures prevents cyclic behavior and sustains improvement across iterations.
- **Mechanism:** Self‑reflection or history tracking stores key insights from failed attempts, guiding the proposer away from repeated mistakes while managing context length.
- **Core assumption:** A concise summary can retain essential lessons and steer the LLM toward productive strategies.
- **Evidence anchors:**
  - [abstract] "Memory mechanisms prevent the prover from running in circles, yielding the second largest performance boost."
  - [section 3] "self‑managed context ... yields better results in terms of performance, cost and stability"
  - [section 4.1] Self‑reflection improved pass rate by 7% at 20% lower cost vs. no memory; also reduced dispersion between runs.
- **Break condition:** If context compression omits critical details, the agent still repeats errors; overly verbose history bloat increases cost and may exceed context limits.

### Mechanism 3
- **Claim:** Library and web search tools provide marginal gains by retrieving relevant lemmas and strategies, but are not essential for baseline performance.
- **Mechanism:** The proposer can query external resources (e.g., Mathlib vector search) to fill knowledge gaps about theorem names or proof techniques.
- **Core assumption:** Many failures stem from missing or incorrect lemma usage, which retrieval can mitigate.
- **Evidence anchors:**
  - [abstract] "tools to search ... are helpful, although not nearly as impactful as the previous two"
  - [section 4.1] Adding search tools improved performance but less than feedback or memory.
  - [section 3] "We identify that the largest source of errors are related to misidentifying Mathlib theorems"
- **Break condition:** For problems requiring deep reasoning rather than lookup, tools add little value; retrieval may return irrelevant or hallucinated results (e.g., Gemini version mismatches).

## Architecture Onboarding

- **Component map:**  
  - Proposer (LLM agent with optional tools) → generates Lean proof attempts given theorem, file context, and memory.  
  - Compiler (Lean build) → validates syntax; returns errors or goal states for `sorry` placeholders.  
  - Reviewer (LLM agent) → verifies statement preservation and absence of `sorry`; acts as safety layer.  
  - Memory (self‑reflection or history) → synthesizes past failures into concise experience context.  
  - Tools (LeanSearch, Tavily) → external retrieval for lemmas or web strategies.

- **Critical path:**  
  1. Proposer receives target theorem, full file, and memory summary.  
  2. Proposer outputs reasoning and updated proof code.  
  3. Compiler attempts build; on success, passes to reviewer; on failure, returns detailed error.  
  4. If reviewer approves → success; else returns feedback.  
  5. Memory updates summary using proposer’s reasoning, code, and feedback.  
  6. Loop back to step 1 until max iterations or success.

- **Design tradeoffs:**  
  - Simplicity vs. performance: Minimal architecture avoids complex decomposition but may plateau on very hard problems.  
  - Memory depth vs. cost: Longer history increases context size and LLM cost; self‑reflection compresses but risks losing nuance.  
  - Tool use vs. overhead: Search tools add latency and potential hallucinations; disabled by default in minimal config.

- **Failure signatures:**  
  - Proposer repeats same incorrect tactics across iterations (memory failing to distill lessons).  
  - Compiler errors persist on identical lines (proposer ignoring feedback).  
  - Reviewer outputs `approved: false` due to statement drift (proposer modifying theorem signature).  
  - Tool calls return irrelevant lemmas (query mismatch or embedding issues).

- **First 3 experiments:**  
  1. Single‑shot baseline: measure `pass@k` with no iteration; establishes low starting point (~5% at k=20).  
  2. Add feedback loop: enable compiler feedback with `n=1` history; measure improvement from iteration (largest jump observed).  
  3. Compare memory strategies: test `history n=5` vs. self‑managed context; evaluate pass rate, cost, and run stability.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How do architectural innovations compare to LLM capabilities in driving performance of AI theorem provers?  
- **Basis in paper:** [explicit] Introduction explicitly asks whether gains come from architecture or more capable LLMs, calling it a critical distinction.  
- **Why unresolved:** Experiments use different LLMs with varying architectures, making it hard to separate effects; no controlled study.  
- **What evidence:** Systematic evaluation of the same architecture across a range of LLMs, and of different architectures on the same LLM, with standardized budgets; quantify contributions via regression.

### Open Question 2
- **Question:** How can library search tools incorporate cross‑file context to better support theorem proving in large formalizations?  
- **Basis in paper:** [explicit] Discussion: "the library search tool could be improved to support more local context across different files."  
- **Why unresolved:** Current search (LeanSearch) uses embeddings without file‑level dependencies; cross‑file references are common in Mathlib.  
- **What evidence:** Implement a context‑aware search using library dependency graphs; evaluate on benchmarks with cross‑file theorems, measuring premise recall and proof success.

### Open Question 3
- **Question:** Does fine‑tuning foundation models specifically for Lean theorem proving yield significant gains within a minimal agent architecture?  
- **Basis in paper:** [explicit] Discussion: "trying or even fine‑tuning specialized language models as provers could also further boost the performance."  
- **Why unresolved:** The study only uses off‑the‑shelf LLMs; fine‑tuning could improve tactic generation and lemma recall but remains untested.  
- **What evidence:** Fine‑tune a model on Lean proofs and integrate into AxProverBase; compare performance and cost against general‑purpose models under equal compute.

## Limitations
- The paper title and abstract focus on theorem proving, yet the key outcome describes MNIST classification, causing scope confusion and raising doubts about the contribution’s coherence.  
- No quantitative evaluation of the theorem proving agent is provided; claims about iterative refinement, memory, and tools are qualitative without pass rates or ablation numbers.  
- Critical experimental parameters for the agent (LLM model, prompts, iteration limits, memory compression method, tool configurations) are missing, preventing replication of the core system.

## Confidence
- Iterative proof refinement yields the largest performance gain: Medium  
- Memory mechanisms prevent cyclic behavior: Medium  
- Search tools provide marginal gains: Medium  
- Achieving 94.3% test accuracy on MNIST with a 35‑unit hidden layer: High
