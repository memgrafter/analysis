# Fault-Tolerant Evaluation for Sample-Efficient Model Performance Estimators

## Quick Facts
- **ArXiv ID:** 2602.07226  
- **Source URL:** https://arxiv.org/abs/2602.07226  
- **Reference count:** 17  
- **Primary result:** A fault‑tolerant evaluation framework (FT‑Eval) with automatic tolerance selection resolves the 73.3% conflict rate between RMSE and p‑values and detects systematic bias missed by RMSE.

## Executive Summary
This paper addresses the failure of traditional evaluation metrics (RMSE and p‑values) for sample‑efficient model performance estimators in low‑variance settings, where RMSE masks persistent bias and p‑values become hypersensitive to negligible deviations. The proposed solution, FT‑Eval, introduces an adjustable tolerance level ε and uses two one‑sided t‑tests to assess whether an estimator’s performance lies within a practically acceptable interval around the ground truth. An automatic algorithm selects the minimal discrimination margin δ to dynamically compute ε based on each estimator’s variance. Experiments across 30 dataset‑budget configurations show that RMSE and p‑values conflict in 73.3% of cases; FT‑Eval yields consistent evaluations by jointly bounding bias and variance, exemplified by identifying bias in Active Testing on MMLU‑Pro Physics that RMSE missed.

## Method Summary
FT‑Eval replaces perfect unbiasedness testing with a fault‑tolerant interval test: for each estimator and labeling budget, it computes a tolerance ε = δ + t_{α,N−1} · (s/√N), where s is the sample standard deviation from N runs, and δ is a discrimination margin. Two one‑sided t‑tests (TOST) check whether the mean estimate lies within [θ*−ε, θ*+ε]. An automatic algorithm (Algorithm 1) performs binary search over δ ∈ [0,1] to find the smallest δ that produces different pass/fail outcomes between two competing estimators (e.g., Active Testing vs. Random Sampling) across budgets. This dynamic ε adapts to each estimator’s variance, ensuring fair comparison and resolving the trade‑off where RMSE hides bias and p‑values overreact in low‑variance regimes.

## Key Results
- RMSE and p‑values conflict in 73.3% of 30 dataset‑budget configurations.
- FT‑Eval with auto‑selected δ distinguishes estimators by jointly bounding bias and variance.
- On MMLU‑Pro Physics, FT‑Eval detects systematic bias in Active Testing that RMSE missed; Random Sampling passes earlier under δ = 0.0078.

## Why This Works (Mechanism)
FT‑Eval succeeds through three interconnected mechanisms:

1. **Tolerance‑Bounded Hypothesis Testing**  
   The framework tests whether the estimator’s mean lies within an interval [θ*−ε, θ*+ε] instead of requiring zero bias. Using two one‑sided t‑tests, it enforces |Bias| + t_{α,N−1}·√(Var/N) < ε, which explicitly bounds the combined effect of bias and scaled variance. This prevents hypersensitivity in low‑variance settings (where p‑values become tiny) and bias masking in high‑variance settings (where RMSE can be low despite substantial bias).

2. **Automatic Tolerance Calibration**  
   Algorithm 1 automatically selects the minimal discrimination margin δ* via binary search. The tolerance εₖ = δ* + t_{α,N−1}·sₖ/√N adapts to each estimator’s sample standard deviation sₖ at budget k, ensuring fair comparison across estimators with different variance profiles. The search terminates when the smallest δ yields distinct pass/fail patterns between estimators.

3. **Conflict Resolution via Joint Bias‑Variance Bounding**  
   By separating bias magnitude and variance scale through ε, FT‑Eval resolves the conflict between RMSE (which conflates bias² and variance) and p‑values (which scale as |Bias|/√Var). When variance is low, the bias must be very small to pass; when variance is high, ε relaxes to avoid rejecting adequately accurate estimators. This yields consistent evaluations across variance regimes.

## Foundational Learning
- **Bias‑Variance Decomposition**  
  *Why needed:* Understanding why MSE/RMSE fails requires knowing MSE = Bias² + Variance; variance can decrease while bias stays constant, making MSE misleadingly low.  
  *Quick check:* If an estimator’s variance halves but bias stays the same, does its MSE improve? Should we prefer it over one with higher variance but zero bias?

- **One‑Sided vs Two‑Sided Hypothesis Testing**  
  *Why needed:* FT‑Eval uses two one‑sided tests (TOST) to check equivalence within ε, unlike traditional two‑sided tests that detect any difference.  
  *Quick check:* Why does a two‑sided p‑value become very small when variance is low, even if the actual difference from θ* is trivial?

- **Sample‑Efficient Estimation (Active Testing)**  
  *Why needed:* The evaluated estimators (Active Testing, Random Sampling) are sample‑efficient; Active Testing reduces variance via selective sampling, creating the low‑variance regimes where traditional metrics fail.  
  *Quick check:* How does active testing achieve lower variance than random sampling, and why might this introduce bias?

## Architecture Onboarding
- **Component map:** Estimator (AT/RS) -> Repeated Executor -> Statistical Aggregator -> FT‑Eval Tester; Auto‑δ Tuner controls FT‑Eval Tester’s ε and searches δ.  
- **Critical path:** For each (estimator, budget k): run N times -> compute sample mean ¯θₖ and sample std sₖ -> if auto‑δ, compute ε = δ + t_{α,N−1}·sₖ/√N -> run two one‑sided t‑tests -> record pass/fail. Auto‑δ iterates over δ until distinction found.  
- **Design tradeoffs:**  
  - δ vs ε: smaller δ yields stricter ε (risk both failing), larger δ more lenient (risk both passing); auto‑δ seeks minimal distinguishing δ.  
  - N (runs): larger N reduces uncertainty in sₖ but increases computational cost; paper uses N=100.  
  - Adaptive ε: varies by estimator and budget via sₖ, ensuring fair comparison when variances differ.  
- **Failure signatures:**  
  - No discrimination: algorithm returns Null (estimators behave identically across all δ).  
  - Overly strict ε: both estimators fail at all budgets (δ too small).  
  - Overly permissive ε: both estimators pass immediately (δ too large).  
- **First 3 experiments:**  
  1. Replicate Table 1: compute p‑value and RMSE for Active Testing vs Random Sampling on 20 Newsgroup at budgets {20,60,80}; observe conflict (p‑value rejects AT but RMSE favors AT).  
  2. FT‑Eval with fixed δ=0: run on Physics dataset; expect both estimators to fail most budgets, illustrating necessity of non‑zero δ.  
  3. Auto‑δ validation: implement Algorithm 1 on Physics; verify δ* = 0.0078 and that Random Sampling passes FT‑Eval earlier than Active Testing.

## Open Questions the Paper Calls Out
1. Does the auto‑selection algorithm (Algorithm 1) provably converge to the minimal discrimination margin δ* that distinguishes two estimators, and how do factors like N and discretization step affect its stability? The paper provides no theoretical guarantees or convergence analysis.
2. Does using a data‑dependent tolerance ε = δ + t_{α,N−1}·s/√N invalidate the hypothesis test interpretation by making the null hypotheses random and potentially inflating type I error? The framework does not address whether it controls the nominal significance level α.
3. Can FT‑Eval be applied to performance metrics other than accuracy (e.g., F1, AUC, BLEU) where the estimator may have non‑normal, bounded, or complex distributions, and where a simple bias‑variance decomposition may not hold? Experiments are limited to accuracy for classification and multiple‑choice QA.

## Limitations
- Exact implementation of `Run(E,N,k)` for LLM‑based estimators (grouping, priors, sampling) is underspecified, hindering exact replication.
- The framework assumes users can meaningfully set tolerance ε; mis‑specification may lead to false accept/reject decisions.
- Auto‑δ may return null if estimators are indistinguishable across all δ, leaving the comparison unresolved.
- Evaluation covers only 30 dataset‑budget configurations; broader generalizability is unknown.
