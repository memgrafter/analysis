# A Guide to Large Language Models in Modeling and Simulation: From Core Techniques to Critical Challenges

## Quick Facts
- **arXiv ID**: 2602.05883
- **Source URL**: https://arxiv.org/abs/2602.05883
- **Reference count**: 40
- **Primary result**: LLMs are often misapplied in modeling and simulation, leading to suboptimal outcomes; evidence-based guidance on prompt design, temperature tuning, and knowledge augmentation (RAG/LoRA) is needed, with emphasis on using LLMs as translators to existing tools rather than direct replacements.

## Executive Summary
This guide synthesizes empirical findings on using large language models (LLMs) for modeling and simulation (M&S), addressing common misconceptions that undermine performance. It provides concrete, evidence-based recommendations across three core areas: prompt design, hyper-parameter tuning (especially temperature), and knowledge augmentation techniques (retrieval-augmented generation, fine-tuning). Key results demonstrate that seemingly minor choices—such as representing a model as a graph versus linear text—can drastically affect accuracy, and that optimal temperature settings are task- and model-specific, with zero temperature not guaranteeing determinism. The guide stresses rigorous evaluation protocols, including factorial designs to quantify non-determinism, and advocates for a "translator" paradigm where LLMs interface with established M&S tools instead of attempting to replace them.

## Method Summary
The paper supports its conclusions through empirical experiments and systematic literature review. A central replication study evaluates GPT‑3.5 Turbo on generating readable explanations of conceptual models. A dataset of textual model descriptions (15–20 sentences each) is prepared. For each model, the first 5 or 10 sentences are used as context. Across temperature values {0.0, 0.25, 0.5, 0.75, 1.0}, the LLM generates an explanation, which is scored for readability (using an unspecified standard metric, likely Flesch Reading Ease). Each condition is repeated 5 times to average out variance. Analysis identifies the temperature that maximizes readability per context size. The broader evidence base draws from 40 referenced studies, comparing techniques like RAG, LoRA, and different model representations across diverse M&S tasks.

## Key Results
- Model representation format causes large accuracy differences: PaLM 62B achieved 53.8% vs. 19.8% when inputs were structured as graphs versus linear text.
- Optimal temperature is task- and model-dependent; setting temperature to zero does not ensure deterministic outputs.
- Retrieval-augmented generation (RAG) can degrade performance—e.g., NetLogo code generation quality worsened with added context.
- Non-determinism arises from multiple sources (sampling, system noise, model updates); its impact can be quantified via factorial experimental designs.

## Why This Works (Mechanism)
The recommendations derive from empirical identification of sensitive leverage points in LLM‑M&S pipelines. Temperature controls the randomness in token sampling, directly affecting the trade‑off between creative fluency and deterministic coherence; its optimum varies because different tasks (e.g., explanation vs. code generation) have differing tolerances for variation. Model representation matters because LLMs process structured inputs (graphs) and unstructured text via different internal pathways; some architectures capture relational data better in non‑linear formats. RAG may hurt performance if retrieved context is noisy or if the LLM struggles to integrate external information without over‑reliance or contradiction. Non‑determinism is inherent to LLM inference and can be isolated by factorial designs that partition variance attributable to temperature, context, and random seeds.

## Foundational Learning
- **Prompt design**: Needed to structure inputs for accurate M&S outputs. *Quick check*: Compare outputs for a task using direct, role‑based, and chain‑of‑thought prompts; measure consistency and correctness.
- **Hyper‑parameter tuning (temperature)**: Needed to balance determinism and creativity per task. *Quick check*: Run a coarse temperature sweep (0.0, 0.5, 1.0) on a sample task; assess output stability and relevance.
- **Knowledge augmentation (RAG)**: Needed to inject current or domain‑specific knowledge. *Quick check*: Add a relevant retrieval passage to a prompt; check if output accuracy improves or degrades on a held‑out case.
- **Fine‑tuning (LoRA)**: Needed to adapt model behavior persistently. *Quick check*: Apply LoRA on a small dataset for a specific M&S pattern; test generalization to similar but unseen patterns.
- **Model representation**: Needed because LLMs encode structured vs. textual data differently. *Quick check*: Express the same model in graph (adjacency list) and plain text; compare LLM output accuracy.
- **Non‑determinism quantification**: Needed to separate signal from noise in evaluations. *Quick check*: Generate 10 replicates at fixed temperature; compute coefficient of variation for your metric.

## Architecture Onboarding
`User Task -> Prompt Template -> LLM API -> Output Parser -> M&S Tool/Evaluation`
- **Critical path**: Prompt design → LLM generation → Output parsing. Failures in any step propagate; prompt engineering is especially pivotal.
- **Design tradeoffs**: RAG offers up‑to‑date knowledge but introduces retrieval noise; fine‑tuning stabilizes behavior but risks overfitting and requires data. High temperature aids exploration but harms reproducibility; zero temperature may still yield variance due to system non‑determinism.
- **Failure signatures**: Large output variance across replicates (non‑determinism); sudden drops in accuracy when adding RAG context; LLM refusals or off‑topic generations for certain prompts; inability to preserve structural relationships (e.g., causality) from input to output.
- **First three experiments**:
  1. Optimize temperature and context window for readability of conceptual model explanations (as in the reproduction study).
  2. Compare accuracy of the same M&S artifact when represented as a graph (e.g., edge list) versus linear text description.
  3. Measure the impact of RAG on a code generation task (e.g., NetLogo) by varying retrieval source quality and relevance.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: Under what specific M&S task conditions does a reasoning-enabled LLM (with medium/high reasoning settings) perform worse than a non-reasoning configuration, and what signals (e.g., refusals) indicate that reasoning is detrimental?
- **Basis in paper**: [explicit] The reflection section explicitly asks to compare results under 'no reasoning' vs. 'low reasoning' and notes that "results may even differ in whether the LLM is willing to engage with the task," treating refusals as a signal.
- **Why unresolved**: The paper states that "reasoning is not always better" but does not provide a framework or empirical mapping of task characteristics to optimal reasoning levels. The interaction between reasoning depth and guardrails (e.g., increased refusals at medium reasoning for GPT-5) is noted as an observed phenomenon requiring systematic investigation.
- **What evidence would resolve it**: A factorial experimental design across diverse M&S tasks (e.g., conceptual modeling, code generation, scenario synthesis) that varies reasoning levels and logs engagement rates, output quality metrics, and refusal patterns. Controlled studies isolating the effect of reasoning from other variables (temperature, prompt structure) are needed.

### Open Question 2
- **Question**: Which facets of 'openness' (beyond weight accessibility) are most critical for ensuring methodological rigor and trust in M&S workflows that rely on fine-tuning open-weight LLMs?
- **Basis in paper**: [explicit] The reflection section references Widder et al.'s multi-faceted view of openness and asks: "Which components of an LLM can meaningfully be made open, and which cannot?" It then asks modelers to consider which forms of openness remain relevant even with local weights.
- **Why unresolved**: The paper critiques the vague use of 'open' but does not define a prioritized set of openness criteria (e.g., reproducible training data, documented filtering, auditability of safety fine-tuning) for M&S contexts. The trade-offs between local deployment benefits and potential loss of provider-side governance/updates are not resolved.
- **What evidence would resolve it**: A comparative analysis of fine-tuning experiments across different "open" models (e.g., Llama vs. Falcon) that tracks not just performance but also reproducibility of safety behaviors, consistency across fine-tuning runs, and the ability to audit or modify alignment. A survey of M&S practitioners on which openness attributes they actually rely on would also clarify priorities.

### Open Question 3
- **Question**: At which stage(s) of a Retrieval-Augmented Generation (RAG) pipeline do LLMs currently introduce the most significant errors or inefficiencies when applied to M&S tasks, and how does this vary with domain structure (e.g., formal semantics vs. narrative descriptions)?
- **Basis in paper**: [explicit] The reflection section on "LLM for RAG for LLM" directs readers to a survey and asks: (i) at which stage of the RAG pipeline does the LLM intervene? (ii) What information does the LLM use? This highlights a gap in understanding the LLM's role *within* RAG systems for M&S.
- **Why unresolved**: The paper reviews RAG usage in M&S (Table 1) but notes that "the practice so far is more a matter of 'we chose a retrieval method and used it' rather than optimized." It identifies issues like noisy retrieval, integration problems, and over-reliance on contextual knowledge, but does not pinpoint which pipeline stage (query transformation, retrieval, context construction, generation) is the primary bottleneck for M&S-specific data (e.g., simulation logs, conceptual models).
- **What evidence would resolve it**: Ablation studies on RAG pipelines for specific M&S tasks that instrument each stage (e.g., logging query reformulations, retrieved chunk relevance scores, context construction heuristics) and measure their individual contribution to final output accuracy and fidelity. Comparative experiments across domains (industrial semantics vs. social simulation narratives) would reveal structural dependencies.

### Open Question 4
- **Question**: How do multimodal LLMs' internal representations of structured M&S artifacts (e.g., simulation output images, UML diagrams) differ from their text-based understanding, and what are the failure modes when visual inputs replace textual descriptions of the same model?
- **Basis in paper**: [explicit] The discussion section states multimodal LLMs "can process images, audio, or video" but notes "a limited use... so far" and that "results can be mixed." It explicitly says "As multimodal models mature... such approaches merit renewed attention and systematic re-evaluation in future M&S research."
- **Why unresolved**: The paper cites one study where video inputs had "little impact" and text was "most robust," but this is based on early models. The mechanisms by which multimodal models encode spatial, temporal, or relational structure from visuals (vs. linear text) and how that affects downstream simulation reasoning are not understood. The potential for semantic drift when converting visual model elements to text prompts is an un quantified risk.
- **What evidence would resolve it**: Controlled experiments presenting identical M&S content (e.g., a causal loop diagram, a simulation state snapshot) in text-only, image-only, and multimodal inputs to state-of-the-art multimodal LLMs. Metrics should include structural fidelity (e.g., correct interpretation of graph topology from an image), consistency with ground-truth model semantics, and sensitivity to image quality/format. Probing studies of attention patterns could reveal whether visual and textual pathways are integrated meaningfully.

### Open Question 5
- **Question**: For which classes of persistent, systematic errors in LLM-generated conceptual models (e.g., temporal misalignment, vague constructs, inconsistent terminology) does approximate unlearning (e.g., through LoRA-based editing) provide a more effective and stable remedy than knowledge augmentation (e.g., RAG, prompt engineering), and what are the trade-offs in terms of model generalizability and safety?
- **Basis in paper**: [explicit] The discussion introduces "design by subtraction" and "unlearning" as alternatives to augmentation. It references a study [99] showing "each essential aspect [of conceptual modeling] was violated by at least one well-known LLM" and notes that unlearning methods "remain largely untested in M&S settings." It explicitly contrasts patching (addition) with deliberate forgetting (subtraction).
- **Why unresolved**: While the paper advocates for unlearning to remove problematic associations, it does not classify which error types are amenable to unlearning vs. augmentation. For example, can unlearning fix a model's tendency to reverse causality, or is that better addressed via RAG with curated references? The risks of destabilizing the model or impairing fairness through unlearning are noted but not mapped to M&S error categories.
- **What evidence would resolve it**: A comparative study on a benchmark of conceptual modeling errors. For each error class (e.g., temporal inconsistencies, vagueness), test: (a) augmentation strategies (RAG with domain guidelines, style-transfer prompts), (b) unlearning strategies (fine-tuning on corrected examples, LoRA-based editing, contrastive decoding), and (c) hybrids. Measure not only error reduction but also side-effects on unrelated tasks and safety guardrail integrity.

## Limitations
- The exact conceptual model corpus (source, size, length distribution) is unreported, limiting replication fidelity.
- The precise prompt template and readability metric (e.g., Flesch vs. SMOG) are unspecified.
- The full temperature sweep range and search strategy are not detailed; only optimal points are reported.

## Confidence
- **Temperature-task optimality**: Low (hinges on unreported prompts, corpus, metric)
- **Model representation impact**: Medium (specific accuracy contrast cited but platform details vague)
- **RAG performance degradation**: Medium (case example provided but conditions not fully defined)
- **Non-determinism sources/quantification**: Medium (factorial design mentioned but implementation specifics missing)

## Next Checks
1. **Corpus & Prompt Standardization**: Procure a fixed set of 20 public conceptual model texts (e.g., system dynamics case studies) and define a versioned prompt template (e.g., “Explain concisely: {context}”).
2. **Metric & Sweep Specification**: Explicitly adopt a readability metric (e.g., Flesch Reading Ease) and test a fine‑grained temperature grid (e.g., 0.0–1.0 in 0.25 steps) for both context lengths (5/10 sentences).
3. **Replication with Controlled Variance**: Use a pinned LLM version (e.g., `gpt-3.5-turbo-0613`) with ≥5 replicates per condition; apply a 2×2 factorial design (context size × temperature) to quantify output variance contributions.
