# Enhancing Retrieval-Augmented Generation with Two-Stage Retrieval: FlashRank Reranking and Query Expansion

## Quick Facts
- **arXiv ID:** 2601.03258
- **Source URL:** https://arxiv.org/abs/2601.03258
- **Reference count:** 7
- **Primary result:** A two-stage RAG pipeline with LLM-driven query expansion and FlashRank reranking improves generation accuracy (F1) by 6–8%, boosts NDCG@10 by up to 5.4%, and reduces context tokens by 35%, while cutting total latency by 22%.

## Executive Summary
This paper addresses the core tension in Retrieval-Augmented Generation (RAG) between retrieving enough relevant evidence (recall) and keeping the context fed to the LLM concise (precision/length). It proposes a two-stage solution: first, an LLM-driven query expansion module generates synonyms and context terms to broaden the initial candidate pool; second, FlashRank—a greedy, token-budget-aware reranker—selects an optimal subset of documents by jointly optimizing for relevance, novelty, brevity, and cross-encoder scores. Evaluated on BEIR, MS MARCO, and FinanceBench, the system demonstrates significant gains in retrieval ranking (NDCG@10), downstream generation accuracy (F1), and efficiency, with ablations confirming the necessity of both stages.

## Method Summary
The system follows a clear pipeline: (1) The original user query is expanded using an instruction-tuned LLM to produce a set of semantically related terms, combined with embedding nearest neighbors. (2) This expanded query set is used with a hybrid BM25 + dense retriever to fetch a large, diverse initial candidate set (e.g., top 100 documents). (3) FlashRank reranks this set under a hard token budget *B*. It initializes an empty selection set *S* and iteratively adds the document with the highest marginal utility Δ(*d*|*S*), where utility is a weighted linear combination of similarity to the expanded query, novelty relative to *S*, inverse length penalty, and a cross-encoder score. Selection stops when the token budget is exhausted or marginal gain falls below a threshold. (4) The final subset *S* is appended to the original query and sent to an LLM generator.

## Key Results
- **Performance:** FlashRank boosts NDCG@10 by up to 5.4% and generation F1 by 6–8% over strong baselines.
- **Efficiency:** Reduces context tokens by 35% and cuts total pipeline latency by 22% compared to using a cross-encoder reranker without token budgeting.
- **Speed:** Reranks 100 candidate documents in under 60 ms, enabling practical deployment.

## Why This Works (Mechanism)
### Mechanism 1: LLM-Driven Query Expansion Boosts Recall
The original query's lexical and semantic representation often fails to match the corpus's vocabulary. An instruction-tuned LLM suggests synonyms, paraphrases, and contextual terms not present in the original query. These are combined with embedding nearest neighbors to form an expanded query *q'*. This expanded set is used with a hybrid BM25+dense retriever to fetch a broader initial candidate pool, increasing the chance that all relevant documents are present in the top-*N* set. The core assumption is that LLM-generated terms can bridge the vocabulary gap without introducing prohibitive noise. Ablation results show a clear drop in performance when query expansion is removed, confirming its role in improving candidate recall.

### Mechanism 2: FlashRank's Greedy Marginal-Utility Reranking Balances Signals
Given a large candidate pool, the goal is to select a small subset *S* that maximizes a utility function *U(q', S)* under a token budget *B*. FlashRank defines *U* as a weighted sum of four signals per document: (1) relevance (similarity to *q'*), (2) novelty (dissimilarity to already selected docs), (3) brevity (inverse length penalty), and (4) quality (cross-encoder score). The greedy algorithm iteratively adds the document with the highest marginal gain Δ(*d*|*S*) until the budget is filled. This explicitly trades off richness (relevance, cross-encoder) against redundancy (novelty) and cost (length), producing a high-utility, budget-compliant set. The linear combination assumes these signals are approximately additive for the selection task.

### Mechanism 3: Synergistic Two-Stage Pipeline
The two stages are designed to be complementary. Query expansion deliberately widens the recall of the initial retrieval stage, ensuring a diverse and comprehensive candidate pool. FlashRank then operates on this pool to compress it into a minimal, high-quality subset. The ablation studies demonstrate that both components are necessary: expansion provides the raw material (recall), and reranking provides the distillation (precision & efficiency). This synergy allows the system to handle the recall-context trade-off more effectively than either component alone or a single-stage reranker without token awareness.

## Foundational Learning
- **Token Budgeting in RAG:** A hard constraint on the total tokens fed to the LLM. This resource limit directly trades off against potential answer quality. *Why needed:* FlashRank's entire design optimizes under this constraint. *Quick check:* If budget *B* increases by 50%, would F1 plateau? Likely yes, once all truly relevant documents are included; further tokens just add noise.
- **Marginal Utility in Greedy Selection:** A document's value is its incremental contribution Δ(*d*|*S*) to the current set *S*. *Why needed:* Core to FlashRank's iterative algorithm. *Quick check:* Why might greedy be sub-optimal? It can't foresee synergistic document pairs. Greedy is reasonable if *U* is submodular (diminishing returns), which the novelty term encourages.
- **Hybrid Retrieval & Query Expansion:** Combining lexical (BM25) and semantic (dense) retrieval mitigates modality gaps. Query expansion further widens coverage. *Why needed:* The paper's first stage relies on this to get a strong candidate pool. *Quick check:* How does LLM expansion differ from Pseudo-Relevance Feedback (PRF)? LLM expansion uses generative knowledge *before* retrieval, while PRF uses top-retrieved docs *after*—LLM is more proactive but risks hallucinated terms.
- **Cross-Encoder Reranking:** A model that jointly encodes query and document for a relevance score, more accurate but slower than bi-encoders. *Why needed:* FlashRank uses it as one signal (δ) for high-precision quality assessment. *Quick check:* Why not use cross-encoder scores alone for selection? Because it ignores novelty and length, leading to redundant or overly long contexts.
- **Submodular Optimization:** A property where the marginal gain of adding an item decreases as the set grows. *Why needed:* The novelty term in FlashRank's utility promotes submodularity, making greedy a good heuristic. *Quick check:* If *U* were supermodular (synergistic), would greedy still be good? No, it would be a poor approximation.
- **Reranking vs. Retrieval:** Reranking re-orders a fixed candidate set. *Why needed:* FlashRank is a reranker that also selects a subset, distinct from the initial retrieval stage. *Quick check:* Could FlashRank be used as a retriever? In principle yes, but its sequential greedy loop is slower than standard ANN search for large corpora.

## Architecture Onboarding
- **Component map:** Original Query (q) -> Query Expansion Module (LLM + embedding neighbors) -> Expanded Query (q') -> Hybrid Retriever (BM25 + Dense) -> Initial Candidate Set (D, size ~100) -> FlashRank Reranker (with token budget B) -> Final Selected Subset (S) -> LLM Generator -> Answer.
- **Critical path:** q -> expansion -> q' -> hybrid retrieval -> D -> FlashRank selection -> S -> generation. The token budget *B* is a key constraint flowing into FlashRank.
- **Design tradeoffs:**
  - *Utility formula complexity:* Four signals (relevance, novelty, brevity, cross-encoder) improve selection quality but require tuning weights (α,β,γ,δ) and a cross-encoder model (latency cost).
  - *Token budget B:* Smaller *B* reduces cost/latency but risks omitting key evidence. Must be set based on LLM context window and application cost targets.
  - *Parallelization:* FlashRank's greedy loop is sequential in *S*, but marginal utility scores for all remaining candidates can be computed in parallel each iteration. The paper's <60 ms claim likely relies on this parallelization.
- **Failure signatures:**
  - *High token count + low F1:* Threshold τ too low or utility weights misconfigured → includes too much noise.
  - *Low Recall@50 despite QE:* LLM expansion generating irrelevant terms, or hybrid retriever's indexing/weighting is poor.
  - *Latency spike (>60ms for 100 docs):* FlashRank not parallelized, or cross-encoder scoring (δ) is a bottleneck (e.g., using a large model).
- **First 3 experiments:**
  1. **Isolate Query Expansion:** Compare Dense-only vs. Dense+QE (no reranking). Measure Recall@50 on BEIR/FinanceBench to confirm expansion increases candidate recall, especially for tail queries.
  2. **Budget Sensitivity Sweep:** Fix QE and retrieval; run FlashRank with varying budgets (e.g., 500, 1000, 1500, 2000 tokens). Plot generation F1 vs. tokens to identify the plateau and optimal cost/quality trade-off.
  3. **Ablate FlashRank Signals:** Disable one signal at a time (e.g., set β=0 for no novelty, γ=0 for no brevity penalty). Measure impact on F1 and total token count of selected set *S* to validate each signal's independent contribution.

## Open Questions the Paper Calls Out
- **Question 1:** How can FlashRank's utility coefficients (α, β, γ, δ) be adaptively determined per query or domain rather than globally tuned? The paper identifies "adaptive weighting" as future work.
- **Question 2:** Should the token budget *B* be dynamically set per query based on retrieval uncertainty or query complexity to optimize the recall-utility trade-off? The paper proposes "budget-aware reinforcement tuning" as a direction.
- **Question 3:** How can LLM-driven query expansion be specialized for domain-specific jargon (e.g., finance) to prevent noisy expansions that harm precision? Error analysis notes "domain-specific financial expansion dictionaries" as an open direction.
- **Question 4:** Does the linear utility model in Eq. 2 suffice, or would a non-linear combination of features improve FlashRank's ranking effectiveness? The current additive form assumes feature independence.

## Limitations
- **Hyperparameter opacity:** The exact values for query expansion (LLM, prompt, term count) and FlashRank's tuned weights (α,β,γ,δ), threshold τ, and budget *B* are not reported, hindering exact replication.
- **Dependence on initial retriever:** Performance relies on the hybrid retriever's quality; if the expanded candidate set contains few truly relevant documents, even optimal reranking cannot achieve high generation accuracy.
- **Generalization risk:** LLM expansion may introduce irrelevant terms in specialized domains or with ambiguous queries, potentially overwhelming later stages and hurting precision despite reranking.

## Confidence
- **Query expansion recall boost:** Medium. Paper evidence (ablation) is strong, but break condition (noise introduction) is a significant risk not fully quantified for all domains.
- **FlashRank token-optimal selection:** Medium. Formal utility defined and evaluated, but corpus support for the specific linear formulation is weak; neighboring papers use different strategies.
- **Two-stage synergy:** Medium-High. Ablation confirms both components are necessary, but the synergy hinges on the initial hybrid retriever's baseline quality being reasonable.
- **Latency claims:** Medium. Claim of <60 ms for 100 docs is plausible with parallelization, but exact implementation details (cross-encoder model size, hardware) are unspecified.

## Next Checks
1. **Expansion recall/noise trade-off:** Compute recall@100 for expanded vs. original queries on a BEIR subset. Manually inspect 20 expansions to quantify the proportion of irrelevant or misleading terms.
2. **Budget sensitivity curve:** Sweep token budgets (500–2000 tokens) in 250-token increments. Plot generation F1 and average selected token count vs. budget to identify the plateau and optimal operating point for cost/quality.
3. **Signal ablation impact:** Systematically disable each FlashRank signal (set weight to 0) in isolation. Measure changes in generation F1 and total tokens of the selected set *S* to confirm each signal's independent contribution and potential redundancy.
