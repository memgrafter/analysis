# What-If Explanations Over Time: Counterfactuals for Time Series Classification

## Quick Facts
- **arXiv ID:** 2603.27792  
- **Source URL:** https://arxiv.org/abs/2603.27792  
- **Reference count:** 40  
- **Primary result:** A structured taxonomy and the open-source CFTS library unify counterfactual methods for time series classification and enable systematic, reproducible benchmarking.

## Executive Summary
This survey tackles the fragmented landscape of counterfactual explanation methods for time series classification by introducing a six-family taxonomy and the CFTS library. CFTS standardizes implementations of 17+ algorithms under a common PyTorch framework and provides a comprehensive, time-aware evaluation suite with metrics such as validity, proximity (L1/L2/DTW), sparsity, plausibility, diversity, and stability. The work enables reliable comparison of methodological trade-offs (e.g., proximity vs. sparsity, temporal coherence) and lays the foundation for rigorous benchmarking in the field.

## Method Summary
The paper does not propose a new single algorithm but presents a survey and an open-source library, CFTS. CFTS wraps existing counterfactual generation methods (optimization-based, evolutionary, instance-based, latent space, segment-based, hybrid) in a unified API. Users load a time series dataset and a trained classifier, select a method, generate counterfactuals via `generate_counterfactual(x, target_class)`, and evaluate with a shared suite that computes standardized metrics. The library also includes visualization tools to compare original and counterfactual series.

## Key Results
- Taxonomy organizes diverse counterfactual methods into six clear families based on generation principles (operating space and search method).  
- CFTS unifies 17+ implementations, eliminating inconsistencies in interfaces and metric definitions.  
- Systematic comparisons reveal inherent trade-offs: optimization-based methods yield low-distance but diffuse changes, while segment-based approaches produce sparse, localized edits.

## Why This Works (Mechanism)
### Mechanism 1
**Claim:** The six‑category taxonomy provides a principled structure that makes the diverse landscape comprehensible and comparable.  
**Mechanism:** A systematic literature review extracted key algorithmic properties (operating space: input, latent, or segments; search method: optimization, evolution, instance substitution) and grouped methods into six families based on core generation principle. This domain‑agnostic categorization highlights inductive biases.  
**Core assumption:** Methods in the same family share characteristics leading to similar trade‑offs (e.g., optimization‑based favor proximity over sparsity).  
**Break condition:** Emergence of a novel method that cannot be classified into any existing family would require taxonomy extension.

### Mechanism 2
**Claim:** CFTS achieves standardization across implementations and evaluations, making empirical comparisons reliable and reproducible.  
**Mechanism:** CFTS wraps each algorithm in a common PyTorch‑based interface, enforcing uniform input/output formats and offering a modular evaluation suite that computes a fixed set of metrics consistently, removing implementation noise.  
**Core assumption:** Inconsistent implementations and metric definitions cause contradictory results; standardizing them reveals true methodological differences.  
**Break condition:** Lack of community adoption or incompatibility of new methods with the interface would limit impact.

### Mechanism 3
**Claim:** Systematic comparison via CFTS reveals inherent trade‑offs that guide method selection for real‑world applications.  
**Mechanism:** Running multiple algorithms on common datasets with the same metrics populates comparative tables and visualizations, highlighting which families excel in which dimensions.  
**Core assumption:** Selected metrics (including temporal‑aware ones like DTW and segment‑level sparsity) adequately capture key quality aspects of time series counterfactuals.  
**Break condition:** If metrics fail to correlate with human judgment of explanation quality, comparative analysis could mislead.

## Architecture Onboarding
- **Component map:**  
  algorithms/ -> implementations of each counterfactual method (e.g., wachter.py, native_guide.py, ts_tweaking.py)  
  data/ -> loaders for standard time‑series archives and preprocessing utilities  
  evaluation/ -> metric calculators (metrics.py) for validity, proximity, sparsity, plausibility, diversity, stability  
  visualization/ -> plotting functions (overlays, segment highlights, metric bar charts)  
  models/ -> wrappers for trained classifiers to provide gradient/score access  
  utils.py -> shared helpers. All algorithm classes implement a common `generate_counterfactual(x, target_class, **kwargs)` interface.

- **Critical path:**  
  1. Install CFTS and dependencies (PyTorch, numpy, scipy, tslearn, matplotlib).  
  2. Load or train a differentiable time‑series classifier and wrap it appropriately.  
  3. Select a dataset and a specific instance `x`.  
  4. Instantiate a counterfactual method (e.g., `WachterCounterfactual(model, ...)`).  
  5. Call `generate_counterfactual(x, target_class)` to obtain `x_cf`.  
  6. Evaluate with `CounterfactualEvaluator` → `evaluator.evaluate(x, x_cf, model)`.  
  7. Visualize via `plot_counterfactual(x, x_cf, ...)`.  
  8. For systematic comparison, loop over multiple algorithms and aggregate results.

- **Design tradeoffs:**  
  - *Flexibility vs. Complexity*: Supporting many algorithms introduces hyperparameter complexity; sensible defaults reduce burden.  
  - *Performance vs. Richness*: Comprehensive metrics increase runtime; users can enable only needed ones.  
  - *Modularity vs. Integration*: Isolated algorithm modules ease maintenance but prevent cross‑module optimizations.  
  - *Interpretability vs. Automation*: CFTS generates counterfactuals but not textual summaries; users must create narratives from visualizations.

- **Failure signatures:**  
  - Shape mismatch errors: verify data preprocessing and model input expectations.  
  - Gradients unavailable: ensure model is in eval mode and differentiable for gradient‑based methods.  
  - Metric NaNs: check counterfactual validity (no non‑finite values).  
  - Excessive runtime: use smaller populations or shorter series for evolutionary methods.  
  - Missing dependencies: install optional packages (e.g., matplotlib, tslearn) for full functionality.

- **First 3 experiments:**  
  1. **Baseline proximity test**: Run `Wachter` on a single `FordA` instance with a CNN. Verify validity and compute L2; note diffuse changes across many timesteps.  
  2. **Sparsity comparison**: Run `SG‑CF` on the same instance and compare sparsity metrics (modified points, segment length) with Experiment 1; expect localized edits.  
  3. **Diversity and runtime**: Run `TSEvo` to generate a Pareto front of 5 counterfactuals. Measure pairwise DTW diversity and total runtime; contrast with single‑output methods.

## Open Questions the Paper Calls Out
1. **User‑specific constraints:** How can methods automatically incorporate actionable constraints and domain knowledge (e.g., clinical rules) to produce feasible counterfactuals?  
2. **Causal coherence:** What causal inference techniques yield temporally coherent and feasible counterfactuals in non‑iid time series?  
3. **Scalability:** How can algorithms be optimized for long, high‑frequency time series in real‑time applications?  
4. **Synergy with other XAI:** How can counterfactuals be combined with feature attributions to enhance interpretability and trust?  
5. **Robustness and uncertainty:** How can robustness and uncertainty of counterfactuals be quantified and improved under data noise and model variations?

## Limitations
- **Taxonomy coverage:** The six families are derived from literature up to submission; novel approaches (e.g., diffusion‑based) might not fit.  
- **Reproducibility:** Hyperparameter settings, model checkpoints, and random seeds are not documented; exact numeric replication requires inspecting the CFTS codebase.  
- **Metric sufficiency:** Automatic metrics are proxies; no user study confirms they reflect explanation quality in practice.
