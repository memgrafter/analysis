# Scalable Cross-Facility Federated Learning for Scientific Foundation Models on Multiple Supercomputers
## Quick Facts
- **arXiv ID:** 2603.19544
- **Source URL:** https://arxiv.org/abs/2603.19544
- **Reference count:** 40
- **Primary result:** Demonstrated scalable cross-facility federated learning across four DOE supercomputers; FedCompass reduced final test loss by 4.5% compared to FedAvg under realistic queuing.

## Executive Summary
This paper addresses the challenge of training large scientific AI models via federated learning across geographically distributed High Performance Computing (HPC) facilities where data cannot be centralized. The authors integrate the Advanced Privacy-Preserving Federated Learning (APPFL) framework with Globus Compute and Globus Transfer to orchestrate local training jobs under site-specific schedulers (e.g., SLURM, PBS) while managing model exchange. They evaluate the system by fine-tuning a Llama2-7B model on the SMolInstruct chemistry dataset partitioned across four DOE supercomputers (Aurora, Frontier, Perlmutter, Polaris). Results reveal significant heterogeneity in computational throughput (250 to 2100 samples/sec) and wide-area transfer speeds (differences up to 200 MB/s). Under realistic queuing conditions, the FedCompass algorithm outperforms standard FedAvg, reducing final test loss by 4.5%, highlighting the critical need for scheduler-aware FL algorithm design in cross-facility HPC environments.

## Method Summary
The proposed system builds on APPFL as the federated learning engine. Globus Compute dispatches local training functions to each HPC cluster, where they execute under the site’s native batch scheduler. Model parameters, too large for direct function arguments, are transferred via Globus Transfer; ProxyStore manages lightweight proxies for these large objects, automatically triggering transfers when accessed and bypassing Globus Compute’s 10 MB argument limit. Local training uses DeepSpeed with ZeRO data parallelism, where the optimization stage (e.g., ZeRO-3 for 40 GB GPUs, ZeRO-1 for ≥64 GB GPUs) is chosen based on GPU memory capacity. The authors compare several FL algorithms—FedAvg (synchronous), FedAsync, FedBuff, and the scheduler-aware FedCompass—under two experimental setups: (1) co-scheduled runs with guaranteed resource reservations to establish baseline convergence, and (2) queue-based runs without reservations to simulate realistic HPC scheduling. The SMolInstruct dataset is partitioned by chemistry task groups, with each of the four supercomputers representing a client holding a distinct subset of tasks.

## Key Results
- Feasibility: Cross-facility FL was successfully run across four DOE supercomputers, demonstrating the practicality of the APPFL+Globus+ProxyStore stack.
- Throughput heterogeneity: Measured throughput ranged from 250 to over 2100 samples/sec due to GPU memory-driven ZeRO optimization trade-offs.
- Network heterogeneity: Wide-area transfer speeds for large models differed by up to 200 MB/s depending on network latency between sites.
- Algorithm performance: Under realistic queuing, FedCompass achieved the best global model performance, reducing final test loss by 4.5% relative to FedAvg.

## Why This Works (Mechanism)
**1. Orchestration abstraction via APPFL, Globus Compute, and ProxyStore**  
Integration of APPFL with Globus Compute and Transfer enables cross-facility FL by abstracting heterogeneous HPC schedulers and secure data movement. APPFL manages FL logic (aggregation, algorithm selection). Globus Compute dispatches local training functions to remote clusters, executing under each site’s native scheduler (e.g., SLURM, PBS). Model parameters are moved via Globus Transfer, while ProxyStore replaces large model objects with lightweight proxies, automatically triggering transfers when accessed and bypassing the 10 MB argument limit of Globus Compute. Core assumption: Each HPC has a functional Globus Compute endpoint and permits external authentication; network paths allow Globus Transfer. Evidence: Abstract and Section 4.2 describe the three-engine architecture and ProxyStore’s role; related work (e.g., cross-facility data streaming) corroborates the data movement challenges. Break condition: If a facility blocks external Globus triggers or lacks Globus infrastructure, task dispatch and transfers fail.

**2. GPU memory determines ZeRO optimization and throughput heterogeneity**  
GPU memory capacity dictates the DeepSpeed ZeRO optimization stage, creating >8× throughput heterogeneity across supercomputers and necessitating computational awareness in FL algorithm design. GPUs with ≤40 GB memory require ZeRO-3 (partitioning optimizer states, gradients, parameters), increasing inter‑GPU communication. Larger GPUs (≥64 GB) use ZeRO-1 (only partition gradients), reducing communication overhead. This leads to vastly different samples/sec per node (e.g., 250 vs. 2100), causing stragglers in synchronous FL and imbalance in asynchronous FL. Core assumption: FL algorithms treat clients as equal contributors unless explicitly adapted; faster clients then waste time waiting (FedAvg) or dominate updates (FedAsync). Evidence: Section 2.3 shows Perlmutter’s two configurations: the 40 GB variant achieves only 250 samples/sec, while the 80 GB variant reaches 1,200 samples/sec; Section 2.4.2 shows FedCompass adapts local steps to throughput and yields the best test loss. Break condition: Uniform GPU memory across clients (identical ZeRO stage) minimizes heterogeneity.

**3. HPC queueing delays require scheduler-aware FL**  
HPC queueing introduces temporal unpredictability in client participation, degrading standard FL and necessitating scheduler-aware algorithms that incorporate waiting‑time estimates. Without advance reservations, clients enter site‑specific queues with highly variable wait times (e.g., >100 h for 64+ nodes). This desynchronizes local training rounds: synchronous FL stalls aggregation; asynchronous methods allow fast clients to contribute more updates, biasing the global model. FedCompass partially mitigates by scaling local steps inversely to throughput, but it does not explicitly model queue dynamics. Core assumption: Queue wait times dominate wall‑clock time and differ across sites due to policies, workloads, and allocation sizes. Evidence: Section 2.4.2 experiments; Section 3.2 discussion; Figure 5 shows Polaris queue wait time grows with node count and varies by queue. Break condition: Clients obtain immediate starts (e.g., dedicated reservations) or all queues have negligible wait times.

## Foundational Learning
- **Cross-silo federated learning**  
  *Why needed:* The paper targets collaborative training across institution-scale HPC facilities (silos), each holding large domain-specific datasets. Cross-silo FL assumptions (reliable participation, large data per client) differ from cross-device FL.  
  *Quick check:* How does the non‑IID distribution of chemistry task groups across supercomputers affect local model drift and global aggregation?

- **HPC job scheduling and queueing**  
  *Why needed:* HPC clusters use batch schedulers (SLURM, PBS) to allocate resources, introducing wait times that desynchronize FL rounds. Understanding queue dynamics is critical for algorithm design and deployment planning.  
  *Quick check:* Why might large node allocations face longer queue wait times than small ones, based on Figure 5?

- **Computational heterogeneity in distributed training**  
  *Why needed:* Throughput varies across supercomputers due to GPU memory, architecture, and software optimizations (ZeRO stages). FL algorithms must account for these differences to avoid stragglers or biased aggregations.  
  *Quick check:* What is the trade‑off between using ZeRO-3 (memory‑efficient) and ZeRO-1 (communication‑efficient) in the context of FL?

## Architecture Onboarding
**Component map (plain text flow):**  
APPFL Server -> Globus Compute (server endpoint) -> ProxyStore -> Globus Transfer -> Client-side Globus Compute -> HPC Scheduler (SLURM/PBS) -> APPFL Client -> DeepSpeed -> ProxyStore -> Globus Transfer -> APPFL Server

**Critical path for one FL round:**  
1. Server selects clients and sends current global model (via Globus Transfer, triggered by ProxyStore).  
2. Client job starts in HPC queue; once running, it fetches the model via ProxyStore (which may wait for transfer).  
3. Local training runs via DeepSpeed (using MPI engine).  
4. Client uploads updated model via ProxyStore/Globus Transfer.  
5. Server aggregates updates (synchronously or asynchronously).  
6. Repeat for next round.

**Design tradeoffs:**  
- ZeRO stage: Memory vs. communication; choose based on per‑GPU memory.  
- Synchronous vs. asynchronous FL: Sync ensures convergence quality but suffers stragglers; async tolerates delays but may bias model.  
- Reservations vs. queues: Reservations give predictability but require advance coordination; queues are accessible but introduce variable delays.  
- ProxyStore vs. direct transfer: ProxyStore automates transfer but adds dependency; direct transfer gives more control but requires custom code.

**Failure signatures:**  
- Globus Transfer failure: Model not delivered; client hangs waiting for proxy resolution. Check Globus endpoint status and network connectivity.  
- HPC job failure: Client never returns; could be due to scheduler preemption, node failure, or incorrect environment. Monitor via scheduler (squeue/sacct).  
- High network latency: Transfers slow; affects large models. Check Table 6 for typical RTTs; consider hierarchical aggregation if cross‑site latency is high.  
- Memory OOM: If ZeRO stage too low for GPU memory; reduce batch size or use higher ZeRO stage.

**First 3 experiments:**  
1. **Throughput scaling test:** Run 1–64 nodes per supercomputer with fixed micro‑batch size, measure samples/sec. Identifies each site’s performance profile and optimal ZeRO stage.  
2. **Co‑scheduled FedAvg:** With reservations, run 64 nodes per client for 8 rounds. Validates basic FL functionality and measures convergence under ideal sync conditions.  
3. **Queue‑based algorithm comparison:** Without reservations, run 2 nodes per client comparing FedAvg, FedAsync, FedBuff, FedCompass under real scheduling. Reveals which algorithm best handles heterogeneity and queue delays (target: FedCompass).

## Open Questions the Paper Calls Out
**1. How can FL algorithms explicitly incorporate HPC job scheduling dynamics (queue wait times, scheduler policies) to improve convergence and resource utilization?**  
*Basis:* The abstract and Section 3.2 identify scheduler‑aware algorithm design as a critical open challenge.  
*Why unresolved:* Existing algorithms (FedAvg, FedAsync, FedBuff, FedCompass) do not model queueing delays, leading to suboptimal performance under realistic HPC conditions.  
*Resolution evidence:* A new FL algorithm that predicts queue times or adapts aggregation based on scheduler state, validated across multiple HPC facilities, showing improved convergence speed and final model accuracy under variable queue conditions.

**2. How can hierarchical aggregation be leveraged in cross‑facility FL to reduce wide‑area communication overhead while maintaining model convergence?**  
*Basis:* Section 3.2 suggests hierarchical aggregation exploiting geographic locality; Section 2.5 reveals large communication cost differences across facilities.  
*Why unresolved:* Direct client‑server communication becomes expensive for large models; hierarchical approaches may cut costs but introduce aggregation complexity and potential bias.  
*Resolution evidence:* Implementation and evaluation of a hierarchical FL algorithm that groups clients by proximity, demonstrating reduced total communication volume and/or faster training time without sacrificing model accuracy relative to flat communication.

**3. How can client drift from extreme non‑IID data distributions across HPC facilities be mitigated in cross‑facility FL, especially under large‑scale local training?**  
*Basis:* The paper observes client drift in Section 2.4.1 and states it is a core challenge in Section 3.2; techniques like SCAFFOLD are proposed but not evaluated.  
*Why unresolved:* The evaluated algorithms lack drift‑correction mechanisms, causing local models to diverge significantly when training on highly specialized datasets.  
*Resolution evidence:* Comparative evaluation of drift mitigation methods (e.g., SCAFFOLD, FedProx) in the cross‑facility HPC setting, showing improved global model performance and reduced client divergence under non‑IID partitions.

## Limitations
- HPC‑specific configurations (scheduler policies, network topology, Globus endpoint authentication) are not detailed, hindering exact replication.  
- Local training hyperparameters (learning rate, optimizer, local steps) are omitted; performance may vary with different tuning.  
- SMolInstruct dataset partitioning and exact train/test splits are undisclosed, risking data leakage concerns.

## Confidence
- Cross‑facility FL feasibility (APPFL+Globus+ProxyStore): **High**  
- GPU memory‑driven throughput heterogeneity: **High**  
- FedCompass gains under queueing: **Medium**  
- Wide‑area transfer speed heterogeneity: **High**

## Next Checks
1. **Statistical robustness:** Run ≥5 independent seeds for FedAvg vs. FedCompass under identical queue conditions; compute significance of the 4.5% loss reduction (e.g., paired t‑test).  
2. **Generalizability:** Deploy the same stack on at least two non‑DOE HPC centers (different schedulers/network) to evaluate portability and infrastructure requirements.  
3. **Algorithm dissection:** Compare FedCompass against an “oracle” scheduler that knows exact client throughput and queue wait times to quantify remaining performance headroom.
