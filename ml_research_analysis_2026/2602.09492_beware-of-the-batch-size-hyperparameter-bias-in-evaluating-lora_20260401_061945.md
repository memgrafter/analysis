# Beware of the Batch Size: Hyperparameter Bias in Evaluating LoRA

## Quick Facts
- **arXiv ID:** 2602.09492
- **Source URL:** https://arxiv.org/abs/2602.09492
- **Reference count:** 15
- **Primary result:** Batch size is a critical, overlooked hyperparameter that explains contradictory performance claims among LoRA variants; when properly tuned, vanilla LoRA often matches or outperforms more complex variants, and an optimal batch size exists that can be efficiently proxied using a smaller model.

## Executive Summary
This paper identifies batch size as a major source of bias in evaluating Low-Rank Adaptation (LoRA) variants for large language model fine-tuning. Systematic experiments on LLaMA-2 models reveal that performance rankings between vanilla LoRA and variants like PiSSA and MiLoRA are highly sensitive to batch size, with accuracy gaps exceeding 10% depending on the configuration. Contrary to common heuristics, the relationship between batch size and test accuracy is non-monotonic, exhibiting a clear optimum. Furthermore, the authors show that this optimum is largely invariant to model size and adapter rank but sensitive to dataset scale, enabling a cost-effective proxy strategy: tune batch size on a small model with low rank using the full target dataset, then transfer the configuration. These findings reconcile prior inconsistencies and establish batch size as a first-order design parameter for reliable and efficient fine-tuning.

## Method Summary
The study conducts controlled fine-tuning experiments on LLaMA-2 (7B and 13B) models using the MetaMathQA training set (first 100K samples) and evaluating on GSM8K. A fixed sample protocol is enforced: each configuration sees exactly one epoch of data (100K samples), so larger batches result in fewer gradient updates. For each batch size, a learning rate sweep is performed (typically 1e-5 to 3e-3) to isolate batch size effects from learning rate confounding. LoRA is applied to attention and MLP layers with a base rank of 128 (α=r). The core evaluation compares test accuracy across batch sizes for vanilla LoRA, PiSSA, and MiLoRA. To test the proxy strategy, experiments vary rank (32–256), model size (7B vs. 13B), and dataset scale (subsets of MetaMathQA), measuring shifts in the optimal batch size.

## Key Results
- Contradictory performance claims among LoRA variants are largely artifacts of differing batch size configurations; when batch size and learning rate are properly tuned, vanilla LoRA frequently matches or exceeds PiSSA and MiLoRA.
- The accuracy vs. batch size curve is non-monotonic, with a distinct optimum that defies the "smaller batches are always better" heuristic.
- The optimal batch size is consistent across different LoRA ranks and model capacities (7B→13B) but shifts with dataset scale, enabling a proxy strategy: tune on a small model with low rank on the full dataset, then transfer the batch size to larger configurations.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Inconsistent performance claims across LoRA variants stem partly from batch size confounding, not solely algorithmic superiority.
- **Mechanism:** Batch size interacts with low-rank optimization dynamics, altering gradient noise scale and convergence. A variant may appear superior under one batch size regime but underperform under another. Proper tuning reveals vanilla LoRA as often competitive.
- **Core assumption:** The optimization landscape of LoRA is sensitive to batch size in ways not captured by full-parameter tuning heuristics.
- **Evidence anchors:** Abstract states contradictions arise from batch size; Section 3.1 shows performance crossovers between variants; neighboring works (e.g., BA-LoRA) discuss hyperparameter confounds.

### Mechanism 2
- **Claim:** The batch size-accuracy relationship is non-monotonic; an optimal batch size exists.
- **Mechanism:** Smaller batches increase gradient noise (regularization but slower convergence); larger batches reduce noise and improve hardware utilization but can harm generalization due to update correlation. An optimal trade-off point emerges.
- **Core assumption:** The "sweet spot" balances gradient noise scale (data-dependent) and number of parameter updates under a fixed sample protocol.
- **Evidence anchors:** Abstract notes larger batches don't necessarily hurt; Section 2 discusses fixed sample protocol; Figures 1 & 2 show U-shaped curves.

### Mechanism 3
- **Claim:** The optimal batch size for a target fine-tuning job can be proxied using a smaller model with lower rank, if the full dataset scale is preserved.
- **Mechanism:** Batch size effects are primarily sensitive to the number of training samples (affecting gradient noise), not to model capacity or adapter rank. A small model on full data mimics data-wise noise characteristics of a large model.
- **Core assumption:** Batch size effects are invariant to model parameter count and adapter dimensionality but scale with data volume.
- **Evidence anchors:** Abstract says optimal batch size is consistent under rank/model size changes but not dataset size; Section 4.1 shows rank consistency; Section 4.3 shows model scale consistency.

## Foundational Learning
- **Concept: Gradient Noise Scale (GNS) & Batch Size**  
  *Why needed here:* The core mechanism (optimal batch size) hinges on the trade-off between gradient noise and update count. GNS theory predicts the batch size where sampling noise equals update noise, often aligning with the observed optimum. It explains why data size matters most.  
  *Quick check:* If you double the dataset size while keeping total training samples fixed (one epoch), what happens to the optimal batch size's position on the accuracy curve, and why?

- **Concept: Low-Rank Adaptation (LoRA) Parameterization**  
  *Why needed here:* To understand why batch size effects might differ from full fine-tuning. LoRA constrains updates to a low-rank subspace (B·A), changing optimization geometry and effective learning rate per parameter.  
  *Quick check:* How does the number of LoRA updates (steps) relate to batch size under a fixed sample protocol (one epoch), and why does this matter for the "smaller is better" heuristic?

- **Concept: Hyperparameter Interaction & Confounding**  
  *Why needed here:* The paper's main warning is about confounding—batch size and learning rate are coupled, and differences between papers' batch sizes can masquerade as algorithmic gains. Isolating main effects requires controlling this interaction.  
  *Quick check:* If you find Variant X beats vanilla LoRA by 2% at batch size 8, but you didn't sweep the learning rate for each batch size, what is the most likely explanation for your result?

## Architecture Onboarding
- **Component map:**  
  Pretrained Model (LLaMA-2, frozen) -> LoRA Modules (low-rank A,B matrices in attention/MLP) -> Optimizer (AdamW) -> Data Pipeline (MetaMathQA tokenized batches) -> LR Scheduler (cosine decay, no warm-up) -> Evaluation (GSM8K accuracy)

- **Critical path:**  
  1. For target (model, rank, full dataset), use a smaller proxy model (e.g., 7B vs. 13B) with lower rank (e.g., 64 vs. 128) on the *full target dataset*.  
  2. Sweep batch size logarithmically and, for each, perform a learning rate grid search to find optimal LR under one epoch (fixed samples).  
  3. Identify the batch size that maximizes validation performance on the proxy.  
  4. Transfer this optimal batch size to the target configuration. Optionally perform a narrow LR sweep around the proxy's optimal LR for the target rank/model.  
  5. Train target model with transferred batch size and tuned LR; evaluate on GSM8K.

- **Design tradeoffs:**  
  - **Proxy Fidelity vs. Cost:** Lower rank and smaller model reduce cost dramatically. Valid if batch size effects are invariant to rank/model size but sensitive to data size. Risk: invariance may break for extreme scaling or different architectures.  
  - **Fixed Samples vs. Fixed Steps:** Fixed samples isolates batch size effect but reduces updates for large batches. Fixed steps conflates batch size with data seen; paper uses fixed samples for data-efficiency objectives.  
  - **LR Sweep Cost:** Sweeping LR per batch size is expensive. Proxy strategy amortizes cost across many batch sizes by using a cheap proxy.

- **Failure signatures:**  
  - **Hyperparameter Confound:** Vanilla LoRA underperforms a variant at your chosen batch size, but you haven't swept LR for that batch. The reported gain may vanish with proper tuning.  
  - **Proxy Failure:** Using a 7B/64 proxy to tune batch size for a 70B/256 target yields worse results than a naive guess. Violates invariance assumption.  
  - **Task Sensitivity:** Optimal batch size curve on MetaMathQA (math) does not transfer to coding or instruction-following datasets.

- **First 3 experiments:**  
  1. **Re-confirm core non-monotonic curve:** On target (e.g., LLaMA-2-7B, MetaMathQA 100K, rank 128), perform full batch size sweep (e.g., 2^20 to 2^30 tokens) with LR search per batch. Plot accuracy vs. batch size; verify optimum exists.  
  2. **Test proxy invariance (rank):** Using same full dataset, compare optimal batch size curve for rank 32 vs. rank 256. Curves should be consistent per paper.  
  3. **Test proxy invariance (model size):** Using same full dataset and rank (e.g., 128), compare optimal batch size curve for LLaMA-2-7B vs. LLaMA-2-13B. Curves should be consistent per paper.

## Open Questions the Paper Calls Out
- **Open Question 1:** Can a formal theoretical framework be derived to predict optimal batch size in LoRA fine-tuning based on factors like rank, dataset size, and model capacity?  
  *Basis in paper:* [explicit] The limitations section states: "the underlying optimization dynamics that govern the observed phenomena, such as batch size trends, remain underexplored. The absence of a formal theoretical framework prevents the derivation of universal, concise guidelines for batch size selection in LoRA scenarios."  
  *Why unresolved:* Current guidelines rely on empirical patterns without causal understanding, making generalization difficult without costly tuning.  
  *What evidence would resolve it:* A mathematical model linking batch size to LoRA's low-rank constraints and optimization dynamics, tested across multiple ranks, datasets, and models to predict optimal batch sizes accurately.

- **Open Question 2:** Do the observed batch size effects and the proposed proxy strategy generalize to other tasks beyond mathematical reasoning, such as code generation or instruction following?  
  *Basis in paper:* [explicit] The limitations note: "our study mainly focuses on a single mathematical reasoning task... different tasks (e.g., code generation or instruction following) may exhibit divergent behaviors."  
  *Why unresolved:* The study is confined to MetaMathQA/GSM8K; task-specific data distributions and objectives might alter batch size sensitivity.  
  *What evidence would resolve it:* Replicating the batch size tuning experiments on diverse tasks (e.g., HumanEval for code, Alpaca for instruction) and comparing optimal batch size trends to those in the paper.

- **Open Question 3:** Are the batch size effects consistent across other model architectures beyond LLaMA 2, such as GPT, Mistral, or encoder-decoder models?  
  *Basis in paper:* [explicit] The limitations state: "while we utilize the LLaMA 2 series to ensure reproducibility and relevance, the generalizability of our findings to other architectures remains to be seen. Further extensive studies are required to validate these patterns across diverse model families."  
  *Why unresolved:* LoRA's optimization dynamics may interact with architectural differences (e.g., attention mechanisms, normalization), potentially changing batch size optimality.  
  *What evidence would resolve it:* Conducting the same batch size sweep on multiple architectures (e.g., LLaMA 3, Mixtral, T5) with comparable scales and tasks, and analyzing whether the invariance to rank/model size and sensitivity to dataset scale hold.

## Limitations
- Findings are restricted to LLaMA-2 (7B/13B) on a single math QA dataset (MetaMathQA/GSM8K); generalizability to other architectures, tasks, or domains is unverified.
- The proxy strategy's invariance assumption (batch size independent of model/rank) is only validated up to 13B and rank 256; scaling to larger models or extreme ranks may fail.
- Training used a fixed sample protocol with AdamW and cosine decay; interactions with gradient accumulation, warm-up, or alternative optimizers are unexplored.

## Confidence
- **Mechanism 1 (batch size confounding variant comparisons):** High within studied setting; Medium for broader applicability.
- **Mechanism 2 (non-monotonic batch size curve):** High for existence of an optimum; Medium for exact curve shape across tasks.
- **Mechanism 3 (proxy strategy via small model):** Medium for moderate scaling (7B→13B); Low for extreme scaling or different architectures.

## Next Checks
