# GLM-5: from Vibe Coding to Agentic Engineering

## Quick Facts
- **arXiv ID**: 2602.15763  
- **Source URL**: https://arxiv.org/abs/2602.15763  
- **Reference count**: 40  
- **Primary result**: State‑of‑the‑art performance on ARC benchmarks (77.8% SWE‑bench Verified, 75.9% BrowseComp) and first open‑weight model to score 50 on AI Index v4.0, demonstrating end‑to‑end agentic engineering capability.

## Executive Summary
GLM‑5 is a 744B‑parameter Mixture‑of‑Experts model (40B active) that shifts AI from human‑guided “vibe coding” to autonomous agentic engineering for complex, long‑horizon software tasks. It introduces two core innovations: (1) **DeepSeek Sparse Attention (DSA)**, which cuts training/inference costs by ~1.5–2× for long sequences while maintaining 200K context fidelity; and (2) a **fully asynchronous reinforcement learning infrastructure (slime)** that decouples rollout generation from training, eliminating GPU bubbles and enabling stable on‑policy RL with token‑level importance clipping and Token‑in‑Token‑out (TITO). These advances yield SOTA on key agentic benchmarks (e.g., 77.8% SWE‑bench Verified, 75.9% BrowseComp) and a score of 50 on the Artificial Analysis Intelligence Index v4.0—an 8‑point jump from its predecessor and the first open‑weight model at that level. The work also highlights unresolved challenges in long‑context consistency, self‑correction, and unbiased open‑source evaluation.

## Method Summary
The post‑training pipeline starts with a DSA‑augmented MoE base model. DSA is introduced via a two‑stage continued pre‑training: first, a 1k‑step warm‑up where only the lightweight indexer is trained while the base model is frozen; second, 20B tokens of joint sparse adaptation. Mid‑training then extends context to 200K using agentic trajectories. Pre‑training data totals 28.5 trillion tokens (web, code, math/science). Post‑training combines multi‑task SFT with interleaved/preserved thinking modes, followed by sequential RL stages: reasoning RL (GRPO + IcePop), agentic RL (leveraging the asynchronous slime infrastructure), and general RL. The slime infrastructure runs rollout workers on separate devices continuously; when a batch threshold is met, trajectories are sent to a trainer via the TITO gateway, which passes raw token IDs and log‑probs to avoid re‑tokenization mismatches. Token‑level importance clipping (double‑sided) and DP‑aware routing stabilize updates. Finally, on‑policy cross‑stage distillation transfers knowledge from the final policy to earlier stages.

## Key Results
- **SOTA on agentic benchmarks**: 77.8% on SWE‑bench Verified, 75.9% on BrowseComp (with context management), and 50 on AI Index v4.0.
- **Long‑horizon engineering dominance**: $4,432 final balance on Vending‑Bench 2; top scores on internal CC‑Bench‑V2 for frontend/backend/long‑horizon tasks.
- **Efficiency gains**: DSA reduces computational costs 1.5–2× for 200K sequences; async RL infrastructure boosts post‑training throughput by eliminating GPU bubbles.

## Why This Works (Mechanism)
### Mechanism 1: DeepSeek Sparse Attention (DSA)
- **Claim**: DSA reduces training/inference computational costs by ~1.5–2× for long sequences while maintaining performance up to 200K context.
- **Mechanism**: Replaces O(L²) dense attention with a dynamic top‑k selection of key‑value entries per token via a lightweight indexer. Training uses a two‑stage continued pre‑training: (i) warm‑up the indexer for 1k steps while freezing the base model; (ii) joint sparse adaptation on 20B tokens.
- **Core assumption**: Most attention entries in long contexts are redundant; a content‑based dynamic sparsity pattern can preserve essential dependencies.
- **Evidence anchors**: [abstract]; [Section 2.1.1] (Tables 3,6; Figure 6) show near‑parity with MLA.
- **Break condition**: Non‑deterministic top‑k operators cause RL instability; the indexer must learn meaningful sparsity.

### Mechanism 2: Asynchronous RL Infrastructure (slime)
- **Claim**: Decoupling rollout generation from training eliminates GPU bubbles and drastically improves post‑training throughput.
- **Mechanism**: Separate inference engines continuously generate trajectories; once a batch threshold is reached, trajectories are sent to a training engine. Periodically, training weights are pushed to inference engines. A central Multi‑Task Rollout Orchestrator manages diverse task microservices and standardizes trajectories.
- **Core assumption**: Agentic rollout lengths vary widely; synchronous training forces workers to wait for the slowest sample, wasting resources.
- **Evidence anchors**: [abstract]; [Section 3.6] (server‑based rollouts, tail‑latency optimizations, PD disaggregation, heartbeat fault tolerance); [Section 4.1] (asynchronous design, orchestrator, weight synchronization).
- **Break condition**: Frequent rollout server failures or excessive policy lag introduce off‑policy bias.

### Mechanism 3: Token‑level Importance Clipping & TITO
- **Claim**: Token‑level importance clipping combined with Token‑in‑Token‑out (TITO) enables stable on‑policy learning from long‑horizon interactions without tracking historical policies.
- **Mechanism**: Reuse rollout log‑probs as behavior proxy. Compute token‑level importance ratio rₜ = πₜₕ(ₐₜ|sₜ) / πᵣₒₗₗₒᵤₜ(ₐₜ|sₜ). Apply double‑sided clipping: mask tokens where rₜ ∉ [1−ϵℓ, 1+ϵₕ]. TITO passes raw token IDs + metadata directly to trainer, avoiding re‑tokenization. DP‑aware routing binds rollout requests to same DP rank for KV‑cache reuse.
- **Core assumption**: Off‑policy bias can be controlled by local token‑level constraints; exact token alignment is critical for stable gradients.
- **Evidence anchors**: [Section 4.1.2] (TITO, Direct Double‑sided Importance Sampling); reports dropping stale/noisy samples and DP‑aware routing.
- **Break condition**: Clipping thresholds mis‑set or non‑deterministic generation cause divergence.

## Architecture Onboarding
- **Component map**: Pre‑training → DSA indexer → Mid‑training (agentic data, 200K context) → SFT (thinking modes) → Reasoning RL (GRPO+IcePop) → Agentic RL (async slime) → General RL → On‑policy distillation. Infrastructure supports: slime (rollout servers, Multi‑Task Orchestrator, TITO gateway, DP‑aware router). Deployment: INT4 QAT, custom kernels, multi‑chip.
- **Critical path**: 1) Gather pre‑training corpus (web, code, math) → 2) Train base model with DSA → 3) Mid‑train on agentic data to 200K → 4) SFT with thinking modes → 5) Reasoning RL → 6) Agentic RL (requires slime) → 7) General RL → 8) On‑policy distillation. Dependencies: DSA before mid‑training; slime before Agentic RL; distillation after all RL.
- **Design tradeoffs**:  
  1. DSA vs SWA/GDN: DSA lossless but adds indexer overhead; SWA/GDN simpler but quality drop (Table 5).  
  2. Async RL vs synchronous: Higher GPU utilization but off‑policy bias; mitigated by token clipping and stale filtering.  
  3. MTP: Boosts throughput/acceptance but increases memory; 3‑layer shared keeps memory similar to DeepSeek‑V3.  
  4. Quantization: INT4 QAT fits 750B on one node but risks accuracy; requires outlier suppression (QuaRot) and careful calibration.
- **Failure signatures**:  
  - RL loss spikes & entropy collapse → non‑deterministic top‑k in DSA indexer (switch to torch.topk).  
  - Low acceptance length (<2) → MTP head‑dimension mismatch or incorrect parameter sharing.  
  - >5% drop on RULER@128K → incomplete DSA adaptation or under‑trained indexer.  
  - High variance in rollout times → unbalanced task routing; enable DP‑aware routing and monitor orchestrator.
- **First 3 experiments**:  
  1. Validate DSA: Run RULER@128K on a DSA checkpoint vs MLA; expect ≤1% difference (Table 6).  
  2. Measure async RL throughput: Use slime to run 32 concurrent rollouts of mixed agentic tasks; compare wall‑clock/step to a synchronous baseline.  
  3. Context management impact: Reproduce Figure 8 – run BrowseComp with/without keep‑recent‑k and hierarchical discard‑all; expect improvement from ~55% to ~76%.

## Open Questions the Paper Calls Out
- **Open Question 1**: How can long‑context consistency be improved for agents handling extremely long sequences (e.g., 200K tokens) to maintain coherent state and accurate reasoning? The paper asserts that narrowing the performance gap on chained tasks requires advances in long‑context consistency (page 26); current models still show a significant drop compared to Claude Opus 4.5.
- **Open Question 2**: How can long‑horizon self‑correction be enhanced so that AI agents avoid compounding errors when executing multi‑step coding tasks? The authors identify self‑correction as an area needing advancement to close the gap on chained tasks (page 26); errors propagate and cause later failures.
- **Open Question 3**: How can we develop unbiased, open‑source judge models for evaluating complex agentic behaviors that are as reliable as proprietary judges like o3‑mini? BrowseComp results are highly sensitive to the judge prompt and model; open‑source judges introduce systematic bias, forcing reliance on o3‑mini (page 24), which hinders reproducibility.

## Limitations
- **Implementation opacity**: Core components (DSA indexer architecture/training, slime orchestrator message schema, cross‑stage distillation logic) are not fully specified, blocking exact replication.
- **Benchmark reproducibility**: Reported scores lack confidence intervals and detailed evaluation configs; results depend on proprietary judges (e.g., o3‑mini) for consistency.
- **Off‑policy risk**: Asynchronous RL relies on token‑level clipping and stale filtering; exact thresholds and decay schedules are undisclosed, potentially causing hidden instabilities.
