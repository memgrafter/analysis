# Semantic Centroids and Hierarchical Density-Based Clustering for Cross-Document Software Coreference Resolution

## Quick Facts
- **arXiv ID:** 2603.24246
- **Source URL:** https://arxiv.org/abs/2603.24246
- **Reference count:** 0
- **Primary result:** Achieved CoNLL F1 scores of 0.98 on Subtasks 1 and 2, and 0.96 on Subtask 3, with scalability to over 200,000 mentions.

## Executive Summary
This paper tackles cross-document coreference resolution for software mentions in scientific texts, where the same tool may be referenced inconsistently across documents. The proposed system combines semantic embeddings from Sentence-BERT with a knowledge base of training cluster centroids retrieved via FAISS. Unmatched mentions are clustered using HDBSCAN, supported by surface-form normalization and abbreviation resolution. A blocking strategy by entity type and canonical name enables handling of large-scale data. The approach demonstrates robust performance and scalability, achieving near-perfect scores on smaller tasks and high scores on the large-scale subtask.

## Method Summary
The pipeline begins by constructing a structured context string for each mention: the surface form is duplicated and concatenated with its entity type and relational mentions. This string is encoded using `all-MiniLM-L6-v2` into a 384-dimensional L2-normalized embedding. A knowledge base (KB) is built from training data by averaging embeddings per gold cluster to form centroids, stored in a FAISS index for efficient cosine-similarity search. During inference, test mentions are first checked for exact canonical name matches (in large-scale settings) or assigned to KB clusters if their similarity exceeds a high threshold (≥0.7) or a medium threshold (0.5–0.7) with a name match. Remaining unmatched mentions undergo density-based clustering with HDBSCAN. For scalability on large corpora, mentions are blocked by entity type and, if necessary, by the first letter of their canonical name. After clustering, any clusters sharing a canonical name are forcibly merged, and mentions matching a KB canonical name are reassigned to that KB cluster.

## Key Results
- **Subtask 1 (gold mentions):** CoNLL F1 = 0.98.
- **Subtask 2 (predicted mentions, small test):** CoNLL F1 = 0.98.
- **Subtask 3 (predicted mentions, large-scale):** CoNLL F1 = 0.96, demonstrating scalability to over 200,000 mentions.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Context string construction with surface-form duplication produces embeddings where the software name dominates the semantic signal, mitigating noise from surrounding metadata.
- **Mechanism:** The mention’s surface form is duplicated and concatenated with its entity type and relational context (Equation 1). This increases the token weight of the name in the mean-pooled embedding, counteracting dilution from longer context strings. The resulting 384-dimensional vector is L2-normalized for cosine similarity search.
- **Core assumption:** The software name is the primary coreference signal; metadata (e.g., relational mentions) is secondary and must not overwhelm the name’s contribution.
- **Evidence anchors:**
  - [abstract] “We construct a short, structured context string… The surface form itself is insufficient… we counteract this by duplicating the surface form mention token.”
  - [section 2.1.1] “Mean-pooling distributes representational weight evenly… a long metadata-heavy string risks diluting the name’s contribution… We counteract this by duplicating the surface form.”
  - [corpus] Weak: Neighboring papers focus on event/coreference; no direct evidence for software mention duplication. Assumption: mechanism generalizes from sentence embedding best practices.
- **Break condition:** If relational context is highly discriminative (e.g., version-specific usage contexts), duplication may oversuppress useful signals, causing false splits.

### Mechanism 2
- **Claim:** A Knowledge Base (KB) of training-set cluster centroids retrieved via FAISS enables high-precision assignment of mentions to known software entities, leveraging exact name matches as a corroborating signal.
- **Mechanism:** Training mentions are embedded, averaged per gold cluster into L2-normalized centroids. For a test mention, FAISS searches for nearest centroid by inner product (cosine similarity). Assignment follows a tiered rule: exact canonical string match → high-confidence (cosine > 0.7) → medium-confidence (0.5–0.7 with name match). Unmatched mentions proceed to clustering.
- **Core assumption:** Mentions referring to known software will either have high embedding similarity to their cluster centroid or share a canonical surface form with a training mention.
- **Evidence anchors:**
  - [abstract] “Knowledge Base (KB) lookup strategy built from training-set cluster centroids using FAISS for efficient retrieval… Surface-form normalization and abbreviation resolution are applied to improve canonical name matching.”
  - [section 2.2–2.3] Explicit centroid construction, FAISS IndexFlatIP, and the three-tier assignment thresholds (θ=0.7, 0.5) with canonical name lookup.
  - [corpus] Weak: Neighbors use FAISS for nearest-neighbor search but not for centroid-based CDCR. Assumption: centroid representativeness holds for software mentions.
- **Break condition:** If training data lacks coverage of test software variants (e.g., new versions, domain-specific abbreviations), centroid similarity drops below threshold and exact name match fails, causing false “unmatched” flags.

### Mechanism 3
- **Claim:** Hierarchical density-based clustering (HDBSCAN) with a blocking strategy resolves mentions unmatched to the KB by grouping them based on local vector density, while blocking prevents quadratic complexity in large corpora.
- **Mechanism:** Unmatched mentions are first partitioned by entity type, and large blocks are subdivided by the first letter of the canonical name. Within each block, HDBSCAN clusters embeddings using min_cluster_size=2, min_samples=1, and cluster_selection_epsilon (0.5 for Subtasks 1/2, 0.15 for Subtask 3). Post-clustering, mentions sharing a canonical name are forcibly merged into a single cluster.
- **Core assumption:** Unmatched mentions of the same software form dense regions in the embedding space, and blocking by type/first letter creates approximately independent subproblems without splitting true clusters.
- **Evidence anchors:**
  - [abstract] “HDBSCAN density-based clustering for mentions that cannot be confidently assigned… To address the large scale settings of Subtask 3, the pipeline was adapted by utilising a blocking strategy based on entity types and canonicalized surface forms.”
  - [section 2.5] Detailed blocking logic (“partitioned by entity type… blocks exceeding 20,000 mentions… first letter”), HDBSCAN parameters per subtask, and mandatory canonical-name merging.
  - [corpus] Weak: Neighbors use blocking for entity resolution (Papadakis et al. cited) but not with HDBSCAN for CDCR. Assumption: blocking granularity preserves intra-block cluster cohesion.
- **Break condition:** If a true software cluster spans multiple blocking keys (e.g., “MATLAB” and “Matlab” in different first-letter blocks due to canonicalization quirks), it remains split; or if epsilon is too restrictive (0.15 in Subtask 3), valid clusters may be fragmented.

## Foundational Learning
- **Concept:** Sentence-BERT (all-MiniLM-L6-v2) embeddings  
  **Why needed:** Provides dense, context-aware vector representations of software mentions that capture both surface form and relational context, enabling similarity-based clustering.  
  **Quick check:** How does duplicating the surface form in the input string affect the contribution of that token in the mean-pooled embedding, relative to using the context string without duplication?
- **Concept:** FAISS IndexFlatIP for nearest-neighbor retrieval  
  **Why needed:** Enables efficient cosine-similarity search over thousands of KB centroids during test-time assignment, scaling linearly with query count.  
  **Quick check:** Why is L2-normalization of embeddings necessary before using IndexFlatIP (inner product) for cosine similarity?
- **Concept:** HDBSCAN density-based clustering  
  **Why needed:** Automatically determines the number of clusters from unmatched mention embeddings and labels outliers as singletons, accommodating unseen software without pre-specifying cluster count.  
  **Quick check:** What is the effect of decreasing `cluster_selection_epsilon` on cluster granularity, and why was a smaller value (0.15) chosen for Subtask 3?

## Architecture Onboarding
- **Component map:**  
  Input (train/test JSONL) -> Context Constructor -> Embedder (all-MiniLM-L6-v2) -> KB Builder (centroid averaging) -> FAISS Index -> KB Matcher (threshold rules) -> Canonicalizer -> Blocker (Subtask 3) -> HDBSCAN Clusterer -> Merger (canonical name) -> Output (test_labels.json)
- **Critical path:** Embedding → KB Matching → (if unmatched) → Blocking → HDBSCAN → Canonical-name merging → Final merge.
- **Design tradeoffs:**
  - **Speed vs. Precision:** Threshold 0.7 favors high-precision KB assignment but may leave more mentions for expensive HDBSCAN. Lower threshold increases recall but risks false KB assignments.
  - **Blocking Granularity:** Finer blocking (e.g., first letter) reduces HDBSCAN’s O(n²) cost but may split coherent clusters across blocks. Coarser blocking risks quadratic slowdown.
  - **Parameterization:** `cluster_selection_epsilon=0.15` in Subtask 3 prevents over-merging in a denser vector space but may increase cluster count and post-merge overhead.
- **Failure signatures:**
  - **HDBSCAN runtime spike:** Indicates a blocking failure (e.g., a block still too large); check block size distribution.
  - **Low recall on new software:** High unmatched rate from KB → inspect embedding similarity distribution; threshold may be too high or training centroids non-representative.
  - **Post-merge explosion:** Many HDBSCAN clusters merging via canonical name → indicates canonicalization too aggressive (e.g., “SPSS” and “SPSS Inc.” collapse incorrectly).
- **First 3 experiments:**
  1. **Threshold sweep:** On validation split, vary KB assignment threshold (0.5–0.8) and measure CoNLL F1 vs. HDBSCAN runtime; select Pareto-optimal point.
  2. **Blocking key ablation:** For Subtask 3, compare (type only) vs. (type + first letter) blocking on a 25% sample; track HDBSCAN time and cluster quality.
  3. **Canonicalization impact:** Ablate abbreviation resolution and non-alphanumeric stripping; evaluate F1 change to quantify normalization contribution.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can the fixed semantic similarity threshold (θ=0.7) for KB matching be adaptively selected or learned to optimize performance across diverse software mention contexts and entity types? The authors state future work could explore adaptive threshold selection.
- **Open Question 2:** Does the proposed blocking strategy for Subtask 3 introduce harmful fragmentation that separates mentions of the same software entity into different blocks, thereby preventing their correct clustering by HDBSCAN? The blocking heuristic assumes true coreferent mentions share a blocking key, which may fail.
- **Open Question 3:** To what extent does the reliance on a static KB of training-set centroids limit the system's ability to recognize and correctly cluster mentions of entirely new software tools not represented in the training data? The system does not discuss novelty detection.
- **Open Question 4:** How effective is the "asymmetry" (one surface form maps to at most one software) in guiding the clustering objective, and could explicit modeling of this constraint improve performance over the current similarity-and-merge post-processing? The pipeline does not enforce this as a hard constraint during clustering.

## Limitations
- **Canonicalization ambiguity:** Exact rules for "canonical name" extraction and KB dictionary construction (e.g., which metadata fields, normalization steps) are unspecified.
- **Exact-match logic uncertainty:** For Subtask 3, it is unclear whether the pre-FAISS canonical name check uses exact equality or substring matching, and its precise order relative to FAISS search.
- **External validity weak:** Neighboring work focuses on event/coreference, not software mentions; no direct evidence for mechanism generalizability to this domain.

## Confidence
- **Mechanism 1 (surface-form duplication):** Medium. Well-described internally, but lacks software-specific empirical validation; break condition unprobed.
- **Mechanism 2 (FAISS centroid KB):** Medium. High scores, but centroid representativeness for diverse software variants is a plausible unaddressed risk.
- **Mechanism 3 (HDBSCAN + blocking):** Medium-Low. Blocking may split true clusters; parameters chosen per subtask without stated rationale or sensitivity analysis.

## Next Checks
1. **Exact-match pre-check ablation:** Run Subtask 3 with/without the pre-FAISS canonical name exact match; quantify F1 impact and assignment distributions.
2. **Blocking integrity analysis:** On a 10% sample, compute average pairwise cosine similarity between mentions sharing entity type but differing first-letter blocks; if inter-block similarity exceeds intra-block, blocking likely splits clusters.
3. **Threshold sensitivity curve:** Using a validation split, sweep KB assignment thresholds (0.5–0.8) and plot CoNLL F1 vs. HDBSCAN runtime; identify Pareto-optimal threshold balancing precision and scalability.
