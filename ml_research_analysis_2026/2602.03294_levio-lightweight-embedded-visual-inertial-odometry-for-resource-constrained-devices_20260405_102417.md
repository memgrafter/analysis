# LEVIO: Lightweight Embedded Visual Inertial Odometry for Resource-Constrained Devices

## Quick Facts
- **arXiv ID:** 2602.03294
- **Source URL:** https://arxiv.org/abs/2602.03294
- **Reference Count:** 40
- **Primary Result:** A VIO pipeline achieving 20 FPS at <100 mW on a GAP9 SoC with <110 kB L1 and ~850 kB L2 memory, and 3.46 m absolute RMSE on EuRoC.

## Executive Summary
LEVIO is a visual-inertial odometry pipeline designed for ultra-low-power embedded devices, such as micro-drones and smart glasses, where conventional VIO systems are too computationally heavy. It achieves real-time six-degree-of-freedom motion estimation at 20 FPS while consuming under 100 mW of power and fitting within tight memory budgets. This is enabled by a hardware-software co-design approach tailored for the parallel RISC-V GAP9 SoC, incorporating optimizations like QQVGA resolution, parallelized feature extraction and RANSAC, and a custom linear algebra library. On the EuRoC dataset, LEVIO attains competitive accuracy (absolute RMSE 3.46 m) without loop closure, demonstrating that high-performance VIO is feasible on severely resource-constrained platforms.

## Method Summary
LEVIO implements a monocular visual-inertial odometry pipeline using ORB features for tracking and IMU pre-integration for motion constraints. The system runs a pose-graph optimization with bundle adjustment on a sliding window to maintain consistency. Key hardware-aware optimizations include: a custom linear algebra library to replace heavy general-purpose BLAS, hierarchical memory management to fit within ~850 kB L2 cache, and parallelization of ORB extraction, feature matching, and RANSAC across the eight cores of the GAP9 cluster. Images are downscaled to QQVGA (160×120) to reduce computational load. The pipeline forgoes loop closure due to memory limitations, focusing on local tracking and optimization. A Python golden model exists for algorithm development, while the production code is written in C and tuned for the GAP9’s fabric controller and cluster cores.

## Key Results
- **Performance:** 20 FPS on a GAP9 SoC with <100 mW power consumption.
- **Memory:** <110 kB L1 and ~850 kB L2 usage.
- **Accuracy:** 3.46 m absolute RMSE on the EuRoC dataset (MH01–MH05) with full pipeline.

## Why This Works (Mechanism)
LEVIO succeeds by deeply co-designing software algorithms with the GAP9’s parallel RISC-V architecture. The use of QQVGA resolution drastically cuts pixel processing, while the ORB feature extractor is parallelized across eight cores to maintain feature throughput. Custom linear algebra routines eliminate overhead from generic libraries, and hierarchical memory management ensures data stays in cache, avoiding slow DRAM accesses. IMU pre-integration reduces the optimization problem size, and the pose-graph is kept small via keyframing. These choices collectively meet the strict 100 mW power budget by minimizing both computation and memory traffic.

## Foundational Learning
- **ORB Features:** Oriented FAST and rotated BRIEF descriptors provide fast, rotation-invariant matching. *Why needed:* Efficient feature extraction and matching are critical for real-time tracking on low-power hardware. *Quick check:* Verify feature detection and descriptor computation times on target hardware match expectations (e.g., <5 ms per frame).
- **IMU Pre-integration:** Summarizes IMU measurements between keyframes into a single motion constraint. *Why needed:* Avoids integrating high-rate IMU data repeatedly during optimization, reducing computational cost. *Quick check:* Check that pre-integrated biases and covariance are correctly updated and used in the factor graph.
- **Pose-Graph Optimization:** Factor graph with poses, biases, and landmarks optimized via Levenberg-Marquardt. *Why needed:* Maintains global consistency by correcting drift through bundle adjustment. *Quick check:* Ensure the optimization window size (e.g., 5–10 keyframes) yields consistent residuals and convergence.
- **RANSAC for Pose Estimation:** Random sample consensus for robust essential/pose matrix estimation. *Why needed:* Handles outliers from incorrect feature matches. *Quick check:* Validate that enough inliers (>25) are found for reliable EPnP pose estimation.
- **Hierarchical Memory Management:** Manual data placement between L1 and L2 caches. *Why needed:* Prevents memory bandwidth bottlenecks and reduces energy use on a scratchpad-based architecture. *Quick check:* Profile L1/L2命中率 (hit rates) and verify no spills to DRAM during normal operation.
- **Parallelization on RISC-V Cluster:** Workload distribution across eight cores for ORB, matching, and RANSAC. *Why needed:* Exploits data-parallelism to meet 20 FPS on a low-clock-speed many-core. *Quick check:* Confirm all worker cores are active and load-balanced via cycle counters.

## Architecture Onboarding
The LEVIO pipeline runs on a GAP9 SoC featuring a fabric controller (FC, single RISC-V core) and a cluster of eight RISC-V cores with shared L2 memory. The FC orchestrates high-level tasks (IMU handling, optimization), while the cluster parallelizes compute-intensive parts (ORB extraction, feature matching, RANSAC). Data flows: camera frames → cluster for ORB → FC for tracking/initialization → cluster for matching/RANSAC → FC for pose-graph optimization. Memory is manually managed: L1 holds active structures (current frame features), L2 holds map data (landmarks, keyframes). Critical path: feature extraction → matching → pose estimation → optimization. Design tradeoffs: QQVGA resolution sacrifices detail for speed; no loop closure saves memory but allows drift. Failure signatures: FPS drop (core underutilization), memory overflow (L1/L2 exceeded), high RMSE (poor parameters or data handling).

## Limitations
- **Optimal configuration parameters** (e.g., window size, thresholds) are not explicitly documented, hindering exact replication of the reported 3.46 m RMSE.
- **Power measurement methodology** is unspecified, making the <100 mW claim difficult to verify without proprietary tools or detailed setup.
- **Memory hierarchy details** (e.g., L1/L2 paging) are incompletely described, risking portability issues across hardware variants.

## Confidence
- **Hardware–software co-design optimizations:** High — tightly coupled to GAP9 and clearly described.

- **Dataset accuracy (3.46 m RMSE):** Low — depends on unreported parameter choices and preprocessing; cannot be validated without internal configuration.
- **Generalizability to other platforms:** Low — design is specialized for GAP9’s cluster architecture and memory hierarchy.
