# From Stories to Cities to Games: A Qualitative Evaluation of Behaviour Planning

## Quick Facts
- **arXiv ID:** 2601.04911
- **Source URL:** https://arxiv.org/abs/2601.04911
- **Reference count:** 11
- **Primary result:** Behaviour planning using Behaviour Sorts Suite and Forbid Behaviour Iterative algorithm generates distinct plan sets across storytelling (3 Aladdin endings), urban planning (2 St Andrews plans), and game evaluation (2 Mario traces), with behaviour diversity count as the primary metric.

## Executive Summary
Behaviour planning addresses the challenge of producing multiple distinct plans for diverse real-world applications. The approach defines an n-dimensional behaviour space through a user-specified Behaviour Sorts Suite (BSS), where each cell encodes a unique combination of feature values. An iterative algorithm, Forbid Behaviour Iterative (FBI), then searches for plans whose behaviours fall into previously unvisited cells, explicitly banning those behaviours in subsequent iterations to enforce diversity. Two implementations are presented: FBI SMT for model-based planning (using SAT/SMT solvers) and FBI LTL for model-free simulator-based planning (using LTL formulae). The method is evaluated in three case studies: generating Aladdin narratives with different marriage endings, producing alternative St Andrews land-use plans with varying sustainability and diversity scores, and creating distinct Super Mario 1-1 traces to assess replayability. The primary outcome is the Behaviour Diversity Count—the number of distinct behaviour cells achieved—demonstrating the framework’s versatility across domains.

The framework’s strength lies in its explicit encoding of diversity as a constraint on behaviour, shifting from post-hoc filtering to an integrated planning process. By offering both model-based and model-free variants, it accommodates domains with or without explicit planning models. The case studies show that even with simple feature definitions, FBI can uncover qualitatively different plans, highlighting its potential for applications where plan diversity is critical, such as creative storytelling, urban design, and game content generation.

## Method Summary
The method begins with the user defining a Behaviour Sorts Suite (BSS) consisting of n features. Each feature has a discrete domain Δ_i, an extraction function ⊙_i(π) that computes the feature’s value for a plan π, and a logical expression (Expr_i) that characterises the value in the target formalism (e.g., LTL for simulator domains). The behaviour space is the Cartesian product Δ_1 × ... × Δ_n. The Forbid Behaviour Iterative (FBI) algorithm maintains a forbidden set Ψ_Ξ of behaviour cells already produced. In each iteration, a BehaviourGenerator_X searches for a plan whose behaviour is not in Ψ_Ξ; if it fails, a fallback PlanGenerator_X produces any valid plan. For model-based domains (FBI SMT), the planning problem is encoded as a SAT/SMT formula with additional constraints that forbid the conjunction of feature assignments corresponding to cells in Ψ_Ξ. For model-free domains (FBI LTL), a tree-search planner (e.g., A*) checks LTL formulas against partial traces during expansion, rejecting any that violate a forbidden behaviour. The loop terminates when k distinct behaviours are found or the behaviour space is exhausted. The evaluation uses Behaviour Diversity Count—the number of distinct behaviour cells among generated plans—as the primary metric, demonstrated in storytelling (PDDL, FBI SMT), urban planning (simulator, FBI LTL), and game evaluation (emulator, FBI LTL with specialised A*).

## Key Results
- Storytelling: Generated 3 distinct Aladdin narratives with different marriage endings (BDC = 3).
- Urban planning: Produced 2 alternative St Andrews land-use plans exhibiting varying sustainability and diversity scores (BDC = 2).
- Game evaluation: Created 2 distinct Super Mario 1-1 traces—one where the enemy is killed, another where it is avoided—to assess replayability (BDC = 2).

## Why This Works (Mechanism)
#### Mechanism 1
- **Claim:** Behaviour planning generates diverse plans by iteratively finding a plan, extracting its behaviour (a point in a user-defined n-dimensional space), and forbidding that exact behaviour in subsequent iterations.
- **Mechanism:** The Forbid Behaviour Iterative (FBI) algorithm (Algorithm 1) alternates between a `BehaviourGenerator_X`, which searches for a plan whose computed behaviour is not in Ψ_Ξ, and a standard `PlanGenerator_X` if no novel behaviour can be found. This explicitly encodes diversity as a constraint on the behaviour space rather than as a post-hoc filter or secondary objective.
- **Core assumption:** That defining diversity via a discrete behaviour space (BSS) and forbidding seen cells is an effective heuristic for producing a set of maximally distinct plans, given the expressive power of the defined features.
- **Evidence anchors:**
  - [section: Algorithm 1] Outlines the iterative forbid-and-regenerate loop central to the mechanism.
  - [section: Background] Defines `BehaviourGenerator_X` as searching for a plan whose behaviour is not in Ψ_Ξ.
- **Break condition:** The loop terminates when either the required number of plans (*k*) is reached or `BehaviourGenerator_X` returns an empty set, signifying the behaviour space is exhausted or no valid plan exists for a remaining cell.

#### Mechanism 2
- **Claim:** The Behaviour Sorts Suite (BSS) provides a qualitative model for diversity by mapping plan outcomes to a Cartesian product of user-defined feature domains.
- **Mechanism:** The user specifies *n* features, each with a discrete domain Δ_i, an extraction function ⊙_i(π) that computes the feature's value for a given plan π, and a feature expression (Expr_i) that defines the value in logical terms. The behaviour of a plan is the n-tuple of its extracted feature values, placing it in a specific cell of the behaviour space BS_ΔΞ = Δ_1 × ... × Δ_n.
- **Core assumption:** That a finite, discretised set of user-interpretable features can adequately capture the notion of "distinctness" for the given planning domain and end-user goals.
- **Evidence anchors:**
  - [abstract] "...explicitly incorporating a diversity model into the planning process... using the Behaviour Sorts Suite to define an n-dimensional behaviour space..."
  - [section: Background] Formal definition of feature components (Δ_i, ⊙_i, Expr_i) and the behaviour space.
- **Break condition:** The mechanism fails if defined extraction functions are uncomputable for generated plans, if feature domains are poorly chosen (e.g., too granular causing premature exhaustion, too coarse causing ambiguous mappings), or if the logical expressions are unsatisfiable given the planning problem.

#### Mechanism 3
- **Claim:** Model-free behaviour planning (FBI LTL) adapts the forbid-regenerate loop to simulator-based domains by using Linear Temporal Logic (LTL) formulae to represent and check behaviour constraints during search.
- **Mechanism:** For model-free problems (no PDDL model), each behaviour dimension is encoded as an LTL formula (e.g., ◇□`killed`). During the tree search (e.g., A*), a generated plan trace is checked against the conjunction of LTL formulae for all forbidden behaviours. A plan is accepted only if it satisfies the goal and violates none of the forbidden LTL specifications.
- **Core assumption:** That LTL is a sufficiently expressive and efficiently checkable formalism to represent the boolean or discretised feature conditions relevant to a simulator's trace, and that the underlying search planner can be modified to incorporate this online pruning.
- **Evidence anchors:**
  - [section: Background] "...the second implementation... uses Linear Temporal Logic (LTL) to specify the behaviour space. Each dimension is expressed as an LTL formula..."
  - [section: Game Evaluation] "...Expr_ee formula will be □`avoided` or ◇□`killed`."
- **Break condition:** The LTL checking becomes a bottleneck if the formula is complex or the trace is long; the approach is limited to boolean/categorical features as per LTL's nature; or the base search planner cannot efficiently incorporate the behavioural pruning without exponential slowdown.

## Foundational Learning
- **Concept: Classical Planning Formulation (PDDL/SAS+)**
  - **Why needed here:** The FBI SMT implementation requires the problem to be encoded in a declarative planning language (like PDDL) to compile it into a satisfiability formula. Understanding states, actions, goals, and plan horizons is essential to define the initial problem before adding diversity constraints.
  - **Quick check question:** Given a simple logistics problem (two packages, two trucks, two locations), write the PDDL `:action` for a truck loading a package, specifying preconditions and effects.
- **Concept: Behaviour Space Design (Feature Engineering)**
  - **Why needed here:** The BSS is entirely user-defined. The quality and diversity of the output depend critically on choosing features (f_i) that are both meaningful to the end-user and computationally decidable from a plan trace. This requires domain expertise to translate high-level goals (e.g., "sustainability", "narrative tension") into measurable, discrete dimensions.
  - **Quick check question:** For the urban planning case, why were sustainability and diversity scores converted into categorical ranges (VL, L, ..., ID) instead of using the raw continuous scores for the FBI LTL implementation?
- **Concept: Linear Temporal Logic (LTL) for Trace Properties**
  - **Why needed here:** FBI LTL uses LTL to specify properties that must hold over an entire plan trace generated by a simulator. One must understand the semantics of LTL operators (□, ◇, U, etc.) to correctly encode a feature like "avoided all enemies" (□`avoided`) versus "killed an enemy eventually" (◇□`killed`).
  - **Quick check question:** Write an LTL formula that expresses "the agent visits location A at least once, and after that, never visits location B."

## Architecture Onboarding
- **Component map:**
  1.  **Diversity Model (BSS):** User input module. Defines features {f_i}, their domains Δ_i, extraction functions ⊙_i, and LTL/Expr specifications.
  2.  **FBI Core Loop:** Orchestrator. Maintains the forbidden behaviour set Ψ_Ξ. Interfaces with either `BehaviourGenerator_X` (constrained) or `PlanGenerator_X` (unconstrained).
  3.  **Solver Interface (X):**
      - *FBI SMT:* Translates planning problem + current behaviour forbid constraints into a SAT/SMT formula. Uses an off-the-shelf solver.
      - *FBI LTL:* Integrates a tree-search planner (e.g., A*). The node expansion step includes a call to an LTL model checker to verify if the partial trace from initial state to the node violates any forbidden behaviour formula.
  4.  **Plan Post-Processor:** Computes the final behaviour tuple for an accepted plan using ⊙_i and updates Ψ_Ξ.
- **Critical path:** Feature definition → Planning problem formulation → Initialize Ψ_Ξ=∅ → Call `BehaviourGenerator_X` → If plan π found: compute `PBehaviour(⊙_Δ, π)`, add π to Ψ_Ξ, forbid its behaviour → Repeat until stop condition. For FBI LTL, this path is embedded within the search tree expansion.
- **Design tradeoffs:**
  - *Model-based (SMT) vs. Model-free (LTL/Simulator):* SMT guarantees completeness (if encoded correctly) but requires a declarative model, which can be brittle for complex real-world dynamics (e.g., urban land-use conversion rules). LTL with a simulator handles complex, procedural dynamics but relies on the simulator's fidelity and the base search planner's effectiveness, and is limited to LTL-expressible features.
  - *Feature Granularity:* Finer-grained domains (more cells) increase potential diversity count but exponentially increase the search difficulty and risk exhausting the space quickly. Coarser domains are easier but may conflate meaningfully different plans.
- **Failure signatures:**
  - *Early termination:* `BehaviourGenerator_X` returns ∅ quickly, suggesting either the behaviour space is too small, features are too restrictive, or the underlying planner cannot find *any* valid plan meeting the forbid constraints.
  - *Low BDC:* Many generated plans map to the same behaviour cell, indicating feature definitions are not discriminative enough (e.g., two different Mario traces both satisfy `avoided` because they never encounter the single Goomba).
  - *Inconsistent behaviours:* Same plan yields different behaviour tuples on different runs, indicating a non-deterministic extraction function or simulator.
- **First 3 experiments:**
  1.  **Storytelling (FBI SMT):** Verify you can generate plans for a simple intentional planning problem (e.g., Aladdin domain) where the single feature is `(married-to ?x ?y)` in the goal. Expected outcome: 3 distinct marriages. Check mapping to Figure 3.
  2.  **Urban Planning (FBI LTL):** Implement a simple grid-based simulator where actions convert cell types. Define two categorical features (Sustainability, Diversity) with 3 buckets each. Verify the planner can produce plans landing in at least two different (S, D) cells within a 10-action horizon. Check output matches pattern of Figure 5b vs 5c.
  3.  **Game (FBI LTL + Specialised Planner):** Using an A* planner with a heuristic for a simple game (like a grid-based Mario clone), define one LTL dimension: `◇□(enemy_killed)` vs `□¬enemy_killed`. Confirm distinct traces are found for a level with one enemy. Validate LTL formula evaluation traces.

## Limitations
- Exact SAT encoding for FBI SMT is not provided, hindering faithful reproduction of the storytelling case study.
- Urban planning simulator details (transformation rules, score calculations) are under-specified, impeding verification of land-use diversity outcomes.
- Game evaluation lacks specifics on A* planner integration, heuristic, and ROM version, making replication of Mario traces difficult.

- Core mechanism (BSS + FBI loop) is sound: Medium
- FBI SMT generates diverse plans for model-based domains: Medium
- FBI LTL adapts to simulator-based domains: Medium
