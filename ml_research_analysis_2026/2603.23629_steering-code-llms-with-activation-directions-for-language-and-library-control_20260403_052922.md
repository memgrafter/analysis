# Steering Code LLMs with Activation Directions for Language and Library Control

## Quick Facts
- arXiv ID: 2603.23629
- Source URL: https://arxiv.org/abs/2603.23629
- Reference count: 3
- Primary result: Code LLM library preferences are linearly steerable via activation interventions, though stronger steering degrades output quality.

## Executive Summary
Large language models for code exhibit default preferences for certain programming languages and libraries even when prompts are neutral. This paper investigates whether these preferences can be controlled by steering the model’s activations along carefully crafted directions. The authors estimate layer-wise steering vectors for five language/library pairs using a difference-in-means approach across three open-weight code models. By adding these vectors to intermediate activations during generation, they achieve large increases in the fraction of code using the target library on neutral prompts. The steering can even override explicit instructions to use a different library. However, effectiveness varies across ecosystems and models, and stronger interventions harm output quality through repetition and incomplete code. The findings suggest that code-style biases are encoded in compact, linearly accessible activation directions.

## Method Summary
The authors construct steering vectors by contrasting model activations on prompts that elicit a target library with those on neutral prompts. Specifically, for a given layer, they compute the mean activation over many responses that use the target library and subtract the mean over neutral responses, yielding a difference-in-means direction. During generation on neutral prompts, they add a scaled version of this vector (α times) to the activations at that layer before continuing forward. They apply this procedure to five language/library pairs (e.g., PyTorch vs TensorFlow) in three open-weight models: CodeGemma-7B, Llama3.1-8B, and another. The intervention's impact is measured by the fraction of generated code that uses the target library, as well as qualitative assessments of output quality across different α values.

## Key Results
- Steering vectors substantially increased target library usage on neutral prompts, often superseding explicit instructions to use a different library.
- Steerability differed by ecosystem: common libraries like Python and NumPy were easier to steer towards than rarer ones like Boost and CuPy; model-wise, CodeGemma-7B exhibited near-complete control while Llama3.1-8B was weaker.
- Higher intervention strength (α) amplified steering but degraded output quality via increased repetition and incomplete code generation.

## Why This Works (Mechanism)
Code LLMs develop internal representations that capture high-level attributes such as programming language idioms and library APIs. These attributes are believed to be encoded in a low-dimensional subspace of the activation space. By aggregating activations from outputs that exhibit a desired attribute (e.g., use of PyTorch) and contrasting with neutral activations, the difference-in-means vector approximates a direction that shifts the model’s distribution toward that attribute. Adding this direction to intermediate activations biases the subsequent layers to generate tokens consistent with the target style. The linearity of the intervention suggests that the model’s behavior in these dimensions is approximately linear, allowing effective steering with a simple additive tweak.

## Foundational Learning
**Activation Interventions**: Modifying neural activations during forward passes to steer model behavior without weight changes. *Why needed*: Enables precise, reversible control over specific model behaviors. *Quick check*: How would you test whether an intervention changes the model’s internal representation or just its output distribution?  
**Difference-in-Means**: A statistical method to estimate a steering vector by averaging activations from two conditions and subtracting. *Why needed*: Provides a simple, computationally cheap way to isolate the signal associated with a desired attribute. *Quick check*: What biases might arise if the two sets of prompts differ in uncontrolled ways?  
**Code Library Preference**: The tendency of code models to default to certain libraries or languages due to training data distribution. *Why needed*: Understanding these defaults is essential for steering towards less common but correct choices. *Quick check*: How could you measure the strength of a model’s inherent library preference?  
**Steering Strength (α)**: The scalar multiplier controlling how far along the steering direction the activation is moved. *Why needed*: Balances the trade-off between achieving the desired attribute and maintaining output coherence. *Quick check*: What symptoms indicate that α is set too high?  
**Linear vs Nonlinear Effects**: The assumption that additive steering suffices, ignoring potential nonlinear interactions. *Why needed*: Simplicity of linear interventions; however, complex decisions may require nonlinear corrections. *Quick check*: How could you detect a nonlinear effect that a linear steering vector misses?

## Architecture Onboarding
*Component Map*:  
Input Prompt -> Tokenization -> Token Embedding -> Transformer Layers (with optional Steering Injection at a chosen layer) -> LM Head -> Softmax -> Token Sampling -> Output Token -> (loop back for next position).

*Critical Path*:  
1. Tokenize the input prompt.  
2. Obtain token embeddings.  
3. Process sequentially through transformer layers. At the predetermined injection layer, add the scaled steering vector to each token’s activation.  
4. After the final layer, apply the language modeling head to produce logits.  
5. Sample the next token (e.g., with temperature).  
6. Append the sampled token to the context and repeat from step 3 until generation ends.

*Design Tradeoffs*:  
- **Injection layer**: Earlier layers affect more abstract representations; later layers directly influence token predictions.  
- **Magnitude α**: Larger α increases steering success but risks repetition, incoherence, or syntactic errors.  
- **Steering vector construction**: Using many prompts yields a more robust direction but may dilute specificity; single-prompt vectors might be noisy.  
- **Model specificity**: Steering vectors are likely model- and even layer-specific, limiting transfer across architectures.

*Failure Signatures*:  
- Repetitive loops (e.g., infinite “while” cycles).  
- Incomplete or truncated code snippets.  
- Syntax errors or mismatched brackets.  
- Generation of irrelevant library imports.  
- Sharp drop in perceived code quality.

*First Three Experiments*:  
1. **Layer Sweep**: Apply the same steering vector at every layer individually to identify which layer yields the strongest and cleanest steering effect.  
2. **α Trade-off Curve**: Systematically vary α and measure both target library usage and quality metrics (e.g., repetition rate, syntax errors) to characterize the quality–steering trade-off.  
3. **Cross-Task Generalization**: Test a steering vector derived from a simple coding task on a diverse set of neutral prompts (e.g., HumanEval problems) to evaluate how well the vector generalizes across different coding contexts.

## Limitations
- Prompt specificity: Steering vectors are derived from a narrow set of prompts; their ability to generalize to diverse tasks remains uncertain.  
- Quality trade-off: Stronger intervention (higher α) improves target library usage but introduces repetition and incomplete code, limiting practical utility.  
- Model scope: Experiments cover only three open-weight models; findings may not extend to closed-source or larger proprietary models.

## Confidence
- Default preferences exist: **High**  
- Steering is effective: **Medium**  
- Variation by ecosystem and model: **High** (observed) / **Medium** (explanatory)  
- Trade-off between strength and quality: **High**  
- Compact steerable directions: **Medium**

## Next Checks
1. Generalize each steering vector across a diverse set of neutral prompts (e.g., HumanEval, MBPP) and measure consistency of target library generation.  
2. Perform dimensionality analysis (e.g., SVD) on activation differences to estimate the intrinsic subspace size and compare steering efficacy using the top principal component versus random directions.  
3. Evaluate functional correctness of generated code under varying α by running unit tests, and quantify executability, syntax errors, and correctness rates.
