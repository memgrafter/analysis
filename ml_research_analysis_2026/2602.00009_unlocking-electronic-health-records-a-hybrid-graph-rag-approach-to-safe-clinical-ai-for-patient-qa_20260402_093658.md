# Unlocking Electronic Health Records: A Hybrid Graph RAG Approach to Safe Clinical AI for Patient QA

## Quick Facts
*   **arXiv ID:** 2602.00009
*   **Source URL:** https://arxiv.org/abs/2602.00009
*   **Reference Count:** 34
*   **Primary Result:** A hybrid Graph RAG system achieved 100% recall on factual queries and a mean expert quality score of 4.25/5 for complex inference tasks with zero reported safety violations.

## Executive Summary
Clinicians face significant cognitive burden from EHR data overload, while standard LLMs are prone to hallucinations and lack context grounding in clinical settings. This paper introduces MediGRAF, a hybrid Graph RAG system designed to safely answer patient-specific clinical questions. It uniquely integrates Neo4j's Text2Cypher for precise traversal of structured relational data with vector similarity search over unstructured clinical narratives. Evaluated on MIMIC-IV data from 10 patients, the system demonstrated perfect recall for factual queries and high expert-rated quality for complex inferences, suggesting a viable path for safe, grounded clinical AI.

## Method Summary
The authors built MediGRAF by first preprocessing MIMIC-IV structured tables and clinical notes from 10 diverse patients. They constructed a Neo4j knowledge graph with eight node types (Patient, Admission, Diagnosis, etc.) and explicit relationships (e.g., `HAS_DIAGNOSIS`). Unstructured note text was chunked, embedded using OpenAI's `text-embedding-3-small`, and stored with HNSW indexing. The hybrid retrieval pipeline runs in parallel: a GPT-4o-mini-powered Text2Cypher module generates and executes Cypher queries on the graph, while a separate vector search retrieves relevant note chunks. Both result sets are concatenated into a single context block, which is fed to GPT-4o for final answer generation. Queries are manually classified by complexity for evaluation.

## Key Results
*   Achieved **100% recall** for factual queries against a curated set.
*   Attained a **mean expert quality score of 4.25/5** for complex inference tasks.
*   Reported **zero safety violations** during evaluation on the test query set.

## Why This Works (Mechanism)
The hybrid design directly addresses the core failure modes of using either pure structured querying or pure vector search alone in clinical QA. **Text2Cypher** provides exact, hallucination-free retrieval of discrete facts (e.g., medication lists, lab dates) from the structured graph, ensuring factual precision. **Vector search** captures the nuanced, contextual information buried in free-text narratives (e.g., clinical reasoning, symptom descriptions) that is not easily formalized in a schema. By merging both contexts, the system grounds the LLM's generation in a comprehensive, multi-modal fact set, dramatically reducing the space for hallucination. The graph's explicit relationships also inherently constrain the retrieval to patient-specific, temporally coherent data, enforcing a basic safety layer against cross-patient contamination.

## Foundational Learning
*   **Graph RAG:** Augments LLMs by retrieving from a knowledge graph, enabling precise multi-hop reasoning. *Why needed:* To answer questions requiring traversal of explicit relationships (e.g., "What diagnoses were associated with this admission's procedures?"). *Quick check:* Can your system answer a query that requires joining three different node types?
*   **Text2Cypher:** Uses an LLM to translate natural language into a Cypher graph query. *Why needed:* Allows non-expert users to query a complex graph database without knowing Cypher syntax. *Quick check:* Test the generated Cypher against the database schema; does it run and return patient-specific results?
*   **Vector Embeddings for Text:** Converts text chunks into dense vectors for similarity search. *Why needed:* To retrieve semantically relevant passages from unstructured clinical narratives. *Quick check:* Do the top-k retrieved chunks for a known fact contain the supporting text?
*   **Clinical QA Evaluation:** Uses a mix of automated metrics (accuracy, recall, F1) for simple facts and expert Likert scales for complex inference. *Why needed:* Simple metrics fail to capture clinical reasoning quality; human judgment is gold-standard for complex tasks. *Quick check:* Would a clinician agree the answer to a complex query is accurate, complete, and relevant?
*   **Safety in Clinical AI:** Focuses on preventing hallucinations, ensuring patient data isolation, and avoiding unsafe recommendations. *Why needed:* Clinical errors have severe consequences; systems must be auditable and reliable. *Quick check:* Can you trace every claim in the answer back to a specific node or text chunk in the source data?
*   **MIMIC-IV Dataset:** A large, de-identified EHR database from a single ICU. *Why needed:* Provides standardized, research-accessible structured and unstructured clinical data for development and benchmarking. *Quick check:* Does your graph contain all expected admissions and notes for your selected patient cohort after preprocessing?

## Architecture Onboarding
**Component Map:** User Query -> Query Classifier -> [Text2Cypher Module -> Neo4j Graph] + [Vector Search Module -> Note Chunks] -> Context Concatenator -> LLM Generator -> Final Answer

**Critical Path:** The end-to-end latency is dominated by the parallel execution of the graph query and vector search, followed by the final LLM generation call. Context concatenation and window management are crucial junctures where failures occur.

**Design Tradeoffs:**
*   **Graph Fidelity vs. Usability:** A richer, more detailed graph schema improves factual precision but complicates Text2Cypher translation and increases query failure risk.
*   **Context Breadth vs. Coherence:** Retrieving more graph nodes and text chunks increases recall potential but risks context overflow, verbosity, and signal dilution.
*   **Automation vs. Safety:** Fully automated query decomposition and result filtering improve scalability but introduce new failure modes that could compromise factual accuracy.

**Failure Signatures:**
*   **Empty or Erroneous Cypher:** Context window mismatch or schema misunderstanding in Text2Cypher prompt leads to invalid queries.
*   **Context Overflow:** Concatenated results exceed the LLM's context window, causing truncation or API errors, especially for broad "hospital-wide" queries.
*   **Irrelevant/Verbose Answers:** LLM generation is unfocused, summarizing retrieved noise instead of synthesizing a concise, accurate response, reflected in low Likert scores for relevance/completeness.
*   **Source Attribution Breakdown:** The flattened context block makes it impossible to determine whether a specific fact came from a structured relationship or a text chunk.

**First Three Experiments:**
1.  **Schema Sanity Check:** For a test patient, manually write a simple Cypher query (e.g., "List all diagnoses for admission X"). Verify the expected nodes/relationships exist and return correct data. Then, run the Text2Cypher module with the same natural language query and compare the generated Cypher and results.
2.  **Component Isolation Evaluation:** Run the full pipeline on a small set (e.g., 5) of factual queries, but capture and evaluate only the *graph results* and only the *vector results* separately against ground truth. Measure precision/recall of each modality in isolation to understand its individual contribution.
3.  **End-to-End Smoke Test:** Execute the complete hybrid pipeline on 3-5 pre-selected QA pairs (one simple, one medium, one complex). Log: generated Cypher, vector search results, final context token count, generated answer, and a manual pass/fail against known ground truth. This validates integration and identifies the first bottleneck.

## Open Questions the Paper Calls Out
1.  Does integrating Text2Cypher with vector embeddings yield superior clinical QA performance compared to using either method alone, especially for queries requiring both structured traversal and unstructured semantic search?
2.  How does MediGRAF's performance and resource usage scale with increasing patient cohort size and document complexity, and what architectural optimizations are needed for hospital-wide deployments?
3.  Can the MediGRAF architecture generalize to diverse EHR systems and institutional data standards without significant performance degradation?
4.  How can the system improve source attribution to trace generated answers back to specific graph nodes or text chunks, enabling clinical auditability?

## Limitations
*   **Evaluation Scale & Generalizability:** Results are based on a very small cohort (10 patients) from a single institution (MIMIC-IV), raising concerns about robustness across diverse patient populations and EHR systems.
*   **Dataset & Reproducibility:** The curated evaluation set of 141 QA pairs and their ground truths is not publicly available, preventing independent validation of the reported 100% recall and 4.25 score claims.
*   **Safety Evaluation Scope:** The "zero safety violations" claim is based on a limited, curated query set and does not include rigorous adversarial or edge-case testing against hallucination on unseen data.

## Confidence
*   **Hybrid Implementation Feasibility:** **Medium** – The pipeline description is clear, but missing hyperparameters (chunk size, top_k, result limiting logic) impede exact replication.
*   **Reported Performance Metrics (100% recall, 4.25 score):** **Low** – Extraordinary results on an unreleased test set cannot be externally verified and may be context-specific.
*   **Schema Design Rationale:** **Medium** – Node types are listed, but full property schemas, constraints, and cardinalities are underspecified.

## Next Checks
