# Bare-Metal Tensor Virtualization: Overcoming the Memory Wall in Edge-AI Inference on ARM64

## Quick Facts
- **arXiv ID:** 2601.03324
- **Source URL:** https://arxiv.org/abs/2601.03324
- **Reference count:** 36
- **Primary result:** Achieves 61.3 tokens/second and 16.3ms median latency on a 110M model, 2.5× speedup over scalar baseline, meeting sub‑200ms psycholinguistic threshold.

## Executive Summary
The paper introduces a bare‑metal approach to LLM inference on edge ARM64 devices, targeting the memory bandwidth bottleneck. By using zero‑copy mmap loading, a cache‑line‑aligned Structure‑of‑Arrays layout, and hand‑tuned NEON SIMD kernels for GEMV, the system avoids standard runtime overheads. Evaluated on an M2 Pro with a 110M parameter model, it achieves 61.3 tokens/second and 16.3ms median latency, a 2.5× improvement over a scalar baseline, while maintaining deterministic performance below the 200ms psycholinguistic threshold.

## Method Summary
The implementation is a C++ header‑only library that memory‑maps the model file directly into the process address space, eliminating data copies. Tensor data is stored in a Structure‑of‑Arrays (SoA) layout with 64‑byte alignment to maximize cache line utilization. Core computation (GEMV and RMSNorm) uses hand‑written NEON SIMD intrinsics with instruction‑level parallelism (four independent accumulators) to hide FMLA latency on Firestorm cores. The system supports Llama 2 architectures with RMSNorm and SwiGLU, and runs autoregressive decoding in a single thread for deterministic latency.

## Key Results
- Throughput: **61.3 tokens/second** on M2 Pro with 110M model.
- Latency: **16.3ms median** per token, with low jitter.
- Speedup: **2.5×** over scalar C++ baseline (24 tok/s).
- Comparison: Proprietary hardware (Apple AMX) achieves higher throughput (~298 tok/s) but the open solution provides transparency and portability.

## Why This Works (Mechanism)

### Mechanism 1: Zero‑Copy Tensor Virtualization via mmap
- **Claim:** Eliminates data copying by mapping the model file into the process address space.
- **Mechanism:** The model file is memory‑mapped with `mmap`; weight tensors become pointers into the OS page cache. On first access, the kernel loads pages via DMA, bypassing user‑space copies.
- **Break conditions:** OS without `mmap`, encrypted or fragmented storage, or memory pressure causing page faults.

### Mechanism 2: Cache‑Line‑Aligned Structure‑of‑Arrays (SoA)
- **Claim:** Guarantees 100% cache line utilization by aligning tensors to 64 bytes and using SoA layout.
- **Mechanism:** All buffers allocated with `aligned_alloc(64)`. SoA ensures SIMD loads (`vld1q_f32`) never cross cache lines.
- **Break conditions:** Non‑64‑byte cache lines, incorrect alignment, or compiler misbehavior.

### Mechanism 3: ILP‑Optimized NEON GEMV Kernel
- **Claim:** 2.5× speedup via four independent accumulators to hide 4‑cycle FMLA latency on Firestorm cores.
- **Mechanism:** The kernel processes four input elements per iteration, using `vmlaq_f32` on four separate accumulators (`v_sum0..3`) to exploit dual‑issue.
- **Break conditions:** Different core microarchitectures (e.g., Cortex‑A78) with different latencies or without dual‑issue may not benefit; register pressure or compiler spills can degrade performance.

## Foundational Learning

### Roofline Model
- **Why needed here:** The roofline analysis shows GEMV is memory‑bound (operational intensity ~2 FLOPs/Byte), justifying focus on bandwidth optimization over compute.
- **Quick check:** For a weight matrix [out, in] and input vector of length `in`, compute FLOPs/Byte using 4‑byte floats. (Answer: ~2 FLOPs/Byte, because 2·|W| FLOPs and |W|+|x|+|y| ≈ |W| bytes for large |W|.)

### Cache Line Alignment
- **Why needed here:** To achieve 100% cache line utilization, every 16‑byte NEON load must fit within a single 64‑byte cache line. SoA with `aligned_alloc(64)` avoids split loads that halve bandwidth.
- **Quick check:** If a 16‑byte NEON load starts at address 0x3E, how many cache lines are fetched? (Answer: 2, because 0x3E–0x4F spans two lines.)

### SIMD Vectorization and Instruction‑Level Parallelism (ILP)
- **Why needed here:** Vectorization and ILP (multiple accumulators) are essential to sustain memory bandwidth on the memory‑bound path. Without them, the CPU would issue scalar operations at a fraction of the bandwidth.
- **Quick check:** Why does using four independent accumulators improve throughput on Firestorm? (Answer: The FMLA instruction has a 4‑cycle latency; four independent chains allow new FMLA every cycle by dual‑issuing, hiding latency.)

## Architecture Onboarding

- **Component map:**  
  Memory layer (mmap arena, aligned_alloc) → Layout layer (SoA, RunState) → Compute layer (NEON kernels) → Loader (binary parser, weight tying) → Driver (bench executable).
- **Critical path:** Token embedding lookup → (for each layer: RMSNorm → Q/K/V projections (GEMVs) → Attention → FFN (SwiGLU, GEMVs) → Output projection (GEMV)) → Logits sampling. Hot loop: GEMV kernel.
- **Design tradeoffs:**
  - Precision vs. bandwidth: FP32 over Int4 for baseline.
  - Single‑threaded vs. multi‑threaded: single‑threaded for deterministic latency.
  - Intrinsics vs. assembly: intrinsics for portability.
  - Zero‑copy vs. explicit loading: zero‑copy reduces footprint but risks page faults.
- **Failure signatures:**
  - High tail latency (P99 >200 ms): page faults or cache thrashing.
  - Segfault on startup: weight‑tying heuristic or alignment issue.
  - Perplexity degradation >0.1%: numerical instability in NEON accumulation.
  - Throughput <50 tok/s on M2 Pro: compiler flags or vectorization failure.
- **First 3 experiments:**
  1. Baseline reproduction: compile and run on M2 Pro, expect ~61.3 tok/s, 16.3 ms median.
  2. Cache alignment validation: replace `aligned_alloc(64)` with `malloc`, expect ~2× drop.
  3. ILP unroll validation: change GEMV to single accumulator, expect ~2.5× slowdown.

## Open Questions the Paper Calls Out

1. **High‑throughput 4‑bit quantization with NEON:** How to implement an int4 kernel using `vdotq_s32` and `vqdmlal` while maintaining precision? (Section 8.2 identifies this as future work.)
2. **Linguistics‑aware mixed‑precision KV caching:** Can mixed precision (Int4 for low‑info tokens, FP16 for high‑info) reduce memory pressure without coherence loss? (Section 9.3 proposes conceptually.)
3. **Scalability to larger models and diverse ARM64:** Does the architecture scale to 7B models and different ARM64 microarchitectures (e.g., Gravaton 3, Raspberry Pi 5) and approach the roofline? (Inferred from limited evaluation.)

## Limitations

- **Hardware specificity:** Optimizations tuned for Apple M2 Pro; portability to other ARM64 CPUs uncertain.
- **Loader fragility:** Unpublished weight‑tying heuristic may fail on model variations.
- **Zero‑copy jitter:** Demand paging can cause tail‑latency spikes, contradicting deterministic claim.
