# Trade-offs in Ensembling, Merging and Routing Among Parameter-Efficient Experts

## Quick Facts
- **arXiv ID:** 2603.03535  
- **Source URL:** https://arxiv.org/abs/2603.03535  
- **Reference count:** 26  
- **Primary result:** SGD-optimized routing nearly matches oracle performance (0.91 vs. 0.75 loss), while merging underperforms uniform ensembling (1.28 loss).

## Executive Summary
This paper studies how to combine multiple independently fine-tuned LoRA experts for task-agnostic multi-task large language models. Using a library of 256 LoRA experts derived from Phi-2 on Flan v2 tasks, the authors compare three fusion strategies: ensembling (output averaging), merging (parameter averaging), and routing (input-dependent fusion). Key findings show that learned non-uniform ensembling improves over uniform averaging; SGD-optimized routing achieves near-oracle performance; merging performs worse than even uniform ensembling, indicating mode connectivity may not hold across diverse tasks; and expert selection via clustering or greedy subsetting retains near-optimal performance with far fewer experts.

## Method Summary
The authors evaluate fusion strategies on a library of 256 LoRA adapters fine-tuned from a Phi-2 base model across Flan v2 tasks. For ensembling, they optimize uniform and learned weights (λ) via SGD on a multi-task training set to weight expert outputs. For merging, they compute weighted averages of LoRA parameters (A, B matrices) with uniform or learned coefficients (global or layer-specific). For routing, they learn an input-dependent function λ(x) (e.g., linear transformation per layer) to merge experts dynamically. They also explore expert selection: model-based clustering reduces the library to 10 cluster experts, and greedy subsetting selects a subset (e.g., 150 of 256). Performance is measured by average multi-task test loss, comparing against an oracle (best expert per task) and baselines like uniform merging and Arrow routing.

## Key Results
- Learned non-uniform ensembling via SGD improves over uniform ensembling.
- SGD-optimized routing achieves the strongest non-oracle performance, nearly matching oracle (0.91 vs. 0.75 loss).
- Merging underperforms even uniform ensembling (1.28 loss), suggesting mode connectivity may not hold across diverse tasks.
- Expert selection via clustering (10 experts) or greedy subsetting (150 experts) retains near-optimal performance.

## Why This Works (Mechanism)

### Mechanism 1: Learned non-uniform ensembling improves over uniform averaging.
- **Claim:** SGD-optimized ensembling weights yield lower average multi-task test loss than uniform ensembling.
- **Mechanism:** The weights λ_i are trained via gradient descent to minimize cross-entropy loss over a dataset covering all tasks, allowing the model to up-weight experts that are more accurate on the input distribution. Because ensembling averages probabilities, weighting effectively shifts the ensemble distribution.
- **Core assumption:** A fixed linear combination of expert predictions can outperform simple averaging; tasks are drawn from a distribution that the training set represents.
- **Evidence:** Abstract states non-uniform ensembling via SGD improves over uniform; Section 3.2.1 describes optimization and reports improvement; related work supports learned weighting benefits.
- **Break condition:** If training distribution is biased or experts are highly correlated, weighting may overfit and harm generalization.

### Mechanism 2: Input-dependent routing approaches Oracle performance by dynamically combining experts.
- **Claim:** Routing with learned input coefficients nearly matches the oracle baseline, significantly outperforming merging and ensembling.
- **Mechanism:** Routing computes coefficients λ_i(x) as a function of the input (e.g., via a learned linear transformation), merging LoRA matrices accordingly. This allows the fused model to adapt per input, effectively selecting the most suitable expert(s) for the task at hand.
- **Core assumption:** The input provides sufficient signal to infer which expert(s) are appropriate; the optimal coefficient can be approximated by a differentiable function.
- **Evidence:** Abstract notes SGD-optimized routing achieves strongest non-oracle performance; Section 4.4 details routing optimization and comparison; Section 4.2 shows simple merging cannot match oracle selection, motivating routing.
- **Break condition:** Routing may fail if the routing function lacks capacity, training data is insufficient to learn input-dependent weights, or expert specializations are too fine-grained for linear combination to capture.

### Mechanism 3: Expert selection via clustering or greedy subsetting retains performance by removing redundancy.
- **Claim:** A large fraction of LoRA experts is redundant; reducing to 10 clustered experts or 150 greedily selected experts recovers near-optimal multi-task loss.
- **Mechanism:** Experts fine-tuned on similar tasks have correlated LoRA parameters; clustering groups tasks with similar update directions, allowing one expert per cluster to serve multiple tasks. Greedy selection picks a subset that covers the task distribution, discarding experts that offer diminishing returns.
- **Core assumption:** Task-specific LoRA updates lie in low-dimensional subspaces; many experts do not add unique knowledge beyond a core set. The validation loss is submodular with respect to expert set, allowing greedy approximation.
- **Evidence:** Abstract notes expert selection retains performance; Section 5.1 shows 58 experts are not even best on their own task; Figure 7 shows diminishing returns; Section 5.2 shows MBC experts improve merging/ensembling relative to private experts.
- **Break condition:** Clustering may merge dissimilar tasks if parameter similarity does not reflect task similarity; greedy selection might miss synergistic combinations if coverage function is not submodular.

## Foundational Learning
- **LoRA (Low-Rank Adaptation)**  
  - *Why needed:* The experts are LoRA adapters; understanding that they consist of low-rank matrices (A, B) is crucial because merging and routing operate directly on these matrices, and their low rank influences computational cost and expressivity.  
  - *Quick check:* How does LoRA represent fine-tuning updates as a product of two low-rank matrices?
- **Model ensembling**  
  - *Why needed:* Ensembling is a primary fusion strategy evaluated; it forms the baseline for comparing inference-costly but strong performance.  
  - *Quick check:* What is the main computational drawback of ensembling at inference time?
- **Input-dependent routing (Mixture-of-Experts)**  
  - *Why needed:* Routing is the top-performing method in the paper; it extends merging by making expert coefficients a function of the input, which is key to near-oracle performance.  
  - *Quick check:* How does routing differ from ensembling in terms of forward passes required at inference?

## Architecture Onboarding
- **Component map:** LoRA expert library -> Fusion engine -> Expert selector (optional) -> Evaluator
- **Critical path:**  
  1. Acquire or train a diverse set of LoRA experts from a common pretrained model.  
  2. Choose a fusion strategy: if inference budget allows, consider ensembling; otherwise, merging or routing.  
  3. If using merging, decide on uniform vs learned coefficients (global or layer-specific).  
  4. If using routing, design a routing function (e.g., linear projection per layer) and train it on a multi-task dataset.  
  5. Optionally, reduce expert set via clustering (re-training cluster experts) or greedy selection.  
  6. Evaluate on all tasks to assess average loss and compute standard error.
- **Design tradeoffs:**  
  - Accuracy vs computation: Routing > ensembling > merging (routing best, ensembling next, merging lowest accuracy). Ensembling requires N forward passes; merging single pass; routing single pass but extra compute for routing coefficients.  
  - Training cost: Learned methods require optimizing coefficients or routing function, adding overhead.  
  - Expert cardinality: More experts increase potential performance but also memory and routing parameters; selection reduces cost.  
  - Flexibility: Routing offers per-input adaptivity; merging is static; ensembling is static but uses multiple models.
- **Failure signatures:**  
  - Merging loss higher than uniform merging: indicates mode connectivity breakdown; may need different merging method or switch to routing.  
  - Routing fails to beat ensembling: possibly underfitting routing function, poor training data, or insufficient training.  
  - Expert selection does not reduce loss: clustering merged incompatible tasks; greedy selection stuck in local optimum.  
  - High variance in test loss across tasks: suggests outliers; consider task-specific routing or separate experts.
- **First 3 experiments:**  
  1. Baseline comparison: Run uniform ensembling, uniform merging, and the Arrow routing baseline to establish performance hierarchy on the full expert set.  
  2. Ablate mode connectivity: For a few random expert pairs, interpolate between their LoRA parameters and evaluate loss on mixed task data; verify non-monotonic loss barriers.  
  3. Test expert selection impact: Apply the proposed MBC clustering (or greedy selection) on the expert library, then re-run the best fusion method (routing) to quantify performance drop vs number of experts retained.

## Open Questions the Paper Calls Out
- **Open Question 1:** Do the relative performance trade-offs between ensembling, merging, and routing generalize to larger language models (e.g., >10B parameters) and different multi-task datasets beyond Flan v2?  
  *Basis in paper:* The paper's experiments are conducted exclusively on Phi-2 (2.8B) and Flan v2 tasks. The authors do not claim broader applicability, leaving open whether the observed patterns hold for other scales or data distributions.  
  *Why unresolved:* The conclusions are based on a single model family and dataset. Model scale and task distribution can affect mode connectivity, expert specialization, and routing efficacy.  
  *What evidence would resolve it:* Replicating the study with diverse base models (e.g., Llama-2, Mistral) and multiple multi-task benchmarks (e.g., BIG-bench, CrossFit) would show if the findings are robust. Systematic variation of model size and task diversity could identify conditions under which the trade-offs change.
- **Open Question 2:** What underlying properties of the loss landscape cause mode connectivity to break down when merging experts fine-tuned on different tasks, and can we predict which expert pairs will have high loss barriers?  
  *Basis in paper:* The paper investigates mode connectivity in Section 4.2 and finds that linear interpolation between experts on different tasks often increases loss, contrary to single-task mode connectivity. They state that this assumption may not hold when models are fine-tuned on diverse tasks, but do not explain why.  
  *Why unresolved:* The paper empirically demonstrates the phenomenon but does not analyze the geometric causes (e.g., curvature, task dissimilarity metrics). Without understanding, we cannot design merging methods that avoid high-loss barriers.  
  *What evidence would resolve it:* Analyzing the Hessian or mode connectivity metrics along interpolation paths for many expert pairs, correlated with task embeddings (e.g., from task descriptions or model representations), could reveal predictors. Theoretical analysis of LoRA-specific parameter spaces might also explain.
- **Open Question 3:** Can we design a parameter-efficient routing mechanism that reduces the number of trainable parameters (currently scaling with number of experts and layers) while maintaining the performance gains of input-dependent fusion?  
  *Basis in paper:* The paper notes that learning input- and layer-dependent routing parameters introduces a significant computational cost. The number of parameters in the routing model scales linearly with the number of experts. They use MBC experts to mitigate but do not propose architectural improvements.  
  *Why unresolved:* The routing approach uses a learned transformation per layer to route among experts. This is computationally heavy. A more efficient design (e.g., shared router across layers, low-rank routing) could maintain benefits with fewer parameters, but it's unexplored.  
  *What evidence would resolve it:* Designing and evaluating alternative routing architectures (e.g., a single router network applied across layers, using factorized routing matrices) on the same benchmark would show if efficiency can be improved without sacrificing accuracy. Ablation studies on router capacity would indicate the minimal required complexity.
- **Open Question 4:** What is the optimal subset of experts for task-agnostic multi-task learning, and can we discover it algorithmically without exhaustive evaluation of all subsets?  
  *Basis in paper:* The paper explores expert selection via model-based clustering and greedy subsetting, showing that using only 150 of 256 experts recovers near-optimal performance. They motivate compressed expert sets but do not claim optimality.  
  *Why unresolved:* The greedy and clustering heuristics may not be optimal. The question of the minimal expert set that maximizes average multi-task performance remains open, and finding it is combinatorial.  
  *What evidence would resolve it:* Developing provably near-optimal subset selection algorithms (e.g., using submodular optimization, or learning a selection policy) and comparing their performance to the greedy baseline on the expert library would demonstrate practical improvements. Theoretical bounds on the trade-off between number of experts and performance could guide design.

## Limitations
- **Reproducibility:** Core expert checkpoints and exact train/val splits are private; independent verification is currently blocked.
- **Generality:** Experiments only on Phi‑2 + Flan v2; unclear if findings extend to larger models or other domains.
- **Implementation gaps:** Key hyperparameters (SGD schedules, routing network specs) are loosely described, introducing ambiguity in performance attribution.

## Confidence
- Non-uniform ensembling > uniform ensembling: **High**
- Routing ≈ oracle performance: **Medium**
- Merging < ensembling: **High**
- Expert selection retains performance: **Medium**
