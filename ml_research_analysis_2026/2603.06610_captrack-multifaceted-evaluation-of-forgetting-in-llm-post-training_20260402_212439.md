# CapTrack: Multifaceted Evaluation of Forgetting in LLM Post-Training

## Quick Facts
- arXiv ID: 2603.06610  
- Source URL: https://arxiv.org/abs/2603.06610  
- Reference count: 40  
- Primary result: Forgetting in LLM post‑training extends significantly beyond factual recall, with pronounced degradation in robustness and default behaviors, and mitigation strategies face a fundamental stability‑plasticity trade‑off.

## Executive Summary
CapTrack introduces a capability‑centric framework to evaluate forgetting in LLMs after post‑training, decomposing it into three groups: latent competence (CAN), default behavioral preferences (WILL), and protocol compliance (HOW). Through comprehensive evaluation across 7 models up to 80B parameters, the study finds that forgetting is not limited to parametric knowledge loss but also affects robustness and default behaviors. Instruction fine‑tuning induces the strongest relative drift, while preference optimization (DPO) is more conservative and can partially recover lost capabilities. Existing mitigation strategies—data selection, model merging, LoRA—all reveal a stability–plasticity trade‑off, with no universal solution. The framework enables multifaceted detection of post‑training‑induced model drift.

## Method Summary
The reproduction task involves implementing the CapTrack evaluation suite to measure relative capability drift between out‑of‑the‑box (OOB) instruction‑tuned models and their post‑trained variants. Inputs include 30 benchmark datasets covering CAN/WILL/HOW, OOB models (LLaMA, Qwen, Gemma families), and post‑training data mixtures for legal/medical domains. Models are post‑trained with instruction fine‑tuning (IFT) or direct preference optimization (DPO) using fixed hyperparameters (e.g., LR 1e‑6 for IFT, 2e‑7 for DPO). Evaluation uses vLLM for efficient inference and GPT‑4o‑mini as a judge for subjective metrics. For each capability, the average relative deviation (%) from the OOB counterpart is computed, providing a continuous measure of forgetting. The method emphasizes relative comparison to isolate post‑training effects.

## Key Results
- Forgetting extends beyond factual recall, with pronounced degradation in robustness (CAN) and default behaviors (WILL).  
- Instruction fine‑tuning (IFT) induces the strongest relative drift across capabilities.  
- Preference optimization (DPO) is more conservative and can partially recover lost capabilities.  
- Mitigation strategies (data selection, model merging, LoRA) all exhibit a fundamental stability–plasticity trade‑off, with no universal solution.

## Why This Works (Mechanism)
The paper does not explicitly analyze a single mechanism; instead, it posits that post‑training alters model behavior in multifaceted ways beyond mere parametric knowledge loss. By decomposing forgetting into CAN (latent competence), WILL (default preferences), and HOW (protocol compliance), CapTrack captures distinct dimensions of model drift. The observed patterns—IFT causing strong drift, DPO being conservative—suggest that different post‑training objectives elicit different degrees of plasticity, with IFT aggressively overwriting existing behaviors while DPO refines preferences more cautiously. The stability–plasticity trade‑off arises because interventions that preserve OOB capabilities (stability) tend to limit in‑domain adaptation (plasticity), indicating inherent tensions in weight updates.

## Foundational Learning
- **Latent Competence (CAN)**: The model's underlying ability to perform tasks correctly. *Why needed*: Forms the baseline capability set. *Quick check*: Does the model solve MMLU or GSM8K accurately without special prompting?  
- **Default Behavioral Preferences (WILL)**: The model's spontaneous choices when multiple valid outputs exist (e.g., helpfulness, safety). *Why needed*: Captures shifts in model "personality" or biases. *Quick check*: Does the model refuse safe requests more often post‑training?  
- **Protocol Compliance (HOW)**: Adherence to specified formats, instructions, or constraints. *Why needed*: Measures instruction following precision. *Quick check*: Does the model follow JSON output schemas consistently?  
- **Post‑Training Objectives (IFT/DPO)**: IFT teaches new tasks via supervised demonstrations; DPO aligns preferences via pairwise comparisons. *Why needed*: Different objectives cause different plasticity. *Quick check*: Which yields higher in‑domain performance but more forgetting?  
- **Relative Deviation Metric**: Percentage change in capability score relative to OOB model. *Why needed*: Isolates post‑training effects from base model quality. *Quick check*: Is the metric robust to baseline score variations?  
- **Stability–Plasticity Trade‑off**: Balancing retention of original capabilities (stability) vs. adaptation to new data (plasticity). *Why needed*: Central challenge in model editing/continuous learning. *Quick check*: Does any mitigation break the trade‑off in CapTrack's experiments?

## Architecture Onboarding
Component map: Base Model (OOB) -> Post‑Training (IFT/DPO) -> Evaluation Suite (30 benchmarks) -> Capability Grouping (CAN/WILL/HOW) -> Relative Deviation Metrics -> Analysis (spider plots, heatmaps)

Critical path: 1) Select OOB model checkpoint; 2) Apply post‑training with specified data mixture and hyperparams; 3) Run evaluation on all benchmarks using vLLM and GPT‑4o‑mini judge; 4) Map each benchmark to CAN/WILL/HOW; 5) Compute average relative deviation per group; 6) Visualize and compare across models/interventions.

Design tradeoffs: - Benchmark coverage vs. cost: 30 datasets provide comprehensive view but increase compute/time. - Judge reliance: Using GPT‑4o‑mini automates subjective evaluation but introduces external model bias and API costs. - Relative metrics: Focus on drift isolates post‑training effects but loses absolute performance context.

Failure signatures: - Judge score divergence: Unexpected low/high scores on grounding or refusal tasks; prompt mismatch likely. - OOM crashes during long‑context evaluation (e.g., RULER‑4k); indicates improper vLLM config or model length limits. - Training loss stagnation: In‑domain metrics (LegalBench) not improving; suggests data loading or loss masking issues. - High variance across seeds: Inconsistent forgetting trends; need multiple runs as in paper.

First experiments: 1) Baseline run: Evaluate OOB model on all 30 benchmarks to establish reference scores; verify judge consistency on a small sample. 2) Single‑model IFT: Apply instruction fine‑tuning to Llama‑3.1‑8B using legal mixture; compute CapTrack relative deviations; confirm IFT causes strong drift in WILL/HOW. 3) Mitigation test: Apply LoRA to same IFT model; measure whether deviation decreases without sacrificing in‑domain performance; check for trade‑off pattern.

## Open Questions the Paper Calls Out
1. How can we design mitigation strategies that selectively protect vulnerable capabilities without sacrificing the benefits of post‑training, thus overcoming the fundamental stability‑plasticity trade‑off? *Basis*: Explicit. *Why unresolved*: Current methods apply global constraints; none selectively safeguard specific capability groups. *Evidence needed*: Capability‑aware interventions (e.g., differential learning rates, gradient routing) tested with CapTrack.  
2. What finer‑grained properties of post‑training data (e.g., task distribution, instruction style, data quality) drive capability‑level forgetting, beyond simple domain specificity? *Basis*: Inferred. *Why unresolved*: Data ablations compared general vs. domain‑specific mixtures but did not decompose data characteristics. *Evidence needed*: Controlled experiments varying data attributes while keeping domain constant, mapped to forgetting signatures.  
3. What explains the systematic differences in forgetting across model families, and can these causes be determined without relying on proprietary training data details? *Basis*: Inferred. *Why unresolved*: Proprietary training pipelines prevent direct analysis; causal factors only speculated. *Evidence needed*: Comparative studies on fully open models with documented training data, or data attribution techniques validated by CapTrack.  
4. Is the stability‑plasticity trade‑off observed across merging and LoRA interventions an inherent limitation of post‑training, or can it be broken through more selective architectural or algorithmic approaches? *Basis*: Inferred. *Why unresolved*: Experiments only used standard global regularization; more fine‑grained interventions might decouple stability from plasticity. *Evidence needed*: Exploration of novel architectures (e.g., capability‑specific modules, modular networks) with CapTrack validation.  
5. Does the CapTrack taxonomy and benchmark suite generalize to other model modifications (e.g., compression, knowledge editing, continual pre‑training) as effectively as it does to post‑training? *Basis*: Explicit. *Why unresolved*: Taxonomy designed with post‑training in mind; different interventions might affect capabilities differently or reveal new dimensions. *Evidence needed*: Application to diverse modifications (quantization, pruning, editing) across multiple families, assessing taxonomy interpretability.

## Limitations
- Exact post‑training data mixtures (legal/medical) are not enumerated or versioned, preventing identical reproduction.  
- Trained checkpoints for the 7 models are unreleased; retraining at scale is prohibitively expensive.  
- Judge prompts for GPT‑4o‑mini are not provided; substitutions may yield divergent scores.  
- Evaluation details (e.g., RULER truncation, LongBench filtering, schema formats) are underspecified.  
- Training specifics (scheduler, warmup steps, seeds) are missing, potentially affecting outcomes.

## Confidence
- CAN/WILL/HOW decomposition: High (framework and benchmarks explicit).  
- Forgetting beyond facts: Medium (depends on judge/eval nuances).  
- IFT strongest drift: Medium (experimentally shown but unverifiable at scale).  
- DPO conservatism & partial recovery: Medium‑Low (subtle, relies on specific checkpoints).  
- Stability–plasticity trade‑off: Medium (pattern observed, but “no universal solution” may be context‑dependent).
