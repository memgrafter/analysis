# Engineering Reasoning and Instruction (ERI) Benchmark: A Large Taxonomy-driven Dataset for Foundation Models and Agents

## Quick Facts
- **arXiv ID:** 2603.02239
- **Source URL:** https://arxiv.org/abs/2603.02239
- **Reference count:** 0
- **Primary result:** A 57,750-record benchmark with a controlled cross-product taxonomy reveals a statistically significant three-tier performance structure among LLMs and bounds reference hallucination risk to 1.7%.

## Executive Summary
The Engineering Reasoning and Instruction (ERI) benchmark introduces a large-scale, taxonomy-structured dataset to evaluate the engineering-specific reasoning and instruction-following capabilities of foundation models and agents. It spans nine engineering fields, 55 subdomains, seven intent types (e.g., calculation, design), and three difficulty tiers, yielding 57,750 records. A multi-LLM study reveals a clear performance stratification: frontier models (GPT-5, Claude Sonnet 4, DeepSeek V3.1) achieve mean scores above 4.3/5.0, while smaller 7B-8B models show higher failure rates and steeper degradation on graduate-level questions. The benchmark employs a convergent validation protocol using cross-provide judges to bound reference hallucination risk, offering a more reliable evaluation than single-judge or text-based approaches.

## Method Summary
The dataset is synthetically generated using a controlled cross-product design: for each combination of field, subdomain, intent, and difficulty, 50 samples are produced, ensuring balanced coverage across 1,155 unique cells. Generation uses a "GPT-5 Mini" model seeded with the tuple and constrained to a strict JSON output schema containing instruction, response, and metadata. Post-processing validates schema adherence, performs deduplication, and applies length filters; a 10% stratified subsample is manually verified. Evaluation uses a panel of three judge models from distinct providers (Claude Haiku 4.5, GPT-4.1 Mini, Mistral Small 3) scoring responses on a 1-5 rubric with dimensions like correctness, units, and verification. Automatic checks (numeric bounds, unit consistency) are applied where applicable. Final scores are the arithmetic mean of the three judges, with hallucination risk bounded by identifying items where frontier models disagree significantly.

## Key Results
- The benchmark achieves broad coverage with 57,750 records across a fixed (field, subdomain, intent, difficulty) cross-product, preventing high-volume classes from dominating aggregate scores.
- Frontier models (GPT-5, Claude Sonnet 4, DeepSeek V3.1) form a top tier with mean scores >4.30/5.0; smaller 7B-8B models exhibit >10% failure rates and sharper performance drops on graduate-level questions.
- A convergent validation protocol using three cross-provider judges limits reference hallucination to 1.7% of items, with inter-judge Spearman correlations of 0.70–0.80.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** A structured, taxonomy-driven cross-product of domain, intent, and difficulty prevents aggregate scores from masking systematic weaknesses.
- **Mechanism:** By enforcing fixed sample counts (e.g., 50 per cell) across 1,155 unique (field, subdomain, intent, difficulty) combinations, the benchmark ensures that performance metrics are attributable to specific axes of engineering competence rather than being dominated by high-volume prompt classes.
- **Core assumption:** Engineering capability is multi-dimensional; a model can excel in some slices (e.g., undergraduate calculations) while failing in others (e.g., graduate-level design), and these weaknesses must be isolatable.
- **Evidence anchors:** 
  - [abstract] "spans nine engineering fields... 55 subdomains, and is crossed with seven intent types and three difficulty tiers, yielding 57,750 records."
  - [section 4.1] "Each field–subdomain–intent–difficulty cell is populated with a fixed number of samples to prevent high-volume prompt classes from dominating overall scores."
  - [corpus] Weak direct corpus support; neighbor papers (e.g., EngiBench) argue for domain-specific structuring but do not implement the same controlled cross-product.
- **Break condition:** If any taxonomy cell is underpopulated or omitted, the ability to diagnose slice-specific failures degrades; aggregate scores become misleading.

### Mechanism 2
- **Claim:** Synthetic generation constrained by explicit output contracts enables scalable, machine-checkable evaluation of discipline-specific reasoning (e.g., unit consistency, constraint awareness) rather than just textual plausibility.
- **Mechanism:** The generator is seeded with a (field, subdomain, intent, difficulty) tuple and instructed to produce responses in a strict JSON schema. The evaluation harness applies automatic checks (e.g., numeric extraction, unit consistency, bound violations) and a rubric scoring verification behavior.
- **Core assumption:** Engineering tasks have deterministic correctness criteria and require specific output formats (e.g., stated assumptions, verification steps) that can be programmatically validated or rubric-scored.
- **Evidence anchors:**
  - [section 5.1] "constrains model outputs to a strict JSON object... to make these records machine-checkable at scale."
  - [section 5.4] "The first layer of scoring applies automatic checks... When the instruction includes explicit numeric bounds... the harness attempts to verify."
  - [section 4.2] Rubric dimensions include "Units/Dimensions," "Verification/sanity check," "Traceability."
- **Break condition:** If the output contract is ignored by models (e.g., free-form text despite JSON instruction) or if automatic checks cannot parse constraints, the benchmark relies solely on LLM-as-a-judge scoring, re-introducing subjectivity.

### Mechanism 3
- **Claim:** A convergent validation protocol using cross-provider, multi-judge averaging with frontier-model agreement analysis empirically bounds hallucination risk in LLM-generated reference answers.
- **Mechanism:** Three judge models from distinct providers (Claude, OpenAI, Mistral) score each model response. Hallucination risk is bounded by identifying items where frontier models (GPT-5, Claude Sonnet 4, DeepSeek V3.1) score ≤3.0 (indicating potential reference error) and measuring inversion rates where smaller models outperform frontiers.
- **Core assumption:** High-capability models from independent training pipelines will converge on correct answers for well-posed engineering problems; divergence indicates reference error or extreme ambiguity.
- **Evidence anchors:**
  - [section 6.1] "panel of three LLM judges from distinct providers... final score... arithmetic mean across all three judges."
  - [section 6.3] "only 1.7% of items met this criterion [frontier models ≤3.0]... inversion rate... less than 0.1%."
  - [section 6.3] "cross-model standard deviations remained low overall (mean σ = 0.74)."
- **Break condition:** If frontier models themselves exhibit systematic errors on certain subdomains (due to training gaps), the convergence argument fails; the 1.7% bound underestimates true hallucination.

## Foundational Learning
- **Concept: Taxonomy-Driven Dataset Design**
  - **Why needed here:** ERI’s validity hinges on a balanced, multi-axis taxonomy; without understanding how fields, intents, and tiers interact, one cannot interpret score disparities.
  - **Quick check:** If a model scores 4.0 on undergraduate CALC but 2.5 on graduate DES, what does that imply about its engineering competence?
- **Concept: Synthetic Data Generation with Domain Constraints**
  - **Why needed here:** The scale (57,750 items) and controlled format are only useful if the synthetic process respects engineering correctness criteria and avoids drifting into generic text.
  - **Quick check:** How does seeding generation with a specific (subdomain, intent, difficulty) tuple differ from unconstrained Self-Instruct, and why does that matter for evaluation?
- **Concept: Multi-Judge Evaluation for Reliability**
  - **Why needed here:** Single-judge LLM evaluation is vulnerable to provider-specific biases; the three-judge protocol is central to the claimed hallucination bounding and stable rankings.
  - **Quick check:** Why does the paper use judges from three different providers instead of three instances of the same model?

## Architecture Onboarding
- **Component map:**
  Taxonomy Engine -> Record Generator -> Post-processing Pipeline -> Judge Panel -> Evaluation Harness
- **Critical path:** Seed tuple → Generator → Raw JSONL → Post-processing → Filtered/test split → Judge scoring → Metric aggregation (mean score, failure rate, slice analysis).
- **Design tradeoffs:**
  - *Coverage vs. Cost:* 10% stratified subsampling (≈5,750 items) vs. full dataset evaluation; allows multi-model study but limits detection of ultra-rare failure modes.
  - *Automation vs. Rigor:* LLM judges enable scale but require convergent validation (cross-provider, frontier agreement) to approximate human-like reliability; no human gold standard for full set.
  - *Generality vs. Currency:* Synthetic generation is scalable but references a fixed knowledge cutoff; CODE/DES items may become outdated.
- **Failure signatures:**
  - High inter-judge disagreement (ρ < 0.60) on a slice indicates ambiguous rubric or poorly defined problem.
  - Sudden score drop on a specific subdomain or intent for all models suggests a taxonomy-population error (e.g., mismatched difficulty).
  - Inversion rate >0.1% (small model > frontier) flags potential reference hallucination in that slice.
- **First 3 experiments:**
  1. **Taxonomy Coverage Audit:** Generate a report from the released dataset showing record counts per cell; verify no cell has <50 samples and that distributions match the spec.
  2. **Judge Consistency Sanity Check:** Run the judge panel on a small, manually reviewed subset (e.g., 100 items) and compute pairwise Spearman correlations; expect ρ ≥ 0.70 as in the paper.
  3. **Frontier Model Baseline:** Evaluate GPT-5 and Claude Sonnet 4 on the full test split; confirm mean score >4.30 and that DES is the lowest-scoring intent type, as reported. This validates your harness matches the paper's setup.

## Open Questions the Paper Calls Out
- **Open Question 1:** What methodology should be used to create a human-verified "gold" subset of ERI that provides a reliable calibration anchor for rubric-based scoring across the full taxonomy?
  - **Basis in paper:** [explicit] Section 8.2 identifies this as a roadmap item: "A first roadmap item is a human-verified 'gold' subset that is small enough for expert review yet broad enough to cover multiple fields and intent types. Such a subset would provide a calibration anchor for rubric-based scoring without forcing full human labeling."
  - **Why unresolved:** The current benchmark uses LLM judges with convergent validation, but lacks definitive human-validated reference answers to assess judge reliability and detect subtle engineering reasoning failures that automated scoring might miss.
  - **What evidence would resolve it:** A stratified sampling protocol that selects representative items from all 1,155 cells, expert adjudication by certified engineers across multiple fields, and analysis of judge agreement against this gold standard to measure bias and error rates in the LLM-as-judge approach.
- **Open Question 2:** How can the ERI taxonomy be systematically extended to cover excluded engineering disciplines (biomedical, nuclear, software) while maintaining the cross-product structure and quality control of the original dataset?
  - **Basis in paper:** [explicit] Section 7.4 acknowledges gaps: "ERI still does not cover other disciplines (e.g., biomedical engineering, nuclear engineering, software engineering beyond CODE-type items)" and notes coverage was based on "subdomain salience at the time of taxonomy design rather than principled sampling of all professionally relevant topics."
  - **Why unresolved:** Claims about engineering competence from ERI scores apply only to the nine covered fields; the methodology for expanding to new fields while preserving the controlled coverage and difficulty rubric is unspecified.
  - **What evidence would resolve it:** A replication study generating ERI-style items for a new discipline (e.g., biomedical engineering) using the same generation protocol, with comparative analysis of quality, difficulty calibration, and judge reliability to validate that the taxonomy expansion produces comparable metrics.
- **Open Question 3:** What diagnostic evaluations can distinguish genuine engineering reasoning improvements from benchmark overfitting when models are trained or fine-tuned on ERI?
  - **Basis in paper:** [inferred] Section 7.2 warns of "teaching to the test" dynamics and recommends "out-of-distribution prompts, adversarially underspecified cases, and human review on critical slices" as complements.
  - **Why unresolved:** The standard evaluation uses a fixed held-out split; models may achieve high ERI scores by exploiting dataset-specific patterns without acquiring robust reasoning that generalizes to novel engineering problems with different phrasing, constraint representations, or real-world messiness.
  - **What evidence would resolve it:** Development of controlled perturbation benchmarks (e.g., rephrased questions, added irrelevant constraints, underspecified inputs requiring clarification) and measurement of performance drops relative to standard ERI scores, establishing a generalizability gap metric.
- **Open Question 4:** What maintenance and versioning protocol should govern ERI to ensure its continued relevance as engineering codes, standards, and professional practices evolve?
  - **Basis in paper:** [explicit] Section 7.3 identifies temporal validity issues: "ERI's records reflect the knowledge state... at a fixed point in time... code-related (CODE) and design-oriented (DES) items may reference superseded material" and suggests "periodic refresh cycles to regenerate or manually revise time-sensitive cells."
  - **Why unresolved:** No concrete plan exists for tracking which subdomain-intent-difficulty cells are time-sensitive, how to prioritize updates, or how to version the benchmark to allow meaningful longitudinal comparisons as standards change.
  - **What evidence would resolve it:** A time-sensitivity audit classifying cells by susceptibility to obsolescence (e.g., code citations, safety factors, material properties), coupled with a versioning scheme that retains deprecated items for historical comparison while flagging current-standard equivalents, and a schedule for periodic updates based on standard revision cycles.
- **Open Question 5:** How should ERI be augmented to evaluate whether tool-augmented agentic workflows (e.g., using calculators, solvers, verification tools) actually reduce engineering-specific error modes?
  - **Basis in paper:** [explicit] Section 8.2 roadmap includes: "A second item is a tool-trace extension that includes selected tool-use trajectories as references to enable the evaluation of agentic pipelines that claim reliability gains through structured action."
  - **Why unresolved:** The current benchmark evaluates only monolithic LLM responses; it cannot assess whether incorporating external tools improves outcomes on engineering-critical dimensions like unit consistency, constraint satisfaction, or verification behavior.
  - **What evidence would resolve it:** Collection of tool-augmented solution traces for a representative sample of ERI items, with evaluation comparing error rates on engineering-specific failure modes (silent constraint violations, dimensional inconsistency, missing assumptions) against baseline LLM-only responses, and correlation analysis between tool usage patterns and error reduction.

## Limitations
- **Dataset generation opacity:** Exact model identifiers (e.g., "GPT-5 Mini"), API parameters (temperature, top_p), and generation prompt templates are unreleased, preventing precise regeneration and introducing potential drift between described and actual corpus.
- **Judge protocol opacity:** Specific judge prompt templates, full rubric JSON schema, and malformed output fallback logic are not public; evaluation relies on external scripts whose exact behavior is a black box, affecting score stability and the claimed hallucination bound.
- **Hallucination bound validity:** The 1.7% bound assumes frontier models are near-perfect references; systematic knowledge gaps in these models could cause convergent errors, making the bound an underestimate of true reference error.

## Confidence
- **Taxonomy structure & coverage:** High (directly verifiable from released dataset metadata and cell counts).
- **Performance tiering (frontier vs. small models):** Medium (results depend on exact judge setup and test split replication; claims are strongly supported but require harness confirmation).
- **Hallucination risk bound (1.7%):** Low (method is clear but core assumption—frontier model correctness—is untested against a human gold standard).
