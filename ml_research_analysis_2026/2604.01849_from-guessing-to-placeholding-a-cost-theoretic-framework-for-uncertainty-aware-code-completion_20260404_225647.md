# From Guessing to Placeholding: A Cost-Theoretic Framework for Uncertainty-Aware Code Completion

## Quick Facts
- **arXiv ID:** 2604.01849  
- **Source URL:** https://arxiv.org/abs/2604.01849  
- **Reference count:** 31  
- **Primary result:** APC reduces expected editing costs by 19–50% while preserving standard completion quality.

## Executive Summary
Analysis of 3 million real-world IDE interactions revealed that 61% of code completions are edited or rejected despite high similarity, exposing frequent costly corrections due to forced guessing under uncertainty. The paper proposes Adaptive Placeholder Completion (APC), which strategically outputs placeholders (`<|cursor|>`) at high-entropy token positions instead of incorrect concrete predictions. A cost-theoretic framework formalizes completion as expected user effort minimization, proving APC achieves strictly lower cost than hard completion when conditional entropy exceeds a derived threshold. APC is trained via a two-stage pipeline: supervised fine-tuning on edit-augmented data followed by reinforcement learning with a cost-based reward. Evaluations across 1.5B–14B parameter models show APC reduces expected editing cost by 19–50% while maintaining hard completion rates and edit similarity.

## Method Summary
APC’s training begins with a dataset constructed from filtered user edit logs: model predictions are aligned token-wise with user-edited ground truth; mismatched tokens are replaced with a placeholder token (`<|cursor|>`), yielding balanced samples of hard completion (exact matches) and placeholder completion. The base LLM is fine-tuned via supervised learning on this dataset to generate both concrete tokens and placeholders. Then, reinforcement learning with Group Relative Policy Optimization (GRPO) fine-tunes the model using a cost-based reward that directly penalizes user editing effort (e.g., hallucinations and lazy placeholders). At inference, the policy implicitly decides per token whether to emit a concrete token or placeholder, without requiring explicit entropy computation.

## Key Results
- 61% of code completions were edited or rejected despite high similarity, revealing costly errors from forced guessing under high uncertainty.
- APC reduces expected editing cost by 19–50% across models (Qwen2.5-Coder, CodeGemma, CodeLlama, StarCoder2) while preserving 100% hard completion rate and stable edit similarity.
- Placeholder completion rates reach 60–68%, with ablation studies confirming the necessity of placeholder-augmented training data and the cost-based reward signal.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** APC reduces expected user editing cost compared to hard completion (HC) in high-uncertainty token positions.
- **Mechanism:** APC strategically inserts explicit placeholders (`<|cursor|>`) at positions where the conditional entropy of the next token exceeds a theoretical threshold \(H^*\), trading the high cost of correcting an erroneous concrete prediction (\(C_{HC}\)) for the lower cost of filling a placeholder (\(C_{PC}\)).
- **Core assumption:** \(0 < C_{PC} < C_{HC}\) (Assumption 3.1). Filling a placeholder requires less cognitive and physical effort than identifying, deleting, and re-typing a specific incorrect prediction, especially in high-entropy contexts where errors are likely to be substantive mismatches rather than minor typos.
- **Evidence anchors:**
  - **[abstract]** "61% of code completions were edited or rejected despite high similarity, revealing costly errors from forced guessing under high uncertainty."
  - **[section 3.2]** Derives expected cost equations: \(J_{APC} = \sum_i [m_i C_{PC} + (1-m_i) C_{HC} (1-P_{\text{max}}^{(i)})]\) vs \(J_{HC} = \sum_i C_{HC} (1-P_{\text{max}}^{(i)})\).
  - **[corpus]** No direct counter-evidence found in retrieved neighbors; the concept of uncertainty-aware abstention appears unique to this work's code completion context.
- **Break condition:** If \(C_{PC} \ge C_{HC}\) (violating Assumption 3.1), placeholder insertion would not reduce expected cost, and HC would be superior. This could occur if placeholder navigation/typing overhead in a specific IDE environment exceeds the cognitive cost of editing a near-miss prediction.

### Mechanism 2
- **Claim:** The model learns to adaptively switch between HC and PC strategies via end-to-end training, without requiring explicit entropy computation during inference.
- **Mechanism:** A two-stage training pipeline first instills placeholder generation capability via Supervised Fine-Tuning (SFT) on data augmented with placeholders (constructed from real user edit traces). This is followed by Reinforcement Learning (RL) with a cost-based reward (using GRPO) that directly optimizes for reduced expected user editing cost, not just token similarity.
- **Core assumption:** Models can internalize the context-dependent decision boundary between HC and PC from training data and reward signals, even though the theoretical threshold \(H^*\) is dynamic and varies with context.
- **Evidence anchors:**
  - **[abstract]** "APC is trained via supervised fine-tuning on data constructed from filtered user edit traces, followed by reinforcement learning with a cost-based reward."
  - **[section 4.1.2 & C]** Details the SFT dataset construction (balancing HC/PC instances) and the reward function \(R(\hat{y}, y^*)\) which penalizes hallucinations (\(C_{model}\)) and lazy placeholders (\(C_{gt}\)) differently.
  - **[section 5.3]** Empirical failure of fixed-threshold post-hoc placeholder insertion (Figure 1), proving the necessity of implicit learning.
- **Break condition:** If the training data lacks sufficient coverage of high-entropy scenarios with clear placeholder annotations, the model will not learn to abstain appropriately. Mis-specified reward weights (e.g., \(\alpha_{\text{lazy}}\), \(\alpha_{\text{error}}\)) could lead to over-abstention (excessive placeholders) or under-abstention (insufficient placeholders).

### Mechanism 3
- **Claim:** Placeholder regions correspond to positions of systematically higher conditional entropy compared to positions where HC succeeds.
- **Mechanism:** Human annotators, when constructing the PC benchmark, identify token positions where the ground truth deviates from model predictions in high-uncertainty contexts. These positions inherently carry higher information entropy because the context is insufficient to determine a single probable token.
- **Core assumption:** Human intuition about "ambiguous" code regions aligns with high conditional entropy under the model's own distribution \(P(y_i^* | c, y_{<i}^*)\).
- **Evidence anchors:**
  - **[section D, Figure 2]** Empirical analysis showing "cumulative average entropy for PC regions vs. HC regions. PC regions show substantially higher entropy accumulation."
  - **[abstract]** The 61% statistic indicates frequent model guesses in regions that later require user edits, implying those positions had high uncertainty.
  - **[corpus]** Neighbors like "UNCLE-Grasp: Uncertainty-Aware Grasping" and "Uncertainty-Aware Deployment..." show general interest in uncertainty-aware systems, but none directly validate the entropy-placeholder link for code.
- **Break condition:** If human annotators systematically misidentify placeholder positions (e.g., labeling ambiguous regions that are actually low-entropy for the model), the training data would misalign placeholder insertion with true high-entropy states, degrading APC's cost-minimization guarantee.

## Foundational Learning

- **Concept: Conditional Entropy & Information Theory**  
  - **Why needed here:** The theoretical optimality condition \(H(y_i^* | c, y_{<i}^*) > H^*\) is defined in terms of Shannon entropy. Understanding how entropy quantifies prediction uncertainty at a token position is fundamental to grasping why placeholders are optimal in some contexts.  
  - **Quick check:** Given a token position with two equally likely candidate tokens, what is the conditional entropy? How does that relate to \(P_{\text{max}}\) and the threshold \(\theta = 1 - C_{PC}/C_{HC}\)?

- **Concept: Cost-Minimization Framework vs. Likelihood Maximization**  
  - **Why needed here:** APC shifts the objective from maximizing token probability (standard LM training) to minimizing an expected user effort cost. This requires thinking in terms of downstream interaction costs rather than static prediction accuracy.  
  - **Quick check:** Why would a model with high Exact Match (EM) on a test set still produce high user editing costs in practice? (Hint: Consider the cognitive cost of correcting a wrong but confidently predicted token vs. typing an unknown token from scratch.)

- **Concept: Reinforcement Learning from Custom Reward Signals**  
  - **Why needed here:** The final APC policy is tuned via RL with a reward function that explicitly encodes the theoretical cost model (Sections C.3–C.4). This is not standard RLHF for helpfulness; it's a domain-specific alignment to a quantifiable user cost.  
  - **Quick check:** How does the reward \(R(\hat{y}, y^*)\) differ between a "Structural Correctness" PC output and a "Structural Error" PC output? Why is the penalty for \(\alpha_{\text{error}} \cdot C_{model}\) necessary?

## Architecture Onboarding

- **Component map:**  
  1. Data Construction Pipeline: Filters raw user edit logs → aligns prediction \(\hat{y}\) with edited ground truth \(y^*\) → replaces mismatched tokens with `<|cursor|>` placeholder to create PC instances. Balances HC (exact match) and PC samples.  
  2. SFT Module: Fine-tunes base LLM on the balanced dataset (5k HC, 10k PC) to initialize placeholder generation capability. Preserves HC ability while introducing PC.  
  3. RL Fine-tuning Module (GRPO): Takes SFT model as policy. For each output, computes cost-based reward \(R(\hat{y}, y^*)\) using alignment metrics (ES, \(C_{model}\), \(C_{gt}\)). Groups multiple outputs per prompt for relative normalization (GRPO). Updates policy to maximize reward.  
  4. Inference Engine: During code completion, the policy decoder chooses token-by-token whether to emit a concrete token or the `<|cursor|>` placeholder. IDE plugin interprets `<|cursor|>` as a tab-navigable hole.

- **Critical path:** Real-world log collection → Data filtering & alignment → Manual placeholder validation (for test set) → SFT training → GRPO reward function implementation & RL training → Evaluation on HC/PC benchmarks with Cost metric.

- **Design tradeoffs:**  
  - Placeholder token design: Using a single `<|cursor|>` token is simple but coarse; could extend to typed placeholders (e.g., `<|cursor:string|>`) but adds complexity to training and IDE integration.  
  - Reward shaping: The saturation function \(f(x) = 1 - 1/(1+0.1x)\) prevents catastrophic negative rewards but may compress gradient signals for large errors. Alternative penalty functions (e.g., linear) were not explored.  
  - Training data balance: 5k HC / 10k PC is small relative to typical code LM pre-training. Risk of overfitting to placeholder patterns; could benefit from more diverse or synthetic high-entropy data.

- **Failure signatures:**  
  - Over-abstention: Very high Placeholder Completion Rate (PCR) with low Precision/F1 on PC test. Model defaults to placeholders even in low-entropy regions.  
  - Under-abstention: PCR remains low (near 0%), HC performance degrades post-SFT/RL (HCR drops, Cost high). Model fails to learn PC strategy.  
  - Cost divergence: Expected Cost metric does not decrease relative to base model despite PCR increase. Placeholders are inserted in wrong positions (low-entropy regions) or accompanied by hallucinations (high \(C_{model}\)).  
  - HC degradation: EM or Edit Similarity on the standard HC benchmark drops significantly after APC training, indicating catastrophic forgetting of concrete completion.

- **First 3 experiments:**  
  1. SFT Data Ablation: Compare APC-SFT (trained on aligned data with placeholders) vs. User-Instruction SFT (trained on raw edited code as "correct" completion). Hypothesis: APC-SFT will achieve higher PCR and lower Cost on PC test while maintaining HC performance.  
  2. Reward Function Ablation: Compare GRPO with cost-based reward vs. GRPO with Edit Similarity (ES) reward. Hypothesis: Cost-based reward yields better Cost metric and higher Precision (fewer lazy placeholders) by directly optimizing user effort.  
  3. Fixed-Threshold Baseline: Apply a static entropy/confidence threshold to base model outputs to force placeholder insertion. Hypothesis: This will increase PCR but *increase* Cost (or keep it at base level) because thresholds misalign with context-specific optimal boundary, confirming need for implicit learning.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How can we move from implicitly learned decision boundaries to an interpretable, controllable mechanism for adaptive placeholder insertion that generalizes across diverse coding contexts and model architectures?
- **Basis in paper:** The paper states the entropy threshold H* is "not a fixed constant but rather context-dependent" and that "the optimal decision boundary is a dynamic, high-dimensional surface," motivating an implicit learning approach via SFT and RL. It also shows that a fixed-threshold post-processing heuristic fails to reduce cost.
- **Why unresolved:** The current solution requires training with specific datasets and reward functions, making it opaque and potentially brittle to new environments (e.g., different programming languages, IDE integrations, or user expertise levels). A theoretical or practical method to derive or approximate the dynamic boundary without extensive per-context RL would improve deployability.
- **What evidence would resolve it:** A study demonstrating a plug-and-play uncertainty estimator (e.g., based on model entropy or other uncertainty metrics) that, when plugged into a base model, achieves similar cost reductions as the fully RL-trained APC without model retraining. Success would be shown by consistent cost reductions (>15%) across multiple unseen model families and code domains using the same fixed, interpretable rule.

### Open Question 2
- **Question:** What is the optimal theoretical and practical trade-off between placeholder completion rate (PCR) and cost reduction, and does the observed moderate PCR (60-68%) indicate that models are under-utilizing the APC strategy or that there is a fundamental limit to beneficial abstention?
- **Basis in paper:** Results show placeholder rates "remain moderate rather than extreme" while achieving 19-50% cost reduction. The theoretical framework establishes a condition (H > H*) for when APC is beneficial per token but does not prescribe a global optimal strategy balancing overall system metrics like user disruption or workflow continuity.
- **Why unresolved:** A higher PCR might reduce costs further but could annoy users with excessive placeholders. Conversely, a lower PCR might miss savings. The paper does not analyze the cost-PCR Pareto frontier or model the long-term impact on user trust and adoption. The current evaluation uses a single cost function (1-ES), which may not capture all user effort dimensions.
- **What evidence would resolve it:** A controlled user study varying the PCR (e.g., via adjustable cost sensitivity) to measure total developer task completion time, cognitive load, and satisfaction. An optimal point would emerge where marginal cost reduction from more placeholders is offset by increased user frustration or navigation overhead. Additionally, a theoretical analysis extending the cost model to include a "placeholder annoyance cost" term would provide a formal optimum.

### Open Question 3
- **Question:** To what extent does the performance of APC depend on the quality and representativeness of the training data constructed from filtered user edit traces, and how robust is it to distribution shifts (e.g., new software libraries, coding paradigms, or novice vs. expert developers)?
- **Basis in paper:** The training pipeline starts with "constructing training data from filtered real-world edit logs" and uses a "balanced exposure to both completion paradigms." The PC benchmark is built from these traces and manually verified. However, the paper does not analyze data diversity or potential biases.
- **Why unresolved:** The paper demonstrates effectiveness across model scales but all data originates from an unspecified (likely corporate) environment. It is unclear if the learned placeholder policy generalizes to code written under different constraints (e.g., competitive programming, embedded systems) or by developers with different skill levels. The reliance on edit traces assumes user edits represent the "true" intended code, which may not hold for exploratory or erroneous coding.
- **What evidence would resolve it:** Evaluating the trained APC models on out-of-distribution benchmarks (e.g., HumanEval for functional correctness, SWE-bench for issue resolution) to see if cost reductions hold. Alternatively, analyzing the training data's diversity (languages, API usage, code complexity) and correlating it with APC's performance on corresponding test slices. A failure mode analysis identifying specific contexts where APC increases cost would also clarify limitations.

### Open Question 4
- **Question:** Can the cost-based reward design (GRPO-APC) be disentangled from specific implementation choices (e.g., the saturation function f(x), α parameters) to yield a universal reward function that aligns with human editing effort across different tasks and user populations?
- **Basis in paper:** The ablation study compares GRPO-APC (cost-based) against GRPO-ES (edit-similarity based), showing the former's superiority. The reward function is detailed in Appendix C with specific coefficients (α_lazy = 1.0, α_error = 1.0) and a handcrafted saturation function.
- **Why unresolved:** The reward's hyperparameters were likely tuned on their specific dataset. It is not theoretically derived from a first-principles model of human editing time (e.g., incorporating keystroke dynamics, error comprehension cost). The current function may overfit to the measured cost proxy (1-ES) and may not generalize to other cost definitions or user interfaces (e.g., voice coding).
- **What evidence would resolve it:** A systematic sensitivity analysis of the reward hyperparameters across different cost models (e.g., including placeholder navigation time) and validation against real user editing times logged in an IDE study. A theoretically grounded reward derived from cognitive models of programming would be more robust. Success would be shown by the same reward function working effectively with minimal tuning on a new dataset with a different cost metric.

### Open Question 5
- **Question:** How does APC's collaborative paradigm fundamentally change the nature of the code completion task from a prediction problem to a mixed-initiative interaction, and what new evaluation metrics beyond cost reduction are needed to capture its full impact on developer productivity and code quality?
- **Basis in paper:** The paper frames APC as shifting from "passive prediction" to "uncertainty-aware collaboration," but all evaluations focus on cost (1-ES), EM, ES, and PCR. There is no measure of downstream effects like code correctness, maintainability, or developer workflow continuity. The impact statement mentions "client-side cursor jumping" but provides no data on adoption or usability.
- **Why unresolved:** Reducing editing cost is necessary but not sufficient for productivity. A placeholder might reduce immediate typing but could interrupt flow or lead to incorrect code if the user filling it makes a mistake. The 100% HCR preservation suggests HC ability is maintained, but we don't know if APC's "skeletons" lead to better or worse final code than HC suggestions.
- **What evidence would resolve it:** Longitudinal studies with professional developers using an IDE plugin with APC vs. HC, measuring not only editing time but also code correctness (via tests), bug density, and self-reported cognitive load. New metrics like "collaboration efficiency" (output quality per unit user intervention) or "abstention appropriateness" (precision of placeholder locations) would complement cost. Showing that APC leads to higher-quality code or faster overall task completion would validate the paradigm shift.

## Limitations
- Data construction specifics (alignment algorithm, filtering from 3M logs to 15k samples) not detailed, hindering replication.
- PC benchmark test set is small (N=523), leading to potential metric instability.
- Missing training hyperparameters (SFT learning rate, GRPO group size, KL coefficient) prevents exact reproduction.

## Confidence
- APC reduces cost: **Medium-High** (empirical gains across models but training details unclear)
- Theoretical threshold validity: **Medium** (logic sound but assumptions untested; break condition not eliminated)
- Adaptive learning via implicit boundary: **Medium** (ablations support necessity but sensitive to data/reward)
- Generalization across scales: **High** (consistent improvements from 1.5B to 14B)
