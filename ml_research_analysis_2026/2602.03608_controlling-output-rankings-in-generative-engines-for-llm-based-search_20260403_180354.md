# Controlling Output Rankings in Generative Engines for LLM-based Search

## Quick Facts
- **ArXiv ID:** 2602.03608
- **Source URL:** https://arxiv.org/abs/2602.03608
- **Reference count:** 40
- **Primary result:** CORE achieves average promotion success rates of 91.4% (Top-5), 86.6% (Top-3), and 80.3% (Top-1) across four LLMs, while maintaining fluent and relatively undetectable content.

## Executive Summary
LLM-based search rankings suffer from strong positional bias: items retrieved later (e.g., last) have near-zero probability of appearing in top positions. This paper introduces CORE, a black-box optimization method that appends specially crafted content – string-based, reasoning-based, or review-based – to a target product’s description to override this bias. CORE operates via two modes: (1) shadow-model gradient updates using a local surrogate, or (2) a query-based generator-optimizer loop using the target LLM itself. Evaluated on the new ProductBench dataset (15 categories, 200 products each) across four advanced LLMs (GPT-4o, Gemini-2.5, Claude-4, Grok-3), CORE achieves high promotion success (over 80% for Top-1) and the optimized content remains fluent (perplexity close to original) and relatively undetectable to humans. The work highlights both the efficacy of such manipulation and its potential security risks for LLM-based search systems.

## Method Summary
Given a user query \(q\), an ordered candidate set \(I\) from a retrieval engine, and a target item \(i^*\) (initially last), CORE appends an “optimization content” \(C\) to \(i^*\)’s description to influence the final ranking produced by a synthesizing LLM. Two implementation modes exist.  
- **Shadow-model mode:** A local model (e.g., Llama) is fine-tuned via few-shot prompting to mimic the target LLM’s ranking behavior. Gradients of a ranking loss w.r.t. the target item’s embedding are computed and iteratively updated (Gaussian noise added). The updated embedding is decoded to text producing \(C\).  
- **Query-based (black-box) mode:** An iterative loop runs: a Generator (prompted LLM) drafts \(C\); \(C\) is appended; the target LLM re-ranks; an Optimizer (prompted) compares the new ranking to a desired ranking (usually \(i^*\) at #1) and revises \(C\) if similarity falls below threshold \(\tau\). The loop repeats until success or max iterations.  
Three content types are explored:  
- **String:** High-perplexity non‑linguistic sequences (e.g., repeated characters).  
- **Reasoning:** Step‑by‑step logical argument converging on the target.  
- **Review:** First‑person experiential narrative mimicking a user review.  
Success is measured by Promotion Success Rate (PSR) at Top‑1/3/5; secondary metrics include text perplexity (GPT‑2) and human evaluation of fluency/detectability.

## Key Results
- Average PSR across four LLMs: **91.4% (Top‑5), 86.6% (Top‑3), 80.3% (Top‑1)**; CORE significantly outperforms prior ranking manipulation methods.  
- Reasoning‑ and review‑based strategies match or exceed string‑based success while preserving fluency (perplexity near baseline) and remaining relatively undetectable (human detection rates only slightly above baseline).  
- Simple mitigations (perplexity filtering, pattern blacklists, length limits) prove insufficient, particularly against review‑based content.

## Why This Works (Mechanism)
### Mechanism 1: String-based disruption
- **Claim:** Appending high‑perplexity, non‑semantic strings disrupts the LLM’s positional attention, creating an anomalous signal that distracts next‑token predictions and temporarily boosts the target’s salience.  
- **Mechanism:** The anomalous tokens interfere with the model’s attention patterns, overriding the strong positional prior that normally penalizes late items.  
- **Core assumption:** LLMs are sensitive to token‑level anomalies even when semantic content is minimal.  
- **Evidence anchors:** [abstract] mentions specially crafted content; [section 4.2] shows string‑based achieving ~30–37% Top‑1 promotion; related work on prompt injection notes effects of incoherent prompts.  
- **Break condition:** When the synthesizing LLM applies perplexity‑based filtering or attention calibration that downweights anomalous tokens (detectable via perplexity > 1000).

### Mechanism 2: Reasoning hijacking
- **Claim:** Reasoning‑based insertions align with the LLM’s internal chain‑of‑thought structure, allowing the target to “hijack” the stepwise rationale.  
- **Mechanism:** A constructed multi‑step comparison that concludes with the target as the best option mirrors the model’s CoT template, increasing the chance it adopts that conclusion.  
- **Core assumption:** LLMs that extensively use CoT during synthesis are vulnerable to pre‑emptively seeded reasoning pathways.  
- **Evidence anchors:** [section 3.4.2] describes aligning rationale with user reasoning; [section 4.6] shows reasoning‑based strategies benefit from Generator–Optimizer alignment; [Table 6] reveals performance drops when alignment is poor.  
- **Break condition:** Target LLM does not use prominent CoT, or the Generator’s reasoning style mismatches the target (e.g., GPT‑4o content optimized by Grok‑3).

### Mechanism 3: Review credibility
- **Claim:** Review‑based insertions exploit the LLM’s tendency to treat past‑tense, user‑generated narratives as high‑credibility evidence.  
- **Mechanism:** First‑person, experiential style mimics authentic reviews, which LLMs weight more heavily due to perceived social proof and authenticity, thereby boosting ranking.  
- **Core assumption:** LLMs assign higher relevance to text matching stylistic patterns of genuine user‑generated content compared to neutral descriptions.  
- **Evidence anchors:** [section 4.4] shows review‑based fluency (4.6/5) close to baseline (4.7/5) and low detection (18.4% vs baseline 12%); [section 4.2] review‑based often outperforms reasoning for Gemini‑2.5 and Grok‑3.  
- **Break condition:** The LLM’s synthesis explicitly devalues anecdotal evidence, or the product category (e.g., industrial tools) does not naturally associate with reviews.

## Foundational Learning
- **Positional bias:** The inherent tendency of LLMs to favor items appearing earlier in the input list. *Why needed:* Explains the baseline near‑zero success for last items and underpins the theoretical penalty term \(λk\). *Quick check:* According to Equation 5, how does retrieval position \(k\) affect log‑probability of rank 1? (Answer: subtracts \(λk\), creating exponential penalty.)
- **Shadow‑model approximation:** Using a surrogate model to mimic the target LLM’s ranking behavior for gradient‑based optimization. *Why needed:* Enables efficient optimization without requiring target model internals; theoretical bounds on error (\(δ\)). *Quick check:* What does Assumption C.6 state about the shadow model’s content score error? (Answer: Absolute difference between shadow and target scores is bounded by \(δ\).)
- **Generator–Optimizer loop:** A black‑box iterative process where an LLM generates and revises content based on feedback from the target LLM’s ranking. *Why needed:* Allows optimization for closed‑source models without gradients. *Quick check:* What role does similarity threshold \(τ\) play? (Answer: Controls how strictly candidate updates must remain similar to original content, balancing relevance and manipulation strength.)

## Architecture Onboarding
**Component map:**  
User query \(q\), candidate set \(I\), target item \(i^*\) → Optimization Engine (Shadow‑model or Generator–Optimizer loop) → Content Strategist (String/Reasoning/Review) → Append \(C\) to \(i^*\) → Modified set \(I'\) → Synthesizing LLM (black‑box) → Output ranking \(R(q, I')\).

**Critical path:**  
1. Retrieve initial \(I\) (fixed).  
2. Select target \(i^*\) (last position).  
3. Generate optimization content \(C\) via chosen strategy.  
4. Append \(C\) to \(i^*\) → \(I'\).  
5. Submit \(q\) and \(I'\) to synthesizing LLM.  
6. Observe ranking \(R\); if not desired, iterate (query‑based) or decode (shadow‑model).

**Design tradeoffs:**  
- *Shadow‑model:* Requires compute for gradient updates; effectiveness depends on shadow model fidelity (\(δ\)); faster convergence but needs white‑box or accurate approximation.  
- *Query‑based:* Purely black‑box; slower due to multiple API calls; performance sensitive to Generator–Optimizer alignment.  
- *Content type:* String is fast/simple but high‑perplexity and detectable; reasoning/review are fluent but require longer context and careful prompt design.

**Failure signatures:**  
- *String:* Perplexity > 1000, human detection > 90%, collapses under perplexity filtering.  
- *Reasoning:* Sharp Top‑1 drop when Generator/Optimizer mismatched; sensitive to \(τ\) (performance drops at \(τ=0.5\)).  
- *Review:* Category‑specific underperformance (e.g., Electronics vs. Beauty); vulnerable if review phrases become too formulaic.

**First 3 experiments:**  
1. Baseline verification: Measure PSR@k for unmodified last‑placed items across 15 categories; confirm near 0% success.  
2. Strategy comparison: Run CORE‑String, CORE‑Reasoning, CORE‑Review on ProductBench for all four LLMs; record PSR@5, @3, @1 and perplexity.  
3. Defense stress‑test: Apply perplexity filtering (threshold 50), pattern filtering (predefined phrase list), and length constraints (4000 words) to optimized outputs; measure PSR degradation.

## Open Questions the Paper Calls Out
- **Open Question 1:** *Generalizability beyond product search.* The evaluation is confined to Amazon‑derived ProductBench and limited passage/travel tests. It is unclear if CORE works across diverse domains (e.g., academic, legal) and unstructured data formats. Resolution requires systematic multi‑domain benchmarking.  
- **Open Question 2:** *Validity of the theoretical position bias model.* The analysis assumes a linear position penalty \(λk\); empirical validation across LLMs and queries is missing. Violation could undermine convergence guarantees. Resolution requires controlled experiments with identical content placed at varying positions.  
- **Open Question 3:** *Transfer across model architectures.* Cross‑model tests show performance drops, especially for reasoning/review; shadow‑model experiments only cover similar decoder‑only families. Transfer to fundamentally different architectures (e.g., multimodal) is unknown.  
- **Open Question 4:** *Ecosystem‑level consequences.* Long‑term effects (e.g., arms race, trust erosion, platform adaptations) are not modeled. Resolution would need longitudinal simulations or field experiments.  
- **Open Question 5:** *Robust mitigation strategies.* Simple defenses (perplexity/pattern filtering) fail against fluency‑preserving content. More advanced detectors or architectural changes are required to counter black‑box CORE variants.

## Limitations
- ProductBench dataset is not publicly released; exact queries and retrieved lists are unavailable, hindering exact replication.  
- Shadow‑model optimization lacks full hyperparameters (learning rate, noise schedule, few‑shot prompt details), making precise reconstruction difficult.  
- Evaluation is restricted to four LLMs and fifteen product categories; generalizability to other models or domains remains untested.  
- No real‑world deployment studies; dynamic user interactions and search engine updates could affect CORE’s efficacy.  
- Human detection study had limited sample size; adversarial detectors (stylometric, perplexity‑based) were not thoroughly evaluated.

## Confidence
- CORE achieves high promotion success rates (e.g., 91.4% Top‑5) across four LLMs: **High**  
- The three content types (string, reasoning, review) are effective and exhibit distinct trade‑offs: **High**  
- Optimized content remains fluent (low perplexity) and relatively undetectable to humans: **Medium**  
- Both optimization modes (shadow‑model and query‑based) function as described: **High**  
- The proposed mechanisms (attention disruption, CoT hijacking, review credibility) explain the effectiveness: **Low**

## Next Checks
1. **Shadow‑model replication:** Reimplement the described shadow‑mode; conduct ablations on learning rate, iteration count, and noise level to quantify performance sensitivity and verify reported numbers.  
2. **Independent benchmark construction:** Crawl Amazon top‑10 results for a new category (e.g., “sports equipment”) to create a fresh dataset; run CORE and compare PSR against the paper’s averages to test external validity.  
3. **Adversarial filtering stress‑test:** Apply a perplexity filter (threshold 50) and a repetition‑pattern detector to optimized outputs; measure the resulting drop in PSR for each content type across all target LLMs.
