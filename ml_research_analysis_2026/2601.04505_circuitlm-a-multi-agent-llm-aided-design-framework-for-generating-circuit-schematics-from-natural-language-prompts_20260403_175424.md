# CircuitLM: A Multi-Agent LLM-Aided Design Framework for Generating Circuit Schematics from Natural Language Prompts

## Quick Facts
- arXiv ID: 2601.04505
- Source URL: https://arxiv.org/abs/2601.04505
- Reference count: 40
- Primary result: Achieves up to 88% ERC Pass@1 with Gemini, near-zero fatal errors, and human expert agreement Fleiss' κ=0.82.

## Executive Summary
CircuitLM presents a multi-agent framework that transforms natural language descriptions of embedded systems into accurate, machine-readable circuit schematics in CircuitJSON format. By orchestrating specialized agents—Identification, Retrieval, Electronics Expert, and Generation—the system grounds component choices in a curated knowledge base, employs chain-of-thought reasoning for constraint satisfaction, and applies dual validation (deterministic ERC and LLM-as-Judge) to ensure electrical safety and protocol correctness. Evaluated on 100 prompts across five LLMs, the approach yields ERC Pass@1 rates up to 88% (Gemini) and strong human expert alignment, while drastically reducing token usage compared to zero-shot baselines. The work highlights the synergy between retrieval-augmented generation and structured reasoning for automated hardware design.

## Method Summary
CircuitLM employs a fixed five-stage multi-agent pipeline. First, an Identification Agent extracts component categories from the user prompt via named entity recognition. The Retrieval Agent then performs embedding-based search over a curated local vector database (ChromaDB) to map these categories to exact component records with canonical pin definitions, preventing hallucination of part names and pins. Next, an Electronics Expert Agent uses chain-of-thought prompting to decompose the task and produce a structured wiring plan that encodes power requirements, safety constraints, and pin-level logic. The Circuit Generation Agent synthesizes a CircuitJSON netlist/placement from the pin mappings and the wiring plan. Finally, a Visualizer renders an interactive SVG, while validation consists of a deterministic ERC engine checking for electrical hazards and a separate LLM-as-Judge assessing protocol-level correctness. The pipeline halts if the Retrieval Agent fails to match a component (Out-of-Distribution), ensuring safety. No model training is involved; frozen LLMs are invoked via APIs with engineered prompts. Key metrics include ERC Pass@1, LLM-as-Judge Pass@1, token efficiency (~3000 tokens per run), and human expert agreement.

## Key Results
- ERC Pass@1 up to 88% (Gemini) with near-zero fatal errors; human expert agreement Fleiss' κ=0.82.
- LLM-as-Judge Pass@1 drops to 53% (Gemini), exposing protocol-level semantic gaps missed by ERC.
- Token usage reduced by ~80% (~3000 vs ~15000 tokens) versus zero-shot baseline.

## Why This Works (Mechanism)
### Mechanism 1: Retrieval-Augmented Grounding
- **Claim:** Embedding-based retrieval from a curated component database prevents hallucination of part names and pinouts.
- **Mechanism:** The Retrieval Agent uses vector similarity search over ChromaDB to map vague component mentions (e.g., "sonar") to exact, verified records with fixed pin labels (e.g., "HC-SR04: VCC, GND, TRIG, ECHO"). This canonicalization eliminates invalid pin generation.
- **Core assumption:** The database comprehensively covers the embedded-systems domain and maintains accurate pin definitions.
- **Evidence anchors:** Abstract mentions grounding in a "curated, embedding-powered component knowledge base"; Section III.B describes strict pin canonicalization.
- **Break condition:** When a requested component is absent, an OOD flag stops execution, requiring human intervention—a safety feature.

### Mechanism 2: Chain-of-Thought Constraint Reasoning
- **Claim:** A dedicated CoT phase front-loads electrical constraints, reducing violations in the final schematic.
- **Mechanism:** The Electronics Expert Agent decomposes the prompt and component list into hierarchical sub-tasks (least-to-most prompting) and produces a structured document that explicitly encodes power domains, safety constraints, and wiring logic.
- **Core assumption:** The LLM can follow structured CoT prompts to generate logically consistent, constraint-aware plans for embedded systems.
- **Evidence anchors:** Abstract cites "chain-of-thought reasoning by an electronics expert agent"; Section III.C details high-level engineering reasoning.
- **Break condition:** Omission of critical constraints (e.g., voltage boundaries, pull-up resistors) leads to Major errors flagged later by ERC or the judge.

### Mechanism 3: Dual-Layered Validation
- **Claim:** Combining deterministic ERC with an LLM-as-Judge catches both topological faults and higher-level protocol/logic errors.
- **Mechanism:** ERC performs graph-based checks for immediate hazards (shorts, missing current limiters). A separate QA Agent (LLM-as-Judge) evaluates protocol-level correctness (UART direction, SPI wiring, pin multiplexing) that ERC’s static rules cannot assess.
- **Core assumption:** An LLM meta-evaluator, guided by an error taxonomy, can reliably identify complex, context-aware design flaws.
- **Evidence anchors:** Abstract mentions "Dual-Metric Circuit Validation (DMCV)"; Section IV.D contrasts ERC’s structural focus with the judge’s semantic coverage; Section V.C shows the Pass@1 gap (88% vs 53%).
- **Break condition:** The judge may miss subtle firmware-hardware mismatches or overgeneralize and flag valid designs.

## Foundational Learning
- **Concept: Multi-Agent System Orchestration**
  - **Why needed here:** CircuitLM decomposes hardware synthesis into specialized, sequential roles (Identification, Retrieval, Reasoning, Generation). Understanding handoffs clarifies how each agent constrains and validates the next.
  - **Quick check:** If the Identification Agent returns `["microcontroller", "sensor"]` but the Retrieval Agent’s database lacks the specific sensor model, what happens and why is this a safety feature?

- **Concept: Retrieval-Augmented Generation (RAG) for Technical Grounding**
  - **Why needed here:** LLMs hallucinate component pins and properties. RAG with a curated vector database provides deterministic, canonical references (pin names, electrical specs) to ground generation in physical reality.
  - **Quick check:** How does using a vector database for component lookup differ from simply including a component datasheet in the system prompt, based on the token-efficiency findings?

- **Concept: Chain-of-Thought (CoT) Prompting for Constraint Satisfaction**
  - **Why needed here:** Circuit design must satisfy multiple simultaneous constraints (power, logic levels, protocols). Explicit CoT forces stepwise reasoning before producing a structured output.
  - **Quick check:** According to the paper, what is the risk of removing the CoT agent (as done in the ablation), and which model family performed *worse* without it?

## Architecture Onboarding
**Component Map:**  
Identification Agent (NER) → Retrieval Agent (vector + fuzzy lookup) → Electronics Expert Agent (CoT reasoning) → Circuit Generation Agent (CircuitJSON synthesis) → Visualizer (force-directed SVG). Parallel validation: ERC Engine and QA Agent (LLM-as-Judge).

**Critical Path:**  
Natural language prompt → [Identification] → component list → [Retrieval] → canonical pins → [CoT Reasoning] → wiring plan → [Schematic Generation] → CircuitJSON → [Visualizer] (output) + [ERC] + [QA Agent] (validation). Retrieval is the pivotal grounding point; failure triggers OOD halt.

**Design Tradeoffs:**
1. Token efficiency vs. latency: CircuitLM uses ~3000 tokens/run (targeted retrieval, staged) vs. zero-shot baseline ~15000 tokens (full library injection), but multi-agent calls increase wall-clock latency (~8s vs ~3s).
2. Determinism vs. flexibility: Strict pin canonicalization from the DB ensures validity but limits adaptability to non-cataloged parts; the OOD halt prioritizes safety over "creativity."
3. ERC rigor vs. semantic coverage: ERC catches immediate electrical hazards but cannot verify protocol logic (e.g., I²C address conflicts), necessitating the LLM-as-Judge layer.

**Failure Signatures:**
- **OOD Halt:** Retrieval fails to match a component → pipeline stops. Action: Add component to DB or refine prompt.
- **High LLM-as-Judge failure despite ERC Pass:** Indicates protocol/logic flaws (e.g., miswired UART, missing pull-ups). Action: Improve CoT prompts to address bus protocols.
- **Frequent "Major" ERC errors:** Often logic-level mismatches (3.3V↔5V) or missing current-limiting resistors. Action: Strengthen CoT reasoning about power domains and protective components.

**First 3 Experiments:**
1. End-to-end smoke test: Run a simple prompt (e.g., "Blink an LED with Arduino") through the full pipeline. Verify CircuitJSON structure, ERC passes, and visualization renders.
2. Retrieval ablation: Force a request for a component not in the DB (e.g., a rare sensor). Confirm OOD halt triggers; then inject a similar alias to test fuzzy matching.
3. Constraint stress test: Use an adversarial prompt with mixed-voltage domains (e.g., "Connect a 5V relay and a 3.3V sensor to an ESP32"). Analyze ERC vs. LLM-as-Judge reports; check if CoT reasons about level shifters.

## Open Questions the Paper Calls Out
1. **Simulator-in-the-loop verification:** How would integrating tools like Wokwi or Proteus change assessment of functional correctness? Current evaluation (ERC + LLM-as-Judge) may miss dynamic behavioral faults. Evidence from simulation runs on the 100 prompts would quantify added coverage.
2. **Generalization to analog circuits:** Can the pipeline produce valid analog schematics (e.g., op-amp amplifiers) without redesign? The architecture and component DB are tuned for digital/embedded; analog requires biasing and continuous-time constraints. Evidence: build an analog benchmark, extend DB and ERC, evaluate Pass@1.
3. **Heterogeneous multi-LLM consensus for evaluation:** Does a consensus of multiple LLM judges improve reliability over a single-model judge? The current single judge (Claude Sonnet 4.5) has blind spots; running diverse models and applying majority/debate could reduce false negatives. Evidence: compare consensus Pass@1 and expert agreement against single-judge baseline.
4. **Transpilation to standard netlist formats:** What engineering effort is needed to convert CircuitJSON to KiCad/SPICE netlists? Without a robust transpiler, adoption in industry workflows is hindered. Evidence: implement a transpiler (e.g., to SKiDL), validate by importing into KiCad, measure fidelity and manual correction effort.

## Limitations
- **Undisclosed component database:** The exact schema and content of the curated component knowledge base are not provided, making reconstruction for reproduction difficult and likely to cause OOD halts.
- **Undocumented agent prompts and hyperparameters:** System prompts, few-shot examples, and temperature settings for each agent stage are omitted, yet they critically affect CoT quality and retrieval success.
- **LLM-as-Judge reliability:** The judge itself misses protocol-level flaws (Pass@1 as low as 53%) and may overgeneralize, limiting its effectiveness as a gold-standard validator.

## Confidence
- Retrieval grounding for pin fidelity: High
- Chain-of-thought reasoning for constraint satisfaction: Medium
- Dual-validation catching semantic gaps: High (existence of gap is certain, but LLM-as-Judge reliability is Low)

## Next Checks
1. Reconstruct and stress-test the component DB: Build a minimal viable DB (~50 parts) with public datasheets; intentionally query OOD components to confirm halt mechanism and test fuzzy matching boundaries.
2. Adversarial protocol test suite: Create 20 prompts with known protocol pitfalls (e.g., missing I2C pull-ups, mixed voltage without level shifters). Measure false-negative rate of the LLM-as-Judge on these known-bad circuits.
3. Token efficiency ablation with real DB: Run the full pipeline with the reconstructed DB and measure average token usage; compare against a zero-shot baseline that injects the entire DB text (within context limit) to empirically verify the claimed ~80% reduction.
