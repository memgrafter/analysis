# HabitatAgent: An End-to-End Multi-Agent System for Housing Consultation

## Quick Facts
- arXiv ID: 2604.00556  
- Source URL: https://arxiv.org/abs/2604.00556  
- Reference count: 26  
- Primary result: End-to-end accuracy of 95% on 100 real consultation scenarios (300 Q&A pairs), improving 20 percentage points over the Dense+Rerank baseline (75%).

## Executive Summary
Housing selection is a high-stakes decision requiring reliable multi-constraint consultation. Existing systems often reduce it to opaque ranking with poor factuality and brittle handling of user constraints. HabitatAgent introduces a closed-loop multi-agent architecture featuring verification-gated memory, adaptive hybrid vector-graph retrieval (GraphRAG), evidence-grounded generation, and multi-tier validation with failure-aware remediation. Evaluated on 100 real consultation scenarios (300 multi-turn Q&A pairs) from a Beijing housing platform, it achieves 95% end-to-end accuracy, a 20 percentage point gain over the strongest baseline (Dense+Rerank at 75%). The system significantly outperforms baselines on complex queries, constraint satisfaction, and faithfulness, while maintaining competitive latency.

The four agents work in concert: Memory tracks evolving preferences with verification gates; Retrieval adapts to query complexity via hybrid search; Generation uses task-specific templates and dual-model selection; Validation ensures correctness and triggers remediation when needed. This design yields robust, transparent decision support for housing consultations.

## Method Summary
HabitatAgent’s core is a four-agent pipeline operating in a closed loop. The Memory Agent extracts structured constraints (hard, soft, negative) and a complexity score from user queries, storing them across four layers (conversational, entity, bias, retrieval). Updates are gated by the Validation Agent to prevent preference drift. The Retrieval Agent combines four retrieval methods—dense vector search, BM25, SQL filtering, and Neo4j graph traversal—selected by a complexity-based router; due to missing details of the learned router fθ, a heuristic thresholding on the complexity score is used as an approximation. The Generation Agent classifies the query into one of 14 task types, selects between Qwen-7B (simple) and DeepSeek (complex) based on complexity, and generates responses with inline evidence tags. The Validation Agent applies three checks: fact consistency (±5% of evidence), entity accuracy (>90% match), and compliance (no prohibited terms). On failure, remediation strategies (retrieve-by-entity, relax thresholds, local correction) are invoked. After successful validation, the Memory is updated and the response is delivered, completing the turn. This loop repeats across multi-turn conversations.

## Why This Works (Mechanism)
The system’s success stems from tight integration of verification, adaptation, and remediation across the pipeline. Verification-gated memory prevents unverified information from corrupting long-term preferences, a common failure mode in multi-turn dialogs. Adaptive hybrid retrieval ensures that both semantic similarity and structured constraints (e.g., distances, numeric filters) are captured, which is critical for housing queries. Evidence-grounded generation forces responses to be tied to retrieved facts, reducing hallucinations. Multi-tier validation catches errors early, while failure-aware remediation recovers from mistakes without user intervention. These mechanisms collectively address brittleness in constraint handling and factuality, leading to high accuracy even on complex, evolving consultations.

## Foundational Learning
- **Hybrid retrieval (vector + graph)**: Combines semantic search with relational queries to handle heterogeneous property data. *Why needed*: Pure vector search cannot enforce numeric or spatial constraints. *Quick check*: Verify that graph queries correctly filter properties by subway proximity.  
- **Verification-gated memory**: Updates memory only after validation passes, preventing drift. *Why needed*: Unverified constraints in early turns can cascade into larger errors. *Quick check*: Introduce a false constraint; check that memory does not retain it after a failed validation.  
- **Evidence-grounded generation**: Requires citations to retrieved passages, improving traceability. *Why needed*: High-stakes decisions demand verifiable facts. *Quick check*: Inspect generated responses for evidence_ref tags and cross-check with source documents.  
- **Failure-aware remediation**: Dynamically adjusts retrieval/generation on validation failure. *Why needed*: Avoiding dead-ends preserves user experience. *Quick check*: Simulate a factual discrepancy; confirm that remediation re-retrieves or corrects it.

## Architecture Onboarding
**Component map**: User → Memory Agent → Retrieval Agent → Generation Agent → Validation Agent → Response; if validation fails, loop back to Retrieval/Generation with remediation; after success, Memory Agent updates.

**Critical path**: For each turn: (1) Memory extracts constraints and complexity; (2) Retrieval selects methods via router and retrieves; (3) Generation classifies task, picks model, generates evidence-tagged response; (4) Validation checks consistency, entity accuracy, compliance; (5) If passes, update Memory and respond; else apply remediation (retrieve-by-entity, relax thresholds, local correction) and repeat from step 2 or 3.

**Design tradeoffs**: 
- Verification gating adds latency but improves long-term accuracy.
- Adaptive router (learned fθ) vs heuristic routing: learned router may be more precise but requires training data; heuristic is simpler but may misroute.
- Dual-model generation balances cost (Qwen-7B) and quality (DeepSeek).
- Remediation strategies trade additional retrieval/computation for robustness.

**Failure signatures**:
- Memory drift: Inconsistent preferences across turns (e.g., user contradicts earlier budget).
- Low CSR@5 on complex queries: Retrieval router fails to include necessary graph constraints.
- Low faithfulness: Generation hallucinates details not in evidence.
- Validation loop thrashing: Repeated failures causing high latency.

**First experiments**:
1. **Simple query test**: Run a single-turn query ("apartments under 5000 yuan") and verify retrieval recall and generation correctness; measure baseline latency.
2. **Memory gate test**: Across two turns, present a conflicting constraint (e.g., change budget) and check if Memory updates only after validation passes; observe preference drift if gate is disabled.
3. **Complex query stress**: Issue a multi-constraint spatial query (e.g., "apartments near a subway >1km but <2km, with a school within 500m") and evaluate CSR@5 and end-to-end accuracy; inspect remediation invocations.

## Limitations
- Proprietary dataset and knowledge graph structure hinder exact replication and cross-domain validation.
- Critical implementation details (14 task templates, router fθ training, validation thresholds) are missing, requiring approximations.
- Generalization beyond Beijing housing market remains unproven; accuracy likely drops on new contexts without re-tuning.

## Confidence
- End-to-end accuracy claim (95%): **Medium**  
- Architecture design (closed-loop, verification-gated memory, hybrid retrieval): **Medium-High**  
- Baseline superiority (20 pp over Dense+Rerank): **Medium**

## Next Checks
1. **Router Fidelity Check**: Implement heuristic complexity-based routing and compare CSR@5 on complex queries against the claimed adaptive router; if heuristic yields >5% lower CSR, the learned router’s value is confirmed.
2. **Template Reconstruction Check**: Mine paper examples to reverse-engineer the 14 task templates; use LLM clustering on consultation scenarios to infer task types; if classifier alignment is <80%, the missing templates are a major gap.
3. **Cross-Domain Stress Test**: Apply the reconstructed system to a public multi-turn housing QA dataset (e.g., from real estate forums); if end-to-end accuracy drops >15% relative to 95%, it suggests overfitting to the proprietary corpus.
