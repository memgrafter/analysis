# No Attacker Needed: Unintentional Cross-User Contamination in Shared-State LLM Agents

## Quick Facts
- arXiv ID: 2604.01350
- Source URL: https://arxiv.org/abs/2604.01350
- Reference count: 21
- Primary result: Benign user interactions cause cross-user contamination in 57-71% of cases; write-time sanitization reduces contamination to 6% in conversational settings but 33-41% in code-sharing settings.

## Executive Summary
Shared-state LLM agents, which persist information across user sessions, are vulnerable to unintentional cross-user contamination (UCC). UCC occurs when benign interactions from one user introduce locally valid artifacts—such as semantic conventions, data transformations, or procedural workflows—that later degrade another user's outcomes because the agent misapplies these artifacts outside their original scope. The authors formalize UCC, propose a taxonomy of three contamination types (semantic, transformation, procedural), and evaluate two shared-state mechanisms: shared memory (EHRAgent) and shared conversational context (MURMUR). Experiments on healthcare and Slack datasets show raw shared state leads to contamination rates of 57–71%. A write-time sanitization method (SSI) nearly eliminates contamination in the conversational setting (57%→6%) but leaves substantial residual risk (33–41%) when shared state includes executable artifacts like solution code, because SSI only sanitizes text. Procedural conventions prove hardest to mitigate, and failures often manifest as silent wrong answers, especially in simpler schemas.

## Method Summary
The authors evaluate UCC by constructing source–victim pairs across two shared-state agent implementations. EHRAgent uses a shared memory bank of past interactions (including generated SQL code) and retrieves relevant entries via cosine similarity. MURMUR maintains a persistent conversational context. Source interactions introduce a locally valid convention (e.g., redefining “last year” as “past 12 months”, rounding numbers, or using a specific counting method). Victim tasks are semantically related queries that would succeed without prior contamination. The evaluation measures contamination by comparing victim outputs with and without the preceding source interaction. Three conditions are tested: raw shared state (no sanitization), SSI (a write-time LLM-based sanitizer that rewrites interaction traces to remove scope-bound artifacts), and baseline (clean state). Contamination is judged via exact match for EHRAgent and LLM-as-a-judge for MURMUR. The study uses public datasets MIMIC-III, eICU, and Slack, with GPT-4o as the backbone.

## Key Results
- Under raw shared state, benign interactions cause contamination rates of 57–71% across both agent types and datasets.
- Write-time sanitization (SSI) reduces contamination to 6% in the shared-context setting (MURMUR/Slack) but leaves residual contamination of 33–41% when shared state includes executable artifacts (EHRAgent), because SSI only processes text, not code.
- Procedural contamination (PC) is the hardest to mitigate, with the smallest reduction after SSI (e.g., 44%→41% in MIMIC-III, 64%→50% in eICU). Failures often produce silent wrong answers, particularly in simpler schemas like eICU.

## Why This Works (Mechanism)

### Mechanism 1: Semantic Contamination
- **Claim:** Benign user interactions introduce scope-bound interpretation rules that persist in shared state and are later misapplied to other users.
- **Mechanism:** An agent stores a locally valid semantic convention (e.g., redefining “last year” as “past 12 months”) in shared state without preserving its contextual scope. During later interactions, the retrieval or context-inclusion mechanism surfaces this convention, causing the agent to interpret a new user’s query through the wrong semantic lens.
- **Core assumption:** Shared-state retrieval/context mechanisms do not differentiate between universally valid knowledge and user-specific, context-bound conventions.
- **Evidence anchors:** [abstract] “information that is locally valid for one user can silently degrade another user’s outcome when the agent reapplies it without regard for scope.”; [section 3.3] “a state fragment … written by user us causes a UCC event … when es influences the agent’s decision for uv, despite being locally valid only for the source interaction.”
- **Break condition:** The system preserves and later reuses an interaction artifact that changed the agent’s internal representation of a term or concept for the source user, and that representation is not generalized or tagged with scope metadata.

### Mechanism 2: Transformation Contamination
- **Claim:** Benign user interactions introduce scope-bound data transformation rules that persist in shared state and alter aggregation/normalization for later users.
- **Mechanism:** A user’s request includes a presentation-limited transformation (e.g., rounding, bucketing, binary labeling). The agent stores the resulting solution (often code or a formatted result) in shared state. For a later user, the retrieved solution template or included context applies the same transformation, corrupting the quantitative output.
- **Core assumption:** The shared state retains executable artifacts (code) or result-processing logic that encodes the transformation, and the reusing agent treats these artifacts as canonical rather than context-specific.
- **Evidence anchors:** [section 3.5] “TC conventions … change how the agent aggregates, filters, normalizes, deduplicates, or summarizes information.”; [section 5.5] “TC and SC conventions are typically encoded in specific fields … a single function call for TC (e.g., ROUND) … the convention survives in the solution code and propagates through exemplar reuse.”
- **Break condition:** The shared state contains an executable solution or transformation pipeline that was generated under a user-specific formatting/aggregation constraint, and the agent reuses that pipeline unchanged for a task with different output semantics.

### Mechanism 3: Procedural Contamination
- **Claim:** Benign user interactions introduce scope-bound procedural workflows that persist in shared state and become the default action pattern for later users.
- **Mechanism:** A user’s interaction leads the agent to adopt a specific sequence of tool calls, filtering steps, or counting methodologies. This procedural pattern is stored (as code, a plan, or a confirmed dialogue turn). When serving a later user with a similar but procedurally distinct task, the agent retrieves and executes the stored workflow, producing an incorrect result due to mismatched procedure.
- **Core assumption:** Procedural conventions are not easily localized to a single data field or function; they shape the entire solution structure, making them resistant to text-level sanitization and prone to template reuse.
- **Evidence anchors:** [section 3.5] “PC conventions … change the agent’s action pattern, workflow default, or tool-use sequence.”; [section 5.5] “Unlike TC and SC, a PC convention is not localized … it shapes the entire solution … PC shows the smallest reduction and the most consistent residual across both datasets.”
- **Break condition:** The shared state contains a multi-step solution template or a confirmed procedural preference that alters the agent’s default action sequence for a class of tasks, and the agent lacks a mechanism to re-plan without inheriting the stored procedure.

## Foundational Learning

- **Concept:** Scope-bound artifacts
  - **Why needed here:** UCC fundamentally arises because agents cannot distinguish between knowledge that is universally valid and artifacts (interpretations, transformations, procedures) that are only valid within the narrow context of a single user’s session or task.
  - **Quick check question:** For a given memory entry or context snippet, can you determine if its modification rule would be correct if applied to a different user’s semantically similar but distinct query?

- **Concept:** Shared-state contamination pathways
  - **Why needed here:** Different shared-state mechanisms (memory retrieval vs. persistent context) have different contamination risk profiles. Understanding *how* state is read and written is key to predicting and mitigating UCC.
  - **Quick check question:** Does the agent’s read operation (`R`) surface entire templates/code (high PC/TC risk) or only general semantic facts (higher SC risk)?

- **Concept:** Artifact-level sanitization vs. text-level sanitization
  - **Why needed here:** The paper shows SSI (text-level) fails when shared state includes executable artifacts. Preventative defenses must reason about the *type* of artifact being stored (code, plan, formatted result) not just its surface text.
  - **Quick check question:** If a stored solution code contains a `ROUND()` function, can your sanitizer identify and potentially remove it without breaking the core query logic?

## Architecture Onboarding

### Component Map
St -> R -> f -> W -> h -> St

### Critical Path
1. User `ut` submits query `xt`.
2. Agent calls `R(St, ut, xt)` to get context view `zt`.
3. Agent calls `f(ut, xt, zt)` → produces `(yt, at)`.
4. Agent calls `W(St, ut, xt, yt, at)` → updates to `St+1` (optionally via `h` first).
   - *UCC occurs when `zt` (from Step 2) contains a scope-bound artifact from a prior user’s `W` operation.*

### Design Tradeoffs
- **Utility vs. Safety:** Aggressive sanitization may remove useful reusable patterns; conservative sanitization leaves contamination risk. SSI errs on the side of writing `NONE` if uncertain.
- **Context Length vs. Contamination Risk:** Longer shared context (e.g., full transcripts) increases SC/PC risk but may be needed for complex tasks; structured memory isolates artifacts but risks template copying (TC/PC).
- **Defense Placement:** Write-time (SSI) is simpler but cannot fix artifacts already in stored code; read-time or retrieval-time sanitization might be more precise but adds latency/complexity.

### Failure Signatures
- **Silent wrong answer:** Agent confidently returns a quantitatively or factually incorrect result (common in eICU, simpler schemas).
- **No answer / error:** Agent fails to produce a valid output (common in MIMIC-III, complex schemas where contaminated code breaks).
- **Behavioral drift:** Agent adopts an unexpected workflow or formatting preference not requested by the current user.

### First 3 Experiments
1. **Baseline contamination quantification:** For a set of pre-designed source–victim pairs, measure contamination rate with `SSI` disabled. Expected: 57–71% overall.
2. **SSI efficacy by mechanism:** Run the same pairs with `SSI` enabled. Compare reduction rates between MURMUR (conversational) and EHRAgent (code-inclusive). Expected: Near-zero on Slack, partial reduction on EHRAgent.
3. **Residual failure analysis:** For EHRAgent instances that remain contaminated under `SSI`, classify failure as SC/TC/PC and inspect whether the surviving artifact resides in solution code vs. text fields. Expected: PC and code-embedded TC/SC show highest residual.

## Open Questions the Paper Calls Out

### Open Question 1
How can shared-state agents sanitize conventions embedded in executable artifacts (e.g., SQL code) to prevent UCC, given that text-level sanitization like SSI fails to neutralize code-encoded rules?  
*Basis:* The paper shows SSI nearly eliminates contamination in conversational context but leaves residual risk (33–41%) in EHRAgent where solution code is stored; SSI only sanitizes text, not code.  
*Why unresolved:* Current approaches do not modify code-level artifacts; conventions persist in solution templates and propagate through exemplar reuse.  
*What evidence would resolve it:* Evaluating code-level sanitization techniques (e.g., static analysis, code rewriting) on EHRAgent-style agents, measuring contamination reduction without breaking functionality.

### Open Question 2
Can provenance metadata (e.g., user, task, scope tags) be designed for shared-state agents to enable fine-grained cross-user access control without significant utility loss?  
*Basis:* The discussion proposes tagging artifacts with provenance as a direction, but no implementation or trade-off analysis is provided.  
*Why unresolved:* Unknown overheads, retrieval complexity, and potential information loss from over-tagging; agents may struggle to use metadata correctly.  
*What evidence would resolve it:* Prototyping metadata systems in EHRAgent/MURMUR, measuring accuracy, latency, and memory overheads compared to raw shared state.

### Open Question 3
How effective is dynamic re-validation (re-generating solutions from sanitized specifications instead of reusing templates) at preventing UCC, and what are its computational costs?  
*Basis:* The authors suggest generating fresh solutions from sanitized specifications as a defense, but its feasibility and efficiency are unexplored.  
*Why unresolved:* Re-generation may increase latency and API costs; may not always produce correct solutions if specifications are incomplete after sanitization.  
*What evidence would resolve it:* Compare contamination rates and runtime metrics between template reuse and on-demand re-generation in controlled UCC settings.

### Open Question 4
Why is procedural contamination particularly resistant to text-level sanitization, and can alternative detection methods (e.g., workflow pattern analysis) mitigate it?  
*Basis:* The paper finds procedural contamination shows the smallest reduction after SSI (44%→41% in MIMIC-III, 64%→50% in eICU) and is described as “hardest to mitigate” because it shapes entire solution structures.  
*Why unresolved:* PC conventions are not localized to specific code lines; they affect workflow globally, making them hard to identify and remove via pattern matching.  
*What evidence would resolve it:* Case studies analyzing PC conventions in solution code; developing methods to detect and neutralize workflow-level patterns (e.g., through control-flow analysis or runtime checks).

## Limitations
- Victim task selection algorithm is underspecified, risking evaluation bias.
- SSI prompt adaptation for MURMUR’s multi-turn format is ambiguous; exact sanitization scope unclear.
- Related work corpus shows low citations (avg 0.0) and high FMR (0.535), indicating nascent field with limited external validation.

## Confidence
- UCC existence & baseline contamination rates (57–71%): **High**
- SSI efficacy in text-only settings (Slack: 57%→6%): **High**; with code artifacts (EHRAgent residual 33–41%): **Medium**
- Taxonomy completeness (SC/TC/PC) & generalizability across domains: **Medium**
