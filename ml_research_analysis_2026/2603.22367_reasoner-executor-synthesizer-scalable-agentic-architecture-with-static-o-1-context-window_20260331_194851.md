# Reasoner-Executor-Synthesizer: Scalable Agentic Architecture with Static O(1) Context Window

## Quick Facts
- **arXiv ID:** 2603.22367
- **Source URL:** https://arxiv.org/abs/2603.22367
- **Reference count:** 0
- **Primary result:** The RES architecture achieves constant LLM token cost (mean 1,574 tokens) and eliminates data hallucination for analytical queries over datasets from 42K to 16.3M records by strictly separating deterministic data aggregation from LLM-based processing.

## Executive Summary
The Reasoner-Executor-Synthesizer (RES) architecture addresses the dual challenges of hallucination and linear token cost scaling in Retrieval-Augmented Generation (RAG). It introduces a strict separation of concerns: a Reasoner LLM parses natural language queries into structured plans, an Executor performs deterministic data retrieval and aggregation using zero LLM tokens, and a Synthesizer LLM generates narratives from a fixed-size statistical summary. This design ensures that LLM token usage remains constant (O(1)) regardless of underlying dataset size and prevents hallucination by never exposing raw data to the LLM.

## Method Summary
RES employs a three-layer pipeline without fine-tuning. The Reasoner (Claude Sonnet) converts user queries into JSON plan objects specifying intent, metrics, and filters. The Executor (deterministic code) uses faceted search APIs (e.g., Crossref) to compute aggregates, always returning a JSON summary bounded to ~500–800 tokens. The Synthesizer (Claude Sonnet) consumes this summary to produce a user-facing narrative and chart configuration. All LLM calls use fixed system prompts; no model training is involved.

## Key Results
- **O(1) token complexity:** Mean LLM token cost of 1,574 across datasets ranging from 42K to 16.3M articles, proving constant cost relative to dataset size.
- **Hallucination elimination by construction:** The LLM never processes raw records, eliminating the possibility of inventing unseen data points.
- **Empirical token savings:** Compared to a naive RAG baseline feeding 50 records to the LLM, RES achieved 73.5% savings; extrapolated to 16.3M articles, savings reach 99.9996%.

## Why This Works (Mechanism)
**Mechanism 1: O(1) Token Cost**  
The Executor handles all data processing with deterministic code (e.g., API calls, SQL-like aggregations) and outputs a fixed-size statistical summary (e.g., top-K rankings, aggregated metrics). The Synthesizer LLM only sees this bounded summary plus a constant system prompt, not raw records. This shifts the computational burden from expensive LLM tokens to inexpensive CPU work. The core assumption is that user analytical questions can be answered via aggregated statistics rather than deep reading of individual documents. If a query requires full document interpretation, the system cannot maintain O(1) guarantees.

**Mechanism 2: Hallucination Elimination**  
Because the LLM (Reasoner and Synthesizer) never encounters raw data records, it cannot misremember or invent facts it was never shown. The Reasoner outputs only a structured plan; the Executor returns verified numeric/categorical aggregates; the Synthesizer can only narrate these pre-computed facts. This architectural guarantee avoids the probabilistic pitfalls of long-context RAG. Errors may still arise from bugs in the Executor's deterministic logic (e.g., flawed aggregation), but these are execution faults, not LLM hallucinations.

**Mechanism 3: Computation Trade-off**  
RES does not reduce total computational work over large datasets; it moves O(n) record processing from the LLM (probabilistic, costly per token) to the Executor (deterministic, cheap CPU cycles). This trade-off is favorable because marginal LLM token costs dominate at scale. The Executor's output size remains constant by design, decoupling token cost from data volume.

## Foundational Learning
- **Fixed-Size Statistical Summary Contract**  
  *Why needed:* The O(1) guarantee hinges on the Executor producing a bounded output regardless of dataset cardinality. Understanding which queries admit such summaries is critical.  
  *Quick check:* For "top 10 most published authors," what is the maximum data points the Executor returns, irrespective of total articles? (Answer: 10 author-count pairs.)

- **LLM Context Window Mechanics & "Lost in the Middle"**  
  *Why needed:* RES solves problems caused by long raw contexts: increased hallucination from attention dilution and irrelevant noise.  
  *Quick check:* Why might an LLM answer less faithfully when given 100 relevant documents vs. one? (Answer: Longer contexts introduce noise, reduce focus on key facts, and strain attention mechanisms.)

- **Deterministic vs. Probabilistic Computation Boundaries**  
  *Why needed:* RES's philosophy is to confine LLMs to probabilistic understanding/generation tasks only; deterministic data processing stays in code.  
  *Quick check:* In RES, which layer ensures a journal's 2024 article count is mathematically correct? If that count is wrong, is that a hallucination? (Answer: Executor ensures correctness; if wrong, it's an execution error, not an LLM hallucination.)

## Architecture Onboarding
**Component map:**  
Reasoner -> Executor -> Synthesizer

**Critical path:**  
User query → Reasoner (outputs JSON plan) → Executor (returns fixed-size summary JSON) → Synthesizer (produces narrative) → User. The Executor is the gatekeeper; if it fails or returns an empty summary, the Synthesizer cannot invent data.

**Design tradeoffs:**  
RES sacrifices flexibility for scalability and fidelity. It cannot answer queries requiring semantic interpretation of full documents (e.g., summarization). It demands that the data source support efficient aggregation (e.g., faceted APIs). Complexity shifts to the Executor, which must correctly map plans to deterministic operations.

**Failure signatures:**  
- *Reasoner failure:* Produces invalid JSON (missing fields, bad intent). Symptom: Executor rejects plan.  
- *Executor failure:* API timeout, malformed response, or aggregation bug. Symptom: Empty/invalid summary passed to Synthesizer.  
- *Synthesizer failure:* Generates claims not present in the summary (hallucination *about the summary*). Symptom: Narrative mentions specifics absent from summary fields.

**First 3 experiments:**  
1. **Executor contract test:** For various plans, verify summary JSON never exceeds 800 tokens, even when matching millions of records.  
2. **Reasoner boundary test:** Feed queries requiring full-document reading (e.g., "summarize methodology of paper X"). Confirm Reasoner fails to produce a valid aggregation plan.  
3. **End-to-end scaling test:** Run identical analytical query on 42K and 16.3M record datasets. Measure Synthesizer input size; confirm statistical indistinguishability (~1,574 tokens).

## Open Questions the Paper Calls Out

- What caching strategies can optimize repeated statistical queries without breaking O(1) guarantees or accuracy?
- How can automated fact-checking formally verify RES's hallucination-free property, and what are the verification boundaries?
- For what query classes does the fixed-size summary constraint become insufficient, and how can the architecture adapt to handle variable-size outputs?

## Limitations
- **Query boundary:** Only analytical questions reducible to bounded statistical aggregates (e.g., counts, trends) are supported; full document interpretation tasks are out of scope.
- **Executor correctness dependency:** Hallucination elimination assumes the Executor's deterministic logic is bug-free; code errors propagate as factual inaccuracies.
- **Inflexibility:** Requires data sources with efficient aggregation capabilities (e.g., faceted search, SQL GROUP BY); unsuitable for unstructured or poorly indexed datasets.

## Confidence
- **O(1) Token Scaling:** High (empirically validated across 42K to 16.3M records with constant mean token cost).
- **Hallucination Elimination:** Medium (guaranteed by design if Executor is correct; shifts risk to deterministic code errors).
- **Architectural Boundary:** High (the requirement for aggregatable queries is a clearly stated, fundamental constraint).

## Next Checks
1. **Reasoner boundary stress test:** Systematically provide queries demanding full document reading (e.g., "compare writing styles of papers X and Y"). Verify Reasoner either fails to produce a valid plan or generates an Executor-incompatible intent.
2. **Summary contract enforcement:** Instrument Executor to log exact output size (bytes/tokens) for a diverse query set. Statistically confirm output remains bounded (~500–800 tokens) regardless of result cardinality or dataset size.
3. **Synthesizer faithfulness audit:** Deliberately corrupt Executor summaries (e.g., off-by-one counts). Check if Synthesizer accurately reports corrupted numbers. Accurate reporting indicates propagation of execution errors, not LLM hallucinations.
