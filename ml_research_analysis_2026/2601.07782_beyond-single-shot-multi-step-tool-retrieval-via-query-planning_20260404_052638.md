# Beyond Single-Shot: Multi-step Tool Retrieval via Query Planning
## Quick Facts
- arXiv ID: 2601.07782
- Source URL: https://arxiv.org/abs/2601.07782
- Reference count: 40
- Primary result: TOOLQP, a lightweight multi-step tool retrieval framework, improves nDCG@10 by up to 10.6 points over single-shot dense retrievers and yields downstream gains of +8.3% pass rate on StableToolBench and +2.8% accuracy on API-Bank.

## Executive Summary
Tool retrieval is a critical component for LLM agents operating in large, dynamic tool libraries. Existing single-shot dense retrievers often suffer from semantic misalignment between abstract user requests and technical tool documentation, and they fail on compositional queries that require chaining multiple tools. TOOLQP addresses these limitations by reformulating retrieval as an iterative query planning process. A lightweight planner (1.7B parameters) first decomposes the user query into sub-tasks, then interacts with a retriever to generate targeted search queries, and finally aggregates results using a peak-rank strategy. The system is trained via synthetic trajectory generation, supervised fine-tuning, and reinforcement learning with verifiable rewards (RLVR). On the ToolRet benchmark (44k tools across 35 datasets), TOOLQP achieves state-of-the-art retrieval performance, with large gains over strong baselines, and transfers robustly to unseen retrievers. In end-to-end tool-calling tasks, it delivers substantial improvements, demonstrating the effectiveness of multi-step planning for complex tool environments.

## Method Summary
TOOLQP treats tool retrieval as a sequential decision-making problem. Given a user query, a lightweight planner first produces a task decomposition (a plan) and then interleaves query generation with retrieval: each query is sent to a dense retriever, and the returned top‑k tools are fed back to the planner to inform the next query. The planner stops when it emits a special token, and an aggregator merges all retrieved lists using a peak‑rank strategy. Training proceeds in three stages: (1) synthetic trajectory generation using a teacher model to simulate the interactive process, including both successful and failed query attempts; (2) supervised fine‑tuning of the planner on these trajectories with retrieval feedback in context; (3) reinforcement learning with verifiable rewards (RLVR) where the reward combines retrieval metrics (nDCG@10, completeness), format adherence, and a stopping bonus, optimized via GRPO. The planner works with any off‑the‑shelf dense retriever, making the approach modular and generalizable.

## Key Results
- State-of-the-art retrieval on ToolRet: +10.6 nDCG@10 in‑domain and +7.1 zero‑shot over the base gte‑Qwen retriever; outperforms cross‑encoders and query‑expansion models with 30B parameters.
- Strong transfer: consistent improvements across five unseen retrievers without any retraining.
- Downstream gains: +8.3% pass rate on StableToolBench and +2.8% accuracy on API‑Bank in end‑to‑end tool‑calling tasks.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Decomposing a complex user query into sequential sub‑tasks enables targeted query generation that bridges the semantic gap between high‑level user intent and low‑level tool documentation.
- **Mechanism:** The Planner first generates a natural language plan `P` and breaks the query `q` into sub‑tasks `{s_n}`. Each sub‑task is then addressed with a dedicated search query `q_t`, avoiding the need to compress all intent into a single embedding. This allows the system to focus on functional keywords (e.g., "password modification," "authentication token") that are absent from the original phrasing.
- **Core assumption:** The semantic misalignment stems from abstract goal descriptions ("make high quality") versus technical implementation terms ("lfilter"). Sub‑tasks isolate distinct functional intents, each with clearer lexical overlap with tool documentation.
- **Evidence anchors:** [abstract] "TOOLQP decomposes instructions into sub‑tasks and dynamically generates queries to interact with the retriever, effectively bridging the semantic gap by targeting the specific sub‑tasks required for composition." [section 3.1] "To bridge this gap, TOOLQP first generates a natural language plan P, and then decomposes the user query q into a logical sequence of sub‑tasks {s_n}."
- **Break condition:** If sub‑tasks are poorly decomposed (e.g., overlapping or missing key intents), the generated queries will remain misaligned, failing to retrieve relevant tools.

### Mechanism 2
- **Claim:** Interactive query generation with retriever feedback allows the system to discover inter‑tool dependencies and adapt to dynamic toolset changes, which a single static query cannot.
- **Mechanism:** After each query `q_t`, the system observes retrieval results `O_t`. This feedback informs the next query `q_{t+1}`. For example, retrieving a tool that requires a specific input argument may prompt a subsequent query for the prerequisite tool that provides that argument.
- **Core assumption:** The retriever's top‑ranked results contain signals about implicit dependencies (e.g., a forecasting tool's documentation mentioning a required `region_id` from a lookup utility). Trial‑and‑error within the planning trajectory surfaces these dependencies.
- **Evidence anchors:** [abstract] "interactively generates targeted search queries using feedback from the retriever" [section 3.1] "This feedback loop addresses the limitations of single‑shot retrieval by allowing the model to dynamically adjust its strategy based on the retrieval feedback." [section 5, Figure 2] Qualitative example where TOOLQP retrieves `GetUserToken` as a prerequisite for `ModifyPassword`, while baselines fail.
- **Break condition:** If the retriever's top‑k results are consistently irrelevant or the dependency chain is too deep/long, the interactive loop may not converge to a complete tool set within a fixed number of turns.

### Mechanism 3
- **Claim:** Peak‑rank aggregation (assigning final rank based on the highest rank a tool achieved across any query) prevents bias toward sub‑tasks that required more query attempts, leading to more balanced and accurate final rankings.
- **Mechanism:** Unlike Reciprocal Rank Fusion (RRF), which averages ranks and thus favors tools appearing in more retrieved lists (more query attempts), peak‑rank uses only the best rank a tool ever achieved. This ensures a tool retrieved once at rank 1 is not demoted by being retrieved later at rank 10 for a different sub‑task.
- **Core assumption:** The optimal final tool list should reflect the strongest evidence of relevance across all sub‑tasks, not the quantity of mentions. A tool that is highly relevant to one sub‑task should not be penalized for being less relevant to others.
- **Evidence anchors:** [section 3.1] "Since the model may generate a varying number of queries for different sub‑tasks, prior methods tend to bias the final ranking toward sub‑tasks that require more query attempts. Therefore, we employ a simple yet robust peak‑rank aggregation strategy..." [section 4.4, Table 4] Ablation shows peak‑rank outperforms RRF on in‑domain and zero‑shot metrics.
- **Break condition:** If the most relevant tools for a query are consistently ranked lower in initial attempts and only appear in later, less focused queries, peak‑rank might still surface them, but the aggregation could miss tools that are modestly relevant across many sub‑tasks (which might be intentionally favored by RRF).

## Foundational Learning
- **Task Decomposition for Complex Queries**
  - *Why needed:* The core innovation is shifting from single-shot to multi-step retrieval. An engineer must understand how to break a user's abstract request into discrete, executable sub‑tasks that align with tool documentation.
  - *Quick check:* Given the query "Analyze how rain affects retail sales," what are 2‑3 logical sub‑goals a planner should generate?
- **Reinforcement Learning with Verifiable Rewards (RLVR)**
  - *Why needed:* Supervised fine‑tuning on synthetic trajectories provides an initial policy but may not optimize for the final retrieval metric (nDCG@K). RLVR uses the retrieval performance as a sparse, verifiable reward to refine the policy, crucial for out‑of‑domain generalization.
  - *Quick check:* Why is a standard RL value network unnecessary in TOOLQP's GRPO setup, and what serves as the environment?
- **Synthetic Trajectory Generation for Training Data**
  - *Why needed:* No existing dataset provides the multi‑turn query‑retrieval pairs needed. The paper's algorithm uses a teacher model to simulate the planning process, including failed attempts, to create diverse trajectories for SFT.
  - *Quick check:* What is the purpose of intentionally keeping failed query attempts in the training data with probability `p`?

## Architecture Onboarding
**Component map:**
- Planner (TOOLQP model): A lightweight LLM (1.7B parameters) responsible for: (1) generating the initial task breakdown `P` and sub‑tasks `{s_n}`; (2) generating iterative queries `q_t` based on retriever feedback `O_t`; (3) emitting `<stop_retrieval>`.
- Retriever Interface `E`: Any existing dense retriever (e.g., `gte‑Qwen`). It receives a query string and returns a ranked list `O_t` of tools from the library `D`. The Planner treats this as a dynamic environment.
- Aggregator: Post‑processes the sequence of `O_t` lists using peak‑rank to produce a final ranked tool list for the downstream agent.

**Critical path:**
1. User query `q` enters Planner.
2. Planner outputs `<task_breakdown>` and `<sub_goals>`.
3. System signals "Begin retrieval."
4. Planner outputs first `<query>` `q_1`.
5. Retriever `E` returns `O_1`.
6. Steps 4‑5 repeat, with Planner seeing previous `(q_t, O_t)` in context.
7. Planner outputs `<stop_retrieval>`.
8. Aggregator applies peak‑rank to all collected `O_t` → final list.
9. Final list passed to downstream LLM agent for tool calling.

**Design tradeoffs:**
- **Lightweight Planner vs. Retriever Quality:** TOOLQP's strength is its modularity—it works with *any* retriever. However, its performance is fundamentally bounded by the base retriever's capability. A poor retriever yields poor feedback, leading the Planner astray.
- **Iterative Latency vs. Accuracy:** Each additional query turn adds latency. The system uses a `<stop_retrieval>` token to end early, but determining sufficiency is a learned policy. Simpler queries might be over‑decomposed, wasting steps.
- **Synthetic Data Bias:** Training data is generated with a single base retriever (`gte‑Qwen`). While the paper shows good transfer, the policy may still be subtly biased toward that retriever's embedding space (acknowledged in Limitations).

**Failure signatures:**
- **Infinite loops:** Planner fails to emit `<stop_retrieval>`. Mitigation: maximum query turn limit (10 in paper).
- **Repetitive queries:** Planner generates near‑identical queries for a sub‑task, indicating the feedback is not being effectively used to refine strategy.
- **Irrelevant final list:** Peak‑rank aggregates from poor `O_t` lists. Check intermediate `q_t` and `O_t` for relevance.
- **Over‑decomposition:** Planner creates too many sub‑tasks for a simple query, leading to unnecessary queries and potential noise injection.
- **Formatting errors:** Planner outputs malformed `<query>` or `<stop_retrieval>` tags (hence the `Rformat` reward during RLVR).

**First 3 experiments:**
1. **Baseline comparison on ToolRet:** Implement base retriever (gte‑Qwen), prompting baselines (Q2E, HyDE), fine‑tuning (ContrastiveFT), and TOOLQP. Measure nDCG@10 and Completeness@10 on in‑domain and zero‑shot splits. Expect TOOLQP to outperform, especially on zero‑shot and compositional subsets.
2. **Retriever transfer test:** Take the trained TOOLQP model and plug it into 4‑5 *different* base retrievers (e.g., bge‑large, e5‑base) without retraining. Evaluate on the same ToolRet splits. Expect consistent improvements over each base retriever's native performance, proving policy robustness.
3. **Ablation - Aggregation method:** Replace peak‑rank with RRF or multi‑view fusion in the final aggregation step. Keep all else identical. Expect peak‑rank to match or outperform, confirming its design choice against frequency bias.

## Open Questions the Paper Calls Out
1. Does training TOOLQP on synthetic trajectories generated from multiple diverse retrievers improve zero‑shot generalization to unseen retrieval models compared to training on a single retriever?
2. How does integrating explicit tool knowledge graphs (TKGs) into the planning process affect retrieval efficiency (queries per request) and accuracy compared to purely interaction‑based dependency discovery?
3. At what tool library size does the iterative query planning overhead of TOOLQP become justified by its retrieval accuracy gains over single‑shot methods?
4. Can an adaptive mechanism that decides when to decompose queries improve TOOLQP's latency without sacrificing accuracy on simple queries?

## Limitations
- Under‑specification of retrieval feedback format and synthetic data construction details may lead to reproduction variance.
- Baseline implementations (e.g., ContrastiveFT, D2Q) lack full methodological details, so performance gaps might shrink with precise reimplementation.
- Downstream integration (tool list formatting) is not fully described, making attribution of end‑to‑end gains uncertain.

## Confidence
- Retrieval accuracy improvements (in‑domain/zero‑shot nDCG@10): **High**.
- Robustness to unseen retrievers (transfer performance): **Medium**.
- Downstream tool‑calling gains (StableToolBench, API‑Bank): **Medium**.
- Causal isolation of the proposed mechanisms (decomposition, interaction, peak‑rank): **Medium‑Low**.

## Next Checks
