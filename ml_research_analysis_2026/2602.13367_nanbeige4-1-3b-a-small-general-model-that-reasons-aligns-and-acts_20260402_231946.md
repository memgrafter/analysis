# Nanbeige4.1-3B: A Small General Model that Reasons, Aligns, and Acts

## Quick Facts
- **arXiv ID:** 2602.13367
- **Source URL:** https://arxiv.org/abs/2602.13367
- **Reference count:** 40
- **Primary result:** A unified 3B-parameter model achieving strong reasoning, coding, and agentic capabilities, outperforming prior 3B models and larger ones like Qwen3-30B-A3B on key benchmarks.

## Executive Summary
Nanbeige4.1-3B demonstrates that a compact 3B-parameter model can achieve broad competence across reasoning, coding, and tool-augmented agentic tasks through a carefully designed multi-stage training pipeline. The approach combines point-wise and pair-wise reward modeling for alignment, introduces gated time-complexity rewards in code reinforcement learning, and employs turn-level supervision to enable stable long-horizon interactions (up to 600 turns). The model sets new standards for its scale, notably surpassing larger competitors on benchmarks such as LiveCodeBench-V6 (76.9) and GAIA deep search (69.90).

## Method Summary
Training begins with extended supervised fine-tuning (SFT) using a curated data mixture (27% code, 26% deep-search, 23% STEM, 13% tool-use, 10% general) and a 256K context length, enhanced by Solution Refinement and Chain-of-Thought Reconstruction. This is followed by staged reinforcement learning: point-wise RL first stabilizes response quality, then pair-wise RL with swap-consistency sharpens preference alignment. For coding, a two-stage RL first optimizes correctness (pass rate) and then adds a gated time-complexity reward only for fully correct solutions. Deep search capabilities are built via synthesized trajectories with turn-level critic filtering, integrated into both SFT and RL to ensure reliable multi-step tool use.

## Key Results
- **LiveCodeBench-V6:** 76.9 (vs. 57.4 for Qwen3-4B)
- **Arena-Hard-V2:** 73.8
- **Deep search:** GAIA 69.90; xBench-DeepSearch-05 75.00; LeetCode weekly contests 85.0% pass rate

## Why This Works (Mechanism)
**Mechanism 1 (Combined Point-wise and Pair-wise Reward Modeling):** Point-wise RL uses a general reward model to score individual responses, reducing redundancy and formatting errors; pair-wise RL applies a pairwise reward model on strong-weak comparisons with swap-consistency to sharpen preference boundaries, especially in multi-turn dialogues. The sequential combination improves both standalone response quality and comparative alignment. Evidence includes point-wise RL's suppression of overlong truncation [section 2.1.2] and pair-wise RL's gains on Arena-Hard V2 and Multi-Challenge [section 2.1.3]. If reward models are biased or preference data is limited, alignment may stagnate.

**Mechanism 2 (Gated Time-Complexity Reward in Code RL):** A two-stage code RL process first optimizes for test pass rate. Only when a solution achieves 100% pass rate does the system activate an additional time-complexity reward (`R_time`), gating efficiency optimization behind correctness. The judge system combines sandbox execution with an instruct model to assess complexity. Training dynamics show `R_time` rising only after correctness stabilizes [section 2.3.4], indicating effective gating. Inaccurate complexity estimation or scarce correct solutions in Stage 2 would weaken the learning signal.

**Mechanism 3 (Turn-Level Supervision for Deep Search):** During deep search data synthesis, a critic model evaluates each trajectory turn for logical soundness, tool-call accuracy, and informational gain. Turns failing these criteria are filtered out, ensuring the training data consists of high-fidelity steps. This fine-grained supervision prevents error accumulation and enables stable long-horizon tool interactions, as evidenced by strong GAIA and xBench scores [section 3.2]. Inconsistent critic judgments or noise propagation could degrade stability beyond the demonstrated 600-turn limit.

## Architecture Onboarding
**Component map:**
Nanbeige4-3B-Base -> Extended SFT (256K context, data mix) -> Point-wise RL -> Pair-wise RL -> Code RL Stage 1 (correctness) -> Code RL Stage 2 (gated complexity) -> Agentic RL

**Critical path:**
1. Initialize from Nanbeige4-3B-Base.
2. Perform extended SFT with 256K context and specified data mixture.
3. Apply point-wise RL using GRPO and a general reward model.
4. Apply pair-wise RL with swap-consistency regularizer on strong-weak comparisons.
5. Conduct Code RL Stage 1 to optimize pass rate.
6. Conduct Code RL Stage 2, adding gated time-complexity reward when pass rate=1.
7. Apply lightweight agentic RL for tool-use robustness.

**Design tradeoffs:**
- **Capacity vs. Versatility:** With 3B parameters, data mixing ratios and RL stage intensity are balanced to avoid overfitting any single domain while maintaining broad competence.
- **Training Stability:** Staged RL prevents catastrophic forgetting; gated rewards avoid premature efficiency optimization that could harm correctness.
- **Efficiency vs. Performance:** 256K context enables deep search but increases memory; complexity rewards improve code quality but depend on accurate judge systems.

**Failure signatures:**
- Degradation in alignment benchmarks (e.g., Arena-Hard drop) after pair-wise RL if reward models are underfitted or biased.
- Short-horizon collapse in deep search tasks if turn-level supervision is weak, leading to failure after a few tool calls.
- Code inefficiency or correctness drop if gated reward timing is misaligned (e.g., activating `R_time` too early).

**First 3 experiments:**
1. **SFT Data Mix Ablation:** Train models with varying proportions of code and deep-search data; evaluate impact on LiveCodeBench and GAIA scores to validate data distribution design.
2. **General RL Staging Study:** Compare models after point-wise RL only, pair-wise RL only, and sequential application; measure changes in Arena-Hard V2 and Multi-Challenge to isolate each stage's contribution.
3. **Deep Search Stability Test:** Evaluate on GAIA with increasing tool-call limits (e.g., 100, 300, 600 turns); observe success rate decay to confirm turn-level supervision enables sustained interaction.

## Open Questions the Paper Calls Out
1. **Scalability of 3B Generalists:** The paper questions how far a 3B model can be pushed as a generalist without compromising strengths, but does not systematically explore the absolute performance ceiling or failure modes across all capabilities at this scale.
2. **Tension in Combined Reward Modeling:** Sequential application of point-wise and pair-wise RL shows additive gains, but potential conflicts between maximizing standalone response quality and aligning with comparative human preferences are unanalyzed.
3. **Long-Horizon Turn-Level Supervision Limits:** The approach enables stable interactions up to 600 turns, but its effectiveness with even longer tasks or more complex planning, and whether turn-level rewards remain sufficient for credit assignment, is unknown.
4. **Gated Complexity Reward Genuineness:** It is unclear whether the gated reward fosters deep algorithmic efficiency or merely encourages mimicking reference complexity labels without transferable understanding.

## Limitations
- **Reproducibility Gaps:** Critical implementation details are missing (exact base model configuration, RL hyperparameters, judge system prompts), and the "lightweight agentic RL" stage is underspecified.
- **Evaluation Scope:** Reported scores are on standard benchmarks; real-world, open-ended task performance and robustness to adversarial tool environments are not demonstrated.
- **Component Isolation:** The synergistic effect of the staged pipeline (SFT -> Point RL -> Pair RL -> Code RL) is inferred but not ablated; individual stage contributions, especially final agentic tuning, remain unclear.

## Confidence
- **Combined RL (point-wise + pair-wise):** Medium-High. The mechanism aligns with RLHF principles and shows additive gains, but the magnitude of benefit from the specific combination and order is not isolated.
- **Gated code complexity reward:** Medium. The gating logic is precise and training dynamics are suggestive, but the accuracy of the instruct judge for complexity assessment is a major external dependency not validated.
- **Turn-level supervision for long-horizon stability:** Low-Medium. The claim of enabling "up to 600 turns" is strong but based on a single benchmark suite using a proprietary critic; generalizability to other tool sets and environments is an unknown.

## Next Checks
1. **Ablate the RL Stage Sequence:** Train three models from the same SFT checkpoint: (a) apply only Pair-wise RL, (b) apply only Code RL, (c) apply the full published sequence. Compare performance on Arena-Hard-V2 (alignment), LiveCodeBench (code), and GAIA (deep search) to isolate each stage's contribution and detect synergistic effects or catastrophic forgetting.
2. **Audit the Code Complexity Judge:** Manually evaluate a stratified sample of solutions from Stage 1 and Stage 2 of Code RL. Score each for correctness and actual time/space complexity. Correlate the judge model's scores with human/computational analysis; a correlation below 0.7 would challenge the gated reward's premise.
3. **Stress-Test Long-Horizon Generalization:** Use the final model with a different suite of tools (e.g., calculator, web search API, file system) in a novel deep-search task (e.g., "Analyze this financial report and draft a summary"). Gradually increase allowed turns (50, 100, 200) and measure success rate decay. Failure before 100 turns would challenge the "stable up to 600 turns" claim, suggesting overfitting to the GAIA trajectory distribution.
