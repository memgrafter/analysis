# Talking with Verifiers: Automatic Specification Generation for Neural Network Verification

## Quick Facts
- **arXiv ID**: 2603.02235
- **Source URL**: https://arxiv.org/abs/2603.02235
- **Reference count**: 40
- **Primary result**: An automated pipeline translates natural-language robustness specifications into formal verification queries, achieving 85–100% parser accuracy and up to 55% detector accuracy per configuration (83% best-case ensemble), enabling verifier-ready outputs for semantic queries previously inaccessible to automated tools.

## Executive Summary
Neural network verification tools are powerful but require expert-level manual effort to translate high-level, semantic requirements (e.g., "the bird's beak shouldn't change") into low-level numerical constraints. This paper introduces a fully automated pipeline that bridges this gap. It uses a large language model (LLM) parser to extract referenced objects and operations from natural language, a perception model (e.g., an open-vocabulary detector) to ground those objects in a concrete input image or table, and a specification generator to produce a formal perturbation constraint compatible with standard verifiers like α-β-CROWN. Evaluated on tabular (Statlog) and image (CUB-200-2011) datasets, the system demonstrates high fidelity to user intent with minimal overhead, making verification accessible for semantic robustness queries.

## Method Summary
The proposed framework is a modular, three-stage pipeline with no trainable components. First, an LLM parser processes a natural-language specification *P* and a neural network *N*'s input-output schema to extract a structured list of objects (e.g., "bird beak") and operations (e.g., "should not change"). Second, a perception model (e.g., Grounding DINO for images) localizes each extracted object within a concrete input *x*, producing a set of coordinates or region masks. Third, a specification generator converts these grounded regions into a standard local robustness constraint, typically of the form *∀x′∈B(x, coords), N(x′)=N(x)*, which is fed to an established verifier (e.g., β-crown). The pipeline includes an optional interactive approval step where a user validates the detector's bounding boxes before verification.

## Key Results
- Parser accuracy in extracting objects and actions from natural language specifications ranged from 85% to 100% across domains.
- Detector accuracy on the fine-grained CUB-200-2011 dataset reached up to 55% per single configuration (loose/tight modes) and 83% best-case using an ensemble (disjunction of modes).
- The framework successfully generated verifier-ready formal specifications for semantic robustness queries, demonstrating end-to-end functionality with low computational overhead beyond the cost of running the off-the-shelf perception and LLM models.

## Why This Works (Mechanism)
The approach works by decomposing a hard problem—semantic-to-numerical translation—into three tractable sub-problems, each solved by a state-of-the-art, off-the-shelf model. The LLM parser leverages few-shot prompting and constrained JSON output to reliably extract a machine-interpretable semantic plan. The perception model provides the necessary "grounding" link between abstract symbols (e.g., "beak") and concrete pixels or table cells, using open-vocabulary capabilities to handle novel concepts. Finally, the specification generator applies a simple, verifier-agnostic transformation (region-based L∞ ball) to produce a sound formal query. This modularity allows each component to be independently upgraded as better models become available.

## Foundational Learning
**Concept 1: Formal Verification of Neural Networks**
*Why needed*: Provides the target output format (e.g., VNNLIB) and defines what it means to "verify" a property (e.g., local robustness). The entire pipeline culminates in a query for these tools.
*Quick check*: Can you write a VNNLIB constraint stating that for all perturbations within an L∞ ball of radius ε around input *x*, the network's top-1 class remains unchanged?

**Concept 2: Open-Vocabulary Object Detection**
*Why needed*: The detector must localize arbitrary semantic concepts ("purple thorn") without being constrained to a fixed label set, which is essential for processing natural language specs.
*Quick check*: Given an image and the text query "a small brown bird with a pointed beak," could a model like Grounding DINO output a bounding box without having seen "pointed beak" in its training taxonomy?

**Concept 3: Structured Output Parsing with LLMs**
*Why needed*: To convert free-form natural language into a deterministic, machine-readable structure (list of objects, operations) without ambiguity.
*Quick check*: Can you design a system prompt and JSON schema that forces an LLM to output `{"objects": [...], "actions": [...]}` for the spec "The background color should not affect the classification"?

**Concept 4: Local Robustness as a Perturbation Ball**
*Why needed*: The most common and tractable verification property; the generator maps grounded regions into a bounded region (L∞ ball) around the input.
*Quick check*: If a detector outputs a bounding box *B* around an object, how would you define an L∞ ball *B(x, ε)* such that perturbing pixels only inside *B* satisfies "the object's appearance shouldn't change"?

**Concept 5: Semantic Gap in Verification**
*Why needed*: The core problem the paper addresses—the mismatch between what a user intuitively means ("the car is red") and what a verifier understands (pixel value bounds).
*Quick check*: For an image classifier, why can't you directly verify the property "the digit is a 3" without first specifying which pixels define the "digit"?

## Architecture Onboarding
**Component Map**
Parser (LLM) -> Detector (GroundingDINO) -> Specification Generator -> Neural Network Verifier (e.g., α-β-CROWN)
User -> (Approve/Reject) -> Detector Output -> Specification

**Critical Path**
1. Natural language spec *P* and input *x* are fed to the LLM parser.
2. Parser outputs structured `{objects, actions}`.
3. Detector uses `objects` as text queries to localize regions in *x*.
4. Generator uses `actions` and `regions` to build a formal constraint.
5. Constraint is sent to verifier with network *N*.

**Design Tradeoffs**
- **Modularity vs. End-to-End Error Propagation**: Using separate, pre-trained models simplifies development but errors in parsing or detection can cascade without recovery.
- **Generality vs. Performance**: The L∞ ball constraint is universally supported by verifiers but may be overly restrictive for some semantic specs (e.g., "the car moves left" requires geometric transformations, not pixel bounds).
- **Automation vs. Safety**: The interactive approval step introduces human-in-the-loop to catch detector failures, trading full automation for reliability.

**Failure Signatures**
- **Parser failure**: LLM outputs malformed JSON, misses objects/actions, or introduces hallucinations not present in *P*.
- **Detector failure**: Grounding DINO returns no boxes, boxes with low confidence, or boxes on irrelevant regions (e.g., background instead of target object).
- **Generator/Verifier failure**: Generated constraint syntax is invalid for the target verifier, or the constraint is semantically misaligned (e.g., bounding box region does not match the intended "object").

**First Three Experiments**
1. **Parser sanity check**: Run the provided prompt on 10 sample specs from the paper's dataset. Verify 100% JSON parse success and that all expected objects/actions are extracted.
2. **Detector baseline**: Load Grounding DINO (config: `groundingdino_swint_ogc.pth`) and run on the CUB-200-2011 validation set with the paper's "loose" (`box_threshold=0.15, text_threshold=0.15`) and "tight" (`box_threshold=0.35, text_threshold=0.25`) parameters. Compute per-configuration accuracy as defined in the paper (IoU with ground-truth boxes?).
3. **End-to-end verifier integration**: Take one successful detection from Experiment 2, generate the corresponding L∞ ball constraint in VNNLIB format, and run α-β-CROWN on a simple, verified network (e.g., a 2-layer FC net on MNIST) to ensure the constraint is accepted and a verification result (SAT/UNSAT) is returned.

## Open Questions the Paper Calls Out
**Open Question 1**
**Question**: How can the framework be extended to handle video inputs with temporal semantic constraints, as mentioned in future work?
**Basis in paper**: The Conclusion (Sec. 6) states: "Future work includes extending our framework to video [38] and supporting temporal constraints for audio events."
**Why unresolved**: The current pipeline is designed for static images/tabular/audio frames. Video introduces motion, frame dependencies, and temporal language (e.g., "the car moves left"), requiring new grounding and constraint generation mechanisms not implemented.
**What evidence would resolve it**: Implement a video-specific pipeline (e.g., using video-language models for temporal grounding) and evaluate on video robustness benchmarks with time-dependent specifications.

**Open Question 2**
**Question**: What specific architectural or algorithmic improvements to open-vocabulary detection models could close the gap between single-configuration (max 55%) and best-case ensemble (83%) localization accuracy on CUB-200-2011?
**Basis in paper**: The Evaluation (Sec. 4) notes: "the disjunction... reaches 83%... future refinements in detection heuristics or multi-mode ensembles could bridge this gap."
**Why unresolved**: The paper identifies the accuracy gap but does not test or propose concrete methods (e.g., test-time augmentation, confidence calibration, region proposal networks) to improve single-configuration performance, leaving the practical reliability uncertain.
**What evidence would resolve it**: Systematic experiments comparing detection architectures (e.g., GroundingDINO vs. newer models), post-processing heuristics, or ensemble strategies, measuring impact on final verification success rate.

**Open Question 3**
**Question**: To what extent do choices in the parsing stage (LLM model, prompt design, minimal vs. detailed mode) propagate errors and affect the success of the end-to-end verification query?
**Basis in paper**: The paper evaluates parsing accuracy in isolation (Tab. 1) and detection accuracy separately (Tab. 2), but does not measure how parsing errors ultimately cause invalid or unsound verification specifications.
**Why unresolved**: The pipeline’s modular design assumes each stage is sufficiently accurate, but error propagation across LLM parsing → detector grounding → specification generation is not quantified. This affects confidence in the framework’s overall robustness.
**What evidence would resolve it**: Ablation study where parsing outputs are perturbed (e.g., swapped object names, incorrect actions) to measure failure rates at the verifier stage, or correlation analysis between parsing/detection scores and final verification correctness.

**Open Question 4**
**Question**: How does the interactive user approval step (`approved(x, coords)`) impact the practical usability and coverage of the specification generation process in real-world deployments?
**Basis in paper**: The pipeline (Alg. 1) includes an interactive approval step before verification, but the evaluation does not assess its frequency, user burden, or effect on automation goals. The paper acknowledges a full usability study is future work.
**Why unresolved**: The step is a critical usability safeguard but may undermine the “automated” promise if users frequently reject detections. Its necessity, design, and impact on verification throughput are unknown.
**What evidence would resolve it**: A user study measuring approval rate across diverse specifications/detectors, qualitative feedback on the interface, and analysis of how often rejection leads to specification reformulation vs. abandonment.

**Open Question 5**
**Question**: Can the framework’s modular approach be seamlessly applied to domains beyond image and tabular, such as audio with open-vocabulary sound event detection (OV-SED), without compromising verification soundness?
**Basis in paper**: The paper describes an audio domain instantiation (Sec. 3, Fig. 1b) but explicitly states: "we present this instantiation at the level of specification translation, but do not implement the audio detection component." Future work mentions "supporting temporal constraints for audio events."
**Why unresolved**: The audio pipeline is conceptual; key challenges like detecting non-stationary sound events, handling overlapping sources, and translating temporal intervals into perturbation constraints (e.g., amplitude changes in specific segments) are untested. Sound event detection models (e.g., FlexSED) may have different error profiles affecting verification.
**What evidence would resolve it**: Implement the audio detection and specification generator using state-of-the-art OV-SED models, evaluate on an audio classification dataset (e.g., DCASE) with natural language specs about sound events, and measure verification success comparable to image/tabular results.

## Limitations
- **Verifier integration unspecified**: The exact formal constraint format (beyond example L∞ balls) and its precise mapping to tools like α-β-CROWN are not detailed, posing a risk for implementers.
- **Unreleased LLM dependency**: Reported parser accuracies are based on unreleased models (GPT-5 Mini, Gemini 3 Flash). Substituting with contemporary APIs (GPT-4, Claude) may degrade performance and require significant prompt re-engineering.
- **Evaluation scope narrow**: Framework validated only on two datasets (Statlog, CUB). Generalization to other image distributions, more complex tabular data, or the unimplemented audio domain remains unproven.

## Confidence
- **Parser extraction accuracy (85–100%)**: **High**. Constrained JSON output with modern LLMs is highly reliable when prompts are well-designed; minor variance expected with different model families.
- **Detector accuracy (up to 55%, 83% best-case)**: **Medium**. Grounding DINO's performance on fine-grained CUB concepts is plausible but sensitive to threshold choices; the 83% ensemble figure suggests substantial room for improvement in single-configuration reliability.
- **End-to-end specification generation**: **Medium**. Success hinges on flawless chaining of all stages. The paper shows feasibility but lacks error-recovery mechanisms and full-system robustness analysis.
- **Generalization to audio**: **Low**. The audio component is purely conceptual; major implementation hurdles and unknown detection error profiles make any confidence estimate speculative.

## Next Checks
1. **Constraint format validation**: Generate a sample VNNLIB constraint from the pipeline (using a handcrafted spec + detection) and successfully parse/verify it with α-β-CROWN on a tiny test network to confirm syntax/semantic compatibility.
2. **Detector threshold sweep**: Replicate the CUB-200-2011 detection experiment exactly as described (loose vs. tight modes) and report per-configuration accuracy, focusing on failure modes for rare attribute combinations (e.g., "purple thorn").
3. **Cross-model parser portability**: Implement the parser using GPT-4 (or Claude 3.5 Sonnet) with the paper's prompts on the same spec test set. Quantify the drop (if any) in object/action extraction accuracy compared to the reported 85–100% range.
