# Agentic Control Center for Data Product Optimization

## Quick Facts
- **arXiv ID:** 2603.10133
- **Source URL:** https://arxiv.org/abs/2603.10133
- **Reference count:** 14
- **Primary result:** An autonomous Agentic Control Center reduces manual effort in creating data products by continuously optimizing against user-defined quality contracts, meeting or approaching targets for coverage and performance in benchmark case studies.

## Executive Summary
This paper introduces an Agentic Control Center to automate the creation and refinement of data products (such as example queries and views). The system employs specialized AI agents within a continuous optimization loop—plan → parameterize → execute → update → measure—guided by user-defined quality contracts. A case study on three BIRD benchmark databases demonstrated that the system could automatically achieve or approach objectives like 90% table coverage and sub-5-second query times. The system adapts its strategy based on schema complexity and detects diminishing returns to recommend human intervention, significantly reducing the need for manual expert effort.

## Method Summary
The system ingests a database schema and optional seed questions, then operates under user-defined "quality contracts" specifying targets for metrics like table coverage and query speed. A Planner Agent selects the highest-impact tool action (e.g., generate more questions, create views) by comparing current state metrics against contract gaps. An Input Planner Agent calibrates the scale of the action using schema features and historical performance. Specialized tool agents execute, producing new artifacts (SQL, views) that update the central DataProductState. The Metrics Module recalculates affected metrics, and the loop repeats until contracts are met or progress stalls. All artifacts and state versions are tracked in a Git repository.

## Key Results
- Automatically achieved or approached benchmark targets: ~90% table coverage, ~50% column coverage, and average query execution under 5 seconds.
- Demonstrated adaptive behavior: rapid convergence on simple schemas and complex, multi-stage query generation on complex schemas.
- Efficiently tuned parameters and recommended manual review upon detecting diminishing returns, avoiding wasteful iterations.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** The Planner Agent drives targeted improvements by mapping quality metric gaps to the highest-impact tool action.
- **Mechanism:** It continuously compares current `DataProductState` metrics against user-defined contracts. Using a precondition graph, it evaluates which available tool (e.g., SQL Generation, View Creation) would most efficiently close the largest gap, then outputs a structured execution plan.
- **Core assumption:** The tool precondition graph correctly models which actions optimally influence specific metrics.
- **Evidence anchors:** [abstract] "specialized AI agents operating in a continuous optimization loop... guided by user-defined quality contracts." [section IV] "The Planner Agent... continuously evaluates the DataProductState against completeness and performance contracts. It analyzes actual metric values versus targets using a tool precondition graph to identify the single highest-impact action."
- **Break condition:** If multiple metric gaps are equally large and tool preconditions create ambiguous mappings, the planner may select sub-optimal actions, stalling convergence.

### Mechanism 2
- **Mechanism:** The Input Planner Agent translates the planner's strategic action into effective operational parameters (e.g., number of questions to generate) by analyzing schema characteristics (table count, size), historical tool outputs, and the magnitude of the remaining contract gap.
- **Core assumption:** Schema features and historical performance are reliable proxies for determining the optimal scale of an action.
- **Evidence anchors:** [section IV] "The Input Planner Agent transforms high-level action requests into precisely calibrated tool parameters by analyzing schema characteristics, historical outputs, and contract gaps. It employs adaptive heuristics... It may produce 80 questions when more than 50 tables remain under-covered, while limiting this to around 20 when only a handful of tables require attention." [section V] Case study shows "automatically increasing question generation quantities" for complex databases.
- **Break condition:** Heuristics fail on highly atypical schemas (e.g., thousands of tiny tables) where historical patterns do not predict the effort needed for meaningful coverage, leading to parameter overshoot (wasted compute) or undershoot (ineffective action).

### Mechanism 3
- **Claim:** The closed-loop `plan → parameterize → execute → update → measure` cycle enables meta-reasoning and efficient termination.
- **Mechanism:** After each tool execution, the State Manager updates the `DataProductState` and triggers metric recalculation. The Planner Agent then re-assesses the new state. This allows the system to detect when a tool's marginal improvement falls below a threshold (diminishing returns) and recommend human intervention, avoiding wasteful iterations.
- **Core assumption:** Recalculated metrics provide a sufficiently accurate and timely signal of progress toward contracts.
- **Evidence anchors:** [abstract] "continuous optimization loop (plan → parameterize → execute → update → measure)... demonstrated adaptive strategies—rapid convergence... and complex, multi-stage query generation... efficiently tuning parameters and recommending manual intervention upon detecting diminishing returns." [section V] "The Planner Agent was capable of detecting diminishing returns and transitioning between stages at optimal points... recommended manual review rather than continuing inefficient iterations."
- **Break condition:** If metric recalculation is slow or inaccurate (e.g., due to complex view dependencies or slow query execution), the planner's perception of progress is delayed or erroneous, leading to premature termination on hard problems or endless loops on easy ones.

## Foundational Learning
- **Concept: Quality Contracts as Optimization Objectives.**
  - **Why needed:** The entire autonomous loop is goal-directed. User-defined, multi-dimensional targets (e.g., "90% table coverage") are the single source of truth for all agent decisions.
  - **Quick check:** If a user sets a contract for 50% column coverage and 5-second query times, and the system achieves 45% coverage with 2-second queries, has it met its primary objective? What does it do next?

- **Concept: State as a Single Source of Truth.**
  - **Why needed:** The `DataProductState` (schemas, questions, SQL versions, views) is the immutable data structure all agents read from and write to. Its consistency and completeness directly determine metric accuracy and action validity.
  - **Quick check:** A new table is added to the database. Which component must first update the `DataProductState` before any metric can be correctly recalculated?

- **Concept: Tool-Action Dependencies and Side Effects.**
  - **Why needed:** Each specialized tool (SQL Gen, View Creation) affects multiple metrics in different directions (e.g., View Creation may improve speed but increase complexity). Architects must understand these dependency graphs to set contracts and predict loop behavior.
  - **Quick check:** If the goal is to *reduce* average query complexity, which tool from the paper's set would likely be counterproductive to invoke, and why?

## Architecture Onboarding
- **Component map:** State Manager -> Metrics Module -> Tool Registry -> Orchestration Layer (Planner Agent & Input Planner Agent)
- **Critical path:** System initialization -> State Manager populates schema -> User sets quality contracts -> Loop Begins: Planner reads State/Metrics -> selects tool -> Input Planner sets parameters -> Tool Agent executes & writes new artifacts to State -> Metrics Module recalculates -> Loop repeats until contracts met/diminishing returns.
- **Design tradeoffs:**
  - **Automation vs. Control:** Full autonomy risks low-quality artifacts; mitigated by human-in-the-loop review prompts and Git audit trails.
  - **Metric Granularity:** Recalculating all metrics on every change is costly; system uses a dependency graph for selective recalculation, trading absolute real-time accuracy for efficiency.
- **Failure signatures:**
  1. **Convergence stall:** Metrics plateau far from targets despite continuous loop.
  2. **Metric oscillation:** Metrics improve then degrade in a cycle, indicating conflicting tool effects or faulty parameterization.
  3. **Excessive manual review prompts:** Suggests Input Planner heuristics are failing, often due to poor initial state or unrealistic contracts.
- **First 3 experiments:**
  1. **Tool Validation Test:** For a known simple schema, manually invoke each Tool Agent (Question Gen, SQL Gen) and verify its outputs correctly update the `DataProductState` and trigger the expected specific metric changes.
  2. **Planner Decision Audit:** Set a simple contract (e.g., 80% table coverage). Run the loop and log the Planner Agent's JSON decisions. Validate that each selected tool directly addresses the largest current metric gap.
  3. **Heuristic Stress Test:** Create a schema with an extreme number of small, disjoint tables. Observe if the Input Planner's "number of questions" heuristic scales appropriately or defaults to a static number, leading to slow coverage gains.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** What specific quality metrics beyond table/column coverage and query speed should be incorporated into data product quality contracts to more holistically assess data usability, and how can these be automatically measured and integrated into the optimization loop?
- **Basis in paper:** [explicit] The conclusion identifies the need for "an expanded set of metrics" as a key requirement for a comprehensive framework.
- **Why unresolved:** The current system focuses on a limited set of metrics (coverage, speed, complexity) that do not capture broader data quality dimensions like freshness, accuracy, or user engagement, leaving gaps in what "quality" means for diverse data products.
- **What evidence would resolve it:** A systematic study defining and implementing 3–5 new automated metrics (e.g., data lineage completeness, semantic consistency scores), followed by case studies showing their impact on optimization outcomes and user satisfaction.

### Open Question 2
- **Question:** How can the Agentic Control Center be extended to solve complex multi-objective optimization problems where quality contracts conflict (e.g., maximizing coverage while minimizing query complexity), rather than relying on sequential target achievement?
- **Basis in paper:** [explicit] The conclusion directly cites "the ability to solve complex multi-objective optimization problems" as a needed advancement.
- **Why unresolved:** The system currently handles objectives sequentially (e.g., meet coverage before speed), but real-world scenarios involve trade-offs; without Pareto-optimal or weighted optimization, the system may not find globally optimal solutions.
- **What evidence would resolve it:** Implementing a multi-objective algorithm (e.g., NSGA-II) within the Planner Agent and evaluating it on benchmark databases with deliberately conflicting targets, measuring solution quality and convergence compared to the sequential approach.

### Open Question 3
- **Question:** What architectural modifications are necessary to scale the Agentic Control Center’s interactive interface and state manager to support enterprise-scale databases (thousands of tables) while maintaining real-time responsiveness and meaningful human-in-the-loop control?
- **Basis in paper:** [explicit] The conclusion calls for "a more scalable and interactive interface" as essential for deployment.
- **Why unresolved:** The current prototype’s performance on three BIRD databases (small to medium scale) is undocumented; state management, metric recalculation, and UI updates may not scale linearly, risking latency and usability issues in larger environments.
- **What evidence would resolve it:** Stress-testing the system with synthetic databases of increasing size (e.g., 100–10,000 tables), measuring latency of metric updates and agent iterations, and conducting user studies to assess control efficacy at scale.

## Limitations
- The precise algorithm and scoring model within the Planner Agent’s precondition graph is not disclosed, creating a key black box for reproducing optimal action selection.
- Internal prompts, validation logic, and failure handling for specialized agents (e.g., Text-to-SQL) are unspecified, making output quality and reliability difficult to ensure.
- Claims about "efficient tuning" and "diminishing returns detection" rely on case study observations without detailing the quantitative thresholds or sensitivity of the break conditions.

## Confidence
- **Planner Agent drives high-impact actions:** High confidence (architectural role clearly defined, though exact decision logic opaque).
- **Input Planner heuristics calibrate parameters:** Medium confidence (example heuristics and case study support provided, but generality and failure modes unproven).
- **Closed-loop enables meta-reasoning and efficient termination:** Medium confidence (loop structure well-described, but robustness of "diminishing returns" signal depends on unimplemented metric recalculation details).
