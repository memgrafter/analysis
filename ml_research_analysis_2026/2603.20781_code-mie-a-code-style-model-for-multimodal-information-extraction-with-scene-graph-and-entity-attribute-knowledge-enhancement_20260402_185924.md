# Code-MIE: A Code-style Model for Multimodal Information Extraction with Scene Graph and Entity Attribute Knowledge Enhancement

## Quick Facts
- **arXiv ID:** 2603.20781  
- **Source URL:** https://arxiv.org/abs/2603.20781  
- **Reference count:** 35  
- **Primary result:** Achieves state-of-the-art performance on four MIE datasets (M³D, Twitter-15/17, MNRE) with up to 6.94% improvement over natural language templates, while significantly reducing hallucination errors by formalizing MIE as unified code generation.

## Executive Summary
Code-MIE tackles the mismatch between natural language prompts and structured multimodal information extraction (MIE) by reformulating MIE as a unified code-generation task. It integrates entity attributes from text, scene graphs from images, and visual features into a single task-agnostic Python function template. This approach leverages large language models' (LLMs) inherent competence with code to produce deterministic, parsable outputs, minimizing free-form generation errors. The framework demonstrates superior performance across entity recognition, relation extraction, chain extraction, and visual grounding, setting new benchmarks on M³D (English/Chinese), Twitter-15/17, and MNRE datasets.

## Method Summary
The core innovation is expressing all MIE subtasks—named entity recognition, entity chain extraction, relation extraction, and visual grounding—as a single Python function that fills predefined dictionaries. Inputs combine raw text, structured entity attributes (extracted by Qwen3-Max), scene graphs (triples from Qwen3-VL), and ViT patch embeddings. These are fused via a visual projection layer and fed to a LoRA-fine-tuned Qwen3-8B. The model generates executable code that populates `entity_dic`, `chain_dic`, `relation_dic`, and `grounding_dic`. A final parser extracts structured results. This eliminates task-specific prompt engineering and enforces output consistency through syntactic constraints.

## Key Results
- SOTA on M³D (English 61.03%, Chinese 60.49%), Twitter-15 (76.04%), Twitter-17 (88.07%), and MNRE (73.94%).
- Absolute F1 improvement up to 6.94% over natural language template baselines.
- Hallucination errors significantly reduced due to rigid code-style formatting.

## Why This Works (Mechanism)

### Mechanism 1: Structured Code Templates Reduce Hallucination
**Claim:** Python templates impose syntactic constraints that align with LLMs' code-generation training, minimizing free-form text and formatting errors.  
**Mechanism:** Functions and dictionaries enforce a deterministic schema (e.g., `entity_dic[type] = [...]`), guiding the LLM to output exactly parsable structures.  
**Core assumption:** LLMs pre-trained on code corpora follow structured templates more faithfully than ad-hoc natural language prompts for structured IE outputs.  
**Evidence anchors:** [abstract] "Code-style templates... significantly reducing hallucination errors"; [section V-C] "Code-style templates exhibited lower hallucination error rates... due to stricter grammatical rules"; indirect support from neighboring work (e.g., DIM) using LLMs for MEL but not code templates.

### Mechanism 2: Entity Attributes Provide Contextual Role Clues
**Claim:** Extracted entity attributes (e.g., gender, affiliation) offer soft constraints that improve relation extraction, especially for deep-reasoning relations.  
**Mechanism:** Attributes like `"affiliation": "Nazis"` for `Luftwaffe` signal an `ORG-ORG_affiliated` relation, helping resolve ambiguous textual patterns.  
**Core assumption:** Attributes encode latent semantic roles not always explicit in raw text but recoverable from context and critical for RE.  
**Evidence anchors:** [abstract] "Entity attributes... to guide the model to understand the context and role of entities"; [section III-A] attribute sets and generation process; [section V-B, Table VIII] ablation shows RE performance drop on M³D when removing EA (EN RE: 41.49% → 39.20%).

### Mechanism 3: Scene Graphs Anchor Cross-Modal Grounding
**Claim:** Scene graphs (explicit (subject, object, relation) triples from images) provide visual relational structure that anchors textual entity chains and improves grounding.  
**Mechanism:** Triples like `("mother", "infant", "near")` serve as evidence to infer plausible textual relations (e.g., `PER-PER_parents`) and coordinate grounding.  
**Core assumption:** Scene graphs reliably capture salient visual semantics correlating with textual relations and align via the shared code-template space.  
**Evidence anchors:** [abstract] "Images are converted into scene graphs... to incorporate rich visual information"; [section III-B] scene graph generation via Qwen3-VL; [section V-D, Figure 5] case study where scene graph enables correct `PER-PER_parents` relation; absence leads to false `couple` relation.

## Foundational Learning
- **Multimodal Feature Fusion**  
  Why needed: Combine heterogeneous modalities—text (raw + attributes), explicit visual structure (scene graphs), and implicit visual features (ViT patches)—into a single LLM input stream.  
  Quick check: How does concatenating averaged ViT patch embeddings with text feature embeddings preserve necessary spatial information for visual grounding tasks?

- **Structured Code Generation for IE**  
  Why needed: The core innovation expresses multiple IE subtasks (NER, chain extraction, RE, grounding) in a unified Python function/dictionary format, avoiding task-specific templates.  
  Quick check: Why might a single task-agnostic template struggle with highly divergent IE subtasks (e.g., NER vs. visual grounding) compared to specialized prompts?

- **Scene Graph Parsing**  
  Why needed: Scene graphs convert pixel data into symbolic relational triples, bridging low-level vision and high-level IE by making visual relations explicit and language-like.  
  Quick check: How does the choice of relation vocabulary in scene graphs (e.g., "near" vs. "standing near") affect the LLM's ability to map to predefined textual relation types?

## Architecture Onboarding
- **Component map:** Text processor (Qwen3-Max) → Visual processor (Qwen3-VL for scene graphs, ViT-base for features) → Template builder → Fusion layer (visual projection) → LLM backbone (Qwen3-8B fine-tuned via LoRA) → Parser.  
- **Critical path:** Input (text + images) → parallel attribute/SG/VF extraction → assemble code template → fuse modalities → LLM forward pass → parse Python output → structured IE results. Attribute and SG generation must precede template construction; fusion must occur before LLM input.  
- **Design tradeoffs:**  
  - Task-agnostic template simplifies deployment but may not optimize each subtask; ablation shows gains but per-task tuning might still help.  
  - Scene graph depth vs. noise: More triples improve recall but risk irrelevant relations confusing the LLM; current approach uses Qwen3-VL with minimal filtering.  
  - Entity attribute richness vs. noise: Detailed attributes aid reasoning but increase template length and potential hallucinations; post-processing filters some noise.  
- **Failure signatures:**  
  - High hallucination in output: Likely due to ambiguous template instructions or insufficient code-style training; check if LLM generates explanatory text outside dict structures.  
  - Poor relation extraction: Often stems from missing/noisy entity attributes or incomplete scene graphs; trace via ablation.  
  - Visual grounding errors: Typically from inaccurate scene graphs (missing objects) or ViT features losing fine-grained spatial details; evaluate IoU drop without VF.  
  - Entity boundary errors: Common across tasks; may require better tokenization or span-based decoding within code.  
- **First 3 experiments:**  
  1. Ablation on M³D: Remove EA, SG, or VF individually to quantify each component's contribution to all four subtasks.  
  2. Code vs. Natural Language Template: Replace Python template with natural language prompts on M³D and measure hallucination rate.  
  3. Cross-dataset generalization: Test on Twitter-15/17 (MNER) and MNRE (MRE) to verify transfer across datasets with different modalities and task combinations.

## Open Questions the Paper Calls Out
- How does the choice of visual encoder (e.g., ViT vs. alternatives) impact Code-MIE's performance across MIE tasks?  
- Can the explicit scene graph intermediate representation be replaced by an implicit multimodal alignment mechanism within the LLM without sacrificing performance?  
- To what extent does a single task-agnostic code template limit performance on individual MIE tasks compared to task-adapted templates?  
- Can entity attribute extraction be integrated into the main LLM fine-tuning process instead of relying on an external model, and how does attribute quality affect final MIE results?

## Limitations
- Exact prompt formulations and template formatting details are unspecified, risking reproduction variance.  
- Visual projection layer and LoRA hyperparameters are not fully described.  
- Reliance on external models (Qwen3-Max/VL) introduces potential noise in attributes and scene graphs.  
- Template rigidity may fail for complex nested relations beyond current dict structure.

## Confidence
- **Code-style templates reduce hallucination:** High (strong empirical evidence; direct NLT comparison).  
- **Entity attributes improve RE:** Medium (modest ablation gain; depends on attribute quality).  
- **Scene graphs enhance grounding/RE:** Medium (case study support; limited ablation detail; SG quality sensitive).

## Next Checks
1. **Oracle Scene Graph Evaluation:** Replace predicted scene graphs with ground-truth SGs to measure maximum achievable RE/grounding gains, quantifying SG quality impact.  
2. **Attribute Noise Sensitivity:** Inject controlled noise into entity attributes (random removal/alteration) and assess RE performance degradation to test robustness.  
3. **Template Expressiveness Stress Test:** Generate test cases with nested relations beyond dict capacity; evaluate model's failure modes (syntax errors, incorrect simplifications).
