# AscendOptimizer: Episodic Agent for Ascend NPU Operator Optimization

## Quick Facts
- **arXiv ID:** 2603.23566
- **Source URL:** https://arxiv.org/abs/2603.23566
- **Reference count:** 40
- **Primary result:** AscendOptimizer achieves a 1.19× geometric-mean speedup over the open-source baseline, with 49.61% of operators outperforming their hand-written references.

## Executive Summary
Optimizing AscendC operators for Huawei Ascend NPUs requires tuning a coupled host-side tiling program and device-side kernel. Existing approaches suffer from a knowledge bottleneck: no reference implementations or training data are available. AscendOptimizer introduces an episodic two-stage agent to overcome this challenge. Stage I performs hardware-in-the-loop evolutionary search to discover high‑performing tiling configurations. Stage II mines transferable optimization motifs by systematically de‑optimizing seed kernels (“rewind”) and distilling the patterns into a retrievable experience bank that guides kernel rewrites. The two stages alternate in a closed loop, allowing improvements in one component to reshape the search space of the other. On a benchmark of 127 real AscendC operators, AscendOptimizer yields a 1.19× geometric‑mean speedup over the open‑source baseline and outperforms hand‑written references on 49.61% of operators. It also surpasses strong baselines such as BoN and OpenEvolve, demonstrating the complementary benefits of host and kernel co‑optimization.

## Method Summary
The task is the joint optimization of host‑side tiling and device‑side kernels for AscendC operators on an Ascend 910B4 NPU. The episodic agent alternates between two stages. In Stage I, an LLM mutates a base tiling function; each candidate is compiled and executed on real hardware. Failures are discarded, and valid runs are scored by measured latency, selecting the fastest configuration via hardware‑in‑the‑loop evaluation. In Stage II, the system constructs an experience bank by rewinding optimized kernels: an LLM removes specific optimizations stepwise, retaining only those rewrites that cause a significant latency increase. The resulting “bad‑to‑good” trajectories are distilled into semantic tuples (Title, Description, Bottleneck, Code Diff). During online optimization, the agent diagnoses the current kernel’s bottleneck, retrieves relevant tuples using embedding similarity, and rewrites the kernel with an LLM refiner. After both stages complete, the best (tiling, kernel) pair is carried forward into the next round. End‑to‑end latency serves as the primary metric.

## Key Results
- 1.19× geometric‑mean speedup over the open‑source baseline across 127 operators.
- 49.61% of operators achieve latency lower than their hand‑written references.
- AscendOptimizer surpasses strong agent and search baselines (BoN, OpenEvolve) across operator complexity levels, showing complementary gains from host and kernel optimization.

## Why This Works (Mechanism)

### Mechanism 1: Hardware‑in‑the‑loop evolutionary tiling search
An LLM mutates a base tiling function; each candidate is compiled and executed on real NPU hardware. Failures are discarded, and valid runs are ranked by measured latency. This HIL evaluation implicitly captures discontinuous hardware constraints (e.g., buffer limits, alignment) without an explicit cost model. The core assumption is that the tiling space is highly fragmented, so only real hardware execution can reliably distinguish feasible, high‑performance configurations. Evidence: Section 3.3 details evolvable template synthesis, LLM‑based mutation, and rigorous HIL evaluation with zero tolerance for compilation failures. Break condition: if profiling becomes too noisy or slow, the loop may converge prematurely; the mutation approach may fail if tiling logic is fundamentally non‑modular.

### Mechanism 2: Optimization rewind and transferable motifs
Starting from high‑performance seed kernels, an LLM acts as an “inverse agent” to systematically remove optimizations (e.g., unrolling, vectorization, pipelining). Variants are hardware‑validated; only pairs with a significant latency increase are retained. Each trajectory is distilled into a structured tuple (Title, Description, Bottleneck, Code Diff). Assuming such patterns are composable and transferable, during online Stage II the agent diagnoses bottlenecks, retrieves relevant tuples via embedding similarity, and applies the diffs to rewrite the current kernel. Evidence: Abstract describes mining transferable motifs via rewinding; Section 3.4.1 explains stepwise de‑optimization, hardware‑grounded validation, and semantic distillation; Section 4.4.1 shows the experience bank clusters aligned with documentation best practices and new implicit patterns. Break condition: if seed kernels lack diversity or bottleneck descriptions are vague, retrieval may yield irrelevant or harmful patterns.

### Mechanism 3: Closed‑loop alternation for synergistic co‑optimization
The agent runs an outer loop. In each round, Stage I fixes the current kernel and evolves the tiling via HIL search; Stage II then fixes the resulting tiling and refines the kernel using the experience bank. The best (tiling, kernel) pair is inherited by the next round. This block‑coordinate descent exploits coupling between host tiling and device kernel: improvements in one reshape the feasible, high‑performing region of the other. Evidence: Abstract states that alternation steadily expands feasibility and reduces latency; Section 3.5 frames it as block coordinate descent with explicit time scales; Section 4.4.2 presents a case study showing round‑by‑round gains. Break condition: if best pair inheritance fails or inner iteration budgets are too low, alternation may stagnate.

## Foundational Learning
**Tiling Configuration** – Host‑side parameters that partition computation and data movement across NPU resources. *Why needed:* Determines how work is mapped to compute units and on‑chip memory; incorrect tiling leads to underutilization or resource exhaustion. *Quick check:* Can you identify and adjust tile sizes and mapping loops in a tiling function?  
**Device‑side Kernel Optimization** – Low‑level code transformations (loop unrolling, vectorization, DMA pipelining) that affect compute throughput and memory bandwidth. *Why needed:* Directly controls the efficiency of the kernel on the NPU’s execution units. *Quick check:* Can you locate DMA transfers, compute loops, and barrier synchronizations in an AscendC kernel?  
**Hardware‑in‑the‑Loop (HIL) Evaluation** – Executing candidate programs on actual NPU hardware to measure latency and validate correctness. *Why needed:* Captures real hardware constraints (e.g., resource limits, alignment rules) that are difficult to model accurately. *Quick check:* Does your search infrastructure compile and profile each candidate on the target NPU and use measurements as the fitness signal?  
**LLM‑Driven Program Mutation** – Using a large language model to modify source code (tiling or kernel) while preserving syntactic correctness. *Why needed:* Provides semantic priors that guide exploration more effectively than random edits in a large, fragmented search space. *Quick check:* Are mutations constrained to preserve compilability, and do they yield diverse yet plausible variations?  
**Optimization Rewind** – Systematically de‑optimizing a high‑performing kernel to generate counterfactual “bad” versions, then extracting the reverse transformations as optimization motifs. *Why needed:* Identifies which specific edits contribute most to performance and creates reusable knowledge. *Quick check:* Can you enumerate a sequence of reversible optimizations and measure the latency difference at each step?  
**Experience Bank with Embedding Retrieval** – A storage of optimization tuples indexed by semantic embeddings; used to find relevant patterns for a given kernel bottleneck. *Why needed:* Allows past optimization experiences to guide future rewrites without reinventing solutions. *Quick check:* Given a bottleneck description, does the retriever return tuples whose diffs address similar issues on other operators?

## Architecture Onboarding

**Component map**  
LLM_Mutator -> Evolvable_Tiling_Template -> Compiler -> NPU_Profiler -> Fitness_Evaluator -> Selection -> Best_Tiling -> Bottleneck_Diagnoser -> Experience_Retriever -> LLM_Kernel_Refiner -> Compiler -> NPU_Profiler -> Kernel_Acceptor -> Best_Kernel. Outer loop controller carries the best (Tiling, Kernel) between stages.

**Critical path**  
For each round: 1) Stage I iterates (mutation → compile → profile → selection) until tiling converges; 2) Stage II diagnoses kernel bottleneck, retrieves relevant tuples, rewrites kernel, and validates; 3) The best pair is updated and fed into the next round. Hardware execution is the dominant cost; the critical path follows the HIL search within Stage I.

**Design tradeoffs**  
- LLM mutation vs. random search: LLM brings semantic guidance but may reduce diversity; random mutation explores more broadly but yields many invalid candidates.  
- Zero‑tolerance compilation filter vs. partial credit: strict filter guarantees only valid configs are considered but discards potentially fixable near‑misses.  
- Experience bank size vs. retrieval latency: larger banks increase coverage but suffer slower lookups and risk of irrelevant matches.  
- Alternation frequency: running too many inner iterations per stage may cause diminishing returns; too few prevents the coupling benefits from manifesting.

**Failure signatures**  
- High compile failure rate in Stage I (mutations often syntactically invalid).  
- Stage II retrieves tuples that do not improve or worsen latency (low retrieval precision).  
- Closed‑loop shows no latency improvement across rounds.  
- Noisy latency measurements mask true performance differences, leading to inconsistent selection.

**First experiments**  
1. **Baseline validation of HIL tiling search:** Run Stage I alone on a simple operator (e.g., matrix multiplication) to verify the mutation‑compile‑profile pipeline and assess mutation correctness.  
2. **Experience bank sanity check:** Build the bank from a small set of seed kernels (e.g., 5 operators). Manually inspect a sample of distilled tuples to ensure they capture meaningful optimizations and have clear bottleneck descriptions.  
3. **One‑round alternation test:** Execute a full iteration (Stage I then Stage II) on 3 diverse operators. Compare the final (tiling, kernel) pair against the initial baseline to confirm that the alternation can improve both components.

## Limitations
- **Reproduction gaps:** Exact LLM prompts, decoding parameters, hyperparameters (population size, mutation rate, retrieval top‑k), and profiling methodology are not disclosed, preventing faithful replication.
- **Narrow evaluation context:** Results are obtained on a specific benchmark (127 operators from `cann-ops`) with minimal external citation, limiting claims about generalizability.
- **Missing ablations:** The independent contribution of the experience bank versus the evolutionary tiling search is not isolated; the necessity of closed‑loop alternation is not definitively proven.

## Confidence
- **HIL evolutionary tiling search efficacy:** Medium
- **Transferable motifs via rewind:** Low
- **Synergistic closed‑loop alternation:** Medium

## Next Checks
1. Ablate the experience bank: Disable Stage II and measure the performance gain attributable solely to evolutionary tiling search.
2. Test transferability across operator types: Apply the pre‑built experience bank to a held‑out set of operator categories (e.g., only reductions or convolutions) to quantify motif generalizability.
3. Independent replication on public Ascend hardware: Execute the full pipeline on a publicly accessible Ascend NPU instance (if available) using reported hyperparameters or a reasonable search to verify the 1.19× geometric‑mean speedup.
