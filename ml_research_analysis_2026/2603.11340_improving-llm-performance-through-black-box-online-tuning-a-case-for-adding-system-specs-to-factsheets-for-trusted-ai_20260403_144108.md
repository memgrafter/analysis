# Improving LLM Performance Through Black-Box Online Tuning: A Case for Adding System Specs to Factsheets for Trusted AI
## Quick Facts
- **arXiv ID:** 2603.11340
- **Source URL:** https://arxiv.org/abs/2603.11340
- **Reference count:** 29
- **Primary result:** SLO-Tuner reduces p99 latency from ~1.36s to ~0.70s and nearly doubles goodput (from 8 to 15 req/s) under a 1.2s SLO for TinyLlama served via vLLM.

## Executive Summary
This paper tackles tail-latency violations in LLM serving by introducing SLO-Tuner, a black-box online hill-climbing controller that maximizes goodput (requests meeting a p99 SLO). Using only end-to-end measurements, it tunes logical knobs—concurrency, batch size, and speculative decoding parameters—to balance throughput and strict latency targets. On TinyLlama/vLLM, it achieves nearly a 50% reduction in p99 and doubles goodput, demonstrating that treating speculative decoding as a tunable runtime parameter is essential for tight SLOs. A lightweight simulator guides safe exploration and shows qualitative alignment with live system behavior.

## Method Summary
SLO-Tuner employs deterministic hill-climbing over a logical knob vector (concurrency, max_num_seqs, speculative width, on/off). Starting from a baseline, it evaluates a fixed set of neighboring configurations by measuring end-to-end latency percentiles over short segments (e.g., 30s measurement after 10s warmup). Each configuration’s score combines goodput, a penalty for p99 exceeding the SLO, and a hardware cost term. The controller moves to a neighbor if its score improves sufficiently or if the current p99 violates the SLO. A discrete-event simulator, calibrated for queueing and speculative dynamics, is used for stress-testing and trend exploration, but final decisions rely on live server measurements. An adapter layer maps logical knobs to stack-specific flags (e.g., vLLM’s `--num-speculative-tokens`), enabling black-box portability.

## Key Results
- p99 latency dropped from ~1.36s to ~0.70s under a 1.2s SLO.
- Goodput nearly doubled from 8 to 15 requests/s.
- Ablations confirm speculative width strongly impacts tail latency; reducing it is critical for meeting tight SLOs.

## Why This Works (Mechanism)
### Mechanism 1: Black‑Box Hill‑Climbing via End‑to‑End Measurements
The controller iteratively evaluates the current configuration and a small neighbor set, computing a score `S(K)=goodput(K)−λ·max(0,p99(K)−SLO)−hw_cost(K)`. It moves to the highest‑scoring neighbor if improvement exceeds a threshold or if the current p99 violates the SLO. The approach assumes a locally smooth performance surface and stable estimates from short measurement segments. Evidence: The vLLM experiments show consistent trajectory improvement. Break condition: May converge to a local optimum if the surface is non‑convex or measurement noise misleads moves.

### Mechanism 2: Treating Speculative Decoding as a Tunable Parameter
Speculative decoding can reduce average latency but introduces variance from rejected drafts, which inflates tail latency. By including speculative width as a tunable knob, the controller automatically backs off from aggressive speculation (or disables it) when p99 threatens the SLO, trading average throughput for tail compliance. Evidence: Ablations (Fig. 5b) show p99 worsening as width increases (0→16: ~0.77s→~2.00s); the controller reduces width. Break condition: Requires stack to expose speculative controls; rapid workload shifts may outpace adaptation.

### Mechanism 3: Lightweight Simulator for Safe Exploration
A discrete‑event simulator models arrivals, FCFS queuing, batch formation, and speculative decoding via logical factors (draft width W, verifier cadence k). It estimates p99 and goodput to guide the search toward SLO‑feasible regions, while live measurements ensure hardware‑specific saturation points are captured. Evidence: Simulator trajectories mirror live vLLM results (e.g., moving toward smaller k and moderate batch size). Break condition: Calibration may be inaccurate for different hardware/models; it does not model multi‑tenant interference, so trends may diverge in cluster deployments.

## Foundational Learning
- **Tail Latency SLOs and Goodput** – Optimizes requests meeting a p99 target, not raw throughput. Goodput = SLO‑satisfying throughput. *Quick check:* If throughput=20 req/s but only 8 meet p99≤1.2s, goodput=8 req/s.
- **Speculative Decoding Mechanics** – Draft tokens generated by a small model are verified by the target model; wider drafts increase verification variance and can harm tail latency. *Quick check:* Why might disabling speculative decoding improve p99? Because rejected drafts add extra verification work that inflates tail latency.
- **Black‑Box Optimization via Hill Climbing** – No internal instrumentation; uses deterministic neighbor evaluation and a scored move rule. *Quick check:* Two risks: (1) converging to a local optimum on a non‑convex surface; (2) noise in short segments causing erroneous moves.

## Architecture Onboarding
Component map: Request Generator → Server Target (simulator or live vLLM) → Metrics Module (computes p99, goodput) → Tuner Controller (hill‑climb loop, scoring) → Adapter Layer (maps logical knobs to stack flags). Simulator also used in parallel for trend guidance.

Critical path: Initialize baseline `K0` → Per iteration: start segment, warmup, measure → compute `p99(K)`, `goodput(K)`, `S(K)` → evaluate all neighbors’ scores → decide move: `K ← K*` if `S(K*)−S(K) ≥ δ` or `p99(K)>SLO` and `S(K*)>S(K)` → repeat until step budget → re‑evaluate `K_best`.

Design tradeoffs:
- Black‑box portability vs. control granularity: Public APIs enable cross‑stack deployment but miss fine‑grained knobs.
- Simulator‑guided exploration vs. fidelity: Cheap, safe stress‑testing but requires calibration; may mispredict absolute p99.
- Fixed neighbor steps vs. adaptive search: Predictable overhead but may get stuck; Bayesian optimization could be more sample‑efficient but noisier.

Failure signatures:
- Persistent p99 violation: SLO too aggressive or knob space insufficient.
- Oscillating knobs: Noisy measurements or inappropriate step size `δ`.
- Simulator‑vLLM trend mismatch: Queueing delay model mis‑calibrated.

First 3 experiments:
1. Baseline sweep on simulator: Grid search over knobs (spec width W, verifier cadence k, batch size B) to visualize goodput vs. p99 trade‑off surface.
2. Hill‑climb on simulator: Run controller for 6–8 steps from mid‑range config (e.g., W=2, k=12, B=16); verify trajectory moves toward smaller k and moderate B, keeping EMA p99 near SLO.
3. Live vLLM tuning: Execute controller on vLLM; confirm p99 drops from ~1.36s to ~0.70s and goodput doubles, primarily by reducing speculative width.

## Open Questions the Paper Calls Out
- How to calibrate the simulator for accurate absolute p99 prediction across speculative widths? (Simulator underestimates p99 at width 16; future work notes tightening calibration.)
- Does SLO‑Tuner work with larger models (>7B) and realistic multi‑tenant workloads? (Current evaluation uses 1.1B model with synthetic steady load; conclusion calls for extension.)
- Can SLO‑Tuner tune without restarting the server? (Limitations note restarts are untenable; current implementation restarts vLLM per segment.)

## Limitations
- Simulator calibration parameters and exact client workload details are unreleased, hindering exact replication.
- The knob space may be insufficient for complex models/hardware, and hill‑climbing may converge to local optima on non‑smooth performance surfaces.
- Results are validated only on a 1.1B model with synthetic single‑prompt steady load; generalizability to larger models and production workloads is unknown.

## Confidence
- Black‑box hill‑climbing maximizes goodput: **Medium** (vLLM evidence strong but local smoothness assumption risks suboptimality).
- Treating speculative decoding as tunable is critical: **High** (ablation data clearly shows p99 worsening with increased width).
- Simulator safely guides live tuning: **Medium** (qualitative trend alignment shown but quantitative misalignment and limited generalizability).

## Next Checks
- Verify simulator calibration: Request exact timing parameters (prefill/decode latencies, noise distributions) and `defaults.yaml` used in vLLM‑aligned runs to assess fidelity.
- Test generalization: Re‑run live vLLM experiment on larger models (e.g., Llama‑2‑13B) or different hardware (e.g., A100) to check if the same knob trajectory holds and simulator trends remain directionally correct.
- Compare optimization strategies: Implement a Bayesian optimizer (e.g., GPyOpt) for the same knob space and compare sample efficiency and final goodput against deterministic hill‑climber on the simulator, measuring sensitivity to measurement noise.
