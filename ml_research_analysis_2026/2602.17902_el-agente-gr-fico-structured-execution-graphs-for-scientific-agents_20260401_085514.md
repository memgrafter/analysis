# El Agente Gráfico: Structured Execution Graphs for Scientific Agents

## Quick Facts
- **arXiv ID:** 2602.17902
- **Source URL:** https://arxiv.org/abs/2602.17902
- **Reference count:** 40
- **Primary result:** Achieved ~99% accuracy on quantum chemistry tasks with GPT-5 while reducing token consumption by 14× and cost by 96% versus a prior multi-agent system.

## Executive Summary
El Agente Gráfico introduces a single-agent framework that replaces unstructured textual context in LLM-driven scientific workflows with a type-safe execution graph and a persistent knowledge graph. Computational state is managed as validated Python object graphs (ConceptualAtoms) via an object-graph mapper, enabling precise tool orchestration and full provenance tracking without inflating LLM context. On quantum chemistry benchmarks, the system reached near-perfect accuracy with GPT-5, drastically lowered token usage and monetary cost, and scaled robustly to complex workflows like conformer search and metal-organic framework design through parallel computation and cross-session memory.

## Method Summary
The task is to build a single-agent framework that uses typed execution graphs and a knowledge graph (KG) to manage computational state for scientific workflows, thereby reducing LLM context and improving reliability. Inputs include natural language prompts and molecular structures (SMILES, XYZ, CIF) across six quantum chemistry exercises at two difficulty levels (120 total runs). Objectives are high accuracy (~99% with GPT-5), significant token reduction (~14× vs. prior multi-agent system), and lower cost (96% reduction). The method employs a pydantic-ai-based agent with typed workflows for GPU4PySCF and MOF tools. An object-graph mapper (OGM) serializes Python objects (ConceptualAtoms) to/from a Blazegraph KG, while an LLM router dynamically controls workflow progression. Evaluation runs across eight LLMs on fixed benchmarks, comparing against the prior El Agente Q multi-agent system.

## Key Results
- Near-perfect accuracy (~99%) achieved with GPT-5 on quantum chemistry tasks.
- ~14-fold token reduction (from ~1.6M to ~100k) and 96% cost reduction ($4.67 to $0.17) compared to El Agente Q.
- Successful scaling to complex workflows (conformer search, MOF design) with robust parallel computation and cross-session memory via the KG.

## Why This Works (Mechanism)
The system mitigates LLM fragility and context overload by externalizing computational state from the prompt. A type-safe execution graph encodes workflows as validated Pydantic models, ensuring structural correctness and enabling efficient tool sequencing. The persistent knowledge graph stores ConceptualAtoms (Python object graphs) via an OGM, providing durable, queryable state that survives across LLM calls and sessions. This separation prevents context window saturation, reduces token waste from repeated state serialization, and maintains strict provenance. The LLM router operates on the compact graph representation, dynamically selecting next actions without re-parsing full histories, while the OGM handles lazy loading and identity management to keep runtime memory lean.

## Foundational Learning
- **Execution Graph**: A typed, validated DAG of computational steps. *Why needed*: Replaces free-form LLM reasoning with deterministic, inspectable workflows; prevents invalid state transitions. *Quick check*: Verify graph nodes/edges are defined as Pydantic models with strict schemas.
- **Knowledge Graph (Blazegraph)**: A persistent RDF store for ConceptualAtoms. *Why needed*: Enables cross-session memory, provenance queries, and state sharing without LLM context. *Quick check*: Query KG for objects created in a prior session and confirm retrieval.
- **Object-Graph Mapper (OGM)**: Bidirectional serializer between Python objects and KG triples. *Why needed*: Bridges in-memory object graphs with persistent storage; manages identity and lazy loading. *Quick check*: Serialize a ConceptualAtom to KG, then deserialize and assert object equality/identity.
- **ConceptualAtoms**: Validated Python object graphs representing computational entities (molecules, energies). *Why needed*: Enforces type safety and domain constraints at runtime; provides a stable state representation. *Quick check*: Attempt to instantiate a ConceptualAtom with invalid data (e.g., negative bond length) and confirm Pydantic validation error.
- **pydantic-ai**: Framework for LLM tool orchestration with type hints. *Why needed*: Integrates typed tools seamlessly with the LLM router; auto-generates schemas for tool calls. *Quick check*: Define a simple tool with a Pydantic input model and observe correct LLM function-calling behavior.
- **Dynamic Routing**: LLM-driven selection of next graph node based on current state. *Why needed*: Allows flexible workflow adaptation to intermediate results without predefined linear scripts. *Quick check*: Log router decisions during a multi-step task and verify they follow graph edges.

## Architecture Onboarding
**Component map:** Prompt -> LLM Router -> Execution Graph (Workflow) -> OGM -> Knowledge Graph (Blazegraph) -> Tools (GPU4PySCF, CREST, Zeo++, etc.) -> Results; Tools also update KG via OGM.

**Critical path:** 1) Parse user prompt into initial graph state. 2) Router selects next executable node. 3) OGM fetches required objects from KG (or creates new ones). 4) Tool runs with validated inputs. 5) Results wrapped as new ConceptualAtoms, validated, and persisted via OGM. 6) Graph advances; repeat until completion. 7) Final output derived from graph state.

**Design tradeoffs:** Single-agent simplicity vs. multi-agent scalability (current design avoids coordination overhead but limits parallel specialization); graph serialization cost vs. context reduction (KG access adds latency but saves tokens); persistent KG enables memory but requires careful versioning and consistency management.

**Failure signatures:** 
- GPU context conflicts when multiple jobs compete (missing custom scheduler).
- Dependency mismatches from forked packages (e.g., GPU4PySCF patches).
- KG query timeouts or triple store connectivity issues.
- ConceptualAtom validation failures due to incorrect tool outputs.
- Token limit errors if graph serialization unexpectedly grows.

**First experiments:**
1. **Dependency validation**: Set up Python 3.12.12 environment with exact packages from Section 5.2; independently run GPU4PySCF, CREST, and Zeo++ on sample inputs to verify installations.
2. **KG persistence test**: Start Blazegraph via Docker, load provided ontology, use OGM to store and retrieve a simple ConceptualAtom (e.g., a molecule with XYZ coordinates); confirm object identity preservation across sessions.
3. **End-to-end dry run**: Execute one easy quantum chemistry exercise with a low-cost LLM (e.g., GPT-4o), tracing the full graph execution, OGM serialization logs, and final accuracy; compare token count against a baseline ReAct agent prompt.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the type-safe execution graph be extended to support asynchronous, resource-aware execution with portable agent skills?
- **Basis in paper:** The authors identify extending to "asynchronous and resource-aware environment" as future work, noting the current "single-runtime design implicitly couples workflows through global GPU contexts" requiring "careful parallelism configuration."
- **Why unresolved:** The architecture lacks explicit resource primitives and isolation mechanisms, limiting scalability and fault tolerance for heterogeneous computational environments.
- **What evidence would resolve it:** Implementation of portable agent skills with declarative resource requirements demonstrating automatic, dynamic allocation across GPU/CPU resources in multi-workload scenarios.

### Open Question 2
- **Question:** How can ontologies and evaluation criteria co-evolve to handle agent-discovered solution pathways that fall outside manually-specified rubrics?
- **Basis in paper:** The authors state: "agents often discover solution pathways that fall outside manually-specified rubrics, making it increasingly difficult to evaluate accurately... central challenge for future research is the co-evolution of semantic representation and the evaluation framework."
- **Why unresolved:** Benchmark construction and ontological definitions are "time-consuming and laborious," creating a bottleneck as agent capabilities expand beyond anticipated solution strategies.
- **What evidence would resolve it:** An adaptive evaluation system where ontology refinements automatically propagate to evaluation metrics, validated by consistent assessment across agent-discovered pathways in multiple domains.

### Open Question 3
- **Question:** Can the knowledge graph architecture scale to multi-agent collaboration and long-horizon tasks requiring temporal reasoning and memory consolidation?
- **Basis in paper:** The authors note extending to "multi-agent collaboration or long-term operation introduces challenges in synchronizing shared state, managing divergent KGs, ensuring consistency across sessions, and need for richer context graphs across agents and time."
- **Why unresolved:** The current design assumes single-agent, single-session operation over persistent KG; distributed coordination and temporal memory remain unexplored.
- **What evidence would resolve it:** Demonstration of distributed KG synchronization protocol and multi-agent system performing collaborative discovery over extended time horizons with preserved provenance.

## Limitations
- Core state management (OGM and ConceptualAtoms implementation) is not publicly released, preventing verification of type safety, lazy loading, and identity claims.
- Ground truth datasets and full evaluation rubrics are missing; forked tool versions lack detailed documentation, hindering independent benchmark replication.
- Scalability assertions about parallel coordination and cross-session memory rely on proprietary KG pipeline and custom GPU scheduler, which are not reproducible.

## Confidence
- **State representation & token reduction:** Medium (graph serialization plausibly yields savings, but unverified without OGM code and logging).
- **Accuracy (~99% on quantum tasks):** Medium (benchmark design clear, but missing ground truth and fork details block validation).
- **Generalizable framework:** Low (no open-source release; broader workflow claims are anecdotal and lack third-party replication).
