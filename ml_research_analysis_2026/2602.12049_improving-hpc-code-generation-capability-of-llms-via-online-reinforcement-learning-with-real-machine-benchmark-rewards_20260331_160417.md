# Improving HPC Code Generation Capability of LLMs via Online Reinforcement Learning with Real-Machine Benchmark Rewards

## Quick Facts
- **ArXiv ID:** 2602.12049
- **Source URL:** https://arxiv.org/abs/2602.12049
- **Reference count:** 40
- **Primary result:** Achieved 549 GFLOPS (20.4% of theoretical peak) on 256³ matrix multiplication via staged RL, improving baseline by up to 125% at -O0.

## Executive Summary
Large language models (LLMs) can generate functionally correct HPC code but often lack runtime performance optimizations. This paper addresses that gap by applying online reinforcement learning (RL) with real-machine performance rewards. The method uses Group Relative Policy Optimization (GRPO), where the LLM generates multiple code samples per prompt, their actual GFLOPS on a supercomputer are measured, and group-relative advantages guide policy updates without a critic. Exploration is structured by a Staged Quality-Diversity (SQD) algorithm that progressively permits optimization techniques (e.g., SIMD, prefetching) across sequential stages. On a 256³ matrix multiplication kernel, the approach yields up to 549 GFLOPS (20.4% of peak) and eliminates pre-training biases like unnecessary read-modify-write patterns, with gains of 125% at -O0, 16% at -O1, and 18% at -O3 over baselines.

## Method Summary
The training loop is synchronous and online: the LLM (Qwen2.5-Coder 14B) generates batches of C code for a fixed matrix multiplication prompt. Each sample is transferred to a CPU cluster, compiled with GCC (flags vary by experiment), executed, and its runtime converted to GFLOPS. These raw rewards are normalized within the batch (subtract mean, divide by std) to compute advantages for GRPO updates, which use a clipped surrogate objective and a KL penalty to a reference model. SQD imposes stage-specific constraints via regex; per iteration, the top 40% of codes advance to the next stage, the middle 30% generate variants at the same stage, and the bottom 30% (including errors) generate repaired variants. This creates a curriculum that gradually introduces optimization techniques while maintaining diversity.

## Key Results
- Experiment 1 (fixed prompt, no SQD) peaked at 230.70 GFLOPS.
- Experiment 2 (with SQD) reached 549 GFLOPS (20.4% of theoretical peak), improving over baseline by 125% at -O0, 16% at -O1, and 18% at -O3.
- Optimal generated code used a simple triple loop with 8 accumulators and prefetching, explicitly avoiding read-modify-write patterns present in pre-training outputs.

## Why This Works (Mechanism)

**Mechanism 1: GRPO Advantage Stabilization**  
Group Relative Policy Optimization converts raw GFLOPS into a stable, critic-free learning signal. For each prompt, *G* code samples are generated; advantages are computed as (reward − group mean) / group std. This group-relative baseline removes dependency on an absolute scale, making updates resilient to hardware noise or compiler non-determinism, as only intra-batch rankings matter. Evidence includes the paper’s equations, ablations showing β sensitivity, and alignment with RLEF principles. Failure occurs if reward corruption or gradient instability (e.g., misconfigured KL penalty) disrupts ranking stability.

**Mechanism 2: Staged Quality-Diversity (SQD) Curriculum**  
SQD structures exploration across optimization techniques by defining sequential stages (e.g., register blocking → SIMD → OpenMP). Within each iteration, top 40% of codes advance, middle 30% stay, and error-prone 30% generate repairs. This creates a search tree that incrementally introduces constraints while preserving diversity, preventing premature convergence. Experiment 2’s superior results and cleaner learning curves support this. Risks include stage constraints being too restrictive (population collapse) or misaligned with model capability (failed transitions).

**Mechanism 3: Overcoming Pre-training Biases**  
The reward function (solely final GFLOPS) directly penalizes inefficient patterns like read-modify-write updates to `C`, which incur extra memory traffic. Through many GRPO updates, such patterns are down-weighted relative to write-after-accumulate approaches. Evidence shows the best code eliminated read-modify-write, which was common in pre-training outputs. This relies on the performance delta being detectable despite other optimizations; compiler auto-vectorization at -O3 could shrink the delta and weaken the signal.

  *Why needed:* Core method uses scalar execution performance (GFLOPS) as reward, not human labels.

## Architecture Onboarding
GPU Training Cluster (LLM + vLLM + ms-swift) → Coordinator Node → CPU Benchmark Cluster (GCC compilation, execution, GFLOPS measurement) → Coordinator Node → GPU Training Cluster (GRPO update). Storage/Logging persists codes, rewards, and checkpoints.

**Critical path:** Synchronous generate → transfer → compile/run → compute reward → GRPO update. Any bottleneck (network, compiler queue, timeout) stalls training.

**Design tradeoffs:**  
- Realism vs. cost/latency: real-machine rewards are accurate but introduce seconds-per-sample latency and resource contention.  
- Staged constraints vs. flexibility: regex-based stages provide clean curricula but may prune novel pattern combinations.  
- Group size (G=64): larger *G* stabilizes advantages but increases benchmark cost per step.

**Failure signatures:**  
- Reward skew: >90% samples in same penalty bucket (e.g., compile errors) indicates model stuck.  
- Stage leakage: Stage 1 codes using SIMD (Stage 3) suggest constraint bypass.  
- No learning: Learning-rate run tracks no-update baseline, implying ineffective gradients or high KL penalty.

**First 3 experiments:**  
1. **Hyperparameter sweep:** Fix prompt and stage (all techniques); sweep compiler level (-O0/-O3), learning rate (2e-7/5e-7), KL penalty β (0/0.001/0.01). Monitor mean/max GFLOPS to identify stable, improving configs. Insight: -O0 gives cleaner signal; β=0 enables exploration.
2. **SQD exploration-only baseline:** Set learning rate to 0; run SQD for iterations. Observe if max GFLOPS per stage improves via selection alone, separating curriculum benefit from parameter updates.
3. **Stage transition analysis:** For successful SQD run (e.g., O1, LR=5e-7), track population composition per iteration. Verify 40%/30%/30% expansion ratios and successful stage advancement; identify bottlenecks in later stages.

## Open Questions the Paper Calls Out
The paper does not explicitly enumerate open questions; however, its narrow experimental scope and method choices naturally lead to several lines of inquiry:
- **Generalization**: The study is restricted to a single 256³ dense matrix multiplication kernel. It remains unknown whether the same approach transfers to other HPC kernels (e.g., stencils, sparse matrix-vector multiplication) or to GPU programming models (CUDA, HIP).
- **Reward signal robustness**: The reliance on real‑machine GFLOPS measurements introduces noise from OS jitter, thermal throttling, and background workload. The group‑relative advantage may tolerate some noise, but the threshold where rankings become unstable is not quantified.
- **Curriculum design**: The staged progression is manually crafted via regex constraints. A learned or adaptive curriculum that dynamically adjusts stage boundaries could improve exploration and avoid premature convergence or stage leakage.
- **Scaling to larger models**: The experiments use Qwen2.5‑Coder 14B. It is unclear how performance would change with larger base models or different architectures, or whether the cost of synchronous real‑machine evaluation becomes prohibitive.
These questions are further highlighted in the Limitations and Next Checks sections.

## Limitations
- **Reward noise:** Real-machine GFLOPS measurements include OS jitter, thermal throttling, and background load; group-relative advantages assume stable intra-batch rankings, but noise tolerance is unquantified.
- **Evaluation scope:** Results are limited to a single 256³ dense matrix multiplication kernel; generalization to other HPC kernels (sparse, stencils) or programming models (MPI, CUDA) is unknown.
- **SQD constraint rigidity:** Stage definitions are fixed, kernel-specific, and manually curated; they may inadvertently prune valid high-performance patterns not in the predefined technique list.

## Confidence
- **GRPO stability:** High (strongly supported by equations, ablations, and corpus alignment).
- **SQD curriculum benefit:** Medium (supported by Experiment 2’s superior results but lacks direct ablation of the staged mechanism).
- **Eliminating pre-training bias:** Medium (direct evidence from code patterns, but causality vs. selection pressure not isolated).

## Next Checks
1. **Reward noise sensitivity test:** Inject controlled noise (e.g., ±5% GFLOPS perturbation) to quantify the breakpoint where intra-batch ranking fails and learning degrades.
2. **Kernel generalization test:** Apply SQD-trained model to at least two other HPC kernels (e.g., 2D/3D stencil, SpMV) with minimal prompt adaptation; measure GFLOPS improvement.
3. **SQD constraint ablation:** Replace staged progression with (a) random stage assignment per sample or (b) single stage with all techniques allowed but same selection ratios; compare performance and diversity to published SQD curve.
