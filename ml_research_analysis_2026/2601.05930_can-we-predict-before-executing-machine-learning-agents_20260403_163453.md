# Can We Predict Before Executing Machine Learning Agents?

## Quick Facts
- **arXiv ID:** 2601.05930
- **Source URL:** https://arxiv.org/abs/2601.05930
- **Reference count:** 40
- **Primary result:** Predicting solution performance via a semantically-augmented data report yields 61.5% pairwise accuracy, enabling a 6× acceleration and +6% performance gain when integrated into a Predict-then-Verify loop.

## Executive Summary
This paper tackles the execution bottleneck in autonomous machine learning agents by introducing the task of **Data-centric Solution Preference**. Instead of physically running every generated code candidate, the method uses a **Verified Data Analysis Report**—a natural language narrative of dataset properties—to prime an LLM to compare two solutions and predict which will perform better on the given data. Evaluated on a large corpus of 18,438 pairwise comparisons across 26 tasks, the approach achieves 61.5% accuracy with well-calibrated confidence. Integrated into the FOREAGENT framework via a **Predict-then-Verify loop**, this predictive capability prunes low-potential candidates before execution, yielding a 6× speedup in convergence and a +6% final performance improvement over execution-only baselines like AIDE, while expanding the search space by 3.2×.

## Method Summary
The core method formalizes **Data-centric Solution Preference**: given a task description `I`, a **Verified Data Analysis Report** `D_rep` generated via a Code-Execution-Verbalization pipeline, and two candidate code solutions `{C0, C1}`, an LLM acts as an **implicit world model** to predict which solution will achieve higher validation performance (`ˆy`) and output a confidence score `c`. The `D_rep` transforms raw dataset statistics into a semantically-rich narrative, enabling the LLM to reason about data-model alignment (e.g., "small N → overfitting risk for deep nets"). This predictive accuracy (61.5%) is leveraged in the **FOREAGENT** system, which wraps the AIDE agent. For each iteration, FOREAGENT generates `m` candidate solutions in parallel, uses the world model to perform all `C(m,2)` pairwise comparisons, and accepts high-confidence predictions (`c ≥ 0.7`) to prune candidates. Only the top-`k` finalist from the predicted rankings undergoes physical execution to obtain ground-truth performance, which then guides the next generation step. This **Predict-then-Verify** loop dramatically reduces the number of expensive executions.

## Key Results
- LLMs achieve **61.5% micro-averaged accuracy** on pairwise solution preference, significantly above random (50%) and a complexity-based heuristic (50.8%).
- The predictive model exhibits **robust confidence calibration**; accuracy rises monotonically with reported confidence, enabling a reliable gating threshold (`c=0.7`).
- Integrated into FOREAGENT, the approach yields a **6× acceleration** in convergence and a **+6% performance gain** over the execution-based AIDE baseline, while exploring a **3.2× larger search space** within the same time budget.

## Why This Works (Mechanism)
### Mechanism 1: Semantic Alignment via Verified Data Report
Raw dataset values (e.g., "N=5,500") are "weak-semantic symbols" that fail to activate the LLM's structured reasoning. The `Code-Execution-Verbalization` pipeline projects numerical statistics (sample size, skew, leakage risks) into a natural language **Data Analysis Report** (`D_rep`). This report, structured as "Observation → Implication," injects inductive biases about data-model fit (e.g., "high class imbalance → consider stratified sampling") directly into the prompt. The LLM, acting as a "rhetorical reasoner," makes an "inference jump" from this semantic framing to assess algorithmic suitability. Evidence: the "Context Mismatch" ablation shows performance drops to 56.8% without `D_rep`, confirming its role as a critical reasoning scaffold. **Break condition:** For entirely novel data modalities or statistical regimes not covered in the verbalization patterns, the `D_rep` may fail to provide relevant implications, degrading prediction accuracy.

### Mechanism 2: Confidence-Calibrated Pruning
The world model's self-reported confidence score `c` correlates strictly with actual accuracy (Figure 3e). This calibrated uncertainty is used as a **reliability gate** in the FOREAGENT loop: only predictions with `c ≥ 0.7` are accepted to prune a candidate immediately; lower-confidence predictions trigger the fallback of physical execution. This selective trust balances the trade-off between speed and fidelity, avoiding catastrophic pruning errors. Evidence: the gating threshold is explicitly set at `c=0.7` based on the calibration curve, and the system's gains depend on this discriminative power. **Break condition:** On out-of-distribution task types (e.g., new ML paradigms), the model's confidence may become miscalibrated—overconfident on invalid patterns—leading to either wasted executions on wrong top candidates or erroneous pruning of valid solutions.

### Mechanism 3: Search Decoupling via Predict-then-Verify
FOREAGENT decouples **cheap, parallelizable hypothesis generation** (LLM inference for `m` codes) from **expensive, sequential validation** (physical execution). The world model performs `C(m,2)` rapid pairwise comparisons to rank all candidates before any execution. Only the finalist (top-`k=1`) is verified. This shifts the bottleneck from execution latency to inference throughput, achieving a **6× speedup** and a **3.2× node expansion**. The acceleration gain is bounded by the prediction accuracy ceiling (~72.2%, the execution-based validation accuracy), as any error in pruning directly wastes the saved execution budget. **Break condition:** If the generative diversity of the `m` candidates is low ("Homogeneity Barrier"), or if the pairwise prediction accuracy is too close to random, the pruning signal becomes noisy and the search expansion yields diminishing or negative returns.

## Foundational Learning
### Concept: Data-centric Solution Preference
- **Why needed:** This formalized task re-frames the problem from "generate and execute" to "predict relative performance from data narratives." It defines the input-output structure that makes the corpus construction and `D_rep` augmentation meaningful.
- **Quick check:** What are the four input components (`I`, `D_rep`, `{C0, C1}`, `P`) and three output components (`cot`, `ˆy`, `c`) of this task, and what does each represent?

### Concept: Implicit World Modeling for Code
- **Why needed:** The paper's thesis adapts RL's "world models" to the *code execution domain*. The "world" is the computational outcome of running ML code on a specific dataset, and the "model" is the LLM's internal simulation of that outcome via semantic reasoning.
- **Quick check:** How does predicting "test set performance" differ from predicting "next token" or "logical consistency"? What makes the data distribution (`D`) a critical, non-symbolic variable?

### Concept: Confidence-Calibrated Pruning
- **Why needed:** FOREAGENT's efficiency gains come from selectively trusting the world model. This requires the model's confidence to be a meaningful, monotonic proxy for correctness, linking the predictive study (Section 5) to the system design (Section 6).
- **Quick check:** If confidence were miscalibrated (e.g., high confidence on wrong predictions), what would be the two primary failure modes in the Predict-then-Verify loop?

### Concept: Semantic Projection of Numerical Data
- **Why needed:** Raw numbers lack the topological structure in embedding space to trigger generalizable reasoning. The verbalization pipeline projects them into a "strong-structural symbol" space (natural language) that aligns with the LLM's pre-training on rhetorical patterns.
- **Quick check:** Why can't an LLM effectively use a table of raw statistics (e.g., mean, std) to reason about algorithmic fit, whereas a sentence like "the target is heavily skewed" activates the right inductive bias?

### Concept: Indirect Epistemic Bound
- **Why needed:** This concept defines the theoretical limit of static prediction: it can never exceed the accuracy of dynamic execution-based validation (`M_val` ceiling ~72.2%), due to fundamental constraints like Rice's theorem.
- **Quick check:** If execution-based validation achieves 72.2% accuracy in predicting test performance, what is the maximum possible accuracy for a purely predictive (non-executing) model, and why?

## Architecture Onboarding
### Component map
Task Description & Dataset -> Data Report Generator -> Verified Data Analysis Report (D_rep) -> World Model (LLM with CoT) -> (predicted winner, confidence) -> FOREAGENT Controller -> (if c≥0.7: prune loser; else: execute both) -> Execution Engine (physical code run) -> performance metric -> feedback to candidate generation (AIDE backbone)

### Critical path
1.  **Pre-processing:** For a new task `I` and dataset `D`, the **Data Report Generator** runs profiling scripts and verbalizes the logs to produce a static `D_rep`. This is done once per task.
2.  **Candidate Evaluation:** When comparing two solutions `{C0, C1}`, the **World Model** is queried with `(I, D_rep, {C0, C1})`.
3.  **Gating:** The **FOREAGENT Controller** checks confidence `c`. If `c ≥ 0.7`, the predicted winner is accepted and the loser is pruned. If `c < 0.7`, both candidates are scheduled for physical execution.
4.  **Verification & Feedback:** The winner (from prediction or execution) is physically executed on `D` to obtain true performance `M`. This result feeds back into the AIDE tree search to guide the next `Generate` phase.
5.  **Loop:** Steps 2-4 repeat until a time budget or convergence criterion is met.

### Design tradeoffs
- **Static Report vs. Dynamic State:** `D_rep` is a one-time, static summary. It cannot capture intermediate training dynamics (e.g., validation curve shape). Tradeoff: immense computational savings vs. loss of temporal signal that might predict overfitting or underfitting.
- **Pairwise vs. Listwise:** The system uses `C(m,2)` pairwise comparisons. This is reliable for LLMs but scales quadratically with candidate pool size `m`. Tradeoff: higher judgment fidelity per comparison vs. potentially prohibitive query cost for large `m`; a tournament or Elo system could reduce queries.
- **Confidence Threshold:** A fixed threshold (`c=0.7`) is used. Tradeoff: higher threshold → fewer executions (more speed) but risks accepting incorrect predictions; lower threshold → more executions (less speed) but safer. Optimal value likely varies by task difficulty.
- **Generative Diversity:** The acceleration relies on the `Generate` phase producing `m` diverse candidates. If all are minor variants, pruning yields little benefit. Tradeoff: increasing `m` boosts diversity chance but linearly increases prediction query count.

### Failure signatures
- **Semantic Misalignment:** The `D_rep` is irrelevant or incorrect (e.g., misses key data issues). **Sign:** Model accuracy drops significantly in the "Context Mismatch" ablation (56.8% vs. 61.3% with report). **Monitor:** Audit `D_rep` for key phrases (e.g., "small sample", "leakage") against ground-truth data properties.
- **Calibration Drift:** Confidence `c` no longer correlates with accuracy on new task types. **Sign:** High-confidence predictions have low match rate with execution results; `Solution Evolution Consistency` metric drops. **Monitor:** Track consistency scores (e.g., Table 13) across domains; a sustained drop indicates miscalibration.
- **Generative Homogeneity:** Candidate pool `C` lacks architectural diversity (e.g., all are ResNets for a tabular task). **Sign:** World model repeatedly selects similar solutions; node expansion (Figure 7c) plateaus early. **Monitor:** Count unique algorithm types/architectures in the candidate pool per iteration.
- **Complexity Heuristic Leakage:** The model is not using data reasoning but a bias that "more complex models win." **Sign:** Accuracy is only marginally above the Complexity Heuristic baseline (50.8%) on "High Complexity Gap" pairs and collapses on "Low Complexity Gap" pairs. **Monitor:** Stratify accuracy by `Complexity Gap` (Figure 3f); a non-positive gap indicates leakage.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Can predictive solution selection ever approach the performance ceiling of actual execution (72.2% accuracy), or is there an unbridgeable epistemic gap due to overfitting and Rice's theorem limits?
- **Basis in paper:** [explicit] Section 5.4 reports that execution-based validation (`M_val`) achieves 72.2% accuracy as a proxy for test performance, while LLM prediction achieves 61.5%. Discussion 6.1 explicitly states this creates an "Indirect Epistemic Bound" and cites Rice's theorem to argue static prediction cannot outperform dynamic verification.
- **Why unresolved:** The paper identifies the gap but does not explore whether advanced representation learning or confidence calibration can close it, nor does it formally characterize the theoretical limit.
- **What evidence would resolve it:** Systematic experiments measuring prediction accuracy as a function of confidence threshold, comparing to the execution ceiling; theoretical analysis of necessary conditions for prediction to approach verification accuracy.

### Open Question 2
- **Question:** What techniques can break the "homogeneity barrier" where current agents produce functionally isomorphic solutions, enabling truly novel, context-specialized algorithm generation?
- **Basis in paper:** [explicit] Discussion 6.1 identifies that current LLMs "hit a Homogeneity Barrier, producing functionally isomorphic solutions that lack context-specific specialization" and calls this a deficit in "Generative Innovation."
- **Why unresolved:** The paper diagnoses the problem but does not propose or evaluate any mechanisms to increase solution diversity or specialization. The FOREAGENT implementation focuses on conservative pruning, not innovation.
- **What evidence would resolve it:** Metrics for solution diversity (e.g., code embedding distances, functional equivalence classes) correlated with performance; experiments with diversity-promoting decoding strategies or training objectives.

### Open Question 3
- **Question:** How can we evolve static "world-blind learners" into models that internalize genuine causal execution dynamics, possibly via interactive simulation rather than static corpus ingestion?
- **Basis in paper:** [explicit] Section 5.3 Discussion argues that scaling fails because "static training corpora consist of code paired with merely trivial inputs or abstract descriptions, lacking the large-scale data distributions required for true dynamic execution interplay." They call for a pivot to "Interactive Simulation."
- **Why unresolved:** The paper shows predictive capability saturates early (scaling laws plateau) but does not implement or test interactive training loops with execution feedback.
- **What evidence would resolve it:** Comparative experiments training models on trajectories that include execution results vs. static code-only data; measuring causal intervention success (e.g., counterfactual reasoning).

### Open Question 4
- **Question:** What architectural or reasoning modifications are needed to extend pairwise preference accuracy (61.5%) to robust global ranking, given the observed dramatic drop in ranking consistency (ρ≈0.23)?
- **Basis in paper:** [explicit] Section 5.2 and Table 3 show that listwise ranking performance degrades sharply: Accuracy@1 falls from 61.3% (pairwise) to 31.1% (5-way ranking) while Spearman correlation remains low (ρ≈0.23).
- **Why unresolved:** The paper identifies this as a scalability defect but does not investigate causes (e.g., intransitivity, context window limits) or propose ranking-specific architectures.
- **What evidence would resolve it:** Analysis of transitivity violations; experiments with listwise training or iterative pairwise comparisons; measuring consistency under varying list sizes.

## Limitations
- **`D_rep` generation ambiguity:** The exact Code-Execution-Verbalization pipeline and prompts are not fully specified, risking variability in the semantic reports that underpin the mechanism.
- **LLM dependency:** Results rely on proprietary models (DeepSeek-V3.2-Thinking, GPT-5.1); future API changes or access issues could hinder replication.
- **Domain coverage:** All evaluations are on 26 MLE-bench tasks; claims about novel ML paradigms or unseen data distributions lack validation.
- **Compute sensitivity:** The reported 6× speedup assumes multi-GPU parallelism; different hardware may yield different acceleration factors.

## Confidence
- **Pairwise prediction accuracy (61.5%)**: Medium – directly reported but depends on unreleased dataset and exact `D_rep` construction.
- **`D_rep` semantic advantage (ablation lift)**: Medium – supported by ablation within same tasks only; generalizability to unseen domains uncertain.
- **Confidence calibration**: Medium – strong correlation shown on test set, but out-of-distribution miscalibration possible.
- **FOREAGENT speedup (+6% gain)**: Medium – integrated outcome relies on multiple Medium-confidence components (prediction accuracy, gating, generative diversity).
