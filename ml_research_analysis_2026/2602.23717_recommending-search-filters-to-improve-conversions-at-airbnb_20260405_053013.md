# Recommending Search Filters To Improve Conversions At Airbnb
## Quick Facts
- arXiv:2602.23717
- Source URL: https://arxiv.org/abs/2602.23717
- Reference count: 30
- One-line primary result: Deployed a multi-task filter recommender at Airbnb, achieving +0.28% (filter panel) and +2.4% (filter bar) lifts in uncanceled bookings.

## Executive Summary
Airbnb’s existing search filter systems prioritize navigation or engagement, not direct conversion. This paper introduces a multi-task machine learning framework that jointly predicts the probability of applying a filter given a query, P(F|Q), and the probability of booking given a filter and query, P(B=1|F,Q). These probabilities are combined into a ranking score with a higher weight on the booking term to counter presentation bias. Online A/B tests demonstrated significant increases in uncanceled bookings, filter usage, and bookings from filtered results, while reducing searches that hit low-inventory states.

## Method Summary
The core method is a multi-task learning model that outputs two scores per filter: the likelihood a user will apply it (P(F|Q)) and the likelihood it leads to a booking (P(B=1|F,Q)). The final ranking combines these scores, emphasizing the booking probability to shift focus toward lower-funnel conversions. The approach also incorporates a technique to mitigate presentation bias—systematic skew from historical filter exposure—by adjusting the training objective. The model was trained on historical Airbnb search logs and deployed as a real-time recommendation service in the filter panel and filter bar.

## Key Results
- Online A/B tests showed statistically significant lifts in uncanceled bookings: +0.28% in the filter panel and +2.4% in the filter bar.
- The treatment increased overall filter usage and bookings originating from filtered searches, while decreasing the rate of searches that resulted in low-inventory (no bookable listings) states.
- Offline evaluation of the P(B=1|F,Q) model achieved a 100.5% improvement in PR-AUC compared to the previous production model.

## Why This Works (Mechanism)
By explicitly modeling the booking probability conditioned on both query and filter, the system optimizes for the ultimate business goal—conversions—rather than intermediate engagement metrics like filter clicks. Weighting the booking term higher in the ranking score incentivizes filters that are more likely to lead to a successful booking. Additionally, the multi-task structure allows sharing of query understanding across both tasks, improving data efficiency. The adjustment for presentation bias ensures that the model does not reinforce historical exposure patterns, which could otherwise favor popular but less profitable filters.

## Foundational Learning
- **Multi-task Learning**  
  *Why needed*: Jointly modeling filter application and booking conversion shares representations and leverages correlations between tasks.  
  *Quick check*: Do both tasks improve when trained together versus separately?
- **Presentation Bias Correction**  
  *Why needed*: Historical filter exposure is biased by UI placement and user habits, misleading the model if uncorrected.  
  *Quick check*: Is there a counterfactual loss adjustment or inverse propensity weighting in the training pipeline?
- **PR-AUC for Imbalanced Targets**  
  *Why needed*: Booking events are rare; PR-AUC focuses on positive class performance.  
  *Quick check*: Does the model maintain high precision at low recall thresholds?
- **Weighted Score Fusion**  
  *Why needed*: Balances engagement (filter usage) with conversion goals.  
  *Quick check*: How sensitive is the overall lift to the weight hyperparameter?

## Architecture Onboarding
Component map: Query Input -> Feature Extraction -> Filter Candidate Retrieval -> Multi-task Scoring (P(F|Q), P(B|F,Q)) -> Weighted Sum Ranking -> Sorted Filter List -> UI Rendering

Critical path: When a user submits a search query, the system extracts query features, fetches candidate filters from a catalog, runs the multi-task model to compute scores for each filter, combines them with a learnable weight (higher for booking), sorts, and returns the top filters to the frontend.

Design tradeoffs:  
- Model complexity vs. latency: deeper networks improve accuracy but add inference cost.  
- Weight on booking term: higher weight may reduce filter diversity and user satisfaction.  
- Real-time vs. batch: updates require balancing freshness with computational overhead.

Failure signatures:  
- Sudden drop in filter click-through rate or booking conversion.  
- Increased latency leading to UI timeouts.  
- Disparate impact on specific user segments (e.g., new vs. returning guests) or filter categories (e.g., price ranges).

First three experiments:  
1. Offline holdout evaluation comparing multi-task model to baseline on PR-AUC and booking prediction.  
2. A/B test on 1% traffic: measure impact on filter usage, booking rate, and low-inventory search reduction.  
3. Subgroup analysis by user geography, device, and filter type to surface potential biases or unintended consequences.

None explicitly identified.

## Limitations
- External validity: Results are from a single marketplace (Airbnb); generalizability to other platforms is unknown.  
- Long-term effects: No evidence on user adaptation, filter fatigue, or sustained conversion gains.  
- Fairness risks: Weighting scheme may disadvantage niche filters or host/guest segments; lack of subgroup evaluation.

## Confidence
- **High**: Observed lifts in uncanceled bookings (+0.28% filter panel, +2.4% filter bar) from online A/B test.
- **Medium**: Claim that directly modeling P(B=1|F,Q) improves conversions over engagement-only models.
- **Low**: Assertion that the approach robustly handles presentation bias without unintended consequences across diverse groups.
- **Low**: Generalizability of the 100.5% PR-AUC improvement to other contexts.

## Next Checks
1. Cross-platform replication: Test the multi-task framework on a different two-sided marketplace (e.g., hotel or rental car booking) to measure conversion lift consistency.
2. Longitudinal A/B analysis: Extend measurement to 6+ months post-deployment, tracking user retention, filter usage decay, and impact on host supply diversity.
3. Subgroup fairness audit: Disaggregate A/B results by user demographics and filter categories to detect unequal benefit distribution or systematic bias.
