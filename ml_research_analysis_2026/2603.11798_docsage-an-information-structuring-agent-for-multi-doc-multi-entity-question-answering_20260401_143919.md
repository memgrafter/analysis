# DocSage: An Information Structuring Agent for Multi-Doc Multi-Entity Question Answering

## Quick Facts
- arXiv ID: 2603.11798
- Source URL: https://arxiv.org/abs/2603.11798
- Reference count: 19
- Primary result: Achieves state-of-the-art on MEBench (89.2% accuracy, +27.2% over GPT-4o+RAG) and Loong (0.53 perfect rate, more than doubled).

## Executive Summary
DocSage is an agentic framework that addresses the limitations of standard RAG and long-context LLMs in Multi-document Multi-entity Question Answering (MDMEQA). Where coarse-grained retrieval and lack of schema awareness hinder cross-document evidence chaining, DocSage introduces a three-module pipeline: interactive schema discovery to infer query-specific relational schemas, logic-aware structured extraction with cross-record consistency checks, and schema-guided relational reasoning via SQL. Evaluated on MEBench and Loong, it substantially outperforms prior approaches, demonstrating robust scaling with entity count and document length.

## Method Summary
DocSage processes a natural language query `q` and a set of unstructured documents `D` through three sequential stages. First, the ASK algorithm interactively discovers a minimal, joinable relational schema `S_q` by generating clarification questions to resolve uncertainties detected across documents. Second, the CLEAR module populates `S_q` with tuples extracted by a fine-tuned language model, then applies conformal confidence calibration and symbolic constraint validation (e.g., functional dependencies, referential integrity) to ensure cross-record consistency. Third, the reasoning module compiles `q` into an optimized SQL query using `S_q`, executes it on the constructed database `DB_q`, and synthesizes the final answer with provenance tracing. The schema `S_q` serves as the central artifact linking all stages.

## Key Results
- On MEBench, DocSage achieves 89.2% accuracy, improving 27.2 percentage points over GPT-4o+RAG.
- On Loong, it more than doubles the perfect answer rate to 0.53.
- Performance remains robust as entity count and document length increase, with minimal degradation beyond 100 entities or 200K tokens.

## Why This Works (Mechanism)

### Mechanism 1: Interactive Schema Discovery
**Claim:** Interactive schema discovery infers a minimal, query-specific relational schema that captures essential entities and their relationships, enabling targeted evidence gathering across documents.  
**Mechanism:** The ASK algorithm starts with a preliminary schema from a document sample, then actively generates clarification questions to resolve alignment conflicts, attribute anomalies, or missing relationships. It uses these questions for targeted retrieval and iteratively refines the schema until convergence.  
**Core assumption:** The query implicitly defines a set of entities and relationships that can be elicited through iterative questioning and validation, even if not explicitly stated in the source documents.  
**Evidence:** [abstract] "dynamic schema discovery to infer query-specific relational schemas"; [section 3.1] details the ASK algorithm steps (initial hypothesis, uncertainty detection, question generation, iterative update). Neighboring papers (e.g., GraphRAG, SRAG) use static or graph schemas, highlighting DocSage's unique *interactive* and *query-specific* approach.  
**Break condition:** If the query is underspecified or the document set lacks coherent relational information, iterative questioning fails, yielding an empty or incoherent schema.

### Mechanism 2: Logic-Aware Structured Extraction
**Claim:** Logic-aware structured extraction with cross-record consistency checks transforms unstructured text into high-fidelity relational tables, reducing extraction errors that would propagate to reasoning.  
**Mechanism:** A base extraction model (fine-tuned via LoRA for schema alignment) produces candidate tuples. A two-level correction (CLEAR) then applies: (A) statistical confidence calibration via conformal prediction, and (B) symbolic logic constraint checking (functional dependencies, temporal orders, referential integrity). Low-confidence or logic-violating tuples trigger targeted re-extraction or disambiguation.  
**Core assumption:** The domain governed by the inferred schema obeys deterministic logical constraints that can be explicitly defined and validated across extracted records.  
**Evidence:** [abstract] "logic-aware structured extraction with cross-record consistency checks"; [section 3.2] details CLEAR’s LoRA-enhanced calibration and constraint validation engine. Related work on error-aware queries is cited, but DocSage’s integration of *cross-record* logic with schema-specific constraints is novel.  
**Break condition:** If source documents contain pervasive contradictions or the schema’s constraints are poorly defined, the correction process either rejects too much valid data or fails to catch critical errors.

### Mechanism 3: Schema-Guided Relational Reasoning
**Claim:** Schema-guided relational reasoning via SQL executes complex multi-hop queries over structured tables, avoiding LLM attention diffusion and enabling deterministic, traceable answer synthesis.  
**Mechanism:** The reasoning module compiles the natural language query into an optimized SQL query using the explicit schema (join keys, relationship definitions). Database operations perform joins, aggregations, and filtering. The result set is traced back to source tuples and document chunks for answer synthesis.  
**Core assumption:** The relational schema accurately models the underlying entity-relationship structure needed to answer the query, such that a SQL query on the populated tables yields the correct answer.  
**Evidence:** [abstract] "schema-guided relational reasoning via SQL" and "precise fact localization via SQL-powered indexing"; [section 3.3] explains query compilation/optimization and traceback. Neighbors (e.g., GNN-RAG) use graph/neural retrieval; DocSage’s *relational, SQL-based* scaffold is a key contrast.  
**Break condition:** If the schema is incomplete or the extraction module populates tables with residual errors violating the query’s logical premises, SQL execution returns incorrect or empty results.

## Foundational Learning

**Concept: Relational Databases & SQL**  
*Why needed:* DocSage represents extracted information as relational tables and uses SQL for reasoning, requiring understanding of tables, primary/foreign keys, joins, and query optimization to achieve deterministic cross-document evidence chaining.  
*Quick check:* How would you design a schema (tables and keys) to answer: "Compare the funding amounts and principal investigators of all research projects mentioned in these 20 grant award documents, grouped by university"?

**Concept: Retrieval-Augmented Generation (RAG)**  
*Why needed:* DocSage is an advancement over standard RAG; understanding coarse-grained vector retrieval, its limitations for multi-entity reasoning, and graph-based RAG variants is necessary to appreciate DocSage's structured alternative.  
*Quick check:* Why might a standard RAG system fail to answer: "What is the average h-index of all researchers who have co-authored papers with both Dr. X and Dr. Y, where their joint papers are cited in Documents A, B, and C?"?

**Concept: Agentic Workflows & LLM Orchestration**  
*Why needed:* DocSage is an agentic framework with sequential modules and feedback loops, requiring understanding of task decomposition, state management (schema, database), and dynamic decision-making.  
*Quick check:* What are the risks of an iterative, multi-stage agentic pipeline like DocSage compared to a single monolithic LLM call, and how does the paper attempt to mitigate them?

## Architecture Onboarding

**Component map:**  
Schema Discovery (ASK) -> Structured Extraction (CLEAR) -> Relational Reasoning

**Critical path:**  
Query → Schema Discovery (S_q) → Extraction (DB_q) → SQL Compilation → Execution → Answer Synthesis. The schema S_q is the central artifact passed between all stages.

**Design tradeoffs:**
- Accuracy vs. Latency: Interactive schema discovery and multi-stage extraction introduce significant overhead but trade for higher precision on complex queries.
- Schema Minimalism vs. Completeness: Minimal joinable schema reduces noise but risks omitting critical relationships if ASK’s questions are insufficient.
- Generalization vs. Domain Specificity: Generic logical constraints may require customization for specialized domains (e.g., legal, clinical).

**Failure signatures:**
- Schema-level: No joinable keys between entity tables; missing critical relationship types in S_q.
- Extraction-level: High rejection rate in CLEAR; persistent foreign key mismatches.
- Reasoning-level: SQL returns empty or implausible aggregates; provenance traces to low-confidence or conflicting source tuples.
- System-level: End-to-end latency exceeds thresholds; ASK iterations fail to converge.

**First 3 experiments:**
1. **Schema Discovery Isolation:** Feed a fixed document set and query. Manually inspect the output schema S_q from ASK vs. a baseline (e.g., extract all entities/relations). Does S_q contain expected entities/relationships? Are join keys sound?
2. **Controlled Extraction Test:** Create a synthetic document set with known factual relationships and intentional noise (typos, numerical errors). Run extraction with and without CLEAR. Measure precision/recall of populated tables against ground truth.
3. **SQL Reasoning Probe:** For a set of simple multi-entity questions with known answers, manually write the expected SQL query. Compare the auto-generated SQL and its execution result. Is the SQL syntactically/semantically correct? Does it use the correct joins from S_q?

## Open Questions the Paper Calls Out
1. **Computational efficiency:** How can the iterative agentic workflow’s non-trivial cost be reduced while maintaining accuracy? The paper states this as a limitation but provides no solutions.
2. **Robustness to noise/contradictions:** To what extent does performance degrade with extremely noisy, contradictory, or domain-specialized texts? Evaluations use curated benchmarks; real-world boundaries are untested.
3. **Scalability of ASK:** Does the interactive schema discovery remain effective and efficient as document count and entity diversity scale to thousands? The iterative questioning cycle’s complexity and convergence are unanalyzed for large-scale scenarios.
4. **Constraint design space:** What is the relative contribution of specific logical constraint types (functional dependencies, temporal rules, foreign keys) across different MDMEQA domains and query types? The paper does not explore the constraint design space.

## Limitations
- Schema discovery convergence and question curation under ambiguous queries are uncertain; sampling strategy for initial document sample is unspecified.
- Extraction constraint engine completeness and re-extraction workflow details are unreported; LoRA training data/hyperparameters are missing.
- Evaluations use curated benchmarks (MEBench, Loong); real-world generalizability to noisy, contradictory, or domain-specific corpora remains unvalidated.

## Confidence
- Architectural novelty (agentic, schema-guided): High
- End-to-end SOTA results (MEBench/Loong): High
- Robustness to scale (entities/tokens): Medium

## Next Checks
1. **Schema Discovery Probe:** Run ASK on a held-out query set with manually defined "gold" schemas. Measure schema completeness (recall of required entities/relations) and minimalism (precision). Track convergence iterations vs. query ambiguity.
2. **Constraint Engine Stress Test:** Populate synthetic tables with controlled logic violations (e.g., `start_date > end_date`). Quantify false positive/negative rates of CLEAR’s validation and correction success rate.
3. **SQL Compilation Fidelity:** For 50 complex multi-hop queries from Loong, manually write oracle SQL. Compare auto-generated SQL for semantic equivalence (join correctness, aggregation logic) and execution result match.
