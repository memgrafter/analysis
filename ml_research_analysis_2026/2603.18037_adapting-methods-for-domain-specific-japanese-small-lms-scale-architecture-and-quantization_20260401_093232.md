# Adapting Methods for Domain-Specific Japanese Small LMs: Scale, Architecture, and Quantization

## Quick Facts
- arXiv ID: 2603.18037
- Source URL: https://arxiv.org/abs/2603.18037
- Reference count: 35
- Primary result: A three-stage QLoRA approach identifies optimal training scale (4k samples), base-model selection (Japanese-continual pre-trained Llama-3 models outperform multilingual GQA), and quantization effects (Q4_K_M benefits Llama-3 but degrades GQA) for domain-specific Japanese 8B models.

## Executive Summary
This paper investigates how to efficiently build domain-specific Japanese small language models (around 8B parameters) using QLoRA. It tackles three practical questions: the optimal amount of training data, which base model to choose, and how quantization affects performance. The authors propose a progressive three-stage methodology: first, scale-learning on Swallow-8B with datasets of 1k–5k samples identifies 4,000 as the optimal size (test NLL minimal, overfitting at 5k). Second, using this optimal dataset, they compare four Japanese LLMs (Swallow-8B, ELYZA-JP-8B, Qwen2.5-7B, Tanuki-8B). Llama-3 models with Japanese continual pre-training (Swallow, ELYZA) outperform the multilingual GQA model Qwen2.5-7B. Third, quantization analysis shows that converting merged models to GGUF Q4_K_M improves Llama-3 models slightly (+0.01–0.03 points) but significantly degrades Qwen2.5-7B (‑0.28 points) due to its GQA architecture. The recommended production model is Swallow-8B Q4_K_M, achieving 2.83/3 score with 8.9 s/question and 4.9 GB size.

## Method Summary
The study employs a three-stage progressive QLoRA pipeline. Stage 1: Train Swallow-8B with LoRA (r=16, 4‑bit NF4, 3 epochs, lr=2e‑4, cosine warmup 10%) on five nested subsets (1k–5k) of a technical QA dataset derived from Japanese River and Sediment Control standards (total 5,578 pairs, rebalanced). Test-set negative log-likelihood (NLL) determines the optimal scale (n=4,000). Stage 2: Using n=4,000, fine‑tune four candidate models (Swallow-8B, ELYZA-JP-8B, Qwen2.5-7B, Tanuki-8B) with LoRA (r=32, dropout=0.05). Merge adapters to produce FP16 checkpoints. Stage 3: Convert each checkpoint to GGUF Q4_K_M via llama.cpp, then evaluate all models (both FP16 and Q4) on a 100‑question human‑written test set using Qwen2.5‑14B as an LLM‑as‑a‑judge (0‑3 rubric). Metrics include average score, perfect‑score rate, inference time, and model size.

## Key Results
- Optimal training scale: 4,000 samples minimizes test NLL; larger sets cause overfitting.
- Base model ranking: Swallow-8B and ELYZA-JP-8B (Japanese-continual pre-trained) outperform Qwen2.5-7B (multilingual GQA); Tanuki-8B performs moderately.
- Quantization impact: Llama‑3 models (Swallow, ELYZA) gain +0.01–0.03 points under Q4_K_M; Qwen2.5‑7B drops ~0.28 points. Production recommendation: Swallow-8B Q4_K_M yields 2.83/3 score, 8.9 s/question, 4.9 GB.

## Why This Works (Mechanism)
- **Scale learning via test NLL** avoids overfitting by selecting the dataset size where generalization improves, not just training loss. The NLL U‑curve indicates the sweet spot before the model memorizes.
- **Japanese-continual pre‑training** aligns tokenization and embeddings with the target domain/language, making LoRA adaptation more effective than starting from a multilingual base that lacks focused Japanese coverage.
- **Quantization‑architecture interaction**: GQA models like Qwen2.5 have grouped query attention that is sensitive to low‑bit quantization, causing significant accuracy loss. Llama‑3’s standard MHA is more robust to Q4_K_M, even showing slight gains possibly due to noise regularization.

## Foundational Learning
**QLoRA (Quantized LoRA)** – Why needed: Enables fine‑tuning large models on consumer GPUs by freezing 4‑bit base weights and training low‑rank adapters. Quick check: Verify that only ~0.1% parameters are trainable and memory usage fits GPU.

**Progressive Scale Selection** – Why needed: Determines minimal effective data to avoid overfitting and wasted annotation. Quick check: Plot test NLL vs. training set size; look for a minimum before NLL rises.

**LLM‑as‑Judgment** – Why needed: Provides automated, human‑like evaluation of open‑ended answers at scale. Quick check: Run judge on a few known good/bad responses to ensure rubric alignment; set temperature=0 for reproducibility.

**Quantization Formats (GGUF Q4_K_M)** – Why needed: Reduces model size and speeds inference on CPUs. Quick check: Compare model file size and inference speed; ensure no crash in llama.cpp.

**Architecture Awareness (GQA vs. MHA)** – Why needed: Quantization behaves differently across attention mechanisms. Quick check: Inspect model config (e.g., `config.num_key_value_heads`) to detect GQA before quantization.

**Technical Domain Data Construction** – Why needed: Domain QA pairs must be accurate and balanced; otherwise, model learns spurious patterns. Quick check: Spot‑check samples for correctness and category distribution.

## Architecture Onboarding
Component map: Raw Text → Knowledge Graph (Neo4j) → Question–Answer Pair Generator → Balanced Dataset → QLoRA Trainer (LoRA + 4‑bit Base) → Merged FP16 Checkpoint → GGUF Converter → Quantizer (Q4_K_M) → Ollama Deployment → Qwen2.5‑14B Judge.

Critical path: 1) Build dataset (graph extraction, LLM augmentation, deduplication, rebalancing). 2) Determine optimal training scale (Stage 1). 3) Fine‑tune candidate base models (Stage 2). 4) Quantize and re‑evaluate (Stage 3). The scale selection and base‑model comparison are sequential; quantization can be applied after any checkpoint.

Design tradeoffs:
- Data size: More data improves coverage but risks overfitting and higher annotation cost. Optimal n balances both.
- Base model: Japanese‑continual pre‑training gives domain relevance but may lack general knowledge; multilingual GQA offers breadth but is more quantization‑sensitive.
- Quantization: Lower bits (Q4) reduce size and speed up inference but may harm accuracy; architecture choice dictates tolerance.

Failure signatures:
- No U‑curve in Stage 1 NLL → data quality issue or learning rate mis‑config.
- Qwen2.5‑7B does not degrade with Q4 → may be using a different architecture or quantization not applied correctly.
- Tanuki‑8B fails to convert to GGUF → tokenizer incompatibility; fallback to 4‑bit HF inference.
- Judge scores extremely high (>2.9) for all models → rubric too lenient; check prompt.

First three experiments:
1. **Scale experiment**: Train Swallow‑8B on 1k, 2k, 3k, 4k, 5k subsets; compute test NLL; select n with lowest NLL.
2. **Base‑model comparison**: Using the chosen n, fine‑tune Swallow‑8B, ELYZA‑JP‑8B, Qwen2.5‑7B, Tanuki‑8B with LoRA (r=32); evaluate FP16 checkpoints on the 100‑question test set via Qwen2.5‑14B judge.
3. **Quantization analysis**: Convert each FP16 checkpoint to GGUF Q4_K_M; repeat evaluation; compare score deltas, inference time, and model size.

## Limitations
- The exact QA dataset generation (Neo4j schema, augmentation LLM, deduplication) is unreleased, preventing faithful reconstruction of the 5,578‑sample corpus.
- The test set of 100 human‑written questions is not public; all reported scores are tied to this oracle set.
- Evaluation relies on a single LLM‑as‑judge (Qwen2.5‑14B) without reproducibility details (prompt, temperature), introducing stochasticity and potential bias.
- Model version identifiers (specific HuggingFace repos/commits) are not provided, risking subtle performance differences.

## Next Checks
1. **Scale replication with varied data**: Using a different Japanese technical QA dataset, rerun the scale experiment on Swallow‑8B to see if the optimal n remains near 4,000 or if the NLL curve shape changes.
2. **GQA degradation stress test**: Quantize Qwen2.5‑7B with alternative low‑bit methods (e.g., GGUF Q6_K, GPTQ 4‑bit) and on a held‑out subset of the paper's categories to confirm whether the score drop is specific to Q4_K_M or general to low‑bit quantization for GQA.
3. **Judge ablation study**: Re‑evaluate the same model outputs (F16 and Q4) using a different judge (e.g., GPT‑4o with a manually crafted rubric) and with multiple random seeds per question to measure variance and correlation with the reported scores.
