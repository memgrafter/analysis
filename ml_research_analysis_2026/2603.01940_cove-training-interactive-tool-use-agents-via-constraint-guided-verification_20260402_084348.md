# CoVe: Training Interactive Tool-Use Agents via Constraint-Guided Verification
## Quick Facts
- arXiv ID: 2603.01940
- Source URL: https://arxiv.org/abs/2603.01940
- Reference count: 7
- Primary result: CoVe-4B (4B parameters) achieves 43.0% pass1 on τ²-bench Airline and 59.4% on Retail, matching or exceeding much larger models; a 5K CoVe dataset outperforms a 90K prior dataset.

## Executive Summary
Training interactive tool-use agents that handle ambiguous user queries requires large-scale, high-quality training data with guaranteed correctness. CoVe addresses this by synthesizing verifiably correct trajectories through constraint-guided verification. It samples explicit task constraints from a sandbox database, fuzzifies them into complex ambiguous user queries, and uses a rule-based verifier to check outcomes. This yields perfect trajectories for supervised fine-tuning (SFT) and precise reward signals for reinforcement learning (RL). On the τ²-bench benchmark, CoVe-4B achieves state-of-the-art results for its scale, demonstrating superior data efficiency.

## Method Summary
CoVe is a post-training data synthesis framework. It starts by sampling a set of deterministic task constraints (e.g., “cancel order #X”) from a sandbox database, ensuring solvability. These constraints are fuzzified into ambiguous natural language queries (e.g., “cancel my recent order containing a blue shirt”) while preserving a unique mapping to the original target. A user simulator (powered by a strong LLM) then interacts with the agent model, conducting multi-turn dialogue and revealing requirements gradually. After the trajectory completes, a deterministic verifier checks whether all constraints have been satisfied and penalizes redundant tool calls, outputting a score Sτ. For SFT, only trajectories with a perfect score (Sτ=1) are retained. For RL, the score serves as a reward signal. The training orchestrator then updates the agent model accordingly, either via standard fine-tuning (AdamW, lr=1e-6) or with RL (GRPO).

## Key Results
- CoVe-4B yields 43.0% (Airline) and 59.4% (Retail) pass1 success rates on τ²-bench, significantly outperforming similar-scale baselines and competing with models up to 17× larger.
- A 5K CoVe SFT dataset surpasses a 90K dataset from prior work (Simia) in data efficiency.
- The framework, model weights, and 12K trajectories are open-sourced, enabling reproducibility.

## Why This Works (Mechanism)
### Dual-Role Constraints for Solvable Complexity and Ground-Truth Verification
Constraints sampled directly from the sandbox database guarantee that at least one correct execution path exists. The same constraint set later acts as a deterministic verifier, checking the agent’s final tool invocation history against required outcomes rather than a prescribed sequence. This dual use ensures both solvable tasks and objective evaluation. Core assumption: fuzzified expressions uniquely map to constraint elements. Break condition: if fuzzification yields ambiguous expressions that map to multiple entities, verification becomes non-deterministic.

### Constraint Fuzzification to Elicit Multi-Turn Ambiguity
Fuzzification transforms precise identifiers into attribute-based descriptions, forcing agents to disambiguate through dialogue and database queries, mirroring real-world interactions where users lack exact IDs. The uniqueness check ensures the fuzzified description still resolves to a single target. Evidence includes detailed fuzzification strategies in Section 4.2. Break condition: uniqueness check failure makes the task unsolvable.

### Deterministic Verifier as a Filter and Reward Signal
The rule-based verifier V(τ, C) assigns a score based on constraint satisfaction (mandatory) and redundant action penalties. For SFT it filters trajectories (keep only Sτ=1); for RL it provides a continuous, hallucination-free reward signal. Core assumption: the verifier’s rules accurately encode domain success criteria. Break condition: misalignment with the benchmark’s hidden success criteria yields incorrect training signals.

## Architecture Onboarding
**Component map:**  
Constraint Sampler -> Fuzzifier -> User Simulator LLM -> Agent Model -> Deterministic Verifier -> Training Orchestrator (with teacher agent for SFT, student agent for RL).

**Critical path:** Constraint Sampling -> Fuzzification -> User Simulator Interaction -> Trajectory Verification -> (Filter for SFT / Reward for RL) -> Model Update.

**Design tradeoffs:**
- Simulator capability vs. cost/scale: stronger simulators (e.g., Gemini-3-Pro) yield higher-quality, more unique trajectories but are expensive; weaker simulators cause an environment bottleneck, especially for RL.
- SFT stability vs. RL adaptability: pure SFT on high-quality filtered data performs best; sequential SFT+RL degrades due to distribution shift from weaker online simulators.
- Constraint complexity vs. simulator graceful failure: harder tasks increase difficulty but raise the risk that less capable simulators will terminate prematurely, reducing data yield.

**Failure signatures:**
- Simulator premature termination: Simulator outputs ###STOP### before all constraints are satisfied.
- Redundant or unfinished tool calls: Verifier detects tool calls not mapped to any constraint or missing required outcomes.
- Fuzzification mapping failure: Fuzzified description fails the uniqueness check, making the task unsolvable.

**First 3 experiments:**
1. Validate fuzzification uniqueness: Programmatically query the sandbox DB for a large sample of fuzzified queries to ensure each uniquely identifies one target; report failure rate.
2. Isolate data quality effect: Fine-tune the same base model (Qwen3-4B-Instruct) on CoVe-5K, Simia-5K, and Simia-90K; expect CoVe-5K to outperform Simia-5K and match/exceed Simia-90K, demonstrating verifiable correctness over volume.
3. Test simulator impact on yield & quality: Generate SFT datasets using different user simulators (e.g., Qwen3-235B, Gemini-1.5-Pro, GPT-4o). Compare yield ratio (Sτ=1 / total), dialogue diversity (entropy), and downstream pass1 of a fixed 4B model trained on each subset.

## Limitations
- Generalizability: Evaluation is limited to τ²-bench (Airline/Retail); performance on other tool ecosystems (e.g., web navigation, coding) is unknown.
- Simulator dependency: Data quality and yield depend heavily on a strong teacher simulator (Gemini-3-Pro), introducing an environment bottleneck when scaling to RL.
- Real-world ambiguity: The fuzzification strategy assumes unique attribute-to-entity mappings; actual user queries may involve ambiguous or composite references not captured by the uniqueness check.

## Confidence
