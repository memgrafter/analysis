# Beyond Static Pipelines: Learning Dynamic Workflows for Text-to-SQL
## Quick Facts
- **arXiv ID**: 2602.15564
- **Source URL**: https://arxiv.org/abs/2602.15564
- **Reference count**: 40
- **Primary result**: SquRL dynamically constructs workflow pipelines from modular actors, consistently surpassing static baselines on Spider, BIRD, and SynSQL (e.g., 86.27% vs 84.30% on Spider-Dev).

## Executive Summary
Text-to-SQL systems typically rely on fixed pipelines that cannot adapt to query heterogeneity. This paper introduces SquRL, a reinforcement learning framework that dynamically constructs workflows from a pool of modular actors at inference time. SquRL first undergoes supervised fine-tuning to learn valid workflow structures, then refines its policy via RL with rule-based rewards, dynamic actor masking, and pseudo rewards for efficient exploration. Experiments on Spider, BIRD, and SynSQL show SquRL consistently outperforms the best static workflows, with particularly strong gains on complex queries (e.g., 86.27% vs 84.30% on Spider-Dev). An oracle analysis confirms dynamic selection achieves a theoretical upper bound of 81.5% accuracy with reduced runtime, demonstrating the fundamental advantage of adaptive workflows over static pipelines.

## Method Summary
SquRL operates in two stages. First, supervised fine-tuning converts standard Text-to-SQL datasets into workflow-level supervision by exhaustively searching a template library for a combination of actors that reproduces the gold SQL execution. The model is trained to mimic the first successful workflow for each query, ensuring the generated structures are executable. Second, reinforcement learning with GRPO refines the policy using a composite reward function (format, timeout, execution, result, time) and two efficiency mechanisms: dynamic actor masking (randomly dropping actors during rollouts) and pseudo rewards (LLM‑based pairwise comparisons that sometimes replace execution feedback). At inference, the policy samples multiple workflows and returns the majority vote.

## Key Results
- SquRL‑7B achieves 86.27% execution accuracy on Spider‑Dev, beating the best static workflow (84.30%).
- On SynSQL highly complex queries, SquRL reaches 46.51% vs 38.54% for the static baseline.
- Oracle analysis yields a theoretical upper bound of 81.5% accuracy with reduced runtime, confirming the advantage of dynamic selection.

## Why This Works (Mechanism)
### Mechanism 1: Supervised Fine‑Tuning for Valid Structures
- **Claim**: Supervised fine‑tuning teaches the policy to generate valid workflow structures, ensuring dynamically constructed workflows are executable.
- **Mechanism**: Transform standard Text‑to‑SQL datasets into workflow‑level supervision by systematically searching for a template‑actor combination that reproduces correct SQL execution; train the model to mimic the first successful workflow for each query.
- **Core assumption**: Most queries admit at least one correct workflow composed from available actors; simpler templates often suffice and can be discovered automatically.
- **Evidence anchors**: [abstract] "SquRL uses supervised fine‑tuning to learn valid structures"; [section] "4.1: The goal of supervised fine‑tuning is to teach the model to generate valid workflow structures... we construct supervised training data by transforming standard Text‑to‑SQL datasets into workflow‑level supervision".
- **Break condition**: If the template space is too restrictive or greedy selection biases toward overly simple workflows, SFT may fail to cover complex patterns, leading to invalid rollouts during RL.

### Mechanism 2: Reinforcement Learning with Multi‑Aspect Reward
- **Claim**: RL with a rule‑based multi‑aspect reward optimizes workflow selection for both accuracy and efficiency using execution feedback.
- **Mechanism**: Define reward components (format, timeout, execution, result, time) applied sequentially; use GRPO to update the policy with normalized advantages within sampled groups.
- **Core assumption**: Execution feedback can be decomposed into interpretable signals that guide the policy toward better trade‑offs; on‑policy RL can effectively search the combinatorial workflow space.
- **Evidence anchors**: [abstract] "RL with rule‑based rewards"; [section] "4.2.1: We design a rule‑based reward function... five aspects... GRPO computes advantages via group‑wise reward normalization".
- **Break condition**: Mis‑specified reward weights may bias toward speed over accuracy; noisy execution (e.g., flaky databases) can mislead RL.

### Mechanism 3: Dynamic Actor Masking and Pseudo Rewards
- **Claim**: Dynamic actor masking and pseudo rewards ensure robust exploration and training efficiency in the large action space of workflow construction.
- **Mechanism**: Randomly mask actors with retention rate *r* during rollouts to force alternative compositions; with probability *p* replace real execution reward with LLM‑based pairwise comparison reward.
- **Core assumption**: Explicit exploration incentives are necessary to avoid collapse to a few high‑reward workflows; LLM judgments can serve as dense, low‑cost reward proxies.
- **Evidence anchors**: [abstract] "dynamic actor masking to encourage broader exploration, and pseudo rewards to improve training efficiency"; [section] "4.2.2: dynamic actor masking... forces the model to explore alternative workflow compositions" and "4.2.3: pseudo reward mechanism... replaces execution‑based feedback with LLM‑based evaluations".
- **Break condition**: Masking rate too low (<0.3) eliminates valid workflows; too high (>0.9) reduces exploration. Pseudo‑reward noise above *p*=0.2 degrades performance (ablation in Table 4).

## Architecture Onboarding
### Component map (plain text)
Actor Pool + Template Library -> SFT Pipeline -> Initial Policy πθ -> RL Trainer (with Dynamic Masking Controller & Reward Engine) -> Updated πθ (loop back) -> Evaluation Sandbox (for dev/test) -> Majority Vote Output.

### Critical path
1. Define actor implementations and templates; validate each template can be instantiated.
2. Build SFT dataset: for each training query, iterate templates until a correct workflow is found; store the workflow.
3. Fine‑tune base LLM on SFT data to get πθ_initial.
4. Initialize RL with πθ_initial; set hyperparameters (G, β, r, p).
5. For each RL iteration:
   a. Sample batch of queries.
   b. For each query, generate binary mask *m* by retaining each actor with prob *r*.
   c. Generate *G* workflows per query using πθ_old constrained to actors with *m*=1.
   d. For each workflow: with prob *p* compute pseudo reward via LLM judge; else execute and compute rule‑based reward.
   e. Normalize rewards within group, compute advantages *A_i*, update πθ with GRPO objective.
6. Validate on dev set after *N* steps; adjust *r/p* if format errors or reward variance abnormal.
7. Save best checkpoint.

### Design tradeoffs
- **SFT vs RL**: SFT ensures valid outputs but may bias toward simplicity; RL refines but requires careful reward shaping and many samples.
- **Reward granularity**: More aspects improve guidance but increase tuning complexity; over‑weighting time may sacrifice accuracy.
- **Exploration (masking) vs validity**: Lower *r* increases exploration but may yield no valid workflow; higher *r* maintains validity but risks policy collapse.
- **Pseudo‑reward ratio *p***: Higher *p* reduces compute cost but introduces LLM bias; optimal *p* balances noise and efficiency (empirically ~0.1).

### Failure signatures
- Persistent >5% format errors: policy generates malformed workflows; increase format reward weight or improve SFT data diversity.
- Near‑zero reward variance: all rollouts yield similar scores; policy not learning. Increase dynamic masking (lower *r*) or adjust KL penalty β.
- Pseudo‑reward correlation with real reward <0.3: LLM judge inconsistent; reduce *p* or enhance judging prompt.
- Training instability (loss spikes): likely due to large advantage outliers; consider reward clipping or smaller learning rate.

### First 3 experiments
1. **SFT Coverage Test**: For 500 random training queries, perform exhaustive template search (up to 3 actors) to compute the fraction that have at least one correct workflow. If <90%, expand templates/actors.
2. **Dynamic Masking Sweep**: Train models with *r* ∈ {0.1, 0.3, 0.5, 0.7, 1.0} while keeping other hyperparams fixed; compare final EX and format error. Expect peak around *r*=0.5.
3. **Pseudo Reward Noise Calibration**: Run RL with *p* ∈ {0, 0.05, 0.1, 0.2, 0.3} and measure final EX and training steps. Expect optimal *p* near 0.1; higher *p* degrades due to noise.

## Open Questions the Paper Calls Out
1. **Generalization to Novel Schemas/Domains**: How does SquRL's dynamic policy generalize to entirely novel database schemas or domains not encountered during training? The paper focuses on established benchmarks; testing on held‑out domains (e.g., healthcare, legal) is needed to assess zero‑shot adaptation.
2. **Reward Design's Role in Efficiency‑Accuracy Trade‑offs**: What specific aspects of the reward design (rule‑based vs. pseudo) most effectively shape the learned policy's preference for efficiency versus accuracy, and how stable is this preference across query difficulties? The interaction between reward components is not isolated.
3. **Impact of Dynamic Actor Masking on Discovery of Novel Workflows**: To what extent does dynamic actor masking prevent overfitting to a small subset of high‑reward workflows, and does it encourage the discovery of genuinely novel, high‑performing workflow compositions absent from SFT data? The paper shows robustness but does not quantify workflow diversity.
4. **Backend Model's Ceiling Effect**: How does the choice and capability of the frozen backend model limit the ceiling of SquRL's learned policy, particularly for complex queries? The policy may co‑adapt to a specific backend's failure modes, harming transferability.
5. **Theoretical Gap When Expanding Workflow Space**: Does the theoretical performance gap between dynamic and static workflows hold when the dynamic policy must also generate new, previously undefined workflows? Current theory assumes a fixed workflow set; SquRL composes new structures from actors, potentially widening the gap.

## Limitations
- Incomplete reporting of key implementation details (actor specifications, hyperparameters, data splits) blocks faithful replication.
- Results lack statistical validation (error bars, significance tests), undermining confidence in reported gains.
- Oracle analysis methodology and computational overhead are not thoroughly characterized; external validation is limited (low citation count).

## Confidence
- SquRL achieves superior execution accuracy on standard benchmarks: **Medium**
- The combination of SFT, RL, dynamic masking, and pseudo rewards is effective: **Medium**
- The oracle analysis suggests a significant theoretical gap favoring dynamic workflows: **Medium**

## Next Checks
1. **Ablation study**: Systematically remove each RL component (dynamic masking, pseudo rewards, individual reward terms) to measure isolated impact on execution accuracy and training stability.
2. **Efficiency profiling**: Measure wall‑clock time and monetary cost (API calls, compute) of SquRL vs. the best static pipeline across query complexity levels; report trade‑offs.
3. **Out‑of‑distribution test**: Evaluate on a held‑out domain (e.g., scientific databases) absent from Spider/BIRD/SynSQL to assess whether dynamic adaptation genuinely improves robustness to schema/query shifts.
