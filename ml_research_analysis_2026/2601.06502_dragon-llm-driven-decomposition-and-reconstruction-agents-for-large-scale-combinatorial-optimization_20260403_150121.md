# DRAGON: LLM-Driven Decomposition and Reconstruction Agents for Large-Scale Combinatorial Optimization

## Quick Facts
- **arXiv ID:** 2601.06502
- **Source URL:** https://arxiv.org/abs/2601.06502
- **Reference count:** 40
- **Primary result:** DRAGON scales LLM-based combinatorial optimization to large instances via iterative decomposition-reconstruction, achieving feasible solutions on TSPLIB/CVRPLIB/Weibull-5k and a 0.16% optimality gap on MKP with >3M variables.

## Executive Summary
DRAGON introduces a novel framework to overcome the context-length limitations of large language models (LLMs) when solving combinatorial optimization problems (COPs). Traditional LLM-based solvers struggle with large instances due to token limits and reasoning complexity. DRAGON addresses this by iteratively decomposing the problem into smaller subproblems, each optimized by an LLM agent, and reintegrating improvements into a global solution. This decomposition-reconstruction cycle enables handling of instances far beyond the typical scale of direct LLM prompting.

Empirical results on standard benchmarks (TSPLIB, CVRPLIB, Weibull-5k) show that DRAGON consistently produces feasible solutions where prior LLM methods fail. On multiple knapsack problems with over three million variables, it achieves an optimality gap of just 0.16%. Ablation studies confirm the efficacy of using LLMs for both decomposition and reconstruction, highlighting the synergistic design of the multi-agent system.

## Method Summary
DRAGON is an iterative Large Neighborhood Search framework that uses LLMs to solve large-scale combinatorial optimization problems. Given problem metadata `M` (structured JSON) and an initial solution `S` (from a fast heuristic), the Decomposer agent selects an active segment of `S` with high optimization potential and a static remainder. The Compressor then creates a compressed subproblem `(M', S', C)` containing only active elements and boundary constraints derived from the static part. The Reconstructor agent solves this subproblem via LLM prompting, aided by an experience storage that records infeasible attempts and their violation reasons to guide revision. Feasible improvements are accepted probabilistically (simulated annealing) and reintegrated into `S`. The cycle repeats until a time limit or stagnation. The framework supports TSP, CVRP, BPP, and MKP, with explicit constraint integration into prompts and fast heuristics for initialization.

## Key Results
- DRAGON consistently produces feasible solutions for large TSP, CVRP, and bin packing benchmarks where prior LLM solvers fail.
- On multiple knapsack problems with over 3 million variables, it achieves a 0.16% optimality gap.
- Ablation studies confirm that using LLMs for both decomposition and reconstruction is essential to performance.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** An LLM agent can autonomously identify sub-regions of a solution with high improvement potential for targeted refinement.
- **Mechanism:** The decomposition agent `D` analyzes the current global solution `𝑆` and problem metadata `𝑀` to partition the solution into *active segments* (candidates for improvement) and *static segments* (fixed during the iteration). This isolates a manageable subproblem while preserving global feasibility through boundary constraints.
- **Core assumption:** LLMs possess sufficient semantic and structural reasoning to detect inefficient tour segments (e.g., crossing edges in TSP) or poorly packed items without explicit algorithmic rules.
- **Evidence anchors:**
  - [abstract] "autonomously identifies regions in initial solution with high optimization potential and strategically decompose large-scale COPs into manageable subproblems."
  - [section 3.2] Formalizes decomposition as `(a_i, s_i) = D(𝑀, 𝑆_i)` and describes the identification of active segments with improvement potential.
  - [corpus] *Weak evidence*: Neighbors focus on GNNs or unified frameworks; no direct evidence for LLM-driven decomposition detection.
- **Break condition:** If the active segment is too small or misidentified (e.g., removing already optimal edges), reconstruction yields no improvement or infeasibility.

### Mechanism 2
- **Claim:** Compressing active segments with boundary constraints into a local subproblem preserves global feasibility while reducing context length.
- **Mechanism:** The `Compress` step takes active `a_i` and static `s_i` segments, extracts only relevant metadata `𝑀'_i`, and encodes constraints `𝐶_i` (e.g., required edge sequences for routing, aggregated items for packing) to ensure the local solution can be reintegrated.
- **Core assumption:** A constrained local subproblem, when solved optimally, can be stitched back into the global solution without violating original problem constraints.
- **Evidence anchors:**
  - [section 3.2] "`(𝑀'_i, 𝑆'_i, 𝐶_i) = Compress(𝑀, a_i, s_i)` ... significantly reduces the size of the local data `|𝑀'_i| << |𝑀|`."
  - [section 3.3] "Constraints `𝐶_i` are explicitly integrated into natural language within the LLM prompt."
- **Break condition:** Incorrect constraint formulation (e.g., mis-aggregating demands in CVRP) leads to reintegration failures or infeasible global tours.

### Mechanism 3
- **Claim:** Iterative reconstruction with experience storage enables constraint-compliant local optimization even for non-trivial subproblems.
- **Mechanism:** The reconstructor `R` solves the compressed instance using LLM prompting. Infeasible proposals are stored with violation reasons; subsequent prompts append these to guide revision toward feasibility, as shown in Figure 3.
- **Core assumption:** LLMs can learn from textual feedback on constraint violations to gradually produce feasible solutions for constrained subproblems.
- **Evidence anchors:**
  - [section 3.3] "The agent’s experience storage records all previous attempts, regardless of whether they result in feasible solutions or not, along with annotations on the type and cause of any constraint violations."
  - [section 4.1.4] Describes storing infeasible solutions with comments to avoid repeated errors.
- **Break condition:** If constraints are too complex or the LLM cannot interpret feedback (e.g., subtle capacity overflows), the agent may cycle through infeasible solutions indefinitely.

- **Concept: Prompt Engineering for LLMs**
  - *Why needed here:* Decomposition and reconstruction rely on structured natural language prompts (Figures 2b-c, Appendix A) to extract node indices and generate feasible XML/JSON solutions. Poor prompt design yields irrelevant segments or infeasible reconstructions.
  - *Quick check question:* What prompt elements enforce that a reconstructed CVRP route starts and ends at the depot while respecting fixed sub-tours?

## Architecture Onboarding
- **Component map:** Metadata `𝑀` → Decomposer `D` → (active `a_i`, static `s_i`) → Compressor → (`𝑀'_i`, `𝑆'_i`, `𝐶_i`) → Reconstructor `R` (with experience storage) → improved `𝑆'_new` → Integrator → Global `𝑆` update.
- **Critical path:**
  1. Initialize `𝑆` with a fast heuristic (e.g., Nearest Neighbor).
  2. `D` identifies active nodes (e.g., `{4,6,7,8}` in Figure 1).
  3. `Compress` builds local instance with constraints from static segments.
  4. `R` generates new local solution, revising based on stored failures.
  5. If `Accept` passes (probabilistic improvement), `Integration` updates global `𝑆`.
  6. Repeat until time limit or 5 non-improving iterations.
- **Design tradeoffs:**
  - Decomposition granularity: Smaller subproblems reduce LLM complexity but may miss larger structural improvements; larger ones risk exceeding context limits.
  - Solver choice for reconstruction: LLM-only (`LLM×LLM`) is flexible but may struggle with tight constraints; exact solver (`Solver`) guarantees optimal local solutions but requires manual constraint encoding.
  - Experience storage size: More history improves revision but increases prompt length and cost.
- **Failure signatures:**
  - Infeasible global solution after reintegration: Likely due to incorrect `Compress` constraints (e.g., mis-summed demands).
  - No improvement over iterations: Decomposer may select unproductive segments; consider randomizing active selection or diversifying prompts.
  - API errors or timeouts: Input tokens exceed LLM context (check `Input tokens (k)` in logs); reduce `NUM` (max active nodes) or split into more iterations.
- **First 3 experiments:**
  1. **Sanity check on tiny TSP:** Run `berlin52` with `gpt-4o`; verify decomposer selects a non-trivial segment (e.g., `4,6,7,8`) and reconstructor shortens tour. Confirm feasibility by checking all nodes visited exactly once.
  2. **Constraint stress test on MKP:** Use `mkp_393_5`; ensure reconstructor respects knapsack capacities. Inspect `<reason>` tags in experience storage for capacity violations.
  3. **Scalability probe:** Compare `Input tokens` for `d2103` vs. `brd14051`. If tokens spike >64k for DeepSeek `r1`, switch to `gpt-4.1` or reduce active segment size.

## Open Questions the Paper Calls Out
1. **Robust decomposition:** How can decomposition be made robust to segmentation and prompt choices? The paper explicitly states a need for more robust and adaptive decomposition mechanisms (Sec. 4.5) because current handcrafted decomposition is sensitive and yields suboptimal segments. Evidence would be a method that performs consistently across varied segment sizes and prompts.
2. **Reducing computational overhead:** How can the computational overhead of the iterative cycle be reduced? The iterative nature of DRAGON introduces substantial overhead and extended runtime (Sec. 4.5), especially for medium-scale instances. Evidence: a redesign that lowers token usage while preserving solution quality on medium-scale benchmarks.
3. **Automatic integration of external solvers:** Can external solvers be automatically integrated into decomposition and reconstruction? The paper suggests integrating external tools to automatically model customized constraints (Sec. 4.5), as current manual encoding demands domain expertise. Evidence: an auto-modeling framework that ingests metadata and generates valid subproblems for OR-Tools across various COPs.
4. **Central coordination agent:** Does a central coordination agent improve efficiency and consistency of multi-agent interaction? The paper envisions introducing a central coordinator to manage interactions (Sec. 4.5), as implicit state passing may cause redundancy and inconsistent solutions. Evidence: implementing a coordinator with clear protocols that demonstrates faster convergence and higher solution quality compared to the original pipeline.

## Limitations
- **LLM hyperparameters:** Undisclosed temperature, max_tokens, and other API settings risk irreproducible agent behavior.
- **Experience storage mechanics:** Vague specification of how infeasible solutions are annotated, retrieved, and integrated into prompts.
- **Prompt sensitivity:** Performance likely hinges on unpublished prompt templates (Appendix A), with no robustness analysis provided.

## Confidence
- **Scalability claims:** Medium – Strong empirical results on large instances, but replication is hindered by missing implementation details.
- **Decomposition mechanism:** Low – Relies on LLM semantic reasoning without independent verification; weak neighbor evidence.
- **Reconstruction with experience:** Medium – Iterative revision is described, but storage/retrieval implementation is unspecified.
