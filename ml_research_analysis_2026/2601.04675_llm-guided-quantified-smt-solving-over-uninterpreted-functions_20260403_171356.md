# LLM-Guided Quantified SMT Solving over Uninterpreted Functions

## Quick Facts
- **arXiv ID:** 2601.04675
- **Source URL:** https://arxiv.org/abs/2601.04675
- **Reference count:** 9
- **Primary result:** AquaForte increases solved quantified SMT instances with uninterpreted functions by 80.0% (Z3) and 183.6% (CVC5) under 24-second timeouts, with strongest gains on satisfiable formulas.

## Executive Summary
AquaForte is a framework that uses large language models (LLMs) to generate semantically meaningful concrete instantiations for uninterpreted functions (UFs) in quantified SMT problems over non-linear arithmetic (QUFNIRA). Traditional instantiation methods like E-matching and MBQI suffer from "semantic blindness" because they treat UFs as uninterpreted symbols without inferring mathematical meaning. AquaForte addresses this by prompting LLMs to hypothesize UF definitions (e.g., algebraic expressions) that satisfy local constraints. The system preprocesses formulas via constraint separation to break them into independent components, then iteratively applies LLM-suggested instantiations, validating each with an SMT solver and learning exclusion clauses from UNSAT results. Soundness is preserved by relying on the solver's final decision, and completeness is ensured by falling back to the base solver with learned clauses. On 1,481 benchmarks, AquaForte yields substantial improvements, particularly on satisfiable instances.

## Method Summary
AquaForte integrates with existing SMT solvers (Z3 v4.15.0, CVC5 v1.2.1) as a post-processing layer. It takes SMT-LIB quantified formulas with UFs in non-linear arithmetic. First, formulas are rewritten and decomposed into independent constraint components using a union-find structure on shared UFs. For each component, a structured prompt (`⟨instruction, data, format, tips⟩`) queries an LLM (GPT-4.1, DeepSeek-V3, Claude-4-Sonnet) for a concrete UF definition (SMT-LIB syntax) and an instantiation trigger. The LLM response is parsed and validated. The instantiation is applied to the original formula, and a bounded SMT solve is attempted. If SAT, the original problem is solved. If UNSAT, the negation of the instantiation (`¬(f = def)`) is recorded as a learned exclusion clause, and the LLM is re-queried with history. After a fixed iteration budget (N=10) or timeout, the base solver is called on the original formula augmented with all exclusions. Experimental setup: prepare benchmarks (SMT-COMP UFNIRA/UFLRA plus SOS and MFD datasets), run with 24s per-instance timeout, and measure solver time excluding LLM latency.

## Key Results
- Solved instances increased by 80.0% for Z3 and 183.6% for CVC5 over 24-second timeouts across 1,481 benchmarks.
- Asymmetric gains: ~3.6× improvement on SAT instances but minimal on UNSAT ones.
- Most improvement came from the first LLM iteration, with diminishing returns after 5–7 iterations.

## Why This Works (Mechanism)
### Mechanism 1: Constraint Separation
- **Claim:** Decomposes the formula into smaller, semi-independent subproblems to reduce complexity of UF instantiation.
- **Mechanism:** A union-find structure groups constraints sharing UFs. Each connected component is processed separately, focusing LLM and solver on a smaller set of co-dependent functions. This transforms a global O(|F|²) challenge into manageable per-component subproblems.
- **Core assumption:** Constraints on different UF sets are largely independent; solving components separately and merging preserves global satisfiability.
- **Evidence anchors:** [abstract] "preprocesses formulas through constraint separation"; [section] Algorithm 1 details union-find grouping and component extraction.
- **Break condition:** Constraint graph fully connected (all UFs in one component) eliminates decomposition benefits.

### Mechanism 2: LLM-Generated Semantic Instantiations
- **Claim:** LLMs generate semantically grounded, concrete definitions for UFs, converting abstract symbols into mathematically coherent expressions that satisfy local constraints.
- **Mechanism:** Structured prompts (instruction, data, format, tips) prime the LLM to infer intended mathematical meaning (e.g., `f(x)=2x`) from constraint context. Output is a valid SMT-LIB definition replacing the UF symbol.
- **Core assumption:** LLMs possess sufficient mathematical intuition from training to hypothesize definitions consistent with a given constraint set.
- **Evidence anchors:** [abstract] "LLMs to provide semantic guidance for UF instantiation by generating instantiated candidates"; [section] "LLM Instantiation... materialize each uninterpreted function..."
- **Break condition:** LLM fails to generate syntactically valid or semantically consistent instantiation (handled by retry/post-processing).

### Mechanism 3: Adaptive Iterative Validation with Exclusion Learning
- **Claim:** Iterative validation with learned exclusion clauses maintains soundness and drives completeness, integrating probabilistic LLM output into a sound SMT loop.
- **Mechanism:** An LLM-suggested instantiation is applied. If SAT, original problem solved. If UNSAT, the negation `¬(f = def)` is recorded. Subsequent LLM queries include history to avoid repeating refuted interpretations. After N iterations, base solver receives original formula augmented with all learned exclusions.
- **Core assumption:** A UNSAT result from a *valid* instantiation implies the original quantified problem is also UNSAT under that materialization, making the exclusion clause sound. Fallback ensures at least base solver completeness.
- **Evidence anchors:** [abstract] "Soundness preserved through systematic validation... UNSAT results generate exclusion clauses"; [section] Algorithm 2 details iterative history tracking and fallback.
- **Break condition:** LLM repeatedly suggests instantiations that lead to timeout (neither conclusive), exhausting iteration budget without useful exclusions.

## Foundational Learning
- **Concept: Quantified SMT & Uninterpreted Functions (QUFNIRA)**
  - *Why needed:* Core problem domain. Understanding why quantification + UFs + non-linear arithmetic is undecidable and how instantiation is the practical approach.
  - *Quick check:* Explain why `∀x. f(x) > 0` is challenging for an SMT solver if `f` is uninterpreted and appears in arithmetic constraints.
- **Concept: E-matching & MBQI Instantiation**
  - *Why needed:* To contrast "semantic blindness." These are traditional syntactic methods. Need to grasp triggers, pattern matching, and model-based counterexample generation.
  - *Quick check:* Given `∀x. P(f(x))` with trigger `f(x)`, what ground terms cause an E-matching instantiation when `f(a)` appears in the context?
- **Concept: Prompt Engineering for Structured Output**
  - *Why needed:* LLM's utility hinges on generating correct, parseable SMT-LIB expressions. Understanding the `⟨S, D, O, T⟩` prompt structure is key to reliability.
  - *Quick check:* If the prompt's output format requires a JSON object with `"reasoning"` and `"definition"` keys, what happens if the LLM returns only a raw expression like `(define-fun f ((x Real)) Real (* 2 x))`?

## Architecture Onboarding
- **Component map:**
  Formula Preprocessor → Prompt Generator → LLM Client → Post-processor → Integration Engine → (iterative loop with fallback to base solver)
- **Critical path:**
  Input formula → Preprocessing (rewriting, constraint separation into components) → for each component: generate prompt → query LLM → post-process (extract, validate, merge instantiations) → apply instantiations with triggers → bounded SMT solve → if SAT, return SAT; if UNSAT, add exclusion clause and repeat → after N iterations, fallback to base solver with original formula + all learned exclusions.
- **Design tradeoffs:**
  - LLM latency vs. precision: Single fast call (N=1) vs. slower iterative refinement. Most gain from first call.
  - Fallback timing: When to stop LLM iteration and fallback? Tradeoff between LLM exploration cost and base solver's independent progress.
  - Trigger co-generation: LLM also suggests triggers. Risk of poor triggers misguiding solver even with good instantiations.
- **Failure signatures:**
  - LLM output invalid (JSON parse error, non-SMT-LIB syntax) → post-process retry loop.
  - Instantiation SAT but irrelevant (model violates original quantified formula) → exclusion generated but wastes iteration.
  - No improvement on UNSAT instances (paper notes minimal UNSAT gain) → overhead without helping base solver.
- **First 3 experiments:**
  1. Constraint separation sanity check: On simple formulas with separate UF groups, verify union-find produces expected components.
  2. Prompt validation: For a component with known simple definition, check if LLM returns correct SMT-LIB definition with high confidence and format adherence.
  3. Single-iteration baseline: Run AquaForte with N=1 and 24s timeout on subset of SMT-COMP UFNIRA; measure solved count vs. base solver; confirm ~80% (Z3)/~180% (CVC5) relative improvement on SAT.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Why do LLM-guided instantiations yield minimal gains on unsatisfiable (UNSAT) instances compared to substantial improvements on satisfiable (SAT) ones?
- **Basis in paper:** Discussion notes asymmetric performance: 3.6× improvement on SAT vs. minimal UNSAT gains, indicating LLMs excel at proposing satisfying instantiations but struggle with exhaustive unsatisfiability proofs.
- **Why unresolved:** Paper does not analyze fundamental reason—whether due to LLMs' inability to generate comprehensive impossibility proofs, solvers' difficulty in using LLM constraints to derive contradictions, or mismatch between LLM training and formal unsatisfiability reasoning.
- **What evidence would resolve:** Detailed error analysis categorizing UNSAT failure modes (e.g., LLM never proposes key instantiation vs. solver fails to refute), comparing against known unsatisfiable cores or certified proofs.

### Open Question 2
- **Question:** What specific aspects of prompt design (instruction clarity, example selection, output formatting) most effectively elicit mathematically sound instantiations for diverse UF constraint patterns?
- **Basis:** Methodology describes structured prompt template `⟨S_instruction, D_data, O_format, T_tips⟩` but no empirical ablation on prompt components.
- **Why unresolved:** Prompt engineering treated as settled without investigating sensitivity or optimal configurations across problem classes, limiting reproducibility and theoretical understanding.
- **What evidence would resolve:** Systematic experiments varying prompt components across benchmark subsets, measuring impact on instantiation validity, solver success rate, and LLM confidence calibration.

### Open Question 3
- **Question:** How well does AquaForte generalize beyond mathematically structured benchmarks (SMT-COMP UFNIRA/UFLRA, SOS, MFD) to real-world verification tasks where UFs model complex software/hardware abstractions?
- **Basis:** Evaluation uses mathematically-oriented datasets; Introduction mentions hybrid systems motivation but no evaluation on concrete verification case studies (e.g., SV-COMP, CHC-COMP).
- **Why unresolved:** Paradigm shift lacks validation on applications where UF semantics are implicit and domain-specific, not expressible as simple algebraic identities; performance may degrade if LLMs lack training on such domains.
- **What evidence would resolve:** Running on established verification benchmarks with UF-heavy tasks, comparing against base solvers and analyzing whether LLM instantiations capture necessary domain invariants.

### Open Question 4
- **Question:** Why does solver performance improvement plateau after 5-7 LLM iterations (Figure 3), and can this diminishing return be mitigated by smarter iteration strategies beyond simple historical exclusion?
- **Basis:** RQ3 shows diminishing gains after 5-7 iterations; Algorithm 2 uses basic exclusion clause from failed attempts.
- **Why unresolved:** Paper does not investigate whether plateau results from LLM repetition, solver saturation with learned clauses, or discovery of all "useful" instantiations; fallback is passive rather than adaptive.
- **What evidence would resolve:** Analyzing diversity and novelty of instantiations across iterations, correlating with solver progress; testing advanced iteration policies (e.g., clustering LLM outputs, active learning, dynamic timeout allocation).

### Open Question 5
- **Question:** When LLM-generated instantiations pass syntactic validation but lead to incorrect SAT/UNSAT outcomes, what are the primary semantic failure modes (e.g., over-constraining, under-constraining, misinterpreting quantifier scope)?
- **Basis:** Soundness relies on solver's final decision; paper does not report or analyze cases where LLM instantiation yields SAT for instantiated formula but violates original quantified formula, or UNSAT from spurious constraints.
- **Why unresolved:** Without examining solver counterexamples or proof artifacts for LLM-guided runs, the paper cannot guarantee LLM instantiations are semantically faithful beyond syntactic correctness; risks subtle soundness violations if bounded check misses errors.
- **What evidence would resolve:** Manually inspecting sample of "successful" SAT cases to verify model satisfies original quantified formula; using certified SMT solvers or proof checkers to ensure instantiation preserves equivalence; measuring frequency of spurious UNSAT from exclusion clauses.

## Limitations
- Prompt template and LLM configuration details undisclosed, hindering reproducibility and causing performance variance.
- LLM's ability to generate correct UF definitions for complex non-linear constraints remains unproven; success on simple cases may not generalize.
- Constraint separation's independence assumption can fail on heavily interconnected formulas, reducing decomposition benefits.

## Confidence
- Overall performance improvement (80% Z3, 183% CVC5): Medium (experimentally plausible but missing critical details).
- Constraint separation (Mechanism 1): Medium (algorithm clear, but isolated impact unmeasured).
- LLM-generated instantiations (Mechanism 2): Low (core assumption unverified, highly prompt-sensitive).
- Iterative validation (Mechanism 3): Medium (fallback sound, but effectiveness depends on LLM quality).
