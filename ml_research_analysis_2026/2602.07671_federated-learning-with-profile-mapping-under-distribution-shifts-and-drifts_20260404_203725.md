# Federated Learning with Profile Mapping under Distribution Shifts and Drifts

## Quick Facts
- **arXiv ID**: 2602.07671
- **Source URL**: https://arxiv.org/abs/2602.07671
- **Reference count**: 40
- **Primary result**: FEROMA dynamically aggregates client updates using similarity of privacy-preserving profiles, achieving up to 14.1 percentage point accuracy gains on MNIST and up to 12 on average across six benchmarks, with overhead comparable to FedAvg.

## Executive Summary
FEROMA is a novel federated learning framework that tackles the twin challenges of distribution shift across clients and temporal drift during training. It introduces compact, privacy-preserving client data profiles that enable the central server to compute similarity-based aggregation weights, dynamically adjusting the influence of each client’s update. This mechanism ensures that the global model remains robust to heterogeneous and evolving data landscapes. Moreover, at inference time, FEROMA assigns the most appropriate model (either a clustered shared model or a personalized one) to each client based solely on its profile, eliminating the need for retraining or prior cluster definitions.

Extensive evaluations on six benchmarks, including MNIST, demonstrate that FEROMA surpasses ten state-of-the-art federated learning methods, yielding accuracy improvements of up to 14.1 percentage points on MNIST and an average gain of 12 points across datasets. Despite the added functionality, FEROMA’s communication and computational overhead remain comparable to standard FedAvg. The approach scales efficiently to over 100 clients and exhibits strong resilience to four major types of distribution shift (P(X), P(Y), P(Y|X), P(X|Y)) as well as varying drift frequencies.

## Method Summary
FEROMA operates in a cyclic training process. Each client locally constructs a succinct profile of its current data distribution, designed to reveal no raw information (e.g., via hashed histograms or differential private summaries). These profiles are transmitted to the server at the beginning of a training cycle. The server maintains a database of profiles and periodically recomputes pairwise similarities (e.g., using cosine or Hellinger distance) between all clients. From these similarities, it derives aggregation weights that determine how much each client’s model update contributes to the global model in subsequent federated averaging rounds. The weight for a client is typically proportional to its similarity to a reference (e.g., the mean profile or the current test distribution) or to the similarities of others.

During a communication round, the server selects a random subset of clients, broadcasts the current global model, and receives local updates after a few epochs. It then aggregates these updates using the precomputed similarity weights, updates the global model, and sends it back to all clients. After training, the server uses the final set of client profiles to perform model assignment: for any new or existing client at test time, its profile is compared against the stored profiles; if sufficiently similar to a cluster of clients, the cluster’s model is assigned; otherwise, a personalized model (possibly the client’s own last local model) is provided. This adaptive selection balances the benefits of collaboration with the need for personalization, all without additional retraining.

## Key Results
- Achieves state-of-the-art performance, beating 10 baseline methods on six datasets, with maximum improvement of 14.1 pp on MNIST and average improvement of 12 pp.
- Maintains communication and computational overhead on par with FedAvg, while scaling efficiently beyond 100 clients.

## Why This Works
FEROMA works because it directly tackles the root cause of performance loss in non‑IID and drifting environments: the mismatch between client updates and the true target distribution. By representing each client with a privacy‑preserving profile that captures its data distribution, the system can measure similarity between clients in a shared embedding space. The server then biases the aggregation towards updates from clients that are more similar to the desired distribution (e.g., the current test distribution or a moving average), effectively filtering out irrelevant or outdated contributions. This dynamic reweighting ensures the global model remains aligned with the data geometry across clients and over time. Furthermore, the use of profiles at inference time allows the server to retrieve the most suitable model without retraining: clients that are close in profile space likely benefit from similar models, while isolated clients receive personalized ones. This adaptability, driven solely by the profiles, yields robustness to all four shift types and varying drift frequencies, explaining the significant accuracy gains reported.

## Architecture Onboarding
**Component Map**: Client Data -> Local Profile Builder -> Encrypted Profile -> Server (Profile Storage, Similarity Calculator, Aggregation Weight Generator, Model Aggregator, Assignment Module) -> Global Model -> Clients; At test: Client Profile -> Similarity Matching -> Model Deployment (Clustered/Personalized)

**Critical Path**: (1) Clients compute and send profiles to server. (2) Server updates profile database and recomputes similarity matrix (periodically). (3) Server samples a subset of clients for the round, broadcasts the current global model. (4) Sampled clients perform local epochs and send model updates. (5) Server aggregates updates using similarity‑derived weights, updates the global model. (6) Server broadcasts the new global model to all clients. (7) Repeat from step 2. After training, model assignment uses the stored profiles to select the appropriate model for any client.

**Design Tradeoffs**:
- Privacy vs. Utility: Profiles must be compact and privacy‑preserving, but overly coarse summaries may reduce similarity discrimination.
- Communication Overhead vs. Adaptivity: Transmitting profiles adds overhead, yet enables dynamic weighting; FEROMA claims this overhead remains comparable to FedAvg by keeping profiles small.
- Cluster vs. Personalization: Adaptive selection trades off the stability of shared models against the fit of personalized ones; the automatic threshold on profile density is a design parameter.
- Scalability of Similarity Computation: Pairwise similarity is O(n²) in number of clients; for large fleets approximation or sampling is needed, sacrificing some accuracy for speed.
- Profile Update Frequency: More frequent profile refreshes better capture drift but increase communication; FEROMA likely uses a fixed schedule or triggers based on drift detection.

**Failure Signatures**:
- Stagnant or decreasing accuracy despite many rounds may indicate that profiles are not representative or similarity weights are mis‐calibrated.
- High variance in performance across clients suggests that aggregation weights are overly concentrated on a few clients, possibly due to poor similarity estimates.
- Increased communication delay or lost profile messages can desynchronize the similarity matrix, leading to stale or inconsistent weighting.
- If all client profiles become nearly identical, the system defaults to standard FedAvg, losing the personalization benefit.
- Successful membership inference attacks on exchanged profiles would signal inadequate privacy protection.

**First Experiments**:

2. **Privacy Evaluation**: Perform membership inference attacks (e.g., using shadow modeling) on the transmitted client profiles to quantify reconstruction risk; compare profiles with and without differential privacy mechanisms.
3. **Scalability Stress Test**: Increase the client count to 200+ while measuring per‑round training time, total communication volume, and final accuracy under varying non‑IID degrees and drift frequencies; also emulate network latency to assess robustness.
