# REFINE: Real-world Exploration of Interactive Feedback and Student Behaviour

## Quick Facts
- **arXiv ID:** 2603.29142  
- **Source URL:** https://arxiv.org/abs/2603.29142  
- **Reference count:** 32  
- **Primary result:** REFINE leverages small open-source LLMs and an LLM‑as‑judge refinement loop to produce high‑quality interactive formative feedback; evaluations show significant improvements in feedback correctness, response quality comparable to GPT‑5 with fewer tool steps, and strong steering of student inquiry via rubric highlighting (OR = 8.1).

## Executive Summary
Formative feedback is essential for learning but difficult to scale personally. REFINE addresses this with a locally deployable multi‑agent system that uses small open‑source LLMs. The system comprises two main agents: a Feedback Generation Agent that iteratively refines a pedagogically structured report using an LLM judge, and an Interactive Feedback Agent that answers student follow‑up questions by invoking domain tools. Evaluations in authentic classroom and exam‑preparation settings demonstrate that judge‑guided refinement significantly boosts feedback correctness across models, the fine‑tuned interactive agent matches GPT‑5 in relevance and actionability while using fewer tool steps, and highlighting rubric components steers student inquiry by a factor of 8.1. These results point to a viable path for scalable, high‑quality interactive feedback.

## Method Summary
RESEARCH TASK: Build a system for scalable, personalized formative feedback that supports student interaction.  
INPUTS: Handwritten student solutions (transcribed), correct solutions, course materials (textbook, slides, exercises in structured markdown), and a pedagogical rubric. Datasets include 177 feedback solutions (Df_b) and ~7k interaction traces (Dtrain_int/Dtest_int).  
OBJECTIVE: Improve feedback correctness and interactive response quality (relevance, actionability, tool relevance) while maintaining efficiency.  
METHOD:  
- **Feedback Generation Agent:** A “Feedback Thinking LLM” produces an initial structured report aligned with Hattie’s feedback framework. A separate “Feedback LLM Judge” (human‑aligned) evaluates each component against the rubric; failures trigger targeted explanations, and the Thinking LLM revises only the failing parts. This generate–evaluate–revise loop repeats until the rubric is satisfied or a limit is reached.  
- **Interactive Feedback Agent:** A fine‑tuned thinking LLM performs closed‑loop reasoning. Given a student query and the feedback report, it conditionally invokes pedagogical tools (retrieval over course materials, prerequisite maps, behavioural reasoning) to gather evidence, revises tool calls on errors, and synthesises a final response. Fine‑tuning uses supervised interaction traces via a two‑stage LoRA procedure (reasoning first, then tool‑use).  
DEPLOYMENT: In live classroom and exam‑prep settings with one refinement iteration to meet latency constraints.

## Key Results
- Judge‑guided refinement significantly improves feedback correctness (task‑level next‑step correctness gains for all models, *p* < .001).  
- The fine‑tuned interactive agent achieves response quality (relevance, actionability) comparable to GPT‑5 while using fewer tool steps (2.26 vs. 2.39, *p* = 0.043).  
- Highlighting rubric components in feedback increases their discussion in student follow‑up questions by a factor of 8.1 (*p* < .001), demonstrating systematic steering of inquiry.

## Why This Works (Mechanism)
### Mechanism 1: Iterative LLM‑as‑Judge Refinement
**Claim:** Iterative LLM‑as‑judge refinement systematically improves the pedagogical correctness of generated feedback.  
**Mechanism:** A Feedback Thinking LLM produces an initial structured feedback report aligned with Hattie’s framework. A separate, human‑aligned Feedback LLM Judge evaluates each component against a rubric (coverage, correctness for current‑state and task‑next steps). When a component fails, the judge provides a targeted explanation; the Thinking LLM revises only the failing components. This generate–evaluate–revise loop repeats until the rubric is satisfied or a limit is reached.  
**Core assumption:** The judge’s rubric‑based evaluation reliably identifies pedagogical deficiencies and that targeted revision explanations are sufficient for the Thinking LLM to correct them.  
**Evidence:** Statistical gains in current‑state and task‑level next‑step correctness after one iteration across all models (*p* < .001) (Section 4.1, Figure 2). Corpus neighbours discuss iterative refinement but do not directly validate this specific mechanism.  
**Break condition:** Human–judge agreement (Cohen’s κ) falls below 0.8 or iterative refinement does not yield significant improvement on a held‑out validation set over multiple iterations.

### Mechanism 2: Fine‑Tuned Tool‑Calling Agent Efficiency
**Claim:** A fine‑tuned, tool‑calling interactive feedback agent can produce responses comparable in relevance and actionability to a state‑of‑the‑art closed‑source model (GPT‑5) while using fewer tool‑mediated reasoning steps.  
**Mechanism:** The Interactive Feedback Agent (a fine‑tuned thinking LLM) performs closed‑loop, multi‑step reasoning. Given a student query and the feedback report, it conditionally invokes pedagogical tools (retrieval, prerequisite maps, behavioural tools) to gather evidence, revises tool calls on errors, and synthesises a final response. Fine‑tuning on supervised interaction traces teaches efficient tool selection and response generation.  
**Core assumption:** The fine‑tuning process successfully distils efficient tool‑use patterns from the interaction data and that conditioning on the structured feedback report provides sufficient context for accurate, actionable responses without excessive tool calls.  
**Evidence:** Qwen3‑8B REFINE is not significantly different from GPT‑5 on relevance, actionability, or tool relevance; it uses fewer mean steps (2.26 vs. 2.39, *p* = 0.043) and reduces queries exceeding two steps (Section 4.1, Figure 3).  
**Break condition:** Tool relevance scores drop below 90% or mean steps per response increase beyond 3.0 without quality improvements.

### Mechanism 3: Rubric Highlighting Steers Student Inquiry
**Claim:** The content of generated feedback, specifically highlighting rubric components, systematically steers subsequent student inquiry toward those components.  
**Mechanism:** The feedback report explicitly highlights key rubric components (Basis, IH, Step, etc.). Students, when formulating follow‑up questions, are more likely to discuss components that were highlighted, as measured by annotation of chat logs against the rubric.  
**Core assumption:** Students attend to and base their follow‑up questions on the explicitly highlighted elements of the feedback, rather than on other aspects of their solution or the task.  
**Evidence:** Logistic regression (clustered by student) shows highlighted components are substantially more likely to be discussed (OR = 8.10, 95% CI [2.92, 22.46], *p* < .001). Discussion rates: e.g., “Step” discussed 92% when highlighted vs. 40% when not (Section 4.3, Table 2).  
**Break condition:** The odds ratio for discussion of highlighted vs. non‑highlighted components falls below 2.0 or becomes non‑significant (*p* > 0.05) in replication.

## Foundational Learning
#### Hattie’s Feedback Framework (“Where am I going? How am I going? Where to next?”)
- **Why needed:** Structures the feedback report into pedagogically validated components (task clarification, current‑state diagnosis, next steps at task/strategy/self‑regulated levels, praise), ensuring coverage beyond superficial comments.
- **Quick check:** *How would you decompose a feedback comment about a student’s incorrect proof into the three Hattie questions?*

#### LLM‑as‑Judge with Rubric‑Guided Refinement
- **Why needed:** Enables iterative improvement of feedback quality using a separate, human‑aligned model that evaluates against pedagogical criteria, avoiding costly human‑in‑the‑loop cycles.
- **Quick check:** *Given a rubric dimension (e.g., “task‑level next‑step correctness”), what would a judge’s “targeted explanation” look like for a failing feedback component?*

#### Tool‑Augmented LLMs for Interactive Agents
- **Why needed:** The interactive agent must access course‑specific resources (textbook, prerequisites) and behavioural models to answer follow‑up questions accurately; tool calls ground responses in authoritative materials.
- **Quick check:** *For a student asking “How does this relate to what we learned in Lecture 4?”, which tool(s) should the interactive agent invoke and why?*

#### Fine‑Tuning with LoRA on Interaction Trajectories
- **Why needed:** Adapts a base thinking model to the specific multi‑step, tool‑calling interaction pattern of REFINE, improving efficiency and quality beyond zero‑shot reasoning.
- **Quick check:** *Why might the two‑stage LoRA procedure (reasoning first, then tool‑use) be preferable to end‑to‑end training on full trajectories?*

#### Thematic Analysis of Student Engagement
- **Why needed:** To categorize open‑ended follow‑up questions into meaningful engagement patterns (e.g., task‑focused, feedback‑focused) and relate them to performance, moving beyond quantitative metrics.
- **Quick check:** *How would you distinguish a “feedback‑focused” question from a “solution‑focused” question in a student’s chat log?*

## Architecture Onboarding
**Component map:**  
Feedback Generation Agent (Thinking LLM + Feedback Judge) → Structured Feedback Report → Interactive Feedback Agent (Fine‑tuned Thinking LLM + Toolset) → Response.  
Shared resources: Transcribed student solution, question, correct solution, course material index.  
Evaluation modules: Feedback Judge (offline), Interactive Feedback Judge (offline), human annotators.

**Critical path:**  
Student upload → transcription (Qwen2.5‑VL‑72B‑Instruct) → Feedback Generation Agent (judge loop) → student views report → student submits query → Interactive Feedback Agent (tool loop) → response.

**Design tradeoffs:**  
- **Local deployment vs. latency:** Smaller open‑source models enable local hosting but generate slower; mitigated by capping refinement iterations and using efficient inference (A100 GPUs).  
- **Judge alignment vs. cost:** Human‑aligned judge improves feedback quality but adds compute; trade‑off: use single iteration in real‑time, multi‑iteration offline.  
- **Tool richness vs. complexity:** More tools increase grounding but risk misselection; mitigated by fine‑tuning on interaction traces and self‑reflective error recovery.

**Failure signatures:**  
- Judge misalignment: Cohen’s κ < 0.8 on rubric dimensions.  
- Tool misuse: >20% of queries requiring >3 steps without quality gain; tool relevance <90%.  
- Latency spikes: End‑to‑end response time >30 seconds in classroom setting.  
- Steering failure: Odds ratio ~1.0 for discussion of highlighted components.

**First 3 experiments:**  
1. **Judge calibration:** Run the Feedback Judge on 25 expert‑annotated feedback instances; compute Cohen’s κ against human annotations per dimension. Target: κ ≥ 0.9.  
2. **Tool‑calling validation:** Simulate 50 known student queries with ground‑truth answers; measure tool relevance and final correctness via the Interactive Feedback Judge. Target: >90% tool relevance, >85% correctness.  
3. **Latency & throughput test:** Deploy the full pipeline on a single NVIDIA A100; measure tokens/second for both agents under concurrency (5 simultaneous users). Target: >15 tokens/s for interactive agent, >20 tokens/s for feedback generation (with 1 iteration).

## Open Questions the Paper Calls Out
1. **Generalization across disciplines:** Does REFINE’s effectiveness generalize to diverse academic disciplines beyond discrete mathematics? *Basis:* Study conducted in a single undergraduate discrete mathematics course. *Unresolved:* Architecture may be tailored to proof‑based tasks; performance likely differs in other formats (essays, programming). *Resolution:* Deploy REFINE in multiple courses across fields and compare metrics.  
2. **Impact on learning outcomes:** Does interactive feedback via REFINE lead to measurable improvements in student learning outcomes compared to static feedback? *Basis:* Paper focuses on interactional evidence, not direct gains. *Unresolved:* Engagement does not guarantee better understanding. *Resolution:* Randomized controlled trial measuring pre/post assessments or exam scores.  
3. **Adaptive refinement policy:** Can an adaptive policy that selects which rubric dimensions to improve based on student needs or instructor intent enhance feedback quality and reduce computational cost? *Basis:* Future work suggestion. *Unresolved:* Current system refines only a fixed subset (current‑state, task‑level) to meet latency. *Resolution:* Implement an adaptive agent that chooses refinement targets and evaluate all rubric dimensions and latency.  
4. **Richer domain‑specific tools:** How do richer, domain‑specific tools (e.g., code execution, symbolic solvers) affect the quality and nature of interactive feedback in REFINE? *Basis:* Future work extension. *Unresolved:* Current tool set is limited to retrieval and basic behavioural reasoning. *Resolution:* Integrate domain tools (e.g., Python interpreter) and analyze changes in tool usage, correctness, and student satisfaction.

## Limitations
- Reliance on proprietary LLMs (e.g., GPT‑5) for judges and baselines hinders full replication.  
- Insufficient disclosure of prompt templates, LoRA hyperparameters, and tool schemas; reproducibility depends on unreleased code.  
- Single‑course deployment limits external validity; generalizability to other disciplines remains untested.

## Confidence
- Judge‑guided refinement improves feedback correctness: **Medium**  
- Fine‑tuned interactive agent matches GPT‑5 quality with fewer steps: **Medium**  
- Rubric highlighting steers student inquiry: **High**

## Next Checks
1. **Judge calibration study:** Annotate 50 feedback instances with human educators; compute Cohen’s κ against the Feedback Judge per rubric dimension; require κ ≥ 0.9 for all dimensions.  
2. **Tool‑use ablation:** Run the interactive agent with fine‑tuning disabled and with a random tool selector on a held‑out query set; compare tool relevance, correctness, and step count to quantify the contribution of LoRA training.  
3. **Steering experiment:** Randomly assign students to receive feedback with or without rubric component highlighting; measure the proportion of follow‑up questions discussing highlighted components; target odds ratio ≥ 4.0, *p* < .01.
