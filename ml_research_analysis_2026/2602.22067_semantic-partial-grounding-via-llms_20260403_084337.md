# Semantic Partial Grounding via LLMs

## Quick Facts
- **arXiv ID:** 2602.22067  
- **Source URL:** https://arxiv.org/abs/2602.22067  
- **Reference count:** 4  
- **Primary result:** SPG-LLM reduces grounded actions by up to two orders of magnitude, yielding the fastest grounding times across seven hard-to-ground benchmarks while preserving or improving plan costs on commonly solved tasks.

## Executive Summary
SPG-LLM tackles the grounding bottleneck in classical planning by leveraging an LLM to heuristically prune semantically irrelevant objects, predicates, and action schemas from PDDL domain and problem files *before* grounding. This task-level pre-pruning dramatically shrinks the grounded representation—often by 100×—cutting grounding time substantially. Although 36 of 175 tasks yield unsound plans, SPG-LLM achieves comparable or better plan costs and faster solving times on the majority, with striking improvements in domains like Zenotravel (solving time reduced by an order of magnitude with only a marginal cost increase). The approach is complementary to existing partial grounding methods and relies on a validation loop to ensure syntactic and computational feasibility.

## Method Summary
SPG-LLM processes a PDDL domain and problem pair through a pipeline: a prompt formatter injects the files into a structured template, which instructs the LLM to identify and remove irrelevant elements. The LLM produces a pruned domain and problem. These outputs undergo multi-level validation—syntactic parsing, solvability within a bounded time using a fast planner (e.g., LAMA), and semantic consistency (pruned elements are subsets of originals and the goal is preserved). If validation fails, the original task, the LLM’s output, and an error description are fed back to the LLM for up to *K* retries (*K*=1 in the paper’s main setting). Once validated, the pruned PDDL files are passed to a classical planner for solving. The method operates prior to grounding, thereby avoiding the combinatorial explosion of materializing the full ground action space.

## Key Results
- Grounded action count reduced by up to two orders of magnitude versus full grounding and a learned object importance baseline (PLOI).  
- SPG-LLM achieves the fastest grounding times on commonly solved tasks across all seven domains.  
- On Zenotravel, solving time decreased by an order of magnitude with only a marginal increase in plan cost; overall soundness rate was 139/175 valid plans.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** SPG-LLM reduces grounding computation by heuristically removing superfluous planning components before the expensive grounding phase.  
- **Mechanism:** The LLM analyzes the semantic content of the PDDL files (type hierarchies, goal condition, action definitions) to predict which elements are unlikely to contribute to a plan achieving the goal. This pre‑processing shrinks the input space for grounding, which is exponential in the number of objects and action schema parameters.  
- **Core assumption:** The textual and structural cues in standard PDDL descriptions contain sufficient semantic information for an LLM to make reasonably accurate, task‑specific relevance judgments about objects, predicates, and actions relative to the goal.  
- **Evidence anchors:**  
  - *Abstract*: "uses LLMs to analyze the domain and problem files to heuristically identify potentially irrelevant objects, actions, and predicates prior to grounding, significantly reducing the size of the grounded task."  
  - *Section 1*: "We argue that many planning tasks specified in PDDL contain enough detail to provide rich semantic information, which LLMs can leverage to heuristically identify the sub‑components of the task that are relevant for finding a plan."  
- **Break condition:** If the LLM’s semantic analysis is consistently incorrect (e.g., removing objects critical for any valid plan), the pruned task becomes unsolvable, leading to failure in plan soundness or coverage.

### Mechanism 2
- **Claim:** A multi‑level validation loop (syntactic, computational, semantic) increases reliability, enabling practical use despite LLM formatting errors or hallucinations.  
- **Mechanism:** After the LLM generates a pruned task, rigorous checks are performed: (1) syntax validation ensures PDDL correctness, (2) computational validation attempts to solve the pruned task within a time bound to confirm solvability, (3) semantic validation verifies that pruned elements are subsets of the originals and the goal is preserved. If validation fails, the original task and error description are fed back to the LLM for up to *K* retries.  
- **Core assumption:** Iterative feedback with explicit error descriptions can guide an LLM to correct its own output for this structured code‑generation task, mitigating initial failures.  
- **Evidence anchors:**  
  - *Section 3*: "This validation is performed at 3 different levels: syntactic, computational, and semantic... If validation fails, the prompt template is populated with the original task description (D and P), the LLM‑generated output (D' and P'), and a description of the identified error to facilitate correction in subsequent LLM interactions."  
  - *Section 4*: "SPG‑LLM has been run with K=1...", indicating the process often succeeds on the first try.  
- **Break condition:** If the LLM cannot produce a syntactically valid and computationally solvable reformulation within *K* attempts, the procedure fails and falls back to full grounding.

### Mechanism 3
- **Claim:** Operating at the task level (pruning the lifted representation before grounding) provides complementary benefits to operator‑level or object‑level partial grounding methods.  
- **Mechanism:** SPG‑LLM’s pre‑grounding pruning reduces the combinatorial space before it is materialized into ground atoms and actions. This differs from methods that incrementally ground operators (e.g., Gnad et al.) or rank objects for inclusion after partial grounding (e.g., PLOI). By acting earlier, SPG‑LLM avoids the cost of generating and filtering a massive grounded space.  
- **Core assumption:** A large portion of the grounded action space in hard‑to‑ground benchmarks is semantically irrelevant to the goal and can be identified and removed from the lifted representation without instantiation.  
- **Evidence anchors:**  
  - *Section 1*: "This approach works at the task level, prior to grounding, hence it is complementary to the partial grounding solutions of Areces et al. (2023) and Gnad et al. (2019)."  
  - *Section 4*: "SPG‑LLM outperforms both baselines by grounding fewer operators in most tasks, achieving reductions of up to two orders of magnitude." and "SPG‑LLM is the fastest approach across the commonly solved tasks in all domains [for grounding time]."  
- **Break condition:** If semantic cues in the PDDL are insufficient for reliable pre‑pruning (relevance only detectable after partial grounding), task‑level pruning may remove necessary elements, causing solver failure or suboptimal plans.

## Foundational Learning
- **PDDL (Planning Domain Definition Language)**  
  *Why needed*: SPG‑LLM’s input and output are PDDL domain and problem files; understanding their structure (object types, predicates, action schemas, initial state, goal) is essential to interpret the LLM’s modifications and design validation checks.  
  *Quick check*: Given a PDDL action schema `move(?x - block, ?y - block, ?z - block)` and an initial state containing `(on objA table)`, if object `objA` is pruned from the problem, what must also be removed from the initial state to maintain consistency?

- **Grounding in Classical Planning**  
  *Why needed*: The core bottleneck SPG‑LLM addresses is exponential blowup during grounding. One must understand that grounding substitutes all objects into action schema variables to produce a propositional representation searched by most planners.  
  *Quick check*: If a domain has an action schema `move(?x - block, ?y - block, ?z - block)` and a problem with 100 block objects, how many ground actions does this single schema produce before any pruning? Why is this number problematic?

- **Partial Grounding & Soundness vs. Completeness**  
  *Why needed*: SPG‑LLM is a form of *pre*-grounding partial grounding. The paper’s trade‑off (faster grounding vs. some unsound plans) hinges on these concepts; soundness means any found plan is valid for the original task, completeness means the method can find a plan if one exists. SPG‑LLM sacrifices completeness (and sometimes soundness) for efficiency.  
  *Quick check*: If SPG‑LLM’s pruned task yields a valid plan, why might that plan still be invalid for the original, unpruned task? What property must the pruning process satisfy to guarantee soundness?

## Architecture Onboarding
**Component map:**  
Input (PDDL domain/problem) -> Prompt Formatter -> LLM Engine -> Validation Pipeline (Syntactic -> Computational -> Semantic) -> Retry Controller -> Output (pruned PDDL) -> Downstream (Planner)

**Critical path:** Read Files -> Format Prompt(Φ) -> Call LLM() -> Validate() -> {if valid return pruned; else if retries left feedback → LLM()} -> return result.

**Design tradeoffs:**  
- *Speed vs. Soundness*: Aggressive pruning speeds up grounding but risks unsolvability or invalid plans.  
- *LLM Capability vs. Cost*: More capable LLMs improve accuracy but increase latency and expense; paper uses a single call (K=1) to prioritize low latency.  
- *Validation Rigor vs. Time*: Computational validation (trying to solve) is expensive but catches semantic errors the subset check misses; time bound is a key parameter.

**Failure signatures:**  
1. **Syntactic Failure**: LLM output not valid PDDL (missing parentheses, wrong keywords). Caught by syntax parser.  
2. **Computational Failure**: Pruned task unsolvable within time bound. Caught by computational check; often due to over‑pruning.  
3. **Semantic Failure (Proxy)**: Pruned files fail subset check (`P'⊈P` etc.) or goal appears altered. Caught by semantic check.  
4. **Plan Soundness Failure**: A plan is found for pruned task but `VAL` rejects it for the original task; this is the primary reported failure mode (36/175 tasks), indicating validation gaps.

**First 3 experiments:**  
1. **Baseline Comparison**: Replicate Table 1—run SPG‑LLM (K=1), Full Grounding, and PLOI on 25 tasks per domain (7 domains). Compare grounded action count, grounding time, plan cost, solving time, coverage/soundness. Expect SPG‑LLM to show orders‑of‑magnitude grounding reduction with domain‑dependent plan cost trade‑offs.  
2. **Ablation – Validation Role**: Run SPG‑LLM with K=1 but skip the Computational Validation step. Compare resulting soundness rate to full validated pipeline to isolate computational check’s contribution.  
3. **Domain Transfer Probe**: Take a high‑performing domain (e.g., Zenotravel) and manually add superfluous but “goal‑adjacent” objects/actions (e.g., a `luxury‑aircraft` type with no role in the goal). Run SPG‑LLM to test whether it correctly prunes this semantic noise.

## Open Questions the Paper Calls Out
- **Can the validation mechanism be improved to significantly reduce unsound plans while preserving grounding speedups?**  
  *Basis*: Authors note 36 unsound tasks and propose enhancing validation with soundness checks.  
  *Why unresolved*: Unsound plans undermine reliability; improvement is needed for practical adoption.  
  *Resolution evidence*: Implement stronger validation (e.g., lightweight plan sampling or symbolic soundness checks) and measure soundness rate and grounding overhead on the benchmark.

- **What domain characteristics correlate with SPG‑LLM’s ability to produce sound pruned tasks?**  
  *Basis*: Results show large variation in soundness across domains (e.g., Blocksworld all valid, Agricola only 8 valid) but no analysis of underlying factors.  
  *Why unresolved*: Understanding correlations would allow predicting safe usage and guiding prompt/model improvements.  
  *Resolution evidence*: Systematic error analysis extracting features (type hierarchy depth, predicate arity, goal complexity) and correlating with soundness outcomes.

- **Can SPG‑LLM generate human‑interpretable explanations for pruning decisions, and do these increase trust and facilitate debugging?**  
  *Basis*: Authors plan to investigate explanation generation.  
  *Why unresolved*: Explanations are crucial for transparency and debugging yet the current approach provides no insights.  
  *Resolution evidence*: Develop an explanation module (e.g., LLM‑generated rationales) and conduct a user study measuring trust, perceived usefulness, and error‑correction efficiency vs. a no‑explanation baseline.

- **Does SPG‑LLM scale effectively to larger, real‑world planning domains with richer semantics?**  
  *Basis*: Authors desire to experiment with real‑world domains like those in the introduction.  
  *Why unresolved*: Current benchmark comprises seven artificially hard‑to‑ground domains; real‑world domains may pose new challenges (complex type systems, nuanced goals).  
  *Resolution evidence*: Evaluate SPG‑LLM on diverse real‑world planning domains (logistics, robotics, manufacturing) and compare grounding times, action counts, plan costs, solving times, and soundness against full grounding and other baselines.

## Limitations
- The exact prompt template (including the example domain/problem) is not fully specified, which may drastically affect LLM behavior.  
- Validation implementation details (e.g., time bound for computational check, exact subset comparison procedure) are vague, hindering precise replication.  
- The method depends on GPT‑5‑2025‑08‑07, which is unavailable; portability to other LLMs remains unclear.  
- No detailed breakdown of the 36 unsound plans; unclear whether failures stem from over‑pruning, validation gaps, or domain‑specific quirks.

## Confidence
- **Grounding reduction** (up to 100× fewer actions): **High**  
- **Validation loop effectiveness** (reducing but not eliminating unsound plans): **Medium**  
- **Cross‑domain generality** (7 benchmarks from one source): **Medium**  
- **Task‑level vs. operator‑level partial grounding** (outperforms PLOI on grounding metrics): **Medium‑High**

## Next Checks
1. **Ablation of validation components**: Run SPG‑LLM with each validation stage disabled (syntactic only, syntactic+computational, etc.) to quantify individual contributions to soundness and grounding reduction.  
2. **Prompt variation study**: Systematically alter the prompt (remove example, rephrase instructions) on a subset of tasks and measure variance in pruning aggression and plan validity to assess robustness.  
3. **Unsounded plan forensics**: For each of the 36 unsound plans, use `VAL` to identify the exact discrepancy (e.g., missing action, unsatisfied precondition) and map it back to pruned elements to diagnose systematic failure modes.
