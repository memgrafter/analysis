# LUT-KAN: Segment-wise LUT Quantization for Fast KAN Inference

## Quick Facts
- **ArXiv ID:** 2601.03332  
- **Source URL:** https://arxiv.org/abs/2601.03332  
- **Reference count:** 21  
- **Primary result:** LUT-KAN accelerates CPU inference for Kolmogorov–Arnold Networks by replacing B-spline evaluation with segment-wise lookup tables, achieving 10–14× (NumPy) and 9.5–11× (Numba) speedup on synthetic layers, preserving classification quality (F1 drop <0.0002) and reducing steady-state inference latency by 12× (NumPy) and 10× (Numba) on a DoS detection case study, with ≈10× memory overhead at LUT resolution L=64.

## Executive Summary
LUT-KAN tackles the computational cost of Kolmogorov–Arnold Network (KAN) inference on CPUs. Standard KANs represent edge functions via B‑splines, whose recursive evaluation is relatively slow. LUT-KAN replaces this with segment‑wise lookup tables (LUTs) and linear interpolation, using per‑segment affine quantization (int8/uint8). It also defines explicit out‑of‑bounds semantics via boundary modes and OOB policies. The method compiles a trained KAN using calibration data to generate quantized LUTs and dequantization parameters, then runs inference via NumPy or Numba backends. Evaluations on controlled synthetic layers and a real‑world DoS attack detection model (CICIDS2017) show large speedups (10–14×) while preserving downstream accuracy (F1 drop <0.0002) and reducing latency by up to 12×. Memory overhead scales with LUT resolution, roughly 10× at L=64.

## Method Summary
LUT-KAN transforms a trained KAN’s spline‑based edge functions into a discrete representation. Each univariate edge function, originally a linear combination of B‑spline bases over a knot grid, is approximated by piecewise linear interpolation over uniform segments. For a given input dimension, the knot grid partitions the domain into K segments; each segment is discretized into L uniformly spaced samples. These floating‑point samples are quantized using affine scaling per segment (symmetric int8 or asymmetric uint8) to produce integer LUT entries. During inference, for each edge and input x: (1) safe clipping (per boundary mode) is applied; (2) the active segment is located via knot grid search; (3) local coordinate within the segment is computed; (4) two adjacent LUT indices are fetched; (5) their values are dequantized using segment‑specific scale and offset; (6) linear interpolation yields the spline component; (7) if `value_repr="spline_component"`, the result is combined with an analytic base branch (scaled by learned coefficients); (8) an OOB mask (e.g., zero_spline) is applied if needed. The LUT artifacts (knots, q_table, scales, metadata) are stored separately and loaded at runtime, enabling backends in NumPy (vectorized) or Numba (JIT). The approach maintains an “honest baseline” by comparing LUT and spline within the same backend to isolate representation effects.

## Key Results
- **Speedup:** 10–14× (NumPy) and 9.5–11× (Numba) on controlled synthetic layers vs. B‑spline baseline.
- **DoS detection case study:** F1 score drop <0.0002; steady‑state inference latency reduced by 12× (NumPy) and 10× (Numba).
- **Memory overhead:** ≈10× increase at LUT resolution L=64 relative to original floating‑point parameters.

## Why This Works (Mechanism)

### Segment-wise LUT substitution for spline evaluation
Replacing B‑spline basis evaluation with segment‑wise linear interpolation via lookup tables reduces compute overhead. Each edge function is discretized into K segments with L uniformly spaced samples. Inference locates the active segment via knot grid search, retrieves adjacent quantized values, dequantizes them affinely, and linearly interpolates. This replaces recursive B‑spline basis computation (Cox–de Boor) with fixed‑complexity indexing and arithmetic. Core assumption: piecewise linear interpolation over sufficiently fine segments approximates the spline within tolerance.

### Per‑segment affine quantization
Applying affine quantization per segment (int8/uint8) compresses LUT storage while preserving representational capacity. For each segment, floating‑point LUT values are scaled/offset to fit integer dtype; dequantization uses `y_min + α * q`. This isolates quantization error to narrow per‑segment ranges. Core assumption: spline branch outputs have bounded dynamic range within each knot segment.

### Explicit out‑of‑bounds (OOB) semantics
Defining boundary mode (`half open`/`closed`) and OOB policy (`clip x`/`zero spline`) makes LUT inference reproducible and semantically consistent. Boundary mode determines in‑range predicate; `clip x` saturates inputs to domain; `zero spline` masks spline contribution outside domain while retaining base branch. Both are enforced during safe indexing and output computation. Core assumption: real‑world inputs may exceed training knot domain; explicit handling prevents unpredictable extrapolation.

## Architecture Onboarding
**Component Map**  
Knot grid -> defines segment boundaries -> Quantized LUT (3D array [E, K, L]) -> Dequantization params (scale, y_min per segment) -> Linear interpolation output -> Reconstruction scalars (s_base, s_spline, s_out, base ID) -> final output; OOB policy and boundary mode metadata control safe indexing and masking.

**Critical Path**  
During inference, the engine loads the artifact (knots, q_table, scales, etc.). For each edge and input x: it clips x according to boundary mode, locates the active knot segment, computes local coordinate, fetches adjacent LUT indices, dequantizes the two integer values, and linearly interpolates to get the spline component. If `value_repr="spline_component"`, it combines the interpolated value with the analytic base branch scaled by s_base and s_spline, then applies s_out. If OOB policy is zero_spline, it multiplies by a mask that zeros the spline contribution when x is out‑of‑bounds.

**Design Tradeoffs**
- L resolution: higher L reduces approximation error but increases memory.
- Quantization scheme: symmetric (int8) simpler, zero offset; asymmetric (uint8) better for offset distributions.
- Boundary mode: closed avoids OOB if inputs clipped to knot max; half open mathematically clean but may trigger OOB at exact boundary.
- value_repr: "spline_component" keeps base branch accurate; "phi" simpler but may quantize full output.

**Failure Signatures**
- High OOB fraction: check preprocessing vs knot domain alignment; consider boundary_mode=closed if inputs clip to t_K.
- Unexpected MAE spikes: verify L adequacy and calibration distribution coverage.
- Memory exhaustion: first‑layer d_in × d_hidden dominates; consider feature selection or pruning.
- Backend discrepancy: ensure NumPy/Numba backends enforce identical OOB semantics.

**First 3 Experiments**
1. Controlled accuracy sweep: For fixed L (e.g., 64), compute in‑range MAE/MaxAbs vs. reference spline across seeds. Confirm O(1/L) trend.
2. Honest baseline latency: Under single‑threaded NumPy and Numba, measure steady‑state ms/iter for B‑spline vs. LUT with identical batch/inputs. Isolate representation effect.
3. OOB robustness matrix: For half open vs. closed × clip_x vs. zero_spline, compute OOB fraction, MAE on OOB‑only samples, and in‑range MAE. Validate policy semantics.

## Open Questions the Paper Calls Out

### Open Question 1: Memory overhead reduction for dense layers
**Question:** How can the memory overhead of LUT‑KAN be reduced for dense KAN layers, especially the first layer which dominates storage, without sacrificing speed or accuracy?  
**Basis:** Memory analysis shows first layer accounts for >80% of total memory; limitations cite memory overhead as a constraint.  
**Why unresolved:** Current design stores a full LUT per edge; for wide input layers this is prohibitive. No exploration of structured sparsity, low‑rank, or sharing.  
**Evidence needed:** A study introducing compressed LUT formats (e.g., pruning, clustering, mixed resolutions) with accuracy‑speed‑memory trade‑offs.

### Open Question 2: Calibration distribution sensitivity
**Question:** How sensitive is LUT‑KAN's accuracy to distribution shift between calibration data and deployment data, and what calibration strategies can improve robustness?  
**Basis:** Paper notes dependence on calibration distribution; limitations mention that if calibration does not cover deployment distribution, quantization ranges may be suboptimal.  
**Why unresolved:** Only fixed calibration scheme (in‑range standard normal) tested on one dataset; impact of covariate shift not measured.  
**Evidence needed:** Controlled experiments with mismatched calibration/test distributions (shifted means, variances, correlations) across datasets, reporting degradation curves and evaluating adaptive recalibration.

### Open Question 3: Adaptive LUT resolution
**Question:** Can the LUT resolution L be adapted non‑uniformly across edges or segments to optimize accuracy‑memory trade‑off for a given model and budget?  
**Basis:** Paper sweeps L uniformly and notes L affects accuracy more than latency; memory scales linearly with L; conclusion suggests adaptive quantization.  
**Why unresolved:** All evaluations use a single global L; no analysis of edge‑wise error or importance to guide non‑uniform allocation.  
**Evidence needed:** Framework to estimate per‑edge error/importance (e.g., from validation set) and allocate L under memory constraint, comparing uniform vs. adaptive schemes.

### Open Question 4: Generalization to other KAN variants and domains
**Question:** How does LUT‑KAN's performance and OOB robustness generalize to other KAN architectural variants (e.g., shallow vs. deep, different grid sizes, sparse connectivity, base functions) and to other application domains beyond intrusion detection?  
**Basis:** Paper explicitly notes future work on sparse/factored architectures and that case study is on a single task; controlled sweeps use fixed architecture.  
**Why unresolved:** Core experiments on narrow architecture and one real‑world model; variants with different spline characteristics (curvature, OOB frequency) may affect optimal L, quantization, OOB policy.  
**Evidence needed:** Broad evaluation across diverse trained KAN models from repositories (various architectures, grid sizes, domains) measuring accuracy drop, speedup, memory, OOB error.

### Open Question 5: Alternative OOB policies
**Question:** Are there OOB policies beyond clip_x and zero_spline that offer a better balance between safety and utility for real‑world deployments?  
**Basis:** Paper defines 2×2 matrix of boundary modes and OOB policies but does not evaluate other policies; zero_spline can cause large errors if base branch insufficient.  
**Why unresolved:** Space of policies larger (e.g., extrapolation, learned constant, blending). Suitability for heavy‑tailed data or critical OOB inputs unexplored.  
**Evidence needed:** Propose and evaluate additional policies (e.g., boundary extrapolation, safe constant, masked interpolation) on synthetic functions and real datasets where OOB inputs are frequent; measure downstream task impact.

## Limitations
- Reproducibility of speedup numbers depends on specific hardware, random seeds, and warm‑up handling, introducing uncertainty.
- Accuracy preservation demonstrated only on CICIDS2017; generalization to other datasets and distribution shifts is unclear.
- Memory overhead evaluated for a single model configuration (78×32 first layer); scaling to larger or denser architectures not fully characterized.

## Confidence
- Latency reduction: Medium  
- Accuracy preservation (in‑range): High  
- OOB handling correctness: Medium  
- Memory overhead: High
