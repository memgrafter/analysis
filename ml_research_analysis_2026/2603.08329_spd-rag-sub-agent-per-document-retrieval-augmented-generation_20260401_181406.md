# SPD-RAG: Sub-Agent Per Document Retrieval-Augmented Generation

## Quick Facts
- **ArXiv ID:** 2603.08329
- **Source URL:** https://arxiv.org/abs/2603.08329
- **Reference count:** 15
- **Primary result:** SPD-RAG achieves an Avg Score of 58.1 on the LOONG benchmark (GPT-5 evaluation), a ~76% relative gain over Normal RAG and Agentic RAG baselines, while using only 38% of the API cost of a full-context baseline.

## Executive Summary
SPD-RAG is a novel framework for exhaustive multi-document question answering that decomposes the retrieval and synthesis process across specialized agents. It addresses the challenge of information scattered across many long documents by assigning a dedicated sub-agent to each document, ensuring focused, exhaustive search within that document's content. A central coordinator first translates the user query into a shared set of atomic extraction tasks and a synthesis directive, which are broadcast to all sub-agents. Each sub-agent performs iterative retrieval within its private vector index (limited to 5 searches) and produces a findings report with a confidence score. A token-bounded synthesis layer then merges all sub-agent outputs using recursive, similarity-ordered agglomerative clustering to produce a final answer that fits within a fixed context budget.

On the LOONG benchmark—a collection of 102 multi-document instances averaging 11 documents each, drawn from academic papers and financial reports—SPD-RAG achieves state-of-the-art performance. It attains an average score of 58.1 (as judged by GPT-5), surpassing Normal RAG (33.0) and Agentic RAG (32.8) by approximately 25 points (a 76% relative improvement). Remarkably, it does so while incurring only 38% of the API cost of a full-context baseline. The system shows particularly strong gains on tasks requiring exhaustive fact extraction from all documents, such as Clustering (+40.5 over Normal RAG) and academic paper instances (60.0 vs. 15-17 for baselines). These results demonstrate the effectiveness of per-document specialization combined with a disciplined synthesis strategy.

## Method Summary
SPD-RAG employs a hierarchical three-layer architecture tailored for exhaustive multi-document QA. The **Coordination Layer** uses a Gemini 2.5 Pro agent to decompose the user query into a list of atomic extraction tasks (`WriteTodos`) and a synthesis directive, ensuring all sub-agents have a shared, query-aligned instruction set. The **Parallel Retrieval Layer** assigns each document in the corpus `D` to a dedicated Gemini 2.5 Flash sub-agent. Each sub-agent operates exclusively on its assigned document's private vector index (Qdrant with Cohere embeddings) and conducts up to 5 iterative retrieve-and-reason cycles, outputting a findings report `si` and a confidence score `ri`. Finally, the **Synthesis Layer** takes all `{oi}` and recursively merges them: it embeds each findings report, computes a cosine similarity matrix, applies agglomerative clustering (UPGMA), and greedily batches the most similar summaries until a token budget (`B=750,000`) is reached. Each batch is synthesized concurrently into a new summary using Gemini 2.5 Pro, and the process repeats until a single coherent answer remains. The system is evaluated on the LOONG benchmark (English Set 4), which comprises 102 instances with an average of 11 long documents (academic papers or financial reports), using GPT-5 as a judge to produce Avg Score and Perfect Rate metrics.

## Key Results
- **Avg Score:** 58.1 on LOONG, compared to 33.0 (Normal RAG) and 32.8 (Agentic RAG)—a ~25-point absolute gain and 76% relative improvement.
- **Cost efficiency:** API cost is only 38% of the full-context baseline.
- **Domain-specific gains:** Most pronounced on Clustering tasks (+40.5 over Normal RAG) and academic paper instances (60.0 vs. 15-17 for baselines).

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Assigning one dedicated retrieval agent per document eliminates cross-document distraction and ensures exhaustive evidence coverage.
- **Mechanism:** Each sub-agent operates within a strictly isolated vector index of its assigned document, performing iterative retrieve-and-reason loops without seeing other documents' content. This constrains the search space, forcing the agent to exhaustively mine its own document for relevant facts rather than prematurely settling on globally retrieved but potentially irrelevant chunks.
- **Core assumption:** Information required to answer a query is distributed across documents, and a single global retrieval pass will miss critical evidence scattered in lower-ranked or document-specific contexts.
- **Evidence anchors:**
  - [abstract] "decomposes the problem along the document axis... each document is processed by a dedicated document-level agent operating only on its own content, enabling focused retrieval"
  - [section 3.2] "Each document di serves as an isolated retrieval universe; the assigned sub-agent is strictly constrained to search tool calls within di"
  - [corpus] Table 3: Normal RAG achieves 0% PR and 15.2 Avg Score on academic papers, while SPD-RAG reaches 60.0/7.5%, demonstrating recovery in dense, distributed evidence settings.
- **Break condition:** If documents are highly redundant or the query requires synthesizing contradictory information across documents, isolation might prevent necessary cross-document comparison during the extraction phase, overloading the synthesis layer.

### Mechanism 2
- **Claim:** A central coordinator generating a shared, atomic instruction set ensures consistent, query-aligned extraction across all heterogeneous documents.
- **Mechanism:** The coordinator agent decomposes the user query into a `WriteTodos` list of self-contained extraction tasks (e.g., "extract all reported financial risk factors") and a `synthesis_directive`. This shared instruction set is broadcast to all sub-agents, standardizing what each must look for within its own document, preventing idiosyncratic or incomplete extraction strategies.
- **Core assumption:** A single, high-capability model (Gemini 2.5 Pro) can produce a set of unambiguous, document-agnostic extraction instructions that are sufficient for all documents in a heterogeneous corpus.
- **Evidence anchors:**
  - [abstract] "coordinator dispatches tasks to relevant agents and aggregates their partial answers"
  - [section 3.1] "decompose the user query into a Shared Instruction Set for Documents and Synthesis Directives... atomic, self-contained extraction tasks"
  - [corpus] Table 2: Largest gains over baselines are on Clustering (+40.5) and Chain of Reasoning (+26.2), tasks requiring exhaustive, structured extraction from all documents, suggesting the shared todos enable systematic coverage.
- **Break condition:** For highly technical or domain-specific queries (e.g., niche academic subfields), the coordinator may generate tasks that are too generic or miss critical domain-specific extraction needs, leading to incomplete document-level findings, as partially observed in the paper's discussion on academic paper performance.

### Mechanism 3
- **Claim:** A token-bounded, similarity-ordered recursive synthesis layer prevents information loss and redundancy when aggregating many partial answers.
- **Mechanism:** The synthesis layer embeds all sub-agent findings, computes a pairwise cosine distance matrix, and uses agglomerative clustering (UPGMA) to group semantically similar summaries. It greedily batches the most similar summaries together until a token budget (B=750k) is filled, then synthesizes each batch into a new summary. This recursive map-reduce process condenses the corpus of findings efficiently while preserving semantic coherence.
- **Core assumption:** Grouping by semantic similarity before synthesis yields more coherent and less redundant merged summaries than arbitrary batching or simple concatenation, especially when many documents contain overlapping or complementary facts.
- **Evidence anchors:**
  - [abstract] "Agent outputs are synthesized by merging partial answers through a token-bounded synthesis layer (which supports recursive map-reduce for massive corpora)"
  - [section 3.3] "We embed each summary... compute a cosine-similarity matrix... AgglomerativeClustering... greedily accumulating nodes into a batch as long as the total tiktoken count does not exceed the target budget"
  - [corpus] The design is validated by the strong overall performance (58.1 Avg Score) despite the synthesis layer being a potential bottleneck; however, the recursive path was not triggered in Loong experiments, so its necessity for larger corpora remains an assumption.
- **Break condition:** If sub-agent findings are extremely heterogeneous or contain many low-quality/extraneous details, similarity clustering may group unrelated summaries, or the synthesis step may be unable to resolve contradictions, degrading final answer quality.

## Foundational Learning

### Document-Scoped Retrieval
- **Why needed here:** SPD-RAG's core innovation relies on treating each document as an isolated retrieval universe. Understanding this requires knowing how vector indices are typically built per-document and why global indices introduce noise in multi-document, all-relevant scenarios.
- **Quick check question:** "In a standard RAG system with a global index, why might a query about 'financial risks' retrieve chunks from a technically detailed but irrelevant appendix of a different document?"

### Hierarchical Map-Reduce Synthesis
- **Why needed here:** The synthesis layer's recursive merging is a specific application of the map-reduce pattern adapted for textual summaries with a token budget constraint. Grasping this requires understanding how to aggregate outputs from parallel processes without exceeding context limits.
- **Quick check question:** "If you have 100 short summaries and a context window of 50, how does a single-step concatenation differ from a two-step similarity-based clustering synthesis in terms of potential information loss?"

### Centralized Task Decomposition for Multi-Agent Systems
- **Why needed here:** The coordinator's role is to create a shared, atomic instruction set. This requires understanding the challenges of designing prompts that generate structured, reusable tasks for heterogeneous agents, and the risks of under-specification.
- **Quick check question:** "What is a key risk if the coordinator's 'todos' are not atomic and self-contained (e.g., 'summarize the document') when each agent only sees its own document?"

## Architecture Onboarding

### Component Map
- **Coordinator Agent (Gemini 2.5 Pro):** Input: query. Output: `WriteTodos` (list of atomic extraction tasks) + `synthesis_directive`.
- **Document Sub-Agents (Gemini 2.5 Flash, one per document):** Input: query, document name, shared todos. Loop: `search` (query local vector index) -> reason. Cap: 5 searches. Output: `(findings, relevance_score)`.
- **Synthesis Layer (Gemini 2.5 Pro):** Input: all `(findings)` + `synthesis_directive` + query. Process: Recursive similarity-ordered clustering & synthesis until within token budget. Output: final answer.
- **Infrastructure:** Per-document Qdrant indices, Cohere embeddings/reranker, LangGraph for parallel dispatch (`Send` API), `asyncio` for batch synthesis calls.

### Critical Path
1. User query received.
2. **Sequential:** Coordinator generates tasks & directive.
3. **Parallel Fan-out:** All document sub-agents execute concurrently.
4. **Sequential Barrier:** Wait for all sub-agent findings.
5. **Iterative (potentially recursive):** Synthesis layer clusters & merges findings until single summary remains.
6. Return final summary.

### Design Tradeoffs
- **Cost vs. Quality:** Uses cheaper Flash model for many parallel sub-agents, reserving expensive Pro model for coordinator and synthesis. Tradeoff: potential quality drop from Flash's reasoning during extraction.
- **Latency vs. Coverage:** Parallel sub-agents reduce wall-time vs. sequential processing, but the sequential dependency on coordinator output and synthesis barrier adds overhead vs. single-pass RAG.
- **Scalability vs. Complexity:** Recursive synthesis handles massive corpora but adds algorithmic complexity; for Loong-sized corpora (102 docs), it simplified to one merge step.

### Failure Signatures
- **Low Perfect Rate (PR%) on dense docs (e.g., academic papers):** Likely coordinator task generation is under-specified for technical content, leading to incomplete extraction.
- **High token usage / cost接近 full-context baseline:** Synthesis layer may be failing to compress summaries effectively (e.g., poor clustering, verbose findings).
- **Latency significantly higher than baselines:** Could indicate sub-agent loops hitting the 5-iteration cap frequently or synthesis layer triggering unexpected recursion.
- **Poor performance on Clustering/Chain of Reasoning tasks:** Suggests synthesis layer cannot effectively merge disparate findings; check similarity clustering parameters (e.g., `linkage="average"`).

### First 3 Experiments
1. **Sanity Check:** Run on a 2-document instance with a simple query (e.g., "What is the common publication year?"). Verify: coordinator creates 1-2 atomic todos (e.g., "extract publication year"), both sub-agents find a year, synthesizer correctly merges/compares. Confirms basic pipeline flow.
2. **Coverage Test:** Use a query where one document contains the answer and the other does not. Verify: sub-agent for irrelevant document outputs "Not found in this document" for all tasks, and final answer only cites the relevant document. Tests "Not found" handling and synthesis fidelity.
3. **Stress Synthesis Layer:** Artificially increase corpus size for a single instance to 50+ documents (duplicate or use a larger benchmark subset). Verify: the recursive loop activates (|S|>1 in next iteration) and final answer quality doesn't collapse. Tests the intended scalability mechanism.

## Open Questions the Paper Calls Out
1. How does the recursive similarity-based synthesis layer scale in terms of answer quality and operational cost when processing corpora containing hundreds to thousands of documents per query?
2. To what extent does SPD-RAG's performance generalize to non-evaluated document domains (e.g., legal, medical, enterprise) with different structural characteristics?
3. How can the coordinator agent's sub-task generation be made more robust to prevent underspecification, particularly for technical or densely distributed evidence in documents like academic papers?
4. What are the cost-quality trade-offs when varying the LLM backbone choices for document sub-agents versus the synthesis layer, and can cheaper models be used more aggressively without significant quality loss?
5. Can the sequential latency overhead in SPD-RAG's layered pipeline be reduced through architectural modifications (e.g., overlapping coordination with retrieval) while maintaining exhaustive document coverage?

## Limitations
- Missing exact prompts (coordinator, synthesis, sub-agent) and indexing details hinder faithful replication and risk cross-document leakage.
- Recursive synthesis layer was never triggered in LOONG experiments; its scalability remains unvalidated.
- Evaluation limited to two domains (academic papers, financial reports) with Gemini models; generalizability to other domains or LLM backbones is uncertain.
