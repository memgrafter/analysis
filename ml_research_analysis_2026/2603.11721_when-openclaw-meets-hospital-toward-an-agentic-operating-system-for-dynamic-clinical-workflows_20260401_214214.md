# When OpenClaw Meets Hospital: Toward an Agentic Operating System for Dynamic Clinical Workflows

## Quick Facts
- **arXiv ID:** 2603.11721
- **Source URL:** https://arxiv.org/abs/2603.11721
- **Reference count:** 23
- **Primary result:** Manifest-guided retrieval matches metadata-filtered RAG in overall recall (0.877) but achieves 2.2× higher precision (0.779 vs 0.352) and 21% higher recall on multi-admission (tier-3) queries (0.846 vs 0.701).

## Executive Summary
This paper introduces an Agentic Operating System (AOS) architecture to safely deploy LLM agents in hospitals for dynamic clinical workflows. The core innovation is a page-indexed memory system using manifest-guided retrieval, where agents navigate a hierarchical organization of longitudinal patient records (patient → admission → document) by reading human-readable manifest summaries instead of relying on vector similarity. This approach aims to enhance precision and recall for complex clinical queries while ensuring safety through OS-level isolation and document-centric coordination.

The system is evaluated on 100 MIMIC-IV patient records with 300 clinical queries. The manifest-guided retrieval matches the metadata-filtered RAG baseline in recall (0.877) but yields 2.2× higher precision (0.779 vs 0.352). For tier-3 queries requiring reasoning across multiple admissions, manifest recall is 21% higher (0.846 vs 0.701). The architecture also features inter-agent coordination via structured document writes and event subscriptions, and enforces least-privilege execution using Linux user/namespace/seccomp barriers.

## Method Summary
The authors build a longitudinal EHR corpus from MIMIC-IV v2.2, selecting 100 patients with at least three admissions and six document types per admission. Records are organized into a patient/admission/leaf hierarchy in Markdown, with YAML provenance headers. For each internal node, a manifest file (Markdown table) is generated with LLM-produced "Scope" summaries based on metadata and content.

Queries are automatically created using the same LLM (Kimi K2.5) and stratified into three tiers: (1) single-document queries, (2) 2–3 documents within one admission, (3) ≥2 admissions. Gold evidence sets are built by iterative LLM sufficiency checks and expansion via manifests. Three retrieval systems are compared: (1) Manifest-guided navigation (agent selects admissions and documents by reading manifests), (2) flat RAG (chunked embeddings), (3) RAG-AF (flat RAG with admission metadata filtering). Retrieved documents are fed to an LLM to generate answers, which are scored by an LLM judge on a 1–5 scale against gold answers.

## Key Results
- Overall recall: manifest 0.877 vs RAG-AF 0.876; precision: 0.779 vs 0.352 (2.2× higher); fewer retrieved documents on average.
- On tier-3 (multi-admission) queries: manifest recall 0.846 vs RAG-AF 0.701 (21% higher).
- Manifest achieves higher precision across all tiers, demonstrating effectiveness for longitudinal reasoning.

## Why This Works (Mechanism)

### Mechanism 1: Manifest-guided hierarchical navigation
**Claim:** Retrieves clinically relevant longitudinal evidence with higher precision than flat vector retrieval by leveraging document structure and LLM reasoning.  
**Mechanism:** Records are organized into a tree (patient/admission/document). At query time, an agent iteratively reads human-readable manifest summaries (generated by an LLM) at each level, selecting which child subtrees to descend into. This replaces embedding similarity with language reasoning to disambiguate temporal and structural context.  
**Core assumption:** An LLM can reliably interpret concise manifest scope descriptions to make correct navigation decisions about which clinical episodes and document types are relevant.  
**Evidence:** Abstract metrics (precision 2.2× higher, tier-3 recall +21%), Section 3.2 (formal description), Section 4.2/Table 2 (tier-3 results), and corpus evaluation on 100 MIMIC-IV records.  
**Break condition:** Stale, inaccurate, or non-distinguishing manifest descriptions cause navigation errors (e.g., 13 tier-1 failures).

### Mechanism 2: Inter-agent coordination via document writes and events
**Claim:** Mediating communication exclusively through structured document writes and event subscriptions yields a verifiable, auditable, and safe channel without direct messaging.  
**Mechanism:** Agents have scoped write access to specific document subtrees. Each write generates an append-only mutation event with versioning. An event broker dispatches events to subscribed agents, enabling reactive workflows. Safety and ordering are enforced via filesystem leases (atomic mkdir) that serialize writes per patient.  
**Core assumption:** File-system-level operations and notifications suffice for all necessary clinical coordination patterns and can be secured/audited via OS tools.  
**Evidence:** Section 3.1 (design of mutation model and concurrency control), Section 3.4 (argument that safety is delegated to OS auditd/inotify). The mechanism is a proposed component; evaluation focused on retrieval, not coordination.  
**Break condition:** High contention for a patient-level lock could cause timeouts or serialization bottlenecks.

### Mechanism 3: OS-level least-privilege execution
**Claim:** Enforcing isolation via Linux user/namespace/seccomp provides stronger and more auditable safety than model-level instruction-following for containing agent actions.  
**Mechanism:** Each agent role runs in an isolated namespace under a dedicated OS user. The permitted interface is restricted to reading/writing within assigned file paths via standard permission bits and MAC frameworks (AppArmor/SELinux). Direct network access, arbitrary code execution, and privilege escalation are blocked at the kernel level.  
**Core assumption:** Security properties derived from mature OS primitives are more robust and easier to audit than application-layer sandboxing or prompt-based constraints.  
**Evidence:** Abstract, Sections 3.1 & 3.4 (mapping to Linux primitives), and comparative rationale versus permissive frameworks. This is an architectural proposal; no experimental security validation reported.  
**Break condition:** Misconfiguration of OS policies or a kernel vulnerability could break isolation; harmful content within permitted write scope remains possible.

## Architecture Onboarding

**Component map:**  
Agents ↔ Document Store (hierarchical pages + manifests)  
Agents → Medical Skills Library (invoke pre-audited modules)  
Document Store mutations → Event Broker → Agents (subscriptions)  
OS Enforcement Layer (Linux users, namespaces, seccomp, auditd) sandboxes all agents

**Critical path (for a query):**  
1. Query received by agent (e.g., clinician agent).  
2. Agent performs manifest-guided retrieval: reads patient-level manifest → selects relevant admission manifests → selects relevant document pages.  
3. Agent reasons over retrieved pages.  
4. Agent may invoke one or more skills (e.g., `ANALYZE_LONGITUDINAL_TREND`).  
5. Agent writes result to a document (e.g., risk assessment page).  
6. Write triggers mutation event → Event Broker notifies subscribed agents (e.g., care management agent).

**Design tradeoffs:**  
- **Precision vs. Recall:** Deeper manifest traversal increases recall but may load more non-gold documents, reducing precision; system uses tier-specific depth bounds.  
- **Safety vs. Throughput:** Coarse-grained per-patient filesystem locks ensure consistency but serialize all writes for a given patient, potentially creating bottlenecks for high-activity cases.  
- **Static vs. Dynamic Structure:** The hierarchy is institution-defined (patient/admission); finer-grained navigation (e.g., by document type) could improve precision but adds complexity to manifest generation.

**Failure signatures:**  
- **Stale/Inaccurate Manifests:** Missed navigation targets or incorrect subtree selection, especially after rapid document mutations; manifests update incrementally on events; a missed event leads to drift.  
- **Lock Contention/Timeout:** Agent reasoning cycles fail to acquire patient lease within timeout, indicating too many concurrent write attempts; logs show repeated `mkdir` failures on lease directory.  
- **Metadata Gap for Tier-3 Queries:** Query text lacks explicit admission identifiers; manifest navigation fails to select correct cross-admission episodes, leading to low recall (observed in RAG-AF baseline).

**First 3 experiments:**  
1. **Simple retrieval sanity check:** Construct a minimal test patient with 2 admissions, 3 documents total. Issue a Tier-1 query referencing a specific document type in a specific admission. Verify the manifest navigator retrieves exactly 1 document (the target) and that the trace shows correct L1 and L2 selections.  
2. **Mutation & event propagation:** Have a patient agent write a new vital-sign summary page. Verify: (a) the patient's admission manifest is updated automatically, (b) a mutation event is logged, (c) a subscribed clinician agent receives the notification and triggers its next reasoning cycle.  
3. **OS isolation verification:** Attempt to have a "patient agent" process (running under its designated Unix user) read a file outside its assigned `S{id}` directory or make an outbound network call. Confirm the operation is blocked by the filesystem permission or seccomp filter.

## Open Questions the Paper Calls Out

### Open Question 1: Manifest accuracy under high-frequency updates
**Question:** How do inaccuracies or staleness in LLM-generated manifest descriptions impact the reliability of progressive disclosure retrieval in high-frequency, real-time clinical environments (e.g., ICU)?  
**Basis in paper:** The paper notes that manifest descriptions are LLM-generated and susceptible to inaccuracy, omission, or temporal drift; a high-frequency update environment (e.g., ICU sensor data) may stress the O(L) LLM-call-per-update budget.  
**Why unresolved:** The evaluation used a static corpus reconstruction; behavior under continuous, real-world document mutation rates and resilience to manifest update failures remain unknown.  
**What evidence would resolve it:** A longitudinal stress-test on a simulated high-throughput ICU data stream, measuring retrieval accuracy decay against a manually audited ground truth as manifest update latency or failure rates are varied.

### Open Question 2: Concurrency control throughput
**Question:** Can the coarse-grained patient-level filesystem lease concurrency control be replaced with a finer-grained, higher-throughput mechanism (e.g., document-level or operation-type locking) while preserving the same safety and auditability guarantees?  
**Basis in paper:** The paper acknowledges that the current design serializes write-producing reasoning cycles at the patient level, which may reduce throughput, and suggests evaluating finer-grained locking.  
**Why unresolved:** No empirical data on contention under realistic multi-agent workloads or formal analysis of alternative policies is provided.  
**What evidence would resolve it:** A simulation or experimental deployment modeling a busy hospital ward with multiple competing agents, comparing the current lease model against candidate finer-grained policies on metrics like average operation latency, deadlock incidence, and audit trail completeness.

### Open Question 3: EHR integration challenges
**Question:** What are the specific architectural and operational challenges in creating a robust bidirectional synchronization layer between the proposed document-centric store and mainstream commercial EHRs (e.g., Epic, Cerner) that use HL7 FHIR?  
**Basis in paper:** The design of bidirectional synchronization with existing EHR infrastructure is beyond the scope; hospital data exists in HL7 FHIR-compliant formats that would need translation.  
**Why unresolved:** The architecture assumes data originates within its managed hierarchy. The practicalities of mapping between a mutable, manifest-indexed document tree and the transactional, API-driven FHIR resource model (including conflict resolution, provenance tracking, and change data capture) are unaddressed.  
**What evidence would resolve it:** A prototype integration layer specification and proof-of-concept demonstrating consistent, lossless synchronization of a core FHIR resource set (e.g., Condition, MedicationRequest, Observation) with the document hierarchy, including handling of concurrent edits and preservation of audit trails.

### Open Question 4: Model dependence
**Question:** To what extent do the observed performance advantages of manifest-guided retrieval depend on the specific capabilities of the Kimi K2.5 LLM, and how do they generalize to other model families or open-source models?  
**Basis in paper:** The evaluation uses a single LLM (Kimi K2.5) for all roles; the paper notes that cross-model evaluation and human clinical expert review remain necessary.  
**Why unresolved:** All critical LLM calls (navigation, judgment, gold-label production) used the same model, risking capability confounds and judge bias. The robustness of the manifest navigation strategy to models with differing reasoning or instruction-following fidelity is unknown.  
**What evidence would resolve it:** A replication study using at least two additional, architecturally distinct LLMs (e.g., a strong open-weight model and a different API provider) for all roles, measuring variance in navigation decisions, retrieval metrics, and final answer quality.

### Open Question 5: Precision-recall trade-off for tier-3 queries
**Question:** Can the precision-recall trade-off for longitudinal (tier-3) queries be improved by introducing a secondary, LLM-guided filtering stage within a selected admission, beyond the current document-level manifest?  
**Basis in paper:** The analysis notes manifest's "over-retrieval on tier-3 queries" and suggests finer-grained navigation (e.g., document-type filtering within admissions) could mitigate this effect; the current system descends only to the document level within an admission.  
**Why unresolved:** The paper identifies document-type ambiguity as a failure mode (e.g., selecting `triage.md` over `discharge_summary.md` for chief complaint) but does not implement or test any intra-admission filtering.  
**What evidence would resolve it:** An ablation extending the manifest hierarchy with an optional third level (e.g., section-level manifests within a document) or an LLM re-ranking step post-admission selection, evaluated specifically on the tier-3 query set for changes in precision without significant recall loss.

## Limitations
- **Reproduction gaps:** Exact LLM prompts, hyperparameters (temperature, top_p), and the Kimi K2.5 model itself are not specified; the embedding model (text-embedding-v4) is proprietary; admission-ID extraction method for RAG-AF is unclear. These unknowns block faithful reproduction.
- **Experimental scope:** Security and coordination claims lack empirical validation. The evaluation focuses on retrieval accuracy, not on safety, throughput, or real-time performance under load.
- **Corpus construction:** The gold answer set involved manual correction with vague criteria; potential noise may affect metrics. The de-identification density filter is not concretely defined.

## Confidence
- **Manifest-guided retrieval effectiveness:** Medium. Supported by MIMIC-IV results, but dependent on unverified LLM behavior and corpus construction details.
- **Document-centric agent coordination:** Low. Purely design-based; no throughput/latency or contention data.
- **OS-level safety guarantees:** Low. Relies on correct policy configuration; no adversarial security testing reported.
