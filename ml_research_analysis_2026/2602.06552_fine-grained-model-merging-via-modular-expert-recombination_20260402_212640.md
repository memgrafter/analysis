# Fine-Grained Model Merging via Modular Expert Recombination
## Quick Facts
- arXiv ID: 2602.06552
- Source URL: https://arxiv.org/abs/2602.06552
- Reference count: 40
- Primary result: MERGE achieves near-original model accuracy while drastically reducing storage overhead compared to naive merging, and improves unseen task accuracy by 1.3–4.2%.

## Executive Summary
MERGE introduces a framework for fine-grained model merging that decomposes models into reusable modular experts. By formulating merging as a bi-objective optimization balancing performance and storage, and employing a surrogate-assisted evolutionary search, MERGE constructs a library of experts that can be dynamically recombined via a routing network for each input. This approach overcomes limitations of instance-specific merging and component heterogeneity, demonstrating strong performance on Vision Transformer and RoBERTa models with storage overhead as low as ~1.7× versus 8× for conventional methods, and reducing the gap to task-specific models on unseen tasks from 7.3% to under 2.1%.

## Method Summary
The method begins by decomposing pre-trained models into homologous components (e.g., attention heads, feed-forward layers). These components are treated as candidate “experts.” A bi-objective optimization problem is defined: maximize task performance (accuracy) while minimizing storage cost (number of parameters). To solve this, a surrogate model predicts performance of expert combinations, and an evolutionary search explores the space of modular expert libraries. The resulting library is compact and reusable. During inference, a lightweight routing network selects and combines the appropriate experts from the library based on the input, enabling dynamic adaptation without full model retraining.

## Key Results
- On ViT-B/32, MERGE achieves 90.2% accuracy vs. 90.5% for the original model, using only ~1.7× storage (vs. 8× for naive merging).
- On RoBERTa, storage‑minimal MERGE solutions outperform baseline merging methods at ~30% storage and improve accuracy on unseen tasks by 1.3–4.2%.
- The gap to task‑specific models on unseen tasks is reduced from 7.3% to less than 2.1%.

## Why This Works (Mechanism)
MERGE works because it separates the concerns of model capacity (experts) and input‑dependent routing, allowing the system to allocate only the necessary parameters per input. The modular decomposition ensures that experts are homogeneous and thus combinable. The bi‑objective optimization explicitly trades off performance and storage, while the surrogate‑assisted evolutionary search efficiently navigates the combinatorial space of expert selections, yielding libraries that are both high‑performing and compact. The routing network dynamically composes experts, enabling adaptation to diverse tasks without storing full copies of merged models.

## Foundational Learning
- **Model Merging**: Combining parameters of multiple models to create a single multitask model. *Why needed*: Prior merging approaches produce instance‑specific models that cannot be reused. *Quick check*: Can we merge without sacrificing per‑task accuracy?
- **Modular Neural Networks**: Networks composed of interchangeable modules. *Why needed*: Enables recombination of components. *Quick check*: Are modules sufficiently independent?
- **Bi‑Objective Optimization**: Simultaneously optimizing two conflicting objectives. *Why needed*: Balances accuracy and storage. *Quick check*: Does the Pareto frontier contain acceptable trade‑offs?
- **Surrogate Modeling**: Replacing expensive evaluations with a learned predictor. *Why needed*: Reduces computational cost of search. *Quick check*: Is surrogate error low enough to guide search?
- **Evolutionary Algorithms**: Population‑based search for combinatorial optimization. *Why needed*: Explores large discrete spaces. *Quick check*: Does the algorithm converge to diverse solutions?
- **Routing Networks**: Networks that select or weight modules per input. *Why needed*: Enables dynamic composition. *Quick check*: Does routing add negligible overhead?

## Architecture Onboarding
**Component map**: Model Decomposition -> Expert Library -> Routing Network -> Merged Output

**Critical path**:  
1. Input is processed by the routing network.  
2. Routing network selects a subset of experts from the library.  
3. Selected experts are combined (e.g., concatenated, averaged) to form the effective model for that input.  
4. Output is produced.

**Design tradeoffs**:  
- *Storage vs. performance*: Larger expert library increases coverage but also storage. The bi‑objective search finds a Pareto front.  
- *Routing complexity*: More experts increase routing computation; the routing network is kept lightweight.  
- *Homology constraint*: Decomposition requires components to be structurally similar; this limits applicability to architectures with similar layers.

**Failure signatures**:  
- *Performance drop*: If the expert library lacks diversity, routing cannot cover task variations.  
- *High storage*: Inefficient search may produce unnecessarily large libraries.  
- *Routing bottlenecks*: If routing network is too shallow, it may select suboptimal experts.  
- *Vanishing gradient*: When training the routing network, gradients may not propagate effectively through expert selection.

**First experiments**:  
1. Replicate the bi‑objective search on a small dataset (e.g., CIFAR-10) to validate the Pareto frontier.  
2. Ablate the surrogate model by comparing search time and solution quality with and without it.  
3. Test the routing network’s decision accuracy by measuring how often it selects the optimal expert combination given ground‑truth task labels.

## Limitations
- Evaluation is limited to a single vision transformer (ViT‑B/32) and a single language model (RoBERTa), raising concerns about generalizability.  
- The computational cost and scalability of the surrogate‑assisted evolutionary search are not quantified.  
- Improvements on unseen tasks are based on a narrow benchmark without statistical significance testing, risking selection bias.

## Confidence
- *Methodological novelty*: Medium – well described but lacking independent replication and broad baselines.  
- *Performance‑storage trade‑off on seen tasks*: Low – based on single‑model experiments without error bars; limited community validation.  
- *Generalization to unseen tasks*: Low – supported by narrow benchmarks; possible overfitting.

## Next Checks
1. Replicate experiments on at least two additional model families (e.g., ResNet, GPT-2) and multiple datasets to test generalizability.  
2. Measure and report end‑to‑end training/inference time and memory footprint of the routing network and expert storage for practical deployability.  
3. Conduct statistical significance tests (e.g., multiple runs with variance estimates) and ablate the contributions of the surrogate model and evolutionary search.
