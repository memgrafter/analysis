# CLAG: Adaptive Memory Organization via Agent-Driven Clustering for Small Language Model Agents
## Quick Facts
- **arXiv ID**: 2603.15421
- **Source URL**: https://arxiv.org/abs/2603.15421
- **Reference count**: 40
- **Primary result**: Agent-driven clustering overcomes knowledge dilution in SLM agents, yielding large F1 gains (e.g., Qwen-0.6B: LoCoMo 12.9 → 20.99) and robust retrieval without added latency.

## Executive Summary
Small language model agents suffer from irrelevant context when using a single global memory pool, leading to knowledge dilution and poor reasoning. CLAG addresses this by organizing memories into semantic clusters generated and maintained by the agent itself. A lightweight router assigns new memories to existing clusters or creates new ones, each described by a concise profile. Retrieval is two-stage: first selecting relevant clusters, then retrieving memories within them. Across three QA datasets and three SLM backbones, CLAG consistently improves answer quality and retrieval robustness while maintaining low latency compared to prior agentic memory systems.

## Method Summary
CLAG implements an agent-driven clustering memory system without any training; all decisions (routing, profile generation, evolution) reuse the same SLM backbone with role-specific prompts. Memory is stored as structured notes containing content, cluster ID, timestamp, keywords, tags, context, and links. The system initializes clusters via K-Means on an initial buffer. Online routing uses an embedding-based coarse filter (kroute=3 nearest clusters) followed by an SLM selection prompt; a cosine similarity threshold (τ=0.1) triggers new cluster creation. Adaptive splitting occurs when a cluster exceeds τsplit=300 memories. Upon memory insertion, localized evolution finds klocal=5 nearest neighbors in the same cluster and uses the SLM to generate links and rewrite neighbor contents. Retrieval first selects Kstage1=3 candidate clusters by centroid proximity and SLM judgment, then retrieves the top kretrieve=10 memories from those clusters by similarity. This design confines reasoning to semantically coherent neighborhoods and reduces noise.

## Key Results
- Substantial F1 gains on three QA benchmarks: e.g., Qwen-0.6B on LoCoMo (12.9 → 20.99), HotpotQA (11.75 → 15.50), BioASQ (2.4 → 22.01).
- Retrieval robustness dramatically improved on BioASQ: E-F1 25.11 vs. RAG’s 2.29.
- Latency remains low relative to prior agentic systems like A-mem and MemoryOS.

## Why This Works (Mechanism)
CLAG succeeds by containing the spread of irrelevant information. A global memory pool lets unrelated notes accumulate, forcing the agent to sift through noise during retrieval. By clustering memories around coherent topics and maintaining cluster profiles, CLAG narrows the search space both during storage (routing) and retrieval (cluster selection). Localized evolution further refines cluster contents incrementally, preventing dilution within a cluster. The two-stage retrieval (clusters then memories) acts as a coarse filter before expensive similarity search, improving precision and speed. The router’s embedding pre-filter and adaptive splitting maintain cluster coherence as memory grows.

## Foundational Learning
- **Semantic clustering**: Groups memories by topic to limit context scope. *Why needed*: Prevents knowledge dilution in a single pool. *Quick check*: Verify cluster centroids align with coherent themes across sampled notes.
- **Agent-driven routing**: Uses the SLM itself to assign memories, avoiding fixed embedding thresholds. *Why needed*: Leverages model understanding for soft semantic matches. *Quick check*: Inspect routing decisions; test with ambiguous entities that could belong to multiple clusters.
- **Localized evolution**: Updates only neighbors within the same cluster when adding a memory. *Why needed*: Refines a cluster’s knowledge without global interference. *Quick check*: Compare neighbor content before/after insertion; ensure updates stay on-topic.
- **Two-stage retrieval**: First select clusters, then memories. *Why needed*: Reduces the pool for final similarity search, cutting noise and latency. *Quick check*: Measure recall of gold memories in Stage1-selected clusters vs. global search.
- **Adaptive splitting**: Bisects oversized clusters to maintain granularity. *Why needed*: Prevents a single cluster from becoming a catch-all. *Quick check*: Track cluster size distribution over time; verify split clusters form distinct sub-topics.
- **Profile-based selection**: Cluster summaries guide Stage1 retrieval. *Why needed*: Provides a compressed, semantic view for coarse filtering. *Quick check*: Evaluate whether selected clusters for a query match its main entities/topic.

## Architecture Onboarding
A -> B -> C: Memory encoder -> Routing (embedding coarse filter + SLM selector) -> Cluster storage (with profile) -> Localized evolution (neighbor update) -> Two-stage retrieval (SLM cluster selector + similarity search) -> Answer generation.
Critical path: Memory insertion (routing -> evolution) and retrieval (Stage1 cluster selection -> Stage2 memory fetch).
Design tradeoffs: Routing uses embedding pre-filter to reduce SLM calls but may miss borderline clusters; evolution only updates 5 neighbors for efficiency but may miss more distant relevant notes; Stage1 uses only 3 centroids for speed but risks missing the best cluster if the query is atypical.
Failure signatures: 1) High entity confusion (46% of failures) indicates router misassignment. 2) Temporal reasoning failures (19%) show profiles lack time cues. 3) Extreme cluster counts (e.g., >40) indicate poor threshold settings. 4) Empty Stage1 selection suggests prompt or Kstage1 too strict.
First three experiments: 1) Run on LoCoMo with Qwen-0.6B; target F1 ≈20.99. 2) Vary τ_split (150, 300, 600) and measure cluster count/size distribution and F1 stability. 3) Profile ablation: disable evolution on BioASQ; expect sharp drop in E-F1.

## Limitations
- Missing exact prompt templates for evolution and link generation (Eqs. 3–4), risking implementation divergence.
- Embedding storage details (update schedule, vector backend, normalization) unspecified, affecting retrieval consistency.
- Granularity of cluster “representative snippets” for profiles and retrieval prompts is unclear.
- No memory deletion/decay mechanism described; long-term scalability unvalidated.
- Evaluation limited to three QA datasets; applicability to other agent tasks unknown.
