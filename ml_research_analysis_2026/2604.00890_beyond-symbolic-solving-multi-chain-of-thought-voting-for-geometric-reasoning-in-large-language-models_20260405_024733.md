# Beyond Symbolic Solving: Multi Chain-of-Thought Voting for Geometric Reasoning in Large Language Models

## Quick Facts
- arXiv ID: 2604.00890
- Source URL: https://arxiv.org/abs/2604.00890
- Reference count: 40
- Primary result: MARS-GPS achieves 88.8% accuracy on Geometry3K, an 11.0 percentage point improvement over prior SOTA without any training.

## Executive Summary
Geometric problem solving requires integrating diagrammatic understanding, symbolic manipulation, and logical inference. Existing methods often rely on a single chain-of-thought and underdeveloped logical inference. This paper introduces MARS-GPS, an inference-time framework that generates multiple parallel reasoning rollouts from a frozen large language model, augmented with Python code execution for numerical verification. Rollout confidence is estimated via token-level entropy, and answers are aggregated through a multi-stage pipeline of majority voting, entropy-ranked self-verification, and weighted fallback. Without any training, MARS-GPS achieves 88.8% accuracy on Geometry3K (11.0 pp improvement over prior SOTA) and 77.48% on PGPS9K (nearly 8% higher than Pi-GPS). Accuracy scales log-linearly with the number of rollouts (k=1 to 16).

## Method Summary
MARS-GPS operates in three stages. **Parsing**: A rule-based text parser and PGDPNet diagram parser extract logical predicates from the problem statement and diagram, respectively, and merge them into a unified formal context F*. **Inference**: A frozen LLM (GPT-OSS 120B) generates k parallel CoT rollouts from a prompt constructed from F*. During each rollout, Python code blocks are executed in a sandbox, and outputs are injected back into the context. **Aggregation**: For each rollout, the final answer (boxed) and mean token entropy are extracted. A six-step pipeline selects the final answer: (1) early consensus if any answer receives >k/2+1 votes, (2) hard accept if any answer receives ≥k/2 votes, (3) candidate selection of answers with ≥k/4 votes, (4) entropy-ranked self-verification via a zero-temperature LLM query, and (5) if all candidates are rejected, weighted fallback using λ·votes(a) - (1-λ)·mean_entropy(a).

## Key Results
- 88.8% accuracy on Geometry3K, a 11.0 percentage point improvement over prior SOTA.
- Accuracy scales log-linearly with rollouts (k=1→16), from 82.0% to 88.8%.
- 77.48% on PGPS9K, nearly 8% higher than Pi-GPS.
- Ablation: self-verification +4.5 pp, code augmentation +2.5 pp, entropy-weighted voting +2.0 pp over majority.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Sampling multiple parallel reasoning rollouts from a frozen LLM mitigates single-path failure by aggregating over independent stochastic traces.
- **Mechanism:** The system generates \(k\) independent CoT traces from the same prompt and formal context \(F^*\). Errors in individual rollouts are assumed to be somewhat independent, so majority or weighted voting can identify the correct answer if it appears more frequently than errors.
- **Core assumption:** Independent rollouts will exhibit variance in correctness; the correct answer is more likely to be reproduced across samples than any specific error pattern.
- **Evidence anchors:**
  - [abstract] "generates multiple parallel reasoning rollouts... aggregates answers through a multi-stage pipeline of majority voting"
  - [section 3.3.1] "We sample \(k\) independent rollouts in parallel... The final answer \(\hat{a}\) is selected from \(\{\hat{a}_1, \ldots, \hat{a}_k\}\) via a parallel voting strategy"
  - [corpus] Neighboring papers (e.g., Logic-LM, Faithful Logical Reasoning) also use multi-path consistency, but MARS-GPS applies this specifically to multimodal geometric reasoning without training.
- **Break condition:** If all rollouts share a systematic bias (e.g., misinterpreting \(F^*\), or a flawed prompt), voting reinforces rather than corrects the error. Anecdotal evidence: errors on problems requiring auxiliary constructions (section 6) show correlated failures.

### Mechanism 2
- **Claim:** Token-level entropy provides a cost-free, calibrated confidence signal to prioritize candidate answers for verification and weighting.
- **Mechanism:** For each rollout \(r_i\), compute mean Shannon entropy over token probabilities. Lower mean entropy \(\bar{H}_i\) indicates higher model confidence. This score ranks candidates for self-verification (most confident first) and weights votes in the fallback step.
- **Core assumption:** Per-token entropy correlates with the reliability of the final answer; more confident generations are more likely correct.
- **Evidence anchors:**
  - [abstract] "ranks them using token-level entropy as a confidence signal"
  - [section 3.3.2] "VLMs return per-token log probabilities... \(\bar{H}_i\) serves as an inverse confidence score"
  - [section 5.2] Ablation shows entropy-weighted voting outperforms majority voting by 2.0 pp.
  - [corpus] Weak direct evidence; neighboring works (e.g., IFDNS) use iterative feedback but not entropy. Assumption: entropy-confidence link from general LLM calibration literature, not fully proven in this geometry-specific context.
- **Break condition:** If the LLM is miscalibrated—overconfident on incorrect reasoning or underconfident on correct paths—entropy ranking misprioritizes candidates. The paper does not validate entropy-accuracy correlation per problem type.

### Mechanism 3
- **Claim:** Augmenting reasoning with executable Python code for numerical steps reduces arithmetic and formula application errors.
- **Mechanism:** During a rollout, when the LLM emits a code block, it is executed in a sandbox \(E\); the output is injected back into the context. This offloads exact computation (e.g., square roots, algebraic solving) from token prediction to deterministic execution.
- **Core assumption:** LLMs are unreliable at precise numerical computation, but can correctly generate code for such tasks when prompted.
- **Evidence anchors:**
  - [abstract] "augmented with Python code execution for numerical verification"
  - [section 3.3.3] "each rollout \(r_i\) is paired with a sandbox instance \(E\)... near 40% of rollouts invoke \(E\)"
  - [section 5.2] Removing code augmentation drops accuracy by 2.5 pp (87.5% → 85.0%). Problems that attempted code but were blocked had 75% accuracy vs. 92.2% for those that didn't attempt.
  - [section E] Table 4: problems with 6+ code calls drop to 60% accuracy without sandbox, indicating heavy computational cases suffer most.
  - [corpus] Neighbors (e.g., MathCoder) integrate code for math; this work shows specific benefit for geometry.
- **Break condition:** If the LLM generates incorrect code (syntax errors, wrong formula) or misinterprets the output, the numerical result remains wrong. The sandbox only ensures faithful execution, not correct code generation.

## Foundational Learning
- **Concept: Chain-of-Thought (CoT) Prompting**
  - *Why needed here:* MARS-GPS extends single CoT into multiple parallel rollouts. Understanding standard CoT is prerequisite to grasp why sampling multiple traces improves robustness.
  - *Quick check question:* How does sampling temperature \(\tau > 0\) during CoT generation increase diversity of reasoning paths?
- **Concept: Token-level Probability and Entropy in LLMs**
  - *Why needed here:* The confidence signal relies on per-token log probabilities. Engineers must understand how to compute entropy from softmax probabilities and why lower average entropy may indicate higher certainty.
  - *Quick check question:* Given a token's log probabilities \(\ell_j\) over vocabulary, write the formula for Shannon entropy \(H_t\). How does a sharper distribution (one high-probability token) affect \(H_t\)?
- **Concept: Code Interleaving in LLM Reasoning**
  - *Why needed here:* The system integrates Python execution mid-reasoning. This requires designing prompts that reliably trigger code blocks and handling sandbox injection.
  - *Quick check question:* What are the risks of allowing an LLM to write and execute arbitrary code in a reasoning pipeline? How does a sandbox mitigate them?

## Architecture Onboarding
- **Component map:** Parsing (rule-based text parser + PGDPNet) → Unified formal context F* → k parallel rollouts with Python sandbox → Confidence estimation (mean token entropy) → Multi-stage aggregation (early consensus, hard accept, candidate selection, entropy-ranked self-verification, weighted fallback)
- **Critical path:**
  1. Input (T, I) → parsing → F*.
  2. F* → construct P → parallel rollout sampling (thread pool, batched inference).
  3. Per-rollout: stream tokens with logprobs, detect code → execute → inject output.
  4. Extract answer \(\boxed{N}\), compute \(\bar{H}_i\).
  5. Aggregate answers: voting thresholds → entropy ranking → self-verify → weighted fallback.
  6. Output final a*.
- **Design tradeoffs:**
  - Rollout count k: Accuracy scales log-linearly, but cost linear. k=8 chosen; k=16 gives diminishing returns (+0.5 pp).
  - Voting strategy: Entropy-weighted (λ=0.7) beats majority by 2.0 pp but requires reliable entropy estimation.
  - Self-verification: Largest gain (+4.5 pp) but adds latency; implemented only on candidates to limit cost.
- **Failure signatures:**
  - Parsing errors: PGDPNet or text parser produce incorrect/missing predicates → F* flawed → all rollouts fail. Mitigation: accept only problems with high parser confidence; no recovery downstream.
  - Homogeneous rollouts: All k traces produce same wrong answer (e.g., due to prompt bias). Then voting reinforces error. Early consensus may accept wrong answer unanimously.
  - Verification rejection: Self-verification may incorrectly label correct answer as WRONG, especially if rollouts used complex constructions. Fallback triggered rarely (<8%) but can produce wrong answer if weighted scoring fails.
- **First 3 experiments:**
  1. **Scaling experiment:** Vary k ∈ {1,2,4,8,16} on a fixed subset (Geometry3K). Plot accuracy vs. k; expect log-linear rise. Confirm diminishing returns beyond k=8.
  2. **Code ablation:** Disable Python sandbox. Compare accuracy on problems that attempted code vs. those that didn't. Expect large drop on code-reliant problems (Table 3,4). Also measure execution time difference.
  3. **Voting strategy comparison:** Implement majority voting, entropy sorting, entropy-weighted voting. Keep all else fixed (k=8, code enabled). Expect entropy-weighted to outperform others by ~2 pp (Fig 2a). Also check how often fallback is triggered under each.

## Open Questions the Paper Calls Out
1. How can MARS-GPS be made robust to errors in the initial diagram parsing stage (PGDPNet), given that incorrect or incomplete formal representations F∗ cannot be recovered by downstream reasoning regardless of the number of rollouts?
2. What architectural modifications are necessary to extend MARS-GPS beyond multiple-choice geometry problems to open-ended answer generation or formal theorem proving tasks in environments like Lean or Coq?
3. What explains the observed log-linear scaling of accuracy with the number of parallel rollouts (k) in geometric reasoning, and does this scaling law break down at higher k or for different problem subtypes?
4. Why does inference-time scaling via parallel rollouts yield the largest gains on moderately difficult geometry problems (3–5 reasoning steps) but fail to improve accuracy on the hardest problems (6+ steps with auxiliary constructions), and what complementary training-time improvements (e.g., fine-tuning on geometry data) could address this?
5. Does token-level mean entropy (used per-rollout confidence) optimally predict answer correctness, or could alternative confidence signals—such as rollouts' self-verification outcomes, consistency between intermediate steps, or answer-probability aggregation—improve the selection accuracy?

## Limitations
- Model substitution: GPT-OSS 120B is a placeholder with no public weights; substitute models may differ in CoT and code abilities.
- Parsing pipeline: PGDPNet diagram parser weights and exact text parser regexes are unavailable; may underperform claimed accuracy.
- Aggregation hyperparameters: Self-verification prompt, fallback λ, and voting thresholds are not numerically specified; entropy-confidence correlation lacks validation.

## Confidence
- Multi-rollout voting: High
- Entropy-weighted voting: Medium
- Code augmentation: High
- Self-verification: High
