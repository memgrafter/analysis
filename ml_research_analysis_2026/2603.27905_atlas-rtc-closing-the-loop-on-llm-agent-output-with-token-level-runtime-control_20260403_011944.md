# ATLAS-RTC: Closing the Loop on LLM Agent Output with Token-Level Runtime Control

## Quick Facts
- **arXiv ID:** 2603.27905
- **Source URL:** https://arxiv.org/abs/2603.27905
- **Reference count:** 15
- **Primary result:** Token-level runtime control improved first-attempt schema validity by +20pp and tool call success by +30pp, reducing latency by up to 88% in failure-dominated settings.

## Executive Summary
ATLAS-RTC is a runtime controller that干预s during LLM generation to prevent malformed outputs (e.g., broken JSON, invalid tool calls). It monitors each decoding step, detects structural drift via heuristic and learned signals, and applies graduated interventions (logit biasing, masking, rollback) before errors manifest. Without modifying model weights, it significantly improves first-attempt success rates on ambiguous structured outputs and reduces costly retry loops, though it faces challenges with complex schemas like multiline strings and when baseline validity is already high.

## Method Summary
ATLAS-RTC implements a closed-loop control system operating at the logit distribution during autoregressive decoding. It maintains a runtime state tracking generation progress against an output contract (e.g., JSON schema). A drift estimator combines heuristic signals (e.g., invalid token mass) with a lightweight learned classifier to compute a risk score per step. A graduated "ladder" policy maps this risk to one of six intervention levels, from no operation to rollback, applying the weakest effective correction. Control actions modify logits before sampling, and rollback truncates the KV cache to revert to a prior valid state. The system is stage-aware, enforcing strict constraints only at structural boundaries (e.g., delimiters) while relaxing them during value generation to preserve output quality.

## Key Results
- First-attempt schema validity on ambiguous structured outputs improved from 56.7% to 76.7% (+20 percentage points).
- Tool call success rate increased from 28.3% to 58.3% (+30 percentage points), recovering one task from 0% to 90%.
- Latency reduced by up to 88% in settings dominated by baseline failures by preventing invalid outputs early.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Prevents malformed outputs by intervening directly at the logit distribution during each decode step, before invalid tokens are sampled.
- **Mechanism:** A closed-loop controller observes generation state (tokens, entropy, contract progress), estimates drift risk (ρt), and applies a control signal (ut) to logits prior to sampling, modifying the token distribution in real-time.
- **Core assumption:** Structural violations manifest as detectable trajectory-level signals (e.g., entropy spikes, invalid token probability) before output completion, allowing pre-emptive correction.
- **Evidence anchors:** Abstract states operation "directly at the logit distribution"; Section 3.2/3.4 formalizes control loop `observe→predict→control→sample→update`; corpus shows neighbors lack closed-loop token-level control.

### Mechanism 2
- **Claim:** Performance gains stem from **stage-aware enforcement**, which avoids distorting the model's distribution during free-form value generation while strictly controlling structural decision points.
- **Mechanism:** The contract's stage machine (ct) gates interventions. Token allowlists are enforced only at structural transitions (e.g., after a key, before a delimiter); constraints are relaxed during value generation (e.g., string content).
- **Core assumption:** Uniform constraint application degrades output quality; selective enforcement preserves flexibility where structure is undetermined.
- **Evidence anchors:** Section 3.4: "Constraints are enforced aggressively during structural transitions... and relaxed during value generation." Section 3.10 notes uniform enforcement degrades quality; Section 4.5 reports degradation on multiline string schemas.

### Mechanism 3
- **Claim:** The **graduated intervention ladder** (six-level policy) minimizes unnecessary corrections by scaling intervention strength with estimated risk (ρt), preventing over-correction.
- **Mechanism:** Risk ρt = max(Dt, Ft) maps to interventions: noop → bias → temperature → mask → rollback. Low risk uses subtle biasing; high risk triggers aggressive masking/rollback.
- **Core assumption:** Most structural drift can be corrected with minimal intervention; severe divergence requires rollback, preserving model distribution.
- **Evidence anchors:** Section 3.7 describes escalations and "weakest effective intervention"; Section 3.8 notes rollback is rare (~0.8 per run) but critical; Section 4.5 shows latency reduction from lighter interventions.

## Foundational Learning
- **Concept: Autoregressive decoding & logits**  
  *Why needed:* ATLAS-RTC manipulates the logit distribution before sampling. Understanding `xt+1 ~ Softmax(zt)` is prerequisite to seeing how `zt + ut` changes probabilities.  
  *Quick check:* If a logit processor adds a large positive bias to one token's logit, how does its sampling probability relative to other tokens change?

- **Concept: JSON schema validation rules**  
  *Why needed:* The "output contract" enforces JSON syntax and required fields. Knowing what makes JSON valid/invalid (e.g., missing commas, braces, required keys) is core to understanding "structural drift."  
  *Quick check:* Is `{"name": "Alice", "age": 30}` a valid JSON object? Is `{"name": "Bob" "age": 25}` valid? Why or why not?

- **Concept: Token-level intervention techniques (biasing, masking)**  
  *Why needed:* The control actions (bias, mask, temperature) are the primitives. Knowing how adding to logits vs. setting token probability to zero vs. scaling temperature affects generation is key.  
  *Quick check:* What is the practical difference between applying a +2.0 logit bias to a token vs. using temperature=0.1 to sharpen the distribution?

- **Concept: Stage/state machines for structured generation**  
  *Why needed:* The contract's stage machine tracks progress through a schema (e.g., `start → key → value → delimiter`). Understanding state transitions is crucial for stage-aware control.  
  *Quick check:* For a two-key JSON object, what sequence of stages does the state machine traverse?

- **Concept: Drift detection via entropy and invalid token mass**  
  *Why needed:* Heuristic drift signals (Dt) include entropy spikes and mass on invalid tokens. These indicate when generation is veering off-contract.  
  *Quick check:* Why might a sudden increase in entropy during value generation indicate potential drift rather than creative expression?

## Architecture Onboarding
- **Component map:**  
  Runtime State Tracker -> Contract Module -> Drift Estimator -> Ladder Policy -> Logits Processor

- **Critical path:**  
  `Step t start` → Load `st-1`, get `zt` → Contract updates `ct` → Compute `ϕt` → Estimate `Dt`, `Ft` → Calculate `ρt` → Policy selects `ut` → Apply `ut` to `zt` → Sample `xt` → Update state → `Step t+1`.

- **Design tradeoffs:**  
  - **Stage awareness vs. Complexity:** Defining precise stage transitions for complex schemas is hard; errors cause inappropriate intervention.  
  - **Lightweight signals vs. Accuracy:** Heuristic + lightweight classifier is fast but misses semantic drift; richer signals (e.g., embeddings) would improve detection but increase latency.  
  - **Graduated control vs. brittleness:** Ladder thresholds are empirically tuned; fixed thresholds may not generalize across tasks/models.

- **Failure signatures:**  
  - **Preamble tokens:** Non-structured tokens ("Sure", "Here") appear before contract enforcement begins; early drift may be missed.  
  - **Schema incompleteness:** Valid JSON but missing required fields. ATLAS-RTC enforces syntax, not semantic completeness.  
  - **Multiline string failure:** Over-masking in long string values due to poor stage boundary definition.  
  - **Latency increase on complex tasks:** Repeated corrections and rollbacks add overhead when baseline is already struggling.

- **First 3 experiments:**  
  1. **Validate stage machine on simple JSON:** Prompt for `{"a": 1, "b": "text"}`. Verify `ct` transitions: `start` → `key ("a")` → `value (number)` → `delimiter (,)` → `key ("b")` → `value (string)` → `end`. Confirm masking only active on structural tokens (keys, delimiters, braces).  
  2. **Test ladder thresholds on ambiguous prompt:** Use prompt "Make a JSON with name and age". Intentionally cause drift (e.g., model emits preamble). Verify `ρt` rises, policy escalates from `bias` to `mask` before invalid token sampled. Check rollback triggers only on severe divergence (e.g., after multiple invalid tokens).  
  3. **Measure latency vs. baseline on high-failure task:** Run tool-call generation (e.g., `search` tool) for 50 trials each. Compare average latency and first-attempt success. Expect ~88% latency reduction if baseline produces long malformed outputs that ATLAS-RTC cuts short.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can semantic drift detection be integrated into ATLAS-RTC to prevent semantically invalid outputs?
- **Basis in paper:** [explicit] Authors state that semantic correctness remains an "open challenge" (Conclusion) and note that drift detection "does not yet capture semantic drift" (Limitations).
- **Why unresolved:** The controller relies solely on structural signals (e.g., syntax, entropy), so outputs may be syntactically valid but semantically incomplete or inconsistent.
- **What evidence would resolve it:** Augment the drift score with semantic features (e.g., embedding similarity to task intent) and evaluate on tasks where semantic errors dominate (e.g., send email tool), measuring improvement in first-attempt success.

### Open Question 2
- **Question:** Can the ATLAS-RTC control policy be learned from data to adaptively balance intervention strength and output fidelity?
- **Basis in paper:** [explicit] Future work identifies "Adaptive and Learned Control Policies" as a direction (Section 5.2), and the paper notes the current ladder policy uses "fixed thresholds and manually specified intervention rules" (Section 3.7).
- **Why unresolved:** Manual thresholds may not generalize across tasks or models; a learned policy could optimize the trade-off between validity and computational overhead.
- **What evidence would resolve it:** Train a reinforcement learning or imitation learning policy to map runtime state to intervention levels, using a reward combining validity and latency, and demonstrate superior performance on benchmark tasks compared to the fixed ladder.

### Open Question 3
- **Question:** Does ATLAS-RTC extend to long-horizon multi-step agent workflows, and what architectural modifications are required?
- **Basis in paper:** [explicit] Future work lists "Long-Horizon and Multi-Step Control" as a key direction (Section 5.2).
- **Why unresolved:** The system currently governs single-output generation; multi-step workflows introduce sequential dependencies, partial successes, and the need to carry contract state across steps.
- **What evidence would resolve it:** Extend ATLAS-RTC to maintain contract state across a sequence of tool calls, evaluate on a multi-step agent benchmark (e.g., AlfWorld), and report success rates and rollback efficiency relative to the single-step controller.

### Open Question 4
- **Question:** Why does ATLAS-RTC degrade on schemas requiring multiline string values, and how can the stage machine be adapted?
- **Basis in paper:** [explicit] The abstract and Section 5.1 report degradation on "schemas requiring multiline string values."
- **Why unresolved:** The stage machine and token allowlists likely mishandle newline tokens during multi‑token value generation, leading to over‑masking or missing valid paths.
- **What evidence would resolve it:** Profile token‑level interventions on multiline tasks, modify the contract to allow newlines in value‑generation stages, and measure recovery in first‑attempt validity and latency.

## Limitations
- Stage boundary detection fails on ambiguous schemas (e.g., multiline strings), causing over-masking.
- Drift estimator misses semantic errors (missing required fields), limiting to syntax enforcement.
- Overhead dominates when baseline validity is high; ladder thresholds may not generalize.

## Confidence
- **Token-level intervention:** Medium. Gains shown on specific tasks; long-form outputs untested.
- **Stage-aware enforcement:** Medium-High. Ablation evidence supports it, but complex schemas under-evaluated.
- **Graduated ladder:** Medium. Reduces over-correction but thresholds likely need per-task tuning.
