## Executive Summary
Vista introduces a scene-aware framework for streaming video question answering under post-hoc queries. It dynamically clusters incoming frames into coherent scenes, compresses each scene into a compact token stored in GPU memory, and offloads full frames to CPU storage. Upon query arrival, relevant scenes are selectively recalled from GPU memory to answer the question. This approach mitigates context loss and memory overflow issues in existing streaming methods. Integrated with LLaVA-OneVision-7B, Vista attains significant improvements on StreamingBench (e.g., +15.20 points Omni-Source Understanding) and long-video benchmarks (MLVU, EgoSchema) while scaling efficiently with input length.

## Method Summary
Vista processes a continuous video stream by grouping frames into scenes using an undisclosed clustering algorithm. Each scene is compressed into a single token (preserving essential visual-semantic information) and kept in GPU memory; the original frames are stored on CPU for potential retrieval. When a user query arrives after the stream, the system retrieves the most relevant scene tokens based on semantic similarity, optionally fetching full frames for detailed inspection, and feeds the selected context to a pre-trained multimodal large language model (LLaVA-OneVision) to generate an answer. The three core components—dynamic scene clustering, token-based compression, and selective recall—work together to maintain a bounded memory footprint and low latency even for hours-long streams.

## Key Results
- On StreamingBench, Vista+LLaVA-OneVision-7B reaches 50.30% Omni-Source Understanding (+15.20) and 74.00% Multimodal Alignment (+29.60) over the baseline.
- It outperforms other streaming models on MLVU (63.8%) and EgoSchema (58.7%).
- Memory usage and latency remain stable as input length increases; ablation confirms contributions of all three scene-aware components.

## Why This Works (Mechanism)
The scene-aware design reduces memory and computational demands by compressing long video histories into succinct tokens, avoiding the quadratic growth of attention costs in standard LLMs. Clustering frames into semantically coherent scenes ensures that each token captures a meaningful temporal unit, which improves the precision of relevant context retrieval. Selective recall focuses the LLM on the most pertinent scenes, minimizing distraction from irrelevant frames and thus boosting answer quality. Together, these mechanisms enable efficient, accurate QA over arbitrarily long streams.

## Foundational Learning
- **Streaming video processing**: Real-time frame ingestion without full-video buffering. *Why needed*: Traditional video QA assumes offline access, unsuitable for live streams. *Quick check*: Measure per-frame processing latency; must stay below frame interval.
- **Scene segmentation**: Grouping frames into temporally coherent segments with consistent semantics. *Why needed*: Provides semantic units for compression and retrieval. *Quick check*: Compare predicted scene boundaries against a small set of manual annotations (F1 score).
- **Memory-efficient tokenization**: Representing a scene as a single token (or few tokens). *Why needed*: LLMs have limited context windows; reduces memory/computation. *Quick check*: Plot QA accuracy vs. token budget; find knee point.
- **Selective context retrieval**: Fetching only relevant scenes for a query. *Why needed*: Avoids feeding the LLM with irrelevant frames that waste capacity. *Quick check*: Compute retrieval precision@k and correlate with final QA score.
- **Multimodal LLMs**: Models like LLaVA that handle both image and text. *Why needed*: Core reasoning engine linking visual scenes to language answers. *Quick check*: Zero-shot accuracy on a standard multimodal QA benchmark (e.g., VQAv2).

## Architecture Onboarding
### Component Map
Video Stream -> Scene Clustering -> Scene Token (GPU Memory) + Frame Archive (CPU) -> Query -> Scene Retrieval -> LLaVA-OneVision -> Answer

### Critical Path
1. Ingest video frame.
2. Update scene clustering (online).
3. Upon scene closure, compress to token and store in GPU; offload frames to CPU.
4. When query arrives, compute similarity between query and stored scene tokens.
5. Retrieve top-k relevant scene tokens (and optionally full frames).
6. Feed retrieved context to LLaVA-OneVision for answer generation.
7. Return answer to user.

### Design Tradeoffs
- **Compression vs. fidelity**: Higher compression saves memory but risks losing details needed for fine-grained QA.
- **Scene granularity**: Fine-grained scenes increase token count and retrieval precision but raise memory usage; coarse scenes reduce overhead but may mix distinct events, hurting retrieval relevance.
- **Retrieval budget**: Number of retrieved scenes trades off between providing sufficient context (recall) and keeping LLM input small (latency, cost).

### Failure Signatures
- **Memory blowup**: Unexpected growth in GPU memory indicates over-segmentation (too many scenes) or insufficient compression.
- **Cross-scene reasoning failure**: Drop in accuracy on queries requiring integration of multiple scenes suggests retrieval misses or fragmented context.
- **High query latency**: Latency spikes may stem from large retrieval sets or expensive LLM decoding due to too many tokens.

### First Experiments
1. **Memory scalability**: Stream a multi-hour video; monitor GPU memory. Expect flat memory after initial transient, confirming that memory depends on scene count, not video length.
2. **End-to-end QA replication**: Run Vista+LLaVA-OneVision-7B on StreamingBench; verify reported 50.30% Omni-Source Understanding (vs. baseline).
3. **Component ablation**: Systematically disable scene clustering, token compression, or selective retrieval (e.g., fallback to sliding window) and measure degradation in accuracy and memory efficiency.
