# CodeScout: Contextual Problem Statement Enhancement for Software Agents

## Quick Facts
- **arXiv ID:** 2603.05744
- **Source URL:** https://arxiv.org/abs/2603.05744
- **Reference count:** 40
- **Primary result:** A lightweight pre-exploration augmentation that resolves ~20% more software issues on SWEBench-Verified by transforming underspecified problem statements into comprehensive, actionable specifications.

## Executive Summary
CodeScout is a pre-processing framework that enhances underspecified software issue reports by performing lightweight, automated pre-exploration of the target codebase. It constructs a repository knowledge graph, performs high-level scoping to identify a bounded set of relevant code entities, carries out fine-grained contextual analysis on each, and synthesizes an augmented problem statement with reproduction steps, expected behavior, and targeted exploration hints. When fed to existing AI code agents (e.g., SWE-Agent, OpenHands), this augmented input leads to a 20% absolute improvement in issue resolution rates on the SWEBench-Verified benchmark, with gains consistent across multiple agent scaffolds and underlying LLMs. The approach reduces non-converging agent trajectories without modifying the agents' internal architectures.

## Method Summary
CodeScout operates as a three-stage pipeline applied to each task: (1) **Pre-exploration**: A static analysis pass builds a repository knowledge graph (AST-based) representing code structure and dependencies. (2) **Scoping & Analysis**: An LLM scoping agent uses the graph to select 5–15 high-potential exploration targets (files/classes/functions). For each target, a fine-grained analysis agent retrieves source code and extracts structured insights (e.g., role, fix hints, exploration insights) with a relevance score. Only insights scoring above a threshold τ are retained. (3) **Synthesis**: A synthesis LLM merges the original problem statement with the filtered insights into a coherent augmented specification, adding explicit sections for reproduction steps, expected behavior, and exploration hints. This augmented statement is then provided to a downstream software engineering agent for execution.

## Key Results
- ~20% absolute improvement in issue resolution rate on SWEBench-Verified, resolving up to 27 additional issues compared to using the original problem statement.
- Gains are robust across multiple agent scaffolds (SWE-Agent, OpenHands, Mini-SWE-Agent) and base LLMs (GPT-4o, Claude-3.5-Sonnet, Qwen3 Coder).
- Ablations confirm the necessity of both LLM-driven scoping (vs. keyword BM25) and relevance filtering; removing either component substantially reduces the gains.
- The augmentation most benefits weaker runtime agents, with the largest relative improvements observed for agents that otherwise have lower baseline performance.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Structured upfront context extraction reduces reactive exploration and over-exploration failure patterns.
- **Mechanism:** By building a repository knowledge graph and performing high-level scoping to identify a bounded set of exploration targets (≤15), CodeScout provides a strategic plan. Agents follow these targeted hints instead of discovering code structure incrementally through trial-and-error, avoiding long, non-converging trajectories.
- **Core assumption:** The downstream agent can effectively interpret and act on the provided structured hints (files, classes, functions, insights) to focus its actions.
- **Evidence anchors:**
  - Agents become trapped in reactive exploration due to information asymmetry; pre-exploration directly addresses this.
  - A case study shows an unfocused 21-step failure versus a targeted 6-step success with augmentation.
  - Trajectory analysis shows initial tool calls shift from broad `find` to more targeted `view` and `grep`.

### Mechanism 2
- **Claim:** Augmented problem statements clarify user intent and requirements through multi-perspective synthesis, converting ambiguous natural language into actionable specifications.
- **Mechanism:** The synthesis stage merges the original problem with filtered insights (role assessment, fix hints, exploration insights, alternative hypotheses) into a coherent narrative with reproduction steps, expected behavior, and explicit exploration hints, reducing ambiguity.
- **Core assumption:** The downstream agent's language model can parse and leverage the enriched specification to improve planning and execution.
- **Evidence anchors:**
  - Analysis links failures on underspecified requests to longer trajectories; CodeScout converts such requests into comprehensive specifications.
  - Augmentation increases statement length but reduces noise in the distribution; localization improves.
  - Across scaffolds and LLMs, augmented runs show higher resolution rates and better localization.

### Mechanism 3
- **Claim:** Relevance filtering and LLM-driven scoping ensure high-value context is preserved while discarding noise, making augmentation more effective than simple retrieval.
- **Mechanism:** Fine-grained analysis assigns a relevance score (0–10) to each insight; only insights scoring ≥ τ are kept. Scoping uses an LLM for semantic understanding rather than lexical matching (BM25) to identify targets.
- **Core assumption:** The LLM can accurately assess insight relevance to the problem and identify semantically related code entities beyond keyword overlap.
- **Evidence anchors:**
  - Ablation: Removing relevance filtering ("CodeScout (No Filtering)") reduces or eliminates gains.
  - Replacing LLM scoping with BM25 yields smaller gains, particularly for Qwen3 Coder.
  - The analysis extracts four insight categories; relevance scoring filters them.

## Foundational Learning
- **Concept: Repository Knowledge Graph**
  - *Why needed here:* Provides an efficient, structured representation of the codebase (classes, functions, imports, relationships) for quick lookup during scoping and analysis, avoiding repeated full-file parsing.
  - *Quick check question:* How does the AST visitor extract inheritance and import dependencies, and how are edges defined between code entities?
- **Concept: High-level Context Scoping**
  - *Why needed here:* Narrows the vast codebase to a small set of promising exploration targets (files/classes/functions) to keep subsequent analysis tractable and focused.
  - *Quick check question:* What signals (direct mentions, debugging patterns, structural relationships) does the LLM scoping agent use to select targets, and why is the limit |T| ≤ 15?
- **Concept: Fine-grained Context Analysis**
  - *Why needed here:* For each target, it extracts structured, actionable insights (role, fix hints, exploration insights, alternative hypotheses) that directly inform the augmented problem statement.
  - *Quick check question:* How does the LLM produce each insight category (e.g., fix location hints, exploration insights) from raw code content, and what does the relevance score measure?
- **Concept: Relevance Filtering and Synthesis**
  - *Why needed here:* Filtering removes low-quality or irrelevant analyses to prevent noise; synthesis combines the original problem with filtered insights into a coherent, guided specification.
  - *Quick check question:* How does the synthesis LLM preserve traceability and avoid verbosity while integrating multiple insights into a natural-language narrative?

## Architecture Onboarding
- **Component map:**
  Repository Knowledge Graph Builder -> High-level Scoping Agent -> Fine-grained Analysis Agent -> Relevance Filter -> Synthesis Agent -> Downstream Agent
- **Critical path:**
  1. Precompute repository graph (once per repository, reused across tasks).
  2. For each task instance:
     - Run scoping agent → get targets T.
     - For each target t in T, retrieve code and run analysis agent → get insight i with relevance score.
     - Filter insights: retain i where score ≥ τ.
     - Run synthesis agent with original statement and filtered insights → produce augmented statement.
  3. Feed augmented statement to downstream agent; collect resolution outcome.
- **Design tradeoffs:**
  - *Graph construction cost vs. reuse:* Building the graph is one-time per repository but may become stale; accuracy degrades if codebase drifts.
  - *Target count (|T| ≤ 15):* Limits computational overhead but risks missing relevant code; ablation suggests 5–10 targets is typical.
  - *Relevance threshold (τ):* Fixed in paper; likely needs tuning per model/dataset. Higher τ reduces noise but may drop useful insights.
  - *LLM call budget:* ~9 calls per instance (1 scoping + ~7 analyses + 1 synthesis). Augmentation overhead is modest relative to gains for most models but may be significant for very cheap augmenters.
- **Failure signatures:**
  - *Augmented statement length distribution:* Default has long tail with noise; augmented is tighter but longer. If augmented length grows excessively, synthesis may be adding low-value details.
  - *Ablation drops:* Without filtering or with BM25 scoping, gains diminish, indicating those components are critical.
  - *Cross-synthesis asymmetry:* Weak runtime agents benefit more from strong augmenters; strong agents show diminishing returns. If a weak agent does not improve even with strong augmenter, scoping/analysis may be misaligned.
- **First 3 experiments:**
  1. *Reproduce main result:* Run CodeScout on a small, fixed subset of SWEBench-Verified (e.g., 20 instances) using the same scaffolds and LLMs as the paper. Verify ~20% absolute improvement holds on this subset.
  2. *Ablation - filtering:* Disable relevance filtering (accept all analyses) and compare resolution rates to full pipeline and default; expect significant drop from full pipeline.
  3. *Scoping comparison:* Replace LLM scoping with BM25 retrieval (keyword-based) and measure performance gap vs. LLM scoping on the same downstream agent; expect smaller gains, especially for models with weaker semantic reasoning.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: Can CodeScout generalize to repositories in programming languages other than Python?
- Basis in paper: "Our evaluation focuses exclusively on Python repositories... Other programming languages lack comparable evaluation infrastructure" (Limitations section).
- Why unresolved: The study used SWEBench-Verified, which only contains Python issues; no multilingual data was included, leaving cross-language effectiveness unknown.
- What evidence would resolve it: Evaluate CodeScout on established non-Python benchmarks (e.g., Java, JavaScript, C++) with comparable problem statements and report resolution rate changes.

### Open Question 2
- Question: How does CodeScout scale to very large codebases or multi-repository settings?
- Basis in paper: Future work mentions "extending this framework to multi-repository settings, integrating deeper program analysis techniques" (Conclusion).
- Why unresolved: Experiments were conducted on SWEBench tasks, which involve single-repository issues of moderate size; industrial monorepos with millions of lines remain untested.
- What evidence would resolve it: Deploy CodeScout on large-scale repositories (e.g., Linux kernel, Android OS) and measure augmentation overhead, latency, and success rates compared to baseline.

### Open Question 3
- Question: What are the optimal choices for CodeScout’s hyperparameters (e.g., number of exploration targets, relevance threshold, model size) to maximize cost-effectiveness?
- Basis in paper: The pipeline fixed parameters like |T| ≤ 15 and a single relevance threshold without sensitivity analysis; the cost discussion suggests trade-offs are not fully mapped.
- Why unresolved: No systematic study of these knobs was reported; ablations only compared against simple baselines (no filtering, BM25 scoping) but did not explore the parameter space.
- What evidence would resolve it: Conduct a controlled experiment varying target count, threshold values, and augmenter model size across a representative subset of tasks, then report the Pareto frontier of resolution rate vs. computational cost.

## Limitations
- Knowledge graph schema and relevance threshold τ are unspecified; agent configurations and dataset splits are not fully detailed.
- Evaluation is confined to SWEBench-Verified (Python only), limiting generalizability to other languages or repository scales.
- Augmentation adds ~9 LLM calls per instance, incurring non-trivial cost; cost-benefit may diminish for strong baseline agents.

## Confidence
- Overall ~20% absolute improvement: **High** (robust across multiple scaffolds and LLMs, supported by ablations).
- Mechanism 1 (structured context extraction reduces reactive exploration): **Medium** (trajectory evidence supportive but contingent on accurate scoping).
- Mechanism 2 (augmented statements clarify intent): **Medium** (ablation indicates benefit, but synthesis quality is LLM-dependent).
- Mechanism 3 (relevance filtering and LLM scoping): **High** (ablations show significant performance drops when removed).

## Next Checks
1. **Reproduce main result:** Run the full CodeScout pipeline on a held-out SWEBench-Verified subset (e.g., 20 instances) using the same scaffolds and LLMs; verify the reported ~20% absolute improvement.
2. **Ablation – relevance filtering:** Disable the relevance filter (accept all insights) and compare resolution rates to the full pipeline; expect a substantial decrease, confirming filtering’s necessity.
3. **Scoping method comparison:** Replace LLM scoping with BM25 retrieval and evaluate on the same downstream agent; expect noticeably smaller gains, especially for models with weaker semantic reasoning, highlighting the value of LLM-driven scoping.
