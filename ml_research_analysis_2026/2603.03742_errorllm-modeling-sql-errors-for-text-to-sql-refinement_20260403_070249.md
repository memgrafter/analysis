# ErrorLLM: Modeling SQL Errors for Text-to-SQL Refinement

## Quick Facts
- arXiv ID: 2603.03742
- Source URL: https://arxiv.org/abs/2603.03742
- Reference count: 40
- Primary result: ErrorLLM improves execution accuracy by +18.54% on BIRD (to 66.23%) and +15.24% on Spider (to 86.94%) over GPT-4o backbone, with detection F1 of 78.12%.

## Executive Summary
ErrorLLM is a framework for refining erroneous SQL queries generated by LLMs in text-to-SQL tasks. It addresses the limitations of existing methods: self-debugging misses non-execution errors, while self-correction has low detection precision and high hallucination. ErrorLLM explicitly models 12 SQL error types with dedicated error tokens, extending the LLM’s semantic space. It uses structural representations (question-schema graph, AST) and a two-stage detection (static rules for surface errors and LLM-based semantic detection with constrained decoding). Detected errors guide a localization step (LocLLM) that pinpoints affected AST nodes and schema elements, followed by priority-ordered refinement (RefLLM). On BIRD and Spider benchmarks, ErrorLLM achieves state-of-the-art execution accuracy gains (+18.54% and +15.24% over GPT-4o) without corrupting correct SQLs. Ablation studies confirm the semantic detection component as the core driver.

## Method Summary
ErrorLLM extends a base code LLM (CodeS-7B) by adding 12 dedicated error tokens (e.g., `[Err]1`) to its vocabulary, initialized via averaging semantically related word embeddings. It trains the model with LoRA on a synthetically constructed dataset that mixes three sources: rule-based perturbations of correct SQLs (applying 12 AST-level operators to inject specific errors), LLM-assisted annotation of initial incorrect predictions (using GPT-3.5-Turbo to label errors and produce corrected SQLs, accepting only if the correction executes correctly), and no-error samples (correct SQLs). Each training example is formatted with question, schema, initial SQL, AST, execution feedback, and a set of error token labels. The model learns to predict error types via a permutation-invariant loss that sums log-probabilities over all tokens in the label set.

At inference, ErrorLLM first applies static detection rules (e.g., checking if a literal value exists in the column domain) to catch surface errors. Then it feeds the combined context (serialized question-schema graph, AST, and execution result) along with any rule-detected errors to the fine-tuned LLM, which uses constrained decoding to output only error tokens. The union of static and LLM-detected errors forms the final error set. If non-empty, a localization step (LocLLM, based on GPT-4o) analyzes each error type, guided by predefined templates, to identify specific AST nodes and schema elements. Relevant subtrees and schema fragments are extracted, sorted by a priority order (structural errors first). Finally, a refinement step (RefLLM, also GPT-4o) generates a corrected SQL in one pass, using the ordered list of error contexts and few-shot examples. The pipeline iterates until no errors are detected or a maximum number of refinements is reached.

## Key Results
- +18.54% execution accuracy improvement on BIRD (to 66.23%) and +15.24% on Spider (to 86.94%) over the GPT-4o backbone.
- Detection F1 score of 78.12% (precision 80.12%, recall 76.22%).
- Robust refinement that does not degrade already correct SQLs (low corruption rate).
- Ablation confirms that semantic detection (LLM component) is the core contributor to performance gains.

## Why This Works (Mechanism)
ErrorLLM’s effectiveness stems from three complementary design choices. First, explicitly modeling error types with dedicated tokens extends the LLM’s semantic space, allowing it to distinguish nuanced SQL mistakes that may otherwise be conflated with correct structures. Second, the two-stage detection mechanism combines deterministic static rules (high precision on surface errors) with a learned semantic detector (higher recall on complex errors), and constrained decoding ensures predictions remain within the error vocabulary, reducing hallucinations. Third, the refinement pipeline isolates errors through localization and prioritization, providing the refiner with focused context (subtree, schema, guideline) that prevents unnecessary changes and maintains correctness. Structural representations (question-schema graph, AST) preserve the relational and syntactic context necessary for accurate diagnosis. Together, these elements overcome the trade-offs of prior self-debugging (misses non-execution errors) and self-correction (low precision, high corruption).

## Architecture Onboarding
**Component Map**  
Initial SQL → Static Detection (rule-based) → Rule Errors set → LLM Detection (ErrorLLM with constrained decoding) → LLM Errors set → Combined Errors → (if non-empty) → Localization (LocLLM, GPT-4o) → Extraction of AST subtrees & schema fragments → Priority ordering → Refinement (RefLLM, GPT-4o) → Refined SQL → (loop back to detection if needed).  
Training path: Synthesize data (rule perturbations, LLM injection, no-error) → Format with structural representations → Fine-tune ErrorLLM (CodeS-7B + LoRA).

**Critical Path**  
The core innovation lies in the detection stage; accurate error identification dictates downstream success. The refinement stage relies on high-quality localization but uses a powerful proprietary LLM, making it less critical for the novelty but essential for performance.

**Design Tradeoffs**  
- Error token granularity: More tokens increase coverage but require more training data and risk confusion; the paper fixes 12 types and leaves room for expansion.
- Rule-based vs. neural detection: Rules are precise but have low recall; the LLM boosts recall but may hallucinate; combining them balances precision/recall.
- Proprietary vs. open-source: LocLLM and RefLLM use GPT-4o for strong performance, but this introduces cost and reproducibility issues; replacing them with open-source models is an open question.
- Constrained decoding: Guarantees token-level output but may limit the model’s ability to express nuanced errors if the token set is insufficient.

**Failure Signatures**  
- AST alignment errors: The mapping π between AST nodes and SQL token spans is incorrect, leading to wrong perturbations or mislocalized errors. Symptom: refined SQL changes unrelated parts, or detection rules never fire.
- Overly narrow static rules: Implementation of inverted rules misses many error cases, causing recall to drop far below the expected ~6.5% (static-only). Check: run static detection alone.
- Constrained decoding broken: ErrorLLM outputs natural language instead of error tokens, often due to missing logits masking. Diagnostic: sample outputs from the model on training data; expect only `[Err]i` tokens.
- False-positive detections: The combined error set includes types not present, causing RefLLM to alter already-correct SQLs and reduce execution accuracy. Monitor Corruption Rate; if it rises, adjust detection precision (e.g., increase confidence threshold).

**First Experiments**  
1. Validate AST-token alignment: Parse sample erroneous SQLs (e.g., from Spider) with `sqlglot`; confirm that for a known error (e.g., wrong column in SELECT), the AST node representing that column is correctly identified.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: How can ErrorLLM's error tokens be expanded to include subquery-related and operator-related errors?
- Basis in paper: [explicit] The authors state that ErrorLLM reports zero TSA on these categories because the current taxonomy Λ does not define them, and note that reserved error token slots ([Err]13 to [Err]𝑁) allow future expansion (Section 4.3).
- Why unresolved: The absence of these common error types limits the system's coverage; the method for adding new types and its impact on detection remain unexplored.
- What evidence would resolve it: Design error tokens and training data for subquery/operator errors, retrain ErrorLLM, and evaluate type-specific accuracy and overall D-F1 on a benchmark containing such errors (e.g., NL2SQL-Bugs).

### Open Question 2
- Question: Can the localization and refinement stages that currently use proprietary GPT-4o be replaced with open-source LLMs without sacrificing execution accuracy?
- Basis in paper: [inferred] ErrorLLM employs GPT-4o for LocLLM and RefLLM (Section 3.3), and the efficiency analysis (Appendix D.1) highlights the cost of proprietary LLMs at inference; however, the paper does not investigate alternatives.
- Why unresolved: Proprietary dependence hinders reproducibility and scalability; open-source models could lower costs but their effectiveness in this pipeline is unknown.
- What evidence would resolve it: Substitute GPT-4o with various open-source LLMs (e.g., Llama-3.1, DeepSeek-Coder) for LocLLM and RefLLM, and compare end-to-end execution accuracy on BIRD/Spider.

### Open Question 3
- Question: How can the recall of ErrorLLM's semantic detection (currently 76.22%) be improved while maintaining high precision (80.12%)?
- Basis in paper: [explicit] Table 2 shows detection recall 76.22% and precision 80.12% (D-F1 78.12%). The authors emphasize that detection quality directly determines refinement effectiveness (Section 4.3).
- Why unresolved: The current recall leaves many errors undetected, limiting overall refinement gains; improving recall risk lowering precision, making it a challenging trade-off.
- What evidence would resolve it: Explore scaling up training data, alternative model architectures (e.g., larger base models, different PEFT strategies), or multi-task objectives, and measure changes in D-F1 and end-to-end EX.

## Limitations
- The precise definitions of the 12 perturbation operators and their inverted detection rules are not fully specified, complicating faithful reproduction of the training data synthesis.
- The guideline templates `gλ` for most error types (except Value Error) are omitted; without them, the localization step may produce less accurate analyses when reimplemented.
- AST node-to-token alignment function π is not detailed; incorrect alignment would break perturbation, detection, and localization.

- Detection F1 (78.12%): Medium

- Generalization to unseen error types (e.g., subquery errors): Low
