# JFTA-Bench: Evaluate LLM's Ability of Tracking and Analyzing Malfunctions Using Fault Trees

## Quick Facts
- **arXiv ID:** 2603.22978  
- **Source URL:** https://arxiv.org/abs/2603.22978  
- **Reference count:** 39  
- **Primary result:** Gemini 2.5 Pro achieves the best success rate at 53.76%, while the top open‑source model DeepSeek‑V3.2 reaches 41.40% on the JFTA‑Bench diagnostic benchmark.

## Executive Summary
This paper introduces **JFTA**, a JSON‑based textual representation for fault trees that supports directed acyclic graph structures, and **JFTA‑Bench**, a multi‑turn dialogue benchmark designed to evaluate large language models (LLMs) on complex system maintenance tasks. The authors compile 126 fault trees from 24 domains into 3,130 diagnostic samples that simulate user rollback and recovery scenarios. Results reveal that even the strongest models solve less than 54% of cases, with primary failures stemming from planning deficits and difficulty maintaining consistency over long interactions. The work highlights a significant gap between the structured reasoning required for fault tree analysis and the current capabilities of text‑based LLMs.

## Method Summary
The proposed **JFTA** format encodes fault trees recursively in JSON, where each node contains its children, thereby reducing prompt length (≈6 K tokens vs. ≈14 K for node‑edge lists) and preserving hierarchical context. Path sampling builds fault diagnosis trajectories via a bottom‑up algorithm that selects parent nodes and expands siblings, creating pairs of paths with shared prefixes to enable rollback simulation. A **user simulator** (based on Qwen3‑8B) is trained in two stages: supervised fine‑tuning to produce vague yet correct responses, followed by PPO to improve linguistic fuzziness and naturalness. Evaluation proceeds in a ReAct‑style loop where the assistant queries node IDs or proposes solutions, and the user simulator replies with ambiguous observations. The primary metric is the **success rate**—correctly localizing all root causes and providing valid solutions within a turn limit—complemented by error breakdowns (planning, path, solution, structure errors).

## Key Results
- Gemini 2.5 Pro attains the highest success rate on JFTA‑Bench: **53.76%**.
- The best open‑source model, DeepSeek‑V3.2, achieves **41.40%**.
- The trained user simulator reaches **99.98%** correctness while maintaining realistic vagueness.

## Why This Works (Mechanism)
### Mechanism 1: Hierarchical JSON reduces noise and improves in‑context learning
The nested JFTA structure mirrors the top‑down/bottom‑up deduction flow of fault tree analysis. By collapsing parent‑child relations into recursive objects, it eliminates redundant descriptors, drastically cuts token count, and frees context window space for semantically relevant nodes. This hierarchical formatting aligns with LLMs’ inductive biases for pattern recognition, enabling them to traverse the fault tree more effectively. Evidence shows JFTA consistently outperforms flat node‑edge representations, especially on harder tasks (Section 5.5). The advantage vanishes only if the tree exceeds the LLM’s context window or the model misparses JSON.

### Mechanism 2: Vague user simulation forces robust inference under ambiguity
Real maintenance personnel rarely provide explicit yes/no confirmations; they describe symptoms indirectly. The user simulator is fine‑tuned with SFT on synthetically generated vague dialogues and further optimized with PPO to maximize a hybrid reward (format compliance and semantic correctness). This yields responses that are both semantically accurate and linguistically non‑committal, preventing the assistant from relying on binary cues and demanding deeper reasoning from incomplete information. LLM‑as‑a‑judge scores confirm improvements in fuzziness and naturalness after PPO (Section 5.2). If vagueness became too extreme or correctness fell below a reliable threshold, the simulation would lose its diagnostic value.

### Mechanism 3: Rollback and recovery expose state‑tracking deficiencies
JFTA‑Bench constructs pairs of fault paths sharing a long common prefix. After following the first path to a random point beyond the prefix, the user simulator indicates a prior observation was wrong and switches to the second path. This forces the assistant to backtrack, revise its belief state, and continue diagnosis correctly. The scenario tests long‑range consistency maintenance, and error analysis identifies planning and consistency errors as primary failure modes (Section 5.4). Without an explicit memory or state‑tracking mechanism, LLMs tend to persist with incorrect assumptions or misidentify the rollback target.

## Foundational Learning
- **Fault Tree Analysis (FTA):** Standard hierarchical modeling of system failures using logical gates (AND/OR/XOR). *Why needed:* Provides the underlying structure that the benchmark evaluates. *Quick check:* Describe how an AND gate differs from an XOR gate in terms of required child events.
- **JFTA Textual Representation:** A compact JSON schema that encodes fault trees as nested objects and supports DAGs via node references. *Why needed:* Bridges graphical fault trees with text‑based LLMs while minimizing token noise. *Quick check:* Convert a three‑node fault tree (root with two children under an OR gate) into valid JFTA JSON.
- **Multi‑turn Dialogue Systems:** Interaction paradigms where agents communicate sequentially to solve tasks. *Why needed:* Diagnostic maintenance is inherently interactive; the benchmark simulates this dynamic. *Quick check:* Outline a typical diagnostic dialogue turn structure (assistant query → user response → assistant update).
- **Rollback and Recovery Scenarios:** Sequences where a user corrects an earlier statement, requiring the agent to revisit prior reasoning. *Why needed:* Real‑world users often realize mistakes later; evaluating robustness to such events is crucial. *Quick check:* Given a dialogue history containing a confirmed node, define how a rollback should change the agent’s belief state.
- **User Simulator with Controlled Vagueness:** A model that generates linguistically ambiguous but semantically correct observations. *Why needed:* Avoids over‑fitting to explicit cues and tests inference under uncertainty. *Quick check:* Provide two versions of a user response (clear vs. vague) for a given fault observation.
- **Success Rate Metric:** Deterministic check that all leaf faults and their corresponding solutions are correctly identified within a turn budget. *Why needed:* Offers a clear, reproducible measure of diagnostic completeness. *Quick check:* For a given fault path, verify whether an assistant’s final proposal includes every required solution.

## Architecture Onboarding
**Component map (plain text):**  
Fault Tree Database → JFTA Converter → Path Sampler → Dialogue Generator (User Simulator + Assistant) → Evaluation Engine → Success Rate

**Critical path:** From JFTA conversion through path sampling, two parallel paths with common prefix are generated. During evaluation, the assistant interacts with the user simulator; rollback is triggered at a random turn after the prefix, after which the dialogue proceeds along the second path. Upon termination, the engine checks whether the assistant’s solution matches the ground‑truth fault path.

**Design tradeoffs:**
- *JFTA vs. Node‑Edge:* JFTA reduces token count and preserves hierarchy but requires strict JSON compliance; node‑edge lists are more explicit but verbose and noisy.
- *Vagueness vs. Clarity:* Simulating realistic indirect speech increases difficulty and ecological validity but risks over‑fuzzing and potentially misleading the assistant if correctness drops.
- *Open‑ended responses vs. constrained actions:* Allowing free‑form answers improves realism but complicates automatic evaluation; the benchmark mitigates this by requiring structured auxiliary output (`action`, `name`, `return`).

**Failure signatures:**
1. **Planning/consistency errors:** Assistant repeatedly queries nodes already confirmed or fails to adjust after a rollback.
2. **Path deviation:** Assistant jumps to incorrect branches, skips required children, or misinterprets logical gate semantics.
3. **Solution mistakes:** Proposes a solution not associated with a leaf fault or mismatches solution IDs/text.

**Exactly 3 first experiments:**
1. Implement the JFTA parser and the path sampling algorithm (Algorithm 1) and validate token savings on the provided example tree.
2. Train the user simulator on a small subset (e.g., 10 trees) using SFT followed by PPO, monitoring correctness, fuzziness, and naturalness.
3. Run a sample evaluation with a baseline LLM (e.g., Qwen3‑32B) to ensure the ReAct loop, rollback logic, and success‑rate calculation function correctly.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can JFTA‑Bench incorporate real industrial fault trees despite confidentiality?
- **Basis in paper:** [explicit] Limitations cite lack of native data due to industrial secrecy.
- **Why unresolved:** Industrial fault trees are proprietary and rarely public.
- **What evidence would resolve it:** Privacy‑preserving synthesis or expert‑validated data generation.

### Open Question 2
- **Question:** How can LLMs maintain consistency over long dialogues with user rollbacks?
- **Basis in paper:** [explicit] Section 5.4 reports failures from consistency challenges and incorrect rollback handling.
- **Why unresolved:** Models lose track of revised state over extended interactions.
- **What evidence would resolve it:** Memory augmentation or explicit state tracking evaluated on rollback recovery.

### Open Question 3
- **Question:** How to address planning deficiencies in LLM fault tree navigation?
- **Basis in paper:** [explicit] Analysis identifies planning errors as a primary failure mode.
- **Why unresolved:** Models lack strategic traversal of the fault tree structure.
- **What evidence would resolve it:** Integration of tree search or planning‑oriented training objectives.

### Open Question 4
- **Question:** What integration challenges arise when deploying JFTA in operational maintenance software?
- **Basis in paper:** [explicit] Limitations state JFTA deployment and usability remain unvalidated.
- **Why unresolved:** No real‑world implementation has been tested.
- **What evidence would resolve it:** Field studies in industrial settings measuring workflow impact.

## Limitations
- Fault tree generation details (prompts, seed examples, human review criteria) are insufficiently described, hindering exact corpus replication.
- The mechanism by which the user simulator signals a rollback and the assistant updates its belief state remains ambiguous in the provided appendices.
- User simulator's 99.98% correctness is validated on only 26 test trees; its generalization to broader fault tree variations is uncertain.

## Next Checks
1. **Token & Context Stress Test:** Compute JFTA and Node‑Edge token counts across all 126 trees; evaluate model accuracy under progressive context‑window limits to pinpoint where representation advantage disappears.
2. **Human Evaluation of User Simulator:** Conduct a blind study with domain experts to compare simulator responses against real maintenance dialogues or gold‑standard clear descriptions on realism and informativeness.
3. **Explicit State Tracking Ablation:** Augment the assistant with a structured belief tracker (e.g., a JSON record of confirmed/ruled‑out nodes) and rerun rollback scenarios to measure reduction in planning and consistency failures.
