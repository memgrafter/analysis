# Defense Against Indirect Prompt Injection via Tool Result Parsing

## Quick Facts
- **arXiv ID:** 2601.04795
- **Source URL:** https://arxiv.org/abs/2601.04795
- **Reference count:** 34
- **Primary result:** Combined defense achieves Attack Success Rates of 0.0%–0.5% and average risk (ASR/UA) of 0.2%–1.0%, reducing risk by 8–10× compared to best baselines while maintaining competitive task utility.

## Executive Summary
This paper introduces a lightweight, prompt-based defense against indirect prompt injection (IPI) attacks that hijack LLM agents by embedding malicious instructions in tool outputs. The approach uses two sequential modules—`ParseData` (extracts only essential, properly formatted data) and `CheckTool` (sanitizes text by removing words that trigger unauthorized tool calls)—to filter malicious content before it reaches the agent's reasoning step. Evaluated on the AgentDojo benchmark with three large language models, the combined method reduces attack success to near-zero while preserving utility, outperforming prior detection-based and isolation-based defenses.

## Method Summary
The defense intervenes after each tool call and before the LLM processes the result. `ParseData` prompts the LLM to anticipate the exact data format and logical constraints needed for the next step, then extracts only values matching those constraints, discarding all other content (including potential injections). `CheckTool` addresses large-text outputs: it prompts the LLM to detect whether the content would trigger a tool call; if so, it instructs the LLM to remove the offending segments. These modules can be applied in either order. No model training is involved; the method relies solely on prompt engineering and is model-agnostic. The system is evaluated on AgentDojo with three attack patterns ("Direct", "Ignore previous", "Important Messages") across `gpt-oss-120b`, `llama-3.1-70b`, and `qwen3-32b`, measuring Attack Success Rate (ASR) and Utility under Attack (UA).

## Key Results
- Combined `ParseData+CheckTool` or `CheckTool+ParseData` achieves average ASR of 0.0%–0.5% and average risk (ASR/UA) of 0.2%–1.0% across models and attacks.
- This represents an 8–10× reduction in risk compared to the best baseline (Tool Filter at 3%–6%).
- Utility under Attack (UA) remains competitive, though some models (e.g., `qwen3-32b`) show moderate drops with certain configurations, indicating a trade-off between security and utility.

## Why This Works (Mechanism)

### Mechanism 1: Essential Data Extraction (ParseData)
- **Claim**: Filtering malicious instructions by extracting only the minimal, properly formatted data needed for the next reasoning step, since injected payloads rarely match required formats or logical constraints.
- **Mechanism**: After a tool call, the LLM is prompted to (1) anticipate what data it expects (including format and logical constraints), and (2) parse the tool result to return only values satisfying those constraints. All other content—including potential injections—is discarded.
- **Core assumption**: Tool outputs are often unnecessarily verbose; legitimate needed data follows strict schemas (e.g., email pattern `xxx@xxxx.com`, age range 0–120), while injected instructions are free-form and violate those constraints.
- **Evidence anchors**:
  - [abstract] "...parse tool results and verify their format, returning only the essential data to the LLM while filtering out potential injections."
  - [section 3.2] Observations (1) and (2): "Tool results often return more data than an LLM agent actually needs" and "necessary data should typically conform to specific formatting... indirect prompt injections typically fail to satisfy these strict formatting requirements."
- **Break condition**: If the required data has a very permissive format (e.g., free-text notes) or the attacker can inject content that exactly matches the expected schema, the filter may let malicious data through.

### Mechanism 2: Trigger Word Sanitization (CheckTool)
- **Claim**: Removing words that could trigger unauthorized tool calls neutralizes injection attempts that rely on activating specific tools.
- **Mechanism**: The tool result is fed to the LLM with the name of the tool that was just called. If the LLM decides to call any tool (indicating a potential trigger), the module instructs the LLM to remove the offending segments and resubmit the sanitized text. If no tool call is triggered, the content is passed unchanged.
- **Core assumption**: IPI attacks must cause the LLM to invoke a malicious tool; by eliminating the textual triggers for that tool, the attack path is broken.
- **Evidence anchors**:
  - [section 3.4] "We have identified a simple yet effective method... remove those words which trigger the tool call."
  - [section 3.4] "If a tool call is triggered, it indicates the content is potentially malicious."
- **Break condition**: Attacks that do not rely on explicit keyword triggers (e.g., subtle manipulation of arguments to legitimate tools) or parameter hijacking within already-sanctioned calls bypass this filter.

### Mechanism 3: Complementary Combination
- **Claim**: Applying ParseData and CheckTool sequentially (in either order) covers complementary attack surfaces—structured data extraction and free-text sanitization—yielding dramatically lower ASR while maintaining competitive UA.
- **Mechanism**: The two modules are composed; for example, `CheckTool+ParseData` first sanitizes raw tool output to remove trigger words, then `ParseData` extracts only needed structured values. Their combination leverages the strengths of each.
- **Core assumption**: No single module is universally optimal; `ParseData` excels with structured outputs but can miss free-text injections, while `CheckTool` handles large text but may over-filter. Their combination provides robustness across varied tool result types.
- **Evidence anchors**:
  - [section 3.5] "We can combine these two two modules to achieve different levels of performance."
  - [section 4.2.1] Figure 2 and Table 1: combined methods achieve Avg ASR < 1% vs. best baseline 3–6%.
  - [section 4.3] Ablation shows individual modules have tradeoffs and combination reduces ASR further.
- **Break condition**: If an attack vector evades both parsing (e.g., by embedding malicious instructions that conform to required formats) and trigger sanitization (e.g., via obfuscated triggers), the combined defense may still fail.

## Foundational Learning
- **Concept: Indirect Prompt Injection (IPI)**
  - **Why needed**: The paper’s entire premise is that IPI attacks hijack LLM agents by embedding malicious instructions in tool outputs, not in the user’s prompt. Understanding this distinct threat model is essential.
  - **Quick check**: "How does an indirect prompt injection differ from a direct prompt injection, and why are LLM agents particularly vulnerable?"

- **Concept: Tool Calling and Context Window Management**
  - **Why needed**: The attack surface arises because tool results are concatenated into the LLM’s context without differentiation. The defense manipulates that integration point.
  - **Quick check**: "When an LLM agent calls a tool and receives a result, how is that result typically incorporated into the next LLM prompt?"

- **Concept: Prompt-Based vs. Training-Based Defenses**
  - **Why needed**: The paper explicitly critiques training-based approaches (fine-tuning, auxiliary models) and positions its prompt-based method as lightweight, model-agnostic, and adaptable.
  - **Quick check**: "What are the tradeoffs between prompt-based defenses and fine-tuning-based defenses for IPI?"

## Architecture Onboarding
- **Component map**: User task -> LLM (reasoning) -> tool call decision -> tool execution -> defense module (ParseData/CheckTool) -> sanitized result -> LLM (next reasoning step) -> ... -> final response.
- **Critical path**: The defense module must sit between tool execution and the LLM’s next reasoning step. Delaying it (e.g., after the LLM has already processed the raw result) nullifies protection.
- **Design tradeoffs**:
  - `ParseData` requires the LLM to correctly anticipate data needs; incorrect anticipation loses legitimate data (lower UA). Stronger models perform better.
  - `CheckTool` can over-aggressively remove legitimate content if the LLM misidentifies triggers, especially in verbose outputs; this harms UA.
  - `Combination` adds latency (two LLM calls per tool result) and cumulative error risk, but yields the lowest ASR.
  - `ParseFull` (using full conversation history) helps deeper models but confuses shallower ones, reducing BU.
- **Failure signatures**:
  - ASR > 5% under strongest attack (Important Messages) indicates inadequate filtering.
  - UA dropping > 30% from No Defense suggests over-sanitization (likely `CheckTool` removing essential data).
  - High variance across attacks means the defense is brittle against certain injection styles.
- **First 3 experiments**:
  1. **Individual module evaluation**: Compare `ParseData` alone vs. `CheckTool` alone across models and attacks to isolate strengths/weaknesses.
  2. **Combination evaluation**: Test `ParseData+CheckTool` and `CheckTool+ParseData` to measure synergy and order effects.
  3. **Baseline comparison**: Run against DeBERTa Detector, Repeat Prompt, Spotlighting, Tool Filter on AgentDojo to establish relative performance.

## Open Questions the Paper Calls Out
- **Question 1**: How can LLM agents be defended against indirect prompt injection attacks that hijack parameters within legitimate tool calls rather than triggering unauthorized tools?
  - **Basis**: In the Limitations section, the authors state: “another significant class of IPI attacks exists that targets parameter hijacking rather than action hijacking. ... In this scenario, no unauthorized tool is called, allowing the attack to bypass our proposed defense … This represents a limitation of our current work. We leave this vector for future research.”
  - **Why unresolved**: The current defense modules focus on filtering malicious instructions that trigger tool calls. They do not inspect or sanitize parameter values within legitimate tool responses that might be subtly altered. The evaluation benchmark (AgentDojo) primarily tests unauthorized tool invocation.

- **Question 2**: Do the proposed defense mechanisms generalize to languages other than English, and if not, what adaptations are needed?
  - **Basis**: In the Limitations section, the authors note: “Our experiments are conducted primarily in English, and the effectiveness of the proposed defense mechanisms in other languages remains to be explored.”
  - **Why unresolved**: The defense relies on prompting LLMs to parse and sanitize text. LLMs may have varying performance across languages due to tokenization differences, linguistic complexity, or cultural context. Attacks could be crafted in other languages, potentially bypassing the defenses. Results are limited to English data from AgentDojo.

- **Question 3**: Why does the `CheckTool` module cause more utility degradation in stronger reasoning models (e.g., `qwen3-32b`) compared to weaker ones, and how can its design be improved to reduce false positives?
  - **Basis**: In the conclusion and ablation study, the authors state: “for `CheckTool`, increased reasoning depth tends to introduce more errors, which in turn decreases BU and UA. Consequently, further research is required to refine this module and address these reasoning-induced inconsistencies.”
  - **Why unresolved**: `CheckTool` works by detecting triggered tool calls and then asking the LLM to remove triggering words. Powerful models may over-detect triggers or misinterpret benign content as malicious, leading to removal of essential information. The current prompt may be too sensitive or lack nuance.

## Limitations
- **Generalizability beyond AgentDojo**: The defense assumes tool outputs follow strict schemas (`ParseData`) and contain explicit trigger words (`CheckTool`). Real-world tools with free-form outputs or obfuscated triggers may bypass filters.
- **Implementation fidelity**: Exact prompt templates, delimiters, and model parameters are partially redacted; reproduction depends on an unspecified GitHub branch (`tool-result-extract`).
- **Over-sanitization risk**: `CheckTool` may remove legitimate content, harming Utility under Attack (UA), especially for verbose outputs. The paper reports UA drops for some models, but the trade-off’s practical impact is unclear.

## Confidence
- **Claim 1** (`ParseData` filters injections via format constraints): High confidence in AgentDojo results; Low confidence for tools with permissive output formats.
- **Claim 2** (`CheckTool` neutralizes trigger-based injections): Medium confidence; effective for explicit keywords but not for subtle parameter manipulation.
- **Claim 3** (Combination yields 8–10× risk reduction): High confidence on reported metrics; Medium confidence that gains hold outside the benchmark.
