# annbatch unlocks terabyte-scale training of biological data in anndata

## Quick Facts
*   **arXiv ID:** 2604.01949
*   **Source URL:** https://arxiv.org/abs/2604.01949
*   **Reference Count:** 25
*   **Primary Result:** Annbatch enables ~35,000 samples/sec throughput on the 100M-cell Tahoe-100M benchmark, reducing one epoch from ~21 hours to ~17 minutes.

## Executive Summary
Annbatch is a mini-batch data loader designed for the `anndata` format that removes the I/O bottleneck in large-scale biological deep learning. It achieves this by leveraging a Zarr-backed storage backend combined with pre-shuffled, contiguous chunked disk access, which maximizes sequential read performance. On a massive 100 million cell benchmark (Tahoe-100M), it demonstrated a 22x to 41x speed-up over prior solutions like `scDataset` and `MappedCollection`. This performance gain makes terabyte-scale model training feasible while maintaining compatibility with the scverse ecosystem.

## Method Summary
The method replaces random, scattered disk accesses with a two-phase process. First, the dataset is pre-shuffled and stored in a Zarr array in large, contiguous chunks on disk. During training, the loader reads these pre-arranged contiguous chunks sequentially, which is orders of magnitude faster than the random access patterns typical of HDF5-based loaders. The loader is natively integrated with `anndata` objects, requiring minimal user code changes.

## Key Results
*   Achieved ~35,000 samples/sec on the 100M-cell Tahoe-100M benchmark, compared to ~1,500 for `scDataset` and ~850 for `MappedCollection`.
*   Reduced epoch time from ~21 hours to ~17 minutes on the same benchmark.
*   Demonstrated 22x speed-up for single-cell microscopy images and 18-41x speed-up for whole-genome sparse variant data.

## Why This Works (Mechanism)
The core innovation is aligning physical disk access patterns with the logical mini-batch sampling requirement. Traditional loaders sample random indices, causing slow, non-sequential HDD/SSD seeks. Annbatch's pre-shuffling step performs this random permutation once during dataset preparation, writing data in large, contiguous blocks. At training time, mini-batches are constructed by reading a small number of these large, sequential blocks, turning millions of random reads into a few long, efficient sequential reads. The Zarr format is used for its efficient chunked storage and cloud-compatibility.

## Foundational Learning
*   **Out-of-Core Computing:** Processing data larger than RAM by streaming from disk. *Why needed:* Biological datasets (e.g., 100M cells) exceed typical memory capacities. *Quick check:* Can your training loop run with a batch size of 1 without crashing?
*   **Sequential vs. Random I/O:** The dramatic performance difference between reading contiguous blocks of data versus scattered pieces. *Why needed:* HDDs and SSDs have vastly higher throughput for sequential access. *Quick check:* Time reading 1GB from a file sequentially vs. reading 1GB via 10,000 random 100KB seeks.
*   **Chunked Storage Formats (Zarr/ HDF5):** Storing arrays in fixed-size chunks on disk. *Why needed:* Enables efficient reading of sub-regions and parallel I/O. *Quick check:* What is the chunk size of your current dataset's storage format?
*   **Data Shuffling for Training:** Randomizing sample order to prevent model bias. *Why needed:* A fundamental requirement for stochastic gradient descent. *Quick check:* Is your model's performance worse if you train without shuffling?
*   **Ecosystem Compatibility (scverse):** Integration with tools like `scanpy` and `anndata`. *Why needed:* Adoption requires fitting into existing bioinformatics workflows. *Quick check:* Can you pass an `annbatch` loader directly to a `scvi-tools` model?

## Architecture Onboarding
*   **Component Map:**
    `anndata Object` -> `Pre-shuffle & Write to Zarr` -> `annbatch DataLoader` -> `PyTorch/ scvi-tools Model`
*   **Critical Path:** Disk I/O during `__next__()` call of the DataLoader. The speed of reading the next contiguous Zarr chunk dictates overall throughput.
*   **Design Tradeoffs:** Pre-shuffling incurs an upfront one-time cost and storage overhead (duplicate dataset). Runtime speed gains are highest for very large datasets where I/O is the bottleneck; for small in-memory datasets, it adds unnecessary complexity.
*   **Failure Signatures:** 1) Throughput plateaus far below disk specs: indicates chunks are too small or access pattern isn't sequential. 2) High variance in batch load time: suggests filesystem caching issues or non-contiguous chunk layout. 3) Out-of-memory errors: Zarr chunk size too large for available RAM during decoding.
*   **First 3 Experiments:**

    2.  Integrate `annbatch` with a standard `scvi-tools` model (e.g., `scVI`) on a public single-cell dataset (e.g., PBMC) and confirm identical training loss curves compared to the default loader.
    3.  Measure the disk space overhead of the pre-shuffled Zarr copy relative to the original `anndata`/HDF5 file.

## Limitations
*   Performance validation is limited to two specific benchmarks (Tahoe-100M, microscopy, variant data); generalizability to other data types like spatial transcriptomics or raw reads is unproven.
*   The claimed throughput is for the data loading stage alone; full training throughput (including augmentation and model compute) will be lower and is not quantified.
*   The approach relies on pre-shuffling, making it unsuitable for streaming or online learning scenarios where data order must be dynamic.

## Confidence
*   **Throughput Gain Claims:** High. Direct measurement on defined benchmarks with clear comparison baselines.
*   **Terabyte-Scale Training Enabling:** Medium. I/O bottleneck is solved, but full training scalability depends equally on model compute and other pipeline stages not addressed.
*   **Full scverse Ecosystem Compatibility:** Medium. Asserted based on `anndata` native design, but not exhaustively tested across all downstream libraries.

## Next Checks
1.  **Independent Replication:** Re-run the Tahoe-100M benchmark and a standard dataset (e.g., Mouse Brain) on identical hardware/software to confirm the ~35k samples/sec figure.
2.  **End-to-End Throughput Test:** Measure total epoch time (data loading + augmentation + model forward/backward) for a representative model like scVI on a large dataset to isolate the net training speed-up.
3.  **Longitudinal I/O Profiling:** Profile I/O throughput and latency variance over 10+ consecutive epochs, including cache warm-up effects, to assess performance stability.
