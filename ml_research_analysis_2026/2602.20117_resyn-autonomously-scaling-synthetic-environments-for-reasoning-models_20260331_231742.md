# ReSyn: Autonomously Scaling Synthetic Environments for Reasoning Models

## Quick Facts
- arXiv ID: 2602.20117
- Source URL: https://arxiv.org/abs/2602.20117
- Reference count: 40
- Primary result: Training a 7B model on ReSyn's 418 environments yields +14% relative improvement on BBH and +27% on BBEH.

## Executive Summary
ReSyn addresses the limited scalability of synthetic data for training reasoning models by introducing an autonomous pipeline that uses an LLM to synthesize diverse Python-based reasoning environments. Each environment includes a procedural instance generator and a verifier. The pipeline filters generated environments via LLM-based code and logical validation, then calibrates difficulty. Training a Qwen2.5-7B-Instruct model via reinforcement learning on ReSyn’s 418 unique environments (derived from ~100 seed keywords) consistently improves performance on multiple reasoning benchmarks. The work demonstrates that verifier-based supervision and task diversity are key drivers of improvement.

## Method Summary
ReSyn starts with ~100 seed keywords (e.g., from BBH). For each keyword, an LLM generates Python code defining an environment class with three core functions: a procedural instance generator ρ₀(d) (producing problems at discrete difficulty levels d), an observation function O(s), and a verifier R(s,a). Generated code undergoes two-stage filtering by an LLM-as-a-Judge: first for code quality, then for criteria including reference-free verification and computational advantage. Surviving environments produce instances across difficulties d=1..5. Only environments where solve rate significantly negatively correlates with difficulty (one-sided Wald test, α=0.05) are retained. The final dataset of (question, verifier) pairs is used to train a model via DAPO, where rewards combine a format bonus and the binary verifier score.

## Key Results
- Relative improvements of +14% on BBH and +27% on BBEH compared to baselines.
- Ablations confirm that verifier-based supervision (vs. solution-matching) and greater environment diversity are primary performance drivers.
- Semantic entropy analysis shows ReSyn’s environments are substantially more diverse than prior synthetic datasets.

## Why This Works (Mechanism)

**Mechanism 1: Verifier-Based Supervision**
LLMs find it easier to specify correct verification logic than to solve problems correctly. ReSyn decouples task creation (writing verifier code) from task solving (generating correct answers). The verifier provides a consistent binary reward signal, avoiding errors from solution-matching (e.g., hallucinated reference answers). Evidence: Ablation shows Verifier-RL (75.24% BBH) significantly outperforms Answer-RL (68.83%). Break condition: Subtle bugs in verifier code that evade the LLM judge introduce reward noise.

**Mechanism 2: Autonomous Diversity Scaling**
Starting from ~100 seed keywords, the pipeline autonomously generates hundreds of distinct environment classes, each encapsulating unique reasoning patterns (e.g., constraint satisfaction, graph algorithms). This broad exposure yields more generalizable skills than hand-curated task sets. Evidence: With fixed total instances, using more environments (N=400, M=40) gives higher BBH (75.19%) than fewer environments with more instances each (N=25, M=640, 71.20%). Break condition: If the LLM converges to near-duplicate environment structures, diversity gains saturate.

**Mechanism 3: Difficulty Calibration**
Each environment’s ρ₀(d) generates instances at controlled difficulty levels (d=1..5). The pipeline discards environments where solve rate does not meaningfully increase with d (Wald test, α=0.05). This ensures a curriculum of appropriately challenging problems for RL, matching the model’s learning progression. Break condition: If many environments fail calibration (e.g., trivial or uniformly impossible), the dataset lacks sufficient difficulty range.

## Foundational Learning
- **Reinforcement Learning with Verifiable Rewards (RLVR)**
  - *Why needed*: Core training paradigm where automated verifiers provide binary rewards, enabling large-scale RL without human annotation.
  - *Quick check*: How does RLVR differ from standard RL? RLVR uses programmatic verifiers to generate consistent, dense rewards, whereas standard RL often relies on sparse or manually defined reward functions.

- **Procedural Generation**
  - *Why needed*: Allows unlimited, varied problem instances to be generated efficiently, essential for scaling synthetic data beyond static datasets.
  - *Quick check*: What advantages does procedural generation offer over static datasets? It provides infinite diversity, controllable difficulty, and eliminates data collection bottlenecks.

- **Generator–Verifier Gap**
  - *Why needed*: The insight that LLMs can more reliably write verifiers than generate correct solutions underpins ReSyn’s shift from solution-centric to verifier-centric synthesis.
  - *Quick check*: Why is writing a verifier easier? Verification often requires algorithmic checks (e.g., recomputing an answer), which are less prone to multi-step reasoning errors than solving the problem from scratch.

## Architecture Onboarding
Component map:
Seed Keywords -> Task Synthesizer (LLM) -> LLM-as-a-Judge -> Instance Generator -> Difficulty Calibrator -> RL Trainer (DAPO)

Critical path:
1. Extract seed keywords from BBH/KOR-Bench.
2. Task Synthesizer generates candidate Python environments (ρ₀, O, R).
3. LLM-as-a-Judge filters for code quality, reference-free verification, and computational advantage.
4. Instance Generator creates samples across difficulty levels.
5. Difficulty Calibrator applies Wald test to keep only environments with significant negative correlation between solve rate and difficulty.
6. RL Trainer (DAPO) consumes filtered (question, verifier) pairs to update the policy.

Design tradeoffs:
- Verifier vs. solution: Verifiers yield consistent binary rewards but risk coding bugs; solution-matching is flexible but prone to hallucination.
- Autonomous vs. manual: Automatic generation scales diversity but requires robust quality control; manual curation ensures quality but limits scale.
- Code-based generation: Enables procedural instances and efficient verification but depends on LLM coding proficiency and may hide edge cases.

Failure signatures:
- High verifier error rate during RL training (exceptions/NaNs) indicates buggy verifier code.
- Low semantic entropy in final dataset suggests task redundancy.
- Many environments failing difficulty calibration imply poor ρ₀ design or trivial/impossible tasks.
- RL validation accuracy plateaus or declines, suggesting reward signal is too noisy or sparse.

First 3 experiments:
1. Run keyword extraction on a small sample of BBH/KOR-Bench tasks; verify the list spans diverse reasoning domains.
2. Execute Task Synthesizer for 2–3 keywords; inspect generated code for structural correctness and completeness of ρ₀, O, R.
3. Apply LLM-as-a-Judge to the generated environments; categorize failure modes (e.g., missing reference-free verification) and iterate on the synthesis prompt.

## Open Questions the Paper Calls Out
1. What is the scaling law of performance versus number of unique synthetic environments? The pipeline produced 418 environments due to compute limits; scaling beyond 400 may increase, saturate, or degrade performance.
2. How robust is RLVR training to inaccuracies in automatically generated verifiers? The paper acknowledges residual errors but does not quantify their impact or define a tolerance threshold.
3. Do skills learned from ReSyn generalize to natural-language reasoning tasks without verifiable answers? Evaluations were on formal benchmarks (BBH, BBEH, GSM8K, AIME); transfer to commonsense or ethical reasoning remains untested.

## Limitations
- Exact prompts for task synthesis and LLM-as-a-Judge are omitted, making exact replication difficult and potentially introducing biases.
- No canonical code interface (signatures and contracts for ρ₀, O, R) is provided, risking inconsistent environment implementations.
- Difficulty calibration details (Wald test parameters, regression specifics) are undisclosed, possibly leading to unstable environment selection.

## Confidence
- Verifier-based supervision: **High** (strong ablation evidence and clear theoretical rationale)
- Autonomous diversity scaling: **Medium** (ablation shows benefit, but long-term generalization and saturation points unexplored)
- Procedural difficulty calibration: **Medium** (correlation test is sensible, but direct causal link to RL progress is inferred)

## Next Checks
1. Prompt reconstruction study: Reverse-engineer missing prompts using paper’s criteria; evaluate survival rate, environment quality, and downstream RL performance; publish prompts as replication artifact.
2. Verifier robustness audit: Randomly sample 100 environments that passed the judge; generate adversarial/edge-case inputs; manually inspect verifier code for logical bugs that could corrupt rewards.
3. Diversity–performance curve: Systematically vary the number of distinct environment classes (N) while keeping total instances fixed; measure semantic entropy and BBH accuracy to confirm scaling benefits and identify saturation point.
