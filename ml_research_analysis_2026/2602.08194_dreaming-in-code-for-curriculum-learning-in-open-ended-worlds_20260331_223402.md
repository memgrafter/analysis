# Dreaming in Code for Curriculum Learning in Open-Ended Worlds
## Quick Facts

- **Reference count**: 40

## Executive Summary
Open-ended reinforcement learning often stalls due to lack of suitable experiences. Dreaming in Code (DiCode) addresses this by leveraging foundation models to synthesize executable environment code, creating a dynamic curriculum that scaffolds agent progress. The framework generates new levels by conditioning on parent levels and agent performance, validates them, and mixes them into training with prioritized replay.

Evaluated on the Craftax benchmark, DiCode yields a 16% improvement in mean return and achieves non-zero success on previously unsolvable late-game tasks. Ablations confirm the importance of the closed-loop feedback, and the average success rate on generated levels remains around 0.5, indicating effective zone of proximal development maintenance.

## Method Summary
DiCode introduces a curriculum learning framework that uses foundation models to generate executable environment code. The system maintains an archive of levels and, every v iterations, selects a parent level based on a learnability score (p(1-p)) that favors tasks the agent is likely to learn but hasn't mastered. A foundation model then produces a natural language description of a new level conditioned on the parent and the agent's performance profile. This description is fed to another model that generates Python code inheriting from a fixed world engine's base task class. The code is validated by running a short trajectory; valid levels are added to the training batch. The agent is trained via PPO with a GTrXL policy on a mixture of target, newly generated, and replayed archived levels (sampled via Prioritized Level Replay). This closed-loop process continuously adapts the curriculum to the agent's evolving capabilities.

## Key Results
- DiCode achieves a mean return of 48.33 on Craftax, a 16% improvement over the strongest baseline (41.54).
- It attains non-zero success on late-game combat tasks where prior methods fail entirely (e.g., 11% vs 0% on Defeat Gnome Warrior).
- Ablating the closed-loop feedback (DiCode-OL) reduces performance by approximately 15% (48.33 → 40.91), while the average success rate on generated levels remains stable around 0.5, confirming the curriculum's role in maintaining the agent's zone of proximal development.

## Why This Works (Mechanism)
We now explain the mechanisms that underpin DiCode's effectiveness.

### Mechanism 1
- **Claim**: DiCode generates a curriculum by synthesizing executable environment code via foundation models, enabling structural evolution beyond parameter-based UED.
- **Mechanism**: The generation cycle selects a parent level from an archive based on a learnability score (p(1-p)), conditions a foundation model on the parent's description and the agent's performance profile to produce a new level description, then generates executable code from that description. Validated code is added to the training batch.
- **Core assumption**: The foundation model can consistently generate valid, compilable code that adheres to the world engine's interface and that the generated levels are semantically meaningful for curriculum progression.

### Mechanism 2
- **Claim**: The closed-loop feedback (parent level and agent performance) is critical for generating an effective curriculum, as demonstrated by a 15% performance drop when removed.
- **Mechanism**: Parent levels are selected based on learnability to ensure they are in the agent's zone of proximal development (success rate around 0.5). The foundation model is conditioned on the parent level's description and the agent's performance metrics (success rates on achievements) to generate offspring that target the agent's current weaknesses. This creates a directed curriculum that bridges competence gaps.
- **Core assumption**: The learnability score (p(1-p)) effectively captures levels that are learnable and not yet mastered, and that the foundation model can generate meaningful variations that extend the agent's capabilities.

- **Break condition**: If the learnability score fails to identify appropriate parent levels (e.g., all levels become too easy or too hard) or if the foundation model does not generate offspring that address the agent's performance gaps.

  - **Why needed**: The core design principle of DiCode is to maintain the agent in its ZPD. This concept from educational psychology is adapted to RL curriculum design to ensure tasks are neither too easy nor too hard.

## Architecture Onboarding
A high-level view of the DiCode system:

- **Component map**:
  - **Archive**: Stores levels (executable code, metadata, performance) as a directed graph; tracks parent-offspring relationships and agent success rates.
  - **Parent Selection**: Samples from eligible parents (status A or B with no offspring in D) proportional to learnability score.
  - **Description Generator**: Foundation model that takes parent description, performance profiles (parent and target), and fixed context to produce a natural language description of the new level.
  - **Code Generator**: Foundation model that takes the description, few-shot examples, and fixed context to produce executable Python code (inheriting from `BaseTask`).
  - **Compilation Check**: Executes a short trajectory in the generated environment to filter out invalid code (compilation/runtime errors); no self-correction.
  - **Training Batch**: Combines target environment, newly generated levels (introduced every `v` iterations), and archived levels sampled via Prioritized Level Replay (PLR).
  - **RL Agent**: PPO with Gated Transformer-XL (GTrXL) policy; trained on batches from the mixed distribution.
  - **Performance Tracking**: Updates archive with new levels and agent's success rates on achievements after training cycles.

- **Critical path**:
  1. **Initialization**: Agent starts with seed tasks (pre-defined levels); archive initialized with these.
  2. **Training loop**: For each iteration, sample a batch from the training distribution (target, new, replay) and update the agent with PPO.
  3. **Generation cycle** (triggered every `v` iterations):
     a. Select parent from archive based on learnability.
     b. Generate natural language description via Description Generator.
     c. Generate executable code via Code Generator.
     d. Validate code by short trajectory execution; if valid, add to archive and training batch.
  4. **Archive update**: Add new levels, update performance metrics (success rates) for levels in archive.
  5. **Evaluation**: Periodically evaluate agent on held-out test set of target environment.

- **Design tradeoffs**:
  - **Fixed world engine vs. open-ended physics**: Using a fixed engine (Craftax) ensures generated environments are valid and physically consistent, but limits the scope of invention (cannot create new mechanics from scratch). This is a practical compromise for reliability.
  - **Asynchronous generation**: To mitigate foundation model inference latency, generation runs concurrently with training. Training blocks only if `v-1` cycles elapse without a new batch of valid levels.
  - **Validation without self-correction**: The system generates a surplus of candidates and discards invalid ones, rather than iteratively refining. This is due to computational cost outweighing marginal gains.
  - **PLR replay buffer**: Mixes generated levels with archived levels to maintain diversity and avoid forgetting, using a combination of score-based (learnability) and staleness-based sampling.

- **Failure signatures**:
  - **High compilation failure rate**: Many generated codes fail to compile/runtime, reducing yield of valid levels and potentially starving the curriculum.
  - **Success rate drift**: The average success rate on generated levels consistently exceeds 0.75 or falls below 0.25, indicating the curriculum is not in the ZPD.
  - **Performance plateau**: Agent fails to improve on the target environment, suggesting the curriculum is not effectively bridging competence gaps.
  - **Archive stagnation**: The archive graph shows limited evolutionary lineages (e.g., many levels in status D with no offspring in A/B), indicating poor curriculum progression.
  - **Overfitting to generated levels**: Agent performs well on generated levels but poorly on the target, suggesting the curriculum is too narrow or not transferred.

- **First 3 experiments**:
  1. **Main evaluation**: Compare DiCode against baselines (PPO-GTrXL, DR, PLR, SFL) on Craftax, measuring mean return and achievement success rates after 2B environment steps.
  2. **Ablation study**: Test DiCode without closed-loop feedback (DiCode-OL) to quantify the importance of conditioning on parent and performance.
  3. **Qualitative analysis**: Visualize the curriculum (archive graph and example levels) to understand progression and "teacher-like" strategies of the foundation model.

## Limitations
- **Benchmark scope**: Evaluation is confined to Craftax; generalizability to other open-ended worlds (e.g., physics-based, 3D) is unknown.
- **Foundation Model Cost & Scalability**: Relies on a 235B parameter model (Qwen3-235B); feasibility with smaller or cheaper models remains unexplored.
- **Curriculum Diversity vs. Compilation**: The validation-only approach discards invalid code but may limit semantic diversity; the archive graph evolution suggests potential stagnation in later training.

## Confidence
- **Performance Gains (e.g., +16% mean return)**: High
- **Closed-Loop Curriculum Mechanism**: Medium
- **General Principle (ZPD maintenance)**: Low to Medium

## Next Checks
1. **Cross-Benchmark Transfer**: Replicate DiCode on at least two other open-ended RL benchmarks (e.g., MiniHack, Crafter) to test if the 16% gain and late-game success hold.
2. **Failure Mode Analysis**: Log and categorize all compilation/runtime failures from the code generator. Quantify whether failures stem from syntax, engine API misuse, or semantic incoherence, and test a simple self-correction loop (e.g., one retry with error feedback).
3. **ZPD Target Sensitivity**: Run an ablation varying the target success rate (e.g., 0.3, 0.7) for parent selection and measure final performance on the target environment to validate the 0.5 assumption.
