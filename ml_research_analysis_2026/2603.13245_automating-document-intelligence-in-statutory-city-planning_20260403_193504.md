# Automating Document Intelligence in Statutory City Planning

## Quick Facts
- arXiv ID: 2603.13245
- Source URL: https://arxiv.org/abs/2603.13245
- Reference count: 19
- Primary result: An AI-in-the-Loop system automated document processing for UK planning authorities, achieving F1 scores of 0.84–0.88 on metadata extraction, 0.96 micro-recall on PII detection, and a 92% suggestion acceptance rate at a cost of ~$0.046 per document.

## Executive Summary
UK planning authorities face a high-risk, manual workload balancing public document access with personal data protection. This paper presents an integrated AI system designed with an AI-in-the-Loop (AI2L) paradigm, where all AI-generated suggestions—for PII redaction, metadata extraction, and drawing analysis—are presented for mandatory human review and confirmation within existing planning software. A Proof-of-Concept evaluation demonstrated strong technical performance (F1 scores 0.84–0.88, PII recall 0.96) and high user acceptance (92%). A preliminary ROI model was developed to quantify potential time savings and secure partner participation for a multi-authority pilot.

## Method Summary
The system automates three core tasks: (1) metadata extraction from textual documents (e.g., application title, date), (2) detection and redaction of personally identifiable information (PII) in both text and images, and (3) identification of visual elements (e.g., North arrow, scale bar, boundary lines) on architectural drawings. It employs a hybrid pipeline where Vision-Language Models (VLMs) process document images within a configurable pre- and post-processing framework that enforces deterministic validation and audit logging. All outputs are treated as suggestions requiring explicit human confirmation (AI2L). Evaluation used a held-out test set of 440 curated planning documents, comparing the system against classical baselines (CRF+regex, template matching+Hough transform) and measuring accuracy, user acceptance, processing time, and cost.

## Key Results
- Information extraction F1 scores: 0.84 (Title) to 0.88 (Date).
- PII detection micro-recall: 0.96.
- Visual element detection mAP@0.5 IoU: 0.71 (Red Line) to 0.78 (North Point).
- Suggestion acceptance rate: 92%.
- Processing cost: ~$0.046 per document.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** The system achieves practical utility and adoption not primarily through peak AI accuracy, but by embedding AI suggestions within a **mandatory human review** workflow (AI-in-the-Loop), thereby maintaining legal accountability and user trust.
- **Mechanism:** All AI outputs (metadata suggestions, PII detection, visual element overlays) are presented as proposals requiring explicit planner confirmation before any action is committed. The human operator retains final authority. Audit logs record all suggestions, user actions, and system decisions.
- **Core assumption:** In high-risk, compliance-driven public sector work, preserving human control and a clear audit trail is a prerequisite for operational deployment, even if it forfeits some potential automation gains.
- **Evidence anchors:**
  - [abstract] "operates with an AI-in-the-Loop (AI2L) design, presenting all suggestions for review and confirmation... no action is committed without explicit human approval."
  - [section 4] Details the three workflows where the human "verifies and confirms," "reviews and provides confirmation," and "interprets the visual output." "The final judgment, action, and legal accountability remain with the human operator."
- **Break condition:** If users consistently override or ignore AI suggestions (acceptance rate drops significantly), the assistive value proposition fails, regardless of technical metrics.

### Mechanism 2
- **Claim:** System reliability and auditability are achieved not by seeking fully autonomous AI, but by wrapping non-deterministic VLM calls within a **configurable, deterministic hybrid processing framework** of pre/post-processing rules.
- **Mechanism:** Before a VLM sees a document, configurable pre-processing steps (e.g., PDF rendering, region cropping, prompt templating) standardize the input. After the VLM responds, configurable post-processing steps (schema validation, heuristic filtering, normalization) enforce structure and business logic. All steps and retries are immutably logged.
- **Core assumption:** The inherent non-determinism of large VLMs can be managed for operational use by containing it within a deterministic "sandbox" of rules that validate, correct, and audit their outputs.
- **Evidence anchors:**
  - [section 3.2] "The pilot system introduced a configurable framework... sequences of configurable actions for pre-processing and post-processing... Every action... is recorded in an immutable audit log."
  - [section 5.2] "Redaction Safety: ...regex- and format-based verifiers are applied prior to commit. The immutable audit log binds suggested items, operator selections, redaction coordinates, and the final file hash."
- **Break condition:** If the rule-based post-processing layer cannot consistently catch VLM errors (e.g., schema validation failures, false positives in PII) to an acceptable operational threshold, the system's outputs become too unreliable for the AI2L pattern to be efficient.

### Mechanism 3
- **Claim:** Adoption in risk-averse public sector organizations is facilitated by a **preliminary, interactive ROI model** used as a communication and business-case tool, not as a definitive forecasting engine.
- **Mechanism:** A web-based calculator allows each authority to input their specific variables (application volume, officer cost). It generates projected savings (hours, FTE, net benefit, payback period). Its primary function is to structure value conversations between technical teams, managers, and budget holders.
- **Core assumption:** Quantifying potential time savings in familiar terms (FTEs, £) is a critical enabler for securing managerial buy-in and partner participation in a pilot, overcoming the "how do we know this is worth it?" barrier.
- **Evidence anchors:**
  - [abstract] "a preliminary Return on Investment (ROI) model developed to quantify potential savings and secure partner participation."
  - [section 5.3] "The model... was not used to make definitive predictions but to structure the value conversation and create a shared understanding... It provided a transparent framework for discussion and was instrumental in securing the management buy-in."
- **Break condition:** If the ROI model's assumptions are so unconvincing or opaque that they fail to generate management buy-in for the pilot phase, the project stalls at the adoption stage, regardless of technical merit.

## Foundational Learning

- **Concept: AI-in-the-Loop (AI2L)**
  - *Why needed here:* It is the foundational sociotechnical paradigm that distinguishes this system from a "human-in-the-loop" exception handler. Understanding AI2L is key to grasping why every output is suggested, not automatic, and why human accountability is preserved.
  - *Quick check question:* What is the single most important design decision that ensures legal accountability remains with the planning officer? (Answer: The requirement for explicit human confirmation on every AI-generated suggestion before commit).

- **Concept: Vision-Language Models (VLMs) for Document Understanding**
  - *Why needed here:* The PoC validated that VLMs (like GPT-4, Claude 3) could jointly reason over text *and* layout/visuals in planning documents, enabling tasks like PII detection in images and symbol localization that pure text OCR could not.
  - *Quick check question:* Why is a model that sees both text coordinates and pixel data better suited for finding a 'Scale Bar' on a drawing than a pure text OCR engine? (Answer: It understands the visual symbol and its typical spatial relation to text).

- **Concept: Active Learning Prioritization (vs. Auto-approval)**
  - *Why needed here:* The system is designed to improve from human feedback, but crucially, it does so by using human corrections to *prioritize* which uncertain documents to review next, not by allowing the AI to auto-approval actions. This maintains safety while enabling learning.
  - *Quick check question:* What is the key difference between a system that learns from human corrections by automatically applying them to future similar cases (auto-approval) and the learning approach described here? (Answer: This system only uses feedback to improve future *suggestions*; it never removes the human confirmation step for committed actions).

## Architecture Onboarding

- **Component map:**
  Enterprise App Integration -> Python Backend API -> Configurable Processing Framework -> VLM Provider Gateway
  & Audit Log <- Configurable Processing Framework
  & Rule Packs & Templates -> Configurable Processing Framework

- **Critical path:** Document upload -> Enterprise App calls Backend API -> Framework runs pre-processing -> VLM call(s) -> Framework runs post-processing (validates output) -> Suggestion package (with confidence, overlays) sent back to UI -> Planner reviews & confirms/overrides -> Commit action logged with final file hash.

- **Design tradeoffs:**
  - **API Dependency vs. Control:** Reliance on third-party VLMs (cost, latency, rate limits) vs. maintaining full auditability and deterministic post-processing. Tradeoff: Accept external non-determinism to leverage state-of-the-art models, but contain it with internal rules.
  - **Integration Depth vs. Portability:** Deep UI integration improves adoption but creates coupling to specific enterprise apps. Tradeoff: Favor adoption speed (deep integration) over theoretical ease of porting to another system.
  - **Learning Speed vs. Safety:** Using human corrections for active learning improves models faster, but the "AI2L, not auto-approval" constraint deliberately caps the maximum operational risk. Tradeoff: Sacrifice some efficiency gains for guaranteed human control.

- **Failure signatures:**
  1.  **High Override Rate:** Suggestion acceptance rate drops below a threshold (e.g., <70%) across a authority, indicating model drift or a document type mismatch.
  2.  **Audit Log Gaps:** Missing or incomplete entries for commits, suggesting a bypass of the framework (e.g., direct PDF editing) or a bug in the logging wrapper.
  3.  **VLM Call Failures:** Sustained high rate of fallback prompt triggers or final VLM errors not recovered by retries, indicating prompt or document quality issues.
  4.  **Rule Pack Mismatch:** Recurring validation failures for a specific jurisdiction's documents (e.g., scale regex rejecting all inputs), meaning the local config is incorrect or outdated.

- **First 3 experiments:**
  1.  **"Hello World" Workflow Test:** For a single, simple metadata field (e.g., 'Application Date'), verify the full pipeline: ingest a known document, check the pre-processing output (image), mock the VLM response, verify post-processing normalization, and confirm the UI displays the suggestion. Goal: Establish baseline functionality.
  2.  **PII Redaction Safety Drill:** Process a document with a known, simple PII pattern (e.g., "John Doe, 123 Main St"). Confirm detection, verify the proposed redaction coordinates, perform the commit, and then attempt to recover redacted text from the final PDF using a text extractor. Goal: Validate true content removal and audit binding.
  3.  **Cost & Latency Baseline:** Run a batch of 50 representative documents through the full pipeline (real VLM calls). Measure: a) average cost per document (token accounting), b) 95th percentile latency (p95), c) fallback prompt usage rate. Goal: Establish operational metrics against the PoC claims (~$0.046/doc, ~35 sec/doc).

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How can the system's validation rule set be expanded and integrated with national planning data platforms to maximize its practical utility for planners?
- **Basis in paper:** [explicit] The conclusion states future work will focus on "expanding the set of planning validation rules and deepening the integration with national planning data systems, based on feedback from the pilot."
- **Why unresolved:** The current pilot uses a limited, predefined set of rules. Broader adoption requires understanding which additional validation checks are most valuable across diverse planning contexts and how to interface with external data sources.
- **What evidence would resolve it:** Analysis of pilot feedback identifying high-frequency manual checks not yet automated; successful API integrations with platforms like the Planning Data Platform; metrics showing time saved per new rule type.

### Open Question 2
- **Question:** What is the comparative performance and cost-effectiveness of OCR-free end-to-end models versus the current hybrid OCR+VLM pipeline on heterogeneous, low-quality planning documents?
- **Basis in paper:** [explicit] Future work includes evaluating "the suitability of alternative AI architectures, such as OCR-free models, for handling more heterogeneous document types like unstructured public consultation feedback."
- **Why unresolved:** The current system relies on a classic OCR step, which may degrade on scanned or poorly formatted documents. OCR-free models could offer robustness but have different cost, latency, and accuracy profiles that are not yet measured.
- **What evidence would resolve it:** A controlled benchmark comparing the current pipeline against state-of-the-art OCR-free models (e.g., Donut, Pix2Struct) on a diverse test set of real planning documents, reporting accuracy (F1, mAP) and per-document cost.

### Open Question 3
- **Question:** What are the longitudinal effects of sustained AI2L use on planner trust, cognitive load, and overall human-AI team performance?
- **Basis in paper:** [explicit] The conclusion calls for "dedicated Human-Computer Interaction research... to measure the effects of long-term use and refine the interface."
- **Why unresolved:** The current evaluation (SUS score, acceptance rate) captures initial usability. Long-term dynamics—such as automation bias, deskilling, or adaptation of work routines—are unknown and critical for sustainable deployment.
- **What evidence would resolve it:** A longitudinal field study during the pilot, tracking metrics like time-per-document, correction rates, user confidence surveys, and qualitative interviews over 6-12 months.

### Open Question 4
- **Question:** To what extent do the Proof-of-Concept performance metrics (F1 0.84–0.88, PII recall 0.96) hold under continuous, live operational conditions across the four pilot authorities?
- **Basis in paper:** [inferred] The evaluation section clarifies: "all quantitative results reported in this section derive from the PoC conducted in a controlled setting and do not reflect live usage in the pilot authorities. Real-world data is being collected as part of the Pilot."
- **Why unresolved:** The PoC used a curated, pre-labeled dataset from two authorities. Live deployment introduces variable document quality, new document types, and real human interaction patterns that could affect accuracy and acceptance.
- **What evidence would resolve it:** Publication of the pilot's live evaluation metrics on a held-out, real-time sample, including variance analysis across the four authority types (Table 1) and correlation between model confidence and operator acceptance.

### Open Question 5
- **Question:** How do the accuracy and cost trade-offs between different VLM providers (Google, OpenAI, Anthropic) influence optimal configuration for a cost-sensitive public sector deployment?
- **Basis in paper:** [inferred] Table 6 shows significant per-document cost variance ($0.042–$0.052 for standard paths, $0.071 for fallback), but the paper only reports performance for a single, unspecified "primary path" (Google, $0.046). No comparative accuracy data across providers is provided.
- **Why unresolved:** The system's configurable framework allows model swapping, but the ROI model and deployment decisions require understanding if cheaper providers (OpenAI) yield comparable accuracy to the primary (Google), or if fallback strategies' higher cost are justified by meaningful recall gains.
- **What evidence would resolve it:** A full benchmark reporting intrinsic metrics (F1, mAP, PII recall) for each provider/model path on the same test set, enabling a cost-per-unit-accuracy analysis to inform procurement and configuration.

## Limitations
- Exact VLM model versions, prompt templates, and pre-processing heuristics are undisclosed, hindering performance replication and cost benchmarking.
- The composition and potential biases of the 440-document test set are not detailed, limiting assessment of generalizability.
- The claim that the ROI model "secured partner participation" is based on retrospective feedback, not a controlled study isolating its causal effect.

## Confidence
- **AI2L Utility (Mechanism 1):** Medium. Supported by internal user studies (92% acceptance) but lacks external validation of the "mandatory review" causal effect on trust/adoption.
- **Hybrid Framework Reliability (Mechanism 2):** Medium. Audit logs and safety drills are described, but long-term error rates under real-world variation are unknown.
- **ROI Tool Efficacy (Mechanism 3):** Low. Claims rely on retrospective participant feedback, not pre/post pilot investment decisions.

## Next Checks
1.  **Replicate core metrics** using disclosed model versions (e.g., GPT-4o) and the authors' provided dataset to verify F1/recall/mAP claims.
2.  **A/B test the AI2L pattern**: Deploy a variant with selective auto-approval for high-confidence suggestions; compare acceptance rates, error rates, and operator trust surveys to isolate the effect of *mandatory* review.
3.  **Validate ROI model assumptions**: Conduct structured interviews with pilot partner budget holders to assess whether the tool's projected savings were a decisive factor in participation, vs. other drivers (e.g., regulatory pressure).
