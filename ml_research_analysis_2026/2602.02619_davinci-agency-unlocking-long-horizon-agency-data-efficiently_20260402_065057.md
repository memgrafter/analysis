# daVinci-Agency: Unlocking Long-Horizon Agency Data-Efficiently

## Quick Facts
- **arXiv ID:** 2602.02619
- **Source URL:** https://arxiv.org/abs/2602.02619
- **Reference count:** 40
- **Primary result:** Fine-tuning on 239 mined PR chain trajectories yields a 47% relative improvement on Toolathlon, with trajectories averaging 85k tokens and 116 tool calls.

## Executive Summary
daVinci-Agency addresses the chronic lack of training data for long-horizon agentic tasks by mining authentic, semantically linked Pull Request (PR) sequences from real-world software repositories. This process constructs multi-stage workflows that inherently encode progressive task decomposition, long-term state consistency, and iterative refinement through genuine bug-fix and feature development trajectories. By fine-tuning GLM-4.6 on this highly curated dataset of just 239 samples, the method achieves significant performance gains on the Toolathlon benchmark and demonstrates strong data efficiency, outperforming models trained on datasets orders of magnitude larger. The work proposes that exposure to these real evolutionary chains internalizes robust long-horizon planning and error-correction skills in language models.

## Method Summary
The core innovation is a data construction pipeline that transforms raw GitHub PR history into structured agent training trajectories. It begins by mining a large corpus of PRs, then uses a language model to identify semantically dependent PRs that form a logical chain of development (e.g., a bug report followed by a fix, then a refactor). Each chain is converted into a multi-step agent trajectory where each step corresponds to a PR's description and code changes, with tools (e.g., `git`, `test`) simulating the development environment. A rejection sampling step (score threshold s≥0.8) filters out low-quality or incoherent rollouts. The final output is a dataset of long, coherent chains where each step builds directly on the previous, creating authentic long-horizon dependencies.

## Key Results
- Training on only 239 PR-chain trajectories (avg. 85k tokens, 116 tool calls) yields a **47% relative improvement** on the Toolathlon benchmark versus a baseline model.
- Gains are observed across multiple agentic capabilities, with particular strength in **stable planning and error correction** over extended horizons.
- The approach demonstrates exceptional **data efficiency**, outperforming models trained on substantially larger synthetic or web-crawled datasets.

## Why This Works (Mechanism)
The PR-chain structure provides **natural supervision for three critical meta-skills** required for long-horizon agency:
1.  **Progressive Decomposition:** A long software evolution chain is inherently broken into discrete, meaningful PRs. The agent learns to perceive a high-level goal (e.g., "improve module X") as a sequence of concrete, executable sub-tasks.
2.  **Long-Term Consistency:** Later PRs in a chain depend on the state changes from earlier ones. The agent must maintain and recall context across many steps, learning that actions have persistent effects on the environment state.
3.  **Iterative Refinement:** Real PR chains often involve cycles of bug identification, fix, review, and further adjustment. The agent experiences a realistic loop of execution, observation, diagnosis, and correction.

This supervision is **authentic**—it mirrors how human developers actually work—making the learned policies more robust and generalizable than those trained on synthetic, delusionary, or short-horizon tasks.

## Foundational Learning
*   **Concept:** Pull Request (PR) Sequences
    *   **Why needed:** They are the atomic unit of observable, discrete progress in real-world software evolution, providing a natural "step" in a long-horizon workflow.
    *   **Quick check:** Can you identify a sequence of 3+ PRs from a public repo where each logically follows from the last (e.g., feature-add -> bug-fix -> doc-update)?
*   **Concept:** Semantic Dependency Detection
    *   **Why needed:** To automatically link isolated PRs into coherent chains that represent a continuous line of development, rather than random adjacent commits.
    *   **Quick check:** Does a PR that adds a function have a semantic predecessor that first introduces the need for that function (e.g., a feature request or failing test)?
*   **Concept:** Trajectory Construction via Rollout
    *   **Why needed:** To convert static PR data (description + diff) into a dynamic, interactive agent trajectory with simulated tool calls and environment feedback.
    *   **Quick check:** For a given PR, can you script a sequence of tool actions (`git checkout`, `run test`, `apply patch`) that an agent could execute to "realize" the PR's intent?
*   **Concept:** Rejection Sampling for Coherence
    *   **Why needed:** To ensure the automatically generated rollouts are valid, non-redundant, and maintain logical consistency across the entire chain, filtering out low-quality or broken simulations.
    *   **Quick check:** Would a rollout that fails a test introduced in a prior step, without any corrective action, be considered a coherent part of the chain?
*   **Concept:** Progressive Supervision for Decomposition
    *   **Why needed:** The chain structure explicitly teaches the model that high-level objectives must be broken into the specific, ordered sub-objectives represented by each PR.
    *   **Quick check:** Does the trajectory for a 5-PR chain clearly show a high-level goal being achieved through 5 distinct, dependent sub-goals?

## Architecture Onboarding
**Component Map:**  
Raw GitHub PR Corpus -> Semantic Chain Miner -> Rollout Simulator -> Rejection Filter -> Training Trajectories

**Critical Path:**  
The data construction pipeline. The quality of the final training set is entirely dependent on the success of (1) identifying correct semantic chains and (2) generating coherent, interactive rollouts for each PR in the chain. Failure at either stage corrupts the long-horizon signal.

**Design Tradeoffs:**  
*   **Chain Length vs. Success Rate:** Longer chains provide richer long-horizon signal but have exponentially lower construction success rates, limiting dataset size and diversity.
*   **Authenticity vs. Cleanliness:** Using real PR data ensures authenticity but introduces noise (e.g., merge conflicts, incomplete descriptions) that must be filtered, potentially discarding valid but messy real-world examples.
*   **Dataset Size vs. Quality:** The rejection sampling threshold (s≥0.8) prioritizes high-quality, coherent trajectories but drastically reduces the number of usable samples (to 239).

**Failure Signatures:**  
*   **Short Chains:** Final dataset dominated by 1-2 PR chains indicates the chain miner or rollout simulator is failing to link or simulate longer sequences.
*   **Repetitive Patterns:** Many trajectories follow identical tool call sequences suggests the rollout simulator is generating template-based, non-adaptive behavior.
*   **Low Rollout Scores (s<0.8):** Success rate collapse means the coherence validator is too strict or the simulator cannot handle the complexity of linked PRs.

**First 3 Experiments:**
1.  **Ablate Chain Linking:** Train a model on a version of the dataset where the order of PRs in each chain is shuffled. Measure degradation on Toolathlon to quantify the value of correct temporal ordering.
2.  **Threshold Sweep:** Create training sets with rejection thresholds at 0.7, 0.8, and 0.85. Compare model performance on long-horizon benchmarks to find the optimal quality/diversity trade-off.
3.  **Skill-Probing Evaluation:** Design a minimal diagnostic suite that tests for the three claimed meta-skills (decomposition, consistency, refinement) in isolation. Evaluate the daVinci-trained model against a baseline on this suite.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the success rate in constructing longer PR chains be improved to enable chains beyond the current maximum of 5 PRs?
- **Basis in paper:** [explicit] The authors explicitly state in the Conclusion (page 11): "Currently, constrained by the success rates, our implementation connects a maximum of 5 PRs to construct task chains... Future work will focus on overcoming current success rate bottlenecks to construct even longer evolutionary chains."
- **Why unresolved:** The success rate bottleneck limits the creation of longer-horizon dependencies, preventing exploration of more complex, realistic software evolution trajectories that could further enhance agent capabilities.
- **What evidence would resolve it:** Developing and evaluating techniques to increase rollout success rates (e.g., better agent scaffolds, improved dependency detection) and demonstrating successful construction and training on chains with 6 or more PRs, with corresponding performance gains on long-horizon benchmarks.

### Open Question 2
- **Question:** What is the optimal PR chain length for different model scales and architectures to maximize long-horizon task performance?
- **Basis in paper:** [inferred] The paper shows performance improvements when increasing average trajectory length from ~59K to ~85K tokens (Section 6.3) and notes that MoE models benefit more (Section 5.4). However, experiments only used chains up to 5 PRs; the optimal chain length as a function of model capacity remains unexplored.
- **Why unresolved:** While longer chains generally help, the relationship may not be monotonic; smaller models might saturate or degrade with overly long chains, and optimal length likely varies with architecture.
- **What evidence would resolve it:** A systematic study training models of varying sizes (e.g., 8B, 32B, 70B) and types (dense, MoE) on datasets with PR chains of different lengths (e.g., 1 to 10 PRs), measuring scaling curves on benchmarks like SWE-bench and Toolathlon to identify optimal points.

### Open Question 3
- **Question:** To what extent do the three targeted meta-skills—task decomposition, long-term consistency, and iterative refinement—individually contribute to the observed gains from daVinci-Agency?
- **Basis in paper:** [inferred] The authors claim daVinci-Agency teaches these skills via PR chain structure (Sections 1, 4) and provides qualitative examples (Section 5.4, Figure 5). The ablation compares full chains vs. single PRs vs. temporal chains but does not isolate each skill’s specific impact.
- **Why unresolved:** The combined nature of the PR chain supervision makes it impossible to disentangle which skill(s) drive the improvement; this limits understanding of the core mechanisms for teaching long-horizon agency.
- **What evidence would resolve it:** Designing controlled dataset variants that selectively remove or alter one skill at a time—e.g., chains requiring decomposition but not refinement, or chains with broken consistency—and comparing model performance on targeted probing tasks for each skill.

### Open Question 4
- **Question:** How sensitive is the quality and utility of daVinci-Agency data to the rejection sampling threshold (s≥0.8), and could a more principled threshold improve results?
- **Basis in paper:** [explicit] The paper uses a fixed threshold of 0.8 for rejecting low-quality rollouts (Section 4.3). Appendix B shows an ablation comparing rejection sampling vs. none, but does not vary the threshold value itself.
- **Why unresolved:** The threshold is chosen arbitrarily; a higher threshold may yield higher-quality but fewer samples, while a lower threshold may introduce noise. The optimal trade-off for downstream performance is unknown.
- **What evidence would resolve it:** Conducting a sensitivity analysis by creating training sets with different thresholds (e.g., 0.7, 0.75, 0.85, 0.9), comparing model performance on long-horizon benchmarks, and analyzing diversity metrics (e.g., uniqueness of trajectories) to find the optimal balance.

## Limitations
- **Extremely small training set:** Only 239 samples were used, raising major questions about generalizability beyond the specific software engineering domain and potential overfitting.
- **Limited benchmark validation:** Gains are demonstrated primarily on Toolathlon; performance on other standard long-horizon agent benchmarks (e.g., WebArena, AgentBench) is not reported, and contamination from the web-crawled PR corpus is a risk.
- **Data and model opacity:** The constructed PR-chain dataset and full fine-tuning details for GLM-4.6 are not publicly released, preventing independent verification and exact replication.
