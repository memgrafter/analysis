# Index Light, Reason Deep: Deferred Visual Ingestion for Visual-Dense Document Question Answering
## Quick Facts
*   **arXiv ID:** 2602.14162
*   **Source URL:** https://arxiv.org/abs/2602.14162
*   **Reference count:** 0
*   **Primary result:** Deferred Visual Ingestion (DVI) achieves 65.6% end-to-end QA accuracy on engineering drawings, a +41.3 percentage point improvement over Pre-Ingestion (24.3%).

## Executive Summary
Visual-dense document question answering (e.g., for engineering drawings) fails with conventional Pre-Ingestion (PI), where a Vision-Language Model (VLM) generates generic, query-agnostic descriptions of every page during indexing. These "blind descriptions" irreversibly lose critical visual details. This paper proposes Deferred Visual Ingestion (DVI), which eliminates VLM preprocessing entirely. Instead, it builds a lightweight, hierarchical index from document structure (TOC, drawing numbers) using the Hierarchical Drawing Number Clustering (HDNC) algorithm. At query time, BM25 retrieval locates candidate pages, and the original page images are sent along with the specific question to a VLM for targeted analysis. On challenging datasets (Bridge, Steel catalog, CircuitVQA), DVI dramatically outperforms PI and embedding-based methods (like ColPali) across retrieval and end-to-end QA, proving that retrieval is the primary bottleneck.

## Method Summary
DVI consists of two phases. In **Indexing**, a PDF parser extracts text layers, the Table of Contents (TOC), and drawing numbers. The HDNC algorithm processes drawing numbers to automatically discover hierarchical groupings (e.g., "Pier-3 Details") by balancing a trie on numeric suffixes and validating group coherence via Jaccard similarity with titles. This structure, combined with titles and optional OCR text, populates a document for a standard BM25 index—no VLM or embedding is used. In **Inference**, a user query is matched against the BM25 index to retrieve top-k candidate pages. The original rasterized images for these pages are then passed, alongside the query, to a VLM to produce the final answer. This defers all expensive, lossy visual analysis until the query is known and the relevant pages are identified.

## Key Results
*   On the Bridge dataset (1,323 questions), DVI achieves 65.6% end-to-end accuracy vs. PI's 24.3% (+41.3pp).
*   DVI's retrieval (PageR@3) dramatically outperforms PI and ColPali: Bridge (68.0% vs. 30.7% vs. 20.1%), Steel catalog (65.6% vs. 23.1%), CircuitVQA (ImgR@3: 31.2% vs. 0.7%).
*   The HDNC auto-indexing component contributes a +27.5 percentage point gain in retrieval recall over using titles only.
*   The VLM's accuracy on questions given the *correct* page exceeds 93% for both DVI and PI, confirming that retrieving the right page is the overwhelming bottleneck.

## Why This Works (Mechanism)
### Mechanism 1: Deferred Visual Ingestion Prevents Irreversible Detail Loss
**Claim:** Deferring VLM analysis to inference time prevents the irreversible information loss caused by VLM "blind descriptions" generated during preprocessing.
**Mechanism:** PI requires invoking a VLM on every page during indexing to create a generic, query-agnostic text summary. DVI skips this step entirely. At query time, only the top-k pages found by retrieval are sent to the VLM, along with the specific user question. This directs the VLM's attention to the relevant visual details on a lossless image, significantly improving analysis fidelity.
**Core Assumption:** A VLM's accuracy on a specific visual query is much higher when processing the original high-fidelity image with a concrete question, compared to summarizing an entire page for an unknown future query.
**Evidence Anchors:**
*   [abstract] States PI's VLM descriptions "inevitably lose critical visual details" and DVI sends "original images along with the specific question to a VLM for targeted analysis."
*   [section 1.2] PI errors are "unidirectional and irreversible" because the original image is discarded after preprocessing.
*   [section 4.3.2] VLM conversion rate (accuracy given correct page) exceeds 93%, proving the VLM itself is not the bottleneck; the key is delivering the correct page.
*   [corpus] Prior work like VisRAG [2] and M3DocRAG [4] still use VLM at indexing, making DVI's zero-VLM-indexing a key differentiator.
**Break Condition:** If VLM capability degrades substantially when analyzing high-resolution, complex images with multi-focal queries at inference time, or if inference latency (20-40s/query) is unacceptable.

### Mechanism 2: HDNC Leverages Structure for Precise, Low-Cost Indexing
**Claim:** Hierarchical Drawing Number Clustering (HDNC) automatically builds a high-recall, discriminative index from document structure (drawing numbers, TOC) without any VLM or embedding cost.
**Mechanism:** HDNC exploits the hierarchical naming conventions in engineering drawing numbers (e.g., `PROJID-GRP-PKG-ST-BR-DR-101013`). It extracts numbers, finds the longest common prefix, splits numeric suffixes into optimal segments via a balanced Trie, and infers group labels from title co-occurrence using Jaccard validation. This creates a multi-level taxonomic index (e.g., "Details/Pier/Pier-3") that is far more effective for BM25 retrieval than flat titles or noisy full text.
**Core Assumption:** Within a single engineering project, drawing numbers follow consistent conventions that encode semantic categories aligned with user query intent.
**Evidence Anchors:**
*   [abstract] "HDNC auto-indexing yields a +27.5pp retrieval gain" and recall "surpassing that of manually curated metadata extracted by VLMs."
*   [section 3.2] Full algorithm pipeline; 94% Jaccard validation (64/68 groups) empirically confirms the assumption on the Bridge dataset.
*   [section 4.4.1] Ablation shows HDNC-auto (+27.5pp) significantly outperforms title-only and competes with VLM-extracted manual metadata.
**Break Condition:** If target documents lack structured numbering systems or a usable TOC. DVI would then degrade to TOC parsing or pure BM25 full-text search, losing the hierarchical advantage.

### Mechanism 3: BM25 Matching Outperforms Embeddings on Homogeneous, Identifier-Rich Docs
**Claim:** For visually and semantically homogeneous document sets (e.g., all drawings for a bridge project), BM25's exact keyword matching on structured identifiers (drawing numbers, titles, HDNC labels) systematically fails less than dense embedding retrieval, which suffers from vector collapse.
**Mechanism:** Engineering queries often contain precise identifiers (e.g., `PROJID-GRP-PKG-ST-BR-DR-501521`, "Pier-3"). BM25 directly matches these tokens in the index. In contrast, embedding models map near-identical pages (e.g., all pier details for a bridge type) into highly similar vectors, causing retrieval collapse where the correct page is not distinguished from its neighbors.
**Core Assumption:** In highly similar document clusters, semantic similarity metrics fail to discriminate between pages that differ only in critical identifiers; exact matching on those identifiers is reliable.
**Evidence Anchors:**
*   [abstract] Contrasts retrieval: Bridge PageR@3 68.0% (DVI) vs. 30.7% (PI) vs. 20.1% (ColPali). Calls ColPali's failure "structural rather than due to insufficient model capability."
*   [section 4.2.1] Head-to-head: ColPali and PI-embedding have different hit patterns but both fail systematically due to "highly similar documents... vectors cluster tightly."
*   [section 3.5] Theoretically contrasts BM25's exact matching with embedding's "semantic approximation" on identifier-rich docs.
**Break Condition:** If user queries are purely descriptive without any identifier (e.g., "show a typical pier detail"), BM25 may fail where semantic embedding could succeed. Also, if the text layer is absent/corrupted, BM25 fails.

## Foundational Learning
*   **Concept: Vision Language Model (VLM)**
    *   **Why needed here:** DVI's inference step uses a VLM to answer questions from original page images. Understanding its multimodal reasoning capabilities and limitations (e.g., detail hallucination) is key to trusting final answers.
    *   **Quick Check:** What is a key difference between a VLM (e.g., GPT-4V) and a pure LLM in document QA?
*   **Concept: BM25 Retrieval**
    *   **Why needed here:** BM25 is DVI's core retrieval engine. Knowing it's a probabilistic keyword matcher (not semantic) explains its strength on identifier-rich queries and its dependence on text quality.
    *   **Quick Check:** How does BM25's scoring differ from vector cosine similarity, and what query types favor BM25?
*   **Concept: Engineering Drawing Numbering Conventions**
    *   **Why needed here:** HDNC's premise is that drawing numbers (e.g., `BR-DR-501521`) are structured. Understanding standards (ISO, ANSI) and common patterns (project, discipline, sheet sequence) grounds HDNC's design.
    *   **Quick Check:** In a number like `A-101-FOUND-02`, what might each segment hierarchically represent?
*   **Concept: OCR & Text Fusion**
    *   **Why needed here:** DVI optionally fuses OCR text with BM25. Understanding OCR's variable quality and its impact on keyword retrieval is crucial for the adaptive strategy.
    *   **Quick Check:** Why might OCR text from scanned engineering drawings be particularly noisy, and how could that hurt BM25 retrieval?
*   **Concept: Vector Collapse in Embedding Retrieval**
    *   **Why needed here:** The paper identifies a key failure mode: embedding models produce near-identical vectors for highly similar documents, causing retrieval collapse. This explains DVI's rationale for avoiding embeddings.
    *   **Quick Check:** What property of a document corpus makes dense embedding retrieval prone to "collapse," and why does exact keyword matching avoid this?

## Architecture Onboarding
*   **Component Map:** PDF Parser -> TOC/Drawing Number Extractor -> HDNC -> Index Document Builder (titles + HDNC labels + [optional] OCR text) -> BM25 Index. Inference: User Query -> BM25 Retrieval (top-k pages) -> Image Renderer -> VLM (original image + query) -> Answer.
*   **Critical Path:** Query -> BM25 Retrieval (correct page localization) -> VLM Visual Answering. Experiments show VLM conversion rate >93% given correct page, proving **retrieval is the sole bottleneck**.
*   **Design Tradeoffs:**
    *   *Zero VLM indexing cost* vs. *Inference-time VLM latency*: DVI saves massive preprocessing but adds 20-40s/query. Mitigated by caching (PKA).
    *   *Structural index precision* vs. *Flexibility*: HDNC excels on standardized drawings but fails on unstructured docs, requiring fallbacks.
    *   *Text fusion*: For vector PDFs, fusing clean text helps (+21.3pp). For low-quality scans, it hurts (-40.9pp). Requires adaptive per-page strategy.
*   **Failure Signatures:**
    *   **Retrieval failure:** Low PageR@3 despite correct HDNC indexing -> Check text fusion (noisy OCR harming BM25?) or query lacks identifiers (BM25 cannot match).
    *   **HDNC failure:** Jaccard validation fails (< threshold) -> Documents lack coherent numbering scheme -> Fallback to TOC-only or full-text.
    *   **VLM failure:** Low conversion rate given correct page -> Image quality too poor (blurred scan), or VLM cannot read tiny notations. Rare per experiments (>93%).
*   **First 3 Experiments:**
    1.  **Main retrieval comparison:** Run DVI (HDNC+text) vs. PI (VLM blind desc + embedding) vs. ColPali on Bridge. Expect DVI PageR@3 ~68%, PI ~30%, ColPali ~20%. Validates that embedding fails structurally on homogeneous sets.
    2.  **HDNC ablation:** On Bridge subset, compare `title-only` vs. `HDNC-auto` vs. `VLM-manual metadata`. Expect HDNC-auto +27.5pp gain over title-only, and even surpass manual in recall, proving zero-cost auto-indexing efficacy.
    3.  **Text quality adaptiveness test:** On Bridge (vector PDF) vs. Steel (scanned) with/without OCR text fusion. Expect Bridge: +21.3pp gain with text. Steel: -40.9pp degradation. Demonstrates need for adaptive text inclusion.

## Open Questions the Paper Calls Out
1.  How does DVI perform on real-world engineering queries versus the synthetic QA datasets used in the study?
2.  What automated method can reliably assess per-page OCR quality to enable adaptive text fusion in DVI?
3.  How effective is Progressive Knowledge Accumulation (PKA) at reducing inference latency and VLM costs in DVI over time?
4.  Does DVI generalize to other engineering domains (e.g., architecture, mechanical, electronics) beyond the two tested datasets?

## Limitations
*   **HDNC generalizability:** Relies on consistent, hierarchical drawing number schemes; performance on documents without such structure is unbenchmarked and expected to degrade.
*   **Text fusion adaptiveness:** Requires a per-page OCR quality metric to decide text inclusion; this is left for future work and is critical for heterogeneous scanned collections.
*   **Proprietary data & models:** Key results are on private datasets (Bridge, Steel) using proprietary models (Gemini 3.1 Pro, text-embedding-004), limiting reproducibility and potentially overstating gains vs. open-source alternatives.

## Confidence
*   **Mechanism 1 (Deferred Ingestion):** **Medium** Confidence. Strong evidence (VLM conversion >93% with correct page), but assumes VLM fidelity holds for high-res, complex, query-directed analysis at inference time. Latency trade-off acknowledged but not deeply analyzed for real deployments.
*   **Mechanism 2 (HDNC):** **Medium-High** Confidence for structured engineering documents (94% Jaccard validation). **Low** Confidence for generalizability; it fails on documents without consistent numbering.
*   **Mechanism 3 (BM25 vs. Embeddings):** **High** Confidence for identifier-rich, homogeneous sets (engineering drawings). **Low** Confidence for semantically diverse or purely descriptive queries; paper does not test hybrid strategies.
*   **Overall Limitation:** The system's reliance on a high-quality text layer for BM25 is a major point of fragility, and the adaptive threshold for text fusion is unspecified.

## Next Checks
1.  **Stress-test HDNC generalizability:** Apply the full DVI pipeline (with adaptive text fusion) to publicly available document collections lacking structured numbering (e.g., historical archives, mixed-discipline reports). Measure retrieval degradation against a TOC-only baseline to quantify HDNC's domain dependence.
2.  **Query diversity analysis:** On the Bridge/Steel datasets, curate a balanced subset of queries: (a) with exact drawing numbers/IDs, (b) with partial identifiers, (c) purely descriptive. Compare DVI (BM25) vs. PI (embedding) performance per query type to map the exact failure boundary of keyword matching.
3.  **VLM robustness & latency audit:** Benchmark the final VLM QA step across 3+ model families (e.g., GPT-4o, Claude 3.5 Sonnet, LLaVA) on correctly retrieved pages. Record both accuracy (conversion rate) and inference latency per page to validate the ">93% conversion" claim and assess real-time feasibility of deferred ingestion.
