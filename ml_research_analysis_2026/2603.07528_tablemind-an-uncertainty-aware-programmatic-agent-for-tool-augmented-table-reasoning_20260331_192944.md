# TableMind++: An Uncertainty-Aware Programmatic Agent for Tool-Augmented Table Reasoning

## Quick Facts
- arXiv ID: 2603.07528
- Source URL: https://arxiv.org/abs/2603.07528
- Reference count: 40
- Primary result: Achieves state-of-the-art on five table reasoning benchmarks (WikiTQ, TabMWP, TabFact, HiTab, FinQA) and outperforms TableMind and strong baselines like GPT-5 and Deepseek-R1.

## Executive Summary
TableMind++ is an uncertainty-aware programmatic agent for tool-augmented table reasoning. It extends the TableMind framework with inference-time mechanisms to explicitly address epistemic (logical plan) and aleatoric (syntactic noise) uncertainties. By integrating memory-guided plan pruning, confidence-based action refinement, and dual-weighted trajectory aggregation, the agent reduces hallucinations while maintaining high accuracy. The system is trained via a two-stage pipeline: supervised fine-tuning on distilled trajectories followed by reinforcement learning with Rank-Aware Policy Optimization (RAPO). Evaluated on diverse benchmarks, TableMind++ sets new records and demonstrates that self-consistency-level accuracy can be attained at a fraction of the computational cost.

## Method Summary
TableMind++ begins with a lightweight LLM (Qwen3-8B) that undergoes supervised fine-tuning on a small, high-quality dataset (200 samples) to learn the structured thought-action-observation loop. This is followed by reinforcement learning using RAPO, which optimizes the multi-step tool-use policy without a KL penalty and employs token-level loss normalization to encourage exploration. During inference, the agent samples multiple candidate reasoning plans. Each plan is converted to an abstract action sequence and pruned using a dual-memory bank of successful and failed trajectories via edit-distance scoring. For retained plans, the model generates Python code while monitoring confidence over semantically significant tokens; low-confidence code is re-generated before execution. Finally, answers from multiple trajectories are aggregated using a dual-weight combining structural validity and execution confidence. This pipeline yields robust, executable programs with minimal hallucination.

## Key Results
- SOTA performance: WikiTQ (78.07%), TabMWP (99.57%), TabFact (93.73%), HiTab (73.69%), FinQA (45.48%).
- Improves upon TableMind: +1.25 (WikiTQ), +0.30 (TabMWP), +1.88 (TabFact).
- Outperforms strong baselines including GPT-5 and Deepseek-R1 across in-domain and out-of-domain settings.

## Why This Works (Mechanism)
TableMind++ tackles two fundamental uncertainty sources in table reasoning: epistemic (knowledge/logic gaps) and aleatoric (sampling noise). Memory-guided plan pruning reduces epistemic uncertainty by abstracting candidate plans into action sequences and comparing them to prototypes from a dual-memory bank (successful/failed). Plans with high edit distance to successes or close to failures are discarded, filtering logically implausible reasoning; ablations confirm this component is most critical. Confidence-based action refinement mitigates aleatoric noise by computing token-level confidence over high-information identifiers, literals, and keywords; code below a confidence threshold is re-generated, catching syntactic errors before execution. Dual-weighted trajectory aggregation then combines answers from multiple verified trajectories, weighting each by the product of plan structural soundness and execution confidence, yielding a more reliable consensus than majority vote. Together, these mechanisms enable high accuracy with minimal hallucinations.

## Foundational Learning
- **Reinforcement Learning with RAPO**: Why needed: To optimize the agent’s multi-step tool-use policy beyond imitation, aligning long-horizon actions with task success. RAPO addresses reward misalignment by re-weighting gradients based on confidence-reward discrepancies. Quick check: Why does RAPO eliminate the KL penalty and use token-level loss normalization? To free exploration from reference policy constraints and mitigate length bias.
- **Supervised Fine-Tuning (SFT) Warm-up**: Why needed: To bootstrap the model with the thought-action-observation loop and basic code syntax before RL, providing a stable initial policy that accelerates convergence and prevents early catastrophic failures. Quick check: Why use only 200 SFT samples? To avoid overfitting and preserve exploration flexibility; it serves as a behavioral warm-start, not a full solution.
- **Uncertainty Quantification (UQ) Taxonomy**: Why needed: To systematically address different LLM failure sources: epistemic (knowledge/logic gaps) requires external validation (memory), aleatoric (sampling noise) requires monitoring (token probabilities). Treating all uncertainty alike leads to ineffective mitigation. Quick check: How does the paper distinguish epistemic vs. aleatoric uncertainty? Epistemic = flawed logical plan structure; Aleatoric = noisy token generation in code even with a correct plan.

## Architecture Onboarding
Component map: Qwen3-8B base model -> SFT training (200 samples, 1 epoch) -> RFT model (via RAPO RL). At inference: generate N=16 candidate plans -> memory-guided pruning (retrieve top-K=5 prototypes from dual-memory, edit distance scoring, retain top ρ=0.5) -> for each pruned plan: generate Python code, compute confidence on high-information tokens, if C(a) < τ=0.8 then self-correct -> execute code to get answer -> dual-weighted aggregation (weight w_i = σ(S_con(p_i)) * C(h_i)) -> final answer by argmax sum of weights per unique answer.

Critical path: Input query -> sample multiple plans -> prune via memory -> generate and refine code per plan -> execute -> aggregate answers.

Design tradeoffs:
- Plan pruning: Memory size K trades off noise vs. coverage; pruning ratio ρ trades off conservatism vs. diversity.
- Action refinement: Threshold τ trades off false positives (over-correction) vs. false negatives (missed noise); token selection heuristic K is brittle to code style variations.
- Aggregation: Dual-weighting may over-weight paths with high S_con but subtle errors if memory prototypes are imperfect.

Failure signatures:
- Plan pruning fails on novel query types with no similar memory patterns, discarding valid plans.
- Action refinement fails if τ is too strict or token selection misses critical tokens, corrupting valid code or missing hallucinations.
- Aggregation fails if multiple trajectories share a systematic error (e.g., misinterpreting a header), leading to incorrect consensus.

First 3 experiments:
1. Ablation study: Remove each uncertainty component (pruning, refinement, aggregation) individually to isolate contributions; expect largest drop from pruning.
2. Sensitivity analysis: Vary memory retrieval size K and confidence threshold τ across benchmarks to find optimal defaults and observe task-dependent preferences.
3. Comparative evaluation: Benchmark full TableMind++ against TableMind and strong baselines (GPT-5, Deepseek-R1) on in/out-of-domain datasets to validate SOTA and generalization.

## Open Questions the Paper Calls Out
- How can TableMind++ be extended to handle multi-table reasoning scenarios where a query spans multiple tables? The current design processes a single table per query; multi-table reasoning introduces challenges like table identification, schema alignment, and cross-table operations.
- Can TableMind++ incorporate a broader spectrum of data science tools beyond Python code execution? The agent currently uses a fixed Python sandbox; other tasks may benefit from specialized tools like SQL engines, statistical packages, or visualization libraries.
- How can the sample efficiency of the reinforcement learning fine-tuning (RFT) stage be improved? RFT requires many environment interactions; higher sample efficiency would reduce computational costs and training time.

## Limitations
- SFT data filtering criteria (quality thresholds, diversity metrics) are unspecified, risking reproduction variability.
- RAPO’s rank-aware weight factor α is undisclosed, obscuring its contribution to RL stability.
- Token selection heuristic for action refinement and memory bank construction (size limits, recency) are ambiguous, affecting reliability.
