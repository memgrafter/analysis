# Executive Summary
APEX is an agentic framework for interactive academic poster editing that combines robust multi-level API-based editing with a review-and-adjustment mechanism. It introduces APEX-Bench, a benchmark of 514 human‑verified instructions derived from 59 AI conference papers, categorized by operation type, difficulty, and abstraction. The system uses a zero‑shot prompted Gemini‑3‑Flash‑Preview model to parse posters into JSON, plan API edits, execute them with fault tolerance, and then review the output via a VLM to ensure visual fidelity. Evaluation via a VLM‑as‑a‑judge protocol shows APEX significantly outperforms regeneration‑based and generic slide‑editing baselines across instruction fulfillment, modification scope, and visual consistency.

# Method Summary
The core of APEX is a two‑component pipeline. First, a semantic parser converts a .pptx poster into a structured JSON representation capturing element types, positions, attributes, and media. A planning agent (Gemini‑3‑Flash‑Preview) then generates a sequence of 14 fine‑grained API calls (e.g., insert_textbox, set_element_position) to enact the user’s instruction, optionally invoking a paper understanding tool (Docling + VLM) to extract relevant content or figures from the source PDF. The API executor runs these calls sequentially with pre‑call validation and exception handling to ensure robustness. After editing, a review agent evaluates the modified poster image using the same VLM and, if needed, issues a corrective API sequence. The entire process is zero‑shot; no model training is performed. Evaluation on the APEX‑Bench dataset uses the same VLM to score instruction fulfillment, modification scope, and visual consistency.

# Key Results
- APEX attains SOTA on APEX‑Bench: Instruction Fulfillment 7.97, Modification Scope 9.04, Visual Consistency 7.18 (10‑point scale).  
- The system maintains a 0% execution error rate due to fault‑tolerant API execution.  
- The monetary cost per edit is low at $0.022 (Gemini‑3‑Flash‑Preview pricing).

# Why This Works (Mechanism)
APEX succeeds because its design separates concerns: the multi‑level API layer provides precise, localized control over poster elements, avoiding the bloat and fragility of monolithic script generation. The API granularity allows the planner to make targeted changes and the executor to recover from individual failures. The review‑and‑adjustment loop acts as a safety net, catching subtle visual inconsistencies (e.g., alignment, color harmony) that the planning agent might miss. Together, these components yield high instruction fidelity and robust execution while keeping costs low through efficient API calls and the use of a cost‑effective model.

# Foundational Learning
- **Semantic Parsing of PPTX**: Converts binary .pptx to a machine‑readable JSON with element IDs, geometry, and styling. *Why needed*: Enables the agent to reason about and modify the poster structure. *Quick check*: Parse a sample poster and verify that all shapes, text boxes, and images are captured with accurate coordinates.  
- **Function‑Calling with VLMs**: Uses the model’s tool‑calling capability to generate a sequence of API calls. *Why needed*: Allows the agent to express a complex edit plan in a structured, executable form. *Quick check*: Provide a simple instruction and check that the output includes valid API calls with correct parameters.  
- **Fault‑Tolerant Execution**: Wraps each API call in exception handling and continues despite partial failures. *Why needed*: Prevents a single invalid operation from aborting the entire edit, increasing robustness. *Quick check*: Inject an invalid element ID and confirm the system logs the error but proceeds.  
- **VLM‑Based Review & Adjustment**: After editing, a VLM judges visual consistency and may trigger a second pass. *Why needed*: Addresses the limitation of pure API execution that may overlook aesthetic or layout issues. *Quick check*: Introduce a deliberate misalignment and see if the review agent initiates a correction.  
- **Paper Understanding with Docling**: Extracts text, figures, and tables from the source PDF. *Why needed*: Provides authoritative content for accurate insertion into the poster. *Quick check*: Run Docling on a PDF and verify that figures and captions are correctly identified and saved.

# Architecture Onboarding
Component map:  
PPTX Parser -> JSON -> Planner (with optional PaperTool) -> API Executor (fault‑tolerant) -> Edited PPTX -> LibreOffice Renderer -> PNG Image -> Review Agent (VLM) -> if needs_adjustment: Adjustment Planner -> API Executor (loop) -> final PNG  

Critical path: The main flow without review: parse → plan → execute → render. Review adds an optional second planning‑execution‑render cycle.  

Design tradeoffs:  
- Fine‑grained APIs give precise control and error isolation but require more calls and sophisticated planning compared to generating a monolithic script.  
- The review step improves visual quality but adds cost and latency; it may be reduced if the base planner improves.  
- Dependency on LibreOffice and Docling introduces external tool maintenance and version sensitivity.  

Failure signatures:  
- API pre‑call validation failures (e.g., element not found) indicate planner hallucination or stale JSON.  
- Review agent repeatedly flagging the same issue suggests a systematic planner weakness.  
- Rendering discrepancies between LibreOffice versions could mislead the VLM judge.  
- Unexpectedly high API count or token usage may signal inefficient planning.  

First three experiments:  
1. Validate the semantic parser by comparing the output JSON of a known poster against manual annotation.  
2. Test the planner on a set of 10 simple instructions (e.g., font changes, repositioning) and measure the accuracy of generated API sequences.  
3. Run the full pipeline on one APEX‑Bench instance and confirm that the VLM judge scores are consistent with the expected direction of improvement over baselines.

# Open Questions the Paper Calls Out
1. **Scaling to more powerful frontier models**: How would using models like Gemini‑3‑Pro affect performance, error rates, and cost? The paper only tested Gemini‑3‑Flash‑Preview and smaller Qwen models due to resource constraints.  
2. **Redundancy of the review mechanism**: If base models become significantly more capable, could the review‑and‑adjustment step be removed without loss of quality? The ablation study shows it currently helps, but its necessity with stronger planners is unknown.  
3. **Cross‑domain generalization**: APEX‑Bench covers only AI conference papers (ICLR, ICML, NeurIPS). How well does the system generalize to posters from other fields (e.g., biology, humanities) with different visual conventions?  
4. **Detailed failure analysis of API execution**: The paper reports 0% execution errors, but the specific residual error types (e.g., coordinate miscalculations, invalid references) and how they differ from regeneration baselines are not dissected.  
5. **Robustness of VLM‑as‑a‑judge**: The evaluation relies on a single VLM (Gemini‑3‑Flash‑Preview) with author‑defined rubrics. Its alignment with human expert judgment across diverse poster styles remains unverified, and potential biases are unexplored.

# Limitations
- **Dataset availability**: APEX‑Bench is not publicly released, preventing independent verification of results and further research.  
- **Implementation ambiguities**: The exact JSON schema for poster elements and the full details of the review agent prompt (e.g., extracted_visuals_details) are unspecified, making exact replication difficult.  
- **Baseline reconstruction**: The prompts and code for prior slide‑editing agents (PPTC, Talk‑to‑Your‑Slides) are incomplete, so reproduced baselines may not match the original comparisons.
