# FDA AI Search: Making FDA-Authorized AI Devices Searchable

## Quick Facts
- **ArXiv ID:** 2602.00006  
- **Source URL:** https://arxiv.org/abs/2602.00006  
- **Reference count:** 8  
- **Primary result:** Hybrid retrieval achieves 97.6% Hit Rate@5 for disease+modality queries with 0.38 s mean inference time.

## Executive Summary
FDA-authorized AI medical devices number over 1,200, but identifying specific ones is difficult due to limited searchable metadata and non‑searchable PDF summaries. This work introduces a hybrid retrieval system that makes these devices searchable by combining LLM‑extracted semantic features from authorization summaries with traditional BM25 keyword scoring. The system embeds seven curated features per device using a medical‑specific model (MedEmbed) and fuses semantic similarity with BM25 using optimized weights. Deployed as a public website (fda-ai-search.com), it enables clinicians and developers to query the full database with natural language.

## Method Summary
For each device, the pipeline first uses Gemini‑2.5‑flash to process the FDA summary PDF: chunking long documents, aggregating summaries, and extracting five base features (summary, keywords, relevant questions, thesis, key concepts). Four additional features are then generated: a “search boost” term (company + device name + keywords) and three “query match” terms. These seven text fields are embedded with MedEmbed‑small‑v0.1. At query time, the query is embedded with the same model, and a hybrid score is computed:  
`Score(q,d) = λ * Σ_i (w_i * sim(e_q, e_{i,d})) + (1-λ) * BM25(q,d)`  
Weights `w_i` and λ were pre‑optimized using Optuna on a simulated validation set of 50 devices with queries generated by Gemma‑3. The final weights (e.g., `questions:0.226`, `query match 1:0.217`) and λ=0.8 are fixed. BM25 is computed over the concatenated text of five fields (keywords, questions, thesis, key concepts, search boost). The backend serves the hybrid search, with a simple keyword fallback.

## Key Results
- Hybrid retrieval significantly outperforms both standalone embedding (Hit@5≈0.951) and BM25 (≈0.927) on a curated 140‑device test set, achieving 97.6% Hit Rate@5 for disease+modality queries.  
- Mean inference time per query is 0.38 seconds, supporting interactive use.  
- Qualitative examples show semantic search retrieves devices for clinical terms like "genitourinary" where keyword search fails, demonstrating the value of concept‑level matching.

## Why This Works (Mechanism)
The hybrid design captures two complementary retrieval signals: dense semantic similarity via embeddings understands conceptual matches and medical synonyms, while sparse BM25 ensures exact term matches and handles rare keywords. Optimizing feature weights lets the system emphasize the most predictive fields (e.g., LLM‑generated “questions” and “query matches”) for the FDA device domain. Using a medical‑specific embedding model (MedEmbed) further aligns the vector space with clinical terminology. The pre‑optimization on a simulated validation set stabilizes performance despite the lack of real query logs.

## Foundational Learning
- **Hybrid Retrieval:** Combines dense (embedding) and sparse (BM25) methods. *Why needed:* No single approach captures both semantic and lexical variability in medical device search. *Quick check:* Compare pure embedding vs. BM25 on a few known queries; expect gaps.  
- **Domain‑Specific Embeddings (MedEmbed):** Embedding model trained on medical literature. *Why needed:* General‑purpose embeddings may not distinguish fine‑grained clinical terms. *Quick check:* Test if MedEmbed ranks “cardiac” closer to “heart” than to “pulmonary”.  
- **LLM‑Based Feature Extraction:** Using Gemini to distill unstructured PDFs into structured fields. *Why needed:* FDA summaries are lengthy and inconsistently formatted; concise fields improve retrieval precision. *Quick check:* Manually inspect extracted “thesis” statements for a sample of devices.  
- **BM25 Ranking:** Classic probabilistic keyword retrieval. *Why needed:* Provides deterministic matching for device names, companies, and regulatory codes. *Quick check:* Run BM25 alone on a query containing an exact device trademark; expect top hit.  
- **Hyperparameter Optimization (Optuna):** Automates tuning of weights and λ. *Why needed:* Manual tuning of seven weights and λ is infeasible; the space is high‑dimensional. *Quick check:* Verify that Hit Rate@5 improves over random weight combinations on the validation set.  
- **API‑Hosted LLM (Gemini‑2.5‑flash):** Cloud‑based model for extraction. *Why needed:* Balances accuracy and cost for large‑scale document processing. *Quick check:* Estimate API costs for processing all 1,200+ PDFs; compare to alternative models.

## Architecture Onboarding
PDFs -> Gemini Feature Extraction -> 7 Embeddings (MedEmbed) + Concatenated Text -> Index Storage.  
Query -> Embed Query (MedEmbed) -> Compute 7 Similarities + BM25 Score -> Weighted Hybrid Score -> Ranked Results.  
**Critical path:** Query embedding + similarity computation over 7 vectors + BM25 scoring; measured at 0.38 s.  
**Design tradeoffs:**  
- LLM extraction adds cost and latency but yields rich semantic fields; without it, the hybrid would rely on raw text with poorer signal.  
- Seven features increase index size (7× vectors per device) but allow fine‑grained weighting; fewer features might simplify but reduce recall.  
- λ=0.8 favors semantic matching; a lower λ would emphasize keywords, possibly hurting recall for clinical synonyms.  
**Failure signatures:**  
- Sudden degradation in semantic recall (e.g., missing synonym matches) suggests embedding model drift or weight mis‑assignment.  
- High latency (>1 s) may indicate inefficient vector lookup or BM25 tokenization overhead.  
- Indexing failures for certain PDFs if Gemini output is malformed or exceeds token limits.  
**First three experiments:**  
1. Establish baselines: Run pure BM25 and pure embedding (using only the “thesis” field) on a small sample of 20 devices; record Hit@5.  
2. Weight sensitivity: Fix all weights and vary λ from 0.0 to 1.0 in 0.1 increments; plot Hit@5 to confirm 0.8 is near‑optimal.  
3. Feature ablation: Remove each of the seven features in turn from the hybrid score; measure drop in Hit@5 to identify most critical fields.

## Open Questions the Paper Calls Out
- **Accuracy of LLM‑extracted features:** What are the rates of hallucination or bias in Gemini’s extractions, and how do they affect retrieval?  
- **Generalization beyond CAD devices:** The evaluation used only 140 cardiology devices; does the system perform equally well across all FDA AI device categories?  
- **Simulated vs. real queries:** The hyperparameters were tuned on Gemma‑generated queries; how well do they transfer to actual user search behavior?

## Limitations
- Exact LLM prompts, temperatures, and chunking strategies are not disclosed, making feature extraction irreproducible without reverse‑engineering.  
- BM25 parameters (`k1`, `b`) and preprocessing steps (stemming, stop words) are unspecified, affecting the lexical component.  
- The curated 140‑device test set and query generation logic from McNamara et al. are not public, preventing direct metric replication.  
- Hyperparameter optimization relied on a synthetic validation set of 50 devices, which may not represent the full query distribution.

## Confidence
- **High:** Reported retrieval metrics (Hit Rate@5) and inference time are concrete evaluation results.  
- **Medium:** The live website (fda-ai-search.com) exists and demonstrates the system’s functionality.  
- **Low:** Faithful recreation of the full pipeline is impeded by missing prompts, BM25 settings, and evaluation data.
