# An Agentic System for Schema Aware NL2SQL Generation

## Quick Facts
- **arXiv ID:** 2603.18018  
- **Source URL:** https://arxiv.org/abs/2603.18018  
- **Reference count:** 25  
- **Primary result:** Achieves 47.78% execution accuracy on BIRD with 67% of queries resolved by local SLMs, reducing average cost to $0.0085 per query (over 90% lower than LLM-only baselines) and enabling on-premises deployment.

## Executive Summary
The paper addresses the high computational cost and privacy concerns of LLM-based natural language to SQL (NL2SQL) systems. It proposes a schema-aware agentic system that uses Small Language Models (SLMs) as primary agents for query generation, invoking LLMs only as an error-recovery fallback. The system employs a four-agent pipeline—extraction, decomposition, generation, and validation—with schema-aware prompting and evidence-based correction. On the BIRD benchmark, it achieves 47.78% execution accuracy and a 51.05% validation efficiency score, with 67% of queries resolved by local SLMs. This reduces the average cost per query to $0.0085—over 90% lower than LLM-only baselines—while enabling on-premises deployment for privacy-sensitive environments.

## Method Summary
The method constructs a modular agentic framework where each agent handles a specific subtask: the Extractor retrieves relevant schema elements, the Decomposer breaks the query into subcomponents, the Generator produces SQL, and the Validator checks correctness. Schema-aware prompting incorporates database schema and documentation into each agent's context. An evidence-based correction mechanism allows the Validator to trigger an LLM fallback when errors are detected, which reattempts generation with additional context. By relying on SLMs for the majority of queries, the system drastically cuts costs and supports on-prem deployment.

## Key Results
- Execution accuracy: 47.78% on the BIRD benchmark.  
- Validation efficiency: 51.05% of queries validated successfully without LLM fallback.  
- Cost: Average cost per query reduced to $0.0085, over 90% lower than LLM-only baselines (~$0.094), with 67% of queries resolved by local SLMs.

## Why This Works (Mechanism)
The system achieves cost-efficiency and reasonable accuracy by delegating the bulk of NL2SQL tasks to lightweight SLMs, which are fast and inexpensive to run locally. The four-agent pipeline ensures that each step is focused and schema-aware, improving the quality of intermediate outputs. The validation agent acts as a quality gate: only queries that fail validation (e.g., syntax errors, execution mismatches) trigger the more expensive LLM fallback. This evidence-based recovery means LLMs are used sparingly, primarily for complex or ambiguous cases that SLMs cannot handle. The schema-aware prompting grounds each agent in the database structure, mitigating hallucination and improving relevance. Consequently, the system maintains competitive accuracy on standard benchmarks while dramatically lowering cost and enabling on-prem deployment for privacy.

## Architecture Onboarding
**Component map:**  
User Query -> Extraction Agent -> Decomposition Agent -> Generation Agent -> Validation Agent -> (Success) or (Failure -> LLM Fallback -> Revised SQL)

**Critical path:**  
The sequential execution of extraction, decomposition, generation, and validation constitutes the critical path for queries that do not require LLM fallback. Any failure in these stages propagates forward unless caught by validation.

**Design tradeoffs:**  
- **Cost vs. accuracy:** SLMs reduce cost but have limited reasoning; LLM fallback improves accuracy but increases cost and latency.  
- **Sequential pipeline:** Simple orchestration but vulnerable to error propagation; parallelization is limited by data dependencies.  
- **Schema documentation reliance:** Assumes semantic quality of schema metadata; performance drops on legacy schemas with cryptic names or sparse docs.

**Failure signatures:**  
- Validation failure (e.g., SQL syntax error, empty result, mismatch with expected output) triggers LLM fallback.  
- Extraction errors (e.g., incorrect entity linking) cause downstream agents to operate on wrong premises, leading to invalid SQL.  
- Decomposition errors (e.g., incorrect subquery breakdown) result in flawed generation that may pass validation superficially but produce wrong results.

**First experiments:**

2. Replicate the cost model: compute per-query cost using actual token counts from the paper's setup to verify the $0.0085 figure.  
3. Evaluate the system on the Spider benchmark to assess cross-dataset generalization and potential overfitting to BIRD.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the system's accuracy on complex SQL queries involving nested subqueries, multi-table joins, and temporal reasoning be improved without solely relying on the LLM fallback?
- **Basis in paper:** [explicit] The limitations section states: "The system exhibits performance degradation on queries requiring nested subqueries, joins, or complex temporal reasoning due to the SLM based query generation."
- **Why unresolved:** The current architecture depends on SLMs for initial generation, which have inherent reasoning limitations for complex tasks, and the fallback only activates after a validation failure.
- **What evidence would resolve it:** Controlled experiments comparing SLM fine-tuning on complex SQL corpora, dynamic routing mechanisms that preemptively escalate complex sub-tasks to the LLM, or hybrid model architectures that combine SLM efficiency with targeted reasoning enhancements.

### Open Question 2
- **Question:** What architectural modifications can reduce the tail latency caused by the LLM fallback's retry logic without compromising the system's cost-efficiency gains?
- **Basis in paper:** [explicit] The limitations section notes: "The 'retry logic' results in a slower response time for the most difficult queries, impacting the user's experience in real-time applications."
- **Why unresolved:** The fallback mechanism, while cost-effective, introduces sequential waiting for LLM responses during retries, and optimizing this trade-off between accuracy, cost, and latency is not addressed.
- **What evidence would resolve it:** Empirical analysis of latency distributions across query complexities, A/B testing of fallback trigger thresholds, and evaluation of asynchronous or speculative execution strategies for the validation and fallback loop.

### Open Question 3
- **Question:** How can the sequential agent pipeline be made robust against cascading errors from earlier stages (e.g., incorrect entity linking by the Decomposer Agent)?
- **Basis in paper:** [explicit] The limitations section identifies: "Due to the sequential dependency between agents, errors generated by earlier agent will impact the overall outcome."
- **Why unresolved:** The current design lacks inter-agent validation or error correction mechanisms, so a mistake in decomposition or extraction propagates irrevocably.
- **What evidence would resolve it:** Implementation of confidence scoring or consistency checks between agent outputs, incorporation of feedback loops where downstream agents can query upstream steps, or an ensemble approach where multiple decomposition plans are generated and voted upon.

### Open Question 4
- **Question:** To what extent does the system's performance degrade on databases with poor documentation and cryptic schema names, and how can retrieval be made more robust in such scenarios?
- **Basis in paper:** [explicit] The limitations section states: "The extractor agent relies heavily on semantic similarity between user queries and database schema documentation. In legacy databases with cryptic column names and sparse documentation, the retrieval accuracy drops."
- **Why unresolved:** The RAG-based retrieval assumes a baseline of semantic documentation, which may not exist in real-world legacy systems, creating a hidden assumption about schema quality.
- **What evidence would resolve it:** Evaluation on a curated subset of BIRD or new benchmarks with intentionally degraded schema metadata, and experiments with schema-agnostic retrieval techniques (e.g., using data value distributions or learned embeddings from query history).

### Open Question 5
- **Question:** What effective privacy-preserving techniques can be applied during LLM fallback scenarios to prevent sensitive data leakage without significantly reducing query generation accuracy?
- **Basis in paper:** [explicit] The future work section proposes: "explore additional strategies for privacy preservation during LLM fallback scenarios, including techniques for masking sensitive information in queries sent to external models while maintaining query generation accuracy."
- **Why unresolved:** The system currently sends full query and error context to the external LLM during fallback, which poses a privacy risk in on-prem deployments with sensitive data.
- **What evidence would resolve it:** Development and benchmarking of methods like differential privacy, entity anonymization, or prompt-based redaction that preserve SQL semantics, measured by accuracy drop versus privacy budget on sensitive benchmark datasets.

## Limitations
- Results derive solely from the BIRD benchmark; generalizability to other NL2SQL benchmarks or real-world enterprise schemas is unknown.  
- The "validation efficiency score" (51.05%) is not a standard metric; its computation and relationship to execution accuracy are unclear.  
- System performance breakdown by query complexity (e.g., join count, nested queries) is not provided; the 67% SLM resolution rate may be skewed toward simpler queries.  
- Privacy benefits are theoretical; no empirical data leakage risk assessment is presented.  
- The sequential agent pipeline's failure modes (e.g., error propagation) and robustness are not analyzed.

## Confidence
- **Cost reduction claim:** High confidence (concrete pricing numbers and clear SLM/LLM invocation split).  
- **Execution accuracy claim:** Medium confidence (BIRD-specific, no cross-benchmark validation).  
- **On-prem deployment & privacy claim:** Low confidence (feasibility assumed, no empirical privacy assessment).
