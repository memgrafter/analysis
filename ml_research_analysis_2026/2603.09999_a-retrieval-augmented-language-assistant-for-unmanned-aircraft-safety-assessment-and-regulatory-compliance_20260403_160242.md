# A Retrieval-Augmented Language Assistant for Unmanned Aircraft Safety Assessment and Regulatory Compliance

## Quick Facts
- **arXiv ID:** 2603.09999  
- **Source URL:** https://arxiv.org/abs/2603.09999  
- **Reference count:** 40  
- **Primary result:** A retrieval-augmented language assistant provides traceable, auditable decision support for unmanned aircraft safety assessment using manual chunking, hybrid retrieval, and strict citation-driven generation, though retrieval robustness and grounding guarantees need improvement.

## Executive Summary
The paper addresses inefficiencies in unmanned aircraft safety assessment and regulatory compliance due to operational complexity. It designs a retrieval-augmented language (RAG) assistant that relies exclusively on authoritative regulatory sources (EASA CS-UAS) to deliver auditable, traceable outputs. The system employs manual document chunking aligned with regulatory structure, hybrid dense and lexical retrieval with Reciprocal Rank Fusion, and conservative LLM generation with enforced citations and fallbacks for evidence gaps. Results show high retrieval for direct queries but degraded performance on reformulated questions, and grounding succeeds in only half of direct-match cases. The approach demonstrates bounded assistance with strong auditability, though further work is needed to improve retrieval robustness and grounding reliability.

## Method Summary
The system processes EASA CS-UAS documents by manually chunking each normative element (articles, AMCs, general material) to preserve legal coherence and provenance. Chunks are enriched with metadata (title, summary, keywords) and indexed using all-MiniLM-L6-v2 embeddings stored in a FAISS vector index and a BM25 sparse index. Retrieval combines dense and sparse results via Reciprocal Rank Fusion (k=60), applies Maximal Marginal Relevance for diversity (λ=0.6), field-aware post-scoring (summary similarity, keyword boost), ColBERT reranking, and elbow filtering (threshold 0.8). Generation uses OpenAI gpt-oss-20B with strict prompts requiring citations and conservative fallbacks for insufficient evidence, within a 12k character context budget. Two interfaces are provided: a chat mode with optional query decomposition and an indicator mode for structured operational inputs yielding deterministic JSON outputs.

## Key Results
- Retrieval Hit@10: 100% for direct matches, 100% for synonym paraphrases, 75% for reworked questions; overall 91.7%.
- Grounding: Under direct-match queries, only 50% of answers were fully grounded; some were unsupported or incomplete.
- Indicator tasks: Value consistency 91.7% across repeated runs; overall accuracy 81.8% against ground truth; regulatory pathway accuracy 66.6%.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Manual document chunking aligned with regulatory structure improves retrieval precision and auditability.
- **Mechanism:** Creating a dedicated chunk for each normative element (e.g., article, AMC) avoids fragmenting legally meaningful units, simplifies provenance tracking, and enables targeted retrieval of specific requirements.
- **Core assumption:** Regulatory texts have a clear hierarchical organization that should be preserved in the index; automated segmentation would break this coherence.
- **Evidence anchors:** Abstract mentions "manual document chunking to preserve legal coherence"; Section 2.2 details manual chunking per article/AMC to reduce fragmentation risk.
- **Break condition:** Becomes impractical for large or frequently updated corpora; also fails if regulations lack hierarchical structure.

### Mechanism 2
- **Claim:** Hybrid dense and lexical retrieval with Reciprocal Rank Fusion (RRF) yields robust performance across varied query phrasing.
- **Mechanism:** Dense retrieval (embedding-based) captures semantic similarity; sparse retrieval (BM25) captures exact term matches. RRF combines rankings to balance both approaches.
- **Core assumption:** User queries vary in lexical and semantic alignment with source documents; no single retriever dominates all cases.
- **Evidence anchors:** Abstract cites "hybrid dense and lexical retrieval"; Section 2.5 describes hybrid retrieval and RRF; Section 4.1, Table 3 shows retrieval results across query types.
- **Break condition:** May fail for multi-step reasoning or cross-document linking; RRF parameters (k=60) may need domain-specific tuning.

### Mechanism 3
- **Claim:** Strict citation-driven generation with conservative fallbacks ensures traceable, auditable outputs and mitigates hallucination.
- **Mechanism:** The LLM is prompted to use only retrieved context, output citations, and explicitly state evidence gaps; context is bounded and source-attributed.
- **Core assumption:** LLMs can be instructed to ground responses in provided text and avoid external knowledge; without constraints, they hallucinate.
- **Evidence anchors:** Abstract notes "strict citation-driven generation with conservative fallbacks"; Section 2.7 details generation constraints and evidence gap handling; Section 4.1, Table 4 shows grounding outcomes.
- **Break condition:** If retrieved context is incomplete or misleading, LLM may still produce unsupported statements; instruction following may degrade with model size or prompt complexity.

## Architecture Onboarding
- **Component map:** PDF parser → structure detector → manual chunker → metadata enrichment → retrieval document creation → encoder (all-MiniLM-L6-v2) → FAISS vector index + JSON metadata store → query → encoder → dense retrieval (FAISS) + BM25 → Reciprocal Rank Fusion → MMR → post-scoring (summary similarity + keyword boost) → ColBERT reranker → elbow filtering → context assembly (≤12k chars) → LLM (gpt-oss-20B) with system/developer/user prompts → output with citations. Interfaces: (1) Chat (optional query decomposition → retrieval → generation); (2) Indicator (structured input → deterministic query → retrieval → single-indicator JSON output).
- **Critical path:**  
  1. User query received.  
  2. (Optional) Query decomposition into sub-queries.  
  3. For each sub-query (or original): retrieval pipeline (dense + sparse → fusion → rerank/filter) to get evidence chunks.  
  4. Assemble context from chunks (rank order, within budget).  
  5. Construct prompt with system, developer, user query, context.  
  6. LLM generation with constrained decoding.  
  7. Return answer with citations; log full prompt and evidence.
- **Design tradeoffs:**  
  - Manual chunking ensures legal coherence but does not scale; automatic chunking would require sophisticated domain-specific segmentation.  
  - Exact FAISS search is deterministic but slow; HNSW is faster but approximate and may sacrifice recall.  
  - ColBERT reranker improves accuracy but adds latency; post-scoring with summary/keywords is lightweight but less expressive.  
  - Conservative generation avoids hallucinations but may lead to refusals or incomplete answers when evidence is borderline.  
  - Indicator-oriented prompts enforce structure but reduce flexibility for complex queries.
- **Failure signatures:**  
  - Retrieval failure: Hit@10 drops for paraphrased/reworked questions (down to 75%); missing governing paragraphs.  
  - Grounding failure: Even with correct retrieval, only 50% of answers fully grounded; unsupported sentences appear.  
  - Indicator inconsistency: Regulatory pathway accuracy only 66.6%; value consistency 83.3% (lowest among indicators).  
  - Over-specificity: System produces definitive answers for borderline cases instead of conditional ones.  
  - Evidence gap mishandling: LLM sometimes infers missing parameters despite instructions.
- **First 3 experiments:**  
  1. Retrieval robustness test: For a set of ground-truth chunks, generate direct, synonym, and reworked queries; measure Hit@10 and MRR to verify hybrid retrieval improves over single-method baselines.  
  2. Grounding assessment: For queries with known correct answers, check if every sentence in the generated answer is supported by retrieved context and properly cited; quantify hallucination and citation discipline.  
  3. Indicator stability and accuracy: For fixed operation configurations, run each indicator 10 times; compute value consistency (mode frequency) and compare majority vote to ground truth labels; evaluate repeatability and correctness of structured outputs.

## Open Questions the Paper Calls Out
- **Open Question 1**  
  *Question:* How can query preprocessing and retrieval expansion be designed to maintain high recall for semantically reformulated regulatory queries without introducing noise?  
  *Basis in paper:* The authors propose "stronger query preprocessing, retrieval expansion for multi-aspect questions, adaptive top k selection" in future work (Section 5.2).  
  *Why unresolved:* Current hybrid retrieval shows degraded recall under reworked questions (Table 3), and no systematic evaluation of preprocessing strategies is provided.  
  *What evidence would resolve it:* Controlled experiments comparing query decomposition, expansion techniques, and adaptive thresholds on a held-out set of paraphrased regulatory queries, measuring recall and precision against ground truth chunks.

- **Open Question 2**  
  *Question:* What mechanisms can enforce strict sentence-level grounding in LLM outputs, ensuring every generated claim is directly supported by retrieved evidence?  
  *Basis in paper:* The authors suggest a "post-hoc verifier that maps generated sentences to specific retrieved passages" (Section 5.2).  
  *Why unresolved:* Grounding assessments in Table 4 show that even with correct retrieval, only 50% of answers were fully grounded, indicating generation may ignore or misattribute evidence.  
  *What evidence would resolve it:* Implementation and evaluation of a verifier module that flags unsupported sentences, with human evaluation measuring reduction in unsupported claims on the regulatory assistant use case.

- **Open Question 3**  
  *Question:* How can multiple authoritative regulatory sources (e.g., national implementations) be integrated into a single RAG corpus while preserving per-source provenance and avoiding contradictory interpretations?  
  *Basis in paper:* Future work calls for extending the corpus "with national interpretation material while keeping per source provenance visible" (Section 5.2).  
  *Why unresolved:* The current system uses a single source (EASA CS-UAS), and multi-jurisdictional scenarios could introduce conflicts or ambiguity in sourcing.  
  *What evidence would resolve it:* A case study adding national variants to the corpus, measuring traceability accuracy and conflict detection rates, with audit logs showing source attribution for each claim.

- **Open Question 4**  
  *Question:* Can GraphRAG be safely deployed in safety-critical regulatory environments without compromising auditability, and what minimal viable graph schemas balance expressiveness and governance overhead?  
  *Basis in paper:* The authors discuss GraphRAG as a longer-term enhancement but note risks like "schema design burden, extraction errors" and advocate a "staged approach" (Section 5.2).  
  *Why unresolved:* GraphRAG is mentioned as promising but untested in this domain; the paper's architecture currently uses chunk-based retrieval due to governance concerns.  
  *What evidence would resolve it:* Prototype implementation of GraphRAG on a subset of SORA, with evaluation of multi-hop retrieval accuracy, schema maintenance cost, and error propagation compared to baseline RAG.

- **Open Question 5**  
  *Question:* What design modifications can improve the consistency and accuracy of borderline regulatory pathway classifications, such as distinguishing between Specific PDRA and Specific SORA?  
  *Basis in paper:* Results show "likely regulatory pathway" achieved only 66.6% accuracy and lower value stability (Tables 5 and 6), with authors noting sensitivity to "interpretation boundaries" (Section 4.2).  
  *Why unresolved:* The indicator relies on simplified operational inputs and may not capture nuanced regulatory distinctions, leading to over-specific or inconsistent outputs.  
  *What evidence would resolve it:* Analysis of misclassified cases to identify missing decision factors, followed by redesigned prompts or additional retrieval queries targeting borderline criteria, with statistical testing of accuracy improvement.

## Limitations
- Exact CS-UAS document version and manual chunk boundaries are unreleased, preventing precise replication.  
- The LLM “OpenAI gpt-oss-20B” appears fictitious; its identity and accessibility are unknown.  
- Critical hyperparameters (BM25 k1/b, ColBERT settings) and retrieval pool sizes are omitted.  
- No ground truth labels or query sets for indicator and retrieval tests are provided, blocking independent verification of reported metrics.  
- Grounding success is only 50% even with correct retrieval, indicating limited reliability.  
- Evaluation likely used a small, non-public set, reducing generalizability.

## Confidence
- System design ensures traceable, auditable assistance: **Medium**  
- Retrieval performance is robust across query phrasing: **Low**  
- Grounding is effectively enforced: **Low**  
- Indicator tasks provide consistent and accurate outputs: **Medium** (value consistency) / **Low** (pathway accuracy)

2. Conduct a human audit of grounding: sample 100 direct-match queries and outputs; have two domain experts annotate each sentence as grounded (with correct citation), unsupported, or incomplete; compute inter-rater agreement and compare to the paper’s 50% rate.
