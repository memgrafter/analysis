# Resource-Efficient Iterative LLM-Based NAS with Feedback Memory

## Quick Facts
- **arXiv ID:** 2603.12091
- **Source URL:** https://arxiv.org/abs/2603.12091
- **Reference count:** 39
- **Primary result:** A closed-loop iterative NAS pipeline using frozen LLMs (≤7B) and a sliding-window feedback memory improves one-epoch proxy accuracy on CIFAR-10 from ~28-50% to ~69-72% within up to 2000 iterations, completing a full search in ~18 GPU hours on an RTX 4090.

## Executive Summary
This work tackles the prohibitive computational cost of neural architecture search (NAS) by introducing a low-budget, iterative pipeline that leverages frozen instruction-tuned large language models (LLMs) with up to 7 billion parameters. The core innovation is a historical feedback memory—a sliding window of the last five structured diagnostic triples (problem, suggestion, outcome)—which enables the LLM to learn from both successes and code execution failures. The pipeline employs dual LLM specialization: one generates executable PyTorch code, while the other performs diagnostic reasoning. Evaluated on CIFAR-10, CIFAR-100, and ImageNette, the approach consistently improves one-epoch validation accuracy over thousands of iterations, with a complete search requiring only about 18 GPU hours on a consumer-grade RTX 4090. The method establishes a reproducible, hardware-aware paradigm for efficient NAS without any LLM fine-tuning.

## Method Summary
The pipeline alternates between two frozen LLM calls and an evaluation step. A Code Generator LLM receives the best architecture found so far and a suggested modification (from the previous iteration) and produces a candidate PyTorch `nn.Module`. The Evaluator first validates the candidate via a dummy forward pass; if valid, it trains the model for one epoch on the target dataset using SGD with cosine learning rate decay and records the validation accuracy. A Prompt Improver LLM then analyzes the outcome (success or error) alongside a sliding window of the last five diagnostic triples (each containing a problem, a suggestion, and an outcome) and outputs a new problem-suggestion-outcome triple along with a refined suggestion for the next iteration. The Orchestrator maintains the best architecture, updates the history queue, and feeds the new suggestion back to the Code Generator. The history window enforces a K-order Markov property, keeping context size constant while allowing the system to learn iteratively. The entire process runs on a single consumer GPU (e.g., RTX 4090) with both the LLM and architecture training sharing the same memory, implicitly biasing the search toward compact models.

## Key Results
- On CIFAR-10, DeepSeek-Coder-6.7B improves one-epoch accuracy from 28.2% to 69.2% and Qwen2.5-7B from 50.0% to 71.5% over up to 2000 iterations.
- Similar consistent improvements are observed on CIFAR-100 and ImageNette.
- A full NAS run completes in approximately 18 GPU hours on an RTX 4090, demonstrating extreme resource efficiency.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Historical feedback memory with a bounded sliding window (K=5) enables systematic architectural improvement by treating code execution failures as first-class learning signals.
- **Mechanism:** The Prompt Improver receives a structured triple (problem, suggestion, outcome) from the last K iterations. This allows the LLM to identify causal patterns between specific code modifications and outcomes (success/error), avoiding repeated failures and building on partial successes via a Markovian dependency (P(s_t | A*, H_t) = P(s_t | A*, H^(K)_t)).
- **Core assumption:** The LLM can extract actionable diagnostic insights from structured historical triples and apply them to generate targeted code modifications, despite working with frozen, non-fine-tuned models.
- **Evidence anchors:** The abstract and section 3.4 formalize the K-order Markov property and diagnostic triple structure, stating each history entry records the identified problem, suggested improvement, and resulting outcome. Ablations disabling feedback show degraded convergence, confirming the memory's role.
- **Break condition:** If the LLM fails to synthesize consistent improvement strategies from the triples (e.g., cycles of repeating the same modification that triggers the same error), the feedback loop loses direction and accuracy plateaus or degrades.

### Mechanism 2
- **Claim:** Dual-LLM specialization (Code Generator vs. Prompt Improver) reduces per-call cognitive load, enabling more reliable code generation and diagnostic reasoning within a single limited-context window.
- **Mechanism:** Separating concerns—one LLM call focuses purely on synthesizing executable PyTorch code given structured suggestions, while a separate call reasons about failures and plans modifications—prevents the model from juggling code-generation and diagnostic reasoning simultaneously. This specialization is hypothesized to improve performance on each sub-task.
- **Core assumption:** The same underlying LLM can effectively switch roles based on prompt framing, and the benefit of role specialization outweighs the overhead of sequential LLM calls.
- **Evidence anchors:** The abstract mentions dual-LLM specialization; sections 3.2 and 3.4 describe distinct prompt templates. No direct comparison with a single-LLM setup is provided.
- **Break condition:** If the diagnostic reasoning from the Prompt Improver generates suggestions that are too abstract or incompatible with the Code Generator's understanding, the code synthesis fails or produces invalid architectures, increasing the error rate.

### Mechanism 3
- **Claim:** Hardware-aware search emerges implicitly because the LLM inference and architecture training share the same limited VRAM (e.g., 24GB RTX 4090), biasing the search toward compact, executable models that fit within the memory constraints.
- **Mechanism:** The evaluation step requires loading both the LLM (≤7B parameters) and the candidate architecture's parameters/tensors into GPU memory simultaneously. Larger, more complex architectures risk out-of-memory (OOM) errors during validation or training, causing them to be discarded. Thus, the search process inherently favors architectures that are memory-efficient enough to be evaluated in this constrained environment.
- **Core assumption:** Memory pressure during evaluation is a significant enough failure mode to shape the distribution of discovered architectures toward smaller, more efficient ones, and this bias correlates with edge-deployment suitability.
- **Evidence anchors:** The abstract notes implicit favoring of compact models; section 3.3 describes validation via forward pass and discarding on failure. No explicit experiments vary memory constraints to confirm bias.
- **Break condition:** If the memory constraint is relaxed or the validation step does not include a forward pass that loads full parameters, the implicit bias toward compact architectures disappears.

## Foundational Learning
### Markov Chains / Properties
- **Why needed:** The historical feedback memory is explicitly designed as a K-order Markov process, where the next state (improvement suggestion) depends only on the current best architecture and the last K history entries. Understanding this is key to grasping why the window size is bounded.
- **Quick check:** How would the prompt design change if the history mechanism used a full trajectory (unbounded) instead of a sliding window? What problem does the Markov assumption solve?

### LLM Prompt Engineering & Role Framing
- **Why needed:** The entire pipeline hinges on crafting effective prompts for two distinct roles (Code Generator, Prompt Improver) and structuring their inputs/outputs (diagnostic triples). The success of each iteration depends on the LLM correctly interpreting these structured prompts.
- **Quick check:** What are the key differences in the Prompt Improver's input (history + best/current code + outcome) versus the Code Generator's input (best code + suggestions)? What specific instruction is needed to make the LLM output a valid "diagnostic triple"?

### Proxy Metrics in NAS
- **Why needed:** The pipeline uses one-epoch training accuracy as a fast, cheap proxy to rank architectures. Understanding the trade-off between evaluation cost and ranking reliability is crucial.
- **Quick check:** Why is one-epoch accuracy chosen over zero-shot metrics (like synflow) or full-training accuracy? What are the risks of using such a proxy (e.g., ranking instability, correlation decay)?

## Architecture Onboarding
### Component map
Code Generator LLM (frozen) → Evaluator → Prompt Improver LLM (frozen) → Historical Feedback Memory (sliding window of K=5 triples) → back to Code Generator. The Orchestrator manages the iteration loop, state updates, and history pruning.

### Critical path
The iterative loop: Code Generator produces candidate architecture code → Evaluator validates (shape check) and, if valid, trains for one epoch → Prompt Improver receives the best code, current code/outcome, and the last K triples to produce a new problem-suggestion-outcome triple and a refined suggestion → the new suggestion is fed back to the Code Generator for the next iteration. The Orchestrator updates the best architecture and the history queue after each iteration.

### Design tradeoffs
- **History window size (K):** Larger K provides more context but risks prompt overflow; smaller K limits learning. The paper fixes K=5 based on preliminary trials.
- **One-epoch proxy vs. full training:** Drastically reduces cost (~18 GPU hours) but may not correlate perfectly with final performance.
- **Frozen LLM vs. fine-tuning:** No training cost, but limits adaptation potential and may cap performance.
- **Open code space vs. constrained cell-based:** Maximizes novelty but increases code generation failure rates.

### Failure signatures
1. **Validation failure:** Code has syntax errors, wrong module structure, or shape mismatches; reported as an error message to Prompt Improver.
2. **Training crash/OOM:** Code passes validation but crashes during training (often due to memory), especially for larger architectures.
3. **Stagnant accuracy:** Accuracy plateaus after initial gains, indicating the feedback loop may be cycling without meaningful improvement.

### First 3 experiments
1. Ablation: Disable historical feedback (“No Feedback” condition) on CIFAR-10; verify degradation compared to full loop.
2. Vary K: Test K ∈ {1, 3, 5, 10} over 200 iterations for one LLM on CIFAR-10; plot accuracy trajectories to assess optimal window.
3. Inspect failure modes: Log all error messages from Evaluator; categorize (syntax, shape, OOM, runtime); correlate error types with specific LLMs.

## Open Questions the Paper Calls Out
1. **Success rate variability:** The paper reports large disparities in code generation success rates across LLMs (0.7% to 95.1%) but does not investigate causes. Resolving this requires controlled experiments on prompt design and constrained decoding strategies.
2. **Proxy accuracy correlation:** The one-epoch proxy’s correlation with final converged accuracy is unknown. Evidence: retrain top-K discovered architectures with full schedules and compute Spearman correlation.
3. **History window optimality:** The fixed K=5 is chosen heuristically; an adaptive or learnable window might enhance efficiency. Evidence: systematic ablations across K values on all LLM-dataset combinations.
4. **Dual-LLM specialization benefit:** The paper splits generation and improvement roles but does not compare to a single-LLM approach. Evidence: implement a variant where one LLM handles both roles and compare success rates, accuracy trajectories, and GPU time.

## Limitations
- Prompt templates and dual-LLM implementation details are not disclosed, hampering reproducibility.
- High code generation failure rates (e.g., Qwen2.5 81.2%) are reported but not analyzed; this may bias search and reduce efficiency.
- The one-epoch accuracy proxy is used without full-training validation, leaving its reliability for final performance uncertain.

## Confidence
- Feedback memory (K=5 Markov window): Medium (ablations confirm benefit, but optimal K untested)
- Dual-LLM separation: Low (no ablation; advantage speculative)
- Implicit hardware awareness: Low (inference only; no empirical support)
