# Socratic-Geo: Synthetic Data Generation and Geometric Reasoning via Multi-Agent Interaction

## Quick Facts
- **ArXiv ID:** 2602.03414  
- **Source URL:** https://arxiv.org/abs/2602.03414  
- **Reference count:** 40  
- **Primary result:** Socratic-Solver achieves 49.11% mean accuracy across six benchmarks using one-quarter the training data of baselines, surpassing them by 2.43 points; Socratic-Generator reaches 42.4% on GenExam-Math, setting a new SOTA for open-source models and approaching Gemini-2.5-Flash-Image (43.1%).

## Executive Summary
Geometric reasoning in multimodal large language models (MLLMs) is limited by the scarcity of high-quality image-text pairs. Socratic-Geo introduces a multi-agent framework that tightly couples data synthesis with model learning. A Teacher agent generates parameterized Python geometry scripts and validates them through a Reflect (solvability) and RePI (visual validity) pipeline to ensure purity. A Solver agent learns via Group Relative Policy Optimization (GRPO), a reinforcement learning method that leverages failure-driven curriculum augmentation. A Generator agent distills programmatic drawing instructions into synthetic images via a diffusion model. Starting from only 108 seed problems, the framework produces a curriculum that enables the Solver to achieve state-of-the-art accuracy with drastically reduced training data. The approach demonstrates that synthetic, code-grounded data can close the gap between open-source and proprietary models on geometric reasoning benchmarks.

## Method Summary
Socratic-Geo is an iterative, three-agent system. The Teacher receives a geometric problem (represented as Python code) that the Solver failed to solve. It modifies the code to create a new variant, then subjects the variant to dual verification: Reflect checks that the new problem remains solvable by comparing the Teacher’s solution to a reference, and RePI ensures the code renders a valid, non-degenerate figure. Only problems passing both checks are added to the Data Pool. The Teacher also translates the validated code into step‑by‑step natural‑language drawing instructions (Instruction Rewriting). The Solver is an MLLM trained exclusively via GRPO on the curated curriculum; it explores multiple solution attempts per problem, and when all fail, the Teacher’s solution is injected as the sole positive example, encouraging learning from failure. The Generator (a diffusion model) is fine‑tuned on (instruction, image) pairs drawn from the Data Pool, learning to produce geometrically faithful diagrams. The loop repeats: Solver failures trigger Teacher‑driven data expansion, which in turn refines the Solver and Generator.

## Key Results
- Socratic‑Solver reaches **49.11%** mean accuracy across six geometric reasoning benchmarks, outperforming baselines by **2.43 points** while using only **one‑quarter** of their training data.
- Socratic‑Generator achieves **42.4%** on GenExam‑Math, establishing a new state‑of‑the‑art for open‑source models and approaching Gemini‑2.5‑Flash‑Image (43.1%).
- The entire pipeline scales from just **108 seed problems**, demonstrating exceptional data efficiency.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** The Teacher agent's Reflect‑RePI pipeline ensures geometric data purity by coupling solvability verification with visual validity checks before problem incorporation.
- **Mechanism:** For each candidate problem, `Reflect` validates mathematical solvability by comparing the Teacher's solution to a reference, while `RePI` programmatically inspects the rendered Python geometry code for structural validity (e.g., non‑degenerate figures, correct constraints). Only problems passing both checks enter the curriculum.
- **Core assumption:** Synthetic problems must be *both* logically sound and visually renderable to serve as effective training data; decoupling these leads to noisy, harmful examples.
- **Evidence anchors:**
  - [abstract] "Teacher agent generates parameterized Python scripts with reflective feedback (Reflect for solvability, RePI for visual validity), ensuring image‑text pair purity."
  - [section 4.2] Details the "conceive‑and‑verify loop" where `Reflect` and `RePI` are applied sequentially.
  - [corpus] Weak direct evidence; neighboring papers (e.g., MALT, Theorem‑Validated R‑CoT) validate multi‑agent reflection but do not test the specific dual‑check design.
- **Break condition:** If either `Reflect` (solution mismatch) or `RePI` (code execution/visual error) fails, the problem is discarded, preventing curriculum contamination.

### Mechanism 2
- **Claim:** The Solver's Group Relative Policy Optimization (GRPO) learns targeted reasoning skills from failure‑driven curriculum augmentation rather than imitating teacher outputs.
- **Mechanism:** The Solver generates multiple solution attempts per problem. Binary rewards (correct/incorrect) are computed via verifiable rules. Crucially, when all attempts fail, the teacher's gold solution is injected as the *only* positive example. This forces the Solver to explore via trial‑and‑error, using group‑relative advantages to stabilize learning without a value network.
- **Core assumption:** Performance gains stem from RL‑based search and adaptation to the *Solver's specific weaknesses*, not from knowledge distillation of high‑quality (but potentially imitative) solutions.
- **Evidence anchors:**
  - [abstract] "Solver optimizes via GRPO reinforcement learning from failure‑driven augmentation."
  - [section 4.3] "This is a pure reinforcement learning paradigm rather than knowledge distillation: the Solver never observes the Teacher’s chain‑of‑thought...learns exclusively through trial‑and‑error."
  - [section 5.3, Table 6] Ablation shows RL (49.11%) significantly outperforms SFT on identical data (47.37%), confirming the mechanism's role.
- **Break condition:** If reward signals (`V(q, a_S, a_ref)`) are noisy or misaligned with true correctness, the policy gradient updates become uninformative or destabilizing.

### Mechanism 3
- **Claim:** The Generator distills programmatic drawing intelligence into image synthesis via structured instruction rewriting, achieving geometric fidelity.
- **Mechanism:** The Teacher translates validated geometric code into explicit, step‑by‑step natural language drawing commands (e.g., "draw circle with center O and radius R"). The Generator (a diffusion model) is fine‑tuned on these (instruction, image) pairs. This maps precise symbolic constraints to pixel space, avoiding the ambiguity of raw question prompts.
- **Core assumption:** Direct instruction‑to‑diagram mapping, derived from executable code, provides a stronger supervision signal for geometric image generation than learning from uncurated (question, image) pairs.
- **Evidence anchors:**
  - [section 4.4] "The Teacher translates this information into a descriptive, natural‑language drawing instruction...creating high‑quality (instruction,image) pairs."
  - [section 5.2.2] Ablation in Table 5 shows removing Instruction Rewriting (IR) drops GenExam‑Math relaxed score from 42.4% to 20.1%, demonstrating IR's critical role.
  - [corpus] Contextually supported by work on structured prompts for image generation (e.g., Prompt‑Propose‑Verify), but no direct test of code‑derived instructions.
- **Break condition:** If instructions are imprecise or misaligned with the code's output (e.g., omitting a critical constraint), the Generator learns a flawed mapping, producing geometrically invalid images.

## Foundational Learning
### Group Relative Policy Optimization (GRPO)
- **Why needed here:** Enables RL training without a separate value network, using group‑normalized advantages from binary rewards. Critical for the Solver's efficient, stable learning from sparse correctness signals.
- **Quick check question:** Given a group of 8 solver attempts on one problem with 3 correct, how is the advantage for a correct attempt computed relative to the group? (Answer: `(1 - mean(all rewards)) / std(all rewards)`)

### Programmatic Geometry Representation
- **Why needed here:** All synthesized data is rooted in executable Python code (using `matplotlib`/`numpy`). This provides a ground truth for rendering, solvability, and modification, acting as the "single source of truth" for both Teacher validation and Generator distillation.
- **Quick check question:** If a problem's code fails to render a non‑degenerate triangle (e.g., collinear points), which module catches this first: Reflect, RePI, or the Generator's SFT? (Answer: RePI during Teacher's validation)

### Failure‑Driven Curriculum Evolution
- **Why needed here:** The entire data synthesis loop is triggered by Solver failures. This focuses computational resources on generating problems that address *actual* weaknesses, maximizing data efficiency and avoiding random exploration.
- **Quick check question:** In Equation (3), what condition must be met for a new triplet `(I', q', a')` to be added to `C_{t+1}`? (Answer: The Solver failed all `k` attempts on the seed problem `(I, q, a*)`)

## Architecture Onboarding
**Component map:**  
Teacher (LLM) → Data Pool (stores validated code‑instruction‑image triplets) → Generator (diffusion model)  
Solver (MLLM) ← Curriculum C (subset of Data Pool)  

**Critical path:**  
1. Solver fails on a problem from curriculum `C_t`.  
2. Teacher diagnoses the failure, modifies the problem's code to create a new variant, and verifies it via Reflect/RePI.  
3. Valid variant is added to `C_{t+1}` and its drawing instruction is added to the instruction set `D` for Generator training.  
4. Solver is retrained on updated curriculum `C_{t+1}` via GRPO.  
5. Generator is periodically retrained on the accumulating `D`.

**Design tradeoffs:**  
- *Data efficiency vs. compute cost:* Teacher's LLM‑intensive verification yields ~4× reduction in training samples but requires significant API/GPU resources.  
- *RL stability vs. SFT simplicity:* GRPO adapts better to solver weaknesses but needs careful hyperparameter tuning (`k=8` attempts) and risks instability; SFT is simpler but less effective.  
- *Specialization vs. generality:* Code‑grounded approach ensures geometric precision but may not transfer to non‑parametric domains (e.g., real‑world images).

**Failure signatures:**  
- Teacher yield rate < 15% → `Modify` or verification steps too strict, starving curriculum.  
- Solver reward distribution becomes uniform → GRPO advantages vanish; problems are either too easy or impossible.  
- Generator strict score = 0% → likely missing Instruction Rewriting; model cannot map prompts to precise constraints.

**First 3 experiments (reproduction checks):**  
1. **Teacher Yield Rate Benchmark:** Run Teacher on 100 failing Solver problems; measure % passing both Reflect and RePI. Target ~30% (per Appendix B).  
2. **GRPO vs. SFT Controlled Ablation:** Train Solvers on identical 2.5k synthetic data using (a) GRPO, (b) SFT (KD). Evaluate on MathVerse; expect >1.5% gap for RL.  
3. **Generator Instruction Ablation:** Train Generator with/without Teacher's Instruction Rewriting. Evaluate on GenExam‑Math relaxed score; expect >20% drop without IR.

## Limitations
- **Seed dependency & scalability:** Starting from only 108 seed problems, the framework's ability to generate diverse, high‑quality curricula for broader geometric domains (e.g., 3D, non‑Euclidean) remains unproven; yield rates beyond initial seeds may drop.  
- **Generalization beyond parametric geometry:** The pipeline relies on executable Python code; transfer to diagram types without clean programmatic representations (e.g., hand‑drawn sketches, ambiguous real‑world images) is uncertain.  
- **Compute‑cost vs. data‑efficiency trade‑off:** Although data usage is reduced, the multi‑agent LLM + RL loop is computationally heavy; the paper does not report wall‑clock cost or API expense, making the efficiency claim incomplete.

## Confidence
- Teacher's Reflect/RePI purity mechanism: **Medium**  
- Solver's GRPO over SFT: **High**  
- Generator's Instruction Rewriting (IR): **High**

## Next Checks
1. **Seed scaling stress test:** Run full synthesis loop from 10, 100, and 1000 diverse seed problems; measure final solver accuracy and teacher yield rate vs. seed count. Expected: yield/accuracy plateau or degrade with too few seeds; scales smoothly up to a point.  
2. **Domain transfer evaluation:** Zero‑shot evaluate trained Socratic‑Solver (on synthetic Euclidean geometry) on a non‑parametric diagram benchmark (e.g., GeoText with real‑world photos or DiagramGPT outputs). Expected: significant drop (>15% absolute) indicates lack of transfer.  
3. **Compute audit & breakdown:** Measure total GPU hours / API calls for one full iteration (Solver failure → Teacher modification → Generator update) using the reported 2.5k training data. Compare end‑to‑end cost against a baseline SFT trained on a public geometric dataset (e.g., GeoQA+). Expected: Socratic method may be >5× more compute‑intensive per accuracy point gained.
