# The GRADIEND Python Package: An End-to-End System for Gradient-Based Feature Learning

## Quick Facts
- arXiv ID: 2602.23993
- Source URL: https://arxiv.org/abs/2602.23993
- Reference count: 5
- Primary result: Learns feature directions from factual-counterfactual gradients, achieves high encoder correlation (0.9757) on English pronoun paradigm, and reveals structural parameter overlaps across 44 linguistic features on BERT.

## Executive Summary
GRADIEND is an open-source Python package that provides an end-to-end workflow for gradient-based feature learning and persistent model modification. The system learns low-dimensional feature directions by contrasting gradients from factual and counterfactual instances (e.g., predicting "she" vs. "they") using an encoder-decoder architecture. It evaluates class separation via encoder correlation and applies controlled weight updates to rewrite model behavior while preserving general fluency. Demonstrated on an English pronoun paradigm (3SG vs. 3PL), it achieves a high encoder correlation of 0.9757 and clear class separation. Large-scale analysis across 44 features on BERT uncovers patterns of parameter overlap: German articles share parameters due to syncretism, race/religion features overlap up to ~17%, while English grammatical number and person are largely disjoint. The package enables reproducible and scalable feature comparison, reproducing prior use cases and supporting further interpretability research.

## Method Summary
The GRADIEND package orchestrates a pipeline starting with data generation: `TextPredictionDataCreator` uses `TextFilterConfig` rules to construct factual-counterfactual pairs for two feature classes from a base corpus, producing a `GradientDataset`. A neutral dataset is also generated for evaluation. Training is handled by `TextPredictionTrainer`, which wraps the base Hugging Face model in a `GradientModel` to capture gradients for selected parameters. An auxiliary `FeatureModel` (an encoder-decoder network) is trained to map gradient vectors to a scalar (encoder) and back to a parameter delta (decoder). Pre-pruning (selecting top 1% important parameter dimensions) and post-pruning (top 10% of trained decoder outputs) reduce memory usage. After training, `trainer.evaluate_encoder()` measures class separation via Pearson correlation, and `trainer.evaluate_decoder()` selects a learning rate multiplier that maximizes target class probability while preserving a Language Modeling Score (LMS) constraint. The final step `trainer.rewrite_base_model()` adds the scaled delta to the base model’s weights, producing a persistently modified checkpoint. For cross-feature analysis, `plot_topk_overlap()` compares the top‑k most affected parameters across multiple trained features to reveal structural relationships.

## Key Results
- Achieved encoder correlation of 0.9757 and clear class separation for the English 3SG vs. 3PL pronoun paradigm.
- Large-scale analysis of 44 features on BERT revealed: German articles show high parameter overlap due to syncretism; race/religion features overlap up to ~17%; English grammatical number and person are mostly disjoint.
- The open-source package successfully reproduces prior use cases and enables scalable feature comparison across models.

## Why This Works (Mechanism)
### Mechanism 1: Feature Direction Learning from Contrastive Gradients
- **Claim:** The system learns a reusable, low-dimensional feature direction directly from the difference between a model's gradients on a factual instance (e.g., predicting "she") and a counterfactual instance (e.g., predicting "they").
- **Mechanism:** For a given pair of feature classes (e.g., 3SG vs. 3PL), the system generates text prediction instances where a target token belongs to one class. It computes the gradient of the model's loss for the factual and counterfactual cases. An encoder neural network is trained to map the high-dimensional gradient vector (for a specific layer or parameter set) to a single scalar, where values of +1 and -1 correspond to the two classes. A decoder network then maps this scalar back to a parameter update direction in the original model's weight space.
- **Core assumption:** The contrast between factual and counterfactual gradients for a feature isolates a signal that can be compressed into a meaningful, class-separating scalar without losing the essential information needed to steer the model.
- **Evidence anchors:** [Section 3.1] Describes constructing `TextPredictionDataCreator` with `TextFilterConfig` to generate class-specific training data. [Section 3.2] Details the `TextPredictionTrainer` that trains the encoder-decoder on MLM/CLM gradients. [Figure 2] Shows training convergence and correlation metrics for the encoder.
- **Break condition:** If the factual and counterfactual gradients are not meaningfully different, the encoder will fail to learn a separating scalar, detectable via low correlation in the intra-model evaluation.

### Mechanism 2: Persistent Model Rewriting via Controlled Parameter Updates
- **Claim:** The learned decoder output (a parameter delta) can be applied to the base model as a controlled weight update, persistently shifting the model's behavior along the feature axis without catastrophic forgetting of general capabilities.
- **Mechanism:** After training, the decoder generates a feature direction `δ_w`. This direction is scaled by a learned "learning rate multiplier" and added to the base model's weights: `w_new = w_base + α * δ_w`. The scale `α` is selected via grid search during decoder evaluation, constrained by a Language Modeling Score (LMS) to preserve general fluency.
- **Core assumption:** The parameter update direction `δ_w` is orthogonal enough to the base model's task-relevant directions that a scaled addition modifies the target feature without disproportionately altering other behaviors.
- **Evidence anchors:** [Section 3.4] Explicitly describes `trainer.rewrite_base_model()` applying the decoder's output. [Figure 4] Illustrates the decoder evaluation trade‑off: selecting `α` to maximize target‑class probability increase while maintaining LMS. [Abstract] Mentions "persistent model modification" and "controlled weight updates."
- **Break condition:** An insufficiently constrained `α` (too large) would degrade LMS, indicating the update is too disruptive. Conversely, if the encoder's separation is poor, `δ_w` will not be a clean feature direction, and rewriting will have unpredictable effects.

### Mechanism 3: Scalable Feature Similarity Analysis via Parameter Overlap
- **Claim:** Multiple independently learned feature directions can be compared by analyzing the overlap of their top‑k most affected parameters in the base model, revealing structural relationships (e.g., syncretism, bias overlap) between features.
- **Mechanism:** After training multiple GRADIEND runs for different feature pairs on the same base model, the top‑k parameters with largest absolute values in each feature's `δ_w` are identified. Pairwise Jaccard‑like overlap (intersection over union of top‑k sets) is computed and visualized (Venn diagram or heatmap). Patterns of high overlap suggest shared encoding.
- **Core assumption:** The magnitude of a parameter's change in `δ_w` is a valid proxy for its importance to that feature, and comparing these importance sets across features reveals functional sharing in the model's weight space.
- **Evidence anchors:** [Section 3.5] Introduces `plot_topk_overlap()` for inter‑model evaluation. [Section 4 & Figure 6] Presents the large‑scale heatmap analysis of 44 features, showing patterns like German article syncretism (high overlap) and disjoint English number/person (low overlap). [Abstract] States the package enables "scalable feature comparison."
- **Break condition:** The overlap metric is sensitive to the choice of `k`. If `k` is too small, noise dominates; if too large, overlap becomes ubiquitous. Furthermore, if features are not meaningfully encoded in the same parameter subnetwork, overlap will be low even if they are conceptually related.

## Foundational Learning
- **Concept: Gradient‑Based Interpretability & Contrastive Signals**
  - **Why needed here:** GRADIEND's core input is the gradient of a loss function with respect to model parameters. Understanding how a gradient reflects a model's "surprise" or sensitivity to a change in input/target is essential to grasp why the factual‑counterfactual gradient difference is a feature signal.
  - **Quick check question:** If swapping a target token from "she" to "they" causes a large gradient magnitude in a parameter, what does that imply about that parameter's role in representing that distinction?
- **Concept: Encoder‑Decoder Training in Parameter Space**
  - **Why needed here:** The method uses an auxiliary network (encoder‑decoder) to find a compressed, linear representation of a feature in the original model's high-dimensional weight space. This is not standard supervised learning on data, but "meta‑learning" on gradients.
  - **Quick check question:** Why is it necessary to train an encoder to produce a scalar, rather than simply using the dot product of the gradient with some random vector?
- **Concept: Parameter Space Interventions vs. Activation Patching**
  - **Why needed here:** GRADIEND creates persistent weight updates, unlike runtime activation interventions (e.g., TransformerLens). This requires understanding the implications of modifying weights versus activations for interpretability and control.
  - **Quick check question:** What is a key risk of persistent weight updates that activation patching avoids, and how does GRADIEND's LMS constraint mitigate it?

## Architecture Onboarding
- **Component map:** `TextPredictionDataCreator` generates `GradientDataset`; `TextPredictionTrainer` consumes data, uses `GradientModel` to compute gradients, trains `FeatureModel` (encoder-decoder), and can `rewrite_base_model()` to produce a modified checkpoint. `Evaluator` and `Visualizer` are accessed via `trainer.evaluate_*()` and `plot_topk_overlap()`.
- **Critical path:**
  1. Define feature classes via `TextFilterConfig`.
  2. Run `creator.generate_training_data()` to obtain `GradientDataset`.
  3. Initialize `TextPredictionTrainer` with base model and data.
  4. Call `trainer.train()` to train the encoder‑decoder and save the best `FeatureModel`.
  5. Use `trainer.evaluate_encoder()` and `trainer.evaluate_decoder()` to assess separation and select hyperparameters.
  6. Call `trainer.rewrite_base_model()` to export a modified checkpoint.
  7. For cross‑feature comparison, repeat steps 1–4 for multiple features, then invoke `plot_topk_overlap(models)`.
- **Design tradeoffs:**
  - **Pruning (Pre/Post):** Reduces memory/compute by selecting a subset of parameters, but may discard subtle feature information if thresholds are too aggressive. Defaults (1% pre, 10% post) are conservative.
  - **Gradient Source:** MLM (bidirectional) vs. CLM (causal) gradients; choice affects the feature signal and must align with the linguistic nature of the feature.
  - **Target Layer:** Gradients can be extracted from any layer; the paper uses the output layer (`lm_head`) but earlier layers might capture more abstract (and noisier) features.
- **Failure signatures:**
  - **Encoder correlation ≈ 0:** Indicates poor class separation; likely due to inadequate data construction or non‑linearly decodable feature from the chosen gradient space.
  - **Decoder LMS plummets with small α:** Suggests the learned `δ_w` is too large or misaligned; may indicate encoder collapse or an untrainable decoder.
  - **Inter‑model overlap near 0% or 100% universally:** Points to an inappropriate `k` setting or a data bug causing all features to appear either unrelated or identical.
- **First 3 experiments:**
  1. **Reproduce English 3SG vs. 3PL:** Follow Section 3 verbatim. Expected: encoder correlation >0.95 and clear class separation in plots.
  2. **Compare English Gender vs. Number:** Train two features (e.g., gender: he/she; number: 3SG/3PL) on the same base model (BERT‑base). Run `plot_topk_overlap` with `topk=1000`. Expected: moderate overlap (both involve pronouns) but less than within‑paradigm pairs.
  3. **Handle Syncretism in German Articles:** Use `TextFilterConfig` with spaCy tags to disambiguate syncretic German definite articles (e.g., "die" for Fem.Acc/Neut.Nom). Train multiple article transition pairs (e.g., Fem.Acc → Fem.Dat). Expected: high overlap for pairs sharing surface forms, replicating Figure 6.

## Limitations
- Core dependencies (Python, PyTorch, Transformers, spaCy) are not version‑pinned, risking incompatibility.
- Random seeds for data sampling and training are unspecified, so reported metrics may vary across runs.
- The top‑k overlap metric lacks sensitivity analysis; patterns may depend heavily on the arbitrary choice of *k*.

## Confidence
- **Feature direction learning from contrastive gradients: Medium**  
  Reasoning: Strong empirical validation on a well-defined linguistic paradigm (pronouns) with high encoder correlation (0.9757) supports the mechanism. However, the theoretical basis for why contrastive gradients compress to a linear direction is not deeply established, and results may not generalize to more abstract features without careful tuning.
- **Persistent model rewriting via controlled updates: Medium**  
  Reasoning: The decoder evaluation with LMS constraint demonstrates successful rewriting with minimal fluency loss on the tested paradigm. Yet, the approach relies on grid search for the learning rate multiplier and may not scale to features that interfere more with core model knowledge, as indicated by the low confidence in the overlap analysis.
- **Scalable feature similarity via parameter overlap: Low**  
  Reasoning: The overlap metric shows intriguing patterns (e.g., German syncretism) but lacks sensitivity analysis and may be highly sensitive to the choice of top‑k. The paper presents a single heatmap without robustness checks, making the conclusions tentative.

## Next Checks
