# Adaptive Text Anonymization: Learning Privacy-Utility Trade-offs via Prompt Optimization

## Quick Facts
- **arXiv ID:** 2602.20743
- **Source URL:** https://arxiv.org/abs/2602.20743
- **Reference count:** 40
- **Primary result:** A prompt optimization framework (GEPA) automatically discovers anonymization instructions that achieve superior privacy-utility trade-offs across five diverse datasets, outperforming baselines and matching closed-source model performance with open-source models.

## Executive Summary
The paper introduces adaptive text anonymization, addressing the limitation of static methods that cannot adjust to varying privacy-utility needs across domains. The authors propose GEPA, a two-stage evolutionary prompt optimization framework that uses a local language model both to anonymize text and to propose prompt mutations. Through a warm-start phase with simple scalar feedback followed by refinement with rich detailed feedback, GEPA efficiently explores the prompt space and discovers multiple Pareto-optimal strategies. Evaluated on five benchmark datasets, the method consistently outperforms existing baselines and demonstrates that open-source models can achieve performance comparable to closed-source APIs while keeping sensitive data on-premise.

## Method Summary
GEPA optimizes prompts for text anonymization using an evolutionary algorithm. Starting from a seed prompt, it maintains a population of candidate prompts. In Stage 1 (Warm-Start), prompts are selected via Pareto-based sorting on privacy and utility scores, then mutated by a proposer agent using simple scalar feedback (average of privacy and utility). Early stopping conserves budget. In Stage 2 (Refinement), if budget remains, a rich feedback function (generated by an LLM) provides detailed error analysis and suggestions, and adaptive validation sampling reduces evaluation cost. The final prompt is selected from the Pareto front on the full validation set. The entire process runs locally using an open-source model, avoiding data offloading.

## Key Results
- On DB-Bio, optimized Qwen3-30B-A3B achieves 65.5% privacy and 100% utility, surpassing GPT-5 task-specific prompts (63.6/100).
- On SynthPAI, it reaches 22.5/94.4 versus 18.3/88.1 for baselines.
- On TAB, it attains 92.3/56.2 versus 99.3/48.6 (higher utility but lower privacy), demonstrating varied trade-offs across tasks.

## Why This Works (Mechanism)
### Mechanism 1: Evolutionary Prompt Search
Evolutionary prompt optimization (GEPA) efficiently discovers diverse, high-performing anonymization instructions by exploring the prompt space through mutation and Pareto-based selection. The algorithm maintains a population of prompts. Each iteration selects prompts via non-dominated sorting (Pareto fronts) based on privacy and utility scores, then uses a proposer agent to mutate selected prompts into new candidates. This multi-objective approach preserves a spectrum of trade-offs rather than collapsing to a single scalar optimum.

### Mechanism 2: Two-Stage Feedback Balance
The two-stage feedback (warm-start with simple scalar feedback, then refinement with rich detailed feedback) balances sample efficiency with fine-grained control, maximizing the utility of a fixed rollout budget. Stage 2 uses a base feedback function µ (e.g., average of privacy and utility) that is cheap and provides a coarse signal. It runs until early stopping to conserve budget. Stage 3 switches to a rich feedback function µ_rich that includes natural-language explanations, error analyses, and actionable suggestions generated by a separate LLM. This richer signal allows targeted mutations and escapes plateaus. Adaptive validation sampling (using a subset of D_valid) further reduces evaluation cost during refinement.

### Mechanism 3: Local Model Deployment
By optimizing prompts for a locally deployed open-source model, the framework achieves performance comparable to closed-source APIs while keeping sensitive data on-premise, resolving the privacy paradox of outsourcing anonymization. The same local model serves dual roles: as the anonymization agent that applies prompts to data, and as the proposer agent that mutates prompts during optimization. All data used for optimization (D_train, D_valid) remains local; only a small holdout set is used for external evaluation (e.g., with Gemini-2.5-flash).

## Architecture Onboarding
Component map: Dataset -> GEPAOptimizer (PromptPool, ProposerAgent) -> Evaluator. FeedbackGenerator provides feedback to GEPAOptimizer. PrivacyMetric/UtilityMetric are used by Evaluator and FeedbackGenerator.

Critical path: 1) Define task and metrics; 2) Prepare data splits; 3) Implement base feedback scalar; 4) Generate rich feedback function via LLM; 5) Initialize prompt pool with seed; 6) Run warm-start with base feedback and early stopping; 7) If budget remains, run refinement with rich feedback and adaptive validation sampling; 8) Select best prompt from final pool on full validation; 9) Evaluate on test set.

Design tradeoffs: Budget B controls exploration; early stopping patience n avoids waste; adaptive sampling ratio α trades off evaluation cost vs. noise; feedback choice impacts guidance quality; model choice for proposer vs. anonymizer affects locality and performance.

Failure signatures: No improvement -> check metrics, mutation, early stopping; overfitting to validation -> increase valid size or reduce adaptive sampling; rich feedback degradation -> inspect feedback strings; high variance across runs -> use multiple seeds; poor trade-off -> examine Pareto set.

First 3 experiments: 1) Replicate DB-Bio results with Qwen3-30B-A3B; 2) Ablate two-stage design (warm-start only, refinement only, rich throughout); 3) Compare automatic vs. manual rich feedback on one task.

## Open Questions the Paper Calls Out
### Open Question 1
How does the framework's reliance on a simple arithmetic mean (unweighted aggregation) of privacy and utility scores, versus more complex decision rules (e.g., lexicographic ordering, hard constraints, or weighted sums), affect the quality and diversity of the discovered trade-off strategies in real-world deployments with specific regulatory or operational requirements?

### Open Question 2
To what extent do the privacy and utility evaluator LLMs (e.g., Gemini-2.5-flash) introduce systematic biases or instability that skew the optimization process and the final privacy-utility trade-off, and can these biases be characterized or mitigated?

### Open Question 3
What are the core reasons behind the observed model-specific behaviors (e.g., Mistral's steep privacy gains vs. utility cost, Qwen's balanced performance) in the optimized prompts, and do these stem from inherent model capabilities, inductive biases, or interactions with the GEPA algorithm's search dynamics?

### Open Question 4
How stable and reproducible are the discovered multi-prompt trade-off frontiers across different random seeds of the evolutionary algorithm, different initial prompt pools, or slight variations in the small validation set (D_valid)? What is the variance in the set of Pareto-optimal solutions?

### Open Question 5
Is the two-stage optimization design (warm-start with simple feedback followed by refinement with rich feedback) necessary, or could a single-stage process using only rich feedback (or a different feedback schedule) achieve comparable or better results with the same budget? What is the specific role of each stage in escaping local optima?

## Limitations
- Underspecified details: µ calculation, proposer mutation prompt, rich feedback generation, adaptive validation sampling.
- Evaluation relies on LLM judges, which are noisy and may not reflect true privacy/utility.
- Small fixed validation sets (111) risk overfitting; adaptive sampling not fully described.
- Final test evaluation still uses external LLM, contradicting "fully local" claim.

## Confidence
- GEPA discovers diverse Pareto-optimal prompts: **Medium** (ablations positive, but mutation unclear).

- Open-source models match closed-source performance: **Medium** (comparison across different models may be unfair).
- Overall superiority over baselines: **Medium** (results unverified due to missing baseline details).
