# Can LLMs Beat Classical Hyperparameter Optimization Algorithms? A Study on autoresearch

## Quick Facts
- **arXiv ID**: 2603.24647
- **Source URL**: https://arxiv.org/abs/2603.24647
- **Reference count**: 17
- **Primary result**: Classical optimizers (CMA-ES, TPE) achieve lower validation bits-per-byte than pure LLM agents in fixed search spaces; the hybrid Centaur (state-sharing) attains the best result (0.9763) and reduces variance.

## Executive Summary
This paper benchmarks nine hyperparameter optimization methods—four classical, four LLM-based, and one hybrid—on tuning a 50-million-parameter language model under identical 24-hour GPU budgets. Classical optimizers CMA-ES and TPE consistently produce lower validation bits-per-byte (0.9785 and 0.9768) when the search space is fixed. Among LLM agents, only Karpathy Agent Code (0.9814), which directly edits training code using a 27B model, approaches the classical performance. The hybrid Centaur, which shares CMA-ES's internal state with an LLM on 30% of trials, achieves the best val_bpb (0.9763) and exhibits reduced variance; notably, a 0.8B variant outperforms the 27B version. The analysis reveals that out-of-memory (OOM) avoidance is a strong predictor of success, whereas search diversity is not. Frontier models such as Gemini 3.1 Pro Preview remain competitive but do not close the gap.

## Method Summary
The study evaluates nine hyperparameter optimization approaches on a single 50M-parameter language model, distributing an equal 24-hour GPU budget across all methods. The search space is held constant across all agents except the Karpathy Agent Code variant, which is allowed to modify the training code directly. Classical baselines include CMA-ES, TPE, and two additional methods; LLM-based agents employ various prompting and code-generation strategies; the hybrid Centaur integrates CMA-ES's internal state (mean, step-size, covariance) to guide an LLM's proposals for a predefined fraction (30%) of trials. Performance is measured by validation bits-per-byte (val_bpb), with lower values indicating better compression and thus a better model. The experimental design ensures that differences in results stem from the optimization algorithms rather than variations in compute or search space.

## Key Results
- Classical optimizers dominate in fixed search spaces: CMA-ES (0.9785) and TPE (0.9768) achieve the lowest val_bpb.
- Karpathy Agent Code narrows the performance gap (0.9814) by editing training code with a 27B model but still lags behind classical methods.
- Hybrid Centaur achieves the best overall val_bpb (0.9763), reduces variance, and a 0.8B variant surpasses the 27B version, underscoring the efficiency of state sharing.
- Out-of-memory (OOM) avoidance is a strong predictor of final performance; search diversity shows no such correlation.
- Frontier models (e.g., Gemini 3.1 Pro Preview) are competitive but do not surpass classical optimizers.

## Why This Works
The hybrid Centaur's advantage likely arises from combining the sample efficiency and global search capabilities of CMA-ES with the flexible reasoning of LLMs. By feeding CMA-ES's internal state to the LLM, the agent receives a concise representation of the search landscape, enabling it to propose hyperparameters that are both promising and memory-safe. This synergy reduces the LLM's dependence on massive scale; the 0.8B variant's competitiveness demonstrates that state sharing can substitute for model size. Moreover, the strong link between OOM avoidance and performance suggests that the primary challenge in hyperparameter optimization within tight time budgets is to avoid catastrophic configurations that waste GPU time, rather than to maximize abstract search diversity.

## Foundational Learning
- **Hyperparameter Optimization (HPO)**: Automated search for the best hyperparameters (e.g., learning rate, batch size) of a machine learning model. *Why needed*: Manual tuning is labor-intensive and often suboptimal; HPO systematically explores the configuration space to improve model performance. *Quick check*: Can you differentiate between random search, Bayesian optimization (e.g., TPE), and population-based methods like CMA-ES?
- **CMA-ES**: Covariance Matrix Adaptation Evolution Strategy, a derivative-free optimizer that evolves a population via a multivariate normal distribution whose covariance adapts to the landscape. *Why needed*: It handles non-convex, noisy, and high-dimensional problems robustly, often outperforming gradient-based methods. *Quick check*: Describe how CMA-ES updates its mean vector, step size, and covariance matrix after evaluating a set of samples.
- **TPE**: Tree-structured Parzen Estimator, a Bayesian optimization method that builds separate density models for good and bad observations to select the next hyperparameters. *Why needed*: Efficient for conditional hyperparameter spaces and less sensitive to the order of evaluations than Gaussian processes. *Quick check*: Explain how TPE uses kernel density estimators to compute the probability of a configuration being good and how it selects the next point.
- **LLM-based Optimization Agents**: Systems that harness large language models to propose hyperparameter configurations or alter training code based on prior trial outcomes. *Why needed*: LLMs encode vast knowledge about machine learning practices and can reason about code, offering a new paradigm for black-box optimization. *Quick check*: What prompting template might you use to elicit hyperparameter suggestions from an LLM given a history of trials? What are common pitfalls (e.g., invalid syntax, ignoring budget constraints)?
- **Hybrid Optimization (Centaur)**: A framework that merges a classical optimizer's internal state with an LLM's generative power, periodically querying the LLM using the optimizer's state to guide trial proposals. *Why needed*: Seeks to combine the sample efficiency and theoretical guarantees of classical methods with the adaptive, high-level reasoning of LLMs. *Quick check*: In the Centaur design, which specific CMA-ES state components (mean, step-size, covariance) are shared, and how might the LLM interpret them?
- **Bits-Per-Byte (BPB)**: A metric for language models that measures the average number of bits required to encode each byte of data under the model’s probability distribution. *Why needed*: Lower BPB indicates a better model (higher likelihood) and is comparable across different tokenization schemes; it is a common evaluation for compression and language modeling. *Quick check*: How is BPB calculated from cross-entropy loss, and why is it preferred over perplexity for models with subword tokenization?

## Architecture Onboarding
**Component Map**  
Training Pipeline -> Validation -> Objective Metric (val_bpb) -> Classical Optimizer (CMA-ES) -> Hyperparameter Samples -> Model Training.  
For Centaur: CMA-ES Internal State (mean, step-size, covariance) -> LLM (prompt with state + history) -> Proposed Configurations (on 30% of trials).  
For Karpathy Agent Code: LLM -> Training Code Edits -> Modified training pipeline.

**Critical Path**  
1. Initialize the chosen optimizer (or LLM agent) and set total GPU time budget (24 hours).  
2. For each trial until the budget is exhausted:  
   a. Sample a hyperparameter configuration (or code edit) from the optimizer/LLM.  
   b. Train the 50M-parameter language model using that configuration for the allocated portion of the budget.  
   c. Evaluate the trained model on the validation set to compute val_bpb.  
   d. Record the configuration, val_bpb, and any out-of-memory (OOM) events.  
   e. Update the classical optimizer with the result; if using Centaur and the trial count reaches the 30% LLM threshold, query the LLM with the latest CMA-ES state to obtain a batch of proposals.  
3. After the budget is fully consumed, select the configuration with the lowest val_bpb as the best found.

**Design Tradeoffs**  
- Fixed search space vs. code editing: Fixed spaces enable fair, reproducible comparisons but constrain LLM agents to a limited set of hyperparameters; allowing code editing (Karpathy) expands the design space but introduces risks of syntactic errors and unbounded changes.  
- LLM scale vs. inference cost: Larger LLMs (e.g., 27B) possess more knowledge but are slower and more expensive to query; Centaur’s success with a 0.8B model indicates that providing structured state can offset the need for massive models.  
- Hybrid trial allocation: Using LLM proposals for only 30% of trials balances exploration (via LLM) with exploitation (via CMA-ES); shifting this percentage trades off stability against the chance of discovering unconventional configurations.  
- OOM handling: Proposals that avoid out-of-memory configurations complete training and contribute useful data; thus, methods that implicitly or explicitly consider memory constraints gain more trials within the fixed budget.

**Failure Signatures**  
- Frequent OOM errors during training, indicating infeasible batch sizes or model dimensions.  
- High variance in val_bpb across runs of the same method, suggesting lack of robustness.  
- LLM agents repeatedly outputting invalid Python code or hyperparameters outside the valid ranges.  
- In Centaur, a trend where LLM-proposed trials degrade the CMA-ES state, causing performance to stagnate or worsen.

**First Three Experiments**  
1. **Hybrid Ablation**: Compare pure CMA-ES (0% LLM-guided trials), the standard 30% Centaur, and an LLM-only agent that receives CMA-ES state but makes all proposals (100% LLM). This isolates the effect of LLM guidance and the specific allocation ratio.  
2. **Scale Study**: Test the top methods (CMA-ES, TPE, Centaur) across model sizes (10M, 50M, 100M, 1B) and budget lengths (12h, 24h, 48h) to verify whether the observed ranking holds under varied resources and model scales.  
3. **Domain Transfer**: Apply the same benchmark suite to other tasks: image classification (ResNet on CIFAR-10) and machine translation (Transformer on WMT16 En-De). This checks whether the results are specific to language modeling or generalize across domains.

## Limitations
- The evaluation is restricted to a single 50M-parameter model and a fixed 24-hour GPU budget; results may not generalize to other scales or longer training times.
- The search space is largely fixed (except for Karpathy Agent's code edits), limiting the LLM agents' ability to explore beyond predefined hyperparameters.
- Only one LLM agent per category was tested, and frontier model coverage is limited (primarily Gemini 3.1 Pro Preview); the OOM avoidance correlation remains correlational.

## Confidence
- Classical optimizers consistently beat pure LLM agents (fixed space): Medium  
- Karpathy Agent Code narrows the gap: Medium  
- Hybrid Centaur (state-sharing) best and reduces variance: Medium  
- OOM avoidance predicts performance: Low  
- Frontier models competitive but gap remains: Medium
