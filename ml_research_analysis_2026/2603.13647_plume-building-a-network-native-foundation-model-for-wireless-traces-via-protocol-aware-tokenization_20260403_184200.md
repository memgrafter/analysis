# PLUME: Building a Network-Native Foundation Model for Wireless Traces via Protocol-Aware Tokenization

## Quick Facts
- **arXiv ID:** 2603.13647
- **Source URL:** https://arxiv.org/abs/2603.13647
- **Reference count:** 40
- **Primary result:** A 140M-parameter model achieves 74–97% next-packet accuracy and matches Claude/GPT-5.4 on the same prediction task while using >600× fewer parameters, with zero-shot anomaly detection AUROC ≥0.99.

## Executive Summary
PLUME introduces a foundation model for 802.11 wireless packet traces that overcomes the limitations of standard tokenizers by preserving protocol field boundaries and timing semantics. Its protocol-aware tokenizer dissects Wireshark PDML output along field trees, introduces gap tokens for inter-arrival times, and normalizes identifiers, yielding 6.2× shorter sequences than BPE with higher per-token entropy. Trained on data curated via HDBSCAN+MMR to reduce beacon bias from >50% to 4.7%, the model excels at next-packet prediction and zero-shot anomaly detection. With only 140M parameters, it rivals frontier LLMs in accuracy while running efficiently on a single GPU, enabling privacy-preserving, on-prem root cause analysis.

## Method Summary
PLUME constructs a decoder-only transformer (GPT-2 style, 12 layers, 768D) trained with a causal language modeling objective. Inputs are 802.11 PCAPs dissected with tshark into PDML, then tokenized via a custom protocol-aware process: the PDML field tree is traversed to emit atomic field-name and field-value tokens, gap tokens encode quantized inter-packet delays, layer markers delimit protocol layers, and identifiers (MACs, IPs) are normalized. A secondary BPE handles human-readable strings. The training corpus of 7,890 PCAPs (149,238 packets) is curated by embedding each frame, clustering with HDBSCAN, and selecting diverse representatives via MMR to reduce redundancy and beacon dominance; synthetic generation populates small clusters. The model is trained on 48.9M tokens using AdamW (lr 7e-4) for 20 epochs, with a context window of 2,048 tokens (~6 packets).

## Key Results
- **Next-packet prediction:** 74–97% token accuracy across five 802.11 failure categories, matching Claude/GPT-5.4 with >600× fewer parameters.
- **Zero-shot anomaly detection:** AUROC ≥0.99 on held-out failure PCAPs using mean per-token probability scoring.
- **Efficiency:** Runs at ~200 packets/sec on a single A10G GPU with near-zero marginal cost, enabling on-prem deployment.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Protocol-aware tokenization preserves field boundaries and timing semantics, enabling efficient learning of cross-packet state machines.
- **Mechanism:** Tokenizer splits PDML along the dissector field tree, emits gap tokens for inter-arrival times, normalizes identifiers, and uses layer markers; this yields field-value tokens that respect protocol hierarchy rather than flattening into subwords.
- **Evidence:** [abstract] yields 6.2× shorter sequences than BPE with 7.61 bits/entropy; [section 3.2] details tokenization rules; Table 3 shows compression and entropy gains.

### Mechanism 2
- **Claim:** HDBSCAN+MM curation reduces beacon dominance and reactive-capture bias while preserving rare failure patterns.
- **Mechanism:** Frames are embedded, clustered to identify near-duplicates, and diverse representatives are selected per cluster using MMR; synthetic generation populates small clusters.
- **Evidence:** [abstract] beacon bias reduced to 4.7%; [section 3.4] describes curation pipeline; Table 4 shows beacon fraction drop from >50% to 4.7% with token entropy remaining high.

### Mechanism 3
- **Claim:** Decoder-only auto-regressive architecture aligns with the sequential nature of packet exchanges.
- **Mechanism:** Causal attention masks enforce left-to-right context modeling, mirroring dependency in protocol dialogues (e.g., EAPOL exchanges).
- **Evidence:** [abstract] GPT-style objective; [section 4.2] decoder outperforms encoder; Table 2 shows 83.1% token accuracy vs. 25.7% for 3-gram; Table 8 shows parity with frontier LLMs.

## Foundational Learning

- **Concept: Protocol State Machines**
  - *Why needed:* Packets form dialogues (e.g., 802.11 auth/assoc); model must learn valid/invalid transitions.
  - *Quick check:* Given a DHCP Discover, what are the next two expected packets in success? What indicates failure?

- **Concept: Field Semantics vs. Surface Forms**
  - *Why needed:* Tokenization uses atomic field tokens and normalizes values (e.g., ACK instead of 0x10); model must map equivalent representations.
  - *Quick check:* Why is expanding symbolic values (ACK) preferable to hex codes (0x10) for learning patterns?

- **Concept: Temporal Dynamics as Tokens**
  - *Why needed:* Inter-arrival times encode state (e.g., timeout vs. normal gap); model must distinguish timing scenarios.
  - *Quick check:* How to represent a 50ms silent gap between Assoc Req and Resp? What might it suggest?

## Architecture Onboarding

- **Component map:** PCAP → tshark (PDML) → field-tree traversal → tokenization (field-value, gap tokens, layer markers) → token ID sequence → GPT-2 decoder (12L/12H/768D) → per-token logits → likelihood scoring / next-token generation → structured summary.
- **Critical path:** Capture → PDML dissection → Tokenization → Model forward pass → Per-token logits → Likelihood scoring / Next-token generation → Summary. Tokenization must preserve layer boundaries and timing.
- **Design tradeoffs:** 
  - Context window (2048 tokens) limits packets per context (~6); longer flows need sliding windows.
  - Model size (140M optimal) vs. data size: larger models overfit the 48.9M-token corpus.
  - Field-level tokens require stable Wireshark dissector versions; field name changes break mapping.
- **Failure signatures:**
  - *Training:* Beacon fraction >10% in curated set; token entropy <7.0 bits.
  - *Inference:* Per-field accuracy <90% for address/frame-control fields; high variance across PCAPs in a category.
  - *Deployment:* VRAM >1GB for 140M model; throughput <50 pkt/s on A10G.
- **First 3 experiments:** 
  1. Tokenization ablation: Compare field-value tokenizer vs. BPE on tokens/packet, entropy, next-packet accuracy.
  2. Curation impact: Train identical models on raw vs. HDBSCAN+MMR data; measure beacon fraction and accuracy on rare failures.
  3. Scaling curves: Train Small/Medium/Large variants; plot token accuracy vs. parameters; expect Medium peaks, Large overfits.

## Open Questions the Paper Calls Out
- **Extend Plume to data-plane protocols?** Basis: Conclusion states this is a natural next step. Why unresolved: Tokenizer/training target 802.11 headers; data-plane has payloads and different fields.
- **Improve root cause classification?** Basis: Conclusion notes 73.2% accuracy needs larger evaluation sets and task-specific feature engineering. Why unresolved: Current 19-D features are limited.
- **Calibrate anomaly detector and characterize confident errors?** Basis: Anomaly detector uses raw probabilities without calibration; confidently wrong predictions not analyzed. Why unresolved: Raw probabilities may be miscalibrated, risking safe RCA.
- **Generalize Plume across multiple sites?** Basis: All data from single enterprise deployment; multi-site evaluation remains open. Why unresolved: Performance may be deployment-specific.

## Limitations
- Tokenizer depends on stable Wireshark/tshark dissector field names; version mismatches break semantic mapping.
- Curation pipeline hyperparameters (HDBSCAN `min_cluster_size`, MMR λ) and synthetic generation details are omitted, making replication sensitive.
- Context window (2048 tokens) restricts modeling longer exchanges; generalizability to other protocols unverified.

## Confidence
- **Protocol-aware tokenization:** Medium (compression/entropy gains documented but fragile to dissector changes)
- **HDBSCAN+MMR curation:** Medium (beacon reduction shown but hyperparameter sensitivity unknown)
- **Decoder-only architecture:** High (clear superiority over encoder and consistent scaling trends)
- **Overall system effectiveness:** Medium (strong metrics but replication uncertainties and limited protocol scope)
