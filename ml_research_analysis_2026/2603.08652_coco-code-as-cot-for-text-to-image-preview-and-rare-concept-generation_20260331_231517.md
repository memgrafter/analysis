# CoCo: Code as CoT for Text-to-Image Preview and Rare Concept Generation

## Quick Facts
- arXiv ID: 2603.08652
- Source URL: https://arxiv.org/abs/2603.08652
- Reference count: 18
- Primary result: CoCo achieves large improvements on structural and rare concept benchmarks (+68.83% on StructT2IBench, +54.8% on OneIG-Bench, +41.23% on LongText-Bench) by using executable code as a planning step.

## Executive Summary
CoCo introduces a novel Chain-of-Thought (CoT) approach for text-to-image generation that replaces natural language planning with executable code. The method first generates code that specifies a spatial layout, executes this code to produce a deterministic draft image, and then refines the draft into a high-fidelity final image. This pipeline improves structural accuracy and handling of rare concepts, as demonstrated by significant gains on multiple benchmarks. Trained on the curated CoCo-10K dataset, CoCo outperforms both direct generation and other CoT-based methods.

## Method Summary
CoCo employs a two-stage generation process. Given a text prompt, a language model generates code that defines the layout of objects and their attributes. This code is executed by a layout executor (e.g., a rendering engine) to produce a draft image that precisely follows the specified spatial arrangement. The draft is then fed to an image refiner—typically a diffusion model—to enhance details and fidelity. This separation allows for deterministic layout control and focused refinement. The system is trained on the CoCo-10K dataset, which contains prompt-code-draft-refined image quadruplets.

## Key Results
- Achieved +68.83% on StructT2IBench, +54.8% on OneIG-Bench, and +41.23% on LongText-Bench over direct generation.
- Outperforms other CoT-based text-to-image methods.

## Why This Works (Mechanism)
Executable code serves as a precise intermediate representation that eliminates ambiguity in spatial planning. Unlike natural language, code can unambiguously define coordinates, sizes, and relationships, which the layout executor can render deterministically. This draft provides a concrete scaffold for the refiner, reducing the burden of simultaneously composing layout and details. The two-stage separation thus improves structural compliance and rare concept generation by enforcing explicit layout reasoning.

## Architecture Onboarding
Component map: Text Prompt -> Code Generator (LLM) -> Layout Executor (Renderer) -> Draft Image -> Image Refiner (Diffusion) -> Final Image

Critical path: The core workflow flows sequentially from prompt to code, then to draft, then to refined image. The code generator and refiner are trainable models; the executor is a fixed rendering engine.

Design tradeoffs:
- **Latency vs Quality**: Two-stage pipeline adds execution time but yields better layout.
- **Generality of Code**: The executor must support a limited set of drawing primitives; complex scenes may require expressive code.
- **Error Propagation**: Mistakes in code generation lead to incorrect drafts, which the refiner may not fully correct.

Failure signatures:
- Syntax errors in generated code (execution fails).
- Draft images with misaligned objects or missing elements.
- Refined images that distort the draft layout (over-refinement).

First experiments to run:
1. Verify code generation accuracy on a small set of prompts by manual inspection of code correctness.
2. Measure the consistency of draft images from the same code (determinism check).
3. Compare final image quality with and without the draft stage (ablation) on a few prompts.

## Open Questions the Paper Calls Out
The paper does not have a dedicated open questions section; however, its limitations and confidence assessment highlight several unresolved issues:

- **Generalization**: Do the reported gains on academic benchmarks hold for diverse real-world prompts and truly unseen rare concepts?
- **Dataset bias**: What are the curation criteria and potential biases in CoCo-10K, and how do they affect rare concept handling? (Unknown: full dataset composition)
- **Efficiency**: How does the two-stage pipeline's computational overhead compare to its quality improvements in practical settings?
- **Novelty**: Is the executable code planning approach a significant departure from concurrent CoT methods, or an incremental adaptation?
- **Robustness**: How does the system handle code generation errors, and what are the typical failure signatures in complex scenes?
- **Component contributions**: What is the isolated effect of the deterministic drafting step versus the refinement stage? (Assumption: both stages contribute; needs ablation)

## Limitations
- Benchmark generalizability: Reported gains on academic benchmarks may not extend to diverse real-world prompts or truly unseen rare concepts.
- Dataset biases: CoCo-10K's curation criteria, diversity, and potential biases are unexamined, affecting claims about rare concept handling.
- Computational overhead: The two-stage pipeline introduces latency and execution dependencies; cost vs. marginal quality gain is not analyzed.
- Incremental novelty: Concurrent CoT methods (e.g., DraCco, LayerCraft) question the uniqueness of executable code planning.

## Confidence
- Code-based CoT outperforms direct generation and text-based CoT: **Medium** (large reported gains but lacking statistical tests and independent replication).
- CoCo effectively handles rare concepts and complex layouts: **Low-Medium** (dependent on unexamined dataset and benchmarks; no ablation isolating code execution).
- The plan-draft-refine pipeline is the key innovation: **Medium-High** (novel use of executable code, but necessity of execution step needs validation).

## Next Checks
1. **Statistical Replication**: Re-run evaluations on StructT2IBench, OneIG-Bench, and LongText-Bench with multiple random seeds, reporting means and standard deviations.
2. **Dataset Audit**: Analyze CoCo-10K's composition (object counts, spatial relationships, attribute complexity, concept frequency) and compare its diversity to standard T2I training sets.
3. **Ablation of Execution Step**: Compare full pipeline (code->render->refine) against: (a) code output only (no rendering, feed code directly to refiner) and (b) text CoT description (matched planning detail) to isolate the value of executable code and deterministic drafting.
