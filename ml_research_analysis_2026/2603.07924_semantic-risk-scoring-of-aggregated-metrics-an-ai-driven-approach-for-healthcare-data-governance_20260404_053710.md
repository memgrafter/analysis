# Semantic Risk Scoring of Aggregated Metrics: An AI-Driven Approach for Healthcare Data Governance
## Quick Facts
- **arXiv ID:** 2603.07924
- **Source URL:** https://arxiv.org/abs/2603.07924
- **Reference count:** 11
- **Primary result:** Pre-execution static analysis of SQL metric definitions using AST parsing, CodeBERT embeddings, and XGBoost classification assigns continuous risk scores (0-1), blocking queries above 0.85 with explanations; demonstrated accurate differentiation of high-risk (ZIP grouping 0.87, gender+diagnosis 0.93) versus lower-risk (gender alone 0.74) scenarios.

## Executive Summary
Healthcare organizations face privacy risks when sharing aggregated metrics, as even summarized data can enable re-identification. This paper presents a static AI framework that evaluates SQL metric definitions before execution. The system parses queries into abstract syntax trees (ASTs), extracts syntactic risk signals (e.g., sensitive columns in GROUP BY), and combines them with semantic embeddings from CodeBERT. An XGBoost classifier produces a probabilistic risk score; queries exceeding a configurable threshold (e.g., 0.85) are blocked and accompanied by human-readable explanations. Evaluation on a synthetic dataset shows the method distinguishes high-risk groupings (ZIP, gender+diagnosis) from safer ones (gender alone), offering nuanced, context-aware protection beyond rigid rule‑based systems.

## Method Summary
The task is to assess privacy risk of aggregated SQL queries in a healthcare setting. Inputs are a SQL query string and a schema indicating which columns are considered sensitive (e.g., zip, gender, diagnosis_code). The pipeline consists of: (1) a SQL parser (sqlglot) that generates an AST; (2) a feature extractor that produces two parallel representations: syntactic features (counts of GROUP BY/WHERE columns, joins, flags for sensitive columns) and a semantic embedding from CodeBERT; (3) concatenation of these features; (4) an XGBoost classifier trained on historical labeled queries to output a risk probability; (5) a decision engine applying a threshold; and (6) an explanation engine that derives human‑rationales from the AST. The model is static—it does not access actual data distributions—trading some accuracy for speed and pre‑execution safety.

## Key Results
- The system assigns risk scores of 0.87 to a query grouping by ZIP code and 0.93 to grouping by gender plus diagnosis code, correctly classifying them as high‑risk.
- A query grouping by gender alone receives a score of 0.74 and is approved, demonstrating nuanced discrimination between sensitive and non‑sensitive groupings.
- Queries exceeding the 0.85 threshold are blocked and accompanied by clear explanations (e.g., “ZIP code is a quasi‑identifier”), enabling governance.

## Why This Works (Mechanism)
The framework relies on three complementary mechanisms:

**1. Syntactic pattern extraction via AST parsing.** The SQL parser converts the query into an abstract syntax tree, which is traversed to extract deterministic features such as the number and identity of columns in GROUP BY/WHERE clauses, the count of table joins, and flags for pre‑identified sensitive columns. These structural signals serve as static indicators of re‑identification risk (e.g., grouping by high‑cardinality quasi‑identifiers). Evidence: Sections III.A and III.C detail the AST parsing and feature set. Break condition: Failure to correctly parse advanced SQL constructs (e.g., CTEs, window functions) yields incomplete features and degrades risk assessment.

**2. Semantic intent capture with CodeBERT.** The entire SQL string is encoded using CodeBERT, a transformer pretrained on code, producing a dense embedding that captures semantic relationships (e.g., recognizing that `GROUP BY patient_zip_code` and `GROUP BY postal_code` impose similar privacy risks despite different column names). This allows the model to generalize beyond exact keyword matches. Evidence: Abstract and Section III.B describe CodeBERT’s role in embedding query logic. Break condition: Queries using highly domain‑specific functions, abbreviations, or nested logic outside CodeBERT’s training distribution may be mis‑embedded, leading to incorrect scores.

**3. Supervised fusion and thresholding.** The syntactic feature vector and CodeBERT embedding are concatenated and fed to an XGBoost classifier trained on historically labeled SQL queries (safe vs. risky). The model learns nonlinear interactions between structural and semantic patterns to predict a risk probability. A configurable threshold (e.g., 0.85) determines blocking; blocked queries trigger an explanation engine that uses rule‑based analysis of the AST to produce human‑readable justifications. Evidence: Abstract and Section III.D; validation on synthetic data (Section V) shows score differentiation aligned with expert intuition. Break conditions: Biased or non‑representative training data, or a static threshold not calibrated to a new institution’s risk tolerance, cause systematic over‑/under‑blocking.

## Foundational Learning
**SQL Abstract Syntax Trees (ASTs).** The AST provides a programmatic, hierarchical representation of a SQL query, essential for extracting structural risk features. *Why needed:* All downstream analysis depends on a correct parse. *Quick check:* For `SELECT dept, AVG(salary) FROM employees WHERE hire_date > '2020-01-01' GROUP BY dept`, what are the immediate child nodes of the root SELECT statement in its AST?

**Transformer‑based Code Embeddings (CodeBERT).** CodeBERT encodes a code snippet into a fixed‑dimensional vector where semantically similar queries (e.g., grouping by zip vs. postal code) lie close in vector space. *Why needed:* It captures the functional intent of a metric, generalizing beyond exact column names. *Quick check:* Why might two syntactically different SQL queries that both calculate an average by a sensitive attribute receive similar CodeBERT embeddings?

**Supervised Risk Thresholding & Explainability Trade‑offs.** The classifier outputs a probability that must be thresholded into a binary decision; this trade‑off between false positives and false negatives is policy‑driven. *Why needed:* Understanding this trade‑off is crucial for tuning the system to an institution’s risk appetite. *Quick check:* If the threshold is lowered from 0.85 to 0.75, what happens to precision and recall, and how does the explanation engine aid a data steward considering an override?

## Architecture Onboarding
**Component map:** Input (SQL query) → SQL Parser (sqlglot) → Feature Extractor (Syntactic Features & CodeBERT Embedding) → Feature Fusion → XGBoost Classifier → Decision Engine → [If blocked] → Explanation Engine → Output (status, risk_score, explanation)

**Critical path:** SQL Query → Parser → [Syntactic Features + CodeBERT Embedding] → Fusion → XGBoost Prediction → Threshold Check → (If blocked) → Explanation Generation → Final Output

**Design tradeoffs:** 
- *Static vs. Dynamic Analysis:* Pre‑execution analysis sacrifices potential accuracy from actual data distributions for speed and safety.
- *Model Complexity vs. Interpretability:* The XGBoost+CodeBERT combo offers nuanced scoring but is less inherently interpretable; a separate rule‑based explanation engine restores auditability.
- *Generalization vs. Domain Specificity:* CodeBERT handles diverse SQL syntax, but the sensitive column list and training data are specific to healthcare.

**Failure signatures:**
- **False negative:** A query grouping by a novel quasi‑identifier (e.g., `job_title, shift`) receives a low score because the pattern was absent in training and syntax alone is insufficient.
- **False positive:** A legitimate high‑cardinality grouping (e.g., `research_study_id`) is blocked because the column name contains a substring that triggers a false sensitive‑column match.
- **Parser failure:** Complex queries with CTEs cause AST generation errors, leading to incomplete feature extraction and unpredictable scores.

**First 3 experiments:**
1. **Baseline Validation on Provided Synthetic Set:** Re‑run the three example queries (ZIP, gender+diagnosis, gender) to verify reproduction of reported scores (0.87, 0.93, 0.74).
2. **Sensitive Column Detection Stress Test:** Create queries using synonymous column names (`postal_zip`, `sex`, `icd10_code`) and non‑standard sensitive names (`patient_location`, `gender_identity`). Evaluate detection to probe reliance on exact keyword matching vs. CodeBERT semantic generalization.
3. **Threshold Sensitivity Analysis:** Generate a batch of queries with borderline scores (e.g., 0.80–0.90). Vary the threshold (0.80, 0.85, 0.90) and log status changes; manually review marginal cases to assess whether the model’s confidence aligns with expert judgment.

## Open Questions the Paper Calls Out
- **Dynamic sensitive attribute identification:** How can the system automatically recognize sensitive columns beyond fixed keyword lists to handle diverse schema naming conventions? (The paper notes its current reliance on a fixed keyword list fails on variations like “date_of_birth” or “postal_code”.)
- **Static estimation of group sizes:** Can pre‑execution analysis incorporate probabilistic estimates of subgroup cardinalities to better assess re‑identification risk without accessing data? (The paper acknowledges that actual group sizes are a key factor missing from its approach.)
- **Robust parsing of advanced SQL:** How can the parser and feature extractor be extended to handle CTEs, window functions, and deeply nested subqueries? (Current limitations may yield incomplete ASTs for such constructs.)
- **Cross‑institutional generalization:** What steps are needed to mitigate model bias and ensure the risk classifier generalizes across different healthcare systems with varying data policies and demographics? (The paper calls for broader calibration across multiple institutions.)

## Limitations
- **Training data opacity:** The size, distribution, and labeling criteria of the historical queries used to train XGBoost are not disclosed, hindering assessment of model bias and generalizability.
- **Implementation specifics missing:** Exact CodeBERT checkpoint, XGBoost hyperparameters, feature vector construction, and sqlglot version are unspecified, preventing exact reproduction.
- **Narrow evaluation:** Validation is limited to a small synthetic dataset; real‑world performance with complex queries and diverse schemas remains unproven.
