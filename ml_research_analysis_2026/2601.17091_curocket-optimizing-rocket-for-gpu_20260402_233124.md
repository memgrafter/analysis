# CUROCKET: Optimizing ROCKET for GPU
## Quick Facts
- **ArXiv ID:** 2601.17091
- **Source URL:** https://arxiv.org/abs/2601.17091
- **Reference count:** 9
- **Primary result:** CUROCKET delivers up to 19.3× raw speedup and 11× higher computational efficiency per watt versus an optimized CPU implementation, while preserving feature extraction accuracy.

## Executive Summary
CUROCKET accelerates the ROCKET time series feature extraction algorithm via a custom CUDA kernel. It overcomes the inefficiency of applying ROCKET’s randomly varying kernels—different lengths, dilations, and paddings—by mapping kernels and instances to the CUDA grid’s two dimensions and using thread blocks with internal loops and atomic updates in shared memory. On an NVIDIA RTX 3090, CUROCKET achieves a raw computation speedup of up to 19.3× over a highly optimized CPU baseline and improves computational efficiency per watt by 11×, while maintaining the accuracy required for classification. This enables scalable time series analysis on large datasets.

## Method Summary
CUROCKET restructures ROCKET’s nested loops (kernels × instances) to fit the CUDA execution model: kernels are mapped to the grid’s x‑dimension (capacity 2³¹‑1) and instances to the y‑dimension (max 65,535). When instance count exceeds the y‑limit, batching cycles through subsets while keeping all kernels resident in GPU memory to minimize transfers. Each thread block processes one kernel–instance pair; the number of dot‑product convolutions (positional outputs) is mapped to the block’s x‑dimension (≤1024 threads). Threads compute multiple dot products via an internal loop, and atomic operations in shared memory accumulate the two ROCKET features (PPV and MAX). The custom kernel embeds dilation and padding logic to avoid the high overhead of calling standard convolution libraries thousands of times. Kernels are generated once on the CPU and transferred to the GPU; time series batches are streamed through the kernel and post‑processed on the CPU before training a Ridge classifier.

## Key Results
- Raw computation speedup up to 19.3× compared to an optimized CPU implementation.
- Computational efficiency per watt 11× higher on NVIDIA RTX 3090 versus AMD EPYC 7443P.
- Feature extraction accuracy maintained; minor PPV differences due to GPU floating‑point rounding are acceptable.

## Why This Works (Mechanism)

### Mechanism 1: Grid‑Dimension Mapping
**Claim:** Mapping kernels to the CUDA grid’s x‑dimension and instances to the y‑dimension efficiently utilizes GPU hardware constraints.
**Mechanism:** The x‑dimension handles up to 2³¹‑1 elements, covering ROCKET’s typical 10,000 kernels; the y‑dimension (max 65,535) handles instances, with CPU‑side batching for excess instances. Keeping all kernels in GPU memory while cycling instances minimizes data transfer.
**Core assumption:** Kernel memory footprint is fixed and fits comfortably; instance memory is the variable batched.
**Evidence anchors:** Section 3.2: “The number of kernels is mapped to the x dimension… The number of instances ninstances is mapped to the y dimension… It is more efficient to always have all kernels on the GPU memory and then cycle through the instances.”
**Break condition:** If a single instance (with its intermediate data) plus all kernels exceed GPU memory, batching fails.

### Mechanism 2: Thread‑Block Internal Loop and Atomic Updates
**Claim:** Using thread blocks with an internal loop to compute multiple dot products per thread provides scalable parallelism for the innermost convolution loop.
**Mechanism:** The number of dot‑product positions per kernel–instance pair is mapped to the block’s x‑dimension (≤1024 threads). Each thread processes several dot products via an internal loop. The two features (PPV, MAX) are kept in shared block cache and updated atomically as threads produce partial results, reducing global memory traffic.
**Core assumption:** The number of dot products is large enough to keep threads busy but small enough that shared memory can hold the feature values.
**Evidence anchors:** Section 3.2: “Each thread inside the block performs the calculation of one dot product… Since there are only 1,024 threads per block, there is a loop within each thread… Both of which are stored in the block cache. These updates have to be atomic.”
**Break condition:** Extremely long series with small kernels/dilations could make the internal loop too long, causing underutilization or register pressure leading to spills.

### Mechanism 3: Custom CUDA Kernel vs. Standard Libraries
**Claim:** A custom CUDA kernel is necessary because standard GPU convolution libraries cannot efficiently handle ROCKET’s randomly varying kernel parameters.
**Mechanism:** Instead of calling a convolution library for each of the 10,000 kernels (high launch overhead, no support for variable dilation/padding), the custom kernel incorporates dilation and padding logic directly in the dot‑product loop, avoiding data restructuring and thousands of launches.
**Core assumption:** The overhead of thousands of library calls exceeds the complexity of a single reusable kernel that manually handles parameter variance.
**Evidence anchors:** Section 2.2 shows existing GPU implementations are slower; Section 3.2 describes handling padding and dilation within the kernel.
**Break condition:** If ROCKET were constrained to a small set of fixed kernel lengths (e.g., MiniRocket), a library‑based approach might become efficient.

### Concept 1: CUDA Execution Model (Grids, Blocks, Warps)
**Why needed:** The mapping of kernels/instances to grid dimensions and dot‑products to block dimensions directly relies on understanding CUDA’s hierarchical thread organization and hardware limits (e.g., 1024 threads per block, grid y‑dimension ≤ 65,535).
**Quick check:** Given 10,000 kernels and 100,000 instances on a GPU with grid size (2³¹‑1, 65,535), how would you map these dimensions and why?

### Concept 2: 1D Convolution with Dilation and Padding
**Why needed:** ROCKET’s core operation is a dot‑product convolution with random dilation and optional zero‑padding. Implementing the loop correctly without library support requires understanding how dilation expands the receptive field and how padding shifts the alignment.
**Quick check:** For a kernel of length 5, dilation 2, and no padding on a series of length 10, how many valid dot‑product positions exist? How does applying zero‑padding with probability 0.5 affect this count?

### Concept 3: Atomic Operations and Shared Memory in CUDA
**Why needed:** CUROCKET uses shared memory within a block and atomic updates to accumulate PPV and MAX across threads processing the same kernel–instance pair. This is a classic parallel reduction pattern critical for both performance and correctness.
**Quick check:** Why are atomic operations necessary when accumulating PPV and MAX in shared memory? What would happen if multiple threads tried to update the same shared memory location without atomics?

## Architecture Onboarding

### Component Map
Kernel Generator (CPU) -> Data Loader/Manager -> CUDA Kernel (`rocket_transform`) -> Feature Post‑Processor (CPU) -> Ridge Classifier Trainer (CPU)

### Critical Path
1. Generate random kernels on the CPU (lengths {7,9,11}, weights N(0,1), bias U[-1,1], dilation 2^r, padding with prob 0.5).
2. Transfer kernels to GPU memory (once).
3. For each batch of time‑series instances (sized to fit GPU memory & y‑dimension limit): transfer batch to GPU, launch CUDA kernel, copy resulting feature batch back.
4. Post‑process PPV (divide by number of dot‑product positions) on CPU; handle precision adjustments.
5. Concatenate features from all batches and train a Ridge classifier.

### Design Tradeoffs
- **Grid dimension assignment:** Kernels→x (large capacity), Instances→y (smaller capacity). Swapping would risk OOM if instances require more memory; batch size limited by y‑dimension (65,535).
- **Feature update strategy:** Atomic operations in shared memory reduce global writes but introduce serialization. For extremely small kernels, atomics could become a bottleneck; an alternative is per‑thread private accumulation followed by a parallel reduction.
- **Precision:** GPU uses float32; CPU may use float64. Rounding differences near zero cause marginal PPV shifts; trade‑off between speed and bit‑identical reproducibility.

### Failure Signatures
- **Memory overflow:** Launch failure with “invalid configuration argument.” Caused by batch size × kernel data exceeding GPU memory or block dimension >1024 threads.
- **Incorrect feature values:** Systematic PPV distribution shift vs. CPU implementation. Check normalization (division by correct dot‑product count) and verify dilation/padding logic matches CPU.
- **Poor scaling:** Speedup plateaus or degrades with larger problem sizes. Likely due to internal loop length suboptimal (underutilization) or excessive (register pressure/spilling). Use CUDA profiler to check occupancy and cache hit rates.

### First 3 Experiments
1. **Correctness validation:** Run CUROCKET and a reference CPU ROCKET (e.g., sktime) on a small deterministic dataset (10 instances, series length 50, 100 kernels). Compare all features (MAX, PPV) element‑wise; accept small floating‑point differences, investigate large mismatches.
2. **Parameter sweep:** Measure end‑to‑end feature generation time while varying one parameter (instances, series length, kernels). Validate linear scaling and asymptotic speedup (target ~19.3×). Watch for non‑linearities indicating resource limits.
3. **Multi‑GPU scaling:** Split instances evenly across 2 GPUs (separate processes). Measure total time vs. single GPU, including data transfer and result merge overhead. Expect near‑linear speedup if instances dominate memory usage.

## Open Questions the Paper Calls Out
1. **MultiRocket extension:** Can CUROCKET’s architecture be efficiently extended to MultiRocket, which adds time‑dependent features that depend on the full convolution result? The paper suggests extensive alterations are needed but provides no implementation or evaluation.
2. **Impact of PPV rounding:** Does the floating‑point rounding discrepancy in PPV between GPU and CPU lead to measurable differences in classification accuracy on large‑scale or diverse datasets? The paper acknowledges marginal differences but offers no empirical validation.
3. **Multi‑GPU partition strategy:** How does instance‑splitting compare to kernel‑splitting for multi‑GPU scaling? The paper proposes instance splitting because instances likely require more memory, but no experiments or analysis of alternative partitions are conducted.
4. **Power measurement accuracy:** Would accurate, dynamic power measurements change the magnitude of the reported 11× efficiency‑per‑watt advantage? The paper uses nominal TDP values, admitting that exact measurement is not possible without further modifications.

## Limitations
- **CPU baseline ambiguity:** The optimized CPU implementation is not clearly identified (the paper references sklearn, which lacks ROCKET), making the speedup comparison potentially non‑apples‑to‑apples.
- **Kernel generation parity:** Minor differences in random kernel sampling (length distribution, dilation formula, padding logic) could alter performance and extracted features, hindering faithful reproduction.
- **Hardware/software specificity:** Results are tied to NVIDIA RTX 3090, AMD EPYC 7443P, specific CUDA/CuPy versions, and nominal power estimates; generalizability to other platforms is uncertain.
- **Repository limitations:** The CUROCKET GitHub repository may not support passing precomputed kernels, forcing regeneration and possible kernel mismatches between CPU/GPU runs.

## Confidence
- **Grid‑dimension mapping strategy:** Medium (fits hardware limits but requires code inspection to confirm batching logic for >65,535 instances).
- **Thread‑block internal loops and atomic updates:** Medium (theoretically sound; actual occupancy, bank conflicts, and register pressure must be measured).
- **Custom kernel necessity over standard libraries:** Medium (launch overhead likely high, but alternative grouped/templated library approaches could reduce the gap; not evaluated).
- **Raw speedup (up to 19.3×) and efficiency per watt (11×):** Low (depends on undefined CPU baseline and specific hardware; reproduction plan reveals ambiguities that could alter the factor).
- **Maintained accuracy:** Medium‑High (minor PPV shifts are expected and acceptable; systematic bias from algorithmic mismatch is unlikely but not exhaustively validated).
