# VIGIL: Towards Edge-Extended Agentic AI for Enterprise IT Support

## Quick Facts
- **arXiv ID:** 2603.16110
- **Source URL:** https://arxiv.org/abs/2603.16110
- **Reference Count:** 40
- **Primary Result:** An edge-extended agentic AI system reduced IT support interaction rounds by 39%, achieved at least 4× faster diagnosis (median 36.5 seconds), and enabled self-service resolution in 82% of matched cases in a 100-endpoint pilot, with excellent user usability (SUS 86.2).

## Executive Summary
Enterprise IT support struggles with device heterogeneity and long-tail failures that are difficult to resolve through centralized, human-led processes. VIGIL proposes an edge-extended agentic AI system that deploys on-device agents to perform situated diagnosis, retrieval from enterprise knowledge bases, and policy-governed remediation. A 10-week pilot across 100 resource-constrained endpoints demonstrated significant reductions in interaction rounds and diagnosis latency compared to traditional support, while high user trust and low cognitive workload confirmed the value of local, autonomous reasoning beyond static knowledge lookup.

## Method Summary
VIGIL operates via a closed-loop agentic workflow: Diagnose (collect local evidence via Model Context Protocol tools), Retrieve (perform RAG over enterprise knowledge and historical cases), and Remediate (execute actions under policy enforcement). The system comprises specialized agents—Planner, Diagnosis, Knowledge, and Remediation—orchestrated through an A2A protocol. All state-changing actions are mediated by an Open Policy Agent (OPA) engine, classifying them as allow, warn (requiring user consent), or deny. The pilot used AWS Bedrock (Claude Opus 4.1) for LLM inference and evaluated performance through automated quality assessment (LLM-as-judge) and user experience surveys (SUS, NASA-TLX, Trust).

## Key Results
- Reduced median interaction rounds from 18 (human support) to 11 (39% reduction).
- Achieved median diagnosis time of 36.5 seconds, at least 4× faster than the ≥2.7 minute baseline.
- Enabled self-service resolution in 82% of matched cases (high/medium confidence).
- Attained a System Usability Scale score of 86.2 (industry average 68), high trust (4.29/5), and low cognitive workload (NASA-TLX 2.53/7).

## Why This Works (Mechanism)

### Mechanism 1: On-Device Situated Diagnosis
**Claim:** Executing the diagnose-retrieve-remediate workflow locally on the endpoint reduces interaction rounds and latency by colocating reasoning with the failure environment.
**Mechanism:** Local diagnostic tools (via MCP) access fine-grained context (e.g., live process lists, disk usage) unavailable to centralized systems, eliminating communication delays and enabling autonomous resolution loops.
**Evidence:** Pilot showed 4× faster diagnosis (median 36.5s) and fewer back-and-forth exchanges (11 vs 18 cycles). Section 3 notes that local execution enables lower-latency remediation and access to fine-grained context.

### Mechanism 2: Deterministic Policy Enforcement
**Claim:** A policy layer (OPA) that classifies all actions as allow/warn/deny enables safe, governed autonomy, building user trust and ensuring compliance.
**Mechanism:** Before any state change, the Remediation Agent submits the action to OPA. The deterministic, rule-based evaluation provides auditable, reversible control; "warn" tier actions require explicit user consent, balancing automation with oversight.
**Evidence:** Section 4 describes the three-tier system. Appendix 8.4 provides policy examples. Section 6.2 qualitative feedback confirms users valued transparency and trust from this mechanism.

### Mechanism 3: Structured Experience Signals for Self-Improvement
**Claim:** Traces of tool calls, reasoning steps, and outcomes can refine retrieval, prompts, and memory without model retraining, creating a foundation for continuous improvement.
**Mechanism:** Each interaction produces a structured log. These signals are designed to be analyzed to adjust contextual scaffolding (e.g., retrieval queries, prompt templates), progressively improving performance on similar failure modes.
**Evidence:** Section 3.2 and the introduction mention this loop as a core design goal, though it was not activated during the pilot. The companion paper "VIGIL: A Reflective Runtime for Self-Healing Agents" discusses related introspection.

## Architecture Onboarding
- **Component map:**
  Planner Agent -> Diagnosis Agent (MCP tools) -> Knowledge Agent (local memory + remote KB/CGR) -> Planner synthesizes -> Remediation Agent -> Policy Engine (OPA) -> (If warn) User consent -> Execution -> Verification -> Repeat/Complete/Escalate.
- **Critical path:** User issue initiates Planner; Diagnosis gathers local evidence; Knowledge retrieves context; Planner formulates plan; Remediation proposes action; OPA evaluates; user consent if needed; action executes; system verifies outcome and iterates or resolves.
- **Design tradeoffs:**
  - *Local autonomy vs. global consistency:* Local diagnosis is fast and context-rich but misses fleet-wide patterns; cloud coordination is needed for policy updates and cross-device learning.
  - *Scope of actuation:* Pilot used bounded, reversible commands; expanding scope (e.g., software installs) increases utility but also policy complexity and risk.
  - *Model choice vs. cost/latency:* Using a powerful model (Claude Opus 4.1) improves reasoning but increases inference cost and may affect on-device performance.
- **Failure signatures:**
  - High MCP tool failure rate (>5%) indicates integration or system instability.
  - High "deny" proportion suggests overly restrictive policies or action space mismatch.
  - Low LLM judge scores (<7/10) on root cause accuracy or actionability indicate diagnostic or retrieval gaps.
  - Frequent user overrides/ignorance of "warn" actions or post-resolution escalations signal misaligned remediation plans.
- **First 3 experiments:**
  1. **Tool Integration Test:** Verify all MCP diagnostic tools execute successfully on a representative endpoint, capture outputs in a structured profile, and measure execution latency.
  2. **Policy Compliance Test:** Validate OPA classifies a known-safe command (e.g., restart service) as "allow" and a known-dangerous command (e.g., format drive) as "deny." Test a borderline command to confirm "warn" flow and simulated user consent.
  3. **Retrieval & Quality Evaluation Test:** Use the provided evaluation prompt (LLM-as-judge) on 20–50 historical or simulated VIGIL traces to establish a baseline for response quality dimensions and identify the weakest link (e.g., root cause accuracy).

## Open Questions the Paper Calls Out
- **How can VIGIL's self-improvement mechanisms be safely activated and evaluated in a live enterprise environment without compromising stability or security?** The operational loop was evaluated, but the self-improvement loop (context refinement, prompt optimization) was not activated; its impact on policy evolution, memory updates, and long-term reliability is unknown.
- **To what extent does VIGIL's performance generalize across heterogeneous enterprise fleets?** The pilot was limited to 100 HP G8 Windows devices; performance on other OSes (macOS, Linux), hardware, or proprietary software stacks remains unvalidated.
- **How reliable is automated LLM-based evaluation compared to human expert judgment for IT support tasks?** Response quality was assessed via an LLM judge; potential biases and discrepancy with expert evaluation pose a threat to validity.
- **How does VIGIL handle the evolution of enterprise IT policies and knowledge bases over time?** Policies and knowledge sources were static in the pilot; without update mechanisms, VIGIL risks applying outdated rules or obsolete information as organizational requirements change.
- **What is the computational overhead of on-device agents on resource-constrained endpoints?** Pilot endpoints were described as resource-constrained, but no resource utilization metrics (CPU, memory, battery) were reported, leaving scalability and user experience impact unmeasured.

## Limitations
- **Agent implementation details** (inter-agent protocols, prompt engineering, memory management) are underspecified, hindering precise replication.
- **Knowledge retrieval pipeline specifics** (embedding model, chunking, verification step) are unclear, making independent reproduction of the RAG component difficult.
- **Policy scope and maintenance burden** for a broad enterprise action space is unknown; the pilot likely used a restricted command subset.
- **Evaluative rigor** is limited by lack of transparency in the LLM-as-judge setup (model, prompts, calibration) and user survey administration.
- **Scalability and long-term value** are unaddressed by the 10-week, 100-endpoint pilot; fleet-wide behavior, policy evolution, and the unactivated learning loop's impact remain open.

## Confidence
- **Pilot Performance Metrics (39% rounds reduction, 4× faster diagnosis, 82% self-service):** High (direct outcomes from controlled real-world deployment).
- **Mechanism 1 (Value of On-Device Situated Diagnosis):** Medium (strong pilot evidence, but bounded by toolset/issue types; break conditions acknowledged).
- **Mechanism 2 (Policy-Governed Autonomy for Trust/Safety):** Medium (qualitative feedback supports it, but confidence limited by unspecified policy coverage and pilot's bounded command scope).
- **Mechanism 3 (Self-Improvement via Trace Analysis):** Low (explicitly not activated during pilot; feasibility and impact remain theoretical future work).
