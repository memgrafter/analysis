# SAGE: Structure Aware Graph Expansion for Retrieval of Heterogeneous Data

## Quick Facts
- arXiv ID: 2602.16964
- Source URL: https://arxiv.org/abs/2602.16964
- Reference count: 40
- Primary result: Improves retrieval recall by 5.7 (OTT-QA) and 8.5 (STaRK) points at fixed budgets; SPARK matches fine-tuned methods with a single LLM call.

## Executive Summary
SAGE addresses the limitation of flat retrieval in retrieval-augmented QA over heterogeneous data (text, tables, graphs) by constructing a sparse, chunk-level graph offline using metadata-driven similarity with percentile-based pruning. At query time, it retrieves seed chunks with a baseline retriever, expands to first-hop neighbors, and re-ranks them via dense+sparse signals to select additional context. For explicit schema graphs, SPARK—an agentic retriever—generates Cypher queries for constrained traversal. Evaluations on OTT-QA and STaRK show consistent recall gains, while SPARK achieves efficiency by avoiding iterative loops and set-join operations.

## Method Summary
**Offline graph construction:** Documents and tables are semantically chunked using overlapping windows; chunk boundaries are placed where local coherence drops below the 20th percentile. Table chunks contain 5–10 rows. An LLM extracts metadata (topic, title, entities, column descriptions) from each chunk. Edges are created between chunks (same or different modalities) by computing cosine similarity on these metadata embeddings; only edges exceeding the 95th percentile of the similarity distribution are retained (OR logic), preserving sparsity. Parent/structural links and explicit schema edges (if available) are also kept.  
**Online retrieval:** Given a query, a baseline retriever (hybrid BM25+dense for implicit corpora; SPARK for explicit KGs) returns top-*k* seed chunks. All first-hop neighbors of these seeds are fetched from the stored graph. The neighbor set is re-ranked using the same hybrid signals, and the top-*k*′ are added to the seeds to form the final context of size *k*+*k*′. For SPARK, a single Cypher query combining semantic (HNSW) and structural constraints is generated; if it returns no results, a fallback to BM25+dense ensures robustness.

## Key Results
- SAGE improves Recall@20 by 5.7 points on OTT-QA and 8.5 points on STaRK over strong baselines at fixed context budgets.
- SPARK with selective expansion matches fine-tuned retrieval methods on STaRK while requiring only one LLM call and no set-join operations.
- Ablation studies show the 95th percentile pruning threshold with OR logic yields the best recall–density trade‑off; stricter thresholds fragment connectivity while looser ones increase noise.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Offline metadata-driven graph construction produces a sparse, semantically coherent chunk-level graph that effectively connects heterogeneous data.
- **Mechanism:** Semantic chunking places boundaries where local coherence is low; LLM extracts metadata (topic, entities, column descriptions). Edges are formed between chunks by computing cosine similarity on metadata embeddings; only edges above the 95th percentile are kept (OR logic), maintaining sparsity. Parent/structural links and explicit schema edges are also included.
- **Core assumption:** High-level metadata embeddings reliably encode meaningful cross‑modal relationships, and a single high percentile threshold separates true links from noise.
- **Evidence anchors:** 
  - [abstract] “constructs a chunk-level graph offline using metadata-driven similarities with percentile‑based pruning.”
  - [section 2.1] “We only keep a similarity edge when its metadata similarity exceeds the 95th percentile of the empirical distribution, which maintains sparsity and reduces dense‑neighborhood noise.”
- **Break condition:** Low‑quality metadata (LLM extraction errors) or indistinct similarity distributions cause over‑sparsification (fragmented graph) or over‑connectivity (noisy neighborhoods), directly harming expansion recall.

### Mechanism 2
- **Claim:** The seed→expand→rerank pipeline uncovers relevant evidence missed by flat similarity search by leveraging one‑hop graph connectivity.
- **Mechanism:** A baseline retriever (hybrid BM25+dense or SPARK) returns top‑*k* seeds. All first‑hop neighbors of these seeds are fetched, creating a candidate set. These candidates are re‑ranked with the same hybrid signals; the top‑*k*′ are added to the seeds to form the final context.
- **Core assumption:** Relevant evidence for multi‑hop questions often lies one edge away from a relevant node; the offline graph reliably encodes such connections, and hybrid re‑ranking filters noise.
- **Evidence anchors:** 
  - [abstract] “online retrieval by running an initial baseline retriever to obtain *k* seed chunks, expanding to first‑hop neighbors in the graph, and then filtering the neighbors using dense+sparse retrieval, selecting *k*′ additional chunks.”
  - [section 2.2] “Neighbor Expansion: collect all first‑hop neighbors of the *k* seeds… Neighbor Pruning: re‑rank the *n* candidates using BM25 and dense embedding similarity… Final Context: return the union of the original *k* seeds and the *k*′ neighbors.”
  - [section 3.1] Figure 4 shows Recall@k gains from graph expansion on OTT‑QA, especially at small *k*.
- **Break condition:** Poor seed recall (missing all relevant nodes) cannot be recovered by one‑hop expansion; overly dense neighbor sets (from low pruning thresholds) introduce noise the re‑ranker cannot filter; benefits diminish when node content is too sparse.

### Mechanism 3
- **Claim:** SPARK, an LLM‑based agentic retriever for explicit schema graphs, achieves precise, constraint‑aware retrieval with a single LLM call, avoiding iterative loops and symbolic set‑join overhead.
- **Mechanism:** Given a query and KG schema, an LLM generates a single Cypher query combining semantic constraints (via HNSW candidate generation) and structural constraints (typed nodes/relations). The query is executed in Neo4j; if empty, a fallback to BM25+dense ensures robustness.
- **Core assumption:** The LLM can reliably translate natural language into correct Cypher respecting the schema, and a single‑pass symbolic traversal retrieves all relevant nodes without iteration.
- **Evidence anchors:** 
  - [abstract] “SPARK (Structure Aware Planning Agent for Retrieval over Knowledge Graphs) an agentic retriever for explicit schema graphs.”
  - [section 2.2.A.2] “We introduce SPARK, an LLM‑based agent for SKB retrieval… generates a multi‑step plan that alternates between: (1) Semantic Candidate Generation: retrieving nodes via Hierarchical Navigable Small World (HNSW) search… (2) Structural Expansion: traversing edges with Cypher queries, constrained by entity types and relations.”
  - [section 3.2] Table 4 shows SPARK uses exactly one LLM call and no set‑join operations; Table 2 shows SPARK + SAGE‑Edge matches fine‑tuned methods on STaRK.
- **Break condition:** Invalid Cypher (syntax errors, wrong node/edge types) causes failure or irrelevant results; complex queries requiring multi‑step reasoning may exceed planning capability, causing fallback over‑reliance; sparse node textual content weakens semantic candidate generation.

## Foundational Learning
- **Heterogeneous Chunk‑Level Graph**: Unifies text, tables, and semi‑structured objects into a single graph so cross‑modal evidence chains can be traversed. *Why needed*: Enables graph-based expansion beyond flat similarity. *Quick check*: How are document chunks created, what metadata is extracted for tables, and how are edges between different modalities established?
- **Metadata‑Driven Similarity & Percentile Pruning**: Edges are defined by multiple metadata signals (topic, content, entities, columns) and a universal high percentile threshold to keep the graph sparse yet connected. *Why needed*: Balances graph connectivity and noise across heterogeneous data. *Quick check*: Why use the 95th percentile, and how would lowering or raising the threshold affect graph density and retrieval performance?
- **Hybrid Dense‑Sparse Retrieval**: Combines BM25 (lexical) and dense embeddings (semantic) for both baseline retrieval and neighbor re‑ranking. *Why needed*: Matches both exact keywords and conceptual similarity across heterogeneous chunks. *Quick check*: What are the strengths of BM25 and dense embeddings, and why combine them instead of choosing one?
- **Schema‑Aware Cypher Querying (SPARK)**: Generates Cypher queries that incorporate node labels and relationship types for precise KG traversal. *Why needed*: Ensures structural validity and constraint awareness in schema‑rich graphs. *Quick check*: How does SPARK incorporate entity types and relationships into a single Cypher query, and what fallback mechanism is used?

## Architecture Onboarding
Offline Graph Builder -> Baseline Retriever -> Graph Expansion Module -> Hybrid Reranker -> Context Formatter.  
Critical path: Query → Baseline Retriever (top‑*k* seeds) → Graph Expansion (fetch all 1‑hop neighbors) → Hybrid Reranker (score & select top‑*k*′) → Union(seeds, *k*′) → Final context.  
Design tradeoffs: 
- *Pruning percentile*: 95th percentile empirically optimal; higher thresholds over‑sparsify, lower thresholds increase noise and re‑ranking cost.
- *Initial retriever strength*: Strong seeds (e.g., SPARK) amplify expansion gains; weak seeds limit benefits.
- *Agentic vs. non‑agentic*: SPARK provides schema‑awareness but incurs LLM cost; hybrid retrieval is cheaper but less precise on dense KGs.
- *Modality coverage*: Edge definitions are modality‑specific (e.g., column similarity for tables); incomplete metadata weakens certain edge types.  
Failure signatures:
- Low recall after expansion: seeds recall poor, graph too sparse, or neighbors miss relevant evidence.
- High latency: graph degree high (low pruning), large neighbor sets, expensive re‑ranking.
- SPARK failures: Cypher syntax errors, frequent empty results (fallback triggers), incorrect node/edge types.
- Graph construction errors: LLM metadata mistakes, incorrect percentile pruning, mishandled parent links.  
First 3 experiments:
1. **OTT‑QA Recall@k** (Fig 4): Compares flat hybrid retrieval vs. hybrid + graph expansion; shows consistent gains (up to +5.7 at *k*=20), proving expansion retrieves additional relevant chunks.
2. **STaRK Recall@20** (Table 2): Reports SPARK + SAGE‑Edge against dense, sparse, hybrid, agentic, and fine‑tuned baselines; SPARK + SAGE‑Edge matches/exceeds fine‑tuned methods without training.
3. **Pruning Ablation** (Table 5): Varies percentile threshold and edge logic (OR vs. AND); demonstrates 95th percentile with OR logic best balances recall and density; stricter thresholds fragment connectivity, looser increase noise.

## Open Questions the Paper Calls Out
- What is the optimal strategy for setting the similarity pruning percentile (currently fixed at 95th) during offline graph construction, and can this threshold be adapted dynamically based on corpus-specific characteristics (e.g., modality distribution, node density) to further balance connectivity and noise? The paper selects 95th after sensitivity analysis but does not explore generalizability or adaptive rules.
- How can the accuracy of SPARK's Cypher query generation be improved to reduce the dominant constraint extraction errors (30–36% of failures on STaRK) without requiring extensive task-specific fine-tuning or iterative LLM refinement? The paper suggests future instruction tuning but leaves open robust, low‑overhead solutions.
- To what extent can the reliance on LLMs for metadata extraction and agent planning be reduced or replaced with more efficient, specialized models (e.g., smaller fine‑tuned encoders, rule‑based systems) without degrading graph construction quality or retrieval performance? The paper acknowledges LLM latency/cost but provides no empirical comparison.
- How can SAGE's graph construction and retrieval operators be effectively extended to multimodal corpora (e.g., images, audio) where similarity signals are less aligned and node granularity differs? Future work mentions cross‑modal links, but no design or evaluation exists.
- Why does hybrid sparse‑dense retrieval perform poorly on STaRK's explicit schema graphs compared to agentic SPARK, and can the graph expansion mechanism compensate for weaker seed retrievers in schema‑rich settings? The interaction between seed quality and expansion benefits is not theoretically analyzed.

## Limitations
- Exact split between seed size *k* and expansion budget *k*′ is unspecified; implementations must assume a ratio.
- Metadata fusion method for edge creation (how multiple similarity signals are combined before percentile pruning) is unclear; assumptions may affect graph quality.
- SPARK’s prompt template and parsing logic beyond provided examples are not detailed, hindering faithful reproduction.
- Neighbor expansion may be unbounded if seeds are numerous, risking latency; no sampling or per‑seed limit is described.
- Hybrid retrieval score normalization (scaling BM25 and cosine to comparable ranges) is not specified, affecting re‑ranking fairness.

## Confidence
- Offline graph construction (percentile pruning, metadata similarity): **Medium**. Ablation shows 95th percentile OR works, but sensitivity to metadata quality and fusion is unexplored.
- Seed‑expand‑rerank pipeline: **High**. Consistent gains across datasets with clear steps; failure modes predictable and mitigated.
- SPARK agentic retrieval (single‑call Cypher generation): **Medium**. Efficiency demonstrated, but LLM brittleness for complex constraints is a concern; generalizability across schemas unproven.

## Next Checks
- **Graph construction sensitivity:** Vary percentile thresholds (80–99) and edge logic (OR/AND) across both datasets; measure graph density, connectivity, and final recall to bound robustness.
- **SPARK robustness across LLMs and prompts:** Run SPARK with multiple LLM backbones and prompt variants; record Cypher validity, empty‑result rate, and recall to identify failure modes and generalization.
- **Seed‑retriever dependency:** Fix expansion and graph; vary seed retriever type (BM25, dense, hybrid) and seed size *k*. Plot seed recall vs. expansion gain to find minimum seed quality for net benefit.
