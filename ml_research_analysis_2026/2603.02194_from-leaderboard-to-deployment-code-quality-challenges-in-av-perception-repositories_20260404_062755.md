# From Leaderboard to Deployment: Code Quality Challenges in AV Perception Repositories

## Quick Facts
- **arXiv ID:** 2603.02194
- **Source URL:** https://arxiv.org/abs/2603.02194
- **Reference count:** 19
- **Primary result:** Only 7.3% of 178 analyzed AV perception repositories from KITTI/NuScenes leaderboards meet minimal production-readiness criteria (zero critical errors, no high-severity vulnerabilities), with leaderboard performance showing no correlation with code quality.

## Executive Summary
This study investigates the gap between high benchmark performance and production readiness in autonomous vehicle perception research. Analyzing 178 public repositories from the KITTI and NuScenes 3D object detection leaderboards, it finds that an overwhelming majority (97.2%) contain critical errors or high-severity security vulnerabilities. Security issues are highly concentrated, with five types accounting for nearly 80% of occurrences. While CI/CD pipeline adoption is very low (7.3%), it correlates with significantly higher code maintainability. The findings reveal that leaderboard rankings are unrelated to code quality, highlighting a significant research-to-deployment barrier in safety-critical AI systems.

## Method Summary
The authors collected 178 Python repositories linked from KITTI and NuScenes leaderboards, applying strict filtering to exclude non-code or inaccessible repositories. Each repository was cloned and processed with a standardized static analysis pipeline: Pylint for code errors, Bandit for security vulnerabilities, and Radon for maintainability index (MI) and lines of code. GitHub API data was gathered for repository metrics (stars, forks, CI/CD usage). Statistical analyses included Spearman correlations for metric relationships and Mann-Whitney U tests for group comparisons (e.g., CI/CD adopters vs. non-adopters). Security issue concentration was quantified via Pareto analysis.

## Key Results
- Only 13 of 178 repositories (7.3%) met the binary definition of production-readiness (zero critical Pylint errors, zero high-severity Bandit issues).
- Five Bandit issue types (e.g., unsafe PyTorch loading, shell injection) accounted for 79.3% of all security vulnerability occurrences.
- CI/CD pipeline adoption correlated with a statistically significant increase in maintainability index (mean MI 73.0 vs. 65.9, p=0.0003), a pattern consistent across team sizes.
- No statistically significant correlation was found between leaderboard ranking and any code quality metric (errors, vulnerabilities, maintainability).

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** High leaderboard performance in AV perception does not correlate with production readiness, creating a research-to-deployment gap.
- **Mechanism:** Research code is optimized for benchmark metrics (e.g., mAP) but lacks systematic quality assurance (e.g., static analysis, CI/CD), leading to repositories with critical errors and security vulnerabilities that would be unacceptable in safety-critical deployment contexts.
- **Core assumption:** Production readiness requires criteria beyond functional accuracy, such as absence of critical errors and high-severity vulnerabilities, as mandated by standards like ISO 26262.
- **Evidence anchors:** "leaderboard ranking showed no correlation with code quality metrics."; "Only 7.3% of the repositories qualify as production-ready... 97.2% of the repositories exhibited at least one [critical] error."
- **Break condition:** If future studies find a significant correlation between leaderboard rank and reduced error/vulnerability density across multiple leaderboards and domains.

### Mechanism 2
- **Claim:** Security vulnerabilities in AV perception code are highly concentrated, with a small set of issue types responsible for the majority of occurrences.
- **Mechanism:** Common but unsafe coding patterns (e.g., `torch.load()` without `weights_only=True`, bare `except` blocks, shell injection via `subprocess`) are repeatedly used, likely due to researchers' lack of security training and focus on functionality over security.
- **Core assumption:** Addressing these top patterns would disproportionately improve security posture, as per the Pareto principle applied to vulnerability remediation.
- **Evidence anchors:** "Security vulnerabilities were highly concentrated, with five issue types accounting for 79.3% of occurrences."; B614 (unsafe PyTorch load) affected 80.9% of repositories; top 5 issues cumulatively account for 79.3% of all occurrences.
- **Break condition:** If targeted education on these top issues does not reduce their prevalence in a follow-up study of new AV perception repositories.

### Mechanism 3
- **Claim:** Adoption of CI/CD pipelines correlates with higher code maintainability, independent of team size.
- **Mechanism:** CI/CD enforces automated quality gates (e.g., running linters, tests on commit), which encourages incremental code quality improvements and prevents technical debt accumulation, leading to higher maintainability index scores.
- **Core assumption:** Maintainability index (Radon MI) is a valid proxy for long-term code health and ease of modification in research codebases.
- **Evidence anchors:** "CI/CD pipeline adoption... correlated with significantly higher code maintainability."; Repositories with CI/CD had significantly higher mean MI (73.0 vs 65.9, p=0.0003); analysis across team sizes showed consistently higher MI for CI/CD adopters.
- **Break condition:** If a controlled experiment introducing CI/CD to matched pairs of repositories fails to show a causal improvement in maintainability metrics over time.

## Foundational Learning
- **Concept: Safety-Critical Software Standards (ISO 26262, ISO 21448/SOTIF)**
  - **Why needed here:** The paper's definition of "production-readiness" is explicitly grounded in compliance with these automotive safety standards, which demand rigorous development processes, static analysis, and traceability—far beyond typical research code practices.
  - **Quick check:** How do the requirements of ISO 26262 (for functional safety of hardware/software failures) and ISO 21448 (for safety of intended functionality, e.g., perception limitations) differ, and why does this paper's focus on code-level errors/vulnerabilities relate more directly to one of them?

- **Concept: Static Analysis for Code Quality and Security**
  - **Why needed here:** The entire empirical analysis relies on static analysis tools (Pylint, Bandit, Radon) to quantify errors, vulnerabilities, and maintainability. Understanding what these tools detect (and their limitations) is crucial to interpreting the results.
  - **Quick check:** What is the key difference between what Pylint (code errors/linting) and Bandit (security vulnerabilities) are designed to find? Give one example of an issue each tool would catch that the other might miss.

- **Concept: Maintainability Index (MI) and Technical Debt**
  - **Why needed here:** MI is the primary metric used to assess long-term code health. It combines cyclomatic complexity, lines of code, and Halstead volume into a single score. High MI correlates with lower error/vulnerability density in this study, indicating that maintainable code is also more robust and secure.
  - **Quick check:** According to the established thresholds cited (Coleman et al.), what MI score range is considered "moderately maintainable," and what does a score below 65 imply about a codebase?

## Architecture Onboarding
- **Component map:** Leaderboard Scraping -> Repository Filtering & Cloning -> Static Analysis (Pylint/Bandit/Radon) -> GitHub Metrics Collection -> Statistical Analysis (Correlation/Group Tests) -> Security Concentration Analysis -> Guideline Synthesis.
- **Critical path:** The filtering step (removing non-Python, readme-only, inaccessible repos) is most critical; an error here skews the dataset. Tool execution must be consistent (same versions/configs) for comparability.
- **Design tradeoffs:**
  - **Tool Selection:** Chose popular Python tools (Pylint/Bandit/Radon) matching the dataset's language. Tradeoff: may miss issues detectable by other linters (Flake8) or deeper analyzers (CodeQL). Assumption: Chosen tools provide a sufficient, representative baseline.
  - **Production-Readiness Definition:** Defined narrowly as "zero critical errors + no high-sev vulnerabilities." Tradeoff: Ignores testing, documentation, architecture. Assumption: Meeting this minimal bar is a necessary, though not sufficient, condition for deployment.
  - **Correlational Analysis:** Used Spearman/Mann-Whitney on observational data. Tradeoff: Cannot prove causality (e.g., CI/CD causes better MI). Assumption: Observed correlations are strong enough (p<0.001) to warrant causal investigation.
- **Failure signatures:**
  1.  **High Repository Exclusion Rate:** ~60% of leaderboard models lacked public repos. A failure to replicate this high exclusion rate might indicate a shift toward more open research.
  2.  **Low CI/CD Adoption:** Only 7.3% adoption. If a replication finds significantly higher adoption, it could indicate changing norms.
  3.  **Security Issue Concentration Shift:** If a new study finds a different set of top 5 issues, it would challenge the generalizability of the proposed guidelines.
  4.  **No Correlation Reproduction:** Failure to find the reported strong negative correlation (ρ=-0.547) between security issue density and MI would question the link between security and maintainability.
- **First 3 experiments:**
  1.  Replicate the full pipeline on newer models from KITTI/NuScenes (post-2025) and additional benchmarks (e.g., Waymo Open Dataset); test stability of 7.3% readiness rate and top-5 vulnerability types.
  2.  Intervention Study on Top Vulnerabilities: For a sample with B614 (unsafe PyTorch load), implement `weights_only=True` fix; re-run Bandit; measure reduction in high-sev issues and any model loading/performance regression.
  3.  CI/CD Introduction A/B Test: Add a basic GitHub Actions workflow (Pylint/Bandit on PRs) to matched repos without CI/CD vs. control; track MI and error/vulnerability counts over 3 months.

## Open Questions the Paper Calls Out
- **How do code quality metrics in AV perception repositories compare across different perception tasks such as Semantic Segmentation, Tracking, and Collaborative Perception?**
  - *Basis:* Explicitly stated in conclusion as future work.
  - *Why unresolved:* Study only analyzed 3D Object Detection repos; findings may not generalize.
  - *Evidence needed:* Replication on leaderboards for Segmentation, Tracking, etc., using same static analysis pipeline.
- **What runtime behaviors and model quality aspects are not captured by static analysis tools but can be revealed through dynamic analysis of AV perception code?**
  - *Basis:* Explicitly mentioned as a future direction.
  - *Why unresolved:* Study relied solely on static analysis, missing execution-time issues like memory leaks, concurrency problems, real-time bottlenecks.
  - *Evidence needed:* Execute perception models on sample datasets/simulations to monitor runtime errors, security exploits, and performance.
- **What factors hinder CI/CD adoption in AV perception research, and does promoting CI/CD lead to measurable improvements in code maintainability and security?**
  - *Basis:* Inferred from low adoption rate (7.3%) and observed correlation with maintainability, but causality unclear.
  - *Why unresolved:* Observational study; barriers to adoption not explored; correlation does not imply causation.
  - *Evidence needed:* Mixed-methods study: surveys/interviews to identify barriers, followed by an intervention where CI/CD is introduced to a subset of teams with pre/post quality measurements.
- **How effective are the proposed guidelines for preventing the top five security vulnerabilities in reducing the incidence of these issues in AV perception repositories?**
  - *Basis:* Inferred; guidelines derived from static analysis findings but not empirically tested.
  - *Why unresolved:* Guidelines are proposed based on issue concentration but their practical impact on reducing vulnerabilities is unvalidated.
  - *Evidence needed:* Empirical study where repos are refactored per guidelines; re-analyze with Bandit to compare vulnerability counts before/after, ideally in a controlled experiment.

## Limitations
- **Generalizability:** Findings based solely on KITTI/NuScenes 3D detection leaderboards; may not hold for other AV tasks (segmentation, prediction) or non-AI code.
- **Tool Limitations:** Static analysis misses dynamic/security issues and may have false positives/negatives; no runtime or integration testing.
- **Binary Readiness Definition:** Threshold (zero critical errors, no high-sev vulnerabilities) is necessary but insufficient for deployment; ignores testing coverage, documentation, architecture, and safety case evidence.
- **Sample Bias:** ~60% of leaderboard entries excluded (no public repo, non-Python, etc.); surviving repos may be systematically higher-quality.
- **Causality:** Observational design; correlations (e.g., CI/CD ↔ maintainability) do not imply causation.

## Confidence
- **Leaderboard-performance vs. production-readiness gap:** **Medium**. Strong internal evidence (no correlation, 7.3% readiness) but limited to two benchmarks and a minimal readiness definition; corpus lacks direct corroboration.
- **Security vulnerability concentration (Pareto pattern):** **High**. 79.3% of occurrences from top 5 issues is a robust statistical pattern within the studied dataset.
- **Specific top security issue types (e.g., B614) as universal:** **Medium**. High prevalence in this sample but untested across other AV tasks or time periods.
- **CI/CD correlation with maintainability:** **High** for the correlation (p=0.0003, consistent across team sizes). **Low** for causality due to non-experimental design.
