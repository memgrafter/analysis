# One-Token Verification for Reasoning Correctness Estimation
## Quick Facts
- **arXiv ID:** 2603.01025
- **Source URL:** https://arxiv.org/abs/2603.01025
- **Reference count:** 40
- **Primary result:** A single special token inserted into a frozen LLM's reasoning stream can estimate token-level correctness via KV cache probing, enabling 90% token reduction in best-of-N sampling while outperforming internal and external verifiers.

## Executive Summary
Large language models often generate reasoning traces via parallel sampling, but this is computationally expensive and lacks reliable ways to judge which traces are correct. One-Token Verification (OTV) introduces a lightweight verifier that integrates into a frozen LLM through low-rank adaptation (LoRA). During a separate verification pass, a single special token probes the cached key-value states of the reasoning prefix to produce a confidence score in one forward pass, without altering the base model's generation. Trained with pseudo-labels derived from final outcomes, OTV consistently improves accuracy and token efficiency across mathematical benchmarks, demonstrating a effective and scalable approach to process supervision.

## Method Summary
OTV augments a frozen base LLM with trainable LoRA modules on the Q/K/V projections of selected transformer layers, controlled by a binary gating signal `m_t`. During standard reasoning (`m_t=0`), the model runs unmodified. For verification (`m_t=1`), a special `[ToT]` token is inserted; its queries attend via cross-attention to the cached key-value states from all preceding tokens. The final hidden state of `[ToT]` is passed through a small regression head to output a scalar confidence. Token-level pseudo-labels are generated by linearly ramping from 0.5 to the final binary outcome label over the trace length. During training, multiple `[ToT]` tokens are inserted in parallel at all positions with a triangular mask to ensure each only sees its prefix. At inference, a single `[ToT]` token at any position queries the cache in one forward pass, enabling confidence estimates for early termination or best-of-N selection.

## Key Results
- OTV achieves higher accuracy than both internal logit-based methods and external verifiers like GenRM and DeepConf across GSM8K, AIME24, and AIME25 with Qwen and LLaMA models.
- In best-of-N sampling, OTV-guided confidence thresholds reduce average output token count by up to 90% while maintaining or improving accuracy.
- Weighted majority voting using OTV scores consistently surpasses majority voting and other aggregation strategies.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** OTV integrates a verifier into the LLM without altering its primary reasoning behavior.
- **Mechanism:** LoRA adapters (`R`, `S` matrices) are added to selected linear layers, and their output is gated by `m_t`. When `m_t=0` (reasoning mode), the adapters contribute zero; when `m_t=1` (verification mode), they are activated. This separation ensures fine-tuning the verifier does not degrade base generation.
- **Core assumption:** The gating cleanly isolates the two modes; LoRA updates are small enough to not perturb the base model’s forward pass when `m_t=0`.
- **Evidence anchors:** Equation (1) defines `z_t = (W + m_t RS)x_t`. The paper’s experiments show no drop in Pass@1 when the base model is used without verification.
- **Break condition:** Incorrect gating implementation could cause interference (e.g., LoRA pathway active during reasoning, altering logits).

### Mechanism 2
- **Claim:** A single `[ToT]` token can estimate token-level correctness at any point by attending to the entire cached prefix.
- **Mechanism:** The `[ToT]` token’s queries attend to the cached key-value states (`C_t`) from all previous tokens via cross-attention (Eq. 3). The KV cache is a sufficient statistic of the prefix, allowing task-specific pooling over the full reasoning trajectory.
- **Core assumption:** The KV contains all information needed to assess the quality of the prefix; cross-attention can learn to extract correctness-relevant patterns.
- **Evidence anchors:** Abstract states it "probes the model’s key-value cache". Section 3.2 justifies KV cache sufficiency.
- **Break condition:** If KV caching is corrupted (e.g., by incorrect masking during parallel generation) or cross-attention fails to learn meaningful weights, confidence estimates become noisy.

### Mechanism 3
- **Claim:** Token-level pseudo-labels derived from final outcomes provide an effective training signal for the verifier.
- **Mechanism:** For a trace with final label `y ∈ {0,1}`, each token `t` gets a target `c_t = 0.5 + (y-0.5)·t/T` (linear ramp). The verifier minimizes MSE between predicted `hat{c}_t` and `c_t`.
- **Core assumption:** Correct traces should exhibit monotonically increasing confidence; the linear ramp approximates this under outcome-only supervision.
- **Evidence anchors:** Section 3.3 defines the linear ramp. Ablations show constant labeling hurts performance, supporting the ramp’s utility.
- **Break condition:** If true reasoning correctness is non-monotonic (e.g., early mistakes corrected later), the linear ramp may mislead training, causing biased confidence trajectories.

## Foundational Learning
- **Concept: LoRA (Low-Rank Adaptation)**
  - **Why needed:** OTV must add verifier capability without full fine-tuning to preserve the base model's generation. LoRA injects trainable low-rank updates (`R`, `S`) into existing weight matrices, keeping base weights frozen and parameter-efficient.
  - **Quick check:** How does the gated LoRA module in Eq. (1) guarantee zero contribution to the base model’s outputs during normal generation (`m_t=0`)?
- **Concept: Transformer KV Cache**
  - **Why needed:** OTV reuses cached keys/values from the reasoning pass to avoid recomputation and enable single-token probing. The cache fully determines the forward pass for a given prefix.
  - **Quick check:** Why is the KV cache considered a "sufficient statistic" for the prefix, compared to just the last-layer hidden state?
- **Concept: Outcome-to-Process Supervision**
  - **Why needed:** Token-level correctness labels are scarce; OTV synthesizes them from cheap final outcome labels via a heuristic ramp, bridging the gap between outcome and process supervision.
  - **Quick check:** What is the theoretical effect of the linear ramp on the optimal MSE predictor, as shown in Appendix C.2?

## Architecture Onboarding
- **Component map:** Base LLM (frozen) -> LoRA adapters on Q/K/V (selected layers) -> Gating signal `m_t` -> Special `[ToT]` token -> 3-layer MLP regression head. KV cache from prefix is reused during verification.
- **Critical path:**
  - **Training:** Sample diverse reasoning traces -> cache KV states during generation -> assign pseudo-confidence per token via linear ramp -> construct parallel probe sequence with all `[ToT]` tokens and triangular mask -> compute MSE loss on LoRA + head parameters.
  - **Inference:** Generate (partial) trace and cache KV -> insert single `[ToT]` at desired position -> run forward with `m_t=1` (LoRA active) -> extract confidence from `[ToT]`’s final hidden state.
- **Design tradeoffs:**
  - LoRA rank `r`: Higher rank improves verifier capacity but increases parameters; ablation suggests `r=16` strong, `r=2` already beats baselines.
  - Pseudo-labeling rule: Linear ramp is default; constant label biases toward shorter traces; sigmoid/stepwise may better model non-linear confidence buildup.
  - Verification frequency: More frequent checks improve early stopping but add overhead; parallel probing (training-time) makes full-trace scoring cheap.
- **Failure signatures:**
  - Low correlation between OTV confidence and actual trace correctness on validation set.
  - High variance in confidence across traces for the same problem (unstable probing).
  - Degeneration: verifier assigns higher scores to extremely short traces (common with constant pseudo-labels).
- **First 3 experiments:**
  1. **Ablate LoRA rank** on a small GSM8K subset: train with `r ∈ {1,2,4,8,16}` and compare weighted majority accuracy; expect improvement then plateau.
  2. **Compare pseudo-labeling rules** (constant, linear, sigmoid) on validation set: plot confidence trajectories for correct/incorrect traces; linear should show clearest separation.
  3. **Validate KV cache probing:** For fixed traces, inspect cross-attention weights from `[ToT]` to previous tokens; high weights should align with key reasoning steps (e.g., after a calculation).

## Open Questions the Paper Calls Out
- How can we jointly train the base LLM and OTV verifier to maintain co-adaptation during model updates? (Appendix D proposes joint/continual training.)
- What alternative pseudo-confidence labeling strategies can better capture partial reasoning progress and reduce outcome-only bias? (Appendix D suggests uncertainty-aware labels.)
- Can extending OTV to output a ternary "correct/incorrect/unknown" signal improve robustness by enabling abstention? (Appendix D mentions moving to ternary output.)
- Does OTV generalize to non-mathematical reasoning domains and long-context settings? (Appendix D calls for tests on code reasoning, tool-augmented tasks, and long contexts.)

## Limitations
- Exact LoRA target layers and rank schedule unspecified; may affect parameter efficiency and interference risk.
- Regression head architecture (hidden dimensions, activations) not fully detailed, impacting training stability and reproducibility.
- Baseline verifier implementations (DeepConf, GenRM) lack reproducibility details, hindering fair comparison.
- Efficient variant hyperparameters (Drop@10 period, Stop@600 threshold) have edge cases unstated.
- Pseudo-labeling linear ramp may not capture non-monotonic confidence trajectories in all traces.

## Confidence
- **Mechanism 1 (Gated LoRA integration):** Medium. LoRA is parameter-efficient, but gating novelty raises interference risk without explicit validation of zero contribution in reasoning mode.
- **Mechanism 2 (KV cache probing):** Medium. KV cache sufficiency is plausible, but cross-attention learning depends on training data and may not generalize across domains.
- **Mechanism 3 (Outcome-driven pseudo-labels):** Medium. Linear ramp is simple heuristic; alignment with true token correctness is unverified and may not reflect non-linear reasoning dynamics.
- **Overall effectiveness (OTV vs baselines):** High. Consistent gains across models and benchmarks suggest robustness, though baseline details are sparse.
