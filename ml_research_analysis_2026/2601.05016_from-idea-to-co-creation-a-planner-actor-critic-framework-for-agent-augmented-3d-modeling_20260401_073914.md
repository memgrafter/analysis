# From Idea to Co-Creation: A Planner-Actor-Critic Framework for Agent Augmented 3D Modeling

## Quick Facts
- arXiv: 2601.05016
- URL: https://arxiv.org/abs/2601.05016
- References: 22
- Primary result: Multi-agent Planner-Actor-Critic framework significantly improves geometric accuracy, aesthetic quality, and task completion over single-prompt baselines for 3D modeling.

## Executive Summary
Current single-prompt AI agents for 3D modeling generate uneditable meshes and frequently fail to meet user objectives, necessitating manual iteration. This paper introduces a Planner-Actor-Critic multi-agent framework to address these limitations. The Planner decomposes user prompts into actionable steps, the Actor executes Blender operations via a safe, idempotent scripting interface, and the Critic evaluates intermediate results to guide refinement. Human users can provide supervisory feedback at any stage. In comparative evaluations across multiple low-poly tasks, the framework outperforms single-prompt baselines on geometric accuracy, aesthetic quality, and task completion rates. The Critic’s feedback loop reduces modeling errors and enables more complex, higher-quality outputs.

## Method Summary
The system integrates Blender with a Model Context Protocol (MCP) server, extending the standard toolset to include operations like `execute_code`, `get_scene_info`, and `get_viewport_screenshot`. A Planner agent (powered by GPT-4.1) parses the user prompt and maintains a dynamic todo list of modeling steps. The Actor translates each todo item into idempotent Blender Python code, respecting naming conventions to ensure re-executability, and runs it via MCP. After each execution, the Critic analyzes the updated scene state and a viewport screenshot to produce structured feedback on geometry, alignment, and aesthetics. The Planner then revises the todo list based on this feedback and the remaining iterations (up to five). A React/Three.js frontend displays the scene and allows human users to inject freeform feedback, which the Planner must incorporate. The orchestration is implemented with LangGraph, managing state transitions between the three agents in a cyclic graph.

## Key Results
- Geometric accuracy improved as measured by object count, vertex count, and scene similarity metrics.
- Final models received higher 5-point Likert scores for task alignment and aesthetics from human raters.
- Task completion rates increased across all tested scenarios compared to single-prompt baselines.
- Incorporating Critic feedback reduced common modeling errors and allowed for greater output complexity.

## Why This Works (Mechanism)
The framework’s effectiveness stems from its structured division of labor: the Planner creates a clear, modifiable plan; the Actor focuses on safe, incremental execution; and the Critic provides objective, multi-modal evaluation (scene data + visual screenshot). This separation prevents a single agent from being overwhelmed by the entire modeling burden and enables early error detection. The iterative loop, capped at five rounds, balances refinement with computational cost. Human supervision further adds a layer of high-level correction, ensuring alignment with user intent. Crucially, the Actor’s use of idempotent code protects against destructive side effects, preserving progress across attempts. Together, these design choices create a collaborative co-creation environment that consistently yields more accurate and aesthetically pleasing 3D models than a one-shot approach.

## Foundational Learning
- **Multi-agent systems**  
  *Why needed:* Specialization allows each agent to focus on a distinct aspect of the complex 3D modeling task, improving reliability and enabling debugging.  
  *Quick check:* Can agents operate independently? Does removing one agent degrade performance predictably?

- **Model Context Protocol (MCP)**  
  *Why needed:* Provides a standardized, secure bridge between LLMs and external tools like Blender, abstracting API details and handling communication.  
  *Quick check:* Are all tool calls routed through MCP? Does the server properly serialize/deserialize data and report errors?

- **Idempotent code generation**  
  *Why needed:* Ensures that scripts can be re-run safely without destroying prior work, a critical property for iterative refinement.  
  *Quick check:* Does the Actor produce code that avoids destructive operations (e.g., delete all) and uses named objects for updates?

- **Critique-based iterative refinement**  
  *Why needed:* External critique guides improvement, similar to code review or art direction, and helps identify mismatches with the task objective.  
  *Quick check:* Does the Critic’s feedback lead to concrete changes in the todo list and subsequent Actor actions?

- **Human-in-the-loop supervision**  
  *Why needed:* Humans can resolve ambiguities and provide high-level direction that automated agents may miss, increasing robustness.  
  *Quick check:* Are user inputs captured and reflected in the Planner’s next steps? Is there a risk of feedback being overwritten?

## Architecture Onboarding

**Component map**:  
User prompt -> Planner -> (todo list) -> Actor -> (Blender via MCP) -> Scene state + screenshot -> Critic -> feedback -> Planner ... (up to 5 iterations). Human feedback can be injected at any arrow.

**Critical path**:  
1. Receive user text prompt.  
2. Planner initializes a todo list of modeling steps.  
3. Actor takes the first step, generates idempotent Blender code, and executes it via MCP.  
4. System captures scene info and a viewport screenshot.  
5. Critic evaluates the current state and returns structured feedback.  
6. Planner updates the todo list (adds, modifies, or removes steps) based on feedback.  
7. Repeat steps 3–6 until the todo list is empty, five iterations are reached, or the user declares success.

**Design tradeoffs**:  
- Iteration cap (5) limits refinement for very complex scenes but keeps runtime reasonable.  
- Extended MCP tools increase modeling expressiveness but require careful validation to avoid invalid Blender operations.  
- GPT-4.1 offers high-quality reasoning but introduces cost and latency; smaller models might trade off performance.  
- Human feedback improves outcomes but depends on user availability and may slow the loop if frequent.

**Failure signatures**:  
- Object count suddenly decreases: indicates non-idempotent destructive code in Actor output.  
- Critic feedback appears verbatim in subsequent logs without any change to the todo list: suggests Planner is ignoring critique.  
- MCP tool calls fail with syntax errors: likely code generation mistakes; need to inspect Actor’s prompts.  
- Human feedback messages are not reflected in Planner’s next actions: could be due to state overwrite or insufficient prompt injection.

**First experiments** (for onboarding):  
1. **Primitive smoke test**: Prompt “Create a red sphere” to verify Actor–MCP integration and basic scene generation.  
2. **Iterative refinement observation**: Prompt “Model a low-poly chair” to watch the Planner–Actor–Critic loop in action, noting how feedback shapes the todo list and geometry.  
3. **Human feedback injection**: Prompt “Build a square dining table” and, after the second iteration, manually add feedback “Make the top larger”; verify the Planner’s response.

## Open Questions the Paper Calls Out

1. **Question:** Why does the Actor agent fail to incorporate the Critic's feedback after multiple iterations, leading to model quality degradation or convergence?  
   **Basis in paper:** [explicit] From Section 5.3: “the actor does not always incorporate the critics feedback, and after multiple iterations (often three), the modeling quality degrades or converge, making further improvements difficult.”  
   **Why unresolved:** The paper identifies this phenomenon but does not analyze its causes—whether due to feedback quality, Actor policy saturation, context management, or critic reliability—leaving the underlying mechanism unclear.  
   **What evidence would resolve it:** Controlled experiments tracking feedback incorporation rates per iteration, with ablations on critic model, feedback granularity, and Actor memory; log analysis of Actor decisions relative to Critic suggestions to identify failure patterns.

2. **Question:** How can the framework better integrate human intervention to prevent agents from ignoring or underutilizing supervisory input?  
   **Basis in paper:** [explicit] From Section 5.3: “while human intervention improves outcomes, its impact can be constrained or ignored by agents.”  
   **Why unresolved:** Although human feedback is allowed, the system lacks mechanisms to ensure agent responsiveness, possibly due to unstructured input or conflicts with agent plans. The paper does not study how to weight, parse, or prioritize human directives.  
   **What evidence would resolve it:** User studies comparing feedback formats (e.g., natural language vs. structured edits), metrics on agent compliance rates, and ablation studies measuring outcome variance when human input is mandatory, advisory, or ignored.

3. **Question:** What methods can extend the framework's modeling capabilities beyond primitive shapes to support more complex and expressive 3D assets while maintaining editability?  
   **Basis in paper:** [explicit] From Section 5.3: “the code execution approach often rely on modeling with primitive, which limit expressiveness.”  
   **Why unresolved:** Dependence on primitives restricts the framework to low-detail models, but many domains require complex geometries, imported assets, or procedural techniques. The paper does not explore toolset expansions or workflow adjustments for non-primitive modeling.  
   **What evidence would resolve it:** Prototype extensions adding parametric tools, asset library integrations, or mesh editing operations; evaluation on tasks requiring non-primitive elements, measuring success rates and editability (e.g., component isolation, non-destructive modification).

4. **Question:** How effective are pre-execution validation and automatic repair/retry mechanisms at reducing Blender script failures in the MCP-based workflow?  
   **Basis in paper:** [explicit] From Section 5.3 and future work: “Python scripts driving Blender can fail due to syntax or logic errors” and “we will introduce pre-execution validation and automatic repair/retry in the workflow.”  
   **Why unresolved:** The current system experiences script failures, but the proposed solutions are unvalidated. It is unknown which validation techniques (static analysis, simulation) or repair strategies (code correction, rollback) are feasible and effective for 3D modeling scripts.  
   **What evidence would resolve it:** Implementation of validation/repair modules; benchmarking on a corpus of failed scripts from experiments, measuring failure reduction, recovery success rates, and overhead costs; user studies on workflow interruptions pre- and post-intervention.

## Limitations

- Undisclosed implementation details (extended MCP tool schemas, full agent prompts, human evaluation protocol) hinder exact replication and independent verification.
- Evaluation limited to three low-poly tasks with only three human raters, resulting in low statistical power and potential overfitting to specific scenarios.
- Known failure modes (non-idempotent Actor code, ignored Critic feedback) may degrade performance in more complex or longer-running tasks.
