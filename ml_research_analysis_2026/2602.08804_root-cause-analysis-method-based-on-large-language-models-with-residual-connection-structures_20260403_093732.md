# Root Cause Analysis Method Based on Large Language Models with Residual Connection Structures

## Quick Facts
- **arXiv ID**: 2602.08804
- **Source URL**: https://arxiv.org/abs/2602.08804
- **Reference count**: 40
- **Primary result**: Achieved 48.25% root cause identification accuracy on the CCF AIOps 2025 dataset, reducing average reasoning steps from 6.2 to 3.4.

## Executive Summary
This paper introduces RC-LLM, a framework for root cause localization in complex microservice architectures. It innovates by using a large language model (DeepSeek-V3) with a residual-connection hierarchical fusion structure to integrate heterogeneous telemetry data—logs, traces, and metrics. The residual-like design preserves critical fault signals across data sources while suppressing noise, enabling the LLM to perform efficient temporal causal reasoning. Evaluated on the CCF AIOps 2025 dataset, RC-LLM substantially outperforms naive LLM baselines, demonstrating gains in both effectiveness (accuracy) and efficiency (reasoning steps).

## Method Summary
RC-LLM processes telemetry through a multi-stage pipeline. First, Parquet-format data is loaded and preprocessed (UTC conversion, component aggregation, temporal bucketing). Next, parallel analyzers extract anomalies: traces are modeled as call trees with erroneous leaf nodes; metrics use thresholds and PELT change-point detection; logs filter error-related entries via keywords. These modality-specific anomaly sets are fused hierarchically—starting with trace anomalies as an anchor, then residually adding metric evidence, followed by log evidence—to form a compact, noise-reduced context. This context is fed to a prompted LLM constrained to output structured JSON containing the root cause component, fault explanation, and reasoning trace.

## Key Results
- Final accuracy of 48.25% on the CCF AIOps 2025 dataset, a significant improvement over the naive baseline (23.75%).
- Average reasoning steps reduced from 6.2 to 3.4, indicating more efficient diagnoses.
- Iterative development shows trace-driven analysis (41.75%) as a strong intermediate, with residual fusion further boosting performance.

## Why This Works (Mechanism)

### Residual-like hierarchical fusion
The core innovation uses a residual-inspired structure to integrate multi-source telemetry. Starting with trace anomalies as an anchor, metric and log evidence are added via a residual operation (⊕), which retains the existing context while incorporating new signals. This prevents information degradation as data passes through fusion stages, yielding a compact evidence context that preserves fault signals and reduces noise from fault propagation. A break condition arises when the initial trace anchor lacks anomalies (e.g., failures without gRPC errors), potentially limiting the incorporation of metric/log signals.

### LLM-guided temporal causal reasoning
The integrated context is provided to an LLM (DeepSeek-V3) with a structured prompt that constrains output to JSON fields (root cause component, fault explanation, reasoning trace). This setup leverages the LLM's contextual reasoning to model temporal and cross-microservice causal dependencies, generating stepwise diagnoses that link anomalies across services and time. Hallucination or incorrect causal chains may occur if the LLM's training data lacks patterns matching the system's telemetry.

### Multi-stage anomaly extraction
Each telemetry type undergoes dedicated, heuristic-based analysis: trace call trees identify erroneous leaf nodes; metrics apply thresholds and PELT change detection on CPU, memory, RRT, and error rates; logs filter entries containing error keywords. This condenses raw telemetry into fault-relevant snippets, suppressing noise and reducing token consumption for the LLM. If anomalies are subtle (e.g., gradual decay) or expressed in uncovered patterns (missing keywords), the analysis may overlook critical evidence.

## Foundational Learning
- **Residual Connections (Deep Learning)**: Skip connections in networks like ResNet add input to output, alleviating vanishing gradients and preserving information across layers. Understanding their formats and anomalies is essential to grasp the analysis steps. *Quick check*: What aspect of system behavior can a distributed trace reveal that individual service metrics cannot?

## Architecture Onboarding
Component map: Data Input (PyArrow) -> Preprocessing (UTC conversion, component aggregation, sorting/bucketing) -> Data Analysis (Trace: Anytree call trees; Metrics: thresholds + PELT; Logs: keyword filter) -> Data Integration (hierarchical residual fusion: trace ⊕ metric ⊕ log) -> LLM Reasoning (DeepSeek-V3 with LangChain parser) -> Output (JSON).

Critical path: Raw telemetry undergoes preprocessing, then parallel analysis; the resulting modality-specific anomalies are sequentially fused in a trace→metric→log order; the integrated context prompts the LLM to produce structured JSON.

Design tradeoffs: Residual fusion depends heavily on trace anchor quality; the 671B LLM ensures accuracy but incurs high latency/cost; simple heuristics are fast but may miss complex anomalies; service-level focus sacrifices pod-level granularity.

Failure signatures: node-level misidentification (indistinguishable replicas), missing trace anchor (normal gRPC status), token overflow from many anomalies, LLM hallucination on ambiguous evidence.

First 3 experiments:
1. Baseline (Original): Direct LLM on raw data → 23.75% accuracy, 6.2 avg steps.
2. Trace-driven analysis (Intermediate-stage): Use trace anomalies to select components → 41.75% accuracy, 4.3 steps.
3. Residual fusion (Final): Integrate metric and log residually with trace → 48.25% accuracy, 3.4 steps.

## Open Questions the Paper Calls Out
- **Fine-grained localization**: How can RC-LLM improve pod-level accuracy? Current residual fusion aggregates per-service, and metrics/logs lack replica discrimination. Resolution: incorporate per-replica telemetry and replica-sensitive prompts.
- **Alternative fusion strategies**: Would cross-attention or graph-based fusion outperform the residual-like design? The paper only compares residual variants. Resolution: implement and benchmark other fusion architectures on the dataset.
- ** Smaller LLM trade-offs**: What accuracy-efficiency trade-offs exist for smaller models? The 671B DeepSeek-V3 was used, but cost is prohibitive. Resolution: benchmark across model sizes (7B, 13B, 70B) measuring accuracy, steps, and resources.
- **Integration with RAG**: How does retrieval-augmented generation affect performance? The authors excluded RAG to focus on core fusion. Resolution: add a RAG component for past incidents and evaluate with/without it.

## Limitations
- Exact residual fusion operation (e.g., concatenation, attention) is conceptually described but not algorithmically specified.
- Anomaly detector parameters (metric thresholds, PELT penalty, keyword lists) are undisclosed, requiring heuristic reconstruction.
- LLM prompt template and structured-output parser details are omitted, hindering replication of reasoning behavior.
- The method relies on a trace anchor; failures without trace anomalies may be mislocalized.

## Confidence
- Residual fusion design: Medium (conceptually sound but no ablation against alternatives).
- LLM reasoning approach: Medium (assumes LLM causal inference capability; prompt engineering not detailed).
- Anomaly extraction heuristics: Medium (simple filtering may miss subtle or novel fault patterns).
- Overall reported results: High (evaluated on a standard dataset with clear improvements).

## Next Checks
