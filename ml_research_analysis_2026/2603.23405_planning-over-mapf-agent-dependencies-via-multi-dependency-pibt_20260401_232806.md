# Planning over MAPF Agent Dependencies via Multi-Dependency PIBT

## Quick Facts
- **arXiv ID**: 2603.23405  
- **Source URL**: https://arxiv.org/abs/2603.23405  
- **Reference count**: 40  
- **Primary result**: MD-PIBT generalizes PIBT by handling multiple agent dependencies, enabling significantly higher success rates on large-agent (PMLA) scenarios while matching PIBT/EPIBT performance on standard unit-agent MAPF.

## Executive Summary
Multi-Agent Path Finding (MAPF) seeks collision-free paths for multiple agents on a graph. The classic Priority Inheritance with Backtracking (PIBT) algorithm plans agents in priority order, but it is limited to resolving paths that conflict with at most one other agent. This work introduces Multi-Dependency PIBT (MD-PIBT), which overcomes that limitation by explicitly representing and reasoning about agent dependencies through an Agent Dependency Graph (AgDG). MD-PIBT permits up to *C* safe-path collisions per agent, distinguishes hard (unplanned) and soft (planned) dependencies, and uses a flexible backtracking strategy guided by a replan limit *R*. The approach generalizes both PIBT (*C*=1, always fallback) and EPIBT (*C*=1, retry). Empirical evaluation on one‑shot and lifelong MAPF with diverse dynamics—pebble motion, large agents, rotation, and differential drive—demonstrates that MD-PIBT significantly outperforms EPIBT on large‑agent problems (PMLA) when *C*>1, while replicating PIBT/EPIBT performance on standard unit‑agent benchmarks. Dependency analysis shows a sharp increase in multi‑dependency cases under congestion, underscoring the necessity of multi‑dependency resolution.

## Method Summary
MD-PIBT reformulates MAPF as a search over an Agent Dependency Graph (AgDG). The AgDG is a directed graph where nodes are agents and edges represent dependencies: a hard edge (→) arises when a tentative path collides with the safe path of an unplanned agent, forcing the latter to be replanned; a soft edge (⇢) arises when colliding with a planned agent’s safe path. The algorithm maintains a priority queue of agents to plan. For each agent, it attempts to find a *w*-step path that collides with at most *C* safe paths, respecting a given mode (PIBT avoids all planned agents; EPIBT avoids only higher‑priority ones during the current call). If a valid path is found, the agent is tentatively planned and dependencies are added to the AgDG. If not, the agent either falls back to its safe path (waiting) or triggers replanning of one of its parents (incoming hard edge), bounded by a replan limit *R*. After the initial call, safe paths are updated to the final paths. This mechanism generalizes PIBT (always fallback, *C*=1) and EPIBT (always retry, *C*=1). Termination is guaranteed with finite *R*.

## Key Results
- On large‑agent (PMLA) scenarios, MD-PIBT with *C*>1 yields substantially higher success rates than EPIBT.  
- For standard unit‑agent MAPF, MD-PIBT (with *C*=1, appropriate mode) matches the performance of PIBT and EPIBT while maintaining similar runtimes.  
- Empirical analysis reveals that dependencies per agent increase markedly in congested maps, confirming the need for multi‑dependency handling.

## Why This Works (Mechanism)

### Mechanism 1: Agent Dependency Graph (AgDG) as Search Space
MD-PIBT constructs an Agent Dependency Graph (AgDG) to systematically capture and resolve conflicts. Nodes represent agents; edges are hard (→) if the tentative path collides with an unplanned agent’s safe path, and soft (⇢) if it collides with a planned agent’s safe path. The graph is built dynamically during planning: starting from a high‑priority agent, each tentative path exploration adds edges for collisions; unplanned agents with new hard incoming edges are pushed onto the priority queue. This structure enforces priority inheritance and avoids cycles via backtracking and safe‑path fallback. The paper reinterprets PIBT as a special case of AgDG search (Section III). If the AgDG contains unresolvable cycles (e.g., mutual hard dependencies) and the replan limit *R* is exhausted, agents fall back to their safe paths, which may lead to deadlock or suboptimality (Section IV‑C).

### Mechanism 2: Multi‑Dependency Handling via Collision Budget *C*
MD-PIBT allows each agent to have up to *C* dependencies (collisions with safe paths), where *C*∈ℤ⁺. PIBT and EPIBT implicitly fix *C*=1; MD-PIBT generalizes this. A larger *C* lets a single agent’s path conflict with multiple low‑priority agents, each creating a hard dependency. This is crucial for the Pebble Motion with Large Agents (PMLA) model, where large agents block several small ones simultaneously. The paper shows that *C*>1 dramatically improves success rates on PMLA (Abstract; Section IV‑D). The underlying assumption is that dense/heterogeneous scenarios often require pushing multiple agents at once; *C*=1 renders many such instances infeasible. However, increasing *C* can explode the AgDG size and cause excessive backtracking, though the experiments on PMLA observed no significant runtime growth (Section V‑B.2).

### Mechanism 3: Flexible Backtracking with Safe Paths and Replan Limit *R*
When an agent fails to find a valid path within its collision budget, MD-PIBT chooses between two fallback strategies bounded by a replan limit *R*:  
- **Fallback to safe path**: If the agent’s replan counter exceeds *R*, it adopts its safe path (waiting at the current location) and becomes planned; all parents with hard edges are unplanned recursively.  
- **Parent replan**: Otherwise, the algorithm selects a parent (typically the most recent agent with a hard edge), unplans it, and re‑queues it for replanning.  
This generalizes PIBT (always fallback) and EPIBT (always retry). The safe path guarantees a conflict‑free option and ensures termination with finite *R* (Appendix A1). In practice, *R*=100 for one‑shot and *R*=1000 for lifelong MAPF balanced quality and runtime. Too small *R* forces premature fallback, degrading paths; too large *R* risks exponential worst‑case time O(|P|^N) due to deep dependency chains.

## Architecture Onboarding
**Component Map**  
- *Agent class*: stores tentative path π, safe path τ, priority p, *w*-step path list P, current path index d, replan counter r.  
- *Agent Dependency Graph (AgDG) G*: directed graph (nodes=agents; edges hard → or soft ⇢). Functions: `addDepend` adds edges for path‑safe collisions; `removeDepend` unplans agents, converts soft→hard edges, resets indices.  
- *Priority queue q*: holds agents needing planning; typically a stack (DFS).  
- *Utility functions*:  
  - `findBestPath(ak, Aplan, m, C)` returns the first valid *w*-step path from ak.P that collides with ≤C safe paths and obeys mode *m*.  
  - `fallToSafePath(ak | R)` decides whether ak exceeded the replan limit *R*.  
  - `chooseParent(ak)` returns a parent agent (incoming hard edge) for replan, often the most recent.

**Critical Path** (Algorithm MDPIBT)  
1. **Outer loop**: Iterate agents in priority order; if an agent *ai* is unplanned, invoke `MDPIBT(ai)`.  
2. **MDPIBT**:  
   - Initialize queue *q* with the starting agent.  
   - While *q* not empty:  
     a. Pop agent *ak*; increment *ak*.r.  
     b. Invoke `findBestPath(ak)`. If a tentative path *π′* is found:  
        - Set *ak*.π = *π′* and add *ak* to planned set *Aplan*.  
        - Call `addDepend` to create hard/soft edges for collisions; push any unplanned agents gaining a hard dependency onto *q*.  
     c. Else (no valid path):  
        - If `fallToSafePath(ak | R)` is true: set *ak*.π = *ak*.τ; add to *Aplan*; for each parent *ap* with hard edge (*ap*→*ak*), call `removeDepend(ap)` to unplan *ap* and its subtree.  
        - Else: pick parent *ap* via `chooseParent(ak)`; call `removeDepend(ap)`; push *ap* onto *q*.  
3. **Finalization**: After `MDPIBT` returns, update safe paths: for each agent with a planned path, set τ = π; reset π = ⊥ for the next iteration.

**Design Tradeoffs**  
- *C* (max collisions): Larger *C* aids PMLA/dense scenarios but increases AgDG size; for unit agents, *C*=1 suffices.  
- *w* (planning window): Larger *w* reduces myopia but exponentially increases per‑agent computation and may cause more collisions.  
- *m* (mode): EPIBT (avoids higher‑priority agents in current call) is more permissive than PIBT (avoids all planned); EPIBT often yields higher throughput in lifelong MAPF.  
- *R* (replan limit): Higher *R* improves solution quality but risks exponential worst‑case runtime; typical values: 100 (one‑shot), 1000 (lifelong).  
- *p* (priority order): LET (Longer Elapsed Time) improves warehouse throughput; SD (Shorter Distance) may reduce conflicts.  
- *Queue discipline*: The paper uses a stack (DFS); alternative orders (e.g., priority queue) could alter dependency resolution.

**Failure Signatures**  
- Timeout or high runtime: likely caused by large *w*, high *C*, deep dependency chains, or excessive *R*; monitor replan counters.  
- Low success rate in PMLA: check if *C*=1; increasing *C* often helps.  
- Memory blowup: stemming from AgDG storage and enumeration of *w*-step paths; reduce *w* or limit path enumeration.  
- Throughput drop in lifelong MAPF: experiment with different priorities (*p*), planning window (*w*), or switch to EPIBT mode.  
- Persistent deadlocks (agents repeatedly exceed *R*): lower *R* or adjust *C*; may indicate overly constrained environment.

**First 3 Experiments** (for validation)  
1. **Replicate PIBT**: Set *C*=1, *w*=1, *m*=PIBT; run on `random-32-32-20` with 100 agents; compare success rate and sum‑of‑costs to known PIBT baselines.  
2. **PMLA scaling**: Use `empty-64-64-PMLA` with large (5×5) and small (1×1) agents; test *C* ∈ {1,2,4,∞} with *w*=3; expect success rate to increase with *C* without significant runtime rise.  
3. **Replicate EPIBT**: Set *C*=1, *w*=3, *m*=EPIBT; run on `warehouse-10-20-10-2-1` lifelong scenario with 300 agents; compare throughput to standalone EPIBT.

## Open Questions the Paper Calls Out
#### Open Question 1
- **Question**: How can the hyperparameters of MD‑PIBT (particularly *C*, *w*, *h*, and *R*) be automatically configured for a given MAPF instance to achieve high success rates without exhaustive search?  
- **Basis in paper**: The paper performs exhaustive hyperparameter sweeps and finds that the best configuration varies significantly across scenarios (e.g., PM vs. PMLA, different maps, agent counts). Tables A2–A4 show no consistent pattern, and the authors do not provide a method for automatic configuration.  
- **Why unresolved**: Exhaustive search is computationally expensive and impractical for real‑time deployment. Understanding the relationship between problem characteristics (e.g., congestion, agent size distribution, map topology) and optimal hyperparameters is necessary for practical use.  
- **What evidence would resolve it**: A predictive model or heuristic that maps problem features (like agent density, average distance to goal, corridor widths) to optimal hyperparameter settings, validated across diverse MAPF benchmarks.

#### Open Question 2
- **Question**: How do structural properties of the Agent Dependency Graph (AgDG)—such as its depth, branching factor, presence of cycles, or maximum degree—influence the planning success rate, runtime, and solution quality of MD‑PIBT?  
- **Basis in paper**: The paper introduces the AgDG but only analyzes the number of dependencies per agent (Figure 4, A4). It does not analyze graph topology beyond this. The algorithm’s backtracking and replanning logic is directly governed by the AgDG structure, suggesting a deep connection.  
- **Why unresolved**: Understanding these relationships could lead to improved queue ordering policies, better parent selection strategies (beyond “most recently added”), and potentially new variants of MD‑PIBT that adapt to the AgDG structure during planning.  
- **What evidence would resolve it**: Empirical studies correlating AgDG metrics (computed during planning) with performance metrics, or theoretical analysis linking graph properties to worst‑case runtime bounds.

#### Open Question 3
- **Question**: To what extent can MD‑PIBT be generalized beyond the tested models (PM, PMLA, RM, DDR) to handle more complex heterogeneous agent dynamics (e.g., varying maximum speeds, acceleration limits, turning radii) and non‑grid environments?  
- **Basis in paper**: The future work section states: “Further optimizations for large agents (e.g., similarly motivated with Het‑PIBT [22]) would be promising.” Additionally, the authors claim MD‑PIBT could be “used as broadly as CBS.” However, they only evaluate on agents with identical dynamic models (except size in PMLA) and on grid graphs.  
- **Why unresolved**: HetPIBT handles heterogeneous velocities but is still based on PIBT’s single‑dependency limitation. Combining heterogeneous dynamics with multi‑dependency resolution is non‑trivial. Extending to non‑grid or continuous spaces would require rethinking the path representation and collision checking.  
- **What evidence would resolve it**: Implementation and evaluation of MD‑PIBT with heterogeneous agents (e.g., different speed classes) on standard benchmarks, or extension to continuous state spaces with appropriate motion primitives.

#### Open Question 4
- **Question**: What are the theoretical runtime bounds of MD‑PIBT when considering the maximum collision parameter *C* > 1, and how does *C* affect the trade‑off between solution quality and computational effort?  
- **Basis in paper**: The paper provides a worst‑case bound of O(|P|^N) and a practical bound of O(NR) but does not analyze the role of *C*. Empirically, increasing *C* often improves success rates for large agents without significantly increasing runtime (Figure 3), but this is not explained theoretically.  
- **Why unresolved**: The bound O(NR) depends on *R* (replan limit) but ignores *C*. Since *C* limits the branching factor in the dependency graph, it should improve worst‑case bounds. A tighter analysis could guide parameter selection and predict scalability.  
- **What evidence would resolve it**: Theoretical derivation of runtime complexity in terms of *N*, |P|, *C*, and structural parameters of the AgDG. Experimental validation of the predicted scaling with *C* on large instances.

## Limitations
- **Overhead and worst‑case complexity**: AgDG management and backtracking can degrade performance for high *C* or deep dependency chains; the worst‑case runtime is exponential (O(|P|^N)) and has not been stress‑tested on pathological instances.  
- **Hyperparameter sensitivity**: Optimal settings for *C*, *w*, *R*, and priority order vary across scenarios; the paper relies on default sweeps without a systematic ablation or automatic tuning method.  
- **Evaluation scope**: Comparisons are limited to PIBT/EPIBT; broader benchmarks against state‑of‑the‑art MAPF solvers (e.g., CBS, learning‑based methods) and performance in complex obstacle‑rich environments remain unexplored.

## Confidence
- MD‑PIBT generalizes PIBT and EPIBT (by formal inclusion): **High**  
- Superiority on large‑agent (PMLA) scenarios (with *C*>1): **Medium** (strong on empty maps, but untested on obstacle‑dense maps)  
- Comparable performance on standard unit‑agent MAPF: **Medium** (validated on some benchmarks, lacking broader solver comparisons)  
- Termination guarantee under bounded *R*: **High** (theoretical proof provided)  
- Dependency analysis showing increased multi‑dependency cases in congestion: **High** (empirical data directly supports)
