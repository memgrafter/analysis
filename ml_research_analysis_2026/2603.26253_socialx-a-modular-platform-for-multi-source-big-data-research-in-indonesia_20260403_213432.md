# SocialX: A Modular Platform for Multi-Source Big Data Research in Indonesia

## Quick Facts
- **arXiv ID:** 2603.26253
- **Source URL:** https://arxiv.org/abs/2603.26253
- **Reference count:** 2
- **Primary result:** A modular platform that unifies multi-source Indonesian big data research, achieving 56.3% noise reduction via a context-conditioned relevancy classifier (F1=0.948).

## Executive Summary
SocialX tackles the fragmentation of Indonesian big data research by integrating heterogeneous data collection, language‑aware preprocessing, and pluggable analysis into a single, source‑agnostic platform. Its core innovation is a three‑layer modular architecture—collection, preprocessing, and analysis—connected via a common data schema and a lightweight database‑driven job coordinator. The preprocessing layer employs a composable filter pipeline culminating in a context‑conditioned relevancy classifier fine‑tuned from IndoBERT, which alone removed 28.3% of off‑topic content and contributed to an overall noise reduction of 56.3% on a representative multi‑source dataset. The classifier achieved an F1 score of 0.948 across diverse Indonesian registers. The design demonstrates extensibility: new data sources, filters, and analyzers can be added without modifying existing layers. The platform is publicly accessible at https://www.socialx.id.

## Method Summary
SocialX implements a three‑layer modular system. Collection connectors normalize diverse source formats (social media APIs, news HTML, e‑commerce listings) into a common schema. A database‑driven job queue decouples layers: workers poll for jobs, read input from the data store, execute their task, and write results back. The preprocessing pipeline is configurable and runs in sequence: deduplication, date filtering, language detection, keyword filtering, and finally a context‑conditioned relevancy classifier (fine‑tuned IndoBERT) that judges text against a user‑provided research context. Analysis modules consume the cleaned data and produce outputs such as sentiment or network graphs. This separation allows independent evolution of each layer while maintaining source‑agnostic downstream processing.

## Key Results
- Noise reduction of 56.3% on a multi‑source dataset.
- The context‑conditioned relevancy classifier removed 28.3% of off‑topic content, achieving F1=0.948.
- The modular design allowed new data sources, filters, and analyzers to be added without changes to existing layers.

## Why This Works (Mechanism)

### Mechanism 1: Unifying heterogeneous data via a common schema
- **Claim:** Unifying heterogeneous data into a common schema at the collection layer enables source‑agnostic downstream processing.
- **Mechanism:** Collection connectors normalize diverse source formats into a single structured schema. The preprocessing and analysis layers consume only this normalized format and never the original source‑specific payload.
- **Core assumption:** The common schema is sufficiently expressive to capture essential data elements from all supported sources without loss of research‑critical information.
- **Evidence:** [abstract] states that collection connectors normalize heterogeneous data into a common schema, making downstream processing independent of data origin. [section 3.2] explains that normalization is the key abstraction and downstream layers operate without knowledge of origin. [corpus] provides weak parallel evidence from other modular platforms but does not directly validate the schema design.
- **Break condition:** If a new data source contains attributes critical for analysis that cannot be mapped to the existing schema without modifying downstream layers.

### Mechanism 2: Separation of layers via a shared data store and job coordinator
- **Claim:** Separation of layers via a shared data store and job coordinator allows independent extensibility of collection, preprocessing, and analysis.
- **Mechanism:** A database‑driven job queue decouples layers. Workers poll for jobs matching their type, execute, store results, and update status. Workers interact only with the data store, not with each other.
- **Core assumption:** All necessary state for any job is captured in the data store and job metadata; no runtime inter‑layer communication is required.
- **Evidence:** [abstract] describes three independent layers connected by a lightweight job coordination mechanism. [section 3.1] details that each worker knows only how to execute its task and read/write from the data store; a collection worker does not know preprocessing exists. [corpus] offers little direct evidence for this specific coordination pattern.
- **Break condition:** If a new analysis method requires iterative feedback with preprocessing (e.g., active learning) that the current stateless job model cannot support.

### Mechanism 3: Fine‑tuned context‑conditioned relevancy classifier
- **Claim:** A fine‑tuned, context‑conditioned relevancy classifier removes semantically off‑topic content that keyword filters miss, significantly improving dataset precision for Indonesian text.
- **Mechanism:** IndoBERT is fine‑tuned on text‑context pairs to produce a binary relevancy judgment. It is applied as the final filter, capturing implicit relevance through contextual understanding of informal and code‑mixed registers.
- **Core assumption:** Relevance can be effectively modeled as a binary classification task given a user‑provided research context string.
- **Evidence:** [abstract] reports that the classifier reduced noise by 28.3% and achieved F1=0.948. [section 4.3] provides the F1 score, manual inspection confirming >90% of removed items were off‑topic, and describes the input format: `[CLS] context [SEP] text [SEP]`. [corpus] offers no independent validation for this specific classifier.
- **Break condition:** If the user’s research context is poorly defined or outside the classifier’s training distribution (188 topics), leading to high false negative rates for implicitly relevant content.

## Foundational Learning

### Common Schema Abstraction
- **Why needed:** It is the foundational contract that enables source‑agnosticism. All downstream logic depends on this schema, not on source origins.
- **Quick check:** If you add a new data source (e.g., TikTok comments), what is the single most important implementation task in the connector, and what happens if you get it wrong?

### Composable Filter Pipeline
- **Why needed:** Preprocessing is a sequence of independent, configurable stages; engineers must grasp order dependencies and state transformations between stages.
- **Quick check:** Why is deduplication typically applied first, before language detection or relevancy classification? What would break if the order were reversed?

### Job Coordinator Pattern
- **Why needed:** This pattern enforces layer independence; components must be stateless workers that interact only via the data store.
- **Quick check:** A new analyzer needs to process data from two different preprocessed datasets simultaneously. Can this be done within the current pattern? If not, what architectural change would be required?

## Architecture Onboarding

### Component map
- **Collection:** Source‑specific connectors → normalize to `common_schema` → write to `data_store`.
- **Preprocessing:** `job_queue` triggers filter pipeline (deduplication → date filtering → language detection → keyword filtering → relevancy classification) → transforms `raw_dataset` → `clean_dataset`.
- **Analysis:** `job_queue` triggers analyzer (sentiment/network/etc.) → reads `clean_dataset` → writes `analysis_result`.
- **Infrastructure:** `data_store` (database), `job_queue` (database table), `worker_pool` (stateless processes).

### Critical path
1. Select sources and configure collection.
2. Run collection job to produce normalized raw data.
3. Configure and run preprocessing job (filter pipeline) to produce clean data.
4. Choose and run an analyzer to generate results.
5. Visualize outputs.

### Design tradeoffs
- **Simplicity vs. Real‑time:** The database‑polling job queue is simple and robust but introduces latency; unsuitable for streaming analysis.
- **Schema Generality vs. Fidelity:** A highly generic common schema may lose source‑specific metadata needed for certain analyses (e.g., social media reply chains).
- **FMR Optimization vs. Recall:** The relevancy classifier is tuned for high precision (F1=0.948) but may exclude borderline relevant content; tradeoff is explicit via confidence thresholds.

### Failure signatures
- **Preprocessing collapse:** If a filter removes >70% of records, manually inspect a sample to check for over‑aggressive configuration (especially relevancy threshold).
- **New source breaks pipeline:** Check that connector output perfectly matches `common_schema`; a missing field will cause downstream worker crashes.
- **Analyzer fails on dataset:** Verify the dataset passed the selected filters; e.g., language filter set to "Indonesian" but dataset contains English.

### First 3 experiments
1. **Add a new e‑commerce source:** Implement a connector that scrapes a new marketplace and maps its fields to `common_schema`. Deploy it without touching preprocessing or analysis code. Verify a collection job completes and data appears in the store.
2. **Modify filter order:** Change the pipeline to run `keyword filtering` before `language detection`. Collect a multilingual dataset with keyword spam in English. Observe whether language filtering now removes more total records (because irrelevant English spam is filtered early) versus the standard order.
3. **Add a new analyzer type:** Implement a "topic modeling" analyzer that reads a `clean_dataset` and writes a `topic_distribution` result. Ensure it registers with the job coordinator and renders a visualization. Crucially, confirm no changes were needed in the preprocessing layer for this to work.

## Open Questions the Paper Calls Out
1. **Cross‑source comparison:** The platform currently operates on one dataset at a time; automated simultaneous analysis and comparison across multiple heterogeneous sources is not supported. The modular design separates data by source and analyzers process a single dataset, leaving comparison to manual effort. Resolution would require a new module or job coordinator modification that accepts multiple preprocessed dataset references, aligns them (e.g., temporally or thematically), and produces comparative outputs.
2. **Domain adaptation for the relevancy classifier:** The classifier was trained on 188 topics and may underperform on domains not represented in its training data. Its effectiveness is validated only on that specific distribution; generalization to novel domains (e.g., specialized scientific terminology, emerging slang, new socio‑political contexts) is an unstated assumption. Resolution evidence: a formal domain adaptation study evaluating the classifier on a held‑out set of niche Indonesian text and investigating techniques like few‑shot fine‑tuning or retrieval‑augmented classification.
3. **Real‑time streaming extension:** The platform processes data in batch mode with no real‑time capability. The database‑polling job queue is batch‑focused; streaming would require rethinking job scheduling, data storage (from batch tables to stream buffers), state management for filters/analyzers, and possibly the common schema to handle incremental updates. Resolution evidence: a prototype streaming extension that introduces a "stream" job type, with performance benchmarks (latency, throughput), and an analysis of required changes to preserve modularity.
4. **Global connector generalization:** While the architecture is source‑agnostic, connectors are focused on Indonesian platforms. Scaling to truly global sources (e.g., Chinese social media with different API structures, European news with paywalls, global academic databases with complex metadata) tests the limits of the common schema and connector pattern. Resolution evidence: successful development and integration of at least three connectors for major non‑Indonesian, non‑English platforms without modifications to core preprocessing or analysis layers, along with documentation of new schema mappings, access‑handling challenges, and any necessary connector interface extensions.

## Limitations
- The exact dataset used for the reported 56.3% noise reduction is undisclosed, preventing exact replication of that metric.
- Full training details for the relevancy classifier (splits, hyperparameters, complete topic list) are missing, hindering independent verification of its F1=0.948 performance.
- The common schema’s expressiveness is an untested assumption; if new sources require fields absent from the schema, downstream layers may break or need modification, challenging the source‑agnostic claim.

## Confidence
- **High:** The modular three‑layer architecture with database‑driven coordinator is clearly described and logically consistent with the demonstrated extensibility.
- **Medium:** The classifier’s performance (F1=0.948) and overall noise reduction (56.3%) are well‑anchored in the paper’s own evaluation but lack external replication or detailed methodological transparency.
- **Low:** The claim that the common schema is “sufficiently expressive for all supported sources without loss of research‑critical information” is an assumption not pressure‑tested; break conditions are speculative.
