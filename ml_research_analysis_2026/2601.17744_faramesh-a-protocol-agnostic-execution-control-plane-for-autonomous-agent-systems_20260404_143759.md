# Faramesh: A Protocol-Agnostic Execution Control Plane for Autonomous Agent Systems

## Quick Facts
- **arXiv ID:** 2601.17744
- **Source URL:** https://arxiv.org/abs/2601.17744
- **Reference Count:** 22
- **Primary Result:** Introduces an Action Authorization Boundary (AAB) that non-bypassably mediates all side-effecting actions from autonomous agents, enabling deterministic, replayable authorization with sub-10ms latency and 7,800 actions/min throughput.

## Executive Summary
Faramesh addresses a critical security gap: autonomous agents that trigger real-world effects lack mandatory, execution-time authorization. It proposes a protocol-agnostic control plane built on a non-bypassable Action Authorization Boundary (AAB). All agent intents are normalized into a Canonical Action Representation (CAR), allowing deterministic policy evaluation against system state to produce PERMIT/DEFER/DENY decisions. Decision records are provenance-complete, hash-chained, and replayable. Empirical evaluation shows high mediation coverage (0.9993), resistance to bypass attempts, and strong performance, establishing properties—non-bypassability, determinism, fail-closed behavior, replayable provenance—that existing IAM or orchestration systems do not provide.

## Method Summary
The core method inserts an immutable architectural checkpoint—the AAB—between agent reasoning and effectful execution. Every potential side-effect is mediated through a deterministic authorization function `B(A, P, S)` that evaluates a canonical action `A` against policy `P` and state digest `S`. Execution occurs iff a prior PERMIT decision exists. Canonicalization collapses representational variance (e.g., parameter order, synonyms) into a stable `A`. All decisions are recorded in an append-only, hash-chained log binding `(A, P, S)` to the outcome, enabling replay and audit. Executors are instrumented to accept only valid PERMIT artifacts bound to the action's canonical hash, preventing bypass and ensuring exactly-once semantics via atomic deduplication.

## Key Results
- **Performance:** End-to-end p95 latency of 9.61 ms; sustained throughput of 7,800 actions/min.
- **Security Guarantees:** Mediation coverage of 0.9993; all tested bypass attempts (direct tool calls, token replay, concurrency) blocked; exactly-once semantics under 1,000,000 concurrent requests.
- **Design Properties:** Guarantees non-bypassable enforcement, deterministic authorization, fail-closed behavior, and replayable provenance.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** The Action Authorization Boundary (AAB) enforces mandatory, non-bypassable mediation of all effectful actions.
- **Mechanism:** A deterministic authorization function `B(A, P, S)` evaluates a canonical action `A` against policy `P` and state `S`, emitting a decision (`PERMIT`/`DEFER`/`DENY`). Execution occurs if and only if a prior `PERMIT` decision exists.
- **Core assumption:** All execution-capable paths are architecturally constrained to pass through this boundary; no side-effecting operation may occur without a decision record.
- **Evidence anchors:**
  - `[abstract]` Defines AAB as a "non-bypassable checkpoint that mediates all side-effecting actions."
  - `[section 5]` Formalizes the boundary as `B: (A, P, S) → {PERMIT,DEFER,DENY}` with `Exec(A) ⇐⇒ B(...)=PERMIT`.
  - `[corpus]` Weak support; related work (e.g., AARM) addresses runtime security but lacks a canonical, non-bypassable boundary.
- **Break condition:** Any direct tool invocation, alternate SDK path, or cached token misuse that reaches execution endpoints without a valid decision artifact bound to the canonical action hash `h`.

### Mechanism 2
- **Claim:** Canonical Action Representation (CAR) collapses representational variance to enable deterministic authorization over semantic intent.
- **Mechanism:** A pure, deterministic function `Canon(I)` transforms any agent intent `I` (tool call, natural language, etc.) into a structured, normalized `A` with sorted fields, resolved defaults, and controlled vocabularies. Authorization is computed over `A`, not `I`.
- **Core assumption:** Agent outputs are syntactically unstable (parameter order, synonyms, aliases); stable enforcement requires a representation invariant to these variations.
- **Evidence anchors:**
  - `[section 6]` Defines invariants: Uniqueness, Equivalence Collapse (`Canon(I1)=Canon(I2)` for semantic equivalence), Determinism, Binding.
  - `[section 10.3]` Case studies show tool-local checks fail because "semantically identical refund intents may produce syntactically distinct tool invocations."
  - `[corpus]` Weak; "Unified Tool Integration" proposes protocol abstraction but does not normalize for authorization semantics.
- **Break condition:** Underspecified or ambiguous intents that cannot be resolved into a single, stable canonical form; representational drift outside the canonicalizer's equivalence rules.

### Mechanism 3
- **Claim:** Provenance-complete decision records with hash-chaining enable replayable audit and deterministic re-evaluation without re-running agent reasoning.
- **Mechanism:** Each decision `d` is recorded immutably as `r_i = (seq_i, h_A, v_P, h_S, d, t_i, prev_hash_i)`, binding the canonical hash `h_A=H(A)`, policy version `v_P`, and state digest `h_S=H(S)`. Replay uses `(A, P, S)` resolved from these references.
- **Core assumption:** Governance requires binding authorization outcomes to evaluation context; execution logs alone are insufficient for counterfactual analysis.
- **Evidence anchors:**
  - `[section 9]` "Decision-centric provenance" captures `(A, P, S) → d`; logs are "append-only, causally ordered" with hash chaining.
  - `[section 10.3]` "Execution logs answer 'what happened'; provenance records answer 'why it was allowed'."
  - `[corpus]` Weak; in-toto and Sigstore provide artifact provenance but not execution-time authorization context binding.
- **Break condition:** Loss of policy snapshots (`v_P`), state digests (`h_S`), or corruption of the hash chain that breaks tamper evidence.

## Foundational Learning
- **Concept: Deterministic Evaluation in Distributed Systems**
  - Why needed here: Guarantees that identical canonical actions under identical policy/state yield identical decisions, enabling replay and audit. Without determinism, counterfactual analysis is ill-defined.
  - Quick check question: If two agent intents are semantically equivalent but syntactically different, must the authorization decision be identical? What ensures this?

- **Concept: Immutable, Hash-Chained Audit Logs**
  - Why needed here: Provides tamper-evidence and ordered retrieval for replay. Append-only chaining ensures deletions/reorderings are detectable, which is essential for forensic reconstruction.
  - Quick check question: Why is a simple timestamped log insufficient for replayable provenance? What does the `prev_hash` field add?

- **Concept: Canonicalization as a Normalization Boundary**
  - Why needed here: Removes representational noise from agent outputs, creating a stable unit of control. This is analogous to normalized transactions in databases or canonical requests in distributed systems.
  - Quick check question: How does canonicalization differ from schema validation? Why is collapsing semantic equivalence (e.g., parameter reordering) necessary for deterministic authorization?

## Architecture Onboarding
- **Component map:**
  Agent → Canonicalizer → Action Authorization Boundary (AAB) → Decision Log → Executor
  (Policy/State Store provides inputs to AAB)
- **Critical path:** Intent generation → Canonicalization → AAB Evaluation → Decision record → (if PERMIT) Artifact issuance → Executor validation → Side-effect execution.
- **Design tradeoffs:**
  - **Latency vs. determinism:** Synchronous blocking ensures fail-closed but adds `T_canon + T_eval + T_record`. Deferred approval shifts latency but preserves decision semantics.
  - **Policy centralization vs. multi-tenancy:** Shared control plane simplifies management but requires strict tenant isolation (`P_t`, `S_t` disjoint) to prevent bleed-through.
  - **Protocol independence vs. integration cost:** Treating MCP/A2A as pure transport avoids semantic coupling but requires all agents to adopt the canonicalization boundary.
- **Failure signatures:**
  - **Bypass:** Execution without a preceding decision record or with a mismatched `h_A` (direct tool call, stale token).
  - **Non-determinism:** Same `A` yields different `d` under identical `(P, S)` (indicates policy/state inconsistency or broken canonicalization).
  - **Provenance gap:** Missing `v_P` or `h_S` in record; breaks replay.
  - **Fail-open:** System allows execution when `B` times out or state is unavailable (violates core invariant).
- **First 3 experiments:**
  1. **Semantic equivalence collapse:** Generate `M` syntactic variants of the same intent (reordered params, aliases). Verify all produce identical `A` and `h_A`. Check that authorization decisions are identical across variants.
  2. **Policy evolution replay:** Record a `PERMIT` decision at `t0`. Update policy `P0 → P1` (tighten rules). Replay `A` with `(P1, S)`. Expect `DENY` or `DEFER`. Confirms replay sufficiency.
  3. **Bypass resistance:** Attempt direct tool invocation, alternate SDK route, cached token replay, concurrent duplicate execution. Measure coverage (`1 - bypass_success_rate`). Should approach `1.0` under correct placement.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can we automatically verify that an authorization policy P, when evaluated over canonical actions A, correctly implements intended governance rules?
- **Basis in paper:** [explicit] Section 13.1 declares policy correctness a non-goal and states that guaranteeing policy correctness is out of scope.
- **Why unresolved:** Ensuring policy correctness requires semantic interpretation of P and its alignment with high-level objectives, which is excluded from the trusted computing base to preserve determinism and replayability.
- **What evidence would resolve it:** A sound and complete policy analysis framework that can prove equivalence between P and a reference specification for all possible (A, S) inputs.

### Open Question 2
- **Question:** How can we systematically construct a canonicalization function Canon(·) that provably satisfies the Equivalence Collapse invariant for all semantically equivalent agent intents?
- **Basis in paper:** [inferred] The paper mandates the invariant (Section 6.3.1) but provides no general method beyond illustrative examples, leaving the implementation of a complete canonicalizer open.
- **Why unresolved:** Without a guaranteed complete Canon, semantically equivalent actions may produce different canonical forms, undermining determinism and replayability.
- **What evidence would resolve it:** An algorithm that, given a formal model of tool schemas and equivalence rules, generates a Canon function accompanied by a machine-checkable proof of Equivalence Collapse.

### Open Question 3
- **Question:** Is it fundamentally impossible to guarantee the safety of an agent's underlying intent at execution time without either including agent reasoning in the trusted computing base or sacrificing autonomy?
- **Basis in paper:** [explicit] Lemma 13.1 and Section 13.2.1 establish that intent correctness is undecidable post-canonicalization under the invariants.
- **Why unresolved:** The paper proves a trade‑off: preserving determinism and policy‑agnosticism precludes judging intent correctness, raising the question of whether this is an absolute limitation or if a circumventing mechanism exists.
- **What evidence would resolve it:** Either a constructive scheme that safely integrates intent verification without violating invariants or a strengthened impossibility proof confirming the trade‑off as inherent.

### Open Question 4
- **Question:** How can we automatically verify that the AAB is correctly placed so that all effectful execution paths in a deployed system are mediated, ensuring non‑bypassability?
- **Basis in paper:** [explicit] Section 13.3.1 and Lemma 13.5 state that non‑bypassability requires correct placement but provide no verification technique.
- **Why unresolved:** Complex deployments may contain hidden execution channels (direct tool calls, fallbacks) that bypass the AAB; detecting such bypasses requires analysis beyond the architectural specification.
- **What evidence would resolve it:** A static or dynamic analysis tool that, given code and configuration, can prove that every side‑effecting operation passes through the AAB or at least enumerates potential bypass paths.

## Limitations
- Unspecified details: canonical schema semantics (blast radius, context), policy language, state digest method, artifact format, concurrency control, bypass operationalization.
- Single-node evaluation; scalability and distributed behavior unproven.
- Coverage claim assumes perfect instrumentation across all tool families.
