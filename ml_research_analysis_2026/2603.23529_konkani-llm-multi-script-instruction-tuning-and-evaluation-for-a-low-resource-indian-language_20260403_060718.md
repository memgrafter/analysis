# Konkani LLM: Multi-Script Instruction Tuning and Evaluation for a Low-Resource Indian Language

## Quick Facts
*   **arXiv ID:** 2603.23529
*   **Source URL:** https://arxiv.org/abs/2603.23529
*   **Reference Count:** 40
*   **Primary Result:** A synthetic, multi-script instruction dataset (`Konkani-Instruct-100k`) and resulting LoRA-tuned models (e.g., `konkani-Qwen2.5-14B-Instruct`) achieve state-of-the-art performance in translation (COMET 83.58) and transliteration (chrF++ up to 81.41), dramatically closing the gap with proprietary systems for the low-resource language Konkani.

## Executive Summary
Konkani is a low-resource Indian language written in multiple scripts (Devanagari, Romi, Kannada), leading to significant underperformance by existing LLMs. This paper addresses this by creating a large-scale, synthetic instruction-tuning dataset covering all three scripts using a teacher model (Gemini 3). Through parameter-efficient LoRA fine-tuning on several open-weight models (Llama 3.1, Qwen2.5, Gemma 3), the authors develop specialized Konkani LLMs. Evaluations on a new 200-sample translation benchmark and script transliteration tasks show substantial improvements over base models, with the best model (`konkani-Qwen2.5-14B-Instruct`) achieving competitive scores against much larger proprietary systems, demonstrating a viable path for adapting LLMs to multi-script, low-resource languages.

## Method Summary
The core method involves generating a large, diverse instruction-tuning dataset for Konkani using the Gemini 3 API, with prompts explicitly specifying the target script (Devanagari, Romi, Kannada) to ensure coverage. This `Konkani-Instruct-100k` dataset is then used to fine-tune base models via Low-Rank Adaptation (LoRA), a parameter-efficient technique that updates a small subset of model weights. The resulting models are evaluated on two primary tasks: translation (using a new 200-sentence benchmark into Konkani) and transliteration (between the three scripts), using automatic metrics (COMET, chrF++) and LLM-as-judge assessments for script fidelity and helpfulness.

## Key Results
*   The `konkani-Qwen2.5-14B-Instruct` model achieves a COMET score of **83.58** on the translation benchmark, a massive improvement over its base model's 56.90 and competitive with leading proprietary systems.
*   For transliteration, the same model reaches a **chrF++ score of 81.41** on the Romi→Devanagari pair, far exceeding its base model's 25.77 and outperforming many larger proprietary models on this specific task.
*   LLM-as-judge evaluations confirm that tuned models show significantly improved script fidelity (adherence to the requested script) and task helpfulness across diverse instructions compared to base models.

## Why This Works (Mechanism)
The performance gains stem from two synergistic factors. First, the synthetic `Konkani-Instruct-100k` dataset provides the model with extensive, script-targeted exposure to the linguistic patterns, vocabulary, and orthographic variations of Konkani across all three scripts, a coverage absent in the base model's pre-training data. Second, LoRA fine-tuning efficiently specializes the model's internal representations for Konkani without catastrophic forgetting or the immense computational cost of full fine-tuning, allowing the model's general reasoning capabilities to be rapidly adapted to the specific linguistic and scriptural constraints of the target language.

## Foundational Learning
*   **Low-Resource Language Adaptation:** The challenge of improving LLM performance for languages with scarce digital resources. *Why needed:* Base LLMs are overwhelmingly trained on high-resource languages, leaving low-resource languages significantly behind. *Quick check:* Measure performance delta between a base model and a fine-tuned variant on a small, held-out set of native text.
*   **Multi-Script Handling:** Managing languages that use multiple, distinct writing systems (e.g., Devanagari, Roman). *Why needed:* Script choice is often sociolinguistically significant, and models must produce coherent text in the requested script. *Quick check:* Prompt a model to generate a paragraph in each script and evaluate script-specific character set usage and orthographic rules.
*   **Instruction Tuning:** Training models to follow natural language instructions. *Why needed:* To make LLMs useful and controllable for end-users, moving beyond pure next-token prediction. *Quick check:* Test if a model correctly executes a novel, compositional instruction not seen during training.
*   **Parameter-Efficient Fine-Tuning (PEFT) / LoRA:** Methods that update only a small subset of model parameters. *Why needed:* Makes fine-tuning large models feasible with limited resources and reduces the risk of overfitting on small datasets. *Quick check:* Compare the parameter count and training cost of full fine-tuning versus LoRA for a given model size and dataset.
*   **Synthetic Data Generation for LLMs:** Using a powerful "teacher" model to create training data. *Why needed:* Scales dataset creation for low-resource languages where human-labeled data is prohibitively expensive. *Quick check:* Perform a small human evaluation of a random sample of generated data for fluency, correctness, and diversity.
*   **Evaluation Metrics for Translation/Transliteration:** COMET for translation quality (considering meaning), chrF++ for character-level transliteration accuracy. *Why needed:* Provides standardized, automated ways to compare system performance. *Quick check:* Compute metrics on a small, gold-standard human-translated/transliterated set to establish a performance ceiling.

## Architecture Onboarding
**Component Map:**
Teacher Model (Gemini 3) -> Synthetic Data Generator -> Konkani-Instruct-100k -> LoRA Fine-Tuning Module (applied to Base LLM: Llama 3.1 / Qwen2.5 / Gemma 3) -> Konkani-Specialized LLM -> Evaluation Harness (Translation/Transliteration Benchmarks, LLM-as-judge)

**Critical Path:** The pipeline's success hinges on the quality and script diversity of the synthetic data generation step, as it directly determines what the model learns during the subsequent, more efficient LoRA fine-tuning stage.

**Design Tradeoffs:**
*   **Synthetic Data Scale vs. Quality:** Generating 100k+ examples ensures broad coverage but risks propagating systematic errors or non-native constructions from the teacher model without human oversight.
*   **LoRA Rank (r) vs. Performance:** A higher LoRA rank allows for more substantial adaptation but increases trainable parameters and risk of overfitting on a single-domain dataset; a lower rank is more efficient but may under-fit.
*   **Model Size vs. Efficiency:** Larger base models (14B) have more capacity to learn but require more memory and computation for fine-tuning and inference, potentially unsuitable for deployment in resource-constrained settings.

**Failure Signatures:**
*   **Script Collapse:** Model output mixes scripts or defaults to a single script (likely Devanagari) regardless of instruction.
*   **Metric Disparpancy:** Large gap between automatic metric (COMET/chrF++) and LLM-as-judge scores, indicating the model is getting "right" answers for the wrong reasons (e.g., copying source text).
*   **Task Degradation:** Performance on general reasoning or other languages (in the base model) decreases significantly after fine-tuning, indicating catastrophic forgetting.

**First Three Experiments:**
1.  **Ablation - Script-Specific Tuning:** Fine-tune a base model on only the Devanagari portion of the dataset and evaluate performance on all three scripts to isolate the impact of multi-script training data.
2.  **LoRA Rank Sensitivity:** Perform a sweep over LoRA rank values (e.g., 8, 16, 32, 64) on a single base model to find the optimal efficiency/performance trade-off for this specific dataset size and task.
3.  **Teacher Model Comparison:** Generate a small, comparable dataset subset using a different teacher model (e.g., GPT-4o) and compare the fine-tuned model performance to assess sensitivity to the choice of synthetic data generator.

## Limitations
*   **Dataset Quality Uncertainty:** The core 100k+ synthetic dataset lacks reported human evaluation for fluency, cultural appropriateness, or script accuracy, risking the propagation of errors from the Gemini 3 teacher model.
*   **Benchmark Scale & Scope:** The translation benchmark is very small (200 samples) and may not capture the full diversity of Konkani's multi-script usage; transliteration evaluation is limited to specific script pairs.
*   **Evaluation Proxy Reliance:** Primary qualitative evaluation (script fidelity, helpfulness) uses LLM-as-a-judge, a method with known biases and poor correlation with human judgment, especially for low-resource languages.

## Confidence
*   **Substantial Translation Gains:** High (Supported by clear, standardized COMET metric on a defined benchmark, showing large delta over base models).
*   **Strong Transliteration Performance:** Medium (Supported by chrF++, but confidence limited by narrow script pair testing and lack of comparison to dedicated transliteration systems).
*   **Improved Script Fidelity & Helpfulness:** Medium (Supported by LLM-as-judge, but judge reliability for this context is low).
*   **Generalization to Other Low-Resource Languages:** Low (Study is specific to Konkani; transferability claims are speculative without cross-lingual validation).

## Next Checks
1.  Conduct a human evaluation (n=500+) on a stratified sample of `Konkani-Instruct-100k` for fluency, cultural relevance, and script correctness across all three scripts.
2.  Replicate the entire pipeline (synthetic data generation + LoRA tuning) on another multi-script low-resource Indic language (e.g., Rajasthani, Bhojpuri) to test method portability and performance variance.
3.  Perform a fine-grained error analysis on the 200-sample translation benchmark, categorizing errors by script-specific phenomena, source language, and model size to diagnose where gains are concentrated.
