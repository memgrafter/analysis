# OptiML: An End-to-End Framework for Program Synthesis and CUDA Kernel Optimization

## Quick Facts
- arXiv: 2602.12305
- Source: https://arxiv.org/abs/2602.12305
- References: 40
- Primary result: Unifies program synthesis and optimization to generate high-performance CUDA kernels, achieving up to 1.64× speedup over GPT-5.1 on matrix multiplication.

## Executive Summary
OptiML is a two-stage framework for generating and optimizing CUDA kernels from natural language specifications or existing code. The first stage, OptiML-G, uses a Mixture-of-Thoughts generator that routes queries to frozen expert models via learned cross-attention, producing an initial executable kernel. The second stage, OptiML-X, applies Monte Carlo Tree Search guided by a composite reward derived from Nsight Compute profiling, including runtime improvement, hardware utilization proxies, and an LLM-as-a-Judge, with guardrails against regressions. Evaluated on a diverse CUDA kernel suite, OptiML demonstrates consistent verified speedups over LLM baselines and post-hoc optimization alone, with faster convergence when starting from OptiML-G.

## Method Summary
OptiML-G trains only a router and interaction layers (projectors and cross-attention) over frozen expert models (Qwen2.5-Coder-7B, HPC-Coder-V2-6.7B, StarCoder2-7B) using a mixture-of-experts approach with cross-attention at layer boundaries. The training uses an LM loss plus regularization for entropy, load-balancing, and consistency. OptiML-X performs MCTS with a budget of 6 iterations: each step selects a node via UCT (α=1.4), diagnoses the bottleneck, proposes a patch via an LLM, compiles and tests the candidate, profiles with Nsight Compute, judges correctness and performance with an LLM-as-a-Judge, computes a composite reward (weighted sum of time improvement, proxy metrics, LLM judgment, minus guardrail penalties), and backpropagates. The final selection chooses the best candidate that passes correctness tests and improves runtime.

## Key Results
- Matrix multiplication: 1.64× speedup over GPT-5.1 (4.40s vs. 7.20s), SM SOL ↑ from 71.26% to 81.17%, instruction count ↓ from 419 to 381.
- 5-task subset: full OptiML achieves 85% Pass@1 and 1.30× geometric mean speedup, beating pure generation (40% Pass@1, 1.00×) and OptiML-X on baselines (70-85% Pass@1, up to 1.24×).
- Search converges faster with OptiML-G initialization, requiring fewer MCTS rounds to reach optimal candidates.

## Why This Works (Mechanism)
The combination of a specialized generator (OptiML-G) and iterative, hardware-aware refinement (OptiML-X) addresses both the initial code generation and subsequent optimization challenges. OptiML-G leverages multiple expert models through a learned router to produce a more promising starting point than any single model. OptiML-X then systematically explores transformation space using MCTS, guided by a reward that balances raw runtime with low-level hardware metrics and an LLM-based correctness judge. The guardrails prevent the search from degrading key performance counters, ensuring that improvements are real and not just proxy exploitation. This two-stage approach reduces the search burden and yields kernels that are both correct and high-performing.

## Foundational Learning
These concepts underpin OptiML’s design:

- **Mixture-of-Experts (MoE)**: Why needed: To combine strengths of multiple pretrained models without full retraining. Quick check: Does the router learn to assign queries to the most suitable expert? Measure load balancing and task-specific expert utilization.
- **Monte Carlo Tree Search (MCTS)**: Why needed: To efficiently explore a large space of kernel transformations with limited evaluations. Quick check: Does increasing the budget improve results? Measure convergence with varying B.
- **Hardware-Aware Performance Modeling**: Why needed: Optimization must target real hardware metrics (e.g., SM utilization) to achieve speedups. Quick check: Do proxy metrics correlate with runtime? Compute correlation between SM SOL and actual speedup across candidates.
- **LLM-as-a-Judge**: Why needed: Automated correctness assessment beyond unit tests, catching subtle errors. Quick check: Does the judge agree with human evaluation on a sample? Compare judge decisions on a held-out set.
- **Program Synthesis via LLMs**: Why needed: Generate initial code from natural language. Quick check: How does generation quality vary with prompt? Ablate prompt components and measure Pass@1.
- **Guardrails against Regression**: Why needed: Prevent the optimizer from degrading metrics that would ultimately hurt performance. Quick check: How often do candidates violate guardrails? Track the proportion of discarded candidates due to each guardrail.

## Architecture Onboarding
Component map (simplified):
Natural language spec or CUDA code -> OptiML-G (router + expert selection + generation) -> Initial kernel -> OptiML-X (MCTS loop: node selection -> bottleneck diagnosis -> patch proposal -> compile/test/profile -> reward computation -> backpropagation) -> Final optimized kernel.

Critical path: For natural language input, the flow goes through both stages; for existing CUDA code, it goes directly to OptiML-X.

Design tradeoffs:
- Using frozen experts reduces training cost but limits adaptation; training only the router is a compromise.
- MCTS budget (B=6) bounds search cost but may miss deeper transformations; larger budgets risk overfitting to noisy profiles.
- Composite reward weights (β_time, β_proxy, β_llm) balance runtime vs. proxies vs. correctness; misweighting could lead to proxy exploitation.

Failure signatures:
- Compilation failure: candidate cannot be built; repair loop may fix, but persistent failure leads to discard.
- Correctness failure: passes basic tests but fails on extended cases or exhibits nondeterminism; L2 tests help but may miss subtle bugs.
- Proxy exploitation: candidate improves utilization/work metrics but not runtime; guardrails aim to prevent this, but reliance on time dominance is key.
- Local minima: MCTS may not escape without sufficient exploration; UCT α helps but budget is limited.

## Open Questions the Paper Calls Out
1. How can OptiML be extended to optimize whole applications with multiple interacting CUDA kernels, enabling cross-kernel fusion, scheduling, and memory planning?
2. Can the reliance on expensive runtime profiling (Nsight Compute) be reduced by integrating static analysis or learned performance predictors without sacrificing optimization quality?
3. How well does the OptiML approach transfer to other accelerator programming models such as HIP/ROCm, SYCL, or Triton?
4. What enhancements to the correctness verification harness are needed to ensure that OptiML-X does not produce kernels that pass L0/L1 tests but still contain subtle numerical errors or race conditions?
