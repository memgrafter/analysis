# Arabic Prompts with English Tools: A Benchmark

## Quick Facts
*   **arXiv ID:** 2601.05101
*   **Source URL:** https://arxiv.org/abs/2601.05101
*   **Reference Count:** 32
*   **Primary Result:** Evaluating five open-source models on a translated Arabic benchmark reveals a severe, statistically significant 5–10% accuracy drop when user prompts are in Arabic, with a further compounding penalty when tool definitions are also Arabic.

## Executive Summary
This paper addresses the absence of dedicated evaluation frameworks for Arabic language tool-calling in LLMs. The authors adapt the English-centric Berkeley Function Calling Leaderboard (BFCL) by translating its queries, function definitions, and system prompts into Arabic. They evaluate five open-source models across a matrix of language variations (system, query, function description) and invocation styles. The core finding is a consistent and significant performance degradation for Arabic user prompts, indicating a strong English bias in current models' agentic capabilities. Complex multi-step tasks are disproportionately affected, highlighting a key fragility in multilingual tool-use.

## Method Summary
The study's method is an evaluation framework, not a training procedure. It builds an Arabic test suite by translating the original BFCL dataset's components (user queries, function schemas, system prompts) using automated translation with minimal human quality assurance. This creates a parallel corpus covering 14 task categories. Models are then evaluated on a 2×2×2 matrix (varying the language of the system prompt, user query, and function description) and two invocation styles (native function calling vs. prompt-based generation). Performance is measured using Abstract Syntax Tree (AST) matching to compare predicted function calls against ground truth. The experimental pipeline uses vLLM on NVIDIA L4 GPUs for inference.

## Key Results
*   A severe, statistically significant (p<0.05) average accuracy drop of 5–10% occurs for all models when user queries are in Arabic, irrespective of tool description language.
*   A "compounding language penalty" is observed: performance degrades further when both the user query and the function definitions are in Arabic.
*   Complex, multi-step, parallel, and multi-turn tasks exhibit the largest performance fragility under Arabic prompting, with accuracy often halving compared to English baselines.

## Why This Works (Mechanism)

### Mechanism 1: Pretraining Bias in Core Reasoning
*   **Claim:** Performance degrades for Arabic user prompts because the model's internal reasoning and tool-selection logic are fundamentally tuned to English linguistic patterns from pretraining.
*   **Mechanism:** Pretraining on predominantly English data creates stronger internal representations and activation pathways for English semantics. An Arabic query must be processed through a less-optimized linguistic pipeline, leading to semantic drift or incomplete comprehension before the tool-mapping stage, even if tool definitions are in English.
*   **Evidence Anchors:** Abstract states models are "pretrained on predominantly English data." Section IV.A & Fig.6 show English-based prompts win in 350 test cases vs. 10 for Arabic.
*   **Break Condition:** A model trained with significant high-quality Arabic tool-calling data shows no significant performance gap between Arabic and English prompts (p > 0.05).

### Mechanism 2: Compounding Language Penalty in Schema Matching
*   **Claim:** A compounding penalty occurs because the model's tool-matching process is optimized for English-to-English mapping; an Arabic-to-Arabic mapping introduces a second point of failure in parsing the tool schema.
*   **Mechanism:** The model likely translates the Arabic query into an internal (English-biased) representation to match against tool *intent*. When tool definitions are also Arabic, the model must match two Arabic representations that are both outside its high-fidelity representation space, doubling the chance of misalignment.
*   **Evidence Anchors:** Section IV.D describes the penalty with Fig.10 showing blue points (Arabic tools) uniformly lower than orange (English tools) for Arabic queries. Section IV.C.2 confirms providing functions in English is "vastly superior."
*   **Break Condition:** Arabic query + Arabic tool descriptions consistently outperforms Arabic query + English tool descriptions.

### Mechanism 3: Cascading Errors in Complex Workflows
*   **Claim:** Complex, multi-step, and parallel tool-calling tasks are disproportionately fragile under Arabic prompting due to higher cognitive load where linguistic drift accumulates.
*   **Mechanism:** Tasks requiring multiple calls or long-context memory demand precise understanding and retention. Inefficiencies in Arabic processing cause error propagation across these extended steps.
*   **Evidence Anchors:** Section IV.E states Multi-Turn tasks are "exceptionally difficult" with Arabic accuracy often <20%. Fig.10 clusters diamonds (Multi-Turn) and squares/crosses (Parallel/Multiple) at the bottom-left.
*   **Break Condition:** The performance gap (English vs. Arabic) for Simple tasks is statistically indistinguishable from the gap for Parallel/Multi-Turn tasks.

## Foundational Learning
*   **Concept: Multilingual Tokenization & Embedding Space**
    *   **Why needed:** A suboptimal tokenizer (e.g., splitting Arabic into many sub-tokens) leads to less efficient representation and higher perplexity, cascading into tool-calling errors.
    *   **Quick Check:** How does the tokenizer's vocabulary size and training language distribution affect the model's ability to generate a syntactically correct JSON function call from an Arabic prompt?
*   **Concept: Function Calling Architecture (Native FC vs. Prompt-Based)**
    *   **Why needed:** The similar gaps in both invocation styles suggest a core reasoning problem, not just a fine-tuning artifact specific to a native API.
    *   **Quick Check:** What architectural components (e.g., specialized tokens, PPO tuning) differentiate native FC from general instruction-following, and which is more susceptible to language bias?
*   **Concept: Evaluation Metric for Agentic Workflows (AST Matching)**
    *   **Why needed:** The strict AST metric may disproportionately penalize Arabic outputs for semantically equivalent variations (numeral forms, synonyms, localized formats).
    *   **Quick Check:** For an Arabic parameter value like "خمسة" (five), would AST matching fail if the ground truth uses "٥"? What does this imply about the measured accuracy drop?

## Architecture Onboarding
1.  BFCL Source Dataset -> 2. Translation Pipeline -> 3. Experiment Matrix Generator -> 4. Model Inference Engine -> 5. Evaluator (AST Matching) -> 6. Analysis Suite (Stats, Plots)
*   **Critical Path:** Translation Quality -> Experimental Matrix Completion -> Inference Execution -> AST Comparison -> Statistical Analysis.
*   **Design Tradeoffs:**
    *   *Translation Fidelity vs. Scale:* Used automated translation with minimal human review for scalability, risking loss of nuance and functional equivalence.
    *   *Model Selection Breadth vs. Depth:* Evaluated 5 open-source models for focus, limiting generalization to Arabic-native or closed-source models.
    *   *Task Generalization:* Direct translation of English-centric tasks provides clean comparison but misses Arabic-specific agentic workflows.
*   **Failure Signatures:**
    *   **Data Pipeline:** High post-translation rejection rate in human QA indicates poor translation quality.
    *   **Inference:** Repeated crashes/timeouts on Arabic prompts for specific models may indicate tokenization/generation issues.
    *   **Evaluation:** Atypically high "tie" rate or uniformly low accuracy across *all* language variations suggests an AST matching flaw.
    *   **Analysis:** Non-significant p-values for the User Query Language axis would contradict the primary claim.
*   **First 3 Experiments:**
    1.  **Baseline Sanity Check:** Run the original English BFCL evaluation on all models using Native FC. Verify alignment with published leaderboards.
    2.  **Single-Variable Isolation:** For one simple task, run all 8 language combinations for one model. Plot (English Query, English Tools) vs. (Arabic Query, English Tools).
    3.  **Compounding Penalty Test:** For the same simple task, compare (Arabic Query, English Tools) vs. (Arabic Query, Arabic Tools).

## Open Questions the Paper Calls Out
*   **How can we construct a native Arabic tool-calling benchmark?** A collaboratively built benchmark with native speakers, covering diverse dialects and culturally grounded tasks, is needed instead of relying on translation.
*   **What specific multilingual fine-tuning approaches can close the gap?** Systematic comparison of strategies (cross-lingual alignment, code-switching data) on the Arabic benchmark is required to identify effective interventions.
*   **What are the root causes of the English-centric bias and compounding penalty?** Ablation studies are needed to isolate whether tokenization, pre-training data bias, or internal representations are the primary drivers.

## Limitations
*   **Translation Pipeline Fidelity:** The dataset relies on automated translation with unspecified tools and minimal human QA. Poor translation quality could artificially inflate performance gaps.
*   **Model & Task Scope:** Findings are limited to five specific open-source models and translated English-centric tasks, not generalizing to Arabic-native models or authentic Arabic agentic scenarios.
*   **Evaluation Metric Strictness:** AST matching is binary and cannot account for semantically equivalent Arabic variations, likely overstating the functional deficiency.

## Next Checks
1.  **Translation Quality Audit:** Manually review a stratified sample of translated data with native speakers. Re-run evaluation on a high-quality subset to measure sensitivity to translation noise.
2.  **Closed-Source Model Benchmark:** Replicate the core 2x2x2 matrix for leading APIs (GPT-4-Turbo, Claude-3-Opus) to test universality vs. open-source model specificity.
3.  **Metric Relaxation Study:** Implement a secondary metric allowing semantic equivalence (numeral variants, synonyms). Re-calculate gaps to isolate functional failure from surface-form matching issues.
