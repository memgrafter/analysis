# Evaluate-as-Action: Self-Evaluated Process Rewards for Retrieval-Augmented Agents

## Quick Facts
- **arXiv ID**: 2603.09203
- **Source URL**: https://arxiv.org/abs/2603.09203
- **Reference Count**: 35
- **Primary Result**: EvalAct achieves state-of-the-art average exact match across seven open-domain QA benchmarks, with significant gains (+10.6 pts) on multi-hop tasks using a 3B model.

## Executive Summary
Retrieval-augmented agents often fail in multi-step reasoning because noisy search results propagate errors, and standard reinforcement learning provides only sparse, outcome-level rewards. This paper introduces Evaluate-as-Action (EvalAct), which transforms the implicit assessment of retrieval quality into an explicit `Evaluate` action. This enforces a strict `Search → Evaluate` cycle, generating dense, step-aligned process rewards. To effectively use these self-generated signals, Process-Calibrated Advantage Rescaling (PCAR) adjusts segment-level advantages based on the evaluation scores, highlighting reliable steps. On seven QA benchmarks, EvalAct sets a new average performance ceiling, with the strongest improvements on complex, multi-hop questions.

## Method Summary
EvalAct modifies the action space of a retrieval-augmented agent to include an explicit `Evaluate` step that immediately follows each `Search` action. The model itself produces a self-evaluation score (z) for the retrieved context. During reinforcement learning training (using GRPO), these scores are used to compute Process-Calibrated Advantage Rescaling (PCAR). PCAR rescales the advantage of each reasoning segment (a `Search` followed by its `Evaluate`) by the corresponding self-evaluation score. This mechanism amplifies gradients for steps the model deems high-quality and attenuates them for low-quality steps, providing a denser and more aligned training signal than using only the final outcome. The method typically requires an initial phase of supervised fine-tuning (SFT) to teach the agent the coupled `Search→Evaluate` protocol before RL fine-tuning.

## Key Results
- EvalAct achieves the best average Exact Match (EM) accuracy across seven open-domain QA benchmarks.
- Largest gains are on multi-hop reasoning tasks, e.g., +10.6 EM points on 2WikiMultihopQA with a 3B backbone.
- Ablation studies confirm the explicit `Evaluate` action loop is the primary driver of improvements, with PCAR providing consistent additional gains.

## Why This Works (Mechanism)
The core issue is credit assignment in long, noisy trajectories. Outcome-only RL (like GRPO) only indicates if the final answer was correct, not which retrieval steps contributed. EvalAct addresses this by forcing the agent to explicitly judge each retrieval's utility via the `Evaluate` action. This converts a latent, implicit process (deciding if a retrieved doc is useful) into an observable, trainable action. The generated self-evaluation score (z) serves as a dense, per-step proxy for retrieval quality. PCAR then leverages these z-scores to weight the advantage function at the segment level, effectively up-weighting learning from trajectories the model itself identifies as reliable and down-weighting noisy segments. This creates a self-correcting loop where the policy learns to both retrieve better and better assess its own retrievals.

## Foundational Learning
- **Retrieval-Augmented Generation (RAG)**: augments a language model's context with external documents to improve factuality. *Why needed*: Forms the base agent architecture where EvalAct's actions are inserted. *Quick check*: Does the agent's performance degrade significantly when retrieved docs are noisy?
- **Reinforcement Learning from Outcome Rewards (RL)**: optimizes a policy using only a final sparse reward (e.g., answer EM). *Why needed*: Standard RL's coarse credit assignment is the problem EvalAct solves. *Quick check*: Compare GRPO performance with and without dense process rewards on a held-out set.
- **Process Supervision / Process Reward Models (PRMs)**: provide step-level feedback, often from a separate model or human. *Why needed*: EvalAct implements a self-supervised form of process supervision where the agent is its own PRM. *Quick check*: Are self-evaluation scores (`z`) correlated with an external judge's assessment of step helpfulness?
- **Advantage Function in Policy Gradient Methods**: estimates how much better an action is than the expected baseline. *Why needed*: PCAR modifies this core RL component using self-evaluation scores. *Quick check*: Is the variance of advantages reduced after PCAR rescaling?
- **Action Space Augmentation**: expanding the set of possible actions an agent can take. *Why needed*: Adding `Evaluate` as a discrete action is the key architectural change. *Quick check*: Does the model learn to emit `Evaluate` tokens at the expected frequency after SFT?
- **Coupling in Agent Protocols**: enforcing a fixed order of operations (Search then Evaluate). *Why needed*: Prevents the agent from skipping self-assessment, ensuring process traces are complete for PCAR. *Quick check*: What percentage of `Search` actions are immediately followed by `Evaluate` during inference?

## Architecture Onboarding
**Component Map**
Retriever -> Search Action -> Evaluate Action (produces z) -> [Search+Evaluate Segment] -> PCAR Rescaling -> Policy Gradient Update (GRPO)

**Critical Path**
During training, for a given query: 1) The policy generates a `Search` query. 2) The fixed retriever returns documents. 3) The policy generates an `Evaluate` action and a self-evaluation score `z` for those docs. 4) This `(Search, Evaluate, z)` segment is stored. 5) After a trajectory completes, PCAR rescales each segment's advantage by its `z`. 6) The policy (LLM) is updated via GRPO using these rescaled advantages. During inference, the coupled `Search→Evaluate` cycle is repeated as needed until a final answer is generated.

**Design Tradeoffs**
- **Overhead vs. Accuracy**: Adding an `Evaluate` step increases token generation cost and latency but yields significant accuracy gains on complex tasks.
- **Self-Evaluation Reliability**: The method's success hinges on the model's ability to produce well-calibrated `z` scores. Miscalibration could harm learning.
- **Protocol Rigidity vs. Flexibility**: The enforced `Search→Evaluate` coupling ensures dense signals but may prevent the agent from skipping obvious evaluations, potentially wasting computation.

**Failure Signatures**
- **Protocol Breakdown**: Model emits `Evaluate` without a preceding `Search`, or fails to `Evaluate` after `Search`, indicating SFT/RL failure to learn the coupled protocol.
- **Miscalibrated `z`**: High `z` scores consistently assigned to retrievals that are later contradicted in the reasoning chain, or low `z` on retrievals that lead to correct answers.
- **PCAR Mis-scaling**: If advantage rescaling causes gradient explosion or vanishing for specific segments, suggesting `z` distribution issues.

**First Three Experiments**
1. **Protocol Compliance Check**: After SFT, sample 100 trajectories and manually verify the `Search→Evaluate` coupling is followed >98% of the time. Measure `Evaluate` token frequency distribution.
2. **Self-Evaluation Calibration Probe**: On a held-out set, correlate self-evaluation scores `z` with an oracle metric (e.g., retrieval relevance to gold documents or downstream answer correctness). Compute Expected Calibration Error (ECE).
3. **Ablation of SFT Warm-up**: Train EvalAct from scratch with RL-only (no SFT) using increased rollout budgets (e.g., 10x more) and a more sample-efficient RL algorithm (e.g., PPO). Compare final EM and protocol compliance to the SFT-initialized version.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: Are the self-evaluation scores (z) well-calibrated with respect to actual retrieval quality, and does miscalibration harm PCAR’s gradient updates?
- **Basis in paper**: [inferred] The method relies on self-evaluation scores for advantage rescaling but does not analyze their calibration against oracle retrieval utility.
- **Why unresolved**: Miscalibrated scores could distort credit assignment, amplifying gradients for poor retrievals or suppressing good ones.
- **What evidence would resolve it**: Compute calibration error (e.g., Expected Calibration Error) of self-evaluation scores against ground-truth retrieval relevance on a held set; run ablations with artificially calibrated vs. miscalibrated scores.

### Open Question 2
- **Question**: Is per-search evaluation (i.e., Evaluate after every Search) necessary, or could less frequent evaluation maintain accuracy with lower overhead?
- **Basis in paper**: [inferred] The protocol strictly couples Search→Evaluate, but no ablation on evaluation frequency is reported.
- **Why unresolved**: Evaluating after every retrieval adds token cost and latency; some retrievals may be obviously good/bad, making frequent evaluation redundant.
- **What evidence would resolve it**: Ablate evaluation frequency (e.g., evaluate every 1, 2, 3 searches) on multi-hop benchmarks, measuring both exact match accuracy and computational cost (tokens, latency).

### Open Question 3
- **Question**: Is supervised warm-up (SFT) strictly necessary for EvalAct to learn the coupled protocol, or could advanced RL algorithms learn it from scratch?
- **Basis in paper**: [explicit] Table 2 shows Base EvalAct (without SFT) achieves 17.1% average EM vs. 41.0% with SFT, a 23.9-point gap.
- **Why unresolved**: The gap suggests current RL (GRPO) struggles with the structured action space; it’s unclear if this is fundamental or can be overcome with more sample-efficient RL, curriculum learning, or alternative algorithms.
- **What evidence would resolve it**: Train EvalAct from scratch with enhanced RL settings (more rollouts, longer training, PPO or actor-critic variants) to see if protocol compliance and performance can approach SFT-initialized models.

### Open Question 4
- **Question**: How robust are EvalAct’s gains to variations in the retrieval backbone (e.g., sparse vs. dense, with/without reranking)?
- **Basis in paper**: [explicit] All experiments use a fixed BM25 retriever without reranking; no analysis of robustness to retrieval quality.
- **Why unresolved**: The method’s premise is handling noisy retrievals, but if retrievers improve, the relative benefit over baselines might diminish or change.
- **What evidence would resolve it**: Re-run key multi-hop benchmarks with different retrievers (e.g., Contriever, BGE, with/without cross-encoder reranking) and compare performance deltas between EvalAct and strong baselines like AutoReﬁne.

### Open Question 5
- **Question**: Does the Evaluate-as-Action paradigm generalize beyond retrieval to other tool-using domains (e.g., code execution, database queries), and does it yield similar improvements?
- **Basis in paper**: [inferred] The paper exclusively evaluates on retrieval-augmented QA; the paradigm is described generally but not tested on other tools.
- **Why unresolved**: The core idea is converting implicit quality assessment into an explicit action; this could benefit any tool with variable output quality, but generalizability is unknown.
- **What evidence would resolve it**: Adapt EvalAct to benchmarks involving other tools (e.g., API routing, program synthesis with execution feedback) and measure improvements over baselines without explicit evaluation.

## Limitations
- **Generalization Scope**: Evaluation is restricted to open-domain QA tasks; performance on complex reasoning (math, code) or conversational agents is not demonstrated.
- **Self-Evaluation Analysis**: The reliability and potential biases of the model's own `Evaluate` action are not thoroughly validated against external judgments.
- **Efficiency Costs**: The computational overhead of the extra `Evaluate` step and PCAR calculations is not quantified in terms of inference latency or training FLOPs.

## Confidence
- **State-of-the-art gains on multi-hop QA**: **High** (consistent improvements across 7 benchmarks, strong ablations isolating the Evaluate loop).
- **Causal role of explicit `Evaluate` loop**: **High** (ablation removing the loop causes major performance drop).
- **Reliability of self-evaluation as a process signal**: **Medium** (no external calibration study; relies on internal model judgment).
- **Broader applicability beyond retrieval-augmented QA**: **Low** (no evidence from other tool-using or reasoning domains).

## Next Checks
1. **Cross-Domain Generalization Test**: Implement EvalAct on a non-QA tool-use benchmark (e.g., AgentBench for API calling) to measure transferability of the `Evaluate`-as-Action paradigm.
2. **Human Evaluation of `Evaluate` Outputs**: Sample and have humans judge the correctness of self-evaluations (`z`) against retrieved document relevance to compute real-world calibration error.
3. **Direct Comparison with ProRAG**: Conduct a head-to-head experiment on identical model scales, retrievers, and multi-hop test sets to isolate the unique contribution of EvalAct's coupled protocol and PCAR from other process-supervision methods.
