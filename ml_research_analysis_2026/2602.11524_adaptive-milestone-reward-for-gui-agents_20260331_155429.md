# Adaptive Milestone Reward for GUI Agents
## Quick Facts
- **arXiv ID**: 2602.11524
- **Source URL**: https://arxiv.org/abs/2602.11524
- **Reference count**: 40
- **Primary result**: Introduces Adaptive Milestone Reward (ADMIRE) to resolve the outcome/process reward trade-off in RL for GUI agents, yielding over 10% absolute improvement in success rate on AndroidWorld (e.g., 44.0% with a 7B model vs. 32.8% base) and generalizing across algorithms and domains.

## Executive Summary
Long-horizon GUI agent training with reinforcement learning faces a core dilemma: sparse outcome rewards provide high-fidelity but inefficient learning, while dense process rewards often introduce bias from imperfect verifiers. ADMIRE addresses this by dynamically extracting verifiable sub-goals (milestones) from successful trajectories and applying an asymmetric credit assignment scheme. Successful trajectories are “denoised” by rewarding only milestone achievements, while failed trajectories receive a dense base progress reward plus milestone bonuses to scaffold exploration. This mechanism consistently improves success rates across base models and RL algorithms on the AndroidWorld benchmark and shows strong generalization to diverse environments like ALFWorld and WebShop.

## Method Summary
ADMIRE integrates an adaptive milestone manager with a modified RL objective. Milestones are task-specific sub-goals automatically distilled from any newly discovered successful trajectory using an LLM (GPT-4o) with designed prompts; existing milestones are refined when superior successes are found. During rollouts, a semantic similarity check via Sentence-BERT matches an action’s description against the current milestone pointer. The reward function is asymmetric: for successful episodes, only steps that trigger a milestone receive non-zero reward (sparse, denoised signal); for failed episodes, a constant base reward proportional to the fraction of milestones hit is provided, supplemented by a small bonus per hit (dense scaffolding). This total reward is combined with outcome and format penalties and optimized using Group Relative Policy Optimization (GRPO). The system co-evolves: as the policy improves, milestones adapt to reflect more efficient strategies, maintaining reward alignment.

## Key Results
- On AndroidWorld, ADMIRE yields over 10% absolute improvement in success rate across different base models, e.g., Qwen2.5-VL-7B achieves 44.0% vs. 32.8% with outcome-only RL.
- The asymmetric design is critical; ablating the base reward for failed trajectories causes the largest performance drop, while adding it to successes degrades efficiency.
- Generalizes robustly: gains hold with various RL algorithms (GRPO, RLOO, DAPO) and transfer to heterogeneous environments (ALFWorld, WebShop) with the same pipeline.

## Why This Works (Mechanism)
### Mechanism 1: Adaptive Milestone Generation
**Claim**: Dynamically distilled milestones from successful trajectories provide verifiable, dense intermediate rewards that co-evolve with the agent’s policy, maintaining alignment throughout training.  
**Mechanism**: An LLM abstracts successful trajectories into a milestone sequence. Upon a new successful trajectory, existing milestones are refined to reflect more optimal strategies. During rollouts, semantic similarity (Sentence-BERT) against the current milestone pointer triggers milestone rewards, enabling dense yet objective supervision without per-step LLM calls.  
**Core assumption**: Successful trajectories contain stable, high-level sub-goals abstractable from implementation details, and these remain relevant as the policy discovers more efficient paths.  
**Evidence anchors**: Abstract states milestones “co-evolve alongside the agent’s policy”; Section 3.1 and Algorithm 1 detail the update loop; corpus shows milestone-based shaping is a recognized direction for long-horizon RL.  
**Break condition**: If a task never yields a success early on, its milestone memory stays empty, preventing dense reward and potentially causing permanent learning failure for that task.

### Mechanism 2: Asymmetric Credit Assignment
**Claim**: Treating successful and failed trajectories differently—sparse milestone rewards on successes and dense scaffolding on failures—maximizes signal quality while preserving exploration.  
**Mechanism**: In successful trajectories (O(τ)=1), reward is non-zero only at milestone steps, filtering redundant actions. In failed trajectories (O(τ)=0), a constant base reward k/K (k = milestones hit, K = total milestones) is provided, supplemented by milestone bonuses, breaking the all-or-nothing barrier.  
**Core assumption**: Successful trajectories contain noisy, inefficient actions that would bias policy if rewarded; failed trajectories contain latent partial progress signals that can guide exploration if properly shaped.  
**Evidence anchors**: Abstract says ADMIRE “denoises successful trajectories and scaffolds failed trajectories”; Section 3.2.2 defines the two cases; Figure 4 ablation shows removing base reward from failures hurts most, while adding it to successes harms performance.  
**Break condition**: Removing base reward from failures collapses learning on hard tasks; adding it to successes dilutes the gradient and leads to suboptimal efficiency.

### Mechanism 3: Efficient Semantic Verification
**Claim**: Semantic matching with sequential pointer constraints enables high-fidelity milestone verification at step level without costly LLM-as-a-Judge calls.  
**Mechanism**: An action description is compared to the current milestone via cosine similarity of Sentence-BBERT embeddings. If similarity exceeds threshold δ, the milestone is marked hit and the pointer advances. This prevents out-of-order credit assignment while avoiding expensive per-step LLM evaluation.  
**Core assumption**: Task-agnostic embedding spaces reliably match varied linguistic expressions of the same semantic intent, and sequential ordering enforces causal dependency.  
**Evidence anchors**: Implied by “verifiable” reward triggering; Section 3.2.1 defines the protocol; Appendix B.4.2 shows δ=0.75 yields 81.3% accuracy vs. LLM judge (85.39%) with 70× speedup.  
**Break condition**: δ too low → false positives → reward hacking; δ too high → sparse dense signal; pointer mechanism failure (e.g., allowing skipped milestones) breaks sequential causality.

- **Temporal credit assignment and the outcome/process reward trade-off**: Needed because ADMIRE’s core motivation is resolving the tension between sparse high-fidelity outcome rewards and dense but biased process rewards. *Quick check*: What specific failure mode arises when using a dense LLM-as-a-Judge process reward without verification constraints?
- **Sub-task decomposition and milestone-based reward shaping**: Needed because ADMIRE treats milestones as abstracted sub-goals; understanding decomposition into verifiable checkpoints is key to appreciating adaptive generation. *Quick check*: Why might a fixed, human-defined set of milestones be insufficient for policy optimization across diverse exploration strategies?

## Architecture Onboarding
**Component map**:  
Policy network (Qwen2.5-VL) -> Milestone generator (GPT-4o) -> Semantic matcher (Sentence-BERT) -> Reward calculator -> Advantage normalizer -> GRPO optimizer

**Critical path**:  
1. Rollout: Sample task batch G; collect trajectories {τ_i} using current policy π_old.  
2. Filter successes: Extract successful trajectories B⁺_G per task.  
3. Milestone update: If new success found, initialize or refine task’s milestone list.  
4. Reward assignment: Compute milestone hits via pointer-based semantic matching; apply asymmetric reward formulas; sum total reward.  
5. Advantage & update: Normalize group-wise advantages; perform GRPO policy update.

**Design tradeoffs**:  
- Milestone granularity: Too coarse → insufficient guidance; too fine → high abstraction cost and misalignment.  
- Matching threshold δ: Low → false positives (reward hacking); high → sparse signal.  
- Reward weight λ₀: Balances dense vs. sparse signals; high risks overriding outcome objective, low yields weak exploration.  
- Adaptive vs. static:adaptive maintains alignment but incurs LLM call overhead; static degrades as policy diverges.

**Failure signatures**:  
- Milestone initialization rate remains low (<60% after 100 epochs) → exploration too weak or abstraction too strict.  
- High variance in milestone hit counts across tasks → some milestone sets are too easy/hard, or pointer failing.  
- Ablation failure: Removing base reward from failed trajectories causes sharp drop on hard tasks.  
- Performance decay without reward decay if milestones become misaligned in late training.

**First 3 experiments**:  
1. Baseline comparison: Train Qwen2.5-VL-3B/7B with outcome, process (LLM-as-Judge), and ADMIRE rewards; evaluate success rate on AndroidWorld and MobileMiniWob++.  
2. Ablation study: Test ADMIRE variants—adding base reward to successes, removing base reward from failures, removing reward decay—on both benchmarks.  
3. Cross-domain & algorithm generalization: Integrate ADMIRE with GRPO, RLOO, DAPO; evaluate on ALFWorld and WebShop.

## Open Questions the Paper Calls Out
1. **LLM dependency for milestone generation**: How can milestone generation be decoupled from the VLM’s reasoning capabilities, especially if the VLM hallucinates or misses critical UI transitions? The paper acknowledges ADMIRE is bound by the VLM’s capabilities but does not test weaker or domain-specific VLMs. Resolution would require systematic experiments varying the milestone generator’s quality and correlating it with agent performance.
2. **Fully self-contained RL**: Can the adaptive milestone mechanism be learned directly from policy rollouts without an external LLM/VLM? ADMIRE uses a fixed LLM as an oracle; a truly self-contained system would require a learnable module that discovers and updates milestones. Evidence would come from replacing the LLM with a learned component and comparing performance.
3. **Failure modes of asymmetric assignment**: What are the precise failure modes, particularly for complex tasks where the base reward (k/K) for failures might incentivize semantically meaningless partial progress? The assumption that milestone hits correlate with genuine progress is not stress-tested for tasks with deceptive local optima or multiple paths. Resolution requires fine-grained analysis of failed trajectories, clustering by milestone hit patterns, and manual inspection for futile but milestone-rich patterns.
4. **Milestone density scaling**: How does performance scale with milestone granularity and number? Is there an optimal density, and does it shift with task complexity or agent capability? The base reward scales as k/K, so K’s magnitude affects signal strength. The paper does not investigate controlling K via prompts. Evidence would come from experiments varying maximum milestones and analyzing performance curves and K distributions.
5. **Generalization source**: To what extent is generalization to ALFWorld/WebShop due to the semantic generality of LLM-produced milestones versus the generic asymmetric mechanism? The same LLM prompt (designed for GUIs) was used for all domains. Resolution requires ablating with domain-agnostic prompts or fixed human-annotated milestones to disentangle milestone content from mechanism robustness.

## Limitations
- **LLM dependency**: Milestone quality relies on a capable external LLM (GPT-4o); performance may degrade with weaker or domain-mismatched generators.
- **Scalability and staleness**: Frequent LLM calls per new success are costly; rare successes can lead to stale milestones that misalign with the evolving policy.
- **Semantic matching brittleness**: The embedding-based verifier’s fixed threshold δ may not generalize across tasks; false positives/negatives can corrupt credit assignment.

## Confidence
- **Adaptive milestone generation**: Medium. The dynamic update loop is well-specified but depends on LLM quality and update frequency; risk of staleness if successes are sparse.
- **Asymmetric credit assignment**: High. Strong ablation evidence supports the design; sensitive to λ₀ and decay but robust across algorithms and domains.
- **Semantic verification**: Medium. Efficient and reasonably accurate (81.3% vs. LLM judge) but threshold δ requires calibration; pointer mechanism may fail on non-linear solution paths.

## Next Checks
1. **Long-horizon evaluation**: Test on extended-step versions of AndroidWorld to monitor whether milestone signal remains effective beyond 20 steps and identify decay patterns.
2. **Path diversity study**: For tasks with known alternative optimal trajectories, analyze milestone coverage (do milestones span all valid paths?) and correlate with agent performance to detect shortcut incentives.
3. **Update frequency ablation**: Compare milestone update strategies (every success vs. batched per iteration) to measure the trade-off between alignment freshness and LLM call overhead.
