# TimeWarp: Evaluating Web Agents by Revisiting the Past

## Quick Facts
- **arXiv ID**: 2603.04949  
- **Source URL**: https://arxiv.org/abs/2603.04949  
- **Reference count**: 40  
- **Primary result**: Multi-version TimeWarp-BC yields large gains (Qwen-3 4B +17.3%, Llama-3.1 8B +26.3%) and models trained on five versions generalize better to held-out versions.

## Executive Summary
The TimeWarp benchmark introduces a controlled, reproducible setting for evaluating web agents under UI evolution. It provides six historical versions of three containerized web applications (Wiki, News, Shop) spanning 2001–2025. Trajectories are collected using human-refined high-level execution plans that are instantiated by a GPT-5 teacher across all versions (TimeTraj). Student agents are trained via full-response behavior cloning (TimeWarp-BC), which supervises not only actions but also thinking, memory, and planning tokens. Zero-shot VLMs show high sensitivity to UI changes, with success rates varying widely (e.g., Qwen-3VL SoM from 2.6% to 21.4%). Single-version training fails to generalize, while multi-version training yields substantial improvements and better robustness to unseen versions.

## Method Summary
TimeWarp consists of three core components. First, the environments: three web apps (Wiki, News, Shop) each with six UI versions reconstructed from historical archives, exposing observations as HTML, accessibility tree (AXT), screenshots (SS), and Set-of-Marks (SoM). Second, TimeTraj: humans author version-invariant high-level plans (e.g., “search for X, then navigate”), which a GPT-5 teacher executes in each version to produce successful trajectories; the teacher’s outputs include full response tokens (action, thinking, memory, planning). Third, TimeWarp-BC: open-source LLMs/VLMs are fine-tuned on these trajectories with a loss applied to all tokens (AXT as input for LLMs; SS/SoM for VLMs). Evaluation uses a GPT-5 judge to compute binary success rates across all versions. The study demonstrates that exposure to multiple UI versions during training is key to learning policies that abstract task goals from superficial layout changes.

## Key Results
- Zero‑shot VLM agents exhibit large performance variance across UI versions (e.g., Qwen‑3VL SoM success rates span 2.6%–21.4%).
- Single‑version behavior cloning fails to generalize to dissimilar UI versions; training on v6 yields high performance on v6 but near‑zero on older versions.
- Multi‑version TimeWarp‑BC yields strong gains: Qwen‑3 4B +17.3% (20.4%→37.7%), Llama‑3.1 8B +26.3% (0%→27.0%). Training on five versions generalizes better to a held-out version than training on a single version.

## Why This Works (Mechanism)

### Mechanism 1: Multi‑Version Training Mitigates UI Distribution Shift
- **Claim**: Training web agents on trajectories from multiple UI versions improves robustness to unseen web layouts by reducing overfitting to version‑specific UI patterns.  
- **Mechanism**: Exposure to diverse UI versions during training teaches the agent to abstract task‑relevant objectives (e.g., “find article”, “compare values”) from superficial UI variations (e.g., element placement, styling). This aligns with domain generalization principles where training across domains encourages invariant feature learning.  
- **Core assumption**: The task semantics (goal) remain constant across versions, while the UI manifestations differ; thus, a policy learned from varied presentations can generalize.  
- **Evidence anchors**:  
  - Abstract: Multi‑version TimeWarp‑BC yields large gains (Qwen‑3 4B +17.3%, Llama‑3.1 8B +26.3%). Models trained on five versions generalize better to held‑out versions.  
  - Section: §6.2 (“Does multi‑version training generalize better?”) shows models trained on a single version (v1 or v5) degrade on dissimilar versions, while v1:5 training generalizes better.  
  - Corpus: Neighbors like Meta‑World+ address benchmark stability across tasks, implying multi‑domain training is a known robustness strategy; Sample‑Efficient Online Learning in LM Agents discusses adaptation to environmental shifts, supporting the value of diverse experience.  
- **Break condition**: If UI changes alter fundamental interaction workflows (e.g., search algorithm shifts beyond layout), multi‑version training may fail without explicit workflow adaptation.

### Mechanism 2: Plan Distillation Enables Scalable Multi‑Version Trajectory Collection
- **Claim**: Human‑refined, version‑invariant execution plans allow a single teacher to generate successful trajectories across multiple UI versions, reducing annotation cost.  
- **Mechanism**: Humans create high‑level checkpoints (e.g., “search for X”, “scroll to Y”) that are UI‑agnostic. A teacher executor then instantiates these checkpoints with low‑level actions (e.g., specific element IDs) in each version. This decouples plan creation from UI‑specific execution.  
- **Core assumption**: A well‑designed plan remains executable across versions because the underlying task graph (e.g., “search then navigate”) persists despite UI changes.  
- **Evidence anchors**:  
  - Abstract: TIMETRAJ uses plan distillation to collect trajectories across multiple versions with minimal human involvement.  
  - Section: §5.1 details human refinement of plans and teacher rollouts; §B.3 shows execution diagrams where the same plan guides successful execution in different versions.  
  - Corpus: WebCoach explores memory‑augmented agents but does not address multi‑version collection; the corpus lacks direct parallels, making this an innovation specific to temporal UI shifts.  
- **Break condition**: If a UI version introduces a new interaction paradigm (e.g., voice search replacing text input), the plan may become infeasible, requiring manual re‑planning.

### Mechanism 3: Full‑Response BC Preserves Reasoning Artifacts for Complex Tasks
- **Claim**: Training on the agent’s full response tokens (action, thinking, memory, planning) improves performance on multi‑step, memory‑intensive tasks compared to action‑only BC.  
- **Mechanism**: The full response includes intermediate reasoning (thinking), task decomposition (planning), and state tracking (memory). Supervising these tokens helps the student model learn structured reasoning and avoid cascading errors.  
- **Core assumption**: The teacher’s non‑action tokens are high‑quality and transferable; the student can effectively imitate the reasoning process, not just the actions.  
- **Evidence anchors**:  
  - Abstract: TimeWarp‑BC trains on full responses, achieving substantial gains.  
  - Section: §5.2 defines the loss on full responses; §6.2 (ablations, Table 3) show combinations including thinking/memory/planning tokens outperform action‑only.  
  - Corpus: AgentRewardBench evaluates trajectories, but not training; WebArXiv uses chain‑of‑thought for evaluation, indirectly supporting the value of reasoning tokens. No corpus paper directly studies full‑response BC for web agents.  
- **Break condition**: If the teacher’s reasoning is misaligned with the student’s capabilities (e.g., overthinking leading to context overflow), or if tasks require minimal reasoning, full‑response BC may add no benefit or hurt performance.

## Architecture Onboarding

### Component Map
Environments (Wiki, News, Shop with 6 UI versions each) → TimeTraj (Planner + GPT‑5 Teacher) → Trajectories (observations + full responses) → TimeWarp‑BC (Student model fine‑tuning) → Agent → Evaluation (GPT‑5 Judge)

### Critical Path
1. Define tasks and desired outcomes (human‑written).  
2. For each task, generate and refine a plan (human‑in‑the‑loop).  
3. For each version, run teacher to collect trajectories using the plan.  
4. Filter successful trajectories via judge.  
5. Fine‑tune student on full‑response trajectories (multiple versions).  
6. Evaluate student on all versions (including held‑out).

### Design Tradeoffs
- **Teacher strength vs. cost**: Using GPT‑5 ensures high‑quality trajectories but is expensive; cheaper teachers may yield more failures.  
- **Human plan refinement vs. automation**: Human refinement ensures plan quality but limits scalability; fully automated planning (e.g., via an LLM) may produce less robust plans.  
- **Full‑response BC vs. action‑only**: Full‑response improves reasoning but increases sequence length and training complexity.  
- **Version coverage vs. data size**: Including more versions boosts robustness but expands the training set and compute requirements.

### Failure Signatures
- Trajectory collection fails if the teacher cannot execute a plan in a version (e.g., due to UI changes breaking plan assumptions).  
- Student model fails to generalize if training data lacks version diversity (e.g., only v6).  
- Performance collapse after continual fine‑tuning on a new version (catastrophic forgetting), as shown in §6.2.  
- VLMs with SoM show high variance across versions, indicating visual grounding brittleness.

### First 3 Experiments
1. **Zero‑shot evaluation across versions**: Run VLMs/LLMs on all six versions to measure baseline vulnerability to UI changes.  
2. **Single‑version BC**: Train on v6 trajectories (action‑only or full‑response) and evaluate on all versions; expect improvement on v6 but poor generalization.  
3. **Multi‑version TimeWarp‑BC**: Train on v1–v5 trajectories (full‑response) and evaluate on held‑out v6; expect significant gains and better version robustness.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question**: What continual learning methods can enable web agents to adapt to new UI versions without catastrophic forgetting of previously learned knowledge?  
- **Basis in paper**: [explicit] Section 7 (Discussion & Conclusion) states that the dataset “brings up exciting new areas for work in continual learning for web agents, which until this point has been underexplored.” The version continual learning experiment in §6.2 explicitly shows that “naive sequential fine‑tuning results in a loss of performance,” highlighting the need for better methods.  
- **Why unresolved**: The paper identifies catastrophic forgetting as a critical issue but does not propose or evaluate any continual learning technique to mitigate it. This remains an open challenge for building agents that accumulate knowledge over time.  
- **What evidence would resolve it**: A continual learning algorithm (e.g., rehearsal, regularization, or parameter isolation) that allows fine‑tuning on new UI versions while preserving performance on old versions, validated on TimeWarp’s held‑out version generalization.

### Open Question 2
- **Question**: How can visual web agents be made robust to the large variations in UI design encountered across different historical web versions?  
- **Basis in paper**: [explicit] Section 7 notes that “there is still room for improvement, particularly for agents that rely on visual inputs.” The results in §6.2 show zero‑shot VLM agents with performance ranges spanning up to 18.8% (e.g., Qwen‑3 VL 8B SoM: [2.6,21.4]%), indicating high sensitivity to UI changes.  
- **Why unresolved**: The paper demonstrates the problem but offers no solution for improving visual robustness; training with TimeWarp‑BC focuses on textual observations, and visual performance remains inconsistent.  
- **What evidence would resolve it**: A VLM agent that achieves stable, high success rates (e.g., >30%) across all six UI versions and all visual observation types (SS, SoM) without large variance.

### Open Question 3
- **Question**: Can the plan distillation process in TIMETRAJ be fully automated to eliminate the need for human refinement, thereby enabling truly scalable trajectory collection?  
- **Basis in paper**: [inferred] TIMETRAJ (Section 5.1) relies on human refinement of draft execution plans. The authors acknowledge that manual trajectory collection is resource‑intensive and that their hybrid approach reduces but does not remove human involvement. The appendix B.4 reports that without human refinement, success rates drop to 60–70%, suggesting room for improvement.  
- **Why unresolved**: Human refinement remains a bottleneck for scaling to many environments and versions; a fully automated method would further increase scalability and reduce cost.  
- **What evidence would resolve it**: An automated planning module (e.g., an LLM council or specialized model) that generates plans achieving ≥95% of the teacher rollout success rate of human‑refined plans on TimeWarp, without any human intervention.

### Open Question 4
- **Question**: What architectural or training modifications can mitigate the persistent misalignment between non‑action reasoning tokens and executed actions in web agents?  
- **Basis in paper**: [inferred] The qualitative analysis (Section E.1) identifies “the misalignment between action and non‑action tokens” as a “jarring limitation” observed in both trained and untrained agents. Even after training with TimeWarp‑BC, instances like Fig. 18 show correct reasoning but incorrect actions.  
- **Why unresolved**: The paper does not investigate the root causes or propose solutions; this misalignment undermines agent reliability and is a major source of failures.  
- **What evidence would resolve it**: A training objective, decoding strategy, or model architecture that drastically reduces the frequency of action‑reasoning mismatches, measured by a lower rate of contradictions between thinking/memory/plan tokens and the final action, leading to higher success rates.

### Open Question 5
- **Question**: Can the TimeWarp evaluation paradigm be extended beyond web browsers to other dynamic interface domains (e.g., mobile apps, desktop software) to assess long‑term agent robustness?  
- **Basis in paper**: [explicit] The Impact Statement states that TimeWarp “contributes to the methodological shift toward time‑aware evaluation in AI, with implications for any domain where digital interfaces evolve continuously (e.g., mobile apps, documentation portals). The TIMEWARP benchmark could thus serve as a general testbed for the long‑term reliability of agents in any dynamic information retrieval system.”  
- **Why unresolved**: The paper exclusively evaluates web environments; no experiments or adaptations to other domains are presented, leaving unknown whether the insights and benchmark structure generalize.  
- **What evidence would resolve it**: A TimeWarp‑style benchmark suite for a different domain (e.g., mobile apps with versioned UIs) that replicates the key features (multiple historical versions, realistic tasks) and yields similar insights about agent robustness, demonstrating the paradigm’s broader applicability.

## Limitations
- Reliance on proprietary GPT‑5 for teacher trajectories and evaluation undermines reproducibility and may introduce bias.
- Human‑in‑the‑loop plan refinement is labor‑intensive and not automated, limiting scalability.
- Evaluation restricted to three website domains and six historical versions; findings may not generalize to other web types or more drastic UI shifts.

## Confidence
- **Multi‑version training improves robustness**: Medium (strong empirical gains but limited to similar templates and single held‑out version)  
- **Plan distillation enables scalable collection**: Medium (human‑refined plans work, but automation potential unproven)  
- **Full‑response BC yields superior performance**: High (consistent improvements across models and ablations)
