# Algorithms for Deciding the Safety of States in Fully Observable Non-deterministic Problems: Technical Report

## Quick Facts
- **arXiv ID:** 2603.15282
- **Source URL:** https://arxiv.org/abs/2603.15282
- **Reference count:** 6
- **Primary result:** iPI is a new policy iteration algorithm that matches TarjanSafe’s best-case runtime while guaranteeing polynomial worst-case, and scales exponentially better on worst-case instances like Flappy Bird, establishing it as the new state-of-the-art for FOND state-safety decision.

## Executive Summary
Deciding state safety in fully observable non-deterministic (FOND) problems is crucial for verifying learned policies. The prior best algorithm, TarjanSafe, is efficient in practice but has exponential worst-case runtime. A linear-time alternative, Prop-U, is unusable due to massive unsafe region propagation. This paper introduces iPI, an improved policy iteration algorithm. iPI begins with an initial policy/action ordering and iteratively marks unsafe states using a combined depth-first search and value-iteration approach, making minimal adjustments to the policy when necessary. Theoretically, iPI achieves TarjanSafe’s best-case runtime of Θ(|π_min-safe|) while ensuring a polynomial worst-case bound of O(bmn). Experimentally, on standard planning benchmarks iPI matches TarjanSafe’s speed, but on the Flappy Bird domain—which triggers TarjanSafe’s worst-case—iPI scales exponentially better. The variant iPI with the default action order (iPI(app)) consistently performs best, while Prop-U fails due to memory limitations on all tested problems. Thus, iPI is presented as the new state-of-the-art method for deciding state safety in FOND problems.

## Method Summary
The core method is iPI, an iterative policy iteration algorithm tailored for FOND state-safety. It initializes with a deterministic policy (action ordering) over non-deterministic actions. In each iteration, it performs a combined DFS-value-iteration: a DFS traverses the state space from a candidate safe set, while a value-iteration-like update propagates safety information under the current policy. If a state is found that violates safety constraints (e.g., reaches an unavoidable dead-end), the policy is minimally adjusted by selecting a different available action at the earliest point in the DFS where the violation occurred. This adjustment breaks the non-deterministic choice leading to the unsafe region. The process repeats until no more unsafe states are discovered or a fixed point is reached. The algorithm strategically limits policy changes to avoid the explosive recomputation seen in TarjanSafe’s worst case and the uncontrolled propagation of Prop-U.

## Key Results
- **Theoretical:** iPI achieves best-case runtime Θ(|π_min-safe|) matching TarjanSafe, and worst-case polynomial O(bmn).
- **Experimental:** iPI matches TarjanSafe on standard benchmarks but shows exponential improvement on Flappy Bird (TarjanSafe’s worst-case).
- **Practical:** iPI(app) (default action order) is the top performer; Prop-U fails due to memory on all tested domains.

## Why This Works (Mechanism)
iPI succeeds by combining the structured exploration of DFS with iterative policy refinement. The DFS efficiently explores reachable states under the current policy, quickly identifying potential safety violations. When a violation is found, the algorithm backtracks to the earliest decision point and switches to a *different* action, thereby avoiding the problematic non-deterministic branch. This minimal adjustment strategy prevents the full recomputation of large state subsets that plagues TarjanSafe in worst-case scenarios. Simultaneously, by relying on a fixed policy during each DFS phase, iPI avoids the unfocused, massive propagation that causes Prop-U to run out of memory. The algorithm essentially “guides” the search with a policy, corrects it only when absolutely necessary, and thereby balances exploration cost with policy stability.

## Foundational Learning
- **Fully Observable Non-deterministic (FOND) Problems:** Planning problems where actions have multiple possible outcomes but the state is fully known. *Why needed:* The setting for state-safety decision. *Quick check:* Can you model a domain where an action like “move” has multiple possible successor states under full observability?
- **State Safety:** Determining whether a state can be forced to avoid failure states forever. *Why needed:* The core decision problem addressed. *Quick check:* Given a policy, can you verify if all reachable states from a start state are safe (avoid dead-ends)?
- **Policy Iteration:** Iteratively improving a policy by evaluation and improvement steps. *Why needed:* iPI’s overarching framework. *Quick check:* In a simple MDP, how would you iteratively refine a policy to maximize reward?
- **Value Iteration:** Computing value functions by bootstrapping. *Why needed:* Influences iPI’s safety propagation mechanics. *Quick check:* How does value iteration update state values based on successors?
- **Depth-First Search (DFS):** Graph traversal exploring as far as possible before backtracking. *Why needed:* Enables efficient, stack-based state exploration in iPI. *Quick check:* How does DFS handle cycles in a directed graph?
- **Action Ordering / Initial Policy:** A deterministic selection of actions for non-deterministic choices. *Why needed:* Starting point for iPI’s iterations; impacts performance. *Quick check:* If multiple actions are available in a state, how might the order of trying them affect search?

## Architecture Onboarding
**Component Map:**  
Initial Policy Generator -> DFS-Value-Iteration Engine -> Policy Adjuster -> (loop back to DFS-Value-Iteration Engine) -> Safe State Set Output

**Critical Path:**  
1. Begin with an initial deterministic policy (action ordering).  
2. Run combined DFS-value-iteration: DFS explores reachable states under policy; safety labels propagate.  
3. If an unsafe state (e.g., unavoidable dead-end) is encountered, backtrack to earliest policy decision point in the DFS stack.  
4. Adjust policy at that point to next available action.  
5. Repeat from step 2 until no unsafe states found or no further policy adjustments possible.  
6. Output final safe state set.

**Design Tradeoffs:**  
- *Policy Stability vs. Completeness:* Minimal adjustments preserve explored structure but may require more iterations; aggressive changes risk losing progress.  
- *Initial Ordering Sensitivity:* Default order (iPI(app)) works best empirically, but other orderings may increase iterations—no theoretical guarantee.  
- *Memory vs. Time:* DFS uses stack memory proportional to depth; worst-case polynomial time but constant factors depend on policy adjustment frequency.

**Failure Signatures:**  
- Excessive policy adjustments in early iterations leading to repeated DFS recomputation (approaching O(bmn) worst-case).  
- Deep recursion stacks causing memory overflow on very large state spaces (though less than Prop-U).  
- Stalling when no action ordering yields safety, correctly reporting “unsafe” but potentially after many iterations.

**First Three Experiments:**  
1. **Smallest FOND instance:** A 3-state domain with one non-deterministic action to manually verify iPI’s adjustment step.  
2. **Comparison with TarjanSafe:** Run both on a benchmark where TarjanSafe is known to be fast (e.g., standard logistics variant) to confirm parity.  
3. **Action Ordering Ablation:** Test iPI with 3 different initial orderings (default, reverse, random) on a small domain to observe sensitivity to starting policy.

## Limitations
- **Benchmark scope:** Evaluation limited to standard planning benchmarks and Flappy Bird; generalization to other real-world FOND problems (e.g., robotics) is unverified.
- **Algorithmic dependencies:** Performance heavily relies on initial action ordering; theoretical principles behind `iPI(app)`’s superiority and sensitivity to other strategies remain unclear.
- **Theoretical constants:** Worst-case O(bmn) bound lacks tight analysis of constant factors; may be prohibitive for large branching factor `b`.

## Confidence
- **Theoretical runtime guarantees (best-case Θ(|π_min-safe|), worst-case O(bmn)):** High
- **Experimental superiority over TarjanSafe on Flappy Bird:** Medium
- **Prop-U failure due to memory:** Low (overclaimed without systematic profiling)
- **iPI as new state-of-the-art:** Medium (validated on tested domains only)
