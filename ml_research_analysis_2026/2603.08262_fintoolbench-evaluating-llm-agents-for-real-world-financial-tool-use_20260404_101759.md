# FinToolBench: Evaluating LLM Agents for Real-World Financial Tool Use

## Quick Facts
- arXiv ID: 2603.08262
- Source URL: https://arxiv.org/abs/2603.08262
- Reference count: 40
- Primary result: FinToolBench is the first runnable benchmark with 760 financial tools and 295 tool-dependent queries, introducing finance-specific compliance metrics and demonstrating a trade-off between tool invocation rate and conditional execution reliability.

## Executive Summary
FinToolBench addresses the absence of realistic benchmarks for LLM agents in financial tool use by releasing the first fully runnable suite, comprising 760 executable tools and 295 queries that explicitly require tool interaction. The paper defines a novel evaluation framework with finance-centric compliance metrics—timeliness mismatch rate (TMR), intent mismatch rate (IMR), and domain mismatch rate (DMR)—alongside conventional metrics like tool invocation rate (TIR) and conditional execution reliability (CER). Evaluations on multiple LLM backbones reveal a consistent trade-off: models that invoke tools aggressively (high TIR) suffer lower execution reliability and higher mismatch rates, while conservative models (low TIR) achieve greater precision and compliance. The proposed FATR baseline, which annotates tool cards with finance attributes, significantly improves reliability and reduces violations, highlighting the critical role of domain-aware tool routing.

## Method Summary
The paper lacks explicit reproduction notes. Nevertheless, the evaluation method involves running diverse LLM agents on the FinToolBench suite, measuring TIR, TESR, CER, and the finance-specific mismatch rates. Tools are annotated with attributes (timeliness, intent_type, regulatory_domains) via an LLM-based labeling pipeline. The FATR approach enriches tool cards with these attributes to guide the agent’s selection decisions. The benchmark uses free‑tier financial APIs, limiting realism but enabling broad accessibility.

## Key Results
- Aggressive tool use (e.g., Qwen3‑8B, TIR=0.8712) yields low conditional execution reliability (CER=0.3385), while conservative use (e.g., GPT‑4o, TIR=0.2267) achieves higher CER (0.6176) and lower mismatch rates.
- FATR, the attribute‑injection baseline, improves CER and reduces TMR/IMR/DMR across models, confirming the benefit of finance‑aware routing.
- The TIR‑CER trade‑off holds across tested LLMs, suggesting a fundamental tension between coverage and precision in financial tool use.

## Why This Works (Mechanism)
FATR works by providing structured domain knowledge to the agent’s tool selection process. Finance‑specific attributes (timeliness, intent, regulatory domain) enable the planner to better align tool capabilities with query requirements, directly reducing mismatches. The observed TIR‑CER trade‑off emerges because without attribute guidance, agents may invoke tools too liberally, leading to execution failures; with guidance, they become more selective, increasing precision. The compliance metrics themselves enforce attention to financial constraints that generic success metrics overlook.

## Foundational Learning
- **Tool‑Using Agents**: Agents that can call external tools/APIs to extend their capabilities beyond text generation. *Why needed*: Real‑world tasks require up‑to‑date data or computations unavailable in the model’s parameters. *Quick check*: Can the agent correctly use a calculator tool for a multi‑step arithmetic problem?
- **Finance‑Specific Compliance Metrics**: TMR, IMR, DMR capture mismatches in timeliness, intent, and regulatory domain. *Why needed*: Financial tasks impose strict constraints; generic accuracy metrics are insufficient. *Quick check*: Does the agent avoid using a daily‑close price tool for an intraday trading query?
- **Conditional Execution Reliability (CER)**: Success rate of tool executions conditional on invocation. *Why needed*: High tool invocation does not guarantee useful results; CER measures precision of tool use. *Quick check*: Among invoked tools, what fraction produce correct and relevant outputs?
- **FATR Attribute Injection**: Enriching tool cards with finance attributes to guide routing. *Why needed*: Without structured metadata, agents may misuse tools; attributes provide explicit decision signals. *Quick check*: Does adding timeliness tags reduce TMR without hurting TIR?
- **Tool Invocation Rate (TIR)**: Proportion of queries where the agent decides to use a tool. *Why needed*: Balances exploration versus reliance on internal knowledge. *Quick check*: Is TIR higher on queries that explicitly mention numerical data or recent events?

## Architecture Onboarding
**Component Map**: Query → Planner (LLM) → Tool Router (with FATR attributes) → Tool Executor → Response Generator → Evaluator

**Critical Path**: The sequence from user query to final answer involves: (1) planning whether a tool is needed; (2) selecting an appropriate tool based on encoded attributes; (3) executing the tool; (4) incorporating the result into the response. Failures at any stage yield mismatches or execution errors.

**Design Tradeoffs**: Aggressive tool invocation (high TIR) increases coverage but lowers CER due to more failures; conservative invocation (low TIR) improves precision but may miss necessary tools. FATR adds attribute‑management overhead but improves routing accuracy. The reliance on free‑tier APIs may affect generalizability to high‑frequency or proprietary data environments.

**Failure Signatures**: High TMR indicates use of tools with stale or timing‑inappropriate data; high IMR signals tools that do not fulfill the query’s intent; high DMR reflects regulatory domain violations; low CER points to execution issues (incorrect parameters, API errors, or timeouts).

**First Experiments**:
1. Baseline Run: Evaluate multiple LLM backbones without FATR to establish baselines for TIR, CER, and mismatch rates.
2. FATR Injection: Enable attribute‑enriched tool cards and measure changes in compliance metrics and CER.
3. Ablation Study: Remove individual attribute types (timeliness, intent_type, regulatory_domains) to quantify each contribution to performance.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: How do LLM agents perform when using proprietary or high-frequency financial data feeds instead of free-tier APIs?
- Basis in paper: [explicit] "Future work may extend coverage to proprietary real-time data feeds..."
- Why unresolved: FinToolBench exclusively uses free-tier tools, which may have rate limits, latency, or data granularity mismatches with institutional settings.
- What evidence would resolve it: Integrate a suite of proprietary or simulated high-fidelity financial APIs and re-run the FATR evaluation pipeline, comparing TMR/IMR/DMR shifts.

### Open Question 2
- Question: What underlying factors drive the observed heterogeneity in compliance mismatch rates across question categories (e.g., why does "value extraction" show high IMR in Figure 7)?
- Basis in paper: [inferred] Category-level diagnosis in Appendix H reveals performance variance, but root causes are not analyzed.
- Why unresolved: The paper reports metrics per category without investigating whether failures stem from tool attribute misalignment, question phrasing ambiguity, or planner biases.
- What evidence would resolve it: Conduct error analysis tracing mismatches to specific tool attributes (e.g., intent_type distributions) or question linguistic features, possibly via controlled synthetic perturbations.

### Open Question 3
- Question: Can the finance attribute annotation schema (timeliness, intent_type, regulatory_domains) be reliably automated without LLM-based labeling, and how does annotation consistency affect compliance metrics?
- Basis in paper: [explicit] Attributes are annotated via "LLM-based labeling pipeline utilizing a three-vote majority agreement," but human spot-checking is limited.
- Why unresolved: Reliance on LLM judges for both annotation and evaluation introduces potential circularity and instability; the paper does not measure inter-annotator agreement beyond majority vote.
- What evidence would resolve it: Create a human-annotated gold standard for a subset, compute agreement metrics (Cohen's kappa) with LLM labels, and assess sensitivity of TMR/IMR/DMR to annotation variations.

### Open Question 4
- Question: How do finance-aware constraints (TMR/IMR/DMR) transfer to other high-stakes domains like healthcare or legal tool use, and what domain-specific adaptations are necessary?
- Basis in paper: [explicit] The framework targets "finance-specific constraints" but general tool benchmarks lack domain rigor; the paper implies transferability is underexplored.
- Why unresolved: FinToolBench's attribute schema is tailored to finance (e.g., regulatory_domain subsets). It's unclear if similar constraints (e.g., "timeliness" in medical diagnostics) map directly.
- What evidence would resolve it: Adapt the FinToolBench pipeline to a healthcare API benchmark, define analogous attributes (e.g., data freshness criticality), and evaluate whether FATR's attribute injection improves compliance across domains.

## Limitations
- The claim of being the “first runnable benchmark” is uncertain due to the existence of concurrent benchmarks (FinAgentBench, FinMCP‑Bench); the distinction in runnability and timeline needs clarification.
- The demonstrated TIR‑CER trade‑off is based on only two models (Qwen3‑8B, GPT‑4o), limiting confidence in its generalizability across model scales and architectures.
- Finance‑specific compliance metrics lack external validation against real‑world financial outcomes or expert assessments, leaving their practical relevance unverified.

## Confidence
- First benchmark claim: Medium
- Novel evaluation framework: High
- TIR‑CER trade‑off results: Medium
- FATR improvement: Medium
