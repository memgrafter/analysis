# Bonsai: A Framework for Convolutional Neural Network Acceleration Using Criterion-Based Pruning

## Quick Facts
- **arXiv ID:** 2602.17145
- **Source URL:** https://arxiv.org/abs/2602.17145
- **Reference Count:** 17
- **Primary Result:** Introduces a pruning framework that abstracts criteria and schedules, enabling up to 79% filter pruning with maintained or improved accuracy and up to 68% FLOP reduction on VGG-inspired models.

## Executive Summary
This paper presents "Combine," a unified framework for convolutional neural network (CNN) pruning that abstracts pruning criteria (e.g., filter importance metrics) and their application schedules (static or progressive). The goal is to address the fragmentation in CNN pruning research, where different methods use incompatible implementations, making fair comparison difficult. The framework is evaluated on VGG-inspired models for MNIST and CIFAR-10, demonstrating substantial filter removal and computational savings with negligible accuracy loss, and in some cases, accuracy improvement.

## Method Summary
Combine introduces an abstraction layer separating the pruning criterion (what defines an "unimportant" filter) from the pruning schedule (how and when pruning is applied). This allows users to mix-and-match criteria (e.g., L1-norm, activation-based) with either static pruning (one-shot removal) or progressive pruning (iterative removal with fine-tuning). The framework systematically applies the selected criterion to score filters, removes a target percentage according to the schedule, and optionally fine-tunes the model. This design enables consistent, reproducible evaluation across different pruning strategies within a single codebase.

## Key Results
- Pruned up to 79% of filters in VGG-inspired models while maintaining or improving top-1 accuracy (e.g., MNIST Model A increased to 99.33%).
- Reduced computational FLOPs by up to 68% across tested models.
- Demonstrated that progressive pruning schedules generally outperformed static schedules in preserving accuracy, especially at higher pruning rates.

## Why This Works (Mechanism)
The framework's abstraction decouples the "what" (criterion) from the "when" (schedule), eliminating implementation biases that hinder comparison in prior work. By standardizing the pruning pipeline—score filters, apply mask, fine-tune—Combine ensures that observed performance differences stem from the criterion and schedule themselves, not code variations. This consistent application allows for a clearer assessment of each component's impact on the accuracy-efficiency trade-off.

## Foundational Learning
- **Pruning Criterion:** A metric (e.g., L1-norm of filter weights) used to rank filter importance. *Why needed:* Determines which filters can be removed with minimal accuracy impact. *Quick check:* Verify that the criterion's ranking correlates with filter contribution to output (e.g., via ablation).
- **Pruning Schedule:** The strategy for applying pruning (e.g., static one-shot vs. progressive incremental). *Why needed:* Controls the pace of removal, affecting model stability and recovery during fine-tuning. *Quick check:* Compare accuracy drop after each pruning stage for different schedules.
- **Filter vs. Neuron Pruning:** This work focuses on removing entire convolutional filters (structured pruning). *Why needed:* Structured pruning yields actual speedups on standard hardware, unlike unstructured methods. *Quick check:* Ensure removed filters lead to corresponding channel reductions in subsequent layers.
- **Accuracy-Efficiency Trade-off:** The core tension in pruning between model compression (FLOPs, parameters) and predictive performance. *Why needed:* Guides selection of pruning rate and criterion. *Quick check:* Plot accuracy vs. FLOPs for different pruning configurations to identify Pareto frontier.
- **Fine-tuning after Pruning:** Retraining the pruned network to recover accuracy. *Why needed:* Pruning initially degrades performance; fine-tuning adapts remaining weights. *Quick check:* Monitor accuracy recovery epochs; stagnation may indicate over-pruning.
- **Computational Complexity Metric:** FLOPs (floating-point operations) as a hardware-agnostic measure of inference cost. *Why needed:* Primary target for acceleration. *Quick check:* Calculate FLOPs before/after pruning to confirm reduction matches reported figures.

## Architecture Onboarding
**Component Map:**  
PruningCriterion (e.g., L1Norm) -> PruningSchedule (e.g., Progressive) -> ModelPruner (applies mask) -> FineTuner -> Evaluator

**Critical Path:**  
1. Initialize model and dataset.  
2. For each pruning step: score all filters using Criterion, select bottom-k% based on score, generate binary mask, apply mask to model weights.  
3. If Progressive schedule: fine-tune model for N epochs, repeat from step 2 until target pruning rate.  
4. If Static schedule: apply final mask once, then fine-tune.  
5. Evaluate final model on test set for accuracy and FLOPs.

**Design Tradeoffs:**  
- *Static vs. Progressive:* Static is simpler and faster but risks higher accuracy loss; progressive is more complex but often yields better recovery.  
- *Criterion Selection:* Simple criteria (L1) are fast but may be less accurate; sophisticated criteria (activation-based) are more computationally expensive during scoring.  
- *Pruning Granularity:* Per-layer vs. global pruning affects layer-wise compression uniformity and potential accuracy drops.

**Failure Signatures:**  
- Sudden, non-recoverable accuracy drop after a pruning step, indicating over-pruning or poor criterion selection.  
- Layer collapse: consecutive layers pruned to zero filters, breaking network connectivity.  
- Fine-tuning fails to recover accuracy, suggesting the pruned model lost essential representational capacity.

**First Three Experiments:**  
1. Baseline: Train unpruned VGG-inspired model on MNIST/CIFAR-10 to establish reference accuracy and FLOPs.  
2. Static Pruning Test: Apply Combine with L1-norm criterion and static schedule at 50% global pruning; compare accuracy/FLOPs to baseline.  
3. Progressive vs. Static: Run Combine with same criterion at 70% pruning, using both schedules; measure final accuracy and fine-tuning epochs required.

None reported.

## Limitations
- Evaluation limited to VGG-inspired architectures on MNIST and CIFAR-10; no tests on modern architectures (ResNet, EfficientNet) or large-scale datasets (ImageNet), restricting generalizability.
- The claimed unification benefit of the Combine framework is not contrasted directly against existing pruning libraries (e.g., Torch Pruning, NNCF), making its novelty unclear.
- Reported accuracy improvements on simple datasets (e.g., +0.08% on MNIST) may fall within statistical noise; significance is unverified.

## Confidence
- **High:** Reported FLOP reduction and filter pruning percentages are reproducible metrics with low variance.
- **Medium:** Accuracy maintenance on CIFAR-10 is credible but based on a narrow model suite; could vary with different architectures.
- **Low:** Framework's abstraction advantage and generalizability beyond toy models due to absent comparative studies and limited benchmark scope.

## Next Checks
1. **Replicate on ResNet-50/ImageNet:** Test Combine's pruning schedules and criteria on a modern, complex architecture and large-scale dataset to verify scalability and robustness of accuracy-FLOP trade-offs.
2. **API Comparison Study:** Implement identical pruning runs (same model, criterion, schedule) using Combine and a standard library (e.g., Torch Pruning); compare code complexity, flexibility, and reproducibility.
3. **Statistical Significance Test:** For MNIST Model A experiments, run multiple random seeds (e.g., 5-10) for the reported pruning configuration; perform t-tests to confirm accuracy improvements are statistically significant and not stochastic.
