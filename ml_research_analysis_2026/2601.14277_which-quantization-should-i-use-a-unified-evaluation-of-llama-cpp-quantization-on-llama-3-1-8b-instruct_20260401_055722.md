# Which Quantization Should I Use? A Unified Evaluation of llama.cpp Quantization on Llama-3.1-8B-Instruct

## Quick Facts
- **arXiv ID:** 2601.14277
- **Source URL:** https://arxiv.org/abs/2601.14277
- **Reference count:** 35
- **Primary result:** Mid-bit (4-5 bit) K-quant formats like Q5_0 and Q4_K_S provide the optimal Pareto balance of significant size reduction and minimal accuracy loss for CPU deployment of Llama-3.1-8B-Instruct.

## Executive Summary
This study addresses the lack of unified evaluation for llama.cpp's GGUF quantization schemes by quantizing a single FP16 Llama-3.1-8B-Instruct model using 13 formats (3-8 bits, including K-quant and legacy types) and measuring downstream task performance, WikiText-2 perplexity, CPU throughput, and model size. Key findings reveal that Q5_0 achieves the highest average downstream score with a 65% size reduction, while aggressive 3-bit quantization severely degrades reasoning tasks like GSM8K but improves token-generation throughput. The work establishes 4-5 bit K-quant formats as practical defaults for CPU deployment, highlighting that format design—not just bit-width—critically influences task-specific accuracy.

## Method Summary
The authors used the official `llama.cpp` (commit `b7600`) to quantize a single FP16 GGUF model of Llama-3.1-8B-Instruct into 13 GGUF schemes. Evaluation was conducted with EleutherAI's `lm-eval-harness` (v0.4.9.2) for downstream tasks (GSM8K, HellaSwag, IFEval, MMLU, TruthfulQA), WikiText-2 for perplexity, and llama.cpp's benchmark tools for CPU throughput (prefill and decoding) on a dual-socket Intel Xeon Platinum 8488C. Model size, quantization time, and performance metrics were recorded to compare trade-offs across all formats under a uniform protocol.

## Key Results
- Q5_0 achieved the highest average downstream score (69.92) with a 65.19% size reduction, slightly exceeding the FP16 baseline (69.47).
- Q4_K_S provided a strong balance with 70.83% size reduction and minimal aggregate quality loss.
- Aggressive 3-bit quantization (e.g., Q3_K_S) significantly degraded reasoning (GSM8K: 68.31 vs. 77.63) and increased perplexity (8.96 vs. 7.32), while token-generation throughput improved substantially (9.91 vs. 2.83 tokens/s).

## Why This Works (Mechanism)
### Mechanism 1: Format Design Influences Task Performance Beyond Bit-Width
- **Claim:** The internal design of a quantization format (block structure, scaling metadata) causally influences downstream task performance, not just the nominal bit-width.
- **Mechanism:** Formats with similar effective bits-per-weight employ different block structures and scaling strategies, altering the spatial distribution of quantization error. This error interacts with task-specific computational patterns (e.g., multi-step reasoning vs. commonsense selection), leading to divergent performance even at comparable compression levels.
- **Evidence anchors:** Task sensitivity varied (GSM8K highly sensitive, HellaSwag stable); non-monotonicity in GSM8K scores for formats with similar bit-width (e.g., Q5_K_S underperforms Q5_0).
- **Break condition:** If task performance were a monotonic function of average reconstruction error (perplexity), which the data contradicts.

### Mechanism 2: Mid-Bit K-Quants Are Pareto-Optimal for CPU Deployment
- **Claim:** For resource-constrained CPU deployment, mid-bit (4-5 bit) GGUF K-quant formats (e.g., Q4_K_S, Q5_0) are Pareto-optimal, balancing size reduction and accuracy.
- **Mechanism:** K-quant formats use hierarchical superblocks and finer-grained scaling to better preserve weight distributions at low bit-widths, avoiding severe error spikes of 3-bit quantization that disproportionately harm sensitive tasks.
- **Evidence anchors:** Q5_0 achieved a 65.19% size reduction with slight improvement in aggregate mean; Q4_K_S captured a strong trade-off; Q3_K_L offered modest compression with controlled degradation.
- **Break condition:** The frontier may reorder for different model families, scales, or more demanding evaluation suites.

### Mechanism 3: Throughput Increases Monotonically with Lower Bits for Decoding, but Not for Prefill
- **Claim:** Token-generation throughput increases monotonically with lower bit-widths due to reduced memory bandwidth pressure, but prompt-processing throughput improvements are irregular due to kernel and access pattern dependencies.
- **Mechanism:** Decoding is bandwidth-bound; lower bits reduce data transfer volume. Prefill is more compute-bound with varying kernel implementations per format, causing non-uniform throughput changes.
- **Evidence anchors:** Token-generation speed increased substantially for lower-bit schemes; prompt-processing throughput varied irregularly due to different kernel choices and memory access patterns.
- **Break condition:** Changes in hardware architecture or kernel design could eliminate throughput differentials.

## Foundational Learning
### Concept: Post-Training Quantization (PTQ)
- **Why needed:** The paper evaluates PTQ, where weights are quantized after full-precision training, explaining potential accuracy loss and focus on preserving the pre-trained distribution.
- **Quick check:** Why does PTQ risk greater accuracy degradation on complex reasoning tasks compared to simpler next-token prediction, even if perplexity changes are small?

### Concept: GGUF Format & Block-wise Quantization
- **Why needed:** All evaluated schemes are GGUF tensor types; quantization is applied per-block with stored scales/offsets, explaining multiple formats at the same nominal bit-width.
- **Quick check:** How does a hierarchical "K-quant" superblock with multiple sub-block scales attempt to reduce quantization error compared to a single scale for 32 weights?

### Concept: Downstream Evaluation vs. Perplexity
- **Why needed:** The paper argues perplexity (WikiText-2) is an insufficient proxy; benchmarks like GSM8K (multi-step reasoning) expose different, more sensitive failure modes than next-word prediction.
- **Quick check:** What mathematical property of a multi-step reasoning problem like GSM8K might make it more sensitive to weight quantization noise than a next-token prediction task?

## Architecture Onboarding
### Component map
Base Model (Llama-3.1-8B-Instruct FP16 GGUF) -> Quantizer (llama.cpp quantize) -> Evaluation Harness (lm_eval, perplexity/bench scripts) -> Hardware (Intel Xeon CPU) -> Decision Output (Comparative tables, Pareto plot)

### Critical path
1. Start from single FP16 GGUF.
2. Apply llama.cpp quantize for each target scheme.
3. Run unified evaluation (same prompts, harness versions).
4. Compute derived metrics: size reduction, AvgLoss (vs. FP16), throughput ratios.
5. Plot Pareto frontier (Size Reduction vs. AvgLoss) to identify non-dominated schemes.
6. Cross-reference with task-specific sensitivity and throughput for final scenario mapping.

### Design tradeoffs
- Accuracy vs. Footprint: Explicitly quantified; e.g., Q5_0 beats FP16 on Avg with 65% reduction, but Q3_K_S saves 77% with large accuracy drops.
- Footprint vs. Throughput: Lower bits increase decoding throughput; trade-off is whether accuracy cost is acceptable for speed gain.
- Aggregation vs. Specificity: Using an "Avg" score hides task-specific variance; a scheme good for Avg might still be bad for a critical task like GSM8K.

### Failure signatures
- Task collapse: Severe degradation (>5pt) on a critical task (e.g., GSM8K) while maintaining average via other tasks.
- PPL-accuracy divergence: Near-FP16 perplexity but significantly lower downstream score on a sensitive benchmark.
- Non-monotonicity: Higher nominal bit-width format performs worse than a lower one on a key task (e.g., Q5_K_S vs. Q4_K_S on GSM8K).

### First 3 experiments
1. Replicate Pareto Frontier: Quantize to Q4_K_S, Q5_0, Q3_K_L. Verify Q5_0 is top-left non-dominated and Q4_K_S is the subsequent knee point.
2. Task Sensitivity Probe: On GSM8K, chart score vs. effective bits. Confirm steep drop below ~4.5 bpw and Q5_K_S underperforming Q4_K_S.
3. Throughput-Quality Scatter: Plot token-generation throughput (tg128) against average downstream loss. Identify knee; confirm fastest (3-bit) have largest losses, Q4_K_S/Q5_0 region is optimal.

## Open Questions the Paper Calls Out
1. To what extent do the observed accuracy–compression trade-offs generalize to other model families (e.g., Mistral, Qwen) and scales (e.g., 70B parameter models) when using llama.cpp's GGUF quantizations?
2. What is the mechanistic relationship between the internal design choices of a GGUF format (e.g., super-block structure, scale metadata precision, symmetric vs. affine quantization) and its task-specific failure modes (e.g., GSM8K degradation vs. HellaSwag stability)?
3. How do llama.cpp GGUF quantization trade-offs manifest on non-CPU hardware (e.g., Apple Silicon, GPUs via CUDA/Metal, or specialized accelerators), where memory bandwidth/compute characteristics differ significantly from the evaluated Xeon platform?
4. Can the one-time quantization time (reported in Table 5) be substantially reduced for large models via algorithmic optimizations (e.g., parallelized quantization, smarter calibration sets) without degrading the downstream performance of the resulting GGUF file?
5. How does the optimal quantization scheme shift when operating under different context window lengths (e.g., 4K vs. 128K tokens), given that GGUF formats may have different memory layouts and kernel efficiencies that interact with KV cache quantization and attention computation overheads?

## Limitations
- **Reproducibility gaps:** Exact `llama.cpp` build configuration, specific hardware details (memory topology, BIOS states), and precise `lm-eval-harness` task versions are not fully specified, blocking exact replication of throughput and score numbers.
- **Scope constraints:** Evaluation is on a single model (Llama-3.1-8B-Instruct) and a fixed set of 5 downstream benchmarks; results may not generalize to other architectures, sizes, or more demanding evaluation suites.
- **Proxy limitations:** WikiText-2 perplexity is shown to be an unreliable proxy for some task-specific accuracy (e.g., IFEval), and the underlying mechanistic explanation for task sensitivity beyond GSM8K is incomplete.

## Confidence
- **Mechanism 1 (Format design > bit-width):** Medium (strong intra-format variance evidence, causal link inferred but not directly measured via per-layer error analysis).
- **Mechanism 2 (Mid-bit Pareto frontier):** High (empirical Pareto plot and non-dominated points directly supported by aggregated data).
- **Mechanism 3 (Throughput patterns):** High (measured trends align with theoretical memory-bandwidth vs. compute-bound distinctions and are directly reported).
