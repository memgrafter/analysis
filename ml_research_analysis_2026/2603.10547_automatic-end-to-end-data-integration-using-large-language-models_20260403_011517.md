# Automatic End-to-End Data Integration using Large Language Models

## Quick Facts
- **ArXiv ID:** 2603.10547
- **Source URL:** https://arxiv.org/abs/2603.10547
- **Reference Count:** 27
- **Primary Result:** An LLM-driven end-to-end data integration pipeline matches or exceeds human-configured pipelines in quality while reducing configuration time from ~19 hours to ~2 hours at a cost of ~$10 per case study.

## Executive Summary
This paper tackles the high manual effort in configuring data integration pipelines by proposing a fully automatic end-to-end solution using GPT-5.2. The pipeline generates all necessary configuration artifacts—schema mappings, value mappings, entity matching training data, and fusion validation sets—without human intervention. Evaluated across three case studies, the LLM-based pipeline achieves perfect schema matching F1, superior entity matching performance when using LLM-labeled training data, and comparable (though slightly lower for time-sensitive attributes) data fusion accuracy relative to human experts. Crucially, it dramatically reduces configuration time and cost, demonstrating the viability of LLMs for automating complex data integration workflows.

## Method Summary
The proposed pipeline orchestrates GPT-5.2 to generate each artifact sequentially. For schema matching, the model ingests structured representations of source tables (column names, value statistics, sample rows) and a target JSON Schema, then outputs a JSON array of column correspondences. Value normalization uses deterministic code-based tools (e.g., Babel, Pint) guided by LLM-suggested mappings. Entity matching employs an active learning loop: an LLM labels an initial seed of high-similarity and diverse candidate pairs; a classifier (RandomForest/XGBoost) is trained and iteratively expanded by querying the LLM on points of disagreement. Finally, for data fusion, the LLM generates a validation set of well-known entities (with optional RAG for temporal accuracy) to select the best conflict-resolution heuristic configuration. The entire workflow is executed within the PyDI framework.

## Key Results
- Schema matching achieves perfect F1 (1.00), including on datasets with non-descriptive headers where the model infers semantics from value patterns.
- Entity matching with LLM-labeled training data (via active learning) yields higher average F1 (0.937) than human-labeled data (0.916).
- Data fusion accuracy is slightly lower with LLM-generated validation (76.1% vs. 81.6% human), primarily due to temporal knowledge gaps; the gap is negligible for static domains.
- Configuration time is reduced from an estimated 19 person-hours to approximately 2 hours at a cost of about $10 per case study.

## Why This Works (Mechanism)

### Mechanism 1: Schema Matching via Semantic Alignment
- **Claim:** GPT-5.2 can infer correct schema correspondences by leveraging its embedded knowledge of attribute semantics, even when source column names are non-descriptive.
- **Mechanism:** The pipeline prompts the LLM with a structured representation of each source table (column names, value statistics, sample rows) and a JSON Schema description of the target. The model maps source columns to target attributes based on semantic alignment derived from data values and contextual knowledge.
- **Core assumption:** The LLM's training data contains sufficient examples of similar schemas and real-world entities to recognize cross-domain attribute meanings (e.g., "studio" vs. "developer").
- **Evidence anchors:**
  - [abstract] "schema matching achieves perfect F1 (1.00)... includes two datasets with non-descriptive headers where the model differentiated columns based solely on value patterns."
  - [section III] "The LLM pipeline directly prompts GPT-5.2... The source representation includes column names, a value summary... and sample rows... GPT-5.2 returns a JSON array of correspondences."
  - [corpus] Weak support; neighbor papers focus on different pipeline domains (e.g., building layout, ASR). No direct evidence on schema matching from corpus.
- **Break condition:** Failure expected for complex correspondences (1:n, aggregation), normalized/related tables, or domains absent from the LLM's training data.

### Mechanism 2: Active Learning with LLM Labeling
- **Claim:** Active learning guided by an LLM-generated initial label set produces higher-quality entity matching training data than human-labeled sets, due to focused sampling of informative and diverse candidate pairs.
- **Mechanism:** Embedding-based blocking generates a candidate pool. The LLM labels an initial seed set (prioritizing high-similarity pairs plus diversification). An active learning loop then identifies classifier disagreement points, requests LLM labels for those, and iteratively expands the training set. The final model is selected via an LLM-labeled validation set.
- **Core assumption:** GPT-5.2 can accurately label a sufficiently large and informative subset of candidate pairs to train a conventional ML model (RandomForest/XGBoost) that generalizes well.
- **Evidence anchors:**
  - [abstract] "Entity matching with LLM-labeled training data yields higher average F1 (0.937) than human-labeled data (0.916)."
  - [section V] "The active learning workflow... labels only 600–2,658 examples per dataset pair... The active learning variant achieved the best F1 in five of six cases."
  - [corpus] Neighbor "HILTS" [25] explores human-LLM collaborative labeling, indirectly supporting that LLM pseudo-labeling can reduce annotation effort.
- **Break condition:** Degradation if the LLM exhibits systematic labeling biases on specific entity types, or if the initial seed set misses critical/rare patterns that active learning cannot recover.

### Mechanism 3: LLM-Generated Validation for Fusion
- **Claim:** LLM-generated validation sets (via parametric knowledge or RAG) can effectively select data fusion conflict resolution heuristics for domains with predominantly static attributes, bridging the gap to human-created validation sets.
- **Mechanism:** The LLM selects a set of well-known entities from a random sample and generates the perceived correct value for each conflicting attribute. For RAG, it performs web searches per attribute to verify. The pipeline evaluates multiple resolver configurations against this set and picks the highest-accuracy one.
- **Core assumption:** For well-known entities, the LLM's parametric knowledge (or retrieved web data) contains accurate, time-appropriate ground truth values for the attributes in question.
- **Evidence anchors:**
  - [abstract] "Data fusion accuracy is slightly lower with LLM validation (76.1% vs. 81.6% human), primarily due to temporal knowledge gaps."
  - [section VI] "For domains with predominantly static attributes (Music, Games), the gap is negligible... The gap in Companies is largely attributable to temporal mismatches."
  - [section IX] "LLM-generated validation sets can guide fusion configuration selection comparably to human-created ones for domains with predominantly static attributes."
- **Break condition:** Failure dominates for time-sensitive attributes (e.g., revenue, headquarters city) where dataset values are outdated relative to LLM knowledge, or for obscure entities not covered in training data or web search results.

## Foundational Learning
- **Concept: Data Integration Pipeline Steps** (Schema Matching → Value Normalization → Entity Matching → Data Fusion)
  - **Why needed here:** Understanding the sequential dependencies and artifact requirements (mappings, labels, validation sets) is essential to grasp where and how the LLM intervenes.
  - **Quick check question:** What specific artifact does each step produce that the next step consumes?
- **Concept: Active Learning for Label Efficiency**
  - **Why needed here:** The entity matching quality hinges on a cost-effective labeling strategy; the paper's key innovation is using an LLM to bootstrap an active learning loop instead of labeling all pairs.
  - **Quick check question:** How does the active learning loop decide which candidate entity pairs to send to the LLM for labeling in each iteration?
- **Concept: Evaluation Metrics for Integration Tasks** (F1 for schema/entity matching, accuracy for fusion, structural metrics like row gain/fusion ratio)
  - **Why needed here:** Interpreting the results requires distinguishing between step-wise test set metrics and end-to-end structural outcomes, and understanding their limitations (e.g., small test sets, domain-specificity).
  - **Quick check question:** Why does a higher fusion ratio not always indicate better integrated data quality?
- **Concept: LLM Prompt Engineering for Structured Output**
  - **Why needed here:** The pipeline relies on the LLM generating JSON-formatted correspondences and labels; prompt design directly impacts reliability and parseability.
  - **Quick check question:** How does the prompt structure enforce that the LLM output conforms to the required JSON schema?
- **Concept: Embedding-Based Blocking**
  - **Why needed here:** Entity matching candidate generation uses embeddings to reduce the pairwise comparison space; understanding this step explains the scalability of the active learning loop.
  - **Quick check question:** What similarity threshold or blocking technique is used to generate the initial candidate pool?

## Architecture Onboarding
- **Component map:**
  Prompt Modules -> Active Learning Loop -> Code-Based Normalizers -> Fusion Config Selector -> PyDI Framework
- **Critical path:** Schema Matching → Value Normalization → (Active Learning & Entity Matching Training) → Fusion Validation Set Generation → Fusion Configuration Selection → Full Execution.
- **Design tradeoffs:**
  - **Cost vs. Quality:** RAG for fusion validation (+$21) modestly improves Companies accuracy but is expensive; LLM-only is cheaper but fails on temporal attributes.
  - **Active Learning Budget:** More iterations yield larger training sets but higher LLM cost; paper uses ~100 seed pairs + iterative batches to reach ~2k pairs total.
  - **Generality vs. Performance:** The pipeline uses generic PyDI similarity metrics and classifiers; hand-crafted blocking/key selection in human baseline sometimes outperforms on specific pairs.
- **Failure signatures:**
  - **Schema Matching:** F1 drop on tables with 1:n relationships, nested/related tables, or highly domain-specific attributes not in LLM knowledge.
  - **Entity Matching:** Degraded F1 on entities with scarce/ambiguous textual signals (e.g., companies with common names) or where LLM labeling errors compound in active learning.
  - **Data Fusion:** Accuracy collapse (>10% gap) on use cases with many time-varying attributes (e.g., financial data) if using LLM-only validation.
  - **Cost Overrun:** Unexpectedly high LLM usage if active learning loop fails to converge or if value normalization mappings cover an explosion of unique categorical values.
- **First 3 experiments:**
  1. **Schema Matching Edge Case:** Test on sources with completely opaque headers (e.g., "col_a", "col_b") and values that require deep domain inference (e.g., cryptic product codes). Verify if LLM can recover correspondences without value semantics.
  2. **Label Quality Isolation:** Re-train the entity matcher using *only* the LLM seed labels (no active learning iterations) vs. full active learning output. Measure F1 delta to quantify active learning's marginal contribution.
  3. **Temporal Sensitivity Probe:** In the Companies use case, modify fusion test sets to include only static attributes (e.g., founded year, industry) vs. only time-sensitive ones (revenue, headquarters). Re-run validation set selection with LLM-only to confirm the performance gap closes for static-only.

## Open Questions the Paper Calls Out
- How can the automatic pipeline be extended to handle complex schema correspondences, such as 1:n mappings or aggregation across normalized tables?
- To what extent does the LLM-based pipeline generalize to proprietary or domain-specific data outside the training distribution of GPT-5.2?
- How can temporal knowledge gaps in LLM-generated validation data for data fusion be effectively addressed?
- What standardized benchmarks are required to comprehensively evaluate end-to-end data integration pipelines, including entity matching and data fusion with ground truth?
- Can iterative feedback mechanisms between downstream and upstream pipeline steps improve overall integration quality?

## Limitations
- The pipeline assumes flat source tables with 1:1 attribute correspondences and does not support normalized schemas or complex mappings.
- Performance on time-sensitive attributes degrades due to temporal mismatches between LLM knowledge and dataset values; RAG-based mitigation adds cost.
- Active learning stability depends on the accuracy of initial LLM labels; systematic biases could compound errors across iterations.

## Confidence
- **Schema Matching via Semantic Alignment:** Medium (Perfect F1 on 3 datasets, but includes only 2 with opaque headers; untested on complex/normalized schemas).
- **LLM-Active Learning > Human Labels:** Medium (5/6 cases improved, but marginal contribution of active learning vs. seed labels not isolated; labeling bias risk).
- **LLM Validation for Fusion:** Medium-Low (Comparable for static domains, but 5.5% absolute accuracy drop on temporal attributes—primary failure mode identified).

## Next Checks
1. **Complex Schema Stress Test:** Evaluate on sources requiring 1:n or hierarchical mappings (e.g., multiple source columns → aggregated target attribute) and normalized/related tables.
2. **Label Source Isolation:** Ablate the active learning loop: train entity matchers using *only* LLM seed labels (no iterative queries). Compare F1 to full pipeline to quantify active learning’s marginal gain.
3. **Temporal Attribute Probe:** In the Companies case, recompute fusion accuracy *separately* on static-only (e.g., industry, founded year) vs. time-sensitive-only (e.g., revenue, HQ) attributes using LLM-only validation sets. Expect gap to vanish for static, widen for temporal.
