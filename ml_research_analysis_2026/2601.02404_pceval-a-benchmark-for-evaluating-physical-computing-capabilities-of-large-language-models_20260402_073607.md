# PCEval: A Benchmark for Evaluating Physical Computing Capabilities of Large Language Models

## Quick Facts
- **arXiv ID:** 2601.02404  
- **Source URL:** https://arxiv.org/abs/2601.02404  
- **Reference count:** 35  
- **Primary result:** LLMs struggle with physical breadboard layout, achieving at most 45.2% success due to pin conflicts and bypasses, while code generation reaches up to 67.8%.

## Executive Summary
PCEval introduces the first benchmark to automatically evaluate large language models on physical computing tasks, combining software generation with hardware layout reasoning. The benchmark comprises 50 Arduino projects of increasing complexity, assessing four capabilities: logical circuit design, physical breadboard layout generation, code generation from logical specs, and code generation from physical layouts. Evaluation uses simulation-based functional tests along with circuit validation that detects pin conflicts and layout violations. Testing 13 LLMs reveals a stark disparity: code generation and logical circuit design attain up to 67.8% and 66.0% success respectively (with o3-mini), but physical circuit generation peaks at only 45.2%, with failures primarily caused by breadboard topology errors. Performance on physical tasks degrades sharply with complexity, highlighting persistent challenges in spatial and physical constraint reasoning. Prompting-based mitigation strategies yield only partial improvements.

## Method Summary
PCEval builds on 50 Arduino Uno projects, each annotated with a description, a logical circuit, a physical breadboard layout, corresponding code, and a test procedure. The evaluation pipeline prompts LLMs to generate outputs for four tasks: logical circuit generation (D→L), physical circuit generation (D→P), code from logical specs (L→C), and code from physical layouts (P→C). LLM responses are parsed as JSON and validated against custom circuit rules that check for breadboard violations such as pin conflicts and bypasses. Valid circuits are executed in the Wokwi simulator with the provided test procedures; success requires passing all functional tests. The benchmark also measures error counts (pin conflicts, bypasses, missing/extraneous components) and code similarity via CodeBLEU. This fully automated approach enables scalable and reproducible assessment of both software and hardware reasoning capabilities.

## Key Results
- Physical circuit generation (D→P) peaks at 45.2% success (o3-mini), with pin conflicts and breadboard bypasses as dominant errors.
- Code generation (L→C) and logical circuit design (D→L) achieve higher success rates of up to 67.8% and 66.0% respectively.
- Performance on physical tasks degrades non-linearly with complexity; e.g., o3-mini D→P success drops from 65.0% at Level 1 to 25.5% at Level 4.

## Why This Works (Mechanism)
### Mechanism 1
**Claim:** Physical circuit generation fails primarily due to violations of breadboard electrical topology—specifically pin conflicts (multiple wires to one hole) and breadboard bypasses (direct component-to-component wires skipping the board).  
**Mechanism:** LLMs produce connections that are logically consistent but physically unrealizable on a breadboard because they do not model the spatial constraints (e.g., vertical connectivity within a column segment, isolation between top/bottom halves).  
**Core assumption:** Breadboard layout requires non-local spatial reasoning about shared nodes and routing, which is absent in LLM training on textual circuit descriptions or code.  
**Evidence anchors:**  
- Abstract: "physical breadboard layout creation, particularly in managing proper pin connections and avoiding circuit errors."  
- Section 4.2: "pin-conflict counts per sample are highest among all error types" and "breadboard bypasses vary by model."  
- Corpus: Neighboring benchmarks (e.g., MICRO25, EmbedGenius) do not evaluate physical layout constraints, confirming PCEval’s unique focus on this gap.  
**Break condition:** If pin conflict and bypass error rates approach zero across models without sacrificing functional correctness, the mechanism is resolved.

### Mechanism 2
**Claim:** LLM performance degrades non-linearly with project complexity, especially for physical tasks, due to increasing component count and connection density.  
**Mechanism:** More components and connections amplify the spatial reasoning load, causing inconsistency in pin assignments and layout validity as the model must track more constraints simultaneously.  
**Core assumption:** Complexity metrics (number of connections, components) are stronger predictors of failure in physical circuit generation than code length, as shown by sharper declines versus logical/code tasks.  
**Evidence anchors:**  
- Abstract: "Performance on physical tasks drops drastically with complexity."  
- Section 4.2: Example: o3-mini D,C→P success L1 65.0% → L4 25.5%; similar drops for other models.  
- Corpus: Corpus does not provide direct evidence; related benchmarks (e.g., VerilogEval) focus on HDL, not physical layout complexity effects.  
**Break condition:** If success rates for physical tasks plateau or improve at higher complexity levels, the sensitivity claim is falsified.

### Mechanism 3
**Claim:** Self-improvement and chain-of-thought prompting yield only partial gains because they cannot instill fundamental understanding of physical constraints.  
**Mechanism:** Iterative feedback corrects superficial errors (e.g., missing wires) but does not teach the model breadboard topology rules; CoT may help structure reasoning but still lacks grounded spatial knowledge.  
**Core assumption:** Current LLM architectures require more than better prompting—they need explicit representation of physical constraints to overcome the logical-to-physical gap.  
**Evidence anchors:**  
- Abstract: "Mitigation strategies yield only partial improvements."  
- Section 4.3: o3-mini overall 61.7%→76.5% with self-improvement, but D,C→P only 48.0%→58.0%; CoT helped GPT-4o D,P→C +10.4% but varied across models.  
- Corpus: Other benchmarks use CoT for code generation but not for physical layout, so the limited impact here is novel.  
**Break condition:** If a simple prompting technique (e.g., few-shot with layout rules) achieves >90% on physical tasks, the representational gap is prompting-artifact-limited.

## Foundational Learning
- **Breadboard electrical topology**  
  *Why needed:* PCEval’s validation metrics (pin conflicts, bypasses) depend on understanding how holes connect vertically within columns and separate between top/bottom halves.  
  *Quick check:* If two wires connect to the same breadboard hole in column 10a, is that allowed? Why or why not?

- **Task decomposition for benchmark design**  
  *Why needed:* PCEval isolates four capabilities (logical circuit, physical circuit, code from logical, code from physical) to diagnose specific weaknesses; misinterpreting them conflates distinct reasoning modes.  
  *Quick check:* Why test code generation from physical circuits separately from logical circuits?

- **Simulation-based automated evaluation**  
  *Why needed:* PCEval uses Wokwi to execute test procedures without human input; understanding this explains how scalability and reproducibility are achieved.  
  *Quick check:* What does “simulation success” mean in PCEval, and how does it differ from circuit validation errors?

- **Complexity metrics (connections, components, lines of code)**  
  *Why needed:* Performance correlates more strongly with connection count than code length for physical tasks; this metric choice reveals the spatial reasoning bottleneck.  
  *Quick check:* For physical circuit tasks, which metric correlates more strongly with failure: number of connections or lines of code?

## Architecture Onboarding
Component map: Dataset (50 Arduino projects with D, L, P, C, T) -> LLM interface (prompt templates for D→L, D→P, L→C, P→C, strict JSON output) -> LLM predictions -> Evaluation engine (Wokwi simulator + custom circuit validator checking pin conflicts, bypasses, missing/extraneous components) -> Metrics (simulation success rate, error counts, CodeBLEU).

Critical path: Select project → choose task → format prompt → query LLM API → parse JSON output → validate circuit → run simulation → record success/errors → repeat for all models/projects.

Design tradeoffs:
- Arduino Uno focus ensures educational relevance but limits industrial applicability; component-agnostic I/O specs aim for platform portability.
- Automated simulation sacrifices real-world factors (component tolerances, power noise) for reproducibility and scale.
- Breadboard-only layouts exclude PCB design but simplify validation to hole-based rules.

Failure signatures:
- High pin conflict count (>4 per sample) indicates the model does not respect breadboard’s one-wire-per-hole constraint.
- >30% performance drop from Level 1 to Level 4 in D,C→P signals complexity sensitivity in spatial reasoning.
- CodeBLEU scores similar for success/failure outcomes suggest small pin-number errors cause failure despite syntactic similarity.

First 3 experiments:
1. Reproduce baseline: Run o3-mini on Level 1 “LED Blink Basic” for D,C→P; expect ~65% success and validate circuit errors are near-zero.
2. Error distribution analysis: For GPT-4o on D,C→P Level 4 projects, tally pin conflicts vs. bypasses; expect pin conflicts to dominate (GPT-4o 2.07 vs. 1.16 bypasses per sample).
3. Mitigation test: Apply self-improvement prompting to Claude 3.7 on D,P→C; expect ~5–10% gain (71.6%→83.6%), confirming partial but not complete fix.

## Limitations
- Scope generalizability: Arduino/Uno focus may not transfer to other hardware platforms or real-world assembly.
- Simulation vs. reality: Wokwi omits physical tolerances, power noise, and wiring friction.
- Breadboard specificity: Findings are tied to breadboard topology; PCB and wire-wrapping constraints differ fundamentally.
- Corpus size: Only 50 tasks; risk of model training artifact inflation.

## Confidence
- Mechanism 1 (Pin conflicts/bypasses as primary failure): **High** – Strong error-type analysis isolates breadboard topology violations.
- Mechanism 2 (Non-linear complexity sensitivity): **Medium** – Correlation shown but causality not fully isolated.
- Mechanism 3 (Prompting cannot fix fundamental gaps): **Low** – Partial gains observed; untested advanced prompting could improve further.

## Next Checks
1. Cross-platform generalization: Re-run top models on PCEval tasks retargeted to Raspberry Pi Pico; measure drop in physical layout success vs. Arduino.
2. Real-world transfer test: Build 10 highest-scoring simulated physical circuits on actual breadboards; record assembly errors to quantify simulation-to-reality gap.
3. Ablation on spatial cues: For D,C→P tasks, remove spatial descriptors from logical spec prompts; compare success drop to baseline to isolate dependency on spatial language.
