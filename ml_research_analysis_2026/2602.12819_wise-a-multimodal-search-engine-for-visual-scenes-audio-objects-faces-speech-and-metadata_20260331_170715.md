# WISE: A Multimodal Search Engine for Visual Scenes, Audio, Objects, Faces, Speech, and Metadata

## Quick Facts
- arXiv ID: 2602.12819
- Source URL: https://arxiv.org/abs/2602.12819
- Reference count: 18
- Primary result: WISE enables efficient multimodal retrieval (text, image, audio, composed queries) over large audiovisual collections (55M images, 6000h video) with sub-second latency using vector search and pre-trained models.

## Executive Summary
WISE is an open-source multimodal search engine designed to integrate and search across diverse audiovisual content types, including visual scenes, objects, faces, acoustic events, speech transcripts, and metadata. It supports natural language and reverse-media queries, as well as composed searches combining multiple modalities and metadata filters. The system leverages pre-trained models (OpenCLIP, OWLv2, InsightFace, CLAP) to embed media into a shared vector space, indexed with Faiss for fast approximate nearest neighbor search. Demonstrated to handle collections up to 55 million images or 6,000 hours of video with sub-second response times, WISE has been deployed in journalism, film research, and wildlife conservation, offering a practical solution for sensitive data via local deployment.

## Method Summary
WISE processes media by sampling frames from video (e.g., 2 fps) and audio windows (e.g., 4 s with 2 s overlap). Each modality uses dedicated feature extractors: OpenCLIP for scene-level visual embeddings, OWLv2 for object detection, InsightFace for face embeddings, CLAP for audio events, and WhisperX for speech transcripts. Extracted features and metadata are stored in a SQLite database, while vector embeddings are indexed using Faiss (IVFFlat for most, IVFPQ for high-volume outputs like object regions). Queries are encoded with the same models and dispatched to relevant indices; results are fused and filtered by metadata to produce a final ranked list. The modular pipeline allows independent scaling and replacement of components.

## Key Results
- Scales to 55 million images or 6,000+ hours of video with sub-second query latency.
- Supports cross-modal retrieval (text-to-image/audio, reverse image/audio) and composed queries (e.g., "train" + metadata "Germany").
- Deployed in real-world domains (journalism, film research, wildlife conservation) and released as open-source for local deployment.

## Why This Works (Mechanism)
**Shared Vector Space**: WISE maps all modalities into a common embedding space using pre-trained models (e.g., OpenCLIP aligns images and text; CLAP aligns audio and text). This geometric alignment enables cross-modal similarity search: a text query and a media segment are considered related if their vectors are close. Evidence: Section 3 describes how feature extractors map inputs into a shared space and approximate nearest neighbor retrieval.

**Scalable ANN Indexing**: To handle millions of vectors efficiently, WISE employs Faiss's inverted file (IVF) indices, which cluster vectors and search only a subset of clusters (probes). For high-output extractors (e.g., OWLv2's many region proposals), product quantization (PQ) compresses vectors into discrete codes, drastically reducing memory and I/O while preserving recall. Evidence: Section 3 details the use of IndexIVFFlat and IndexIVFPQ; Section 4 reports sub-second latency on large datasets.

**Modular Fusion for Composite Queries**: Separate indices per modality enable arbitrary query combinations without re-indexing. At query time, the system retrieves candidate lists from each relevant index and applies logical operations (AND) or score fusion, while metadata filters are applied post-retrieval via SQLite FTS. Evidence: Section 2 illustrates composed retrieval (e.g., "train" + "Germany"); Section 3 describes the SQLite metadata store.

- Why needed: WISE's extensibility relies on a clear separation of Loader, Extractor, Store, Index, and Search modules; engineers must trace dataflow to debug or extend.  
- Quick check: To add a new audio event detector (e.g., animal calls), which modules are modified and what interface must the detector adhere to?

## Architecture Onboarding
**Component map**: Loader -> Extractor -> Store -> Index -> Search. Loader ingests media and samples frames/audio; Extractors (pre-trained models) produce embeddings; Store writes features and metadata to SQLite; Index builds Faiss indices from stored vectors; Search handles query encoding, ANN retrieval, fusion, and filtering.

**Critical path**:  
- Ingestion: Load -> Extract -> Store -> Index (offline).  
- Query: User input -> Search encodes -> Index ANN search -> Result fusion/metadata filter -> UI.

**Design tradeoffs**:  
- Precision vs. Latency: IVF `nprobes` and PQ settings directly control speed/accuracy; defaults prioritize sub-second response.  
- Storage vs. Granularity: Per-frame vs. per-second features affect index size and temporal precision; object detectors generate many regions requiring PQ compression.  
- Modularity vs. Consistency: Independent models risk semantic misalignment; no cross-modal fine-tuning.

**Failure signatures**:  
- No results: Check index existence and feature extraction logs for that modality.  
- Irrelevant composite results: Verify fusion logic and metadata filter application; may be too restrictive or misapplied.  
- High latency (>1s): Faiss index misconfigured (too few probes) or extractor queue saturated.

**First 3 experiments**:  
1. Ingestion sanity check: Process a small test set; verify frame/audio sampling, extractor output dimensions, and database writes.  
2. Single-modality recall: For known items, run text queries and confirm appearance in top-k; compute recall@10 on a labeled subset.  
3. Composite query test: Run combined modality and metadata filters; ensure results satisfy all constraints and measure recall drop vs. single-modality baselines.

## Open Questions the Paper Calls Out
**Open Question 1**: How does the selection of specific multimodal foundation models (e.g., OpenCLIP vs. alternatives) affect retrieval accuracy across different query types and modalities?  
*Basis*: The paper employs several pre-trained models but provides no comparative analysis or ablation to justify their choice; focus is on system integration.  
*Why unresolved*: Performance claims emphasize scalability and speed but omit accuracy metrics broken down by modality or model. Optimal model selection remains unclear.  
*What evidence would resolve*: Systematic benchmarking of multiple candidate models on standardized multimodal retrieval datasets with consistent pipelines, publishing per-modality metrics (e.g., mAP@10).

**Open Question 2**: What are the failure modes and reliability limits of composed multimodal queries (e.g., face + text, metadata + visual) in real-world deployments?  
*Basis*: The paper demonstrates composed query examples but lacks error analysis, user studies, or discussion of edge cases.  
*Why unresolved*: Composite search is highlighted as key, yet robustness unassessed; users in critical domains cannot trust results for complex investigations.  
*What evidence would resolve*: Log analysis from operational WISE instances cataloging failure patterns; user studies measuring success rates on ambiguous/composed queries; challenge sets with known difficult compositions.

**Open Question 3**: To what extent does WISE's fixed frame-sampling strategy (2 fps) impair retrieval of temporally extended video events or actions?  
*Basis*: Videos are processed by uniform frame sampling, with no explicit temporal modeling; no evaluation of this design vs. alternatives.  
*Why unresolved*: Many natural queries involve actions requiring temporal coherence; sampling may miss critical frames but trade-off unanalyzed.  
*What evidence would resolve*: Comparative experiments using different sampling rates or temporal aggregation methods (e.g., VideoCLIP) on datasets with temporal annotations (AVA, Charades); measuring recall for event-based queries.

## Limitations
- Exact model checkpoints, preprocessing (image size, audio sample rate), and Faiss hyperparameters (nlist, nprobes, PQ codebook size) used in production are not specified.
- Detailed design of the aggregator mode for distributed search (query routing, result merging, fault tolerance) is omitted.
- Real-world effectiveness lacks quantitative user studies or comparative benchmarks against alternative tools; deployment anecdotes are informal.

## Confidence
- **Core Mechanism (shared vector space + ANN)**: Medium. Described clearly but lacks ablation isolating contributions of each model/fusion strategy; break conditions hypothesized but not validated.
- **Scalability & Latency Claims**: High. Concrete dataset sizes (55M images, 6000h video) and sub-second latency are specific and backed by system description, though exact hardware and query complexity undisclosed.
- **Deployment Utility & Open-Source Availability**: Medium. Case studies mentioned anecdotally; open-source release confirmed but adoption metrics, community activity, and integration ease unknown.
