# XShare: Collaborative in-Batch Expert Sharing for Faster MoE Inference

## Quick Facts
- **ArXiv ID:** 2602.07265
- **Source URL:** https://arxiv.org/abs/2602.07265
- **Reference Count:** 14
- **Primary Result:** Reduces activated experts by up to 30%, cuts peak GPU load by up to 3x in expert-parallel deployments, and improves throughput by up to 14% in speculative decoding while keeping accuracy loss below 1%.

## Executive Summary
XShare tackles the surge in expert activations during inference for Mixture-of-Experts (MoE) models, which is exacerbated by request batching and speculative decoding. It reformulates expert selection as a batch-level optimization: aggregating per-token gating scores across the batch and greedily selecting the most valuable experts to activate, without retraining the model. Experiments demonstrate substantial reductions in the number of experts used and GPU load, along with meaningful throughput improvements, all while preserving model accuracy across heterogeneous data.

## Method Summary
At inference time, XShare takes a batch of tokens and obtains gating scores from the existing MoE gating network for each token. It then solves a modular optimization problem: choose a fixed-size set of experts that maximizes the sum of gating scores over all tokens. The greedy algorithm iteratively adds the expert that yields the largest marginal increase to the total score. Once the expert set is chosen, all tokens in the batch are routed through these experts (each token’s output is a weighted combination of its assigned experts). This collaborative sharing means many tokens reuse the same experts, cutting total computation. The method plugs into existing MoE inference pipelines with minimal changes and incurs negligible overhead.

## Key Results
- Activated experts reduced by up to 30% under standard batching.
- Peak GPU load cut by up to 3x in expert-parallel deployments.
- Throughput gains of up to 14% in speculative decoding.
- Accuracy maintained within 1% across heterogeneous datasets.

## Why This Works (Mechanism)
XShare leverages the redundancy in gating preferences within a batch: many tokens often favor similar experts. The greedy selection identifies a compact expert set that covers the batch well, maximizing the aggregated gating scores. By constraining all tokens to this set, the number of expert forward passes drops dramatically while preserving the essential representational capacity. The greedy approach is computationally cheap (near-linear in number of experts), making it suitable for high-throughput inference. Moreover, because it does not alter model parameters, there is no risk of catastrophic forgetting or distribution shift.

## Architecture Onboarding
**Component Map:** Input Token Batch → Gating Network → XShare Batch-Aware Selector → Dispatcher → Expert Modules (parallel) → Aggregator → Output

**Critical Path:** For each batch, the gating network computes expert scores for all tokens. XShare then runs its greedy algorithm to select a fixed number of experts (budget K). The dispatcher routes each token to all selected experts (or uses original gating weights to weight their contributions). Experts execute in parallel, potentially across multiple GPUs. Finally, the aggregator combines expert outputs according to the original gating weights to produce the final token representations.

**Design Tradeoffs:**
- *Greedy selection vs. optimality*: The greedy algorithm runs in O(EK) time (E = total experts) and yields near-optimal coverage, but is not guaranteed global optimum. Simpler than integer programming.
- *Fixed budget per batch*: XShare requires a predetermined K (experts per batch). Larger K improves accuracy but reduces sharing; smaller K increases sharing but may hurt model capacity.
- *Batch size dependency*: Benefits grow with batch size; very small batches see little sharing and may incur overhead with no gain.

**Failure Signatures:**
- Gating scores are nearly uniform → selection does not meaningfully prune experts; expert reduction and speedup diminish.
- Highly diverse batches (e.g., mixed languages and tasks) → the selected expert set may be insufficient, causing accuracy drop beyond acceptable margin (<1%).
- Extremely small batches → selection overhead dominates, leading to net slowdown.
- Model with highly imbalanced expert utilization → some experts are rarely selected, possibly starving them and affecting training dynamics if the model is later fine-tuned (though XShare is inference-only).

**First Experiments:**
1. **Functional Test:** Run XShare on a single batch of known inputs (e.g., from a validation set) and verify that the number of experts activated is reduced while output logits are identical (or within tolerance) to baseline.
2. **Performance Profiling:** Measure the added latency of the XShare selection step as batch size and expert count vary; confirm it remains a small fraction of total inference time.
3. **Parameter Sweep:** Vary the expert budget K and plot expert reduction, throughput, and accuracy to identify a suitable operating point for a target dataset.

## Limitations
- Evaluation limited to simulations/controlled benchmarks; real-world deployment on diverse MoE architectures and production traffic is unproven.
- The overhead of the greedy selection algorithm is not quantified; it may offset gains for small batches or latency-sensitive applications.
- Generalization to extreme data distributions or non-standard batching patterns (e.g., highly imbalanced request arrivals) remains unclear.
- Comparative advantage over contemporaneous methods (e.g., MoE-SpAc, Speculative MoE) is not directly established.
