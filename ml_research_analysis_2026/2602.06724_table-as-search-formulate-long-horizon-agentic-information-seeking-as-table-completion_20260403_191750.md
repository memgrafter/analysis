# Table-as-Search: Formulate Long-Horizon Agentic Information Seeking as Table Completion

## Quick Facts
- **arXiv ID**: 2602.06724
- **Source URL**: https://arxiv.org/abs/2602.06724
- **Reference count**: 40
- **Primary result**: TaS achieves state-of-the-art on long-horizon information seeking benchmarks (e.g., GAIA Deep Search: 52.4% vs. 38.4%), with superior efficiency and robustness.

## Executive Summary
The Table-as-Search (TaS) framework addresses a fundamental weakness in long-horizon agentic information seeking: the fragility of tracking complex search states within a plain-text context. TaS reformulates the problem as structured table completion, where a user query defines a table schema (rows = candidate entities, columns = constraints and required information). An external database persistently stores filled cells (verified results) and empty cells (explicit plans). A central planner agent orchestrates parallel sub-agents to expand rows (discover candidates) or populate cells (fill attributes), manipulating the table via atomic database operations. This separation of strategic planning from execution offloads state from the agent's context window, yielding significant gains in accuracy, robustness, and search efficiency on Deep, Wide, and DeepWide benchmarks.

## Method Summary
TaS is a multi-agent system that externalizes all search state into a relational table in an external database (MongoDB). The process begins with a planner agent parsing the natural language query into a structured schema `S = <K, C, I>`, where `K` are candidate keys (row identifiers), `C` are constraint columns, and `I` are information columns to retrieve. The planner then enters a loop, deciding between two modes based on table saturation: **Row Expansion** (generating diverse search queries to discover new candidates, appended as new rows) or **Cell Population** (selecting incomplete rows and dispatching sub-agents to fill specific missing cells). Sub-agents perform deep searches using web tools (search, visit) and return results for atomic `update_records` operations. The loop continues until the planner deems the table sufficiently complete, at which point it synthesizes the final answer by filtering and extracting data from the table.

## Key Results
- On GAIA (Deep Search), TaS (Gemini-2.5-Flash) reaches **52.4%** vs. ReAct-MA 38.4% (+14.0%).
- On WideSearch, TaS (Claude-Sonnet-4) achieves **Item-F1 60.5%** (vs. 57.9%) and **Column-F1 74.7%** (vs. 68.0%).
- On the DeepWide E-commerce benchmark, TaS surpasses Gemini DeepResearch with **Column-F1 55.9% vs. 51.2%** and **Item-Precision 63.5% vs. 58.3%**.
- TaS demonstrates better performance with fewer tool calls and wider scaling advantages on hard subsets.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim**: Externalizing search state into a structured table prevents context dilution and "lost-in-the-middle" failures.
- **Mechanism**: The table acts as a persistent, queryable memory, offloading the burden of tracking thousands of search results from the finite context window to an external database. Filled cells store verified facts; empty cells are an explicit, inspectable plan. This maintains state fidelity over long horizons.
- **Core assumption**: The search space can be decomposed into independent candidate entities (rows) and verifiable attributes/constraints (columns).
- **Evidence anchors**: Authors state tracking within plain-text is "inherently fragile" and that the table "precisely manages search states." The problem of context degradation is well-established in neighboring work (e.g., "Lost in the Maze").
- **Break condition**: Tasks where the search state is inherently sequential and not decomposable into candidate-attribute pairs, or where schema definition overhead outweighs benefits for very simple queries.

### Mechanism 2
- **Claim**: The explicit table schema transforms implicit planning into a concrete, verifiable structure, reducing planning errors and hallucination.
- **Mechanism**: The planner must instantiate the schema `(K, C, I)` upfront, forcing a priori decomposition of the query. Subsequent actions are goal-directed towards filling specific cells, making the plan transparent and auditable.
- **Core assumption**: The planner LLM can reliably map a natural language query to a structured schema.
- **Evidence anchors**: The formal mapping `ϕ(q)→S` is defined. The main loop's actions are triggered by empty cells. Strong gains on DeepWide Search (requiring both breadth and depth) suggest the schema effectively unifies conflicting search goals.
- **Break condition**: Queries with highly ambiguous or user-defined constraints that resist clear schema formalization, leading to schema drift mid-execution.

### Mechanism 3
- **Claim**: Decoupling high-level planning (row/cell strategy) from low-level execution (parallel sub-agent search) enables efficient exploration and robust scaling.
- **Mechanism**: The central planner operates on the abstract table state, deciding *what* to fill next. Tool-intensive search is delegated to numerous parallel sub-agents. This separates strategic reasoning from execution cost, allows test-time scaling via more sub-agents, and isolates execution failures.
- **Core assumption**: Sub-tasks (per row or per cell) are sufficiently independent to run in parallel without cross-communication.
- **Evidence anchors**: Algorithm 1 shows a main loop dispatching parallel `foreach` sub-agents. TaS achieves better metrics with fewer tool calls and shows widening performance gaps as compute (N) increases, indicating effective scaling of the parallel layer.
- **Break condition**: Tasks where sub-tasks are highly interdependent (e.g., info for candidate B depends on result from candidate A), or if the main planner becomes a slow bottleneck.

## Foundational Learning

- **Concept: Structured Data Representation (Tables/DBs)**
  - **Why needed here**: The entire framework relies on interpreting information seeking as populating a relational table. Engineers must map a natural language query to a schema (`K`, `C`, `I`) and understand table operations as search actions.
  - **Quick check**: For "Find 10 vegan cafes in Berlin with outdoor seating and retrieve their phone numbers and average rating," rows (`K`) are individual cafes; constraint columns (`C`) include `dietary_type=vegan`, `city=Berlin`, `has_outdoor_seating=true`; information columns (`I`) are `phone_number` and `average_rating`.

- **Concept: Multi-Agent Orchestration Patterns**
  - **Why needed here**: TaS uses a central planner and multiple worker agents. The engineer must grasp the control flow: when to expand rows vs. populate cells, how to dispatch parallel jobs, and aggregate results.
  - **Quick check**: What triggers the transition from "Row Expansion" to "Cell Population"? (Answer: when the table has sufficient valid candidates `K` that satisfy all constraint columns `C`, but some information columns `I` are still empty). What if a sub-agent fails to find a value? (Answer: the cell may be marked `N/A` or the planner may reattempt with a different query later).

- **Concept: State Management in LLM Agents**
  - **Why needed here**: The core motivation is the failure of plain-text state tracking. The engineer should understand *why* a long unstructured `(observation, thought, action)` trajectory loses fidelity (e.g., "lost-in-the-middle", context window limits) and how an external structured store solves this.
  - **Quick check**: Two ways tracking 1000 search results in plain-text degrades performance: (1) Earlier results get squeezed out of the context window, making them unavailable for verification or synthesis; (2) The agent must parse a long, unstructured list to find specific attributes, increasing error and hallucination rates.

## Architecture Onboarding
Main Planner Agent -> Sub-Agents & Shared Database

- **Critical path**:
  1. Schema Initialization: `MainAgent.ConstructSchema(Q)` defines columns and creates empty table.
  2. Row Expansion Loop: If candidate count low or constraint columns not satisfied, planner formulates diverse queries and dispatches parallel `SubAgent.DeepSearch` calls; new candidates are `add_records` as rows.
  3. Cell Population Loop: If candidates exist but information cells are empty, planner selects target (row, column) pairs and dispatches parallel `SubAgent.DeepSearch` calls; results `update_records` the table.
  4. Saturation Check & Synthesis: `MainAgent.CheckSaturation` evaluates if the table meets query goals (enough rows satisfying all `C`, all `I` filled). If done, `Synthesize` compiles answer from table data.

- **Design tradeoffs**:
  - Schema Rigidity vs. Flexibility: Fixed schema provides clarity but may fail on queries needing dynamic attributes.
  - Planner Intelligence vs. Cost: The planner is the bottleneck; downgrading its capability severely hurts performance, while sub-agents can be cheaper.
  - Database Overhead vs. Benefit: External DB adds latency but is essential for escaping context limits; benefit scales with task horizon/width.
  - Parallelism vs. Coordination: Parallel calls improve speed but risk redundant searches if query diversification is poor.

- **Failure signatures**:
  - Schema Misalignment: Critical constraint missing from columns → irrelevant candidates survive filtering.
  - Sub-Agent Hallucination/Laziness: Returns `N/A` or incorrect info for a cell → low Item-Precision, gaps in final data.
  - Planner Saturation Failure: `CheckSaturation` returns "Done" too early or loops forever → answer missing required quantity or timeout.
  - Query Formulation Bottleneck: Planner generates homogeneous row-expansion queries → row count plateaus, low candidate diversity.

- **First 3 experiments**:
  1. Schema Mapping Unit Test: On "Find 5 popular Python libraries for data visualization and their GitHub stars," verify `K`=library names, `C`=popularity (implicit, maybe `purpose=data_viz`), `I`=`github_stars`. Run TaS manually to confirm correct initial columns.
  2. Parallel Row Expansion Validation: On "List all US state capitals," check planner generates diverse regional queries and that `add_records` adds distinct rows without duplicates while multiple sub-agents run concurrently.
  3. Cell Population & Synthesis Check: On "What is the population of the city where the 2024 Summer Olympics were held, and what is its mayor's name?," ensure planner enters Cell Population mode, dispatches sub-agents for each attribute on the single candidate row, and `Synthesize` correctly extracts both answers.

## Open Questions the Paper Calls Out
- **Open Question 1**: How can TaS be generalized to non-search agentic tasks? The authors note future work on adaptive mechanisms to dynamically toggle between structured planning and free-form reasoning, as TaS shows instability on non-search GAIA tasks.
- **Open Question 2**: How can the Planner Main-Agent be optimized (e.g., via Agentic RL) to reduce dependence on large proprietary LLMs? Ablations show the Planner is the critical bottleneck; downgrading it severely degrades performance.
- **Open Question 3**: How can evaluation of DeepWide InfoSeeking be scaled beyond human annotation to be objective and reproducible? The current DeepWide benchmark's dependence on human-in-the-loop verification is a constraint for large-scale reproducibility.

## Limitations
- Exact prompts, system messages, and decision thresholds for the planner are undisclosed, blocking precise replication.
- Schema construction is query-dependent; ambiguous or dynamically evolving constraints may cause misalignment, leading to incomplete tables or irrelevant candidates.
- Parallel sub-agent execution assumes sub-tasks are independent; tasks with inter-dependent information needs could see diminished returns or incorrect aggregation.
- The external MongoDB adds operational overhead and latency, which is not quantified in real-time scenarios.

## Confidence
- External table state prevents context dilution: **Medium** (benchmark gains suggest benefit, but no direct ablation isolating table vs. plain-text state).
- Explicit schema reduces planning errors: **Medium** (schema-driven actions are documented, but planner’s schema quality not evaluated in isolation).
- Decoupled planning/execution enables efficient scaling: **High** (clear scaling trends and tool-call efficiency improvements demonstrated).
- Overall reported improvements across GAIA, WideSearch, and DeepWide: **High** (consistent gains with multiple LLMs and benchmarks).

## Next Checks
1. **Replication with disclosed artifacts**: Obtain exact prompt templates and hyperparameters from authors. Implement TaS using the provided MongoDB primitives and reproduce the WideSearch result with Claude-Sonnet-4 (target: Item-F1 ≥60.0%).
2. **Ablation on state representation**: Replace the external table with an in-context plain-text buffer while keeping all other components identical. Run a Deep Search task and measure the performance drop to isolate the value of structured state tracking.
3. **Break-condition stress test**: Design queries that violate the candidate-attribute decomposability assumption (e.g., open-ended comparative analysis requiring sequential reasoning). Evaluate TaS’s failure modes to validate the hypothesized break conditions and identify where the schema or planner breaks down.
