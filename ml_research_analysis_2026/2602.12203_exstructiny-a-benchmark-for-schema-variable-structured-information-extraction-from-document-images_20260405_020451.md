# ExStrucTiny: A Benchmark for Schema-Variable Structured Information Extraction from Document Images

## Quick Facts
- **arXiv ID:** 2602.12203
- **Source URL:** https://arxiv.org/abs/2602.12203
- **Reference Count:** 24
- **Primary Result:** ExStrucTiny reveals significant gaps in current vision-language models for schema-variable structured extraction, with open-source models struggling as extraction complexity increases and all models performing poorly on localization and chart contexts.

## Executive Summary
ExStrucTiny is a new benchmark designed to evaluate holistic structured information extraction (IE) from document images under variable, user-specified schemas. It addresses a critical gap in existing benchmarks by focusing on flexible output structures rather than fixed ontologies. The dataset comprises 304 query-answer pairs over 110 multi-page documents spanning forms, financial reports, slide decks, and webpages. Queries are diverse, including closed IE with plain text or schema definitions and more challenging on-demand IE, often involving multi-entity requests, unanswerable entities, and low lexical overlap. A hybrid pipeline combines expert manual annotation with LLM-generated, human-validated samples to ensure quality and diversity. Evaluation uses an LLM-based semantic mapper to compare predicted structures against ground truth, measuring text (ANLS), spatial (page accuracy, bounding-box IoU), and structural (tree edit similarity) correctness. Benchmarking multiple state-of-the-art vision-language models shows that while closed models (e.g., Gemini 2.5 Pro) achieve moderate success, significant challenges remain, particularly in schema adaptation, query underspecification, and precise answer grounding.

## Method Summary
ExStrucTiny’s construction uses a three-stage hybrid pipeline. First, expert annotators manually create a seed set of query-answer pairs, enforcing diversity criteria like multi-entity requests and low lexical overlap. Second, a large language model (Gemini-2.5-Flash) generates additional synthetic question-answer pairs, optionally reformulating queries or inserting missing entities. Third, human validators review each synthetic pair using a custom UI, correcting extraction text, bounding boxes, and structural errors. The resulting dataset includes documents from four existing sources (FUNSD, TAT-DQA, SlideVQA, VisualMRC) and defines a structured output format where each extraction leaf contains `text`, `page`, and `bbox` fields. For evaluation, model predictions are parsed into JSON and flattened into path-keyed dictionaries (e.g., `"0.person.age"`). An LLM (gpt-oss-20b) performs semantic mapping between ground truth and prediction keys based on value similarity and key semantics, enabling flexible one-to-many and many-to-one matches. Standard metrics—ANLS for text, page accuracy and bounding-box IoU for spatial grounding, and tree edit similarity for overall structure—are computed on the matched leaves.

## Key Results
- Closed-source models (e.g., Gemini 2.5 Pro) achieve up to 79.5% ANLS, 84.3% page accuracy, 14.4% bounding-box IoU, and 78.3% tree edit similarity.
- Open-source models peak at 61.4% ANLS and exhibit a pronounced performance drop as the number of requested extractions increases.
- All models struggle significantly with chart contexts and precise spatial localization (IoU ≤ 14.4%), highlighting persistent weaknesses.

## Why This Works (Mechanism)

### Mechanism 1: Hybrid Pipeline for Diverse, High-Quality Benchmark
**Claim:** Combining manual annotation with LLM-generated, human-validated samples yields a challenging benchmark with realistic, diverse extraction scenarios.
**Mechanism:** Expert annotators create an initial seed set of query-answer pairs under strict diversity constraints (e.g., multi-entity, low lexical overlap, cross-page, unanswerable entities). Gemini-2.5-Flash then generates additional QA pairs, with optional reformulation or insertion of missing entities. Human validators use a custom UI to review and correct each synthetic pair's extraction text, bounding boxes, and structure.
**Core Assumption:** Human oversight can catch LLM generation errors while maintaining scalability; imposed diversity constraints produce harder questions than existing benchmarks.
**Evidence Anchors:** [abstract] describes the novel pipeline; [section 3.2–3.4] details manual, synthetic, and validation steps; corpus context (KIEval, BuDDIE) underscores the need for diversity.
**Break Condition:** If validators miss subtle errors (e.g., misaligned bounding boxes, incorrect null handling), invalid pairs remain. If the LLM cannot generate sufficiently novel or complex items, diversity may be limited, leading to benchmark saturation.

### Mechanism 2: LLM-Based Semantic Mapping for Flexible Output Comparison
**Claim:** Using an LLM to semantically align predicted and ground truth structures enables fair comparison despite schema variations.
**Mechanism:** Predicted and ground truth structured outputs are flattened into dictionaries with path-based keys (e.g., `"0.person.age"`). A text-only LLM (gpt-oss-20b) is prompted to map ground truth keys to prediction keys based on value similarity and key semantics, supporting one-to-many and many-to-one matches. Unmatched ground truth leaves count as missing extractions. Standard metrics are then computed on the matched leaves.
**Core Assumption:** A language model can perform fuzzy matching of keys and values with high accuracy, approximating human judgment on structural equivalence.
**Evidence Anchors:** [section 3.5] fully describes the evaluation framework; [abstract] mentions LLM-based mapping; related work (KIEval) motivates flexible evaluation.
**Break Condition:** The LLM mapper may fail on unseen structural divergences or complex paraphrasing, leading to misalignments and incorrect scores. The approach also introduces latency and cost compared to deterministic matching.

### Mechanism 3: Benchmark Exposes Persistent VLM Weaknesses
**Claim:** ExStrucTiny reveals significant limitations in current VLMs: poor spatial grounding, difficulty with schema adaptation and on-demand queries, and sensitivity to extraction count for open models.
**Mechanism:** The benchmark evaluates multiple open and closed VLMs on 304 QA pairs across four document types. Performance is analyzed by query type (plain text closed, schema closed, on-demand), document context (charts, free text), and extraction count, using ANLS (text), page accuracy, bounding-box IoU, and tree edit similarity (structure).
**Core Assumption:** The benchmark’s design—low lexical overlap, multi-entity requests, unanswerable entities—isolates weaknesses in schema adaptation, underspecification handling, and localization.
**Evidence Anchors:** [section 4] results tables/figures show performance gaps (e.g., open-model ANLS decline with extraction count, low chart scores, max IoU 14.4%); [abstract] summarizes struggles; [section 4.2] text-only ablation proves visual cues matter.

## Architecture Onboarding
- **Component map:**  
  Data Sources (FUNSD, TAT-DQA, SlideVQA, VisualMRC) -> Annotation Pipeline (Manual QA creation -> Seed set; LLM generator -> Synthetic QAs; Validation UI -> Human correction) -> Final Dataset (304 QA pairs, images, ground truth JSON) -> Evaluation Engine (Model inference -> LLM-based schema mapper -> Metric calculators) -> Metadata & logging (sampling, aggregation).

- **Critical path:**  
  1. Load document images and corresponding queries.  
  2. Run target VLM to obtain a structured prediction (JSON list of extraction dictionaries).  
  3. Parse prediction and ground truth into flattened dictionaries (path keys).  
  4. Invoke LLM mapper to produce a mapping from ground truth keys to prediction keys.  
  5. For each mapped leaf, compute ANLS, page accuracy, and bounding‑box IoU (using normalized coordinates).  
  6. Compute tree edit similarity between full predicted and ground truth JSON trees.  
  7. Aggregate metrics over all QA pairs and report breakdowns.

- **Design tradeoffs:**  
  - *LLM mapping vs. deterministic alignment:* LLM offers flexibility for schema variations but adds latency (~774 s for 202 samples) and cost; deterministic rule‑based matching would be faster but brittle.  
  - *Human validation vs. fully synthetic:* Human editing ensures high quality but limits dataset size; pure synthetic scale risks noise.  
  - *Localization requirement:* Including page and bounding‑box fields tests grounding but penalizes models lacking fine‑grained spatial awareness, as shown by low IoU scores.  
  - *ANLS:* Lenient text scoring tolerates near‑matches but may over‑score incorrect numbers/dates; the paper flags this as a limitation.

- **Failure signatures:**  
  - *Invalid JSON output:* Some models (e.g., Kimi‑VL‑A3B‑16B) produce non‑conforming or malformed JSON, causing mapping failures.  
  - *Mismatched schema:* LLM mapper may incorrectly pair keys, especially on complex structural divergences; reported 96.2% agreement may not generalize.  
  - *Context-specific drops:* Models scoring significantly lower on chart or free‑text contexts indicate visual understanding weaknesses.  
  - *Open‑model length sensitivity:* Performance degrades as extraction count grows, suggesting lack of robustness in long‑form generation.

- **First 3 experiments:**  
  1. **Baseline sanity check:** Run a strong closed VLM (e.g., Gemini‑2.5‑Pro) on the full benchmark to verify end‑to‑end pipeline, ensuring predicted JSON conforms to schema and all query types are handled.  
  2. **Mapper validation:** Use the synthetic mapping test set from Appendix D to confirm the chosen LLM mapper (gpt‑oss‑20b) achieves >95% F1; if performance drops, consider alternative mappers or prompt tuning.  
  3. **Text‑only ablation:** Replicate the text‑only baseline from Section 4.2 (remove images, use OCR tokens) for the target model to quantify the contribution of visual cues; a >10% ANLS drop indicates reliance on layout information.

## Open Questions the Paper Calls Out
- **Schema Generalization:** How can vision-language models be improved to reliably generalize to novel, user-specified schemas for structured information extraction, especially in zero-shot settings?
- **Query Underspecification:** What modeling or prompting strategies can effectively address query underspecification in on-demand information extraction, where the target entity structure is implicit?
- **Visual Grounding Gap:** Why do current VLMs exhibit a pronounced calibration gap between accurate text extraction and poor spatial grounding (bounding box prediction), and how can visual grounding be strengthened?
- **Metrics for Numeric/Date Values:** Are there more suitable evaluation metrics than ANLS for structured extraction of numeric and date values, which constitute a significant portion of real-world documents?
- **Multilingual Performance:** How do state-of-the-art VLMs perform on structured information extraction from non-English document images, and what are the primary linguistic or visual bottlenecks?

## Limitations
- Small dataset size (304 QA pairs, 110 documents) may limit diversity and statistical reliability.
- Human validation of synthetic QA could miss subtle errors (e.g., misaligned bounding boxes, incorrect null entities).
- LLM‐based semantic mapping introduces non‐deterministic alignment errors; reported 96.2% agreement may not generalize.
- ANLS metric may over‑score near matches, especially for numeric/date values (26% of values).
- Extremely low localization IoU (max 14.4%) suggests grounding weaknesses; metric sensitivity is unclear.

## Confidence
- **Hybrid pipeline produces diverse, challenging benchmark:** Medium. Detailed pipeline is plausible, but scale and true diversity remain unquantified.
- **LLM‐based mapping fairly evaluates outputs:** Medium. High test F1 is reported, but prompt details and edge‑case handling lack transparency.
- **Benchmark reveals persistent VLM limitations:** High. Consistent performance gaps across models, query types, and chart contexts are empirically robust.

## Next Checks
1. **Mapper robustness audit:** Run the LLM mapper on a manually aligned, out‑of‑sample set (e.g., 50 diverse predictions) to measure error rate and failure modes.
2. **Human evaluation correlation:** Collect human judgments for text correctness, page accuracy, and bbox precision on a random subset; compare with ANLS/IoU to validate automated metrics.
3. **Cross‑domain generalization test:** Sample documents from an unseen domain (e.g., invoices) and evaluate leading VLMs; verify whether the same limitations (chart grounding, extraction count sensitivity) hold.
