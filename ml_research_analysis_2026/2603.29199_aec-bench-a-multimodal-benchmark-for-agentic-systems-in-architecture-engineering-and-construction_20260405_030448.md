# AEC-Bench: A Multimodal Benchmark for Agentic Systems in Architecture, Engineering, and Construction

## Quick Facts
- **arXiv ID:** 2603.29199
- **Source URL:** https://arxiv.org/abs/2603.29199
- **Reference count:** 5
- **Primary result:** Agent performance is primarily bottlenecked by retrieval; general-purpose coding agents fail on visual-spatial grounding despite having image access, defaulting to CLI/text-extraction workflows that discard geometric structure.

## Executive Summary
AEC-Bench introduces a multimodal benchmark of 196 real-world construction coordination tasks. It evaluates agentic systems within a scaffolded harness that injects artifacts and uses automated verification across three context scopes: Intra-Sheet, Intra-Drawing, and Intra-Project. The core finding is that retrieval—locating the precise sheet, detail, or document region—is the primary bottleneck for current agents. While general-purpose coding agents (Codex, Claude) partially transfer, they fail on tasks requiring visual grounding. Augmenting the harness with domain-specific parsing tools (Nomic) significantly improves performance on retrieval-sensitive tasks (e.g., +32.2 pp on detail-technical-review) but degrades performance on spatially grounded tasks (e.g., -3.6 pp on note-callout-accuracy), where visual-required instances achieve only 5% mean reward.

## Method Summary
The benchmark uses the Harbor harness, a containerized sandbox providing agents with tools like Bash, Python, and CLI PDF utilities (`pdftotext`, `pdftoppm`). Two experimental conditions are defined: **H** (base harness) and **H⁺** (base + Nomic domain-specific parsing/embedding tools). Agents (Codex GPT-5.2/5.4, Claude Opus 4.6/Sonnet 4.6) are evaluated in zero-shot, single-trial runs on 196 tasks derived from real construction documents. Each task presents a problem statement and expects a structured JSON output, which is automatically graded by a task-specific verifier against injected ground-truth artifacts. Performance is measured as mean reward (0–100) per task, with analysis stratified by context scope and tool configuration.

## Key Results
- General-purpose coding agents exhibit partial transfer but fail catastrophically on visually grounded tasks (e.g., 5% mean reward on visual-required note-callout-accuracy).
- Adding Nomic parsing tools improves retrieval-sensitive tasks (detail-technical-review: +32.2 pp) but degrades spatially grounded ones (note-callout-accuracy: -3.6 pp).
- Agent tool usage is heavily dominated by CLI patterns: 100% Bash for Codex agents, 77% overall usage of `pdftotext`, indicating a fundamental paradigm mismatch with multimodal document structures.

## Why This Works (Mechanism)
### Mechanism 1: Retrieval as Primary Bottleneck
- **Claim:** Performance is bottlenecked by the agent's ability to retrieve the correct multimodal context from construction documents.
- **Mechanism:** Agents default to CLI/text-extraction workflows (e.g., `pdftotext`), flattening spatial layout and geometric relationships into linear text, thus discarding the visual structure critical for locating elements.
- **Evidence:** Abstract and section 4 state retrieval is the primary failure point; agents fail before reasoning because they cannot reliably locate the relevant sheet, detail, or document region.

### Mechanism 2: CLI Path Dependency
- **Claim:** Agents exhibit strong path dependency, converging on a narrow CLI-based repertoire even when multimodal inputs and domain tools are available.
- **Mechanism:** Inherited interaction patterns from software engineering (code search, file edit) lead agents to treat complex drawing sets as code repositories, not spatially organized documents.
- **Evidence:** 100% Bash usage for Codex, 77% `pdftotext` invocation across runs; coding agents use existing paradigms rather than adapting to multimodality.

### Mechanism 3: Parsing Trade-offs
- **Claim:** Adding structured parsing improves retrieval-sensitive tasks but degrades or fails to improve tasks requiring precise visual-spatial grounding, potentially increasing cognitive load.
- **Mechanism:** Parsing provides searchable text/layout data, aiding page-finding tasks, but lacks geometric precision for text-geometry alignment (e.g., callout leader lines), and may add noisy context agents cannot resolve.
- **Evidence:** `detail-technical-review` (+32.2 pp) vs. `note-callout-accuracy` (-3.6 pp); `cross-reference-resolution` shows minimal gain with parse augmentation.

## Foundational Learning
- **Multimodal Document Semiotics**: AEC drawings encode meaning in relationships between graphical elements (lines, hatches) and textual annotations (callouts). *Why needed:* Agents must understand that a leader line's geometry binds a note to a specific component. *Quick check:* Given a callout "3" with a leader line pointing to a wall, what minimal geometric/textual features verify correctness, ignoring text content?
- **Cross-Document Reference Resolution**: Tasks require tracking references (e.g., "See Detail 5 on Sheet A-101") across separate PDF pages, simulating a navigation graph. *Why needed:* Intra-Drawing and Intra-Project tasks depend on resolving cross-sheet pointers. *Quick check:* If Sheet A-101 has "Detail 5/A-101" and Sheet A-201 has "Detail 5/A-201", what inconsistencies must an agent check for `sheet-index-consistency`?
- **Domain-Specific Judgment vs. Deterministic Verification**: Tasks like `submittal-review` require applying professional norms (e.g., compliance assessment) rather than keyword matching. *Why needed:* Separates problems with clear injected ground truth from nuanced evaluation. *Quick check:* For `submittal-review`, what distinguishes a trivially verifiable injected artifact (e.g., swapped specification value) from a genuine compliance issue requiring contextual judgment?

## Architecture Onboarding
**Component map:** Harbor Harness (sandbox with Bash/Python) -> Agent Policy (LLM driving tool selection) -> Document Artifacts (PDFs, cached parsed JSON/text, PNGs) -> Nomic Tools (parse, embed for retrieval) -> Task Verifier (automated JSONL grader)

**Critical path:** Initialize -> Retrieve/Explore Documents -> Locate Relevant Artifact(s) -> Extract/Inspect Evidence -> Produce Structured Output -> Verify. The bottleneck is typically at Retrieve/Explore due to inadequate spatial indexing.

**Design tradeoffs:**
- *Parse augmentation:* Boosts token-searchable context but increases window load and may omit geometric precision.
- *Rasterization:* Provides full visual fidelity but is computationally expensive and requires separate vision reasoning.
- *Tool diversity:* Specialized geometry tools could improve grounding but increase harness complexity and agent decision space.

**Failure signatures:**
- Low mean reward (<30%) on `note-callout-accuracy` (visual-required) or `cross-reference-tracing`.
- High false-positive rate in `submittal-review`.
- Trajectory dominated (>90%) by `pdftotext` and `find`/`grep` with minimal structured read operations.

**First 3 experiments:**
1. **Baseline Retrieval Stress Test**: Run base agent (H) on the 10 visual-required `note-callout-accuracy` instances. Expected: ~0% success. Confirms geometric grounding gap.
2. **Parse Impact Isolation**: Compare H vs. H⁺ on `detail-technical-review` (retrieval-sensitive) vs. `note-callout-accuracy` visual-required. Expected: Large H⁺ gain on former, degradation/no gain on latter.
3. **Tool-Usage Profiling**: Log tool call distribution for all 196 instances. Expected: >75% `pdftotext`, near-zero geometry-specific tool invocations. Quantifies CLI-defaulting mechanism.

## Open Questions the Paper Calls Out
The paper frames its core contribution as identifying a retrieval bottleneck and CLI path dependence, but it leaves several underlying questions unexplored. First, what specific architectural or training modifications could break the CLI default behavior? The observed tool usage pattern suggests a deep-seated bias in the agents' policy networks; is this due to pre-training data distribution, the prompt design, or an intrinsic limitation of LLM tool-calling? Second, the degradation in spatially grounded tasks with parse augmentation hints at a representational conflict—how should a system best integrate parsed semantic layout with raw raster or vector graphics to support precise geometric reasoning? Third, the benchmark's reliance on automated verifiers for spatial correctness (e.g., note-callout-accuracy) assumes perfect ground truth injection and evaluation logic; what is the error rate or ambiguity in these verifiers for "subjective" AEC coordination judgments? Finally, given the low external citation count, the generalizability of the "retrieval bottleneck" claim beyond this specific 196-task corpus to broader AEC workflows or document types remains an open empirical question.

## Limitations
- **Reproduction blockers:** Exact model APIs (Codex GPT-5.2/5.4, Claude Opus 4.6) and full document licensing/URLs are unspecified, blocking exact replication.
- **Corpus weakness:** Low neighbor citation count (~0.52 FMR) indicates limited external validation of the "retrieval as primary bottleneck" claim in AEC specifically.
- **Internal validity:** Results hinge on the automated verifier's correctness for spatially grounded tasks; potential metric misalignment for subjective tasks is unexamined.

## Confidence
- **Mechanism 1 (Retrieval bottleneck):** Medium. Strong internal evidence but lacks external corroboration; verifier design for spatial tasks is a silent assumption.
- **Mechanism 2 (CLI path dependency):** High. Directly supported by reported tool-usage statistics (100% Bash, 77% `pdftotext`).
- **Mechanism 3 (Parse trade-offs):** Medium. Table 2 shows task-dependent effects, but causal link to "cognitive load" is inferential.
