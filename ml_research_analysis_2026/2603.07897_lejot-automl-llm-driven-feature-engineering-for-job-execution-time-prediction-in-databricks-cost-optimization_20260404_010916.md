# LeJOT-AutoML: LLM-Driven Feature Engineering for Job Execution Time Prediction in Databricks Cost Optimization

## Quick Facts
- **ArXiv ID:** 2603.07897
- **Source URL:** https://arxiv.org/abs/2603.07897
- **Reference count:** 25
- **Primary result:** Generates over 200 features, reduces feature-engineering and evaluation loop from weeks to 20–30 minutes, achieves 19.01% cost savings in deployment, with R² 0.81 vs. manually engineered 0.91.

## Executive Summary
LeJOT-AutoML addresses the limitations of static, manual feature engineering in Databricks job orchestration, which fails to capture critical runtime signals such as partition pruning and skew. The system employs LLM agents with retrieval-augmented generation (RAG) and a Model Context Protocol (MCP) toolchain to automatically analyze job artifacts (scripts, logs, metadata), synthesize and validate feature-extraction code, and train predictors. Integrated into LeJOT, it generates over 200 features, reduces the feature-engineering loop from weeks to 20–30 minutes, and achieves 19.01% cost savings while maintaining competitive prediction accuracy (R² 0.81 vs. manual 0.91). The approach demonstrates the potential of LLM-driven automation for dynamic feature generation in complex data platforms.

## Method Summary
The method follows a four-agent pipeline. The Feature Analyzer Agent (FAA) uses RAG over a domain knowledge base to propose candidate features that capture runtime behaviors. The Feature Extraction Agent (FExA) then materializes these features using an MCP toolchain—comprising metadata queries, log parsers, and a read-only SQL sandbox—through a four-stage extraction pipeline (static extraction, runtime materialization, normalization, data-quality checks). The Feature Evaluation Agent (FEvA) assesses feature health (coverage, stability), utility (importance, redundancy), and end-to-end impact via ablation studies, providing feedback to refine proposals. A Model Selector trains and selects the final predictor, typically XGBoost. Two safety gates—a code-completion checker and a data-leakage checker—ensure syntactic correctness and temporal integrity. The system is designed for low-latency inference, with job-signature-based caching to avoid redundant tool calls.

## Key Results
- **Feature volume:** Generates over 200 features, significantly exceeding manual engineering efforts.
- **Loop acceleration:** Reduces the feature-engineering and evaluation loop from weeks to 20–30 minutes.
- **Cost reduction:** Achieves 19.01% cost savings in LeJOT deployment.
- **Prediction accuracy:** R² of 0.81 (AutoML) compared to 0.91 for manual features, with competitive MAE and MAPE.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** LLM agents expand the feature space by synthesizing runtime-derived features from fragmented artifacts (logs, metadata, scripts) that static engineering misses.
- **Mechanism:** The Feature Analyzer Agent (FAA) uses retrieval-augmented generation (RAG) over a domain knowledge base to propose candidate features targeting runtime behaviors (e.g., partition pruning, skew). The Feature Extraction Agent (FExA) then materializes these via a toolchain (log parsers, metadata queries, SQL sandbox), converting unstructured traces into structured signals.
- **Core assumption:** LLMs can synthesize semantically meaningful feature extraction plans from heterogeneous evidence when grounded in domain knowledge and validated via tool execution.
- **Evidence anchors:**
  - Abstract: "materializes runtime-derived features that are difficult to obtain through static analysis alone... generates over 200 features"
  - Section II: "high-impact performance signals only emerge at runtime... fragmented across multiple sources (logs, metadata, job scripts)"
  - Corpus: Weak; neighboring papers discuss LLM feature engineering but not this specific runtime artifact integration, suggesting novelty.
- **Break condition:** If tool outputs are too noisy or incomplete, LLM-synthesized extractors fail validation (code-completion or data-leakage checks), stalling feature generation.

### Mechanism 2
- **Claim:** The Model Context Protocol (MCP) toolchain enables safe, deterministic feature materialization by sandboxing access to runtime evidence and enforcing schema conformity.
- **Mechanism:** MCP tools expose typed interfaces for metadata queries, log parsing, and read-only SQL analysis. FExA plans tool calls, executes them in parallel under sandbox policies, and validates outputs against a feature schema before acceptance. Caching by job signature avoids repeated reads.
- **Core assumption:** Deterministic, low-latency tool execution with strict output schemas can reliably convert volatile job artifacts into stable features for training and inference.
- **Evidence anchors:**
  - Section III.D: "Each MCP tool exposes a restricted, typed interface... sandboxed environment with an allowlist... caching keyed by (job signature, feature version)"
  - Section IV.B: "FExA follows a four-stage extraction pipeline: Static extraction, Runtime materialization, Normalization, Data-quality checks"
  - Corpus: Neighboring work (e.g., Gradientsys) employs MCP, but this system’s specific tool definitions are tailored to the problem.
- **Break condition:** Tool latency exceeds inference budget or schema mismatches cascade, causing feature unavailability for new jobs.

### Mechanism 3
- **Claim:** Iterative evaluation with safety gates prevents degradation from data leakage and unstable features, enabling continuous adaptation under drift.
- **Mechanism:** The Feature Evaluation Agent (FEvA) assesses feature health (coverage, stability), utility (importance, redundancy), and end-to-end impact (ablation studies). Feedback refines FAA/FExA plans. Two gates block extractors that are syntactically incomplete or leak label information (i.e., use post-execution data).
- **Core assumption:** Automated, multi-level evaluation can substitute manual oversight to maintain feature pipeline robustness in evolving workloads.
- **Evidence anchors:**
  - Abstract: "feedback-enabled Feature Evaluation Agent (FEvA)... two safety gates—a code-completion checker and a data-leakage checker"
  - Section III.C: "FEvA aggregates... feature health, feature utility, end-to-end impact... emits actionable feedback for refinement"
  - Corpus: Neighboring work on robust feature engineering exists but does not address this specific gating mechanism.
- **Break condition:** Drift accelerates such that FEvA’s feedback cannot refine features fast enough, or the leakage checker becomes overly conservative, starving the feature space.

## Foundational Learning
### Retrieval-Augmented Generation (RAG)
- **Why needed here:** FAA uses RAG to ground LLM suggestions in domain knowledge (Spark SQL practices, Databricks internals) without fine-tuning, ensuring proposed features are plausible for the platform.
- **Quick check question:** How does RAG differ from naive prompting, and why is grounding critical for heterogeneous artifact analysis?

### Model Context Protocol (MCP)
- **Why needed here:** MCP standardizes tool invocation (log parsers, metadata queries, SQL sandbox), allowing LLM agents to safely execute and verify extraction plans in a sandboxed, typed interface.
- **Quick check question:** What are the trade-offs between a custom tool API versus a standardized protocol like MCP for multi-agent systems?

### Data Leakage in Temporal Prediction
- **Why needed here:** Features must be computable before scheduling decisions; using post-execution logs (e.g., actual shuffle volumes) would leak the label and inflate training accuracy but fail in production.
- **Quick check question:** In job runtime prediction, give an example of a feature that would violate temporal isolation and how the leakage checker might detect it.

## Architecture Onboarding
- **Component map:** Inputs include job artifacts (scripts, configs), execution logs, metadata store, and domain knowledge base. The pipeline comprises agents: Feature Analyzer Agent (FAA) for feature spec generation, Feature Extraction Agent (FExA) for extraction and materialization, Feature Evaluation Agent (FEvA) for evaluation and feedback, and a Model Selector for training. Safety components include a code-completion checker and a data-leakage checker. Tools are provided via the Model Context Protocol (MCP) toolchain, offering metadata queries, log parsers, and a read-only SQL sandbox. Outputs are a versioned feature spec, a deployed predictor (e.g., XGBoost), and an extractor bundle. The predictor integrates with LeJOT’s orchestration optimizer.
- **Critical path:** The training loop proceeds as follows: FAA proposes features → FExA materializes them via MCP tools → safety gates validate extractors → FEvA evaluates feature health and utility and sends feedback → FAA/FExA refine extraction plans → Model Selector picks the best model. For inference, extraction plans from FAA/FExA are reused to ensure consistency.
- **Design tradeoffs:**
  - **Accuracy vs. latency:** Feature extraction cost `c(f,d)` is constrained by a budget `B`; high-signal runtime features may be skipped if extraction is too slow.
  - **Automation vs. control:** LLM synthesis accelerates development but may yield invalid extractors; safety gates introduce overhead (e.g., the data-leakage checker is noted as costly).
  - **Feature diversity vs. stability:** AutoML generates 200+ features, increasing coverage, but some may be unstable; FEvA must prune to avoid overfitting and ensure reliability.
- **Failure signatures:**
  - A high data-leakage rejection rate (e.g., >30% of generated extractors) suggests FAA proposes unrealistic features that rely on post-execution data.
  - Degrading feature health metrics—such as rising missing rates or distribution shifts in key features (e.g., `duration_seconds_lag1`)—indicate drift or pipeline instability.
  - Spikes in extraction latency, particularly from FExA or the leakage checker, can breach the inference SLA.
- **First 3 experiments:**
  1. **Feature diversity comparison:** Count features by source (log, metadata, code) as in Table I; confirm AutoML yields >5× the number of manual features.
  2. **Prediction accuracy ablation:** Compare AutoML vs. manual models using R², MAE, and MAPE (Table III); inspect top features (Table II) to verify inclusion of runtime signals.
  3. **Module runtime & safety:** Measure per-agent latency and gate pass rates across iterations (Tables V, VI); ensure feedback reduces MAE and improves R² over successive iterations.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the MCP toolchain be extended to include configuration-change trajectories and pricing context, and to what extent would such extensions improve prediction accuracy (e.g., R²) and cost savings in LeJOT?
- **Basis in paper:** The authors explicitly state that extending the tool interface with configuration-change logs and instance-specification/price knowledge is a clear path to improving resource awareness and narrowing the accuracy gap (Section V-A).
- **Why unresolved:** The paper identifies this limitation but does not implement or evaluate any solution; the current toolset only provides static configuration snapshots.
- **Resolution path:** Deploy an enhanced MCP that ingests configuration-change logs and pricing data, then compare feature diversity, prediction metrics, and end-to-end cost savings against the baseline system.

### Open Question 2
- **Question:** What are the failure rates (false positives and false negatives) of the safety gates (code-completion and data-leakage checkers) in real-world feature extraction scenarios?
- **Basis in paper:** The system relies on two safety gates to ensure syntactic completeness and prevent label leakage (Section III), but no evaluation of their precision or recall is provided; the gates could either block valid extractors or let invalid ones pass silently.
- **Why unresolved:** Without quantitative measures, it is unclear how trustworthy the safety mechanism is, especially when scaling to many LLM-generated extractors.
- **Resolution path:** Run a large corpus of generated extractors through the gates and manually verify a sample to estimate false positive/negative rates, and analyze failure modes to improve gate design.

### Open Question 3
- **Question:** How effective is the drift-triggered retraining mechanism in maintaining model accuracy under continuous workload evolution, and what drift detection thresholds yield the best trade-off between freshness and retraining overhead?
- **Basis in paper:** The authors mention periodic and drift-based updates (Section III, IV-D) and log residuals for drift detection, but the experimental evaluation only covers three static iterations; the long-term behavior under realistic drift is not studied.
- **Why unresolved:** Deployment environments experience concept drift; without evaluating the feedback loop over time, we cannot gauge the system's adaptability or optimum tuning.
- **Resolution path:** A production deployment over several months, recording prediction errors, feature stability, and retraining frequency, with experiments varying drift detection thresholds to measure impact on accuracy and cost.

### Open Question 4
- **Question:** What is the actual end-to-end latency of feature extraction during online inference, and does it satisfy the low-latency requirements of LeJOT's orchestration algorithm?
- **Basis in paper:** Low-latency inference is a stated design goal (Section III B), and the system bounds extraction cost, but no measurements of inference-time extraction are reported; Table V only shows training-phase agent runtimes.
- **Why unresolved:** The orchestration decision must be made quickly; unknown extraction overhead could invalidate the system's practicality if it exceeds the budget.
- **Resolution path:** Empirical measurement of feature extraction times across a representative set of jobs, including per-feature breakdown and total latency, and comparison against LeJOT's latency budget.

## Limitations
- **RAG details undisclosed:** Knowledge base composition, retrieval prompts, and grounding strategies for FAA are unspecified, hindering replication and trust.
- **Safety gate opacity:** Exact rules for code-completion tolerance (e.g., undefined variable policy) and data-leakage detection (especially for derived metrics like shuffle amplification) are not described, limiting understanding of their effectiveness.
- **Feature stability unverified:** Long-term drift adaptation and feature health metrics (coverage, SHAP consistency) are only reported over short ablation cycles; production robustness remains unclear.

## Confidence
- **Feature expansion via LLMs (Mechanism 1):** Medium
- **Deterministic materialization via MCP (Mechanism 2):** Medium
- **Automated robustness via safety gates (Mechanism 3):** Low
