# Constraint-aware Path Planning from Natural Language Instructions Using Large Language Models

## Quick Facts
- **arXiv ID:** 2603.19257
- **Source URL:** https://arxiv.org/abs/2603.19257
- **Reference count:** 34
- **Primary result:** An LLM-based two-pathway framework with self-verification and iterative refinement achieves high solution validity (95.38%) and reduces travel cost (5.28%–8.81%) on constrained routing problems from natural language specs, but degrades beyond 15–20 cities.

## Executive Summary
This paper introduces a framework for solving diverse constrained vehicle routing problems (VRP variants) directly from natural language descriptions. It uses a large language model (LLM) in a two-pathway architecture: either matching the input to a pre-defined structured problem formulation (SPF) from a library, or autonomously generating an SPF via in-context learning for unseen problems. Solutions are produced iteratively with integrated self-verification against SPF constraints and refinement, mimicking a genetic algorithm. Using GPT-4-Turbo, the self-verification module significantly improves solution validity, and iterative refinement lowers travel costs across four tested problem types. However, performance declines for problem instances with over 15–20 cities.

## Method Summary
The method employs an LLM (primarily GPT-4-Turbo) without traditional training. For a given natural language instruction and instance data (city coordinates, depot index, distance matrix), the system first attempts to retrieve a matching SPF from a predefined library. If no match exists, it generates a new SPF via a single-shot in-context learning example. The SPF structures the problem as a set of logical constraints (e.g., inequalities). The LLM then generates initial candidate solutions. A verification step checks feasibility—for library SPFs by programmatic constraint checking, and for generated SPFs via an LLM self-verification prompt. Valid solutions enter an iterative refinement loop where the LLM is prompted to improve the solution while maintaining feasibility, effectively performing a search over candidate solutions. Metrics include solution validity percentage and average travel cost reduction from the initial valid solution.

## Key Results
- Self-verification increases solution validity from 85.63% to 95.38%.
- Iterative refinement reduces average travel cost by 5.28% to 8.81% across four problem types.
- Refinement achieves a success rate between 50% and 78%.
- Performance degrades for problem instances exceeding 15–20 cities.

## Why This Works (Mechanism)
The approach leverages the LLM's ability to parse natural language and generate structured outputs, while using explicit SPFs to formalize constraints. Self-verification acts as a corrective filter, catching infeasible tours before refinement. Iterative refinement uses the LLM's comparative reasoning to mutate solutions toward lower cost within the feasible region, akin to a simple evolutionary step. The two-pathway design balances efficiency (library lookup) with flexibility (autonomous SPF generation), enabling handling of novel constraint combinations without retraining.

## Foundational Learning
- **Structured Problem Formulation (SPF):** A formal, inequality-based representation of constraints. *Why needed:* Provides a machine-readable constraint template for verification and guides solution generation. *Quick check:* Confirm SPFs capture all natural language constraints as logical expressions.
- **In-Context Learning for SPF Generation:** Using a single example to induce a new SPF. *Why needed:* Generalizes to unseen problem types without additional training. *Quick check:* Test if generated SPFs correctly encode the constraints from a held-out natural language description.
- **LLM Self-Verification:** Prompting the LLM to check its own solution against constraints. *Why needed:* Enforces feasibility when programmatic checkers are unavailable (e.g., for generated SPFs). *Quick check:* Compare LLM’s verification judgments against a ground-trosis validator on a sample.
- **Iterative Refinement via Candidate Comparison:** Prompting the LLM to select or mutate the best solution among candidates. *Why needed:* Explores solution space without requiring a full optimizer. *Quick check:* Track whether successive refinements consistently lower cost while maintaining validity.
- **Constraint-Aware Output Parsing:** Extracting tours from LLM text outputs. *Why needed:* Converts unstructured LLM responses into structured data for verification. *Quick check:* Measure parsing error rate on a sample of raw outputs.
- **Euclidean Distance Matrix Precomputation:** Providing pairwise distances. *Why needed:* Reduces LLM computational load and ensures objective consistency. *Quick check:* Verify distance matrix matches coordinate geometry for a few city pairs.

## Architecture Onboarding
Component map: Natural Language Input + Instance Data -> SPF Retrieval/Generation -> Solution Proposal -> Verification -> [Valid Solution -> Refinement Loop -> Output / Invalid Solution -> Regeneration]

Critical path: For a new problem, the critical path is: (1) SPF acquisition (retrieve or generate), (2) initial solution generation, (3) verification, and (4) iterative refinement until a stopping condition (e.g., max iterations or no improvement).

Design tradeoffs:
- **LLM vs. Traditional Solver:** Uses LLM for generalization from language at the cost of optimality guarantees and scalability.
- **Library SPF vs. Autonomous SPF:** Library lookup is reliable but limited; autonomous generation enables novelty but risks incorrect formulations.
- **Self-Verification Overhead:** Adds computational cost but significantly improves validity; less reliable for generated SPFs.

Failure signatures:
- **Scalability cliff:** Sharp drop in validity rate when city count exceeds 15–20, indicating contextual window or reasoning limitations.
- **SPF generation errors:** Autogenerated SPFs that omit key constraints, leading to systematically invalid solutions that self-verification may miss.
- **Format parsing failures:** LLM outputs not adhering to required tour syntax (e.g., missing delimiters, duplicate cities), causing verifier rejection.

First experiments:
1. **API and Prompt Skeleton:** Set up GPT-4-Turbo API, craft a minimal prompt for one known problem type (e.g., basic TSP) with 5 cities, and confirm you can retrieve a parsable tour.
2. **Single-Instance Pipeline:** For a 10-city instance of a library problem type, run the full pipeline (retrieve SPF, generate solution, verify, refine 3 iterations). Record validity and cost at each step.
3. **Autonomous SPF Test:** Provide a novel natural language constraint (e.g., "visit cities in ascending order of population" with dummy population data), use the single-shot example to generate an SPF, then attempt to solve. Check if the SPF correctly encodes the constraint.

## Limitations
- **Scalability constraint:** The method becomes ineffective for instances with more than 15–20 cities due to LLM context and reasoning limits.
- **Unreliable self-verification for generated SPFs:** When the SPF is autonomously created, the LLM-based verifier may not correctly identify all constraint violations.
- **Undisclosed prompt engineering:** Critical prompts for SPF generation, verification, and refinement are not fully specified, hindering precise replication.

## Confidence
- **Self-verification improves validity (85.63% -> 95.38%):** Medium (metric clear, but dependent on unreported prompt design).
- **Iterative refinement reduces cost (5.28%–8.81%):** Medium (results specific to unreported LLM settings and prompts).
- **Scalability limit (~15–20 cities):** High (specific empirical threshold reported).
- **Framework generalizes to novel constraints:** Low-Medium (autonomous SPF generation shown on diverse set but with unknown reliability).
