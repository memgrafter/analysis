# EveryQuery: Zero-Shot Clinical Prediction via Task-Conditioned Pretraining over Electronic Health Records

## Quick Facts
- **arXiv ID**: 2603.07900
- **Source URL**: https://arxiv.org/abs/2603.07900
- **Reference count**: 9
- **Primary result**: Outperforms autoregressive baseline on 82% of 39 tasks (mean AUC +0.16), with ~3000× faster inference.

## Executive Summary
EveryQuery addresses key limitations of autoregressive EHR foundation models—computational expense, statistical noise on rare events, and lack of native promptability—via task-conditioned pretraining. By prepending a structured clinical query (code and time window) to a patient’s history, the model directly estimates outcome likelihood in a single forward pass. On MIMIC-IV, it achieves significant gains in AUROC across most tasks, particularly for rare events, and generalizes to held-out query codes. However, it underperforms on tasks requiring disjunctive reasoning (e.g., 30-day readmission), revealing a limitation of the single-code query language.

## Method Summary
EveryQuery uses MEDS-formatted EHR data. Patient histories are tokenized sequences of medical codes. During pretraining, a query code (from a fixed set of 10,000) and a 30-day window are prepended as a special token. A bidirectional transformer (ModernBERT-base) encodes the combined sequence. The final hidden state of the query token feeds two separate MLP heads that predict event occurrence and censoring probabilities. The loss combines binary cross-entropy for censoring (all samples) and occurrence (only non-censored samples). Training uses AdamW with early stopping. At inference, any query from the supported space can be input without retraining, enabling zero-shot prediction.

## Key Results
- Wins on 82% of 39 random tasks vs. autoregressive baseline (MEDS-EIC-AR).
- Mean AUC improvement of +0.16 (95% CI: [0.10,0.22]).
- Inference ~3000× faster per task.
- Largest gains on rare clinical events (low prevalence).
- No performance drop on held-out (OOD) query codes.
- Underperforms on disjunctive tasks (e.g., 30-day readmission, AUC ~0.56).

## Why This Works (Mechanism)
**Mechanism 1**: Task conditioning via query prepending enables zero-shot inference and efficiency. The model learns to attend between query and history during pretraining, mapping the query token's representation to outcomes in one pass. Evidence: Single-forward-pass design; formal query definition. Break condition: Poor query space coverage or attention capacity limits.

**Mechanism 2**: Direct discriminative prediction avoids variance from autoregressive sampling. For rare events, counting occurrences in sampled trajectories yields quantized, high-variance estimates. EveryQuery's gradient signal comes from the query code itself, leading to prevalence-invariant performance. Evidence: Strong correlation between AR AUC and prevalence (ρ=0.64) but not for EveryQuery (ρ=0.18). Break condition: Too few query examples or weak precursors.

**Mechanism 3**: Query-specific representation clustering allows OOD generalization. Similar query codes produce similar query-token representations due to attention patterns generalizing via embedding space smoothness. Evidence: Consistent performance on ID vs. OOD tasks; UMAP plots show query clustering. Break condition: OOD code embedding far from training queries or poor query token encoding.

## Foundational Learning
- **Task conditioning**: Model ingests query as input, not fixed output heads. Why needed: central to zero-shot capability. Quick check: How does conditioning on a query token during pretraining enable promptability?
- **Autoregressive inference for EHR**: Baseline generates future trajectories. Why needed: highlights computational and statistical limitations. Quick check: Why does trajectory sampling produce quantized probability estimates for rare events?
- **Censoring in time-to-event data**: Model predicts censoring to handle incomplete observation windows. Why needed: prevents bias in training. Quick check: What is the role of the censoring head, and how is the loss masked?

## Architecture Onboarding
- **Component map**: Query prepending -> Transformer backbone -> Query token representation -> Two MLP heads (occurrence, censoring)
- **Critical path**: Input (patient history + query token) -> Transformer self-attention -> Final query token hidden state -> MLP heads -> Predicted probabilities.
- **Design tradeoffs**:
  1. Single query token simplifies but limits expressiveness (fails on disjunctive queries).
  2. Fixed 30-day window reduces query space complexity but hinders generalization to other horizons.
  3. Bidirectional encoder enables single-pass inference but cannot model future dependencies beyond the query.
- **Failure signatures**:
  1. Low AUC on disjunctive tasks (e.g., readmission) indicates query language limitation.
  2. High prediction variance across seeds suggests training instability or insufficient data.
  3. Performance drop on OOD codes with low semantic similarity signals embedding space issues.
- **First 3 experiments**:
  1. Replicate main results: train EveryQuery and AR baseline on MIMIC-IV, evaluate on 39 tasks, compute win rate and mean AUC difference.
  2. Held-out code generalization: Compare performance on in-distribution vs. out-of-distribution query codes.
  3. Disjunctive task evaluation: Test on 30-day readmission using aggregation over 70 admission codes; expect underperformance relative to AR.

## Open Questions the Paper Calls Out
**Open Question 1**: How can EveryQuery's query language be extended to natively support disjunctive reasoning? Basis: Authors state underperformance on tasks requiring disjunctive reasoning (e.g., readmission). Unresolved: Current query `q=(c, Δt)` only supports single codes; aggregation fails. Evidence needed: Integrate query algebra (e.g., `OR {c1,...}`) and evaluate on composite tasks.

**Open Question 2**: Does EveryQuery generalize across different prediction horizons (Δt)? Basis: Fixed Δt=30 days; authors note this reduces expressivity and ability to generalize is untested. Unresolved: Unknown if learned conditioning captures temporal dynamics generically. Evidence needed: Evaluate zero-shot on same codes with varying Δt (7d, 90d, 1y) or pretrain with Δt distribution.

**Open Question 3**: Do advantages hold across datasets and against optimized AR baselines? Basis: Evaluation on single dataset (MIMIC-IV) and one AR baseline; authors list this as limitation. Unresolved: Speedup and rare-event advantage may depend on baseline config and dataset. Evidence needed: Replicate on multiple EHR datasets (eICU, claims) and benchmark against AR with varying K (trajectories) and variance-reduction techniques.

**Open Question 4**: What is the semantic structure of the query embedding space? Basis: Embeddings cluster by query; authors hypothesize smoothness for OOD generalization but don't explore semantics. Unresolved: Unclear if proximity correlates with clinical similarity (UMLS/SNOMED). Evidence needed: Correlate embedding similarities with clinical ontologies; ablation on query sampling biases.

## Limitations
- Evaluation limited to a single dataset (MIMIC-IV) with unreported patient splits.
- Query language restricted to single-code predicates, failing on disjunctive tasks like readmission.
- Fixed 30-day prediction window prevents application to other time horizons.
- Underspecified query sampling distribution may lead to coverage gaps for rare codes.
- Ambiguous censoring implementation could bias training.
