# TodoEvolve: Learning to Architect Agent Planning Systems

## Quick Facts
- **arXiv ID:** 2602.07839
- **Source URL:** https://arxiv.org/abs/2602.07839
- **Reference count:** 9
- **Primary result:** Improves average GAIA score by 16.37% over a Smolagents baseline, achieving 72.12% with GPT-5-Mini.

## Executive Summary
Fixed, hand-crafted planning structures in agent systems lack adaptability across diverse tasks. TodoEvolve introduces a meta-planning paradigm that autonomously synthesizes and revises task-specific planning architectures. It uses PlanFactory, a unified modular design space, to train the Todo-14B model via Impedance-Guided Preference Optimization (IGPO), a multi-objective RL objective balancing performance, stability, and token efficiency. On five benchmarks, TodoEvolve consistently outperforms state-of-the-art engineered planners and demonstrates robust gains across multiple LLM backbones while maintaining comparable computational costs.

## Method Summary
TodoEvolve treats planning architecture design as conditional code generation. A meta-model (Todo-14B) generates complete planning configurations (a Python class + YAML) that are instantiated in the PlanFactory runtime. Execution traces yield metrics (success, stability, token efficiency) used by IGPO to construct preference pairs, tuning the model to favor efficient architectures. The system factorizes planning into four orthogonal components (topology, initialization, adaptation, navigation), enabling polymorphic expression and standardized evaluation of diverse planning paradigms.

## Key Results
- Outperforms state-of-the-art engineered planners on five benchmarks.
- Improves average GAIA score by 16.37% over Smolagents baseline (72.12% with GPT-5-Mini).
- Demonstrates robust gains across multiple LLM backbones (GPT-5-Mini, DeepSeek V3.2, Kimi K2) with comparable computational costs.

## Why This Works (Mechanism)

### Mechanism 1
**Claim:** A meta-planner can synthesize task-specific planning architectures that outperform fixed hand-crafted planners.
- **Mechanism:** The system treats planning architecture design as a generative code synthesis problem. Given a task description and reference examples, the meta-model (Todo-14B) outputs a complete configuration P = ⟨G, I_init, F_adapt, N_nav⟩ (Python class + YAML). This is instantiated in PlanFactory and executed, with performance feedback via IGPO to guide future generations.
- **Core assumption:** The space of viable planning architectures is learnable from execution-verified trajectories; the model can infer structural priors (e.g., when to use DAG vs. linear) from task semantics and reference patterns.
- **Evidence anchors:** Abstract states "autonomously synthesizes and dynamically revises task-specific planning architectures"; section 4.1 formulates it as conditional code generation. Corpus evidence is indirect; neighboring work explores synthesis but lacks TodoEvolve's execution-grounded loop.
- **Break condition:** If the learned mapping from task description to viable P collapses (e.g., generated code is syntactically invalid or semantically non-executable in PlanFactory despite SFT).

### Mechanism 2
**Claim:** A unified modular design space (PlanFactory) is necessary to standardize heterogeneous planning paradigms for scalable generation and evaluation.
- **Mechanism:** PlanFactory decomposes all prior planners into four interoperable components: ♣ Topology (graph structure), ♦ Initialization (state seeding), ♥ Adaptation (dynamic adjustments), and ♠ Navigation (action selection). This polymorphism allows any architecture to be expressed, swapped, and benchmarked under a shared runtime, serving as both execution engine for verification and target API for the meta-planner.
- **Core assumption:** The combinatorial space of planning behaviors can be factorized into these four orthogonal dimensions without loss of expressivity.
- **Evidence anchors:** Abstract mentions "unified modular design space that standardizes diverse planning paradigms"; section 3.2 defines the BasePlanning abstract class with four components. Weak direct corpus support; neighboring work surveys structures but does not propose such factorization.
- **Break condition:** If a novel, high-performing planning paradigm cannot be expressed within the ⟨G, I, F, N⟩ schema (e.g., requires a fifth fundamental dimension).

### Mechanism 3
**Claim:** Impedance-Guided Preference Optimization (IGPO) aligns the meta-planner to generate *efficient* architectures, not just *correct* ones.
- **Mechanism:** IGPO constructs preference pairs from execution traces where both (P_win, P_lose) succeed. The winner minimizes a compound Cognitive Impedance I(τ) = C_tot * exp(λ₁N_fail + λ₂(1-S_stab) + λ₃*(C_plan/C_exec)). The policy is tuned via DPO-style loss to increase the log-probability ratio between low-impedance and high-impedance correct plans.
- **Core assumption:** I(τ) is a valid proxy for "bureaucracy penalty" and that minimizing it leads to Pareto-optimal systems (high success, low overhead).
- **Evidence anchors:** Abstract cites "multi-objective reinforcement learning objective that encourages... performant, stable, and token-efficient"; section 4.2.2 defines I(τ) explicitly and contrasts correctness-first vs. efficiency-as-tie-breaker. Neighbors address test-time compute allocation but not architectural synthesis; IGPO's formulation is novel.
- **Break condition:** If the C_plan/C_exec ratio is a poor signal (e.g., cheap plans are consistently worse long-term due to hidden state issues not captured by S_stab).

## Foundational Learning
- **Concept: Code Generation as Policy Output**
  - **Why needed:** The meta-planner's output is executable Python code (P), not natural language actions. The model must learn the PlanFactory API syntax, class inheritance, and valid configuration patterns.
  - **Quick check:** Given a task like "parallel web search requiring dependency checks," can the model output a valid `class MyPlanner(BasePlanning):` with correctly overridden `topology_initialize` and `navigation` methods?
- **Concept: Reinforcement Learning from Execution Feedback (RLXF)**
  - **Why needed:** SFT only teaches *viable* (Correct(P)=True) code generation. IGPO is essential to shape the distribution toward *efficient* viable codes, using I(τ) computed from real execution as the implicit reward.
  - **Quick check:** Does the model understand that a plan with more steps but lower total cost (C_tot) could be preferred over a shorter, more expensive one?
- **Concept: Modular System Design & Abstraction**
  - **Why needed:** To design P, the model must mentally map any observed planning behavior (e.g., "Flash-Searcher prunes workflows") onto the ⟨G, I, F, N⟩ dimensions. This requires grasping the abstraction, not just copying surface patterns.
  - **Quick check:** Can the model decompose "Co-Sight's conflict-aware meta-verification" into: G=Cross-check net, I=Inconsistency trigger, F=Meta-verification, N=Conflict resolution?

## Architecture Onboarding
- **Component map:** Input Context (C_i: task description + system prompt + Meta-Tools docs + 3 reference P_ref) -> Meta-Planner (Todo-14B generates P_gen) -> PlanFactory Runtime (instantiates P_gen -> execution trajectory τ) -> Verification & Metrics (computes Correct, I(τ), S_stab, C_plan/C_exec) -> IGPO Data Pipeline (builds (P_win, P_lose) pairs) -> Training Loop (SFT on D_SFT, IGPO on D_IGPO).
- **Critical path:** Task Inst. -> Generate P_gen -> Execute τ in PlanFactory -> Compute I(τ) -> Construct Pref. Pair -> IGPO Update -> (repeat).
- **Design tradeoffs:**
  - **Generality vs. Specialization:** PlanFactory's 4D space aims for generality, but overfitting to training domain trajectories could harm novelty. The K-sample exploration in IGPO mitigates this.
  - **Performance vs. Cost:** IGPO explicitly trades off via λ weights in I(τ). Tuning λ₃ (bureaucracy penalty) is critical; too high stifles complex plans, too low yields bloated architectures.
  - **SFT vs. IGPO Data:** D_SFT is filtered only for correctness (Correct(P)=True). D_IGPO requires two correct plans per pair with significant ΔI. This creates a curriculum: first learn to generate any working plan, then learn to generate better ones.
- **Failure signatures:**
  - **Code Validation Failures:** P_gen fails to import/run in PlanFactory. Indicates insufficient SFT or reference quality.
  - **High Impedance, Low Success:** Plans succeed but have C_plan/C_exec >> 1 or N_fail high. Signal: model over-generates complex topologies (e.g., always DAG) when simpler would suffice.
  - **Instability (S_stab low):** Generated F_adapt causes thrashing (frequent, pointless re-planning). Likely D_IGPO lacks enough pairs with stable vs. unstable contrasts.
- **First 3 experiments:**
  1. **SFT Sanity Check:** Feed Todo-14B a held-out task; verify it produces a syntactically valid and executable BasePlanning subclass that runs without runtime errors in PlanFactory.
  2. **IGPO Efficiency Probe:** For a fixed correct P_base, have Todo-14B generate 10 variants under same C_i. Confirm IGPO-trained model produces variants with lower mean I(τ) than SFT-only model, while maintaining Correct=1.
  3. **Cross-Backbone Generalization Test:** Use Todo-14B to generate P for a task, run it with three different execution LLM backbones (e.g., GPT-5-Mini, DeepSeek V3.2, Kimi K2). Check if performance gain (vs. static planner) is consistent across backbones, confirming architectural reasoning is backbone-agnostic.

## Limitations
- **Generalization beyond benchmarks:** PlanFactory's 4D factorization may not capture emergent planning behaviors in open-world tasks not represented in the five evaluated benchmarks.
- **Impedance metric validity:** IGPO's I(τ) assumes C_plan/C_exec and N_fail are sufficient proxies for "bureaucracy"; hidden long-term costs (e.g., state corruption) may be unmeasured.
- **Scalability of code synthesis:** Generating syntactically and semantically valid BasePlanning subclasses for highly novel topologies could degrade sharply outside the SFT distribution.

## Next Checks
1. **Code validity stress test:** Sample 100 diverse tasks from outside the training distribution (e.g., unfamiliar tool suites). Measure % of generated P_gen that are syntactically valid, importable in PlanFactory, and produce any execution trace. Failure mode: silent code generation that crashes at runtime.
2. **IGPO ablation on impedance terms:** Retrain with I(τ) variants: (a) remove C_plan/C_exec, (b) replace N_fail with a learned cost predictor. Quantify change in Pareto front (success vs. token cost) on a held-out benchmark. Failure mode: no significant difference vs. SFT-only, suggesting I(τ) is not the active ingredient.
3. **Cross-backbone fidelity transfer:** Use Todo-14B to generate P for a complex task (e.g., multi-doc QA with conflicting info). Execute the same P with 3+ execution LLMs (e.g., GPT-4o, Claude 3.7, Llama 3.1-70B). Compute variance in Correct(P) and I(τ) across backbones. High variance would indicate the generated architecture is brittle to backbone capability shifts.
