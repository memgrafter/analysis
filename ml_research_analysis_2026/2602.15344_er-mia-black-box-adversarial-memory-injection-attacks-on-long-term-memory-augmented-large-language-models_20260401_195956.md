# ER-MIA: Black-Box Adversarial Memory Injection Attacks on Long-Term Memory-Augmented Large Language Models

## Quick Facts
- **arXiv ID**: 2602.15344
- **Source URL**: https://arxiv.org/abs/2602.15344
- **Reference count**: 40
- **Primary result**: Similarity-based retrieval enables black-box adversarial memory injection, causing up to 88% F1 drop on long-term memory-augmented LLMs with >98% retrieval success.

## Executive Summary
ER-MIA investigates a fundamental vulnerability in long-term memory systems for large language models (LLMs) that rely on dense vector retrieval. By exploiting the black-box nature of these systems, an attacker can inject malicious memories during normal interaction, which are subsequently retrieved due to embedding similarity and corrupt the model's reasoning. The paper formalizes two attack settings—content-based poisoning and question-targeted false answer injection—using composable primitives and ensembles. Evaluations on the LoCoMo benchmark with multiple LLMs and memory systems (A-mem, Mem0) show severe degradation: single-primitive attacks reduce QA F1 by 22.7–71.5%, while ensembles achieve 72–88% drops. Adversarial memories are retrieved in over 98% of cases when top‑k ≥ 20, demonstrating that pure similarity-based retrieval alone persistently compromises reasoning without requiring internal model or memory access.

## Method Summary
The attack operates in two phases: memory writing and retrieval. During writing, the system automatically extracts and stores memories from user–LLM interactions. An adversary, without any internal access, injects carefully crafted text into the interaction stream; this text is then stored as a persistent memory. The memory store uses a dense embedding model to index entries. At inference time, the retriever computes cosine similarity between the query embedding and stored memories, returning the top‑k matches. Because the injected memories are designed to be embedding-close to either existing clean memories or the target query, they are co‑retrieved and influence the LLM's generation. Attack primitives (e.g., harsh instructions, contradictions, noise) are applied to transform clean memories or create new false memories. Ensembles combine multiple primitives per target to increase retrieval likelihood and reinforce misleading context. The evaluation uses the LoCoMo multi‑session conversation dataset, victim LLMs (Llama3.2, Gemma3, GPT‑oss), and memory implementations (A‑mem, Mem0). Metrics include F1, BLEU‑1, ROUGE‑1, Exact Match, and attack success rate; retrieval frequency of adversarial memories is also logged.

## Key Results
- Content‑based attacks using single primitives degrade F1 by 22.7–71.5% across memory systems and models.
- Ensemble attacks (multiple primitives per memory) push degradation to 72–88%, nearly collapsing long‑term reasoning.
- Question‑targeted attacks with 1–2 injected memories per question lower F1 by 40–56%.
- Adversarial memories are retrieved in >98% of cases when top‑k ≥ 20, confirming the reliance on pure similarity.
- Mem0 exhibits higher vulnerability than A‑mem, likely due to its less structured memory representation.

## Why This Works (Mechanism)
### Mechanism 1: Similarity‑based retrieval enables persistent reasoning corruption without internal access.
The adversary injects text that becomes a memory; because retrieval selects memories solely on cosine similarity in the embedding space, adversarial memories that are embedding‑close to clean memories or queries are co‑retrieved. The LLM then conditions on these false memories, adopting incorrect beliefs or instructions. The core assumption is that dense similarity ranking does not verify semantic correctness; embedding proximity suffices for co‑retrieval. Evidence: Abstract and Section 3.2 define imperceptibility as embedding proximity; Tables 2‑4 and 6 show degradation correlating with high retrieval rates of adversarial memories.

### Mechanism 2: Automatic memory writing creates an unbounded attack surface.
Systems like Mem0 and A‑mem automatically extract and store memories from interaction content without explicit user consent or pre‑storage filtering. An attacker can influence the interaction content, causing malicious text to be summarized and persisted as a memory entry. The core assumption is that no gatekeeper validates candidate memories before insertion. Evidence: Section 4.1 and Appendix C.1 describe automatic extraction; Section B notes writing is mediated by LLM‑based policies rather than explicit user consent.

### Mechanism 3: Ensemble attacks amplify degradation by increasing retrieval likelihood and reinforcing misleading context.
Instead of a single adversarial memory per clean memory, ensembles inject multiple variant adversarial memories (e.g., instruction‑based, contradiction, negation). This raises the probability that at least one is retrieved (multiple embedding‑close points) and exposes the LLM to consistent false signals from multiple angles, overwhelming correct memories even when some are also retrieved. Core assumption: top‑k returns multiple memories; multiple adversarial points in the same embedding region increase co‑retrieval and create a compelling misleading context. Evidence: Section 4.2; Table 3 shows ensembles achieve 80‑88% F1 drop vs. ~71.5% max for single primitives; Section 5.3 notes larger k often worsens performance due to increased adversarial co‑retrieval.

## Foundational Learning
- **Concept: Long‑Term Memory‑Augmented LLM Architecture**  
  *Why needed*: Understanding the two‑stage (write → read) pipeline is essential to see where the attacker intervenes. ER‑MIA targets the read stage but exploits the automatic write stage.  
  *Quick check*: What are the two main functions of a long‑term memory system for an LLM, and which one does ER‑MIA target?

- **Concept: Dense Vector Retrieval via Embedding Similarity**  
  *Why needed*: The attack hinges on the retriever using cosine similarity; ranking without verification explains why embedding‑close but semantically wrong memories succeed.  
  *Quick check*: Why does an adversarial memory that is lexically or semantically corrupted but embedding‑close to a clean memory still get retrieved?

- **Concept: Black‑Box Threat Model**  
  *Why needed*: Defines the attacker's capabilities (only interaction input) and constraints (no internal access), distinguishing this from white‑box poisoning or trigger‑based backdoors.  
  *Quick check*: Under ER‑MIA's black‑box setting, what *can* the adversary control, and what *cannot* they see or modify?

## Architecture Onboarding
**Component map**: Interaction Interface -> Memory Writer -> Memory Store -> Retriever -> LLM Backend

**Critical path**: Normal interaction → Writer automatically stores content including attacker text → Later query → Retriever fetches embedding‑close adversarial memory → LLM conditions on adversarial memory → Corrupted output.

**Design tradeoffs**:
- *Writing aggressiveness*: Automatic, frequent writing improves coverage but increases injection surface.
- *Retrieval simplicity*: Pure similarity search is efficient but vulnerable to semantic collisions.
- *Memory structuring*: Unstructured (Mem0) vs. linked notes (A‑mem) influences but does not eliminate vulnerability.

**Failure signatures**:
- Large relative drop in QA metrics (F1, BLEU‑1) after attack (e.g., −71.5% on Mem0).
- Adversarial memory retrieval rate ~100% for k≥20 (Table 6).
- Degradation occurs even when clean memories are also retrieved (qualitative examples in Appendix A).

**First 3 experiments**:
1. Baseline reproduction: Run LoCoMo evaluation with clean memory only on target system (A‑mem/Mem0) and model (e.g., Llama3.2). Confirm baseline F1 matches paper's reproduced baselines.
2. Single‑primitive content attack: Apply "Harsh Instruction" primitive to all clean memories. Verify F1 drop of ~20‑70% and that adversarial memories appear in top‑k for attacked questions.
3. Ensemble attack: Inject 3‑4 primitive variants per clean memory. Verify near‑collapse (F1 drop >80%) and retrieval rate for at least one adversarial memory approaches 100%.

## Open Questions the Paper Calls Out
### Open Question 1
How can we design robust memory sanitization or filtering mechanisms that prevent adversarial memories from being stored, without degrading the utility of legitimate memory updates?  
*Basis*: The authors suggest a gatekeeper can filter or downweight candidate memories (Section D) but do not evaluate or formalize such defenses.  
*Unresolved*: Effective defenses must operate during the writing phase under black‑box constraints, balancing false positives and negatives; no practical, evaluated defense exists.  
*Needed evidence*: Empirical evaluation of memory filtering policies (e.g., adversarial memory detectors, credibility scoring) on ER‑MIA attack success across diverse systems, with metrics on both security and task performance.

### Open Question 2
To what extent are other emerging long‑term memory architectures (beyond A‑mem and Mem0) vulnerable to embedding‑similarity‑based adversarial injection, and which architectural choices mitigate or exacerbate the risk?  
*Basis*: The study evaluates only two memory systems; it speculates on architectural reasons but does not generalize.  
*Unresolved*: New designs (hierarchical, graph‑based, hybrid) may differ; systematic testing is needed.  
*Needed evidence*: A benchmark evaluation spanning a wide array of memory system implementations under consistent ER‑MIA settings, measuring degradation and adversarial retrieval rates, correlated with architectural features.

### Open Question 3
Can retrieval mechanisms decoupled from pure embedding similarity (e.g., using multi‑modal consistency checks, temporal or source credibility weighting, diversified retrieval reranking) effectively mitigate adversarial memory injection while preserving performance on legitimate queries?  
*Basis*: Authors conclude similarity‑based retrieval is a fundamental vulnerability and propose retrieval diversification and re‑ranking using credibility signals (Section D).  
*Unresolved*: Practical efficacy, overhead, and interaction with different LLM reasoning styles are unknown.  
*Needed evidence*: Implementation and rigorous comparison of alternative retrieval pipelines (e.g., clustering‑based, cross‑encoder reranking, memory‑type aware) against ER‑MIA, measuring the robustness‑performance trade‑off.

### Open Question 4
What is the theoretical limit of attack stealthiness versus effectiveness? What is the minimum perturbation (in embedding space) required to reliably induce reasoning failures across diverse LLM architectures, and how does this relate to the model's sensitivity to in‑context instruction or contradiction?  
*Basis*: Attack primitives operate under an imperceptibility constraint (embedding similarity ≥ σ_s) chosen heuristically; the paper does not characterize the decision boundary.  
*Unresolved*: Understanding this boundary could inform stronger attacks and more precise defenses.  
*Needed evidence*: Controlled experiments varying embedding similarity of injected memories across multiple victim LLMs, measuring correlation between similarity and attack success rate to reveal thresholds.

### Open Question 5
How do ensemble attacks optimally combine primitives to maximize degradation across different victim LLMs and memory systems? Is there a universal "most effective" ensemble, or does optimal composition depend on the target model's size, architecture, or instruction‑following tendencies?  
*Basis*: The paper introduces ensembles and evaluates several combinations (Table 3) but does not analyze why certain ensembles perform best.  
*Unresolved*: The combinatorial space of ensembles remains heuristic; no principled guide exists.  
*Needed evidence*: An ablation or attribution study analyzing the contribution of each primitive within successful ensembles to identify whether success stems from redundancy, complementary interference, or specific semantic clashes.

## Limitations
- **Missing Artifacts**: Core attack code is not yet released, hindering exact replication of orchestration, logging, and hyperparameters.
- **Unspecified Attack Generator**: The LLM and decoding settings used to generate adversarial memories (via Appendix F prompts) are unknown, risking variation in embedding similarity and attack efficacy.
- **Assumption Dependency**: Claims rely on specific memory write order (clean then adversarial) and absence of pre‑storage filtering, which are inferred but not explicitly validated or compared against alternative memory architectures.

## Confidence
- **Mechanism 1 (Similarity‑based corruption)**: High – Strong empirical evidence (Tables 2‑4, 6) shows degradation correlating with retrieval of embedding‑close memories; mechanism logically sound given dense retrieval design.
- **Mechanism 2 (Automatic writing surface)**: Medium – Paper documents writing policies (Section C.1) and assumes no filtering, but does not systematically test systems with pre‑storage validation; claim partly based on architectural description.
- **Mechanism 3 (Ensemble amplification)**: High – Clear experimental gradient (Table 3) shows ensembles > single primitives; retrieval analysis (k≥20) supports co‑retrieval logic.

## Next Checks
1. **Baseline verification**: Reproduce clean memory QA performance on LoCoMo for each model/system pair to match reported baselines (±2% F1). If mismatched, check embedding model loading and retrieval k.
2. **Adversarial retrieval audit**: For sampled attacked questions, log top‑k retrieved memories and compute (a) % where at least one adversarial memory appears; (b) average cosine similarity between adversarial and its target clean memory/query. Success requires >95% retrieval and high similarity.
3. **Injection timing test**: Compare two conditions: (a) inject adversarial memories *after* clean memory write; (b) inject *before* any writes. Measure final memory bank and attack success. If (b) reduces success, confirms dependency on write‑order.
