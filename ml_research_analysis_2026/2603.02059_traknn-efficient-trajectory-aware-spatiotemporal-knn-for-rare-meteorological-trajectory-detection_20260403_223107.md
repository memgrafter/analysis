# TRAKNN: Efficient Trajectory Aware Spatiotemporal kNN for Rare Meteorological Trajectory Detection
## Quick Facts
- **arXiv ID:** 2603.02059
- **Source URL:** https://arxiv.org/abs/2603.02059
- **Reference count:** 36
- **Primary result:** Exact spatiotemporal kNN algorithm with constant memory (~6 GB) enables workstation-scale identification of rare trajectories validated by independent storm catalogs.

## Executive Summary
TRAKNN addresses the computational bottleneck of exhaustively searching for geometrically rare short trajectories in multi-decadal, continental-scale spatio-temporal climate data. The method is an exact *k*-nearest neighbors algorithm that updates trajectory distances via a recurrence relation, decoupling the cost from trajectory length. It efficiently precomputes a spatial distance matrix using batched matrix operations and excludes overlapping windows to avoid trivial matches. Evaluated on 75 years of European sea-level pressure data, TRAKNN maintains a constant ~6 GB memory footprint irrespective of trajectory length, in contrast to vector-search libraries that scale linearly with length. Detected rare trajectories align significantly with independent extreme windstorm databases and produce physically coherent composite pressure patterns. The low intrinsic dimensionality of the trajectory data further justifies the use of Euclidean distance.

## Method Summary
TRAKNN first transforms a time series of daily spatial fields into overlapping trajectories of duration *d* days. It precomputes an *n* × *n* spatial distance matrix **S** via batched General Matrix–Matrix Multiplication (GeMM), exploiting Level‑3 BLAS for high computational intensity. For any two trajectories starting at *i* and *j*, the squared Euclidean distance is updated by the recurrence:
\[
D(i,j) = D(i-1,j-1) - S(i-1,j-1) + S(i+d-1,j+d-1),
\]
with initialization summing the first *d* distances. This recurrence makes each update constant‑time in *d*. An exclusion zone *e* enforces \(|i-j|>e\) to avoid overlapping neighbors. Finally, for each trajectory, the *k* smallest distances among eligible candidates are averaged to yield the rarity score. Implemented in PyTorch, the approach supports both CPU and GPU execution.

## Key Results
- Constant memory usage (~6 GB) independent of trajectory length *d*, whereas FAISS memory grows linearly with *d*.
- Significant validation against storm catalogs: for *d* from 1 to 7 days, 6–12 of the top‑100 rarest trajectories overlap with CLIMK‑WINDS (expected random ~0.7).
- Composite analysis of top trajectories reveals physically coherent pressure anomaly patterns, and intrinsic dimensionality is low (~18–21), validating Euclidean distance.

## Why This Works (Mechanism)
### Mechanism 1: Recurrence-Based Trajectory Distance Update
- **Claim:** The computational cost for updating trajectory distances is independent of trajectory length *d*.
- **Mechanism:** Consecutive trajectories share *d* − 1 days. The squared distance is updated by removing the contribution of the first day’s field and adding that of the new last day’s field, using the precomputed spatial distance matrix **S**.
- **Core assumption:** The full *n* × *n* matrix **S** fits in RAM.
- **Break condition:** If *n* is so large that **S** exceeds available memory, the method becomes infeasible on standard workstations.

### Mechanism 2: Batched GeMM for Spatial Distance Matrix
- **Claim:** Efficient computation of the *n* × *n* spatial distance matrix **S** via batched matrix operations.
- **Mechanism:** Squared Euclidean distance = \(\|X_i\|_F^2 + \|X_j\|_F^2 - 2\langle X_i, X_j \rangle_F\). Norms are precomputed. Batched GeMM \(G = B_i^T B_j\) computes inner products for batches of vectorized fields, maximizing FLOP utilization. Symmetry reduces work to the upper triangle.
- **Core assumption:** Hardware provides high‑performance Level‑3 BLAS (e.g., GeMM) and sufficient GPU memory for chosen batch size.
- **Break condition:** Extremely large spatial dimensions could force tiny batch sizes, lowering computational intensity.

### Mechanism 3: Explicit Exclusion Zone for Non‑Trivial Similarity
- **Claim:** Preventing spurious high similarity from temporally overlapping trajectories.
- **Mechanism:** When querying *k* neighbors for trajectory starting at *i*, only trajectories with start index *j* such that \(|i-j| > e\) are considered. Typically *e* is set at least *d* to guarantee non‑overlapping windows.
- **Core assumption:** Trivial matches from overlapping windows would dominate neighbor rankings and mask genuinely rare patterns.
- **Break condition:** An excessively large *e* relative to meaningful pattern durations might erroneously exclude relevant analogues.

## Architecture Onboarding
- **Component map:**  
  Data Loader → **S** Builder → Trajectory Distance Initializer → Recurrence Engine (loop over start indices) → kNN Selector & Scorer → Post‑processor (e.g., composite analysis).
- **Critical path:** **S** Builder dominates runtime; Recurrence Engine performs \(O(n^2)\) constant‑time updates; kNN selection uses efficient batched top‑*k*.
- **Design tradeoffs:**  
  - Memory vs. time: Storing full **S** enables *O*(1) recurrence updates but costs *O*(n²) RAM.  
  - Exactness vs. scale: Exact Euclidean kNN is achieved, but *n* is limited by the memory required for **S**.  
  - Batching: GeMM batching improves GPU utilization but requires careful batch‑size selection to avoid GPU memory overflow.
- **Failure signatures:**  
  - Unexplained memory blowup: likely due to storing **S** in float64 or duplicating storage.  
  - Non‑physical top‑ranked composite patterns: may indicate too small *k*, too small exclusion zone *e*, or incorrect preprocessing.  
  - Poor catalog validation: could stem from mismatched *d*, inappropriate variable, or insufficient record length.
- **First 3 experiments:**  
  1. **Recurrence correctness:** On a tiny synthetic dataset (*n*=10, spatial 2×2, *d*=3), directly compute a few \(D(i,j)\) values and compare against recurrence; relative error < 1e‑6.  
  2. **Memory independence from *d*:** Run TRAKNN on the same data with *d* = 1, 5, 10; peak RAM should remain constant.  
  3. **Detection validation:** For *d*=5, *k*=10, count overlap of top‑100 trajectories with CLIMK‑WINDS; expect ~11 matches, far above random ~0.7.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can TRAKNN be extended to handle spatio‑temporal datasets that exceed available RAM through out‑of‑core computation?
- **Basis in paper:** Future work could investigate out‑of‑core computation to account for large spatial or temporal domains that might not fit in memory.
- **Why unresolved:** The current algorithm requires the full spatial distance matrix and data tensor in memory, limiting scalability.
- **What evidence would resolve it:** An implemented out‑of‑core version that chunks data loading and computation, with benchmarks showing exactness preservation and reduced memory footprint on larger‑than‑memory datasets.

### Open Question 2
- **Question:** How can trajectory‑based analogues from TRAKNN be integrated into existing flow‑analogue frameworks for extreme event attribution?
- **Basis in paper:** Future work will investigate the incorporation of trajectory‑based analogues in the flow analogues analysis.
- **Why unresolved:** The paper positions TRAKNN as a tool for rare trajectory detection but does not connect its outputs to established flow‑analogue methodologies.
- **What evidence would resolve it:** A study applying TRAKNN‑identified trajectories within a flow‑analogue pipeline, demonstrating improved attribution skill or new physical insights.

### Open Question 3
- **Question:** Why does the detection rate of extreme windstorms in impact‑based databases (e.g., EM‑DAT) non‑monotonic with trajectory length, unlike meteorological catalogs?
- **Basis in paper:** Table 2 shows EM‑DAT storm detections drop from *d*=1 to *d*=3 before rising, while CLIMK‑WINDS increases monotonically; detection is more consistent in catalogs constructed using meteorological severity indices.
- **Why unresolved:** The paper does not analyze why longer trajectories sometimes reduce matches for impact‑based events, leaving unclear whether this reflects event temporal fragmentation or database biases.
- **What evidence would resolve it:** A temporal alignment analysis of EM‑DAT events with high‑scoring trajectories across durations, examining event duration distribution and reporting practices versus continuous meteorological indices.

### Open Question 4
- **Question:** Is Euclidean distance equally valid for trajectory‑based rarity detection across different meteorological variables (e.g., temperature, geopotential height), or is its efficacy specific to sea‑level pressure?
- **Basis in paper:** The study only uses sea‑level pressure and justifies Euclidean distance via low intrinsic dimension estimates; no tests on other variables are reported, though the method is claimed “data‑agnostic.”
- **Why unresolved:** The paper assumes Euclidean distance remains meaningful due to low ID, but this property may not hold for variables with different spatial structures.
- **What evidence would resolve it:** Applying TRAKNN with Euclidean distance to multiple variables (e.g., temperature, humidity) and comparing results against domain‑known rare events or alternative metrics, supported by intrinsic dimension estimates per variable.

## Limitations
- The exact exclusion zone *e* value used in experiments is not reported; this parameter is critical for filtering non‑overlapping neighbors.
- The *O*(n²) memory requirement (storing **S**) limits the temporal span to roughly 75 years on workstations; larger *n* would need out‑of‑core solutions.
- Intrinsic dimensionality estimates and their robustness to preprocessing choices and trajectory length have not been thoroughly explored.
