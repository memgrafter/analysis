# Policy Compliance of User Requests in Natural Language for AI Systems

## Quick Facts
- arXiv ID: 2603.00369
- Source URL: https://arxiv.org/abs/2603.00369
- Reference count: 20
- Primary result: Benchmark of 225 requests vs 9 policies shows sequential prompting with reframing (S.P. with Both) achieves highest accuracy (55.11% on 120B), with smaller models (1B/8B) often matching larger ones, indicating task suitability for cost-effective LLMs.

## Executive Summary
This paper introduces the first benchmark for evaluating policy compliance of natural language user requests in AI systems. The benchmark comprises 225 annotated requests against nine non-overlapping tech-sector policies; each non‑compliant request violates exactly one policy. Several plug‑and‑play LLM‑based methods are assessed, the most effective being sequential prompting (S.P.) augmented with reframing techniques—policy association and request planning. Across six open‑source models (1B–120B parameters), overall accuracy peaks at 55.11% (120B). Notably, smaller models (1B, 8B) frequently match or outperform larger relatives in the same family when using S.P. with Both. Complex argument‑based approaches consistently underperform simpler methods. The key finding—model size does not guarantee better compliance assessment—motivates the use of smaller, cost‑effective LLMs for this guardrail task.

## Method Summary
The task is to act as a pre‑filter for AI systems: given a user request and a set of organization‑defined policies, determine whether the request complies and, if not, identify which single policy it violates. The benchmark contains 225 requests (≈53% compliant, ≈47% non‑compliant) and nine policies covering privacy, prompt injection, guardrail exposure, and protected destinations. Solution methods are inference‑time techniques requiring no fine‑tuning: Single Prompting (all policies at once), Sequential Prompting (S.P., i.e., per‑policy checks), and variants with reframing—policy association (is the request associated with the forbidden action?) and request planning (does a step‑by‑step plan violate the policy?). More intricate methods like Two Arguments (T.A.) and Convincing Decision (C.D.) generate and evaluate arguments. All methods are zero‑shot with temperature 0.

## Key Results
- Highest accuracy: 55.11% (120B model).
- Smaller models (1B, 8B) often match or exceed larger counterparts within the same family; S.P. with Both yields strong accuracy for smaller models (e.g., 53.33% for Llama 3.1 8B).
- Complex argument‑based methods underperform simpler sequential prompting across most models.

## Why This Works (Mechanism)
Sequential Prompting with reframing decomposes the joint compliance judgment into per‑policy assessments, reducing cognitive load. By transforming the abstract check into semantic matching—association or planning—the approach leverages the model’s strengths in concrete reasoning over holistic classification. Evidence: S.P. with Both attains top accuracy for smaller models (Sec. 5.2), while Single Prompting suffers from context limits and poor performance on the same.

The task’s constrained nature (well‑defined, negative‑formulated rules; single‑violation requests) favors smaller models. Unlike open‑ended reasoning tasks, compliance assessment does not require emergent capabilities, and smaller models may avoid over‑thinking or hallucinations. Data show 1B/8B models sometimes exceed 70B/120B relatives (Sec. 5.2), contradicting a monotonic size‑performance relationship.

Reframing primarily boosts true negative rates. Compliant requests often contain policy‑related keywords; by forcing explicit intent and step analysis, reframing distinguishes “mentioning” a prohibited concept from actually “requesting” it, thus reducing false positives. For Llama 3.1 8B, S.P. with Both raises TN from 9.33% (Single Prompting) to 43.11% while TP remains similar, illustrating the TN gain (Sec. 5.2, Table 1). Break conditions: policies become overlapping (invalidating isolation); task complexity increases (requiring multi‑step reasoning); or policies are trivial (making reframing overhead unnecessary).

## Foundational Learning
**Concept: Policy Decomposition & Non-Overlap**  
Why needed: The benchmark and solution design assume each non‑compliant request violates exactly one policy, enabling per‑policy checks and clean metrics.  
Quick check: If a request violated two policies, how would accuracy and FN* be affected? What design change would allow multi‑violation handling?

**Concept: Sequential Prompting & Reframing as Inference‑Time Techniques**  
Why needed: These are the core plug‑and‑play methods; understanding the difference between holistic and decomposed assessment is key to implementation.  
Quick check: What is the practical difference between “S.P. with Policy A.” and “S.P. with Request P.”? What aspect of the request does each reframing surface?

**Concept: Classification Metrics for Multi‑Label, Single‑Truth Scenario**  
Why needed: The problem is multi‑label (9 policies) but each non‑compliant request has exactly one true violated policy; metrics like TP, TN, FN*, and accuracy are defined accordingly.  
Quick check: Explain how a model could have low FN yet low accuracy. What would a high FN* indicate?

## Architecture Onboarding
Component map (plain text):  
Policy Bank (static list of prohibitions) → User Request Input → Solution Method Orchestrator (prompt construction, LLM call sequencing) → LLM Backbone (model) → Compliance Verdict (list of violated policies, empty if compliant). Evaluation Harness (compares verdict to ground truth, computes metrics).

Critical path: User Request → Orchestrator (for each policy or all at once) → LLM call(s) → Parse response → Compile Violation List → Output.

Design tradeoffs:
- Simplicity vs. Accuracy: Single Prompting (1 call) is simple but less accurate; S.P. with Both adds calls but improves TN.
- Scalability vs. Precision: S.P. methods scale linearly with number of policies; argument‑based methods add more calls but generally underperform.
- Cost/Latency vs. Robustness: Fewer LLM calls reduce expense but may be less robust to tricky compliant requests; more calls increase robustness.

Failure signatures:
- High FP: Many compliant requests flagged → likely keyword matching; see methods with low TN (e.g., Single Prompting on small models).
- High FN: Many violations missed → overly permissive; check low TP.
- High FN*: Violation detected but wrong policy identified → confusion between policy semantics; check methods without reframing.
- Categorical failure (0% metrics): Non‑parsable output or default “compliant” → improve prompt clarity, check model’s instruction following.

First 3 experiments:
1. Baseline replication: Run Single Prompting with Llama 3.1 8B; verify accuracy ≈22.67%, TP ≈13.33%, TN ≈9.33% (Table 1).
2. Reframing impact: Run S.P. with Both with Llama 3.1 8B; expect accuracy ≈53.33%, TN ≈43.11% (Table 1).
3. Size assumption test: Compare Llama 3.1 8B vs. Llama 3.3 70B using S.P. with Both; expect smaller model to have higher accuracy (53.33% vs. 50.22%) but lower TP and higher TN (Table 2).

## Open Questions the Paper Calls Out
**Open Question 1:** Can existing solution methods correctly identify user requests that violate multiple policies simultaneously?  
Basis: The benchmark deliberately constructed each non‑compliant request to violate exactly one policy (Sec. 3).  
Why unresolved: Real‑world requests may contain several non‑compliant intents; unknown if methods generalize.  
What evidence would resolve: Create a test set with intentional multi‑policy violations and evaluate with multi‑label metrics (e.g., macro‑F1).

**Open Question 2:** How can user‑specific access privileges be incorporated into the policy compliance assessment pipeline?  
Basis: The authors note their framework assumes enforcement on any user, whereas industrial deployments apply policies based on roles (Sec. 3, Remarks).  
Why unresolved: Ignoring user context may cause false positives/negatives; impact of adding role information is unknown.  
What evidence would resolve: Extend the benchmark with role annotations, modify methods to accept requester role, and measure accuracy changes.

**Open Question 3:** Does augmenting prompts with in‑context examples (few‑shot learning) improve accuracy of policy compliance assessment?  
Basis: The authors state in‑context learning can be easily added but was not evaluated (Sec. 4, Remark 4).  
Why unresolved: Few‑shot learning benefits many tasks; its effect here remains untested.  
What evidence would resolve: For each method, include a small number of labeled examples in prompts and compare zero‑shot versus few‑shot results.

**Open Question 4:** Why do complex argument‑based methods (Two Arguments, Convincing Decision and variants) consistently underperform simpler sequential prompting?  
Basis: Results show these methods never exceed simpler ones in accuracy, TP, or TN for most models (Sec. 5.2).  
Why unresolved: Possible reasons include low‑quality arguments, noise from extra LLM calls, or model limitations; not investigated.  
What evidence would resolve: Conduct error analysis—human‑evaluate generated arguments, correlate argument quality with decisions, and test prompt variations to isolate failure modes.

## Limitations
- Benchmark data (9 policies + 225 requests) is not publicly available, hindering direct replication.
- Exact prompt templates for each solution method are not provided; reconstructed prompts may differ from the authors’, affecting performance comparisons.
- The “smaller models match larger ones” finding is limited to a few model families (Llama, Gemma, Mistral); generalizability to other architectures or proprietary models is uncertain.

## Confidence
- Benchmark design & metrics: High confidence (rigorously defined and internally consistent).
- Sequential prompting + reframing efficacy: Medium confidence (strong evidence from reported tables, but exact mechanism inferred and not explicitly validated).
- Inverse scaling law (smaller models better for this task): Medium confidence (based on limited model diversity; proprietary models not tested).

## Next Checks
1. **Dataset Reconstruction**: Generate a proxy dataset adhering to the paper’s constraints (non‑overlapping policies, single‑violation requests, keyword/semantic traps) to re‑run key experiments and validate performance trends.
2. **Prompt Reconstruction & Sensitivity**: Systematically derive prompt templates from methodological descriptions; perform sensitivity analysis on phrasing/formatting to ensure gains from “S.P. with Both” are robust.
3. **Cross‑Family Scaling Test**: Evaluate at least one additional model family (e.g., medium‑sized Claude or GPT via API) using the same methods to test whether the non‑monotonic size‑performance relationship is task‑intrinsic or family‑specific.
