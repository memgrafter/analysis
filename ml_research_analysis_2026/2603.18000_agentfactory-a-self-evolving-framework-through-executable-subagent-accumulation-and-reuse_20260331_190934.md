# AgentFactory: A Self-Evolving Framework Through Executable Subagent Accumulation and Reuse
## Quick Facts
*   **arXiv ID:** 2603.18000
*   **Source URL:** https://arxiv.org/abs/2603.18000
*   **Reference count:** 38
*   **Primary result:** Preserving successful task solutions as executable Python subagents reduces orchestrating agent output tokens by 35-60% compared to ReAct and textual self-evolving baselines.

## Executive Summary
AgentFactory introduces a framework for long-horizon agent self-evolution that addresses the inefficiency of textual experience accumulation. Instead of storing natural language reflections, it preserves successful, complex task solutions as pure Python subagent modules. These subagents are autonomously created, refined based on execution feedback, and stored in a persistent skill library. A Meta-Agent orchestrates tasks by first attempting to reuse relevant saved subagents, dramatically reducing the token effort required for similar future tasks. Evaluation on 30 web interaction tasks using Claude models shows significant token reductions in the orchestrator's output when reusing saved and evolved subagents, demonstrating continuous capability accumulation.

## Method Summary
The framework operates through a three-phase lifecycle per task. **Install**: For a new task, the Meta-Agent constructs a new subagent from scratch if no suitable existing one is found, saving its pure Python code. **Self-Evolve**: When a saved subagent is reused but fails or underperforms on a new instance, the Meta-Agent analyzes the execution trace and invokes `modify_subagent` to iteratively refine the subagent's source code. **Deploy**: Validated subagents are exported as standardized, portable Python modules with a `SKILL.md` file, enabling use outside the AgentFactory runtime. The core hypothesis is that executable code preserves procedural knowledge more reliably for reuse than textual summaries, and that LLM-driven code modification enhances subagent robustness and generality.

## Key Results
*   Reusing saved subagents on Batch 2 tasks reduced the Meta-Agent's average output tokens by 2971–6210 (Claude Opus/Sonnet) compared to ReAct (7022–8298) and textual self-evolving agents (6210–8223).
*   The Self-Evolve phase provided additional benefit over direct reuse, indicating that autonomous code refinement improved subagent applicability.
*   Saved subagents are pure Python with standardized documentation, demonstrated to be portable and invocable by external agents like Claude Code.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** Reusing successful task solutions as executable code reduces orchestrating agent effort more effectively than reusing textual reflections.
*   **Mechanism:** Successful subagent solutions are saved as pure Python modules. For subsequent similar tasks, the Meta-Agent directly invokes these modules as tools, bypassing the need to re-generate complex procedural logic from textual descriptions.
*   **Core assumption:** Executable code captures procedural knowledge more reliably and completely than textual prompts for re-execution in multi-step workflows.
*   **Evidence anchors:** [abstract] "preserves successful task solutions as executable subagent code"; [section 3.2] "Saved subagents consist of pure Python code... become part of the growing skill library."
*   **Break condition:** If saved subagents are too brittle for minor task variations, requiring near-complete rewrites, orchestration effort reduction fails.

### Mechanism 2
*   **Claim:** Subagents become more robust and general through autonomous code refinement based on execution feedback.
*   **Mechanism:** Upon failure, the Meta-Agent analyzes the trace, diagnoses the issue, and uses `modify_subagent` to alter the subagent's source code (e.g., adding error handling), creating an iterative "generate-test-modify" loop.
*   **Core assumption:** Modifying executable code allows for concrete, structural improvements that enhance operational robustness and applicability to wider input ranges.
*   **Evidence anchors:** [section 4.1] Figure 2 shows evolution from a hardcoded path to a regex-based solution via code modification; [section 3.3] describes the autonomous improvement loop.
*   **Break condition:** If code modifications consistently introduce new, harder-to-diagnose errors (error avalanche), self-evolution degrades capability.

### Mechanism 3
*   **Claim:** Portable, standardized subagent modules enable cross-framework capability transfer.
*   **Mechanism:** All saved subagents are pure Python scripts with a standardized `SKILL.md` file, decoupling functionality from the AgentFactory runtime. External LLM-based agents can understand and invoke them by reading the documentation and code.
*   **Core assumption:** Standardized interfaces and pure Python implementations provide sufficient abstraction for external adoption.
*   **Evidence anchors:** [abstract] "Saved subagents are pure Python code with standardized documentation, enabling portability"; [section 3.4] describes integration via invocation prompts and documentation; [section 4.2] demonstrates reuse by Claude Code.
*   **Break condition:** If subagents make deep, non-standardized assumptions about their environment, portability fails.

## Foundational Learning
*   **Concept: Task Decomposition**
    *   **Why needed:** The Meta-Agent must break complex queries into discrete sub-problems assignable to subagents. Poor decomposition misses reuse opportunities or creates unmaintainable scripts.
    *   **Quick check:** For "Analyze AAPL/TSLA 2023 trends and create a PDF report," list plausible sub-tasks and potential reused subagents for each.
*   **Concept: Tool-Augmented Reasoning / Function Calling**
    *   **Why needed:** Subagents must reliably invoke primitive tools (`web_search`, `shell_command`). The Meta-Agent must correctly allocate these tools when constructing a new subagent.
    *   **Quick check:** If a new subagent needs to browse a paginated website, which built-in tool skills are essential, and how should `create_subagent` specify their use?
*   **Concept: Feedback-Driven Iteration**
    *   **Why needed:** This is the engine of Self-Evolve. The system must interpret execution errors as signals to modify code, not just retry.
    *   **Quick check:** A `web_reading` subagent returns `None` for a specific URL. List two distinct code-level modifications (not prompt changes) to handle this robustly.

## Architecture Onboarding
*   **Component map:** Meta-Agent (Orchestrator) -> Skill System (Registry: Fixed Meta-Skills, Fixed Tool Skills, Dynamic Subagent Skills) & Workspace Manager (isolated filesystem per task). The Meta-Agent invokes actions (`create_subagent`, `modify_subagent`, `run_subagent`, `list_saved_subagents`) that interact with both the Skill System and Workspace Manager.
*   **Critical path:** For a task, the Meta-Agent first checks `list_saved_subagents` for reuse candidates. If none fit, it enters the **Install** phase to create and save a new subagent. If a saved subagent is reused but fails, it enters the **Self-Evolve** phase to retrieve, diagnose, modify, and re-validate. Successful subagents eventually enter **Deploy** for standardized export. The path is a loop triggered per task.
*   **Design tradeoffs:** Specialization vs. Generalization (Self-Evolve pushes toward generalization); Safety vs. Autonomy (isolated workspaces vs. risky code generation); Portability vs. Performance (pure Python vs. optimized framework-specific integrations).
*   **Failure signatures:** Inadequate decomposition (monolithic subagent creation); Fragile modifications (`modify_subagent` causes regressions); Dependency hell (saved subagent relies on unavailable library versions).
*   **First 3 experiments:**
    1.  **Baseline Establishment:** Run Batch 1 with `Install` only. Verify new subagent creation and measure initial token usage.
    2.  **Reuse Validation:** Run Batch 2 *without* `Self-Evolve` (only reuse). Confirm token reduction vs. ReAct, isolating direct reuse benefit.
    3.  **Evolution Validation:** Run Batch 2 with full `Self-Evolve`. Compare token counts to Experiment 2; further reduction indicates modification improved efficacy.

## Open Questions the Paper Calls Out
*   **Open Question 1:** How effectively can AgentFactory's self-evolution mechanism adapt to non-web-based tasks, such as those requiring Vision-Language Model (VLM) integration for GUI interaction? The current evaluation is limited to web-interaction tasks; the loop is untested in visual/GUI contexts where feedback may be non-textual.
*   **Open Question 2:** To what extent does the "prompt-based onboarding" method for Deploying subagents to external frameworks (e.g., LangChain, AutoGen) maintain performance parity versus native integration? The primary evaluation measures internal token reduction; external framework efficacy and fidelity are unexplored.
*   **Open Question 3:** How does the robustness and generality of self-evolved subagents compare against manually engineered, task-specific solutions or other code-based evolution methods (e.g., AlphaEvolve)? The evaluation contrasts only against textual baselines and ReAct; optimality vs. expert code and comparison to dedicated evolutionary algorithms are unmeasured.
*   **Open Question 4:** What are the failure modes and limits of the Meta-Agent's `modify_subagent` capability? When does its code modification introduce new bugs or fail to resolve core limitations? The paper does not analyze modification success rates, regression rates, or categories of unfixable bugs.
*   **Open Question 5:** Does continuous subagent accumulation lead to capability degradation or bloat over very long horizons (e.g., hundreds of tasks)? The 30-task demonstration is short; library size growth, retrieval bottlenecks, overfitting, and interoperability issues over longer horizons are unaddressed.

## Limitations
*   **Unreleased internal prompts:** Exact Meta-Agent prompts for creation/modification are not public, limiting precise replication and affecting subagent quality/token counts.
*   **External tool volatility:** Evaluation relies on live web APIs and dynamic sites; rate limits and site changes introduce noise not present in controlled paper runs.
*   **Task selection bias:** The 30 tasks may favor reuse scenarios; generalizability to broader, less homogeneous distributions is unknown.

## Confidence
*   **Token reduction via reuse:** High – Direct experimental comparison on 30 tasks shows strong, consistent reductions.
*   **Executable code > textual reuse:** Medium – Plausible mechanism with partial evidence, but superiority depends on unreleased prompt tuning and subagent brittleness.
*   **Autonomous refinement robustness:** Medium – Figure 2 shows iterative improvement, but break condition (error avalanche) is not stress-tested; long-term modification history unanalyzed.
*   **Cross-framework portability:** Medium – Standardized Python modules demonstrated with Claude Code, but real-world integration hurdles (dependency/env assumptions) remain unexplored.

## Next Checks
1.  **Brittleness stress test:** For each saved subagent from Batch 1, generate 20 minimally perturbed variants of its original task (e.g., altered URLs, data formats). Measure success rate decay to quantify generalization and identify overfitting.
2.  **Modification impact analysis:** Re-run Batch 2 with full Self-Evolve, logging every code modification. Analyze: a) regression rate (modifications breaking prior valid tasks), b) error type distribution, c) correlation between modification count and subagent robustness.
3.  **Portability integration trial:** Take 10 saved subagents and integrate them into external frameworks (LangChain, AutoGen) using only the provided SKILL.md and code. Measure: a) developer time to successful invocation, b) runtime failures from environmental assumptions, c) need for adapter code.
