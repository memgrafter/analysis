# AnalogAgent: Self-Improving Analog Circuit Design Automation with LLM Agents

## Quick Facts
- arXiv ID: 2603.23910
- Source URL: https://arxiv.org/abs/2603.23910
- Reference count: 40
- Primary result: AnalogAgent achieves 97.4% Pass@1 on a 30-task benchmark with GPT-5, reduces time-to-first-success to 1.3 minutes, and boosts Qwen-8B performance by +48.8% Pass@1.

## Executive Summary
Analog circuit design is a complex, expert-driven process. Recent LLM-based approaches struggle with context attrition across long iterations and rely on single-loop generation without accumulating design knowledge. AnalogAgent introduces a training-free multi-agent system (MAS) coordinated by a Self-Evolving Memory (SEM). Three agents—a Code Generator, a Design Optimizer, and a Knowledge Curator—collaborate to generate SPICE/Python scripts, execute simulations, and distill failure feedback into rules stored in an Adaptive Design Playbook. This playbook enables cross-task knowledge retrieval, mitigating context loss and guiding future designs. Evaluated on a 30-task benchmark, AnalogAgent attains up to 97.4% Pass@1 with GPT-5 and 92.0% with Gemini, while also significantly improving small model performance (72.1% Pass@1 with Qwen-8B, a +48.8% gain). The system operates without external circuit libraries or model training.

## Method Summary
The task is to automatically generate functionally correct analog circuit designs from natural-language specifications. Inputs include design instructions (e.g., “design an op-amp comparator”), circuit type identifiers, and verification criteria (simulation assertions). The primary metric is Pass@1, the probability of producing a valid design on the first attempt; secondary metrics include Pass@5 and Time-to-First-Success. Validity requires satisfying all functional assertions and simulator constraints.

AnalogAgent is a training-free framework that orchestrates three agents: (1) the Code Generator writes executable SPICE/Python design scripts; (2) the Design Optimizer runs multi-stage simulation checks (DC, AC, transient) and returns pass/fail diagnostics; (3) the Knowledge Curator analyzes failure modes, extracts generalizable rules (e.g., “ensure proper bulk connection”), and updates the Adaptive Design Playbook—a structured, rule-level memory. During subsequent iterations, the curator retrieves relevant rules from the playbook to constrain the Code Generator’s prompt, thereby enabling cross-task transfer and preventing context attrition. The system incrementally evolves its memory without external libraries, making it adaptable to new tasks.

## Key Results
- AnalogAgent reaches 97.4% Pass@1 with GPT-5 and 92.0% with Gemini on a 30-task benchmark, reducing average time-to-first-success to 1.3 minutes.
- With the compact Qwen-8B model, Pass@1 improves by a relative +48.8% to 72.1% absolute, outperforming prior approaches.
- The Self-Evolving Memory reduces context attrition: prompt token counts drop from 4.1K to 1.4K on a challenging task while maintaining performance.

## Why This Works (Mechanism)
AnalogAgent succeeds because it addresses two fundamental limitations of prior LLM-based design automation: (1) context attrition, where long interaction histories exceed model context windows and critical details are lost; and (2) single-loop generation, which fails to accumulate design knowledge across tasks. By distilling simulation feedback into concise, rule-level entries in the Adaptive Design Playbook, the system retains only the most actionable insights (e.g., missing DC paths, device sizing guidelines). The Knowledge Curator ensures that rules are generalizable and retrievable, allowing the Code Generator to be guided by past experience without bloating the prompt. The multi-agent separation isolates concerns: the Design Optimizer handles the numerical rigor of simulation, the Knowledge Curator focuses on abstraction and memory management, and the Code Generator concentrates on code synthesis. This division of labor, combined with incremental memory updates, enables efficient self-improvement without any model fine-tuning.

## Foundational Learning
- **SPICE simulation**: Why needed: The core validation runs electrical simulations (DC, AC, transient) to verify circuit functionality. Quick check: Can you run a simple ngspice simulation of a resistor divider and read node voltages?
- **LLM code generation**: Why needed: The Code Generator produces executable SPICE/Python scripts from natural language; reliability of the LLM in generating syntactically correct code is crucial. Quick check: Can you prompt an LLM to output a netlist for a CMOS inverter and verify it parses?
- **Multi-agent systems (MAS)**: Why needed: Coordination among specialized agents (generation, optimization, curation) reduces interference and clarifies responsibilities. Quick check: Can you design a two-agent loop where one writes code and another executes tests?
- **Rule-based memory**: Why needed: The Adaptive Design Playbook stores distilled design principles (e.g., “bias current must exceed process minimum”) that survive across tasks and models. Quick check: Can you extract a general rule from a failed netlist error and apply it to a new circuit?
- **Retrieval-augmented generation**: Why needed: Relevant rules must be injected into the Code Generator’s prompt to steer production. Quick check: Given a set of rules, can you select the ones most pertinent to a comparator design?
- **Context management**: Why needed: Long dialogues risk exceeding model context limits; the SEM compresses history into rules. Quick check: If a conversation exceeds 4K tokens, can you summarize key lessons into 3–5 bullet points?

## Architecture Onboarding
**Component map**: Code Generator → (design script) → Design Optimizer → (simulation results, diagnostics) → Knowledge Curator → (rule extraction, memory update) ↔ Adaptive Design Playbook; Knowledge Curator also retrieves rules → Code Generator prompt. This forms a cyclic generate-execute-diagnose-refine loop.

**Critical path**: The iteration begins with Code Generator producing a netlist. Design Optimizer simulates it, checks assertions, and returns pass/fail with logs. Knowledge Curator analyzes failures, extracts or updates rules in the playbook, and retrieves applicable rules for the next generation. The next iteration’s Code Generator prompt includes these retrieved rules plus previous attempts’ summaries.

**Design tradeoffs**:
- Training-free vs. performance: Avoiding external libraries and model fine-tuning increases portability but relies on prompt engineering and retrieval quality.
- Rule granularity: Too specific rules may not transfer; too general may be unhelpful. The curator must balance.
- Memory growth vs. retrieval cost: The playbook grows with each task; unbounded growth could slow retrieval and introduce conflicts. The system uses deduplication and filtering to mitigate this.
- Agent separation overhead: Three LLM calls per iteration increase latency but parallelize conceptually; actual cost depends on model speed.

**Failure signatures**:
- Simulation non-convergence (e.g., “gmin stepping” messages) indicates missing DC paths or improper biasing; rule likely about adding pull-ups or proper bulk connections.
- Netlist syntax errors (duplicate names, invalid `subcircuit` calls) suggest code generation mistakes; rule may involve consistent naming or template usage.
- Functional assertion failures (output stuck at rails) often stem from incorrect sizing or bias; rule may specify minimum overdrive or current mirror ratios.
- Context attrition: Repeated similar failures across iterations despite rule updates may point to retrieval failure or rule conflict.

**First three experiments**:
1. **Run Task 1**: Using the official artifact, execute the inference script on the single-stage amplifier task with a small model (e.g., Qwen-8B) to observe the loop and verify that the playbook populates with rules after failures.
2. **Inspect SEM updates**: After 5 iterations, examine the Adaptive Design Playbook file to confirm that new rules appear and that retrieval picks rules matching the current failure mode (e.g., bias errors).
3. **Prompt variation test**: Disable rule retrieval (empty playbook) and compare Pass@1 and iteration count against the full system on a held-out task to quantify the impact of memory.

## Open Questions the Paper Calls Out
- **Extension to complex circuits**: How does AnalogAgent perform on multi-stage amplifiers, PLLs, or RF front-ends with tighter specifications? Future evaluations on more demanding benchmarks are needed.
- **Scalability of Self-Evolving Memory**: As tasks accumulate to hundreds, will rule conflicts, retrieval latency, or memory bloat degrade performance? No experiments beyond 30 tasks are reported.
- **PDK integration**: Can the framework incorporate process design kit (PDK) constraints (e.g., minimum device sizes, matching rules) while remaining library-independent? The current benchmark uses generic models.
- **MAS overhead tradeoff**: What is the per-iteration computational cost of the three-agent coordination, and how does it scale across LLM sizes? The paper lacks a breakdown of tokens/wall-clock per agent call.

## Limitations
- **Incomplete reproduction details**: Simulator and PDK model paths, required versions, and hardware specs are unspecified, leading to potential environment mismatches.
- **API and rate-limit opacity**: Using GPT-5 or Gemini requires valid keys and handling nondeterministic costs; the paper does not document endpoint usage.
- **Prompt and retrieval black-box**: Exact prompt templates and the SEM retrieval ranking algorithm are omitted, hindering precise replication and analysis of memory dynamics.
