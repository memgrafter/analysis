# CiteAudit: You Cited It, But Did You Read It? A Benchmark for Verifying Scientific References in the LLM Era

## Quick Facts
- arXiv ID: 2602.23452  
- Source URL: https://arxiv.org/abs/2602.23452  
- Reference count: 39  
- Primary result: Multi-agent verification framework achieves F1 score of 0.968 on generated test set and 0.903 on real-world test set, with perfect recall on real-world citations.

## Executive Summary
The paper tackles the growing problem of hallucinated citations in AI‑generated scientific writing, which threatens research integrity and is hard to detect manually. It introduces CiteAudit, a multi‑agent verification framework that decomposes citation checking into specialized stages: claim extraction, evidence retrieval, passage matching, and calibrated judgment. Supported by a large‑scale human‑validated benchmark spanning multiple domains, the system significantly outperforms prior methods, achieving near‑perfect F1 on generated data and strong performance on real‑world citations. The pipeline operates with low runtime and no monetary cost, offering a scalable solution for auditing citation trustworthiness.

## Method Summary
CiteAudit processes a manuscript’s reference list by first extracting each citation’s metadata (title, authors, venue, year, URL) via an OCR/parsing agent. It then consults a memory cache of previously verified citations for a fast‑path decision. For unseen citations, a dual‑path retrieval cascade is triggered: a fast web search agent gathers evidence from top results, and a judge agent applies strict but noise‑tolerant matching rules to decide if the citation is real. If the judge rejects, a fallback scholar agent performs high‑precision crawling of scholarly databases before a final judgment. The system is orchestrated by a planning model that executes a standardized operating procedure, with no model fine‑tuning required.

## Key Results
- F1 score: 0.968 on generated test set (6,475 real, 2,967 fake citations).  
- F1 score: 0.903 on real‑world test set, with perfect recall (1.000).  
- Ablation studies confirm each pipeline component is essential; removing any key agent degrades performance substantially.  
- The framework runs with low latency (2.3 seconds per 10 citations) and incurs no monetary cost beyond API usage.

## Why This Works (Mechanism)

**Decomposition into Specialized Agents**  
The system breaks citation verification into a pipeline of five specialized agents (Extractor, Retriever, Matcher, Reasoner, Judge) coordinated by a planning SOP. This separation prevents a single model from handling unstructured parsing, noisy retrieval, and nuanced judgment simultaneously, reducing error propagation. Evidence: Section 4.2 details the agents; Table 5 ablation shows F1 drops >0.1 when any agent is removed. Break condition: If an agent deviates from its constrained role (e.g., Extractor paraphrases titles) or the SOP allows stage skipping, verifiability collapses.

**Dual‑Path Retrieval Cascade**  
A two‑tier retrieval strategy first uses a fast, broad web search (with deep crawling) to gather evidence, falling back only when necessary to a high‑precision scholar crawler. This balances efficiency with recall, as most citation mismatches are resolved via general web evidence, while resilient hallucinations require authoritative database verification. Evidence: Section 4.2 and Table 5 – removing web increases latency 8×; removing scholar drops recall from 1.000 to 0.684 on real‑world data. Break condition: Web misses a valid source and the scholar agent is not invoked due to a false positive from the judge, leading to misclassification.

**Rule‑Constrained Judge Agent**  
Instead of pure string matching or a black‑box LLM verdict, the Judge receives extracted metadata and retrieved snippets and applies explicit matching rules (ignore case/punctuation, allow venue abbreviations). This combines LLM contextual understanding with deterministic guardrails to tolerate formatting noise while rejecting substantive mismatches. Evidence: Appendix D provides the full prompt; Table 5 shows that replacing the Judge with strict string matching cuts precision from 0.861 to 0.225. Break condition: If the Judge’s rule interpretation is too permissive or the LLM disregards the rules, false positives/negatives rise.

## Foundational Learning

- **Concept**: Multi‑agent orchestration with SOPs  
  - *Why needed*: The verification task requires sequential, conditional stages that must be fault‑tolerant and resource‑aware. An LLM acting as a planner routes tasks, avoiding monolithic reasoning that could skip steps.  
  - *Quick check*: What is the difference between the Planning Agent’s role and the Judge Agent’s role, and why can’t they be the same LLM call?

- **Concept**: Evidence retrieval vs. database lookup  
  - *Why needed*: Citations from PDFs are often noisy or incomplete; structured bibliographic APIs (e.g., Crossref) fail on malformed strings. Web crawling provides “in‑the‑wild” evidence (author homepages, PDF footers) that mirrors real‑world usage.  
  - *Quick check*: Why might a valid paper be absent from a bibliographic database but present on an institutional webpage?

- **Concept**: Strict consistency criterion vs. NLI‑style support  
  - *Why needed*: The goal is verifying bibliographic existence and metadata alignment, not whether the citation supports a claim. This requires exact or near‑exact field matching under defined rules, not natural language inference.  
  - *Quick check*: If a citation’s title has one word changed but the linked paper is real, should this be flagged? Based on the paper’s taxonomy, when is this a hallucination vs. a formatting error?

## Architecture Onboarding

**Component Map**  
PDF manuscript → Extractor (A_ext) → Memory Agent (A_mem) → [cache miss] → Web Search Agent (A_web) → Judge Agent (A_jud) → [reject] → Scholar Agent (A_sch) → Judge Agent again → Output verdict. The Planning/Orchestrator (LLM controller) executes the SOP and manages thread pooling.

**Critical Path**  
1. PDF → A_ext extracts raw citation strings into metadata JSON.  
2. For each citation: A_mem checks memory (similarity τ=0.92); if match, label Real.  
3. If cache miss: A_web retrieves evidence, then A_jud compares metadata to evidence. If match, label Real and update memory.  
4. If A_jud rejects: A_sch fetches canonical record, then A_jud re‑evaluates.  
5. Final verdict (Real/Fake) with provenance is recorded.

**Design Tradeoffs**  
- *Speed vs. Coverage*: Web search is fast but may miss; scholar is accurate but rate‑limited. The cascade optimizes average latency.  
- *Strictness vs. Noise Tolerance*: Judge rules must balance false positives (over‑penalizing formatting noise) and false negatives (missing subtle hallucinations). Venue/year allowances are key levers.  
- *Local vs. Cloud*: Using local Qwen3‑VL‑235B for planning/extraction avoids API costs but requires GPU infrastructure; web/scholar calls incur latency/rate‑limit risks.

**Failure Signatures**  
- High false positives: Judge rules too strict or Extractor mis‑parses metadata (e.g., splitting names).  
- High false negatives: Memory cache poisoning, Web Search ranking fails to surface correct source in top 5, or Scholar Agent blocked by paywalls/robots.txt.  
- Bottleneck: Scholar Agent invoked for >20% of citations → latency spikes (as seen in ablation without Web Search).

**First Three Experiments**  
1. *Unit test Extractor*: Feed 100 known BibTeX strings; verify JSON output preserves exact metadata without semantic alteration. Target 0% errors.  
2. *Memory recall rate test*: Pre‑populate Memory Pool with 10k verified citations; measure % of re‑verified citations that hit fast‑path. Target >80% for papers with overlapping references.  
3. *Judge rule stress test*: Generate citation pairs with known benign variations (e.g., “ICML 2024” vs “International Conference on Machine Learning 2024”); ensure Judge outputs `match=true` for ≥95% of benign cases.

## Open Questions the Paper Calls Out

1. **Scalable Benchmark Construction**: How can the benchmark be scaled to include a larger volume of real‑world hallucinated citations without expensive manual verification? The current human‑in‑the‑loop labeling is labor‑intensive.  
2. **Tolerance Threshold Learning**: To what extent does the strict character‑level matching create false negatives for legitimate formatting variations, and can a calibrated, field‑specific tolerance be learned? The current Judge agent compensates opaquely.  
3. **Adversarial Robustness**: How robust is the pipeline to adversarial hallucinations designed to evade the staged verification (e.g., fake citations indexed by web but not scholar)? The fixed perturbation taxonomy may not capture such attacks.  
4. **Generalization to Faithfulness**: Does the framework generalize beyond existence checking to assessing semantic support (i.e., whether the citation actually supports the claim)? The current benchmark focuses on authenticity, not justification.  
5. **Long‑term Operational Costs**: What are the costs and maintenance requirements of deploying the Scholar Agent at scale, given scholarly sites’ anti‑scraping measures? The “zero monetary cost” claim may hide engineering overhead.

## Limitations
- Dataset accessibility: The full benchmark lacks a stable download link, relying on a web app, which may hinder independent replication.  
- Scholar Agent reproducibility: Implementation details for the Playwright crawler, query formulation, and rate‑limit handling are underspecified, making recall guarantees fragile against anti‑scraping defenses.  
- Memory Agent initialization: The initial state of the knowledge graph (empty vs. pre‑seeded) is unclear, affecting early performance in dynamic deployments.
