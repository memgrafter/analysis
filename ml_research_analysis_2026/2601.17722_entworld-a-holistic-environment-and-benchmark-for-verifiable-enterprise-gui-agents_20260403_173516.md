# EntWorld: A Holistic Environment and Benchmark for Verifiable Enterprise GUI Agents

## Quick Facts
- **arXiv ID:** 2601.17722
- **Source URL:** https://arxiv.org/abs/2601.17722
- **Reference Count:** 35
- **Primary Result:** EntWorld introduces a benchmark where state-of-the-art models like GPT-4.1 achieve only 47.61% success on complex enterprise GUI tasks, far below human performance (85%), revealing a significant capability gap.

## Executive Summary
EntWorld addresses the critical lack of rigorous benchmarks for enterprise GUI agents, which must navigate dense interfaces, complex business logic, and long-horizon, state-consistent workflows. It provides 1,756 tasks across six real-world enterprise systems (CRM, ITSM, ERP) using a novel schema-grounded pipeline that automatically generates tasks from database schemas and employs SQL-based deterministic verification for unambiguous evaluation. Experiments demonstrate that even the most advanced generalist models struggle, with the best open-weight model (EntAgent-RL) reaching only 56.89% success, underscoring the need for specialized enterprise agents.

## Method Summary
EntWorld constructs its benchmark via an automated, schema-grounded pipeline. First, it parses an enterprise application's database schema and infers table relationships using semantic analysis and SQL probes. This forms abstract workflows that encapsulate business logic. Task templates—comprising a natural language intent and a ground-truth SQL verification query—are synthesized from these workflows and instantiated with synthetic or real data. Each task undergoes validation by executing its SQL query within a transaction (with rollback for non-query tasks) to ensure correctness. Final tasks are packaged in a standard format with reset tags, enabling reproducible evaluation in a Dockerized environment where agents interact via accessible UI elements and screenshots.

## Key Results
- State-of-the-art generalist models (GPT-4.1, Claude) achieve <48% success, while humans reach 85%.
- The best open-weight model (EntAgent-RL) attains 56.89%, still leaving a substantial gap.
- Performance degrades sharply with task horizon: GPT-4.1 drops from 34.0% on short tasks (<5 steps) to 2.7% on long tasks (>15 steps).
- Combining screenshot and accessibility tree (A11y) inputs yields the best results (53.7% for GPT-4.1); screenshot-only input performs poorly (10.7%).

## Why This Works (Mechanism)

### Schema-Grounded Task Generation
The system reverse-engineers business logic directly from database schemas, enabling scalable benchmark construction without manual annotation or sensitive user data. By parsing schemas, inferring relationships (via constraints and semantic similarity), and validating with SQL probes, it generates valid, long-horizon workflows that mirror real enterprise processes. This approach assumes schemas faithfully encode business logic; invalid tasks may arise from poor normalization or sparse seed data.

### SQL-Based Deterministic Verification
Success is defined by exact database state transitions, verified by executing ground-truth SQL queries. Wrapping verification in transactions (with rollback for modifications) provides a gold standard, eliminating ambiguity from visual matching or LLM judges. This mechanism assumes the database is accessible and that correctness is primarily a state-change problem, potentially overlooking UI-level or external side effects.

### The Enterprise Gap
Current generalist VLMs fail due to enterprise GUIs' high-density element count and long-horizon state dependencies. Agents must ground actions in cluttered interfaces and maintain consistency across many steps, stressing capabilities beyond typical web/mobile tasks. Evidence shows sharp performance drops for tasks exceeding 15 steps and significant degradation when relying solely on screenshots in legacy systems with poor accessibility metadata.

## Foundational Learning
- **Enterprise System Architecture:** Understanding CRM, ERP, and ITSM distinctions at the data level is crucial, as their schemas generate domain-specific workflows and UI structures.
- **GUI Agent Interaction Loop:** Agents iteratively observe (screenshot + A11y tree) and act (click, type) within an environment; grounding actions to correct elements from the A11y tree is a core challenge.
- **Deterministic Verification via SQL:** Evaluation depends on executing SQL queries against a known database state; transactions and rollback ensure safe, repeatable tests for state-modifying operations.
- **Schema Reverse-Engineering:** Business logic is derived by analyzing database schemas (tables, keys, constraints) to infer valid sequences of data operations that correspond to UI workflows.

## Architecture Onboarding
- **Component map:** DatabaseAdapter -> HydraUniversalWorkflowDiscoverer -> TaskFactory -> Environment (Dockerized App) -> Evaluator. Baseline agents (GPT-4.1, EntAgent) interact with the Environment.
- **Critical path:** 1) Load app schema. 2) Discover/abstract workflows & verify relations. 3) Synthesize & instantiate task templates with data. 4) Validate via transactional SQL execution. 5) Format tasks with reset tags. 6) Evaluate agent actions, then run ground-truth SQL.
- **Design tradeoffs:** Synthetic (Faker) vs. real data (privacy/scale vs. authenticity); SQL verification (precise state check) vs. visual (captures UI aesthetics); task horizon (realism vs. lower success rates).
- **Failure signatures:** High `none` action rates; SQL verification failures during generation; steep performance decline for >15-step tasks; screenshot-only underperformance vs. combined input.
- **First 3 experiments:** 1) Generate tasks for EspoCRM and confirm all pass SQL validation. 2) Evaluate Qwen2.5-VL-32B-Instruct on a 100-task subset to reproduce ~24% success. 3) Ablate input modalities (screenshot-only, A11y-only, combined) to confirm combined input superiority.

## Open Questions the Paper Calls Out

### Extending SQL Verification to Write Operations
How can deterministic verification be extended to evaluate INSERT/UPDATE/DELETE operations and external side effects (e.g., email notifications), given current tasks are exclusively read-only information retrieval?

### Mitigating Error Accumulation in Long-Horizon Tasks
Which architectural mechanism—explicit state tracking, sub-goal decomposition, or episodic memory—most effectively reduces error propagation in enterprise workflows exceeding 15 steps?

### Improving Visual Grounding for High-Density Legacy UIs
Why do multimodal agents fail dramatically with screenshot-only input on enterprise UIs, and how can visual grounding be improved for dense, non-standard interfaces with poor accessibility metadata?

### Generalizing Across Enterprise Domains
What drives the large performance variation across systems (e.g., 67% vs. 36%), and how can agents achieve vertical generalization between CRM, ITSM, and ERP domains?

## Limitations
- Schema dependency on well-normalized databases with explicit foreign keys; poor design risks invalid tasks.
- Use of synthetic data may lack real-world correlations, affecting task authenticity.
- Evaluation scope limited to database state changes; UI visual correctness and external side effects are not assessed.
- Repository specifics (CLI, exact SQL scripts) are not detailed, hindering immediate reproduction.

## Next Checks
1. **Schema robustness test:** Deliberately degrade schemas (remove foreign keys, denormalize) and measure generated task failure rates during SQL verification.
2. **Human‑verification correlation:** For a task subset, compare SQL-based success with human judgments on holistic completion (including UI cues) to assess evaluation sufficiency.
3. **Synthetic vs. real data impact:** Instantiate tasks with both Faker and available real data; compare agent performance to quantify authenticity effects.
