# AI-for-Science Low-code Platform with Bayesian Adversarial Multi-Agent Framework

## Quick Facts
- **arXiv ID:** 2603.03233  
- **Source URL:** https://arxiv.org/abs/2603.03233  
- **Reference count:** 40  
- **Primary result:** Raises SciCode sub-problem resolution by 87% relative (13.2%→24.7%) for a 1.7B model; a 14B model matches a 235B model; achieves 90.2% (no expert knowledge) and 87.3% (with knowledge) valid execution on ScienceAgentBench.

## Executive Summary
This paper introduces a low-code platform for AI‑for‑Science tasks that addresses the unreliability of LLM‑generated code. The system employs a Bayesian adversarial multi‑agent framework with three agents: Task Manager (challenger), Code Generator (solver), and Evaluator. These agents iteratively co‑evolve test cases and code, using Bayesian updates to refine prompt distributions based on functional correctness and structural metrics. The approach aims to reduce the need for manual prompt engineering and enable non‑coding scientists to produce robust scientific code.

On the SciCode benchmark, the framework improves the sub‑problem resolution rate of a 1.7 B Qwen3 model from 13.2% to 24.7% (87% relative gain) and allows a 14 B model to match the performance of a 235 B model. On the ScienceAgentBench (Earth Science), it sets a new state‑of‑the‑art with valid execution rates of 90.2% without expert knowledge and 87.3% with knowledge. Performance improves monotonically over iterations, and the platform dramatically reduces sensitivity to prompt quality, allowing non‑coders to outperform expert‑prompted baselines.

## Method Summary
The framework orchestrates a three‑agent loop. The **Task Manager** decomposes the user’s scientific task, produces a plan, and maintains a pool of test cases. The **Code Generator** (an LLM) receives a prompt composed of selected test cases and sample code, and emits a batch of candidate solutions. The **Evaluator** runs these solutions, computes test‑case scores \(S1\), code scores \(S2\), and an aggregated prompt score \(S3\). A **Bayesian updater** maintains a posterior distribution over (test case, sample code) pairs and samples the next prompt; a Gaussian Process surrogate predicts \(S2\) from code embeddings to guide candidate selection via an Upper Confidence Bound acquisition. After each batch, the Task Manager refines test cases based on \(S1\), and the process repeats until a solution passes all tests or a maximum iteration count is reached. Domain knowledge (e.g., reference code) can be injected to seed the sample pool.

## Key Results
- **SciCode:** 1.7B model resolution gains 87% relative (13.2% → 24.7%); 14B model matches 235B model performance.  
- **ScienceAgentBench:** New SOTA valid execution rates: 90.2% (no expert knowledge) and 87.3% (with knowledge).  
- **Robustness:** Performance improves monotonically across multiple iterations; platform drastically reduces sensitivity to prompt quality, enabling non‑coding scientists to surpass expert‑prompted baselines.

## Why This Works (Mechanism)

### Mechanism 1: Adversarial Co‑evolution of Test Cases and Code
**Claim:** The framework improves code robustness by having the Task Manager iteratively generate more challenging test cases while the Solution Generator iteratively produces code that passes them.  
**Mechanism:** TM acts as Challenger; after each batch of candidate codes, the Evaluator provides pass/fail per test case. TM updates test case scores (\(S1\)) and selects harder tests for the next prompt; SG implicitly adapts to the challenge.  
**Core assumption:** Test cases can be meaningfully ranked by discriminative power (\(S1\)) and exposing SG to progressively harder tests yields monotonic improvement.  
**Evidence anchors:** [abstract] “Three agents — Task Manager (challenger), Code Generator (solver), and Evaluator — iteratively co‑evolve test cases and code via an adversarial loop”; [Section 2.5] “Adversarial interaction: The TM agent’s role evolves to that of a Challenger… selects test cases… optimally challenging for the SG’s current learned capabilities”; corpus signals are weak.  
**Break condition:** If SG fails to produce any code that passes any test after several iterations, \(S1\) updates become uninformative and the loop may stagnate; framework stops at user‑defined max iterations.

### Mechanism 2: Bayesian Prompt Distribution Updates
**Claim:** Bayesian updating of prompt component distributions efficiently identifies high‑quality test‑case and sample‑code combinations without exhaustive search.  
**Mechanism:** Posterior \(p(\text{Prompt}|S_3) \propto p(S_3|\text{Prompt}) \cdot p(\text{Prompt})\); \(p(S_3|\text{Prompt})\) approximated by \(\exp(\text{historical expected } S_3)\). Scores \(S1\), \(S2\), \(S3\) guide which test cases and sample codes survive into the next prompt.  
**Core assumption:** Prompt score \(S3\) correlates with downstream code quality; the likelihood model captures this relationship.  
**Evidence anchors:** [abstract] “Bayesian updates to prompt distributions based on functional correctness and structural metrics.”; [Section 2.5] “Bayesian prompt updates: … governed by a Bayesian update rule (5).”; corpus lacks direct evidence.  
**Break condition:** Posterior collapse due to over‑confident priors could eliminate diversity; mitigated by uniform prior and minimum pool size.

### Mechanism 3: Low‑code Prompt Translation for Non‑Experts
**Claim:** TM’s planning and test‑case auto‑generation lower the expertise barrier, letting non‑programmers achieve expert‑level results without manual prompt engineering.  
**Mechanism:** TM decomposes the task into components, produces a natural language plan, and creates initial test cases and sample code. The user only provides a high‑level description and optional feedback on the plan; TM handles prompt engineering.  
**Core assumption:** TM can reliably interpret domain tasks and generate scientifically valid test cases.  
**Evidence anchors:** [abstract] “dramatically reduces sensitivity to prompt quality, allowing non‑coding scientists to outperform expert‑prompted baselines.”; [Section D] Case studies show non‑coders using LCP beat baseline with expert prompts; corpus signals weak.  
**Break condition:** If TM misinterprets domain nuances, generated tests/code may violate scientific constraints, causing failure even with iterative refinement.

## Foundational Learning

### Bayesian Optimization for Black‑box Evaluation
**Why needed:** Evaluating each generated candidate by full execution is costly; a Gaussian Process (GP) surrogate predicts performance from code embeddings, enabling efficient selection.  
**Quick check:** What acquisition function balances exploitation and exploration, and what is its κ parameter for?

### Adversarial Test Case Generation
**Why needed:** Scientific tasks often have under‑specified constraints; dynamically generated tests adapt to expose subtle bugs that static tests miss.  
**Quick check:** How does the test case score \(S1\) incorporate both difficulty and discriminative power across multiple codes?

### Multi‑agent Score Aggregation (S1, S2, S3)
**Why needed:** Binary pass/fail discards useful signal; weighted scores preserve partial progress and feed Bayesian updates.  
**Quick check:** Why does code score \(S2\) normalize by the sum of \(S1\) values of the tests it passed?

## Architecture Onboarding

### Component Map
User -> Task Manager (plan) -> User approval -> Bayesian Updater (sample prompt) -> Solution Generator (N codes) -> Evaluator -> Scores S1,S2,S3 -> Bayesian update (posterior) & Task Manager (test case refinement) -> loop back until success or max iterations.

### Critical Path
1. Input user task + optional domain knowledge.  
2. Task Manager generates plan → user approval (loop if feedback).  
3. Initialize test case and sample code pools.  
4. Iteration loop:  
   a. Sample prompt from Bayesian posterior.  
   b. Solution Generator produces N candidate codes.  
   c. Evaluator executes codes → compute \(S1\), \(S2\), \(S3\).  
   d. Bayesian update of posteriors.  
   e. Task Manager refines test cases using \(S1\).  
   f. If any code passes all tests, return best; else repeat until max iterations.

### Design Tradeoffs
- **Iterations vs token cost:** Gains diminish after ~3–5 rounds; default max=3.  
- **GP surrogate vs fidelity:** Surrogate avoids executing all candidates but may mis‑rank; top‑k by acquisition (UCB) still executed.  
- **Pool diversity vs relevance:** Larger pool maintains exploration but may dilute \(S1\) signals.  
- **All‑LLM orchestration vs robustness:** Performance depends on base LLM quality; Bayesian non‑LLM update mitigates single‑point failure.

### Failure Signatures
- \(S1\) values remain uniform → TM failing to differentiate test difficulty.  
- Posterior collapses to a single prompt combination → loss of diversity, possible early convergence.  
- High runtime error rate in SG outputs → prompt or code generation misunderstanding.  
- User feedback contradicts earlier plan → TM oscillation or reinterpretation.

## Open Questions the Paper Calls Out

### Open Question 1
**Question:** How can the Bayesian updates be extended to handle multi‑modal inputs like equations and diagrams?  
**Basis in paper:** [explicit] Authors state future work will extend Bayesian updates to handle multi‑modal inputs such as equations and diagrams.  
**Why unresolved:** Current system processes only text; multi‑modal scientific tasks require new representations and update rules.  
**What evidence would resolve it:** Implement an extension that embeds equations/diagrams, and show improved results on a multi‑modal benchmark.

### Open Question 2
**Question:** How can the framework enforce implicit physical laws during code generation?  
**Basis in paper:** [explicit] The paper says it "struggles to enforce implicit physical laws, which may require future integration with symbolic verifiers."  
**Why unresolved:** Violations of physical constraints limit trust in scientific outputs.  
**What evidence would resolve it:** Integrate a symbolic verifier and demonstrate reduced constraint violations on physics benchmarks.

### Open Question 3
**Question:** Can token consumption be reduced without sacrificing performance?  
**Basis in paper:** [explicit] The iterative process "consumes more tokens than one‑shot/zero‑shot prompting."  
**Why unresolved:** High token costs hinder scalability.  
**What evidence would resolve it:** Propose and evaluate a more efficient refinement protocol (e.g., adaptive stopping) that uses fewer tokens while maintaining success rates.

### Open Question 4
**Question:** How does performance variability due to training dynamics affect the Bayesian update stability?  
**Basis in paper:** [explicit] The conclusion notes that "performance variability due to training dynamics and data poses an additional challenge to the update mechanism."  
**Why unresolved:** Fluctuations may cause suboptimal prompt selection and slow convergence.  
**What evidence would resolve it:** Analyze convergence across seeds and incorporate uncertainty estimates to stabilize updates, showing faster convergence on benchmarks.

## Limitations
- **Prompt engineering specifics** are undisclosed, hindering exact replication (system prompts, few‑shot examples).  
- **Bayesian/GP details** (kernel choice, acquisition parameters, AST embedding pipeline) lack full specification, affecting surrogate reliability.  
- **Test‑case generation mechanics** (ensuring scientific validity and executability) remain opaque, potentially causing domain‑specific failures.

## Confidence
- **Adversarial co‑evolution:** Medium – Logical mechanism and monotonic improvement shown, but break conditions and \(S1\) design need empirical stress‑testing.  
- **Bayesian prompt updates:** Low – Core to efficiency claims, but likelihood assumptions and posterior stability lack supporting ablations or sensitivity analysis.  
- **Low‑code accessibility:** Medium – Case studies support non‑expert usability, but TM’s domain‑interpretation robustness on unseen scientific domains is unverified.

## Next Checks
1. **Prompt Template Audit:** Request exact prompts used for TM, SG, and Evaluator; run a sensitivity analysis varying minor phrasing to quantify output stability.  
2. **GP Surrogate Validation:** On held‑out code samples, measure Pearson correlation between GP‑predicted \(S2\) and actual \(S2\); tune kernel/hyperparameters if correlation <0.7.  
3. **Test‑Case Diversity Tracking:** Over 10 benchmark tasks, monitor pairwise embedding similarity (cosine) of TM‑generated tests per iteration; flag convergence (average similarity >0.85) as a failure mode.
