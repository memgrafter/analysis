# Textual Explanations and Their Evaluations for Reinforcement Learning Policy
## Quick Facts
- arXiv ID: 2601.02514
- Source URL: https://arxiv.org/abs/2601.02514
- Reference count: 35
- Key outcome: The paper addresses the challenge of generating correct and evaluable textual explanations for reinforcement learning policies. The core method uses an LLM to interpret user queries, retrieves relevant replay data, and applies a clustering-based summarizer with Gini-derived predicates to extract frequent state-action conditions as text. ## Executive Summary
This paper tackles the challenge of generating correct and evaluable textual explanations for reinforcement learning policies. The authors propose a framework that uses an LLM to interpret user queries into SQL, retrieves relevant replay data, and applies a clustering-based summarizer with Gini-derived categorical predicates to extract frequent state-action conditions as text. These explanations are then converted into weighted IF-THEN rules, which are systematically evaluated for coverage, fidelity (accuracy/recall/F1), and performance if deployed. The framework is demonstrated on multiple RL environments and a telecom use case, showing that the proposed method (CBS) reduces approximated states and duplicates compared to the APE baseline, with Gini-based predicates improving fidelity. Refinement techniques further improve performance, and rule-based agents achieve near-original black-box performance, demonstrating a viable trade-off for transparent deployment.

## Method Summary
The paper proposes a method for generating textual explanations for RL policies using a clustering-based summarizer (CBS) with Gini-derived categorical predicates. The process begins with an LLM interpreting user queries as SQL to retrieve relevant replay data. States are discretized into categorical predicates using thresholds derived from a Gini decision tree. K-means clustering groups similar discretized states, and for each cluster, only the most frequent unique discrete state vectors above a threshold are retained as conditions. These conditions are translated into textual "AND/OR" statements. The explanations are then converted into a formal set of weighted IF-THEN rules, which are evaluated for coverage, fidelity, and performance metrics. Refinement techniques are applied to further improve fidelity by minimizing duplicates or maximizing F1 score.

## Key Results
- CBS method reduces approximated states and duplicates compared to APE baseline.
- Gini-based predicates improve fidelity (accuracy, recall, F1) over median-based thresholds.
- Refinement techniques further reduce duplicates and increase F1 scores.
- In telecom use case, rule-based agents achieve near-original black-box performance (e.g., EAR within 10% loss).

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Using a Large Language Model (LLM) as a natural language interface to convert user queries into structured SQL queries enables flexible, template-free interaction with the explainer system.
- **Mechanism:** The LLM is prompted with few-shot examples to interpret a user's free-text question (e.g., "When will you uptilt?") and generate a precise SQL query against a database storing replay data (states, actions, rewards). This decouples the interactive front-end from the data aggregation back-end.
- **Core assumption:** An LLM can reliably parse diverse natural language questions about policy behavior into syntactically correct and semantically appropriate SQL queries for a known database schema.
- **Evidence anchors:**
  - [abstract] "...uses an LLM to interpret user queries, retrieves relevant replay data..."
  - [section 3.1] "The LLM is used to interpret questions about the RL policy to convert them into a Structured Query Language (SQL) query..."
  - [corpus] Weak direct support; neighbor "TalkToAgent" uses LLMs for XRL conversation but not specifically for SQL generation.
- **Break condition:** If the LLM generates malformed or semantically incorrect SQL queries that fail to retrieve the intended subset of states, the summarization step operates on irrelevant or empty data, leading to meaningless explanations.

### Mechanism 2
- **Claim:** A clustering-based summarizer (CBS) using Gini-derived categorical predicates identifies a concise set of frequent state-action conditions, avoiding the combinatorial explosion and duplicate explanations of prior methods like APE.
- **Mechanism:** Continuous state features are discretized into multiple categorical levels using thresholds derived from a decision tree trained with a Gini criterion (Algorithm 1). K-means clustering groups similar discretized states. For each cluster, only the most frequent unique discrete state vectors (above an inclusion threshold θ) are retained as conditions. These conditions are then translated into textual "AND/OR" statements via a template.
- **Core assumption:** The centroids of frequent clusters of discretized states represent the common, policy-relevant conditions. Categorical predicates (vs. binary) provide finer granularity without linearly increasing condition count, and clustering suppresses infrequent/outlier instances.
- **Evidence anchors:**
  - [abstract] "...clustering-based summarizer with Gini-derived predicates to extract frequent state-action conditions as text."
  - [section 3.2] Details Algorithm 1 (Gini-based limit generation), Equation 1 (categorical predicate formulation), and Algorithm 2 (CBS).
  - [corpus] No direct evidence; neighboring works (e.g., SymbXRL, TREX) use symbolic or trajectory-based methods, not CBS.
- **Break condition:** If the state distribution is highly multi-modal or the clustering (K-means) fails to find meaningful groupings (e.g., due to poor initialization or high dimensionality after discretization), the extracted conditions may be unrepresentative, fragmented, or fail to capture true policy behavior.

### Mechanism 3
- **Claim:** Converting textual explanations into a formal set of weighted IF-THEN rules enables their systematic, quantitative evaluation (fidelity, coverage) and potential deployment as a transparent policy surrogate.
- **Mechanism:** For each action, conditions from the explanation are paired with an occurrence weight (e.g., w2 = N_ca / N_a, the proportion of times that action is taken under that condition). A rule is "IF condition THEN action with weight". For a new state, the action with the highest summed weight from matching conditions is selected (Equation 2). If no condition matches, an approximate nearest condition is found via Euclidean distance (Algorithm 4). These rules are then evaluated against replay data for fidelity (accuracy, recall, F1 vs. original actions) and performance (cumulative reward) if deployed.
- **Core assumption:** The weighted rule set derived from historical replay data is a sufficiently accurate and complete approximation of the original black-box policy's input-output mapping for the states of interest.
- **Evidence anchors:**
  - [abstract] "These explanations are converted into transparent rules for systematic evaluation via coverage, fidelity... and performance metrics when deployed."
  - [section 3.3] Details Algorithms 3 and 4 and the weighting functions (w1-w4).
  - [corpus] Some support from rule extraction literature (e.g., CGX, FRBES in references) and TREX for multi-objective, but the specific rule conversion from *textual* explanations is novel.
- **Break condition:** If the rule set has low coverage (high E_approx) or the weight function poorly predicts the majority action under a condition (low F1), the surrogate policy will perform significantly worse than the original. The approximation fallback (Algorithm 4) may also select incorrect actions for novel states.

## Foundational Learning
- **Concept: Reinforcement Learning Policy as a Function**
  - **Why needed here:** The entire framework explains a *trained policy* (π(s) → a). Understanding that the policy is a deterministic or stochastic mapping from state observations to actions is fundamental to interpreting its behavior and evaluating approximation quality.
  - **Quick check question:** If you have a replay buffer of (s, a, r) tuples, what does the sequence of actions 'a' tell you about the underlying policy for the states 's'?

- **Concept: Discretization via Predicate Functions**
  - **Why needed here:** The summarizer operates on symbolic, human-readable conditions (e.g., "SINR is Low"). Converting continuous state features into categorical predicates is the first step in generating textual explanations and rules. The choice of thresholds (Gini vs. median) directly impacts explanation quality.
  - **Quick check question:** How would you design a predicate function for a continuous feature like "interference" to create two levels ("Low", "High")? What is a pitfall of using the median as a threshold?

- **Concept: Fidelity as a Proxy for Explanation Correctness**
  - **Why needed here:** Without ground-truth "correct" explanations, the paper evaluates explanations by how well the extracted rules *mimic* the original policy's actions on held-out replay data. Fidelity metrics (accuracy, recall, F1) measure this mimicry.
  - **Quick check question:** If a rule set has 90% fidelity (accuracy) on replay data, does that guarantee the textual explanation is "true"? What could a high-fidelity rule set still be missing?

## Architecture Onboarding
- **Component map:**
  1. **Query Interpreter:** LLM (e.g., DeepSeek-R1-Distill-Llama-70B) + prompt template. Input: User question. Output: SQL query string.
  2. **Data Retriever:** SQLite database executor. Input: SQL query. Output: Filtered table of (state, action) instances.
  3. **Summarizer (CBS):** Predicate generator (Algorithm 1) + discretizer + K-means clusterer + condition selector (Algorithm 2). Input: Filtered states, predicate functions. Output: List of textual conditions per action.
  4. **Rule Extractor:** Weight calculator + rule formulator (Algorithm 3) + state approximator (Algorithm 4). Input: Conditions, full replay data. Output: Weighted IF-THEN rule set.
  5. **Evaluator:** Metrics calculator. Input: Rule set, replay data, environment. Output: Scores for E_app, E_len, E_dup, E_F1, E_CR, E_TS, E_AR.

- **Critical path:** The core explanatory flow is linear: `User Query → LLM → SQL → DB → CBS → Rules → Metrics`. The *refinement* path (Algorithms 5 & 6) is a feedback loop that iterates on predicate thresholds based on duplicate count (E_dup) or F1 score.

- **Design tradeoffs:**
  - **LLM vs. Template for Text Gen:** Paper uses a simple template for condition-to-text (efficient, reliable) after using LLM only for query parsing. Tradeoff: Lost narrative flexibility but avoided LLM's numerical processing flaws.
  - **Explanation Length vs. Fidelity/Coverage:** Lower inclusion threshold (θ) includes more cluster instances, increasing coverage (lower E_app) but may add noise, potentially lowering fidelity. More predicate categories (ncat) increase explanation length (E_len) but can reduce duplicates (E_dup) and improve fidelity by offering finer distinctions.
  - **Computational Complexity:** APE's Quine-McCluskey algorithm scales exponentially with predicate count. CBS's K-means scales linearly with data size and predicates (O(|S|*|P|*k^2*i)), making it feasible for larger predicate sets.

- **Failure signatures:**
  - **High E_dup:** Conflicting conditions appear for multiple actions. Indicates predicates are not discriminative enough or clustering produced ambiguous groups.
  - **High E_app:** Large fraction of states not covered by any rule. Indicates θ is too high (too few conditions kept) or CBS failed to find frequent patterns for some state regions.
  - **Low E_F1 & Degraded E_CR:** Rule set does not mimic the policy well. Suggests poor predicate thresholds, an inappropriate weighting function (w), or that the policy's logic is not easily captured by the proposed condition-action form (e.g., highly temporal dependencies).
  - **LLM SQL Failure:** Malformed or empty query results. Would cause CBS to receive no data and generate no explanation.

- **First 3 experiments:**
  1. **APE vs. CBS Baseline (Section 4.3):** Run both methods on CartPole, LunarLander, MountainCar, and RET with binary predicates. Compare key metrics: E_app (coverage), E_len, E_dup, E_acc/E_rec/E_F1 (fidelity), E_CR/E_AR (performance). *Expected outcome:* CBS should produce explanations for all environments (APE failed on CartPole/MountainCar), with generally lower E_app and comparable or better performance degradation.
  2. **Predicate Initiator Comparison (Section 4.4):** Using CBS, compare Gini-derived (Algorithm 1) vs. median thresholds. Vary only the initiator, keep other parameters (θ=0.7, w2). Aggregate fidelity scores (E_F1) and E_app. *Expected outcome:* Gini should yield higher fidelity and lower E_app by finding more discriminative splits.
  3. **Refinement Technique Impact (Section 4.6):** On a selected configuration (e.g., ncat=6 for all envs, ncat=5 for MountainCar), apply "minimize duplicate" (Algorithm 5) and "maximize F1" (Algorithm 6) refinements. Measure changes in E_dup, E_len, E_F1, and E_CR. *Expected outcome:* "min-duplicate" should reduce E_dup and possibly E_len; "max-F1" should increase E_F1 and potentially E_CR, but may increase E_len.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: How can the framework incorporate non-tabular states like images via concept embeddings?
- Basis in paper: [explicit] Conclusion mentions using concept-embedding for visual inputs.
- Why unresolved: Current predicates require tabular features; mapping from raw inputs is undefined.
- What evidence would resolve it: A concept extractor that outputs predicate features and is validated on vision-based RL environments.

### Open Question 2
- Question: Can the rule-based agent adapt and continue learning after deployment?
- Basis in paper: [explicit] Future work includes investigating adaptability of the transparent agent.
- Why unresolved: Extracted rules are static summaries and cannot adjust to new conditions.
- What evidence would resolve it: Mechanisms for incremental rule updates evaluated in non-stationary environments.

### Open Question 3
- Question: How can contrastive and counterfactual explanations be integrated into this framework?
- Basis in paper: [explicit] Conclusion states that integrating such explanation types requires further investigation.
- Why unresolved: The current summarizer only generates descriptive “when-action” statements, not contrastive or counterfactual forms.
- What evidence would resolve it: Extended summarizer and rule extraction producing those alternatives, with tailored evaluation metrics.

### Open Question 4
- Question: Can the clustering summaries be inverted to detect anomalies in agent behavior?
- Basis in paper: [explicit] Future work mentions finding anomalies by inverting the rules.
- Why unresolved: The framework focuses on frequent patterns; anomalies are rare and may not appear in summaries.
- What evidence would resolve it: Anomaly scores based on rule coverage/confidence and validation on data with injected anomalies.

## Limitations
- The LLM's reliability in generating semantically correct SQL queries for arbitrary user questions is assumed but not empirically tested for robustness or error rates.
- The assumption that textual explanations converted to rules provide true "transparency" for human understanding is not validated through user studies.
- The fidelity evaluation, while quantitative, measures mimicry rather than "ground-truth" correctness of the textual explanations.

## Confidence
- **High Confidence**: The core mechanism of using CBS with Gini-derived predicates to generate frequent, categorical conditions and convert them into weighted rules is well-defined and reproducible based on the algorithms provided. The systematic evaluation framework using coverage, fidelity, and performance metrics is clearly articulated.
- **Medium Confidence**: The reported improvements in fidelity (e.g., Gini vs. median) and reduction in duplicates are supported by the experiments, but the variability across environments and the sensitivity to parameter choices (e.g., θ, ncat) are not fully explored. The claim that the approach is "application-agnostic" is supported by testing on four diverse environments but lacks broader validation.
- **Low Confidence**: The LLM's reliability in generating semantically correct SQL queries for arbitrary user questions is assumed but not empirically tested for robustness or error rates. The assumption that textual explanations converted to rules provide true "transparency" for human understanding is not validated through user studies.

## Next Checks
1. **LLM SQL Robustness Test**: Systematically evaluate the LLM's query generation accuracy across a wide range of user questions (including ambiguous or complex ones) against a test set of ground-truth SQL queries. Measure the percentage of malformed or semantically incorrect queries.
2. **State Distribution Sensitivity Analysis**: For each environment, analyze the state feature distributions before and after discretization. Identify cases where K-means clustering fails to find meaningful groupings (e.g., due to high dimensionality or poor initialization) and assess the impact on the quality of extracted conditions.
3. **Temporal Dependency Impact Study**: Design an experiment using a policy known to have significant temporal dependencies (e.g., a game requiring memory of past states). Evaluate whether the CBS approach can still generate high-fidelity explanations, and if not, identify the specific failure modes (e.g., high E_app, low E_F1).
