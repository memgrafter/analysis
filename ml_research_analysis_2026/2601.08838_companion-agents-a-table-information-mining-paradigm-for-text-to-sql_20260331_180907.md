# Companion Agents: A Table-Information Mining Paradigm for Text-to-SQL

## Quick Facts
- **ArXiv ID:** 2601.08838
- **Source URL:** https://arxiv.org/abs/2601.08838
- **Reference count:** 0
- **Primary result:** Companion Agents recover up to +14.13% execution accuracy on BIRD’s fully missing evidence setting, with especially large gains on challenging queries (+16.71% for DAIL‑SQL).

## Executive Summary
Industrial Text-to-SQL often suffers from missing or erroneous database annotations, whereas existing benchmarks assume complete evidence. This paper introduces Companion Agents (CA), a database‑centric paradigm that proactively mines intrinsic structural, statistical, and semantic knowledge from relational databases offline, caches it, and then uses a Query Routing Agent to selectively activate relevant cached knowledge for online evidence generation. Experiments on the BIRD benchmark under fully missing evidence show that CA significantly improves execution accuracy across multiple baselines (RSL‑SQL, CHESS, DAIL‑SQL), with particularly strong gains on challenging queries. Ablation studies confirm the necessity of the closed‑loop design (schema mining, routing, generation), though some failure modes (e.g., incomplete enum instantiation, structural focus drift) remain.

## Method Summary
CA consists of three modules. The Schema Mining Agent (SMA) runs offline on each database to extract schema structure, statistical profiles (value distributions, enumerations), and semantic tags (field descriptions, synonym mappings), and builds a few‑shot QA library. The Query Routing Agent (QRA) uses an LLM to perform multi‑label classification on an input question (and linked schema) to determine which evidence types (numeric reasoning, domain knowledge, synonym/alias, enumeration) are required. The Evidence Generation Agent (EGA) then constructs natural‑language evidence items by synthesizing the activated types and the query context, grounding them in the SMA’s cached knowledge. The generated evidence is injected into the prompt of an existing Text‑to‑SQL baseline (e.g., DAIL‑SQL) to produce the final SQL. The minimum viable reproduction involves: (1) generating schema‑knowledge files for each BIRD database using SMA; (2) implementing QRA and EGA as described; (3) running the augmented baseline and evaluating execution accuracy. Unknowns that block exact replication include the precise LLM prompts for QRA and EGA and the similarity metric for few‑shot retrieval. Common failure modes are missing concrete enum mappings and evidence that drifts from the structural requirements of the query.

## Key Results
- **Significant accuracy recovery:** On BIRD with fully missing evidence, CA improves execution accuracy by +4.49% (RSL‑SQL), +4.37% (CHESS), and +14.13% (DAIL‑SQL) over the respective baselines.
- **Larger gains on challenging queries:** The improvements on the Challenging subset are +9.65%, +7.58%, and +16.71% respectively.
- **Ablation confirms closed‑loop necessity:** Removing SMA, QRA, or both degrades performance, especially on complex queries; the full CA pipeline yields the best results.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Offline mining and caching of database‑intrinsic knowledge (structural, statistical, semantic) provides a stable, reusable knowledge base that substitutes for missing human annotations.
- **Mechanism:** The Schema Mining Agent (SMA) performs automatic structural parsing (DDL, foreign keys), statistical profiling (value distributions, enumerations), and LLM‑based semantic induction (field descriptions, synonym mappings) on the entire database offline. This creates a structured “schema‑knowledge” file stored per database.
- **Core assumption:** The intrinsic data distributions and structural constraints of a relational database are relatively stable over time, while user queries are dynamic. Mining this stable signal once offline is more cost‑effective and transferable than generating evidence per query from scratch.
- **Evidence anchors:**  
  - [abstract] “proactively mine and consolidate hidden inter‑table relations, value‑domain distributions, statistical regularities, and latent semantic cues before query generation.”  
  - [section] 3.2.1 details the three‑stage SMA process: Schema Extraction, Few‑shot Knowledge Library Building, and Similar‑case matching.  
  - [corpus] Contrasts with SEED (neighbor [11]) which generates evidence per question (“question side”), highlighting CA’s novel database‑side caching locus.

### Mechanism 2
- **Claim:** A learned query router selectively activates only the most relevant subsets of cached knowledge for a specific query, reducing noise and focusing the LLM’s attention.
- **Mechanism:** The Query Routing Agent (QRA) uses an LLM to perform multi‑label classification on the input question (and linked schema), determining which evidence types (numeric reasoning, domain knowledge, synonym/alias, enumeration) are required. It then directs the Evidence Generation Agent to construct evidence only for those activated types.
- **Core assumption:** Different natural language questions have predictable, classifiable evidence requirements. Routing based on question semantics can be highly accurate and prevents overwhelming the LLM prompt with irrelevant cached information.
- **Evidence anchors:**  
  - [abstract] “selectively activate relevant cached knowledge at inference time.”  
  - [section] 3.2.2 explicitly lists the routed evidence types and describes the routing process (e.g., identifying candidate numeric columns, triggering web retrieval as fallback).  
  - [corpus] Other works (e.g., [24] MCS‑SQL using multiple‑choice selection) also address evidence selection, but CA’s routing is uniquely tied to pre‑mined, database‑specific knowledge.

### Mechanism 3
- **Claim:** Constructing evidence from activated, cached knowledge components using an LLM yields context‑aware, database‑grounded proxies that are more reliable than hallucinated or generic explanations.
- **Mechanism:** The Evidence Generation Agent (EGA) takes the routed evidence types and the specific query context to produce natural language evidence items. It generates schema‑consistency hints (join paths), semantic constraints (time/range explanations), and retrieves logical templates from the few‑shot library, all grounded in the SMA’s cached knowledge.
- **Core assumption:** An LLM, when provided with high‑quality, database‑specific source material (cached profiles, few‑shot examples), can synthesize accurate and executable contextual evidence that directly addresses the query’s reasoning gaps.
- **Evidence anchors:**  
  - [abstract] “generate query‑relevant contextual evidence to strengthen reasoning and SQL synthesis.”  
  - [section] 3.2.3 provides concrete examples: “Table customer is linked to order via customer_id…” and “Column year denotes the sales year; records with year > 2020 correspond to 2021 and later.”  
  - [corpus] The combination of cached source + LLM synthesis is CA’s distinctive feature; neighbor papers like [7] CHESS use verification, and [11] SEED generates evidence, but CA uniquely couples them.

## Foundational Learning
### Concept: Database Schema Mining & Profiling
- **Why needed here:** The entire CA paradigm rests on the ability to automatically extract stable, fine‑grained signals (foreign keys, value distributions, semantic tags) from a raw database without human annotations. This is the first and foundational step.
- **Quick check question:** Given a database table and sample rows, how would you algorithmically derive a list of probable enumerated values for a categorical column and a one‑sentence semantic summary for it?

### Concept: Query‑Type to Evidence‑Type Routing
- **Why needed here:** Understanding the mapping from a natural language question’s reasoning requirements to the specific kind of database knowledge needed (e.g., a “ratio” query needs numeric reasoning; “school district” needs synonym/domain knowledge) is essential for efficient knowledge activation.
- **Quick check question:** Classify the query “What was the total sales in Q4 2023 for the Western region?” into the evidence types (from BIRD’s taxonomy) a router should likely activate.

### Concept: In‑Context Learning with Database‑Grounded Examples
- **Why needed here:** CA’s Evidence Generation and the SMA’s few‑shot library rely on the LLM’s ability to generalize from provided (question, SQL skeleton) pairs that are similar to the current query, borrowing logical patterns.
- **Quick check question:** If the few‑shot library contains an example about “computing average salary per department,” how might that template be adapted for a new query about “computing total revenue per product category”?

## Architecture Onboarding
**Component map:**
- Offline Phase (SMA): Raw Database & Schema → SMA → `schema‑knowledge` (semantic tags, alias maps, enum dicts, few‑shot QA library) + sampled data profiles.
- Online Phase: Question (q) + Schema (S) + `schema‑knowledge` → QRA → Set of activated evidence types/triggers → EGA → Natural language evidence items → Final LLM call (prompt with q, S, evidence) → SQL (y).

**Critical path:** The closed loop is: Offline SMA mining → stores `schema‑knowledge` → Online QRA routing on (q) → directs EGA → EGA constructs evidence from `schema‑knowledge` using query context → Final LLM generates SQL. Ablations show removing any link (SMA‑only, QRA‑only) degrades performance, especially on Challenging queries.

**Design tradeoffs:**
- Mining depth vs. Cost: Profiling more rows (n=200) yields richer enums/distributions but increases offline compute/time.
- Routing specificity vs. Overhead: More granular routing labels may improve relevance but require more sophisticated LLM prompting and risk misclassification.
- Evidence verbosity vs. Prompt Limits: Generated evidence must be concise enough to fit within the LLM’s context window alongside the question and schema, yet detailed enough to be actionable.

**Failure signatures:**
1. **Missing enum instantiation:** Evidence identifies a categorical filter but fails to provide exact value‑to‑code mappings needed for a WHERE clause. Results in missing constraints or empty result sets.
2. **Focus drift from structural rules:** Evidence captures secondary semantics but omits explicit structural compositions required by the query (e.g., listing all address fields for a “full communication address”), leading to incomplete SELECT lists or incorrect JOIN/aggregation logic.

## Open Questions the Paper Calls Out
**Open Question 1:**  
*Can database‑intrinsic structural and value distributions be automatically mined to generate substitute evidence that reliably matches the utility of human‑curated evidence, especially for complex multi‑step reasoning?*  
- **Basis:** RQ1 explicitly asks whether substitutable evidence can be constructed from database‑intrinsic information and how it compares to gold evidence.  
- **Why unresolved:** The paper shows CA recovers accuracy but admits gaps remain versus gold evidence, particularly on challenging queries. The boundary of what intrinsic knowledge can substitute for explicit human‑provided rules (e.g., complex domain logic) is not fully characterized.  
- **What would resolve:** A fine‑grained error analysis correlating specific evidence types (e.g., numeric formulas vs. domain rules) with recovery rates, plus experiments probing the limits of data distributions in inferring unseen domain constraints.

**Open Question 2:**  
*Does the proposed closed‑loop agent design (schema mining → query routing → evidence generation) provide synergistic benefits that cannot be achieved by independently optimizing each component, and what is the cost of this complexity?*  
- **Basis:** RQ2 questions whether the multi‑agent closed loop outperforms a single evidence generator or schema‑only enhancement. Ablations show full CA best, but interactions are not deeply analyzed.  
- **Why unresolved:** Ablations indicate all modules contribute, but the precise nature of their interactions (e.g., does routing effectiveness depend on the richness of mined schema‑knowledge?) and the overhead of the full pipeline versus simpler augmentations are not quantified.  
- **What would resolve:** Controlled experiments where each module is replaced with a stronger/weaker variant to measure interaction effects, plus runtime/cost analysis comparing the full CA loop against simplified variants on large‑scale deployments.

**Open Question 3:**  
*Why does CA still fail on certain queries despite mining database‑intrinsic knowledge, and can these failure modes be systematically addressed?*  
- **Basis:** RQ3 directly asks about CA’s prominent limitations and failure modes. The Discussion identifies two: missing enum instantiation and focus drift from structural rules.  
- **Why unresolved:** The two identified error patterns are described anecdotally but not quantified or mitigated. It is unclear how prevalent each is, whether they share root causes (e.g., insufficient semantic grounding in EGA), and if they can be resolved without external knowledge.  
- **What would resolve:** A large‑scale categorization of failure cases with statistics on error mode frequency, plus targeted interventions (e.g., enhanced enum extraction, structure‑aware constraints) evaluated in an ablation to isolate which fixes yield the highest marginal gain.

**Open Question 4:**  
*How does the database‑side caching approach in CA compare conceptually and practically to question‑side evidence generation (e.g., SEED), and what are the trade‑offs in transferability, cost, and adaptability?*  
- **Basis:** The paper positions CA against SEED‑like methods, highlighting a key distinction: CA mines stable database‑side knowledge while SEED generates question‑side evidence. This trade‑off is discussed but not formally compared.  
- **Why unresolved:** No direct comparison with SEED or similar question‑side approaches is provided. The claimed advantages of database‑side caching (stability, transferability) are plausible but not measured against the flexibility of question‑side generation, especially for queries requiring dynamic, non‑database knowledge.  
- **What would resolve:** A head‑to‑head evaluation where CA and a SEED‑style system are applied to the same databases/queries, measuring not only accuracy but also caching/generation costs, reusability across different query loads, and sensitivity to database updates.

**Open Question 5:**  
*Can the Query Routing Agent’s confidence‑threshold‑based multi‑label routing be improved to increase precision/recall of evidence selection, and how does routing quality ultimately impact end‑to‑end SQL accuracy?*  
- **Basis:** QRA uses a confidence threshold τ=0.5 to filter irrelevant evidence types but provides no analysis of routing accuracy or its correlation with final EX. Ablation shows “routing‑only” gives limited gains, suggesting routing is underperforming.  
- **Why unresolved:** It is unknown how often QRA misroutes (e.g., fails to signal needed numeric reasoning or false‑positive triggers), and whether routing errors are a primary bottleneck. The threshold τ is chosen without justification and may not be optimal.  
- **What would resolve:** An evaluation of QRA’s routing decisions against oracle evidence requirements, measuring precision/recall per evidence type. Additionally, a grid search over τ values correlated with EX would reveal the routing sensitivity and potential for optimization.

## Limitations
- **Undisclosed prompts and metrics:** Exact LLM prompts for QRA and EGA, and the few‑shot retrieval similarity metric, are not disclosed, hindering precise replication.
- **Data density dependency:** The approach assumes databases have sufficient data density for reliable statistical profiling; sparse columns may degrade the quality of cached knowledge.
- **LLM variability:** Routing errors or incomplete evidence generation due to LLM inconsistencies can lead to failures on enumerated values and structural completeness.

## Confidence
- Offline mining of intrinsic database knowledge: **High** (solid methodology and ablation support)
- Learned query routing: **Medium** (effectiveness shown but classification details unclear)
- LLM‑based evidence construction: **Medium** (gains depend on prompt quality and cached knowledge completeness)
