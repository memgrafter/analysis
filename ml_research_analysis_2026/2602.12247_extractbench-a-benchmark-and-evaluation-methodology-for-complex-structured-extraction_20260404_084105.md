# ExtractBench: A Benchmark and Evaluation Methodology for Complex Structured Extraction
## Quick Facts
- arXiv ID: 2602.12247
- Source URL: https://arxiv.org/abs/2602.12247
- Reference count: 32
- Primary result: Introduces a schema-driven evaluation framework for PDF-to-JSON extraction and reveals frontier models achieve only 4.6% field-level pass rate on complex enterprise schemas, with 0% validity on a 369-field financial schema.

## Executive Summary
ExtractBench addresses the lack of end-to-end benchmarks for structured extraction from PDFs under complex enterprise schemas. It proposes a schema-driven evaluation methodology that treats JSON Schema as an executable specification, assigning field-specific correctness metrics (exact match, tolerance, semantic equivalence). Evaluations of six frontier models across five domains show catastrophic performance degradation as schema breadth increases, with all models producing 0% valid output on a 369-field financial reporting schema. The analysis identifies output volume—the token count of the required JSON—as the dominant predictor of failure, not document length or nesting depth.

## Method Summary
The benchmark comprises 35 PDF documents spanning five domains (financial agreements, scientific papers, legal forms, sports results, SEC filings), each paired with a human-annotated gold JSON and a JSON Schema enriched with per-field `evaluation_config` annotations declaring the scoring metric. Models are prompted zero-shot to extract JSON matching the schema, optionally using structured output modes. The open-source evaluation framework parses the schema into an AST, validates the predicted JSON structure, then traverses the AST jointly with gold and prediction. For leaf fields, it applies the declared metric (e.g., `string_semantic` via an LLM judge, `number_tolerance`). For array fields marked `array_llm`, an LLM judge performs semantic alignment to match items before recursive scoring. Field-level pass/fail results are aggregated into document and domain scores. Reproduction requires obtaining the dataset from GitHub, running model inference via APIs (parameters not fully specified), and executing the evaluation framework. Unknowns include exact API settings and gold annotation inter-annotator agreement.

## Key Results
- Schema-driven evaluation enables field-sensitive scoring: identifiers use exact match, quantities use tolerance, names use semantic equivalence.
- LLM-based semantic alignment for arrays handles reordering, omissions, and spurious entries.
- All six frontier models achieve 0% valid output on a 369-field financial reporting schema; aggregate field-level pass rate across domains is only 4.6%.
- Output volume (gold JSON token count) is the strongest predictor of extraction failure, outweighing document length and nesting depth.

## Why This Works (Mechanism)
### Mechanism 1: Schema-Driven Evaluation as Executable Specification
Treating the JSON Schema as an executable specification with per-field `evaluation_config` annotations enables principled, field-sensitive scoring. The framework parses the schema into an AST, traverses it jointly with gold and predicted JSON, and applies the metric declared for each leaf node (e.g., `string_semantic`, `number_tolerance`). This decouples structure validation from content scoring and allows domain-specific equivalence without ad-hoc post-processing. **Core assumption:** Domain-specific equivalence can be operationalized by a configured metric. **Evidence:** The schema annotations explicitly declare metrics; AST-based dual-traversal is described in Section 3. **Break condition:** Schemas without `evaluation_config` default to a single global metric, losing field sensitivity.

### Mechanism 2: LLM-Based Semantic Alignment for Arrays
Arrays of objects require semantic, not positional, alignment to score correctly under reordering or missing items. For array fields marked `array_llm`, an LLM judge receives the item schema and both arrays, then returns a mapping of matched pairs, false negatives, and false positives. Per-field metrics are applied recursively to matched items. **Core assumption:** An LLM can infer item correspondence based on semantic key fields. **Evidence:** Section 3.4 describes the alignment process; Section 4.1 shows sports results domain has high validity but low pass rate due to array misalignment. **Break condition:** Large arrays may exceed judge context limits, requiring batching that risks alignment errors.

### Mechanism 3: Output Volume as Primary Failure Predictor
The token count of the required JSON output (reflecting schema breadth and array expansion) is the dominant predictor of extraction failure. Longer outputs increase formatting errors, exceed output token budgets, and force models to maintain structural discipline over more tokens, causing cascading failures. **Core assumption:** Model reliability for structured generation degrades non-linearly with output length due to attention/decoding constraints. **Evidence:** Section 4.2 shows sharp drop in validity and pass rate as gold token count increases; credit agreements (0.9k tokens) succeed while research papers (25k tokens) struggle. **Break condition:** If models improve long-output reliability (e.g., via constrained decoding or chunked generation), output volume may cease to be the primary constraint.

## Foundational Learning
- **Concept: Schema-Driven Evaluation**  
  **Why needed:** Traditional metrics (exact match, F1) fail for heterogeneous fields. This concept lets the schema declare the correctness criterion per field.  
  **Quick check:** Why would applying `string_fuzzy` to an agreement ID be inappropriate, and what metric should be used instead? (Answer: Agreement IDs require exact match; `string_exact` is appropriate.)

- **Concept: Semantic Array Alignment**  
  **Why needed:** Position-based matching is brittle; real-world arrays may be reordered or have missing/spurious entries. Alignment must identify which predicted item corresponds to which gold item.  
  **Quick check:** In a bibliography array, if the gold has {"title": "A", "year": 2020} and predicted has {"title": "A", "year": 2021} and {"title": "B", "year": 2020}, how should alignment and scoring proceed? (Answer: LLM judge should match the gold item to the predicted item with title "A" even if year differs, then score fields individually based on declared metrics.)

- **Concept: Complexity Dimensions (Breadth vs. Depth vs. Volume)**  
  **Why needed:** To diagnose why a model fails. ExtractBench shows volume and breadth are key, depth alone is weak.  
  **Quick check:** A schema with 50 fields but no arrays might be easier than a 20-field schema with a 1000-item array. Why? (Answer: Because output volume (long arrays) drives failure more than breadth; many fields without arrays yield shorter output.)

## Architecture Onboarding
**Component map:** Schema Parser -> AST -> Output Validator -> Metric Engine -> Array Aligner -> Aggregator -> Plugin Registry

**Critical path:** Schema → AST (Parser) → Output Validator → Traverse AST → For each leaf: apply metric (Metric Engine) → For each array: align items (Array Aligner) → Recursively score children → Aggregate (Aggregator). Plugin Registry allows adding new metrics.

**Design tradeoffs:**  
- Flexibility vs Support: Decoupling metrics from traversal allows custom rules but requires schema authors to understand metric choices.  
- LLM Judge Cost vs Accuracy: `array_llm` and `string_semantic` rely on a separate LLM call, increasing cost/latency but handling nuanced equivalence.  
- Strictness vs Graceful Degradation: Constrained decoding enforces structure but may harm accuracy on complex schemas; prompt-based allows omissions but yields invalid JSON.

**Failure signatures:**  
- Invalid JSON: trailing commas, truncation, empty response (formatting failures).  
- Low pass rate despite valid JSON: content errors (wrong values, array misalignment).  
- Provider-specific blocks: Claude’s 100-page limit, GPT’s silence on hard schemas.

**First 3 experiments:**  
1. Sanity check: Run evaluation on a trivial schema (2 fields) with known gold/pred to verify metric scoring and aggregation logic.  
2. Metric validation: For a field using `string_semantic`, test with clearly equivalent/non-equivalent strings to confirm LLM judge behavior aligns with expected thresholds.  
3. Stress test: Process a large schema (e.g., 369 fields) with a small valid output to measure AST traversal time and memory; verify parallelization works.

## Open Questions the Paper Calls Out
**Open Question 1:** Can decomposition strategies (e.g., hierarchical or iterative extraction) reliably overcome the output volume barrier for enterprise-scale schemas (e.g., 369 fields), and what architectural patterns (retrieval, agentic workflows) are most effective?  
*Basis:* Conclusion states "Long complex documents require exploration of context-management approaches like retrieval and agentic methods."  
*Why unresolved:* No concrete decomposition architectures are tested; the path forward is undefined.  
*What evidence would resolve it:* Systematic experiments comparing decomposition methods (sub-schemas, retrieval, multi-agent) against monolithic extraction on the SEC 10-K/Q schema, measuring validity and pass rate.

**Open Question 2:** Why do structured output modes (constrained decoding) degrade validity and accuracy on complex schemas compared to prompt-based extraction, and how can constrained decoding frameworks be improved to scale with schema breadth and nesting?  
*Basis:* Section 4.3 reports structured outputs reduced validity from 51% to 37% and pass rate from 6.9% to 5.5%, hypothesizing grammar complexity scaling and rigid enforcement.  
*Why unresolved:* Exact mechanisms (grammar automaton size, interference with reasoning) are speculative; provider-specific limits are noted but not dissected.  
*What evidence would resolve it:* Profiling internal grammar artifacts (automaton size, state complexity) for varying schemas; ablation studies controlling grammar overhead vs. rigidity.

**Open Question 3:** Is the observed correlation between output volume and failure causal due to model capacity limits (e.g., attention, positional encoding) or is it confounded by schema-specific features (e.g., number of array items, optional fields)?  
*Basis:* Output volume (gold token count) is identified as the dominant predictor, but volume is highly correlated with array expansion.  
*Why unresolved:* Domains vary multiple factors; gold token count conflates length with structural complexity; no controlled study isolating volume from breadth.  
*What evidence would resolve it:* Controlled experiments with synthetic schemas that systematically vary: (1) number of fields (breadth) with fixed arrays, (2) array item count with fixed breadth, (3) nesting depth. Isolate output length as independent variable.

**Open Question 4:** How reliable is the schema-driven evaluation framework itself, particularly its reliance on an LLM judge (Gemini 2.5 Flash) for semantic array alignment and semantic equivalence? Does judge choice or prompt engineering significantly affect pass rates?  
*Basis:* Evaluation uses a fixed judge with threshold 0.7; framework is open-sourced but no sensitivity analysis reported.  
*Why unresolved:* Framework validity hinges on judge consistency; pass rates (4.6%) could be noisy artifacts. No inter-judge agreement or robustness checks.  
*What evidence would resolve it:* Ablation study using multiple LLM judges (GPT-4.5, Claude 3.5 Sonnet, open-source models) on a subset; report agreement metrics (Cohen's kappa) for alignment and equivalence; analyze threshold effects.

## Limitations
- Unknown API call parameters (temperature, max_tokens, PDF rendering) and provider-specific handling block precise replication of model outputs.
- Gold standard annotation process details (annotator background, guidelines, inter-annotator agreement) are unreported, limiting confidence in ground truth quality.

## Confidence
- Schema-Driven Evaluation: High (strongly supported by AST traversal and per-field metric declarations).
- LLM-Based Array Alignment: Medium (mechanism specified but judge consistency not calibrated).
- Output Volume as Predictor: High (robust empirical correlation across domains, though causal mechanism inferred).

## Next Checks
1. **Metric sanity test:** Run `string_semantic` on clearly equivalent/non-equivalent pairs (e.g., "IBM" vs. "International Business Machines") to verify judge behavior matches expected thresholds.
2. **Array alignment validation:** Construct controlled arrays with known misalignments (reordered items, minor field differences) to measure precision/recall of the LLM aligner against a gold mapping.
3. **Volume predictor replication:** Train a simple regression model on the reported data (gold token count vs. pass rate) and test on held-out schemas to confirm the non-linear decay trend holds for other frontier models (e.g., o3, Claude 3.7).
