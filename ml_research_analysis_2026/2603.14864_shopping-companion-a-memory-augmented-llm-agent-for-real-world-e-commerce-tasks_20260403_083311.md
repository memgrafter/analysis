# Shopping Companion: A Memory-Augmented LLM Agent for Real-World E-Commerce Tasks
## Quick Facts
- arXiv ID: 2603.14864  
- Source URL: https://arxiv.org/abs/2603.14864  
- Reference count: 33  
- Primary result: Achieves up to 90% preference accuracy and 84% task success on single-product recommendation with a 4B parameter model.

## Executive Summary
This paper introduces a novel benchmark for long-term preference-aware e-commerce shopping tasks, addressing the absence of such evaluations in existing research. It proposes Shopping Companion, a unified two-stage LLM agent that jointly performs memory retrieval and product search, supporting user intervention. Trained with dual-reward reinforcement learning and tool-wise supervision, the agent outperforms strong baselines—including GPT-5—despite using a lightweight Qwen3-4B backbone. Results show high performance on single-product recommendation but a notable gap on more complex add-on deals tasks.

## Method Summary
Shopping Companion uses a two-stage architecture. Stage 1 identifies user preferences by querying a long-term memory of past interactions via tools like `mem_search` and `mem_view`, then confirms findings with the user. Stage 2 executes shopping via `product_search` and `product_view` to recommend products. The base model is Qwen3-4B-Thinking-2507. Training first applies supervised fine-tuning on successful trajectories sampled from GPT-4.1. Reinforcement learning with GRPO then optimizes the policy using a dual-reward signal: stage-specific rewards for preference accuracy and task success, supplemented by tool-wise rewards that score each tool call’s relevance, plus a format reward to enforce structured output.

## Key Results
- GPT-5 attains less than 70% success on the benchmark, underscoring the task’s difficulty.
- With dual and tool-wise rewards, Qwen3-4B reaches 90% preference accuracy and 84% task success on single-product recommendation.
- On add-on deals, it achieves 55% accuracy and 43% success, consistently outperforming baselines but revealing a persistent performance gap.

## Why This Works (Mechanism)
Joint optimization of memory retrieval and product search ensures extracted preferences directly guide shopping actions, reducing error propagation from pipeline separation. Dual-reward RL provides feedback at both outcome and tool-call levels, alleviating the sparsity of terminal rewards. Tool-wise supervision densifies the learning signal, explicitly teaching the agent to use tools effectively. This combination allows a small model to surpass larger ones like GPT-5 on specialized, memory-intensive tasks.

- **Tool-augmented LLMs**: Needed to interact with external product and memory databases. Quick check: Are there defined tools (e.g., `mem_search`, `product_search`) with structured JSON outputs?
- **Reinforcement learning for sparse rewards**: Needed to optimize end-to-end success where intermediate progress is unobserved. Quick check: Is RL applied after SFT, with rewards beyond the final outcome?
- **Dual reward design**: Needed to separately optimize preference extraction and shopping. Quick check: Are there distinct reward components for Stage 1 and Stage 2?

## Architecture Onboarding
- **Component map**: User Input -> Stage 1: Preference Identifier (tools: mem_search, mem_view, mem_summarize_by_date) -> Stage 2: Shopper (tools: product_search, product_view) -> Final Recommendation (@REC::...@)
- **Critical path**: From instruction and dialogue history, Stage 1 retrieves and summarizes relevant past preferences, seeking user confirmation. Stage 2 searches products, views details, and selects items satisfying preferences, constraints, and budget. Both stages must succeed for task completion.
- **Design tradeoffs**: Two-stage decomposition improves interpretability and allows user intervention but may discard information exploitable by an end-to-end policy. Joint RL mitigates some separation costs but complicates training. Tool-wise rewards improve credit assignment but depend on gold-standard annotations.
- **Failure signatures**: Low tool-wise scores (e.g., `mem_search` recall < 50%), high variance in rollout lengths, frequent format violations, or Stage 1 outputs that poorly constrain Stage 2. Logs show many irrelevant product views or redundant memory searches.
- **First experiments**:
  1. Evaluate the trained agent on the held-out test set to verify reported accuracy and success rates.
  2. Ablate the tool-wise reward component to measure its impact on learning stability and final performance.
  3. Vary the length of conversational memory (e.g., 10 vs. 50 turns) to test robustness of preference retrieval.

## Open Questions the Paper Calls Out
1. Why does multi-product coordination in add-on deals tasks present such a persistent performance gap compared to single-product recommendation, even with joint optimization?
2. How can the tool-wise reward design be generalized to arbitrary tool-augmented agent architectures without requiring handcrafted, domain-specific reward heuristics?
3. Does the explicit two-stage decomposition (preference identification then shopping) introduce representational bottlenecks that limit end-to-end optimization, and could a monolithic policy with internal memory attention match or exceed performance?
4. How does the length and sparsity of long-term conversational memory impact the agent's ability to accurately extract implicit preferences, and what memory architectures (e.g., summarization, indexing strategies) mitigate degradation?

## Limitations
- The benchmark dataset (1.2M products, 1k instructions) is not released, preventing independent verification and fair comparison.
- Evaluation relies on GPT-5 as a judge; this model is inaccessible, and substitutions may bias results.
- Reward server details (e.g., fuzzy matching thresholds) and distributed training configuration are underspecified, increasing replication risk.

## Confidence
- Benchmark claim (new long-term preference benchmark): Medium
- Agent architecture (two-stage joint retrieval): High
- Training method (dual-reward RL with tool-wise supervision): Medium
- Reported performance numbers: Low
