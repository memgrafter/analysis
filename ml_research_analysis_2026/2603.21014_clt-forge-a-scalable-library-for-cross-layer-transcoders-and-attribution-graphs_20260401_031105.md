# CLT-Forge: A Scalable Library for Cross-Layer Transcoders and Attribution Graphs

## Quick Facts
*   **arXiv ID:** 2603.21014
*   **Source URL:** https://arxiv.org/abs/2603.21014
*   **Reference count:** 7
*   **Primary result:** An open-source library that enables practical training of large Cross-Layer Transcoders (CLTs) via compressed activation caching and feature-wise sharding, achieving near-baseline reconstruction quality with 4–12× less storage and scaling to models like LLaMA 3.2 1B (expansion factor 48) on 8 GPUs.

## Executive Summary
Training Cross-Layer Transcoders (CLTs) at scale is hindered by immense computational and memory costs, primarily due to the need to store vast amounts of activations and the quadratic growth of parameters with feature count. This paper introduces **CLT-Forge**, a unified library that addresses these bottlenecks through a combination of compressed activation caching, feature-wise model sharding, and an integrated pipeline from training to visualization. The system demonstrates that CLTs can be trained efficiently for modern small-to-medium language models (e.g., LLaMA 3.2 1B), producing compact and complete attribution graphs while matching prior benchmarks on GPT-2.

## Method Summary
The reproduction plan involves a four-stage pipeline. First, precompute and cache all MLP activations for a large token dataset from the base model, applying per-layer normalization and quantization (e.g., int4) with zstd compression to reduce storage. Second, launch distributed training of a CLT where the massive encoder/decoder matrices are sharded across GPUs along the feature dimension; the training objective combines reconstruction loss, JumpReLU sparsity penalties, and dead feature regularization. Third, run the AutoInterp pipeline on the trained CLT to find top-activating sequences and generate LLM-based feature explanations. Finally, compute feature attribution graphs for specific prompts using Circuit-Tracer and explore them via the provided Dash-based visual interface.

## Key Results
*   Compressed activation caching reduces storage requirements by **4–12×** (e.g., 20TB to 4TB for LLaMA 1B) with only a **2–3% drop** in reconstruction quality.
*   Achieves ~0.8 **explained variance** and ~0.8 **replacement score** on GPT-2 benchmarks with L0=100.
*   Enables training a CLT for **LLaMA 3.2 1B** with an expansion factor of 48 across 8 GPUs.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** Compressed, quantized activation caching reduces storage requirements enough to make large-scale CLT training feasible.
*   **Mechanism:** Precomputed MLP activations are normalized per layer, quantized (e.g., int4/int2), and compressed with zstd. During training, chunks are loaded on-demand, trading a small, bounded increase in reconstruction error for massive I/O and storage savings.
*   **Core assumption:** The minor degradation from quantization/compression does not significantly harm final CLT reconstruction quality or feature interpretability.
*   **Evidence anchors:**
    *   [abstract] "compressed activation caching reduces storage requirements by 4–12× ... with only a 2–3% drop in reconstruction quality"
    *   [Section 3.1] Details symmetric per-layer quantization, zstd coding, and the 20TB->4TB example for LLaMA 1B.
*   **Break condition:** Reconstruction error penalty from quantization grows non-linearly (e.g., >5% drop), causing CLT to fail baseline explained variance targets (~0.8).

### Mechanism 2
*   **Claim:** Feature-wise model sharding distributes the massive CLT parameter matrix across GPUs, overcoming memory limitations.
*   **Mechanism:** The CLT's encoder/decoder matrices are split along the feature dimension (`dfeatures`). Each GPU holds a shard, computes forward/backward passes only for its shard, and aggregates outputs. This makes models like LLaMA 3.2 1B (expansion factor 48) trainable on 8x80GB GPUs.
*   **Core assumption:** Linear aggregation of partial outputs from feature shards is numerically stable and does not degrade training convergence or sparsity.
*   **Evidence anchors:**
    *   [abstract] "...feature-wise sharding ... enabling practical CLT training for models like LLaMA 3.2 1B with an expansion factor of 48 across 8 GPUs."
    *   [Section 3.3] Contrasts feature sharding with DDP/FSDP, stating sharding is necessary for expansion factor 48.
*   **Break condition:** Communication overhead for aggregating sharded outputs becomes the bottleneck, causing super-linear training slowdown or memory pressure during gradient sync.

### Mechanism 3
*   **Claim:** A tightly integrated, unified pipeline from activation caching to visual exploration eliminates workflow friction, making CLT research reproducible and scalable.
*   **Mechanism:** The library provides a single configuration system orchestrating: compressed activation storage, distributed CLT training with sharding, parallelized AutoInterp, Circuit-Tracer attribution, and a Dash UI. Data flows via standardized formats (e.g., per-layer/feature databases).
*   **Core assumption:** The overhead of building/maintaining this integration is offset by gains in reduced manual data juggling and faster iteration cycles.
*   **Evidence anchors:**
    *   [abstract] "unifies scalable distributed training ... automated interpretability pipeline, attribution graph computation ... and a flexible visualization interface into a single workflow."
    *   [Section 3] Describes interconnected stages (3.1 to 3.6) with a unified API.
*   **Break condition:** A major upstream change (e.g., new model architecture, Circuit-Tracer formula change) breaks a core interface, requiring disproportionate adaptation effort.

## Foundational Learning
*   **Concept: Cross-Layer Transcoders (CLTs)**
    *   **Why needed:** CLTs are the core object being trained. They use a single shared sparse feature set across all layers, unlike layer-specific transcoders, leading to quadratic parameter count and more compact attribution graphs.
    *   **Quick check:** If a CLT has `dfeatures`=100 and `L`=10 layers, how many decoder weight matrices (`W^ℓ→ℓ'`) exist (excluding biases)? → 90 (all ordered pairs ℓ≠ℓ').
*   **Concept: Attribution Graph & Circuit-Tracing**
    *   **Why needed:** The end goal is a graph of feature influences computed by Circuit-Tracer using a trained CLT and frozen model Jacobians. Graph compactness is a key metric.
    *   **Quick check:** What two vectors (`f` and `g` in Eq. 5) from the CLT are multiplied with the Jacobian to compute an attribution score? → Source feature activations `f_ℓ` and destination feature activations `g_ℓ'`.
*   **Concept: JumpReLU & Sparsity Regularization**
    *   **Why needed:** The CLT is trained to produce sparse, interpretable features. JumpReLU (`σ`) and `L0`/dead feature penalties in the loss control the trade-off between reconstruction quality and interpretability/graph size.
    *   **Quick check:** In the loss function (Eq. 6), what does increasing the `λ0` (L0 coefficient) hyperparameter encourage? → Higher sparsity (more zero activations) in the CLT's feature representation.

## Architecture Onboarding
*   **Component map:**
    ActivationsStore -> CLTTrainingRunner -> AutoInterp -> AttributionRunner -> Visual Interface (Dash)
*   **Critical path:** **Activations → CLT Training → AutoInterp → Attribution Graph → Visualization**. The cached activations are the foundational data artifact. All downstream stages depend on a trained CLT checkpoint.
*   **Design tradeoffs:**
    *   *Quantization level (int8/int4/int2):* Lower bit-depth = smaller storage/faster I/O vs. higher reconstruction error. int4 recommended for large models.
    *   *Feature sharding vs. DDP/FSDP:* Feature sharding is essential for large CLTs but requires careful output aggregation. DDP is simpler but hits memory limits quickly.
    *   *AutoInterp token count:* More tokens (e.g., 10M) yield better feature explanations but increase compute time. Balance based on feature count.
*   **Failure signatures:**
    *   High dead feature rate (>30% per layer): Poor encoder init, too high `λ0`, or insufficient training tokens.
    *   Explained variance plateaus below 0.7: Bad hyperparameters (LR, `λ0` schedule), inadequate expansion factor, or corrupted activation cache.
    *   Memory spike during graph computation: Non-sharded Circuit-Tracer on a too-large prompt or failure to prune low-magnitude attributions early.
    *   Visual interface fails to load: Mismatch between feature database schema and CLT checkpoint version.
*   **First 3 experiments:**
    1.  **Test activation pipeline:** Run `ActivationsStore` for GPT-2 Small with `context_size=32` and `int8` quantization. Verify output structure, check file sizes, load one chunk to confirm shapes and dequantization sanity (norm ≈1).
    2.  **Train minimal CLT:** Use cached activations to train a tiny CLT (`expansion_factor=4`, 1 layer) for 1000 steps on a single GPU. Check that `L0` matches target schedule and loss decreases.
    3.  **Generate a known circuit graph:** For prompt `"The opposite of 'large' is"`, run the full pipeline (small CLT, AutoInterp, AttributionRunner). Compare output graph to a reference simple circuit (e.g., "greater-than") and confirm semantic coherence of feature explanations in the UI.

## Limitations
*   Exact training details for LLaMA 3.2 1B (e.g., `λ0` schedule, dataset) are omitted, preventing exact replication.
*   Unclear if CLT-Forge uses an unmodified Circuit-Tracer or custom patches, risking graph computation discrepancies.
*   Scalability ceiling untested: Claims demonstrated up to LLaMA 1B; performance on larger models (3B+) or denser CLTs (>48 expansion) is not shown.

## Confidence
*   **Mechanism 1 (Activation caching):** Medium. Storage reductions are quantified, but long-term impact on feature quality beyond 2–3% loss is unproven.
*   **Mechanism 2 (Feature sharding):** Medium. Feasibility for 8×80GB GPUs is shown, but communication overhead at scale lacks stress testing.
*   **Mechanism 3 (Unified pipeline):** Medium. Integration benefits are claimed but maintenance burden and interface fragility are not measured.
