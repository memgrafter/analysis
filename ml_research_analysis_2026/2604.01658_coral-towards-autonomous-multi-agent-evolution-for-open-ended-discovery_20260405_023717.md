# CORAL: Towards Autonomous Multi-Agent Evolution for Open-Ended Discovery

## Quick Facts
- **arXiv ID**: 2604.01658  
- **Source URL**: https://arxiv.org/abs/2604.01658  
- **Reference count**: 40  
- **Primary result**: CORAL achieves new SOTA on 10 of 11 tasks, with 3–10× higher improvement rates and far fewer evaluations; on Anthropic's kernel engineering task, it improves the best known score by 20% (1363 to 1103 cycles).

## Executive Summary
CORAL introduces a framework for autonomous multi-agent evolution in open-ended discovery problems. Unlike fixed evolutionary search baselines that rely on rigid heuristics, CORAL enables agents to control retrieval, proposal, evaluation, and knowledge accumulation through shared persistent memory, asynchronous execution, and heartbeat interventions. Across mathematical, algorithmic, and systems optimization tasks, CORAL substantially outperforms baselines, demonstrating that multi-agent autonomy and knowledge reuse drive more efficient open-ended discovery.

## Method Summary
CORAL replaces the evaluate-select-mutate loop with long-running LLM agents that autonomously decide when to retrieve prior solutions, propose modifications, run local tests, and store knowledge. Agents operate in isolated git worktrees but share a common filesystem hub (`.coral/public/`) where they write attempts, notes, and skills. Heartbeat mechanisms periodically inject reflective, consolidating, or pivot prompts to steer search. Knowledge accumulates as structured artifacts that other agents can read, enabling emergent cross-agent transfer. The framework is evaluated on 11 open-ended discovery tasks, comparing against state-of-the-art fixed evolutionary methods (e.g., MAP-Elites, Heuristic Evolution) using metrics such as best score, improvement rate, and evaluation count.

## Key Results
- CORAL sets new state-of-the-art on 10 of 11 tasks, with 3–10× higher improvement rates and significantly fewer evaluations compared to baselines.
- On Anthropic's Kernel Engineering task, four co-evolving agents improve the best known score from 1363 to 1103 cycles (20% gain).
- Cross-agent knowledge transfer is substantial: 36% of attempts use another agent’s commit as parent, and 66% of new records originate from cross-agent parents.

## Why This Works (Mechanism)

### Mechanism 1: Agent Autonomy
- **Claim**: Granting agents autonomy over the evolutionary search loop (retrieval, proposal, evaluation, update) improves efficiency by enabling context-aware decisions.
- **Mechanism**: Agents internally decide which prior solutions to inspect, when to run local tests, and what knowledge to store, replacing fixed selection heuristics.
- **Core assumption**: LLM agents can make effective meta-decisions about search strategy given task feedback.
- **Evidence**: Paper states agents control all aspects of the loop; fixed baselines lack this agency. Ablation studies show autonomy leads to better improvement rates.
- **Break condition**: Agents repeatedly make harmful strategic choices (e.g., persistent local optimization without exploration) and heartbeat triggers fail to redirect.

### Mechanism 2: Shared Persistent Memory
- **Claim**: Shared persistent memory (attempts, notes, skills) enables cross-agent knowledge reuse and cumulative progress.
- **Mechanism**: Agents asynchronously read and write structured artifacts to a common filesystem; later agents inspect these to bootstrap new search directions.
- **Core assumption**: Reusable insights (e.g., algorithmic patterns, architectural bottlenecks) can be externalized and later reincorporated effectively.
- **Evidence**: Paper describes a library-like hub where agents contribute and retrieve; qualitative analysis shows diffusion of useful techniques.
- **Break condition**: Shared memory becomes polluted with low-quality artifacts, misleading subsequent agents and degrading performance.

### Mechanism 3: Asynchronous Multi-Agent Execution
- **Claim**: Asynchronous multi-agent execution with indirect coordination (via shared memory) increases exploration diversity and extends the search frontier beyond single-agent capability.
- **Mechanism**: Multiple agents run in isolated workspaces, pursuing different local strategies; discoveries propagate through shared artifacts without explicit messaging.
- **Core assumption**: Parallel, diverse exploration with emergent knowledge transfer outweighs the cost of redundant work.
- **Evidence**: Cross-agent parentage statistics (36% attempts, 66% new records) and multi-agent runs outperforming single-agent runs.
- **Break condition**: Agents' search trajectories remain highly overlapping despite isolation, yielding minimal diversity gain over independent runs.

## Foundational Learning

### Evolutionary Algorithms
- **Why needed**: CORAL modifies the classic evaluate-select-mutate loop; understanding fixed baselines (e.g., MAP-Elites) clarifies what "autonomous" replaces.
- **Quick check**: What are the roles of parent selection and variation operators in a traditional evolutionary algorithm, and why might hard-coding them limit open-ended search?

### LLM Agent Autonomy
- **Why needed**: CORAL agents control their own workflow; grasping how LLMs can act as long-horizon planners vs. one-shot generators is central.
- **Quick check**: How might an autonomous agent decide *when* to evaluate a candidate versus iterating locally, and what risks does this introduce?

### Shared Memory Coordination
- **Why needed**: Multi-agent gains rely on a common file-based repository; understanding decentralized coordination via artifacts (not messages) is crucial.
- **Quick check**: In CORAL, how does an agent indirectly influence another agent’s future behavior without direct communication?

## Architecture Onboarding

### Component Map
Config (YAML), AgentManager (lifecycle), HeartbeatRunner (triggers), Grader (evaluation), Workspace (isolated git worktrees), Hub (.coral/public/ filesystem), CLI (coral eval/log/checkout)

### Critical Path
Agent startup → read CORAL.md → loop (plan → edit → coral eval) → heartbeat might inject reflection/consolidate/pivot prompts → write artifacts to Hub → other agents read Hub.

### Design Tradeoffs
- Isolation vs. communication: Per-agent git worktrees prevent interference but rely on eventual consistency via filesystem.
- Heartbeat frequency: Too frequent disrupts flow; too rare risks stagnation. Defaults (1/10/5) are heuristics.
- Shared memory schema: Fixed root folders (attempts/notes/skills) bootstraps structure but may constrain emergent organization.

### Failure Signatures
- Agent loops without improvement → pivot heartbeat should trigger.
- Memory corruption (e.g., malformed note) → grader or retrieval failures.
- Resource exhaustion → evaluator timeouts or disk full; monitor via coral status.

### First 3 Experiments
1. Run single agent on a simple task (e.g., Circle Packing) with `coral start -c task.yaml`. Observe `coral log` and file creation in `.coral/public/attempts/`.
2. Disable heartbeats (`heartbeat set reflect every 999`) and note degradation in improvement rate; re-enable and compare.
3. Launch two agents on same task; inspect `.coral/public/notes/` to see cross-agent contributions and verify attempts referencing other agents' commits.

## Open Questions the Paper Calls Out
- **Open Question 1**: Can small specialized models replace frontier LLMs in CORAL without sacrificing discovery performance?  
  *Basis*: Appendix A identifies as a key limitation; future work is to train customized small models.  
  *Why unresolved*: Frontier models are costly and often inaccessible; small models may lack needed reasoning.  
  *Resolving evidence*: Systematic benchmarking of CORAL runs using small fine-tuned models (e.g., CodeLlama, StarCoder) across all 11 tasks, comparing improvement rates, evaluation efficiency, final scores, and cost-per-discovery.

- **Open Question 2**: How can agent heterogeneity (roles, personalities, private knowledge) be injected and managed to improve multi-agent evolutionary search?  
  *Basis*: Appendix A notes current lack of bootstrapped heterogeneity.  
  *Why unresolved*: Identical initialization may limit exploration diversity; heterogeneity might boost diversity but risks coordination failures.  
  *Resolving evidence*: Controlled experiments comparing homogeneous vs. heterogeneous populations (different system prompts, private memory buffers, skill biases), measuring exploration diversity (strategy Jaccard similarity) and final quality.

- **Open Question 3**: For tasks with ambiguous or incomplete objectives, how should the evaluator co-evolve with candidate solutions to maintain meaningful search progress?  
  *Basis*: Appendix A assumes well-specified evaluator; evaluation may need to co-evolve.  
  *Why unresolved*: Static evaluators can misalign or incentivize hacking over true improvement.  
  *Resolving evidence*: Design a meta-evolution loop where the evaluator is an LLM agent that refines scoring criteria based on cross-agent consensus and/or human feedback, measuring search alignment and solution quality on tasks with human preferences.

- **Open Question 4**: Is agent-directed, opportunistic inspection of prior attempts more effective than fixed retrieval mechanisms in driving evolutionary improvement?  
  *Basis*: Section 4.4.2 notes agents inspect prior attempts but isolating effect is difficult.  
  *Why unresolved*: CORAL's autonomy includes flexible inspection, but its contribution relative to fixed retrieval is unclear.  
  *Resolving evidence*: Three-way ablation on identical tasks: (a) full CORAL, (b) CORAL with retrieval constrained to mimic fixed baselines, (c) fixed baselines with enhanced inspection; compare improvement rates and final scores.

## Limitations
- Heartbeat mechanics (plateau detection threshold, cooldown) are unspecified.
- ADRS benchmark evaluators require manual sourcing and patching (Appendix D.3), risking deviation from intended scoring.
- Kernel Engineering task relies on external (possibly proprietary) Anthropic code, blocking direct replication.
