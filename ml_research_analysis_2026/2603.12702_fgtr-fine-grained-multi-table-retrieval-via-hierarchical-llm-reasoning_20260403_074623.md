# FGTR: Fine-Grained Multi-Table Retrieval via Hierarchical LLM Reasoning
## Quick Facts
- **ArXiv ID:** 2603.12702  
- **Source URL:** https://arxiv.org/abs/2603.12702  
- **Reference count:** 40  
- **Primary result:** FGTR improves F2 metric by 18% on Spider and 21% on BIRD versus state-of-the-art, with superior precision-recall balance and downstream QA accuracy.

## Executive Summary
FGTR addresses the inefficiency of coarse-grained LLM-based table retrieval in multi-table scenarios by introducing a hierarchical reasoning strategy. It first performs schema retrieval to identify query-relevant columns, then cell retrieval to locate precise data using constraint-aware matching. Evaluated on newly constructed SpiderQA and BirdQA benchmarks, FGTR achieves state-of-the-art retrieval performance (e.g., F2 91.20 on Spider schema retrieval) and downstream question answering accuracy (78.26% exact match on SpiderQA), while reducing token consumption and handling large tables robustly.

## Method Summary
FGTR operates via offline preprocessing and online retrieval. Offline, each table is transformed: schema semantization generates natural language descriptions for tables/columns; join-path discovery computes foreign-key connection weights; columnar storage builds an HNSW index over unique non-numeric cell values. Online, given a query, schema retrieval parses the query into key entities, maps them to columns using LLM reasoning with iterative voting, and fills in necessary primary/foreign keys for joins. Cell retrieval then classifies columns as constrained (with explicit conditions) or dependent. For constrained columns, non-numeric values use semantic similarity search on the HNSW index, while numeric values use exact matching; dependent columns include all rows. The final sub-table merges rows across tables based on retrieved columns.

## Key Results
- **Retrieval gains:** +18% F2 on Spider, +21% F2 on BIRD vs. SOTA methods.
- **Schema retrieval F2:** 91.20 on Spider.
- **Downstream QA:** 78.26% exact match on SpiderQA.
- **Efficiency:** Reduced token consumption versus full-table encoding baselines; robust to large tables.

## Why This Works (Mechanism)
**Mechanism 1: Hierarchical Decomposition**
- **Claim:** Decomposing retrieval into schema-then-cell reduces noise and improves efficiency versus holistic table encoding.
- **Mechanism:** Schema retrieval narrows the search space to relevant columns; cell retrieval operates only on these pre-filtered columns and associated rows, avoiding O(N*M) full-table scanning. This mirrors human table-reading and leverages LLMs' textual reasoning for structured data.
- **Core assumption:** Query-relevant information is concentrated in a small, non-overlapping subset of columns and rows.
- **Evidence anchors:** [abstract] describes the two-stage process; [section 4.2] notes narrowing retrieval scope; corpus (e.g., REaR) supports multi-table retrieval challenges.
- **Break condition:** Low strict recall (SR) in schema retrieval cannot be recovered downstream, causing complete query failure.

**Mechanism 2: Parsing–Mapping–Filling with Iterative Voting**
- **Claim:** This strategy ensures high schema recall while controlling precision, handling ambiguous queries and implicit join paths.
- **Mechanism:** (1) Parsing decomposes query into entities/phrases. (2) Mapping aligns these with candidate columns using schema descriptions, prioritizing recall. (3) Filling adds primary/foreign keys to connect selected schemas. Multiple mapping iterations with voting (frequency ≥ θ) mitigate LLM positional bias and stochasticity.
- **Core assumption:** LLMs can reliably map query entities to schema elements with natural language descriptions and examples, but single-pass predictions are noisy.
- **Evidence anchors:** [section 4.2] details the stages; Table 1 shows FGTR@5+key SR (e.g., 89.32) significantly higher than w/o schema filling, validating join path handling.
- **Break condition:** Threshold θ mis-set harms recall (too high) or precision (too low); voting fails if LLM predictions are consistently misaligned.

**Mechanism 3: Adaptive Cell Retrieval**
- **Claim:** Constraint-aware range parsing and adaptive semantic/exact matching achieves a superior precision-recall trade-off.
- **Mechanism:** Range parsing categorizes columns as constrained (explicit query conditions) or dependent. For constrained columns, cell mapping uses HNSW-based approximate nearest neighbor search over pre-encoded unique values for non-numeric constraints (semantic similarity), and exact matching for numeric constraints. Dependent columns default to full row inclusion.
- **Core assumption:** Query constraints can be reliably extracted; value-level semantic similarity is more robust than row-level encoding for fuzzy matching.
- **Evidence anchors:** [section 4.3] describes classification and matching; Table 2 shows FGTR(adapt) precision (e.g., 64.75 on Spider) dramatically higher than baselines like TableRAG (24.31); corpus (CLTR) explores cell-level retrieval differently.
- **Break condition:** Misclassification of constrained columns as dependent drops recall; poor semantic threshold harms precision or recall.

## Foundational Learning
- **Hierarchical Decomposition for Structured Data:** Splits monolithic retrieval into schema then cell stages, leveraging different matching strategies and bypassing LLM limitations in handling large, flat contexts.  
  *Quick check:* "Why is identifying correct columns first more effective than scanning all cells directly? What LLM limitations does this bypass?"
- **Schema Semantization & Precomputed Join Graphs:** Offline transformation of raw schemas into natural descriptions and FK weights enables efficient online mapping/filling without expensive on-the-fly joins.

## Architecture Onboarding
**Component map:**  
Offline Preprocessor (Schema Semantizer, Join-Path Discoverer, Columnar Storage Builder) -> Online Retriever (Schema Retriever -> Cell Retriever -> Sub-table Constructor)

**Critical path:** Schema Retriever output (set S) is mandatory input for Cell Retriever; failure or low recall in schema retrieval cannot be corrected downstream. Join-Path Discovery output is critical for Schema Filling.

**Design tradeoffs:**
- Recall vs. Precision (Schema): Voting mechanism (K iterations, threshold θ) trades recall (low θ) vs. precision (high θ). Schema Filling improves recall for joins but may add slight noise.
- Semantic vs. Exact Matching (Cell): Adaptive mapping uses semantic search for non-numeric values (robust to synonyms) but is slower/less precise than exact matching for strict numeric constraints; classification of constrained columns is pivotal.
- Offline Cost vs. Online Speed: Pre-building HNSW indexes and computing all pairwise FK weights is expensive offline (O(d²) for d columns) but guarantees low-latency online querying.

**Failure signatures:**
- Schema SR ≈ 0: Indicates Parsing/Mapping/Filling pipeline failed. Check: prompt design, column description quality, θ value.
- High Schema P, Low Schema R: Overly aggressive filtering in Mapping (θ too high) or poor filling. Check: voting K value, join key addition.
- Cell P ~= 0 while R high: Adaptive mapping too broad (threshold too low) or Range Parsing misclassified most columns as constrained. Check: similarity threshold, constraint extraction logic.
- Sub-table too large/larger than full table: Cell Merging logic (union of row sets) is over-inclusive, or dependent columns are treated incorrectly. Check: row union logic (Eq. 6).

**First 3 experiments:**
1. **Isolated Schema Retrieval Benchmark:** Run only the Schema Retriever on a small, labeled subset (e.g., 50 queries). Compute Precision, Recall, F2, and Strict Recall (SR) to isolate schema pipeline quality.
2. **Ablation: Schema Filling Impact:** Repeat experiment 1 with `w/o schema filling`. Expect significant SR drop on BIRD (complex joins), validating join-path discovery utility.
3. **Gold Schema Cell Retrieval Stress Test:** Provide the gold schema set (S_gold) directly to the Cell Retriever. Compare results to full pipeline cell metrics to quantify error propagation and test adaptive cell mapping purity.

## Open Questions the Paper Calls Out
1. **Impact on other downstream tasks:** FGTR claims broad applicability but is only evaluated on QA and fact verification. How does it perform on table-to-text generation or summarization?  
   *Basis:* Explicit claim in paper; *Why unresolved:* Not validated across diverse tasks; *Resolving evidence:* Benchmark on ToTTo, WikiTableQuestions, etc.
2. **Query-dependent join paths:** Schema filling uses static, precomputed join weights. Could dynamic, query-aware join reasoning improve accuracy on complex multi-table queries?  
   *Basis:* Inferred from ablation showing filling boosts recall; *Why unresolved:* No exploration of query-guided joins; *Resolving evidence:* Replace static addition with LLM-based, query-guided join retrieval and measure changes.
3. **Scalability to many tables:** Benchmarks use ~5–7 tables. How does FGTR scale to databases with hundreds of tables?  
   *Basis:* Inferred from average table counts; *Why unresolved:* Real-world corpora may have many tables; schema retrieval scanning many schemas may degrade; *Resolving evidence:* Evaluate on databases with 10, 50, 100 tables, measuring F2, token use, latency vs. full-table methods.
4. **Quantitative token savings:** The paper claims reduced token consumption but provides no numbers. What is the exact trade-off between token reduction and retrieval accuracy?  
   *Basis:* Explicit claim in Section 5.5; *Why unresolved:* No token counts reported; *Resolving evidence:* Measure tokens used by FGTR vs. TableRAG across table sizes, plot savings against metrics.

## Limitations
- **Reproducibility gaps:** Exact LLM prompt templates, HNSW hyperparameters (M, efConstruction), adaptive similarity threshold, and specific embedding model (likely text-embedding-ada-002) are not disclosed.
- **Evaluation scope:** Benchmarks derived from text-to-SQL datasets; performance on truly heterogeneous, real-world multi-table corpora with messy schemas is unverified.
- **Core assumption reliance:** Hierarchical split critically depends on high schema retrieval Strict Recall (SR); failure mode with low SR has no downstream recovery.

## Confidence
- **Hierarchical Decomposition Efficacy:** Medium (strong internal F2 gains, limited external corpus corroboration).
- **Parsing-Mapping-Filling with Voting:** High (ablation in Table 1 shows significant SR drop w/o filling, directly supporting claim).
- **Adaptive Cell Retrieval (Range Parsing + Matching):** Medium (Table 2 shows precision gains, but classification logic and threshold tuning are key unknowns).
