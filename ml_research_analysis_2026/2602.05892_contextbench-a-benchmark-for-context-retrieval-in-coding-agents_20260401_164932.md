# ContextBench: A Benchmark for Context Retrieval in Coding Agents
## Quick Facts
- **ArXiv ID:** 2602.05892
- **Source URL:** https://arxiv.org/abs/2602.05892
- **Reference count:** 40
- **Primary result:** ContextBench provides a multi-language benchmark with human-verified gold contexts and metrics (recall, precision, F1, evidence-drop) that reveal retrieval inefficiencies and the superiority of simple agents over complex scaffolding.

## Executive Summary
ContextBench addresses the lack of process-oriented evaluation for coding agents' context retrieval. It comprises 1,136 multi-language issue-resolution tasks augmented with human-verified gold contexts—minimal sufficient code regions that must be edited—and an automated framework that tracks agents' inspected code during execution. Using this benchmark, the authors evaluate four LLMs (GPT-5, Claude Sonnet 4.5, Gemini 2.5 Pro, Devstral 2) and five agents (all with GPT-5). Key findings include: sophisticated scaffolding often underperforms a simple mini-SWE-agent baseline; LLMs exhibit a recall-precision trade-off favoring recall; a large evidence drop (up to 43.5%) indicates that retrieved gold context is frequently omitted from the final patch; and balanced retrieval improves Pass@1 at lower cost. The gold contexts are robust, with high Jaccard similarity (0.951) across alternative valid patches.

## Method Summary
The authors construct ContextBench from existing repositories (e.g., SWE-bench) via deduplication and solvability filtering. Human experts then annotate each task by tracing dependencies from the gold patch, iteratively verifying via LLM patch generation and ensuring compactness. The evaluation framework instruments coding agents to log every inspected file and line range in a structured `<PATCH CONTEXT>` block before patch submission. These logs are aligned with gold contexts using tree-sitter parsers across file, block (AST definition units), and line granularities. Metrics include recall, precision, F1, efficiency (AUC-Cov), redundancy (Redun), and evidence-drop (Drop). The process enables fine-grained analysis of retrieval behavior beyond final correctness.

## Key Results
- **Mini-SWE-agent superiority:** Despite simpler scaffolding, it achieves the highest F1: file 0.634, block 0.375, line 0.312 vs. SWE-agent (0.544/0.285/0.208) and others.
- **Recall-precision imbalance:** LLMs such as GPT-5 show high block recall (0.645) but low precision (0.369), indicating broad but noisy retrieval.
- **High evidence drop:** Gemini and Devstral drop 43.5% of retrieved gold context before final patch; suggests consolidation failures.
- **Robust gold contexts:** Jaccard similarity of gold contexts across different valid patches is 0.951, confirming stability.

## Why This Works (Mechanism)
### Mechanism 1: Human-verified gold contexts as sufficient reference
Human experts annotate essential code regions by tracing dependencies from the gold patch, then cross-check with LLM-generated patches that must pass tests. The compactness check ensures minimal sufficiency. Core assumption: a small, human-curated context set reliably indicates necessary code for issue resolution. Evidence: Abstract mentions human-verified contexts; Section 2.3 details annotation and verification; high inter-annotator Jaccard (0.9518) supports robustness.

### Mechanism 2: Agent context tracing instrumentation
The framework intercepts file-observation actions, logs file paths and line ranges into structured `<PATCH CONTEXT>` blocks, and maps them to a unified tree-sitter coordinate system. This allows dynamic computation of recall/precision against gold contexts. Core assumption: agents can be modified to expose intermediate logs without altering reasoning. Evidence: Section 2.5 describes tracing; Section C documents adaptations; neighboring works also instrument agents but for different goals.

### Mechanism 3: Multi-granularity metrics reveal trade-offs
Aligning gold and agent contexts via tree-sitter enables computing overlap at file, block (definition units), and line levels. These metrics expose patterns like recall-precision trade-off and evidence drop. Core assumption: block-level definitions are semantically meaningful across languages. Evidence: Section 2.5, E define blocks; Section 3.3-3.4 show patterns (GPT-5 high recall/low precision, Claude balanced, etc.). Break condition: If blocks are not cohesive (e.g., large monolithic classes), block-level metrics become noisy.

## Foundational Learning
- **Tree-sitter parsing and AST-based alignment:** Needed to map code regions to a shared structural coordinate system (file → AST blocks → lines). Without it, granular comparisons are unreliable. Quick check: How would you define a "block" consistently across Python (functions/classes) and Java (methods/classes) using tree-sitter node types?
- **Gold context as minimal sufficient set:** Annotators trace dependencies and prune redundancies to produce a compact but sufficient reference; precision penalizes extra retrieved code. Quick check: Why might an agent retrieve code not in gold context but still helpful? How does this affect precision interpretation?
- **Agent context tracing instrumentation:** To compute recall/precision, we must know exactly which code elements the agent inspected; this requires modifying agents to log observations in a structured format. Quick check: What are two challenges in instrumenting a closed-source coding agent (e.g., via API only) to expose its intermediate code inspections?

## Architecture Onboarding
**Component map:**  
Data pipeline: Source benchmarks → Deduplication → Difficulty filtering → Expert annotation → LLM verification → Compactness check → Gold contexts.  
Evaluation engine: Agent runner (with context extraction) → Tree-sitter parser → Alignment module → Metric calculator (recall/precision/F1, AUC-Cov, Redun, Drop).  
Analysis tools: Trajectory logger, Jaccard consistency checker, Per-language splitter.

**Critical path:** Task selection → annotation → verification → agent adaptation → trajectory collection → metric computation → pattern analysis. The annotation-verification loop took ~4 months of expert time, making it the longest pole.

**Design tradeoffs:**  
- Manual annotation cost vs. scalability: 1,136 tasks at ~40 minutes each ensures quality but limits dataset size; automated extraction (e.g., from diffs) would be faster but less reliable for semantic dependencies.  
- Granularity choice: Line-level is precise but brittle to formatting; block-level balances semantics but depends on AST quality and may be noisy for large classes.  
- Agent adaptation: Forcing a strict `<PATCH CONTEXT>` output may constrain natural agent behavior; mitigated by per-agent prompt template adjustments (Section C).

**Failure signatures:**  
- High recall + low precision: Agent retrieves overly broad context (e.g., GPT-5, Agentless).  
- High evidence drop (>30%): Agent discards gold context during consolidation (e.g., Gemini, Devstral).  
- Low efficiency (AUC-Cov): Agent takes many steps to find gold context, indicating poor search strategy.

**First 3 experiments:**

## Open Questions the Paper Calls Out
- **How can gold contexts be used to actively improve coding agent performance?** The paper views gold contexts as intermediate signals but does not explore training or fine-time supervision (e.g., RL, imitation). Resolution would involve using gold contexts as reward signals or demonstrations and measuring Pass@1 gains.
- **What are the root causes of high evidence drop (up to 43.5%)?** The metric is defined and measured, but the paper does not diagnose why agents frequently discard gold-relevant context observed during exploration. Evidence could come from fine-grained trajectory analysis and interventions like persistent memory.
- **Why does sophisticated agent scaffolding underperform the simple mini-SWE-agent baseline?** The paper hypothesizes over-engineering but does not isolate which scaffold components (e.g., graph retrieval, tool orchestration) harm performance. Systematic ablations are needed.
- **Can gold context annotation be automated or semi-automated to scale beyond 1,136 tasks?** Manual annotation required ~40 min/task and four months; no scalable alternative is proposed. An LLM-assisted pipeline with active learning and human review could reduce cost.

## Limitations
- **Gold context validity:** High Jaccard consistency (0.951) supports robustness, but this holds only for the specific 1,136 tasks; may not generalize to repositories with more divergent valid solutions or ambiguous issues.
- **Instrumentation & alignment:** The framework relies on agent cooperation to emit `<PATCH CONTEXT>`; adaptations for closed-source/API agents (e.g., Claude via Anthropic API) are not detailed, possibly affecting evidence drop measurements.
- **Multi-granularity metrics:** The semantic meaningfulness of "block"-level definitions varies by language and code style; for monolithic classes, block recall may be inflated, reducing predictive power for patch utility.
