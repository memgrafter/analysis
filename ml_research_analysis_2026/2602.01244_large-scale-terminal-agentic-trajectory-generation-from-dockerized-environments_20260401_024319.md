# Large-Scale Terminal Agentic Trajectory Generation from Dockerized Environments

## Quick Facts
- **arXiv ID:** 2602.01244
- **Source URL:** https://arxiv.org/abs/2602.01244
- **Reference count:** 40
- **Primary result:** Generates 50,733 verified trajectories across 8 domains; training on this data improves Qwen2.5-Coder models by up to +20% on TB1.0 and +10% on TB2.0, with TerminalTraj-32B achieving 35.30% / 22.00% and 63% pass@16.

## Executive Summary
The paper addresses the scarcity of high-quality, executable, and verifiable terminal agent trajectories by introducing TerminalTraj, a scalable pipeline that constructs Dockerized environments from GitHub repositories, generates tasks with automatically synthesized pytest validators, and verifies agent rollouts through execution. This yields 50,733 validated trajectories spanning eight specialized domains. Training Qwen2.5-Coder models on this data yields substantial gains on the TerminalBench suite, with the 32B variant setting a new state-of-the-art and demonstrating notably steeper test-time scaling curves.

## Method Summary
TerminalTraj begins by crawling GitHub repositories and filtering them using a learned reward model (ScoreModel) to prioritize those likely to build successfully as Docker images. Approximately 32,325 Docker images are constructed. For each image, the pipeline extracts relevant files and prompts a powerful LLM (Qwen3-Coder-480B) to generate a task query and an accompanying pytest-based validator. An agent scaffold (Terminus-2) then performs multiple independent rollouts (k=4) per task; only trajectories that cause the pytest suite to pass are retained. These verified (query, trajectory) pairs form an SFT dataset used to train smaller, efficient models (Qwen2.5-Coder). The use of Docker ensures executability, while the pytest validators provide a deterministic, execution-grounded quality signal.

## Key Results
- **Scale:** 50,733 verified trajectories generated from 32,325 Docker images across eight domains.
- **Benchmark improvement:** Training on TerminalTraj improves Qwen2.5-Coder models by up to +20% on TB1.0 and +10% on TB2.0.
- **State-of-the-art:** TerminalTraj-32B achieves 35.30% on TB1.0 and 22.00% on TB2.0, with a pass@16 of 63%, indicating strong test-time scaling.

## Why This Works (Mechanism)

### Mechanism 1: Model-based repository scoring
Replaces heuristic filtering (e.g., star counts) with a learned reward model (ScoreModel) that predicts repository completeness and executability. By discarding low-scoring repos (τ=0.2), the pipeline nearly doubles the Docker build success rate (19.5% vs 9% random), directly addressing the executability bottleneck. Core assumption: repository-level code quality signals correlate with build feasibility. Break condition: if ScoreModel fails to generalize to new languages/structures, the correlation degrades and image yield drops.

### Mechanism 2: Instance-specific executable validation
For each task, the system synthesizes a pytest suite that checks for correct environmental side effects (file creation, output content, process state) rather than relying on text matching or LLM judges. This provides a binary, execution-grounded signal that filters out trajectories failing to produce the required real-world state changes. Core assumption: correct solutions leave deterministic, checkable footprints. Break condition: tasks with probabilistic outcomes or multiple valid end states may be incorrectly rejected.

### Mechanism 3: Diversity-driven scaling
Exposure to 32,325 distinct Docker images across eight domains forces the model to learn general terminal principles (command-line interaction, state management, error recovery) rather than overfitting to a narrow distribution. This diversity yields steeper test-time scaling curves (63% pass@16) and removing any domain consistently harms performance, confirming that broad coverage of tool-use and system-level interactions is essential. Core assumption: generalizable competency requires diverse, executable problem-solving contexts. Break condition: if additional environments do not introduce novel interactions, marginal benefits saturate.

## Foundational Learning

### Dockerized Environment Isolation
- **Why needed:** The entire pipeline relies on reproducible, isolated execution contexts. The agent must interact with a real terminal whose state is confined to a specific Docker image; without this, execution-based verification is impossible and trajectories are not grounded.
- **Quick check:** If a task requires `ffmpeg` and the Docker image lacks it, the command `ffmpeg -i input.mp4 output.gif` fails with "command not found", causing trajectory verification to fail unless the agent installs it first (which may be out-of-scope).

### Executable Verification (pytest as oracle)
- **Why needed:** Moves beyond LLM-as-judge or fuzzy text matching to provide a deterministic, automated pass/fail signal for every trajectory. This is the linchpin for creating a high-signal training dataset at scale.
- **Quick check:** For a task requiring a file `/results/output.csv` with specific content, a validator that only checks `os.path.exists('/results/output.csv')` is insufficient—it would pass an empty or incorrect file. The validator must read and compare the content to a golden reference.

## Architecture Onboarding

### Component map
Data Sources Collection (GitHub crawler, domain filters, context gatherer) → Docker Image Curation (ScoreModel + Docker build service) → Instance Generation (Qwen3-Coder-480B) → Trajectory Rolling & Verification (Terminus-2 agent + pytest executor) → Training (SFT with Megatron-LM)

### Critical path
1. Crawl & filter repositories  
2. Score repos with ScoreModel  
3. Build Docker images  
4. For each image, extract files & generate (query, pytest)  
5. Roll out agent trajectories  
6. Execute pytest  
7. Keep only passing trajectories  
8. Pack into SFT dataset

### Design tradeoffs
- **Score threshold (τ=0.2):** Lower threshold increases diversity but reduces build success (more wasted compute); higher threshold does the opposite. Chosen empirically.
- **Trajectory sampling (k=4):** More samples increase data yield but linearly raise compute cost; saturation observed at k=4.
- **Validator design:** Executable pytest is high-precision but may suffer low recall if overly strict; LLM judges are high-recall but low-precision.

### Failure signatures
- High repo rejection rate → ScoreModel mis-calibrated or corpus too noisy.
- Low Docker build success rate (<10%) → Threshold τ too low or build environment instability.
- Low verified trajectory rate (<2%) → Tasks too difficult, weak rollout agent, or buggy/strict validators.
- Ablation sensitivity negligible for a domain → That domain's data quality or relevance may be low.

### First 3 experiments
1. **Validate ScoreModel:** Sample 100 repos above τ=0.5 and 100 below τ=0.2; manually attempt Docker builds. Expect >15% success for high-score group vs <5% for low-score.
2. **Sanity-check validator generation:** Inspect 50 random (query, pytest) pairs; manually verify pytest correctly tests the query's requirements and runs against a known-correct solution with 100% pass.
3. **Agent rollout sanity:** Use Terminus-2 with a strong agent (e.g., GPT-4) on 10 generated instances; confirm trajectories are coherent and the `task_complete` flag aligns with pytest passing.

## Limitations
- ScoreModel may not generalize to unseen repository languages or structures, lowering build yields outside its training distribution.
- Executable pytest validators can be overly strict, incorrectly rejecting valid but non-standard solutions, or fail for tasks with probabilistic outcomes.
- The massive Docker image construction pipeline requires significant compute and storage, posing reproducibility challenges for smaller labs.

## Confidence
- ScoreModel effectiveness: High
- Executable validation: High
- Diversity-driven scaling: High
- Benchmark gains: High

## Next Checks
1. **ScoreModel generalization:** Evaluate on a held-out set of repositories from languages not in training (e.g., Rust, Go) and compare build success rate to random selection.
2. **Validator audit:** Manually inspect 200 randomly sampled pytest suites to confirm they correctly and fully capture task success criteria without false negatives.
3. **Diversity scaling ablation:** Train models on progressively larger environment subsets (5k, 10k, 20k, 32k images) and measure pass@k to identify saturation points and marginal returns.
