# AnalyticsGPT: An LLM Workflow for Scientometric Question Answering

## Quick Facts
*   **arXiv ID:** 2602.09817
*   **Source URL:** https://arxiv.org/abs/2602.09817
*   **Reference Count:** 17
*   **Primary Result:** A two-stage LLM planning workflow with rule-based query assembly significantly outperforms a naive RAG baseline on expert-evaluated Coverage and Validity for complex scientometric queries, while nearly eliminating critical data retrieval errors.

## Executive Summary
AnalyticsGPT introduces a system for Scientometric Question Answering (SQA), a task requiring accurate entity recognition and complex, multi-step database queries over academic metrics. It employs a sequential LLM workflow centered on a two-stage planning module (High-Level and Detailed Planning) to generate robust, executable data retrieval plans. Retrieved data from a proprietary analytics platform is then synthesized into a final, referenced response. Evaluated by subject matter experts and an LLM jury on 84 questions, AnalyticsGPT achieves significantly higher scores in Coverage and Validity compared to a naive RAG baseline and reduces critical data retrieval failures from five to one, though at the cost of increased latency.

## Method Summary
The system is a linear pipeline of five modules. First, the High-Level Planning Module (HLPM) performs named-entity recognition and decomposes the user query into a tool-agnostic outline. The Detailed Planning Module (DPM) then translates this outline into a concrete, step-by-step plan with precise tool parameters, guided by method contracts and few-shot examples. The Action Module (AM) executes these steps, handling dependencies and using a rule-based approach to assemble syntactically correct database queries from the DPM's structured parameters, thereby avoiding direct LLM-generated query strings. The Writing Module (WM) synthesizes the final, referenced answer, and a Visualization Module (VM) can optionally generate plots. The pipeline uses GPT-4o for the DPM and GPT-4o Mini for other modules, interfacing with a proprietary platform via three tools: `resolve_entity`, `search_articles`, and `faceted_search`.

## Key Results
*   **Significant Quality Gains:** Outperforms a naive RAG baseline in expert-evaluated **Coverage** (4.40 vs 4.06) and **Validity** (4.56 vs 4.19) on a 5-point scale.
*   **Improved Reliability:** Reduces critical data retrieval errors from **5 to 1** across 84 questions.
*   **Trade-off:** Increases average API time due to the planning overhead (**20.9s vs 14.2s**), while maintaining comparable response length.

## Why This Works (Mechanism)
### Mechanism 1: Two-Stage Planning for Robust Executable Plans
*   **Claim:** A two-stage planning module (High-Level and Detailed) improves the robustness and executability of data retrieval plans for complex scientometric questions.
*   **Mechanism:** The HLPM first decomposes the query into an abstract, tool-agnostic outline and performs entity resolution. The DPM then elaborates this outline into a concrete, step-by-step plan with precise tool parameters and dependencies, using method contracts and few-shot examples to ensure correct syntax.
*   **Core Assumption:** Separating abstract task understanding from low-level implementation details reduces cognitive load on the LLM and mitigates syntax/parameterization errors.
*   **Evidence Anchors:** Paper sections 3.3 & 3.4 describe HLPM and DPM as distinct steps. Section 4.5 shows the baseline's 5 critical errors included parameterization mistakes, which AnalyticsGPT mitigated.
*   **Break Condition:** If the HLPM misidentifies core entities or intents, the DPM's plan is fundamentally flawed, leading to incorrect data retrieval regardless of syntactic correctness.

### Mechanism 2: Rule-Based Query Assembly for Reliability
*   **Claim:** A rule-based assembly of database queries from LLM-generated parameters prevents syntax errors and ensures compliant API calls, increasing system reliability.
*   **Mechanism:** The Action Module does not pass LLM-generated strings directly to the database. Instead, it uses a deterministic wrapper to construct the final query from the DPM's structured parameters (tool name, subtask, parameters), handling common LLM mistakes (e.g., identifier confusion) before execution.
*   **Core Assumption:** LLMs are prone to producing syntactically invalid or non-compliant query strings for complex, custom APIs; a deterministic wrapper enforces correctness.
*   **Evidence Anchors:** Section 3.5 states the rule-based approach "facilitates the formulation of syntactically-correct queries." Section 4.5 attributes the baseline's parameterization errors to conflating identifier types (Topics vs. Subject Areas).
*   **Break Condition:** If the DPM provides parameters that are logically incorrect or missing (e.g., wrong entity type ID), the rule-based assembler cannot fix the semantic error, only the syntax.

### Mechanism 3: LLM Jury for More Robust Evaluation
*   **Claim:** Using an LLM "jury" with confidence-weighted pooling provides a more robust and less biased assessment of nuanced response quality than a single LLM judge.
*   **Mechanism:** Multiple, diverse LLM evaluators score each response. Their scores are pooled using a confidence-weighted function (falling back to majority vote), aiming to mitigate individual model biases and increase agreement with human judgments.
*   **Core Assumption:** A panel of models averages out idiosyncratic biases of any single LLM judge, yielding evaluations that better align with human expert judgment for complex rubrics.
*   **Evidence Anchors:** Section 4.2 adopts the jury method to "mitigate intra-model bias." However, Table 3 shows low agreement (often near-zero kappa) between the LLM jury and SMEs, while SME-SME agreement was higher, suggesting the jury's efficacy for this specific task is unproven.
*   **Break Condition:** If all jury models share a common bias (e.g., leniency on verbosity), the jury method could amplify that bias. Its efficacy is contingent on model diversity.

## Foundational Learning
*   **Concept: Retrieval-Augmented Generation (RAG)**
    *   *Why needed here:* The system must answer questions using data from a proprietary, non-parametric database. RAG connects the LLM's reasoning to this external, factual source.
    *   *Quick check:* "Why can't the LLM just 'know' the answers to scientometric questions from its training data, and what problem does RAG solve in this context?"
*   **Concept: Agentic Workflow Design (Planning & Tool Use)**
    *   *Why needed here:* SQA requires multi-step data retrieval with dependencies (e.g., find author ID, then their papers, then co-authors). The system is designed as a sequential agent that plans and executes tool calls.
    *   *Quick check:* "What is the difference between a naive RAG system (tool call + generation) and the agentic workflow presented here, in terms of handling a question like 'Who are the most cited co-authors of the top 5 authors in Topic X?'"
*   **Concept: LLM-as-Judge with Aggregation**
    *   *Why needed here:* Evaluating nuanced qualities like "Validity" and "Coverage" is subjective. Using multiple LLMs with a pooling strategy is the scalable alternative to human evaluation.
    *   *Quick check:* "What are two specific risks of using a single, generic LLM (like GPT-4) as a judge for a niche task like SQA, and how does a 'jury' method attempt to address them?"

## Architecture Onboarding
*   **Component map:** User Input -> HLPM -> (Entity Resolution) -> DPM -> AM -> WM -> VM. Tools: `resolve_entity`, `search_articles`, `faceted_search`.
*   **Critical path:** The sequence **HLPM → DPM → AM** is the irreplaceable core. A failure in the DPM's plan (missing steps, wrong dependencies) cannot be recovered by later modules. WM and VM are output renderers dependent on AM's success.
*   **Design tradeoffs:**
    1.  **Planning Depth vs. Latency:** The two-stage planning increases API time (20.9s vs 14.2s baseline) but reduces critical retrieval errors (1 vs 5). This trades speed for reliability.
    2.  **Determinism vs. Flexibility:** The rule-based query assembly in AM sacrifices potential LLM query optimization for guaranteed syntactic correctness and compliance.
    3.  **Abstraction vs. Control:** Encapsulating low-level API endpoints into three high-level tools simplifies tool selection for the LLM but hides granular filtering options from the planner.
*   **Failure signatures:**
    *   **HLPM Failure:** NER misses an entity (e.g., tags "University of Tokyo" as a location, not an `Institution`), or the outline is too vague. *Symptom:* DPM plan omits a required retrieval step.
    *   **DPM Failure:** Plan includes logically impossible dependencies (e.g., step 2 depends on data from step 5) or specifies invalid parameter values (e.g., using a `Topic` ID where a `SubjectArea` ID is required). *Symptom:* AM execution fails or returns no/incorrect data.
    *   **AM Failure:** Rule-based assembler receives a parameter value beyond its handling logic (e.g., an unexpected date format). *Symptom:* API call returns an error.
    *   **WM Failure:** LLM generates claims not supported by the retrieved data ("hallucinated references") or misinterprets metrics. *Symptom:* Low SME Validity/Verifiability scores despite correct data retrieval.
*   **First 3 experiments:**
    1.  **HLPM/DPM Unit Test:** Feed a fixed set of ~20 diverse SQA questions. Measure: (a) % of questions where NER correctly identifies ALL supported entities, (b) % of DPM-generated plans that are logically sound and complete (by human inspection of plan steps against question requirements).
    2.  **End-to-End Retrieval Accuracy:** Execute the full pipeline (HLPM→DPM→AM) on the same question set. For each, manually execute the correct query on the database. Compare the actual retrieved data against the system's retrieved data. **Key metric:** Critical Omission Rate (as defined in paper: no data retrieved when correct query would return data).
    3.  **Parameter Robustness Stress Test:** Modify 50 real user questions to include ambiguous entity names (e.g., "MIT" could be Massachusetts Institute of Technology or other institutions) or temporal modifiers ("recent", "last 5 years"). Measure system's ability to correctly resolve these to specific IDs or year ranges via the plan/dependent steps. Track failure mode (NER error vs. DPM planning error).

## Open Questions the Paper Calls Out
*   **Open Question 1: How can an automated, scalable evaluation framework for SQA be developed that reliably aligns with subject matter expert (SME) judgments?** Basis: Future Work states this need. Why unresolved: Current evaluation relies on costly SME scoring and an LLM jury that showed low agreement with humans. Evidence needed: A proposed automated metric (e.g., based on entailment) demonstrating strong correlation (Spearman’s ρ > 0.8) with SME scores across a held-out set.
*   **Open Question 2: Do large reasoning models (e.g., o1, Claude 3.7 Sonnet) improve the quality of detailed plan generation in the DPM compared to standard instruction-tuned models like GPT-4o?** Basis: Future Work mentions investigating large reasoning models. Why unresolved: No model comparison was performed. Evidence needed: A controlled experiment measuring plan executability and downstream response quality when swapping the DPM model.
*   **Open Question 3: What causes the persistent low agreement between LLM juries and human SMEs when evaluating nuanced SQA response criteria like Verifiability and Validity?** Basis: Table 3 shows low/negative kappa between jury and SMEs, while SME-SME agreement is higher. Why unresolved: The root cause of misalignment (e.g., criterion misunderstanding, verbosity bias) is unclear. Evidence needed: A qualitative error analysis comparing LLM jury vs. SME rationales.
*   **Open Question 4: Can the system's handling of nuanced, non-literal user requests (e.g., "emerging" topics) be improved without sacrificing robustness on factual queries?** Basis: Future Work lists "translation of nuanced user requests" as an area for improvement; Failure Modes note descriptive temporal modifiers were often lost. Why unresolved: The current pipeline literalizes queries for database parameters, with no mechanism for contextual interpretation of vague qualifiers. Evidence needed: An augmented pipeline with an interpretation module and A/B testing showing improved handling of vague questions without degrading factual query performance.
*   **Open Question 5: What is the individual contribution of the High-Level Planning Module (HLPM) versus the Detailed Planning Module (DPM) to the overall reduction in critical data retrieval errors?** Basis: Limitations state a more detailed ablation study is needed. Why unresolved: The two-stage planning is central but not isolated; it's unknown whether HLPM's NER/outline or DPM's parameterization is more critical. Evidence needed: An ablation study disabling HLPM or DPM individually, measuring critical error rates and plan executability on a held-out set.

## Limitations
*   **Proprietary Barrier:** Exact API specifications, data schema, and complete prompt templates are undisclosed, blocking faithful replication and limiting generalizability to public scholarly APIs.
*   **Evaluation Scale & Alignment:** Study size is small (84 questions). The LLM jury shows low agreement with SMEs and is systematically more lenient, raising concerns about the robustness of the reported gains and the jury's utility for this task.
*   **Operational Cost:** The two-stage planning introduces a significant latency increase (~47% longer API time) compared to the baseline, which may hinder real-world deployment.

## Confidence
*   **Two-stage planning improves robustness:** Medium. Error reduction is evident but the component is not isolated; break condition shows vulnerability to HLPM failures.
*   **Rule-based query assembly prevents syntax errors:** Medium. Directly addresses observed parameterization errors but cannot correct logically invalid parameters from the DPM.
*   **LLM jury provides reliable evaluation:** Low. Persistent low SME agreement and systematic leniency question its reliability for nuanced SQA metrics.

## Next Checks
1.  **Ablate HLPM:** Implement a single-stage direct planning baseline (no HLPM decomposition). Compare plan executability and critical retrieval error rates on a held-out SQA question set.
2.  **Assembly method comparison:** For identical, validated DPM plans, vary the AM between rule-based query construction and direct LLM‑generated query strings. Measure syntax error frequency and successful data retrieval.
3.  **Jury vs. human correlation:** Expand human evaluation to ≥200 diverse questions. Compute Spearman correlation of LLM jury scores with human judgments, and compare to a single LLM judge; test if jury significantly improves alignment.
