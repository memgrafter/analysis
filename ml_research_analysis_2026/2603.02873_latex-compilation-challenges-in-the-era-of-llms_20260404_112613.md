# LaTeX Compilation: Challenges in the Era of LLMs
## Quick Facts
- **arXiv ID:** 2603.02873
- **Source URL:** https://arxiv.org/abs/2603.02873
- **Reference count:** 40
- **Primary result:** Mogan STEM’s .tmu format enables显著的 incremental compilation speedups (>10x) and superior LLM task utility (+20-25 points) versus LaTeX by replacing batch macro expansion with an explicit tree-based model and on-demand plugin loading.

## Executive Summary
This paper identifies fundamental architectural limitations in LaTeX—its batch compilation model, high token entropy from linear macro expansion, and a fragile, multi-pass ecosystem—as critical bottlenecks for efficient LLM-assisted scientific writing. The authors propose Mogan STEM, a WYSIWYG structured editor that uses an explicit tree-based document format (.tmu) with on-demand plugin loading, eliminating the need for global recompilation on local edits. Experimental results demonstrate that Mogan accelerates full compilation (up to ~4x) and dramatically speeds up incremental updates (often >10x). For LLM-centric tasks like structure location, file merging, and error debugging, .tmu files yield significantly higher utility scores (e.g., +20-25 points) due to lower information entropy and grammatical consistency. Supervised fine-tuning with Qwen2.5-7B shows faster convergence and lower loss (0.4 vs. 0.7) on formula generation from .tmu data. The paper advocates for adopting .tmu in future LLM training to improve efficiency and reliability.

## Method Summary
The evaluation employs three controlled experiments comparing LaTeX (.tex) and Mogan (.tmu) formats. First, compilation and rendering latency are measured on six arXiv papers (full and after incremental edits) using identical hardware. Second, four state-of-the-art LLMs perform structured tasks (locating document elements, merging style files, debugging errors); utility scores combine correctness and token efficiency. Third, Qwen2.5-7B is fine-tuned via LoRA on 1000 formulas in each format to predict suffixes, tracking cross-entropy loss. The .tmu representation is generated from LaTeX sources via Mogan’s importing engine, ensuring identical visual output after rendering.

## Key Results
- Mogan reduces full compilation time by up to ~4x and accelerates incremental updates by >10x for typical research documents.
- LLMs achieve higher utility scores (+20-25 points) on structure location, file merging, and error debugging when processing .tmu files versus .tex.
- Formula completion fine-tuning converges faster and to a lower loss (0.4 vs. 0.7) on .tmu data, attributed to lower token entropy and deterministic syntax.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** LaTeX’s batch compilation model causes inefficient incremental updates because its unidirectional, state-free execution cannot localize re-computation.
- **Mechanism:** Linear macro expansion couples parsing, semantic interpretation, and typesetting into a single irreversible pass. Any edit requires re-reading the entire input stream, re-expanding macros, and re-calculating global layout (e.g., pagination), as intermediate state is stored only in external auxiliary files (e.g., `.aux`, `.toc`) for later passes.
- **Evidence anchors:** Abstract highlights “batch compilation model” and “accelerates incremental updates (>10x).” Section 3.1.1 details unidirectional flow and shows a local edit (deleting `\lipsum`) forces full recompilation due to cascading pagination changes. Neighbor paper “Inconsistencies in TeX-Produced Documents” (158740) corroborates ecosystem fragility stemming from this model.
- **Break condition:** If Mogan still required full recompilation for local edits, the mechanism would be falsified. Benchmark (Fig 8) shows Mogan avoids this.

### Mechanism 2
- **Claim:** LaTeX’s linear, verbose source code and syntactic redundancy create high token entropy, reducing learnability and utility for LLMs in structure-sensitive tasks.
- **Mechanism:** Multiple valid surface forms (e.g., `\frac{a}{b}` vs. `{a \over b}`) and macro-based semantic coupling increase unpredictability of next-token probabilities. LLMs must learn a noisy mapping from syntax to rendered semantics, increasing training cost and error rates in tasks requiring precise structural understanding.
- **Evidence anchors:** Abstract states .tmu yields higher utility scores due to “lower information entropy.” Section 6.3 shows fine-tuning Qwen2.5-7B on Mogan S-expressions converges to 0.4 loss vs. 0.7 for LaTeX, attributed to “lower information entropy” and “grammatical consistency.” Section 6.2 (Figs 9–11) documents consistent LLM utility advantages for .tmu.
- **Break condition:** Equivalent LLM performance on equal data would falsify the entropy hypothesis. Results oppose this.

### Mechanism 3
- **Claim:** LaTeX’s ecosystem fragility (multiple engines, package conflicts, multi-pass workflows) increases cognitive load and error rates, hampering LLM-assisted workflows by complicating the execution environment and log interpretation.
- **Mechanism:** Divergent engines (pdfLaTeX, XeLaTeX, LuaLaTeX) have differing font, encoding, and package support (Table 4). Features like bibliographies require external tools (BibTeX vs. Biber) and multiple compilation passes, creating “compilation rituals” and non-deterministic outputs that hinder automated error diagnosis and consistent generation.
- **Evidence anchors:** Abstract lists “fragile ecosystem” as a limitation. Section 3.2 details compatibility dilemmas (e.g., emoji requiring LuaLaTeX) and tool selection cognitive load. Section 3.3 describes multi-pass compilation as a “fragile stopgap.” Neighbor paper on cross-engine output differences corroborates.
- **Break condition:** A single, fully compatible engine with deterministic single-pass compilation would weaken the argument. Current trends (Fig 1’s growing ISO size, Table 4 differences) show the opposite.

## Foundational Learning
- **Concept: Tree-based document representation (vs. linear macro stream)**
  - *Why needed:* Mogan’s core innovation is an explicit structural tree (e.g., `(frac "1" "2")`) vs. LaTeX’s `\frac{1}{2}`. This enables localized error reporting, fast incremental updates, and simpler LLM parsing.
  - *Quick check:* Why does deleting an image in Mogan only re-render its leaf node, while the same edit in LaTeX may repaginate the entire document?

- **Concept: Token entropy in structured vs. verbose markup**
  - *Why needed:* The paper’s fine-tuning results hinge on .tmu’s lower entropy. Synonymous LaTeX commands (e.g., `\frac` vs. `\over`) increase prediction uncertainty for LLMs.
  - *Quick check:* Give two LaTeX snippets that render identically but have different token sequences. Why would an LLM find the second harder to predict?

- **Concept: Batch vs. incremental compilation models**
  - *Why needed:* Performance benchmarks (Figs 7–8) and WYSIWYG claims depend on this distinction. Batch processes the whole document per pass; incremental updates only changed subtrees.
  - *Quick check:* What LaTeX feature (e.g., cross-references) forces multi-pass compilation, and how does Mogan avoid it?

## Architecture Onboarding
- **Component map:**  
  Mogan STEM: Tree-parser -> Rendering engine (parallel subtree redraw) -> Plugin loader (on-demand activation) -> WYSIWYG front-end.  
  LaTeX: Macro expander (linear, stateful) -> Typesetting engine (batch) -> External toolchain (BibTeX, MakeIndex) -> Editor-agnostic source model.
- **Critical path for “edit a formula and see result”:**  
  Mogan: Edit tree node -> local subtree re-render -> immediate visual update.  
  LaTeX: Edit source -> full macro expansion -> typesetting -> multiple passes -> external tool calls -> PDF generation.
- **Design tradeoffs:**  
  Mogan: Larger in-memory tree, fast local updates, simpler mental model, heavy initial install, minimal runtime deps.  
  LaTeX: Stateless source files, fragile multi-pass compilation, tiny source but huge ecosystem (TeX Live ~6GB), universal compatibility but engine-dependent behavior.
- **Failure signatures:**  
  LaTeX: “Runaway argument?” far from missing brace; `??` for cross-references after one pass; pagination shifts after minor edits; engine-specific failures (e.g., `fontspec` with pdfLaTeX).  
  Mogan: Localized rendering error only in affected subtree; no global cascade; clear error at tree-node level; no multi-pass needed.
- **First 3 experiments:**  
  1. Benchmark compilation/rendering time (Section 6.1): Time full and incremental updates on 6 arXiv papers; expect Mogan faster on incremental (Fig 8).  
  2. LLM task utility scoring (Section 6.2): Test 4 LLMs on structure location, merging, debugging; expect .tmu higher utility (Figs 9–11).  
  3. Fine-tuning convergence (Section 6.3): SFT Qwen2.5-7B on 1000 formulas in both formats; expect lower loss for .tmu (Fig 12).

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How does .tmu-based LLM training scale across diverse model architectures (decoder-only vs. encoder-decoder) and larger, more varied scientific corpora beyond the 1000-formula dataset?
- **Basis:** The authors “launch an appeal for larger experiments on LLM training using the .tmu format” based on initial Qwen2.5-7B results.
- **Why unresolved:** Only a single-model, small-scale proof-of-concept is presented. Generalization to other model families, multi-modal LLMs, and large-scale heterogeneous academic datasets is untested.
- **Resolving evidence:** Ablation studies across multiple foundational models (GPT, Claude, Llama) trained on millions of .tmu documents from diverse scientific domains, measuring convergence speed, final loss, and downstream task performance.

### Open Question 2
- **Question:** Which specific structural properties of .tmu (explicit tree tags, functional symbols, lack of semantic ambiguity) most drive LLM performance gains, and can they be isolated and quantified?
- **Basis:** Gains are attributed to “lower information entropy” and “grammatical consistency,” but no decomposition of atomic features’ contributions.
- **Why unresolved:** Experiments compare end-to-end .tmu vs. .tex without controlled ablations. It’s unclear if benefits stem from deterministic syntax, reduced token variance, or explicit tree navigability.
- **Resolving evidence:** Controlled experiments selectively disabling .tmu features or simulating them in LaTeX (e.g., injecting AST tags, normalizing commands), measuring changes in LLM utility and token efficiency.

### Open Question 3
- **Question:** Does LaTeX-to-.tmu conversion (via Mogan’s importing engine) introduce semantic loss/distortion that inflates .tmu’s performance benefits, or does it preserve full equivalence?
- **Basis:** Paper claims identical rendering output and conversion guarantees, but does not analyze whether the .tmu tree perfectly captures all LaTeX semantics (e.g., recursive macros, package-specific behaviors).
- **Why unresolved:** Identical rendering does not guarantee a lossless, one-to-one mapping at the token/tree level. Conversion might normalize ambiguities, making .tmu artificially “easier.”
- **Resolving evidence:** Formal/empirical conversion fidelity analysis: (1) specification of mapping rules, (2) testing on pathological LaTeX examples (recursive macros, engine-specific code), (3) training LLMs on original .tmu documents vs. converted ones.

### Open Question 4
- **Question:** How robust are Mogan’s incremental update and error-localization advantages under real-world, large-scale collaborative editing with concurrent modifications, vs. batch-compiled LaTeX with modern tooling (Overleaf + git)?
- **Basis:** Paper touts localized edits and clear errors, but benchmarks are single-user; no evaluation of collision handling, merge conflicts, or complex packages (TikZ, custom cls) in multi-author settings.
- **Why unresolved:** LaTeX has mature version control/diff tools. Mogan’s tree may enable better semantic merges, but this is untested. Incremental speed benefits might diminish with tree serialization costs or plugin resolution during concurrent edits.
- **Resolving evidence:** User studies or simulations measuring conflict resolution time, correct merge rates, and incremental compilation latency in multi-user tasks on identical complex documents using Mogan vs. LaTeX + modern tooling.

## Limitations
- Timing results (Mechanism 1) may be sensitive to disk I/O (SSD vs. HDD, filesystem) and OS differences; paper specifies hardware but not OS disk configurations.
- LLM utility scores (Mechanism 2) depend on an undefined “token usage” metric (inclusion of tool calls, thinking tokens); exact prompt templates and counting rules are unspecified.
- Fine-tuning data (Mechanism 2) assumes a balanced formula corpus; category dominance or conversion equivalence failures (e.g., `\frac` vs. `\over`) could skew loss convergence.
- Mogan’s LaTeX import may not fully preserve semantics for complex papers (e.g., recursive macros), potentially inflating incremental update gains if unsupported commands are stripped.

## Confidence
- **Mechanism 1 (Incremental Updates):** Medium. Benchmarks are specific but I/O and plugin overhead could alter real-world performance.
- **Mechanism 2 (LLM Utility/Entropy):** Medium. Loss curves and scores support the claim, but token accounting and data diversity are uncontrolled.
- **Mechanism 3 (Ecosystem Fragility):** High. Engine differences and multi-pass needs are well-documented and observable.
