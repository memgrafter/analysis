# CliffSearch: Structured Agentic Co-Evolution over Theory and Code for Scientific Algorithm Discovery
## Quick Facts
- arXiv ID: 2604.01210
- Source URL: https://arxiv.org/abs/2604.01210
- Reference count: 40
- Primary result: In transformer hyper-connection evolution, code_only discovered a Poincaré‑Givens hybrid with validation loss 0.00733, far outperforming the best theory+code result (1.6935).

## Executive Summary
CliffSearch is a novel framework that uses large language models (LLMs) as agents to drive an evolutionary process for discovering scientific algorithms. Individuals are structured artifacts comprising a prose summary, optional theoretical description, and executable code. Two modes are supported: `theory+code` (both fields) and `code_only` (theory omitted, summary carries design rationale). Evolution relies on LLM-based reviewers that enforce correctness and originality as hard gates, alongside benchmark performance. Mutation is split into exploration (cross-domain novelty) and correction (evidence-guided repair). Experiments across three tasks demonstrate that code_only mode can yield superior algorithmic discoveries, highlighting the trade-off between interpretability and token efficiency. The work showcases the potential of agentic co-evolution for automated scientific innovation.

## Method Summary
CliffSearch maintains a population of node artifacts, each a JSON object with fields `summary_md`, `theory_content`, and `code_content`. Two artifact modes exist: `theory+code` (both non-empty) and `code_only` (theory empty). The evolutionary loop is orchestrated by a runtime that invokes LLM agents for review, pair selection, crossover, and mutation. Each generation, every node is benchmarked on a task-specific adapter, producing a primary metric. A reviewer LLM then evaluates the node’s correctness (implementation matches claims) and originality (non-obvious improvement), outputting numeric scores. Winners satisfy: correctness ≥ 4, originality ≥ 4, and directional score > generation median. Winners become eligible as parents. The pair selector chooses two parents based on summary-only descriptions; crossover produces child nodes. Non-winners are routed to mutation: correct but unoriginal nodes undergo exploration mutation (importing mechanisms from other domains), while incorrect or weak nodes undergo correction mutation (targeted repair). The next generation is composed of elite copies, crossover children, and mutation children, filling to the population size. This cycle repeats for a fixed number of generations, with all artifacts persisted.

## Key Results
- Transformer hyper-connection evolution: `code_only` discovered a Poincaré‑Givens hybrid achieving 0.00733 validation loss, while the best `theory+code` result was 1.6935.
- Optimizer discovery on a fixed nanoGPT stack under the `short_json` prompt bundle yielded valid non‑seed optimizers (e.g., MuonCausalMomentum) with loss 1.7782; the stricter `workflow_v2` bundle reduced discovery rates.
- Native optimizer ablation on classification tasks confirmed `code_only` superiority: the top node CautiousAdamProj reached 0.4261 loss, and larger populations increased the count of reviewer‑valid discoveries.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Structured artifacts (summary_md, theory_content, code_content) enable both scientific interpretability and creative ideation; even in code_only mode the summary_md preserves design principles while freeing token budget for code.
- **Mechanism**: The node schema is fixed across modes. In code_only, theory_content is set empty but summary_md remains required and records the intended mechanism and design principles.
- **Core assumption**: A concise prose summary is sufficient to convey the node’s intended mechanism and design rationale for review and selection, without requiring a formal theory file.
- **Evidence anchors**:
  - [abstract] "each node is a structured scientific artifact, instantiated in either theory+code or code_only mode"
  - [section 3.2] "In code_only, theory_content is intentionally empty, but summary_md remains required and records the intended mechanism and design principles"
  - [corpus] Related frameworks (OR-Agent, InternAgent) use structured hypotheses but do not explicitly separate theory and code; CliffSearch’s split is distinctive.
- **Break condition**: If summary_md is vague or misleading, review quality degrades; additionally, without theory_content, formal correctness checks are limited to code behavior.

### Mechanism 2
- **Claim**: Making reviewer correctness and originality outputs first-class selection gates (hard constraints) prevents benchmark-score-only optimization and ensures scientifically valid, non-redundant discoveries.
- **Mechanism**: Winner rule requires correct(n)=1, original(n)=1, and directional score s(n) > median(P_g). Only winners enter the pairing pool; non-winners are routed to mutation.
- **Core assumption**: Benchmark metrics are necessary but insufficient for scientific discovery; correctness (implementation matches claims) and originality (non-obvious improvement) are essential filters.
- **Evidence anchors**:
  - [abstract] "reviewer judgments of correctness and originality are first-class selection gates alongside optimization of the benchmark metric"
  - [section 3.4] Formal winner definition with correctness and originality gates.
  - [section 4.2] Workflow-v2 reviewer downgraded low-loss optimizers that were literature-adjacent, demonstrating gating beyond loss.
- **Break condition**: If reviewer reliability is low (LLM inconsistency), gates may reject valid nodes or admit invalid ones; the paper notes this as a limitation.

### Mechanism 3
- **Claim**: Splitting mutation into exploration (adjacent-domain novelty transfer) and correction (evidence-guided repair) pathways improves both discovery potential and population stability.
- **Mechanism**: Routing: correct & non-original → exploration mutation; incorrect or weak-score → correction mutation. Exploration imports ideas from other domains; correction performs minimal targeted fixes.
- **Core assumption**: Exploration and correction have conflicting objectives (broad innovation vs. precise stabilization); a single mutation operator cannot optimize both.
- **Evidence anchors**:
  - [abstract] "mutation is split into exploration and correction pathways with distinct objectives"
  - [section 3.3] Figure 2 and detailed triggers/goals.
  - [section 4.1] Correction mutation fixed dtype bugs in HC seeds; exploration mutation produced Givens and Poincaré families.
- **Break condition**: If routing thresholds are poorly tuned, exploration may flood the population with invalid nodes, or correction may be too conservative to recover useful candidates.

## Architecture Onboarding
**Component map (plain text)**

Task contract -> Runtime -> Node artifact
Node artifact -> Benchmark adapter (executes code_content) -> Runtime (metrics, logs)
Node artifact -> Reviewer agent -> Runtime (correctness, originality, score)
Runtime -> Winner selection (applies correctness/originality gates + score > median)
Winner set -> Pair selector agent -> Crossover agent -> children
Non-winners -> (Exploration mutation agent OR Correction mutation agent) -> children
Runtime composes next generation (elite + crossover children + mutation children) -> repeat

**Critical path**
1. Initialize population from seeds + exploration children if needed.
2. For each node: run benchmark → review → store results.
3. Determine winners via correctness/originality gates + score > median.
4. Pair selector chooses parent pairs from winners (summary-only view).
5. Crossover creates children from pairs.
6. Non-winners routed to exploration or correction mutation.
7. Compose next population: elite copies, crossover children, mutation children, fill.
8. Persist generation snapshot and repeat.

**Design tradeoffs**
- theory+code vs code_only: theory+code gives explicit claims for review but uses more tokens; code_only saves tokens and can sharpen code-level heuristics but relies on summary_md and code inspection for ideation.
- Hard review gates vs soft: Hard gates enforce quality but may reject borderline valid nodes; reviewer consistency is a known limitation.
- Exploration vs correction split: Balances novelty and repair but requires careful routing thresholds (correctness/originality cutoffs).

**Failure signatures**
- High benchmark failure rate: Check contract violations in code_content (e.g., missing required functions, shape mismatches). Inspect benchmark logs and validation errors.
- Low winner rate: Possibly too strict review thresholds or task too difficult; examine reviewer narratives for common correctness issues.
- Population collapse: If winners are too few, crossover underproduces; runtime may augment parents if `augment_crossover=true`, otherwise mutation dominates.
- Mode confusion: Ensure artifact_mode matches expected prompt behavior; code_only requires separate reviewer prompts that ignore theory_content.

**First 3 experiments**
1. Smoke test: Run one generation with only human seeds (no operators) to verify benchmark and review pipelines produce valid scores and reviews.
2. Mode comparison: On a simple optimizer task (e.g., linear regression), compare theory+code vs code_only evolution for g=2, p=8; note differences in node complexity and review outcomes.
3. Mutation routing: Intentionally create a node with a known bug (e.g., missing closure handling); verify correction mutation fixes it, while exploration mutation on a correct but unoriginal node produces a novel variant.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: What are the convergence properties of CliffSearch's LLM-based evolutionary operators, and under what conditions can we prove convergence to optimal or stable solutions?
- **Basis in paper**: The framework does not by itself provide convergence guarantees for agent-guided operators.
- **Why unresolved**: The stochastic nature of LLM operators and lack of analytical tractability prevent standard convergence proofs. Assumptions about operator consistency, population diversity, and fitness landscape smoothness are not established.
- **What evidence would resolve it**: Develop theoretical bounds under simplified operator models (e.g., Markov chain approximations), or empirical convergence studies across repeated runs on benchmark tasks showing consistent approach to optima.

### Open Question 2
- **Question**: Can calibrating reviewer uncertainty beyond scalar scores improve selection reliability in CliffSearch?
- **Basis in paper**: Reviewer uncertainty is currently represented through scalar scores rather than calibrated uncertainty models.
- **Why unresolved**: Scalar scores encode no confidence measure; a review that is unsure might still give a 4, defeating the gate's purpose. Calibration could involve probabilistic outputs from the reviewer LLM (e.g., via sampling or confidence elicitation).
- **What evidence would resolve it**: Implement a reviewer that outputs uncertainty estimates (e.g., variance over multiple passes or explicit confidence), then compare evolutionary outcomes (winner quality, robustness to prompt noise) against the baseline scalar-only reviewer.

### Open Question 3
- **Question**: Does anchoring novelty judgments in a retrieval-augmented literature database reduce false positives from retrieval-like outputs?
- **Basis in paper**: Novelty judgment is still only weakly grounded; a stronger system should anchor reviewer originality analysis to a retrieval-backed literature database so that novelty claims are explicitly tied to searchable evidence.
- **Why unresolved**: Without external grounding, the reviewer relies on latent knowledge which may conflate genuine novelty with closely related known ideas. RAG could provide explicit citations to prior work, enabling precise novelty scoring.
- **What evidence would resolve it**: Build a RAG system over relevant literature (HC, manifold attention, optimizer papers), have the reviewer query it during assessment, and compare originality scores and discovery validity against the baseline.

### Open Question 4
- **Question**: How does artifact mode (theory+code vs code_only) affect the nature and quality of scientific discoveries, and what is the trade-off between interpretability and search efficiency?
- **Basis in paper**: The paper shows code_only found a much better hyper-connection (0.00733 vs 1.6935) and suggests token budget reallocation, but systematic evaluation is lacking.
- **Why unresolved**: It is unknown whether theory+code could match code_only with equal token budgets, or whether code_only's success is task-specific. The trade-off between scientific interpretability (theory) and computational resources (code) is not quantified.
- **What evidence would resolve it**: Conduct controlled experiments with equal token budgets per agent call, varying the amount of theory generation vs code generation, and measure discovery metrics (novelty, correctness, benchmarking) to isolate the effect of artifact structure.

## Limitations

- LLM-based reviewer consistency and nondeterminism introduce variability and potential unreliability in the selection gates.
- The framework depends on access to the full codebase and human seed implementations, which are only available via the authors' website.
