# General Agent Evaluation

## Quick Facts
- **arXiv ID:** 2602.22953
- **Source URL:** https://arxiv.org/abs/2602.22953
- **Reference count:** 24
- **Primary result:** General agents achieve comparable performance to domain-specific agents without tuning; model choice dominates success rate variance (28.2%) while agent architecture accounts for only 0.6%.

## Executive Summary
The paper tackles the lack of systematic benchmarks for general-purpose AI agents by introducing a Unified Protocol and the Exgentic framework. The protocol standardizes agent-benchmark interactions through three fields—task, context, and actions—while external adaptors enable seamless integration without modifying existing code. Evaluating five agent architectures with three frontier LLMs across six benchmarks (90 configurations) shows that general agents can match domain-specific counterparts, with model quality being the primary performance determinant. Cost analyses reveal up to 33× efficiency differences, and tool shortlisting significantly improves weaker models. The framework and a leaderboard are publicly available.

## Method Summary
Exgentic mediates between agents and benchmarks via a Unified Protocol that defines canonical representations for tasks, context, and actions. External adaptors translate these representations to and from each component's native API, preserving original behavior. The evaluation covers five agents (ReAct, ReAct Short, SmolAgents, OpenAI Solo, Claude Code) and three LLMs (GPT 5.2, Claude Opus 4.5, Gemini 3 Pro) on six benchmarks (AppWorld, BrowseComp+, SWE-Bench Verified, τ²-Bench Airline/Retail/Telecom). Each configuration runs 100 tasks per benchmark, with a maximum of 100 turns, measuring success rate, monetary cost, and step count. The framework orchestrates sessions, isolates components, and aggregates results.

## Key Results
- General agents perform on par with domain-specific agents: the best general agent scores 0.81 on SWE-Bench Verified versus the prior domain-specific best of 0.79.
- Model choice explains 28.2% of the variance in success rate, whereas agent architecture contributes only 0.6%.
- Cost-efficiency spans a 33× range; GPT 5.2 is most cost-effective but weakest, Claude Opus 4.5 is strongest but expensive. Tool shortlisting boosts GPT 5.2 by 5 percentage points in tool-rich environments.

## Why This Works (Mechanism)
#### Mechanism 1
- **Claim:** The Unified Protocol enables evaluation of any agent on any benchmark by mediating incompatible communication protocols.
- **Mechanism:** It defines a canonical `task`, `context`, and `actions` representation that decouples agent-benchmark interaction. Benchmarks are adapted by exposing their native actions and semantics through this protocol; agents are adapted by mapping the protocol to their native APIs.
- **Core assumption:** All agent-benchmark interactions can be reduced to these three fields, and any existing protocol can be translated losslessly.
- **Evidence anchors:** [abstract] "Unified Protocol defining standardized 'task', 'context', and 'actions' fields"; [section 2.1] Detailed definition and example from τ²-Bench; [corpus] Weak support from neighboring papers that pursue general evaluation but do not validate this specific mediation claim.
- **Break condition:** A benchmark or agent whose core interaction model cannot be expressed in the three-field protocol (e.g., continuous real-time physical interaction).

#### Mechanism 2
- **Claim:** External adaptors allow integration without modifying agent or benchmark code, preserving native behavior and enabling reuse.
- **Mechanism:** Separate adaptor processes translate between the Unified Protocol and the specific APIs of agents (e.g., MCP, Python functions) and benchmarks. The orchestrator mediates all communication via queues, running components in isolation.
- **Core assumption:** Adapters can be built to perfectly mirror the semantics of native interfaces, and isolation does not introduce race conditions or state inconsistencies.
- **Evidence anchors:** [section 2.3 & 3.1] Methodology for adapting agents and the external adaptor design pattern; [section A] Concrete interaction example with SmolAgents and τ²-Bench showing queue-based synchronization; [corpus] Strong support: Related work (HAL, BrowserGym) also uses adaptors/consolidation, but Exgentic's protocol-preserving approach is its novel contribution.
- **Break condition:** An agent or benchmark with a closed, non-inspectable binary protocol where reverse-engineering is impossible.

#### Mechanism 3
- **Claim:** Model quality (LLM capability) is the dominant determinant of general agent performance, explaining 28.2% of variance, far exceeding agent architecture (0.6%).
- **Mechanism:** The evaluation runs 90 configurations (5 agents × 3 models × 6 benchmarks). Variance decomposition (`η²`) isolates the contribution of the model factor versus the agent factor to task success rate.
- **Core assumption:** The selected agents and benchmarks form a representative sample of the general-agent design space, and the interaction effect (5.0%) does not mask a stronger latent agent effect.
- **Evidence anchors:** [section 5.3] Explicit variance decomposition results and the 28.2% vs. 0.6% figures; [section 5.1] Performance rankings dominated by model (Claude Opus 4.5 top 3, GPT 5.2 bottom 4); [corpus] Moderate: Corpus shows related work on patching architectures and web agents, but none perform this specific multi-factor variance analysis on general agents.
- **Break condition:** If the agent sample is too narrow (e.g., all tool-calling based) or if benchmarks are not diverse enough to stress different agent capabilities.

## Foundational Learning
- **Concept: Protocol Mediation**
  - *Why needed here:* Understanding how to abstract heterogeneous APIs into a common representation is the core insight enabling this work. Engineers must grasp why direct integration is unscalable.
  - *Quick check question:* What are the three fields of the Unified Protocol, and give an example of how a tool call from a benchmark maps to an `action`?

- **Concept: External Adaptation Pattern**
  - *Why needed here:* The framework’s practicality hinges on building thin adaptors instead of forking code. Engineers need to design stateless translation layers.
  - *Quick check question:* Why can't we simply modify the benchmark's source code to call the agent directly, and what problem does the external adaptor solve?

- **Concept: Multi-Factor Experimental Design & Variance Decomposition**
  - *Why needed here:* To justify the claim that "model quality dominates," one must understand how to structure experiments (crossed factors) and analyze variance (`η²`) to attribute performance differences.
  - *Quick check question:* If model X has a mean success rate of 0.7 across all agents/benchmarks, and agent Y has a mean of 0.6 across all models/benchmarks, does that alone prove model is more important? What additional analysis is required?

## Architecture Onboarding
- **Component map**
  Orchestrator ↔ Agent Adaptor ↔ Agent
  Orchestrator ↔ Benchmark Adaptor ↔ Benchmark
  Evaluation Harness manages parallel runs and logging.

- **Critical path**
  Benchmark Adaptor → Orchestrator → Agent Adaptor → Agent → (action) → Orchestrator → Benchmark Adaptor → Benchmark → (observation) → Orchestrator (loop).

- **Design tradeoffs**
  - Generality vs. Expressiveness: The three-field protocol is simple but may not capture every nuanced interaction (e.g., bidirectional streaming). Custom metadata is often lost.
  - Adaptor Complexity vs. Fidelity: A thin adaptor preserves native behavior but may require deep understanding of both sides. A thick adaptor "helps" the agent/benchmark but risks evaluating a modified system.
  - Isolation vs. Performance: Running components in separate processes/Docker ensures reproducibility but adds IPC overhead, especially for fine-grained tool calls.

- **Failure signatures**
  - Protocol violation: Agent returns an action schema not in the provided list → adaptor/benchmark rejects it. Check adaptor's tool specification mapping.
  - State desync: Agent's internal memory diverges from environment state (e.g., file changes not visible). Ensure `step()` calls are atomic and environment is reset per task.
  - Tool limit overflow: Model context window exceeded by full action list (as with GPT 5.2 on AppWorld). Manifested as immediate failure or truncated tools. Requires shortlisting.

- **First 3 experiments**
  1. **Smoke test:** Run OpenAI Solo + Claude Opus on τ²-Bench-Airline (one task). Verify a full trajectory completes, logs are written, and success is recorded. Isolates basic orchestration.
  2. **Adaptor sanity check:** Run the same agent on SWE-Bench Verified. Check that `bash` actions execute in the correct repo directory and `submit_patch` generates a valid `git diff`. Tests action translation fidelity.
  3. **Cross-benchmark generalization:** Run ReAct Short with Gemini 3 on all 6 benchmarks. Measure performance variance. Goal: Confirm agent shows *some* cross-domain capability (non-zero on all) before scaling to full sweeps.

## Open Questions the Paper Calls Out
1. **Extending the protocol to visual/multimodal environments**
   - *Basis:* The paper notes that Exgentic currently only supports text-based interactions.
   - *Why unresolved:* The three-field protocol does not accommodate image, video, or GUI actions/observations.
   - *What evidence would resolve:* Develop adaptors that encode visual inputs and decode multimodal actions; validate on benchmarks like OSWorld or VisualWebArena.

2. **Reducing the cost of general agent evaluation**
   - *Basis:* Full evaluations cost ~$22K for 90 configurations; the paper suggests exploring intelligent sampling and early stopping.
   - *Why unresolved:* High costs limit frequency and scale of assessments, hindering research progress.
   - *What evidence would resolve:* Implement cost-saving strategies (e.g., dynamic task sampling, early termination) and demonstrate that reduced-cost evaluations maintain statistical reliability and correlation with full-benchmark results.

3. **Understanding the lack of robust cross-benchmark generalization**
   - *Basis:* Agent rankings vary widely across benchmarks, and no agent dominates all domains.
   - *Why unresolved:* Current architectures appear optimized for specific distributions rather than true generalization.
   - *What evidence would resolve:* Conduct large-scale ablation studies on agent components to identify features that enhance cross-domain stability; engineer new agents explicitly maximizing multi-benchmark scores and show improved Spearman correlations between benchmark performances.

## Limitations
- The study's sample of agents (5) and benchmarks (6) may be too narrow to generalize performance and variance findings.
- External adaptors could introduce overhead or state desynchronization, but these effects are not measured.
- The Unified Protocol is limited to discrete text-based actions and cannot model continuous or real-time interactions (e.g., robotics).
