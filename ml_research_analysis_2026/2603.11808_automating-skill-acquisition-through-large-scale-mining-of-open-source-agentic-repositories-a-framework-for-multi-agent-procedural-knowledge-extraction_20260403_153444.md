# Automating Skill Acquisition through Large-Scale Mining of Open-Source Agentic Repositories: A Framework for Multi-Agent Procedural Knowledge Extraction

## Quick Facts
*   **arXiv ID:** 2603.11808
*   **Source URL:** https://arxiv.org/abs/2603.11808
*   **Reference Count:** 24
*   **Primary Result:** A framework for automated skill extraction from agentic repositories achieves a 40% improvement in knowledge transfer efficiency while maintaining human-level pedagogical quality.

## Executive Summary
This paper introduces a framework to automate the acquisition of specialized procedural skills for AI agents by mining open-source repositories. It addresses the scaling limitations of manually crafted skills or expensive model retraining. The core method structurally analyzes repositories, identifies latent reusable procedural patterns via semantic retrieval, and translates them into a standardized, context-efficient `SKILL.md` format. Evaluation on educational video generation systems demonstrates significant gains in knowledge transfer efficiency. The approach is underpinned by a rigorous security governance pipeline to ensure extracted skills are safe for deployment.

## Method Summary
The proposed pipeline consists of four sequential stages. First, a structural analysis tool (`repo2AI`) creates a hierarchical Markdown map of the target repository, providing context on workflow patterns. Second, a two-stage semantic identification process uses dense retrieval (bi-encoder) for candidate recall followed by a cross-encoder for precise ranking, filtering for recurrence, verification, non-obviousness, and generalizability. Third, a compiler synthesizes the selected code modules into a `SKILL.md` artifact, employing a progressive disclosure architecture with metadata (Level 1), instructions (Level 2), and assets (Level 3). Finally, a four-tier security governance pipeline (G1-G4) verifies the skill's safety before integration into a library.

## Key Results
*   Extracted skills from educational video generation systems (TheoremExplainAgent, Code2Video) demonstrate a **40% improvement in knowledge transfer efficiency** as measured by the TeachQuiz benchmark.
*   The pedagogical quality of skills generated by the framework is **comparable to human-authored tutorials**.
*   The progressive disclosure `SKILL.md` format enables agents to maintain awareness of **10,000+ skills** without context window overflow.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** Repository structural analysis creates a contextual map that distinguishes reusable procedural patterns from project-specific implementation details.
*   **Mechanism:** Tools like `repo2AI` generate a hierarchical Markdown representation of the repository's directory structure and file contents. This map identifies core orchestration scripts, configuration directories, and domain-specific modules, providing the LLM-based extraction agent with essential context about workflow patterns and logical dependencies.
*   **Core assumption:** The structural hierarchy of a well-architected agentic repository implicitly encodes the separation between generalizable procedural logic and bespoke glue code.
*   **Evidence anchors:**
    *   [abstract] "The framework encompasses repository structural analysis..."
    *   [page 3, section 3.1] "This structural mapping provides essential context for LLM-based extraction agents, enabling understanding of task orchestration patterns..."
    *   [corpus] Weak direct evidence; neighbor papers discuss deployment and skill frameworks but not structural mining specifics. **Assumption:** This mechanism is inferred from the paper's described pipeline.
*   **Break condition:** Repository structure is too convoluted or non-standard (e.g., monolithic scripts without modular organization), preventing clear identification of discrete procedural units.

### Mechanism 2
*   **Claim:** Semantic skill identification via a dense retrieval + cross-encoder ranking pipeline isolates "latent skills"—recurring, generalizable procedural patterns—from the codebase.
*   **Mechanism:** Candidate code modules and task descriptions are encoded into dense vectors. Initial retrieval uses cosine similarity (Equation 2) to find top-K candidates. A cross-encoder then performs fine-grained relevance scoring, promoting only modules above a threshold τ that satisfy criteria like recurrence, verification, non-obviousness, and generalizability.
*   **Core assumption:** High-quality, reusable procedural knowledge manifests as semantically coherent code patterns that consistently match a class of task descriptions across different contexts.
*   **Evidence anchors:**
    *   [abstract] "...semantic skill identification through dense retrieval..."
    *   [page 4, section 3.2] "This identification task is formulated as a two-stage ranking problem combining dense retrieval and cross-encoder refinement."
    *   [page 5, section 3.2.2] Lists explicit extraction criteria (recurrence, verification, etc.).
    *   [corpus] Neighbor paper "Skill Learning Using Process Mining..." (arXiv:2410.12870) uses different methodologies but shares the goal of procedural pattern extraction, offering peripheral support for the concept.
*   **Break condition:** The codebase lacks recurring patterns (unique, one-off scripts), or the retrieval model's embeddings fail to capture the semantic relationship between code functionality and natural language task descriptions.

### Mechanism 3
*   **Claim:** Translation to the progressive disclosure SKILL.md format enables scalable agent integration by minimizing context window consumption while maintaining access to deep procedural knowledge.
*   **Mechanism:** Extracted patterns are synthesized into a three-level artifact: lightweight Level 1 metadata (pre-loaded), procedural instructions (loaded on activation), and auxiliary resources (loaded on-demand). This structure allows agents to maintain awareness of thousands of skills without performance degradation, injecting instructions as hidden meta-messages to reshape reasoning.
*   **Core assumption:** An agent's operational efficiency is critically constrained by its context window; separating "what" (metadata) from "how" (instructions) and "resources" allows for efficient skill discovery and utilization.
*   **Evidence anchors:**
    *   [abstract] "...translation to the standardized SKILL.md format."
    *   [page 2-3, section 2.2 & Table 1] Details the progressive disclosure architecture and token usage estimates (Level 1: 30-100 tokens).
    *   [page 9, section 6.1] "Progressive disclosure architecture enables agents to maintain awareness of 10,000+ skills..."
    *   [corpus] Neighbor "Agent Skills for Large Language Models..." (arXiv:2602.12430) and Anthropic/Claude documentation [16] are cited as foundational for the SKILL.md spec, providing strong corroborating evidence for the format's existence and intent.
*   **Break condition:** The skill's procedural logic is too interwoven with external state or requires constant reference to large resources, defeating the on-demand loading model and causing latency spikes.

## Foundational Learning
*   **Concept: SKILL.md Progressive Disclosure Architecture**
    *   *Why needed here:* The entire value proposition of scalable skill libraries depends on this format. Without understanding Level 1 (metadata)/Level 2 (instructions)/Level 3 (resources) separation, one cannot grasp how the system avoids context overflow.
    *   *Quick check question:* If an agent has 5,000 skills in its library, how many tokens are minimally consumed in its static awareness state, and what triggers the loading of a skill's detailed procedure?
*   **Concept: Dense Retrieval for Code-Text Alignment**
    *   *Why needed here:* This is the core technical engine for finding candidate skills. Understanding that code modules and task descriptions are mapped to a shared embedding space via bi-encoders is key to evaluating the identification stage's feasibility and limitations.
    *   *Quick check question:* What is the functional difference between the dense retrieval stage (bi-encoder) and the subsequent binary ranking stage (cross-encoder) in the skill identification pipeline?
*   **Concept: Security Governance Tiers (G1-G4)**
    *   *Why needed here:* Automated extraction from public repos is inherently risky. The paper's claim of "rigorous security governance" is anchored in this four-stage verification pipeline. Ignoring it invalidates the framework's practical deployability.
    *   *Quick check question:* What specific threat does the G3 "Behavioral Sandboxing" stage mitigate that G1 "Static Analysis" might miss?

## Architecture Onboarding
*   **Component map:**
    Input (GitHub URL) -> Stage 1: Context Builder (`repo2AI`) -> Stage 2: Skill Miner (Dense Retrieval + Cross-Encoder) -> Stage 3: Skill Compiler (LLM -> `SKILL.md`) -> Stage 4: Verifier (G1-G4) -> Output (Verified Skill Package)
*   **Critical path:** Repository URL → Structural Analysis → Semantic Identification → Translation → Security Verification. The most experimentally volatile segment is Stage 2 (retrieval thresholds, embedding model choice).
*   **Design tradeoffs:**
    *   *Recall vs. Precision in Retrieval:* A low τ (threshold) yields more candidate skills but increases false positives (non-generalizable code). A high τ misses valid skills. Requires domain-specific calibration.
    *   *Automation vs. Security Rigor:* Skipping or simplifying G3/G4 verification drastically reduces time-to-skill but increases malware/backdoor risk. The paper advocates mandatory G1-G4 for production.
    *   *Standardization vs. Fidelity:* Aggressive refactoring of Level 3 assets for portability may break subtle, repository-specific environmental dependencies crucial for the skill's function.
*   **Failure signatures:**
    *   **Stage 1:** `repo2AI` produces a flat, unstructured dump (indicating a non-standard repo layout). *Action:* Manually identify core scripts; consider pre-filtering.
    *   **Stage 2:** Top-ranked modules are trivial utility functions (e.g., `utils.py` helpers) or contain hard-coded API keys. *Action:* Adjust retrieval prompts/criteria; enforce "non-obviousness" and "verification" filters.
    *   **Stage 3:** Generated `SKILL.md` instructions are just copied code snippets, not procedural guidance. *Action:* Improve LLM prompting to emphasize "step-by-step workflow" over "code dump"; add post-hoc validation.
    *   **Stage 4:** G3 sandbox consistently crashes skills. *Action:* Check dependency containerization; skill may require network/filesystem access beyond its declared manifest, indicating a flawed extraction.
*   **First 3 experiments:**
    1.  **End-to-End Extraction Sanity Check:** Run the full pipeline on TheoremExplainAgent. Verify that the `visual-theorem-walkthrough` skill's Level 2 instructions match the Planner-Coder workflow described in [page 5-6, section 4.1]. Does the extracted skill correctly reference `manim-voiceover`?
    2.  **Retrieval Threshold Tuning:** Using Code2Video, vary τ in the cross-encoder stage. Measure the trade-off between the number of extracted skills and the subsequent *Executability Success Rate* (from Table 3) in a test suite. Find the knee of the curve.
    3.  **Security Pipeline Stress Test:** Take a known-vulnerable Python script (e.g., with an `eval(input())` call) and embed it in a mock repository. Does the G1 static analysis flag it? Does G3 sandbox execution detect the data exfiltration attempt (e.g., to a mocked external server)?
