# TAROT: Test-driven and Capability-adaptive Curriculum Reinforcement Fine-tuning for Code Generation with Large Language Models

## Quick Facts
- **ArXiv ID**: 2602.15449
- **Source URL**: https://arxiv.org/abs/2602.15449
- **Reference count**: 40
- **Primary result**: TAROT introduces a four‑tier test suite and a capability‑adaptive curriculum to balance reward signals in reinforcement fine‑tuning for code generation, yielding improvements up to **+4.26 percentage points** on benchmarks.

## Executive Summary
TAROT addresses the imbalanced reward signal problem in reinforcement fine‑tuning (RFT) for code generation. It introduces a test‑driven four‑tier test suite (basic, intermediate, complex, edge) and a curriculum that decouples progression from raw reward scores, enabling tailored training schedules based on model capability. Experiments across Qwen2.5 (1.5B‑7B), Gemma2 (2B‑9B), and Qwen3‑4B models show consistent gains, with less capable models benefiting from basic‑focused curricula and more capable ones from complex‑focused curricula. The method improves functional correctness and robustness on HumanEval, MBPP, and other benchmarks by up to 4.26 percentage points. Analysis reveals that solution conciseness during training correlates better with downstream performance than raw reward magnitude.

## Method Summary
TAROT builds a dataset of 15,000 Python problems, each associated with four tiers of test cases generated by frontier LLMs (o3/o4) and validated against reference solutions, totaling 60,000 tiered test suites. The reinforcement objective uses a tier‑aggregated return:  
\(R = \sum_{l\in L} \alpha_l \cdot w_l \cdot r_{i,l}(\pi)\),  
where \(r_{i,l}\) is the pass rate on tier \(l\), \(\alpha\) allocates focus across tiers, and \(w\) are tier‑specific weights. The curriculum (schedule of \(\alpha\) and \(w\)) is chosen based on model capability (scale and coding specialization). Models are fine‑tuned with GRPO for one epoch using AdamW (lr=1e‑6, \(\beta\)=0.01), temperature 1.0, batch size 8 (4 for large models), and 8 completions per prompt. Optimal curricula: less‑capable models use basic‑focused schedules (e.g., Forward with B/I weighting or Basic Only); more capable models use complex‑focused schedules (C/E weighted).

## Key Results
- Gains of up to **+4.26 percentage points** on HumanEval, MBPP, HumanEval+, MBPP+, LiveCodeBench, CodeForces, and CruxEval.
- **Capability‑dependent optimal curriculum**: basic‑to‑complex progression helps less capable models; complex‑focused curricula benefit more capable or code‑specialized models.
- **Solution conciseness** during training is a stronger predictor of downstream performance than raw reward magnitude.

## Why This Works (Mechanism)
Standard RFT for code generation suffers from imbalanced rewards because test difficulties vary widely, causing simple tests to dominate the learning signal. TAROT’s four‑tier test suite explicitly separates tests by difficulty, ensuring balanced representation of skills. The tier‑aggregated return with adjustable weights (\(\alpha, w\)) allows the trainer to emphasize specific tiers. Crucially, the curriculum **decouples progression from raw reward scores**, so a model can be exposed to harder tests even if it performs poorly on them initially—preventing stagnation. The capability‑adaptive aspect matches the curriculum to the model’s learning capacity: weaker models get gradual exposure (basic‑first) to avoid collapse; stronger models are challenged early (complex‑first) to maximize growth. This yields a more consistent learning signal, improving both correctness and robustness across the difficulty spectrum.

## Architecture Onboarding
**Component Map** (plain text):  
Dataset (tiered test suites) → Model (policy π) → RL Trainer (GRPO) → Curriculum Controller (sets α_l, w_l) → Reward Aggregator → Policy Update → (loop) → Evaluator (on benchmarks)

**Critical Path**:  
1. Load dataset containing problems and their four‑tier test suites.  
2. Initialize policy model and GRPO trainer with hyperparameters (lr=1e‑6, β=0.01, etc.).  
3. For each training step: generate multiple completions per prompt, execute test cases per tier, compute per‑tier pass rates \(r_{i,l}\), aggregate reward using current α and w.  
4. Perform GRPO policy update.  
5. Periodically evaluate on a validation set (or at epoch end) to observe progress; if using an adaptive schedule, adjust α and w based on performance (though the paper uses fixed capability‑based schedules).

**Design Tradeoffs**:  
- **Tier generation cost vs. quality**: Using o3/o4 yields high‑quality tests but is expensive and non‑reproducible; alternative generation may reduce cost but risk lower test diversity or correctness.  
- **Manual curriculum selection vs. automation**: The paper’s heuristic (based on model scale/specialization) is simple but may not generalize; an automated curriculum that reacts to per‑tier performance could be more robust but adds algorithmic complexity.  
- **Linear reward aggregation vs. nonlinear interactions**: The weighted sum is interpretable and stable, but it may miss synergistic effects between tiers; a more complex aggregation (e.g., learned weighting) could improve performance at the risk of overfitting.

**Failure Signatures**:  
- **Training collapse**: sharp drop in average reward or pass rates, often when complex‑focused weights are applied to an under‑capable model. Detect by monitoring per‑tier pass rates; if a tier remains near zero while its weight is high, consider reducing that weight.  
- **Memory overflow**: GRPO with multiple completions can exhaust GPU memory, especially for 7B/9B models. Watch `nvidia‑smi`; mitigate by reducing batch size (e.g., to 4), using gradient accumulation, or enabling vLLM memory‑paging.  
- **Overfitting to training distribution**: training reward increases while validation Reward/ pass@1 stalls or declines. Use early stopping or adjust curriculum to encourage generalization.

**First Three Experiments**:  
1. **Smoke test**: Train Qwen2.5‑1.5B for 10 steps with Basic Only curriculum on a small subset; verify that basic‑tier pass rate increases and no runtime errors occur.  
2. **Curriculum comparison**: On a held‑out validation set, compare Basic Only, Forward (B/I weighted), and Complex/Edge Weighted schedules; select the one with highest validation pass@1 for subsequent full training.  
3. **Robustness probe**: After full training, evaluate on both in‑distribution (balanced tier mix) and out‑of‑distribution (unseen hard tests from HumanEval+); ensure the chosen curriculum improves robustness without sacrificing basic correctness.

## Limitations
- Dataset regeneration requires access to proprietary o3/o4 models, making exact replication costly and potentially impossible for some researchers.
- Curriculum selection is manual and based on heuristics; no automatic method to determine the optimal schedule for an arbitrary new model.
- Small models risk training collapse when exposed to complex‑focused curricula due to extremely sparse rewards; careful tuning is needed.

## Confidence
