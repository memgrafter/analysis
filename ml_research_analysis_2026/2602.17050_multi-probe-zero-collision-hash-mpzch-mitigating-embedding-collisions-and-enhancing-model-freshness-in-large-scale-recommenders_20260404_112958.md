# Multi-Probe Zero Collision Hash (MPZCH): Mitigating Embedding Collisions and Enhancing Model Freshness in Large-Scale Recommenders

## Quick Facts
- arXiv ID: 2602.17050
- Source URL: https://arxiv.org/abs/2602.17050
- Reference count: 19
- Primary result: MPZCH eliminates hash collisions, improves new-item impressions by 0.83% and intra-owner embedding similarity from 25% to 38%, while keeping training QPS and inference latency comparable to baseline methods.

## Executive Summary
Large-scale recommendation systems rely on massive embedding tables, but traditional hash-based indexing causes collisions that degrade model quality and propagate stale representations. MPZCH replaces direct hashing with a linear probing mechanism backed by auxiliary tensors that track ID-to-slot mappings and enable configurable eviction (TTL/LRU). New IDs either secure dedicated slots or evict expired ones, and upon eviction both embedding weights and optimizer state are reset to prevent negative transfer. The system integrates seamlessly into TorchRec and has been deployed in production.

Online A/B tests confirm zero user embedding collisions and Normalized Entropy improvements in 14 of 17 ranking tasks. For item embeddings, new videos gained 0.83% more impressions and intra-owner embedding similarity rose from 25% to 38%. Crucially, training throughput and inference latency remained on par with the baseline, demonstrating that MPZCH delivers substantial quality gains at negligible operational cost.

## Method Summary
MPZCH modifies the embedding lookup pipeline by introducing two auxiliary tensors: `Identities` (slot→ID mapping) and `Metadata` (timestamps for TTL/LRU). The core is a CUDA kernel that executes a two-pass linear probing scan for each ID. In Pass 1, it probes sequentially up to `max_probe` slots from the initial hash index to either locate the ID (hit) or identify candidate slots (empty or evictable). In Pass 2, updates occur: existing IDs are updated; if the ID is new and an empty slot exists, it is inserted; if no empty slot but an evictable slot (expired by TTL or least recently used) is found, that slot is evicted and reused, with both embedding and optimizer state reset; if all probed slots are occupied by non-evictable IDs, the kernel falls back to the initial hash slot (collision fallback).

The auxiliary tensors are row-wise sharded alongside the embedding table in distributed training (e.g., TorchRec). During training, the kernel runs on each forward pass, maintaining local consistency per rank. For inference, only the `Identities` tensor is needed; `Metadata` is omitted, and the kernel is replaced by a simpler read-only lookup. MPZCH’s design ensures per-feature configurable eviction policies, and the two-pass approach keeps training latency near baseline as validated by experiments.

## Key Results
- Zero collisions achieved for user embeddings, with Normalized Entropy improvements in 14 of 17 ranking tasks.
- New video impressions increased by 0.83% and intra-owner embedding similarity improved from 25% to 38%, thanks to eviction-driven capacity for fresh content.
- Training QPS and inference latency remained comparable to the hash-based baseline, indicating practical deployability.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** MPZCH avoids hash collisions by using linear probing to find dedicated slots for IDs within a shared embedding table.
- **Mechanism:** For each ID, a hash function computes an initial table index. The system probes sequentially (up to `max_probe` slots) to either find an existing slot with the same ID (update) or an empty/evictable slot (insert). This replaces direct hash-to-slot assignment.
- **Core assumption:** Sufficient table capacity (`N_table >= N_ids`) and probe depth exist to find a free slot before the probe range exhausts.
- **Evidence anchors:**
  - [abstract]: "replacing traditional hashing with a linear probing mechanism... With reasonable table sizing, it often eliminates these collisions entirely."
  - [section 3.2]: Describes the two-pass linear probing scan (discovery then action).
  - [corpus]: Limited direct validation; neighboring papers explore alternative collision mitigation but do not replicate MPZCH's probing design.
- **Break condition:** If `table_size < ID_cardinality` *and* `max_probe` is too small, collisions persist ("Collision Fallback" returns initial slot).

### Mechanism 2
- **Claim:** Configurable eviction (TTL/LRU) actively retires stale IDs, freeing slots for fresh content and preventing obsolete embeddings from occupying space indefinitely.
- **Mechanism:** Metadata (e.g., expiration timestamp, last-access time) is stored per slot. During insertion, if the ID is new and no empty slot is found, the kernel evicts the first expired (TTL) or least recently used (LRU) slot encountered in the probe range.
- **Core assumption:** A meaningful definition of "stale" exists (e.g., items not seen for 24–72 hours) and eviction policies align with content lifecycle dynamics.
- **Evidence anchors:**
  - [section 3.4]: Explicitly details TTL and LRU eviction policies with figures illustrating their execution.
  - [section 4.2]: A/B test results show 0.83% more impressions for new videos, attributing gains partly to eviction-driven capacity optimization.
  - [corpus]: Weak; corpus discusses eviction less directly.
- **Break condition:** If eviction policies are misconfigured (TTL too long), stale IDs persist; if too aggressive, frequently returning IDs are repeatedly evicted, harming stability.

### Mechanism 3
- **Claim:** Resetting optimizer state upon eviction prevents "negative transfer" by ensuring new IDs learn from a neutral initialization rather than inheriting stale embeddings.
- **Mechanism:** When an ID is evicted, MPZCH triggers a reset of both the embedding weights and associated optimizer state (e.g., momentum buffers) for that slot. The next time the slot is allocated (for a new ID), training starts from zero.
- **Core assumption:** Inherited embeddings from colliding/stale IDs significantly harm convergence for new items more than random initialization.
- **Evidence anchors:**
  - [section 3.4]: "Crucially, upon eviction, both the embedding weights and the optimizer state... are reset."
  - [section 4.2.2]: Notes "stabilized learning trajectories" and speculates that volatile shifts in baseline models are due to collision noise; reset state contributes to smoother paths.
  - [corpus]: No direct evidence; related work tries to make collisions beneficial, contrasting MPZCH's reset approach.
- **Break condition:** If eviction is disabled or optimizer reset is omitted, new IDs may inherit misleading representations, degrading cold-start performance.

## Architecture Onboarding

### Component Map
1. **Auxiliary Tensors:** `Identities` stores slot→ID mapping, `Metadata` stores TTL/timestamps; both are row-wise sharded with the embedding table.
2. **CUDA Kernel:** Implements two-pass linear probing for lookup/insert/evict.
3. **Eviction Policies:** TTL and LRU modules interpreting `Metadata`.
4. **TorchRec Integration:** Wraps MPZCH as `EmbeddingBagCollection`/`EmbeddingCollection` shard, handling distribution and online delta publishing.
5. **Publish/Inference Module:** Freezes `Identities` and drops `Metadata` for read-only serving.

### Critical Path
Training batch → deduplicate IDs → for each shard, launch MPZCH kernel (pass 1: discover; pass 2: update/insert/evict) → update embedding & optimizer state (reset if evicted) → periodic snapshot & delta publish (sync `Identities`).

### Design Tradeoffs
- **Probe depth vs. memory:** Larger `max_probe` reduces collisions but increases worst-case lookup cost.
- **Eviction aggressiveness vs. stability:** Short TTL frees slots for fresh IDs but increases re-learning overhead for returning IDs.
- **Auxiliary tensor overhead:** `Identities` (int32) and `Metadata` (int64) increase memory per shard but are row-sharded, keeping overhead linear.

### Failure Signatures
- High collision rate despite adequate capacity → `max_probe` too low or poor hash function.
- Latency spike during training → non-batched CPU fallback or contention on Metadata updates.
- Degraded item freshness → TTL misconfigured or eviction not resetting optimizer state.
- Inconsistent `Identities` across ranks → broken row-wise sharding alignment.

### First 3 Experiments
1. **Collision Rate Sweep:** Vary `table_size`/`max_probe` with fixed `N_ids`; measure collisions (replicate Table 1). Expect zero collisions at sufficient capacity/probe.
2. **Freshness Validation:** Track intra-owner embedding similarity and new-item impression share pre/post MPZCH deployment. Expect similarity increase and new-item lift.
3. **Kernel Latency Benchmark:** Measure batched/non-batched latency under HBM/UVM/CPU (replicate Table 2). Expect HBM batched ~0.8ms and probe-depth invariance.
