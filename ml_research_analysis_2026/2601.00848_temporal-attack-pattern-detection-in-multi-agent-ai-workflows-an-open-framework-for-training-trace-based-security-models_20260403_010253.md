# Temporal Attack Pattern Detection in Multi-Agent AI Workflows: An Open Framework for Training Trace-Based Security Models

## Quick Facts
- arXiv ID: 2601.00848
- Source URL: https://arxiv.org/abs/2601.00848
- Reference count: 0
- Primary result: Fine-tuned security model achieves 31.4-point accuracy improvement on cybersecurity MCQ (42.86% → 74.29%), but suffers 66.7% false positive rate on benign workflow traces due to training data imbalance.

## Executive Summary
The research addresses the inability of existing LLM safety systems to detect temporal attack patterns in multi-agent AI workflows, where benign individual actions combine into malicious sequences. The authors fine-tune a security-focused language model using a large curated dataset of attack examples and synthetic OpenTelemetry traces via iterative QLoRA, yielding a statistically significant improvement on a custom cybersecurity benchmark. However, practical validation on real-world-like traces reveals a critical barrier: a 66.7% false positive rate on benign workflows and 0% true negative rate, stemming from a severe training data imbalance (∼90% attack-focused). This bias is irreparable by prompt engineering, necessitating human oversight and balanced retraining for deployment. All datasets, code, and benchmarks are openly released.

## Method Summary
The core method iteratively applies QLoRA to the 8-billion-parameter Foundation-Sec-1.1-8B-Instruct model. Training starts from a base dataset of 80,851 examples compiled from 18 public cybersecurity sources and 35,026 synthetic OpenTelemetry traces. Three stages are executed: V2 trains for 1,500 steps on the full base set (learning rate 2e-4), V3 continues for 500 steps with an additional 111 OWASP examples (lr 1e-4), and V4 adds 500 steps with 30 adversarial examples (lr 1e-4). Configurations employ 4-bit NF4 quantization, LoRA rank 16, AdamW 8-bit optimizer, and batch size 8. Evaluation uses a 70-question custom cybersecurity MCQA benchmark and 30 manually labeled OpenTelemetry traces (15 malicious, 15 benign).

## Key Results
- MCQA accuracy increases by 31.4 points, from 42.86% to 74.29% (p < 0.001).
- On trace validation, accuracy is only 30%, with a 66.7% false positive rate and 0% true negative rate.
- The ∼90% attack-focused training distribution causes over-sensitivity to benign workflows; ablations confirm prompt engineering cannot resolve this bias.

## Why This Works (Mechanism)
Fine-tuning on a large corpus of attack patterns—both textual descriptions and synthetic OpenTelemetry traces—imparts the model with the ability to recognize temporal sequences indicative of multi-agent attacks. Iterative QLoRA efficiently specializing the large base model by updating a small set of low-rank parameters, preserving general knowledge while focusing on security reasoning. The marked improvement on the MCQ benchmark validates this specialization. However, the extreme skew toward attack examples trains the model to overclassify traces as malicious, yielding near-zero true negatives on benign data. This fundamental data imbalance creates a deployment barrier that cannot be patched post‑training.

## Architecture Onboarding
Component map: OpenTelemetry collector -> trace parser -> security model (fine-tuned Foundation-Sec) -> classification output.

Critical path: Raw trace ingestion → structured parsing → model inference with task‑specific prompt → BENIGN/SUSPICIOUS/MALICIOUS label.

Design tradeoffs: Synthetic traces offer scalability but may lack real‑world complexity; 4‑bit quantization cuts memory use at potential accuracy cost; ARM64 DGX Spark hardware improves efficiency but limits portability to x86 clusters.

Failure signatures: False positive rate >66% on benign traces and true negative rate 0%, indicating severe distribution shift between training (attack‑heavy) and deployment (mixed) data.

First three experiments:
1. Run the fine‑tuned model on the 70‑question cybersecurity MCQ benchmark to confirm accuracy gain.
2. Evaluate on the 30‑trace balanced validation set (15 malicious, 15 benign) to measure false positive/negative rates.
3. Train a model on a balanced 50:50 subset of the released data to assess whether reduced class imbalance lowers false positives without sacrificing MCQ performance.

## Limitations
- Training data is ∼90% attack‑focused, causing deployment‑blocking false positives on benign workflows.
- The exact 30‑trace validation set used for practical testing is not released, preventing exact replication of false positive results.
- The deduplication and merging logic for assembling the final 80,851 examples is incompletely documented, leaving minor ambiguity about the dataset composition.

## Confidence
- Data imbalance & false positives as a deployment barrier: High
- Unreleased trace validation set limiting replication: Medium
- Dataset construction ambiguity: Low
