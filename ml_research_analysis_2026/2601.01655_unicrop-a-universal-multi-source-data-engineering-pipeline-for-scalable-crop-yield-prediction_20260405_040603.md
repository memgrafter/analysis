# UniCrop: A Universal, Multi-Source Data Engineering Pipeline for Scalable Crop Yield Prediction

## Quick Facts
- **arXiv ID:** 2601.01655  
- **Source URL:** https://arxiv.org/abs/2601.01655  
- **Reference count:** 19  
- **Primary result:** LightGBM on 15 features achieved RMSE 465.1 kg/ha (R² 0.6576); constrained ensemble improved to RMSE 463.2 kg/ha (R² 0.6604).

## Executive Summary
UniCrop is a universal data engineering pipeline that automates the acquisition, harmonization, and feature engineering of multi-source environmental data (satellite, climate, soil, topography) for crop yield prediction. It decouples data specification from implementation via a declarative configuration file, enabling use across crops and regions without code changes. The pipeline reduces ~200 raw variables to a compact set using minimum redundancy maximum relevance (mRMR) feature selection with a family preservation heuristic, and enforces strictly nested cross-validation to prevent information leakage. Validated on 557 rice field observations, baseline models achieved competitive performance and SHAP analysis confirmed agronomically meaningful contributions from all environmental families.

## Method Summary
The pipeline requires field observations (coordinates, harvest date, yield) and a `feature_mapping.csv` that defines desired variables and their retrieval parameters. It generates a fetch plan, acquires data via Google Earth Engine and public APIs, harmonizes spatial and temporal resolutions, and engineers agronomic features (e.g., growing degree days). After statistical screening (near-zero variance, high collinearity), mRMR feature selection is applied *independently within each cross-validation training fold* to select a compact, diverse subset. Preprocessing (imputation, scaling) and model training (LightGBM, Random Forest, SVR, ElasticNet) occur within the same fold; a constrained ensemble combines out-of-fold predictions. Performance metrics and SHAP values are derived from out-of-sample predictions.

## Key Results
- LightGBM on 15 mRMR-selected features: RMSE 465.1 kg/ha, R² 0.6576.  
- Constrained ensemble (non-negative weights, sum-to-one) improved to RMSE 463.2 kg/ha, R² 0.6604.  
- SHAP analysis confirmed interpretable, agronomically consistent feature contributions across optical, SAR, climate, soil, and topography families.

## Why This Works (Mechanism)

### Mechanism 1: Configuration-Driven Decoupling
UniCrop achieves crop/region independence by separating *what* data to fetch from *how* to fetch it. A human-readable `feature_mapping.csv` specifies variables, source APIs, and derivation rules. The pipeline translates this mapping into a Cartesian fetch plan linking each field observation to required retrievals; the implementation logic (GEE calls, API requests) remains invariant to mapping contents. This design allows adaptation to new crops or regions via configuration edits alone, avoiding code modification. *Break condition:* a new data source’s API cannot be abstracted into the existing parameter-derivation framework, forcing code changes.

### Mechanism 2: mRMR with Family Preservation
After initial screening, mRMR iteratively selects features maximizing `I(f;y) - avg_{s in S}(I(f;s))`, balancing relevance to yield and redundancy with already chosen features. A family preservation heuristic explicitly retains at least one feature from each environmental family (meteorology, vegetation, SAR, soil, topography). This yields a compact, diverse predictor set that preserves multi-modal signals and enhances generalizability. *Break condition:* the most predictive signals are concentrated in a single family, causing the heuristic to force inclusion of irrelevant features and degrade performance.

### Mechanism 3: Strictly Nested Cross-Validation
To avoid over-optimistic estimates, all preprocessing steps—imputation, scaling, statistical screening, feature engineering, and mRMR selection—are performed *using only the training data of each CV fold*. The held-out validation fold never influences any global statistics or selection decisions. This guarantees honest out-of-sample performance. *Break condition:* computational cost forces a fallback to a global feature set, invalidating the CV estimate.

## Foundational Learning

- **Concept: Configuration-Driven Pipeline Design**  
  *Why needed here:* UniCrop’s core innovation is a system for data engineering; the `feature_mapping.csv` is the primary user interface.  
  *Quick check:* If adding a new soil variable from a different dataset, what file would you edit and what information would you provide?

- **Concept: Minimum Redundancy Maximum Relevance (mRMR)**  
  *Why needed here:* It reduces ~200+ raw variables to a compact, interpretable set by balancing relevance and redundancy.  
  *Quick check:* Why might a feature highly correlated with yield still be excluded by mRMR? (Answer: high redundancy with already selected features.)

- **Concept: Nested Cross-Validation for Feature Selection**  
  *Why needed here:* Prevents the subtle but critical error of using the entire dataset to choose features, then testing on the same data.  
  *Quick check:* What happens to reported RMSE if mRMR is run on the full dataset before CV, rather than inside each training fold? (Answer: artificially lower/over-fitted.)

## Architecture Onboarding

- **Component map:**  
  `config/feature_mapping.csv` → Data Acquisition (GEE/API clients) → Harmonisation (spatial reprojection, temporal resampling) → Feature Engineering (GDD, SAR texture, interactions) → Feature Selection (screening + mRMR) → Modelling (CV loop with fold-specific imputation/scaling, model train/eval) → outputs (metrics, SHAP).

- **Critical path:** `feature_mapping.csv` → `fetch_plan` → Acquisition & Harmonisation → Engineering → **mRMR (per CV fold)** → Model Training → Evaluation. The per-fold selection is the linchpin for valid metrics.

- **Design tradeoffs:**  
  - *Generality vs. Performance:* Generic features may miss crop-specific signals; fixed 15-feature budget might be suboptimal.  
  - *Simplicity vs. Extensibility:* Adding new data sources or selection budgets requires config changes but tests mRMR stability.  
  - *Computational Cost vs. Leakage Prevention:* Nested mRMR per fold is heavy; shortcuts (global selection) break integrity.

- **Failure signatures:**  
  - `ValueError` during `fetch_plan` generation: malformed coordinates/dates in input CSV or unsupported `API Param` in mapping file.  
  - Severe missingness (>60%) in final features for many fields: source data unavailability for region/season (e.g., persistent SAR gaps).  
  - mRMR selects 15 features from only 1-2 families: family-preservation heuristic failed due to extreme dominance of one source.  
  - Extremely high CV error (RMSE ~2000+ kg/ha) vs. yield std dev: input features have no predictive relationship.

- **First 3 experiments:**  
  1. Smoke test with provided maize example: run end-to-end, verify `outputs/` contains `selected_features.csv`, `cv_metrics.csv`, and SHAP plots.  
  2. Minimal region adaptation: modify `config.py` for a small known region (e.g., a single USDA NASS county) and a common crop (e.g., corn); check `master_table.parquet` for non-null key features (NDVI, temperature).  
  3. Leakage sanity check: intentionally leak test fold information by running mRMR on full dataset *before* CV splitting; compare RMSE to nested CV (leaked run should show significant performance drop).

## Open Questions the Paper Calls Out
1. Does UniCrop maintain predictive accuracy and transferability when applied to crops beyond rice (e.g., wheat, maize) and across diverse global agro-climatic zones?  
2. To what extent does the integration of field-level management data (e.g., irrigation, fertiliser, cultivar) improve yield prediction accuracy beyond UniCrop's current environmental-only feature set?  
3. Can extending UniCrop to output full temporal sequences (e.g., multi-date NDVI, SAR, climate time series) instead of single "snapshot" features unlock superior performance with sequence-based deep learning models (e.g., LSTMs, Transformers)?  
4. Does a systematic, cloud-robust fusion of Sentinel-1 (SAR) and Sentinel-2 (optical) data—beyond their separate inclusion—meaningfully improve prediction accuracy in frequently cloud-affected regions?

## Limitations
- The original rice dataset and exact `feature_mapping.csv` are undisclosed, preventing exact metric replication and full validation across crops/regions.  
- Crop-agnostic features may miss critical domain-specific signals; the fixed 15-feature budget is heuristic and likely suboptimal for many contexts.  
- Nested mRMR per CV fold is computationally heavy; real-world use may tempt shortcuts (global selection) that invalidate performance estimates.

## Confidence
- Mechanism 1 (Config-Driven Decoupling): Medium  
- Mechanism 2 (mRMR with Family Preservation): Medium-High  
- Mechanism 3 (Strictly Nested CV): High
