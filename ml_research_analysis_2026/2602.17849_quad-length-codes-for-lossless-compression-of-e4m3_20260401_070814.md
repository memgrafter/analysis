# Quad Length Codes for Lossless Compression of e4m3

## Quick Facts
- **ArXiv ID:** 2602.17849  
- **Source URL:** https://arxiv.org/abs/2602.17849  
- **Reference count:** 26  
- **Primary result:** Quad Length Codes achieve 13.9% compressibility on FFN1 activations (vs. Huffman 15.9%) and 19.0% on FFN2 (vs. 23.2%), trading a small compression loss for faster decoding and simpler hardware.

## Executive Summary
This paper tackles the network bandwidth bottleneck in LLM training and serving by proposing Quad Length Codes, a lossless compression scheme tailored for e4m3 quantized activations. Unlike traditional Huffman coding, which suffers from slow bit‑sequential decoding and complex hardware, Quad Length Codes use 3 prefix bits to partition the 256 symbols into 8 areas with only 4 distinct code lengths. Decoding is reduced to a fixed sequence: read the first 3 bits to identify the area and total length, read the remaining bits to form an index, and lookup the symbol in a 256‑entry table. For the Gemma 2B model’s FFN1 activations, the method achieves 13.9% compressibility (vs. 15.9% for Huffman). With a simple adaptation for the more skewed FFN2 distribution, compressibility reaches 19.0% (vs. 23.2% for Huffman). The approach thus offers a practical trade‑off: a modest reduction in compression ratio in exchange for significantly faster decoding and greatly simplified hardware implementation.

## Method Summary
The technique encodes 8‑bit e4m3 symbols using a fixed set of four code lengths (6, 7, 8, 11 bits for the default scheme; 4, 6, 8, 11 bits for adapted FFN2). The 256 symbols are divided into 8 “areas” via the first 3 bits; each area contains a specific number of symbols (e.g., first five areas: 8 symbols each, sixth: 16, seventh: 32, eighth: 168). Encoding uses a 256‑entry lookup table (LUT) mapping each input symbol to its prefix + suffix bit pattern. Decoding uses the prefix to determine total code length, reads the suffix bits to form an index, and looks up the original symbol in a second LUT. Area assignments (which symbols go in which area) are chosen offline based on the empirical symbol frequency distribution of a given tensor type; the paper presents a universal assignment for FFN1 and a manually tuned adaptation for FFN2 to better match its skewed distribution.

## Key Results
- FFN1 activations: Quad Length Codes achieve 13.9% compressibility, vs. 15.9% for Huffman.
- FFN2 activations (adapted scheme): 19.0% compressibility, vs. 23.2% for Huffman.
- Decoding is simplified to constant‑time area lookup and a single LUT access, avoiding variable‑depth tree traversal.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** The use of 3 prefix bits to create 8 fixed‑length areas replaces the variable‑depth Huffman tree traversal with a constant‑time area identification step.
- **Mechanism:** The 256 possible symbols are partitioned into 8 predefined groups (“areas”). The first 3 bits of any encoded symbol directly indicate which area it belongs to, which in turn dictates the total code length (6, 7, 8, or 11 bits). This eliminates the sequential bit‑by‑bit tree walk required by Huffman decoding.
- **Core assumption:** The symbol frequency distribution is sufficiently skewed such that grouping symbols into a small number of fixed‑length buckets (with sizes 8, 8, 8, 8, 8, 16, 32, 168) captures most of the entropy, and the prefix bits for area selection are efficient.
- **Evidence anchors:**  
  [abstract] “…uses 3 prefix bits to divide the 256 symbols into 8 areas. Each area has a different code length…”  
  [section 5] “Identifying the area requires 3 bits… The first five areas have 8 symbols each… the sixth area has 16 symbols… the seventh area has 32 symbols… and the last area has the remaining 168 symbols…”
- **Break condition:** If the underlying symbol probability distribution is too uniform or has a multi‑modal shape that cannot be well‑approximated by just 4 distinct code lengths assigned to these specific group sizes, the compression ratio will degrade significantly compared to an optimal Huffman code, as seen in the FFN2 case before adaptation.

### Mechanism 2
- **Claim:** A single, static 256‑entry Look‑Up Table (LUT) for both encoding and decoding replaces complex, dynamic tree traversal hardware with simple, parallelizable memory accesses.
- **Mechanism:** The encoder LUT maps every possible input symbol to its predetermined quad‑length code (prefix + suffix). The decoder LUT maps every possible encoded symbol (0‑255) back to the original symbol. Decoding involves: 1) read first 3 bits → determine total length L, 2) read next (L‑3) bits → form index I, 3) LUT[I] → output symbol. This is a direct index operation, not a sequential decision process.
- **Core assumption:** The overhead of maintaining and accessing a small, fixed‑size LUT (256 entries) in hardware or software is lower than the control logic and state management for a deep, variable‑depth binary tree decoder, especially at high throughput.
- **Evidence anchors:**  
  [abstract] “The scheme uses a Look Up Table with 256 entries, significantly simplifying the hardware implementation compared to Huffman trees.”  
  [section 7] “During decoding, we use the ‘area code’ i.e., the first three bits to determine the length of the code… Then we add the appropriate offset to obtain the encoded symbol. The decoder maintains a 256 entry LUT…”
- **Break condition:** If the target hardware has severe constraints on on‑chip memory (SRAM) such that a 256‑entry LUT (storing codes and/or mappings) is too large, or if the symbol alphabet size is vastly increased (e.g., 16‑bit symbols), the LUT approach may become impractical compared to a more compact tree structure.

### Mechanism 3
- **Claim:** The scheme’s performance can be adapted to different symbol frequency distributions by empirically re‑assigning which symbols go into which of the 8 fixed‑size areas, trading off between the number of symbols per area and the code length assigned to that area.
- **Mechanism:** The core structure (3 prefix bits → 8 areas → 4 total code lengths) is fixed. However, the *mapping* of the 256 most‑probable symbols to the 8 area ranges (and thus to a specific total code length) is not fixed. For a given distribution (like FFN2 activations), the authors manually adjust the boundaries (e.g., giving the single most probable symbol a 4‑bit code by placing it in a very small Area 1) to better match the skew of the distribution.
- **Core assumption:** The optimal assignment of symbols to areas for a given target distribution can be found by sorting symbols by probability and then placing the highest‑probability symbols into the areas assigned the shortest total code lengths (6, 7, 8, 11), with the number of symbols in each area constrained by the fixed offset size (3, 4, 5, 8 suffix bits).
- **Evidence anchors:**  
  [section 6] “We can adapt the coding scheme to better fit this distribution… This coding scheme also has codes of 4 different lengths viz., 4, 6, 8 and 11 bits.” (Note: Table 2 shows adaptation from a 6‑bit minimum to a 4‑bit minimum by making Area 1 contain only 2 symbols).  
  [section 6] “…the compressibility achieved using this new coding scheme is 19.0%, an improvement of 2.3% from the scheme in Table 1…”
- **Break condition:** If the distribution has a very long tail of low‑probability symbols or a very sharp peak that cannot be captured by the limited set of area sizes (2, 8, 8, 8, 8, 32, 32, 158 in the adapted scheme), the adaptive re‑mapping will still incur a substantial compression penalty vs. a full Huffman tree. The method is a heuristic, not a globally optimal assignment algorithm.

## Foundational Learning
- **Shannon Entropy**  
  Why needed here: The paper’s compressibility metrics (e.g., 15.9% vs ideal 16.3% for FFN1) are defined relative to the Shannon entropy of the symbol distribution (6.69 bits). Understanding that entropy is the theoretical minimum average code length is crucial to evaluating how much “headroom” any scheme like Quad Length Codes is leaving on the table.  
  Quick check question: If a symbol distribution has an entropy of 5.2 bits per 8‑bit symbol, what is the theoretical maximum possible compression ratio (as a percentage), and why might real schemes not achieve this?

- **Huffman Coding**  
  Why needed here: Huffman is the baseline for “exploiting symbol frequency distributions” and the source of the problem (slow, deep tree traversal). The paper’s entire premise is a trade‑off against Huffman’s optimality for the sake of speed/hardware.  
  Quick check question: Why does a Huffman tree with code lengths ranging from 6 to 18 bits (as shown for FFN1) lead to “high hardware complexity” and “slow, bit‑sequential decoding”?

- **e4m3 Floating‑Point Format**  
  Why needed here: The entire scheme is designed for the 256 finite symbol encodings of this specific 8‑bit data type used in ML (e.g., OCP MX format). Understanding that these are not arbitrary bytes but structured floating‑point numbers (with specific NaN handling) is context for why the distribution looks as it does (e.g., clustering around certain exponent values).  
  Quick check question: In an e4m3 format, if the exponent field is 4 bits, how many distinct exponent values are possible, and why might the symbol probability mass function (PMF) show clusters at specific symbol values?

## Architecture Onboarding

### Component Map
Symbol Sorter & Probability Analyzer (Offline) -> Quad‑Code Configurator (Offline) -> Encoder LUT Generator (Offline) -> Encoder Engine (Runtime)  
Quad‑Code Configurator (Offline) -> Decoder LUT Generator (Offline) -> Decoder Engine (Runtime)

### Critical Path
Decoding latency is dominated by the maximum code length (11 bits). The pipeline: (1) read first 3 bits (area identification), (2) read remaining (L‑3) bits, (3) LUT access. This is a 3‑stage pipeline with variable‑length bit‑read stage bounded by 8 bits.

### Design Tradeoffs
- **Compression Ratio vs. Decode Simplicity/Speed:** Using only 4 distinct code lengths (6, 7, 8, 11 or 4, 6, 8, 11) simplifies decoding but loses some compression compared to full Huffman. More granular lengths would improve ratio but increase decoder complexity.
- **Static vs. Adaptive Scheme:** A universal table (e.g., FFN1 scheme) is simpler but suboptimal for skewed distributions. An adapted table per tensor type improves ratio by ~2% but requires offline analysis and storage of multiple LUTs.
- **LUT Size vs. Symbol Set Size:** The 256‑entry LUT scales with alphabet size; feasible for 8‑bit types but not for 16‑bit symbols without hierarchical coding.

### Failure Signatures
- **Compression Ratio Collapse:** If the symbol distribution is nearly uniform, the fixed area sizes force high‑probability symbols into large areas with long codes, leading to low or negative compressibility. Monitor achieved ratio against entropy lower bound.
- **Decoder Bottleneck:** If the maximum code length or LUT access time exceeds hardware timing constraints, decoding throughput will suffer. Profile cycle counts of the 3‑stage path.
- **LUT Mismatch:** Using an inappropriate LUT (e.g., FFN1 LUT for FFN2 data) causes incorrect decoding because area boundaries differ. Ensure encoder/decoder LUTs are paired and matched to the data distribution.

## Open Questions the Paper Calls Out
### Open Question 1
**Question:** How to formulate Quad Length Code design mathematically for optimal compression?  
**Basis in paper:** Authors state future work: “develop a mathematical formulation of the problem.”  
**Why unresolved:** Current empirical approach lacks optimality guarantees and systematic method.  
**What evidence would resolve it:** An optimization model with efficient solvers and empirical validation showing improved compression ratios.

### Open Question 2
**Question:** How can Quad Length Codes be automatically adapted to any symbol distribution?  
**Basis in paper:** The paper manually adapts the scheme for FFN2 activations but provides no general algorithmic method.  
**Why unresolved:** Manual tweaking is not scalable across tensor types or models; automatic adaptation is needed for practical deployment.  
**What evidence would resolve it:** An algorithm that, given a PMF, determines optimal area boundaries and code lengths (under the quad‑length constraint) and demonstrates effectiveness on multiple distributions.

### Open Question 3
**Question:** What are the hardware resource requirements and decoding latency of a Quad Length decoder compared to a Huffman decoder?  
**Basis in paper:** The claim “significantly simplifies hardware complexity” lacks quantitative evaluation.  
**Why unresolved:** Without measurements, the hardware benefits are speculative; LUT memory could negate simplicity gains.  
**What evidence would resolve it:** Hardware synthesis results (e.g., ASIC/FPGA) reporting area, timing, and power for both decoders under identical technology constraints.
