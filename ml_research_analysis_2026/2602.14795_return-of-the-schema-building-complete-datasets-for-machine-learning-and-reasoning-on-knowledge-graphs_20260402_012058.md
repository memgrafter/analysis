# Return of the Schema: Building Complete Datasets for Machine Learning and Reasoning on Knowledge Graphs

## Quick Facts
- **arXiv ID:** 2602.14795  
- **Source URL:** https://arxiv.org/abs/2602.14795  
- **Reference count:** 40  
- **Primary result:** KG-SaF produces schema-complete, consistent, ML-ready OWL datasets from RDF/OWL KGs, enabling evaluation of reasoning-aware methods with expressive schemas (SROIQ) and principled negatives.

## Executive Summary
The paper addresses a critical gap in knowledge graph reasoning benchmarks: most datasets lack paired expressive schemas (ontologies) and ground facts, hindering evaluation of neuro-symbolic and reasoning-aware methods. To solve this, the authors present KG-SaF, an automated workflow that extracts consistent, schema-complete datasets from large RDF/OWL knowledge graphs. The pipeline refines the source schema to ensure satisfiability, extracts a density-filtered subset of assertions, enforces global consistency, and modularizes the schema to match the extracted facts. The resulting datasets are serialized in OWL for compatibility with reasoners and include utilities for conversion to machine-learning tensors. By applying KG-SaF to six source KGs, the authors release ten new benchmarks that preserve rich schema features (disjointness, restrictions, property chains) and provide semantically meaningful negative examples, advancing the evaluation of knowledge graph reasoning.

## Method Summary
KG-SaF-JDeX is a multi-stage workflow that transforms a raw RDF/OWL knowledge graph into a machine-learning-ready OWL dataset. First, the schema (TBox/RBox) is pre-processed: import closures are collapsed, unsatisfiable classes and object properties are removed with minimal intervention, and deductive closure (materialization) is computed to make implicit axioms explicit. Second, an ABox subset is extracted via SPARQL queries, filtered by a degree threshold *k* so that individuals appear in at least *k* object property assertions, and class assertions are retained for kept individuals. Third, the schema and filtered ABox are merged and checked for consistency using an OWL reasoner; any detected inconsistencies are resolved through a manual curation step that removes problematic triples based on justifications, followed by realization to infer all class assertions. Fourth, a signature-based modularization algorithm extracts a self-contained schema module covering all symbols present in the final ABox, producing separate TBox and RBox components. Finally, ML post-processing splits the object property assertions into train/validation/test sets with leakage checks and converts them into tensor formats (e.g., PyTorch COO) via provided utilities, while the full OWL file is retained for reasoning.

## Key Results
- KG-SaF yields ten datasets from six source KGs (DBpedia, YAGO3, YAGO4, ApuliaTravel, ARCO, WHOW), including three expressive domain-specific KGs never before used for KGR benchmarks.
- Datasets retain full source schema expressivity, including SROIQ axioms like disjointness, cardinality restrictions, and property chains—features largely absent in prior enriched datasets such as DB100K+ and YAGO3-10+.
- The datasets provide principled negative examples derived from ontological constraints, are the first ML-ready OWL datasets compatible with both standard reasoners (e.g., HermiT) and frameworks like PyKEEN, and support both transductive and inductive splits.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Schema refinement and materialization yield a satisfiable, deductively closed TBox/RBox.
- **Mechanism:** The workflow collapses import closures, then performs satisfiability checks on classes and object properties, removing only unsatisfiable constructs to adhere to minimal modification. It then computes deductive closure (materialization) for implicit axioms like subsumption, inverses, and domains/ranges.
- **Core assumption:** Removing unsatisfiable constructs is sufficient to achieve a satisfiable schema without extensive manual alteration of the original ontology's intended semantics.
- **Evidence anchors:** [abstract] "refines schemas... enforces consistency"; [section 3.3] "systematically eliminated only unsatisfiable classes and roles... yielding a satisfiable subset"; [corpus] Weak: neighboring papers focus on sparse KG completion, NKG construction, or LLM agents; no direct evidence on schema refinement mechanics.
- **Break condition:** If unsatisfiable constructs are deeply embedded (e.g., via complex chains), removal may fragment the schema excessively, requiring manual correction beyond the automated minimal-modification policy.

### Mechanism 2
- **Claim:** Density-based ABox extraction produces a manageable subset that retains relational structure while excluding non-essential assertions.
- **Mechanism:** Filters object property assertions (⟨s, p, o⟩) where individuals appear in at least *k* assertions. Also removes triples with unsatisfiable properties and filters class assertions for kept individuals.
- **Core assumption:** A degree threshold *k* effectively balances dataset size and relational density, preserving patterns relevant to link prediction while discarding sparse noise.
- **Evidence anchors:** [abstract] "extracts a density-filtered ABox subset"; [section 3.4] "keeps only the object property assertions whose individuals appears in at least *k* assertions"; [corpus] Weak: corpus neighbors address NKG construction, dynamic schema induction, or temporal KG extraction; no direct evidence on density-filtering efficacy.
- **Break condition:** If *k* is too high for a given KG, the extracted ABox may become disconnected or lose critical entity-relation coverage; if too low, dataset size remains unmanageable.

### Mechanism 3
- **Claim:** Signature-based schema modularization tailors the TBox/RBox to the ABox subset, ensuring relevance and efficiency.
- **Mechanism:** Starting from the class and object property signatures in the ABox, iteratively collects axioms whose symbols overlap with the current signature (Alg. 1), reaching a fixpoint. Produces a self-contained schema module.
- **Core assumption:** The signature derived from class assertions and object properties in the ABox sufficiently identifies all schema axioms necessary for reasoning over that factual subset.
- **Evidence anchors:** [abstract] "performs schema modularization"; [section 3.6] "computes a module... based on the signature induced by the selected facts" and describes Alg. 1; [corpus] Weak: corpus neighbors do not discuss schema modularization; evidence is internal.
- **Break condition:** If the initial signature omits symbols indirectly required by axioms (e.g., through chains), the module may be incomplete, causing reasoning failures when re-imported.

## Foundational Learning
- **Concept: Description Logics (DLs) TBox/RBox/ABox**  
  - **Why needed:** The workflow formalizes KGs in DLs (OWL2), distinguishing intensional schema (TBox/RBox) from extensional facts (ABox). Understanding this separation is essential to follow each processing stage.  
  - **Quick check:** Given an OWL axiom `SubClassOf(Child Parent)`, is it TBox or ABox? How would its materialization affect the ABox?  
- **Concept: Ontology Modularization (e.g., PROMPT-FACTOR)**  
  - **Why needed:** The signature-based extraction (Alg. 1) ensures the final dataset’s schema is minimal yet complete relative to the ABox. Without this, the full KG schema would be unnecessarily large.  
  - **Quick check:** If an object property appears only in an `ObjectPropertyDomain` axiom but never in ABox assertions, should it be included in the module? Why?  
- **Concept: OWL 2 Serialization & Reasoner Compatibility**  
  - **Why needed:** Datasets are released in OWL to enable standard reasoning services (consistency, entailment). Engineers must understand OWL syntax and reasoner interfaces to use the datasets beyond ML tensor conversion.  
  - **Quick check:** What OWL feature (e.g., disjointness, property chain) enables deriving *true negatives* via reasoning, as claimed in the paper?

## Architecture Onboarding
- **Component map:** Schema Pre-processor -> ABox Extractor -> Consistency Engine -> Modularizer -> ML Post-processor  
- **Critical path:** Input KG → Satisfiable Schema → Filtered ABox → Consistent Merge → Signature-based Module → OWL Serialization + Tensor Utilities. Skipping consistency check before modularization risks propagating contradictions.  
- **Design tradeoffs:**  
  - *Minimal modification vs. completeness:* Removing unsatisfiable classes/roles preserves original modeling but may discard useful constructs; manual correction could preserve more but breaks automation.  
  - *Expressivity vs. size:* Modularization reduces schema footprint but may exclude axioms not directly referenced by ABox symbols, limiting some reasoning tasks.  
  - *OWL vs. tensor:* OWL preserves full semantics but requires reasoners; tensors enable ML frameworks but lose nuances like disjointness unless explicitly encoded.  
- **Failure signatures:**  
  - Manual curation required during consistency check (justifications point to multiple conflicting triples).  
  - ABox extraction yields ≤ threshold individuals for chosen *k* (dataset too small).  
  - Modularization result lacks expected axioms (e.g., no property chains) due to incomplete initial signature.  
- **First 3 experiments:**  
  1. Run KG-SaF-JDeX on a small, well-known KG (e.g., `dbo:Person` subset of DBpedia) with low *k* (e.g., 5) to verify each step’s output: check materialized TBox axioms, ABox size, and consistency status.  
  2. Load the resulting OWL dataset into a reasoner (e.g., Pellet or HermiT) and run a realization query to confirm inferred class assertions match the materialized ABox.  
  3. Use the provided PyTorch loader to train a simple KGE model (e.g., TransE) on the tensor split; verify that all validation/test entities/relations appear in training set (coverage check).

## Open Questions the Paper Calls Out
- **Open Question 1:** How can the manual inconsistency resolution step in KG-SaF-JDeX be automated while preserving dataset quality and source KG semantics?  
  - **Basis:** Section 3.5 states manual curation is needed because DL justifications are not unique and each includes multiple axioms.  
  - **Why unresolved:** Manual curation does not scale and introduces subjectivity; no automated solution is provided.  
  - **What evidence would resolve:** Algorithms that automatically select triples for removal based on minimal semantic impact, validated via expert review or downstream task performance.  
- **Open Question 2:** What is the empirical impact of schema expressivity (e.g., SROIQ axioms) on the performance of neuro-symbolic vs. pure embedding-based KGR methods?  
  - **Basis:** The paper creates schema-rich datasets to enable evaluation but does not compare how different KGR paradigms exploit varying schema features.  
  - **Why unresolved:** Without comparative benchmarks, it is unclear whether schema-rich datasets benefit neuro-symbolic approaches more, or what specific schema components matter.  
  - **What evidence would resolve:** Systematic experiments training diverse KGR methods (KGE, logic-based, hybrid) across KG-SaF datasets with controlled schema variations, measuring link prediction MRR, rule learning quality, reasoning efficiency.  
- **Open Question 3:** Can the KG-SaF-JDeX workflow be extended to handle KGs whose primary schema formalism is SHACL rather than OWL?  
  - **Basis:** The paper excludes YAGO 4.5 because its schema is primarily SHACL constraints; KG-SaF-JDeX relies on OWL reasoning.  
  - **Why unresolved:** Many modern KGs use SHACL; the OWL dependency limits applicability and broader benchmarking.  
  - **What evidence would resolve:** A SHACL→OWL translation layer or direct SHACL validation integration, followed by successful extraction from SHACL-dominated KGs verified by reasoner compatibility.  
- **Open Question 4:** Which schema modularization strategy optimally balances dataset utility for KGR tasks against computational and storage overhead?  
  - **Basis:** Conclusions state "explore alternative module extraction strategies" as future work; current signature-based modularization is task-agnostic.  
  - **Why unresolved:** The paper does not compare modularization strategies, leaving unknown whether different KGR methods benefit from different schema subsets or granularities.  
  - **What evidence would resolve:** Comparative analysis of modularization techniques (locality-based, ontology-based, task-driven) on reasoning time, dataset size, and performance of representative KGR methods using the modules.  
- **Open Question 5:** Do negative examples derived from ontological constraints (e.g., disjointness, functionality) improve schema-aware KGR models compared to standard negative sampling?  
  - **Basis:** The paper highlights "principled source of semantically meaningful negatives" from constraints but does not evaluate their utility.  
  - **Why unresolved:** It is uncertain whether constraint-based negatives yield better generalization, robustness, or interpretability than common sampling strategies, or whether they introduce biases.  
  - **What evidence would resolve:** Integration studies where KGE or NeSy models are trained with constraint-derived negatives versus traditional negatives on KG-SaF datasets, with evaluation on link prediction, robustness to noise, and confidence calibration.

## Limitations
- Manual curation for inconsistency resolution is required, is non-scalable, and lacks deterministic tie-breaking rules for multiple justifications.
- Exact density thresholds *k* for enriched datasets (e.g., DB-100K-C) and precise source KG versions are undocumented, hindering faithful reproduction.
- ML split ratios are unspecified; reliance on PyKEEN defaults may cause variance across reproductions.

## Confidence
- **Workflow correctness (satisfiability→materialization→filtering):** Medium. Internally consistent with DL theory, but external validation is weak; break conditions (e.g., fragmented schema) are acknowledged but not systematically benchmarked.
- **Dataset expressivity & negative example generation:** Medium. Claims of retaining SROIQ axioms and constraint-based negatives are plausible based on design, yet independent verification (e.g., axiom coverage against raw source KG) is absent.
- **ML-readiness & cross-framework compatibility:** Medium-High. Tensor conversion utilities and PyKEEN integration are concretely described, but long-term stability with evolving reasoners/libraries is unverified.

## Next Checks
1. **End-to-end smoke test on a micro-KG:** Run KG-SaF-JDeX on a controlled subset (e.g., 50 triples from DBpedia `dbo:Person` with known unsatisfiable classes). Validate materialized TBox includes expected inferred axioms (e.g., `SubClassOf`), ABox filtering respects *k*, and final OWL is consistent in HermiT.
2. **Negative example soundness audit:** For a selected dataset (e.g., ApuliaTravel-5), enumerate all disjointness or cardinality constraints in the TBox/RBox. Sample 100 "negative" triples (absent from ABox) that reasoners would derive as false; confirm none appear in the final ABox or splits.
3. **Reasoner–ML pipeline coherence:** Load the produced OWL file into a reasoner, perform *realization* to infer all class assertions for individuals, and cross-check that these inferred assertions are present in the ABox tensor (as positive training examples). Any mismatch indicates materialization or serialization flaws.
