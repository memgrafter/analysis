# AD-Bench: A Real-World, Trajectory-Aware Advertising Analytics Benchmark for LLM Agents

## Quick Facts
- arXiv ID: 2602.14257
- Source URL: https://arxiv.org/abs/2602.14257
- Reference count: 40
- Primary result: Gemini-3-Pro achieves 68.0% Pass@1 overall but drops to 49.4% Pass@1 on complex L3 tasks, with trajectory coverage at 70.1%.

## Executive Summary
AD-Bench addresses the absence of realistic evaluations for LLM agents in complex, tool-intensive domains like advertising analytics. It introduces a benchmark built from real user queries, paired with expert-validated answers and execution trajectories. A dynamic ground-truth pipeline re-executes expert tool calls to ensure answer timeliness as underlying data and platform rules evolve. Trajectory coverage measures execution fidelity via subsequence matching against expert paths. Results show state-of-the-art models perform well on simple retrieval tasks but struggle with multi-step planning and tool orchestration on complex queries, revealing significant gaps in real-world readiness.

## Method Summary
The benchmark comprises 823 instances derived from actual advertising platform queries, each associated with an expert solution trajectory using 9 domain-specific tools (e.g., `daily_data_by_group_and_field`, `calculator`). To combat static answer staleness, the evaluation pipeline records expert tool calls and dynamically re-executes them against a synchronized offline sandbox, regenerating ground-truth answers that reflect current data. Trajectory coverage is computed by checking whether the agent’s full tool sequence contains the expert’s reference trajectory as a contiguous subsequence. A curated subset of 100 “unique-trajectory” instances—where no alternative tool combinations yield a correct answer—enables dual evaluation of end-to-end accuracy and procedural fidelity.

## Key Results
- Overall, Gemini-3-Pro achieves 68.0% Pass@1 and 83.0% Pass@3 across all tasks.
- On complex L3 tasks (multi-source reasoning + knowledge retrieval), performance drops to 49.4% Pass@1 and 62.1% Pass@3.
- Trajectory coverage averages 70.1%, with a strong positive correlation (r=0.801) to Pass@1 on the unique-trajectory L3 subset.

## Why This Works (Mechanism)

**Mechanism 1: Dynamic ground-truth regeneration**  
The benchmark avoids static answer obsolescence by recording expert problem-solving trajectories and re-executing the tool calls during evaluation against a live or synchronized environment, thereby regenerating ground-truth answers that reflect current data and rules. Core assumption: expert tool sequences are robust enough that re-execution yields valid answers even as underlying data changes. Evidence: [abstract] “dynamic ground-truth pipeline that re-executes expert tool calls to ensure answer timeliness”; [section 2.1] describes replay and re-execution. Break condition: If the advertising platform’s API or tool schema changes between recording and evaluation, re-execution may fail or yield incomparable results.

**Mechanism 2: Trajectory coverage**  
Execution fidelity is isolated by comparing the agent’s full tool-call sequence to a reference trajectory; coverage is achieved if the reference appears as a contiguous subsequence. This reduces false positives from lucky guesses or inefficient alternative solutions. Core assumption: a correct answer on ambiguous queries can be reached via multiple trajectories, but subsequence match indicates adherence to a critical path of mandatory steps. Evidence: [abstract] “trajectory coverage to measure execution fidelity alongside end-to-end accuracy”; [section 2.2] defines subsequence matching; [section 3.2] shows strong coverage-Pass@1 correlation (r=0.801 on L3). Break condition: If the reference trajectory is not truly unique, high coverage may not be necessary for correctness, penalizing efficient alternatives.

**Mechanism 3: Unique-trajectory curation**  
Human experts filter 100 instances where the solution path is exclusive—no other tool combinations or orders yield a verifiable correct answer. This forces alignment with the reference trajectory for a correct answer, tightly coupling answer correctness and trajectory fidelity. Core assumption: for these “hard” queries, any correct solution must follow the expert’s exact procedural steps. Evidence: [section 2.3] describes selection of unique-trajectory instances; [section 3.2] uses this subset for correlation analysis. Break condition: If experts misjudge uniqueness (hidden alternative paths exist), the evaluation over-penalizes agents that find legitimate but unforeseen solutions.

## Foundational Learning
- **Tool orchestration with dependency constraints**: Later tools (e.g., `daily_data_by_group_and_field`) depend on earlier outputs (e.g., `get_user_account_list`). Violating dependencies causes cascading errors. Quick check: What happens if an agent calls `calculator` before fetching any data? (Answer: The code has no input data, leading to empty or erroneous output.)
- **Ground-truth staleness in dynamic domains**: Advertising metrics (cost, CTR, budgets) change daily; static QA pairs become outdated quickly. Quick check: If an expert recorded an answer on Day 1 but evaluation runs on Day 2, why might the static answer be wrong? (Answer: Underlying data (e.g., yesterday’s impressions) changed, or platform policies updated.)
- **Long-horizon planning and error propagation**: L3 tasks require 5+ tool calls; a single parameter error early on yields a final answer that is coherent but incorrect. Agents must maintain state and verify intermediate results. Quick check: In the L3 example (video vs. image CTR), what if the agent uses a 7-day date range instead of “yesterday”? (Answer: The computed CTRs are for the wrong period; the final comparison to the excellence threshold is invalid even if arithmetic is correct.)

## Architecture Onboarding
**Component map**: Online Environment → Trajectory Recording → Offline Sandbox (Agent Core + Tool Suite) → LLM Judge → Metrics

**Critical path**:
1. Receive query → agent plans → calls `get_user_account_list` (mandatory first step for scoping).
2. Depending on query, fetch data (daily/hourly), account info, adgroup info, or knowledge via `search`.
3. Use `calculator` to process retrieved data (only after data calls).
4. Generate final answer → `summarize_results`.
Dependency violations (e.g., calling data tools without account list) are common failure modes.

**Design tradeoffs**:
- Trajectory coverage vs. flexibility: Exact subsequence match is strict; minor parameter variations may break coverage even if logically equivalent.
- Dynamic re-execution vs. reproducibility: Replay relies on environment stability; flaky APIs make evaluation noisy.
- Unique-trajectory curation vs. dataset size: The 100-instance subset is clean but small; generalizability to all 823 queries is unclear.

**Failure signatures**:
- Parameter errors: Wrong `group_by_type`, incorrect field names in `calculator`.
- Dependency errors: Calling `daily_data_by_group_and_field` without prior `get_user_account_list`.
- Hallucination: Using guessed thresholds (e.g., “excellent CTR = 3%”) instead of retrieving via `search`.
- Long-context breakdown: Repeated retries exhaust context, leading to lost dependencies.

**First 3 experiments**:
1. Run Gemini-3-Pro on the full 823-instance suite; record overall Pass@1/Pass@3 and average trajectory length. Validate that L1/L2/L3 performance stratifies as in Table 2.
2. On the 100-instance unique-trajectory subset, compute trajectory coverage per model. Expect strong positive correlation (r > 0.7) between coverage and Pass@1, especially on L3.

## Open Questions the Paper Calls Out
- **Is the LLM judge (Gemini-3-Pro) reliable for AD-Bench evaluation?** Basis: Uses Gemini-3-Pro as judge without validation. Why unresolved: Judge bias could skew metrics. What evidence would resolve it: Human evaluation; correlation analysis needed.
- **Do the 100 "unique trajectory" instances truly lack alternative correct paths?** Basis: Defined as unsolvable via alternatives, but untested. Why unresolved: If alternatives exist, coverage metric is unfair. What evidence would resolve it: Obtain diverse solutions; check correctness of different trajectories.
- **Does dynamic ground-truth regeneration remain valid under platform changes?** Basis: Re-executes expert tool calls; no robustness analysis. Why unresolved: Semantic changes may produce outdated ground truth. What evidence would resolve it: Simulate changes; compare regenerated answers to fresh human annotations.
- **Is trajectory coverage a valid quality metric or does it penalize semantic equivalence?** Basis: Used as proxy but not validated. Why unresolved: May reward syntactic similarity over correctness. What evidence would resolve it: Correlate human ratings with coverage; test alternative metrics.
- **What causes error cascades in multi-step tool orchestration?** Basis: Failed cases average 1.4–1.9 error types; no causal analysis. Why unresolved: Without causal model, improvements are symptomatic. What evidence would resolve it: Build error dependency graph; identify trigger patterns statistically.

## Limitations
- Dynamic ground-truth regeneration relies on a stable environment; platform updates may break re-execution (Medium confidence).
- Trajectory coverage’s strict subsequence matching may penalize semantically equivalent but syntactically different solutions (Medium confidence).
- The unique-trajectory subset is small (n=100) and expert-judged uniqueness is unverified, limiting generalizability (Low confidence).
- Tool schemas and data formats are underspecified, hindering exact replication (Low confidence).

## Confidence
- Dynamic ground-truth regeneration: Medium
- Trajectory coverage metric: Medium
- Unique-trajectory subset validity: Low
- Reproducibility (underspecified schemas): Low
