# InstMeter: An Instruction-Level Method to Predict Energy and Latency of DL Model Inference on MCUs

## Quick Facts
*   arXiv ID: 2603.04134
*   Source URL: https://arxiv.org/abs/2603.04134
*   Reference count: 40
*   Primary result: A predictor using statically counted clock cycles achieves 3× lower energy and 6.5× lower latency prediction error than state-of-the-art methods while requiring 100× less training data (as few as 5 samples).

## Executive Summary
InstMeter is a predictor for the energy consumption and latency of deep learning model inference on microcontrollers (MCUs). Existing methods rely on coarse proxies like multiply-accumulate (MAC) operations, which are inaccurate and require large amounts of training data. InstMeter’s core innovation is using instruction-level clock cycles—fundamental metrics tied to MCU execution—as a predictor. It maps a model's source code to the disassembled binary to count the exact cycles per operator. This mapping reveals a strong linear relationship between total cycles and energy/latency, enabling a simple linear regression model. This approach drastically reduces prediction error and data requirements, generalizing across multiple MCU architectures, compilers, and software versions, and proving effective for neural architecture search under tight energy budgets.

## Method Summary
InstMeter operates in two main phases. First, a one-time **instruction library** is built for a specific MCU/software stack (e.g., ARM Cortex-M4 with a specific TFLM version). A template model containing common operators is compiled, and its source code is mapped to the disassembled binary. This loop-level mapping identifies how source-level loop bounds (from model parameters) correspond to loops in the assembly. By counting instructions within these loops and multiplying by known cycles-per-instruction (CPI), the total cycles for each kernel function are determined, creating a lookup table from operator to cycle cost. Second, for a new model, its architecture is parsed to sum the cycle costs of its operators using the library, yielding a total predicted cycle count. A linear model (`E = a·Cycles + b`, `L = c·Cycles + d`) is then fitted using ground-truth measurements from just 5–10 models, enabling prediction for any model on that hardware/software configuration.

## Key Results
*   InstMeter reduces 90th-percentile energy prediction error by 3× and latency error by 6.5× compared to state-of-the-art (nn-Meter, MACs).
*   It achieves this accuracy with 100× less training data for energy (5 vs. ~500 samples) and 10× less for latency (10 vs. ~100 samples).
*   The method generalizes across four MCU architectures (Cortex-M4/M7/M33, RISC-V ESP32-C3), multiple compiler versions and optimization flags, temperature variations, and TFLM versions.

## Why This Works (Mechanism)

### Mechanism 1: Linearity Between Clock Cycles and Energy/Latency
*   **Claim:** Total clock cycles from instruction execution have a strong linear relationship with energy consumption and latency for DL inference on MCUs.
*   **Mechanism:** On a fixed MCU under stable conditions, each instruction has a deterministic cycles-per-instruction (CPI). Energy per cycle and time per cycle are relatively constant. Therefore, summing cycles across all executed instructions yields a metric that scales linearly with total energy (`E = a·Cycles + b`) and latency (`L = a'·Cycles + b'`), where `b` and `b'` account for fixed overheads (e.g., initialization).
*   **Evidence:** Abstract and Section 3 state the linear relationship. Section 5.1 (Figures 10 & 11) show near-perfect linear fits (R² > 0.99) between computed cycles and measured energy/latency across pure-layer models.
*   **Break condition:** Non-linear effects could arise from dynamic voltage/frequency scaling (DVFS) during inference, thermal throttling, or uncaptured micro-architectural features (e.g., cache hierarchies), though the paper shows robustness under the tested DVFS and temperature ranges.

### Mechanism 2: Loop-Level Source-Disasm Mapping
*   **Claim:** Mapping loops in TFLM kernel source code to corresponding loops in the disassembled binary allows extraction of exact loop iteration counts, enabling accurate per-function cycle estimation without dynamic profiling.
*   **Mechanism:** TFLM kernels (e.g., `arm_convolve_s8`) have fixed instruction sequences; only loop bounds change with model parameters. By matching loops between C++ source and disassembly using structural (CFG intersections/subsets via graph matching) and semantic features (comparison operators, variable names), iteration counts from the source are transferred to the binary. Multiplying instruction occurrences by CPI then yields per-function cycles.
*   **Evidence:** Abstract mentions "mapping model source code to disassembled instructions." Section 3.1.1 presents two observations: (1) tuning parameters only modifies loop variables, not instructions; (2) loop variable values are inferable from source. Sections 3.3–3.4 detail the mapping algorithm using CFG and semantic similarity with random scalarization.
*   **Break condition:** Aggressive compiler optimizations (e.g., `-O2` loop unrolling/fusion) may alter loop structures enough to break the CFG-based matching, increasing mapping error (acknowledged in Section 6).

### Mechanism 3: Minimal Training Via Linear Regression
*   **Claim:** The strong linearity between cycles and energy/latency means only a few training samples (as few as 5) are needed to fit the regression coefficients, unlike non-linear SOTA predictors requiring thousands.
*   **Mechanism:** Once the instruction library is built, total cycles for any model can be computed statically. Measuring energy/latency for a small set of models provides ground truth to solve for the linear coefficients `a, b, c, d`. The linearity ensures this fit generalizes across diverse model architectures.
*   **Evidence:** Abstract and Section 3 note the minimal data requirement. Section 5.2 shows that with 5 training samples, InstMeter achieves ~30% 90th-percentile error vs. >200% for MACs and >100% for nn-Meter using 100× more data.
*   **Break condition:** If fixed overhead `b` varies significantly between models (e.g., due to model-specific memory allocation or initialization), a single linear model may be insufficient, requiring more samples or model stratification.

## Foundational Learning
*   **Concept: MCU Instruction Execution and Clock Cycles**
    *   *Why needed:* InstMeter’s core metric is clock cycles; understanding how instructions map to cycles (CPI) on a specific MCU architecture (e.g., ARM Cortex-M) is foundational. CPI variability across instruction types and memory accesses must be accounted for.
    *   *Quick check:* How do compiler instruction scheduling and memory access patterns affect the number of clock cycles per instruction on a Cortex-M4?
*   **Concept: Compiler Optimizations for Embedded Code**
    *   *Why needed:* InstMeter relies on consistent kernel function implementations. Optimizations like dead code elimination, loop transformations, and instruction selection change binary structure, affecting the source-disasm mapping and cycle counts.
    *   *Quick check:* Why might the `-O2` flag cause higher prediction error than `-Os` in InstMeter, and how does the paper address this?
*   **Concept: Neural Architecture Search (NAS) with Hardware Constraints**
    *   *Why needed:* InstMeter is designed for NAS on resource-constrained MCUs; understanding the role of fast, accurate predictors in exploring thousands of architectures under energy/latency budgets is key to appreciating its impact.
    *   *Quick check:* In NAS for MCUs, why is a predictor with low data requirements (e.g., 5 samples) more valuable than a more complex predictor requiring thousands?

## Architecture Onboarding
*   **Component map:**
    Instruction Library Builder (profiles TFLM kernels, builds CPI-weighted lookup) → Model Cycle Estimator (sums operator cycles from library) → Linear Regressor (fits E/L vs. Cycles from few samples)
*   **Critical path:** Library construction is the one-time bottleneck (~30 min per MCU/TFLM version) due to source-disasm mapping. Prediction for new models is fast (<100 ms/query).
*   **Design tradeoffs:**
    *   *Accuracy vs. generality:* Library is tied to a specific MCU, compiler flags, and TFLM version; changes may require rebuilding, though the paper shows some robustness.
    *   *Effort vs. reuse:* Initial library build is labor-intensive but amortized over many NAS evaluations; prebuilt libraries mitigate this.
    *   *Simplicity vs. completeness:* The linear model is simple but assumes constant per-cycle energy, ignoring micro-architectural effects like cache hits/misses, which the paper shows is acceptable in practice.
*   **Failure signatures:**
    1.  High error if a model uses an operator absent from the instruction library.
    2.  Degraded accuracy under aggressive compiler optimizations (`-O2`) that break loop mapping.
    3.  Cross-architecture transfer without rebuilding the library (e.g., using M4 library on M33).
*   **First 3 experiments:**
    1.  Validate linearity: Compile single-layer models (Conv2D, Dense) with varying parameters, compute cycles, measure energy/latency, confirm near-perfect linear fit (R² > 0.99).
    2.  Check mapping accuracy: Manually inspect source-disasm loop matches for a kernel function (e.g., `arm_convolve_s8`) to ensure loop bounds from source correctly map to disasm loops.
    3.  End-to-end test with minimal data: Use 5 training models to fit the linear predictor, evaluate on 440+ models, and verify 90th-percentile error ~30% (vs. >200% for MACs).

## Open Questions the Paper Calls Out
*   Can InstMeter’s approach be extended to MCUs with proprietary hardware accelerators that use closed-source software stacks instead of TFLM?
*   How can temperature-dependent leakage and threshold variations be integrated into InstMeter’s linear prediction model to improve accuracy under extreme thermal conditions?
*   Can the loop-level source-disasm mapping algorithm be made robust to aggressive compiler optimizations (e.g., loop fusion, fission) that alter loop structures at -O2 or higher?
*   Does the requirement for both source code and disassembly limit InstMeter’s applicability to closed-source MCU libraries or third-party binaries, and can this be mitigated?

## Limitations
*   The complete, version-specific list of TFLM kernel functions and their precise operator mappings is not fully enumerated, requiring deep inspection of the specific TFLM source.
*   Cycle-per-instruction (CPI) accuracy across compiler flags and MCU variants (e.g., using M4 data for M7/M33) is a potential source of error not fully quantified.
*   The method is tightly coupled to the structure of handwritten TFLM kernels; generality to other embedded inference engines (e.g., CMSIS-NN) or automatically generated code is unknown.

## Confidence
*   **Linearity between total cycles and energy/latency:** Medium Confidence. Strongly evidenced on pure-layer models and across tested conditions, but break conditions (extreme DVFS, thermal throttling) are acknowledged and not exhaustively validated.
*   **Loop-level source-disasm mapping algorithm:** Medium Confidence. Validated on a specific TFLM version with `-O0`; significant degradation under `-O2` is admitted, indicating fragility to compiler optimizations.
*   **Minimal training data requirement (5 samples):** Medium Confidence. The claim depends on the validity of cycle estimation and linearity; it holds within the evaluated model distribution but would fail with an incomplete cycle library or unstable coefficients.

## Next Checks
1.  Stress-test linearity under extreme operating conditions (e.g., wide DVFS range, temperatures beyond 43°C) to identify the point of deviation and quantify prediction error without retraining.
2.  Test cross-framework generality by constructing an instruction library for a different kernel implementation (e.g., ARM's CMSIS-NN) and measuring prediction accuracy on models using those kernels.
