# MATA: Multi-Agent Framework for Reliable and Flexible Table Question Answering

## Quick Facts
- arXiv ID: 2602.09642
- Source URL: https://arxiv.org/abs/2602.09642
- Reference count: 40
- Primary result: MATA achieves up to 40.1% higher exact match, 46.7% fuzzy matching, and 33.1% F1 score over the strongest baselines across ten LLMs, while reducing LLM agent calls by up to 95.8% on simpler tasks and 60.6% on complex ones.

## Executive Summary
This paper introduces MATA, a multi-agent framework for table question answering (TableQA) designed to improve reliability and efficiency in resource-constrained environments where using large closed‑source LLMs is impractical. MATA orchestrates multiple reasoning paths (Chain‑of‑Thought, Program‑of‑Thought, text‑to‑SQL) using lightweight small language models (SLMs) as tools to dynamically prioritize execution, avoid unnecessary calls, and ensure concise outputs. Evaluated on TableBench, MATA significantly outperforms baselines (e.g., up to 40.1% higher exact match) and reduces LLM agent calls by up to 95.8% on simple tasks and 60.6% on complex ones, demonstrating scalable, model‑agnostic performance.

## Method Summary
MATA employs a multi‑agent architecture with three primary reasoning agents: a CoT agent (always invoked), and either a PoT or text‑to‑SQL agent selected by a Scheduler. The Scheduler (Sch) analyzes table and question features to predict which code‑based path is more likely to succeed first, running it alongside CoT. If CoT’s answer matches the selected path’s answer, the third path is skipped. Both code agents use debug agents for iterative refinement. A Confidence Checker (CC) scores candidate answers from executed paths; if any score exceeds a threshold (θ=0.1), the highest‑scoring answer is selected without invoking the expensive Judge Agent (JA). Otherwise, JA decides. Finally, a Format Matcher (FM) condenses verbose answers. All orchestration tools—Sch (MobileBERT‑based), CC (DeBERTaV3‑based), and FM (Qwen2.5‑0.5B)—are lightweight SLMs, minimizing overhead while maintaining high accuracy via selective LLM use.

## Key Results
- MATA achieves up to 40.1% higher exact match and 46.7% higher fuzzy matching compared to the strongest baselines across ten LLMs.
- It reduces LLM agent calls by up to 95.8% on simpler tasks (Penguins) and 60.6% on complex ones (TableBench) while maintaining state‑of‑the‑art accuracy.
- The framework demonstrates model‑agnostic performance, enabling the use of small LLMs (as small as 3B) without sacrificing accuracy.

## Why This Works (Mechanism)
### Mechanism 1: Scheduler‑driven path prioritization
Claim: MATA dynamically selects and prioritizes reasoning paths (CoT, PoT, text2SQL) to balance accuracy and efficiency.  
Mechanism: The Scheduler (Sch) analyzes table features (size, schema) and question semantics to predict whether PoT or text2SQL is more likely to succeed first. The higher‑probability path runs alongside always‑invoked CoT. If CoT’s answer matches the selected path’s answer, the third path is skipped, reducing unnecessary LLM calls while preserving robustness via fallback execution.  
Core assumption: Success probability of reasoning paths is predictable from table‑question characteristics, and agreement between CoT and a stronger path indicates answer reliability.  
Evidence: [Section 3.3] Sch determines execution order and skips a path if CoT aligns; [Section 4.4] ablation shows Sch reduces LLM calls by 14.6% (Penguins) and 7.6% (TableBench) with context‑dependent accuracy impact.  
Break condition: If Sch’s generalization fails on unseen distributions (e.g., novel schemas), misrouting may occur, reducing accuracy or efficiency.

### Mechanism 2: Confidence‑based early exiting
Claim: A Confidence Checker (CC) fine‑tuned on diverse model outputs makes early, cost‑effective decisions by assigning confidence scores to candidate answers, bypassing expensive JA calls when a high‑confidence answer exists.  
Mechanism: CC ingests structured representations (with special tokens) of CoT solutions, PoT/text2SQL code iterations, and execution results. It outputs per‑path confidence scores. If any score exceeds threshold θ=0.1, that answer is selected directly; otherwise, JA is invoked.  
Core assumption: A discriminative model (DeBERTaV3) trained on soft‑labeled (Exact Match + F1) multi‑reasoning outputs can reliably estimate answer correctness before JA evaluation.  
Evidence: [Section 3.3] Algorithm 3 details the skipping logic; [Section 4.4] Removing CC causes largest performance drop; CC reduces JA invocation by 95.8% (simple) and 60.6% (complex) while maintaining accuracy; [Appendix B.3] describes soft labeling and special tokens.  
Break condition: If CC’s training distribution (three datasets, three LLMs) does not cover a test case’s reasoning pattern or error mode, it may assign misleading scores, leading to missed correct answers or unnecessary JA calls.

### Mechanism 3: Lightweight SLM‑based tools
Claim: Small language models as specialized tools (Scheduler, Confidence Checker, Format Matcher) provide necessary orchestration and refinement at minimal computational overhead, enabling efficient scaling with small or diverse LLM backbones.  
Mechanism: Three <500M‑parameter tools handle scheduling (MobileBERT+MLP), confidence scoring (fine‑tuned DeBERTaV3‑large ~435M), and output formatting (qwen2.5‑0.5B). They process structured inputs and require far less compute than the ≥3B‑parameter LLM agents, which are selectively invoked.  
Core assumption: Task decomposition allows subfunctions to be learned effectively by smaller models, and their errors do not catastrophically affect final answer quality because JA remains as a fallback.  
Evidence: [Abstract] highlights lightweight tools; [Section 3.1] explicit parameter counts; [Section 4.3] MATA achieves SOTA with open‑source models as small as 3B, whereas baselines fail.  
Break condition: If tool training data (synthetic outputs from only three LLMs) does not capture error patterns or reasoning styles of a new backbone LLM, tool errors may propagate, leading to accuracy degradation that cannot be fully corrected by JA.

## Foundational Learning
- **Multi‑reasoning path diversity**: Using multiple reasoning approaches (CoT for textual/nuanced queries, PoT for numerical execution, text2SQL for structured tabular operations) because no single path is universally optimal across models and question types. *Why needed*: Avoid model‑specific failures and improve robustness. *Quick check*: For a given LLM backbone, how would you empirically determine whether CoT, PoT, or text2SQL is strongest on a validation set of mixed table questions?
- **Confidence‑based early exiting**: A mechanism to avoid expensive evaluations (like Judge Agent) when a confident answer exists. *Why needed*: LLM inference is expensive; invoking JA for every query negates efficiency gains. *Quick check*: What are the risks of setting the confidence threshold θ too low versus too high, based on the ablation study results?
- **Tool‑augmented LLM orchestration**: Offloading sub‑tasks (scheduling, scoring, formatting) to smaller specialized models instead of full LLMs. *Why needed*: Full reliance on LLMs for all sub‑tasks is computationally prohibitive; offloading reduces cost while maintaining performance via selective LLM use. *Quick check*: Why might a 500M‑parameter model (Format Matcher) suffice for answer extraction where a 7B+ LLM might over‑generate verbosely?

## Architecture Onboarding
Component map: T+Q → Sch → CoTA + (PoTA or t2SA) with debug loops → CC → (if max confidence < θ then JA) → FM (if len>100) → Final answer.

Critical path:
1. Scheduler activates before any LLM agent to determine execution order.
2. Confidence Checker activates after selected reasoning paths complete but before Judge Agent.
3. Format Matcher activates last, only on final answer length.

Design tradeoffs:
- Efficiency vs. Diversity: Sch reduces calls but may miss a correct path if prediction is wrong; disabling Sch uses all paths (more diverse candidates) but at higher cost. Benefit larger on simpler tasks; on complex TableBench, sometimes using all paths helps.
- Tool Reliance vs. fallback robustness: Tools (Sch, CC, FM) are small and fast but may fail on out‑of‑distribution patterns. JA acts as safety net but expensive. Tradeoff: how much tool error can be tolerated before JA must be invoked more often, eroding efficiency gains.
- Debug iterations (N): More iterations improve PoT/text2SQL correctness but incur extra LLM calls. Early stopping heuristics limit cost; diminishing returns beyond N≤2 for most models.

Failure signatures:
- Scheduler misprediction: On complex tables, Sch may incorrectly deprioritize a path that actually produces the correct answer, leading to lower accuracy if CoT and prioritized path disagree and the skipped path was correct. Monitor: correlation between Sch’s confidence scores and final answer correctness.
- Confidence Checker miscalibration: If CC’s soft labels do not align with true correctness on new data, high‑confidence candidates may be wrong. Monitor: calibration curve (confidence vs. actual accuracy) on held‑out domain.
- Debug loop non‑convergence: For some models (e.g., Mistral‑7B), code refinement may oscillate or fail to correct errors within N iterations. Monitor: stability metrics (code similarity, repeated errors) per model.
- Format Matcher over‑trimming: FM may extract too little context from verbose answers, dropping correct entities. Monitor: entity extraction F1 on paraphrase‑rich answers.

First three experiments:
1. **Scheduler standalone validation**: Run Sch on a held‑out set of (T,Q) pairs, record which path it prioritizes. Then run both paths to ground truth and compute: (a) accuracy if only prioritized path used, (b) accuracy if only non‑prioritized path used, (c) accuracy if both used. Hypothesis: prioritized path should have higher base accuracy; significance test (McNemar) on agreement cases where skipping the other path is safe.
2. **Confidence Checker calibration audit**: Feed CC with candidate answers from multiple LLMs on a diverse set, record output confidence scores. Plot reliability diagram (bin confidence vs. bin accuracy). Expected: well‑calibrated if scores correlate with EM/F1. If poorly calibrated, adjust θ or retrain CC with more diverse failure modes.
3. **Full MATA efficiency/accuracy sweep**: Run MATA with varying settings: (a) Sch on/off, (b) CC on/off, (c) N∈{1,3,5}, (d) θ∈{0.05,0.1,0.2}. Measure: (i) % JA invocations, (ii) total LLM agent calls, (iii) EM/F1. Expected: Optimal region where CC and Sch reduce calls >50% with <2% accuracy drop vs. full‑all‑paths baseline. Identify breakpoints where tool failures cause steep accuracy declines.

## Open Questions the Paper Calls Out
1. How can the fundamental computational cost of LLM inference be reduced in multi‑agent TableQA frameworks like MATA, beyond selectively minimizing agent calls? The paper identifies this as a key remaining bottleneck but provides no exploration on model compression, distillation, or hybrid architectures. Resolution requires systematic studies quantifying trade‑offs between accuracy and cost when replacing or compressing agent LLMs.
2. Under what specific conditions (e.g., table size, question type, model scale) does the Scheduler improve efficiency without degrading accuracy, and when does omitting it yield better results? The ablation shows context‑dependent contributions but lacks a controlled analysis to provide clear guidelines.
3. What are the underlying model‑specific factors (beyond size and openness) that cause such dramatic variations in the effectiveness of CoT, PoT, and text2SQL reasoning paths? The paper demonstrates variability but does not investigate root causes like training data distribution or architectural biases.
4. How well does the training dataset for Sch and CC generalize to out‑of‑distribution table schemas, domains, and question styles? Evaluation on two benchmarks shows strong performance but lacks error analysis categorizing failures by domain or schema novelty.
5. How does the multi‑agent, multi‑reasoning‑path architecture of MATA impact the propagation and mitigation of biases inherent in the backbone LLMs? The paper acknowledges inherited biases but provides no empirical study of bias in MATA’s outputs.

## Limitations
- Scheduler’s feature definitions and training splits are undocumented, impeding replication and generalization assessment.
- Tool training data is limited to three LLM backbones, raising concerns about reliability on novel models or domains.
- Confidence Checker’s reliance on soft labels may lead to mis‑calibration on unseen error patterns, causing false confidence or unnecessary Judge Agent calls.

2. **Confidence Checker calibration audit**: On a held‑out set generated by a novel backbone (e.g., Mistral‑7B), plot reliability diagram (binned confidence vs. actual EM/F1). Retune threshold θ based on calibration and measure JA invocation rate/accuracy trade‑off.
