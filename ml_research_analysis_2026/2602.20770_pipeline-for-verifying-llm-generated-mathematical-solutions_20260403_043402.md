# Pipeline for Verifying LLM-Generated Mathematical Solutions
## Quick Facts
- **arXiv ID:** 2602.20770  
- **Source URL:** https://arxiv.org/abs/2602.20770  
- **Reference count:** 30  
- **Primary result:** A three‑agent verification pipeline using structured lemmas, autoformalization to Lean4, and stepwise proving achieves high precision (98.4% on similar set, 94.2% on full Math‑500) but moderate recall (60.9% on similar), with interactive mode yielding zero false negatives/positives.

## Executive Summary
This paper introduces a pipeline for verifying the reasoning quality of LLM‑generated mathematical solutions, moving beyond mere answer correctness. By prompting a Solver LLM to produce structured proofs with explicit lemmas, autoformalizing them to Lean4 via a Translator, and then verifying each step with a Prover, the system can determine whether a solution is logically sound. Evaluated on subsets of the Math‑500 benchmark, the pipeline achieves high precision (up to 98.4%) and variable recall (95.3% on easy problems, 60.9% on a “similar” set). An interactive mode, where a human expert can intervene, eliminates all false negatives and positives, demonstrating the potential for hybrid human‑AI verification.

## Method Summary
The pipeline processes a problem and an LLM‑generated solution through a sequence of agents. First, a Solver LLM (e.g., Qwen3‑8B) outputs a proof composed of lemmas, each with a premise set and a single conclusion. A preprocessing script parses this output, enforces the schema, and separates standalone facts. The Translator LLM (Kimina‑Autoformalizer‑7B) then converts each lemma and fact into Lean4 tactic proofs, with post‑processing scripts that fix systematic errors (e.g., type mismatches). The Prover LLM (Kimina‑Prover‑Preview‑Distill‑7B) attempts to prove every formalized lemma using the context of earlier lemmas. Finally, a linking step uses Lean’s `solve_by_elim` tactic to assemble the proven lemmas into a full formal proof. The system runs either automatically (stopping at the first failure) or interactively, allowing a user to correct translations or admit `sorry` placeholders.

## Key Results
- Precision: 98.4% on 150‑problem “similar” set, 94.2% on full Math‑500.  
- Recall: 95.3% on 10‑problem easy set, 60.9% on “similar” set.  
- Interactive mode (with expert user) achieves 0 false negatives/positives.

## Why This Works (Mechanism)
### Mechanism 1: Structured Lemma Decomposition
**Claim:** Structuring the Solver LLM’s output into a sequence of lemmas with explicit premises and single‑conclusion outcomes dramatically simplifies downstream verification.  
**Mechanism:** Prompt engineering forces a “premises → conclusion” format for each logical step, where premises are limited to problem givens, prior lemmas, or obvious facts. This eliminates ambiguous or compound conclusions, creating a hypergraph of verifiable nodes.  
**Core assumption:** Human‑like reasoning can be decomposed into atomic, easily provable steps that a proof assistant can consume if explicitly delineated.  
**Evidence anchors:** [abstract] and [section 3.1] (formal schema, constraints on single conclusion, ≤3‑5 formal steps per lemma); neighboring work like “Step‑Wise Formal Verification for LLM‑Based Mathematical Problem Solving” (FMR 0.517) supports decomposition but the specific schema is novel here.  
**Break condition:** Solver LLM fails to produce any output adhering to the required schema, causing immediate pipeline failure (False Negative). Common for harder, olympiad‑style problems.

### Mechanism 2: Script‑Based Translator Correction
**Claim:** Post‑translation script‑based correction of the Translator LLM’s output compensates for the model’s inability to robustly handle the highly specific, structured input format.  
**Mechanism:** Scripts pre‑process the Solver’s structured output (e.g., removing tautologies, splitting compound conclusions) and post‑process the Translator’s Lean4 code to catch systematic errors (type mismatches, missing contexts). This bridges the gap between a general‑purpose autoformalizer (Kimina‑7B) and the pipeline’s narrow requirements.  
**Core assumption:** A fine‑tuned model for this exact schema would be ideal but is resource‑prohibitive; heuristic scripts are a cost‑effective stopgap for known failure modes.  
**Evidence anchors:** [section 3.2] notes overcoming Kimina‑Autoformalizer’s lack of responsiveness; [section 3.3, Step 2] describes rewriting error‑prone statements and checking structure/type correctness.  
**Break condition:** Scripts encounter an error pattern they are not programmed to handle, leading to a faulty Lean4 translation that fails to compile.

### Mechanism 3: Hypergraph‑Based Linking of Lemmas
**Claim:** Proving each lemma individually in isolation, then linking them via a hypergraph traversal (`solve_by_elim`), verifies the global logical coherence of the solution.  
**Mechanism:** The Prover LLM attempts to prove each formalized lemma using context from previous lemmas as additional premises. After all lemmas are proven, a separate linking step uses Lean’s `solve_by_elim` tactic to find a valid inference path connecting the lemma conclusions to the final theorem. This separates local correctness (each lemma) from global structure (the proof chain).  
**Core assumption:** If every local step is correct and the final linking tactic succeeds, the entire proof is correct. The separation allows the prover to focus on smaller sub‑goals.  
**Evidence anchors:** [section 3.3, Step 5 & 6] describes proving all lemmas with earlier context and then linking; [section 4.1] links correctness of formal solution to explicit logical steps; neighboring “Step‑Wise Formal Verification…” does not include the hypergraph linking, making this mechanism distinctive.  
**Break condition:** A single lemma cannot be proven even with context, or the `solve_by_elim` linking fails because the lemma graph is disconnected or a conclusion is missing (False Negative).

## Foundational Learning
- **Concept: Formal Verification with Lean4**  
  *Why needed here:* The pipeline’s final judgment is binary based on whether a Lean4 proof compiles; understanding Lean’s strict type system, tactic language, and Mathlib dependencies is essential to diagnose failures (e.g., a proof failure may be due to a missing type cast, not flawed reasoning).  
  *Quick check:* If a lemma states “x > 0” but `x` is declared as a `Nat` (non‑negative integer), will Lean accept this premise as given? What would you need to add? (Answer: Need to derive `x > 0` from properties of `Nat` or use a different type such as `ℤ`.)

- **Concept: Prompt Engineering for Structured Output**  
  *Why needed here:* The entire pipeline hinges on the Solver LLM producing a very specific, non‑standard format. Success depends on crafting prompts that reliably elicit this structure from a model not inherently trained for it.  
  *Quick check:* How would you modify the prompt for a word problem (e.g., “Alice has 5 apples…”) to force the introduction of explicitly typed variables (`a : ℕ`) as mentioned in section 3.4? (Answer: Include instructions to declare variables with explicit types and to reference problem givens as premises.)

## Architecture Onboarding
### Component map
Problem → Solver → Pre‑processing Script → Translator → Post‑translation Script → Prover → Linking → Report

### Critical path
The pipeline is sequential; each component must succeed before the next runs. A failure at any agent halts automatic progression.

### Design tradeoffs
- **Precision vs. Recall:** Strict schema and small models yield high precision (≥98% on similar set) but lower recall (60.9%).
- **Generality vs. Performance:** Tuned for Math‑500 (algebra/number theory); performance drops for geometry, higher math, and olympiad problems.
- **Automation vs. Cost:** Automatic mode is scalable but brittle; interactive mode (human‑in‑the‑loop) achieves 0 errors but requires a Lean expert.

### Failure signatures
- **Solver Failure:** Output does not match lemma format (missing `→`, compound conclusions, ambiguous references).
- **Translator Failure:** Lean code fails to compile (type mismatch, unknown identifier, failed synthesis).
- **Prover Failure:** `by` block fails; often due to lemma complexity, missing premises, or insufficient context.
- **Linking Failure:** `solve_by_elim` cannot connect final lemma to goal, indicating a structural break or missing step.

### First 3 Experiments
1. **Schema Adherence Test:** Run pipeline on easy dataset with `introduce_variables=False`; measure percentage of problems where Solver’s raw output matches required lemma format without script correction.
2. **Script Impact A/B Test:** For a fixed set of 20 problems where Translator fails compilation, run pipeline with and without post‑processing scripts; compare final success rates to quantify script contribution.
3. **Prover Substitution Stress Test:** Replace Kimina‑Prover with a larger model (e.g., DeepSeek‑V2.5) on the “similar” dataset; measure change in recall (lemma proving success) and any precision trade‑off.

## Open Questions the Paper Calls Out
1. **What technical approaches can effectively reduce false negatives arising from the discrepancy between human mathematical reasoning and proof assistant strictness?**  
   *Basis in paper:* Explicitly states that many false negatives arise due to type problems or small missed steps that are normal for humans but fatal for a proof assistant, and that this seems only partially overcome with ML and scripts.  
   *Why unresolved:* The bottleneck is identified but no concrete mitigation strategies are proposed or evaluated.  
   *What evidence would resolve it:* Comprehensive failure analysis on a benchmark to categorize strictness‑induced errors, development of automated correction mechanisms, and demonstration of statistically significant false negative reduction.

2. **How can the pipeline’s reliance on structured lemma decomposition be adapted to solve problems that don’t naturally decompose into independent, easily formalizable steps, such as advanced olympiad or research‑level mathematics?**  
   *Basis in paper:* Notes that the pipeline is harder to generalize onto harder, more olympiad‑oriented problems because each step would be harder to formalize as an “easy/evident” lemma; such problems are excluded because the Solver LLM cannot produce the required structure.  
   *Why unresolved:* The core assumption (easy lemmas) may be invalid for complex reasoning; alternative decomposition or representation methods are unexplored.  
   *What evidence would resolve it:* Design and implementation of a modified pipeline that handles a representative sample of currently failing olympiad problems, with validation showing successful verification where the original pipeline fails.

3. **Which specific components (Solver LLM prompting, Translator scripts, Prover model capacity) are the primary limiting factors for recall, and how much can recall on the “similar” dataset be improved through targeted enhancements?**  
   *Basis in paper:* Reports recall = 0.609±0.006 on the similar set and notes “can be improved with scripts and larger models” without further details.  
   *Why unresolved:* Limiting factors are not identified; claimed improvability is unquantified and unverified.  
   *What evidence would resolve it:* Ablation study isolating each component’s impact on recall, followed by systematic improvements (e.g., better prompts, larger Prover models, more sophisticated scripts) and measurement of recall gains on the same benchmark.

4. **Does the choice of proof assistant significantly impact the pipeline’s domain coverage and accuracy, and could alternative systems (e.g., Isabelle/HOL, Coq) enable verification of currently unsupported problem types like geometry?**  
   *Basis in paper:* Paper states switching proof assistants “will not change the steps of the algorithm” but only implements Lean4; geometry and higher math are excluded, potentially due to Lean4’s library limitations. No comparative evaluation is performed.  
   *Why unresolved:* The claim of proof‑assistant independence is speculative; other systems might have different strengths/weaknesses affecting generalizability.  
   *What evidence would resolve it:* Reimplementation of the pipeline with a different proof assistant covering a distinct domain (e.g., geometry via Isabelle’s geometry libraries), direct comparison of verification success rates on overlapping and domain‑specific problem sets.

## Limitations
- Unspecified toolchain versions (Lean4/Mathlib), exact solver prompts, and hardware/sampling settings hinder faithful reproduction and performance benchmarking.
- Moderate recall (60.9% on “similar” set) indicates brittleness, especially on complex or poorly‑structured solutions.
- Domain is confined to Math‑500 (algebra/number theory); geometry, higher mathematics, and many olympiad problems are unsupported.
