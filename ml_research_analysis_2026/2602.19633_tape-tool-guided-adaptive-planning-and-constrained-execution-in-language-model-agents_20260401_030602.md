# TAPE: Tool-Guided Adaptive Planning and Constrained Execution in Language Model Agents

## Quick Facts
- arXiv ID: 2602.19633
- Source URL: https://arxiv.org/abs/2602.19633
- Reference count: 40
- Primary result: TAPE improves average success rates by 21.0 percentage points on hard settings and by 20.0 points for weaker base models.

## Executive Summary
Language model (LM) agents often fail irrecoverably under strict feasibility constraints (e.g., step budgets, tool usage limits) due to imperfect planning and stochastic execution errors. TAPE introduces a framework that combines multi-candidate planning with an external constraint solver and adaptive execution control. It generates multiple abstract plans, builds a plan graph merging equivalent states, annotates edges with costs and nodes with rewards using the LLM’s internal world model, and then selects a constraint-feasible path via integer linear programming (ILP). During execution, constrained decoding forces the agent to follow the planned action, suppressing sampling errors. If the environment deviates from the predicted state, TAPE replans. Evaluations on Sokoban, ALFWorld, MuSiQue, and GSM8K-Hard show consistent improvements over ReAct and Plan-and-Act, with large gains (21.0 pp) on hard constrained variants and even 20.0 pp for weaker base models.

## Method Summary
TAPE is a training-free framework that leverages an off-the-shelf LLM. At each decision point it: (1) samples M distinct abstract plans from the current abstract state; (2) simulates each plan to derive state transitions and merges nodes with identical observations into a directed plan graph; (3) uses the LLM to predict edge costs and node rewards, encoding the internal world model; (4) formulates an ILP to find a path from the current node to a goal respecting global budgets (step limits, tool costs); (5) executes the first action of the chosen path via constrained decoding (e.g., logit masking) to avoid sampling drift; (6) after execution, projects the true environment state back to an abstract state and compares with the planned next node; a mismatch triggers replanning from step 2. The loop continues until the goal is reached or budgets are exhausted.

## Key Results
- TAPE outperforms ReAct and Plan-and-Act across all four benchmarks under constrained settings.
- On hard variants, it raises average success rates by 21.0 percentage points (stronger models) and 20.0 points (weaker models).
- Ablations attribute gains to reduced planning errors (via ILP selection) and fewer sampling errors (via constrained decoding).

## Why This Works (Mechanism)
TAPE’s effectiveness stems from addressing both planning and execution failure modes simultaneously. First, by generating multiple candidate plans and merging them into a graph, the approach explores a richer space of trajectories than a single linear plan. The ILP solver then globally optimizes path selection under the given feasibility constraints, eliminating local planning errors that would otherwise cause dead ends. Second, the use of constrained decoding guarantees that the agent’s stochastic output adheres to the planned action, removing a major source of sampling errors. Finally, the mismatch-driven replanning mechanism provides adaptivity: if the environment behaves differently than predicted (e.g., due to partial observability or LLM world model inaccuracies), the graph is regenerated from the new state, preventing the agent from persisting along an invalid path. This combination yields robust performance even under tight budgets and with weaker LLMs.

## Foundational Learning
- **Abstract State Representation**: A compact, task-specific textual encoding (e.g., player/object locations). Why needed: enables state comparison and merging across different plans. Quick check: two states with identical text are considered equal.
- **Plan Graph**: A directed graph whose nodes are abstract states and edges are actions with associated cost predictions. Why needed: captures multiple plan alternatives and their interactions, allowing global constraint satisfaction. Quick check: graph contains at least one path from start to goal if a feasible solution exists.
- **ILP-based Path Selection**: An optimization that selects a path minimizing cost (or maximizing reward) subject to budget constraints. Why needed: finds a globally feasible route when individual plans may violate constraints. Quick check: solver returns a path when the graph is feasible; returns infeasible otherwise.
- **Constrained Decoding**: Modification of the LLM’s decoding process to restrict the output vocabulary to a predetermined action. Why needed: prevents the model from deviating due to sampling randomness. Quick check: logit masking or grammar enforcement ensures only the planned action can be generated.
- **Adaptive Replanning**: After each execution step, the agent checks if the realized state matches the planned successor; mismatches cause graph regeneration. Why needed: recovers from world model errors and environmental stochasticity. Quick check: any state mismatch triggers a replanning cycle.

## Architecture Onboarding
Component map (plain text):
Candidate Plan Generator (LLM) -> Plan Graph Builder -> ILP Solver -> Constrained Executor -> Environment -> State Projector -> Mismatch Detector --(mismatch)--> Plan Graph Builder

Critical path:
1. Generate M plans from current abstract state.
2. Build plan graph (merge states, predict costs/rewards).
3. Solve ILP to obtain feasible action sequence.
4. Execute first action via constrained decoding.
5. Observe next environment state, project to abstract state, compare with planned successor.
6. If match, advance current node and repeat from step 3; if mismatch, return to step 2.

Design tradeoffs:
- Plan count (M): larger M yields more graph coverage and higher chance of feasible path but increases LLM calls and graph size.
- State merging granularity: coarse merging reduces graph size but may conflate distinct states, leading to invalid edges; fine merging increases accuracy at the cost of complexity.
- Budget tightness: tighter budgets increase risk of infeasibility; may require adjusting M or lookahead.
- Replanning threshold: frequent replanning introduces overhead; a single mismatch does not always imply graph regeneration is needed—could consider tolerance windows.

Failure signatures:
- ILP reports infeasible while a brute-force search finds a feasible path → graph construction or cost annotation error.
- Constrained decoder allows non-planned actions → decoding mask not applied correctly.
- Continuous replanning loop → world model predictions are poor; state projection mismatches too often.
- Graph explosion (exponential nodes) → state merging function too permissive or M too large.

First experiments:
1. **Plan Diversity Test**: For a fixed start state in Sokoban, call the plan generator with different temperatures and measure plan edit distance; confirm diversity as M increases.
2. **Graph-Solver Sanity Check**: Manually construct a tiny graph with 3 nodes and a known feasible path, assign simple costs, run the ILP solver and verify it returns the expected path under a budget.
3. **Constrained Decoding Verification**: Given a planned action "move left", force constrained decoding and confirm the LLM never outputs other actions across multiple sampling runs, even at high temperature.

## Limitations
- Implementation gaps for non-Sokoban tasks: exact prompts and state merging functions are unspecified, limiting cross-task reproducibility. (Confidence: Low for cross-task generality)
- Hyperparameter sensitivity: optimal plan count M, lookahead L_max, and decoding constraints vary by task and are not systematically tuned. (Confidence: Medium for core mechanism, Low for practical tuning)
- Reliance on external ILP solver and LLM-based cost/reward predictions: correctness depends on solver accuracy and the quality of LLM predictions, which are loosely defined. (Confidence: Medium)

## Confidence
- Core mechanism (graph + ILP + constrained decoding): Medium – conceptually sound, but empirical details affect performance.
- Cross-task generalization (handling ALFWorld, MuSiQue, GSM8K-Hard): Low – missing prompt templates and state merging specifics.
- Hyperparameter robustness: Medium/Low – core mechanism robust to some variation, but practical tuning remains uncertain.
- Solver reliance: Medium – ILP solving is reliable, but its effectiveness depends on accurate cost annotations.

## Next Checks
1. **Prompt audit**: Re-derive and test prompts for ALFWorld, MuSiQue, and GSM8K-Hard following the Sokoban style; measure resulting plan diversity and consistency of state abstractions.
2. **Graph sanity check**: On a subset of tasks, manually verify via brute-force search that a feasible path exists in the constructed graph whenever the ILP solver reports infeasibility.
3. **Ablation thresholds**: Systematically vary M (e.g., 5, 10, 20) and L_max across budgets on a representative benchmark to identify tipping points where replanning overhead outweighs success gains.
