# EVMbench: Evaluating AI Agents on Smart Contract Security

## Quick Facts
- **arXiv ID:** 2603.04915
- **Source URL:** https://arxiv.org/abs/2603.04915
- **Reference count:** 40
- **Primary result:** Frontier agents achieve up to 71.0% on end-to-end exploits; hint experiments reveal vulnerability discovery as the primary bottleneck, with medium hints boosting GPT-5.2’s patch score to 90.2% and exploit score to 78.3%.

## Executive Summary
EVMbench introduces a comprehensive benchmark for evaluating AI agents on smart contract security, focusing on three critical tasks: detecting vulnerabilities, patching code, and exploiting contracts on a live blockchain. The benchmark comprises 117 high-severity vulnerabilities sourced from real-world Code4rena audits, with programmatic grading via tests and on-chain state verification. Frontier models show promising but incomplete capabilities: GPT-5.3-Codex achieves 71.0% on end-to-end exploits, while Claude Opus 4.6 leads detection at 45.9% recall. Crucially, medium hints (e.g., file location) dramatically boost GPT-5.2’s patch and exploit scores to 90.2% and 78.3%, indicating that vulnerability discovery—rather than code repair or transaction construction—is the primary bottleneck. False positives and limited task scope remain constraints, highlighting areas for future improvement in agent-based security analysis.

## Method Summary
The evaluation runs each agent in an isolated Ubuntu 24.04 Docker container pre-installed with Foundry and internet disabled. The agent interacts with the codebase and a local Ethereum chain (Anvil) via a scaffold such as OpenCode’s ReAct loop or vendor CLIs (Codex CLI, Claude Code). For detection, the agent outputs an audit report; for patching, it directly modifies Solidity files; for exploitation, it constructs and dispatches transactions through JSON-RPC. Grading is fully automated: detection uses a judge model to match reported vulnerabilities to a ground-truth ID list; patching requires that the original test suite passes and provided exploit tests fail; exploitation replays the agent’s recorded transaction sequence on a fresh chain and checks vulnerability-specific state changes (e.g., attacker balance increase). The corpus includes 117 high-severity flaws from 40 Code4rena audit repositories, each packaged in a Docker image with source code, tests, and optional hints (low/medium/high). The harness prevents cheating via a Veto RPC proxy that blocks Anvil admin methods and uses a Rust-based `ploit` tool to record and deterministically replay agent actions.

## Key Results
- GPT-5.3-Codex achieves 71.0% success on end-to-end exploit tasks.
- Claude Opus 4.6 leads detection with 45.9% recall.
- Providing medium hints raises GPT-5.2’s patch success to 90.2% and exploit success to 78.3%, confirming that vulnerability discovery is the main bottleneck; false positives and limited scope remain constraints.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Vulnerability discovery in large codebases is the primary performance bottleneck, not code repair or transaction construction.
- **Mechanism:** Agents possess foundational Solidity and EVM knowledge but struggle with systematic code exploration and pinpointing the specific vulnerable code path among many. Providing targeted hints (file location, mechanism type) dramatically boosts Patch and Exploit scores, indicating that narrowing the search space alleviates the core limitation.
- **Core assumption:** The agent's internal representation of the codebase is noisy or incomplete; reducing the combinatorial search space enables its existing reasoning and coding skills to succeed.
- **Evidence anchors:**
  - [abstract] "...medium hints boost GPT-5.2’s patch and exploit scores to 90.2% and 78.3%, indicating discovery—not repair or transaction construction—is the primary bottleneck."
  - [section 4.1] "The results of this experiment indicate that the difficulty in the Patch mode can largely be attributed to the difficulty of vulnerability discovery in large repositories."
  - [corpus] Corpus neighbors focus on general vulnerability detection or auditing, not the specific discovery-vs-repair dissociation measured here. Evidence is weak/absent.
- **Break condition:** If hint experiments showed no performance gap between hint and no-hint conditions, this mechanism would be invalidated.

### Mechanism 2
- **Claim:** Agent performance is heavily mediated by scaffold/tooling design, not just base model capability.
- **Mechanism:** The agent's control loop (e.g., OpenCode's ReAct pattern vs. Codex/Claude CLIs) determines how effectively it can use tools, manage context, and sequence actions. Differences in scaffold explain performance gaps between model families and reasoning levels beyond raw token output.
- **Core assumption:** The benchmark's environment (Docker, blockchain RPC, file system) is complex enough that the agent's orchestration logic is a first-order factor in success.
- **Evidence anchors:**
  - [section 4] "GPT-5.2 scores higher when run via Codex CLI compared to when run via OpenCode."
  - [section 5] "the OpenCode baseline trails stronger scaffolds even with similar model families, underscoring that tooling and workflow choices materially affect outcomes."
  - [corpus] Neighbors like "SmartAuditFlow" and "Cybergym" also investigate tooling/agent frameworks, providing contextual evidence that architecture matters, though not specific to this benchmark.
- **Break condition:** If a controlled experiment with the same model but swapped scaffolds showed no significant performance difference, the claim would weaken.

### Mechanism 3
- **Claim:** Deterministic, on-chain state verification enables a realistic and reproducible end-to-end exploit evaluation.
- **Mechanism:** By running agent transactions against a local EVM (Anvil) and grading via programmatic state checks (balances, events), the harness creates a sandbox where exploit success is a verifiable outcome of the agent's actions, resistant to grading ambiguity or cheating.
- **Core assumption:** A live, deterministic blockchain environment with a funded attacker wallet and isolated state accurately captures the core skills of a real-world smart contract exploit without requiring live mainnet interaction.
- **Evidence anchors:**
  - [section 3.2.3] "In the Exploit mode... we replay its transactions in an isolated grader container and run vulnerability-specific checks over contracts and balances."
  - [section 3] "Blockchains provide natural, machine-checkable indicators of success, such as balance changes..."
  - [appendix D] Details on `ploit` and `veto` tooling that ensure faithful replay and prevent cheating via admin RPC calls.
- **Break condition:** If a significant fraction of "successful" exploits in the harness failed on a forked mainnet state due to external dependencies (oracles, other contracts), the realism—and thus the mechanism's validity—would be compromised.

## Foundational Learning
- **Smart Contract Vulnerability Classes** (e.g., reentrancy, access control)
  - *Why needed here:* The agent must map code patterns to specific loss-of-funds mechanisms. Detection, patching, and exploiting all require recognizing the canonical flaw.
  - *Quick check:* For the `withdraw` function that calls `msg.sender.call` before zeroing `balances[msg.sender]`, what is the vulnerability class and the minimal fix?
- **Agent Control Loops** (e.g., ReAct)
  - *Why needed here:* The scaffold determines if the agent can effectively alternate between code analysis, tool use (compilation, casting), and transaction construction. A poorly designed loop leads to wasted steps or context collapse.
  - *Quick check:* In a ReAct loop for Exploit mode, what are the three core action types the agent must sequence after finding a vulnerability?
- **Deterministic State Replay**
  - *Why needed here:* The Exploit grader's reliability depends on identical chain state evolution from the same initial conditions and transaction sequence. Understanding this is key to trusting the evaluation.
  - *Quick check:* If an agent's exploit depends on the block timestamp, why might the `ploit` grader produce a false negative?

## Architecture Onboarding
**Component map:**
1. *Task Curator:* Selects 117 vulnerabilities from Code4rena audits, defines per-audit Docker images with source code, tests, and hints.
2. *Agent Runtime:* Spins up an isolated Ubuntu container with Foundry, internet disabled, and connects to a local blockchain RPC. The agent (via CLI scaffold) reads code, reasons, and issues actions (file edits, shell commands, cast transactions).
3. *Blockchain Harness (`ploit`):* Rust tool that starts Anvil, deploys contracts via Foundry scripts, records the agent's RPC calls/transactions.
4. *Grader:* Separate container. Re-deploys contracts, replays agent's transaction sequence against Anvil, runs per-vulnerability verification scripts (e.g., "check attacker balance > X ETH").
5. *Veto Proxy:* JSON-RPC gateway that blocks Anvil-specific admin methods (e.g., `anvil_impersonateAccount`) to prevent cheating.

**Critical path:** Agent's RPC transaction sequence → `ploit` recording → Grader replay on clean chain → Script-based state checks → Score.

**Design tradeoffs:**
- *Realism vs. Control:* Fresh chain deployment (no mainnet state) increases reproducibility but omits cross-protocol dependencies. Mock tokens simplify setup but may distract agents.
- *Generality vs. Cost:* Hand-crafted exploit scripts per vulnerability are reliable but limit task scale (only 23 exploits). Automatic exploit generation would scale but risk false negatives.
- *Hint Transparency:* Providing hints boosts scores but may measure the agent's ability to use hints rather than raw discovery skill; the paper reports both.

**Failure signatures:**
- **Exploit:** Agent's transactions replay successfully but final state checks fail (incomplete exploit path) or exploit involves `veto`-blocked methods.
- **Detect:** Agent's audit report is verbose but misses the specific ground-truth vulnerability ID; or judge model flags false positives/hallucinations.
- **Patch:** Agent's changes break existing non-vulnerable tests; or exploit test still passes post-patch.

**First 3 experiments:**
1. **Run a Detect task manually.** Execute the OpenCode CLI on a sample audit. Verify that the model writes to `submission/audit.md`. Inspect the judge prompt output to understand scoring logic.
2. **Test the hint regime.** Run a Patch task for the same vulnerability with no hints, then with medium hints. Observe the difference in agent behavior (does it find the vulnerable function faster?).
3. **Validate an Exploit grader.** Manually execute the oracle exploit script against a fresh Anvil instance. Then, replay a known-failing agent transaction sequence and confirm the grader correctly returns a failure score.

## Open Questions the Paper Calls Out
1. **How can the Detect mode be improved to both reward discovery of unknown vulnerabilities and penalize false positives?** The current evaluation relies on a closed set of vulnerabilities from historical reports; it cannot credit agents for finding new valid issues nor penalize false positives that slip through. A redesign involving expert validation or cross-run consistency could address this.
2. **What approaches can automate the generation of Patch and Exploit tasks to scale EVMbench beyond the current small set?** Manual curation of oracle patches and exploits is time-intensive, limiting the benchmark to 44 patch and 23 exploit vulnerabilities. A semi-automated pipeline that produces valid patches and exploits with minimal human intervention would enable broader coverage.
3. **To what extent do the smart contract security capabilities evaluated in EVMbench transfer to other blockchain environments?** The benchmark is restricted to EVM-Solidity; capabilities on chains like Solana (Rust) or in protocol/node security may differ due to distinct execution models. Creating analogous benchmarks for those domains would measure transferability.
4. **What are the primary factors limiting agents' comprehensive coverage in Detect tasks?** Even when agents can exploit individual vulnerabilities end-to-end, they often fail to cover all vulnerabilities in a codebase. The nature of the coverage bottleneck (e.g., codebase navigation, attention allocation, tool usage) remains unclear and warrants behavioral ablations.

## Limitations
- **Hint transparency bias:** Medium hints may measure an agent’s ability to leverage guidance rather than pure discovery skill; the dissociation between discovery and repair is inferential.
- **External validity gap:** Evaluation on fresh chain deployments may miss real-world dependencies (oracles, cross-contract calls) that affect exploit feasibility on live mainnet.
- **Scaffold/configuration opacity:** Exact Anvil parameters (timestamp, gas) and the `veto` guard’s full deny-list are unspecified, potentially enabling subtle cheating or timing failures.

## Confidence
- **Mechanism 1 (discovery bottleneck):** Medium confidence. Strong internal evidence from hint experiments, but limited external corroboration and potential confound from hint utility.
- **Mechanism 2 (scaffold impact):** High confidence. Direct comparative runs (Codex CLI vs. OpenCode) show significant score deltas, aligning with tooling literature.
- **Mechanism 3 (deterministic replay):** High confidence, conditional. The grader’s state-check design is sound, but realism hinges on the break condition: if many exploits rely on mainnet-specific dependencies, scores may overestimate success.

## Next Checks
1. **Controlled hint ablation:** Run identical Detect/Patch/Exploit tasks with/without medium hints on the same agent scaffold to quantify the isolated discovery gap, controlling for model and tooling.
2. **Forked-mainnet replay test:** For a subset of Exploit tasks, grade against a mainnet-forked chain state (with real dependencies) to measure false-negative rates attributable to missing external context.
3. **Veto guard penetration test:** Attempt to bypass the `veto` proxy using non-`anvil_*` admin methods (e.g., `hardhat_setBalance`) in the agent container; verify if the grader rejects such transaction sequences.
