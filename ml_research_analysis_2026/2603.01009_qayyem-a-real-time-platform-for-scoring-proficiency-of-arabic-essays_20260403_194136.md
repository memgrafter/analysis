# Qayyem: A Real-time Platform for Scoring Proficiency of Arabic Essays

## Quick Facts
- **ArXiv ID:** 2603.01009
- **Source URL:** https://arxiv.org/abs/2603.01009
- **Reference count:** 21
- **Primary result:** Qayyem is a deployable web platform for Arabic Automated Essay Scoring (AES) that uses cross-prompt models; the TRATES model achieves the best effectiveness (avg. QWK 0.653) but is ~30x slower than feature-based models like XGBoost.

## Executive Summary
Qayyem addresses the lack of deployable Arabic AES systems by providing a full-stack web platform for end-to-end assessment workflows. It abstracts the technical complexity of model APIs, allowing instructors to create assignments, upload batches of essays, configure multi-trait rubrics, and review scores through a user-friendly interface. The system deploys state-of-the-art models trained on the LAILA dataset in a cross-prompt setting, enabling immediate use on new prompts without retraining. Evaluation reveals a clear trade-off: the TRATES model offers the highest accuracy (average Quadratic Weighted Kappa of 0.653 across seven traits) but requires about 30 seconds per essay, while the XGBoost model is approximately 20 times faster (~0.2s/essay) with moderately lower accuracy (avg. QWK 0.593). The platform is publicly accessible via both a web interface and an API.

## Method Summary
Qayyem leverages the LAILA dataset (7,859 Arabic essays across 8 prompts) to train models in a cross-prompt manner using official leave-one-prompt-out splits. Three model categories are deployed: (1) advanced LLM-based (TRATES, which uses Fanar-1-9B to generate trait-specific features), (2) intermediate (MOOSE, an AraBERT-based mixture-of-experts), and (3) efficient feature-based (Random Forest, XGBoost, neural networks). All models rely on 816 handcrafted linguistic features (surface, lexical, syntactic, readability, semantic), with feature selection applied via correlation thresholds. The system architecture separates a Next.js frontend from a FastAPI scoring backend, connected via an NGINX gateway and a key manager for authorization. Instructors interact solely with the frontend to manage assignments and trigger batch scoring, while the backend handles model inference and streams real-time progress.

## Key Results
- The TRATES model achieves the highest average Quadratic Weighted Kappa (QWK) of 0.653 across seven writing traits on the LAILA test set.
- A stark effectiveness–efficiency trade-off exists: TRATES requires ~30 seconds per essay, while XGBoost is ~20x faster (~0.2s/essay) but with lower accuracy (avg. QWK 0.593).
- Qayyem is publicly available as a web platform and API, enabling instructors to apply cross-prompt Arabic AES without direct model interaction.

## Why This Works (Mechanism)

**Mechanism 1: Abstraction of API Complexity**
Claim: Qayyem enables instructors to use state-of-the-art Arabic AES without technical API interaction.
Mechanism: The Assignment Manager frontend encapsulates all communication with the Scoring Server, presenting a simplified UI for assignment creation, rubric design, and batch essay upload. It translates user actions into authorized API requests and handles streaming responses.
Core assumption: Instructors' primary barrier is API complexity, not a lack of desire for advanced scoring.
Evidence anchors: Abstract states Qayyem abstracts technical complexity; Section 4.1 describes the full-stack web application design that avoids direct API interaction.
Break condition: If the backend API changes or model endpoints are deprecated without frontend updates, the abstraction fails, exposing instructors to complexity.

**Mechanism 2: Cross-Prompt Generalization via LAILA Training**
Claim: Cross-prompt generalization is achieved by training models on the LAILA dataset and deploying them without retraining per new assignment.
Mechanism: Models are trained on LAILA's 8 diverse prompts using leave-one-prompt-out cross-validation, forcing them to learn prompt-agnostic linguistic features. The platform allows immediate application to new, unseen prompts.
Core assumption: Linguistic features (e.g., syntax, vocabulary range) are stable indicators of writing quality across different Arabic essay prompts.
Evidence anchors: Abstract mentions generalization without retraining; Section 5 states all models are trained in a cross-prompt setting using LAILA's released splits.
Break condition: Performance degradation on prompts with extreme topical or genre divergence from LAILA's persuasive/explanatory essays (e.g., creative narratives, technical subjects).

**Mechanism 3: Configurable Effectiveness-Efficiency Trade-off**
Claim: The system provides a configurable trade-off via multiple model deployments.
Mechanism: Qayyem bundles models with varying architectures: complex LLM-based (TRATES: ~30s/essay, QWK 0.653), intermediate (MOOSE: ~1s, QWK 0.597), and efficient feature-based (XGBoost: ~0.2s, QWK 0.593). The UI presents performance ratings (0-5 stars) to guide selection.
Core assumption: Users have heterogeneous needs for throughput vs. accuracy and can make informed trade-offs.
Evidence anchors: Section 5 Table 1 and Figure 4 explicitly compare QWK and inference time; Section 3.2 describes UI performance ratings.
Break condition: If all models are too slow for a user's batch size requirement (e.g., thousands of essays) or if the fastest model's accuracy (QWK ~0.59) is below their minimum acceptable threshold for high-stakes decisions.

## Architecture Onboarding

**Component map:**
Frontend (Next.js) -> Assignment Manager (Node.js/Prisma) -> API Gateway (NGINX) -> Scoring Server (FastAPI/Uvicorn) -> Models (PyTorch/sklearn/XGBoost). Also: Key Manager for auth and rate limiting.

**Critical path:**
1) Instructor creates assignment (Frontend → Assignment Manager DB)
2) Uploads essays (Frontend → Assignment Manager DB)
3) Clicks "Score" (Assignment Manager → API Gateway → Scoring Server)
4) Scoring Server loads model, streams progress via SSE
5) Scores returned, stored in DB
6) Review UI displays results

**Design tradeoffs:**
- Effectiveness vs. Latency: TRATES uses LLM calls per trait → high accuracy, high latency; feature-based models use pre-computed vectors → low latency, lower accuracy.
- Generality vs. Specialization: Cross-prompt models work for new prompts but may underfit domain-specific cues compared to prompt-specific models (not deployed).
- Bundling vs. Modularity: Models are bundled in one server for simplicity, but a failure in one model (e.g., OOM with TRATES) could affect service if not isolated.

**Failure signatures:**
- Gradual degradation: QWK scores on review prompts drop significantly below reported averages (~0.65 for TRATES, ~0.59 for XGB).
- Timeout/error: Batch uploads with TRATES time out (>30s/essay) if GPU memory exhausted or LLM API rate-limited.
- Data mismatch: Essay format rejection (e.g., wrong file type) or rubric-trait misalignment (user selects unavailable trait).

**First 3 experiments:**
1. Model sanity check: Score 5 known LAILA test essays via API with TRATES; verify returned QWK-scaled scores align with expected distribution.
2. Performance benchmark: Batch-upload 50 essays; measure end-to-end time for each model type (XGBoost vs. TRATES) to confirm ~20x speed difference.
3. API contract test: Call the `/score` endpoint with a deliberately malformed JSON payload; verify a structured error (HTTP 422) without server crash.

## Open Questions the Paper Calls Out
1. Can TRATES's inference time be reduced from ~30 seconds to under 1 second with less than a 0.03 QWK drop relative to XGBoost?
2. Does expanding the LAILA dataset with more diverse Arabic essays (e.g., dialects, genres) disproportionately benefit LLM-based models over feature-based ones in cross-prompt settings?
3. How does instructor-led manual refinement of automated scores in Qayyem affect final grading agreement with human raters, and what traits are most frequently adjusted?
4. Can Qayyem’s architecture efficiently serve multiple high-resource models (e.g., TRATES) under concurrent user load without degradation in response time?

## Limitations
- Exact code for extracting the 816 handcrafted features is unknown, blocking faithful model replication.
- Official LAILA file schema and leave-one-prompt-out split definitions are not detailed, risking data leakage in reproduction.
- Full API endpoint schemas and Scoring Server configuration format are inaccessible, hindering integration testing.
- TRATES internals (Fanar prompts, feature fusion method) are vaguely described.
- Generalization to prompts divergent from LAILA's persuasive/explanatory genre is unverified.

- Mechanism 2 (Cross-prompt generalization via LAILA): High
