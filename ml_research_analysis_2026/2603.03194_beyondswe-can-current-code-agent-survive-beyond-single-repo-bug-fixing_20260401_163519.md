# BeyondSWE: Can Current Code Agent Survive Beyond Single-Repo Bug Fixing?

## Quick Facts
- **ArXiv ID:** 2603.03194  
- **Source URL:** https://arxiv.org/abs/2603.03194  
- **Reference count:** 40  
- **Primary result:** Frontier models achieve ≤45% success on BeyondSWE; search integration yields inconsistent gains.

## Executive Summary
BeyondSWE introduces a benchmark of 500 real‑world software engineering instances spanning four tasks that go beyond single‑repo bug fixing: cross‑repository resolution, domain‑specific fixes, dependency migration, and full repository generation from specifications. Evaluation of nine frontier models reveals that no model exceeds 45% success and none dominates all task types, highlighting significant capability gaps. Augmenting agents with web search (SearchSWE) produces inconsistent improvements—helping some tasks while hurting others—exposing a fundamental disconnect in current LLMs' ability to interleave external search with code reasoning. The authors also propose rigorous environment reconstruction and sanitization methods to ensure evaluation integrity.

## Method Summary
The authors built the BeyondSWE benchmark by scraping real GitHub pull requests, filtering for well‑defined issues, and constructing reproducible Docker environments. Each instance includes a pre‑built Docker image, a problem statement (issue or specification), and a test suite (P2P/F2P tests for bug fixing; full suite for repo generation). Environments are validated through a 5‑run stability test to ensure determinism. For evaluation, they use OpenHands as the base agent framework and extend it with SearchSWE, adding search tools (SerpAPI, Jina Reader) and a blocklist to prevent access to the target repository. Agents operate for up to 200 turns; their final patches are applied to fresh containers and verified against the test suite. Success metrics are Resolved Rate for the first three tasks and Pass Rate for Doc2Repo.

## Key Results
- Frontier models achieve ≤45% success on BeyondSWE; no single model dominates across all four task types.
- Search augmentation yields inconsistent gains: improves some tasks (e.g., CrossRepo) but degrades others (e.g., Doc2Repo), revealing a fundamental disconnect in integrating external search with code reasoning.
- These results highlight that current code agents struggle with multi‑dimensional software engineering challenges beyond single‑repo bug fixing.

## Why This Works (Mechanism)

### Mechanism 1
**Claim:** Expanding evaluation dimensions exposes fundamental capability gaps invisible to narrow benchmarks.  
**Mechanism:** By varying resolution scope (function → repository → system) and knowledge scope (local → cross‑repo → domain → web), BeyondSWE forces agents to demonstrate distinct reasoning patterns. Single‑repo bug fixing allows memorization of common patterns; cross‑task evaluation reveals whether capabilities generalize.  
**Core assumption:** Real‑world software engineering requires integration of multiple skill dimensions, not isolated patch generation.  
**Evidence anchors:**  
  - [abstract] "current benchmarks...overlooking critical real‑world challenges such as cross‑repository reasoning, domain‑specialized problem solving, dependency‑driven migration, and full‑repository generation"  
  - [section 1] "existing benchmarks remain fundamentally localized...This stands in stark contrast to real‑world software engineering"  
  - [section 5.2] "different tasks demand different capabilities: Gemini 3 Pro leads on DepMigrate, Seed‑Coder excels on CrossRepo...no single model dominates across all dimensions"  
  - [corpus] Neighbors focus on agent survival and search, but lack systematic multi‑dimensional benchmark design—this paper's contribution is distinctive  
**Break condition:** If benchmark tasks prove artificial or ceiling effects emerge (all models >90% success), indicating insufficient challenge.

### Mechanism 2
**Claim:** External search integration is fundamentally non‑linear; it can harm performance due to information misalignment.  
**Mechanism:** SearchSWE reveals three failure modes: (1) Information landscape gap (search returns human docs when code artifacts are needed), (2) Temporal misalignment (search gives latest docs vs. legacy constraints), (3) Semantic drift (polysemous terms retrieve irrelevant content). These cause search to act as noise injection rather than knowledge augmentation.  
**Core assumption:** Search and coding capabilities have matured independently; their integration requires explicit architectural mechanisms not present in current LLMs.  
**Evidence anchors:**  
  - [abstract] "search augmentation yields inconsistent gains and can in some cases degrade performance"  
  - [section 5.3] "CrossRepo benefits most broadly...Doc2Repo suffers most consistently...code‑specialized models struggle most with search integration"  
  - [section D] Detailed case studies (unidata_siphon, behave_behave‑django, abravalheri_validate‑pyproject) illustrating each failure mode  
  - [figure 5] Search frequency varies by task but performance gains don't correlate monotonically  
**Break condition:** If search augmentation consistently improves performance across all tasks and model types, indicating resolved integration challenges.

### Mechanism 3
**Claim:** Strict environment reconstruction and problem statement sanitization prevent evaluation gaming.  
**Mechanism:** Agent‑based Docker construction with 5‑run stability testing ensures reproducibility. PR‑to‑issue transformation using Gemini 3 Pro removes solution leakage while preserving problem context. Isolation applies patches to fresh containers, preventing side‑effect contamination.  
**Core assumption:** Without these safeguards, agents could exploit git history or environmental inconsistencies rather than solving the intended problem.  
**Evidence anchors:**  
  - [section 3.1] "Each generated Dockerfile is built and all test suite executed five times...Instances failing any criterion...are discarded"  
  - [section 3.3] "Environment Isolation...prevents any environmental side effects...Integrity Safeguard...sanitize...by removing all commits...after the target commit"  
  - [section E] Full prompt enforcing "NO SPOILERS" and "USER PERSPECTIVE" for problem statement generation  
  - [section 4] "blocklist mechanism that prevents access to the target repository"  
**Break condition:** If leakage through alternative channels (e.g., training data contamination) becomes dominant or stability inspection proves insufficient.

## Architecture Onboarding

**Component map:**  
- BeyondSWE dataset: Four task configurations (CrossRepo, DomainFix, DepMigrate, Doc2Repo) with 500 total instances, each with Docker image URL, problem statement, P2P/F2P test lists  
- SearchSWE framework: OpenHands base extended with SearchTool (SerpAPI) and BrowserTool (Jina Reader), blocklist filtering, system/user prompts with task‑specific phase instructions  
- Infrastructure: Agent‑based environment builder (Gemini 3 Pro), stability inspector (5‑run consistency), expert review pipeline, isolation verifier  

**Critical path:**  
1. **Construction:** Repository scraping → PR filtering → Agent‑based Docker build → 5‑run stability test → PR‑to‑issue transformation → Human validation → Dataset  
2. **Evaluation:** Agent initialization → Task execution (explore → reproduce → fix) → Patch extraction → Fresh container application → Test suite → Success determination  

**Design tradeoffs:**  
- **Generality vs. optimization:** SearchSWE uses uniform tool configuration across tasks to enable systematic comparison, sacrificing potential per‑task performance gains.  
- **Automation vs. verification:** Pipeline heavily automates environment construction but requires expensive human review (domain experts, senior engineers) for final quality control.  
- **Breadth vs. depth:** 500 instances across 4 tasks enable cross‑task comparison but limit in‑depth study of any single task category.  

**Failure signatures:**  
- **Search degradation pattern:** Model‑specific performance drops with search (e.g., Seed‑Coder -5.8% on CrossRepo), indicating negative transfer.  
- **Version hallucination:** Agent assumes environment matches latest docs (e.g., "Django 5.2" in Django 2.2 environment), causing incompatible fixes.  
- **Semantic contamination:** Query polysemy pulls irrelevant domain content (e.g., "family" in repo‑review retrieves BIM/legal docs).  
- **Inefficient search usage:** High search call count without performance gain (DeepSeek‑V3.2: 4.2–5.4 calls/instance, -0.2% avg) suggests poor query formulation or result filtering.  

**First 3 experiments:**  
1. **Baseline comparison:** Evaluate 9 frontier models on BeyondSWE via OpenHands; verify no model exceeds 45% average success.  
2. **Search integration:** Run same models with SearchSWE; measure delta per task; confirm inconsistency (some improve, some degrade).  
3. **Behavioral analysis:** Track tool call statistics (total turns, search frequency) across models; correlate with performance to test "more search = better" hypothesis.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** What are the fundamental reasons behind the disconnect between search and coding capabilities in current code agents?  
- **Basis in paper:** The authors state in the abstract and Section 5.3 that search augmentation yields inconsistent gains and sometimes degrades performance, highlighting the difficulty of emulating developer‑like workflows that interleave search and reasoning. They also note in the conclusion that the integration does not emerge automatically.  
- **Why unresolved:** The paper identifies three failure modes (information landscape gap, temporal misalignment, semantic drift), but these are symptoms, not root causes. Understanding the underlying cognitive or architectural limitations is necessary to design effective solutions.  
- **What evidence would resolve it:** Systematic experiments isolating components of the search‑code pipeline (e.g., modifying search result quality, analyzing model representations) to determine where the integration fails.

### Open Question 2
- **Question:** Under which task and model conditions does external search improve coding performance, and when does it harm?  
- **Basis in paper:** In Section 5.3(1), the authors directly ask “When does search help and when does it hurt?” and present patterns: CrossRepo generally benefits, DomainFix shows high variance, Doc2Repo suffers, and code‑specialized models degrade.  
- **Why unresolved:** The analysis is descriptive; we lack a predictive framework. Without understanding the key factors, we cannot reliably decide when to use search.  
- **What evidence would resolve it:** Controlled studies varying task type, search query design, result relevance, and model characteristics to build a model that predicts the utility of search augmentation.

### Open Question 3
- **Question:** How can code agents be made robust to search failures like information landscape gaps, version misalignment, and semantic drift?  
- **Basis in paper:** The qualitative analysis in Section D details three failure modes: (D.1) retrieval of high‑level docs instead of source code, (D.2) version mismatches leading to incorrect API usage, (D.3) polysemous terms causing context contamination. These are presented as challenges without solutions.  
- **Why unresolved:** These failure modes significantly degrade performance and may even turn search into a liability. Mitigation strategies are needed for reliable search integration.  
- **What evidence would resolve it:** Implementation and evaluation of techniques such as query refinement to retrieve source code, version‑aware retrieval filters, and result re‑ranking based on domain relevance, with empirical success rates on BeyondSWE tasks.

### Open Question 4
- **Question:** Why do code‑specialized models (e.g., Seed‑Coder) suffer performance drops when equipped with search, while general‑purpose frontier models often maintain gains?  
- **Basis in paper:** In Section 5.3, the authors observe: “At the model level, code‑specialized models struggle most with search integration. Seed‑Coder declines on three of four tasks, despite strong baseline performance. In contrast, general‑purpose frontier models like Gemini 3 Pro and MiniMax‑M2.1 demonstrate more stable gains.”  
- **Why unresolved:** This indicates a possible divergence in training or capabilities, but the exact cause (e.g., over‑optimization for local code patterns, insufficient exposure to web data) is unknown.  
- **What evidence would resolve it:** Comparative analyses of training data composition, probing tasks to measure search utilization skills, or fine‑tuning experiments that blend web data into code‑specialized models.

## Limitations
- **Data & Infrastructure Availability:** The benchmark dataset and pre‑built Docker images are announced but not yet publicly released, making exact reproduction difficult and potentially introducing variance due to dependency decay or test flakiness.  
- **Search Configuration Fidelity:** Exact parameters for SerpAPI, Jina Reader, and DeepSeek‑V3.2 summarization are unspecified; minor differences can alter retrieval quality and affect the observed search degradation patterns.  
- **Model Version Equivalence:** The paper tests specific proprietary model versions (e.g., "Gemini 3 Pro", "GPT-5.2"). Public API endpoints may expose different snapshots or capabilities, leading to capability drift that could change performance rankings and search interactions.
