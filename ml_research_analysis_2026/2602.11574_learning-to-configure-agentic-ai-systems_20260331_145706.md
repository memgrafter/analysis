# Learning to Configure Agentic AI Systems
## Quick Facts
- **arXiv ID:** 2602.11574
- **Source URL:** https://arxiv.org/abs/2602.11574
- **Reference count:** 40
- **Primary result:** ARC, a hierarchical RL framework, dynamically configures agentic AI systems per query, achieving up to 25% higher accuracy while reducing token and runtime costs, consistently lying on the accuracy-cost Pareto frontier.

## Executive Summary
The paper tackles the inefficiency of static, one-size-fits-all configurations for LLM-based agent systems, which waste computational resources by applying complex settings to simple queries. It introduces ARC, a hierarchical reinforcement learning framework that learns to dynamically select workflows, tools, and token budgets for each query using a lightweight policy, without retraining the backbone LLM. ARC employs a hybrid pipeline: masked PPO explores the configuration space, followed by supervised fine-tuning on elite trajectories to stabilize and concentrate probability mass on successful strategies. Evaluations on reasoning and tool-use benchmarks show ARC significantly improves task accuracy while lowering costs compared to static baselines and optimization-based approaches.

## Method Summary
ARC learns a configuration policy via a two-level hierarchy. A high-level structural policy (π_struct) selects a workflow, enabled tools, and a token budget given a query embedding and handcrafted features. A low-level prompt policy (π_prompt) then sequentially selects prompt fragments from a library to compose the final system prompt, conditioned on the structural choice. Invalid actions are masked. The agent executes the configured system, and a shaped reward combines task correctness with efficiency penalties (steps, tokens, and asymmetric tool-use rewards). Training proceeds in two phases: first, masked PPO explores to populate a replay buffer; second, both policies are fine-tuned via maximum likelihood on the top-τ (30%) highest-reward trajectories to distill successful strategies into a lower-variance policy. The backbone LLM remains frozen throughout.

## Key Results
- ARC achieves up to 25% higher task accuracy compared to static and optimized baseline configurations across reasoning and tool-use benchmarks.
- The dynamic configuration reduces per-query token consumption and runtime, often by significant margins.
- ARC consistently lies on the Pareto frontier for the accuracy-cost trade-off, outperforming or matching baselines across all evaluated cost constraints.

## Why This Works (Mechanism)
### Mechanism 1: Hierarchical Policy Decomposition
- **Claim:** Decomposing the configuration decision into structural (workflow/tools/budget) and prompt selection reduces effective search complexity.
- **Mechanism:** The high-level π_struct first chooses the architectural blueprint (ω, t, b), after which the low-level π_prompt selects prompt atoms conditioned on this choice. This replaces a single joint decision over |A_struct| × |A_prompt| possibilities with two sequential, smaller decisions.
- **Core assumption:** The configuration space factors meaningfully; optimal structural choices constrain and inform optimal prompt choices without significant performance loss from the factorization.
- **Evidence anchors:**
  - [section 3.1] Explicitly defines the hierarchy and notes an "effective reduction in search complexity."
  - [section 4.3] Transfer experiments show policies trained on one dataset perform reasonably on others, suggesting learned structural priors are robust.
  - [corpus] Ablations (e.g., vs. flat "RL Episodes" policy in Table 1) validate the factorization's benefit.
- **Break condition:** If the optimal configuration requires a prompt instruction incompatible with the chosen workflow (e.g., a "verifier" prompt for a Direct workflow), the factorization fails. The paper uses action masking to mitigate this but notes limitations in domains like MedQA.

### Mechanism 2: Asymmetric Tool-Use Reward Shaping
- **Claim:** The asymmetric reward term R_tool resolves credit assignment between allocating tools and actually invoking them.
- **Mechanism:** The reward penalizes provisioned but unused tools (δ₃·n_alloc) and rewards used tools (δ₁·n_used + δ₂·I[correct]·n_used). This incentivizes the structure policy to allocate tools that the downstream LLM is likely to invoke.
- **Core assumption:** The LLM's tool invocation decision is sufficiently predictable from the query state s_q and allocated tools t.
- **Evidence anchors:**
  - [section 3.2] Defines R_tool and states it addresses the key challenge where the structure policy allocates tools but the LLM decides on invocation.
  - [section 4.6] Error analysis shows low policy configuration error rates (<10%) on tool-use tasks; Figure 13 shows stable, appropriate tool usage in high-reward workflows.
  - [corpus] This specific asymmetric form is a novel contribution; it aligns with classic reward shaping principles.
- **Break condition:** If the LLM's tool invocation is highly stochastic or not inferable from s_q (e.g., depends on random CoT), the shaping provides misaligned signals, causing over/under-allocation.

### Mechanism 3: SFT on Elite Trajectories
- **Claim:** Supervised fine-tuning on elite RL trajectories stabilizes the policy and provides a performance guarantee by concentrating probability on successful configurations.
- **Mechanism:** After RL, the top-τ (e.g., 30%) highest-reward trajectories (correct and high-reward) are extracted. Both policies are then fine-tuned via maximum likelihood on these (state, elite-action) pairs, distilling RL discoveries into a deterministic, low-variance policy.
- **Core assumption:** The elite buffer contains a rich, diverse set of high-performing configurations for each state cluster; the policy network has capacity to fit this distribution.
- **Evidence anchors:**
  - [section 3.3] Introduces SFT to "stabilize the policy" and "distill successful strategies."
  - [Theorem 3.2] Provides a theoretical guarantee: under Lemma 3.1 (MLE convergence), the SFT policy's expected reward is ≥ τ.
  - [section 4.5] Empirically, SFT improves average reward by 5–35% and accuracy by 1–3%, and reduces variance; Figure 9 shows more stable convergence.
  - [corpus] Policy distillation is established in RL; the specific guarantee is paper-specific.
- **Break condition:** If the elite buffer lacks diversity (e.g., RL converges to a single dominant workflow), SFT overfits to a narrow strategy and fails on out-of-distribution queries. Mask-based RL exploration aims to prevent this.

## Foundational Learning
- **Concept: Hierarchical Reinforcement Learning (HRL)**
  - **Why needed here:** ARC uses HRL to decompose the vast joint action space into a manageable hierarchy. Without understanding HRL (e.g., Options framework), the rationale for separating π_struct and π_prompt and the expected benefits in exploration efficiency are opaque.
  - **Quick check question:** How does factoring a decision into a high-level "what to do" and a low-level "how to do it" reduce the effective dimensionality of the policy search problem compared to learning a single monolithic policy?

- **Concept: Proximal Policy Optimization (PPO)**
  - **Why needed here:** PPO is the core learning algorithm. Understanding its clipped objective, advantage estimation, and entropy regularization is necessary to parse the training procedure and hyperparameters, and to understand how the policies are optimized from a sparse reward signal.
  - **Quick check question:** Why is a clipped surrogate objective used instead of vanilla policy gradient, and what problem does it mitigate when learning from a binary correctness reward?

- **Concept: Reward Shaping & Sparse Rewards**
  - **Why needed here:** The configuration task has a sparse primary reward (I[correct]). ARC designs a dense, multi-component reward to guide learning. Grasping this is key to understanding why ARC learns efficiently versus a naive RL agent that only gets +1/-1 at the end.
  - **Quick check question:** What are the three interpretable terms in the shaped reward, and what specific bias or inefficiency does each term aim to correct in the learning process?

## Architecture Onboarding
**Component map:** State Encoder -> Hierarchical Policy Networks (π_struct, π_prompt) -> Agentic System Executor -> LLM Backbone -> Reward Calculator -> Replay Buffer

**Critical path:** Input query -> State Encoder computes s_q (embedding + features) -> π_struct samples (workflow ω, tools t, budget b) -> Action Masking prunes invalid combos -> π_prompt samples sequence of prompt atoms (p) -> Workflow Executor instantiates configured agent -> LLM produces answer â -> Reward Calculator computes r (correctness + efficiency) -> (s_q, a_struct, p, r) stored in buffer B.

**Design tradeoffs:**
- **Policy Capacity vs. Training Time:** Larger policy networks may fit complex mappings but increase RL sample complexity. The paper uses "lightweight" networks to keep LLM execution as the main cost.
- **Reward Weights (α, βs, βt, δ):** Tuning controls the accuracy-efficiency trade-off. High α favors accuracy but may waste cost; high βs/βt forces parsimony but may hurt correctness. The paper uses fixed coefficients; users may need to adjust for their constraints.
- **Prompt Library Size & Diversity:** A larger library gives π_prompt more expressivity but increases action space and composition risk. The paper uses GPT-5.2 to generate dataset-specific atoms, trading generation cost for quality.

**Failure signatures:**
- **High policy configuration error rate:** π_struct picks workflows/tools/budgets mismatched to query complexity. Diagnose: Are state features discriminative enough? Is the mask logic correct?
- **Tool shaping failure:** Many allocated tools go unused (high n_alloc, n_used=0). Diagnose: Increase δ₃ penalty; may indicate LLM isn't invoking tools or policy fails to predict invocation.
- **SFT overfitting:** Validation accuracy drops after SFT. Diagnose: Elite threshold τ too low (includes noisy trajectories) or buffer lacks diversity.
- **Poor transfer:** Policy fails on new task types. Diagnose: Overfitting to dataset-specific quirks in state embedding or prompt library; need broader training data or more general ϕ(q).

**First 3 experiments:**
1. **Reproduce Baseline Performance:** Run ARC (with SFT) on a single benchmark (e.g., GSM8K) using the provided codebase. Verify >85% accuracy and observe Pareto-optimal cost vs. accuracy as in Figure 4.
2. **Ablate SFT Phase:** Train ARC without the SFT step (stop after RL). Compare accuracy and reward variance to full ARC on the same validation set; expect a consistent drop (1-3% accuracy, higher variance).
3. **Visualize Workflow Distribution:** For a trained policy, run inference on the test set and plot the selected workflow distribution (similar to Figure 11). Check it is not uniform; it should concentrate on 2-4 dominant workflows per dataset. Also, check tool usage trends (Figure 10) stabilize.

## Open Questions the Paper Calls Out
- **Question:** How can domain-specific prompt optimization be integrated with hierarchical configuration learning to improve performance on knowledge-intensive tasks?
  - **Basis:** Section 4.2 notes combining structural optimization with domain-specific prompts is a promising future direction.
  - **Why unresolved:** ARC relies on a fixed library of general-purpose prompts; in domains like MedQA, prompt content may dominate performance but remains untapped.
  - **What evidence would resolve it:** Empirical study where the prompt policy selects from both general and automatically generated domain-specific atoms; compare accuracy on MedQA against the baseline.

- **Question:** What factors determine cross-task transferability of learned configuration policies?
  - **Basis:** Section 4.3 observes transfer depends more on shared workflow/tool structure than on semantic similarity, but exact factors are unclear.
  - **Why unresolved:** Understanding these factors would enable zero-shot deployment on new tasks, reducing retraining need.
  - **What evidence would resolve it:** Controlled experiments dissecting contributions of tool overlap, workflow similarity, and task semantics; or building a predictive model of transfer performance from task characteristics.

- **Question:** Can the state representation be learned jointly with the policy to improve configuration decisions?
  - **Basis:** Section 3.1 and Appendix D use a frozen embedding (MetaCLIP-H/14) plus handcrafted features; authors ablate embedding choices but do not explore end-to-end learning.
  - **Why unresolved:** A trainable representation might capture more nuanced task aspects relevant for workflow and budget selection.
  - **What evidence would resolve it:** Replace the fixed embedding with a learnable encoder (e.g., fine-tuned CLAP) trained alongside the policy; compare against the fixed representation baseline.

- **Question:** How can residual reasoning and knowledge errors that persist even with optimal configuration be mitigated?
  - **Basis:** Section 4.6 attributes remaining errors to inherent LLM limitations, indicating configuration alone cannot solve all failure modes.
  - **Why unresolved:** Further gains may require addressing these root causes, not just better configuration.
  - **What evidence would resolve it:** Introduce targeted recovery mechanisms (e.g., fallback workflows, self-correction loops) or external knowledge modules; measure reductions in reasoning and knowledge-gap error rates on challenging benchmarks like GAIA.

## Limitations
- Policy architecture and hyperparameters are not fully specified; variations may impact stability and sample efficiency.
- The prompt library depends on GPT-5.2-generated atoms; alternative generation methods or manual prompts may yield lower quality.
- Generalization is only validated on a set of similar reasoning/tool-use benchmarks; performance on novel domains or tool sets is unknown.

## Confidence
- **Claim:** Hierarchical decomposition reduces effective search complexity. **Confidence:** Medium (supported by transfer/ablations, but prompt-workflow incompatibility risk remains).
- **Claim:** Asymmetric reward shaping resolves tool credit assignment. **Confidence:** Low (novel contribution; no external validation; LLM tool invocation may be stochastic).
- **Claim:** SFT on elite trajectories stabilizes policy and provides guarantee. **Confidence:** High (theorem + consistent empirical gains, assuming diverse elite buffer).

## Next Checks
1. **Architecture sensitivity:** Vary network size and PPO hyperparameters on GSM8K; measure accuracy & sample efficiency to identify robust configurations.
2. **Prompt source ablation:** Use human-curated or Llama-3-generated prompt atoms instead of GPT-5.2; test on a tool-use benchmark like HotpotQA to quantify library quality impact.
3. **Cross-domain transfer:** Train a policy on reasoning datasets (GSM8K, DROP); test on a code generation benchmark (MBPP) with calculator-only tool support; measure accuracy drop to assess transfer limits.
