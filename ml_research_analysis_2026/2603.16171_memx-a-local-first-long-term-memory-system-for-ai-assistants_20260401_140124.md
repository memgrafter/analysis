# MemX: A Local-First Long-Term Memory System for AI Assistants

## Quick Facts
- **arXiv ID:** 2603.16171
- **Source URL:** https://arxiv.org/abs/2603.16171
- **Reference count:** 4
- **Primary result:** Deterministic hybrid retrieval with RRF and low-confidence rejection yields stable recall (Hit@1 91.3–100%) and strong spurious result suppression.

## Executive Summary
MemX is a deterministic hybrid retrieval system for AI assistant memory, combining vector (DiskANN) and keyword (FTS5) search with Reciprocal Rank Fusion and a four-factor re-ranking (semantic, recency, frequency, importance). It employs a low-confidence rejection rule to suppress spurious results and uses a local-first architecture for stability and explainability.

On custom Chinese benchmarks with up to 1,014 records, MemX achieves 91.3–100% Hit@1 with conservative miss suppression. On the large-scale LongMemEval (500 queries, up to 220k records), fact-level retrieval doubles session-level performance to Hit@5=51.6% and MRR=0.380, with end-to-end search kept under 90 ms.

## Method Summary
The MemX system implements a deterministic retrieval pipeline for long-term AI memory. Input queries are embedded using Qwen3-Embedding-0.6B (1024-dim) and processed in parallel: a DiskANN vector index (cosine similarity) and an FTS5 full-text index retrieve candidate sets. These are fused via Reciprocal Rank Fusion (k=60), then re-ranked using a composite score combining semantic similarity (weight 0.45), recency (exponential decay, weight 0.25), frequency (log-capped, weight 0.05), and importance (weight 0.10). Scores are normalized via z-score and sigmoid compression. A low-confidence rejection rule (τ=0.50) returns an empty set if no keywords match and the top vector score is below threshold. Final results are deduplicated by content and tag-signature. The system stores memories in a libSQL database with vector and full-text extensions, and updates retrieval counts and timestamps as side effects. Evaluation uses custom Chinese scenarios and LongMemEval, measuring Hit@k, MRR, Miss rates, and latency.

## Key Results
- Custom Chinese benchmarks (43 queries, ≤1k records): Hit@1 of 91.3–100% with conservative miss suppression.
- LongMemEval (500 queries, up to 220k records): fact-level Hit@5=51.6%, MRR=0.380, doubling session-level performance.
- FTS5 indexing reduces keyword latency by 1,100× at 100k records, keeping end-to-end search under 90 ms.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Hybrid retrieval (vector + keyword) with Reciprocal Rank Fusion (RRF) improves stability against spurious recalls by requiring consensus between semantic and lexical signals.
- **Mechanism:** Queries are processed in parallel by DiskANN (cosine similarity) and FTS5 (full-text match). RRF scores each candidate by summing reciprocal rank positions (k=60) from both lists, then re-ranking uses the RRF score as the semantic factor.
- **Core assumption:** Valid answers tend to appear in both semantic and lexical top-n lists, while distractors may dominate only one modality.
- **Evidence anchors:**
  - [abstract]: "deterministic hybrid retrieval pipeline combining vector (DiskANN) and keyword (FTS5) search via Reciprocal Rank Fusion"
  - [section 3.3]: Formal Algorithm 1 shows VECTORRECALL and KEYWORDRECALL in parallel, fused via RRF.
  - [corpus]: Corpus evidence is limited; neighboring works (e.g., LongMemEval, HiMeS) evaluate memory systems but do not evidence MemX's specific RRF design.
- **Break condition:** If keyword recall is consistently empty across queries (e.g., due to token mismatch), RRF degrades to vector-only ranking, removing the consensus guard.

### Mechanism 2
- **Claim:** Four-factor re-ranking (semantic, recency, frequency, importance) with z-score normalization prioritizes recent retrieved, frequently useful memories while maintaining cross-query comparability.
- **Mechanism:** Composite score `score(m) = α_s*f_sem + α_r*f_rec + α_f*f_freq + α_i*f_imp`. `f_rec` uses exponential decay on `last_retrieved_at`; `f_freq` caps log(`retrieval_count`). Z-score normalizes scores per candidate set, followed by sigmoid to compress outliers.
- **Core assumption:** Memories useful in prior retrievals (`retrieval_count`) are more valuable than those merely accessed (`access_count`), and recency decay smoothly prefers newer useful memories.
- **Evidence anchors:**
  - [section 3.4]: Equations 1–4 and Table 1 define weights and factor computations; explicitly contrasts retrieval vs. access tracking.
  - [section 6.2]: Worked example shows ranking reversal between profiles A (admin-heavy access) and B (search-heavy retrieval) under different tracking strategies.
  - [corpus]: Neighbors (e.g., Mem-PAL, CarMem) model user preferences but do not evidence the specific four-factor weighting or access/retrieval separation.
- **Break condition:** If all candidates have identical raw scores (`σ_s < 10^{-6}`), normalization is skipped, reducing discriminability.

### Mechanism 3
- **Claim:** Low-confidence rejection rule (`¬kw ∧ v_max < τ`) suppresses spurious results on unanswerable queries by requiring weak signals in both modalities.
- **Mechanism:** After re-ranking, if keyword recall set `K` is empty **and** the top vector similarity `v_max` is below threshold `τ=0.50`, the system returns an empty set.
- **Core assumption:** Valid queries typically match either semantics (`v_max` high) or keywords (`K` non-empty); unanswerable queries fail both.
- **Evidence anchors:**
  - [abstract]: "low-confidence rejection rule that empties results when the top vector score is below a threshold (τ=0.50) and no keywords match."
  - [section 3.6]: Formal rule definition; Table 10 compares five candidate rules.
  - [section 5.7]: Simulation on 24 queries shows R1 (conjunctive rule) is only candidate with zero false negatives.
  - [corpus]: Neighbors (e.g., O-Mem, HiMem) explore memory architectures but do not evidence a conjunctive rejection rule tuned for local-first stability.
- **Break condition:** If a false recall has `v_max > τ` and `K` empty, it passes the filter (e.g., `public_cloud_region_miss` with `v_max=0.621`).

## Foundational Learning
- **Concept:** Reciprocal Rank Fusion (RRF)
  - *Why needed here:* Combines ranked lists from heterogeneous retrievers (dense vs. sparse) without score normalization or learned weights, crucial for hybrid retrieval simplicity.
  - *Quick check question:* Why does RRF use reciprocal ranks (1/(k+60)) instead of averaging raw similarity scores?
- **Concept:** Z-score normalization with sigmoid compression
  - *Why needed here:* Ensures final scores are comparable across queries with different candidate-set distributions and prevents outlier dominance.
  - *Quick check question:* What happens to ranking if all candidates have identical pre-normalization scores?
- **Concept:** Access vs. retrieval separation
  - *Why needed here:* Prevents administrative views (access) from inflating ranking signals, ensuring frequency/recency reflect actual search utility.
  - *Quick check question:* Under retrieval-based tracking, why does profile B (search-heavy) outrank profile A (admin-heavy) despite A having more total interactions?

## Architecture Onboarding
- **Component map:**
  - Input: Query string → Embedding API (Qwen3-0.6B, 1024-d) → `e_q`
  - Parallel recall: DiskANN index (vector) + FTS5 index (keyword) → candidate sets V, K
  - Fusion: RRF (k=60) → fused list C
  - Re-ranking: Four-factor score (Eq.1) → z-score (Eq.4) → sorted list Ŝ
  - Filter: Rejection gate (τ=0.50) → possibly ∅
  - Post-process: Deduplication (content + tag-signature) → top-k results R
  - Side-effect: Update `retrieval_count`/`last_retrieved_at` in `memories` table.
- **Critical path:** Query → embed → V+K recall → RRF → four-factor → z-score → reject? → dedup → return.
- **Design tradeoffs:**
  - Stability over recall: Rejection rule reduces false positives but may reject borderline valid queries.
  - Local-first: libSQL file simplifies deployment but limits cloud-scale graph traversal; graph links (`memory_links`) unused in retrieval.
  - Simple weights: Fixed α ratios avoid training data needs but may not optimize for all query distributions.
- **Failure signatures:**
  - Multi-topic queries return only one dominant topic (coverage gap).
  - High-confusion queries with lexical overlap produce false recalls when `v_max > τ` and `K` empty.
  - Temporal/multi-session queries fail (≤43.6% Hit@5) due to lack of time-aware indexing.
  - Tag-signature deduplication collapses all tag-free facts, reducing recall on fact-granularity datasets.
- **First 3 experiments:**
  1. **Threshold sweep:** Vary τ across {0.48, 0.50, 0.52, 0.64} on custom scenarios; measure Hit@1 vs. Miss-Empty-Rate tradeoff. Expected: τ=0.50 best balance.
  2. **Pipeline ablation:** Compare V vs. V+K vs. V+K+Rej vs. Full on custom scenarios. Expected: Rejection adds Miss-Empty-Rate without hurting Hit@k; deduplication improves Hit@3 only with structured tags.
  3. **Granularity study:** Convert LongMemEval into session/round/fact stores; measure Hit@5 and MRR. Expected: Fact-level doubles retrieval quality; knowledge update queries benefit most.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the retrieval pipeline be extended to handle multi-topic queries requiring multiple distinct memories, given its current design optimizes for single-topic "needle-in-a-haystack" retrieval?
- **Basis in paper:** [explicit] Section 6.1 identifies "multi-topic coverage gap" as a failure case, noting that queries needing two topics retrieve only the most prominent one, and Coverage@5 is as low as 75% in high-confusion scenarios.
- **Why unresolved:** The pipeline lacks query decomposition or diversity-promoting re-ranking mechanisms; all fused and re-ranked results cluster around a single semantic peak, suppressing co-relevant but lower-scoring topics.
- **What evidence would resolve it:** Implement and evaluate query decomposition (e.g., generating sub-queries for each expected topic) or diversity-aware re-ranking (e.g., Maximal Marginal Relevance) on the custom scenario's multi_fact queries, measuring Coverage@k improvements while monitoring Hit@k to ensure no recall trade-off.

### Open Question 2
- **Question:** Can cross-encoder re-scoring or a learned classifier improve the low-confidence rejection rule's ability to suppress spurious recalls when miss queries have high semantic overlap with valid memories?
- **Basis in paper:** [explicit] Section 5.7 demonstrates a fundamental score-gap limitation: the easiest false recall (v_max=0.621) overlaps the hardest valid query (v_max=0.504), making any single-threshold v_max rule insufficient to separate them. Section 6.1 calls for "stronger rejection rules."
- **Why unresolved:** The current conjunctive rule (¬kw ∧ v_max < τ) relies solely on a single vector similarity score and keyword absence; it cannot model fine-grained query–document interactions, leading to false positives on adversarially overlapping queries (e.g., public_cloud_region_miss).
- **What evidence would resolve it:** Integrate a cross-encoder (e.g., BGE-reranker) as a second-stage re-ranker or classifier on top-k results, then re-run the high-confusion scenario and LongMemEval. Success would show reduced Miss-Empty-Rate and Miss-Strict-Rate for overlapping miss queries without increasing false negatives (valid queries rejected).

### Open Question 3
- **Question:** How should the existing memory_links graph structure be incorporated into retrieval to address the poor temporal and multi-session reasoning performance (≤43.6% Hit@5) observed on LongMemEval?
- **Basis in paper:** [explicit] Section 6.1 notes that "temporal and multi-session reasoning remain challenging" and attributes this to missing mechanisms; it also states the graph infrastructure (memory_links with seven relation types) exists but "multi-hop traversal and graph-aware re-ranking are not yet integrated." Section 3.2 documents the links table.
- **Why unresolved:** Single-query vector recall alone cannot synthesize information scattered across sessions or reason about temporal order; the graph's causal, temporal, and supersession links remain unused, limiting these ability types.
- **What evidence would resolve it:** Implement a graph-augmented retrieval stage (e.g., expand initial results via related/superseded/caused_by links, or use graph signals as re-ranking features) and evaluate on LongMemEval's multi-session and temporal query subsets. A significant increase in Hit@5 for these categories, without degrading fact-level performance, would validate the integration.

## Limitations
- **Data & Model Specificity:** Exact Chinese benchmark queries/records and ground truths are unreleased. τ=0.50 rejection threshold is calibrated for Qwen3-Embedding-0.6B; transferability to other embedding models is unknown.
- **Scalability Evidence:** Latency claims rely on libSQL/FTS5; performance under concurrent loads or with significantly larger corpora (>>220k records) is not evaluated.
- **Deduplication Pitfall:** Tag-signature deduplication may collapse fact-granularity results when tags are sparse/uniform, as in LongMemEval’s fact-level setting.
