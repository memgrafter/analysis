# The World Won't Stay Still: Programmable Evolution for Agent Benchmarks

## Quick Facts
- **arXiv ID:** 2603.05910  
- **Source URL:** https://arxiv.org/abs/2603.05910  
- **Reference count:** 40  
- **Primary result:** ProEvolve, a graph-based framework for programmable environment evolution, automatically generated 200 environment variants and 3,000 task sandboxes with 100% unit test coverage and 90.83% pass rate; benchmarking five major LLM agents revealed substantial performance variability and divergent tool-use patterns across controlled evolution trajectories, and simple replay strategies failed to yield consistent adaptation improvements.

## Executive Summary
Current agent benchmarks assume static environments, failing to capture real-world dynamics. This paper introduces ProEvolve, a framework that models environments as typed relational graphs and enables coherent, programmable evolution via graph transformations. Applied to an e-commerce seed, it scales to hundreds of evolving environments and thousands of tasks. Benchmarking major LLM agents across evolution trajectories shows that agent robustness is highly transition- and model-dependent, and naive memory-based adaptation (history or reflection) does not reliably help. The work highlights the need for agents that explicitly recognize and respond to structural environmental changes.

## Method Summary
ProEvolve starts from a seed environment (e-commerce domain) represented as a typed relational graph capturing schemas, data, and tools. Evolution strategies (completion, saturation, deprecation) are applied via an LLM-driven pipeline: first, an agent proposes graph edits (add/remove nodes/edges) that propagate coherently; second, code (Pydantic models, tool implementations, unit tests) is automatically generated from the updated graph. Task sandboxes are created by sampling connected subgraphs, materializing initial states, and generating oracle reference trajectories with state-wise instructions. Agents are evaluated using a user simulator that enforces state-specific success criteria, measuring state-success rate, turns, and tool calls. A full curriculum consists of 50 evolution trajectories (each sequence: comp → sat → dep), yielding 200 versioned environments and 3,000 tasks.

## Key Results
- Generated 200 environment versions and 3,000 tasks with high implementation quality (100% unit test coverage, 90.83% pass rate).
- Benchmarking five LLM agents (GPT-5, Claude-3.5, Gemini-1.5, etc.) across evolution transitions showed significant performance drops (up to 50% state-success rate) and divergent tool-use behaviors (e.g., GPT-5 increases tool calls, Gemini becomes conservative).
- Simple replay strategies (history or reflection) did not consistently improve adaptation, underscoring the challenge of dynamic environments.

## Why This Works (Mechanism)

### Mechanism 1
**Claim:** A typed relational graph formalism enables scalable yet coherent environment evolution by explicitly modeling dependencies among schemas, data, and tools.  
- **Mechanism:** Environment elements are typed nodes (e.g., `User.user_id`, `Order.order_id`) and directed edges (relationships or tool-enabled transitions). Evolution strategies apply structured graph edits (add/remove nodes/edges). Because relationships are explicit, changes propagate coherently—e.g., adding a `cancel_subscription` tool automatically updates related schema nodes and edges.  
- **Core assumption:** Environment components are tightly coupled; isolated modifications break system integrity.  
- **Evidence anchors:** [abstract] "typed relational graph provides a unified, explicit representation... adding, removing, or modifying capabilities are expressed as graph transformations that coherently propagate updates"; [section 4.1] "Since the environment elements and their relationships are not explicitly modeled, it becomes intractable to evolve them in a coherent and controllable manner... a graph formalism that models environment elements and their relationships in an explicit, integrated representation."  
- **Break condition:** If the graph fails to capture all relevant dependencies (e.g., indirect relationships), transformations introduce incoherent updates (e.g., new tools lack required schema nodes), breaking implementation validity.

### Mechanism 2
**Claim:** Agentic workflows automate the translation of evolution strategies into executable code and diverse environment variants, balancing scalability with controlled dynamics.  
- **Mechanism:** LLM agents traverse the current graph to propose transformation plans (Phase I: Completion/Saturation/Deprecation), then generate updated code (data models, tools, unit tests) consistent with the evolved graph (Phase II). The sequence and parameters of strategies program evolution trajectories.  
- **Core assumption:** LLMs can reliably design coherent graph changes and generate syntactically correct, semantically aligned implementations given the graph context.  
- **Evidence anchors:** [section 4.2] "We introduce an agentic pipeline which programs evolutions automatically... Phase I: Evolution Proposal... Phase II: Implement and Validate."; [section 5.1] "We employ the proposed automatic environment evolution pipeline... to instantiate the evolution curriculum... We generate 50 evolution episodes... yielding 200 versioned environments."  
- **Break condition:** LLM-generated transformation proposals introduce invalid graph edits (e.g., removing a node still referenced by an edge) or code that fails unit tests (<100% coverage), undermining scalability.

### Mechanism 3
**Claim:** Subgraph sampling and oracle walks ground task sandboxes in the evolved environment graph, ensuring dependency-consistent, state-wise evaluations that capture partial progress.  
- **Mechanism:** A task τ is a connected subgraph Gτ ⊆ G(k) sampled from the evolved environment. An oracle agent expands along Gτ, generating state-wise user instructions u⋆t that target the current frontier of reachable nodes. Success is judged per state based on graph-derived criteria Y⋆t, not just final outcome.  
- **Core assumption:** The graph structure fully captures all necessary dependencies for tasks, allowing sequential, dependency-aware instruction generation and evaluation.  
- **Evidence anchors:** [abstract] "instantiate task sandboxes via subgraph sampling and programming."; [section 4.3] "Each task can be cast as a constrained task subgraph H ⊆ G(k)... state-wise user instruction ut that targets the next frontier of information exposed by the current task subgraph."; [section 4.4] "State-wise instructions {u⋆t} are consecutive and dependency-aware by construction... enables turn-level evaluation without relying on ad-hoc heuristics."  
- **Break condition:** Sampled subgraphs omit critical dependency paths, or oracle walks generate instructions that do not align with graph frontiers, making state success criteria unreachable or trivial.

## Foundational Learning
- **Typed relational graph modeling:**  
  *Why needed:* The entire framework hinges on an explicit graph where nodes (schemas/data) and edges (relationships/tools) have types. This enables automated transformation propagation, code generation, and task grounding.  
  *Quick check:* If you add a new tool node `get_user_purchased_products`, which existing schema nodes must be connected to maintain coherence? How does the graph ensure this?

- **Evolution strategies as graph transformations:**  
  *Why needed:* Strategies (completion, saturation, deprecation) define how environments change. Understanding these as graph edits (node/edge additions/removals) is key to predicting environmental dynamics and generating valid variants.  
  *Quick check:* What is the difference between a saturation and completion transformation in terms of graph operations? Give an example of each in the e-commerce domain.

- **State-wise task simulation and evaluation:**  
  *Why needed:* Evaluating agents in dynamic environments requires measuring progress through dependency chains, not just final success. The state-wise approach uses the graph to define sequential criteria.  
  *Quick check:* How does the state success rate C(τ) differ from traditional end-to-end success metrics? Why is this particularly important when tools/schemas evolve?

## Architecture Onboarding
- **Component map:**  
  Graph Manager → Evolution Engine → Code Generator → Task Generator → Evaluation Harness  
  (Graph Manager maintains the environment graph; Evolution Engine applies transformation strategies; Code Generator produces executable code and unit tests; Task Generator samples subgraphs and materializes sandboxes; Evaluation Harness benchmarks agents with state-wise criteria.)

- **Critical path:** Seed graph → [Evolution Engine: apply ∆(k)] → [Code Generator: produce implementation] → [Task Generator: create sandboxes] → [Evaluation Harness: benchmark agents] → repeat for next G(k+1).

- **Design tradeoffs:**  
  - Coherence vs. scalability: Graph formalism ensures updates propagate correctly but requires exhaustive relationship modeling; LLM automation scales proposal generation but risks incoherent edits.  
  - Automation vs. correctness: Fully automated code generation speeds up environment creation but relies on unit tests to catch errors; manual review may be needed for edge cases.  
  - Task diversity vs. solvability: Subgraph sampling yields diverse tasks but must prune unsolvable subgraphs (no tool path to goal).

- **Failure signatures:**  
  - Low unit test pass rate (<?90%) indicates graph transformations produced invalid code (e.g., mismatched schemas).  
  - Tasks where oracle walk fails to reach goal state suggest subgraph sampling omitted necessary nodes/edges.  
  - Replay strategies yield no performance gain or increased cost without success improvement, indicating agents cannot leverage past experience.  
  - Incoherent graphs (edges reference non-existent nodes/attributes) break referential integrity.

- **First 3 experiments:**  
  1. **Graph transformation validation:** Apply a single completion strategy (e.g., add subscription feature) to seed graph. Verify new tool edges connect to existing schema nodes and generated code passes unit tests. Check that removal (deprecation) updates all dependent tools.  
  2. **Task solvability check:** For a sampled subgraph, run the oracle walk to ensure all state instructions u⋆t are reachable via tool calls and Y⋆t criteria are attainable. Measure fraction of sampled subgraphs with valid oracle trajectories.  
  3. **Adaptation gap measurement:** Benchmark a fixed agent (e.g., GPT-5 Baseline) across one full evolution trajectory (G(0)→G(1)→G(2)→G(3)). Compute success rate delta per transition; expect substantial variability (as in Table 2) indicating brittleness.

## Open Questions the Paper Calls Out
**Open Question 1:** How can we design agent adaptation strategies that effectively handle environment evolution, given that simple replay mechanisms (history or reflection) fail to consistently improve performance?  
*Basis:* Section 5.3 reports that "simple replay strategies (history or reflection) did not yield consistent improvements," and Section 6 lists "developing optimal adaptive agent strategies that explicitly recognize and respond to environment evolution" as future work.  
*Why unresolved:* The paper demonstrates that naive memory-based approaches are insufficient but does not propose or evaluate more sophisticated mechanisms for detecting or responding to structural changes.  
*What evidence would resolve it:* Benchmarking novel adaptation algorithms (e.g., change detection, meta-learning, dynamic tool selection) on ProEvolve’s evolution trajectories, showing consistent and statistically significant improvements in state-success rates across diverse transformations compared to replay baselines.

**Open Question 2:** What evolution curricula (i.e., sequences and patterns of graph transformations) most effectively train or evaluate agent robustness under dynamic environments?  
*Basis:* Section 6 identifies "exploring curriculum-learning approaches to design effective evolution sequences" as a future direction; the paper uses a fixed sequence (∆comp → ∆sat → ∆dep) but notes the need to program diverse dynamics.  
*Why unresolved:* The framework supports programmable evolution but does not investigate which sequences (e.g., order, frequency, or complexity of transformations) yield agents that generalize better or reveal specific failure modes.  
*What evidence would resolve it:* Systematic ablation studies varying evolution trajectories (e.g., different orders of comp/sat/dep, varying difficulty ramps) and measuring agent performance variability, transferability, and sample efficiency to identify curriculum principles.

**Open Question 3:** Do the observed agent robustness patterns and tool-use behaviors generalize beyond the e-commerce domain, and what domain-specific factors influence adaptability?  
*Basis:* Section 6 calls for "extending the framework to diverse domains to uncover general principles"; Appendix provides airline examples but empirical validation is limited to e-commerce.  
*Why unresolved:* The paper’s experiments rely on a single seed environment (e-commerce) and a limited set of models; it remains unclear whether findings (e.g., model-dependent performance swings, tool-use conservatism) hold in other domains with different entity-relation structures or evolution pressures.  
*What evidence would resolve it:* Implementing ProEvolve for multiple domains (e.g., healthcare, finance, gaming), generating parallel evolution trajectories, and comparing agent performance distributions, tool-use patterns, and failure modes across domains to isolate domain-general versus domain-specific robustness factors.

**Open Question 4:** What underlying factors (e.g., model architecture, training data, reasoning mechanisms) explain the divergent performance and tool-use behaviors of different LLM agents under identical environment evolution trajectories?  
*Basis:* Section 5.3 observes "substantial environment-to-environment variability" and "distinct and heterogeneous behaviors" across agents (e.g., GPT-5’s tool-use intensity vs. Gemini’s conservatism), but does not analyze causes.  
*Why unresolved:* The paper benchmarks diverse models but treats them as black boxes; it is unknown whether differences stem from scale, fine-tuning, tool-use prompting, or inherent reasoning strategies, limiting actionable insights for building adaptable agents.  
*What evidence would resolve it:* Controlled experiments with model variants (e.g., ablations on tool-use instructions, chain-of-thought prompting) or interpretability analyses (e.g., logging decision points, tool-selection heuristics) on ProEvolve tasks to correlate internal behaviors with adaptation success.

## Limitations
- Graph coherence relies on exhaustive dependency modeling; missing indirect relationships cause incoherent updates.
- Code generation quality depends on undisclosed LLM version/prompting; semantic bugs may be hidden by unit tests (90.83% pass rate without error breakdown).
- Findings are restricted to a single e-commerce domain and five models; generalizability to other domains or agent types is unknown.

## Confidence
- Graph Coherence Mechanism: Medium  
- Automated Code Generation: Medium  
- Agent Robustness Conclusion: Medium-Low
