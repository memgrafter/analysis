# $\texttt{lrnnx}$: A library for Linear RNNs

## Quick Facts
- **arXiv ID:** 2602.08810
- **Source URL:** https://arxiv.org/abs/2602.08810
- **Reference count:** 33
- **Primary result:** `lrnnx` consolidates fragmented Linear RNN implementations (S4, S5, Mamba) under a unified PyTorch interface with custom CUDA kernels, enabling competitive training speeds and practical inference while reducing engineering effort.

## Executive Summary
The paper presents `lrnnx`, an open‑source PyTorch library that unifies the implementation of Linear Recurrent Neural Networks (LRNNs) such as S4, S5, and Mamba. By introducing a three‑tier class hierarchy and optimized CUDA kernels for time‑varying layers, the library abstracts away model‑specific details, allowing researchers to switch between architectures with minimal code changes. Benchmarks show that `lrnnx` achieves training speeds comparable to original JAX/PyTorch baselines across diverse configurations, while inference is slightly slower due to PyTorch overheads but remains usable. The library thus improves accessibility, reproducibility, and experimental efficiency in LRNN research.

## Method Summary
`lrnnx` employs a hierarchical design: a base `LRNN` class defines the common forward interface and discretization; subclasses `LTI_LRNN` (time‑invariant) and `LTV_LRNN` (time‑varying) implement architecture‑specific parameterizations and recurrence logic. Concrete layers (e.g., `S4`, `S5`, `Mamba`) inherit from these subclasses. For training, LTI layers precompute kernels via parallel scans, while LTV layers rely on fused custom CUDA kernels that merge scanning and projection, ensuring memory‑efficient parallelization. Autoregressive inference uses the `step` method and CUDA Graphs to achieve O(1) per‑step cost. The library also provides standardized benchmarking tools that run identical experiments across all supported models, facilitating fair performance comparisons. A minimal reproduction involves installing `lrnnx` and its dependencies, instantiating a model with given hyperparameters, and timing forward/backward passes for training and stepwise loops for inference using CUDA events.

## Key Results
- Training throughput meets or exceeds that of original implementations (JAX/PyTorch) across batch sizes, model dimensions, and sequence lengths (256–2048).
- Autoregressive inference is slightly slower than optimized JAX baselines due to PyTorch overheads but remains practical for typical use cases.
- The unified interface significantly reduces engineering effort, enabling rapid experimentation and cross‑architecture reproducibility.

## Why This Works (Mechanism)
`lrnnx` succeeds by addressing three core challenges:

**Unified Three‑Tier Hierarchy:** The library abstracts LRNN variants through a clear inheritance structure. The base `LRNN` class implements the generic recurrence and discretization selection. The `LTI_LRNN` and `LTV_LRNN` subclasses encapsulate time‑invariant and time‑varying matrix handling, respectively, while concrete architectures (S4, S5, Mamba) define their specific parameterizations. This design allows users to swap models by merely changing the instantiated class, without modifying surrounding code, thereby decoupling algorithmic differences from training loops.

**Custom CUDA Kernels for LTV Layers:** Time‑varying layers (e.g., Mamba) depend on input‑dependent dynamics that preclude simple precomputation. `lrnnx` provides fused CUDA kernels derived from Mamba’s selective scan, which integrate the scan operation with the output projection and support multiple discretization schemes (ZOH, bilinear, dirac). These kernels avoid materializing the full hidden state during parallel training, reducing memory consumption. For inference, kernels are combined with CUDA Graphs to eliminate per‑step CPU launch overhead, achieving O(1) amortized cost.

**Standardized Interface for Benchmarking & Accessibility:** By enforcing identical constructor signatures and method sets across all layers, `lrnnx` makes it trivial to run identical training and inference scripts for any supported architecture. The included benchmark suite then evaluates all models under the same hardware, tensor shapes, and timing protocols. This standardization directly tackles the fragmentation problem historically hindering LRNN research, where each new model required a bespoke codebase.

  *Why needed:* The library abstracts the core recurrence `x_k = A_k x_{k-1} + B_k u_k, y_k = C_k x_k + D_k u_k` and the distinction between LTI (constant `A`) and LTV (input‑dependent `A`) variants.  
  *Quick check:* What is the key mathematical difference between an LTI (e.g., S4) and an LTV (e.g., Mamba) layer, and why does this impact implementation strategy?

- **Discretization of Continuous‑Time Systems**  
  *Why needed:* The `discretization` argument (ZOH, bilinear, etc.) maps continuous state‑space parameters to discrete recurrence steps, affecting stability and performance.  
  *Quick check:* How does Zero‑Order Hold (ZOH) differ from bilinear (Tustin) discretization in frequency response?

- **Parallel Training vs. Autoregressive Inference**  
  *Why needed:* Efficient LRNN training uses parallel scans over the sequence, while inference must generate tokens step‑by‑step; the library optimizes both paths.  
  *Quick check:* Why is the naive `for` loop over sequence positions during training a performance killer, and how does the parallel scan algorithm solve this?

## Architecture Onboarding
- **Component map:**  
  LRNN -> LTI_LRNN / LTV_LRNN -> (S4, S5, Mamba, ...); LRNNLMHeadModel -> stacked LRNN blocks; CUDA kernels and utilities support LTV operations.

- **Critical path:**  
  1. Choose LTI (stable, precomputed kernel) or LTV (selective, fused kernels).  
  2. Select concrete architecture (e.g., S5 for MIMO‑LTI, Mamba for selective LTV).  
  3. Instantiate with `d_model`, `d_state`, `discretization`.  
  4. For training: call `forward()` on full sequences.  
  5. For inference: allocate cache once via `allocate_inference_cache()`, then call `step()` repeatedly.

- **Design tradeoffs:**  
  - *PyTorch‑only vs. multi‑framework:* Full PyTorch optimization but excludes JAX/TensorFlow users.  
  - *Custom kernels vs. maintainability:* Peak NVIDIA GPU performance adds debugging complexity.  
  - *Unified API vs. specialization:* Easy swapping may hide architecture‑specific tuning knobs (e.g., Mamba’s `A` constraints).  
  - *Inference overhead:* CUDA Graphs mitigate but do not fully eliminate PyTorch loop costs, leading to slight slowdown vs. JAX.

- **Failure signatures:**  
  - Numerical mismatch between `forward()` and `step()` outputs → kernel or discretization bug.  
  - Slow training: LTV kernel not used (check CUDA compilation).  
  - Slow inference: per‑step CPU‑GPU sync (ensure CUDA Graph usage).  
  - OOM on long sequences: state cache too large for `d_state` or kernel memory limits.

- **First 3 experiments:**  
  1. **Validation:** For a random batch, assert `torch.allclose(layer(x), layer.step(x, state)[0], atol=1e-5)` on a short sequence (len=8).  
  2. **Baseline replication:** Run library’s benchmark for one layer (e.g., S5) on a single config (batch=4, seq_len=512, d_model=256) to confirm environment matches reported speeds.  
  3. **Kernel activation:** Profile a Mamba layer with `nsys` to confirm `selective_scan` kernel launches and no full state materialization.

## Open Questions the Paper Calls Out
- **Cross‑framework portability:** Can `lrnnx` be ported to JAX or TensorFlow while preserving its unified interface and performance? The current PyTorch‑only implementation excludes those communities.
- **Hardware backend diversification:** How can the dependency on NVIDIA‑specific CUDA kernels be mitigated to support AMD, Intel, or CPU backends without >15% performance loss?
- **PyTorch inference overhead:** What specific PyTorch mechanisms cause slower inference compared to JAX, and can they be eliminated via further optimizations?
- **Ecosystem integration:** What adapter layers are needed to integrate `lrnnx` natively with Hugging Face Transformers and DeepSpeed?
- **Bidirectional LRNNs:** How can bidirectional variants be implemented within the three‑tier architecture without breaking existing functionality, despite the interface being designed to support them?

## Limitations
- **Benchmark specifics unstated:** Exact hyperparameters (batch sizes, sequence lengths, model dimensions), model versions, and discretization schemes used in the paper’s sweeps are not provided, hindering exact replication.
- **Framework/hardware lock‑in:** The library is restricted to PyTorch and relies on custom CUDA kernels, limiting use on other frameworks or non‑NVIDIA hardware.
- **Abstraction leakage risk:** The unified hierarchy may not expose all architecture‑specific tuning parameters (e.g., Mamba’s `A` parameterization constraints), potentially limiting advanced research or leading to suboptimal settings.
