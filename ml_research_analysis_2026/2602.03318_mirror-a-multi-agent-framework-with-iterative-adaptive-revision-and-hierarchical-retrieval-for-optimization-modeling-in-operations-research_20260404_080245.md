# MIRROR: A Multi-Agent Framework with Iterative Adaptive Revision and Hierarchical Retrieval for Optimization Modeling in Operations Research

## Quick Facts
- **arXiv ID:** 2602.03318
- **Source URL:** https://arxiv.org/abs/2602.03318
- **Reference count:** 30
- **Primary result:** MIRROR achieves state-of-the-art performance on OR benchmarks with a macro-average pass@1 accuracy of 71.88%, and significant gains on complex industrial datasets.

## Executive Summary
MIRROR is a fine-tuning-free multi-agent framework that automates operations research modeling from natural language. It integrates two core mechanisms: execution-driven iterative adaptive revision (IAR) for automatic error correction and hierarchical retrieval-augmented generation (HRAG) for fetching relevant exemplars. On standard benchmarks, it achieves a macro-average pass@1 of 71.88%, outperforming prior multi-agent methods, especially on complex industrial problems. The framework also boosts smaller open-source models without task-specific training.

## Method Summary
MIRROR uses a generator agent to produce initial optimization models and code, guided by exemplars retrieved from a curated library via HRAG. The output is executed in a solver (Gurobi); if errors occur, an IAR reviser agent uses execution feedback and historical tips stored in a local memory to propose revisions. This loop repeats until a feasible solution is found or a limit is reached. The hierarchical retrieval first filters by metadata (problem type/subtype) then reranks by LLM, ensuring relevant examples.

## Key Results
- Macro-average pass@1 accuracy of 71.88% across standard OR benchmarks, setting a new SOTA among multi-agent methods.
- On complex industrial datasets, MIRROR achieves 67.50% on Mamo-ComplexLP and 57.00% on IndustryOR, surpassing prior SOTA by 6.4 and 9.0 percentage points respectively.
- Enhances smaller models significantly; for qwen3-30B, pass@1 improves by 12.15 points without task-specific training.

## Why This Works (Mechanism)
The synergy between HRAG and IAR drives performance. HRAG reduces fundamental modeling errors by providing high-quality, relevant exemplars, as evidenced by its larger impact in ablations. IAR then systematically corrects execution errors using feedback and accumulated revision tips in local memory, enabling progress across iterations. The fine-tuning-free design leverages existing LLM reasoning while avoiding domain-specific training, making it adaptable.

## Foundational Learning

   *Why needed:* HRAG extends RAG to retrieve exemplars that ground the model in correct OR patterns.  
   *Quick check:* How does a two-stage retrieval (metadata filter + LLM rerank) improve relevance over pure embedding search?

2. **Iterative Refinement with Execution Feedback**  
   *Why needed:* IAR uses solver feedback to correct code, a core loop for error recovery.  
   *Quick check:* Why store revision tips in local memory rather than re-generating each iteration?

3. **Multi-Agent Systems for Code Generation**  
   *Why needed:* Separates generation, execution, and revision into specialized agents for focused capabilities.

   *Why needed:* The target domain involves formulating and solving optimization problems (e.g., LP, MILP).

5. **Hierarchical Retrieval**  
   *Why needed:* HRAG balances efficiency (metadata filtering) and precision (LLM reranking).

## Architecture Onboarding
User Query -> Generator Agent (with HRAG retrieval) -> Initial Model/Code -> Executor (Gurobi) -> On error: IAR Reviser (uses local memory) -> Revised Model/Code -> Loop until success or max iterations.

*Critical Path:* The main flow is retrieval -> generation -> execution -> if error, revision -> back to execution. Local memory persists across iterations.

*Design Tradeoffs:*
- Fine-tuning-free vs. peak accuracy: Avoiding fine-tuning increases generalizability but may limit performance on narrow domains.
- Retrieval library size vs. speed: Larger libraries improve coverage but increase retrieval cost; HRAG's hierarchy mitigates this.
- Iteration limit vs. resource use: More revisions can fix complex errors but increase inference cost and latency.

*Failure Signatures:*
- Retrieval failure: HRAG returns irrelevant exemplars, leading to persistent modeling errors.
- Revision failure: IAR cycles without progress or introduces new errors due to misdiagnosed tips.
- Solver mismatch: Generated code uses unsupported features (e.g., non-linear constraints in Gurobi) causing unrecoverable failures.

*First Three Experiments:*
1. Ablate HRAG: Disable hierarchical retrieval (use random or no exemplars) to measure its impact on accuracy.
2. Clear local memory: Compare performance when IAR's memory is reset each iteration versus retained.
3. Scale exemplar library: Vary library size (e.g., 100, 300, 602) to assess coverage effects, especially on out-of-distribution problems.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: How does the scale and diversity of the exemplar library (L) impact MIRROR's generalization to novel or highly specialized OR problem domains not represented in the current 602-instance collection?
- Basis in paper: [inferred] The exemplar library is constructed from a fixed set of sources (OptiBench, OptMATH, Mamo-EasyLP) and filtered for balance and correctness (Section C.1), but its coverage of subproblem types and real-world complexity is not analyzed.
- Why unresolved: The paper demonstrates strong performance on five benchmarks, but these may share distributional similarities with the library. Unseen domains (e.g., stochastic optimization, non-convex NLP) or extreme-scale problems could expose retrieval limitations.
- What evidence would resolve it: Systematic evaluation on out-of-distribution benchmarks (e.g., new industrial case studies, academic problems from unfamiliar domains) with controlled variation in exemplar library composition. Ablation studies varying library size and domain diversity would quantify the relationship between exemplar coverage and accuracy.

### Open Question 2
- Question: To what extent can the structured revision tips (τ) generated by the IAR mechanism introduce or propagate subtle modeling errors if initial tips are flawed, and how does the local memory pool's historical tips affect long-term reliability?
- Basis in paper: [explicit] The IAR mechanism stores "historical models, solver code, and associated revision tips" in local memory to provide context for subsequent iterations (Section 3.1.2, Page 5). The case study (Appendix D) shows tips correcting specific errors, but the cumulative effect of potentially incorrect tips is not examined.
- Why unresolved: Tips are generated by LLM agents based on execution errors; if a tip misdiagnoses a root cause (e.g., due to ambiguous error messages), subsequent revisions might compound errors. The framework lacks a verification mechanism for tip correctness beyond re-execution.
- What evidence would resolve it: Controlled experiments where known incorrect tips are injected into the memory pool, measuring degradation in solution accuracy over multiple revision rounds. Analysis of tip-generation accuracy across datasets and error types would reveal failure modes.

### Open Question 3
- Question: How effective is the hierarchical retrieval mechanism (HRAG) at handling natural language problem descriptions that are ambiguous, incomplete, or contain implicit domain assumptions not captured in the exemplar metadata annotations?
- Basis in paper: [inferred] HRAG relies on pre-annotated "problem_type" and "problem_subtype" metadata for coarse-grained filtering (Section C.1), assuming problem descriptions align with labeled categories. The paper does not address robustness to linguistic variation or missing details.
- Why unresolved: Real-world OR problems often involve underspecified constraints (e.g., "reasonable," "typical") or mixed problem types. The retrieval's two-stage strategy (metadata filter + LLM reranking) may fail to surface relevant exemplars if the query's semantic essence diverges from annotated labels.
- What evidence would resolve it: Adversarial or perturbed problem statements (e.g., paraphrasing, removing key constraints, adding irrelevant details) to test retrieval recall and downstream solution accuracy. Human evaluation of retrieved exemplars' relevance for ambiguous queries.

### Open Question 4
- Question: Does MIRROR's fine-tuning-free design maintain its performance advantage when applied to next-generation reasoning-optimized LLMs (e.g., o1-style models) versus general-purpose LLMs, and how do the contributions of IAR vs. HRAG shift with model capability?
- Basis in paper: [explicit] The paper uses qwen-plus (general) and qwen3-30B (small) as backbones, comparing to CoT on DeepSeek-v3 (a reasoning model) but without a full MIRROR variant on reasoning architectures (Table 1). The ablation (Table 2) shows HRAG has larger impact on reducing wrong answers, but this may be model-dependent.
- Why unresolved: Reasoning models incorporate internal self-correction; the added value of external IAR/HRAG might differ. The relative importance of retrieval (HRAG) versus execution-driven revision (IAR) could change if the base model already excels at certain reasoning steps.
- What evidence would resolve it: Replicate experiments using reasoning-focused LLMs (e.g., o1, DeepSeek-R1) as MIRROR backbones, performing identical ablations. Compare error decomposition (compile vs. wrong answer rates) to the results in Figure 2 to see if IAR's role diminishes or HRAG remains critical.

### Open Question 5
- Question: How does MIRROR perform on optimization problems requiring non-standard solver features (e.g., quadratic constraints, piecewise linear approximations, or stochastic elements) that are under-represented in the Gurobi-focused exemplar library?
- Basis in paper: [inferred] The exemplar library and generated code are tailored for Gurobi with linear/MILP emphasis (Section 3.1.1, Page 4; case study uses linear constraints). The paper benchmarks on primarily LP/MILP datasets (NL4Opt, Mamo, etc.) with limited mention of non-linear or stochastic problems.
- Why unresolved: The library's construction prioritizes "balanced optimization instances" and executable code (Section C.1), likely biasing toward well-structured, deterministic models. Complex OR tasks involving non-convexities, risk constraints, or simulation-based objectives may fall outside the library's distribution and Gurobi's native capabilities.
- What evidence would resolve it: Evaluate MIRROR on benchmarks featuring non-linear programming (NLP), mixed-integer non-linear programming (MINLP), or stochastic programming, using appropriate solvers (e.g., IPOPT, SCIP). Analyze failure modes to determine whether retrieval or revision mechanisms can adapt to such problem classes.

## Limitations
- **Benchmark Generalizability:** Performance is validated on a narrow set of LP/MILP benchmarks; applicability to non-linear, stochastic, or combinatorial design problems remains unproven.
- **Component Interaction:** Ablations show additive benefits, but the dynamics of retrieval and revision in complex failure chains are not deeply characterized.
- **Resource & Cost:** The iterative multi-agent setup likely increases computational cost and latency compared to single-prompt or fine-tuned baselines, but this trade-off is not quantified.
