# SAGE: Multi-Agent Self-Evolution for LLM Reasoning

## Quick Facts
- arXiv ID: 2603.15255
- Source URL: https://arxiv.org/abs/2603.15255
- Reference count: 10
- Primary result: SAGE improves LLM reasoning on math and code benchmarks by 8.9% (LiveCodeBench) and 10.7% (OlympiadBench) while achieving state-of-the-art average across three model scales.

## Executive Summary
SAGE is a multi-agent framework that enables large language models to self-evolve for reasoning tasks without relying on large human-labeled datasets or unstable self-play. It instantiates four agents—Challenger, Planner, Solver, and Critic—from a single LLM backbone, which co-evolve using only a small seed set of examples. The Challenger generates verifiable tasks; the Planner creates solution plans; the Solver executes plans; and the Critic ensures quality and format. All agents are trained end-to-end with reinforcement learning using automatic verifiers as rewards. On Qwen-2.5-7B, SAGE achieves significant improvements on LiveCodeBench (+8.9%) and OlympiadBench (+10.7%). Across 3B, 7B, and 4B-base models, it attains the highest average scores on combined code and math benchmarks, demonstrating strong generalization and stability.

## Method Summary
SAGE employs a closed-loop multi-agent system where all agents share a single LLM (e.g., Qwen-2.5-7B) with LoRA adapters. Training alternates between two phases: (1) the Challenger generates new questions conditioned on reference examples; the Critic filters these by quality and format, admitting only high-scoring ones into a growing dataset D. (2) The Planner produces a solution plan for a sampled question from D; the Critic gates the plan, and if accepted, the Solver executes it. All agents are updated using Task-Relative REINFORCE++, with rewards derived from external verifiers (e.g., test pass rates for code, exact match for math) and Critic scores. The seed dataset of ~500 examples bootstraps the process, enabling self-improvement without human annotation.

## Key Results
- On Qwen-2.5-7B, SAGE yields +8.9% absolute improvement on LiveCodeBench and +10.7% on OlympiadBench.
- Across three model scales (3B, 7B, 4B-base), SAGE achieves the highest overall average scores on combined code and math benchmarks.
- The framework demonstrates strong out-of-distribution generalization without sacrificing in-distribution accuracy.

## Why This Works (Mechanism)

**Mechanism 1: Adversarial Curriculum Generation via Challenger-Solver Loop**  
The Challenger generates tasks conditioned on reference examples. Its reward includes a difficulty term derived from the Solver's success rate: if the Solver fails, the Challenger is rewarded for harder tasks; if the Solver succeeds easily, the difficulty reward is low. The Solver is trained simultaneously with verifier-based correctness signals. This co-evolutionary loop pushes the curriculum toward tasks that are challenging yet solvable, preventing collapse. Core assumption: the external verifier is reliable and Solver success rate is a monotonic proxy for difficulty. Evidence: abstract mentions self-rewarding cycle; section 4.2 describes difficulty reward; R-Diverse shows naive self-play suffers diversity collapse, mitigated by SAGE's Critic and difficulty suppression. Break condition: noisy verifier or low quality threshold α may cause drift to unsolvable tasks.

**Mechanism 2: Multi-Agent Role Specialization with Shared Backbone**  
Decomposing reasoning into four roles using the same LLM backbone (conditioned on role instructions) yields better performance and stability than a monolithic policy. Each agent performs a specific subtask (question generation, planning, solving, critiquing). They are trained jointly with Task-Relative REINFORCE++ and per-role advantage normalization, enabling specialization while sharing knowledge. Core assumption: a single LLM can capably perform multiple functions when properly prompted, and decomposition benefits outweigh interference. Evidence: abstract states four agents co-evolve from shared backbone; section 3 describes role-based multi-agent reasoning; sections 4.3-4.5 detail agent prompts and rewards. Break condition: ambiguous prompts or conflicting gradients may blur specialization.

**Mechanism 3: Critic-mediated Quality Control and Format Calibration**  
The Critic agent filters generated questions and plans by quality and enforces required output formats. It outputs numeric scores; only items above thresholds (α for questions, β for plans) are admitted. Format rewards ensure compliance with tags (e.g., <question>, <answer>), stabilizing training. Core assumption: Critic's assessments correlate with downstream success and format compliance is necessary. Evidence: abstract mentions Critic scores and filters; section 4.1 and 4.5 describe format rewards and quality scores; section 5.3 ablation shows Critic's removal degrades code performance; R-Zero notes instability without quality control. Break condition: mis-calibrated Critic may starve pipeline or admit low-quality data; overly rigid format enforcement may hinder expression.

## Architecture Onboarding

**Component map:** Shared backbone LLM Mθ (with LoRA adapters) → four role-conditioned agents: Challenger (πc), Planner (πp), Solver (πs), Critic (πcr). Dataset D stores (question, verifier) pairs, initialized with seed set D0 (~500). External verifier Vgt provides correctness scores. Training alternates between Challenger phase (generate questions, Critic filters, add to D) and Plan-Solve phase (Planner plans, Critic gates, Solver solves).

**Critical path (one iteration):**  
1. Sample (q_ref, v_ref) from D.  
2. Challenger generates (q_t, v_t) conditioned on reference.  
3. Critic scores q_t; if score ≥ α and v_t valid, add to D.  
4. Sample multiple Solver answers on q_t; compute average verifier score ¯s_gt; difficulty reward r_d = 1 - ¯s_gt.  
5. Compute Challenger reward rc and update πc and shared θ via Task-Relative REINFORCE++.  
6. Sample (q, v) from D.  
7. Planner generates plan p; Critic scores → sp.  
8. If sp ≥ β, use plan ˜p = p; else ˜p = ∅.  
9. Solver generates answer a_t conditioned on q and ˜p; verifier gives sgt = Vgt(q, a_t, v).  
10. Compute Planner reward rp = λ_plan sp + λ_f rf(op); Solver reward rs = w_p ˜sp + w_c sgt + w_f rf(os).  
11. Update πp, πs, and shared θ with per-role normalized advantages.  
12. Critic optionally updated with format reward.

**Design tradeoffs:**  
- Shared backbone vs separate models: sharing reduces memory and enables transfer but risks interference; separate avoid interference but increase cost.  
- Quality threshold α: higher ensures quality but reduces generation rate; lower increases data but risks drift. Paper uses α=0.7.  
- Planning gating threshold β: lower increases plan usage but may include poor plans; higher reduces influence; paper uses β=0.3.  
- Temperatures: higher (0.6) for generative agents to encourage diversity; lower (0.1) for Critic determinism.  
- LoRA rank: low-rank adaptation balances efficiency and capacity; rank 128 is a compromise, too low may limit specialization.

**Failure signatures:**  
- Validation accuracy peaks then declines, indicating over-specialization.  
- Low valid verifier pass rate from Challenger (e.g., non-executable code tests) signals degradation.  
- Critic scores collapse to narrow range (e.g., all ~0.5 or all ~9), indicating mis-calibration.  
- Format reward consistently low, causing parsing errors.  
- Dataset size grows rapidly while performance plateaus or drops after a point.

**First 3 experiments:**  
1. **Critic ablation:** Disable Critic updates (freeze πcr or remove its reward) and measure impact, expecting degradation on code benchmarks (per Table 3).  
2. **Threshold sensitivity:** Vary α ∈ {0.5,0.7,0.9} and β ∈ {0.1,0.3,0.5}. Measure dataset quality (human evaluation of 100 generated questions) and final benchmark scores; expect optimal around α=0.7, β=0.3.  
3. **Planner gating study:** Compare: (a) always provide plan (β=0), (b) never provide plan (β=1), (c) adaptive (β=0.3). Evaluate on math vs code tasks; expect (c) best, as plans help multi-step reasoning but may hurt if low-quality.

## Open Questions the Paper Calls Out
- **Open Question 1:** Extending SAGE to open-ended tasks requiring subjective evaluation. Basis: Section 7 suggests extending to subjective tasks via learned reward models. Unresolved: SAGE relies on verifiable domains; subjective tasks need learned models that risk instability. Resolution evidence: Integrate a reward model trained on human preferences, evaluate on benchmarks like AlpacaEval.
- **Open Question 2:** Minimal seed dataset size needed. Basis: Section 7 notes the 500-example seed requirement. Unresolved: Lower bound not explored; too few seeds may cause poor initialization. Resolution evidence: Systematically vary seed size (500 down to 10), track performance, diversity, failure modes.
- **Open Question 3:** Generalization to other structured reasoning domains (logic, scientific). Basis: Section 7 suggests exploring such domains. Unresolved: Evaluation only on math/code; other domains may have different verification, planning needs. Resolution evidence: Apply SAGE to logical reasoning (LOGIC, ReClor) and scientific QA (GPQA, SCIENCEQA), compare baselines and analyze agent roles.
- **Open Question 4:** Causes of post-peak accuracy decline and mitigation of over-specialization. Basis: Figure 3 shows decline after steps 100-140. Unresolved: Root causes (curriculum narrowing, reward hacking) unexplored; early stopping only mitigation. Resolution evidence: Monitor task distribution over training, correlate with performance; test interventions like curriculum diversification, adaptive Critic thresholds, diversity rewards.

## Limitations
- Verifier reliability dependency: SAGE assumes noiseless verifiers; imperfect ones destabilize curriculum.
- Critic calibration fragility: Fixed thresholds (α, β) may be mis-calibrated, starving pipeline or admitting low-quality data.
- Shared backbone interference: Joint training risks gradient conflicts between roles, especially across scales.

## Confidence
- Multi-agent framework efficacy: High
- Critic's stabilizing role: Medium
- Self-sustaining curriculum: Low

## Next Checks
1. Verifier noise stress test: Introduce controlled noise (10-20% incorrect labels) into code test execution; measure performance decay versus baseline.
2. Role interference probe: After training, extract per-role LoRA adapters and evaluate each agent's standalone capability on its target task; significant gaps indicate interference.
3. Critic calibration audit: Periodically compare Critic scores on a human-labeled subset against ground-truth quality; track correlation drift over iterations.
