# LLM Readiness Harness: Evaluation, Observability, and CI Gates for LLM/RAG Applications

## Quick Facts
- arXiv ID: 2603.27355
- Source URL: https://arxiv.org/abs/2603.27355
- Reference count: 11
- Primary result: The readiness harness enables multi-dimensional evaluation with CI gates, showing gpt-4.1-mini optimal for SLA-first FiQA (readiness 0.808) and blocking policy-violating releases.

## Executive Summary
Production deployment of LLM/RAG systems often suffers from silent regressions and policy violations due to lack of rigorous release workflows. This paper introduces a readiness harness that combines automated benchmarks, OpenTelemetry observability, and CI quality gates under a minimal API contract. The harness computes scenario-weighted readiness scores from metrics like workflow success, policy compliance, groundedness, retrieval hit rate, cost, and latency, and uses Pareto frontiers to visualize trade-offs. Hard gates block policy violations and regressions automatically.

The framework was evaluated on BEIR (SciFact, FiQA) and ticket-routing datasets using Azure-hosted models. Results show that readiness is multi-dimensional: for SLA-first scenarios on FiQA, gpt-4.1-mini leads in readiness (0.808) and faithfulness (0.777) while incurring lower latency than gpt-5.2. Regression gates consistently reject unsafe prompt variants, demonstrating the harness's ability to prevent risky releases.

## Method Summary
The harness comprises an API service, a batch runner, OpenTelemetry instrumentation, CI gates via promptfoo, and artifact storage. The API exposes an inference endpoint returning structured JSON with metadata (run_id, latency, cost, trace ids). The batch runner orchestrates dataset sampling, calls the API, writes artifacts (report.json, summary.csv), and triggers RAGAS evaluation. OpenTelemetry spans (infer, route.classify, rag.retrieve, rag.generate, validate.policy, respond.finalize) enable observability. CI gates enforce schema compliance, policy checks, and regression thresholds against baselines, failing builds on violations. Readiness scores are computed as weighted aggregates of available metrics, with normalization when some metrics are missing, and Pareto frontiers identify non-dominated configurations per scenario.

Reproduction involves cloning the public repository, installing dependencies, configuring Azure OpenAI credentials, and running batch jobs with parameters such as dataset (BEIR or ticket-routing), models, scenarios, top_k, seeds, and sample sizes. Artifacts are parsed to compute scores and frontiers. Challenges include incomplete prompt templates for ticket routing and Azure-specific latency variability.

## Key Results
- gpt-4.1-mini achieved highest readiness (0.808) and faithfulness (0.777) on FiQA under SLA-first scenario (k=5).
- gpt-5.2 incurred approximately double the latency compared to smaller models.
- Regression gates successfully blocked all tested unsafe prompt variants, preventing policy-violating releases.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Readiness cannot be reduced to a single metric; it must be a composite score reflecting task-specific operational constraints.
- **Mechanism:** The harness computes a weighted aggregate `R = Σ (w_i * m_i) / Σ (w_i)` over available metrics (workflow success, policy compliance, groundedness/faithfulness, retrieval hit@k, cost, p95 latency). Weights are scenario-specific (cost-first, risk-first, SLA-first) and normalized when some metrics are absent (e.g., retrieval metrics omitted for pure ticket-routing tasks).
- **Core assumption:** Stakeholders can agree on relative importance (weights) for their deployment context, and missing metrics are acceptably rare or ignorable.
- **Evidence anchors:**
  - [abstract] "aggregates workflow success, policy compliance, groundedness, retrieval hit rate, cost, and p95 latency into scenario-weighted readiness scores"
  - [section] Section 3 details the scoring formula, normalization for missing metrics (`P`), and Table 2 defines scenario weights.
  - [corpus] Corpus analysis shows related work (e.g., HELM, ARES) focuses on multi-metric benchmarking but the target paper uniquely binds metrics to deployment gates and observability.
- **Break condition:** If critical metrics are frequently missing across runs, or if weight selection is arbitrary/unvalidated, the score becomes non-auditable and potentially misleading.

### Mechanism 2
- **Claim:** Deployment decisions require visualizing cost–utility trade-offs via Pareto frontiers, not just absolute scores.
- **Mechanism:** For each scenario, the harness identifies non-dominated pipeline configurations (varying model, `k`, seed) by maximizing quality signals (faithfulness, hit@k) while minimizing cost and latency. These frontiers make explicit which configurations offer better quality for the same cost/latency.
- **Core assumption:** Stakeholders can interpret frontier plots to choose configurations aligning with their budget and SLA constraints, and that the selected quality and cost metrics are sufficient proxies for business value.
- **Evidence anchors:**
  - [abstract] "aggregates ... into scenario-weighted readiness scores with Pareto frontiers."
  - [section] Section 3 describes frontier computation; Figures 2 and 3 visualize latency vs. readiness; Table 4 lists frontier runs for SciFact.
  - [corpus] Related work (e.g., Zellinger & Thomson 2025) formalizes accuracy-cost trade-offs, supporting the frontier approach.
- **Break condition:** If all configurations are dominated (no clear winners) or if cost/quality metrics conflict strongly (e.g., best quality is too expensive), the frontier provides no actionable guidance without external business rules.

### Mechanism 3
- **Claim:** CI quality gates must block releases on hard policy violations and regressions, not just report scores.
- **Mechanism:** The harness integrates `promptfoo` in CI to enforce schema compliance, policy checks (e.g., no credential requests), and threshold-based regressions against a baseline. Failed gates prevent deployment regardless of aggregate readiness score.
- **Core assumption:** Policy rules capture non-negotiable safety/regulatory requirements, and regression thresholds are set sensitively enough to detect meaningful degradation.
- **Evidence anchors:**
  - [abstract] "CI gates ... blocking risky releases" and "Ticket-routing regression gates consistently reject unsafe prompt variants."
  - [section] Section 6 shows policy regression variants failing gates (Table 7: ∆Policy ≈ -0.93 to -0.97) while bias variants also fail.
  - [corpus] Barnett et al. (2024) identify policy/grounding as key RAG failure points, motivating hard gates.
- **Break condition:** If policy rules are incomplete or outdated, or if gate thresholds are set too loosely/tightly, the system either misses harmful releases or blocks benign improvements.

## Foundational Learning
- **Concept: RAG evaluation metrics (faithfulness, retrieval hit@k)**
  - *Why needed here:* These are core quality dimensions in the readiness score. Faithfulness (via RAGAS) measures answer grounding in retrieved context; hit@k measures retrieval recall. Without these, the harness cannot assess groundedness.
  - *Quick check question:* What does a low faithfulness score imply about the RAG output's reliability?

- **Concept: OpenTelemetry instrumentation**
  - *Why needed here:* Creates standardized spans (Table 1) for every inference step (retrieve, generate, validate.policy). This observability is essential for post-mortem debugging when a gate fails or latency spikes.
  - *Quick check question:* Which span would you inspect to diagnose a high p95 latency caused by slow retrieval?

- **Concept: CI/CD quality gates with hard/soft logic**
  - *Why needed here:* Gates automate release safety. Hard gates (policy violations) block unconditionally; soft gates (score thresholds) depend on scenario weights. Understanding this distinction is key to configuring the harness.
  - *Quick check question:* In a risk-first scenario, would a minor cost increase ever trigger a hard gate? Why or why not?

## Architecture Onboarding
- **Component map:**
  1. **API Service** (`/v1/infer`): Handles single/batch inference, returns structured JSON + metadata (run_id, latency, cost, trace ids).
  2. **Batch Runner**: Orchestrates dataset sampling, calls API, writes artifacts (`report.json`, `summary.csv`), triggers RAGAS evaluation.
  3. **OpenTelemetry Instrumentation**: Injects spans (Table 1) into API calls; exported to backend for analysis.
  4. **CI Gates** (`promptfoo`): Consume artifacts, check schema/policy, compare against baselines, pass/fail build.
  5. **Artifact Storage**: Persists run-level outputs for audit and reproducibility.

- **Critical path:** 
  `Dataset → Batch Runner → API (with OTel spans) → Metrics calculation → Readiness scoring → Pareto frontier update → CI gate evaluation → Pass/Fail decision.`
  Any break in spans or artifact generation disrupts scoring and gate logic.

- **Design tradeoffs:**
  - **Simplicity vs. Coverage:** The harness uses a small, fixed metric set to remain auditable, but may miss domain-specific signals (e.g., answer relevance returned empty in experiments).
  - **Hard gates vs. Scores:** Policy violations are hard blockers, but overly strict rules could stifle innovation; weight-based scores allow trade-offs but require stakeholder calibration.
  - **Cross-provider comparability:** The evaluation matrix is provider-specific (Azure OpenAI); transferring weights/frontiers to other LLM providers requires re-running benchmarks.

- **Failure signatures:**
  - **Missing OTel spans:** `rag.retrieve` or `validate.policy` absent in trace → instrumentation misconfigured.
  - **Schema validation failures in CI:** Output JSON doesn't match required schema → prompt or parser broken.
  - **Policy violation rate > 0:** Gate fails immediately; inspect `policy_violations` array in artifacts.
  - **P95 latency outliers:** e.g., 30s+ in BEIR runs → likely transient Azure issues (Section 8) or retrieval inefficiency.
  - **Readiness score NaN:** Too many metrics missing (`P` empty) → check dataset configuration and metric collection.

- **First 3 experiments:**
  1. **Baseline end-to-end run:** Execute batch runner on a small public dataset (e.g., SciFact sample) with `sample_n=10`. Verify artifacts (`summary.csv` has all expected columns; `report.json` contains valid spans and metrics). Confirm readiness score calculates without errors.
  2. **CI gate test:** Create a deliberate policy-violating prompt variant (e.g., remove "Do not request passwords" from system message). Run in CI and confirm `promptfoo` fails the gate with `policy_violation_rate > 0`.
  3. **Regression detection:** Compare two prompt versions (v1 vs. v2) on the same dataset seed. Verify that a significant drop in workflow success or policy pass rate (e.g., ∆Policy < -0.1) triggers a gate failure per Table 7's pattern.

## Limitations
- Ticket-routing prompt templates (v1/v2) are inferred, not fully specified—reconstruction may diverge from authors' implementation.
- Azure-specific latency/cost metrics may not generalize to other cloud/on-prem providers.
- Corpus signals show low external validation (avg citations 0.0, avg FMR 0.574), suggesting the approach is not yet widely replicated.

## Confidence
- Harness design & metrics: High (well-defined formula, OTel spans, CI gates validated on 162 cells).
- Generalizability beyond BEIR/Azure: Medium (evaluated on 2 datasets; cross-provider transfer untested).
- Business value alignment (weight selection): Low (subjective scenario weights lack empirical stakeholder validation).
