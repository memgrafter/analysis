# SoftMatcha 2: A Fast and Soft Pattern Matcher for Trillion-Scale Corpora

## Quick Facts
- **arXiv ID**: 2602.10908
- **Source URL**: https://arxiv.org/abs/2602.10908
- **Reference count**: 40
- **Primary result**: Achieves 95th-percentile latency of 0.34 ms (exact) and 278.17 ms (soft) on the 1.4‑trillion‑token FineWeb‑Edu corpus, outperforming prior methods by 33× (exact) and scaling to multiple languages.

## Executive Summary
SoftMatcha 2 introduces a system for fast soft pattern matching over trillion‑scale text corpora, handling semantic variations such as substitutions, insertions, and deletions. It combines a disk‑aware suffix array for constant‑time exact lookups with dynamic corpus‑aware pruning that exploits the power‑law distribution of n‑grams to control exponential candidate growth. On the 1.4‑trillion‑token FineWeb‑Edu corpus, it achieves a 95th‑percentile latency of 0.34 ms for exact search (33× faster than infini‑gram) and 278.17 ms for soft search, while demonstrating cross‑lingual scalability and uncovering benchmark contamination via semantic and template leakages that exact matching misses.

## Method Summary
The method hinges on three innovations: (1) a two‑staged disk‑aware suffix array where a sparse RAM index points to compressed on‑disk blocks, enabling exact substring lookup with one random disk access; (2) iterative candidate generation and pruning that uses exact corpus lookups to filter similar tokens at each position, leveraging Zipf’s law to keep the candidate set small; (3) a smooth minimum similarity score over token embeddings with insertion/deletion penalties proportional to word vector norms, down‑weighting uninformative words. Together, these enable soft pattern matching at scale with sub‑second latency.

## Key Results
- Exact search p95 latency: **0.34 ms** on 1.4 T tokens (vs. infini‑gram: 11.05 ms).
- Soft search p95 latency: **278.17 ms** on same corpus.
- Pruning reduces n‑gram candidate growth from **5.17× to 2.27×** per token (ablation).

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Fast exact string lookup with one random disk access per query, enabling scalable indexing for trillion‑token corpora.
- **Mechanism**: A two‑staged disk‑aware suffix array: a sparse index `Y` (stored in RAM) points to blocks of a compressed suffix array `X` (stored on disk). For a query, binary search in `Y` identifies a block in `X`; a second binary search within that block finds exact matches. Run‑length compression reduces disk footprint.
- **Core assumption**: Queries are short (≤12 tokens), and the block size `B` is tuned so that the second search range fits in the OS page cache, avoiding additional disk seeks.
- **Evidence anchors**:
  - [abstract] "disk‑aware design ... one random disk access per match"
  - [section 3.2] Describes the staged index and compression; reports 33× speedup over infini‑gram (11.05 ms → 0.34 ms p95).
  - [corpus] On FineWeb‑Edu (1.4 T tokens), exact search p95 latency 0.34 ms; index size 21.6 TB with compression (from 56 TB uncompressed).
- **Break condition**: If query length exceeds `L` (12) or `B` is misconfigured relative to page size, disk accesses may rise to O(log |C|), degrading performance.

### Mechanism 2
- **Claim**: Dynamic corpus‑aware pruning restricts exponential candidate growth by exploiting the power‑law distribution of n‑grams in natural language.
- **Mechanism**: Iterative pruning: at each token position, generate candidate continuations via similarity, filter to those occurring in the corpus using the suffix array. Supplemented by k‑gram caching (precomputed 2/3‑gram existence in RAM) and last‑bits pruning (direct enumeration for ultra‑rare patterns).
- **Core assumption**: Natural language n‑gram frequencies follow a power law (Zipfian); thus the ratio |L_i|/|S_i| ≈ |C_i^*|/|V|^i is very small for large i (Hypothesis 1). This limits the number of corpus‑validated candidates per step.
- **Evidence anchors**:
  - [abstract] "dynamic corpus‑aware pruning that exploits the power‑law distribution of n‑grams"
  - [section 3.3] Algorithm 1 and pruning techniques; ablation in §5.3 shows growth per token reduced from 5.17× to 2.27×.
  - [corpus] Query length up to 10 tokens still yields sub‑second latencies; p95 soft search 278.17 ms on 1.4 T tokens (Fig 4).
- **Break condition**: If the corpus lacks Zipfian statistics (e.g., synthetic uniform n‑grams), pruning effectiveness drops; adaptive threshold relaxation (§3.1) may be required for longer queries.

### Mechanism 3
- **Claim**: Smooth minimum similarity with norm‑based insertion/deletion penalties enables robust soft matching that aggregates token‑level semantics and down‑weights uninformative words.
- **Mechanism**: Similarity = 1 − log_β(∑(β^(1−c_i) − 1) + 1), a smooth minimum over token cosine similarities c_i. Insertions/deletions scale similarity by exp(−v/γ), where v is squared word norm after Zipfian whitening (correlates with information entropy). β=10⁴, γ proportional to query length.
- **Core assumption**: Word vector norms encode informativeness; common function words (e.g., "the") have low norms and should incur smaller penalties. The smooth minimum avoids ignoring all but the worst token similarity.
- **Evidence anchors**:
  - [section 3.1] Formulation and examples: captures "olympics gold medal" vs. "olympics silver medal" and variable‑length matches like "importance of machine learning" (Table 4).
  - [section 6] Contamination detection: 81% precision (29/36) on soft‑only flagged examples, revealing semantic and template leakages missed by exact match.
  - [corpus] Multilingual examples (Tables 5–10) show consistent handling of insertions/deletions across languages.
- **Break condition**: If embeddings are misaligned with corpus semantics or norms do not correlate with entropy, similarity scores become noisy; β and γ require corpus‑specific tuning.

## Foundational Learning
- **Suffix Arrays**: Why needed: The core index for exact substring enumeration; binary search on sorted suffixes gives O(log |C|) lookup, but disk‑aware design reduces to constant accesses. Quick check: Why does a suffix array enable fast exact search for a query string? By sorting all suffixes, the query's occurrence range can be found via binary search, returning all positions in that range.
- **Power‑law distributions in natural language**: Why needed: Pruning leverages the fact that only a tiny fraction of all possible n‑grams actually occur; candidate patterns similar to the query but rare are eliminated early via corpus checks. Quick check: Why does Zipf's law imply that |C_i^*| ≪ |V|^i for large i? Because frequency decays as a power law; the number of distinct n‑grams grows sublinearly with corpus size, while |V|^i explodes.
- **Word embeddings and cosine similarity**: Why needed: To quantify semantic substitution similarity between tokens; embeddings map words to vectors where cosine similarity captures meaning proximity. Quick check: Why use a smooth minimum instead of min(c₁,…,cₘ) for pattern similarity? The plain minimum ignores all but the worst token; smooth minimum aggregates all token similarities, making the score more robust.

## Architecture Onboarding
- **Component map**: 
  Index construction: Tokenize corpus → Build run‑length compressed suffix array X (disk) → Generate sparse index Y (RAM). 
  Query processing: Tokenize query → Adaptive α relaxation → Iterative candidate generation (with smooth similarity) → Exact lookup (disk‑aware suffix array) → k‑gram/last‑bits pruning → Return top‑K. 
  Embedding lookup: Cache word vectors for similarity computation.
- **Critical path**: Latency dominated by number of exact lookups (reduced by pruning) and per‑lookup disk access time (minimized by disk‑aware design). The iterative loop (Algorithm 1) is the bottleneck.
- **Design tradeoffs**:
  - Memory vs. disk: Index compressed but requires SSD; tradeoff compression ratio vs. lookup speed (decompression cost).
  - Recall vs. precision: Lower α finds more matches but increases noise; adaptive thresholding balances by targeting fixed K.
  - Language support: Requires compatible tokenizer and embeddings; subword tokenizers may need case normalization (Appendix G).
- **Failure signatures**:
  - High latency: Candidate explosion due to poor pruning (e.g., many high‑frequency similar words); monitor |L_i| growth.
  - Low recall: Embeddings not aligned with corpus (e.g., domain mismatch); similarity thresholds too stringent.
  - Disk thrashing: Block size B not aligned with OS page size; monitor disk I/O patterns.
- **First 3 experiments**:
  1. Exact search benchmark: Compare p95 latency vs. infini‑gram on FineWeb‑Edu at multiple corpus sizes (Fig 3); verify ~33× speedup.
  2. Soft search scalability: Measure p95 latency across languages (EN, JA, ZH) and corpus sizes (100 M to 1 T tokens); confirm sub‑400 ms at trillion scale (Fig 4).
  3. Ablation study: Disable iterative, k‑gram, and last‑bits pruning individually; measure exact lookup counts (Fig 5) and latency impact (Fig 15) to quantify pruning contribution.

## Limitations
- Query length assumption: mechanisms assume queries ≤12 tokens; longer queries may break disk‑aware index (multiple seeks) and overwhelm pruning.
- Zipfian pruning dependency: critically relies on power‑law n‑gram distribution; unverified on corpora with different statistics (e.g., technical, synthetic, code).
- Embedding space alignment: assumes pre‑trained embeddings align with corpus semantics and norms correlate with informativeness; domain mismatch may harm recall.

## Confidence
- Exact search speed (0.34 ms p95): **High**
- Soft search scalability (278 ms p95): **Medium**
- Pruning effectiveness (2.27× growth per token): **Medium**
- Contamination detection utility (81% precision): **Medium**
- Embedding‑based similarity formulation: **Low‑Medium**

## Next Checks
1. **Stress‑test disk access for longer queries**: Run exact search on FineWeb‑Edu with artificially concatenated queries (12–32 tokens), instrument disk I/O (e.g., `blktrace`), and measure average seeks per query. Expectation: Seeks remain ~1 for ≤12 tokens but rise logarithmically beyond if block size `B` is exceeded.
2. **Evaluate pruning on non‑Zipfian corpora**: Construct a controlled corpus with uniform n‑gram frequencies over the same vocabulary. Run soft search with identical settings and compare candidate explosion rate and latency vs. FineWeb‑Edu. Expectation: Latency and candidate growth increase sharply if Zipf’s law is violated.
3. **Test embedding corpus mismatch**: Run contamination detection on a domain‑specific corpus (e.g., PubMed abstracts) using standard GloVe embeddings (trained on Common Crawl). Compare precision/recall of soft matches against a domain‑adapted embedding (e.g., BioWordVec). Expectation: Standard embeddings yield lower precision due to semantic misalignment.
