# The Million-Label NER: Breaking Scale Barriers with GLiNER bi-encoder

## Quick Facts
- arXiv ID: 2602.18487
- Source URL: https://arxiv.org/abs/2602.18487
- Reference count: 3
- Primary result: A bi-encoder architecture for NER that scales to millions of entity types, achieving 130× throughput improvement and 61.5% zero-shot Micro-F1 on CrossNER.

## Executive Summary
GLiNER introduces a bi-encoder design for Named Entity Recognition that decouples the processing of input text and entity type labels. This separation enables precomputation of label embeddings, eliminating the quadratic scaling bottleneck of joint encoding and making inference cost nearly independent of the number of labels. As a result, the model can handle millions of entity types efficiently—up to 130× faster on an H100 GPU compared to uni-encoder approaches—while maintaining competitive accuracy, achieving state-of-the-art zero-shot performance on CrossNER (61.5% Micro-F1). The architecture also supports heterogeneous encoder pairing and optional cross-attention fusion, offering a flexible trade-off between speed and representational richness.

## Method Summary
The proposed bi-encoder uses separate transformers: a text encoder (e.g., ModernBERT) processes the input sequence to produce contextual token embeddings, from which candidate span representations are extracted via start and end MLPs (with a maximum width K). Independently, a label encoder (e.g., BGE or MiniLM) encodes each entity type description into a fixed-dimensional embedding. During offline preparation, all label embeddings are computed once and indexed using an approximate nearest neighbor (ANN) library like FAISS. At inference, the text encoder runs per input, span embeddings are matched against the precomputed label index via fast similarity search, and top-k labels are assigned based on dot-product similarity. Optionally, a bidirectional cross-attention module (CrossFuser) can be inserted after the separate encodings to allow limited cross-modal interactions. The model is trained with a focal loss and negative sampling, using a two-stage procedure: first pre-training on a large web-derived dataset (8–10M samples) and then post-training on 40k annotated examples. This design enables efficient zero-shot NER with millions of types while preserving accuracy.

## Key Results
- Throughput improves up to 130× at 1,024 labels on an H100 GPU, scaling near-constantly with label count when using precomputed embeddings and ANN retrieval.
- Achieves state-of-the-art zero-shot NER performance with 61.5% Micro-F1 on the CrossNER benchmark.
- Matches the accuracy of uni-encoder models despite the architectural separation, demonstrating that decoupling does not sacrifice quality.

## Why This Works (Mechanism)
### Mechanism 1: Decoupling and Precomputation
The bi-encoder splits the workload: the text encoder handles the input sequence and produces span representations, while the label encoder independently generates embeddings for entity type descriptions. During offline preparation, all label embeddings are computed once and stored in an ANN index (e.g., FAISS). At inference, only the text encoder runs per input; span embeddings are then matched against the precomputed label index via fast similarity search. This removes the quadratic scaling of joint encoding (which requires scoring all labels for each span) and makes inference cost nearly independent of label count. The core assumption is that entity type semantics are stable and can be captured by a single embedding compatible across contexts. If entity types require dynamic contextualization or if label definitions change frequently, the static precomputation approach may fail or incur recomputation overhead.

### Mechanism 2: Optional Cross-Attention Fusion
To inject limited cross-modal interactions without full joint encoding, the architecture can include a bidirectional cross-attention module (CrossFuser) after the separate encodings. This module allows each label embedding to attend to relevant span features and vice versa, updating both representations before scoring. Because fusion is applied once and only over the set of candidate spans (not all labels), its computational cost does not necessarily scale with the total number of labels, offering a tunable trade-off between efficiency and representational richness. The underlying assumption is that most necessary alignment between text and labels can be captured by a shallow cross-attention layer, avoiding the need for full joint encoding. However, for extremely large label sets, even a single cross-attention pass could reintroduce quadratic complexity if implemented naively, and the added latency may not justify accuracy gains in real-time scenarios.

### Mechanism 3: Heterogeneous Encoder Pairing
The bi-encoder achieves accuracy parity with joint encoding by pairing a text encoder optimized for contextual understanding (e.g., ModernBERT) with a label encoder optimized for semantic similarity (e.g., BGE, MiniLM). The label encoder maps entity type descriptions into the same vector space as the text encoder's span embeddings. Joint fine-tuning aligns these spaces so that dot products between corresponding embeddings become reliable compatibility scores. The core assumption is that the two encoders' vector spaces can be effectively aligned through training. Mismatched dimensions, lack of joint fine-tuning, or an unsuitable label encoder (e.g., one not pre-trained on similarity tasks) can break this alignment and degrade performance.

## Foundational Learning
- **Named Entity Recognition (NER)**: The core task; zero-shot NER requires predicting entity types unseen during training, highlighting the need for flexible type representations. Quick check: "In zero-shot NER, how does a model determine entity types it has never been trained on?"
- **Quadratic complexity of self-attention**: Self-attention in transformers has O(n²) cost relative to sequence length; joint encoding multiplies this by the number of labels, creating a scalability bottleneck. Quick check: "If you double the number of tokens in a transformer's input, how does the computational complexity of self-attention change, assuming constant head dimension?"
- **Precomputation and approximate nearest neighbor search**: Precomputing label embeddings and using ANN indices reduces per-input cost from O(L) to near-constant, enabling scaling to large label sets. Quick check: "Why does precomputing label embeddings reduce per-input computational burden, and what role does an approximate nearest neighbor index play?"

## Architecture Onboarding
**Component map**: Input text → Tokenizer → tokens → Text Encoder (e.g., ModernBERT) → contextual token embeddings → Span builder (MLP_start, MLP_end) → candidate span representations (max width K) → (Optional CrossFuser) → Scoring: dot product with label embeddings (precomputed via Label Encoder, e.g., BGE) → logits → Thresholding & greedy decoding → final entities. Training uses focal loss and negative sampling.

**Critical path**:
1. Tokenize input.
2. Encode tokens through text encoder.
3. Extract span representations via start/end MLPs.
4. If enabled, apply cross-fusion to update spans/labels.
5. Query label embedding index (ANN) for top-k similar labels per span.
6. Apply confidence threshold.
7. Resolve overlapping spans greedily.

**Design tradeoffs**:
- Accuracy vs speed: Disabling cross-fusion and using smaller encoders increases throughput but may lower F1.
- Span width K: Larger K captures longer entities but increases candidate spans, affecting latency.
- Label encoder choice: Sentence-transformers improve semantic fidelity but require dimension matching.
- Precomputation vs freshness: Caching speeds up inference but introduces stale embeddings if label definitions change.
- Token-level vs span-level: Token-level is faster but requires BIO post-processing; span-level is more direct.

**Failure signatures**:
- Low recall on entities longer than K tokens → K too small.
- Throughput degrades as label count grows → label index missing or not using ANN.
- Memory spikes when loading label index → index too large for GPU; offload to CPU or shard.
- Many overlapping predictions → threshold too low or greedy selection misconfigured.
- Low CrossNER F1 despite large model → misaligned encoders or missing joint fine-tuning.
- OOM during fusion → cross-attention memory scales with spans × labels; reduce batch size.

**First 3 experiments**:
1. **Precomputation and ANN retrieval test**: Precompute label embeddings for counts (100, 1k, 10k) and build FAISS index. Measure latency per input with ANN vs brute-force dot product; expect near-constant latency across label counts with ANN.
2. **Accuracy baseline**: Evaluate bi-encoder (no fusion) on CrossNER; confirm Micro-F1 matches reported numbers (~61.5% large, ~60.3% base) within ±1%.
3. **Scalability stress test**: With fixed text length (256 tokens), vary label count from 1 to 1024 and record throughput. With precomputed index, throughput should decrease by <10%; without precomputation, it should drop >90%.

## Open Questions the Paper Calls Out
**Open Question 1**: Why does the bi-encoder architecture struggle with highly contextual datasets like HarveyNER and FabNER despite scaling improvements on biomedical benchmarks?  
Basis: Section 4.6 notes "performance on highly contextual datasets remains challenging" with HarveyNER (10.6–15.0%) and FabNER (22.4–24.3%) showing limited gains. The paper attributes this to entities whose boundaries depend on surrounding context but does not isolate whether this is due to architectural limits (lack of joint encoding) or dataset characteristics. No ablation studies test this hypothesis. Resolution would require controlled experiments varying contextual dependency or error analyses comparing span boundaries and label confusions across dataset types.

**Open Question 2**: How can the fixed maximum span width constraint (K=12) be overcome for domains with longer entity mentions, such as legal or scientific texts?  
Basis: Section 4.6 states the "fixed maximum span width constraint (K=12) limits recognition of longer entity mentions" and mentions a token-level variant but does not evaluate it. The token-level alternative is proposed but not empirically tested; it is unclear if it matches span-level accuracy or introduces new issues (e.g., BIO tagging errors on long mentions). Resolution would require evaluating the token-level bi-encoder on datasets with known long entities, comparing F1, span extraction accuracy, and computational cost against the span-level approach.

**Open Question 3**: Under what conditions does the optional cross-attention fusion layer provide meaningful accuracy gains that justify its computational overhead?  
Basis: Section 4.6 calls for a "systematic study of when and to what extent cross-modal interaction benefits different domains," noting fusion is currently unevaluated in primary experiments. The paper discusses fusion as a tunable trade-off but presents no results comparing fused vs. unfused models across domains. Resolution would require benchmarking fused bi-encoder variants (with varying fusion depth and attention heads) across diverse datasets, measuring accuracy improvements relative to latency penalties, and identifying dataset characteristics that predict fusion benefits.

**Open Question 4**: Can contrastive pre-training objectives specifically designed for bi-encoder NER improve label-text alignment and zero-shot generalization?  
Basis: Section 4.6 suggests "Contrastive pre-training objectives specifically designed for the bi-encoder NER setting may improve label-text alignment" as a future direction. Models are currently trained with focal loss on NER tokens; contrastive objectives (e.g., infoNCE) remain unexplored. It is unknown if such objectives would enhance semantic matching for unseen entity types. Resolution would involve pre-training bi-encoder models with contrastive losses on large corpora, then evaluating zero-shot NER performance on benchmarks like CrossNER, particularly for rare or descriptively defined entity types.

**Open Question 5**: Can retrieval-augmented approaches scale to millions of entity types by dynamically filtering relevant labels, and what is the accuracy–efficiency trade-off?  
Basis: Section 4.6 proposes "integration with retrieval-augmented approaches could enable even larger label vocabularies by dynamically retrieving relevant entity types rather than scoring against all candidates." The current bi-encoder precomputes all label embeddings, which may still be inefficient for ultra-large KBs (e.g., UMLS with 4M+ concepts). Retrieval could reduce computation but risks missing relevant labels; the trade-off is unmeasured. Resolution would involve implementing a two-stage pipeline: fast retrieval (e.g., embedding-based ANN) to select top-K candidate labels per input, then bi-encoder scoring on this subset, and evaluating accuracy vs. latency on synthetic or subsets of million-scale KBs.

## Limitations
- Evaluation only up to 1,024 labels; the claimed million-scale efficiency lacks empirical validation.
- Static label embeddings may fail for context-sensitive entity types that require dynamic contextualization.
- Cross-attention design specifics (number of layers, heads) are not disclosed, hindering reproducibility and scalability analysis.

## Confidence
- **Decoupling removes quadratic bottleneck**: Medium
- **SOTA zero-shot NER (61.5% on CrossNER)**: Medium
- **130× throughput improvement at 1,024 labels**: High
