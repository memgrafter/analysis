# DyACE: Dynamic Algorithm Co-evolution for Online Automated Heuristic Design with Large Language Model

## Quick Facts
- **arXiv ID:** 2603.13344
- **Source URL:** https://arxiv.org/abs/2603.13344
- **Reference count:** 25
- **Primary result:** DyACE significantly outperforms state-of-the-art static LLM-based baselines (FunSearch, EoH, ReEvo) on JSSP, TSP, and CVRP benchmarks, with notable improvements on large instances (e.g., 11.13% gap on TA71 vs. 17.40–26.39%).

## Executive Summary
DyACE addresses the limitation of static algorithm design in Automated Heuristic Design (AHD) by reformulating the problem as a Non-stationary Bi-level Control Problem. It uses a Receding Horizon Control architecture combined with Look-Ahead Rollout Search to extract real-time Search Trajectory Features that diagnose the current search landscape. An LLM meta-controller then dynamically co-evolves heuristic logic alongside the solution population, enabling phase-specific adaptations. Empirical evaluations on Job Shop Scheduling, Traveling Salesman, and Capacitated Vehicle Routing benchmarks demonstrate substantial performance gains over static methods, especially on large-scale instances where DyACE reduces optimality gaps by up to 6 percentage points. Ablation studies confirm that the integration of look-ahead perception and continuous co-evolution is essential for its effectiveness.

## Method Summary
DyACE targets the automated design of perturbative heuristics (e.g., crossover, mutation, local search) for combinatorial optimization problems. It operates under a unified computational budget of 300 algorithm evaluations. The core loop iterates over 30 algorithm generations; each step observes the current solution population \(P_t\) and performs a short Look-Ahead Rollout (probe horizon \(\tau=30\)) to extract two feature streams: Landscape Kinematics (fitness velocity, acceleration, diversity loss) and Operator Telemetry (precision, impact). These form the state vector \(s_t\), which is fed to a two-stage LLM meta-controller: a Diagnosis Agent first produces a natural language "Verbal Gradient" explaining the search status, and a Coding Agent then synthesizes a new heuristic operator (crossover, mutation, or local search) using one of three genetic modes (Combine, Mutate, Explore). The new operator is applied to the population for a fixed horizon \(H=5\) solution generations, producing \(P_{t+H}\). Algorithms are scored by Iso-State Rollout Evaluation (averaging gap over Monte Carlo rollouts) to guide parent selection. Baselines include offline-evolved static algorithms (FunSearch, EoH, ReEvo) that are frozen after a full evolution phase and applied unchanged for 150 solution generations.

## Key Results
- On the Taillard JSSP benchmark, DyACE achieves an average optimality gap of 14.73%, outperforming ReEvo’s 19.38% by 4.65 percentage points.
- On the large-scale TA71 instance (100 jobs × 20 machines), DyACE attains a gap of 11.13%, while static LLM baselines range from 17.40% to 26.39%.
- Across all tested domains (JSSP, TSP, CVRP), DyACE consistently yields significantly lower optimality gaps than state-of-the-art static approaches.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** DyACE continuously adapts the heuristic logic to the current search phase via a Receding Horizon Control architecture, replacing a single static algorithm with a time-variant policy.
- **Mechanism:** The upper-level problem is reformulated from optimizing a fixed code \(c^*\) to learning a meta-control policy \(\pi: S \rightarrow \Omega\). At each decision step \(t\), the current population state \(P_t\) is observed, a new operator \(h_t = \pi(\psi(P_t))\) is synthesized, and applied for a limited horizon \(H\). This creates a closed loop where algorithmic logic evolves alongside the solution population.
- **Core assumption:** The optimal perturbation strategy is non-stationary; early-stage exploration requires different operators than late-stage exploitation.
- **Evidence anchors:** Abstract: "DyACE use a Receding Horizon Control architecture to continuously co-evolve the heuristic logic alongside the solution population." Section 2.3: "We redefined AHD as a Non-stationary Bi-level Control Problem... we aim to synthesize a dynamic meta-control policy \(\pi\) that adapts the heuristic operator to the real-time evolutionary state."

### Mechanism 2
- **Claim:** Look-Ahead Rollout Search provides grounded perception by extracting causal Search Trajectory Features from short-term simulated rollouts, enabling the LLM to diagnose landscape dynamics.
- **Mechanism:** Parallel shadow rollouts from current \(P_t\) for a probe horizon \(\tau\) generate trajectories. From these, two feature streams are extracted: 1) *Landscape Kinematics* (velocity, acceleration, diversity loss rate of fitness trajectory) to infer local geometry, and 2) *Operator Telemetry* (precision, impact) to attribute causality. These features form the state vector \(s_t\) for meta-reasoning.
- **Core assumption:** Short-horizon rollout features are predictive proxies for longer-term trajectory potential and reveal the current phase (exploration vs. exploitation).
- **Evidence anchors:** Abstract: "Look-Ahead Rollout Search, which queries the landscape geometry to extract Search Trajectory Features." Section 3.2: "To diagnose the optimization status, this process summarizes the raw search trajectories into a compact vector of Search Trajectory Features... capture the search dynamics through two aspects: Landscape Kinematics... Operator Telemetry."

### Mechanism 3
- **Claim:** Decoupled Meta-Reasoning with a Diagnosis-Coding separation and three reasoning modes ensures the LLM synthesizes phase-specific, causally aligned algorithmic interventions rather than hallucinating code.
- **Mechanism:** The LLM meta-controller operates in two stages: 1) *Diagnosis Agent* analyzes \(s_t\) and outputs natural language "Verbal Gradients" (e.g., "Single-block crossover limits mixing; refactor to Two-Point Crossover"). No code is generated. 2) *Coding Agent* uses the gradient to synthesize code for a new operator \(h_t\). Three modes (*Combine*, *Mutate*, *Explore*) govern the genetic operation on the algorithm population, providing structured novelty.
- **Core assumption:** Separating analysis (gradient extraction) from code generation improves reliability and aligns the synthesized logic with the verified search dynamics (\(s_t\)).
- **Evidence anchors:** Abstract: "This sensory feedback allows the Large Language Model (LLM) to function as a grounded meta-controller, prescribing phase-specific interventions tailored to the real-time search status." Section 3.3: "We break the meta-reasoning process into two sequential steps to ensure a 'Think-then-Code' approach... This step ensures the system understands why the search is stuck before deciding how to fix it."

## Foundational Learning

- **Perturbative Heuristics**  
  *Why needed:* DyACE designs operators that perturb complete solutions (crossover, mutation, local search). Understanding population dynamics and operator effects is essential to interpret search trajectory features.  
  *Quick check:* How does a crossover operator's effect on population diversity differ from its effect on solution quality in a converging vs. stagnating search?

- **Non-Stationary Optimization / Receding Horizon Control**  
  *Why needed:* The framework reformulates AHD as a dynamic control problem; a static policy is insufficient when the search landscape shifts over time. Receding horizon re-planning addresses non-stationarity.  
  *Quick check:* Why is evaluating an algorithm over a full 150-generation rollout insufficient for guiding its adaptation during a 150-generation search?

- **LLM as a Stochastic Program Synthesizer with constrained reasoning modes**  
  *Why needed:* The LLM must generate executable, semantically coherent code from natural language gradients while adhering to structured modes (Combine, Mutate, Explore).  
  *Quick check:* What is the risk of the `Combine` mode simply concatenating parent code instead of merging logic, and how does the prompt mitigate this?

## Architecture Onboarding

### Component Map
Look-Ahead Rollout Search (extracts features) → Decoupled Meta-Reasoning (Diagnosis Agent → Coding Agent) → new operator → Receding Horizon Evolution (applies to solution population) → updates population state; the Algorithm Population stores and selects parent operators based on Iso-State Rollout Evaluation scores.

### Critical Path
Current \(P_t\) → Look-Ahead Rollout → state vector \(s_t\) → Diagnosis Agent → Verbal Gradient → Coding Agent → new operator \(h_t\) → Receding Horizon Evolution (apply for \(H=5\) gens) → new \(P_{t+H}\) → loop.

### Design Tradeoffs
- Look-ahead horizon \(\tau\) vs. computational cost: Larger \(\tau\) yields more reliable features but increases per-step overhead (paper uses \(\tau=30\) vs. full 150).
- Algorithm population size \(M\) vs. adaptation speed: Smaller \(M=5\) allows more meta-updates within budget \(B=300\) but reduces operator diversity.
- Decoupling (two-stage LLM) vs. latency: Increases inference time per generation but improves code quality and alignment.

### Failure Signatures
- Stagnant algorithm gap: Meta-controller fails to improve operators (DyACE-Blind scenario); likely noisy features or mis-specified gradients.
- Rapid performance collapse after meta-update: New operator invalid or misaligned; check Coding Agent output validity and gradient logic.
- High variance in algorithm scores \(J(h_k)\): Rollout evaluations too stochastic; increase Monte Carlo runs or \(\tau\).

### First 3 Experiments
1. **Replicate Ablation:** Run `DyACE-Blind` (remove feature extractor) and `DyACE-Static` (remove receding loop) on a single JSSP instance (e.g., TA21). Confirm `DyACE-Blind` underperforms static baselines, validating the need for grounded perception.
2. **Component Isolation Test:** On a small TSP instance (e.g., `eli51`), freeze the algorithm population after the first generation and apply the same operator for all subsequent solution steps. Compare to full DyACE to isolate continuous co-evolution’s value.
3. **Feature Sanity Check:** Log Search Trajectory Features during a run. Manually verify that "diversity loss rate" increases during convergence and "operator precision" drops during stagnation, ensuring features capture expected dynamics.

## Open Questions the Paper Calls Out

1. **How can the inference latency of the DyACE meta-controller be reduced for real-time deployment?**  
   The main bottleneck is the time cost of the meta-controller. Exploring a hierarchical structure (smaller models for frequent adjustments, large models for major changes) could lower latency.

2. **Can verbal gradients and algorithmic trajectories learned by DyACE be transferred across problem domains to reduce instance-specific computation?**  
   The natural language representation of Verbal Gradients offers a unique medium for cross-domain transfer. Storing insights from multiple domains could create a generalist agent that avoids learning from scratch.

3. **Can the sequence of evolved algorithms (trajectory) be automatically analyzed to extract human-readable design principles or mathematical conjectures about problem structure?**  
   Explicitly analyzing these trajectories may lead to automated scientific discovery, using secondary LLM agents to distill patterns into principles or conjectures.

## Limitations
- Critical hyperparameters for solution evolution (selection pressure, mutation rates) are not detailed, hindering exact replication.
- Exact Look-Ahead Rollout settings (number of Monte Carlo rollouts, feature normalization) are unspecified.
- Evaluation is confined to three combinatorial domains (JSSP, TSP, CVRP); generalization to other problem classes remains unknown.
- High computational overhead from frequent look-ahead rollouts may limit scalability to very large populations or instances.
