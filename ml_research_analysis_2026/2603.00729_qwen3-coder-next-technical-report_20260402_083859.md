# Qwen3-Coder-Next Technical Report

## Quick Facts
- arXiv ID: 2603.00729
- Source URL: https://arxiv.org/abs/2603.00729
- Reference count: 30
- Primary result: An 80B MoE model activating only 3B parameters achieves 70.6% on SWE-Bench Verified, competitive with much larger active models.

## Executive Summary
Qwen3-Coder-Next is an 80‑billion‑parameter Mixture‑of‑Experts (MoE) model that activates only 3 billion parameters per forward pass, enabling efficient yet powerful coding agents. Its core innovation is scaling agentic training by synthesizing millions of verifiable coding tasks paired with reproducible Docker environments, allowing the model to learn from execution feedback via mid‑training and reinforcement learning. The model also leverages extended context (262k tokens), diverse tool‑call templates, and expert distillation to unify capabilities across web development, UX, single‑turn RL, and software engineering.

On evaluation, Qwen3-Coder-Next reaches 70.6% on SWE‑Bench Verified using SWE‑Agent, competitive with DeepSeek‑V3.2 (70.2%) and GLM‑4.7 (74.2%) while using far less active compute. It also scores 62.8% on SWE‑Bench Multilingual, 42.7% on SWE‑Bench Pro, and 36.2% on Terminal‑Bench 2.0. General coding (EvalPlus 86.56) and reasoning (MMLU‑Redux 91.18) remain strong, demonstrating a favorable efficiency‑performance trade‑off for real‑world coding agents.

## Why This Works (Mechanism)
### Mechanism 1: Sparse Activation via MoE
- **Claim**: Sparse activation via Mixture‑of‑Experts (MoE) enables high‑capability coding agents with low inference cost.
- **Mechanism**: The model uses a hybrid MoE architecture with 80B total parameters but activates only ~3B per forward pass. Routing decisions presumably direct inputs to a small subset of expert layers, maintaining computational efficiency while preserving representational capacity.
- **Core assumption**: Task distribution is sufficiently specialized that a small subset of parameters can handle most coding agent queries without significant performance loss.
- **Evidence anchors**:
  - [abstract] "80‑billion‑parameter model that activates only 3 billion parameters per forward pass"
  - [section 1] "hybrid mixture‑of‑experts architecture with 80 billion total parameters and only 3 billion active parameters"

- **Break condition**: If routing becomes inefficient (e.g., many experts activated per token) or the active parameter budget is insufficient for complex repository‑level reasoning.

### Mechanism 2: Execution‑Based Agentic Training
- **Claim**: Scaling agentic training with executable environments and execution feedback yields robust multi‑step coding behavior.
- **Mechanism**: The pipeline synthesizes millions of verifiable coding tasks paired with reproducible Docker environments. Agents interact with these environments during mid‑training and reinforcement learning, receiving scalar rewards from test execution. This creates a closed loop where the model learns from real environmental outcomes (success/failure, errors, state changes) rather than static code corpora.
- **Core assumption**: Execution‑based feedback provides a dense, reliable, and scalable learning signal for complex, long‑horizon software engineering tasks.
- **Evidence anchors**:
  - [abstract] "agentic training through large‑scale synthesis of verifiable coding tasks paired with executable environments, allowing learning directly from environment feedback via mid‑training and reinforcement learning"
  - [section 2] Detailed description of task synthesis from GitHub PRs and bug injection, plus MegaFlow orchestration for parallel rollout and evaluation.
  - [corpus] Corpus evidence not directly relevant to this mechanism – based on paper sections only.
- **Break condition**: If environment construction becomes noisy (non‑functional verifiers) or agents exploit reward shortcuts (e.g., accessing future commit information) despite blockers.

### Mechanism 3: Tool Template Diversity and Expert Distillation
- **Claim**: Exposure to diverse tool‑call templates and expert distillation yields a single model that generalizes across multiple agent scaffolds and domains.
- **Mechanism**: During SFT, the model is trained on trajectories using many different XML/JSON/function‑call formats (e.g., from SWE‑agent, OpenHands, Cline). This teaches format‑invariant tool‑use semantics. Concurrently, domain experts (WebDev, UX, Single‑turn RL, Software Engineering) are trained and then distilled into one unified model, combining their strengths.
- **Core assumption**: Training on syntactic variation decouples tool semantics from surface format, and knowledge distillation can merge specialized capabilities without catastrophic forgetting.
- **Evidence anchors**:

  - [section 4.2.5] "Finally, we perform expert distillation to consolidate capabilities from multiple domain experts into a single unified deployment model"

- **Break condition**: If template diversity causes confusion (performance degrades with too many formats) or distillation overwrites key specialist knowledge.

## Architecture Onboarding
- **Component map**: Base model → Mid‑training corpus → SFT dataset → Domain experts → Unified model → Inference stack
- **Critical path**: Pretrained base → Mid‑training (exposure to long contexts & agent patterns) → SFT (alignment & verification filtering) → Expert specialization → Distillation → Deployment.
- **Design tradeoffs**:
  - Active parameter count (3B) vs. total size (80B): Lower cost but may limit complex reasoning capacity.
  - Synthetic vs. natural data balance: More synthetic improves target tasks but risks over‑specialization.
  - Single vs. multiple tool formats: Diversity improves generalization but adds training complexity.
- **Failure signatures**:
  - Reward hacking: Agent uses `git remote add` to access future commits, indicating environment leakage.
  - Tool-format errors: High rate of malformed function calls in certain scaffolds (e.g., Scaffold5 performance drop).
  - Context fragmentation: BFP needed to avoid head‑side truncation; poor packing would degrade long‑horizon tasks.
- **First 3 experiments**:
  1. MoE sparsity validation: Measure activation count distribution on coding vs. general queries; expect consistent ~3B active tokens.
  2. Environment reproducibility: Re‑run a sample of synthesized Docker tasks; check pass/fail consistency across multiple runs.
  3. Template diversity ablation: Train with 1 vs. 5 vs. 21 tool templates; evaluate cross‑scaffold generalization (e.g., SWE‑Agent → OpenHands) to confirm benefit of diversity.

## Open Questions the Paper Calls Out
1. **How can Qwen3-Coder-Next close the performance gap with frontier models on highly complex, large-scale software engineering tasks despite its smaller active compute footprint?**  
   **Basis**: The conclusion notes a gap for large‑scale tasks and plans to address by scaling exposure during pre‑training.  
   **Why unresolved**: The efficiency from sparse activation may limit capacity for long‑horizon, multi‑file reasoning.  
   **Evidence needed**: Scaling experiments with larger, more intricate codebases during mid‑training and evaluation on extended SWE‑Bench Pro.

2. **Why does cross‑scaffold transfer remain limited in agentic training, and how can generalization across different tool‑calling frameworks be improved?**  
   **Basis**: Section 3.1.2 and Figure 3 show poor transfer between scaffolds.  
   **Why unresolved**: The cause (format, action space, data distribution) is unclear.  
   **Evidence needed**: Controlled experiments mixing data from multiple scaffolds, isolating variables like tool‑call format, action space, task distribution.

3. **Can the heuristic reward‑hacking blocker be replaced with a more principled approach that prevents exploitation while maintaining legitimate tool usage?**  
   **Basis**: Section 4.2.4 describes a heuristic rule blocking tool calls with repository links and network‑access keywords.  
   **Why unresolved**: Heuristics may block valid operations and could be bypassed.  
   **Evidence needed**: Formal model of reward‑hacking vectors and a dynamic detector that adapts without false positives.

4. **What is the mechanism by which diverse tool chat templates improve robustness to unseen formats—does it teach format invariance or simply increase data diversity?**  
   **Basis**: Figure 5 shows gains with more templates, but the cause is not disentangled.  
   **Why unresolved**: Without ablations controlling semantics while varying format, the contributor is unknown.  
   **Evidence needed**: Train with templates preserving semantics but varying only syntax (JSON vs XML) and test on new formats.

5. **How can frontend and UI coding capabilities be enhanced in coding agents, given the current model's limitations?**  
   **Basis**: Limitations section identifies frontend/UI as an area for improvement; future work includes integrating visual capability.  
   **Why unresolved**: Current training lacks visual feedback; relies on textual descriptions.  
   **Evidence needed**: Incorporate vision‑language models to evaluate screenshots or interactive behavior, with benchmarks requiring visual correctness.

## Limitations
- **MoE routing efficiency**: Unclear if routing is stable across query types; potential load imbalance among experts.
- **Synthetic task fidelity**: Noise in automatic verifiers may propagate misaligned rewards; false‑positive/negative rates unanalyzed.
- **Tool‑format generalization**: It remains unknown whether the model learns abstract tool semantics or memorizes template patterns.

## Confidence
- **MoE sparsity claim**: High
- **Agentic training efficacy**: Medium
- **Tool‑diversity & distillation benefit**: Low

## Next Checks
1. Activation pattern analysis: Run a diverse query set (coding, reasoning, general chat); measure per‑expert activation frequency, load imbalance, and active parameter count deviation from 3B; expect stable ~3B activation with low variance.
2. Environment reproducibility test: Re‑execute a random sample (e.g., 100) of the synthesized Docker tasks across multiple runs; compute pass/fail consistency; target >99% reproducibility to validate verifier reliability.
3. Template diversity ablation: Retrain a smaller control model with identical data but a single tool‑call format (e.g., only JSON); evaluate cross‑scaffold generalization (SWE‑Agent → OpenHands); expect significant drop (>5 points) in scaffold‑transfer performance, confirming format diversity as a key factor.
