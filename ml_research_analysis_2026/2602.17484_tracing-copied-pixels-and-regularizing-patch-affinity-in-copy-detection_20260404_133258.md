# Tracing Copied Pixels and Regularizing Patch Affinity in Copy Detection

## Quick Facts
- arXiv ID: 2602.17484  
- Source URL: https://arxiv.org/abs/2602.17484  
- Reference count: 40  
- Primary result: SOTA on DISC21 – matcher 88.7% µAP / 83.9% RP90; descriptor 72.6% µAP / 68.4% RP90  

## Executive Summary
The paper tackles insufficient fine‑grained correspondence in self‑supervised image copy detection. It introduces **PixTrace**, a pixel coordinate tracking module that maintains explicit spatial mappings through editing transformations, and **CopyNCE**, a contrastive loss that uses overlap ratios derived from PixTrace to regularize patch affinity. Integrated into a Vision Transformer framework, the method yields state‑of‑the‑art results on the DISC21 benchmark, with notable gains in robustness to complex edits and improved interpretability.

## Method Summary
PixTrace maintains a coordinate table that maps pixels in an edited image back to the original image via known transformation functions, enabling precise spatial correspondences between copies. CopyNCE converts these correspondences into per‑patch overlap ratios, which serve as a soft, multi‑positive target distribution in a contrastive loss. The system uses a ViT backbone: for the descriptor, global `[CLS]` tokens are trained with InfoNCE and KoLeo while intermediate patch tokens are supervised by CopyNCE; for the matcher, dual ViT encoders with cross‑attention fusion produce a binary classification, with fused tokens also regularized by CopyNCE. Training combines the baseline loss with the CopyNCE term, and inference employs descriptor‑based candidate retrieval followed by matcher re‑ranking with local crops ensembling.

## Key Results
- **Matcher:** 88.7% µAP, 83.9% RP90 on DISC21.  
- **Descriptor:** 72.6% µAP, 68.4% RP90 on DISC21.  
- Significant improvements over heuristic baselines (LocNN, FeatNN) and enhanced interpretability via spatial mappings.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** PixTrace maintains explicit, traceable pixel coordinate mappings across a sequence of editing transformations, converting geometric edits into deterministic spatial correspondences.  
- **Mechanism:** It initializes a coordinate table `T` where each pixel maps to itself. For each edit operation (e.g., affine, image matting), a known coordinate transform function `f` is applied to update all values in `T`. Reverse operation `T⁻¹` is supported via key‑value swap. This creates a pairwise mapping table between the edited copy and the original image (or between two copies via a shared original).  
- **Core assumption:** Editing operations applied during self‑supervised training are based on known, invertible (or at least trackable) transform functions (e.g., geometric warps, matting masks).  
- **Evidence anchors:**
  - [abstract] "pixel coordinate tracking module that maintains explicit spatial mappings through editing transformations."
  - [section 3.2] Detailed definition of the coordinate table `T` and its operations (update via `F(T)`, reversal).
  - [corpus] Limited direct corpus evidence; neighboring papers focus on different paradigms (in‑context learning, video datasets, damage detection).  
- **Break condition:** The mechanism fails for edits where the pixel‑level transformation is stochastic, non‑invertible, or not modeled by an available function `f` (e.g., complex generative inpainting, arbitrary content‑aware fills).

### Mechanism 2
- **Claim:** CopyNCE uses geometrically‑verified overlap ratios from PixTrace's mappings as a soft, multi‑positive target distribution to regularize patch‑level affinity, reducing noise from false or partial matches in contrastive learning.  
- **Mechanism:** For a query patch `R_q_i`, it computes the proportion of its pixels that map to each reference patch `R_r_j` using the coordinate table (`Eq. 4`). This proportion `q(R_r_j | R_q_i)` is sharpened by `γ` to form a target distribution. The loss then minimizes the KL divergence between this target and the model's predicted patch affinity distribution (`Eq. 6`), encouraging the model to assign higher similarity to patches with larger overlapping copied regions.  
- **Core assumption:** The overlap ratio between patches is a valid and discriminative prior for identifying copy relationships, superseding binary positive/negative labels.  
- **Evidence anchors:**
  - [abstract] "regularizes patch affinity using overlap ratios derived from PixTrace's verified mappings."
  - [section 3.3] Full derivation from InfoNCE to CopyNCE, definition of `q(R_r_j | R_q_i)`, and the symmetric loss form.
  - [corpus] Neighbors discuss contrastive learning and affinity but not with pixel‑derived overlap priors; evidence is weak.  
- **Break condition:** If PixTrace's mappings are inaccurate (e.g., due to unmodeled edits), the computed overlap ratios become noisy, potentially harming more than helping learning.

### Mechanism 3
- **Claim:** Integrating pixel‑level traceability (PixTrace) into a patch‑level contrastive framework (CopyNCE) within a self‑supervised learning pipeline suppresses supervision noise from non‑corresponding regions, enabling more robust feature learning for sophisticated edits.  
- **Mechanism:** Standard self‑supervised view‑level contrastive learning neglects fine‑grained correspondence. By adding CopyNCE as an auxiliary loss on mid‑level patch tokens (e.g., 12th layer of ViT), the model is explicitly guided to align features of patches that share a copied region, as defined by the ground‑truth pixel mapping. This provides a cleaner learning signal than heuristic nearest‑neighbor matching.  
- **Core assumption:** Enhancing SSL with pixel‑accurate, region‑aware supervision at the patch level improves the model's ability to discriminate edited copies, especially for partial and non‑rigid transformations.  
- **Evidence anchors:**
  - [abstract] "bridges pixel‑level traceability with patch‑level similarity learning, suppressing supervision noise in SSL training."
  - [section 2.2] Critique of heuristic local SSL methods (FeatNN, LocNN) for false/partial matches.
  - [section 4.4] Ablation studies show CopyNCE significantly outperforms FeatNN/LocNN baselines and that NCE loss with PixTrace supervision is more effective than cosine loss.
  - [corpus] Neighbors explore local feature learning but not with explicit coordinate tracking; evidence is indirect.  
- **Break condition:** The benefit diminishes if the base SSL model already learns strong local descriptors (e.g., from different pretraining) or if the edit types in training strongly mismatch those in evaluation.

## Foundational Learning
- **Concept: Self‑Supervised Learning (SSL) via Contrastive Learning**  
  *Why needed here:* The entire framework builds upon a standard SSL pretraining paradigm (e.g., DINO) where images are augmented to create "positive" pairs. CopyNCE is an auxiliary loss injected into this pipeline.  
  *Quick check question:* How does a standard contrastive loss (InfoNCE) differ from CopyNCE in terms of its treatment of positive samples within a reference image?

- **Concept: Vision Transformer (ViT) Token Structure**  
  *Why needed here:* Both descriptor and matcher use ViT architectures. CopyNCE operates on patch tokens. Understanding the sequence of tokens (patch tokens + `[CLS]` token) and layer‑wise feature extraction is critical for placing the loss correctly.  
  *Quick check question:* In a ViT, what is the spatial correspondence between a patch token and the input image? How does this relate to PixTrace's coordinate table?

- **Concept: Spatial Transformation Functions**  
  *Why needed here:* PixTrace's operation depends on known mathematical functions (`f`) that describe how coordinates transform under each edit (e.g., affine matrix, homography, alpha matte). These functions must be available during training.  
  *Quick check question:* For an affine transformation (rotation + translation + scaling), how would you write the function `f` that maps original pixel `(x, y)` to new coordinates?

## Architecture Onboarding
- **Component map:**
  1. **Data Pipeline:** Original image `I_o` → sequential edits → `I_a`, `I_b`. Each edit has an associated `f`.  
  2. **PixTrace Module:** Maintains `T_ao` and `T_bo` (and reverses). Used **offline** during batch preparation to compute per‑patch overlap ratios `q(R_r_j | R_q_i)`.  
  3. **Model Backbone:** ViT‑S/16 for both descriptor and matcher.  
  4. **Descriptor Head:** `[CLS]` token for global image feature (trained with InfoNCE + KoLeo). Final layer patch tokens supervised by CopyNCE.  
  5. **Matcher Architecture:** Dual ViT encoders (shared weights) → concatenated tokens → fusion layers (cross‑attention) → `[CLS]` token for binary prediction (BCE loss). Mid‑layer tokens from fusion module supervised by CopyNCE.  
  6. **Loss Function:** `L_total = L_baseline + w_NCE * L_CopyNCE`.

- **Critical path:**
  1. **Training Start:** Precompute/online‑compute coordinate tables `T` for each synthetic copy pair using known edit functions.  
  2. **Forward Pass:** Pass query/reference images through ViT(s) to get patch tokens at the designated layer (e.g., layer 12).  
  3. **Overlap Calculation:** Using `T_qr`, compute target distribution `q(R_r_j | R_q_i)` for all overlapping patch pairs.  
  4. **Loss Computation:** Calculate `L_CopyNCE` (Eq. 6) between query patch tokens and all reference patch tokens, using the precomputed `q` as target.  
  5. **Backward Pass:** Combine with baseline loss (`L_des` or `L_mat`) and backpropagate.

- **Design tradeoffs:**
  - **PixTrace Overhead:** Maintaining and reversing large coordinate tables (224×224) adds CPU/GPU memory and computation during data loading. This is a key bottleneck.
  - **Loss Placement (`w_NCE`, layer):** CopyNCE is added at an intermediate layer (default 12th). Too early/late may not align with features capable of fine‑grained discrimination. `w_NCE` balances baseline vs. fine‑grained objectives.
  - **`γ` Parameter:** Controls sharpness of target distribution. `γ=1` is proportional to overlap. Higher `γ` focuses on highest‑overlap patch; lower distributes weight. Tradeoff between emphasizing the most certain positive and encouraging global agreement.
  - **Matcher vs. Descriptor:** Matcher uses cross‑attention fusion, enabling detailed patch comparison but is 260× slower with Local Crops Ensembling (LCE). Descriptor is efficient for retrieval but may miss small copy regions.

- **Failure signatures:**
  - **Small Copy Regions:** Descriptor's global `[CLS]` token may not aggregate enough signal from a tiny edited patch, leading to low scores. Matcher with LCE can recover but is computationally expensive.
  - **Unseen/Complex Edits:** Performance drops on aggressive, non‑differentiable edits (e.g., as in AnyPattern test set) not represented in the training transform suite, indicating limited generalization of the `f` functions.
  - **Matting/Non‑Rigid Edits:** While PixTrace handles image matting if an alpha mask is provided, complex warps or deformations without a clean transform function will break the coordinate tracking.
  - **Feature Collapse with `w/o NCE`:** Using only cosine loss with PixTrace targets leads to trivial solutions where all patch tokens become identical, as noted in ablation studies.

- **First 3 experiments:**
  1. **Validate PixTrace Mapping Accuracy:** For a synthetic pair `(I_o, I_a)` generated with known edits, visualize `T_ao`. Pick a pixel in `I_a`, use `T_ao` to find its location in `I_o`, and verify it matches the ground‑truth warp. Test with affine, perspective, and matting.
  2. **Isolate CopyNCE Effect:** Train a descriptor (ViT‑S) with *only* the baseline loss (InfoNCE+KoLeo) vs. adding CopyNCE. Keep all else (augmentations, pretraining) identical. Evaluate µAP/RP90 on a DISC21 *dev set* subset. Expect significant gain from CopyNCE.
  3. **Heuristic Baseline Comparison:** Implement LocNN (centroid k‑NN) and FeatNN (feature k‑NN) positive pair selectors. Train with NCE loss using these instead of PixTrace/CopyNCE. Compare results to the published ablation table (Tab. 2 for descriptor, Tab. 3 for matcher). Expect CopyNCE to outperform.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can we establish reliable pixel‑wise correspondences between edited image pairs and effectively integrate this geometric awareness into SSL frameworks to enhance ICD robustness?  
- **Basis in paper:** [explicit] The introduction explicitly states: "How can we establish reliable pixel‑wise correspondences between edited image pairs and effectively integrate this geometric awareness into SSL frameworks to enhance ICD robustness?" This question directly motivates the PixTrace and CopyNCE approach.  
- **Why unresolved:** While PixTrace provides a solution using coordinate tables, it requires full knowledge of edit transformations and generates significant computational overhead. The approach may not generalize to unknown or black‑box editing methods.  
- **What evidence would resolve it:** Comparative evaluations of CopyNCE performance on images edited with unknown operations (non‑differentiable transforms, GAN‑based edits) versus known transformations. Analysis of failure cases where pixel tracking breaks down under complex edit sequences.

### Open Question 2
- **Question:** How can we reduce the computational overhead of CopyNCE (particularly the coordinate table generation requiring 224×224 key‑value pairs per pair) for practical deployment while maintaining performance?  
- **Basis in paper:** [inferred] The limitations section states: "Unlike image‑level supervision, CopyNCE requires a coordinate table as their supervisory signal... training process may encounter CPU bottlenecks, resulting in longer training time for CopyNCE compared to that for image‑level supervised pipelines." The paper also notes that local crops ensembling (LCE) gives a 6.7%+ µAP boost but incurs 260× computational cost.  
- **Why unresolved:** The paper presents PixTrace and CopyNCE as SOTA but acknowledges significant computational costs from both coordinate table generation during training and LCE during inference. These costs hinder real‑world adoption.  
- **What evidence would resolve it:** Developing sparse or compressed coordinate representations that preserve spatial correspondence accuracy while reducing memory footprint. Measuring the performance degradation trade‑off curve when using approximations versus full coordinate tables at various resolutions.

### Open Question 3
- **Question:** What is the boundary between simple transformations where locality‑based nearest neighbor (LocNN) remains effective versus complex transformations where explicit pixel tracking (PixTrace) becomes necessary?  
- **Basis in paper:** [inferred] The paper states: "In cases where images are augmented by simple transformations, e.g., cropping, scaling and flipping, LocNN actually could use patch centroids along with four vertices of patches to determine whether there is an overlap between patches. However, when faced with more complex edits, such as rotation, stretching, or image matting... LocNN becomes nearly ineffective." The boundary is not quantified.  
- **Why unresolved:** Understanding this boundary would help practitioners choose the most efficient approach based on expected edit types. Currently, the transition point between LocNN adequacy and PixTrace necessity remains unclear.  
- **What evidence would resolve it:** Systematic evaluation across varying edit complexity (rotation angles, affine parameters, matting boundaries) to identify performance thresholds where LocNN degrades below acceptable levels compared to PixTrace. Creating a taxonomy of edit types with difficulty metrics.

### Open Question 4
- **Question:** Why does CopyNCE for the matcher show performance saturation with increasing model size (ViT‑S to ViT‑B provides no gain) while the descriptor continues to benefit from scaling, and what does this reveal about the differing needs of pairwise classification versus global retrieval?  
- **Basis in paper:** [inferred] Table 9 shows matcher µAP: ViT‑S (85.8) ≈ ViT‑B (85.7), while Table 10 shows descriptor µAP: ViT‑S (70.5) < ViT‑B (72.3). The supplementary discusses: "matcher allows interaction between query and reference tokens, while CopyNCE provides direct supervision for interaction. Such guidance is sufficient enough for either ViT‑S or larger ViT‑B to tell whether query edits upon reference."  
- **Why unresolved:** The differing scaling behaviors suggest fundamentally different learning dynamics between the two architectures. Understanding this could optimize model design choices for different ICD deployment scenarios.  
- **What evidence would resolve it:** Ablation studies controlling for CopyNCE supervision strength across model scales, analyzing attention patterns in matcher fusion layers at different sizes, and measuring whether descriptor scaling benefits plateau at larger architectures when using stronger CopyNCE variants.

### Open Question 5
- **Question:** How can copy detection models balance the texture‑focused features necessary for detecting pixel‑level manipulations with semantic understanding needed to handle cases where copy involves semantic changes or object‑level transformations?  
- **Basis in paper:** [inferred] The limitations section notes: "Since copy detection emphasizes features that contain rich texture information, such features often lack semantic understanding... they tend to focus on detailed texture information between two images while overlooking semantic foregrounds." Success cases in visualizations show clear texture matching but failures may involve semantic edits.  
- **Why unresolved:** Current CopyNCE supervision is explicitly pixel‑based, which may inherently bias toward texture matching over semantic correspondence. This creates vulnerability to attacks that preserve semantics but alter textures significantly.  
- **What evidence would resolve it:** Designing hybrid losses that combine CopyNCE's pixel‑level guidance with semantic consistency constraints (e.g., from pretrained segmentation models). Evaluating performance on edited copies that alter textures while preserving semantics (e.g., style transfer, GAN‑based edits) versus those that preserve textures while altering semantics.

## Limitations
- PixTrace assumes known, invertible coordinate functions; it fails for stochastic or complex generative edits (e.g., arbitrary inpainting).  
- Significant computational overhead from coordinate table maintenance (224×224 per pair) and local crops ensembling (260× cost) limits scalability.  
- Generalization degrades on unseen or aggressive edit types (e.g., AnyPattern test set), indicating limited robustness to novel transformations.
