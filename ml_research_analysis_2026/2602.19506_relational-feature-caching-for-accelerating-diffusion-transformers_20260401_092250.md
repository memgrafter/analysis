# Relational Feature Caching for Accelerating Diffusion Transformers

## Quick Facts
- arXiv ID: 2602.19506
- Source URL: https://arxiv.org/abs/2602.19506
- Reference count: 40
- Primary result: Relational Feature Caching (RFC) reduces sFID (e.g., 2.52 vs 2.70 for TaylorSeer on ImageNet) while maintaining similar FLOPs.

## Executive Summary
Diffusion transformers (DiTs) have shown impressive generative capabilities, but inference remains computationally expensive. Existing feature caching methods rely on temporal extrapolation, which suffers from large prediction errors due to irregular feature changes across diffusion steps. This paper introduces Relational Feature Caching (RFC), a novel approach that exploits the strong correlation between a module's input and output feature changes. RFC comprises two components: Relational Feature Estimation (RFE) predicts the magnitude of output changes using input differences, and Relational Cache Scheduling (RCS) dynamically decides whether to reuse cached outputs or perform full recomputation based on estimated prediction error. Experiments on DiTs for image and video generation demonstrate that RFC consistently yields better quality metrics (lower sFID, higher PSNR/SSIM, lower LPIPS) than prior caching methods while keeping computational cost comparable.

## Method Summary
RFC modifies the standard DiT inference pipeline by adding a lightweight estimation and scheduling layer around each transformer block. For each block, the previous output is cached. At a new timestep, the change in the block's input (ΔI) is computed. RFE then predicts the corresponding change in the output (ΔO) magnitude, often using a simple linear model derived from historical correlations. The estimated new output is O_est = O_prev + ΔO_est. RCS evaluates the expected prediction error (e.g., via a confidence bound) and if it surpasses a predefined threshold, the block is fully recomputed; otherwise the estimated output is used and the cache is updated. Because the input-output correlation is typically strong in DiTs, RFE yields accurate estimates for many timesteps, allowing significant reduction in expensive matrix multiplications without degrading sample quality.

## Key Results
- RFC attains lower sFID on ImageNet (2.52) compared to TaylorSeer (2.70) at approximately 6.7 TFLOPs.
- It achieves higher PSNR and SSIM, and lower LPIPS across generated images and videos.
- The method maintains similar FLOP counts to prior caching techniques, confirming its efficiency.

## Why This Works (Mechanism)
RFC works because the output features of a transformer block in a diffusion model are strongly correlated with the changes in their inputs across adjacent timesteps. This relational property allows a simple estimator to predict output deltas accurately for a large fraction of timesteps, reducing the need for full block recomputation. The scheduling mechanism ensures that when the correlation weakens (e.g., during rapid feature changes), the block falls back to exact computation, thus preserving overall generation quality. The additional overhead (computing input differences and running a tiny estimator) is modest compared to the cost of a full transformer block, enabling net savings in FLOPs and wall‑clock time.

- **Relational Cache Scheduling (RCS)**: Decision logic that triggers full recomputation when the estimated error exceeds a threshold. *Why needed*: Balances computational savings and output fidelity. *Quick check*: Set a threshold and measure the trade‑off between sFID and FLOP reduction on a small dataset.

## Architecture Onboarding
**Component Map**

Input (noisy latent) -> DiT Block 1 -> DiT Block 2 -> ... -> DiT Block N -> Output prediction

With RFC: Each block i has associated Cache O_i, RFE estimator, and RCS controller. Data flow: At timestep t, for block i: retrieve O_i(t-1); compute I_i(t) and ΔI = I_i(t) - I_i(t-1); RFE predicts ΔO_est; RCS decides recompute or use O_est = O_i(t-1) + ΔO_est; if recompute, run full block to get O_i(t) and update cache; else use O_est and update cache; forward O_i(t) to next block.

**Critical Path**

The critical path runs sequentially through the N blocks. For each block, the latency is either (full compute cost) or (ΔI compute + RFE + RCS + small cache update). The overall speedup depends on the fraction of blocks that take the cheap path at each timestep.

**Design Tradeoffs**
- **Error threshold**: Lower thresholds increase recomputations, improving quality but reducing speed; higher thresholds do the opposite.
- **Estimator complexity**: A more accurate estimator (e.g., learned neural network) may reduce errors but adds overhead; the paper uses a simple magnitude predictor, keeping overhead minimal.
- **Cache granularity**: Storing full outputs vs. deltas; storing full outputs is simpler but uses more memory.

**Failure Signatures**
- Degeneration of quality (sudden sFID spike) when correlation drops unexpectedly and the scheduler under‑recomputes.
- Memory usage growing linearly with the number of cached blocks; may need to limit cache size for very deep DiTs.
- Overhead dominating compute if the cheap path is too slow or if per‑step scheduling adds significant branching cost.

**First Three Experiments**
1. **Correlation profiling**: Measure input‑output delta correlation per block across 20 random diffusion trajectories to validate the core assumption.
2. **Threshold sweep**: Run RFC with varying error thresholds on a single DiT checkpoint and record sFID vs. FLOPs to illustrate the Pareto frontier.
3. **End‑to‑end timing**: Compare wall‑clock inference time of RFC against TaylorSeer on a fixed hardware setup for generating 500 images, measuring total time and peak memory.

## Limitations
- Input‑output correlation may weaken in some blocks/timesteps, leading to estimation errors.
- Overhead from feature difference calculations and scheduling is not reflected in FLOP counts; actual wall‑clock speedup may be lower.
- Evaluation is confined to ImageNet and a single video dataset; broader domain, resolution, and architecture scalability remain unproven.

## Confidence
- Quality superiority (lower sFID, higher PSNR/SSIM, lower LPIPS): Medium
- Comparable computational cost (similar FLOPs): High
- Generalization to image and video generation: Low
