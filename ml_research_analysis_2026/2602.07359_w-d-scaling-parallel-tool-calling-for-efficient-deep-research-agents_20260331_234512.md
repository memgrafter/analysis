# W&D:Scaling Parallel Tool Calling for Efficient Deep Research Agents

## Quick Facts
- **arXiv ID:** 2602.07359
- **Source URL:** https://arxiv.org/abs/2602.07359
- **Reference count:** 23
- **Primary result:** Parallel tool calling reduces turns and cost while improving accuracy; e.g., 3 parallel calls with GPT-5-Medium on BrowseComp achieve 68% accuracy in 21.0 turns vs. 66% in 45.7 turns for single-tool, cutting cost by 35.9% and wall-clock time by 40.6%.

## Executive Summary
This paper investigates scaling the width of deep research agents by enabling multiple parallel tool calls within a single reasoning step, rather than relying on complex multi-agent orchestration. On web-based benchmarks (BrowseComp, HLE, GAIA), increasing the number of parallel calls per turn consistently improves accuracy and reduces total turns. Notably, with GPT-5-Medium, 3 parallel calls achieve 68% accuracy on the first 100 BrowseComp questions in only 21 turns, compared to 66% in 45.7 turns for the standard single-tool approach. A descending scheduler (more calls early, fewer later) further pushes accuracy to 74% on BrowseComp. Gains generalize across frontier models (Gemini, Claude) and open-source LLMs, demonstrating that optimizing the width-depth trade-off via parallel calling is a key pathway for efficient, high-performance deep research agents.

## Method Summary
The study builds on the MCP-Universe agent framework, which already supports multi-step reasoning with web tools (search, scraping, Python). The modification introduces parallel tool calling: before each LLM call, the scheduler injects a user instruction specifying the exact number `m` of tool calls the model must make. The LLM then emits `m` function calls in one response, which the environment executes concurrently and returns aggregated observations. The research systematically varies `m` (1, 2, 3, 5, 8) and compares scheduling strategies (constant, ascending, descending, automatic) to measure accuracy, average turns, cost, and wall-clock time. No model training is performed; all experiments are inference-time framework modifications using off-the-shelf LLMs.

## Key Results
- 3 parallel tool calls with GPT-5-Medium on BrowseComp (first 100) achieve 68% accuracy in 21.0 turns vs. 66% in 45.7 turns for single-tool (35.9% cost, 40.6% time reduction).
- On the full BrowseComp, parallel calling yields 62.2% accuracy, exceeding the previously reported 54.9% of GPT-5-High.
- A descending scheduler (3 calls early, then 2, then 1) further improves BrowseComp accuracy to 74%.

## Why This Works (Mechanism)
### Mechanism 1: Exploration improves source credibility
- **Claim:** Parallel tool calls improve accuracy by enabling broader exploration of information sources, allowing the model to compare and select the most credible one.
- **Mechanism:** Multiple concurrent search queries retrieve results from a diverse set of websites or databases. The subsequent reasoning step can cross-reference these results, identify patterns of consensus, and preferentially weight outputs from authoritative sources (e.g., official UN reports over third‑party APIs).
- **Core assumption:** For a given factual query, at least one high‑credibility source exists within the retrieval budget, and its signal can be distinguished from lower‑credibility sources through aggregation.
- **Evidence anchors:** Paper abstracts and sections showing that parallel calls retrieve more information per turn and examples where a single API call returned a low‑quality aggregator while parallel calls found an official UN report.
- **Break condition:** If all retrieved sources are similarly low‑credibility or the authoritative source is not within the parallel query set.

### Mechanism 2: Tool call redundancy enables verification
- **Claim:** Parallel tool calls introduce functional redundancy that allows the model to verify tool outputs and avoid being misled by single‑point tool failures or hallucinations.
- **Mechanism:** By issuing multiple tool calls with varied arguments targeting the same underlying information (e.g., scraping the same URL with different extraction queries, or searching for the same fact with different keywords), the model receives multiple, potentially overlapping observations. Inconsistencies across these observations signal unreliability, prompting the agent to discard the results and initiate a new search.
- **Core assumption:** Tool failures are not perfectly correlated across calls with different parameters; at least one call in the redundant set will yield a usable, consistent signal.
- **Evidence anchors:** Abstract and sections demonstrating how parallel calls detected a hallucinated scraping summary for Virginia Tech tuition by cross‑checking multiple calls.
- **Break condition:** All redundant calls fail in the same manner (e.g., all scrape attempts hit a paywall) or the tool’s failure mode is consistent across argument variations.

### Mechanism 3: Query decomposition enhances retrieval
- **Claim:** Parallel tool calls enhance retrieval effectiveness for complex queries by facilitating natural query decomposition, where a single complex information need is split into multiple simpler, targeted searches.
- **Mechanism:** The model’s single reasoning step for a turn can formulate several distinct search queries, each focusing on a subset of the constraints in the original question. This avoids the “keyword stuffing” problem of a single overloaded query and aligns better with how search engines rank relevant pages for specific sub‑questions.
- **Core assumption:** Search engines have higher recall and precision for simpler, focused queries than for a single query attempting to satisfy all constraints simultaneously; the information from these simpler queries can be successfully re‑integrated in a later reasoning step.
- **Evidence anchors:** Abstract and sections contrasting a failed composite query about a soccer match with successful decomposed parallel queries.
- **Break condition:** The query’s constraints are inherently inseparable or the search engine’s index lacks coverage for the decomposed sub‑queries.

## Architecture Onboarding
The system comprises:
1. **LLM Core (fθ):** Generates reasoning thoughts and structured tool calls. Prompt includes system message, conversation history, and a per‑turn user instruction that specifies required call count `m`.
2. **Tool Environment:** Executes all calls in `A_t^par` concurrently (e.g., search API, scraper, Python interpreter). Returns `O_t^par` as a set.
3. **Scheduler Controller:** Determines `m_t` (number of calls per turn). Can be constant, ascending, descending, or automatic (LLM‑decided). Injects user instruction `U_t` with `m_t` before each LLM call.
4. **Trace Manager:** Maintains full agent history `τ_par` and enforces the max‑turn limit (injects final answer prompt).

Critical path:  
User Query `X` → `(U_1, LLM → R_1, A_1^par)` → Parallel Tool Execution → `O_1^par` → … → `(U_T, LLM → R_T, Y_hat)`. The scheduler intervenes before every LLM call to set `m_t` via `U_t`.

Design tradeoffs:
- **Width vs. Depth:** More calls/turn (width) reduce total turns but increase per‑turn latency and cost. Fewer calls/turn (depth) increase total turns but may allow more refined reasoning. Descending scheduler attempts an explore‑then‑exploit compromise.
- **Scheduler Complexity:** Fixed scheduler (e.g., Constant 3) is simple but sub‑optimal. Automatic scheduler is flexible but relies on LLM judgment, which proved unreliable.

Failure signatures:
- **Tool call count mismatch:** Model emits fewer or more than `m_t` calls despite instruction.
- **Redundancy without variation:** Parallel calls are near‑identical, providing no verification benefit.
- **Scheduler ignorance:** Automatic scheduler fails to follow “more early, less late” principle, often maintaining high `m_t`.
- **Context overwhelm:** With high width and depth, the trace grows very long, potentially causing the LLM to lose track of early information (not addressed by this paper).

First 3 experiments:
1. **Baseline Width Scaling:** Fix max‑turn limit (e.g., 50). Run agent with `m_t` = 1, 2, 3, 5, 8. Plot accuracy vs. average turns; expect performance to peak at moderate `m_t` (e.g., 3) and decline if `m_t` is too high.
2. **Scheduler Comparison:** Using best constant `m_t` from Exp 1 (e.g., 3), compare against Descending (3→2→1) and Ascending (1→2→3). Measure accuracy and average turns; expect descending to show a gain.
3. **Mechanism Ablation – Redundancy:** Design a test where single‑tool and parallel‑tool agents (e.g., `m_t=3`). Query where sole search result is a page that the scraper tool fails on (e.g., returns a summary hallucinated from empty content). Measure failure rates; expect parallel agent to detect inconsistency and recover more often.

## Limitations
- Critical implementation details omitted (API tiers, exact repository commit, scheduler prompt wording, summarizer LLM settings) hinder full reproduction.
- Evaluation relies on static benchmarks; risk of overfitting to dataset quirks; no out‑of‑distribution tests.
- Width exploration limited to ≤8; performance and context stress at higher parallelism unknown.

## Confidence
- Parallel width scaling improves accuracy and reduces turns: **High**
- Descending scheduler yields extra accuracy: **Medium**
- Mechanisms (credibility, redundancy, decomposition) drive gains: **Medium**
- Generalization to unseen models/tools: **Low**
