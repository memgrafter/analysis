# GREPO: A Benchmark for Graph Neural Networks on Repository-Level Bug Localization

## Quick Facts
- **ArXiv ID:** 2602.13921
- **Source URL:** https://arxiv.org/abs/2602.13921
- **Reference count:** 40
- **Primary result:** GAT achieves Hit@1=14.80, Hit@5=31.51, Hit@10=37.40, Hit@20=41.25, outperforming strong IR/LLM baselines.

## Executive Summary
Repository-level bug localization—identifying the exact code elements to fix given a natural‑language issue—is a critical yet challenging task. Large language models (LLMs) struggle due to context‑window limits, while graph neural networks (GNNs) offer a promising alternative to model complex code dependencies, but a dedicated benchmark was lacking. This paper introduces GREPO, the first GNN benchmark for repository‑level bug localization, comprising 86 Python repositories and 47,294 real bug‑fixing instances. GREPO constructs heterogeneous temporal graphs capturing code structure (containment, calls, inheritance) and evolution, enriches nodes with text embeddings and query similarity, and selects anchor nodes via an LLM‑based Rewriter and temporal co‑change patterns. Evaluations show that GAT consistently surpasses state‑of‑the‑art retrieval and LLM baselines, and ablations confirm the contribution of each component. The dataset and methodology enable future research on GNN‑powered bug localization.

## Method Summary
GREPO transforms each repository into a heterogeneous temporal graph where nodes represent directories, files, classes, and functions extracted via Tree‑sitter and Jedi, and edges model containment, method calls, inheritance, and version‑linking across commits. For a given bug report, an LLM Rewriter produces semantic queries (lexical keywords and dense retrieval terms) while a temporal retriever scores nodes by co‑change history. The union of these signals seeds anchor nodes, from which a time‑sliced subgraph of up to 80 k nodes is extracted. Nodes are enriched with pre‑computed Qwen3‑Embedding‑8B code embeddings and query–node similarity scores. A query‑aware GAT (typically 4 layers, 128 hidden) then scores nodes, and the top‑K predictions are evaluated against the actual modified nodes in the fixing PR. Training uses AdamW on the combined chronological splits of 77 repositories (80% of issues per repo) and evaluates on nine held‑out repositories.

## Key Results
- GAT significantly outperforms strong baselines: CF‑RAG, LocAgent (Qwen2.5‑72B), and Agentless (GPT‑4o), achieving Hit@1=14.80, Hit@5=31.51, Hit@10=37.40, Hit@20=41.25.
- Ablations validate each design choice: removing similarity features drops Hit@1 by ~1.4, dropping containment edges by ~0.7, and omitting temporal anchors by ~0.5.
- Scaling experiments show monotonic improvement as the number of training repositories increases, suggesting that GNNs can learn transferable bug‑localization patterns.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Repository-level code dependencies and history are effectively modeled as a heterogeneous temporal graph, enabling multi-relational reasoning over code structure and evolution.
- **Mechanism:** Parse each commit’s Python files with Tree‑sitter to extract AST nodes (directories, files, classes, functions). Use Jedi for static analysis to add call and inheritance edges. Temporal version links ("previous"/"next") connect node lifespans across commits. This graph is built incrementally by updating only changed files per commit, with propagation for containment‑consistent lifespans and call‑closure across versions.
- **Core assumption:** The combination of syntactic containment (AST hierarchy), semantic dependencies (calls/inheritance), and temporal versioning captures the relevant code context for bug localization without losing historical causality.
- **Evidence anchors:**
  - [abstract]: "heterogeneous temporal graphs (nodes: directories, files, classes, functions; edges: containment, calls, inheritance, temporal version links)"
  - [section 4.1]: Details AST parsing, Jedi inference, and incremental construction with temporal node intervals.
- **Break condition:** If temporal versioning introduces noise (e.g., frequent entity renaming/relocation breaking identity) or if critical dependencies (e.g., data flow, dynamic imports) are missing from static analysis, the graph’s expressivity degrades.

### Mechanism 2
- **Claim:** Anchor node selection via a hybrid of semantic rewriting (LLM‑based) and temporal co‑change patterns focuses subgraph extraction on likely buggy regions, balancing precision and recall.
- **Mechanism:** For each issue, an LLM Rewriter generates (a) extracted code entities/keywords for lexical matching and (b) up to five search queries for semantic similarity. Separately, a temporal retriever trained on commit history (no future leakage) scores nodes by co‑change recency/support. The union of top lexical and semantic matches, plus temporal priors, seeds 1‑hop subgraph extraction with a node budget.
- **Core assumption:** Buggy code is reachable from a small set of entry points that combine current textual relevance (from issue description) and historical modification likelihood (temporal locality).
- **Evidence anchors:**
  - [abstract]: "anchor nodes for subgraph extraction are selected via an LLM‑based Rewriter (semantic) and temporal co‑change patterns"
  - [section 4.3.3 & H]: Rewriter prompt templates, output schemas, and retrieval pipelines.
- **Break condition:** If issue descriptions are vague/non‑informative (low lexical/semantic signal) or if the bug’s fix lies outside recently modified regions (low temporal overlap), anchor hit/recall drops sharply.

### Mechanism 3
- **Claim:** Query–node similarity features derived from text embeddings provide a strong, transferable retrieval prior that initializes GNN message passing toward relevant code, even before structural reasoning.
- **Mechanism:** Node text (code + path) and rewritten issue queries are embedded with Qwen3‑Embedding‑8B. Inner product similarity scores (max over queries) are concatenated with node features as a similarity vector. This acts as an anchor‑aware prior: nodes with high similarity are more likely to be classified as buggy after GNN propagation.
- **Core assumption:** Lexical/semantic similarity between bug reports and code entities is a robust signal for localization, generalizing across repositories and partially overlapping with structural bug patterns.
- **Evidence anchors:**
  - [abstract]: "enriches nodes with text embeddings and query–node similarity features"
  - [section 4.3 & F]: Similarity computation, validation via ROC‑AUC (positives vs. negatives) and linear probes on frozen embeddings.
- **Break condition:** If bug reports contain domain‑specific jargon or vague descriptions that embeddings fail to capture, or if the fix involves deep structural dependencies unrelated to surface text, similarity alone becomes a weak prior.

## Foundational Learning
### Heterogeneous Graph Neural Networks
- **Why needed here:** GREPO’s graph has multiple node types (dir/file/class/func) and edge types (containment, calls, inheritance). GNNs must distinguish these to propagate information correctly—e.g., a call edge should flow differently than a containment edge.
- **Quick check question:** Can a homogeneous GNN (ignoring node/edge types) match GAT’s performance on this task? If not, what specific edge types drive the gain?

### Temporal Graph Modeling
- **Why needed here:** Bugs are fixed in a specific repository snapshot. Nodes have lifespans across commits; edges must respect temporal validity. The model must not “see” future code entities that didn’t exist at bug time.
- **Quick check question:** If we shuffle commit order or drop temporal edges, does performance degrade?

### Retrieval‑Augmented Graph Learning
- **Why needed here:** Full repository graphs are too large; we need a retrieval step to focus computation. Similarity features and anchor nodes create a bridge between information retrieval (fast, coarse) and graph neural networks (expensive, fine‑grained reasoning).
- **Quick check question:** Does removing the similarity feature hurt more than removing anchor labeling? Which phase—retrieval or graph learning—contributes more to final Hit@K?

## Architecture Onboarding
### Component map
Repo‑to‑Graph Builder → Feature Generator → Anchor Selector → Subgraph Extractor → GNN Reranker

### Critical path
Issue → Rewriter + temporal prior → anchor nodes → time‑sliced subgraph extraction → feature assembly (similarity, anchor indicator, prior) → GAT forward pass → ranked node list → Hit@K evaluation.

### Design tradeoffs
- **Graph scale vs. coverage:** Larger subgraph budgets improve ground‑truth recall but increase GPU memory and noise. Hop=1 with 80k nodes balances this.
- **Static vs. dynamic analysis:** Tree‑sitter + Jedi is fast but misses dynamic imports/reflection; could add runtime call traces but at high cost.
- **Anchor precision vs. recall:** Extractor (lexical) is precise but low recall; Inferer (semantic) is high recall but noisy; union improves F1.

### Failure signatures
- **Low anchor hit/recall** (<0.3 for patched nodes) indicates poor Rewriter output or temporal mismatch.
- **Temporal prior non‑overlap** (Appendix N): if candidate sets for nearby issues are disjoint, temporal signal may be weak for that repo.
- **Ablation drops:** Removing any edge type hurts; *Inherit* removal least, suggesting inheritance edges are less critical than calls/containment.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How well do GNN models trained on GREPO’s Python repositories generalize to bug localization in other programming languages?
- **Basis in paper:** GREPO includes only Python repositories; future extensions to broader languages are suggested.
- **Why unresolved:** No multilingual data or evaluation is provided; cross‑lingual transfer capabilities remain unknown.
- **What evidence would resolve it:** Construct comparable GNN benchmarks for other languages (e.g., Java, JavaScript) and evaluate zero‑shot transfer of models trained on GREPO.

### Open Question 2
- **Question:** Can bug localization performance continue to scale with more training repositories, and is there a saturation point beyond the current 86 repos?
- **Basis in paper:** Scaling experiments show improved Hit@K as the number of training repositories increases up to 77, but the maximum tested is 86 (all repos). The authors suggest transferable models but do not explore beyond.
- **Why unresolved:** The scaling curve might plateau; also, the 9 held‑out repos are specialized, so true generalization to new ecosystems is untested.
- **What evidence would resolve it:** Train on increasingly larger sets of repositories (e.g., hundreds) and evaluate on a diverse test bed of unseen projects to measure saturation and transfer limits.

### Open Question 3
- **Question:** What is the optimal combination of semantic and temporal anchor signals for subgraph extraction in repository‑level bug localization?
- **Basis in paper:** GREPO uses two anchor strategies: LLM‑based Rewriter (semantic) and temporal co‑change patterns. Both improve results in ablations, but their union is simple and not tuned.
- **Why unresolved:** The relative contribution and potential redundancy between semantic and temporal anchors is unknown; the current union may be suboptimal in terms of recall vs. budget.
- **What evidence would resolve it:** Systematically vary the proportion of anchors from each source (e.g., top‑k from each) and measure Hit@K and subgraph size to find Pareto‑optimal combinations.

### Open Question 4
- **Question:** Can incorporating additional edge types (e.g., data flow, import dependencies) beyond containment, call, and inheritance further improve GNN‑based bug localization?
- **Basis in paper:** The heterogeneous graph includes only three primary relation types; the authors note these capture structural hierarchy and semantic dependencies but do not explore richer semantics.
- **Why unresolved:** Other edges might encode useful information (e.g., variable definitions, type hints, module imports) that could aid localization, but their impact is not evaluated.
- **What evidence would resolve it:** Augment the graph with additional static analysis edges and re‑run ablations to measure performance changes, controlling for graph size and noise.

## Limitations
- Public dataset may exclude temporal anchors; generating them requires undocumented GET retriever training.
- Exact GNN loss function is unspecified, risking reproducibility gaps.
- Subgraph extraction rules (e.g., anchor merging) are ambiguous, potentially causing variance.
