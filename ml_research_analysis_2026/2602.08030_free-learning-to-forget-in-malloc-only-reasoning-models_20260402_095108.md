# Free(): Learning to Forget in Malloc-Only Reasoning Models
## Quick Facts
- arXiv ID: 2602.08030
- Source URL: https://arxiv.org/abs/2602.08030
- Reference count: 40
- Primary result: Free()LM uses a LoRA-based Free-Module to prune redundant context in long reasoning, achieving 3.3% average accuracy gain and recovering from 0% to ~50% on ultra-long tasks.

## Executive Summary
Standard LLMs fail on long-horizon reasoning due to passive context accumulation ("malloc-only"), where noise from redundant steps causes catastrophic performance collapse. Free()LM addresses this by introducing a trainable LoRA adapter (Free-Module) that switches the model between reasoning and cleaning modes. In cleaning mode, it outputs structured JSON commands to precisely delete redundant text spans via prefix/suffix matching. Trained with a reward mechanism that retains only pruning operations preserving or improving accuracy, Free()LM achieves consistent gains across model scales (8B–685B), sets a new SOTA on IMOAnswerBench (+2.3%), and critically rescues failure on ultra-long trajectories (>80k tokens) while reducing KV cache memory by 45.6%, albeit with a 56.4% latency increase.

## Method Summary
Free()LM’s training synthesizes candidate pruning commands from segmented reasoning trajectories using an external model (e.g., Gemini-2.5-Pro). Each candidate is filtered via a reward mechanism: K rollouts are run on the pruned context, and only commands that maintain or improve final answer accuracy are retained. A LoRA adapter (Free-Module) is then trained on these filtered examples to generate prefix/suffix JSON deletion commands. During inference, the Free-Module is periodically merged (every L_clean tokens) to output pruning commands; an external executor deletes the specified spans and triggers re-prefilling of the KV cache, after which the Free-Module is unmerged to resume reasoning.

## Key Results
- Free()LM yields a 3.3% average accuracy improvement across model scales (8B–685B) and achieves +2.3% absolute gain on IMOAnswerBench, setting a new SOTA.
- On ultra-long tasks (>80k tokens), it rescues catastrophic collapse: Qwen3-235B accuracy recovers from 0% to ~50% while reducing context length by ~45%.
- Trade-offs include a +56.4% latency overhead due to re-prefilling, but a 45.6% reduction in KV cache memory usage.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Standard LLM reasoning degrades on long tasks due to passive, append-only context accumulation ("malloc-only"), where noise from redundant steps crowds out necessary information and causes catastrophic collapse.
- **Mechanism:** The model's fixed context window fills with intermediate thoughts. As length grows, attention is diluted across valid and obsolete content, increasing the probability of repetitive loops or retrieval failure for critical clues, leading to accuracy crashing to zero.
- **Core assumption:** Context quality, not just quantity or architecture, determines sustainable reasoning performance beyond a threshold length.
- **Evidence anchors:**
  - [abstract] "Standard LLMs suffer performance collapse on long-horizon reasoning tasks due to passive context accumulation without pruning, analogous to a 'malloc-only' system."
  - [section 1] Empirical data on Qwen3-8B shows degeneration ratio hits 100% by 48k tokens, with 84% of context-limited cases in repetitive loops.
  - [corpus] Weak direct evidence; neighboring papers on overthinking [37] and context length decay [33] describe correlated symptoms but do not establish the malloc-only framing or Free()LM's pruning solution.
- **Break condition:** Performance collapse is avoided if the model can maintain a compact context whose size stays within a "sweet spot" (e.g., <80k tokens for Qwen3-235B) by actively removing identified redundancies.

### Mechanism 2
- **Claim:** Switching between a frozen backbone (Reasoning mode) and a trainable LoRA adapter merged as the Free-Module (Cleaning mode) enables effective, targeted pruning without altering core reasoning capabilities.
- **Mechanism:** The LoRA adapter, when merged, repurposes the model's forward pass to output structured `{"prefix":..., "suffix":...}` JSON commands. These define precise text spans for deletion via anchor matching, allowing large chunks to be removed with minimal token generation cost.
- **Core assumption:** A small, trainable adapter can learn to distinguish genuinely redundant reasoning segments (e.g., corrected errors, superseded branches) from essential logical anchors without retraining the entire backbone.
- **Evidence anchors:**
  - [section 2.1] Detailed architecture: "Free-Module is a LoRA adapter... switches between two modes... outputs a structured pruning command... specifying a prefix and suffix."
  - [section 2.2] Training data uses `prefix`/`suffix` pairs synthesized from segmented trajectories.
  - [corpus] Directly supported by LoRA literature [6] (adjacent work) but novel in application to intra-trajectory pruning.
- **Break condition:** If the Free-Module's generation of `prefix`/`suffix` pairs is imprecise (false positives or negatives), pruning will either damage necessary context (forcing regeneration) or leave noise, failing to prevent collapse.

### Mechanism 3
- **Claim:** A reward-filtered dataset where only pruning operations that preserve or improve accuracy are retained trains the Free-Module to make safe, utility-preserving deletion decisions.
- **Mechanism:** Candidate deletion commands are generated (e.g., via Gemini ICL). For each candidate, K=8 rollouts are run on the pruned context. Only commands where `Acc(cleaned) >= Acc(raw)` are kept for training. This reinforcement-style filtering teaches the module to avoid harmful pruning.
- **Core assumption:** Accuracy on the final answer is a sufficient proxy for judging the safety of intermediate context reduction; preserving the solution path's integrity is the primary goal of pruning.
- **Evidence anchors:**
  - [section 2.2] "A candidate operation is retained if and only if the pruning preserves or improves the accuracy: Acc(Cnew) ≥ Acc(Craw)."
  - [section 3.6] Case study shows Free()LM deletes without regeneration, while Gemini (ICL baseline) often deletes essential setup, causing regeneration—implying the reward filter eliminates such harmful patterns.
  - [corpus] Related to RL-based reasoning compression [40, 41], but Free()LM's reward is binary (preserve accuracy) rather than a length penalty.
- **Break condition:** The binary accuracy reward may not capture subtle degradations (e.g., slightly worse reasoning that still converges) or may encourage overly aggressive pruning if rollouts have variance; the dataset may bias toward conservative deletions.

## Foundational Learning
- **Concept: Chain-of-Thought (CoT) / Overthinking**
  - *Why needed here:* Free()LM directly addresses overthinking—the generation of redundant, superfluous, or corrected steps that become noise. Understanding how standard CoT can degrade is prerequisite to seeing the need for active pruning.
  - *Quick check question:* Can you identify three types of "redundant" tokens in a long reasoning trace that might become noise (e.g., corrected miscalculations, repeated verification statements, abandoned approaches)?
- **Concept: KV Cache Management**
  - *Why needed here:* The "memory" being managed is the KV cache of past tokens. Pruning text context necessitates cache eviction or re-prefilling. The efficiency gains (45% KV reduction) and latency costs are direct consequences of cache management strategy.
  - *Quick check question:* What is the difference between Strategy 1 (re-prefilling) and Strategy 2 (direct KV cache pruning) in terms of implementation complexity and expected latency overhead?
- **Concept: Parameter-Efficient Fine-Tuning (LoRA)**
  - *Why needed here:* Free-Module is a LoRA adapter. Understanding that a small, trainable side-network can be dynamically merged/unmerged to switch model behavior is central to the plug-and-play design.
  - *Quick check question:* If the backbone is frozen and only the LoRA is trained, what does this imply about the nature of the "cleaning" skill being learned (e.g., is it modifying base knowledge or adding a control layer)?

## Architecture Onboarding
- **Component map:**
  Backbone LLM (frozen) -> Free-Module (LoRA adapter, merged for cleaning, unmerged for reasoning) -> Pruning Executor (external Python). Trigger Scheduler dictates merge/unmerge timing.
- **Critical path:**
  1. **Reasoning Loop:** Backbone (Free-Module unmerged) generates tokens until `tokens_generated % L_clean == 0`.
  2. **Cleaning Trigger:** Free-Module is merged. Model's next output is a JSON list of deletion commands.
  3. **Prune & Rebuild:** Executor deletes spans. Context is logically shortened. vLLM re-prefills from the last unchanged token, reusing KV cache for the prefix.
  4. **Resume:** Free-Module unmerged. Reasoning continues on the cleaned context.
- **Design tradeoffs:**
  - *Precision vs. Safety:* Aggressive pruning saves more memory but risks deleting crucial context; reward mechanism biases toward safety, potentially under-pruning.
  - *Latency vs. Memory:* Cleaning cycles incur decoding cost + re-prefilling overhead (+56.4% latency). Direct KV pruning could reduce this to ~20% but lacks vLLM support.
  - *Generality vs. Specificity:* 8B Free-Module generalizes to 235B and DeepSeek models, suggesting architecture-agnostic heuristics. However, optimal L_clean may be model/task-specific.
- **Failure signatures:**
  - *Over-pruning:* Model regenerates previously deleted content; increased response length; accuracy drop on general tasks.
  - *Under-pruning:* Context length grows linearly; performance still collapses on >80k token tasks.
  - *Malformed commands:* JSON parse errors or prefix/suffix not found; leads to no-op or crash.
- **First 3 experiments:**
  1. **Validate Trigger Logic:** On a small validation set, log when cleaning is triggered. Verify L_clean is respected and cleaning occurs before catastrophic lengths (e.g., <80k tokens).
  2. **Sanity Check Pruning Commands:** Manually inspect 50 random JSON outputs. Check that prefix/suffix spans are non-overlapping, match actual text, and target plausible redundancy (e.g., "Wait, let me check" or corrected algebra).
  3. **Cross-Model Generalization Test:** Apply the trained Qwen3-8B Free-Module to Qwen3-235B and DeepSeek-V3.2 on a 20-question subset. Confirm >0% absolute accuracy gain and >20% token reduction without re-training.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** To what extent can the latency overhead of Free()LM be mitigated by implementing direct KV cache pruning (Strategy 2) within serving frameworks like vLLM, and what are the resulting trade-offs in memory savings, accuracy, and engineering complexity?
- **Basis in paper:** The paper explicitly reports a 56.4% latency increase and notes that adopting Strategy 2 could reduce this to ~20%, but it was not implemented due to incompatibility with vLLM.
- **Why unresolved:** Practical engineering challenges and performance implications of Strategy 2 in real-world, high-throughput setups remain unevaluated.
- **What evidence would resolve it:** A re-implementation with native KV cache pruning support in vLLM, measuring per-sample latency, peak memory, and accuracy across model scales and benchmarks.

### Open Question 2
- **Question:** Is the cross-model generalization demonstrated by the Qwen3-8B-trained Free-Module evidence of a universal context-pruning capability, or is it primarily an artifact of shared model families or similar reasoning patterns?
- **Basis in paper:** The paper labels this a critical question after showing improvement on DeepSeek-V3.2-Speciale, suggesting a potential "Universal Context Pruning Service" but questioning the scope.
- **Why unresolved:** Generalization was tested on only one non-Qwen model; broader evaluation across diverse families (Llama, Mistral, GPT) is lacking.
- **What evidence would resolve it:** A systematic study applying the same Free-Module to diverse model families on a common benchmark suite, measuring consistency of gains and pruning behavior.

### Open Question 3
- **Question:** How does the accuracy-only reward mechanism affect learned pruning behavior, and could auxiliary rewards (e.g., conciseness, avoiding regeneration) lead to more efficient or robust reasoning?
- **Basis in paper:** The reward is strictly `Acc(C_new) ≥ Acc(C_raw)`; no alternative reward designs are explored.
- **Why unresolved:** The binary reward may encourage overly aggressive or conservative pruning; nuances like preserving intermediate inferences are unexamined.
- **What evidence would resolve it:** Training Free-Modules with augmented reward functions (accuracy + token reduction penalties, consistency rewards) and comparing pruning patterns, accuracy, and regeneration rates.

## Limitations
- Training requires proprietary DeepMath-103k; open-source substitutes may degrade performance.
- Fixed cleaning trigger interval (L_clean=5000) may not generalize across tasks/models.
- Binary accuracy reward may bias toward conservative pruning, under-utilizing memory savings.
- Re-prefilling strategy introduces significant latency overhead (+56.4%), limiting real-time use.

## Confidence
- Malloc-only collapse: Medium (strong correlation, indirect causality).
- Free-Module effectiveness: High (consistent gains across scales and SOTA results).
- Reward-filtered training: Medium (case study supportive, lacks ablations).
