# Can Small Language Models Use What They Retrieve? An Empirical Study of Retrieval Utilization Across Model Scale

## Quick Facts
- **arXiv ID:** 2603.11513
- **Source URL:** https://arxiv.org/abs/2603.11513
- **Reference count:** 16
- **Primary result:** Even with oracle retrieval guaranteeing the answer is present, sub-7B models fail to extract it 85–100% of the time on questions they cannot answer alone, and adding any retrieval context harms performance on previously correct answers by 42–64%.

## Executive Summary
This paper investigates whether small language models (≤7B parameters) can effectively utilize retrieved information in retrieval-augmented generation (RAG) systems. Using an oracle retrieval setup that guarantees an answer-containing passage and a parametric knowledge split that isolates utilization from retrieval quality, the study finds a fundamental bottleneck: these models cannot extract correct answers from provided context even when it is present. Furthermore, adding retrieval context—even perfect passages—significantly harms performance on questions the model already knows, indicating a distraction effect driven by context presence rather than quality. The dominant failure mode is irrelevant generation, where the model ignores the context entirely. The net trade-off of adding retrieval is negative for all sub-7B models tested, suggesting that at this scale, the primary constraint is context utilization, not retrieval quality.

## Method Summary
The study evaluates five instruction-tuned decoder-only models (360M to 8B parameters) on an extractive QA task using 1,000 questions from Natural Questions and HotpotQA. For each model, questions are first split into KNOWN (answered correctly without retrieval) and UNKNOWN (not) based on a no-retrieval baseline. Retrieval is performed from a 500K-passage Wikipedia corpus using BM25, dense (E5-large-v2), hybrid, and an oracle retriever that guarantees a gold answer-containing passage at rank-1. The oracle evaluation is restricted to the 75.6% of questions having such a passage in the corpus. Exact Match (EM) is the primary metric. The design isolates utilization (EM on UNKNOWN with oracle) from distraction (EM drop on KNOWN with any retrieval). An automated error analysis classifies oracle failures into six categories.

## Key Results
- Oracle retrieval yields at most 14.6% EM for the 7B model on UNKNOWN questions, meaning 85–100% of potential retrieval utility is lost due to poor utilization.
- Adding any retrieval context destroys 42–64% of previously correct answers (KNOWN), with no significant difference between oracle and noisy context for models ≤3B, proving the harm stems from context presence.
- Irrelevant generation—where the model’s output bears no meaningful lexical or semantic overlap with the provided passage—is the dominant failure mode, accounting for 61–100% of oracle retrieval failures across model scales.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Small models (≤7B) exhibit a fundamental **utilization bottleneck**—they cannot extract answers from retrieved passages even when the answer is guaranteed present.
- **Mechanism:** The model's internal representation and decoding fail to ground generation in the provided context, producing outputs semantically unrelated to the passage. This suggests a lack of conditional generation capability for in-context knowledge extraction at this scale.
- **Core assumption:** Standard instruction-tuning on generic corpora does not instill robust "context following" or "information grounding" skills for factual extraction when model size is below a threshold (~7B).
- **Evidence anchors:** Oracle EM on UNKNOWN ≤14.6% for 7B; related work shows distraction in larger models but isolates utilization failure as primary for small models.

### Mechanism 2
- **Claim:** Adding *any* retrieval context (even perfect oracle passages) **destroys a large fraction of previously correct parametric answers** (42–64% loss), a "distraction effect" driven by the mere *presence* of context.
- **Mechanism:** The model's generation is adversarially perturbed by concatenated retrieved text, overriding its parametric knowledge. Possible causes include attention dilution over longer contexts, instruction conflict, or positional biases favoring early context tokens.
- **Core assumption:** Small models lack robust mechanisms to resolve conflicts between parametric memory and in-context information, defaulting to the latter even when harmful.
- **Evidence anchors:** 7B loses 41.6–51.2 percentage points on KNOWN; permissive prompt fails to recover baseline; oracle vs. noisy distraction difference insignificant for ≤3B.

### Mechanism 3
- **Claim:** The **dominant failure mode** for oracle retrieval is **irrelevant generation** (61–100% of failures)—the model produces output with no meaningful overlap with the gold passage.
- **Mechanism:** The model does not recognize the answer resides within the context and defaults to generating from parametric memory or free-association, failing the "locate and extract" step.
- **Core assumption:** Small models cannot perform the basic pattern-matching or attention focus required to identify a factual answer string within a distractor-rich passage.
- **Evidence anchors:** Error analysis of 2,588 failures; irrelevant generation is largest category at all scales (360M: 100%, 1.5B: 64%, 3B: 73%, 7B: 61%).

## Foundational Learning
- **Concept: Parametric Knowledge Split**
  - **Why needed:** Separates questions a model can answer without retrieval (KNOWN) from those it cannot (UNKNOWN). This isolates *utilization failure* (failing with oracle context) from *retrieval failure* (no good passage exists). Without this split, poor RAG performance cannot be attributed to context use vs. retrieval quality.
  - **Quick check:** If a model scores 20% EM without retrieval and 30% with noisy retrieval, how would you use a parametric split to determine whether the net gain is from helpful retrieval or lucky noise? What would you look for in the KNOWN vs. UNKNOWN subsets?
- **Concept: Oracle Retrieval**
  - **Why needed:** Oracle retrieval (guaranteed answer-containing passage at rank-1) is the experimental lever that cleanly separates retrieval quality from utilization ability. It answers the counterfactual: "If retrieval were perfect, would the model succeed?" The finding that oracle EM remains very low proves utilization is the binding constraint.
  - **Quick check:** A 3B model gets 15% EM with noisy retrieval and 20% EM with oracle retrieval on the same UNKNOWN questions. What does the 5pp gap represent? What does the remaining 80% failure under oracle represent?
- **Concept: Distraction Effect**
  - **Why needed:** The paper shows retrieval harms performance on questions the model already knows. Understanding this requires comparing KNOWN sets across retrieval conditions. The finding that even oracle context destroys knowledge proves the harm is from context *presence*, not *content*.
  - **Quick check:** A model answers 90% of KNOWN questions correctly without retrieval. With oracle retrieval, it drops to 50%. What is the "destruction rate"? If noisy retrieval also causes a 40% drop, what does that suggest about the role of context quality vs. context presence?

## Architecture Onboarding
- **Component map:** Model Zoo (SmolLM2-360M, Qwen2.5-1.5B/3B/7B, Llama-3.1-8B) -> Retriever Suite (BM25, dense E5, hybrid RRF, oracle) -> 500K-passage Wikipedia corpus -> Split Engine (KNOWN/UNKNOWN classifier) -> Evaluation Harness (EM, F1, stats)
- **Critical path:** 1) Run all models on `none` condition → derive per-model KNOWN/UNKNOWN splits. 2) For each model, evaluate on `oracle` only for corpus-matched questions (756/1000). 3) Compute utilization: EM on UNKNOWN subset under oracle. 4) Compute distraction: EM drop on KNOWN subset from `none` to `oracle`/`noisy`. 5) Run error analysis on all oracle failures → classify into 6 categories.
- **Design tradeoffs:**
  - **EM vs. F1:** EM is strict; F1 is lenient but may reward partial overlap. Paper uses EM for consistency; qualitative pattern holds under both.
  - **Quantization:** All local models use 4-bit NF4. Cross-check with FP16 Llama-3.1-8B shows same pattern, arguing quantization isn't root cause.
  - **Corpus coverage:** 500K-passage corpus yields 75.6% oracle coverage. Tradeoff: smaller corpus ensures retriever comparability but limits question set.
  - **Prompt design:** Test at least 3 templates (forced, permissive, minimal) to confirm robustness; permissive prompt does not rescue performance.
- **Failure signatures:**
  1. Oracle EM on UNKNOWN ≤ 15% for 7B ( utilization bottleneck ).
  2. >40% drop in EM on KNOWN with any retrieval ( distraction effect ).
  3. >60% of oracle failures classified as "Irrelevant generation" ( model ignores context ).
  4. No significant difference between oracle and noisy distraction for models ≤3B ( presence > quality ).
- **First 3 experiments:**
  1. **Replicate parametric split:** For a new model (e.g., Phi-3-mini), run 1k questions with `none` retrieval. Record EM and split. Verify KNOWN rate is low (<20% for sub-7B).
  2. **Oracle utilization test:** Filter to UNKNOWN questions with a gold passage in the corpus. Run `oracle` retrieval. Expected: EM low (<20%). If EM high (>50%), investigate fine-tuning data.
  3. **Distraction quantification:** On KNOWN subset, compare `none` vs. `oracle` EM. Compute destruction rate. Expected: >40% drop. If drop minimal (<10%), check for architectural features like x-attention gating or RAG fine-tuning.

## Open Questions the Paper Calls Out
- Which mechanism—attention dilution, instruction conflict, or position bias—primarily explains the distraction effect caused by retrieval context in small models? The study identifies the effect but does not experimentally isolate these causal factors.
- What is the exact model scale (parameter count) at which retrieval utilization exceeds the distraction effect, leading to net positive gains in RAG? The authors extrapolate from 360M to 8B and suggest >7B may be needed, but lack empirical data beyond 8B.
- Does the utilization bottleneck generalize to non-extractive tasks, such as generative summarization or reasoning with retrieved documents? The study is limited to extractive QA, leaving open whether findings apply to other task types.
- Can RAG-specific fine-tuning (e.g., RAFT) eliminate the irrelevant generation failure mode and improve utilization in sub-7B models? The paper cites RAFT as promising but does not test it; standard instruction tuning fails.

## Limitations
- The exact 1,000-question set and hash-based 500K-passage corpus construction are not publicly available, so reproduction depends on approximations that may affect oracle coverage and results.
- The primary prompt template is unspecified; different phrasings could alter the magnitude of the distraction effect.
- Error analysis relies on automated heuristics; thresholds for "irrelevant generation" and other categories are not detailed, limiting interpretability.
- EM normalization rules are partially described (lowercasing, article/punctuation removal); full specification is needed for exact replication.

## Confidence
- **Utilization bottleneck:** High. Oracle retrieval yields ≤14.6% EM on UNKNOWN questions even for the 7B model; finding holds across retrieval methods and models.
- **Distraction effect:** High. Adding any context destroys 42–64% of previously correct parametric answers; effect is statistically significant and persists with perfect oracle passages.
- **Irrelevant generation dominance:** Medium. Automated classification shows 61–100% of failures are irrelevant, but this hinges on heuristic design; human validation is required to confirm.

## Next Checks
1. **Prompt sensitivity study:** Test multiple prompt variants (e.g., forced, permissive, minimal) on the oracle setup to assess whether the distraction effect and irrelevant generation are robust to instruction wording.
2. **Human-annotated error analysis:** Sample 200–300 oracle failures per model for manual labeling into the six categories; compare distributions to automated results to verify the dominance of irrelevant generation.
3. **Scale probing:** Evaluate larger models (13B, 34B, 70B) on the identical benchmark to pinpoint the scale at which utilization improves and/or distraction diminishes, testing for a capability threshold.
