# Structured Prompt Language: Declarative Context Management for LLMs

## Quick Facts
- arXiv ID: 2602.21257
- Source URL: https://arxiv.org/abs/2602.21257
- Reference count: 30
- Primary result: SPL reduces prompt boilerplate by 65%, provides a pre-execution 68× cost signal across models, and runs identical scripts at $0.002 on cloud or zero cost locally.

## Executive Summary
Structured Prompt Language (SPL) is a declarative, SQL-inspired language for managing LLM context windows as constrained resources. It introduces explicit token budgeting, an automatic optimizer, and EXPLAIN-style transparency, integrating retrieval-augmented generation (RAG) and persistent memory natively. SPL achieves a 65% average reduction in prompt boilerplate, a pre-execution 68× cost signal across models, and allows scripts to run at $0.002 on cloud or zero local cost. Its Logical Chunking via CTEs reduces attention complexity from O(N²) to O(N²/k) for long documents. The system is delivered as two pip-installable packages with a formal EBNF grammar. By treating context as a quantifiable resource, SPL enables developers to write efficient, cost-predictable prompts and to understand resource usage before incurring LLM costs.

## Method Summary
SPL parses scripts written in a SQL-like syntax, producing an AST that undergoes semantic analysis and optimization. The optimizer estimates token counts for each context source, applies user-defined LIMIT caps, and compresses the largest sources if the total exceeds the input budget. Before execution, EXPLAIN generates a plan showing token allocations, cache status, compression ratios, and cost estimates. The executor resolves sources in priority order (cache → memory → RAG → context), assembles the final prompt, and calls the LLM via adapters. Logical Chunking via CTEs enables declarative map-reduce, splitting long documents into independent chunks to reduce quadratic attention costs. The runtime is distributed across `spl-llm` (core language engine) and `spl-flow` (orchestration, UI, CLI).

## Why This Works (Mechanism)

### Mechanism 1: Explicit Token Budgeting with Automatic Optimization
- **Claim**: Treats the LLM context window as a constrained resource and automatically allocates tokens across heterogeneous sources, eliminating manual token counting and reducing prompt boilerplate.
- **Mechanism**: The optimizer estimates each SELECT item’s token count (̂𝑡𝑖), applies user-defined LIMIT caps (𝐿𝑖), and if total exceeds input budget (𝐵input) it compresses the largest items first (up to 50% reduction each) until within budget. This is analogous to relational query optimization minimizing I/O.
- **Core assumption**: Token allocation can be modeled as a resource allocation problem and content can be truncated or compressed without catastrophic loss of task-critical information.
- **Evidence anchors**: [abstract] "explicit token budgeting, an automatic optimizer"; [section 3.3] formal equation (1) and priority/compression logic; [section 6.1.4] Algorithm 1 implementation; [corpus] Corpus shows adjacent work on prompt optimization but no direct validation of SPL’s optimizer (weak evidence).
- **Break condition**: Critical factual details reside in large sources that get compressed away, or context sources are highly interdependent so truncation breaks necessary relationships.

### Mechanism 2: EXPLAIN Execution Plan Transparency
- **Claim**: Provides pre-execution visibility into token usage, cache behavior, and cost estimates, enabling developers to tune queries without incurring LLM call costs.
- **Mechanism**: Before execution, EXPLAIN runs the optimizer and renders a tree showing each source’s token allocation (absolute and percentage), cache status (hit/miss), compression ratios, and the estimated dollar cost based on the selected model’s pricing.
- **Core assumption**: Transparency improves developer decisions, and the cost model (input + output token pricing) is sufficiently accurate for model selection.
- **Evidence anchors**: [abstract] "EXPLAIN transparency analogous to SQL’s EXPLAIN ANALYZE"; [section 4.6] full EXPLAIN output specification; [section 8.4] example plan; [corpus] No neighboring papers implement a similar pre-execution inspection (corpus not applicable).
- **Break condition**: Token estimation errors (e.g., model-specific tokenizer quirks) produce misleading allocations or costs; dynamic pricing changes make cost estimates stale.

### Mechanism 3: Logical Chunking via CTEs (Declarative Map-Reduce)
- **Claim**: For documents exceeding a single context window, splitting the work into k independent CTEs reduces transformer attention compute from O(N²) to O(N²/k) and allows the same script to run in parallel on cloud or sequentially on local hardware at zero marginal cost.
- **Mechanism**: The query defines k CTEs each processing one chunk (Map phase). Each CTE’s output is limited; the outer GENERATE synthesizes the chunk results (Reduce phase). Because each chunk of size N/k has quadratic attention cost (N/k)², total becomes k·(N/k)² = N²/k.
- **Core assumption**: The document can be split into semantically coherent chunks whose individual summaries retain sufficient information for accurate final synthesis.
- **Evidence anchors**: [abstract] "Logical Chunking via CTEs reduces attention complexity from O(N²) to O(N²/k)"; [section 9.3] Map-Reduce formulation; [appendix C] experiment with "Attention Is All You Need"; [corpus] Corpus contains efficient Transformer research but does not address declarative chunking (no direct evidence).
- **Break condition**: The document requires cross-chapter context (e.g., argument builds across sections), causing the Reduce step to lose coherence; or chunk size becomes so small that summaries omit essential details.

## Foundational Learning

### SQL and Declarative Query Languages
- **Why needed here**: SPL’s syntax (SELECT, FROM, WHERE, CTEs) and mental model are intentionally parallel to SQL; without this background, the conceptual separation of resource allocation and generation is obscure.
- **Quick check question**: In SPL, why is SELECT used for context gathering while GENERATE triggers synthesis? How does this differ from SQL’s SELECT?

### Tokenization and Context Window Limits
- **Why needed here**: The token budget is the fundamental constraint; developers must understand how tokens are counted (model-specific tokenizers) and the context window size of their target LLM.
- **Quick check question**: Given total budget 8000 tokens, output budget 2000, and SELECT sources with raw estimates 3000, 2000, and 1500 tokens, what is the maximum buffer before compression must be applied?

### Retrieval-Augmented Generation (RAG)
- **Why needed here**: SPL embeds RAG as a first-class context source (rag.query); understanding why RAG injects external knowledge and how limits affect retrieval quality is key to effective queries.
- **Quick check question**: How does rag.query("search terms", top_k=5) differ from fetching the top-5 vector results manually? What does SPL automatically handle that manual RAG does not?

## Architecture Onboarding

### Component map
- **spl-llm package**: Lexer → Parser (recursive descent) → Semantic Analyzer → Optimizer (Algorithm 1) → Executor. Backends: LLMAdapters (Ollama, OpenRouter, Claude CLI, direct Cloud), MemoryStore (SQLite), VectorStore (FAISS/ChromaDB).
- **spl-flow package**: PocketFlow orchestration nodes (Text2SPLNode, ValidateSPLNode, ExecuteSPLNode, Sync/AsyncDeliverNode), plus CLI and Streamlit UI.
- **Data layer**: `.spl/` directory holds `memory.db` (key-value), `vectors.*` (vector DB), and client-side prompt cache with TTL.

### Critical path
1. Parse `.spl` → AST.  
2. Semantic analysis resolves names, checks budgets.  
3. Optimizer produces `ExecutionPlan` (ordered sources with allocations, compression decisions).  
4. Executor resolves sources in priority order: cache → memory → RAG → context, applying LIMIT truncation.  
5. Assemble final prompt and call LLMAdapter.generate().  
6. Store result if `STORE RESULT IN memory.key`, return `GenerationResult`.

### Design tradeoffs
- **Declarative vs. imperative**: SPL sacrifices flexibility for optimizability and transparency; complex procedural logic must be encapsulated in user-defined functions.
- **Compression strategy**: Greedy largest-first compression may truncate large but vital content; future versions may add priority-based protection.
- **Provider-agnostic adapters**: Simplify switching but may not expose all provider-specific features (e.g., Claude extended thinking requires direct adapter).
- **Parallel vs. sequential execution**: Logical chunking scripts run in parallel on cloud (asyncio) but sequentially on a single local GPU; same script works both ways.

### Failure signatures
- **Parse error**: Syntax issue; run `spl validate` to pinpoint.
- **Budget overflow after compression**: EXPLAIN shows many sources compressed >50%; increase budget or use logical chunking.
- **Repeated cache misses**: Cache TTL too short or query too dynamic; inspect `.spl/cache`.
- **Adapter failure** (e.g., Ollama down, model missing, OpenRouter rate limit): SPL-flow triggers fallback (Ollama → OpenRouter → retry); check logs for retry attempts.
- **Poor output quality**: Inspect EXPLAIN plan—perhaps over-compression or wrong model; adjust LIMITs or model selection.

### First 3 experiments
1. **EXPLAIN inspection**: `spl explain examples/simple_qa.spl`. Verify token allocation matches expectations before spending any tokens.
2. **RAG integration**: Ingest a few documents into `.spl/vectors`, then run a query with `rag.query("test")`. Observe cache behavior and token distribution.
3. **Logical chunking**: Take a long paper, split into 4 sections, write a Map-Reduce SPL script (Listing 12). Run with Ollama (sequential, zero cost) and with OpenRouter (parallel, fast) to compare speed and cost.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question**: Can SPL's over-budget compression strategy be improved from uniform proportional scaling to a semantically-aware compression (e.g., summarization via a cheaper model) that better preserves information utility?
- **Basis in paper**: [explicit] The authors state in Section 10.1 that "simple truncation remains the fallback for minor per-CTE budget overflows where full chunking is not warranted. Semantic compression—summarising over-budget content via a cheaper model rather than cutting it—is a natural next step."
- **Why unresolved**: The current size-driven greedy compression (Algorithm 1) does not consider content importance or semantic value, potentially discarding critical information from large but high-priority sources.
- **What evidence would resolve it**: Implement and evaluate a prototype summarization-based compression module (e.g., routing an over-budget CTE through a small model for summarization) against the current truncation method on information-retrieval benchmarks, measuring output quality degradation vs. token savings.

### Open Question 2
- **Question**: Does introducing a typed schema system for context sources (e.g., RAG document types, memory value types, function signatures) measurably improve developer productivity, static analysis error detection, and IDE tooling support in SPL?
- **Basis in paper**: [explicit] Section 10.1 lists "Limited type system" as a current limitation: "SPL does not yet provide typed schemas for context sources. Typed RAG document schemas, memory value types, and function signatures would enable richer static analysis and IDE tooling."
- **Why unresolved**: The grammar currently treats all context sources as untyped text blobs. This prevents compile-time checks (e.g., ensuring a `memory.get()` call retrieves a JSON object before being passed to a function expecting a specific field).
- **What evidence would resolve it**: Design a type system extension (e.g., `context.user_profile: UserProfile`), integrate it into the semantic analyzer, and run a user study measuring error rates and development time for tasks requiring schema consistency versus the current untyped approach.

### Open Question 3
- **Question**: How does SPL's declarative token budgeting and optimization perform across a broader range of LLM application tasks (e.g., code generation, multi-turn dialogue, complex multi-hop reasoning with tool use) compared to imperative frameworks?
- **Basis in paper**: [inferred] The evaluation in Section 8 is restricted to question-answering variants (Simple QA, RAG-augmented QA, Multi-step CTE). The authors acknowledge in Section 10.1 that "the current benchmark suite covers question-answering variants. Broader task diversity—code generation, multi-turn conversation, complex multi-hop reasoning, and agent tool-use—is the subject of ongoing evaluation work."
- **Why unresolved**: SPL's value proposition (budget visibility, automatic optimization) may behave differently for tasks with highly dynamic context needs (e.g., long coding sessions with many tool calls) or outputs with strict structural constraints.
- **What evidence would resolve it**: Construct a diverse benchmark suite (HumanEval for code, multi-turn dialogue datasets, agent benchmarks like WebArena) and implement corresponding SPL patterns (CTEs for tool results, memory for state). Compare against imperative LangChain/DSPy implementations on metrics like token efficiency, cost, and developer effort.

### Open Question 4
- **Question**: Can SPL's keyword-based Mixture-of-Models (MoM) routing be replaced or augmented with a learned, embedding-based router that handles ambiguous or cross-domain queries more robustly without adding classification latency?
- **Basis in paper**: [explicit] Section 9.2 describes the current heuristic: "The router infers task type from the GENERATE clause and system_role content... using rule-based keyword matching... This heuristic is transparent and predictable but brittle for ambiguous or mixed-domain queries. Embedding-based or learned routing... is identified as the primary improvement path." Section 10.1 also lists "Dynamic MoM routing" as a learned optimization direction.
- **Why unresolved**: The rule-based approach fails on queries where domain signals are subtle or conflicting (e.g., a request to "explain quantum mechanics in simple German" involves science and language). A lightweight classifier could provide better accuracy but must not add prohibitive overhead.
- **What evidence would resolve it**: Train a small embedding model (e.g., sentence-transformers) to classify GENERATE clause + system_role text into the routing table categories. Evaluate on a held-out set of ambiguous/mixed-domain SPL scripts, measuring routing accuracy and end-to-end latency/quality compared to the keyword heuristic.

### Open Question 5
- **Question**: Can the SPL grammar's structural guardrails be extended with a formal policy layer that enforces semantic safety (e.g., scanning literals for disallowed content, model allowlisting) without compromising the language's declarative simplicity?
- **Basis in paper**: [explicit] Section 10 (Safety and Prompt Injection Hardening) lists "Open problems" including "Semantic content filters on literals" and "Model allowlisting." The authors state: "SPL's validator checks syntactic correctness, not semantic safety. A script that passes ValidateSPLNode is structurally sound but may still encode harmful intent inside quoted string literals."
- **Why unresolved**: SPL's strength is a formal grammar that prevents certain injection classes, but it cannot inspect the semantic meaning of string literals (e.g., a `system_role("Ignore previous instructions...")` is syntactically valid but malicious). A policy layer is needed for compliance and security in production.
- **What evidence would resolve it**: Design a policy API (e.g., `policy_engine.validate(script)`) that hooks into the semantic analyzer to inspect literals and model names against configured rulesets (regex filters, allowlists). Demonstrate on a corpus of adversarial SPL scripts (e.g., attempts to override `system_role` via injected CTEs) that the policy layer successfully blocks malicious scripts while allowing legitimate ones.

## Limitations
- Token compression may lose critical information for large or interdependent sources.
- Token estimation accuracy across models is unverified, risking misleading EXPLAIN forecasts.
- Logical chunking's independence assumption often fails in real documents, degrading output quality.
