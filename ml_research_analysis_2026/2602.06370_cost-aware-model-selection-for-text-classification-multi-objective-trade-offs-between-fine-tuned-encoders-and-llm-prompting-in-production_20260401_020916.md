# Cost-Aware Model Selection for Text Classification: Multi-Objective Trade-offs Between Fine-Tuned Encoders and LLM Prompting in Production

## Quick Facts
- **ArXiv ID:** 2602.06370
- **Source URL:** https://arxiv.org/abs/2602.06370
- **Reference count:** 40
- **Primary result:** Fine-tuned BERT-family encoders match or exceed LLM prompting accuracy while costing 1-2 orders of magnitude less and offering lower latency, making them the default efficient choice for production text classification.

## Executive Summary
This paper investigates model selection for fixed-label text classification in production environments, comparing fine-tuned encoder models (BERT family) against large language model (LLM) prompting (GPT-4o, Claude). Evaluating macro F1, inference latency, and monetary cost across four standard benchmarks, the study finds that fine-tuned encoders achieve comparable or superior accuracy (macro F1 ~94–99% vs. ~87–98% for LLMs) at dramatically lower cost ($5–10 vs. $200–2700 per 1M requests) and latency (p50 <200ms vs. >300ms for LLMs). Pareto analysis confirms encoders dominate across realistic operational regimes, while LLM few-shot prompting increases token usage and cost without closing performance gaps. The results advocate for fine-tuned encoders as the efficient default, with LLMs better suited for complementary roles in hybrid systems.

## Method Summary
The authors conduct a controlled comparison on four English text classification datasets (IMDB, SST-2, AG News, DBPedia). For encoders, they fine-tune BERT, RoBERTa, and DistilBERT using AdamW for up to 4 epochs, selecting the best checkpoint via a generalization-aware score (validation F1 minus train-validation gap). The selected models are deployed as stateless services on Google Cloud Run (2 vCPU, 2 GiB) to measure end-to-end inference latency (p50/p95/p99) and cost. For LLMs, they use zero-shot and few-shot prompts via provider APIs with deterministic decoding (temperature=0), constraining outputs to single-digit labels. Token counts are logged to compute monetary cost based on January 2026 pricing. All metrics are aggregated across multiple runs.

## Key Results
- Fine-tuned encoders achieve macro F1 scores of 94–99%, comparable to or exceeding LLMs (87–98%).
- Encoders operate at 1–2 orders of magnitude lower cost: $5–10 vs. $200–2700 per 1M requests.
- Encoders exhibit substantially lower latency: p50 typically <200ms vs. >300ms for LLMs, with much lighter tails.
- Pareto analysis shows encoders dominate across operational regimes; few-shot LLM prompting increases cost without improving accuracy.
- A utility function that weights accuracy, cost, and latency further confirms encoder preference under realistic weightings.

## Why This Works (Mechanism)
Fine-tuned encoders dominate because they are specialized, compact models that directly produce classification outputs with minimal computation. In contrast, LLMs are general-purpose, large models that require extensive token generation (including prompt overhead) and incur higher network latency when accessed via APIs. The few-shot paradigm further increases token count without providing enough signal to close the accuracy gap, as encoders already learn task-specific representations from labeled data. Thus, for fixed-label tasks with sufficient training data, encoders offer a more favorable accuracy-cost-latency trade-off.

## Foundational Learning
- **Macro F1:** Balanced metric for multi-class classification. Why needed: robust measure of per-class performance, especially on imbalanced datasets. Quick check: confirm it is the average of per-class F1 scores.
- **Generalization Score (F1_val - |F1_train - F1_val|):** Used for model selection. Why needed: penalizes overfitting by considering the gap between training and validation performance. Quick check: ensure it selects the epoch with high validation F1 and small train-val gap.
- **Pareto Front:** Identifies non-dominated solutions in multi-objective optimization. Why needed: helps decision-makers understand trade-offs between accuracy, cost, and latency. Quick check: verify that no other model is better in all three objectives.
- **Token-Based Pricing:** LLM cost proportional to input/output tokens. Why needed: enables direct monetary cost estimation. Quick check: multiply token counts by provider rates.
- **Latency Percentiles (p50/p95/p99):** Characterize response time distribution. Why needed: tail latency (p99) is critical for user experience. Quick check: ensure enough samples (≥100) after warm-up.
- **Generalization Gap:** Difference between training and validation performance. Why needed: indicator of overfitting. Quick check: larger gap suggests overfitting.

## Architecture Onboarding
**Component Map (Encoder-based):**  
Dataset -> Encoder Fine-Tuning -> Model Checkpoint -> Cloud Run Deployment -> Client Request -> Latency/Cost Measurement

**Component Map (LLM-based):**  
Dataset -> Prompt Template -> API Call (GPT-4o/Claude) -> Response Parsing -> Latency/Cost Measurement

**Critical Path:**  
Encoders: request processing is a single forward pass through the model.  
LLMs: request involves network round-trip, server-side generation, and response parsing; network and generation time dominate.

**Design Tradeoffs:**  
- Encoders: higher upfront training cost, negligible inference cost and low latency; require task-specific labeled data.  
- LLMs: no training needed, high flexibility via prompting, but high per-request monetary cost, variable latency, and sensitivity to prompt engineering.

**Failure Signatures:**  
- Encoder: validation F1 stagnates or drops after epoch 1; high train-val gap indicates overfitting.  
- LLM: inconsistent label extraction due to formatting variations; cost overruns from excessive token usage; high tail latencies from API throttling or cold starts.

**First Three Experiments:**  
1. Fine-tune DistilBERT on a 10% subset of IMDB, compute macro F1 on validation, and verify generalization score peaks at epoch 1.  
2. Deploy the selected encoder to Cloud Run, send 100 warm requests, and record p50/p95/p99 latency; compare against paper values.  
3. Run zero-shot and few-shot prompts for SST-2 via GPT-4o API, capture raw outputs, parse labels, and compute mean F1 ± std and token counts; assess stability.

## Open Questions the Paper Calls Out
- **CoT Prompting:** Does chain-of-thought narrow the cost-accuracy gap? Not evaluated; would require measuring tokens, latency, cost for CoT and self-consistency.
- **Ambiguous/Open-World Tasks:** Do trade-offs hold for tasks with ambiguous labels or open-world reasoning? Only four fixed-label benchmarks tested; external validity uncertain.
- **Governance Metrics:** How to quantify reproducibility, auditability, interpretability and include them in model selection? Treated as constraints but lack operational metrics.
- **Hybrid Architectures:** What hybrid designs best leverage LLMs for knowledge generation and encoders for efficient classification? Unexplored design space.

## Limitations
- The referenced code repository is unverified, making exact replication of hyperparameters, prompts, and infrastructure uncertain.
- Latency measurements depend on Cloud Run configuration (region, concurrency, warm-up) and network conditions, limiting reproducibility of tail latencies.
- Evaluation covers only four English datasets and two proprietary LLMs; findings may not generalize to other languages, domains, or open-source models.
- LLM output parsing robustness and tokenization details can affect cost and accuracy calculations.

## Confidence
- **Accuracy (encoders vs. LLMs):** Medium – depends on fine-tuning randomness and dataset splits.
- **Efficiency (cost & latency):** Medium – sensitive to LLM token counts and infrastructure variability.
- **Pareto dominance & recommendation:** Low-Medium – derived from uncertain efficiency metrics and limited model set.
