# MoE-SpAc: Efficient MoE Inference Based on Speculative Activation Utility in Heterogeneous Edge Scenarios
## Quick Facts
- **arXiv ID:** 2603.09983
- **Source URL:** https://arxiv.org/abs/2603.09983
- **Reference count:** 40
- **Primary result:** Achieves a 42% improvement in tokens per second over the best speculative decoding baseline and a 4.04× speedup over all standard baselines on seven benchmarks using Qwen3-30B-A3B.

## Executive Summary
MoE-SpAc is a framework designed to enable efficient inference of Mixture-of-Experts (MoE) models on edge devices with limited GPU memory. It repurposes speculative decoding as a predictive sensor to estimate future expert demand, allowing dynamic partitioning of experts between GPU and CPU and asynchronous I/O management. The system consists of a Speculative Utility Estimator that converts binary activation signals into informative frequency values, a Heterogeneous Workload Balancer that solves an online integer optimization to set a utility threshold for expert placement, and an Asynchronous Execution Engine that unifies prefetching and eviction. Evaluated on seven diverse benchmarks with the Qwen3-30B-A3B model, MoE-SpAc delivers substantial speedups, demonstrating its effectiveness in overcoming memory and I/O bottlenecks.

## Method Summary
MoE-SpAc leverages speculative decoding to obtain a lookahead window of activation frequencies per expert. During the draft phase, multiple tokens are generated; the verification pass yields cumulative activation counts for each expert, producing a frequency map instead of a binary signal. These frequencies are mapped to discrete utility scores using an inertial transition mechanism with adaptive calibration to filter noise. For each Transformer layer, an online convex optimization determines a threshold τ that partitions experts into a GPU-resident hot set (high utility) and a CPU-executed cold set (low utility), balancing I/O latency and memory capacity. An asynchronous engine manages prefetching (based on descending utility) and eviction (based on ascending utility) using shared utility scores, overlapping I/O with draft computation. The implementation extends the llama.cpp backend and was evaluated with Qwen3-30B-A3B as the target model and Qwen3-4B-FP8 as the draft model.

## Key Results
- 42% improvement in tokens per second (TPS) over the best speculative decoding baseline.
- 4.04× average speedup over all standard (non-speculative) baselines.
- Consistent gains across seven benchmarks (MMLU-Pro, MT-bench, GSM8K, HumanEval, Alpaca, CNN/DailyMail, and QA).

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Speculative Decoding (SD) transforms low-information binary expert activation signals into informative frequency-valued signals, enabling robust utility estimation for memory management.
- **Mechanism:** During the draft phase, multiple tokens are generated and verified in parallel. The verification pass yields cumulative activation counts for each expert across the γ draft tokens, producing a frequency map fi,t ∈ [0, γ+1] instead of a binary {0,1}. This frequency directly indicates expert demand intensity over the near future context. The system maps these frequencies to discrete utility scores si,t using an inertial transition mechanism that only updates when fluctuations exceed adaptive boundaries, filtering noise while tracking trends.
- **Core assumption:** The draft model has a non-trivial acceptance rate α and is sufficiently aligned with the target model such that expert reuse across the speculation window occurs (a/b < Ω(γ,α), Appendix A). The activation frequencies evolve smoothly (bounded drift, Theorem 1), allowing inertial tracking.
- **Evidence anchors:**
  - [abstract] "SD transforms the low-information binary signals of autoregressive decoding into non-binary, informative signals for expert scheduling."
  - [section 2.3] Defines activation frequency fi,t for SD as in [0, γ+1] vs AR's {0,1}, and describes the estimation problem.
  - [corpus] Concurrent works (e.g., MoE-Spec, Speculative MoE) focus on SD for compute acceleration or expert budgeting, not repurposing it as a lookahead sensor for heterogeneous memory management.
- **Break condition:** If the acceptance rate α is very low (draft tokens frequently rejected) or draft length γ is mis-tuned, the speculative window provides little valid lookahead, and the frequency signal becomes sparse or noisy, degrading utility estimation.

### Mechanism 2
- **Claim:** A dynamic threshold τ, derived from solving an online integer optimization at each layer, partitions experts into GPU-resident "hot" and CPU-executed "cold" sets to balance heterogeneous compute loads and hide I/O.
- **Mechanism:** The balancer models the problem as minimizing |Tcpu - Tgpu|, where Tcpu depends on the ratio rc(τ) of activated experts offloaded to CPU, and Tgpu depends on the ratio rg(τ) of de-duplicated experts processed on GPU. These ratios are estimated from historical data during a warm-up phase (Figure 9a shows stability). The optimization is subject to I/O prefetching time ≤ available window (draft time + computation) and VRAM capacity constraints. Because f(τ) is convex over discrete τ ∈ [1,K], the optimal τ* is found analytically at the intersection point or boundary of the feasible set.
- **Core assumption:** The ratios rc(τ) and rg(τ) are stable and predictable for a given layer and workload pattern, allowing offline estimation and online application. The system can accurately measure remaining VRAM and I/O bandwidth.
- **Evidence anchors:**
  - [abstract] "solves online integer optimization to dynamically partition experts between GPU and CPU based on real-time I/O and memory constraints."
  - [section 3.3] Formulates the optimization problem (Eq. 9-12) and notes the convexity and O(1) solution.
  - [corpus] HybriMoE uses a greedy algorithm without theoretical optimization; MoE-SpAc introduces a principled convex formulation.
- **Break condition:** A sudden, large shift in activation distribution (e.g., new input domain) invalidates the stored rc/rg estimates, making τ suboptimal and potentially causing I/O congestion or GPU underutilization.

### Mechanism 3
- **Claim:** An asynchronous execution engine unifies prefetching and eviction under the same utility metric, masking I/O latency by pipelining transfers during the draft phase and preventing cache thrashing.
- **Mechanism:** Prefetching uses a multi-level priority queue indexed by utility si,t, processing requests for experts with si,t ≥ τ in descending utility order during the draft model's execution. Eviction uses a state-ordered pool (Red-Black tree) of GPU-resident experts indexed by si,t; when τ updates, experts with si,t < τ are evicted in O(log N). Both operations share the same utility score, ensuring consistent policy.
- **Core assumption:** The draft phase's computation time is sufficient to prefetch the necessary experts for the upcoming verification phase (Eq. 10: T_io · n(τ) ≤ T_total + γ·T_draft/L_target). The utility scores are stable enough between steps that prefetching based on current estimates remains valid.
- **Evidence anchors:**
  - [abstract] "unifying prefetching and eviction in the same utility space."
  - [section 3.4] Describes the priority queue for prefetching and state-ordered pool for eviction, both driven by si,t.
  - [corpus] Existing systems like Fiddler and HybriMoE decouple prefetching and caching, leading to suboptimal load balancing [16].
- **Break condition:** If I/O bandwidth is severely limited or the number of prefetches n(τ) is large, T_io · n(τ) may exceed the draft time window, causing pipeline bubbles and stalling verification.

## Foundational Learning
### Concept: Speculative Decoding (SD)
- **Why needed here:** SD provides the lookahead window for estimating expert demand. Without SD, activation signals are binary and uninformative, making utility estimation unreliable.
- **Quick check question:** How does the acceptance rate α and draft length γ affect the information gain from SD for expert scheduling?

### Concept: MoE Activation Sparsity
- **Why needed here:** MoE models activate only a subset of experts per token (Top-k routing). This sparsity is why offloading is possible—most experts reside on CPU. Understanding activation patterns (which experts are hot/cold) is essential for scheduling.
- **Quick check question:** In the Top-k routing equation (Section 2.2), what does the gating weight g_i(h) represent, and why is it sparse?

### Concept: Heterogeneous Offloading
- **Why needed here:** Edge devices have limited GPU VRAM. Offloading infrequently used experts to CPU memory is necessary but introduces I/O bottlenecks. The framework must decide which experts to keep on GPU.
- **Quick check question:** What are the two main strategies for handling CPU offloading in MoE inference, and what are their typical drawbacks?

## Architecture Onboarding
- **Component map:** Speculative Utility Estimator -> Heterogeneous Workload Balancer -> Asynchronous Execution Engine (integrates with llama.cpp backend).
- **Critical path:** Draft tokens generated → verification pass yields activation frequencies per layer → utility estimator updates scores per expert → balancer computes layer-specific τ → execution engine prefetches hot experts (si,t ≥ τ) during draft, evicts cold ones (si,t < τ) → target model verification uses GPU-resident hot experts and CPU cold experts → repeat.
- **Design tradeoffs:** 
  - Utility upper bound K: Smaller K reduces computation but may group experts imprecisely; Figure 5 (right) shows K=4 optimal.
  - Cache ratio: Allocating VRAM to draft model vs expert cache; MoE-SpAc tolerates lower expert cache (17%) because SD masks I/O, while baselines need more cache to avoid stalls.
  - Online estimation vs warm-up: rc(τ), rg(τ) estimated once during warm-up; if workload shifts, performance degrades until re-estimation.
- **Failure signatures:** 
  - High TPS drop when removing speculative utility estimator (Table 4: w/o SpecUE ~30% lower TPS).
  - OOM when expert cache ratio too high due to draft model memory (Figure 5 left: OOM at 21% cache).
  - Increased latency if prefetching time exceeds draft window (violates Eq. 10), visible in pipeline profiling.
- **First 3 experiments:**
  1. **Overall performance comparison:** Run MoE-SpAc and all baselines (llama.cpp, HybriMoE, etc.) on seven benchmarks with Qwen3-30B-A3B. Measure TPS and latency. Expected: MoE-SpAc achieves 4.04× average speedup over standard baselines and 42% over best SD-based baseline (llama.cpp-w/SD).
  2. **Information gain from SD:** Plot hot-or-cold prediction accuracy over steps for MoE-SpAc (SD) vs HybriMoE (AR) on MMLU-Pro (Figure 4). Expected: MoE-SpAc reaches ~0.85 accuracy quickly, showing SD provides stable frequency signals; AR accuracy hovers lower.
  3. **Ablation study:** Disable each component (SpecUE, AdaBC, HetWB, SG-Prefetcher, SG-Evictor, SD) and measure TPS/latency (Table 4). Expected: Removing SpecUE or SG-Prefetcher/Evictor causes major drop; removing AdaBC or HetWB causes moderate drop; removing SD (AR mode) drops to baseline level.

## Open Questions the Paper Calls Out
### Open Question 1
**Question:** Can MoE‑SpAc’s speculative utility estimation be effectively generalized to emerging sparse architectures such as Mixture‑of‑Lookup‑Experts (MoLE)?
**Basis:** Explicitly stated in the conclusion and Appendix H as a future research direction.
**Why unresolved:** MoLE introduces fundamentally different expert access patterns (discrete lookups), and it is unclear whether the inertial transition and adaptive calibration mechanisms designed for smooth activation frequencies remain valid.
**What evidence would resolve it:** A reimplementation of MoE‑SpAc on a MoLE‑based model, measuring utility score continuity, prediction accuracy, and end‑to‑end tokens per second compared to standard MoE.

### Open Question 2
**Question:** How can the heterogeneous workload balancer be extended to jointly consider KV cache offloading, thus optimizing both expert and KV movement?
**Basis:** Mentioned in Appendix H as an open enhancement to the current formulation.
**Why unresolved:** The existing integer program optimizes prefetch/eviction solely based on expert I/O and memory; incorporating KV cache adds new temporal and size constraints that may change the structure of the optimal solution.
**What evidence would resolve it:** A modified balancer that models KV cache occupancy as an additional constraint, validated via simulation or prototype on a target model, reporting TPS and memory overhead improvements.

### Open Question 3
**Question:** Does MoE‑SpAc retain its performance advantages when the separate draft model is replaced by a self‑speculative decoding scheme?
**Basis:** The authors note in the limitations that MoE-SpAc relies on speculative decoding and identify self‑speculation as an orthogonal approach that could reduce memory overhead but remain unintegrated.
**Why unresolved:** Self‑speculation alters the source and distribution of speculative tokens, potentially affecting the frequency‑based utility estimation and the fault‑tolerance assumptions derived from separate draft‑target alignment.
**What evidence would resolve it:** An implementation of self‑speculative decoding within the MoE‑SpAc pipeline, comparing TPS, utility prediction accuracy, and speedup against the standard draft‑target configuration across multiple benchmarks.

## Limitations
- Exact model checkpoints (Hugging Face repositories, commits, quantization details) and conversion steps for Qwen3-30B-A3B and Qwen3-4B-FP8 are unspecified, hindering precise replication.
- Benchmark evaluation details (prompt templates, sampling parameters) are omitted, risking inconsistencies in reported metrics.
- The workload balancer relies on static expert ratio estimates from a warm-up phase; sudden domain shifts may degrade performance until re-estimation.
