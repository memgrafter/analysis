# SciTaRC: Benchmarking QA on Scientific Tabular Data that Requires Language Reasoning and Complex Computation

## Quick Facts
- **arXiv ID:** 2603.08910
- **Source URL:** https://arxiv.org/abs/2603.08910
- **Reference count:** 17
- **Primary result:** State-of-the-art models fail on at least 23% of tasks; frontier models like GPT-5 achieve 76.8% accuracy, with a universal "execution bottleneck" identified as the dominant failure mode.

## Executive Summary
SciTaRC is a new benchmark of 371 expert-authored questions that demand deep language reasoning and complex computation over scientific tables presented in raw LaTeX formats. Evaluating 24 models zero-shot reveals that even the most advanced systems, such as GPT-5, struggle, achieving only 76.8% accuracy. The core finding is that the primary bottleneck is not in generating a correct reasoning plan but in faithfully executing it—a failure mode termed "execution fidelity." This challenges assumptions that code-based methods (Program-of-Thought) are inherently superior for tabular reasoning; instead, they prove brittle on heterogeneous scientific tables, while natural language reasoning (Chain-of-Thought) shows greater robustness.

## Method Summary
The benchmark comprises questions over scientific tables sourced from AI-domain arXiv papers, each with a validated gold answer and a manually written pseudo-code reasoning plan. Evaluation is conducted in a zero-shot setting using two main paradigms: Chain-of-Thought (CoT) for generalist language models and Program-of-Thought (PoT) for code-optimized models, with specific prompt templates provided. A key ablation study decouples planning from execution by comparing three conditions: Direct (model handles both), Autonomous (model generates and follows its own plan), and Oracle (provided with the gold plan). Model outputs are scored by an LLM-as-a-Judge (Llama-3.3-70B-Instruct) against gold answers using strict criteria. Complexity metrics (e.g., table size, plan length) are computed post-hoc to stratify performance.

## Key Results
- State-of-the-art models fail on at least 23% of tasks; frontier models like GPT-5 achieve 76.8% accuracy, while Llama-3.3-70B fails 65.5%.
- Execution fidelity, not strategy formation, is the dominant failure mode across all models when provided with oracle plans.
- Program-of-Thought (PoT) performs substantially worse than Chain-of-Thought (CoT) on raw scientific tables due to brittleness with heterogeneous structures.

## Why This Works (Mechanism)
### Mechanism 1: Execution Fidelity Bottleneck
- **Claim:** The dominant failure mode for scientific table QA is **execution fidelity**, not strategy formation.
- **Mechanism:** When provided with an oracle (gold-standard) reasoning plan, models still fail to answer correctly at high rates. This indicates the bottleneck is in the faithful, stepwise implementation of a given plan—handling table lookups, numerical operations, and conditional logic—rather than in generating the plan itself.
- **Core assumption:** Decoupling planning from execution isolates the source of error. If execution were not the bottleneck, oracle plans would close the performance gap to near-perfect accuracy.
- **Evidence anchors:**
  - [abstract]: "Separating planning from execution shows execution fidelity, not strategy formation, is the dominant failure mode."
  - [section 5.3]: "Execution Failure (Red)—failure despite a correct Oracle Plan—dominates across all models, consistently exceeding Plan Failure (Yellow)."
  - [corpus]: Weak/absent. Neighboring papers (e.g., *Chain-of-Table*, *How Robust are the Tabular QA Models...*) diagnose table reasoning challenges but do not isolate execution fidelity via oracle plans.
- **Break condition:** If oracle planning yielded accuracy near 100% for all models, the execution bottleneck hypothesis would be falsified.

### Mechanism 2: Compliance Cost of Explicit Planning
- **Claim:** Explicit planning imposes a **compliance cost** that harms performance on simpler tasks for generalist language models.
- **Mechanism:** The cognitive overhead of adhering to a rigid, external pseudo-code plan (even a correct one) disrupts the model's intrinsic, more fluid reasoning process. This overhead is particularly damaging for questions where the model's native reasoning is already sufficient (easier questions), causing regressions.
- **Core assumption:** Model reasoning is not optimally expressed via enforced syntactic structures; forcing compliance can degrade performance on tasks that do not require such scaffolding.
- **Evidence anchors:**
  - [section 5.3]: "generalist language models consistently regress (-5.4% to -10.0%)... the overhead of strictly following a rigid script outweighs its benefit for models whose intrinsic reasoning already suffices."
  - [figure 9]: Shows net regression (rightward red bars) on easier questions for language models when moving from Direct to Autonomous planning.
  - [corpus]: Weak/absent. Neighbors discuss multi-agent or neuro-symbolic planning but not the specific negative transfer of planning scaffolds on easy tasks.
- **Break condition:** If autonomous planning uniformly improved performance across all difficulty levels for generalist models, the compliance cost hypothesis would be weakened.

### Mechanism 3: Brittleness of Program-of-Thought on Raw Tables
- **Claim:** **Program-of-Thought (PoT) is brittle** on raw, heterogeneous scientific tables compared to natural language reasoning (CoT).
- **Mechanism:** Generating executable Python code directly over LaTeX-serialized scientific tables fails frequently due to parsing ambiguities, non-standard formatting, and complex domain-specific notation. The code generation process introduces failure points (syntax errors, incorrect table indexing, misreferenced columns) that natural language reasoning, being more robust to noise, does not face.
- **Core assumption:** The brittleness stems from the zero-shot code generation's inability to robustly parse and manipulate irregular scientific table structures from raw text.
- **Evidence anchors:**
  - [section 4.2]: "Contrary to the expectation that tables are best handled by code, Program-of-Thought (PoT) performs substantially worse than natural language reasoning... DeepSeek-V3.2 drops from 69.3% (CoT) to 36.1% (PoT)... Code appears brittle when applied to the ad-hoc, heterogeneous structures of scientific tables."
  - [figure 4]: Shows PoT accuracy degrades more steeply with increasing table structural size (Scell) compared to CoT.
  - [corpus]: Partial support. Neighbors like *How Robust are the Tabular QA Models...* and *RUST-BENCH* note challenges with real-world/heterogeneous tables but do not specifically contrast PoT vs. CoT brittleness.
- **Break condition:** If PoT and CoT showed similar performance curves across table complexity metrics (Scell, Stok), the brittleness hypothesis would be challenged.

## Foundational Learning
- **Concept: Scientific Table Complexity & Heterogeneity**
  - *Why needed here:* Scientific tables are not clean CSVs; they come as LaTeX with multi-row/column headers, merged cells, embedded formulas, and domain-specific notations. Models must interpret this messy, non-uniform structure.
  - *Quick check question:* What are three specific formatting elements in a LaTeX science table (e.g., `\multicolumn`, `\hline`, nested tables) that could break a simple Python `pandas.read_csv()` approach?
- **Concept: Multi-step Reasoning Decomposition**
  - *Why needed here:* Questions require chains of retrieval, comparison, and arithmetic operations (e.g., "compute average, then find min across models"). Understanding the need to break a question into atomic, ordered operations is fundamental.
  - *Quick check question:* For the example question in Figure 1, list the high-level sequence of operations (e.g., 1. Filter for Qwen2-Audio rows, 2. Group by language, 3. Average settings, 4. Identify min language, 5. Repeat for other models).
- **Concept: Zero-shot Evaluation Paradigm**
  - *Why needed here:* All reported results are zero-shot. This tests a model's inherent, pre-trained knowledge and reasoning without adaptation via examples. The observed failures are thus attributed to core capability gaps, not lack of fine-tuning on this specific format.
  - *Quick check question:* How would you expect results to change if the models were provided with 3-5 exemplars (few-shot) from SciTaRC? What would that imply about the nature of the failure?
- **Concept: Error Taxonomy for Table QA**
  - *Why needed here:* The paper categorizes failures into Comprehension, Localization, Calculation, and Memory errors. This taxonomy is critical for diagnosing whether a model's weakness lies in understanding the question, finding the right data, performing operations, or tracking state.
  - *Quick check question:* Given a model's failed reasoning trace where it misidentifies a column header but performs arithmetic correctly, which error category should be assigned?
- **Concept: Planning vs. Execution Decoupling**
  - *Why needed here:* The core experimental design separates the generation of a reasoning plan (strategy) from its implementation (execution). This allows isolating whether failures occur in devising a correct approach or in carrying it out faithfully.
  - *Quick check question:* In the Oracle planning condition, what does a failure imply about the model's capabilities compared to a failure in the Direct condition?

## Architecture Onboarding
- **Component map:** Dataset (LaTeX tables, questions, gold plans) -> Evaluation Harness (LLM judge) -> Model Pipeline (CoT/PoT inference with planning conditions) -> Complexity Analyzer (post-hoc metrics)
- **Critical path:** Data Preparation → Baseline Model Evaluation (CoT/PoT) → Planning Ablation Study → Complexity Stratification → Error Analysis → Diagnostic Reporting.
- **Design tradeoffs:**
  - *Zero-shot vs. Fine-tuning:* The benchmark diagnoses inherent capability, but limits applicability to tractable improvement via prompting/planning. Fine-tuning might close execution gaps.
  - *LLM-as-a-Judge vs. Executable Oracles:* The LLM judge is scalable but can be lenient or biased; an executable program verifier (like unit tests) would be more rigorous for calculation-heavy answers but harder to design for free-form text.
  - *Raw Tables vs. Preprocessed:* Evaluating on raw LaTeX (as done) tests true robustness but penalizes code methods. Pre-parsing tables would level the field for PoT but reduce ecological validity.
- **Failure signatures:**
  - High **Comprehension Error** rate (~73%): Model misinterprets question intent or table semantics.
  - PoT **catastrophic collapse** on large/heterogeneous tables (e.g., >400 cells, >2k tokens).
  - **Negative Gain** from Autonomous planning on easier questions for CoT models.
  - Minimal improvement from Oracle plans for frontier models, indicating a hard ceiling.
- **First 3 experiments:**
  1. **Baseline Replication:** Run the full 24-model zero-shot CoT/PoT evaluation on the test set. Verify the main leaderboard results (e.g., GPT-5 ~76.8%, Llama-3.3-70B ~34.5%) and the PoT degradation pattern.
  2. **Planning Ablation:** For 2-3 models (one code-focused, one language-focused), run the Direct, Autonomous, and Oracle conditions. Plot the Gain Curves and compute the "Execution Gap" (`Oracle - Autonomous`). Expect execution failures to dominate.
  3. **Error Taxonomy Application:** Manually review a sample of DeepSeek-V3.2's incorrect answers. Categorize each as Comprehension, Localization, Calculation, or Memory. Confirm Comprehension is the primary error (~70%), then Calculation (~15-20%).

## Open Questions the Paper Calls Out
- **Open Question 1:** How can we improve faithful execution of reasoning plans in neuro-symbolic systems for scientific table QA? *Basis in paper:* [explicit] Conclusion states that "improving faithful execution over structured data remains a central challenge for future agentic and neuro-symbolic systems." *Why unresolved:* Models exhibit an execution bottleneck; even when provided with correct strategies, they fail to implement them accurately, indicating a gap in stepwise fidelity. *What evidence would resolve it:* Develop and evaluate model architectures with enhanced state tracking, error correction mechanisms, or training objectives that explicitly enforce plan adherence, measuring success through plan-step accuracy and execution trace analysis.
- **Open Question 2:** How can program-of-thought methods be made robust to the heterogeneous structures and raw LaTeX representations of scientific tables in zero-shot settings? *Basis in paper:* [explicit] Abstract and Section 4.2 report that "code-based methods prove brittle on raw scientific tables" and that PoT performance degrades drastically compared to CoT. *Why unresolved:* The brittleness suggests current code generation models cannot reliably parse and operate on unstructured scientific tables without specialized preprocessing or adapted code generation. *What evidence would resolve it:* Introduce domain-specific table parsers, pre-processing pipelines that convert LaTeX to structured formats, or hybrid neuro-symbolic code generators; assess robustness across varied table layouts and notations.
- **Open Question 3:** What architectural or training modifications can reduce initial comprehension errors in language models processing scientific tables? *Basis in paper:* [explicit] Error analysis (Section 6) shows that 73% of DeepSeek-V3.2's failures stem from "Comprehension" errors, i.e., misunderstanding question intent or table semantics. *Why unresolved:* The high proportion indicates models lack deep understanding of scientific conventions, domain-specific notation, and implicit assumptions in tables. *What evidence would resolve it:* Pre-train on diverse scientific tables, design prompting strategies that explicitly extract table semantics, or build multimodal architectures that jointly reason over table structure and textual context; evaluate via ablation on comprehension-focused diagnostic sets.
- **Open Question 4:** How can we expand expert-annotated scientific table QA benchmarks to multiple domains while maintaining high-quality verification and scalability? *Basis in paper:* [explicit] Limitations section notes that "tables are sourced exclusively from AI-domain arXiv papers" and that the current scale (370 questions) is limited by rigorous expert verification. *Why unresolved:* Domain-specific tabular conventions may affect generalizability; a larger, cross-domain benchmark is needed to validate whether findings hold across sciences. *What evidence would resolve it:* Establish collaborations with domain experts in fields like biology, finance, or medicine; develop scalable annotation tools with built-in review workflows; construct and release multi-domain test sets with consistent complexity metrics.

## Limitations
- The exact table serialization format (linearization of LaTeX headers, merged cells, math notation) is unspecified, critically impacting PoT performance and blocking faithful replication.
- Gold answer computation scripts for complex numeric/relational questions are unreleased, preventing exact validation of results and error attribution.
- The LLM-as-a-Judge evaluation lacks quantifiable error bounds; no executable oracle verifier was used for calculation-heavy answers, introducing potential scoring bias.

## Confidence
- **Execution Fidelity Bottleneck:** High. Oracle-plan ablation robustly isolates execution failure as dominant across models.
- **Compliance Cost of Planning:** Medium. Observed regression on easy tasks is correlational; no controlled test of "rigid script" overhead vs. intrinsic reasoning fluency.
- **Program-of-Thought Brittleness:** Medium. Strong PoT vs. CoT performance gap on complex tables is shown, but parsing-specific failure modes not directly logged.

## Next Checks
1. **Serialization impact test:** Re-run PoT on a subset with standardized CSV conversion vs. raw LaTeX; measure accuracy delta to quantify brittleness source.
2. **Judge validation:** Sample 100 scored numeric answers; recompute correctness via deterministic script (±1 tolerance) and measure LLM-judge agreement.
3. **Execution fidelity probing:** For failed Oracle-plan cases, manually execute the pseudo-code on the table; categorize residual failures as lookup, arithmetic, or conditional logic errors.
