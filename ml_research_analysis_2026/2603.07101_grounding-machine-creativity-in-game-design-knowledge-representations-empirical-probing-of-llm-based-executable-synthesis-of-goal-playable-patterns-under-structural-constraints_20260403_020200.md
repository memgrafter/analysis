# Grounding Machine Creativity in Game Design Knowledge Representations: Empirical Probing of LLM-Based Executable Synthesis of Goal Playable Patterns under Structural Constraints

## Quick Facts
*   **arXiv ID:** 2603.07101
*   **Source URL:** https://arxiv.org/abs/2603.07101
*   **Reference Count:** 40
*   **Primary Result:** LLM-based synthesis of executable Unity game code from goal patterns achieves zero compilation success (pass@k = 0.0) across all tested intermediate representation (IR) conditions and models, with more detailed IRs causing near-universal compilation timeouts.

## Executive Summary
This paper investigates the automated conversion of structured game design knowledge—specifically, *goal playable patterns*—into executable Unity game code, framing it as a constrained creative synthesis problem. The authors compare a direct large language model (LLM) generation approach (natural language to C#) against pipelines conditioned on a human-authored, Unity-specific intermediate representation (IR). Testing across 26 pattern instantiations with two open-source code models, they find no generated code successfully compiles. The study reveals a critical trade-off: while a detailed IR schema eliminates certain architectural errors, it systematically induces code complexity that exhausts the compiler's time budget, leading to 96–99% timeouts. A failure analysis distinguishes between *grounding* failures (missing project/engine references) and *hygiene* failures (syntactic/formatting errors), identifying unresolved project-level and engine-level grounding as the primary bottleneck.

## Method Summary
The study empirically probes the constrained synthesis of Unity C# code from goal pattern descriptions. The core method compares four generation configurations: a direct `NL→C#` baseline and three `NL→C#` pipelines conditioned on a human-authored IR schema with varying detail (`free`, `min`, `full`). For each of 26 goal pattern instantiations (e.g., "Ownership", "Stealth"), the pipeline generates C# code using two open-source models (DeepSeek-Coder-V2-Lite-Instruct, Qwen2.5-Coder-7B-Instruct). Generated code is written as assets into a prepared Unity project (version 2022.2.23f1) and evaluated via a headless batch compilation with a 120-second timeout. Primary success is binary compilation viability (M1). Failed compilations are diagnosed by parsing compiler error codes and categorizing them as either *grounding* failures (missing references to project-specific types or Unity APIs) or *hygiene* failures (syntax and formatting errors).

## Key Results
*   **Zero Compilation Success:** Across all 26 patterns, two models, and four generation configurations, not a single generated code snippet compiled successfully (pass@k = 0.0).
*   **IR Detail Induces Timeouts:** Increasing the constraint strictness and detail of the IR schema (from `free` to `full`) leads to a monotonic and drastic increase in compilation timeouts, rising from 37–51% to 96–99%, indicating generated code becomes too complex to compile within the budget.
*   **Persistent Grounding Bottleneck:** The dominant failure mode across all conditions is *grounding*, manifested as compiler errors like `CS0246` (type not found) and `CS0234` (namespace missing), pointing to unresolved references to project-specific entities and Unity engine APIs.

## Why This Works (Mechanism)

### Mechanism 1: IR as a Representational Scaffold
*   **Claim:** The Intermediate Representation (IR) acts as a representational scaffold that transfers Unity-specific architectural conventions from human-authored reference implementations to the LLM-generated code.
*   **Mechanism:** The IR explicitly encodes stable project-level structural knowledge (object IDs, prefab instances, script class names) and semantic gameplay relations. By conditioning generation on this structured schema, the model is guided away from inventing placeholder structures and toward the concrete implementation patterns of the target Unity project.
*   **Core Assumption:** The architectural conventions for Unity projects (wiring GameObjects, Components, Prefabs) are sufficiently stable across the 26 patterns to be captured in a single frozen schema.
*   **Evidence Anchors:**
    *   [abstract] "IR-conditioned generation provides a principled representational interface for knowledge injection, encoding both project-level structural conventions and goal-pattern semantic knowledge."
    *   [section] "Under IR-conditioned configurations... architectural grounding failures (CS0115) are nearly eliminated."
*   **Break Condition:** The mechanism fails if the IR's structural layer is inexpressive for a pattern's unique runtime needs, or if generated code complexity exceeds the compiler's resource budget.

### Mechanism 2: IR Detail vs. Compilation Tractability Trade-off
*   **Claim:** Increasing the detail and constraint strictness of the IR schema induces a systematic trade-off: improved structural conformity at the cost of generated code complexity, leading to compilation timeouts.
*   **Mechanism:** A more detailed IR (`full` vs. `min`) provides richer instantiation knowledge but instructs the model to produce syntactically longer and more interconnected C# code (e.g., fully enumerated object/script lists with runtime parameters). This increased complexity exhausts Unity's batch compilation time budget (120s), causing timeouts that rise monotonically with IR detail.
*   **Core Assumption:** The LLM's output length and structural density scale predictably with the detail of the conditioning IR schema.
*   **Evidence Anchors:**
    *   [abstract] "A sharp increase in compilation timeouts occurs with more detailed IRs (up to 96–99%), indicating generated code becomes too complex to compile within the time budget."
    *   [section] "The monotonic increase... suggests that IR-conditioned generation produces structurally more complex C# outputs that systematically exhaust the compilation budget."
*   **Break Condition:** The mechanism fails if code complexity does not scale with IR detail, or if timeout thresholds are adjusted.

### Mechanism 3: Grounding vs. Hygiene Taxonomy
*   **Claim:** The proposed failure taxonomy (Grounding vs. Hygiene) effectively localizes the failure locus within the creative synthesis pipeline, separating knowledge-deficit errors from syntactic/formatting errors.
*   **Mechanism:** By analyzing specific C# compiler error codes from failed builds, failures are categorized. *Grounding failures* (e.g., `CS0246`) indicate references to absent project/engine entities—a knowledge gap. *Hygiene failures* (e.g., `CS0101`) indicate corrupted output structure—a generation control issue.
*   **Core Assumption:** Compiler error codes provide a reliable, granular proxy for diagnosing the underlying generation deficiency.
*   **Evidence Anchors:**
    *   [abstract] "We propose grounding and hygiene failure modes... identifying structural and project-level grounding as primary bottlenecks."
    *   [section] "Inspection of the error messages reveals two distinct failure types... We term these grounding failures... We term these hygiene failures."
    *   [corpus] Table 1 shows the full distribution of 41 error codes mapped to these categories.
*   **Break Condition:** The taxonomy breaks down if error codes become ambiguous or if failures arise from factors orthogonal to knowledge vs. syntax (e.g., semantic logic errors that still compile).

## Foundational Learning
*   **Concept: Gameplay Design Patterns & Goal Patterns**
    *   **Why needed here:** The entire synthesis task operationalizes abstract pattern descriptions into concrete Unity implementations. Understanding that patterns are relational, mid-level design knowledge is crucial to grasp what the IR encodes.
    *   **Quick check question:** What is the key difference between a general gameplay pattern and a *goal* pattern, and why is the latter chosen as the testbed?
*   **Concept: Unity Engine Architecture (Component Model)**
    *   **Why needed here:** "Grounding" failures are specific to Unity's conventions (MonoBehaviour scripts as components, Prefab instances, serialized fields). Understanding that a `GameObject` needs a specific `MonoBehaviour` attached explains errors like `CS0115`.
    *   **Quick check question:** Why would generating a C# class that inherits from `MonoBehaviour` but not attaching it to a `GameObject` in the scene cause a specific compiler or runtime error?
*   **Concept: Intermediate Representation (IR) in Code Generation**
    *   **Why needed here:** The core methodological innovation is using a human-authored, engine-specific IR to bridge design knowledge and executable code. This requires understanding that an IR is a *controlled interface* that externalizes stable knowledge to reduce the model's inference burden.
    *   **Quick check question:** What is the key trade-off introduced by adding a detailed IR conditioning step to an LLM code generation pipeline?

## Architecture Onboarding
Pattern Repository -> IR Extractor & Schema -> LLM Inference Pipeline -> Code Sanitiser & Asset Writer -> Unity Batch Compiler & Replayer -> Analysis Engine
*   **Critical Path:** Pattern Selection -> IR Generation (if conditioned) -> LLM Inference -> Sanitization -> Unity Batch Compilation -> Log Analysis -> Result Aggregation. The failure point is almost always at the Compilation stage.
*   **Design Tradeoffs:**
    *   **IR Detail vs. Compilation Tractability:** Richer schema fields improve structural grounding but cause timeout-dominant failures due to output complexity.
    *   **Human Authored IR vs. Scalability:** The IR must be human-authored per pattern (or via bootstrapped extraction), limiting immediate scalability but providing high-quality knowledge.
    *   **Compiler-Ground Truth vs. Semantic Fidelity:** Evaluation uses *compilation success* as a necessary but insufficient condition. A compiled artifact may still be semantically incorrect for the pattern.
*   **Failure Signatures:**
    *   **G-Failure Dominant:** High rates of `CS0246` (type not found), `CS0234` (namespace missing), `CS0122` (inaccessible member). Indicates missing project-specific or engine API knowledge.
    *   **H-Failure Dominant:** High rates of `CS0101` (duplicate definition), `CS1029` (marker comment leakage), `CS1001/CS1003` (syntax errors). Indicates unclean generation output.
    *   **Timeout (>120s):** Strongly correlated with `full` IR schema. Suggests output code is too large/complex for compiler.
*   **First 3 Experiments:**
    1.  **Baseline Replication:** Run the `no_schema` pipeline for 1 pattern (e.g., `1_Ownership`) with 5 seeds. Confirm compiler error distribution matches paper (primarily `CS0115`, `CS0234`, `CS0246`). Validates the pipeline and establishes the grounding failure baseline.
    2.  **Schema Impact Probe:** For a single pattern, run `with_schema_free` and `with_schema_min` with 5 seeds each. Measure (a) change in G-failure error codes (expect `CS0115` drop), (b) compilation timeout rate (expect increase from free to min). Isolates the effect of adding hard referential constraints.
    3.  **Timeout Code Analysis:** Take 5 timeout records from a `with_schema_full` run. Manually inspect the generated `.cs` file length and structure. Confirm code is syntactically valid but excessively long/complex (deeply nested, many classes/methods), supporting the complexity-timeout hypothesis.

## Open Questions the Paper Calls Out
*   **Open Question 1:** What techniques can effectively mitigate project-level grounding failures (e.g., `CS0246` errors) in LLM-based Unity code generation for goal patterns?
    *   **Basis in paper:** The failure analysis identifies `CS0246` as a dominant grounding failure persisting across all IR configurations, indicating that project-specific knowledge is not fully captured by current IR conditioning. Project-level grounding is a primary bottleneck.
    *   **Why unresolved:** The IR's structural layer reduces architectural errors but does not resolve references to project-specific entities, suggesting richer or targeted knowledge injection is needed.
    *   **What evidence would resolve it:** Experiments with enhanced knowledge sources (e.g., project symbol tables, RAG over codebase), fine-tuning on Unity project-specific data, or dynamic lookup mechanisms.
*   **Open Question 2:** How can hygiene failures (syntax and formatting errors) be systematically eliminated in constrained LLM generation for Unity game code?
    *   **Basis in paper:** Authors propose future work on constrained decoding or rule-based sanitization. Hygiene failures dominate IR-conditioned outputs (e.g., `CS0101`, `CS1029`).
    *   **Why unresolved:** Current pipelines lack mechanisms to enforce syntactic constraints during decoding or post-generation.
    *   **What evidence would resolve it:** Implementation and evaluation of constrained decoding strategies (grammar-based, syntax-aware) or robust sanitization pipelines, measuring reduction in hygiene error rates.
*   **Open Question 3:** Should human knowledge injection for goal pattern instantiation be adaptively tailored per pattern, rather than uniformly via a fixed IR, and what pattern characteristics predict grounding difficulty?
    *   **Basis in paper:** Discussion notes pattern-level asymmetry in failure distributions (e.g., Ownership pattern exhibits persistent grounding failures) and suggests the human-machine boundary may need pattern-specific negotiation.
    *   **Why unresolved:** The current IR schema is uniform across all 26 patterns, but failure data indicates variable difficulty; without understanding per-pattern properties, optimization is coarse-grained.
    *   **What evidence would resolve it:** Correlational analysis between pattern features (object count, rule complexity) and grounding failure rates; development of adaptive IR configurations.
*   **Open Question 4:** How can the semantic fidelity of generated goal pattern instantiations be evaluated beyond compilation success, ensuring preservation of intended gameplay meanings?
    *   **Basis in paper:** The paper scopes evaluation to compile-grounded viability (M1) and states future work will extend to "structural adherence, gameplay meaning preservation." Compilation is necessary but insufficient.
    *   **Why unresolved:** Compiled code may be syntactically valid but semantically misaligned with the goal pattern's interactive dynamics; current metrics do not assess runtime behavior.
    *   **What evidence would resolve it:** Development of gameplay-level metrics (state trace comparison, player experience proxies) or human studies comparing generated vs. reference patterns; automated testing within Unity to validate pattern-specific win conditions.

## Limitations
*   **Metric Limitation:** Compilation success is a necessary but not sufficient condition for functional or semantic correctness of the generated gameplay pattern.
*   **Coverage Limitation:** Evaluation is restricted to two mid-size code LLMs (≤13B parameters) and 26 specific goal patterns, limiting generalizability to other models or broader pattern taxonomies.
*   **IR Scalability Limitation:** The human-authored, per-pattern IR limits scalability and may introduce authoring bias, preventing a large-scale study.

## Confidence
*   **Zero compilation success across all conditions:** High (consistent result across all patterns, models, and configurations).
*   **IR detail increase causes monotonic timeout rise:** Medium (observed monotonic trend, but causal link to code complexity is inferred, not directly measured).
*   **IR eliminates specific architectural errors (`CS0115`):** High (`CS0115` occurrences near-zero under any schema condition).
*   **Grounding failures (missing references) remain the dominant bottleneck:** High (errors like `CS0246`, `CS0234` persist at high rates despite IR conditioning).

## Next Checks
1.  Measure generated code complexity (e.g., token length, AST depth, cyclomatic complexity) per IR condition and correlate quantitatively with compilation timeout rates to test the complexity causality hypothesis.
2.  Evaluate additional, larger code models (e.g., CodeLlama-34B, GPT-4) and a broader set of patterns to test the generalizability of the zero-success finding and the IR trade-off.
3.  Conduct a manual repair study: for a sample of non-compiling outputs, fix the most common hygiene and grounding errors (e.g., strip IR markers, add missing references) and assess whether the resulting code compiles and exhibits semantically correct runtime behavior for the pattern.
