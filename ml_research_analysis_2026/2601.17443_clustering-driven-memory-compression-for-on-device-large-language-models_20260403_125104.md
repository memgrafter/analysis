# Clustering-driven Memory Compression for On-device Large Language Models

## Quick Facts
- **arXiv ID:** 2601.17443  
- **Source URL:** https://arxiv.org/abs/2601.17443  
- **Reference count:** 0  
- **Primary result:** Clustering-driven compression uses 50% fewer tokens than concatenation (512 vs. 1024) while achieving higher average ROUGE-L scores across models and datasets (13.99% vs. 13.80% for concatenation and 12.40% for averaging).

## Executive Summary
On-device large language models face strict context window limits, making it challenging to incorporate multiple user memories for personalization. Simply concatenating memories exhausts tokens, while averaging all memories loses coherence by merging dissimilar information. This paper introduces a clustering-driven compression strategy: memories are first encoded into token embeddings, then grouped by semantic similarity using K-means. Within each cluster, memories are merged via averaging, producing one representative per cluster. This balances token reduction and information retention. Experiments on personalization benchmarks show the method consistently outperforms naive baselines under matched token budgets and across model sizes, offering a practical trade-off for resource-constrained deployments.

## Method Summary
The system uses a trainable "compressor" LLM (frozen model with LoRA and new memory tokens) to convert each retrieved user document into a fixed-length `D_m`-token memory vector. Given `N` retrieved memories, three merging strategies are compared:  
- **Concat:** direct concatenation (`N * D_m` tokens).  
- **Mean:** token-wise average of all memories (`D_m` tokens).  
- **Clustering:** represent each memory by its mean embedding, run K-means clustering, then average memories within each cluster and concatenate the `K` cluster representatives (`K * D_m` tokens).  

The generator LLM (same base model, optionally with LoRA) conditions on the instruction and the merged memory prefix. Training minimizes cross-entropy loss on the target response, updating only the compressor's memory embeddings and LoRA parameters. The number of clusters `K` directly controls the token budget, enabling adaptation to strict on-device constraints.

## Key Results
- With `D_m=128` and `N=8`, clustering (`K=4`) uses 512 tokens vs. 1024 for concatenation and achieves higher average ROUGE-L (13.99% vs. 13.80% and 12.40%).  
- Under a matched 128-token budget, clustering (`K=4`, `D_m=32`) outperforms the mean baseline (43.64% vs. 43.13% ROUGE-L).  
- Performance improves with more clusters (up to `K=4`) and holds across varying model sizes and memory counts.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Grouping memories by semantic similarity before merging reduces destructive interference and preserves coherent information.  
- **Mechanism:** Memories are compressed into embeddings; K-means clusters them by vector similarity. Averaging occurs only within clusters, yielding one representative per coherent theme.  
- **Core assumption:** Memories within a cluster share a semantic theme, so their average remains meaningful.  
- **Evidence anchors:** Abstract states the method "groups memories by similarity and merges them within clusters." Section 3 details K-means and within-cluster averaging.  
- **Break condition:** If all memories are already highly homogeneous, clustering offers no advantage over global averaging and adds overhead.

### Mechanism 2
- **Claim:** Clustering achieves a better trade-off between token compression and information retention than extreme baselines.  
- **Mechanism:** Total tokens = `K * D_m`. This linearly tunes between `1 * D_m` (global mean) and `N * D_m` (concatenation), preserving multiple distinct memory facets.  
- **Core assumption:** An optimal compression point exists between extremes, and clustering can discover it.  
- **Evidence anchors:** Table 1 shows clustering at 512 tokens outperforms concatenation at 1024. Table 2 confirms superiority under a matched 128-token budget.  
- **Break condition:** If optimal `K` is very low (e.g., `K=1`), clustering degenerates to the mean baseline.

### Mechanism 3
- **Claim:** The number of clusters `K` is an interpretable, direct control knob for context efficiency, adjustable without retraining.  
- **Mechanism:** Changing `K` changes the number of cluster representatives while keeping `D_m` fixed, enabling adaptation to token budgets.  
- **Core assumption:** Performance impact of `K` is predictable and monotonic within a range.  
- **Evidence anchors:** Section 4.3 (Figure 4) shows performance rises with `K` up to a point. Section 3 notes `K` controls token count.  
- **Break condition:** If clustering overhead becomes prohibitive on-device, or if high `K` causes over-fragmentation and coherence loss.

## Foundational Learning

  Why needed: Core partitioning algorithm groups memory embeddings. Implementation choices (init, distance metric, restarts) affect stability.  
  Quick check: What failure mode occurs if memory embeddings have uneven cluster densities or sizes?

- **Concept: Context Window & Token Budgeting**  
  Why needed: The entire problem is constrained by a fixed on-device context length; all design parameters (`D_m`, `N`, `K`) trade off against this budget.  
  Quick check: If the LLM's context window is 1024 tokens and the user input requires 200 tokens, what is the maximum token budget for memories?

- **Concept: Memory Token Extraction via Compressor LLM**  
  Why needed: A separate compressor model (frozen LLM + trainable embeddings) converts raw documents into dense `D_m`-token sequences; its quality is foundational.  
  Quick check: Why might the compressor be trained with a moderate compression rate (e.g., 4:1) instead of an extreme rate like 100:1?

## Architecture Onboarding
Retriever -> Compressor -> Clustering -> Merger -> Generator  
Critical path: Document retrieval → per-document compression → clustering → within-cluster averaging → concatenation → LLM generation. Any flaw in compression or clustering corrupts final input.  
Design tradeoffs:  
- `K` vs. compute: higher `K` improves quality but increases clustering cost and token count.  
- `D_m` vs. compressor quality: larger `D_m` gives more capacity per document but reduces tokens available for clusters under a fixed budget.  
- Clustering algorithm vs. feasibility: K-means is simple but requires all memory embeddings in memory; for large `N`, streaming/approximate methods may be needed.  
Failure signatures:  
- Clustering failure: high ROUGE variance across K-means seeds indicates unstable clusters.  
- Merger failure: `K=1` performing as poorly as global mean suggests destructive averaging due to poor cluster coherence.  
- Context overflow: final length `(input tokens + K*D_m)` exceeds LLM max context, causing truncation.  
First 3 experiments:  
1. **Baseline replication:** Reproduce "Concat" and "Mean" baselines from Table 1 on one dataset/model to validate setup.  
2. **Ablation on K:** For fixed `D_m` and token budget, sweep `K=1,2,3,4,5` to verify performance trend and identify optimal `K`.  
3. **Token budget stress test:** Fix `K` and vary `D_m` (e.g., 32, 64, 128) to see if gains plateau, confirming minimum effective `D_m`.

## Open Questions the Paper Calls Out
- How can the optimal number of clusters `K` be determined automatically for varying memory distributions and model capacities without manual tuning?
- Could learned merging functions within clusters (e.g., attention-weighted or small neural mergers) outperform simple averaging while maintaining the same token budget?
- Does the clustering approach generalize to conversational memory tasks where memories are dialogue turns with strong temporal and structural dependencies?
- How does the quality of the initial memory retrieval step (e.g., BM25 vs. learned retrievers) interact with the effectiveness of clustering-driven compression?

## Limitations
- Generalization: evaluated only on LaMP with BM25 retrieval; unknown for other domains or retrievers.  
- On-device feasibility: clustering compute/memory overhead not analyzed; may be prohibitive on constrained hardware.  
- Stability: no reported variance across K-means seeds; performance could be unstable.  
- Metrics: reliance solely on ROUGE-L; other quality aspects (fluency, relevance) unmeasured.

## Confidence
- **Efficacy:** Medium – small marginal gains (0.19–1.59% ROUGE-L) without significance tests.  
- **Robustness:** Low–Medium – "consistent" claim based on limited settings; variance unquantified.  
- **Tunability:** Medium – `K` trend shown up to 4; higher `K` effects unclear.

## Next Checks
1. **Statistical validation:** Repeat experiments with ≥5 random seeds; compute p-values for ROUGE-L differences.  
2. **Retrieval variation:** Replace BM25 with a dense retriever (e.g., Sentence-BERT) and re-evaluate key results.  
3. **Device profiling:** Benchmark K-means runtime and memory on target hardware (e.g., mobile phone) with realistic memory counts (`N=8–32`).
