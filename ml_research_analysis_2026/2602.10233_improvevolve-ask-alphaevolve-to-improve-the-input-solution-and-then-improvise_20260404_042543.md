# ImprovEvolve: Ask AlphaEvolve to Improve the Input Solution and Then Improvise

## Quick Facts
- **arXiv ID:** 2602.10233  
- **Source URL:** https://arxiv.org/abs/2602.10233  
- **Reference count:** 25  
- **Primary result:** Modular decomposition of LLM-guided evolution into generate_config, improve, and perturb functions yields new state-of-the-art results on hexagon packing and the second autocorrelation inequality, significantly outperforming prior end-to-end approaches.

## Executive Summary
ImprovEvolve reimagines LLM-guided evolutionary computation by breaking the optimization problem into three distinct, modular functions—`generate_config`, `improve`, and `perturb`—instead of evolving a single monolithic program. This decomposition reduces cognitive load on the LLM, making it easier to generate effective, domain-specific code. The system is evaluated on two challenging mathematical optimization problems: hexagon packing and the second autocorrelation inequality. It achieves new state-of-the-art results, including improved side lengths for multiple hexagon counts and a lower bound of 0.96258 on the autocorrelation inequality, surpassing previous methods. Human-guided refinements to the evolved code further push performance on several instances. Ablation studies confirm the necessity of both multi-seed initialization and iterative basin-hopping, while also revealing that LLM-suggested edits often degrade performance.

## Method Summary
ImprovEvolve evolves a candidate `Improver` class that implements three focused methods: `generate_config` produces feasible initial solutions, `improve` performs local optimization (using standard constrained optimizers like L-BFGS-B or SLSQP with custom penalty schedules), and `perturb` applies controlled noise for exploration. A validation scheme (Algorithm 1) evaluates each candidate in two stages: Stage A samples multiple seeds via `generate_config`, immediately refines each with `improve`, and keeps the best result; Stage B applies basin-hopping—alternating `perturb` (with geometrically decaying perturbation magnitude σ) and `improve`—to escape local minima and converge in new basins. The outer loop uses a MAP-Elites evolutionary algorithm (GigaEvo) to maintain a population of `Improver` programs, select elites, and prompt an LLM (Gemini Flash) to generate mutated offspring. This modular approach shifts the LLM’s task from designing a full optimizer to implementing specialized subroutines, improving reliability.

## Key Results
- Hexagon packing: ImprovEvolve improves side lengths for n=11 (3.9245), 12, 15, and 16; a human-edited variant further improves n=14 (4.2690), 17 (4.6136), and 23 (5.4000).
- Second autocorrelation inequality: The human-edited program reaches a lower bound of 0.96258, surpassing AlphaEvolve’s 0.96102.
- Ablation studies show both multi-seed initialization (Stage A) and basin-hopping (Stage B) are necessary for best performance; LLM-generated edits often degrade results.

## Why This Works (Mechanism)
### Mechanism 1: Modular Decomposition Reduces LLM Cognitive Load
Evolving three focused subroutines (`generate_config`, `improve`, `perturb`) is easier for an LLM than evolving a single monolithic optimization program. The LLM’s task shifts from designing a complete, end-to-end optimizer to implementing well-defined, single-responsibility functions, aligning with separation of concerns.  
*Evidence anchors:* [abstract] "reducing the cognitive load on the LLM by separating the distinct concerns of initialization, local improvement, and exploration." [section 3] "the LLM’s task from designing an end-to-end optimization algorithm to designing domain-specific improve and perturb operators—a more tractable objective."

### Mechanism 2: Multi-Seed Initialization Explores Diverse Basins
Sampling multiple initial configurations via `generate_config` followed by `improve` increases the probability of starting in a high-quality basin of attraction. This combats the sensitivity of local optimization to initial conditions on rugged landscapes.  
*Evidence anchors:* [section 3] "Since the quality of the final solution depends heavily on the basin in which the search begins, sampling multiple initial configurations and selecting the best one reduces sensitivity to poor initializations." [section 4.1] "The existence of two qualitatively different high-quality packings suggests that the fitness landscape contains multiple deep basins, underscoring the importance of Stage A diversity." [table 4] Ablation shows "A only" generates a prototype but cannot refine; "A + B" achieves best.

### Mechanism 3: Basin-Hopping with Scheduled Perturbation Enables Escapes and Refinement
Iteratively applying `perturb` (with geometrically decaying intensity σ) and `improve` allows escaping local minima and then converging within a new basin. Large early perturbations facilitate exploration across barriers; subsequent decay enables fine-grained convergence. Monotonic acceptance ensures only improvements are kept.  
*Evidence anchors:* [section 3] Explicitly links to basin-hopping and describes the σ schedule. [figure 2] Visualizes a large perturbation scattering hexagons but `improve` recovers; a smaller perturbation discovers a tighter basin (L=4.6136). [section 4.2] Shows a similar jump in C(f) for ACI 2 at ε=10⁻³.

## Architecture Onboarding
- **Component map:**  
  Evolved Class (Improver) implements generate_config/improve/perturb → Validation Scheme (Algorithm 1: Stage A multi-seed init + Stage B basin-hopping) evaluates fitness → Evolutionary Loop (GigaEvo, MAP-Elites) selects elites and prompts LLM → LLM (Gemini Flash) mutates programs → Execution Engine handles code execution/timeouts → fitness fed back to archive.

- **Critical path:** Evolution loop selects elite Improver → LLM mutates program → Validation Scheme runs Algorithm 1 → fitness assigned → archive updated. Validation fitness directs evolution.

- **Design tradeoffs:**  
  *Modularity vs. context:* Three small functions may consume less LLM context than one large function, but the prompt must still describe the interface clearly.  
  *Validation cost vs. fidelity:* More seeds (K) and hops (R) yield better fitness estimates but linearly increase evaluation time; evolution uses lower R, final validation uses higher R.  
  *LLM selection:* Capable model (Gemini Pro) for initialization vs. cheaper (Gemini Flash) for evolution trades initial quality for throughput.

- **Failure signatures:**  
  `improve` returns invalid configurations (overlaps/OOB) → program discarded.  
  `generate_config` produces consistently poor seeds → Stage A yields weak starts.  
  `perturb` changes dimensionality or violates constraints → `improve` may fail.  
  LLM edits degrade performance (e.g., increasing Langevin noise inappropriately).

- **First 3 experiments:**  
  1. Baseline comparison: Run GigaEvo with monolithic `entrypoint` and ImprovEvolve on HEX n=11 with identical evolution hyperparameters; compare validation fitness distributions (Figures 5 & 6).  
  2. Ablation validation: On best HEX-11 Improver, run Algorithm 1 with Stage A only (K=100,R=0), Stage B only (K=1,R=100), and full (K=100,R=100); record best L (Table 4).  
  3. Generalization test: Apply HEX-11 evolved Improver to n=12,15,16 without re-evolution; compare to baseline's failure on n>11 (Section 4.1).

## Open Questions the Paper Calls Out
### Open Question 1
Does ImprovEvolve generalize to problem domains beyond hexagon packing and the autocorrelation inequality, such as combinatorial optimization or scientific simulation?  
*Basis:* [explicit] "Our evaluation is limited to two mathematical optimization problems... the generalizability of ImprovEvolve to other problem classes... remains to be demonstrated."  
*Why unresolved:* Only two continuous optimization benchmarks from the same suite were tested; other domains (e.g., discrete, black-box) may have different landscapes that challenge the modular improve/perturb design.  
*What evidence would resolve:* Systematic benchmarking across diverse problem families (e.g., bin packing, neural architecture search) with uniform protocol; success would show broad applicability, while domain-specific failures would reveal limitations.

### Open Question 2
Can an LLM autonomously propose beneficial hyperparameter adjustments (e.g., optimizer choice, penalty weights) to match the improvements from human-guided edits in ImprovEvolve+E?  
*Basis:* [explicit] "LLM edits for the ImprovEvolve program... produced results inferior to the unedited version" and "even the most advanced LLMs tend to suggest theoretically plausible but empirically harmful changes."  
*Why unresolved:* Human edits (e.g., switching to SLSQP, softening penalties) yielded state-of-the-art results, but LLM-suggested edits degraded performance, indicating models lack reliable intuition for optimization hyperparameters.  
*What evidence would resolve:* Designing prompting schemes or training data that teach LLMs to suggest effective hyperparameter changes, then comparing LLM-edited versus human-edited programs across multiple runs; consistent improvement would show autonomy.

### Open Question 3
What are the statistical distributions (means, variances, confidence intervals) of ImprovEvolve's performance across independent evolutionary runs?  
*Basis:* [explicit] "Our experiments report single-run best results without confidence intervals, and the stochastic nature... means that outcomes may vary across runs."  
*Why unresolved:* Single-run results may be outliers; without repeated trials, the significance and reliability of reported state-of-the-art improvements are unknown.  
*What evidence would resolve:* Conducting multiple independent runs for each problem, aggregating results to compute confidence intervals for key metrics (e.g., L for HEX n, C for ACI 2); this would quantify robustness and statistical significance.

### Open Question 4
Can an agentic AI system dynamically modify the Improver class interface (e.g., adding methods or changing structure) during evolution to better suit the problem, reducing reliance on human-designed decomposition?  
*Basis:* [explicit] "Combining task decomposition with agentic workflows—where an AI agent autonomously decides which modules to refine and when to invoke external solvers—is a promising direction."  
*Why unresolved:* ImprovEvolve uses a fixed three-method interface; allowing the LLM to evolve the interface itself could handle a wider range of problems but risks instability and increased search complexity.  
*What evidence would resolve:* Implementing an agent that can propose interface modifications (e.g., new methods, parameter changes) during the evolutionary loop, then comparing success rates and solution quality against the static interface across diverse problems.

## Limitations
- **Version & API ambiguity:** Exact GigaEvo commit, LLM model versions (Gemini 3 Pro/Flash), and API endpoints are unspecified, risking implementation drift.
- **Validation hyperparameters incomplete:** For HEX n=25–30, only an inferred budget (K=100, R=100, σ schedule) is used; no official settings are provided.
- **Statistical robustness:** Results are reported as single-run best values without confidence intervals or fixed seeds; variance across runs is unknown.
- **Generalization boundary:** The human-edited programs’ improvements on n=14,17,23 are not reproduced automatically; the extent of required human intuition is unclear.

## Confidence
- **Modular decomposition reduces cognitive load** – High (explicitly motivated, ablation shows full scheme beats partial).
- **Basin-hopping with scheduled perturbation enables escapes** – Medium (visual evidence and acceptance logic support it; no direct ablation vs. fixed σ).
- **LLM-generated edits often degrade performance** – Low (Table 4 shows some harmful edits, but sample size is small and not systematically quantified).
