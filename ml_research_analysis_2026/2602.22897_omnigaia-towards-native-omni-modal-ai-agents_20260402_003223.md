# OmniGAIA: Towards Native Omni-Modal AI Agents
## Quick Facts
- **arXiv ID:** 2602.22897
- **Source URL:** https://arxiv.org/abs/2602.22897
- **Reference Count:** 40
- **Primary Result:** Introduces OmniGAIA, a challenging 360-task benchmark for omni-modal agents, and OmniAtlas, a model that improves Qwen-3-Omni's Pass@1 from 13.3 to 20.8 via masked SFT and OmniDPO.

## Executive Summary
This paper addresses the lack of unified evaluation for AI agents that natively process vision, audio, and language together with complex, tool-augmented reasoning. It introduces OmniGAIA, a benchmark of 360 omni-modal tasks requiring multi-hop reasoning and multi-turn tool use over video-with-audio and image+audio inputs. The benchmark is constructed via an event-graph pipeline that synthesizes hard, verifiable questions from real media. To improve open-source models, the authors propose OmniAtlas, a native omni-modal agent with active perception and tool-integrated reasoning, trained using hindsight-guided tree exploration, masked supervised fine-tuning, and OmniDPO. Results show OmniGAIA is highly challenging: the best proprietary model (Gemini-3-Pro) reaches 62.5 Pass@1, while Qwen-3-Omni scores only 13.3. OmniAtlas closes part of this gap to 20.8, substantially reducing ineffective tool use and reasoning errors, though perception remains a key bottleneck.

## Method Summary
The paper’s method combines benchmark creation and agent training. OmniGAIA is built by extracting structured event graphs from real media (FineVideo, LongVideoBench, COCO+audio), then systematically expanding these graphs via tool-augmented LLM calls to generate multi-hop, verifiable questions. For training OmniAtlas, the authors first synthesize successful agent trajectories using tree exploration: a base LLM (DeepSeek-V3.2) proposes thought-action sequences at each step, while a verifier (Gemini-3-Flash) prunes incorrect branches to retain only trajectories reaching the correct answer. These trajectories are then used for masked supervised fine-tuning (loss applied only to agent-generated tokens, not tool observations) and OmniDPO (a DPO variant that identifies the first error in failed trajectories and trains on contrastive prefix pairs). The final agent integrates an omni-modal LLM base with tools for active perception (`read_video`, `read_audio`, `read_image`) and external reasoning (`web_search`, `code_executor`).

## Key Results
- **Benchmark difficulty:** Gemini-3-Pro achieves 62.5 Pass@1, while open-source models like Qwen-3-Omni score only 13.3, showing a large performance gap.
- **Training efficacy:** OmniAtlas lifts Qwen-3-Omni to 20.8 Pass@1, a 56% relative improvement, mainly by reducing tool-use and reasoning errors.
- **Error analysis:** Perception errors remain frequent (30–50%), identified as a persistent bottleneck despite overall gains.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Hindsight-guided tree exploration synthesizes diverse, successful agent trajectories that capture complex multi-hop reasoning and tool-use patterns, providing high-quality training data.
- **Mechanism:** Starting from a root state, the method samples multiple candidate continuations (thoughts + tool actions) at each step; a verifier (conditioned on the ground‑truth answer) prunes incorrect branches, retaining only trajectories that reach the correct final answer.
- **Core assumption:** A strong verifier model (Gemini‑3‑Flash) can reliably judge whether a partial trajectory leads to the correct solution, enabling selection of successful paths.
- **Evidence anchors:** Abstract mentions “hindsight‑guided tree exploration for trajectory synthesis”; Section 4.2 describes sampling *k=3* candidates and using a verifier to prune branches. Corpus provides weak direct support.
- **Break condition:** If the verifier is biased or inaccurate, selected trajectories may not generalize to the true task distribution, degrading policy learning.

### Mechanism 2
- **Claim:** Masked supervised fine‑training (SFT) teaches the model to generate appropriate reasoning and tool‑call tokens while avoiding memorization of tool observations, thus focusing on the decision‑making policy.
- **Mechanism:** Cross‑entropy loss is computed only on tokens produced by the agent (thoughts and actions); tokens corresponding to tool observations are masked out. This prevents the model from fitting the specific content returned by tools.
- **Core assumption:** A robust agent policy should be independent of the exact details of tool outputs; masking encourages learning of a general strategy that can handle variations in tool responses.
- **Evidence anchors:** Abstract includes “masked supervised fine‑tuning”; Section 4.3 presents the masked loss objective (Eq. 2) and explains loss masking. Corpus lacks direct evidence.
- **Break condition:** Over‑masking might prevent the model from learning necessary correlations between actions and expected observations, leading to incoherent tool‑use sequences.

### Mechanism 3
- **Claim:** OmniDPO performs fine‑grained error correction by identifying the first erroneous step in a failed trajectory and training on contrastive prefix pairs, thereby addressing specific failure modes (e.g., perception, reasoning, tool‑use).
- **Mechanism:** For each failed rollout, Gemini‑3‑Flash (given the ground‑truth solution) pinpoints the first error and generates a corrected prefix up to that point. The original (incorrect) and corrected prefixes form a preference pair for a masked DPO objective (Eq. 3).
- **Core assumption:** The root cause of failure is the first error; correcting it yields a viable successful continuation, and the model can learn from these targeted contrasts without over‑fitting to the full trajectory.
- **Evidence anchors:** Abstract states “OmniDPO for fine‑grained error correction”; Section 4.4 details error localization and masked DPO. A neighboring paper (*OmniDPO: A Preference Optimization Framework to Address Omni‑Modal Hallucination*) overlaps conceptually but targets hallucination.
- **Break condition:** Misidentification of the first error (e.g., due to judge bias) would generate noisy correction signals, potentially reinforcing incorrect reasoning steps.

## Architecture Onboarding
- **Component map:**
Data ingestion (Image, audio, video processors using Gemini-3-Flash) -> Event graph builder (DeepSeek-V3.2 creates initial graph) -> Graph expansion (DeepSeek-V3.2 with tools adds next-hop evidence) -> QA generation (Event fuzzification, LLM screening, human verification) -> Training pipeline (Trajectory synthesizer: tree exploration with verifier; masked SFT; OmniDPO: error localization + DPO) -> Inference agent (OmniAtlas: base omni-modal LLM + tools: read_* for active perception, web_search, code_executor) -> Evaluation (LLM-as-a-Judge: DeepSeek-V3.2)

- **Critical path:**
1. Build OmniGAIA dataset (media collection → info extraction → graph construction → expansion → QA generation → quality checks).
2. Generate synthetic training trajectories using tree exploration (DeepSeek-V3.2 as policy, verifier) on the training split.
3. Perform masked SFT on a base model (e.g., Qwen-3-Omni) with the successful trajectories.
4. Apply OmniDPO: run the SFT model on training data, locate first errors, build correction pairs, fine-tune with DPO.
5. Evaluate final OmniAtlas model on OmniGAIA test set with full tool access and active perception.

- **Design tradeoffs:**
  - Tree exploration: Larger branching factor (*k*) increases trajectory diversity but raises computational cost and may introduce noise.
  - Masked SFT: Masking tool observations reduces over-fitting to specific tool outputs but risks losing cues needed for coherent planning.
  - OmniDPO: Focusing on the first error is efficient but assumes errors are sequential and locatable; mislocalization degrades correction.
  - Active perception: Selective reading saves tokens but depends on the model’s ability to identify relevant regions; mis‑selection loses critical details.
  - Synthetic data: Teacher‑generated trajectories may not capture all real‑world variations, creating a distribution gap.

- **Failure signatures:**
  - Ineffective tool use: Either no tool calls when required or excessive calls without progress (seen in error heatmaps).
  - Perception errors: Misreading visual or audio content (e.g., confusing similar bridges).
  - Reasoning errors: Correct facts but flawed logic or arithmetic.
  - Cascading failures: An early mistake (e.g., wrong hypothesis) propagates through subsequent steps (case studies).
  - Tool‑query drift: Agent fixes on an incorrect prior and issues confirming queries instead of disambiguating ones.
  - Over‑reliance on priors: Ignoring media‑specific evidence in favor of stereotypical knowledge.

- **First 3 experiments:**
  1. Main benchmark results (Table 2): Quantify Pass@1 of various proprietary and open‑source models on OmniGAIA, showing the large gap closed by OmniAtlas.
  2. Training ablation (Table 4): Isolate contributions of masked SFT and OmniDPO by measuring error‑type reductions and overall Pass@1 gain.
  3. Native vs. tool‑based perception (Table 3): Compare performance when the model uses its inherent omni‑modal input versus delegating missing modalities to perception tools, demonstrating the advantage of native perception for strong agents.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can reinforcement learning be effectively applied to optimize long-horizon agentic policies in omni-modal settings?
  - **Basis in paper:** [explicit] The conclusion identifies "Omni-modal Agentic RL to directly optimize long-horizon agentic policies under omni-modal feedback" as a key direction.
  - **Why unresolved:** Current training (SFT+DPO) may not fully capture delayed rewards and complex trade-offs in multi-step tool use; RL could improve robustness on hard tasks.
  - **What evidence would resolve it:** An RL algorithm that leverages omni-modal observations and learns a policy that significantly improves Pass@1 on challenging subsets of OmniGAIA, with analysis of reward shaping and sample efficiency.

- **Open Question 2:** What scalable MCP services are necessary to broaden the toolset for omni-modal agents, and how can they be standardized?
  - **Basis in paper:** [explicit] The future work proposes "Omni-modal MCP Services with scalable tools for broader omni-modal tasks."
  - **Why unresolved:** Existing tools (web search, code) are limited; MCP could enable diverse modalities (e.g., audio processing, video editing) but requires protocols and implementations.
  - **What evidence would resolve it:** A set of MCP-compliant omni-modal tools, integrated into an agent framework, demonstrating expanded task coverage and ease of tool addition.

- **Open Question 3:** How can benchmarks and foundation models for omni-modal embodied agents be created to operate in physical worlds?
  - **Basis in paper:** [explicit] The conclusion calls for "Omni-modal Embodied Agents benchmarks and foundation models in physical world."
  - **Why unresolved:** OmniGAIA evaluates media understanding; embodied agents need real-time sensorimotor skills and physical reasoning, which are underexplored.
  - **What evidence would resolve it:** A realistic simulation or robotics platform with vision, audio, and language tasks, and models that complete physical goals (e.g., assembly, navigation).

- **Open Question 4:** Why do native omni-modal perception errors persist despite training, and how can they be reduced?
  - **Basis in paper:** [inferred] Error analysis (Fig 5, Sec 5.3) shows high perception error rates (30–50%) and states perception is a "persistent bottleneck."
  - **Why unresolved:** OmniAtlas focuses on tool-use and reasoning; perception may require architectural changes (e.g., higher-resolution encoders) or better multimodal alignment.
  - **What evidence would resolve it:** Ablation studies identifying perception weakness, followed by targeted modifications (e.g., active perception mechanisms, multi-scale features) that lower perception errors without compromising other capabilities.

## Limitations
- Benchmark and training rely heavily on proprietary models (DeepSeek‑V3.2, Gemini‑3‑Flash) for data generation, verification, and evaluation, preventing exact replication and potentially embedding model‑specific biases.
- Critical details of the OmniGAIA construction pipeline (event‑graph expansion rules, fuzzification) are not released, hindering verification of task diversity and difficulty.
- Hyperparameters for training (learning rates, batch sizes) and resource specifications are underspecified, making reproduction challenging even with code.

## Confidence
- **OmniGAIA benchmark challenge:** High – multiple independent models show the expected performance gap.
- **Training gains from masked SFT + OmniDPO:** Medium – ablations are reported but depend on proprietary teachers.
- **Mechanistic explanations (tree exploration, fine‑grained correction):** Low – no direct evidence; could be confounded by teacher model quality.
