# MerNav: A Highly Generalizable Memory-Execute-Review Framework for Zero-Shot Object Goal Navigation

## Quick Facts
- **ArXiv ID:** 2602.05467  
- **Source URL:** https://arxiv.org/abs/2602.05467  
- **Reference count:** 19  
- **Primary result:** Achieves an average absolute success rate improvement of 7% over all training-free methods and 5% over all zero-shot methods, with peaks of 8% on HM3D_v0.1 and 6% on HM3D_OVON; also surpasses supervised fine-tuning methods on MP3D and HM3D_OVON.

## Executive Summary
MerNav introduces a novel training-free framework for zero-shot object goal navigation (OGN) that addresses the trade-off between success rate and generalization. It employs a hierarchical memory system (short-term, long-term, commonsense) to inform decision-making, an execute module for routine navigation actions, and a review module that detects and corrects anomalies such as obstacles or floor transitions. Evaluated across four datasets (MP3D, HM3D_v0.1, HM3D_v0.2, and HM3D_OVON), MerNav achieves substantial gains over both training-free and zero-shot baselines, and even outperforms supervised fine-tuning methods on the most challenging benchmarks.

## Method Summary
MerNav is composed of three modules: Memory, Execute, and Review. The Memory module maintains a hierarchy: short-term memory stores the current observation (RGB-D, pose); long-term memory holds an exploration map (bird’s-eye view) and a sliding window of recent images; commonsense memory encodes persistent rules (e.g., robot size) via prompts. The Execute module transforms goals into actions via a four-stage pipeline: (1) analysis—fusing local, global, and historical views to score directions; (2) planning—generating concise subgoals; (3) action selection—sampling traversable points from depth; (4) stopping—based on goal proximity or step limits. The Review module runs in parallel, using a two-step check (visual/positional delta) to detect obstacles and a multi-step check (exploration map) to identify completed rooms/floors, outputting corrective phase goals that condition the Execute module. All components rely on a foundation vision-language model (e.g., Qwen3-vl-plus) without any training, enabling zero-shot generalization.

## Key Results
- Average absolute SR improvement: **7%** over all training-free methods, **5%** over all zero-shot methods.  
- Strong dataset-specific gains: **+8%** SR on HM3D_v0.1, **+6%** SR on HM3D_OVON (zero-shot).  
- Outperforms both training-free and supervised fine-tuning methods on MP3D (**+5%** SR) and HM3D_OVON (**+2%** SR).

## Why This Works (Mechanism)

### Mechanism 1: Hierarchical Memory as Structured Informational Scaffolding
- **Claim:** A hierarchical memory system (short-term, long-term, commonsense) provides distinct, complementary informational support that improves decision robustness and interpretability under routine navigation.
- **Mechanism:** Short-term memory holds immediate sensory data (RGB-D, pose). Long-term memory stores task-specific, episodic information (exploration maps, sliding-window observations) compressed to control capacity. Commonsense memory injects cross-task, persistent rules (e.g., robot width, object distinctions) via prompts. During the `Execute` module's observation analysis, these sources fuse (local/global/history views) to produce more reliable direction scores.
- **Core assumption:** Different memory types serve non-interchangeable roles; isolating them allows the system to weight immediate details, persistent spatial context, and semantic priors appropriately.
- **Evidence anchors:** [abstract] "hierarchical memory system (short-term, long-term, commonsense) to support decision-making"; [section 2.3] Detailed definitions and usage distinctions: "short-term memory and long-term memory are both task-related... common-sense memory is reused across tasks and is better injected into the model prompt"; neighboring papers (APEX, Stairway to Success) also explore memory decoupling.
- **Break condition:** If commonsense rules are poorly specified (e.g., incorrect width assumption) or long-term maps become too compressed/lossy, the fused analysis may degrade. Failure would manifest as repeated exploration of blocked areas or misidentification of objects due to missing critical spatial context.

### Mechanism 2: Execute Pipeline as Coarse-to-Fine Routine Handler
- **Claim:** A structured four-stage pipeline (analysis → planning → action selection → stop) within the `Execute` module transforms high-level goals into executable actions more robustly than a single-step decision.
- **Mechanism:** Analysis agent scores directions using integrated multi-view input. Planning agent distills verbose analysis into concise subgoals. Action selection uses depth-based traversability sampling to pick a reachable point, converted to polar coordinates. Stop decision checks goal proximity or step limits. Each stage refines the decision, reducing compounding errors.
- **Core assumption:** Routine navigation can be decomposed into verifiable sub-steps where errors are detectable and containable; verbose VLM outputs are better compressed into actionable subgoals.
- **Evidence anchors:** [abstract] "execute module for routine decision-making and actions"; [section 2.4] Explicit pipeline equations (3-8) and agent descriptions; related work (Tango, UniGoal) uses multi-stage decomposition, supporting the premise that single-round decisions are insufficient.
- **Break condition:** If any stage produces a flawed output (e.g., analysis agent hallucinates an unexplored direction, subgoal becomes contradictory), downstream actions will fail. The pipeline lacks an internal loop to re-analyze after a subgoal, relying on the review module for correction.

### Mechanism 3: Review Module as Independent Anomaly Detector and Corrector
- **Claim:** A separate, parallel `Review` module monitors execution deltas and exploration state, triggering corrective modes (obstacle-skipping, room/floor-jumping) to prevent error accumulation.
- **Mechanism:** Two-step review compares current vs. previous observation (image similarity) and positional delta; if static, concludes obstacle and excludes last direction. Multi-step review uses the exploration-area map to assess room/floor completion; if complete, sets phase goal to "find stairs" then "reach new floor." This separates anomaly handling from routine flow.
- **Core assumption:** The agent's expected state change can be modeled from its own recent history; deviations indicate external obstruction (obstacle) or inefficient exploration (completed room/floor), without needing external reward.
- **Evidence anchors:** [abstract] "review module to detect and correct anomalous situations like obstacles or floor transitions"; [section 2.5] Detailed triggers: "visual delta... below a threshold" for obstacles; "exploration-area record map" for room/floor exit; training-free methods (ESC, VLFM) incorporate heuristics for obstacles but MerNav's structured two/multi-step review is a formalized, memory-anchored mechanism.
- **Break condition:** False positives: if two-step review triggers unnecessarily (e.g., due to lighting change misread as obstacle), the agent may abandon promising directions. False negatives: if multi-step review fails to detect room completion (e.g., map inaccuracies), the agent may waste steps re-exploring.

## Foundational Learning

### Hierarchical Memory Systems
- **Why needed here:** MerNav's memory is not a single buffer but a structured hierarchy where each type (short-term, long-term, commonsense) has specific encoding, storage, and access rules. Understanding this prevents treating all "memory" as equivalent.
- **Quick check question:** If you were to add a new memory type (e.g., "social memory" for human-agent interaction), what core property (timescale, source, usage) would you define first to slot it into the existing hierarchy?

### Zero-Shot Generalization vs. Supervised Fine-Tuning
- **Why needed here:** MerNav's claim hinges on being both zero-shot and outperforming SFT. The key is that it avoids finetuning on navigation datasets, preserving foundation model generality. SFT methods overfit to training distribution (see Table 3's JanusVLN drop).
- **Quick check question:** Why does a training-free method like MerNav potentially generalize better than a zero-shot SFT method (JanusVLN‡)? What does "zero-shot" mean in each context?

### Multi-Modal Fusion for Embodied Perception
- **Why needed here:** The `Execute` module's analysis stage fuses local (high-detail), global (panoramic structure), and historical (exploration map) views. This is not simple concatenation but a designed integration where each modality addresses a specific failure mode (e.g., local view confusing sofa for bed).
- **Quick check question:** In the analysis agent's prompt (section 2.4), what specific question does the "historical-view" (exploration map) answer that local/global views cannot?

## Architecture Onboarding

### Component map
Input: Observation (RGB-D, pose) → Memory (short-term: current observation; long-term: BEV exploration maps & sliding-window history; commonsense: prompt rules) → Decision: Execute (Analysis → Planning → Action Selection → Stop) + Review (Two-step obstacle & Multi-step room/floor exit monitors → Gp) → Control: Gp overrides/supplements Execute's planning → Action.

### Critical path
1. Observe O_t → update short-term memory.
2. Load commonsense prompts.
3. Execute: Fuse I_integ → Analysis scores → Select direction D_t^sel → Plan subgoal G_t^sub → Sample reachable points → Select action A_e^t.
4. Parallel: Review computes two-step & multi-step checks → if anomaly, set G_p.
5. Final action A_e^t is conditioned on G_p from Review (if any).
6. Act A_r^t → new state → loop.

### Design tradeoffs
- **Memory richness vs. cost:** Compression (BEV maps) reduces storage but loses fine details; uncompressed window (L_w=1) retains critical last view but limited history.
- **Review sensitivity vs. efficiency:** Tight thresholds (T_sim) catch more obstacles but may trigger falsely on visual changes; loose thresholds miss real blocks. Multi-step review relies on map accuracy.
- **Commonsense flexibility vs. reliability:** Prompt-based injection is easy to modify but depends on VLM's instruction following; incorrect rules degrade all tasks.

### Failure signatures
- **Obstacle handling failure:** Agent repeatedly moves but position unchanged → two-step review not triggering (false negative) or over-triggering (false positive causing circling).
- **Exploration inefficiency:** Agent re-explores same area (room/floor) → multi-step review's Flag_jump not set due to poor map or threshold.
- **Subgoal drift:** Planned subgoal contradicts current state (e.g., "go to stairs" while facing wall) → planning agent not adequately constrained by G_p or memory.

### First 3 experiments
1. **Ablation (Table 4):** Removes modules incrementally from baseline (WMNav+Qwen3). Shows isolated gains: commonsense memory → +0.8% SPL; review "jump out room" → +2.2% SR; "jump out floor" → +4% SR; execute pipeline refinement → +1.7% SR, +2.3% SPL. Validates each component's contribution.
2. **Foundation model scaling (Table 5):** Swap Qwen3-vl-plus → GPT-5.2 → SR+3% (68.0→70.9). Demonstrates MerNav's ceiling is model-agnostic; better VLMs directly boost performance.
3. **Zero-shot SFT comparison (Table 3):** JanusVLN* (SFT on HM3D_v0.1) vs. JanusVLN‡ (zero-shot transfer) → SR drop ~11%. MerNav (zero-shot) outperforms both. Proves that MerNav's TF design avoids SFT's distribution overfitting while achieving higher SR.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** Can the Memory-Execute-Review framework generalize to other Vision-Language Navigation tasks beyond Object Goal Navigation?
- **Basis in paper:** [explicit] The authors state: "We validate our framework on the Object Goal Navigation task." They do not evaluate on other VLN tasks like instruction-following or image-goal navigation.
- **Why unresolved:** The MER framework is designed with components tailored for OGN (e.g., phase goals for obstacle/floor transitions, goal-based stopping). It is unknown if these components are transferable or need modification for tasks with different input formats (e.g., step-by-step instructions) and goal specifications.
- **What evidence would resolve it:** Test MerNav on established benchmarks for other VLN tasks (e.g., R2R for instruction following, PhotoNav for image goals) and report performance relative to task-specific state-of-the-art methods. Ablation studies could identify which MER components are task-agnostic.

### Open Question 2
- **Question:** What are the computational efficiency and memory scalability of the MerNav framework?
- **Basis in paper:** [inferred] The paper does not report computational metrics (inference time, memory usage) or analyze how the hierarchical memory (e.g., BEV maps, exploration records) scales with environment size and exploration duration.
- **Why unresolved:** For practical deployment in embodied agents, real-time performance and resource constraints are critical. Without this analysis, it is unclear if MerNav is feasible for real-world applications or large-scale environments, especially given its reliance on multiple VLM calls per step.
- **What evidence would resolve it:** Measure and report runtime, memory footprint, and how these metrics change with varying environment complexity (e.g., number of rooms, floors) and episode lengths. Compare with baseline TF methods. Also, explore optimizations like caching or asynchronous operations.

### Open Question 3
- **Question:** How robust is the review module to diverse and unforeseen anomaly types?
- **Basis in paper:** [explicit] The review module explicitly handles only two anomaly categories: obstacles (via two-step review) and room/floor transition issues (via multi-step review). The triggers are hand-crafted thresholds (e.g., image similarity threshold Tsim, step count Te).
- **Why unresolved:** Real-world navigation can encounter many other anomalies (e.g., dynamic obstacles, perceptual errors, goal relocation, sensor failures). The current design may fail to detect or correct these, limiting reliability. The paper does not test on environments with novel anomalies.
- **What evidence would resolve it:** Evaluate MerNav on environments with a variety of anomalous conditions, including those not seen during design (e.g., moving objects, temporary occlusions, ambiguous goals). Also, investigate adaptive or learning-based approaches for anomaly detection and recovery, perhaps by analyzing failure logs.

### Open Question 4
- **Question:** Does the performance advantage of the MER framework hold across a wide range of foundation models, and what is the cost-performance trade-off?
- **Basis in paper:** [explicit] The authors tested two foundation models (Qwen3-vl-plus and GPT-5.2) and showed that the newer model improves SR by 3%. They note that performance can be boosted further with more advanced models.
- **Why unresolved:** It is unknown whether the relative gains of MER over baselines are consistent across different model families, architectures, and scales. Also, the trade-off between computational cost (e.g., API latency, monetary cost) and performance improvement is not analyzed. The paper only mentions that cost constraints led them to use Qwen3-vl-plus for main experiments.
- **What evidence would resolve it:** Benchmark MerNav with a diverse set of foundation models (e.g., open-source VLMs of varying sizes, proprietary models at different price points) and plot performance vs. cost metrics. Determine if MER consistently outperforms baselines regardless of model choice and identify the point of diminishing returns.

## Limitations
- Specification omits exact VLM prompts, output formats, and key thresholds (e.g., T_sim, T_h), requiring reconstruction and dataset-specific tuning.
- Evaluation is simulation-only (Habitat) with no real-world tests; also lacks direct comparisons to recent zero-shot OGN methods like APEX or Stairway to Success.
- Performance is sensitive to foundation model choice and prompt design; the scalability of memory and computational cost with environment complexity is not analyzed.
