# Low-pass Personalized Subgraph Federated Recommendation

## Quick Facts
- arXiv ID: 2603.20338  
- Source URL: https://arxiv.org/abs/2603.20338  
- Reference count: 40  
- Primary result: LPSFed significantly surpasses nine state-of-the-art baselines, achieving up to 24.2% NDCG@20 improvement on Amazon-Book, with consistent gains of 6.1–24.2% across five public datasets.

## Executive Summary
Federated recommender systems (FRS) often suffer from subgraph structural imbalance—client subgraphs vary widely in size and connectivity—leading to misaligned local models and poor global aggregation. This paper introduces Low-pass Personalized Subgraph Federated Recommendation (LPSFed) to address these challenges. LPSFed employs a low-pass graph convolutional network to extract low-frequency structural signals that are relatively invariant to subgraph scale, enabling a robust measure of structural similarity between clients. This similarity guides personalized aggregation, weighting the global model toward structurally similar clients. Additionally, LPSFed mitigates localized popularity bias by having each client compute an adaptive margin based on item degree, which is interpolated with a global bias context derived from aggregated client statistics. Evaluations on five public datasets show substantial improvements over state-of-the-art methods, with up to 24.2% gain in NDCG@20.

## Method Summary
LPSFed operates in a federated learning setting where each client holds a subgraph of user-item interactions. The method consists of three main components. First, clients locally train a recommendation model that includes a low-pass graph convolution (LGCN) which projects node embeddings onto the top Φ eigenvectors of the normalized Laplacian, preserving core community structure while suppressing noise. Training uses a bias-aware contrastive loss where the margin for each user-item pair is adaptively set based on local item popularity. Second, each client computes its low-pass eigenvalue distribution and average margin, and sends these along with model parameters to the server. Third, the server constructs a reference graph (via GNMK) from aggregated statistics, obtains its eigenvalue distribution, and computes KL divergences with each client’s distribution to derive a personalization weight. The server then aggregates model parameters and margins, and forms personalized updates for each client by interpolating the global and local values according to the weight. Clients update their models and margins accordingly. This cycle repeats for a fixed number of global rounds.

## Key Results
- LPSFed achieves up to 24.2% improvement in NDCG@20 on Amazon-Book and consistent gains of 6.1–24.2% across five datasets.  
- It significantly outperforms nine state-of-the-art baselines.  
- The method demonstrates robustness to subgraph structural imbalance and effectively reduces popularity bias.

## Why This Works (Mechanism)

### Mechanism 1: Low-pass Spectral Stabilization
- **Claim**: Low-pass filtering extracts structural signals invariant to subgraph size and connectivity.
- **Mechanism**: Apply a low-pass graph convolution (Eq. 3) retaining only the first Φ eigenvectors, suppressing high-frequency noise that varies with local topology.
- **Core assumption**: Graph Fourier modes below cut-off λ_c capture community structure stable across scales.
- **Evidence anchors**:
  - [abstract]: “Low-pass graph convolutional network to each client subgraph, using spectral filtering to extract denoised low-frequency structural signals that are relatively invariant to subgraph scale.”
  - [section 3.1]: “extract denoised structural signals by constructing a low-pass convolution kernel distribution … This low-pass kernel effectively suppresses high-frequency noise while preserving the core structural patterns.”
  - [corpus]: Neighbors include spectral FL methods (FedSSP, S2FGL) validating low-pass filters for heterogeneity.
- **Break condition**: Eigengap δ (λ_{k+1}-λ_k) too small, so low/high frequencies not separable (Thm 3.2). Then similarity metric (Mechanism 2) becomes unreliable.

### Mechanism 2: Similarity-Guided Personalized Aggregation
- **Claim**: Structural similarity to a neutral anchor guides aggregation, reducing misalignment from subgraph imbalance.
- **Mechanism**: Server generates reference graph G_R (GNMK) and its kernel K_R; each client computes KL-divergence ρ_c between K_R and local K_c (Eq. 11); server normalizes ρ_c to \bar{ρ}_c (Eq. 12) and interpolates global model toward local: θ_new = \bar{θ}·\bar{ρ}_c + θ_local·(1-\bar{ρ}_c) (Eq. 14).
- **Core assumption**: KL-divergence between filtered eigenvalue distributions correlates with model misalignment; clients with similar spectra benefit from mutual updates.
- **Evidence anchors**:
  - [abstract]: “compute a client’s structural similarity to a server-generated neutral random graph anchor, which personalizes aggregation by weighting the global model toward structurally similar clients.”
  - [section 3.2]: “computes structural similarity by using the KL-divergence between its local kernel K_c and the reference kernel K_R.”
  - [section 3.4, Thm 3.1]: Proves similarity converges and is bounded by eigengap.
  - [corpus]: FedPUB uses random graphs for client clustering; supports anchor concept.
- **Break condition**: Reference graph G_R does not represent typical subgraph structure (e.g., ER model without community structure), causing poor weights. Table 8 shows GNMK works best; strict privacy (w/o stats) still robust but slightly lower.

### Mechanism 3: Bias-Aware Margin Personalization
- **Claim**: Locally-computed adaptive margin with global interpolation mitigates localized popularity bias.
- **Mechanism**: Each client computes per-user-item margin M_ui^c based on item-degree (Eq. 8); aggregates to scalar M^c (Eq. 10); server averages M across clients to \bar{M} (Eq. 13) and sends updated M^{updated} to each client; client interpolates: fM_ui^c = ω M^{updated} + (1-ω) M_ui^c (Eq. 15); this refined margin used in BC-loss (Eq. 9).
- **Core assumption**: Popularity bias varies across subgraphs; global context of aggregated bias helps correct local skew without exposing raw degrees.
- **Evidence anchors**:
  - [abstract]: “localized popularity bias-aware margin … shared with the server to construct a global bias context and then interpolated with local margin to correct for popularity bias.”
  - [section 3.1]: Details Lbias, M_ui^c computation, and Eq. 15 interpolation.
  - [corpus]: Literature on popularity bias (Abdollahpouri et al., Chaney et al.) identifies feedback loops; this mechanism directly counters them per subgraph.
- **Break condition**: Local M_ui^c too noisy (very sparse subgraph); interpolation weight ω mis-set; or M aggregation loses too much information (but scalar aggregation seems sufficient per Table 4).

## Foundational Learning

### Concept 1: Graph Fourier Transform & Spectral Filtering
- **Why needed here**: Extracts scale-invariant structural features from heterogeneous subgraphs via low-frequency modes.
- **Quick check**: Why is a spatial GNN (e.g., NGCF) unsuitable for subgraph structural imbalance? (Answer: Message passing aggregates over varying neighborhood sizes; deeper layers over-smoothen sparse subgraphs.)

### Concept 2: Federated Aggregation with Heterogeneous Clients
- **Why needed here**: Standard FedAvg averages parameters assuming identically distributed data, failing under structural imbalance.
- **Quick check**: What happens if personalization weight \bar{ρ}_c is reversed (higher for dissimiliar clients)? (Answer: Worse performance—dissimilar updates inject noise.)

### Concept 3: Popularity Bias in Recommendation
- **Why needed here**: Dense subgraphs over-recommend popular items; sparse subgraphs have unstable long-tail learning.
- **Quick check**: Why can’t we simply use global item popularity (available centrally) to debias? (Answer: FL prevents sharing global interactions; each client only sees local degree distribution.)

## Architecture Onboarding

- **Component map**:
  - **Client-side**:  
    1. LGCN layers (Eq. 3) producing per-layer embeddings.  
    2. Pooling MLP (f_θ^Pool) merges layers into single node emb (Eq. 4).  
    3. Predictive MLP (f_θ^Pred) scores user-item pairs (Eq. 5).  
    4. Extract low-pass kernel K_c from eigenvalues (Eq. 6).  
    5. Compute local margin M_ui^c from item degree (Eq. 8) and aggregate to M^c (Eq. 10).  
  - **Server-side**:  
    1. Generate reference graph G_R (GNMK) from average subgraph stats; run GCN → get K_R.  
    2. Receive (θ_c, K_c, M^c) from clients.  
    3. Compute ρ_c = KL(K_R || K_c); normalize to \bar{ρ}_c (Eq. 12).  
    4. Aggregate θ and M (Eq. 13).  
    5. Compute personalized updates: θ_new = \bar{θ}·\bar{ρ}_c + θ_c·(1-\bar{ρ}_c) (Eq. 14).  
    6. Send θ_new, M^{updated} to clients.  
  - **Client update**: Interpolate local margin with M^{updated} → fM_ui^c (Eq. 15); use in BC-loss (Eq. 9).

- **Critical path** (per global epoch):
  1. **Local training** (Stage 1): Clients train LGCN, produce K_c & M^c.  
  2. **Similarity check** (Stage 2): Clients compute ρ_c using server-provided K_R.  
  3. **Server aggregation** (Stage 3): Normalize ρ_c, aggregate parameters & margins.  
  4. **Personalized distribution**: Server sends personalized updates.  
  5. **Client update**: Interpolate margin, continue local training.  
  6. Repeat.

- **Design tradeoffs**:
  - **Random graph construction**: ER vs GNMK. GNMK preserves degree distribution better → better similarity metric (Table 8).  
  - **Φ (cut-off)**: Too small → lose informative frequencies; too large → include noise. Empirically Φ=128 best (Fig 3c).  
  - **ω (interpolation)**: Balances global bias context vs local specificity; ω=0.25 used.  
  - **Precomputing eigenvectors**: Costs O(nΦ²) once vs every epoch; worthwhile for sparse graphs.

- **Failure signatures**:
  - **Low Φ**: Under-smoothing → signals remain sensitive to local noise → misaligned representations.  
  - **High Φ**: Over-smoothing → lose structural distinctions → personalization weakened.  
  - **Eigengap δ small**: Similarity metric ρ_c high variance (Thm 3.1 bound C/δ); aggregation unstable.  
  - **Mismatched G_R**: If reference graph not structurally representative, \bar{ρ}_c meaningless.  
  - **γ too small**: Bias-aware margin ineffective; popularity bias persists (Fig 3a).  
  - **Communication mismatch**: Clients not synchronizing global epochs properly cause staleness.

- **First 3 experiments** (validate design):
  1. **Ablation (Table 4)**: Remove LGCN → catastrophic drop (spatial GNN fails). Remove bias-aware or personalization → significant loss. Validates necessity of both mechanisms.  
  2. **Structural imbalance test (Table 2)**: Group clients by size/degree. LPSFed improves in all groups, especially Large-Dense where bias amplification worst. Validates robustness to heterogeneity.  
  3. **Hyperparameter sweeps (Fig 3)**:  
     - Φ sensitivity: peak at 128, confirming optimal low-pass cut-off.  
     - γ: higher γ reduces bias amplification (Jaccard growth).  
     - τ: moderate τ avoids over/underfitting.  
     These experiments ensure stable operation under varying conditions.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question**: How can the spectral computations (eigendecomposition) in LPSFed be scaled to handle extremely large client subgraphs, and how can its hyperparameters (e.g., Φ, γ, ω) be automatically tuned without manual intervention?
- **Basis in paper**: Appendix H explicitly identifies scalability of spectral approximation and automation of hyperparameter selection as key future research priorities.
- **Why unresolved**: The current implementation relies on a precomputed Lanczos-based eigendecomposition and manual hyperparameter tuning, which may be insufficient for massive graphs or diverse deployment scenarios. These practical constraints limit the method's broad applicability.
- **What evidence would resolve it**: Development and empirical validation of new scalable eigensolvers (e.g., randomized sketching, Chebyshev expansion) on billion‑edge graphs; and an integrated automatic hyperparameter optimization framework (e.g., federated AutoML) that consistently achieves or surpasses manual tuning across multiple benchmarks.

### Open Question 2
- **Question**: Can LPSFed be equipped with rigorous privacy guarantees (e.g., differential privacy) while preserving recommendation accuracy?
- **Basis in paper**: The Ethics Statement claims privacy because only model parameters and scalar values are shared, but no formal privacy analysis (such as differential privacy) is provided to quantify or guarantee protection against reconstruction or membership inference attacks.
- **Why unresolved**: The absence of a formal privacy model leaves open whether structural similarity scores or bias margins leak sensitive user‑item interaction information. The current heuristic argument is insufficient for strong privacy assurances.
- **What evidence would resolve it**: Formal proof or empirical demonstration that the communication protocol satisfies (ε,δ)-differential privacy; systematic evaluation of the accuracy‑privacy trade‑off under varying privacy budgets; and privacy audits using membership inference attacks to quantify leakage.

### Open Question 3
- **Question**: How robust are the theoretical guarantees (Theorems 3.1 and 3.2) to violations of the idealized graph assumptions (e.g., community structure, bipartite topology, power‑law degree distributions)?
- **Basis in paper**: Appendix B’s Assumption 1 models graphs via stochastic block models or graphons, which may not hold for real‑world bipartite recommendation graphs that exhibit heavy‑tailed degree distributions and heterogeneous connectivity.
- **Why unresolved**: The error bounds depend on the idealization and the eigengap; if real graphs deviate significantly (e.g., weak or no community structure, irregular bipartite patterns), the bounds might overestimate stability and misguide parameter choices.
- **What evidence would resolve it**: Empirical correlation between eigengaps and performance across datasets with diverse structural properties; theoretical extensions that explicitly incorporate degree heterogeneity and bipartite structure; and sensitivity analyses that perturb organic graphs to test the stability of the derived bounds.

### Open Question 4
- **Question**: Does compressing each client’s localized popularity bias into a single scalar Mc discard useful information for bias mitigation? Could richer bias representations be shared in a privacy‑preserving manner to improve global bias correction?
- **Basis in paper**: Section 3.1 acknowledges that Mc is aggregated into a "non‑invertible value" to minimize privacy risks, implying a trade‑off that may sacrifice information about the full item‑degree distribution.
- **Why unresolved**: The impact of using only a global scalar on the precision of bias mitigation is unexplored. Richer statistics (e.g., histograms, quantiles) might better capture local skew, but how to share them safely and effectively remains an open design problem.
- **What evidence would resolve it**: Experimentally compare privacy‑preserving schemes such as local differential privacy or secure multi‑party computation for sharing quantized bias summaries; measure improvements in bias‑related metrics (tail recall, popularity amplification) as granularity increases; and identify the point of diminishing returns to inform practical deployment.

## Limitations
- Reproducibility: Key implementation details (partitioning method, GNMK reference graph construction, Mc aggregation over full training positives) are omitted, making faithful replication challenging.
- Real-world robustness: Evaluations rely on spectral partitions; performance under natural client heterogeneity (non-IID user preferences, temporal dynamics) is not validated.
- Scalability: Lanczos eigendecomposition and reference graph generation introduce computational and memory overhead that may not scale to extremely large subgraphs.

## Confidence
- Core mechanisms: High
- Reproducibility: Medium
- Real-world robustness: Medium-Low
- Scalability: Medium

1. Partitioning Sensitivity: Re-run experiments using alternative client partitionings (e.g., random, geographic, temporal splits) to test whether gains hold under natural heterogeneity.
