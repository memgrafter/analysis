# FactorEngine: A Program-level Knowledge-Infused Factor Mining Framework for Quantitative Investment

## Quick Facts
- **arXiv ID:** 2603.16365
- **Source URL:** https://arxiv.org/abs/2603.16365
- **Reference count:** 39
- **Primary result:** FE achieves IC 0.0474 (CSI300) and 0.0536 (CSI500) with excess annual returns 18.99% and 8.36%, substantially outperforming baselines (e.g., ~58% higher IC vs. Alpha158).

## Executive Summary
FactorEngine (FE) introduces a program-level approach to automated alpha factor mining, representing factors as Turing‑complete executable programs. Its core innovation lies in separating logic evolution (handled by an LLM) from parameter tuning (delegated to Bayesian search), combined with a knowledge‑infused bootstrapping module that converts financial research reports into valid factor code. In extensive backtests on CSI300/500 data, FE significantly surpasses state‑of‑the‑art baselines, delivering higher Information Coefficients, annual returns, factor diversity, and lower drawdowns.

## Method Summary
FE comprises three modules: (1) **Bootstrapping** uses a multi-agent pipeline (PDF processing, factor extraction, iterative code generation) to transform unstructured financial reports into executable factor programs, seeding the evolution pool with domain knowledge. (2) **Evolution** maintains a tree‑structured program population. Each iteration selects nodes via UCT, generates macro‑mutations guided by a Chain of Experience (CoE) with an LLM, then executes a two‑phase implementation: LLM‑based code correction followed by parallel Bayesian hyperparameter optimization. Feedback updates node statistics and drives a multi‑island migration scheme. (3) **Integration** elits high‑fitness factors, combines them with Alpha158 to train a LightGBM multi‑factor model, and runs a 5‑day equal‑weight backtest with explicit transaction‑cost modeling.

## Key Results
- For FE‑report (400 iterations), IC reaches **0.0474** on CSI300 and **0.0536** on CSI500; excess annual returns are **18.99%** and **8.36%**, respectively (~58% higher IC and ~126% higher AR vs. Alpha158).
- FE exhibits superior factor diversity (larger Radius of Gyration) and lower drawdowns compared to baseline methods.
- Ablation studies confirm the benefit of Bayesian parameter tuning and knowledge‑infused bootstrapping.

## Why This Works (Mechanism)

### Separation of Logic Revision and Parameter Optimization
FE decouples semantic/logic evolution from numerical parameter tuning. The LLM focuses on high‑level program structure, while a local Bayesian optimizer (e.g., TPE) efficiently explores continuous hyperparameters in parallel. This separation improves search efficiency by leveraging LLMs for discrete, directional insight and specialized algorithms for fine‑grained optimization. Evidence: [section 4.2] describes the two‑stage process; ablation in [section 6.5] shows the Bayesian‑augmented trajectory ("bay_avg") outperforms the unaugmented one.

### LLM-Guided Directional Search Coupled with Bayesian Micro-Search
LLM proposals, informed by a "Chain of Experience" containing historical successes and failures, provide stochastic macro‑mutations. The resulting program’s parameters are then refined by Bayesian search, creating a dense fitness signal. The feedback loop updates tree Q‑values, guiding future proposals. Evidence: [section 4.2] outlines Idea Generation and Implementation phases; [section 6.5] Figure 5 (left) demonstrates the synergistic performance gain.

### Knowledge-Infused Bootstrapping via Multi‑Agent Pipeline
A closed‑loop, three‑stage pipeline processes financial reports: extraction of factor ideas/pseudocode, logic verification, and iterative code generation under strict I/O contracts. This converts qualitative human expertise into a scalable set of executable seeds, providing a stronger evolutionary prior than random or manual initializations. Evidence: [section 6.1] shows FE‑report consistently outperforms FE‑alpha (manual seeds), with gains growing as iteration budget increases.

## Foundational Learning

### Program-level (Turing‑complete) factor representation
**Why needed:** Enables complex control flow, conditionals, and iterative logic beyond the fixed operator sets of symbolic expression systems, dramatically expanding the search space’s expressiveness.  
**Quick check:** What factor logic (e.g., involving loops or stateful updates) is impossible to express with symbolic GP but straightforward in FE?

### Macro‑Micro Co‑evolution
**Why needed:** Separates concerns—LLM handles discrete, high‑level logic mutations (macro), while Bayesian search efficiently optimizes continuous parameters (micro). This division exploits the strengths of each method and prevents the LLM from costly fine‑tuning.  
**Quick check:** In the evolution loop, which stages belong to macro (Idea Generation, Analysis) vs. micro (Implementation‑Phase‑2)?

### Chain of Experience (CoE) for Experience‑Guided Reasoning
**Why needed:** Transmits historical evolution trajectories (including failures) to the LLM, moving beyond single‑parent refinement to trajectory‑aware exploration, thereby improving sample efficiency.  
**Quick check:** How does the Coverage Score (Eq. 2) balance leveraging successful paths and maintaining exploration diversity?

## Architecture Onboarding

### Component map
1. **Bootstrapping Module**: Input = Financial Reports/Manual Factors → Output = Executable Python factor programs (seed pool). Submodules: PDF Processing, Factor Extraction (JSON/pseudocode), Code Generation (iterative correction).
2. **Evolution Module**: Input = Seed Pool → Output = Evolved factor programs. Core loop: (a) Program Selection (UCT on tree), (b) Idea Generation (LLM + CoE → macro mutation), (c) Implementation (Phase 1: LLM code validation/correction; Phase 2: Bayesian parameter search), (d) Feedback Propagation (update Q‑values, store node metadata).
3. **Integration Module**: Input = Evolved program pool → Output = Multi‑factor model for backtesting. Tasks: Elite selection (fitness score filter), correlation management (threshold‑based), LGBM training, portfolio backtesting with costs/slippage.

### Critical path
Report → [Bootstrapping: Extract→Refine→Generate Code] → Seed Program → [Evolution: Select→Ideate (CoE)→Implement (Bayes)→Feedback] × N → Elite Program Pool → [Integration: Filter→Combine→Backtest] → Performance Metrics.

### Design tradeoffs
- **LLM Cost vs. Search Quality**: Powerful LLMs yield better logic but are expensive; FE mitigates by limiting LLM calls to logic creation and offloading evaluation to parallel Bayesian search.
- **Expressiveness vs. Executability**: Turing‑complete programs risk non‑executable outputs; the two‑phase validation (LLM correction then execution) ensures executability before costly search.
- **Diversity vs. Convergence**: Multi‑island with periodic migration promotes diversity, but overly aggressive migration may cause premature convergence on suboptimal logic clusters.

### Failure signatures
- High "Debug" API call ratio (>50%) indicates the LLM struggles to generate valid code, bottlenecking Phase 1.
- Low "Radius of Gyration" (RoG) in factor correlation space shows the evolution is producing redundant factors, failing to explore diverse logic.
- Rapid performance decay in later test years (unmitigated by FE) suggests evolved logic lacks robustness to regime shifts.

### First 3 experiments
1. **Bootstrapping Sanity Check**: Process a known pre‑2017 financial report (e.g., describing a momentum factor). Verify the output is an executable `factor(pricing_data)` function that adheres to the I/O contract and produces plausible, finite signals without NaNs.
2. **Single‑Island Evolution Smoke Test**: Initialize the pool with 2–3 simple manual factors. Run 5 evolution iterations with a small Bayesian budget. Confirm tree updates (Q/N values), node generation, Bayesian parameter suggestions, and monitor `combined_score` trend.
3. **Multi‑Island & CoE Validation**: Configure 2 islands. After 7 iterations, inspect migration logs to confirm top‑3 program copies are transferred. In the next LLM prompt, verify the Chain of Experience includes migrated programs. Run 20 iterations and compare final pool RoG against a single‑island run.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can FactorEngine systematically incorporate alternative data modalities (e.g., news sentiment, social media, macro indicators) alongside OHLCV features to improve alpha factor diversity and predictive power?
- **Open Question 2:** What are the quantitative impacts of realistic transaction costs (slippage, volume limits) and non‑stationary market regimes on out‑of‑sample stability and profitability of FE‑evolved factors, and how can the framework be made more robust?
- **Open Question 3:** Can augmenting the LLM agent with direct, interactive data interrogation capabilities (e.g., querying specific periods, generating ad‑hoc visualizations) enhance the relevance and adaptiveness of macro‑level factor logic revisions?
- **Open Question 4:** How does factor diversity (e.g., Radius of Gyration or correlation topology) correlate with generalization to unseen market periods, and what diversity‑regularization techniques can prevent over‑specialization during evolution?

## Limitations
- **Underspecified CoE sampling logic:** The exact coverage function `Cvg` and hyperparameters (α,β,γ) for selecting experience paths are not detailed, which may affect LLM guidance.
- **Missing Bayesian search details:** Key parameters of the micro‑level optimizer (number of trials, acquisition function, combined_score aggregation) are not provided, hindering faithful reproduction.
- **LLM code generation fragility:** The system’s reliance on LLM‑produced valid code introduces a bottleneck; a high debug call ratio (>50%) could severely stall evolution.
