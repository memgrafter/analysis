# EnvScaler: Scaling Tool-Interactive Environments for LLM Agent via Programmatic Synthesis

## Quick Facts
- **arXiv ID:** 2601.05808  
- **Source URL:** https://arxiv.org/abs/2601.05808  
- **Reference count:** 40  
- **Primary result:** Produced 191 executable tool-interactive environments (~7K scenarios) and achieved +9.50–11.39 point gains on multi-turn, multi-tool benchmarks (BFCL-v3 Multi-Turn, Tau-Bench, ACEBench-Agent) via SFT and RL with Qwen3 models.

## Executive Summary
EnvScaler addresses the scarcity of scalable, consistent tool-interactive environments for training LLM agents. It introduces a two-stage automated synthesis pipeline: SkelBuilder mines themes from existing tasks and programmatically constructs environment skeletons with dual-agent quality assessment; ScenGenerator then generates solvable scenarios and rule-based validation functions for each skeleton. The resulting 191 environments and ~7K scenarios are used for supervised fine-tuning and reinforcement learning, yielding significant improvements on real-world multi-turn tool-use benchmarks. This demonstrates that high-quality synthetic, executable environments can effectively train capable multi-tool agents.

## Method Summary
The pipeline begins with SkelBuilder, which filters existing task corpora (e.g., API-Bank, ToolACE) to identify stateful environments, infers and deduplicates environment descriptions via clustering, and uses an LLM to plan state space, rules, and tool operations. These plans are converted into executable Python class code (attributes and methods). A dual-agent loop—where a testing agent generates tool calls and a checking agent judges outcomes—assesses functional correctness; environments with pass rates below 0.85 are discarded. ScenGenerator then takes each validated skeleton: it generates a JSON initial state respecting the class schema, creates a task requiring state modification, decomposes the task into independent checkpoint conditions, and writes Python validation functions for each. For training, a teacher model (Qwen3-30B-Thinking) interacts with 140 environments under two settings (Non-Conversation: full task upfront; Conversation: progressive task revelation) to produce ~9K trajectories for SFT. Reinforcement learning (Reinforce++) is applied on 51 held-out environments, using the proportion of passed validation functions as reward. Trained models are evaluated on BFCL-v3 Multi-Turn, Tau-Bench, and ACEBench-Agent.

## Key Results
- SFT on Qwen3-4B improved BFCL-MT score from 25.38 to 34.88 (+9.50), Tau-Bench from 55.28 to 66.67 (+11.39), and ACEBench from 55.28 to 66.67 (+11.39).
- RL after SFT further increased gains, demonstrating the effectiveness of state-check rewards and environment diversity.
- The pipeline successfully produced 191 unique environment skeletons and approximately 7,000 task scenarios.

## Why This Works (Mechanism)

**Mechanism 1: SkelBuilder automates environment skeleton creation.** It filters tasks to retain those in stateful domains, infers environment descriptions, clusters and deduplicates them, then uses an LLM to plan state, rules, and tools. The plan is converted into Python class attributes (`Fattr`) and methods (`Fmethi`), merged into an executable file (`Fexec`). A dual-agent loop evaluates correctness: a testing agent generates random tool calls (positive and negative), and a checking agent judges if execution meets expectations based on code, results, and state changes. Environments with pass rate <0.85 are discarded. *Core assumption:* Latent environment themes exist in task corpora and LLMs can generate correct, consistent code when given detailed blueprints; dual-agent assessment approximates functional correctness. *Evidence anchors:* [abstract] "SkelBuilder constructs diverse environment skeletons through topic mining, logic modeling, and quality evaluation"; [section 3] detailed stages and prompts; neighboring work (PoE-World, ToolSandbox) supports programmatic synthesis feasibility. *Break condition:* Pass rate below 0.85.

**Mechanism 2: ScenGenerator produces solvable, challenging scenarios.** Given an environment class, it first generates a JSON initial state that respects the class schema and internal constraints. Using this state, the tool set, and environment rules, an LLM creates a task requiring state modification (e.g., "cancel order X"). The task is decomposed into a checklist of independent "Has …?" conditions. For each condition, an LLM writes a Python function returning `True` iff the final state satisfies it. After an agent trajectory, the reward is the proportion of passed functions. *Core assumption:* Feasibility and difficulty can be controlled by conditioning on a crafted initial state; state-based validation (vs. exact action matching) is robust and flexible; decomposition yields dense, interpretable reward. *Evidence anchors:* [abstract] "ScenGenerator generates multiple task scenarios and rule‑based trajectory validation functions"; [section 4] explains initial state generation, task design requirements, and function generation rules. *Break condition:* Infeasible task, syntactically invalid or misaligned check functions cause regeneration or discard.

**Mechanism 3: Training on synthetic environments transfers to real benchmarks.** Synthetic environments are used in two interaction settings: Non-Conversation (full task given upfront) and Conversation (task revealed progressively). For SFT, a teacher model (Qwen3-30B-Thinking) interacts with 140 environments to produce diverse trajectories, which fine-tune student models. For RL, the student explores 51 unseen environments under Non-Conversation; reward comes from scenario validation functions. Reinforce++ optimizes the policy with a KL constraint. *Core assumption:* Skills learned in synthetic, programmatic environments transfer to unseen real-world environments; state-check reward adequately captures completion; environment diversity and scale avoid overfitting. *Evidence anchors:* [abstract] significant enhancements on BFCL‑v3 Multi‑Turn, Tau‑Bench, ACEBench‑Agent; [section 5] reports large absolute gains, ablations on similarity and scaling, RL curves. *Break condition:* Synthetic distribution too narrow or misaligned with target benchmarks leads to no improvement or degradation.

## Architecture Onboarding
**Component map:**  
Task Mining → SkelBuilder (Discovery, Construction, Assessment) → ScenGenerator (State Gen, Task Gen, Check Func Gen) → Training (SFT/RL) → Evaluation

**Critical path:**  
1. Gather existing task corpora (API-Bank, ToolACE).  
2. Run SkelBuilder: filter tasks → infer & deduplicate environment descriptions → for each: plan → code → assess (discard below threshold).  
3. For each retained skeleton, run ScenGenerator: generate initial state → generate task → generate check functions.  
4. Collect SFT data: teacher interacts with 140 environments in Non-Conversation and Conversation modes; filter invalid trajectories → ~9K samples.  
5. Train student models: first SFT, then optionally RL on 51 unseen environments with reward from check functions.  
6. Evaluate on held‑out benchmarks (BFCL-MT, Tau-Bench, ACEBench-Agent) and report scores.

**Design tradeoffs:**  
- Automation vs. control: LLM‑driven synthesis enables massive scale but introduces variability; prompt engineering and quality thresholds mitigate risks.  
- Assessment cost: Dual‑agent looping requires many tool executions; pass‑rate threshold trades quality against compute/time.  
- Mode diversity: Including both Non-Conv and Conv data yields best overall performance but doubles teacher rollout cost.  
- Reward granularity: State‑check functions provide dense, interpretable rewards but depend entirely on correctness of generated functions; errors lead to mis‑specified rewards.

**Failure signatures:**  
- SkelBuilder: High discard rate at assessment; many tools fail pass rate; generated code has AST errors or logical inconsistencies.  
- ScenGenerator: Teacher rollout shows low trajectory completion; generated tasks reference non‑existent tools/objects; check functions throw exceptions.  
- Training: RL curve does not increase or crashes; validation scores stagnate or drop vs. SFT‑only baseline.  
- Evaluation: No improvement or negative transfer, especially on benchmarks requiring reasoning (e.g., Tau‑Bench Airline) if synthetic environments lack that depth.

**First 3 experiments:**  
1. **Quality threshold ablation:** Vary the dual‑agent pass‑rate threshold (e.g., 0.75, 0.85, 0.95) to study impact on retained environments and benchmark performance.  
2. **Interaction pattern ablation:** Train on Non-Conv only, Conv only, and combined data (as in Table 6) to isolate each setting's contribution to multi‑turn, multi‑tool skills.  
3. **Environment scaling:** Sample subsets with increasing numbers of training environments (e.g., 0, 10, 20, 50, 141) for SFT and measure scores on BFCL‑MT and ACEBench‑Agent (Figure 7) to confirm scaling trends.

## Open Questions the Paper Calls Out
1. How do biases from LLM-based environment synthesis (e.g., in business logic, state definitions, task design) affect the transferability of skills learned from synthetic environments to real-world systems?
2. To what extent can the EnvScaler pipeline be extended to generate open, unbounded environments (e.g., full web browsing, information retrieval) rather than domain-specific, stateful ones?
3. How crucial are real-system characteristics (e.g., interface latency, network fluctuations, partial failures) for training robust agents, and can they be programmatically synthesized in a controlled way?
4. Does the state‑check reward function (based on terminal state validation) fully capture task completion for complex, multi‑step workflows, or does it inadvertently incentivize "creative" but invalid shortcuts?
5. How does scaling the diversity and number of synthetic environments influence generalization to completely unseen domains, and is there a point of diminishing returns?

## Limitations
- Unspecified model assignments and hyperparameters for SkelBuilder sub‑stages and RL (e.g., KL coefficient, rollout budget) hinder faithful reproduction.
- Prompt engineering nuances (few‑shot examples, system messages) and parameters like deduplication similarity threshold are not fully disclosed.
- Teacher interaction details (max steps, stopping condition, invalid trajectory handling) remain unclear, affecting SFT data fidelity.

## Next Checks
1. **Ablation on dual‑agent pass‑rate threshold:** Vary the threshold (0.75, 0.85, 0.95) and measure resulting environment count, quality, and downstream benchmark performance to quantify the trade‑off between quality and quantity.
2. **Cross‑LLM robustness:** Replace LLMs in SkelBuilder (e.g., GPT‑4.1) with alternatives (Claude 3.5, Llama‑3‑70B) and compare environment diversity and training gains to assess model‑agnostic claims.
3. **Task feasibility audit:** Execute teacher rollouts on all generated scenarios and compute completion rates; analyze correlations between initial state complexity, toolset size, and success to expose potential infeasibility or bias.
