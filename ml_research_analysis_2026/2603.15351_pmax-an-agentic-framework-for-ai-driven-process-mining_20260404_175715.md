# PMAx: An Agentic Framework for AI-Driven Process Mining
## Quick Facts
- **arXiv ID:** 2603.15351
- **Source URL:** https://arxiv.org/abs/2603.15351
- **Reference count:** 35
- **Primary result:** PMAx replaces direct LLM analysis with a local, multi-agent framework where an Engineer agent autonomously generates and executes PM4Py-based Python scripts on user data, and an Analyst agent interprets the resulting artifacts, ensuring mathematical correctness and keeping sensitive data on-premise.

## Executive Summary
PMAx is an agentic framework designed to democratize process mining for non-technical users while mitigating two critical risks of direct LLM usage: hallucinations and data privacy breaches. It achieves this by separating analytical tasks into two specialized agents: an Engineer that autonomously generates and executes deterministic Python code (using PM4Py) on local event log data, and an Analyst that interprets the resulting artifacts (models, tables, visualizations). Validated on the BPI Challenge 2017 loan application log using GPT-5.4, the system successfully transformed natural language business questions into accurate, data-grounded reports without ever exposing raw event data to external AI services.

## Method Summary
The framework employs a metadata-driven abstraction layer that extracts only structural summaries (column names, types, samples) from the event log, addressing privacy concerns and LLM context limits. This abstraction, combined with the user's natural language query, is provided to the Engineer Agent, which generates Python scripts constrained to a whitelisted PM4Py API. Scripts undergo static verification and are executed locally; any runtime errors trigger an autonomous self-correction loop. Successful executions produce artifacts stored in a shared state, which the Analyst Agent then interprets into a final report. The Analyst's output is validated against a strict schema to prevent hallucinations, ensuring all interpretations are strictly grounded in the executed results. By relying on deterministic code execution rather than LLM-based metric estimation, PMAx guarantees mathematical correctness.

## Key Results
- Eliminates LLM hallucinations in process mining by replacing direct analysis with deterministic, locally executed code.
- Engineer Agent autonomously translates natural language business questions into executable PM4Py Python scripts.
- Analyst Agent produces accurate, artifact-grounded reports while maintaining strict data privacy (raw logs never leave premises).
- Successfully demonstrated on the BPI Challenge 2017 loan application dataset using GPT-5.4.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** PMAx reduces LLM hallucinations and ensures mathematical correctness by separating code execution from interpretation.
- **Mechanism:** A specialized Engineer Agent generates deterministic Python scripts (using PM4Py) that run locally on the user's raw data. The Analyst Agent then interprets the resulting artifacts, never seeing raw data or computing metrics itself.
- **Core assumption:** Deterministic code execution on local data is more reliable than LLM-based metric estimation for structured analytical tasks.
- **Evidence anchors:** Abstract and section 3.3 describe the Engineer synthesizing executable scripts and Analyst interpreting insights; corpus shows agentic frameworks exist but PMAx's specific split for process mining is novel.
- **Break condition:** If the Engineer consistently generates invalid PM4Py code that fails self-correction, reliable artifacts cannot be produced.

### Mechanism 2
- **Claim:** PMAx preserves data privacy and overcomes LLM context limits by never transmitting raw event logs externally.
- **Mechanism:** A "Data Abstraction" step extracts only lightweight metadata (column names, types, samples) from the event log. This abstraction is sent to agents; all code execution and data processing happens locally.
- **Core assumption:** A sufficient structural summary (schema) guides correct code generation, and that code will properly operate on the full private raw data kept on-premise.
- **Evidence anchors:** Abstract and section 3.2 detail the metadata-driven abstraction layer for privacy and scalability; corpus signals indicate privacy concerns in related work.
- **Break condition:** If metadata abstraction is too impoverished (e.g., missing key attribute relationships), the Engineer will fail to produce valid analysis scripts.

### Mechanism 3
- **Claim:** PMAx improves reliability and reduces human intervention through closed-loop self-correction for code and report synthesis.
- **Mechanism:** Static verification precedes code execution; runtime errors feed back into an iterative refinement loop. Similarly, the Analyst's report is validated against a strict artifact-referencing schema; non-conformance triggers correction.
- **Core assumption:** Automatic capture and reinjection of error traces (from code or schema validation) are sufficient for LLM-based agents to iteratively repair outputs without expert intervention.
- **Evidence anchors:** Section 3.3 and 3.4 describe self-correction loops for code and report validation; corpus contains self-correcting agent references but application to process mining's artifact validation is primarily from this paper.
- **Break condition:** If the LLM cannot resolve an error after the maximal iteration threshold (e.g., fundamental PM4Py API misunderstanding), the system halts, requiring human intervention.

## Architecture Onboarding
- **Component map:** Data Ingestion → Schema Extractor → Collaborative Memory State → (Engineer Agent ⇄ State ⇄ Analyst Agent) → Report UI
- **Critical path:** User query → (Metadata abstraction + query) → Engineer generates code → Static check → Local execution → Artifacts saved → Analyst generates report → Schema validation → Final report
- **Design tradeoffs:**
  - **Security vs. Flexibility:** Restricting Engineer to a predefined `api` object prevents arbitrary system calls but limits spontaneous use of new PM4Py functions not yet wrapped.
  - **Context Efficiency vs. Richness:** Sending only metadata preserves privacy/context but may force Engineer to make assumptions about data semantics (e.g., which attribute is "case ID").
  - **Automation vs. Explainability:** Full self-correction reduces user burden but may create opaque revision chains; the UI's code panel aims to offset this.
- **Failure signatures:**
  - **Engineer Agent:** Repeated static verification failures, imports outside whitelist, attempts to use `open()` or `os` modules.
  - **Analyst Agent:** Output schema rejection (wrong keys, referencing non-existent artifact IDs), verbose reports ignoring artifacts, reasoning about raw data samples.
  - **System:** Artifact persistence failures (disk full), runtime errors exceeding iteration loop (e.g., PM4Py algorithm timeout on huge DFG).
- **First 3 experiments:**
  1. **Metadata Extraction Test:** Load a sample CSV/XES event log. Confirm the schema extractor correctly identifies case ID, activity, timestamp columns and produces a concise summary with attribute samples. Validate this summary is what the Engineer receives.
  2. **Simple Query Execution:** Ask a trivial question ("What is the number of unique cases?"). Verify the Engineer generates a single `pandas` script using `api.get_case_summary()`, it executes without error, and the Analyst produces a one-sentence answer citing the correct metric from the saved dataframe.
  3. **Error Injection & Recovery:** Manually introduce a malformed column name in the metadata (simulating a bad schema). Submit a query requiring that column. Observe the Engineer's first attempt fails (runtime `KeyError`). Confirm the self-correction loop captures the traceback, the Engineer revises the code (e.g., to use a fallback attribute or ask for clarification), and the system either recovers or gracefully halts after max iterations.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can PMAx be effectively extended to handle Object-Centric Event Logs (OCEL) for Object-Centric Process Mining (OCPM)?
- **Basis:** Future Work section explicitly states extension to OCPM is planned, envisioning agentic workflows for relational/graph-based queries.
- **Why unresolved:** Current implementation is based on traditional case event logs; architectural changes needed for OCEL's multi-object, relational nature are not designed or evaluated.
- **What evidence would resolve it:** A functional extension of both agents to generate/interpret PM4Py's OCEL-specific code and a validation case study on an OCEL dataset like OCPA challenge logs.

### Open Question 2
- **Question:** What are the empirical performance bounds and failure modes of the self-correction loop when the Engineer Agent generates syntactically correct but logically flawed or inefficient code?
- **Basis:** Paper describes self-correction for runtime exceptions but does not analyze semantic errors (code runs but produces incorrect results) or loop exhaustion cases.
- **Why unresolved:** Demonstration on BPI 2017 reports manual code verification; no systematic metrics on error frequency, types, or resolution success rate for subtle logical errors.
- **What evidence would resolve it:** A controlled experiment injecting common logical errors (wrong filtering, misapplied algorithm) into generated scripts, measuring the loop's detection/correction ability, and quantifying max iterations/failure rate across diverse queries.

### Open Question 3
- **Question:** To what extent is PMAx's performance and reliability dependent on the specific LLM (e.g., GPT-5.4) used, and what is the minimum capability threshold for a model to function effectively?
- **Basis:** Demonstration exclusively uses "OpenAI’s GPT-5.4"; architecture's success hinges on Engineer's code generation and Analyst's artifact grounding. No comparison across model families or capability thresholds.
- **Why unresolved:** Single proprietary model choice leaves open whether the framework is model-agnostic or requires specific reasoning/coding capabilities; impacts claim of being an open, extensible platform.
- **What evidence would resolve it:** A benchmark evaluation running identical business questions through PMAx with multiple LLMs (GPT-4o, Claude 3.5, Llama 3.1 70B, Mixtral). Metrics: code generation success rate, self-correction iterations, expert-judged report correctness.

### Open Question 4
- **Question:** How does the "metadata-driven abstraction" balance the trade-off between data minimization for the LLM and potential loss of critical contextual information needed for accurate code synthesis?
- **Basis:** Section 3.2 states abstraction overcomes context constraints and mitigates privacy via data minimization; it provides column names, types, samples but not full distributions.
- **Why unresolved:** Paper asserts sufficiency but does not empirically analyze potential failures. Queries requiring value distributions or rare patterns might need richer summaries; the boundary of feasible queries is undefined.
- **What evidence would resolve it:** A study categorizing natural language process mining questions by required data knowledge (value distributions, sequential patterns). Measure success rates with current abstraction versus richer statistical summaries (min/max/unique counts) to map information limits.

### Open Question 5
- **Question:** Can the strict separation of concerns (Engineer for code, Analyst for interpretation) scale to complex, multi-step analytical workflows requiring iterative refinement based on intermediate insights, and does it limit the Analyst's ability to suggest follow-up queries?
- **Basis:** Architecture is built on "divide-and-conquer" and "strict separation of concerns"; workflow is described as a linear pipeline: question -> code -> artifacts -> report.
- **Why unresolved:** Real-world process mining is iterative and exploratory. A user may want follow-up questions based on unexpected findings (e.g., "The first analysis showed a bottleneck; now drill down"). Current design may not support dynamic, insight-driven pivots without restarting.
- **What evidence would resolve it:** User studies with practitioners performing open-ended analysis tasks on PMAx, probing for scenarios where they want to chain/pivot analyses. Log interaction patterns (turns, frustration, abandoned inquiries) compared to integrated agent or traditional tools.

## Limitations
- **LLM model specificity:** System validated only on undocumented "GPT-5.4"; unclear if publicly available models (e.g., GPT-4o, Claude 3.5) can replicate code-generation reliability within constraints.
- **Implementation opacity:** PMAx is an extension within ProMoAI but precise installation steps, module structure, and invocation parameters are not provided; reproduction requires inferring integration points from the codebase.

## Confidence
- **Reduced hallucinations via code-gen/interpret split:** Medium (architectural separation is sound, but evidence is primarily internal; no independent comparative studies)
- **Privacy preservation via metadata abstraction:** Medium (mechanism coherent, but empirical validation on logs with complex schemas is lacking)
- **Self-correction loop reliability:** Low-Medium (design described and shown on one dataset, but systematic evaluation of failure modes and edge cases is absent)

## Next Checks
1. **Metadata sufficiency test:** Process diverse event logs (e.g., with sparse or hierarchical attributes) to measure the Engineer Agent's first-attempt code success rate when provided only schema summaries.
2. **Model substitution benchmark:** Replace GPT-5.4 with state-of-the-art public models (e.g., GPT-4o, Claude 3.5) and compare code executability and report accuracy on identical BPI Challenge 2017 queries.
3. **Error recovery stress test:** Submit intentionally ambiguous or mathematically complex queries to quantify how often the self-correction loop exhausts its iteration limit, and categorize resulting failures (e.g., API misuse vs. logical errors).
