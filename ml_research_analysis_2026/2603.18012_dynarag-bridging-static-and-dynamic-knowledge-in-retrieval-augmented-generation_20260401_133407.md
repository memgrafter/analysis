# DynaRAG: Bridging Static and Dynamic Knowledge in Retrieval-Augmented Generation
## Quick Facts
- **arXiv ID:** 2603.18012
- **Source URL:** https://arxiv.org/abs/2603.18012
- **Reference count:** 10
- **Primary result:** On the CRAG benchmark's API-augmented task, DynaRAG improved accuracy from 34.23% (Direct RAG) to 41.00% and reduced hallucination from 43.09% to 22.09%.

## Executive Summary
DynaRAG is a retrieval-augmented generation system designed for time-sensitive question answering. It augments a static document retrieval pipeline with a dynamic routing mechanism that selectively invokes external APIs when retrieved documents are deemed insufficient. The system employs an LLM-based reranker to filter noisy web results, a threshold-driven sufficiency classifier to gate the fallback decision, and a retriever-aware Gorilla v2 model to execute precise API calls. Evaluated on the CRAG benchmark, DynaRAG demonstrates significant improvements in accuracy and hallucination reduction compared to a baseline static RAG approach.

The core innovation lies in its conservative, evidence-aware routing: it avoids unnecessary API calls when static context is adequate, preserving efficiency, while reliably falling back to dynamic APIs for answers that require up-to-date or structured data. This hybrid strategy addresses a key weakness of traditional RAG—its inability to handle queries where the answer lies outside the retrieved document snapshot.

## Method Summary
DynaRAG processes a query through a sequential pipeline. First, a retriever fetches raw HTML documents from a provided corpus (e.g., web pages). These are cleaned to extract text snippets. An LLM reranker then scores each snippet for relevance to the query; the top-N passages are selected. A sufficiency classifier compares the highest reranker score against a tuned threshold τ. If the score meets or exceeds τ, the passages are fed directly to an answer generator (Llama 3‑70B‑Instruct). If below τ, the system triggers an API fallback: a FAISS index retrieves top-M relevant API schemas from a catalog, which condition Gorilla v2 to generate a syntactically correct API call. The API's response is fused with the static snippets before final generation. The threshold τ is optimized on a development set to balance sufficiency precision and recall.

## Key Results
- **Accuracy gain:** On CRAG Task 2 (API-augmented QA), DynaRAG achieved 41.00% accuracy versus 34.23% for Direct RAG.
- **Hallucination reduction:** Hallucination rate dropped from 43.09% to 22.09%.
- **Routing efficacy:** The sufficiency classifier and API router correctly identified when static context was inadequate, enabling the dynamic knowledge source to provide missing information.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** An LLM-based reranker filters retrieved documents for relevance before generation, reducing noise from web search.
- **Mechanism:** Raw HTML results are cleaned and passed to an LLM that assigns a relevance score `s_j` to each snippet `˜d_ij` given query `q`. Top-N passages are selected by sorting on this score, replacing simpler vector-based retrieval.
- **Core assumption:** LLM judgment of textual relevance more accurately identifies passages containing answer spans than traditional sparse/dense retrievers for heterogeneous web data.
- **Evidence anchors:** The abstract states it "employs an LLM-based reranker to assess document relevance." Section III.D describes the scoring function: `s_j = f_rank(q, ˜d_ij)`.
- **Break condition:** If the reranker consistently misranks relevant documents below the sufficiency threshold, the system will trigger unnecessary API fallbacks even when static context is adequate, increasing latency and cost.

### Mechanism 2
- **Claim:** A fixed sufficiency threshold on the top reranker score determines whether static context is adequate or an API fallback is needed, acting as a conservative guardrail.
- **Mechanism:** The maximum reranker score `s_(1)` is compared to threshold `τ`. If `s_(1) ≥ τ`, generation proceeds with static passages; otherwise, the API router activates. `τ` is tuned on a dev set for sufficiency F1.
- **Core assumption:** The reranker's top-score correlates with the presence of a complete answer in the retrieved set; a low score reliably indicates insufficiency.
- **Evidence anchors:** The abstract mentions "a sufficiency classifier to determine when fallback is necessary." Section III.E formalizes: `δ(q) = 'sufficient' if s_(1) ≥ τ, 'insufficient' otherwise`.
- **Break condition:** The fixed threshold `τ` fails to adapt to query-type distribution shifts (e.g., more complex questions in a new domain), causing either excessive API calls (if `τ` too high) or increased hallucinations from stale static context (if `τ` too low).

### Mechanism 3
- **Claim:** A retriever-aware API router (Gorilla v2 with schema filtering) executes precise, hallucination-resistant tool calls when static context is insufficient.
- **Mechanism:** Upon insufficiency, the system retrieves top-M API schemas via FAISS from a catalog. These schemas condition Gorilla v2, which is fine-tuned to produce syntactically and semantically correct API calls. The API result is fused with static snippets for answer generation.
- **Core assumption:** Conditioning Gorilla v2 on retrieved API schemas (RAT) prevents hallucination of non-existent APIs/parameters and enables generalization to unseen but similar API specs.
- **Evidence anchors:** The abstract notes "Gorilla v2—a state-of-the-art API calling model—for accurate tool invocation... incorporating schema filtering via FAISS." Section III.F explains that retrieved schemas are passed to Gorilla v2 "via Retriever-Aware Training."
- **Break condition:** If the API schema catalog lacks coverage for the needed entity/domain, or if FAISS retrieval fails to surface the correct schema, Gorilla v2 may produce a malformed call or select an irrelevant API, yielding useless results and failing to reduce hallucination.

## Foundational Learning
- **Concept: Standard RAG Pipeline (Retrieve-Then-Generate)**
  - **Why needed here:** DynaRAG extends the baseline "Direct RAG" mentioned in the paper, which naively retrieves and appends documents. Understanding this static baseline is prerequisite to appreciating the dynamic routing innovation.
  - **Quick check question:** What are the two primary failure modes of a static RAG system on time-sensitive queries?
- **Concept: LLM-as-a-Reranker vs. Traditional Rankers**
  - **Why needed here:** DynaRAG replaces typical bi-encoder or cross-encoder rankers (like BM25 or BERT) with an LLM. This shift requires understanding how LLM judgment differs from embedding similarity in handling nuance and ambiguity.
  - **Quick check question:** Why might an LLM reranker be more robust than a dense retriever to web document noise (e.g., boilerplate, ads)?
- **Concept: Tool-Augmented LLMs & API Calling**
  - **Why needed here:** The fallback mechanism relies on an LLM's ability to map a natural language intent to a structured API call. This requires knowledge of function calling paradigms, parameter binding, and error handling.
  - **Quick check question:** What is "Retriever-Aware Training" (RAT) and why does it reduce API hallucination compared to a non-retrieval-augmented LLM?

## Architecture Onboarding
- **Component map:** Retriever -> Data Cleaner -> Reranker -> Sufficiency Classifier -> (Generator) OR (API Router -> Generator)
- **Critical path:** Query initiates the flow. After cleaning and reranking, the sufficiency classifier acts as a gate. A "sufficient" flag routes directly to the generator; "insufficient" triggers the API router, whose result is then combined with static passages before generation.
- **Design tradeoffs:**
  - **Accuracy vs. Latency:** Reranking + API fallback adds seconds of latency versus Direct RAG's single pass.
  - **Precision vs. Recall in Sufficiency:** A high `τ` reduces hallucination (high precision) but increases missing rate (low recall). The paper's fixed `τ` is a blunt tool.
  - **Schema Coverage vs. Generality:** A larger API catalog improves coverage but increases FAISS search time and risk of irrelevant schema retrieval.
- **Failure signatures:**
  - **False "sufficient":** High reranker score on irrelevant but confidently written pages → no API call → hallucination from stale/off-topic text. Monitor: high hallucination rate on dynamic questions.
  - **False "insufficient":** Low reranker score on actually relevant pages → unnecessary API call → increased latency/cost, possible API error. Monitor: high API call rate on static questions.
  - **API Router failure:** Gorilla v2 call malformed or schema not found → API returns error/empty → missing answer. Monitor: high "missing" rate only on API-augmented task.
- **First 3 experiments:**
  1. **Reproduce Table 1:** Run DynaRAG on CRAG Task 2 with provided checkpoints to confirm 41.00% accuracy and 22.09% hallucination baselines.
  2. **Ablation - Reranker:** Replace LLM reranker with BM25, keeping other components fixed. Expected: drop in accuracy/increase in hallucination, showing reranker's filtering value.
  3. **Threshold Sensitivity Sweep:** Vary `τ` on dev set and plot accuracy/hallucination/missing trade-off curves. Expected: clear Pareto front, confirming `τ` is a critical, non-robust hyperparameter.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can DynaRAG reduce reliance on prebuilt API schemas to operate in knowledge domains with sparse or outdated API documentation?
- **Basis in paper:** Section VI.Limitations states: "API Catalog Dependency. DynaRAG depends on a prebuilt set of structured API schemas. In domains with sparse or outdated API specs, fallback performance may degrade."
- **Why unresolved:** The system’s API invocation via Gorilla v2 requires existing schema retrieval; lacking schemas prevents tool use, making DynaRAG ineffective for such domains.
- **What evidence would resolve it:** Evaluate DynaRAG on domains with deliberately removed API specs, measure failure rates, and test schema inference methods (e.g., LLM-generated API calls from natural language) for recovery.

### Open Question 2
- **Question:** What architectural modifications can lower DynaRAG’s latency and computational overhead to enable deployment in low-latency environments?
- **Basis in paper:** Section VI.Limitations notes: "Latency and Computational Overhead. Incorporating reranking, sufficiency classification, and real-time API invocation introduces nontrivial latency and resource demands."
- **Why unresolved:** The sequential LLM calls (reranker, classifier, Gorilla, generator) and external API network calls create high latency, unsuitable for real-time QA.
- **What evidence would resolve it:** Profile latency per component on CRAG, design approximations (e.g., parallelization, early-exit criteria), and measure accuracy-latency trade-offs empirically.

### Open Question 3
- **Question:** Can the fixed sufficiency threshold be replaced with an adaptive mechanism that responds to query or domain shifts to balance missing answers and hallucinations?
- **Basis in paper:** Section III.E suggests "future implementations could explore adaptive thresholding" and Section VI identifies "Static Sufficiency Thresholding" as a limitation: "fixed setting may not adapt well."
- **Why unresolved:** A manually tuned threshold τ may misroute queries in new distributions, causing either excessive API calls (high latency) or insufficient ones (more hallucinations/missing).
- **What evidence would resolve it:** Develop adaptive models (e.g., query-complexity estimators, domain classifiers) that adjust τ dynamically, and compare their F1 on sufficiency classification and downstream accuracy across multiple domain splits.

### Open Question 4
- **Question:** Does DynaRAG’s design generalize to other dynamic QA benchmarks like RealTimeQA, and how does it handle long-tail entities or extremely fast-changing knowledge?
- **Basis in paper:** Section VI.Limitations says: "Benchmark Scope... generalizability... requires further exploration. Future work will extend... to RealTimeQA."
- **Why unresolved:** CRAG’s structure (mock APIs, curated web pages) may not reflect real-world noise or extreme dynamism; performance could drop on benchmarks with noisier retrieval or faster update cycles.
- **What evidence would resolve it:** Replicate the CRAG evaluation pipeline on RealTimeQA or similar datasets, analyze failure cases, and identify which components (reranker, classifier, router) are most sensitive to distribution shifts.

## Limitations
- **Implementation unknowns:** The exact reranker prompt, score parsing, Gorilla v2 version, FAISS embedding model, and schema retrieval size (M) are unreported, risking divergence from the intended behavior.
- **Brittle sufficiency threshold:** The fixed τ tuned on one dev set may fail under domain or query distribution shifts, leading to poor routing decisions.
- **Evaluation scope:** Results are demonstrated only on the CRAG benchmark; generalizability to other dynamic QA settings (e.g., RealTimeQA) is unproven.

## Confidence
- **Core claim** (accuracy ↑34.23→41.00%, hallucination ↓43.09→22.09% on CRAG Task 2): **Medium** (single dataset, modest gain, no statistical significance reported).
- **Mechanism 1 – LLM reranker**: **Medium** (no ablation in paper; could be replaced by simpler rankers; effectiveness depends on unstated prompt).
- **Mechanism 2 – Fixed threshold**: **Low** (rigid design, identified as a limitation, likely brittle across domains).
- **Mechanism 3 – Gorilla v2 API router**: **Medium** (depends on schema coverage and unstated details; RAT is promising but untested on unseen APIs).
