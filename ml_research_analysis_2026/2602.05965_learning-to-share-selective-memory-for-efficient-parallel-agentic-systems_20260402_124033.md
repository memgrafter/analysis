# Learning to Share: Selective Memory for Efficient Parallel Agentic Systems

## Quick Facts
- arXiv ID: 2602.05965
- Source URL: https://arxiv.org/abs/2602.05965
- Reference count: 32
- Primary result: LTS reduces wall-clock runtime by 44.6% (AssistantBench) and 25.1% (GAIA) while improving accuracy (+2.7 percentage points on AssistantBench with GPT-5.1) via selective memory sharing.

## Executive Summary
Parallel agentic systems often waste computation because independent teams repeatedly perform overlapping intermediate steps. This paper introduces Learning to Share (LTS), which equips parallel teams with a global shared memory bank and a lightweight reinforcement learning–based controller that selectively admits intermediate steps. The controller is trained with usage-aware reward shaping to identify steps that are likely to be reused by other teams, while sparsity regularization controls memory growth. On challenging benchmarks GAIA and AssistantBench, LTS achieves substantial speedups (up to 44.6% reduction in wall-clock time) and even improves task accuracy, contrasting with naive memory sharing that harms accuracy. The controller adds negligible overhead (~0.2% of runtime). Results demonstrate that selective admission prevents context pollution and yields high cross-team recall (69.0%) while maintaining performance.

## Method Summary
LTS extends the M1-Parallel baseline, which runs K=3 independent MagenticOne teams. A global shared memory bank stores intermediate steps as (summary, full output) pairs. A lightweight controller (based on Qwen3-0.6B with LoRA and trainable projections) decides, for each step, whether to admit its summary/output to the bank. The controller receives embeddings of the current task query, all existing memory summaries, and the step’s (input, output, summary). Its decision is a binary YES/NO. Orchestrator agents in each team can, at subsequent steps, scan the memory’s summaries and selectively inject the corresponding full outputs into their context. The controller is trained via reinforcement learning on the AssistantBench development set only. The reward signal combines a base trajectory reward (aggregated answer correctness plus a bonus for first answer) with a stepwise usage bonus: for each admitted step later retrieved by any orchestrator within the same trajectory, an extra β is added to its advantage estimate, provided the final trajectory reward is positive. A sparsity regularization term penalizes excessive admissions. Training uses group-relative advantage estimation with G=5 trajectories per task, 5 epochs, and trajectory reuse 10 times. At inference, all agents and orchestrators are frozen; only the controller is used.

## Key Results
- LTS reduces wall-clock runtime by 44.6% on AssistantBench and 25.1% on GAIA compared to the M1-Parallel baseline.
- Task accuracy improves, e.g., +2.7 percentage points on AssistantBench when using GPT-5.1.
- Selective admission achieves 69.0% cross-team recall with 84.9% of step savings; naive memory sharing (add-all) reduces runtime but degrades accuracy. Controller overhead is only ~0.2% of total runtime.

## Why This Works (Mechanism)

**Mechanism 1: Selective admission prevents context pollution**
- Claim: The RL controller filters out noisy or redundant steps, maintaining high-quality shared knowledge.
- How: At each intermediate step, the controller evaluates embeddings of the task query, memory keys, and the step’s (input, output, summary) and outputs a binary decision. It learns to admit only steps that provide cross-team utility, suppressing errors and path-specific attempts.
- Core assumption: Indiscriminate storage clogs agent contexts with irrelevant information, harming performance.
- Evidence: Naive memory sharing reduces accuracy; LTS achieves 69.0% cross-team recall while maintaining performance (abstract, Section 3.2). Cross-recall indicates that nearly 70% of retrieved memories are useful to multiple teams.
- Break condition: If the controller overfits to short-term usage signals, it may reject steps that become useful later (long-horizon dependencies), reducing recall and runtime gains.

**Mechanism 2: Usage-aware RL credit assignment**
- Claim: The controller’s training objective directly ties admission decisions to downstream retrieval events, shaping it to favor knowledge that will be reused.
- Mechanism: For each step t in trajectory τᵢ, the advantage estimate is ˆAₜ = A_base + β·I(t∈U ∧ R(τ)>0), where U are indices of admitted steps that are later selected by any orchestrator. This provides a sparse bonus only for memories that are both admitted and actually used, and only if the overall task succeeded. Policy gradient updates thus reinforce admissions that lead to successful reuse.
- Core assumption: Memory utility is observable only through retrieval; the bonus bridges admission to final outcome.
- Evidence: Section 3.3 defines this advantage; the abstract states usage-aware reward shaping.
- Break condition: If usage signals are too sparse or the retrieval mechanism noisy, the controller may adopt a myopic policy, admitting only immediately obvious steps and missing latent value.

**Mechanism 3: Key-value separation with lightweight summaries**
- Claim: Storing concise summaries as retrieval keys keeps the amount of context each orchestrator must scan small, while still enabling precise matching; full outputs are injected only when needed, preventing context explosion.
- Mechanism: Each memory entry is (summary, raw output). Orchestrators examine only the summary keys to decide which memories to retrieve; the corresponding full value is then added to their context. This design limits per-step context growth even as memory grows.
- Core assumption: Summaries retain enough information for relevance matching; injecting full outputs only after selection keeps context manageable.
- Evidence: Abstract and Section 3.1 describe the design. High cross-team recall (69.0%) suggests summaries are effective for matching.
- Break condition: Summaries that are too coarse or lose critical details will cause orchestrators to miss relevant memories, lowering recall and nullifying efficiency gains.

## Architecture Onboarding

**Component map**  
Task -> Orchestrator Agents (K teams) -> Worker Agents -> Step (input, output, summary)  
Controller (C_θ) receives (task query, memory keys, step) -> YES/NO decision -> admitted steps added to Shared Memory Bank  
Orchestrator Agents also read Shared Memory summaries -> select keys -> inject corresponding full values into context  
Aggregator (A) combines final answers from all Orchestrator Agents

**Critical path**  
1. An orchestrator agent generates an action; a corresponding worker agent produces an output.  
2. The current step (input, output, and generated summary) along with the task query and existing memory summaries are fed to the memory controller C_θ.  
3. C_θ outputs YES/NO; if YES, the (summary, output) pair is added to the shared memory bank.  
4. At the next step, each orchestrator scans all summaries in the memory bank, selects zero or more keys, and injects the associated full outputs into its context.  
5. Steps 1–4 repeat until the team finishes; the aggregator A then combines the final answers from all K teams.

**Design tradeoffs**  
- Selectivity vs. Utility: The sparsity coefficient (λ_sparse) and usage bonus weight (β) control admission sparsity; too high λ_sparse under-admits, too low causes noise.  
- Overhead vs. Gain: The controller adds marginal overhead (~0.2%) but must be kept lightweight to preserve speedup.  
- Summary fidelity: Summaries must be concise yet distinctive; poor summarization harms retrieval recall.

**Failure signatures**  
- Memory growth high + no runtime reduction → controller over-admitting (like LTS-AddAll); check λ_sparse or usage shaping.  
- Low cross-team recall (<50%) → summaries fail to match or controller too conservative; inspect summary quality and retrieval prompts.  
- No accuracy gain on hard GAIA level-3 → controller missing long-horizon utility; usage shaping may need longer credit assignment.

**First 3 experiments**  
1. **Baseline comparison**: Compare M1-Parallel (no memory), LTS (learned selective memory), and LTS-AddAll (naive memory) on AssistantBench and GAIA. Expect LTS to outperform on both runtime and accuracy, LTS-AddAll to reduce runtime but harm accuracy.  
2. **Ablation study**: Remove usage-aware shaping (β=0) and/or sparsity regularization (λ_sparse=0). Higher memory growth and longer runtimes without utility gain are expected.  
3. **Overhead check**: Profile controller inference time as a percentage of total wall-clock runtime; it should be ~0.2% as reported. If higher, examine controller backbone size or projection overhead.

## Open Questions the Paper Calls Out
1. **Persistent memory across tasks**  
   *Question*: Can shared memory be made persistent across tasks to amortize costs on recurring problem types without interference?  
   *Basis*: The current design resets memory per task; persistent memory could capture cumulative knowledge but risks negative transfer (Section 4.5).  
   *Why unresolved*: Not explored; requires careful management to avoid interference.  
   *Resolution evidence*: Evaluate cross-task memory variants across task similarity spectrum; measure runtime reduction and accuracy vs. similarity; analyze interference patterns.

2. **Memory deletion and revision mechanisms**  
   *Question*: How should the controller handle deletion or revision of existing entries to maintain quality over long executions?  
   *Basis*: The paper admits that it does not reason about memory deletion or revision, leaving it for future work.  
   *Why unresolved*: Memory may accumulate outdated, redundant, or incorrect entries that harm retrieval as execution progresses.  
   *Resolution evidence*: Implement deletion policies (e.g., based on usage recency, similarity, contradiction detection) and test on extended horizons or many teams; monitor memory size, retrieval accuracy, and task metrics.

3. **Joint training of agents and controller**  
   *Question*: Does joint training of agent policies and the memory controller yield additional efficiency gains, and what algorithms can stabilize such joint optimization?  
   *Basis*: During training, all agents remain frozen; only the controller’s projection layers and LoRA adapters are updated.  
   *Why unresolved*: Agents might adapt outputs to be more shareable, but credit assignment becomes more complex and training may be unstable.  
   *Resolution evidence*: Develop alternating or two-phase training where agents are fine-tuned with RL (e.g., on memory retrieval rewards) while controller co-adapts; compare against frozen-agent baseline; analyze stability.

4. **Scaling with number of parallel teams**  
   *Question*: How does the number of parallel teams affect the optimal selectivity of the controller and overall efficiency?  
   *Basis*: Experiments use K=3 teams, consistent with prior work.  
   *Why unresolved*: More teams could increase redundancy but also increase memory pollution; the policy may be tuned to K=3 and not scale.  
   *Resolution evidence*: Run experiments varying K (e.g., 1,2,3,5,7) with both fixed controller (trained at K=3) and retrained per K; measure accuracy, runtime, memory size, cross-team recall; analyze scaling trends.

## Limitations
- Missing RL hyperparameters (λ_sparse, β, learning rate, etc.) critical for balancing selectivity vs. utility.
- Summary generation specifics (model, prompt) are undescribed, affecting memory quality and retrieval.
- Controller is trained only on AssistantBench dev; its generalization to GAIA's harder tasks is unvalidated (potential overfitting).

## Confidence
- Overall runtime and accuracy improvements: High
- Selective admission prevents context pollution: Medium
- Usage-aware RL credit assignment works: Low
- Key-value summaries enable efficient reuse: Medium

## Next Checks
1. Ablate RL shaping coefficients: systematically vary β and λ_sparse; monitor memory growth, cross-team recall, and final accuracy. Expect optimal region matching reported metrics (~84.9% admission, 69.0% recall).
2. Audit summary quality: manually sample admitted summaries for conciseness, distinctiveness, and retrieval sufficiency; compare orchestrator success when using summaries vs. full outputs.
3. Test generalization: train the controller on GAIA development set and evaluate on AssistantBench test; a significant drop would indicate benchmark overfitting.
