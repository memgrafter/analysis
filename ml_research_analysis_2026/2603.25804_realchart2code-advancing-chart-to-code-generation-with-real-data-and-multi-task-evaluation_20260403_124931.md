# RealChart2Code: Advancing Chart-to-Code Generation with Real Data and Multi-Task Evaluation

## Quick Facts
- arXiv ID: 2603.25804
- Source URL: https://arxiv.org/abs/2603.25804
- Reference count: 40
- Primary result: RealChart2Code benchmarks chart-to-code generation with 2,896 instances from real Kaggle datasets; evaluation of 14 VLMs shows significant performance gaps, with top proprietary models scoring ~8/10 and open-weight models ~3.6/10.

## Executive Summary
RealChart2Code introduces a challenging benchmark for chart-to-code generation grounded in authentic Kaggle datasets and complex multi‑panel visualizations. It defines three tasks—Replication, Reproduction, and Refinement—to isolate visual translation, raw data processing, and iterative debugging capabilities. Evaluation of 14 vision‑language models reveals that even state‑of‑the‑art proprietary systems (Claude‑4.5‑Opus, Gemini‑3‑Pro‑Preview) struggle, while open‑weight models lag further behind. The benchmark employs a multi‑agent judging system with strong human agreement (Cohen’s κ=0.83) and uncovers distinct error patterns: syntax/execution failures for open‑weight models, data‑mapping errors for proprietary ones, and regressive editing during refinement. These results highlight the remaining gap between current VLMs and the demands of real‑world data visualization assistance.

## Method Summary
The dataset construction begins with over 8,000 Kaggle datasets, filtered for richness to select 1,036 high‑quality ones. Human experts then design 1,016 visualization scenarios across 50+ chart types and 7 high‑level intents, writing reference implementations in Matplotlib/Seaborn. For the Refinement task, errors are manually injected to create flawed starting points. The final 2,896 instances are split among three tasks: (1) Replication: generate code from a chart image; (2) Reproduction: generate code from the image plus raw CSV/XLSX files; (3) Refinement: iteratively fix flawed code via dialogue. Models produce code via API calls (greedy decoding, up to 32k tokens). Generated code is executed in an isolated Docker container (Python 3.13, matplotlib, seaborn, pandas, numpy). Output charts are evaluated by a panel of LLM agents using eight fine‑grained metrics (0‑2 scores) and three quality criteria, with strong correlation to human judgment (Cohen’s κ=0.83).

## Key Results
- Top proprietary models score modestly (Claude‑4.5‑Opus: 8.2, Gemini‑3‑Pro‑Preview: 8.1) on the 10‑point scale.
- Open‑weight models trail significantly (best: Qwen3‑VL‑235B: 3.6).
- Error analysis: open‑weight models fail mainly on syntax/execution; proprietary models on data mapping; refinement often introduces regressive edits.

## Why This Works (Mechanism)
### Mechanism 1  
- **Claim:** RealChart2Code’s grounding in authentic Kaggle datasets and complex multi‑panel layouts creates a more ecologically valid and challenging evaluation, exposing limitations not surfaced by synthetic benchmarks.  
- **Mechanism:** By curating over 8,000 real‑world datasets (≈30 billion rows) and filtering for richness, the benchmark introduces noise, scale, and irregularity that mirror genuine data‑science workflows. It then designs 1,016 visualizations spanning 50+ chart types and 7 high‑level intents, forcing models to perform sophisticated spatial reasoning and compositional layout generation.  
- **Core assumption:** Models trained on clean, synthetic chart data do not automatically generalize to the messiness and complexity of real‑world visualizations.  
- **Evidence anchors:**  
  - [abstract]: “grounded in realistic visualization scenarios and utilizes authentic datasets… incorporates intricate chart structures and a diverse range of chart types.”  
  - [section B.2]: Details the two‑stage filtering of 8,000+ Kaggle datasets into 1,036 high‑quality ones.  
  - [corpus]: The nearest neighbors (e.g., ChartMimic, Plot2Code) focus on single‑panel imitation; none emphasize raw data handling or composite layouts, confirming RealChart2Code’s distinct focus.  
- **Break condition:** If the Kaggle datasets used appeared in model training corpora (data leakage), the benchmark’s difficulty would be artificially reduced. The authors attempted to mitigate this by using raw, unannotated datasets and custom task designs, but the risk remains if models inadvertently memorized similar distributions.

### Mechanism 2  
- **Claim:** The three‑task suite—Chart Replication, Chart Reproduction, and Chart Refinement—diagnostically isolates visual translation, data processing, and iterative debugging capabilities.  
- **Mechanism:** Each task varies input scope: Replication uses only the image; Reproduction adds raw CSV files; Refinement introduces a dialogue‑based correction phase. This structure reveals which sub‑skill fails (e.g., data mapping errors vs. syntax errors).  
- **Core assumption:** A single monolithic task cannot capture the full spectrum of chart‑to‑code competence needed for real‑world assistance.  
- **Evidence anchors:**  
  - [abstract]: “first benchmark to systematically evaluate chart generation from large‑scale raw data and assess iterative code refinement in a multi‑turn conversational setting.”  
  - [section 3.1]: Formal definition and examples of the three tasks.  
  - [corpus]: None of the top related papers describe such a triad of tasks, underscoring RealChart2Code’s novelty in including iterative refinement.  
- **Break condition:** If the tasks are not well‑separated (e.g., success on Replication always implies success on Reproduction), the diagnostic benefit erodes. The paper’s error analysis (Section 5.2) shows divergent error patterns, supporting separation.

### Mechanism 3  
- **Claim:** The multi‑agent judging framework with high inter‑rater reliability (Fleiss’ κ = 0.824) and strong human correlation (Cohen’s κ = 0.83) provides a scalable and trustworthy evaluation of complex visualizations.  
- **Mechanism:** Eight fine‑grained metrics (e.g., chart type consistency, spatial layout) scored 0–2 by multiple LLM agents; aggregated scores reflect nuanced visual fidelity. This approach avoids the brittleness of pass/fail while remaining automated.  
- **Core assumption:** Automated agents, when designed with clear rubrics and redundancy, can approximate expert human judgment at scale.  
- **Evidence anchors:**  
  - [section 3.4]: Describes the evaluation metrics and multi‑agent voting system.  
  - [section 5.1]: Reports κ statistics and shows narrow confidence intervals in Figure 5.  
  - [corpus]: Prior benchmarks rely mainly on execution success rates; RealChart2Code’s multi‑dimensional visual scoring is a methodological advance not present in the nearest works.  
- **Break condition:** If agents fail to detect subtle visual artifacts (e.g., slight color shifts, element overlaps) that humans would catch, the correlation could drop on unseen error types. The authors acknowledge this limitation but demonstrate strong current agreement.

## Foundational Learning
### Concept: Chart‑to‑Code Generation  
- **Why needed here:** The paper’s entire focus is on evaluating this task. Understanding that it requires reverse‑engineering a visualization image into executable code (rather than generating a chart from a description) is fundamental to interpreting the benchmark’s design and results.  
- **Quick check question:** What are two key differences between chart‑to‑code generation and the more common text‑to‑visualization task?

### Concept: Data Leakage in Benchmarks  
- **Why needed here:** The authors contrast RealChart2Code with prior benchmarks that risk data leakage (i.e., test data appearing in model training). Grasping this concept explains why RealChart2Code’s scores are lower and its construction choices are made.  
- **Quick check question:** How does the two‑stage Kaggle filtering process help avoid data leakage, and why is data leakage particularly problematic for code generation benchmarks?

### Concept: Multi‑Turn Iterative Refinement  
- **Why needed here:** The Chart Refinement task adds a conversational debugging dimension that is unusual in existing benchmarks. Recognizing its significance is key to understanding the paper’s claim of comprehensive evaluation.  
- **Quick check question:** According to the error analysis, what is “regressive editing” and what does it reveal about model limitations?

## Architecture Onboarding
- **Component map:** Data Ingestion → Filtering Module → Task Designer → Ground‑Truth Implementation → Error Injection → Instance Construction → Execution Sandbox → Multi‑Agent Judge → Aggregation & Reporting.
- **Critical path:** Kaggle → Filter → Task design → Ground‑truth code → (Error injection) → Dataset assembly → Model inference → Sandbox execution → Rendering → Multi‑agent scoring → Final metrics.
- **Design tradeoffs:**  
  - *Matplotlib‑only:* Ensures granular control and a uniform standard, but excludes other libraries; however, this simplifies evaluation and focuses on fundamental visualization logic.  
  - *Sandbox isolation:* Provides security and reproducibility, but may limit use of certain advanced packages; the environment is pre‑built to cover common needs.  
  - *LLM‑based judge:* Highly scalable and consistent, but may miss subtle visual nuances; the authors mitigated this by strong correlation with human evaluation and multi‑agent voting.  
  - *Expert human curation:* Produces high‑quality ground truth and error injection, but is time‑consuming and not easily extensible; the dataset size remains moderate (2,896 instances) for tractable human review.
- **Failure signatures (from error analysis):**  
  - Open‑weight models: frequent syntax/execution errors (e.g., hallucinated libraries like `seaborn‑v0_11`).  
  - Proprietary models: data mapping errors (wrong column‑to‑visual mapping) despite correct layout.  
  - Multi‑panel layouts: overlapping subplots, missing `GridSpec` usage, incorrect grid dimensions.  
  - Canvas scaling: disproportionate figure size leading to tiny plots or excessive whitespace.  
  - Composite charts: flattened semantic structures (e.g., treating joint‑plot components as separate subplots).  
  - Iterative refinement: regressive editing—fixing one error introduces another due to poor context maintenance.
- **First 3 experiments:**  
  1. **Smoke test:** Run a small model (e.g., Qwen3‑VL‑7B) on 5 random Replication instances to verify the pipeline (loading data, API call, execution, scoring) works end‑to‑end.  
  2. **Task separation:** Evaluate Claude‑4.5‑Sonnet on all three tasks; compare pass rates and scores. Expect Replication > Reproduction > Refinement in difficulty, and note that error types differ (syntax vs. data mapping).  
  3. **Complexity gap replication:** Take a model that excels on ChartMimic (e.g., Gemini‑3‑Pro‑Preview) and run it on RealChart2Code; confirm the ~50% score drop shown in Figure 7, validating the benchmark’s increased difficulty.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can Vision-Language Models be architecturally improved to reliably perform iterative code refinement without introducing regressive errors in multi-turn conversations?
- **Basis in paper:** [inferred] The error analysis in §5.2 identifies "Regressive Editing" as a critical failure mode in the Chart Refinement task, where models fix one issue but inadvertently break previously correct parts of the code.
- **Why unresolved:** Current models, even state-of-the-art proprietary ones, show fundamental weaknesses in maintaining global code consistency during localized edits. The paper does not propose specific architectural or training interventions to address this.
- **What evidence would resolve it:** An ablation study demonstrating that a modified model (e.g., with enhanced state tracking, program analysis, or verification modules) achieves a statistically significant reduction in regressive error rates on the Chart Refinement task while maintaining or improving overall performance.

### Open Question 2
- **Question:** Can the generation of high-quality, complex synthetic training data for chart-to-code tasks effectively bridge the performance gap on benchmarks like RealChart2Code, and what are the key principles for ensuring such synthetic data matches the complexity and diversity of authentic Kaggle datasets without data leakage?
- **Basis in paper:** [explicit] The Conclusion and Future Works section explicitly states: "we aim to develop automated pipelines for generating high-quality synthetic data to address the scarcity of complex training examples and improve model generalization on intricate layouts."
- **Why unresolved:** The paper identifies the scarcity of complex training data as a limitation but does not define the methodology, validation criteria, or scalability of such a pipeline. It is unknown if synthetic data can replicate the "noise, scale, and irregularity" of real-world datasets (§7 Limitations) without simply memorizing patterns from existing benchmarks.
- **What evidence would resolve it:** The release of a scalable synthetic data generation pipeline for visualizations, accompanied by empirical evidence that models trained on this synthetic data show significant (e.g., >15% absolute) performance gains on RealChart2Code's Chart Reproduction and Refinement tasks, with rigorous checks confirming no direct contamination from the benchmark.

### Open Question 3
- **Question:** What underlying architectural or training differences cause proprietary VLMs to predominantly fail on "Data Mapping Errors" while open-weight models are most susceptible to "Syntax and Execution Errors," and can targeted fine-tuning or expert systems be designed to mitigate these distinct failure modes?
- **Basis in paper:** [explicit] Figure 6 and §5.2 explicitly categorize and contrast error patterns: "Open-weight models... are particularly susceptible to Syntax and Execution Errors... Proprietary models... demonstrate robust coding capabilities... Their failures are predominantly Data Mapping Errors."
- **Why unresolved:** The paper observes this dichotomy but does not investigate its root causes (e.g., differences in training data composition, code-specific fine-tuning, reasoning chain length, or tool-use capabilities). No solutions are proposed to specifically strengthen open-weight models' spatial logic or proprietary models' data semantics alignment.
- **What evidence would resolve it:** A controlled study ablating components (e.g., code-specific pre-training data volume, execution-based reinforcement learning, or integrated symbolic reasoning modules) that demonstrates a causal shift in the error distribution of a given model family toward more complex, data-centric errors, indicating progress on the previously weaker skill.

### Open Question 4
- **Question:** Do current automated evaluation metrics (based on multi-agent judges) fully capture subtle visual fidelity issues in complex multi-panel charts, such as precise spatial relationships, minimalist design errors, or semantic grouping integrity, and how can evaluation be refined to better align with expert human judgment on these nuanced dimensions?
- **Basis in paper:** [inferred] The Limitations (§7) state: "our MLLM-based judges... may still fail to detect subtle visual artifacts, such as minor element overlaps or precise color nuances." The evaluation rubric (§C.1.1) uses ±2-15% tolerances for spatial and color metrics, but it is unclear if these thresholds align with human perception of "fidelity" for intricate layouts like joint grids or hierarchical dashboards (see Error Cases 2 & 4).
- **Why unresolved:** While Cohen's κ=0.83 shows strong correlation, the paper provides no breakdown of agreement on the most complex instances or on the specific "subtle artifacts" mentioned. The metrics may not penalize the semantic layout decomposition failures (Error Case 4) appropriately.
- **What evidence would resolve it:** A fine-grained error analysis on a subset of the most complex charts (e.g., those with nested subplots, composite charts) where human experts judge whether the automated metrics correctly scored visible fidelity issues. This could lead to revised rubric definitions or supplementary programmatic checks (e.g., for bounding box overlaps, alignment precision) that improve correlation on these hard cases.

### Open Question 5
- **Question:** Are the capabilities evaluated on the Matplotlib-centric RealChart2Code benchmark transferable to other plotting ecosystems (e.g., Plotly, Seaborn, ggplot2, D3.js), and does mastery of imperative Matplotlib code serve as a sufficient proxy for general visualization reasoning?
- **Basis in paper:** [explicit] The Limitations (§7) state: "our code implementations are currently confined to Matplotlib... the granular and imperative nature of Matplotlib code effectively reflects a model’s fundamental visualization understanding... serving as a robust proxy for general plotting skills." This is an unstated assumption that requires validation.
- **Why unresolved:** The benchmark's design and scoring are tightly coupled with Matplotlib's API (e.g., GridSpec, subplot management). Models may simply learn to produce Matplotlib snippets without grasping higher-level visualization grammar (e.g., the *Grammar of Graphics* underlying Plotly or ggplot2). Performance on Matplotlib may not predict success in declarative or JavaScript-based environments.
- **What evidence would resolve it:** A parallel evaluation suite using the same set of chart images but with code generation prompts for a different library (e.g., Plotly Express). If a model's ranking order or absolute scores change significantly, it would challenge the "proxy" claim and indicate library-specific rather than general reasoning skill.

## Limitations
Major uncertainties and limitations identified by the authors:
- **Data leakage risk:** Despite filtering, Kaggle datasets might appear in model training corpora, potentially understating difficulty.
- **Judge opacity:** Multi‑agent LLM judge configuration (models, prompts, voting) is not fully disclosed, limiting replicability and external trust.
- **Refinement regression:** The "regressive editing" phenomenon is noted but not mechanistically analyzed; root causes (context loss, over‑correction) are unclear.
