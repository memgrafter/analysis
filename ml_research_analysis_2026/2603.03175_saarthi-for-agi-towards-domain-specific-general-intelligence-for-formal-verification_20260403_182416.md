# Saarthi for AGI: Towards Domain-Specific General Intelligence for Formal Verification

## Quick Facts
- **arXiv ID:** 2603.03175
- **Source URL:** https://arxiv.org/abs/2603.03175
- **Reference count:** 40
- **Primary result:** 70% improvement in assertion accuracy and 50% reduction in iterations to coverage closure on NVIDIA's CVDP suite.

## Executive Summary
Saarthi is a framework that leverages large language models (LLMs) for automated formal verification, specifically for generating SystemVerilog Assertions (SVA) and achieving coverage closure. It mitigates LLM hallucinations through two key innovations: a structured rulebook and specification grammar that standardize SVA generation, and GraphRAG integration that grounds agent reasoning in a domain-specific knowledge graph. Evaluated on NVIDIA's CVDP benchmark, Saarthi significantly improves assertion accuracy (70%) and reduces the number of iterations needed to reach coverage closure by 50%, representing a step toward domain-specific general intelligence in hardware verification.

## Method Summary
Saarthi employs a multi-agent orchestration (using Microsoft AutoGen) to automate the formal verification workflow. It begins by parsing natural language specifications into a canonical rulebook format (keywords: Signals, Property, Condition) to constrain LLM output and reduce syntactic/semantic errors. A GraphRAG service constructs a knowledge graph from authoritative sources (standards, RTL, prior assertions) and retrieves relevant subgraphs to ground agent decisions. The workflow iterates: generate assertions via a property author agent, fix syntax errors through a dedicated pipeline, run formal verification, analyze coverage reports to identify gaps, and generate new assertions. Failures trigger root cause analysis. Human-in-the-loop (HIL) corrections are captured to enrich the rulebook and prompts, creating a self-improving feedback loop.

## Key Results
- 70% improvement in assertion accuracy (measured by % Proven) compared to baseline LLM generation.
- 50% reduction in iterations required to achieve coverage closure on NVIDIA's CVDP suite.
- Demonstrated effectiveness across multiple foundation models (GPT-4.1, GPT-5, Llama 3.3), with GPT-5 showing strongest performance on complex designs.

## Why This Works (Mechanism)
### Mechanism 1: Structured Rulebook and Specification Grammar
- **Claim:** A structured rulebook and specification grammar reduces syntactic and semantic errors in SystemVerilog Assertion (SVA) generation by enforcing a deterministic, keyword-based intermediate representation.
- **Mechanism:** Natural language specifications are parsed into a canonical set of keywords (Signals, Property, Condition) that constrain the LLM's output space, minimizing ambiguous interpretations and aligning generation with SVA syntax rules. Cached mistake examples provide concrete repair patterns.
- **Core assumption:** That a constrained, structured intermediate representation is more reliably mapped to correct SVA code by an LLM than unstructured natural language prompts.
- **Evidence anchors:** The abstract states the rulebook improves "accuracy and controllability of SystemVerilog Assertion (SVA) generation." Section D details the keyword-based specification format and shows a before/after comparison where the structured format yields a correct property on the first attempt.
- **Break condition:** If the original specification is too vague or complex to be mapped into the predefined keyword categories, the rulebook's constraint becomes a bottleneck, leading to incorrect or incomplete property generation.

### Mechanism 2: GraphRAG Integration
- **Claim:** Integration of GraphRAG grounds agent reasoning in domain-specific, relational knowledge (e.g., signal protocols, design hierarchies), reducing hallucinations and enabling multi-hop inference for more accurate assertion suggestions and root cause analysis.
- **Mechanism:** A knowledge graph is built from authoritative sources (standards, RTL, prior assertions). When an agent queries for guidance (e.g., "how to check WLAST matches AWLEN?"), GraphRAG retrieves a relevant subgraph of interconnected nodes (signals, relations, rules) rather than isolated text chunks. The LLM conditions its response on this structured evidence, improving factual consistency and traceability.
- **Core assumption:** That the relational structure of a knowledge graph provides a superior evidence context for complex, interconnected hardware verification queries compared to vector-based chunk retrieval.
- **Evidence anchors:** The abstract cites GraphRAG integration to "provide agents with access to technical knowledge" and links it to improved accuracy. Section II.C defines the approach and provides a concrete AXI protocol example showing how the graph retrieves and links `AWLEN`, `WLAST`, and handshake rules to generate a correct check.
- **Break condition:** If the knowledge graph is incomplete, poorly constructed, or the query requires inference beyond the stored relationships (e.g., novel protocol corner cases), GraphRAG retrieval will fail to provide adequate grounding.

### Mechanism 3: Iterative Multi-Agent Workflow with HIL Refinement
- **Claim:** An iterative, multi-agent workflow with automated coverage hole analysis and Human-in-the-Loop (HIL) refinement creates a feedback loop that progressively improves assertion quality and convergence toward coverage closure.
- **Mechanism:** Coverage agents analyze verification reports to identify uncovered design regions. They then generate targeted assertion requests. Generated assertions cycle through syntax-fixing and validation agents. Failures (CEXs) trigger a multi-agent Root Cause Analysis (RCA). The HIL pipeline captures human corrections, which enlarge the rulebook and fine-tune prompts, creating a self-improving dataset.
- **Core assumption:** That decomposing verification into specialized, sequential agents and systematically feeding back tool diagnostics and human corrections can overcome the one-shot failure modes of standalone LLM generation.
- **Evidence anchors:** The abstract mentions "automated coverage hole–filling" and HIL data collection, linking them to reduced iterations. Section III.B describes the multi-agent workflow and feedback loop. Section III.C details the HIL response capture mechanism.
- **Break condition:** If the initial assertion set is fundamentally insufficient (e.g., missing critical design invariants) or if the coverage model is inaccurate, the iterative loop may converge to a local optimum far from full closure, and HIL corrections may not generalize.

## Foundational Learning
### SystemVerilog Assertion (SVA) Syntax & Semantics
- **Why needed:** The rulebook's keyword grammar directly maps to SVA constructs (`property`, `assert`, `@(posedge clk)`, `|=>`, `disable iff`). Understanding the formal semantics (e.g., implication vs. leads-to, vacuity) is essential to judge if a generated property matches the spec.
- **Quick check:** Given the spec "if `req` is high, `ack` must be high within 2 cycles unless `error` is high," write the correct SVA property and identify why `req |=> ##[1:3] ack unless error;` is wrong? (Hint: `unless` applies to the entire property, not just the consequent; correct: `req |=> (##[1:3] ack) unless error;` or use `disable iff`.)

### Knowledge Graph Construction & Querying
- **Why needed:** GraphRAG's efficacy depends on a well-structured KG where nodes are verification artifacts and edges capture relationships (`implements`, `constrains`). One must understand how to extract and link these from technical documents.
- **Quick check:** For a simple FIFO, what KG nodes and edges would you create to represent the relationship between `wr_en`, `rd_en`, `full`, and the conditions that set `full`? (Nodes: `wr_en`, `rd_en`, `full`, `fifo_depth`; Edges: `wr_en` increments count, `rd_en` decrements count, `full` when count == depth.)

### Formal Verification Coverage Metrics
- **Why needed:** The 50% reduction in iterations metric is based on achieving coverage closure. Understanding line/expression/transition/FEC coverage and vacuity is necessary to interpret benchmark results and agent goals.
- **Quick check:** What is the difference between a proof (property holds for all scenarios) and coverage (exercising all design behaviors), and why might you have high proof % but low coverage %? (Proof checks specific assertions; coverage measures how much of the design state space was exercised. High proof % could be from simple assertions that don't explore corner cases, leaving coverage low.)

## Architecture Onboarding
### Component Map
Orchestrator (AutoGen) → PropertyGenerationAgent → (parallel) SyntaxErrorFixingPipeline (Analyzer→Fixer→Validator) & CoverageAgent (LocationAnalyzer→SVAPropertyEngineer) → FormalVerificationExecutor → (on failure) RCATeam (VCDParser, SpecAssertionAnalyst, RTLAnalysis, Verifier) → CodeExtractor/Manager → HIL. GraphRAG service sits behind all LLM calls.

### Critical Path
1. Input spec → Rulebook grammar → PropertyGenerationAgent.
2. Generated code → SyntaxFixPipeline → Valid compilation.
3. Compiled assertions → Formal run → Coverage report.
4. Coverage gaps → CoverageAgent → new assertions → loop back to step 2.
5. CEX → RCATeam → patch proposal → loop back to step 2.

### Design Tradeoffs
- Rulebook strictness vs. specification expressiveness (avoids hallucination but may reject valid complex specs).
- GraphRAG precision vs. latency (graph traversal is slower than vector search).
- Fully automated iteration vs. HIL cost (auto runs cheap but may plateau; HIL boosts metrics but requires expert time).

### Failure Signatures
1. Repeated syntax errors at validation → Rulebook grammar likely missing patterns for that spec type.
2. Low coverage % after multiple iterations → GraphRAG graph likely lacks key protocol relationships or coverage agent is generating shallow assertions.
3. High vacuity warnings → Assertions are too generic or triggering conditions are incorrect; RCA needed on property semantics.

### First 3 Experiments
1. **Rulebook Sanity Check:** Take a simple, unambiguous spec from the paper's Figure 6 (e.g., "Done Signal Validity"). Feed it without the rulebook (raw NL) and with the rulebook (keyword format) to the PropertyGenerationAgent. Compare first-generation success rate over 10 runs.
2. **GraphRAG Retrieval Validation:** For a known protocol (e.g., AXI handshake), formulate a query like "What ensures data validity during a write burst?" Manually inspect the subgraph retrieved by GraphRAG. Does it contain nodes for `WVALID`, `WREADY`, and the `data transfer` relationship? Does the generated assertion cite these nodes?
3. **Coverage Loop Termination Test:** Run the full Saarthi flow on the "Memory Scheduler" design from CVDP. Record coverage % after each of 5 autonomous iterations (as in Table III). Identify the iteration where coverage gain drops below 2%. This defines a practical auto-run limit before HIL is needed.

## Open Questions the Paper Calls Out
1. **Automated spec-parsing:** Can the natural language specification-to-keyword conversion step be automated to fully realize the rulebook's potential and reduce human intervention?
2. **GraphRAG quality:** How effectively does the GraphRAG component construct and retrieve knowledge subgraphs that capture complex, multi-hop temporal and protocol semantics from formal verification standards and RTL documentation?
3. **Coverage iteration limits:** Why do autonomous coverage improvement iterations show diminishing or negative returns for some designs (e.g., Automotive IP, AXI4Lite in Table III), and what mechanisms could enable agents to strategically terminate or redirect their efforts?
4. **HIL compounding:** To what extent does the Human-in-the-Loop (HIL) data collection pipeline actually enable continuous learning and reduce future human intervention, beyond immediate one-off fixes?
5. **Model differences:** What specific architectural or reasoning differences between foundation models (GPT-4.1, GPT-5, Llama 3.3) explain their divergent performance on complex designs like the Float Multiplier, and how can these insights inform agent design?

## Limitations
- Knowledge graph schema and construction method are unspecified, hindering faithful reproduction.
- Rulebook grammar and mistake-caching mechanism lack detail; complex specifications may bottleneck.
- Benchmarking restricted to NVIDIA CVDP designs; generalizability uncertain. Use of proprietary LLMs (GPT-4.1, GPT-5) limits reproducibility.

## Confidence
- Rulebook & grammar: Medium
- GraphRAG integration: High
- Iterative multi-agent workflow: Medium
