# DSevolve: Enabling Real-Time Adaptive Scheduling on Dynamic Shop Floor with LLM-Evolved Heuristic Portfolios

## Quick Facts
- **arXiv ID:** 2603.27628
- **Source URL:** https://arxiv.org/abs/2603.27628
- **Reference count:** 11
- **Primary result:** Reduces average makespan by 33.2 units on hard dynamic scheduling scenarios vs. best AHD baseline (EoH) while occupying 68.5 of 1000 MAP-Elites cells, demonstrating superior behavioral diversity and adaptability.

## Executive Summary
DSevolve addresses dynamic manufacturing scheduling where machine breakdowns and new orders require dispatching rules to adapt within seconds. Existing LLM-powered heuristic design produces only single static rules. DSevolve’s offline phase evolves a quality-diverse portfolio of interpretable dispatching rules using multi-persona seeding and topology-aware evolutionary operators within a MAP-Elites archive. Online, a lightweight probe fingerprint characterizes the current shop floor state, enabling rapid retrieval and selection of the best-suited rule from the archive via look-ahead simulation. Evaluated on 500 industrial instances, it achieves significant makespan reductions and maintains high diversity, enabling real-time adaptation to disruptions.

## Method Summary
Offline, an LLM-driven evolutionary loop generates a diverse archive of dispatching rules. The process initializes the population with seven persona prompts (e.g., "Extreme Greedy") to seed distinct behavioral niches, then uses topology-aware operators—distance-maximization crossover and contrastive mutation—to actively explore the 3D feature space (load skewness, waiting ratio, diversity) while maintaining a MAP-Elites grid. Online, a 6-dimensional fingerprint (instantaneous state + features from a fast SPT probe) is computed at each disruption. This fingerprint retrieves candidate rules from a knowledge base built by evaluating all archive rules on 100 calibration instances. The best rule is selected via rapid look-ahead simulation from the current state and dispatched until the next event.

## Key Results
- Makespan reduction: 33.2 units on hard dynamic scenarios versus best AHD baseline (EoH).
- Behavioral diversity: Archive occupies 68.5 cells out of a 1000-cell MAP-Elites grid, substantially outperforming baseline archives (31.7–47.3 cells).
- Adaptability: Probe-based retrieval significantly outperforms global-best or random rule selection across all evaluated AHD frameworks.

## Why This Works (Mechanism)
DSevolve’s performance arises from three synergistic mechanisms. First, multi-persona seeding initializes the evolutionary population with seven orthogonal scheduling philosophies, pushing initial rules into separate regions of the behavioral feature space and preventing premature convergence. Ablations confirm performance degrades when this seeding is removed. Second, topology-aware operators use the current MAP-Elites archive structure to guide variation: crossover pairs the most behaviorally distant individuals, and mutation targets crowded cells with prompts requesting opposing characteristics. This actively sustains diversity, evidenced by higher archive occupancy. Third, a lightweight probe-based fingerprint—derived from a fast SPT simulation and instantaneous metrics—effectively characterizes shop floor states. Retrieval via weighted Euclidean distance to calibration fingerprints, followed by look-ahead simulation, selects instance-appropriate rules; this retrieval consistently outperforms alternatives, confirming the fingerprint’s predictive power.

## Foundational Learning
- **Quality-Diversity (QD) Optimization / MAP-Elites**  
  *Why needed:* DSevolve seeks a diverse archive of high-performing rules across behavioral niches, not a single optimum. MAP-Elites discretizes the feature space and maintains the best rule per cell.  
  *Quick check:* If a cell already holds a high-quality rule, what pressure generates a *different* rule for that cell? (Answer: New individuals must outperform the elite to replace it; otherwise, they occupy new cells.)

- **Behavioral Feature Space Design**  
  *Why needed:* The entire system relies on a low-dimensional embedding of a rule’s scheduling behavior (e.g., load skewness, waiting ratio). These dimensions define “diversity” and drive both evolution and retrieval.  
  *Quick check:* Would two rules with drastically different code but identical feature values be considered redundant? This tests whether features capture meaningful behavioral distinctions.

- **Case-Based Reasoning (CBR) / Retrieval-Augmented Generation**  
  *Why needed:* The online component avoids real-time synthesis by retrieving pre-evaluated candidates from a knowledge base indexed by problem-state fingerprints.  
  *Quick check:* What is the trade-off between knowledge base size (number of calibration instances) and online latency? Larger KB improves coverage but increases candidate set size for simulation.

## Architecture Onboarding
- **Component map:** Offline Evolution Engine (LLM + MAP-Elites) → Knowledge Base Constructor (evaluates rules on calibration instances, stores fingerprints and top-R rules) → Online Scheduler (disruption handling, fingerprint computation, retrieval, look-ahead simulation, dispatch)
- **Critical path:** End-to-end latency is dominated by the look-ahead simulation of candidate rules (up to *k*×*R*, e.g., 20). Fingerprint computation and similarity search must be faster than this simulation loop to meet second-level response requirements.
- **Design tradeoffs:** Archive size vs. retrieval cost; feature space dimensionality vs. grid sparsity and distance reliability; probe rule simplicity vs. discriminative power.
- **Failure signatures:** Archive underutilization (selection concentrated in few cells); retrieval mismatch (high variance in retrieved rule performance); latency spike (candidate set too large).
- **First 3 experiments:**  
  1. *Feature Sanity Check:* Inspect rules from different archive cells; confirm their priority logic and resulting schedules align with expected differences in load skewness and waiting ratio.  
  2. *Probe Robustness Test:* Re-run evaluation using alternative probe rules (e.g., LPT, SRM) for fingerprinting; verify that the performance advantage of probe-based retrieval persists.  
  3. *Latency Benchmark:* Instrument the online loop to measure time for fingerprint computation, KB retrieval, and simulation of 20 candidates; confirm total latency stays below 2 seconds.

## Open Questions the Paper Calls Out
- Can the manually defined three-dimensional behavioral feature space be automatically learned or expanded to better capture niche behaviors for different manufacturing domains or objectives?
- Is the SPT-based probe fingerprint optimal, or could alternative probes (e.g., learned lightweight policies or ensembles) improve retrieval accuracy and scheduling performance?
- How does the variance-weighted Euclidean distance metric compare to more sophisticated similarity measures (e.g., learned metrics) in matching current states to effective historical rules?
- Can DSevolve’s framework be extended to multi-objective dynamic scheduling (e.g., minimizing makespan while maximizing on-time delivery or minimizing energy)?

## Limitations
- Missing exact persona prompts for initialization, risking inconsistent diversity outcomes.
- Undisclosed generation parameters for the 100 calibration instances (scale, job/machine counts, flexibility levels), hindering faithful reproduction.
- Ambiguous implementation of the code similarity function (`f_div`), affecting diversity measurement.
- Incomplete LLM call parameters (temperature, max tokens) for evolutionary operators.
- Neighboring literature focuses on DRL/GP, offering limited direct validation for DSevolve’s specific components.
