# SciDER: Scientific Data-centric End-to-end Researcher

## Quick Facts
- **arXiv ID:** 2603.01421
- **Source URL:** https://arxiv.org/abs/2603.01421
- **Reference count:** 5
- **Primary result:** Outperforms SOTA on AI-Idea-Bench (nearly doubles novelty), MLE-Bench (36.40% gold), and SciCode (15.38% main, 42.71% sub solve rates); human helpfulness 4.846/5.000.

## Executive Summary
Existing AI research agents struggle with autonomous processing of raw experimental data and translating abstract hypotheses into executable code for specialized scientific domains. SciDER addresses this gap through a modular, data-centric system comprising four collaborative agents—Ideation, Data Analysis, Experimentation, and Critic—augmented by a self-evolving memory that categorizes knowledge for retrieval-augmented generation. Evaluated on AI-Idea-Bench, MLE-Bench (Lite), and SciCode, SciDER achieves substantial gains, nearly doubling novelty scores on AI-Idea-Bench, securing a 36.40% gold medal rate on MLE-Bench, and reaching up to 42.71% solve rate on SciCode, while receiving high helpfulness ratings from human evaluators.

## Method Summary
SciDER automates the scientific research lifecycle for data-centric domains. The system accepts raw experimental data (e.g., CSV, JSON, Parquet, images), a research query, and optional prior papers or code. It orchestrates four LLM-based agents via LangGraph: the Ideation Agent formulates hypotheses; the Data Analysis Agent examines data structure, quality, and semantics; the Experimentation Agent writes and executes code; and the Critic Agent evaluates outputs, providing feedback for iterative refinement. A self-evolving memory mechanism stores and retrieves reasoning chunks, adapting to task- and project-specific contexts. The pipeline uses gemini-2.5-flash for ideation and main control, and Claude 4 Sonnet for coding tasks via the Claude Code framework. After each stage, the Critic may request revisions, enabling multi-round improvement before producing final reports and code.

## Key Results
- AI-Idea-Bench novelty scores nearly double: 47.06 (motivation) and 44.52 (experiment).
- MLE-Bench (Lite) gold medal rate reaches 36.40%; SciCode solve rates are 15.38% (main) and 42.71% (sub), surpassing GPT-5.
- Human evaluators rate SciDER’s helpfulness at 4.846 out of 5.000.

## Why This Works (Mechanism)
SciDER’s effectiveness stems from its modular, memory-augmented architecture. Specialized agents allow focused capabilities: ideation for creative hypothesis generation, data analysis for interpreting raw inputs, experimentation for translating ideas into executable code, and critique for ensuring quality and feasibility. The self-evolving memory provides retrieval-augmented generation, grounding each agent’s decisions in relevant past successes and domain knowledge. Iterative critique loops catch errors and bias early, while the orchestrator (LangGraph) manages state transitions and memory updates, enabling coherent multi-step reasoning. Leveraging frontier LLMs (Gemini, Claude) supplies strong foundational capabilities, which are further refined through the structured workflow.

## Foundational Learning
- **Retrieval-Augmented Generation (RAG)** – *Why needed:* To ground LLM outputs in relevant, up-to-date knowledge, reducing hallucinations and improving factual accuracy. *Quick check:* Does the system retrieve prior experiments or papers before generating new hypotheses?
- **Multi-Agent Systems** – *Why needed:* Complex tasks can be decomposed into specialized roles, improving performance and interpretability. *Quick check:* Do agents have distinct responsibilities and communicate via a shared state?
- **Self-Evolving Memory** – *Why needed:* Long-term knowledge accumulation across tasks enhances reasoning without fine-tuning. *Quick check:* Does the system store intermediate reasoning and reuse it in future similar problems?
- **Iterative Critique** – *Why needed:* Multiple evaluation rounds catch errors that a single pass might miss. *Quick check:* Is there a dedicated critic agent that can request revisions from prior agents?

## Architecture Onboarding
**Component map:**  
User (query + raw data) → Ideation Agent → Data Analysis Agent → Experimentation Agent → Critic Agent → Final Output. All agents access a global Self-Evolving Memory; Critic can trigger iteration back to any prior agent. LangGraph coordinates state transitions.

**Critical path:** Initial ideation, data analysis, experiment coding, execution, critique, and (if needed) revision loops. The path may cycle between Experimentation and Critic repeatedly before finalization.

**Design tradeoffs:** Modularity improves specialization but adds coordination overhead; external LLM APIs offer high capability but incur cost, rate limits, and privacy risks; memory retrieval enhances relevance but requires tuning to avoid noise; open-ended iteration improves quality but increases runtime.

**Failure signatures:** API errors (rate limits, invalid keys), data parsing failures (unsupported formats), infinite critique loops (excessive iterations), and irrelevant memory retrievals (low-quality context).

**Three first experiments:**  
1. Replicate the Kepler Exoplanet case study using the provided example dataset and query to validate the end-to-end pipeline.  
2. Run a single task from AI-Idea-Bench to test hypothesis generation and novelty scoring.  
3. Solve a simple problem from SciCode to assess code generation, execution, and critic feedback.

## Open Questions the Paper Calls Out
1. **Automatic manuscript generation** – The paper lacks a paper-writing module; integrating one would require handling narrative structure, citations, and alignment of results with claims. Evidence: Add a dedicated agent trained on scientific corpora and evaluate on benchmarks like PaperBench.  
2. **API dependency constraints** – Reliance on external APIs limits scalability, cost-effectiveness, and data privacy for sensitive datasets. Evidence: Run controlled experiments comparing API-based vs. local LLM deployments on cost, speed, failure rates, and privacy audits.  
3. **Memory component contributions** – The relative impact of short-term vs. long-term memory categories on novelty and feasibility is unknown. Evidence: Perform ablations on AI-Idea-Bench, selectively disabling memory types, and analyze retrieval patterns.  
4. **Critic feedback dimensions** – Which aspects of the critic’s feedback (accuracy, completeness, bias detection, etc.) most improve code executability? Evidence: Ablate individual critic criteria on SciCode and measure changes in solve rates and correctness.  
5. **Generalization to novel domains** – It is unclear whether SciDER generalizes to unseen data formats and experimental paradigms. Evidence: Test on raw datasets from underrepresented fields (e.g., climate simulations, quantum chemistry) and compare success rates to in-distribution benchmarks.

## Limitations
- Exact prompts, critic rubrics, and memory parameters are undisclosed, hindering faithful replication.
- Support for non-standard scientific file formats (e.g., FITS, HDF5) beyond CSV/JSON/Parquet is unclear.
- Dependency on proprietary LLMs (Gemini, Claude) introduces cost, rate limits, and potential output variability across API versions.

## Confidence
