# ResearchPilot: A Local-First Multi-Agent System for Literature Synthesis and Related Work Drafting

## Quick Facts
- **arXiv ID:** 2603.14629
- **Source URL:** https://arxiv.org/abs/2603.14629
- **Reference count:** 7
- **Primary result:** A functional local-first multi-agent system that decomposes literature review into four stages (retrieve, extract, synthesize, draft), achieving end-to-end processing in ~12.5 seconds with 10 papers and producing a structured markdown draft.

## Executive Summary
ResearchPilot is an open-source, local-first system that assists researchers in drafting related work sections by breaking down the literature review process into a transparent pipeline of four stages: retrieval, structured abstract extraction, cross-paper synthesis, and citation-aware drafting. Built with DSPy for typed orchestration and FastAPI/Next.js for the frontend, it supports multiple LLM providers and offers fallback mechanisms against external service failures. The system has been validated with automated tests and demonstrated to complete an end-to-end query in approximately 12.5 seconds, retrieving 10 papers and generating a draft of about 2046 characters. Its design prioritizes inspectability and reproducibility over opaque single-prompt approaches.

## Method Summary
ResearchPilot operationalizes literature review as a fixed sequence of four DSPy-defined agents: SearchAgent retrieves papers from Semantic Scholar and arXiv; ExtractionAgent parses each abstract into a structured JSON schema (e.g., background, methods, results); SynthesisAgent aggregates the extractions to produce a narrative of consensus, contradictions, and open gaps; WriterAgent generates a markdown draft with proper citations. The system accepts a natural-language query and optional runtime overrides (model provider, API key, embedding mode). All intermediate outputs are stored in SQLite, and optionally vectorized in Qdrant for search.

The architecture is local-first: core services (FastAPI backend, Qdrant, Next.js frontend) can be run via Docker Compose, with optional remote APIs. It supports multiple embedding strategies (remote, local, auto) and tolerates partial failures—e.g., if Semantic Scholar rate-limits, it continues with arXiv; if Qdrant is unavailable, keyword fallback is used. Evaluation is currently functional: 11 backend and 1 frontend automated tests pass, and an end-to-end demo shows a full run in 12.47 seconds.

## Key Results
- End-to-end runtime: 12.47 seconds for 10 papers.
- Output: Structured extractions for all retrieved papers, a synthesis identifying consensus/contradictions/open-gaps, and a 2046-character markdown draft.
- Validation: All 11 backend tests and 1 frontend test passed; system exhibits resilience to external API limits and embedding failures via graceful fallbacks.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Decomposing literature review into a fixed four-stage pipeline (retrieve → extract → synthesize → draft) increases transparency and inspectability compared to a single opaque prompt.
- **Mechanism:** Each stage has explicit input/output contracts (Table 1) and runs as an isolated module with its own prompt/LLM call. Intermediate artifacts (paper list, structured extractions, synthesis) are persisted and exposed to the user.
- **Core assumption:** Segmenting the cognitive sub-tasks aligns better with LLM capabilities and allows targeted validation at each boundary.
- **Evidence anchors:**
  - [abstract] "decomposing the task into a transparent four-stage pipeline"
  - [section 5] Detailed contracts for `SearchAgent` → `ExtractionAgent` → `SynthesisAgent` → `WriterAgent`
  - [corpus] Neighbors like *Facets, Taxonomies, and Syntheses* also use structure, but ResearchPilot specifies a fixed sequence; *RepoReviewer* uses a similar staged approach for code review.
- **Break condition:** If any stage produces invalid/non-conforming output (e.g., JSON parsing failure in extraction), the pipeline may halt or propagate errors, as observed in provider JSON variance failures.

### Mechanism 2
- **Claim:** Using DSPy for orchestration with typed signatures enables model-provider agnosticism without per-provider prompt rewriting.
- **Mechanism:** Each agent is defined by a DSPy `Signature` with typed input/output fields (e.g., `List[Paper]`, `Synthesis`). The runtime binds these signatures to configured models (OpenAI, Anthropic, etc.) via environment settings, letting DSPy handle prompt compilation and output parsing.
- **Core assumption:** Different LLM providers can reliably follow structured field definitions when guided by a compiled DSPy program.
- **Evidence anchors:**
  - [abstract] "DSPy for typed orchestration... supports multiple model providers through configuration rather than prompt rewrites"
  - [section 6.1] "Each agent is implemented as a DSPy module or signature with explicit input and output fields"
  - [corpus] Neighbors use various frameworks (LangChain, custom); *LitLLM* mentions tool use but not typed orchestration. Evidence for DSPy’s role is primarily from the paper’s design description.
- **Break condition:** If a provider’s output consistently deviates from the declared schema (e.g., missing fields), the signature-based parsing fails, requiring runtime overrides or prompt adjustments.

### Mechanism 3
- **Claim:** A local-first architecture with fallback paths (partial retrieval tolerance, local embeddings, keyword search) maintains functionality despite external service limitations.
- **Mechanism:** The system decouples core logic from external dependencies: retrieval tolerates one source failing; embeddings can use local models (`BAAI/bge-small-en-v1.5`) if remote APIs are unavailable; Qdrant failures fall back to SQLite keyword search.
- **Core assumption:** Users can run the entire stack locally without relying on any single cloud service’s uptime or quotas.
- **Evidence anchors:**
  - [abstract] "local-first architecture... supports bring-your-own-key model access and remote-or-local embeddings"
  - [section 7] Details three embedding modes (`remote`, `local`, `auto`) and fallback to keyword search.
  - [section 9.3] "External API rate limits... Missing remote embeddings... Persistence-layer errors" with mitigations listed in Table 3.
  - [corpus] *MemX* and *RepoReviewer* also emphasize local-first designs, suggesting this is a viable pattern for privacy/control.
- **Break condition:** If all retrieval sources fail (e.g., both Semantic Scholar and arXiv return errors) and no cached papers exist, the pipeline cannot proceed past stage 1.

## Architecture Onboarding
- **Component map:**
  - Frontend: Next.js SPA → POST `/research` (stream) & GET `/reports` (history)
  - Backend: FastAPI → DSPy pipeline (4 agents) → SQLite (reports) + Qdrant (vectors)
  - Agents: `SearchAgent` (Semantic Scholar/arXiv), `ExtractionAgent` (per-paper JSON), `SynthesisAgent` (cross-paper), `WriterAgent` (markdown)
  - Config: `.env` for defaults; per-request overrides for provider/model/key.
- **Critical path:**
  1. User submits query with optional overrides.
  2. Backend launches pipeline, streams `agent_started`/`agent_completed` events.
  3. `SearchAgent` retrieves & dedupes papers → store in SQLite.
  4. `ExtractionAgent` runs per paper → store extractions.
  5. `SynthesisAgent` aggregates extractions → store synthesis.
  6. `WriterAgent` produces draft → store final report.
  7. Report vectorized → stored in Qdrant (if available).
- **Design tradeoffs:**
  - Abstract-only vs. full-text: Keeps latency low but limits fidelity to abstract content.
  - Fixed sequence vs. dynamic: Simpler to debug but may not suit all review styles.
  - Local embeddings (cheap, private) vs. remote (potentially higher quality, rate-limited).
- **Failure signatures:**
  - `SearchAgent`: HTTP 429 from Semantic Scholar → warning, continue with arXiv.
  - `ExtractionAgent`/`SynthesisAgent`: JSON parse error → schema validation failure, partial results saved.
  - `Qdrant`: Connection error → fallback to keyword search, warning logged.
  - Streaming: Client disconnect → backend continues but frontend stops receiving updates.
- **First 3 experiments:**
  1. **End-to-end smoke test:** Run with defaults (`groq` + `llama-3.3-70b` + local embeddings). Verify 10 papers retrieved, all stages complete, report appears in history.
  2. **Partial-failure test:** Block Semantic Scholar (e.g., via `/etc/hosts`). Submit query. Expect arXiv-only retrieval with 429 warning, full pipeline completion.
  3. **Malformed output test:** Modify `ExtractionAgent` prompt to intentionally omit a JSON field. Observe schema validation warning, extraction stage skips invalid papers, synthesis proceeds with valid subset.

## Open Questions the Paper Calls Out
1. How does the multi-stage pipeline compare in output quality and researcher utility to a single-prompt RAG system or a simpler baseline? The authors state the current evaluation is "functional rather than comparative" and that a stronger future study would compare the multi-stage pipeline against simpler baselines, including human ratings for output usefulness and citation quality.
2. Can a dedicated "verification agent" effectively detect and flag unsupported or inaccurate citations in the generated draft without prohibitive latency? The limitations explicitly state the draft is "citation-aware but not citation-verified" and that claim or citation verification agents are a promising future direction, but feasibility, accuracy, and cost remain unknown.
3. To what extent does the reliance on abstract-only extraction limit the fidelity and completeness of the synthesized consensus, contradictions, and gaps? The limitations list "abstract-only extraction" and note that abstracts are often insufficient for precise reporting of datasets, experimental settings, or quantitative outcomes; the paper does not measure how much critical information is missed.
4. Does the fixed sequential four-stage pipeline optimally balance inspectability, latency, and output quality, or could a more dynamic agent routing (e.g., parallel extraction, iterative synthesis) improve outcomes? The architecture uses a fixed sequence reflecting the stable structure of literature-review work, but the trade-offs of alternatives like parallelizing extraction or allowing synthesis to trigger re-retrieval are unexplored.

## Limitations
- Evaluation is limited to functional metrics (success/failure, runtime); no human assessment of draft quality or comparative studies.
- Implementation details (DSPy signatures, frontend-backend override configuration) are not fully documented; reproduction depends on repository code completeness.
- Generalizability of claims about transparency and inspectability lacks user validation; benefits to researcher understanding remain assertions.
