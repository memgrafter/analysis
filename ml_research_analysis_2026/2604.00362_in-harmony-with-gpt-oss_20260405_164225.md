# In harmony with gpt-oss

## Quick Facts
- **arXiv ID**: 2604.00362
- **Source URL**: https://arxiv.org/abs/2604.00362
- **Reference count**: 10
- **Primary result**: Achieved the first independent reproduction of gpt-oss-20b benchmark scores, matching published results within confidence intervals.

## Executive Summary
OpenAI's gpt-oss-20b model was evaluated on key benchmarks using proprietary tool formats and an undisclosed harness, preventing outside verification. This work reverse-engineered the model's in-distribution tools (container.exec, repo_browser.print_tree/search/open_file, apply_patch) by analyzing its spontaneous tool calls. The authors then built a native Harmony agent harness that bypasses the lossy Chat Completions conversion, preserving token efficiency and exact format fidelity. Running the same benchmarks (SWE Verified and AIME25 with tools) with this setup produced scores that align with the original publication (e.g., SWE Verified HIGH 60.4% vs. 60.7%), demonstrating that the previously observed gaps were artifacts of the evaluation harness rather than model limitations.

## Method Summary
The reproduction relied on two key technical steps. First, the team captured and dissected the model’s spontaneous tool invocations during benchmark runs to deduce the precise signatures and behaviors of its internal tools. Second, they implemented a native Harmony harness that directly consumes and produces Harmony-structured messages, eliminating the need to translate tool calls through the Chat Completions API. This harness was then used to evaluate the gpt-oss-20b model on the SWE Verified and AIME25 with tools suites. The resulting scores closely matched the originally reported numbers, confirming that the reverse-engineered tools and harness accurately emulate the intended evaluation environment.

## Key Results
- SWE Verified HIGH: 60.4% (original 60.7%), MEDIUM: 53.3% (original 53.2%).
- AIME25 with tools: 91.7% (original 90.4%).
- All reproduced scores fall within the expected confidence intervals, validating independent replication.

## Why This Works (Mechanism)
The original evaluation likely suffered from two inefficiencies: (1) converting Harmony tool calls to Chat Completions format introduced token bloat and semantic loss; (2) the proprietary harness may have applied additional transformations that altered model behavior. By using a native Harmony harness that directly handles the tool call format, the authors preserved the exact interface the model was trained on, thereby eliminating these sources of discrepancy. The reverse-engineered tools further ensured that the execution environment matched the in-distribution setup. Consequently, the model’s true performance on these benchmarks is revealed, aligning with the published figures.

## Foundational Learning
- **Reverse Engineering Tool Calls**  
  *Why needed*: The proprietary tool specifications were undocumented, so understanding the exact input-output format was essential to faithfully replicate the environment.  
  *Quick check*: Validate that the inferred call patterns cover all tool variants observed in the spontaneous logs.

- **Native Harmony Harness**  
  *Why needed*: Converting tool calls through Chat Completions adds latency, token overhead, and may distort semantics; a native harness maintains format fidelity and efficiency.  
  *Quick check*: Compare token counts and parse accuracy between native and converted runs on a sample task.

- **Token Efficiency**  
  *Why needed*: Excessive tokens can truncate context or cause the model to behave differently, skewing benchmark results.  
  *Quick check*: Measure average tokens per task and ensure they are comparable to the original reported usage.

- **Benchmark Reproducibility**  
  *Why needed*: Independent verification is a cornerstone of scientific rigor; it ensures that reported scores are not artifacts of hidden implementation details.  
  *Quick check*: Run the entire benchmark with multiple random seeds; results should fall within a narrow confidence interval.

## Architecture Onboarding
- **Component map**: gpt-oss-20b → Harmony Parser → Tool Dispatcher → Tool Environments (container, repo_browser, apply_patch). The harness coordinates the loop: model generates Harmony-formatted output, parser extracts tool calls, dispatcher routes to the appropriate executor, results are formatted back into Harmony and fed to the model.

- **Critical path**: The end-to-end sequence from model generation to tool execution and back must preserve latency and avoid message transformation. The critical path is: model output → Harmony parsing → tool invocation → result capture → Harmony formatting → model input. Any overhead or conversion here can affect token budget and thus model performance.

- **Design tradeoffs**: Native integration vs. modularity: a fully native harness is efficient but may be tightly coupled to a specific model or tool set. The authors chose to implement model-specific parsers, sacrificing generalizability for fidelity. Another tradeoff: simplicity of a single unified format versus supporting multiple tool variants; the harness focuses on the three observed tools.

- **Failure signatures**: Typical failures include malformed Harmony messages (causing parse errors), token overflow when feeding tool results back to the model, and tool execution errors (e.g., container failures). These manifest as abrupt termination or abnormal score drops and can be detected via logging.

- **Three first experiments**:  
  1. *Cross-harness comparison*: Run a subset of SWE Verified tasks with both the native Harmony harness and a Chat Completions wrapper; measure token usage and score delta.  
  2. *Full benchmark validation*: Execute the entire SWE Verified and AIME25 with tools suites using the native harness to confirm score parity across all difficulty levels.  
  3. *Tool call fidelity audit*: Manually inspect a random sample of tool calls from the harness to ensure the arguments and responses match the expected schemas and semantics.

## Limitations
- Reverse-engineered tool specifications may not exactly match the proprietary definitions used by OpenAI, as they rely solely on observed spontaneous calls.
- The native harness evaluation was performed only on the gpt-oss-20b model, limiting generalizability to other architectures or sizes.
- The attribution of score gaps to harness/format mismatches assumes no confounding factors such as test set variations or model updates between runs.

## Confidence
- Tool reverse-engineering correctness: Medium  
- Native harness fidelity: High  
- Independent score reproduction: High  
- Harness/format mismatch as primary cause: Medium
