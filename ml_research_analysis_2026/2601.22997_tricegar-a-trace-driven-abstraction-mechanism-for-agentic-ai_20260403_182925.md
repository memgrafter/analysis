# TriCEGAR: A Trace-Driven Abstraction Mechanism for Agentic AI

## Quick Facts
- **ArXiv ID**: 2601.22997
- **Source URL**: https://arxiv.org/abs/2601.22997
- **Reference count**: 33
- **Primary result**: Automates state abstraction from execution traces via decision tree learning, refines with counterexamples, constructs MDPs for probabilistic model checking, and uses run likelihood for anomaly detection; in file I/O agent evaluation, detected injected anomalies but incurred false positives.

## Executive Summary
TriCEGAR addresses the manual state abstraction bottleneck in runtime verification for agentic AI. It automatically constructs a predicate tree (decision tree) from execution traces, uses counterexample-guided abstraction refinement, and builds an MDP from abstracted traces to enable quantitative probabilistic model checking (e.g., Pmax(success), Pmin(failure)). Additionally, it computes run likelihoods to flag anomalous executions. In an evaluation with a file I/O agent (1000 baseline, 1000 anomalous traces), TriCEGAR successfully detected injected anomalies, though it also produced false positives, indicating the need for further refinement to improve precision.

## Method Summary
TriCEGAR intercepts agent events to capture execution traces consisting of concrete states and tool invocations. It learns an initial predicate tree via a decision tree algorithm that splits states based on information gain computed from the distribution of next actions; abstract states correspond to leaves. Abstracted traces are projected onto these leaves and used to construct an MDP: abstract states become MDP states, actions become transitions, and transition probabilities are estimated from empirical counts. The MDP is exported to a probabilistic model checker (Storm) to evaluate reachability properties (Pmax, Pmin). For runtime guardrailing, each new execution’s prefix is mapped to abstract states and its likelihood is computed; low likelihood relative to a statistical baseline triggers an anomaly warning. If model checking reveals a spurious counterexample (a violating abstract path with no corresponding concrete trace), the responsible leaf’s concrete states are re‑split using the same information gain criterion to refine the abstraction. The pipeline can iterate.

## Key Results
- TriCEGAR detected all injected anomalies in the file I/O agent evaluation.
- The approach incurred false positives, particularly for ratio‑based anomalies, suggesting overgeneralization in the abstraction.
- Quantitative bounds (Pmax(success), Pmin(failure)) were produced, but false positives indicate the need for improved precision via refinement.

## Why This Works (Mechanism)

### Mechanism 1: Data-Driven Abstraction via Decision Tree Learning
**Claim:** TriCEGAR automatically constructs a meaningful initial state abstraction by learning a predicate tree (decision tree) from execution traces, avoiding manual rule definition.
**Mechanism:** It applies a greedy decision-tree construction on observed concrete states, using information gain (IG) on the empirical next-action distribution as the splitting criterion. Each internal node tests a predicate (e.g., `filesWritten > 0`), routing states to leaves that become abstract states.
**Core assumption:** The next tool invocation is a reliable behavioral signal; distinct action distributions indicate semantically meaningful state separations.
**Evidence anchors:**
- [abstract] "learn predicate trees via decision trees"
- [section 4.1.3] Details the IG-based splitting procedure and initialization.
- [corpus] Neighbors like "AgentGuard" and "Multi-Threaded Software Model Checking via Parallel Trace Abstraction Refinement" confirm abstraction-from-traces is an active research direction.
**Break condition:** If initial traces under-sample diverse behaviors, IG may split on noise or miss critical partitions, leading to overfitting or insufficient abstraction granularity (Section 6, Limitations).

### Mechanism 2: Counterexample-Guided Abstraction Refinement
**Claim:** TriCEGAR refines its abstraction by identifying leaves that support spurious counterexamples (abstract violations with no concrete trace evidence) and splitting them to reduce behavioral uncertainty.
**Mechanism:** After model checking, if a counterexample path cannot be concretized in the observed trace trie, the responsible leaf's concrete states are re‑split using the same IG criterion to separate divergent next‑action distributions.
**Core assumption:** A spurious counterexample indicates that the abstraction merged concrete states with distinct future behaviors; targeted splitting improves model precision.
**Evidence anchors:**
- [abstract] "refines them using counterexamples"
- [section 4.1.5] Describes the spuriousness check via trace trie and refinement targeting.
- [section A.4] Formalizes the loop: "If the witness is unsupported‑by‑log...refine".
**Break condition:** Refinement may terminate if no split yields IG above a threshold, if a resource bound (max depth/leaves) is hit, or if splitting leads to overfitting on small trace sets (Section 6).

### Mechanism 3: Online MDP Construction and Likelihood-Based Guardrailing
**Claim:** TriCEGAR builds a Markov Decision Process (MDP) from abstracted traces and uses transition likelihoods to provide quantitative bounds (`Pmax(success)`, `Pmin(failure)`) and detect anomalous runs.
**Mechanism:** Abstract states (tree leaves) and tools (actions) form MDP vertices and actions. Transition probabilities are empirical frequencies from abstracted traces. Run likelihood is the product of transition probabilities along an observed abstract path; low likelihood indicates deviation from learned behavior.
**Core assumption:** The empirical MDP captures the agent's typical behavior envelope; likelihood under this model is a meaningful anomaly score for runtime guardrailing.
**Evidence anchors:**
- [abstract] "constructs an MDP for probabilistic model checking... run likelihoods enable anomaly detection"
- [section 4.2.4] Defines MDP construction via counts `C(s,a,s')`.
- [section 4.3 & C] Details run likelihood computation and one‑sided low‑likelihood warning rule.
**Break condition:** The MDP may be inaccurate if traces are non‑representative (e.g., missing failure modes) or if abstraction lumps distinct behaviors, causing high false‑positive anomaly rates (Section 5 evaluation).

## Foundational Learning
- **Concept: Decision Tree Learning**
  - **Why needed here:** The predicate tree is the core abstraction mechanism; IG‑driven splits automatically discover state partitions that separate behavioral modes from traces.
  - **Quick check question:** If the next‑action distribution is uniform within a leaf, what does that imply about the leaf's utility for distinguishing behaviors?
- **Concept: Markov Decision Process (MDP)**
  - **Why needed here:** The agent's tool‑using behavior is stochastic and choice‑driven; MDPs model nondeterministic (environment/agent) choices and probabilistic outcomes, enabling quantitative PCTL queries.
  - **Quick check question:** Why can't a deterministic automaton capture the "upper/lower envelope" semantics of `Pmax`/`Pmin`?
- **Concept: Counterexample‑Guided Abstraction Refinement (CEGAR)**
  - **Why needed here:** Manual abstraction is brittle; CEGAR provides a systematic, evidence‑based loop to iteratively improve abstraction precision when spurious violations are detected.
  - **Quick check question:** How does "spuriousness" defined via trace‑trie concretization differ from classic CEGAR's use of concrete executions?

## Architecture Onboarding
**Component map:**  
1. Event Interceptor  
2. Trace Trie  
3. Predicate Tree Learner  
4. MDP Inducer  
5. Model Checker Interface  
6. Anomaly Scorer  

**Critical path:**  
Trace capture → Abstraction (tree) → Abstract trace projection → MDP update → Property check/Anomaly score → (if needed) Refinement loop.

**Design tradeoffs:**  
- **Abstraction granularity:** Deeper trees capture finer distinctions but increase MDP size and sparsity; configurable min‑IG threshold and max‑depth manage this.
- **Online vs. batch:** Current prototype rebuilds periodically; true online incremental learning (per‑step) would require efficient tree updates.
- **Semantic predicates:** Lack of embeddings in current version limits text‑variable abstraction (Section 4.1.4).

**Failure signatures:**  
- **High false‑positive anomaly rate:** Indicates abstraction over‑generalizes; leaf states contain heterogeneous next‑action distributions.
- **Unstable `Pmin`/`Pmax` bounds:** MDP probabilities fluctuate with small trace additions; suggests insufficient data per `(s,a)` pair.
- **Refinement stagnation:** IG below threshold after several iterations; may indicate need for new predicate types or different classification target.

**First 3 experiments:**  
1. **Baseline collection:** Run agent with normal tool usage, capture 1000+ traces; inspect initial tree depth and leaf purity (next‑action entropy).
2. **Anomaly injection:** Perturb traces (e.g., tool‑call loops, missing steps), measure anomaly detection recall/precision; correlate false positives with leaf entropy.
3. **Refinement stress test:** Force refinement on specific leaves, observe reduction in spurious counterexamples and changes in model size/checking time.

## Open Questions the Paper Calls Out
### Open Question 1
**Question:** How should TriCEGAR perform probabilistic counterexample‑guided refinement to tighten MDP probability bounds when counterexamples represent sets of paths or critical subsystems rather than single paths?
**Basis in paper:** The paper states: "The planned probabilistic refinement extracts the subset of abstract states and transitions that contribute most to the violating probability mass, then refines those states to tighten bounds and reduce spurious probability flow [14]. Given the complexity and subtlety involved in applying probabilistic refinements, this work concentrates exclusively on the modeling aspects of the problem, while the refinement itself is deferred to future research."
**Why unresolved:** The core refinement mechanism for probabilistic settings is identified as a planned but unimplemented component. The paper provides the high‑level goal (targeting probability mass contributors) but no algorithmic details, implementation, or evaluation of how to select splitting predicates that specifically address quantitative spuriousness in MDPs.
**What evidence would resolve it:** A detailed algorithm for probabilistic CEGAR within TriCEGAR's predicate tree framework, including a metric (beyond next‑action IG) for selecting refinement predicates that reduce bound looseness. Empirical validation showing refined models produce tighter `Pmax(success)`/`Pmin(failure)` bounds on benchmark agent tasks, with fewer spurious counterexamples.

### Open Question 2
**Question:** Does the decision‑tree initialization using information gain (IG) with respect to the next‑action distribution consistently yield abstractions that are optimal or near‑optimal for the subsequent probabilistic model checking of reachability properties like `Pmax(success)`?
**Basis in paper:** The initialization (Section 4.1.3, Appendix A.3) uses IG on next‑action as a proxy for "behavioral signal." This is a heuristic choice; the paper does not justify why maximizing separation of next‑actions correlates with minimizing abstraction error for *reachability probability* queries. The evaluation shows false positives, suggesting some abstractions over‑generalize, which may stem from this initialization criterion not aligning with the verification objective.
**Why unresolved:** The link between the training objective (next‑action prediction) and the verification objective (reachability probabilities) is assumed but not analyzed. The false positives in the file I/O evaluation indicate potential misalignment, but the root cause (initialization vs. lack of refinement) is not isolated.
**What evidence would resolve it:** An ablation study comparing initial predicate trees built with (a) next‑action IG (current), (b) IG on a proxy for eventual success/failure (e.g., classifying states by eventual reachability of goal/failure within N steps), and (c) random splits. The comparison would measure the gap between abstract and concrete (ground‑truth) reachability probabilities on held‑out traces, and the number of refinement iterations needed to converge.

### Open Question 3
**Question:** How does TriCEGAR's trace‑driven abstraction generalization perform on agentic systems with fundamentally different structures (e.g., multi‑agent crews, planning‑heavy agents, or agents with rich natural language state) compared to the single‑agent, tool‑call‑centric file I/O benchmark?
**Basis in paper:** The paper notes: "The current implementation includes the pipeline... The probabilistic CEGAR refinement loop and dynamic translation of high‑level properties to the induced model labels are ongoing work." The evaluation is limited to one domain (file I/O). The "Future Work" section implies scalability and domain applicability are open.
**Why unresolved:** The paper's claim of automating abstraction to "increase adoption friction" reduction is not validated across diverse agent architectures. The predicate grammar includes semantic predicates for text ("in active development"), but their efficacy and necessity for non‑trivial agents are unknown. The file I/O results show high false positives, raising concerns about scalability to more complex state spaces.
**What evidence would resolve it:** Case studies applying TriCEGAR to at least two other agent frameworks (e.g., CrewAI, LangGraph) with tasks requiring different abstraction needs (e.g., multi‑step planning, conversational state). Metrics would include: (a) number of predicates/leaf states relative to manual abstraction effort, (b) verification precision/recall against a suite of injected faults, and (c) runtime overhead of abstraction learning and refinement.

### Open Question 4
**Question:** What is the impact of the "model‑irrelevance abstraction" (citing [21]) on the soundness guarantees of TriCEGAR's quantitative bounds (`Pmax`, `Pmin`) when the learned MDP may not capture all environmental nondeterminism or policy variations?
**Basis in paper:** The approach constructs an MDP where nondeterminism is interpreted as "uncertainty about the deployed agent’s tool‑selection policy" (Section 4.1.1). However, the abstraction merges concrete states that may differ in unobserved environmental factors or internal stochasticity of the LLM. The paper notes: "the abstraction may miss unobserved concrete behaviors; completeness ... is not guaranteed." This suggests the computed bounds are only as sound as the abstraction's coverage of relevant concrete distinctions.
**Why unresolved:** The paper does not formalize what "admissible tool‑selection strategies" means in the presence of a learned abstraction. The bounds are described as "conservative risk indicators," but the degree of conservatism (i.e., how much the abstraction over‑approximates the true set of possible executions) is unquantified. This is critical for trust in the assurances.
**What evidence would resolve it:** A theoretical analysis relating the abstraction's predicate partitioning to the set of concrete executions it under‑approximates/over‑approximates. Experimental validation where the "true" MDP (from exhaustive simulation or a known simulator) is compared to the learned MDP under different abstraction granularities, measuring the tightness of the computed `Pmax/Pmin` intervals relative to the true reachability probabilities.

### Open Question 5
**Question:** Can the run‑likelihood anomaly detector (Section 4.3, Appendix C) effectively distinguish between *genuine* novel behaviors (e.g., a new, efficient tool usage pattern) and *anomalous* failures, or does it merely flag any deviation from the training distribution?
**Basis in paper:** The paper describes anomaly detection via low prefix‑conditioned log‑likelihood. The evaluation detected "injected anomalies" but also had "a high number of false positives for ratio‑based properties." The paper explicitly states: "This suggests that some abstract states over‑generalize the execution patterns." The counterexample‑guided refinement step is meant to address this.
**Why unresolved:** The fundamental limitation is that likelihood‑based detectors are *distributional* detectors; they flag low‑probability events under the learned model. However, in open‑ended agent tasks, novel but correct behaviors may also be low‑probability if not seen in training. The paper's refinement aims to reduce spurious signals from over‑general abstraction, but it's unclear whether refinement can distinguish semantic novelty from anoma without external labels. The current approach lacks a mechanism to incorporate positive examples of new, valid behaviors.
**What evidence would resolve it:** An evaluation where "anomalies" include not just injected faults but also *benign novelty* (e.g., a new tool sequence that successfully completes the task). The detector's performance would be measured with and without refinement, assessing precision/recall for *failure* detection while tracking false positive rate on novel successes. A refined abstraction should better separate failure modes from novel successes if predicates capture semantically meaningful distinctions.

## Limitations
- Evaluation shows high false positives; the exact cause (predicate set vs. IG threshold) is unclear.
- The refinement loop's automation status is ambiguous; probabilistic refinement is deferred, so the prototype may use a fixed tree.
- Anomaly injection procedures are underspecified, and reliance on manually defined state variables may limit generalization to complex agents.

## Confidence
- **Abstraction via Decision Tree Learning:** **High**
- **MDP Construction & Quantitative Bounds:** **High**
- **Counterexample‑Guided Refinement:** **Medium**
- **Anomaly Detection via Run Likelihood:** **Low**
