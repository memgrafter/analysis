# Persona2Web: Benchmarking Personalized Web Agents for Contextual Reasoning with User History

## Quick Facts
- **arXiv ID:** 2602.17003
- **Source URL:** https://arxiv.org/abs/2602.17003
- **Reference count:** 40
- **Primary result:** Without history, all agents achieve 0% success; with history, the best model (o3 with Browser-Use, pre-execution) attains only 13% success, demonstrating that personalization remains a major challenge for web agents.

## Executive Summary
Current web agents fail to handle ambiguous queries that require personalization based on user history. To address this, the authors introduce Persona2Web, the first benchmark for personalized web agents on the real open web. It features long-term implicit user histories derived from behavioral patterns, ambiguous queries designed under a clarify-to-personalize principle, and a reasoning-aware evaluation framework that separately scores personalization (website and preference retrieval/utilization) and intent satisfaction. Experiments show that without history, all agents achieve 0% success; with history, the best agent (o3 with Browser-Use using pre-execution) achieves only 13% success. Performance degrades as query ambiguity increases, and even clear queries show failures in utilizing retrieved preferences. Explicit user profiles substantially improve scores, confirming the need for agents to reason over implicit histories. The benchmark reveals that personalization is a major unsolved challenge for web agents.

## Method Summary
The benchmark creates synthetic user histories (~2,000 entries per user) over a simulated year, embedding preferences implicitly across timestamps, entry types, and objects. Queries are constructed at three ambiguity levels: clear (Level 0), semi-ambiguous (Level 1), and fully ambiguous (Level 2), with constraints on preferred website and product attributes masked. Evaluation uses a rubric-based LLM judge (GPT-5-mini) that scores agent trajectories on three dimensions: website preference retrieval/use (Pweb), user preference retrieval/use (Ppref), and intent satisfaction independent of personalization. The primary metric is Success Rate (SR), requiring full scores in all three. No agent training is performed; instead, two agent architectures (AgentOccam and Browser-Use) are combined with a personalization module comprising a planner (decides when to query history), a retriever (embedding-based search over history entries indexed by `type+object`), and a generator (synthesizes retrieved history to resolve ambiguity). Two history access schemes are tested: on-demand (retrieve at each step) and pre-execution (retrieve once before execution). Backbone models tested include o3, GPT-4.1, Gemini-2.5-Flash, Qwen3-80B-Instruct, and Llama-3.3-70B.

## Key Results
- Without user history, all agents fail (0% success) on ambiguous queries, confirming that disambiguation requires historical context.
- With history, the best agent achieves only 13% success (o3 with Browser-Use, pre-execution), and performance drops monotonically as query ambiguity increases.
- Explicit user profiles boost scores dramatically, indicating that implicit history reasoning is the core difficulty rather than personalization concept itself.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Implicit user histories constructed from long-term behavioral patterns enable agents to infer user preferences without explicit cues.
- **Mechanism:** The benchmark generates synthetic browsing histories where preferences (e.g., product categories, websites, price ranges) are embedded indirectly across thousands of entries over a simulated year. Agents must recognize recurring patterns (e.g., "frequently buys hardcover business books on Amazon") rather than consult a single explicit profile.
- **Core assumption:** Real-world user preferences are revealed through repeated actions, not stated directly; agents must perform multi-step retrieval and synthesis across temporally dispersed entries.
- **Evidence anchors:**
  - [abstract] "...long-term implicit user histories...require agents to infer implicit user preferences."
  - [section 3.1] "User history...reveals user preferences in implicit and indirect ways over long time spans...preferences should be revealed implicitly from contextual cues distributed across the history."
  - [corpus] Weak direct evidence; neighboring papers (e.g., *AgenticShop*, *PerPilot*) also use implicit history but do not anchor this specific construction mechanism. **Assumption:** The implicit construction is novel to *Persona2Web* and not validated externally.
- **Break condition:** If histories are replaced with explicit profiles, performance improves dramatically (Table 5), proving the mechanism's necessity for genuine personalization challenges.

### Mechanism 2
- **Claim:** Ambiguous queries with masked constraints force agents to engage in disambiguation via history retrieval, rather than executing fully specified instructions.
- **Mechanism:** Queries are systematically degraded from Level 0 (all constraints explicit) to Level 2 (both website and preference constraints masked). Agents must identify missing parameters and retrieve relevant historical evidence to fill them.
- **Core assumption:** Practical web queries are often underspecified; personalization requires active clarification from context, not passive instruction-following.
- **Evidence anchors:**
  - [abstract] "ambiguous queries designed under the clarify-to-personalize principle...resolve ambiguity based on user history rather than relying on explicit instructions."
  - [section 3.2] "We intentionally conceal specific parts of the query to let the agent clarify based on user history."
  - [corpus] No direct anchor; related benchmarks (*Mind2Web*, *WebArena*) use fully specified tasks. **Assumption:** The *clarify-to-personalize* principle is uniquely operationalized here.
- **Break condition:** Without history, all agents achieve 0% success on ambiguous queries (Table 3), confirming that resolution depends on history access.

### Mechanism 3
- **Claim:** Separating evaluation into personalization (retrieval/utilization) and intent satisfaction metrics isolates failure modes and reveals that navigation and personalization are orthogonal challenges.
- **Mechanism:** A rubric-based LLM judge scores trajectories on (1) website preference retrieval/utilization, (2) user preference retrieval/utilization, and (3) intent satisfaction independent of personalization. This decouples "did it go to the right site?" from "did it apply the user's budget constraint?"
- **Core assumption:** Task completion is a compound metric that masks whether failures stem from navigation or personalization deficits.
- **Evidence anchors:**
  - [abstract] "reasoning-aware evaluation framework that separately scores personalization...and intent satisfaction."
  - [section 3.3] "Accurate evaluation...requires distinguishing personalization failures from navigation failures...Our framework examines the full trajectory including reasoning traces."
  - [section 5.3] Explicit examples: "Llama succeeds at personalization but struggles with navigation, while Gemini navigates reasonably but fails at personalization...same low success rate, yet they fail for opposite reasons."
  - [section 5.1] Meta-evaluation shows reasoning-aware scores correlate best with human judgment (Table 4).
- **Break condition:** If final success rate were the sole metric, the same score could reflect opposite underlying capabilities, preventing targeted improvements.

## Foundational Learning
- **Concept: Retrieval-Augmented Generation (RAG) for memory**  
  *Why needed here:* Agents must retrieve relevant entries from a ~2,000-entry history per user. Understanding embedding-based retrieval (FAISS) and its limitations (e.g., noise from timestamp/website attributes, Appendix E) is key.  
  *Quick check question:* Why does indexing with only `type+object` outperform `all attributes` for the retriever in Appendix E?

- **Concept: Ambiguity resolution in NLP**  
  *Why needed here:* Queries are underspecified at Levels 1–2. Agents must identify missing slots (website, preferences) and fill them from history—a form of slot-filling/clarification.  
  *Quick check question:* How would you automatically generate a Level 2 query from a Level 0 query for the "restaurant reservation" domain?

- **Concept: Compound evaluation design**  
  *Why needed here:* Success rate conflates navigation and personalization. Engineers must design rubrics that score subskills separately, requiring careful decomposition of tasks into retrieval and utilization steps.  
  *Quick check question:* For a task "buy my usual headphones in my preferred store," what are the distinct retrieval and utilization steps? How would you score each?

## Architecture Onboarding
### Component Map
Planner → Retriever → Generator (with reasoning) → Web navigation → (loop) → Judge. The agent accesses user history via the planner's decision; the retriever embeds and searches history entries; the generator uses retrieved entries to produce personalized rationale and next action; the navigation component interacts with the web (via Browser-Use or AgentOccam). The judge (GPT-5-mini) scores the final trajectory.

### Critical Path
Input: ambiguous query + user history → Planner decides history access → Retriever returns top-k entries → Generator synthesizes personalization rationale → Navigator acts on web → Repeat until stop → Judge scores final trajectory. The path branches on history access scheme: on-demand (retrieve at each step) vs pre-execution (retrieve once before execution).

### Design Tradeoffs
- **On-demand:** Tests situational awareness (knowing when to access history) but risks missing future needs.
- **Pre-execution:** Tests long-horizon planning (anticipating all constraints) but cannot adapt if initial retrieval fails.
- **Observation space:** AgentOccam (pruned accessibility tree) vs Browser-Use (full enhanced DOM). Richer DOM preserves more personalization cues but increases cost/noise.

### Failure Signatures
- **History retrieval failure** (most common): Irrelevant/incomplete entries returned → agent cannot infer preference.
- **History utilization failure:** Correct entries retrieved but not applied to action (e.g., retrieved location but searched globally).
- **Redundant history access:** Underspecified queries to retriever cause repeated failed retrieval attempts.
- **Personalization hallucination:** Agent fabricates preference not grounded in history.

### First 3 Experiments
1. **No-history baseline:** Run Level 2 queries without history access. Expect 0% success (Table 3). Confirms ambiguity cannot be resolved without context.
2. **Compare access schemes:** For same backbone/agent, run both on-demand and pre-execution. Identify which scheme model excels at (e.g., GPT-4.1 better on-demand, Qwen better pre-execution, Section 5.3).
3. **Ambiguity sweep:** Test Level 0, 1, 2 queries with history enabled. Expect monotonic drop in success rate (Figure 3). Isolates impact of increasing disambiguation burden.

## Open Questions the Paper Calls Out
### Open Question 1
How can retrieval of relevant user history from long implicit browsing logs be improved?  
*Basis in paper:* Section 6 shows history retrieval failure is the dominant error, accounting for nearly half of personalization errors.  
*Why unresolved:* Only a single dense retriever with type+object concatenation was evaluated; alternative designs remain unexplored.  
*What evidence would resolve it:* Compare retrieval architectures (e.g., query generation, BM25, multi-stage) on retrieval accuracy and downstream task success.

### Open Question 2
Why do agents fail to utilize correctly retrieved user preferences during navigation, and how can this be addressed?  
*Basis in paper:* Section 6 defines history utilization failures, exemplified by agents missing to apply retrieved location information.  
*Why unresolved:* The study provides no analysis of underlying causes nor tests interventions to improve utilization.  
*What evidence would resolve it:* Ablation studies with prompting or architectural changes that explicitly incorporate retrieved history into action generation, measuring utilization accuracy.

### Open Question 3
Do the observed differences between pre-execution and on-demand history access schemes hold across diverse web agent benchmarks and domains?  
*Basis in paper:* Section 4.2 introduces both schemes and Section 5.4 reveals backbone-dependent performance gaps.  
*Why unresolved:* Evaluation is limited to Persona2Web tasks; cross-benchmark generalization is unknown.  
*What evidence would resolve it:* Replicate the comparison on other web agent benchmarks (e.g., WebArena, WebVoyager) using varied task types and real user histories.

### Open Question 4
Can implicit browsing histories be automatically distilled into explicit user profiles without losing personalization capability?  
*Basis in paper:* Section 5.5 shows explicit profiles substantially boost performance, indicating raw histories contain equivalent information.  
*Why unresolved:* The paper does not attempt to extract such profiles automatically; this transformation remains an open challenge.  
*What evidence would resolve it:* Develop and evaluate profile extraction methods (e.g., clustering, summarization) and measure agent performance when using inferred profiles versus raw history.

## Limitations
- The exact LLM judge rubrics (Appendix D) are undisclosed, threatening reproducibility of evaluation scores.
- Synthetic history generation details (prompts, temperature, seeds) are unspecified; minor variations could affect agent performance.
- Public accessibility of the provided code repository URL is uncertain, potentially blocking data and script retrieval.

- Clarify-to-personalize principle: **High**
- Separate evaluation framework: **High**
