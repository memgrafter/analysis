# HiMAP-Travel: Hierarchical Multi-Agent Planning for Long-Horizon Constrained Travel

## Quick Facts
- **arXiv ID**: 2603.04750  
- **Source URL**: https://arxiv.org/abs/2603.04750  
- **Reference count**: 40  
- **Primary result**: On TravelPlanner (Qwen3-8B), reaches 52.65% test Final Pass Rate, beating DeepTravel by 8.67 pp and cutting latency by 2.5× on FlexTravelBench.

## Executive Summary
HiMAP-Travel addresses constraint drift in sequential LLM planners for long-horizon travel itineraries. It introduces a hierarchical multi-agent architecture where a Coordinator allocates global resources and parallel Day Executors handle daily planning. A synchronized transactional monitor enforces budget and uniqueness invariants atomically, while a bargaining protocol enables iterative reallocation when Executors report infeasibility. All agents share a single GRPO-trained policy with role conditioning, improving memory efficiency and transfer. On TravelPlanner, the system achieves state-of-the-art Final Pass Rate and significant latency reductions.

## Method Summary
The system decomposes travel planning into strategic allocation (Coordinator) and tactical day-level execution (Day Executors). A global state Σ tracks committed budget, venues, and transport modes, providing atomic check/commit operations to prevent conflicts. Day Executors use tool calls to build itineraries and must commit results through Σ; rejections trigger regeneration. If a day is infeasible, a bargaining loop allows the Coordinator to reallocate tasks (e.g., adjust cities or budgets) up to three times. All agents operate under a single language model policy, differentiated only by role-specific prompts, trained end-to-end with Group Relative Policy Optimization (GRPO) using a shared replay buffer.

## Key Results
- **TravelPlanner**: 52.65% Final Pass Rate (Qwen3-8B), +8.67 pp over DeepTravel, +17.65 pp over ATLAS, +10.0 pp over MTP.
- **FlexTravelBench**: 44.34% (2-turn) and 37.42% (3-turn) Final Pass Rate, with 2.5× lower latency.
- **Efficiency**: Parallelism (P=3) yields 2.5–2.8× speedup over sequential baselines.

## Why This Works (Mechanism)

### Mechanism 1: Atomic Constraint Enforcement via Synchronized Global State (Σ)
- **Claim**: Σ provides atomic enforcement of shared resource invariants (budget, non-duplication, transport mode) to prevent conflicts among parallel executors.
- **Mechanism**: An external store with a global mutex. When an Executor calls `finish`, it triggers `check(action)`; if invariants hold, `commit` atomically updates Σ; else the action is rejected. This guarantees mutual exclusion and invariant preservation.
- **Core assumption**: The policy can regenerate after rejection; resource conflicts are the primary source of infeasibility; lock contention is negligible.
- **Evidence anchors**: Abstract mentions "transactional monitor"; Section 4.3 details safety guarantees; Table 8 defines operations.
- **Break condition**: Σ does not cover non-resource constraints (route, temporal, cuisine), so it cannot alone ensure validity. Extreme lock contention could degrade speedup.

### Mechanism 2: Cooperative Bargaining for Reallocation
- **Claim**: Cooperative Bargaining enables iterative reallocation of task structure (cities, routes) when Executors report infeasibility, without changing the total budget.
- **Mechanism**: Executors return JSON `{status, deficit, violation_type}`. The Coordinator revises distribution; Σ checkpoint/rollback supports clean retries. Limited to Kmax iterations.
- **Core assumption**: Executors accurately detect infeasibility early and the Coordinator can find feasible alternatives.
- **Evidence anchors**: Abstract describes "bargaining protocol"; Section 4.4 gives Algorithm 1 and convergence (Table 31: 61.7% iter1, 97.8% by iter3).
- **Break condition**: Fails if the query is inherently unsatisfiable or feedback is uninformative; 2.2% of queries remain infeasible after Kmax.

### Mechanism 3: Unified Role-Conditioned Policy with GRPO
- **Claim**: A single policy trained with GRPO enables memory-efficient multi-agent learning, transfers skills across roles, and stabilizes training.
- **Mechanism**: One model πθ with role prefix. GRPO collects G trajectories per role partition, computes group-relative advantages within the partition, and updates. A shared FIFO buffer flushes per partition to bound memory.
- **Core assumption**: Role prompts suffice for specialization; group advantages are comparable within a partition; FIFO maintains gradient diversity.
- **Evidence anchors**: Abstract states "single policy trained with GRPO"; Section 4.6 describes shared buffer; Section 5.4 ablation shows -8.08 pp loss with separate policies.
- **Break condition**: Role interference if prompts are insufficient; small G increases variance; FIFO may discard useful old trajectories.

## Architecture Onboarding
- **Component map**:  
  Coordinator -> Day Executors (P=3) -> Synchronized Global State Σ  
  Coordinator <-> Bargaining Controller  
  Shared Policy πθ (role-conditioned)  
  GRPO Trainer (shared FIFO buffer)

- **Critical path**:  
  1. Query → Coordinator extracts constraints, selects cities, calls `distribute_task` → Σ initialized.  
  2. Spawn day planners in batches (P=3). Each day: search tools → tentative itinerary; `cost_enquiry` vs Σ.Bused; `finish` → Σ.check/commit; on failure, regenerate.  
  3. If any day INFEASIBLE, Controller stops others, rollbacks Σ, collects feedback, triggers Coordinator replanning (up to Kmax=3).  
  4. All days succeed → Coordinator assembles final itinerary → evaluation → FPR.  
  5. Training: Trajectories stored by role in shared buffer; when any role reaches G=4, compute advantages within that role, update πθ (with KL penalty), flush those trajectories.

- **Design tradeoffs**:  
  - Parallelism vs coupling: Speedup (2.5–2.8×) vs added complexity of Σ and bargaining.  
  - Shared policy vs specialization: Memory/transfer benefits vs potential interference; ablations show clear gain.  
  - Monitor scope vs simplicity: Σ handles only resource conflicts; other constraints left to policy, simplifying monitor but requiring robust policy.  
  - Bargaining iterations: Kmax=3 balances success rate (97.8%) and latency; extra iterations add little.  
  - Concurrency P: Larger P improves speedup but increases lock contention; P=3 chosen empirically.

- **Failure signatures**:  
  - BudgetExceeded, DuplicateVenue, ModeLock: immediate Σ rejection → regeneration.  
  - INFEASIBLE day: after tool limit or repeated violations; triggers bargaining.  
  - Bargaining exhaustion: after Kmax still infeasible; returns partial plan.  
  - Sandbox violation (venue not in city, duplicate due to fuzzy failure): evaluator catches; indicative of Σ false negative or data issues.  
  - MinimumNights violation, Route infeasibility: not tracked by Σ; policy errors.

- **First 3 experiments**:  
  1. Day Planner smoke test: single day, ensure Σ commit works and budget updates.  
  2. Coordinator sanity: ambiguous city disambiguation and `distribute_task` output validation.  
  3. Full system on Easy-tier subset: expect >70% FPR, low variance, latency ~50s for 3-day trips.

## Open Questions the Paper Calls Out
- Does the hierarchical multi-agent approach generalize to other constrained optimization domains beyond travel planning?
- Can the Synchronized Global State be extended to enforce minimum-nights and other temporal constraints, thereby reducing the 13.7% failure rate due to temporal violations?
- Can an early feasibility detection module improve overall success rate by aborting provably infeasible queries before entering costly bargaining iterations?
- Why does parameter sharing across Coordinator and Executor roles yield superior performance compared to separate policies, and what specific skills transfer between roles?
- Do other hard constraints (cuisine, room type, diversity) exhibit similar drift patterns, and does hierarchical decomposition equally mitigate drift for these constraints?

## Limitations
- Prompts, tool APIs, and dataset version not fully specified → replication barrier.
- Σ covers only resource constraints; non-resource constraints (temporal, route, min nights) remain policy-handled, causing residual errors.
- Training set small (~45 queries) → generalization concerns.
