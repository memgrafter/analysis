# Brain-Inspired Graph Multi-Agent Systems for LLM Reasoning

## Quick Facts
- arXiv ID: 2603.15371
- Source URL: https://arxiv.org/abs/2603.15371
- Reference count: 40
- Primary result: BIGMAS yields substantial accuracy gains on complex reasoning benchmarks (e.g., +36 points for Claude 4.5 +thinking on Tower of London).

## Executive Summary
Large language models (LLMs) and large reasoning models (LRMs) suffer from accuracy collapse on complex, multi-step reasoning tasks despite scaling. This paper introduces Brain-Inspired Graph Multi-Agent Systems (BIGMAS), a novel architecture where a GraphDesigner constructs a task-specific directed graph of specialized LLM agents. Agents coordinate exclusively through a centralized shared workspace, orchestrated by a global router with full-state visibility. Evaluated on three benchmarks (Game24, Six Fives, Tower of London) using six frontier LLMs, BIGMAS consistently outperforms both base models and existing multi-agent baselines like ReAct and Tree of Thoughts. Gains are particularly large for weaker models and LRMs, demonstrating that architectural multi-agent coordination offers orthogonal improvements to model-level reasoning enhancements.

## Method Summary
BIGMAS comprises three core components. First, the GraphDesigner analyzes the task and generates a directed graph where nodes represent specialized LLM agents and edges define permissible information flow. Second, a global router with access to the entire shared workspace dynamically selects the next agent to activate based on the current state and graph topology. Third, all agents interact solely via a centralized shared workspace that holds the evolving reasoning state. This design partitions complex reasoning into focused subtasks, maintains global consistency, and enables efficient, state-aware orchestration without direct agent-to-agent communication.

## Key Results
- BIGMAS improves accuracy over base models and multi-agent baselines (ReAct, Tree of Thoughts) across all three benchmarks.
- Weaker models show large gains; e.g., DeepSeek-V3.2 improves by 14–16 points.
- LRMs also benefit significantly; Claude 4.5 +thinking on Tower of London gains 36 points.
- Results hold across six frontier LLMs, indicating orthogonality to model-level scaling.

## Why This Works (Mechanism)
The centralized shared workspace ensures all agents operate on a consistent global state, preventing fragmentation. The global router’s full-state visibility enables intelligent scheduling, avoiding redundant or conflicting actions. Specialized agents focus on particular subtasks, reducing the cognitive burden and error propagation that monolithic models experience on multi-step problems. The directed graph structure adapts the reasoning flow to the task, allowing modular decomposition and recombination of intermediate results. Together, these mechanisms mitigate the accuracy collapse observed in single-model approaches.

## Foundational Learning
- **GraphDesigner**: Constructs task-specific directed graphs of agents. *Why needed*: Tailors the agent topology to the problem structure, enabling efficient decomposition. *Quick check*: Can the GraphDesigner generate a graph with cycles?
- **Specialized LLM Agents**: Individual agents dedicated to specific reasoning subtasks. *Why needed*: Limits each agent’s scope, improving reliability and reducing error propagation. *Quick check*: Would a single generalist agent achieve similar performance?
- **Centralized Shared Workspace**: A single state repository accessible to all agents. *Why needed*: Maintains global consistency and provides the router with full context. *Quick check*: Can agents bypass the workspace to communicate directly?
- **Global Router**: Orchestrates execution with full workspace awareness. *Why needed*: Coordinates the multi-agent process, avoiding deadlock and ensuring progress. *Quick check*: Does the router have access to agents’ internal reasoning?

## Architecture Onboarding
**Component map**: GraphDesigner -> GlobalRouter -> SpecializedAgents; SharedWorkspace as a central hub connected to all agents.  
**Critical path**:  
1. Task input is given to the GraphDesigner.  
2. GraphDesigner outputs a directed graph specifying agent types and connections.  
3. GlobalRouter initializes the shared workspace with the initial problem state.  
4. Router selects the next agent based on current workspace and graph edges.  
5. Selected agent reads from the workspace, reasons using its LLM, writes output back.  
6. Steps 4–5 repeat until a termination condition (e.g., answer found) is met.  
7. Final answer is extracted from the workspace.  
**Design tradeoffs**:  
- Centralized vs. distributed control: Centralization simplifies coordination but introduces a single point of failure and potential bottleneck.  
- Graph complexity: More agents and edges allow finer decomposition but increase routing overhead and cost.  
- Agent specialization depth: Highly specialized agents improve subtask performance but require more careful graph design and may reduce flexibility.  
**Failure signatures**:  
- Routing loop: Router repeatedly activates the same sequence of agents without state change.  
- Workspace contention: Overwrites or concurrent writes corrupt the shared state.  
- Agent inconsistency: An agent’s output violates expected types, causing downstream failures.  
- Router starvation: Some agents never get scheduled due to a poor routing policy.  
**First experiments**:  
1. Replicate the Game24 experiment with a minimal graph (two agents: a proposer and a validator) and compare accuracy against a single-model baseline.  
2. Vary the number of agents (e.g., 2, 3, 4) on a single benchmark to measure impact on accuracy and token usage.  
3. Ablate the global router by replacing it with a random scheduler to quantify the importance of state-aware orchestration.

## Limitations
- Benchmarks are limited to math/puzzle tasks; performance on open-domain or creative tasks is unknown.
- System introduces multiple LLM calls and a global router; computational cost and latency are not quantified.
- Generalizability to ambiguous or conflicting scenarios, and integration of heterogeneous reasoning types, remains unclear.

## Confidence
- Reported Benchmark Improvements: High
- Architectural Coordination Benefits: Medium
- Orthogonality to Model Scaling: Low
- "Brain-Inspired" Justification: Low

## Next Checks
1. Benchmark Generalization: Replicate BIGMAS on at least two additional, diverse benchmarks (e.g., GPQA for expert QA, or a complex dialogue/Planning benchmark) to test the claim of broad task applicability.
2. Efficiency Analysis: Rigorously measure and report average tokens used, inference latency, and estimated cost per task across BIGMAS and all baselines, including the cost of the GraphDesigner and router operations.
3. Open-Source Reproduction & Ablation: If code is released, independently reproduce the main results on Tower of London. Crucially, perform an ablation study removing the centralized workspace (allowing direct agent-agent messaging) and randomizing the router to isolate the contribution of each proposed component.
