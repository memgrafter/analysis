# RocqSmith: Can Automatic Optimization Forge Better Proof Agents?
## Quick Facts
- arXiv ID: 2602.05762
- Source URL: https://arxiv.org/abs/2602.05762
- Reference count: 7
- Primary result: Automatic few-shot bootstrapping improves a ReAct-style Rocq agent from 19% to 40% success, but remains below a human-engineered SOTA agent (53%).

## Executive Summary
This paper evaluates whether automatic optimization can improve a Rocq theorem-proving agent beyond a simple ReAct-style baseline. Testing prompt-centric, context-centric, and topology-level optimizers, the study finds that a simple few-shot bootstrapping method—which injects successful proof trajectories into the prompt—yields the most consistent and substantial gains. However, none of the automatic methods match the performance of a carefully designed human agent, highlighting a gap between automated and expert-engineered solutions in formal theorem proving.

## Method Summary
The authors implement a baseline ReAct agent using GPT-4.1 within the DSPy framework, where the agent iteratively reasons about a Rocq proof state and selects tactics from a fixed toolset. Several optimizers are then applied to this baseline using a training set of 60 theorems from the IMM benchmark: prompt-centric methods (BootstrapFewShot, MIPROv2, SIMBA, GEPA) modify the prompt; context-centric methods (ACE, ReasoningBank) manage an experience memory; and topology-level optimization (ADAS) evolves the agent's control flow code. Each optimized agent is evaluated on a separate test set of 150 theorems (grouped by difficulty) with a budget of 20 tactic calls. Success is measured by whether the agent completes the proof.

## Key Results
- Simple few-shot bootstrapping (BootstrapFewShot) is the most consistently effective optimizer, raising overall success from 19% to 40% in the DSPy implementation.
- More complex prompt optimizers (e.g., MIPROv2, SIMBA) do not yield clear advantages over the simple few-shot baseline, suggesting the primary benefit comes from including successful demonstrations rather than refined instruction phrasing.
- Topology-level optimization (ADAS) produces agents that overfit to the training distribution and rely on brittle, hard-coded logic, failing to generalize.
- None of the automatic optimizers reach the 53% success rate of a state-of-the-art human-designed proof agent.

## Why This Works (Mechanism)
### Mechanism 1
Including successful execution traces as few-shot demonstrations reliably improves a ReAct-style theorem-proving agent. The optimizer selects high-reward trajectories from the training set and injects them into the prompt, enabling the LLM to mimic effective reasoning-action patterns via in-context learning. This assumes the proof state representation is informative enough that similar states benefit from similar tactics, and the model can generalize from a few examples. Evidence shows BootstrapFewShot yields particularly strong gains, with performance peaking at around four demonstrations before context limits degrade results. Effectiveness breaks down if successful traces are too long or if the training distribution misaligns with test proofs, leading to overfitting on brittle patterns.

### Mechanism 2
More complex prompt optimizers (MIPROv2, SIMBA) do not consistently outperform the simple few-shot baseline. These methods automate search over prompt phrasing or instruction-demonstration combinations, but their comparable performance suggests the key signal is the *presence* of successful trajectories rather than their precise linguistic formulation. The reward signal (binary proof success) is sparse and the optimization landscape over string space is noisy, limiting marginal gains from instruction tuning. This implies the LLM’s pre-trained understanding of the task is sufficient given good demonstrations; further prompt engineering yields diminishing returns.

### Mechanism 3
Topology-level optimization (ADAS) produces brittle agents that overfit to training data. ADAS generates and selects agent control-flow code based on training performance, which can discover short-lived heuristics and spurious correlations (e.g., tactic sequences specific to certain proof lengths). The resulting code lacks the high-level planning and robustness of human-engineered pipelines, as the optimal control topology for formal theorem proving is not easily discovered by black-box code generation from a limited toolset and few training instances. ADAS agents show non-monotonic improvement and strong training bias.

## Foundational Learning
- **Concept: ReAct (Reason-and-Act) paradigm**  
  The baseline agent follows an observe-reason-act loop. Understanding this pattern is crucial because all optimizers modify the reasoning/action step without altering the environment.  
  *Quick check:* How does inserting an explicit reasoning step before tactic selection change the optimization surface compared to a direct-action agent?

- **Concept: Few-shot learning / in-context learning**  
  BootstrapFewShot’s success hinges on providing the LLM with successful proof traces. This leverages the model’s ability to mimic demonstrated patterns without weight updates.  
  *Quick check:* Why might including four successful proof trajectories improve performance, but adding ten degrade it due to context limits?

- **Concept: Retrieval-augmented context (vs. full-context injection)**  
  ReasoningBank (with retrieval) outperforms ACE (full context injection), highlighting the need for selective context management in long-horizon tasks like theorem proving.  
  *Quick check:* What property of the proof state makes similarity-based retrieval feasible, and why might the raw theorem identifier be a poor query?

## Architecture Onboarding
- **Component map:** Rocq Prover (environment) -> LLM Agent (core with prompt/template) -> Tools (Rocq tactics) -> Optimizer (modifies prompt/context/code) -> Evaluator (runs test set).  
- **Critical path:** Theorem input → Agent generates reasoning and selects tactic → Execute in Rocq → Receive new proof state → Repeat until success or call budget exhausted. Optimization modifies the reasoning/selection step.  
- **Design tradeoffs:**  
  *Simplicity vs. expressivity:* The simple ReAct loop is optimizable but lacks planning/reflection of SOTA agents; adding components may require more complex optimization.  
  *Context window:* Injecting demonstrations/memories improves performance but reduces space for proof state details, requiring selective curation.  
  *Optimization cost:* BootstrapFewShot (~45 min) is cheap; ADAS (~70 h) is expensive with uncertain payoff.  
- **Failure signatures:**  
  *Early stagnation:* Agent solves only very short proofs (<5 tactics).  
  *Context overflow:* LLM truncates proof state, leading to nonsensical tactic choices.  
  *Brittle heuristics:* Agent solves training-set-like proofs but fails on novel strategies, common with ADAS.  
- **First 3 experiments:**  
  1. Replicate baseline: Implement the simple ReAct agent in DSPy, establish ~20% success baseline on a test subset, validate tool-calling correctness.  
  2. Apply BootstrapFewShot: Run optimizer on 60 training theorems, select 4 best demonstrations, inject into prompt. Measure absolute gain; expect ~15–20% improvement.  
  3. Test ReasoningBank: Build memory bank from training trajectories, embed queries (using an encoder like all-MiniLM-L6-v2), retrieve top-5 at inference. Compare to ACE (full injection) and no-context baseline. Ensure retrieval uses full proof state string, not just theorem ID.

## Limitations
- Exact baseline prompt templates and proof state formatting are unreleased, preventing faithful replication of the LLM input interface.
- Specific IMM training/test theorem splits are not provided; any reproduction uses a surrogate split, risking distribution mismatch.
- The unreleased human-engineered SOTA agent (53%) cannot be replicated or compared directly.

## Confidence
- Mechanism 1 (Few-shot efficacy): **High**. Directly supported by the paper’s core results showing BootstrapFewShot’s consistent, large gains.
- Mechanism 2 (Complex optimizers underperform): **Medium**. Supported by comparative results, but depends on specific implementations and training data scale.
- Mechanism 3 (Topology optimization brittleness): **Low**. Supported by ADAS analysis, but conclusions may not generalize to other topology search methods or with more data.

## Next Checks
1. Prompt Template Audit: Request and verify the exact string templates for the ReAct agent’s system/user prompts and the formatting of the Rocq proof state.
2. Split Reproducibility Test: Use a fixed random seed to generate a new 60/150 train/test split from the IMM corpus. Evaluate BootstrapFewShot on this split to quantify performance variance due to split choice.
3. Context Window Stress Test: Deliberately vary the number of few-shot demonstrations injected by BootstrapFewShot (e.g., 1 vs. 4 vs. 8) to confirm the reported peak at 4 and identify the exact context overflow point for the chosen state representation.
