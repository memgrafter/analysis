# CEDAR: Context Engineering for Agentic Data Science

## Quick Facts
- **arXiv ID:** 2601.06606
- **Source URL:** https://arxiv.org/abs/2601.06606
- **Reference count:** 4
- **Primary result:** CEDAR automates data science workflows via context engineering, enabling readable step-by-step solutions with local code execution and smart history rendering, demonstrated on Kaggle competitions.

## Executive Summary
CEDAR is an agentic system that automates end-to-end data science tasks by addressing two core challenges: LLM context length limits and data privacy. It structures user prompts into a predefined schema, orchestrates alternating natural-language planning and code generation through specialized agents, executes code locally in a container, and injects only aggregate statistics into prompts. A smart history renderer trims the running context to ~10k characters. The system produces human-readable, enumerated notebook-like workflows and has been functionally validated on beginner Kaggle competitions, though without quantitative performance metrics.

## Method Summary
CEDAR transforms a user’s data science request into a structured “project summary” with DS-specific fields (task description, data location, metrics, etc.). An orchestrator agent sequentially routes tasks: it calls a text sub-agent to produce a plan, then a code sub-agent to generate executable Python for that step. Code runs in a Docker container; only selected aggregates (e.g., `.head()`, error traces) are fed back to the LLM. A history renderer condenses the full step history to a ~10k-character string, preserving recent steps, heads of successful outputs, and tails of error traces. No model training is involved; the system operates at inference time. Reproduction is hindered by unreleased source code and unspecified Docker/library details.

## Key Results
- Generates readable, step-by-step workflows with iterative code error recovery.
- Maintains full data locality and supports on-premise LLM deployment.
- Validated through functional end-to-end runs on beginner Kaggle competitions.

## Why This Works (Mechanism)

### Mechanism 1: Structured prompts reduce ambiguity
CEDAR imposes a predefined schema (general instructions + task-specific fields) on the initial prompt, converting vague requests into a consistent project summary. This reduces ambiguity and improves LLM comprehension for multi-step DS workflows. The core assumption is that a DS-oriented schema is more effective for agent coordination than free-form prompts. Evidence: the abstract and section 2.1 describe splitting the project summary into high-level and task-specific instructions. Break condition: if the fixed schema misses critical task nuances, the system may proceed with incorrect constraints, leading to irrelevant outputs despite correct step execution.

### Mechanism 2: Interleaved plan/code blocks enhance readability and verification
An orchestrator agent alternately invokes a text sub-agent (for a natural language plan/specification) and a code sub-agent (for Python implementation). This creates an enumerated, notebook-like history that is human-scrutinizable and supports stepwise debugging. The core assumption is that alternating narrative planning with concrete code prevents context from becoming monolithic and unintelligible. Evidence: the abstract and section 2.2 highlight the interleaved structure. Break condition: if the orchestrator’s routing fails (e.g., calling agents in wrong order), the workflow could become incoherent or stall.

### Mechanism 3: Local execution and smart rendering mitigate context limits and privacy risks
All data remains on the local machine; code executes in Docker. Only aggregates (e.g., heads, error traces) are injected into prompts. The history renderer truncates context to ~10k characters, keeping recent steps, heads of successful outputs, and tails of errors. The core assumption is that LLMs need only summary statistics and recent errors to generate logical next steps. Evidence: the abstract and section 2.6 describe aggregate injection and the 10k character cap with head/tail rules. Break condition: if a step requires fine-grained data patterns not captured by aggregates (e.g., a specific outlier), the LLM may make incorrect decisions, causing cascading failures.

## Architecture Onboarding
- **Component map:** User Interface (Streamlit) → Orchestrator Agent → Sub-Agents (Text, Code) → Tool Executor (Docker) → History Renderer → Assets Manager (persistence/export).
- **Critical path:** Structured prompt → context build (prompt + empty history) → Orchestrator call → `request_code(purpose)` → Code Agent generates code → Docker execution → output/error capture → History Renderer condenses → new context → repeat until `finish()`.
- **Design tradeoffs:**  
  - Transparency vs. Efficiency: Full step enumeration is readable but increases token count vs. monolithic code generation.  
  - Generality vs. Control: Generic LLM agents are flexible but may require retry logic/tool emulation for weaker models.  
  - Privacy vs. LLM Capability: Local data maximizes privacy but forces reliance on aggregate statistics, which may omit critical patterns.
- **Failure signatures:**  
  - Orchestrator emits non-JSON or wrong action name → tool call fails (use tool emulation).  
  - Code execution fails repeatedly → hits max retries, likely due to ambiguous `purpose` or missing libraries.  
  - History rendering truncates mid-step → LLM loses recent context, may generate redundant steps.  
  - Docker environment lacks required library → code fails; extend Docker image.
- **First 3 experiments:**  
  1. **Structured prompt efficacy:** Run a Kaggle task with structured vs. free-form prompt; compare step coherence, retries, validity.  
  2. **History truncation impact:** Vary 10k character limit (5k, 10k, 20k) on a moderately long task; measure orchestrator degradation (repetition, constraint forgetting).  
  3. **Agent routing robustness:** Force two consecutive `request_code` calls (skip text); observe if code steps remain logical.

## Open Questions the Paper Calls Out
- **How can CEDAR be extended with independent meta-agents to automatically verify solution faithfulness to user intent and critique workflows for metric optimization?**  
  Basis: The conclusion proposes introducing independent agents for faithfulness inspection and metric critique. Unresolved because current system lacks meta-agents; no evaluation of automated critique.
- **How effective is the smart history rendering (e.g., 10k character truncation, output head/tail selection) in preserving necessary context for solution quality while respecting LLM context limits?**  
  Basis: The paper describes rendering rules but reports no quantitative metrics on context efficiency or impact on task success. The 10k limit and output trimming are untested heuristics.
- **Can CEDAR scale beyond beginner-level Kaggle competitions to handle complex, multi-modal, or enterprise-scale data science problems with larger data sizes and longer workflows?**  
  Basis: The scope explicitly states it solves beginner-level Kaggle tasks. Ability for harder tasks (advanced feature engineering, large datasets) is untested and may break context or code generation.

## Limitations
- Source code unreleased; specifics of orchestrator logic, history rendering, and Docker environment not publicly verifiable.
- No quantitative metrics (e.g., success rate, token efficiency, accuracy vs. baseline) reported; viability shown anecdotally.
- Core design assumptions (aggregate statistics sufficiency, 10k truncation heuristic) remain unvalidated and may fail on tasks requiring fine-grained data patterns.

## Confidence
- Structured prompts: Medium
- Interleaved plan/code: Medium
- Local execution + smart rendering: Low
- Overall viability claim: Medium
