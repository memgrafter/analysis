# A Human-in-the-Loop, LLM-Centered Architecture for Knowledge-Graph Question Answering

## Quick Facts
- **arXiv ID:** 2602.05512
- **Source URL:** https://arxiv.org/abs/2602.05512
- **Reference count:** 40
- **Primary result:** An interactive framework where LLMs generate and explain Cypher queries over knowledge graphs, with users refining them via natural language, achieving high accuracy on real-world KGs but with model-specific and domain-dependent limitations.

## Executive Summary
This paper presents a modular pipeline for knowledge graph question answering that centers on LLM-generated Cypher queries. To address hallucination and opacity, the system incorporates natural-language explanations and user-driven query amendments. Evaluated on synthetic and real-world KGs, results show that state-of-the-art LLMs can solve most tasks, but explanation faithfulness and domain generalization vary significantly. The approach demonstrates that human-in-the-loop interaction can enhance transparency and correctness without requiring Cypher expertise, though it highlights persistent challenges in explanation quality and complex domain adaptation.

## Method Summary
The architecture comprises four core LLM-powered modules: a **Generator** creates Cypher queries from natural language questions using schema-aware prompts; an **Executor** runs these queries in Neo4j and returns results; an **Explainer** produces step-by-step and summary explanations of the query logic, flagging potential errors; and an **Amender** revises queries based on user-provided natural-language feedback. The pipeline operates iteratively: the initial query is executed and explained, the user reviews the explanation and results, and can submit amendments to refine the query. Evaluation used a synthetic movie KG benchmark to measure explanation accuracy and fault detection, and two real-world KGs (MaRDI, Hyena) to test query generation success rates and amendment efficiency across multiple LLMs. No model fine-tuning was performed; all LLMs were used off-the-shelf via APIs or local deployment.

## Key Results
- Explanation accuracy varied by model: o1-preview, deepseek-reasoner-api, and o3-mini exceeded 70% correct one-sentence summaries, while Claude 3.7 Sonnet was lowest at 52%.
- Fault detection rates were above 80% for top models, but false positive rates ranged up to 47%, indicating over-sensitivity.
- On real-world KGs, most LLMs solved most tasks, but success rates differed: on MaRDI, o3-mini and GPT-5.2 achieved 100% accuracy; on Hyena, only o3 and deepseek-reasoner-api were perfect, with other models failing entirely.
- Amendment rounds improved outcomes but efficiency dropped on complex, domain-specific questions (Hyena), with many queries requiring multiple attempts or remaining unsolved.

## Why This Works (Mechanism)

### Mechanism 1: Transparency via Explanation
- **Claim:** The framework increases transparency and user trust by generating natural-language explanations of generated Cypher queries.
- **Mechanism:** An LLM (same or separate from the generator) is prompted to produce a step-by-step walkthrough and a concise summary of the query’s logic and purpose, explicitly flagging semantic or syntactic anomalies (e.g., reversed relationships, implausible node types).
- **Core assumption:** LLMs can accurately interpret and verbalize the logical structure and intent of a syntactically correct Cypher query.
- **Evidence anchors:** Abstract states "LLMs generate and explain Cypher queries"; Section 2.1 describes the Query Explanation component with a dedicated prompt for structured explanations and error flagging.
- **Break condition:** Explanations may omit critical constraints (e.g., temporal filters), as seen in the benchmark where year omissions caused over 50% of errors for top models, potentially misleading users.

### Mechanism 2: Iterative Refinement via Amendments
- **Claim:** Iterative query refinement via natural-language amendments enables non-expert users to correct LLM errors without learning Cypher.
- **Mechanism:** User feedback in natural language is processed by an “Amender” LLM module, which modifies the existing query rather than regenerating from scratch, preserving valid parts while incorporating the amendment.
- **Core assumption:** LLMs can precisely apply targeted textual amendments to a Cypher query while respecting graph schema constraints.
- **Evidence anchors:** Abstract states "users refine them via natural language"; Section 2.1 details the Amendment component with a prompt that takes the current query, user instruction, and schema to produce a revised query; Section 1.1 shows an example interaction correcting "software package, not publication".
- **Break condition:** Amendments may introduce new errors or fail to capture nuanced user intent, particularly on domain-specific questions (e.g., Hyena KG questions often required multiple attempts, indicating amendment difficulty).

### Mechanism 3: Grounding in Knowledge Graph Execution
- **Claim:** Grounding LLM responses in a structured Knowledge Graph execution reduces hallucinations and ensures factual accuracy.
- **Mechanism:** Generated Cypher queries are executed against a Neo4j database; results are returned directly from the KG, bypassing LLM memory or parametric knowledge for factual retrieval.
- **Core assumption:** The KG is a curated, accurate source of truth, and the LLM can generate syntactically and semantically valid queries that execute successfully.
- **Evidence anchors:** Abstract notes "preserving factual accuracy and semantic rigor"; Section 1 contrasts KG-based retrieval with text-based RAG, noting KGs support "precise, explainable querying"; Section 2.1 describes Query Execution using a Neo4j driver.
- **Break condition:** Query execution fails (syntax error, schema mismatch) or returns empty/incorrect results due to flawed query logic, which the explanation and amendment steps aim to catch.

## Foundational Learning
- **Cypher query structure (MATCH, WHERE, RETURN):** Needed to interpret the system’s explanations and assess whether an amendment request is feasible within Cypher’s semantics. Quick check: "Given `MATCH (a:Actor)-[:ACTED_IN]->(m:Movie) WHERE m.year > 2000 RETURN a.name`, what does the `WHERE` clause filter on?" (Answer: movies released after 2000).
- **Knowledge Graph basics (nodes, relationships, properties, traversal):** Needed to understand the schema provided to the LLM and reason about why a query might succeed or fail. Quick check: "If a graph has `(Person)-[:WORKS_AT]->(Company)`, how would you find people who work at ‘Google’?" (Answer: `MATCH (p:Person)-[:WORKS_AT]->(c:Company {name: 'Google'}) RETURN p`).
- **Prompt engineering for constrained generation:** Needed because the system’s success hinges on prompts that force the LLM to adhere to the schema and produce executable Cypher. Quick check: "Why might a prompt instruct ‘Use only the provided relationship types’? What could go wrong without it?" (Answer: The LLM might invent relationship types not in the schema, causing execution errors).

## Architecture Onboarding
- **Component map:** User -> Generator -> Executor -> Explainer -> User; (optional) User -> Amender -> Executor loop.
- **Critical path:** 1) User question → Generator produces initial Cypher; 2) Executor runs query; results returned; 3) Explainer generates explanation shown to user; 4) User optionally provides amendment → Amender revises query → loop to step 2.
- **Design tradeoffs:**
  - Transparency vs. Brevity: Explanations must be concise yet complete; omission of details (e.g., years) harms faithfulness.
  - Automation vs. User Effort: More amendment rounds improve accuracy but increase user interaction burden.
  - Model Choice: Stronger models (o1, o3, deepseek-reasoner) reduce amendment needs but may have cost/latency tradeoffs.
- **Failure signatures:**
  - High false-positive error flags (e.g., Claude’s 33% FP rate) erode trust.
  - Persistent query failures on specific question types (e.g., “shared authors” in MaRDI; all Hyena questions for some models).
  - Amendment inefficiency: requiring >2 amendments for correct query, especially on domain-specific KGs.
- **First 3 experiments:**
  1. Synthetic Movie KG Benchmark: 90 handcrafted queries with perturbations to measure explanation accuracy and fault detection across 5 LLMs.
  2. MaRDI KG Case Study: 9 software-centric questions on a mathematical research KG; measures first-attempt and within-3-attempts accuracy across 14 LLMs.
  3. Hyena KG Case Study: 5 expert-written biological questions on a long-term hyena monitoring KG; tests cross-domain robustness and amendment efficiency under realistic conditions.

## Open Questions the Paper Calls Out
- **Open Question 1:** Why do Cypher queries with OPTIONAL MATCH or WITH clauses (i.e., (+1) variants) yield higher explanation accuracy than base queries of equivalent hop count? Basis: The authors observed that "base 1-hop queries were easier than 2–3 hops, whereas '(+1)' variants created by OPTIONAL MATCH or WITH were unexpectedly easier than their bases, with the cause being uncertain and meriting follow-up investigation" (Section 3.5.1.2). Why unresolved: The cause of this performance difference is not understood; clarifying it could inform better query design and model training. What evidence would resolve it: Controlled experiments comparing these query types while holding other factors constant, analyzing model attention or error patterns, or testing hypotheses about clause structure and intermediate results.
- **Open Question 2:** How can prompting or fine-tuning be improved to prevent LLMs from omitting critical constraints (e.g., temporal values) in explanations, thereby increasing faithfulness? Basis: The evaluation found that omission of years was a major error in one-sentence summaries, with over 80% of some models' incorrect summaries missing the year. The authors suggest that "explicitly requiring the retention of temporal information during instruction tuning could address this issue" (Section 3.6). Why unresolved: Current prompts lead to a trade-off between brevity and completeness; without effective methods, explanations may lack necessary detail. What evidence would resolve it: Comparative studies of prompt variants that emphasize inclusion of numeric/temporal constraints; fine-tuning on datasets that penalize omission; measuring explanation accuracy on the benchmark with relaxed vs. strict criteria.
- **Open Question 3:** To what extent do expert-sourced, domain-specific questions expose limitations in LLM-based KG querying that are not apparent from synthetic benchmarks? Basis: Based on the comparison between MaRDI and Hyena experiments, the authors conclude: "First, expert-sourced questions are essential for discriminating among models that appear comparable on synthetic tests, and several Knowledge Graphs should be used to evaluate a method" (Section 4.6). Why unresolved: The synthetic movie KG benchmark may not capture real-world complexities; understanding the gap is vital for robust evaluation. What evidence would resolve it: Systematic evaluation across multiple domains using both synthetic and expert-curated question sets, with detailed error analysis to identify domain-specific failure modes.
- **Open Question 4:** Can automatic metrics be developed that reliably measure the quality of natural language explanations for Cypher queries, aligning with human judgments of completeness and correctness? Basis: The authors note that "the scoring process relied on human judgement, introducing some subjectivity in determining what constitutes a 'complete' and correct summary" (Section 3.6), implying a need for automated alternatives. Why unresolved: Human evaluation is costly and potentially inconsistent; scalable, objective metrics are lacking. What evidence would resolve it: Development of metrics based on reference explanations, logical equivalence, or constraint satisfaction; validation against human scores on a diverse query set with injected errors.

## Limitations
- Small, domain-specific benchmarks (90 synthetic, 9 MaRDI, 5 Hyena) limit generalizability.
- Amendment instructions were author-generated; real user feedback may behave differently.
- Some LLMs are unreleased/private, and benchmark queries/Hyena KG are not fully public, hindering replication.
- Explanation accuracy modest (52–73% correct summaries); fault detection false positives up to 47%.
- Domain shift hurts performance: Hyena KG stumped most models.

## Confidence
- **Transparency claims:** Medium. Evidence from explanation accuracy, but no user trust measurements and significant omission errors.
- **Iterative refinement:** Medium-Low. Amendment works on simple/synthetic data but degrades on complex real domains.
- **Grounded accuracy:** High. KG execution guarantees factuality *if* the query is correct; query generation remains the weak link.

## Next Checks
