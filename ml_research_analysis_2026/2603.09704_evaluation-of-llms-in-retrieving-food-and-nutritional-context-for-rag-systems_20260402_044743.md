# Evaluation of LLMs in retrieving food and nutritional context for RAG systems

## Quick Facts
- **ArXiv ID:** 2603.09704
- **Source URL:** https://arxiv.org/abs/2603.09704
- **Reference count:** 22
- **Primary result:** LLMs achieve near-perfect retrieval (F1>0.999) on easy/medium food queries but performance drops sharply on complex queries (max F1=0.450), indicating reliability only for schema-expressible constraints.

## Executive Summary
This study evaluates four large language models (Gemini, GPT, Claude, Mistral) for their ability to generate structured metadata filters from natural language queries to search a food composition vector database. The core finding is that these models retrieve with near-perfect accuracy on straightforward queries but struggle significantly on more complex ones, revealing a key limitation: LLM-driven retrieval is reliable solely for constraints that can be explicitly represented within the predefined metadata schema.

## Method Summary
The authors likely constructed a benchmark of natural language queries about food and nutrition, each paired with a ground-truth set of relevant food items from a vector database. For each query, the evaluated LLMs were prompted to output a metadata filter (e.g., `category="fruit" AND vitamin_c>10`) conforming to a fixed schema. This filter was then used to query the database, and the retrieved results were compared to the ground truth using F1 score. Performance was stratified by query difficulty (easy, medium, hard).

## Key Results
- Near-perfect retrieval on easy and medium queries (F1 > 0.999).
- Maximum F1 on hard queries is 0.450, demonstrating a significant performance drop.
- LLM-driven retrieval reliability is constrained to query facets explicitly expressible in the metadata schema.

## Why This Works
Performance is high on easy/medium queries because their constraints (e.g., specific food names, clear categories, single numeric thresholds) map directly and unambiguously to the available metadata fields. The LLM effectively translates these into valid filter syntax. For "hard" queries, failure likely arises when constraints involve reasoning beyond the schema's literal fields—such as multi-step comparisons, implicit dietary patterns, or ambiguous terms—which the LLM cannot encode into a valid filter, leading to empty or incorrect retrievals.

## Architecture Onboarding
- **Component map:**  
  Natural Language Query -> LLM (Filter Generator) -> Structured Metadata Filter -> Vector Database (with metadata indexing) -> Retrieved Document IDs

- **Critical path:**  
  User query is sent to LLM with schema definition; LLM outputs a syntactically correct filter; filter is applied as a pre- or post- step to vector similarity search; top-k matching documents are returned.

- **Design tradeoffs:**  
  Schema simplicity vs. coverage: A minimal schema (few fields) makes filter generation easier for the LLM but severely limits the types of queries that can be answered. A complex, nested schema allows richer constraints but increases the risk of invalid filter syntax or mis-specified values.

- **Failure signatures:**  
  - Empty result sets: filter is over-constrained or uses values not present in the DB.  
  - Low-precision retrievals: filter is under-constrained or misinterprets query intent.  
  - Syntax errors: LLM produces non-parsable filter expressions (though likely filtered in evaluation).

- **First three experiments:**  
  1. **Baseline model comparison:** Run all four LLMs on a fixed set of 100 easy, 100 medium, and 100 hard queries to confirm the reported performance gap per model.  
  2. **Schema expansion test:** Add a new metadata field (e.g., `meal_type`) to the schema and re-evaluate only on hard queries that could leverage this field; measure F1 change.  
  3. **Prompt ablation for hard queries:** For hard queries, compare standard prompting vs. Chain-of-Thought vs. few-shot examples to isolate whether improved reasoning can boost F1 without schema changes.

## Limitations
- The operational definition of "hard" queries (e.g., multi-hop, ambiguous, or out-of-schema constraints) is not clearly specified.
- The metadata schema's specific fields and its inherent expressiveness limits are not detailed, making it hard to generalize why certain queries fail.
- Evaluation is restricted to four proprietary/closed models, limiting insights into open-source or smaller models and broader reproducibility.

## Confidence
- **Near-perfect retrieval on easy/medium queries (F1>0.999):** High (metric explicitly reported).  
- **Significant performance drop on hard queries (max F1=0.450):** Medium (result stated but without per-model variance or error analysis).  
- **LLM-driven retrieval is reliable only for constraints explicitly expressible in the metadata schema:** Medium (inferred from results, but schema-design confounders like field cardinality or nesting are not ruled out).

## Next Checks
1. **Schema Audit:** Catalog all metadata fields and formally define which query constraints are *in principle* expressible vs. inexpressible in the schema.
2. **Query Taxonomy:** Re-annotate “hard” queries by failure mode (e.g., requires numerical comparison, temporal reasoning, disambiguation) to isolate whether low F1 stems from LLM reasoning or schema gaps.
3. **Prompt Sensitivity Test:** Re-run hard queries with Chain-of-Thought, few-shot, and constraint-elicitation prompts to measure if performance gains are possible without schema changes.
