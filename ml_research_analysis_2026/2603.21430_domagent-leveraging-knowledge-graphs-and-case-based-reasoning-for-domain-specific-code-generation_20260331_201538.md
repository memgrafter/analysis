# DomAgent: Leveraging Knowledge Graphs and Case-Based Reasoning for Domain-Specific Code Generation

## Quick Facts
- **arXiv ID:** 2603.21430
- **Source URL:** https://arxiv.org/abs/2603.21430
- **Reference Count:** 40
- **Primary Result:** Integrates knowledge graph retrieval and case-based reasoning to boost small open-source LLMs by up to +57% on domain-specific code generation, nearly matching large proprietary models.

## Executive Summary
DomAgent addresses the poor performance of generic large language models (LLMs) on domain-specific code generation by combining structured knowledge retrieval from a domain knowledge graph (KG) with case-based reasoning (CBR). Its core component, DomRetriever, dynamically performs top-down KG reasoning and bottom-up case retrieval, then uses an LLM-guided review step to filter and synthesize the most relevant context. Evaluated on the DS-1000 data science benchmark and real-world truck CAN signal tasks, DomAgent improved a 7B parameter model by +9.9% and +57.0% pass@1 respectively, while requiring far fewer curated examples than random sampling. The system has been deployed in an industrial setting for truck signal code generation.

## Method Summary
DomAgent constructs a domain knowledge graph from official documentation and builds a compact case base via a KG-guided selection process that maximizes coverage of packages and functional clusters. At inference, an LLM agent (DomRetriever) equipped with special tool tokens (`<search_kg>`, `<search_case>`) actively decides when to retrieve. It first retrieves candidate KG entities (top-down) and code cases (bottom-up), re-ranks cases by overlap with KG results, then enters a review loop where an LLM filters irrelevant items and may trigger additional searches. The refined context (knowledge and a selected case) is concatenated with the query and passed to a code generator LLM. Training involves supervised fine-tuning on demonstrations of tool use and reinforcement learning (GRPO) with a reward model that scores the relevance of the retrieved context.

## Key Results
- Improved Qwen2.5-7B pass@1 by **+9.9%** on DS-1000 (from 29.3% to 39.2%) and by **+57.0%** on truck CAN tasks (from 39.62% to 96.64%).
- KG-guided case selection achieved performance equivalent to using 100% of data with only **~30%** of randomly sampled cases on DS-1000.
- The full DomAgent setup (KG+CBR+Review) showed significant gains over ablations using only KG or only CBR, demonstrating the synergy of bidirectional retrieval and LLM-guided synthesis.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** KG-guided hierarchical case selection efficiently builds a small, high-coverage case base.
- **Mechanism:** The KG's package-function hierarchy is exploited: package-level anchors ensure broad package coverage, while function-level clustering within packages ensures diverse usage patterns. Cases are iteratively added only if they increase package or cluster coverage ratios (α, β) beyond thresholds (τ₁, τ₂).
- **Core assumption:** Covering more KG nodes/relationships correlates with solving a wider range of coding tasks; functional usage patterns in the KG (clusters) predict task diversity.
- **Evidence anchors:** [abstract] "exploits relational information in the KG to guide case selection, ensuring diversity by covering as many functions in the graph as possible." [section 4.1] Details the package-level anchoring, function-level clustering, and coverage-driven iterative selection with stopping criteria.
- **Break condition:** If the KG is incomplete or its relational structure poorly maps to functional diversity in code tasks, selected cases may have low practical relevance despite high coverage metrics.

### Mechanism 2
- **Claim:** Dynamic bidirectional retrieval (top-down KG + bottom-up CBR) followed by LLM-guided review yields more relevant and precise context than static RAG.
- **Mechanism:** 1) Top-down: LLM classifier selects candidate packages from KG descriptions, then semantic similarity ranks KG entities. 2) Bottom-up: Semantic similarity retrieves candidate code cases, re-ranked by overlap with retrieved packages. 3) LLM review: A reasoning LLM inspects the top case and KG results, filtering irrelevant items or triggering additional searches via tool tokens.
- **Core assumption:** An LLM can act as an effective meta-reviewer to filter superficial matches and synthesize the most contextually appropriate blend of structured knowledge and examples.
- **Evidence anchors:** [abstract] "dynamically integrates top-down knowledge-graph reasoning with bottom-up case-based reasoning, enabling iterative retrieval and synthesis... LLM-guided review." [section 4.2.1] Details the two-stage retrieval, overlap-based re-ranking, and review process enclosed in ` to a refined answer `.
- **Break condition:** If initial retrieval is systematically off-topic or the LLM reviewer lacks capability to discern true relevance (e.g., for highly novel patterns), the review may filter out useful information or fail to correct errors.

### Mechanism 3
- **Claim:** Training the LLM via SFT + RL to invoke retrieval tools and optimize for integrated relevance makes retrieval an active reasoning process rather than static pre-processing.
- **Mechanism:** 1) SFT: Create demonstrations where a teacher LLM generates reasoning with tool invocation tokens for domain tasks. 2) RL: A reward model scores final output relevance (q || bK || ĉ). GRPO updates the policy to maximize this reward, encouraging effective tool-use and review.
- **Core assumption:** A learnable policy exists where the optimal action is to retrieve and review; the reward signal effectively captures quality of retrieved+reviewed context for code generation.
- **Evidence anchors:** [section 4.3] Explicitly describes SFT data construction with synthetic reasoning chains and RL optimization using GRPO with a reward model based on query-context relevance.
- **Break condition:** If the reward model is misaligned with true code generation success (pass@1) or RL exploration is insufficient, the policy may learn to sparsely invoke tools or produce superficially plausible but irrelevant reviews.

## Foundational Learning
- **Knowledge Graph (KG) for Software Domains**  
  *Why needed:* Provides structured, noise-reduced representation of domain entities (packages, functions, parameters) and relationships, enabling precise "top-down" retrieval by matching concrete identifiers rather than ambiguous natural language.  
  *Quick check:* Given a task `utils.can.read()`, how does a KG representation allow retrieval of *only* relevant signal processing knowledge versus general file I/O knowledge?

- **Case-Based Reasoning (CBR)**  
  *Why needed:* Supplies executable "bottom-up" examples of domain-specific code patterns and idioms missing from generic LLM training but critical for context-specific adaptation (e.g., CAN signal value mappings).  
  *Quick check:* Why is a dynamically retrieved, KG-filtered case more effective for a novel truck signal task than a static, fixed set of few-shot examples?

- **Retrieval-Augmented Generation (RAG) with Tool-Use**  
  *Why needed:* Forms the interface where the LLM agent actively decides *when* and *what* to retrieve, integrating external knowledge into its internal state before final code generation, rather than blindly appending static context.  
  *Quick check:* What is the failure mode of a "standard RAG pipeline" (retrieve-then-generate) that DomAgent's ``-based review step aims to mitigate?

## Architecture Onboarding
**Component map:**  
Task Query -> DomRetriever (uses Case Base B and Knowledge Graph G) -> Refined Context (bK, ĉ) -> Code Generator (LLM_gen) -> Generated Code (ŷ).  
Reward Model (fᵣ) provides training signal for DomRetriever.

**Critical path:**  
1. Query `q` is received.  
2. DomRetriever invokes `SearchKG(q)` → retrieves KG nodes `K`; and `SearchCase(q)` → retrieves cases `C`.  
3. LLM review within ` to a refined answer `` filters `K` and `C` to produce `bK` and `ĉ`.  
4. Concatenate `[q || bK || ĉ]` and feed to `LLM_gen` to generate code `ŷ`.

**Design tradeoffs:**  
- **KG construction cost vs. retrieval precision:** Richer KG improves top-down accuracy but requires more effort to build/maintain.  
- **Case base size vs. coverage:** KG-guided selection aims to minimize required cases (e.g., 30% vs. random) but depends on KG quality and clustering parameters.  
- **Review depth vs. latency:** LLM adds inference steps; deployed systems must balance filtering benefit against response time.

**Failure signatures:**  
- **Low package coverage (α) or cluster coverage (β):** Case base is insufficiently diverse → poor performance on tasks involving certain packages/functions.  
- **High irrelevant knowledge in `bK`:** LLM review failed → generated code calls wrong APIs despite correct pattern.  
- **Tool misuse:** LLM does not generate `<search_kg>`/`<search_case>` tokens or generates them in wrong order → empty or default `bK`/`ĉ`.

**First 3 experiments:**  
1. **Case Base Construction Validation:** On DS-1000, vary sampling proportion for KG-guided vs. random selection. Plot pass@1 vs. proportion. Expect KG-guided to reach near-peak at ~30%.  
2. **Component Ablation:** For fixed backbone (e.g., Qwen2.5-7B), test: Baseline, +KG (only top-down), +CBR (only bottom-up), +KG+CBR (DomAgent). Measure pass@1 on DS-1000 and Truck CAN. Expect full DomAgent to show largest gain, with review step adding margin over simple RAG.  
3. **Retriever-Generator Decoupling:** Test DomRetriever (with small LLM) as plug-in for larger generator (e.g., GPT-4o). Compare `GPT-4o` vs. `DomRetriever(Qwen2.5-7B) + GPT-4o`. Expect significant lift, demonstrating DomRetriever's value independent of generator strength.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** To what extent does incorporating AST-based fine-grained structural similarity improve the effectiveness of case retrieval and overall code generation in DomAgent?
- **Basis:** [explicit] Future work: "incorporate AST–based fine-grained similarity analysis [44], to improve the performance of retrieving relevant code cases at the structural level."
- **Why unresolved:** DomRetriever relies on embedding semantics and KG-guided package overlap, potentially missing fine-grained syntactic relationships. Impact of AST-based reranking on retrieval precision and pass@1 remains unevaluated.

### Open Question 2
- **Question:** Can soft prompts (continuous prompt tuning) enable efficient, low-cost domain adaptation of DomAgent compared to full fine-tuning with RL?
- **Basis:** [explicit] Future work: "explore the use of soft prompts [22], a lightweight form of knowledge injection, to enable the model to efficiently adapt to new domains with minimal retraining."
- **Why unresolved:** Current approach requires SFT+RL to teach tool use and reasoning, which is computationally heavy. Soft prompts might achieve similar adaptation but their ability to preserve retrieval-triggering behavior and review capability is unknown.

### Open Question 3
- **Question:** How does DomAgent's performance and component dynamics generalize across a broader spectrum of industrial domains beyond data science and automotive CAN signal processing?
- **Basis:** [explicit] Future work: "evaluate DomAgent in a wider range of real-world industrial scenarios to further validate its practicality and generalizability."
- **Why unresolved:** Evaluation covers only two domains (library-heavy vs. signal-mapping). DomAgent's dependence on a knowledge graph and case base may face challenges in domains with sparse documentation, unconventional patterns, or dynamic APIs. Relative value of KG vs. CBR in such settings is unclear.

## Limitations
- **KG dependency:** Performance hinges on a comprehensive, accurate knowledge graph; incomplete/noisy documentation may cripple top-down retrieval.
- **Black-box RL training:** Critical details of the reinforcement learning stage (reward model implementation, GRPO hyperparameters) are underspecified, hindering exact replication.
- **Deployment context:** Real-world truck CAN task lacks public benchmarks or independent replication, limiting generalizability claims beyond the reported factory deployment.

## Confidence
- **High:** Reported performance gains (+9.9% DS-1000, +57% truck tasks) and case-base efficiency (30% vs. random) are empirically validated within the paper's experiments.
- **Medium-High:** The dynamic retrieval+review mechanism shows ablative benefit, but its sufficiency for highly novel tasks depends on LLM reviewer capability, which was not stress-tested.
- **Low:** The RL training loop's design and reward alignment; without full details, robustness of learned tool-invocation strategies remains uncertain.

## Next Checks
1. **Replicate case-base scaling:** Independently run the KG-guided selection algorithm (with disclosed `k-means` seeds/`k`) on DS-1000. Verify that 30% of cases achieve >90% of peak performance, as in Figure 3.
2. **Component isolation test:** On a fixed small model (e.g., Qwen2.5-7B), ablate *only* the LLM-guided review step. Implement a simple overlap-based fusion instead; measure drop in pass@1 to quantify review's marginal contribution.
3. **Sensitivity to KG sparsity:** Artificially remove 20% of KG nodes (simulating incomplete documentation). Measure degradation in top-down retrieval precision and final code generation pass@1 to characterize brittleness.
