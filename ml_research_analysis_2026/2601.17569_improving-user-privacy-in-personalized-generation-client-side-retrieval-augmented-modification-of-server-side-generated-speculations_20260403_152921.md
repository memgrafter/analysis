# Improving User Privacy in Personalized Generation: Client-Side Retrieval-Augmented Modification of Server-Side Generated Speculations

## Quick Facts
- arXiv ID: 2601.17569
- Source URL: https://arxiv.org/abs/2601.17569
- Reference count: 40
- Primary result: P³ improves personalized QA utility by 7.4–9% over baselines while adding only 1.5–3.5% privacy leakage, with the client generating just 9.2% of tokens.

## Executive Summary
Personalized large language model (LLM) generation typically requires sharing user profiles with the server, posing privacy risks. This paper introduces P³ (Privacy-Preserving Personalization), a novel framework that decouples personalization from server access to private data. In P³, a powerful server-side model generates draft tokens using only the query, while a small client-side model with retrieval access to the user’s private profile verifies and modifies these drafts in an iterative loop. Personal Identifiable Information (PII) is filtered from the server’s history to prevent leakage. Evaluated on the LaMP-QA benchmark, P³ achieves statistically significant improvements of 7.4–9% in utility over both non‑personalized server‑side and personalized client‑side baselines, recovers 90.3–95.7% of the utility of a leaky upper bound that exposes the full profile, and introduces only 1.5–3.5% additional privacy leakage compared to a query‑only baseline. The client‑side model generates only 9.2% of total tokens, keeping user‑side computational costs low. These results demonstrate a practical privacy‑utility trade‑off for real‑world personalized LLM services.

## Method Summary
P³ operates as an interactive speculate‑verify‑correct pipeline. Initially, the client retrieves the top‑10 relevant documents from the user’s private profile using a Contriever retriever and extracts all PII spans with regex. The client then builds two prompts: one for the server (query only) and one for itself (query plus retrieved context). In each generation step, the server model (e.g., Qwen‑14B) proposes a sequence of 10 draft tokens conditioned solely on its prompt. The client model (e.g., Qwen‑3B) evaluates each draft token by comparing its probability under the client’s context‑aware distribution to the probability of the most likely alternative. If the ratio falls below a threshold τ (default 0.05), the client replaces the token with the alternative and stops consuming the draft. Accepted tokens are appended to the response and the client’s history. The client then filters any PII spans from the newly generated tokens (replacing them with a [PII] marker) and updates the server’s history before the next draft. This loop continues until an end‑of‑sequence token is produced. By never exposing raw profile data to the server and by limiting the server’s context to filtered history, P³ achieves personalization with minimal privacy leakage and reduced client computation.

## Key Results
- **Utility gain**: P³ improves normalized personalization scores by 7.4–9% over non‑personalized server‑side and client‑side baselines on three LaMP‑QA datasets.
- **Near‑optimal recovery**: P³ attains 90.3–95.7% of the utility of a leaky upper bound that provides the full profile to the server.
- **Privacy preservation**: Linkability and attribute inference attacks show only 1.5–3.5% additional leakage compared to submitting the query alone.
- **Efficiency**: The client‑side model generates only 9.2% of all tokens on average; it accepts the full draft in 62.8% of steps, requiring minimal user‑side computation.

## Why This Works (Mechanism)
### Mechanism 1: Iterative Speculate‑Verify‑Correct
The core of P³ is an asymmetric speculative decoding loop. The large server model proposes batches of draft tokens based only on the query, while the small client model, equipped with private profile context, acts as verifier and corrector. The client computes the probability of each proposed token under its own distribution and compares it to the probability of the most likely alternative. A low ratio indicates the token is inappropriate for the user, prompting replacement and early termination of the draft. This mechanism allows the server to contribute the bulk of generation (reducing client load) while the client steers the output toward personal preferences without exposing the profile. The approach assumes the client model, despite its smaller size, can reliably judge token appropriateness when conditioned on the profile—a claim supported by empirical results showing significant utility gains. Potential failure arises if the client model is too weak to judge or if the threshold τ is poorly tuned, leading to over‑ or under‑correction.

### Mechanism 2: Privacy via Token‑Level Exchange and PII Filtering
P³ ensures privacy by strictly limiting the information crossing the client‑server boundary. The server never sees the raw user profile or the retrieved documents; only token IDs are transmitted. Moreover, before any tokens generated under the influence of the client’s context are fed back to the server, a PII extractor identifies sensitive spans (emails, phone numbers, SSNs, etc.) in those tokens and replaces them with a [PII] marker. This prevents the server from inadvertently memorizing or leaking explicit private information. The threat model assumes a passive server that follows the protocol; even in this case, some leakage may occur via stylistic cues or missed PII, but the measured increase in linkability and attribute inference accuracy (1.5–3.5%) is marginal. The mechanism’s robustness depends on the coverage of the PII detector and the assumption that token streams alone reveal little about the profile.

### Mechanism 3: Client Efficiency via Selective Steering
Because the server produces the majority of tokens, the client’s computational burden is small. Empirically, the client generates only 9.2% of tokens and accepts the full draft in 62.8% of iterations, meaning it often agrees with the server’s proposal. This asymmetry is a deliberate design choice: a tiny client model can effectively guide a large server model as long as it only intervenes occasionally. The trade‑off is governed by the draft size k and the threshold τ. A larger k reduces communication overhead but risks greater server drift before correction; a lower τ increases personalization but may raise client workload. The reported hyperparameters (k=10, τ=0.05) strike a good balance. If the server’s outputs are consistently misaligned, the intervention rate could rise, eroding efficiency gains.

## Foundational Learning
Understanding P³ benefits from three key concepts:

- **Speculative Decoding**: In standard speculative decoding, a small “draft” model proposes tokens and a large “target” model verifies them in a single pass. P³ inverts this paradigm: the large server proposes drafts and the small client verifies, but adds a personalization twist where the verifier has privileged context.  
  *Quick check*: In standard speculative decoding, which model proposes draft tokens and which verifies? How does P³ reverse this and why?

- **Retrieval‑Augmented Generation (RAG) for Personalization**: Typical server‑side RAG personalization retrieves user profile documents on the server, then conditions the LLM on them. This leaks the full profile. P³ instead retrieves on the client and never sends raw documents, only token‑level modifications.  
  *Quick check*: In typical RAG‑based personalization, where is retrieval executed and where is retrieved context consumed? What is the primary privacy risk?

- **Privacy Threat Modeling (Linkability & Attribute Inference)**: These two attacks measure different aspects of privacy leakage. Linkability assesses whether an adversary can link a generated response to the correct user among candidates, indicating identity leakage. Attribute inference checks whether specific profile attributes (e.g., occupation) can be deduced from the output.  
  *Quick check*: What does a linkability attack measure versus an attribute inference attack? What would high accuracy indicate in each?

## Architecture Onboarding
### Component Map
User Profile (P_u) → Retriever → Retrieved Context (C_q)  
C_q → PII Extractor → PII Spans (E)  
Query (q) + C_q → Client Prompt → Client LLM (M_client)  
Query (q) → Server Prompt → Server LLM (M_server)  
Token loop: Server drafts k tokens → Client evaluates each (using M_client on H_C) → Accept/Replace → Update response & H_C → Filter PII from new tokens → Update H_S → repeat.  
Buffers: H_C (client history), H_S (server history). PII Filter replaces E spans with [PII] in H_S.

### Critical Path
1. Input: query q, user profile P_u.
2. Client retrieval: C_q = R(P_u, q, m=10).
3. PII extraction: E = ExtractPII(C_q).
4. Initialize prompts: H_C = template(q, C_q); H_S = template(q).
5. While not EOS:
   a. Server: Generate T₁:k ∼ M_server(H_S, k).
   b. Client: For Tᵢ from 1 to k:
      - Compute p = P_client(Tᵢ | H_C, V, T₁:i₋₁).
      - Find Tᵢ* = argmax_ω P_client(ω | H_C, V, T₁:i₋₁).
      - If p / P_client(Tᵢ*) < τ: accept Tᵢ*, break draft loop; else accept Tᵢ.
   c. Append accepted tokens V to response y and to H_C.
   d. Update H_S = FilterPII(H_S ∪ V, E) (replace E spans with [PII]).
6. Output y.

### Design Tradeoffs
- **τ (rejection threshold)**: Lower values (e.g., 0.025) cause more client corrections (better personalization? but higher latency); higher values (e.g., 0.1) reduce interventions (faster, but less personalized). Optimal found near 0.05.
- **k (draft size)**: Larger k reduces communication rounds but risks server drift before client can intervene; too small increases overhead. Optimal around 10.
- **Client model size**: Larger M_client improves verification accuracy but increases user‑side compute and memory. Gains diminish beyond certain size (Figure 6A).
- **PII detection granularity**: Aggressive filtering (high recall) protects privacy but may remove useful personal context; conservative filtering risks leakage. The paper uses a simple regex; more sophisticated methods could shift the trade‑off.
- **Retrieval chunk size (m)**: More documents give richer context but increase client memory and prompt length; retrieval quality also matters.

### Failure Signatures
- **Utility drop**: If normalized scores fall toward non‑personalized baseline, check client intervention rate (Figure 7B). A spike suggests τ too low or client model too weak.
- **Privacy leak**: If linkability/attribute inference accuracy approaches the leaky upper bound (≈24%/58.5%), inspect PII filter coverage and examine whether token streams unintentionally encode profile‑specific facts or style.
- **High client latency**: If client token generation share exceeds 15% or per‑token latency increases, verify k (should be 10) and τ (0.05); also check server output quality—misaligned drafts may cause many corrections.
- **Coherence breaks**: If responses become nonsensical after multiple [PII] insertions, consider smoothing the replacement (e.g., retain part of speech) or limiting filter substitutions to non‑critical spans.

## Open Questions the Paper Calls Out
1. **Generalization to other personalized generation tasks**  
   *Basis*: Evaluation restricted to LaMP‑QA (question answering); other tasks like dialogue or summarization are not examined.  
   *Why unresolved*: Personalization mechanisms may behave differently across text genres; P³’s token‑level correction could be more or less effective.  
   *What evidence would resolve*: Apply P³ to diverse benchmarks (e.g., LaMP dialogue, LongLaMP summarization) with comparable privacy attacks and compare utility‑leakage trade‑offs.

2. **Adaptive hyperparameter selection**  
   *Basis*: P³ uses fixed k=10 and τ=0.05; sensitivity analysis shows performance varies but no adaptive method is proposed.  
   *Why unresolved*: Optimal settings likely depend on client model capacity, profile complexity, and network latency; static defaults may underperform in some settings.  
   *What evidence would resolve*: Design and evaluate a dynamic controller that adjusts k and τ in real time based on metrics like token acceptance ratios, latency constraints, and model confidence, testing across various model sizes and network conditions.

3. **Impact of PII detection accuracy**  
   *Basis*: The framework uses a regex‑based PII extractor “for simplicity” and notes that more advanced detectors could be substituted, but the effect on the privacy‑utility balance is not studied.  
   *Why unresolved*: A more precise detector might better protect privacy but could over‑filter, removing useful personal context and degrading utility; the optimal operating point is unknown.  
   *What evidence would resolve*: Replace the regex filter with different PII tools (e.g., Presidio, NER models, commercial APIs) and measure changes in (a) utility scores and (b) privacy attack success rates to identify the best precision‑recall trade‑off.

4. **Robustness against active adversarial servers**  
   *Basis*: The threat model assumes a passive server that follows the standard generation procedure; the server is not considered malicious.  
   *Why unresolved*: A compromised or adversarial server could deliberately generate probing drafts designed to elicit corrective responses that leak more profile information than under the passive threat model, potentially invalidating P³’s privacy guarantees.  
   *What evidence would resolve*: Simulate an adversarial server that optimizes draft tokens to maximize attribute inference success (e.g., prompting about rare profile facts). Compare leakage metrics to the standard P³ setup and analyze whether the framework needs modifications (e.g., stricter filtering, randomized τ) to resist such probing.

## Limitations
- **Undocumented implementation details**: The exact regex patterns for PII extraction, Contriever chunking strategy, and judge model prompts are not fully specified, which may hinder exact replication.
- **Benchmark scope**: Evaluation is limited to the LaMP‑QA benchmark (question answering in three domains). Generalizability to other personalization tasks (dialogue, summarization) or domains remains unproven.
- **Threat model scope**: Privacy evaluation considers only a passive server and explicit PII leakage; it does not account for indirect leakage via stylistic patterns or active probing attacks, which could reveal additional private information.

## Confidence
- **Utility improvement (7.4–9% over baselines)**: High – supported by multi‑dataset statistical significance and clear algorithmic specification.
- **Privacy leakage (1.5–3.5% above query‑only)**: Medium – depends on completeness of PII filtering and attack setup; token‑level leakage from style or facts is not quantified.
- **Client efficiency (9.2% token generation share)**: Medium – directly reported but contingent on server quality and hyperparameter choices; higher intervention rates could increase client load.
