# Leveraging Large Language Models for Automated Scalable Development of Open Scientific Databases

## Quick Facts
- **arXiv ID**: 2603.07050
- **Source URL**: https://arxiv.org/abs/2603.07050
- **Reference count**: 22
- **Primary result**: A scalable, web-based tool that automates scientific literature collection via parallel multi-source querying and zero-shot LLM classification achieves over 90% overlap with small expert-curated databases, with Phi-2 reaching 100% accuracy on some tasks.

## Executive Summary
The paper addresses the time-consuming and error-prone process of manually collecting domain-specific scientific literature. It introduces a scalable web tool that automates this by combining parallel keyword-based queries to multiple academic sources (Scopus, Google Scholar, etc.) with zero-shot text classification using LLMs like Llama2, Gemma-2, and Phi-2. Evaluated on agriculture-related queries, the system achieves high overlap (>90%) with expert-curated datasets, demonstrating significant reduction in manual effort while maintaining domain agnosticism.

## Method Summary
The system aggregates literature from diverse sources through concurrent API calls and web scraping. It then applies a hierarchical deduplication process using identifiers (DOI, Scopus_id) and title matching to unify records. Finally, it filters for relevance using zero-shot LLM classification on article abstracts or titles, guided by a fixed prompt incorporating original keywords. This approach avoids domain-specific fine-tuning, enabling scalable deployment across queries.

## Key Results
- Achieved over 90% overlap with expert-curated databases across multiple agriculture queries.
- Phi-2 model reached 100% accuracy on 3 out of 4 evaluation queries.
- System significantly reduces manual workload in literature collection while being scalable and domain-agnostic.

## Why This Works (Mechanism)
### Mechanism 1: Parallel Multi-Source Retrieval
The system concurrently queries multiple academic databases (Scopus, Web of Science, ScienceDirect via APIs; Google Scholar via scraping) to aggregate a comprehensive initial corpus. This reduces retrieval time and increases coverage by leveraging each source's unique index. Evidence includes implementation details in Section 3.1 and raw article counts (e.g., 77,489 for a multispectral query). Break condition: API unavailability, policy changes, or rate limiting degrade comprehensiveness and speed.

### Mechanism 2: Hierarchical Deduplication
After merging results, records are filtered sequentially: source-specific identifiers (e.g., Scopus_id) remove intra-source duplicates, DOI matching removes cross-source duplicates, and title string matching catches duplicates missed by DOI due to missing/inconsistent entries. Evidence from Section 3.2 shows specific duplicate counts removed (e.g., 496 by Scopus_id, 277 by DOI). Break condition: Title formatting variations (e.g., "N" vs. "Nitrogen") can cause matching failures.

### Mechanism 3: Zero-Shot LLM Classification
Each article's abstract or title is sent to an LLM (Llama2-7b, Gemma-2, Phi-2) with a fixed prompt that includes the original keywords and asks for a binary relevance decision. The prompt may incorporate keyword frequency as a signal. The LLM's response is parsed to assign the label. Core assumption: pre-trained LLMs can generalize to scientific relevance without fine-tuning. Evidence: Section 4.1 reports >90% overlap accuracy, with Phi-2 at 100% on some queries. Break condition: ambiguous keywords, low-quality abstracts, or niche sub-domains not covered in LLM training data reduce accuracy.

## Architecture Onboarding
**Component map**: Flask web frontend → Query Orchestrator → Source Scrapers/API Clients (Scopus, WOS, ScienceDirect, Google Scholar) → Raw Data Aggregator → Deduplication Engine → Language Filter → LLM Classification Service → Result Formatter (CSV export)

**Critical path**: User defines keywords & sources → parallel retrievals → merge & deduplicate → language filter → LLM classification with prompt → parse responses → filter to "relevant" set → CSV download. LLM classification is the main bottleneck.

**Design tradeoffs**: 
- Google Scholar inclusion provides gray literature but requires scraping (risk of IP blocks); defaults to "No".
- Smaller models (Phi-2) chosen for cost/speed vs. potential accuracy gains from larger models; tradeoff evaluated in Table 3.
- Fixed prompt with keyword frequency vs. complex query-specific engineering; simplicity aids scalability but may miss nuanced relevance cues.

**Failure signatures**:
- API client errors or empty result sets in logs.
- Post-deduplication record count shows minimal decrease, indicating failed identifier matching.
- LLM response parsing yields empty/invalid labels for many articles.
- Final "relevant" set size is suspiciously large (overly permissive) or zero (overly restrictive).

**First 3 experiments**:
1. Single-source retrieval sanity check: Query one source (e.g., Scopus) with a simple keyword ("nitrogen") and verify record count and metadata.
2. Deduplication validation: Create a synthetic dataset with known duplicates (same DOI, title variants). Run through deduplication pipeline and verify removal and preservation.
3. LLM classification baseline: Use 20 manually labeled articles (10 relevant, 10 irrelevant) from evaluation set. Run through LLM with standard prompt, calculate accuracy.

## Limitations
- **Domain Generalizability**: Evaluated only on agriculture; effectiveness in other scientific domains (e.g., physics, biomedicine) remains unproven.
- **LLM Zero-Shot Robustness**: Performance may degrade with ambiguous keywords, poor abstracts, or niche sub-domains not covered in LLM training data.
- **Source Reliability & Policy Risk**: Google Scholar scraping is vulnerable to IP blocks and HTML changes; API sources may alter rate limits or terms, breaking parallel retrieval.

## Confidence
- **Parallel Multi-Source Retrieval**: High – Detailed implementation and raw counts provided; mechanism is standard but well-documented.
- **Hierarchical Deduplication**: High – Clear process and quantitative duplicate removal evidence (Table 2).
- **Zero-Shot LLM Classification Effectiveness**: Medium – Strong overlap metrics on agriculture, but generalizability and failure modes not fully stress-tested.

## Next Checks
1. **Cross-Domain Generalization Test**: Run identical queries (e.g., "quantum computing", "maternal health") across 3+ non-agricultural domains. Measure overlap with expert-curated gold standards to quantify accuracy drop-off.
2. **Deduplication Stress Test**: Inject a synthetic dataset of 500 records with known duplicates featuring messy titles (e.g., "N2O emissions" vs. "Nitrous oxide emissions"), missing DOIs, and encoding variants. Report true duplicate recall and false positive rate.
3. **LLM Prompt Robustness Evaluation**: For a fixed query, systematically vary prompt complexity (e.g., add/remove keyword frequency instruction) and input quality (full abstract vs. title-only vs. truncated abstract). Measure accuracy variance to define operational boundaries.
