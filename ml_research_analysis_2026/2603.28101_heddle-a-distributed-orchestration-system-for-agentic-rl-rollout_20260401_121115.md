# Heddle: A Distributed Orchestration System for Agentic RL Rollout
## Quick Facts
- **arXiv ID:** 2603.28101
- **Source URL:** https://arxiv.org/abs/2603.28101
- **Reference count:** 40
- **Primary result:** A trajectory-centric orchestration system that achieves up to 2.5× higher rollout throughput versus SOTA baselines by mitigating long-tail stragglers in agentic RL rollouts.

## Executive Summary
Heddle addresses the performance bottleneck in agentic RL rollouts caused by the long-tail distribution of trajectory lengths. Traditional step-centric scheduling leads to queueing delays, interference, and inflated per-token times for straggling trajectories. The system introduces a trajectory-centric orchestration framework with three synergistic mechanisms: progressive priority scheduling that escalates priority for long-tail trajectories as runtime predictions improve, trajectory-aware placement that segregates trajectories to minimize interference while preserving cache locality, and trajectory-adaptive resource management that dynamically assigns model parallelism to balance latency and throughput. Evaluated across coding, search, and math agents, Heddle significantly improves throughput and reduces tail latency compared to existing baselines like Slime and Verl.

## Method Summary
Heddle rethinks rollout orchestration around complete trajectories rather than individual LLM generation steps. It employs a lightweight predictor to estimate trajectory length after each step, using these estimates to drive a progressive priority scheduler that preempts active requests to immediately execute high-priority (long) trajectories. For placement, trajectories are presorted by predicted length and partitioned via dynamic programming to minimize makespan under an empirically derived interference model; if predictions update, migrations occur asynchronously during tool-call idle periods. A resource manager uses a sort-initialized simulated annealing heuristic to assign heterogeneous model parallelism degrees across workers, aligning high-latency-sensitive long trajectories with low-MP workers and high-throughput short trajectories with high-MP workers. The system is evaluated on multi-node GPU clusters using Qwen models and standard agentic RL datasets.

## Key Results
- Achieves up to 2.5× higher rollout throughput (tokens/s) versus SOTA baselines (Slime, Verl*, Verl).
- Cuts queueing delays by up to 1.26× for long-tail trajectories.
- Effectively neutralizes the straggler effect, improving tail latency (p99 rollout time) across coding, search, and math tasks.

## Why This Works (Mechanism)
### Mechanism 1: Progressive Priority Scheduling (PPS)
- **Claim:** Minimizes cumulative queueing delay for long-tail trajectories by dynamically escalating their priority as runtime prediction accuracy improves.
- **Mechanism:** A lightweight predictor estimates trajectory length after each step; the scheduler orders pending requests by predicted length and preempts lower-priority active requests to execute high-priority (long) trajectories immediately.
- **Core assumption:** Prediction fidelity improves monotonically as trajectory context accumulates during rollout.
- **Evidence anchors:** [abstract] "trajectory-level scheduling using runtime prediction and progressive priority"; [section 4] "progressive trajectory prediction... predictor monotonically refines length estimates" and "progressive priority scheduling (PPS)... reorders the LLM inference requests".
- **Break condition:** If prediction error does not decrease sufficiently after initial steps, priority escalation may misdirect resources, increasing queueing for true stragglers.

### Mechanism 2: Trajectory-Aware Placement with Migration
- **Claim:** Minimizes interference overhead for long-tail trajectories by segregating them from short trajectories while preserving cache locality via presorted dynamic programming and opportunistic migration.
- **Mechanism:** Trajectories are presorted by predicted length; dynamic programming computes an initial partition minimizing group makespan (assuming monotonic interference with group size). At runtime, trajectories are migrated during tool-call idle periods if prediction updates change their rank, using GPU-Direct RDMA for prefix cache transfer.
- **Core assumption:** Interference is a monotonically increasing function of concurrent trajectories per worker; initial placement can be corrected via migration without blocking critical path.
- **Evidence anchors:** [abstract] "trajectory-aware placement via presorted dynamic programming and opportunistic migration during idle tool-call intervals"; [section 5] Lemma 5.1 (contiguous optimal partition) and state transition formula; migration masks overhead by "transmitting data asynchronously during tool-call intervals".
- **Break condition:** If tool-execution intervals are too short to mask migration latency or migration scheduler causes endpoint contention, interference reduction may be offset by added overhead.

### Mechanism 3: Trajectory-Adaptive Resource Management
- **Claim:** Reduces base per-token time for long-tail trajectories while maintaining high throughput for short trajectories by dynamically assigning heterogeneous model parallelism (MP) degrees.
- **Mechanism:** A sort-initialized simulated annealing heuristic optimizes GPU allocation across workers; long-tailed trajectory partitions are mapped to high-MP (low-latency) workers, short trajectories to low-MP (high-throughput) workers.
- **Core assumption:** There exists a latency-throughput trade-off with MP degree; heterogeneous allocation can outperform homogeneous configurations by aligning resource characteristics with trajectory demands.
- **Evidence anchors:** [abstract] "trajectory-adaptive resource manager that dynamically tunes model parallelism"; [section 6] Figure 7 illustrates the trade-off; Algorithm 2 details annealing; Figure 16 shows throughput gains over Fix-1/Fix-8 baselines.
- **Break condition:** If annealing converges to suboptimal allocations due to noisy estimates or workload shifts faster than re-allocation cycles, the latency-throughput balance may degrade.

- **Concept: Agentic RL rollout as multi-step trajectory generation**  
  *Why needed:* Rollout consists of interleaved LLM generation and tool execution; long-tail distribution in trajectory length/tool time causes stragglers.

- **Concept: Model parallelism (MP) and per-token time trade-off**  
  *Why needed:* MP degree affects per-token time; lower MP increases throughput but raises per-token latency for long sequences; Heddle exploits this heterogeneity.  
  *Quick check:* How does increasing model parallelism reduce per-token time, and why might it reduce aggregate throughput?

- **Concept: Interference coefficient in batched LLM execution**  
  *Why needed:* Concurrent trajectories on a worker contend for memory/compute, inflating per-token time (𝛼 > 1); interference grows with batch size.  
  *Quick check:* Why does batching more trajectories on a single worker sometimes increase the per-token time for each trajectory?

  *Why needed:* PPS uses preemption to promote high-priority pending requests over lower-priority active ones, essential for long-tail prioritization.

## Architecture Onboarding
- **Component map:** Scheduler (PPS) -> Router -> Workers; Placement Engine (presorted DP + migration logic) -> Router; Resource Manager (simulated annealing) -> Workers; Tool Manager -> Serverless Backend; Runtime Telemetry -> Control Plane (Scheduler, Placement, Resource Manager)

- **Critical path:**
  1. Trajectory enters; initial prediction runs asynchronously with tool exec.
  2. Scheduler assigns priority; router places on worker per presorted DP result.
  3. Worker executes; after each step, prediction updates; if rank change triggers migration, router schedules KV cache transfer during next tool-call idle.
  4. Resource manager periodically re-runs annealing based on aggregate telemetry; adjusts worker MP configurations.
  5. Tool invocations routed to serverless backend; completion triggers next LLM step.

- **Design tradeoffs:**
  - Preemption vs. cache persistence: Preemption yields low queueing but requires KV cache persistence; frequent preemption increases memory pressure.
  - Migration frequency vs. overhead: More frequent migration adapts to prediction updates but risks saturating RDMA; scheduler prioritizes longest trajectories to maximize impact.
  - Annealing runtime vs. optimality: Longer annealing finds better allocations but increases control-plane latency; aggregation of short trajectories reduces DP input size to speed placement evaluation.

- **Failure signatures:**
  - Straggler persists: Long-tail trajectory's completion time does not improve vs. baseline → prediction failure or migration failure (check telemetry for rank volatility).
  - Throughput collapse: All trajectories slow → interference coefficient 𝛼 too high; likely placement co-located many long trajectories (check partition sizes vs. predicted lengths).
  - Underutilized workers: Some workers idle while others busy → load imbalance; placement DP may use stale predictions or migration not triggering.
  - High control-plane latency: Annealing or DP taking too long → input size n too large before aggregation; adjust short-trajectory threshold.

- **First 3 experiments:**
  1. **Isolate PPS:** Run with fixed placement (e.g., cache-aware) and homogeneous resources; compare queueing delay of top-10% longest trajectories vs. round-robin baseline. Expect reduced queueing, especially after step 2+.
  2. **Validate migration benefit:** Disable migration; force initial placement using first-step predictions only. Measure tail latency (p99 rollout time) and interference factor (proxy: per-token time of longest trajectory in each worker). Expect higher tail latency and interference when predictions are inaccurate.
  3. **Test resource manager:** Compare Heddle's heterogeneous allocation against best homogeneous configuration (found via grid search over MP degrees). Measure throughput and per-token time of long-tail (bottom 20% by length) vs. short (top 50%). Expect trade-off: Heddle improves long-tail per-token time while maintaining short-trajectory throughput.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Can a closed-form analytical model of the interference factor \(F\) replace the current profiler-simulator approach in trajectory-aware placement?
- **Basis in paper:** Section 5.1 states \(F\) lacks a closed-form analytic expression, forcing reliance on a profiler-based simulator, which precludes off-the-shelf solvers and complicates runtime decisions.
- **Why unresolved:** The empirical model may not generalize to diverse hardware architectures or novel interference patterns, limiting portability and optimality guarantees.
- **What evidence would resolve it:** Derivation of an analytical interference model validated across multiple GPU generations and cluster configurations, or demonstration that the simulator's outputs consistently match real-world measurements in heterogeneous settings.

### Open Question 2
- **Question:** How does Heddle's trajectory-centric design scale to large clusters (e.g., thousands of workers) where coordination overheads become non-negligible?
- **Basis in paper:** Evaluation uses a 64-GPU testbed; presorted dynamic programming has \(O(n^2 m)\) complexity and simulated annealing runs periodically, but overheads are only quantified on modest scales.
- **Why unresolved:** Centralized control plane decisions (placement, resource allocation) may become bottlenecks at massive scale, and migration traffic could strain network fabrics, eroding throughput gains.
- **What evidence would resolve it:** Large-scale cluster experiments measuring control plane latency, migration overhead under concurrent transfers, and end-to-end throughput as worker count grows, coupled with scaling analysis of algorithmic complexity.

### Open Question 3
- **Question:** How robust is Heddle's progressive trajectory predictor across diverse agentic domains (e.g., robotics, gaming) with fundamentally different step distributions and tool call patterns?
- **Basis in paper:** Predictor is trained and evaluated on three NLP-heavy tasks (coding, search, math) with token-based length metrics; high intra-group variance due to sampling temperature noted, but no testing on domains with non-textual or discrete state transitions.
- **Why unresolved:** Predictor's reliance on runtime context (LLM generations, tool outputs) assumes textual state representations; domains with non-textual or high-dimensional state spaces may break this assumption, reducing prediction accuracy and undermining scheduling.
- **What evidence would resolve it:** Benchmarking Heddle on varied agentic RL benchmarks (e.g., web navigation, embodied AI, strategy games) with different action/tool semantics, measuring prediction precision and throughput gains against baselines.

### Open Question 4
- **Question:** Does the sort-initialized simulated annealing for resource allocation provide theoretical performance guarantees (e.g., approximation ratios) under dynamic, heterogeneous workload characteristics?
- **Basis in paper:** Section 6.2 acknowledges combinatorial explosion and uses simulated annealing as a heuristic but provides no worst-case analysis or bounds on suboptimality relative to the intractable global optimum.
- **Why unresolved:** Without guarantees, the resource manager may produce allocations arbitrarily far from optimal under certain trajectory length distributions or worker heterogeneity, risking unpredictable production performance.
- **What evidence would resolve it:** Formal analysis of annealing schedule convergence properties, empirical evaluation of optimality gap across synthetic and real workloads, or development of a provably approximate algorithm with bounded performance loss.

### Open Question 5
- **Question:** How does Heddle interact with asynchronous RL training algorithms that impose maximum staleness thresholds—does accelerating stragglers introduce policy divergence or training instability?
- **Basis in paper:** Section 8 briefly mentions compatibility with asynchronous RL but notes staleness thresholds prevent gradient bias; does not evaluate whether dynamic prioritization and migration could cause some trajectories to be significantly newer/older, affecting advantage estimation.
- **Why unresolved:** Prioritizing long-tail trajectories might cause their rollouts to be used in policy updates with higher staleness, potentially violating assumptions of on-policy algorithms (e.g., PPO, GRPO) and harming convergence.
- **What evidence would resolve it:** Training experiments integrating Heddle with asynchronous RL frameworks, measuring policy gradient variance, final task performance, and convergence speed under different staleness thresholds compared to synchronous baselines.

## Limitations
- Prediction fidelity may decay for complex tool interactions, causing misprioritization.
- Migration overhead may not be fully masked if tool-execution intervals are short or network contention occurs.
- Simulated annealing may converge to suboptimal allocations under noisy telemetry or rapidly shifting workloads.
- Baseline hyperparameter tuning (batch size, MP) may be incomparable, potentially inflating reported speedups.
- Implementation is not publicly released; exact algorithm details (cooling schedule, DP pruning) are unspecified.

## Confidence
- Queueing delay reduction (PPS): Medium. Evaluation shows benefit, but dependency on prediction accuracy is a critical vulnerability.
- Interference reduction (placement + migration): Medium-High. DP optimality proof is strong, but migration efficacy depends on measurable tool-call durations.
- Throughput gains (heterogeneous MP): Medium. Trade-off is demonstrated, but annealing’s robustness to dynamic workloads is unproven.
