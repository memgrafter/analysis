# Retrieval Challenges in Low-Resource Public Service Information: A Case Study on Food Pantry Access

## Quick Facts
- **arXiv ID:** 2602.21598  
- **Source URL:** https://arxiv.org/abs/2602.21598  
- **Reference Count:** 9  
- **Primary Result:** A pilot RAG-based conversational system for food pantry information achieved 48% accuracy (23/50 for Llama 3.1 8B, 26/50 for GPT-3.5 Turbo) on community-sourced queries, with key failures in county retrieval, underspecified queries, and eligibility constraints.

## Executive Summary
Fragmented and inconsistent public service data severely hampers access to critical resources like food pantries. This paper presents a retrieval-augmented generation (RAG) pipeline designed to address this issue: it scrapes pantry metadata from the Kansas Food Source website, indexes it with FAISS, and deploys a web interface using Llama 3.1 8B and GPT-3.5 Turbo. On a pilot evaluation of 50 real-world queries, the system achieved moderate accuracy (48% average), but revealed persistent failure modes related to geographical misretrieval, query underspecification, and errors on eligibility rules—all stemming from underlying data quality problems.

## Method Summary
The authors built a conversational retrieval system via a RAG pipeline. First, they scraped pantry metadata from the Kansas Food Source website, a single-state public directory. This data was processed and indexed using FAISS for dense vector similarity search. The system was wrapped in a web interface where user queries were routed to either Llama 3.1 8B or GPT-3.5 Turbo, which generated responses grounded in the retrieved pantry information. No comparative baseline (e.g., keyword search) was reported.

## Key Results
- System accuracy averaged 48%: 46% (23/50) with Llama 3.1 8B, 52% (26/50) with GPT-3.5 Turbo.
- Primary failure modes: incorrect county retrieval, inability to handle underspecified queries, and errors on eligibility constraints due to data inconsistencies.
- Evaluation based on 50 community-sourced queries without statistical scaling or demographic stratification.

## Why This Works (Mechanism)
The RAG approach aims to mitigate LLM hallucination by grounding responses in retrieved, domain-specific documents. In this public service context, retrieval anchors the generation in actual pantry metadata (locations, hours, eligibility), which is otherwise missing from the LLM’s trainingdata. This is essential because static, fragmented public data cannot be fully memorized by generalist models and requires dynamic lookup.

## Foundational Learning
1. **Retrieval-Augmented Generation (RAG)**  
   *Why needed:* To inject up-to-date, structured public service data into LLM responses, bypassing training data cutoffs and hallucinations.  
   *Quick check:* Compare answer accuracy against a pure LLM baseline without retrieval on a held-out query set.

2. **Dense Vector Retrieval (FAISS)**  
   *Why needed:* Enables semantic similarity search over pantry metadata (e.g., matching “free meals near me” to pantry descriptions) where keyword matching fails due to phrasing variation.  
   *Quick check:* Measure recall@k for known relevant pantries across a sample of diverse query phrasings.

3. **Prompt Engineering for Low-Resource Domains**  
   *Why needed:* To guide LLMs in interpreting ambiguous public service queries (e.g., “I need food”) and extract precise constraints (location, eligibility) from noisy retrieved context.  
   *Quick check:* Ablate prompt templates and measure changes in constraint extraction accuracy.

4. **Data Integration from Fragmented Sources**  
   *Why needed:* Public service data is often unstructured and scattered across websites; systematic scraping and normalization is a prerequisite for any retrieval system.  
   *Quick check:* Assess completeness of scraped fields (e.g., zip code, hours) against a manual audit of source pages.

5. **Evaluation in Resource-Constrained Settings**  
   *Why needed:* Standard NLP benchmarks do not reflect the messiness of real-world public service queries (underspecification, dialect variation).  
   *Quick check:* Stratify query set by specificity, geographic granularity, and demographic proxies to expose failure modes.

6. **Ethical & Accessibility Considerations**  
   *Why needed:* Vulnerable populations may have low digital literacy or language barriers; system design must avoid excluding them.  
   *Quick check:* Conduct usability testing with target users, measuring task success and time-to-result.

## Architecture Onboarding
**Component Map:**  
Web Scraper → Data Cleaner/Normalizer → FAISS Index → Query Processor → Retriever (FAISS) → LLM Generator (Llama/GPT) → Response Formatter → Web UI

**Critical Path:**  
User query → Query parsing → FAISS similarity search (top-k pantries) → Context assembly → LLM prompt generation → Response rendering → Display to user.

**Design Tradeoffs:**  
- *Accuracy vs. Latency:* Larger FAISS index or more sophisticated reranking improves relevance but increases response time.  
- *Data Freshness vs. Stability:* Frequent rescraping keeps pantry hours/stock current but may destabilize the index and require re-embedding.  
- *Model Choice:* Llama 3.1 8B (open, low-cost) vs. GPT-3.5 Turbo (proprietary, potentially higher quality) involves tradeoffs in cost, control, and performance consistency.

**Failure Signatures:**  
- County mismatches: Query specifies a county, but retrieved pantries lie outside it.  
- Underspecified queries: No location or eligibility details provided; system returns irrelevant or overly broad results.  
- Eligibility errors: LLM misinterprets nuanced constraints (e.g., “must have children”) due to inconsistent metadata formatting.

**First Experiments:**  
1. Scale evaluation to 500+ diverse queries, stratified by query type and geography, to measure robustness and generalizability.  
2. Construct a gold-standard benchmark dataset of pantry queries with expert-validated answers and provenance.  
3. Implement hybrid retrieval (BM25 + dense embeddings) and quantify impact on county/eligibility error rates versus current dense-only approach.

## Limitations
- Pilot evaluation uses only 50 community-sourced queries, limiting statistical reliability and generalizability across user demographics and query complexities.
- Scraping was restricted to a single state source (Kansas Food Source); findings may not transfer to regions with different data fragmentation patterns or metadata standards.
- Real-world factors like user digital literacy, language barriers, and dynamic pantry availability (hours/stock) were not measured, constraining ecological validity.

## Confidence
- **System Performance Claims (48% avg. accuracy):** Low – based on small, non-random query set; no comparative baseline.
- **Identified Failure Modes (county errors, underspecified queries, eligibility constraints):** Medium – grounded in error inspection of 50 queries, but root causes may be confounded by data sparsity.
- **Fragmented Public Service Data as Primary Bottleneck:** High – aligns with established literature on low-resource information access challenges.

## Next Checks
1. Scale and diversify evaluation: Test the RAG pipeline on a held-out set of 500+ queries stratified by query type, geography, and user demographic proxies.
2. Benchmark data construction: Create and release a standardized, publicly vetted dataset of food pantry queries with gold-standard answers and provenance.
3. Hybrid retrieval ablation: Compare current dense-vector (FAISS) retrieval against hybrid sparse-dense (BM25 + embeddings) or query expansion methods to quantify impact on county/eligibility errors.
