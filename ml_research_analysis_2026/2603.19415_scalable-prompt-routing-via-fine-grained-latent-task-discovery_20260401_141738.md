# Scalable Prompt Routing via Fine-Grained Latent Task Discovery

## Quick Facts
- **ArXiv ID:** 2603.19415  
- **Source URL:** https://arxiv.org/abs/2603.19415  
- **Reference count:** 11  
- **Primary result:** FineRouter achieves a quality score of 0.652, outperforming the best single model (0.621) and the strongest baseline (IPR, 0.646) while incurring less than half the inference cost.

## Executive Summary
Prompt routing for large pools of frontier models with narrow performance gaps is traditionally hindered by manual task taxonomies and monolithic routers that cannot capture subtle model affinities. This work introduces FineRouter, a two-stage method that first automates the discovery of fine-grained latent tasks via graph-based clustering of prompts using both semantic and model-preference signals. Second, it employs a mixture-of-experts router with task-specific quality prediction heads to estimate model performance per discovered task. Evaluated on 10 benchmarks with 11 frontier models, FineRouter achieves superior quality-cost trade-offs, with ablations confirming the contribution of both stages and fine-grained task discovery.

## Method Summary
FineRouter operates in two offline stages followed by online inference. **Stage 1** discovers fine-grained task clusters: for each training prompt, an LLM generates a task description; embeddings of these descriptions are used to build a k-NN graph, whose edges are filtered by Rank Biased Overlap (RBO) on model preference rankings derived from quality scores. Iterative Leiden clustering partitions the graph into task types. For each cluster, a fused model ranking (MRR) selects a small candidate set \(L_i\) achieving coverage threshold \(\delta\). A bi-linear classifier is trained on these cluster assignments. **Stage 2** trains a mixture-of-experts quality estimator: a shared prompt encoder and LLM embeddings drive two adapter sets—general adapters (one per model) and task-specific adapters (one per model in each task’s \(L_i\)). Training proceeds in two phases: first train the base (encoder + general adapters) on all data; then freeze the encoder and fine-tune only task-specific adapters using Stage 1 task labels. At inference, the router aggregates a prompt-specific estimate \(\tilde{Q}_t(p,M)\) from activated adapters with a task-level prior \(\bar{Q}_t(M)\) (cluster median) via \(Q_{\text{final}} = \alpha \cdot \text{norm}(\tilde{Q}_t) + (1-\alpha) \cdot \text{norm}(\bar{Q}_t)\), then selects the model maximizing \(Q_{\text{final}}\).

## Key Results
- FineRouter attains a macro-averaged quality score of **0.652**, surpassing the best single model (0.621) and all baselines (e.g., IPR: 0.646).
- It achieves this at **less than half the cost** of the strongest single model.
- Ablations confirm **gains from both stages** and from **fine-grained tasks** over coarse categories.

## Why This Works (Mechanism)

### Mechanism 1: Fine-Grained Task Discovery via Graph Clustering
Graph-based clustering combines semantic similarity (prompt task descriptions) and model-preference similarity (RBO on model rankings) to identify latent task structures that manual taxonomies miss. This enables adaptive candidate model selection per cluster, filtering the model pool to a small set \(L_i\) that covers high-performers for that task. The core assumption is that prompts with similar semantics and similar model performance patterns belong to the same fine-grained task type. Evidence includes the abstract and Section 3.1.1 detailing graph construction and Leiden clustering; indirect support from prior graph-based routers (e.g., LLMRank, GraphRouter) that do not automate discovery. Break conditions arise if model preference patterns are noisy or reward-model biased, leading to clusters that group semantically similar tasks but with divergent model strengths.

### Mechanism 2: Mixture-of-Experts Router with Specialized Heads
A mixture-of-experts architecture with task-specific quality prediction heads allows specialization for each discovered task while maintaining coverage via general adapters. Task-specific adapters are activated only for a task’s candidate models \(L_i\); general adapters remain active for all others. This hybrid design lets experts learn task-model affinities without interference, assuming these patterns are learnable and consistent. Evidence appears in the abstract and Section 3.2.1 describing adapter architecture and two-phase training; conceptual analogies exist in X-MoE and LAR-MoE but not in LLM routing. Failure occurs if a task cluster is too small/noisy (overfitting) or if \(L_i\) excludes the true best model for some prompts.

### Mechanism 3: Aggregation of Task-Level Priors and Prompt-Specific Estimates
Final routing scores combine a stable task-level prior (cluster median quality \(\bar{Q}_t(M)\)) with a prompt-specific estimate \(\tilde{Q}_t(p,M)\) to balance robustness and adaptability. The prior mitigates noise in prompt-specific predictions, especially for borderline prompts. Evidence is in the abstract and Section 3.3 defining the aggregation (Eq. 5) and showing higher quality for assigned prompts (0.665 vs. 0.619 for "Others"). No direct corpus support. Misassignment by the task classifier or a poorly tuned aggregation weight \(\alpha\) can degrade performance.

## Foundational Learning

- **Quality-Based Routing (Regression)**  
  *Why needed:* Predicting continuous quality scores \(\tilde{Q}(p,M)\) differentiates subtle performance gaps between frontier models, whereas classification (selecting a single best model) is brittle under narrow margins.  
  *Quick check:* Why is regression more suitable than classification when model performances are closely matched?

- **Graph-Based Semi-Supervised Clustering**  
  *Why needed:* Enables discovery of fine-grained task types from unlabeled prompts by fusing semantic and preference similarity without relying on manual taxonomies.  
  *Quick check:* What two signals are combined in the prompt graph, and why is their combination critical for task discovery?

- **Mixture-of-Experts (MoE) with Sparse Activation**  
  *Why needed:* Allows specialized prediction heads per discovered task while keeping total parameters manageable; only a subset of heads (task-specific adapters for \(L_i\)) activate per prompt.  
  *Quick check:* How does activating task-specific adapters only for a task’s candidate models \(L_i\) differ from traditional MoE where all experts are candidates?

## Architecture Onboarding

### Component Map
Offline: Task description generation (LLM) → Prompt embedding → Graph construction (k-NN + RBO) → Leiden clustering → Candidate selection (\(L_i\) via MRR) → Task classifier training → MoE router training (Phase 1: base; Phase 2: task-specific adapters).  
Online: Input prompt → Task classifier → Task assignment \(t(p)\) → Invoke relevant adapters (task-specific for \(L_i\), general for \(M \setminus L_i\)) → Compute \(\tilde{Q}_t(p,M)\) and \(\bar{Q}_t(M)\) → Aggregate \(Q_{\text{final}}\) → Select \(\arg\max_M Q_{\text{final}}\).

### Critical Path
1. Graph clustering produces meaningful, stable task clusters.  
2. Task classifier accurately assigns prompts (macro F1 0.643 reported).  
3. MoE training avoids catastrophic interference between task-specific heads.  
4. Aggregation weight \(\alpha\) is properly validated.

### Design Tradeoffs
- *Graph hyperparameters*: \(k\), \(\tau\), \(\delta\), \(\ell\) control granularity vs. stability; higher \(\ell\) may overfit, extreme \(\delta\) hurts coverage or introduces noise.  
- *MoE specialization*: More tasks increase memory (more heads) but improve specialization; \(L_i\) size trades coverage vs. noise.  
- *Aggregation*: \(\alpha=0.5\) used in paper; higher \(\alpha\) trusts prompt-specific estimates more but may amplify noise.

### Failure Signatures
- Low task classifier F1 (<0.5) → misrouting, poor Stage 1 prior.  
- Clusters with <5 prompts or extreme candidate overlap → unreliable task definitions.  
- Stage 2 only performing worse than Stage 1 only → task-specific heads not learning.  
- Routing cost curve not dominating baselines → flawed aggregation or candidate selection.

### First 3 Experiments
1. **Cluster validation:** Manually inspect top discovered tasks for semantic coherence and plausible candidate models; check if fine-grained splits align with known model strengths.  
2. **Baseline replication:** Reproduce kNN, IPR, and coarse-CLS on same train/test split; verify quality gap (FineRouter ~0.652 vs. IPR 0.646).  
3. **Aggregation weight sweep:** Grid search \(\alpha \in [0,1]\) on dev set; expect peak near 0.5. Monotonic drop from \(\alpha=0\) to \(\alpha=1\) indicates one stage dominates and the other adds noise.

## Open Questions the Paper Calls Out

1. **Sensitivity to LLM and reward model choices:** How do different LLMs for task description generation or different reward models for quality supervision affect the discovered latent task structure and routing performance? The paper acknowledges reliance on Claude-Sonnet-4.5 and Skywork-Reward-V2 but provides no sensitivity analysis.

2. **Hyperparameter adaptability:** Can graph clustering hyperparameters (e.g., \(k\), \(\tau\), \(\delta\), \(\ell\)) be tuned automatically for new domains or model pools to maintain portability? The paper notes these were tuned on training data and may vary elsewhere.

3. **Training data efficiency:** Is it feasible to reduce the need for responses from all candidate models on training data (e.g., via partial responses, proxy models, or synthetic scores) without significant routing degradation? The paper cites this as a limitation for real-world deployment.

4. **Multimodal extension:** How can the method handle multimodal inputs (e.g., image-text prompts) where task structure may emerge from cross-modal features rather than text semantics? The paper explicitly states current text-only limitation.

5. **Scalability to large model pools:** How does performance and computational cost scale as the candidate pool grows from dozens to hundreds of models? Clustering complexity and MoE head management may become prohibitive; the paper only experiments with 11 models.

## Limitations

- **Hyperparameter sensitivity:** Graph construction and clustering parameters (\(k\), \(\tau\), \(\delta\), \(\ell\), Leiden resolution) are not fully specified; cluster granularity may be arbitrary and require manual tuning.
- **Incomplete training details:** Stage 2 lacks critical specifics (optimizer, LR schedules, dropout, exact epoch counts), and the two-phase procedure risks instability or forgetting.
- **Quality oracle bias:** The reward model (`SKYWORK-REWARD-V2-LLAMA-3.1-8B`) may have inherent biases; no human preference validation is provided.
- **Scalability claims untested:** The method is evaluated on only 11 models; behavior with dozens or hundreds of candidates remains speculative.

## Next Checks

1. **Hyperparameter stability:** Vary graph parameters (\(k \in [3,10]\), \(\tau \in [0.3,0.6]\), \(\delta \in [0.7,0.9]\)) on a validation set; measure cluster NMI and final quality deviation to identify robust ranges.
2. **Aggregation weight sweep:** Grid search \(\alpha \in [0,1]\) on a held-out dev set; report performance curve and optimal value to verify the chosen \(\alpha=0.5\) is not arbitrary.
3. **Classifier robustness:** Evaluate task classifier on out-of-distribution prompts (e.g., new domains); if macro F1 drops below 0.5, implement a confidence-threshold fallback to the "others" cluster to prevent misrouting.
