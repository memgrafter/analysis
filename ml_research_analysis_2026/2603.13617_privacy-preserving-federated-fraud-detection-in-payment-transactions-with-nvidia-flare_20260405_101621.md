# Privacy-Preserving Federated Fraud Detection in Payment Transactions with NVIDIA FLARE

## Quick Facts
- **arXiv ID:** 2603.13617
- **Source URL:** https://arxiv.org/abs/2603.13617
- **Reference count:** 19
- **Primary result:** Federated learning with FedAvg achieved mean F1-score 0.903, nearing centralized performance (0.925) and far surpassing local models (0.643), while DP-SGD (ε<10) maintained strong utility (F1=0.879 at ε=10.0).

## Executive Summary
This paper explores federated learning (FL) for cross-bank payment fraud detection, leveraging NVIDIA FLARE and FedAvg. Using a synthetic non-IID dataset that simulates five heterogeneous banks, the federated model significantly outperforms locally trained models (F1 0.903 vs 0.643) and approaches the centralized upper bound (0.925). Convergence occurs within 10 rounds. Model interpretability via Shapley values confirms reliance on domain-relevant features. Incorporating sample-level differential privacy (DP-SGD) yields formal privacy budgets below ε=10.0 with moderate F1 degradation (0.879 at ε=10.0), demonstrating a feasible privacy-utility trade-off for regulated environments. The study highlights FL’s potential for secure multi-institutional collaboration in fraud detection.

## Method Summary
The authors implement a federated learning pipeline across five synthetic banks, each with distinct fraud type distributions and feature statistics. A three-layer fully connected neural network (64-32-16 units, LayerNorm, ReLU) trained with FocalLoss forms the local model. FedAvg orchestrates aggregation over 20 communication rounds (100 for DP experiments), with local epochs=1, batch size=64, and learning rate 5e-4. Data preprocessing includes log-transform of temporal gaps, Haversine distance calculation, one-hot account type encoding, and per-client StandardScaler normalization. DP-SGD is integrated via Opacus, using per-sample gradient clipping (C=1.0) and Gaussian noise to achieve target ε values. The system is built on NVIDIA FLARE’s Scatter-Gather workflow, with MLFlow for experiment tracking. Baselines include centralized training and local-only models using identical architectures. Performance is assessed primarily by binary F1-score, supplemented by Accuracy, Precision, Recall, and AUPRC; Shapley values (Captum GradientShap) provide interpretability.

## Key Results
- **Federated advantage:** FedAvg global model achieves mean F1-score 0.903 across clients, substantially beating local-only (0.643) and nearing centralized (0.925).
- **Rapid convergence:** Strong performance is reached within 10 communication rounds.
- **Privacy-utility trade-off:** With DP-SGD at ε=10.0, F1-score modestly degrades to 0.879 while providing formal privacy; at ε=1.0, utility drops further but remains viable.
- **Interpretability:** Shapley analysis confirms the model relies on expected fraud indicators (e.g., transaction amount, geospatial distance, activity counts).

## Why This Works (Mechanism)
FedAvg succeeds because it aggregates gradient updates from diverse banks, enabling the global model to learn a broad representation of fraud patterns without data leaving each institution. The non-IID nature (each bank sees only a subset of fraud types) means local models are biased; averaging smooths these biases and yields a model that generalizes across all sites. The DNN architecture, with continuous parameters and smooth loss landscape, is inherently compatible with weight averaging. DP-SGD protects individual transaction privacy by clipping per-sample gradients and adding calibrated noise, with the privacy budget ε controlled by noise scale and composition over rounds. NVIDIA FLARE provides a secure, scalable orchestration layer that handles network communication, job scheduling, and fault tolerance, while MLFlow ensures reproducible tracking. Together, these components deliver a practical system for privacy-preserving cross-institutional learning in regulated domains.

## Foundational Learning
- **Federated Averaging (FedAvg):** Why needed? To combine insights from multiple parties without data sharing. Quick check: Verify that global F1 improves monotonically with rounds and surpasses local baselines.
- **Differential Privacy (DP-SGD):** Why needed? To provide mathematical guarantees against membership inference, meeting regulatory standards. Quick check: Ensure per-sample gradient clipping and noise addition; confirm final ε via Opacus logs.
- **Non-IID Data Simulation:** Why needed? Real banks have heterogeneous fraud distributions; modeling this tests FL’s value. Quick check: Compute per-client local F1 scores; large variance (e.g., >0.2 range) confirms skew.
- **Shapley Values:** Why needed? To attribute predictions to features, fostering trust and compliance. Quick check: Top features should align with domain knowledge (e.g., transaction amount, location).
- **Focal Loss:** Why needed? To address class imbalance (fraud rare) by focusing on hard misclassified examples. Quick check: Compare recall on fraud class with and without focal loss; expect improvement.

## Architecture Onboarding
**Component map:** Synthetic Data Generator -> Client: Preprocessing (feature engineering, scaling) -> Local DNN Training (FocalLoss) -> Gradient Computation (with optional DP-SGD) -> Server: FedAvg Aggregation -> Global Model -> Evaluation (F1, Shapley). Orchestrated by NVIDIA FLARE (Scatter-Gather). Tracking via MLFlow.

**Critical path:** Each FL round: Server broadcasts current global model to all clients → Clients perform local training (E=1 epoch) → Clients send weighted gradient updates to server → Server computes weighted average to update global model → Repeat until convergence (20-100 rounds) → Final global model evaluated on each client’s test set.

**Design tradeoffs:**
- **FedAvg vs. advanced FL:** Chose FedAvg for simplicity and compatibility; while FedProx/FedOpt may handle severe heterogeneity better, FedAvg sufficed for moderate non-IID.
- **DP-SGD:** Adds noise to gradient updates to ensure privacy; higher noise reduces utility but lowers ε. Target ε=10.0 balances feasibility and compliance.
- **Synthetic data:** Provides controlled, reproducible experiments but may not capture real-world complexities like adversarial fraud evolution.
- **DNN over tree models:** DNNs support gradient-based weight averaging directly, while tree ensembles require more complex aggregation; however, trees often excel on tabular data, so this trade-off merits further study.

**Failure signatures:**
- **Federated gain absent:** If global F1 ≈ local F1, heterogeneity may be insufficient or aggregation flawed.
- **DP budget overshoot:** Final ε > target indicates incorrect noise scaling or composition accounting.
- **Training divergence:** Sudden loss spikes may indicate too-high learning rate, inadequate clipping, or data leakage.
- **Feature mismatch:** Inconsistent preprocessing leads to shape errors; ensure all clients use same feature set and scaling.

**First three experiments:**
1. **Baseline FL run:** Train without DP for 20 rounds; expect global F1 >0.9 and convergence by round 10. Compare to local and centralized baselines.
2. **DP verification:** Run with ε=10.0 and ε=1.0; capture Opacus-reported ε and F1; confirm ε ≤ target and F1 drop matches expectations (≈0.879 at ε=10.0).
3. **Interpretability check:** Compute Shapley values on the final global model; verify top features correspond to known fraud signals (e.g., high transaction amount, unusual distance) and are stable across random seeds.

## Open Questions the Paper Calls Out
1. **Synthetic-to-real generalization:** How does the FL framework perform on real-world multi-bank data with adversarial adaptation and concept drift? The paper used synthetic data with rule-based fraud injection, which lacks these complexities.
2. **Severe client heterogeneity:** What is the impact of highly asymmetric data volumes and overlapping/incomplete fraud typologies on FedAvg compared to FedProx or FedOpt? The current experiments used equal volumes and clean fraud-type partitions.
3. **Malicious participant robustness:** How robust is the federated model to model poisoning or gradient inversion attacks, especially under DP? The study assumed honest participants only.
4. **Operational cost-benefit of DP:** Beyond F1-score, how does DP affect false positive rates, alert volumes, and investigator workload in a live system? A small F1 drop may have outsized operational impact.
5. **DNN vs. tree-based models:** Does the superiority of DNNs for FedAvg hold when features are extremely heterogeneous or when using tabular data with sparse categorical variables? The paper’s preference for DNNs was not empirically compared against federated tree ensembles.

## Limitations
- **Synthetic data generation details missing:** Exact hyperparameters (e.g., log-normal means, fraud injection fractions) are unreported, hindering exact replication of the non-IID dataset.
- **DP-SGD configuration incomplete:** The noise multiplier σ selected for target ε values and precise composition accounting over 100 rounds are not disclosed, preventing verification of privacy guarantees.
- **Assumptions of honest, moderately heterogeneous clients:** The evaluation assumes no malicious participants and only moderate heterogeneity; real-world scenarios may be more challenging.

## Confidence
- **Federated model substantially outperforms local models:** Medium (result depends on unreported data generation specifics).
- **Convergence to near-centralized performance:** Medium (contingent on exact data distribution).
- **DP-SGD provides formal privacy with moderate utility loss:** Low (lack of DP hyperparameters prevents independent validation).
- **Shapley interpretability confirms domain-relevant features:** High (method fully specified and reproducible).
