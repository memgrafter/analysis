# mind_call: A Dataset for Mental Health Function Calling with Large Language Models

## Quick Facts
- **arXiv ID:** 2601.06937
- **Source URL:** https://arxiv.org/abs/2601.06937
- **Reference Count:** 13
- **Primary Result:** Introduces `mind_call`, a synthetic dataset mapping diverse mental health queries to structured wearable sensor API calls, including reasoning steps and normalized temporal parameters, to support intent grounding and function invocation research.

## Executive Summary
This paper presents `mind_call`, a novel synthetic dataset designed to bridge a critical gap in applying large language models (LLMs) to mental health assistance. The dataset systematically pairs natural language user queries—spanning explicit, implicit, behavioral, symptom-based, and metaphorical expressions—with structured API calls for retrieving wearable sensor data. Each sample includes an intermediate reasoning annotation ("thinking") and a normalized temporal parameter (`numdays`). The authors generate the data via a controlled multi-stage LLM pipeline and conduct exploratory analysis to validate linguistic diversity and mental health terminology coverage. The public release of `mind_call` aims to foster research on reliable intent grounding, temporal reasoning, and tool invocation in safety-critical mental health agents.

## Method Summary
The dataset is generated synthetically using a multi-stage LLM pipeline. Structured prompts guide the generation process, specifying a target function from a predefined health schema, the query category (e.g., implicit, metaphorical), explicit reasoning rules, and temporal normalization constraints. This setup enforces semantic and functional accuracy while encouraging linguistic variation. Post-processing removes duplicates and validates structural consistency against the schema. The final samples consist of a user query, its category, a step-by-step reasoning trace ("thinking"), a normalized `numdays` value, and the corresponding target function name. The design focuses on single-function invocation with a simplified temporal output space.

## Key Results
- A publicly available dataset (`mind_call`) with diverse query types mapped to a standardized wearable data retrieval API, including explicit reasoning annotations for each sample.
- Exploratory data analysis confirms balanced distribution across query categories (explicit, implicit, behavioral, symptom-based, metaphorical) and realistic coverage of mental health terminology and emotional context.
- The dataset's structure—incorporating intermediate reasoning and normalized time—supports research into interpretable and temporally-aware function calling for LLM-based mental health agents.

## Why This Works (Mechanism)

### Mechanism 1
**Claim:** Synthetic dataset generation with controlled prompt engineering can produce diverse, realistic mental health queries mapped to structured API calls.  
**Mechanism:** A multi-stage LLM pipeline uses structured prompts specifying target function, query category, reasoning rules, and temporal normalization to generate samples. Post-processing enforces consistency and removes duplicates, maintaining schema fidelity while increasing linguistic diversity.  
**Core assumption:** LLM generators, guided by precise prompts and a standardized schema, can create semantically varied yet functionally accurate query-label pairs.  
**Evidence anchors:**  
- [abstract] Dataset maps diverse natural language queries to standardized API calls, covering multiple expression types.  
- [section 8] Pipeline mitigates stylistic bias through controlled multi-stage generation.  
- [corpus] Low citation counts for neighboring tool-calling papers indicate novelty but limited external validation.  
**Break condition:** If prompts fail to elicit nuanced mental health language (e.g., queries remain generic), the dataset may not support robust intent grounding.

### Mechanism 2
**Claim:** Including an explicit intermediate reasoning step ("thinking" annotation) improves model interpretability and may enhance accuracy in function selection and temporal normalization.  
**Mechanism:** Each sample provides a natural language rationale decomposing the query into intent interpretation, function justification, and temporal constraint resolution, creating supervised chain-of-thought that guides the model toward the correct `(f, t)` pair.  
**Core assumption:** Exposing the reasoning process during training encourages step-by-step inference, reducing errors from ambiguous queries.  
**Evidence anchors:**  
- [abstract] Reasoning step supports research on intent grounding and temporal reasoning.  
- [section 7] The `thinking` annotation makes the decision process explicit and grounds temporal normalization.  
- [section 7] References chain-of-thought literature as prior support.  
**Break condition:** If reasoning annotations are inconsistent or fail to capture necessary inference paths, they may introduce misleading supervision.

### Mechanism 3
**Claim:** Normalizing all temporal expressions to a numeric `numdays` parameter creates a consistent, executable interface for wearable data retrieval despite varied natural language time references.  
**Mechanism:** A deterministic mapping converts explicit, relative, and vague temporal phrases into a single integer argument, with a default of 7 days when unspecified.  
**Core assumption:** A normalized temporal argument is sufficient for the target functions and that a default is acceptable for underspecified queries.  
**Evidence anchors:**  
- [section 2] Task definition includes normalized temporal parameter space `T`.  
- [section 6.1.3] All temporal expressions are normalized to `numdays` with a 7-day default.  
- [corpus] No neighboring papers directly address temporal normalization for mental health wearables, indicating novelty but unproven efficacy.  
**Break condition:** If real queries require complex temporal logic (e.g., specific dates, recurring intervals) that `numdays` cannot express, critical information is lost.

## Foundational Learning
- **Concept: Mental Health Query Taxonomy** (explicit, implicit, behavioral, symptom-based, metaphorical)  
  **Why needed here:** The model must classify the user's intent category to apply the correct reasoning pattern and disambiguate function targets, as categories imply different levels of directness and inference.  
  **Quick check:** Given "I haven't been sleeping well," is this symptom-based or behavioral, and what primary function would it map to?

- **Concept: Wearable Sensor Data Schema**  
  **Why needed here:** The model must know the predefined function set `F` (e.g., `get_sleep_data`) and their physiological domains to select the correct API call.  
  **Quick check:** If a user mentions "palpitations," which function category (cardiovascular, stress, etc.) is most relevant?

- **Concept: Temporal Normalization Rules**  
  **Why needed here:** The model must convert arbitrary natural language time references into the exact numeric `numdays` argument expected by the API, handling defaults and conversions.  
  **Quick check:** How would you normalize "over the last three weeks" and "since Monday" into `numdays`, and what assumptions are made?

## Architecture Onboarding
- **Component map:** Query Parser & Classifier -> Reasoning Generator -> Function Selector -> Temporal Resolver -> API Call Formatter  
- **Critical path:** Query Parser & Classifier → Reasoning Generator → Function Selector → Temporal Resolver → API Call Formatter. The reasoning step is inserted between parsing and selection to enforce interpretability.  
- **Design tradeoffs:**  
  - *Synthetic vs. Real Data:* Ensures label quality and diversity but may lack noise and edge cases of genuine queries.  
  - *Single-function vs. Multi-function:* Current design limits to one function per query for simplicity, but real assessments may require concurrent multi-sensor data.  
  - *Normalized Time vs. Rich Time:* `numdays` simplifies execution but discards specificity (e.g., exact dates, weekday vs. weekend).  
- **Failure signatures:**  
  - **Incorrect Function Mapping:** Selecting a function domain misaligned with query keywords (e.g., mapping "anxiety" to `get_nutrition_data`).  
  - **Temporal Mis-normalization:** Converting "last month" to `numdays=30` when user meant "previous calendar month."  
  - **Reasoning-Output Divergence:** `thinking` justifies `get_sleep_data`, but final call is `get_activity_data`.  
- **First 3 experiments:**  
  1. **Zero-shot Category Accuracy:** Evaluate if a pre-trained LLM correctly classifies query types without fine-tuning on a held-out subset.  
  2. **Temporal Normalization Stress Test:** Probe ambiguous/culturally specific time phrases (e.g., "the weekend," "a fortnight") to measure resolver robustness.  
  3. **Reasoning Consistency Check:** Use an LLM-as-a-judge to score alignment between `thinking` annotations and ground-truth `(f, t)` pairs for annotation noise.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can the mind_call dataset be systematically extended to support multi-function workflows and longitudinal interactions for more realistic mental health agent planning?  
- **Basis in paper:** The limitations section states the dataset "focuses on single-function invocation" and "does not model multi-step planning or longitudinal interaction."  
- **Why unresolved:** Real-world mental health support often requires chaining multiple data retrievals or reasoning across time, which is not represented.  
- **What evidence would resolve it:** New dataset samples with sequential/dependent function calls; benchmark evaluations measuring multi-step planning accuracy; user studies with professionals defining required scenarios.

### Open Question 2
- **Question:** What methodologies are most effective for adapting mind_call to multilingual and cross-cultural contexts to ensure global applicability in mental health assistance?  
- **Basis in paper:** Ethical and EDI considerations note the dataset "is limited to English and does not capture cultural variation" and that "future extensions should address multilingual and cross-cultural representation."  
- **Why unresolved:** Mental health language and symptom expression vary significantly across cultures and languages; without adaptation, models may fail in non-English settings.  
- **What evidence would resolve it:** Development of parallel corpora in target languages via translation with cultural validation; analysis of cultural idioms; performance comparison across diverse linguistic groups.

### Open Question 3
- **Question:** To what extent do the synthetic queries in mind_call capture the linguistic variability, ambiguity, and emotional nuance of authentic user utterances in mental health contexts?  
- **Basis in paper:** The dataset is entirely synthetically generated, but no validation against real user data is presented; EDA analyzes term frequencies but cannot confirm ecological validity.  
- **Why unresolved:** Synthetic generation may miss spontaneous expressions, colloquialisms, or complex emotional states found in real conversations, limiting generalizability.  
- **What evidence would resolve it:** Human evaluation comparing synthetic vs. real queries (e.g., from therapy transcripts) on realism and diversity; error analysis of models on authentic user logs; correlation studies between synthetic and real distributions.

### Open Question 4
- **Question:** Does the inclusion of explicit reasoning annotations ("thinking" steps) measurably improve the accuracy, robustness, and interpretability of LLM function calling for mental health queries?  
- **Basis in paper:** The dataset includes structured reasoning inspired by chain-of-thought, but no experiments isolate its impact; benefits are posited but untested.  
- **Why unresolved:** Reasoning is hypothesized to aid interpretability and temporal grounding, but its actual contribution on this task remains unevaluated.  
- **What evidence would resolve it:** Controlled experiments comparing models trained with/without reasoning annotations; metrics on call accuracy, temporal errors, and human-rated interpretability; ablation studies on reasoning design.

## Limitations
- **Reproducibility Blockers:** Exact LLM generation prompts, hyperparameters (temperature, model versions), and the complete finalized function schema are undisclosed, preventing exact reconstruction.
- **Synthetic Data Validity:** The assumption that LLM-generated queries fully capture the nuance, noise, and emotional complexity of real user expressions remains untested.
- **Temporal Simplification Risk:** The single `numdays` parameter may be insufficient for queries needing date-specific ranges or comparative periods.
- **Annotation Quality:** The quality and consistency of the `thinking` reasoning steps are not quantified; potential bias could misguide model learning.

## Confidence
- **Cluster 1 (Dataset as a Resource):** **Medium.** The dataset is available and shows internal balance, but real-world robustness is unproven.
- **Cluster 2 (Reasoning Annotation Utility):** **Medium.** Design is grounded in chain-of-thought literature, but no experiments validate performance impact.
- **Cluster 3 (Temporal Normalization Design):** **Medium.** Mechanism is clear, but sufficiency for the full spectrum of temporal expressions is an open question.

## Next Checks
1. **Prompt Reconstruction Audit:** Reverse-engineer generation prompts from `(query, thinking, function)` triples. Generate new samples and compare diversity/validity to the original dataset.
2. **Temporal Generalization Probe:** Curate a held-out set of 200 queries with complex/ambiguous time phrases (e.g., "a fortnight," "first week of spring"). Evaluate a model fine-tuned on `mind_call` for `numdays` normalization accuracy against a human-annotated gold standard.
3. **Reasoning-Output Alignment Test:** For 500 random samples, use an LLM-as-a-judge to score whether the provided `thinking` step logically necessitates the ground-truth `(f, t)` pair. A low score indicates annotation noise or weak supervision.
