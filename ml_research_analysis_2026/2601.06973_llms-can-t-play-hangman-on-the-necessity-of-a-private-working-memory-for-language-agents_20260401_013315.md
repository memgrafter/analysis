# LLMs Can't Play Hangman: On the Necessity of a Private Working Memory for Language Agents

## Quick Facts
- **arXiv ID:** 2601.06973
- **Source URL:** https://arxiv.org/abs/2601.06973
- **Reference count:** 40
- **Primary result:** Standard LLMs fail at tasks requiring hidden state (0-14% self-consistency), but agents with an explicit, injectable private working memory achieve up to 100% self-consistency on Hangman and Diagnosis tasks.

## Executive Summary
Standard chat-based LLMs and retrieval-augmented agents fail at Private State Interactive Tasks (PSITs) like Hangman because their architecture lacks a persistent, hidden mechanism to maintain state across turns—an impossibility theorem proves that without a private memory module, any agent based on a stateless LLM cannot reliably preserve secrets. The proposed solution is an architecture with an explicit, structured private working memory (a text block with Facts/Knowledge, Plans, and Scratchpad sections) that is updated each turn via dedicated tools (e.g., Overwrite, Append/Delete, Patch). This design restores the ability to store and act on hidden information. Empirical evaluations using a self-consistency fork test show baseline agents score near 0–14%, while the proposed Workflow agents achieve near-perfect self-consistency (e.g., 100% for Qwen3-235B on Hangman), all while using ~10x fewer tokens than Private Chain-of-Thought.

## Method Summary
The study evaluates agents on two PSITs: Hangman (agent hosts, chooses a secret word, reveals letter positions) and a Diagnosis Simulator (agent is a patient hiding a medical condition, answers symptom questions). The core evaluation is a **self-consistency fork test**: after 4 turns, the dialogue is forked with 5 candidate secrets (the true one plus four plausibles). The agent must affirm the true secret and reject others. Baselines include Vanilla LLMs, retrieval-augmented agents (Mem0, A-Mem, LightMem, MemoryOS), and Private CoT. The proposed solution are two architectures: (1) an **Autonomous agent** with memory-update tools called each turn, and (2) a **Workflow agent** with separate response and memory-update nodes. The private memory is a structured text block injected via `<private_state>` tags, updated via Overwrite, Append/Delete, or Patch operations. Experiments run with GPT-OSS (20B/120B) and Qwen3 (32B/235B) models over 50 episodes, measuring self-consistency accuracy and token efficiency.

## Key Results
- Baselines (Vanilla LLM, retrieval agents) score 0–14% self-consistency on PSITs.
- Proposed Workflow agents achieve up to 100% self-consistency (Qwen3-235B on Hangman).
- Private working memory uses ~10x fewer tokens than Private CoT while restoring hidden state capability.

## Why This Works (Mechanism)
The core limitation of standard LLMs is their **statelessness**: each turn is processed independently, so any hidden state must be explicitly maintained in the context. In PSITs, the secret must be hidden from the public dialogue but remembered by the agent. The proposed **private working memory** solves this by decoupling the agent's internal state from the public conversation. It is a structured block (Facts/Knowledge, Plans, Scratchpad) that is:
1. **Injectable**: inserted into the system prompt each turn, invisible to the user.
2. **Updatable via tools**: the agent chooses deterministic operations (Overwrite, Append/Delete, Patch) to modify the memory, ensuring consistency.
3. **Self-consistent by design**: the fork test verifies that the memory reliably stores the true secret and that the agent's verification logic is based on that stored state, not on pattern-matching or guesswork. This architecture provides the persistent, hidden register that standard LLMs lack, making PSITs tractable.

## Foundational Learning
- **Private State Interactive Tasks (PSITs)**: Games/dialogues requiring hidden state (e.g., Hangman's secret word). *Why needed*: They expose the fundamental inability of stateless LLMs to maintain secrets. *Quick check*: Can your agent play Hangman without ever leaking the secret word in public dialogue?
- **Self-consistency fork test**: Forking a dialogue at a fixed turn to probe whether the agent consistently remembers the true hidden state across parallel branches. *Why needed*: Provides a rigorous, automated measure of private state maintenance. *Quick check*: After forking, does the agent answer "yes" only to the true secret and "no" to all others?
- **Structured private memory**: A multi-section text block (Facts/Knowledge, Plans, Scratchpad) injected into the prompt. *Why needed*: Organizes hidden information for reliable retrieval and update. *Quick check*: Is the secret explicitly stored in the Facts section, ideally marked with `<secret>` tags, before the fork?
- **Memory update tools (Overwrite, Append/Delete, Patch)**: Deterministic operations that modify the private memory. *Why needed*: Prevents corruption by avoiding free-form LLM generation of the memory. *Quick check*: Are these tools invoked with precise arguments, and does the memory after each turn remain syntactically valid?
- **Impossibility theorem**: A formal proof that any agent without a private memory module cannot solve PSITs with perfect consistency. *Why needed*: Establishes the architectural necessity of the proposal. *Quick check*: Does the theorem assume the agent's public utterances are fully observable by the user/opponent?

## Architecture Onboarding
**Component map (plain text flow):**
Player (rule-based) -> Public Dialogue (utterances) + Agent (LLM + tools) -> Private Memory (structured block) -> Agent Decision/Response. Fork test: at turn 4, Public Dialogue + Private Memory -> Candidate Set (5 secrets) -> Verification Query -> Agent Response (yes/no). Workflow variant: separate nodes for Response Generation and Memory Update, with explicit state transition.

**Critical path:** The defining loop is: (1) receive player utterance, (2) inject current private memory, (3) generate response and tool calls, (4) apply tool updates to private memory. The fork test interrupts this at step 2 to inject candidate secrets and probe consistency.

**Design tradeoffs:**
- **Token efficiency vs. expressivity**: Structured memory is cheap but requires careful schema design; Private CoT is expressive but token-heavy.
- **Autonomy vs. control**: Autonomous agents choose tools freely (flexible but riskier) vs. Workflow agents follow a fixed two-step graph (more predictable).
- **Deterministic updates vs. LLM flexibility**: Tool-based updates ensure consistency but constrain how memory evolves; free-form generation is riskier but might discover better organization.

**Failure signatures:**
- **Leakage**: Secret appears in public dialogue before fork → indicates memory not used or agent ignoring it.
- **Over-Confirmation**: Agent says "yes" to multiple candidates → verification prompt not strictly followed or memory corrupted.
- **State Substitution**: Agent latches onto a plausible but false secret → memory update lost true secret or candidate set mismatched.
- **All Denial**: Agent rejects all candidates → memory missing secret or verification logic too strict.

**First 3 experiments:**
1. **Memory content audit**: At turn 4 (fork), extract the `<private_state>` block. Verify the true secret is explicitly stored in Facts/Knowledge, ideally marked with `<secret>` tags. If absent, revise prompts/tool usage to force storage.
2. **Baseline leakage test**: For retrieval-augmented agents, inspect retrieved chunks before the fork. Confirm the secret was never present in the player's public utterances. If found, the player policy may leak; enforce strict non-revelation.
3. **Alternative model test**: Replicate with an open-weight model having robust tool-use (e.g., Llama-3.1-405B-Instruct). Check if the performance gap between baselines and private-memory agents persists, ruling out proprietary model quirks.

## Limitations
- **Implementation ambiguity**: Player policies, candidate generation fallback, and LangGraph state machine for Workflow agents are underspecified; subtle differences may affect reproducibility.
- **Model-specific dependencies**: Exact GPT-OSS and Qwen3 checkpoints, tokenizers, and whether reasoning variants were used are undisclosed, making exact replication difficult.
- **Evaluation fragility**: The fork test's rigidity (fork at turn 4, candidate set construction) may not generalize to all PSITs or dialogue lengths.

## Confidence
- **Architectural necessity (impossibility theorem)**: **High** – logical argument independent of implementation.
- **Empirical results (self-consistency scores)**: **Medium** – depends on faithful reproduction of ambiguous details (prompts, update rules, player policies).
- **Token efficiency vs. Private CoT**: **High** – directly measurable if memory size is logged correctly.
