# AIDABench: AI Data Analytics Benchmark

## Quick Facts
- **ArXiv ID:** 2603.15636  
- **Source URL:** https://arxiv.org/abs/2603.15636  
- **Reference count:** 40  
- **Primary result:** State-of-the-art models achieve at most 59.43% overall pass@1; file generation is the hardest category with best pass@1 of 49.43%.

## Executive Summary
AIDABench introduces a comprehensive end‑to‑end evaluation suite for AI‑driven document analysis. It includes over 600 tasks spanning question answering, data visualization, and file generation, using heterogeneous data sources such as spreadsheets, reports, and databases. Tasks are stratified by difficulty and 27.4% require reasoning across multiple files, mirroring real‑world analytical workflows.  

Evaluation of 11 state‑of‑the‑art models reveals that even the best model (Claude Sonnet 4.5) attains only 59.43% pass@1, with file generation being the most challenging at 49.43%. These results highlight that complex, multi‑step analytics remain an unsolved problem. AIDABench is publicly released to standardize progress assessment.

## Method Summary
AIDABench constructs its task set by extracting analytical scenarios reflective of industry demands. Each task provides a natural language instruction, input files (spreadsheets, reports, databases), and reference outputs. Models operate under a tool‑augmented agent framework: a code execution sandbox and a plan–execute–verify loop with up to 20 tool calls per task. The model must ingest inputs, perform necessary computations, and produce the final deliverable (answer, chart, or file). Tasks are labeled by difficulty based on expert operation count (easy ≤6, medium 7–12, hard ≥13) and by cross‑file requirement. Performance is measured using pass@k.

Evaluation relies on automated judges validated against human experts: a binary correctness judge for QA, a two‑criteria rubric (correctness, readability) for visualizations, and a staged verifier for generated spreadsheets. The dataset and evaluation code are released as a public resource.

## Key Results
- Overall best model (Claude Sonnet 4.5) achieves pass@1 of 59.43%; performance declines with difficulty (e.g., pass@3: 84.3% on easy → 50.5% on hard).  
- File generation is the most challenging category; top model reaches only 49.43% pass@1.  
- Cross‑file tasks (27.4% of the benchmark) further reduce scores, exposing limited multi‑file reasoning.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** The end‑to‑end task framing exposes weaknesses in integrating multi‑step operations across heterogeneous data that isolated benchmarks miss.
- **Mechanism:** Tasks require models to chain from raw file ingestion to final deliverable in a single continuous run, forcing orchestration of parsing, computation, and formatting.
- **Core assumption:** Real‑world data analytics are not decomposable into independent subtasks; competence must be evaluated holistically.
- **Evidence anchors:**  
  - Abstract: "We introduce AIDABench... an end‑to‑end evaluation suite... using heterogeneous data."  
  - Section 1: "AIDABench encompasses 600+ diverse document analytical tasks... reflect the analytical demands encountered across diverse industries and job functions."  
  - Neighbor benchmarks (WebDS, AD‑Bench) also adopt end‑to‑end framing, indicating a broader trend.
- **Break condition:** If future models achieve near‑human pass rates without demonstrable improvements in chaining ability, the mechanism’s diagnostic power would be undermined.

### Mechanism 2
- **Claim:** Task‑specific evaluators with high human alignment provide reliable, fine‑grained scoring that distinguishes true capability from noise.
- **Mechanism:** Three output types use dedicated judges: binary judge for QA, two‑scorer rubric for visualizations, staged spreadsheet file evaluator that samples and validates constraints.
- **Core assumption:** Human expert judgments represent the correct standard; automated scores must mirror these to be valid.
- **Evidence anchors:**  
  - Section 3.3: "The QA and Spreadsheet File Evaluators both achieve over 95% agreement with human judges, while the Visualization Evaluator exceeds 90%."  
  - Section 3.3.3: Details the multi‑stage file evaluation that mimics expert verification.
- **Break condition:** Significant divergence between evaluator scores and human judgments would invalidate the benchmark.

### Mechanism 3
- **Claim:** Difficulty stratification by operation‑chain length and inclusion of cross‑file tasks create a discriminating gradient that exposes fine‑grained weaknesses in multi‑step reasoning.
- **Mechanism:** Tasks are labeled by number of expert operations (easy ≤6, medium 7–12, hard ≥13) and 27.4% require joint reasoning over multiple files, forcing depth and breadth of reasoning.
- **Core assumption:** Operation count and file count are valid proxies for real‑world analytical difficulty.
- **Evidence anchors:**  
  - Section 3.1.2: "29.5% easy, 49.4% medium, 21.1% hard; 27.4% are cross‑file tasks."  
  - Section 4.2, Table 4: Performance declines with difficulty (e.g., claude‑sonnet‑4‑5 pass@3: 84.3 → 50.5 from easy to hard).
- **Break condition:** If models show no performance difference across difficulty or cross‑file categories, the stratification fails to provide additional insight.

## Architecture Onboarding
- **Component map:**  
  Task repository (JSON/CSV with instructions, inputs, references, labels) → Inference engine (model API wrapper + execute_code sandbox with 20‑round budget) → Evaluator suite (QA binary judge; Visualization correctness + readability; Spreadsheet staged verifier) → Aggregation scripts (pass@k, difficulty breakdowns, leaderboards).  
  Auxiliary modules (spreadsheet summarizer, token/round counters, error classifier) support pipeline.

- **Critical path:**  
  1. Install dependencies and configure API keys.  
  2. Download dataset and verify file integrity.  
  3. Pilot run on a small stratified subset.  
  4. Full evaluation: iterate tasks, capture model outputs.  
  5. Score outputs with appropriate evaluators.  
  6. Aggregate results and perform error analysis.

- **Design tradeoffs:**  
  - Single generic tool (flexibility vs potential inefficiency).  
  - Heterogeneous judges (tailored performance vs cost/complexity).  
  - Tolerant file matching (practical vs risk of false passes).  
  - 20‑round budget (resource limit vs possible premature termination).  
  - Static dataset (fair comparisons vs saturation risk).

- **Failure signatures:**  
  - *Semantic misunderstanding:* Ignoring output format constraints (e.g., wrong table shape) – dominant in File Generation.  
  - *Numerical miscalculation:* Parsing errors (multi‑row headers) or arithmetic mistakes – primary in QA.  
  - *Garbled non‑English text:* Missing glyphs in charts – common in Visualization.  
  - *Round limit exceed:* Models fail to converge within 20 steps, especially deepseek and small models.  
  - *Cross‑file misalignment:* Inconsistent handling of multiple inputs.

- **First 3 experiments:**  
  1. **Evaluator sanity check:** Verify that reference outputs score 1 and flawed outputs score 0.  
  2. **Baseline reproduction:** Run claude‑sonnet‑4‑5 on a 100‑task sample; expect pass@1 near 59.43% ±5%.  
  3. **Ablation validation:** Repeat without auxiliary summary on 200 tasks; expect performance drop consistent with Table 2.

## Open Questions the Paper Calls Out
The paper identifies several open questions and future research directions:

- How can models improve their performance on the most challenging file generation tasks, where top models achieve less than 50% pass@1?
- What techniques can enable more effective multi‑file reasoning, given that cross‑file tasks consistently lower scores?
- Can evaluation methods be further refined to better capture nuanced aspects of outputs (e.g., visualization aesthetics, spreadsheet compliance) while maintaining scalability?
- How can AIDABench be extended to encompass a wider variety of real‑world data formats, including unstructured data, to improve coverage?
- What is the impact of increasing the tool‑call budget or modifying the agent framework on performance, particularly for hard tasks?

## Limitations
- Dataset may not fully represent real‑world analytics diversity; bias toward structured data.  
- Evaluator agreement validated on limited samples; edge/cross‑file cases remain uncertain.  
- Lack of human baseline makes the "unsolved" claim relative.
