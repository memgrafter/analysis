# GraphRAG for Engineering Diagrams: ChatP&ID Enables LLM Interaction with P&IDs

## Quick Facts
- **arXiv ID:** 2603.22528  
- **Source URL:** https://arxiv.org/abs/2603.22528  
- **Reference Count:** 40  
- **Primary Result:** Graph-based retrieval improves accuracy by 18% and reduces token costs by 85% compared to raw image or direct XML inputs.

## Executive Summary
ChatP&ID is a framework that applies GraphRAG to engineering diagrams, specifically DEXPI-format Piping and Instrumentation Diagrams (P&IDs). It transforms these diagrams into knowledge graphs, which are then queried by an agentic LLM using graph-based retrieval strategies like ContextRAG and PathRAG. This approach enables natural-language interaction with P&IDs for process engineering tasks (e.g., HAZOP studies) with substantially higher accuracy and lower token costs than conventional methods that ingest raw images or direct XML. The best configuration, ContextRAG with GPT-5-mini, achieves 91% accuracy at a marginal cost of $0.004 per task, while GraphRAG variants also significantly boost performance for smaller open-source models.

## Method Summary
The method begins by parsing DEXPI XML P&IDs into a structured knowledge graph where symbols and relationships are represented as nodes and edges. For a given natural-language query, an LLM agent selects and executes one of several graph retrieval strategies: ContextRAG (retrieves relevant subgraphs around anchor nodes), PathRAG (follows semantically meaningful paths), or VectorRAG (embeds graph elements for similarity search). The retrieved graph fragments are then provided as context to the LLM to generate a final answer. This pipeline is evaluated against two baselines: directly feeding raw diagram images to the LLM and ingesting the raw DEXPI XML without graph structuring.

## Key Results
* Graph-based retrieval improves accuracy by 18% and reduces token consumption by 85% compared to raw image or direct XML ingestion.
* The optimal setup—ContextRAG with GPT-5-mini—reaches 91% accuracy at a cost of $0.004 per task.
* For smaller open-source models, VectorRAG and PathRAG provide accuracy gains of up to 40% over non-graph methods.

## Why This Works (Mechanism)
Graph-based retrieval focuses on the precise semantic structure of P&IDs. By representing symbols and their interconnections in a knowledge graph, the system can selectively traverse only relevant portions of the diagram (e.g., specific equipment chains or instrumentation loops). This avoids the noise and inefficiency of processing entire images or verbose XML dumps. The agentic LLM orchestrates the retrieval, enabling complex queries that require multi-step reasoning across the graph. The result is higher accuracy due to cleaner context and drastic token reduction from ignoring irrelevant elements.

## Foundational Learning
1. **GraphRAG** – Retrieval from knowledge graphs instead of text chunks.  
   *Why needed:* Captures relational semantics in structured diagram data.  
   *Quick check:* Verify graph connectivity and node degree distribution after parsing.
2. **DEXPI P&ID Standard** – XML schema for exchanging process diagrams.  
   *Why needed:* Provides standardized, machine-readable input format.  
   *Quick check:* Validate symbol attributes (e.g., tag IDs, types) in parsed graph.
3. **Agentic LLM** – LLM capable of planning and executing multi-step actions.  
   *Why needed:* Handles complex queries that require iterative graph traversal.  
   *Quick check:* Ensure the agent correctly decomposes sample queries into retrieval steps.
4. **Knowledge Graph** – Network of nodes (entities) and edges (relationships).  
   *Why needed:* Explicitly encodes diagram topology and semantics.  
   *Quick check:* Confirm all P&ID symbols appear as nodes with correct categorization.
5. **Retrieval-Augmented Generation (RAG)** – Augmenting LLM with external data.  
   *Why needed:* Supplies precise, structured context for diagram queries.  
   *Quick check:* Measure token count of retrieved subgraph; should be far less than full diagram.
6. **Engineering Diagram Parsing** – Converting visual diagrams to structured data.  
   *Why needed:* Enables computational reasoning over design documents.  
   *Quick check:* Cross-check parsed graph elements against source P&ID for completeness.

## Architecture Onboarding
**Component Map:**  
P&ID (DEXPI XML) -> Graph Parser -> Knowledge Graph -> RAG Modules (ContextRAG/PathRAG/VectorRAG) -> Context Retriever -> LLM Agent -> User Response

**Critical Path:**  
User query enters LLM agent -> agent selects RAG method -> graph traversal retrieves relevant subgraph -> subgraph formatted as context -> LLM generates final answer.

**Design Tradeoffs:**  
- *Graph Granularity:* Finer-grained nodes improve precision but increase traversal cost; coarser nodes reduce latency but may lose detail.  
- *RAG Method Selection:* ContextRAG balances precision and speed; PathRAG excels at relational queries but may over-retrieve; VectorRAG is flexible but depends on embedding quality.  
- *LLM Choice:* Larger models (GPT-5-mini) yield higher accuracy but higher cost; smaller open-source models benefit more from graph context but still lag behind top commercial models.

**Failure Signatures:**  
- Incomplete graph (missing symbols or relationships) leads to incorrect or partial answers.  
- Inappropriate RAG selection yields irrelevant context (e.g., using VectorRAG for path-heavy queries).  
- LLM misinterprets graph notation (e.g., confusing instrument tags with line numbers).  
- Excessive token usage from overly broad retrieval negates cost benefits.

**First Three Experiments:**  
1. Compare accuracy and token cost of all three RAG methods (ContextRAG, PathRAG, VectorRAG) on a fixed query set to identify optimal strategy per query type.  
2. Vary graph density (e.g., merging adjacent symbols) to measure impact on retrieval precision and latency.  
3. Evaluate cost–accuracy tradeoff across LLM sizes (GPT-5-mini, GPT-4o, open-source models like Llama) using the best RAG method.

## Open Questions the Paper Calls Out
The paper does not explicitly identify open questions for future work. However, based on its limitations and results, several open questions emerge:
- How well does GraphRAG generalize to other engineering diagram standards (e.g., P&FD, electrical schematics) or even non-engineering domains?
- What is the impact of graph construction choices (e.g., node/edge granularity) on retrieval performance and cost for diagrams of varying complexity?
- Can the agentic LLM's retrieval strategy selection be optimized or learned from query logs?
- How do alternative approaches, such as vision-language models that directly process diagram images, compare to the graph-based method in accuracy and efficiency?
- What are the scalability limits of graph parsing and retrieval for extremely large P&IDs with thousands of symbols?

## Limitations
* Claims are based on a single DEXPI dataset; baseline methods and dataset specifics are not detailed, hindering performance attribution.
* No code or data release is mentioned, creating a reproducibility gap.
* Applicability to other engineering diagram standards (e.g., P&FD, electrical) or non-process domains remains unproven.
