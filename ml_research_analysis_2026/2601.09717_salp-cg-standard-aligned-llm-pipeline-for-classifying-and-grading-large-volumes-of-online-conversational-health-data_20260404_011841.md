# SALP-CG: Standard-Aligned LLM Pipeline for Classifying and Grading Large Volumes of Online Conversational Health Data

## Quick Facts
- **arXiv ID**: 2601.09717
- **Source URL**: https://arxiv.org/abs/2601.09717
- **Reference count**: 26
- **Primary result**: SALP-CG achieves micro-F1 up to 0.900, mean category compatibility rate (MCCR) ≥0.984, and mean sensitivity grading quality (MSGR) ≥0.970 across ten LLMs, demonstrating backend-agnostic generalizability.

## Executive Summary
Online conversational health data embeds protected health information (PHI) requiring standardized classification and sensitivity grading for privacy protection, but existing automated methods lack alignment with a unified standard and reliable accuracy. This paper introduces SALP-CG, an LLM-based pipeline that adheres to the Chinese national standard GB/T 39725-2020 for PHI classification and grading. SALP-CG integrates three core components: few-shot guidance with carefully curated examples, JSON Schema-constrained decoding to enforce strict output format and category set, and a deterministic rule layer that overrides predictions for unambiguous high-risk patterns. Evaluated on a manually labeled benchmark of 1,000 dialogues from MedDialog-CN, SALP-CG achieves strong performance (micro-F1 up to 0.900, MCCR ≥0.984, MSGR ≥0.970) across ten diverse LLMs, proving its backend-agnostic robustness. Ablation studies confirm the necessity of all three components. Risk analysis shows that while Level 2-3 entities dominate and can combine for re-identification, Level 4-5 items, though less frequent, pose severe privacy harms, underscoring the importance of accurate grading.

## Method Summary
SALP-CG processes lengthy medical consultations by chunking the dialogue and applying a consistent extraction pipeline. The core extraction uses a prompt that combines: (1) a system instruction describing the task and the GB/T 39725-2020 rules (six categories, five sensitivity levels); (2) ten few-shot examples covering common, high-risk, negation, and uncertainty cases; (3) a JSON Schema that dictates the output structure, enumerates the six legal categories, and constrains the sensitivity level to integers 1–5. The constrained generation is handled by the LLM backend via API or decoding strategy. After obtaining the LLM’s raw entity triples, a deterministic rule engine applies curated regular expressions and keyword lists to override assignments for special diseases (promoted to “Special disease”, Level 5) and sensitive test results, while also downgading ruled-out or suspected mentions. The chunked results are merged, exact duplicate entities removed, and the final list sorted by descending sensitivity level. The pipeline is evaluated against gold labels on a 1,000-sample benchmark using micro-F1 for correct maximum-level prediction per dialogue, Mean Category-Compatibility Rate (MCCR) for category validity, and Mean Sensitivity Grading Quality (MSGR) for level accuracy on high-sensitivity (level ≥3) entities.

## Key Results
- SALP-CG achieves **micro-F1 up to 0.900** on maximum-level prediction (best model) and maintains **MCCR ≥0.984** and **MSGR ≥0.970** across all ten tested LLMs, showing consistent schema compliance and grading quality.
- **Ablation** shows removing any core component—few-shot guidance (MCIF drop 0.344), JSON Schema (MCCR drop 0.165), or deterministic rules (MSGR drop 0.030, Micro-F1 drop 0.070)—significantly harms performance.
- **Risk stratification** reveals Level 2 and Level 3 entities constitute the majority of extractions; these fragments can combine to re-identify individuals, while Level 4 and Level 5 items, though rare, represent severe privacy violations if disclosed.

## Why This Works (Mechanism)

### Mechanism 1: Few-Shot Guidance
- **Claim**: Few-shot guidance improves entity recall and reduces over-reliance on the LLM's parametric knowledge for contextually nuanced extraction.
- **Mechanism**: Providing 10 high-quality, manually labeled exemplars (covering common, high-risk, negation, and uncertainty cases) steers the LLM toward the desired extraction pattern (P, C, L) for online conversational health data, aligning its output with the GB/T 39725-2020 derived rules.
- **Core assumption**: Representative few-shot examples sufficiently cover the distribution of entity contexts and edge cases in the target data, enabling the LLM to generalize the classification and grading logic.
- **Evidence anchors**:
  - [abstract] "Combining few-shot guidance, JSON Schema constrained decoding, and deterministic high-risk rules..."
  - [section 3.2] "we include 10 high-quality exemplars from a labeled corpus, covering common entities... high-risk cases... as well as negation and uncertainty edge cases."
  - [section 4.4] Ablation: removing few-shot causes the largest drop in MCIF (0.344) and Micro-F1 (0.560), indicating its primary role in recall and correct maximum-level prediction.
- **Break condition**: Performance degrades severely if the few-shot set does not cover novel or underrepresented contextual patterns present in the input data (e.g., new slang, uncommon disease mention formats).

### Mechanism 2: JSON Schema-Constrained Decoding
- **Claim**: JSON Schema-constrained decoding enforces strict schema compliance for the category field (C), ensuring all predicted categories belong to the predefined set and minimizing post-processing effort.
- **Mechanism**: The prompt specifies a JSON Schema that enumerates all legal category values and constrains the level field (L) to integers [1,5]. The LLM's generation is guided (via API or decoding strategy) to produce syntactically valid JSON that adheres strictly to this schema, preventing "creative" category labels.
- **Core assumption**: The predefined category set (from Table 1) is complete and exhaustive for the extraction task; any real-world entity can be mapped to one of these categories.
- **Evidence anchors**:
  - [section 3.2] "the JSON schema enumerates all legal fields and constrains the level∈[1,5] via strict structured outputs, which yields near-zero format errors and minimal post-editing."
  - [section 4.4] Results show uniformly high MCCR (≥0.984) across all 10 LLMs, and ablation shows removing schema causes a 0.165 drop in MCCR.
- **Break condition**: The system fails to handle entities that do not fit any predefined category (out-of-schema entities), potentially forcing incorrect mappings or causing generation failures if the schema is too rigid.

### Mechanism 3: Deterministic High-Risk Rules
- **Claim**: Deterministic high-risk rules provide reliable, interpretable overrides for LLM predictions on specific, unambiguous patterns (e.g., positive high-risk HPV genotypes, explicit special disease names), ensuring correct sensitivity level assignment for the highest-risk items.
- **Mechanism**: A rule layer applies curated regular expressions and keyword lists *after* or *in parallel to* LLM inference. When a rule pattern matches (e.g., "HPV 16" + "positive"), it force-assigns the entity to the "Sensitive test result" category and Level 5, overriding the LLM's output.
- **Core assumption**: For a defined set of high-risk entities and patterns (special diseases, specific test results, direct identifiers), the rule-based mapping is unambiguous and superior to contextual LLM judgment, which may be swayed by negation or uncertainty in the dialogue.
- **Evidence anchors**:
  - [section 3.2] "deterministic high-risk rules that override the model when certain patterns are present... We also promote disease mentions to 'Special disease' via curated regex lists. In contrast, suspected/ruled-out mentions are downgraded to level 2."
  - [section 4.4] High MSGR scores (≥0.970 for most models) and the ablation showing removal of rules primarily impacts sensitivity grading (MSGR -0.030, Micro-F1 -0.070).
- **Break condition**: Rules fail or cause errors if the pattern matching is too broad (false positives) or too narrow (misses variants). They cannot handle contextual nuance (e.g., "tested for HPV" without a result) and may conflict with correct LLM judgment on borderline cases.

## Foundational Learning

### Concept 1: GB/T 39725-2020 Standard Structure
- **Why needed here**: The entire pipeline's outputs are defined relative to this standard. An engineer must understand the category definitions (e.g., "Medical Application Data" vs. "Health Status Data") and the risk rationale for each level (Level 5 = special disease) to design effective prompts, rules, and evaluate results correctly.
- **Quick check**: Given the phrase "HIV positive test result," what is the correct Category and Sensitivity Level per Table 1, and why is it Level 5?

### Concept 2: JSON Schema for Constrained Decoding
- **Why needed here**: This is the technical mechanism for enforcing schema compliance. The engineer must be able to write a valid JSON Schema that defines the output structure (`entities: [{entity: str, category: enum, level: int}]`) to integrate with the LLM API's response format or a constrained decoding library.
- **Quick check**: How would you modify the JSON Schema to make the `category` field an enum of exactly the 6 main categories from Table 1, and why is this better than leaving it as a free-form string?

### Concept 3: Few-Shot Prompting for Structured Extraction
- **Why needed here**: The prompt template is the primary interface guiding the LLM's behavior. The engineer must craft a clear instruction, embed the rules, and select/format exemplars that demonstrate the precise triple extraction format and handle edge cases (negation, uncertainty).
- **Quick check**: Design one few-shot example (input dialogue snippet, output JSON) that demonstrates how to correctly handle a ruled-out disease mention (e.g., "not HIV") according to the grading rules.

## Architecture Onboarding

### Component Map
- Input Preprocessor: Chunks long dialogues, stores in .xlsx.
- Prompt Builder: Assembles system instruction (role, rules), few-shot exemplars (from .jsonl), JSON Schema, and user input into a single prompt.
- LLM Backend Interface: HTTP API client for multiple providers (OpenAI, Groq, DeepSeek). Handles authentication, model selection, and parameter configuration.
- Rule Engine: Applies deterministic regex/keyword patterns to LLM's raw output or directly to input text to override/assign sensitivity levels for high-risk patterns.
- Post-Processor & Deduplicator: Merges results from chunked inputs, removes exact duplicate entities, sorts final list by descending sensitivity level.
- Output Serializer: Writes final list of (P, C, L) triples to .xlsx.

### Critical Path
Input -> Prompt Builder -> LLM Inference -> Rule Engine Override -> Deduplication/Sorting -> Output. The rule engine is a parallel/modification step, not strictly sequential.

### Design Tradeoffs
- *Backend-agnostic vs. Rule Maintenance*: Using generic API calls allows any LLM but pushes complexity to prompt engineering and rule definition. A model-specific fine-tune could reduce prompt/rule complexity but loses agnosticism.
- *LLM Recall vs. Precision*: Few-shot guidance and rules aim to boost recall of true entities, but the high MCIF variance (0.063 to 1.282) shows some models still hallucinate (over-extract) or are conservative (under-extract). Tuning prompt aggressiveness is a key lever.
- *Standard Fidelity vs. Contextual Nuance*: Strict rules ensure Level 5 for "HIV positive" but may downgrade "suspected HIV" to Level 2 correctly per spec, even if the clinical context implies high risk. The pipeline prioritizes rule compliance over contextual risk assessment beyond the standard.

### Failure Signatures
- **Format Errors**: LLM output not parseable as JSON. Indicates insufficient schema constraint or model capability issue.
- **Category Drift**: MCCR < 0.95. LLM generating categories not in the enum, suggesting schema not properly enforced or exemplars inadequate.
- **Sensitivity Misgrading**: Low MSGR on specific categories (e.g., "Test/exam result"). Indicates rule set incomplete for that category's sub-types or LLM failing on contextual cues (negation).
- **Count Inflation**: MCIF >> 1.0. LLM extracting non-entities or overly long spans; requires adjusting few-shot examples or entity span definition.

### First 3 Experiments
1. **Schema Compliance Smoke Test**: Feed a simple, unambiguous input (e.g., "Patient: Zhang Wei, 35, has diabetes.") with a minimal prompt. Assert output JSON is valid, `category` is exactly from the enum list, and `level` is an integer 1-5. This validates the core constrained generation path.
2. **High-Risk Rule Override Test**: Use an input with a clear high-risk pattern (e.g., "HPV 16 positive"). With rules enabled, assert the extracted triple has `category="Sensitive test result"` and `level=5`. Then disable the rule layer and re-run; assert the LLM alone may misclassify it (e.g., as "Test/exam result" level 3), demonstrating the rule's necessity.
3. **Few-Shot Ablation on Edge Case**: Use an input with a negation/uncertainty edge case (e.g., "ruled out cancer"). Run with the full 10-shot prompt and with a zero-shot prompt. Assert the full system correctly assigns a lower level (e.g., Level 2) per rules, while zero-shot may incorrectly assign Level 5. This quantifies the few-shot impact on nuanced classification.

## Open Questions the Paper Calls Out
1. **Generalizability** – How does SALP-CG's performance generalize to diverse conversational health data beyond the single MedDialog-CN-2020 benchmark, such as multilingual dialogues, different internet hospital platforms, or data from other time periods?
2. **Adaptive Rules** – Can the deterministic high-risk rules be made more adaptive or learnable to handle nuanced linguistic contexts (e.g., negation, speculation, family history mentions) that currently cause grading errors, without sacrificing precision on clear cases?
3. **Re-identification Risk** – What is the practical re-identification risk when an adversary combines numerous Level 2 and Level 3 data fragments (e.g., dates, hospital names, medication names) extracted from conversational data, as hypothesized in the risk stratification?
4. **Downstream Utility** – For health data governance, beyond sensitivity level assignment, how does SALP-CG's output facilitate or hinder downstream utility-preserving tasks (e.g., research, model training) when sensitive information is masked or transformed based on its grades?
5. **Few-Shot Optimization** – Can the few-shot guidance component be optimized or automated (e.g., via dynamic example selection) to further reduce reliance on manual prompt engineering and improve consistency across LLM backends, especially for smaller models?

## Limitations
- The exact content of the ten few-shot exemplars, the precise JSON Schema, and the deterministic rule regex patterns are not fully disclosed, hindering exact replication.
- Evaluation is confined to a single Chinese dataset (MedDialog-CN-2020); generalizability to other languages, platforms, or time periods remains unvalidated.
- LLM generation parameters (temperature, max tokens, etc.) are unspecified, which could affect output stability and reproducibility.

## Confidence
- **Few-shot guidance efficacy**: High (strong ablation evidence; MCIF drop 0.344).
- **JSON Schema enforcement**: High (uniformly high MCCR ≥0.984; ablation drop 0.165).
- **Deterministic rule layer**: Medium (ablation shows MSGR drop 0.030, but rule completeness/FP-FN tradeoffs untested).
- **Overall backend-agnostic generalizability**: Medium (tested on 10 LLMs, but commercial API drift/updates could break constraints).
