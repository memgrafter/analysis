# Beyond Quantity: Trajectory Diversity Scaling for Code Agents

## Quick Facts
- **arXiv ID:** 2602.03219
- **Source URL:** https://arxiv.org/abs/2602.03219
- **Reference count:** 20
- **Primary result:** Qwen3-Coder-30B-A3B trained with just 500 TDScaling samples achieved 36.66% on BFCL Multi-turn, exceeding the 480B baseline (35.91%) and scaling to 40.44% with 5k samples.

## Executive Summary
Code agents often suffer from diminishing returns when scaling training data by quantity alone, due to low-quality synthetic data and lack of diversity. TDScaling (Trajectory Diversity Scaling) addresses this by shifting the focus to maximizing trajectory diversity under a fixed budget. The framework introduces a Business Cluster mechanism that preserves MCP server modularity to capture real-service dependencies, a blueprint-driven multi-agent paradigm with dynamic schema locking for coherent execution, and an adaptive evolution loop guided by Domain Entropy, Reasoning Mode Entropy, and Cumulative Action Complexity to target long-tail scenarios. A sandboxed code tool is selectively injected to maintain coding skills.

On benchmarks, TDScaling yields strong improvements with minimal data: Qwen3-Coder-30B-A3B trained with just 500 samples achieves 36.66% on BFCL Multi-turn, surpassing a 480B baseline (35.91%), and reaches 40.44% with 5k samples. On coding tasks (RebenchT, CodeCI, BIRD), it gains +4.00% overall, reversing negative transfer from prior methods. Diversity metrics show substantial gains, confirming the effectiveness of the diversity-focused synthesis.

## Method Summary
TDScaling generates high-quality, diverse trajectories for fine-tuning code agents under a fixed data budget. The process begins with Business Cluster selection: MCP servers are clustered by semantic functionality, and a greedy maximum-coverage algorithm picks a toolset that maximizes the number of unique functional classes covered. Next, a BlueprintAgent creates a Scenario Blueprint (goal, plan, constraints, strategy) using the selected tools and insights from Global Memory. Then a multi-agent executor—comprising UserAgent, AssistantAgent, ObservationAgent (with Dynamic Schema Locking), and QualityAgent—runs the trajectory, ensuring structural consistency by caching JSON schemas. After execution, an Evolution Evaluator scores the trajectory on Domain Entropy, Reasoning Mode Entropy, and Cumulative Action Complexity, updating Global Memory to guide future blueprint generation toward under-explored domains and higher complexity. Finally, a sandboxed Code Tool is injected when computation is required. The generated trajectories are used to fine-tune a base model, such as Qwen3-Coder-30B-A3B.

## Key Results
- **Tool-use benchmarks:** With only 500 samples, TDScaling reaches 36.66% on BFCL Multi-turn, surpassing a 480B parameter baseline (35.91%). Scaling to 5k samples further improves to 40.44%.
- **Coding agent tasks:** TDScaling yields a +4.00% absolute gain on RebenchT, CodeCI, and BIRD, reversing the negative transfer observed in quantity-scaled baselines.
- **Diversity metrics:** The generated dataset shows substantially higher diversity: Domain Entropy 4.25 vs. 2.15, Reasoning Mode Entropy 8.97 vs. 5.42, and Cumulative Action Complexity µ=20.9 vs. 11.3.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Preserving the native modularity of MCP servers as Business Clusters increases semantic coverage and captures real-service logical dependencies under a fixed data budget.
- **Mechanism:** Treating each MCP server as a semantic cluster (instead of flattening tools) allows a greedy maximum-coverage selection to maximize the number of unique functional classes spanned by the chosen toolset. This forces the synthetic data to cover broader domain interactions rather than redundant, single-domain repetitions.
- **Core assumption:** Real-world tool usage exhibits intra-cluster logical coherence and inter-cluster diversity; mimicking this structure in training data improves generalization to new, modular tool ecosystems.
- **Evidence anchors:**
  - [abstract] "Business Cluster mechanism that captures real-service logical dependencies"
  - [section 3.1] "Leveraging MCP Servers as Business Clusters... Preserving this structure allows the model to learn coherent, dependency-aware workflows... We formulate... as a Maximum Coverage Problem"
  - [corpus] Related work (e.g., DIVE, ScaleEnv) also targets diversity, but TDScaling's cluster-specific approach is unique to MCP's modular architecture; corpus signals confirm diversity scaling is an active research direction.
- **Break condition:** If the greedy selection fails to increase cross-domain co-occurrence in generated trajectories (as measured by Domain Entropy and heatmaps in Figure 5), the mechanism does not improve tool-use generalization beyond random sampling.

### Mechanism 2
- **Claim:** A blueprint-driven multi-agent paradigm enforces trajectory coherence and prevents structural hallucination by pre-defining a logical topology (goal, plan, constraints, strategy) before execution.
- **Mechanism:** A BlueprintAgent generates a Scenario Blueprint conditioned on the selected toolset and global memory. During execution, a Dynamic Schema Locking mechanism caches a tool's output JSON schema from its first invocation and enforces strict adherence in subsequent calls, preventing inconsistent state simulations.
- **Core assumption:** Pure reactive generation leads to state inconsistency and logical drift; anchoring to a pre-computed plan with enforced schema contracts yields more reliable, stateful interactions.
- **Evidence anchors:**
  - [abstract] "blueprint-driven multi-agent paradigm that enforces trajectory coherence"
  - [section 3.2] "Blueprint-then-Execute paradigm... Dynamic Schema Locking... caches the output schema... and strictly enforces structural adherence"
  - [corpus] APIGen-MT also uses blueprints, but TDScaling adds schema locking and integrates with global evolution; corpus shows blueprinting is a common verification technique.
- **Break condition:** If trajectories still exhibit high rates of schema drift or plan deviation despite blueprinting (detected via QualityAgent's consistency checks), the mechanism fails to provide coherence benefits over simpler role-play.

### Mechanism 3
- **Claim:** An adaptive evolution loop guided by Domain Entropy, Reasoning Mode Entropy, and Cumulative Action Complexity actively steers synthesis toward under-explored, high-complexity long-tail scenarios, preventing mode collapse and raising the performance ceiling.
- **Mechanism:** Validated trajectories are scored on three metrics. Global Memory (G) aggregates insights and feeds a Strategy Profile back to the BlueprintAgent, which then biases new blueprint generation to fill gaps in domain distribution (`Hdom`), reasoning patterns (`Hmode`), or structural complexity (`CAC`).
- **Core assumption:** Passive data accumulation leads to homogeneity; explicit quantification and optimization of diversity/complexity dimensions is necessary to cover the long-tail of tool-use behaviors (e.g., nested calls, error recovery).
- **Evidence anchors:**
  - [abstract] "adaptive evolution mechanism... using Domain Entropy, Reasoning Mode Entropy, and Cumulative Action Complexity to prevent mode collapse"
  - [section 3.4] Formal definitions of `Hdom`, `Hmode`, `CAC` and description: "BlueprintAgent queries G to identify distributional gaps... dynamically steers synthesis"
  - [section 4.3 & Figure 5] Quantitative improvements: `Hdom` 4.25 vs 2.15, `Hmode` 8.97 vs 5.42, `CAC` µ=20.9 vs 11.3, and corresponding performance gains.
  - [corpus] DIVE and ScaleEnv also optimize diversity, but TDScaling introduces fine-grained entropy/complexity steering; corpus confirms the importance of steering for diversity.
- **Break condition:** If scaling data volume with this loop still shows inverse scaling (performance degradation with more samples) or if entropy/complexity scores plateau without performance improvement, the evolution strategy fails to effectively target novel scenarios.

## Foundational Learning
- **Concept: Maximum Coverage Problem (Greedy Algorithm)**
  - **Why needed here:** The Business Cluster selection is formulated as maximizing the union of functional classes covered by selected clusters under a budget. Understanding this combinatorial optimization explains why the greedy approach is used and its approximation guarantees.
  - **Quick check question:** Given three clusters covering functional sets {A,B}, {B,C}, and {C,D}, and a budget of 2, which clusters does the greedy algorithm select first and why?

- **Concept: Shannon Entropy for Distributional Uniformity**
  - **Why needed here:** `Domain Entropy` and `Reasoning Mode Entropy` are Shannon entropy measures over cluster and reasoning-mode frequencies. High entropy indicates a uniform, diverse spread across categories, which is the target for avoiding mode collapse.
  - **Quick check question:** If 90% of trajectories use the "Weather" domain and 10% use "Finance", what is the Domain Entropy? Is this high or low diversity?

- **Concept: Cumulative Action Complexity (CAC)**
  - **Why needed here:** CAC quantifies the intrinsic difficulty of a trajectory by summing per-action costs, which include switching costs (domain changes) and depth costs (parameter dependency levels). This metric guides the system toward structurally deeper, longer-horizon interactions.
  - **Quick check question:** Does a trajectory with three sequential tool calls all within the same "Search" domain have higher or lower CAC than one alternating between "Search" and "Database"? Why?

## Architecture Onboarding
- **Component map:**
  1. **Tool-Space Constructor:** Raw MCP tools → Business Clusters (K-Means) → Greedy functional-class coverage selection.
  2. **Global Memory (G):** Database storing distribution statistics (`Hdom`, `Hmode`, `CAC` trends) and strategy profiles (`Ψ`).
  3. **Blueprint Agent:** Consumes selected toolset + `G` → outputs Scenario Blueprint (`g, P, C, Ψ`).
  4. **Multi-Agent Executor:** UserAgent, AssistantAgent, ObservationAgent (with Dynamic Schema Locking), QualityAgent → generate/validate trajectory `τ`.
  5. **Evolution Evaluator:** Computes `Hdom`, `Hmode`, `CAC` for `τ` → updates `G`.
  6. **Code Tool:** Sandboxed Python interpreter, injected per Blueprint's "General-Tool-First" principle.

- **Critical path:** Cluster Selection (1) → Blueprint Synthesis (3) → Multi-Agent Execution (4) → Trajectory Evaluation (5) → Update Global Memory (2) → Influence next Blueprint (3). The Code Tool (6) is a conditional branch during execution.

- **Design tradeoffs:**
  - **Synthesis cost vs. quality density:** Multi-agent, teacher-model-backed synthesis is API/latency expensive but produces higher-entropy, more complex trajectories that yield better data efficiency.
  - **Code Tool injection:** Restricting to standard APIs first ("General-Tool-First") avoids over-reliance on code but risks missing needed computation; dynamic injection based on Blueprint assessment balances this.
  - **Schema locking vs. flexibility:** Enforcing a fixed output schema from turn 1 prevents state hallucination but may reduce adaptability to tools with inherently variable responses (a potential failure if tool specs are inconsistent).

- **Failure signatures:**
  - **Inverse scaling:** Performance decreases as training samples increase (observed in APIGen-MT, Simia in Figure 4). Indicates low-diversity, homogeneous data causing overfitting.
  - **Mode collapse:** Low `Hmode` (<5) or `Hdom` (<3) in final dataset, with heatmaps showing strong diagonal (single-domain) patterns (Figure 5a).
  - **Catastrophic forgetting:** Coding benchmark scores (BIRD, CodeCI) drop significantly compared to base model when Code Tool is absent (Table 3, `w/o Code Tool`).
  - **Schema violation:** QualityAgent rejects trajectories with inconsistent tool output schemas across turns.

- **First 3 experiments:**
  1. **Diversity Metric Validation:** Compute `Hdom`, `Hmode`, and `CAC` distribution for a baseline (random sampling) vs. TDScaling dataset. Expect significantly higher entropy and right-shifted CAC (as in Figure 3 & 5c). *Pass condition:* `Hdom` > 4.0, `Hmode` > 8.0, `CAC` µ > 20.
  2. **Ablation on BFCL Multi-turn:** Train four models: full TDScaling, w/o Cluster Sampling, w/o Global Evolution, w/o Code Tool (500 samples each). Evaluate on BFCL Multi-turn. Expect full model > others; `w/o Code Tool` may gain slightly on BFCL but lose on coding benchmarks. *Pass condition:* Full model outperforms all ablations in average score (Table 3).
  3. **Scaling Curve with Fixed Budget:** Train models with 500, 1k, 2k, 5k TDScaling samples. Plot BFCL Multi-turn accuracy. Expect monotonically increasing or stable performance (positive scaling), contrasting with baselines' inverse scaling (Figure 4). *Pass condition:* 5k model > 500 model by >3% absolute, and 5k model surpasses 480B baseline's 35.91%.

## Limitations
- **Generalizability beyond MCP:** The Business Cluster mechanism is tightly coupled with MCP server modularity; its effectiveness for non-modular or monolithic tool APIs (e.g., a single large LLM tool with many functions) remains an open question.
- **Long-term Horizon & Error Recovery:** While the pipeline targets complexity, evaluation primarily uses static, curated benchmarks. The paradigm's robustness to dynamic, real-time failures (e.g., tool downtime, inconsistent outputs) and its ability to learn from multi-step error recovery chains are not fully demonstrated.
- **Synthesis Cost & Scalability:** The multi-agent, teacher-model-backed synthesis pipeline is computationally expensive. The paper does not analyze the wall-clock cost per high-quality trajectory, making the practical data-efficiency trade-off for large-scale production unclear.

## Confidence
- *Claim:* Relative improvement on specific benchmarks (BFCL, RebenchT, etc.) with TDScaling over quantity-scaled baselines. *Confidence:* High.
- *Claim:* The causal mechanism: that trajectory diversity directly causes the performance gains. *Confidence:* Medium.
- *Claim:* Broad generalizability of TDScaling to arbitrary tool ecosystems or future agent architectures. *Confidence:* Low.

## Next Checks
1. **Cross-Architecture Replication:** Implement the TDScaling pipeline (cluster selection, blueprinting, evolution) using a different base agent model (e.g., GPT-4o, Claude-3.5-Sonnet) and a non-MCP toolsuite (e.g., a monolithic web API like Shopify's). Measure if the performance delta over random sampling persists and if the entropy gains replicate.
2. **Robustness Stress Test:** Generate a test set of trajectories containing induced tool failures (invalid parameters, rate limits, schema drift) and silent data corruptions. Compare TDScaling-trained agents against quantity-scaled agents on recovery rate and final task success, isolating the value of the coherence mechanisms.
3. **Cost-Benefit Analysis:** Run a detailed throughput and cost analysis of the synthesis pipeline. Calculate the total API/token cost per final, validated trajectory for TDScaling vs. naive random sampling. Determine the break-even point where TDScaling's higher data efficiency outweighs its higher per-sample synthesis cost for a given target performance level.
