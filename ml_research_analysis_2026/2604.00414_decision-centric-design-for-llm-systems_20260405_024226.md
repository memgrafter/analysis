# Decision-Centric Design for LLM Systems

## Quick Facts
- **arXiv ID**: 2604.00414
- **Source URL**: https://arxiv.org/abs/2604.00414
- **Reference count**: 40
- **Primary result**: A decision-centric framework that explicitly separates signals from action selection reduces futile actions (e.g., wasted executions) and enables diagnosable failures, achieving near-perfect success in controlled tasks and isolating signal quality effects.

## Executive Summary
Current LLM systems often intermix control logic (e.g., when to ask for clarification or retrieve information) with generation, making it hard to pinpoint failure causes. This paper proposes a decision-centric abstraction that cleanly separates three elements: actions, decision context (explicit signals and state), and a deterministic decision function. This separation creates an inspectable control layer, allowing failures to be attributed to signal estimation, policy, or execution and enabling modular improvements. The framework is evaluated on three tasks: calendar scheduling, graph disambiguation, and retrieval control. In calendar scheduling, it achieved 100% success across all missing-field scenarios and reduced wasted executions by up to 2.9 per run compared to prompt-based clarification. In graph disambiguation, it reached 100% success while baselines fell to 35–95% in a scenario requiring correlated belief updates. In retrieval, varying the sufficiency signal while holding the policy fixed improved medium-difficulty question success from 14% (prompt) to 88–94%, demonstrating the diagnosability of signal quality issues. Across settings, the approach reduces futile actions, enhances task success, and provides a clear blueprint for building more reliable LLM systems.

## Method Summary
The decision-centric framework consists of five components: signal estimators that produce scalar decision-relevant signals, a decision context that aggregates these signals along with updatable state, a deterministic decision function that maps the context to actions, an execution engine that carries out the chosen action, and a state updater that modifies the context based on execution outcomes. This explicit pipeline replaces monolithic prompting where control decisions are entangled with generation. The invariant is that every action selection explicitly consumes the current context, which is never “internal” to a generative call.

The authors instantiate the framework on three tasks—calendar scheduling, graph disambiguation, and retrieval control—using zero‑shot prompts for estimators without any training. For calendar scheduling, a single sufficiency signal and a threshold policy decide between clarifying and executing; for graph disambiguation, joint sufficiency and correctness signals and a rule‑based policy that can backtrack; for retrieval, three sufficiency signals (LLM judge, embedding similarity, composite) are compared under a common stop/expand controller. Baselines include implicit prompt‑based control variants. Models used are IBM Granite‑4:micro and LLaMA3 8B. Evaluation measures success rates, wasted actions, and efficiency metrics, and logs intermediate signals for failure attribution.

## Key Results
- **Calendar scheduling**: 100% success across all missing-field scenarios; wasted executions reduced by up to 2.9 per run vs. prompt‑based clarify.
- **Graph disambiguation**: 100% success in the correlated update scenario (S5); baselines dropped to 35–95%.
- **Retrieval control**: Medium‑difficulty question success rose from 14% (prompt) to 88–94% using DC variants; isolating signal construction effects showed that both signals overestimating sufficiency caused most failures.

## Why This Works (Mechanism)
**Mechanism 1: Inspectable Act/Clarify Decisions**  
The explicit separation of decision‑relevant signals from the action selection policy makes the act/clarify decision inspectable and enforceable, preventing premature execution on incomplete information. A sufficiency signal (e.g., “all required fields confirmed”) is computed from the decision context and consumed by a deterministic policy (e.g., “execute only if sufficiency=1.0”). This prevents the model from implicitly outputting an execute action when its internal assessment indicates insufficiency. Evidence: In calendar scheduling, DC’s wasted executions were near zero across missing‑field counts, while Prompt‑Clarify’s waste grew with missing fields (Table 2). Break condition: If the sufficiency estimator consistently underestimates completeness, the system may over‑clarify; if it overestimates, premature execution persists.

**Mechanism 2: Joint Belief Tracking for Sequential Decisions**  
Externalizing multiple co‑evolving signals (e.g., sufficiency and correctness) and allowing the policy to reason over their joint state enables correct sequential decisions where actions indirectly update beliefs. The decision context maintains explicit, updatable state (e.g., candidate pool size, correctness estimate). The policy maps the pair (sufficiency, correctness) and auxiliary state to actions. Because state updates like elimination are captured in the context, subsequent decisions reflect the new reality. Evidence: In graph disambiguation, Scenario S5 showed DC 100% success while prompt‑based methods failed (35%) because DC’s context captured candidate pool shrinkage from a failed traversal, enabling correct backtracking. Break condition: If the context fails to capture a key indirect effect (e.g., an elimination rule not coded) or the policy’s joint mapping is incorrect in some region, optimal actions will be missed.

**Mechanism 3: Modular Signal Construction for Diagnosability**  
Making the sufficiency signal a first‑class, logged output creates a modular interface for component improvement and enables attribution of failures to signal estimation, policy, or execution. The decision function is fixed; only the construction of the sufficiency signal varies. Logging the scalar signal at each turn allows offline analysis: failures can be traced to the round and signal values that drove the wrong action, diagnosing whether the signal itself was poorly calibrated. Evidence: In retrieval, DC variants (different signals) under the same controller yielded different success on medium questions (14% → 88–94%), isolating signal quality effects. Table 12 attributed most medium failures to “both signals high” incorrectly, guiding next‑step signal design. Break condition: If the policy is overly sensitive to signal noise, improving the signal may not help; if logging is absent, attribution fails.

## Foundational Learning

**Concept: Decision‑Centric Abstraction (A, c, δ)**  
*Why needed*: This is the core architecture. It defines the explicit interface: actions A, decision context c (exposed signals/state), and deterministic decision function δ. Understanding this triplet is necessary to see how current systems differ (implicit) and how the framework enforces separation.  
*Quick check*: In calendar scheduling, what are A, c, and δ?  
A = {clarify, execute}; c = confirmed fields vector from estimator; δ = threshold policy on completeness.

**Concept: Evolving Context in Sequential Decisions**  
*Why needed*: The framework extends beyond single‑step routing to multi‑turn interactions where actions change the information available. The context c_t must be updateable; the policy consumes c_t at each turn. This is critical for graph disambiguation and retrieval, where each action (visit, clarify) alters the candidate set or passage set.  
*Quick check*: In graph Scenario S5, what specific event updates the sufficiency signal without a clarification turn?  
A failed traversal triggers candidate elimination, increasing 1/|candidates|.

**Concept: Modular Signal Construction**  
*Why needed*: The retrieval experiment shows that holding δ fixed while varying signal construction isolates what part of the system needs improvement. This modularity is a key advertised benefit for diagnosability and iterative development.  
*Quick check*: Why could DC‑Dense (cosine similarity) over‑expand while DC‑LLM (answerability judge) was more selective?  
Dense signal reacts to topical relevance, not explicit answer presence; LLM judge is trained for answerability, thus more conservative.

## Architecture Onboarding

**Component map**  
Signal Estimators → Decision Context → Decision Function → Execution Engine → State Updater → (back to Decision Context for next turn)

**Critical path**  
1. Input (user query) → Build initial c₀  
2. δ(c₀) → action  
3. Action → execution  
4. Observe outcome → update c₁ (via State Updater)  
5. Repeat from step 2 until terminal action (e.g., final execute) → output.  
Invariant: every action selection explicitly consumes c_t; c_t is never “internal” to a generative call.

**Design tradeoffs**  
- **Explicitness vs. overhead**: Maintaining explicit state and separate estimators adds latency and complexity vs. single‑call prompting; benefit is diagnosability and enforceability.  
- **Signal fidelity vs. policy simplicity**: A very simple policy (e.g., threshold) requires highly reliable signals; a more complex policy may be less interpretable. The framework favors simple, transparent policies with richer contexts.  
- **Hard‑coded updates vs. learned belief tracking**: In sequential settings, how state updates occur (e.g., elimination rules) must be encoded. This is powerful but requires domain knowledge; a fully Bayesian approach would learn updates but sacrifice transparency.

**Failure signatures**  
- **Signal estimation failure**: Logged signal value is wrong for the true state (e.g., ˆpsuff=1.0 when fields are missing). Diagnose by inspecting estimator’s raw output on known cases.  
- **Policy failure**: Signal is correct, but δ chooses suboptimal action for that c_t. Diagnose by analyzing (c_t, action) pairs against a ground‑truth policy or heuristic.  
- **Execution failure**: Signal and policy correct, but execution produces invalid output (e.g., malformed JSON). Isolated by comparing expected vs. actual output.  
- **State update failure**: c_t does not reflect a key change (e.g., elimination after traversal not captured). Diagnose by comparing logged c_t before/after an action to expected state transition.

**First 3 experiments**  
1. **Calendar Scheduling (Minimal act/clarify)**: Validates that a single explicit sufficiency signal + threshold policy eliminates wasted executions. Shows failure attribution: LLaMA 3’s k=1 failure traced to question generator, not estimator or policy.  
2. **Graph Disambiguation (Multi‑signal sequential)**: Tests joint beliefs (ˆpsuff, ˆpcorr) and correlated updates. Shows prompt‑based methods fail to observe elimination updates; DC’s explicit context captures them. Policy jointly maps (signals + state) to clarify/execute/backtrack.  
3. **Retrieval Control (Modular signals)**: Holds δ fixed (threshold stop/expand), varies signal construction (LLM, dense, composite). Demonstrates diagnosable feedback: logging ˆp per round attributes medium failures to both signals overestimating sufficiency, guiding next signal design (e.g., require explicit answer span).

## Open Questions the Paper Calls Out

1. **Hierarchical decision layers**  
   *Question*: How can hierarchical decision layers be designed and optimized within the decision‑centric framework for complex, multi‑stage tasks?  
   *Basis*: The conclusion identifies “hierarchical decision layers” as a natural extension.  
   *Why unresolved*: The paper only demonstrates single‑level decisions; no architecture, training method, or evaluation for hierarchies is provided.  
   *Resolution evidence*: A prototype hierarchical system applied to a benchmark requiring multiple nested control decisions (e.g., long‑horizon tool‑use workflows), with ablations showing the value of explicit layering versus flat end‑to‑end policies.

2. **Learning the decision policy**  
   *Question*: Would learning the decision policy (e.g., via reinforcement learning) improve performance over hand‑crafted deterministic rules, and what are the trade‑offs in data efficiency, robustness, and interpretability?  
   *Basis*: The framework’s policy (δ) is presented as a placeholder for learned or optimization‑based methods, but all experiments use fixed, human‑specified thresholds and rules.  
   *Why unresolved*: The paper contrasts explicit vs. implicit control but does not compare hand‑crafted vs. learned policies, leaving open whether learning could further improve the separation of concerns.  
   *Resolution evidence*: A study where the policy is trained (e.g., with RL from synthetic or human feedback) on the same decision points used in the calendar or graph tasks, measuring success, failure attribution clarity, and generalization to new scenarios compared to the hand‑crafted policy.

3. **Comparative signal estimation methods**  
   *Question*: What are the comparative strengths and failure modes of different signal estimation methods (e.g., LLM‑based judges, embedding similarity, rule‑based checks) across diverse domains, and how can they be robustly combined?  
   *Basis*: Section 5.3 isolates signal quality by holding the controller fixed while varying the sufficiency signal (DC‑LLM, DC‑Dense, DC‑Composite), showing large performance differences.  
   *Why unresolved*: The paper tests only a small set of signals in retrieval; it does not provide a systematic framework for choosing or combining signals in other settings (e.g., scheduling, graph search), nor does it analyze when each fails.  
   *Resolution evidence*: A cross‑domain benchmark where multiple signal types are evaluated on the same decision tasks, with failure attribution traces categorizing errors as signal estimation vs. policy vs. execution, and a study on signal fusion techniques that maintain modularity while improving reliability.

4. **Scalability to open‑ended interactions**  
   *Question*: Does the decision‑centric framework maintain its benefits (reduced futile actions, diagnosable failures) when scaled to open‑ended, long‑horizon interactions with stochastic users and noisy environments?  
   *Basis*: All experiments use simulated, deterministic user simulators or precomputed retrieval states; real‑world deployments involve unpredictable user behavior, partial observability, and dynamic contexts.  
   *Why unresolved*: The controlled settings isolate decision mechanics but may not capture the complexity and noise of real deployments where signal estimation and policy must operate under greater uncertainty.  
   *Resolution evidence*: Deploying the framework in a live, multi‑turn system (e.g., a calendar assistant with real users or an open‑domain QA agent) and measuring the rate of futile actions, user satisfaction, and the accuracy of failure attribution logs compared to a baseline implicit‑control system.

5. **Integration with multi‑agent orchestration**  
   *Question*: How can the decision‑centric abstraction be integrated with existing multi‑agent orchestration frameworks (e.g., AutoGen, ReAct) to provide explicit, inspectable control at both the task and sub‑task levels?  
   *Basis*: The conclusion and related work mention multi‑agent architectures but frame the decision layer as “within‑task control,” leaving unclear how it composes with or replaces high‑level orchestration.  
   *Why unresolved*: The paper positions the framework as complementary to agentic workflows but does not specify how decision points align with agent actions, message passing, or group planning mechanisms.  
   *Resolution evidence*: An implementation that wraps common agent communication patterns with decision‑centric controllers, evaluating metrics like orchestration efficiency, failure diagnosability across agent turns, and the ability to enforce cross‑agent constraints (e.g., budget caps) through the decision layer.

## Limitations
- Evaluation limited to three curated tasks; transfer to open‑ended LLM systems (e.g., coding, dialogue) remains unknown.
- Graph experiment underspecified: random seeds, exact candidate count seeding, elimination rule details, and correctness penalty values are missing, hindering faithful replication.
- No measurement of added latency or cost from explicit state tracking and multiple estimator calls, which could impact practicality.

## Confidence
- **Reduction in futile actions**: *Medium‑High* (consistent gains in calendar and retrieval)
- **Diagnosability and failure attribution**: *Medium* (logging interface enables tracing but real‑world complexity may challenge clean attribution)
- **Generality as an architectural principle**: *Low‑Medium* (theoretical soundness strong, but empirical validation confined to three narrow scenarios)

## Next Checks
1. **Cross‑model replication**: Re‑run all experiments with at least two additional model families (e.g., GPT‑4, Claude 3) to test robustness across model scales.
2. **Threshold boundary analysis**: Systematically vary decision thresholds (e.g., sufficiency, stop) in calendar and retrieval tasks to map failure modes and confirm signal vs. policy error separability.
3. **Overhead benchmarking**: Measure wall‑clock time, token usage, and monetary cost of the decision‑centric pipeline versus monolithic prompting as context length and number of decision signals scale.
