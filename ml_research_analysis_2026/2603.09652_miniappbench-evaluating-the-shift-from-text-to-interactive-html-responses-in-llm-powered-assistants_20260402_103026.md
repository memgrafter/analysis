# MiniAppBench: Evaluating the Shift from Text to Interactive HTML Responses in LLM-Powered Assistants

## Quick Facts
- **arXiv ID**: 2603.09652
- **Source URL**: https://arxiv.org/abs/2603.09652
- **Reference count**: 40
- **Primary result**: Top LLMs achieve only 45.46% pass rate on MiniAppBench under strict thresholds, highlighting significant challenges in generating correct interactive applications.

## Executive Summary
This paper introduces MiniAppBench, a benchmark of 500 real-world tasks requiring interactive HTML MiniApps across six domains, and MiniAppEval, an agentic evaluation framework that uses browser automation to assess generated apps. MiniAppEval evaluates three dimensions—Intention, Static, and Dynamic—and employs a double-blind protocol to avoid bias. Results show state-of-the-art LLMs struggle, with GPT-5.2 reaching only 45.46% pass rate. The framework demonstrates strong human alignment (Cohen’s κ up to 0.89) and provides a reliable standard for evaluating the shift from static text to interactive responses.

## Method Summary
MiniAppBench was built by distilling millions of user queries through rigorous filtering into 500 representative tasks that demand functional interactive web applications. For evaluation, MiniAppEval utilizes an LLM-based agent (Gemini-3-Pro-Preview) combined with browser automation to execute generated MiniApps. The agent judges each app on: Intention (matches user request), Static (code quality and principle adherence), and Dynamic (runtime behavior). A double-blind design ensures the evaluator does not know the generator, reducing confirmation bias. Human evaluations confirmed high agreement with the automated scores.

## Key Results
- MiniAppBench contains 500 tasks derived from real user queries across six domains.
- The best model (GPT-5.2) attains a pass rate of 45.46% under a strict threshold.
- MiniAppEval shows high correlation with human judgment (Cohen’s κ up to 0.89) and mitigates bias through double-blinding.

## Why This Works (Mechanism)
MiniAppEval succeeds by executing generated MiniApps in a real browser environment, capturing both static code properties and dynamic interactions. The three dimensions offer a comprehensive assessment: Intention verifies semantic alignment, Static checks principle adherence without execution, and Dynamic validates actual functionality. The double-blind protocol prevents evaluator bias from known model reputations. This combination of executable testing and blind evaluation yields human-aligned, nuanced scores that can differentiate MiniApp quality effectively.

## Foundational Learning
- **Interactive HTML Generation**: LLMs must output runnable web apps rather than plain text. *Why needed*: Reflects the evolving role of assistants. *Quick check*: Does the generated app support the requested interactions?
- **Browser Automation**: Tools (e.g., Puppeteer) automate browser actions for testing. *Why needed*: Enables scalable evaluation of dynamic behavior. *Quick check*: Can automation reliably trigger events and read DOM state?
- **Double-Blind Evaluation**: Evaluator is unaware of the generator’s identity. *Why needed*: Avoids bias from model prestige. *Quick check*: Do scores shift when evaluator knows the source?
- **Principle Adherence**: Generated apps must respect real-world constraints (e.g., physics, timing). *Why needed*: Interactive apps often embed domain rules. *Quick check*: Does the app correctly implement constraints like “after 5 seconds” or “collision detection”?

## Architecture Onboarding
- **Component Map**: Query Source → Distillation Pipeline → Task Repository (MiniAppBench); Task Repository → LLM Generator → Generated MiniApp → Evaluation Agent (Gemini-3-Pro-Preview + Browser Automation) → Scoring Module; Scoring Module ↔ Human Evaluators (validation).
- **Critical Path**: From a benchmark task, an LLM produces a MiniApp; the Evaluation Agent runs it via browser automation and assigns scores on the three dimensions; scores are aggregated for a final pass/fail decision.
- **Design Tradeoffs**: 
  - Single evaluator model (Gemini-3-Pro-Preview) reduces variance but may embed model-specific biases.
  - Strict pass threshold prioritizes precision, potentially rejecting borderline acceptable apps.
  - Browser automation offers realism but depends on environment stability and selector robustness.
- **Failure Signatures**:
  - Intention: App deviates from the user’s intended functionality.
  - Static: Code errors, missing principles, or insecure patterns.
  - Dynamic: Runtime crashes, incorrect state changes, or broken interactions.
- **First Experiments**:
  1. Evaluate recent open-source LLMs (e.g., Llama-3.1, Mistral) on MiniAppBench to compare with proprietary models.
  2. Assess evaluation consistency by running MiniAppEval with multiple judge models (GPT-5.2, Claude-4.5) on a fixed set of outputs.
  3. Deploy the top model (GPT-5.2) in a live assistant with user-facing HTML generation and correlate benchmark scores with real-world usability metrics.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: Which real-world principles (e.g., physical laws, temporal constraints) are hardest for LLMs to correctly implement in MiniApps?
- Basis in paper: [inferred] The paper reports performance varies across domains and notes struggles with principle adherence but does not break down which specific principles cause the most failures.
- Why unresolved: Without identifying the hardest principles, we cannot target model improvements or training data effectively.
- What evidence would resolve it: A fine-grained error analysis of benchmark failures, categorizing each by principle type and underlying cause (e.g., knowledge gap, reasoning error, code bug).

### Open Question 2
- Question: How robust is MiniAppEval to the choice of LLM evaluator, and could using a single evaluator model introduce systematic bias in benchmark results?
- Basis in paper: [inferred] The evaluation agent relies exclusively on Gemini-3-Pro-Preview; the paper does not test whether other LLM judges would produce consistent scores.
- Why unresolved: If scores vary widely with the evaluator, model rankings may not be reproducible or fair across studies.
- What evidence would resolve it: Run MiniAppEval on a fixed set of MiniApps using multiple evaluator models (e.g., GPT-5.2, Claude-4.5, open-source LLMs) and measure inter-evaluator agreement and alignment with human judgments.

### Open Question 3
- Question: Are the three evaluation dimensions (Intention, Static, Dynamic) adequate to assess MiniApp quality for real-world deployment, or are important non-functional attributes (e.g., usability, accessibility, security) missing?
- Basis in paper: [inferred] The framework focuses on functional correctness and principle adherence; it does not discuss whether other quality aspects are needed for interactive applications.
- Why unresolved: Real-world applications must satisfy usability, accessibility, etc. Overlooking these may lead to models that excel on the benchmark but produce poor user experiences.
- What evidence would resolve it: Correlate existing dimension scores with user study metrics (task success, satisfaction) and expert audits; identify additional dimensions that significantly predict real-world fitness.

### Open Question 4
- Question: How representative is MiniAppBench of actual user requests for interactive web apps, and what significant coverage gaps exist in domains, interaction patterns, or principle types?
- Basis in paper: [inferred] The benchmark was distilled from millions of queries through strict filtering; the final 500 tasks likely omit many valid request types.
- Why unresolved: An unrepresentative benchmark may steer research toward narrow subproblems, limiting the relevance of results to production settings.
- What evidence would resolve it: Compare the benchmark's distribution (domains, subclasses, interactions) with that of a random sample of raw user queries or an expert-defined taxonomy; perform statistical tests to identify undercovered categories and potentially augment the benchmark.

## Limitations
- **Benchmark representativeness**: The 500-task set may not capture the full diversity of user requests, especially long-tail interactions and domain coverage.
- **Evaluator dependency**: MiniAppEval relies on a single LLM judge; scores may vary with different evaluator models, affecting reproducibility.
- **Generalization caution**: The reported low pass rate may be specific to MiniAppBench’s distribution and not indicative of broader interactive app generation capability.

## Confidence
- **Evaluation Framework Reliability**: High (double-blind protocol and strong human alignment with Cohen’s κ up to 0.89).
- **Benchmark Representativeness**: Medium (derived from real queries but limited size and domain diversity).
- **Claim on LLM Capability Gap**: Low (result confined to benchmark; representativeness unverified).

## Next Checks
1. **Cross-Dataset Generalization**: Run MiniAppEval on an independent, publicly available dataset of HTML/JS generation tasks to test if the performance gap holds beyond MiniAppBench.
2. **Tool-Bias Adversarial Test**: Manually construct test cases where browser automation criteria are ambiguous or conflict with intention to probe for framework-induced artifacts.
3. **Real-World Deployment Pilot**: Integrate the top model (GPT-5.2) into a live, low-stakes assistant with user-facing HTML generation; log user success rates, edit patterns, and abandonment reasons to compare with benchmark metrics.
