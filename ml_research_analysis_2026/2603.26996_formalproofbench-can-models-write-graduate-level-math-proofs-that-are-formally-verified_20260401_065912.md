# FormalProofBench: Can Models Write Graduate Level Math Proofs That Are Formally Verified?
## Quick Facts
- **arXiv ID**: 2603.26996
- **Source URL**: https://arxiv.org/abs/2603.26996
- **Reference count**: 14
- **Primary result**: Claude Opus 4.5 (Thinking) achieves 33.5% pass rate on 200 graduate-level Lean 4 proving tasks; the next best model scores 18.5%.

## Executive Summary
FormalProofBench introduces a private benchmark for evaluating large language models on formal theorem proving at the graduate level. It comprises 200 challenging problems from advanced mathematics textbooks and qualifying exams, covering analysis, algebra, probability, and logic. Models interact with a Lean 4 environment through an agent harness that provides tools for searching Mathlib (`lean_loogle`) and executing code (`lean_run_code`), and must submit a proof within 40 turns. The Lean kernel acts as a binary correctness oracle: proofs either compile or fail. The best-performing model, Claude Opus 4.5 (Thinking), reaches 33.5% accuracy, with a steep drop-off for other models. Analysis indicates that frequent code execution correlates with success, while excessive search without execution correlates with failure. Evaluation costs range from $0.05 to $1.34 per problem and latency averages between 20 minutes and over 3 hours.

## Method Summary
The benchmark evaluates models via an agentic harness. Each problem consists of a natural-language description paired with a Lean 4 formal statement. The model receives a system prompt emphasizing Lean 4 syntax and a user prompt with the problem and tool guidance. Over up to 40 turns, the model may call up to 6 tools per turn, choosing among `lean_loogle` (searches Mathlib via loogle.lean-lang.org), `lean_run_code` (executes Lean snippets in a sandbox and returns kernel feedback), and `submit_proof` (final submission). The Lean execution environment uses version 4.25.2 with Mathlib at commit c98ae54af. Proofs are accepted only if they compile without `sorry` or `axiom`; the kernel’s binary signal determines success. The harness logs tool usage, latency, token counts, and computes costs based on provider pricing. Problems were curated from qualifying exams and standard textbooks to be formalizable with current Mathlib yet beyond olympiad-level difficulty. The full benchmark is private to prevent data contamination.

## Key Results
- Claude Opus 4.5 (Thinking) achieves 33.5% pass rate; the next best model scores 18.5%, with performance dropping sharply thereafter.
- Higher frequency of `lean_run_code` calls correlates with success; excessive `lean_loogle` without execution correlates with failure.
- Evaluation cost per test ranges from $0.05 to $1.34; latency averages 20 minutes to over 3 hours.

## Why This Works (Mechanism)

**Mechanism 1: Binary correctness via Lean kernel**
- Claim: Formal verification using the Lean 4 kernel provides a binary, automated correctness signal that eliminates grading ambiguity.
- Mechanism: The kernel acts as a deterministic oracle; proofs either type-check and compile or they fail.
- Core assumption: The formal statement accurately reflects the problem intent, verified by secondary human review.
- Evidence: The abstract states the benchmark provides a binary automated correctness signal. Page 2 clarifies each task pairs natural language with a Lean statement and the model must output a proof accepted by the kernel.
- Break condition: Misformalization could invalidate results despite the review process.

**Mechanism 2: Iterative refinement through code execution**
- Claim: Multi-turn agentic interaction with code execution enables iterative refinement through immediate feedback, correlating with success.
- Mechanism: Models receive up to 40 turns per problem; frequent `lean_run_code` calls provide rapid error feedback, allowing adjustment of tactics and statements.
- Core assumption: Immediate feedback from Lean execution is more valuable than search-only strategies.
- Evidence: Page 7 reports higher rates of code execution feedback correlate with stronger success and that models executing code can iterate toward correct solutions. Page 4 lists the tools and their feedback types.
- Break condition: Excessive `lean_loogle` calls without execution lead to failure trajectories, as models may search for non-existent lemmas.

**Mechanism 3: Problem selection at the frontier**
- Claim: Selecting problems at the graduate/advanced undergraduate boundary within current Mathlib creates a meaningful evaluation frontier.
- Mechanism: Problems from qualifying exams and textbooks require knowledge beyond olympiad style, yet are constrained by what can be formalized and solved with existing Mathlib lemmas, ensuring solvability while maintaining difficulty.
- Core assumption: Mathlib contains sufficient coverage and models can retrieve and apply needed theorems.
- Evidence: Page 3 details curation criteria (beyond olympiad, formalizable with current Mathlib) and sources (qualifying exams, textbooks). Page 9 shows subject distribution.
- Break condition: As Mathlib grows, problems may become easier; conversely, new problems may exceed current model capabilities, creating a moving target.

## Architecture Onboarding

**Component Map**
The evaluation pipeline consists of seven components: Problem Loader, Agent Orchestrator, Tool Dispatcher, Lean Execution Service, Model Adapter, Metrics Logger, and Cost Calculator.

**Critical Path**
The core loop is: Problem Loader → Agent Orchestrator → (Model Adapter → Tool Dispatcher → Lean Execution Service) repeated across turns; upon `submit_proof`, the Lean kernel validates the proof and the Metrics Logger and Cost Calculator process the outcome.

**Design Tradeoffs**
- 40‑turn limit vs. unlimited iteration: bounds cost/latency but may cut off near‑miss proofs.
- 6 tool calls per turn vs. sequential execution: allows parallel hypothesis testing but complicates prompt construction and may encourage wasteful calls.
- Private benchmark vs. public release: prevents data contamination but hinders external replication and community analysis.
- Lean 4 specificity vs. multi‑prover support: deep integration with Mathlib simplifies tooling but lacks portability to other proof assistants.

**Failure Signatures**
- No `submit_proof` within 40 turns (automatic failure).
- Submission contains `sorry` or `axiom` (explicit rejection).
- Repeated `lean_loogle` calls without subsequent `lean_run_code` (correlated with failure trajectories).
- Continuous type errors or missing lemmas (poor retrieval or misuse).
- Instance resolution failures (e.g., “failed to synthesize” errors).
- Syntax/tactic mismatches (e.g., unknown tactic names).
- Misformalization of problem statements (systematically low success across models).

**First Experiments**
1. Verify the tool chain by submitting a trivial, known‑correct proof (e.g., `theorem trivial : True := by trivial`) through the full pipeline.
2. Establish baseline model behavior using a low‑cost model (e.g., GPT‑5 Nano) to instrument tool‑call distribution and confirm turn counting and per‑turn limits.
3. Test search utility on a problem requiring a recent or uncommon lemma; confirm `lean_loogle` retrieves it and the model can incorporate it into a successful proof.

## Limitations
- The benchmark is private, preventing independent replication and verification.
- Tool implementations (e.g., `lean_loogle` API, `lean_run_code` sandbox) are underspecified, making exact reproduction difficult.
- Model configurations (exact versions, sampling parameters) are not fully documented, further hindering reproducibility.
