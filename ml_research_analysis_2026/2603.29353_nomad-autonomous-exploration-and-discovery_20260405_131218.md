# Nomad: Autonomous Exploration and Discovery

## Quick Facts
- arXiv ID: 2603.29353
- Source URL: https://arxiv.org/abs/2603.29353
- Reference count: 40
- Primary result: Nomad significantly outperforms query-driven baselines on trustworthiness, factuality, quality, and diversity, achieving 70.4% numeric grounding and 0.427 inter-run diversity on UN/WHO reports.

## Executive Summary
Current question-answering systems explore only a narrow slice of data defined by user queries, missing broader insight spaces. Nomad addresses this by autonomously exploring an entire corpus without a fixed query. It constructs an explicit Exploration Map (a hierarchical topic tree), systematically traverses it breadth‑first, generates hypotheses via an explorer agent, verifies claims with an independent verifier, and produces cited reports and meta‑reports.

In evaluations on UN/WHO reports, Nomad substantially outperformed state‑of‑the‑art baselines (o3‑deep‑research, GPT Researcher) on trustworthiness (numeric grounding 70.4% vs 34.9% and 17.3%; factuality 65.2% vs 40.2% and 28.5%), overall quality (61.0 vs 54.2 and 42.5), and inter‑run diversity (0.427 vs 0.208 and 0.088). These gains demonstrate the effectiveness of structured exploration and verification for reliable, high‑quality insight discovery.

## Method Summary
Nomad’s pipeline begins with Exploration Map construction. The map can be built bottom‑up from the corpus: documents are chunked, concepts extracted via LLM, disambiguated, and scored for insight potential. Concepts are embedded, clustered (UMAP + HDBSCAN), and a hierarchical Topic Tree is generated by prompting an LLM. Alternatively, the map can be built top‑down from a user goal and web results. The topic selector then traverses the tree breadth‑first, always choosing the least explored leaf, and for leaves without unexplored hypotheses it generates a batch of candidate hypotheses scored for relevance, impact, and diversity.

Selected hypotheses enter an explorer‑verifier loop. The explorer agent uses ReAct with sub‑agents for document search, web search, and SQL queries to iteratively gather evidence and refine the hypothesis into an insight. An independent verifier decomposes the insight into atomic sub‑claims and, using its own tool calls, checks each claim against the sources. Only insights achieving a verification threshold proceed. Verified insights feed into a structured report generator: it first creates an outline with report‑ and section‑level throughlines, then fills each section sequentially while adhering to the outline and evidence, and finally runs a citation auditor to repair missing or incorrect citations. Meta‑reports are produced by clustering highlights from multiple reports. The system relies solely on pretrained LLMs (e.g., azure‑o3, Llama‑3.3‑70B) with prompting and tool use; no training is involved.

## Key Results
- **Trustworthiness**: numeric grounding 70.4% (o3‑deep‑research: 34.9%, GPT Researcher: 17.3%); factuality 65.2% (40.2%, 28.5%).
- **Quality**: overall score 61.0 (54.2, 42.5).
- **Diversity**: inter‑run diversity 0.427 (0.208, 0.088).

## Why This Works (Mechanism)

### Mechanism 1
- **Claim**: The Exploration Map’s breadth‑first traversal ensures broad coverage and diverse insights across the corpus, preventing the system from converging on a narrow set of high‑probability topics.
- **Mechanism**: The Exploration Map (a hierarchical Topic Tree) is constructed either top‑down from the goal and web results or bottom‑up from document concepts. During exploration, the topic selector moves level‑wise, always choosing the child node with the lowest exploration score, i.e., the least explored subtopic. This systematic breadth‑first search forces the agent to sample across heterogeneous regions before deepening, generating hypotheses from many different parts of the map.
- **Core assumption**: A hierarchical topic representation can approximate the space of valuable research directions, and exploring widely before going deep yields a more varied set of insights than following the most obvious high‑probability paths.
- **Evidence anchors**:
  - [abstract]: “constructs an explicit Exploration Map over the domain and systematically traverses it to balance breadth and depth.”
  - [section 3.2]: Algorithm 4 (Topic Selection) and the description of the insight potential and exploration scores that drive breadth‑first traversal.
  - [corpus]: The neighboring systems (e.g., QUIS, AutoDiscovery, InsightEval) rely on question‑guided or surprise‑driven searches without a structured map, which the paper argues leads to narrow coverage and redundant insights; Nomad’s map is a direct response.
- **Break condition**: If the initial topic hierarchy is poorly structured (e.g., missing entire relevant domains or grouping dissimilar concepts), breadth‑first traversal may still fail to cover the full insight space. Similarly, a corpus with extremely high dimensionality might require a much larger map than feasible.

### Mechanism 2
- **Claim**: The independent verifier loop filters unsupported claims and reduces hallucinations, leading to more trustworthy reports.
- **Mechanism**: After the explorer agent proposes a candidate insight, the verifier agent (a separate instance with no access to the explorer’s reasoning) decomposes the insight into atomic sub‑claims and independently validates each using the same data sources (documents, web, databases). The verifier issues its own tool calls and assigns a binary score per sub‑claim. Only insights with an average score above a threshold are passed to reporting; otherwise, verifier feedback is fed back to the explorer for refinement.
- **Core assumption**: An independent agent, when given the same evidence, can reliably judge whether a claim is directly supported, and this separation prevents the explorer from over‑fitting to spurious correlations or fabricating details.
- **Evidence anchors**:
  - [abstract]: “candidate insights are then checked by an independent verifier before entering a reporting pipeline.”
  - [section 3.7]: Detailed verifier workflow, sub‑claim decomposition, and scoring, plus the explicit design choice to use a less creative but more faithful model for verification.
  - [corpus]: Related works such as Self‑RAG and Chain‑of‑Verification incorporate internal checks, but Nomad’s external verifier and the loop structure are distinct; the corpus lacks systems that use a separate agent for post‑exploration validation.
- **Break condition**: If the verifier is too strict (e.g., requiring direct quotes for complex inferences), valid but nuanced insights may be rejected; if too lenient, hallucinations pass through. A weak verifier model or mismatched tool capabilities could also fail to catch unsupported claims.

### Mechanism 3
- **Claim**: The structured report generation pipeline—with outline planning, throughline enforcement, and citation auditing—produces coherent, well‑cited, and readable reports, improving overall quality.
- **Mechanism**: Given a verified insight and its trace, the report generator first creates a detailed outline that includes a report‑level throughline and section‑level throughlines, each assigned a specific type (text, table, chart, etc.). Sections are then filled sequentially, constrained by the outline and the evidence. A citation auditor subsequently repairs missing or incorrect citations by comparing claims to the citation database. This staged process mitigates common LLM pitfalls like drift, repetition, and unsupported assertions.
- **Core assumption**: Explicit narrative planning (throughlines) and strict adherence to a fixed schema per section type yield more reliable long‑form outputs than free‑form generation.
- **Evidence anchors**:
  - [abstract]: “reporting pipeline that produces cited reports and higher‑level meta‑reports.”
  - [section 4]: The complete report generation workflow, including outline generation, throughlines, section generation with type constraints, and citation auditing.
  - [corpus]: Systems like GPT Researcher and STORM also use outline‑based generation, but Nomad’s emphasis on throughlines and the post‑hoc citation auditor are additional guardrails not commonly present; the corpus indicates that hallucination and poor coherence remain open problems.
- **Break condition**: If the outline generation misunderstands the throughline or omits critical evidence, the report will be narratively incoherent. If the citation database is incomplete or the auditor is inaccurate, trustworthiness suffers. Extremely long traces might also exceed context limits during section filling.

## Foundational Learning
- **Concept: Exploration Map (Topic Tree)**
  - Why needed here: The map is the central control state; understanding its construction (concept extraction, clustering, LLM‑based hierarchy generation) and traversal (breadth‑first with insight potential scores) is essential to predict what the system will explore.
  - Quick check question: “How does the insight potential score influence which hypotheses get generated, and how does the topic selector balance breadth and depth?”
- **Concept: Explorer–Verifier Loop**
  - Why needed here: This loop is the engine that turns a hypothesis into a verified insight. The engineer must know the loop structure (observe‑reason‑act), hypothesis action types (REFINE, REVISE, KEEP, VALIDATE_FURTHER, USER_RESPONSE), and how verifier feedback is integrated.
  - Quick check question: “What happens when the verifier returns a low score for an insight? How does the explorer adjust its next turn?”
- **Concept: Report Throughline and Section Types**
  - Why needed here: The throughline is the narrative backbone that guides outline creation and section filling; section types impose structure. Without understanding these, an engineer cannot debug report quality issues.
  - Quick check question: “Why is a ‘throughline’ required at both report and section levels, and how does the citation auditor repair citations without altering content?”

## Architecture Onboarding
- **Component map**:
  - Preprocessing: Document chunking, concept extraction, metadata extraction (Section 3.2.3).
  - Exploration Map Builder: Bottom‑up (concept layer → Topic Tree) or top‑down construction; web‑augmentation module (Section 3.2, 3.3).
  - Topic Selector: Breadth‑first traversal, hypothesis generation pool, scoring (Section 3.4, 3.5).
  - Explorer Agent: ReAct loop with tool sub‑agents (document: Appendix B.3; web: Appendix B.5; SQL: Appendix B.4) (Section 3.6).
  - Verifier Agent: Sub‑claim decomposition, independent tool use, scoring (Section 3.7).
  - Report Generator: Outline → title/summary → section filling → citation auditing → poster (Section 4.1–4.6).
  - Meta‑Report Generator: Highlight extraction, entity‑based clustering, progressive refinement (Section 4.7).
- **Critical path**:
  1. Build or load Exploration Map.
  2. Select leaf topic with unexplored hypotheses (or generate new ones).
  3. Run explorer‑verifier loop for the chosen hypothesis.
  4. If verified, generate a standalone report and store it.
  5. When enough reports exist, trigger meta‑report generation.
  6. Repeat 2‑5 until a compute/time budget or coverage goal is met.
- **Design tradeoffs**:
  - Map‑guided breadth‑first vs. MCTS‑style adaptive traversal: Breadth‑first is simple and ensures diversity, but may waste time on dead ends. Future work considers MCTS based on insight novelty.
  - Independent verifier adds latency but is essential for trust; the tradeoff is cost vs. reliability.
  - Structured report generation limits narrative freedom but improves coherence; free‑form might yield more creative but less reliable outputs.
  - Bottom‑up map construction leverages corpus specifics but may miss broader context that top‑down (goal‑driven) capture.
- **Failure signatures**:
  - **Low diversity across runs**: Reports have near‑identical titles/scope (as in GPT Researcher’s Table 1). Check that breadth‑first selection is functioning and hypothesis generation diversity scoring (weight `w_d`) is effective.
  - **Low numeric grounding/factuality**: Many numeric claims ungrounded or unsupported. Inspect the citation database integrity and verifier strictness (threshold). Also check if the explorer is over‑relying on web snippets without deep verification.
  - **High report redundancy**: Sections repeat information within a single report. Look at the distinctness metric and examine the outline; likely the throughline is weak or the explorer trace lacks sufficient evidence to fill multiple distinct sections.
  - **Excessive latency**: Explorer loops taking many turns or verifier retries. Audit tool call efficiency (e.g., document search sub‑agent reflection loops, SQL semantic resolution) and turn budgets (`max_explorer_turns`, `max_verifier_turns`).
- **First 3 experiments** for a new engineer:
  1. **Map inspection**: Run Nomad on the small WHO corpus and visualize the Exploration Map (nodes and edges). Verify that concept disambiguation and topic tree construction produced coherent subtopics and that leaf nodes have hypothesis children.
  2. **Single loop debugging**: Manually trigger one hypothesis from a leaf node and capture the full explorer‑verifier transcript. Check that the explorer correctly classifies its hypothesis action and that the verifier’s sub‑claims align with the final insight.
  3. **Report quality ablation**: Compare reports with and without the citation auditor. Measure the change in numeric grounding and factuality scores. Also try varying the outline generation (e.g., force more sections) to observe the impact on distinctness.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question**: How can inter-concept relationships be explicitly modeled in the Exploration Map to enable subgraph-based hypothesis generation and anomaly detection?
- **Basis in paper**: [explicit] "One is to move beyond the current structure, in which inter‑concept relationships are not central, and model those relationships more explicitly. This would open up subgraph analysis, pattern and anomaly detection, and hypothesis generation from subgraphs."
- **Why unresolved**: The current map represents concepts as nodes without explicit relational edges, limiting the system’s ability to analyze connected subgraphs that might reveal non‑obvious patterns or generate hypotheses from their structure.
- **What evidence would resolve it**: Build a graph‑based Exploration Map with typed edges (e.g., causal, co‑occurrence), generate hypotheses via subgraph traversal, and compare insight novelty and coverage against the current implementation.

### Open Question 2
- **Question**: Does MCTS traversal on the Exploration Map improve insight diversity and originality compared to breadth‑first traversal?
- **Basis in paper**: [explicit] "The current system uses breadth‑first topic selection only, but it would be useful to study exploration–exploitation tradeoffs more directly – where branches in the exploration map are scored by the originality of insights generated in the corresponding subtree. This would enable MCTS‑style traversals on the exploration map."
- **Why unresolved**: Breadth‑first ensures wide coverage but may under‑exploit highly original branches; MCTS could focus on promising subtrees but risks reducing overall diversity or missing emergent connections.
- **What evidence would resolve it**: Run Nomad with MCTS vs. breadth‑first traversal on identical maps, measure inter‑report diversity (embedding distance) and semantic distinctness of insights across multiple runs.

### Open Question 3
- **Question**: What is the quantitative contribution of the independent verifier to report trustworthiness, and how does verification thoroughness trade off with exploration depth?
- **Basis in paper**: [explicit] "On the evaluation side, better metrics are needed for discovery systems, including measures of diversity and non‑redundancy of insights, and quantifying how the verifier contributes to trustworthiness."
- **Why unresolved**: The verifier’s role in filtering hallucinations is central to trustworthiness, but its isolated impact (e.g., reduction in numeric grounding failures) is not measured; also, the cost of deeper verification vs. exploration breadth is unstudied.
- **What evidence would resolve it**: Ablation experiments comparing runs with verifier disabled, weakened, or with varying `max_verifier_turns`, evaluating trustworthiness metrics (numeric grounding, factuality) and insight yield per unit time.

### Open Question 4
- **Question**: How can the report generation pipeline be redesigned to increase intra‑report distinctness without sacrificing coherence or citation accuracy?
- **Basis in paper**: [explicit] "On distinctness within a report, both baselines outperform Nomad – we note this as a weakness of the current report generation system and an opportunity for improvement in future work."
- **Why unresolved**: The current outline‑driven sequential generation leads to moderate redundancy (distinctness score 53.4 bottom‑up), likely because sections may revisit similar evidence; improving this could enhance usability but risks fragmenting narrative flow.
- **What evidence would resolve it**: Introduce diversity‑promoting mechanisms (e.g., section‑level topic distribution constraints, mutual information penalties), evaluate distinctness, analytical quality, and citation accuracy on a held‑out set.

## Limitations
- Exact model versions, parameters, and embedding models are unreported, preventing precise replication.
- Corpus preprocessing details (chunk size, overlap, metadata extraction) and the exact UN/WHO corpus composition are not fully specified.
- A broad set of hyperparameters (exploration budgets, verifier thresholds, weights for hypothesis scoring) are missing; their values likely affect performance and may need domain‑specific tuning.

## Confidence
- Exploration Map breadth‑first traversal ensures diverse insights: **Medium confidence**.
- Independent verifier reduces hallucinations and improves trustworthiness: **High confidence**.
- Structured report generation improves quality: **Medium confidence**.

## Next Checks
1. **Ablation of the verifier**: Disable the verifier or replace it with a simple baseline on a held‑out subset; measure changes in numeric grounding and factuality to isolate the verifier’s contribution.
2. **Traversal strategy comparison**: Implement depth‑first or random topic selection as a drop‑in for breadth‑first; compare inter‑run diversity and coverage while keeping other components fixed.
3. **Hyperparameter sensitivity analysis**: Perform a grid search over key parameters (diversity weight `w_d`, hypothesis batch size, verification threshold) to assess robustness and identify critical values.
