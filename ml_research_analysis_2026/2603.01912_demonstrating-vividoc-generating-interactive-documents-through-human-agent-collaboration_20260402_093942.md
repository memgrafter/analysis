# Demonstrating ViviDoc: Generating Interactive Documents through Human-Agent Collaboration
## Quick Facts
- **arXiv ID:** 2603.01912
- **Source URL:** https://arxiv.org/abs/2603.01912
- **Reference count:** 8
- **Primary result:** ViviDoc substantially outperforms naive agentic generation in expert blind evaluation, scoring significantly higher in Content Richness (4.17 vs 2.07), Interaction Quality (4.00 vs 2.40), and Visual Quality (3.73 vs 2.37) on a 5-point scale.

## Executive Summary
ViviDoc addresses the challenge of creating interactive educational documents, which are costly to produce manually and yield unpredictable results from naive LLM agents. It introduces a human-agent collaborative system featuring a multi-agent pipeline (Planner, Executor, Evaluator) and the Document Specification (DocSpec), a structured intermediate representation that decomposes interactive visualizations into State, Render, Transition, and Constraint components. Educators review and refine the DocSpec before code execution, ensuring alignment with pedagogical intent. Expert evaluation on 10 topics shows ViviDoc achieves significantly higher quality than naive generation, and a user study confirms the DocSpec editing interface is intuitive and effective.

## Method Summary
The system employs a staged pipeline: a Planner agent generates a DocSpec by decomposing a topic into knowledge units, each with an SRTC Interaction Specification. A human educator reviews and edits this structured plan via a dedicated UI. An Executor agent then synthesizes text and code (HTML/CSS/JS) for each unit based on the finalized DocSpec. An Evaluator agent checks output coherence and HTML validity, triggering re-execution if needed. This decomposition isolates failure modes and leverages human oversight at a high level of abstraction, aiming to bridge the gap between pedagogical intent and executable interactive documents.

## Key Results
- Expert blind evaluation (N=10 topics) shows ViviDoc outperforms naive agentic generation: Content Richness (4.17 vs 2.07), Interaction Quality (4.00 vs 2.40), Visual Quality (3.73 vs 2.37) on a 5-point scale.
- User study (N unspecified) reports high usability for the DocSpec editing interface, with mean ratings between 4.33 and 5.0 across dimensions.

## Why This Works (Mechanism)
**Mechanism 1:** The Document Specification (DocSpec) reduces the intent-to-code translation gap by providing a structured, human-readable intermediate representation. The Planner decomposes topics into knowledge units with explicit SRTC components, forcing representation of pedagogical invariants (Constraints) and interaction logic before coding. Humans review this specification, aligning system output with intent. Evidence: DocSpec serves as a contract between stages. Break condition: If SRTC components are ambiguously defined or the human lacks expertise, the contract fails.

**Mechanism 2:** The multi-agent pipeline isolates failure modes through staged verification. Specialization allows each agent to focus on a specific subtask: Planner on structure/pedagogy, Executor on faithful code synthesis from a fixed spec, Evaluator on output validation. The Evaluator's feedback can trigger regeneration. Evidence: Evaluator checks quality and can trigger re-execution; substantial quality gap vs naive agent supports decomposition benefits. Break condition: Flawed DocSpec from Planner leads to downstream failures; Evaluator may miss high-level pedagogical flaws.

**Mechanism 3:** Strategic placement of human review after planning but before execution maximizes control and leverage. Edits at the DocSpec stage are high-level and low-cost (e.g., changing a slider range) compared to debugging generated code. Evidence: Human review spans pipeline; DocSpec edits are targeted; user study confirms interface effectiveness. Break condition: Inexperienced or disengaged human editors may fail to catch flawed plans, losing the early intervention benefit.

## Foundational Learning
- **Interactive Visualization Decomposition (Munzner's What-Why-How / SRTC):** The DocSpec's Interaction Specification adapts Munzner's framework (State, Render, Transition, Constraint). Understanding this separation is essential to interpret and edit ViviDoc's core representation. *Quick check:* For a "resistance circuit simulator," identify the pedagogical Constraint a learner should discover.
- **Guarded Generation via Intermediate Representations:** ViviDoc uses a formal, constrained IR (DocSpec) to guide LLM generation, contrasting with unconstrained single-prompt generation. The constraint acts as a "contract" improving reliability. *Quick check:* What are two ways a malformed DocSpec (e.g., Transition referencing undefined State variable) would cause Executor failure?
- **Human-in-the-Loop Timing and Leverage:** The system's design hinges on involving humans at the DocSpec stage, where edits are conceptual and low-cost versus code-level edits. *Quick check:* Compare effort of changing an interactive visualization's control from slider to dropdown at (a) DocSpec editing stage vs. (b) after viewing generated HTML file.

## Architecture Onboarding
**Component map:** Planner Agent → DocSpec Editor UI (Human) → Executor Agent → Evaluator Agent. The Orchestrator manages pipeline state and data flow between these components.

**Critical path:** Topic Input → Planner → DocSpec → Human Edit → Executor (Stage 1 & 2) → Generated HTML → Evaluator → [Pass: Final Document | Fail: Feedback to Orchestrator for targeted re-execution].

**Design tradeoffs:**
- Human control vs. automation speed: Mandatory DocSpec review introduces latency but is primary source of quality.
- Schema rigidity vs. expressivity: SRTC schema ensures controllability but may limit novel interaction patterns.
- Single LLM vs. multi-agent: Using same base model (Gemini 3.0 Flash) reduces complexity; gains come from decomposition, not agent-specific tuning.

**Failure signatures:**
- Planner: DocSpec with empty `unit_summary`, meaningless `text_description`, or `Interaction Specification` with undefined State variables referenced in Render/Transition.
- Executor: Repeated validation errors in Stage 2 (e.g., "variable not defined" in JS) indicating SRTC-code mismatch.
- Evaluator: Permissive coherence checks allowing documents with logical gaps; HTML validator is stronger.
- Human: User spends excessive time on DocSpec edits due to poor UI or overly complex SRTC.

**First 3 experiments:**
1. Planner Output Stability Test: For 5 diverse topics, generate 20 DocSpecs each. Measure variance in knowledge unit count, SRTC field completeness, and semantic similarity of descriptions.
2. Executor SRTC Fidelity Benchmark: Curate gold-standard DocSpec covering all SRTC patterns. Run Executor 30 times. Evaluate % of units correctly implementing all four SRTC components and behavioral conformance via automated tests.
3. Ablation: Human-in-the-Loop Timing: Within-subject study (N=12 educators). Condition A: Edit DocSpec; Condition B: Edit final HTML/JS. Measure time to satisfactory document, final quality, cognitive load.

## Open Questions the Paper Calls Out
1. **Generalization beyond education:** To what extent can ViviDoc and DocSpec be generalized to domains like interactive journalism or scientific publishing? *Basis:* Paper focuses on educational context; components tailored to pedagogical invariants. *Why unresolved:* Assumptions about knowledge units, interaction types, and correctness metrics are education-specific. *Evidence needed:* Apply pipeline to non-educational tasks with domain-specific invariants and evaluate against domain baselines.
2. **Evaluator reliability:** How robust is the Evaluator agent's LLM-based assessment as a substitute for human judgment? *Basis:* Evaluator is critical but unvalidated; no precision/recall data. *Why unresolved:* System's self-correction depends on uncalibrated Evaluator; evaluation results conflate all components. *Evidence needed:* Ablation with human expert judgments; measure agreement and analyze feedback impact.
3. **Impact of human edits:** What is the quantitative impact of human edits to DocSpec on output quality, and what edit types are most effective? *Basis:* User study measures usability but not edit impact; Section 5.1 experiment disabled human review. *Why unresolved:* Quality advantage attributed to DocSpec structure, not human editing; no data linking edits to quality delta. *Evidence needed:* Controlled experiment with/without editing, logging edits and correlating with expert scores.
4. **SRTC expressive power:** Does SRTC have sufficient expressivity for full spectrum of interactive visualizations, especially complex multi-view coordination? *Basis:* SRTC adapted from Munzner but examples focus on simple interactions; paper states support for common patterns only. *Why unresolved:* Unclear if SRTC can model multi-view linked filters or scripted transitions; dataset analysis not reported. *Evidence needed:* Formal analysis of 101-document dataset to categorize interaction types and test SRTC coverage; user testing with designers on complex examples.
5. **Scaling limitations:** What are scaling limits regarding document length, interaction complexity, and LLM context window? *Basis:* No discussion of DocSpec size or Executor context handling; retry mechanism implies failures. *Why unresolved:* Evaluation on 10 topics without characterizing complexity; long documents may challenge Planner coherence or context limits. *Evidence needed:* Stress-test with long DocSpecs (50+ units); measure Planner validity, Executor success rate, completeness, and quality vs. document length.

## Limitations
- Planner output stability is unquantified; high variance would undermine the "contract" premise.
- Evaluator agent's judgment is unvalidated against human experts, risking undetected flaws or unnecessary regeneration.
- The impact of human edits on final quality is not isolated; the system comparison used disabled editing, so DocSpec structure alone may drive improvements.
