# MemArchitect: A Policy Driven Memory Governance Layer

## Quick Facts
- **arXiv ID:** 2603.18330
- **Source URL:** https://arxiv.org/abs/2603.18330
- **Reference Count:** 12
- **Primary Result:** Achieves a +7.45% average accuracy gain over baseline memory systems on LoCoMo-10, with a +39.2% improvement in temporal reasoning versus SimpleMem.

## Executive Summary
Persistent LLM agents suffer from a "Governance Gap" where passive memory storage leads to contradictions, privacy violations, and stale "zombie memories." MemArchitect introduces a decoupled, policy-driven middleware layer that actively governs the memory lifecycle, consistency, retrieval, and efficiency. Evaluated on the LoCoMo-10 benchmark against SimpleMem and MemOS, it demonstrates that active governance shifts failure modes from hallucination (common in SimpleMem) to tunable over-pruning, improving open-domain and multi-hop coherence at a calculable cost in raw recall.

## Method Summary
The proposed system acts as a middleware layer between an LLM agent and its persistent memory store. It ingests administrator-defined policies that encode rules for memory creation, updates, retrieval, pruning, and access control. During operation, the layer intercepts memory operations (writes, reads, deletes) and enforces these policies in real-time. For example, a temporal consistency policy might prevent the storage of a fact that contradicts a newer, higher-confidence entry, while a privacy policy could trigger automatic expiration of sensitive data. The evaluation compares this governed approach against two baselines: SimpleMem (passive storage) and MemOS (a maximalist, ungoverned system) using the LoCoMo-10 long-conversation benchmark, measuring accuracy, recall, and coherence across reasoning types.

## Key Results
- Outperforms SimpleMem by +7.45% in average accuracy, with a dominant +39.2% gain in temporal reasoning tasks.
- Versus the recall-focused MemOS, improves open-domain coherence (+11.3%) and multi-hop coherence (+4.1%) by reducing context pollution.
- Explicitly sacrifices some raw recall compared to MemOS, demonstrating a deliberate governance trade-off between memory completeness and consistency.

## Why This Works (Mechanism)
MemArchitect works by shifting the memory system from a passive, append-only model to an actively governed one. Instead of allowing contradictions and staleness to accumulate (the "zombie memory" problem), policies provide deterministic rules for resolving conflicts, enforcing freshness, and controlling access. This reduces the contextual noise that leads to hallucination in models like SimpleMem. The trade-off with MemOS shows that raw, unpruned recall can harm coherence; governance filters noise at the cost of some signal, moving failure modes from unpredictable hallucinations to a more controllable pattern of over-pruning, which can be tuned via policy parameters.

## Foundational Learning
- **Persistent LLM Agents:** Agents that maintain state/memory across multiple sessions. *Why needed:* Supports long-term interaction and personalization. *Quick check:* Can the agent recall a user's stated preference from 100 turns ago?
- **Memory Governance Gap:** The lack of active management in memory systems, leading to contradictions, privacy risks, and outdated content. *Why needed:* Identifies the core problem MemArchitect solves. *Quick check:* Does a baseline system store two contradictory facts from different sessions?
- **Policy-Driven Systems:** Systems where behavior is defined by declarative rules rather than hard-coded logic. *Why needed:* Allows flexible, auditable governance without modifying core agent code. *Quick check:* Can an admin change a data retention rule without redeploying the agent?
- **Memory Lifecycle Management:** Active control over creation, update, archival, and deletion of memories. *Why needed:* Prevents unbounded growth and staleness. *Quick check:* Are old, superseded facts automatically invalidated?
- **Consistency Enforcement:** Mechanisms to detect and resolve contradictory information in memory. *Why needed:* Maintains a coherent world model for the agent. *Quick check:* If "X is true" and later "X is false" are stored, which is retrievable?
- **Retrieval Filtering:** Applying governance policies during the memory retrieval phase (e.g., filtering by privacy tags). *Why needed:* Prevents prohibited information from reaching the agent's context. *Quick check:* Does a "HIPAA-compliant" policy block patient data from being returned?

## Architecture Onboarding
**Component Map:** Policy Interpreter -> Lifecycle Manager -> Consistency Enforcer -> Retrieval Filter -> Pruning Scheduler -> Memory Store

**Critical Path:** A memory write is intercepted by the Policy Interpreter, which validates it against lifecycle and consistency policies. The Lifecycle Manager may modify metadata (e.g., set expiration). On a read query, the Retrieval Filter applies access and relevance policies before returning results. The Pruning Scheduler periodically runs to enforce archival/deletion policies.

**Design Tradeoffs:** 
- Governance overhead (latency, compute) vs. improved coherence and safety.
- Recall (completeness) vs. precision (consistency). MemArchitect accepts lower raw recall for higher coherence.
- Policy expressiveness vs. specification complexity. Rich policies are powerful but harder to define correctly.

**Failure Signatures:**
- **Over-pruning:** Valid memories deleted due to overly aggressive policies, manifesting as a sharp drop in recall.
- **Policy Conflict:** Contradictory policies (e.g., "retain forever" vs. "expire in 1 day") causing enforcement deadlock or unexpected precedence.
- **Latency Spikes:** Policy evaluation becoming a bottleneck during high-throughput retrieval.

**First Three Experiments:**
1. **Contradictory Policy Stress Test:** Define two opposing policies (e.g., one requiring all data retention, another demanding immediate deletion of PII). Observe resolution behavior (e.g., policy precedence logs) and impact on memory contents.
2. **Recall-Coherence Curve:** Vary the aggressiveness of a single pruning policy (e.g., age threshold) and measure the trade-off between raw recall (vs. MemOS) and multi-hop coherence. Identify the "knee" of the curve.
3. **Zombie Memory Audit:** Using a modified LoCoMo-10 where facts are deliberately contradicted in later sessions, compare the count of stale, contradicted memories remaining in the store across MemArchitect, SimpleMem, and MemOS.

## Limitations
- **Implementation Opacity:** The paper lacks details on the policy language, enforcement engine internals, and integration APIs, hindering reproducibility.
- **Policy Specification Burden:** The difficulty for non-expert administrators to author correct, non-conflicting policies is unaddressed, posing a major usability risk.
- **Adversarial & Edge Robustness:** Unknown performance under dynamic schema evolution, ambiguous policy interpretations, or adversarial environments designed to trigger governance failures.

## Confidence
- **High:** The specific +39.2% temporal reasoning improvement over SimpleMem is a direct, quantitative result from the evaluation.
- **Medium:** The claim that governance shifts failure modes (hallucination → over-pruning) is inferred from comparative coherence gains (+11.3%, +4.1%) vs. MemOS but not directly isolated.
- **Medium:** The severity of the "Governance Gap" (contradictions, privacy violations, zombie memories) is supported by cited literature but not empirically measured in the baseline conditions of this study.
- **Low:** Qualitative claims about overall "active governance" efficacy and the efficiency trade-off lack quantified metrics (e.g., added latency, memory overhead).
