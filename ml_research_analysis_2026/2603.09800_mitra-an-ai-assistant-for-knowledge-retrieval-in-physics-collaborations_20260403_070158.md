# MITRA: An AI Assistant for Knowledge Retrieval in Physics Collaborations

## Quick Facts
*   **arXiv ID:** 2603.09800
*   **Source URL:** https://arxiv.org/abs/2603.09800
*   **Reference Count:** 21
*   **Primary Result:** A fully on-premise RAG system for CMS internal documents that significantly outperforms BM25 on realistic, paraphrased expert queries (P@1 0.75 vs 0.13, MRR 0.81 vs 0.35).

## Executive Summary
Large physics collaborations like CMS generate vast internal documentation, creating a navigational challenge where traditional keyword search fails to capture semantic context and external AI APIs raise privacy and cost concerns. MITRA is a purpose-built, on-premise Retrieval-Augmented Generation (RAG) pipeline that automates the ingestion of internal analysis documents and provides accurate, cited answers to domain-specific queries. It employs a two-tier vector database architecture to first identify the relevant analysis and then retrieve from its full text, using specialized embeddings and reranking before generating answers with a local quantized LLM. Evaluated on expert queries, MITRA shows a substantial performance advantage over BM25 on paraphrased questions while demonstrating robustness against hallucinations.

## Method Summary
MITRA's pipeline begins with automated document retrieval from internal databases using Selenium. Extracted PDFs undergo high-fidelity text and layout parsing via Surya and Tesseract. Documents are chunked by paragraph. A two-tier retrieval system first uses a vector database of document abstracts (embedded with a DPR model) to identify the target analysis, then searches a second vector database containing only that analysis's full-text chunks. Retrieved passages are reranked with a cross-encoder. Finally, a 4-bit quantized Mistral-7B LLM, running on-premise via Ollama, generates a grounded answer citing the retrieved context.

## Key Results
*   On paraphrased expert queries, MITRA dramatically outperforms BM25: Precision@1 (0.75 vs 0.13), Mean Reciprocal Rank (0.81 vs 0.35), and NDCG@5 (0.88 vs 0.59).
*   Performance on exact-match queries is comparable to BM25, validating the system's strength in semantic understanding.
*   The system robustly avoids hallucinations, correctly refusing to answer when retrieved context is unrelated to the query.

## Why This Works (Mechanism)
MITRA's effectiveness stems from its domain-specific design choices that directly address the failure modes of generic search in a complex knowledge base. The two-tier retrieval architecture is critical: by first selecting the correct analysis via abstracts, it prevents the "cross-analysis confusion" that would occur if a single vector database searched all documents, where chunks from different studies on similar topics would compete. The on-premise deployment with a quantized model eliminates API costs and data privacy risks for a large collaboration, while the use of specialized neural retrievers (DPR for embeddings, cross-encoder for reranking) provides the semantic matching necessary for paraphrased physics queries that keyword search (BM25) cannot handle. Finally, grounding the LLM's generation explicitly on the retrieved context, coupled with the high-fidelity OCR pipeline, ensures answers are traceable and reduces hallucination risk.

## Foundational Learning
*   **Retrieval-Augmented Generation (RAG):** Why needed: Augments an LLM with external, specific knowledge to improve accuracy and reduce hallucinations. Quick check: Can the system cite exact passages from source documents for its answers?
*   **Dense Passage Retrieval (DPR):** Why needed: Generates embeddings specifically optimized for question-answer matching, superior to general-purpose embeddings for semantic search in a QA context. Quick check: Does the system perform better with DPR embeddings than with a generic model like `all-MiniLM-L6-v2`?
*   **Cross-Encoder Reranking:** Why needed: Provides a more precise, computationally intensive relevance score for a shortlist of candidates, improving ranking quality after a fast first-stage retrieval. Quick check: Is there a measurable gain in MRR/NDCG when adding a cross-encoder step after DPR retrieval?
*   **Quantized On-Premise LLM:** Why needed: Balances model capability with hardware constraints and eliminates per-query API costs and data exfiltration risks for sensitive internal data. Quick check: Does the 4-bit quantized model's answer quality degrade significantly compared to a full-precision variant on the target domain?
*   **Two-Tier/Hierarchical Retrieval:** Why needed: Disambiguates the target document (analysis) from the corpus before performing expensive full-text search, crucial for collections with many thematically similar documents. Quick check: What is the failure rate when the abstract-retrieval stage selects the wrong analysis?
*   **Layout-Aware OCR:** Why needed: Physics documents feature complex layouts (multi-column, equations, figures); standard OCR merges text incorrectly, destroying semantic structure. Quick check: Does the extracted text maintain correct reading order and separation of sections/tables compared to the source PDF?

## Architecture Onboarding
**Component Map:**
Internal DB (PDFs) -> Selenium (Download) -> Surya/Tesseract (OCR/Text) -> Paragraph Chunker -> Abstract Summarizer -> Abstract Vector DB (DPR) -> Query -> Abstract DB Search -> Selected Analysis ID -> Full-Text Vector DB (Chunks for that Analysis) -> Cross-Encoder Rerank -> Top-k Passages -> Quantized Mistral-7B (Prompted) -> Cited Answer

**Critical Path:** Query -> Abstract DB Search -> Full-Text DB Search -> Cross-Encoder Rerank -> LLM Generation. The abstract-selection step is the mandatory gatekeeper.

**Design Tradeoffs:**
1.  **Two-Tier vs. Single Vector DB:** The two-tier design adds latency and a potential failure point (wrong analysis selection) but is necessary to avoid catastrophic confusion in a corpus of highly similar analysis notes. A single DB would be simpler but likely fail on ambiguous queries.
2.  **On-Premise vs. External API:** On-premise avoids recurring costs and privacy issues but requires hardware management, model maintenance, and limits model choice/size. The tradeoff is justified for a large, permanent collaboration with sensitive data.
3.  **DPR + Cross-Encoder vs. Single Retriever:** The two-stage retrieval balances speed (DPR for broad search) and precision (cross-encoder for fine ranking). The cost is increased system complexity and latency.

**Failure Signatures:**
*   **OCR/Layout Failure:** Garbled text output, merged columns, unreadable equations in the extracted `.txt` files. Propagates to nonsensical retrieval.
*   **Abstract-Tier Misidentification:** The system consistently retrieves full-text from an analysis that is topically adjacent but incorrect for the query, leading to answers that are plausible but wrong.
*   **Cross-Encoder Failure:** The reranker fails to move a truly relevant passage into the top-k fed to the LLM, causing a correctible retrieval failure at the final stage.

**First 3 Experiments:**
1.  **OCR Fidelity Audit:** Manually extract text from a stratified sample of 50 complex CMS PDFs (vintage scans, multi-column, heavy math). Compute character error rate (CER) and structural accuracy (section heading detection) against human transcription. Tune Surya/Tesseract parameters.
2.  **Abstract Retrieval Isolation Test:** Create a test set of 100 queries with a known target analysis. Run *only* the abstract DB search (bypassing full-text). Measure top-1 and top-3 accuracy in selecting the correct analysis document. This isolates the first stage's failure rate.
3.  **Proxy Query Benchmark:** Generate a surrogate evaluation set. Take 20 public CMS analysis summaries (e.g., from CDS), manually write 2-3 paraphrased questions per summary that could be answered by the full note. Use these to run the full MITRA pipeline and establish a baseline performance metric, approximating the unreleased expert query set.

## Open Questions the Paper Calls Out
1.  How does MITRA's performance scale when expanding beyond analysis notes to include other internal document types (e.g., wikis, procedural guidelines, emails), and what modifications to the chunking and embedding pipeline are necessary?
2.  What is the quantitative impact of the two-tiered database architecture on preventing cross-analysis confusion in scenarios with highly similar or overlapping analyses, and does the human-in-the-loop confirmation step become a bottleneck for user adoption?
3.  For a large collaboration with thousands of users, what are the concrete trade-offs in cost, latency, and throughput between the proposed on-premise deployment using a quantized Mistral-7B and a hypothetical optimized external API solution, under realistic query loads?
4.  How robust is the OCR and layout parsing pipeline (Surya, Tesseract) to the typical quality degradation and varied formatting found in decades of legacy PDF documents from a physics collaboration, and what is its error propagation effect on final answer quality?
5.  To what extent does the current RAG generation step introduce subtle hallucinations or unsupported inferences even when retrieved context is relevant, and how do "LLM-as-a-judge" faithfulness metrics correlate with expert human evaluation in the physics domain?

## Limitations
*   **Major Uncertainty 1:** The exact expert query sets and their relevance judgments are not released, preventing independent verification of the reported performance gains over BM25.
*   **Major Uncertainty 2:** The automated Selenium retrieval depends on proprietary internal CMS database structures and authentication, making end-to-end reproduction impossible without access to those private systems.
*   **System Limitation:** The two-tier retrieval design is optimized for queries belonging to a single analysis; its robustness for inherently cross-analysis or ambiguous queries has not been evaluated.

## Confidence
*   **High Confidence:** The described pipeline implementation (OCR, two-tier vector DB, DPR + cross-encoder, quantized Mistral) is technically sound and follows established RAG patterns.
*   **Medium Confidence:** The specific performance claims (P@1=0.75, MRR=0.81, etc.) on paraphrased queries, as the unreleased test set prevents replication.
*   **Low Confidence:** The generalizability of these results to the full, unfiltered spectrum of user questions in a live, large-scale collaboration environment.
