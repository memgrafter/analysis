# ReplicatorBench: Benchmarking LLM Agents for Replicability in Social and Behavioral Sciences

## Quick Facts
- arXiv ID: 2602.11354  
- Source URL: https://arxiv.org/abs/2602.11354  
- Reference count: 40  
- Primary result: LLM agents excel at experiment design and execution but critically struggle with data retrieval and accurate final replicability judgments.

## Executive Summary
ReplicatorBench is a novel benchmark for evaluating LLM agents on the full replication pipeline in social and behavioral sciences. It comprises 19 human-verified cases with both replicable and non-replicable outcomes. The benchmark assesses agents across three stages: Extraction of claims and retrieval of new data, computational experiment generation (including Docker container orchestration), and result interpretation against preregistered criteria. Testing with GPT-4o, GPT-5, GPT-5-mini, and o3 reveals that agents achieve strong execution and interpretation scores (e.g., GPT-5: 96.20 execution LLMEval, 93.35 interpretation LLMEval) but perform poorly on data retrieval (hit@any up to 63.16%) and exhibit a significant gap between successful execution and accurate binary outcome classification (macro F1 up to 77.38%). These findings highlight that current LLM agents cannot reliably translate computational success into correct scientific judgment and lack robust open-world retrieval skills needed for real-world replication.

## Method Summary
The benchmark evaluates agents via ReplicatorAgent, an agentic framework following a ReAct-style thought-action loop. Inputs include the original paper PDF, a claim definition, and a workspace containing a new dataset. The agent proceeds through three stages: Extraction (extract structured claim information, perform web search for replication data), Generation (preregister a replication plan, design a Docker environment, execute the analysis with iterative debugging), and Interpretation (compare results to original, judge criteria met/unmet). Tools enable file operations, dataset queries, and Docker orchestration. Outputs are stage-specific JSON files. Evaluation uses an LLM-as-a-judge (GPT-4o) to score 1,568 checkpoints, supplemented by retrieval metrics (hit@any, precision, recall) and binary outcome classification (macro F1). The study tests Native (run original code) vs. Python (translate to Python) execution modes and a data-only condition (no original code).

## Key Results
- Agents achieve high execution and interpretation LLMEval scores (e.g., GPT-5: 96.20, 93.35) but lower macro F1 for binary outcome classification (max 77.38%).  
- Data retrieval performance is weak: best hit@any is 63.16% (GPT-5), with precision (7.41%) and recall (30.62%) extremely low.  
- A significant execution-outcome gap exists: many runs produce successful execution logs but incorrect final judgments due to semantic translation errors or misinterpretation of statistical criteria.

## Why This Works (Mechanism)
The benchmark reveals a decoupling between computational execution and accurate replicability judgment. The final binary outcome requires aligning numerical outputs with preregistered statistical criteria. Even a successful run may contain subtle deviations (e.g., from translation errors) that lead to an incorrect judgment, exposing a gap between execution success and correct assessment. Data retrieval for replication is a qualitatively different challenge from code execution; agents must search the web for appropriate new datasets, evaluate sources, and retrieve valid data. Consistently low retrieval metrics demonstrate that current tool-augmented agents excel in controlled computational tasks but fail at open-world information acquisition. The trade-off between Native and Python execution modes illustrates that simplifying the environment via translation reduces crashes but introduces silent semantic errors (e.g., loading wrong filenames) that compromise interpretation fidelity. Thus, execution success is not a reliable proxy for outcome correctness.

## Foundational Learning
**Concept: Reproduction vs. Replication** – Replication uses new data (agent must retrieve it) whereas reproduction reuses original data/code. The benchmark focuses on replication, testing data retrieval skills. Quick check: If an agent uses the exact original dataset, is it performing replication or reproduction? What changes make it a replication?  
**Concept: Preregistration and Criteria Met/Unmet** – The final judgment is binary (criteria met) based on a preregistered statistical test (e.g., effect in same direction and p<0.05). Agents must compare their results against these exact criteria. Quick check: Given preregistered “coefficient > 0 and p < 0.05”, and replication results “coefficient=0.3, p=0.06”, what is the correct judgment?  
**Concept: Process-Oriented vs. Outcome-Only Evaluation** – ReplicatorBench scores partial credit across many checkpoints, allowing identification of where failures occur. This contrasts with a single pass/fail outcome. Quick check: If an agent retrieves wrong data but executes flawlessly, should it receive full credit? How would an outcome-only benchmark score it?

## Architecture Onboarding
**Component map:** ReAct Loop → Tool Palette (file/dataset utilities, orchestration) → Execution Orchestrator (Docker build/run) → Workspace (container) → Output JSONs; Evaluation: LLM-as-judge consumes outputs.  
**Critical path:**  
1) Extraction: read paper, fill post_registration.json, web search → URLs.  
2) Generation-Design: use post_registration and replication_data to create replication_info.json (preregistration, docker specs, code plan).  
3) Generation-Execution: build Docker image, run analysis, debug crashes iteratively → execution_results.json.  
4) Interpretation: read all outputs, inspect data, compare to original → interpretation_report.json with final binary judgment.  
**Design tradeoffs:**  
- Native vs Python Mode: Native preserves original code but often crashes on dependencies; Python avoids crashes but risks semantic drift via translation.  
- Data-only vs Code-available: Data-only forces implementation from paper description, increasing plan detail but raising execution failure risk.  
- LLM Choice: Larger models (GPT-5, o3) have better debugging and logic but may alter task decomposition, affecting design scores.  
**Failure signatures:**  
- Extraction: low hit@any, missing fields in post_registration.json.  
- Generation-Design: vague instructions in replication_info.json, missing/incorrect docker_specs.packages.  
- Generation-Execute: repeated Docker build failures, runtime NameError/FileNotFoundError, non-zero exit without recovery.  
- Interpretation: final “criteria met” that contradicts human due to misread statistics, plan deviation, or silent translation errors.  
**First 3 experiments:**  
1. Baseline run on a single case (e.g., study 4) with GPT-5 Python mode, code-available; observe time distribution.  
2. A/B test Native vs Python on an R-coded case; compare execution success and binary outcome alignment.  
3. Stress test data-only setting on a simple case; measure impact on design score and execution/interpretation fidelity.

## Open Questions the Paper Calls Out
- How can LLM agents be made more effective at retrieving replication data from the web? Current models struggle, and data retrieval is the weakest link.  
- Why do agents with high execution scores still produce incorrect final replicability judgments? The execution-outcome gap suggests limitations in interpretation fidelity or undetected errors.  
- How can the field scale replication benchmarks beyond the current 19-case limitation, given the scarcity of expert-documented replications?  
- What capabilities are required for LLM agents to replicate experimental studies (involving primary data collection) rather than observational studies with existing datasets?

## Limitations
- Small benchmark size (19 cases) limits statistical power and generalizability.  
- Evaluation relies on LLM-as-a-judge (GPT-4o), whose alignment with human experts is uncertain.  
- Web search tool specifics are not fully detailed; performance likely varies with search engine and prompt design.  
- Use of proprietary models (GPT-5, o3) hinders reproducibility.  
- Silent semantic errors in code translation may be more widespread than detected.

## Confidence
- ReplicatorBench design and validity: High  
- Data retrieval weakness is a robust finding: High  
- Execution-judgment gap: Medium (human validation of binary outcomes needed)  
- Trade-offs between execution modes: Medium  
- Failure signature taxonomy: Medium (based on qualitative analysis)

## Next Checks
1. Scale the benchmark to 100+ replication cases across diverse domains to test generalizability of observed gaps.  
2. Conduct a human expert study on a stratified sample of agent outputs to calibrate the LLM-as-judge metric and identify systematic biases.  
3. Perform sensitivity analysis of the web search component by varying the search backend (e.g., Google vs Bing) and measuring changes in retrieval metrics.
