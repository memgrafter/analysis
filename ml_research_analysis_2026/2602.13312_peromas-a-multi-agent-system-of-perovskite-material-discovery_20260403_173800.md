# PeroMAS: A Multi-agent System of Perovskite Material Discovery

## Quick Facts
- arXiv ID: 2602.13312
- Source URL: https://arxiv.org/abs/2602.13312
- Reference count: 40
- Primary result: Claude-4.5 achieved 72.4% task completion under multi-objective constraints, outperforming single LLM and generalist agents by 10.2%, and wet-lab validated an AI-designed Sn-Pb recipe with 17% PCE aligning with predictions.

## Executive Summary
PeroMAS is a hierarchical multi-agent system that integrates literature retrieval, generative design, virtual screening, and mechanistic analysis for perovskite solar cell discovery. A central Meta Agent orchestrates a closed-loop PDCA cycle across four functional agents via standardized Model Context Protocols (MCPs), propagating physical constraints throughout the workflow. In evaluations, Claude-4.5 attained 72.4% task completion under multi-objective goals, surpassing baselines. An AI-designed Sn‑Pb composition was experimentally validated, achieving 17% power conversion efficiency and matching the dry‑lab predicted range (16–19%). The system also introduces PeroMAS‑Bench, the first hierarchical evaluation benchmark for perovskite discovery.

## Method Summary
The architecture revolves around a Meta Agent that decomposes user queries into a sequence of tasks for specialized functional agents. The Miner extracts structured insights from literature using semantic tools; the Designer generates candidate perovskite recipes constrained by prior data; the Emulator predicts properties (PCE, stability) via graph neural networks; and the Analyst validates candidates with rule‑based checks and SHAP‑based attribution to inform the next iteration. All agents share a persistent memory and invoke heterogeneous domain tools through MCPs, enabling seamless integration of curated models (e.g., MatterGen, CGCNN). Closed‑loop optimization is evaluated on 20 complex, multi‑objective tasks, with the top candidate subjected to a standard p‑i‑n fabrication protocol.

## Key Results
- Claude-4.5 achieved 72.4% task completion under multi-objective constraints, a 10.2% improvement over single LLM and generalist baselines.
- Wet-lab validation of an AI‑proposed Sn‑Pb recipe (1:1 FASnI₃:MAPbI₃ + SnF₂ + EDAI₂) yielded 17% PCE, aligning with the system’s predicted 16–19% range.
- The work established PeroMAS‑Bench, the first hierarchical benchmark for evaluating multi‑agent systems in perovskite research.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Hierarchical orchestration by a Meta Agent reduces workflow fragmentation and enables closed-loop optimization under multi-objective constraints.
- **Mechanism:** The Meta Agent translates user objectives into a PDCA (Plan‑Do‑Check‑Act) cycle. It plans the sequence of functional agent invocations (Miner, Designer, Emulator, Analyst), prunes redundant sub‑tasks using historical memory, and refines hypotheses based on Analyst feedback. This global planning ensures physical constraints (e.g., lead toxicity, stability) are propagated across discrete tasks.
- **Core assumption:** A central reasoning unit can effectively decompose and coordinate complex scientific workflows better than monolithic agents or independent models.
- **Evidence anchors:**
  - **[abstract]:** "introduces a hierarchical multi-agent system with a Meta Agent orchestrating four functional agents... to execute a closed-loop process... to propagate physical constraints across the research workflow."
  - **[section 3.2]:** Details the Meta Agent's three‑stage reasoning (Goal Alignment, Reflection, Strategy Formulation) and its role in instantiating constraints into hypotheses.
  - **[corpus]:** Weak direct evidence; neighboring papers (e.g., SciAgents, AtomAgents) describe multi‑agent benefits generally but do not validate this specific hierarchical architecture for perovskites.
- **Break condition:** If the Meta Agent's pruning mechanism incorrectly marks necessary data‑gathering tasks as redundant (e.g., skipping literature retrieval for a novel composition space), foundational knowledge gaps will propagate, causing invalid downstream designs.

### Mechanism 2
- **Claim:** Standardized tool integration via Model Context Protocols (MCPs) allows heterogeneous, domain‑specific models to be invoked reliably within a unified agent framework, extending functional capabilities beyond pure LLM reasoning.
- **Mechanism:** Each functional agent is equipped with curated MCP tools (e.g., `arxiv‑mcp`, `MatterGen`, `CGCNN`). The agent's LLM backbone decides when and how to call these tools based on its current instruction and shared memory. This decouples high‑level reasoning from low‑level execution, letting the system leverage specialized ML models (trained on perovskite data) for precise tasks like property prediction or synthesis feasibility.
- **Core assumption:** Externalizing domain knowledge into callable tools is more effective than fine‑tuning a single LLM on all tasks, especially for tasks requiring high precision or specialized computation.
- **Evidence anchors:**
  - **[section 3.3]:** Explicitly describes each agent's "toolchain" (e.g., Miner's "Semantic Extraction Toolchain," Emulator's "Heterogeneous Prediction Toolchain") and how they are invoked via MCP.
  - **[section A.2 & Table 5]:** Lists concrete MCP tools and their backend sources (e.g., `CGCNN` for bandgap, `MatProj‑mcp` for crystal structures).
  - **[corpus]:** The corpus mentions tool‑use in other agents (e.g., `Toolformer` [57], AutoLabs [52]) but does not provide direct evidence for MCP's efficacy in perovskite‑specific orchestration.
- **Break condition:** Poorly designed MCP interfaces (e.g., ambiguous input/output schemas) or tool failures (e.g., `CGCNN` model drift) will cause execution errors or invalid outputs. The system relies on the Analyst Agent's validation to catch these.

### Mechanism 3
- **Claim:** The Analyst Agent's two‑layer "Rule Filtering‑Attribution" pipeline provides a scientific grounding mechanism that filters physically impossible candidates and generates mechanistic improvement strategies, closing the feedback loop for iterative design.
- **Mechanism:** First, the Analyst uses rule‑based tools (`Pymatgen`, `ASE`) to check stoichiometry and crystal structure legality. Second, for candidates failing objectives, it uses `SHAP‑mcp` to perform feature attribution on the Emulator's predictions, identifying which parameters (e.g., Sn content, annealing temp) most limit PCE or stability. This diagnostic report (`R`) is fed back to the Meta Agent to inform the next design iteration.
- **Core assumption:** Post‑hoc interpretability (SHAP) on surrogate ML models can reliably identify actionable physical insight (e.g., "SnF₂ concentration critically impacts T₈₀") to guide experimental redesign.
- **Evidence anchors:**
  - **[section 3.3.4]:** "executes a two‑layer 'Rule Filtering‑Attribution' pipeline... [using] Material Rule Validator... and Interpretable Inference Engine (based on SHAP analysis)."
  - **[section 4.2.5 & Figure 5b]:** The wet‑lab validation (17% PCE) aligns with the dry‑lab predicted range (16‑19%), suggesting the feedback loop produced physically viable candidates.
  - **[corpus]:** The corpus references SHAP for interpretability in perovskite ML [20, 27] but does not confirm its utility within a multi‑agent loop for *generating* new hypotheses.
- **Break condition:** If SHAP attributions are misleading (e.g., due to correlated features in the training data), the Meta Agent may pursue ineffective strategies (e.g., over‑optimizing a non‑critical parameter), stalling convergence.

## Foundational Learning
- **Concept: Multi‑Agent Orchestration vs. Monolithic Agents**  
  **Why needed here:** Perovskite discovery involves distinct sub‑tasks (literature mining, inverse design, simulation, analysis). A single ReAct agent (baseline) struggles with long‑horizon planning and context switching across these. Understanding *why* hierarchical decomposition reduces cognitive load is key.  
  **Quick check question:** What are the risks if the Meta Agent incorrectly sequences the Designer and Emulator agents (e.g., calling Emulator before Designer has generated any candidates)?

- **Concept: Physical Constraints as Hard Filters in AI‑Driven Science**  
  **Why needed here:** The system must respect perovskite‑specific laws (charge neutrality, tolerance factor, synthesis feasibility). This isn't just an accuracy metric; invalid compositions will fail in wet‑lab. Learners must grasp how rules (`Pymatgen`, `ASE`) are applied *after* generative design but *before* prediction.  
  **Quick check question:** If the Analyst Agent's `Pymatgen` check rejects a candidate due to an impossible oxidation state, should the Meta Agent (a) discard it permanently, or (b) ask the Designer to propose a chemically alternative? Why?

- **Concept: Tool Standardization via Protocol (MCP)**  
  **Why needed here:** The system's power comes from plugging in specialized tools (e.g., `CGCNN`, `MatterGen`) without the Meta Agent needing to know their internals. Understanding the MCP as a *contract* (input schema, output format) is crucial for adding new tools.  
  **Quick check question:** If you wanted to add a new DFT calculation tool (e.g., VASP) to the Emulator Agent, what are the minimum requirements for wrapping it as an MCP tool?

## Architecture Onboarding
- **Component map:** Meta Agent -> Miner, Designer, Emulator, Analyst; all share Memory `M`; Wet‑Lab Interface is external.
  - **Meta Agent:** Central planner (LLM‑based). Inputs: user query `G`, memory `M`, prior feedback `R`. Output: orchestration instructions `P_t` for functional agents.
  - **Functional Agents:** 
    - **Miner:** `arxiv‑mcp`, `Sci‑mcp`, `extract‑mcp` → outputs structured data `D_obs`.
    - **Designer:** `MatterGen`, `CSLLM`, `MatProj‑mcp` → outputs candidate recipes `X_new`.
    - **Emulator:** `CGCNN`, `Pero‑ML` → outputs evaluated candidates `X_eval` with predictions/uncertainty.
    - **Analyst:** `SHAP‑mcp`, `Pymatgen`, `ASE` → outputs diagnostic report `R`.
  - **Shared Memory (`M`):** Accumulates all `D_obs`, `X_new`, `X_eval`, and `R` across iterations.
  - **Wet‑Lab Interface:** Separate module that executes the final recipe.

- **Critical path:** 
  1. User query → Meta Agent (`G` defined). 
  2. Meta Agent → Miner (`I_Miner`): "Retrieve recent Sn‑Pb alloy papers." 
  3. Miner → `D_obs` (extracted ratios, additives). 
  4. Meta Agent → Designer (`I_Designer`): "Generate lead‑reduced compositions using Sn." 
  5. Designer → `X_new` (e.g., (FASnI₃)₀.₆(MAPbI₃)₀.₄ + 10% SnF₂). 
  6. Meta Agent → Emulator (`I_Emulator`): "Predict PCE and T₈₀." 
  7. Emulator → `X_eval` (e.g., PCE 16‑19%, T₈₀ 500‑800h). 
  8. Meta Agent → Analyst (`I_Analyst`): "Check validity and attribute T₈₀ limitations." 
  9. Analyst → `R` (e.g., "Sn oxidation is key risk; recommend SnF₂ additive"). 
  10. Loop back to step 4 or proceed to wet‑lab if `G` met.

- **Design tradeoffs:**
  - **Open‑source (DeepSeek‑V3) vs. Proprietary (Claude‑4.5):** Table 2 shows DeepSeek‑V3 matches task completion but trails in output validity (Expert Score: 6.59 vs. 7.14). Tradeoff: Cost/control vs. reasoning depth.
  - **Pruning aggressiveness:** Over‑pruning (skipping Miner) risks missing critical literature; under‑pruning wastes compute on redundant searches. Tune via historical memory analysis.
  - **Tool fidelity vs. speed:** `CGCNN` (fast, approximate) vs. DFT (slow, accurate). Emulator uses ML for speed; Analyst must flag high‑uncertainty predictions for possible DFT refinement.

- **Failure signatures:**
  - **Miner:** Low `Tool‑Any‑Order` accuracy (<80%) indicates poor query formulation or tool API misuse. Check retrieval query set `Q` construction.
  - **Designer:** High invalidity rate in `X_new` (non‑charge‑balanced formulas) suggests `CSLLM` is not properly constrained by `extract‑mcp` outputs.
  - **Emulator:** High prediction uncertainty (`σ_i`) across all candidates may indicate `D_obs` lacks coverage of the proposed design space (out-of-distribution).
  - **Analyst:** `R` report repeats same attribution (e.g., always blames "Sn content") without mechanistic nuance—possible SHAP exploitation or feature correlation in `Pero‑ML`.

- **First 3 experiments:**
  1. **Atomic Miner Test:** Query "Find all Sn‑based perovskites with T₈₀ > 500h." Measure `Tool‑In‑Order` accuracy. Goal: >90%. Failure indicates `extract‑mcp` needs fine‑tuning on stability parameters.
  2. **Designer Constraint Test:** Provide `D_obs` containing only Pb‑based recipes. Instruct Designer: "Generate lead‑free (≤10% Pb) with PCE > 20%." Measure validity of `X_new`. Goal: >70% chemically valid. Failure indicates `CSLLM` lacks constraint reasoning.
  3. **Closed‑Loop Meta Test:** Set user goal: "PCE > 22%, T₈₀ > 2000h, Pb‑free." Run 3 iterations. Track if `R` from Analyst iteratively improves `X_eval` scores. Expected: PCE/T₈₀ predictions trend upward. Stagnation indicates Meta Agent's reflection strategy is broken.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How can PeroMAS be optimized to simultaneously achieve high efficiency (>20% PCE) and near‑zero lead content in perovskite solar cells, given the current trade‑off demonstrated in the wet‑lab validation (17% PCE with 50% lead reduction)?
- **Basis in paper:** [inferred] The wet‑lab experiment achieved 17% PCE for a Sn‑Pb recipe that halves lead content (Section 4.2.5), while the user query example targets >20% PCE with low‑lead (Appendix B). The paper discusses multi‑objective trade‑offs but doesn't resolve how to push PCE higher while minimizing toxicity.
- **Why unresolved:** The system's current design prioritizes constraint satisfaction but may lack generative mechanisms to explore compositions beyond existing data biases. The 17% PCE falls short of the >20% target, indicating a gap in balancing conflicting objectives.
- **What evidence would resolve it:** Systematic ablation studies varying lead content and compositional parameters, coupled with expanded wet‑lab validation across a Pareto front of efficiency‑toxicity trade‑offs. Analysis of failure modes in high‑efficiency, low‑lead candidates via the Analyst Agent's attribution reports.

### Open Question 2
- **Question:** To what extent can the PeroMAS architecture (hierarchical agents with MCP tool integration) be generalized to other materials discovery domains (e.g., solid‑state batteries or catalysts) without domain‑specific retooling?
- **Basis in paper:** [explicit] The paper positions PeroMAS as the first specialized system for perovskites (Section 1, Section 4.1.3) and compares against generalist agents (Manus), implying domain‑specific design is crucial. However, it does not explore cross‑domain transferability.
- **Why unresolved:** The MCP tools are deeply integrated with perovskite‑specific data sources and models (Table 5, Appendix A). Generalization would require redefining tools, knowledge bases, and constraints for new domains, which is not addressed.
- **What evidence would resolve it:** A replication study applying the same agent hierarchy and MCP protocol to a different material system, using analogous domain tools and benchmarks. Performance comparison against domain‑specific single‑task models and generalist agents in the new domain.

### Open Question 3
- **Question:** How robust is the MCP‑based tool invocation and constraint propagation when faced with novel material compositions or processing parameters that significantly deviate from the training data distribution?
- **Basis in paper:** [inferred] The system relies on tools trained on The Perovskite Database (Section 4.1.1, Appendix A). The paper demonstrates success within known design spaces but doesn't test out‑of‑distribution scenarios, such as unprecedented cation/anion combinations or synthesis methods.
- **Why unresolved:** Physical constraints in materials science are often non‑linear and context‑dependent. Tools like the Synthesis Feasibility Assessor or Property Predictors may fail silently on novel inputs, and the Meta Agent's pruning might skip unexplored regions without detection.
- **What evidence would resolve it:** Stress‑testing with adversarial or extrapolative queries (e.g., hypothetical compositions not in the database) and measuring tool failure rates, false constraint satisfaction, and recovery mechanisms via the Analyst Agent. Incorporate uncertainty quantification in tool outputs to flag deviations.

## Limitations
- Exact MCP tool implementations (e.g., `MatterGen‑mcp` prompts, `CSLLM` weights) are unspecified; no code or API details are provided.
- Wet‑lab synthesis specifics for the top recipe are incomplete (precursor molarities, anti‑solvent timing, annealing temperature ramp, encapsulation method).
- No ablation studies isolate the contributions of the Meta Agent's pruning or the SHAP feedback loop; performance gains may stem from other components.

## Confidence
- Hierarchical orchestration reduces fragmentation: **Medium**
- MCP standardization enables reliable tool integration: **Medium**
- Analyst’s SHAP feedback drives iterative improvement: **Low**
