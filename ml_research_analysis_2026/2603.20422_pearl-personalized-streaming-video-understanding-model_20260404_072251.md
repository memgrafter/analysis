# PEARL: Personalized Streaming Video Understanding Model

## Quick Facts
- **arXiv ID:** 2603.20422
- **Source URL:** https://arxiv.org/abs/2603.20422
- **Reference count:** 0
- **Primary result:** PEARL achieves state-of-the-art on the new PSVU task, improving frame-level and video-level accuracy by 13.79% and 12.80% over eight baselines while maintaining real-time latency.

## Executive Summary
PEARL introduces Personalized Streaming Video Understanding (PSVU), a task requiring real-time, interactive responses to user-defined concepts in continuous video streams—a capability absent in current static or offline video understanding methods. The authors propose PEARL, a training‑free, plug‑and‑play framework with a Dual‑grained Memory System (separate storage for streaming clips and defined concepts) and a Concept‑aware Retrieval Algorithm (rewrites queries using concept descriptions to retrieve relevant historical evidence). Evaluated on the new PEARL‑Bench benchmark (132 videos, 2,173 timestamped QA annotations), PEARL attains state‑of‑the‑art performance across three VLM architectures, yielding average gains of 13.79% (frame‑level) and 12.80% (video‑level) over eight offline and online baselines while operating in real time.

## Method Summary
PEARL addresses the PSVU task, where a system must answer two query types—Real‑Time (about the current scene) and Past‑Time (about earlier content)—after arbitrary user‑defined concepts have been introduced during the stream. The method is training‑free and relies on two memory structures:

- **Streaming Memory** stores segmented video clips (detected by PySceneDetect) as multimodal embeddings (1 fps frames encoded by Qwen3‑VL‑Embedding‑2B).
- **Concept Memory** holds each user‑defined concept’s name, a stable textual description (generated by a base VLM from visual evidence at definition time), and the evidence clip(s).

During operation:
1. The video stream is segmented into clips; each clip’s embedding is added to Streaming Memory.
2. On a Concept‑Definition instruction, the system extracts representative evidence (last frame for frame‑level entities, full clip for video‑level actions) and uses a VLM with a fixed prompt to produce a concise, feature‑stable description, which is stored in Concept Memory.
3. For a query containing one or more concept names, the system retrieves the corresponding descriptions, rewrites the query by replacing each name with its description, embeds the rewritten query, and retrieves the top‑K most similar clip embeddings from Streaming Memory (cosine similarity). The retrieval is optionally expanded by N adjacent clips.
4. The current clip, retrieved context, and the original query are fed to the base VLM (e.g., Qwen3‑VL‑8B), which selects the correct multiple‑choice answer.

Hyperparameters used in the paper: K=4, N=1 for frame‑level Past‑Time QA; N=0 for video‑level Real‑Time QA; all videos sampled at 1 fps for embeddings.

## Key Results
- Introduced the PSVU task and PEARL‑Bench, a benchmark with 132 videos and 2,173 QA annotations.
- PEARL improves frame‑level Real‑Time and Past‑Time accuracy by average 13.79% and video‑level Real‑Time accuracy by 12.80% over eight offline and online baselines.
- Achieves consistent gains across three VLM architectures (LLaVA‑OV‑7B, Qwen2‑VL‑7B, Qwen3‑VL‑8B) while maintaining real‑time latency.

## Why This Works (Mechanism)

**Mechanism 1: Dual‑grained Memory System**  
- **Claim:** The Dual‑grained Memory System enables efficient long‑term retention and retrieval of personalized concepts and streaming visual context without retraining.  
- **Mechanism:** It explicitly decouples storage into (a) a Streaming Memory that archives segmented video clips with multimodal embeddings for scalable evidence retrieval, and (b) a Concept Memory that stores structured representations (name, visual evidence, textual description) of user‑defined concepts. This separation prevents interference between evolving concept definitions and the continuous visual stream.  
- **Core assumption:** Personalized concepts can be represented by stable visual/kinematic descriptors (e.g., facial features for frame‑level, movement patterns for video‑level) that remain retrievable across long streams and varying contexts.  
- **Evidence anchors:** [abstract] “Dual‑grained Memory System that separately archives streaming clips and defined concepts.”; [section 4.2] Detailed description of Streaming Memory (clip embedding storage) and Concept Memory (concept registration via evidence extraction and description generation).  
- **Break condition:** If concept descriptions fail to capture stable features (e.g., overfit to transient clothing), retrieval accuracy degrades, especially for Past‑Time QA requiring cross‑temporal matching.

**Mechanism 2: Query Rewriting with Concept Descriptions**  
- **Claim:** Query rewriting using concept descriptions bridges the gap between user‑defined concept names (unseen by the embedding model) and the semantic space of stored visual evidence.  
- **Mechanism:** Upon a query, the system replaces each concept name in the question with its stored textual description (e.g., “a young female with long black hair” instead of “<Adaliz>”). This rewritten query is then embedded and compared against clip embeddings in Streaming Memory via cosine similarity, improving retrieval of relevant historical clips.  
- **Core assumption:** Multimodal embedding models align better with descriptive natural language than with arbitrary user‑assigned tokens; thus, rewriting enhances semantic matching.  
- **Evidence anchors:** [abstract] “rewrites queries using concept descriptions to retrieve relevant historical evidence.”; [section 4.3] Formal description of query rewriting and embedding‑based retrieval.  
- **Break condition:** If generated concept descriptions are incomplete or inaccurate (e.g., missing key stable features), the rewritten query misaligns with relevant clips, reducing Past‑Time QA accuracy. Ablation in Table 4 shows a 4.28% avg drop without rewriting.

**Mechanism 3: Streaming Interaction Formulation**  
- **Claim:** Task formulation as multi‑turn, streaming interaction with dynamic concept registration aligns the system with real‑world human cognition and assistant scenarios.  
- **Mechanism:** Unlike static/offline personalization, PSVU requires the model to (i) accept concept definitions at arbitrary timestamps, (ii) maintain an evolving concept set, and (iii) answer Real‑Time and Past‑Time queries within a continuous stream. This forces the architecture to support incremental memory updates and precise temporal grounding.  
- **Core assumption:** Real‑world AI assistants must handle open‑ended, continuous inputs and instant feedback; personalization must be online and interactive.  
- **Evidence anchors:** [abstract] “real‑time, interactive responses to user‑defined concepts in continuous video streams.”; [section 3.1] Formal task definition and query types (Concept‑Definition, Real‑Time, Past‑Time).  
- **Break condition:** If the system cannot register concepts incrementally (e.g., overwrites old concepts) or fails to segment streams meaningfully, it cannot support multi‑turn interactions, collapsing to offline single‑turn performance.

## Foundational Learning

**Concept: Streaming Video Segmentation**  
- **Why needed here:** PEARL must partition an infinite video stream into semantically coherent clips for storage and retrieval. Poor segmentation (e.g., too long/dense clips) dilutes semantic focus and harms retrieval precision.  
- **Quick check:** How does clip duration affect Past‑Time QA accuracy for video‑level concepts that span several seconds?

**Concept: Multimodal Embedding Similarity**  
- **Why needed here:** All retrieval (concept‑to‑clip, query‑to‑clip) relies on cosine similarity in a joint vision‑text embedding space. The embedding model’s quality directly determines retrieval relevance.  
- **Quick check:** If the embedding model is trained only on static images, how might its performance degrade on video‑level action descriptions?

**Concept: Dynamic Concept Registration**  
- **Why needed here:** Concepts are user‑defined on‑the‑fly, not from a fixed pool. The system must extract visual evidence and generate a stable description at definition time, which becomes a persistent memory entry.  
- **Quick check:** What happens if a concept definition occurs at a timestamp where the target subject is partially occluded?

## Architecture Onboarding

### Component Map
Continuous video stream + user instructions --> Scene detection (PySceneDetect) --> Dual‑grained Memory (Streaming Memory + Concept Memory) --> Query rewriting & retrieval (embedding model Qwen3‑VL‑Embedding‑2B) --> Base VLM (e.g., Qwen3‑VL‑8B) --> Answer (multiple‑choice selection).

### Critical Path
1. Ingest video stream; segment into clips via scene detection.
2. For each clip: compute multimodal embedding and store in Streaming Memory.
3. On Concept‑Definition instruction: extract evidence (last frame for frame‑level; full clip for video‑level); generate concise, stable description via VLM with fixed prompt; store in Concept Memory.
4. On query: identify mentioned concepts → retrieve their descriptions → rewrite query by replacing names with descriptions → embed rewritten query → retrieve top‑K most similar stored clip embeddings → expand with N adjacent clips → feed current clip + retrieved clips + original query to base VLM → parse model’s output to select A/B/C/D.

### Design Tradeoffs
- **Memory growth vs. retrieval cost:** Unlimited storage increases latency; practical deployments may need age‑based eviction.
- **Description verbosity vs. matching:** Overly concise descriptions lose discriminative features; overly verbose descriptions introduce noise. The paper’s templates (Appendix C) aim to balance this.
- **Retrieval scope (K, N) vs. noise:** Larger K and N improve recall but risk including irrelevant context, as shown in Fig. 9 for Real‑Time QA.

### Failure Signatures
- **Low Past‑Time accuracy with high Real‑Time accuracy** → Streaming Memory retrieval failure (insufficient K, poor embeddings, bad scene segmentation).
- **High latency outlier** → Excessive N expansion or slow embedding model; monitor per‑component latency (Fig. 5).
- **Inconsistent answers across cyclic option rotations** → VLM reasoning error; check if retrieved context is relevant.

### First 3 Experiments
1. **Ablation core components:** Using Qwen3‑VL‑8B, test without Concept Memory, without Streaming Memory, and without query rewriting (Table 4). Expect the largest drop from removing Concept Memory for Real‑Time QA.
2. **Hyperparameter sensitivity:** Vary K (top‑K clips) and N (adjacent expansion) on Past‑Time QA (Fig. 4). Expect accuracy to plateau after K≥3 and N=1; further increases yield diminishing returns or noise.
3. **Cross‑architecture robustness:** Apply PEARL to three VLMs (LLaVA‑OV‑7B, Qwen2‑VL‑7B, Qwen3‑VL‑8B). Expect consistent absolute gains (>8% avg) over offline baselines, confirming plug‑and‑play generality.

## Open Questions the Paper Calls Out

**Open Question 1: Concept Drift**  
- **Question:** What mechanisms are needed for PEARL to handle concept drift, where user‑defined entities (e.g., persons or objects) undergo visual changes over time (such as clothing changes, accessories, or aging), and how does this impact long‑term retrieval accuracy?  
- **Basis:** The Concept Memory stores a static textual description generated at registration, with no provision for updating these descriptions as the entity’s appearance evolves.  
- **Why unresolved:** Real‑world streaming scenarios involve persistent entities that may change visual attributes, but the paper assumes the initial description remains sufficiently discriminative indefinitely, which may not hold over long durations.  
- **Resolving evidence:** Conduct experiments on video streams containing deliberate concept drift (e.g., a person changing outfits multiple times), measure degradation in Past‑Time QA accuracy as the stream progresses, and implement a dynamic updating scheme (e.g., periodic re‑description based on recent clips) to quantify potential recovery.

**Open Question 2: Scalability to Long Streams and Many Concepts**  
- **Question:** Can PEARL maintain real‑time performance and memory scalability when confronted with extremely long streaming histories (e.g., days of video) and large numbers of user‑defined concepts (e.g., thousands), and what architectural modifications are required?  
- **Basis:** The Dual‑grained Memory System archives all segmented clips and concept entries without discussed pruning, compression, or efficient indexing for large‑scale retrieval.  
- **Why unresolved:** Current evaluations use relatively short clips (average ~24 minutes), but practical deployment in continuous AI assistants would involve unbounded growth of memory, potentially leading to prohibitive storage and latency increases during retrieval.  
- **Resolving evidence:** Perform stress tests with synthetic streams of varying lengths (hours to days) and concept counts, monitor memory consumption and end‑to‑end latency, and explore hierarchical memory structures or adaptive eviction policies to maintain efficiency.

**Open Question 3: Handling Ambiguous or Poor Concept Definitions**  
- **Question:** How robust is PEARL to ambiguous, vague, or conflicting user concept definitions, which are common in natural human‑AI interactions, and can the system recover from poorly specified registrations?  
- **Basis:** PEARL‑Bench uses precise, template‑driven concept definitions, and the framework assumes that generated descriptions are accurate and discriminative for retrieval.  
- **Why unresolved:** Real users may provide incomplete or subjective descriptions (e.g., “the cool guy”), leading to ineffective concept grounding and retrieval failures; the paper does not evaluate such cases or propose clarification strategies.  
- **Resolving evidence:** Collect natural language concept definitions from human users with varying clarity, test PEARL’s registration and subsequent QA performance, and develop interactive mechanisms (e.g., asking clarifying questions) to improve concept resolution.

**Open Question 4: Generalization to Challenging Real‑World Video Conditions**  
- **Question:** Does PEARL generalize to diverse, in‑the‑wild video streams with challenging conditions (e.g., motion blur, occlusions, low lighting, and noisy backgrounds) beyond the curated domains (anime, movies, digital humans) in PEARL‑Bench?  
- **Basis:** The benchmark videos are carefully selected for quality and clarity from structured sources, whereas real‑world streaming data (e.g., surveillance, user‑generated vlogs) often contains significant visual noise and variability.  
- **Why unresolved:** Such challenging conditions could degrade scene detection, embedding quality, and the reliability of both concept description generation and clip retrieval, but the paper’s experiments are confined to high‑quality synthetic or professional content.  
- **Resolving evidence:** Evaluate PEARL on established real‑world video datasets (e.g., driving scenes, live streaming content), analyze performance drops per component (scene detection, embedding), and adapt the framework with robust models or domain adaptation techniques.

**Open Question 5: Extension to Multi‑Modal Streaming Inputs**  
- **Question:** Can the PEARL framework be extended to incorporate multi‑modal streaming inputs (e.g., audio, depth sensors, GPS) for richer personalized understanding, and how should the Dual‑grained Memory System be redesigned to handle such heterogeneous data?  
- **Basis:** The task definition, benchmark, and framework focus exclusively on visual (video) streams, with no consideration for other sensory modalities that future AI assistants will likely fuse.  
- **Why unresolved:** Multi‑modal signals (e.g., speech commands, environmental sounds) could enhance concept definition and query context, but PEARL’s memory and retrieval are video‑centric, lacking mechanisms for cross‑modal alignment and joint indexing.  
- **Resolving evidence:** Propose extensions to the memory system to store multi‑modal embeddings, design cross‑modal retrieval algorithms, and evaluate on a multi‑modal streaming benchmark to measure gains and integration challenges.

## Limitations
- **Dataset Accessibility:** PEARL‑Bench’s public availability is unconfirmed; without direct download access, full performance replication is blocked.
- **Implementation Gaps:** Exact VLM answer prompts and parsing logic (beyond Appendix C prompts) are not detailed in the paper; minor deviations could impact cyclic rotation accuracy.
- **Generalization Scope:** Gains are shown on three VLMs, but robustness to other embedding models or scene detection algorithms remains unknown; long‑stream memory management (eviction policies) is not evaluated.

## Confidence
- **Dual‑grained Memory System Efficacy:** Medium – strong internal ablations support the design, but confidence is tempered by dependence on the unreleased benchmark and specific hyperparameters.
- **Query Rewriting Utility:** Medium – the 4.28% average drop in ablations is compelling, yet this assumes consistently high‑quality concept descriptions.
- **PSVU Task Formulation & SOTA Claims:** Medium – the new benchmark and comparisons against 8 baselines are solid, but independent validation is pending due to dataset/code access constraints.
