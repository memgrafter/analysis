# From Flat Logs to Causal Graphs: Hierarchical Failure Attribution for LLM-based Multi-Agent Systems

## Quick Facts
- **arXiv ID**: 2602.23701
- **Source URL**: https://arxiv.org/abs/2602.23701
- **Reference count**: 34
- **Primary result**: CHIEF achieves state-of-the-art agent-level (up to 77.59%) and step-level (up to 52.00%) accuracy on the Who&When benchmark, outperforming eight baselines including prompting, spectrum, and fine-tuning methods.

## Executive Summary
CHIEF is a framework for failure attribution in LLM-based multi-agent systems (MAS). It addresses the opaqueness of MAS failures by transforming flat execution logs into a hierarchical causal graph (HCG), which explicitly models latent execution topology. The system then employs virtual oracles for efficient top-down backtracking and applies a counterfactual screening strategy to separate root causes from propagated symptoms. Evaluated across 127 agent architectures on the Who&When benchmark, CHIEF significantly outperforms existing attribution methods. Ablation studies confirm the necessity of all three proposed modules: graph construction, oracle-guided backtracking, and counterfactual screening.

## Method Summary
CHIEF operates in three stages. First, it constructs an HCG from raw logs by decomposing trajectories into semantically coherent subtasks using RAG-based prototypes and reflection, parsing agent steps into structured OTAR tuples (Observation, Thought, Action, Result), and building causal edges via counterfactual patterns and explicit data flow. Second, for each subtask, a virtual oracle (Goal, Preconditions, Key Evidence, Acceptance Criteria) is synthesized using LLM prompts; a three-level backtracking then evaluates subtask outputs, agent OTAR, and step details to collect candidate error nodes. Third, a counterfactual attribution engine applies four progressive screening stages (Local, Planning‑Control, Data‑Flow, Deviation‑Aware) to isolate the true root cause from candidate errors. The method relies solely on LLM prompting, with no fine‑tuning.

## Key Results
- Agent‑level accuracy reaches up to 77.59% on the hand‑crafted Who&When subset and 76.80% on the algorithm‑generated subset.
- Step‑level accuracy peaks at 29.31% (hand‑crafted) and 52.00% (algorithm‑generated).
- CHIEF outperforms eight baselines (prompting, spectrum, fine‑tuning) across 127 diverse MAS architectures.
- Ablation studies confirm that removing any of the three modules degrades performance substantially.

## Why This Works (Mechanism)

- **Mechanism 1: Hierarchical Causal Graph Construction**
  - Claim: CHIEF transforms chaotic MAS logs into a hierarchical causal graph (HCG) that explicitly models latent execution topology, enabling systematic failure attribution.
  - Mechanism: The graph is built by decomposing the trajectory into semantically coherent subtasks via RAG-based prototypes and reflection, parsing agent steps into OTAR tuples, and constructing edges using counterfactual patterns (for subtask/agent dependencies) and explicit data flow (for step edges).
  - Core assumption: MAS execution inherently exhibits a hierarchical structure with clear data and control dependencies; errors propagate along these explicit pathways.
  - Evidence anchors: [Abstract] "transforms chaotic trajectories into a structured hierarchical causal graph"; [Section 4.1] details of hierarchical node definition, OTAR parsing, and edge construction.
  - Break condition: If subtask decomposition misaligns with actual execution phases, graph boundaries become artificial, breaking causal continuity and causing missed/spurious edges.

- **Mechanism 2: Oracle‑Guided Backtracking**
  - Claim: Hierarchical oracle‑guided backtracking efficiently localizes failures by using synthesized virtual oracles as intermediate supervision, avoiding exhaustive linear scans or costly replays.
  - Mechanism: For each subtask, an oracle (Goal, Preconditions, Key Evidence, Acceptance Criteria) is generated via LLM with RAG and sequential consistency checks. A three‑level backtracking evaluates subtask outputs against oracle Goal/Criteria; agent OTAR against Preconditions/Evidence; and step details against agent OTAR and oracle constraints.
  - Core assumption: Virtual oracles accurately capture expected subtask behavior; deviations from oracles at the finest granularity correspond to decisive errors.
  - Evidence anchors: [Abstract] "employs hierarchical oracle‑guided backtracking to efficiently prune the search space via synthesized virtual oracles"; [Section 4.2] formal definition of oracles and the backtracking algorithm.
  - Break condition: If oracles are under‑specified or over‑specified, they may fail to detect true errors or produce false alarms; LLM‑based evaluator Feval may also be inconsistent.

- **Mechanism 3: Counterfactual Attribution with Progressive Screening**
  - Claim: Counterfactual attribution with progressive causal screening rigorously separates root causes from propagated symptoms by analyzing causal scope, dependency nature, and reversibility.
  - Mechanism: Starting from candidate error steps, four stages: (1) Local Attribution checks if error originates locally (no upstream bias via counterfactual patterns). (2) Planning‑Control Attribution distinguishes planner vs. executor responsibility in cyclic behaviors. (3) Data‑Flow Attribution traces data corruption to its source along step edges. (4) Deviation‑Aware Attribution filters reversible self‑corrected errors. The root cause is the earliest irreversible local‑origin or data‑corruption step with high downstream impact.
  - Core assumption: Errors propagate along explicit causal edges and can be classified as cause vs. symptom; counterfactual patterns enable tracing responsibility; self‑correction is detectable.
  - Evidence anchors: [Abstract] "implements counterfactual attribution via a progressive causal screening strategy"; [Section 4.3] detailed description of each stage, including loop groups and data‑flow tracing.
  - Break condition: If causal edges are missing/incorrect, propagation paths may be misidentified; screening heuristics may fail on edge cases.

## Foundational Learning

- **Causal Inference (Counterfactual Reasoning)**
  - Why needed: The framework relies on counterfactual patterns (Bias → Anomaly) to model error propagation and responsibility.
  - Quick check: In the counterfactual pattern, what does "Bias" represent and what does "Anomaly" represent? (Answer: Bias is a latent upstream deviation; Anomaly is the observable downstream error caused by that bias.)

- **Hierarchical Task Decomposition**
  - Why needed: The HCG construction decomposes a flat trajectory into semantically meaningful subtasks; this decomposition defines the graph's high‑level structure.
  - Quick check: Why does CHIEF use a RAG‑based decomposition with reflection instead of a single LLM call? (Answer: To ensure decomposition is both rational (via retrieved prototypes) and faithful to the actual execution log (via reflection), avoiding hallucinated subtask boundaries.)

- **LLM Agent Execution Traces (OTAR)**
  - Why needed: Agent behaviors are represented as structured OTAR tuples, which serve as node attributes for oracle matching and edge construction.
  - Quick check: What are the four components of OTAR, and what aspect of agent behavior does each capture? (Answer: Observation (what the agent saw), Thought (reasoning), Action (what it did), Result (output/effect).)

- **Multi‑Agent System Error Propagation**
  - Why needed: The framework assumes errors propagate through data and control dependencies among agents.
  - Quick check: Give an example of how an error in an upstream agent's result could cause a failure in a downstream agent even if the downstream agent executed correctly. (Answer: Upstream agent returns incorrect data; downstream agent bases its action on that data and produces a wrong final answer, so the root cause is upstream.)

## Architecture Onboarding

- **Component map**:
  Raw log → Graph Constructor → Oracle Synthesis → Backtracking Engine → Attribution Engine
  (Graph Constructor includes Subtask Decomposer, OTAR Parser, Edge Builder; Backtracking Engine includes subtask‑, agent‑, and step‑level evaluators; Attribution Engine applies the four screening stages.)

- **Critical path**:
  Raw log → Subtask decomposition → OTAR parsing → Edge construction → (per subtask) Oracle synthesis → Backtracking (subtask → agent → step candidate identification) → Counterfactual screening → Root cause.

- **Design tradeoffs**:
  - Graph granularity: Finer substep division improves precision but risks noise and higher LLM cost; coarser may miss critical dependencies.
  - Oracle specificity: Oracles must be precise enough to catch errors but not so strict they flag correct variations; prompt design is critical.
  - Backtracking depth: Top‑down pruning is efficient but a mistake at a higher level (e.g., misjudging a subtask) can eliminate the true root cause.
  - Screening heuristics: The four‑stage pipeline adds robustness but introduces complexity; misclassification in any stage can lead to wrong attribution.

- **Failure signatures**:
  - Subtask misalignment: Decomposed boundaries do not match logical phases, breaking causal continuity.
  - OTAR extraction errors: Components mixed or missing, leading to incomplete node attributes.
  - Edge construction hallucinations: False or missing causal links.
  - Oracle contradictions: Oracles for consecutive subtasks conflict (e.g., Precondition of S2 conflicts with Goal of S1).
  - Evaluator drift: LLM‑based Feval gives inconsistent binary decisions.
  - Screening false positives: Transient errors labeled as root causes due to missed self‑correction.

- **First 3 experiments**:
  1. Graph Validation: Manually inspect 10 logs. Check subtask alignment with phases, OTAR completeness, and edge correctness against human annotations. Compute precision/recall of edges.
  2. Oracle Quality Assessment: Sample 20 oracles; have experts rate accuracy/completeness of each oracle component. Measure agreement and identify common failures (e.g., missing key evidence).
  3. Controlled Failure Injection: Inject single errors (e.g., altered tool output, omitted constraint) into successful logs at known steps. Run CHIEF and verify root cause attribution. Test different error types to validate each screening stage.

## Open Questions the Paper Calls Out

- **Open Question 1**: How does CHIEF generalize to other MAS failure attribution benchmarks beyond Who&When, particularly those with varied agent topologies and domain complexities? The evaluation is limited to Who&When; future validation on broader systems is needed.

- **Open Question 2**: Can CHIEF correctly attribute failures that stem from cumulative error propagation, i.e., a chain of minor deviations rather than one decisive error? The method focuses on a single decisive root cause; cumulative error propagation remains to be verified.

- **Open Question 3**: How robust is CHIEF to inaccuracies in its upstream components, i.e., the hierarchical causal graph and virtual oracles? The paper acknowledges that upstream inaccuracies may propagate to the final diagnosis, but no quantitative analysis exists.

- **Open Question 4**: To what extent does the choice of base LLM and prompt design affect CHIEF's attribution accuracy, and can prompts be optimized to close performance gaps across models? Performance varies across models (e.g., GPT‑5.2 underperforms DeepSeek‑V3.2), suggesting sensitivity to prompting; systematic analysis is lacking.

## Limitations

- Subtask decomposition misalignment may break causal continuity if graph boundaries do not match logical execution phases.
- Oracle specification issues (under‑ or over‑specification) can cause missed errors or false alarms.
- Edge construction errors (malformed counterfactual patterns or missing links) can corrupt propagation paths.
- Replication unknowns (LLM invocation details, RAG setup, step‑indexing conventions) hinder faithful reproduction.
- Model dependence: Performance tied to DeepSeek‑V3.2; other LLMs may degrade accuracy.
- Benchmark scope limited to Who&When; generalizability to other multi‑agent systems is unproven.
