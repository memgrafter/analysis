# 4OPS: Structural Difficulty Modeling in Integer Arithmetic Puzzles

## Quick Facts
- **arXiv ID:** 2603.25356
- **Source URL:** https://arxiv.org/abs/2603.25356
- **Reference count:** 5
- **Primary result:** Task difficulty in integer arithmetic puzzles is fully determined by the number of distinct input values used in a minimal solution (minimal input usage), which serves as a minimal sufficient statistic.

## Executive Summary
This paper tackles the problem of modeling task difficulty for integer arithmetic puzzles (4OPS) to enable adaptive learning. The authors create an exact dynamic-programming solver that generates a large, labeled dataset of over 3.4 million puzzle instances, with difficulty defined as the minimum number of operations required to reach a target from a given set of integers. Their analysis reveals a precise structural determinant: the number of input values used in any minimal solution (minimal input usage) perfectly predicts the difficulty label. Baseline machine learning models using only surface-level features (e.g., bag statistics, target magnitude) perform poorly (~73% accuracy), but incorporating this single solver-derived feature yields perfect classification. The work demonstrates how an exact symbolic solver can uncover interpretable, minimal sufficient statistics for cognitive task difficulty.

## Method Summary
The research employs an exact dynamic-programming solver to enumerate all reachable values for a given multiset of input integers ("bag") and a target. The solver tracks not just reachability but the minimal expression tree (witness) for each value, recording which subset of input indices was used. This generates a corpus of puzzle instances (bag, target) labeled with solvability, minimum operation count, and structural attributes like minimal input usage. A feature-based analysis then identifies that the size of the input subset in a minimal witness is a perfect predictor of the operation-count-based difficulty label. Finally, machine learning experiments compare the performance of classifiers using only solver-independent surface features versus those augmented with the solver-derived structural feature.

## Key Results
- Generated a dataset of 3,474,900 labeled puzzle instances from 3,861 distinct bags.
- Proved that minimal input usage is a minimal sufficient statistic for difficulty: instances with the same subset size have identical difficulty labels, and different subset sizes imply different labels.
- Baseline ML models on surface features achieved only ~73% accuracy and failed to identify easy instances; adding minimal input usage yielded 100% classification accuracy.

## Why This Works (Mechanism)

### Mechanism 1
**Claim:** Task difficulty (defined as minimum operation count) is fully determined by the number of distinct input values used in a minimal construction (minimal input usage).
**Mechanism:** The exact dynamic-programming solver enumerates all reachable targets and extracts minimal-operation witnesses (optimal expression trees). Analysis of these witnesses across the dataset reveals a perfect correlation: for any two instances with the same minimal input usage, the difficulty label (operation count) is identical. Conversely, different minimal input usage values always correspond to different difficulty labels. This makes subset size a perfect predictor.
**Core assumption:** The solver's definition of minimal operations (shortest expression tree) is a valid and stable proxy for cognitive difficulty.
**Evidence anchors:** [abstract]: "...difficulty is fully determined by the number of input values used in a minimal construction... minimal input usage... serves as a minimal sufficient statistic." [section 7.2]: "Ablation analysis reveals that the number of inputs used in a minimal witness... alone is sufficient to recover the difficulty labels exactly... This establishes subset size as a minimal sufficient statistic for difficulty."
**Break condition:** The mechanism breaks if the difficulty labeling scheme (operation count buckets) is changed. The sufficiency of minimal input usage is proven *for that specific labeling*.

### Mechanism 2
**Claim:** An exact symbolic solver, by providing verifiable minimal witnesses, enables the discovery of interpretable structural determinants that purely data-driven approaches miss.
**Mechanism:** The solver computes the complete closure of reachable values for each input bag and records not just *if* a target is reachable, but *how*—storing the minimal expression tree and which input subset was used. This creates a labeled dataset where features derived from the witness (like subset size) have guaranteed semantic meaning tied to solution structure. Baseline ML models trained only on surface statistics (e.g., bag stats, target magnitude) cannot access this witness structure and thus fail to capture the key determinant.
**Core assumption:** The solution space structure, as captured by minimal witnesses, contains the salient information for this definition of difficulty, and surface statistics are insufficient proxies.
**Evidence anchors:** [abstract]: "We show that difficulty is fully determined by a small set of interpretable structural attributes derived from exact witnesses." [section 4.3]: "This formulation yields minimal witnesses and identifies which inputs are used in optimal constructions." [section 6]: "Baseline machine learning models... fail to reliably distinguish easy instances."
**Break condition:** The mechanism fails if a more expressive set of solver-independent surface features could perfectly predict difficulty (which the paper's experiments disprove for their dataset).

### Mechanism 3
**Claim:** Difficulty arises from *structural necessity* (how many elements must be combined) rather than *surface complexity* (e.g., target magnitude, bag statistics).
**Mechanism:** The solver-derived feature "minimal input usage" abstracts away operational details and operator types, reducing complexity to a single combinatorial count. A problem requiring 5 inputs in any solution is inherently more difficult than one solvable with 2 inputs, regardless of whether the operations are + and - or × and /. This explains why models using features like average bag value or target size perform poorly—they do not measure this core combinatorial coordination demand.
**Core assumption:** For learners in this domain, the primary cognitive load is managing the integration of multiple given quantities into a single expression, not the arithmetic of specific operations.
**Evidence anchors:** [abstract]: "...difficulty emerges from structural necessity rather than surface-level properties." [section 7.3]: "Subset size provides a direct and interpretable measure of compositional demand... reflects how many quantities must be simultaneously coordinated." [section 7.1]: Models augmented with solver-derived features achieve "perfect accuracy," while those without "fail to reliably identify easy instances."
**Break condition:** The mechanism would be challenged if empirical human performance data showed that learners found "low subset-size" problems difficult due to other factors (e.g., non-intuitive operation sequences).

## Foundational Learning
- **Concept: Minimal Sufficient Statistic**
  - **Why needed:** It is the core theoretical result. An engineer must understand that "minimal input usage" is not just a *correlated* feature but a *complete* representation for the defined difficulty. All other information is redundant.
  - **Quick check:** If two puzzles have the same minimal input usage but different target values and different operations in their minimal solutions, must they have the same difficulty label according to the paper's definition? Why?

- **Concept: Witness-Based Dynamic Programming**
  - **Why needed:** This is the algorithmic engine that makes the structural features available. It’s not just solving for reachability, but for optimal structure. An engineer implementing or extending this needs to grasp the subset-indexed DP formulation (DP[S](v)).
  - **Quick check:** How does the DP formulation ensure that the recorded witness is truly minimal (uses the fewest operations) and not just any valid expression?

- **Concept: Hybrid Symbolic-Statistical System Design**
  - **Why needed:** The paper's practical implication is a deployment architecture: use the exact solver offline to generate labels and discover the key feature (subset size), then deploy a lightweight model online that uses only that feature. An engineer must understand this split and its rationale (interpretability, efficiency).
  - **Quick check:** What are the specific trade-offs of using the exact solver in "offline dataset generation" mode versus a purely learned model trained on human response data?

## Architecture Onboarding
- **Component map:** Puzzle Generator & Solver (Offline) -> Feature Extractor (Offline) -> Difficulty Labeler (Offline) -> Online Prediction Model (Runtime) -> Adaptive Sequencer (Application)
- **Critical path:** The entire dependency chain starts with the **Exact Solver's correctness**. If the solver's witness extraction is flawed, the discovered sufficient statistic is invalid. The offline analysis must conclusively show that "minimal input usage" perfectly maps to labels. Only then can the online model be reduced to a lookup or simple threshold on this single feature.
- **Design tradeoffs:** 
  - Exactness vs. Scalability: Solver is exponential but works for fixed-size bags (n=6). Scaling to larger/variable sizes requires approximation, risking the perfect determination property.
  - Generality vs. Specificity: Mechanism proven for specific 4OPS rules; changing rules (e.g., requiring all inputs) likely breaks sufficiency.
  - Offline Cost vs. Online Simplicity: Heavy offline computation enables a trivial, interpretable online model. A purely online learned model would be faster to train but black-box and may miss the structural insight.
- **Failure signatures:**
  - Solver failure: Timeout or memory error on a novel bag configuration. Signifies the offline analysis domain was exceeded.
  - Feature mismatch: In runtime, the computed "minimal input usage" (via an approximated heuristic) does not match the solver's true value for that puzzle, causing incorrect sequencing.
  - Model brittleness: Perfect classification holds only for the solver's specific difficulty buckets (0-2, 3-4, 5 ops). Changing bucket boundaries destroys the mapping.
  - Human divergence: High-performing learners consistently solve "hard" (high subset-size) puzzles quickly, or find "easy" (low subset-size) puzzles tricky, indicating structural difficulty ≠ perceived difficulty.
- **First 3 experiments:**
  1. **Solver Validation:** For a small, manually enumerated set of 100 puzzles, verify the solver's minimal operation count and witness subset size by independent exhaustive search or human reasoning.
  2. **Sufficiency Check:** On a held-out sample from the 3.4M dataset, confirm that the mapping from "minimal input usage" to "min operation count" is injective (one-to-one) and covers all buckets. Calculate the exact conditional entropy H(difficulty | subset_size) and confirm it's 0.
  3. **Baseline Replication:** Replicate the baseline ML experiment: train a model on solver-independent features (bag stats, target) and measure its F1-score, specifically for the "Easy" class. Expect poor performance, confirming the need for structural features.

## Open Questions the Paper Calls Out
**Question 1:** To what extent does minimal input usage correlate with human learners' perceived difficulty and actual performance in solving arithmetic puzzles?
- **Basis:** [explicit] Section 7.5 and the conclusion explicitly state that evaluating alignment between structural difficulty and human-perceived difficulty remains an important future direction.
- **Why unresolved:** The paper uses solver-defined difficulty based on minimum operations, but human difficulty may be influenced by unmodeled factors like strategy familiarity, fluency, or affective states.
- **What evidence would resolve it:** Conduct controlled user studies where learners solve puzzle instances, providing subjective difficulty ratings and accuracy data. Correlate these measures with minimal input usage from the solver, and use cognitive protocols to validate if higher input usage reflects greater coordination demands.

**Question 2:** Is minimal input usage a sufficient statistic for difficulty in other mathematical reasoning domains, such as algebraic equation solving or geometric construction tasks?
- **Basis:** [explicit] The conclusion mentions extending these ideas to richer domains where solution structure governs complexity as a key future direction.
- **Why unresolved:** The findings are specific to the 4OPS integer arithmetic puzzle formulation with its subset-allowed rules; other domains may have different solution space structures or constraints that alter the relationship.
- **What evidence would resolve it:** Develop exact or approximate solvers for target domains, enumerate solution spaces to extract minimal witnesses, and test if a similar structural invariant perfectly predicts difficulty labels. Cross-validate with human performance data if available.

**Question 3:** Does the sufficiency of minimal input usage for difficulty hold under a formulation that requires all input values to be used in solutions, rather than allowing subsets?
- **Basis:** [inferred] The problem definition specifies a subset-allowed formulation, but the paper does not explore the alternative where all inputs must be used.
- **Why unresolved:** Requiring all inputs could fundamentally change the solution space topology, potentially making other structural features relevant or redefining the operational meaning of minimal input usage.
- **What evidence would resolve it:** Modify the solver to enforce all-inputs-used constraints, regenerate the dataset, and re-run the analysis to determine if minimal input usage (now fixed to total inputs) still perfectly classifies difficulty or if new determinants emerge.

**Question 4:** Can accurate difficulty predictions for adaptive sequencing be achieved without exact solving, using only solver-independent features or learned approximations of minimal input usage?
- **Basis:** [inferred] Section 6 shows baseline models on surface features fail, while Section 7 achieves perfection with exact solver-derived features, but the paper does not address efficiency for real-time use.
- **Why unresolved:** Exact solvers may be computationally prohibitive for online adaptive systems; lightweight predictors are needed, but it is unclear if minimal input usage can be approximated from input statistics alone.
- **What evidence would resolve it:** Train machine learning models to predict minimal input usage directly from bag and target features without solver access. Evaluate if these approximations yield high accuracy in difficulty classification and whether they generalize across puzzle distributions.

## Limitations
- **Solver scalability:** Exponential runtime prevents extending to larger input sets (n>6) or richer operations, risking breakdown of subset-size sufficiency.
- **Difficulty metric sensitivity:** Perfect mapping hinges on specific operation-count bucket definitions; alternative bucketing may introduce ambiguity.
- **Human validity:** No empirical data linking solver-defined difficulty to actual learner performance; cognitive factors may diverge from structural predictions.
- **Baseline feature incompleteness:** The ~73% accuracy figure could improve with a more exhaustive surface feature set; necessity of structural features is not fully disproven.
- **Dataset scope:** Restricted to 6-number bags with fixed distributions; puzzles with different constraints may have different determinants.

## Confidence
- **Core claim:** *Minimal input usage perfectly predicts difficulty* – **High** (proven by exhaustive DP on the studied domain; valid within constraints).
- **Baseline failure:** *Surface-only ML models cannot reliably classify difficulty* – **Medium** (experiment shows limited accuracy, but unmeasured feature space leaves uncertainty).
- **Solver reliability:** *DP solver correctly enumerates minimal witnesses* – **High** (algorithmically sound; confidence depends on implementation fidelity).
- **Human generalization:** *Structural difficulty aligns with learner experience* – **Low** (no human data; remains speculative).
