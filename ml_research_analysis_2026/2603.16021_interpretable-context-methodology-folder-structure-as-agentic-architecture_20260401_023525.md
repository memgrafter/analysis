# Interpretable Context Methodology: Folder Structure as Agentic Architecture

## Quick Facts
*   **arXiv ID:** 2603.16021
*   **Source URL:** https://arxiv.org/abs/2603.16021
*   **Reference Count:** 40
*   **Primary Result:** Replaces dynamic multi-agent orchestration with a static, filesystem-based architecture that reduces context window size, produces a U-shaped human intervention pattern, and enables non-technical user control via editable markdown files.

## Executive Summary
The Interpretable Context Methodology (ICM) proposes a paradigm shift for sequential, human-reviewed AI workflows. Instead of complex, dynamic multi-agent frameworks requiring orchestration code, ICM uses a simple, numbered folder structure (`stages/01_name/`, `stages/02_name/`, etc.) and plain-text files (markdown, JSON) to define the entire pipeline. An agent navigates this static filesystem, reading stage-specific context from designated files and writing outputs to intermediate folders for human review. This architectural simplicity drastically reduces the context window per stage (from 40k+ to 2k–8k tokens), creates a predictable "U-shaped" pattern of human intervention, and lowers the barrier to entry by making all pipeline artifacts directly editable without developer assistance.

## Method Summary
The method involves constructing a workspace with a strict hierarchy. A `workspace-builder` questionnaire scaffolds the initial structure. A single orchestrating agent operates by: 1) reading a global `CONTEXT.md` to route a user request to a specific stage folder, 2) loading only the inputs (reference files and prior outputs) specified in that stage's `CONTEXT.md`, 3) executing the defined process, and 4) writing the result to that stage's `output/` directory. Humans review and optionally edit each output file before proceeding. There is no internal dependency tracking; re-running stages after manual edits is manual. The paper provides no formal reproduction package or controlled benchmarks, relying on internal case studies and user reports.

## Key Results
*   Context window reduction from monolithic 40,000+ tokens to staged 2,000–8,000 focused tokens per stage.
*   Practitioner reports (92%) show a U-shaped intervention pattern: heavy human editing at the first (direction-setting) and final (alignment-checking) stages, with lighter intervention in the middle.
*   Successful adoption by three non-technical users who created and executed workspaces by editing markdown files, without requiring developer assistance for routine changes.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** Folder boundaries and explicit stage contracts scope context delivery, preventing irrelevant tokens from degrading model performance.
*   **Mechanism:** Numbered `stages/` folders enforce sequence and containment. Each stage's `CONTEXT.md` Inputs table explicitly lists which Layer 3 (reference) and Layer 4 (working) files to load. The agent reads only these files, not the entire workspace. This architectural scoping delivers a focused context window (2k–8k tokens) instead of a monolithic prompt (>40k tokens).
*   **Core assumption:** LLM performance degrades when processing long contexts containing irrelevant information ("lost in the middle").
*   **Evidence anchors:** [abstract] context window reduction; [section 3.2] total context range per stage. Corpus evidence for the *approach* is absent; universal neighbor papers describe dynamic orchestration.
*   **Break condition:** If LLMs reliably handle very long contexts (e.g., 200k tokens) without degradation, the primary performance benefit of scoping vanishes, though human-interaction benefits remain.

### Mechanism 2
*   **Claim:** Human review gates at stage boundaries, enabled by editable intermediate file outputs, create a U-shaped intervention pattern, improving alignment and reducing rework cost.
*   **Mechanism:** Each stage writes to its `output/` folder. The human must review and optionally edit this file before the next stage runs. This makes human judgment part of the pipeline's state. The U-shape emerges because middle stages are constrained by well-defined inputs (stage 1 output) and rules (Layer 3 reference), while stage 1 sets direction and the final stage verifies fidelity.
*   **Core assumption:** Human judgment is most valuable at pipeline entry (setting direction) and exit (verifying fidelity), with middle stages being more deterministic given clear anchors.
*   **Evidence anchors:** [abstract] 92% U-shape pattern; [section 4.5] detailed pattern description. Corpus on mixed-initiative systems supports human control at breakpoints but not this specific pattern.
*   **Break condition:** If a workflow has no logical breakpoints or all stages are equally creative/ambiguous, the intervention pattern would flatten.

### Mechanism 3
*   **Claim:** Plain-text filesystem interfaces (markdown, JSON) lower the barrier to entry and modification, enabling non-technical users to control complex agent workflows without developer assistance.
*   **Mechanism:** Workspace definition, prompts (`CONTEXT.md`), reference material, and outputs are all editable with a basic text editor. No code deployment or framework configuration is needed for routine changes. The workspace-builder questionnaire encodes best practices into the scaffold.
*   **Core assumption:** The ability to directly inspect and edit all pipeline artifacts is a primary determinant of user autonomy in AI systems.
*   **Evidence anchors:** [abstract] adoption by non-technical users; [section 4.5] three community members with no coding experience. Corpus implies higher technical barriers for code-based frameworks.
*   **Break condition:** If a workflow requires complex conditional logic, external API auth, or stateful sessions not expressible via file edits and local scripts, the plain-text interface becomes insufficient.

## Foundational Learning
*   **Concept:** Unix Pipe-and-Filter & Modular Decomposition
    *   **Why needed here:** ICM's structure borrows the "do one thing" principle. Understanding why one program's output becomes another's input—and why plain text is the universal interface—is key to grasping why a folder structure can replace orchestration code.
    *   **Quick check question:** If Stage 2 must run after Stage 1, what file or folder in the ICM structure enforces this order, and how would you change the sequence?
*   **Concept:** Context Engineering (vs. Prompt Engineering)
    *   **Why needed here:** The core argument is that *what context is loaded* (and when) matters more than a single prompt. A practitioner must think in terms of assembling context layers (identity, routing, reference, artifacts) per stage.
    *   **Quick check question:** For a given stage, what is the practical difference between a file placed in `references/` (Layer 3) and the same file placed in `output/` from the previous stage (Layer 4)?
*   **Concept:** Human-in-the-Loop & Mixed-Initiative Design
    *   **Why needed here:** ICM is designed for *sequential, human-reviewed* workflows. The review gates and editable outputs are the primary interaction model, aligned with principles from Horvitz and Shneiderman.
    *   **Quick check question:** What specific property of the ICM architecture implements Amershi et al.'s guideline "support efficient correction"?

## Architecture Onboarding
*   **Component map:**
    `workspace/CLAUDE.md` (Layer 0) -> `workspace/CONTEXT.md` (Layer 1) -> `workspace/stages/##_name/CONTEXT.md` (Layer 2) -> reads from `workspace/_config/` & `workspace/stages/##_name/references/` (Layer 3) & `workspace/stages/##_name/output/` (Layer 4) -> writes to stage `output/` -> Human
*   **Critical path:** 1. User request -> `workspace/CONTEXT.md` (Layer 1) routes to a stage folder. 2. Agent navigates to that stage's folder. 3. Agent reads stage's `CONTEXT.md` (Layer 2) and its specified Inputs (Layer 3 & 4 files). 4. Agent executes Process, writes to stage's `output/`. 5. Human reviews output file. 6. Loop back to step 1 for next stage.
*   **Design tradeoffs:**
    *   Simplicity vs. Expressivity: Trades dynamic branching/concurrency for a simple, inspectable sequence. Conditional logic requires human intervention or custom scripting.
    *   Generality vs. Scoping: The five-layer hierarchy is a strong convention. Deviating (e.g., putting reference files in `output/`) breaks the context-loading assumption.
    *   Single-Agent vs. Multi-Agent: Uses one orchestrating agent. Sub-agent delegation is driven by the folder structure; no separate agent registry or message-passing bus.
*   **Failure signatures:**
    *   Misalignment: Output in stage N contradicts stage N-1's decisions (e.g., script length vs. research brief). Addressed by final-stage editing.
    *   Context Bloat: Stage's Inputs table includes too many Layer 3 files. Fix by tightening references or splitting the stage.
    *   Stale Output: Human edits stage 1 output after stage 2 has run. Solution: Manually re-run stage 2 (and downstream); ICM has no built-in dependency tracking.
*   **First 3 experiments:**
    1.  Build & Run a Workspace: Use the provided workspace-builder, answer its questionnaire, run the generated pipeline end-to-end, and observe the folder structure and `output/` files.
    2.  Prompt Edit & Rerun: Pick a stage (e.g., `02_script`), edit its `CONTEXT.md` Process section (e.g., change a stylistic instruction), re-run only that stage, and compare outputs.
    3.  Manual Intervention: After stage 1 runs, open its `output/` file and make a substantive edit. Run stage 2 and observe how the agent incorporates the edit, testing the "every output is an edit surface" principle.

## Limitations
*   Evidence is from internal case studies; lacks controlled A/B tests against dynamic multi-agent frameworks.
*   Small adoption sample (3 non-technical users) limits generalizability of accessibility claims.
*   Assumes LLM context degradation is severe; may not hold as models handle longer contexts reliably.
*   Designed for strictly sequential, human-reviewed pipelines; untested for dynamic branching or concurrent agents.
*   No long-term data on workspace maintenance complexity or scaling of folder structures.

## Confidence
*   **Context window reduction (Mechanism 1):** Medium (internal measurement strong, but dependent on external LLM limitations).
*   **U-shaped intervention pattern (Mechanism 2):** Medium-High (consistent practitioner reports, aligned with HCI theory).
*   **Lowered barrier for non-technical users (Mechanism 3):** Medium (anecdotal success, small cohort).
