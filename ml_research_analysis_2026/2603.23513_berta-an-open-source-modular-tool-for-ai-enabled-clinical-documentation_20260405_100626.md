# Berta: an open-source, modular tool for AI-enabled clinical documentation

## Quick Facts
*   **arXiv ID:** 2603.23513
*   **Source URL:** https://arxiv.org/abs/2603.23513
*   **Reference count:** 40
*   **Primary result:** An open-source, modular AI scribe reduced operational costs by 70–95% (to <$30/physician/month) and scaled from 680 to 5,530 monthly sessions across 198 physicians.

## Executive Summary
Berta is an open-source, modular platform for AI-assisted clinical documentation designed to avoid the high costs and data governance issues of commercial AI scribes. It combines speech recognition (ASR) and large language models (LLMs) within an institution's secure cloud infrastructure (e.g., Snowflake). Deployed across Alberta Health Services, it achieved significant adoption (22,148 sessions) and dramatic cost reduction, leading to approval for a major expansion.

## Method Summary
The system uses a Next.js front-end and a FastAPI backend. Its modular design allows pluggable components for ASR (e.g., WhisperX) and LLM processing (e.g., GPT-4o, local models via Ollama). Audio from clinical encounters is transcribed and processed into structured notes using configurable templates. The entire pipeline is deployed within the institution's own cloud environment, ensuring sensitive patient data never leaves the firewall. There is no direct EHR integration; generated notes are copy-pasted by the clinician.

## Key Results
*   Adoption grew from 680 to 5,530 monthly sessions over eight months across 198 physicians at 105 facilities.
*   Operating costs averaged under $30 per physician per month, representing a 70–95% reduction versus commercial alternatives.
*   Successful deployment led to approval for expansion to 850 physicians within the same health system.

## Why This Works (Mechanism)
Berta succeeds by addressing two core barriers: cost and data control. By using open-source models (WhisperX, Ollama) and existing institutional cloud infrastructure (Snowflake), it avoids recurring SaaS license fees. Modularity allows technical teams to swap components (ASR, LLM) based on performance, cost, or privacy needs, preventing vendor lock-in. Deploying behind the institutional firewall satisfies stringent health data governance requirements. The simple copy-paste workflow, while not ideal, minimized integration complexity and allowed rapid pilot deployment.

## Foundational Learning
*   **Modular Architecture:** Separates ASR, LLM, and UI into independent, swappable services. *Why needed:* Enables technology agnosticism, easier updates, and risk mitigation. *Quick check:* Can you replace the LLM backend without changing the front-end?
*   **Local/On-Prem LLM Inference:** Uses models like those served by Ollama running within the institution's network. *Why needed:* Eliminates data egress to third-party API providers, enhancing privacy and potentially controlling compute costs. *Quick check:* Is all PHI (Protected Health Information) confined to the institutional network perimeter?
*   **Cloud-Native Data Stack (Snowflake):** Leverages a enterprise cloud data platform for storage and computation. *Why needed:* Provides scalable, secure, and auditable data handling with existing institutional contracts and expertise. *Quick check:* Are data access controls and audit logs managed by the cloud platform's native tools?
*   **Template-Driven Prompt Engineering:** Uses structured templates to guide LLM note generation. *Why needed:* Standardizes output format and quality, allows clinician customization, and improves consistency over free-form prompts. *Quick check:* Does changing a template visibly alter the structure and content of the generated note?
*   **Workflow-First, Not EHR-First Integration:** Prioritizes a standalone tool with copy-paste output over complex EHR integration. *Why needed:* Drastically reduces deployment time, technical risk, and vendor dependency in a pilot phase. *Quick check:* Can a clinician generate and copy a note without logging into the EHR?
*   **Open-Source Core with Closed Ecosystem Deployment:** The code is public, but the production deployment is a controlled institutional instance. *Why needed:* Enables transparency and community scrutiny while maintaining deployment security and support. *Quick check:* Is the production instance's configuration (API keys, internal URLs) excluded from the public repository?

## Architecture Onboarding
**Component Map:**
Frontend (Next.js) -> Backend API (FastAPI) -> ASR Service (WhisperX/Whisper) & LLM Service (Ollama/GPT-4o) -> Template Engine -> Structured Note. Storage (Snowflake) sits alongside, accessed by Backend for persistence/auditing.

**Critical Path:** Audio File Upload -> Transcription (ASR) -> Text Segmenting -> Prompt Construction (with Template) -> LLM Inference -> Note Rendering -> Clinician Review/Edit -> Copy to EHR.

**Design Tradeoffs:** Simplicity and security over seamless EHR integration. Speed of deployment over perfect UI/UX. Modelled on familiar cloud data stacks over specialized healthcare middleware.

**Failure Signatures:** 1) Backend logs show model loading errors. 2) Frontend network tab shows failed API calls (CORS, timeout). 3) Generated notes are garbled or miss critical sections (transcript quality or LLM prompt issue).

**First Three Experiments:**
1.  **Local Pipeline Test:** Install the repo, run WhisperX and Ollama locally, upload a 30-second WAV file, verify a coherent note is produced.
2.  **Component Swap:** Replace the `ollama` LLM backend with `openai` (using a test key) in the config and observe change in note quality/latency on the same audio.
3.  **Template Edit:** Modify an existing note template (e.g., change `Assessment:` to `Impression:`), regenerate a note, and confirm the new heading appears in the output.

## Open Questions the Paper Calls Out
*   What is the detailed cost breakdown of Snowflake storage, compute, and any egress fees that justify the <$30 per physician per month claim? The paper reports significant cost reduction but lacks granularity for reproducibility.
*   How does the performance (accuracy, edit burden) of local open-source LLMs (e.g., Llama via Ollama) compare against commercial ones (GPT-4o) in real-world clinical use? The modular design permits swaps, but comparative data is not presented.
*   Can the modular architecture be ported to other common cloud data stacks (e.g., Azure Synapse, Google BigQuery) and EHR-integrated workflows without major redesign? Generalizability across heterogeneous health IT environments remains an open question.
*   What are the long-term operational requirements (e.g., IT staff time, model updates, security patches) for sustaining a local deployment at scale? The pilot’s success may depend on yet-unquantified ongoing support costs.
*   Has the system undergone formal usability testing or clinical validation (e.g., note completeness, clinician satisfaction, impact on workflow efficiency)? The adoption metrics are strong, but quality and safety outcomes need systematic evaluation.
*   Does the copy-paste workflow introduce risks of data fragmentation or errors compared to seamless EHR integration, and how do clinicians perceive this trade-off?

## Limitations
*   Exact Snowflake integration details (data models, security policies, cost allocation) are undocumented, hindering cost model reproducibility.
*   The specific template schemas and prompt engineering that achieved good performance with GPT-4o are not specified.
*   Generalizability to other health systems with different IT stacks and cloud contracts is unproven.

## Confidence
*   **High Confidence:** Adoption and usage metrics (sessions, users, hours) are clearly reported and internally consistent.
*   **Medium Confidence:** The claimed <$30/physician/month cost reduction depends on unrevealed Snowflake pricing specifics and local compute optimizations.
*   **Low Confidence:** Assertions about data governance and security lack third-party audit or detailed architectural diagrams for verification.
