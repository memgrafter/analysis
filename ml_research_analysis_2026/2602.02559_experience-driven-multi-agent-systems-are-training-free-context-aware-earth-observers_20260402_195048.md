# Experience-Driven Multi-Agent Systems Are Training-free Context-aware Earth Observers
## Quick Facts
- arXiv ID: 2602.02559
- Source URL: https://arxiv.org/abs/2602.02559
- Reference count: 40
- Primary result: GeoEvolver improves end-to-end accuracy by 12.56 percentage points on average (top 76.56%) across three Earth Observation benchmarks without any model training.

## Executive Summary
Earth Observation tasks often involve tool-intensive workflows and strict spatial constraints that cause standard LLM agents to fail at execution. This paper introduces GeoEvolver, a training‑free multi‑agent framework that overcomes these issues through parallel exploration of tool configurations and contrastive experience distillation into a shared memory bank.

Evaluated on three specialized benchmarks, GeoEvolver yields an average accuracy gain of 12.56% (up to 76.56% on one benchmark) over existing memory and multi‑agent baselines. The results demonstrate that accumulating interaction‑driven experience can effectively replace parameter updates for domain‑specific optimization.

## Method Summary
GeoEvolver orchestrates a multi‑agent pipeline: a retrieval‑augmented orchestrator decomposes a natural language query into sub‑goals. For each query, the system retrieves the most relevant past memory and spawns multiple parallel executor variants (K) that independently attempt the sub‑goals using different tool parameterizations. A judge agent then evaluates the resulting trajectories and selects the most successful one. The system performs contrastive experience distillation: successes and failures are attributed and stored in an evolving memory bank, which augments future retrievals. The entire process is training‑free; no LLM parameters are updated, and performance improves solely through experience accumulation. Step‑level metrics (Tool‑A‑O/I‑O/E‑M) and efficiency (trajectory length ratio) guide selection and memory updates.

## Key Results
- End‑to‑end accuracy improved by an average of 12.56 percentage points over baselines across three benchmarks.
- Top accuracy reached 76.56% on one benchmark, significantly outperforming memory‑based and multi‑agent baselines.
- The approach generalizes across multiple LLM backbones, including GPT‑4o‑mini, without any fine‑tuning.

## Why This Works (Mechanism)
GeoEvolver succeeds by addressing two root causes of LLM agent failures in Earth Observation: (1) mismatches in tool parameters (e.g., spatial reference systems, resolutions) and (2) violation of spatial constraints. Parallel executor variants explore a diverse space of plausible tool configurations, increasing the chance of a valid trajectory. The judge selects the best outcome based on step‑level metrics. Contrastive distillation then extracts the reasons behind successes and failures, storing them as structured memories that future retrievals can use to avoid repeating errors. This interaction‑driven experience accumulation mimics learning from trial‑and‑error without altering model weights, making the system both training‑free and adaptable.

## Foundational Learning
- **Tool chaining**: Why needed? Earth Observation tasks require sequencing multiple remote sensing tools correctly. Quick check: Verify that each step of a trajectory calls a valid tool with arguments matching the tool's signature.
- **Spatial reasoning**: Why needed? Operations must respect coordinate reference systems, extents, and resolutions to avoid misalignment. Quick check: Inspect intermediate data metadata (CRS, shape, transform) before and after each tool call; ensure consistency.
- **Memory augmentation**: Why needed? Accumulated experience helps future queries; memory bank stores distilled lessons. Quick check: After a trajectory, confirm that a new memory entry is created with a clear success/failure label and attribution.
- **Multi‑agent parallel exploration**: Why needed? Different parameterizations can lead to correct solutions; parallel execution explores this space efficiently. Quick check: Ensure that K executor variants produce distinct trajectories (measured by argument differences or tool call sequences).
- **Contrastive distillation**: Why needed? Identifies which aspects of a trajectory contributed to success/failure, enabling targeted memory updates. Quick check: Compare selected best trajectory against failed ones; distillation should highlight differing steps or parameters.

## Architecture Onboarding
Component map:
Orchestrator -> Sub‑goal Decomposition -> Parallel Executors -> Judge -> Memory Bank

Critical path:
1. Query arrives.
2. Orchestrator retrieves top‑1 memory and decomposes query into sub‑goals.
3. K executor variants run in parallel, each generating a trajectory.
4. Judge evaluates trajectories and selects the best one.
5. Contrastive distillation extracts memories from selected and failed trajectories.
6. Memory bank is updated with deduplicated memories.

Design tradeoffs:
- Number of executors (K) vs. cost: more executors increase exploration but raise LLM calls and latency.
- Retrieval memory size vs. relevance: larger memory contains more experiences but risks retrieving less relevant ones; top‑1 retrieval is simple but may miss useful memories.
- Judge weighting (α,β,λ) influences selection; misweights can penalize efficiency or reward irrelevant patterns.

Failure signatures:
- Spatial misalignment errors: broadcast shape mismatches or nodata in rasters indicate CRS/resolution inconsistency.
- Unit inconsistency warnings: out‑of‑range physical values (e.g., NDVI > 1) suggest incorrect unit handling.
- Memory explosion: rapid growth of memory bank without deduplication causes retrieval slowdown and irrelevant memories.
