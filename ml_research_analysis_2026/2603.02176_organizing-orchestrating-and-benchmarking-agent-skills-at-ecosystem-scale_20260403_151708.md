# Organizing, Orchestrating, and Benchmarking Agent Skills at Ecosystem Scale
## Quick Facts
- arXiv ID: 2603.02176
- Source URL: https://arxiv.org/abs/2603.02176
- Reference count: 7
- Primary result: AgentSkillOS achieves top Bradley–Terry scores across three ecosystem scales (200, 1K, 200K skills), substantially outperforming vanilla Claude Code and skill-free baselines.

## Executive Summary
Rapid proliferation of agent skills creates challenges in effective selection, composition, and ecosystem-scale management. This paper presents AgentSkillOS, a system that organizes skills into a capability tree via node-level recursive categorization for efficient discovery and uses DAG-based orchestration (with Quality/Efficiency/Simplicity strategies) to compose multi-skill pipelines.

On a benchmark of 30 multi-format creative tasks spanning data computation, document creation, motion video, visual design, and web interaction, AgentSkillOS achieves top Bradley–Terry scores (0–100) across three ecosystem scales (200, 1K, 200K skills), substantially outperforming vanilla Claude Code and skill-free baselines. Ablations confirm that tree retrieval approximates oracle skill selection and DAG orchestration yields significant gains even with identical skill sets, validating structured composition as key to unlocking skill potential.

## Method Summary
AgentSkillOS operates in two stages: Manage Skills and Solve Tasks. The first stage constructs a capability tree by recursively partitioning the skill set into hierarchical categories using LLM-guided group discovery and skill assignment, stopping when nodes reach a capacity threshold. Active skills are selected by install count; dormant skills are indexed via vector similarity. The second stage retrieves relevant skills by traversing the tree layer by layer, with vector fallback, then generates a DAG orchestration plan using one of three strategies (Quality-First, Efficiency-First, Simplicity-First). The DAG is executed layer-wise, passing artifacts between parallel nodes. Evaluation uses pairwise LLM judgments with position-bias mitigation, aggregated via a Bradley–Terry model.

## Key Results
- AgentSkillOS attains the highest Bradley–Terry scores on 30 diverse creative tasks across all three tested skill ecosystem sizes.
- It significantly outperforms vanilla Claude Code and skill-free baselines, demonstrating the value of structured skill management and orchestration.
- Ablation studies confirm that the capability tree retrieval closely approaches oracle skill selection, and DAG-based orchestration yields substantial quality gains even with the same set of skills.

## Why This Works (Mechanism)
### Mechanism 1: Organizing skills into a capability tree
**Claim:** Organizing skills into a capability tree via node-level recursive categorization enables efficient and broad skill discovery from large ecosystems.  
**Mechanism:** The system recursively partitions the skill set into hierarchical category nodes (starting from 5 fixed top-level domains). Each partition uses an LLM to generate category groups and assign skills, stopping when nodes reach a capacity threshold. This creates a coarse-to-fine index where agents traverse layers to narrow search.  
**Core assumption:** Skills with similar functionality can be grouped into meaningful categories that nest hierarchically, and LLM-guided partitioning can discover these groupings without human annotation.  
**Evidence anchors:**  
- [abstract] "organizes skills into a capability tree via node-level recursive categorization for efficient discovery"  
- [section 2.1] Describes breadth-first tree construction, group discovery, skill assignment, and special-case handling.  
- [corpus] Weak evidence—neighbor paper "Towards Compositional Generalization of LLMs via Skill Taxonomy Guided Data Synthesis" (Li et al., 2026) uses taxonomies for data synthesis, not retrieval; no direct corpus validation of recursive categorization for large-scale skill discovery.  
**Break condition:** If recursive partitioning fails to create semantically coherent categories (e.g., due to LLM hallucination or noisy skill metadata), the tree becomes a noisy index, and retrieval degrades to near-random selection.

### Mechanism 2: Tree-guided skill retrieval approximates oracle selection
**Claim:** Tree-guided skill retrieval approximates oracle skill selection by leveraging hierarchical reasoning to surface both obvious and non-obvious skills.  
**Mechanism:** For a task, an LLM traverses the capability tree layer by layer, selecting relevant category nodes at each level. This coarse-to-fine filtering collects candidate leaf skills, which are then deduplicated, ranked, and optionally user-selected. Skills outside the tree are retrieved via vector similarity as fallback.  
**Core assumption:** Hierarchical traversal allows the LLM to reason about capability domains before drilling to specifics, improving recall of functionally relevant skills that may not be lexically similar to the task.  
**Evidence anchors:**  
- [abstract] "tree-based retrieval effectively approximates oracle skill selection"  
- [section 2.2.1] Details traversal, pruning, and vector fallback; notes this approach "surfaces non-obvious yet functionally relevant skills."  
- [section 4.2] Ablation shows w/ Retrieval (tree only) outperforms w/ Full Pool (flat), and Quality-First (tree+DAG) approaches Oracle (oracle skills+DAG).  
- [corpus] No direct evidence; corpus lacks studies comparing hierarchical vs. flat retrieval in skill ecosystems.  
**Break condition:** If the capability tree misrepresents skill functionality (e.g., skills placed in wrong branches), tree traversal will systematically exclude relevant skills, causing retrieval failure.

### Mechanism 3: DAG-based skill orchestration unlocks composition potential
**Claim:** DAG-based skill orchestration (versus flat invocation) unlocks the potential of multi-skill composition by explicitly managing dependencies and enabling parallel execution.  
**Mechanism:** Retrieved skills are arranged into a directed acyclic graph where nodes represent skill invocations and edges encode data/temporal dependencies. Three strategies (Quality-First, Efficiency-First, Simplicity-First) shape the DAG’s topology (depth, width, edge count). Execution proceeds layer-by-layer, with artifacts passed upstream.  
**Core assumption:** Many tasks decompose into sub-tasks that map cleanly to skills, and the quality of the final output depends critically on the orchestration structure (e.g., preparation/refinement stages, parallelism), not just skill availability.  
**Evidence anchors:**  
- [abstract] "DAG-based orchestration substantially outperforms native flat invocation even when given the identical skill set"  
- [section 2.2.2–2.2.3] Defines DAG construction, strategies, and layered execution with artifact flow.  
- [section 4.2] Ablation in Fig. 5: Quality-First (DAG) beats w/ Oracle Skills (oracle skills, flat) across scales; Fig. 6 shows strategy-specific graph structures.  
- [corpus] No direct evidence; tool-use benchmarks (ToolLLM, API-Bank) evaluate flat tool invocation, not DAG composition.  
**Break condition:** If task decomposition fails (e.g., sub-tasks cannot be mapped to available skills) or DAG generation produces invalid graphs (cycles, missing dependencies), execution will stall or produce incoherent outputs.

## Foundational Learning
- **Capability Tree**  
  - Why needed: It is the core indexing structure that scales to large skill ecosystems by replacing O(|S|) search with hierarchical traversal.  
  - Quick check: How does the per-node capacity threshold affect the tree’s depth and retrieval efficiency?

- **DAG (Directed Acyclic Graph) Orchestration**  
  - Why needed: It provides a formal model for multi-skill composition, enabling explicit dependency management and parallel execution, which flat invocation lacks.  
  - Quick check: Why might Quality-First produce deeper DAGs than Efficiency-First for the same task?

- **Bradley–Terry Model**  
  - Why needed: It aggregates noisy LLM pairwise judgments into a continuous quality ranking, allowing fine-grained comparison across systems.  
  - Quick check: How does position-bias mitigation (swapping order) affect the win matrix before fitting the Bradley–Terry model?

## Architecture Onboarding
**Component map:** TreeBuilder → SkillRetriever → DAGOrchestrator → TaskExecutor; supporting components: RecipePool (vector-triggered task-DAG reuse) and EvaluationHarness (offline pairwise judging)

**Critical path:** Task input drives SkillRetriever to fetch candidate skills via tree traversal and vector fallback; selected skills and task feed DAGOrchestrator to generate structured plan; TaskExecutor runs the DAG layer-wise, passing artifacts between skills to produce final output.

**Design tradeoffs:**  
- Tree construction: Branching factor B balances depth vs. category granularity; per-node capacity C controls leaf precision. Higher B reduces traversal steps but risks coarse categories; lower B increases depth and latency.  
- Orchestration strategies: Quality-First adds refinement stages (higher quality, higher latency); Efficiency-First maximizes parallelism (lower latency, may miss sequential improvements); Simplicity-First minimizes steps (fast, may underuse skills).  
- Active vs. dormant skills: Limiting tree to top K active skills ensures quality indexing but excludes niche skills; vector fallback recovers them at retrieval cost.

**Failure signatures:**  
- Retrieval returns few/no relevant skills: Check tree construction coherence (category grouping, leaf isolation) or traversal prompt.  
- DAG invalid (cycles, missing dependencies): Validate DAG generation ensures layered ordering; adjust orchestration prompt.  
- Execution errors at nodes: Inspect upstream artifact availability and skill input compatibility.

**First 3 experiments:**  
1. Compare tree retrieval (SkillRetriever) against flat full pool retrieval on a subset of tasks; expect higher recall of relevant skills from tree.  
2. Hold skill set constant (oracle skills), compare DAG orchestration (Quality-First) against flat sequential invocation; expect DAG to win on quality.  
3. Run all three strategies on diverse tasks; measure graph metrics (node count, depth, width) and output quality; expect distinct structural patterns (Quality-First deeper, Efficiency-First wider, Simplicity-First fewer nodes).

## Open Questions the Paper Calls Out
1. How can AgentSkillOS automate the discovery, quality assessment, and continuous integration of new skills from open sources without human intervention? The current framework assumes skills are pre-collected; automating would require solving challenges in skill parsing, quality metric definition, and dynamic tree updates.
2. Can skills autonomously refine their own instructions and fix failures based on execution feedback? Skills lend themselves to self-evolution, but the paper does not specify how feedback loops are structured, what triggers updates, or how to ensure stability.
3. Does the fixed branching factor and per-node capacity in capability tree construction generalize to skill ecosystems with highly skewed or niche-heavy distributions? Real ecosystems may have clusters of densely related skills or sparse domains; fixed parameters may lead to unbalanced trees or poor category coherence.
4. To what extent does the benchmark's human-crafted tasks capture the diversity and unpredictability of real-world skill usage scenarios? Tasks may reflect expert intent rather than organic user needs; real users might combine skills in unanticipated ways.
5. Can orchestration strategies be learned or adapted from execution data rather than relying on predefined heuristics? Heuristic strategies may not optimize for user-specific preferences; learned policies could better capture trade-offs.

## Limitations
- Prompt details for LLM components (group discovery, skill assignment, retrieval, DAG orchestration) are absent, hindering exact reproduction and bias assessment.
- The source and format of the 200K skill ecosystem are underspecified (marketplace API, snapshot date, metadata schema), making reconstruction infeasible.
- Evaluation relies on LLM judges; position-bias mitigation is present, but other biases (verbosity, style) may skew scores.

## Confidence
- Tree-based retrieval approximates oracle skill selection: Medium
- DAG orchestration unlocks composition potential: High
- Scalability to 200K skills: Medium

## Next Checks
1. Prompt variation study: Re-run tree construction and DAG generation with multiple prompt formulations; measure retrieval recall (against a gold skill set) and DAG validity (acyclicity, strategy differentiation).
2. Graph pattern verification: On an expanded task set, compute DAG metrics (depth, width, edges) and run statistical tests to confirm Quality-First yields deeper graphs, Efficiency-First yields wider graphs, and Simplicity-First yields fewer nodes.
3. Human-LLM judge correlation: Sample 50 pairwise comparisons (with order swap) and have human experts judge; compute agreement (e.g., Cohen’s κ) with LLM scores to validate evaluation reliability.
