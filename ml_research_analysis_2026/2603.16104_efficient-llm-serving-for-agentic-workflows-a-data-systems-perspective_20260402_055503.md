# Efficient LLM Serving for Agentic Workflows: A Data Systems Perspective

## Quick Facts
- **arXiv ID:** 2603.16104
- **Source URL:** https://arxiv.org/abs/2603.16104
- **Reference count:** 40
- **Primary result:** Helium achieves up to 1.56× speedup over state-of-the-art agent serving systems and up to 100.92× over naive vLLM by eliminating redundancy in agentic workflows.

## Executive Summary
Helium introduces a data systems approach to serving LLM-based agents by treating agentic workflows as query plans with LLMs as first-class operators. Unlike existing per-call serving systems, Helium performs end-to-end optimization across interdependent LLM calls. It proactively caches static prompt prefixes and deterministic operator outputs, and employs a cost-based, cache-aware scheduler that maximizes KV cache reuse. Evaluated on standard agentic patterns and a composite trading workflow, Helium demonstrates substantial latency reductions, proving that workflow-level optimization is essential for efficient agent serving.

## Method Summary
Helium transforms an agentic workflow defined in a Python DSL into a directed acyclic graph (DAG) of LLM invocations and data transformations. An optimizer applies database-style rewrites: dead code elimination, common subgraph elimination, and substitution of cacheable operators with lightweight `CacheFetch` nodes that retrieve precomputed results from a global prompt cache. The system then builds a templated radix tree (TRT) capturing the prefix hierarchy of prompts and operator dependencies. A greedy scheduler assigns operators to workers and orders them to maximize KV cache reuse, while proactively pre-warming GPU memory with static KV states. Execution runs on modified vLLM workers that respect the schedule and leverage continuous batching; results flow back through the DAG, with cached values injected at `CacheFetch` nodes.

## Key Results
- Helium attains up to **1.56× speedup** over state-of-the-art agent serving systems (OpWise, LangGraph, etc.) on standard agentic patterns.
- For naive vLLM serving, Helium achieves up to **100.92× speedup**, highlighting the cost of per-call optimization.
- The global prompt cache combined with proactive KV caching yields high cache hit rates, and the cache-aware scheduler approaches optimal makespan in theory and practice.

## Why This Works (Mechanism)
### Mechanism 1: DAG-based end-to-end optimization
- **Claim:** Modeling agentic workflows as query plans with LLMs as first-class operators enables end-to-end optimization across interdependent calls.
- **Mechanism:** The system parses a workflow definition into a directed acyclic graph (DAG) where each node is an LLM invocation or data transformation. This global view allows the optimizer to apply database-inspired transformations (e.g., common subgraph elimination, cache substitution) that eliminate redundant operators and rewrite dependencies before execution.
- **Core assumption:** Agentic workflows can be expressed as static DAGs with deterministic operators, and their structure reveals exploitable redundancies (e.g., shared prompt prefixes, identical subgraphs).
- **Evidence anchors:** [abstract] "models agentic workloads as query plans and treats LLM invocations as first-class operators." [section 3] Details the parsing of a DSL into a DAG and logical plan optimization (pruning, CSE, cache substitution). [corpus] Corpus neighbors (Autellix, Orla) confirm the trend toward workflow-aware serving but do not directly anchor Helium's DAG optimization approach.
- **Break condition:** Dynamic control flows (e.g., conditional loops, runtime fan-out) that cannot be statically expressed as a DAG would limit the optimizer's visibility and reduce optimization opportunities.

### Mechanism 2: Proactive caching of static content
- **Claim:** Proactive caching of static prompt prefixes and operator outputs avoids redundant LLM inference work within and across batches.
- **Mechanism:** During a profiling or warm-up phase, the system identifies static prompt segments (e.g., system prompts, fixed context) and deterministic operator outputs. These are precomputed and stored in a global prompt cache (for full outputs) and pinned in the GPU KV cache (for prefix states). Subsequent batches bypass the corresponding LLM calls via lightweight `CacheFetch` operators.
- **Core assumption:** Agentic workloads contain significant static or repeatable content (prompts, intermediate results) that remains invariant across queries or batches, and GPU memory can accommodate the precomputed KV states.
- **Evidence anchors:** [section 4] Describes the global prompt cache and substitution of LLM operators with `CacheFetch`. [section 5] Details proactive KV caching: "precomputes and stores the KV cache for these static token sequences in GPU memory." [corpus] KVFlow also targets KV caching but reactsively; Helium's proactivity is a key differentiator not strongly evidenced in neighbors.
- **Break condition:** Highly dynamic prompts (e.g., user-specific, non-deterministic) or extreme memory pressure causing frequent eviction would diminish cache hit rates and precomputation benefits.

### Mechanism 3: Cost-based, cache-aware scheduling
- **Claim:** A cost-based, cache-aware scheduler maximizes KV cache reuse by ordering LLM calls to align with prefix sharing opportunities while respecting dependencies.
- **Mechanism:** The optimizer constructs a templated radix tree (TRT) from the logical plan, capturing the hierarchical prefix structure of prompts and dependencies among LLM operators. A greedy algorithm then schedules operators across workers, prioritizing calls that share longer common prefixes on the same worker and interleaving independent calls to hide dependency latency.
- **Core assumption:** Token usage (prefill/decode costs) can be estimated offline, and the primary bottleneck for throughput is KV cache reuse, not external factors (e.g., API latencies).
- **Evidence anchors:** [section 5] Introduces the TRT: "represents the prefix structure of both static prompt components and dynamic parts" and the scheduling formulation using token steps and precedence delays. [section 5] Algorithm 1 and evaluation show near-optimal schedules and improved cache hit rates over LSPF. [corpus] SGLang's radix cache and online scheduling (LSPF) are precursors; Helium's global TRT-based planning is the novel extension.
- **Break condition:** Unpredictable output lengths or frequent external tool calls (with variable latency) would degrade the accuracy of the cost model and reduce scheduling optimality.

## Architecture Onboarding
### Component map
DSL & Parser → Query Optimizer → Query Processor → Workers (each with modified vLLM engine)  
Global Prompt Cache (shared)

### Critical path
1. User defines a workflow DAG via DSL and compiles it with a data batch.  
2. Optimizer rewrites the DAG: prunes redundant operators, replaces cache-hit operators with `CacheFetch`.  
3. Processor builds TRT from optimized DAG, runs cache-aware scheduling to assign operators to workers and order them.  
4. Processor pre-warms KV cache for static prefixes (first batch) or reuses pinned states (subsequent batches).  
5. Workers execute the nested schedule, batching continuous requests per worker while respecting precedence delays; cache hits avoid prefill.  
6. Results flow back through the DAG, with `CacheFetch` nodes injecting cached values.

### Design tradeoffs
- Cache locality vs. load balancing: The scheduler prioritizes prefix reuse by grouping related operators on the same worker, which can imbalance load if operator costs vary significantly.
- Deterministic caching only: The prompt cache is restricted to greedy (zero-temperature) LLM calls and non-LLM operators to ensure semantic preservation, sacrificing potential reuse from stochastic outputs.
- Offline profiling dependency: Accurate token usage estimates (for scheduling) require pre-profiling the workflow on sample data, adding a one-time cost.
- Memory vs. reuse: Proactive KV caching consumes GPU memory for static prefixes; under memory pressure, vLLM's LRU eviction may evict pre-warmed prefixes, reducing benefits.

### Failure signatures
- Low cache hit rate: Indicates poor prefix sharing detection (TRT construction issue) or aggressive KV eviction due to memory pressure or suboptimal scheduling.
- Load imbalance across workers: Some workers remain idle while others are backlogged. Suggests scheduling heuristic failed to distribute operators effectively.
- Long precedence delays dominating makespan: Dependency chains are not interleaved with independent work, leading to worker starvation. Check if `d(i,j)` values are too high or scheduler is not forcing progress.
- High planning overhead relative to execution: If the workflow is very small or batch size is tiny, optimization latency may dominate. Consider disabling optimization for such cases.

### First experiments
1. **Microbenchmark primitive workflows:** Evaluate Helium against baselines on isolated patterns (Map-Reduce, Debate, etc.) to verify each caching/scheduling component's contribution.
2. **End-to-end complex workflow (Trading):** Test on a composite workflow combining multiple patterns to measure ability to handle realistic scale and interleaved sharing opportunities.
3. **Ablation study:** Disable individual components (proactive KV cache, plan pruning, prompt cache, cache-aware scheduling) on the Trading workflow to quantify marginal contributions.

## Open Questions the Paper Calls Out
1. **Dynamic control flows:** How can Helium's DAG-based abstraction be extended to natively support dynamic control flows (e.g., conditional branching, iterative loops) that are common in advanced agentic patterns? The paper notes this as a limitation and suggests integrating control flow primitives as in TensorFlow.
2. **External tool latency:** Can Helium's cost-based scheduler effectively handle workflows that incorporate external tool calls (e.g., web search, databases) with highly variable and unpredictable latencies? The deterministic cost model may become suboptimal; stochastic models are proposed.
3. **Non-deterministic caching:** To what extent can Helium's caching strategies be applied to non-deterministic LLM operations (e.g., sampling with temperature > 0) without altering output semantics? Current cache is restricted to deterministic operators.
4. **Heterogeneous models:** Does Helium's optimization and scheduling performance hold for heterogeneous agent workflows that use multiple different base LLM models? The scope currently assumes the same base LLM.
5. **Scalability of scheduling:** How does Helium's cache-aware scheduling algorithm scale in terms of optimization time and optimality gap for very large workflows (e.g., hundreds of agents and thousands of LLM calls)? Complexity analysis suggests potential challenges, and empirical evidence beyond 16 branches is lacking.

## Limitations
- Baseline configurations (hardware, software, integration) are unspecified, raising concerns about fairness.
- Dataset sampling details (seeds, splits, preprocessing) are missing, hindering exact reproduction.
- Profiling method for operator statistics not described, which may affect scheduling accuracy.
- Core assumptions (static DAGs, deterministic operators, predictable token usage) may break under dynamic workflows, variable prompts, or external tool latency.
