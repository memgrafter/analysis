# GNNVerifier: Graph-based Verifier for LLM Task Planning

## Quick Facts
*   **arXiv ID:** 2603.14730
*   **Source URL:** https://arxiv.org/abs/2603.14730
*   **Reference Count:** 40
*   **Primary Result:** A graph neural network verifier, trained on synthetically perturbed plan graphs, detects structural errors in LLM-generated task plans (e.g., type mismatches, missing steps) and provides localized feedback to guide an LLM corrector, yielding consistent improvements over state-of-the-art LLM-based verifiers across multiple datasets.

## Executive Summary
GNNVerifier addresses a key weakness of LLM-based planners: their tendency to generate plans with subtle structural defects that break executability, such as type mismatches between tool inputs and outputs or missing intermediate steps. The core innovation is to represent a task plan as a directed attributed graph, where nodes are tool invocations and edges encode dependency relationships (e.g., data flow). A graph neural network (GNN) processes this structure to produce both a global plausibility score and fine-grained risk scores for individual nodes and edges. Crucially, training data is generated automatically by applying controlled perturbations (replacement, deletion, compression) to ground-truth correct plan graphs. During inference, if the global score is low, the high-risk nodes and edges identified by the GNN are used to construct a constrained prompt for an LLM corrector, instructing it to perform minimal, localized edits using a candidate pool of tools. Experiments across four planning datasets show this graph-based, feedback-driven approach outperforms existing verification methods, particularly in accuracy and handling of specific error types like wrong or missing tools.

## Method Summary
The method involves three main stages: 1) **Graph Construction**: A planner's output is converted into an attributed directed graph. Nodes represent tool calls, embedding tool semantics and their alignment to the user request. Edges represent executable dependencies based on a predefined tool compatibility graph. 2) **GNN-based Verification**: A 3-layer GNN performs message passing over the plan graph to produce a graph-level plausibility score and node/edge-level risk scores. The GNN is trained in two stages using graphs synthesized from ground-truth plans. Perturbation operators (REPLACE, DROP, COMPRESS) create "incorrect" variants, with a cost function generating soft targets for graph-level ranking and hard labels for local diagnosis. 3) **Guidance for Correction**: For plans with low global scores, node and edge risks are thresholded to identify editable regions. Candidate tools for replacement or insertion are retrieved from the tool dependency graph. An LLM is prompted with the original plan, these risk scores, and the candidate lists, constrained to output at most 3 JSON-formatted edit operations. The edited plan is re-verified and accepted only if its score improves.

## Key Results
*   GNNVerifier achieves average relative gains of **3.95% in node-F1** (tool selection accuracy) and **8.44% in link-F1** (dependency accuracy) over state-of-the-art LLM verifiers.
*   On the HuggingFace dataset, it yields a **19.93% improvement in accuracy** (exact graph match), highlighting strong gains in producing fully correct plans.
*   The approach shows consistent effectiveness across three different LLM planners (ProAgent, RAP, LLM-Decider) and four benchmark datasets (TaskBench variants, UltraTool), demonstrating broad applicability.

## Why This Works (Mechanism)

### Mechanism 1
*   **Claim:** A graph neural network (GNN) can detect structural inconsistencies in LLM-generated task plans by modeling execution dependencies that LLM-based verifiers miss.
*   **Mechanism:** Plans are converted into directed attributed graphs where nodes are tool invocations and edges encode I/O compatibility and execution order. The GNN performs message passing along these edges, aggregating contextual signals from neighboring steps to produce graph-, node-, and edge-level scores.
*   **Core assumption:** Structural errors (e.g., type mismatches, missing intermediates) manifest as disruptions in the graph’s relational patterns, which can be captured by neural message passing.
*   **Evidence anchors:**
    *   [abstract] states GNNVerifier “represents plans as directed attributed graphs and uses a GNN to produce graph-level plausibility scores and node/edge-level risk scores for diagnosis” and that it “addresses structural errors… which LLM-based verifiers fail to detect.”
    *   [Section 3.4] details the GNN architecture with separate incoming/outgoing message aggregation, explicitly conditioning on request embedding and edge features.
    *   [corpus] The neighbor “GraphReason” [arxiv:2308.09267] similarly uses graph-based verification for reasoning, suggesting a broader trend; however, direct evidence for task planning is limited to the paper itself.
*   **Break condition:** If plan structural defects do not correlate with graph neighborhood features (e.g., errors are purely semantic without relational impact), GNN message passing may not improve over non-graphical models.

### Mechanism 2
*   **Claim:** Perturbing ground truth plan graphs with controlled operators (REPLACE, DROP, COMPRESS) generates diverse, fine-grained training data that teaches the GNN to distinguish correct from incorrect structural configurations.
*   **Mechanism:** Starting from error-free graphs, operators simulate realistic planning failures while preserving type executability (via dependency graph constraints). Each perturbation is logged and mapped to a cost, yielding soft graph-level targets and precise node/edge-level labels.
*   **Core assumption:** Synthetic perturbations produce error distributions sufficiently similar to real LLM-planning failures to train an effective verifier.
*   **Evidence anchors:**
    *   [Section 3.5] defines the perturbation operators, their sampling distributions (e.g., span lengths for DROP), and how they derive supervision (Eq. 9–19). The two-stage training (Section 3.5.3) uses these signals for graph-level ranking and local diagnosis.
    *   [Section 4.3] ablation shows removing perturbation-based supervision (via w/o Stage-I/II) degrades performance, indicating the synthetic data’s utility.
    *   [corpus] No direct corpus support; neighbor papers focus on verification without describing synthetic data generation. This mechanism is primarily evidenced by the paper’s own experimental design.
*   **Break condition:** If real planning errors have patterns not captured by the defined operators (e.g., novel dependency violations), the verifier may fail on out-of-distribution cases.

### Mechanism 3
*   **Claim:** GNN-generated risk scores enable constrained, minimal edits by an LLM correction module, effectively repairing high-risk regions while preserving correct plan segments.
*   **Mechanism:** After verification, nodes/edges exceeding risk thresholds are exposed as edit candidates. The LLM is prompted with these high-risk locations, candidate tools from the dependency graph, and strict output constraints (e.g., at most 3 edits, only from provided candidates), forcing local, plausible modifications.
*   **Core assumption:** An LLM can execute precise, small-scale edits when given structured feedback and candidate pools, even if it cannot self-diagnose the full plan.
*   **Evidence anchors:**
    *   [Section 3.6] describes thresholding risks to define Vedit/Eedit, candidate construction (Eq. 25–28), and the prompt template (Figure 5) that restricts output to JSON edit operations.
    *   [Section 4.4] error analysis shows reductions in Wrong Tool and Missing Tool errors across planners, supporting that risk-guided edits correct these failure modes.
    *   [Section 4.3] ablating any feedback signal (graph/node/edge) worsens accuracy, indicating complementary roles.
    *   [corpus] Neighbor “AdaPlanner” [arxiv:2305.16653] uses feedback for planning but not graph-based; “Plan-and-Act” [arxiv:2503.09572] separates planning/acting, loosely aligning with local correction.
*   **Break condition:** If the LLM ignores constraints (e.g., proposes invalid candidate tools) or makes harmful edits despite low risk scores, the correction step may degrade plan quality.

## Foundational Learning
*   **Concept: Graph Neural Networks for Structured Data**
    *   **Why needed here:** GNNs are the core engine for propagating information along plan execution dependencies, enabling detection of relational errors that sequential models (e.g., LLMs reading steps in isolation) would miss.
    *   **Quick check question:** How does message passing in a directed GNN differ from a simple node-wise MLP in capturing plan structure?

*   **Concept: Attributed Plan Graphs**
    *   **Why needed here:** Representing tools as nodes with I/O types and step semantics, and dependencies as typed edges, provides a uniform interface for GNN processing and candidate generation during correction.
    *   **Quick check question:** Why include both tool-level types (in/out) and step–tool alignment features (Δᵢ) in node attributes?

*   **Concept: Perturbation-Based Self-Supervised Learning**
    *   **Why needed here:** Ground truth plans lack error labels; synthetic perturbations create pseudo-labels for graph/node/edge-level supervision without manual annotation.
    *   **Quick check question:** How does the cost function 𝘤(𝘎ᵖᵉʳᵗ) in Eq. 9 ensure that more severe corruptions yield lower graph scores?

*   **Concept: Constrained LLM Editing**
    *   **Why needed here:** Unconstrained LLM revision risks introducing new errors; limiting edits to high-risk locations and dependency-graph candidates keeps corrections minimal and executable.
    *   **Quick check question:** What stops the LLM from ignoring the provided candidate tool list during editing?

## Architecture Onboarding

### Component map
Plan Graph Constructor -> GNN Verifier -> Perturbation Supervisor (training only) / LLM Corrector (inference)

### Critical path
Input plan (from any planner) -> Graph construction -> GNN forward pass -> If graph score low, compute Vedit/Eedit -> Generate candidate tool lists -> Format prompt with risks/candidates -> LLM returns edits -> Apply edits to graph -> Re-score; accept if improved.

### Design tradeoffs
*   **Graph vs. sequential modeling:** GNNs capture dependencies but require a well-formed dependency graph 𝙶ₜₒₒₗ; if tool relationships are sparse or noisy, graph construction may fail.
*   **Automated vs. manual labeling:** Perturbations avoid annotation cost but may not cover all real error modes (assumption: synthetic ≈ real).
*   **Global vs. local feedback:** Graph score decides whether to edit; node/edge risks localize edits. Over-reliance on any single signal reduces robustness (see ablations).

### Failure signatures
*   Verifier assigns high graph score to clearly flawed plans -> risk thresholds may never trigger -> no correction.
*   LLM returns invalid JSON or uses non-candidate tools -> retry prompt may fail if model ignores constraints.
*   Edits produce lower graph score -> original plan retained; this is conservative but may miss fixable plans.
*   Candidate generation yields empty sets (no compatible tools) -> editable region skipped.

## Open Questions the Paper Calls Out

### Open Question 1
*   **Question:** Can the graph-based verification approach be extended to "execution-aware" verification, where the verifier incorporates real-time execution feedback (e.g., tool call outcomes, runtime errors) rather than relying solely on static plan structure?
*   **Basis in paper:** [explicit] The conclusion explicitly states: "For future work, a possible direction is to move from static verification to execution-aware verification and correction by integrating online signals from real tool calls."
*   **Why unresolved:** The current GNNVerifier operates on the symbolic plan graph before execution. It does not account for dynamic execution failures (e.g., a tool returning an error, timing out, or producing unexpected output), which are common in real-world agent deployments.
*   **What evidence would resolve it:** A new version of the verifier that accepts execution traces (tool call logs, return values, error messages) as additional inputs, with a modified GNN architecture or hybrid model that reasons over both the static graph and dynamic execution outcomes. Empirical validation would require a testbed with real tool execution and failure injection, measuring whether execution-aware signals improve final task success rates beyond static structural verification.

### Open Question 2
*   **Question:** To what extent does the perturbation-based training data generation strategy introduce bias, and how well do models trained on such synthetic errors generalize to *naturally occurring* planning errors made by LLMs in the wild?
*   **Basis in paper:** [inferred] The paper constructs training data by perturbing ground truth graphs with operations like `REPLACE`, `DROP`, and `COMPRESS`. While this creates fine-grained supervision, the authors do not analyze whether these synthetic error distributions match the true error distribution of LLM planners (e.g., whether LLMs more frequently make "wrong tool" errors that are *semantically distant* rather than near-synonym replacements as emphasized in their `REPLACE` operator).
*   **Why unresolved:** The perturbation operators are designed to create "type-executable but semantically corrupted" graphs, but the prevalence and nature of real LLM planning failures (e.g., hallucinations, context window issues) may differ. A model trained on a biased synthetic error distribution might learn spurious patterns and underperform on certain real error types not well-covered by the perturbations.
*   **What evidence would resolve it:** A comparative analysis of error type distributions in synthetic training data versus a held-out set of *real* LLM-generated erroneous plans (annotated by humans). Training separate models on different perturbation strategies and evaluating them on real errors would quantify generalization gaps. Additionally, ablating specific perturbation families (e.g., only `DROP` vs. only `REPLACE`) and measuring performance on corresponding real error subsets could diagnose biases.

### Open Question 3
*   **Question:** Does the graph-based verifier's advantage persist in planning domains where the dependency graph between tools is sparse, noisy, or incompletely specified, compared to domains with dense, clean tool ontologies like the benchmarks used?
*   **Basis in paper:** [inferred] The methodology heavily relies on a predefined `dependency_graph` (`Gtool`) that enforces strict I/O compatibility constraints (`out(t_u) ∩ in(t_v) ≠ ∅`). The candidate tool generation for correction (`C_rep`, `C_ins`) and the design of edge features (e.g., `compat(.,.)`) depend on this graph. The paper evaluates on four datasets (TaskBench, UltraTool) that presumably have well-defined tool ontologies.
*   **Why unresolved:** Many real-world agent scenarios involve third-party tools with undocumented interfaces, evolving APIs, or ambiguous type signatures. If `Gtool` is incomplete or erroneous, the verifier's structural checks and candidate suggestions could mislead the correction process. The paper does not discuss robustness to noise in the dependency graph.
*   **What evidence would resolve it:** Experiments where the provided `dependency_graph` is systematically perturbed (e.g., random edge deletion, introducing incompatible edges, removing tool type definitions). Performance metrics (n-F1, l-F1, Acc) of GNNVerifier vs. LLM-based verifiers under varying levels of graph noise would reveal sensitivity. A resilient verifier should maintain advantage or degrade gracefully.

### Open Question 4
*   **Question:** Can the multi-granularity feedback (graph, node, edge risks) be more tightly integrated with the LLM corrector, rather than using it as a one-shot prompt? Could iterative, interactive verification-correction loops yield further improvements?
*   **Basis in paper:** [explicit] The current framework uses a single round: GNNVerifier scores the plan → LLM performs constrained local edits if `S_r < τ_G` → accept if new score improves. The paper mentions this as the "verification-guided local correction" module. The conclusion's future work hints at more dynamic integration but does not explore it.
*   **Why unresolved:** The correction is a single pass; high-risk regions identified might interact (e.g., fixing one node creates a new risk on an adjacent edge). A multi-round loop where the verifier re-evaluates after each edit could allow progressive refinement. However, this risks edit compounding and increased LLM calls. The paper does not analyze the marginal benefit of multiple correction rounds versus the single-round approach reported.
*   **What evidence would resolve it:** An ablation where the correction loop is run for 1, 2, or more iterations (re-running the verifier after each edit batch), comparing final plan quality and number of successful corrections. Cost-benefit analysis (compute, latency) would be needed to assess practicality.

## Limitations
*   Synthetic perturbation distribution may not fully cover real LLM planning errors, risking verifier overfitting to artificial patterns.
*   Step–tool alignment module `g(s,t)` training details (negative sampling, early stopping) are underspecified, hindering exact reproduction.
*   Candidate generation depends on `G_tool` quality; sparse or noisy tool dependencies yield empty candidate sets, skipping edits.

## Next Checks
1.  **Graph-structure ablation:** Replace the GNN with a Transformer that processes nodes in topological order (using identical input features). Compare verification accuracy on held-out test sets to isolate the specific contribution of message passing for dependency modeling.
2.  **Synthetic-real error alignment:** Manually annotate error types (e.g., tool mismatch, missing step, ordering error) in a random sample of LLM-generated erroneous plans from the test sets. Quantify the similarity/difference between these real error distributions and those produced by the `REPLACE`, `DROP`, and `COMPRESS` perturbation operators.
3.  **Constraint adherence audit:** During correction runs, log all LLM outputs. Programmatically parse the returned JSON to verify: (a) the number of edit operations is ≤ 3, (b) every proposed tool identifier exists in the provided candidate list, and (c) the JSON syntax is valid. Report overall adherence rates and correlate them with actual plan improvement to diagnose corrector reliability.
