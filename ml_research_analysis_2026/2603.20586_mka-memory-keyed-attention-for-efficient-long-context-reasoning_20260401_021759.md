# MKA: Memory-Keyed Attention for Efficient Long-Context Reasoning

## Quick Facts
- **arXiv ID:** 2603.20586
- **Source URL:** https://arxiv.org/abs/2603.20586
- **Reference count:** 29
- **Primary result:** FastMKA matches Multi-Latent Attention perplexity (3.26 vs 3.22 at 16K) while delivering up to 5× faster training throughput and up to 1.86× lower decode latency on Qwen2.5-7B, with gains scaling to 256K context.

## Executive Summary
Memory-Keyed Attention (MKA) addresses the KV cache bottleneck in long-context language modeling through a hierarchical memory system with local, session, and long-term levels. Queries are dynamically routed across these levels via learned weights. FastMKA, its efficient variant, fuses memory sources before attention computation, drastically reducing overhead. Evaluations on Qwen2.5-7B show FastMKA achieves perplexity comparable to Multi-Latent Attention while boosting training throughput by up to 5× and cutting decode latency by up to 1.86× across context lengths up to 256K, offering a practical accuracy-efficiency trade-off.

## Method Summary
MKA structures the KV cache into three memory tiers: L1 (recent local tokens), L2 (session-level summaries), and L3 (long-term external memory bank). For each query, a routing MLP produces soft weights to combine outputs from separate attentions over each tier (full MKA). FastMKA improves efficiency by applying these weights to the memory representations *before* projection, fusing them into a single tensor that is projected once and attended to, collapsing three attention paths into one. L3 retrieval uses vectorized hashing to fetch only the most relevant historical chunks, bounding complexity sub-quadratically.

## Key Results
- Comparable perplexity to Multi-Latent Attention: 3.26 vs 3.22 at 16K context on Qwen2.5-7B.
- Up to 5× faster training throughput: 1614 vs 387 tokens/s at 16K; 742 vs 148 at 256K.
- Up to 1.86× lower decode latency: 8.4 vs 12.8 ms/token at 16K; 26.3 vs 48.9 at 256K.
- Gains hold across model scales and long-context benchmarks.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Hierarchical memory routing reduces effective attention complexity by dynamically selecting relevant memory tiers (L1, L2, L3) per query token, avoiding full quadratic attention over the entire KV cache.
- **Mechanism:** Each query token computes routing weights (via learned MLP) to softly combine outputs from three separate attention computations over different memory sources (local window, session summary, retrieved long-term chunks). The final output is a weighted sum of these per-tier attention results.
- **Core assumption:** Different tokens benefit from attending to memory at different temporal scales (recent, session, distant), and this can be learned per-token without manual heuristics.
- **Evidence anchors:**
  - [abstract]: "hierarchical mechanism with local, session, and long-term memory levels that dynamically routes queries across them."
  - [section 4.1]: "Route-Fused MKA (FastMKA)... fuses these memory sources before attention computation." (Implies original MKA computes separate attentions)
  - [section 5.1]: Presents recursive formulation where output is gated mixture of per-level unnormalized scores.
- **Break condition:** If learned routing weights collapse to selecting only one memory level (e.g., always L1), the mechanism degrades to standard local attention, losing long-range reasoning capability.

### Mechanism 2
- **Claim:** Route-fusion (FastMKA) reduces runtime overhead by combining memory sources *before* KV projection and attention, replacing multiple attention paths with one.
- **Mechanism:** Routing weights are applied to the *memory representations* (L1, L2, L3 tensors) before they are projected to keys/values. This creates a single fused memory tensor `X_fused`, which is then projected once to generate KV cache. Attention is computed once over this fused cache.
- **Core assumption:** The information from different memory levels can be linearly combined in the representation space (pre-projection) without significant loss, and the subsequent single projection is sufficient.
- **Evidence anchors:**
  - [abstract]: "FastMKA, its efficient variant, fuses these memory sources before attention computation."
  - [section 4.1, Algorithm 2 step 6]: `X_fused ← ∑ λ_ℓ ⊙ L_ℓ` followed by single `K,V ← X_fused W_k, X_fused W_v`.
  - [section 6.5.2]: Ablation shows soft routing (used in fusion) outperforms hard routing, implying the fusion itself is effective.
- **Break condition:** If the memory representations are not linearly composable (e.g., L3 contains information in a space orthogonal to L1/L2), fusion could cause destructive interference, harming perplexity.

### Mechanism 3
- **Claim:** Vectorized hashing in L3 memory enables sub-quadratic long-range retrieval by efficiently finding relevant historical chunks without full scan.
- **Mechanism:** The long-term memory (L3) stores past token blocks in a hash table indexed by vectorized hash codes derived from the query. During attention, for a given query block, only the top-R most similar past blocks (by hash similarity) are retrieved and attended to, limiting cost to O(B*R*d) per block.
- **Core assumption:** Semantic similarity between a current query block and relevant past blocks can be approximated by a hash function, allowing recall of pertinent history with bounded operations.
- **Evidence anchors:**
  - [section 4.2]: "Vectorized hashing mechanisms into the L3 memory to facilitate rapid and efficient chunk-based recall."
  - [section 4.4, Algorithm 3 step 12]: `Retrieve ˆ𝛼_𝑖𝑗, ˆ𝑧_𝑖𝑗 via vectorized hash from L3`.
  - [section 5.4]: Theoretical runtime O(B*T*d + B*R*d) with R << T.
- **Break condition:** If the hash function poorly correlates with true semantic relevance, retrieved chunks will be irrelevant, causing accuracy drop on tasks requiring precise long-distance retrieval (e.g., passkey tasks at extreme lengths).

## Foundational Learning
- **Concept: Standard Multi-Head Attention (MHA) & KV cache**
  - *Why needed here:* MKA modifies the core attention computation and cache structure. Understanding standard attention’s quadratic cost and cache growth (O(N) per layer) is prerequisite.
  - *Quick check question:* "For a model with H heads, sequence length N, and head dimension d, what is the memory size of the KV cache (in elements) under MHA? How does this scale with N?"
- **Concept: KV cache compression techniques (MQA, GQA, MLA)**
  - *Why needed here:* MKA is positioned as an alternative/replacement to these. Understanding their trade-offs (MQA/GQA: share KV across heads → loss of diversity; MLA: low-rank compression → added projection cost) explains MKA’s design goals.
  - *Quick check question:* "How does MLA reduce KV cache size compared to GQA? What is a potential downside of the low-rank factorization?"
- **Concept: Block-wise / Tiled attention computation (FlashAttention)**
  - *Why needed here:* MKA’s implementation (especially L1/L2 memory hierarchy and online softmax) builds directly on FlashAttention’s tiling and IO-aware design to fit GPU memory hierarchies.
  - *Quick check question:* "Why is 'online softmax' (scan-based) necessary for tiled attention? What hardware problem does it solve?"

## Architecture Onboarding
- **Component map:**
  1. **Routing Gate:** MLP taking query token as input, outputting 3 softmax weights (λ1, λ2, λ3) per token.
  2. **Memory Levels:**
     - L1: Standard causal KV cache for current/local tokens.
     - L2: Causal session summary (e.g., running mean/EMA of past activations per block).
     - L3: External memory bank of past blocks, indexed via vectorized hash.
  3. **Route-Fusion Module (FastMKA):** Element-wise weighted sum of L1, L2, L3 tensors using routing weights.
  4. **KV Projection:** Single `W_k, W_v` applied to fused memory (FastMKA) or separate projections per level (full MKA).
  5. **Block-wise Attention Kernel:** Modified FlashAttention-style kernel that can incorporate retrieved L3 blocks.
- **Critical path:**
  Training/Inference step for token `t`:
  `Query proj (Q) → Routing MLP (λ) → Fuse [L1_t, L2_t, Retrieve(L3)] → KV proj → Attention(Q, fused_KV) → Output`
  Cache update: Store *fused* K/V for L1 (not raw tokens) in FastMKA.
- **Design tradeoffs:**
  - **Accuracy vs. Speed:** Full MKA (3 attention paths) may reach higher accuracy than FastMKA (1 path) but at 3x compute cost. FastMKA trades a small perplexity increase (~0.04 in experiments) for 3-5x speedup.
  - **Memory vs. Retrieval:** L3 size (R) controls trade-off: larger R improves recall accuracy (Table 8) but increases latency and memory for hash table.
  - **Caching Strategy:** Caching *fused* KV (FastMKA) vs. raw token KV (full MKA). Fusion cache is smaller but may lose granular token-level information for future routing decisions.
- **Failure signatures:**
  - **Degraded perplexity on long-context benchmarks** (e.g., >3.5 PPL on WikiText-2 at 32K) indicates routing failure or insufficient L3 capacity.
  - **Routing collapse** (λ ≈ [1,0,0] for >95% tokens) means the model isn't using multi-level memory, likely due to poor routing MLP training or insufficient regularization.
  - **Latency not scaling subquadratically** suggests L3 retrieval isn't bounding R effectively or hash collisions are high.
- **First 3 experiments:**
  1. **Tier ablation:** Train FastMKA with (L1+L2+L3), (L1+L2 only), (L1 only). Expect: (L1 only) high PPL/low speed; adding L2/L3 improves PPL with minor speed change; confirms hierarchical benefit.
  2. **Routing weight analysis:** Log average λ per layer/position across validation set. Expect: L1 dominant in early layers, L3 increases in later layers; uniform distribution across positions for complex tasks.
  3. **L3 retrieval recall test:** On RULER passkey, vary R (number of retrieved chunks). Expect: accuracy plateaus after R=8; if not, increase L3 capacity or improve hash function.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How does the complexity of the routing mechanism (e.g., depth of the MLP, conditioning on multiple layers or heads) affect the accuracy-efficiency trade-off in MKA?
- **Basis in paper:** [inferred] The paper uses a single-layer MLP for routing and compared only soft vs fixed vs hard routing; more complex designs are not explored.
- **Why unresolved:** The optimal routing capacity is unknown; a more expressive router might better allocate memory tiers but could increase overhead.
- **What evidence would resolve it:** Conduct experiments varying the router's architecture (e.g., number of layers, inclusion of cross-attention) and measure perplexity and latency on long-context benchmarks, identifying the point of diminishing returns.

### Open Question 2
- **Question:** Is the three-level hierarchical memory (L1, L2, L3) optimal, or can additional levels or an adaptive number of tiers further improve performance and efficiency for very long contexts?
- **Basis in paper:** [inferred] The paper fixes three levels and shows ablations where removal of any tier degrades performance, but does not consider adding more levels or adaptively determining the number.
- **Why unresolved:** The hierarchical design space is unexplored; deeper hierarchies might allow finer-grained memory management but may increase routing complexity.
- **What evidence would resolve it:** Implement models with 4 or more memory levels (e.g., adding an intermediate summary tier) and evaluate perplexity, training throughput, and decode latency across context lengths; also test adaptive methods that adjust tier count based on sequence length.

### Open Question 3
- **Question:** Can the L3 long-term memory retrieval be made differentiable or learned end-to-end to improve relevance and reduce the need for hand-tuned vector hashing?
- **Basis in paper:** [inferred] The current retrieval uses vectorized hashing with a fixed top-k; the paper notes this as part of the design but does not explore learning the retrieval process.
- **Why unresolved:** Hand-tuned retrieval may be suboptimal and not adaptable to different data distributions; a differentiable approach could integrate with training and potentially enhance accuracy.
- **What evidence would resolve it:** Replace the hashing-based retrieval with a softmax attention over a compressed memory bank or a learned index, and compare performance on long-range tasks (e.g., passkey retrieval, LongBench) while measuring overhead.

### Open Question 4
- **Question:** How does FastMKA's efficiency and effectiveness scale to context lengths beyond 256K tokens, such as 512K or 1M, and how should hyperparameters (block size, retrieval count) be adjusted?
- **Basis in paper:** [inferred] Experiments are reported only up to 256K context; the theoretical analysis predicts subquadratic scaling but practical limits (e.g., memory bandwidth, kernel launch overhead) may emerge at larger scales.
- **Why unresolved:** Real-world deployment for extremely long contexts is a key use case; without empirical data, it's uncertain if gains hold or if new bottlenecks arise.
- **What evidence would resolve it:** Run scaling experiments at 512K and 1M context lengths, measuring perplexity, throughput, and latency; perform sensitivity analysis on block size and retrieval count to identify scaling trends and potential limits.

## Limitations
- Performance trade-offs at extreme lengths (beyond 256K) are unvalidated; degradation patterns or hash table collision rates for >512K contexts are unknown.
- Robustness on tasks requiring precise long-range retrieval (e.g., needle-in-haystack with complex semantics) or non-causal patterns is unproven.
- Real-world deployment costs (memory bandwidth for hash table lookups, kernel optimization complexity) are not quantified.

## Confidence
- **High:** Efficiency claims (throughput/latency improvements) — directly supported by empirical benchmarks with specific model/context pairs.
- **Medium:** Accuracy parity with MLA (3.26 vs 3.22 PPL) — small margin on single model; statistical significance across diverse architectures unclear.
- **Low:** Generalization across "model scales and long-context benchmarks" — statement lacks breakdown; potential overfitting to evaluated benchmarks not ruled out.

## Next Checks

2. **L3 capacity stress test:** Scale sequence length to 512K+ with fixed L3 retrieval budget *R*; track perplexity and hash retrieval recall to identify saturation points.
