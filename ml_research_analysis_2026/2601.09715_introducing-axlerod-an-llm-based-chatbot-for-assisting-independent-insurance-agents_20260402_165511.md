# Introducing Axlerod: An LLM-based Chatbot for Assisting Independent Insurance Agents

## Quick Facts
- **arXiv ID:** 2601.09715
- **Source URL:** https://arxiv.org/abs/2601.09715
- **Reference Count:** 40
- **Primary Result:** An LLM-based agent- assistive chatbot achieves 93.18% accuracy in policy retrieval tasks and reduces average search time by 2.42 seconds per query.

## Executive Summary
Axlerod addresses the inefficiency of insurance agents manually searching large policy databases by providing an LLM-powered assistant embedded directly into their workflow. Built on a retrieval-augmented generation (RAG) architecture with structured tool calls, it interfaces with Safety Insurance’s internal systems—including a 730,000-policy search engine—to answer natural language queries. Designed for agent-assistive rather than consumer-facing use, the system leverages human expertise to validate outputs, aiming for high accuracy and trust in a regulated domain.

## Method Summary
Axlerod is a RAG-based agent that uses Google Gemini 2.5 Pro to orchestrate three structured tools: `policy_search` (querying a Typesense index), `policy_detail` (fetching full policy records), and `documentation_search` (semantic search over manuals). The LLM decides when to call these tools based on user queries, chains the results, and synthesizes a final answer. The system is built with a custom lightweight framework ("Smoltalk"), FastAPI, and LiteLLM for model routing, and is embedded within the agent’s existing PowerDesk application.

## Key Results
- 93.18% overall accuracy on a 1200-query test set for policy retrieval tasks.
- 99.3% accuracy on bill plan identification subtask.
- Average search time reduction of 2.42 seconds per query.
- Calculated cost of approximately $0.0075 per response.

## Why This Works (Mechanism)
### Mechanism 1: RAG-Powered Policy Search
- **Claim:** Axlerod reduces manual search time by using RAG to locate relevant policies from a search engine.
- **Mechanism:** The LLM translates a user query into a search intent and triggers a `policy_search` tool call to query a Typesense index containing ~730,000 policy records (policy number, holder name, address). Results are returned to the LLM for synthesis.
- **Core assumption:** The policy database is indexed with sufficient metadata (name, address) to support fuzzy matching for common ambiguities.
- **Evidence anchors:** [abstract] describes RAG and tool calls; [section III.B] details Typesense and policy database features.
- **Break condition:** Underlying data is highly fragmented or name ambiguity exceeds the LLM’s ability to request clarification (e.g., >5 results without disambiguating attributes).

### Mechanism 2: Multi-Step Tool Orchestration
- **Claim:** Axlerod handles complex requests by chaining sequential tool calls (e.g., `policy_search` → `policy_detail`) via LLM reasoning.
- **Mechanism:** Given a query, the LLM decides if a tool call is needed. For a name lookup, it calls `policy_search`. If multiple results appear, it asks for clarification. Once a policy number is isolated, it calls `policy_detail` for billing info and generates the answer.
- **Core assumption:** The LLM can reliably generate structured tool calls and reason over returned data to sequence actions.
- **Evidence anchors:** [section III.A] describes the tool call cycle; [section IV.D] shows an example dialogue with successful chaining.
- **Break condition:** LLM incorrectly sequences tool calls (e.g., calls `policy_detail` without a valid policy number) or fails to extract the correct entity from search results.

### Mechanism 3: Agent-Assistive Safety
- **Claim:** Deploying as an agent-assistive tool improves reliability because expert agents can validate outputs and catch hallucinations.
- **Mechanism:** The chatbot is embedded in the agent’s PowerDesk platform. Agents use domain knowledge to interpret the LLM’s responses, which are grounded in retrieved data. The paper posits agents are better than consumers at detecting inaccuracies in nuanced policy language.
- **Core assumption:** Independent insurance agents possess sufficient expertise to critically evaluate chatbot outputs.
- **Evidence anchors:** [abstract] mentions agent-assistive focus; [section I] argues agents can validate outputs and detect hallucinations.
- **Break condition:** Agents over-rely on the system without reviewing data, or policy complexity exceeds even expert intuition.

## Foundational Learning
- **Concept: Retrieval-Augmented Generation (RAG)**
  - *Why needed:* Axlerod must retrieve specific, structured policy data from a large database. Pure LLM generation would hallucinate policy details. RAG grounds responses in real-time, authoritative data.
  - *Quick check:* What are the two main steps in a RAG pipeline for a policy search query, and why is each necessary?
- **Concept: Tool Calling / Function Calling**
  - *Why needed:* The LLM must interact with external systems (Typesense API, policy database). Tool calls provide a structured, deterministic way for the model to request exact data and receive JSON results to reason over.
  - *Quick check:* What is the input (from LLM) and output (to LLM) format of a tool call, and what ensures `policy_detail` is only used after a valid policy number is obtained?
- **Concept: Domain-Specific Data Fragmentation**
  - *Why needed:* Insurance data exists in multiple forms: structured policy databases, semi-structured claims, and unstructured documentation. Axlerod addresses this with separate tools (`policy_search` vs. `documentation_search`) for different sources.
  - *Quick check:* For "What does the commercial general liability policy say about subcontractor coverage?", which tool(s) would likely be invoked and why?

## Architecture Onboarding
- **Component map:** User Interface (PowerDesk widget) -> FastAPI backend -> Smoltalk orchestrator -> LiteLLM gateway -> Gemini 2.5 Pro. Tool functions (`policy_search`, `policy_detail`, `documentation_search`) connect FastAPI to data sources (Typesense, Policy DB, Documentation store).
- **Critical path (happy path for "Find covered vehicles for John Smith's auto policy"):**
  1. Agent types query into UI.
  2. FastAPI receives query, adds session context.
  3. Smoltalk constructs prompt + tool specs, sends to LiteLLM.
  4. LiteLLM forwards to Gemini 2.5 Pro.
  5. Gemini decides to call `policy_search` with `"John Smith"` and `"auto"`.
  6. FastAPI executes `policy_search` -> Typesense -> returns matching policies.
  7. Results fed back to Gemini.
  8. Gemini sees multiple matches, asks clarifying question ("Which city?").
  9. Agent provides city -> new cycle; Gemini calls `policy_detail` with specific policy number.
  10. `policy_detail` returns vehicle list -> Gemini formats final answer -> sent back to UI.
- **Design tradeoffs:**
  - **Simplicity vs. Capability:** Built custom "Smoltalk" microframework instead of LangChain/Semantic Kernel to avoid complexity, trading off advanced features for control and debugging ease.
  - **RAG vs. CAG:** Chose RAG (dynamic query) over Cache-Augmented Generation because policy data is highly dynamic (new policies, changes); CAG's static context window would be ineffective for 730k+ records.
  - **Agent vs. Consumer Focus:** Agent-assistive model constrains scope (no pleasantries) and leverages human oversight, trading broad consumer appeal for higher accuracy/trust in a high-stakes domain.
- **Failure signatures:**
  - High ambiguity: `policy_search` returns >5 results, agent fails to provide disambiguating info (city/address); LLM may pick wrong policy.
  - Tool misuse: LLM calls `policy_detail` with invalid policy number format from malformed `policy_search` result.
  - Context loss: Agent switches to new policy but session memory doesn't update, causing subsequent queries to reference old policy.
  - Documentation mismatch: `documentation_search` returns state-specific procedure not applicable to the policy's state, leading to incorrect guidance.
- **First 3 experiments:**
  1. **Unit Test - Policy Search Precision:** For a known policyholder name/address, verify `policy_search` returns correct policy number as top result; tests index integrity.
  2. **Integration Test - Simple Tool Chain:** Given "What is the due date for policy [known number]?", verify LLM calls `policy_detail` directly and extracts `due_date` correctly from JSON.
  3. **End-to-End Test - Ambiguous Name Resolution:** Query "What is John Smith's auto policy?" with a test set where 3 policies match. Verify system always asks for a city before `policy_detail` and correctly identifies the policy after city is provided.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How does Axlerod's performance generalize to complex, multi-step insurance agent workflows that require synthesizing information across multiple policies, documents, or tools?
- **Basis in paper:** [explicit] Future work calls for "richer empirical validation through... more complex multi-step tasks." Current evaluation (Section IV) tested single, discrete queries.
- **Why unresolved:** No testing of sequential reasoning, tool chaining, or integration of disparate information (e.g., "Compare coverage limits on new policy to existing policy and summarize differences").
- **What evidence would resolve it:** Longitudinal field study with practicing agents performing representative multi-step workflows. Measure accuracy, task completion time, and agent satisfaction vs. traditional methods.

### Open Question 2
- **Question:** What specific design modifications or retrieval strategies are most effective at mitigating errors caused by ambiguous policyholder names, the primary source of retrieval failures?
- **Basis in paper:** [inferred] Accuracy analysis states "majority of these errors are attributed to ambiguities arising from common or frequently occurring names" and system prompts for clarification if >5 results.
- **Why unresolved:** Paper documents problem but does not investigate or propose technical/UX interventions (e.g., re-ranking by metadata, fuzzy matching, clarification dialogue templates). Current prompting strategy unevaluated.
- **What evidence would resolve it:** A/B test or ablation study comparing disambiguation strategies (thresholds, ranking heuristics, dialogue templates) on a held-out set of ambiguous queries, measuring accuracy and clarifying turns.

### Open Question 3
- **Question:** Beyond raw accuracy and time savings, what is the impact of Axlerod on operational metrics like agent trust, adoption rates, and customer satisfaction in a live production environment?
- **Basis in paper:** [explicit] Future work notes need for validating "real-world utility, assessing agent trust, and measuring efficiency." Current study is a controlled internal test with limited users.
- **Why unresolved:** No data on whether agents trust outputs enough for critical interactions, usage frequency in practice, or whether faster retrieval translates to better client outcomes (call time, conversion).
- **What evidence would resolve it:** Field study deploying to a cohort of agents. Measure adoption (usage logs), perceived trust (surveys on hallucination concerns), and business metrics (CSAT, quote turnaround, binding rates) vs. control group.

### Open Question 4
- **Question:** How does the performance and cost-effectiveness of the custom "Smoltalk" microframework compare to established frameworks like LangChain or Semantic Kernel for building similar insurance tool-calling agents?
- **Basis in paper:** [explicit] Future work plans to "position our lightweight Smoltalk framework against established alternatives," but no comparison is presented.
- **Why unresolved:** Claim of advantages (simplicity, integration ease) is unsubstantiated. Metrics like development time, runtime performance (latency, error rates), maintainability, scalability are not benchmarked.
- **What evidence would resolve it:** Controlled experiment rebuilding core Axlerod functionality (three tool integrations) using Smoltalk, LangChain, and Semantic Kernel. Compare lines of code, development time, integration complexity, and performance (throughput, tool-calling accuracy) under identical loads.

### Open Question 5
- **Question:** To what extent does Axlerod's RAG approach effectively handle "fragmented and difficult-to-access internal data sources," and what are the diminishing returns of further RAG optimization versus improving underlying data infrastructure?
- **Basis in paper:** [explicit] Future work identifies "reducing the impact of fragmented and difficult-to-access internal data sources" as a goal. Current system uses separate Typesense index and documentation database.
- **Why unresolved:** Paper does not analyze how data fragmentation (silos, inconsistent formats) limits accuracy or necessitates complex orchestration. Cost-benefit of data consolidation vs. advanced RAG techniques (hybrid search, query expansion) unexplored.
- **What evidence would resolve it:** Error analysis categorizing failures by root cause (e.g., "info not in any source" vs. "retrieved but mis-synthesized"). Simulate/estimate accuracy lift from a hypothetical unified data store. Model trade-offs between RAG sophistication and data engineering effort.

## Limitations
- **Prompt/Tool Schema Opacity:** Exact system prompt, tool descriptions, and few-shot examples are unknown, heavily influencing LLM behavior and reported accuracy.
- **Test Data Undisclosed:** Specific 1200-query test set and linguistic variation distribution are unreported, preventing metric replication.
- **Implementation Black Box:** Details of "Smoltalk" framework, Typesense configuration, and documentation chunking strategy are opaque.
- **Limited External Validation:** Low citation impact and moderate thematic relatedness suggest limited community benchmarking or comparison.

## Confidence
- **High:** Agent-assistive safety premise (human oversight mitigates hallucination risk) is well-argued.
- **Medium:** Core mechanism (RAG + tool calling) is standard and plausible per neighboring literature.
- **Low:** Reported 93.18% overall accuracy and 2.42s reduction; susceptible to prompt engineering, test set bias, and unreported failure modes.
