# Behavioral Fingerprints for LLM Endpoint Stability and Identity
## Quick Facts
- **arXiv ID:** 2603.19022
- **Source URL:** https://arxiv.org/abs/2603.19022
- **Reference count:** 15
- **Primary result:** A black-box monitoring system detects behavioral drift in LLM endpoints (e.g., from weight updates or stack changes) by comparing response distributions using energy distance and sequential e-values.

## Executive Summary
The paper introduces Stability Monitor, a black-box system that detects behavioral changes in LLM endpoints over time. Traditional metrics like uptime and latency fail to capture subtle drifts caused by model updates or infrastructure changes. Stability Monitor periodically samples responses to a fixed prompt set, embeds them, and compares distributional shifts using a nonparametric energy distance statistic coupled with permutation tests. Sequential aggregation of p-values via e-values enables continuous monitoring with controlled false positives. Validation shows it detects model family changes, version updates, quantization shifts, and temperature adjustments. Real-world monitoring across providers reveals stark stability differences, with some endpoints exhibiting constant drift while others remain stable.

## Method Summary
Stability Monitor operates by first establishing a baseline fingerprint: for a fixed set of diverse prompts, it samples numerous responses (e.g., 80 per prompt), embeds each response into a vector, and stores the set of vectors per prompt. At regular intervals, a new fingerprint is generated identically. For each prompt, the energy distance between the baseline and new embedding sets is computed; these are summed across prompts to yield an aggregate distance. A permutation test (by randomly re-splitting pooled embeddings per prompt) produces a p-value indicating whether the observed distance is statistically significant. This p-value is transformed into an e-value (a measure of evidence for change), and a cumulative product of e-values is tracked. When this product exceeds a predefined threshold, a change event is declared and the new fingerprint becomes the baseline. The process repeats indefinitely, logging all data for analysis.

## Key Results
- Detected all controlled changes (model family, version, inference stack, quantization) immediately; a small temperature change (0.7 to 0.6) required about 18 samples.
- Cross-provider monitoring of the same model showed one provider (DeepInfra) triggering change events nearly every sample, while the creator’s endpoint was 100% stable.
- Quantified stability differences via pairwise distance matrices and provider divergence ratios, demonstrating the method’s ability to distinguish endpoint behaviors objectively.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Behavioral changes in an LLM endpoint produce measurable shifts in the distribution of response embeddings for a fixed prompt set.
- **Mechanism:** A fingerprint consists of multiple embedded responses per prompt, forming a distribution. Changes to the model or infrastructure alter this distribution.
- **Core assumption:** The prompt set is diverse and sensitive enough to capture relevant behavioral shifts; the embedding space reflects meaningful semantic differences.
- **Evidence anchors:** Abstract mentions sampling outputs and comparing distributions; section 4.1 details fingerprint construction; neighbors focus on identity drift but not this specific mechanism.

### Mechanism 2
- **Claim:** A nonparametric, permutation-test-based energy distance statistic reliably detects distributional shifts without distributional assumptions.
- **Mechanism:** Energy distance is computed per prompt between two fingerprint sets and summed. Permutation test (pooling and re-splitting embeddings) yields a p-value; low p indicates unlikely under null hypothesis of identical distributions.
- **Core assumption:** Permutation test approximates the null distribution correctly; summed statistic aggregates evidence meaningfully across prompts.
- **Evidence anchors:** Section 4.2 describes energy distance summation and permutation test; section 2 justifies energy distance choice; corpus neighbors use different detection methods.

### Mechanism 3
- **Claim:** Sequential aggregation of p-values using e-values enables continuous monitoring with controlled false positive rates and optional stopping.
- **Mechanism:** Each monitoring round produces a p-value, converted to an e-value (e.g., via methods from references [9,12]). Cumulative product of e-values is compared to threshold; exceedance triggers change event and baseline reset.
- **Core assumption:** The e-value process provides valid, anytime-valid statistical evidence; the chosen e-variate transformation is appropriate.
- **Evidence anchors:** Section 4.3 explains sequential evidence accumulation; section 2 mentions streaming detection; references [9,12] are theoretical on e-values; neighbors do not implement this for LLM monitoring.

## Foundational Learning
- **Concept:** Energy Distance as a Distribution Metric  
  **Why needed:** Parameter-free metric to compare sets of embedding vectors without assuming normality.  
  **Quick check:** When is energy distance zero between two distributions?  
  *(Answer: When the distributions are identical, under mild conditions.)*

- **Concept:** Permutation Test for Nonparametric Significance  
  **Why needed:** Model-free p-value computation for energy distance, avoiding distributional assumptions.  
  **Quick check:** Why does random shuffling of pooled data simulate the null hypothesis of no difference?  
  *(Answer: It breaks any assignment structure, making group labels exchangeable under the null.)*

- **Concept:** E-values and E-processes for Sequential Monitoring  
  **Why needed:** Allow continuous monitoring with error rate control over indefinite sequence, essential for high-cadence checks.  
  **Quick check:** How does an e-value differ from a p-value in sequential testing?  
  *(Answer: An e-value is a non-negative random variable with expectation ≤1 under the null; it can be multiplied sequentially to form an e-process that controls false positives.)*

## Architecture Onboarding
**Component map:**  
Stability Monitor Worker -> Database -> Stability Arena Web App  
Provider API Clients -> Stability Monitor Worker

**Critical path:**  
Baseline fingerprint F0 -> Timer triggers -> Generate new fingerprint Fi -> Compute p-value comparing Fi to F0 -> Update cumulative e-value Mi -> If Mi > threshold, log event, set Fi as new baseline; else await next trigger.

**Design tradeoffs:**  
- Black-box vs. white-box: Universal applicability but no root-cause insight.
- Fixed prompt set vs. adaptive: Simplicity and comparability vs. risk of missing unprobed changes.
- Frequency vs. cost: Faster detection vs. higher API load and expense.
- Summed aggregation vs. per-prompt: More power vs. loss of change localization.

**Failure signatures:**  
- False positive: Change event despite no real update, likely due to high inherent nondeterminism from provider infrastructure.
- False negative: No event after real change, possibly due to subtle change or insensitive prompt set.
- Stuck baseline: Baseline too old, all new p-values high, preventing future detection (mitigated by reset on event).

**First 3 experiments:**  
1. Reproduce controlled temperature change: Run monitor on local endpoint, change temperature from 0.7 to 0.6, verify event after ~18 samples.
2. Cross-provider same-model drift: Monitor same model on two providers (e.g., kimi-k2-0905-instruct), compute pairwise distance matrix and divergence ratio; expect high instability on one vs. stable on other.
3. Infrastructure change simulation: On self-hosted vLLM, switch inference engine to Hugging Face Transformers or toggle a CUDA kernel; verify immediate change detection.

## Open Questions the Paper Calls Out
1. Can Stability Monitor distinguish between infrastructure-induced nondeterminism and discrete model updates as sources of behavioral change?
2. What underlying factors explain the observed substantial stability differences between providers hosting the same nominal model?
3. How does the selection of the fixed prompt set used for fingerprinting impact detection sensitivity and robustness across diverse model changes?
4. What is the optimal strategy for setting the sequential detection threshold (via e-values) to balance false alarms and detection delay under operational constraints?

## Limitations
- Exact prompt set, per-prompt sample counts, and embedding model are unspecified, hindering precise replication and affecting sensitivity.
- Precise e-value construction and threshold calibration are not detailed; assumed simple transformation may not match true method, compromising false positive guarantees.
- Cadence and sample size choices are empirical without theoretical justification; optimal trade-offs between detection speed and cost remain unclear.
