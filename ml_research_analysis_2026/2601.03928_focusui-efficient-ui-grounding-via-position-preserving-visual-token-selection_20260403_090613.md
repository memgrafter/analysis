# FocusUI: Efficient UI Grounding via Position-Preserving Visual Token Selection
## Quick Facts
- **arXiv ID**: 2601.03928
- **Source URL**: https://arxiv.org/abs/2601.03928
- **Reference count**: 40
- **Primary result**: Improves UI grounding accuracy by 3.7% on ScreenSpot-Pro while reducing inference time by 1.44× and memory by 17% at 30% token retention via position-preserving token selection.

## Executive Summary
FocusUI tackles the inefficiency of UI grounding in high-resolution screenshots, where thousands of redundant visual tokens burden multimodal models. It introduces a two-part solution: a Query-Guided Saliency Scorer that selects relevant image patches using fused supervision from bounding-box overlap and UI-graph priors, and a PosPad strategy that compresses dropped token sequences into single position-preserving markers. On ScreenSpot-Pro, FocusUI-7B achieves a 3.7% accuracy gain over GUI-Actor-7B. Even with only 30% of visual tokens retained, accuracy drops by just 3.2% while delivering 1.44× faster inference and 17% lower peak GPU memory. General pruning methods fail catastrophically without PosPad, underscoring the importance of spatial continuity.

## Method Summary
FocusUI comprises two key innovations. First, a lightweight Query-Guided Saliency Scorer predicts patch-level relevance by combining query and patch embeddings via a self-attention layer, followed by tanh and L2 normalization. It is trained with fused supervision: an instruction-conditioned bounding-box overlap score (weight λ=0.8) and a rule-based UI-graph prior using union-find with threshold τ=2. Second, PosPad replaces each contiguous dropped token sequence with a single learnable `<pos pad>` token placed at the last index of the sequence, preserving spatial coordinates for M-RoPE. The training proceeds in two stages: pre-train the saliency scorer for one epoch (LR 1e-4), then fine-tune the full model for one epoch (LR 5e-6) with a combined loss including instruction-to-patch, next-token prediction, and attention objectives. The retention ratio r is uniformly sampled per sample during training to enable flexible token budgets.

## Key Results
- On ScreenSpot-Pro, FocusUI-7B improves accuracy by 3.7% over GUI-Actor-7B.
- At 30% token retention, accuracy drops only 3.2% relative to full retention, while achieving 1.44× faster inference and 17% lower peak GPU memory.
- General pruning methods without PosPad incur catastrophic performance drops, confirming the necessity of position preservation.

## Why This Works (Mechanism)
FocusUI’s efficiency stems from two synergistic mechanisms. The Query-Guided Saliency Scorer identifies task-relevant image patches early, discarding background or irrelevant UI elements before they enter the large language model. This is supervised by a fused signal: a spatial overlap score that grounds the instruction to visible UI components, and a structural prior from a UI element graph that encourages coherence among selected patches. PosPad then maintains spatial continuity by inserting a single marker at the end of each dropped patch run, ensuring that the model’s positional encodings (M-RoPE) retain correct raster-scan coordinates despite the shorter sequence. Together, these reduce computational cost without compromising the fine-grained localization required for UI grounding.

## Foundational Learning
- **Visual token pruning**: Trimming non-essential image patches to reduce sequence length. *Why needed*: High-resolution screenshots produce thousands of tokens, causing slow inference and high memory. *Quick check*: Ablate token retention ratio and measure accuracy drop; ensure pruning retains task-relevant regions.
- **Position-preserving token merging**: Replacing dropped sequences with markers that retain spatial coordinates. *Why needed*: Standard token dropping misaligns positions, breaking models that rely on absolute coordinates (e.g., M-RoPE). *Quick check*: After dropping, verify that retained tokens and markers have correct (h,w) coordinates matching original raster grid.
- **Query-guided saliency scoring**: Using the natural language instruction to bias patch selection. *Why needed*: Relevance is instruction-dependent; static pruning would discard important context. *Quick check*: Compute recall@K% of ground-truth bounding box patches; expect higher recall when query is used vs. uniform sampling.
- **Fused supervision**: Combining bounding-box overlap and UI-graph prior for training the saliency scorer. *Why needed*: Bounding-box supervision alone may yield noisy or sparse signals; UI-graph prior adds structural consistency. *Quick check*: Visualize saliency heatmaps; ensure they respect UI element boundaries and align with instruction.
- **M-RoPE (Multi-dimensional Rotary Position Encoding)**: Encodes row and column coordinates of image patches. *Why needed*: Provides spatial awareness for precise localization. *Quick check*: Confirm that model uses (h,w) coordinates from patches and pos pads in attention computation.
- **Two-stage training**: Pre-train saliency scorer then fine-tune full model. *Why needed*: Separates learning of patch selection from language grounding, stabilizing training. *Quick check*: Compare full joint training vs. two-stage; expect lower loss variance and better convergence with two-stage.

## Architecture Onboarding
Component map: Vision Encoder -> Saliency Scorer -> PosPad -> LM Backbone -> Action Head

Critical path: Input image is split into patches and encoded. Saliency Scorer ranks patches using query embedding. PosPad selects top-K patches, compresses dropped runs, and inserts `<pos pad>` tokens. The resulting sequence (retained patches + pos pads + text tokens) is fed to the LM. The Action Head takes the hidden state at the `<ACTOR>` token, attends over retained patch features, and predicts the target click location.

Design tradeoffs: Retention ratio directly trades accuracy for efficiency; the saliency scorer adds minimal overhead but requires careful supervision; PosPad is simple but relies on correct coordinate mapping; M-RoPE compatibility limits backbone choice.

Failure signatures: Low patch recall indicating poor saliency scoring; mismatched coordinates after PosPad; no memory reduction despite token dropping (e.g., pos pad count too high); training instability in stage 2 (loss spikes).

First three experiments:
1. Validate saliency scorer: compute Patch Recall@50% on validation set; aim for >60% to ensure effective selection.
2. Test PosPad coordinate integrity: for a fixed image, log (h,w) of each token before and after PosPad; ensure retained patches unchanged and pos pads adopt last dropped patch’s coordinates.
3. Benchmark efficiency: run inference with r=30% and r=100% on identical hardware; measure tokens per sequence, throughput, and peak memory; verify ~1.44× speedup and ~17% memory reduction.

## Open Questions the Paper Calls Out
- **Open Question 1**: How can FOCUSUI be extended to efficiently handle multi-round UI interactions by exploiting temporal redundancy?
- **Open Question 2**: Can the Query-Guided Saliency Scorer be trained without requiring ground-truth bounding box annotations?
- **Open Question 3**: Is the PosPad position-preserving strategy generally compatible with vision-language models beyond the Qwen family?
- **Open Question 4**: Why does placing the PosPad marker at the end of each dropped contiguous sequence achieve the best performance, and can this be formally justified?

## Limitations
- Exact saliency scorer architecture (heads, dropout, normalization order) is unspecified, requiring assumptions that may affect performance.
- Training configuration details (loss weights beyond λ, optimizer warmup, gradient clipping) are missing, potentially impacting convergence.
- Mapping between "max pixels" and actual patch count is ambiguous due to potential vision encoder downsampling.
- Baseline comparison with GUI-Actor-7B may be unfair if not re-trained under identical conditions.

## Confidence
- **Accuracy improvement (3.7% on ScreenSpot-Pro)**: Medium – strong result but dependent on unreproduced baseline and missing details.
- **Efficiency gains at 30% retention (1.44× speedup, 17% memory reduction)**: Medium – plausible but requires identical hardware and software verification.
- **PosPad necessity (catastrophic failure of general pruning)**: Medium – needs confirmation of tested pruning methods and failure severity across UI distributions.
