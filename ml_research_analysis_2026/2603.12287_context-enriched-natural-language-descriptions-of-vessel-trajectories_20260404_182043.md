# Context-Enriched Natural Language Descriptions of Vessel Trajectories

## Quick Facts
- **arXiv ID**: 2603.12287
- **Source URL**: https://arxiv.org/abs/2603.12287
- **Reference count**: 30
- **Primary result**: A framework segments noisy AIS trajectories into mobility-annotated episodes, enriches them with multi-source context (ports, weather, bathymetry), and enables LLMs to generate accurate, faithful natural language descriptions of voyages.

## Executive Summary
Raw AIS data is noisy, sparse, and lacks semantic context, making it difficult for humans and machines to interpret vessel movements. This paper introduces a framework that first processes raw AIS into a structured, semantic representation by detecting mobility events (stops, turns) and segmenting trajectories into episodes. Each episode is then enriched with external geospatial and environmental context (ports, weather, depth). This enriched JSON is fed to a Large Language Model via a carefully engineered prompt, which synthesizes concise, factual natural language narratives of the voyage. Evaluation on 460 real trips shows that larger models (e.g., gpt-oss-120b) produce highly relevant, faithful, and correct descriptions with very low statistical errors, while smaller models struggle with calculation.

## Method Summary
The framework operates in three deterministic stages. First, a rule-based preprocessor cleans raw AIS messages and annotates each point with a mobility label (e.g., STOPPED, TURNING) using velocity and heading thresholds. Second, a segmentation engine groups annotated points into trips (between stops or long gaps) and contiguous episodes (sub-sequences sharing a label), computing per-episode statistics like duration and distance. Third, a context enricher performs spatial and temporal joins between each episode's geometry and external data sources (OpenStreetMap for ports/straits, Copernicus for weather, GEBCO for bathymetry). The final output per trip is a JSON array of enriched episodes. This JSON, combined with a fixed prompt that prohibits external knowledge, is sent to an LLM to generate a two-part output: a narrative description and aggregated statistics.

## Key Results
- Larger LLMs (gpt-oss-120b) achieve high description quality: mean relevance 4.91, faithfulness 4.96, correctness 4.69 (on a 1-5 scale).
- Statistical estimation errors are very low for top models: mean duration deviation 1.53%, mean distance deviation 0.89%.
- Context enrichment is highly effective: ports are identified in 100% of STOP episodes; geospatial features (straits, capes) are added to 63% of SAILING episodes.

## Why This Works (Mechanism)
### Mechanism 1: Semantic Compression via Mobility Annotation
Raw AIS point clouds are transformed into a discrete sequence of mobility-annotated episodes (STOPPED, SAILING, TURNING). Rule-based filters on speed and heading detect pivotal behavioral shifts, drastically reducing spatiotemporal complexity and introducing relational semantics. This structured intermediate representation is essential for LLM comprehension.
- **Core assumption**: Meaningful vessel behavior can be reliably abstracted from velocity vector patterns in cleaned AIS data.
- **Break condition**: Failure to detect key events (e.g., due to extreme noise or atypical motions) corrupts the entire downstream input.

### Mechanism 2: Grounding with Multi-Source Context
Each episode geometry is spatial-joined with static (ports, straits) and dynamic (weather, bathymetry) geospatial layers. This attaches causally relevant, domain-specific facts (e.g., "crossing Fehmarnbelt under west winds BF4"), grounding mobility patterns in external knowledge and enabling factual, explainable narratives.
- **Core assumption**: Relevant context exists in aligned space-time data sources and is necessary for explanatory descriptions.
- **Break condition**: Temporal-spatial misalignment (e.g., wrong weather timestamp) or coarse grids attach irrelevant features, misleading the LLM.

### Mechanism 3: Constrained LLM Synthesis via Prompt Engineering
A fixed, detailed prompt defines the LLM's role, explicitly limits source material to the provided JSON, specifies unit interpretations, and mandates a structured output (narrative + JSON stats). This creates a "closed-book" task that constrains the model's output space, reducing hallucination and guiding numerical aggregation.
- **Core assumption**: State-of-the-art LLMs can follow complex instructions and perform reliable arithmetic on provided structured data.
- **Break condition**: Model biases or reasoning limits cause it to ignore or misinterpret input facts, especially in smaller models, leading to unfaithful outputs.

## Foundational Learning
- **Concept: Semantic Trajectories**
  *Why needed*: The framework's core abstraction replaces raw spatiotemporal points with a sequence of semantically meaningful episodes (stop, sail, turn) linked to context, enabling machine readability.
  *Quick check*: What is the key difference between a raw AIS point sequence and a "semantic trajectory" episode?
- **Concept: Mobility Event Detection**
  *Why needed*: The first computational step identifies behavioral primitives via rules (e.g., speed <0.5 knots for stops, heading Δ >5° for turns); understanding these thresholds predicts generated episodes.
  *Quick check*: How would you distinguish a "TURNING" episode from a "MANEUVERING" episode based on heading change?
- **Concept: Contextual Grounding via Spatial Join**
  *Why needed*: Enrichment depends on spatial operations (point-in-polygon, line-proximity) to attach features like port names or crossing straits; misunderstanding this leads to incorrect context.
  *Quick check*: What operation would you use to find if a SAILING episode's line geometry intersects a "Protected Marine Area" polygon?

## Architecture Onboarding
**Component map**: Preprocessor -> Mobility Annotator -> Segmentation Engine -> Context Enricher -> Formatter -> LLM Interface

**Critical path**: AIS messages -> Annotated points -> Episodes (with stats) -> Context attachment -> JSON trip -> LLM prompt -> NL description.

**Design tradeoffs**:
- Annotation rigidity: Fixed thresholds (0.5 kn, 5°) are simple but may not generalize to all vessel types; parameterization is possible.
- Context freshness: Using forecast NetCDF data risks temporal mismatch with actual observed conditions; historical context is safer for retrospective analysis.
- LLM cost/latency: Larger models (120B) yield better results but are slower and more expensive; smaller models may be unacceptable due to miscalculation.

**Failure signatures**:
- Annotation failure: Excessively fragmented or merged episodes → nonsensical narrative.
- Context failure: "placemarks" field empty on SAILING episodes crossing known straits → check spatial index/coordinate systems.
- LLM failure: JSON summary stats deviate >10% from ground truth or narrative includes values not in input JSON → low faithfulness score.

**First 3 experiments**:
1. **Unit test annotation**: Feed a raw AIS snippet with a known stop (speed ~0 for 30 min). Verify annotator tags points as STOPPED and segmentation creates one trip with a STOP episode at that location.
2. **Validation of context retrieval**: For a SAILING episode geometry known to cross a strait (e.g., Fehmarnbelt), check that the "placemarks" field includes that strait name from OSM. Also verify weather NetCDF is sampled at correct timestamp.
3. **End-to-end LLM audit**: Take a 3-episode trip JSON. Run through full pipeline. Compare LLM's output narrative against the JSON line-by-line to catch any inserted/omitted facts or misstated numbers (e.g., duration of episode 2).

## Open Questions the Paper Calls Out
- **Open Question 1**: How can vessel interactions across multiple trips be integrated into context-enriched trajectory descriptions to improve maritime safety analytics?
- **Open Question 2**: To what extent do AI-generated trajectory descriptions align with official nautical sailing directions, and can deviations indicate navigational anomalies?
- **Open Question 3**: Why do smaller LLMs exhibit large errors in estimating trip statistics (duration, distance), and how can their numerical reliability be improved for spatiotemporal data?
- **Open Question 4**: What factors limit the coverage of contextual enrichment (e.g., geospatial features only added to 63% of sailing episodes), and how can the framework ensure more comprehensive context integration?
- **Open Question 5**: How well does the framework generalize to other vessel types (e.g., cargo, tanker) and geographic regions beyond the Danish maritime study area?

## Limitations
- Parameter values for mobility event detection (speed <0.5 knots, heading deviation >5°, gap duration) are not explicitly reported; only defaults are mentioned.
- Context data sources (specific OSM extract, Copernicus product, GEBCO resolution) are not specified; enrichment may differ in other setups.
- Ground truth formulas for trip duration and distance are absent; reported estimation errors cannot be independently verified.
- Evaluation metrics rely on LLM-as-a-judge or unspecified human ratings; potential bias affects score validity.
- The 460-trip test set may not represent diverse vessel types or regions, limiting generalizability.

## Confidence
- **Segmentation into mobility episodes**: Medium
- **Multi-source context enrichment**: Medium
- **LLM description quality** (relevance, faithfulness, correctness): Medium
- **Estimation errors** (duration deviation 1.53%, distance 0.89%): High

## Next Checks
1. **Parameter sensitivity analysis**: Run the pipeline with varied mobility detection thresholds (e.g., speed cutoffs 0.3–1.0 knots, heading change 3–10°) to assess stability of episode boundaries and LLM output metrics.
2. **Context correctness audit**: For a random sample of episodes, manually verify that attached placemarks (ports, straits) and weather values match authoritative sources and are temporally aligned.
3. **Ground truth recomputation**: Using raw AIS points, compute trip duration and total sailing distance with standard geodesic calculations; compare against the framework’s aggregated statistics to confirm error percentages.
