# mtslearn: Machine Learning in Python for Medical Time Series

## Quick Facts
- **arXiv ID:** 2603.29432
- **Source URL:** https://arxiv.org/abs/2603.29432
- **Reference count:** 0
- **Primary result:** mtslearn achieves 96% accuracy on COVID-19 mortality prediction and 97% accuracy on sepsis early diagnosis, though sepsis recall is low at 0.24.

## Executive Summary
mtslearn is an end-to-end Python toolkit designed to bring machine learning to medical time-series data in clinical practice. It addresses the challenge of heterogeneous data formats (wide, long, flattened) by providing a unified interface that automatically parses and aligns raw clinical tables. The toolkit integrates a full pipeline—from data processing and feature engineering to model training and evaluation—into a cohesive workflow that can be executed in just a few lines of code. Its modular classifier architecture supports both static and temporal prediction tasks and allows incorporation of custom models. Validated on two clinical tasks, it delivers high accuracy for COVID-19 mortality prediction (96%) and sepsis early diagnosis (97%), though the latter suffers from poor sensitivity for the minority class.

## Method Summary
The core of mtslearn is a Processor class that ingests raw clinical data in one of three tabular schemas (wide, long, or flattened) and converts it into a canonical wide format indexed by patient ID and timestamp. Two specialized processors—StaticProcessor and TSProcessor—extend this base to either aggregate sequences into static features or handle temporal sequences with padding and time alignment. The toolkit then splits, cleans (imputation and outlier handling), and scales the data. A set of classifier classes (e.g., Static_Static_Classifier, Temporal_Temporal_Classifier) provide a scikit-learn-like API and internally manage a registry of built-in models (XGBoost, LSTM, Transformer, Cox). Custom models can be added by registering them with the appropriate classifier’s MODELS dictionary. The entire pipeline is demonstrated via short scripts for a static classification task (COVID-19 mortality) and a temporal classification task (sepsis early detection), requiring only a handful of user-specified parameters.

## Key Results
- COVID-19 mortality prediction: 96% accuracy using XGBoost (Static_Static_Classifier).
- Sepsis early diagnosis: 97% overall accuracy using Transformer (Temporal_Temporal_Classifier).
- Sepsis class recall (sensitivity): 0.24, indicating difficulty in identifying positive cases.

## Why This Works (Mechanism)
The toolkit’s effectiveness stems from three interconnected mechanisms:

### Unified data interface
- **Claim:** Automatically parsing and aligning heterogeneous clinical tabular formats reduces data cleaning overhead.
- **Mechanism:** The Processor module accepts wide, long, or flattened inputs, converts them into a standardized wide representation keyed by patient ID and timestamp, and performs string/time parsing and column removal before outputting a clean DataFrame.
- **Core assumption:** Raw clinical data predominantly matches one of the three supported schemas; automatic conversion suffices for downstream tasks.
- **Evidence anchors:** Abstract states the unified interface significantly reduces overhead; Section 3.1 formalizes the three formats and automatic standardization; Section 4 listings demonstrate usage.
- **Break condition:** Non-standard schemas (e.g., nested JSON, proprietary binary) not covered by the parsers cause failure, requiring manual pre-processing.

### End-to-end pipeline encapsulation
- **Claim:** Integrating disjoint steps into a linear workflow with few lines of code lowers the barrier to entry for clinicians.
- **Mechanism:** Pre-built classes chain operations (read_file → extract_features → train_test_split → data_cleaning → scale_features → fit → evaluate), masking engineering complexity.
- **Core assumption:** Clinicians with limited programming can successfully run a full ML experiment without needing to understand intermediate structures or hyperparameters.
- **Evidence anchors:** Abstract mentions complete pipeline simplified into few lines; Section 3.2 describes branching static/temporal pipelines; Listings 2 and 3 show end-to-end scripts in ~15 lines.
- **Break condition:** Tasks requiring custom feature engineering, non-standard cross-validation, or intermediate data inspection break the linear flow and need external code.

### Modular classifier design with extensibility
- **Claim:** A fixed fit/predict/evaluate interface across four I/O paradigms (static/static, static/temporal, temporal/static, temporal/temporal) provides algorithm flexibility while maintaining consistency.
- **Mechanism:** Four classifier subclasses map input/output dimensionality to appropriate built-in models (XGBoost, LSTM/T-LSTM, Cox, Transformer); custom models are added by registering a class with the appropriate subclass’s MODELS dictionary.
- **Core assumption:** The four paradigms cover most clinical prediction tasks, and custom algorithms can be adapted to one of them.
- **Evidence anchors:** Section 3.3 lists the four paradigms and associated models; Section 3.4 shows a custom Random Forest integration; Listing 3 uses Temporal_Temporal_Classifier with Transformer.
- **Break condition:** Tasks that do not fit any of the four I/O patterns (e.g., multi-output with mixed static/temporal heads) require core modifications.

## Foundational Learning
- **Medical Time Series Heterogeneity**  
  *Why needed:* Real-world clinical data come in various tabular forms (sparse vitals, discrete events, pre-pivoted). Understanding these formats is essential for correctly specifying `data_type` and metadata columns.  
  *Quick check:* A CSV where each row is a patient and columns are `[patient_id, glucose_0h, glucose_6h, glucose_12h, ...]` is in wide format. A key limitation is inability to represent irregularly sampled measurements without sparsity.

- **Static vs. Temporal Modeling Paradigms**  
  *Why needed:* The toolkit bifurcates processing and models based on whether the output is a single prediction (static) or a sequence (temporal). Choosing the right processor and classifier class is critical.  
  *Quick check:* For predicting in-hospital mortality from 24-hour ICU vitals, use `StaticProcessor` and `Static_Static_Classifier` (or `Static_Temporal_Classifier` if features are temporal but outcome static). The processor aggregates the sequence into summary statistics (e.g., mean, std, duration).

- **Scikit-learn Compatible API**  
  *Why needed:* The toolkit follows the familiar `fit`/`predict`/`transform` pattern, so users must understand proper sequencing (e.g., train/test split before scaling) to avoid data leakage.  
  *Quick check:* In Listing 2, `data_cleaning` and `scale_features` are called separately on the training and test sets after splitting to ensure scaler parameters are learned only from training data. Scaling before splitting would leak information and overestimate performance.

## Architecture Onboarding
- **Component map:** Raw Data → Processor → (StaticProcessor or TSProcessor) → (Static_Classifier or Temporal_Classifier) → Evaluation
- **Critical path:** Specify format & metadata → instantiate Processor (`read_file`/`read_directory`) → (if static) `extract_features` → `train_test_split` → `data_cleaning` → `scale_features` → instantiate Classifier → `fit(X_train, y_train)` → `evaluate(X_test, y_test)` → (optional) `visualize()`.
- **Design tradeoffs:** The pipeline prioritizes ease of use over granular control; power users must access internal attributes or subclass. It includes mature models (XGB, LSTM, Transformer, Cox) but omits cutting-edge architectures. Imputation and outlier methods are basic; complex clinical patterns require external preprocessing.
- **Failure signatures:** 
  - *Data format error:* `ValueError` during `read_file` if required columns missing. Verify raw schema matches one of the three canonical formats.
  - *Shape mismatch:* `RuntimeError` in `fit` if input dimensions don’t match model expectations. For temporal models, ensure 3D tensor `(n_samples, timesteps, n_features)`; for static, ensure 2D.
  - *Poor minority-class performance:* As seen in sepsis (recall=0.24). Not a toolkit bug; requires external imbalance handling (e.g., class weights, oversampling).
  - *Memory explosion:* Long sequences or large batches in `TSProcessor` may OOM. Reduce `max_len` or batch size (may require model wrapper changes).
- **First 3 experiments:**
  1. **Static proof-of-concept:** Use `StaticProcessor` on a small wide-format dataset (e.g., the COVID19-375 example) with `extract_features(agg_funcs=['mean'])`. Verify `X_train` shape and train `Static_Static_Classifier` with `'XGB'`. Confirm it runs and produces a classification report.
  2. **Temporal proof-of-concept:** Use `TSProcessor` on a small directory of wide-format files (e.g., PhysioNet sepsis subset). Set `max_len=10`. Train `Temporal_Temporal_Classifier` with `'Transformer'`. Validate sequence padding, 3D tensor creation, and training loop.
  3. **Custom model integration:** Follow Listing 1 to register a scikit-learn model (e.g., `RandomForestClassifier`) with `Static_Static_Classifier`. Train and evaluate to ensure the wrapper correctly invokes `fit`/`predict`.

## Open Questions the Paper Calls Out
- **Advanced architectures:** How can mtslearn incorporate state-of-the-art deep learning models (e.g., hierarchical transformers, neural differential equations) to improve performance on complex clinical time-series tasks?
- **Explainable AI:** What interpretability methods (e.g., SHAP for sequences, attention visualization) can be integrated to provide transparent clinical reasoning and increase physician trust?
- **Sepsis recall:** Why does the temporal Transformer achieve low recall (0.24) for sepsis, and how can preprocessing or modeling be optimized to improve sensitivity?
- **Robustness to heterogeneity:** How well does the data standardization interface handle extreme irregularities like non-uniform sampling rates, nested missingness, or non-tabular formats?

## Limitations
- The COVID19-375 dataset used for the static task is not publicly available, hindering exact replication.
- Default hyperparameters and training details for the Transformer model are unspecified, making independent verification difficult.
- The toolkit does not automatically address class imbalance, leading to poor recall for minority classes (e.g., sepsis).
- Data parsing is limited to three tabular schemas; more complex or proprietary formats may require manual conversion.
