# SuperLocalMemory: Privacy-Preserving Multi-Agent Memory with Bayesian Trust Defense Against Memory Poisoning

## Quick Facts
- **arXiv ID:** 2603.02240  
- **Source URL:** https://arxiv.org/abs/2603.02240  
- **Reference count:** 31  
- **Primary result:** Replaces cloud-based memory with a local-first architecture using Bayesian trust scoring and adaptive re-ranking to eliminate OWASP ASI06 memory poisoning, achieving sub-11ms search latency and zero concurrency errors while improving relevance by 104%.

## Executive Summary
SuperLocalMemory is a local-first memory system for cloud-based multi-agent AI that mitigates memory poisoning attacks by eliminating centralized storage and network transmission. It stores all data in a user's SQLite database and uses Bayesian trust scoring to dynamically degrade trust in malicious or compromised agents. An adaptive learning-to-rank layer, trained without LLM inference, re-ranks retrieval results using nine behavior-derived features, significantly improving relevance. The design enforces GDPR-compliant data isolation and integrates with over 17 tools via the Model Context Protocol.

## Method Summary
The system implements a three-layer architecture. Layer 1 is a SQLite-backed storage engine with FTS5 search, WAL journaling, and a thread-safe write queue to ensure ACID compliance and zero concurrency errors under load. Layer 2 coordinates multi-agent operations: a per-agent Bayesian trust scorer (Beta-Binomial posterior) updates trust based on behavioral signals (writes, recalls, errors) with asymmetric magnitudes and decay. Writes from agents below a trust threshold (t < 0.3) are blocked. Layer 3 adds an adaptive re-ranker: a three-phase progression (baseline → rule-based → LightGBM with LambdaRank) uses implicit feedback from tool usage and CLI commands to learn user preferences across nine dimensions (e.g., technology match, workflow fit). The knowledge graph (TF-IDF edges, Leiden clustering) is optional for context-aware retrieval. All behavioral training data is isolated in a separate `learning.db` to support erasure.

## Key Results
- 10.6ms median search latency with zero concurrency errors under 10 simultaneous agents.
- Trust separation gap of 0.90 between benign and malicious agents; sleeper attacks degrade trust by 72%.
- 104% improvement in NDCG@5 (from 0.441 to 0.900) from adaptive re-ranking.
- Supports GDPR Article 17 erasure via one-command learning reset.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Eliminating cloud dependency removes the centralized attack surface for memory poisoning.
- **Mechanism:** A local-first architecture ensures all memory storage, retrieval, and trust scoring occur on the user's machine. Memories never traverse networks, and only locally initiated tool invocations can write data. Provenance tracking (`created_by`, `source_protocol`) is stored locally and cannot be obscured by a cloud provider.
- **Core assumption:** Network transmission and multi-tenant cloud storage are necessary conditions for the documented cross-session and cross-user propagation of poisoned memories.
- **Evidence anchors:** [abstract] "local-first memory system... eliminates cloud dependency... architectural isolation"; [section 2.2] Details how cloud-default designs create "multi-tenant exposure," "network exposure," "opaque provenance," and "vendor lock-in"; [corpus] Neighbor papers (e.g., DynaTrust, AgentSafe) focus on trust graphs and hierarchical data management *within* networked multi-agent systems, implying the local-first boundary is a novel, non-trivial defense shift.
- **Break condition:** If a compromised local agent can write to the memory store without triggering the trust scoring enforcement (Section 4), the local isolation is circumvented. The system degrades to a trust-only defense.

### Mechanism 2
- **Claim:** Bayesian trust scoring with Beta-Binomial posterior inference reliably degrades trust for sleeper agents while allowing benign agents to converge to high trust.
- **Mechanism:** Each agent starts with a prior (e.g., Beta(2,1)). Positive and negative behavioral signals (writes, recalls, errors) update the posterior (`α`, `β`). The decay factor `1/(1+nη)` gives early signals more weight but ensures accumulated history resists rapid change. A malicious agent's early benign behavior builds a high `α`, but subsequent negative signals increment `β`, causing a significant posterior mean drop.
- **Core assumption:** The behavioral signal magnitudes (asymmetric: negative > positive) and the decay schedule accurately model the difference between consistent benign operation and the gradual onset of malicious activity.
- **Evidence anchors:** [abstract] "Bayesian trust scoring... trust separation (gap =0.90) with 72% trust degradation for sleeper attacks"; [section 4.1] Formal equation `t_{i+1} = t_i + δ·1/(1+n·η)` and signal magnitude table; [section 5.6] Table 4 shows quantitative results: benign trust 0.945 vs. malicious 0.048 (single poisoner), and sleeper degradation from 0.902 to 0.249; [corpus] "DynaTrust: Defending Multi-Agent Systems Against Sleeper Agents via Dynamic Trust Graphs" and "Adaptive Trust Consensus..." study sleeper/Byzantine attacks but use game theory/RL, not Bayesian inference—suggesting the Bayesian approach for this specific application is under-explored.
- **Break condition:** If an attacker can generate sufficiently many high-magnitude *positive* signals (e.g., by correctly recalling large volumes of data) to offset negative signals, trust may not degrade. The model assumes signal veracity can be approximated by consistency metrics.

### Mechanism 3
- **Claim:** A zero-LLM adaptive learning-to-rank layer, using three-layer behavioral analysis, dramatically improves within-topic result relevance (NDCG@5 +104%) without introducing inference cost or cloud dependency.
- **Mechanism:** The system collects implicit feedback (tool `memory_used`, CLI `useful`, passive decay). After a threshold (200+ signals), it trains a Gradient Boosted Decision Tree (LightGBM) re-ranker with LambdaRank. Features include the base search score (BM25/TF-IDF) plus nine enrichment dimensions: technology match, project context, workflow pattern fit, source quality, importance, recency, and access frequency.
- **Core assumption:** User preference for memory relevance can be effectively modeled by these nine deterministic, locally computable features derived from interaction patterns, without semantic understanding from an LLM.
- **Evidence anchors:** [abstract] "adaptive learning-to-rank framework... 104% improvement in NDCG@5 from adaptive re-ranking"; [section 3.3] Details the three behavioral layers (cross-project tech prefs, project context, workflow patterns), the three-phase progression (baseline → rule-based → ML), and synthetic bootstrapping for cold-start; [section 5.5] Table 3 shows ablation: base system NDCG@5=0.441, full system + adaptive ranker = 0.900. Notes evaluation circularity with importance scores; [corpus] Neighbors focus on trust or graph-based memory (GraphRAG, A-MEM), not privacy-preserving local re-ranking. "Personalized re-ranking for local document collections using implicit feedback" (Santos & Wei 2025) is cited but not evaluated in a memory system context.
- **Break condition:** If the synthetic bootstrap data distribution drifts significantly from real user preferences (Section 7), or if a user's behavior patterns are too sparse (<200 signals) or inconsistent, the ML phase may not activate or could produce poor rankings. The rule-based phase (20-199 signals) provides a fallback.

## Foundational Learning

- **Concept: SQLite Write-Ahead Logging (WAL) & Serialized Write Queues**
  - **Why needed here:** The system must support concurrent reads from multiple agents while guaranteeing serialized, ACID-compliant writes to prevent corruption. This is the core of the "zero concurrency errors" claim.
  - **Quick check question:** How does WAL mode allow readers to proceed while a writer holds a lock, and why is a separate application-level write queue still necessary on top of it?

- **Concept: Beta-Binomial Bayesian Updating for Trust**
  - **Why needed here:** To implement the trust scoring model where prior belief (`α`, `β`) is updated with binary success/failure signal counts (`k`, `N`). The posterior mean `α/(α+β)` is the trust score.
  - **Quick check question:** If an agent starts with Beta(2,1) (prior trust 0.667) and receives 10 "positive" signals and 2 "negative" signals, what is the updated trust? (Assume δ magnitudes are baked into effective count updates).

- **Concept: Learning-to-Rank with Gradient Boosted Trees & LambdaRank**
  - **Why needed here:** To transform the base search results (BM25/TF-IDF) into a personalized ranking based on the 9-dimensional feature vector. LambdaRank optimizes NDCG directly.
  - **Quick check question:** What is the difference between optimizing for MRR (Mean Reciprocal Rank) and NDCG@5, and why did the base system have high MRR but low NDCG@5?

## Architecture Onboarding

- **Component map:**
  Storage Layer (memory.db, DbConnectionManager) -> Enrichment Layers (Hierarchical Index, Knowledge Graph) -> Coordination & Trust (Event Bus, Agent Registry, Provenance Tracker, Trust Scorer) -> Adaptive Layer (learning.db, Feedback Collectors, Feature Engine, Re-ranker) -> Protocol Interface (MCP server)

- **Critical path (new memory write):**
  1. Agent calls `memory_add` tool via MCP/CLI.
  2. `DbConnectionManager` gets write connection from pool; request enters serialized queue.
  3. Write operation: content, tags, importance, **provenance** (`created_by`, `source_protocol`, `trust_score_at_write`).
  4. **Trust update:** Agent's counter `n` increments. Signal magnitude `δ` (based on write type/content) is applied with decay factor.
  5. **Event broadcast:** `memory.created` event emitted (if Agent Registry active).
  6. **Async graph update:** (Later) TF-IDF terms extracted, cosine similarity edges computed (if <10k memories), Leiden clusters refreshed.

- **Design tradeoffs:**
  - **Graph scaling (O(n²)) vs. utility:** Brute-force edge computation is capped at 5,000-10,000 memories. HNSW index (O(n log n)) is optional to raise the cap. The tradeoff is computational cost for structural insight.
  - **Trust enforcement strictness:** Default threshold `t < 0.3` blocks writes. This prevents poisoning but may block a genuinely new or error-prone agent. The decay factor is tuned to resist rapid trust loss from transient issues.
  - **Adaptive ranking latency vs. personalization:** ML re-ranking adds ~20ms. The three-phase progression (Phase 0/1/2) prevents premature personalization on sparse data.
  - **GDPR isolation:** `memory.db` (memories) vs. `learning.db` (patterns). One-command `slm learning reset` destroys personalization data but preserves memories. This tradeoff privileges user control over model continuity.

- **Failure signatures:**
  - **Write queue backlog:** Monitor `write_queue_size`. Sustained growth indicates write throughput >~25 ops/sec (from Table 2) or long-running transactions blocking the queue.
  - **Trust score stagnation:** An agent's trust remains near initial value (`t₀=1.0` or prior) for many operations, suggesting signal magnitudes or decay factor may be misconfigured, or the agent is not producing detectable signals.
  - **Re-ranking degradation:** NDCG@5 drops after Phase 2 activation. Check for synthetic bootstrap drift (warning in Section 7) or feature vector corruption. Fallback to Phase 1 rule-based ranking is automatic.
  - **Graph build failure:** At >10,000 memories, brute-force build times out (277s at 5,000). HNSW index must be enabled and functional.

- **First 3 experiments:**
  1. **Baseline Storage & Search:** Write 100 synthetic memories. Run 10 diverse queries. Measure median search latency (expect ~10-11ms). Verify WAL mode (`PRAGMA journal_mode=WAL`) and zero "database is locked" errors under 2 concurrent writer simulation scripts.
  2. **Trust Scoring Simulation:** Create 2 agent identities. Agent A generates 100 benign writes. Agent B generates 50 benign writes then 50 "contradictory" writes (detected by content hash collision with prior). Observe trust divergence. **Expected:** Agent A trust ~0.945, Agent B trust ~0.25-0.35.
  3. **Adaptive Re-ranking Bootstrap:** Seed `learning.db` with 300 synthetic feedback signals (simulating `memory_used` events with biased relevance). Activate rule-based phase (20+ signals). Run 20 test queries. Compare NDCG@5 of base FTS5 results vs. re-ranked results. **Expected:** ~40-60% improvement from rule-based multipliers.

## Open Questions the Paper Calls Out

- **Open Question 1:** What is the minimum real-world usage duration (in days/weeks) and signal diversity required for the adaptive re-ranker to achieve stable, meaningful personalization without relying on synthetic bootstrapping?
  - *Basis:* Paper states rule-based requires 20+ signals and ML needs 200+ signals across 50+ unique queries. Synthetic bootstrap mitigates cold-start but cannot substitute for genuine signals.
  - *Why unresolved:* Thresholds derived from controlled experiments and a single-user pilot. Real-world workflows have irregular patterns and sparse interactions.
  - *What evidence would resolve it:* Longitudinal field study (n>30) over 3–6 months, measuring NDCG@5 against human judgments as organic feedback accumulates.

- **Open Question 2:** Does repeated synthetic bootstrapping for training the gradient-boosted re-ranker cause measurable distribution drift over long-term deployment (e.g., >1 year), and do the proposed mitigation strategies (regularization, phase-gated transition) fully prevent performance degradation?
  - *Basis:* Paper cites model collapse literature and mitigates with "aggressive regularization and phase-gated transition" but provides no long-term evaluation of synthetic-to-real transition.
  - *Why unresolved:* Evaluation only covers initial phases (≤200 signals). Long-term drift from synthetic data mirroring historical but not evolving behavior is theoretically acknowledged but unmeasured.
  - *What evidence would resolve it:* Controlled A/B test for 12+ months: one system using only synthetic bootstrap indefinitely vs. one transitioning to real data, comparing re-ranking quality and feature importance drift.

- **Open Question 3:** For knowledge graph construction at scale (>10,000 memories), how does HNSW-accelerated edge computation affect the quality and stability of Leiden community detection compared to brute-force pairwise cosine similarity, particularly for hierarchical subclustering depth and modularity scores?
  - *Basis:* Brute-force O(n²) limits builds to 5,000 memories; optional HNSW raises to 10,000. Leiden results (6–7 top-level communities) reported only for brute-force up to 5,000.
  - *Why unresolved:* HNSW trades recall for speed. Unknown if approximation errors degrade graph topology, fragment communities, or alter hierarchical structure.
  - *What evidence would resolve it:* Ablation on fixed 10,000+ memory dataset: compare graph metrics (modularity, conductance, hierarchical depth) and downstream retrieval (MRR, NDCG) between brute-force and HNSW (varying recall).

- **Open Question 4:** Does incorporating agent trust scores (from Bayesian trust framework) as a feature in the adaptive re-ranking layer improve retrieval relevance in adversarial multi-agent environments, or does it risk under-ranking benign but low-trust agents' memories?
  - *Basis:* Trust enforcement blocks writes for t < 0.3, but "trust scores do not yet influence the re-ranker’s feature vector." Listed as future for "soft degradation."
  - *Why unresolved:* Design tension: high-trust agents may provide higher-quality memories, but low-trust agents might store unique, relevant info. Impact on ranking quality and robustness against poisoning unknown.
  - *What evidence would resolve it:* Experiment injecting malicious memories from agents with varying trust histories, measuring NDCG@k and poisoning success rate with and without trust as a feature.

- **Open Question 5:** How does SuperLocalMemory's retrieval performance generalize to diverse developer workflows beyond the single-user pilot, and what benchmark metrics best capture its value for cross-project, long-term memory tasks?
  - *Basis:* "No formal user study has been conducted." "Developer-workflow-specific benchmarks are needed; MemoryBench found no advanced system consistently outperforms RAG baselines." LoCoMo is for conversational memory and not comparable.
  - *Why unresolved:* Human pilot (n=1, 182 memories) lacks power and diversity. Synthetic benchmark (5 topic categories) may not reflect real developer needs (architectural decisions, API choices, debugging). No standardized benchmark exists.
  - *What evidence would resolve it:* Create Developer Workflow Memory Benchmark (DWM-Bench) with queries/ground truths from professional engineers across projects, followed by multi-participant study measuring time-to-solution, satisfaction, and NDCG vs. baselines (filesystem search, vector-only memory).

## Limitations
- Trust scoring signal definitions (e.g., "anomalous burst," "contradictory writes") are unspecified, hindering replication of sleeper attack results.
- Adaptive re-ranking feature engineering (e.g., "workflow fit" formulas) and synthetic bootstrap details are opaque, affecting verification of NDCG gains.
- Evaluation data (query sets, human judgments, synthetic templates) are not released, preventing independent benchmarking.
- Knowledge graph scaling beyond 5,000 memories relies on optional HNSW whose impact on community detection quality is unevaluated.

## Confidence
- **Local-first architectural defense:** High – design clearly removes network/cloud attack surfaces; validation requires testing if a compromised *local* agent can bypass trust enforcement.
- **Bayesian trust separation:** Medium – mathematical model is specified, but confidence depends on unverified signal magnitude parameters and decay tuning.
- **Adaptive re-ranking utility:** Medium-Low – reported gains are large but rely on opaque feature engineering and potential circularity in importance-score usage.
