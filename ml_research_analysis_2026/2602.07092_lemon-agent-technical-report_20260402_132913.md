# Lemon Agent Technical Report
## Quick Facts
- arXiv ID: 2602.07092
- Source URL: https://arxiv.org/abs/2602.07092
- Reference count: 7
- Primary result: Lemon Agent achieves state-of-the-art 91.36% overall accuracy on GAIA and tops xbench-DeepSearch leaderboard with 77+.

## Executive Summary
Lemon Agent is a multi-agent orchestrator-worker system built on the AgentCortex framework that addresses key inefficiencies in LLM-powered agent systems: static resource allocation, limited memory evolution from partial successes, and multimodal perceptual constraints. It introduces a hierarchical self-adaptive scheduling mechanism, a three-tier progressive context management strategy, and a Self-Evolving Semantic Memory (SES-Memory) module. On authoritative benchmarks, it achieves 91.36% overall accuracy on GAIA and secures the top position on xbench-DeepSearch with a score of 77+. Its industrial deployment in Lenovo’s Super Intelligent Agent handles hundreds of millions of transactions.

## Method Summary
The Lemon Agent system is implemented on the open-source AgentCortex framework (code at https://github.com/Open-LemonAgent/LemonAgent). It uses a GPT-5 class LLM backbone with high reasoning level for the main agent (10 rounds) and sub-workers (20 rounds), medium for summarization, temperature 1.0, and max output 128k tokens. The toolset includes intelligent image, street view agent, and multi-source search. Evaluation follows a pass@3 strategy with 3 concurrent processes on GAIA and xbench-DeepSearch benchmarks.

Reproduction requires installing dependencies, configuring API access for GPT-5 and external tools (Google Search, Google Maps, etc.), and downloading the benchmark datasets. However, the open-source repository may lack some core AgentCortex modules and exact hyperparameter values (τ thresholds, SES-Memory similarity/top-k), which could hinder faithful replication.

## Why This Works (Mechanism)
### Mechanism 1: Hierarchical Self-Adaptive Scheduling
- **Claim**: Dynamically modulating computational intensity (worker count, tool parallelism) based on task complexity optimizes resource utilization while maintaining reasoning coherence.
- **Mechanism**: 
  - *Macro-level*: Orchestrator assesses task structure (orthogonal sub-goals vs. linear sequence) to spawn 1..N specialized sub-workers for parallel subtask execution.
  - *Micro-level*: Each sub-worker independently scales tool parallelization (1..5 concurrent calls) based on sub-task needs (e.g., high parallelism for data retrieval, sequential for logical chains).
  - Two-tier adaptivity balances global coordination overhead against local execution speed.
- **Core assumption**: Task complexity/structural independence can be reliably judged by an LLM orchestrator; parallel tool execution within a sub-worker does not break causal dependencies for reasoning-heavy steps.
- **Evidence anchors**:
  - [abstract] "hierarchical self-adaptive scheduling mechanism that operates at both the overall orchestrator layer and workers layer."
  - [section 2.2] Explicit description of macro (Task Routing & Dynamic Subagents) and micro (Dynamic Parallel Tool Calling) levels.
  - [corpus] Weak direct evidence; neighboring papers (e.g., "Agentic Lybic: Multi-Agent Execution System with Tiered Reasoning") discuss orchestration but not the specific dual-layer adaptivity.
- **Break condition**: If sub-tasks have hidden sequential dependencies not detectable by the orchestrator, parallel execution introduces contradictory intermediate states that cannot be resolved by later verification.

### Mechanism 2: Three-Tier Progressive Context Management
- **Claim**: A hierarchical compression strategy (intra-tool truncation → intra-round summarization → cross-round retroactive compression) maintains information density and prevents context window overflow during long-horizon trajectories with large data retrievals.
- **Mechanism**:
  1. *Intra-tool truncation*: Raw tool output >τ_max gets truncated immediately; metadata (origin, truncation point) is preserved.
  2. *Intra-round adaptive summarization*: When cumulative round content exceeds τ_multi, the system synthesizes a summary, prioritizing precise reconstruction of previously truncated segments.
  3. *Cross-round retroactive compression*: When historical context capacity is reached, the system backtracks to truncation points in older rounds and replaces raw results with compressed summaries, resetting the truncation registry.
- **Core assumption**: Lossy compression (truncation → summarization) applied hierarchically can preserve the logical anchors and evidence needed for multi-step reasoning without cumulative degradation.
- **Evidence anchors**:
  - [abstract] "three-tier progressive context management strategy."
  - [section 2.3] Full specification of the three layers and their triggers (τ_max, τ_multi, τ_context).
  - [corpus] Neighboring papers focus on context reduction but not this specific retroactive, metadata-guided protocol; evidence is primarily internal.
- **Break condition**: If critical evidential details are always in the truncated minority of outputs, and summarization consistently fails to reconstruct them accurately, reasoning on evidence-dependent tasks degrades.

### Mechanism 3: Self-Evolving Semantic Memory (SES-Memory)
- **Claim**: Extracting reusable "skill snippets" (process patterns, code fragments, decision rules) from *all* execution traces (successes and failures) enables continuous capability refinement beyond binary success-based learning.
- **Mechanism**:
  - Post-execution, the system analyzes the *trajectory* (not just final answer) to isolate high-value intermediate steps (e.g., "use spectral flux for audio clip extraction").
  - These snippets are stored as structured natural language descriptions, decoupled from full codebases.
  - Retrieval uses similarity search with a threshold filter; redundant memory generation is suppressed if multiple high-similarity memories exist.
  - New tasks recombine snippets from diverse past attempts.
- **Core assumption**: Valuable procedural knowledge exists in partial successes and specific failures; this knowledge can be abstracted into transferable, context-light snippets that an LLM can effectively reuse.
- **Evidence anchors**:
  - [abstract] "extract multi-dimensional valid information from all historical experiences to assist in completing similar tasks."
  - [section 2.4] Detailed description of process-centric extraction, snippet format, and quality control (similarity filter, redundancy check).
  - [section 3.3] Concrete case study showing combination of snippets from two failed attempts to succeed on a third audio ID task.
  - [corpus] Neighboring work (e.g., "Jenius Agent: Towards Experience-Driven Accuracy Optimization") explores experience-driven optimization but SES-Memory's explicit focus on *all* trajectories and snippet-based storage is distinctive.
- **Break condition**: If extracted snippets are too context-specific or low-level, they fail to generalize; if too abstract, they lose actionable precision. The similarity filter may also suppress novel but valid approaches.

## Foundational Learning
- **Concept: Planner-Executor-Memory Paradigm**
  - *Why needed here*: Lemon Agent's AgentCortex framework formalizes this classic AI paradigm. Understanding it is key to seeing how the system decomposes a user goal (Plan), iterates with tools (Execute), and learns (Memory).
  - *Quick check question*: How does the "Planner" role in Lemon Agent differ from a traditional single-step planner, given the hierarchical scheduling?
- **Concept: ReAct-style Reasoning (Reasoning + Acting)**
  - *Why needed here*: The sub-workers' loop ("Independent ReAct" in Algorithm 1) is the micro-execution engine. This paradigm underpins how the agent interleaves thought, tool use, and observation.
  - *Quick check question*: In the context of parallel tool calls, how does the agent maintain a coherent "Reasoning" trace when multiple tool results arrive asynchronously?
- **Concept: Context Window Management & Compression**
  - *Why needed here*: The three-tier strategy is a sophisticated solution to the fundamental LLM constraint of fixed context length. One must understand truncation vs. summarization trade-offs.
  - *Quick check question*: Why is the cross-round "retroactive compression" step necessary if intra-round summarization already condenses each round's output?

## Architecture Onboarding
- **Component map**:
  1. **AgentCortex Framework**: Provides modular infrastructure (intent, planning, tool execution, logging).
  2. **Orchestrator (Main Agent)**: Performs macro-routing, aggregates sub-agent outputs, triggers memory write.
  3. **Sub-Worker Pool**: Stateless executors; each runs its own ReAct loop with dynamic tool parallelism.
  4. **SES-Memory**: Separate module for snippet extraction/storage/retrieval. Not used in the real-time context.
  5. **Tool Suite**: MCP-compliant tools; includes Intelligent Image Tool, Street View Agent, Multi-Source Search.
  6. **Context Manager**: Enforces three-tier compression; hooks into tool responses and the main/sub-agent contexts.
- **Critical path** (typical successful flow):
  `User Task → Intent Recognition → SES-Memory Recall (pre-load hints) → Macro-routing (spawn workers) → Sub-worker ReAct loops (with micro-tool scheduling) → Intra-round compression → Sub-agent summary → Orchestrator aggregation → Final answer → SES-Memory write (post-execution snippet extraction)`
- **Design tradeoffs**:
  - *Parallelism vs. Dependency Risk*: More workers/tools parallelized = faster but higher risk of incoherent intermediate states.
  - *Compression vs. Evidence Fidelity*: Stronger truncation/summarization saves tokens but may lose subtle details critical for verification.
  - *Memory Growth vs. Novelty*: Strict redundancy suppression prevents bloat but may discard variations of a useful skill.
- **Failure signatures**:
  - *Context Overflow*: System halts with "context length exceeded" despite compression—likely un-truncated large outputs or summarization failure.
  - *Contradictory Sub-agent Outputs*: Orchestrator cannot reconcile parallel sub-worker results—sign of poor macro-routing or hidden dependencies.
  - *SES-Memory Pollution*: Retrieved snippets are irrelevant or misleading—similarity threshold too low, or extraction from failed traces is too noisy.
- **First 3 experiments** (for a new engineer to validate understanding):
  1. **Scheduling calibration**: Run a simple linear task (e.g., "What's the weather in Paris?") and a clearly decomposable task (e.g., "Compare the GDP and population of France and Japan"). Observe worker counts and tool parallelism. Does the system use 1 worker for the simple task? Does it spawn multiple for the complex one?
  2. **Compression stress test**: Execute a task that intentionally retrieves large documents (e.g., "Summarize this 100-page PDF"). Use logging to inspect the context at each tier: check truncation markers, examine intra-round summaries for loss of key data points, and verify cross-round retroactive updates.
  3. **SES-Memory snippet validation**: After two distinct successful runs of a task type (e.g., "Identify a song from an audio clip" using different methods), manually inspect the stored SES-Memory snippets. Are they abstract enough to be reusable (e.g., "extract audio clip via spectral flux") but specific enough to be actionable? Then run a third variant and check if retrieved snippets influence the chosen method.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: How can sandboxed execution environments be integrated to minimize data transfer overhead while preserving agent functionality in multi-agent systems?
- **Basis in paper**: [explicit] The LIMITATION AND FUTURE WORK section states the investigation of sandboxed execution environments to eliminate repetitive uploads/downloads and reduce context length.
- **Why unresolved**: The current system uses external tool calls with data transfers, and sandbox integration is a proposed future direction not implemented in this work.
- **What evidence would resolve it**: A prototype implementation with sandboxed tool operations, compared against the baseline in terms of communication latency, context window usage, and task accuracy on benchmarks like GAIA.

### Open Question 2
- **Question**: What multi-agent collaboration topologies are optimal for tasks with highly fragmented and orthogonal sub-goals?
- **Basis in paper**: [explicit] The future work mentions exploring more sophisticated multi-agent collaboration topologies to handle fragmented and orthogonal sub-goals.
- **Why unresolved**: The existing hierarchical orchestrator-worker architecture may not scale efficiently for tasks with many independent sub-tasks, and new topologies are needed.
- **What evidence would resolve it**: Design and empirical evaluation of alternative topologies (e.g., dynamic agent formation, decentralized coordination) on synthetic or benchmark tasks designed to have orthogonal sub-goals, measuring coordination overhead and success rates.

### Open Question 3
- **Question**: How can the precision of self-evolving semantic memory (SES-Memory) be improved to enhance skill extraction and reduce noise?
- **Basis in paper**: [explicit] The future work aims to enhance the precision of the SES Memory module for better efficiency and scalability.
- **Why unresolved**: SES-Memory uses a similarity-based threshold filter, but the optimal parameters and advanced techniques for precision are not explored, potentially leading to noisy memory entries.
- **What evidence would resolve it**: Development of enhanced memory updating algorithms (e.g., contextual filtering, reinforcement learning from feedback), tested via ablation studies showing improved retrieval accuracy and downstream task performance.
