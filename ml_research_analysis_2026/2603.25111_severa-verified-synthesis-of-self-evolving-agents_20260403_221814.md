# SEVerA: Verified Synthesis of Self-Evolving Agents

## Quick Facts
- arXiv ID: 2603.25111
- Source URL: https://arxiv.org/abs/2603.25111
- Reference count: 40
- Primary result: Synthesizes self-evolving agents with formal safety guarantees, achieving zero constraint violations and state-of-the-art performance on Dafny verification, GSM-Symbolic math, and τ²-bench tool-use tasks.

## Executive Summary
SEVerA is a framework that generates LLM-based agents with provable correctness by combining a planner LLM, Formally Guarded Generative Models (FGGMs), and a three-stage Search-Verify-Learn pipeline. FGGMs embed generative model calls with a rejection sampler and a statically verified fallback, ensuring outputs always satisfy local first-order logic contracts. The system searches for candidate programs, verifies them against global specifications for all parameters, and then fine-tunes generative parameters via gradient-based optimization to improve task performance without breaking correctness. Across verification, symbolic math, and policy-compliant tool use, SEVerA attains zero violations and surpasses prior baselines.

## Method Summary
SEVerA synthesizes agents through an iterative loop. A planner LLM writes candidate Dafny programs containing FGGM invocations. Each FGGM specifies a local contract (Φₗ,Ψₗ), a parametric generative function `𝑓𝑝`, a fallback `𝑓𝑑`, and a rejection sampler with a contract checker. The Search phase generates up to Δ candidates. In Verify, the program is checked against global specs (Φ,Ψ) using Dafny; because FGGMs provide parameter‑independent contracts, verification reduces to proving the fallback’s contract satisfaction and correct program structure. Verified programs enter Learn, where GRPO fine‑tunes the generative parameters to maximize a combined objective of task performance and local conformance, while preserving universal correctness. Execution traces feed back to the planner to refine future searches.

## Key Results
- Zero constraint violations across all evaluated tasks while achieving state‑of‑the‑art performance.
- HumanEvalDafny: 97.0% verification success (vs 86.9% baseline).
- GSM‑Symbolic: 66.0% accuracy (vs 44.7% SOTA) and τ²‑bench airline: 52.6% pass rate (outperforms Agent‑C with Claude Sonnet 4.5).

## Why This Works (Mechanism)
### Mechanism 1
SEVerA guarantees that every output of a synthesized agent satisfies formal specifications (Φ,Ψ) for all inputs and all generative model parameters. It does so by wrapping each generative call in an FGGM, which defines a local contract (Φₗ,Ψₗ). At runtime, a rejection sampler accepts outputs that pass a sound contract checker; if all samples fail, a pre‑verified non‑parametric fallback `𝑓𝑑` (proven to satisfy the contract) is executed. The checker’s soundness (and completeness for quantifier‑free contracts) ensures the FGGM always outputs a compliant value. The mechanism fails only if the fallback cannot be verified against the contract or if the checker is incomplete for quantified contracts and rejects valid outputs excessively.

### Mechanism 2
The pipeline decomposes constrained synthesis into discrete search and continuous optimization while preserving correctness. The planner generates candidate parametric programs embedding FGGMs; the verifier checks each candidate against (Φ,Ψ) for all parameter values—feasible because FGGMs provide parameter‑independent contracts. If verification succeeds, the program is fixed. Then GRPO tunes the generative parameters to improve task loss, without re‑verification because correctness holds universally over parameters. This CEGIS‑style loop fails if the planner cannot propose any verifiable candidate within the search budget Δ.

### Mechanism 3
Local FGGM contracts yield a binary reward (1 if GM output passes the checker, 0 otherwise). The learning objective blends the global task loss with a weighted sum of local conformance losses, which estimate the probability of contract violation over inputs. Optimizing this encourages the generative model to assign higher probability to contract‑satisfying outputs, increasing the acceptance rate of the rejection sampler and reducing fallback reliance. However, misalignment between local contracts and the global task, or insufficient model capacity to satisfy contracts, can limit gains.

- **First‑Order Logic & SMT Solving**  
  Specifications and contract checking rely on first‑order logic; verifiers and checkers use SMT solvers to decide formulas, handling quantifiers, decidability, and timeouts.

  SEVerA’s Search‑Verify loop is a CEGIS variant: the planner proposes candidates, the verifier checks universal correctness, and failure feedback refines search.

## Architecture Onboarding
**Component map:**  
Planner LLM (Lₚ) -> FGGM Parser & Validator -> Program Verifier (VC[Φ,Ψ]) -> Learning Module (GRPO) -> Candidate Pool -> Feedback -> Planner LLM (repeat)

**Critical path:**  
Task prompt → Planner Lₚ outputs FGGMs + candidate program → validateFGGM → validateProgram (VC[Φ,Ψ]) → if valid: learn (GRPO) → add to pool → feedback from pool execution → repeat.

**Design tradeoffs:**  
- Rejection sampling vs. constrained decoding: FGGM uses output‑space rejection with fallback, compatible with closed‑source models but may waste samples. Constrained decoding preserves distribution but is limited to open models and syntactic constraints.  
- Parameter independence: FGGMs do not share parameters across call sites, simplifying verification and learning but missing opportunities for parameter tying.  
- Resource‑unawareness: Specifications constrain functional correctness but not computational cost (tokens, LLM calls). Extensions need resource‑bound specs.

**Failure signatures:**  
- FGGM validation error: fallback `𝑓𝑑` fails verification against (Φₗ,Ψₗ), or `𝑓𝑝`/`𝑓𝑑` does not terminate/type‑check.  
- Program verification timeout: proof obligations too complex for Dafny within timeout.  
- High fallback rate: rejection sampler rarely accepts GM outputs, indicating GM not converging to contract.  
- Planner stagnation: planner repeatedly generates similar invalid candidates despite feedback.

**First 3 experiments:**  
1. Validate FGGM mechanics: Implement the `boundedParam` example from §4.2.2. Verify that for any θ, the FGGM output lies in [𝑙,𝑢] across diverse inputs and parameters, confirming Theorem 5.2 empirically.  
2. Test verification on a minimal agent: Create a simple Dafny agent that calls a single FGGM wrapping a constant function. Prove it satisfies a trivial global spec (e.g., output ≥ 0). Ensure the verifier succeeds and the contract checker works.  
3. Measure constraint violation elimination: On a small GSM‑Symbolic subset (e.g., 10 examples), run SEVerA with and without constraint enforcement (i.e., without FGGM/verification). Confirm zero violations vs. non‑zero in unconstrained version, and measure pass rate difference.

## Open Questions the Paper Calls Out
1. **Resource‑bound specifications:** Can SEVerA extend to include resource constraints (e.g., token limits) without sacrificing its zero‑violation property? Current specifications are functional only; adding resource constraints may make verification harder and reduce the solution space.
2. **Library function assumptions:** How sensitive is SEVerA to the correctness and purity of provided library functions? The framework assumes all non‑parametric library functions are correct, pure, and terminating. A buggy library could invalidate soundness proofs.
3. **Scalability of search‑verify loop:** Does the loop scale to agents with many FGGM calls? The paper uses fixed budgets Δ=10 and K=5; more complex programs may require larger budgets, but the trade‑off with verification time is unexplored.
4. **Portability beyond Dafny:** The design is tightly coupled with Dafny. Adapting to other verification languages (e.g., Why3, Viper) may face challenges due to differences in verifier integration, termination checking, and AST manipulation.
5. **Closed vs. open model tuning:** For closed‑source LLMs (e.g., Claude), SEVerA skips parameter tuning and relies on prompt engineering. The relative contribution of prompt tuning vs. parameter tuning to performance gains is unclear; it is unknown whether closed models could benefit further from fine‑tuning if accessible.

## Limitations
- Planner LLM identity and prompt details are unspecified, hindering exact replication.
- Axiom completeness for tasks is not guaranteed; missing axioms can cause verification failures unrelated to agent quality.
- FGGM contract checker is incomplete for quantified contracts, potentially rejecting valid outputs and increasing fallback usage.
- The framework assumes a verifiable non‑parametric fallback exists for every contract; this may not hold for complex or under‑specified tasks.
- The design is currently resource‑unaware and tightly bound to Dafny, limiting applicability.

## Confidence
- **Safety guarantee** (all outputs satisfy formal spec): *High* theoretically (Theorems 5.2, 5.3) but *Medium* practically due to checker incompleteness for quantified contracts and solver timeout sensitivity.
- **Performance results** (zero violations, accuracy gains): *Medium*. Results are strong on three tasks but lack breadth and sensitivity analysis.
- **Three‑stage pipeline** (search‑verify‑learn) effectiveness: *Medium*. Novel integration shows promise but scalability to larger agents and longer horizons remains unproven.

## Next Checks
1. **Axiom completeness audit:** For each task, automatically attempt to prove all library function contracts using multiple SMT solvers (Z3, CVC5). Identify missing axioms and measure their impact on verification success across a held‑out candidate set.
2. **Quantified contract checker evaluation:** Build a controlled test suite of inputs/outputs known to satisfy a quantified contract. Measure checker recall and fallback activation under varying SMT timeouts; compare against quantifier‑free baseline.
3. **Planner robustness test:** Substitute the planner with multiple diverse LLMs (e.g., GPT‑4, Claude 3.5, Llama 3.1‑70B) using identical prompts. Compare verification pass rates and final task performance to assess sensitivity.
