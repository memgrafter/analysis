# Cornserve: A Distributed Serving System for Any-to-Any Multimodal Models

## Quick Facts
- **arXiv ID:** 2603.12118
- **Source URL:** https://arxiv.org/abs/2603.12118
- **Reference count:** 23
- **Primary result:** Serves Any-to-A multimodal models with up to 3.81× higher throughput and up to 5.79× lower tail latency versus monolithic deployment; monolith fails on larger models due to OOM.

## Executive Summary
Cornserve is a distributed serving system designed for Any-to-Any multimodal models that handle dynamic input/output modalities. It abstracts models into composable unit tasks (e.g., encoders, LLMs, generators) which can be disaggregated and scaled independently. The system uses a record-and-replay execution model to automatically dispatch the correct subgraph of unit tasks per request without static graph definitions, and a sidecar-based direct tensor forwarding mechanism (shared memory or RDMA) to bypass the control plane for data movement. Evaluated on Qwen Omni, Cornserve achieves significant throughput and latency improvements over monolithic deployment, while avoiding out-of-memory failures on larger models.

## Method Summary
Cornserve introduces a flexible task abstraction where model components are defined as reusable *unit tasks* that implement a standard interface. *Composite tasks* orchestrate multiple unit tasks to form the full model, with their `invoke` method written in plain Python. The runtime performs a two-phase execution: a record phase collects the exact subgraph of unit tasks invoked for a request by tracing dummy placeholders, and a replay phase executes the real computation following the recorded dependency graph. This approach automatically adapts to dynamic request patterns without manual graph definition. Inter-component communication is handled by sidecar daemons that forward tensors directly via shared memory (intra-node) or RDMA (inter-node), minimizing control-plane overhead. The system is deployed on Kubernetes and integrates with existing inference engines via specialized executors (e.g., vLLM forks). This design enables fine-grained fission and independent scaling of heterogeneous components, overcoming the resource inefficiency and OOM limitations of monolithic serving.

## Key Results
- On Qwen 2.5 Omni, Cornserve achieves up to **3.81× higher throughput** compared to monolithic deployment.
- It achieves up to **5.79× lower tail latency** (P99) on the same model.
- The monolithic approach **fails on larger models** due to GPU out-of-memory errors, while Cornserve scales by disaggregating components.

## Why This Works (Mechanism)
Based on the paper’s analysis:

### Mechanism 1: Flexible Task Abstraction
- **Claim:** Task abstraction enables expressing arbitrary Any-to-Any model computation graphs and facilitates fission and independent scaling.
- **Mechanism:** Model components are defined as *unit tasks* (reusable) and *composite tasks* (orchestrate unit tasks via `invoke`). During deployment, each unit task is mapped to a separate, scalable Task Manager & Executor instance.
- **Core assumption:** Model computation decomposes into discrete, modality-specific components with deterministic control flow per request.
- **Break condition:** Data-dependent branching/looping (e.g., tool calls based on LLM output) may cause the record-phase to capture an invalid subgraph.

### Mechanism 2: Record-and-Replay Execution
- **Claim:** Automatically extracts the precise subgraph of unit tasks for each request without static graph definition.
- **Mechanism:** For each request, the composite task’s `invoke` runs twice. First (*record*): unit tasks return dummy placeholders while logging calls and input placeholder IDs. The system builds a dependency graph by matching placeholder IDs. Second (*replay*): unit tasks return real results, and the dispatcher executes the recorded graph.
- **Core assumption:** The composite task’s `invoke` is *pure* with respect to control flow—identical decisions in both phases.
- **Break condition:** Non-determinism (random.choice, time‑based logic, mutable global state) causes replay divergence.

### Mechanism 3: Sidecar-based Direct Tensor Forwarding
- **Claim:** Bypassing the control plane for inter-component data movement reduces latency and avoids central bottlenecks.
- **Mechanism:** Each GPU runs a Sidecar daemon. When a producer executor finishes a tensor, it writes directly to shared memory (intra-node) or RDMA memory (inter-node) and notifies the consumer’s Sidecar via lightweight gRPC. The consumer’s Sidecar copies the tensor from shared/RDMA memory into its executor’s GPU memory.
- **Core assumption:** Intermediate tensors are large enough that CPU/network involvement would be a bottleneck; direct GPU-to-sharedmem/RDMA transfers are feasible.
- **Break condition:** Very small tensors (< MB) incur overhead; non‑RDMA interconnects degrade cross‑node performance.

Concepts underlying Cornserve’s design:

1. **Distributed Serving vs. Monolithic Deployment**
   - **Why needed:** Disaggregating a single model into distributed components enables independent scaling and avoids resource interference, but introduces communication overhead and scheduling complexity. ## Architecture Onboarding
### Component map
Gateway -> Task Dispatcher -> Task Manager (per unit task) -> Task Executor (replica) and Sidecar (per GPU). Resource Manager orchestrates lifecycle. App (user code) runs in Gateway.

### Critical path
1. Request arrives at Gateway.
2. Record-phase executes composite task’s `invoke` to identify subgraph.
3. Task Dispatcher schedules unit tasks to appropriate Task Managers.
4. Task Executors start and wait for input tensors.
5. Sidecars shuttle tensors as they become available.
6. Final unit task result returned to Gateway.
7. Replay-phase `invoke` aggregates results into response.
8. Response sent to client.

### Design tradeoffs
- **Fission granularity:** Finer fission increases scheduling flexibility but adds Sidecar overhead and potential stragglers from more dependencies.
- **Component sharing:** Sharing executors (e.g., a common vision encoder) reduces GPU footprint but can create contention if the shared component becomes a bottleneck.
- **Placement:** The Planner decides tensor parallelism vs. replication per component. Over‑replicating small components wastes GPUs; under‑replicating bottlenecks throttles the entire graph.

### Failure signatures
- **Monolith OOM:** Immediate failure on larger models → indicates need for fission.
- **High sidecar latency tail:** Straggling producer executor or network congestion.
- **Task dispatcher queue buildup:** Bottleneck at a specific unit task → check replica count.
- **Replay mismatch error:** Non‑determinism in composite task `invoke`.

### First 3 experiments
1. **Baseline replication:** Deploy Qwen 2.5 Omni as a monolith on N GPUs. Measure throughput/latency; expect OOM or poor scaling on larger models.
2. **Fission validation:** Deploy the same model with `encoder_fission=True` in Cornserve. Verify (logs/tracing) that encoder and LLM run on separate GPUs. Compare performance to monolith.
3. **Component sharing test:** Deploy two Cornserve apps that share the same encoder (as in Listing 2). Confirm only one EncoderTask deployment exists. Measure total GPU usage reduction vs. isolated deployments.

## Limitations
- Evaluation limited to Qwen Omni; generalizability to other any‑to‑any architectures unclear.
- Implementation details of specialized executors (Eric, Geri) and their vLLM integration are opaque, hindering full reproducibility.
- Planner configuration, replica scaling policies, and resource allocation specifics are not documented.
