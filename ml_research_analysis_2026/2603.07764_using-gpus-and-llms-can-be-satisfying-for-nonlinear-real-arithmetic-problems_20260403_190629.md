# Using GPUs And LLMs Can Be Satisfying for Nonlinear Real Arithmetic Problems

## Quick Facts
- arXiv ID: 2603.07764
- Source URL: https://arxiv.org/abs/2603.07764
- Reference count: 40
- Primary result: GANRA solves over five times as many Sturm-MBO instances with less than 1/20th the runtime of previous best solvers, and LLM-generated code approaches manual optimization performance.

## Executive Summary
GANRA presents a novel SMT solver for quantifier-free nonlinear real arithmetic (NRA) that integrates gradient descent, GPU acceleration, and LLM-based code generation. By converting NRA constraints into a differentiable loss function and using batched optimization on GPUs, GANRA efficiently explores the search space. A key innovation is automatic operation grouping—either manually tailored or generated by an LLM—to maximize GPU utilization. Evaluated on the Kissing and Sturm-MBO benchmarks, GANRA dramatically outperforms state-of-the-art solvers, solving many more instances in a fraction of the time. This work highlights the synergistic potential of formal methods, machine learning, and high-performance computing for hard NRA problems.

## Method Summary
GANRA addresses NRA by first transforming the formula into a loss function L2O_ϵ, where any satisfying assignment yields a value ≤ 0. It then employs batched gradient descent (Adam optimizer, learning rate 10⁻³) on random initial points within a bounded domain, projecting variables as needed. Candidates with L2O_ϵ ≤ 0 are verified by Z3 or direct checking to ensure soundness. To exploit GPU parallelism, operations in the L2O computation are grouped into vectorized or matrix operations; this grouping is performed manually for each benchmark or automatically via an LLM (OpenAI o1-preview) that generates PyTorch code from example instances. The LLM output is validated for syntax and semantics. The overall process requires no manual per-benchmark optimization beyond parsing, making it scalable to new NRA problems.

## Key Results
- On Sturm-MBO, GANRA proves satisfiability for over five times as many instances as the previous best solver, with runtime reduced to less than 1/20th.
- On Kissing, GANRA solves 40 out of 45 instances; LLM-generated code achieves near-identical performance to manual optimization (9.62s vs. 9.13s).
- LLM-based code generation produces functional and efficient GPU code, though it sometimes falls short of manual-level optimization (Sturm-MBO: 38 vs. 57 instances solved).

## Why This Works (Mechanism)
### Mechanism 1: Gradient Descent as a Heuristic for NRA
- **Claim**: Gradient descent can efficiently find potential satisfying assignments for NRA problems by optimizing a derived function.
- **Mechanism**: Convert the NRA formula ϕ(x) into a function L2O_ϵ(ϕ(x)) such that any model x satisfies L2O_ϵ(ϕ(x)) ≤ 0. Apply batched gradient descent to minimize this function. Candidates with L2O_ϵ(ϕ(x)) ≤ 0 are verified by Z3 or direct checking.
- **Core assumption**: Gradient descent converges to non-positive regions that likely contain satisfying assignments; verification ensures soundness.
- **Evidence anchors**:
  - [abstract] "prior work proposed a promising approach based on gradient descent ... we extend their ideas"
  - [section 3] Formal L2O definitions in Equations (2)–(5); process of converting constraints.
  - [corpus] Not directly addressed; relies on prior work (Cimatti et al., 2022; Liu et al., 2023). Assumption: Gradient descent is effective per those works.
- **Break condition**: Failure to find non-positive point within timeout; ϵ=0 worsens performance for equality-heavy instances (Kissing).

### Mechanism 2: Operation Grouping for GPU Parallelism
- **Claim**: Grouping independent operations in the L2O computation enables efficient GPU utilization, yielding significant speedups.
- **Mechanism**: Structure computations to maximize parallelizable operations. For Kissing: compute squared norms and pairwise distances via matrix ops. For Sturm-MBO: precompute variable powers, then multiply by coefficients.
- **Core assumption**: Problem structure admits such grouping; GPUs excel at batched independent operations.
- **Evidence anchors**:
  - [abstract] "automatically grouping similar operations ... to maximize GPU utilization"
  - [section 4] Manual grouping strategies for Kissing and Sturm-MBO.
  - [section 5] LLM automates grouping; examples show partial success (Kissing) and suboptimal grouping (Sturm-MBO).
- **Break condition**: Sequential dependencies limit grouping; LLM may miss opportunities (e.g., repeated powers in Sturm-MBO).

### Mechanism 3: LLM-Based Automatic Code Generation
- **Claim**: LLMs can generate optimized GPU code for L2O functions by pattern detection, removing manual per-benchmark optimization.
- **Mechanism**: Prompt LLM (o1-preview) with two example instances; it outputs PyTorch code that groups operations. Syntax errors fixed via feedback; semantic errors filtered by verification.
- **Core assumption**: LLM understands formula structure and produces semantically equivalent, efficient code; even suboptimal code helps.
- **Evidence anchors**:
  - [abstract] "LLM-based code generation ... automatically grouping similar operations"
  - [section 5] LLM prompt, responses; Kissing LLM code misses some optimizations (duplicate pairwise distances); Sturm-MBO LLM code had syntax error, fixed via feedback.
  - [section 6] LLM version near manual performance (Kissing: 40 SAT, runtime 9.62s vs. manual 9.13s; Sturm-MBO: 38 SAT vs. manual 57).
- **Break condition**: Syntax errors (caught) or semantic errors (lead to spurious candidates, but sound due to verification). LLM may not achieve manual-level optimization.

## Architecture Onboarding
- **Component map**: Formula Parser → Code Generator → GPU Executor → Optimizer → Verifier → Main Loop
- **Critical path**: Parse formula → generate GPU code → initialize batch → repeat: evaluate L2O, gradient update, project, verify until success or timeout.
- **Design tradeoffs**:
  - Manual vs. LLM code: Manual optimal but labor-intensive; LLM flexible but suboptimal.
  - Batch size: Larger batches increase parallelism but use more memory.
  - ϵ: Larger ϵ eases optimization but may increase false positives; ϵ=0 for equalities makes problem harder.
  - Verification: Z3 sound but slow; direct check faster when no equalities.
- **Failure signatures**:
  - Timeout: Hard instance, unsatisfiable, or poor initialization.
  - High rejection rate: ϵ too large or L2O function misspecified.
  - LLM errors: Syntax errors (caught at runtime) or semantic errors (cause spurious candidates, filtered by verification).
  - Low GPU utilization: Poor grouping leads to sequential execution; monitor GPU occupancy.
- **First 3 experiments**:
  1. Kissing benchmark: Compare GANRA variants (sequential/manual/LLM) against baselines (Z3, CVC5, UGOTNL, NRAgo). GANRA solves 40 SAT (LLM 40) with lower runtime.
  2. Sturm-MBO benchmark: GANRA (modified interval version) solves 57 (LLM 38) vs. best baseline 10; large runtime reduction.
  3. Ablation on Sturm-MBO-like instances: Vary polynomial size (P, N). Show GANRA outperforms Z3 more for larger N (complex products), highlighting gradient descent scalability.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: How can the performance gap between LLM-generated and manually optimized GPU code for NRA problems be systematically reduced?
- **Basis in paper**: [explicit] "Even though we successfully demonstrate that LLMs are capable of writing efficient code for the computation of given formulas, they also lack behind the performance of hand-written code. This demonstrates two orthogonal research directions: On the one hand, a tuning of the LLM prompt, or a better feedback loop that allows the LLM to iteratively improve its code may be able to increase the performance of the LLM-based implementation."
- **Why unresolved**: The paper shows LLMs produce functional but suboptimal code (e.g., failing to precompute repeated powers in Sturm-MBO). The relative importance of prompt design, iterative refinement, and inherent LLM limitations remains unexplored.
- **What evidence would resolve it**: Controlled experiments measuring code quality (execution time, parallelization efficiency) across systematic variations in prompt structure, few-shot examples, and automated feedback mechanisms (e.g., execution-based refinement loops) on a diverse benchmark set.

### Open Question 2
- **Question**: Can a finite set of generic optimization patterns be identified that covers the structure of most NRA benchmarks, enabling automatic (non-LLM) code generation with performance comparable to manual optimization?
- **Basis in paper**: [explicit] "On the other hand, a more thorough analysis of a larger set of benchmarks may unearth underlying patterns that would allow to write hand-optimized code that directly supports a wide variety of different benchmarks. This would potentially remove the need for LLMs entirely."
- **Why unresolved**: The patterns exploited in Kissing (vectorized norms, pairwise distances) and Sturm-MBO (parallel monomial products) are specific to those benchmark families. It is unknown whether these generalize or if a pattern-based compiler for NRA is feasible.
- **What evidence would resolve it**: A large-scale empirical study analyzing the ASTs or computational graphs of hundreds of NRA instances from multiple sources to cluster recurring structural motifs. Success would be demonstrated by a pattern-matching code generator that matches or exceeds LLM-based performance on unseen benchmarks.

### Open Question 3
- **Question**: How can gradient-descent-based NRA solving (GANRA) be effectively combined with complete (decision) procedures to handle both satisfiable and unsatisfiable instances within a single solver framework?
- **Basis in paper**: [explicit] "GANRA has no ability to prove unsatisfiability. For unsat instances, it would always result in a timeout, making them indistinguishable from hard but satisfiable instances. Ultimately, the concept of GANRA should therefore be integrated with a complete solver by calling GANRA as part of a portfolio approach." The paper also notes missed opportunities: "our implementation does not benefit from any of the improvements implemented in UGOTNL and NRAgo, such as Basinhopping ... or the topological degree test."
- **Why unresolved**: The paper suggests integration but provides no architecture, evaluation, or analysis of the challenges (e.g., when to invoke gradient descent vs. complete methods, how to combine partial information, overhead management).
- **What evidence would resolve it**: Design and implementation of a portfolio or incremental solver that dynamically schedules GANRA alongside a complete SMT solver (e.g., using a timeout-based portfolio or a learned selector). Evaluation would measure overall solver performance (PAR-2 score) on mixed benchmark suites, particularly the ability to quickly prove satisfiability while still guaranteeing eventual unsatisfiability answers.

### Open Question 4
- **Question**: What are the precise problem characteristics (e.g., polynomial degree, number of variables, sparsity, structure) that predict whether a gradient-descent approach like GANRA will be effective for a given NRA instance?
- **Basis in paper**: [explicit] "Evaluating GANRA on more benchmarks, preferably the entire set of available quantifier-free NRA problems, may provide valuable insights into its strength and failure cases." [inferred] The ablation study in Section 6.3 shows GANRA excels for larger total exponents (N) in Sturm-MBO-like problems, but the underlying reason (e.g., problem hardness for CAD vs. suitability for optimization) is not analyzed.
- **Why unresolved**: The paper's custom benchmark study suggests a correlation with problem "complexity" but lacks a rigorous feature analysis. Without a predictive model, users cannot know a priori if GANRA is appropriate for a new problem.
- **What evidence would resolve it**: Statistical analysis (e.g., regression, feature importance) on a large benchmark corpus where each instance is annotated with syntactic features (degree, term count, variable count, sparsity) and semantic features. The goal is to build a classifier or heuristic that predicts GANRA's success probability or expected runtime, enabling informed solver selection.

## Limitations
- LLM dependency: Results rely on OpenAI o1-preview, which is not publicly available, hindering direct replication and raising questions about generalizability to other LLMs.
- Benchmark scope: Evaluation is limited to two specialized NRA benchmarks (Kissing, Sturm-MBO); performance on broader, diverse NRA problems remains unknown.
- Hardware specificity: Reported speedups assume NVIDIA H100 GPUs; performance on other GPU architectures is not characterized.

## Confidence
- Gradient descent heuristic: Medium
- GPU operation grouping: Medium-High
- LLM code generation utility: Low-Medium
