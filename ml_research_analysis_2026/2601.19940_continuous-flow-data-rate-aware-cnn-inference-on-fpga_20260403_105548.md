# Continuous-Flow Data-Rate-Aware CNN Inference on FPGA

## Quick Facts
- **arXiv ID**: 2601.19940  
- **Source URL**: https://arxiv.org/abs/2601.19940  
- **Reference count**: 40  
- **Primary result**: Proposes a continuous-flow architecture that maintains near 100% hardware utilization for FPGA-based CNN accelerators, reducing arithmetic resources from 4.3M to 12.2k for MobileNetV1 α=1.0 while achieving 6,944 inferences/sec at 3.55 mJ/inference.

## Executive Summary
FPGA-based CNN accelerators often suffer severe hardware underutilization when data rates drop in layers with pooling or stride >1. This paper introduces a continuous-flow, data-rate-aware architecture that uses pipeline interleaving and reconfigurable processing units (KPUs for convolution, PPUs for pooling, FCUs for fully connected) to keep utilization near 100%. Implicit zero-padding via multiplexers and adaptive component sharing ensure a seamless data flow across layers. Evaluated on a Xilinx Virtex UltraScale+, the design delivers orders-of-magnitude reductions in arithmetic resources compared to fully parallel implementations, with competitive throughput, latency, and energy efficiency.

## Method Summary
The approach combines quantization-aware training (using MQUAT to 8-bit fixed-point, 12-bit last layer) with automated HDL generation. A code generator takes a CNN specification (e.g., MobileNetV1, ResNet18), computes per-layer data rates (equation 8), and configures interleaving factors and unit counts. KPUs handle convolution with implicit padding, PPUs perform pooling, and FCUs aggregate data for fully connected layers. The generated HDL is synthesized in Vivado for the target FPGA, with post-synthesis simulation for power analysis. A bit-accurate simulator validates inference accuracy.

## Key Results
- Resource reduction: MobileNetV1 α=1.0 uses only 12.2k adders/multipliers vs. 4.3M in a reference fully parallel design.
- Performance: 6,944 inferences/sec at 200 MHz on a Xilinx Virtex UltraScale+ (XCVU37P).
- Energy efficiency: 3.55 mJ per inference, outperforming state-of-the-art in throughput, latency, and energy.

## Why This Works (Mechanism)
Pipeline interleaving merges low-rate streams from layers with stride >1 into a continuous high-rate flow, eliminating stalls. Implicit zero-padding in KPUs (via multiplexers) removes the need for explicit padding hardware while preserving output continuity. Reconfigurable units (KPUs/PPUs/FCUs) adapt to each layer’s specific data rate and computational needs, and component sharing (e.g., multiplexing arithmetic units) drastically cuts area without sacrificing utilization. Together, these techniques maintain a steady flow of data through the pipeline, ensuring that arithmetic resources are almost always busy.

## Foundational Learning
- **Continuous-flow data rate adaptation**: *Why needed*: Prevents hardware stalling when layer data rates drop due to pooling or large strides. *Quick check*: Verify per-layer output rates (using eq. 8) form a monotonic sequence or are equalized via interleaving.
- **Pipeline interleaving**: *Why needed*: Merges multiple low-rate input streams into a single high-rate stream to feed downstream layers. *Quick check*: Confirm interleaving factor \(I_\ell\) satisfies \(r_{\ell-1} \cdot I_\ell = r_\ell\) (eq. 9) for all layers.
- **Implicit zero-padding**: *Why needed*: Eliminates explicit padding logic and buffers, reducing area while maintaining feature map continuity. *Quick check*: Inspect `pad_i` signals (eq. 10) to ensure zeros are inserted only at boundary cycles and do not affect valid outputs.
- **Reconfigurable processing units (KPUs/PPUs/FCUs)**: *Why needed*: Each layer type (convolution, pooling, fully connected) has distinct data access patterns and arithmetic needs. *Quick check*: Match unit configuration (kernel size, channels, aggregation factor) to layer specifications from code generator output.
- **Quantization-aware training (MQUAT)**: *Why needed*: Ensures 8-bit fixed-point inference accuracy aligns with hardware arithmetic precision. *Quick check*: Validate top-1 ImageNet accuracy of the quantized model (e.g., ~70.5% for MobileNetV1 α=1.0) before hardware mapping.
- **Automated HDL generation**: *Why needed*: Translates high-level model specs into optimized, layer-specific hardware descriptions with correct data rates and interleaving. *Quick check*: Compare generated resource estimates (adders, multipliers, MUXes) against theoretical values in Tables VI–VII.

## Architecture Onboarding
**Component map**: Input -> KPU (convolution + implicit padding) -> PPU (pooling) -> [KPU / FCU] (per subsequent layer) -> Output, with interleaving units inserted between stages where consecutive layer data rates differ.

**Critical path**: Longest delay through arithmetic units (adders/multipliers in KPU/FCU) and multiplexing logic for implicit padding and stream interleaving.

**Design tradeoffs**:
- Interleaving factor vs. buffer size: Higher \(I_\ell\) improves utilization but increases buffer depth and control complexity.
- Resource sharing vs. throughput: Sharing arithmetic units across layers reduces area but may cap maximum frame rate.
- Reconfigurability vs. overhead: Flexible units add control logic but enable adaptation to diverse CNN architectures.

**Failure signatures**:
- Underutilization: Data rate mismatch causing idle cycles; monitor KPU/PPU/FCU busy signals.
- Resource overuse: Incorrect counts of units \(C_\ell\) or interleaving factors \(I_\ell\); compare generated HDL to expected formulas (Section V).
- Accuracy drop: Quantization errors; run bit-accurate simulator on ImageNet validation set.
- Timing failure: Critical path exceeds clock target; check Vivado timing report for interleaving/padding logic.
- Data corruption: Implicit padding inserting zeros at wrong cycles; test boundary feature map pixels.

**Exactly 3 first experiments**:
1. Generate HDL for MobileNetV1 α=1.0 using the provided code generator; extract arithmetic resource counts (adders, multipliers) and compare to Table VI.

## Limitations
- Code generator and FloPoCo integration details are unspecified, hindering independent verification of HDL generation.
- MQUAT training hyperparameters (quantization ranges, fine-tuning schedule) are not disclosed, risking accuracy deviations.
- Residual connection merging logic in models like ResNet is underspecified; control circuitry for pixel indexing is omitted from resource accounting.
