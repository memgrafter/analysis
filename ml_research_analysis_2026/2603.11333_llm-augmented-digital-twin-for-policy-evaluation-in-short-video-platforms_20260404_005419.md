# LLM-Augmented Digital Twin for Policy Evaluation in Short-Video Platforms

## Quick Facts
- **arXiv ID:** 2603.11333
- **Source URL:** https://arxiv.org/abs/2603.11333
- **Reference count:** 30
- **Primary result:** LLM-based creator campaign planning increased total gift revenue by 3.6% while reducing revenue inequality (Gift Gini from 0.624 to 0.584).

## Executive Summary
Evaluating platform policies in short-video ecosystems is challenging due to human-AI feedback loops that shape long-horizon and distributional outcomes. This paper introduces an LLM-augmented digital twin with a modular four-twin architecture (User, Content, Interaction, Platform) and an event-driven execution layer to support reproducible counterfactual experiments. LLMs are integrated as schema-constrained decision services (e.g., for creator campaign planning, trend prediction) and managed by a cost-aware optimizer to preserve scalability. Experiments demonstrate that LLM-based campaign planning improves monetization and equity, while trend forecasting boosts engagement without sacrificing topical diversity—even under tight LLM budgets via progressive degradation.

## Method Summary
The simulator models a short-video platform as four bounded twins that interact via a typed event bus. The Environment Orchestrator routes agent actions to the Platform Twin, where policies (e.g., recommendation, promotion) are implemented as pluggable components. Events propagate state changes to the User, Content, and Interaction twins in a deterministic loop. LLM services (e.g., `CREATOR_CAMPAIGN`, `TREND_PREDICTION`) are invoked through a unified optimizer that enforces JSON schemas, manages caching, and supports three-tier execution (live LLM, cached responses, deterministic surrogates) to control costs. This design isolates policy logic within the Platform Twin, enabling counterfactual substitution while maintaining closed-loop dynamics.

## Key Results
- LLM-based creator campaign planning increased total gift revenue by 3.6% and reduced revenue inequality (Gift Gini: 0.624 → 0.584).
- LLM-assisted trend forecasting raised average watch time (9.656s → 9.785s) with stable topical diversity (hashtag entropy unchanged), but increased view concentration (View Gini: 0.886 → 0.964).
- The system remained stable under a $10 LLM budget cap via progressive degradation without collapsing key metrics.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** A modular four-twin architecture with event-driven execution reproduces closed-loop feedback dynamics for policy evaluation.
- **Mechanism:** The architecture decomposes the ecosystem into bounded subsystems with explicit state and interaction contracts via a typed event bus. Platform policies are pluggable components within the Platform Twin; counterfactual substitution holds other state constant. The event-driven layer ensures deterministic state transitions, preserving circular dependencies between agent behavior and algorithmic exposure.
- **Core assumption:** Isolating policy logic within the Platform Twin and using explicit event schemas maintains stable feedback loops across counterfactual runs.
- **Evidence anchors:** [abstract] describes the modular architecture and event-driven layer; [section 3.1-3.2] details the four twins and event bus; neighboring work (e.g., "Y Social") uses similar digital twins.
- **Break condition:** If a policy mutation alters shared state outside the Platform Twin’s registry (e.g., unrecorded side effects), counterfactual isolation fails.

### Mechanism 2
- **Claim:** Selective integration of LLMs as schema-constrained decision services injects semantic realism without collapsing scalability.
- **Mechanism:** LLMs are invoked only for tasks requiring high-fidelity semantic reasoning (e.g., campaign plans, trend forecasts). Their outputs are constrained to JSON schemas and routed through a cost-aware optimizer with tiered fallbacks (live → cached → surrogate). This confines LLM stochasticity to specific nodes while the core simulation remains deterministic.
- **Core assumption:** Macro-level outcomes are not overly sensitive to fine-grained LLM variability, provided output distributions match observed ranges.
- **Evidence anchors:** [abstract] and [section 3.3] describe the optimizer and tiered execution; experiments in [section 4.1-4.2] show controlled outcome differences when toggling LLMs.
- **Break condition:** If LLM output distribution drifts significantly from calibration (e.g., implausible hashtag bundles), downstream twins produce unnatural content, destabilizing the loop.

### Mechanism 3
- **Claim:** A cost-aware progressive degradation system enables stable long-horizon simulation under tight LLM budgets by falling back to deterministic surrogates.
- **Mechanism:** The optimizer tracks spend and triggers tier demotion at thresholds (e.g., >80% → surrogate for comment generation; >95% → persona generation). Surrogates implement the same output schemas, ensuring handlers never fail. Batching and caching amortize live calls.
- **Core assumption:** Surrogate behaviors are sufficiently close to LLM outputs that macro-level trends remain within acceptable variance for policy comparison.
- **Evidence anchors:** [section 3.3] describes progressive degradation; [section 4.2] shows stability under a $10 budget cap.
- **Break condition:** If surrogates introduce systematic biases (e.g., overestimating low-velocity hashtags), the governance loop may pursue spurious interventions.

## Architecture Onboarding

### Component Map
The system consists of:
- Four Twins: User, Content, Interaction, Platform
- Event Bus: typed events for inter-twin communication
- Environment Orchestrator: routes actions to Platform handlers
- LLM Optimizer: manages LLM calls with caching and budget tracking

Data flow:
User/Content/Interaction/Platform Twins <-> Event Bus <-> Orchestrator
Platform Twin -> LLM Optimizer -> (Live -> Cached -> Surrogate)
LLM Optimizer -> schema-validated response -> Platform Twin

State boundaries: Each twin owns persistent state; cross-twin reads via queries; writes only via events.

### Critical Path
1. User agent emits `WATCH_VIDEO` action.
2. Orchestrator routes to Platform’s `watch_video` handler.
3. Handler retrieves content from Content Twin, calls Interaction Twin’s simulator.
4. Interaction emits `VIDEO_WATCHED` event.
5. Event bus dispatches to User (memory update) and Content (engagement stats) handlers.
6. Platform updates its observational state and may trigger governance/promotion cycles.
7. If platform invokes trend forecasting, it serializes a `TREND_PREDICTION` request through the LLM Optimizer before the next control iteration.

### Design Tradeoffs
- **Fidelity vs. Cost:** High-fidelity LLM personas/captions improve individual realism but are expensive; system reserves live LLM for policy-relevant cohorts and uses cached/surrogate for bulk.
- **Modularity vs. Integration Complexity:** Strict event boundaries simplify ablation but require careful schema design; adding a new cross-twin signal means defining a new event type and updating multiple handlers.
- **Determinism vs. Adaptivity:** Core interaction physics is deterministic for reproducibility; LLM services introduce controlled stochasticity only at specific decision nodes.

### Failure Signatures
- **Budget exhaustion:** LLM Optimizer logs show >95% spend with frequent surrogate fallbacks; monitor `BUDGET_EXCEEDED` events.
- **Schema mismatch:** Event handlers throw parsing exceptions when LLM outputs violate expected JSON structure; check optimizer’s validation logs.
- **State inconsistency:** If a twin’s state diverges from platform registry (e.g., Content Twin’s view count ≠ Platform’s logged aggregate), look for direct state mutations bypassing events.
- **Performance collapse:** Orchestrator queue latency spikes when many agents await LLM responses in live tier; enable more aggressive batching or increase surrogate quota.

### First 3 Experiments
1. **Sanity check event propagation:** Run a single-agent, single-content scenario. Verify that a `WATCH_VIDEO` action yields exactly one `VIDEO_WATCHED` event and that User/Content state updates are idempotent across repeated runs with same seed.
2. **LLM tier routing test:** Configure a `CREATOR_CAMPAIGN` request with a tiny budget (e.g., $0.01). Confirm the optimizer routes to surrogate immediately and returns a valid but deterministic plan (e.g., the fixed 3‑day template).
3. **Policy component swap:** Replace the default recommender with a “no‑viral‑boost” variant in the Platform Twin. Measure shift in View Gini and hashtag entropy over 100 steps to confirm the counterfactual interface works as intended.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How can the digital twin achieve scalable simulation of one million users without altering its core action-event interface or cost-governance mechanisms?
- **Basis in paper:** The conclusion states: “we will improve scalability via parallel execution and surrogate modeling so that large‑population regimes (e.g., one million users) can be simulated without changing the action/event interface or the cost‑governance contract.”
- **Why unresolved:** Current implementations may face computational bottlenecks or architectural constraints when scaling to massive agent populations, potentially requiring redesigns that break modularity.
- **What evidence would resolve it:** Implement parallel processing and surrogate models, then benchmark simulation speed, memory usage, and outcome fidelity against smaller‑scale runs to confirm maintained performance and reproducibility.

### Open Question 2
- **Question:** What is the impact of replacing abstract content representations with pixel‑level multimodal generative synthesis on simulation fidelity for short‑video platform dynamics?
- **Basis in paper:** The conclusion notes: “we will enhance fidelity by integrating multimodal generative models for pixel‑level video synthesis.”
- **Why unresolved:** The existing feature‑based content profiles may omit visual and auditory nuances that critically affect user engagement, trend diffusion, and platform feedback loops.
- **What evidence would resolve it:** Run comparative simulations with and without pixel‑level synthesis, measuring deviations in key metrics (e.g., watch time, trend lifespan) against ground‑truth platform data to quantify fidelity gains.

### Open Question 3
- **Question:** How do explicit human‑in‑the‑loop interfaces change the effectiveness of policy testing and moderation strategies within the digital twin?
- **Basis in paper:** The conclusion proposes: “we plan to implement explicit human‑in‑the‑loop interfaces that allow researchers to interactively test policy interventions and moderation strategies against dynamic, adaptive populations.”
- **Why unresolved:** Fully automated simulations may miss nuanced human‑AI interactions; incorporating real‑time human input could reveal new behavioral adaptations or policy vulnerabilities.
- **What evidence would resolve it:** Deploy human‑in‑the‑loop features, conduct controlled experiments where researchers use the interface to adjust policies, and compare outcomes (e.g., fairness, stability) to fully automated runs.

### Open Question 4
- **Question:** Which additional AI‑driven platform modules (e.g., content moderation, ad allocation) should be integrated into the twin to enable comprehensive evaluation of AI‑enabled policies?
- **Basis in paper:** The conclusion indicates: “we will broaden the set of platform‑relevant AI decision modules evaluated within the twin (e.g., governance workflows and operational analytics).”
- **Why unresolved:** The current evaluation focuses on creator campaign planning and trend forecasting; omitting other AI systems like moderation bots or recommendation algorithms limits the twin’s applicability to real‑world policy scenarios.
- **What evidence would resolve it:** Survey industry platforms to identify prevalent AI modules, implement representative ones in the twin, and assess their interactions with existing policies through counterfactual experiments.

## Limitations
- Core simulation parameters (e.g., user preference evolution rates, watch‑time distribution, hook‑threshold coefficients) are not numerically specified and must be tuned to match reported baseline metrics.
- GPT‑4 model version, API parameters (temperature, max tokens), and full prompt templates for LLM services are missing; only high‑level context and schemas are provided.
