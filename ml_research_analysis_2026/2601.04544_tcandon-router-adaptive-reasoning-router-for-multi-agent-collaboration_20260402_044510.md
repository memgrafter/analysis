# TCAndon-Router: Adaptive Reasoning Router for Multi-Agent Collaboration

## Quick Facts
- **arXiv ID:** 2601.04544
- **Source URL:** https://arxiv.org/abs/2601.04544
- **Reference count:** 40
- **Primary result:** An adaptive reasoning router that selects multiple expert agents per query and refines their outputs, achieving state-of-the-art accuracy on multiple benchmarks and a 63% win rate for troubleshooting queries.

## Executive Summary
TCAndon-Router (TCAR) introduces a novel multi-agent collaboration framework that overcomes key limitations of traditional task routing. Instead of making brittle single-agent decisions, TCAR first generates an explicit natural-language reasoning chain to semantically align a query with *multiple* relevant agent descriptions. This enables flexible handling of overlapping capabilities and dynamic agent onboarding without retraining. The selected agents execute in parallel, and a dedicated Refining Agent synthesizes their responses into a final answer, effectively resolving conflicts and integrating complementary expertise. Evaluated on four public benchmarks and a real enterprise dataset (QCloud), the 4B-parameter TCAR model outperforms larger models, demonstrating that adaptive reasoning and collaborative refinement yield robust, high-performance multi-agent systems suitable for evolving enterprise environments.

## Method Summary
TCAR employs a two-stage training procedure for its Router component. First, Supervised Fine-Tuning (SFT) trains a language model to generate a reasoning chain (`Cq`) followed by a set of selected agent IDs (`Aq`) for each query, using curated (query, gold agent set) pairs. Second, Reinforcement Learning (DAPO) optimizes a custom reward function combining precision-like (`R1`) and recall-like (`R2`) scores with a length penalty, shifting the policy from conservative single-agent selection to robust multi-agent coverage. At inference, the Router constructs a prompt containing the query and all available agent descriptions. It outputs a reasoning trace and a subset of agent IDs. The corresponding domain-specific agents are invoked in parallel. A separate Refining Agent then aggregates their responses into a single, coherent final answer. New agents are added by simply appending their description to the prompt, requiring no model retraining.

## Key Results
- Achieves 91.63% accuracy on HWU64, 96.70% on MINDS14, and 91.58% on SGD.
- Reaches 93.98% F1 on the real-world enterprise dataset QCloud.
- The Refining Agent yields a 63% win rate in human evaluation for troubleshooting queries vs. using a single randomly selected agent.
- Operates with low overhead, selecting an average of 1.37 agents and maintaining sub-second end-to-end latency.

## Why This Works (Mechanism)
### Mechanism 1: Reasoning-Based Multi-Agent Selection
- **Claim:** Generating explicit natural-language reasoning before selecting agents enables flexible multi-agent selection and resolves conflicts from overlapping capabilities.
- **Mechanism:** The router first produces a `Cq` reasoning chain that semantically aligns the query with agent descriptions, then predicts a subset `Aq ⊆ A` (rather than a single label). This transforms routing from brittle classification to interpretable set prediction.
- **Core assumption:** Semantic alignment via reasoning allows the model to identify *all* relevant agents in ambiguous or cross-domain queries, rather than forcing a single choice.
- **Evidence anchors:** [abstract] "TCAR supports dynamic agent onboarding and first generates a natural-language reasoning chain before predicting a set of candidate agents." [section 3.3] "Instead of outputting only a discrete agent label, the router generates both a natural-language reasoning chain Cq and the corresponding agent subset Aq."
- **Break condition:** If reasoning generation becomes mechanically templated or diverges from agent description semantics (see Section 5.1 error type 3), the multi-agent selection advantage degrades toward single-label performance.

### Mechanism 2: Collaborative Execution with Refining Agent
- **Claim:** Parallel execution of selected agents followed by a dedicated Refining Agent aggregates complementary expertise and reconciles conflicts, improving final answer quality.
- **Mechanism:** After routing outputs `Aq = {a_i1, ..., a_ik}`, all `k` agents independently respond `rij = aij(q)`. The Refining Agent `F` then synthesizes `{rij}` into a single coherent `yq`, explicitly handling conflicts and complementary information.
- **Core assumption:** Domain-specific agents provide partial, potentially conflicting perspectives that, when integrated by a coordinator, yield more comprehensive and accurate solutions than any single agent.
- **Evidence anchors:** [abstract] "We design a collaborative execution pipeline in which selected agents independently produce responses, which are then aggregated and refined into a single high-quality response by a dedicated Refining Agent." [section 3.3] "Through the design of multi-agent selection + collaborative execution + aggregated fusion, the system no longer relies on a one-shot single-point decision to eliminate conflicts."
- **Break condition:** If the Refining Agent fails to correctly integrate conflicting or complementary information (e.g., due to poor RAG support or synthesis errors), the multi-agent overhead may degrade performance relative to a single expert.

### Mechanism 3: Prompt-Based Dynamic Agent Onboarding
- **Claim:** Prompt-based dynamic agent onboarding (appending new description `d_new` to `D`) allows seamless expansion without retraining the router, maintaining performance as business domains evolve.
- **Mechanism:** The router `R` operates on `Prompt(q, A) = Φ(ins, q, D)`. Adding an agent only modifies `D → D ∪ {d_new}`, leaving `R`'s parameters unchanged. The model's generalization from SFT+RL handles novel descriptions.
- **Core assumption:** The router's reasoning capability, trained via SFT+RL, can perform zero-shot semantic alignment between queries and *unseen* agent descriptions at inference time.
- **Evidence anchors:** [abstract] "TCAR supports dynamic agent onboarding... requires only appending a new `d_new` to the existing set." [section 3.2] "In TCAR, adding a new agent requires only appending a new `d_new`... The routing process then becomes `(Cq, Aq) = R(Prompt(q, D'))`... the router R itself does not need to be modified or retrained."
- **Break condition:** If new agent descriptions are poorly written (too brief/ambiguous) or introduce significant lexical/semantic shift, the router's generalization fails, leading to misrouting (Section 6 limitation).

## Foundational Learning
- **Concept:** Multi-Agent Routing as Set Prediction (vs. Single-Label Classification)
  - **Why needed here:** Traditional routers force `|Aq| = 1`, causing errors in overlapping domains. TCAR redefines routing as selecting a *subset* `Aq ⊆ A`, requiring understanding of multi-label semantics and conflict preservation.
  - **Quick check question:** How does treating routing as set prediction (rather than classification) change the loss function design and evaluation metrics?

- **Concept:** Reasoning Chains for Interpretable Alignment
  - **Why needed here:** Explicit `Cq` generation forces the model to articulate *why* multiple agents might be relevant, improving robustness to ambiguous queries and enabling engineer debugging (Section 5.1).
  - **Quick check question:** Why might a model produce a high-quality reasoning chain but still output an incorrect agent subset? (Hint: See error type 3 in Section 5.1.)

- **Concept:** Reinforcement Learning for Set-Level Rewards (DAPO)
  - **Why needed here:** SFT alone leads to conservative `|Aq| = 1` predictions. RL with custom rewards `R1` (precision-like) + `R2` (recall-like) + length penalty optimizes for *coverage* while avoiding irrelevant agents.
  - **Quick check question:** What is the purpose of the `max(1, |Aq|)` denominator in `R1` and `R2`, and how does it prevent reward hacking?

## Architecture Onboarding
- **Component map:** User Query -> Prompt Builder -> Router (R) -> (Reasoning Cq, Agent Set Aq) -> Parallel Agent Invocation (forall a_i in Aq) -> Individual Responses {rij} -> Refining Agent (F) -> Final Answer (yq)
- **Critical path:** User query `q` → Construct `Prompt(q, D)` → `R` generates `(Cq, Aq)` → Parallel invoke `{a_i(q) for a_i ∈ Aq}` → `F` synthesizes `yq` → User.
- **Design tradeoffs:**
  - Reasoning token overhead (~100 tokens) vs. interpretability/robustness.
  - Multi-agent parallelism vs. latency: `|Aq|_avg=1.37` keeps cost low; worst-case `k≤3` by prompt constraint.
  - Refining Agent complexity vs. answer quality: Adds a downstream call but resolves conflicts (63% win rate).
- **Failure signatures:**
  - Router misalignment: `Cq` mentions an agent not in `Aq`, or `Aq` omits agents implied by `Cq`.
  - Over-conservative routing: `|Aq| = 1` in high-conflict queries (SFT-only symptom).
  - Refining Agent refusal: `F` outputs "cannot answer" when agents provide partial info.
  - Description decay: Poorly maintained `d_i` causes systematic misrouting for an agent.
- **First 3 experiments:**
  1. **Ablation: Reasoning vs. No-Reasoning:** Train SFT model with/without `<Reason>` tag; expect multi-domain datasets (HWU64, SGD) show >3% gap due to conflict resolution.
  2. **Ablation: SFT-only vs. SFT+RL:** Compare `|Aq|` distribution and F1 on QCloud; RL should increase recall (coverage) without sacrificing precision.
  3. **Refining Agent Win Rate:** For troubleshooting queries with `|Aq|>1`, compare `random single-agent` vs. `multi-agent + Refining Agent` via human evaluation; expect >60% win rate.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can we ensure alignment between the generated reasoning chain and the final agent selection predictions in TCAR?
- **Open Question 2:** To what extent can the reliance on manually written agent descriptions be reduced or automated to maintain routing robustness when descriptions are suboptimal?
- **Open Question 3:** How can TCAR maintain high routing accuracy for low-frequency or highly specialized domains (long-tail scenarios) without extensive domain-specific retraining?

## Limitations
- **Agent description schema incompletely specified:** Exact required fields/format for `d_i` beyond the single appendix example are unclear.
- **RL training details withheld:** Key hyperparameters (`α`, `β`, `τ`, `G`, Slerp merging) are not provided, preventing exact replication.
- **Generalizability unknown:** Evaluation relies on tailored enterprise and specific public benchmarks; performance on unseen domains or with non-LLM agents is unverified.

## Confidence
- **Performance claims (SOTA numbers):** High — internally validated on 5 datasets with clear metrics.
- **Mechanism 1 (Reasoning → Multi-agent selection):** Medium — supported by paper's ablations and error analysis, but break condition noted; limited external evidence.
- **Mechanism 2 (Refining Agent synergy):** Medium-High — win-rate experiment shows clear benefit, though reliant on specific agent pool quality.
- **Mechanism 3 (Dynamic onboarding):** Low-Medium — conceptually sound but only demonstrated on 1–2 new agents; schema sensitivity not tested.
- **Scalability/latency claims:** Medium — average `|Aq|=1.37` is reported, but worst-case latency for `k=3` and long agent lists not fully disclosed.

## Next Checks
1. **Schema sensitivity test:** Systematically vary agent description richness (minimal name-only vs. detailed capability lists) and measure `|Aq|`/F1 degradation on HWU64; expected threshold: >15% drop with impoverished descriptions confirms overfitting to prompt template.
2. **RL hyperparameter ablation:** Re-train SFT model with sampled `α∈[0.3,0.7]`, `β∈[0.01,0.1]`; validate that precision/recall trade-off shifts as predicted by `R1`/`R2` design, and that `τ` filtering affects stability.
3. **Reasoning–selection consistency audit:** Manually annotate 100 reasoning chains for implied agent candidates; compute precision/recall of `Aq` against implied set. Expect >85% recall in ambiguous queries; lower indicates reasoning is not driving multi-agent selection.
