# Multilingual Reasoning Gym: Multilingual Scaling of Procedural Reasoning Environments

## Quick Facts
- arXiv ID: 2603.10793
- Source URL: https://arxiv.org/abs/2603.10793
- Reference count: 17
- Key outcome: Extends Reasoning Gym to 14 languages via template translation and procedural generation

## Executive Summary
The Multilingual Reasoning Gym addresses the absence of multilingual procedural reasoning environments for RLVR by extending the English-only Reasoning Gym to 14 languages. It translates 94 task templates via a hybrid LLM-human workflow with native speaker validation, adapting code for linguistic naturalness in morphologically rich languages. The release includes 74 fully translated tasks, 20 with adaptations, and retains core benefits: unlimited problem instances, adjustable difficulty, and cross-lingual parallelism. Evaluation across multiple models shows tasks are solvable, with performance scaling with model size but varying substantially by language (English consistently highest), demonstrating scalable data generation for multilingual reasoning research.

## Method Summary
The system extends the Reasoning Gym by translating task templates instead of individual samples, enabling unlimited multilingual problem generation. A hybrid LLM-human workflow extracts all English strings into template JSON files, with procedural logic remaining in code. Native speakers validate generated instances (not just templates) for logical fidelity and linguistic naturalness. Cross-lingual parallelism is preserved by using identical random seeds across languages, ensuring the same underlying reasoning challenge appears in all languages with only surface text differing.

## Key Results
- Successfully translates 94 task templates to 14 languages (74 fully translated, 20 adapted)
- Native speaker validation confirms logical fidelity and linguistic naturalness for 10 languages
- Cross-lingual parallelism preserved via identical random seeds across languages
- Models solve translated tasks with performance scaling by model size and varying by language (English highest)

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Template-based procedural generation enables unlimited, verifiable reasoning problems across languages without re-implementing core logic.
- **Mechanism:** The system extracts all hard-coded English strings from task generators into language-agnostic template JSON files. The procedural logic (e.g., generating a math problem, computing its solution) remains in code; only the surface rendering (prompts, instructions, answer formats) is replaced per language.
- **Core assumption:** The logical structure of a reasoning task (e.g., "find GCD of numbers X and Y") is language-independent; only its textual presentation requires translation.
- **Evidence anchors:**
  - [abstract]: "translating templates instead of individual samples enables us to create virtually unlimited samples also in non-English languages"
  - [section 3.1]: "we extract all hard-coded English strings into template JSON files, rewriting task code to support this if necessary"
- **Break condition:** Tasks fundamentally bound to language-specific properties (e.g., English word games, anagram lists from English corpora) are untranslatable without altering task difficulty or essence.

### Mechanism 2
- **Claim:** A hybrid LLM-human translation workflow with native-speaker validation ensures linguistic naturalness and correctness for morphologically rich languages.
- **Mechanism:** Claude Sonnet 4 generates initial translations, which are iteratively refined via LLM-based grading against rubrics. Native speakers then evaluate three procedurally generated samples per task (not just templates) for logical fidelity, word choice, and naturalness.
- **Core assumption:** Native speaker judgments on generated instances (not just templates) are necessary to catch issues that emerge only when dynamic parameters interact with grammar.
- **Evidence anchors:**
  - [section 3.2]: "we provide three procedurally generated samples per task to the human raters instead of showing the templates"
  - [section 3.2]: "translations are first graded using pre-defined rubrics and subsequently polished using a refinement prompt"
- **Break condition:** Validation fails for languages without available native speakers (Bengali, Telugu, Swahili) or for tasks where translation introduces logical ambiguities.

### Mechanism 3
- **Claim:** Cross-lingual parallelism is preserved by using identical random seeds across languages, enabling controlled, scalable comparison of model reasoning.
- **Mechanism:** The procedural generator uses a deterministic seed to produce a specific problem instance. The same seed produces the same underlying instance in all 14 languages, differing only in surface text.
- **Core assumption:** Reasoning difficulty is determined by the abstract problem structure, not linguistic framing; thus, the same seed yields equivalent difficulty across languages.
- **Evidence anchors:**
  - [abstract]: "Problems in the Multilingual Reasoning Gym are parallel across languages, enabling crosslingually parallel data generation at massive scale"
  - [section 1]: "instance generation across languages using the same seed allows for direct cross-lingual data at massive scale"
- **Break condition:** Linguistic framing influences perceived difficulty (e.g., longer words, complex morphology) or cultural context alters problem interpretation.

## Foundational Learning

- **Concept:** Procedural Generation
  - *Why needed here:* The entire system relies on code that can generate unlimited, unique, and verifiable problem instances. Understanding how generators and verifiers work is essential to extend or debug tasks.
  - *Quick check question:* How would you modify a generator to increase the difficulty range of a "simple equations" task while keeping its verifier valid?

- **Concept:** Template Abstraction
  - *Why needed here:* All multilingual functionality depends on clean separation of logic (code) from presentation (templates). Engineers must know how to correctly extract and structure template strings.
  - *Quick check question:* If a task's English template says "The {animal}'s {count} are {color}", what template structure would avoid pluralization issues in German or Russian?

- **Concept:** Verification Independence
  - *Why needed here:* Verifiers must operate on model outputs in any language (e.g., accept "4" or "vier" for "4"). Understanding how verifiers parse and compare answers across scripts and formats is critical.
  - *Quick check question:* How does the verifier for a "True/False" task handle translated boolean keywords like "Vero/Falso" (Italian) or " vrai/faux" (French)?

## Architecture Onboarding

- **Component map:** task_generator.py -> templates/{lang}.json -> verifier.py -> utils/seed_manager.py
- **Critical path:**
  1. Identify a task to multilingualize → check if it's "English-bound" (e.g., word ladder)
  2. Refactor code to extract all strings → populate base English template JSON
  3. Run LLM translation → iterate with rubric-based refinement
  4. Native speaker validation on 3 generated samples per task
  5. Manual final check of templates + 10+ sample outputs
  6. Add language to config; run cross-lingual seed test
- **Design tradeoffs:**
  - Template purity vs. adaptation: Some tasks (e.g., plural-dependent prompts) require code adaptation to avoid complex template logic. Tradeoff: more maintainable code vs. slight template flexibility loss.
  - Validation cost: Full native-speaker validation per task per language is expensive. Tradeoff: coverage (14 languages) vs. depth (only 10 validated; 3 unvalidated).
  - Parallelism fidelity: Using same seed ensures structural identity, but linguistic differences can affect difficulty. Tradeoff: strict parallelism vs. naturalness.
- **Failure signatures:**
  - English strings leaking into non-English outputs (check for "True/False", "example:", units like "days")
  - Verifier rejecting correct answers due to formatting (e.g., Japanese full-width punctuation)
  - Non-parallel instances: same seed produces different underlying data
  - Morphology errors: e.g., German adjective endings wrong when number is parameterized
- **First 3 experiments:**
  1. **Template extraction validation:** Pick a simple task (e.g., `basic_arithmetic`). Refactor to use templates. Generate 5 instances in English. Verify no hard-coded strings remain in generator code.
  2. **Translation workflow dry-run:** For one task (e.g., `gcd`), run the LLM translation + refinement pipeline on a new language (e.g., Thai). Manually inspect 3 generated samples for naturalness and logical fidelity.
  3. **Cross-lingual parallelism test:** For one task across 3 languages, fix seed=42. Generate 10 instances per language. Programmatically compare numerical values, logical structure, and answer values.

## Limitations

- Translation coverage gaps: Only 10 of 14 languages fully validated by native speakers, leaving Bengali, Telugu, Hindi, and Swahili with potential quality issues
- English-bound task restrictions: Word-based puzzles and English-specific games cannot be effectively multilingualized without reimplementation
- Cross-lingual difficulty parity: Linguistic complexity (e.g., longer German words, complex Russian morphology) may affect perceived difficulty despite identical underlying reasoning

## Confidence

- **High:** Template-based procedural generation mechanism and cross-lingual seed parallelism
- **Medium:** Hybrid LLM-human translation workflow with native speaker validation
- **Low:** Claims about universal applicability across all reasoning task types

## Next Checks

1. **Native speaker verification expansion:** Recruit native speakers for Bengali, Telugu, Hindi, and Swahili to validate 10 samples per task per language, measuring logical fidelity and naturalness against established rubrics.

2. **Cross-lingual difficulty assessment:** Run controlled experiments where the same seed generates tasks across 5 diverse languages (English, Chinese, German, Arabic, Japanese), measuring both solution accuracy and subjective difficulty ratings from bilingual evaluators.

3. **Morphological edge case analysis:** Systematically test tasks with parameters that trigger complex morphological agreement in Russian, Arabic, and German (e.g., gendered nouns, case agreement with numbers) to identify and fix generation bugs that produce grammatically incorrect outputs.
