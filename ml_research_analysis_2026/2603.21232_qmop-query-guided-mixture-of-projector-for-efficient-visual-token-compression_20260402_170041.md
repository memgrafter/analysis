# QMoP: Query Guided Mixture-of-Projector for Efficient Visual Token Compression

## Quick Facts
- **ArXiv ID:** 2603.21232  
- **Source URL:** https://arxiv.org/abs/2603.21232  
- **Reference count:** 40  
- **Primary result:** QMoP matches or exceeds the 576‑token baseline of LLaVA‑1.5‑7B using only 144 tokens, achieving 100.73% average performance on ten standard benchmarks and 61.8% on VTCBench, while reducing FLOPs and KV‑cache memory by 75%.

## Executive Summary
Multimodal large language models (MLLMs) face severe efficiency bottlenecks due to the large number of visual tokens produced by off‑the‑shelf vision encoders. QMoP introduces a **Query Guided Mixture‑of‑Projector** that dynamically compresses visual tokens with three specialized branches—pooling for global semantics, resampler for high‑level semantics, and pruning for fine‑grained details—orchestrated by a lightweight Query Guided Router (QGR). The QGR selects the two most relevant branches for each image‑text pair. A new benchmark, **VTCBench**, evaluates token compression across five complementary dimensions. QMoP attains state‑of‑the‑art results: it matches or surpasses the strong 576‑token LLaVA‑1.5‑7B baseline with merely 144 tokens, delivering up to 75% reductions in computational FLOPs and KV‑cache size while adding negligible projector overhead.

## Method Summary
QMoP processes an image with a CLIP vision encoder, yielding patch tokens \(X_{img}\) and a CLS token \(v_{CLS}\); the text query is encoded by CLIP to an EOS token \(t_{EOS}\). The QGR concatenates \(v_{CLS}\) and \(t_{EOS}\), passes them through a two‑layer MLP, and applies a softmax to obtain weights \(\{\alpha_1,\alpha_2,\alpha_3\}\) for the three compression branches, which run in parallel:

1. **Pooling branch** reshapes \(X_{img}\) into a 2D grid and performs local attention with learnable 2D queries, aggregating spatially adjacent tokens into a compact grid.
2. **Resampler branch** uses a fixed set of learnable query tokens that cross‑attend over all visual tokens, synthesizing high‑level semantic representations.
3. **Pruning branch** scores each token by combining visual saliency (attention from the vision encoder’s CLS token) and text relevance (similarity to \(t_{EOS}\)); tokens below a dynamic threshold are discarded.

During training (two stages), the router is first frozen and all three outputs are fused (simple sum or concatenation) to align each branch with the LLM embedding space. In stage‑2, the router and LLM are fine‑tuned on instruction data; the router’s temperature is annealed and Gumbel noise is added to stabilize routing. At inference, only the top‑2 weighted branches are selected, their weights renormalized, and their outputs summed to produce the final compressed token set \(T_{img}\), which is fed to the LLM along with text tokens.

## Key Results
- **Competitive efficiency:** Using only 144 tokens, QMoP reaches 100.73% of the normalized average accuracy of the 576‑token LLaVA‑1.5‑7B baseline on ten standard vision‑language benchmarks.
- **Strong VTCBench score:** Achieves 61.8% on the new comprehensive compression benchmark, outperforming prior compression methods.
- **Substantial resource savings:** Reduces computational FLOPs by 75% and KV‑cache memory by 75% relative to the baseline, with the projector overhead negligible (<0.5%).

## Why This Works (Mechanism)
### Mechanism 1: Pooling Branch for Global Semantics
The pooling branch preserves coarse‑grained global context by aggregating spatially adjacent tokens within local windows via a learnable 2D query map. This hierarchical pooling retains spatial coherence while discarding pixel‑level redundancy. The core assumption is that global scene structure can be captured by processing only proximate tokens, a premise shared with prior work (e.g., LDP‑v2, TokenPacker). Evidence: the paper states it “aggregates spatially adjacent tokens into a compact representation, effectively reducing spatial redundancy while preserving essential visual cues that capture global scene structures.” Break condition: tasks requiring long‑range spatial reasoning (e.g., counting widely scattered objects) may suffer because local windows cannot capture non‑local dependencies.

### Mechanism 2: Resampler Branch for High‑Level Semantics
The resampler branch employs a set of fixed‑length learned query tokens that attend to all visual tokens via cross‑attention, dynamically summarizing task‑relevant semantic content and filtering noise. The underlying assumption is that a small, adaptive query set can effectively condense salient information from a larger token set, as demonstrated in BLIP‑2 and related resampler designs. Evidence: the paper describes it as “leveraging learnable query tokens with cross‑attention mechanisms to selectively extract and aggregate critical visual information from high‑dimensional token representations.” Break condition: for fine‑grained tasks like reading small text, the resampler may discard critical low‑level details as noise.

### Mechanism 3: Pruning Branch for Fine‑Grained Details
The pruning branch retains critical fine‑grained details by scoring each token with a combination of two heuristics: **Importance** (attention from the vision encoder’s CLS token) and **Relevance** (similarity to the text EOS token). Tokens below a dynamic threshold are removed, preserving visually salient and text‑aligned patches. The assumption is that this rule‑based scoring approximates token importance. Evidence: the paper defines “Importance, which measures how much attention the class token allocates to each visual token” and “Relevance, which evaluates how closely each visual token is associated with the textual content.” Similar ideas appear in FasterVLM and VisionZip. Break condition: rigid pre‑defined scores may incorrectly prune subtle but task‑critical tokens if they receive low CLS attention or have poor text similarity.

## Foundational Learning
- **Mixture‑of‑Experts (MoE) Gating:** The Query Guided Router is a lightweight MoE‑style gating mechanism. Understanding MoE (learning to route to specialized sub‑networks) explains why QMoP dynamically weights branch outputs instead of fixed averaging. Quick check: Why does the router select different branches for the same image given different text queries? (Answer: The text query alters the joint feature \(f\), changing routing weights to activate branches suitable for the query’s task.)

- **Visual Token Redundancy in MLLMs:** CLIP‑ViT and similar encoders produce highly correlated tokens due to overlapping receptive fields and strong spatial coherence, creating computational inefficiency. Recognizing this redundancy motivates compression and highlights the danger of losing distinct information with naïve reduction. Quick check: Why might pooling work for “how many people?” but fail for “what brand is on the small logo?”? (Answer: Pooling discards fine details needed for small‑text recognition.)

- **Two‑Stage Instruction Tuning for MLLMs:** The standard pipeline—first align a visual projector, then fine‑tune the LLM on instructions—underpins QMoP’s training. Stage 1 ensures each branch learns basic cross‑modal alignment; stage 2 introduces the router and adapts the LLM to the compressed representations. Quick check: What purpose does a large temperature \(\tau\) serve early in stage 2 fine‑tuning? (Answer: It yields smoother routing distributions to encourage exploration before annealing to sharper selections.)

## Architecture Onboarding
**Component map:**  
Image → CLIP‑ViT (produces \(X_{img}\) ∈ ℝ^{576×1024} and \(v_{CLS}\)) ; Text → CLIP Text Encoder (produces \(t_{EOS}\)) ; \(v_{CLS} + t_{EOS}\) → QGR (2‑layer MLP + softmax) → weights \(\{\alpha_1,\alpha_2,\alpha_3\}\) ; Parallel branches: (1) Pooling(\(X_{img}\)) → \(X_{pool}\) (M tokens) ; (2) Resampler(\(X_{img}\)) → \(X_{resample}\) (M tokens) ; (3) Pruning(\(X_{img}\)) → \(X_{prune}\) (M tokens) ; Inference: select top‑2 weights, renormalize, weighted sum of corresponding outputs → \(T_{img}\) (M tokens) ; \(T_{img}\) + text tokens → LLM → response.

**Critical path:** The router’s weight computation is the central decision point. After the vision and text encoders produce \(v_{CLS}\) and \(t_{EOS}\), the QGR yields branch preferences. Branches compress in parallel; inference trims to two branches and fuses their outputs for the LLM.

**Design tradeoffs:**  
- Router overhead vs. flexibility: QGR adds ~3.57 GFLOPs (negligible vs. LLM savings) but introduces a trainable component prone to collapse.  
- Two‑branch selection vs. all‑three: Ablation shows fusing all three hurts performance due to noise; discarding the weakest branch improves results.  
- Heuristic pruning vs. learning: Pruning uses fixed rules (CLS attention + text similarity), avoiding extra parameters but potentially lacking adaptability.

**Failure signatures:**  
- Routing collapse: router weights become nearly one‑hot for one branch across all inputs → monitor weight entropy.  
- Aggressive compression (<36 tokens) yields sharp performance drops, indicating a hard limit on information preservation.  
- On VTCBench, if QMoP underperforms single‑branch baselines on specific dimensions (e.g., Local Details), it suggests misrouting for those data types.

**First 3 experiments:**  
1. **Router weight analysis:** Compute routing statistics on VTCBench; verify that pooling is favored for GU tasks, pruning for LD, resampler for SE/RC; check entropy for collapse.  
2. **Fusion strategy ablation:** Compare all‑three fusion (training), top‑1, top‑2 (default), and learned weighted sum at inference on VTCBench; expect top‑2 to maximize average performance.  
3. **Single‑branch VTCBench probing:** Evaluate each branch in isolation across all five dimensions; the gap between QMoP and the best single‑branch per dimension quantifies the router’s adaptive contribution and identifies potential misrouting.

## Open Questions the Paper Calls Out
1. **Adaptive sparsity:** Is the fixed top‑2 branch selection optimal, or could an adaptive mechanism (learning the number of active branches per sample) improve the trade‑off between information retention and noise suppression?  
2. **Advanced operators:** Could replacing the fundamental pooling, resampler, and pruning modules with more sophisticated, learnable compressors further boost robustness under aggressive token reduction (e.g., ≤64 tokens)?  
3. **Router input features:** Are the CLIP CLS and EOS tokens sufficient for context‑aware routing, or would richer cross‑modal interactions (e.g., from intermediate LLM layers or attention maps) lead to more accurate branch selection?  
4. **Benchmark coverage:** Does VTCBench’s five‑dimensional evaluation cover all critical visual information loss modes, or are there important failure modes (e.g., video, 3D structure, adversarial robustness) that remain unevaluated?

## Limitations
- Missing detailed specifications: QGR MLP hidden dimension, dynamic pruning threshold computation, Stage 1 fusion method, and training hyperparameters.
- Potential weaknesses: pooling may fail for non‑local relationships; resampler may discard necessary fine details; heuristic pruning scoring could remove subtle but important tokens.
- Evaluation scope confined to CLIP‑ViT‑L/14‑336 and LLaVA‑1.5 on static images; generalization to other vision encoders, LLMs, or video is unknown.
- Risk of routing collapse and performance degradation at very high compression ratios (<36 tokens).

## Confidence

- Pooling branch mechanism: **Medium** (aligned with prior work)
- Resampler branch mechanism: **Medium** (well‑established but may lose fine details)
- Pruning branch mechanism: **Low‑Medium** (heuristic rules may be brittle)
