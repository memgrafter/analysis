# Analysis of LLM Performance on AWS Bedrock: Receipt-item Categorisation Case Study

## Quick Facts
- arXiv ID: 2604.01615
- Source URL: https://arxiv.org/abs/2604.01615
- Reference count: 8
- Primary result: Claude 3.7 Sonnet achieved 90.2% accuracy with zero array-length mismatches under baseline prompting, and 93.3% strict accuracy with refined categories and rules, at the cost of doubled token usage.

## Executive Summary
This study evaluated four AWS Bedrock LLMs for receipt item classification to identify a production-ready, cost-effective solution. Using a curated dataset of 389 receipt items, models were compared on accuracy, stability, and token cost under zero-shot and refined prompting. Claude 3.7 Sonnet emerged as the best candidate, achieving the highest accuracy and perfect output schema adherence in baseline tests. Adding explicit disambiguation rules and refining categories further improved accuracy to 93.3% (strict) and 95.6% (lenient), though input token cost approximately doubled. Few-shot prompting offered no accuracy gain over rules-only variants. The recommended configuration is Claude 3.7 Sonnet with updated categories and zero-shot prompting.

## Method Summary
The research employed a two-phase empirical evaluation on a manually labelled dataset of 389 receipt items. Phase 1 compared four Bedrock models (Claude 3.7, Claude 4, Mixtral 8x7B, Mistral 7B) using a schema-first, zero-shot prompt that enforced a JSON array output matching the number of items. Phase 2 focused on the top performer (Claude 3.7 Sonnet) and iteratively refined the category set (from 26 to 27 categories) and prompts by adding either explicit disambiguation rules or few-shot examples. Metrics included accuracy, balanced accuracy, precision/recall/F1, runtime, token usage, and array-length mismatch rate.

## Key Results
- Claude 3.7 Sonnet achieved 90.2% overall accuracy and zero array-length mismatches in Phase 1 baseline testing.
- With refined categories and explicit disambiguation rules (zero-shot), strict accuracy increased to 93.3% and lenient to 95.6%, but input token cost doubled.
- Few-shot prompting did not improve accuracy over the rules-only variant despite higher token usage.

## Why This Works (Mechanism)
### Mechanism 1: Schema-Driven JSON Constraint
- **Claim:** A schema-first, JSON-constrained prompt design reduces hallucinations and parsing failures, leading to stable array-length outputs.
- **Mechanism:** By hard-coding the allowed category list and requiring a JSON array output of exactly N items, the model is forced into a structured response format that aligns with downstream parsing logic. This eliminates free-form text generation that could cause array-length mismatches.
- **Core assumption:** The model can reliably follow strict output formatting instructions when the schema is explicitly provided in the prompt.
- **Evidence anchors:** 
  - [abstract]: "...requiring a JSON array of category labels, each corresponding to the number of detected items, with no commentary or extra text."
  - [section 3.2.1]: "To ensure that the models remained tightly bound to valid outputs, each prompt explicitly included a predefined list of categories... This design choice also ensured alignment with the application’s reporting logic..."
- **Break condition:** The model generates malformed JSON or includes extra text/comments, causing downstream parsing errors.

### Mechanism 2: Category Boundary Disambiguation via Rules
- **Claim:** Refining category definitions and adding explicit disambiguation rules reduces inter-category confusion, improving accuracy especially for overlapping classes.
- **Mechanism:** Clearer boundaries (e.g., "dairy eggs fridge" for refrigerated/perishable vs. "pantry snacks" for shelf-stable) and context-based heuristics (e.g., vendor type cues) guide the model to resolve ambiguities that would otherwise cause misclassification between semantically similar categories.
- **Core assumption:** The model can internalise and apply rule-based boundaries provided in natural language within the prompt.
- **Evidence anchors:** 
  - [section 3.3.3]: "The classification rules covered the full category set and included boundaries such as: Distinguishing refrigerated or perishable items from shelf-stable goods..."
  - [section 4.2.1]: "Adding rules/heuristics delivers the strongest results, with overall precision/recall/F1 around 93%... suggesting that explicit disambiguation reduces overlap errors across adjacent categories."
- **Break condition:** Ambiguous items (e.g., "iced coffee") still show high misclassification rates even after rule addition, indicating rules are insufficient or inconsistently applied.

### Mechanism 3: Token-Cost-Accuracy Trade-off Analysis
- **Claim:** An input-token-aware prompt design balances accuracy gains against proportional cost increases, enabling cost-effective deployment.
- **Mechanism:** By measuring and reporting token usage per variant, the study quantifies the direct cost impact of prompt engineering choices (e.g., adding rules/examples increases input tokens). This allows selecting a configuration (e.g., Variant 3) that achieves near-optimal accuracy while accepting a known, measured cost overhead (roughly 2x baseline).
- **Core assumption:** Token counts reported by the API are accurate and directly correlate with monetary cost under Bedrock pricing.
- **Evidence anchors:** 
  - [section 4.2.3]: "Input tokens increased with the refinements, mainly due to the added rules and few-shot examples... the estimated cost per call rose with each step of prompt refinement... This reflects a clear trade-off: improvements in accuracy... come at the cost of higher token usage."
  - [Table 12]: Shows average input tokens increasing from 421 (V1) to 979 (V3), with cost/call rising from $0.00395 to $0.00874.
- **Break condition:** The cost-per-call increase outweighs business-case value, or token reporting is inconsistent across model families.

## Foundational Learning
- **Concept: Schema-Driven Prompting**
  - *Why needed here:* To enforce parseable, array-based outputs that integrate seamlessly with the application's downstream logic (e.g., mapping each item to a category). Without this, hallucinations or format deviations break the pipeline.
  - *Quick check question:* If a model returns `["snacks", "extra commentary"]` for a 2-item receipt, what went wrong in the prompt design?

- **Concept: Category Boundary Disambiguation via Prompt Rules**
  - *Why needed here:* Receipt items like "frozen dumplings" or "iced coffee" naturally span multiple plausible categories. Rules provide deterministic tie-breakers (e.g., temperature, packaging) to reduce inconsistent labeling.
  - *Quick check question:* How would you formulate a rule to distinguish `dairy eggs fridge` from `pantry snacks` for an item like "hummus"?

- **Concept: Token-Cost-Accuracy Trade-off Analysis**
  - *Why needed here:* Production systems must optimise for inference cost. This study shows that accuracy gains (Variant 3 over Variant 1) come at an ~118% cost increase; understanding this ratio is critical for budget planning.
  - *Quick check question:* If Variant 3 costs $0.00874/call and processes 250 receipts/day, what is the daily inference cost vs. the baseline?

## Architecture Onboarding
Component map:
Receipt Ingestion -> Prompt Template Selector -> Bedrock Invoker -> JSON Output Validator -> Ground Truth Comparator -> Metrics Aggregator

Critical path: Prompt Template Selection → Bedrock Invocation → JSON Validation → Ground Truth Comparison → Metrics Calculation.

Design tradeoffs:
- Accuracy vs. Cost: Variant 3 (highest accuracy) doubles input tokens vs. V1.
- Schema Rigidity vs. Flexibility: Strict JSON array requirement ensures parseability but may force incorrect choices on ambiguous items (handled via lenient evaluation).
- Model Family Differences: Claude provides token counts and perfect array length; open-weight models (Mixtral/Mistral) are faster but less stable and lack token metrics.

Failure signatures:
- Array-length mismatch (open-weight models, ~1.9–9.3% rate).
- Category-level hallucinations (e.g., `"category": "nonexistent_label"`).
- High tail latency (>3s for Claude, >15s for Mistral 7B).
- Cost overrun due to prompt bloat (Variant 4: 1212 avg input tokens vs. 421).

First 3 experiments:
1. Baseline Model Comparison (Phase 1): Run all 4 models with identical zero-shot, schema-first prompts to identify Claude 3.7 Sonnet as the best initial candidate.
2. Category Set Refinement Test (Phase 2, V1 vs. V2): Isolate impact of updated categories (e.g., splitting `Pantry & Snacks` → `Fruits & Vegetables`, `Meat & Seafood & Deli`, etc.) on accuracy without added rules.
3. Rules vs. Few-Shot Comparison (Phase 2, V3 vs. V4): Test whether explicit disambiguation rules (V3) outperform few-shot examples (V4) for accuracy gain per additional token.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How does the receipt categorisation performance generalise to globally diverse receipts beyond the current Australian, university-sourced dataset?
- **Basis in paper:** [inferred] The dataset lacks diversity in geography, vendors, and image formats (only JPG/PNG, no PDFs), limiting external validity.
- **Why unresolved:** The study's single-source dataset may not represent real-world production scenarios where receipts vary widely in origin and quality.
- **What evidence would resolve it:** Evaluate the optimal configuration on a multi-national dataset with varied vendors, image conditions, and formats, measuring accuracy and stability.

### Open Question 2
- **Question:** What is the impact of OCR errors from receipt text extraction on LLM categorisation accuracy, and how can prompts be robustified?
- **Basis in paper:** [inferred] The study assumes perfect AWS Textract output and does not test robustness to extraction errors.
- **Why unresolved:** Real-world OCR often introduces noise, which could degrade model performance but is unexamined.
- **What evidence would resolve it:** Introduce controlled noise (e.g., character corruption) into receipt text and measure accuracy changes across models and prompts.

### Open Question 3
- **Question:** Can the inherent ambiguity in ~5% of receipt items (e.g., "iced coffee") be resolved without high token cost, via taxonomy refinement or context-aware prompting?
- **Basis in paper:** [inferred] Lenient evaluation acknowledges ~20 ambiguous items; strict accuracy penalises them, and current solution uses lenient scoring.
- **Why unresolved:** Production requires definitive categories; the trade-off between accuracy and cost for disambiguating these items is unexplored.
- **What evidence would resolve it:** Iteratively adjust category boundaries or incorporate vendor/context clues in prompts, testing on the ambiguous subset for strict accuracy gains versus token cost.

## Limitations
- Small dataset (n=389) limits generalizability.
- Missing prompt templates and ground-truth labels hinder replication.
- Token counts for open-weight models are estimated; no statistical testing of differences.
