# Near-Miss: Latent Policy Failure Detection in Agentic Workflows

## Quick Facts
- **arXiv ID**: 2603.29665  
- **Source URL**: https://arxiv.org/abs/2603.29665  
- **Reference count**: 19  
- **Primary result**: A trajectory-level metric uncovers latent policy failures (near-misses) in 8–17% of successful agent trajectories that involve state-altering tool calls across state-of-the-art LLMs.

## Executive Summary
This paper addresses a critical blind spot in evaluating LLM-based agents: standard benchmarks compare only the final system state to ground truth, missing cases where agents bypass required policy checks but still succeed due to favorable circumstances. The authors introduce a method to detect such "near-misses" by analyzing whether mutating tool calls were preceded by sufficient information-gathering steps, as mandated by policy. Building on the ToolGuard framework—which encodes policies as executable guard code—they simulate guards to extract required read-only tool calls and search the agent's history for evidence of those actions. Evaluation on the τ²-verified Airlines benchmark reveals latent failures in a significant portion of otherwise successful trajectories, highlighting systemic risk in outcome-only evaluation.

## Method Summary
The method operates offline on logged agent trajectories. For each mutating tool call (e.g., `cancel_reservation`), an associated guard function (generated via ToolGuard from natural-language policies) is simulated to identify the set of read-only tools necessary to satisfy policy conditions (e.g., `get_reservation_details`). The trajectory history prior to the mutating call is then searched for any invocation of these required read-only tools (or their semantic equivalents). If none are found, the mutating call is flagged as a near-miss. Two search strategies are evaluated: an LLM-based reasoning approach and a code-generation-based systematic scan; the latter achieves higher accuracy. Near-miss rates are computed among trajectories containing mutating calls that ultimately match the expected final state.

## Key Results
- Near-misses occur in 8–17% of trajectories with mutating tool calls across six state-of-the-art LLMs (Claude-Sonnet4, GPT5-chat, GPT5.1-Codex, o3, Qwen2.5-72b, and Qwen3-235b).
- The phenomenon is widespread: even models with low total failure rates exhibit substantial latent failure rates, indicating that outcome-based benchmarks overlook prevalent policy bypasses.
- The code-generation-based history search (using Claude-Sonnet4) achieves perfect precision and recall on a manually annotated subset, validating its feasibility.

## Why This Works (Mechanism)

### Mechanism 1
Guard code generation translates natural-language policies into executable functions that explicitly call read-only tools to verify conditions. The accuracy of required information extraction depends entirely on the guard code’s correctness and completeness.

### Mechanism 2
History search identifies whether the required read-only tools (or equivalent alternatives) were invoked before the mutating call. The code-generation approach matches tool calls by schema and semantic equivalence, minimizing false positives/negatives when implemented with a capable LLM.

### Mechanism 3
Near-misses are defined as mutating calls lacking prior required information-gathering *within otherwise successful trajectories*. This isolates agent behaviors that rely on luck rather than compliance, exposing risks that would manifest under adversarial conditions.

## Foundational Learning
- **Mutating vs. Read-Only Tools**: Mutating tools (e.g., `cancel_reservation`) change system state; read-only tools (e.g., `get_reservation_details`) only query. Policies mandate read-only checks before mutation.  
  *Quick check*: In Airlines, what read-only tool must precede `update_reservation_flights` to satisfy a policy requiring flight availability verification?
- **Policy Representation as Guard Code**: Policies become Python functions that wrap mutating tools and invoke read-only tools to validate conditions. Guard simulation reveals which data accesses are necessary.  
  *Quick check*: How would a guard for “cancellations within 24 hours” use `get_reservation_details()` in its code?
- **Near-Miss vs. Explicit Violation**: Near-misses reach correct final state but skip required checks; explicit violations produce incorrect final state. Near-misses reveal latent risk masked by benign circumstances.  
  *Quick check*: Provide an Airlines scenario where a near-miss occurs during a booking that ultimately succeeds.

## Architecture Onboarding
Guard Code Repository -> Trajectory Parser -> Guard Simulator -> History Search Module -> Near-Miss Aggregator -> Evaluation Harness.
- **Critical path**: For each mutating tool call in a trajectory: load guard; simulate to get required read-only tools; search prior history for any required tool; flag if none found; aggregate near-miss rate.
- **Design tradeoffs**: Code-generated search offers high accuracy and low runtime but depends on guard code quality and may be brittle to schema changes. LLM-based search is flexible but introduces hallucination risk and latency.
- **Failure signatures**: Guard code miscompilation (missing required checks); search false negatives (missed equivalent tool calls); search false positives (accepting irrelevant calls); trajectory recording failures; tool set mismatches.
- **First 3 experiments**: (1) Replicate near-miss rates across six agents on Airlines; (2) Validate search accuracy against manual annotation of mutating calls; (3) Inject deliberate defects into guard code and measure impact on near-miss detection.

## Open Questions the Paper Calls Out
- To what extent do latent policy failures occur across different domains and larger-scale settings, beyond the τ²-verified Airlines benchmark?
- Can the latent failure detection metric be extended to cover non-mutating policy types, such as information disclosure restrictions or confirmation requirements?
- How can the quality and robustness of ToolGuard-generated guard code be improved to reduce errors in latent failure detection?
- Can latent failure detection be deployed as a runtime enforcement mechanism with acceptable performance overhead?

## Limitations
- The method depends on the quality of LLM-generated guard code; errors or omissions directly compromise detection accuracy.
- The evaluation is confined to a single domain (Airlines); generalizability to other agentic workflows remains unproven.
- The approach only detects missing pre-mutation data accesses, not incorrect use of retrieved data or violations of non-mutating policies.

## Confidence
- **Guard code accuracy**: Medium – validated via ToolGuard’s pipeline but without full manual audit of all functions.
- **History search correctness** (Claude-Sonnet4 code): High – perfect precision/recall on annotation; Medium for other models.
- **Near-misses as latent failures**: Medium – strong evidence in Airlines but unverified under adversarial conditions or in other domains.

## Next Checks
1. **Exact replication**: Run the full pipeline on all six agents; confirm near-miss rates fall within the reported 8–17% range for trajectories with mutating calls.
2. **End-to-end accuracy study**: Manually annotate a stratified sample of ~200 mutating tool calls and compute overall precision/recall of the detection method.
3. **Robustness to guard errors**: Introduce controlled defects (e.g., remove a required read-only tool call) into guards and measure resulting change in near-miss rates.
