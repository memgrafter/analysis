# Not All Invariants Are Equal: Curating Training Data to Accelerate Program Verification with SLMs

## Quick Facts
- **arXiv ID:** 2603.15510
- **Source URL:** https://arxiv.org/abs/2603.15510
- **Reference count:** 40
- **Primary result:** WONDA-curated data enables a 4B-parameter SLM to nearly double its base model's correctness (44.4% vs 22.8%) and speedup rates (24.7% vs 11.1%), matching the performance of a 120B model.

## Executive Summary
Loop invariants are essential for deductive program verification, but their synthesis remains a major bottleneck. While large language models (LLMs) can generate invariants, they often produce invalid or inefficient ones, and fine-tuning demands high-quality training data. This paper introduces WONDA, a data curation pipeline that transforms raw verifier-generated invariants into a compact, correct, and useful training set. WONDA first normalizes invariants using AST-based rewriting to remove syntactic noise, then employs an LLM (Kimi K2) to simplify them, and finally filters candidates via formal verification to ensure correctness and utility. Fine-tuning small language models (SLMs) on the resulting dataset (V2) yields substantial gains on the challenging InvBench benchmarks: a 4B-parameter SLM doubles its base model’s correctness (44.4% vs 22.8%) and speedup rate (24.7% vs 11.1%), and matches a 120B model. The results demonstrate that high-quality data, not just model scale, is critical for practical automated invariant synthesis.

## Method Summary
WONDA’s curation pipeline consists of three stages. First, raw invariants from the UAutomizer verifier are normalized via AST rewriting, applying rules that eliminate tautologies, redundant parentheses, and excessive casts, producing a canonical form. Second, for invariants that exceed a length threshold η (i.e., are “verbose”), an LLM (Kimi K2 Thinking) generates multiple candidate simplifications guided by a prompt that encourages compactness and semantic clarity. Third, each candidate is verified in parallel using the same verifier: query V1 checks correctness (the invariant implies the verification condition), and V2 checks sufficiency and speedup (the invariant reduces verification time). Candidates receiving a quality grade Q≥2 (where Q combines V1, V2, and a speedup condition) are retained. The final dataset V2 contains approximately 7,283 (program, invariant) pairs.

For training, Qwen3 SLMs (0.6B, 4B, 8B) are fine-tuned on V2 using LoRA for two epochs with a cosine learning rate schedule. During evaluation, models generate invariants in a non-thinking mode; each output is graded via the same parallel verification procedure. Performance is measured by validity (Rvalid), correctness (Rcorrect), speedup rate (Rspeedup), average speedup (¯S>1), and Virtual Best Performance (VBP) on the InvBench Hard split (123 instances).

## Key Results
- The 4B-parameter fine-tuned model achieves 44.4% correctness and 24.7% speedup on InvBench Hard, nearly doubling its base model’s 22.8% correctness and 11.1% speedup.
- The same 4B model matches the performance of GPT-OSS-120B and approaches GPT-5.2, despite having <1% of its parameters.
- Virtual Best Performance improves by up to 14.2%, reducing verification time by 12–20 seconds compared to the base model.

## Why This Works (Mechanism)
### Mechanism 1: AST Normalization Removes Syntactic Noise
- **Claim:** AST-based normalization eliminates verifier-specific syntactic artifacts (tautologies, redundant parentheses, excessive casts) from raw invariants, making them more learnable by SLMs.
- **Mechanism:** The `NORMALIZE` function applies bottom-up rewrite rules (Table 2) that are semantic-preserving, converting invariants to a canonical, minimal form. This reduces data sparsity and prevents models from learning irrelevant verifier idiosyncrasies.
- **Core assumption:** SLMs trained on normalized invariants will focus on logical structure rather than syntactic clutter, improving generalization.
- **Evidence anchors:** 
  - [abstract]: "WONDA first normalizes invariants using AST-based rewriting to remove syntactic noise"
  - [section 4.1]: Describes the rewrite rules and Proposition 4.1 (soundness).
  - [corpus]: Neighboring papers do not focus on normalization; e.g., "Ranking LLM-Generated Loop Invariants" uses ranking instead. Corpus evidence is weak for this mechanism.
- **Break condition:** If normalization over-aggressively strips semantically meaningful information (e.g., type casts that encode overflow semantics), the resulting invariants may become unsound or lose necessary constraints, leading to incorrect model predictions.

### Mechanism 2: LLM Simplification with Verification Yields High-Quality Invariants
- **Claim:** The LLM-driven simplification step, combined with formal verification filtering, produces invariants that are compact, correct, sufficient, and provide verification speedup.
- **Mechanism:** For verbose normalized invariants, an LLM (prompted with transformation goals) generates candidate simplifications. Each candidate is graded via parallel verification queries (Algorithm 1). Only invariants with grade ≥2 (correct, sufficient, and speedup) are retained for training.
- **Core assumption:** LLMs can perform semantic abstraction beyond syntactic rewriting, and the verification oracle ensures simplified invariants remain valid and useful.
- **Evidence anchors:**
  - [abstract]: "then employs an LLM to simplify them into compact, semantically clear forms, with formal verification ensuring correctness and utility."
  - [section 4.2]: Details simplification procedure, quality grading, and Algorithm 2.
  - [corpus]: Papers like "Quokka" and "Enhancing Automated Loop Invariant Generation" use LLMs for invariant generation but lack the specific combination of LLM simplification with verification-based quality filtering. Corpus evidence is indirect.
- **Break condition:** If the LLM over-simplifies (excessively weakening invariants) or introduces errors that evade verification due to incomplete solver results (UNKNOWN), the training data may contain invalid or inefficient invariants, degrading model performance.

### Mechanism 3: High-Quality Data Enables Small Models to Rival Large LLMs
- **Claim:** Fine-tuning SLMs on WONDA-curated data substantially improves their verification performance, allowing a 4B model to match GPT-OSS-120B and approach GPT-5.2.
- **Mechanism:** The curated dataset (V2) contains invariants that are correct, sufficient, and compact. This teaches the model to generate invariants that are practically effective for verification, not just syntactically plausible. Compactness aids learnability and generalization.
- **Core assumption:** Data quality (correctness, utility, compactness) is the key bottleneck; given high-quality data, SLMs can learn invariant synthesis effectively without requiring massive scale.
- **Evidence anchors:**
  - [abstract]: "Fine-tuning small language models (SLMs) on this curated data yields substantial improvements... The fine-tuned 4B model matches GPT-OSS-120B and approaches GPT-5.2."
  - [section 6 (Results)]: Table 3 shows Qwen3-4B-V2 achieving 44.4% correctness and 24.7% speedup, comparable to the 120B model.
  - [corpus]: Corpus papers demonstrate that LLM-based invariant generation often requires large models for decent performance. WONDA challenges this by showing curated data enables small models to compete, suggesting data quality trumps scale.
- **Break condition:** If the curated data lacks diversity (e.g., only covers linear invariants from UAutomizer), the fine-tuned model may fail to generalize to harder or out-of-distribution programs, limiting scalability beyond the benchmark domain.

## Architecture Onboarding
### Component map
UAutomizer -> Normalizer -> LLM Simplifier -> Verification Filter -> Training Data -> SLM -> Evaluation Harness

### Critical path
The data curation pipeline (UAutomizer → Normalizer → LLM Simplifier → Verification Filter) is the critical path. Its output (high-quality invariants) directly determines the effectiveness of the fine-tuned SLM. Any weakness here propagates to the final model.

### Design tradeoffs
- **Normalization vs. Semantic Preservation:** Stripping casts improves readability but risks losing bit-precise semantics; mitigated by verifying final invariants.
- **LLM Simplification Cost vs. Abstraction Power:** Using a large LLM (Kimi K2) is expensive but yields better abstractions; could substitute a smaller LLM but may reduce simplification quality.
- **Verification Grading Overhead:** Running full verification for every candidate is computationally heavy; authors mitigate by only grading verbose invariants and using parallel execution.
- **Dataset Size vs. Quality:** Prioritizing quality yields only ~7k samples (small for ML), but fine-tuning works well; adding more low-quality samples might harm performance.

### Failure signatures
- **Normalization over-simplification:** Invariants become too weak (e.g., `true`) or lose necessary constraints; would see low correctness/speedup rates after fine-tuning.
- **LLM over-abstraction:** Simplified invariants are incorrect but pass verification due to incomplete solver results (UNKNOWN); would see high validation but low actual speedup.
- **Dataset lack of diversity:** Training invariants cover limited patterns (e.g., only linear invariants); model fails on non-linear or complex loops in evaluation.
- **Evaluation mismatch:** Curated data from UAutomizer may bias model toward that verifier’s style; when evaluated with same verifier, performance drops if patterns differ.

### First 3 experiments
- **Ablation study (Table 4):** Train on raw (V0), normalized (V1), and simplified+verified (V2) data. V2 yields the largest improvements in correctness and speedup, demonstrating the value of simplification with verification.
- **Scaling comparison (Table 3):** Fine-tune SLMs of various sizes (0.6B, 4B, 8B) on V2 and compare against GPT-OSS-120B and GPT-5.2. The 4B-V2 matches the 120B model, showing small models can rival large ones with curated data.
- **Quality distribution analysis (Figure 6):** Examine the V2 dataset’s grade distribution. A large fraction are Grade 3 (speedup), confirming that curated data contains practically useful invariants, not just correct ones.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How does WONDA's data curation perform when using invariant generators other than UAutomizer as the initial source?
- **Basis in paper:** [explicit] The conclusion states: "Moving forward, we plan to evaluate WONDA with additional backend verifiers, besides UAutomizer."
- **Why unresolved:** The pipeline's normalization and simplification steps may interact differently with invariants produced by different verification engines (e.g., Eldarica, different interpolation strategies), potentially affecting the quality and diversity of the final training set.
- **What evidence would resolve it:** Running the full WONDA pipeline on invariants from at least two other state-of-the-art verifiers, comparing the resulting fine-tuned model performance on the same evaluation benchmarks. This would test the portability and robustness of the curation approach.

### Open Question 2
- **Question:** Does the observed performance gain from WONDA-curated data scale to non-loop invariants (e.g., class invariants, function contracts) or to other program analysis tasks beyond verification?
- **Basis in paper:** [inferred] The methodology and experiments are exclusively focused on loop invariants for safety verification. The definition of a "property" in §3.2 is tied to loop locations, and the transformation goals in §4.2 (e.g., range generalization) are tailored to loop structures.
- **Why unresolved:** The techniques (AST normalization, semantic simplification for compactness) may not directly apply or may need significant adaptation for other invariant forms or analysis tasks. The "pedagogical value" and "overfitting trap" problems might manifest differently.
- **What evidence would resolve it:** Applying the WONDA pipeline (with appropriate modifications) to a dataset of, for example, class invariants (as in ClassInvGen) or pre/post-condition specifications, then evaluating the resulting model's performance on the corresponding task.

### Open Question 3
- **Question:** What is the minimum model capacity (parameter count) required to effectively learn from WONDA's curated dataset, and is there a "sweet spot" where the quality improvement is maximal?
- **Basis in paper:** [inferred] The ablation study shows that the smallest model (0.6B) gains in speedup rate and VBP but not in a statistically significant correctness improvement compared to its base model, while the 4B and 8B models show larger jumps in correctness. This suggests a capacity threshold below which the model cannot fully leverage the improved data format.
- **Why unresolved:** The paper evaluates only three specific model scales from the same family. The relationship between model size, data quality, and task performance is not systematically explored. It is unclear if a 1B-2B model would show intermediate benefits or if the 4B model is the true minimum effective scale for this curated data distribution.
- **What evidence would resolve it:** Fine-tuning a larger, more diverse set of base models (e.g., 1B, 2B, 3B variants from different architectures) on the V2 dataset and plotting performance metrics (correctness, speedup) against parameter count to identify the scaling curve and any capacity breakpoints.

### Open Question 4
- **Question:** Can the specification of "usefulness" (grade ≥ 2) in WONDA's filtering step be further refined to produce even more effective training signals, for instance by incorporating a measure of invariant complexity or diversity?
- **Basis in paper:** [explicit] The Quality Grade Q (§4.2) is defined with a binary cutoff at grade 2 (correct and sufficient, with or without speedup). The paper notes that grade 3 invariants provide speedup, but grade 2 invariants are also retained. The rationale is to include a wider set of correct invariants.
- **Why unresolved:** The paper does not analyze the training impact of mixing grade 2 and grade 3 samples. It is possible that a curriculum or filtering that prioritizes grade 3 samples (or a more nuanced grade) could lead to faster convergence or better final performance. Furthermore, the current grade depends on a single baseline time `t_b`; it may not capture robustness across multiple runs or program instances.
- **What evidence would resolve it:** Conducting an ablation where training datasets are constructed using only grade 3 invariants, only grade 2 invariants, and a mixture, then comparing the fine-tuned models' performance. Additionally, exploring other quality metrics (e.g., invariant minimality, solver runtime reduction percentile) as filters could yield insights.

### Open Question 5
- **Question:** To what extent do the LLM-driven simplifications in WONDA introduce a bias toward specific invariant patterns (e.g., linear arithmetic, factored forms) that might limit the model's ability to generate correct invariants for programs requiring more complex (e.g., non-linear, disjunctive) properties?
- **Basis in paper:** [inferred] The simplification guidelines (§4.2) explicitly prefer "LINEAR arithmetic expressions" and "mathematical relationships over case enumeration." The examples in the paper (e.g., `5x + 3y == 300`) are linear. The raw verifier outputs often contain complex disjunctions and non-linear terms.
- **Why unresolved:** The curated dataset V2 is a filtered subset where the LLM's simplifications were verified to be correct and sufficient. However, this creates a dataset distribution skewed toward simpler, more "beautiful" invariants. For programs where the only correct invariant is inherently complex (e.g., a specific disjunctive normal form), a model trained primarily on simplified invariants might fail to generate a valid candidate, even though such a complex invariant exists and could be verified.
- **What evidence would resolve it:** Analyzing the subset of evaluation instances where the fine-tuned model still fails. Correlating failure with the known complexity of the ground truth invariant (if available from other tools) or with the complexity of the program's loop structure. A controlled user study with the LLM simplification step, where the prompt is varied to encourage or discourage simplification for a held-out set of programs, could measure the impact on model diversity and coverage.

## Limitations
- Exact dataset curation parameters (split indices, verbose threshold η) are unreported, hindering full replication.
- Dependence on proprietary Kimi K2 for simplification; substitution may degrade data quality.
- Potential dataset bias toward UAutomizer’s invariant style, risking poor generalization to other verifiers or non-linear loops.

## Confidence
- AST normalization (**Medium**): Sound by design (Prop 4.1) but corpus evidence weak; risk of over-simplification (e.g., losing overflow semantics).
- LLM simplification with verification (**Medium**): Verification filter ensures correctness/utility, but relies on a specific LLM (Kimi K2) and may over-abstract.
- Data enabling small models (**High**): Strong empirical results on InvBench (Table 3, Table 4), though bias from UAutomizer-sourced data remains a concern.

## Next Checks
1. Recreate V2 using an open-source LLM (e.g., Llama-3-70B) instead of Kimi K2, then fine-tune and compare performance.
