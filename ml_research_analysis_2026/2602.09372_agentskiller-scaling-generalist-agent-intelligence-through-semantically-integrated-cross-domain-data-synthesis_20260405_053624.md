# AgentSkiller: Scaling Generalist Agent Intelligence through Semantically Integrated Cross-Domain Data Synthesis

## Quick Facts
- **arXiv ID**: 2602.09372
- **Source URL**: https://arxiv.org/abs/2602.09372
- **Reference count**: 28
- **Primary result**: AgentSkiller-14B achieves state-of-the-art function calling (79.1% on τ2-bench, 78.0% on ACEBench-Agent) with far fewer parameters than many proprietary baselines, demonstrating that high-quality synthetic data can bridge the open-source/proprietary gap.

## Executive Summary
AgentSkiller tackles the critical bottleneck of scarce, high-quality, long-horizon training data for generalist LLM agents. Existing data sources—real API logs or simple scripted interactions—are limited by privacy concerns and lack of diversity. The proposed solution is a fully automated framework that synthesizes multi-turn interaction data across semantically linked domains. It employs a DAG-based architecture with explicit state transitions to ensure determinism and a Person-Centric Entity Graph to maintain relational consistency. Cross-domain fusion of services creates complex, realistic tasks. Approximately 11K interaction samples were generated, and models fine-tuned on this dataset show significant improvements in function-calling performance, particularly for larger models, with cross-domain data notably enhancing robustness on challenging benchmarks.

## Method Summary
The framework consists of a five-phase automated pipeline: (1) **Domain Ontology** expands seed domains, extracts entities, and constructs Person-Centric Entity Graphs; (2) **Service Specification** generates standardized Service Blueprints and tool interfaces for MCP servers; (3) **Implementation** synthesizes constraint-satisfying databases and domain policies, then implements MCP servers; (4) **Cross-Domain Fusion** links semantically related domains by merging databases and harmonizing policies; (5) **Task Instantiation** enumerates trajectories, grounds instances, synthesizes user queries, and validates execution via a dual-path mechanism. A dual-LLM setup (Textual LLM for semantic reasoning, Coding LLM for syntax) drives the pipeline. The final dataset is used for supervised fine-tuning (SFT) of open-source models (e.g., Qwen3) via the `verl` framework to train generalist agents.

## Key Results
- AgentSkiller-14B achieves 79.1% on τ2-bench, 78.0% on ACEBench-Agent, and 67.2% on τ-bench, outperforming many larger baselines.
- Cross-domain data fusion yields significant robustness gains on complex benchmarks, validating the semantic integration approach.
- The pipeline successfully synthesizes ~11K executable, multi-turn trajectories across multiple domains.

## Why This Works (Mechanism)

### Mechanism 1: Semantic Scaffolding via Person-Centric Entity Graphs
The Person-Centric Entity Graph models human actors as central nodes connected to peripheral resources (e.g., Patient–Doctor–Ticket), creating a hub-and-spoke topology that mirrors real-world workflows. This enforces relational consistency, preventing semantically invalid associations (e.g., a Ticket linked to a non-person entity). It assumes human actors are primary agents of state changes. Evidence: Sections 3.3–3.4 define the Domain-Invariant Granularity and Person-Centric constraints; Section 3.12.1 describes shared state carriers; the abstract mentions graph construction. Break condition: If domain workflows are system-centric rather than person-centric, the graph fails to capture essential dynamics.

### Mechanism 2: DAG-Based Deterministic State Machine
The directed acyclic graph (DAG) architecture treats each tool call as a node with dependency edges, guaranteeing determinism and recoverability. Constraints require a single source (authorization), full reachability, and acyclicity. This ensures reproducible agent evaluation and reliable simulation. Evidence: Section 3.1.1 introduces the DAG for determinism; Section 3.10 formalizes topological constraints; Section 3.9.2 uses test-driven self-correction relying on determinism. Break condition: Non-deterministic policies or APIs (e.g., random failures, time-dependence) violate DAG guarantees.

### Mechanism 3: Cross-Domain Semantic Fusion
By identifying domain pairs sharing core entities (e.g., Patient in Healthcare and Insurance), the system fuses their databases and policies into unified contexts. This forces agents to maintain state across service boundaries, simulating real-world complexity and promoting generalization. Evidence: Section 3.11 details trajectory fusion and feasibility-aware logic; Section 4.1 shows dense interlinking; Section 5.2 demonstrates performance gains from cross-domain data. Break condition: Semantically unrelated domain pairs produce incoherent tasks that do not test cross-domain reasoning.

### Mechanism 4: Execution-Based Validation
Rather than relying on static analysis, the system executes each trajectory against the synthesized database and policies, filtering out theoretically valid but practically invalid instances. A dual-path mechanism (slow path for new templates, fast path for cached) makes this scalable. Evidence: Section 3.16 describes task filtering as a dynamic verification layer; Section 4.3 reports a 31.5% exclusion rate; Section 3.19 covers multi-dimensional evaluation including environment diff verification. Break condition: Discrepancies between the execution environment and intended runtime (e.g., database engine differences) cause false negatives.

## Foundational Learning

**Concept: POMDP (Partially Observable Markov Decision Process)**
- **Why needed**: The paper formalizes agent interaction as a POMDP, where environment state is partially observable through tool outputs and user messages. This highlights the importance of deterministic state transitions and informative observations.
- **Quick check**: Given a POMDP tuple (S, A, O, T, O, R, γ) from Section 2, what specific aspect makes the problem "partially observable" in the AgentSkiller setting? *(Answer: The agent does not directly observe the full environment state S; it only receives observations O from actions.)*

**Concept: Directed Acyclic Graph (DAG) for Workflow Modeling**
- **Why needed**: The entire architecture uses DAGs to represent tool dependencies and execution orders. Violations (cycles, disconnected nodes) break pipeline guarantees.
- **Quick check**: Why must the tool graph have exactly one node with in-degree 0, and what happens if this constraint is violated? *(Answer: It ensures a single authorization source; violation creates multiple entry points, breaking determinism and recoverability.)*

**Concept: Constraint Satisfaction for Database Generation**
- **Why needed**: Database synthesis uses constraint identification and index-based sampling rather than random generation, ensuring semantic plausibility (e.g., a math teacher teaches a math course).
- **Quick check**: What's the difference between naive "sample-and-filter" rejection sampling and the proposed "Active Construction Scripts with Index-Based Sampling"? *(Answer: The latter proactively enforces constraints during generation using pre-built indexes, avoiding expensive post-hoc filtering.)*

## Architecture Onboarding

**Component map**:
Domain Expansion → Entity Extraction → Person-Centric Graph Construction → Blueprint Generation → Tool Interface Standardization → Database Synthesis → Policy Generation → MCP Server Implementation → (Optional) Trajectory Fusion → Database Aggregation → Policy Harmonization → Trajectory Enrichment → Instance Grounding → Query Synthesis → Execution Validation → Final Curation

**Critical path**: For single-domain: Steps 1–3 → 4–5 → 6–8 → 9 → 14–17. For cross-domain: Insert Steps 10–13 after Step 9. Execution validation (Step 16) is mandatory before query synthesis.

**Design tradeoffs**:
- Dual-LLM architecture (Textual + Coding) increases cost but separates semantic reasoning from syntactic precision.
- Execution-based validation is computationally expensive but ensures executability; dual-path caching mitigates this.
- Cross-domain fusion dramatically increases task complexity but introduces policy harmonization challenges.

**Failure signatures**:
- Step 2: Low entity counts due to overly strict Domain-Invariant Granularity.
- Step 3: Person-Centric graph fails to find actor→resource relationships.
- Step 8: Policy hallucination referencing non-existent attributes.
- Step 9: MCP server unit test failures.
- Step 13: Unresolvable policy conflicts after fusion.
- Step 16: High exclusion rate (>30%) indicating synthesis quality issues.

**First 3 experiments**:
1. Build a single-domain pipeline (e.g., Library) and verify end-to-end: entity extraction → blueprint → database → single tool call execution.
2. Add tool graph generation and enforce topological constraints (single source, full reachability, acyclicity); validate with unit tests.
3. Implement task filtering on 10 sample trajectories; measure pass rate and adjust prompts/tuning until >80% pass.

## Open Questions the Paper Calls Out

**Open Question 1**: To what extent can models trained on AgentSkiller's synthesized data generalize to completely unseen domains not in the seed expansion or cross-domain fusion?
- **Basis**: Evaluation on benchmarks (τ-bench, τ2-bench, ACEBench) may share domain similarities; no explicit held-out domain tests.
- **Why unresolved**: Without controlled experiments excluding specific domains, it is unclear whether models learn general tool-use competencies or memorize domain-specific patterns.
- **Needed evidence**: Train on a subset of domains (e.g., excluding Telecom/Retail) and evaluate on those held-out domains; analyze error breakdowns.

**Open Question 2**: Can the cross-domain fusion mechanism scale beyond pairwise combinations, and what challenges arise when merging three or more domains?
- **Basis**: Section 3.11 describes fusing a "domain pair"; the chord diagram shows pairwise connections.
- **Why unresolved**: k>2 fusion introduces combinatorial explosion in combinations and harder policy/schema conflicts than pairwise issues; current LLM-mediated harmonization may not guarantee global consistency.
- **Needed evidence**: Prototype triple-domain fusion (e.g., Healthcare + Insurance + Payment); report trajectory success rates, policy coherence, and overhead; identify failure modes.

**Open Question 3**: Why does model accuracy decline with longer tool call sequences in Retail and Airline but not in Telecom, and how can synthesis produce more robust long-horizon tasks?
- **Basis**: Figure 8 shows negative correlations for Retail (ρ = -0.688) and Airline (ρ = -0.566) but positive for Telecom (ρ = 0.300); authors speculate Telecom workflows are deterministic.
- **Why unresolved**: The degradation cause (tool-graph depth, data sparsity, domain complexity) is unanalyzed; without pinpointing, refinement is empirical.
- **Needed evidence**: Analyze synthesized tool graphs and policies across domains; correlate properties with performance decay; adjust synthesis (e.g., more intermediate validations) and reassess.

**Open Question 4**: How does the distribution of synthetic interactions compare to real human-agent conversations, and does exclusive synthetic training cause behavioral gaps in real-world deployments?
- **Basis**: The paper uses a Persona-based Simulator but never compares with real human logs; evaluation is on synthetic benchmarks.
- **Why unresolved**: Synthetic data may miss human communication nuances (colloquialisms, implicit intents, error recovery); agents might falter with real users due to distribution shift.
- **Needed evidence**: Collect a human-agent dataset in similar domains; compare linguistic features and interaction patterns; conduct a user study comparing synthetic-vs-real-trained agents on task success and satisfaction.

## Limitations
- **Prompt/LLM dependency**: Exact prompts and model versions for semantic synthesis steps are unreleased; quality is sensitive to prompt engineering.
- **Scalability cost**: No reporting of token usage, wall-clock time, or API costs for generating 11K samples; dual-LLM + execution loops may be prohibitive.
- **Generalization boundary**: Claims of cross-domain robustness are limited to the 5 seed domains (Healthcare, Finance, etc.); performance on truly novel domains (e.g., Manufacturing) is unverified.

## Confidence
- **High**: Cross-domain fusion improves robustness on reported benchmarks (τ2-bench, ACEBench-Agent). Evidence: Section 5.2 ablation studies.
- **Medium**: Person-Centric Entity Graphs enforce semantic consistency *within* synthesized domains. Evidence: Logical design in Sections 3.3–3.4, but real-world entity complexity untested.
- **Low**: DAG-based determinism guarantees hold under non-synthetic, noisy real-world policies. Break condition in Section 3.10 is theoretical; no stress-testing with stochastic APIs.

## Next Checks
1. **Prompt ablation**: Re-run single-domain synthesis with open-source LLMs (e.g., Llama-3.1-70B) using only high-level prompt descriptions from the paper; measure drop in executable trajectory yield vs. reported 68.5% pass rate.
2. **Resource audit**: Instrument the pipeline to log total input/output tokens, API costs, and time per trajectory; estimate replication budget for ~11K samples.
3. **Cross-domain stress test**: Fuse Healthcare with a semantically distant domain (e.g., Hospitality); measure trajectory failure rate in execution validation to quantify the break condition for semantically weak fusions.
