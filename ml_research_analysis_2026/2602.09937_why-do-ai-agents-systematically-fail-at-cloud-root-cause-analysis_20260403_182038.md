# Why Do AI Agents Systematically Fail at Cloud Root Cause Analysis?

## Quick Facts
- arXiv ID: 2602.09937  
- Source URL: https://arxiv.org/abs/2602.09937  
- Reference count: 15  
- Primary result: LLM-based agents exhibit systematic failures in cloud RCA due to communication bottlenecks and reasoning pitfalls; enriched inter-agent protocol mitigates some failures.

## Executive Summary
This paper investigates why LLM-based agents struggle with cloud root cause analysis (RCA). Rather than only measuring final answer accuracy, the authors develop a process-level failure taxonomy with 12 pitfall types across intra-agent reasoning, inter-agent communication, and agent-environment interaction. Through 1,675 executions of the OpenRCA benchmark across five models, they find that Hallucination in Interpretation (71.2%) and Incomplete Exploration (63.9%) are dominant and persistent across all models. Prompt engineering failed to address these, but enriching the inter-agent communication protocol—by sharing code and raw outputs—reduced communication failures by up to 15 percentage points, increased perfect detection rates, and cut execution time by 22.3%. The study concludes that the shared agent framework itself is the primary bottleneck.

## Method Summary
The authors executed the OpenRCA benchmark, which simulates cloud incidents using telemetry data (metrics, logs, traces) across Telecom, Bank, and Market domains. They ran 1,675 agent executions using five LLMs (Claude Sonnet 4, GPT-5 mini, GPT-OSS 120B, Solar Pro 2, Gemini 2.5 Pro). A semi-automated pipeline with Claude Code classified each step into 12 pitfall types. Mitigation experiments tested prompt engineering, enriched communication (adding Executor code/output and Controller context), and a memory watcher to prevent OOM crashes.

## Key Results
- Hallucination in Interpretation (71.2%) and Incomplete Exploration (63.9%) are the most frequent pitfalls, occurring across all models.
- Enriched inter-agent communication reduced communication-related failures by up to 15 percentage points, increased perfect detection rates, and decreased execution time by 22.3%.
- Prompt engineering failed to suppress hallucination or incomplete exploration, indicating structural issues.

## Why This Works (Mechanism)
### Mechanism 1: Communication Fidelity Bottleneck
Claim: The natural language summary interface between Controller and Executor creates information loss, causing instruction misinterpretation and repetitive loops.  
Mechanism: Summarized instructions strip contextual cues, leading to Executor generating code that diverges from intent (Instruction-Code Mismatch) and Controller failing to recognize failed attempts (Meaningless Repetition). Direct exposure to code and granular outputs reduces ambiguity.  
Break condition: Even with direct exposure, if the Controller consistently misinterprets the Executor's implementation or the Executor's code remains misaligned with diagnostic goals.

### Mechanism 2: Narrative Fabrication in Interpretation
Claim: The agent's reasoning inherently imposes coherent but unfounded interpretations on telemetry data, a failure independent of model capability.  
Mechanism: The Controller prioritizes generating a plausible narrative over evidence-bound interpretation, a generative bias toward coherence.  
Break condition: If a verification mechanism forces grounding to data reduces hallucination below >60%.

### Mechanism 3: Lack of Exhaustive Exploration
Claim: The framework lacks incentives for breadth-first exploration, causing premature convergence.  
Mechanism: The Controller does not systematically track coverage across components, KPIs, and modalities, leading to ignored categories (e.g., network KPIs) and over-reliance on metrics.  
Break condition: If an intervention that enforces exhaustive candidate enumeration (e.g., checklist sub-agent) reduces Incomplete Exploration and Limited Telemetry Coverage to near zero.

## Foundational Learning
- **Multi-Agent System Decomposition (Controller-Executor Pattern)**: The Controller handles reasoning and planning; the Executor handles data access and code execution. Failures occur at boundaries (communication) and within roles (reasoning, execution). Quick check: What pitfall is most directly caused by the Controller having no visibility into the Executor's generated code? (Answer: Instruction-Code Mismatch)  
- **Telemetry Modalities & Diagnostic Coverage**: RCA requires correlating Metrics, Logs, and Traces. The "Limited Telemetry Coverage" pitfall shows agents fail to use all three. Quick check: If an agent only finds anomalies in CPU metrics but ignores trace data showing a downstream latency spike, which pitfall? (Answer: Limited Telemetry Coverage)  
- **Process-Level Failure Taxonomy vs. Outcome-Level Evaluation**: Moving beyond final answer correctness to classify *how* failures happen enables targeted fixes. Quick check: Agent A skipped all network-related KPIs → exhibited Incomplete Exploration. Agent B misinterpreted a log timestamp → exhibited Hallucination in Interpretation.

## Architecture Onboarding
- **Component map**: Controller -> Executor -> Python kernel (persistent environment with telemetry data)  
- **Critical path**: Controller generates instruction → Executor translates to code, executes, returns summary → Controller updates hypothesis and repeats.  
- **Design tradeoffs**:  
  1. Communication fidelity vs. efficiency: Natural language summaries are token-efficient but lossy; direct code/output exposure improves fidelity but increases token cost.  
  2. Exploration breadth vs. step budget: Exhaustive checking consumes more steps, risking step exhaustion.  
  3. State persistence vs. awareness: Persistent kernel avoids redundant data loads but causes OOM crashes without agent awareness.  
- **Failure signatures**:  
  1. Hallucination in Interpretation: Controller's claims not directly supported by Executor's output.  
  2. Instruction-Code Mismatch: Executor's code does not address the Controller's instruction.  
  3. Incomplete Exploration with early termination: Agent halts after few steps having analyzed only one component/KPI family.  
- **First 3 experiments**:  
  1. Baseline replication: Run standard OpenRCA on a subset (e.g., Bank domain) with one model, classify pitfall frequencies.  
  2. Enriched communication test: Modify messages to include Executor code and full output, and give Executor Controller's prior analysis snippet. Compare pitfall reductions and accuracy.  
  3. Memory isolation intervention: Integrate memory watcher to reset kernel upon high memory usage; validate OOM crash elimination.

## Open Questions the Paper Calls Out
1. Does the pitfall taxonomy generalize to other multi-agent RCA systems beyond OpenRCA?  
2. What specific architectural interventions effectively mitigate the dominant "Hallucination in Interpretation" pitfall?  
3. Are the observed performance gains from enriched inter-agent communication consistent across all three service domains (Telecom, Bank, Market)?  
4. Can the pitfall classification process be fully automated without human verification while preserving accuracy?

## Limitations
- Generalizability: Findings are tied to OpenRCA's specific domain/telemetry structure; unknown if pitfalls persist in other cloud environments or with newer models.  
- Taxonomy validation: Pitfall classification relies on semi-automated analysis without full human cross-check; potential labeling noise.  
- Mitigation scope: Enriched communication tested only on Bank domain; unclear if gains hold for Telecom and Market, and whether it amplifies other issues like token bloat.

## Confidence
- High: Prevalence of Hallucination (71.2%) and Incomplete Exploration (63.9%) across five models—empirically robust.  
- Medium-High: Communication bottlenecks as root cause—intervention reduced failures by 15pp, but causal isolation incomplete.  
- Low: Extrapolating mechanisms beyond the benchmark or to future agent architectures.

## Next Checks
1. Cross-benchmark replication: Run identical agent framework on a different RCA benchmark (e.g., Cloud-OpsBench) to measure pitfall transferability.  
2. Component isolation test: Ablate enriched protocol elements (code-only vs. output-only vs. both) to quantify each contribution to failure reduction.  
3. Human-annotated concordance: Sample 200 execution steps for independent human labeling; compute Cohen’s κ against paper’s automated pipeline.
