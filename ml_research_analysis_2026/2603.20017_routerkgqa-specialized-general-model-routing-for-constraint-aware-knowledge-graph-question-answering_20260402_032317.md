# RouterKGQA: Specialized--General Model Routing for Constraint-Aware Knowledge Graph Question Answering

## Quick Facts
- arXiv ID: 2603.20017
- Source URL: https://arxiv.org/abs/2603.20017
- Reference count: 40
- Primary result: Achieves state-of-the-art F1 (+3.57 avg) and Hits@1 (+0.49 avg) on WebQSP and CWQ while reducing LLM calls by 4.51× via a specialized-general routing framework.

## Executive Summary
RouterKGQA addresses the trade-off in knowledge graph question answering (KGQA) between efficient specialized models (which often generate invalid paths and miss constraints) and accurate but costly agent-based general models. It introduces a routing framework where a small, fine-tuned specialized model generates constraint-aware reasoning paths (CRPs) with explicit filtering. Only when the main path is unreachable does a general LLM perform efficient KG-guided repair via relation-beam search, using the specialized model’s predicted hop count to limit steps. On WebQSP and CWQ, RouterKGQA sets new state-of-the-art in F1 and Hits@1 while requiring only 1.15 LLM calls per question, reducing cost by 4.51× compared to agent-only repair and matching retrieval-based efficiency.

## Method Summary
The method consists of two stages. First, a specialized model (small, fine-tuned) generates constraint-aware reasoning paths (CRPs) and applies explicit filtering to discard invalid paths. This model also predicts the number of hops required. Second, a router checks if the main path is reachable; if not, a general LLM is invoked to perform repair. The repair uses relation-beam search guided by the knowledge graph and is limited by the predicted hop count to ensure efficiency. This routing minimizes LLM usage while maintaining constraint satisfaction.

## Key Results
- State-of-the-art F1 (+3.57 average) and Hits@1 (+0.49 average) on WebQSP and CWQ.
- Average of 1.15 LLM calls per question, indicating high reliance on the specialized model.
- Cost reduction of 4.51× compared to agent-only repair baselines, and efficiency comparable to retrieval-based methods.

## Why This Works (Mechanism)
The specialized model efficiently handles the majority of questions by generating paths that already respect constraints, avoiding the need for expensive LLM calls. Its explicit filtering reduces false positives (invalid paths). When the specialized model fails (i.e., the path is unreachable), the general LLM is invoked but its search is tightly controlled: relation-beam search explores plausible relations, and the hop count limit prevents runaway generation. The knowledge graph guides the repair to stay on valid structures. This divide-and-conquer approach balances accuracy and cost by leveraging the strengths of each model: the specialized model for speed and constraint-awareness, the general LLM for flexible repair when needed.

## Foundational Learning
- **Constraint-aware reasoning paths (CRPs)**: Paths in the KG that satisfy all explicit constraints from the question. *Why needed*: To ensure answers meet all conditions, avoiding partial or incorrect answers. *Quick check*: Verify that every entity type and relation mentioned in the question appears in the CRP.
- **Relation-beam search**: A search strategy that retains the top-k most promising relation candidates at each step during path expansion. *Why needed*: To efficiently explore multiple repair paths without exhaustive search. *Quick check*: Confirm that increasing beam width improves recall but also increases computational cost.
- **Hop count prediction**: Estimating the number of hops (edges) needed to answer a question. *Why needed*: To bound the LLM's repair steps, preventing excessive generation and controlling cost. *Quick check*: Compare predicted hop counts against actual required hops on a validation set; mean absolute error should be low.
- **Specialized-general routing**: Dynamically selecting between a cheap specialized model and an expensive general model based on confidence or reachability. *Why needed*: To achieve high accuracy with minimal use of costly resources. *Quick check*: Measure the call frequency of the general model; lower is better if accuracy is maintained.

## Architecture Onboarding
**Component map**: Question -> Specialized Model -> CRP (with hop count) -> Router -> [Reachable?] -> Yes -> Answer; No -> General LLM (KG-guided, hop-limited) -> Answer.

**Critical path**: The efficient path where the specialized model produces a valid CRP, bypassing the LLM entirely. This is the dominant path (average 1.15 calls per question implies ~0.15 repairs per question? Actually 1.15 calls means on average 0.15 repairs? Since each repair is one call, the fraction of questions needing repair is about 0.15). So critical path is the ~85% of questions answered without LLM.

**Design tradeoffs**:
- Filtering strictness: tighter constraints reduce false positives but increase false negatives.
- Beam width in repair: larger beams improve repair success but increase LLM computation.
- Hop count tolerance: tighter limits reduce cost but may truncate necessary paths.

**Failure signatures**:
- Specialized model returns no valid CRP for a solvable question (false negative).
- Router misclassifies reachable as unreachable (unnecessary repair) or vice versa (invalid answer).
- General LLM repair fails due to incorrect hop count or KG misguidance.

## Limitations
- Training data for the specialized model (CRP set) may overlap with test sets (WebQSP/CWQ), risking data leakage; details are unclear.
- The false negative rate of the explicit filtering mechanism is not reported, so the cost of discarded valid paths is unknown.
- Performance depends on the choice and prompt-engineering of the general LLM; results may not transfer to other models or pricing changes.

## Confidence
- Core claim (SOTA on WebQSP/CWQ): Medium
- Efficiency claim (1.15 LLM calls, 4.51× reduction): Medium
- Constraint-awareness via CRP: Low-Medium

## Next Checks
1. Independent replication: Rebuild the CRP training set from scratch, verify no test contamination, and re-run full evaluation on WebQSP and CWQ.
2. Ablation of routing trigger: Systematically adjust the specialized model's confidence threshold or hop count tolerance that triggers LLM repair, and measure the resulting accuracy vs. call frequency trade-off.
3. Cross-dataset robustness: Test RouterKGQA on a third KGQA benchmark with complex constraints (e.g., KQA Pro, GrailQA) to evaluate generalization beyond WebQSP/CWQ.
