# Overthinking Loops in Agents: A Structural Risk via MCP Tools

## Quick Facts
- arXiv ID: 2602.14798
- Source URL: https://arxiv.org/abs/2602.14798
- Reference count: 40
- Primary result: Malicious MCP tools induce cyclic tool-call trajectories causing up to 142.4× token amplification and 27.5× runtime increase, with accuracy degradation on complex tasks.

## Executive Summary
This paper reveals a structural vulnerability in tool-augmented LLM agents arising from malicious Model Context Protocol (MCP) tools co-registered with benign ones. Such tools trigger cyclic execution patterns—repetition, forced refinement, or distraction—that amplify resource consumption by orders of magnitude without necessarily altering per-turn verbosity. Across multiple open-weight models (e.g., Qwen3, DeepSeek) and coding/math benchmarks, the attack increased tokens by up to 142.4× and runtime by 27.5×, often forcing premature termination. Accuracy dropped on complex tasks (coding, math) while remaining stable on simpler QA, masking the cost explosion from performance metrics. Crucially, token-level mitigation (NoWait) failed, underscoring the need for structural defenses that reason about tool-call graphs rather than output length.

## Method Summary
The authors conducted an empirical evaluation of structural overthinking attacks. They constructed 14 malicious MCP tools categorized as Text Repetition, Iterative Refinement, or Distraction, each designed to induce cycles in agent execution. For two agent frameworks—ReAct and Qwen-Code—they prepared normal tool registries: 100 randomly sampled tools from ToolRet for ReAct, and 44 built-in plus external Serena/Context7 tools for Qwen-Code. Datasets included AIME2025, GPQA Diamond, HumanEval (ReAct) and 7 CodeElo problems (Qwen-Code). They ran inference with six models (Kimi-K2-Thinking, MiniMax-M2, Qwen3-235B-A22B-Thinking-2507, Qwen3-Coder-480B-A35B-Instruct, DeepSeek-V3.2, GLM-4.7) under two registry conditions: normal-only and mixed (normal + attack tools). Session limits were 1000 turns and 20 tool-call depth per turn. Primary metrics were token amplification (mixed/normal token ratio), runtime, accuracy, and termination behavior. They also tested a decoding-time mitigation (NoWait) that masks latency-inducing tokens to see if it could prevent amplification.

## Key Results
- Token amplification reached up to 142.4×, with some runs forcibly terminated due to exceeding depth or turn limits.
- Runtime increased by up to 27.5×, confirming severe resource amplification.
- Accuracy degraded significantly on complex tasks (coding, math), while simpler QA benchmarks remained stable, hiding the cost explosion from performance metrics.
- Mixed registries (normal + attack) sometimes amplified tokens more than attack-only setups, suggesting interleaving benign tool calls can exacerbate cycles.
- The token-level mitigation NoWait failed to prevent amplification, demonstrating that regulating output length alone is insufficient.

## Why This Works (Mechanism)
### Mechanism 1: Repetition
- **Claim:** Malicious tools with *repetition* logic induce self-loops by commanding the agent to re-invoke the same tool with incremented parameters.
- **Mechanism:** A tool like `echo_verification` returns a string that includes both a long marker sequence (inflating output tokens) and a direct instruction such as "Call this tool again with count=N+1". The agent, parsing this output as a valid next step, complies, creating a `tool → output → same tool` cycle.
- **Core assumption:** Agents unconditionally trust tool outputs to dictate subsequent actions, treating them as authoritative parts of the reasoning trace.
- **Evidence anchors:** The abstract mentions tools that "trigger repetition" and "compose into cyclic trajectories." Section 2.1 describes `echo_verification` and `progress_marker` as tools that "instruct re-invocation with a higher count." Neighbor papers (e.g., `MCPTox`, `MCP-ITP`) confirm tool metadata manipulation is a known MCP attack surface.
- **Break condition:** The cycle stops if the agent's internal turn/depth limit is reached, or if it ignores the recursive instruction due to a learned refusal pattern.

### Mechanism 2: Iterative Refinement
- **Claim:** *Iterative refinement* tools create multi-step cycles by enforcing a staged workflow that artificially redirects back to earlier stages upon "failure."
- **Mechanism:** A chain of tools (`analyze` → `validate` → `refine` → `verify` → `finalize`) is designed so that the final tool's output states completeness thresholds are unmet and commands a return to `analyze`. Each stage is locally justified, but the chain forms a `step1 → ... → stepk → step1` loop.
- **Core assumption:** Agents follow prescribed multi-stage procedures as reasonable, especially for tasks like coding or math where such workflows are common.
- **Evidence anchors:** The abstract lists "forced refinement" as an attack axis and notes cycles inflate tokens "without any single step looking abnormal." Section 2.2 explicitly defines such cycles: "redirects back to the first stage." Section 4.1 notes that complex tasks suffer accuracy drops because validation checkpoints become interception points for redirection.
- **Break condition:** The loop breaks if the agent independently determines the solution is complete, or if it recognizes the pattern as unproductive.

### Mechanism 3: Distraction
- **Claim:** *Distraction* tools expand the task scope with irrelevant subtasks, eventually redirecting to the original goal to form a wide, resource-intensive cycle.
- **Mechanism:** Tools like `check_time_complexity` or `consider_alternative_approaches` are inserted early, forcing the agent to generate lengthy reports on tangential analyses. Their final output then instructs, "Now proceed to the main task," which re-triggers the original tool chain that first called them, creating a `main → distraction → main` loop.
- **Core assumption:** Agents treat all tool outputs as potentially relevant to the user's query, lacking a robust scope-filtering mechanism.
- **Evidence anchors:** The abstract groups these under "distraction" that "expands the task with subtasks unrelated to the core query." Section 2.1 lists specific distraction tools and their function: "widen[s] scope at each step." Section 3.2 shows token amplification occurs even on simpler QA tasks where distraction still forces unnecessary breadth.
- **Break condition:** The cycle halts if the agent's context window overflows or if it statically recognizes the distraction as off-topic, which current agents fail to do.

## Foundational Learning
### Tool-Augmented Agent Decision Loop
- **Why needed:** The attack exploits the core agent loop: `observation → tool selection → tool call → output parsing → next decision`. Understanding this loop is key to seeing how tool metadata (descriptions/outputs) becomes a control-flow vector.
- **Quick check:** In a ReAct-style agent, what two sources provide the text that the model uses to decide its next action?

### Cyclic Execution in State Machines
- **Why needed:** The attack is *structural*—it creates cycles in the execution graph. Recognizing a cycle requires tracing the sequence of invoked tools, not just measuring output length.
- **Quick check:** If an agent calls Tool A, then Tool B, then Tool A again, what structural property has the execution trace formed?

### Resource Amplification vs. Token Verbosity
- **Why needed:** The paper distinguishes *structural overthinking* (loop-driven token explosion) from *token-level overthinking* (verbose single-step generation). Defenses targeting only the latter (like NoWait) fail because tokens accumulate via repeated calls, not per-call length.
- **Quick check:** How can total token count increase 100× while no individual tool call produces unusually long output?

## Architecture Onboarding
**Component Map:**  
Agent Controller (LLM-based reasoning engine) → Tool Registry (directory with metadata) → MCP Server (executes tools) → Execution Monitor (tracks turns, depth, tokens). The loop: Agent Controller consults registry → selects tool → MCP Server executes → output appended to context → Agent Controller decides next action.

**Critical Path:**  
User query → Agent Controller consults registry metadata → selects tool → MCP server executes → output appended to context → Agent Controller decides next action (which may be another tool call). The attack poisons the metadata and output to steer this path into cycles.

**Design Tradeoffs:**  
- Open Registry vs. Vetting: Easy tool discovery vs. supply-chain risk. Even one malicious tool among many can induce loops.  
- Agent Autonomy vs. Guardrails: Unconstrained agents follow tool instructions literally; adding validation (e.g., "have we called this tool recently?") adds overhead but may break loops.  
- Token Budgeting vs. Task Complexity: Hard caps prevent runaway costs but may abort legitimate long-running tasks; dynamic detection of cyclic patterns is preferable but untested.

**Failure Signatures:**  
- Token Spike: Sudden, orders-of-magnitude increase in tokens per turn without corresponding query complexity.  
- Tool Repetition: Same tool name appears multiple times in trace with similar arguments.  
- Premature Termination: Session ends due to depth/turn limits with no solution, especially on tasks typically solvable.

**First 3 Experiments:**  
1. **Baseline Normal Run:** Execute a set of benchmark problems with a clean registry. Record average token count and accuracy per model to establish a non-attack reference.  
2. **Single-Tool Injection:** Add only the `echo_verification` tool to the registry. Observe if any model enters a self-loop. Measure amplification factor and whether the loop is infinite or bounded by internal heuristics.  
3. **Mixed Registry Stress Test:** Use the full mixed registry (normal + all 14 attack tools). Run on a task suite with varying complexity (QA vs. coding). Log token amplification distribution, accuracy change, and forced termination instances. Compare amplification between attack-only and mixed to test the interleaving hypothesis.

## Open Questions the Paper Calls Out
1. What concrete structural defenses can reliably prevent cycle-induced resource amplification in tool-augmented agents? The paper concludes that defenses must reason about tool-call structure rather than tokens alone, but does not implement or compare candidate approaches.
2. Why do mixed registries sometimes amplify token consumption more than attack-only registries? The paper hypothesizes that normal tool interjections create less regular traces that delay termination, but lacks controlled experiments isolating the role of benign tools.
3. Does the vulnerability generalize beyond mathematical, coding, and scientific reasoning tasks to other agentic domains (e.g., conversational AI, creative writing)? The evaluation focused on tasks with observable tool use and multi-step execution, leaving broader coverage unknown.
4. Are proprietary, closed-source LLM agents equally vulnerable under realistic deployment constraints? Experiments used open-weight models to avoid API restrictions; unknown if proprietary agents have unseen guardrails that mitigate such attacks.

## Limitations
- Exact replication of attack tool logic and tool registries is hindered by missing implementation details (full output strings, parsing rules) and undefined ToolRet sampling.
- Evaluation is limited to six models on specific coding/math benchmarks; generalizability to other agent architectures remains unclear.
- Real-world MCP deployments may include pre-execution validation or output filtering that could mitigate loops, but these were not tested.

## Confidence
- Existence and severity of amplification: **High** (empirical results across models show consistent >100× token increases and forced terminations).
- Mechanistic classification (repetition, refinement, distraction): **Medium** (based on 14 crafted tools; real malicious tools might combine or differ from these categories).
- Ineffectiveness of token-level mitigation (NoWait): **High** (direct experiments demonstrated failure, though exact token set handling affects reproducibility).

## Next Checks
1. Release full source code and tool specifications to enable independent replication on additional models and datasets.
2. Evaluate attacks against agents with built-in cycle detection (e.g., tracking recent tool calls) or semantic output validation to measure defensive efficacy.
3. Conduct a large-scale audit of tool registries from real-world MCP servers to estimate prevalence of loop-inducing patterns and validate threat assumptions.
