# Compiler-Assisted Speculative Sampling for Accelerated LLM Inference on Heterogeneous Edge Devices
## Quick Facts
*   **arXiv ID:** 2602.08060
*   **Source URL:** https://arxiv.org/abs/2602.08060
*   **Reference count:** 29
*   **Primary result:** A compiler-driven heterogeneous partitioning scheme for Speculative Decoding achieves up to 1.68× speedup on an NXP i.MX95 edge SoC.

## Executive Summary
This paper tackles the problem of slowing LLM inference on edge devices by using Speculative Decoding (SD), where a fast "drafter" model proposes tokens that a slower "target" model verifies. A major hurdle is efficiently mapping the two models to the heterogeneous compute units (CPU, GPU) within a single SoC. The authors introduce an analytical cost model to predict when SD combined with specific hardware mappings will reduce latency. Guided by this model, they partition the computation, executing the drafter on the Mali GPU and the target on a single Cortex-A55 CPU core on an NXP i.MX95. This compiler-assisted setup yields a speedup of up to 1.68× for translation tasks, with the model's prediction deviating from measured results by only 4%.

## Method Summary
The method is a pipeline for compiler-assisted SD on edge SoCs. First, models (Llama 3.2 1B drafter, 3B target) are quantized (target INT8, drafter FP16). Profiling is then performed: the latency of a single forward pass for each model is measured on each processing unit (PU) across varying sequence lengths to compute a cost coefficient `c` (ratio of drafter to target latency). The acceptance rate `α` (proportion of draft tokens accepted by the target) is measured on server-grade hardware for the model pair on the specific task (translation from Spec-Bench). An analytical model `S(α,γ,c) = (1 - α^(γ+1)) / ((1-α)(γc+1))` predicts the speedup for a given draft length `γ` and hardware mapping. The optimal mapping (drafter on GPU, target on 1 CPU core) is selected based on this model. The full SD pipeline is compiled with IREE, with custom operators bound to physical devices during lowering to enforce the partitioning. End-to-end latency is measured against a CPU-only, non-speculative baseline.

## Key Results
*   **Speedup:** Up to 1.68× end-to-end latency improvement for translation tasks on the NXP i.MX95.
*   **Optimal Mapping:** The best performance occurs when the drafter runs on the Mali-G310 GPU and the target runs on a single Cortex-A55 CPU core.
*   **Model Accuracy:** The analytically predicted acceleration deviates from the measured result by only 4% for the optimal configuration.

## Why This Works (Mechanism)
The core mechanism is a **predictive cost model** that jointly evaluates two orthogonal optimizations: speculative decoding and heterogeneous execution. It quantifies the latency trade-off: while SD can reduce the total number of target calls (`γ` draft tokens verified in one go), it introduces drafter overhead. The model incorporates the hardware-specific cost ratio `c` and the model-specific acceptance rate `α`. A mapping is only beneficial if the combined cost of drafting and verifying a batch of `γ` tokens is lower than generating those tokens sequentially on the baseline. By pre-profiling `c` for each PU and measuring `α` offline, the model can select the `γ` and hardware partition that minimizes expected latency before deployment, avoiding expensive runtime autotuning.

## Foundational Learning
*   **Speculative Decoding (SD):** A technique where a small, fast "draft" model generates a sequence of tokens which are then verified in parallel by a larger "target" model. **Why needed:** Reduces the sequential dependency of autoregressive decoding, improving throughput. **Quick check:** If `α` (acceptance rate) is high and `c` (drafter/target latency ratio) is low, SD provides speedup.
*   **Cost Model for SD:** Analytical formula `S(α,γ,c)` predicting speedup. **Why needed:** Provides a lightweight, hardware-aware predicate to guide partitioning decisions without exhaustive runtime search. **Quick check:** Plug empirical `α`, `c` into the formula to see which `γ` and mapping maximizes `S`.
*   **Compiler-Assisted Heterogeneous Partitioning:** Using a compiler (IREE) to split a single model graph into subgraphs and bind them to specific hardware backends (LLVM-CPU, SPIR-V for Mali GPU). **Why needed:** Enforces the hardware mapping predicted by the cost model with minimal runtime overhead. **Quick check:** Examine compiled MLIR modules for device affinity attributes (e.g., `iree.placement`).
*   **Quantization for Edge Inference:** Using lower precision (INT8, FP16) to reduce memory footprint and accelerate computation. **Why needed:**Edge devices have limited memory bandwidth and compute; quantization is essential for feasible LLM execution. **Quick check:** Profile model size and single-pass latency for different precisions on target hardware.
*   **Workload Characterization (Profiling):** Measuring operation latency for specific models and sequence lengths on each PU. **Why needed:** The cost coefficient `c` is not architectural; it depends on the specific model, precision, and input sequence length. **Quick check:** Time a single forward pass of the drafter and target on each PU for the target sequence length.
*   **Acceptance Rate Measurement:** Evaluating how often the drafter's proposals match the target's distribution. **Why needed:** `α` is task- and model-dependent; it directly controls SD's efficiency. **Quick check:** Run drafter-target pair on validation samples, count matches, compute median proportion.

## Architecture Onboarding
**Component Map:**
Input Tokens -> Drafter Subgraph (Mali GPU) -> Draft Token Buffer -> Target Subgraph (Cortex-A55 Core 1) -> Verification & Output -> Next Token Loop

**Critical Path:**
1.  Drafter generates `γ` tokens sequentially on GPU.
2.  Draft tokens are transferred to CPU memory.
3.  Target verifies the entire draft sequence in parallel on one CPU core.
4.  Accepted tokens (prefix of draft) are emitted; rejected token triggers one target-generated token.
5.  Loop continues from the first rejected position or next token after the accepted prefix.

**Design Tradeoffs:**
*   **Precision vs. Speed:** Drafter on GPU ideally uses INT8 for speed, but Mali may promote to FP32, increasing `c` and negating benefits. Target on CPU uses INT8 effectively.
*   **Modular vs. Monolithic:** Using separate compiled modules for drafter/target adds inter-device memory copy and API call overhead. The cost model assumes idealized partitioning; real overhead must be measured.
*   **Draft Length `γ`:** Longer `γ` reduces target invocations but increases drafter work and risk of low acceptance. Optimal `γ` is sensitive to `α` and `c`.
*   **Core Allocation:** Using one CPU core for the target minimizes interference but underutilizes the hexacore; using more cores may speed up the target but increases shared resource contention (memory bandwidth, caches).

**Failure Signatures:**
*   **Measured speedup << predicted:** Likely due to unaccounted modular overhead, GPU precision promotion, or poor `α` on-edge.
*   **Low acceptance rate (`α < 0.5`):** SD will not provide speedup; drafter and task are misaligned.
*   **High `c` (drafter latency >> target):** Even with good `α`, SD overhead dominates; likely caused by inefficient drafter placement (e.g., on CPU) or precision issues.
*   **No speedup with "optimal" mapping:** Check for DVFS interference during profiling, incorrect device binding in IREE, or excessive cross-device data transfer.

**First Three Experiments:**
1.  **Profiling Run:** Compile and time single forward passes of quantized drafter (FP16/INT8) and target (INT8) on Mali GPU and 1-6 Cortex-A55 cores for sequence lengths 1-100. Compute `c` for SL=63.
2.  **Acceptance Rate Run:** On the i.MX95, run the semi-quantized drafter-target pair on Spec-Bench translation inputs. Measure median `α` after warm-up.
3.  **End-to-End SD Latency:** Implement the partitioned pipeline (drafter on Mali, target on 1 CPU core) in IREE. Measure average generation latency over 10 tokens on translation task, compare to CPU-only non-speculative baseline.

## Limitations
*   **Heterogeneous Mapping Implementation:** Exact IREE flags, MLIR attributes, and core pinning strategies for NXP i.MX95 are not detailed, making exact replication difficult.
*   **Acceptance Rate Generalizability:** `α` was measured on server-grade hardware; edge platform effects (thermal throttling, memory constraints) may alter it.
*   **GPU Precision Support:** The Mali-G310's native INT8 support is questionable; promotion to FP32 would invalidate the cost model's precision assumptions and increase `c`.

## Confidence
*   **Cost Model Predictive Accuracy:** High (4% deviation on tested config).
*   **Optimal Mapping Generality:** Medium (demonstrated on one hexacore SoC; other platforms need profiling).
*   **Quantization Scheme Optimality:** Low (semi-quantized scheme explored, but full trade-off space not isolated).
