# MXNorm: Reusing MXFP block scales for efficient tensor normalisation

## Quick Facts
- arXiv ID: 2603.13180  
- Source URL: https://arxiv.org/abs/2603.13180  
- Reference count: 40  
- Primary result: MXNorm reduces normalization reduction cost by 32×, matches RMSNorm training loss on LLMs up to 8B, and yields up to 2.4× kernel speedup.

## Executive Summary
MXNorm addresses the computational bottleneck of normalization layers (e.g., RMSNorm) in low-precision training by reusing the block scales computed during MXFP quantization to estimate the root mean square. This reduces the required reduction by a factor equal to the block size (32× for MXFP8, 16× for NVFP4). Validated on Llama 3 models up to 8B parameters, MXNorm with p=2 achieves final training losses comparable to RMSNorm (e.g., 2.126 vs 2.132 for 8B) and similar zero-shot task performance. On GB200 hardware, it delivers up to 2.4× kernel speedup over RMSNorm fused with MXCast, translating to a 1.3% (MXFP8) and 2.6% (NVFP4) layer-level speedup.

## Method Summary
MXNorm replaces RMSNorm with an estimator based on the p‑mean (p=2) of absolute maximum values from each quantization block. During MXFP quantization, the block absmaxes are already computed; MXNorm multiplies them by a precomputed correction factor c(p,B) (derived via Monte Carlo on Gaussian data) to estimate the RMS. This estimate scales the activations, which are then quantized to MX formats and multiplied with the linear layer weights (fused). The reduction complexity drops from O(D) to O(D/B), where B is the block size (32 for MXFP8, 16 for NVFP4). The backward pass uses a straight‑through estimator with cached activations and RMS estimate.

## Key Results
- Training loss matches RMSNorm: 2.126 vs 2.132 for Llama 3 8B with MXFP8.  
- Zero‑shot task performance (OLMES) remains comparable to RMSNorm.  
- Kernel speedup up to 2.4× over RMSNorm+MXCast; layer‑level speedup of 1.3% (MXFP8) and 2.6% (NVFP4) on GB200.

## Why This Works (Mechanism)
MXNorm exploits the fact that MXFP quantization already computes per‑block absolute maximums (absmax) to set quantization scales. Under i.i.d. Gaussian activation assumptions, the RMS is proportional to the expected absolute value, which relates to the block absmax via order statistics: the expected maximum of absolute Gaussians is approximately sqrt(2 log B) times the standard deviation. The constant c(p,B) captures this factor for p=2 and a given B, obtained via Monte Carlo. By reusing these absmaxes, MXNorm avoids a full reduction over the hidden dimension, cutting the cost by factor B. Choosing p=2 yields tighter output bounds (scaling with sqrt(K) where K is number of blocks) compared to p=1, improving stability. Fusing the normalization scaling into the subsequent linear layer’s weights further reduces memory traffic and compute overhead.

## Architecture Onboarding
- **Component map**: `Input Activations -> Block Absmax (from MXFP) -> RMS Estimate (c(p,B) * mean(|absmax|^p)^{1/p}) -> Norm Scale -> MX Quantization -> Linear (weight fused with norm gain) -> Output`.  
- **Critical path**: 1) Compute block absmax values (concurrent with quantization prep). 2) Reduce absmaxes to obtain RMS estimate (O(D/B)). 3) Apply normalization scaling. 4) Quantize activations. 5) Perform matrix multiply with fused weight.  
- **Design tradeoffs**:  
  - Block size B: Larger B reduces reduction cost but may increase approximation error; must match hardware Tensor Core widths (32 for MXFP8, 16 for NVFP4).  
  - Exponent p: p=2 gives tighter bounds than p=1; larger p may tighten further but changes constant c(p,B) and stability.  
  - Correction factor: Accuracy depends on Gaussian assumption; deviations (e.g., outliers) increase error.  
  - Fusion: Scaling into weights reduces memory traffic but requires storing scaled weights and careful update handling.  
- **Failure signatures**:  
  - Loss spikes early in training (especially with p=1).  
  - RMS of normalized outputs consistently >1.2, indicating poor approximation.  
  - Low r² (<0.9) between dequantized MXNorm outputs and RMSNorm+MXCast tensors for small hidden dimensions.  
  - Kernel speedup <1.1x despite correct block size, suggesting misconfiguration of pow2_round or compilation.

## Open Questions the Paper Calls Out
- **O1: Does MXNorm maintain training stability and accuracy with extremely low‑precision quantization (e.g., INT2, ternary)?**  
  *Basis*: Conclusion suggests potential for narrower formats. *Why unresolved*: Experiments only on MXFP8 and NVFP4. *Evidence needed*: Pre‑train Llama 3 models with MXNorm+INT2/ternary, compare loss curves, zero‑shot performance, and stability against RMSNorm baselines; measure kernel speedups on supporting hardware.

- **O2: Can MXNorm be generalized to other block quantization schemes (e.g., VS‑Quant)?**  
  *Basis*: Conclusion mentions generalization to forms that compute block absmaxes. *Why unresolved*: MXNorm tailored to MXFP’s E8M0 scales; VS‑Quant uses per‑vector scaled quantization, so compatibility unknown. *Evidence needed*: Implement MXNorm within VS‑Quant framework, replace MXCast with VS‑Quant’s block absmax, pre‑train models, and compare against VS‑Quant with RMSNorm on training loss, accuracy, and normalization fidelity.

- **O3: For which values of the norm exponent p does MXNorm provide a stable and accurate approximation across diverse model scales?**  
  *Basis*: Paper tested p=1 (unstable) and p=2 (stable); no systematic study of other p. *Why unresolved*: Theoretical bounds suggest larger p yields tighter output bounds, but constant c(p,B) changes; interaction with model size/hidden dimension unclear. *Evidence needed*: Hyperparameter search over p∈{1.0,1.2,1.5,1.8,2.0,2.2,2.5} on multiple model sizes (125M,1B,8B+), using LR sweeps; monitor loss spikes, final loss, zero‑shot performance, and correlate with theoretical bounds.

- **O4: How sensitive is MXNorm’s approximation accuracy to violations of the Gaussian activation assumption (e.g., outliers, non‑i.i.d. activations)?**  
  *Basis*: Theorem 1 assumes i.i.d. Gaussian activations with E[Z²]=1; paper notes outlier features cause spikes. *Why unresolved*: Real transformer activations can have heavy tails and correlations; impact of deviations not analyzed. *Evidence needed*: Analyze activation statistics (kurtosis, outlier frequency) during RMSNorm training; synthetically perturb activations to introduce non‑Gaussianity and measure MXNorm estimation error; optionally train with regularization to reduce outliers and observe performance changes.

## Limitations
- Correction factors (c(p,B)): Monte Carlo procedure underspecified; only provided for B∈{16,32,64}, limiting adaptation to other block sizes.  
- Kernel speedup claims: Highly sensitive to block size matching Tensor Core widths and non‑standard pow2_round; replication on alternative systems uncertain.  
- Training stability at scale: Exact FSDP, optimizer (AdamW β₂, clipping), and stability tricks not fully described, raising reproducibility risks for similar‑scale runs.

## Confidence
- Correction factor generalizability: Low  
- Kernel speedup claims: Medium  
- Training stability at scale: Medium
