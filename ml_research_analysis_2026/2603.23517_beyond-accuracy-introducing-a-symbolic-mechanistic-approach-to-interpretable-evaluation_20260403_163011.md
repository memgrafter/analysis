# Beyond Accuracy: Introducing a Symbolic-Mechanistic Approach to Interpretable Evaluation

## Quick Facts
- **arXiv ID:** 2603.23517
- **Source URL:** https://arxiv.org/abs/2603.23517
- **Reference count:** 10
- **Primary result:** Symbolic-mechanistic evaluation revealed that standard accuracy metrics mask memorization; a model trained without schema achieved 93.5% field-name accuracy but only 59% pass rate on algorithmic rules (R1-R3), while a schema-trained model achieved 76% pass rate.

## Executive Summary
Accuracy-based evaluation alone cannot distinguish whether a model truly generalizes using intended algorithms or merely memorizes patterns. This paper introduces a symbolic-mechanistic framework that combines symbolic rule specification with mechanistic interpretability techniques (e.g., activation patching) to test if models employ the desired computational mechanisms. Applied to natural language-to-SQL generation, the approach shows that a model fine-tuned without schema information attains high field-name accuracy (93.5%) yet fails mechanistic checks (59% pass rate), whereas a model trained with schema grounding passes at 76%. The method thus exposes hidden memorization and localizes the circuit responsible for correct reasoning.

## Method Summary
The authors fine-tune two TinyStories-33M language models on the TinySQL CS1 Synonyms dataset, a benchmark for NL-to-SQL that forces schema grounding via column synonyms. The “Schema” model receives the database schema in every training prompt; the “NO Schema” model never sees the schema. Evaluation proceeds in two ways: (1) standard metrics (exact match, field-name accuracy) and (2) a novel symbolic-mechanistic protocol comprising three hierarchical rules. R1 measures schema sensitivity by computing the change in logit preference for the correct field name when the schema token is corrupted; R2 localizes the causal effect using residual activation patching across layers and requires a minimum recovery fraction; R3 enforces circuit reusability by demanding that high-recovery layers are consistent across examples. The overall pass rate is the fraction of examples satisfying all three rules. This pipeline directly tests whether the model uses an algorithmic mechanism that grounds the query in the schema.

## Key Results
- The NO Schema model achieved 93.5% field-name accuracy but only 59% pass rate on R1-R3.
- The Schema model achieved 76% pass rate on R1-R3, demonstrating stronger use of the intended grounding circuit.
- Standard accuracy metrics masked the NO Schema model’s reliance on memorization, highlighting the value of mechanistic evaluation.

## Why This Works (Mechanism)
### Mechanism 1: Schema Sensitivity (R1)
**Claim:** The model’s output preference for the correct token is causally dependent on the schema token present in the prompt.  
**Mechanism:** For each example, compute the logit difference between correct and incorrect tokens for the clean prompt and for a corrupted prompt where only the schema token is changed. The change in logit difference (Δ) measures the shift in preference. If |Δ| exceeds a threshold τ_gap (R1), the model’s decision is sensitive to the schema token.  
**Core assumption:** If the model employs a schema-checking circuit, altering the schema token will disrupt that circuit and thus affect the final logits.  
**Evidence anchors:** The authors state that their approach tests “if models use intended algorithms” and exposes failures in schema grounding. The formal definition of R1: `R1i = I[|Δi| ≥ τ_gap]`. Neighboring work on rule-and-fact separation supports sensitivity testing.  
**Break condition:** If nearly all examples fail R1 (|Δ| < τ_gap), the model likely ignores schema information entirely, indicating reliance on memorization or heuristics.

### Mechanism 2: Causal Localization (R2)
**Claim:** The causal effect observed in R1 can be localized to specific layers via activation patching, indicating a concentrated computational circuit.  
**Mechanism:** For each layer L, patch the residual activation at the schema token position from a clean example into the corrupted forward pass. Compute recovery as the fraction of the original Δ that is restored. If recovery ≥ α (R2), the effect localizes to that layer.  
**Core assumption:** A dedicated schema-processing circuit should reside in a limited set of layers; patching those layers should restore the preference, while others will not.  
**Evidence anchors:** The framework combines “symbolic rules with mechanistic interpretability”. The paper details the patching protocol, defines `RecFrac_i`, and R2: `R2i = R1i ∧ I[RecFrac_i ≥ α]`. Prior work finds transformers use specific layers for compositional tasks.  
**Break condition:** If examples that pass R1 show no layer with recovery ≥ α, the effect is either too distributed or patching fails, suggesting no localized circuit.

### Mechanism 3: Circuit Reusability (R3)
**Claim:** The same layer(s) are used across multiple examples, demonstrating circuit reusability and thus a consistent algorithmic mechanism.  
**Mechanism:** For each example passing R1 and R2, identify its set of high-recovery layers (TopLayers_i, recovery ≥ 90%). Find the most common high-recovery layer L* across all such examples. An example passes R3 if L* is in its TopLayers, testing consistency.  
**Core assumption:** A genuine algorithmic skill should be implemented by a reusable computational pathway; if different examples use different layers, the model is likely exploiting input-specific heuristics.  
**Evidence anchors:** The evaluation “show[s] exactly where models generalize versus exploit patterns”. R3: `R3i = R1i ∧ R2i ∧ I[L* ∈ TopLayers_i]`. Results show the schema-trained model with 89% of R3-passing examples using Layers 0–2.  
**Break condition:** If examples passing R1 and R2 have disjoint high-recovery layers, circuit reusability fails, suggesting no consistent algorithmic implementation.

## Foundational Learning
### Concept: Logit Difference as Preference Metric
**Why needed:** The rules rely on quantifying the model’s preference for the correct token using the difference in logits at the final position. This is the fundamental measure of output bias.  
**Quick check:** Why might using logit difference at the final position be misleading if the model’s output distribution is multimodal or if there are multiple correct tokens?

### Concept: Activation Patching for Causal Localization
**Why needed:** Activation patching is the core intervention in R2 to test whether a specific layer’s computation mediates the schema effect. Understanding how to perform interventions and interpret recovery is essential.  
**Quick check:** What is the difference between activation patching and path patching, and why might activation patching produce false positives if there are multiple causal pathways?

### Concept: Symbolic Rule Specification
**Why needed:** The evaluation hinges on defining task-relevant symbolic rules (R1–R3) that capture the intended algorithm. These rules must be expressible in terms of model-internal measurements.  
**Quick check:** If a task has multiple valid algorithms (e.g., different ways to parse NL-to-SQL), how might that affect the design of symbolic rules?

## Architecture Onboarding
### Component Map
Model -> Evaluation dataset -> Symbolic rule engine -> Activation patcher -> Logit analyzer -> Reporting

### Critical Path
1. Dataset preparation: For each base example, generate 5 corrupted versions differing only in the schema token.
2. Clean/corrupted logit extraction: For each prompt, compute logit difference between correct and incorrect field tokens; derive Δ per example.
3. Patching sweep: For each corrupted prompt, iterate over all layers L: cache clean activation at schema token position (residual after layer L), patch into corrupted forward pass, compute patched logit difference, and calculate `shift_i(L)`.
4. Recovery calculation: Compute `best_recovery_i = max_L max(0, sign(Δ_i)·shift_i(L))` capped at |Δ_i|. `RecFrac_i = best_recovery_i / |Δ_i|`. Identify `TopLayers_i` as layers where `shift_i(L) ≥ 0.9·|Δ_i|`.
5. Layer consistency: From examples satisfying R1 and R2, find the most frequent layer L* among all `TopLayers_i`. For each such example, R3 passes if L* ∈ `TopLayers_i`.
6. Aggregation: Overall pass rate = fraction of examples passing R3; also compute per-corruption-type pass rates and layer usage histograms.

### Design Tradeoffs
- Threshold selection: τ_gap and α heavily influence pass rates; lower τ_gap increases sensitivity but may admit noise; higher α demands stricter localization.
- Example count: 100 examples (20 per corruption type) balances cost and reliability; more examples yield narrower confidence intervals but increase compute.
- Corruption diversity: Five types probe different aspects; adding more improves coverage but complicates analysis.
- Layer range: Patching all layers is straightforward but costly for deep models; restricting to a hypothesized range reduces compute but risks missing the true circuit.
- Model access: Requires full weights and activation extraction; not feasible for closed API models.

### Failure Signatures
- Symmetrically low pass rates for both models: suggests rule definitions or thresholds are flawed.
- High variance across corruption types within a model: indicates poorly designed corruptions or inconsistent behavior.
- No layer convergence for R3 (TopLayers_i widely dispersed): task may not rely on a single reusable circuit or circuit is distributed.
- Recovery fractions consistently near zero for non-zero Δ: patching fails to capture causal pathway, possibly due to superposition.
- Schema model yields lower pass rate than NO Schema on certain corruptions: could indicate overfitting to exact schema tokens.

### First 3 Experiments
1. **Sanity check with expected generalization:** Fine-tune a model with schema included (Schema condition). Expect high R3 pass rate (>70% overall), large mean Δ, and recovery concentrated in early layers (L* near 0–2). If not, debug rule implementation.
2. **Sanity check with memorization control:** Use the NO Schema model. Expect low R3 pass rate (<60% overall), small Δ, low and distributed recovery. If it passes highly, rules may be too weak.
3. **Threshold robustness:** Vary τ_gap (e.g., {0.25, 0.3, 0.4, 0.5}) and α (e.g., {0.8, 0.9, 0.95}). Ensure Schema model consistently outperforms NO Schema across settings. If ordering flips, thresholds are unstable; choose values that maximize separation while maintaining plausible effect sizes.

## Open Questions the Paper Calls Out
### Open Question 1
*Question:* What systematic framework can calibrate hyperparameters (τ_gap, α) for symbolic-mechanistic rules across diverse tasks?  
*Basis:* The paper states that their rules depend on hyperparameters requiring principled calibration; control tasks with known ground-truth mechanisms are needed.  
*Why unresolved:* Thresholds are chosen arbitrarily per experiment, preventing cross-study comparison and risking overfitting.  
*Evidence needed:* A suite of canonical control tasks with verified generalization circuits to enable threshold optimization and validation protocols.

### Open Question 2
*Question:* Do activation patching results faithfully isolate targeted computational circuits, or are they confounded by distribution shifts from the intervention?  
*Basis:* The paper acknowledges that activation patching risks distribution shifts and may allow recovery through confounding pathways.  
*Why unresolved:* Patching replaces activations from one context to another, potentially creating unnatural inputs that activate alternative circuits.  
*Evidence needed:* Comparative analyses using multiple mechanistic intervention methods (e.g., path patching, causal tracing) on the same tasks to measure consistency.

### Open Question 3
*Question:* Can symbolic-mechanistic evaluation be meaningfully applied to tasks without clearly specified algorithmic primitives, such as open-ended text generation?  
*Basis:* The paper admits symbolic rules become hard to define for complex tasks lacking clear algorithmic primitives; the framework suits targeted capability assessment.  
*Why unresolved:* Many real-world tasks involve fuzzy objectives or diverse solution strategies, making rule specification subjective or impossible.  
*Evidence needed:* Case studies extending the framework to moderately complex tasks (e.g., multi-step reasoning) using composite or probabilistic rules.

### Open Question 4
*Question:* For tasks with multiple valid algorithms, how can mechanism-aware evaluation certify the presence of any correct reasoning pathway rather than enforcing a single mechanistic profile?  
*Basis:* Inferred from the paper’s scope restriction and reliance on a single rule set per task.  
*Why unresolved:* Realistic tasks often have several correct approaches; requiring one specific circuit may penalize valid alternatives.  
*Evidence needed:* Development of rule sets capturing families of mechanisms, with pass criteria based on satisfaction of any sufficient combination, validated against human-recognized correct reasoning.

## Limitations
- Missing fine‑tuning hyperparameters and incomplete specification of activation patching implementation hinder exact replication and may introduce variance.
- Arbitrary threshold choices (τ_gap, α) without robustness analysis threaten the stability of reported results.
- Evaluation limited to a single small model and dataset, with no statistical tests, reducing generalizability and confidence in observed differences.

## Confidence
- **Accuracy metrics mask memorization:** Medium confidence. Plausible and supported by neighbor work, but not directly proven here.
- **R1–R3 rules capture intended algorithm use:** Low confidence. Novel rules lack external validation; threshold choices appear arbitrary.
- **Schema‑trained model shows higher circuit reusability than NO Schema:** Medium confidence. Internal results consistent, but reproducibility uncertainties dominate.

## Next Checks
1. **Threshold robustness:** Vary τ_gap (0.2–0.6) and α (0.7–0.95) across both models; confirm that the R3 pass‑rate ordering (Schema > NO Schema) persists. If ordering flips, method is unstable.
2. **Causal localization cross‑check:** Use path patching or direct effect mediation analysis to verify that the layers identified by activation patching are necessary and sufficient for schema grounding. Compare “high‑recovery” layer sets.
3. **Cross‑dataset and model transfer:** Apply the same symbolic‑mechanistic protocol on Spider (NL‑to‑SQL) and on a larger model (e.g., Llama‑2‑7B). Successful transfer would demonstrate general validity beyond the original narrow setup.
