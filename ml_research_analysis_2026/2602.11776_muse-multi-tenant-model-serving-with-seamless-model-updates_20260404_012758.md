# MUSE: Multi-Tenant Model Serving With Seamless Model Updates

## Quick Facts
- **arXiv ID:** 2602.11776
- **Source URL:** https://arxiv.org/abs/2602.11776
- **Reference count:** 40
- **Primary result:** Reduced model lead time from weeks to minutes, preventing over $1.7 million in confirmed fraud losses.

## Executive Summary
Multi-tenant scoring systems suffer critical bottlenecks when model updates shift score distributions, invalidating client-managed decision thresholds and causing operational delays. MUSE solves this by decoupling model scores from business thresholds via a two-level transformation: Posterior Correction removes undersampling bias from individual ensemble members, and Quantile Mapping maps the final score to a stable, pre-defined reference distribution. Combined with intent-based routing, this enables seamless model updates without client intervention. Deployed at Feedzai, MUSE processes over 55 billion events annually with sub-30ms p99 latency and 99.95% availability, directly preventing significant fraud losses by accelerating the deployment of resilient models.

## Method Summary
MUSE applies a deterministic, two-stage transformation to raw model outputs. First, **Posterior Correction** adjusts each ensemble member’s score using its known undersampling ratio (β_k) to reverse bias from training on imbalanced data. Second, **Quantile Mapping** aligns the aggregated corrected score to a fixed reference distribution via piecewise linear interpolation over precomputed quantiles, preserving ranking while stabilizing the output distribution. Client requests carry intent metadata (e.g., tenant ID, use case); a stateless router uses declarative `scoringRules` to map intents to predictor configurations (model ensembles + transformations). Updates occur by swapping the rule’s target predictor, enabling zero-downtime rollouts. For new tenants, a cold-start Beta-mixture model initializes the mapping without live data.

## Key Results
- Scales to over 1,000 events per second and 55+ billion events annually across dozens of tenants.
- Maintains sub-30ms p99 latency and 99.95% availability.
- Reduced model lead time from weeks to minutes.
- Directly prevented over $1.7 million in confirmed fraud losses by enabling rapid deployment of more resilient models.

## Why This Works (Mechanism)

### Mechanism 1: Posterior Correction
**Claim:** Removes undersampling bias from individual model scores, enabling fair aggregation in ensembles.  
**Mechanism:** For each model \(m_k\) with undersampling ratio \(\beta_k\), the raw score \(\tilde{y}_k\) is transformed via \(T_{Ck}(\tilde{y}_k) = \frac{\beta_k \tilde{y}_k}{1 - (1-\beta_k) \tilde{y}_k}\). This rescales posterior probabilities to correct inflation caused by training on an undersampled dataset.  
**Core assumption:** The raw model score approximates a posterior probability under the undersampled training distribution, and \(\beta_k\) is accurately known from training configuration.  
**Evidence anchors:** Abstract and section 2.3.1 (Equation 3); limited direct corpus evidence beyond related calibration work.  
**Break condition:** Incorrect or unknown \(\beta_k\) leads to biased corrections; also fails if raw scores are non-probabilistic (e.g., uncalibrated outputs).

### Mechanism 2: Quantile Mapping
**Claim:** Stabilizes final score distributions across model updates by mapping them to a fixed reference distribution, preserving ranking while ensuring downstream thresholds remain valid.  
**Mechanism:** Precompute \(N\) quantiles of the source distribution \(S\) (per tenant-predictor) and a reference distribution \(R\). For an aggregated score \(\tilde{y}\), find the interval \([q_S^i, q_S^{i+1})\) via binary search and apply linear interpolation: \(T_Q(\tilde{y}) = q_R^i + (\tilde{y} - q_S^i) \cdot \frac{q_R^{i+1} - q_R^i}{q_S^{i+1} - q_S^i}\). The transformation is monotonic.  
**Core assumption:** The reference \(R\) is static and appropriate; source quantiles can be accurately estimated from sufficient unlabeled data; ranking preservation suffices for predictive utility.  
**Evidence anchors:** Abstract and section 2.3.3 (Equation 4); corpus work on adaptive thresholding under non-stationarity is related but not identical.  
**Break condition:** Poor choice of \(R\) (e.g., mismatched alert rate granularity), insufficient data for accurate quantile estimation, or failure to refresh quantiles after significant drift.

### Mechanism 3: Intent-Based Routing
**Claim:** Decouples client requests from specific model versions, enabling seamless model updates without requiring client-side changes.  
**Mechanism:** Clients include an intent (e.g., tenant ID, use case) in request metadata. Server-side declarative rules (`scoringRules`) map intents to predictors (which encapsulate models and transformations). Updates are performed by reassigning the rule's `targetPredictorName` (e.g., from v1 to v2) and rolling out via Kubernetes. Shadow rules allow parallel evaluation.  
**Core assumption:** Clients consistently provide correct intent metadata; routing rules are accurately maintained; the predictor's transformations ensure score stability so thresholds stay valid.  
**Evidence anchors:** Abstract and section 2.5 (Figure 2); multi-tenant serving systems like Punica and EdgeLoRA demonstrate resource sharing, but MUSE's intent-based approach uniquely targets score stability.  
**Break condition:** Misconfigured routing rules send clients to wrong predictors; missing or tampered intent causes fallback failures; if transformations are absent or broken, score distribution shifts invalidate thresholds.

## Architecture Onboarding

**Component map:**  
Client -> MUSE Router (with Transformation Engine, scoring rules from Config Store) -> Feature Store (optional) -> Model Servers -> MUSE Router (post-processing) -> Client. Data Lake used offline for quantile estimation.

**Critical path:**  
1. Receive request and extract intent metadata.  
2. Lookup `scoringRules` in Config Store to resolve predictor ID.  
3. Enrich features from Feature Store if required.  
4. For each model in the predictor: send batched inference request to Model Servers and receive raw score.  
5. Apply Posterior Correction to each raw score using the model’s \(\beta_k\).  
6. Aggregate corrected scores (e.g., weighted average).  
7. Apply Quantile Mapping: binary search in tenant-specific source quantiles, interpolate using reference quantiles.  
8. Return final score to client.

**Design tradeoffs:**  
- *Stateless router:* Enables horizontal scaling but requires consistent, fast config propagation; brief inconsistency possible during rolling updates.  
- *Shared model servers:* Cost-efficient but risk of hot models; requires scaling of model server replicas.  
- *Per-tenant quantiles:* High storage cost but ensures accurate mapping; could group similar tenants to reduce cost.  
- *Fixed reference distribution:* Simplifies threshold management but may lack customizability; some predictors could use alternative references if needed.  
- *Cold-start Beta-mixture:* Provides initial mapping without data but may be less accurate; tradeoff between early stability and precision.

**Failure signatures:**  
- High p99 latency (>30ms): Check model server saturation, feature store latency, or excessive quantile search time.  
- Score distribution drift: Monitor bin-wise relative error vs. target distribution; may indicate outdated source quantiles or incorrect \(\beta_k\).  
- Routing errors: Logs with unmatched intents or HTTP 400/404 responses.  
- Resource exhaustion: Pod restarts/OOM due to memory pressure from large quantile arrays or model containers.  
- Cold-start skew: New tenants showing extreme score concentration in low bins.

**First 3 experiments:**  
1. **Smoke test:** Deploy a predictor with a single model and no transformations. Send requests and verify raw scores are returned unchanged; measure end-to-end latency and compare with direct model server inference latency.  
2. **Posterior Correction validation:** Using a model with known \(\beta_k\) (e.g., from training logs), compute corrected scores on a fixed dataset. Verify that corrected scores are systematically higher (if \(\beta_k < 1\)) and that the transformation is applied correctly in the DAG.  
3. **Quantile Mapping validation:** Compute source quantiles from a dataset and define a uniform reference. Apply the mapping to a test set and check that the output distribution matches the reference (e.g., via histogram or Kolmogorov-Smirnov test). Also test edge cases: scores below the lowest or above the highest quantile should be handled (typically clipped or extrapolated).

## Open Questions the Paper Calls Out
1. **Automated calibration refresh:** How can MUSE automatically trigger and execute Quantile Mapping recalibrations in response to unseen, gradual distribution drift between scheduled model retraining events? The paper mentions future work on "Automated Calibration Refresh... based on a closed-loop distribution drift monitoring" but lacks specifics on drift metrics, thresholds, and safe autonomous update mechanisms in a latency-sensitive environment.
2. **Generalized Posterior Correction:** Can the Posterior Correction be generalized beyond undersampling bias correction to dynamically re-weight ensemble experts based on additional heuristics like validation performance, training data recency, or per-tenant volume? The current method is static and solely based on \(\beta_k\); adapting to dynamic expert quality or data staleness could improve ensemble robustness in adversarial multi-tenant settings.
3. **Long-term reference distribution trade-offs:** What are the operational trade-offs and failure modes of using a fixed reference distribution (R) as client business goals and data landscapes evolve over years? Changing R would require re-setting thresholds, which MUSE was designed to avoid. No analysis exists on a migration protocol or consequences if strategic objectives shift (e.g., from aggressive fraud capture to stricter false-positive limits).

## Limitations
- Undisclosed reference distribution R and cold-start Beta-mixture parameters impede exact replication and tuning.
- Quantile Mapping may misalign on sparse or new tenant data due to insufficient samples for accurate quantile estimation.
- Posterior Correction is sensitive to precise \(\beta_k\); errors from training logs or distribution shift cause calibration drift.
- Feature store integration specifics (latency guarantees, schema evolution, missing features) are not detailed.
- Routing assumes correct intent metadata; no mechanism to detect client-side changes or tampering.

## Confidence
- **Posterior Correction:** Medium (derivation is sound but limited independent validation; sensitive to \(\beta_k\) accuracy).
- **Quantile Mapping:** Medium-High (strong deployment evidence in Figure 4, monotonicity guarantees; but quantile estimation errors risk instability).
- **Intent-based Routing:** High (standard multi-tenant pattern; production scale demonstrates robustness).
- **Overall impact (fraud loss reduction, lead time gains):** Medium (plausible and correlated but not causally isolated from other system changes).

## Next Checks
1. **Quantile Mapping sensitivity:** Vary quantile count \(N \in \{100, 500, 1000, 5000\}\) for a fixed tenant; measure distribution alignment error (mean relative bin error). Identify elbow point for cost-accuracy trade-off.
