# OpenExtract: Automated Data Extraction for Systematic Reviews in Health

## Quick Facts
- **arXiv ID:** 2603.13338
- **Source URL:** https://arxiv.org/abs/2603.13338
- **Reference count:** 8
- **Primary result:** Achieves precision and recall >0.8 on a digital health SLR using a RAG pipeline with LLMs.

## Executive Summary
OpenExtract is an automated system for data extraction in systematic literature reviews (SLRs). It employs a retrieval-augmented generation (RAG) pipeline: scientific articles are chunked, relevant sections are retrieved using PubMedBERT embeddings, and a large language model (LLM) predicts answers from a predefined set of labels. Evaluated on 10 digital health papers (150 data entries), it achieved high precision and recall (>0.8) against human researchers, demonstrating the potential to scale SLR data extraction.

## Method Summary
The pipeline processes PDFs by extracting text and splitting into 1000-token chunks with 500-token overlap. Each chunk is embedded using the domain-specific PubMedBERT model. For each predefined data entry (query), the top-3 most relevant chunks are retrieved via cosine similarity. These chunks, along with the query and a list of output labels, are formatted into a strict JSON prompt and sent to an LLM via the OpenRouter API. The LLM is constrained to return only a JSON array of matching label IDs from the provided context. Performance is evaluated by comparing these predictions to human-extracted ground truth, calculating precision and recall based on label set matches.

## Key Results
- DeepSeek V3.1 (671B): Precision 0.820, Recall 0.820.
- Qwen2.5-72B: Precision 0.846, Recall 0.813.
- Qwen2.5-7B: Precision 0.624, Recall 0.564.
- All models exceeded a precision and recall of 0.8 except the smallest 7B model.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Retrieval-Augmented Generation (RAG) improves extraction accuracy by grounding LLM predictions in specific, retrieved article text.
- **Mechanism:** For each query, the system retrieves the top-3 most relevant 1000-token chunks (500-token overlap) using cosine similarity of embeddings. These chunks are injected into the LLM prompt as context, constraining the model to answer only from the provided text.
- **Core assumption:** The correct answer for a given data entry is contained within at least one of the retrieved text chunks.
- **Evidence anchors:**
  - The system "queries large language models (LLMs) to predict data entries based on relevant sections of scientific articles."
  - The design uses retrieval to "encourage the LLM to base its answers on the actual article, rather than relying on more general knowledge from its training data."
- **Break condition:** The ground truth answer is not present in any chunk (due to chunking boundaries, information in figures/tables, or text being outside the top-3 retrieved chunks).

### Mechanism 2
- **Claim:** Using a domain-specific embedding model (PubMedBERT) improves the relevance of retrieved chunks for biomedical literature.
- **Mechanism:** Article chunks and data entry queries are encoded into vector embeddings using PubMedBERT. The retrieval step ranks chunks by semantic similarity to the query, leveraging PubMedBERT's medical domain knowledge to better match terminology and concepts.
- **Core assumption:** A model fine-tuned on PubMed text will produce embeddings where semantically similar medical concepts are closer in vector space than a general model.
- **Evidence anchors:**
  - The system uses "a BERT model finetuned on PubMed... as a domain-specific embedding model to encode chunks and identify the top-3 most relevant chunks."
  - The approach is framed as enabling "domain adaptation, by adapting the pipeline to different domains by selecting appropriately fine-tuned text encoders."
- **Break condition:** The SLR domain is outside biomedical scope (e.g., materials science), where PubMedBERT's vocabulary and semantics are a poor fit.

### Mechanism 3
- **Claim:** Forcing the LLM to select answers from a predefined list of labels reduces hallucination and standardizes output format.
- **Mechanism:** The prompt explicitly lists all possible output labels for a data entry and instructs the LLM to return *only* a JSON array of correct option IDs, extracted solely from the provided context chunks.
- **Core assumption:** The set of predefined labels is exhaustive for the data entry; the correct answer is always one of the provided options.
- **Evidence anchors:**
  - The formatting prompt specifies: "If one or more options are correct, return ONLY a JSON array of the correct option IDs... Return the IDs exactly as provided in ANSWERS."
  - The precision/recall calculation compares LLM-predicted label sets to human-extracted answers, implying output is constrained to the label set.
- **Break condition:** The true answer requires an option not in the predefined label list, or the context requires synthesis/interpretation beyond selecting provided options.

## Foundational Learning
- **Concept: Retrieval-Augmented Generation (RAG)**
  - **Why needed here:** The entire pipeline's efficacy depends on retrieving the correct context. Understanding the trade-off between retrieval recall (finding all relevant chunks) and precision (avoiding irrelevant chunks) is key.
  - **Quick check question:** If the true answer appears in the 4th-ranked retrieved chunk, what is the likely outcome for that data point?
- **Concept: Text Chunking Strategies for LLM Context Windows**
  - **Why needed here:** The system uses overlapping 1000-token chunks with a 500-token overlap. This sliding window design addresses BERT's 512-token limit and aims to prevent answers from being split across chunks.
  - **Quick check question:** What is the primary purpose of the 500-token overlap between 1000-token chunks?
- **Concept: Prompt Engineering for Structured Output**
  - **Why needed here:** The strict JSON prompt design converts an open-ended LLM into a deterministic classifier over a fixed label set. Prompt misformatting would break automated evaluation.
  - **Quick check question:** How does the instruction "Do NOT include any text besides the JSON array" support the pipeline's automation goal?

## Architecture Onboarding
- **Component map:** PDF/HTML Parser -> Text Chunker (1000-token, 500-overlap) -> Embedding Encoder (PubMedBERT) -> Vector Store (per-article chunks) -> Retriever (top-3 cosine similarity) -> Prompt Builder (query + labels + context) -> LLM API (OpenRouter) -> JSON Parser -> Output.
- **Critical path:** Article ingestion must complete chunking and embedding *before* any data entry queries can be processed. The retrieval step is stateless per query but depends on the pre-computed chunk embeddings.
- **Design tradeoffs:**
  - **Chunk size (1000 tokens) vs. context coherence:** Larger chunks may contain more answer context but increase noise; smaller chunks risk splitting semantic units. The 500-token overlap is a compromise to capture boundaries.
  - **Top-k retrieval (k=3) vs. cost/latency:** More chunks provide more context but increase prompt length and LLM cost. Three is a heuristic balance.
  - **Label list exhaustiveness vs. review scope:** An exhaustive label list minimizes false negatives but requires meticulous SLR design up-front.
- **Failure signatures:**
  - Empty JSON array returned: LLM found no matching label in context.
  - Non-JSON output: Prompt instruction failed; LLM added explanatory text.
  - Consistently low scores on a specific data entry: Likely label set is incomplete or answer is in a figure/table.
  - High inter-LLM agreement but low human agreement (as seen in Table 1): Indicates systematic LLM bias or misinterpretation of the query/labels.
- **First 3 experiments:**
  1. **Chunking sanity check:** Process a sample paper, count chunks, and inspect boundaries around key methods/results sections to ensure critical sentences aren't orphaned.
  2. **Retrieval validation:** For a known data entry (e.g., "study design"), manually check if the top-3 retrieved chunks contain the phrase describing the design (e.g., "randomized controlled trial").
  3. **Prompt compliance test:** Run the LLM on a trivial query with a context that contains the exact answer phrase. Verify it returns *only* the correct JSON ID, with no extra text.

## Open Questions the Paper Calls Out
- **Open Question 1:** Does the performance of OpenExtract (precision/recall >0.8) generalize to larger, more diverse systematic literature reviews beyond the single digital health case study with only 10 evaluated papers?
- **Open Question 2:** Can incorporating multimodal data extraction (parsing figures, tables, and non-textual elements) significantly improve the accuracy and coverage of data extraction for entries that are typically presented visually in biomedical literature?
- **Open Question 3:** To what extent do the observed discrepancies between LLM outputs and human annotators stem from inadequate prompt specification versus inherent ambiguity in the data entry definitions, and can prompt engineering or structured output constraints reliably bridge this reliability gap?
- **Open Question 4:** How do the cost, computational requirements, and extraction performance trade-off vary across the spectrum of available open-weight and proprietary LLMs (beyond the three tested) for this specific RAG-based data extraction task, and is there a clear optimal model size or architecture for this application?

## Limitations
- Evaluation scale is small (10 papers, 150 entries), limiting statistical power and generalizability.
- Exact dataset and prompt templates are not fully described in the paper, making faithful replication dependent on GitHub repository availability.
- Performance varies significantly across LLM sizes (e.g., Qwen-72B vs. 7B), suggesting robustness issues not explored.
- Break conditions (e.g., answers outside top-3 chunks, incomplete label sets) are theoretically identified but not empirically quantified.

## Confidence
- **RAG improves accuracy by grounding LLM in text:** Medium (plausible but no ablation study isolating retrieval impact).
- **PubMedBERT enhances retrieval relevance:** Medium (domain adaptation logic strong, but no comparison to general embedding models).
- **Structured JSON prompts reduce hallucination:** High (output constraints are explicit and directly enable automated scoring).

## Next Checks
1. **RAG ablation:** Process queries with full-text input (no retrieval) versus RAG to isolate retrieval's contribution to precision/recall.
2. **Embedding model comparison:** Replace PubMedBERT with a general model (e.g., Sentence-BERT) and measure change in retrieval recall of ground-truth chunks.
3. **Label exhaustiveness test:** Introduce an "Other" option in the label set and record recall drop, quantifying failures from incomplete label lists.
