# TurkicNLP: An NLP Toolkit for Turkic Languages
## Quick Facts
*   **arXiv ID:** 2602.19174
*   **Source URL:** https://arxiv.org/abs/2602.19174
*   **Reference Count:** 40
*   **Primary Result:** A unified Python library integrates rule-based and neural NLP tools for 24 Turkic languages, delivering significant accuracy gains in morphological analysis and parsing while exposing severe tokenization inefficiencies in existing LLMs.

## Executive Summary
Turkic languages, spoken by millions across 24 distinct languages using four different scripts, suffer from highly fragmented NLP tooling. This fragmentation hinders research and practical application development. The TurkicNLP toolkit addresses this by providing a single Python API that unifies several existing resources—including Apertium's rule-based finite-state transducers and neural models from Stanza, Glot500, and NLLB—with automatic script detection and transliteration. It outputs standard CoNLL-U format and supports core tasks like tokenization, morphology, POS tagging, parsing, NER, embeddings, and translation. Evaluations demonstrate that its neural morphological analyzer outperforms the Apertium FST (68% vs. 53% detection accuracy) and that its Glot500-based parser exceeds average per-language Stanza models in Labeled Attachment Score (63.6% vs. 56.4%). Furthermore, analysis reveals that current LLM tokenizers are exceptionally inefficient for Turkic languages, with a fertility rate reaching 6.85 tokens per word.

## Method Summary
The library’s construction is an integration engineering effort rather than a novel model proposal. It wraps and standardizes the outputs of several established NLP frameworks: Apertium for rule-based morphological analysis, Stanza for per-language neural pipelines, Glot500 for multilingual parsing, and NLLB for translation. A key technical contribution is the implementation of automatic script detection and transliteration modules to handle the Latin, Cyrillic, Arabic, and Old Turkic scripts seamlessly. All components are orchestrated through a common Python interface that ensures consistent preprocessing, processing, and output formatting (CoNLL-U), abstracting the heterogeneity of the underlying tools and language resources.

## Key Results
*   The integrated neural morphological analyzer achieves 68% detection accuracy, a 15-point absolute improvement over the Apertium FST baseline (53%).
*   The Glot500-based multilingual parser yields a 63.6% LAS, exceeding the average performance of individually trained Stanza models (56.4% LAS) across Turkic languages.
*   Tokenizer analysis for Turkic languages shows extreme inefficiency in existing LLMs, with up to 6.85 tokens required to represent a single word, highlighting a major preprocessing bottleneck.

## Why This Works (Mechanism)
TurkicNLP succeeds by strategically combining the strengths of rule-based and neural approaches within a unified integration layer. Rule-based FSTs from Apertium offer high precision and interpretability for morphology, especially in low-resource scenarios, but have limited recall. Neural models (Stanza, Glot500) provide better generalization and handle more complex syntactic structures like parsing, but require substantial training data. The toolkit’s architecture allows it to leverage Apertium’s comprehensive linguistic knowledge where available while falling back to or supplementing with neural models. The automatic script detection and transliteration module is foundational, as it removes a major practical barrier: users can input text in any of the four scripts without manual conversion, enabling the pipeline to function on real-world, heterogeneous text data.

## Foundational Learning
*   **Agglutinative Morphology:** Turkic words are formed by stringing together multiple morphemes, leading to very long, sparse word forms. *Why needed:* Standard tokenizers and models struggle with this high type-to-token ratio. *Quick check:* Apply a simple whitespace tokenizer to a Turkish/Kazakh sentence and count unique word forms versus total tokens.
*   **Script Diversity & Historical Layers:** Languages use Latin, Cyrillic, Arabic, or Old Turkic scripts, often with mixed usage in digital spaces. *Why needed:* Script choice is not language-deterministic and requires normalization. *Quick check:* Collect social media text for a single language (e.g., Uzbek) and manually classify script instances.
*   **FST-Based Linguistic Engineering:** Finite-state transducers encode morphological grammars as state machines. *Why needed:* Provides rule-based, explainable analysis crucial for low-resource languages. *Quick check:* Install `apertium` and run analysis on a complex Kazakh verb form to see explicit morpheme segmentation.
*   **Multilingual Model Generalization:** Models like Glot500 are trained on hundreds of languages to share representations. *Why needed:* Allows a single model to serve many Turkic languages, bypassing the need for per-language training data. *Quick check:* Test a Glot500 parser on a language it was not explicitly fine-tuned for (e.g., Tatar) and measure LAS.
*   **CoNLL-U Standardization:** A universal dependency format for annotated corpora. *Why needed:* Ensures interoperability between different toolkits and downstream tasks. *Quick check:* Convert a TurkicNLP output to CoNLL-U and verify field consistency against the UD guidelines.
*   **Tokenization Fertility:** The number of tokens a subword model (like BPE) produces per word. *Why needed:* High fertility indicates poor compression and inefficiency for a language family. *Quick check:* Calculate fertility for a Turkic language using a common LLM tokenizer (e.g., GPT-2) versus an agglutinative-aware tokenizer.

## Architecture Onboarding
**Component Map:** Raw Text -> Script Detection -> Transliteration (Optional) -> Tokenization -> Morphological Analysis (FST or Neural) -> POS Tagging -> Dependency Parsing -> CoNLL-U Output. For translation: Raw Text -> Script Detection -> Transliteration -> NLLB -> Target Text.

**Critical Path:** The most resource-intensive and accuracy-determining path is: Script Detection -> Tokenization -> (Neural Morphology + POS) -> Neural Parsing (Glot500). For fully supported languages (Turkish, Kazakh), all steps are neural; for others, morphology may default to Apertium FST.

**Design Tradeoffs:**
*   *Rule-based vs. Neural:* FSTs offer precision and no training data need but poor recall on unseen forms. Neural models offer better recall but require data and compute.
*   *Unified API vs. Native Performance:* The abstraction layer simplifies use but may not expose the full configurability or latest features of individual backends (e.g., Stanza).
*   *Coverage vs. Accuracy:* Supporting 24 languages means some have only embeddings or FST analysis, trading full pipeline depth for breadth.

**Failure Signatures:**
1.  Incorrect script detection (e.g., Cyrillic text flagged as Latin) leads to failed transliteration or model inference.
2.  FST analysis returns "???" or empty for a valid word, indicating a lexicon gap.
3.  Neural parser produces non-projective trees or extremely low LAS, suggesting domain mismatch (e.g., model trained on news, applied to social media).

**Three First Experiments:**
1.  Run the full pipeline on a mixed-script Uzbek sentence (e.g., with both Cyrillic and Latin words) and verify script detection and consistent morphological output.
2.  Compare the output of the FST analyzer vs. the neural analyzer for a single complex Kazakh noun case; note differences in segmentation and feature tagging.
3.  Use the tokenization module on a 100-word Turkish paragraph and calculate fertility using the default tokenizer; compare against a whitespace baseline to quantify subword overhead.

## Open Questions the Paper Calls Out
The paper does not explicitly list open research questions. However, the evaluation raises several implicit questions about the generalizability of the reported performance gains and the underlying causes of the observed tokenization inefficiency.

## Limitations
*   **Evaluation Context Opaqueness:** Performance comparisons lack details on test set composition, domain matching, and exact model versions, making independent replication and fair comparison difficult.
*   **Coverage Asymmetry:** Only Turkish and Kazakh have confirmed "full pipelines"; the functionality and quality for the other 22 supported languages are unspecified and likely vary widely.
*   **Script Robustness Unquantified:** The accuracy of automatic script detection and transliteration across all four scripts, especially for low-resource languages with irregular or historical script usage, is not measured.

## Confidence
*   **Unified API & Integration Claim:** **High.** This is a direct software engineering achievement verifiable by installing and using the library.
*   **Performance Improvements (Neural vs. FST/Stanza):** **Medium.** The reported metrics are specific but require validation on the same test data with identical setups to confirm the magnitude of the gain.
*   **Broad Language & Script Support:** **High.** The list of 24 languages and four scripts is a factual statement of scope. The support level declarations (e.g., "parsing for 10") are also factual claims about resource inclusion.
*   **Tokenizer Inefficiency Finding:** **Low-Medium.** The high fertility figure is plausible but requires scrutiny of the methodology (which tokenizers, which texts, definition of "word") to assess its generality across the Turkic family.

## Next Checks
1.  **Replicate Core Evaluations:** Re-run the morphological analysis (68% vs. 53%) and parsing (63.6% vs. 56.4% LAS) experiments using the *exact* test data splits, preprocessing, and model checkpoints (Apertium version, Stanza language models, Glot500 checkpoint) reported or provided by the authors.
2.  **Audit Tokenizer Fertility:** Apply the same tokenization analysis (using the same LLM tokenizers cited) to diverse, genre-balanced text corpora (news, social media, Wikipedia) for all 24 languages to verify the fertility range and identify which morphological features (e.g., case stacking, vowel harmony) correlate with highest subword splits.
3.  **End-to-End Pipeline on Low-Resource Languages:** Execute the complete TurkicNLP pipeline (tokenization to parsing) on a held-out, multi-domain dataset for at least two languages beyond the fully-supported Turkish and Kazakh (e.g., Azerbaijani, Uyghur) to quantify real-world performance degradation and identify the weakest pipeline link.
