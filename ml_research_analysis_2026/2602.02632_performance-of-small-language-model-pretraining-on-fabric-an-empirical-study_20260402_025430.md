# Performance of Small Language Model Pretraining on FABRIC: An Empirical Study

## Quick Facts
- **arXiv ID:** 2602.02632
- **Source URL:** https://arxiv.org/abs/2602.02632
- **Reference count:** 40
- **Primary result:** Alpa's Pipeshard parallelism (combined intra- and inter-operator) yields highest throughput in high-latency distributed clusters, while data parallelism outperforms in low-latency single-site settings.

## Executive Summary
This paper investigates pretraining small language models under constrained academic infrastructure, where GPUs are geographically distributed with high network latency. The authors evaluate various parallelism strategies—data, intra-operator (tensor), inter-operator/pipeline, and their combinations—using Alpa's Pipeshard on GPT-2 models across homogeneous and heterogeneous FABRIC clusters. Key findings show that Pipeshard consistently achieves superior training performance under high latency (e.g., 57 ms) due to its reliance on point-to-point communication, whereas data parallelism excels in low-latency single-site clusters. However, Pipeshard incurs higher memory overhead and may fail on heterogeneous hardware, prompting the proposal of a systematic selection algorithm to choose the optimal technique based on cluster topology and model constraints.

## Method Summary
The study conducts controlled experiments on the FABRIC testbed, allocating GPU slices at different sites with configurable network latency (via L2STS). For each cluster configuration (homogeneous/heterogeneous, single/multi-site), the authors train GPT-2 small, medium, and large models using four parallelism modes: pure data parallelism, pure intra-operator parallelism (Shard), pure inter-operator/pipeline parallelism, and Alpa's combined Pipeshard. Throughput is measured in TFLOP/s, and memory consumption and plan feasibility are recorded. The evaluation spans multiple cluster setups (e.g., TACC-TACC, UTAH-GPN, UTAH-MASS) to isolate the impact of latency and hardware heterogeneity.

## Key Results
- Pipeshard (combined intra- and inter-operator parallelism) achieves the highest training throughput under high network latency (e.g., 2.32 vs. 0.44 TFLOP/s for gpt2L at 57 ms latency).
- In low-latency single-site clusters, traditional data parallelism outperforms Pipeshard (e.g., 15.74 vs. 12.17 TFLOP/s on 2 RTX GPUs).
- Pipeshard has higher memory requirements and can fail (OOM) on heterogeneous clusters where ZeRO2 (a memory-optimized data parallelism variant) succeeds.

## Why This Works (Mechanism)
### Mechanism 1: Pipeshard’s Latency Robustness via Point-to-Point Communication
- **Claim:** Alpa’s Pipeshard (combined intra- and inter-operator parallelism) maintains higher training throughput as network latency increases because it primarily uses point-to-point communication between pipeline stages, which is less sensitive to latency than collective communication.
- **Mechanism:** Pipeline parallelism splits the computational graph into stages assigned to GPU meshes. Forward/backward passes are pipelined across microbatches, with communication between stages being point-to-point (send/receive). This avoids the all-to-all synchronization overhead of collective operations (e.g., all-reduce in data parallelism). As latency rises, collective costs grow superlinearly with participants, while point-to-point costs increase linearly per link.
- **Core assumption:** Network latency dominates communication overhead in geographically distributed clusters (e.g., across FABRIC sites using L2STS), and the cost model for collective operations scales worse with latency than point-to-point.
- **Evidence anchors:** 
  - Abstract: “Alpa’s execution plans that collectively optimized intra-operator and inter-operator/pipeline parallelism consistently performed the best when GPUs were geographically distributed. This was especially true when the network latencies were in 10’s of milliseconds.”
  - Section IV.F, Table II: `Shard` (pure intra-operator) and `Data` (all-reduce) execution times degrade sharply with latency (e.g., `Data` 41 min → 1375 min), while `Pipeshard` degrades modestly (29 min → 100 min).
- **Break condition:** When network latency is trivial (e.g., <1 ms on a single site with NVLink), the overhead of pipeline staging and increased memory usage outweighs the benefit, making data parallelism faster.

### Mechanism 2: Data Parallelism Advantage in Low-Latency Clusters
- **Claim:** Data parallelism (`Data`, `ZeRO2`) outperforms Pipeshard in low-latency, single-site clusters because collective communication (all-reduce) is extremely efficient on tightly-coupled GPUs and avoids Pipeshard’s pipeline bubble and memory overhead.
- **Mechanism:** Data parallelism replicates the full model on each GPU and synchronizes gradients via all-reduce after each step. On a single site, GPUs communicate over high-bandwidth, low-latency interconnects (e.g., PCIe/NVLink), making all-reduce very fast. Pipeshard introduces pipeline “bubbles” (idle time) and requires storing activations for multiple microbatches across stages, increasing memory pressure and sometimes reducing effective throughput.
- **Core assumption:** In a single VM or single-site cluster, inter-GPU communication latency and bandwidth are sufficiently good that the overhead of pipeline parallelism (bubbles, extra memory) dominates its potential benefits.
- **Evidence anchors:**
  - Abstract: “However, in single-site clusters with low latency, traditional data parallelism often performed better (e.g., 15.74 vs. 12.17 TFLOP/s on 2 RTX GPUs).”
  - Section IV.A, TACC-TACC: For `gpt2m` on 2 RTX GPUs (single VM), `Data` achieved 15.74 TFLOP/s vs `Pipeshard`’s 12.17 TFLOP/s.
- **Break condition:** When the model size exceeds the memory capacity of a single GPU (or a small cluster using only data parallelism), model parallelism (intra-operator) or pipeline parallelism becomes necessary, and Pipeshard may become viable even with moderate latency if memory permits.

### Mechanism 3: Pipeshard’s Memory Overhead and Heterogeneity Sensitivity
- **Claim:** Pipeshard fails on heterogeneous GPU clusters or when GPU memory is limited because its memory allocation strategy assumes homogeneous mesh capacities and requires storing full stage states, activations, and optimizer states across multiple GPUs simultaneously.
- **Mechanism:** Pipeshard partitions the model into stages assigned to 2D meshes (homogeneous GPU groups). Each stage’s memory consumption includes model parameters, gradients, optimizer states, and activations for multiple microbatches. The automatic plan search does not fully account for heterogeneous memory capacities across meshes. If any GPU in a stage’s mesh lacks sufficient memory for its partition (including activation checkpoints), execution fails with out-of-memory (OOM). `ZeRO2` succeeds by sharding optimizer states/gradients more flexibly across data-parallel groups, often requiring less per-GPU memory.
- **Core assumption:** The automatic parallel plan generator in Alpa optimizes for throughput under the constraint of homogeneous device meshes and may not find a feasible plan when memory capacities are mismatched or tightly constrained.
- **Evidence anchors:**
  - Abstract: “Pipeshard had higher memory requirements, sometimes failing where ZeRO2 succeeded.”
  - Section IV.D, BRIS-STAR: Heterogeneous cluster (2 A30 + 2 RTX): `Pipeshard` succeeded for `gpt2L` while `Data/Shard/ZeRO2` failed. Conversely, [section IV.C, UTAH-MASS] homogeneous 4 RTX: `Pipeshard` worked for `gpt2L`. In [section IV.G summary] “When Pipeshard failed in a two-site GPU cluster due to memory issues (e.g., when using heterogeneous GPU hardware), ZeRO2 was able to execute successfully.”
- **Break condition:** When all GPUs in the intended cluster have sufficient and homogeneous memory to accommodate the largest stage partition plus microbatch activations, or when the model is small enough to fit with simpler parallelism.

## Foundational Learning
- **Concept: Parallelism Taxonomy (Data, Tensor/Intra-Operator, Pipeline/Inter-Operator)**
  - *Why needed here:* The paper’s core comparison rests on these three fundamental strategies for distributing a model’s computation and memory. Understanding what each parallelizes (data batches, tensor dimensions, model layers) is essential to interpret why one might outperform another given cluster topology.
  - *Quick check question:* If you split a 12-layer Transformer model across 3 GPUs, assigning layers 1-4, 5-8, 9-12 to each, what type of parallelism is this?

- **Concept: Collective vs. Point-to-Point Communication**
  - *Why needed here:* The key performance differentiator in high-latency clusters is the communication pattern: `Pipeshard` relies on point-to-point between pipeline stages, while `Data`/`Shard` rely on collective operations (all-reduce, all-gather). Their scaling with latency underpins the main findings.
  - *Quick check question:* Why might an all-reduce operation across 4 GPUs on different network segments be more sensitive to latency than a send/receive between two GPU pairs?

- **Concept: Memory-Throughput Trade-off in Distributed Training**
  - *Why needed here:* The “higher memory requirements” of `Pipeshard` explain its failure modes. Engineers must balance achieved TFLOP/s against the per-GPU memory footprint, which dictates feasibility on a given cluster.
  - *Quick check question:* How does pipeline parallelism (with microbatches) increase activation memory compared to data parallelism?

## Architecture Onboarding
- **Component map:** User/Experimenter -> FABRIC Portal -> Ray Cluster -> Alpa -> GPU Hardware
- **Critical path:** Slice provisioning → VM/GPU attachment → Ray cluster setup → Alpa plan generation (per technique) → Training loop execution (20 epochs) → TFLOP/s measurement.
- **Design tradeoffs:**
  - Latency vs. Parallelism: High WAN latency penalizes collective-heavy (`Data`, `Shard`) plans; favors pipeline (`Pipeshard`).
  - Memory vs. Scale: `Pipeshard` enables larger models across more GPUs but per-GPU memory use is higher; `ZeRO2` reduces memory via optimizer sharding but suffers in high latency.
  - Homogeneity: Heterogeneous GPUs (different memory sizes/types) break `Pipeshard`’s homogeneous mesh assumption; may force fallback to `ZeRO2`.
  - GPU Count: More GPUs don’t guarantee speedup; overhead can outweigh compute gain (e.g., single-VM `Data` faster than multi-VM `Pipeshard` for small models).
- **Failure signatures:**
  - OOM (Out-of-Memory): Most common for `Pipeshard` on heterogeneous clusters or large models (`gpt2L`). `ZeRO2` often survives where others fail.
  - Low TFLOP/s (<1): Symptom of high-latency cluster using `Data`/`Shard`/`ZeRO2`; check network latency (ping) and consider `Pipeshard`.
  - Plan Generation Failure: Alpa may fail to find a feasible plan if model too large for available GPU memory even with any parallelism.
- **First 3 experiments:**
  1. **TACC-TACC (single-site, 4 GPUs: 2 RTX + 2 T4, 0.1ms latency):** Benchmark all techniques. Expect `Pipeshard` wins on 4 GPUs, but `Data` wins on 2 GPUs (single VM). Identifier: low latency tests baseline.
  2. **UTAH-GPN (two-site, 4 GPUs: 2 RTX + 2 T4, 20ms latency):** Introduce moderate WAN latency. Expect `Pipeshard` dominance on 4 GPUs becomes clear; `Data`/`Shard` degrade severely.
  3. **UTAH-MASS (two-site, 4 GPUs: 4 RTX, 57ms latency):** Higher latency with homogeneous GPUs. Expect `Pipeshard` still best, `Shard`/`Data` very poor. Test if `Pipeshard` can handle `gpt2L` (larger model) given more total memory.

## Limitations
- Model scale: Findings based on GPT-2 (small/medium/large) may not generalize to modern LLMs (>10B parameters), where memory/communication bottlenecks differ.
- Cluster representativeness: Results are tied to FABRIC’s specific hardware (RTX/T4/A30) and network emulation (L2STS); real-world WAN latency/jitter could behave differently.
- Memory analysis: "Higher memory requirements" for Pipeshard is asserted but not fully profiled (e.g., per-stage activation storage, optimizer state distribution).

## Confidence
- Mechanism 1 (Pipeshard latency robustness): High
- Mechanism 2 (Data parallelism advantage in low-latency): High
- Mechanism 3 (Pipeshard memory failures): Medium

## Next Checks
1. **Scale validation:** Replicate key experiments with ≥6B parameter models (e.g., GPT-3 scale) on the same FABRIC clusters to test if Pipeshard’s latency tolerance persists as model memory grows.
2. **Framework comparative:** Run identical cluster/topology setups using alternative parallelism frameworks (e.g., Megatron-LM, DeepSpeed) to isolate Alpa-specific optimizations from fundamental parallelism trade-offs.
3. **Memory profiling:** Instrument training runs to measure per-GPU memory breakdown (parameters, gradients, optimizer states, activation checkpoints) for each parallelism strategy, especially in heterogeneous configurations.
