# Case-Aware LLM-as-a-Judge Evaluation for Enterprise-Scale RAG Systems

## Quick Facts
- **arXiv ID**: 2602.20379
- **Source URL**: https://arxiv.org/abs/2602.20379
- **Reference count**: 9
- **Primary result**: A case-aware LLM-as-a-Judge framework exposes critical RAG workflow tradeoffs (e.g., gpt-oss vs. LLaMA on long queries) missed by generic metrics.

## Executive Summary
Enterprise multi-turn RAG systems suffer from workflow-aligned failures like case misidentification and resolution misalignment, which standard evaluation frameworks overlook. This paper introduces a case-aware LLM-as-a-Judge that conditions on case metadata, conversation history, and retrieved evidence to score eight operational metrics. A severity-aware protocol prevents score inflation, and a weighted aggregate enables monitoring and regression testing. In a comparative study, the framework reveals that gpt-oss significantly outperforms LLaMA on long diagnostic queries—a tradeoff hidden from proxy metrics. Human validation shows 84–91% agreement on high-risk dimensions, and metric-level outputs enable targeted engineering interventions.

## Method Summary
The evaluation requires per-turn records containing conversation history, current query, case subject/description, retrieved chunks, model answer, and optional reference. A single deterministic LLM call (GPT-4, temperature=0) produces continuous [0,1] scores and justifications for eight metrics: hallucination, retrieval correctness, context sufficiency, helpfulness, answer type fit, identifier integrity, case issue identification, and resolution alignment. Outputs are validated against a JSON schema; the final score is a weighted sum (e.g., hallucination weight 0.20). Aggregation can be per-turn or per-conversation. The design is batch-friendly and intended for release gating and regression testing.

## Key Results
- On long diagnostic queries, gpt-oss significantly outperforms LLaMA (weighted aggregate 0.8099 vs. 0.7136, p=0.0011), demonstrating superior workflow alignment.
- Metric-level scores expose specific failure modes (e.g., resolution alignment, identifier integrity) that generic retrieval or answer matching metrics miss.
- Human validation shows 84–91% agreement on high-risk dimensions, with disagreements concentrated in borderline cases involving partial compliance or implicit identifiers.

## Why This Works (Mechanism)
The framework works by grounding the LLM judge in enterprise-specific context—case metadata, multi-turn history, and retrieved evidence—that generic evaluators ignore. This conditioning allows the judge to detect subtle workflow failures like using the wrong case identifier or proposing a resolution that violates implicit business rules. The severity-aware protocol (mapping scores to bands) curbs inflation by penalizing high-severity errors more heavily, while the weighted aggregate balances operational priorities (e.g., hallucination is weighted highest). The single-call, deterministic setup ensures reproducibility for CI/CD pipelines.

## Foundational Learning
- **LLM-as-a-Judge**: Uses a capable LLM to simulate human evaluation; needed to assess nuanced, multi-dimensional quality beyond automated metrics. *Quick check*: Verify judge consistency across model variants and against a human sample.
- **Case-aware conditioning**: Judges must incorporate case subject/description and multi-turn history; needed to surface workflow-specific errors. *Quick check*: Ablate case metadata inputs and measure score degradation on identifier/resolution metrics.
- **Severity-aware scoring**: Maps continuous scores to severity bands (e.g., Critical/Minor); needed to prioritize high-impact failures. *Quick check*: Audit band thresholds against retrospective operational impact data.
- **Weighted aggregation**: Fixed weights reflect business priorities (e.g., hallucination 0.20); needed to produce a single release-gating signal. *Quick check*: Perform sensitivity analysis by varying weights and confirming model rankings remain stable.
- **Deterministic prompting**: Single API call with temperature=0 and strict JSON output; needed for reproducible regression testing. *Quick check*: Run multiple times on same input; ensure identical scores.
- **Evidence grounding**: Judge constrained to provided chunks and history; needed to prevent reliance on parametric knowledge. *Quick check*: Introduce contradictory external knowledge in prompt; judge should ignore it.

## Architecture Onboarding
Component map: Data Prep (format turn records) -> Judge Prompt (string with all fields) -> LLM API (GPT-4 call) -> JSON Validation (schema check + retry) -> Aggregation (apply weights, sum). Critical path: from raw turn data to final S_final score. Design tradeoffs: Determinism and simplicity (single call) vs. rigidity (prompt engineering heavily influences scores) and fixed weights (may not adapt to all risk profiles). Failure signatures: Malformed JSON outputs, score inflation (e.g., all metrics near 1.0), inconsistent multi-turn handling (history truncation or misformatting). First three experiments: (1) Test judge prompt with a small synthetic dataset containing known error types (e.g., wrong identifier) to verify metric sensitivity. (2) Run validation on JSON outputs; log and classify any schema violations. (3) Compare scores using GPT-4 and a smaller instruction model (e.g., Llama-3.1-8B) to assess judge stability and cost-quality tradeoff.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: To what extent does the proposed case-aware evaluation framework generalize across diverse enterprise domains (e.g., healthcare, finance) with differing workflow constraints and identifier schemas?
- **Basis in paper**: The authors state that "rubric calibration and metric weights may require adjustment across different organizations, industries, and risk tolerances" (Section 9) and that evaluation relies on "high-quality case fields" (Section 9).
- **Why unresolved**: The empirical study was conducted on a limited set of enterprise storage/infrastructure product families (Appendix D). The framework's core premise—conditioning on case metadata and workflow—may behave differently in domains with radically different operational protocols, regulatory constraints, or identifier structures (e.g., patient IDs vs. error codes). The authors do not test cross-domain transferability.
- **What evidence would resolve it**: A multi-domain study applying the same judge prompt and weights to evaluator conversations from at least three distinct enterprise verticals (e.g., IT support, healthcare triage, financial compliance), measuring metric stability (e.g., inter-judge agreement, score distribution shifts) and the need for domain-specific rubric recalibration.

### Open Question 2
- **Question**: How reliably does the LLM judge distinguish nuanced, high-severity failure modes (e.g., Resolution Alignment violations) from borderline, partially correct responses in multi-turn workflows?
- **Basis in paper**: Human validation shows 84% agreement on Resolution Alignment, with "disagreements occurring primarily in borderline cases involving partially correct remediation steps or implicitly referenced identifiers" (Section 8.7).
- **Why unresolved**: The framework's utility for release gating hinges on accurate detection of subtle workflow breaches. The paper identifies borderline cases as a primary source of judge-human disagreement but does not analyze the specific linguistic or contextual features causing ambiguity. This limits trust in the metric for high-stakes decisions where partial correctness has major operational impact.
- **What evidence would resolve it**: A targeted analysis of the 16% of sampled turns where the judge and humans disagreed on Resolution Alignment, categorizing the failure patterns (e.g., implicit vs. explicit constraints, prior turn context ambiguity). This should be coupled with an ablation study on prompt design to see if adding explicit definitions of "partial compliance" improves human-judge concordance.

### Open Question 3
- **Question**: Can the severity-aware scoring protocol and fixed aggregation weights remain stable and diagnostic when applied to heterogeneous enterprise cases with vastly different lengths, complexities, and risk profiles?
- **Basis in paper**: The authors propose a single set of default weights (Figure 2) and severity bands (Appendix B) and claim conclusions are stable under weight variations (Section 6). However, the evaluation dataset only includes "short" and "long" queries, and the severity band definitions are presented as general recommendations without empirical validation across a spectrum of risk tiers (e.g., low-risk configuration queries vs. high-risk production outage triage).
- **Why unresolved**: Enterprise environments contain cases where a minor Identifier Integrity failure might be critical (e.g., a corrupted production command) versus a moderate Hallucination that is harmless (e.g., a generic best-practice suggestion). A fixed weighting scheme may not reflect this operational reality, potentially leading to score inflation or deflation that masks true risk. The paper does not investigate weight sensitivity across a risk-stratified case sample.
- **What evidence would resolve it**: An experiment stratifying evaluated cases by operational risk tier (e.g., using retrospective impact analysis: escalation rate, mean time to resolution). For each tier, re-run the evaluation with tier-optimized weights (derived from expert input) and compare the predictive validity of S_final against actual operational outcomes (e.g., case escalation). This would test whether a single weight profile is sufficient or if adaptive weighting is necessary.

### Open Question 4
- **Question**: How does the case-aware framework's discriminative power and diagnostic clarity change when evaluating smaller, cost-efficient models (e.g., 7B-13B parameter models) commonly deployed in resource-constrained enterprise settings?
- **Basis in paper**: The comparative study uses only two large models: Llama-3.3-70B-Instruct and "gpt-oss-120b" (Section 7.3). The authors state the comparison is "intentionally heterogeneous," but all tested models are at the extreme high end of parameter scale. The framework's ability to expose "enterprise-critical tradeoffs" (Abstract) is thus only validated for top-tier model capabilities.
- **Why unresolved**: Many enterprises deploy smaller, domain-fine-tuned models for cost and latency reasons. These models may exhibit different failure profiles (e.g., more severe hallucination, weaker multi-turn memory) that could interact uniquely with the eight metrics. The framework's ability to provide actionable signals for improving such models is unknown. For instance, would Retrieval Correctness dominate S_final for small models, or would Identifier Integrity failures become the primary differentiator?
- **What evidence would resolve it**: Replicate the study's protocol (Section 7) with a diverse set of models spanning parameter scales (e.g., 7B, 13B, 34B, 70B+) and architectures (e.g., dense vs. MoE). Analyze how the pairwise separation (like in Table 2) and the per-metric score profiles change with model scale. Specifically, check if the framework's "actionable signals" (Section 8.6) remain interpretable and non-redundant for weaker models.

## Limitations
- Framework design and metrics are specialized for enterprise support workflows; generalizability to other multi-turn domains (e.g., creative chat, education) is untested.
- Reported comparative results depend on the unreleased proprietary dataset and the exact judge prompt/rubrics, which could affect score calibration and ranking stability.
- Human-judge agreement is lower on borderline cases (e.g., partial resolution alignment), limiting trust in high-stakes release decisions.

## Confidence
- **High**: The framework's design (case-aware inputs, eight metrics, severity bands, aggregation weights) is clearly specified and reproducible given the artifacts.
- **Medium**: The reported comparative results (gpt-oss vs. LLaMA advantage) due to unknown prompt/rubric details and dataset characteristics.
- **Low**: Cross-domain generalizability beyond the studied enterprise storage/infrastructure support domain.
