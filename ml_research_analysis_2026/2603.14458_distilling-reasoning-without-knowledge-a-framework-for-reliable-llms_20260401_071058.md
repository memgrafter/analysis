# Distilling Reasoning Without Knowledge: A Framework for Reliable LLMs
## Quick Facts
- arXiv ID: 2603.14458
- Source URL: https://arxiv.org/abs/2603.14458
- Reference count: 40
- Primary result: A supervised student planner achieves 10.8% accuracy at 27.8 seconds average latency on SEAL-0, significantly outperforming monolithic and prompted baselines while using a small, fast model.

## Executive Summary
Fact-seeking question answering with LLMs suffers from hallucinations, especially for up-to-date or conflicting information. This work proposes a modular framework that explicitly separates planning, retrieval, extraction, and aggregation. A lightweight student planner is trained via teacher-student supervision to generate structured decompositions containing only abstract reasoning steps and atomic fact requests, without factual answers. At inference, the student outputs a JSON plan that is executed by separate prompt-engineered modules for web search, computation, extraction, and synthesis. Evaluated on the challenging SEAL-0 benchmark (111 questions), the student planner achieves 10.8% accuracy with 27.8 seconds latency, outperforming the monolithic QWEN3-8B baseline (1.8%, 159.9s) and prompted planners without reasoning (6.3%, 41.1s) and with reasoning (3.6%, 107.9s). The results demonstrate that supervised planning improves both factual reliability and efficiency.

## Method Summary
The framework addresses hallucination by decoupling reasoning from parametric fact memorization. A teacher model (GPT-5.2) generates planning traces for training questions, where each trace consists of abstract reasoning steps and atomic fact requests (queries, source types, dependency flags) but no factual answers. A student model (QWEN3-8B) is fine-tuned via supervised instruction tuning (QLoRA) to mimic these traces, learning only the structure of information needs. At inference, the student planner produces a JSON plan. A dependency resolver processes the plan, substituting placeholders for prior results. Separate modules then execute web searches (SerpAPI), compute operations, extract concise facts from search results, and aggregate them into a final answer. The entire pipeline relies on retrieved evidence, not the model's internal knowledge.

## Key Results
- The student planner achieves 10.8% accuracy on SEAL-0, surpassing the monolithic QWEN3-8B baseline (1.8%) and prompted planners (6.3% without reasoning, 3.6% with reasoning).
- Latency is reduced to 27.8 seconds per question compared to baselines (159.9s, 41.1s, 107.9s), due to efficient JSON planning and elimination of repair overhead.
- The framework yields competitive performance against stronger agentic models while using a small, fast planner, demonstrating that supervised planning enhances both factual reliability and efficiency.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Supervised planning decouples reasoning from parametric fact memorization, forcing reliance on external verification.
- **Mechanism**: The teacher generates decomposition traces containing only abstract steps and atomic fact requests, never factual answers. The student learns to imitate this structure, not to produce answers. Thus, the student learns how to structure information needs, not what facts are true. At inference, its JSON plan contains placeholders for facts, ensuring the final answer must be assembled from retrieved evidence.
- **Evidence**: Supervision signals contain only planning traces without factual answers; the student is not supervised with factual answers or retrieved evidence.

### Mechanism 2
- **Claim**: Explicit dependency resolution in plans minimizes error propagation and enables verifiable, groundable fact chains.
- **Mechanism**: Each atomic fact request is tagged as `dependent` or not and references prior results via `<RESULT_i>` placeholders. This enforces a strict computational graph where each step's input is a concrete, previously retrieved fact, preventing reasoning over unretrieved assumptions.
- **Evidence**: Plans specify dependencies (section 2.1); examples show verification before computation (section 2.2.1).

### Mechanism 3
- **Claim**: Constraining the planner to output well-formed, deterministic JSON plans eliminates inference-time repair overhead and stabilizes tool orchestration.
- **Mechanism**: The student is fine-tuned to reproduce the teacher's strict JSON format. Valid plans require no repair module invocation, yielding shorter generation lengths and avoiding repetitive/looping outputs common in prompted planners.
- **Evidence**: Student planner achieves lowest latency (27.8 s) and eliminates JSON repair steps; prompted planners incur overhead due to longer generation and repair (section 3.2).

## Foundational Learning
- **Concept: Chain-of-Thought Decomposition**  
  *Why needed here*: The planner must output abstract reasoning steps separate from fact requests. Understanding CoT as a structure (sequence of steps) rather than a reasoning trace is key.  
  *Quick check*: Given a question, can you list the minimal abstract operations (e.g., "compare X and Y", "calculate duration") without stating any actual values?
  
- **Concept: Retrieval-Augmented Generation (RAG)**  
  *Why needed here*: The entire pipeline assumes retrieved evidence is the sole source of facts. The learner must grasp that the planner's output feeds a retrieval system, and the extractor/aggregator cannot use parametric knowledge.  
  *Quick check*: If a fact request returns "no results", what should the aggregator do according to the system prompt?
  
- **Concept: Knowledge Distillation without Label Leakage**  
  *Why needed here*: The student is trained on traces, not answers. This requires understanding that the supervision signal is the form of the plan (structure, query types, dependencies), not its content.  
  *Quick check*: If the teacher's plan for "capital of France" were `{query: "Paris", source: "web"}`, why would that be a failed example of proper supervision?

## Architecture Onboarding
- **Component map**: Student Planner (QWEN3-8B) -> JSON Plan -> Dependency Resolver -> Tool Executors (Web: SerpAPI; Compute: prompted QWEN3-8B) -> Extractor (prompted) -> Aggregator (prompted) -> Final Answer. JSON Repair (prompted) invoked conditionally if planner output invalid.
- **Critical path**: Planner generates JSON plan -> Iterative execution of `required_information` items in order with dependency resolution (substituting `<RESULT_i>` placeholders) -> Web search followed by extraction for each `web` query -> Compute operations for `compute` queries -> Aggregation of all extracted facts into final answer.
- **Design tradeoffs**:
  - *Modularity vs. Tool Reliability*: Separation improves debuggability but makes system brittle to retrieval failures.
  - *Planning Quality vs. Training Cost*: Student performance hinges on teacher's decomposition quality; constructing large training set is expensive.
  - *Latency vs. Accuracy*: Planner is efficient, but end-to-end latency dominated by external tools (web search).
- **Failure signatures**:
  - **JSON Parse Error**: Planner output not valid JSON → triggers repair module (adds latency).
  - **Missing Dependency**: A `dependent: true` query references `<RESULT_i>` never produced → execution halts.
  - **Extractor Hallucination**: Extractor uses knowledge outside provided SerpAPI JSON.
  - **Aggregator Overclaim**: Aggregator produces answer not fully supported by retrieved facts.
- **First 3 experiments**:
  1. **Plan Format Validation**: Run 100 random training questions through student planner. Measure % of outputs that are valid JSON with correct keys (`required_information`, `reasoning_steps`). Target: >95%.
  2. **Dependency Resolution Test**: For plans with `dependent: true` queries, inject mock results and verify placeholders are correctly substituted before tool call. Check for circular dependencies.
  3. **End-to-End Retrieval Fidelity**: On a subset of SEAL-0, log every web query issued. Manually check if top SerpAPI result directly answers the atomic query. Target: >80% of queries are "answerable" by top result.

## Open Questions the Paper Calls Out
1. How does the framework's performance generalize across a diverse set of factual QA benchmarks beyond the SEAL-0 split? The authors state that further experiments on easier yet time-sensitive factual benchmarks would help characterize performance across a broader range of real-world scenarios.
2. To what extent does the choice of teacher model (e.g., GPT-5.2 vs. other LLMs) affect the quality and transferability of the generated planning traces? The paper uses a specific teacher model but does not analyze whether planning traces are generalizable or sensitive to the teacher's decomposition style.
3. Can the prompt-engineered extraction and aggregation modules be replaced with learned components to improve robustness without sacrificing factual grounding? The framework relies on prompt-engineered modules but does not explore whether these could be optimized through fine-tuning.
4. How does the framework detect or resolve contradictory or insufficient evidence from external search results? The authors note that retrieval failures can propagate to the final answer but provide no explicit mechanism for conflict detection or insufficiency handling.
5. Does supervised planning scale efficiently to high-throughput or real-time settings given the latency dominated by external tools? The authors acknowledge that inference latency is still dominated by external search and extraction, which may limit scalability in high-throughput or real-time settings.

## Limitations
- Teacher model details (GPT-5.2) are inaccessible; replication may require a substitute (e.g., GPT-4o), potentially altering planning distribution.
- Exact prompts for extractor/aggregator/repair modules are underspecified; minor formatting differences could destabilize the pipeline.
- SEAL-0 benchmark access/evaluation script is not public; reimplementation may deviate from official grading.

## Confidence
- Mechanism 1 (Supervised planning decouples reasoning): Medium
- Mechanism 2 (Dependency resolution minimizes error): High
- Mechanism 3 (JSON constraint stabilizes orchestration): Medium
