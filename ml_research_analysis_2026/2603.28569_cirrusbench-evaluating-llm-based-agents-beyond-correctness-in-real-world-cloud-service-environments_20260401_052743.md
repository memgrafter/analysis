# CirrusBench: Evaluating LLM-based Agents Beyond Correctness in Real-World Cloud Service Environments

## Quick Facts
- **arXiv ID**: 2603.28569  
- **Source URL**: https://arxiv.org/abs/2603.28569  
- **Reference count**: 40  
- **Primary result**: State-of-the-art LLM agents exhibit significant performance gaps in real-world cloud service tasks, particularly in tool-use, multi-turn consistency, and clarification, with thinking models incurring high latency without proportional success gains.

## Executive Summary
CirrusBench introduces a realistic evaluation framework for LLM-based agents in cloud service environments, constructed from over 1,500 authentic support tickets. It assesses both single-turn subtasks (tool-use, problem-solving) and full multi-turn dialogues using novel Customer-Centric Metrics: Normalized Efficiency Index (NEI) and Multi-Turn Latency (MTL). Experiments with leading models (GPT, Qwen, DeepSeek series) reveal substantial deficiencies: performance drops sharply on tool-call tasks, "thinking" models incur high latency without corresponding success improvements, success rates decline with interaction depth due to error accumulation, and models consistently fail at inquiry/clarification tasks by prematurely closing. These findings indicate that current LLM agents lack the robustness and efficiency needed for practical technical service deployment, highlighting the need for research focused on multi-turn consistency and resolution speed beyond isolated accuracy.

## Method Summary
CirrusBench parses authentic cloud support tickets into structured tasks and checkpoints, each representing a turn in a service interaction. A record-and-replay tool mock simulates backend cloud services, providing deterministic responses based on real execution traces. Agents engage with the tasks via natural language and tool calls; their interactions are logged and evaluated using NEI (which normalizes efficiency by task complexity) and MTL (which aggregates latency across multi-turn dialogues). The benchmark covers both single-turn subtasks (tool-use, problem-solving) and full multi-turn dialogues, enabling a comprehensive assessment of agent capabilities in realistic settings.

## Key Results
- SOTA LLM agents (GPT, Qwen, DeepSeek series) exhibit substantial performance gaps in cloud service environments, failing to meet real-world viability standards.  
- Tool-call success rates drop sharply; "thinking" models (e.g., DeepSeek-R1) suffer high Multi-Turn Latency without commensurate success gains.  
- Success rates decline monotonically with interaction depth (checkpoints) due to error accumulation, and models perform worst on inquiry/clarification tasks, demonstrating a tendency toward premature closure.

## Why This Works (Mechanism)
CirrusBench effectively isolates agent deficiencies by leveraging authentic support tickets that embody real-world task distributions and complexities. The checkpoint-based design captures progressive task completion, allowing measurement of error accumulation. Novel metrics NEI and MTL focus on efficiency and latency, aligning evaluation with practical service constraints. The record-and-replay tool mock ensures reproducible yet realistic simulation of cloud tool interactions, including schema variations and error conditions.

## Foundational Learning
- **Tool-Use Evaluation**: Needed to assess agents' ability to correctly select and invoke backend APIs; quick check: Does the agent generate tool calls that match the expected schema and arguments?  
- **Multi-Turn Dialogue Consistency**: Needed to measure error accumulation over extended interactions; quick check: Does the agent maintain context and logical coherence across 10+ turns?  
- **Efficiency-Centric Metrics**: Needed to capture real-world operational constraints (latency, token cost); quick check: Is the agent's response time within acceptable service-level agreement limits?  
- **Survivorship Bias Awareness**: Needed to avoid overestimation of agent viability by excluding failed cases; quick check: Does the dataset include only successful tickets, and how might that bias performance estimates?  
- **Tool Mock Realism**: Needed to simulate dynamic backend behaviors; quick check: Does the tool mock handle state changes and unexpected failures?  
- **Premature Closure Detection**: Needed to identify when agents skip necessary clarification steps; quick check: Does the agent ask relevant clarifying questions when information is incomplete?

## Architecture Onboarding
**Component map**: Ticket Parser -> Task Generator -> Agent (LLM + Tool Executor) -> Tool Mock -> Interaction Logger -> Metric Calculator

**Critical path**: (1) Ingest raw support tickets; (2) Parse into structured tasks and checkpoints; (3) Execute agent interactions via the tool mock; (4) Log all actions and outcomes; (5) Compute NEI and MTL for evaluation.

**Design tradeoffs**:  
- Record-and-replay tool mocks ensure reproducibility but omit live API variability (e.g., transient failures, race conditions).  
- Building from successful tickets guarantees solvable tasks but introduces survivorship bias and limits assessment of recovery capabilities.  
- NEI/MTL prioritize efficiency but lack external validation against human operator benchmarks.

**Failure signatures**:  
- High Average Multi-Turn Latency (AMTL) with low Success Rate (SR) indicates inefficient reasoning.  
- Low SR on Inquiry/Clarify tasks suggests premature closure.  
- Decreasing Task Progression Rate (TPR) with increasing checkpoint count signals error accumulation.

**First three experiments**:  
1. Benchmark SOTA models on tool-call subtasks to measure success rates and AMTL.  
2. Analyze performance across increasing checkpoint depths to quantify error accumulation.  
3. Evaluate models on inquiry/clarification scenarios to assess proactive questioning and success.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question**: How can LLM-based agents be architected to sustain logical consistency and mitigate error accumulation over long-horizon, multi-turn interactions in technical service tasks?
- **Basis in paper**: [explicit] The paper identifies multi-turn consistency as a critical bottleneck, noting that "Success rates decline as interaction depth (checkpoints) increases due to error accumulation" and that models exhibit "logical fragility" in extended dialogues.
- **Why unresolved**: Current SOTA models show a sharp drop in Task Progression Rate (TPR) as checkpoint count increases, indicating an inability to maintain state and reasoning coherence across many turns. The underlying mechanisms for this fragility—such as error propagation patterns or memory limitations—are not diagnosed.
- **What evidence would resolve it**: Controlled experiments that isolate sources of error (e.g., via gradient-based analysis of attention patterns or by ablating context window sizes) combined with model architectures explicitly designed for robust state tracking (e.g., external memory modules) evaluated on CirrusBench's long-tail, high-checkpoint tasks.

### Open Question 2
- **Question**: What specific deficiencies cause LLM agents to systematically fail at inquiry and clarification tasks, and how can models be trained to proactively gather missing information instead of resorting to premature closure?
- **Basis in paper**: [explicit] The paper states that models "consistently fail to ask necessary clarifying questions during inquiry tasks" and "exhibit a tendency toward premature closure," with Inquiry/Clarify response types showing the lowest success rates and higher token costs.
- **Why unresolved**: The root cause—whether a lack of uncertainty identification, insufficient goal-directed questioning strategies, or reward misalignment in training—is not empirically pinpointed. The paper suggests two principal limitations but does not test interventions.
- **What evidence would resolve it**: Ablation studies comparing models with/without uncertainty estimation heads or reinforcement learning from human feedback (RLHF) specifically targeting clarification behaviors. Success would be measured by improved SR and reduced token count on Inquiry/Clarify sub-tasks in CirrusBench.

### Open Question 3
- **Question**: Why does explicit "thinking" (e.g., chain-of-thought) in LLMs incur prohibitive latency penalties in tool-use scenarios without proportional gains in success rates, and can efficient reasoning mechanisms be decoupled from sequential token generation?
- **Basis in paper**: [explicit] The paper observes that "‘thinking’ models incur high latency without proportional success gains" in tool-call tasks, citing examples like DeepSeek-R1 achieving lower SR than DeepSeek-V3.2 while having much higher AMTL.
- **Why unresolved**: The trade-off is documented but not explained. It is unclear whether the latency stems from verbosity in reasoning traces, inefficient tool-selection reasoning, or architectural constraints of autoregressive decoding for complex tool schemas.
- **What evidence would resolve it**: Fine-grained analysis of token-level latency breakdowns (e.g., time spent on reasoning vs. tool formatting) and experiments with non-autoregressive or speculative decoding for reasoning steps, evaluated on tool-intensive tasks in CirrusBench to isolate efficiency vs. accuracy.

### Open Question 4
- **Question**: Does constructing evaluation benchmarks exclusively from successful resolution tickets introduce survivorship bias, and how would including failed or abandoned interactions change our understanding of agent robustness?
- **Basis in paper**: [inferred] CirrusBench is built from "tickets with a successful resolution," as stated in the Data Collection section. This excludes unsuccessful cases where agents might have deviated irrecoverably or users escalated to humans.
- **Why unresolved**: By omitting failure modes, the benchmark may overestimate agent viability and underrepresent critical error patterns (e.g., irreversible divergence early in a dialogue). The paper acknowledges error accumulation but only observes it within successful trajectories.
- **What evidence would resolve it**: Curating a parallel dataset of failed tickets (with clear failure points) and comparing agent behavior on both sets. Metrics should capture not just final success but also recovery capability, escalation rates, and divergence severity.

### Open Question 5
- **Question**: How valid are record-and-replay tool mocks for simulating real-world tool dependencies, and to what extent do they fail to capture dynamic state changes or API latency/errors present in live cloud environments?
- **Basis in paper**: [inferred] The Tool Mock methodology (Section 3.2.1) uses "real-time tool invocations and their corresponding execution results" to create static replays, avoiding live backend APIs. This is acknowledged as a reproducibility measure but may oversimplify tool dynamics.
- **Why unresolved**: Real cloud tools have mutable states, race conditions, and transient failures that static replays cannot emulate. The paper does not quantify how this simplification affects tool-use performance (e.g., whether agents rely on deterministic outputs that don't exist in practice).
- **What evidence would resolve it**: Running a subset of tasks with a live sandbox environment that introduces controlled variability (e.g., random tool delays, partial failures) and comparing agent performance against the static CirrusBench results. Discrepancies would measure the mock's ecological validity.

## Limitations
- **Data Generalizability**: The benchmark is derived from a specific cloud service domain and ticket distribution, potentially limiting applicability to other technical service contexts.  
- **Metric Validation**: The novel Customer-Centric Metrics (NEI, MTL) lack external validation against human judgments or established benchmarks, raising construct validity concerns.  
- **Performance Attribution**: Observed failures (tool-call drop, premature closure, error accumulation) are correlational; root causes (model architecture, prompting, tool design) are not isolated.

## Confidence
- **Framework realism**: High  
- **Metric utility**: Medium  
- **Model viability gap**: Medium-Low  

## Next Checks
1. **Cross-Benchmark Concordance**: Replicate key experiments using parallel agent benchmarks (e.g., CR-Bench, CORE) to test if performance hierarchies and failure modes (tool-call, multi-turn decay) hold.  
2. **Metric Calibration**: Conduct human evaluation on a subset of CirrusBench dialogues to validate NEI/MTL scores against expert assessments of efficiency and resolution quality.  
3. **Ablation of Error Propagation**: Design controlled experiments varying turn depth and tool complexity to isolate whether performance drop is due to model memory limits, tool misuse, or environmental stochasticity.
