# Neurosymbolic Language Reasoning as Satisfiability Modulo Theory

## Quick Facts
- **ArXiv ID:** 2602.18095
- **Source URL:** https://arxiv.org/abs/2602.18095
- **Reference count:** 40
- **Primary result:** Logitext integrates natural language text constraints (NLTCs) with SMT solving to reliably reason over mixed textual and logical documents, significantly improving accuracy on classification and coverage on constrained generation tasks.

## Executive Summary
Logitext introduces a novel neurosymbolic framework that treats LLM-based reasoning as a theory within SMT solving. By representing documents as natural language text constraints (NLTCs), it makes partial logical structure explicit and enables logical propagation across mixed content. The system uses an LLM-based solver (NLSolver) in a propose-verify-refine loop to evaluate textual constraints while respecting logical constraints from an SMT solver (Z3). Experiments on content moderation, LegalBench, and Super-NaturalInstructions show substantial gains: classification accuracy improves, and the combinatorial reasoning gap in coverage generation (exceeding 99% for GPT-5) is reduced to near zero. Logitext outperforms direct prompting and staged neurosymbolic baselines across all benchmarks.

## Method Summary
The Logitext framework processes documents annotated with NLTCs—partial logical representations expressed in natural language. A parser converts the document into an abstract structure: Boolean variables for clauses, unbound string variables for text, and logical formulas linking them. An orchestrator (`check`) invokes Z3 to propose Boolean assignments consistent with the logical constraints. For each unbound string variable, an LLM-based theory solver (NLSolver) is called. NLSolver iteratively proposes candidate text assignments using an LLM, verifies each against relevant NLTCs, and refines based on violations until constraints hold or a timeout occurs. This interleaved approach allows logical propagation to prune the search space, avoiding brute-force enumeration. The system is evaluated on text classification (TE), instance generation (TIG), and coverage generation (TCG) tasks.

## Key Results
- Logitext significantly improves accuracy on text classification tasks across LegalBench and a new content-moderation benchmark (CMOD).
- For coverage generation, it reduces the combinatorial reasoning gap from over 99% (GPT-5) to near zero, achieving near-saturation performance even with a smaller model (GPT5‑nano).
- The framework consistently outperforms direct prompting and staged neurosymbolic baselines on all three task types: TE, TIG, and TCG.

## Why This Works (Mechanism)

### Mechanism 1: NLTCs make partial logical structure explicit
- **Claim:** Natural Language Text Constraints (NLTCs) make partial logical structure in natural documents explicit, enabling logical propagation across mixed textual and symbolic content.
- **Mechanism:** NLTCs bind textual clauses to Boolean variables and record their dependencies on context variables (e.g., the input message). This abstract representation allows an SMT solver to reason about logical relationships (e.g., conjunctions, disjunctions) between clauses even when the clauses themselves are evaluated by an LLM.
- **Core assumption:** Real-world documents (e.g., policies, legal texts) often contain implicit logical structure that can be partially formalized into Boolean variables and constraints without requiring full translation into formal logic.
- **Evidence anchors:** [abstract] "represents documents as natural language text constraints (NLTCs), making partial logical structure explicit."; [section 3.1] Details of Logitext language constructs; [corpus] Neighbors like "Autoformalizing Natural Language to First-Order Logic" (FMR 0.632) target full formalization; Logitext’s partial approach is novel with average FMR 0.505 and no citations.
- **Break condition:** If the logical structure is too ambiguous or context‑dependent to capture with Boolean variables and simple dependencies, NLTCs cannot represent it adequately.

### Mechanism 2: Treat LLM-based reasoning as an SMT theory
- **Claim:** Treating LLM-based reasoning as an SMT theory extends solvers like Z3 to handle textual constraints while preserving efficient logical propagation.
- **Mechanism:** The NLSolver acts as a theory solver for NLTCs. In the SMT loop, Z3 proposes Boolean assignments; NLSolver then attempts to assign string variables via LLM calls. This integration prunes the search space logically before invoking the LLM, avoiding brute‑force enumeration.
- **Core assumption:** LLM‑based constraint satisfaction can be structured as a sound (though not necessarily complete) theory solver within an SMT framework.
- **Evidence anchors:** [abstract] "This work is the first that treats LLM‑based reasoning as an SMT theory, extending neurosymbolic methods beyond fully formalizable domains."; [section 3.3] describes the loop; [corpus] Neighbors show SMT extensions but not combining LLMs as an SMT theory.
- **Break condition:** If the LLM theory solver is highly inaccurate or slow, the SMT loop may fail to find solutions or become impractical due to repeated backtracking.

### Mechanism 3: Propose‑verify‑refine loop improves reliability
- **Claim:** The propose‑verify‑refine loop in NLSolver improves reliability of textual constraint satisfaction by iteratively refining candidate assignments based on explicit violation feedback.
- **Mechanism:** For a target string variable, NLSolver first proposes a candidate via LLMPropose. It then verifies each relevant NLTC using LLMVerify, comparing predicted truth values to required ones. Violations are fed back to LLMPropose to guide refinement. This continues until constraints hold or a timeout.
- **Core assumption:** LLM‑generated text often initially violates constraints but can be guided to satisfaction through targeted feedback on specific failures.
- **Evidence anchors:** [section 3.3] "It does so through a propose‑verify‑refine loop."; [section A.5.2 and A.5.3] details of prompts; [corpus] neighbors use iterative refinement with feedback.
- **Break condition:** If the LLM cannot generate any candidate that progressively satisfies constraints (e.g., due to task complexity or intrinsic model limits), the loop will time out without success.

## Architecture Onboarding

**Component map:**  
Logitext document parser → Z3 solver ↔ NLSolver (LLMPropose, LLMVerify) → check() orchestrator → LLM backend

**Critical path:**  
1. Parse a Logitext document (e.g., content policy) into D = (vs, us, ϕ, ν).  
2. For a task (e.g., classify message M), call `check(D, {'M': M})`.  
3. `check()` invokes Z3 to get Boolean assignment πZ for clause variables.  
4. For each unbound string variable u (e.g., M or intermediate clauses), call `NLSolver(u, ν[u], π)` to propose a string u*.  
5. NLSolver proposes u* via LLMPropose, then verifies with LLMVerify; if violations, refines.  
6. If all string variables satisfied, return full assignment; else block πZ and repeat from step 3.  
7. Extract decision variable (e.g., d) from final assignment.

**Design tradeoffs:**  
- *Interleaved vs. staged*: Interleaving allows logical propagation to guide text generation but increases LLM calls; staged approaches are simpler but fail on partial formalization.  
- *LLM as theory solver*: Flexible for textual constraints but non‑deterministic and slow; mitigated by caching proposals and limiting iterations.  
- *Partial formalization effort*: Requires manual annotation of policies into Logitext syntax, which adds overhead but enables reasoning over otherwise informal documents.

**Failure signatures:**  
- Clause‑level errors: LLM mis‑evaluates a textual constraint, causing incorrect final decisions despite correct logical structure.  
- Timeouts: NLSolver exceeds iteration limit T without finding a satisfying assignment, often due to complex constraints or weak LLM performance.  
- UNSAT: Z3 finds no Boolean assignments consistent with constraints, or NLSolver fails for all Boolean candidates.  
- High latency: Excessive LLM calls, especially in coverage generation; observed as slower than baselines in some tasks.

**First 3 experiments:**  
1. **Smoke test:** Run classification on a single content‑moderation example (e.g., Political policy). Verify that `check()` returns a consistent assignment and the decision matches the expected label.  
2. **Instance generation test:** For a policy like Fraudulent (Listing 10), call `check(D, {'matches_online_fraud_subcategory': False, 'matches_hacking_cheating_subcategory': False})` and confirm that the generated message M satisfies the policy without triggering any subtopics.  
3. **Coverage comparison:** On a small policy (e.g., Religious with 8 clauses), enumerate satisfying assignments with Logitext (`cover=True`) and compare the number of distinct messages against direct GPT‑5 prompting under a fixed time budget (3000 s). Expect Logitext to cover significantly more.

## Open Questions the Paper Calls Out

### Open Question 1: How can clause‑level errors in NLTC evaluation be automatically corrected within the Logitext framework?
- **Basis:** [explicit] "clause‑level outputs [[Ci]] were incorrectly predicted by the LLM… These issues point to the need for clause‑level error correction" (Section 4, Figure 8).  
- **Why unresolved:** Clause misinterpretation propagates to final decisions, undermining reliability; manual inspection is infeasible at scale.  
- **What evidence would resolve it:** A method that detects and repairs erroneous clause assignments (e.g., via consistency checks or interactive refinement) demonstrated to improve end‑to‑end accuracy on benchmarks.

### Open Question 2: How can Logitext reliably differentiate between lists intended as enumerative examples versus logical conjunctions in natural language policies?
- **Basis:** [explicit] "lists such as “x, y, and z” were intended as examples rather than conjuncts, but were annotated as the latter" (Section 4).  
- **Why unresolved:** Misclassifying list semantics introduces incorrect logical constraints, leading to unsound reasoning.  
- **What evidence would resolve it:** A parser that infers the intended role of lists from context, evaluated on a variety of policy documents with ground‑truth annotations of list usage.

### Open Question 3: Can the conversion of natural language documents to Logitext programs be automated to reduce manual annotation effort?
- **Basis:** [inferred] The framework assumes NLTCs are manually annotated (Section 3.1); no automated extraction is discussed.  
- **Why unresolved:** Manual annotation limits scalability to large corpora of policies or legal documents; automation would broaden applicability.  
- **What evidence would resolve it:** An end‑to‑end system that inputs raw text and outputs Logitext documents, measured by annotation time reduction and accuracy compared to human annotations.

### Open Question 4: What modifications to the NLSolver algorithm can significantly reduce the number of LLM calls required for constraint solving while preserving solution quality?
- **Basis:** [inferred] NLSolver uses iterative LLM calls; caching yields only modest gains (Section 4, Figures 6 and 11).  
- **Why unresolved:** High LLM call count incurs computational cost and latency, hindering efficiency.  
- **What evidence would resolve it:** An improved algorithm (e.g., learned proposal model, better search pruning) that cuts average LLM calls by >50% on benchmark tasks without drop in success rate.

## Limitations
- The CMOD test set and annotated LegalBench/SNI documents are unreleased, preventing exact replication.  
- Reliance on proprietary GPT‑5/GPT5‑nano forces the use of weaker substitute models, affecting reported performance.  
- Manual annotation of policies into Logitext syntax is labor‑intensive and its scalability remains unproven.
