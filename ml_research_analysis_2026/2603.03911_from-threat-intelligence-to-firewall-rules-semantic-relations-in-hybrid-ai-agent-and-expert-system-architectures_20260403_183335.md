# From Threat Intelligence to Firewall Rules: Semantic Relations in Hybrid AI Agent and Expert System Architectures
## Quick Facts
- **arXiv ID:** 2603.03911
- **Source URL:** https://arxiv.org/abs/2603.03911
- **Reference count:** 23
- **Primary result:** A neuro-symbolic multi-agent system using hypernym-hyponym semantic enrichment for CTI text achieved a weighted F1 of 0.329 (a ~7% gain over baselines) and generated firewall rules judged by experts as technically correct (Krippendorff's α = +0.5768) and well-calibrated (Spearman's ρ = +0.6540).

## Executive Summary
This paper tackles the difficulty of automatically generating security responses (firewall rules) from Cyber Threat Intelligence (CTI) reports, a task complicated by highly imbalanced and complex data. The authors propose a neuro-symbolic multi-agent architecture. An LLM-driven agent iteratively extracts hypernym-hyponym ("is-a") relations from CTI text to create a semantically enriched knowledge graph. This structured semantics then feeds a symbolic CLIPS expert system, which generates and verifies syntactically correct firewall rules. Evaluated on multilabel ATT&CK technique classification and a full rule-generation pipeline, the semantic retrieval strategy shows a measurable improvement over baseline methods, and the generated rules receive high agreement scores from human security experts for correctness and scope.

## Method Summary
The approach uses a three-stage LLM prompting pipeline within a "CoALA" agent. First, it extracts cybersecurity entities (e.g., malware names, tools) from raw CTI. Second, it iteratively identifies specific hyponyms and general hypernyms for those entities, building a graph of semantic relations. Third, this structured semantics is used for retrieval/classification against a target taxonomy (MITRE ATT&CK) and to instantiate CLIPS templates. A separate symbolic expert system (Expert System A) validates the LLM's output against predefined CLIPS schemas before another (Expert System B) uses rule templates to generate the final firewall rules. The system was tested on the CTI-HAL dataset (81 reports, 116 techniques) for classification (Task A) and a dataset of 66 malware entries with analyst synopses for end-to-end rule generation evaluated by experts (Task B).

## Key Results
*   In a multilabel classification task on imbalanced CTI data (Task A), the semantic retrieval method using hypernym-hyponym relations achieved a weighted F1 score of 0.329 and a top-10 accuracy of 0.968, outperforming embedding-based and chain-of-thought baselines by approximately 7%.
*   In a full pipeline evaluation (Task B), human experts judged the automatically generated CLIPS firewall rules as technically correct (Krippendorff’s α = +0.5768) and well-calibrated in scope (Spearman’s ρ = +0.6540), indicating strong inter-rater agreement and effective mitigation of data imbalance.
*   The neuro-symbolic design, where a symbolic CLIPS layer verifies LLM output, was noted as key to ensuring syntactically valid rule artifacts and reducing hallucination risks.

## Why This Works (Mechanism)
### Mechanism 1
*Claim:* Hypernym-hyponym relations help overcome CTI data complexity and imbalance by enriching text with structured taxonomic semantics for more robust retrieval.
*Mechanism:* The system prompts an LLM to iteratively extract specific entities (hyponyms) and then their broader categories (hypernyms) from CTI prose. This creates a layered semantic representation where a concrete threat indicator is linked to abstract capabilities, allowing retrieval to match on both specific and general threat concepts.
*Core assumption:* The semantic distance between CTI content and the target security control taxonomy can be bridged by modeling "is-a" relationships within the text itself, without external ontologies.
*Evidence anchors:*
  - [abstract]: "leverage hypernym-hyponym textual relations to extract relevant information from Cyber Threat Intelligence (CTI) reports."
  - [section 4]: "extracts semantic information from input reports by first retrieving hyponyms and then hypernyms of the security concepts... via an iterative call to an LLM."
*Break condition:* If the CTI text contains novel jargonistic terms without clear lexical hierarchies in the LLM's knowledge, the extracted relations may be spurious, degrading retrieval.

### Mechanism 2
*Claim:* A neuro-symbolic agent architecture, where neural components extract/abstract and symbolic components verify/generate, yields more trustworthy and syntactically correct security rule artifacts than pure neural pipelines.
*Mechanism:* The LLM (neural) performs semantic extraction and abstraction, populating a graph-based KB. A separate CLIPS expert system (symbolic) uses this structured data to instantiate templates and generate verifiable firewall rule syntax, acting as a deterministic sanity check against LLM hallucinations.
*Core assumption:* The determinism of rule-based systems like CLIPS can be coupled with LLM flexibility for semantic parsing, provided the neural output is sufficiently structured.
*Evidence anchors:*
  - [abstract]: "By leveraging a neuro-symbolic approach, the multi-agent system automatically generates CLIPS code for an expert system."
  - [section 4]: "The Expert System A role is of a syntactic verification layer against potential LLM hallucinations... sequential instantiation of templates, facts, and production rules enables systematic detection of error propagation."
*Break condition:* If the LLM's extracted entities or relationships fail to map cleanly onto predefined CLIPS `deftemplate` structures (e.g., mismatched types), the symbolic engine rejects the input, halting generation.

### Mechanism 3
*Claim:* Semantic retrieval based on hypernym-hyponym relations may be more robust to severe class imbalance in multilabel CTI classification than embeddings or chain-of-thought alone, by allowing a single report to match multiple technique labels via shared abstraction.
*Mechanism:* Instead of classifying raw text embeddings, the system retrieves snippets based on semantic overlap with target class labels via shared hypernym/hyponym nodes. A rare technique can be retrieved if its specific hyponym matches a snippet, anchoring similarity in lexical relationships rather than distributional statistics.
*Core assumption:* The lexical taxonomy (implicit in the LLM) provides a more stable similarity metric for rare classes than embedding-based classifiers biased toward majority distributions.
*Evidence anchors:*
  - [abstract]: "outperforming baselines by approximately 7%... demonstrating the approach's effectiveness in mitigating imbalanced threat data."
  - [section 5, Table 1 & 3]: The proposed method shows a weighted F1 of 0.329, higher than CoT (0.308) and traditional ML (max 0.263). Table 3 shows variants using semantic thresholds (50%) perform best.
*Break condition:* If imbalanced data contains "long-tail" concepts lacking clear shared hypernyms with common concepts (e.g., a novel malware variant with no established parent), the semantic bridge fails.

## Foundational Learning
*Concept:* **MITRE ATT&CK Taxonomy**
  - *Why needed here:* The target defensive actions (firewall rules) are mapped to security capabilities and ATT&CK techniques. Understanding this matrix is essential to interpret the generated rules' intended blocking purpose.
  - *Quick check question:* If a CTI report describes "T1059.001: JavaScript execution via Windows Script Host," what ATT&CK tactic (e.g., Execution) and parent technique (T1059) would be relevant for a blocking rule?
*Concept:* **Hypernymy & Hyponymy (Lexical Semantics)**
  - *Why needed here:* The core extraction method relies on identifying "is-a" relationships (e.g., "Emotet" *is a* "banking trojan" *is a* "malware"). This is the semantic signal used to enrich the CTI text.
  - *Quick check question:* In the phrase "The attacker used a PowerShell script to download Mimikatz," identify one potential hyponym and one potential hypernym for a security-relevant concept.
*Concept:* **CLIPS Rule-Based Programming**
  - *Why needed here:* The final output is CLIPS code (`deftemplate`, `defrule`) for an expert system. Understanding LHS patterns and RHS actions is necessary to debug generated rule syntax or logic.
  - *Quick check question:* In a CLIPS rule `(defrule block-ip (malicious-ip (ip ?ip) (family ?fam)) => (assert (block-ip-rule (ip ?ip) (reason ?fam))))`, what is the pattern (LHS) and what is the action (RHS)?

## Architecture Onboarding
*Component map:*
Input Processor -> Enhanced CoALA Agent (Semantic Extractor + Knowledge Graph Builder) -> Graph KB -> Refinement Engine [Expert System A (Validate) -> Expert System B (Generate)] -> Output (CLIPS / firewall rules)
*Critical path:* Raw CTI Text -> CoALA Agent (Extract Hyponyms) -> CoALA Agent (Extract Hypernyms) -> Graph KB -> Expert System A (Syntactic Validate) -> Expert System B (Rule Template Instantiation) -> Firewall Rules.
*Design tradeoffs:*
  - *Neural Flexibility vs. Symbolic Determinism:* LLMs handle noisy prose but hallucinate; CLIPS ensures correctness but is brittle to input format. Managed via strict prompts and validation layers.
  - *Depth vs. Breadth of Semantic Extraction:* Deeper, iterative hypernym extraction may capture more relations but increases cost and error risk. The paper uses a fixed 3-stage iterative process.
  - *Task-Specific vs. General LLMs:* Qwen2.5-Coder was preferred over Foundation-Sec-14B for better CLIPS support, highlighting a tradeoff between domain knowledge and code-generation fidelity.
*Failure signatures:*
  - **LLM Extraction Failure:** Graph KB contains nonsensical relations or no entities. *Check:* Manually inspect extracted triplets.
  - **Validation Failure:** Expert System A rejects LLM output. *Check:* Validate entity mappings to CLIPS `deftemplate` slots and data types.
  - **Rule Generation Failure:** Expert System B produces empty output or references undefined capabilities. *Check:* Trace which security capability templates were matched by semantics.
  - **Performance Failure (Task A):** Low weighted F1, especially on minority ATT&CK techniques. *Check:* Analyze per-class precision/recall; likely semantic retrieval failure for rare classes.
*First 3 experiments:*
  1.  **Isolated Semantic Retrieval (Task A replication):** Run the CoALA agent's extraction and retrieval module on Dataset A without the CLIPS pipeline. Compare weighted F1 and Top-10 accuracy against baselines to validate the core hypernym/hyponym mechanism.
  2.  **CLIPS Syntax Validation Stress Test:** Feed the Graph KB from 100 CTI reports directly into Expert System A. Record the rejection rate and common error types (missing slot, wrong type) to isolate the symbolic layer's robustness.
  3.  **End-to-End Pipeline Human Evaluation (Task B replication):** Generate full firewall rules for the 66 reports in Dataset B. Have domain experts rate outputs on Technical Correctness, Fidelity to CTI, and Scope Calibration. Compute Krippendorff's α and Spearman's ρ to confirm reproducibility of human agreement scores.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How can true determinism be achieved in LLM-based cybersecurity applications to ensure reliable and reproducible outputs?
- **Basis in paper:** [explicit] The authors state, "Future studies should also focus on exploring determinism in LLM use. In this article, it is a heuristic for true determinism."
- **Why unresolved:** The current approach uses deterministic inference heuristics (fixed seeds, greedy decoding) but acknowledges this is not true determinism, risking inconsistent outputs in safety-critical tasks.
- **What evidence would resolve it:** Formal verification of LLM outputs across multiple runs with varied seeds, or development of constrained decoding techniques guaranteeing identical outputs for identical inputs in cybersecurity contexts.

### Open Question 2
- **Question:** What are the practical challenges and requirements for deploying the generated CLIPS firewall rules in operational, large-scale network environments?
- **Basis in paper:** [explicit] The authors note the system is for "research purposes" and "leaves room for further development for downstream usage of filtering rules."
- **Why unresolved:** Evaluation was limited to expert judgment on correctness and calibration, not real-world deployment factors like integration with existing infrastructure, performance under high threat volume, or rule management overhead.
- **What evidence would resolve it:** Case studies or pilot deployments in live networks measuring operational metrics (false positive rates, rule conflicts, maintenance effort) and feedback from security operations teams.

### Open Question 3
- **Question:** Does the hypernym-hyponym semantic enrichment strategy generalize effectively across diverse CTI sources, threat domains, and beyond MITRE ATT&CK mappings?
- **Basis in paper:** [inferred] Evaluation uses two specific datasets (CTI-HAL with 81 reports, a 66-entry corpus) focused on MITRE ATT&CK. The methodology’s reliance on taxonomic relations may not capture other semantic nuances in varied CTI styles or emerging threats.
- **Why unresolved:** Performance gains are demonstrated on specific, imbalanced datasets, but scalability to larger, noisier, or conceptually different CTI collections (e.g., open-source intel, dark web reports) is untested.
- **What evidence would resolve it:** Cross-validation on multiple external CTI datasets covering different threat actors, malware families, and reporting standards; error analysis on in-vocabulary vs. out-of-vocabulary attack techniques.

### Open Question 4
- **Question:** Could other semantic relations (e.g., meronymy, troponymy) or structured knowledge (e.g., ATT&CK matrix embeddings) enhance the pipeline’s accuracy or robustness compared to hypernym-hyponym pairs alone?
- **Basis in paper:** [inferred] The methodology exclusively uses hypernym-hyponym extraction, justified by their NLP prevalence. However, CTI semantics involve multifaceted relationships ("uses," "targets") that may not be fully captured by hierarchical relations.
- **Why unresolved:** The paper compares against embedding baselines but not against alternative semantic relation strategies. The choice of hypernym-hyponym is not validated against other potentially more expressive relations.
- **What evidence would resolve it:** Systematic ablation study replacing/augmenting hypernym-hyponym extraction with other relation types or knowledge graph embeddings, measuring impact on classification and rule generation, particularly on minority threat classes.

## Limitations
- **Prompt engineering details omitted** – exact LLM instructions, few-shot examples, and confidence thresholds are unspecified, hindering exact replication.
- **CLIPS schema and mapping logic unclear** – the `deftemplate` structures and transformation from semantic triples to firewall rules are not fully described.
- **Evaluation scope narrow** – Task A uses only the CTI-HAL dataset (81 reports); Task B’s human study involves 66 items, limiting statistical power. Krippendorff’s α (+0.5768) indicates moderate agreement.
- **LLM choice bias** – reliance on Qwen2.5-Coder-14B (selected for CLIPS support) may not generalize; its internal lexical taxonomy could uniquely affect extraction.
- **Imbalance mitigation partial** – weighted F1 = 0.329 is still low; it is uncertain if the ~7% gain stems from hypernymy or other design choices (e.g., 3-stage prompting).

## Confidence
- **Claim 1 (Hypernym-Hyponym retrieval aids imbalance):** Medium – results are positive but lack ablation on individual relation types and rely on a single, small dataset.
- **Claim 2 (Neuro-symbolic trustworthiness):** Medium – human judges rated rules highly, but without baselines (pure LLM or pure symbolic) the hybrid's added value is not isolated.
- **Claim 3 (Robustness to rare classes):** Low-Medium – improvement over embeddings is modest and may not hold for ultra-rare ATT&CK techniques lacking lexical bridges.

## Next Checks
1.  **Ablate the semantic mechanism:** Run the retrieval pipeline using only hyponyms, only hypernyms, and random semantic expansions to quantify each component’s contribution to the weighted F1 gain.
2.  **Cross-LLM generalizability:** Replace Qwen2.5-Coder with a different LLM (e.g., GPT-4 or Claude) while keeping prompts unchanged, and measure performance changes on both tasks.
3.  **Per-class error analysis on long-tail techniques:** Manually validate whether mis-classified rare ATT&CK techniques lack a hypernym link in the extracted graph; correlate missing links with classification failures.
