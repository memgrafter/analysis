# REGAL: A Registry-Driven Architecture for Deterministic Grounding of Agentic AI in Enterprise Telemetry

## Quick Facts
*   **arXiv ID:** 2603.03018
*   **Source URL:** https://arxiv.org/abs/2603.03018
*   **Reference Count:** 17
*   **Primary Result:** A prototype REGAL system reduced cross-system navigation in incident investigation to a single interaction, with subsecond metric retrieval latency and token usage scaling with pre-aggregated metrics rather than raw log volume.

## Executive Summary
REGAL addresses the unreliability of LLM-based agents operating on raw enterprise telemetry by introducing a registry-driven architecture. It solves three core problems: context overload from vast logs, ambiguous local semantics, and tool drift where tool interfaces diverge from implementations. The system uses deterministic Medallion ELT pipelines to transform raw events into replayable, semantically compressed "Gold" artifacts. A central declarative metrics registry then compiles these definitions into bounded Model Context Protocol (MCP) tools, ensuring a single source of truth. This separation enforces a non-interference property, making data computation invariant to changes in probabilistic LLM reasoning.

## Method Summary
The architecture comprises two orthogonal layers. The deterministic write path ingests heterogeneous telemetry (e.g., logs, issue trackers) through a Medallion pipeline (Bronze raw archive → Silver harmonized records → Gold aggregated metrics), guaranteeing idempotent, replayable transformations. A central metrics registry declaratively defines each Gold artifact’s identifier, description, retrieval logic, and governance. A compilation layer automatically translates these registry entries into MCP tool schemas, descriptions, and access policies. The agent's read path is strictly constrained to invoking these compiled tools against the Gold store, never interacting with raw data.

## Key Results
*   Agent-assisted incident investigation workflows reduced cross-system navigation to a single interaction.
*   Latency for aggregated metric retrieval remained subsecond under load, with model inference as the dominant factor.
*   Token usage scaled with the number of pre-aggregated Gold metrics, yielding a qualitative reduction compared to raw-log grounding.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** Registry-driven semantic compilation mitigates tool drift by ensuring alignment between tool specification and execution.
*   **Mechanism:** A single declarative metrics registry defines metric semantics, retrieval logic, and governance metadata. A compilation step generates Model Context Protocol (MCP) tool schemas, descriptions, access controls, and caching policies directly from this registry, eliminating manual duplication between interface and implementation.
*   **Core Assumption:** Maintaining a single source of truth for metric definitions prevents divergence as schemas evolve.
*   **Evidence Anchors:**
    *   [abstract] "The registry functions as an 'interface-as-code' layer, ensuring alignment between tool specification and execution, mitigating tool drift..."
    *   [section III.A] "In many LLM-integrated systems, the tool definition visible to the model and the backend implementation evolve independently... We refer to this misalignment as tool drift."
*   **Break Condition:** If the registry itself becomes inconsistent or if compilation logic diverges from registry schemas, alignment is compromised.

### Mechanism 2
*   **Claim:** Deterministic Medallion ELT pipelines produce replayable, semantically compressed Gold artifacts that bound token usage and prevent context overload.
*   **Mechanism:** Raw telemetry undergoes staged transformations: Bronze (immutable archive), Silver (schema harmonization), and Gold (deterministically aggregated, semantically rich metrics). This upstream aggregation means LLM agents interact with compact artifacts instead of raw event streams.
*   **Core Assumption:** Pre-aggregation into stable, version-controlled metrics reduces the entropy of data exposed to probabilistic reasoning.
*   **Evidence Anchors:**
    *   [abstract] "deterministic Medallion ELT pipelines produce replayable, semantically compressed Gold artifacts."
    *   [section IV.D] "The role of this pipeline is not merely data hygiene. It serves two architectural purposes: (1) To make metric computation explicit and version-controlled. (2) To reduce entropy before LLM interaction..."
*   **Break Condition:** If Gold artifact definitions become overly broad or fail to compress effectively, token usage may scale poorly, undermining the design.

### Mechanism 3
*   **Claim:** A strict non-interference property between deterministic data computation and probabilistic reasoning ensures that changes in model inference do not alter telemetry semantics or artifacts.
*   **Mechanism:** Deterministic transformations (ingestion, harmonization, compilation) are isolated from probabilistic LLM inference. Gold artifacts and tool definitions are version-controlled and replayable independently of model choice, prompt design, or reasoning strategy.
*   **Core Assumption:** Separating the "deterministic→probabilistic handoff" preserves correctness and auditability across model updates.
*   **Evidence Anchors:**
    *   [abstract] "The architecture’s non-interference property ensured deterministic data computation remained invariant to probabilistic reasoning changes."
    *   [section II.B] "Deterministic computation (ingestion, transformation, compilation) produces version-controlled artifacts and tool definitions. Probabilistic reasoning (LLM inference) may consume these artifacts, but probabilistic inference must not alter or redefine telemetry computation."
*   **Break Condition:** If probabilistic components (e.g., dynamic tool selection) influence deterministic pipeline parameters or if artifact versioning is not enforced, non-interference fails.

## Foundational Learning
*   **Concept:** Medallion Architecture (Bronze/Silver/Gold layers)
    *   **Why needed here:** It provides the structured refinement that transforms raw, heterogeneous telemetry into deterministic, AI-consumable artifacts. Without this layered transformation, semantic compression and replayability cannot be systematically achieved.
    *   **Quick Check:** What is the primary purpose of the Gold layer in REGAL’s pipeline, and how does it differ from Silver?
*   **Concept:** Model Context Protocol (MCP) as a tool interface standard
    *   **Why needed here:** MCP defines the concrete interface through which agents invoke compiled metrics. REGAL leverages MCP to expose a bounded, version-controlled action space, rather than allowing free-form queries.
    *   **Quick Check:** How does compiling MCP tools from a registry differ from manually writing tool wrappers, and what risk does this difference address?
*   **Concept:** Deterministic Upsert Semantics & Replayability
    *   **Why needed here:** These operational guarantees ensure that repeated execution over identical inputs yields identical Gold artifacts, which is foundational for auditability, caching, and the non-interference property.
    *   **Quick Check:** Why is idempotent ingestion critical for agentic systems that may retry queries or require historical recomputation?

## Architecture Onboarding
Sources (GitHub, Jira, Splunk) -> Fetchers -> Bronze (immutable archive) -> Silver (schema harmonization) -> Gold (aggregated metrics). Registry (declarative YAML/JSON) -> Compilation Layer -> MCP Tool Server -> Agent. Agent invokes MCP tools -> queries Gold storage -> returns artifact.

**Critical Path:** A user query flows: Natural language -> Agent selects MCP tool -> Tool executes deterministic query on Gold storage -> Returns compact artifact -> Agent reasons and responds. The registry defines the tool; the Medallion pipeline defines the artifact.

**Design Tradeoffs:**
*   **Bounded expressiveness vs. Governance:** Registry-curated tools limit agent flexibility but enforce access control and prevent harmful queries.
*   **Upfront aggregation cost vs. Inference latency:** Gold-layer computation adds pipeline latency but ensures subsecond retrieval and bounded token usage.
*   **Version control overhead vs. Reproducibility:** Immutable Bronze and versioned transformations enable backfills but require storage and pipeline management.

**Failure Signatures:**
*   **Tool drift symptom:** LLM tool description no longer matches returned data semantics (e.g., metric definition changed but tool docstring not updated).
*   **Non-determinism symptom:** Re-running ingestion for the same window produces different Gold values (check for non-idempotent upserts or non-deterministic joins).
*   **Token explosion symptom:** Agent query returns many raw events instead of aggregated metrics (inspect Gold layer definitions—aggregation may be missing).

**First 3 Experiments:**
1.  **Registry compilation validation:** Modify a metric definition in the registry (e.g., change crash rate threshold). Re-run compilation and verify MCP tool schema, description, and caching policy update accordingly. Check that old Gold artifacts remain valid for historical queries.
2.  **Token scaling comparison:** For a fixed time window (e.g., 24h), simulate grounding on raw Bronze events vs. Gold metrics. Serialize both to token counts. Expected outcome: Token usage scales with number of Gold metrics, not raw event volume.
3.  **Non-interference stress test:** Swap the underlying LLM (e.g., from Llama to GPT) and re-run identical agent queries. Validate that Gold artifact retrieval latency and content remain unchanged. Also, rerun ingestion pipeline with identical inputs to confirm Gold artifacts are byte-for-byte identical.

## Open Questions the Paper Calls Out
### Open Question 1
*   **Question:** How can REGAL's deterministic grounding be extended to support safe, bounded autonomous remediation actions without introducing unintended system changes?
*   **Basis in paper:** [explicit] Future Directions (Section IX.A): "Extending the architecture to support bounded corrective actions requires formal safety policies that distinguish transient anomalies from systemic faults."
*   **Why unresolved:** The paper proposes safety policies as a requirement but does not specify how to define, enforce, or verify such policies in practice across diverse enterprise systems and failure modes.
*   **What evidence would resolve it:** Implementations of policy engines that encode safety boundaries, case studies demonstrating successful autonomous remediation within constraints, and formal methods proving action safety under defined telemetry conditions.

### Open Question 2
*   **Question:** How can multiple independent REGAL registries (e.g., across infrastructure, security, CI/CD domains) interoperate while maintaining semantic consistency and trust in federated MCP tool exposure?
*   **Basis in paper:** [explicit] Future Directions (Section IX.A): "Multiple registry domains... may interoperate through federated MCP interfaces, raising questions of cross-agent trust and capability negotiation."
*   **Why unresolved:** Federated sharing introduces risks of semantic drift, privilege escalation, and inconsistent metric definitions across trust boundaries; the architecture assumes a single-source registry and does not address federation.
*   **What evidence would resolve it:** Protocols for capability negotiation and access delegation, implementations of cross-registry tool composition, and evaluations of semantic alignment in multi-organization scenarios.

### Open Question 3
*   **Question:** Can causal models be practically integrated into the deterministic Gold-layer to provide sound counterfactual reasoning for root-cause analysis, and does this integration preserve the architecture's non-interference property?
*   **Basis in paper:** [explicit] Future Directions (Section IX.A): "Integrating causal models into deterministic Gold-layer transformations could support confidence estimation and counterfactual analysis in root-cause workflows."
*   **Why unresolved:** Causal inference typically relies on assumptions difficult to verify from observational telemetry; integrating such models into a deterministic pipeline risks violating non-interference if causal computations become probabilistic or non-replayable.
*   **What evidence would resolve it:** Implementations of causal transformations within the Medallion pipeline, validation against known cause-effect incidents, and proofs or empirical demonstrations that causal steps remain deterministic and versioned.

### Open Question 4
*   **Question:** Can lightweight formal verification methods be developed to automatically check that compiled MCP tools precisely implement their declared registry semantics and governance policies (e.g., access controls, caching)?
*   **Basis in paper:** [explicit] Future Directions (Section IX.A): "Formal verification of interface invariants... could verify properties such as tool-definition alignment and idempotent replayability."
*   **Why unresolved:** Enterprise schemas and transformation logic are complex; existing formal methods may not scale to real-world data models or integrate with engineering workflows.
*   **What evidence would resolve it:** Verifier tools that ingest registry definitions and transformation code, check alignment and policy enforcement, and demonstrate effectiveness on production-like schemas and access policies.

### Open Question 5
*   **Question:** How does REGAL's token efficiency and latency scaling generalize beyond prototype workloads to large, multi-tenant enterprise environments with high-volatility telemetry and concurrent agentic queries?
*   **Basis in paper:** [inferred] Limitations (Section VIII.D): "Prototype scope... limited sample size... not evaluated against... identical conditions." The paper claims qualitative token reduction and subsecond latency but lacks large-scale benchmarks.
*   **Why unresolved:** The prototype used modest hardware and limited sources; enterprise scale introduces challenges in Gold artifact storage, caching efficacy under varied volatility, and concurrent access patterns that could affect determinism and latency.
*   **What evidence would resolve it:** Large-scale deployments measuring token usage per investigation across thousands of engineers, latency distributions under high concurrency, and comparisons with raw-log grounding at petabyte-scale telemetry volumes.

## Limitations
*   **Registry specification:** The exact schema and required fields for the declarative metrics registry are not detailed.
*   **MCP compilation details:** The precise transformation logic from registry entries to functioning MCP tools is unspecified.
*   **Generalizability:** Evidence is limited to a single prototype case study; scalability across diverse enterprise telemetry sources remains unproven.

## Confidence
*   **Tool drift mitigation (registry-driven alignment):** Medium. Internal architectural reasoning is clear, but external corpus validation is weak.
*   **Token reduction via Gold artifacts:** Medium. Case study shows qualitative improvement, but quantitative scaling claims need controlled measurement.
*   **Non-interference property:** Low. The invariant is well-defined but lacks rigorous empirical testing across model and pipeline iterations.
