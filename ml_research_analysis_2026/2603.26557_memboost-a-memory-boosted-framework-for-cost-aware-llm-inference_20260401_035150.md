# MemBoost: A Memory-Boosted Framework for Cost-Aware LLM Inference

## Quick Facts
- **arXiv ID**: 2603.26557
- **Source URL**: https://arxiv.org/abs/2603.26557
- **Reference count**: 19
- **Primary result**: MemBoost matches or exceeds Oracle accuracy (76.7–87.4% vs 76.4–85.0%) while drastically reducing expensive oracle calls; memory-use rate rises over time, directly lowering total inference cost and latency.

## Executive Summary
MemBoost is a framework designed to reduce the cost of serving large language models (LLMs) by reusing previously generated answers for repeated or semantically similar queries. It combines semantic caching, retrieval, and selective escalation. The core components are an Associative Memory Engine (AME) that stores and retrieves prior answers based on embedding similarity, a lightweight Meta Controller (MC) that decides whether to serve a cached response or escalate to a costly Oracle, and a write‑back mechanism that stores new Oracle answers for future reuse. Evaluation on the MMLU‑Pro benchmark with Zipf‑distributed query workloads shows that MemBoost with small MCs (e.g., Qwen3.5‑2B) achieves accuracy comparable to or better than an Oracle‑only baseline (76.7–87.4% vs 76.4–85.0%) while significantly reducing the number of expensive oracle invocations. The memory‑hit rate increases over time, especially under skewed workloads, leading to lower total inference cost (assuming Oracle cost dominates) and reduced latency.

## Method Summary
The authors did not provide explicit reproduction notes. Based on the system description, MemBoost operates as follows: When a query arrives, the Meta Controller first checks the Associative Memory Engine for semantically similar past queries using an embedding model (all‑MiniLM‑L6‑v2) and a similarity threshold (τ=0.95). If a high‑similarity cached answer is found, it is returned immediately. Otherwise, the query is escalated to the Oracle (a powerful LLM), and the generated answer is written back to the AME before being returned. The MC is designed to be computationally cheap so that its overhead is much lower than an Oracle call.

## Key Results
- **Accuracy**: MemBoost with small MCs attains 76.7–87.4% accuracy on MMLU‑Pro (range across subjects), matching or exceeding the Oracle‑only baseline of 76.4–85.0%.
- **Cost saving**: The fraction of queries handled by the AME (memory‑use rate) grows over time and approaches 100% under highly skewed workloads (e.g., Zipf exponent α=1.4), drastically reducing expensive oracle calls.
- **Latency**: As memory‑hit rate increases, average response latency decreases because cached retrieval is faster than Oracle inference.

## Why This Works (Mechanism)
MemBoost reduces cost by avoiding unnecessary invocations of the expensive Oracle. The AME provides a fast path for queries that are semantically similar to previously answered ones, and the MC acts as a traffic controller that only escalates when necessary. Because the MC is lightweight, its decision cost is negligible compared to Oracle inference. The write‑back mechanism gradually populates the AME with high‑quality answers from the Oracle (assuming Oracle answers are correct and applicable), increasing the hit rate over time. Under workloads with repeated or similar queries (as modeled by Zipf distributions), the system naturally shifts load from the Oracle to the cache, cutting total cost while maintaining accuracy. Latency improves because cache hits are served quickly without waiting for the Oracle.

## Foundational Learning
- **Semantic caching**: Storing and retrieving answers based on semantic similarity of queries rather than exact string match. *Why needed*: Natural language queries often vary in wording; semantic similarity allows reuse despite paraphrasing. *Quick check*: Embedding cosine similarity > τ (e.g., 0.95).
- **Selective escalation**: Decision‑making to forward only necessary queries to a high‑cost component. *Why needed*: Minimizes use of the expensive Oracle, which dominates serving cost. *Quick check*: Meta Controller routing accuracy (should send only misses to Oracle).
- **Associative Memory Engine**: A system that maps query embeddings to stored answers with nearest‑neighbor retrieval. *Why needed*: Efficiently find relevant past answers in large memory. *Quick check*: Retrieval latency and recall@k.
- **Cost‑aware inference**: Optimization that considers relative costs of different inference paths. *Why needed*: In production, different models/hardware have vastly different costs; minimizing total cost while meeting accuracy targets is crucial. *Quick check*: Cost model where c_Oracle >> c_MC + c_retrieval; total cost reduction proportional to hit rate.

## Architecture Onboarding
Component map: Query -> Meta Controller -> {Associative Memory Engine (AME) -> hit -> response; else -> Oracle -> response + write‑back to AME}

Critical path: For a cache hit: MC consults AME, retrieves answer, returns. For a cache miss: MC consults AME (miss), invokes Oracle, receives answer, writes to AME, returns. The Oracle step dominates latency.

Design tradeoffs:
- Similarity threshold (τ): Higher τ reduces false positives (improving accuracy) but increases misses (more Oracle calls). Lower τ increases hits but risks returning incorrect cached answers.
- Memory growth vs quality: Unbounded write‑back may bloat memory and introduce stale answers; an eviction policy might be needed.
- MC model size: Smaller MCs are cheaper but may make poorer routing decisions; larger MCs add overhead but might improve accuracy.
- Embedding model: More powerful embeddings improve retrieval quality but increase embedding computation cost and possibly memory footprint.
- Write‑back policy: Always writing back may introduce stale or incorrect answers, whereas a selective policy (e.g., based on confidence) could maintain memory quality but add complexity.

Failure signatures:
- Elevated oracle call rate: AME retrieval too strict or memory insufficient.
- Accuracy drop: False cache hits due to low τ or poor embeddings; or stale cached answers.
- Memory bloat: Unchecked write‑backs cause large index, slowing retrieval.
- Latency spikes: Many concurrent misses overload Oracle.

First experiments:
1. Replicate main findings: Run MemBoost on MMLU‑Pro with Zipf workloads (α=0.8, 1.0, 1.4), record accuracy, oracle call percentage, memory‑hit rate, and cost/latency.
2. Sensitivity to similarity threshold: Fix other parameters, vary τ (0.90, 0.95, 0.99), measure impact on hit rate, oracle calls, and accuracy.
3. Meta Controller model ablation: Replace the MC with variants (e.g., 2B, 7B, 13B parameter models) and compare routing decisions (e.g., hit vs miss rates) and overall cost/accuracy.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: How does MemBoost perform on more diverse and demanding tasks beyond multiple‑choice QA, such as open‑ended long‑form question answering or coding tasks?
- Basis in paper: [explicit] The "Limitations" section states, "the framework has not yet been evaluated in more diverse and demanding settings, such as open‑ended long‑form question answering or coding tasks."
- Why unresolved: The experiments are confined to the MMLU‑Pro (multiple‑choice) benchmark, leaving generalizability to other task formats untested.
- What evidence would resolve it: Systematic evaluation on standardized benchmarks for long‑form generation (e.g., TriviaQA) and coding (e.g., HumanEval), measuring accuracy and cost trade‑offs.

### Open Question 2
- Question: How robust is MemBoost to workloads with paraphrased or semantically overlapping queries that are not exact duplicates, given the risk of false hits in associative memory retrieval?
- Basis in paper: [explicit] The "Limitations" section notes, "queries are often not exact duplicates but only semantically similar, which can increase the risk of retrieval errors... A more realistic evaluation would therefore include workloads with paraphrased or semantically overlapping queries."
- Why unresolved: The study uses Zipf‑sampled queries from a fixed benchmark (MMLU‑Pro), which primarily involves repeated or near‑identical questions, not paraphrased variations.
- What evidence would resolve it: Evaluation on a test set with deliberately paraphrased queries (e.g., using back‑translation or LLM‑based paraphrasing) to measure retrieval precision and its impact on final accuracy and cost.

### Open Question 3
- Question: What specific criteria or signals does the Meta Controller use to decide whether to write back a newly generated oracle answer into the associative memory?
- Basis in paper: [inferred] The system description (Section 2.2) says the MC "decides... whether the newly generated query answer pair should be stored in AME for future reuse," but the decision policy (e.g., based on confidence, answer consistency, or metadata) is not detailed.
- Why unresolved: The paper emphasizes cost‑aware routing but leaves the write‑back trigger mechanism underspecified, which is critical for memory growth quality and eventual performance.
- What evidence would resolve it: Ablation studies varying write‑back policies (e.g., always write, confidence‑threshold‑based, category‑based) and their effect on long‑term memory‑hit accuracy and total cost.

### Open Question 4
- Question: How sensitive is MemBoost's performance to the choice of embedding model and the fixed similarity threshold (τ=0.95) used for AME retrieval?
- Basis in paper: [explicit] Table 2 lists a fixed embedding model (all‑MiniLM‑L6‑v2) and similarity threshold (0.95). The "Related Work" and methodology sections do not explore alternatives.
- Why unresolved: The configuration is presented as a given without justification or sensitivity analysis. Different embedding models or thresholds could significantly affect retrieval recall/precision and, consequently, overall system accuracy and cost.
- What evidence would resolve it: Cross‑validation with multiple embedding models (e.g., different sizes, domains) and threshold values on a held‑out set, reporting trade‑offs between memory‑hit rate, oracle escalation rate, and final accuracy.

### Open Question 5
- Question: To what extent does the assumed cost model (where oracle cost cO dominates cM + cR) hold in real‑world serving deployments with heterogeneous hardware, network latency, or variable batch sizes?
- Basis in paper: [explicit] Section 2.3 explicitly states, "In typical deployments, cO(xt) is much larger than cM(xt) + cR(xt)... since frontier‑model inference dominates GPU compute, whereas retrieval is primarily CPU‑bound." This is a central assumption for the cost‑saving claims.
- Why unresolved: The cost model is theoretical and not validated against empirical measurements in diverse production settings (e.g., cloud vs. edge, shared hardware, network‑bound retrieval). The relative costs could vary, altering the cost‑benefit balance.
- What evidence would resolve it: Empirical cost profiling of MemBoost components (MC inference, retrieval, oracle) across different hardware/network conditions, and sensitivity analysis of total cost savings under varying cost ratios.

## Limitations
- **Implementation opacity**: No release of code/weights; internal thresholds for the Meta Controller (e.g., similarity cutoffs for cache hits) are unspecified, hindering reproducibility.
- **Evaluation narrowness**: Results limited to MMLU‑Pro with Zipf‑simulated queries; performance on open‑ended, multi‑turn, or domain‑specific workloads is unknown.
- **Real‑world gaps**: Zero citation count suggests minimal peer scrutiny; absence of A/B testing in production systems leaves deployment viability unverified; write‑back accuracy decay and memory bloat risks over long horizons are unexplored.

## Confidence
- *Cost reduction claim*: **High** – claim supported by clear reductions in oracle call metrics in simulation.
- *Accuracy maintenance*: **Medium** – based on a single benchmark without statistical significance tests; may not generalize.
- *Scalability & generality*: **Low** – evaluation restricted to one dataset and simulated workload; no evidence across diverse tasks or production environments.
