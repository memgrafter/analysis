# From BM25 to Corrective RAG: Benchmarking Retrieval Strategies for Text-and-Table Documents
# Quick Facts
- arXiv ID: 2604.01733
- Source URL: https://arxiv.org/abs/2604.01733
- Reference count: 40
- Primary result: A two-stage pipeline combining hybrid retrieval (BM25 + dense via RRF) with neural reranking (Cohere Rerank) achieves Recall@5 of 0.816 and MRR@3 of 0.605, substantially outperforming all single-stage methods.

# Executive Summary
This paper benchmarks retrieval strategies for RAG systems handling mixed text-and-table documents, using the T²-RAGBench financial QA dataset (23,088 queries, 7,318 documents). Ten methods are evaluated, ranging from sparse (BM25) and dense (OpenAI embeddings) to hybrid fusion, neural reranking, and query expansion.

The best results come from a two-stage pipeline: hybrid retrieval (BM25 + dense via Reciprocal Rank Fusion) combined with Cohere Rerank. This system achieves Recall@5 = 0.816 and MRR@3 = 0.605, outperforming all single-stage approaches. Notably, BM25 alone outperforms dense retrieval, and query expansion (HyDE) fails to improve or even degrades performance on precise numerical queries. The dominant error (73%) is table structure mismatch, where markdown tables impede embedding-based matching. The authors recommend hybrid retrieval with neural reranking as the optimal architecture for such heterogeneous documents.

# Method Summary
The study evaluates ten retrieval strategies on the T²-RAGBench dataset, which comprises 23,088 queries over 7,318 financial documents containing both text and markdown tables. Documents are indexed whole (average ~920 tokens) without chunking. Sparse retrieval uses BM25 with parameters k1=1.2, b=0.75 and whitespace tokenization. Dense retrieval employs OpenAI's text-embedding-3-large (3072 dimensions) via Azure AI Foundry, with FAISS for cosine similarity search. Hybrid retrieval fuses BM25 and dense rankings using Reciprocal Rank Fusion (RRF, k=60). The top-performing system extends this hybrid with a neural reranker: it retrieves the top-50 candidates via hybrid RRF, then re-ranks them using Cohere Rerank v4.0 Pro, returning the top-10. Additional methods include query expansion (HyDE and Multi-Query using GPT-4.1-mini), index augmentation (Contextual Retrieval with LLM-generated prefixes), and an adaptive pipeline (CRAG) that rewrites queries based on relevance classification. For end-to-end evaluation, a generator (GPT-4.1-mini or GPT-5.4) produces answers using the retrieved documents and a fixed prompt. Primary metrics are Recall@k (k=1,3,5,10,20), MRR@3, nDCG@10, MAP, and Number Match (NM) for answer correctness. Statistical significance is tested via paired bootstrap (10,000 samples, Bonferroni correction).

To reproduce the main result, researchers should: (1) acquire the T²-RAGBench dataset from the Zenodo repository (DOI: 10.5281/zenodo.19382814) or the original source; (2) set up an environment with libraries (rank_bm25, faiss, openai, cohere, Azure SDKs) and API credentials; (3) build BM25 and dense indices for all documents; (4) for each query, retrieve top-50 candidates using hybrid RRF, rerank with Cohere Rerank, and take top-10; (5) run evaluation scripts and verify that Recall@5 reaches approximately 0.816 and MRR@3 approximately 0.605 on the test set.

# Key Results
- Hybrid retrieval (BM25 + dense via RRF) with Cohere Rerank achieves the highest performance: Recall@5 = 0.816, MRR@3 = 0.605.
- BM25 alone outperforms state-of-the-art dense retrieval on this financial corpus.
- Table structure mismatch accounts for 73% of retrieval failures, indicating markdown tables hinder embedding-based matching.

# Why This Works
The two-stage pipeline works by leveraging complementary strengths: BM25 provides precise lexical matching for keywords and numbers, while dense embeddings capture semantic relatedness. Reciprocal Rank Fusion (RRF) merges their results without score normalization, creating a robust candidate set that mitigates the weaknesses of each individual retriever. Neural reranking with Cohere Rerank then performs deep interaction scoring on these candidates, refining the ordering to prioritize truly relevant documents. This architecture directly addresses the primary failure mode—table structure mismatch—by allowing the cross-encoder to understand contextual relationships across table cells that are lost in isolated embeddings, though table-related errors remain significant.

# Foundational Learning
- **BM25**: Sparse retrieval based on term frequency and inverse document frequency. *Why needed*: Captures exact keyword matches, crucial for numerical and named entities in financial documents. *Quick check*: Implement with rank_bm25; verify k1=1.2, b=0.75 on a sample query.
- **Dense embeddings**: Vector representations from neural models (e.g., OpenAI text-embedding-3-large) that encode semantic similarity. *Why needed*: Retrieves documents with related concepts even without exact term overlap, complementing BM25. *Quick check*: Generate query embedding, compute cosine similarity with FAISS index; confirm dimensionality (3072) and similarity search.
- **Reciprocal Rank Fusion (RRF)**: A score-agnostic method to merge multiple ranked lists. *Why needed*: Combines BM25 and dense results without requiring score normalization, effectively balancing lexical and semantic retrieval. *Quick check*: Apply RRF with k=60 to top-50 from each retriever; measure hybrid Recall@5 vs. individual retrievers.
- **Neural reranking**: Using a cross-encoder (e.g., Cohere Rerank) to re-score candidate documents. *Why needed*: Provides fine-grained relevance assessment, improving top-k accuracy by considering query-document interactions deeply. *Quick check*: Rerank top-50 hybrid candidates; evaluate MRR@3 gain over unreranked hybrid.
- **Table structure mismatch**: A failure mode where markdown tables hinder embedding-based matching because related information spans multiple cells. *Why needed*: Recognizing this guides future work on table-aware indexing and retrieval. *Quick check*: Analyze errors; count gold documents containing markdown tables that are missed by dense retrieval.

# Architecture Onboarding
**Component map**:  
Query -> BM25 Retriever -> (list A); Query -> Dense Retriever (OpenAI embeddings) -> (list B); [list A, list B] -> Reciprocal Rank Fusion (k=60) -> Hybrid Candidates (top-50); Hybrid Candidates -> Cohere Rerank v4.0 Pro -> Final Ranked Results (top-10)

**Critical path**:
1. Compute BM25 scores for all documents and extract top-N (e.g., 50).
2. Generate dense embedding for the query using text-embedding-3-large and perform similarity search via FAISS to get top-N.
3. Fuse the two ranked lists using RRF (k=60) to produce a hybrid ranking; take top-50.
4. Feed the hybrid candidates to Cohere Rerank, which returns a reordered list; take top-10 as final retrieval results.
5. Pass retrieved documents to generation model (GPT-4.1-mini) for answer synthesis.

**Design tradeoffs**:
- Whole-document indexing vs. chunking: whole documents preserve context but may include irrelevant content; chunking could improve focus but risk splitting tables.
- Hybrid retrieval: Combines complementary strengths but requires maintaining two indices and incurs extra latency.
- Reranking: Improves accuracy significantly but adds cost and latency, especially with many candidates.
- Markdown tables: Simple to store but cause embedding mismatches; specialized table serialization could help but may break existing pipelines.

**Failure signatures**:
- Table structure mismatch: Gold document contains a markdown table, but the retrieved dense candidates lack such tables; errors concentrate on queries requiring table data (e.g., from TAT-DQA).
- Numerical query failures: Queries with precise numbers often not retrieved by HyDE-expanded queries due to hallucinated figures.
- High cost/latency: Reranking 50 candidates per query may be prohibitive for large-scale deployment.

**First experiments**:
1. Baseline evaluation: Run BM25-only and dense-only retrievers on a small subset (e.g., 100 queries) to establish individual performance (expected: BM25 Recall@5 > dense).
2. Hybrid fusion: Implement RRF to combine BM25 and dense results; verify that hybrid Recall@5 improves over both single retrievers.
3. Reranking impact: Apply Cohere Rerank to the hybrid output; measure delta in MRR@3 and Recall@5, particularly on table-heavy queries.

# Open Questions the Paper Calls Out
**Open Question 1:** How do different chunking strategies (e.g., fixed-size, semantic, table-aware) impact retrieval performance for mixed text-and-table documents?
- *Basis in paper:* [explicit] The authors used whole-document retrieval (average 920 tokens) and note in limitations that "performance patterns may differ for chunked corpora." Future work explicitly includes "chunking strategy ablations."
- *Why unresolved:* Chunking is a fundamental RAG design choice, especially for tables that may span multiple chunks. The optimal approach for preserving table structure and context is unknown.
- *What evidence would resolve it:* Systematic experiments comparing chunking methods on the same benchmark, measuring retrieval metrics (Recall@k, MRR) and failure mode breakdowns, particularly for table-heavy queries.

**Open Question 2:** To what extent do the findings (BM25 superiority, hybrid fusion benefits) generalize beyond financial documents to other domains like scientific papers or medical records?
- *Basis in paper:* [explicit] The paper states in limitations: "T2-RAGBench covers only financial documents; our findings may not generalize to other domains." Future work explicitly proposes "extending the benchmark to non-financial domains."
- *Why unresolved:* Financial documents have standardized terminology and numerical focus; other domains may have different content mixes, table structures, or query types, affecting retrieval dynamics.
- *What evidence would resolve it:* Replication of the benchmark methodology on diverse domain datasets (e.g., scientific tables, clinical reports) with similar evaluation, comparing performance patterns and identifying domain-specific retrieval principles.

**Open Question 3:** Do late-interaction models like ColBERT provide significant advantages over bi-encoders for text-and-table retrieval, particularly in matching fine-grained tabular data?
- *Basis in paper:* [explicit] Future work lists "evaluating ColBERT late interaction" as a direction.
- *Why unresolved:* Late-interaction retains per-token representations, potentially capturing row-column relationships in tables better than pooled embeddings, but this is untested on heterogeneous documents.
- *What evidence would resolve it:* Implement ColBERT variants (e.g., Jina-ColBERT-v2) on the benchmark, compare against dense bi-encoders and sparse methods, and analyze per-token alignment for table queries.

**Open Question 4:** What architectural modifications or preprocessing techniques can mitigate the 73% table structure mismatch failure mode in markdown document retrieval?
- *Basis in paper:* [inferred] Error analysis reveals table structure mismatch as the dominant failure (73%), where markdown tables hinder embedding matching because related terms appear in separate cells.
- *Why unresolved:* No evaluated method explicitly handles table semantics; current embedding models treat markdown as flat text. The paper does not propose solutions for this key bottleneck.
- *What evidence would resolve it:* Develop and evaluate structured-aware retrievers (e.g., table-specific tokenization, graph representations, or models pretrained on tabular data) and measure reduction in table-related failures.

**Open Question 5:** Why do hypothetical document generation methods (HyDE) degrade performance on numerical financial queries, and can query expansion be adapted for such fact-intensive domains?
- *Basis in paper:* [inferred] Results show HyDE underperforms vanilla dense retrieval; the paper hypothesizes LLM hallucinations of financial figures introduce noise, but this is not systematically verified.
- *Why unresolved:* Understanding the failure mechanism (hallucination, poor instruction following, embedding mismatch) is critical for designing effective query expansion in domains requiring precise facts.
- *What evidence would resolve it:* Analyze HyDE-generated passages for factuality and term overlap with gold documents; test variations in prompting, generation parameters, or post-processing to improve retrieval success on numerical queries.
