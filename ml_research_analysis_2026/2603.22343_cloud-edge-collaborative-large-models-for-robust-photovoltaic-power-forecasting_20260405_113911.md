# Cloud-Edge Collaborative Large Models for Robust Photovoltaic Power Forecasting

## Quick Facts
- arXiv ID: 2603.22343
- Source URL: https://arxiv.org/abs/2603.22343
- Reference count: 36
- Primary result: CAPE reduces normalized MAE by up to 22.3% and normalized RMSE by up to 23.3% while meeting latency and cloud usage constraints.

## Executive Summary
Photovoltaic (PV) power forecasting is critical for grid stability but faces challenges in balancing accuracy, robustness to weather-driven distribution shifts, and low-latency requirements in edge-enabled grids. This paper introduces CAPE, a condition-adaptive cloud-edge collaborative framework that combines a site-specific expert model, a lightweight edge-side model, and a cloud-based large retrieval model. A screening module evaluates uncertainty, out-of-distribution (OOD) signals, weather mutations, and model disagreement to decide when cloud assistance is needed. A Lyapunov-guided routing strategy dynamically selects inference paths while respecting long-term constraints on latency, communication, and cloud usage. Evaluated on real-world datasets from Hunan and Shanxi, CAPE significantly outperforms strong baselines, achieving up to 22.3% lower normalized MAE and 23.3% lower normalized RMSE, improved ramp event handling, and higher routing quality (AUROC up to 0.931) without violating system constraints.

## Method Summary
CAPE employs a hierarchical model structure: a site-specific expert trained on local PV data, a lightweight edge model for fast inference, and a cloud-based large retrieval model that leverages extensive historical data. For each prediction request, both edge models generate forecasts and associated uncertainty estimates. The screening module computes features including prediction disagreement, OOD detection based on recent statistics, and weather mutation indicators. These features, along with the current state of virtual queues representing long-term constraints, feed into a Lyapunov-based router that decides whether to use the edge expert's forecast or offload to the cloud. The Lyapunov optimization ensures that time-averaged latency, communication cost, and cloud usage remain within prescribed bounds. The system adapts continuously: when weather conditions are stable and edge models are confident, edge inference is used; when anomalies or high uncertainty arise, the cloud model is invoked to maintain accuracy.

## Key Results
- Up to 22.3% reduction in normalized MAE and 23.3% reduction in normalized RMSE compared to strong baselines.
- Lower ramp event error and reduced out-of-distribution degradation ratio.
- Routing quality (AUROC) up to 0.931 while respecting long-term latency, communication, and cloud-usage constraints.

## Why This Works (Mechanism)
CAPE's effectiveness stems from its adaptive division of labor. The site-specific expert captures fine-grained local patterns, yielding high accuracy under normal conditions. The lightweight edge model provides a fast fallback when the expert is unavailable or too slow. The cloud-based retrieval model, trained on vast and diverse data, excels in handling distribution shifts such as extreme weather. The screening module acts as an early warning system, detecting situations where edge models are likely to fail via multiple complementary signals. The Lyapunov router then optimally trades off immediate accuracy gains against long-term resource constraints, preventing overuse of the cloud and ensuring sustainable operation. This design allows CAPE to maintain low latency for routine forecasts while dynamically escalating to the more powerful cloud model only when necessary, thereby achieving superior accuracy and robustness without violating system limits.

## Architecture Onboarding
Component map: Input -> Edge Models (Site-specific Expert, Lightweight) -> Screening (uncertainty, OOD, mutation, disagreement) -> Lyapunov Router -> (Edge Output | Cloud Retrieval) -> Forecast.

Critical path: For edge-only inference: Input -> Edge Models -> Screening -> Router -> Edge Output (lowest latency). For cloud-assisted: same initial path, then Router -> Cloud Retrieval -> Forecast (higher latency due to network/cloud processing).

Design tradeoffs:
- Accuracy vs. Latency: Cloud model is more accurate but slower; edge models are fast but less accurate under shifts. The router balances via adaptive triggering.
- Robustness vs. Resource Usage: More cloud calls improve robustness but increase cloud costs and network load; Lyapunov control enforces long-term budgets.
- Model Complexity vs. Edge Feasibility: Site-specific expert may be heavy; lightweight model ensures fallback. Cloud retrieval is large but offloaded.

Failure signatures:
- Excessive cloud calls leading to constraint violations (high latency, cloud overload) indicate screening thresholds too sensitive or router not respecting constraints.
- Persistent large errors without cloud assistance suggest screening fails to detect certain distribution shifts (e.g., gradual drift).
- Cloud model returns biased forecasts for rare weather patterns not covered in training, causing systematic errors even when invoked.

First experiments:
1. **Ablation Study**: Remove each component (screening, router, one of the models) and measure impact on accuracy, robustness, and constraint adherence.
2. **Screening Threshold Sensitivity**: Vary thresholds for uncertainty/OOD/mutation to characterize the trade-off between cloud usage and performance.
3. **Lyapunov Parameter Tuning**: Adjust virtual queue weights and constraints to observe effects on long-term resource usage and forecasting error.

## Open Questions the Paper Calls Out
1. **Question**: How valid is the mean-field cloud delay approximation for small-to-moderate N in practice?  
   **Basis**: [inferred] Section III-B models cloud waiting time as ϕ(ρ) with mean-field justification when N is large; experiments test N up to 50 but lack a granular queuing comparison.  
   **Why unresolved**: The potential mismatch between ϕ(ρ) and real cloud contention could lead to inaccurate latency estimates and constraint violations.  
   **What evidence would resolve it**: Compare the mean-field model against discrete-event cloud simulations across N, reporting differences in predicted vs actual cloud delay and resulting constraint adherence.

2. **Question**: Can the hand-crafted screening signals be replaced by a learned module to improve routing decisions?  
   **Basis**: [inferred] Section IV-A uses fixed features (uncertainty, OOD, weather mutation, disagreement) with no exploration of learned alternatives.  
   **Why unresolved**: The optimality of these features is not established; a learned screening might capture more nuanced patterns of when cloud assistance is beneficial.  
   **What evidence would resolve it**: Replace the feature-based router with a small neural network trained on historical routing data, while maintaining the Lyapunov control structure, and compare AUROC/AUPRC and system constraints.

3. **Question**: Does CAPE remain effective for long-term deployment with gradual distribution shifts (e.g., panel aging)?  
   **Basis**: [inferred] The OOD detector uses recent statistics to catch abrupt shifts; experiments cover only short periods without slow drift.  
   **Why unresolved**: Gradual shifts may not trigger OOD alerts, causing persistent performance decay without cloud escalation.  
   **What evidence would resolve it**: Run long-horizon simulations with slowly drifting PV output distributions, track forecasting error and cloud request ratio over time, and assess whether the adaptive router automatically increases cloud usage.

## Limitations
- Reproducibility is limited due to lack of public code, data, and baseline details.
- Generalization is uncertain as evaluation uses only two geographically specific datasets (Hunan, Shanxi).
- System assumptions about cloud latency and resource constraints may not hold in all real-world edge-grid deployments.
