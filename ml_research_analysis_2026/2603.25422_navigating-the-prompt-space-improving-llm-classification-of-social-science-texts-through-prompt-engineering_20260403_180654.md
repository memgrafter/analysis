# Navigating the Prompt Space: Improving LLM Classification of Social Science Texts Through Prompt Engineering

## Quick Facts
- **arXiv ID:** 2603.25422
- **Source URL:** https://arxiv.org/abs/2603.25422
- **Reference Count:** 40
- **Primary Result:** Minimal prompt context (e.g., label descriptions, instructions, or few-shot examples) yields the largest accuracy gains (weighted F1 ↑ ~0.15), with further additions providing marginal or negative returns; optimal batch size is task-specific, and outputs are non-deterministic even at temperature=0.

## Executive Summary
This study systematically investigates prompt engineering for large language model (LLM) classification of social science texts. Across two distinct tasks—a 21-class policy topic classification and binary emotionality detection—using GPT-4o and Gemini 2.0 Flash, the authors find that adding a single prompt component (label descriptions, instructional nudges, or few-shot examples) to a baseline zero-shot prompt delivers the most substantial performance improvements. Further components often yield diminishing or negative returns. Batch processing multiple inputs in a single API call generally improves cost-efficiency and accuracy up to a task-specific threshold, beyond which performance declines. Critically, model outputs exhibit non-determinism even with temperature set to zero, and this variability is modulated by prompt complexity, underscoring the need for empirical validation for each deployment.

## Method Summary
The study employs a full factorial experimental design varying three binary prompt components (Label Descriptions, Instructional Nudges, Few-Shot Examples), five batch sizes (1, 10, 100, 500, 1000), and two proprietary LLMs (GPT-4o, Gemini 2.0 Flash). Two social science datasets are used: CAP congressional bill titles (21-class) and ANES survey responses (binary emotionality). For each configuration, prompts are constructed from predefined templates (Appendix A), submitted via API with temperature=0, and model labels are parsed and evaluated against ground truth using weighted F1 score as the primary metric. Each configuration is repeated to assess output variability.

## Key Results
- Adding a single prompt component (any of the three) to the baseline yields the largest weighted F1 improvements, up to ~0.15.
- Batch processing (sizes 10–500) typically outperforms single-text calls in both accuracy and cost, but very large batches (1000) cause significant performance collapse.
- Outputs are not fully deterministic at temperature=0; variability increases with prompt complexity and differs between models.

## Why This Works (Mechanism)
### Mechanism 1
**Claim:** Structured prompt components improve accuracy by providing in-context learning signals that reduce ambiguity and activate the model's latent knowledge.
**Mechanism:** Label descriptions clarify categorical boundaries, instructional nudges correct domain-specific misconceptions, and few-shot examples demonstrate the input-output mapping. Together, they steer the model beyond noisy zero-shot heuristics.
**Break condition:** Adding beyond an initial minimal set causes diminishing/negative returns, likely due to context saturation or distraction.

### Mechanism 2
**Claim:** Batch processing multiple inputs in a single call improves performance and cost-efficiency.
**Mechanism:** The model may leverage inter-sample context for more consistent labeling and amortizes fixed prompt-parsing overhead. Optimal batch size is task/model-specific.
**Break condition:** Batches that exceed an effective context window or cause attention dilution (e.g., size 1000) lead to significant performance decline.

### Mechanism 3
**Claim:** LLM outputs are not fully deterministic at temperature=0, and variability is modulated by prompt complexity.
**Mechanism:** Non-determinism may arise from floating-point parallelism, hardware execution paths, or residual stochasticity. Complex prompts increase sequential decisions, exacerbating variance.
**Break condition:** A fully local, fixed-seed, open-weight inference setup might mitigate this but was not tested.

## Architecture Onboarding
- **Component map:**  
  Prompt Template Engine -> Batch Formatter -> LLM API Client -> Evaluation Module -> Experiment Orchestrator
- **Critical path:** Define base prompt schema → Implement three component toggles → Integrate batch formatting → Run full factorial experiment → Analyze performance matrices → Identify optimal configuration (typically 1-2 components + optimal batch size).
- **Design tradeoffs:**  
  - *Context Depth vs. Saturation:* One component yields most gains; more adds cost with uncertain/negative returns.  
  - *Batch Size vs. Performance:* Batches 10–500 improve cost/accuracy vs. size 1; very large batches (1000) harm accuracy.  
  - *Reproducibility vs. Cost:* Multiple repeats per configuration needed to capture variance, increasing cost.
- **Failure signatures:**  
  - Sharp F1 drop at high batch sizes (e.g., 1000 for GPT-4o).  
  - Negative context effect: more components underperform simpler ones.  
  - High variance across repeats, especially with complex prompts and batch size 1.  
  - Class-specific collapse (near-zero recall/precision for some classes) despite acceptable overall F1.
- **First 3 experiments:**  
  1. **Baseline Establishment:** Run minimal prompt (`-,-,-`) across all batch sizes to establish zero-shot floor and default batch behavior.  
  2. **Single-Component Isolate:** Test `+,-,-`; `-,+,-`; `-,-,+` to identify which single component gives the largest absolute F1 gain.  
  3. **Optimal Batch Search:** Take best single-component configuration and test a wider batch range (e.g., 5, 20, 50, 200, 300) to pinpoint the performance peak before downturn.

## Open Questions the Paper Calls Out
- **Open Question 1:** What is the optimal number of few-shot examples for different classification tasks and models?  
  *Basis:* Future work needed to vary few-shot count/selection (Section 5). *Why unresolved:* Fixed at two per class. *Resolving evidence:* Systematic experiments varying few-shot size (1–25 per class) across tasks/models.
- **Open Question 2:** How do open-source LLMs compare to proprietary ones in prompt engineering effectiveness and output determinism?  
  *Basis:* Authors suggest replicating with open-source models (Section 5). *Why unresolved:* Only proprietary models tested. *Resolving evidence:* Replicate design with open-weight models (e.g., Llama, Mistral).
- **Open Question 3:** Under what conditions does adding prompt context reduce accuracy, and which components are most likely to cause such decreases?  
  *Basis:* Paper notes decreases but doesn't isolate components (Abstract, Section 4). *Why unresolved:* Analysis aggregates components. *Resolving evidence:* Ablation studies adding each component in isolation across batch sizes/models, analyzing error patterns.
- **Open Question 4:** What mechanisms cause non-deterministic outputs at temperature=0, and how does prompt complexity modulate this variability?  
  *Basis:* Variability observed and linked to prompt complexity (Section 4, Discussion). *Why unresolved:* Root causes not investigated. *Resolving evidence:* Quantify output variance (label disagreement) across repeated identical prompts with varying complexity, correlate with prompt length/batch size.

## Limitations
- Exact test set splits, few-shot selection methods, and parsing rules for malformed outputs are unspecified, blocking faithful replication.
- Only proprietary cloud-based LLMs tested; findings may not generalize to open-source/local models.
- No investigation into the root causes of non-determinism or the optimal number of few-shot examples.

## Confidence
- **Mechanism 1 (prompt components):** High. Strong within-paper evidence across tasks/models.
- **Mechanism 2 (batch size sweet spot):** Medium. Heterogeneity noted; optimal size/task specifics remain empirical.
- **Mechanism 3 (non-determinism):** High (observation), Medium (root cause). Empirically solid but mechanistic explanation speculative.
