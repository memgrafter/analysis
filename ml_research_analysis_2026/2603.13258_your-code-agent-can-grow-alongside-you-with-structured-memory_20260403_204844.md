# Your Code Agent Can Grow Alongside You with Structured Memory

## Quick Facts
- **arXiv ID:** 2603.13258
- **Source URL:** https://arxiv.org/abs/2603.13258
- **Reference count:** 40
- **Primary result:** MemCoder achieves a 77.8% resolved rate on SWE‑bench Verified with DeepSeek‑V3.2, a 9.4% absolute improvement over the baseline.

## Executive Summary
MemCoder is a code agent framework designed to co‑evolve with developers over time. It transforms raw repository commit histories into structured, retrievable memory entries that capture latent intent‑to‑code mappings. A verification‑driven self‑refinement loop corrects candidate patches in real‑time, and human‑approved solutions are internalized into long‑term memory, creating a closed learning cycle. Evaluated on SWE‑bench Verified, MemCoder sets a new state‑of‑the‑art, outperforming prior models by significant margins.

## Method Summary
MemCoder is not a trained model but an agent system built around three core mechanisms. First, an offline *memory construction* pipeline uses an LLM to convert each commit into a standardized sextuple (keywords, problem, root‑cause, solution), which is embedded and stored in a vector database. Second, during task execution, a *self‑refinement* process is triggered: a Refining Sub‑agent generates test code and a verification checklist, which are executed to expose integration errors and guide iterative fixes. Third, a *self‑internalization* step adds human‑validated solutions back into memory, allowing the agent to accumulate project‑specific knowledge. Retrieval employs a two‑stage “retrieval‑then‑rerank” approach (FAISS ANN followed by a cross‑encoder) to surface context‑aware precedents.

## Key Results
- Achieves **77.8% pass@1** on SWE‑bench Verified with DeepSeek‑V3.2, improving the previous state‑of‑the‑art (68.4%) by **9.4% absolute**.
- Reaches **83.8% pass@2** using GPT‑5.2, further demonstrating scalability.
- Ablation studies show that removing the verification‑driven self‑refinement (DSR) reduces performance by **1.4%**, highlighting its contribution.

## Why This Works (Mechanism)

### Mechanism 1: Structured Memory from Commit History
- **Claim:** Structuring historical commits into standardized memory entries enables agents to retrieve and apply latent intent‑to‑code mappings from past successful practices.
- **Mechanism:** Raw commits are processed by an LLM to produce a sextuple (keywords, problem, root‑cause, solution). These entries are embedded and stored in a vector database. At runtime, the agent queries this store using a two‑stage retrieval (ANN + cross‑encoder rerank) to obtain context‑aware precedents, which concretize abstract instructions.
- **Core assumption:** Repository histories contain reusable patterns inaccessible from a static snapshot but distillable into agent‑friendly forms.
- **Evidence anchors:** [abstract] “structures historical human experience to distill latent intent‑to‑code mappings”; [section 3.1] defines the sextuple and construction pipeline; [corpus] neighboring work on long‑term memory discusses structuring but validation is limited to this paper.
- **Break condition:** Retrieval precision degrades if top‑k is too large (Figure 5); also ineffective if the project history lacks relevant precedents.

### Mechanism 2: Verification‑Driven Self‑Refinement
- **Claim:** A dedicated Refining Sub‑agent, driven by verification feedback, iteratively corrects candidate code before final submission.
- **Mechanism:** Given the current problem and retrieved memories, the sub‑agent generates test code *t* and a verification checklist *l*. These are executed; outcomes update the feedback state and steer the Primary Agent’s next actions. This loop repeats until the solution passes verification.
- **Core assumption:** Real‑time, automated testing exposes subtle misalignments between the agent’s output and repository‑specific conventions that static reasoning misses.
- **Evidence anchors:** [abstract] “employs a self‑refinement mechanism driven by verification feedback”; [section 3.2] formalizes the process with equations (8) and (9); [section 4.3] ablation (“w/o DSR”) shows a 1.4% drop.
- **Break condition:** Generated tests may be incomplete or checklists ambiguous; computational cost can become prohibitive for long‑running tasks.

### Mechanism 3: Closed‑Loop Experience Internalization
- **Claim:** Internalizing human‑validated solutions into long‑term memory creates a closed‑loop co‑evolution, allowing the agent to accumulate knowledge across tasks.
- **Mechanism:** Once a patch passes automated tests and receives human approval, the commit is processed by the memory constructor and added to the memory bank (equation 10). Over time, the memory shifts from purely human priors to mixtures of human‑agent co‑evolved entries.
- **Core assumption:** Human review reliably filters out erroneous solutions; re‑structuring commits reinforces the intent‑to‑code mapping.
- **Evidence anchors:** [abstract] “experience self‑internalization mechanism…crystallize human‑validated solutions”; [section 3.2] describes the update rule; [section 4.2] improvement over DeepSeek‑V3.2 suggests cumulative memory benefit, though internalization’s exact contribution is inferred.
- **Break condition:** Inconsistent human validation or memory saturation with low‑quality entries could degrade future retrievals.

## Foundational Learning
- **Structured Memory Representation**  
  *Why needed:* Raw commits are noisy and implicit; a consistent schema (sextuple) extracts reusable intent and solution patterns.  
  *Quick check:* How would you represent a commit fixing a database column name mismatch? (Answer: keywords: column name, db_column; problem: ON CONFLICT uses field name not db_column; root cause: misuse of field.name vs field.column; solution: replace references with field.column.)
- **Verification‑Driven Self‑Refinement**  
  *Why needed:* Single‑shot generation misses integration‑level errors only visible when code interacts with the repo’s environment.  
  *Quick check:* What two artifacts does the Refining Sub‑agent produce, and how are they used? (Answer: test code *t* to exercise the change, and verification checklist *l* to guide the Primary Agent’s fixes.)
- **Closed‑Loop Internalization Cycle**  
  *Why needed:* Without retaining successful fixes, the agent cannot learn progressively and will repeat mistakes.  
  *Quick check:* When is a new memory entry created, and what triggers its construction? (Answer: After a human‑validated solution is committed; the trigger is inclusion of that commit in the subsequent memory synchronization phase.)

## Architecture Onboarding
- **Component map:** Git Repository -> Memory Constructor -> Vector Store (FAISS) -> Cross-Encoder Reranker -> Primary Agent; Primary Agent -> Refining Sub‑agent; Refining Sub‑agent produces test code *t* and checklist *l*; *t* executed; upon Human Reviewer approval, new commit added to Git Repository.
- **Critical path:**  
  1. Issue arrives; system updates memory from new commits (Stage 1).  
  2. Primary Agent initiates retrieval → obtains relevant memories.  
  3. Primary Agent proposes code patch → Refining Sub‑agent generates *t*, *l*.  
  4. Execute *t*; if pass, proceed to human review.  
  5. If human approves, commit is stored; Memory Constructor adds it to the vector store.  
  6. Loop until solved or step limit.
- **Design tradeoffs:**  
  - *Retrieval granularity:* Larger `top‑k` provides broader context but risks noise; tuning needed per dataset.  
  - *Memory construction cost:* LLM summarization per commit adds latency but improves retrieval precision.  
  - *Verification overhead:* Running tests each iteration slows execution but catches integration bugs.
- **Failure signatures:**  
  - No relevant memories retrieved → agent relies on generic knowledge, leading to lower success.  
  - Refining Sub‑agent repeatedly fails to produce passing tests → weak verification logic or missing repo context.  
  - Human rejection rate high → agent’s solutions misalign with project standards despite refinement.  
  - Performance degrades when `top‑k` exceeds optimal range (e.g., >16) due to “lost‑in‑the‑middle” effect (Figure 5).
- **First 3 experiments:**  
  1. **Baseline replication:** Run MemCoder with DeepSeek‑V3.2 on SWE‑bench Verified; confirm ~77.8% pass@1.  
  2. **Ablation study:** Disable CR, ER, DSR modules individually and measure change; expect drops as in Table 2.  
  3. **Retrieval tuning:** Sweep `top‑k` values (1–64) and plot resolved rate vs. retrieval frequency (replicate Figure 4) to identify optimal context size.

## Open Questions the Paper Calls Out
1. **Sensitivity of memory construction:** How does commit message quality or prompt template variations affect memory quality and final resolution? The paper uses an LLM to structure “non‑standardized” commits but provides no robustness analysis.
2. **Accuracy of generated tests/checklists:** What is the correctness of the Refining Sub‑agent’s outputs, and how does their quality correlate with the net benefit of the refinement loop? The component’s output is never validated.
3. **Cumulative memory corruption:** Does permanent internalization without forgetting lead to degradation if occasional erroneous solutions are accepted? The update rule (equation 10) assumes human validation is always correct.
4. **Generalization across languages/models:** Evaluation is restricted to Python (SWE‑bench Verified) and proprietary models (DeepSeek‑V3.2, GPT‑5.2). The framework’s applicability to other languages or open‑source LLMs remains untested.

## Limitations
- Exact prompt templates (`P_gen`, `P_refine`), embedding/reranker models, and sub‑agent triggering policy are undisclosed, hindering reproducibility.
- Evaluation is confined to SWE‑bench Verified; generalizability to other domains, languages, or real‑world workflows is unknown.
- Computational overhead from repeated testing and memory updates is not quantified; scalability to large repositories is unclear.
- Human validation is approximated by test passes in the benchmark, which may not reflect actual developer review quality.

## Confidence
- **Structured memory (CR):** Medium – Evidence includes internal results and an ablation drop (magnitude unspecified); effectiveness depends on existence of relevant precedents and optimal top‑k.
- **Verification‑driven refinement (DSR):** High – Ablation removing DSR reduces performance by 1.4%, demonstrating a measurable, isolated contribution.
- **Closed‑loop internalization (ER):** Medium – The overall improvement over baselines suggests benefit, but the exact impact of internalization is not isolated and could suffer from noise or saturation.

## Next Checks
1. **Internalization isolation:** Freeze the memory bank after initial construction (no new entries) and re‑evaluate; the performance difference quantifies internalization’s contribution.
2. **Retrieval robustness:** Sweep `top‑k` (e.g., 1–64) and record resolved rate plus precision@k; also compare different embedding models (e.g., `all‑MiniLM‑L6‑v2` vs. `text‑embedding‑ada‑002`) to gauge sensitivity.
3. **Memory quality audit:** Randomly sample 100 memory entries across repositories and have human annotators judge correctness of `problem`, `root‑cause`, and `solution`; correlate annotation scores with retrieval‑task success to validate the structuring assumption.
