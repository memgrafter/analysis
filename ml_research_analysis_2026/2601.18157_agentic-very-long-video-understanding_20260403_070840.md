# Agentic Very Long Video Understanding
## Quick Facts
- **arXiv ID**: 2601.18157
- **Source URL**: https://arxiv.org/abs/2601.18157
- **Reference count**: 40
- **Primary result**: EGAgent achieves 57.5% accuracy on EgoLifeQA (+20.6% absolute over prior SOTA) and 74.1% on Video-MME (Long), with especially large gains on RelationMap (+32%) and TaskMaster (+39.7%).

## Executive Summary
This paper presents EGAgent, an agentic framework for continuous week-long egocentric video understanding, tailored for always-on AI assistants. The core innovation lies in constructing a time-aware entity scene graph that captures people, objects, places, and their relationships with precise temporal intervals. A planning agent decomposes complex queries and orchestrates hybrid search tools—visual embeddings, audio transcripts, and structured graph queries—to retrieve cross-modal evidence. On the EgoLifeQA benchmark, EGAgent achieves 57.5% accuracy, a 20.6% absolute improvement over the previous state-of-the-art, and reaches 74.1% on the long-video subset of Video-MME. Notably, it gains +32% on RelationMap and +39.7% on TaskMaster, both of which require multi-hop, longitudinal reasoning, while processing over ten times fewer frames than prior video RAG systems.

## Method Summary
EGAgent operates in three stages. First, it extracts a temporal entity graph from fused 30-second video captions and audio transcripts. Each graph edge (subject, relation, object, start time, end time) is stored as a row in a SQLite database. Second, given a query, a planning agent generates a sequence of sub-tasks, each paired with a retrieval tool. The visual tool searches SigLIP 2 frame embeddings; the audio tool searches transcripts; the graph tool executes SQL queries. A “strict-to-relaxed” query policy maximizes precision while handling imperfect temporal anchors. Third, an analyzer tool summarizes each tool's output and appends it to a working memory. After all sub-tasks are satisfied, a final VQA agent consumes the query and working memory to answer. This modular, iterative design avoids stuffing all modalities into a single prompt and enables precise evidence aggregation over week-long streams.

## Why This Works (Mechanism)
### Mechanism 1: Temporal Entity Scene Graphs
The system extracts a graph \(G=(V,E)\) where each edge \(e=(v_s, v_t, r, t_{start}, t_{end})\) is stored in a SQLite database. This structure explicitly encodes entities (people, objects, places) and their relationships with precise temporal intervals, enabling structured, cross-modal reasoning over very long videos. The core assumption is that relationships derived from 30-second fused captions are accurate and temporally localizable enough for longitudinal queries when aggregated. Evidence: The abstract describes entity scene graphs representing entities and relationships over time; Section 3.2 details edge annotation and SQLite storage; Table 4 shows large gains on RelationMap (+32%) and TaskMaster (+39.7%), which require multi-hop, longitudinal reasoning and are attributed to the graph. Break condition: If the extraction LLM fails to identify correct entities or temporal anchors (e.g., due to noisy ASR or poor visual captions), query precision collapses; Table 3 shows a ~6% drop when using BM25 instead of LLM-based transcript search, indicating sensitivity to extraction quality.

### Mechanism 2: LLM-based Planning Agent
A planning agent decomposes a complex query into a sequence of sub-tasks \((S_i, T_i, q_i)\) and selects the appropriate retrieval tool for each. This prevents context overflow and enables targeted evidence gathering. The core assumption is that a frontier LLM (e.g., GPT-4o, Gemini 2.5 Pro) can reliably decompose long-horizon video questions and map sub-tasks to the correct tool modality. Evidence: The abstract mentions query decomposition and hybrid search tools; Section 3.3 (Algorithm 1) shows joint decomposition and tool selection with working memory accumulation; Table 5 shows removing the entity graph tool hurts RelationMap accuracy by 23.2%, demonstrating the value of structured tool orchestration. Break condition: If the planner misroutes sub-tasks (e.g., sends an entity-relationship query to visual search only), working memory lacks structured relational data, crippling multi-hop reasoning; no direct failure rate is reported.

### Mechanism 3: Strict-to-Relaxed Query Strategy
When querying the SQLite graph, the agent first issues an exact-match query on all fields (day, timestamps, entity names, relation type). If no results, it incrementally relaxes constraints: broadens time window, allows partial text matching (`LIKE`), drops relation type, then searches only by entity name. The core assumption is that the most precise matches are most likely correct; relaxing only when necessary reduces hallucination and irrelevant rows. Evidence: Section 3.3 describes the “strict-to-relaxed” policy; Figure 6 shows a strict query returning multiple rows, then the analyzer filters relevant ones; related work on agentic search supports adaptive retrieval. Break condition: If the initial strict query is too brittle (e.g., a 2-second transcription error prevents any match) and relaxation steps fail to recover relevant rows quickly, critical evidence is missed; Appendix D.3 shows entity graph recall is lower than visual search at fine granularity, indicating potential gaps in temporal anchoring.

## Foundational Learning
1. **Graph Databases & SQL Querying**  
   *Why needed*: The entity graph is stored as a SQLite table; the planning agent generates SQL to filter by time, entity, and relation type. Engineers must understand relational querying to extend or debug retrieval logic.  
   *Quick check*: How would you write a SQL query to find all `USES` relationships involving a "phone" between 10:00 and 11:00 on day 3?

2. **Agentic Tool Orchestration (e.g., LangGraph)**  
   *Why needed*: EGAgent is a state machine with conditional edges (planner → tool → analyzer → memory). Engineers need to grasp how state is passed, how loops terminate, and how tools are selected.  
   *Quick check*: What happens if the analyzer tool determines the retrieved context is irrelevant? Which component decides the next step?

3. **Temporal Reasoning & Annotation**  
   *Why needed*: Edges are annotated with `(tstart, tend)` derived from fused captions and transcripts. Mapping noisy ASR timestamps or textual time mentions (“after lunch”) to precise graph intervals is crucial for retrieval quality.  
   *Quick check*: If a transcript says “Jake: Let’s go” from 14:05:10 to 14:05:15, and a visual caption describes “Jake uses keys” from 14:05:12 to 14:05:20, how should the `Jake → USES → Keys` edge be temporally anchored?

## Architecture Onboarding
**Component map**:  
Planning Agent → Retriever Tools (T_vis, T_aud, T_eg) → Analyzer Tool → VQA Agent. Working memory (M) updated after each analyzer step; planner loops until all sub-tasks satisfied.

**Critical path**:  
1. Input query **Q** → Planner generates plan list of \((S_i, T_i, q_i)\).  
2. Router sends first sub-task to chosen tool \(T_i\).  
3. Tool returns raw data → Analyzer analyzes → **M** updated.  
4. Check if **M** covers all sub-tasks; if yes, proceed to VQA; else, Planner picks next sub-task.  
5. Repeat steps 2–4 until plan complete.

**Design tradeoffs**:  
- Entity graph sparsity vs recall: Coarse relations (`TALKS_TO`, `USES`) improve recall but lose nuance (e.g., `whispers_to`).  
- Transcript search speed vs quality: BM25 is 3.6× faster than LLM search but drops ~6% accuracy; LLM search is default.  
- Frame sampling rate: 1 FPS visual DB balances coverage and storage but adds latency.

**Failure signatures**:  
- **Planner looping**: If **M** never satisfies future sub-tasks, planner keeps generating new ones (max 5 sub-tasks limit).  
- **Entity graph empty**: Extraction failure (no edges) forces fallback to visual/audio only, hurting relational accuracy.  
- **Analyzer hallucination**: Analyzer may synthesize facts not in retrieved data, contaminating **M** and leading to wrong answers.

**First 3 experiments**:  
1. **Tool ablation** (Table 5): Run EGAgent with EG only, F+T, and EG+F+T on EgoLifeQA. Expect full fusion to excel on RelationMap/TaskMaster, confirming cross-modal benefits.  
2. **Oracle vs. tool search** (Table 6, 7): Replace tool searches with ground-truth timestamps. Expect oracle to close ~12% gap, highlighting temporal localization as a bottleneck.  
3. **Strict-to-relaxed ablation**: Modify T_eg to use strict-only, relaxed-only, or hybrid. Hybrid should balance precision and recall better than extremes.

## Open Questions the Paper Calls Out
1. **How does EGAgent's performance degrade when using off-the-shelf automatic speaker diarization instead of manual diarization for audio transcripts?**  
   *Basis in paper*: [explicit] In the limitations section, the authors note: “our experiments relied on transcripts and for EgoLife, manually annotated speaker diarization. In scenarios where off-the-shelf diarization models are used, downstream performance is likely to be adversely affected by prediction errors.”  
   *Why unresolved*: The paper only evaluates with perfect manual diarization; the robustness to realistic diarization errors (e.g., speaker confusion, overlaps) is unknown, which is critical for deployment on unscripted, everyday video.  
   *What evidence would resolve it*: Conduct experiments on EgoLifeQA by artificially degrading diarization quality (e.g., introducing word error rate or speaker label noise) or using real ASR+diarization pipelines; measure accuracy drop across question types (RelationMap, TaskMaster, etc.) to identify failure modes.

2. **Can the entity scene graph be incrementally constructed and updated in a streaming manner as new video segments arrive, without re-processing the entire history, and what are the trade-offs in accuracy, memory usage, and latency?**  
   *Basis in paper*: [explicit] Section 3.2 states: “The graph construction process supports incremental updates as new documents arrive, allowing G to grow and refine over time.” However, the implementation and evaluation are batch-oriented (per hour or per video).  
   *Why unresolved*: Real-world always-on assistants require continuous online updates. Incremental construction may lead to entity inconsistency, duplicate nodes, or outdated relations, but the paper provides no empirical validation or cost analysis.  
   *What evidence would resolve it*: Build a streaming version of the entity graph extractor; process EgoLife week-long video chronologically and compare the resulting graph (completeness, edge accuracy) against a batch-extracted gold standard. Track memory consumption, update latency, and downstream QA performance to quantify trade-offs.

3. **How does EGAgent scale to extremely long video durations (e.g., months or years) in terms of entity graph size, retrieval efficiency, and reasoning accuracy, and do the current tool selections and planning strategies remain effective?**  
   *Basis in paper*: [explicit] The paper targets “very long” videos of 50+ hours over a week, as defined in the introduction and evaluated on EgoLife. Scaling beyond this horizon is not investigated.  
   *Why unresolved*: Longer durations could cause the entity graph to explode in size (millions of nodes/edges), degrade retrieval and planning latency, and require deeper multi-hop reasoning. The current planning agent uses up to five sub-tasks; it may not suffice for years-long reasoning.  
   *What evidence would resolve it*: Simulate longer videos by concatenating multiple weeks of EgoLife or generating synthetic long-form data; measure graph growth (nodes/edges), query execution times, and QA accuracy. Test whether the planning agent needs hierarchical decomposition or other adaptations to maintain performance.

## Limitations
- Planner reliability: No direct metrics on tool-routing errors; assumes frontier LLMs consistently map sub-tasks to correct modalities.
- Graph extraction quality: Core assumption that 30-second fused captions yield temporally precise, accurate relationships; no error analysis for entity/relation/timestamp extraction.
- Strict-to-relaxed efficacy: Strategy’s recall-precision trade-off is described but not ablated against simpler baselines (e.g., always-relaxed).

## Confidence
- **High**: Framework existence & reported SOTA gains (EgoLifeQA +20.6%, Video-MME +74.1%).
- **Medium**: Role of entity graphs & planning agent (supported by ablations but not causal isolation).
- **Low**: Assumption of robust temporal anchoring & planner orchestration (no failure-rate data).
