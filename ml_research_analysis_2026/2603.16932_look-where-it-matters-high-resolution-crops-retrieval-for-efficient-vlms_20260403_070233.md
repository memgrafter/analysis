# Look Where It Matters: High-Resolution Crops Retrieval for Efficient VLMs

## Quick Facts
- **arXiv ID:** 2603.16932
- **Source URL:** https://arxiv.org/abs/2603.16932
- **Reference count:** 40
- **Primary result:** AwaRes achieves 80.30% average accuracy across six benchmarks with only 36% of visual tokens (RTR=0.36), matching the full-resolution baseline (80.46%) and reducing latency by 4.4×.

## Executive Summary
Vision-language models (VLMs) face a trade-off between accuracy and computational efficiency, as processing high-resolution images demands many visual tokens. This paper introduces AwaRes, a framework that resolves this by using a low-resolution global view and selectively retrieving high-resolution crops only when necessary via tool-calling. A two-stage training process, combined with an automatic data curation pipeline, enables the model to make coupled decisions on whether and where to crop. AwaRes matches full-resolution accuracy while using only 36% of tokens, outperforming prior adaptive methods in both accuracy and efficiency.

## Method Summary
AwaRes employs an automatic data curation pipeline to create multi-turn training trajectories. An LLM judge determines if a query requires high resolution (HR) based on low- vs. full-resolution model answers, and an oracle VLM localizes the answer region via bounding boxes. These are mapped to a predefined set of 10 discrete crops (quadrants, halves, center, full). Training proceeds in two stages: first, cold-start supervised fine-tuning (SFT) on the curated trajectories teaches the model the tool-calling protocol; second, multi-turn GRPO fine-tuning optimizes a reward combining semantic correctness (via sentence transformer similarity) and asymmetric crop-cost penalties. At inference, the model processes the low-resolution image in the first turn; if it emits a tool call (GET_CROPS: [...]), the specified high-resolution crops are retrieved and appended to the KV cache for a second-turn answer generation.

## Key Results
- Average accuracy 80.30% across six benchmarks, matching the full-resolution baseline (80.46%) while using only 36% of visual tokens (RTR=0.36).
- Outperforms VisionThink (adaptive baseline) in accuracy (80.30 vs. 79.23) and efficiency (RTR 0.36 vs. 0.61).
- Reduces wall-clock latency by 4.4× on average compared to full-resolution processing.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Processing only spatially sparse high-resolution crops preserves accuracy while drastically reducing visual token count.
- **Mechanism:** The model uses a low-resolution global view for most queries; only when query details require fine-grained perception (e.g., small text) does it invoke a tool call to retrieve specific high-resolution crops from a predefined discrete set. This exploits the observation that high-fidelity demand is usually localized.
- **Core assumption:** The answer-evidence region can be approximated by one of the predefined coarse crops (quadrants, halves, center, full).
- **Evidence anchors:** Abstract: "operating on a low-resolution global view and using tool-calling to retrieve only high-resolution segments needed"; Section 3.1: "the demand for high fidelity is usually spatially sparse."

### Mechanism 2
- **Claim:** A fused coupled-decision policy (CDP) that jointly decides whether to escalate and where to crop is more efficient than decoupled or global escalation.
- **Mechanism:** The first-turn action emits either a direct answer or a structured crop request (GET_CROPS: [...]). This fuses the two decisions, preventing the waste of requesting the full high-resolution image when only a small region is needed.
- **Core assumption:** The value of escalating depends on which regions are retrieved; inaccurate localization wastes compute.
- **Evidence anchors:** Section 3.1: "these decisions are fused into the model’s first-turn action... The two are inherently coupled."; Section 4.5: AwaRes uses RTR 0.36 vs. VisionThink's 0.61 at higher accuracy.

### Mechanism 3
- **Claim:** Two-stage training (cold-start SFT → multi-turn GRPO) reliably instills tool-use behavior and then optimizes the explicit accuracy–efficiency trade-off.
- **Mechanism:** SFT on automatically curated trajectories establishes a robust reference policy that knows the tool protocol. GRPO then refines this policy using a reward that combines semantic correctness with asymmetric crop-cost penalties (penalizing missed calls more than unnecessary ones, and penalizing total crop area).
- **Core assumption:** The model will not spontaneously learn structured tool-calling and cost-sensitive cropping from scratch with RL alone.
- **Evidence anchors:** Section 3.3: "cold-start supervised fine-tuning... teaches the model to follow the multi-turn tool-calling protocol."; Section 3.4: "multi-turn GRPO... explicitly optimizing the accuracy–efficiency trade-off."; Section 4.6: Ablation shows "GRPO only" achieves lower accuracy (77.11) and higher RTR (0.31) vs. full method (80.30, 0.36).

## Architecture Onboarding

- **Component map:** Low-Resolution Encoder -> Coupled-Decision Policy (CDP) -> Tool Interface & Cache Manager -> (optional) High-Resolution Crops -> Second Turn -> Answer. Reference policy π_ref used for KL penalty.

- **Critical path (inference):** Input (q, I_low) -> First Turn (CDP decides: Answer? OR GET_CROPS: C_req?) -> IF tool call: Append {I_high_c for c in C_req} to KV cache -> Second Turn -> Final Answer. KV cache from first turn is reused.

- **Design tradeoffs:** 
  - Discrete crop set vs. continuous boxes: Discrete set (10 regions) ensures predictable compute but limits spatial precision; continuous boxes future work.
  - Tool-call verbosity vs. latency: Short structured calls (GET_CROPS: [...]) minimize extra decoding vs. verbose reasoning traces.
  - SFT initialization vs. pure RL: SFT needed to bootstrap reliable tool protocol; pure GRPO fails (Table 4).

- **Failure signatures:**
  - Malformed tool call: Output cannot be parsed into C ⊆ C (Table 5: ~10% failure without SFT emphasis).
  - Over-cropping: High call rate and large requested area (e.g., all crop) → high RTR, low efficiency.
  - Under-cropping (missed calls): Low recall on y=HR samples → accuracy drop on detail-sensitive tasks.
  - Localization error: Requested crop has low IoU with oracle target C⋆ → may answer incorrectly despite high-res evidence.

- **First 3 experiments:**
  1. Validate CDP calibration: On held-out set with known y=HR/LR, measure call precision/recall/FPR and requested area. Expect high recall on HR, low FPR on LR after GRPO.
  2. Reward component ablation: Run GRPO with λ=0 (no area cost) and without C_tool. Predicted: RTR increases (Table 4: 0.36→0.51) with mixed accuracy impact.
  3. Latency vs. accuracy benchmark: Replicate Table 1 & Fig. 4 on fixed hardware (H100). Verify AwaRes achieves ~4× latency reduction vs. VisionThink while matching/exceeding its accuracy. Check tool-call parsing success rate >98%.

## Open Questions the Paper Calls Out
1. Can AwaRes be extended to predict continuous bounding boxes for crop selection, and how does this impact the accuracy-efficiency trade-off? (Conclusion mentions future work on discrete to continuous.)
2. How can spatial-on-demand perception be effectively generalized to video understanding to exploit temporal sparsity, and what architectural modifications are needed? (Conclusion mentions video as promising direction.)
3. To what extent does the automatic data curation pipeline rely on large proprietary models (LLaMA-3.3-70B, Qwen3-VL), and can this dependency be reduced? (Section 3.2 uses proprietary models; ablations show sensitivity to choice.)
4. How sensitive is the accuracy-efficiency trade-off to the hyperparameters of the GRPO reward (α_miss, α_use, λ), and can they be set automatically per task? (Values fixed; not swept.)
5. Could allowing iterative multi-crop requests (more than one tool call) improve accuracy for queries needing evidence from multiple dispersed regions, and what are the efficiency costs? (Current policy makes single tool call; richer strategies mentioned but unexplored.)

## Limitations
- Oracle grounding model (Qwen3-VL) and LLM judge (LLaMA-3.3-70B) are proprietary; substitutions may alter curation quality and crop annotations.
- Exact definitions of the 10 discrete crops (precise rectangles) are not fully specified.
- GRPO implementation details (log-prob handling across turns, KL computation) rely on unspecified code modifications.

## Confidence
- Accuracy–efficiency trade‑off claim (80.30% vs. 80.46% with RTR 0.36): Medium. Core result holds, but depends on automatic curation; judge/oracle substitutions may shift numbers.
- Coupled‑policy superiority over global escalation: High. Ablation vs. VisionThink shows consistent gains.
- Two‑stage training necessity (SFT → GRPO): High. Ablation confirms GRPO alone fails to adopt tool use; SFT bootstraps protocol.
- Break conditions for spatially distributed fine details: Low–Medium. Theoretical; not systematically benchmarked.
