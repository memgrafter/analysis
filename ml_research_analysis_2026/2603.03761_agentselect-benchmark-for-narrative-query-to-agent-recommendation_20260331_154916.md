# AgentSelect: Benchmark for Narrative Query-to-Agent Recommendation

## Quick Facts
*   **arXiv ID:** 2603.03761
*   **Source URL:** https://arxiv.org/abs/2603.03761
*   **Reference Count:** 40
*   **Primary Result:** Converts heterogeneous evaluation artifacts into a benchmark with 111,179 queries and 107,721 agents; content-aware matching dominates long-tail regimes, and models transfer to a real marketplace (MuleRun), improving nDCG@10 from 0.5491 to 0.5870.

## Executive Summary
The paper addresses the fragmented evaluation of LLM agents by introducing AgentSelect, a large-scale benchmark for end-to-end agent recommendation conditioned on natural language narratives. The core method systematically recasts existing leaderboard scores and tool-use benchmark results into a unified, positive-only query–agent interaction format over capability profiles (model backbone + toolset). This process yields a massive dataset of 251,103 positive interactions. Key results show that content-aware retrieval models (e.g., TwoTower with BGE-M3) significantly outperform ID-based collaborative filtering and graph methods on the long-tail parts of the benchmark. The approach transfers to a real-world agent marketplace (MuleRun), demonstrating practical utility, and counterfactual intervention analyses confirm that models learn meaningful capability sensitivities.

## Method Summary
The benchmark construction comprises three parts. Part I derives positive interactions from LLM-only leaderboards by taking top-ranked models per query as positives. Part II uses tool-use benchmarks where a gold toolkit for a query defines positives. Part III synthesizes compositional agents: for a set of prototype queries, it trains retrievers on Parts I and II to fetch top-k LLMs and tools, then forms candidate agents via cross-product; retrieved (model, tool) pairs are marked positive. Agents are represented by textual descriptions of their LLM backbone and toolset, with optional discrete IDs. Models are trained on these implicit-positive interactions, typically using an InfoNCE loss with in-batch negatives. Evaluation uses ranking metrics (Precision@k, nDCG@k, MRR@k) with a fixed candidate pool per query to simulate realistic sparsity.

## Key Results
*   Content-aware matching (TwoTower with BGE-M3) dominates the long-tail Part III of the benchmark, achieving nDCG@10 of 0.8501 and MRR@10 of 0.8654.
*   ID-based collaborative filtering and graph neural network methods (MF, NGCF, KGAT, LightGCN) perform well on the dense head (Part I) but collapse on Parts II and III.
*   Models trained on AgentSelect transfer to the real MuleRun marketplace, improving nDCG@10 from 0.5491 to 0.5870 and Precision@1 from 0.3556 to 0.4000.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** Converting fragmented evaluation artifacts into a unified positive-only query–agent interaction format provides scalable supervision for learning agent recommendation.
*   **Mechanism:** Each deployable agent is a capability profile (M, T). Existing evaluation signals (per-query model rankings, gold toolkits) are treated as implicit positive feedback, transforming component-level scores into query-conditioned preferences over end-to-end configurations.
*   **Core Assumption:** The mapping from evaluation outcomes to positive interactions preserves meaningful capability distinctions; a top-ranked model/tool for a benchmark query implies suitability for semantically similar narrative queries.
*   **Evidence Anchors:** The benchmark yields 111,179 queries and 107,721 agents [abstract]. Construction details are in Section 4.2 (three-part synthesis). The assumption relies on community artifacts containing reusable signal.
*   **Break Condition:** If upstream artifacts are misaligned with deployment success (e.g., leaderboard tasks are not representative of user narratives), derived positives may not reflect real-world utility.

### Mechanism 2
*   **Claim:** The shift from dense head reuse (Part I) to long-tail, near one-off supervision (Parts II/III) makes content-aware capability matching dominant over ID-based collaborative filtering.
*   **Mechanism:** Part I features a few popular agents repeatedly evaluated, enabling CF/GNN to exploit ID co-occurrence. Parts II/III have vastly larger agent catalogs with minimal reuse, forcing generalization via semantic matching of query text to agent content descriptions rather than memorizing popular IDs.
*   **Core Assumption:** Agent capability profiles (textual descriptions of LLMs and tools) are sufficiently descriptive to enable semantic matching with narrative queries; ID-based shortcuts fail when agents are rarely repeated.
*   **Evidence Anchors:** Authors identify a "regime shift" in analysis [abstract]. Table 2 and Figure 4 show CF/GNN excelling on Part I but collapsing on Part II/III, while content-aware TwoTower (BGE-M3) dominates Part III. Ablation (Table 7) shows removing IDs mildly affects performance, while IDs alone underperform.
*   **Break Condition:** If agent textual descriptions are poor or mismatched to query language (e.g., overly technical tool docs), content matching may fail even with sparse IDs.

### Mechanism 3
*   **Claim:** Counterfactual capability edits reveal that models learn sensitivity to configuration details (tool relevance, backbone strength), validating the quality of synthesized pseudo-positives.
*   **Mechanism:** After training a ranker, interventions are made on a positive agent (e.g., remove a key tool, swap to a weaker backbone). Consistent negative shifts in score/rank indicate the model has learned meaningful capability representations rather than spurious correlations.
*   **Core Assumption:** A capable recommender should assign lower utility to agents with reduced or mismatched capabilities relative to the query's inferred needs.
*   **Evidence Anchors:** Abstract mentions counterfactual edits. Table 4 shows significant score drops and rank degradations after removing key/secondary tools, adding irrelevant tools, or swapping to a lower-ranked backbone; adding redundant tool has minimal expected effect.
*   **Break Condition:** If training data contains systematic biases (e.g., certain tools always co-occur with strong backbones), the model might not isolate true capability contributions, leading to inconsistent counterfactual responses.

## Foundational Learning
*   **Concept: Positive-only implicit feedback (BPR-like learning)**
    *   *Why needed:* The benchmark provides only observed positive query–agent interactions; models must treat unobserved agents as implicitly negative or unlabeled.
    *   *Quick Check:* Given a query with 5 positive agents out of 10,000 candidates, how should the loss function treat the 9,995 unobserved agents?

*   **Concept: Two-tower retrieval architecture**
    *   *Why needed:* Enables efficient large-catalog ranking by embedding queries and agents separately, then scoring via dot product. Dominates in long-tail regimes where content matching is key.
    *   *Quick Check:* Why might a two-tower model generalize better than an ID-based matrix factorization when agent catalogs are large and sparse?

*   **Concept: Capability profiling (M, T abstraction)**
    *   *Why needed:* Represents agents as (backbone model, toolset) pairs, the minimal deployable unit. This abstraction decouples recommendation from runtime specifics and allows systematic comparison.
    *   *Quick Check:* What are the limitations of using (M, T) versus full YAML configurations (including policies) for agent selection?

## Architecture Onboarding
*   **Component map:** Data Ingestion -> Feature Encoder -> Scoring Head -> Evaluation Harness. Optionally, a Graph Builder feeds into the Scoring Head for CF/GNN baselines.
*   **Critical path:**
    1.  Preprocess raw artifacts to extract unified (query, agent ID, positive flag) triples per Part (I/II/III).
    2.  Train/fine-tune text encoders (e.g., BGE-M3) or use TF-IDF on in-domain data.
    3.  For CF/GNN baselines, build an interaction matrix using query IDs approximated via TF-IDF KNN.
    4.  Evaluate per-part with a fixed sampled candidate pool (size 1,000) to simulate realistic sparsity.
    5.  For transfer tests (MuleRun), map new agents to Part II-like tool primitives.
*   **Design tradeoffs:**
    *   **Content vs. IDs:** IDs risk popularity bias; content-only generalizes to new agents but requires high-quality descriptions.
    *   **Implicit vs. explicit negatives:** Using all unobserved as negatives is noisy; in-batch negatives mitigate but may still include plausible candidates.
    *   **Part III synthesis quality:** Pseudo-positives from component retrieval may not reflect true execution success; counterfactual sensitivity helps but is not a full execution guarantee.
*   **Failure signatures:**
    *   High recall but low nDCG/MRR → ranking quality poor; model retrieves some positives but cannot order them well.
    *   Performance drop on Part II/III vs. Part I → over-reliance on ID-based patterns; content encoder weak or not fine-tuned.
    *   Counterfactual edits show low consistency → model not capability-aware; may be exploiting dataset artifacts (e.g., tool co-occurrence with specific LLMs).
*   **First 3 experiments:**
    1.  **Baseline replication:** Train a TwoTower (TF-IDF) on Part I only; expect high performance (nDCG >0.9) due to dense reuse. Validate that query-ID features are heavily used.
    2.  **ID ablation:** Train TwoTower on Part III with/without LLM/tool IDs; expect minor drop when removing IDs, confirming content-driven matching.
    3.  **Part III contribution:** Train on Parts I+II vs. I+II+III; expect large gain on Part III evaluation indicating learnable, non-redundant signal.

## Open Questions the Paper Calls Out
The paper highlights several open questions stemming from its limitations and assumptions:

*   **Artifact-narrative alignment:** How can we ensure that evaluation artifacts (e.g., leaderboard queries, tool-use benchmarks) are representative of real user narratives, given the assumption that top-ranked models for benchmark queries imply suitability for similar narrative queries?
*   **Description sufficiency:** To what extent do textual agent descriptions (LLM backbone and toolset) capture the nuanced compatibility factors (e.g., parameter conventions, cost considerations) that affect real-world deployment success?
*   **Replication and robustness:** How can we improve the reproducibility and stability of the benchmark synthesis pipeline, particularly regarding unreported settings such as retriever top-k values, training epochs, and candidate pool sampling seeds?

## Limitations
*   **Artifact alignment:** Converting leaderboard/tool benchmark scores into positives assumes they reflect narrative query suitability; no execution traces validate this.
*   **Description sufficiency:** Agent textual profiles (LLM/tool docs) may not capture nuanced compatibility (e.g., parameter conventions, cost).
*   **Replication gaps:** Exact retriever settings (top-k, training epochs) and candidate pool sampling seeds are unreported, risking variance.

## Confidence
*   Unified benchmark conversion gives scalable supervision: **Medium**
*   Content-aware methods dominate long-tail regimes: **Medium**
*   Counterfactual edits confirm capability sensitivity: **Low**

## Next Checks
1.  **Artifact-narrative alignment:** Compute topic distribution similarity (e.g., BERTopic) between leaderboard queries and MuleRun user narratives; human annotate 100 pairs for relevance.
2.  **Description-success correlation:** For 500 MuleRun agents not in AgentSelect, compute text-similarity vs. query and compare to actual success rates; expect positive correlation if descriptions are adequate.
3.  **Replication stability:** Re-run Part III synthesis with estimated settings (e.g., BGE-M3 retrievers, top-k=100); report mean/stdev of nDCG@10 over 3 random splits to quantify sensitivity to undocumented choices.
