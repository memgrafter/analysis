# Don't Vibe Code, Do Skele-Code: Interactive No-Code Notebooks for Subject Matter Experts to Build Lower-Cost Agentic Workflows

## Quick Facts
- **arXiv ID**: 2603.18122
- **Source URL**: https://arxiv.org/abs/2603.18122
- **Reference count**: 40
- **Primary result**: Skele-Code reduces token consumption and runtime costs by limiting LLM usage to code generation and error recovery, executing workflows deterministically via modular Python scripts with Markov blanket context.

## Executive Summary
Skele-Code is a no-code, graph-based environment that enables subject matter experts (SMEs) to design and run agentic workflows. It tackles the high token costs and unpredictability of fully agentic systems (e.g., multi-agent conversations) by separating LLM use to an offline code‑generation phase, while execution proceeds deterministically through programmatically orchestrated Python scripts. Users construct a directed acyclic graph (DAG) on an interactive canvas, describe each node’s task in natural language, and the system automatically generates modular code with a fixed `preprocess()`, `compute()`, `save()` structure. A context‑engineering technique—inspired by Markov blankets—supplies the coding agent only with the JSON and code of a node’s immediate neighbors, reducing token usage and mitigating context‑rot. Workflow outputs and intermediate states are stored as pickles and summary text, ensuring transparency and reusability.

The paper presents Skele‑Code’s architecture, UI components, and orchestration logic, while acknowledging critical limitations: the DAG model is rigid for iterative processes, local context may miss transitive dependencies, and empirical evaluation is pending. Future work includes support for loops, nested workflows, repository integration, and quantitative comparisons against vibe‑coding and fully agentic baselines.

## Method Summary
Skele‑Code fuses a visual graph editor with a backend that orchestrates workflow execution. Users define nodes (tasks) and directed edges (dependencies) via an interactive canvas; each node has an input cell for natural language description and optional file uploads. The backend stores the workflow as a `process.json` and creates a per‑node subfolder containing code, data, and logs. Upon execution request, the server topologically sorts the DAG. For each node, if a Python script is absent, the system invokes an LLM coding agent: it builds a prompt from the node’s task, project metadata, and the JSON definitions plus existing code of the node’s immediate predecessor(s) and successor(s) (the “Markov blanket”). The agent must output a script abiding by the `preprocess()` (load/validate priors), `compute()` (core task), and `save()` (serialize outputs) pattern. Once generated, the script runs in an isolated sandbox, reading required inputs from predecessor pickle files and writing its own outputs. The orchestrator captures stdout/stderr into a summary file shown in the UI. If a node fails, the agent is re‑invoked in error‑recovery mode, given the failing script and context, to produce a fix. Thus, LLM calls occur only during code generation or recovery; deterministic execution incurs no further token cost.

## Key Results
- **Token efficiency**: Skele‑Code confines LLM usage to code generation and error recovery, avoiding the high consumption of systems that call agents at runtime.
- **Context management**: Markov blanket context drastically cuts tokens per generation step and mitigates context‑rot by excluding irrelevant workflow history.
- **Transparency and reusability**: The resulting artifacts (JSON graph plus modular Python scripts) are inspectable, versionable, and shareable, independent of the LLM.

## Why This Works (Mechanism)

### Mechanism 1: Separation of Code Generation and Deterministic Execution
LLM agents are used solely to produce node scripts and to fix errors; once a script following the `preprocess()/compute()/save()` contract is generated, the workflow executes programmatically via topological traversal. No LLM interpretation is needed during runtime for deterministic steps [abstract, §2.2.3]. This structure reduces token costs and avoids the unpredictability of conversational agents during execution. The core assumption is that each node’s logic can be fully encoded in a script that consumes pre‑saved outputs (`*.pkl`) from its predecessors. If a node fundamentally requires dynamic LLM reasoning at runtime, the mechanism forces an error‑recovery loop, which is a break condition.

### Mechanism 2: Markov Blanket Context Engineering
To generate correct code, the coding agent receives only the JSON definitions and existing Python code of the target node’s immediate predecessor and successor nodes, plus project‑level metadata. This locality, inspired by graphical models, shrinks the context window, lowers token usage, and combats context‑rot [§2.3.1]. The assumption is that necessary information about input data shapes and expected outputs resides within those one‑hop neighbors. However, if a node depends on non‑adjacent ancestors (e.g., a schema defined three steps earlier), the blanket may omit required details, leading to incorrect generation.

### Mechanism 3: Graph + Notebook UI Reduces Cognitive Load
The directed graph externalizes workflow structure, allowing SMEs to reason visually about dependencies. Combined with Jupyter‑style input/output cells for each node, the interface supports incremental development and intermediate result inspection without the conversational overhead of “vibe coding” [§1, §2.1]. Users focus on the “what” (task description) rather than the “how” (coding), and the visual layout helps manage complexity. This approach may be constraining for inherently iterative workflows or those lacking a clear acyclic decomposition.

## Foundational Learning

- **Directed Acyclic Graph (DAG) Workflow Representation**  
  *Why needed*: The system is built on a DAG model; understanding nodes, edges, and topological ordering is essential for decomposing a process and ensuring deterministic orchestration.  
  *Quick check*: If Node B depends on output from Node A, and Node C depends on both A and B, draw the graph and list a valid topological execution order (e.g., A → B → C; or A then B then C).

- **State Saturation via Serialized Pickle Files**  
  *Why needed*: Inter‑node communication is exclusively through `node_name.pkl` files placed in each node’s subfolder. A node’s `preprocess()` reads its predecessors’ pickles, and `save()` writes its own. Understanding this file‑based hand‑off is critical for debugging data flow.  
  *Quick check*: Node X writes `{'result': 42}` to its pickle. Node Y, a successor, must use this value. What snippet would Node Y’s `preprocess()` contain? (e.g., `with open('X.pkl','rb') as f: data = pickle.load(f); val = data['result']`)

- **The `preprocess()`, `compute()`, `save()` Contract**  
  *Why needed*: Every generated script must obey this rigid structure. `preprocess()` validates inputs and sets up local state; `compute()` performs the core task and populates `state['output']`; `save()` serializes the output to a pickle and may write a summary. Orchestration depends on this consistency.  
  *Quick check*: Where should a node write a status message like “Task completed successfully” to be captured in the UI’s output cell? What about an error message? (Write to stdout in `compute()`; errors raised or printed to stderr will be captured in the summary.)

## Architecture Onboarding

### Component Map (plain text)
Frontend UI (browser canvas, NL cells, JSON editor, chat) <-> Flask Backend Server (REST/WebSocket)  
Flask Backend Server -> Graph Execution Module (DAG parsing, topological sort, orchestration)  
Graph Execution Module -> Context Assembler (gathers neighbor JSON/code for a target node)  
Context Assembler -> Coding Agent (LLM) (prompt with context, constraints)  
Coding Agent -> Graph Execution Module (returns Python script, unit tests)  
Graph Execution Module -> Command Execution & Sandbox (runs node script)  
Command Execution & Sandbox -> Project Storage (reads/writes node subfolders: *.py, *.pkl, summary.txt)  
Project Storage -> Frontend UI (serves outputs, summaries, files)  
*(Graph Execution Module also reads from Project Storage to assemble context.)*

### Critical Path
1. Server receives workflow JSON and initiates execution.  
2. Graph Execution Module performs topological sort of the DAG.  
3. For each node in order:  
   a. If the node’s Python script does not exist, Context Assembler collects JSON and code of the node’s immediate predecessor(s) and successor(s).  
   b. Coding Agent generates a new script and tests under the preprocess/compute/save contract.  
   c. Command Executor runs the script in the node’s isolated subfolder.  
   d. The script’s `save()` writes the output pickle and a summary file (`node_name_summary.txt`).  
   e. The server captures stdout/stderr and updates the UI via polling or WebSocket.  
4. After all nodes complete, the UI displays final outputs.

### Design Tradeoffs
- **Upfront structuring vs. conversational exploration**: The DAG must be defined before execution, trading off the ease of “just start chatting” for deterministic orchestration and lower token usage.
- **Fixed script structure vs. agent freedom**: The mandatory `preprocess/compute/save` pattern ensures reliable data handoff but constrains the LLM’s implementation patterns, potentially forcing awkward workarounds for complex logic.
- **Local context vs. global awareness**: The Markov blanket reduces tokens and context‑rot but may fail for tasks that need understanding of non‑adjacent nodes (e.g., a formatting node relying on a data schema defined several steps earlier).

### Failure Signatures
- **JSON Schema Violation**: Malformed `process.json` (e.g., missing `"priors"` as a list) aborts the Graph Execution Module. Check server logs for JSON parsing errors.
- **Missing Pickle Dependency**: Node script fails because a required predecessor `.pkl` file is absent or its structure does not match expectations. The node’s `summary.txt` will indicate a missing prior output.
- **Context Assembly Failure**: Generated code incorrectly accesses data because the Markov blanket omitted necessary context. Inspect predecessor `summary.txt` and actual pickle contents to verify data shapes.
- **Security Sandbox Block**: The agent’s suggested shell command (e.g., `pip install`) is flagged as unsafe by the security evaluator and blocked; agent logs show “VERDICT: UNSAFE.”
- **Non‑conforming node code**: Agent forgets required functions or fails to write the pickle. Orchestrator may detect missing `node_name.pkl` after execution and flag failure.

### First 3 Experiments
1. **Basic DAG Execution**: Create a two‑node workflow. Node 1: “Write ‘hello world’ to a text file.” Node 2: “Read Node 1’s file and count lines.” Run and verify Node 2’s `preprocess()` successfully reads the file created by Node 1. Confirm topological order execution via UI status.
2. **Context Boundary Test**: Build a three‑node chain A → B → C. In Node C’s task, ask to use a variable defined in Node A’s `compute()` (e.g., “use `raw_data` from Node A”). Observe whether the LLM can locate `raw_data` given only Node B’s code and Node A’s code (if both are included as neighbors?). Expected: The agent may fail or request clarification, highlighting the limitation of the 1‑hop Markov blanket.
3. **Error Recovery Loop**: Intentionally break Node 2 (e.g., wrong file path). Run the workflow; the UI shows an error. Then trigger a re‑run of Node 2. Verify that the coding agent (in error‑recovery mode) reads the failing script and Node 1’s output and produces a corrected version, resulting in a new `.pkl` and updated `summary.txt`.

## Open Questions the Paper Calls Out
- How can Skele‑Code design intuitive visual interfaces for loops and conditionals that remain accessible to non‑technical users while maintaining deterministic execution?  
- How can Skele‑Code integrate with code repositories to enable retrieval and reuse of pre‑approved modules without compromising transparency or increasing cognitive load?  
- What are scalable UI/UX patterns for composing and managing nested workflows (sub‑workflows) that preserve the graph‑based mental model for SMEs?  
- How does Skele‑Code compare quantitatively to vibe‑coding and fully agentic systems in token consumption, development time, error rates, and workflow reliability across diverse real‑world tasks?  
- Does extending the Markov blanket context to 2‑hop neighbors during code verification meaningfully reduce edge‑case errors in code generation without causing disproportionate token cost increases or context‑rot?

## Limitations
- Tasks that require runtime LLM reasoning (e.g., real‑time content evaluation with changing criteria) break the deterministic execution model and force error‑recovery loops or manual intervention.
- The Markov blanket context may omit necessary transitive dependencies, leading to incorrect code for nodes that rely on non‑adjacent ancestors.
- The DAG decomposition is rigid and does not naturally support iterative or highly conditional workflows, limiting its applicability to linear or branching processes.

## Confidence
- **Token efficiency** (LLM used only for generation, Markov blanket): Medium (plausible but unmeasured empirically)
- **Deterministic orchestration** (no runtime LLM, reproducible execution): High (structural guarantee as long as node scripts are correct)
- **SME usability** (graph + NL interface lowers cognitive load): Medium (theoretically supported, pending user validation)

## Next Checks
- **Token consumption benchmark**: Implement a multi‑agent baseline (e.g., AutoGen‑style) and run a suite of workflows; compare total tokens used by Skele‑Code (code generation only) vs. the baseline (runtime LLM calls).
- **Context boundary stress test**: Design workflows with long‑range dependencies (e.g., node needing data from a grand‑parent) and measure failure rate under the 1‑hop Markov blanket; then augment with selective 2‑hop inclusion to quantify error reduction vs. token increase.
- **Determinism and error recovery**: Run a fixed workflow multiple times to verify identical outputs and zero LLM calls; then introduce deliberate errors (e.g., missing file) and confirm the error‑recovery loop successfully repairs the node and completes the workflow.
