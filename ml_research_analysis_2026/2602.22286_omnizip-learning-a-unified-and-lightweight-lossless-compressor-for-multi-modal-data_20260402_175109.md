# OmniZip: Learning a Unified and Lightweight Lossless Compressor for Multi-Modal Data
## Quick Facts
- **arXiv ID:** 2602.22286
- **Source URL:** https://arxiv.org/abs/2602.22286
- **Reference count:** 40
- **Primary result:** Achieves 42–62% compression improvement over gzip across images, text, and speech while maintaining near real-time (~1 MB/s) inference on resource-constrained edge devices with model sizes from 4.8M to 152M parameters.

## Executive Summary
The paper addresses the lack of a unified, efficient lossless compressor for heterogeneous multi-modal data. Existing learning-based compressors are typically single-modality and computationally heavy. OmniZip introduces a lightweight compressor built on an RWKV backbone with three innovations: a reversible modality-unified tokenizer that maps diverse data into a shared token space; a modality-routing mixture-of-experts (MoE) mechanism for context learning; and a modality-routing feedforward process, complemented by a reparameterization training strategy that boosts capacity without increasing inference cost. Evaluated on image, tactile, text, gene, database, and speech datasets, OmniZip reduces bits per byte by 42–62% compared to gzip, operates at speeds up to 1 MB/s on MacBook CPUs and iPhone NPUs, and attains or surpasses state-of-the-art methods despite using far fewer parameters than LLM-based compressors.

## Method Summary
OmniZip’s core pipeline begins with a reversible tokenizer that converts raw bytes from any modality into a sequence of tokens from a unified vocabulary. Each sequence is prefixed with a modality-specific token (e.g., `<image>`), and during prediction a modality mask zeroes out probabilities for tokens not belonging to the target modality. The predictive model is a stack of OmniZip blocks based on the RWKV recurrent architecture. Each block modifies the standard RWKV by applying a mixture-of-experts (MoE) to the Value (V) projection in the time-mixing module and to the feedforward MLP, with a small router assigning each token to two out of four experts. To increase training capacity without incurring inference overhead, the R/K/V layers are augmented with high-rank reparameterization branches (W ← W + A·B) that are merged into the main weights before deployment. The model is trained with a three-stage optimizer that gradually unfreezes routing modules, using cross-entropy loss plus auxiliary Z-loss and load-balancing loss. During compression, the model predicts next-token probabilities, which are fed to an arithmetic coder; decompression uses the same model to regenerate probabilities.

## Key Results
- Compression: OmniZip reduces bits/Byte by **42–62%** over gzip on image/tactile datasets (CLIC-M, TouchandGo), **42–57%** on text/gene/database (enwik9, WikiSQL), and **42–53%** on speech (LibriSpeech).
- Efficiency: Inference reaches **~1 MB/s** on MacBook CPU and iPhone NPU; model sizes range from **4.8M to 152M** parameters.
- Comparative: OmniZip matches or outperforms modality-specific and LLM-based compressors while being orders of magnitude smaller.

## Why This Works (Mechanism)
### Mechanism 1: Reversible Modality-Unified Tokenization Enables Shared Latent Space
OmniZip maps heterogeneous data (images, text, speech, etc.) into a single token space using reversible discretization (e.g., patch flattening for images, BPE for text, raw bytes for speech). Each sequence is prefixed with a modality-specific token (e.g., `<image>`), and a modality mask zeroes out probabilities for non-target tokens during coding. This allows the model to learn modality-aware priors while operating within a common representational space. Evidence appears in the abstract and Section 3.2, and the approach differs from prior dual-modality compressors that maintain separate encoders. A break condition is that tokenization must be truly lossless for all modalities; any irreversible step (e.g., rounding in tactile data) would prevent perfect reconstruction.

### Mechanism 2: Modality-Routing MoE in Context Learning Adapts to Modality-Specific Dependencies
The time-mixing module of RWKV computes new representations using R, K, and V projections. OmniZip applies a mixture-of-experts (MoE) only to the V projection, which encodes concrete memory content. A lightweight router assigns each token to two out of four V experts, while K and R remain shared. This specialization lets the model capture distinct contextual patterns across modalities (e.g., spatial for images, sequential for text, temporal for speech). The design is justified by ablation (Table 6) showing V-routing outperforms routing other projections. The mechanism assumes different modalities have diverse dependency structures; if the router collapses (all tokens using the same expert) or the assumption fails, gains diminish.

### Mechanism 3: Modality-Routing Feedforward Enhances Non-Linear Representation per Modality
The standard MLP in the feedforward stage is replaced by a modality-routed MoE of four smaller experts (each with hidden size half of the original MLP). Top-2 routing ensures similar activated parameter count while providing modality-specific nonlinear transformations. This addresses the heterogeneity of feature distributions across modalities. Ablation (Table 5) confirms that removing feedforward routing harms performance. The design relies on sufficient expert capacity; an inadequate hidden factor or poor routing assignment can degrade representation quality.

## Foundational Learning
**Concept 1: Lossless Compression via Probability Estimation + Entropy Coding**  
- *Why needed:* OmniZip follows the standard paradigm: predict the probability distribution of the next token given context, then encode the token with arithmetic coding to achieve an average bit count close to the negative log-likelihood. Understanding this pipeline clarifies where the innovations lie (the neural predictor).  
- *Quick check:* If the model assigns probability 1 to the true next token, the ideal number of bits added is 0 (since -log₂(1)=0). Arithmetic coding achieves near-zero bits by maintaining a fractional interval that shrinks according to the probability.

**Concept 2: Mixture-of-Experts (MoE) and Sparse Activation**  
- *Why needed:* The modality-routing designs rely on MoE to allocate specialized sub-networks. A router computes scores for each expert, activates only top-k, and uses a load-balancing loss to prevent collapse.  
- *Quick check:* Why use top‑k=2 with 4 experts instead of activating all 4? Top‑k reduces compute and memory proportional to k/E, while still allowing diversity; using all experts would double compute and risk overfitting, losing the efficiency benefit.

**Concept 3: Reparameterization for Training-Time Capacity Boost**  
- *Why needed:* OmniZip uses high-rank reparameterization (adding A·B branches to R/K/V layers) to increase training capacity without changing the inference graph. This allows a lightweight backbone to achieve strong performance.  
- *Quick check:* If during training a weight matrix is represented as W = W_main + A·B, merging at inference is done by W_merged = W_main + A·B. The computational graph remains identical because the extra branch is absorbed into the main weight; no extra operations are introduced.

## Architecture Onboarding
**Component map:** Raw multi-modal data -> Modality-unified tokenizer (with prefix and mask) -> Stack of OmniZip blocks (each: LayerNorm, token shift, R/K shared projections, V-MoE, WKV recurrence, LayerNorm, MLP-MoE) -> Logits (modality masked) -> Softmax -> Arithmetic coder -> Compressed bits. Router networks sit beside V-MoE and MLP-MoE.

**Critical path:**  
1. Tokenize: convert raw bytes to token IDs, prepend modality prefix, note modality for masking.  
2. Forward through all blocks sequentially (RNN-style); each token passes through the block stack, with MoE routing decisions per token.  
3. Compute logits for the next token, apply modality mask to zero out irrelevant token probabilities, then softmax.  
4. Arithmetic coder uses the resulting probability distribution to write the actual token to the bitstream.  
5. Loss (cross-entropy + Z-loss + load-balancing) computed for backpropagation during training.

**Design tradeoffs:**  
- Model size vs. speed: Larger models (e.g., OmniZip-L) compress better but are slower; OmniZip-S balances speed (~1 MB/s) with moderate compression.  
- Routing granularity: More experts (E) and higher k increase capacity but add overhead; the paper finds E=4, k=2 optimal.  
- Vocabulary design: A larger unified vocabulary (e.g., 16K for text plus 256 bytes) increases embedding size but is necessary for text quality; masking prevents interference.  
- Reparameterization rank: Higher rank (r) boosts training capacity but uses more memory; they use r = 4×embedding_dim.

**Failure signatures:**  
- Poor cross-modality performance: If the model only excels on one modality (e.g., text), check tokenization balance and batch sampler.  
- Routing collapse: All tokens routed to the same expert; monitor expert usage histograms (like Fig. 6). Increase load-balancing loss weight or adjust router architecture.  
- High bits/Byte: May indicate insufficient model capacity, poor tokenization (e.g., lossy steps), or inadequate training steps.  
- Slow inference: On CPU/NPU, ensure sparsity (top‑k) is effective and model size is appropriate; avoid excessive batch size.

**First 3 experiments:**  
1. **Backbone selection (Table 1):** Train Transformer, Mamba, RWKV on enwik8; compare bits/Byte, MACs, and CPU speed. RWKV chosen for best speed/compression tradeoff.  
2. **Ablation of multi-modal components (Table 5):** Remove unified tokenizer (train single-modality), remove contextual routing, remove feedforward routing, remove reparameterization. Measure impact on representative datasets; all three components contribute positively.  
3. **Routing configuration ablation (Tables 6–7):** Test applying MoE to different layers (R/K/V), varying number of routed blocks, expert counts (3–5), top‑k (1–2), and feedforward hidden factor (1×–4×). Validates the chosen design (V‑only, all blocks, 4 experts, k=2, 2× hidden).

## Open Questions the Paper Calls Out
1. **Generalization to novel modalities:** How does modality‑routing MoE perform on data types not seen during training (e.g., video, 3D point clouds)? The paper only evaluates seven fixed modalities.  
2. **Modality‑specific routing configurations:** The uniform routing hyperparameters (4 experts, top‑k=2) may be suboptimal for certain modalities; can per‑modality tuning or adaptive routers improve results?  
3. **Cross‑modality interference:** Does the shared token vocabulary and modality masking fully prevent interference between modalities (e.g., overlapping byte values)? The paper provides no analysis of potential confusion.  
4. **Extending reparameterization:** Could reparameterization be applied to other components (e.g., MLP experts, embeddings) to further boost capacity without inference cost? The current study only targets R/K/V layers.  
5. **Training on imbalanced data:** The three‑stage training uses a balanced batch sampler; how does it behave with natural, imbalanced multi‑modal datasets where some modalities are scarce or more complex?

## Limitations
- **RWKV-7 specification gap:** The paper cites RWKV‑7 “goose” but omits key equations, forcing implementers to rely on external repositories that may diverge.
- **Arithmetic coding underspecification:** Details on precision, tail handling, and exact masking application are missing, potentially affecting measured bits/Byte.
- **Tokenizer reversibility verification:** The reversibility of proposed tokenization pipelines for images, tactile data, and domain‑specific text is not rigorously validated.

## Confidence
- Unification claim (single model processes all modalities): Medium
- Compression performance (42–62% gains over gzip): Medium
- Efficiency claim (near real‑time speed on edge, small model size): Medium
