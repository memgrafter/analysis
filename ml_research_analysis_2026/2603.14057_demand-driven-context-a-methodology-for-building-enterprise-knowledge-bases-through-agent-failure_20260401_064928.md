# Demand-Driven Context: A Methodology for Building Enterprise Knowledge Bases Through Agent Failure

## Quick Facts
- **arXiv ID:** 2603.14057
- **Source URL:** https://arxiv.org/abs/2603.14057
- **Reference count:** 12
- **Primary result:** Agent failure on real problems drives targeted knowledge curation, leading to a converging, reusable knowledge base with minimal human effort (270 minutes for 46 entities across 9 cycles in a retail case study).

## Executive Summary
Enterprise LLM agents fail on domain-specific tasks due to missing undocumented "tribal knowledge." Traditional top-down or bottom-up knowledge engineering is inefficient. Demand-Driven Context (DDC) inverts this process: it uses an agent's failure on a real problem as the signal to identify precisely what knowledge is missing. A human expert then provides minimal, targeted answers, which are structured into typed, version-controlled entities and added to a knowledge base. Over successive cycles, the knowledge base converges, enabling greater reuse and fewer correction loops.

## Method Summary
DDC executes a repeatable 9-step cycle. An agent attempts a real problem with the current knowledge base. Upon failure, it generates a structured "information checklist" of required knowledge items. A human expert supplies answers, which an automated service drafts into typed entity files (YAML frontmatter + markdown) following a predefined meta-model. The agent re-attempts the problem with these new entities. The human validates the final output; if accepted, the new entities are submitted via a pull request to the central Git-based knowledge base. The cycle logs metrics (new/reused entities, correction loops) to monitor convergence.

## Key Results
- 9 DDC cycles in retail order fulfillment produced 46 reusable entities.
- New entities per cycle decreased from 8 to 2; reused entities per cycle increased from 0 to 6.
- Total human curation time was 270 minutes (~4.5 hours) across all cycles.
- Convergence hypothesis posits 20–30 cycles per domain role yield a stable knowledge base.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Agent failure on real problems reliably signals specific, missing domain knowledge.
- **Mechanism:** The agent, when attempting a task with current context, generates an "information checklist" of required knowledge. Its failure to answer correctly pinpoints gaps not present in general training or the existing KB.
- **Core assumption:** An LLM agent can accurately introspect and articulate its own knowledge gaps for a given problem.
- **Evidence anchors:** [abstract] "uses agent failure on real problems as the primary signal"; [section 3.2] "Agent Identifies Gaps... produces an information checklist."
- **Break condition:** If the agent's checklist omits critical knowledge or includes irrelevant items, the signal becomes noisy, misdirecting curation.

### Mechanism 2
- **Claim:** Human-curated, typed entities structured via a meta-model create a navigable, reusable KB.
- **Mechanism:** Human answers are structured into typed entities (e.g., `system`, `jargon-tech`) with YAML frontmatter defining typed relationships (`uses`, `owned_by`). This enables machine-readable navigation and consistent reuse.
- **Core assumption:** A finite set of typed entity types can represent tribal knowledge for a given domain role.
- **Evidence anchors:** [abstract] "structured as typed, version-controlled entities"; [section 3.3] defines entity types and relationship graph; [section 4.4] shows reuse increase.
- **Break condition:** If the meta-model is incomplete or relationships are inconsistently applied, reuse stalls.

### Mechanism 3
- **Claim:** Convergence occurs because early cycles curate foundational knowledge reused by later incidents.
- **Mechanism:** Each cycle's problem shares underlying domain structures. Initial cycles cover core concepts; subsequent problems overlap, reusing existing entities and requiring few new ones.
- **Core assumption:** Domain knowledge for a role has a "long-tail" distribution where a core set covers most common problems.
- **Evidence anchors:** [abstract] "convergence hypothesis suggesting that 20–30 problem cycles produce a knowledge base"; [section 4.4] shows decreasing new entities and increasing reuse.
- **Break condition:** If the domain is highly heterogeneous, core knowledge coverage may never plateau.

## Architecture Onboarding

**Component map:**
Problem Ingestion -> Agent Runtime -> Human-in-the-Loop Interface -> Entity Drafting Service -> Knowledge Base (Git Repo) -> PR Governance & Automation -> Cycle Logger

**Critical path:**
1. Real problem arrives → creates sandbox.
2. Agent attempts with `KB` → fails → generates checklist.
3. Human provides answers → system drafts entities.
4. Agent re-attempts with new entities → output.
5. Human validates → if accepted, entities submitted as PR.
6. PR passes automated checks → domain steward reviews/merges → `KB` updated.
7. Cycle log persisted.

**Design tradeoffs:**
- **Human Time vs. Knowledge Quality:** Manual curation ensures accuracy but scales poorly. The 20/80 strategy (deep vs. stub entities) trades completeness for speed, prioritizing what the agent needs to reason about.
- **Centralization vs. Parallelism:** A single `KB` repo with PR governance ensures consistency but creates a review bottleneck. Parallel cycles require conflict resolution.
- **Automation Boundary:** Automating entity drafting and validation reduces human burden but risks propagating errors if human answers are flawed or validation is superficial.

**Failure signatures:**
- High correction loop rate (>2 attempts) in later cycles.
- PR merge conflicts or repeated edits on same entity.
- Stagnant new entity count but persistent failures.
- Human review becomes queue bottleneck (increasing time-to-merge).

**First 3 experiments:**
1. **Manual Cycle Run:** Execute a full DDC cycle on a simple, real problem with a domain expert. Measure human time per step, entity count, agent confidence. Goal: Validate base cycle logistics and meta-model fitness.
2. **Reuse Measurement:** After 5 cycles, introduce a new problem with intentional overlap. Track automatic entity incorporation vs. new checklist items. Goal: Quantify early convergence signal.
3. **PR Workflow Dry Run:** Simulate 2 parallel cycles from different humans targeting same domain role. Observe merge conflicts, review comments, consistency. Goal: Stress-test scaling architecture governance.

## Open Questions the Paper Calls Out
- **Open Question 1:** Is the DDC convergence hypothesis (20-30 cycles → stable KB) valid across diverse enterprise domains? Only nine synthetic cycles analyzed; domain differences may prevent convergence.
- **Open Question 2:** Can the scaling architecture with semi-automated curation and PR governance handle parallel team cycles without bottlenecks or quality loss? Architecture untested; parallel cycles may overwhelm reviewers or cause inconsistent entities.
- **Open Question 3:** How can DDC address curation subjectivity to ensure consistent entity definitions across multiple experts? Subjective curation leads to duplication and fragmented knowledge, harming reuse and reliability.

## Limitations
- Single-domain evaluation (retail fulfillment).
- Scaling architecture (semi-automated curation, PR governance) is proposed but unproven.
- Key parameters (prompt for checklist, formal reuse metric, validation rubric) are unspecified.

## Confidence
- **Mechanism 1 (failure→gaps):** Medium (trend observed, introspection reliability unverified).
- **Mechanism 2 (typed entities→reuse):** Medium (reuse increase, no baseline).
- **Mechanism 3 (convergence):** Low-Medium (only 9 cycles, hypothesis extrapolated).
- **Scalable architecture:** Low (untested).

## Next Checks
1. Cross-domain replication (3 roles) with gold-standard gap evaluation to test generality and meta-model fitness.
2. Formalize reuse metric; run >20 cycles to fit convergence curve and detect meta-model gaps via residual failures.
3. Simulate parallel PRs from multiple teams; measure conflicts and review latency to stress-test governance.
