# ScoringBench: A Benchmark for Evaluating Tabular Foundation Models with Proper Scoring Rules
## Quick Facts
- **arXiv ID**: 2603.29928
- **Source URL**: https://arxiv.org/abs/2603.29928
- **Reference count**: 6
- **Primary result**: Model rankings for tabular foundation models depend significantly on the chosen proper scoring rule; no single pretraining objective is universally optimal, highlighting the need for application-specific evaluation aligned with tail-risk penalties.

## Executive Summary
ScoringBench addresses a critical flaw in tabular machine learning benchmarks: reliance on point metrics (RMSE, R²) that obscure tail performance, which is vital for high-stakes decisions. It introduces a comprehensive benchmark that evaluates full predictive distributions using a suite of proper scoring rules (CRPS, CRLS, Interval Score, Energy Score, weighted CRPS, Brier Score) alongside traditional metrics. By assessing fine-tuned variants of TabPFNv2.5 and TabICL across 46 datasets with a rigorous permutation-test protocol that avoids pseudoreplication, the benchmark demonstrates that model performance rankings shift dramatically depending on the scoring rule used. For example, TabICL ranks best under CRPS while a CRLS-finetuned TabPFN tops CRLS. This shows that pretraining objectives must align with the specific error penalties of the target application. A git-maintained leaderboard ensures transparent, reproducible, and up-to-date comparisons.

## Method Summary
The benchmark evaluates regression models on 46 OpenML datasets (capped at 3,000 samples) using 5-fold cross-validation. Instead of only point metrics, it computes a diverse set of proper scoring rules that assess the entire predictive distribution, including CRPS, CRLS, the 90% Interval Score, the Energy Score, a weighted CRPS focusing on the center, and the Brier Score (for discrete distributions). To enable valid statistical comparison across datasets, it first averages the 5 CV fold scores per model per dataset, then ranks models within each dataset. A permutation test over these within-dataset ranks (20,000 simulations) computes empirical p-values for average rank performance. This protocol avoids pseudoreplication by treating the dataset, not the fold, as the independent unit. The evaluation harness supports plug-in model wrappers that output predictive distributions (e.g., quantiles or PMFs). Final leaderboards are maintained via a git-based pull request workflow.

## Key Results
- Model rankings are not stable across different proper scoring rules; the choice of metric fundamentally alters which model is considered best.
- No single pretraining objective (e.g., CRPS, CRLS, β-Energy) yields a model that is universally optimal across all scoring rules.
- Fine-tuning the same base model (realTabPFNv2.5) with different scoring rule losses shifts its inductive bias, making it excel under its training objective's penalty structure.
- The live, git-maintained leaderboard provides a transparent and reproducible platform for future comparisons.

## Why This Works (Mechanism)
### Mechanism 1: Scoring Rule Choice Alters Model Rankings
- **Claim**: The proper scoring rule used for training and evaluation encodes specific error penalties (e.g., for tail misses vs. central bias). This fundamentally changes model rankings because different rules reward different predictive qualities.
- **Mechanism**: During fine-tuning, the loss function's gradient landscape shapes the model's parameters to minimize that specific penalty. During evaluation, the scoring rule used to measure performance will highlight different errors (e.g., under-dispersed tails vs. miscalibrated central intervals). Even if all rules share the same population minimizer (the true distribution), finite-sample optimization with distinct penalties leads to non-identical learned models and thus re-ranking.
- **Evidence**: The paper explicitly states "model rankings depend significantly on the chosen scoring rule; no single pretraining objective is universally optimal." Empirical results show TabICL best under CRPS, while CRLS-finetuned TabPFN best under CRLS. The neighboring paper by Landsgesell and Knoll (2026) provides analytical support via the β-energy score family.
- **Break condition**: If rankings were perfectly correlated across all scoring rules and datasets, the mechanism would fail. The observed divergence contradicts this.

### Mechanism 2: Avoiding Pseudoreplication via Dataset-Level Averaging
- **Claim**: Treating individual cross-validation fold scores as independent observations (pseudoreplication) inflates false confidence in performance differences. Averaging folds first to create one score per (model, dataset) yields valid statistical units.
- **Mechanism**: The k CV scores for a single model on a single dataset are correlated because they come from the same underlying data. Using them as independent samples violates test assumptions and artificially increases effective sample size. By first averaging the 5 folds, each data point in the subsequent permutation test is a truly independent dataset, with fold-level variance treated as within-block noise. The primary source of variation is assumed to be between different datasets.
- **Evidence**: Section 5 defines pseudoreplication and mandates averaging 5 CV folds first. It cites Lazic (2010) for the concept and Demšar (2006) for recommending non-parametric tests in multi-dataset ML evaluation.
- **Break condition**: If within-dataset fold variance was as large as between-dataset variance, the fold-average would discard meaningful signal. The protocol assumes the opposite—that dataset difficulty is the dominant variance source.

### Mechanism 3: Git-Maintained Leaderboard Ensures Transparency
- **Claim**: A leaderboard updated exclusively through git pull requests creates an immutable, auditable history of benchmark results, preventing "score decay" and hidden methodology changes.
- **Mechanism**: All contributions (model wrapper code, prediction parquet files, computed leaderboard CSVs) are stored in a version-controlled repository. Submitting a result requires a documented pull request that is reviewed and merged. The live leaderboard website automatically updates from the merged `main` branch. This allows anyone to trace a specific score back to the exact code version, data splits, and scoring rule implementation used.
- **Evidence**: The abstract mentions the git-based approach for "transparency, traceability, agility and reproducibility." Section 7 details the workflow: commit parquet and CSVs, open a PR, merge, and the site updates.
- **Break condition**: If maintainers bypassed the git workflow and allowed manual, non-versioned updates, the audit trail would break, reducing reproducibility.

## Foundational Learning
- **Proper Scoring Rules**: Functions that evaluate probabilistic forecasts by penalizing specific error types (e.g., CRPS penalizes both calibration and sharpness). **Why needed**: The paper's core innovation is using these instead of point metrics to capture tail performance. **Quick check**: What is the key property of a *strictly* proper scoring rule, and why does it matter for fine-tuning? *(Ans: It is minimized in expectation by the true data-generating distribution; fine-tuning pushes the model's predictive distribution toward the true one under that rule's specific penalty structure.)*
- **Pseudoreplication**: Treating non-independent observations as independent in statistical tests. **Why needed**: The benchmark's permutation test protocol is built on avoiding this to ensure valid p-values. **Quick check**: In 5-fold CV on 46 datasets, what are pseudoreplicates and what is the correct independent unit? *(Ans: The 5 scores from folds for one (model, dataset) pair are pseudoreplicates. The independent unit is the dataset.)*
- **Calibration vs. Sharpness**: Calibration measures whether predicted uncertainty matches observed frequency (e.g., 90% intervals contain 90% of outcomes). Sharpness measures the concentration/narrowness of predictions. **Why needed**: Proper scoring rules balance these; diagnostics like Sharpness and Dispersion help interpret scores. **Quick check**: How does the 90% Interval Score penalize a model, and what does a low score indicate? *(Ans: IS90 = (u-l) + 2/0.1*(l-y) if y<l + 2/0.1*(y-u) if y>u. It penalizes wide intervals (low sharpness) and misses (poor calibration). A low score indicates narrow, well-calibrated intervals.)*

## Architecture Onboarding
- **Component map**: Model Wrappers -> Evaluation Harness (CV loops) -> Scoring Calculator -> Output Parquet -> Permutation Test Engine -> Leaderboard CSV -> Git Commit/PR -> Merged main -> Live Website
- **Critical path**: A new model is added by implementing a wrapper with `.predict()`. The harness runs 5-fold CV, the scoring calculator computes all metrics per fold, results are saved to parquet. The permutation test script aggregates per-dataset averages, computes ranks and p-values, and writes the leaderboard CSV. This CSV is committed via PR; upon merge, the static site updates.
- **Design tradeoffs**: The architecture prioritizes **extensibility** (easy to add models/metrics via modular components) and **statistical rigor** (permutation test on dataset-level ranks) over **speed** (full CV on 46 datasets is slow; 20k permutations costly). The git-based update cycle trades **agility** (manual PR) for **auditability** (immutable history).
- **Failure signatures**:
  - **Wrapper mismatch**: `.predict()` returns an object the Scoring Calculator cannot parse (e.g., wrong format). Symptom: `KeyError` or NaN scores.
  - **Scoring inconsistency**: A custom metric implementation deviates from its definition (e.g., CRPS on discrete grid). Symptom: Unusually high/low scores for that metric only.
  - **Pseudoreplication reintroduction**: Harness outputs per-fold scores instead of per-dataset averages. Symptom: Permutation p-values become unrealistically small.
  - **Leaderboard staleness**: CSVs updated locally but live site unchanged. Symptom: Check if commit went to the correct output repository and PR merged.
- **First 3 experiments**:
  1. **Sanity Check**: Run `python run_bench_regression.py` with only `TabPFN` on one small dataset (e.g., `boston`). Verify the output parquet has 5 rows (folds) with non-NaN values for R2 and MAE.
  2. **Metric Consistency**: For the same run, manually compute CRPS from the model's output distribution and compare to the parquet value. Ensures Scoring Calculator integration.
  3. **Protocol Validation**: Run full benchmark for `tabicl` and `finetune realtabpfnv2_5 crps`. Run `python permutation_leaderboard.py`. Verify TabICL ranks #1 for CRPS and p-values are not all 1.0 or 0.0.

## Open Questions the Paper Calls Out
- **Open Question 1**: How can ScoringBench be extended to handle multivariate (joint) target distributions, and what methodological adjustments are required? **Basis**: Section 9 states extension plans, referring to Landsgesell [2026] for details. **Why unresolved**: Univariate focus; multivariate requires new scoring rules (e.g., multivariate energy score) and dataset selection.
- **Open Question 2**: What alternative normalization methods beyond ranking could improve the robustness of the permutation-test protocol for multi-dataset model comparison? **Basis**: Section 5 acknowledges limitations of ranking and plans to explore min-max scaling or z-scoring. **Why unresolved**: Ranking discards magnitude information; other schemes may handle dataset heterogeneity better.
- **Open Question 3**: Which proper scoring rules are currently missing from ScoringBench that could reveal additional model biases, particularly for asymmetric tail risks? **Basis**: The paper notes different rules yield different rankings and custom rules may be needed for high-risk applications; logarithmic score is defined but not in leaderboard tables. **Why unresolved**: Unimplemented rules might expose new model trade-offs not captured by the current suite.

## Limitations
- Finetuning procedures (dataset, epochs, learning rate) for TabPFN variants are not disclosed in the paper, limiting full replication.
- Sources/versions for TabICLv2 and TabPFNv2.6 lack public links or checksums, creating potential access barriers.
- Implementation details for the XGBoost "vectorleaf" and "vector quantile" adaptations are not described, requiring code inspection.
- The permutation test's handling of ties and exact ranking method (average vs. dense) is unspecified in the text; the code is definitive.
- The 46-dataset corpus, while substantial, may not capture all tabular domains or application-specific tail-risk scenarios.

## Confidence
- **High**: The core claim that scoring rule choice alters model rankings—supported by empirical results across 46 datasets and analytical arguments from the cited Landsgesell and Knoll (2026) work.
- **High**: The necessity of avoiding pseudoreplication via dataset-level averaging—standard statistical practice (Lazic 2010, Demšar 2006) applied correctly.
- **Medium**: The long-term effectiveness of the git-maintained leaderboard for transparency—the mechanism is sound, but operational success depends on community adoption and maintainer adherence.
- **Medium**: Generalizability beyond the evaluated model set (TabPFN, TabICL, XGBoost) and 46 datasets; other models or domains might show different patterns.
- **Low**: Specific finetuning details for TabPFN variants and the exact behavior of un documented XGBoost wrappers; these require repository inspection.
