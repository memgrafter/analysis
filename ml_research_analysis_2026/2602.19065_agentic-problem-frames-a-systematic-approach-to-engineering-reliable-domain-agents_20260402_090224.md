# Agentic Problem Frames: A Systematic Approach to Engineering Reliable Domain Agents

## Quick Facts
- **arXiv ID:** 2602.19065  
- **Source URL:** https://arxiv.org/abs/2602.19065  
- **Reference count:** 6  
- **Primary result:** The paper introduces Agentic Problem Frames (APF) and the Act-Verify-Refine (AVR) loop to engineer reliable LLM agents through dynamic specification and closed-loop control, with validation via case studies.

## Executive Summary
This paper tackles the “frameless” development of LLM agents, which often leads to scope creep and open-loop failures. It proposes a systematic engineering framework called Agentic Problem Frames (APF). APF structures agent–environment interactions using a **dynamic specification paradigm** and an **Act-Verify-Refine (AVR)** closed‑loop control system. The central engineering artifact is the **Agentic Job Description (AJD)**—a formal contract that defines jurisdictional boundaries, operational context, and verification criteria. Two case studies (a business travel proxy and an equipment supervisor) demonstrate that APF keeps agent operations within defined boundaries and drives asymptotic convergence toward mission requirements. The work conceptually proves that agent reliability can be achieved by anchoring stochastic AI within deterministic, verifiable processes.

## Method Summary
The method is a specification‑driven engineering process (not model training). It comprises: (1) defining an **Agentic Job Description (AJD)** that formally specifies the agent’s mission (R), workplace (W), scope (M), operational context (S), and evaluation method (K); and (2) implementing an **Act‑Verify‑Refine (AVR) loop** that processes incoming events (Eₜ) by injecting contextual knowledge (Cₜ) to produce a bounded execution specification (Sₜ), executing actions (A) via domain tools, verifying outcomes through callbacks and confirmations, and refining a knowledge asset (Kₜ₊₁) for future cycles. AVR transforms raw execution results into verified knowledge, enabling the agent to asymptotically converge on its mission.

## Key Results
- APF provides a formal framework (AJD + AVR) to bound stochastic LLM behavior and prevent scope creep.
- The AVR loop enables asymptotic convergence toward mission requirements by converting execution results into verified knowledge assets.
- Case studies (business travel proxy, equipment supervisor) show operational scenarios are systematically controlled within defined boundaries.

## Why This Works (Mechanism)

### Mechanism 1 – Dynamic Context Injection
- **Claim:** Ambiguous user intents are transformed into bounded execution specifications at runtime via domain‑knowledge injection.
- **Mechanism:** An event (Eₜ) is processed within a jurisdictional context (Cₜ) from the workplace. Cₜ includes manuals, policies, memory, and tool specs, producing a concrete Sₜ that confines the LLM’s reasoning to a professional scope.
- **Core assumption:** Properly bounded context narrows the LLM’s probabilistic output to a deterministic, domain‑aligned specification.
- **Evidence anchors:** abstract and §3.5.1; corpus lacks direct evidence, making this a novel contribution.
- **Break condition:** If context is incomplete or contradictory, Sₜ misaligns, causing scope creep or incorrect execution.

### Mechanism 2 – AVR Closed‑Loop Control
- **Claim:** The AVR loop closes the execution gap by turning opaque results into verified knowledge assets, driving asymptotic convergence.
- **Mechanism:** After execution (A) changes the world to Wₜ₊₁, Verify checks outcomes via callbacks (fact verification) and confirmations (value verification). Only confirmed results become incremental knowledge (ΔK), integrated into Kₜ₊₁ and fed back as context, reducing epistemic uncertainty.
- **Core assumption:** The world provides trustworthy signals (callbacks or human confirms) to verify action outcomes.
- **Evidence anchors:** abstract and §3.3; corpus lacks direct evidence for AVR.
- **Break condition:** Missing, delayed, or unreliable verification prevents knowledge solidification, leading to open‑loop failures.

### Mechanism 3 – Agentic Job Description (AJD) Contract
- **Claim:** The AJD formally defines jurisdictional boundaries, operational context, and evaluation criteria, turning an LLM into a reliable Job Performer.
- **Mechanism:** The AJD table specifies: Mission (R) – goal state; Workplace (W) – interaction domains; Scope (M) – identity, authority, negative constraints; Operational Context (S) – contexts, memory, capabilities; Evaluation Method (K) – callback and confirm procedures. This blueprint structures both input (via S) and output (via K) for deterministic control.
- **Core assumption:** An LLM strictly confined by a clear job description with explicit boundaries and verification gates will operate reliably within those limits despite inherent randomness.
- **Evidence anchors:** abstract and §3.6; corpus contains related specification work but AJD is distinct.
- **Break condition:** An incomplete AJD (missing context or evaluation) leaves the agent ungrounded, causing untraceable failures.

## Architecture Onboarding
- **Component map:**  
  Event (Eₜ) -> Agent (M) with AJD constraints  
  Agent -> requests context from WContext (RAG store)  
  Agent -> produces St (bounded spec)  
  Agent -> Act: calls WInteraction (tool APIs) -> changes world (Wₜ₊₁)  
  WVerification (callbacks/confirms) -> sends signals to Verify stage  
  Verify -> if success, Refine stores ΔK in Knowledge Base (Kₜ₊₁)  
  Knowledge Base -> updates WContext for next cycle  
  AVR loop repeats: Act -> Verify -> Refine.

- **Critical path:**  
  1. Receive event (Eₜ).  
  2. Context injection: retrieve relevant knowledge from WContext based on Eₜ and AJD boundaries.  
  3. Specification: construct St within Scope constraints.  
  4. Execution: invoke tools via WInteraction to perform A, causing Wₜ₊₁.  
  5. Verification: monitor WVerification for callbacks; obtain explicit confirm.  
  6. Refine: compile confirmed results into Kₜ₊₁; store in knowledge base.  
  7. Repeat for next event; convergence when cumulative evidence ⊢ R.

- **Design tradeoffs:**  
  - Scope breadth vs safety: Wider context increases adaptability but risks hallucinations; mitigate with strict negative constraints in AJD Scope.  
  - Verification latency vs certainty: Real‑time callbacks are fast but noisy; human confirms are accurate but slow; choose based on domain risk.  
  - Single‑agent vs decomposed: Single agent simpler but may exceed context window; decomposition reduces scope per agent but adds coordination overhead and requires A2A protocols.  
  - Dynamic vs static context: RAG yields up‑to‑date info but retrieval variability; caching improves stability but may become stale.

- **Failure signatures:**  
  - Unauthorized actions: agent calls APIs not listed in Workplace or beyond Scope; indicates insufficient boundary enforcement.  
  - Missing verification: execution logs show actions without corresponding callback or confirm; suggests open‑loop operation.  
  - Repeated clarification requests: agent generates many clarifying questions; points to inadequate Operational Context or poor retrieval.  
  - Stagnant knowledge: same failure reoccurs; knowledge assetization may be broken (confirm not stored, memory not indexed).  
  - Cascading errors: one agent’s incorrect output triggers downstream agents; lack of input validation at composition boundaries.

- **First 3 experiments:**  
  1. **Minimal Proxy Agent:** Build a “Conference Room Booker”. AJD: Scope limited to internal calendar API; Context includes booking policy; Evaluation via calendar callback and optional human confirm. Test with ambiguous requests; measure boundary compliance and correctness.  
  2. **Supervisor with Physical Feedback:** Simulate an IoT thermostat agent. AJD: Scope includes read/write to temperature sensor and heater API; Context includes safety thresholds; Verification via sensor callback and simulated manager confirm. Introduce anomalies; verify detection and logging.  
  3. **Composition and Knowledge Flywheel:** Connect “Travel Assistant” (proxy) and “Expense Auditor” (supervisor). Travel books flights; auditor verifies receipts via email callback. Assetize successful audits as memory for travel agent to prefer compliant airlines. Observe improvement over iterations.

## Open Questions the Paper Calls Out
- **Open Question 1:** How does the Agentic Problem Frames (APF) framework empirically compare to existing LLM agent frameworks (e.g., ReAct, Reflexion) in terms of reducing scope creep and open‑loop failures in real‑world deployments?  
  - *Basis in paper:* The paper positions APF as a solution to “frameless” development risks but validates efficacy only through two conceptual case studies. It cites related work but does not provide head‑to‑head experimental comparisons.  
  - *Why unresolved:* Without comparative empirical data, it is unclear whether APF’s structural rigor provides a measurable reliability advantage.  
  - *What evidence would resolve it:* Controlled experiments deploying equivalent agent tasks using APF vs. baselines, with metrics for scope adherence, verification success rates, and convergence speed.

- **Open Question 2:** What formal specification language or schema should standardize the Agentic Job Description (AJD) to enable tooling, automation, and cross‑organizational portability?  
  - *Basis in paper:* The AJD is presented as a “formal specification tool” and “blueprint,” yet its components are described in natural language without a machine‑readable grammar.  
  - *Why unresolved:* Without a standardized format, consistent interpretation, automated validation, and pipeline integration remain aspirational.  
  - *What evidence would resolve it:* Development and community adoption of a JSON/YAML/DSL schema for AJD, accompanied by a reference implementation (e.g., validator or code generator).

- **Open Question 3:** What precise metrics and thresholds define “asymptotic convergence” (limₜ→Т {Sₜ, Kₜ₊₁} ⊢ R) for the AVR loop, and how can they be monitored in practice to prevent divergent or oscillatory agent behavior?  
  - *Basis in paper:* The core theoretical claim relies on asymptotic convergence, but the paper does not define quantitative measures for the delta between current state and R, nor conditions under which convergence fails.  
  - *Why unresolved:* Without operational metrics, the reliability claim is qualitative; engineers lack guidance on when to intervene or detect non‑convergence.  
  - *What evidence would resolve it:* A formalized convergence metric (e.g., requirement satisfaction probability score) validated in case studies showing correlation with mission success and sensitivity to context/verification perturbations.

- **Open Question 4:** How does the APF framework scale to multi‑agent systems where agents have overlapping or hierarchical AJDs, and what mechanisms prevent interference or “jurisdictional creep” between agents?  
  - *Basis in paper:* The paper mentions composing “reliable unit agents” into higher‑order systems and includes a nested structure in case studies, but interaction protocols for resolving conflicts between agents’ contexts, scopes, or verification outputs are not addressed.  
  - *Why unresolved:* The “Single‑Responsibility Principle” is invoked, but real‑world systems involve complex dependencies; without explicit orchestration rules, the framework risks reintroducing “frameless” ambiguity at the system level.  
  - *What evidence would resolve it:* Case studies or simulation models of multi‑agent workflows defining clear handoff protocols, shared context governance, and conflict resolution grounded in AJD boundaries.

- **Open Question 5:** What is the optimal balance between dynamic context injection (Cₜ) and computational/economic cost (e.g., RAG retrieval latency, token usage) for maintaining reliable convergence without prohibitive overhead?  
  - *Basis in paper:* The APF relies on rich context injection and verification callbacks but does not analyze cost‑benefit trade‑offs of context richness or verification frequency.  
  - *Why unresolved:* In industrial settings, latency and cost are critical; over‑injection or over‑verification could make agents impractical. The framework provides no tuning guidelines.  
  - *What evidence would resolve it:* Empirical studies measuring convergence rates and reliability against variables like context window size, retrieval depth, and verification schedule, producing cost‑aware tuning guidelines for different domain criticalities.

## Limitations
- Validation relies on two qualitative case studies without systematic quantitative baselines, limiting generalizability and statistical confidence.
- Core implementation details (formal AJD syntax, knowledge assetization algorithm, verification protocols) remain underspecified, hindering faithful reproduction and engineering.
- The approach assumes readily available, reliable verification signals (callbacks/confirms), which may be costly or infeasible in many domains.
- LLM adherence to strictly bounded contexts is conjectural; stochastic drift could still cause scope creep.
