# SCRIBE: Structured Mid-Level Supervision for Tool-Using Language Models

## Quick Facts
*   **arXiv ID:** 2601.03555
*   **Source URL:** https://arxiv.org/abs/2601.03555
*   **Reference Count:** 35
*   **Primary Result:** A mid-level supervision framework using Skill Prototypes reduces reward noise, yielding >20-point gains on AIME25 for Qwen3-4B and large improvements on MATH500 and BFCL.

## Executive Summary
SCRIBE introduces a structured mid-level supervision framework to address noisy and inconsistent reward signals in tool-augmented language models. Instead of relying on monolithic outcome rewards or dense token-level process rewards, it curates a library of Skill Prototypes that represent verifiable subgoals (e.g., "solve equation," "call API"). An LLM router dynamically assigns subgoals to these prototypes during training. Final reward computation uses structured rubrics tied to each prototype, transforming open-ended judging into precise, low-variance verification. On Qwen3-4B, this yields a 20-point absolute gain on AIME25 (43.3% → 63.3%) and significant improvements on MATH500 and the BFCL tool-use benchmark. Gains are additive with low-level tool optimizations like FunRL, and analysis shows mid-level skill stabilization precedes high-level planning improvements.

## Method Summary
SCRIBE operates in three phases. First, it extracts and clusters successful subgoal executions from a seed model's trajectories to build a library of Skill Prototypes, each with a clear input-output specification and verification rubric. Second, during RL training, a router (the base LLM) is prompted to decompose the current high-level goal and map each subgoal to the most relevant prototype from the library. Third, for each executed subgoal, a verifier (another LLM) evaluates the outcome against the prototype's rubric, producing a dense, structured intermediate reward. This mid-level abstraction provides consistent, instrumentally grounded supervision that is more stable than outcome-only rewards and more feasible to specify than dense per-token rewards. The prototype library is periodically refreshed to adapt to the model's improving capabilities.

## Key Results
*   On Qwen3-4B: AIME25 accuracy improves from 43.3% to 63.3% (+20.0), MATH500 from 92.3% to 95.8% (+3.5), and BFCL overall from 33.0% to 51.3% (+18.3).
*   On LLaMA-3.2-3B: MATH500 improves from 48.3% to 63.4% (+15.1) and BFCL from 24.8% to 30.8% (+6.0).
*   SCRIBE's benefits are additive with the low-level tool optimization method FunRL, leading to further gains on BFCL.

## Why This Works (Mechanism)
SCRIBEs mid-level abstraction reduces reward variance and provides learnable, instrumentally grounded signal. By routing subgoals to a library of verifiable prototypes, it transforms the ambiguous task of "judging a long reasoning trace" into a series of small, checkable assertions. This yields more consistent and lower-variance process rewards compared to monolithic outcome judges. The co-evolution analysis shows that as the model masters these mid-level skills (evidenced by decreasing prototype selection uncertainty), its high-level planning ability concurrently improves, likely because stable subgoal execution creates clearer, more separable outcomes for the high-level planner to discriminate between.

## Foundational Learning
*   **Concept:** Reward Shaping with Dense Process Rewards
    *   **Why Needed:** Standard RL with only sparse outcome rewards is inefficient for long-horizon tool-use; dense supervision is required but per-token rewards are notoriously noisy and hard to specify.
    *   **Quick Check:** Does providing intermediate rewards for *correct tool calls* or *valid reasoning steps* improve sample efficiency over only rewarding final answer correctness?
*   **Concept:** Subgoal Decomposition for Tool-Augmented Reasoning
    *   **Why Needed:** Complex problems solved with tools require breaking a high-level query into a sequence of verifiable, executable sub-tasks (e.g., compute X, search Y, call API Z).
    *   **Quick Check:** Can a model reliably generate a sequence of subgoals for a multi-step math or information-seeking problem, and can each subgoal be validated in isolation?
*   **Concept:** Prototype-Based Skill Abstraction
    *   **Why Needed:** To scale supervision, we need a reusable library of common subgoal *types* (skills) rather than writing novel verification for every unique subgoal instance.
    *   **Quick Check:** Can successful execution traces be clustered into a compact set of recurring prototype patterns (e.g., "algebraic simplification," "date extraction") that cover a majority of subgoals?
*   **Concept:** rubric-based Verification
    *   **Why Needed:** Human or LLM judges are inconsistent on open-ended traces; a structured checklist (rubric) tied to a prototype's specification enforces consistent, precise evaluation.
    *   **Quick Check:** Does providing a verifier with a prototype's input spec and a 3-5 point rubric (e.g., "output must be a single integer") yield higher inter-rater agreement than asking "was this step correct?"?
*   **Concept:** Adaptive Skill Library Curation
    *   **Why Needed:** A static skill library becomes outdated as the model's capabilities evolve; the set of frequent, failing subgoals changes during training.
    *   **Quick Check:** Does periodically re-clustering trajectories from the current model and updating the prototype library lead to sustained or increasing reward signal quality over a long training run?

## Architecture Onboarding
*   **Component Map:** Seed Data Collection -> Skill Prototype Library (Clustering/Curating) -> RL Training Loop: [Current State] -> Router (LLM) -> Proposed Subgoal -> Prototype Match -> Executor (Base LLM + Tools) -> Execution Trajectory -> Verifier (LLM + Rubric) -> Mid-Level Reward -> RL Update. Library Refresh triggers periodic re-clustering of recent trajectories.
*   **Critical Path:** The fidelity of the skill prototypes and their rubrics is the single most critical component. A poor library leads to mis-routed subgoals and meaningless rewards. The router's matching ability is second; it must correctly map a desired subgoal to an existing prototype's intent.
*   **Design Tradeoffs:** *Precision vs. Coverage:* A small, clean prototype library ensures reliable verification but may force unnatural subgoal fits; a large library covers more cases but risks noisy prototypes and harder matching. *Static vs. Adaptive Library:* A fixed library is simpler but degrades as the model learns; frequent refresh is computationally costly and may destabilize learning if not smoothed.
*   **Failure Signatures:** 1) High variance in mid-level rewards despite structured rubrics (indicates poor prototype-definition or verifier prompt). 2) Router consistently selects "misc" or overly broad prototypes (library too narrow or router undertrained). 3) High-level performance plateaus while mid-level uncertainty remains high (skill library not capturing key difficulties). 4) Performance collapse after a library refresh (refresh rate too aggressive or clustering threshold mis-set).
*   **First 3 Experiments:** 1) **Ablate the Library:** Replace the prototype library with a naive "one-step" policy (reward every tool call as correct) or with randomly assigned prototypes. Measure BFCL performance and reward variance. 2) **Ablate the Rubric:** Remove the structured rubric and revert to a single binary "subgoal correct?" judgment for each step. Compare sample efficiency and final MATH500 score against full SCRIBE. 3) **Vary Refresh Frequency:** Train with library refresh every K iterations (K=1, 5, 10, 50) on a smaller benchmark. Track mid-level reward consistency and BFCL accuracy to find a stable refresh schedule.

## Open Questions the Paper Calls Out
### Open Question 1
*   **Question:** How does SCRIBE's performance and stability scale when applied to significantly larger language models (e.g., 70B+ parameters) or models with different post-training pipelines?
*   **Basis in paper:** [explicit] The Limitations section states: "our experiments focus on small- to mid-sized instruction-tuned models; it is unclear how the proposed skill-conditioned supervision scales to substantially larger architectures or to models trained with different post-training pipelines."
*   **Why unresolved:** The empirical results are limited to Qwen3-4B and LLaMA-3.2-3B. Scaling RL with dense process rewards to larger models introduces challenges like increased memory usage, slower rollouts, and potential instability, which haven't been investigated.
*   **What evidence would resolve it:** Replicate the training pipeline on larger base models (e.g., Meta's Llama 3.1 70B or equivalent), measuring not only final accuracy on MATH/BFCL but also training stability metrics (reward variance, KL divergence) and computational costs. Comparisons should include both models with similar instruction-tuning and those with different post-training (e.g., DPO-trained) to see if SCRIBE's benefits generalize.

### Open Question 2
*   **Question:** Can the mid-level skill abstraction and prototype-based reward formulation effectively generalize to open-ended generation tasks or domains without clear, instrumentally defined subgoals (e.g., creative writing, open-domain dialogue)?
*   **Basis in paper:** [explicit] The Limitations section notes: "our evaluation primarily targets structured reasoning and tool-use tasks; the effectiveness of the approach for open-ended generation or non-instrumental reasoning remains an open question." The Future Work also suggests exploring skill libraries for "open-domain tasks."
*   **Why unresolved:** SCRIBE's design assumes decomposable subgoals with verifiable outcomes (e.g., solving an equation, calling a tool). Open-ended tasks often lack discrete, checkable subgoals and instead involve subjective quality dimensions (e.g., creativity, coherence), making the prototype-routing and verification rubric inapplicable without fundamental redesign.
*   **What evidence would resolve it:** Adapt SCRIBE's pipeline (subgoal extraction, prototype clustering, skill-conditioned judging) to an open-ended task like story generation. Define "skills" (e.g., character development, plot pacing) and design rubrics that can be judged reliably by an LLM. Compare model outputs and human evaluations against baseline PRM and outcome-only RL to see if structured mid-level supervision improves non-instrumental qualities.

### Open Question 3
*   **Question:** Are there any hidden trade-offs or negative interactions when combining mid-level skill supervision (SCRIBE) with multiple forms of low-level tool optimization, or does the additivity observed with FunRL hold universally across diverse low-level enhancements?
*   **Basis in paper:** [inferred] The paper demonstrates additivity with one low-level method (FunRL) in Table 3, claiming "complementary benefits." However, it does not test combinations with other low-level optimizations (e.g., improved tool-calling syntax, better API error handling) or explore potential interference (e.g., if low-level fine-tuning alters the distribution of mid-level skills).
*   **Why unresolved:** The conclusion of complementarity is based on a single pairing. Different low-level optimizations might target overlapping aspects of the behavior (e.g., both might affect argument formatting), leading to redundant or conflicting gradients. The paper's adaptive prototype refresh might also clash with certain low-level constraints.
*   **What evidence would resolve it:** Systematically combine SCRIBE with a suite of low-level tool-use optimizations (e.g., syntactic accuracy rewards, execution success bonuses, diverse tool invocation patterns). Measure performance on BFCL subcategories (Web Search, Memory, etc.) and analyze failure modes. Track whether certain low-level gains vanish when mid-level supervision is added, indicating interference, or if all combinations are synergistic.

### Open Question 4
*   **Question:** What is the causal mechanism behind the observed co-evolution of mid-level skill mastery and high-level planning? Is improved mid-level stability necessary and sufficient for high-level gains, or are there alternative pathways?
*   **Basis in paper:** [inferred] Section 6.1 shows a temporal correlation: mid-level uncertainty decreases before high-level plan selection ability increases (Fig. 3). The authors interpret this as "mid-level skill mastery acts as a precursor," but the analysis is observational and doesn't isolate causation.
*   **Why unresolved:** The training dynamics are measured on the same model; correlation does not prove that mid-level gains cause high-level improvements. It's possible that an unmeasured factor (e.g., improved world knowledge, better token-level optimization) drives both. The "Plan Separability" metric suggests a mechanism (clearer execution outcomes help plan discrimination), but this is still a mediated correlation.
*   **What evidence would resolve it:** Run an ablation where mid-level execution is artificially stabilized (e.g., by providing perfect subgoal rewards or freezing the router during high-level training) while preventing genuine skill learning. Alternatively, train models with high-level planning rewards but randomized mid-level rewards. If high-level gains disappear without authentic mid-level improvement, it supports necessity. Sufficiency could be tested by training on mid-level rewards alone and measuring emergent high-level behavior without any planning supervision.

## Limitations
*   Evaluation scope is limited to math (AIME25, MATH500) and specific tool-use benchmarks (BFCL); transfer to open-ended agentic tasks or non-mathematical domains is unproven.
*   The causal mechanism linking mid-level skill stabilization to high-level planning gains is inferred from observational training dynamics; key ablations (e.g., disabling the router, freezing the prototype library) are missing.
*   All experiments use small models (3B–4B parameters). Scaling to larger architectures (≥10B) or different training regimes (e.g., MoE, different post-training) is an open question.

## Confidence
*   **Performance on tested benchmarks (MATH500, BFCL, AIME25):** High. Results are consistent across two model families and show large absolute gains.
*   **Core mechanism (mid-level abstraction reduces reward variance):** Medium. The paper shows reduced variance metrics and the ablations in Fig. 2 support the value of structured rubrics, but ablations of the *prototype library itself* versus open-ended judgment are not shown.
*   **Additivity with low-level optimizations (e.g., FunRL):** Medium. Demonstrated for one combination; generalizability to other low-level methods is untested.
*   **Scalability to larger models (>10B):** Low. No empirical evidence; computational and stability challenges are likely.
*   **Generalization to open-ended/non-instrumental tasks:** Low. The approach is designed for verifiable subgoals; applicability elsewhere is speculative.

## Next Checks
1.  **Cross-Benchmark Generalization:** Apply SCRIBE to at least two diverse, non-math tool-augmented benchmarks (e.g., API-based question answering, interactive web tasks) to validate transfer beyond arithmetic reasoning.
2.  **Component Ablation:** Ablate the Skill Prototype library (e.g., random routing, full open-ended judgment) and the rubric-structured verification separately on BFCL to disentangle their individual contributions to reward signal quality and final performance.
3.  **Scaling Study:** Apply SCRIBE to a model ≥10B parameters (e.g., Qwen3-14B, LLaMA-3.1-70B) on MATH500 and BFCL, comparing absolute and relative gains against the 3–4B scale to assess scalability.
