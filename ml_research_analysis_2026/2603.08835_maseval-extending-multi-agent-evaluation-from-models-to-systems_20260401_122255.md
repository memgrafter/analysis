# MASEval: Extending Multi-Agent Evaluation from Models to Systems

## Quick Facts
- **arXiv ID:** 2603.08835
- **Source URL:** https://arxiv.org/abs/2603.08835
- **Reference count:** 11
- **Primary result:** Framework choice induces performance differences comparable to model choice within the same capability tier.

## Executive Summary
MASEval is a framework-agnostic library that shifts multi-agent evaluation from model-centric to system-level analysis. By treating the complete agent system—including framework, topology, and orchestration—as the unit of analysis, it enables controlled experiments that isolate the impact of framework choice. A full factorial experiment across 3 benchmarks, models, and frameworks reveals that framework-induced performance differences are comparable to those between models, with notable gaps up to 30.9 percentage points. MASEval also significantly reduces implementation effort for benchmark consumers by abstracting common orchestration logic.

## Method Summary
MASEval introduces a unified evaluation harness with core abstractions (AgentAdapter, Environment, Evaluator) and a standardized lifecycle (Setup, Execute, Collect, Evaluate, Report). This design allows benchmark consumers to implement thin adapters for their chosen frameworks, avoiding rewrites of orchestration logic. The framework supports full factorial experiments by holding agent topology and tasks constant while varying frameworks and models. Traces are collected per-agent, enabling detailed diagnosis of coordination failures. The library includes pre-built adapters for popular frameworks and benchmarks, facilitating reproducible system-level evaluation.

## Key Results
- Framework-induced performance differences (mean range: 12.4 pp) are comparable to those between models within the same capability tier (mean range: 14.2 pp).
- Extreme gaps observed: same model (Haiku-4.5) across frameworks on MACS Travel shows 30.9 pp difference.
- Implementation effort reduced by 83–91% in interface code and overall by 35–57% via shared infrastructure.

## Why This Works (Mechanism)

### Mechanism 1: Unified Interface Reduces Implementation Overhead
**Claim:** MASEval reduces implementation effort by providing a unified, framework-agnostic interface that abstracts away benchmark-specific orchestration logic.  
**Mechanism:** By defining core abstractions (AgentAdapter, Environment, Evaluator) and a standardized lifecycle (Setup, Execute, Collect, Evaluate, Report), MASEval replaces the need to rewrite wiring code for each benchmark. The core runtime orchestrates execution and trace collection, so benchmark consumers only need thin adapters for their chosen framework.  
**Core assumption:** The fragmentation of benchmark interfaces is the primary source of implementation overhead, not the evaluation logic itself.  
**Evidence anchors:** [abstract] effort reduction 83–91% in interface code; [section 4.3] Table 3 shows lines of code reduction (e.g., -82.7% for τ2-Bench).

### Mechanism 2: System-Level Experimentation Isolates Framework Effects
**Claim:** System-level evaluation (holding model and task constant while varying framework) reveals that framework choice induces performance differences comparable to model choice within a capability tier.  
**Mechanism:** MASEval's design enables a full factorial experiment where the same multi-agent topology is implemented idiomatically in different frameworks (smolagents, LangGraph, LlamaIndex) and run on different models (GPT-5-mini, Gemini-3.0-Flash, Haiku-4.5). By controlling for topology, task, and evaluation, variance attributed to framework implementation can be isolated.  
**Core assumption:** Performance differences in prior model-centric benchmarks were confounded by fixed, unexamined framework implementations; decoupling framework from model is necessary.  
**Evidence anchors:** [abstract] framework-induced differences comparable to model differences (12.4 pp vs 14.2 pp); [section 4.2] Table 2 shows cross-framework ranges (e.g., 30.9 pp gap on MACS Travel for Haiku).

### Mechanism 3: Per-Agent Tracing Diagnoses Coordination Failures
**Claim:** First-class, per-agent tracing within a shared trace structure enables diagnosis of complex failure modes arising from framework-model interactions and multi-agent coordination.  
**Mechanism:** MASEval's ComponentRegistry automatically collects independent message histories for each agent, alongside tool invocations and model calls, allowing post-hoc reconstruction of interaction sequences. When a failure is observed (e.g., inefficient retries), the trace can be inspected to identify whether the root cause lies in a framework's default, a model's response pattern, or their combination.  
**Core assumption:** Debugging multi-agent systems requires visibility into the partially observable states of each agent and their sequential decisions; aggregated metrics alone are insufficient.  
**Evidence anchors:** [section 3.5] description of multi-agent tracing; [section 4.2] analysis of smolagents + GPT-5-mini on MACS: traces revealed forced tool calls leading to 23 retries.

## Foundational Learning
- **System vs. Model as Unit of Analysis:** Why needed: Challenges the standard "model-on-benchmark" evaluation; understanding that the orchestration harness is a variable requiring isolation is foundational. Quick check: If you implement the same 3-agent collaboration design in two different frameworks, should you expect identical performance? Why or why not?
- **Adapter Pattern for Framework Agnosticism:** Why needed: MASEval's "Bring Your Own" philosophy depends on a minimal, stable interface (`_run_agent()`, `get_messages()`) that any framework can adapt to. Quick check: What two methods must a custom `AgentAdapter` implement? What is the trade-off of keeping this interface minimal?
- **Trace-First, Metric-Later Evaluation:** Why needed: Final accuracy metrics can hide critical failure modes in coordination, tool usage, or error recovery. MASEval collects rich, structured traces during execution, separating data collection from metric computation. Quick check: Why might computing a "Task Success Rate" directly from final outputs be misleading for a multi-agent system? How does a two-stage evaluator (filter_traces then compute) help?

## Architecture Onboarding
- Component map: Core (abstract base classes, orchestrating Benchmark runtime) -> Interfaces (pre-built adapters for frameworks, models, logging backends) -> Benchmarks (concrete implementations, e.g., MACSBenchmark) -> User Code (agent logic inside a framework, environment tools, custom adapters/evaluators)
- Critical path:  
  1. Define/Customize Components: Implement `AgentAdapter` for your framework, define `Environment` with tools, optionally implement `User` simulator and `Evaluator`.  
  2. Subclass Benchmark: Create a class inheriting from `Benchmark`, override hooks (`setup_agents`, `setup_environment`, `setup_evaluators`).  
  3. Run: Instantiate your benchmark class and call `.run()`. The core orchestrates the lifecycle (Setup → Execute → Collect → Evaluate → Report).  
  4. Inspect: Load reports to access full traces (per-agent histories, tool calls) and metrics.
- Design tradeoffs:  
  - Flexibility vs. Convenience: Maximum flexibility (any framework, any backend) but requires manual setup; gain is no vendor lock-in.  
  - Minimal Adapter Contract vs. Framework Complexity: Two-method contract works for many frameworks, but complex frameworks with unique memory/async models may need "thicker" adapters.  
  - Trace Volume vs. Debugging Value: Full per-agent tracing increases storage but essential for diagnosing coordination issues; overhead assumed negligible compared to agent runtime cost.
- Failure signatures:  
  - AgentError: Contract violation (e.g., malformed message); penalized in scoring; may include suggestion for retry.  
  - EnvironmentError / UserError: Infrastructure or simulator failure; not penalized; task may be retried or skipped.  
  - Trace Missing Components: Unregistered component (e.g., tool) actions absent from traces, hindering debugging.  
  - Scaling Limits: Tracing overhead grows linearly with agents; tested up to 5 agents; massive topologies may strain storage/analysis.
- First 3 experiments:  
  1. Hello World Adapter: Wrap a trivial agent (e.g., function returning "Hello") in minimal `AgentAdapter`; run on dummy benchmark (no-op tool) to verify end-to-end flow and simple evaluator (100%).  
  2. Multi-Agent Smoke Test: Use pre-built adapter (e.g., SmolAgentAdapter) with two simple agents (planner + executor) on tiny benchmark; verify separate per-agent traces and tool call appearances.  
  3. Cross-Framework Comparison: Implement same 2-agent topology (manager + worker) in two frameworks via adapters; run on one MACS domain; compare scores and inspect traces for interaction pattern differences.

## Open Questions the Paper Calls Out
- **Open Question 1:** Does MASEval's minimal adapter contract support future frameworks with novel abstractions? Basis: Broader Impact notes accommodation of future frameworks determines longevity; unresolved due to limited frameworks tested.
- **Open Question 2:** What are the performance scaling limits of MASEval for large multi-agent systems (>5 agents)? Basis: Broader Impact states scaling behavior unexplored; only tested up to five agents.
- **Open Question 3:** What causes the observed framework-model interaction failures, and can they be predicted? Basis: Paper details one failure mode (smolagents + GPT-5-mini retries) but lacks systematic analysis across configurations.
- **Open Question 4:** Under what conditions does framework choice dominate model choice in performance? Basis: Findings limited to mid-tier models and few benchmarks; boundary unknown for wider model spectrum.

## Limitations
- **Implementation fidelity:** Exact benchmark specs (tool schemas, user simulators) and framework version mappings are not detailed; assumes provided MASEval modules are faithful reimplementations.
- **Corpus support:** Neighboring literature lacks comparable cross-framework, system-level experiments, limiting contextual validation of core premise.
- **Scaling assumption:** Tracing and evaluation design assumes overhead negligible for small-to-medium topologies (≤5 agents); viability for large-scale systems untested.

## Confidence
- **Effort reduction claim:** High confidence (quantitative code metrics, clear architectural mechanism).
- **Framework impact parity claim:** Medium confidence (strong experimental results but reliant on controlled, idiomatic framework implementations; assumes default behaviors persist).
- **Tracing utility for diagnosis claim:** Medium confidence (concrete failure mode analyses but limited to demonstrated scale; assumes adapters fully intercept framework internals).
