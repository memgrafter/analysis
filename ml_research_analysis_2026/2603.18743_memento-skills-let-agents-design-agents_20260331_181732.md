# Memento-Skills: Let Agents Design Agents
## Quick Facts
- arXiv ID: 2603.18743
- Source URL: https://arxiv.org/abs/2603.18743
- Reference count: 23
- Primary result: Achieves +13.7pp (+26.2% relative) on GAIA and +20.8pp (+116.2% relative) on HLE over static Read-Write ablation.

## Executive Summary
Memento-Skills addresses the inherent limitation of frozen LLM agents that cannot learn from deployment experience. It introduces a system where an agent autonomously designs, adapts, and improves task-specific agents by treating reusable skills—stored as structured markdown files—as persistent, evolving external memory. The core mechanism is a Read–Write Reflective Learning loop: a behaviour-aligned skill router selects relevant skills (Read), the LLM executes them (Act), and failure-driven updates optimize or generate new skills (Write), all without LLM parameter updates. Evaluated on the GAIA and Humanity's Last Exam benchmarks, Memento-Skills yields improvements of 13.7 and 20.8 percentage points, respectively, over a static Read-Write ablation. The skill library grows substantially (from 5 seeds to 41 skills on GAIA and 235 on HLE), with performance gains correlating with domain-aligned skill reuse.

## Method Summary
Memento-Skills implements an autonomous agent that improves itself by evolving a library of reusable skills—executable artifacts stored as structured markdown folders containing SKILL.md specifications, script.py code, and prompt templates. The agent follows a Read–Write Reflective Learning loop: for each task query, a behaviour-aligned skill router selects a skill from the library (Read); the frozen LLM executes the skill’s workflow using its tools (Act); an LLM-based judge evaluates the outcome (Feedback); and upon failure, a failure attribution step identifies the responsible skill, which is then rewritten or replaced (Write). All learning occurs in the external skill memory without updating the LLM parameters. The router is trained via single-step offline RL (InfoNCE loss) on synthetic positive and hard-negative query-skill pairs to align retrieval with execution success. Skills are mutated via LLM-driven rewriting and validated by a unit-test gate before persistence. The system is evaluated on GAIA (165 questions) and Humanity’s Last Exam (788 train, 342 test across 8 subjects), starting from 5 atomic seed skills. Metrics include test accuracy, skill library growth, retrieval hit rates, and judge success rates. Ablation studies compare against a static Read-Write variant that lacks skill optimisation.

## Key Results
- GAIA: +13.7 percentage points absolute improvement (+26.2% relative) over static Read-Write ablation.
- Humanity’s Last Exam (HLE): +20.8 percentage points absolute improvement (+116.2% relative) over static ablation.
- Skill library expands from 5 seeds to 41 skills on GAIA and 235 on HLE, with performance gains strongly correlated with domain-aligned skill reuse.

## Why This Works (Mechanism)
The system’s effectiveness derives from three interconnected mechanisms:

### Mechanism 1: Read–Write Reflective Learning Loop
- **Claim:** Continual learning without parameter updates is achieved by treating an external skill library as a writable memory; the agent's policy improves as the library evolves.
- **Mechanism:** A closed loop where (1) a skill router selects a relevant skill from memory (Read), (2) the frozen LLM executes the skill's workflow (Act), and (3) post-execution reflection rewrites skill artefacts (prompts/code) or discovers new skills based on failures (Write). This directly implements policy iteration (evaluation via utility updates, improvement via skill optimisation) on the external memory `M_t`.
- **Core assumption:** The LLM, when conditioned on a high-quality, behaviourally relevant skill artefact, can execute complex multi-step tasks successfully; thus, improving the artefacts improves the overall policy.
- **Evidence anchors:**
  - [abstract] "retrieves a relevant skill... executes them... failure-driven updates optimize or generate new skills... all without LLM parameter updates."
  - [section 2.1] "Writing [is] policy evaluation... Reading [is] policy improvement... each write step directly improves the policy embodied in the skill."
  - [corpus] Neighbors like MemSkill and Proposer-Agent-Evaluator(PAE) explore related skill evolution, but direct evidence for *this specific loop's* effectiveness is primarily from the paper's own benchmarks (GAIA/HLE), not the cited corpus.
- **Break condition:** If the skill library fails to grow (no new skills are created) or if skill optimisations consistently degrade performance (utility score decreases post-Write), the loop stalls and performance plateaus or declines.

### Mechanism 2: Behaviour-Aligned Skill Router
- **Claim:** Retrieval must optimise for *execution success* (behavioural similarity), not just semantic similarity between query and skill text.
- **Mechanism:** The router is a contrastive model fine-tuned via single-step offline RL (InfoNCE loss) on synthetic query-skill pairs. Positives are queries where the skill *should* be selected (leads to successful execution); hard negatives are domain-relevant queries where the skill is *not* the correct tool. This trains the embedding space to approximate a Q-function predicting execution utility.
- **Core assumption:** A model trained on execution-outcome labels (from synthetic or logged data) can generalise to rank skills by their likelihood of leading to a correct answer, even for unseen queries.
- **Evidence anchors:**
  - [abstract] "a behaviour-aligned skill router... selects the most relevant skill" and "static Read-Write ablation" comparison.
  - [section 2.3] "We train the router with single-step offline RL... retrieval optimises for behaviour similarity."
  - [section 2.4/Figure 9] End-to-end evaluation shows the behaviour-aligned router ("Memento-Qwen") significantly improves both route hit rate (0.58 vs 0.53 for Qwen3) and judge success rate (0.80 vs 0.79) over a strong semantic baseline.
- **Break condition:** If the synthetic query generation (Appendix C) produces low-quality or non-representative positives/negatives, the router learns a flawed reward signal. This manifests as high offline recall but low end-to-end judge success rate (the "retrieval-success gap").

### Mechanism 3: Skills as Persistent, Evolving External Memory
- **Claim:** Reusable skills (structured markdown files with code, prompts, specs) are the correct unit of external memory for an LLM agent, enabling consolidation and transfer of procedural knowledge.
- **Mechanism:** Each skill is a persistent, independently versioned artefact. The Write operation mutates these files directly (e.g., patching a Python script, updating a prompt), not just appending to a log. This allows successful patterns to be consolidated into a robust routine ("muscle memory") and brittle ones to be patched or replaced. The library's growth densifies the embedding space, shrinking the effective LLM competence radius `r_M`.
- **Core assumption:** Modular, reusable procedural knowledge can be effectively captured, stored, and revised in a file-system-based format that an LLM can edit and re-execute.
- **Evidence anchors:**
  - [abstract] "reusable skills (stored as structured markdown files) serve as persistent, evolving memory."
  - [section 1.2/Definition 1.1] "A skill memory `M_t` is a finite, growing collection of reusable skill artefacts."
  - [section 3.1/Figure 12] The learned skills form semantically coherent clusters (e.g., "Quantum / Physics"), and performance gains correlate with domain-aligned reuse (stronger on HLE with subject categories than on diverse GAIA).
- **Break condition:** If skill files become monolithic or entangled (as parodied in the "30,000-line main.py" dialogue), they cannot be effectively reused or patched. This leads to skill bloat where the library grows but fails to improve execution because new skills are not truly generalisable or optimisations break existing functionality.

## Foundational Learning
Understanding Memento-Skills requires several conceptual foundations:

- **Concept: Stateful Reflective Decision Process (SRDP)**  
  - **Why needed here:** SRDP is the theoretical foundation. It formalises the agent's state as `(s_t, M_t)`, where the evolving memory `M_t` restores the Markov property. Understanding this is key to grasping *why* freezing the LLM parameters is not a limitation—the policy lives in the memory.  
  - **Quick check question:** If you double the number of skills in `M_t`, what happens to the effective "competence radius" of the LLM and why?

- **Concept: Skill-Level vs. Trajectory-Level Memory**  
  - **Why needed here:** Memento-Skills upgrades Memento 2's raw trajectory logs to *executable skill artefacts*. This changes the Write operation from "append a log" to "rewrite a program/prompt". The practitioner must understand that a "skill" is a folder with `SKILL.md` (spec), `script.py` (code), and `prompts/` (LLM guidance), not just a text chunk.  
  - **Quick check question:** What are the concrete file components of a single skill folder, and which component is most likely to be rewritten after a failure?

- **Concept: One-Step Offline RL for Routing**  
  - **Why needed here:** The router is not a semantic search engine; it's a behaviour-fitted policy. The InfoNCE training with hard negatives is a practical implementation of a KL-regularised one-step Q-learning update. Engineers must understand the data synthesis pipeline (synthetic queries + judge verification) that creates the training signal.  
  - **Quick check question:** Why is using only *semantic* similarity (e.g., BM25) insufficient for skill routing, and what specific failure mode does the RL fine-tuning prevent?

## Architecture Onboarding
Component map:
1. **Memento Agent Core**: Orchestrates the loop. Holds state (current task `q_t`, tip memory `T_t`).
2. **Skill Router**: Takes augmented input `x_t = (q_t, T_t)` and skill library `S_t`, returns selected skill `c_t` (or triggers `CreateSkill`). Implements the contrastive model from section 2.3.
3. **Skill Library (`S_t`)**: A directory of skill folders. Each folder contains `SKILL.md` (declarative spec, keywords), `script.py` (executable code/tool calls), and `prompts/` (LLM guidance prompts).
4. **Execution Engine**: Loads the selected skill's artefacts, renders prompts with `x_t`, calls tools, runs `script.py`, and returns the full trace `a_t` and diagnostic logs.
5. **Judge & Reflection Module**: A separate LLM call (or function) that scores `a_t` against ground truth `a*_t`. On failure, the `Failure Attribution Selector` identifies the responsible skill `c†` from the trace, then the `Skill Rewriter` proposes file-level mutations.
6. **Unit Test Gate**: A synthetic test case generator/executor that validates proposed skill mutations before they are persisted.

Critical path:
`Receive Task (q_t)` → `Router(x_t, S_t) -> c_t` → `Execute(c_t) -> a_t, trace` → `Judge(q_t, a_t) -> r_t` → **If Failure:** `SelectTargetSkill(trace) -> c†` → `RewriteSkill(c†, trace) -> c'` → `UnitTestGate(c') -> persist S_{t+1}`. **If Success:** `UpdateUtility(c_t, r_t)`.

Design tradeoffs:
- **Router Complexity vs. Latency:** A heavier cross-encoder reranker (section 2.4) improves top-1 relevance but adds ~100ms per call. The system defaults to a two-stage (sparse + dense) recall with optional rerank.
- **Skill Granularity:** Too coarse (one skill for all web tasks) → brittle. Too fine (one skill per unique URL) → library bloat, poor transfer. The system targets skills that solve a *class* of similar tasks (e.g., "download PDF from academic site and extract text").
- **Write Aggressiveness:** Rewriting after every failure risks catastrophic forgetting of a skill's generalisable parts. The utility threshold `δ` and sample count `n_min` guard against overfitting to a single failure mode.

Failure signatures:
1. **Retrieval Misalignment** (High route hit rate, low judge success): The router picks a *relevant* skill that is *execution-brittle*. Signature: Skills retrieved have high semantic similarity but fail due to missing edge cases. Fix: Improve synthetic negative quality or add execution trace data to router training.
2. **Skill Bloat** (Library size ↑, accuracy plateau): New skills are near-duplicates or overly specific. Signature: t-SNE (Figure 12) shows tight clusters with high intra-cluster similarity but no new cluster formation. Fix: Adjust `DiscoverSkill` thresholds (`δ`, `n_min`) to favour optimisation over creation.
3. **Optimisation Regression:** Utility of a skill drops after a Write. Signature: `U_{t+1}(c) < U_t(c)` after a rewrite. Fix: Unit Test Gate is failing to catch regressions; need better synthetic test generation or more conservative rewrite prompts.

First 3 experiments:
1. **Router Ablation**: Run GAIA with three routers: (a) BM25, (b) frozen Qwen3-Embedding, (c) Memento-Qwen. Measure `route_hit_rate` and `judge_success_rate`. Hypothesis: (c) > (b) > (a) on both metrics, demonstrating behaviour alignment.
2. **Write-Path Ablation**: Compare full Memento-Skills vs. "Read-Write" ablation (no failure attribution, no skill rewriting, only utility updates and new skill creation). On HLE, expect a significant accuracy gap (e.g., ~20 pt) showing that *in-place optimisation* is critical, not just library growth.
3. **Domain Transfer Test**: Train on a subset of HLE subjects (e.g., Bio, Chem), test on a held-out subject (e.g., Math). Expect near-zero transfer. Then, train on *all* subjects, test on held-out *questions*. Expect significant transfer, confirming that skill reuse requires domain-aligned library structure (Figure 11).

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** What is the precise convergence rate of the memory coverage radius as the skill library scales to very large sizes (e.g., millions of skills), and does the Parzen kernel-based retrieval remain computationally efficient at that scale?
- **Basis in paper:** [explicit] The Epilogue (Page 18) directly asks: "What happens when we hit a million cases? Does the Parzen kernel scale?" and "can we get the convergence rate? Not just 'it converges' but 'it converges in O(n^{-1/d}) episodes'?"
- **Why unresolved:** The current empirical results show convergence on benchmarks with up to 235 skills, but theoretical and practical scalability to much larger libraries remains untested. Computational complexity of retrieval and the asymptotic behavior of the coverage radius are critical for real-world deployment.
- **What evidence would resolve it:** Empirical scaling experiments with skill libraries of increasing size (e.g., 10^4, 10^5, 10^6 skills) measuring retrieval latency, memory footprint, and performance gains. Theoretical analysis extending the Memento 2 bound to large-n regimes with specific kernel choices.

### Open Question 2
- **Question:** How can sandbox safety and isolation be rigorously enforced during skill execution to prevent harmful actions or system damage when running autonomously generated skills in production environments?
- **Basis in paper:** [explicit] In the evaluation dialogue (Page 14), S states: "Sandbox safety — whether it solves the task without breaking anything else — is the third axis, but that requires a proper isolation harness. Future work."
- **Why unresolved:** The current system relies on a unit-test gate with synthetic test cases, but real-world skills may interact with external systems (web, file system, APIs) in unpredictable ways. No formal safety guarantees or containment mechanisms are described.
- **What evidence would resolve it:** Development and integration of a robust sandboxing framework (e.g., containerization, capability restrictions) with formal verification of safety properties. Empirical red-teaming studies assessing failure modes when skills are executed in realistic, high-stakes environments.

### Open Question 3
- **Question:** To what extent can the behaviour-aligned skill router generalize to out-of-distribution natural language queries and novel skill types not represented in the synthetic training data?
- **Basis in paper:** [inferred] The router is trained on 3k synthetic queries derived from a curated catalog of 8k GitHub skills (Page 12). Real user queries are messier (Page 14), and the system generates new skills during deployment that may differ structurally from the training distribution.
- **Why unresolved:** The evaluation uses synthetic recall and real trajectory metrics on the same distribution, but does not test generalization to truly novel phrasing or skill categories. The robustness of the contrastive learning approach to distribution shift is unknown.
- **What evidence would resolve it:** Controlled experiments with adversarial or atypical user queries, and analysis of router performance on skills created de novo by the agent versus those from the seed catalog. Ablation studies varying query noise and domain mismatch.

### Open Question 4
- **Question:** What are the fundamental limits of skill-based external memory for continual learning, and when does the approach become insufficient compared to parameter updating (e.g., fine-tuning)?
- **Basis in paper:** [inferred] The paper asserts "continual learning without updating LLM parameters" (Abstract) but only evaluates on static benchmarks. The theoretical bound (Page 17) includes an LLM quality term ε_LLM(r_M), suggesting performance plateaus when the frozen LLM cannot generalize within the memory's coverage radius.
- **Why unresolved:** No comparison to fine-tuning baselines beyond the static Read-Write ablation. The conditions under which skill memory saturates—e.g., tasks requiring subtle weight adjustments or long-horizon credit assignment—are not explored.
- **What evidence would resolve it:** Experiments on benchmarks with gradually shifting distributions or tasks requiring incremental acquisition of nuanced strategies. Comparisons against lightweight fine-tuning (e.g., LoRA) in terms of sample efficiency and final performance.

### Open Question 5
- **Question:** How should the skill library be managed long-term to avoid unbounded growth, redundancy, and retrieval inefficiency while preserving useful capabilities?
- **Basis in paper:** [inferred] The skill library grows from 5 to 41 (GAIA) and 235 (HLE) skills (Page 15-16) with no pruning mechanism discussed. The convergence analysis (Page 17) assumes growing coverage but does not address library size as a computational constraint.
- **Why unresolved:** In open-ended deployment, the library could grow indefinitely, harming retrieval speed and potentially introducing conflicting skills. No policy for skill consolidation, archiving, or deletion is presented.
- **What evidence would resolve it:** Implementation and evaluation of skill management strategies (e.g., clustering-based compression, utility-based pruning, skill merging). Metrics on retrieval time, memory usage, and performance impact as the library scales beyond current benchmarks.

## Limitations
- **Skill artefact schema undefined**: The exact file structure and required fields for a skill folder are not specified, blocking precise replication of skill evolution and mutation.
- **Judge implementation missing**: The LLM-as-a-judge prompt, model choice, and correctness criteria are not provided, which is critical for evaluating reported accuracy.
- **Synthetic query generation opaque**: The process for generating positive and negative training pairs for the router is undocumented, raising concerns about the quality and representativeness of the routing training data.

## Confidence
- Read–Write Reflective Loop effectiveness: Medium
- Behaviour-Aligned Skill Router: Medium
- Skills as Persistent Memory: High
