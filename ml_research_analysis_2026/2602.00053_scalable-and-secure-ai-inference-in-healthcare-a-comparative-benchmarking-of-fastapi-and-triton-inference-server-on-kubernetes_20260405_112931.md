# Scalable and Secure AI Inference in Healthcare: A Comparative Benchmarking of FastAPI and Triton Inference Server on Kubernetes

## Quick Facts
- **arXiv ID**: 2602.00053  
- **Source URL**: https://arxiv.org/abs/2602.00053  
- **Reference count**: 17  
- **Primary result**: Hybrid FastAPI (gateway) + Triton (backend) architecture optimizes latency, throughput, and HIPAA compliance for healthcare AI deployment.

## Executive Summary
This paper benchmarks two AI inference serving frameworks—FastAPI and NVIDIA Triton—within a Kubernetes environment, focusing on healthcare deployment requirements of scalability, low latency, and HIPAA compliance. Using a DistilBERT model, the study evaluates performance metrics (p50/p95 latency, throughput) under various configurations. Results show that FastAPI on CPU offers lower single-request latency (p50 22 ms, p95 45 ms), while Triton on GPU with dynamic batching achieves much higher throughput (780 req/s, p50 34 ms, p95 60 ms), nearly doubling baseline performance. Based on these findings, the authors propose and validate a hybrid architecture where FastAPI acts as a secure gateway for PHI de-identification and Triton handles compute-intensive inference, providing an optimal balance for enterprise healthcare AI.

## Method Summary
The study compares FastAPI and Triton by deploying a DistilBERT sentiment analysis model on Kubernetes. FastAPI serves the PyTorch model on CPU, while Triton runs the ONNX-exported model on a single NVIDIA T4 GPU with dynamic batching enabled. A separate preprocessing microservice performs PHI de-identification. Performance is measured using Locust load tests at varying concurrency (10, 50, 100 users), collecting latency percentiles and throughput. The hybrid architecture’s end-to-end latency and security compliance are evaluated to determine enterprise suitability.

## Key Results
- FastAPI (CPU) yields lower single-request latency: p50 22 ms, p95 45 ms.  
- Triton (GPU, dynamic batching, batch size 16) achieves high throughput: 780 req/s, p50 34 ms, p95 60 ms.  
- Hybrid FastAPI‑gateway/Triton‑backend architecture validated as optimal for scalable, secure healthcare AI.

## Why This Works (Mechanism)
### Mechanism 1: FastAPI Lower Latency for Single Requests
- **Claim**: FastAPI on CPU yields lower median latency for single-request workloads compared to Triton on GPU.  
- **Mechanism**: The architectural overhead of Triton (scheduling, GPU data transfer) for a single inference request exceeds the time saved by GPU acceleration, whereas FastAPI's direct CPU inference loop has minimal middleware latency.  
- **Core assumption**: Single-request, latency-sensitive scenarios prioritize per-request overhead reduction over raw compute speed.  
- **Evidence anchors**:  
  - Abstract: "FastAPI provides lower overhead for single-request workloads with a p50 latency of 22ms"  
  - Section VII.B.1: "For single, sequential requests, the time required to schedule the inference and move data to the GPU outweighs the acceleration benefits... FastAPI... encounters less architectural overhead."  
- **Break condition**: If request batching is enforced (even small batches), Triton's throughput scaling may negate the latency advantage; or if the model is too large for CPU memory, forcing CPU swapping.

### Mechanism 2: Triton Higher Throughput via Dynamic Batching
- **Claim**: Triton's dynamic batching on GPU significantly increases throughput (req/s) with a marginal increase in tail latency (p95).  
- **Mechanism**: Dynamic batching aggregates multiple incoming requests into a single GPU kernel execution, amortizing fixed costs (data transfer, kernel launch) across many inferences, thus maximizing GPU utilization.  
- **Core assumption**: Healthcare batch workloads (e.g., overnight EHR processing) can tolerate slightly higher tail latency for massively increased volume.  
- **Evidence anchors**:  
  - Abstract: "Triton achieves superior scalability through dynamic batching, delivering a throughput of 780 requests per second... nearly double that of the baseline."  
  - Section VII.B.2: "Shifting to a Batch Size of 16 resulted in a dramatic increase in throughput... This demonstrates that Triton allows the system to process significantly more volume with only a marginal increase in latency."  
- **Break condition**: If requests have strict real-time deadlines preventing queuing; or if batch size is capped too low (e.g., due to memory constraints), limiting aggregation benefits.

### Mechanism 3: Hybrid Architecture for Security and Performance
- **Claim**: A hybrid FastAPI-gateway/Triton-backend architecture optimally balances HIPAA compliance and scalable performance for enterprise healthcare AI.  
- **Mechanism**: Decoupling security/PHI handling (in FastAPI gateway) from compute-intensive inference (in Triton) allows each component to be optimized independently: FastAPI for auth/routing/logging, Triton for GPU batching.  
- **Core assumption**: PHI de-identification must occur before inference to minimize data exposure surface; Triton's performance is degraded by non-compute security logic.  
- **Evidence anchors**:  
  - Abstract: "A hybrid architecture using FastAPI as a secure gateway for PHI de-identification and Triton for backend inference is validated as the optimal enterprise solution."  
  - Section VIII: "The separation of concerns... allows for robust PHI de-identification in the preprocessing layer... The architecture... using FastAPI to sanitize inputs and Triton to execute inference represents the optimal configuration."  
- **Break condition**: If preprocessing latency dominates (e.g., complex PHI redaction), the end-to-end gain is lost; or if regulatory rules require PHI to never leave a secure enclave that Triton cannot access.

## Foundational Learning
- **Dynamic Batching**:  
  - *Why needed*: It is the primary lever Triton uses to achieve >2x throughput over non-batched serving; misunderstanding this leads to misinterpreting latency vs. throughput trade-offs.  
  - *Quick check*: If Triton's batch size is 1, how would its p95 latency compare to FastAPI's, and why?

- **PHI De-identification as a Preprocessing Step**:  
  - *Why needed*: Separating this security-critical step from inference is a core design choice for HIPAA compliance; conflating it with model serving creates risk and performance bottlenecks.  
  - *Quick check*: What happens to system design if PHI de-identification must occur *inside* the Triton model's preprocessing pipeline?

- **Kubernetes Horizontal Pod Autoscaling (HPA) Metrics**:  
  - *Why needed*: The paper's HPA uses CPU utilization, which is a lagging indicator for GPU workloads; understanding this limitation is key to scaling inference servers correctly.  
  - *Quick check*: Why might CPU-based HPA cause under-scaling of a GPU inference server during a traffic surge?

## Architecture Onboarding
### Component Map
Load Generator → FastAPI Gateway → Preprocessor → Triton Inference Server; Kubernetes Control Plane orchestrates all.

### Critical Path
Request → FastAPI (Auth) → Preprocessor (De-identify) → Triton (Batch+Infer) → FastAPI (Format response) → Client.

### Design Tradeoffs
- Latency vs. Throughput: FastAPI (low latency, low throughput) vs. Triton (higher tail latency, high throughput).  
- Security vs. Performance: PHI sanitization in a separate microservice adds network hop but contains breach risk.  
- Complexity vs. Control: Hybrid is more complex to deploy but offers granular security and scaling policies.

### Failure Signatures
- High p95 latency with good throughput: Normal for batched Triton; investigate if batch wait times are excessive.  
- Authentication errors from FastAPI: Misconfigured JWT or OAuth2 provider; check SECURITY.md policies.  
- Triton pod OOM/CPU throttling: Model too large for GPU memory or HPA not scaling; check DCGM metrics (missing in current HPA).  
- Preprocessor backlog: PHI de-identification is too slow; monitor queue lengths; may need more replicas.

### First 3 Experiments
1. **Baseline Latency Test**: Send single requests (batch_size=1) to FastAPI-only and Triton-only (no batching) to reproduce p50/p95 gap (Expected: FastAPI ~22ms p50, Triton ~28ms p50).  
2. **Throughput Scaling Test**: Ramp concurrent users to 100 with Triton dynamic batching (max_batch_size=16). Measure req/s and p95. Expected: ~780 req/s, p95 ~60ms.  
3. **Hybrid PHI Flow Test**: Send raw text with embedded PHI (e.g., "Patient John Doe, SSN 123-45-6789") through full pipeline. Verify PHI is stripped in Triton's input tensor and that audit logs in FastAPI record the de-identification event.

## Open Questions the Paper Calls Out
- **GPU-aware autoscaling**: How can GPU-aware autoscaling be implemented for Triton on Kubernetes using DCGM metrics? (Basis: Future work should implement GPU-aware autoscaling using NVIDIA DCGM metrics.)  
- **Edge deployment**: How can the hybrid architecture be adapted for edge deployments with limited resources? (Basis: Adapting this stack for lightweight edge devices remains a challenge.)  
- **Drift detection**: What integrated drift detection mechanism can ensure patient safety by alerting to clinical data distribution shifts? (Basis: Integrating statistical monitoring to detect when clinical data distributions shift is a critical next step.)

## Limitations
- Missing exact deployment configurations (YAML manifests, container images, resource limits) prevents faithful replication.  
- Benchmark restricted to DistilBERT on a single NVIDIA T4 GPU; generalization to other models or hardware is uncertain.  
- HPA based on CPU metrics is a poor indicator for GPU workloads, potentially undermining scaling claims.

## Confidence
- FastAPI yields lower median latency for single requests: **Medium**  
- Triton achieves higher throughput via dynamic batching: **Medium**  
- Hybrid FastAPI‑gateway/Triton‑backend is optimal for enterprise healthcare: **Medium**
