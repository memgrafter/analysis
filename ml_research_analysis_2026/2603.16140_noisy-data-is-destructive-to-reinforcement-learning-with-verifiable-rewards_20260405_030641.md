# Noisy Data is Destructive to Reinforcement Learning with Verifiable Rewards

## Quick Facts
- **arXiv ID:** 2603.16140
- **Source URL:** https://arxiv.org/abs/2603.16140
- **Reference count:** 40
- **Primary result:** Truly annotation-noisy data causes 8–10% performance degradation in RLVR on math benchmarks, and current SOTA improvements fail to mitigate this, underscoring that high-quality annotations are indispensable.

## Executive Summary
This paper disputes the claimed robustness of reinforcement learning with verifiable rewards (RLVR) to noisy data. It reveals that prior "100% noisy" datasets were contaminated with correct answers due to weak verification. Using a rigorous re-verification pipeline (GPT-5 Pro, symbolic checking, manual validation), the authors construct a truly noisy dataset. Experiments demonstrate that training on this cleanly synthesized noise significantly harms performance (8–10% drop) on mathematical reasoning benchmarks, matching the poor results of training with format-only rewards. Crucially, five state-of-the-art RLVR algorithm enhancements—including DAPO, SAPO, and Dr. GRPO—do not overcome this degradation, performing on par with basic GRPO. Real-world human annotation errors in a corrected Text2SQL dataset also cause a 5–12% accuracy drop versus a clean version. The core conclusion is that present RLVR methods cannot compensate for poor data quality; meticulous annotation remains non-negotiable.

## Method Summary
The authors first exposed contamination in existing RLVR datasets by re-verifying examples labeled as "incorrect" using a multi-stage pipeline: GPT-5 Pro for initial assessment, symbolic execution for programmatic checks, and manual validation for edge cases. This removed 16.4% of originally tagged incorrect examples that were actually correct, yielding a dataset with pure synthetic noise. They then trained several RLVR algorithms (GRPO, DAPO, SAPO, Dr. GRPO, and others) on both this truly noisy set and a clean counterpart, evaluating on mathematical reasoning (e.g., MATH) and Text2SQL benchmarks. A similar correction was applied to a real-world Text2SQL dataset with human annotation errors to assess practical impact.

## Key Results
- Dataset contamination was severe: 16.4% of "incorrect" examples in prior noisy RLVR datasets were re-verified as correct.
- Training on truly noisy data degrades mathematical reasoning performance by 8–10% compared to clean data, performing similarly to training with format-only rewards.
- Five SOTA RLVR improvements (DAPO, SAPO, Dr. GRPO, etc.) fail to mitigate noise-induced degradation; all perform comparably to basic GRPO.
- Real human annotation errors in a corrected Text2SQL dataset cause a 5–12% accuracy drop versus the clean version.

## Why This Works (Mechanism)
RLVR algorithms depend on accurate binary correctness signals from verifiable rewards to guide policy updates. Noisy labels introduce misleading gradients that corrupt the learning process, as the policy is steered by incorrect reward feedback. The paper shows this effect is robust across algorithmic improvements, indicating that current methods lack explicit mechanisms to detect or downweight erroneous reward signals. The degradation occurs because noise effectively reduces the signal-to-noise ratio in the reward function, and without robust noise modeling, optimization diverges from the intended objective.

## Foundational Learning
- **Reinforcement Learning with Verifiable Rewards (RLVR):** Training paradigm where a programmatic checker provides binary correct/incorrect rewards. *Why needed:* Avoids reward modeling, directly optimizing for task success. *Quick check:* Can every model output be automatically judged?
- **Annotation Noise:** Errors in data labeling, whether synthetic or human-induced. *Why needed:* Real datasets are imperfect; understanding noise impact is critical for reliability. *Quick check:* What is the estimated label error rate?
- **Policy Gradient Methods (e.g., GRPO):** RL algorithms that update the policy by estimating reward gradients. *Why needed:* Core optimization engine for RLVR. *Quick check:* Does the update use relative reward differences between outputs?
- **Benchmark Evaluation:** Standardized test sets (e.g., MATH) for measuring model performance. *Why needed:* Provides objective, comparable metrics. *Quick check:* Are test samples held-out and unambiguous?
- **Reward Signal Quality:** Fidelity of the verifiable reward function. *Why needed:* Directly determines learning signal correctness. *Quick check:* Does the reward match ground-truth solution equivalence?

## Architecture Onboarding
**Component map:** Data Annotation -> Re-verification Pipeline (GPT-5 Pro + Symbolic Check + Manual) -> Clean/Noisy Dataset Splits -> RL Training (GRPO Variants) -> Benchmark Evaluation

**Critical path:** Rigorous re-verification ensures dataset quality -> Controlled training on noisy vs. clean data -> Quantitative performance comparison on held-out benchmarks.

**Design tradeoffs:** Synthetic noise offers control but may not mirror real error distributions; manual verification is accurate but costly and non-scalable; binary correctness simplifies reward but ignores partial correctness.

**Failure signatures:** Consistent accuracy drop (8–10%) on mathematical benchmarks when training on noisy data, irrespective of algorithmic enhancements; performance converges to that of format-only reward training.

**First three experiments:**
1. Reproduce the 8–10% degradation on the MATH benchmark using the authors' truly noisy dataset vs. clean data with GRPO.
2. Test a broader set of RLVR algorithms (e.g., RLOO, KTO) on the noisy dataset to verify universality of failure.
3. Vary noise injection levels (e.g., 5%, 20%, 50%) to characterize the degradation curve and determine a noise tolerance threshold.

## Open Questions the Paper Calls Out
The paper does not explicitly enumerate open questions. However, the findings and discussion raise several important questions for future research, including: whether noise-robust RLVR algorithms can be designed; how noise sensitivity varies across tasks and domains; and whether automatic methods can detect or correct annotation errors during training.

## Limitations
- Synthetic noise may not capture the distribution of real-world annotation errors.
- The multi-stage re-verification pipeline itself may contain residual errors or biases.
- Experimental scope is limited to mathematical reasoning and Text2SQL; generalizability to other tasks remains unknown.

## Confidence
- Prior RLVR datasets were significantly contaminated: **High** (direct re-verification evidence).
- True annotation noise degrades RLVR performance: **High** (consistent 8–10% drops across benchmarks).
- SOTA RLVR improvements fail to mitigate noise: **Medium** (only five algorithms tested).
- Real human annotation errors cause performance drop: **Medium** (single corrected dataset).
- Current RLVR cannot compensate for poor data quality: **Medium** (broadly supported but not exhaustive).

## Next Checks
1. Expand evaluation across diverse tasks (code generation, instruction following) and a wider array of RLVR algorithms to test the universality of noise sensitivity.
2. Collect multiple real-world noisy datasets with independently estimated error rates, apply the same re-verification pipeline, and correlate noise level with RLVR performance degradation.
3. Design and implement noise-robust RLVR variants (e.g., confidence-weighted rewards, explicit noise modeling in loss) and benchmark them against standard GRPO on truly noisy data.
