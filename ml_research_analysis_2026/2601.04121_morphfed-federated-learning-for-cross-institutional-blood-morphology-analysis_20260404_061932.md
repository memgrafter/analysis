# MORPHFED: Federated Learning for Cross-institutional Blood Morphology Analysis
## Quick Facts
*   **arXiv ID:** 2601.04121
*   **Source URL:** https://arxiv.org/abs/2601.04121
*   **Reference Count:** 0
*   **Primary Result:** Federated learning models achieve 87-93% of centralized training balanced accuracy (0.58 vs 0.61-0.67) while preserving privacy and generalizing better to a completely unseen external site (67% vs 64%).

## Executive Summary
MORPHFED tackles the challenge of building robust AI for blood morphology analysis across different hospitals without sharing sensitive patient data. It evaluates multiple federated learning (FL) aggregation strategies (FedAvg, FedMedian, FedProx, FedOpt) and model architectures (ResNet-34, DINOv2-S) on data from multiple clinical sites. Key findings show that FL models perform nearly on par with centrally trained models on internal validation and crucially outperform them on a held-out external hospital. The combination of FedOpt with the pre-trained DINOv2-S architecture excels at learning representations for rare diagnostic cell types, such as Metamyelocytes, where simpler aggregation fails entirely.

## Method Summary
The study implements standard federated learning across multiple clinical sites. Each site trains a local model on its private blood smear dataset. Model updates (weights or gradients) are sent to a central server, which aggregates them using one of several strategies (FedAvg, FedMedian, FedProx, FedOpt) to produce an improved global model, which is then redistributed. This process repeats for a fixed number of rounds. Two architectures are compared: a from-scratch ResNet-34 and a fine-tuned DINOv2-S transformer. Performance is measured primarily using balanced accuracy, with external validation on a completely unseen hospital site to test generalization.

## Key Results
*   Federated models (best case) achieve a balanced accuracy of 0.58 on internal validation, which is 87-93% of the centralized model's 0.61-0.67.
*   On a completely unseen external hospital site, the best federated model (FedOpt with DINOv2-S) achieves 67% balanced accuracy, outperforming the centralized model's 64%.
*   For the rare class "Metamyelocytes," FedOpt with DINOv2-S attains an F1-score of 0.14, while FedMedian aggregations fail entirely (F1: 0.00).

## Why This Works (Mechanism)
The paper suggests that federated learning's success stems from its ability to learn domain-invariant representations by exposing the model to the natural heterogeneity (dataset shifts) across multiple sites during training, without requiring the actual data to be pooled. This process forces the global model to become robust to variations in staining, scanners, and patient populations that would be missed in a single-site or naive centralized training setup. The privacy guarantee is inherently provided by the FL framework, as raw images never leave their originating institution.

## Foundational Learning
*   **Federated Learning (FL):** A distributed machine learning framework where multiple clients (e.g., hospitals) collaboratively train a shared model without exchanging raw data. **Why Needed:** Enables model development under strict data privacy and regulatory constraints. **Quick Check:** Does the communication protocol (client -> server -> client) prevent any raw data transmission?
*   **Non-IID Data:** The statistical distribution of data (e.g., class prevalence, image characteristics) is different across clients. **Why Needed:** Real-world FL scenarios involve natural dataset shifts between institutions; the paper's core premise is handling this. **Quick Check:** Are per-site class balance and feature statistics reported or visualized?
*   **Model Aggregation (FedAvg, FedMedian, etc.):** Algorithms to combine locally trained model updates into a single global model. **Why Needed:** This is the core server-side operation of FL, directly impacting convergence and robustness to Non-IID data. **Quick Check:** Is the mathematical update rule for each aggregation strategy clearly defined?
*   **Privacy Preservation (FL vs. DP):** FL provides a basic privacy property by keeping data local. **Why Needed:** The primary motivation for using FL in healthcare. **Quick Check:** Is there any discussion or implementation of formal privacy mechanisms like Differential Privacy (DP) or empirical privacy auditing?
*   **Domain Generalization:** A model's ability to perform well on data from a distribution not seen during training. **Why Needed:** The external validation site represents a novel domain; FL's advantage is claimed to be improved generalization. **Quick Check:** Is the external site's data distribution compared to the training sites (e.g., via feature statistics or visualization)?

## Architecture Onboarding
### Component Map
Clients (Site 1, Site 2, ...) -> Local Training (Epochs) -> Send Model Update -> Central Server -> Aggregation (FedAvg/Median/Prox/Opt) -> Updated Global Model -> Broadcast Global Model -> Clients.

### Critical Path
1.  Local training on private data for a fixed number of epochs.
2.  Transmission of model parameters (weights) to the central server.
3.  Server-side aggregation of received updates according to the chosen strategy.
4.  Distribution of the new global model back to all clients.
5.  Repeat steps 1-4 for a predetermined number of communication rounds.

### Design Tradeoffs
*   **Aggregation Robustness vs. Sensitivity:** FedMedian is robust to outlier updates (e.g., from high-noise clients) but, as shown, can suppress weak but valid signals (rare classes). FedOpt is sensitive to such conflicts, causing divergence on some architectures (ResNet-34), but can capture nuanced signals when stable (DINOv2-S).
*   **Architecture Prior (Random vs. Pre-trained):** Using a pre-trained backbone (DINOv2-S) provides a robust feature extractor that appears more compatible with adaptive optimizers (FedOpt) and better at capturing rare patterns. A from-scratch ResNet-34 is more susceptible to diverging under the same aggregation.
*   **Computational Load:** More complex aggregation (FedOpt) and larger models (DINOv2-S) increase per-round server computation and communication bandwidth needs.

### Failure Signatures
*   **FedMedian + Rare Class:** Complete failure (F1=0.00) to predict a specific rare diagnostic class like Metamyelocytes, indicating the median operation is discarding all relevant gradient information for that class across all clients.
*   **FedOpt + ResNet-34:** Divergence or severely degraded performance (balanced accuracy 0.3638), suggesting gradient conflicts from Non-IID data overwhelm the adaptive optimizer on a sharp loss landscape.
*   **Generalization Gap:** If federated performance on the external site drops significantly closer to the centralized model's gap, it would indicate the FL benefits were specific to the training sites' heterogeneity and not truly generalizable.

### First 3 Experiments
1.  **Per-Class Gradient Tracking:** During FL rounds, track the average norm and cosine similarity of gradients *specific to the Metamyelocyte class* across clients. This tests the hypothesis that median aggregation discards weak, minority-class gradient signals.
2.  **Architecture Gradient Conflict Analysis:** For ResNet-34 vs. DINOv2-S under FedOpt, compute the variance and pairwise cosine similarity of client updates after local training. High variance/low similarity would quantify "gradient conflicts" and their mitigation by the pre-trained transformer.
3.  **Resource Benchmarking:** Run local training epochs on hardware simulating an LMIC clinic (e.g., a mid-range CPU or a low-end GPU). Measure time per epoch and peak memory usage. Compare total communication cost (model size * rounds) against realistic bandwidth constraints.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Why does FedMedian aggregation systematically fail to detect rare diagnostic classes like Metamyelocytes, and how can aggregation algorithms be modified to preserve weak minority-class signals without sacrificing robustness to heterogeneous client updates?
- **Basis in paper:** [explicit] The paper states: "FedMedian demonstrates the most consistent performance across both architectures... but completely failed to classify Metamyelocytes (F1: 0.00)" and "median-based aggregation suppresses weak signals from the rarest classes."
- **Why unresolved:** The paper identifies the outcome but does not analyze whether this stems from gradient sparsity, update magnitude disparities, or median filtering discarding minority-class gradients. No mechanism is proposed to reconcile median robustness with rare-class preservation.
- **What evidence would resolve it:** Controlled experiments tracking per-class gradient norms and directions across federated rounds; simulation studies with synthetic non-IID splits where rare-class prevalence is manipulated; development of a weighted median variant that upweights minority-class updates.

### Open Question 2
- **Question:** What architectural properties determine the stark divergence in FedOpt performance between ResNet-34 (0.3638 balanced accuracy) and DINOv2-S (0.5594), and can aggregation strategies be made robust to such architectural heterogeneity?
- **Basis in paper:** [explicit] "FedOpt’s adaptive optimization amplifies gradient conflicts arising from non-IID data distributions, causing ResNet34’s sharp loss landscape to diverge, while DINOv2-S’s pre-trained transformer backbone demonstrates robustness."
- **Why unresolved:** The speculation about loss landscape sharpness and pretraining benefits is not empirically validated; no metrics (e.g., gradient variance, client update similarity) are provided to quantify "gradient conflicts" or explain why transformers resist them.
- **What evidence would resolve it:** Compare gradient cosine similarity and magnitude variance across clients for both architectures; evaluate FedOpt with different pretraining strategies (e.g., supervised ResNet); measure loss curvature (e.g., via Hessian traces) during FL.

### Open Question 3
- **Question:** Does federated learning trained on only two Western sites consistently generalize to diverse low- and middle-income country (LMIC) settings, and does it retain its advantage over centralized training under such extreme dataset shifts?
- **Basis in paper:** [inferred] External validation used a single Spanish hospital (Client 3); the paper claims benefits for LMICs but lacks data from actual LMIC sites. The introduction emphasizes LMIC applicability but the validation does not target that context.
- **Why unresolved:** Generalization to Barcelona may not represent the full spectrum of staining, device, and population heterogeneity in LMICs; the comparative advantage over centralized training on unseen LMIC data remains conjectural.
- **What evidence would resolve it:** Prospective multi-center study involving hospitals from multiple LMICs; evaluation of FL vs. centralized models on each site's local hold-out set; measurement of domain shift severity (e.g., via Fréchet inception distance) between training sites and LMIC test sites.

### Open Question 4
- **Question:** What are the actual computational and communication costs of federated learning deployment in resource-constrained clinical settings (e.g., limited GPU memory, slow networks), and do these costs make FL infeasible compared to centralized alternatives?
- **Basis in paper:** [inferred] The introduction states that "storing and processing large medical imaging datasets often exceeds the computational capacity available in many LMIC clinical settings," and positions FL as a solution. However, experiments assume standard local training (5 epochs × 5 rounds) without simulating low-resource hardware.
- **Why unresolved:** The feasibility claim is based on privacy and data-sharing benefits, not on measured local resource utilization (e.g., RAM, training time per epoch on low-end devices); communication overhead (model size × rounds) is not discussed in the context of poor network connectivity.
- **What evidence would resolve it:** Benchmark local training time, memory footprint, and energy consumption on hardware typical of LMIC clinics (e.g., entry-level GPUs or CPUs); simulate bandwidth constraints and quantify total communication volume; compare with centralized training's server-side costs and data-transfer requirements.

## Limitations
*   **Unquantified Dataset Shift:** The nature and extent of heterogeneity (e.g., scanner models, stain protocols, demographic distributions) across the five sites are not described, making it difficult to interpret *why* FL generalizes better.
*   **Centralized Baseline Ambiguity:** The composition and training protocol of the centralized model (which sites' data were pooled?) is unclear, undermining the validity of the "87-93% of centralized" performance ratio.
*   **Lack of Statistical Validation:** No confidence intervals or significance tests are provided for key comparisons (e.g., FL 67% vs Centralized 64% on external site), leaving the reported advantages potentially attributable to chance.
*   **Qualitative Privacy Claim:** Privacy is asserted by the FL framework's design (no raw data sharing) but lacks quantitative backing (e.g., a differential privacy ε budget or resistance to membership inference attacks).

## Confidence
*   **FL Generalization to Unseen Site (67% vs 64%):** **High**. This is a clean, externally validated result on a held-out site.
*   **Rare Class Learning (Metamyelocyte F1=0.14 with FedOpt/DINOv2):** **Medium**. The result is specific and contrasts with FedMedian's failure, but the absolute F1-score remains very low.
*   **FL Achieving 87-93% of Centralized Performance:** **Medium**. This hinges on the unspecified quality and heterogeneity of the centralized baseline.
*   **Privacy Preservation via FL:** **Low**. The claim is methodological (no data sharing) without measurable privacy-utility trade-off accounting or attack evaluation.

## Next Checks
1.  **Request Site-Wise Performance Breakdowns:** Obtain per-site validation balanced accuracy for all FL strategies and the centralized model to diagnose heterogeneity impact and validate aggregate claims.
2.  **Demand Privacy Budget Calculation or Attack Simulation:** Require the authors to report a formal privacy budget (ε) if Differential Privacy is used, or to provide results of a membership inference attack evaluation against the federated models.
3.  **Insist on Paired Statistical Testing:** For primary comparisons (e.g., external site performance, rare-class F1), demand p-values from appropriate tests (e.g., bootstrapped CIs, McNemar's test) to establish statistical significance.
