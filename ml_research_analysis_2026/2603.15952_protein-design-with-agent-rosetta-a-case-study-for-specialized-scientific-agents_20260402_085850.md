# Protein Design with Agent Rosetta: A Case Study for Specialized Scientific Agents
## Quick Facts
- **arXiv ID**: 2603.15952
- **Source URL**: https://arxiv.org/abs/2603.15952
- **Reference count**: 40
- **Primary result**: Agent Rosetta matches ProteinMPNN and human experts on canonical design and achieves up to 14.5% successful non-canonical amino acid insertion on the hardest target, outperforming human baseline (0%).

## Executive Summary
Protein design tools are limited: machine learning methods excel with canonical amino acids but are constrained to fixed pipelines, while the powerful physics-based Rosetta suite remains inaccessible due to complex scripting and steep expertise requirements. This paper introduces Agent Rosetta, an LLM agent paired with a structured environment that abstracts Rosetta’s XML-based RosettaScripts into semantic actions. The agent iteratively refines designs by selecting actions, generating parameters, and incorporating feedback, combining LLM reasoning with Rosetta’s generality. Evaluated on canonical-only and non-canonical (N1-formyl-tryptophan) design tasks, Agent Rosetta matches specialized ML models and human experts on canonical design and significantly outperforms humans on NCAA insertion where ML fails. The study demonstrates that tailored environment design, not merely prompt engineering, is essential to integrate LLMs with specialized scientific software, opening a path to broader scientific tool accessibility.

## Method Summary
Agent Rosetta builds a Gym-like environment around Rosetta’s FastDesign, exposing three action types: `rotamer_change`, `backbone_change`, and `go_back_to_step`. The agent operates in a two-step loop: first, it selects an action based on a summarized state (energy statistics, per-residue diagnostics, structural metrics); then the environment returns documentation for that action, and the agent generates parameters in a simplified syntax. The environment’s converter translates these parameters into valid RosettaScripts XML, executes the design on an ensemble of 128 candidates, computes metrics (Rosetta energy, cavity volume, per-residue strains, ESMFold/AF3 properties), filters to the Pareto front, and updates the state. A key innovation is the simplified syntax for composition penalties and task operations, which boosts action-generation success from ~70% to >98%. The agent runs for up to 30 steps per trajectory. This architecture allows LLMs to leverage Rosetta’s generality without requiring expert-level scripting knowledge.

## Key Results
- **Canonical design**: Across eight protein backbones, Agent Rosetta matches ProteinMPNN and human experts, achieving ESMFold RMSD within ~0.2 Å.
- **Non-canonical amino acid design**: For N1-formyl-tryptophan insertion, Agent Rosetta outperforms the human baseline; GPT-5 attains up to ~14.5% successful core inclusion on the hardest structure (8UZL) where humans achieve 0%.
- **Efficiency gains**: Simplified environment syntax raises action-generation success from ~70% to >98% across all tested LLMs, reducing monetary and computational costs by orders of magnitude.

## Why This Works (Mechanism)
### Abstraction of RosettaScripts into Semantic Actions
- **Claim**: Success stems from abstracting Rosetta’s complex XML scripting into semantic actions with simplified syntax, not from prompting alone.
- **Mechanism**: The environment provides structured action templates and converts agent-generated simplified parameters into valid RosettaScripts XML. This separation lets the LLM focus on domain reasoning while the wrapper guarantees syntactic correctness. The two-step protocol (action selection → parameter generation) uses documentation to avoid recall errors.
- **Core assumption**: LLMs have biophysical knowledge but cannot reliably produce correct RosettaScripts due to its uncommon syntax and intricate parameter interactions; abstraction bridges this gap.
- **Evidence**: Prompt engineering alone fails; action-generation success jumped from ~70% to >98% with simplified syntax (Page 6, Section 3.1).
- **Break condition**: If simplified syntax cannot capture advanced Rosetta features, the agent’s expressiveness will be limited, necessitating more complex wrappers or a constrained design space.

### Iterative Refinement with Surrogate Metrics
- **Claim**: Multi-turn refinement using low-cost proxy metrics allows LLMs to adapt protocols and match specialized ML models and human experts.
- **Mechanism**: After each action, the environment computes ensemble statistics (energy, RMSD, cavity volume, per-residue strains) and retains Pareto-optimal designs. The agent reasons on these metrics and history to pick the next action, performing a guided search through protocol space.
- **Core assumption**: Surrogate metrics, though biased (e.g., ESMFold favors naturalistic sequences), are sufficiently correlated with true quality to guide the search.
- **Evidence**: On eight backbones, Agent Rosetta’s median ESMFold RMSD matches ProteinMPNN within 0.2 Å (Section 3.2). The metrics are chosen to reflect how scientists use Rosetta (Page 5).
- **Break condition**: Surrogates may mislead on exotic designs (e.g., NCAs), leading to locally optimal but globally poor solutions; AF3 validation suggests the risk is manageable but not eliminated.

### Two-Step Reasoning with Documentation
- **Claim**: The protocol of first selecting an action, then generating parameters with access to documentation, yields reliable biophysical reasoning while ensuring syntactic validity.
- **Mechanism**: The agent chooses an action based on the current state. The environment then supplies full documentation (parameter names, allowed values). The agent reasons again to produce concrete parameters. This prevents guessing of complex syntax and keeps focus on scientific parameter choices.
- **Core assumption**: LLMs can identify appropriate high-level actions but struggle with implementation details; providing documentation at this stage leverages their instruction-following without overwhelming context.
- **Evidence**: Without documentation, models failed to generate correct penalty blocks; with the two-step protocol, success exceeded 98% (Sections 3.1). The agent is instructed to produce an "action plan that expert scientists can understand, review, and criticize."
- **Break condition**: Incomplete or ambiguous documentation can still lead to invalid parameters; the authors resorted to ad-hoc summaries, indicating the documentation itself requires expert curation.

## Foundational Learning
- **Monte Carlo sampling in Rosetta**  
  *Why needed*: Rosetta movers run stochastic moves and accept/reject based on energy. The agent must know that each action yields an ensemble (128 candidates) and interpret distribution metrics (mean vs. std).  
  *Quick check*: Why does the environment run 128 parallel processes per action, and how should the agent treat standard deviation versus mean metrics?

- **Energy function components and per-residue diagnostics**  
  *Why needed*: The agent uses per-residue energy terms (e.g., `interresidue_repulsion`, `ramachandran_preference`) to pinpoint problematic residues. Understanding what each term penalizes (clashes, strained backbone) is key to corrective actions.  
  *Quick check*: What does a high `ramachandran_preference` penalty indicate, and which `backbone_change` parameters might reduce it?

- **Residue selection logic in RosettaScripts**  
  *Why needed*: Actions target regions defined by ResidueSelectors (Layer, Index, Neighborhood, And/Or). The agent must correctly specify selectors to designate core, boundary, surface, or custom segments for NCAA accommodation.  
  *Quick check*: When inserting an NCAA into a protein core, why might an Index selector for a single residue fail with `backbone_change`, and what minimum segment size is required?

## Architecture Onboarding
#### Component map
1. **LLM Agent**: Generates natural language reasoning and structured action parameter XML; receives system prompt, design brief, state summary, and action documentation.
2. **Environment Wrapper**: Maintains the pose ensemble, computes metrics, filters Pareto front, executes RosettaScripts via Rosetta’s C++ API, handles errors.
3. **Simplified Syntax Converter**: Parses the agent’s simplified penalty/restriction descriptions and renders valid RosettaScripts XML (e.g., maps “SHAPE ABOVE” to proper PENALTIES line).
4. **State Summarizer**: Compresses full pose data into human-readable tables covering energy statistics, compositional changes, per-residue outliers, structural metrics (cavity, Rg), and task-specific metrics (ESMFold RMSD/pLDDT or NCAA inclusion rate).
5. **Action Documentation Database**: Holds pre-written simplified docs for each action type with examples and edge cases.
6. **Task Configurator**: User supplies PDB file, NCAA params file (e.g., TRF.params), design brief, metric weights, ensemble size, and maximum steps.
7. **Pareto Filter**: After each action, ranks designs by multiple objectives (e.g., low energy, low RMSD, high TRF inclusion) and retains a top fraction for the next iteration.

#### Critical path
Design brief → Load PDB → Initialize poly-G or native sequence → For each step: Agent selects action → Environment returns documentation → Agent generates parameters → Converter produces XML → Rosetta executes on 128 candidates → Metrics computed → Pareto filter selects survivors → State updated → Next step. Termination occurs at step limit or when no metric improvement is observed.

#### Design tradeoffs
- **Simplified syntax coverage**: Current wrappers support `rotamer_change`, `backbone_change` (Small/Shear/Backrub), and `go_back_to_step`. Adding other movers (e.g., docking) requires new converters.
- **Ensemble size vs. cost**: 128 balances diversity and compute load; smaller ensembles risk missing good designs, larger ones increase cost linearly. The agent could adaptively adjust based on metric variance.
- **Metric selection**: ESMFold is fast but biased; AF3 is accurate for NCAs but too slow for per-step. The system relies on Rosetta metrics for guidance and uses AF3 only for post-hoc validation.
- **Two-step latency**: Separate LLM calls for action selection and parameter generation double API cost per step. Merging could reduce cost but might compromise reliability.

#### Failure signatures
- **High unsatisfied H-bond penalty** despite good packing → backbone strain; apply `backbone_change`.
- **Zero TRF inclusion** after several steps → agent omitted NCAA composition penalty or used a ResidueSelector that excludes the core; recheck penalties and selectors.
- **Action success rate < 85%** → environment wrapper missing edge cases; inspect error logs for schema violations.
- **ESMFold RMSD decreases while Rosetta energy increases** → agent overfitting to ML surrogate; reweight metrics to favor Rosetta energy.
- **Backbone_change runtime error “segments_.size() failed”** → ResidueSelector segment too small (<3 residues) or invalid (e.g., single noncontiguous residue); ensure selector covers a valid contiguous segment.

#### First 3 experiments
1. **Baseline canonical design on 1UBQ**: Run Agent Rosetta (GPT-5) for 30 steps using only `rotamer_change`. Expect median final ESMFold RMSD ~0.8 Å, action success >90%. Compare against a naive baseline lacking selectors.
2. **NCAA insertion on 1QYS**: Incorporate one TRF in the core using `rotamer_change` with TRF composition penalty and `backbone_change`. Expect median TRF inclusion rate >10% in ensembles; top designs validated by AF3 should have RMSD <2.0 Å.
3. **Ablation: simplified vs. original syntax**: Repeat experiment 1 with original RosettaScripts syntax (no converter) for penalty generation. Expect action success rate drops to ~70%, cost increases due to retries, and final RMSD slightly worse due to error recovery overhead.

## Open Questions the Paper Calls Out
1. How can the environment design be generalized to support a broader range of RosettaScripts movers and filters without sacrificing the high action-generation success rates achieved with the current simplified syntax?
2. What architectural or training differences cause some LLMs (e.g., Qwen3 Instruct) to perform significantly worse on non-canonical amino acid design tasks, especially on backbone change actions, compared to models like GPT-5?
3. To what extent do Agent Rosetta’s physics-based designs differ structurally and functionally from ML-only methods (e.g., ProteinMPNN) upon experimental validation, given that ESMFold and AF3 are biased toward naturalistic sequences?
4. How does the iterative, multi-turn refinement loop compare to a single-step, fine-tuned human expert protocol when the human is allowed multiple iterations based on intermediate results?
5. Can the framework be extended to multi-component systems (e.g., protein-protein complexes) and larger-scale objectives (e.g., allosteric regulation, de novo active sites) without fundamental changes to the environment or agent reasoning?

## Limitations
- Rosetta configuration details (FastDesign parameters, mover defaults, weight modifications) remain unspecified, hindering exact replication.
- Human baselines are static and may be suboptimally tuned; iterative human protocols could close the performance gap.
- The simplified syntax converter algorithm and LLM inference parameters are not publicly released, introducing variability and potential reproducibility issues.

## Confidence
- **Abstraction of RosettaScripts**: High confidence (simplified syntax boosted success from ~70% to >98%).
- **Iterative refinement with surrogates**: Medium confidence (matches ProteinMPNN on canonical design but NCAA success limited to 14.5%; surrogate bias possible).
- **Two-step reasoning**: High confidence (documentation-driven parameter generation yields >98% valid actions).

## Next Checks
1. **Converter validation**: Test the simplified→RosettaScripts mapping on a comprehensive set of penalty/restriction specifications by comparing against hand-crafted XML.
2. **Expressiveness boundaries**: Stress the agent with tasks requiring multiple NCAs or extensive backbone changes to identify where the current abstraction fails.
3. **Surrogate bias quantification**: Conduct a small-scale study using AF3 as the per-step metric (despite cost) to determine if it improves final design quality over ESMFold.
