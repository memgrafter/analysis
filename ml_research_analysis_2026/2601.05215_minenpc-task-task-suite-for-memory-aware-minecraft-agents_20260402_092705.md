# MineNPC-Task: Task Suite for Memory-Aware Minecraft Agents

## Quick Facts
- **arXiv ID**: 2601.05215
- **Source URL**: https://arxiv.org/abs/2601.05215
- **Reference count**: 40
- **Primary result**: Introduced MineNPC-Task, a benchmark for memory-aware, mixed-initiative LLM agents in Minecraft; GPT-4o evaluation showed a 33% subtask failure rate across 216 subtasks with common failures in code execution and inventory/tool handling.

## Executive Summary
The paper presents MineNPC-Task, a benchmark suite designed to evaluate memory-aware, mixed-initiative LLM agents operating in Minecraft. It tackles fairness and reproducibility by restricting agents to public Mineflayer APIs (bounded-knowledge policy) and judging outcomes solely via validators that consider in-world evidence. The framework enforces plan previews, issues at most one clarification question per subtask to resolve underspecifications, and maintains a lightweight memory of landmarks, preferences, and artifacts with provenance. A user study with eight experienced players across 44 tasks (216 subtasks) using GPT-4o found a 33% subtask failure rate, with code execution faults being the largest category. Participants praised the interaction quality and the mixed-initiative recovery mechanism but requested stronger memory persistence.

## Method Summary
Tasks are derived from expert co-play, normalized into templates with explicit preconditions and machine-checkable validators. Agents must operate under a bounded-knowledge policy, using only public Mineflayer APIs that mimic a player’s perceptual limits. For each user request, the system generates a subtask plan; if any required parameter is missing, a single contextual clarification question is asked, and the user’s answer binds the slot before code generation. The agent then produces and executes Mineflayer JavaScript code, with execution validated against in-world evidence. A typed memory store persists entries (landmarks, preferences, artifacts) tagged with provenance (“seen”, “told”, “inferred”) to support continuity across subtasks.

## Key Results
- Overall subtask failure rate was 33% (71 out of 216 subtasks).
- Leading failure causes: code execution faults (24/71), inventory/tool issues (10/71), referencing errors (6/71), navigation failures (5/71).
- Participants rated interaction quality and usability positively, noting effective mixed-initiative recovery but requesting stronger memory persistence.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim**: The single‑turn targeted clarification mechanism reduces ambiguity in underspecified user requests, enabling more accurate task execution.
- **Mechanism**: When the planner generates a subtask, any missing required parameter (slot) triggers exactly one contextual question. The user’s answer updates the plan and is written to memory with provenance (“told”). This binds the slot before code generation.
- **Core assumption**: Users can correctly interpret and concisely answer disambiguation questions within the game context.
- **Evidence anchors**: 
  - [abstract]: “plan previews, single‑turn clarifications, execution via Mineflayer”.
  - [section 4]: Detailed description of planning and clarification flow (Fig. 5, prompting listings).
  - [corpus] Weak: Neighboring papers (e.g., CrafterDojo, Ghost in the Minecraft) do not focus on mixed‑initiative clarification design; direct comparative evidence is absent.
- **Break condition**: If the user’s answer is misinterpreted, ambiguous, or if multiple missing slots require more than one question, the single‑turn design may propagate errors or stall.

### Mechanism 2
- **Claim**: Enforcing a bounded‑knowledge policy (public Mineflayer APIs only, no privileged world introspection) ensures fair, reproducible evaluation across LLM agents.
- **Mechanism**: The harness disallows admin commands, global map/seed queries, and scans beyond loaded chunks. Validators judge outcomes solely from in‑world evidence (inventory deltas, nearby blocks/entities, recent chat). This mimics a player’s perceptual limits.
- **Core assumption**: The public API provides sufficient affordances for the benchmark’s task distribution.
- **Evidence anchors**: 
  - [abstract]: “bounded‑knowledge policy restricting agents to public Mineflayer APIs”.
  - [section 3]: “perception and action are constrained to public, in‑game interfaces… A bounded‑knowledge policy forbids privileged capabilities”.
  - [corpus] Weak: Corpus contains evaluation harnesses (e.g., VeRO) but none explicitly adopt an identical bounded‑knowledge constraint; evidence is internal to the paper.
- **Break condition**: If a task implicitly relies on hidden state (e.g., locating a distant landmark without line‑of‑sight), the policy forces agents to fail due to perceptual limits, not capability.

### Mechanism 3
- **Claim**: Lightweight memory with provenance (landmarks, preferences, artifacts) supports context reuse across subtasks, reducing repeated clarifications and improving continuity.
- **Mechanism**: A typed store persists entries with sources (“seen”, “told”, “inferred”). Clarification answers become scoped preferences retrievable by nearest‑k queries. Memory reads/writes are logged and influence slot binding in subsequent subtasks.
- **Core assumption**: Memory entries remain sufficiently relevant and not stale; retrieval effectively matches current context.
- **Evidence anchors**: 
  - [abstract]: “lightweight memory for landmarks and preferences”.
  - [section 4]: “Memory. A simple typed store persists named landmarks, artifacts, preferences…”.
  - [section 6.2]: Participants noted memory‑based recall as helpful but requested stronger persistence.
  - [corpus] Weak: Neighbors discuss memory‑aware agents (MINDSTORES, MrSteve) but not the specific provenance‑tracking design; claims rest on paper’s user study.
- **Break condition**: Stale or irrelevant memory entries may misguide slot binding; poor retrieval relevance leads to incorrect parameter choices.

## Foundational Learning

- **Concept**: Embodied AI evaluation design  
  **Why needed**: MineNPC‑Task exemplifies evaluation in a simulated world; understanding why they use in‑world evidence and public APIs clarifies the benchmark’s fairness goals.  
  **Quick check**: What are the risks of evaluating an embodied agent with privileged state access, and how does MineNPC‑Task mitigate them?

- **Concept**: Mixed‑initiative human‑agent interaction  
  **Why needed**: The framework hinges on the agent asking clarifying questions. Recognizing when and how initiative shifts is key to interpreting the results.  
  **Quick check**: In a mixed‑initiative system, who decides when to ask a clarification, and what triggers that decision?

- **Concept**: Bounded rationality in agent constraints  
  **Why needed**: The bounded‑knowledge policy is a deliberate constraint; understanding bounded rationality explains why such limits improve reproducibility.  
  **Quick check**: How does restricting an agent’s perception and action space to “public” interfaces change the interpretation of its performance?

## Architecture Onboarding

**Component map**:  
User Interface (chat + spectator view) → Intent Router (classifies intent) → Task Planner (generates subtasks, reads Memory) → Plan Preview → (if missing slots) Clarification Module → Memory (store answer, provenance) → Code Generator (produces Mineflayer JS) → Code Reviewer (API/guard checks) → Executor (runs code, streams toasts) → State Snapshot (captures bot state) → Validator (checks criteria) → Memory (post‑task update) → Task Feedback (to UI).  
Memory is also queried by Task Planner during subsequent subtask generation.

**Critical path**:  
User request → routing → plan preview → conditional clarification → code generation → review → execution → state capture → validation → feedback. On failure, bounded repair prompts user to choose retry/backtrack; on success, advance to next subtask. Memory writes occur after clarifications and after task completion; reads occur during planning.

**Design tradeoffs**:  
- Single‑turn clarification vs multi‑turn: reduces interaction overhead but may not disambiguate complex slots.  
- Bounded knowledge vs completeness: ensures fair comparison but may render some tasks infeasible.  
- Validator pass/fail vs partial credit: simplifies reproducible scoring but obscures partial progress.  
- Lightweight memory vs full episodic recall: efficient but risks staleness; provenance helps trace origin.

**Failure signatures** (observed failure counts out of 71 subtask failures):  
- Code execution faults (24)
- Inventory/tool issues (10)
- Referencing failures (6)
- Navigation failures (5)
- Context misunderstandings (7)

**First 3 experiments** for a new engineer:  
1. **Baseline replication**: Run GPT‑4o on the full 44‑task suite to reproduce the ~33% subtask failure rate and confirm validator‑backed outcomes.  
2. **Clarification probe**: Craft tasks with an intentionally underspecified slot (e.g., “get a pickaxe”) and verify the agent emits exactly one targeted question, binds the parameter correctly, and records the answer to memory.  
3. **Memory continuity test**: Execute two sequential tasks where the second refers to a location or preference established in the first (e.g., “remember this as X”, then later “go to X”). Check that the agent retrieves the memory without asking again, and note any stale‑memory failures.

## Limitations
- Generalizability limited by small user study (8 players, 44 tasks).
- Bounded‑knowledge policy may force failures on tasks requiring privileged perception.
- Memory design’s provenance tracking and retrieval relevance lack comparative validation; participants requested stronger persistence.

## Confidence
- Single‑turn clarification effectiveness: **Medium**  
- Bounded‑knowledge fairness: **High**  
- Lightweight memory utility: **Medium**

## Next Checks
1. Scale evaluation: Run GPT‑4o and 2–3 other LLMs on full suite to confirm failure distribution and assess generalizability.
2. Clarification stress test: Craft tasks with multi‑slot ambiguity; measure if single‑turn clarification binds parameters correctly vs. multi‑turn alternatives.
3. Memory continuity probe: Execute 5+ sequential tasks referencing prior landmarks/preferences; log memory hits/misses and staleness‑induced failures.
