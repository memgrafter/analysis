# FinToolSyn: A forward synthesis Framework for Financial Tool-Use Dialogue Data with Dynamic Tool Retrieval

## Quick Facts
- **arXiv ID**: 2603.24051
- **Source URL**: https://arxiv.org/abs/2603.24051
- **Reference count**: 40
- **Primary result**: FinTool-Qwen3-14B achieves a 21.06% improvement on FinToolBench while maintaining general reasoning capabilities, surpassing larger models like GPT-4o in complex multi-turn executions.

## Executive Summary
FinToolSyn presents a forward synthesis paradigm for generating financial tool-use dialogues, countering the "artificial explicitness" of traditional reverse synthesis. By grounding query generation in diverse user personas and real-time financial corpus, the framework produces natural, event-driven instructions. These are decomposed into a vast library of 43,066 atomic tools, each adhering to strict schemas. A multi-agent simulation with globally-controlled dynamic retrieval and closed-loop supervision produces 148,984 dialogues featuring noisy candidate sets and plan adaptations. Fine-tuning on this data yields significant gains: FinTool-Qwen3-14B improves by 21.06% on the new FinToolBench and demonstrates superior robustness in multi-turn serial tool executions, even outperforming GPT-4o while preserving performance on general reasoning benchmarks.

## Method Summary
The synthesis pipeline consists of three stages. First, **persona-grounded instruction generation** infers user profiles from raw queries and combines them with financial news and earnings reports to create seed instructions that capture realistic information asymmetry. Second, **demand-driven atomic tool synthesis** decomposes each seed instruction into fine-grained subtasks via deep logical inference, maps each to an atomic tool with a standardized MCP schema, and applies dual-layer verification (LLM and rule-based) to ensure correctness and atomicity, resulting in a modular tool library of 43,066 tools. Third, **multi-agent dialogue generation** employs a global agent to create an initial dialogue plan and oversee a User, Assistant, and Tool agent interacting under dynamic retrieval. At each turn, the assistant selects tools from a noisy candidate set (static, vector, or graph-enhanced), and the global agent validates actions and triggers re-planning on conflicts, ensuring logical consistency. The final corpus of 148,984 dialogues undergoes quality filtering before use for fine-tuning.

## Key Results
- Built a comprehensive library of **43,066 atomic financial tools** covering diverse operations.
- Synthesized **148,984 dialogues** (1.3M turns) with noisy candidate retrieval and closed-loop supervision.
- Models fine-tuned on this data (**FinTool-Qwen3-14B**) achieved a **21.06% improvement** on the FinToolBench benchmark, surpassing GPT-4o in multi-turn serial execution while retaining general reasoning abilities.

## Why This Works (Mechanism)
### Mechanism 1: Persona-Grounded Forward Synthesis Generates Natural Queries
- **Claim:** Starting from user personas and financial context generates natural, event-driven queries that reflect real-world information asymmetry, avoiding the "artificial explicitness" of reverse synthesis.
- **Mechanism:** The system first infers diverse user profiles (demographics, financial literacy, risk appetite) from raw queries and then synthesizes seed instructions by combining a persona with current financial corpus (news/earnings reports). This decouples intent from specific tools, ensuring queries are grounded in realistic events and user expertise.
- **Core assumption:** Real financial inquiries are triggered by external events and vary by user expertise; synthetic data must preserve this implicit, ambiguous nature to train models that handle realistic requests.
- **Evidence anchors:**
  - [Abstract] "forward synthesis paradigm... effectively overcoming the 'artificial explicitness' bias in traditional 'reverse synthesis'."
  - [Section 3.1] Details persona inference and corpus-based instruction synthesis: "inew ∼ PM(·|P, C)" ensures professional grounding and cognitive alignment.
  - [Corpus] Corpus evidence is indirect; neighboring papers (e.g., FinToolBench) highlight the need for realistic tool-use data but do not directly validate forward synthesis.
- **Break condition:** If persona diversity is limited or corpus context is irrelevant, synthesized instructions may still exhibit explicitness or fail to match event-driven patterns.

### Mechanism 2: Demand-Driven Atomic Tool Library Enables Fine-Grained Composition
- **Claim:** Decomposing complex financial tasks into atomic, single-responsibility tools yields a modular ecosystem (43,066 tools) that supports precise tool selection and composition for diverse financial operations.
- **Mechanism:** Given seed instructions, an LLM performs deep logical inference to derive information interaction chains, then maps each sub-task to an atomic tool via atomic mapping. Each tool adheres to strict schemas (MCP) and undergoes dual-layer verification (LLM + rule-based). This demand-driven approach (from user intent) rather than crawling existing APIs ensures tools match latent functional requirements.
- **Core assumption:** Real-world tool use requires modular, reusable components; monolithic "God APIs" hinder learning and reusability.
- **Evidence anchors:**
  - [Abstract] "demand-driven atomic tool synthesis" and "43,066 tools".
  - [Section 3.2] Details the three-phase decomposition and verification: "Deep Logical Inference", "Atomic Mapping", "Standardized Tool Generation".
  - [Corpus] The large tool count (43k) far exceeds prior works (e.g., ToolLLaMA's 16k) [Table 1], indicating a scale that supports diverse financial tasks.
- **Break condition:** If decomposition produces tools that are too fine-grained or verification is lax, the library may contain redundant or incorrect tools, reducing utility.

### Mechanism 3: Globally-Controlled Dynamic Retrieval with Closed-Loop Supervision Builds Robustness
- **Claim:** Simulating noisy candidate retrieval (static, vector, graph-enhanced) under global agent supervision and dialogue plan adaptation trains models to handle real-world tool-space navigation and error recovery.
- **Mechanism:** A global agent generates an initial dialogue plan and oversees a multi-agent simulation (User, Assistant, Tool). At each turn, the assistant selects tools from a dynamically retrieved candidate set (V_cand). The global agent validates actions against the evolving plan and context, triggering re-planning on conflicts. This closed-loop supervision and noisy retrieval mimic real-world dynamics.
- **Core assumption:** Real deployment involves large, noisy tool spaces; models must learn to filter distractors and maintain logical chains despite imperfect retrieval.
- **Evidence anchors:**
  - [Abstract] "globally-controlled dynamic retrieval" and "noisy candidate retrieval".
  - [Section 3.3] Describes the multi-agent framework, dialogue plan generation/updating, and three retrieval configurations.
  - [Table 6] Ablation: Dynamic retrieval improves overall performance (55.86 vs 54.93 for static) and particularly in complex serial tasks (55.43 vs 54.02), confirming robustness gains.
  - [Corpus] Neighbors (e.g., ToolRerank, Retrieval models aren't tool-savvy) highlight noisy retrieval as a key challenge, supporting the mechanism's relevance.
- **Break condition:** If the global agent's supervision is too rigid, it may constrain natural dialogue; if retrieval noise is excessive, learning may suffer. Balance is critical.

## Architecture Onboarding
### Component Map
Raw financial queries -> Persona Generator -> User Personas -> Instruction Synthesizer -> Seed Instructions (I_seed) -> Tool Decomposer -> Atomic Tool Library (V) with vector index and dependency graph. For each seed instruction, Global Agent generates a Dialogue Plan -> Multi-agent interaction (User, Assistant, Tool) with Dynamic Retriever -> Dialogue turns. Global Agent validates and updates plan; retry on conflict. Filtered dialogues stored in corpus.

### Critical Path
1. Raw financial queries → Persona inference → User personas.
2. Personas + financial corpus → Seed instructions (I_seed).
3. I_seed → Task decomposition → Atomic tools → Tool library (V) with index and graph.
4. For each I_seed: Global agent generates dialogue plan → Multi-agent interaction with dynamic retrieval → Dialogue turns.
5. Dialogues filtered/discarded based on quality; final corpus of 148,984 dialogues.

### Design Tradeoffs
- *Forward synthesis complexity* vs. *query naturalness*: More sophisticated persona and context modeling but avoids artificial explicitness.
- *Dynamic retrieval noise* vs. *robustness*: Noisy candidates improve model resilience but increase synthesis difficulty and may cause more failures.
- *Closed-loop supervision* vs. *computational cost*: Continuous validation ensures quality but adds overhead; the paper limits retries (T_max=3) to balance.
- *Atomic tools* vs. *tool space size*: Many small tools enhance modularity but enlarge retrieval space and may require more calls.

### Failure Signatures
- High discard rate (>10%) during synthesis indicates quality issues.
- In dialogues, frequent plan updates by Global Agent may signal instability in user/assistant behavior.
- Low human acceptance rate (<90%) on sampled dialogues suggests unrealistic interactions.
- After fine-tuning, poor performance on FinToolBench, especially in multi-turn serial tasks, indicates failure to capture long-horizon dependencies.

### First 3 Experiments
1. *Persona diversity check*: Sample inferred personas and evaluate coverage of demographics, financial literacy, risk appetite. Aim for varied profiles.
2. *Tool atomicity validation*: Randomly sample tools from the library; verify each adheres to single-responsibility and has correct schema. Check for duplicates.
3. *Mini-dialogue synthesis*: Generate a small batch (e.g., 100 dialogues) with static retrieval; manually inspect for artificial explicitness, logical consistency, and naturalness of user queries.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Can FinToolSyn's forward synthesis and dynamic retrieval pipeline be effectively adapted to other high-stakes, tool-intensive verticals (e.g., medicine, law) without prohibitive expert-driven re-calibration of the taxonomies and dependency graphs?
- **Basis in paper:** The "Limitations" section states that reliance on domain-specific tool taxonomies and dependency graphs means adapting to fields like medicine or law would require non-trivial expert re-calibration. This is presented as a key scalability barrier.
- **Why unresolved:** The paper demonstrates success in finance but does not provide a methodology or evidence for porting the framework's core components (persona grounding, atomic tool synthesis, graph construction) to a new domain with different regulatory, terminological, and workflow structures.
- **What evidence would resolve it:** A replication study applying the full FinToolSyn pipeline to a new domain (e.g., clinical decision support tools) with a detailed assessment of the manual effort required for taxonomy/graph construction versus the quality/realism of the resulting synthetic dialogues.

### Open Question 2
- **Question:** To what extent does the "pro-tool bias" (over-triggering tool calls in non-tool scenarios) observed in FinTool-Tuned models stem from the synthetic data distribution versus the inherent characteristics of the base model architecture?
- **Basis in paper:** Section 5.2's fine-grained error analysis notes FinTool-Qwen3-14B has a higher overall error rate in non-tool scenarios, driven by "Invalid Invocation" (56.8% FC mode), attributing it to a "pro-tool bias induced by training on a corpus rich in tool-use dialogues."
- **Why unresolved:** The paper identifies the symptom and its likely cause (training data distribution) but does not disentangle it from potential base model tendencies. It is unclear if a model pre-trained with different reasoning priors would exhibit the same bias when fine-tuned on the same data, or if data curation (e.g., balancing non-tool scenarios) could fully mitigate it.
- **What evidence would resolve it:** An ablation study holding the base model constant (e.g., Qwen3-14B) and varying the ratio of tool-call to non-tool-call dialogues during fine-tuning, measuring the resulting trade-off between tool-call precision and non-tool rejection/CI accuracy.

### Open Question 3
- **Question:** How closely do the stochastic tool outputs and simulated "plan-fact conflicts" in the FinToolSyn environment mirror the statistical properties and failure modes (e.g., latency spikes, partial data returns, cascading errors) of live, production-grade financial APIs?
- **Basis in paper:** The "Limitations" section acknowledges "a subtle gap remains between our synthetic simulation and the extreme corner cases or real-time latency fluctuations inherent in production-grade financial APIs."
- **Why unresolved:** The paper's "Tool Agent" generates stochastic outputs to reflect "real-world API instability," but the nature of this stochasticity (e.g., failure rates, error types, latency distributions) is not parameterized or validated against real API logs. The dynamic retrieval uses noisy candidate sets, but the tool execution layer's realism is assumed.
- **What evidence would resolve it:** A validation study comparing the distribution of tool execution outcomes (success rates, error codes, response times) in FinToolSyn-synthesized dialogues against a large corpus of real-world API call logs from a financial data provider. The synthetic error model could be tuned to match this empirical distribution.

### Open Question 4
- **Question:** Does the closed-loop, globally-controlled supervision in FinToolSyn (with its adversarial discriminator and dynamic re-planning) lead to more consistent and diverse dialogue plans compared to open-loop generation, and is this consistency correlated with downstream model performance on complex, unseen multi-turn tasks?
- **Basis in paper:** Section 3.3 introduces the "globally controlled framework" and "closed-loop supervised trajectory synthesis" as key innovations to prevent error accumulation and support non-linear flows. Table 6's ablation shows dynamic retrieval (part of this loop) improves overall performance.
- **Why unresolved:** While the paper claims the closed-loop mechanism prevents error accumulation, it does not provide a direct metric for "plan fidelity" or "dialogue coherence diversity." The link between the synthesis supervisory mechanism and the observed robustness in multi-turn serial executions (Section 5.1) is correlational, not causal.
- **What evidence would resolve it:** An analysis quantifying the stability of the initial dialogue plan throughout the generation process (e.g., plan edit distance) for closed-loop vs. open-loop baselines. Then, a controlled experiment where models are trained on data from each paradigm and evaluated on perturbed or out-of-distribution multi-turn benchmarks to see if plan stability in training data predicts generalization robustness.

### Open Question 5
- **Question:** Are the domain-specific evaluation metrics (Key Digit Accuracy, Invocation Timing Accuracy) and the CB-HWS circuit-breaker mechanism generalizable principles for tool-use evaluation in other precision-critical domains (e.g., healthcare dosing, legal citation), or are they overly tailored to financial context?
- **Basis in paper:** Section 4.2 introduces CB-HWS, KDA, and ITA specifically for "high-stakes financial settings" and "strict pre-execution compliance." Table 4 contrasts FinToolBench with general benchmarks, highlighting its finance-specific metrics.
- **Why unresolved:** The metrics are designed with financial domain constraints (e.g., zero-tolerance for digit errors, strict business workflow ordering). Their applicability elsewhere is not explored. For instance, KDA's "critical digit" concept may map to drug dosages in medicine, but ITA's "logical business workflow" may not have a direct analogue.
- **What evidence would resolve it:** A conceptual analysis mapping the error types penalized by CB-HWS/KDA/ITA (hallucination, schema violation, timing/order errors, precision failures) to error taxonomies in another precision domain (e.g., clinical trial query tools). A pilot study could adapt the scoring mechanism to that domain and test its discriminative power on human-annotated errors.

## Limitations
- **Undisclosed prompts/hyperparameters**: Core components (persona inference, tool verification, global planning) lack explicit details, hindering faithful replication.
- **Small benchmark size**: FinToolBench contains only 843 samples, raising concerns about statistical reliability and domain coverage.
- **Tool library granularity**: The massive 43k-tool library may contain redundancy; its real-world usability and efficiency remain unexamined.

## Confidence
- **Forward synthesis reduces artificial explicitness**: Medium (human acceptance >90% but no direct reverse-synthesis comparison)
- **Atomic tool library enables composition**: Medium (scale documented but composition efficacy not isolated)
- **Dynamic retrieval builds robustness**: High (Table 6 shows significant improvements in overall and serial task performance)
