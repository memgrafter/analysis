# Enhancing Web Agents with a Hierarchical Memory Tree

## Quick Facts
- arXiv ID: 2603.07024  
- Source URL: https://arxiv.org/abs/2603.07024  
- Reference count: 40  
- Primary result: Hierarchical Memory Tree (HMT) significantly improves cross-website Step Success Rate (39.7% vs. 33.7% for prior methods) and Task Success Rate on WebArena (38.7%).

## Executive Summary
Existing retrieval-based web agents fail to generalize to unseen websites because their flat memory structures mix high-level task logic with site-specific action details—a problem termed "intention-execution entanglement." This paper proposes the Hierarchical Memory Tree (HMT), a structured memory framework that decouples logical planning from execution through a three-level hierarchy: standardized task intents, reusable semantic subgoals with observable pre/post-conditions, and abstract action patterns paired with transferable element descriptions. During inference, a Planner selects the appropriate subgoal by matching the current state to subgoal conditions, and an Actor grounds actions via semantic matching to UI elements. Evaluations on Mind2Web (offline) and WebArena (online interactive) show that HMT substantially boosts cross-website performance and efficiency, with a 72.7% reduction in context tokens and notable gains in logic-heavy domains.

## Method Summary
The method consists of two phases: memory construction and stage-aware inference. In memory construction, successful interaction trajectories are processed via an LLM-based pipeline to build a Hierarchical Memory Tree. Instructions are normalized to standardized intents and constraints. Trajectories are segmented into semantic subgoals, each annotated with observable pre-conditions and post-conditions. Actions are abstracted into patterns linked to transferable semantic element descriptions (e.g., role, label, positional context), discarding raw element identifiers. During inference, hierarchical retrieval first fetches relevant task nodes and subgoal candidates. The Planner then selects a subgoal by comparing the current abstracted state to subgoal conditions. Finally, the Actor retrieves exemplar steps for the chosen subgoal and grounds the action by matching semantic descriptions to candidate UI elements in the current observation.

## Key Results
- Mind2Web cross-website split: HMT achieves 39.7% Step Success Rate, outperforming AWM offline (33.7%) and flat retrieval (33.2%).
- WebArena: Highest total Task Success Rate (38.7%), with specific gains of +5.8% in GitLab and +5.0% in CMS domains.
- Efficiency: 72.7% reduction in context tokens and lower latency compared to flat retrieval.

## Why This Works (Mechanism)
Flat memory structures cause "intention-execution entanglement," where transferable task logic is polluted by site-specific action details, leading to irrelevant retrievals on new websites. HMT resolves this by cleanly separating concerns across three hierarchy levels. The intent level captures reusable task logic independent of any site. The stage level defines semantic subgoals with observable state conditions, enabling modular planning and progress tracking. The action level pairs abstract patterns with semantic element descriptions, allowing grounding without relying on brittle raw IDs. During inference, the Planner focuses on subgoal selection via condition matching, while the Actor handles semantic grounding. This decoupling ensures that only transferable knowledge is reused, dramatically improving cross-website generalization and robustness.

## Foundational Learning
1. **Intention-Execution Entanglement**: Mixing high-level task goals with low-level, site-specific action details in memory.  
   *Why needed*: Causes agents to retrieve irrelevant steps when encountering new websites.  
   *Quick check*: Does the memory structure separate "what to achieve" from "how to click specific elements"?

2. **Hierarchical Memory Tree**: A three-level tree (Intent, Stage, Action) organizing knowledge from general to specific.  
   *Why needed*: Enables selective retrieval and recombination of transferable components.  
   *Quick check*: Can subgoals from different websites be combined to form new workflows?

3. **Pre/Post-Conditions**: Observable state predicates (e.g., "navigation complete") attached to subgoals.  
   *Why needed*: Provides a verifiable signal for the Planner to track progress without site-specific assumptions.  
   *Quick check*: Are conditions defined in terms of generic DOM features (e.g., element visibility) rather than IDs?

4. **Semantic Element Description**: Abstract UI element descriptors using roles, labels, positions, etc.  
   *Why needed*: Allows action grounding across websites with different underlying identifiers.  
   *Quick check*: Can the description match elements in different layouts (e.g., a "submit" button in a header vs. a footer)?

5. **Stage-Aware Inference**: Two-component decision process (Planner + Actor) respecting the memory hierarchy.  
   *Why needed*: Prevents flat retrieval from collapsing the hierarchy and reintroducing entanglement.  
   *Quick check*: Does the system first commit to a subgoal before retrieving concrete action steps?

6. **Cross-Website Generalization**: Ability to apply learned skills to unseen websites.  
   *Why needed*: Essential for real-world deployment where agents encounter novel sites.  
   *Quick check*: Does performance drop significantly when moving from seen to unseen websites in ablation studies?

## Architecture Onboarding
- **Component map**: Memory Tree -> Planner -> Actor  
- **Critical path**: (1) Hierarchical retrieval fetches task and subgoal candidates; (2) Planner selects subgoal by matching current abstract state to subgoal conditions; (3) Actor retrieves exemplar steps for that subgoal and grounds actions via semantic matching to UI elements.  
- **Design tradeoffs**: Hierarchy adds complexity but enables generalization; semantic matching improves transfer but may cause ambiguity; LLM-based components offer flexibility but introduce non-determinism and cost.  
- **Failure signatures**: Ambiguous grounding (multiple elements match descriptor); state verification error (Planner's conditions too rigid for SPA updates); workflow mismatch (flat retrieval pulls temporally misaligned steps); raw identifier failure (cross-website grounding collapses).  
- **First experiments**:  
  1. Reproduce full pipeline on Mind2Web cross-split using reported hyperparameters; target StepSR within ±1% of 39.7%.  
  2. Stress-test Planner on single-page applications by introducing alternative state signals (URL hash, DOM mutation events); measure subgoal accuracy and TaskSR.  
  3. Conduct zero-shot evaluation on five unseen commercial websites (Amazon, Airbnb, Uber, Spotify, Walmart); compare HMT vs. flat retrieval on StepSR/TaskSR and analyze failure modes.

## Limitations
- Reliance on LLM outputs for memory construction introduces non-determinism and potential dataset bias.
- Evaluation limited to Mind2Web and WebArena; generalizability to highly dynamic SPAs and diverse commercial sites remains unproven.
- Planner's condition-matching may fail on unconventional state changes like modal popups or client-side routing that do not alter typical observables.

## Confidence
- Cross-website gain: **High** (consistent significant improvements across datasets and ablations).  
- Hierarchy decoupling: **Medium** (strong ablation evidence but implementation details limit causal clarity).  
- Efficiency gains: **Medium-High** (clear token and latency reductions reported).  
- Raw ID failure: **High** (ablation shows catastrophic drop to 12.4% StepSR in cross-website settings).
