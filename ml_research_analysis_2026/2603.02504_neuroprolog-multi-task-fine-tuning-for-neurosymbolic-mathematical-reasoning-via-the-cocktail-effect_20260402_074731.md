# NeuroProlog: Multi-Task Fine-Tuning for Neurosymbolic Mathematical Reasoning via the Cocktail Effect

## Quick Facts
- **arXiv ID:** 2603.02504  
- **Source URL:** https://arxiv.org/abs/2603.02504  
- **Reference count:** 40  
- **Primary result:** Cocktail training yields +3.43% to +5.54% accuracy gains on GSM8K across 3B–32B models, with GPT‑OSS‑20B reaching 88.3% accuracy.

## Executive Summary
NeuroProlog improves the reliability of large language models in mathematical reasoning by forcing them to generate verifiable, executable Prolog programs instead of free‑form text. It employs a multi‑task “cocktail” fine‑-tuning strategy that jointly optimizes formula‑to‑rule translation, natural‑language‑to‑program synthesis, and program‑answer alignment within a unified Prolog output space. During inference, an execution‑guided decoding pipeline uses a fine‑grained error taxonomy to iteratively repair faulty programs. Across model scales from 3B to 32B parameters, NeuroProlog achieves statistically significant accuracy improvements on GSM8K, with the 20B‑parameter variant outperforming much larger program‑synthesis systems. The approach reveals a capacity threshold near 10B parameters beyond which symbolic reasoning becomes both syntactically and semantically robust.

## Method Summary
The framework is built on two datasets: a Knowledge Base (KB) of 200 human‑curated mathematical formulas translated into type‑safe, commented Prolog predicates, and a Problem‑Solving set (SOLVE) of 7,786 word problems (310 curated + 7,476 GSM8K‑Prolog) paired with executable Prolog programs. Models are fine‑tuned with LoRA using a cocktail loss \(L = \lambda_{kb} L_{KB} + \lambda_{solve} L_{SOLVE}\), where both terms are token‑level cross‑entropy over the same Prolog output syntax. During inference, the model generates an initial program, executes it via SWI‑Prolog, classifies any error into a five‑class taxonomy (SYNTAX, TYPE_ERROR, DOMAIN_ERROR, INSTANTIATION, WRONG_ANSWER), and constructs a targeted repair prompt; this loop repeats up to \(k = 3\) iterations. Evaluation on the GSM8K test set reports accuracy (final numeric answer match), executability, first‑try success, correction rate, and average iterations.

## Key Results
- Cocktail fine‑-tuning delivers statistically significant accuracy gains of +3.43% to +5.54% over single‑task baselines across 3B–32B models; GPT‑OSS‑20B attains 88.3% on GSM8K, surpassing ToRA‑Code‑34B (80.7%) with 3.5× fewer parameters.
- Execution‑guided decoding with the error taxonomy enables self‑debugging; at 32B scale, cocktail training shifts unfixable TYPE_ERRORs (12% repair) to fixable DOMAIN_ERRORs (96% repair), achieving a 92.7% overall correction rate.
- A scale‑dependent failure mode emerges: below ~10B parameters (e.g., Qwen3‑8B), cocktail training boosts first‑try success but catastrophically reduces correction capability, indicating a threshold for type‑safe symbolic reasoning.

## Why This Works (Mechanism)

### Mechanism 1: Declarative Knowledge Grounding Enables Compositional Reuse
**Claim:** Joint training on formula‑to‑Prolog translation (KB) provides reusable symbolic building blocks that improve word‑problem‑to‑program synthesis (SOLVE) through positive transfer.  
**Mechanism:** The KB encodes mathematical concepts (e.g., `factorial/2`, `combination_count/3`) as type‑safe, commented Prolog predicates. During cocktail training, the model observes these declarative definitions *and* their procedural application in SOLVE examples, creating an associative link between abstract formulas and executable implementations. This allows the model to compose SOLVE programs by reusing and adapting KB predicate patterns rather than generating ad‑hoc logic.  
**Core assumption:** The model’s internal representation can align the semantics of natural‑language descriptions (KB input) with Prolog code structure, and this alignment generalizes to novel problem contexts (SOLVE input).  
**Evidence anchors:**  
- Abstract: “Joint supervision enables positive transfer, where symbolic grounding in formula translation directly improves compositional reasoning capabilities.”  
- Sec 3.2: “KB predicates become reusable building blocks for SOLVE programs”; “Procedural Demonstrations reuse predicate patterns from the KB.”  
- Sec 4.4: Qwen‑32B cocktail reduces final errors from 39 to 9, with KB shifting error distribution from unfixable `TYPE_ERROR` to fixable `DOMAIN_ERROR`.  
- Corpus: Related cocktail effect papers exist, but evidence for this specific declarative‑procedural transfer is drawn from internal ablation and error analysis.  
**Break condition:** If the KB lacks predicates relevant to the SOLVE distribution (e.g., missing `permutation_count/3`), transfer diminishes. Ablation in Table 3 shows KB benefit varies by model scale (+0.38% to +5.24%), indicating dependence on capacity to internalize symbolic patterns.

### Mechanism 2: Shared Symbolic Representation Space Induces Cross‑Task Synergy
**Claim:** Training KB and SOLVE tasks within a unified Prolog generation framework creates a shared latent space where improvements in one task’s objective (e.g., syntax correctness from KB) benefit the other (e.g., semantic correctness in SOLVE).  
**Mechanism:** Both tasks are formulated as causal language modeling over Prolog code (Eqs. 2‑3). The model must learn to generate syntactically valid, type‑constrained Prolog for both declarative definitions (KB) and imperative problem‑solving scripts (SOLVE). This forces internalization of Prolog’s grammar, CLP(Q) constraint syntax, and type discipline in a way that single‑task SOLVE‑only training may not, as SOLVE alone provides weaker supervision on pure symbolic structure.  
**Core assumption:** The cognitive load of learning Prolog’s formal syntax and semantics is distributed across two complementary task distributions: KB provides clean, self‑contained concept definitions; SOLVE provides contextual, compositional usage. The combined objective yields a more robust internal model of the symbolic language.  
**Evidence anchors:**  
- Abstract: “Multi‑task Cocktail training strategy that jointly optimizes three synergistic objectives in a unified symbolic representation space.”  
- Sec 3.2: “Unified Type System: Joint training on Prolog syntax and CLP(Q) constraints induces shared type‑safe representations.”  
- Sec 4.2: Cocktail FT outperforms Prolog FT for 3/4 models (e.g., +2.22% for GPT‑OSS‑20B), despite using the same SOLVE data plus additional KB entries.  
- Sec B.2: Cocktail training achieves lower final validation loss than Prolog‑only training across all models, indicating better fit to the held‑out SOLVE validation set.  
**Break condition:** If the two tasks are too dissimilar in symbolic patterns (e.g., KB uses pure logic while SOLVE uses heavy arithmetic), the shared space may cause interference. The paper’s KB and SOLVE both use similar Prolog/CLP(Q) patterns, enabling synergy.

### Mechanism 3: Execution‑Guided Decoding with Fine‑Grained Error Feedback Enables Zero‑Shot Self‑Debugging
**Claim:** Leveraging the Prolog interpreter’s deterministic error taxonomy during inference provides structured, actionable feedback that allows the model to iteratively repair its own programs without dedicated correction training.  
**Mechanism:** The pipeline executes the generated program, classifies the failure (`SYNTAX`, `TYPE_ERROR`, `DOMAIN_ERROR`, etc.), and constructs a targeted repair prompt containing the error type, line number, and specific fix guidance (from Table 9). The same model weights are used for repair, forcing it to interpret the diagnostic and adjust its code generation accordingly. This turns the interpreter into a “teacher” providing granular, principled feedback on logical flaws.  
**Core assumption:** The model, having been trained on syntactically and semantically correct Prolog, possesses latent knowledge of correct patterns and can map an error diagnosis to the required correction when prompted explicitly. The taxonomy must be sufficiently expressive to cover common failure modes.  
**Evidence anchors:**  
- Abstract: “Execution‑guided decoding pipeline with fine‑grained error taxonomy that enables iterative program repair and quantifies model self‑debugging capacity.”  
- Sec 3.3: “Zero‑shot debugging: identical weights for generation and repair demonstrate internalized semantics without correction‑specific training.”  
- Sec 4.3: Qwen‑32B cocktail achieves 92.7% correction rate, shifting `TYPE_ERROR` (12% fixable) to `DOMAIN_ERROR` (96% fixable). This demonstrates the repair mechanism is effective *because* the error types changed to more correctable ones.  
- Sec 4.4: Cocktail FT reduces Qwen‑32B’s correction penalty from −13.6% to −5.2% (Table 4), showing synergy between training (KB‑induced error shift) and inference (taxonomy‑guided repair).  
**Break condition:** If the model’s initial generation is too semantically flawed (e.g., at 3B scale, `Corr. %` is 8.9) or if the error type is fundamentally un‑actionable (e.g., `TYPE_ERROR` at 8B has only 5% fixability), the repair loop fails. Effectiveness is gated by model capacity and the quality of the initial error classification.

## Foundational Learning

### Declarative vs. Imperative Programming
**Why needed here:** NeuroProlog uses Prolog, a *declarative* logic language where programs specify *what* is true (relations, constraints) rather than *how* to compute (step‑by‑step assignments). This contrasts with the imperative Python used in PAL/PoT. Understanding this shift is key to grasping why Prolog enables formal verification and why type errors (e.g., mixing atoms and numbers) are semantic, not just syntactic.  
**Quick check:** If a Prolog predicate `factorial(0, 1).` is declarative, what does that statement assert about the relationship between `0` and `1`, and how does that differ from an imperative `result = 1`?

### Constraint Logic Programming (CLP(Q))
**Why needed here:** The paper consistently uses `library(clpq)` and `{ }` constraints instead of Prolog’s `is/2` arithmetic. CLP(Q) treats equations as constraints over rational numbers, allowing the interpreter to propagate and check consistency *before* solving. This is core to the “formal verification guarantees” claim. Misusing `is/2` (eager evaluation) vs. `{X = A+B}` (deferred constraint) is a primary source of `TYPE_ERROR`.  
**Quick check:** Why might `{X = 10 / 0}` throw a `DOMAIN_ERROR` during constraint posting, whereas `Y is 10 / 0` might throw a different error or even succeed in some Prolog systems?

### Multi‑Task Learning & The Cocktail Effect
**Why needed here:** The paper’s central hypothesis is that mixing *reasoning modalities* (declarative KB, procedural SOLVE) in one model yields synergistic gains. This isn’t just mixed data; it’s mixing *types of supervision* on the same output space (Prolog). The “cocktail effect” implies complementary tasks improve each other, which is tested via ablation (Table 3) and error shift analysis (Fig 5, 9).  
**Quick check:** If you only trained on the 310 SOLVE examples, what specific knowledge about Prolog’s type system might the model *miss* that the 200 KB entries provide?

## Architecture Onboarding

### Component Map
[Dataset Layer (KB: 200 knowledge definitions, SOLVE: 7,786 problem‑program pairs)] -> [Training Layer (LoRA fine‑tuning with cocktail loss \(L = \lambda_{kb} L_{KB} + \lambda_{solve} L_{SOLVE}\))] -> [Inference Pipeline (Generate \(P_0\) → Execute via SWI‑Prolog → Classify error → Repair prompt → Generate \(P_{i+1}\), up to \(k=3\) iterations)] -> [Evaluation Layer (Accuracy, Executability, First‑Try Success, Correction Rate, Average Iterations)]

### Critical Path
The positive transfer hinges on the **KB→SOLVE** path: KB training must improve the model’s internal Prolog generator such that, when prompted with a word problem (`[SOLVE]`), it more frequently produces programs that are (1) syntactically valid, (2) type‑safe, and (3) semantically aligned. This is measured by improved *First‑Try Success* and reduced error rates in SOLVE, even though KB and SOLVE are separate tasks during training.

### Design Tradeoffs
- **Accuracy vs. Efficiency:** Larger models (32B) achieve high first‑try success (~90%) and use fewer iterations. Smaller models (8B) trade first‑try for more iterations, but correction ultimately fails. The Pipeline Efficiency metric captures this tradeoff; Qwen‑32B Prolog FT is efficiency‑optimal, GPT‑OSS‑20B Cocktail is accuracy‑optimal.  
- **Syntax vs. Semantics:** At 8B scale, cocktail training improves syntax (eliminates `SYNTAX_OPERATOR_EXPECTED`) but introduces `TYPE_ERROR`. This suggests fine‑tuning on symbolic tasks can overfit to surface form if capacity is insufficient to learn deep type constraints.  
- **Generality vs. Brittleness:** Prolog’s verifiability ensures correctness but makes the system brittle to minor formulation errors—a feature for high‑stakes domains but a limitation for fuzzy reasoning.

### Failure Signatures
- **Scale‑dependent error shift:** At ≥32B, errors shift from `TYPE_ERROR` (unfixable) → `DOMAIN_ERROR` (fixable). At 8B, errors shift from `SYNTAX` → `TYPE_ERROR`.  
- **Correction collapse:** For models <10B (Qwen3‑8B, Llama‑3B), fine‑tuning improves first‑try success but catastrophically reduces correction rate, making the pipeline less robust than the base model.  
- **Executability drop:** Llama‑3B Prolog FT causes executability to plummet (−24.41%), indicating the model generates syntactically invalid code more often despite task‑specific supervision.

### First 3 Experiments
1. **Replicate core cocktail effect:** For a given model (e.g., GPT‑OSS‑20B), run the three configurations (Base, Prolog FT, Cocktail FT) on GSM8K with \(k=3\) correction. Verify cocktail FT accuracy > Prolog FT (\(p<0.05\)) and that Cocktail FT has lower validation loss than Prolog FT. This confirms positive transfer.  
2. **Probe error taxonomy dynamics:** For the best performing cocktail model (e.g., Qwen‑32B), run the pipeline with \(k=3\) and log the error type at each iteration. Compute the pre/post error distribution shift; expect `TYPE_ERROR`↓, `DOMAIN_ERROR`↑, and overall error count↓. This validates Mechanism 1 and 3 synergy.  
3. **Test capacity threshold:** Take a model in the ambiguous zone (e.g., Qwen3‑8B). Compare Base vs. Cocktail FT: (a) Does first‑try success increase? (b) Does correction rate decrease? (c) Does final accuracy change significantly? Expect (a) yes, (b) yes, (c) no or negative. This confirms the ~10B parameter threshold for type‑safe symbolic reasoning.

## Limitations
- **Missing training details:** Hyperparameters such as \(\lambda_{kb}\), \(\lambda_{solve}\), curriculum schedule, optimizer, and learning‑rate specifics are not disclosed, hindering exact replication.  
- **Dataset ambiguity:** The exact versions of the KB and SOLVE datasets, preprocessing steps, and splits are unclear; reconstruction may be required.  
- **Brittleness & scope:** Prolog’s strict syntax and type system make the system fragile to minor formulation errors, and evaluation is limited to GSM8K, leaving generalization to other benchmarks unknown.

## Confidence
- **Accuracy gains:** High (consistent +3.43% to +5.54% across four model scales with statistical significance).  
- **Error taxonomy repair:** Medium (repair rates documented but causal link to training not fully isolated).  
- **Capacity threshold near 10B:** Low (based on only four model sizes; requires broader scaling study).

## Next Checks
1. Replicate the cocktail effect on other model families (e.g., Llama‑3, Mistral) to verify generalizability of the >3% accuracy improvement.  
2. Systematically ablate the contribution of the KB task by varying \(\lambda_{kb}\) (0 to 1) and measure the impact on accuracy and error‑distribution shift.  
3. Evaluate the framework on the MATH dataset without further tuning to test transferability beyond GSM8K.
