# Access Controlled Website Interaction for Agentic AI with Delegated Critical Tasks
## Quick Facts
- arXiv ID: 2603.18197
- Source URL: https://arxiv.org/abs/2603.18197
- Reference count: 20
- Primary result: Extends Secure Swarm Toolkit with cryptographic delegation and HMAC-based scope enforcement for agentic AI website access.

## Executive Summary
The paper addresses the challenge of fine-grained access control for agentic AI performing critical delegated tasks on websites. It proposes an extension to the open-source Secure Swarm Toolkit's Auth service, introducing a Delegation target type and ExpectedOwnerGroups to securely issue and manage cryptographic session keys for agents. Website implementations then enforce user-defined access scopes through HMAC-based authentication.

Evaluation demonstrates the system's effectiveness: valid agent operations achieve 100% success in authentication, authorized data access, and session expiration, while invalid or repeated key requests are entirely rejected. Latency measurements average 127–140 seconds for successful access and 98.7 seconds for unauthorized rejections.

## Method Summary
No reproduction notes were provided by the authors. The described method involves enhancing the Secure Swarm Toolkit's Auth service with additional target types and group expectations to manage agent delegations, and implementing HMAC-based scope validation on websites to restrict agent access according to user-defined policies.

## Key Results
- 100% success for valid agent authentication, authorized data access, and session expiration.
- 0% success for invalid or repeated key requests.
- End-to-end latency: 127–140 seconds for successful access, 98.7 seconds for unauthorized rejection.

## Why This Works (Mechanism)
The proposed mechanism extends the Secure Swarm Toolkit's Auth service with a Delegation target type and ExpectedOwnerGroups. When a user delegates a task, the Auth service generates a unique cryptographic session key and binds it to an ExpectedOwnerGroups policy that specifies which agent groups are permitted to use the key. The session key is then provided to the agent (assumed to be over a secure channel). For each request to a protected website, the agent includes the session key and an HMAC (computed over relevant request data) as authentication credentials. The website's enforcement module verifies the HMAC using the shared secret and checks that the requested operation is within the user-defined access scope. This ensures only authorized agents can perform actions within their granted scope, and HMAC provides integrity and authenticity of requests. The security relies on the confidentiality of the session key and the HMAC key, and the system assumes the Auth service is trusted.

## Architecture Onboarding
**Component Map**  
- *User*: Initiates delegation, defines access scope and allowed agent groups.  
- *Auth Service* (Secure Swarm Toolkit): Processes delegation requests, generates session keys, records ExpectedOwnerGroups, and provides keys to agents (or via user).  
- *Agent*: Receives session key, constructs HMAC-signed requests to target websites.  
- *Website Enforcement Module*: Validates HMAC and checks scope on incoming requests.  
- *Crypto Library*: Supplies HMAC functionality (assumed part of Auth service and website).

**Critical Path** (for a successful operation)  
1. User sends delegation request to Auth Service with target agent group and scope.  
2. Auth Service generates a session key, associates it with ExpectedOwnerGroups and scope, and returns the key (assumed to user/agent).  
3. Agent uses the session key to compute an HMAC for each request and sends request + HMAC to the website.  
4. Website retrieves the corresponding secret (assumed shared with Auth Service) and verifies HMAC and that the requested action is within the granted scope.  
5. If valid, website processes the request; otherwise it rejects.

**Design Tradeoffs**  
- *Security vs. Performance*: HMAC verification adds latency (reported 127–140 seconds for successful access) but ensures request integrity; tradeoff may be acceptable for critical tasks.  
- *Flexibility vs. Complexity*: User-defined scopes enable fine-grained control but increase policy management complexity and risk of misconfiguration.  
- *Centralization vs. Availability*: Relying on an Auth Service centralizes delegation logic but introduces a single point of failure; replication could mitigate.

**Failure Signatures**  
- *HMAC mismatch*: Indicates request tampering or incorrect key.  
- *Expired session key*: Request rejected after key's time-to-live.  
- *Repeated key request*: Auth Service rejects if agent attempts to obtain the same key again (preventing key reuse abuse).  
- *Scope violation*: Agent attempts an action not covered by the granted scope; website denies.

**3 First Experiments**  
1. *Valid Authentication and Access*: Issue a delegation with a narrow scope, have agent perform allowed actions, confirm 100% success.  
2. *Invalid Key Reuse*: Attempt to reuse a session key after it has been revoked or expired; verify rejection.  
3. *Scope Enforcement*: Have agent request an operation outside the defined scope; expect denial by website.
