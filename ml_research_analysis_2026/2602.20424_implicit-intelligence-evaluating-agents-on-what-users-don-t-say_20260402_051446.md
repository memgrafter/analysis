# Implicit Intelligence -- Evaluating Agents on What Users Don't Say

## Quick Facts
- **arXiv ID**: 2602.20424  
- **Source URL**: https://arxiv.org/abs/2602.20424  
- **Reference count**: 40  
- **Primary result**: Top model (GPT-5.2-pro) achieves 48.3% scenario pass rate; open-weight models trail by up to 21 percentage points.

## Executive Summary
This paper addresses the challenge of underspecified user requests—where important constraints are implied but not stated—by introducing the Implicit Intelligence framework. Its core instantiation is Agent-as-a-World (AaW), an evaluation harness where interactive worlds are defined in human‑readable YAML and simulated by a fixed LLM (World Model). Across 205 test cases spanning Implicit Reasoning, Catastrophic Risk Avoidance, Privacy & Security, and Accessibility, AaW evaluates 16 frontier and open‑weight models. The best model passes fewer than half of scenarios, with persistent failure patterns including insufficient environmental exploration, incomplete configuration, and poor state preservation. Even extended thinking yields only marginal gains. The results indicate that reasoning about implicit requirements constitutes a distinct capability gap beyond general instruction‑following, even for state‑of‑the‑art models.

## Method Summary
AaW constructs interactive scenarios in declarative YAML files specifying context, entities, actions, execution rules, and a binary rubric. A fixed LLM (World Model) acts as a deterministic simulator: it validates action preconditions, enforces execution rules, updates entity states, and returns neutral feedback. The agent under test interacts turn‑by‑turn with this world until completion or a step limit. A separate evaluator model then judges the final trajectory against the rubric. Scenario quality is assured via a hybrid validation pipeline combining synthetic generation, attempter models, and human expert review to ensure logical consistency, discoverability of hidden constraints, and fairness.

## Key Results
- Top performer (GPT-5.2-pro) achieves 48.3% scenario pass rate; open-weight models trail by up to 21 percentage points.
- Failure modes: insufficient environmental exploration (e.g., not querying device state before changes), incomplete feature configuration, and inadequate state preservation across steps.
- Extended thinking (e.g., chain‑of‑thought) provides only marginal or inconsistent improvements.

## Why This Works (Mechanism)
### Mechanism 1
**Claim**: Declarative YAML specification enables rapid, scalable scenario creation without domain‑specific engineering.  
**Mechanism**: Scenarios are encoded in a single human‑readable file containing context, entities, actions, execution rules, and a rubric. This allows experts to express hidden constraints and world dynamics without coding.  
**Core assumption**: Complex, implicit requirements can be captured in a structured format that both humans and the World Model interpret consistently.  
**Evidence anchors**: Abstract states worlds are defined in YAML; Section 4.2 details the five components; corpus lacks direct YAML specification work but aligns with instruction‑following benchmarks.  
**Break condition**: If YAML cannot express dynamic or temporal constraints (e.g., state changes dependent on elapsed time), scenarios may become artificially static.

### Mechanism 2
**Claim**: Using an LLM as a universal simulator provides flexible, realistic environment dynamics without hand‑crafted simulators.  
**Mechanism**: The World Model (fixed LLM) receives the full scenario spec and acts as a deterministic executor: it validates preconditions, applies execution rules, updates states per the `returns` field, and returns neutral feedback.  
**Core assumption**: A capable LLM can faithfully follow specified action semantics and maintain state consistency without unwanted biases.  
**Evidence anchors**: Abstract mentions LLM as universal simulator; Section 4.3 describes constrained World Model role; Appendix A.4 shows Claude Opus 4.5 achieved 93.29% exact‑match consistency.  
**Break condition**: Inconsistent outputs for identical actions (e.g., different state updates) degrade simulation fidelity and fairness.

### Mechanism 3
**Claim**: Hidden constraints are made discoverable through environmental exploration, forcing agents to infer unstated requirements.  
**Mechanism**: Scenarios have apparent simplicity in the user request, hidden complexity in the solution, and constraints encoded in execution rules that are discoverable via observation actions (e.g., `get_*`, `list_*`).  
**Core assumption**: Information needed to satisfy implicit requirements is present in the environment and accessible through neutral actions, without tricks or external knowledge.  
**Evidence anchors**: Abstract lists the three scenario properties; Section 3 defines categories and Section 5.3 validates discoverability; corpus includes work on underspecification but AaW operationalizes it interactively.  
**Break condition**: If constraints are not actually discoverable (e.g., require guessing), the scenario becomes an unfair "gotcha" rather than a valid test.

## Foundational Learning
- **Concept: Implicit vs. explicit intelligence**  
  *Why needed*: The framework targets reasoning about unstated user needs, a distinct skill from literal instruction‑following. Engineers must distinguish these to design meaningful scenarios and interpret results.  
  *Quick check*: "Is 'Delete old documents' an implicit reasoning task? What hidden constraint might a reasonable user expect?"

- **Concept: LLM‑based environment simulation**  
  *Why needed*: AaW’s core innovation is using an LLM as a simulator. Engineers must understand the World Model’s constrained role (strict `returns` adherence, no intent reasoning) and how to ensure consistency.  
  *Quick check*: "What are the World Model’s responsibilities? What should it *not* do?"

- **Concept: Scenario discoverability and fairness**  
  *Why needed*: Scenarios must be challenging yet fair; constraints should be inferable from the environment, not arbitrary. The hybrid validation pipeline is critical for quality.  
  *Quick check*: "During validation, what three criteria must a scenario satisfy? How do they prevent 'gotcha' scenarios?"

## Architecture Onboarding
Component map: Primary Agent -> World Model -> Evaluator Model; Scenario YAML defines the world; Execution Loop mediates agent‑world interaction.

Critical path: 1) Load validated YAML scenario. 2) Initialize World Model with full spec. 3) For each step: send Agent’s action to World Model, receive feedback and updated state. 4) On `TASK_COMPLETE` or step limit, pass trajectory + final state to Evaluator with rubric. 5) Collect per‑criterion pass/fail and compute Scenario Pass Rate.

Design tradeoffs: 
- **World Model choice**: Consistency (Claude Opus 4.5) vs. cost/availability; cheaper models risk simulation variance.
- **YAML vs. code**: YAML is accessible but may not capture extremely complex dynamics; trade‑off between simplicity and expressiveness.
- **LLM evaluator**: Scalable but potentially biased; mitigated by objective, binary criteria and human validation.
- **No clarification**: Single‑turn interaction matches some real‑world deployments but excludes strategic question‑asking as a separate skill.

Failure signatures:
- Agent modifies settings without first querying relevant state (e.g., changes playback route without checking current route).
- World Model returns inconsistent state updates for identical actions (violates determinism).
- Evaluator yields contradictory judgments on identical trajectories (indicates rubric ambiguity or prompt issues).
- Scenario fails human validation (e.g., constraints not discoverable, rubric not binary).

First 3 experiments:
1. **Smoke test**: Run example scenario `ios-accessibility-mono-balance` with known good trajectory; expect full pass.
2. **World Model consistency**: Execute trivial action sequence (e.g., `list_audio_devices` then `pair_device`) multiple times; verify identical state changes and messages.
3. **Rubric edge case**: Create scenario where agent disables mono audio instead of enabling; verify evaluator fails relevant criterion and passes others appropriately.

## Open Questions the Paper Calls Out
- **Question**: How can AaW be extended to evaluate third‑party applications with their own domain‑specific implicit conventions, beyond the current iOS Shortcuts action space?  
  *Basis*: Paper acknowledges action space limited to ~300 native iOS actions, while real‑world usage extends to third‑party apps.  
  *Why unresolved*: No methodology or examples for extending AaW to custom applications; scalability and design patterns unclear.  
  *Resolving evidence*: Implement and validate AaW scenarios for at least two popular third‑party apps (e.g., WhatsApp, Spotify), defining entities, actions, and implicit requirements in YAML, and demonstrate successful evaluation of frontier models.

- **Question**: To what extent do implicit requirements vary across cultures, age groups, and technical backgrounds, and does the current benchmark's author‑centric construction lead to systematic evaluation biases?  
  *Basis*: Paper notes implicit requirements may not represent diversity of real‑world user expectations.  
  *Why unresolved*: Scenarios authored by limited team, validated against narrow model set; no cross‑demographic user studies.  
  *Resolving evidence*: Conduct large‑scale user study where participants from varied demographics generate and validate implicit constraints for given simple prompts; measure performance discrepancies on culturally grounded scenarios vs. original benchmark.

- **Question**: Can agents learn to strategically ask clarifying questions to resolve underspecification, and how should such question‑asking be integrated into the Implicit Intelligence evaluation protocol?  
  *Basis*: Paper suggests measuring both implicit inference and strategic question‑asking as separate skills is a natural extension.  
  *Why unresolved*: Current single‑turn, no‑clarification design isolates implicit inference but does not assess question‑asking ability.  
  *Resolving evidence*: Modify AaW protocol to allow agents limited clarification turns; define metrics for question relevance and efficiency; evaluate whether better question‑askers achieve higher success rates.

- **Question**: Does the choice of World Model affect scenario difficulty or relative agent ranking, and could simulation bias inadvertently favor certain model families?  
  *Basis*: Paper fixed Claude Opus 4.5 as World Model after consistency testing; all agent evaluations used this simulator.  
  *Why unresolved*: No analysis of whether simulator's inherent biases (e.g., interpreting ambiguous rules) interact with agent strategies; results may not generalize across simulators.  
  *Resolving evidence*: Re‑run significant scenario subset using multiple high‑consistency World Models (e.g., GPT‑5.2‑pro, Gemini 3 Pro) and compare agent performance correlations and ranking stability.

- **Question**: Are the four categories (Implicit Reasoning, Catastrophic Risk Avoidance, Privacy & Security, Accessibility) exhaustive, or do significant types of underspecified requirements—such as social norm adherence, temporal dynamics, or economic efficiency—remain unmeasured?  
  *Basis*: Categories designed to cover "major failure modes" but selected pragmatically based on iOS Shortcuts affordances and author judgment.  
  *Why unresolved*: No systematic derivation from a taxonomy of real‑world user ambiguity; may miss important implicit dimensions from other domains.  
  *Resolving evidence*: Analyze corpus of real human‑agent interactions (e.g., customer service logs, voice assistant queries) to identify and taxonomize implicit requirements; assess coverage of four categories and design new scenarios for uncovered dimensions.

## Limitations
- **Simulation fidelity**: The World Model may produce inconsistent state updates for edge cases, risking unfair agent evaluations despite 93.29% reported consistency.
- **Scenario coverage & discoverability**: The 205 iOS‑focused scenarios may not generalize; hidden constraints could be arbitrarily easy or hard to infer, and human validation was limited.
- **Evaluator reliability**: Using a single LLM for rubric assessment introduces potential bias and lacks inter‑rater agreement metrics.

## Confidence
- **Framework validity**: Medium – YAML expressiveness and World Model consistency remain partially unverified for complex dynamics.
- **Empirical performance gaps**: Medium – Evaluation noise from LLM evaluator and scenario selection may affect reported pass rates.
- **Distinct capability gap**: Low – Insufficient evidence to rule out alternative explanations (e.g., lack of exploration strategies).

## Next Checks
1. **World Model deterministic stress test**: Run 10,000 random action sequences across all scenarios; compute exact‑match consistency, aiming for ≥99%.
2. **Cross‑evaluator agreement**: Re‑evaluate 500 trajectories using 5 diverse LLM evaluators; report binary rubric agreement (target ≥95%).
3. **Human solvability study**: Recruit 20 participants to solve 50 scenarios without hints; measure success rate to validate discoverability (target ≥80% of scenarios solvable by ≥60% of participants).
