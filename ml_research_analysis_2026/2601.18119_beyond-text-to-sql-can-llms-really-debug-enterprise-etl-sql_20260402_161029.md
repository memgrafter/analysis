# Beyond Text-to-SQL: Can LLMs Really Debug Enterprise ETL SQL?

## Quick Facts
- arXiv ID: 2601.18119
- Source URL: https://arxiv.org/abs/2601.18119
- Reference count: 40
- Primary result: State-of-the-art LLMs achieve only 36.46% accuracy on syntax errors and 32.17% on semantic errors in enterprise ETL SQL debugging, with most models below 20%.

## Executive Summary
This paper addresses the persistent challenge of debugging complex enterprise ETL SQL, where even advanced large language models (LLMs) struggle with iterative corrections. The core contribution is the Squirrel Benchmark, the first enterprise-level SQL debugging benchmark. It employs an automated reverse-engineering pipeline to inject realistic bugs into large, complex SQL scripts (averaging over 140 lines) and introduces an execution-free evaluation framework based on graph metrics. Evaluation of nearly 30 LLMs reveals a substantial performance gap: the best model, Claude-4-Sonnet, achieves only 36.46% accuracy on syntax errors and 32.17% on semantic errors, with most models below 20%. The study further explores supervised fine-tuning (SFT) and agent-based strategies, showing that in-domain SFT yields significant improvements, while agent effectiveness depends heavily on the main agent’s capabilities, underscoring the difficulty of the task.

## Method Summary
Squirrel Benchmark constructs debugging tasks by starting from correct, complex enterprise SQL scripts. A hierarchical bug taxonomy derived from production logs guides the minimal injection of realistic bugs into queries. Candidate instances (buggy SQL, reference solution, error message) undergo an attack-defense validation: they are tested with a diverse suite of advanced LLMs, and only those that are challenging yet solvable are retained. For evaluation, both predicted and reference SQL are parsed into normalized abstract syntax trees via Apache Calcite. Semantic equivalence is assessed through graph isomorphism on these logical plans, avoiding costly database execution and privacy issues.

## Key Results
- Best model (Claude-4-Sonnet) accuracy: 36.46% (syntax) and 32.17% (semantic) on graph-match metric.
- Majority of evaluated LLMs perform below 20% on both error types.
- In-domain SFT (e.g., DM-SFT on Qwen-2.5-Coder-7B) yields a 33.17% gain on Squirrel-Syntax.
- Agent-based debugging (e.g., Kimi-K2 + Qwen3-Coder) improves exact match by 65% relative but often reduces Modify Better scores, indicating instability.

## Why This Works (Mechanism)

### Reverse-Engineering-Based Bug Injection
The construction pipeline begins with a correct SQL query, analyzes its structural profile (AST, functions, clauses), selects appropriate bug types from a production-derived taxonomy, and applies the smallest possible change to induce the targeted error. This preserves the query’s overall complexity while introducing realistic, isolated faults. The core assumption is that minimal perturbations of correct SQL reflect common production errors. Evidence: The pipeline is guided by principles of structural awareness, taxonomy-guided selection, and minimal-change injection, ensuring fidelity to real debugging scenarios.

### Execution-Free Graph-Based Evaluation
Predicted and reference SQL are transformed into normalized logical plans using Apache Calcite. These plans are simplified via logical rewrites (e.g., operator reordering), and graph isomorphism determines semantic equivalence. This avoids actual database execution, addressing scalability and privacy concerns in enterprise settings. The core assumption is that normalized logical plans adequately capture functional equivalence for debugging tasks. Evidence: The framework defines three metrics (Exact Match, Graph Match, Modify Better) centered on AST comparison, enabling efficient assessment without data dependencies.

### Attack-Defense Validation for Benchmark Difficulty
After generating candidate instances, the pipeline tests them with a diverse set of advanced LLMs. Instances solved by the majority are discarded as too easy; those solved by only a few are retained; unsolved cases are manually reviewed. This adversarial filtering ensures the benchmark maintains an appropriate difficulty curve and predictive validity for future models. Evidence: The process systematically removes trivial cases, as reflected in the low absolute performance across all evaluated LLMs.

## Architecture Onboarding

**Component map:**  
Seed SQL Curation -> Scenario Library -> Synthetic SQL Generator -> Bug Taxonomy -> Bug Injector -> Attack-Defense Validator -> Evaluation Module

**Critical path:**  
- Data construction: Seed SQL → (optional) Synthetic generation → Bug injection → Attack-defense validation → Final benchmark.  
- Evaluation: Input (issue SQL, error message, DDL) → Model prediction → AST normalization → Graph comparison → Score.

**Design tradeoffs:**  
- Automation vs. realism: LLM-driven generation scales but may introduce unrealistic patterns; manual validation mitigates but is costly.  
- Execution-free vs. execution-based: Avoids database access and privacy issues but may miss data-dependent errors.  
- Attack-defense filtering: Heuristic thresholds may bias coverage or difficulty if not carefully tuned.

**Failure signatures:**  
- Bug injection produces unrealistic or unsolvable errors not representative of production.  
- Graph normalization over-aggressively rewrites queries, leading to false semantic matches.  
- Filtering inadvertently removes entire error categories due to attacking LLM biases.  
- Synthetic SQL generation fails to replicate nested, cross-database ETL logic complexity.

## Open Questions the Paper Calls Out

1. To what extent can supervised fine-tuning (SFT) enable LLMs to reach human-level performance on enterprise SQL debugging? The paper explicitly asks this and reports that SFT on Qwen-2.5-Coder-7B yields a 33.17% gain on Squirrel-Syntax, yet the best model (Claude-4-Sonnet) achieves only 36.46% GM on syntax and 32.17% on semantic, with most models below 20%. Absolute performance remains far from practical deployment thresholds. It is unknown whether more advanced fine-tuning, larger models, or richer data distributions can close the gap. Large-scale SFT experiments with state-of-the-art models (>100B parameters) across diverse SFT methods and both error types, coupled with fine-grained error analysis, would be needed.

2. Can agent-based frameworks substantially improve LLM debugging performance beyond single-model approaches, and what design factors are critical? The paper poses this question and presents an agent baseline showing mixed results: e.g., Kimi-K2+Qwen3-Coder improves EM by 65% relative, while GPT-4o as main agent still underperforms the best single model. The MB score often declines, indicating instability. The agentic strategy is nascent; only one architecture (main agent + code sub-agent + TQS checker) is explored. Alternative tool integrations, memory mechanisms, and iteration policies may yield more consistent gains. A systematic study comparing multiple agent configurations (tool choices, iteration limits, memory) across a broad model set, with statistical analysis of success rates per bug type and iteration dynamics, plus human evaluations, would resolve this.

3. How can the Squirrel Benchmark be extended to cover a broader range of SQL dialects and ensure its generalization beyond Hive/Spark SQL? The Limitations section explicitly states "the limited SQL dialect coverage" as a constraint, noting the benchmark is built on Hive/Spark SQL, though the method is dialect-agnostic. Enterprise environments often use other dialects (e.g., PostgreSQL, MySQL, T-SQL). It is unclear whether conclusions from Hive/Spark generalize, and whether dialect-specific bugs are adequately captured. Constructing parallel dialect versions of Squirrel using the same pipeline, then evaluating model performance across dialects and measuring transfer learning effects, would provide evidence.

4. Do the execution-free evaluation metrics (Exact Match, Graph Match, Modify Better) reliably predict real-world debugging success, or can they be gamed? The methodology introduces these metrics to avoid execution but acknowledges they rely on a single reference solution. The paper claims strong correlation with practical outcomes but provides no empirical validation; the limitations note they are less suitable for tasks with many valid solutions. The metrics may fail to capture semantic equivalence when multiple repairs are correct, and Modify Better assumes minimal edits toward a single target, which may not match developers' iterative processes. Adversarial outputs could inflate scores without genuine bug resolution. Human expert evaluation of model outputs rated by each metric, measuring agreement with human judgments, and correlating metric scores with traditional execution accuracy on a held-out set of real production bugs would quantify predictive validity.

## Limitations
- Bug realism: Synthetic bugs may not capture the full diversity of complex, multi-step enterprise errors despite taxonomy guidance.
- Evaluation coverage: Graph-based AST normalization may miss data-dependent semantic errors or side effects (e.g., NULL handling, collation).
- Filtering bias: Attack-defense thresholds and model selection could over-filter rare error types or bias toward weaknesses of attacking LLMs.
- Synthetic data fidelity: Transferred scenarios via LLMs might not fully replicate nested, cross-database ETL logic of real enterprise SQL.

## Confidence
- Bug Injection Mechanism: Medium
- Execution-Free Evaluation Validity: Medium
- Attack-Defense Filtering Efficacy: Low
- Performance Gap Results: High
