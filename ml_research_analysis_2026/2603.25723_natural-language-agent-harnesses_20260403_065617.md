# Natural-Language Agent Harnesses

## Quick Facts
- **arXiv ID:** 2603.25723
- **Source URL:** https://arxiv.org/abs/2603.25723
- **Reference count:** 31
- **Primary result:** Introduces Natural-Language Agent Harnesses (NLAHs) and the Intelligent Harness Runtime (IHR) to decouple harness logic from framework-specific code, improving maintainability and shifting verification toward artifact-backed closure.

## Executive Summary
The paper tackles the problem that agent harnesses are typically tightly coupled to specific code frameworks, impeding transfer, comparison, and scientific rigor. It proposes Natural-Language Agent Harnesses (NLAHs), which define harness logic in structured natural language, and the Intelligent Harness Runtime (IHR), a shared execution engine that runs these harnesses directly. Evaluations on SWE-bench (coding) and OSWorld (OS tasks) show that while IHR increases intermediate process metrics (tokens, tool calls), it yields similar overall success rates to ablations, with failures concentrated in a small "component-sensitive frontier." Adding explicit harness modules (e.g., self-evolution, file-backed state) helps on specific boundary cases but does not uniformly boost performance, suggesting that alignment with evaluator behavior is key. Migrating a code-based harness (OS-Symphony) to NLAH under IHR significantly improves OSWorld success (30.4% to 47.2%) and moves verification from brittle GUI repair to durable, artifact-backed closure.

## Method Summary
The authors develop NLAHs, a declarative format for specifying agent harness logic in structured natural language (e.g., YAML-like with NL fields), and implement IHR, a runtime that interprets NLAHs, manages state, tool calls, and evaluation. They compare full IHR against framework-specific code harnesses and NLAH ablations (without explicit modules). Experiments run on SWE-bench (Python issue resolution) and OSWorld (desktop OS tasks), measuring success rates, process metrics (tokens, tool calls), and qualitative closure modes. A case study migrates the OS-Symphony code harness to NLAH/IHR to assess portability and impact.

## Key Results
- Under RQ1, Full IHR significantly increases process metrics (tokens, tool calls) versus ablations but yields similar SWE-bench success rates; flips are concentrated in a small component-sensitive frontier.
- RQ2 shows explicit harness modules (self-evolution, file-backed state) improve outcomes on specific boundary cases but do not uniformly raise performance, indicating alignment with evaluator behavior matters more than added structure alone.
- RQ3 finds migrating OS-Symphony from code to NLAH under IHR improves OSWorld success (30.4% → 47.2%) and shifts verification toward durable artifact-backed closure rather than brittle GUI repair.

## Why This Works (Mechanism)
NLAHs decouple harness design from implementation by expressing logic in structured natural language, making harnesses portable, readable, and modifiable without code changes. IHR provides a unified execution layer that interprets NLAHs, handling tool orchestration, state management, and evaluation consistently across agents and tasks. This separation allows harness components (e.g., self-evaluation loops, file-backed state) to be added or removed declaratively, enabling targeted improvements where they align with evaluation criteria. The shift to artifact-backed closure occurs because IHR-executed NLAHs can more reliably enforce persistent state and verify outcomes via durable artifacts (e.g., file changes) rather than transient GUI states, which are often brittle.

## Foundational Learning
- **Agent Harness:** Framework-embedded code that controls agent loop, tools, and evaluation. *Why needed:* Current design prevents transfer and scientific comparison. *Quick check:* Can you swap the harness between two agent frameworks without rewriting?
- **Structured Natural Language (for harnesses):** Formalized NL (e.g., key-value with NL prompts) defining harness steps and conditions. *Why needed:* Balances human readability with machine interpretability. *Quick check:* Does the format support conditional branching and loops unambiguously?
- **Shared Runtime (IHR):** Engine that parses and executes NLAHs across different agents. *Why needed:* Eliminates framework lock-in and standardizes execution. *Quick check:* Can IHR run the same NLAH on a CodeAct vs. ReAct agent?
- **Process Metrics:** Tokens used, tool calls made during execution. *Why needed:* Provide intermediate behavioral signals beyond binary success. *Quick check:* Do higher token counts correlate with success on a given benchmark?
- **Evaluator Alignment:** Harness behavior matching how a benchmark judges success (e.g., file changes vs. GUI clicks). *Why needed:* Explains why structural additions sometimes fail to improve scores. *Quick check:* Does the harness check exactly the same conditions as the benchmark’s evaluation script?

## Architecture Onboarding
Component map: NLAH Definition -> IHR Parser -> State/Tool Manager -> Agent Execution -> Environment -> Evaluator

Critical path: IHR reads NLAH configuration -> initializes state -> for each step: generates NL instruction to agent -> agent acts via tools -> IHR updates state and checks termination conditions -> evaluation compares final state to success criteria.

Design tradeoffs: Flexibility of NL specification vs. parsing overhead and ambiguity; explicit modules increase harness complexity but may better match evaluator logic; shared runtime introduces abstraction cost but gains portability.

Failure signatures: "Component-sensitive frontier" – certain tasks fail due to specific harness module interactions (e.g., self-evolution loop misalignment); brittle GUI repair when harness relies on transient UI states; success flips when harness and evaluator logic diverge.

First experiments: 1) Run baseline NLAH/IHR on SWE-bench, compare process metrics and success to a code-based harness. 2) Add a file-backed state module, test on tasks requiring persistent file changes, measure boundary-case improvements. 3) Migrate OS-Symphony’s code harness to NLAH/IHR, run on OSWorld, analyze shift in closure mode (GUI vs. artifact).

## Limitations
- Reproducibility gap: No reproduction notes provided; raw data/code for IHR/NLAH not confirmed available.
- Generalization scope: Evaluation limited to SWE-bench and OSWorld; unclear if results hold for other agent domains (e.g., robotics).
- Ambiguity in "component-sensitive frontier": RQ1’s flipped instances lack diagnostic breakdown of which harness components failed or correlated task types.

## Confidence
- RQ1 (IHR process metrics ↑, success ≈, frontier flips): Medium. Process increases are direct; success parity and frontier explanation are reported but not deeply diagnosed.
- RQ2 (Explicit modules ≠ uniform gains): Low. Claim relies on "alignment with evaluator behavior" without quantifying evaluator consistency or defining boundary cases precisely.
- RQ3 (NLAH migration ↑ OSWorld, shifts closure): High-Medium. Clear metric jump and qualitative shift described; needs verification that migration itself (not reimplementation) drove change.

## Next Checks
1. Cross-benchmark replication: Re-run IHR vs. ablations on WebArena and AgentBench to test generalizability beyond SWE-bench/OSWorld.
2. Frontier case forensics: Manually analyze all flipped instances from RQ1 to identify which NLAH modules (e.g., state tracking, tool selection) correlated with failure/success.
3. Maintainability study: Conduct controlled user study comparing modification time/bug rates for adding a new tool to an NLAH vs. traditional code-based harness.
