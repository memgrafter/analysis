# Automated Generation of Microfluidic Netlists using Large Language Models

## Quick Facts
- arXiv ID: 2602.19297
- Source URL: https://arxiv.org/abs/2602.19297
- Reference count: 17
- Primary result: Achieved 88% average syntactical accuracy and near-perfect functional flow inference, with top models reaching 100% pass rates on several benchmarks.

## Executive Summary
Microfluidic design automation (MFDA) presents a high barrier to entry for non-experts. This paper introduces the first LLM-based approach to transform natural language device specifications into structural Verilog netlists, enabling easier generation of MFDA-compatible designs. The proposed system combines retrieval-augmented generation (RAG) with a constrained system prompt. RAG retrieves relevant microfluidic primitive definitions from a library, while the system prompt instructs the model to output only structural Verilog using those primitives and encourages chain-of-thought reasoning. No model retraining is required.

The approach was evaluated on ten benchmark specifications using several open-source LLMs. It achieved an average syntactical accuracy of 88% and correctly inferred microfluidic functional flow for nearly all test cases. Top-performing models (Qwen2, DeepSeek-R1) reached 100% syntax and function pass rates on several benchmarks, demonstrating the potential of LLMs to democratize microfluidic design.

## Method Summary
The method takes a natural language specification and produces a structural Verilog netlist without any training. It relies on a predefined library of microfluidic primitive modules (e.g., mixers, reservoirs). For a given prompt, a retrieval-augmented generation (RAG) component fetches the top‑k most relevant primitive definitions based on vector similarity. These definitions, together with a carefully crafted system prompt that enforces output format and domain constraints, are fed to an LLM. The system prompt also encourages step‑by‑step reasoning. The generated netlist is then checked for Verilog syntax using tools like iverilog and assessed for functional correctness against the specification. The pipeline was tested on ten benchmarks, with prompt and RAG parameters tuned on a held‑out set of five.

## Key Results
- Average syntactical accuracy across LLMs: 88%.
- Top models (Qwen2, DeepSeek-R1) achieved 100% pass rates on several benchmarks, demonstrating near‑perfect functional flow inference.
- The RAG‑constrained approach reliably uses only predefined primitives, ensuring netlist compatibility with downstream MFDA tools like OpenMFDA.

## Why This Works (Mechanism)

### Mechanism 1: Retrieval-Augmented Generation (RAG)
- **Claim**: RAG provides the LLM with precise, up‑to‑date domain knowledge without retraining.
- **Mechanism**: The user’s prompt is vectorized and compared against a library of Verilog module definitions; the top‑k most similar modules are injected as context. This grounds the LLM in the exact syntax and available component set.
- **Core assumption**: Vector similarity can reliably map natural language descriptions (e.g., “mix”) to correct hardware primitives.
- **Evidence anchors**: [abstract] “combines retrieval‑augmented generation (RAG) with a constrained system prompt to ensure outputs use only predefined microfluidic primitives”; [section III.C] “The RAG process compares the similarity of the user prompt… retrieves the top‑k relevant primitives as context… bypasses the need to retrain a new model every time a module is added to the library.”; [corpus] Related work in netlist‑focused LLM applications validates the RAG approach for structured hardware generation, though specific microfluidic+RAG is novel.
- **Break condition**: If the library lacks a primitive for the requested function, RAG retrieves an irrelevant or no module, causing generation failure.

### Mechanism 2: Constrained System Prompt
- **Claim**: A constrained system prompt enforces output structure and domain boundaries.
- **Mechanism**: The system prompt instructs the model to generate only structural Verilog netlists using modules from the RAG context, forbidding behavioral Verilog and out‑of‑scope operations. It also encourages chain‑of‑thought reasoning.
- **Core assumption**: A detailed, directive system prompt can override the LLM’s general training and steer it toward a narrow, formal output.
- **Evidence anchors**: [abstract] “constrained system prompt to ensure outputs use only predefined microfluidic primitives and correct syntax”; [section III.C] “Using the system prompt, we limit the model to generating structural Verilog code… This ensures the tool does not produce behavioral Verilog or functionality outside the microfluidic domain… encourage chain‑of‑thought reasoning.”; [section IV.B.1] “The system prompt included sections aimed at teaching the LLM proper syntax… One way to address these syntactical errors is to fine‑tune the model… or including a more comprehensive library… in the RAG procedure.”
- **Break condition**: Vague user prompts or complex operations exceeding the prompt’s instructional examples may lead the model to violate constraints or invent invalid primitives.

### Mechanism 3: Large Context Length
- **Claim**: Large context length in modern LLMs is critical for integrating the lengthy system prompt, RAG context, and user query.
- **Mechanism**: The combined context (system prompt + retrieved module definitions) must fit within the model’s window; larger windows (e.g., 131k tokens in DeepSeek‑R1) allow full reference and cross‑referencing.
- **Core assumption**: Performance differences are primarily due to context capacity, not just parameter count, when handling complex prompts.
- **Evidence anchors**: [section III.B] Table I shows DeepSeek‑R1 and Qwen2 have the largest context lengths and outperformed others; [section IV.B.2] “Qwen2 and DeepSeek‑R1 outperformed all other models… However, Codestral, despite having fewer parameters… performed better due to its context length being four times larger [than Llama3]. This is crucial given the extensive system prompt.”
- **Break condition**: If the combined prompt exceeds the model’s context window, truncation occurs, likely removing critical constraints or modules.

## Foundational Learning

### Microfluidic Primitive Library & Functional Flow
- **Why needed**: The entire output is a netlist of predefined components. Engineers must understand the available primitives (reservoirs, mixers, diluters, heaters, filters) and their port interfaces to design valid prompts, interpret LLM outputs, and debug failures. Functional flow (serial vs. parallel mixing, dilution‑before‑mixing) is the core logic the LLM must infer.
- **Quick check**: Given the prompt “Dilute solution A, then mix with B”, what are the minimum required primitives and their correct interconnection order?

### Structural Verilog for Hardware Description
- **Why needed**: The target output format is structural Verilog netlists (`module top(...); inst1 inst1_0(...); ... endmodule`). An engineer must distinguish this from behavioral Verilog (using `always` blocks) and understand netlist syntax (module instantiation, wire declaration) to verify outputs, integrate with OpenMFDA, and diagnose syntax errors.
- **Quick check**: Is `mixer m1 (.in1(w1), .out(w2));` a valid structural instantiation? What is missing if `w1` is not declared as a `wire`?

### Retrieval‑Augmented Generation (RAG) for Domain Knowledge Injection
- **Why needed**: RAG is the mechanism connecting the abstract prompt to concrete, tool‑compatible primitives. An engineer must grasp how vector search retrieves relevant module definitions and how the retrieved context is formatted into the LLM prompt to troubleshoot mismatches (e.g., if the model retrieves a “heater” for a “mix” operation).
- **Quick check**: If the LLM generates an undefined module `splitter`, what are two probable causes related to the RAG process?

## Architecture Onboarding

#### Component Map
User Prompt -> RAG Retriever (vector search over Primitive Library) -> System Prompt + RAG Context + User Prompt -> LLM Engine -> Raw Verilog Netlist -> Output Verifier (syntax check) -> Valid Netlist -> Downstream Tool (OpenMFDA)

#### Critical Path
1. User provides natural language specification.
2. RAG retriever fetches relevant primitive definitions from the library based on semantic similarity.
3. System prompt (rules, examples) is combined with RAG context and user prompt.
4. LLM generates a structural Verilog netlist.
5. Verifier checks syntax; if valid, netlist is passed to OpenMFDA for layout generation.

#### Design Tradeoffs
- **Prompt Complexity vs. Usability**: More detailed prompt improves accuracy but increases context size, potentially exceeding model limits and confusing simpler models.
- **Model Scale vs. Cost/Latency**: Larger models (e.g., Qwen2 72B) give higher accuracy but require more GPU resources and slower inference.
- **Generality vs. Safety**: Overly constrained prompt ensures syntactical correctness but may reject slightly novel specifications; a looser prompt risks invalid syntax or primitives.

#### Failure Signatures
- **Syntax errors**: Missing `endmodule`, undeclared wires, incorrect port mapping.
- **Unknown module**: Generated primitive name not in retrieved library.
- **Logical flow error**: Correct primitives and syntax but incorrect wiring (e.g., wrong sequence of operations).
- **No output/reprompt**: LLM returns a conversational message instead of code.

#### First 3 Experiments (to onboard a new engineer)
1. **Primitive Smoke Test**: Prompt “Take 2 solutions as input. Mix them.” Verify the netlist has exactly one `mixer` with two inputs from reservoirs and one output wire. Confirm RAG retrieved `mixer` and `reservoir`.
2. **Sequential Composition Test**: Prompt “Take 3 solutions. Mix A and B, then mix result with C.” Verify two `mixer` instances in series, with the first output fed into the second mixer’s input.
3. **Context Stress Test**: Use a complex prompt (mixing 5 solutions with parallel steps) on a small‑context model (CodeLlama) vs. a large‑context model (DeepSeek‑R1). Document failures (truncation, lost constraints) versus success.

## Open Questions the Paper Calls Out
1. **Question**: Can an automatic verification loop, integrating EDA syntax checking with iterative LLM prompting, reliably achieve near‑perfect syntactical accuracy for microfluidic netlists?
   - **Basis**: Future Work suggests implementing a verification system akin to [15] where outputs are checked by an EDA tool and iteratively corrected.
   - **Why unresolved**: The verification system was not implemented; syntactical accuracy remained 88% with single‑prompt approach.
   - **Evidence (potential validation)**: Integrate a Verilog linter/simulator into a feedback loop, measure Pass@1 syntax accuracy, and compare to baseline.

2. **Question**: Would a dedicated fine‑tuned LLM, trained on microfluidic Verilog netlists and domain‑specific syntax, significantly outperform general‑purpose or code‑optimized models?
   - **Basis**: Future Work states that fine‑tuning could improve syntactical accuracy beyond 88%.
   - **Why unresolved**: Only pretrained models were evaluated; potential of specialized fine‑tuned model unknown.
   - **Evidence**: Create a fine‑tuning dataset from OpenMFDA examples, train a base LLM, evaluate on the same benchmarks.

3. **Question**: How does the RAG‑based methodology scale to complex, multi‑step microfluidic designs that exceed the simple linear/parallel reasoning in the current benchmark suite?
   - **Basis**: Inferred: evaluation used only five basic benchmarks; real designs involve intricate sequences, conditionals, feedback loops not represented.
   - **Why unresolved**: The paper acknowledges it is “preliminary” and focused on “basic systems”; performance on complex designs is untested.
   - **Evidence**: Curate new benchmarks from published microfluidic designs (e.g., DNA sequencing chips), generate prompts, evaluate fidelity against reference netlists.

4. **Question**: Does reliance on a fixed library of predefined primitives and top‑k RAG retrieval limit the LLM’s ability to handle novel microfluidic components or hybrid designs?
   - **Basis**: Inferred: Methodology constrains LLM to only primitives from library; if required component absent, output may be invalid.
   - **Why unresolved**: The study assumes library is comprehensive for the benchmark; boundary conditions where library is insufficient are unexplored.
   - **Evidence**: Introduce “out‑of‑library” test cases that require a primitive not in the database, measure failure modes (hallucination, incorrect substitution).

5. **Question**: To what extent does the design of the system prompt govern the LLM’s success, and can prompt optimization be automated?
   - **Basis**: Inferred: The system prompt was empirically developed; syntax errors persist despite functionality, suggesting suboptimal prompt formulation.
   - **Why unresolved**: Prompt engineering process not systematically analyzed; interactions with model architecture (e.g., context length) are unstudied.
   - **Evidence**: Conduct ablation study decomposing the system prompt (remove examples, vary chain‑of‑thought instructions) across models, measure Pass@1 changes; alternatively apply automated prompt optimization.

## Limitations
- The exact primitive library, full system prompt, and RAG implementation details (embedding model, k, context format) are not disclosed, preventing exact replication.
- Evaluation is limited to 10 basic benchmarks, which may not generalize to complex, realistic microfluidic designs.
- Reported metrics (88% syntax, functional pass rates) are self‑reported without independent reproduction, and the functional evaluation criteria are unspecified.

## Confidence
- Overall reported accuracy (88% syntax, ~100% function for top models): Medium
- RAG enables domain‑grounded generation: Medium
- Constrained system prompt ensures syntactic/semantic correctness: Medium
- Large context window drives performance differences: Medium
- Novelty claim (first LLM for microfluidic netlists): Low
