# Towards Cold-Start Drafting and Continual Refining: A Value-Driven Memory Approach with Application to NPU Kernel Synthesis

## Quick Facts
- **arXiv ID:** 2603.10846
- **Source URL:** https://arxiv.org/abs/2603.10846
- **Reference count:** 40
- **Primary result:** Boosts frontier LLMs' correctness on an Ascend C benchmark from 11.0% to 83.0% and achieves a median 3.60× speedup over initial drafts through iterative refinement, without model fine-tuning.

## Executive Summary
EvoKernel addresses the cold-start problem in kernel synthesis for data-scarce domain-specific architectures like NPUs, where large language models (LLMs) fail due to a lack of training data. It formulates synthesis as a memory-based reinforcement learning task, using a value-driven retrieval mechanism with stage-specific Q-values to prioritize experiences for drafting (bootstrapping correctness) and refining (optimizing latency). By enabling cross-task memory sharing, the approach generalizes insights from simpler to more complex operators and even to out-of-distribution workloads, demonstrating effective transfer without any model weight updates.

## Method Summary
The system uses a frozen frontier LLM (e.g., GPT-5.2) as a generator within a two-stage pipeline. In the drafting stage, the agent retrieves context from a dynamic memory bank using Q-values that estimate an item's contribution to generating a functionally correct kernel. After the first feasible kernel is found, the stage switches to refining, where retrieval uses a separate Q-value to prioritize items that reduce latency. A multi-gate verifier provides structured feedback (anti-hacking, compilation, correctness, profiling), which is converted into binary or normalized continuous rewards to update the Q-values via Monte-Carlo returns. Memory is shared across all tasks, enabling cross-operator transfer.

## Key Results
- Correctness on an Ascend C benchmark (KernelBench) improves from a baseline of 11.0% (Acc) to 83.0% (Acc) after EvoKernel.
- Achieves a median latency speedup of 3.60× over the initial draft.
- Generalizes to out-of-distribution workloads, including CUDA attention operators and DeepSeek mHC kernels.

## Why This Works (Mechanism)

### Mechanism 1: Value-Driven Retrieval for Stage-Specific Objectives
The agent learns separate Q-values Q₁(s,m) and Q₂(s,m) for memory items *m* via Monte-Carlo updates. During drafting, ϵ-greedy over Q₁ selects context that historically led to feasible kernels (binary +1 reward). During refining, Q₂ guides selection for latency optimization using a relative reward normalized online. This prioritizes high-utility demonstrations without updating the LLM weights, leveraging its in-context learning capacity. Evidence includes correctness jumps from 11% to 98.5% (CR) and the outperformance of value-driven retrieval over heuristic similarity in later iterations. A break condition is if the LLM fails to generalize from retrieved examples due to fundamental architectural mismatches, potentially trapping the agent in local optima.

### Mechanism 2: Cross-Task Memory Sharing and Emergent Curriculum
A unified memory bank *M* accumulates experiences across all tasks. Retrieval operates over *M*, not per-task history, allowing patterns from simple operators (e.g., `Tanh`) to transfer to complex fused operators (e.g., `Conv3d HardSwish GroupNorm Meanfuse`). This induces an emergent curriculum: pre-building memory on L1 operators enables L2 operators to solve faster (64% L2 correctness vs. 34% for L2 scratch). The approach also generalizes to unseen Attention and mHC kernels. The core assumption is that kernel synthesis problems share reusable sub-skills discoverable via value-guided retrieval. A break condition is if tasks are too disparate (e.g., NPU vs. GPU memory models), introducing harmful patterns.

### Mechanism 3: Two-Stage Pipeline with Multi-Gate Verifier for Dense Rewards
The drafting stage uses a binary feasibility reward to bootstrap any compilable, correct kernel. The refining stage switches to a continuous latency reward (tanh(log speedup)) normalized online, enabling fine-grained optimization. The verifier's gates (anti-hacking, compilation, correctness, profiling) provide structured, mostly binary feedback, turning the rigid compilation environment into a denser signal for stable credit assignment. Evidence includes the overall performance gains and the ablation showing value-driven retrieval’s advantage. A break condition is if verifier feedback is brittle (false negatives) or latency measurements are too noisy, corrupting reward signals and Q-value estimates.

## Foundational Learning
- **Cold-start problem in data-scarce domains:** Needed because NPU kernel synthesis lacks training corpora and expert demonstrations. Standard LLMs fail due to over-reliance on memorized CUDA patterns, not hardware reasoning. Quick check: Without kernel examples, what errors appear? (Compilation failures, runtime mismatches, or "cheating" via high-level calls.)
- **Memory-based reinforcement learning (M-MDP):** Models synthesis as a long-horizon process with a dynamic memory context. Suitable because the policy factors into *retrieval* (what to show) and *generation* (how to write), allowing learning of retrieval strategies separately from the fixed LLM. Quick check: How does M-MDP differ from standard MDP? (Memory adds a dynamic context set; retrieval policy µ learns to optimize long-term reward.)
- **Stage-specific value functions:** Needed because objectives shift drastically: Stage 1 seeks *any* feasible solution (binary reward), Stage 2 seeks performance (continuous reward). A single Q-function would conflate these. Quick check: Why not encode stage in state sₜ? (Possible, but separate Q-tables simplify credit assignment and avoid value interference.)
- **Cross-task memory sharing for transfer:** Enables an emergent curriculum where simpler tasks provide foundational patterns for harder ones. Assumes reusable sub-skills (memory layouts, synchronization) are latent in memory and discoverable via value-driven retrieval. Quick check: Does transfer work if tasks are from different families? (Paper's out-of-distribution results suggest yes, but bounds are undefined.)

## Architecture Onboarding
- **Component map:**
  Task x -> Stage Controller -> Retrieval Policy µ (uses Q₁/Q₂) -> Generator Gθ (LLM) -> Verifier V -> Outcome oₜ / Reward rₜ -> Memory M (update Q via MC) & P(x) (feasible pool)
  Stage Controller switches from drafting (Q₁) to refining (Q₂) after first feasible kernel.
- **Critical path:**
  1. For task x, retrieve context cₜ via Q₁ (ϵ-greedy), generate kernel yₜ.
  2. Run V(x,yₜ) → oₜ. If feasible (g_feas=1), store (sₜ,aₜ,r₁,t) in M, add yₜ to P(x).
  3. Select start point pₜ ∈ P(x) via Q₂, retrieve refinement context cₜ (bottleneck-matched traces), generate refined yₜ.
  4. Compute r₂,t = tanh(log bₜ - log ℓ_lat(yₜ)), normalize online, update Q-values for pₜ and cₜ items.
  5. Repeat until iteration budget T=30 exhausted.
- **Design tradeoffs:**
  - Candidate pool size λ: Larger λ improves coverage (λ×15 boosted correctness from 67% to 84%) but adds noise/cost. Paper uses adaptive λ.
  - Stage switching: Hard switch after first feasible kernel is natural (binary correctness boundary); softening could mix objectives.
  - Q-value granularity: Global Q-tables across tasks enable cross-task transfer; per-task would limit sharing.
  - Normalization: Uses online normalization (PopArt-style) for r₂ but omits full PopArt rescaling, simpler but riskier if (µ,σ) shift.
- **Failure signatures:**
  - Anti-hacking failures: LLM generates binding code calling `torch.matmul` or uses constant folding → g_hack=0.
  - Stagnant Q-values: No correctness improvement after 10+ iterations indicates retrieval stuck in local optimum; consider increasing λ or resetting ϵ.
  - Performance regression: Latency reward negative despite correct kernels suggests profiling noise or Q₂ overfitting to early noise; check normalization stability (σ₂ floor).
  - Memory pollution: Failed attempts dominate memory if learning rate α too high; ensure failed drafts have negative reward and are filtered by Q₁ over time.
- **First 3 experiments:**
  1. Single-operator validation: Run EvoKernel on a simple L1 operator (e.g., `Tanh`) with T=30. Verify first feasible draft within 5–10 iterations, Q-values for successful templates increase, final latency beats reference.
  2. Q-value update sanity check: Instrument the MC update. For a retrieved item leading to success, confirm Q rises after r=+1; for failure, Q drops after r=-1. Check normalized rewards stay bounded |R₂| ≤ B.
  3. Cross-task transfer test: Pre-build memory on all L1 operators (30). Then run on a held-out L2 operator (e.g., `Conv3d HardSwish GroupNorm Meanfuse`). Measure time-to-first-correct vs. L2-scratch baseline; expect >10 iteration improvement.

## Limitations
- Proprietary LLMs (GPT-5.2, DeepSeek-V3.2) and unreleased code hinder reproducibility; key parameters (ε decay, λ) undisclosed.
- Value-driven retrieval assumes LLM in-context learning can exploit memories; risk of local optima if architecture mismatch is severe.
- Cross-task transfer lacks theoretical bounds; emergent curriculum may fail for highly divergent kernel families.
- Verifier correctness/latency noise could corrupt rewards; PopArt details are sparse, potentially causing normalization instability.

## Confidence
- **Cold-start solution**: High (empirical 11%→83% correctness gain on NPU benchmark).
- **Value-driven retrieval**: Medium (ablations support effectiveness but LLM reliance limits theoretical guarantees).
- **Cross-task memory sharing**: Medium (L1→L2 transfer shown, but transfer bounds undefined).
- **Overall pipeline robustness**: Medium-High (verifier-dependent; no reported catastrophic failures in paper).
