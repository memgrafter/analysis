# H2LooP Spark Preview: Continual Pretraining of Large Language Models for Low-Level Embedded Systems Code

## Quick Facts
- arXiv ID: 2603.11139
- Source URL: https://arxiv.org/abs/2603.11139
- Reference count: 20
- Primary result: Continual pretraining reduces in-domain perplexity by 70.4% and enables a 7B model to outperform larger frontier models in 8 of 13 embedded domains.

## Executive Summary
Large language models (LLMs) exhibit poor performance on low-level embedded systems code due to insufficient exposure to hardware-specific patterns. This paper presents H2LooP Spark Preview, a system that applies continual pretraining (CPT) to the 7B-parameter OLMo-3 model using a curated 23.5B-token corpus derived from repository-datasheet pairs processed via the SpecMap pipeline. Training with BF16 LoRA (rank 512, full-module coverage, rank-stabilized scaling) on 5.2B tokens (∼36% of one epoch) yields a 70.4% reduction in in-domain perplexity and a 66.1% reduction on a held-out repository test set. Generative evaluation across 13 embedded domains shows Spark surpassing Claude Opus 4.6 and Qwen3-Coder-30B in token accuracy in 8 categories, demonstrating that targeted CPT enables small open-weight models to rival frontier systems on specialized technical tasks.

## Method Summary
The authors construct a domain-specific pretraining corpus of 23.5B tokens from 818 repository-datasheet pairs spanning 117 hardware manufacturers using the SpecMap hierarchical mapping pipeline. This pipeline applies section-aware chunking, quality filtering (separator removal, repetition cleaning), and tokenization with a maximum sequence length of 2048 tokens, with samples assembled in strict order. Continual pretraining is performed on an 8×H100 GPU cluster using the OLMo-3-7B base model in BF16. Adaptation employs LoRA with rank r=512, alpha=1024, dropout=0.05, and rank-stabilized (RSLoRA) scaling, applied to all transformer modules (attention Q/K/V/O, MLP gate/up/down, embeddings, and LM head). The AdamW optimizer uses two learning rate groups: 1.5e-5 for adapters and 0.75e-5 for embeddings (0.5× multiplier), with a cosine schedule and 10% warmup. Training proceeds for approximately 45,000 steps, processing 5.2B tokens, with gradient clipping (max norm 5.0), packing efficiency near 95%, and a reported effective batch size of 256.

## Key Results
- In-domain perplexity reduced by 70.4% (4.06 → 1.20).
- Held-out repository perplexity reduced by 66.1% (3.92 → 1.33).
- In generative code completion across 13 embedded domains, Spark achieves higher token accuracy than Claude Opus 4.6 and Qwen3-Coder-30B in 8 categories.

## Why This Works (Mechanism)
The underperformance of general-purpose LLMs on embedded code stems from a lack of exposure to hardware-specific constructs, datasheet terminology, and low-level patterns. Continual pretraining on a large corpus of repository-datasheet pairs directly injects this specialized knowledge. The use of high-rank LoRA (r=512) with rank-stabilized scaling provides sufficient adaptation capacity while maintaining training stability; the scaling factor α/√r prevents gradient explosion that would occur with standard α/r at high ranks. Full-module targeting—including attention, MLP, and embeddings—ensures that all parts of the model can adjust to the new domain, which is critical for capturing nuanced hardware interactions. The section-aware chunking preserves contextual continuity, allowing the model to learn coherent code-spec relationships. The combination of these factors yields large perplexity reductions and superior token-level generation in embedded contexts, enabling a small model to compete with much larger frontier systems.

## Foundational Learning
- **Continual Pretraining (CPT)**: Further pretraining an already-trained model on a new domain to adapt it without catastrophic forgetting.  
  *Why needed*: Base LLMs lack domain-specific knowledge; CPT efficiently adds it while preserving general abilities.  
  *Quick check*: How does CPT differ from standard fine-tuning on labeled data?

- **LoRA (Low-Rank Adaptation)**: Inserts trainable low-rank matrices into frozen model weights to reduce trainable parameters.  
  *Why needed*: Enables efficient adaptation of large models with limited compute and memory.  
  *Quick check*: If LoRA rank is doubled, approximately how do trainable parameters change?

- **RSLoRA (Rank-Stabilized LoRA)**: Variant of LoRA that uses α/√r scaling instead of α/r to stabilize training at high ranks.  
  *Why needed*: Allows using high LoRA ranks (e.g., 512) without gradient explosions.  
  *Quick check*: What scaling factor does RSLoRA employ for a LoRA with α=1024, r=512?

- **Flash Attention**: An I/O-aware algorithm that speeds up attention computation and reduces memory usage.  
  *Why needed*: Supports long sequences (2048 tokens) with reasonable training throughput.  
  *Quick check*: What is the typical memory complexity benefit of flash attention compared to standard attention?

- **SpecMap**: A hierarchical mapping pipeline that pairs repository code with datasheets to create aligned training samples.  
  *Why needed*: Generates high-quality, domain-specific training data from raw hardware documentation and code.  
  *Quick check*: What are the two main inputs to SpecMap?

## Architecture Onboarding

Component map:
Data Collection (Repos + Datasheets) -> SpecMap Pipeline (Chunking, Filtering, Tokenization) -> Training Corpus (23.5B tokens) -> LoRA-adapted OLMo-3-7B -> Evaluation (Perplexity, Token Accuracy)

Critical path: The pipeline must preserve sample ordering and section boundaries during tokenization and packing to maintain the structural coherence needed for learning hardware-code mappings. Any deviation (e.g., shuffling) can break this coherence and harm performance.

Design tradeoffs:
- High LoRA rank (r=512) increases adaptation capacity but risks instability; mitigated by RSLoRA.
- Full-module tuning (including embeddings) improves performance at the cost of more memory and slower training.
- Processing only ~36% of an epoch trades completeness for faster experimentation; full training may yield further gains but requires more resources.
- BF16 precision balances speed and memory against numerical stability (requires gradient clipping).

Failure signatures:
- Gradient norm spikes >10 or NaN loss indicate too high learning rate or missing RSLoRA scaling.
- Sudden drop in tokens/sec (~35% or more) post-checkpoint suggests memory fragmentation (adjust PyTorch allocator).
- Final training loss >1.2 after 150 steps suggests insufficient LoRA rank, incomplete module targeting, or poor data ordering.
- Overly high loss plateau (e.g., >1.5) may indicate data pipeline errors (wrong tokenization, shuffling).

First experiments:
1. Verify data pipeline integrity: after parallel tokenization, check that sample indices are monotonic increasing and that packing efficiency is ≥90%. Inspect a few raw samples to confirm section delimiters are respected.
2. Run a short training trial (e.g., 100 steps) with the intended LoRA configuration (r=512, full-module, RSLoRA) on a small subset (100M tokens). Monitor loss: it should decrease from ~1.42 to ≈1.2 within 150 steps. Compare against an ablated run (e.g., attention-only) to confirm benefit of full-module tuning.
3. Check gradient statistics: compute the 95th percentile of post-clip gradient norms; it should be stable around 2-5. If it regularly exceeds 10, reduce learning rate by 2× and/or verify RSLoRA scaling is applied.

## Open Questions the Paper Calls Out

1. **Question**: What performance gains result from scaling CPT to the full 100B-token corpus (∼4.26 epochs) instead of the current ∼8.6B/23.5B tokens?  
   **Basis**: Future Work (Section 9) identifies completing training to 100B tokens as a priority, noting the reported results are from an early checkpoint.  
   **Why unresolved**: The trajectory of further training (diminishing returns, overfitting, or continued perplexity reduction on harder domains like Zephyr RTOS and crypto) remains unknown.  
   **Resolution evidence**: Full training run to 100B tokens with periodic evaluation on in-domain, held-out, and general code benchmarks.

2. **Question**: To what extent does Spark's high token accuracy translate into functionally correct, compilable embedded code, and which categories benefit most from compilation-based evaluation?  
   **Basis**: Limitations (Section 8.6) and Future Work (Section 9) explicitly note the absence of compilation-based evaluation.  
   **Why unresolved**: Token accuracy does not measure compilability, hardware constraints, or semantic correctness.  
   **Resolution evidence**: Integrate Spark with embedded toolchains (e.g., GCC for ARM) to automatically compile generated code, capture errors, and run hardware-in-the-loop or simulation tests across the 13 categories.

3. **Question**: Can instruction tuning of the Spark CPT checkpoint produce an effective chat-based coding assistant for embedded systems without sacrificing domain-specific performance?  
   **Basis**: Future Work (Section 9) lists instruction tuning for chat-based assistance as a planned direction.  
   **Why unresolved**: The current model is a raw completion model; instruction tuning may degrade specialized token predictions.  
   **Resolution evidence**: Apply a lightweight instruction-tuning stage (using synthetic or curated chat data) to the Spark checkpoint, then benchmark both tuned and base models on instruction-following and the original generative tasks.

4. **Question**: Do the hyperparameter findings—particularly high LoRA rank (r=512) and full-module targeting—generalize to other model architectures (e.g., Llama, Mistral, Qwen) for embedded systems CPT?  
   **Basis**: Future Work (Section 9) proposes extending the approach to other base models for comparison.  
   **Why unresolved**: The Bayesian sweep was conducted solely on OLMo-3-7B; architectural differences could shift optimal hyperparameters.  
   **Resolution evidence**: Replicate the rank/target/LR sweep on at least two other 7B-scale open models, measuring final loss, gradient stability, and downstream perplexity/accuracy.

5. **Question**: How can Spark be integrated into real-world embedded development workflows (e.g., via SpecMap) to provide automated specification adherence checking or driver synthesis, and does this improve developer productivity or code quality?  
   **Basis**: Future Work (Section 9) envisions integration with SpecMap for real-time compliance monitoring in CI/CD and downstream tasks.  
   **Why unresolved**: The paper only demonstrates isolated code generation; interactive or tool-augmented use cases remain unexplored.  
   **Resolution evidence**: Build a prototype using Spark to suggest code from datasheet inputs, embed it in a CI/CD pipeline to flag spec mismatches, synthesize drivers, and conduct user studies with engineers.

## Limitations
- The 23.5B-token curated training corpus is not publicly released, making exact data composition and quality unverifiable.
- The full training script, DDP/NCCL configuration, and memory optimizations are not provided, introducing hidden variables that could affect reproducibility.
- Evaluation protocol details (prompt construction, decoding hyperparameters, test split definitions) are inadequately described, limiting independent replication.

## Confidence
- **Claim**: LLMs underperform on embedded code due to insufficient hardware-specific pattern exposure.  
  **Confidence**: Medium (underperformance is measurable, but the causal claim is inferred rather than directly demonstrated).
- **Claim**: Continual pretraining reduces in-domain perplexity by 70.4%.

- **Claim**: The model surpasses Claude Opus 4.6 and Qwen3-Coder-30B in 8 of 13 domains.
