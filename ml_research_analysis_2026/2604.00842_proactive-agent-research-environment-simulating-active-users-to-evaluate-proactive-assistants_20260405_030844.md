# Proactive Agent Research Environment: Simulating Active Users to Evaluate Proactive Assistants
## Quick Facts
- arXiv ID: 2604.00842  
- Source URL: https://arxiv.org/abs/2604.00842  
- Reference count: 40  
- Primary result: Frontier LLMs achieve ~42% success on Pare-Bench; on‑device models reach ~3%, highlighting execution capability as the main bottleneck for on‑device deployment.

## Executive Summary
The paper addresses the gap in evaluating proactive assistants by introducing Pare, a simulation environment that models user interactions with stateful applications via finite state machines while giving assistants a privileged API. It includes the Observe‑Execute architecture to preserve user autonomy and a benchmark, Pare‑Bench, of 143 tasks across 10 apps. Evaluation of seven LLMs shows frontier models (Claude 4.5 Sonnet, Gemini 3 Flash) attain ~42% success, while smaller on‑device models (e.g., Gemma 3 4B) manage only ~3%. Claude stands out with a low proposal rate (12.8%) and high acceptance (78.2%). Robustness tests indicate that larger models maintain performance under tool failures and noise, whereas smaller ones degrade significantly.

## Method Summary
Pare models each app as a finite state machine (FSM) that constrains the user simulator’s actions to those available in the current state, while the assistant sees a flat, state‑independent API. The environment operates on a turn‑taking loop: the user acts first, then the assistant enters Observe mode (read‑only information gathering and optional proposal). If the user accepts the proposal, the assistant switches to Execute mode and performs multi‑step actions with full APIs. The benchmark, Pare‑Bench, comprises 143 scenarios seeded with an initial app state, a sequence of events, and an oracle validator. Noise (Poisson‑process spam) and tool failures can be injected to test robustness. Typically, runs use the assistant LLM paired with a user simulator (e.g., GPT‑5‑mini) for up to 10 turns, measuring success rate, proposal rate, acceptance rate, and number of read actions.

## Key Results
- Frontier models (Claude 4.5 Sonnet, Gemini 3 Flash) achieve success rates around 42%.
- On‑device models (e.g., Gemma 3 4B) reach only about 3% success.
- Claude 4.5 Sonnet exhibits a low proposal rate (12.8%) and high acceptance rate (78.2%).
- Robustness: larger models maintain performance under tool failures (40% failure probability) and noise (up to 6 events/min), while smaller models degrade significantly.

## Why This Works (Mechanism)
**Mechanism 1: Asymmetric agent–user interfaces**  
The simulation leverages a key asymmetry: the user simulator is restricted by the current state of the app’s finite state machine (FSM), allowing only state‑dependent actions, while the assistant agent has direct access to a flat, state‑independent API. The environment’s turn‑taking loop (user acts first, then assistant) routes notifications accordingly. This captures the real‑world scenario where users must navigate UI screens step by step, whereas an assistant can invoke backend functions directly. Break condition: If FSM graphs are incomplete or inaccurate, the simulation diverges from authentic user behavior, undermining evaluation validity.

**Mechanism 2: Observe‑Execute architecture with consent**  
The assistant operates in two phases. In Observe mode it performs read‑only information gathering and may send a proposal to the user via `send_message_to_user`. In Execute mode, after the user explicitly accepts the proposal (`accept_proposal`), the assistant performs multi‑step actions using full APIs. This propose‑and‑accept loop enforces user consent before any state‑changing action, preserving autonomy and reducing premature or erroneous interventions. Break condition: Insufficient context in the observation phase leads to high gather‑context rates and task truncation.

**Mechanism 3: Robustness through controlled disturbances**  
Scenarios can inject scheduled critical events, distractor notifications (via a Poisson process), and configurable tool failures. The assistant must therefore differentiate signal from noise and recover from partial failures, mimicking real mobile environments that are asynchronous, noisy, and error‑prone. Break condition: Unrealistic disturbance distributions (e.g., failure rates far from real usage) may limit transferability of robustness conclusions.

## Foundational Learning
**Finite State Machine (FSM) for user navigation** – *Why needed:* User actions are constrained by the current app state; understanding FSM transitions determines which actions are possible. *Quick check:* Given an Email app state diagram, what actions are available in the "Compose" state, and how does sending an email transition the state?

**Stackelberg POMDP formulation** – *Why needed:* The interaction is modeled as a Stackelberg leader–follower game where the user (leader) acts first and the assistant (follower) responds, framing proactive goal inference and intervention timing. *Quick check:* Why is the user the leader, and how does that affect the assistant’s observation space compared to a standard POMDP?

**Asymmetric observation and action spaces** – *Why needed:* The assistant sees full notifications and user actions; the user only sees truncated notifications and cannot see the assistant’s internal actions. This asymmetry simulates realistic information flow. *Quick check:* If the assistant proposes a task, through which interface does the user receive it, and what action(s) can the user take in response?

## Architecture Onboarding
Component map: User Agent (FSM‑constrained) -> Environment (turn loop, state database, event queue) -> Assistant Agent (Observe & Execute sub‑agents). The environment mediates all interactions and maintains shared memory between sub‑agents.

Critical path:
1. User executes an action determined by the FSM.
2. Environment updates state and notifies assistant with full details.
3. Assistant in Observe mode performs read‑only tool calls and decides to `wait` or `send_message_to_user`.
4. If a proposal is sent, the user subsequently calls `accept_proposal` or `reject_proposal`.
5. Upon acceptance, assistant switches to Execute mode and performs the plan with full APIs.
6. After execution or after max turns, an oracle validator checks success against scenario criteria.

Design tradeoffs:
- API‑level vs visual UI: API abstraction offers privacy and scalability but omits visual grounding; adding screenshots increases realism but raises privacy and compute costs.
- Symmetric vs asymmetric model deployment: Using the same model for observe and execute simplifies evaluation; a real deployment might use a small on‑device model for observation and a larger cloud model for execution, trading latency for capability.
- Turn budget: Limited turns (10) force a tradeoff between gathering sufficient context and intervening promptly; a higher budget may improve success but slow interaction.

Failure signatures:
- High proposal rate coupled with low acceptance → assistant intervenes too eagerly.
- Low number of read actions in Observe mode → insufficient context gathering, often correlates with low success.
- High `gather_context → truncation` rate → user needs more time but hits turn limit, indicating late or overly complex proposals.
- Large performance drop under tool failures or noise → lack of robustness, especially for smaller models.

## Limitations
- Exact model identifiers (e.g., "Claude 4.5 Sonnet") and the full set of 143 scenarios are not disclosed, preventing faithful replication.
- The FSM state graphs for the 10 apps may not capture all real‑world navigation paths, threatening ecological validity.
- The chosen noise and failure distributions are arbitrarily set and may not reflect actual smartphone usage statistics.

## Confidence
- Asymmetric agent‑user interface (FSM‑based user simulation): Medium  
- Observe‑Execute architecture with mandatory consent: Medium  
- Robustness evaluation via controlled noise/failures: Medium
