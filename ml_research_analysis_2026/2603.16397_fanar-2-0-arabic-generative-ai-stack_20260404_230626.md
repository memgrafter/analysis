# Fanar 2.0: Arabic Generative AI Stack

## Quick Facts
- arXiv ID: 2603.16397
- Source URL: https://arxiv.org/abs/2603.16397
- Reference count: 40
- Primary result: Fanar-27B (27B) outperforms Fanar 1.0 despite using 8× fewer training tokens, achieving +9.1 points on Arabic knowledge (MMMLU/Ar: 67.4), +7.3 on Arabic (ArabicMMLU: 74.7), +3.5 on dialects (Belebele: 86.8), and +7.6 on English (MMLU: 78.9).

## Executive Summary
Fanar 2.0 addresses the severe underrepresentation of Arabic in AI—where Arabic speakers (400M+) have only ~0.5% of web data—by building a sovereign Arabic generative AI stack at QCRI. Despite limited compute (256 H100 GPUs vs. frontier scales), it employs a quality-over-quantity strategy: continual pre-training of Gemma-3-27B on 120B carefully curated Arabic/English tokens across three recipes, followed by annealing and model merging. The resulting Fanar-27B sets new Arabic performance while maintaining strong English capabilities. The stack also includes a suite of culturally-aligned components: FanarGuard safety filter, Arabic long-form ASR, image generation (Oryx-IG), vision-language model (Oryx-IVU), bilingual translation, multi-agent Islamic QA, poetry generation, and an orchestrator.

## Method Summary
The core training pipeline involves three sequential "recipes" of data composition: (1) curated high-quality Arabic/English/code data (~50B tokens), (2) the same plus additional educational web data (~70B tokens), and (3) a translation-centric parallel dataset without code (~30B tokens). Each recipe runs for one epoch on 256 H100 GPUs with a peak learning rate of 1e-6, cosine decay to 5e-7, and 100-step warmup. After each recipe, an annealing phase processes 8B tokens with linear LR decay to zero. The final model merges checkpoints via linear interpolation: 0.6×(Recipe1 annealed) + 0.2×(Recipe2 annealed) + 0.2×(Recipe3 non-annealed). Data quality is enforced via multi-stage filters, including perplexity scoring with KenLM on Arabic Wikipedia and an ArabicWeb-Edu classifier.

## Key Results
- Arabic benchmarks: MMMLU/Ar +9.1 to 67.4, ArabicMMLU +7.3 to 74.7, Belebele +3.5 to 86.8.
- English (MMLU) +7.6 to 78.9.
- Outperforms Fanar 1.0 despite 8× fewer tokens (120B vs ~1T).

## Why This Works (Mechanism)
The gains stem from a targeted quality-over-quantity approach. Curated high-quality data reduces noise and cultural misalignment, while the three-recipe structure systematically exposes the model to diverse but clean Arabic contexts (general, educational, parallel translation). Annealing stabilizes learning and prevents overfitting to any single recipe, especially benefiting Arabic. The merging step combines complementary strengths: Recipe1 provides strong foundational knowledge, Recipe2 adds educational depth, and Recipe3 contributes cross-lingual alignment, with annealing preserving Arabic gains. This pipeline maximizes performance within strict compute and token budgets.

## Foundational Learning
1. **Continual Pre-training**  
   - *Why needed*: To adapt a base model (Gemma-3-27B) to Arabic without full pre-training from scratch, saving compute.  
   - *Quick check*: Explain how gradient accumulation and learning rate schedules differ between initial pre-training and continual pre-training.
2. **Data Curation for Low-Resource Languages**  
   - *Why needed*: Arabic is underrepresented; high-quality, culturally relevant data is critical to avoid bias and degrade.  
   - *Quick check*: List three linguistic or cultural artifacts that might be missing from generic web corpora and need explicit inclusion for Arabic.
3. **Annealing (LR decay to zero)**  
   - *Why needed*: To fine-tune the model onto the final data distribution without disrupting previously learned representations, particularly for Arabic.  
   - *Quick check*: How does annealing differ from a standard cosine decay that ends at a small learning rate?
4. **Model Merging (Linear Interpolation)**  
   - *Why needed*: To combine checkpoints trained on different data recipes into a single model with balanced capabilities.  
   - *Quick check*: What are the risks of linear interpolation (e.g., mode collapse) and how might alternative methods (TIES, SLERP) mitigate them?
5. **Multilingual Training with Code Mixing**  
   - *Why needed*: Including code (10% in recipes 1 & 2) helps maintain model general reasoning and prevents English-only overfitting.  
   - *Quick check*: Why might code tokens be beneficial even for a primarily Arabic model?
6. **Arabic NLP Specifics**  
   - *Why needed*: Arabic has dialectal variation, diglossia, and rich morphology; tokenization and evaluation must account for this.  
   - *Quick check*: What are the main challenges in evaluating Arabic language models with MCQ benchmarks like MMLU?

## Architecture Onboarding
**Component Map**:  
Gemma-3-27B (base) → Fanar-27B (pre-trained) → downstream components: FanarGuard (safety filter), Oryx-IG (image generation), Oryx-IVU (vision-language QA), Arabic long-form ASR, bilingual translation, multi-agent Islamic QA, poetry generation, Orchestrator (routing). Data flow: curated corpora → pre-training pipeline → merged Fanar-27B → fine-tuned/adapted for each task.

**Critical Path**: The end-to-end training pipeline is the critical path: data curation (3 recipes) → distributed pre-training (256 H100) → per-recipe annealing → checkpoint merging → final model release. Downstream components depend on the final model but can be developed in parallel.

**Design Tradeoffs**:  
- *Quality vs. Quantity*: Using only 120B tokens vs. Fanar 1.0's ~1T reduces compute but risks insufficient coverage; mitigated by meticulous curation.  
- *Compute Constraints*: 256 H100 GPUs limit batch size and training speed; necessitated efficient NeMo implementation and moderate context (32K).  
- *Merging Strategy*: Linear interpolation is simple but may not preserve all capabilities; weighting favors Recipe1 (0.6) to anchor Arabic knowledge.  
- *Language Balance*: 45%/45%/10% (Arabic/English/code) in first two recipes maintains English and coding skills; Recipe3 is 50%/50% to boost translation alignment.

**Failure Signatures**:  
- Arabic benchmark scores (MMMLU/Ar, ArabicMMLU) plateau or decline during training, indicating poor data quality or overfitting to English.  
- English MMLU drops significantly (>1 point) after merging, suggesting imbalance in interpolation weights.  
- Safety filter (FanarGuard) fails to block harmful prompts in Arabic dialects, revealed by red-teaming.  
- Vision components (Oryx-IVU) show high code-switching or inaccurate Arabic descriptions in generation.

**First 3 Experiments**:  
1. **Data Curation Sanity Check**: Apply the described KenLM perplexity filter (Arabic Wikipedia) and ArabicWeb-Edu classifier to a sample of FineWeb-EDU; measure Arabic token retention rate and compare to paper's implied ratios.  
2. **Small-Scale Recipe Trial**: Train a 1B-parameter model on Recipe1 only for one epoch (no annealing) and evaluate on a subset of OALL-v2 to confirm that the data recipe improves Arabic knowledge relative to a random mix.  
3. **Merge Sensitivity Test**: Take the three full checkpoints (R1+A, R2+A, R3) and perform linear merges with varying weights (e.g., [0.5,0.3,0.2], [0.7,0.2,0.1]) and evaluate Arabic/English trade-offs to validate the chosen 0.6/0.2/0.2 weighting.

## Open Questions the Paper Calls Out
1. **Scaling Limits of Quality-over-Quantity**  
   - *Basis*: Paper notes ceiling of continual pre-training on small token budget and calls for larger high-quality corpus.  
   - *Unresolved*: Trade-off between curation cost and gains from scaling to 2×–10× token budget not stress-tested; unknown if merging remains optimal.
2. **Causal Contribution of Pipeline Components**  
   - *Basis*: Paper evaluates pipeline as whole; shows annealing helps Arabic and merging yields gains beyond single checkpoint.  
   - *Unresolved*: Without ablations isolating each recipe's data mix, annealing per recipe, and merging method, the synergy is unclear; limits future design.
3. **Cultural Alignment Evaluation Validity**  
   - *Basis*: Oryx-IG uses Gemini as judge; paper acknowledges human references vary in punctuation.  
   - *Unresolved*: No human evaluation to verify if Gemini's judgments align with native Arabic speakers; risk of optimizing for judge's biases.
4. **MCQ vs. Generative Evaluation Gap**  
   - *Basis*: Oryx-IVU notes MCQ accuracy masks differences in faithfulness, Arabic fluency, and cultural phrasing.  
   - *Unresolved*: Underlying cause (factual vs. compositional) not investigated; impedes benchmark design.
5. **Multi-turn Safety Robustness**  
   - *Basis*: Summary states Fanar 2.0 safety evaluation is single-turn; Fanar 3.0 will focus on multi-turn.  
   - *Unresolved*: Defense-in-depth (FanarGuard, Sadiq) may fail in extended dialogues with gradual jailbreaking; no adversarial multi-turn benchmark.

## Limitations
- **Data reconstruction**: Exact token counts, precise language ratios, and source lists per recipe are undisclosed; replication requires inferring from principles and cited corpora.
- **Filter thresholds**: Quantitative thresholds for perplexity and ArabicWeb-Edu classifier are unspecified, risking inconsistent data quality.
- **Hyperparameter gaps**: Global batch size, sequence length, and warmup steps are not provided; must be inferred from typical 27B settings.
- **Performance confidence**: Self-reported without independent audit; few-shot setup details missing.
- **Data curation efficacy**: No verification that reconstructed filters achieve claimed quality; potential residual noise or bias.

## Confidence
- **Performance claims (MMMLU/Ar, ArabicMMLU, Belebele, MMLU)**: Medium (self-reported, no external validation).
- **Training pipeline (recipes, annealing, merging)**: High (explicitly described, though some hyperparameters inferred).
- **Data curation efficacy**: Low (no quantitative filter thresholds, no verification of output quality).
- **Downstream component claims (FanarGuard, Oryx-IG, etc.)**: Low to Medium (evaluated with LLM-as-judge, no human validation for cultural alignment).
