# Code2World: A GUI World Model via Renderable Code Generation
## Quick Facts
- arXiv ID: 2602.09856
- Source URL: https://arxiv.org/abs/2602.09856
- Reference count: 40
- Primary result: Code2World-8B achieves state-of-the-art next UI prediction, rivaling GPT-5 and Gemini-3-Pro-Image, with top scores on Android Control and robust OOD generalization.

## Executive Summary
Code2World introduces a novel GUI world model that predicts the next UI state by generating renderable HTML code, decoupling structural control from visual rendering. The model is trained on AndroidCode, a dataset of 80K+ high-fidelity screen-action pairs created using GPT-5 with a visual-feedback revision loop to ensure pixel-level alignment. A two-stage training pipeline first applies supervised fine-tuning (SFT) to learn HTML syntax, then uses Render-Aware Reinforcement Learning (RL) with dual rewards—visual semantic fidelity and action consistency—derived from VLM judges. Code2World-8B attains state-of-the-art performance on next UI prediction benchmarks, surpassing large proprietary models like GPT-5 and Gemini-3-Pro-Image on Android Control metrics (e.g., Action Adherence 94.28). It also serves as an effective simulator, improving downstream agent navigation success rates on AndroidWorld by 9.5%. Ablations confirm that both SFT and the dual-reward RL are essential for high performance.

## Method Summary
Code2World formulates GUI state transition as predicting the next screen’s HTML code given the current screenshot, action, and goal. The predicted code is deterministically rendered by a browser engine to produce the visual output. The core innovation lies in using renderable code as the world model’s output, which provides both structural control and high visual fidelity. Training data (AndroidCode) consists of over 80K high-quality screen-action pairs. Synthesis starts with GPT-5 generating HTML code for a target UI change; the code is rendered and compared to the ground truth screenshot using SigLIP. If similarity falls below 0.9, GPT-5 is prompted with visual feedback to revise the code. This revision loop ensures pixel-level alignment. The model (Qwen3-VL-8B backbone) undergoes two-stage training: first, supervised fine-tuning (SFT) on the token-level HTML sequences to learn layout syntax; second, Render-Aware Reinforcement Learning (RL) using Group Relative Policy Optimization (GRPO). RL optimizes a combined reward from two VLM judges: one evaluates visual semantic fidelity (R_sem), the other assesses action consistency (R_act). A KL penalty keeps the policy close to the SFT model. During inference, the model generates multiple candidate codes, renders them, and selects the one with highest reward, enabling simulation for downstream planning.

## Key Results
- Code2World-8B sets new SOTA on Android Control, achieving 94.28 on Action Adherence and 88.64 on Action Identifiability, outperforming large proprietary models (GPT-5, Gemini-3-Pro-Image).
- As a plug-and-play world simulator, it improves navigation success rates of Gemini-2.5-Flash on AndroidWorld by +9.5%.
- Ablation studies demonstrate that both the SFT stage and the dual-reward RL are critical for high performance; removing either leads to significant drops.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Renderable code generation (HTML) simultaneously achieves high visual fidelity and fine-grained structural controllability by decoupling *what* to render from *how* to render it.
- **Mechanism:** The world model predicts structured HTML code (`C_{t+1}`) instead of raw pixels. This symbolic output is then deterministically rendered (`R(C_{t+1})`) by a browser engine. The code’s explicit DOM tree guarantees structural integrity (element containment, positioning, text content), while the renderer translates this structure into a pixel-accurate screenshot.
- **Core assumption:** A browser rendering engine is a perfect, lossless transducer from HTML/CSS to pixels for the relevant UI component set. The fidelity of the final visual state (`I_{t+1}`) is therefore entirely determined by the correctness of the generated code.
- **Evidence anchors:**  
  [abstract] "symbolic code inherently guarantees structural controllability while enabling high-fidelity visualization via deterministic rendering."  
  [section 3] "We define the state transition as a two-step conditional generation process: `ˆCt+1 =Mθ(It, at,G), ˆIt+1 =R( ˆCt+1)` where ... the predicted visual representation ˆIt+1 is obtained deterministically via a browser rendering engine R."  
  [corpus] Neighbors like *ViMo* and *GEBench* also explore generation-based world models but use pixel-space or abstract sketches, confirming the trade-off Code2World addresses. Corpus signal strength is moderate (avg FMR 0.506).
- **Break condition:** If the rendering engine (`R`) introduces non-determinism or if the HTML/CSS standard subset used is insufficient to express a target UI's visual style (e.g., complex custom shaders), the decoupling fails and visual fidelity drops regardless of code correctness.

### Mechanism 2
- **Claim:** The two-stage training (SFT → Render-Aware RL) is necessary to align a general-purpose VLM's textual generation capabilities with the specialized objective of producing code that renders correctly.
- **Mechanism:** Stage 1 (SFT) provides a "cold start" by teaching the model the syntactic format and basic spatial logic of HTML/UI construction via token-level supervision (`C*`). Stage 2 (Render-Aware RL) shifts the optimization objective from token likelihood to the *rendered outcome* using dual rewards (`R_sem`, `R_act`) derived from the rendered image. This bridges the gap between the textual code space and the visual reality the code must produce.
- **Core assumption:** The VLM backbone (Qwen3-VL-8B) possesses latent knowledge of UI semantics and HTML syntax but lacks instruction-following precision for this specific task. SFT activates this latent knowledge, and RL finetunes it based on a differentiable (via policy gradient) visual feedback signal.
- **Evidence anchors:**  
  [section 3.2] "To adapt existing VLMs into code prediction, we first perform SFT as a cold start for format layout following, then further apply Render-Aware Reinforcement Learning... This strategy integrates dual outcome rewards to align the model with visual reality and action consistency."  
  [table 3] Ablation shows SFT alone improves base model metrics significantly (e.g., `Sad` 59.20 → 78.45, `Sele` 43.10 → 58.65), but RL is needed for top-tier visual (`Sele` 71.35) and logic (`Sad` 94.28) scores.  
  [figure 6] Adding RL components sequentially yields incremental SR gains, proving their complementary roles.
- **Break condition:** If the SFT stage fails to produce a policy that generates *syntactically valid and parsable* HTML (e.g., unclosed tags, malformed DOM), the renderer (`R`) will produce a broken or empty image. The RL reward signal then becomes meaningless noise, preventing convergence.

### Mechanism 3
- **Claim:** The visual-feedback revision loop in AndroidCode construction is critical for achieving high data quality (SigLIP > 0.9), which is necessary for training a high-fidelity world model without requiring prohibitively expensive human annotation.
- **Mechanism:** Initial GPT-5 synthesis produces code. This code is rendered (`R(C)`), and its visual similarity to the ground truth screenshot is computed (`SigLIP( R(C), I )`). If below a threshold (τ=0.9), the multimodal coder is prompted with the GT image, the rendered image, and the flawed code. It must *visually compare* and *revise*. This creates a self-correcting data curation pipeline that enforces pixel-level alignment.
- **Core assumption:** A powerful multimodal model (GPT-5) can serve as an effective "visual debugger" when given direct image comparison context, and that a SigLIP score > 0.9 is a sufficient proxy for "high-fidelity" training data for the purpose of learning UI dynamics.
- **Evidence anchors:**  
  [section 3.1] "to ensure data quality, we implement a selective revision mechanism with visual feedback... This mechanism effectively forces the model to revise its own output based on visual evidence, ensuring that AndroidCode maintains high fidelity."  
  [algorithm 1] Explicitly defines the revision loop with threshold τ=0.9 and max iterations N_max=1.  
  [section A.2] Details the `Prompt_revision` instructing the model to diagnose and fix mismatches in order of priority.
- **Break condition:** If the visual similarity metric (SigLIP) is poorly correlated with human judgment of UI correctness for the specific renderable code paradigm (e.g., penalizing valid semantic placeholders), the filter will reject correct samples or accept incorrect ones. The paper's custom `R_sem` VLM-judge suggests SigLIP alone is insufficient for final reward, implying the data filter's choice of τ is a heuristic.

## Foundational Learning
### Concept 1: Renderable Code Generation
Why needed here: It is the core paradigm shift. The engineer must understand that the output is not a "description" but an *executable specification* for a renderer. Debugging requires inspecting the rendered output, not just the code string.
Quick check question: If your generated HTML looks correct to the VLM judge but renders to a broken page, what is the most likely point of failure in the pipeline?

### Concept 2: VLM-as-a-Judge for Multimodal Rewards
Why needed here: Standard image metrics (SigLIP, DINO) fail to capture functional logic (`Action Adherence`) and are brittle to the paper's intentional "semantic placeholder" strategy. A VLM is used to provide dense, qualitative rewards based on high-level understanding.
Quick check question: Why can't a simple pixel-difference loss (L1) between `R(C)` and `I*` be used as the sole reward for RL?

### Concept 3: Group Relative Policy Optimization (GRPO)
Why needed here: It's the specific RL algorithm used. It estimates the baseline from a group of sampled outputs for the same prompt, avoiding the need for a separate value network and enabling stable reward-based updates with the dual-reward signal.
Quick check question: In GRPO's advantage calculation `Ai = (R - group_mean) / group_std`, what would happen if the group size `G` was set to 1?

## Architecture Onboarding
### Component map
Input Encoder -> Multimodal Fusion -> Policy Network -> Render Engine -> Reward Extractor -> RL Optimizer

### Critical path
Data Construction (AndroidCode) → SFT Training (teach format) → GRPO Loop (sample `G` codes → render → judge → compute `R_total` → policy update). The path must flow from *data that enforces visual alignment* to *a policy that optimizes for it*.

### Design tradeoffs
- **HTML Expressivity vs. Rendering Simplicity**: Using a restricted CSS subset and semantic placeholders ensures deterministic rendering but limits the model's ability to mimic exact photographic textures. This is a conscious trade-off for structural correctness.
- **Reward Complexity vs. Training Stability**: Using two VLMs as judges provides nuanced feedback but introduces significant computational overhead (running two extra large models per sample) and potential judge inconsistency. The paper weights them equally (`λ1 = λ2`), a simplifying assumption.
- **Data Scale vs. Quality**: The revision loop (`N_max=1`) prioritizes efficiency over exhaustiveness. Some low-quality samples might slip through, while some high-quality ones might be discarded if the SigLIP threshold is too strict.

### Failure signatures
- **High `R_sem` but Low `S_ad`**: Model generates visually pleasing but logically incorrect pages (e.g., clicking "Back" stays on same page). Reward hacking on pixel similarity.
- **Low `R_act` despite decent code**: The model understands layout but not action consequences (e.g., typing text does not update the input field).
- **High variance in group rewards during GRPO**: The policy isn't exploring diverse enough structural solutions, or the VLM judges are inconsistent.
- **Rendered output (ˆI_{t+1}) has blank regions or broken layout despite syntactically valid code**: Indicates the CSS subset or placeholder strategy in SFT was insufficient; the model learned syntax but not rendering rules.

### First 3 experiments
1. **SFT Sanity Check**: Train only on AndroidCode with standard token loss. Manually render 50 samples. Check for: valid HTML, basic layout accuracy, placeholder usage. Expect: mostly correct structure but logical/visual flaws.
2. **Single-Reward RL Ablation**: Take the SFT model and run GRPO with only `R_sem`. Measure change in `Sele` and `S_ad`. Expect: `Sele` improves, `S_ad` stagnates or drops (reward hacking).
3. **Single-Reward RL Ablation (Action)**: Take the SFT model and run GRPO with only `R_act`. Measure change in `S_ad` and `Sele`. Expect: `S_ad` improves significantly, `Sele` improves moderately.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: Does Code2World maintain high fidelity in multi-step rollouts, or does error accumulate over time when predictions are chained?
- Basis in paper: [inferred] The evaluation protocol (Section 4.1 and 5.1) measures only single-step next UI prediction; multi-step simulation is not addressed. The “Propose, Simulate, Select” application (Section 4.2) uses single-step foresight for action pruning, implicitly assuming that one-step predictions are sufficient and accurate enough to avoid compounding errors during long-horizon planning.
- Why unresolved: Long-horizon navigation tasks (e.g., AndroidWorld) require sequential decisions; if the world model drifts after several steps, agents may follow erroneous plans. Without explicit multi-step validation, the robustness of Code2World as a long-term simulator remains unknown.
- What evidence would resolve it: An experiment where the model generates a sequence of predicted screens (e.g., 5–10 steps) conditioned on a sequence of actions, and metrics compare the cumulative predicted trajectory against real trajectories. Analysis could track fidelity decay or identify failure modes.

### Open Question 2
- Question: How dependent is Code2World’s performance on the choice of VLM-as-a-Judge for rewards and evaluation, and could biases in the judge affect reported results?
- Basis in paper: [explicit] The Render-Aware RL (§3.2) and evaluation metrics (§4.1, Appendix D) rely on a VLM judge (Qwen3-VL-8B-Instruct) to provide semantic and logical scores. The paper does not investigate robustness to different judges or alternative assessment methods.
- Why unresolved: VLMs can exhibit systematic biases or misjudgments in nuanced UI semantics. If the judge’s notion of “visual fidelity” or “action consistency” diverges from human judgment, both training rewards and reported metrics may be misleading. The reliability of the entire framework hinges on the judge’s objectivity.
- What evidence would resolve it: Conduct a study using multiple VLM judges (e.g., different architectures, sizes) and/or human annotators to correlate scores. A sensitivity analysis would reveal variations; consistency across judges would validate the approach.

### Open Question 3
- Question: Can the visual-feedback revision pipeline for constructing AndroidCode be effectively performed with smaller, open-source models instead of GPT-5, and would the resulting dataset still yield a high-performing Code2World?
- Basis in paper: [inferred] The data synthesis (Section 3.1) uses GPT-5 for initial generation and revision. The cost and accessibility of GPT-5 are not discussed; the paper does not explore whether cheaper, publicly available models can achieve comparable data quality.
- Why unresolved: If GPT-5 is essential, the approach may not be reproducible or scalable for broader research. Understanding the trade-off between model capability and dataset quality is crucial for democratizing code-based world models.
- What evidence would resolve it: Replace GPT-5 in the pipeline with models like Qwen3-VL-8B or Claude-4.5-Sonnet while keeping the revision loop. Compare the resulting dataset (e.g., pass rates, visual alignment scores) and the final performance of Code2World trained on each variant.

### Open Question 4
- Question: Does Code2World generalize beyond Android apps to other GUI paradigms such as desktop web browsers, iOS, or emerging platforms like foldable/AR interfaces?
- Basis in paper: [inferred] The training and evaluation datasets are derived from AndroidControl and AndroidWorld. The paper claims “general-purpose world model” capabilities, but all benchmarks are Android-centric. GUI Odyssey provides some cross-app variation but remains within the mobile Android ecosystem.
- Why unresolved: Different platforms use distinct UI toolkits, interaction patterns, and screen geometries. Success on Android does not guarantee transfer to, e.g., desktop webpages with complex CSS layouts or iOS with different design languages. The unstated assumption that the learned dynamics are platform-agnostic requires validation.
- What evidence would resolve it: Collect a representative dataset from diverse platforms (e.g., RICOH, WebArena, iOS screenshots), convert them to renderable HTML (or another consistent representation), and evaluate Code2World in zero-shot or few-shot settings. Performance drop-offs would quantify the need for platform-specific adaptation.

## Limitations
- Data synthesis pipeline uses GPT-5 with unreported settings and a SigLIP threshold tuned for a specific checkpoint; replicating with open-source models may degrade dataset quality.
- Evaluation metrics and RL rewards depend on VLM judges with incompletely specified prompts, leading to potential inconsistencies and bias.
- The paper does not provide explicit train/test splits, which may lead to inadvertent data leakage and overestimation of OOD generalization.

## Confidence

- Renderable code paradigm: Medium
- Visual-feedback revision pipeline: Medium
