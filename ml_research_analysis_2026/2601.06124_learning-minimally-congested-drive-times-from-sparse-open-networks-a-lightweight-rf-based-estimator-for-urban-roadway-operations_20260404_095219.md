# Learning Minimally-Congested Drive Times from Sparse Open Networks: A Lightweight RF-Based Estimator for Urban Roadway Operations

## Quick Facts
- **arXiv ID:** 2601.06124  
- **Source URL:** https://arxiv.org/abs/2601.06124  
- **Reference count:** 12  
- **Primary result:** A random forest model using only sparse OpenStreetMap data reduces mean absolute percentage error (MAPE) for minimally-congested travel time prediction from 21.15% (naive Dijkstra baseline) to 8.41%, with no significant mean bias.

## Executive Summary
Accurate travel time prediction often relies on either data-hungry deep learning models or overly simplistic heuristics that systematically underestimate times. This paper introduces a lightweight random forest estimator that bridges this gap. It computes a baseline traversal time via Dijkstra’s algorithm using speed limits, then corrects it using operational features extracted from open data—counts of traffic controls (signals, stops, crossings, yields, roundabouts) and turning movements along the route. Validated on 41,378 origin-destination pairs in Los Angeles during minimally-congested conditions (3:00 AM), the model achieves a MAPE of 8.41% and an R² of 0.93 on a held-out test set, significantly outperforming the naive baseline (MAPE 21.15%) and other machine learning algorithms. The approach offers a practical, interpretable solution for metropolitan-scale travel time estimation without requiring proprietary sensors or complex neural architectures.

## Method Summary
The method begins by ingesting the drivable, strongly connected subgraph of the Los Angeles road network from OpenStreetMap via OSMnx. For each origin-destination pair, a baseline path and traversal time are computed using Dijkstra’s algorithm with edge weights derived from road length and posted speed limits. Along this path, the system counts five types of traffic controls and classifies turning movements at intermediate nodes based on bearing changes into five categories (e.g., left, slight right, U-turn). Ground-truth travel times for the same OD pairs are collected from the Google Maps Routes API at 3:00 AM to represent minimally-congested conditions. A random forest regressor is then trained to predict the actual travel time, either directly or as a correction to the naive baseline, using these sparse operational features. Hyperparameters (400 trees, max depth 10) are tuned via 5-fold cross-validation, minimizing mean absolute error.

## Key Results
- The random forest model reduces MAPE from 21.15% (naive Dijkstra) to 8.41% and MAE from 183.68s to 75.32s on the test set.
- Model R² improves from 0.74 to 0.93, with negligible mean bias (δ = 0.38s).
- Gradient boosting yields a slightly lower MAPE (7.86%) but introduces significant under-prediction bias (δ = –19.2s).
- Five-fold cross-validation shows consistent MAE (73.2–75.3s), indicating robust performance and minimal overfitting.

## Why This Works (Mechanism)
The naive Dijkstra baseline underestimates actual travel time because it assumes vehicles travel at speed limits continuously, ignoring mandatory delays at intersections. This creates a consistent negative bias, which the model corrects by learning a mapping from sparse operational features to the missing time penalty. Features like traffic signal counts and turn type frequencies serve as proxies for the frequency and severity of deceleration, stopping, and turning maneuvers. Even without precise signal timing or queue lengths, these counts are sufficiently correlated with cumulative delay to enable accurate correction. The random forest algorithm is well-suited to this task: its ensemble structure reduces variance inherent in single decision trees, while its nonlinear splits capture interactions between features (e.g., a signal on a short segment versus a long one). Its robustness to outliers and missing values accommodates the inherent sparsity and heterogeneity of open-source GIS tags.

## Foundational Learning
- **Concept: Traversal Time as a Baseline**  
  *Why needed:* The entire correction method is anchored to a physically interpretable baseline (Dijkstra with speed limits). Understanding its limitations—ignoring intersection delays—is key to grasping why correction is necessary.  
  *Quick check:* Why does a shortest-path calculation based on speed limits still under-predict travel time in a city?

- **Concept: Feature Engineering from Network Topology**  
  *Why needed:* Open data lacks direct delay measurements. The method invents predictive features (control counts, turn categories) from the graph structure to expose latent causes of the baseline’s error. This translation from raw GIS data to features is the core innovation.  
  *Quick check:* How would you derive “number of left turn maneuvers” from a sequence of road segment nodes in a path?

- **Concept: Ensemble Learning for Robustness with Sparse Data**  
  *Why needed:* Single models (e.g., a deep tree) would overfit to noise and sparsity in open-source feature data. Ensembles like random forest average out this instability, providing a better bias-variance trade-off for limited datasets.  
  *Quick check:* What is the primary statistical reason an ensemble of trees typically has lower variance than a single deep decision tree?

## Architecture Onboarding
- **Component map:**  
  Network Ingestion -> Baseline Solver -> Feature Extractor -> Reference Data Collector -> Model Trainer/Predictor

- **Critical path:**  
  Ingest OSM network -> compute Dijkstra path -> extract operational features along that path -> collect Google API ground truth times -> train random forest model.

- **Design tradeoffs:**  
  - **Accuracy vs. Data Cost:** Google API provides accurate reference times but is costly and rate-limited; the model aims to replace future API calls.  
  - **Feature Simplicity vs. Expressiveness:** Using only counts of 5 controls and 5 turn types is lightweight but misses nuances like signal coordination or turn lane existence; adding more risks overfitting on sparse OSM tags.  
  - **RF vs. GB:** RF chosen for lower bias and stability; GB had lower MAPE but significant under-prediction bias, possibly from aggressive regularization on noisy sparse features.

- **Failure signatures:**  
  - High residual error on validation set, especially if correlated with a specific feature (e.g., many signals), suggesting inadequate feature encoding.  
  - Large discrepancy between cross-validation folds, indicating overfitting to specific network topologies or unstable feature extraction.  
  - Model predicts negative travel times, a catastrophic failure requiring checks on feature scaling and baseline positivity.

- **First 3 experiments:**  
  1. Reproduce baseline bias: Compute naive Dijkstra times for a sample of OD pairs against reference; confirm systematic under-prediction (~–183s).  
  2. Feature sanity check: Manually trace a route on a map, count signals/stops/turns, and compare to automated extractor output.  
  3. Model sanity check – single tree: Train a shallow decision tree (depth=3) and visualize splits; confirm it first splits on `t_naive`, then on `signal_count`, etc.

## Open Questions the Paper Calls Out
- How does the model's accuracy degrade under peak congestion, and can minimal additional reference data enable coarse temporal differentiation (e.g., peak vs. off-peak)?
- To what extent can integrating other open data sources (e.g., crowd-sourced traffic speeds, public transit schedules, weather) measurably improve prediction accuracy without sacrificing the method's lightweight, open-data ethos?
- Can machine learning imputation effectively recover missing or sparse traffic control data (e.g., unmapped signals) in OpenStreetMap to maintain model performance in regions with poor tagging completeness?
- What transfer learning or regional calibration techniques allow a model trained on a data-rich city (e.g., Los Angeles) to achieve comparable accuracy in a new urban context with only minimal local reference travel times?
- Does the model's reliance on a Dijkstra shortest-path (minimizing traversal time) as the baseline introduce a structural bias when the Google API's fastest route differs, and can this be mitigated by incorporating path dissimilarity features?

## Limitations
- Study area definition and OD filtering rely on undocumented Uber Movement thresholds, hindering exact replication.
- Ground truth travel times come from Google Maps API (“BESTGUESS”), a proprietary model whose own errors may bias evaluation.
- OSM tag completeness for traffic controls varies widely; sparse or missing tags could weaken feature signal in other regions.
- Evaluation confined to Los Angeles; no evidence of generalizability to cities with different intersection designs or data quality.

## Confidence
- Systematic baseline underestimation (Dijkstra ignores intersection delays): **Medium**
- Sparse operational features are predictive: **Medium**
- Random Forest optimally balances bias-variance: **Medium**
- Overall performance (MAPE ~8.4%): **High**

## Next Checks
1. Cross-city generalization test: Replicate the entire workflow in a city with different OSM tagging density (e.g., New York) and report metric changes.
2. Ablation of operational features: Retrain the model after removing traffic-control counts or turn-movement categories to isolate each group's marginal contribution.
3. Independent ground-truth validation: Obtain travel times from a third source (e.g., GPS probe data) to verify that the Google-based reference is not introducing systematic bias.
