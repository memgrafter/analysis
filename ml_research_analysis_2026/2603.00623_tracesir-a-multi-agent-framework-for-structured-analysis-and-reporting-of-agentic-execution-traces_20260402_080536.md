# TraceSIR: A Multi-Agent Framework for Structured Analysis and Reporting of Agentic Execution Traces

## Quick Facts
- **arXiv ID:** 2603.00623
- **Source URL:** https://arxiv.org/abs/2603.00623
- **Reference count:** 22
- **Primary result:** TraceSIR significantly outperforms ClaudeCode in generating diagnostic reports from agent execution traces, with average improvements of 9.7% (human eval) and 7.5% (LLM judge), and shows particular strength in error analysis, root cause analysis, and optimization analysis.

## Executive Summary
TraceSIR is a multi-agent framework designed to diagnose failures in complex agentic systems by analyzing long execution traces. It addresses the challenge of processing verbose, unstructured logs through a three-stage pipeline: StructureAgent compresses raw traces into a structured `(thought, action, observation)` format while preserving behavioral semantics; InsightAgent performs fine-grained diagnosis, localizing errors, identifying root causes, and suggesting optimizations; ReportAgent aggregates insights across multiple traces to produce coherent, evidence-grounded reports. Evaluated on TraceBench—150 failure cases from deep research, function calling, and agentic coding scenarios—using the ReportEval protocol, TraceSIR consistently generates more informative and actionable reports than prior methods.

## Method Summary
The framework processes traces in a staged manner. First, StructureAgent parses OpenAI-format message logs into sequential `(thought, action, observation)` rounds and applies length-aware compression to verbose fields, yielding a compact `TraceFormat` that retains causal alignment. Next, InsightAgent consumes this structured trace and task description, invoking internal analysis tools to produce a diagnostic bundle containing a completion score, categorized error labels, identified weaknesses, root causes, and concrete optimization suggestions (including fine-tuning samples). Finally, ReportAgent aggregates multiple diagnostic bundles, estimates error frequency and score distributions, and synthesizes a Markdown report that links conclusions to specific trace IDs and appends raw trace data for traceability.

## Key Results
- TraceSIR achieves average improvements of 9.7% (human evaluation) and 7.5% (LLM-as-a-judge) over ClaudeCode in overall report quality.
- Gains are consistent across all five ReportEval dimensions (overall quality, error analysis, root cause analysis, optimization analysis, organization/insight), with strongest advantages in error and root cause analysis.
- In agentic coding (SWE-bench) with GLM-5, human-evaluated improvement reaches up to 26.0%.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Structured trace abstraction (TraceFormat) enables scalable analysis of long execution traces by preserving essential behavioral semantics while reducing input length.
- **Mechanism:** StructureAgent transforms raw OpenAI-format messages `M` into a deterministic `(thought, action, observation)` tuple sequence `T` via function `Φ`. It then applies length-aware abstraction `A_θ` to compress verbose fields (e.g., code snippets, tool outputs) beyond threshold `θ`, retaining only signals critical for behavioral understanding. This creates a compact, analyzable representation `T'` that fits within LLM context limits without losing causal/temporal alignment.
- **Core assumption:** Verbose elements in long-horizon traces are often redundant; core failure signals reside in the structure of reasoning-action-observation loops rather than exhaustive content.
- **Evidence anchors:**
  - [abstract]: "StructureAgent abstracts traces into TraceFormat while preserving essential behavioral information"
  - [section 3.1]: "TraceFormat strictly preserves the temporal order and causal alignment among reasoning, action, and observation"
  - [section 3.2]: "StructureAgent applies a length-aware abstraction operator... to produce a compressed trace T′"
- **Break condition:** If the abstraction threshold `θ` is set too aggressively, critical fine-grained steps (e.g., minor tool errors, subtle reasoning flaws) may be lost, preventing accurate issue localization in InsightAgent.

### Mechanism 2
- **Claim:** InsightAgent’s fine-grained diagnostic reasoning over structured traces produces insight-driven root cause analysis beyond surface-level error description.
- **Mechanism:** Given a compressed trace `T'` and task `q`, InsightAgent autonomously invokes analysis tools to generate a diagnostic bundle `D = {s, E, W, R, O}`: a completion score `s`, error labels `E` (categorized as main/other), weaknesses `W`, root causes `R`, and optimizations `O` (including fine-tuning samples). It reasons across the full trace sequence, correlating failure points with behavioral patterns, rather than relying solely on final outcomes.
- **Core assumption:** Root causes are inferable from the sequential pattern of thoughts, actions, and observations when viewed in a structured, compressed format.
- **Evidence anchors:**
  - [abstract]: "InsightAgent performs fine-grained diagnosis including issue localization, root cause analysis, and optimization suggestions"
  - [section 3.3]: "Rather than relying solely on final task outcomes, it reasons over the entire structured execution trace to uncover behavioral issues"
  - [section 4.4]: "particularly pronounced gains in error analysis and root cause analysis"
- **Break condition:** If the structured trace `T'` omits key intermediate states (due to over-abstraction) or if the backbone LLM lacks sufficient reasoning depth, InsightAgent may produce generic or incorrect root cause attributions.

### Mechanism 3
- **Claim:** ReportAgent’s cross-case aggregation and statistical modeling generate coherent, evidence-grounded reports by synthesizing pattern-level insights from per-instance diagnostics.
- **Mechanism:** ReportAgent collects diagnostic bundles `{D₁…D_M}` and first checks if the case count `M` warrants reporting (threshold-based triggering). It then estimates error label frequencies `P(ℓ)` and score distributions over intervals `B`, combining quantitative aggregation with qualitative summarization. Crucially, it links reported conclusions to specific trace cases via standardized `id` fields and appends raw trace data to the report appendix for traceability.
- **Core assumption:** Recurring failure patterns across multiple instances are indicative of systematic weaknesses in the agentic system, and aggregating evidence prevents overfitting to single-case noise.
- **Evidence anchors:**
  - [abstract]: "ReportAgent aggregates insights across multiple traces into comprehensive reports"
  - [section 3.4]: "ReportAgent integrates quantitative statistics with qualitative insights to generate comprehensive analysis reports"
  - [section 4.4]: "TraceSIR yields clear and robust advantages... demonstrating its effectiveness in trace structuring and analysis across different underlying LLMs"
- **Break condition:** If the initial set of cases is too small (`M` below threshold) or highly heterogeneous (no common patterns), ReportAgent may generate a generic report with low actionable value, or incorrectly infer spurious correlations.

## Foundational Learning
- **Concept: TraceFormat Abstraction**
  - **Why needed here:** This is the core representational innovation. Without understanding how raw execution logs are transformed into `(thought, action, observation)` tuples and then compressed, one cannot grasp how TraceSIR overcomes input length limits.
  - **Quick check question:** What are the three fields in a TraceFormat round, and why is preserving their temporal alignment critical for diagnosis?

- **Concept: Multi-Agent Orchestration**
  - **Why needed here:** TraceSIR is not a single monolithic LLM call; it’s a pipeline of specialized agents. Understanding the handoff (trace → StructureAgent output → InsightAgent input → ReportAgent aggregation) is key to debugging the system itself.
  - **Quick check question:** What specific information does ReportAgent require from InsightAgent that it does not get from raw traces?

- **Concept: ReportEval Dimensions**
  - **Why needed here:** The paper’s evaluation framework (OS, EA, RCA, OA, OI) defines what a "good" report looks like in this domain. An engineer must know these criteria to interpret results and improve reports.
  - **Quick check question:** Which ReportEval dimension specifically measures whether optimization suggestions are concrete and actionable, and why is this distinct from root cause analysis?

## Architecture Onboarding
- **Component map:**
  Input (trace `.json`/`.zip` + optional `task`, `gold_score`, `gold_judge`) -> StructureAgent -> InsightAgent -> ReportAgent -> Output (`conclude_report.md` + archived results)

- **Critical path:**
  1. **Trace ingestion & standardization** (StructureAgent): Any failure here (e.g., malformed `messages`) halts the pipeline.
  2. **Abstraction tuning** (StructureAgent): The length threshold `θ` is the first major hyperparameter; too low → context overflow later; too high → signal loss.
  3. **Diagnostic completeness** (InsightAgent): Must extract *all* error types (`E`) and generate *actionable* `R` and `O`. Missing a main error cascades into incomplete reports.
  4. **Pattern aggregation** (ReportAgent): Requires sufficient `M` (paper uses multiples of 10). With `M < 10`, it may skip report generation or produce weak summaries.

- **Design tradeoffs:**
  - **Abstraction fidelity vs. length reduction:** Aggressive `A_θ` saves tokens but risks losing subtle cues (e.g., a single erroneous tool call amidst verbose output). The paper sets `θ=100 words/1000 chars` (Appendix B), a domain-agnostic default that may need tuning per scenario.
  - **Single-case vs. cross-case value:** InsightAgent produces useful `D` for one trace. ReportAgent’s value emerges only with `M` large enough to reveal patterns (paper uses 50 traces per scenario). A user submitting 2 traces gets a weak report.
  - **Default vs. custom reporting:** Without user `additional requirements`, reports default to Chinese and a fixed schema. Forcing English or a different structure requires explicit input.

- **Failure signatures:**
  - **StructureAgent:** Output `T′` with mismatched `len(thought)=len(action)=len(observation)` → indicates parsing failure. Over-compressed `thought` fields (e.g., 1-word summaries) → loss of reasoning context.
  - **InsightAgent:** `s` score wildly inconsistent with `gold_score` (if provided) → flawed assessment. Empty `R` or generic `O` (e.g., "improve search") → shallow reasoning.
  - **ReportAgent:** Report lacks cited `TraceBench-*` IDs in appendix → broken traceability. Error distribution table shows 50 unique error labels for 50 cases → no pattern detected, likely due to noisy InsightAgent outputs or insufficient `M`.

- **First 3 experiments:**
  1. **Sanity check single trace:** Submit one `.json` from `TraceBench-1`. Verify StructureAgent output has `N` rounds matching original turn count (within abstraction). Check InsightAgent `D` tags all obvious errors from the raw trace.
  2. **Compare abstraction variants:** Process same trace with `θ=50` vs. `θ=200`. Does the higher `θ` report capture more subtle errors? Does lower `θ` cause InsightAgent to miss a key error that appears in the raw trace’s verbose observation?
  3. **Scale aggregation:** Submit 5, then 10, then 50 traces from one scenario. Observe when ReportAgent triggers (paper: `M` multiple of 10). Does the error frequency table `P(ℓ)` stabilize after 30 cases? Are the top 3 error trends intuitive given domain knowledge (e.g., "search strategy failure" in Deep Research)?

## Limitations
- Optimal abstraction threshold θ is domain-sensitive; paper uses fixed default (100 words/1000 chars) without per-scenario tuning, risking over/under-compression.
- ReportAgent’s aggregation requires sufficient trace count M; paper uses M=50, but performance for M<10 (common in user settings) is unevaluated and likely degraded.
- LLM backbone dependency not isolated: paper claims consistency across "different underlying LLMs" but doesn’t specify models or whether same LLM serves all agents, confounding attribution.
- TraceBench case distribution across BrowseComp/Tau2Bench/SWE-bench is undisclosed, potentially biasing per-scenario comparisons.
- Human evaluation details (e.g., evaluator expertise, inter-rater agreement) are missing, undermining confidence in the 9.7% improvement claim.

## Confidence
- *Mechanism 1 (Structured Abstraction)*: **Medium**. Evidence from paper sections supports design, but lack of θ ablation studies leaves optimality uncertain; break condition plausible.
- *Mechanism 2 (InsightAgent Diagnosis)*: **Medium-High**. Gains in error/root cause analysis are consistent across evaluations, but backbone LLM capability remains a key confounder.
- *Mechanism 3 (ReportAgent Aggregation)*: **Medium**. Strong results at M=50, but no validation for smaller M where statistical aggregation may fail.

## Next Checks
1. **θ Sensitivity Analysis**: Hold all else constant, vary θ (50, 100, 200, 500 words) on a held-out TraceBench subset; measure error detection F1 against gold labels. Expected: peak performance near θ=100, decline at extremes.
2. **Minimum Case Count Threshold**: For one scenario (e.g., SWE-bench), generate reports for M=1,5,10,20,30,50 traces; conduct human evaluation on actionability (1-5 Likert). Expected: sharp improvement from M=10 to 30, plateau thereafter.
3. **Cross-Scenario Portability**: Train InsightAgent on full SWE-bench diagnostics, then apply to BrowseComp traces without adaptation; compare report quality (OS/RCA/OA scores) to in-domain runs. Expected: significant drop, indicating scenario-specific tuning needs.
