# Compiled Memory: Not More Information, but More Precise Instructions for Language Agents

## Quick Facts
- **arXiv ID:** 2603.15666
- **Source URL:** https://arxiv.org/abs/2603.15666
- **Reference Count:** 3
- **Primary Result:** Compiling verified task experience into the system prompt via a distillation pipeline improved GPT-4o's token F1 by +8.7pp on CUAD and joint F1 by +3.16pp on HotpotQA; identical prompts transferred gains to Claude Sonnet 4.5, confirming task-shaped knowledge.

## Executive Summary
Atlas introduces a memory system that improves agent utility not by retrieving more context, but by distilling verified task experience into permanent modifications of the system prompt. It uses a four-layer memory with a three-step verification gate to extract high-confidence "facts" (boundary rules from errors, guard facts from successes) and rewrites the base prompt with these facts. On contract analysis (CUAD) and multi-hop QA (HotpotQA), the evolved prompt significantly boosted performance. Cross-model transfer showed that gains concentrated where each model had baseline weaknesses, indicating the compiled knowledge is task-shaped rather than model-shaped. A key constraint is that the system learns only what its analysis prompt explicitly teaches.

## Method Summary
Atlas operates via a write-path and a read-path. The write-path runs the base agent on training examples, compares outputs to gold labels, and uses an analysis LLM to extract candidate facts: boundary rules from failures and guard facts from successes. These candidates pass through a three-step promotion gate (deduplication by embedding similarity, LLM verification, lexical grounding) before being stored in the Historical layer. The read-path, triggered at epoch end, filters Historical facts by confidence (c≥0.85), deduplicates, and sanitizes them. An evolution LLM then rewrites the base system prompt by inserting selected facts as sub-bullets under relevant existing instructions and adds task-specific anchors. This evolved prompt replaces the base prompt for all subsequent inference, without fine-tuning or RAG.

## Key Results
- On CUAD contract analysis, the evolved prompt improved GPT-4o token F1 by +8.7 percentage points and precision by +12.5 percentage points.
- On HotpotQA multi-hop QA, joint F1 improved by +3.16 percentage points.
- The same GPT-4o–compiled prompt, applied to Claude Sonnet 4.5, yielded a +2.31pp joint F1 gain, with improvements concentrated on dimensions where Claude's baseline was weaker (answer F1 nonsignificant, supporting fact F1 +2.37pp).

## Why This Works (Mechanism)
### Mechanism 1: Distillation over Retrieval
Atlas improves utility by permanently altering the instruction set with distilled, high-confidence lessons, not by injecting temporary context. A four-layer memory (Fresh→Task→Contextual→Historical) accumulates raw signals. A three-step promotion gate (deduplication, LLM verification, lexical grounding) filters candidates into the Historical layer. The read-path rewrites the system prompt with high-confidence facts (c≥0.85). The core assumption is that behavioral change is best achieved by permanent instruction modification. Evidence includes the architectural description and ablations showing degradation when gates are removed. If the gate admits low-confidence or ungrounded facts, the prompt may degrade.

### Mechanism 2: Training Signal Constraint
The performance ceiling is bounded by the scope and quality of extracted training facts. The analysis LLM extracts fact types based on a fixed prompt; the read-path can only recombine these types. Changing the analysis prompt's objective surgically alters the improvement profile without affecting other dimensions. The system is a compiler, not a learner; it generalizes only within the captured dimensions. Evidence includes the HotpotQA v2 (answer-only) vs. v3 (multi-objective) ablation: answer F1 gap unchanged while supporting fact gap widened. If a critical failure mode is absent from the analysis prompt, the system cannot learn to correct it.

### Mechanism 3: Task-Shaped Knowledge
Compiled knowledge is task-shaped, not model-shaped, as identical prompts compiled from one model's errors improve a different model, with gains concentrated where each model's baseline leaves room. The evolved prompt encodes task-level rules (e.g., "extract only jurisdiction name"). Different base models have varying proficiencies in executing those rules, yielding heterogeneous gains aligned with residual weaknesses. Evidence includes cross-model transfer results: Claude's answer F1 gain was minimal while supporting fact F1 gained significantly, matching predictions based on its higher baseline answer score. If task patterns were intrinsically model-dependent, the same prompt would not yield heterogeneously concentrated gains.

## Foundational Learning
- **Distillation vs. Retrieval:** Atlas treats memory as a source for *instruction synthesis*, not *context augmentation*. Understanding this distinction is key to evaluating its design tradeoffs. *Quick check:* If a system injects retrieved facts as context at inference time, is it using memory for distillation or retrieval?
- **Training Signal Constraint:** This is the mechanism's defining property. All fact extraction objectives must be deliberately aligned with all evaluation metrics. *Quick check:* If an evolved prompt improves answer F1 but degrades attribution F1, what does that indicate about the training signal?
- **Verification Gate as a Filter:** The three-step gate (dedup, LLM verify, lexical ground) is the quality control that makes distillation trustworthy. Its design choices directly impact precision and recall of the final instruction set. *Quick check:* What is the purpose of the "grounding" step (keyword overlap) if an LLM already verified the fact?

## Architecture Onboarding
- **Component Map:** Agent runs → Error/Success analysis (LLM) → Fact extraction → Three-step promotion gate → Historical layer store. Read Path: Filter Historical facts (c≥0.85) → Evolve LLM (prompt rewrite) → Anchor injection → Replace system prompt.
- **Critical Path:** `Run on training example` → `Compare to gold` → `Extract failure cause as rule OR success as guard` → `Pass 3-step gate` → `Store in Historical` → `Filter & evolve at epoch end` → `Deploy new prompt`.
- **Design Tradeoffs:** Token budget vs. specificity: evolved prompt ~5× longer (960→1570 tokens); gains may stem from precision or just more tokens. Gate strictness: high thresholds reduce noise but may filter valid lexically dissimilar facts. Analysis LLM calibration: extraction errors become instructions.
- **Failure Signatures:** Precision collapse without recall anchors (ablation Table 2 C1+C2). Task metric displacement (v2 on HotpotQA: answer F1 up, support F1 down). Cross-model gain inversion (if weaker model gains more on same dimension stronger model improved).
- **First 3 Experiments:** 1) Gate validation: run gate on human-validated facts; measure precision/recall; tune thresholds. 2) Training signal scope test: on a two-metric task, target only one metric via analysis prompt; confirm surgical improvement. 3) Prompt bloat control: pad base prompt with random sub-bullets to match evolved length; compare to isolate content vs. length effects.

## Open Questions the Paper Calls Out
- **Does the evolved prompt's gain stem from specific content or merely increased token count?** The evolved prompt is ∼5× longer; no length-matched control isolates content from length effects.
- **Does the three-step verification gate's keyword-based grounding heuristic sufficiently prevent unverified facts from promotion?** The heuristic uses "kmin=2 keyword overlap" and is not semantic entailment; its impact on downstream performance is untested.
- **How do errors in the analysis LLM's fact extraction propagate into the evolved prompt and affect downstream performance?** Extraction errors become compiled instructions; no empirical assessment of error rates or correlation with performance changes exists.
- **For tasks with multiple evaluation dimensions, how can we ensure the training signal captures all necessary aspects?** Current approach relies on manual analysis prompt design; scaling to complex, multi-dimensional tasks is unclear.

## Limitations
- **Unknown Implementation Details:** Exact prompts for analysis/evolution LLMs, sanitization algorithm, anchoring strategy, and four-layer storage specifics are underspecified, blocking faithful reproduction.
- **Potential Confounds:** The evolved prompt is significantly longer; without a length-matched control, gains could partly reflect added token budget rather than precise instruction quality.
- **Evidence for Core Claims:** The "task-shaped knowledge" claim relies on cross-model transfer results but lacks deep mechanistic analysis of *why* the prompt generalizes; evidence is suggestive but not definitive.
