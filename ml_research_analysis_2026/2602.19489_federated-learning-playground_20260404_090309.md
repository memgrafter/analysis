# Federated Learning Playground
## Quick Facts
- arXiv ID: 2602.19489
- Source URL: https://arxiv.org/abs/2602.19489
- Reference count: 3
- Primary result: An interactive browser-based tool that lowers educational barriers to federated learning by enabling real-time experimentation with hyperparameters, algorithms, and privacy settings without infrastructure setup.

## Executive Summary
Federated learning (FL) presents significant entry barriers due to its distributed infrastructure and complex dynamics. This paper introduces the Federated Learning Playground, a browser-based simulation that extends TensorFlow Playground to allow users to manipulate FL parameters—such as data heterogeneity, client dropout, and aggregation algorithms—and observe immediate visual feedback. The tool successfully democratizes FL experimentation, providing intuitive insights into challenges like non-IID data and scalability, while serving as a functional sandbox for prototyping. It is publicly accessible and represents a substantial codebase expansion to support comprehensive FL modules.

## Method Summary
The tool implements a full FL pipeline client-side using JavaScript/WebAssembly. It generates synthetic 2D classification data partitioned across virtual clients via a Dirichlet distribution to create non-IID scenarios. Users configure parameters through a UI that triggers an orchestrator `oneStepFL` loop: sample clients → perform local training (with optional modifications like FedProx proximal terms) → aggregate updates server-side → update visualizations. Supported algorithms include FedAvg, FedProx, FedAdam, SCAFFOLD, and clustered FL, with differential privacy via clipping and Gaussian noise. The entire process runs in-browser on tiny MLPs, eliminating deployment overhead.

## Key Results
- Lowers the experimental barrier by replacing distributed deployments with a client-side browser simulation.
- Provides real-time visualizations that convey core FL dynamics (e.g., non-IID effects, client drift, aggregation trade-offs).
- Serves as a functional sandbox for rapid prototyping and comparison of FL algorithms and privacy settings.
- Codebase more than doubled in size to integrate comprehensive FL modules.

## Why This Works (Mechanism)
The Federated Learning Playground lowers the experimental barrier by replacing infrastructure-dependent FL deployments with a client-side browser simulation. It implements the entire FL pipeline (client sampling, local training, server aggregation) in JavaScript/WebAssembly within the browser, eliminating the need for distributed computing setup, multiple devices, or server access. The core assumption is that simplified synthetic 2D data and tiny MLPs are sufficient to convey core FL dynamics (e.g., non-IID effects, aggregation trade-offs) without requiring real-world dataset complexity. Evidence includes statements that it runs "directly in the browser without coding or system setup" and that the implementation is "lightweight and easily deployable." A break condition would be if the simulation's simplified model dynamics fail to generalize to real FL system behaviors (e.g., network delays, hardware heterogeneity).

Real-time multi-panel visualizations enable causal intuition about FL hyperparameter effects by coupling immediate feedback with comparative views. The UI synchronizes parameter changes (e.g., non-IID α, dropout rate) with live plots of client loss distributions, convergence curves, participation tracking, and communication costs, allowing users to directly observe phenomena like client drift or aggregation instability. The core assumption is that visual correlation between control inputs and metric outputs is cognitively sufficient for users to infer underlying causal mechanisms. Evidence includes the abstract's claim that users can "observe their effects... gaining intuition for challenges such as non-IID data." A break condition is if visualizations oversimplify or misrepresent FL state (e.g., aggregated loss masks per-client divergence).

A modular FL engine architecture allows rapid prototyping and comparison of algorithms by abstracting shared operations (delta computation, clipping, aggregation) while plugging in variant-specific logic. The `oneStepFL` orchestrator handles client sampling, local epoch loops, and aggregation universally; algorithm-specific logic (FedProx proximal term, SCAFFOLD control variates, FedAdam server state) is injected as configurable modules, enabling side-by-side comparison with minimal UI changes. The core assumption is that isolating algorithmic differences in a shared, deterministic simulation environment cleanly highlights algorithmic behavior without confounding system noise. Evidence includes descriptions of `oneStepFL` supporting multiple algorithms via lightweight extensions. A break condition is if modular interactions introduce subtle bugs (e.g., incorrect delta computation when combining FedProx and DP).

## Foundational Learning
- **Concept: Federated Averaging (FedAvg) canonical loop**  
  Why needed: Users must grasp the base client-server cycle (sample → local train → aggregate) before understanding algorithm modifications.  
  Quick check: "What changes when you add a proximal term to local loss, and why might that help with non-IID data?"

- **Concept: Non-IID data and client drift**  
  Why needed: Central to FL challenges; playground’s Dirichlet sampler and loss distribution plots directly target this concept.  
  Quick check: "If each client’s local data distribution is highly skewed, what happens to the global model after one round of FedAvg?"

- **Concept: Differential Privacy in FL (DP-SGD on updates)**  
  Why needed: The tool models privacy via clipping and Gaussian noise on client updates, a key distinction from central DP.  
  Quick check: "Why might adding noise to client weight deltas preserve privacy even though the server sees all updates?"

## Architecture Onboarding
**Component map:**  
UI Controls (hyperparameters, algorithm selector) -> oneStepFL orchestrator -> Client instances (local training with algorithm mods) -> Server (aggregation, optimizer state) -> Visualization panels (loss, participation, etc.) -> Data Layer (synthetic datasets, client partitions, metric logs)

**Critical path:**  
1) Initialize synthetic dataset & client partitions. → 2) Configure FL parameters (algorithm, non-IID α, dropout). → 3) Run `oneStepFL` loop: sample clients → local training (with algorithm mods) → aggregate updates → update visualizations. → 4) Observe metric trends across rounds.

**Design tradeoffs:**  
- Simplicity vs. realism: Tiny MLPs/2D data enable browser speed but cannot capture complexities of deep FL (e.g., gradient dissimilarity magnitude, straggler effects).  
- Interactivity vs. scalability: Real-time updates favor small client counts (<100) and tiny models; larger scales require discrete "run" buttons.  
- Algorithm coverage vs. depth: Supports 4 major algorithms but omits many variants (e.g., personalization methods); each implemented with minimal code for clarity.

**Failure signatures:**  
- Visualizations lag or freeze: likely due to excessive DOM updates; throttle redraws.  
- Convergence curves diverge unexpectedly: check learning rate scaling, clipping norm, or Dirichlet α extreme values.  
- Algorithm switcher has no effect: verify `oneStepFL` is applying the selected algorithm’s logic (common bug: FedProx term not injected in local loss).

**First 3 experiments:**  
1. **Baseline:** Run centralized (Federated off) vs. FL (FedAvg, IID) to confirm global model converges similarly; then switch to non-IID (α=0.1) to observe slower/noisy convergence.  
2. **Algorithm comparison:** Keep non-IID fixed; run FedAvg, then FedProx (μ=0.1), then SCAFFOLD; compare client loss distribution plots for drift reduction.  
3. **Privacy impact:** With fixed non-IID, enable DP (set noise σ from 0.1 to 1.0); observe convergence curve degradation and note communication cost unchanged.

## Open Questions the Paper Calls Out
**Question 1:** How can the Federated Learning Playground integrate explainable AI techniques to provide real-time visual interpretations of individual client model decisions and server aggregation outcomes?  
Basis: "Future work will add trustworthy-FL features for explainability..."  
Why unresolved: Current visualizations show aggregate metrics but not model behavior at client/feature level.  
Resolution evidence: Implement on-client explanation methods (e.g., SHAP, LIME) in-browser; conduct user studies measuring understanding improvements.

**Question 2:** What fairness-aware aggregation mechanisms and diagnostics can be incorporated to detect and mitigate biases exacerbated by non-IID data distributions across clients?  
Basis: "Future work will add trustworthy-FL features for... fairness..."  
Why unresolved: Tool emphasizes convergence under heterogeneity but not fairness implications or interventions.  
Resolution evidence: Add fairness metrics (client-wise accuracy variance, group fairness) to visualizations; enable configurable fairness penalties in aggregation; evaluate user ability to identify bias.

**Question 3:** Can the simulator be meaningfully extended to support vertical FL, and how do its unique challenges compare to horizontal FL in terms of user comprehension?  
Basis: "Broaden the simulator to vertical FL..."  
Why unresolved: Current implementation exclusively models horizontal FL; vertical FL involves different communication patterns and privacy assumptions.  
Resolution evidence: Develop vertical FL mode with simulated feature partitioning; visualize sample-aligned gradient exchanges; run controlled experiments comparing learning curves and user understanding.

**Question 4:** How should the playground adapt to simulate FL with foundation models (e.g., parameter-efficient fine-tuning), and what novel trade-offs (e.g., communication vs. utility) emerge at scale?  
Basis: "Broaden the simulator to... FL foundation models."  
Why unresolved: Tiny MLPs on 2D data abstract away complexities of large models (e.g., high-dimensional parameters, catastrophic forgetting).  
Resolution evidence: Integrate lightweight transformer or MLP modules with simulated parameter-efficient updates (e.g., LoRA); visualize parameter sparsity and communication volume; assess user grasp of scaling challenges.

## Limitations
- **Simplification validity:** Synthetic 2D data/tiny MLPs may fail to capture critical FL dynamics like gradient dissimilarity scales or straggler effects.
- **Learning efficacy:** No user-study evidence that visualizations produce correct causal understanding of FL challenges.
- **Reproducibility gaps:** Exact hyperparameters (α, LR, client count) and synthetic data generator details for paper figures are undisclosed.

## Confidence
- Barrier reduction claim: **High** – Browser-based, no-setup tool demonstrably accessible.
- Educational intuition claim: **Medium** – Visual feedback exists, but learning outcomes unvalidated.
- Prototyping utility claim: **Medium** – Modular design supports comparisons, but algorithmic correctness unbenchmarked.

## Next Checks
1. **Benchmark simplification fidelity:** Compare Playground’s FedAvg convergence curves (on synthetic 2D) against a canonical FL implementation (e.g., TensorFlow Federated) on a comparable tiny model/synthetic dataset to test whether simplified dynamics preserve key FL phenomena.
2. **User intuition audit:** Recruit FL novices to perform structured tasks (e.g., “minimize client drift”) using the Playground; assess if post-task explanations correctly identify causal factors (non-IID, dropout).
3. **Modular engine stress test:** Systematically combine all supported modules (e.g., FedProx with SCAFFOLD controls, add DP clipping) and compare aggregate loss against isolated implementations to detect interaction bugs in `oneStepFL` orchestration.
