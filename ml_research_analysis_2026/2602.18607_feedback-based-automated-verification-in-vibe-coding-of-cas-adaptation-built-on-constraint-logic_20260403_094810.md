# Feedback-based Automated Verification in Vibe Coding of CAS Adaptation Built on Constraint Logic
## Quick Facts
*   **arXiv ID:** 2602.18607
*   **Source URL:** https://arxiv.org/abs/2602.18607
*   **Reference Count:** 30
*   **Primary Result:** Combining LLM vibe coding with runtime verification using the fine-grained temporal logic FCL yields valid Adaptation Managers in typically ≤3 iterations, with 70–100% success within 10 iterations for GPT-5 nano.

## Executive Summary
This paper introduces a method for automatically generating correct Adaptation Managers (AMs) for Collective Adaptive Systems (CAS) by combining "vibe coding" (iterative LLM-based code generation) with runtime verification. The core innovation is the use of a novel temporal logic called FCL (Functional Constraints Logic), which provides fine-grained, quantitative constraints (e.g., "at least N times within T steps"). During system execution, a Constraint Verifier evaluates these FCL constraints; any violation triggers a detailed feedback report that is fed back to the LLM to correct the AM code. Evaluated on two case studies (Dragon Hunt game, Smart Farm simulation), the approach converges quickly (≤3 iterations typical) and produces AMs with performance comparable to hand-written ones. The study demonstrates that precise, actionable feedback from FCL constraints is key to efficient LLM-based AM generation.

## Method Summary
The method implements an iterative generate-verify-refine loop. First, a prompt is constructed from a natural language domain description, an architecture specification (ADSL), and a set of FCL functional constraints. An LLM generates Python code for the Adaptation Manager from this prompt. The generated AM is then integrated into a managed CAS simulation (e.g., a game) and executed. Concurrently, a runtime Constraint Verifier monitors the system state and evaluates the AM's behavior against both generic constraints (e.g., code structure) and the FCL functional constraints. If any constraint is violated during the run, the execution is halted, and a structured violation report—detailing the specific constraint and trace segment that failed—is generated. This report is appended to the prompt, and the LLM is queried again to produce a revised AM. The loop repeats until an AM passes all constraints or a maximum iteration limit (10) is reached.

## Key Results
*   Detailed constraint violation feedback from FCL yields valid AMs in few iterations (typically ≤3), achieving a 70–100% success rate within 10 iterations using GPT-5 nano, depending on feedback type.
*   The Smart Farm case study demonstrated that generated valid AMs achieved a median 6.9% damage rate, nearly matching the 7.0% rate of a hand-written AM.
*   FCL's fine-grained temporal operators (e.g., `within` windows) were critical for expressing precise strategies and generating specific, actionable violation feedback, offering a clear advantage over classical LTL.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** Detailed constraint violation feedback (from FCL) effectively guides the LLM to correct AM code within few iterations.
*   **Mechanism:** The Constraint Verifier evaluates functional constraints during system runs. A violation generates a structured report specifying the exact constraint and trace segment where the AM's behavior diverged. This report is appended to the prompt for the next LLM iteration, providing concrete evidence of the logical failure for targeted correction.
*   **Core assumption:** The LLM can interpret these structured violation reports and modify its code accordingly.
*   **Evidence anchors:** Abstract states detailed feedback yields valid AMs in ≤3 iterations. Section III-C describes the feedback loop activation and report inclusion. Corpus context on vibe coding challenges supports the need for precise feedback.

### Mechanism 2
*   **Claim:** Integrating the adaptation loop and the vibe-coding feedback loop via runtime verification creates an efficient convergence cycle.
*   **Mechanism:** The AM's proposed updates are verified against constraints during the *same* system run used for evaluation. A failing run stops early upon a critical violation, saving computation. The resulting report directly feeds the LLM's next attempt, ensuring feedback is based on the *actual executed behavior*.
*   **Core assumption:** Early termination provides sufficiently diagnostic information without needing a full trace.
*   **Evidence anchors:** Abstract mentions combining loops with FCL evaluation. Section III-A details the concurrent run and stop-on-violation. Section V-E3's Figure 4 illustrates convergence vs. stagnation.

### Mechanism 3
*   **Claim:** FCL's fine-grained temporal expressiveness (vs. LTL) is key to generating precise, actionable constraint violation feedback.
*   **Mechanism:** FCL's `within` operator (`♢n_t φ`) specifies *how many times* (`n`) a condition `φ` must hold within a *specific window* of `t` steps (including backwards-looking windows). This allows constraints to target precise adaptation tactics. Violation reports can pinpoint exactly which temporal window failed. LTL lacks this quantitative windowing.
*   **Core assumption:** FCL's specificity translates into more discriminative, less ambiguous feedback for the LLM.
*   **Evidence anchors:** Abstract states FCL's finer granularity was key. Section IV-A defines semantics and contrasts with LTL. Section IV-B lists constraints using this granularity. Section V-E4 highlights FCL's utility for multi-step window constraints.

## Foundational Learning
*   **Concept: FCL (Functional Constraints Logic)**
    *   **Why needed:** Provides the formal, executable specification of desired AM behavior. It is the oracle for the verification feedback loop; without precise constraints, feedback is vague and the LLM cannot converge.
    *   **Quick check:** How would you express "All warriors must attack the dragon at least twice within the first 10 steps" as an FCL constraint? (Answer: `Warriors={v∈Villagers|v.role='Warrior'}; ♢2_10 |{v∈Warriors | v∈Attack}| ≥2`)
*   **Concept: Vibe Coding Feedback Loop**
    *   **Why needed:** The core generative process. It's an iterative generate-verify-refine cycle where the verifier (using FCL) provides the crucial signal to the LLM. Understanding this loop is key to designing the experiment and interpreting results.
    *   **Quick check:** What are the two "loops" shown in Fig. 1 and how do they interact? (Answer: The inner *adaptation loop* (red) runs the system with the AM. The outer *feedback loop* (black) is triggered if the Constraint Verifier finds violations, feeding the report back to the LLM.)
*   **Concept: Ensemble-Based CAS (DEECo)**
    *   **Why needed:** Defines the architectural model being adapted. The AM's job is ensemble resolution. Constraints and prompts reference ensembles (Farm, Attack) and component attributes. Misunderstanding this model leads to incorrect constraint formulation or prompt generation.
    *   **Quick check:** In Dragon Hunt, what is the difference between the `assign_in_village` and `assign_in_cave` methods the AM must implement? (Answer: They resolve ensembles for Villagers based on their *current* location (`location == 'Village'` vs `location == 'Cave'`). The AM assigns components from the input list `components` to specific group IDs like "farm", "attack", "spawn warrior".)

## Architecture Onboarding
*   **Component map:** Prompt Generator -> LLM API -> Generated AM Code -> System Runner (with AM) -> Constraint Verifier (FCL Engine) -> Violation Report -> Feedback Loop Manager -> (back to) Prompt Generator
*   **Critical path:** The convergence path is: Prompt Generation -> LLM Code Generation -> System Run with Constraint Verifier -> (if violation) Violation Report -> Feedback Loop (back to Prompt Gen). The cycle terminates when the Constraint Verifier reports zero violations or the max iteration count is reached.
*   **Design tradeoffs:**
    *   *Constraint Specificity vs. Generality:* Overly specific FCL constraints may reject valid but non-standard AMs; too general constraints may allow invalid AMs to pass. Requires tuning.
    *   *Feedback Detail vs. LLM Context Window:* Detailed violation reports consume prompt tokens. With long constraint sets, this may hit context limits, necessitating summarization and loss of detail.
    *   *Early Termination vs. Full Coverage:* Stopping at the first violation saves time but may miss other violations that could provide more comprehensive feedback.
*   **Failure signatures:**
    *   **Dead end:** LLM repeatedly produces similar invalid AMs across iterations. Feedback is insufficient (e.g., only high-level metrics) or constraints are misaligned.
    *   **False positive/negative in CV:** AM declared valid but fails in practice, or a valid AM is rejected due to a bug in the FCL engine or constraint phrasing.
    *   **LLM syntax errors:** Generated AM fails to import/run (often triggers generic constraint violation). Usually fixed in 1-2 iterations.
*   **First 3 experiments:**
    1.  **Dragon Hunt - Baseline tuning:** Run with initial FCL set to ensure any losing AM triggers a violation. Iteratively refine constraints (e.g., adding "attack in first 15 steps") until passing AMs reliably win.
    2.  **Dragon Hunt - Feedback ablation:** For fixed tuned constraints, compare feedback conditions: (a) generic+functional violation reports, (b) generic-only, (c) metric-only (win rate). Measure iterations to valid AM. Expect (a) to converge fastest.
    3.  **Smart Farm - Cross-case validation & LLM scaling:** Apply framework to Smart Farm. Test if tuned approach generalizes. Compare LLM capability (GPT-5 nano vs. mini). Expect feedback type still matters, more capable LLM needs fewer iterations, and generated AM damage rate ~ hand-written (7.0% vs 6.9%).

## Open Questions the Paper Calls Out
### Open Question 1
*   **Question:** How can Adaptation Managers be designed to dynamically leverage FCL temporal obligations for proactive adaptation decisions during system execution?
*   **Basis in paper:** [explicit] In Section V.E.5, the authors state: "Another potential use for FCL, apart from constraint verification, is to prioritize AM adaptation decisions based on the access of the AM to the temporal obligations in the FCL interpreter... For now, this is left as a potential direction for future work."
*   **Why unresolved:** The current approach uses FCL solely for post-hoc verification. Integrating real-time access to pending obligations to guide AM decisions is not implemented or evaluated.
*   **What evidence would resolve it:** An extended framework where the AM queries the FCL interpreter for pending obligations during adaptation, tested via experiments comparing adaptation efficiency and system outcomes.

### Open Question 2
*   **Question:** To what extent does the vibe coding method with FCL constraints remain effective when applied to complex, real-world Collective Adaptive Systems with large-scale, dynamic components?
*   **Basis in paper:** [inferred] The construct validity threat in Section V.F.1 notes: "we did not perform any experiments with real-world CAS," implying evaluation was restricted to two simplified examples.
*   **Why unresolved:** Real-world CAS involve more components, intricate interactions, and volatile environments, which could challenge FCL expressiveness, LLM comprehension, and feedback efficiency; this limits claims of generalizability.
*   **What evidence would resolve it:** Case studies or empirical evaluations on authentic CAS applications (e.g., from industry), measuring success rates, iteration counts, constraint specification effort, and scalability.

### Open Question 3
*   **Question:** What automated strategies can detect and recover from dead ends in LLM-based vibe coding loops for AM generation to avoid stagnation and improve convergence?
*   **Basis in paper:** [inferred] Section V.E.3 describes dead ends and notes "we found it might be better to break the feedback loop and start over," but offers no systematic mechanism.
*   **Why unresolved:** The paper lacks methods for identifying stagnation (e.g., via code/behavior similarity) or autonomous recovery (e.g., prompt adjustments), relying on ad-hoc human intervention.
*   **What evidence would resolve it:** Development and testing of dead-end detection algorithms (e.g., clustering generated code) and recovery policies (e.g., random restarts, constraint relaxation) in controlled experiments.

### Open Question 4
*   **Question:** How can the alignment between natural language adaptation strategies and formal FCL constraints be partially automated to reduce manual tuning and ensure consistency?
*   **Basis in paper:** [inferred] In Section V.E.2, the authors detail manually re-formulating constraints and suggest "human involvement in the feedback loop might be necessary," revealing constraint derivation is labor-intensive.
*   **Why unresolved:** Translating informal strategies into precise FCL currently requires expert intervention and iterative refinement; without automation, scalability to non-experts is risky.
*   **What evidence would resolve it:** A prototype tool that generates FCL constraint candidates from natural language specifications (e.g., using an LLM), evaluated via user studies or empirical comparisons against manual constraints.

## Limitations
*   **LLM Model Fidelity:** Core results depend on unreleased "GPT-5 nano/mini" models. Success with these specific models cannot be externally validated, creating a reproducibility gap.
*   **FCL Toolchain Implementation:** The exact capabilities and supported subset of the provided FCL parser/evaluator are not fully detailed. A mismatch with the paper's examples would invalidate the key comparison to LTL.
*   **Case Study Validity & Transfer:** The Smart Farm's complexity and realism as a "harder case" are subjective. Its metrics may not fully capture functional correctness, and the transfer of tuning from Dragon Hunt is asserted but not deeply analyzed.

## Confidence
*   **Feedback Loop Convergence (≤3 iterations):** **Medium.** Strong internal evidence from experiments, but dependent on unreleased model and FCL tool implementation.
*   **FCL Granularity Advantage:** **Medium.** Internal examples and user study support the claim within the framework, but independent verification of the FCL tool is needed for full confidence.
*   **Cross-Case Generalizability:** **Low.** The Smart Farm result is a single data point with an unclear baseline; the leap from a toy game to a plausible domain lacks robust justification.
