# ToolFlood: Beyond Selection -- Hiding Valid Tools from LLM Agents via Semantic Covering

## Quick Facts
- arXiv ID: 2603.13950
- Source URL: https://arxiv.org/abs/2603.13950
- Reference count: 40
- Primary result: ToolFlood achieves up to 99% attacker success on MetaTool and 96.1% on ToolBench by injecting a small fraction of crafted tools (86.3% and 1.2% injection rates respectively), reliably dominating top‑k retrieval results.

## Executive Summary
ToolFlood is a retrieval‑layer attack against tool‑augmented LLM agents. By injecting a few semantically crafted tools into the catalog, the attacker can flood the top‑k search results for a large fraction of user queries, suppressing benign tools and causing the agent to select an adversarial tool. The attack proceeds in two phases: first, an LLM generates candidate tool metadata conditioned on random subsets of target queries; second, a greedy algorithm selects a minimal subset that semantically covers each target query at least k times under a distance threshold. Experiments on MetaTool (199 tools) and ToolBench (11,760 tools) show near‑perfect top‑k domination (97.2% TDR, 91% TDR) and high attack success rates (up to 99% ASR, 96.1% ASR). The attack transfers across embedding models, and a basic MMR defense only reduces domination to 44.8% while leaving ASR around 91%, underscoring the challenge of mitigating such semantic covering attacks.

## Method Summary
The attack consists of two phases per task. Phase 1 (Monte Carlo generation): For each task, the attacker samples subsets of 20 queries from a set of target generation queries (Q_gen). An LLM (e.g., GPT‑4o‑mini) is prompted to produce 10 tool metadata strings (name and one‑sentence description) that are semantically relevant to all queries in the subset. Over 1000 iterations, this yields a candidate pool of ~10,000 tools. Phase 2 (Greedy semantic multi‑cover): Using a shadow embedding model, the attacker computes a cosine‑distance threshold δ as the 5% quantile of distances between queries and benign tools. Each candidate tool is embedded, and a coverage matrix indicates whether the tool is within δ of a query. The greedy algorithm iteratively selects tools that cover the most still‑uncovered queries, respecting a quota r=k (each query must be covered at least five times), until all queries are covered or a budget is exhausted. The selected adversarial tools are then injected into the tool catalog. During inference, the agent retrieves top‑k tools via the target embedding model; if all top‑k are adversarial, the attack achieves top‑k domination (TDR). Attack success (ASR) requires the agent’s selection LLM to pick an adversarial tool from the retrieved set.

## Key Results
- On MetaTool (199 tools), ToolFlood achieves 97.2% top‑k domination rate (TDR) and up to 99% attack success rate (ASR) with an injection rate of 86.3%.
- On ToolBench (11,760 tools), it achieves 91% TDR and up to 96.1% ASR while injecting only 1.2% of the tools into the catalog.
- The attack transfers across different embedding models; however, a simple MMR reranking defense reduces TDR to 44.8% but fails to lower ASR significantly (∼91%).

## Why This Works (Mechanism)
The attack exploits the fact that embedding‑based retrieval is driven by semantic similarity. By generating tools that are deliberately aligned with the surface semantics of user queries, the attacker can cause those tools to appear highly similar in the embedding space. The greedy multi‑cover algorithm ensures that each target query is covered by enough adversarial tools to saturate the top‑k positions, even under a tight distance threshold. Because the selector LLM lacks intrinsic knowledge of the true tool catalog, it often picks an adversarial tool when presented among the top retrievals. The approach is model‑agnostic with respect to the selector LLM and relies only on the retrieval layer, making it broadly applicable. The theoretical guarantee shows that with sufficient iterations, the greedy selection can cover all queries under the threshold.

## Foundational Learning
- **Semantic embedding retrieval:** Tools and queries are represented as dense vectors; similarity (cosine) determines retrieval. *Why needed:* The attack manipulates this similarity. *Quick check:* Verify that changing the embedding model shifts δ and coverage.
- **Top‑k domination attack:** Goal is to have adversarial tools occupy all top‑k retrieval slots for target queries. *Why needed:* The core attack objective. *Quick check:* Measure TDR by counting adversarial tools in top‑k.
- **Greedy set cover:** Approximates the minimum set of candidates covering all queries with a quota. *Why needed:* Efficiently select a small adversarial set. *Quick check:* Compare greedy selection size to optimal (NP‑hard) on a small instance.
- **Cosine‑distance threshold (δ):** Determines semantic equivalence; tools within δ of a query are considered covering. *Why needed:* Binarizes similarity to a coverage relation. *Quick check:* Plot histogram of distances to confirm δ near 5% quantile.
- **LLM‑generated tool metadata:** Using an LLM to produce plausible tools conditioned on query subsets. *Why needed:* Scales candidate generation without human intervention. *Quick check:* Validate relevance of generated tools via human or automatic scoring.

## Architecture Onboarding
Component map: [Target Queries] -> [LLM Generator] -> [Candidate Pool] -> [Embedding Model (shadow)] -> [Coverage Matrix] -> [Greedy Multi-Cover Selector] -> [Adversarial Tools] -> [Injection into Tool Catalog] -> [Retriever (target embedding)] -> [Top‑k Tools] -> [Selector LLM] -> [Tool Call]

Critical path:
1. For each task, sample query subsets and generate candidate tools via LLM.
2. Embed queries and candidates with shadow model; compute δ.
3. Build coverage matrix; run greedy selection with quota r=k.
4. Inject adversarial tools into the tool catalog.
5. During evaluation, for each test query, retrieve top‑k using target embedding; compute TDR and ASR.

Design tradeoffs:
- Shadow model choice vs target model: Using a different shadow may reduce coverage transfer; the paper reports transferability anyway.
- δ quantile: Lower δ yields stricter coverage (fewer false positives) but may require more adversarial tools; higher δ increases coverage but risks including irrelevant tools.
- Greedy algorithm: Fast but suboptimal; may need more tools than the true minimum.
- Candidate pool size I and subset size n: Larger I and n increase coverage diversity but cost more LLM calls.

Failure signatures:
- TDR < expected: Check coverage matrix; many queries have <k covering candidates. Increase I or n, or relax δ.
- ASR << TDR: The selector LLM may be refusing to pick adversarial tools; verify prompt encourages a choice and parse output correctly.
- High injection rate on one benchmark (MetaTool) vs low on ToolBench suggests catalog size impacts coverage; small catalogs may need more injected tools to dominate.

First three experiments:
1. **Baseline replication**: Reproduce reported TDR and ASR on both benchmarks using the described pipeline with a fixed shadow model and LLM.
2. **Ablation on candidate pool size**: Vary I (number of LLM iterations) and n (subset size) to measure impact on coverage and injection rate.
3. **δ sensitivity across embedding models**: Compute δ on several common embedding models (e.g., all‑MiniLM‑L6‑v2, bge‑base, text‑embedding‑3‑small) and evaluate resulting TDR/ASR with the same candidate pool.

## Limitations
- The exact tool selection prompt used for ASR is unspecified, making ASR results sensitive to prompt wording.
- The shadow embedding model used to compute δ is not identified; δ=0.3 may not generalize to other models.
- The Q_gen/Q_test splits are not released; random splits introduce variability in reproduction.
- LLM generation parameters (temperature, top_p) and metadata formatting details are missing.

## Confidence
- **Greedy multi-cover algorithm** (correctness and theoretical guarantee): High
- **Reproduced attack effectiveness** (TDR/ASR numbers): Medium
- **Cross‑embedding model transferability**: Medium‑Low
- **MMR defense efficacy**: Low

## Next Checks
1. **Prompt reconstruction audit**: Design and test multiple plausible selection prompts to quantify ASR variance.
2. **δ sensitivity analysis**: Repeat the attack across a range of embedding models and quantiles to determine robustness of injection rates.
3. **Candidate pool coverage profiling**: After Phase 1, compute the fraction of queries with at least k covering candidates; if below threshold, increase I or n.
