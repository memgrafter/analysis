# Exploring Plan Space through Conversation: An Agentic Framework for LLM-Mediated Explanations in Planning

## Quick Facts
- arXiv ID: 2603.02070
- Source URL: https://arxiv.org/abs/2603.02070
- Reference count: 40
- Primary result: A multi-agent LLM architecture significantly improved subjective user experience (helpfulness, reduced difficulty) and interaction efficiency in iterative planning tasks.

## Executive Summary
This paper tackles the challenge of providing interactive explanations for AI planning systems to assist non-expert users in refining goal preferences. The proposed solution is a multi-agent LLM framework that converts natural language user questions into formal queries for an explanation engine based on Minimal Unsolvable Subsets (MUS) and Minimal Correction Sets (MCS). The system supports context-dependent conversations about goal conflicts and solvability. A user study with 131 participants on a complex planning task showed that the LLM-mediated interface led to statistically significant subjective improvements (helpfulness, difficulty reduction) and more efficient interactions, despite questions being fewer but richer in content.

## Method Summary
The method uses a web-based platform where users iteratively refine a set of planning goals. The backend employs four specialized LLM agents: T_Q (question classifier/dispatcher), T_G (goal translator, disabled in study), S_Q (question suggester), and T_E (explanation translator). User natural language questions are classified by T_Q and routed to the Explanation Framework (EFCC) which computes MUS/MCS to answer formal queries about conflicts and resolutions. The Planner (Fast Downward) generates sample plans. The study compared the LLM chat interface against a template-based menu interface, measuring utility achieved, number of questions, and subjective Likert scores. The LLM group used GPT-4.1-mini; EFCC queries were precomputed for the fixed set of 19 goals to ensure responsiveness.

## Key Results
- The LLM group reported higher perceived helpfulness (p=0.01) and lower task difficulty (p=0.02) compared to the template group.
- Average number of raw questions was lower in the LLM group (11.4 vs. 22.8), while the number of equivalent formal queries to EFCC was higher (41.7), indicating more efficient, multi-part interactions.
- The question suggester was adopted in 61.7% of interactions, and the question translator achieved 91% accuracy in classification and argument mapping across a manual review of 100 questions.

## Why This Works (Mechanism)
**Mechanism 1: Translation Offloads Cognitive Load**
- *Claim*: The multi-agent LLM architecture reduces user cognitive load by handling translation of natural language questions into formal queries.
- *Mechanism*: Specialized agents (Question Translator, Goal Translator) parse user intent and map to predefined formal question types (e.g., `S-why-not`) and goal representations (LTLf formulas). Users need not learn formal syntax.
- *Core assumption*: Users can articulate information needs naturally, and LLMs can reliably map them to the formal space required by the MUS/MCS engine.
- *Evidence*: The Dispatcher routes questions based on type classification (`µQ`), and the study reported 91% accuracy in classification and argument mapping.
- *Break condition*: A drop in classification accuracy (e.g., misrouting) would force users to rephrase, collapsing efficiency gains.

**Mechanism 2: Question Suggestions Accelerate Exploration**
- *Claim*: The Question Suggester increases efficiency by prompting users with contextually relevant questions, reducing the number of raw queries needed to achieve plan utility gains.
- *Mechanism*: The SQ agent analyzes the current iteration step (enforced/satisfied/unsatisfied goals, solvability) to generate 1–3 NL questions targeting unexplored conflicts or corrections.
- *Core assumption*: Users in complex domains struggle to formulate productive questions; curated suggestions guide inquiry more effectively.
- *Evidence*: The suggester was adopted in 61.7% of interactions, and the LLM group asked fewer total questions yet generated more formal queries per step, suggesting richer multipart interactions.
- *Break condition*: Irrelevant suggestions or over-reliance could diminish benefits.

**Mechanism 3: Context-Dependent Dialogue Reduces Overhead**
- *Claim*: Maintaining separate LLM contexts per iteration enables coherent multi-turn dialogues, reducing the need to re-specify goal references in follow-up questions.
- *Mechanism*: Each agent retains conversation history for the current step, allowing implicit reference resolution (e.g., "Can you enforce it?" referring to a previously mentioned goal).
- *Core assumption*: Conversational continuity lowers cognitive load compared to repeating full specifications.
- *Evidence*: The system design explicitly maintains separate contexts per step to avoid mixing information and reduce hallucinations; manual review showed 91% accuracy, implying context handling did not severely degrade performance.
- *Break condition*: If context windows overflow or cross-step references are missed, users must re-specify, increasing friction.

## Foundational Learning
**MUS/MCS**: Minimal Unsolvable Subsets (minimal unsatisfiable goal sets) and Minimal Correction Sets (minimal goal removals to achieve solvability). *Why needed*: The EFCC explanation engine uses MUS/MCS to answer user queries about conflicts and resolutions. *Quick check*: "Given goals {A, B, C} where {A,B} and {B,C} are MUS, what are the corresponding MCS?"

**Iterative Planning with Reference/Enforced Goals**: Each iteration step δ is defined by a reference set G_ref (all considered goals) and an enforced set G_enf (mandatory goals). The planner produces a sample plan π, and the framework evaluates goal satisfaction. *Why needed*: Question routing and explanation computation depend on solvability of τ(G_enf) and the satisfaction status of goals in π. *Quick check*: "In a solvable step with G_enf = {X} and π satisfying {X, Y}, what does G_false(π) contain?"

**Multi-Agent LLM Role Decomposition**: The system decomposes NL interaction into four specialized agents (T_Q, T_G, S_Q, T_E) each with distinct prompts and output schemas. *Why needed*: Decomposition simplifies the mapping from free-form dialogue to formal operations and keeps each agent's task well-defined. *Quick check*: "When a user asks 'Why can't I do music lesson?' in a solvable step, which agent first maps 'music lesson' to a formal goal, and which agent maps the question type to `S-why-not`?"

## Architecture Onboarding
**Component Map** (plain text):
Front-end (Angular) → Back-end (Node.js/Express) → LLM Agents (T_Q, T_G, S_Q, T_E) → Services (Planner, EFCC)

**Critical Path**:
1. User submits NL question Q_NL.
2. T_Q classifies µ_Q and extracts goal arguments G_NL.
3. If µ_Q ∈ M_Q and arguments map to existing goals → EFCC query with ⟨µ_Q, args⟩.
4. If arguments are new → T_G creates LTLf formula, updates G_ref_all, then EFCC query.
5. EFCC returns conflict/resolution sets E*(args).
6. T_E naturalizes answer using Q_NL, µ_Q, E*(args), and context.

**Design Tradeoffs**:
- *Same base LLM vs. specialized agents*: Using one model (GPT-4.1-mini) simplifies deployment but may not be optimal for each subtask; specialized fine-tuning could improve accuracy but adds complexity.
- *Per-step context isolation*: Prevents mixing and reduces hallucinations but loses long-term conversational memory across steps; cross-step follow-ups require explicit reference.
- *Precomputation for studies*: Ensures responsiveness but fixes the reference goal set; dynamic goal addition would require online EFCC updates.

**Failure Signatures**:
- T_Q misclassification (observed 9% error in manual review) leads to misrouted queries and user rephrasing.
- T_G errors (disabled in study) would produce invalid LTLf formulas and EFCC failures if enabled.
- T_E summarization failures (over-/under-inclusion of conflicts) may reduce answer faithfulness; not measured in the study.

**First 3 Experiments**:
1. Validate T_Q accuracy on a held-out test set of user NL questions; target >85% correct classification and argument mapping.
2. Measure SQ adoption impact via A/B test of prompt variants; track suggester click-through rate and resulting question diversity to quantify efficiency gains.
3. Compare LLM vs. template interfaces on time-per-iteration and EFCC queries per utility point; expect LLM group to have higher query efficiency.

## Open Questions the Paper Calls Out
1. How does the framework generalize across diverse planning domains and with expert users? Current study used a single instance with lay participants.
2. How effective are the goal translator (T_G) and explanation translator (T_E) in practice? T_G was disabled and TE summarization correctness was not evaluated.
3. Can the MUS/MCS-based explanation engine be extended to other paradigms (e.g., contrastive, CP), and should the system meta-select the best approach per question?
4. To what extent do UI/UX design choices (e.g., layout, input modality) independently influence the effectiveness of the conversational interface?
5. How does computational scalability of exponential MUS/MCS affect responsiveness for larger, realistic planning problems? Precomputation may not suffice for dynamic goal addition.

## Limitations
- Reverse-engineering the PDDL domain risks mismatches with the original problem instance.
- Missing full LLM prompts and EFCC implementation details hinders exact replication.
- The user study is limited to one domain with lay participants, and UI confounds make it hard to isolate the effect of the LLM agents.

## Confidence
- Subjective improvement (helpfulness, difficulty reduction): Medium
- Interaction efficiency (fewer raw questions, more formal queries): Medium
- Component reliability (translation accuracy, suggester adoption): Medium

## Next Checks
1. Conduct an independent accuracy test of T_Q on a held-out, diverse set of user queries to verify the reported 91% classification rate and identify common failure modes.
2. Perform an ablation study comparing the full LLM system against a rule-based translator while holding the UI constant, to isolate the contribution of LLM-mediated understanding.
3. Run a live user study with T_G enabled, measuring translation accuracy of new goals and its impact on planning utility and interaction length.
