# From Dead Pixels to Editable Slides: Infographic Reconstruction into Native Google Slides via Vision-Language Region Understanding

## Quick Facts
- arXiv ID: 2602.07645
- Source URL: https://arxiv.org/abs/2602.07645
- Reference count: 29
- Primary result: Images2Slides reconstructs editable Google Slides from infographic images with high element recovery (0.989) and low text error (CER 0.033).

## Executive Summary
The paper introduces Images2Slides, a system that transforms static infographic images into editable Google Slides presentations. By leveraging a vision-language model (VLM) to parse the image into regions of text and images, the pipeline extracts textual content via OCR, maps pixel coordinates to Slides points, and reassembles the elements using the Google Slides API. Evaluated on 29 programmatically generated infographics, the system achieves near-perfect element recovery (0.989) and low character error rate (0.033) for text, though layout fidelity (IoU) remains moderate.

## Method Summary
The pipeline begins with a VLM that receives the infographic image and produces a set of region-level specifications, each tagged as text or image. For text regions, OCR is applied; for images, the region is cropped. Pixel coordinates are converted to Google Slides point units using a linear scaling based on image dimensions. Text boxes are created with heuristics to approximate original font sizes and handle line breaks, while image boxes are placed with preserved aspect ratios. Backgrounds are synthesized either as solid colors or tiled patches to replace removed text regions. The final slide is built via the Slides API, inserting text boxes, images, and shapes.

## Key Results
- Element recovery rate: 0.989±0.057 (text: 0.985±0.083, images: 1.000)
- Mean text CER: 0.033±0.149
- Layout IoU: text 0.364±0.161, images 0.644±0.131

## Why This Works (Mechanism)
The success hinges on three factors: (1) The VLM's ability to ground both visual and textual elements into coherent regions, bridging the gap between raw pixels and semantic components. (2) The coordinate mapping and scaling heuristics that translate image space to Slides point space with reasonable accuracy. (3) The Slides API's flexibility in creating and positioning native elements, allowing reconstruction that preserves editability. However, the moderate text IoU indicates that text region segmentation and font metric calibration remain challenging.

## Architecture Onboarding
**Component map**: Input Image -> VLM Region Parser -> Region Classifier (text/image) -> OCR for text regions / Image Cropper for image regions -> Coordinate Mapper -> Slides API (Create TextBoxes, Images, Backgrounds) -> Output Slide

**Critical path**: Image ingestion -> VLM parsing -> region processing -> coordinate mapping -> API calls.

**Design tradeoffs**:  
- Simplicity vs. accuracy: Heuristics avoid complex modeling but reduce fidelity.  
- Generality vs. specificity: Handles many infographics but struggles with typographic nuances.  
- Automation vs. control: Fully automated may need user tweaks for perfect layout.

**Failure signatures**:  
- Over/under-segmented text blocks  
- Text overflow or misalignment  
- Background synthesis artifacts  
- Incorrect element placement (low IoU)

**First experiments**:  
1. Run pipeline on the 29 synthetic infographics and compute metrics.  
2. Ablate VLM region parser using ground-truth boundaries to isolate segmentation errors.  
3. Vary font scaling and line-breaking to improve text IoU.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: How can we improve text region segmentation to prevent over-segmentation (splitting paragraphs) and under-segmentation (merging logical blocks) in infographics?
- Basis in paper: [inferred] From failure modes in Table 4 (Section 8.4), where these issues are listed with heuristic mitigations (e.g., style-based merging), but persist and affect editability.
- Why unresolved: VLM-based extraction lacks fine-grained semantic understanding of text grouping, leading to regions that deviate from logical blocks, contributing to low text IoU (0.364±0.161).
- What evidence would resolve it: A controlled benchmark with ground-truth text block boundaries from real-world infographics, evaluating segmentation accuracy (precision/recall) and its impact on element recovery and layout fidelity metrics.

### Open Question 2
- Question: How can we enhance font metric calibration and text box sizing in Google Slides to better preserve the original infographic's typography and layout?
- Basis in paper: [explicit] Section 5 details a piecewise-linear font scaling and collision-aware width expansion, yet font metric mismatch remains a failure mode (Section 8.4), causing low text IoU despite accurate transcription (CER 0.033).
- Why unresolved: The calibration heuristics are based on limited observations and do not account for diverse font families, rendering engines, or complex line breaks, leading to overflow or misalignment.
- What evidence would resolve it: Comparative studies using rendered text analysis (e.g., OCR on reconstructed slides) or user assessments, testing adaptive algorithms for font substitution and dynamic line breaking across varied infographic styles.

### Open Question 3
- Question: How can we handle non-uniform or textured backgrounds to generate clean, editable slides without degrading foreground content or introducing synthesis artifacts?
- Basis in paper: [explicit] Section 7 proposes VLM-guided background synthesis (solid or tile modes), but acknowledges limitations for complex backgrounds as a failure mode (Section 8.4).
- Why unresolved: The approach relies on simple patch-based fill or tiling, which may not capture intricate gradients or patterns, and does not separate foreground from background, risking content loss or duplication.
- What evidence would resolve it: Evaluation on a diverse dataset of infographics with annotated background types, measuring background reconstruction quality (e.g., SSIM, user ratings) and foreground integrity preservation.

### Open Question 4
- Question: How can we extend the pipeline to reconstruct complex visual elements (e.g., charts, custom shapes) as native, editable Google Slides objects rather than raster images?
- Basis in paper: [explicit] Section 9 identifies a "raster-to-native gap" and cites chart derendering literature [21–24] as a potential path, but the current system only crops non-text regions as images.
- Why unresolved: The system lacks semantic parsing of visual elements, treating all non-text as raster assets, which limits editability (e.g., cannot modify chart data) and scalability for vector-based designs.
- What evidence would resolve it: Integration of chart understanding models to extract data tables or vector definitions, generating native Slides elements, with evaluation focused on editability of reconstructed components (e.g., successful data updates in charts).

## Limitations
- Evaluated on only 29 programmatically generated infographics, not real-world examples with noise, occlusion, or varied fonts.
- Layout IoU scores are moderate (text 0.364, images 0.644), indicating spatial fidelity gaps.
- Fixed coordinate mapping may fail with scaling, DPI variations, or border areas.

## Confidence
- Element recovery rate (0.989±0.057): High for synthetic data, Low for real infographics.
- Text CER (0.033±0.149): Medium—strong on clean text but variance suggests fragility.
- Layout IoU (text: 0.364±0.161, images: 0.644±0.131): Medium-Low—modest scores indicate room for improvement.
