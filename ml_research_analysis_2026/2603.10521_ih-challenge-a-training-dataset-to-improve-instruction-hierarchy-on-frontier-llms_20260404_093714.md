# IH-Challenge: A Training Dataset to Improve Instruction Hierarchy on Frontier LLMs

## Quick Facts
- **arXiv ID:** 2603.10521
- **Source URL:** https://arxiv.org/abs/2603.10521
- **Reference count:** 23
- **Primary result:** RL fine-tuning on IH-Challenge improved robustness against jailbreaks and prompt injections by +10.0% on average (84.1% to 94.1%) while reducing unsafe responses from 6.6% to 0.7%.

## Executive Summary
This paper introduces IH-Challenge, a reinforcement learning (RL) dataset designed to train language models to robustly resolve conflicts between instructions of different priority levels (e.g., system vs. user). By fine-tuning a model with online adversarial generation—where a separate, unsafeguarded attacker model synthesizes challenging low-priority messages—the defender learns to adhere strictly to high-priority instructions. The approach yields significant gains in robustness against jailbreaks, system prompt extraction, and prompt injection attacks, with minimal regression on standard capability benchmarks.

## Method Summary
The method uses RL fine-tuning on the IH-Challenge dataset, which contains training skeletons with high-priority instructions (system/developer messages) and placeholders for low-priority messages (user/tool). A frozen attacker model, lacking safety guardrails, generates adversarial low-priority messages via a budgeted propose–evaluate–revise loop: it proposes a candidate, inserts it into the skeleton, queries the current defender, receives binary feedback from a Python grader, and revises. The defender samples responses, which are scored by the same grader to compute rewards for policy gradient updates (likely PPO). Capability tasks are mixed in to prevent regression. Evaluation covers in-distribution held-out attacks, out-of-distribution benchmarks (e.g., TensorTrust, Gandalf), safety suites, and academic tasks.

## Key Results
- Robustness improved by +10.0% on average across 16 benchmarks (from 84.1% to 94.1%).
- Unsafe response rate on disallowed content dropped from 6.6% to 0.7% while maintaining helpfulness.
- Saturated performance on an internal prompt injection benchmark; minimal capability regression on GPQA Diamond, AIME, and chat win-rate.

## Why This Works (Mechanism)
The core mechanism is **adversarial reinforcement learning with programmatic rewards**. A frozen attacker continuously generates challenging, evolving low-priority messages that test the defender’s adherence to high-priority constraints. The Python grader provides a crisp, binary signal that directly encodes correct instruction hierarchy (IH) resolution, avoiding the ambiguity of LLM-based judges. This forces the defender to learn a generalizable "hierarchy reasoning" algorithm rather than surface-level heuristics. The online nature ensures training difficulty increases as the defender improves, and mixing in capability tasks preserves general helpfulness. The result is a model that internalizes role-based suppression of lower-priority instructions, transferring to diverse real-world attacks even those not seen during training.

## Foundational Learning
- **Instruction Hierarchy (IH):** The principle that higher-priority instructions (e.g., system messages) must override lower-priority ones (e.g., user requests). *Why needed:* Without explicit training, models often treat all instructions as equal, leading to vulnerabilities. *Quick check:* Can the model correctly ignore a user’s "ignore previous instructions" if a system message prohibits it?
- **Reinforcement Learning from Programmatic Feedback:** Using a deterministic grader (code) to assign rewards instead of human or LLM preferences. *Why needed:* Provides scalable, unambiguous supervision for complex IH rules. *Quick check:* Does the grader catch edge cases where a model tries to "game" the rule?
- **Adversarial Training:** Generating attacks via a separate model to probe weaknesses. *Why needed:* Static datasets become outdated; an adaptive attacker surfaces novel failure modes. *Quick check:* Does attack success rate decrease over training steps?
- **Overrefusal Mitigation:** Ensuring the model complies with non-conflicting, benign requests. *Why needed:* IH training can make models overly conservative. *Quick check:* Does the model fulfill a simple, harmless user request (e.g., "write a haiku") without refusal?
- **Capability Preservation:** Mixing standard tasks to avoid regression on general intelligence. *Why needed:* IH training alone might degrade helpfulness on unrelated queries. *Quick check:* Performance on GPQA or AIME remains within a small margin of the base model.
- **Role-Based Suppression:** The model’s internal mechanism for inhibiting responses that conflict with higher-priority role instructions. *Why needed:* This is the hypothesized algorithmic outcome of IH training. *Quick check:* Probe attention patterns to see if high-priority tokens suppress low-priority ones during generation.

## Architecture Onboarding
**Component Map:**  
Attacker Model (frozen, no safety) -> Proposed Low-Priority Message -> Skeleton (High-Priority + Placeholder) -> Defender Model (RL policy) -> Response -> Python Grader (Binary Pass/Fail) -> Reward -> RL Update (PPO) -> Updated Defender

**Critical Path:**  
1. For each skeleton, the attacker iteratively proposes and refines a low-priority message using the current defender’s responses and grader feedback.  
2. The defender samples a response to the completed adversarial prompt.  
3. The Python grader executes, checking if the response respects the high-priority constraints.  
4. The binary reward updates the defender via policy gradient.  
5. Periodically, capability data is mixed into the batch to maintain helpfulness.

**Design Tradeoffs:**  
- *Frozen vs. Co-trained Attacker:* A frozen attacker is stable and computationally cheap but may plateau in generating diverse, hard attacks. Co-training could yield stronger adversaries but risks goal drift and instability without a programmatic reward oracle.  
- *Programmatic vs. LLM Grading:* Code-based graders are precise and scalable but limited to tasks with clear, testable rules. They cannot evaluate nuanced safety or helpfulness, necessitating separate benchmarks.  
- *Online Adversarial Generation:* Ensures training pressure increases with defender capability but introduces engineering complexity (budgeting, rollout management) and potential reward hacking if the defender learns grader quirks.

**Failure Signatures:**  
- *Overrefusal:* The model refuses benign, non-conflicting requests (high failure on Anti-Overrefusal split).  
- *Reward Hacking:* Responses that technically pass the grader (e.g., exploiting parser loopholes) but violate the spirit of the hierarchy constraint; detectable via manual audit.  
- *Capability Regression:* Drop on academic or chat benchmarks, indicating the model has become overly conservative or lost general skills.  
- *Attacker Saturation:* Defender improvement plateaus because the frozen attacker cannot generate sufficiently novel or difficult conflicts.

**First Three Experiments:**  
1. **Reproduce RL Training Pipeline:** Implement the propose–evaluate–revise attacker loop and PPO defender update on Llama-3.1-8B-Instruct using the public IH-Challenge dataset. Verify that each training step produces valid attacks and that rewards increase over time.  
2. **Public Benchmark Transfer:** Evaluate the trained model on TensorTrust, Gandalf Password, and standard prompt injection suites. Compare robustness and overrefusal against the base model and a model fine-tuned only on capability data.  
3. **Qualitative Error Analysis:** Manually inspect 100 failed cases from the held-out attack set. Categorize failures as: (a) genuine IH violation, (b) overrefusal, (c) capability error (e.g., incoherent response), or (d) grader bypass (reward hacking).

## Open Questions the Paper Calls Out
**Open Question 1:** Does simultaneously training both the attacker and defender models in an adversarial RL loop yield greater robustness gains than the paper's fixed-attacker approach, and can this be stabilized without programmatic reward signals?
**Open Question 2:** What specific architectural or training mechanisms in GPT-5-Mini-R enable the observed generalization from programmatically gradeable, IF-simple IH tasks to complex, LLM-graded safety and prompt-injection evaluations?
**Open Question 3:** To what extent do the "system mitigations" (e.g., output monitor, sandwich) interfere with the intrinsic robustness gained from IH-Challenge training, and what causes the observed capability drop when they are combined?
**Open Question 4:** Can the Anti-Overrefusal task family in IH-Challenge fully decouple robust instruction hierarchy compliance from misgeneralized refusal behaviors, or does it introduce new shortcut risks specific to its design?
**Open Question 5:** How stable and scalable is the online adversarial synthesis process using a frozen, unsafeguarded attacker model as the defender improves, and does the attacker's lack of safety guardrails introduce unintended biases or limitations in the diversity of learned conflicts?

## Limitations
- Hyperparameters for RL (learning rate, PPO clip, batch size) and attacker rollout budget are undisclosed, affecting replication fidelity and performance.
- The attacker model ("anti-refusal GPT-5") is incompletely specified; its training data and prompting scheme are unknown, obscuring the adversarial distribution.
- Reward hacking remains a risk: models may output responses that trick the Python grader without truly respecting hierarchy.
- Generalization claims beyond the evaluated benchmarks (e.g., to multimodal or non-English contexts) are untested.

## Confidence
- **Robustness improvement (+10% across 16 benchmarks):** Medium. Evidence is empirical and consistent, but performance is hyperparameter-sensitive and may not transfer to all architectures.
- **Safety improvement (unsafe ↓6.6%→0.7%):** Medium. Depends on the specific safety evaluation suite; broader safetygeneralization is unproven.
- **Maintained helpfulness/capability:** Medium. Validated on limited academic tasks (GPQA, AIME) and chat win-rate; other capabilities (coding, creativity) are unexamined.
- **Saturation on internal prompt injection benchmark:** Low. The benchmark is not public, making verification impossible.
