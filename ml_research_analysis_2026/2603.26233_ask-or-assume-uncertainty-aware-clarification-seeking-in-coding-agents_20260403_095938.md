# Ask or Assume? Uncertainty-Aware Clarification-Seeking in Coding Agents

## Quick Facts
- **arXiv:** 2603.26233  
- **Source:** https://arxiv.org/abs/2603.26233  
- **References:** 40  
- **Primary result:** Multi-agent uncertainty-aware scaffolding achieves 69.40% task resolve rate on underspecified SWE-bench Verified, significantly outperforming single-agent (61.20%, p<0.001) and nearly matching fully-specified (70.80%).  

## Executive Summary
Large language model (LLM) coding agents often fail to ask clarifying questions when given underspecified instructions, leading to incorrect assumptions and task failure. This paper introduces a multi-agent scaffold that explicitly decouples underspecification detection from code execution. A dedicated Intent Agent continuously monitors the interaction history and tool outputs, pausing the Main Agent whenever missing information is detected and constraining it to generate targeted clarification queries. Evaluated on an underspecified variant of SWE-bench Verified using Claude Sonnet 4.5, the system (UA-MULTI) resolves 69.40% of tasks—a significant improvement over a single-agent uncertainty-aware baseline (61.20%) and approaching the performance of a fully-specified oracle (70.80%). The multi-agent approach exhibits well-calibrated uncertainty, asking concise, iterative questions distributed throughout the execution while conserving queries on simpler tasks. These results demonstrate the value of role specialization and continuous monitoring for building interactive coding agents capable of handling ambiguous real-world software issues.

## Method Summary
The study evaluates LLM coding agents on 500 underspecified software engineering tasks derived from SWE-bench Verified. Underspecified versions are created by withholding details (e.g., file paths, code snippets) from original GitHub issues using GPT-4o. A GPT-5.1 user simulator, holding the full original issue, answers clarification questions under strict guardrails (no test edits, no workspace/testbed confusion). Agents are built with the OpenHands framework and use Claude Sonnet 4.5 as the backbone LLM. The proposed multi-agent scaffold consists of: a Main Agent that performs code edits and test executions via tools (Read, Edit, Execute, Bash); an Intent Agent that consumes a summarized trajectory each turn and outputs a binary `needs_clarification` decision; and an Orchestrator that runs the Intent Agent and, if underspecification is flagged, forces the Main Agent to ask a targeted question instead of executing. Baselines include: `FULL` (complete specification, no interaction), `HIDDEN` (underspecified, no interaction), `INTERACTIVEBASELINE` (underspecified with explicit instruction to query upfront), and `UA-SINGLE` (single agent with a reminder to self-assess underspecification each turn). The primary metric is task resolve rate: a patch is considered successful if it passes all tests in the sandboxed environment.

## Key Results
- **UA-MULTI resolves 69.40%** of underspecified tasks, significantly higher than UA-SINGLE (61.20%, p<0.001) and nearly matching the FULL baseline (70.80%).  
- Queries are distributed across early (41.8%) and mid (43.4%) stages, and are concise (average 171.57 tokens) with correspondingly short answers (173.65 tokens), contrasting with INTERACTIVEBASELINE’s verbose upfront questions.  
- The system exhibits **well-calibrated uncertainty**: ask rate correlates with human-annotated task difficulty, conserving queries on simpler tasks.  

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Decoupling the roles of underspecification detection and code execution improves the agent's ability to identify and resolve missing information.  
- **Mechanism:** A specialized **Intent Agent** continuously monitors the interaction history and tool outputs independently from the **Main Agent** that performs edits and executions. When the Intent Agent detects ambiguity or missing information, it halts the Main Agent and constrains its next action to a user query. This separation allows the Intent Agent to focus solely on contextual interpretation without the cognitive load of simultaneous code generation.  
- **Core assumption:** A single agent (UA-SINGLE) suffers from impaired underspecification detection because its internal state is partitioned between reasoning about code and reasoning about information gaps; a dedicated monitor can maintain a more coherent assessment of the task's information completeness.  
- **Evidence anchors:**  
  - [abstract] "explicitly decouples underspecification detection from code execution... significantly outperforming a standard single-agent setup"  
  - [section 2.2] "to decouple code execution from underspecification detection, we design a multi-agent scaffold consisting of two agents: the Main Agent... and the Intent Agent that continuously analyzes the state history"  
  - [corpus] Related work (e.g., Ambig-SWE, TOM-SWE) also explores interactive agents for underspecification but does not explicitly decouple detection from execution; this paper provides comparative evidence for the architectural split's benefit.  
- **Break condition:** If the Intent Agent's analysis becomes consistently misaligned with actual task requirements (e.g., flagging clear tasks or missing clear ones), the decoupling advantage collapses, and performance would regress to or below the single-agent baseline.

### Mechanism 2
- **Claim:** Continuous, mid-trajectory monitoring enables proactive and iterative clarification-seeking, preventing the agent from committing to faulty assumptions early.  
- **Mechanism:** The Intent Agent reassesses the need for clarification at every turn based on the latest observations (file reads, test outputs, error messages). This allows it to ask follow-up questions in response to new evidence (e.g., a test failure revealing a hidden constraint), rather than relying on a single, upfront assessment of the issue description.  
- **Core assumption:** Information needs in complex software tasks are dynamic and often only become apparent after initial exploration; a one-time "assessment" prompt (as in UA-SINGLE) is insufficient for robust calibration.  
- **Evidence anchors:**  
  - [section 3] "explicitly isolating the intent-detection role improved how the agent interacted... UA-MULTI distributed its queries across the early and middle stages"  
  - [section B.1] Table 2 timing distribution: UA-MULTI queries are 41.8% Early and 43.4% Mid, while UA-SINGLE is 43.9% Late.  
  - [section B.4] Figure 6 shows UA-MULTI asking a mid-execution follow-up question after a test failure ("Should I continue debugging why the changes aren’t taking effect?").  
- **Break condition:** If the majority of critical missing information were present in the initial issue description (i.e., underspecification is static and predictable), continuous monitoring would confer no benefit and only add overhead.

### Mechanism 3
- **Claim:** Concise, context-specific queries yield shorter, more relevant user responses, improving the efficiency of information retrieval.  
- **Mechanism:** Because the Intent Agent observes the Main Agent's recent actions (e.g., which file was just read, what error occurred), it can formulate highly targeted questions that reference concrete intermediate states. This contrasts with the INTERACTIVEBASELINE's strategy of asking broad, exhaustive questions upfront based only on the initial (underspecified) prompt.  
- **Core assumption:** The simulated (or real) user's ability to provide useful answers is constrained by the specificity of the question; vague questions invite long, unfocused replies that may still miss the critical detail.  
- **Evidence anchors:**  
  - [section B.1] Table 2: UA-MULTI has the shortest average query length (171.57 tokens) and receives the shortest average answer length (173.65 tokens), while INTERACTIVEBASELINE has the longest query (251.33) and answer (415.53).  
  - [section B.4] Figure 6: UA-MULTI's questions directly reference observed states ("after modifying the source code... the test still fails"), while INTERACTIVEBASELINE asks generic "What is the specific Python expression?".  
  - [corpus] Limited direct corpus evidence on query conciseness → user answer efficiency in this domain; this is an inferred mechanism from the presented statistics.  
- **Break condition:** If user responses were uniformly terse or uninformative regardless of query specificity, the length difference would not translate to a resolution rate advantage.

## Foundational Learning
### Concept: Uncertainty Calibration in LLMs
- **Why needed here:** The entire scaffold relies on the LLM's ability to accurately assess whether its current knowledge is sufficient. Poor calibration (overconfidence or underconfidence) would lead to either too many unnecessary queries or a failure to query when needed.  
- **Quick check question:** Given a trajectory where a test fails with a cryptic error after an initial edit, should the agent query the user? What specific signal in the history would indicate high uncertainty?

### Concept: Multi-Agent System Design (Role Specialization)
- **Why needed here:** The core innovation is separating "thinking about what's missing" from "doing the coding." Understanding this pattern—assigning distinct roles with explicit handoff protocols—is key to extending the approach.  
- **Quick check question:** If you were to add a third agent (e.g., a "Planner" that creates a high-level plan before the Main Agent executes), how would the communication protocol between agents need to change? Where would the Intent Agent's monitoring point shift?

### Concept: SWE-bench Verified Task Structure
- **Why needed here:** The evaluation environment defines the constraints (sandbox, tools, test harness, iteration limits) and the nature of the "underspecified" inputs (summarized GitHub issues). Misunderstanding the task structure leads to flawed experiment design.  
- **Quick check question:** Why is the `FULL` baseline's resolve rate (70.80%) not 100%? What does that imply about the inherent difficulty of the tasks beyond mere underspecification?

## Architecture Onboarding
### Component map
Main Agent -> Orchestrator -> Intent Agent; Orchestrator -> Main Agent (forces clarify or permits execution); Main Agent -> User Simulator (clarification) OR Main Agent -> Task Environment (execution); Output (user answer or tool result) -> Orchestrator -> history.

### Critical path
1. Start turn: Main Agent proposes next action (tool call or finish).  
2. Orchestrator pauses execution and compiles the turn's history summary.  
3. Intent Agent processes summary → outputs `needs_clarification`.  
4. **If true:** Orchestrator discards Main Agent's proposed action. Prompts Main Agent: "Intent Agent detected underspecification: [reasons]. Formulate a clarification question." Main Agent generates a `clarify` tool call with the question.  
5. **If false:** Orchestrator allows Main Agent's original proposed action to execute.  
6. Tool output / user simulator reply is appended to history. Loop back to step 1 (max 100 iterations).

### Design tradeoffs
- **Cost vs. Performance:** Multi-agent ~2x cost of single-agent ($3.50 vs $2.03/task) for ~8% absolute gain over HIDDEN. Justifiable if developer time savings outweigh API costs.  
- **Simplicity vs. Control:** The Intent Agent is a lightweight monitor, not a full planner. This keeps it focused but means it can't *plan* the clarification; it only flags the *need*.  
- **Generality vs. Prompt Sensitivity:** The scaffold is framework-agnostic (works with any LLM/toolset) but heavily dependent on the Intent Agent's system prompt and the "reminder" for the single-agent. Small prompt tweaks could drastically change behavior.

### Failure signatures
- **Late Querying:** Agent executes many steps, then asks a question that reveals a foundational misunderstanding. Suggests Intent Agent is not reacting to early signals or Main Agent is proceeding without adequate context checks.  
- **Verbose/Generic Queries:** Long, multi-part questions that ask for all possible missing info upfront. Suggests Intent Agent is not leveraging the dynamic history (behaving like INTERACTIVEBASELINE).  
- **No Queries on Hard Tasks:** Agent fails to ask on tasks that are clearly underspecified (e.g., missing file path, key config). Suggests Intent Agent prompt is not sensitive enough to concrete obstacles like "FileNotFoundError".  
- **Circular Queries:** Agent asks, gets answer, then asks the same or a very similar question again. Suggests state summary is not persistent or Intent Agent is not incorporating user answers into its assessment.

### First 3 experiments
1. **Baseline Replication:** Run `HIDDEN`, `FULL`, and `INTERACTIVEBASELINE` to establish the performance gap and confirm the hardcoded prompt forces interaction.  
2. **Single-Agent Uncertainty:** Implement UA-SINGLE with the reminder prompt. Measure ask rate and resolve rate vs. `HIDDEN`. Verify it outperforms `HIDDEN` but still lags `INTERACTIVEBASELINE`.  
3. **Multi-Agent Scaffold:** Implement UA-MULTI with separate Intent Agent. Measure the key outcomes: overall resolve rate (vs. UA-SINGLE), query distribution (early/mid/late), and query conciseness. Validate the "well-calibrated" claim by correlating ask rate with human-annotated task difficulty.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Can a single language model be trained via finetuning or reinforcement learning to natively exhibit the calibrated, proactive clarification-seeking behavior of the multi-agent scaffold?  
- **Basis in paper:** The authors suggest future work could explore training single models on successful interaction trajectories to natively exhibit calibrated information-seeking behavior.  
- **Why unresolved:** It is unknown whether the multi-agent scaffold's behavior can be internalized into a single model without performance degradation or additional scaffolding.  
- **What evidence would resolve it:** Train a single model on the UA-MULTI interaction trajectories and evaluate its uncertainty calibration and task resolve rate on the underspecified SWE-bench Verified dataset, comparing to the original multi-agent system.

### Open Question 2
- **Question:** How do the uncertainty-aware agents generalize to real human users, given that the study relied on an LLM-based user simulator that may not reflect human interaction patterns?  
- **Basis in paper:** The authors note that results may vary if real human users interact with the agents, citing studies that LLM-simulated users are unreliable proxies.  
- **Why unresolved:** The user simulator may be overly cooperative or miss nuances, potentially inflating agent performance or hiding deficiencies in clarification strategies.  
- **What evidence would resolve it:** Conduct a user study where human participants interact with the agents on a subset of underspecified tasks, measuring resolve rate, query relevance, and user satisfaction compared to simulator results.

### Open Question 3
- **Question:** Is the multi-agent uncertainty-aware scaffold effective for open-weight language models that currently lack strong internal calibration for interactive underspecification?  
- **Basis in paper:** The authors state that open-weight models severely lack the internal calibration required for interactive underspecification, and their findings may be limited to frontier models.  
- **Why unresolved:** All experiments used Claude Sonnet 4.5; it is unclear whether the scaffold's success depends on the model's inherent capabilities or can compensate for weaker calibration.  
- **What evidence would resolve it:** Replicate the experiments with state-of-the-art open-weight models (e.g., Llama 3.1, CodeLlama) using the UA-MULTI scaffold, measuring resolve rates, ask rates by difficulty, and calibration metrics.

### Open Question 4
- **Question:** What is the quantitative trade-off between the increased computational cost of the multi-agent system and the resulting gains in developer productivity?  
- **Basis in paper:** The authors mention that the increased inference overhead must be weighed against gains in developer productivity, providing cost breakdowns but no productivity metrics.  
- **Why unresolved:** The cost data exists but the actual productivity impact (e.g., time saved, reduced debugging effort) is not measured, leaving the trade-off unclear.  
- **What evidence would resolve it:** Conduct an A/B test with developers solving underspecified tasks with either the multi-agent system or a baseline, measuring time to solution, iterations, and error rates, then relate the extra inference cost to compute a cost-benefit ratio.

## Limitations
- **Simulator fidelity:** GPT-5.1 user simulation may not reflect real human ambiguity tolerance or response patterns.  
- **Prompt/implementation gaps:** Missing precise prompts for underspecification generation, agent system messages, and tool schemas hinder exact replication.  
- **Generalization scope:** Results are tied to SWE-bench Verified and Claude Sonnet 4.5; performance on other models/domains is unknown.

## Confidence
- Decoupling detection from execution improves performance: **High**  
- Continuous monitoring yields proactive, iterative queries: **Medium**  
- Concise, context-specific queries yield shorter user responses: **Low**
