# LiveWeb-IE: A Benchmark For Online Web Information Extraction

## Quick Facts
- **ArXiv ID**: 2603.13773
- **Source URL**: https://arxiv.org/abs/2603.13773
- **Reference count**: 40
- **Primary result**: VGS with GPT-4o achieves 48.58% F1 score on LiveWeb-IE, more than doubling the next best baseline (AutoScraper at 26.76%).

## Executive Summary
Existing web information extraction (WIE) benchmarks rely on static HTML snapshots, which fail to capture the temporal dynamics of live websites. This paper introduces LiveWeb-IE, a benchmark that evaluates WIE systems directly on live, permission-granted sites. It comprises 15 diverse websites across 8 domains, with natural language queries targeting text, images, and hyperlinks at four complexity levels. Alongside the benchmark, the authors propose the Visual Grounding Scraper (VGS), a multi-stage framework that emulates human visual scanning: it decomposes queries into attributes, visually grounds relevant page regions, pinpoints exact elements via bounding boxes, and synthesizes robust XPaths. Extensive experiments show VGS with GPT-4o achieves 48.58% F1, significantly outperforming strong baselines (CoT, Reflexion, AutoScraper). VGS also attains state-of-the-art results on existing WIE benchmarks. Ablation studies confirm the contributions of visual grounding and pinpointing, while error analysis highlights remaining challenges in visual reasoning.

## Method Summary
LiveWeb-IE was constructed by selecting 15 live websites with explicit permission, spanning domains such as e-commerce, news, and social media. For each site, natural language queries were manually crafted to request specific information (e.g., product price, article author) at varying complexity levels, from single-field to multi-field aggregation. Evaluations are performed via live crawling to account for dynamic content and layout changes. VGS is a modular pipeline: a query decomposer parses the natural language query into structured attributes; a visual grounder (using a vision-language model) identifies a bounding box covering the relevant region on a screenshot; a pinpoint module examines DOM elements within that region to select the precise target; finally, an XPath synthesizer generates a robust selector. The system is implemented with GPT-4o as the backbone LLM and a proprietary vision model for grounding. Performance is measured using F1 score against manually annotated ground truth.

## Key Results
- VGS (GPT-4o) achieves 48.58% F1 on LiveWeb-IE, more than doubling the next best baseline (AutoScraper at 26.76%).
- VGS significantly outperforms strong baselines (Chain-of-Thought, Reflexion, AutoScraper) across multiple backbone models.
- Ablation studies show that both visual grounding and element pinpointing stages contribute substantially; removing either causes >10% absolute drop in F1.

## Why This Works (Mechanism)
VGS's multi-stage design mirrors human visual scanning, breaking a complex extraction problem into manageable sub-tasks. Query decomposition reduces cognitive load, allowing each module to focus on a specific aspect. Visual grounding grounds language in the page's spatial layout, efficiently filtering irrelevant regions. Pinpointing ensures accurate element selection within the coarse region. Robust XPath synthesis mitigates brittleness to minor DOM changes, improving reliability over time. This modularity also enables independent optimization and graceful degradation—if one stage underperforms, others may still provide partial signals.

## Foundational Learning
- **Visual Grounding**: Mapping textual concepts to spatial page regions. *Why needed*: Web pages are visually complex; locating relevant areas without rendering is extremely hard. *Quick check*: Can the system identify the section containing a product's price without scanning the entire DOM?
- **Query Decomposition**: Breaking a natural language request into structured attributes and constraints. *Why needed*: Direct end-to-end extraction is error-prone; decomposition isolates sub-problems. *Quick check*: Does the system correctly parse "the cheapest laptop under $1000" into price and sorting constraints?
- **Robust XPath Synthesis**: Generating XPath selectors resilient to layout changes. *Why needed*: Hard-coded XPaths break easily with minor DOM updates; robust selectors maintain long-term reliability. *Quick check*: Does the XPath still point to the same element after a small perturbation in the DOM hierarchy?
- **Element Pinpointing**: Selecting the exact HTML element within a bounded region. *Why needed*: Bounding boxes are coarse; the target may be a small text node or image. *Quick check*: Can the system choose the correct `<span>` for a product rating when multiple ratings exist in the same area?
- **Multi-stage LLM Reasoning**: Using language/vision models sequentially, each focused on a sub-task. *Why needed*: Complex tasks benefit from specialized reasoning; components can be debugged and improved independently. *Quick check*: Does improving visual grounding alone lead to overall performance gains?

## Architecture Onboarding
**Component map**: Query Decomposer -> Visual Grounder -> Pinpointer -> XPath Synthesizer

**Critical path**: The input natural language query is first parsed by the Decomposer into structured attributes. These attributes, together with a screenshot of the target page, are fed to the Visual Grounder, which outputs a bounding box covering the relevant region. The Pinpointer then examines DOM elements overlapping that region to select the precise target element(s). Finally, the XPath Synthesizer produces a robust selector based on the element's attributes and context.

**Design tradeoffs**:
- Relying on a powerful vision model (e.g., GPT-4o) yields accurate grounding but introduces latency, cost, and API dependence; a lighter model would be faster but less reliable.
- XPath offers broad tool compatibility, but synthetic XPaths can become brittle if overfitted; the synthesis step must balance specificity and robustness.
- Modularity improves debuggability and component-wise optimization, but may propagate errors if early stages fail.

**Failure signatures**:
- Visual grounding returns an empty or irrelevant bounding box → subsequent stages have no valid input.
- Pinpointing selects an adjacent or wrong element within the region → extracted fields are incorrect.
- XPath synthesis yields a selector that matches multiple elements or none → extraction fails or returns noise.
- Decomposer produces inconsistent or incomplete attributes → downstream modules receive flawed specifications.

**First experiments**:
1. Ablate the visual grounding module (e.g., use the entire page) to measure its contribution to overall F1.
2. Evaluate VGS with different LLM backbones (GPT-4o, Claude 3.5 Sonnet, Llama 3.1 70B) to assess sensitivity and cost-performance trade-offs.
3. Compare VGS performance on live pages versus static snapshots (frozen JavaScript) to quantify the impact of dynamic content.

None reported.

## Limitations
- The benchmark uses only 15 permission-granted sites across 8 domains, limiting generalizability to the broader web ecosystem.
- VGS's strong performance is demonstrated primarily with GPT-4o; its effectiveness with smaller or open-source models remains under-evaluated.
- LiveWeb-IE does not explicitly control for or measure performance under high-frequency dynamic updates (e.g., real-time tickers), leaving a gap in assessing robustness to rapid change.

## Confidence
- LiveWeb-IE successfully evaluates WIE on live websites: **High**
- VGS substantially outperforms existing baselines on LiveWeb-IE: **Medium** (constrained by limited site diversity and single-model dominance)
- VGS achieves state-of-the-art results on existing WIE benchmarks: **Medium** (possible benchmark-specific tuning and protocol differences)

## Next Checks
1. Diversify the evaluation corpus: re-run VGS and baselines on a larger, more domain-balanced set of live sites (e.g., 50+ sites across 20+ domains), including sites with heavy JavaScript-driven dynamics.
2. Model-agnostic robustness test: evaluate VGS using a spectrum of LLMs (e.g., GPT-4o, Claude 3.5 Sonnet, Llama 3.1 70B) to quantify performance sensitivity and cost-performance trade-offs.
3. Human-gold standard comparison: conduct a user study where humans extract data from the same LiveWeb-IE queries on live sites; compare VGS's F1 against human agreement scores to quantify the real-world performance gap.
