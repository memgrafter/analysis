# Detection of adversarial intent in Human-AI teams using LLMs
## Quick Facts
- **ArXiv ID:** 2603.20976
- **Source URL:** https://arxiv.org/abs/2603.20976
- **Reference count:** 40
- **Primary result:** LLM-based detection achieves 81–82% accuracy with a 10‑round context; fine‑tuned small model reaches 100% recall with a 17.8% false positive rate, and streaming thresholding yields ~78% accuracy for real‑time oversight.

## Executive Summary
The paper introduces a task‑agnostic method for detecting adversarial AI behavior within human‑AI teams using only observable interaction traces. Leveraging data from a 25‑round trivia game, the authors serialize conversations and decisions into JSON and employ large language models as binary classifiers. With a 10‑round context, GPT‑4.1 and GPT‑o3 attain statistically significant detection accuracy of 81–82%. Smaller models and minimal context (1 round) suffer from a benign bias, yielding zero recall. However, fine‑tuning GPT‑4.1‑mini on just 50 samples restores recall to 100% at a 17.8% false positive rate. Applying a threshold of three consecutive malicious round classifications in streaming mode gives approximately 78% accuracy, demonstrating a viable path to real‑time adversarial oversight.

## Method Summary
Data were collected from human participants and AI agents engaged in a 25‑round trivia game, where some AI agents acted adversarially. Raw interaction logs (dialogue messages and decision outcomes) were transformed into structured JSON objects that encode speaker identity, utterance content, and results for a given context window. These JSON samples served as input to pre‑trained language models, prompted to classify the interaction as “normal” (0) or “malicious” (1). The study varied the number of preceding rounds included as context (1 or 10 rounds). For smaller models, GPT‑4.1‑mini was fine‑tuned on 50 labeled JSON examples. Streaming detection was achieved by aggregating round‑level predictions and raising an alert only after three consecutive malicious classifications. Performance metrics include accuracy, recall, and false positive rate.

## Key Results
- With a 10‑round context, GPT‑4.1 and GPT‑o3 achieve 81–82% detection accuracy, significantly above chance.
- Smaller models and 1‑round contexts suffer from benign bias, resulting in 0% recall for malicious cases.
- Fine‑tuning GPT‑4.1‑mini on 50 samples yields 100% recall with a 17.8% false positive rate; using a 3‑consecutive‑malicious threshold in streaming mode gives ~78% accuracy.

## Why This Works (Mechanism)
LLMs possess strong language understanding capabilities, enabling them to recognize subtle patterns in multi‑party dialogue that signal adversarial intent. Serializing interactions into JSON provides a consistent, structured representation that the models can parse efficiently. A multi‑round context window allows the classifier to observe temporal trajectories, catching deviations that might be invisible in a single round. Fine‑tuning adapts a compact model to the detection task, overcoming its default tendency to assume benign behavior and improving sensitivity.

## Foundational Learning
1. **Serialization of Interaction Traces**  
   - *Why needed*: Converts unstructured dialogue into a structured JSON schema, preserving speaker, utterance, and decision fields for reliable model parsing.  
   - *Quick check*: Validate that all necessary fields are present and tokenization behaves as expected on sample rounds.

2. **Context Window Management**  
   - *Why needed*: Captures temporal dependencies; adversarial actions often reveal themselves over multiple rounds.  
   - *Quick check*: Experiment with varying context lengths (1,3,5,10) to determine the minimal effective window for the target model.

3. **Binary Classification with LLMs**  
   - *Why needed*: Leverages general language knowledge to detect malicious intent without handcrafted features.  
   - *Quick check*: Calibrate on a validation set; adjust prompt and threshold to balance precision and recall.

4. **Benign Bias in Small/Context‑Limited Models**  
   - *Why needed*: Highlights a failure mode where the model defaults to the majority “normal” class, yielding zero recall.  
   - *Quick check*: Monitor confusion matrix; if recall is near zero, increase context size or apply fine‑tuning.

5. **Fine‑Tuning for Task Adaptation**  
   - *Why needed*: Adapts model weights to recognize task‑specific adversarial cues and mitigates benign bias.  
   - *Quick check*: After fine‑tuning, evaluate on a held‑out set to ensure recall improves without excessive false positives.

6. **Streaming Thresholding**  
   - *Why needed*: Reduces noise in real‑time detection by requiring consecutive malicious predictions before raising an alert.  
   - *Quick check*: Sweep threshold values (1–5) on a validation stream and select based on F1 score or acceptable false positive rate.

## Architecture Onboarding
**Component Map:**  
RawInteractionLogs -> JSONSerializer -> LLMClassifier -> StreamAggregator -> AlertSystem

**Critical Path:**  
1. Collect raw interaction data from the trivia game environment.  
2. Serialize data into JSON with the chosen context window.  
3. Feed JSON to the LLM classifier (zero‑shot large model or fine‑tuned small model).  
4. In streaming mode, aggregate predictions over successive rounds and apply a consecutive‑malicious threshold.  
5. Emit an alert when the threshold is met, indicating potential adversarial intent.

**Design Tradeoffs:**  
- *Context length vs. latency*: Longer context improves accuracy but increases token count and inference time; latency‑sensitive applications may need shorter windows.  
- *Model size vs. cost/performance*: Large models deliver high accuracy (80%+) but are slower and more expensive; small models are efficient but require fine‑tuning and may yield higher false positives.  
- *Threshold sensitivity*: Lower threshold (e.g., 1 consecutive malicious) increases sensitivity but may cause alert fatigue; higher threshold (e.g., 3) reduces false positives at the risk of missing brief adversarial bursts.

**Failure Signatures:**  
- *Benign bias*: All predictions are “normal,” missing malicious cases.  
- *Over‑alerting*: False positive rate >20% or frequent alerts, indicating an overly sensitive threshold or classifier.  
- *High latency*: Inference time exceeds operational limits, especially with large models and 10‑round context.  
- *Poor generalization*: Performance degrades on new tasks, suggesting overfitting to game‑specific artifacts.

**First Experiments:**  
1. Measure zero‑shot accuracy of GPT‑4.1 and GPT‑o3 across context lengths (1, 3, 5, 10 rounds) on the trivia dataset.  
2. Fine‑tune GPT‑4.1‑mini on 50 labeled samples; evaluate recall and false positive rate on a held‑out set.  
3. Simulate streaming detection by feeding sequential round predictions from the fine‑tuned model into a threshold filter; vary the consecutive‑malicious threshold and report accuracy/F1.

## Limitations
- *Domain narrowness*: Evaluation limited to a single trivia game; generalizability to other human‑AI collaboration tasks remains unknown.  
- *Data constraints*: Fine‑tuning used only 50 samples; the streaming threshold was selected without a proper held‑out validation set, risking overfitting and optimistic performance estimates.  
- *Model and context limitations*: Study covered only the GPT family; 1‑round context fails due to benign bias, while 10‑round context may be too slow for latency‑sensitive applications.

## Confidence
- Feasibility of task‑agnostic adversarial detection: **Medium**  
- Large models with 10‑round context achieve >80% accuracy: **High**  
- Fine‑tuned small model + streaming threshold enables real‑time oversight: **Low–Medium**

## Next Checks
1. Cross‑domain replication: Test the pipeline on at least two new human‑AI collaboration tasks (e.g., software development, strategic planning) and compare performance.  
2. Rigorous fine‑tuning evaluation: Increase adversarial training samples to ≥500, use proper train/validation/test splits, and report metrics (accuracy, recall, FPR) with confidence intervals.  
3. Threshold robustness study: On a held‑out streaming dataset, sweep consecutive‑malicious thresholds (1–5) and report accuracy/F1 to identify stable operating points.
