# A Human-in/on-the-Loop Framework for Accessible Text Generation

## Quick Facts
- **arXiv ID:** 2603.18879  
- **Source URL:** https://arxiv.org/abs/2603.18879  
- **Reference count:** 0  
- **Primary result:** Proposes a hybrid Human-in/on-the-Loop framework combining real-time human guidance and systematic post-generation review to ensure cognitive accessibility in text simplification, with traceable KPIs and closed-loop model adaptation.

## Executive Summary
This paper addresses the lack of human-centered evaluation in automatic text simplification for cognitive accessibility. It introduces a hybrid Human-in/on-the-Loop (HiTL/HoTL) framework that integrates user study evidence, Plain Language/Easy-to-Read standards, and accessibility metrics throughout generation and review. HiTL adjustments during generation incorporate user profile-specific judgments (e.g., from older adults and people with intellectual disabilities) via prompts or fine-tuning. Post-generation, HoTL supervision uses checklists and Event-Condition-Action (ECA) triggers to ensure compliance with standards and catch risks. Accessibility KPIs (comprehension scores, synonym acceptance, glossary activation) and a Composite Quality Index (weighted readability, semantic fidelity, structural clarity) enable automated decisions while maintaining auditability. Human feedback from HoTL edits and KPI trends feeds model adaptation (e.g., RLHF/DPO), creating a closed loop aligned with cognitive accessibility needs.

## Method Summary
The framework operationalizes a traceable workflow where text simplification is guided by constraints derived from user studies on complex word identification and synonym acceptance. During generation (HiTL), the system applies these constraints via prompting or fine-tuning, logging human interactions. After generation, automatic metrics (readability, BERTScore, SARI, DSARI, SAMSA) are evaluated against ECA rules; if thresholds are breached, outputs are escalated to expert reviewers (HoTL) who assess against a checklist mapping to PL/ER standards and human-centered validation methods. Approved edits and KPI trends (including the Composite Quality Index) are converted into preference data for model adaptation. Reproduction involves implementing the ECA engine, HiTL-constrained prompts, and HoTL review interface. Key unknowns include precise threshold calibration, integration of comprehension tests into the checklist, and the exact format for preference pairs in RLHF/DPO.

## Key Results
- Hybrid HiTL/HoTL framework that merges real-time interactive adjustments with systematic post-generation audit for cognitive accessibility.
- Operationalization of user study evidence and PL/ER standards into ECA triggers, review checklists, and accessibility KPIs (e.g., comprehension gains, synonym-acceptance rates).
- Composite Quality Index (0.4 readability, 0.3 semantic fidelity, 0.3 structural clarity) enables automated decisions while maintaining traceability; profile-specific thresholds ensure alignment with user comprehension.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Human-in-the-Loop (HiTL) adjustments during generation improve lexical and structural accessibility by incorporating user profile-specific judgments in real time.
- **Mechanism:** During text generation, the system integrates constraints derived from user studies (e.g., complex word identification patterns, synonym acceptance rates) via prompting or fine-tuning. Interaction logs (accepted/rejected edits) feed automatic evaluation, ensuring simplifications align with complementary profiles (older adults' broader coverage vs. ID participants' precision).
- **Core assumption:** Real-time human guidance can steer LLM outputs toward accessibility before full generation, reducing post-hoc correction needs.
- **Evidence anchors:**
  - [abstract] "Human-in-the-Loop (HiTL) contributions guide adjustments during generation."
  - [section 5.2] Describes encoding "user-validated resources... into prompts or... fine-tuning procedures" and using "interactive steps" based on CWI and synonym evidence.
  - [corpus] User study data (Section 4.1–4.2) shows divergent CWI precision/recall and acceptance patterns across profiles, motivating adaptive HiTL.
- **Break condition:** If human edits consistently contradict automatic readability gains (e.g., improving simplicity but harming domain adequacy), the HiTL guidance may be misaligned with user comprehension needs. *Assumption: This would be detectable via HoTL review patterns.*

### Mechanism 2
- **Claim:** Human-on-the-Loop (HoTL) supervision via structured checklists and Event-Condition-Action (ECA) triggers ensures outputs meet PL/ER standards and catches accessibility risks missed by automation.
- **Mechanism:** After generation, automatic metrics are checked against ECA rules (e.g., readability gain but low BERTScore). If thresholds are breached, cases escalate to expert review against a checklist integrating standards (ISO, UNE) and human-centered validation methods (comprehension tests, UI logs). Approved edits inform adaptation.
- **Core assumption:** Systematic post-hoc review with normative checklists can audit and correct biases or omissions in automated simplification, especially for domain-specific appropriateness.
- **Evidence anchors:**
  - [abstract] "Human-on-the-Loop (HoTL) supervision ensures systematic post-generation review."
  - [section 5.3] Checklists map accessibility dimensions (lexical clarity, structural clarity) to "human-centered validation" like comprehension tests.
  - [section 5.4] ECA rules use thresholds derived from user-study patterns (e.g., synonym rejection) to trigger HoTL.
  - [corpus] Expert annotation reliability (Section 4.3) and UI validation methods (Section 4.4) provide stable units (multi-word expressions) and validation protocols for HoTL.
- **Break condition:** If HoTL review shows high disagreement among experts or persistent failures on checklist items despite rule triggers, the ECA thresholds or checklist design may be mis-calibrated to the target user profiles. *Assumption: Would manifest as low pass rates or high revision rates in sampled outputs.*

### Mechanism 3
- **Claim:** Accessibility-oriented KPIs (e.g., Composite Quality Index, synonym-acceptance rates) create traceable, quantifiable signals that link evaluation to preference-based model adaptation (RLHF/DPO), closing the human-supervision loop.
- **Mechanism:** KPIs derived from user-study outcomes (comprehension gains, glossary activation) and automatic metrics are aggregated (e.g., CQI with weighted scores). When KPI trends fall below profile-specific thresholds, structured feedback (HoTL edits, synonym judgments) is formatted as preference pairs to adapt the LLM via RLHF/DPO, aligning outputs with PL/ER principles.
- **Core assumption:** Quantifiable, user-grounded KPIs can effectively steer LLM fine-tuning toward cognitive accessibility better than generic text-quality metrics.
- **Evidence anchors:**
  - [abstract] "accessibility Key Performance Indicators (KPIs) such as comprehension test scores... enable structured feedback for model adaptation via methods like RLHF or DPO."
  - [section 5.5] Defines KPIs (KPI_1–KPI_5) referencing specific user signals (synonym acceptance, glossary activation) and the CQI formula.
  - [section 5.6] Explicitly links KPIs to adaptation: "accessibility-grounded KPIs provide a practical basis... for preference-based alignment strategies."
  - [corpus] Evidence from user studies (Section 4) and model-adaptation resources (Section 4.5) provide the ground truth signals (synonym judgments, comprehension outcomes) that feed KPIs.
- **Break condition:** If KPI improvements (e.g., higher CQI) do not correlate with improved comprehension scores in subsequent user testing, the KPI weights or thresholds may not truly reflect accessibility. *Assumption: Would be detected via periodic HoTL-driven user validation sampling.*

## Foundational Learning
- **Concept: Human-in-the-Loop (HiTL) vs. Human-on-the-Loop (HoTL)**  
  Why needed here: Distinguishes real-time interactive guidance from post-hoc supervisory review, which is core to the framework's dual oversight design.  
  Quick check question: What is a concrete example of an intervention that would be HiTL (during generation) vs. HoTL (after generation) in this framework?

- **Concept: Plain Language (PL) and Easy-to-Read (ER) Standards**  
  Why needed here: The framework operationalizes ISO 24495-1, UNE 153101, etc., into checklist items and constraints; misunderstanding standard differences (PL for broad audiences vs. ER for ID) leads to misapplied simplification rules.  
  Quick check question: How would the checklist item "single-idea sentences" differ in strictness between a PL guideline and an ER standard?

- **Concept: KPI-Driven Adaptation Signals**  
  Why needed here: The framework reuses evaluation metrics as training signals (e.g., synonym acceptance as a preference). Without understanding how a KPI like "glossary activation rate" connects to model updates, adaptation becomes arbitrary.  
  Quick check question: If the Composite Quality Index (CQI) increases but user comprehension test scores do not, what might this indicate about the KPI design?

## Architecture Onboarding
**Component map:** Evidence Base → Generation Engine → Metric Evaluator → {ECA Rule Engine → (Auto-Approve | HoTL Supervisor); KPI Tracker ← Metric Evaluator → Adaptation Module} → Governance Layer → Generation Engine (constraints)

**Critical path:** Generation → Metric Evaluation → ECA Check → (Auto-approve if CQI ≥ threshold AND no triggers) OR → HoTL Review → Adaptation → Updated Generation Constraints.

**Design tradeoffs:**
- Automation vs. Oversight: Lower HoTL sampling (5–10%) improves throughput but risks missing subtle accessibility failures; higher sampling increases cost.
- Granularity vs. Efficiency: Using multi-word units (κ=0.64) for supervision improves reliability but may miss single-word errors.
- Profile-specific thresholds: Tailoring triggers per user group improves relevance but requires maintaining multiple rule sets.

**Failure signatures:**
- High auto-approve rate in high-risk domain (e.g., health info) without HoTL review.
- KPI improvement (e.g., readability) but stagnant glossary activation rates, suggesting superficial simplification.
- Frequent R1 triggers (readability gain but low BERTScore) indicating meaning distortion.

**First 3 experiments:**
1. Trigger Sensitivity Tuning: Run a batch of outputs with varying ECA thresholds (e.g., BERTScore from 0.80–0.90) and measure HoTL review load vs. post-review comprehension scores. Goal: Find threshold that balances automation with oversight effectiveness.
2. CQI Weight Validation: Train three model variants with different CQI weightings (e.g., 0.5/0.3/2 readability/semantic/structure) and evaluate with user studies on comprehension and usability. Goal: Validate that weight distribution aligns with real accessibility outcomes.
3. HiTL Guidance A/B Test: Compare two prompt designs: one with generic simplification instructions vs. one embedding specific corpus-derived rules (e.g., "≤20 words per sentence; prefer high-frequency synonyms from EASIER"). Measure synonym acceptance rates and CWI reduction in outputs. Goal: Quantify impact of evidence-based constraints during generation.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How should the framework's trigger rules and HoTL checklist be adapted for domain-specific regulatory differences (e.g., legal vs. health texts) beyond the current general PL/ER standards?
- **Basis in paper:** [explicit] The authors state future work will "extend validation across domains" (Sec. 7) and note that "auto-approve is disabled for high-risk domains (e.g., dosages in drug treatments... legal warnings)" (Sec. 6), but do not define how domain-specific rules are derived or integrated.
- **Why unresolved:** The paper provides a generic rule template (Listing 1) and checklist (Table 2) but leaves the operationalization of domain-specific constraints (e.g., mandatory terminology, liability disclaimers) as an open implementation detail. Without this, deployment in regulated sectors may lack necessary rigor.
- **What evidence would resolve it:** Case studies or guidelines mapping specific domain regulations (e.g., GDPR, FDA labeling) to ECA rule conditions and checklist items, validated by domain experts and end-users in those fields.

### Open Question 2
- **Question:** Are the fixed weights in the Composite Quality Index (0.4 readability, 0.3 semantic fidelity, 0.3 structural clarity) optimal across different user profiles (e.g., older adults vs. people with intellectual disabilities), or should they be dynamically adjusted?
- **Basis in paper:** [inferred] The CQI weights are presented as an "initial operational weighting" (Sec. 5.5), and the paper emphasizes profile-specific thresholds for KPIs like synonym acceptance (Sec. 4.2). However, the CQI itself uses uniform weights, implying an unstated assumption that accessibility trade-offs are consistent across profiles.
- **Why unresolved:** User studies show divergent preferences (e.g., older adults favor broader lexical coverage, ID users prioritize precision; Sec. 4.1–4.2). A single weighting scheme may not reflect these differing needs, potentially biasing outputs.
- **What evidence would resolve it:** A controlled study where CQI weights are varied per profile, measuring resulting text comprehension and satisfaction. Alternatively, a learned weighting model trained on per-profile comprehension test scores and usability data.

### Open Question 3
- **Question:** Can the framework's HiTL interaction patterns (e.g., accepting/rejecting synonyms) be generalized to users with cognitive profiles not covered in the EASIER studies (e.g., non-native speakers, people with aphasia), or are the current triggers and thresholds too narrowly tailored?
- **Basis in paper:** [inferred] The evidence base (Sec. 4) and profile-specific KPIs (Sec. 5.5) derive from older adults and people with ID. The framework assumes these groups represent the spectrum of cognitive accessibility needs, but does not address external validity.
- **Why unresolved:** The paper advocates for "inclusive NLP systems" (abstract) but grounds rules and thresholds in a limited set of user studies. Unstated assumptions about the transferability of CWI patterns, synonym acceptance rates, and glossary utility to other groups could lead to ineffective or biased supervision.
- **What evidence would resolve it:** Replication studies of the CWI and synonym acceptance tasks with diverse cognitive profiles, coupled with HoTL review logs to see if current triggers miss critical failures for these groups.

### Open Question 4
- **Question:** How should the ECA trigger thresholds (e.g., `BERTScore < 0.85` in Rule R1) be dynamically calibrated over time as user preferences, language models, and domain norms evolve, given the current proposal uses static or profile-specific but fixed thresholds?
- **Basis in paper:** [explicit] The paper states thresholds "can be calibrated per profile and domain, and can be revised as evidence is gathered" (Sec. 5.4), and KPIs track trends (e.g., `model_adaptation_accuracy >= previous_cycle + epsilon`; Sec. 5.5). However, no mechanism for automatic or systematic threshold updating is provided.
- **Why unresolved:** Without a closed-loop calibration process, thresholds may become stale as models improve or user expectations shift, leading to either excessive HoTL escalation (inefficiency) or missed errors (risk). The governance section mandates HoTL sampling but does not tie it to threshold adjustment.
- **What evidence would resolve it:** A longitudinal deployment study measuring the correlation between threshold drift (e.g., degradation in comprehension gains despite high CQI) and the need for manual revision, leading to a proposed update protocol (e.g., quarterly recalibration using recent KPI distributions).

### Open Question 5
- **Question:** In the proposed multi-agent orchestration (Sec. 5.8), how should conflicts between agents (e.g., a HiTL-guided lexical substitution vs. a HoTL expert's terminology check) be resolved in a traceable, explainable manner, and what governance model ensures accountability for the final decision?
- **Basis in paper:** [inferred] The multi-agent architecture is presented as a "practical implementation pathway" with an orchestrator, but conflict resolution is not detailed. The framework's explainability relies on ECA rules and checklist rationales (Sec. 6), yet it is unclear how agent disagreements are logged, arbitrated, or attributed.
- **Why unresolved:** In a hybrid human-AI system, disagreements between automated components and human reviewers are inevitable. Without a defined resolution protocol (e.g., voting, senior expert override, confidence-weighted arbitration), the system's "auditable" claim may break down at points of disagreement.
- **What evidence would resolve it:** A prototype implementation with a conflict-resolution module (e.g., argumentation framework or precedence rules) and a governance study assessing expert trust in the resolution process, including audit trail completeness and decision latency.

## Limitations
- Uncalibrated ECA thresholds for different profiles/domains; no provided calibration methodology.
- Unclear integration of human-centered validation (e.g., comprehension tests, eye-tracking) into HoTL checklist workflow.
- Unspecified mechanism for converting HoTL edits and KPI trends into structured preference data for RLHF/DPO.

## Confidence

- HiTL guidance improves accessibility: Low
- HoTL review catches accessibility risks: Medium
- KPIs drive model adaptation: Low
