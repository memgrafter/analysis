# Query as Anchor: Scenario-Adaptive User Representation via Large Language Model

## Quick Facts
- arXiv ID: 2602.14492
- Source URL: https://arxiv.org/abs/2602.14492
- Reference count: 40
- Primary result: Achieves state-of-the-art on 10 Alipay benchmarks (average AUC 0.8225, KS 0.5267) and demonstrates significant online business lifts (e.g., +12.5% drawdown rate, +5.3% average balance).

## Executive Summary
The paper introduces Query-as-Anchor, a novel framework for generating scenario-adaptive user representations using large language models. Unlike static user embeddings, Query-as-Anchor dynamically synthesizes embeddings conditioned on natural language queries, enabling a single model to serve diverse business scenarios. The approach employs a hierarchical coarse-to-fine encoder to compress heterogeneous multi-modal user logs into a structured token sequence, which is processed by a dual-tower LLM with joint contrastive and autoregressive objectives. Scenario-specific adaptation is achieved via cluster-based soft prompt tuning with minimal parameters, while KV-cache reuse ensures efficient inference. Extensive evaluations on 10 Alipay tasks and large-scale online A/B tests validate the method’s effectiveness, setting new state-of-the-art performance and delivering measurable business improvements.

## Method Summary
The method comprises three stages: pretraining, scenario adaptation, and deployment. Pretraining uses the synthetic UserU dataset, which pairs 90-day multi-modal user logs (from PayBill, Mini Program, etc.) with natural language queries and target answers. A hierarchical encoder transforms raw logs into a sequence of tokens at event, modality, and user levels. This sequence serves as a prefix for a dual-tower LLM (Qwen2.5-0.5B-Instruct with LoRA). The anchor tower appends a query to the prefix and extracts an embedding from a special <USER_EMB> token; the semantic tower encodes the answer. The model is trained with a combined contrastive loss (InfoNCE with margin filtering) and next-token prediction loss. For downstream scenarios, the backbone is frozen and a small set of soft prompt tokens (6 optimal) along with class prototypes are learned via prototypical contrastive loss. At inference, the user prefix is cached in KV memory; only the query suffix (and prompts) is processed, enabling low-latency per-scenario embedding extraction.

## Key Results
- On 10 Alipay binary classification benchmarks, Query-as-Anchor with prompt tuning averages AUC 0.8225 and KS 0.5267, significantly outperforming all baselines.
- Online IVR cash-reserve outreach campaign increased user drawdown rate by 12.5% and average balance by 5.3% compared to control.
- Credit delinquency risk identification improved KS by 1.96% in large-scale A/B testing.

## Why This Works (Mechanism)

**Mechanism 1: Query-as-Anchor Dynamic Synthesis**
- *Claim:* Query-as-Anchor produces scenario-adaptive user embeddings from a single frozen model by conditioning on a natural language query.
- *Mechanism:* A dual-tower LLM architecture processes hierarchical user tokens e_i and a query q_i. The anchor tower ingests e_i with q_i appended at the terminus; the LLM’s attention selectively distills query‑relevant features to produce u_i,q. The semantic tower encodes the target answer a_i to v_{a_i}. Joint contrastive and next‑token prediction losses align u_i,q with v_{a_i} while preserving semantic density. KV‑cache reuse is enabled because e_i is a fixed prefix.
- *Core assumption:* The query acts as an effective semantic anchor that can dynamically reshape the representation of the static history e_i without requiring recomputation of the prefix.
- *Evidence anchors:* [abstract] “Query-as-Anchor, a framework shifting user modeling from static encoding to dynamic, query‑aware synthesis.”; [section] Section 3.2.2: “Anchor Tower ingests the hierarchical user tokens e_i and appends the natural language query q_i as a trailing semantic anchor.”; [corpus] Corpus evidence is weak; neighboring papers focus on query‑aware retrieval or privacy, not dynamic user embedding adaptation.
- *Break condition:* If the query is ambiguous or misaligned with the downstream task, the anchor may fail to extract relevant features, causing performance degradation. Similarly, if e_i lacks predictive signals for the query (e.g., very sparse history), the mechanism cannot compensate.

**Mechanism 2: Hierarchical Coarse‑to‑Fine Encoding**
- *Claim:* Hierarchical coarse‑to‑fine encoding reconciles sparse, heterogeneous user logs with the dense input expectations of LLMs by forming multi‑granularity tokens.
- *Mechanism:* Each modality m is encoded via event adapters into fine‑grained event embeddings z_{m,t}^{(evt)}. These are mean‑pooled within modality to produce summary tokens \bar{z}_m^{(evt)} and then transformed to modality‑level z_m^{(mdl)}. A user adapter aggregates all modality vectors into a user‑level z^{(usr)}. The final sequence e_i concatenates [z^{(usr)}; {z_m^{(mdl)}}; {\bar{z}_m^{(evt)}}], preserving explicit structure.
- *Core assumption:* The three‑level hierarchy retains enough information for downstream queries and that explicit user and modality markers guide the LLM’s attention across modalities.
- *Evidence anchors:* [abstract] “hierarchical coarse‑to‑fine encoders”; [section] Section 3.2.1 details the token construction: “Hierarchical Coarse‑to‑fine User Encoder.”; [corpus] Weak; related work like “Scenario‑Adaptive Fine‑Grained Personalization Network” uses coarse‑grained re‑weighting, not hierarchical tokens.
- *Break condition:* Excessive aggregation (too few event tokens K_m) may discard rare but critical events. High noise in modalities could propagate through summaries. Ablation shows that removing both user and modality tokens hurts performance, indicating the structure helps but is not the sole source of performance.

**Mechanism 3: Cluster‑Based Soft Prompt Tuning**
- *Claim:* Cluster‑based soft prompt tuning efficiently adapts the universal representation to diverse business scenarios with minimal parameter updates.
- *Mechanism:* After pretraining, backbone and encoder are frozen. A small set of learnable prompt tokens (e.g., 6) and class prototypes are introduced. These tokens modulate the anchored embedding u_i,q and are optimized with a prototypical contrastive loss that pulls embeddings toward their class center while pushing away others. This aligns the latent space with scenario‑specific decision boundaries.
- *Core assumption:* A low‑dimensional perturbation via a few prompt vectors can sufficiently steer the model’s attention to scenario‑relevant modalities without full fine‑tuning.
- *Evidence anchors:* [abstract] “Cluster‑based Soft Prompt Tuning”; [section] Section 3.2.3: “Cluster‑based Soft Prompt Tuning” and Equation (7); [corpus] Limited; corpus contains query‑aware methods but not specifically soft prompting for user embedding.
- *Break condition:* If the scenario distribution diverges significantly from the pretraining corpora, the small prompt capacity may lead to underfitting. Also, many classes (large K) could cause prototypes to become overly coarse.

## Foundational Learning
1. **Contrastive Learning (InfoNCE)**
   - *Why needed:* The paper’s primary training signal aligns query‑anchored embeddings with semantic targets; without contrastive objective, performance collapses (Ablation).
   - *Quick check:* What are the two terms in the total loss L_total? L_cl (contrastive) and L_ntp (next‑token prediction). How does the contrastive loss handle false negatives? Margin‑based filtering (Eq.5).
2. **Hierarchical Representation**
   - *Why needed:* Raw user logs are multi‑modal and sparse; hierarchical compression creates a fixed‑length structured token sequence compatible with LLM context.
   - *Quick check:* What are the three levels of tokens produced? Event‑level (z_{m,t}^{(evt)}), modality‑level (z_m^{(mdl)}), user‑level (z^{(usr)}). How are event tokens aggregated? Mean‑pooling to summary \bar{z}_m^{(evt)}.
3. **KV‑Cache Optimization**
   - *Why needed:* Multi‑scenario inference must be low‑latency; caching the user prefix avoids recomputing the expensive hierarchical encoding for each scenario.
   - *Quick check:* Why is the query placed at the terminus of the sequence? This allows the prefix (user tokens) to be cached and reused; only the query suffix is computed per scenario.

## Architecture Onboarding
**Component map**: Data Ingestion -> Hierarchical Encoder -> Dual-Tower LLM (Anchor Tower & Semantic Tower) -> Loss Module (Contrastive + Next-Token Prediction) -> Soft Prompt Tuner -> KV-Cache Manager -> Deployment Pipeline

**Critical path**: 
1. Daily: Ingest new user events; for affected modalities, recompute event tokens and modality summaries; update hierarchical token buffer; refresh KV cache for each user.
2. Per request: Retrieve user’s prefix KV cache; run anchor tower on the specific query tokens (plus optional soft prompts) to generate scenario‑aware embedding u_i,q; feed to scenario‑specific classifier.
3. Adding a new scenario: Only need to provide the new query and train new soft prompts; prefix cache remains unchanged.

**Design tradeoffs**:
- Prefix length vs. detail: More event tokens preserve fine‑grained patterns but increase memory and KV‑cache size; fixed K_m balances.
- Dual‑tower vs. single‑tower: Dual‑tower separates user and answer spaces but doubles forward passes in training; training parallelism mitigates.
- Prompt length vs. adaptation: Experiments show 6 tokens optimal; more tokens yield diminishing returns and risk overfitting.
- Frozen backbone vs. full fine‑tuning: Freezing preserves general knowledge and enables cheap scenario addition; but may limit adaptation. Soft prompts provide a middle ground.
- KV‑cache memory: Storing caches for hundreds of millions of users requires a large cluster; trade‑off between memory cost and latency.

**Failure signatures**:
- Scenario‑specific performance drop after prompt tuning (overfitting) or without prompt tuning (lack of adaptation) – monitor per‑scenario AUC/KS.
- Latency spike if prefix recomputation occurs frequently (cache miss or expired entries).
- Representation collapse (e.g., low variance across users) if contrastive loss is disabled or temperature misconfigured.
- Attention weights that do not shift after prompt tuning indicate prompts not influencing modality selection.
- Online metrics: Degradation in business KPIs (e.g., drawdown rate vs. control) signals embedding degradation.

**First 3 experiments**:
1. Main Results (Section 5.1, Tables 2 & 5): Q‑Anchor (Prompt Tuned) achieves average AUC 0.8225 and KS 0.5267 over 10 Alipay benchmarks, beating LLM and user‑embedding baselines.
2. Ablation Study (Section 5.2, Tables 3 & 6): Removing hierarchical tokens, contrastive loss, or pretraining each causes significant performance drops, confirming each component’s necessity.
3. Online A/B Testing (Section 5.3, Table 11): In IVR cash‑reserve outreach, drawdown rate +12.5%, average balance +5.3%. In credit delinquency risk, KS +1.96%. Demonstrates real‑world effectiveness.

## Open Questions the Paper Calls Out
1. **Scaling Paradox**: What causes larger LLM backbones (1.5B-3B) to exhibit gradient attenuation and performance stagnation in user embedding tasks, and how can optimization techniques be adapted to recover learning signals? The paper notes the phenomenon but provides no analysis or solution.
2. **Synthetic Data Faithfulness**: To what extent does the LLM-generated synthetic QA data in UserU accurately reflect true user understanding and intents, and could synthetic biases affect downstream generalization? No human validation or comparison to real data is provided.
3. **Generalization of Soft Prompts**: How well does cluster-based soft prompt tuning generalize to business scenarios not represented in the training clusters, and what is the sample complexity for adapting to novel scenarios? Evaluation is only on 10 fixed scenarios; zero-shot/few-shot adaptation is unexplored.
4. **Conflict Resolution**: When heterogeneous multi-modal user signals provide conflicting evidence for a query, how does Query-as-Anchor resolve these conflicts, and does it implicitly favor certain modalities? The mechanism for handling intra-scenario conflicts is not discussed.

## Limitations
- Exact method for injecting continuous user prefix e_i into the LLM and the role of <USER_EMB> token remain undisclosed, hindering replication.
- The natural language queries for each downstream scenario are not provided; these are central to query‑anchored adaptation.
- Construction details of the UserU pretraining corpus (e.g., 72 life topics, reflection format, negative sampling) are vague, preventing dataset recreation.
