# AIR: Improving Agent Safety through Incident Response

## Quick Facts
- **arXiv ID**: 2602.11749  
- **Source URL**: https://arxiv.org/abs/2602.11749  
- **Reference count**: 34  
- **Primary result**: AIR achieves >90% detection, remediation, and eradication success rates across code, embodied, and computer-use agent evaluations.

## Executive Summary
Large Language Model (LLM) agents are increasingly deployed in high-stakes domains, yet current safety mechanisms focus primarily on preventing failures rather than responding to incidents after they occur. This paper introduces AIR, the first incident response framework for LLM agent systems. AIR integrates a domain-specific language (DSL) into the agent’s execution loop to autonomously manage the full incident response lifecycle—detection, containment, recovery, and eradication. The framework detects incidents via semantic checks, guides containment and recovery using the agent’s own tools, and synthesizes guardrail rules during eradication to prevent recurrence. Evaluated across code agents (RedCode), embodied agents (SafeAgentBench), and computer-use agents (RiOSWorld/OSWorld), AIR achieves detection, remediation, and eradication success rates exceeding 90%. Ablation studies confirm the necessity of its structured remediation and guardrail generation components, and LLM-generated guardrail rules approach the effectiveness of developer-authored rules. These results demonstrate that incident response is a feasible and essential first-class safety mechanism for LLM agents.

## Method Summary
AIR defines an incident rule DSL with three components: `trigger` (tool invocation that activates the rule), `check` (a natural-language condition evaluated against environment state and context), and `remediate` (structured actions to contain and recover). The framework hooks into the agent’s execution loop: after each tool call, activated rules are evaluated; if an incident is confirmed, the agent executes the remediation sequence. After remediation, AIR synthesizes a guardrail rule (a plan-level check) to block similar unsafe plans in future executions. Implementation uses the OpenAI Agent SDK with ANTLR4 for rule parsing. Evaluations employ three agent types: a code agent (CodeAct) on RedCode (4,000+ tasks), an embodied agent on SafeAgentBench (750 tasks), and a computer-use agent on RiOSWorld and OSWorld. Primary metrics include successful detection, remediation, and eradication rates, along with rule counts and overhead.

## Key Results
- >90% success rates on detection, remediation, and eradication across all three agent domains.
- Ablation studies show that removing structured remediation or guardrail generation significantly degrades performance, confirming their necessity.
- Guardrail rules generated by an LLM (GPT-5) achieve effectiveness comparable to developer-authored rules, demonstrating the viability of automated rule synthesis.

## Why This Works (Mechanism)
AIR’s effectiveness stems from its modular incident response lifecycle and tight integration with the agent’s execution. The DSL decouples incident definitions from agent logic, enabling flexible rule activation and evaluation. Semantic checks leverage LLM reasoning to detect complex, context-dependent incidents that simple triggers would miss. Structured remediation uses the agent’s existing tools, ensuring containment and recovery actions are feasible within the environment. Finally, guardrail synthesis creates plan-level constraints that prevent recurrence of similar incidents, effectively eradicating the threat category. The ablation results validate that each component—detection, remediation, and eradication—is essential for overall safety.

## Architecture Onboarding
**Component map**  
Agent -> Tool Call -> Rule Evaluator -> Incident? -> Yes -> Remediation Executor -> Guardrail Synthesizer -> Rule Store -> Agent  
                                      -> No  -> Continue loop  

**Critical path**  
The critical path for an incident begins with a tool invocation that triggers a rule, proceeds through semantic check evaluation, then executes the remediation sequence (which may involve multiple tool calls), and finally triggers guardrail synthesis. This path determines the timeliness of response and eradication.

**Design tradeoffs**  
- *Expressiveness vs. performance*: More expressive DSL allows richer incident definitions but complicates parsing and may increase false positives.  
- *LLM-based checks vs. deterministic checks*: LLMs provide flexibility but introduce latency, cost, and non-determinism.  
- *Automated guardrail generation vs. manual curation*: Automation reduces developer effort but may produce less reliable rules, requiring oversight.

**Failure signatures**  
- Rule parsing errors (DSL syntax issues) cause rule loading failures.  
- Semantic check failures (invalid LLM responses or timeouts) delay detection.  
- Remediation execution errors (tool failures or side effects) hinder recovery.  
- Guardrail synthesis errors (invalid or over-restrictive rules) lead to false positives/negatives.

**First experiments**  
1. Validate DSL parsing by feeding sample rules and confirming correct extraction of `trigger`, `check`, and `remediate` fields.  
2. Simulate a known incident in a controlled environment (e.g., a RedCode task with a risky operation) and verify that AIR detects it and executes the remediation sequence.  
3. Compare guardrail rules generated by the LLM against human-authored rules for a set of incidents, measuring their ability to prevent recurrence while not blocking safe tasks.

## Open Questions the Paper Calls Out
1. **Integration with alternative guardrail mechanisms** – AIR is guardrail-agnostic but only plan-level rules are evaluated. It remains unknown how other mechanisms (e.g., trace-based, probabilistic) affect performance. *Basis*: Explicit in Discussion. *Unresolved*: No experimental testing. *Resolution*: Compare diverse guardrails in same frameworks.  
2. **Enhancing LLM-generated rule quality** – LLM-generated rules suffer from over-tailoring or excessive abstraction, limiting generalizability. *Basis*: Inferred from RQ3. *Unresolved*: No solutions explored. *Resolution*: Develop improved prompting/fine-tuning and cross-task validation.  
3. **Reducing time overhead** – AIR incurs moderate delays, especially in fine-grained domains. Proposed mitigations (decoupling, parallel models) are speculative. *Basis*: Inferred from overhead measurements. *Unresolved*: Not implemented/evaluated. *Resolution*: Implement mitigations and measure latency vs. accuracy.  
4. **Handling agent reasoning errors** – AIR relies on agent reasoning quality; no error-handling for flawed reasoning. *Basis*: Inferred from Discussion. *Unresolved*: No confidence-aware escalation. *Resolution*: Integrate confidence estimation and test on adversarial perturbations.  
5. **Long-term rule effectiveness** – Guardrail rules may accumulate redundancies or over-restrict behavior over evolving task distributions. *Basis*: Inferred from limited evaluation rounds. *Unresolved*: No longitudinal study. *Resolution*: Conduct multi-iteration experiments tracking rule set growth and false positives.

## Limitations
- Unspecified dataset versions and splits may alter incident frequencies and metrics, affecting reproducibility.  
- Core claims rely on GPT-5 (unavailable); using substitute models like GPT-4o may degrade semantic check and rule synthesis quality.  
- Zero independent replications limit confidence in generalizability beyond the evaluated agent types.

## Confidence
- **Framework efficacy** (detection/remediation >90%): Medium (reproducible but sensitive to dataset/model choices).  
- **Ablation necessity** (components are essential): High (controlled experiments support this).  
- **LLM vs. developer rules parity**: Low (based on GPT-5; no public baseline for direct comparison).
