# Probe-then-Plan: Environment-Aware Planning for Industrial E-commerce Search

## Quick Facts
- **arXiv ID:** 2603.15262
- **Source URL:** https://arxiv.org/abs/2603.15262
- **Reference count:** 21
- **Primary result:** Proposed Environment-Aware Search Planning (EASP) resolves the blindness-latency dilemma in e-commerce search with a Probe-then-Plan mechanism, achieving millisecond planning latency and significant online conversion/GMV lifts.

## Executive Summary
The paper introduces Environment-Aware Search Planning (EASP) to address the "blindness-latency dilemma" in industrial e-commerce search: existing LLM-based planners are either retrieval-agnostic (producing invalid plans) or too slow (iterative reflection). EASP employs a lightweight Retrieval Probe to expose the current retrieval snapshot, enabling a single-step Planner to diagnose execution gaps (e.g., entity drift, attribute misalignment) and generate grounded plans. The system is trained via a Teacher-Student framework (SFT + GRPO) to align with business conversion metrics. In offline evaluations on JD.com data, EASP outperforms a retrieval-blind rewriter and matches a slower ReAct agent while maintaining millisecond latency. Online A/B testing shows statistically significant lifts in User Conversion Rate (+0.89%) and Gross Merchandise Value (+0.57%), with end-to-end planning latency under 700ms for complex queries. The system is deployed in production.

## Method Summary
EASP follows a three-stage pipeline. First, offline data synthesis uses a Teacher Agent (a powerful LLM) to generate execution-validated planning demonstrations. For each query, the Teacher receives the original query and a retrieval snapshot from a lightweight Probe, diagnoses the retrieval state (e.g., recall failure, precision failure), and produces a transformation plan (sanitization, concretization, etc.). These demonstrations are filtered by executing the plan and checking improvement. Second, a smaller student Planner is fine-tuned via Supervised Fine-Tuning (SFT) on the demonstrations to learn diagnostic patterns. Then, Group Relative Policy Optimization (GRPO) aligns the Planner with business outcomes: the reward combines predicted conversion rates of retrieved items, gated by a hard relevance threshold. Third, at serving time, a Complexity-Aware Router classifies queries as "Fast Path" (simple, specific) or "Complex Path" (ambiguous, multi-intent). Only complex queries trigger the Probe then the Planner, ensuring sub-second latency for the majority of traffic.

## Key Results
- **Offline performance:** EASP achieves Relevance@30=23.3 and Hitrate@30=31.0%, surpassing a retrieval-blind rewriter (20.7, 28.6%) and matching a slower ReAct agent (24.1, 30.2%) while operating in milliseconds.
- **Online impact:** A/B testing on JD.com yields +0.89% lift in User Conversion Rate and +0.57% lift in Gross Merchandise Value (both p<0.05).
- **Latency:** End-to-end planning latency stays under 700ms at p99 for complex queries, with 80% of traffic (fast-path) experiencing near-zero planning latency.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** The lightweight **Retrieval Probe** resolves the "blindness" aspect of the dilemma by exposing a real-time retrieval snapshot to the planner without exceeding sub-second latency budgets.
- **Mechanism:** The Probe executes a trimmed version of the core retrieval pipeline (omitting expensive conversion-optimized components) to fetch initial results `O_init` for a query `q`. This snapshot reveals retrieval boundaries (e.g., recall gaps, precision biases) which the Planner then diagnoses in a single, grounded reasoning step.
- **Core assumption:** An approximate retrieval snapshot is sufficient for diagnostic planning in e-commerce, avoiding the need for iterative, multi-step agent interaction with the full environment.
- **Evidence anchors:**
  - [abstract] "a lightweight Retrieval Probe first exposes the retrieval snapshot, enabling a single-step Planner to diagnose execution gaps"
  - [section 2.2] "This design reduces tp99 latency by approximately 75%, yet the retrieved items sufficiently reflect the underlying item distribution and expose the system’s retrieval boundaries for diagnostic purposes."
  - [corpus] Weak direct anchor; neighboring papers (e.g., "System-1.x") discuss fast/slow planning tradeoffs but do not address environment-probing specifically.
- **Break condition:** If the Probe's simplified retrieval significantly misrepresents the full system's behavior (e.g., due to omitted ranking signals), the diagnostic foundation becomes invalid, leading to poorly grounded plans.

### Mechanism 2
- **Claim:** The **Teacher-Student training framework** (SFT + GRPO) transfers diagnostic reasoning from a powerful LLM to an efficient planner while aligning outputs with business conversion metrics.
- **Mechanism:** A teacher LLM generates diverse, execution-validated plans `(q, O_init, P)` by diagnosing `O_init`. The student Planner is first SFT-trained on these demonstrations to learn diagnostic patterns. Then, GRPO reinforcement learning optimizes the Planner's policy to maximize a reward function `R(P)` based on *predicted* conversion of retrieved items, gated by a hard relevance threshold.
- **Core assumption:** Conversion-aligned reward, computed via online production models (`φ_cvr`, `φ_rel`), effectively bridges semantic relevance and business value for e-commerce search.
- **Evidence anchors:**
  - [abstract] "Planner is initialized via Supervised Fine-Tuning (SFT) to internalize diagnostic capabilities, then aligned with business outcomes (conversion rate) via Reinforcement Learning."
  - [section 2.3.2] "The reward R(P_i) is defined as the average predicted conversion of these retrieved items... with a Hard Relevance Gate."
  - [section 3.2] "w/o RL... HR@30 lags (29.5% vs 31.0%). This gap confirms that explicit alignment with conversion objectives via GRPO is essential."
  - [corpus] Weak anchor; "Distilling Reasoning Without Knowledge" mentions modular RAG but not business-value alignment via RL.
- **Break condition:** If the predicted CVR model (`φ_cvr`) is poorly calibrated or fails to capture true business drivers, RL optimization may lead to reward hacking (e.g., plans that fetch high-CVR but irrelevant items that never actually convert).

### Mechanism 3
- **Claim:** The **Complexity-Aware Router** dynamically routes queries, applying resource-intensive planning only where needed, to maintain overall system latency within industrial constraints.
- **Mechanism:** A tiny LLM router classifies queries as "Fast Path" (simple, specific product searches) or "Complex Path" (ambiguous, multi-intent queries). Only complex queries trigger the Probe-then-Plan pipeline. This selective activation ensures that for the majority (~80%) of traffic, planning latency is near-zero.
- **Core assumption:** Query complexity can be reliably inferred from the query string alone, without needing retrieval context, to make cost-effective routing decisions.
- **Evidence anchors:**
  - [abstract] "A complexity-aware routing mechanism selectively activates planning for complex queries, ensuring optimal resource allocation."
  - [section 2.4] "Queries targeting specific products (e.g., "iPhone 17") bypass the planner entirely... Complex Path: Only complex queries trigger EASP."
  - [section 3.3] "end-to-end planner latency reaches 20ms at p75 for fast-path traffic and stays under 700ms at p99 for complex queries."
  - [corpus] Weak anchor; "System-1.x" explores fast/slow modes but not query-based dynamic routing.
- **Break condition:** If the router's complexity classifier has high false-negative rate on complex queries (routing them to fast path), many queries will receive no planning benefit, eroding overall conversion lift.

## Foundational Learning

- **Concept: Retrieval Environment as an Observable State**
  - *Why needed here:* The core innovation is treating the retriever's output not as final results but as environmental *feedback* (`O_init`) for planning. This shifts planning from blind generation to grounded diagnosis.
  - *Quick check question:* What two specific failure types (from Table 1) would be invisible to a query-only planner but detectable by analyzing `O_init`?

- **Concept: Diagnostic Planning vs. Generative Rewriting**
  - *Why needed here:* The Planner's task is not to generatively rewrite but to *diagnose* the mismatch between query intent and retrieval reality (e.g., "entity drift," "attribute misalignment") and select a concrete transformation strategy (Sanitization, Concretization).
  - *Quick check question:* For the query "bottoms match green shirt" with shirt-dominated results, what is the diagnosed bias and what planning strategy (Path C sub-type) should be applied?

- **Concept: Business-Aligned Reward Shaping**
  - *Why needed here:* Standard relevance metrics (e.g., nDCG) may not correlate with conversion/GMV. The reward `R(P)` explicitly optimizes for predicted conversion, gated by relevance, to align the planner's objective with business KPIs.
  - *Quick check question:* Why is the "Hard Relevance Gate" (I(`φ_rel` ≥ τ)) critical in the reward formula? What would happen without it?

## Architecture Onboarding

- **Component map:** Retrieval Probe -> Complexity-Aware Router -> Planner (for complex queries); Fast path bypasses Probe and Planner.
  - Retrieval Probe: Lightweight fetch module (latency-critical).
  - Complexity-Aware Router: Tiny LLM classifier (fast-path vs. complex-path).
  - Planner: Efficient LLM (Qwen3-4B) that takes `(q, O_init)` and outputs plan `P`.
  - Teacher Agent: Offline-only SOTA LLM (DeepSeek-R1) for data synthesis.
  - Training Pipeline: SFT dataset creation + GRPO alignment.
  - Online Reward Oracle: Production `φ_rel` and `φ_cvr` models (referenced but not part of planning module).

- **Critical path:** For a complex query: `Router → Probe → Planner → (Executed Plan → Online Search → Conversion)`. The Probe's latency and the Planner's token generation dominate the critical path. Fast-path queries skip Probe and Planner entirely.

- **Design tradeoffs:**
  - **Probe Simplicity vs. Diagnostic Fidelity:** Stripping the Probe of conversion features reduces latency but risks missing signals relevant to diagnosis (e.g., item price bias).
  - **Planner Capacity vs. Latency:** Using a 4B parameter model (vs. 70B+) ensures ms-level latency but may limit diagnostic nuance vs. a larger teacher model.
  - **Routing Granularity:** A more aggressive router (more fast-path) reduces average latency but risks under-planning. The 80/20 split is a tuned heuristic.

- **Failure signatures:**
  - **High fast-path conversion drop:** Router misclassifying complex queries as simple (false negatives).
  - **Planner latency spike at p99:** Unanticipated query complexity or Probe `O_init` size overwhelming the Planner's context window.
  - **Offline/Online metric divergence:** SFT/GRPO overfitting to `φ_cvr` predictions that don't reflect true user conversion patterns in production.

- **First 3 experiments:**
  1.  **Probe Sanity Check:** For a sample of complex queries, run the Probe and full retrieval side-by-side. Measure: (a) Jaccard similarity of top-100 items, (b) correlation of key statistics (item count, brand diversity). Expect high similarity but not identity.
  2.  **Router Stress Test:** Feed the router with queries of known complexity (from logs) and measure false-positive (complex→fast) and false-negative rates. Start with a 1k labeled set; target false-negative rate <10% to preserve planned-lift.
  3.  **Planner Diagnostic Audit:** Manually review `P` outputs for a diverse set of `(q, O_init)` pairs. Verify that for each "Precision Failure" case (Table 1), the plan applies the correct concretization strategy (e.g., entity re-anchoring, attribute specification). Quantify agreement with human annotators.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How can EASP be extended to incorporate user behavioral signals (e.g., click history, session context) for personalized search planning, and what architectural modifications are needed to maintain sub-second latency while doing so?
- **Basis in paper:** [explicit] The "Conclusion and Future Work" section states: "Future work will extend EASP to incorporate user behavioral signals for personalized planning, adapting strategies based on individual preferences and interaction history."
- **Why unresolved:** The current EASP design conditions planning solely on the query and the retrieval snapshot, ignoring rich per-user signals. Integrating behavioral data introduces computational overhead and potential latency increases, conflicting with the strict industrial budget. The proposed routing mechanism and one-step planning assumption may not scale to personalized contexts without redesign.
- **What evidence would resolve it:** An empirical study measuring UCVR/GMV lifts from a personalized EASP variant in an A/B test, coupled with a latency breakdown showing the planning module stays under 700ms p99. Additionally, an ablation isolating the contribution of behavioral features versus environmental probing would clarify the source of gains.

### Open Question 2
- **Question:** For queries where the initial retrieval snapshot is highly ambiguous or fails to expose clear diagnostic cues, does the single "Probe-then-Plan" step suffice, or would an adaptive, multi-probe strategy within the same latency envelope yield better conversion?
- **Basis in paper:** [inferred] The paper assumes a single diagnostic reflection is sufficient for "most complex e-commerce queries" (Sec 1) and contrasts this with multi-turn ReAct agents that are too slow. However, the taxonomy of failures (Table 1) and the reliance on a lightweight probe suggest there may be edge cases where the initial snapshot is insufficient for confident diagnosis.
- **Why unresolved:** The offline and online evaluations aggregate results over all complex queries, masking per-query failure modes. There is no analysis of whether specific query types (e.g., extremely vague or multi-intent queries) benefit from additional environmental interaction. The latency-constrained deployment explicitly avoids iterative tool calls, potentially sacrificing accuracy for speed on a subset of queries.
- **What evidence would resolve it:** An error analysis on the online A/B test or offline test set, categorizing failures of the deployed EASP system. If a significant fraction of failures correlates with low-confidence diagnoses (e.g., retrieval snapshots with uniformly low relevance scores), it would motivate a controlled experiment where a small subset of such queries triggers a second, lightweight probe, measuring the trade-off between additional latency and incremental HR@30/UCVR.

### Open Question 3
- **Question:** How robust is the EASP training pipeline (Teacher synthesis, SFT, GRPO) to variations in the underlying retrieval system's architecture, index, and item catalog? Does the learned planner generalize when transferred to a different e-commerce platform or after a major search stack update?
- **Basis in paper:** [inferred] The entire methodology—from the Teacher Agent's diagnosis strategies (Table 1) to the GRPO reward computed via JD.com's online relevance and CVR models—is tightly coupled with JD.com's specific search ecosystem. The offline dataset is synthesized from JD logs, and the online test is solely on JD traffic. No cross-dataset or cross-platform validation is performed.
- **Why unresolved:** The diagnostic strategies (e.g., "entity drift," "attribute misalignment") and the hard relevance gate are defined relative to JD's retriever behavior and catalog vocabulary. A different platform's retrieval failures might manifest differently, making the teacher's demonstrations less valid. The SFT model might overfit to JD-specific failure patterns, and the GRPO alignment to JD's CVR model may not transfer.
- **What evidence would resolve it:** A transfer experiment: train the entire EASP pipeline on one platform's data (e.g., simulated or public dataset) and evaluate on another's. Alternatively, simulate a retrieval system change (e.g., new embedding model) by re-generating the offline dataset with the new system's snapshots and measuring the delta in planner performance. Significant degradation would indicate brittleness.

### Open Question 4
- **Question:** Is the fixed, rule-based diagnostic taxonomy (Effective/Recall Failure/Precision Failure with sub-types) a complete and optimal framework for the Planner's internal reasoning, or could a more flexible, learned diagnostic space better capture the diversity of real-world query-retrieval misalignments?
- **Basis in paper:** [inferred] The Teacher Agent is explicitly prompted to categorize states into three mutually exclusive buckets and further into five sub-types (Query Noise, Inventory Void, Entity Drift, Granularity Mismatch, Attribute Misalignment, Scenario Misalignment). These categories are hand-crafted based on observed patterns. The Planner is trained to mimic this structured diagnosis via SFT.
- **Why unresolved:** While the taxonomy covers common cases shown in examples, it is a human-designed heuristic. Complex or novel query types might exhibit hybrid failure modes that don't fit cleanly into one bucket (e.g., a query suffering from both entity drift and attribute misalignment). Forcing a mutually exclusive classification might force the Planner into a suboptimal single-path strategy when a combined approach would be more effective.
- **What evidence would resolve it:** An analysis of the Planner's failure cases where the chosen plan (from the diagnosis matrix) leads to poor outcomes. If systematic misclassifications are observed (e.g., the Teacher labels a case as "Precision Failure: Bias" but the optimal plan requires sanitization), it suggests the taxonomy is limiting. Alternatively, replacing the explicit diagnosis step with an end-to-end trained Planner (no forced categorical output) and comparing its performance against the structured EASP could reveal whether the inductive bias of the taxonomy helps or hinders.

## Limitations

- **Probe specification unknown:** The exact retrieval stack and `O_init` format are not disclosed, raising concerns about diagnostic fidelity.
- **GRPO implementation details missing:** Hyperparameters (group size, KL coefficient) and reward model thresholds are unreported, increasing risk of reward hacking and suboptimal alignment.
- **Router training specifics absent:** No details on complexity labeling or decision thresholds; the 80/20 split is a heuristic with unreported error rates, potentially undermining latency guarantees.
