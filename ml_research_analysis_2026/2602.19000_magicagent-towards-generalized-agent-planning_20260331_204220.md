# MagicAgent: Towards Generalized Agent Planning
## Quick Facts
- arXiv ID: 2602.19000
- Source URL: https://arxiv.org/abs/2602.19000
- Reference count: 28
- Primary result: MagicAgent-32B and MagicAgent-30B-A3B achieve state-of-the-art performance (75.1% on Worfbench, 86.9% on BFCL-v3) and surpass larger models like GPT-5.2, Kimi-K2, and GLM-4.7.

## Executive Summary
MagicAgent addresses the core challenges of generalized agent planning—scarcity of high-quality interaction data and gradient interference across heterogeneous tasks—by introducing a lightweight synthetic data framework that generates diverse trajectories for five planning paradigms and a two-stage training paradigm combining supervised fine‑ tuning with multi‑objective reinforcement learning. A load‑balanced mixture‑of‑experts (MoE) strategy stabilizes multi‑task training. The resulting models, MagicAgent‑32B and MagicAgent‑30B‑A3B, deliver state‑of‑the‑art results on multiple benchmarks, outperform leading ultra‑scale models, and the online χPO algorithm further enhances robustness in interactive settings.

## Method Summary
The method comprises three core components: (1) A synthetic data pipeline that constructs tool dependency graphs and uses atomic plan aggregation to produce diverse trajectories for five planning paradigms. (2) A two‑stage training regime: first supervised fine‑tuning (SFT) with novelty‑based sampling to fuse datasets while preserving diversity, followed by multi‑objective reinforcement learning (offline GRPO on static data, online χPO on interactive environments) using a unified reward that balances format, plan, tool, workflow, and schedule correctness. (3) A load‑balanced MoE layer with global load‑balancing loss and z‑loss regularization, integrated throughout training to stabilize multi‑task learning and enable expert specialization.

## Key Results
- State‑of‑the‑art on Worfbench (75.1%) and BFCL‑v3 (86.9%).
- Surpasses ultra‑scale models (GPT‑5.2, Kimi‑K2, GLM‑4.7) despite sub‑100B parameter count.
- Online χPO algorithm enhances robustness and exploration‑exploitation trade‑offs in interactive tasks.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim**: Synthetic data framework alleviates data scarcity by generating diverse, logically coherent trajectories for five planning paradigms.
- **Mechanism**: Builds tool relationship graphs (dependency and parameter‑sharing) to sample atomic plans (isolated, serial, parallel). Aggregates via operators (concatenate, add, group, mask, transform, split) to form complex, multi‑turn trajectories with verifiable constraints.
- **Core assumption**: Graph‑based, rule‑governed synthesis can match structural diversity of real agent interactions.
- **Evidence**: Abstract mentions lightweight scalable framework; Section 3.1 details graph construction; limited corpus validation, but related works show trajectory collection challenges.
- **Break condition**: If tool graph topology misrepresents real dependencies, generated trajectories may lack semantic coherence.

### Mechanism 2
- **Claim**: Two‑stage training (SFT then multi‑objective RL) mitigates gradient interference across heterogeneous planning tasks.
- **Mechanism**: Stage I SFT uses novelty‑based sampling (Eq. 1) to fuse diverse datasets while preserving diversity. Stage II RL employs a unified reward (Eq. 3) combining format, plan, tool, workflow, and schedule correctness; offline RL uses GRPO on static data, online RL uses χPO for exploration‑exploitation balance.
- **Core assumption**: Sequential training with a carefully designed reward enables a single policy to converge on multiple conflicting objectives.
- **Evidence**: Abstract describes two‑stage paradigm; Section 4.2 defines reward and GRPO/χPO; related works (AgentTuning) show SFT helps but lack RL stage.
- **Break condition**: Tasks with fundamentally opposing rewards (e.g., verbosity vs. conciseness) may cause seesaw effects even with multi‑objective RL.

### Mechanism 3
- **Claim**: Load‑balanced MoE routing stabilizes multi‑task training by preventing expert collapse while allowing specialization.
- **Mechanism**: Global batch load‑balancing loss (Eq. 15) across all tasks, combined with z‑loss (Eq. 16) to regularize router logits. Balances token distribution globally without per‑batch enforcement, preserving task‑specific specialization.
- **Core assumption**: Experts can specialize for distinct planning paradigms if load balancing is applied over full task distribution.
- **Evidence**: Abstract mentions load‑balanced MoE; Section 5 describes global LBL and z‑loss; Figure 10 shows distinct expert patterns across tasks.
- **Break condition**: Dominant tasks may cause global balancing to under‑train experts for rare paradigms.

## Foundational Learning
### Hierarchical Task Decomposition
- **Why needed**: Essential for breaking complex user queries into executable subtasks; MagicAgent’s synthetic data builds this via graph aggregation.
- **Quick check**: Can the model decompose "Plan a weekend trip to Beijing" into concrete ordered subtasks (e.g., book flight, reserve hotel)?

### Mixture‑of‑Experts (MoE) Routing
- **Why needed**: MagicAgent‑30B‑A3B uses MoE to maintain capacity while reducing inference cost; engineers must ensure load balancing to avoid training collapse.
- **Quick check**: Does the router distribute tokens across experts without extreme concentration (>80% on one expert)?

### Reinforcement Learning from Verifiable Rewards (RLVR)
- **Why needed**: MagicAgent’s RL stages rely on rule‑based rewards (e.g., exact tool match, F1) for stable optimization without human feedback.
- **Quick check**: Are reward functions deterministic and aligned with task success (e.g., does format reward strictly enforce <Plan></Plan> tags)?

## Architecture Onboarding
**Component map**  
1. Synthetic Data Pipeline (5 modules for each planning paradigm)  
2. SFT Trainer (Qwen3 base, cross‑entropy loss, novelty sampling)  
3. Offline RL (GRPO with unified reward)  
4. Online RL (χPO with token/think/action entropy + IB bottleneck)  
5. MoE Layer (router with global LBL + z‑loss)

**Critical path**  
Synthetic data → Mix & SFT → Offline RL (static benchmarks) → Deploy to ALFWorld → Online RL (χPO). MoE optimization is applied throughout SFT/RL.

**Design tradeoffs**  
- Data generation vs. coverage: Graph‑based synthesis is fast but may miss edge cases present in human logs.  
- RL exploration vs. exploitation: χPO’s entropy regularization improves robustness but may slow convergence.  
- MoE capacity vs. load: Global balancing prevents collapse but can dilute expert specialization if tasks are too similar.

**Failure signatures**  
- Low step accuracy on MagicEval‑Plan → decomposition module failure.  
- High expert load variance (MaxViobatch > 0.5) → router instability.  
- Declining online rewards in ALFWorld → χPO hyperparameters (λ₁, λ₂, λ₃) misconfigured.

**First 3 experiments**  
1. **Synthetic data validation**: Run format/semantic checks (Appendix C/D/E/F/G) on 1k samples; expect >95% pass.  
2. **Offline RL reward sanity**: Compute unified reward components (Eq. 3–8) on a held‑out set; each component should correlate with human judgments.  
3. **MoE load balance**: Monitor expert token ratios during first 100 steps; MaxViobatch should trend downward with z‑loss.

## Limitations
- Synthetic data realism: Graph‑based plan aggregation may not capture semantic complexity; risk of spurious trajectories.
- Reward design: Unified multi‑objective reward may not fully align with true task success; potential for suboptimal trade‑offs.
- MoE load balancing: Global LBL might not handle skewed task distributions, leading to under‑trained experts for rare paradigms.

## Confidence
- Synthetic data framework: Medium
- Two‑stage training (SFT + multi‑objective RL): Medium
- Load‑balanced MoE: Medium
- SOTA vs. ultra‑scale models: Low

## Next Checks
1. **Synthetic Data Fidelity**: Sample 1 k synthetic trajectories; compute BERTScore and constraint satisfaction against a held‑out set of human logs (e.g., AgentBank). Target: similarity > 0.85, pass rate > 95%.
2. **Gradient Interference Ablation**: Compare full pipeline against ablations (SFT‑only, RL‑only). Measure variance of performance across the five planning tasks; expect reduction > 50% relative to single‑stage baselines.
3. **MoE Load Balance Monitoring**: Track per‑expert token proportion CV and maximum load during initial 10 k steps. With LBL + z‑loss, expect CV < 0.2 and no expert > 40% of tokens.
