# UVLM: A Universal Vision-Language Model Loader for Reproducible Multimodal Benchmarking

## Quick Facts
- **arXiv ID:** 2603.13893
- **Source URL:** https://arxiv.org/abs/2603.13893
- **Reference count:** 25
- **Primary result:** Qwen2.5-VL-32B with advanced reasoning achieved 88.0% mean proximity score across five urban street-view tasks.

## Executive Summary
UVLM is a Google Colab framework designed to address fragmentation in vision-language model (VLM) benchmarking by abstracting architectural differences between LLaVA-NeXT and Qwen2.5-VL families behind a single inference function. It enables reproducible experiments through features like a modular prompt builder, consensus validation via majority voting across repeated runs, and configurable token budgets for chain-of-thought reasoning. In an evaluation on 120 street-view images across five tasks of increasing complexity, Qwen2.5-VL-32B with reasoning attained the highest overall proximity (88.0%), with vehicle counting reaching 95.0% accuracy within ±1 of human counts. The results reveal that model size does not guarantee superior performance—LLaVA 34B ranked last (62.2%)—and that reasoning improves some tasks for Qwen while increasing parsing failures for LLaVA models.

## Method Summary
UVLM is implemented as a sequential three-block Google Colab notebook. Block 1 loads a selected VLM (LLaVA-NeXT or Qwen2.5-VL) using Hugging Face Transformers with optional BitsAndBytes quantization, instantiating a family-specific processor. Block 2 defines tasks using a modular prompt structure (Role, Task Description, Theory, Format) and configures generation parameters (token budget, consensus runs). Advanced reasoning mode auto-replaces the Format block with a standardized chain-of-thought directive and increases the token budget. Block 3 processes a folder of images, invoking a unified `run_inference()` function that routes to the appropriate backend pipeline, then parses responses into task-specific values. For consensus-enabled tasks, multiple runs are aggregated via majority vote (excluding parse failures). The output CSV contains raw predictions, consensus values, truncation flags, and, for reasoning tasks, the full reasoning trace. Primary evaluation uses a mean proximity score, defined per task as `max(0, 1 - |y - ŷ| / R)`, where `R` is the observed range of human annotations.

## Key Results
- Qwen2.5-VL-32B with advanced reasoning achieved the highest overall proximity score (88.0%).
- Vehicle counting precision reached 95.0% within ±1 of human annotations.
- Larger models did not systematically outperform smaller ones; LLaVA 34B ranked last overall (62.2%).

## Why This Works (Mechanism)
UVLM succeeds through three core mechanisms. First, it abstracts fundamental architectural differences between VLM families—such as processor APIs (`LlavaNextProcessor` vs. `AutoProcessor` + `process_vision_info`) and decoding patterns—by routing the forward pass through a dual-backend pipeline that converges at a common `parse_response()` function. This allows a single `run_inference()` interface to handle both LLaVA-NeXT and Qwen2.5-VL models, assuming outputs can be reliably reduced to task-specific values after architecture-specific cleaning. Second, consensus validation stabilizes outputs against stochasticity and format non-compliance by executing each task multiple times (2–5 runs) and determining the final value via majority vote over parsed results, with `NA` (parse failure) values excluded. This leverages the assumption that correct answers form the mode across runs while failures are random noise. Third, a modular prompt builder decouples reasoning strategy from task definition, enabling controlled chain-of-thought experiments. Prompts are assembled from four components, and the "advanced reasoning" mode substitutes a standardized CoT directive and expands the token budget to 1024, after which the parser scans the last 5 lines for `ANSWER:`. This isolates the impact of prompting from model architecture, though it relies on the model adhering to format directives.

## Architecture Onboarding
The framework comprises interconnected components: (1) Model Registry & Loader maps model IDs to families and handles `from_pretrained` with quantization; (2) Processor Abstraction wraps family-specific processors; (3) `run_inference()` branches on model family, applying distinct preprocessing and decoding before passing raw text to (4) `parse_response()`, which extracts numeric, category, or text values; (5) Prompt Builder assembles the four-part prompt and stores task configs; (6) Batch Engine iterates images and tasks, writes CSV, and (7) Truncation Detector flags incomplete generations. The critical path: select model → Block 1 loads model+processor → Block 2 defines tasks (creating closures for `run_inference` and `parse_response`) → Block 3 loops: for each image → for each task → call unified `run_inference()` → `parse_response()` → store raw → after all runs → `compute_consensus()` → write row. Design tradeoffs include simplicity vs. control (hides backend complexity but limits per-architecture tweaks), single-GPU focus (Colab-first but no multi-GPU batching), and parser generality (robust last-number extraction but fails on verbose outputs). Failure signatures: CUDA assertion crashes for Qwen-3B on T4 GPUs due to BF16/FP16 mismatch; high truncation and NA rates for LLaVA in reasoning mode (e.g., LLaMA3 8B: 16.8% truncation, 10.9% NA); zero parse failures for Qwen in standard mode; LLaVA 34B's surprisingly low performance (62.2%). First three experiments: (1) Load a LLaVA and a Qwen model, run a simple 50-token task, and compare output formats and processing times. (2) Craft a verbose CoT prompt, run with 3 consensus runs, and observe if `parse_response()` extracts the final answer or returns `NA`. (3) Configure frontage length with advanced reasoning on a truncating LLaVA model, inspect CSV for `_truncated` flags and run variance to see token budget effects.

## Open Questions the Paper Calls Out
- **Extending to new VLM families:** How can UVLM incorporate families like InternVL or BLIP-2 while preserving a unified interface? Each new family may require custom backend work due to divergent tokenization and decoding, and the current abstraction's generalizability is untested. Resolution would involve integrating at least two new families and demonstrating identical prompt handling on a common benchmark.
- **Multi-GPU batching:** What technical challenges must be overcome to implement efficient multi-GPU batching for VLMs with heterogeneous memory requirements? Current single-GPU design hinders large-scale evaluation; batching must manage variable memory footprints and dynamic token generation without OOM crashes. Resolution would be a deployed batched pipeline achieving near-linear speedup across supported models.
- **LLaVA size-performance anomaly:** Why do larger LLaVA-NeXT models (e.g., 34B) underperform smaller ones (e.g., 7B) on urban street-frontage tasks? The counterintuitive trend suggests architectural fit or prompt compatibility matters more than size, but no analysis isolates causes like overfitting or quantization artifacts. Resolution requires controlled experiments varying model size, quantization, and prompts, coupled with representation analysis.

## Limitations
- Missing per-task human value ranges (`R`) for sidewalk detection and entrance counting prevents exact proximity score replication.
- Ambiguity in the Zenodo annotation file format (e.g., CSV structure, image-ID mapping) risks metric miscalculation.
- The dual-backend abstraction may not accommodate new VLM families with incompatible tokenization patterns, limiting generalizability.

## Confidence
- **Abstraction (single inference function):** High – detailed dual-pipeline implementation and routing logic provided.
- **Consensus stabilization:** Medium – empirical NA rates support utility, but dependence on random failures is untested under systematic bias.
- **Modular prompt/CoT:** Medium – mixed results (Qwen improves, LLaVA degrades) indicate model-dependent interactions.
- **Overall reproducibility:** Medium – benchmark validity hinges on undisclosed annotation details and quantized inference quirks.
