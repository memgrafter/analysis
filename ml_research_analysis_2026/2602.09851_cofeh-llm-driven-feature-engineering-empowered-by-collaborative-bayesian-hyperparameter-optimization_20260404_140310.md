# CoFEH: LLM-driven Feature Engineering Empowered by Collaborative Bayesian Hyperparameter Optimization

## Quick Facts
- **arXiv ID:** 2602.09851  
- **Source URL:** https://arxiv.org/abs/2602.09851  
- **Reference Count:** 40  
- **Primary Result:** CoFEH reduces test error by 6–45% over baselines in joint FE+HPO and achieves the best average rank of 1.75.

## Executive Summary
CoFEH is a framework that tightly integrates LLM-driven feature engineering (FE) with Bayesian hyperparameter optimization (HPO) to overcome the traditional decoupling of these two critical AutoML stages. It introduces a mutual conditioning mechanism where the FE optimizer and HPO module share contextual state—FE pipelines are evaluated using HPO’s best-known hyperparameters, and HPO conditions on meta-features derived from FE states. A PUCB-based dynamic selector adaptively allocates the limited budget between FE and HPO based on their marginal utility. The FE search leverages a Tree-of-Thought approach with steerable LLM directives to flexibly compose heterogeneous pipelines. Evaluated on 28 datasets, CoFEH demonstrates superior performance and robustness, validating the necessity of coupled optimization.

## Method Summary
CoFEH interleaves two optimizers under a shared state: an LLM-powered FE module and a Bayesian HPO module. The FE search uses Monte Carlo Tree Search (MCTS) where node expansions invoke an LLM (gemini-2.0-flash) to synthesize executable Python code for feature transformations, guided by directives (Initialization, Exploration, Exploitation). A global memory stores elite operations for retrieval. HPO employs a Random Forest surrogate that predicts validation performance using hyperparameters concatenated with meta-features extracted from the current FE state. Mutual conditioning ensures FE children are evaluated with the best-known HPs for their parent node, and HPO updates node-specific performance ceilings (`˜v_max`). A multi-armed bandit (PUCB) dynamically chooses at each iteration whether to run an FE or HPO step, balancing exploration and budget allocation.

## Key Results
- In joint FE+HPO (200 evaluations), CoFEH reduces test error by 6–45% compared to baselines (OpenFE, Mindware, OCTree, ELLM-FT, LFG).
- Achieves the best average rank of 1.75 across 28 datasets, versus 4.50 for the top baseline.
- Generalizes effectively to different downstream models (XGBoost, MLP, CASH) and scales robustly with dataset size.

## Why This Works (Mechanism)
### Mechanism 1: Mutual Conditioning Between FE and HPO
The LLM-driven FE optimizer and Bayesian HPO share contextual information to make mutually informed decisions, avoiding greedy decoupling. The BO surrogate uses meta-features from FE pipeline states (dataset transformations) to condition hyperparameter search. Conversely, the MCTS-based FE search uses HPO-discovered performance ceilings (`˜v_max`) to guide node selection and evaluates new operations under the best-known hyperparameters for their parent. This bidirectional flow ensures FE proposals are assessed in the context of promising HPs and HPO considers the current FE landscape. The core assumption is that FE and HP performances are strongly coupled; mutual conditioning reduces noise in reward signals and avoids suboptimal local minima. Break condition: if meta-features fail to capture essential transformation impact (e.g., for highly non-linear pipelines), the surrogate becomes mis-specified, causing HPO to misalign with FE states.

### Mechanism 2: PUCB-Based Dynamic Optimizer Selection
A multi-armed bandit selector (Predictor Upper Confidence Bound) dynamically allocates budget between FE and HPO based on task-specific marginal utility. The reward term Q(a) reflects the empirical success rate of each optimizer in achieving performance breakthroughs. Time-varying prior weights steer early exploration toward FE to establish a "model-ready" feature space. Theorem 3.1 shows that under neutral reward signals, the allocated budget converges to equilibrium. The core assumption is that marginal utility varies across datasets and optimization stages; a neutral reward scenario should lead to balanced allocation. Break condition: if Q(a) estimates become noisy (e.g., high evaluation variance), the selector may misallocate budget. The linear prior schedule assumes a learnability warmup; if HPO is the primary bottleneck initially (e.g., on highly preprocessed data), early FE focus wastes budget.

### Mechanism 3: Steerable Tree-of-Thought Search for Free-Form FE
An LLM-powered MCTS explores unbounded FE pipeline topologies via steerable reasoning directives. The FE search is framed as sequential decision-making over dataset states. MCTS balances exploration/exploitation via UCT. The LLM generates new operations conditioned on a directive that steers behavior (Initialization for root nodes, Exploration for novel moves, Exploitation for elite operation retrieval). A global memory stores high-performing operations (Pareto frontier in (score, relative gain) space) to feed the Exploitation directive. The core assumption is that LLMs can reason about semantic feature transformations and produce executable code; MCTS can navigate the combinatorial space. Break condition: LLM generation failures (non-executable code, invalid operations) or poor memory retrieval can stall search. The unbounded space may yield invalid pipeline structures (e.g., applying a selector after a generation that removes generated features).

Knowledge of selection, expansion, playout, backpropagation is essential to understand how FE proposals are generated and evaluated. Quick check: In UCT formula Q(s') = R(s')/N(s') + v_max(s')~, what do the average reward (R/N) and the best-known descendant value (v_max) represent in the FE context?
- **LLM Prompting for Code Generation:** Needed because FE operations are Python code synthesized by an LLM from structured prompts. Understanding steerable reasoning (directives) and output constraints is critical. Quick check: How do the directives (Initialization, Exploration, Exploitation) alter the LLM’s prompt and generation strategy?
- **Meta-Feature Extraction:** Needed because HPO conditioning relies on dataset statistics that characterize FE states. Quick check: Which meta-features (e.g., statistical, information-theoretic) from the MindWare suite are most indicative of transformation impact?
- **Multi-Armed Bandits (MAB):** Needed for the dynamic selector. Understanding UCB variants and reward estimation is key. Quick check: How does PUCB’s use of a time-varying prior weight differ from standard UCB in addressing non-stationary rewards?

## Architecture Onboarding
### Component Map
LLM-driven FE optimizer (MCTS + Tree-of-Thought) -> generates FE pipeline code. Bayesian HPO module (BO + Random Forest surrogate) -> suggests HPs conditioned on meta-features. Dynamic optimizer selector (PUCB MAB) -> decides next action (FE or HPO). Shared state memory -> stores (FE operation, reasoning, meta-features, score, Δscore) tuples for retrieval. Meta-feature extractor -> computes dataset statistics (MindWare suite) from raw/transformed data. Evaluation harness -> executes FE code, trains model with given HPs, returns validation score.

### Critical Path
1. Selector chooses action (FE or HPO) via PUCB.
2. If FE: MCTS selects node; LLM generates operation (steered by directive + memory); code executed; new state evaluated with parent’s best HP; score backpropagated; operation stored in memory.
3. If HPO: BO builds candidate pool (local perturbations + global random) across all tree nodes; surrogate predicts (node meta-features + HP configs); acquisition selects best (s*, λ*); evaluated; surrogate updated.
4. Score updates selector’s Q(a) and node statistics (including ˜v_max).

### Design Tradeoffs
- **LLM cost vs. search efficiency:** Using a powerful LLM (e.g., GPT-5.2) yields better operations but higher API cost; cheaper models (Gemini-2.0-flash) may limit reasoning depth.
- **Memory size vs. relevance:** Larger memory provides more exploitation candidates but increases prompt length and risks irrelevant retrievals; Pareto filtering balances score vs. relative gain.
- **Prior weight initialization:** p1=0.9 assumes FE is the initial bottleneck; if HPO is actually limiting on a dataset, early FE steps waste budget.

### Failure Signatures
- Stagnant validation scores despite many iterations (search stuck; poor LLM proposals or insufficient exploration).
- Extreme budget imbalance (FE proportion <<0.4 or >>0.6 over many datasets) indicates PUCB parameters or Q(a) estimates malfunctioning.
- High variance in final test performance across runs signals instability in LLM generation or surrogate modeling.

### First 3 Experiments
1. **Ablate mutual conditioning:** Run "w/o Cond" variant to confirm performance drop; inspect if FE pipelines become incompatible with tuned HPs.
2. **Inspect selector behavior:** Plot FE proportion over iterations to verify decreasing trend and final balance ~0.5; cross-check with pure FE vs. pure HPO curves to validate task-adaptivity.
3. **Validate meta-feature utility:** Compare surrogate Spearman correlation with/without meta-features; if improvement is negligible, meta-features may not capture transformation impact.

## Open Questions the Paper Calls Out
### Open Question 1
**Question:** How can LLMs be guided to construct truly free-form, heterogeneous feature engineering pipelines—flexibly combining preprocessing, transformation, generation, and selection—rather than isolated feature generation?  
**Basis in paper:** [explicit] Challenge C1: "How can we empower LLMs to construct a truly free-form, human-expert-like FE pipeline that flexibly composes heterogeneous operations...?" They address this via Tree-of-Thought search.  
**Why unresolved:** LLM-based FE remains confined to generation subtasks in prior work; free-form composition is emerging. Limits of LLM reasoning depth, context windows, and scalability to complex domains are not fully understood.  
**What evidence would resolve it:** Systematic evaluation of pipeline diversity (number of distinct operation types) and performance across a broad spectrum of domains (including vision, NLP); stress tests with extremely large search budgets to see if improvements plateau or continue.

### Open Question 2
**Question:** How can LLM-based feature engineering and Bayesian hyperparameter optimization be jointly optimized in a tightly coupled manner, avoiding the greedy myopia of sequential "FE-then-HPO" workflows?  
**Basis in paper:** [explicit] Challenge C2: "How can we jointly optimize LLM-based FE and HPO in a coupled manner, rather than optimizing each in isolation?" The paper introduces mutual conditioning and interleaved optimization.  
**Why unresolved:** The mutual conditioning mechanism is empirically motivated; its theoretical properties (convergence, optimality gaps) are not analyzed. It is unclear whether interleaving always outperforms unified search spaces (like in Auto-sklearn) when the FE space is unstructured.  
**What evidence would resolve it:** Derivation of regret bounds or convergence guarantees under simplifying assumptions (e.g., stationary data, smooth Bayesian surrogate); large-scale experiments comparing interleaved vs. unified search on tasks with strong FE-HPO interactions.

### Open Question 3
**Question:** How should the limited optimization budget be dynamically allocated between FE and HPO, given that their marginal utility varies substantially across datasets and during the search?  
**Basis in paper:** [explicit] Challenge C3: "How should we allocate budget between FE and HPO, given that their marginal utility varies across tasks?" The paper proposes a PUCB-based dynamic optimizer selector.  
**Why unresolved:** The PUCB policy is heuristic; the provided "budget equilibrium" theorem holds only under neutral reward signals. It is unknown how the linear prior scheduling performs under non-stationary gains or with different exploration constants. Alternative bandit strategies (e.g., Thompson Sampling) have not been compared.  
**What evidence would resolve it:** Empirical comparison of PUCB against other adaptive allocation methods across a wide range of datasets; sensitivity analysis of the prior weight parameters; theoretical regret minimization under more realistic reward models.

### Open Question 4
**Question:** Can the CoFEH framework be effectively extended to non-tabular data modalities (e.g., images, text) by simply modifying prompts and operation spaces, while preserving the mutual conditioning and dynamic scheduling principles?  
**Basis in paper:** [inferred] The conclusion states that CoFEH "enables seamless extension to image and text data via simple prompt modifications." However, all experiments are on tabular datasets; no evidence is provided for other modalities.  
**Why unresolved:** Feature engineering for images/text involves fundamentally different primitives (e.g., data augmentations, token embeddings, architectural choices). The meta-features used to characterize FE states for HPO are designed for tabular data and may not apply. The LLM’s ability to generate valid pipeline code for these modalities is unproven.  
**What evidence would resolve it:** Implement a version of CoFEH for image classification (e.g., CIFAR-10) using CNN-based HPO spaces and image-specific FE operations (cropping, color jitter, etc.); similarly for text tasks (e.g., sentiment analysis). Demonstrate end-to-end performance gains over modality-specific AutoML baselines.

## Limitations
- **Meta-feature assumption:** The mutual conditioning relies on hand-crafted meta-features (MindWare suite) to represent FE states; these may not fully capture the semantic impact of complex, heterogeneous transformations, especially for non-tabular data or highly non-linear pipelines.
- **Prior weight schedule:** The PUCB selector’s linear prior (`ω_FE` init=0.9) assumes FE is the primary initial bottleneck; this may not hold for datasets with already well-preprocessed features, leading to wasted budget.
- **Scalability and cost:** The approach depends on frequent LLM calls and MCTS expansions, which may not scale cost-effectively to very large datasets or extremely high evaluation budgets due to API costs and latency.

## Confidence
- **Mutual Conditioning:** High – Well-specified bidirectional context sharing (Sec 3.2), but break condition hinges on meta-features capturing transformation impact—unverified across diverse data.
- **PUCB Selector:** Medium – Theorem 3.1 provides theoretical equilibrium, yet prior weight schedule assumes FE is initially limiting; performance under non-stationary gains is unknown.
- **Steerable ToT Search:** Medium – MCTS + LLM generation is detailed, but success depends on LLM code validity and memory relevance; unbounded space risks invalid pipelines—no error rate reported.
- **Generalization to Non-Tabular:** Low – Claims of extension are speculative; no experiments beyond tabular data, and meta-features are tabular-specific.
