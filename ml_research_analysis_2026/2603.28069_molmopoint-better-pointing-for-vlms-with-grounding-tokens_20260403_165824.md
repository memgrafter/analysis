# MolmoPoint: Better Pointing for VLMs with Grounding Tokens
## Quick Facts
- **arXiv ID**: 2603.28069
- **Source URL**: https://arxiv.org/abs/2603.28069
- **Reference count**: 40
- **Primary result**: MolmoPoint introduces grounding tokens (<PATCH>, <SUBPATCH>, <LOCATION>) for direct visual token selection, achieving state-of-the-art pointing performance with fewer output tokens and improved resolution invariance.

## Executive Summary
MolmoPoint proposes a novel pointing mechanism for vision‑language models that directly selects visual tokens using special grounding tokens, eliminating the need for coordinate generation. This coarse‑to‑fine hierarchy (<PATCH> → <SUBPATCH> → <LOCATION>) reduces output length, improves sample efficiency, and generalizes across image resolutions. Spatial ordering is enforced via rotary embeddings, and a no‑more‑points token prevents degenerate outputs. Evaluations on PointBench (70.7%), ScreenSpotPro (61.1% among open models), video pointing (59.1% human preference), and video tracking (+6.3% J&F) show substantial gains over coordinate‑based baselines. Ablations confirm the contribution of each component.

## Method Summary
MolmoPoint extends a VLM (Molmo2) by adding four special tokens: `<PATCH>`, `<SUBPATCH>`, `<LOCATION>`, and a no‑more‑points token. The vision encoder (ViT) outputs a grid of image tokens (each ~28×28 pixels) and fine‑grained subpatch features (14×14). During generation, `<PATCH>` computes a query from its hidden state and scores all image token keys via dot‑product attention (with rotary embeddings for spatial context). The selected token’s embedding is added to the current token’s representation for continuity. `<SUBPATCH>` then scores the four subpatches within the chosen coarse patch using stored ViT features. `<LOCATION>` predicts a 3×3 offset within that subpatch via a linear head. The no‑more‑points class competes with image tokens in `<PATCH>` scoring; if selected, the model stops emitting points. Training uses standard cross‑entropy loss on the grounding token decisions, with target indices derived from ground‑truth coordinates after mapping to the token grid. The method significantly reduces output tokens (one token per point vs. multiple digits) and shows improved resolution invariance.

## Key Results
- New state‑of‑the‑art on core benchmarks: 70.7% on PointBench, 61.1% on ScreenSpotPro (among fully open models).
- Video pointing achieves 59.1% human preference win rate over a coordinate baseline; video tracking improves by +6.3% J&F on Molmo2Track.

## Why This Works (Mechanism)
### Mechanism 1: Direct visual token selection
- **Claim**: Directly selecting visual tokens avoids learning a coordinate system, making pointing more intuitive and sample‑efficient.
- **Mechanism**: `<PATCH>` scores image tokens to pick a coarse patch; `<SUBPATCH>` chooses a fine‑grained subpatch; `<LOCATION>` predicts a 3×3 offset. This hierarchy reduces output tokens and tightly couples recognition with pointing.
- **Core assumption**: Visual tokens already encode semantic content; pointing reduces to matching.
- **Evidence anchors**: Abstract; Section 3.1; related work (FocusUI) shows promise of visual token selection.
- **Break condition**: If visual tokens are not discriminative or the model fails to learn the selection process, points will be inaccurate.

### Mechanism 2: Spatial ordering via rotary embeddings
- **Claim**: Rotary embeddings encode spatial relationships between selected patches, enabling consistent ordering and preventing double‑pointing.
- **Mechanism**: RoPE rotates query and key vectors based on the positions of the previously selected patch and the candidate patch, providing a relative encoding that helps maintain sorted point order.
- **Core assumption**: The order of points matters for video and multi‑point scenarios.
- **Evidence anchors**: Abstract; Section 3.3.
- **Break condition**: If ordering is unnecessary or position calculations are erroneous, the model may generate unordered or duplicate points.

### Mechanism 3: Stopping with no‑more‑points token
- **Claim**: A dedicated stop token prevents degenerate outputs by giving the model an explicit termination signal.
- **Mechanism**: A special no‑more‑points class with a fixed key embedding is added to the set of keys that `<PATCH>` can attend to; if it scores highest, the model stops generating further points and emits `</s>`.
- **Core assumption**: Without an explicit stop, the model might generate points even when none are correct or after all points have been produced.
- **Evidence anchors**: Abstract; Section 3.4.
- **Break condition**: If the model never selects or prematurely selects the stop token, it will over‑generate or under‑generate points.

## Architecture Onboarding
**Component map**: ViT → image tokens; LLM → grounding tokens; Projection layers (W_pq, W_pk, W_se) align dimensions; RoPE module; no‑more‑points embedding; input embedding modifier.

**Critical path**:
1. Preprocess: map each ground‑truth (x, y) coordinate to (image token index, subpatch index, location index) based on the token grid layout.
2. Training: For each `<PATCH>`, compute its query (linear + layernorm) and score against all image token keys (with RoPE); apply cross‑entropy loss against the target token index. After selection, add the chosen token’s embedding to the current token’s input embedding.
3. `<SUBPATCH>`: score the four ViT patches inside the selected coarse patch using stored subpatch features.
4. `<LOCATION>`: predict a 3×3 grid offset via a linear head applied to the selected subpatch’s features.
5. No‑more‑points: if selected, constrain decoding to terminate the point list.
6. Inference: cache all image token keys and subpatch features; generate points sequentially with monotonic token index constraint.

**Design tradeoffs**:
- Token efficiency vs. memory: Grounding tokens reduce output length but require additional key caching (≈1–2 LLM layers’ memory).
- Resolution independence: Pointing precision is fixed (~4.7 px) regardless of input size, aiding generalization but potentially limiting ultra‑high‑resolution detail.
- Training complexity: New parameters (query/key projections, no‑more‑points key, location head) and constraints (ordering, stop token) increase complexity but improve sample efficiency.
- Coarse‑to‑fine: Hierarchical selection is efficient, but an early mistake propagates to later stages.

**Failure signatures**:
- Overgeneration: many points (>10 or >2× ground truth) indicating failure to learn no‑more‑points.
- Unordered points: especially in video, if rotary embeddings are ineffective or monotonic constraint missing.
- Off‑by‑one counting errors on high‑frequency objects.
- Poor GUI pointing at high resolution if training data lacks such examples.
- Inability to stop: model generates endless points or repeats the same patch.

**First 3 experiments**:
1. Ablate grounding tokens: Replace with a text‑coordinate baseline (as in Table 3) to confirm the core gain.
2. Remove rotary embeddings and evaluate on video pointing (Molmo2‑VC/VP) to measure ordering impact.

## Open Questions the Paper Calls Out
1. **What drives sample efficiency gains?** Is the improvement due to reduced output tokens or the direct selection mechanism? Controlled experiments are needed to disentangle these factors.
2. **Why does video captioning degrade?** MolmoPoint-8B shows a significant drop in video captioning performance compared to image captioning, but the cause is not investigated.
3. **How does point ordering affect complex videos?** The enforced sorted order helps video pointing but hurts static image pointing; the optimal ordering may be domain‑dependent, and adaptive strategies are unexplored.
4. **When does the no‑more‑points token fail?** The fixed embedding may cause premature or delayed stopping; a more nuanced stopping mechanism could be beneficial.
5. **Can the coarse‑to‑fine hierarchy be adaptive?** The fixed three‑stage refinement yields ~4.7 px precision, which may be suboptimal for domains requiring different scales (e.g., microscopy, satellite). Learnable refinement depth or patch sizes could improve performance.

## Limitations
- **Base architecture details** (Molmo2’s ViT/LLM configuration, projection dimensions) are not fully specified, hampering exact replication.
- **Training hyperparameters** (optimizer settings, learning rate schedules, packing strategies) are incomplete, requiring guesswork.
- **Coordinate mapping for multi‑crop inputs** (e.g., 48 overlapping GUI crops) is ambiguous, making it hard to reproduce high‑resolution pointing accurately.
