# CLI-Gym: Scalable CLI Task Generation via Agentic Environment Inversion

## Quick Facts
- **arXiv ID:** 2602.10999
- **Source URL:** https://arxiv.org/abs/2602.10999
- **Reference count:** 40
- **Primary result:** Introduces agentic environment inversion to automatically generate 1,655 CLI tasks from 29 repositories; fine-tuned models achieve up to +46.1% Pass@1 improvement on Terminal-Bench, outperforming much larger open-weight models.

## Executive Summary
CLI-Gym addresses the chronic lack of scalable, environment-intensive CLI tasks for agent training by introducing agentic environment inversion. Starting from a healthy Docker-based gold environment, an agent explores command histories to deliberately induce failures, capturing the degradation process in a Dockerfile. This automates task generation, producing 1,655 tasks from 29 repositories—approximately 20 times more than prior manually curated benchmarks like Terminal-Bench. Fine-tuning Qwen3 models on 291 curated successful trajectories yields LiberCoder, which achieves substantial absolute improvements on Terminal-Bench 1.0: +28.6% to 38.9% Pass@1 for the 32B variant and +21.1% to 46.1% for the 235B variant. The method establishes the first public pipeline for scalable derivation of such tasks.

## Method Summary
CLI-Gym automates CLI task generation via a two-stage SFT pipeline. First, a pretraining stage initializes the agentic coding model on 48K Software Engineering (SWE) trajectories (excluding Terminal-Bench). Second, a finetuning stage uses 291 high-quality trajectories collected on the newly generated CLI-Gym tasks. The core innovation is the task generation pipeline: for each of 29 selected repositories, a gold Docker environment is constructed where all unit tests pass. A query generator samples unit tests and disruption directions to prompt an inversion agent (based on OpenHands). The agent executes CLI commands to degrade the environment, logging modifications into a Dockerfile. After inducing at least one unit test failure, a task assembler auto-generates a natural language problem statement from the error messages and packages the Dockerfile, tests, and description into a task instance. A trajectory collector then runs trained agents on these tasks to gather successful repair trajectories, which are filtered (≥20 steps, no cheating) before finetuning.

## Key Results
- Generated 1,655 tasks from 29 repositories—approximately 20× the scale of prior manually curated benchmarks like Terminal-Bench.
- LiberCoder (Qwen3 fine-tuned) achieves +28.6% to 38.9% Pass@1 (32B) and +21.1% to 46.1% Pass@1 (235B) on Terminal-Bench 1.0.
- Outperforms much larger open-weight models (e.g., Llama 3.1 405B) on the same benchmark.

## Why This Works (Mechanism)

### Mechanism 1: Agent-Driven Environment Degradation
Agents simulate environment histories to deliberately degrade a healthy Docker environment into a failing state. Starting from a gold environment (all unit tests pass), an agent iteratively executes CLI commands (modifying filesystem, dependencies, configurations) guided by execution feedback. The sequence of modifications is captured in a Dockerfile, representing the degradation trajectory that induces test failures. The core assumption is that the agent’s action space and exploration policy are sufficient to generate realistic, diagnosable failures across diverse software environments. Evidence: [abstract] states "starting from a healthy Docker-based gold environment, an agent explores command histories to deliberately induce failures, capturing the degradation process in a Dockerfile." [Section 3.2] describes "an autonomous agent then applies structured perturbations … to intentionally induce failures … the agent produces a perturbed environment." Break condition: If the agent fails to induce any unit test failure within the execution budget (e.g., 15 minutes per task), no valid task is produced.

### Mechanism 2: Fail-to-Pass Task Formation
A buggy environment state coupled with failing unit tests constitutes a well-formed, verifiable CLI task instance. After degradation, the harness runs selected unit tests. If any fail, those become “fail-to-pass” test cases, and the error messages are used to auto-generate a natural language problem statement. The final task packs: (i) the Dockerfile that reproduces the buggy state, (ii) the issue description, and (iii) the unit tests. The core assumption is that induced failures are deterministic, reproducible, and their symptoms are adequately captured by the unit tests and error logs. Evidence: [abstract] "from which a task can be derived by packing the buggy state and the corresponding error messages." [Section 3.2] "reconstruct the environment … If at least one unit test fails, the instance is deemed a successfully generated task." [Section A.3] details prompt-based generation of repair issue from failed tests and task description. Break condition: If tests are flaky, non-deterministic, or if the failure is irreproducible from the Dockerfile, the instance is discarded.

### Mechanism 3: Scalable Automation
Fully automating the inversion pipeline enables scaling CLI task generation by orders of magnitude over manual curation. The pipeline processes many GitHub repositories in parallel: each gold instance seeds multiple agent exploration runs, each potentially yielding a distinct task. A memory pool prevents duplicate task themes, enhancing diversity. No human intervention is needed beyond initial repository selection. The core assumption is that agent-driven exploration yields a sufficiently diverse set of failure modes that mirror real-world environment issues. Evidence: [abstract] reports "1,655 tasks from 29 repositories—approximately 20 times more than prior manually curated benchmarks." [Section 3.3] states "our pipeline is fully automated and operates without any human intervention." [Section 4.3] ablation shows performance gains scale with number of repositories (environment diversity) and trajectory count. Break condition: If agent exploration converges to a narrow set of failure patterns (low diversity), the pipeline’s scalability benefit diminishes despite high quantity.

## Foundational Learning
- **Agentic coding with tool-augmented LLMs:** The inversion agent must decide which CLI commands to execute; understanding tool use (bash, file editor) and iterative reasoning is essential. *Quick check:* How does the agent’s action space differ from standard code-generation, and why is execution feedback critical for environment inversion?
- **Docker-based environment reproducibility:** Gold and buggy states are encoded as Dockerfiles; the pipeline relies on containerization to capture and replay exact system states. *Quick check:* What information does a Dockerfile contain that version control does not, and why is this crucial for environment-intensive tasks?
- **Unit tests as verifiable success signals:** Both degradation (inducing failures) and repair (evaluating solutions) depend on pass/fail outcomes of a fixed set of unit tests. *Quick check:* Why are “fail-to-pass” tests preferred over “pass-to-pass” for training agents, and what risks do pass-to-pass tests pose?

## Architecture Onboarding
Gold constructor -> Query generator -> Inversion agent (OpenHands) -> Task assembler -> Trajectory collector.

- **Critical path:** Gold environment construction → Decomposition of unit tests → Agent-driven degradation → Test evaluation → Problem statement generation → Task instance storage. Any failure in inducing unit test failures aborts the instance.
- **Design tradeoffs:**
  - *Automation vs. quality:* Fully automated generation yields scale but requires filtering (e.g., remove trivial or cheating trajectories).
  - *Diversity vs. cost:* More repositories and longer agent runs increase diversity but linearly increase token/compute expense.
  - *Hint usage:* Adding hints in repair issues increases data yield but may reduce difficulty; whether to keep hints is configurable.
- **Failure signatures:**
  - *Looped behavior:* Agent repeats unproductive actions, leading to context overflow or timeouts.
  - *Trivial tasks:* Solved in <20 steps; likely lack diagnostic depth.
  - *Cheating:* Exploits cached artifacts (e.g., .git, conda caches) that give away the solution without genuine repair.
  - *Non-reproducible:* Dockerfile does not consistently induce the same test failures.
- **First 3 experiments:**
  1. **End-to-end generation sanity check:** Pick one repo, run the full pipeline, verify that at least one task is produced with a failing unit test and a coherent problem statement.
  2. **Reproducibility test:** Take the generated Dockerfile, rebuild the buggy environment from the gold image, and confirm the same tests fail with similar error messages.
  3. **Agent baseline evaluation:** Run the base Qwen3 model (without fine-tuning) on a small sample of generated tasks using OpenHands; measure initial pass rate to establish a performance baseline before fine-tuning.

## Open Questions the Paper Calls Out
- **Open Question 1:** Why are gaming and scientific computing tasks not improved by CLI-Gym training, and how can the pipeline cover these domains? *Basis:* Section 4.4 explicitly identifies gaming and scientific computing as remaining challenging and not addressed by their method, calling them promising directions for future research. *Why unresolved:* These categories represent important real-world applications; without understanding why they resist improvement, the dataset and resulting models may have significant blind spots.
- **Open Question 2:** How can agents be prevented from exceeding context length during extensive exploration while preserving the performance gains from CLI-Gym training? *Basis:* Section 4.4 observes that after training, models engage in more extensive exploration, increasing the likelihood of exceeding the 128k token context limit. *Why unresolved:* Context length is a hard constraint in deployment; if improved agents frequently exceed it, their enhanced capabilities cannot be utilized.
- **Open Question 3:** Beyond simple heuristics like step count and cheating detection, what specific characteristics define a high-quality agent trajectory for environment-intensive tasks? *Basis:* Section 4.3 filters trajectories using only these heuristics and finds that when combined with SWE pretraining, filtered trajectories (291) outperform raw ones (417). The paper does not elaborate on a more nuanced definition of trajectory quality. *Why unresolved:* The current filtering is crude and may discard useful data or retain low-quality examples.
- **Open Question 4:** How sensitive is the CLI-Gym pipeline to the capability of the agent used for environment inversion? Could weaker inversion agents still generate tasks that are useful for training strong downstream agents? *Basis:* Section 3.2 mentions using "strong language models" as rollout agents but does not investigate the impact of inversion agent strength on task quality or training utility. *Why unresolved:* If strong inversion agents are necessary, the pipeline requires already-capable agents to bootstrap, creating a chicken-and-egg problem that limits accessibility.

## Limitations
- The LLM used for degradation agent rollouts and prompt generation is unspecified and likely proprietary, preventing exact replication without a comparable model.
- Gold environment construction details (base image, system dependencies, test harness) are underspecified, risking variability in reproducibility.
- Filtering criteria for "cheating" and trivial trajectories are informal; no thresholds or code are provided, potentially allowing low-quality tasks.

## Confidence
- **Scalable generation (≈20× manual benchmarks):** Medium (supported by reported counts but yield variability and hidden break conditions unclear).
- **Task validity (fail-to-pass instances):** Medium (filtering improves quality, but intrinsic difficulty and diversity are not thoroughly characterized).
- **Training efficacy (+21–46% Pass@1 gains):** High (rigorous exclusion of Terminal-Bench from training data, consistent gains across model sizes).

## Next Checks
1. **Agent capability audit:** Re-run the inversion agent on a subset of gold environments using a strong open-weight LLM (e.g., Qwen-72B) with reported prompts; compare task yield and failure diversity to the paper’s numbers.
2. **Gold environment stability:** Rebuild gold Docker images for all 29 repositories using a standardized protocol; confirm all unit tests pass consistently across multiple builds and document any flakiness.
3. **Contamination audit:** Fingerprint the 48K SWE trajectories and the 291 training tasks against Terminal-Bench test cases to verify no data leakage; compute similarity scores to ensure independence.
