# Language Models Don't Know What You Want: Evaluating Personalization in Deep Research Needs Real Users

## Quick Facts
- **arXiv ID:** 2603.16120
- **Source URL:** https://arxiv.org/abs/2603.16120
- **Reference count:** 40
- **Primary result:** Offline metrics and LLM judges fail to capture user satisfaction in personalized deep research; real user studies reveal critical failure modes missed by synthetic evaluation.

## Executive Summary
This paper introduces MyScholarQA (MySQA), a deep research system that personalizes outputs by inferring researcher profiles from selected papers, proposing tailored actions for queries, and generating reports that visibly incorporate those actions. While offline synthetic benchmarks show MySQA outperforms prior systems on citation accuracy and action adherence, a live user study with 21 active researchers uncovers nine nuanced personalization failures—such as overclaiming, narrow actions, and uninformative reports—that neither offline metrics nor LLM judges could detect. The findings argue that real user feedback is indispensable for evaluating personalized AI and offer design lessons: manage user control transparently, support multimodal content, and adopt mixed evaluation strategies.

## Method Summary
The authors conduct a three-part evaluation. First, they build a synthetic benchmark of research queries paired with paper sets and expertise levels to profile accuracy, action utility, and report quality across models. Second, they run an online user study where participants interact with MySQA, providing satisfaction ratings and qualitative feedback on profiles, actions, and reports. Third, they simulate an LLM-as-judge experiment: for each user-tagged failure instance, they test four LLMs' ability to predict satisfaction, comparing against a majority-class baseline. The contrast between synthetic and human evaluations reveals systematic gaps in automated metrics.

## Key Results
- MySQA surpasses prior deep research baselines (ScholarQA, OpenAI DR) in offline metrics for citation accuracy, answer coverage, and action adherence.
- A user study identifies nine failure modes in personalization (e.g., DOMAIN errors, NARROW actions, UNINFORM reports) that offline evaluations completely missed.
- LLM judges cannot predict user satisfaction better than random baselines across all failure aspects, underscoring the inadequacy of automated evaluation for personalized DR.

## Why This Works (Mechanism)

### Mechanism 1: Profile Inference from Papers
- **Claim:** Inferring a structured user profile from selected research papers captures a researcher’s interests, style, and preferences, enabling downstream personalization.
- **Mechanism:** An LLM generates sentence-level inferences across five categories (knowledge, research style, writing style, audience, positions) by analyzing paper snippets; each inference cites specific paragraphs for transparency, and users can edit/disable inferences.
- **Core assumption:** Research papers reliably signal a researcher’s persistent traits; LLMs can accurately extract high-level, personalized inferences from paper content.
- **Evidence anchors:**
  - [abstract] "infers a profile of a user's research interests" and "infers user profiles via papers users pick to capture their interests"
  - [section 2.1] Detailed prompt design, category definitions, and user-editable profile interface.
  - [corpus] Related work on user profiling supports using user context for personalization, but direct evidence for paper-based profiling is limited.
- **Break condition:** Profile contains overgeneralized, inaccurate, or irrelevant inferences (e.g., DOMAIN mismatches, OVERCLAIM), observed in 27% of user-reviewed profiles (§4.2).

### Mechanism 2: Action Proposal for Control
- **Claim:** Proposing a list of tailored actions for the user to select/adapt balances user control with automation efficiency, steering report generation without repeated clarification.
- **Mechanism:** For a query *q* and profile *P*, generate actions in four implementation categories (search_add, search_refine, organization, generation) with qualitative labels (content, style, specificity, usefulness); users edit/disable actions before report synthesis.
- **Core assumption:** Users prefer upfront, structured control (persistent profile + action selection) over iterative follow-up questions; actions can be executed reliably by the report pipeline.
- **Evidence anchors:**
  - [abstract] "proposes personalized actions for a user's input query"
  - [section 2.2] Action categories, prompt design, and user-editable action list; rationale from formative study.
  - [section 5 Lesson 1] Users reported saved time and appreciated transparency vs. follow-up questions.
  - [corpus] Work on personalization challenges highlights difficulties but does not directly address action-based control.
- **Break condition:** Actions become too narrow (NARROW) or deviate from query intent (OFFTOPIC), leading to reports that miss user goals (§4.2).

### Mechanism 3: Highlighted Report Generation
- **Claim:** Generating a report that follows user-approved actions and highlights where personalization occurs improves perceived quality, trust, and sensemaking.
- **Mechanism:** Adapt ScholarQA’s retrieval and generation prompts to incorporate actions; during generation, insert colored highlights marking text spans corresponding to each action, allowing users to toggle visibility.
- **Core assumption:** Users need to understand and verify how their profile and actions shaped the output; highlighting makes personalization legible without overwhelming.
- **Evidence anchors:**
  - [abstract] "writes a multi-section report for the query that follows user-approved actions"
  - [section 2.3] Prompt modifications and highlight implementation.
  - [section 5 Lesson 2] Users found highlights helpful for focus, though preferences on density varied; overtrust risk noted when no highlights appear.
  - [corpus] No direct corpus evidence for action highlighting; design draws on general HCI principles.
- **Break condition:** Highlights missing for selected actions (IGNORE), or reports remain vague/uninformative (UNINFORM) despite actions (§4.2).

## Architecture Onboarding
- **Component map:** Selected Papers -> Profile Inference -> Action Proposal -> Report Generation -> User Interface
- **Critical path:** User selects papers → system infers editable profile *P* → user submits query *q* → system proposes editable actions *A* → user approves *A* → system retrieves and generates report *R* with highlights → user reviews and provides feedback.
- **Design tradeoffs:**
  - User control vs. effort: Editable profiles/actions increase agency but burden users; system assumes upfront effort saves time later.
  - Specificity vs. generality: Personalized actions risk being too narrow; system mixes personalized and generic actions to hedge.
  - Transparency vs. clutter: Highlights make personalization legible but can overwhelm; user preferences vary.
- **Failure signatures:**
  - Profile: DOMAIN (wrong technical terms), OVERCLAIM (broad claims from limited evidence), CONVENTION (generic field norms).
  - Actions: NARROW (overly restrictive), OFFTOPIC (distracts from query), TRUST (user doubts executability).
  - Reports: UNINFORM (vague content), PRESENT (wrong format), IGNORE (action not followed).
  - Global: Highlights missing/misleading; user overtrust when no highlights appear.
- **First 3 experiments:**
  1. Offline synthetic evaluation: Build (query, paper set, expertise) dataset; measure profile accuracy, action win rate, report quality, action adherence across LLMs and DR baselines.
  2. Online user study: Recruit 21 active DR users; conduct 90-minute interviews with live MySQA; collect satisfaction ratings and qualitative feedback.
  3. LLM judge simulation: For each failure instance, create binary satisfaction labels; test 4 LLM judges to predict satisfaction; compare to majority baseline.

## Open Questions the Paper Calls Out
- **Question 1:** How can personalized DR systems improve factuality to avoid errors like using incorrect domain terms (DOMAIN) or making overgeneralized claims (OVERCLAIM)? Basis: Section 4.2 and Table 4 identify these as top failure modes; offline metrics and LLM judges failed to detect them.
- **Question 2:** What multimodal content (e.g., code snippets, formulas, visualizations) should personalized DR reports include, and how can systems select appropriate modalities based on user background? Basis: Lesson 3: participants requested modalities beyond text, such as code for coders, LaTeX for theorists.
- **Question 3:** What user control mechanisms (e.g., toggles, paper filters, multi-turn dialogue) are most effective for personalized DR, and how should control be adapted for query type or user expertise? Basis: Lesson 1: users desired more control but noted risks like filter bubbles and varying effort tolerance.
- **Question 4:** Can automated metrics (e.g., LLM judges) be developed that reliably predict user satisfaction in personalized DR, or are human evaluations irreplaceable? Basis: Section 4.3: four LLM judges failed to predict satisfaction, performing no better than majority baselines.

## Limitations
- Offline synthetic benchmark may not reflect real-world DR tasks or user expertise distributions.
- User study size (N=21) limits statistical power and generalizability across research domains.
- Profile inference relies on selected papers; performance with sparse or non-representative selections is unclear.
- Failure modes identified may be specific to MySQA's design or the academic DR context.
- LLM-as-judge failure might generalize to other personalized AI tasks, but this needs testing.

## Confidence
- **High Confidence:** "Offline metrics and LLM judges fail to predict user satisfaction for personalized DR." (Supported by direct user study comparison).
- **Medium Confidence:** "MySQA's specific mechanisms (profile, actions, highlights) yield measurable offline benefits." (Supported by synthetic evaluation, but real-world impact is uncertain).
- **Low Confidence:** "The nine failure modes are exhaustive or universally applicable." (Emergent from a small, specific study).

## Next Checks
1. **Scale user validation:** Replicate the online study with a larger, more diverse cohort (e.g., across STEM/humanities, career stages) to confirm failure mode prevalence and satisfaction predictors.
2. **Profile inference stress test:** Evaluate profile quality and downstream personalization when users provide 1-2 papers versus 10+, and with papers from dissimilar subfields to test robustness to "domain drift."
3. **Generalize judge failure:** Test if LLM judges can predict satisfaction for other personalized AI systems (e.g., coding assistants, learning tutors) using the same binary satisfaction-labeling protocol from §4.3.
