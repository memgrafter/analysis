# Rudder: Steering Prefetching in Distributed GNN Training using LLM Agents

## Quick Facts
- **arXiv ID:** 2602.23556
- **Source URL:** https://arxiv.org/abs/2602.23556
- **Reference Count:** 40
- **Primary Result:** Rudder achieves up to 91% faster end-to-end training versus no prefetching and 82% versus static prefetching by using LLM agents to dynamically manage prefetch buffers, while reducing communication volume by over 50%.

## Executive Summary
Distributed training of Graph Neural Networks (GNNs) frequently stalls due to communication overhead when sampling remote nodes. Traditional static prefetching strategies are inefficient because graph structure and sampling patterns change dynamically. This paper introduces Rudder, a system that embeds lightweight LLM agents directly into the DistDGL training framework. These agents asynchronously observe runtime metrics—such as buffer hit rates and communication volume—and use in-context learning to decide whether to replace stale prefetched nodes, eliminating the need for offline training or manual tuning. Evaluated on the NERSC Perlmutter supercomputer across multiple large-scale graph datasets, Rudder significantly outperforms both no prefetching and static prefetching baselines, while also demonstrating superior generalization to unseen training configurations compared to traditional machine learning classifiers.

## Method Summary
Rudder modifies the DistDGL distributed GNN trainer by introducing two asynchronous threads per trainer process: a prefetcher thread and an inference daemon thread. The prefetcher manages a persistent buffer of remote nodes and issues asynchronous GPU-to-GPU communication requests. The inference daemon runs a quantized LLM (e.g., Gemma3-4B) via Ollama. It collects recent runtime metrics (e.g., %-Hits, communication volume, minibatch progress, recent replacement outcomes) into a structured context, queries the LLM for a "replace" or "skip" decision, and applies a scoring policy that decays the score of unused buffer entries (by 0.95) and triggers replacement for stale nodes (score < 0.95). Training and prefetching/agent inference proceed in parallel, with communication handled through shared Python queues. No offline training or fine-tuning of the LLM is performed; the agent relies solely on the provided prompt and in-context history.

## Key Results
- Rudder reduces end-to-end epoch time by up to **91%** compared to noPrefetch and **82%** compared to static prefetching.
- Communication volume is reduced by **over 50%** across evaluated datasets (Reddit, Papers100M, ogbn-arxiv).
- LLM agents achieve higher Pass@1 decision accuracy and better generalization to unseen batch sizes/configurations than supervised ML classifiers, without retraining.

## Why This Works (Mechanism)
Rudder succeeds because it replaces rigid, pre-defined prefetch schedules with a closed-loop adaptive controller. The LLM agent reasons over a concise summary of recent performance metrics and history, enabling it to recognize patterns—such as diminishing returns from frequent replacements or temporary spikes in remote sampling—that static policies miss. The asynchronous design prevents agent inference from stalling the training compute loop, while the scoring policy ensures the buffer gradually prioritizes useful nodes. This combination allows Rudder to maintain a high buffer hit rate (%‑Hits) with fewer unnecessary communication operations, directly cutting the dominant stall time in distributed GNN sampling.

## Architecture Onboarding
**Component Map:** Trainer Process -> Prefetcher Thread (manages buffer, issues async comms) <-> Shared Queues (requests/responses) <- Inference Daemon Thread (LLM agent) -> Ollama Server (local/remote). Metrics Collector runs in trainer thread, feeding the daemon.

**Critical Path:** Minibatch sampling triggers remote node lookup → Metrics updated → Context built (metrics + history) → LLM queried asynchronously → Decision returned → Scoring policy applied → Buffer replacement executed (if "replace").

**Design Tradeoffs:** LLM choice trades latency for reasoning depth (Gemma3-4B vs. SmolLM2-360M). Buffer size trades memory for hit rate. Decision frequency (per-minibatch vs. every N minibatches) trades agent responsiveness for inference overhead.

**Failure Signatures:** (1) Queue backlog >2 minibatches persistent → LLM too slow, decisions stale. (2) %‑Hits spikes early then decays → Agent overfits to initial conditions, lacks long-horizon reasoning. (3) ML classifier accuracy drops on new batch size → Distribution shift, needs periodic retraining.

**First Three Experiments:** 1) Run Rudder+Gemma3-4B on ogbn-arxiv (8 trainers, 2 nodes) against DistDGL baseline and static prefetching; compare epoch time and %‑Hits. 2) Vary buffer size (5%, 10%, 25%) to identify memory-performance sweet spot. 3) Force decision every minibatch vs. every 5 minibatches to measure inference overhead tolerance.

## Limitations
- **Prompt Engineering Gap:** The exact prompt template (system message, metric formatting, history window) is incompletely specified, hindering exact replication of the agent's reasoning logic.
- **Scoring Policy Tuning:** The decay factor (0.95) and staleness threshold are fixed without reported sensitivity analysis; optimal values may vary with dataset scale.
- **LLM Latency Overhead:** Real-world cluster latency (vs. local Ollama) and its interaction with minibatch pacing is unexplored; could limit scalability to larger node counts.
