# Agent Factories for High Level Synthesis: How Far Can General-Purpose Coding Agents Go in Hardware Optimization?
## Quick Facts
- **arXiv ID:** 2603.25719
- **Source URL:** https://arxiv.org/abs/2603.25719
- **Reference count:** 40
- **Primary result:** General-purpose LLM-based coding agents, without hardware-specific training, achieve a mean 8.27× speedup over baseline across 12 HLS kernels through a two-stage decomposition and global exploration pipeline.
## Executive Summary
This paper investigates the potential of general-purpose large language model (LLM) based coding agents to optimize hardware designs from algorithmic specifications, without any hardware-specific training. The authors propose an "agent factory" that orchestrates multiple specialized agents in a two-stage pipeline: Stage 1 decomposes the design into sub-kernels, independently optimizes each using a fixed set of pragma variations, and assembles feasible configurations under an area budget via integer linear programming (ILP); Stage 2 launches multiple parallel global agents from the top ILP solutions to explore cross-function optimizations such as pragma recombination and loop fusion. Evaluated on 12 HLS kernels using Claude Code and AMD Vitis HLS, scaling the number of global agents from 1 to 10 yields a mean 8.27× speedup over a baseline of no pragmas, with standout gains exceeding 20× on streamcluster and nearly 10× on kmeans. Notably, the best final designs often originate from lower-ranked ILP candidates, underscoring the value of global exploration beyond sub-kernel optimization.

The results demonstrate that even without domain-specific fine-tuning, LLM agents can effectively navigate the complex HLS design space by combining structured decomposition with flexible global refinement. The two-stage approach isolates intra-function optimization while allowing cross-function interactions to be discovered later, and agent scaling provides a practical knob to trade off token cost for solution quality.
## Method Summary
The agent factory implements a two-stage design space exploration (DSE) strategy. In Stage 1, a coordinator agent parses the input C/C++ code to build a call graph and identify separable sub-functions. For each sub-function, a dedicated optimizer agent generates M=7 variants (e.g., baseline, conservative pipeline, aggressive unroll, array partitioning). Each variant is functionally validated and synthesized with Vitis HLS to obtain area and latency estimates. The collected variant data feeds an ILP solver, which models total latency as a static composition derived from the call graph (summing latencies along sequential paths, taking maxima over parallel branches). The ILP selects one variant per function to minimize total latency while respecting a global area budget, and returns the top-N feasible solutions. In Stage 2, N parallel exploration agents are spawned, each starting from one of the top-N variant sets. These agents iteratively propose design-wide transformations—such as combining pragmas across functions, fusing loops, or globally restructuring memory—and apply them to the code. Each proposed design is checked for functional correctness and synthesized; valid improvements are retained. The entire system outputs the lowest-latency design found across all agents. This architecture balances exploitation (through systematic sub-kernel optimization) with exploration (via global agent trajectories).
## Key Results
- Mean 8.27× speedup over baseline across 12 kernels; up to 20× on streamcluster and ~10× on kmeans.
- Scaling the number of global agents (N) from 1 to 10 consistently improves solutions, demonstrating the benefit of parallel exploration.
- The best final designs frequently originate from non-top-ranked ILP candidates, confirming that cross-function optimization uncovers improvements missed by sub-kernel selection alone.
## Why This Works (Mechanism)
### Mechanism 1: Sub‑kernel decomposition and ILP assembly
**Claim:** Decomposing a design into sub‑kernels, optimizing each independently, and using an ILP to assemble configurations under area constraints yields a set of promising full‑design candidates more efficiently than monolithic search.  
**Mechanism:** The coordinator agent parses the call graph to identify separable sub‑functions. Independent optimizer agents each explore a structured set of M=7 variants per sub‑kernel (e.g., baseline, pipeline, unroll, array partition). For each variant the agent modifies code/pragmas, runs functional tests, invokes Vitis HLS synthesis, and records latency and area. The ILP solver receives the variant sets and the call graph, derives a latency composition model *h(·)* that sums latencies along sequential paths and takes maxima over parallel branches, then solves a binary ILP to select one variant per function minimizing total latency while respecting the global area budget. This isolates the impact of directives within each sub‑kernel before composing them.  
**Core assumption:** The latency of the full design can be approximated by a static composition of the independently synthesized latencies of its sub‑kernels, according to the program’s dataflow structure. Cross‑function interactions (e.g., memory bandwidth sharing, global loop fusion) are secondary and can be addressed later.  
**Evidence:** Described in the abstract and Section III.B; weak direct corroboration from the corpus (similar decomposition in LLM‑DSE [100868] but the specific ILP latency model is novel).  
**Break condition:** When cross‑function optimizations (e.g., loop fusion across sub‑kernels, shared memory restructuring) offer latency gains that cannot be predicted by summing independent sub‑kernel latencies. This triggers Stage 2.

### Mechanism 2: Agent scaling for global exploration
**Claim:** Launching multiple parallel global optimization agents over the top ILP solutions improves the probability of discovering lower‑latency designs by exploring diverse, non‑monotonic transformation paths that a single agent trajectory might miss.  
**Mechanism:** The coordinator spawns *N* independent exploration agents, each starting from a different top‑ranked ILP candidate. Each agent iteratively proposes design‑wide transformations (pragma recombination, code restructuring, memory optimization) across function boundaries, applies the change, checks correctness, synthesizes via HLS if area permits, and logs the outcome. After a fixed number of steps or convergence, the best valid design across all agents is selected. More agents increase the breadth of the explored region of the design space.  
**Core assumption:** The design space contains multiple, somewhat isolated basins of attraction for high‑performing designs. A single agent’s sequential reasoning may converge to a local optimum; parallel agents with different starting points can jump between basins.  
**Evidence:** Abstract reports mean 8.27× speedup scaling from 1 to 10 agents; Section IV.B.3 shows Pareto front extensions and non‑monotonic gains (e.g., NW: N=8 > N=10 under tight area). Concept aligns with inference‑time scaling [36] and multi‑agent path finding [108873].  
**Break condition:** Saturation when the top‑N ILP starting points are very similar or area budget is so tight that all feasible high‑performance designs are found early. Token cost grows linearly with *N* (median 5.82M tokens/run).

### Mechanism 3: Cross‑function optimization beyond ILP
**Claim:** Global optimization via multiple agents uncovers design improvements that are invisible to the sub‑kernel + ILP selection stage because it can apply cross‑function transformations that alter the call graph’s effective execution structure.  
**Mechanism:** Stage‑2 agents are not confined to a single sub‑kernel. They can perform loop fusion that merges iterations across function calls, restructure memory hierarchies globally (e.g., partitioning an array used by multiple functions in a coordinated way), or apply compute optimizations that span sub‑kernels (e.g., factoring a repeated computation). These transformations change the latency composition model *h(·)* used by the ILP, potentially yielding lower latency for the same area.  
**Core assumption:** The best achievable design for a given area budget may require changing how sub‑kernels interact, not just selecting the best variant for each in isolation. The ILP’s *h(·)* is a fixed, static approximation from the original call graph.  
**Evidence:** Abstract states “the best designs often originate from non‑top‑ranked ILP candidates”; Section IV.B.3 explicitly confirms that Stage 2 can exploit cross‑function interactions that the ILP model cannot capture.  
**Break condition:** For codes with a very simple, linear call graph where sub‑kernels have minimal interaction (e.g., a straight‑line sequence of independent functions), cross‑function transformations may offer little marginal gain over optimal sub‑kernel selection.
## Foundational Learning
- **High-Level Synthesis (HLS) Pragmas**  
  *Why needed:* Agents manipulate directives like `PIPELINE`, `UNROLL`, and `ARRAY_PARTITION` to trade latency for area. Understanding their semantics (e.g., `PIPELINE` reduces initiation interval but may increase register pressure; `ARRAY_PARTITION` breaks memory bottlenecks but uses more BRAMs) is necessary to interpret agent actions and ILP trade‑offs.  
  *Quick check:* If `UNROLL(factor=4)` on a loop with a carried dependency increases latency, what is the most likely bottleneck the agent must resolve first?

- **Function Call Graph Analysis**  
  *Why needed:* The coordinator agent extracts the call graph to (a) decompose the design into sub‑kernels for Stage 1, and (b) derive the latency composition model *h(·)* for the ILP. Incorrect graph analysis leads to wrong variant assignments and latency estimates.  
  *Quick check:* For two functions F and G called sequentially inside a loop that iterates 100 times, how does their latency contribute to total cycles in the ILP model? (Answer: Each iteration incurs latency(F)+latency(G); total = 100*(lat(F)+lat(G)).)

- **Integer Linear Programming (ILP) for Combinatorial Selection**  
  *Why needed:* The ILP formally encodes the problem of selecting one variant per sub‑kernel from a discrete set to minimize a linearizable objective (total latency) under a linear constraint (total area). Understanding binary decision variables, objective function, and constraints is key to grasping Stage 1’s automation.  
  *Quick check:* In the ILP formulation `min L_total(x) s.t. Σ Am_k * xm_k ≤ A_budget, Σ xm_k = 1 ∀k`, what does the constraint `Σ xm_k = 1` enforce? (Answer: Exactly one variant is chosen for each sub‑kernel.)
## Architecture Onboarding
**Component map:**  
Coordinator -> Optimizer Agents (parallel, one per sub‑kernel) -> ILP Solver -> Exploration Agents (parallel, N agents) -> Coordinator

**Critical path:**  
1. Coordinator extracts call graph from input code.  
2. Optimizer agents (in parallel) generate M=7 variants per sub‑kernel, perform functional tests, invoke Vitis HLS synthesis, and return (latency, area) for surviving variants.  
3. Coordinator builds ILP model using variant data and call‑graph latency composition *h(·)*, solves to obtain top‑N feasible variant sets.  
4. Exploration agents (in parallel) start from each top‑N set and iteratively propose design‑wide transformations, apply changes, check correctness, synthesize if area ≤ budget, and log results.  
5. Coordinator aggregates all valid designs and selects the one with minimal latency.  
Bottleneck: HLS synthesis per variant (minutes) causes agents to idle while waiting for feedback.

**Design tradeoffs:**  
- *Agents N vs. Token Cost:* More agents increase exploration breadth and Pareto front quality (up to saturation) but token usage grows linearly (median 5.82M tokens/run). Token budget versus quality trade‑off.  
- *Sub‑kernel M vs. Completeness:* Larger variant set *M* per sub‑kernel raises chance of finding a locally optimal variant but increases total Stage 1 synthesis cost. Paper uses fixed M=7 heuristically.  
- *ILP Top‑N vs. Stage 2 Coverage:* Larger *N* provides more diverse starting points but launches more expensive global agents; parameter tuned experimentally (1,2,4,8,10).

**Failure signatures:**  
- *High area, low speedup:* Agents over‑aggressively unroll/partition without respecting area budget, yielding infeasible designs or designs that fit but show no speedup (observed in simpler kernels like KMP, AES).  
- *Non‑monotonic scaling:* Best design may come from a lower‑rank ILP start; also N=10 may perform worse than N=4 if high‑area variants dominate later agents’ explorations.  
- *Stagnant agent:* An exploration agent repeatedly fails correctness checks or produces syntactically invalid code, contributing no valid designs; monitor per‑agent valid design count.

**First 3 experiments:**  
1. **Baseline Reproduction & ILP Sanity Check:** Run bounded exhaustive baseline (per‑loop pragma enumeration) on a small kernel (e.g., NW). Run Stage 1 only. Verify that the ILP‑selected design matches the best feasible combination from the exhaustive baseline within the variant set, confirming the correctness of the call‑graph‑based latency model *h(·)*.  
2. **Agent Scaling Curve:** For a complex kernel (e.g., streamcluster), run the full pipeline for N ∈ {1,2,4,8,10}. Plot best latency (speedup) vs. N and vs. total area. Expect monotonic (or at least non‑decreasing) improvement up to a point, validating Mechanism 2.  
3. **Origin of Best Design:** For each kernel, run full pipeline with N=10. Record which of the top‑N ILP starting solutions (*s_i*) produced the final best design. Anticipate varied ranks (often not rank 1), confirming Mechanism 3 that global optimization can start from suboptimal ILP candidates and improve them.
## Open Questions the Paper Calls Out
1. **Generalization across tools, architectures, and models:** How do the observed speedups hold when using different HLS tools (Intel HLS, Cadence Stratus), target architectures (ASIC, GPU), and LLM backbones (open‑source or other proprietary models)?  
2. **Comparison to specialized DSE frameworks:** How does the agent factory’s solution quality, exploration time, and required human expertise compare against state‑of‑the‑art automated DSE frameworks like AutoDSE?  
3. **Learning‑based efficiency improvements:** Can incorporating learning techniques (fine‑tuning, reinforcement learning) improve sample efficiency, reducing token consumption while maintaining or improving latency reductions?  
4. **Understanding ILP suboptimality:** What specific properties of the design space (call graph structure, memory access patterns, pragma interaction complexity) cause the ILP‑based candidate selection to rank suboptimal variants that Stage 2 agents later improve upon?
## Limitations
- Small benchmark set (12 kernels) limits diversity and statistical power.
- Evaluation restricted to a single LLM (Claude Code), HLS tool (Vitis), and FPGA target; generalizability uncertain.
- High token consumption (~5.8M tokens per run) and long synthesis latency hinder scalability.
## Confidence
- Mechanism 1 (sub‑kernel ILP selection): Medium  
- Mechanism 2 (agent scaling): Medium  
- Mechanism 3 (global cross‑function optimization): High
