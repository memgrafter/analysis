# TVCACHE: A Stateful Tool-Value Cache for Post-Training LLM Agents
## Quick Facts
- arXiv ID: 2602.10986
- Source URL: https://arxiv.org/abs/2602.10986
- Reference count: 40
- Primary result: Caches tool outputs in RL post‑training using a stateful tool call graph, achieving up to 70% hit rates and cutting median tool time by 6.9× without reward loss.

## Executive Summary
TVCACHE addresses a major inefficiency in RL post‑training of LLM agents: external tool calls (often seconds to minutes) leave GPUs idle. Because tool outputs depend on mutable sandbox state, naive key‑value caching fails. TVCACHE introduces a stateful cache structured as a tool call graph (TCG), where each node records a tool call, its result, and optionally a sandbox snapshot. On a tool call, the system performs longest‑prefix matching (LPM) against the TCG: an exact match returns the cached result instantly; a partial match forks the sandbox from the matched node and executes only the remaining suffix. Selective snapshotting (store only for expensive tools) and proactive sandbox forking with reference‑counted concurrency further reduce overhead. Evaluations on terminal‑bench, SkyRL‑SQL, and EgoSchema show hit rates up to 70%, median tool‑time speedups up to 6.92×, and no degradation in final reward. The server adds ~3 ms P95 latency and uses 1–2 GB memory.

## Method Summary
TVCACHE operates as a client‑server system. The server maintains the TCG, sandbox snapshots, and exposes HTTP endpoints (`/put`, `/get`, `/prefix_match`). The client library (`ToolCallExecutor`) intercepts each tool call during training and sends the preceding tool sequence to the server. The server computes the longest prefix present in the TCG. On an exact match, it returns the cached result; on a partial match, it returns the identifier of the best prefix node and whether a snapshot exists. The client then either returns the cached value or reconstructs the sandbox by forking from the snapshot (or from a clean state) and executes the suffix. The new node, with its result, is added back to the TCG. Snapshotting is selective: a snapshot is stored only if the tool’s execution time exceeds the measured serialization + restoration overhead. To hide reconstruction latency, the server proactively forks sandboxes for nodes with snapshots and spawns background threads for instantiation after a tool completes. Concurrency control via reference counting prevents eviction of in‑use sandboxes. The service is sharded by task ID to scale to many concurrent training workers.

## Key Results
- Up to 70% cache hit rates; median tool‑time speedup 6.9× across tasks.
- terminal‑bench: 14–25% hits, up to 6.92× speedup on medium tasks.
- SkyRL‑SQL: average 33% hits, average 2.9× speedup.
- EgoSchema: average 64.3% hits, 3× reduction in token usage (API‑based tools).
- Cache get latency ≤ 3 ms (P95) with sharding; memory footprint 1–2 GB.
- No loss in final reward compared to uncached training.

## Why This Works (Mechanism)
**Mechanism 1: Longest‑prefix matching guarantees correct state reuse.**  
TVCACHE organizes observed tool calls into a tree (the TCG). Each node corresponds to a tool invocation and stores the result and an optional sandbox snapshot. When a new tool call arrives, the system finds the longest prefix of the current tool sequence that appears in the TCG. If the prefix exactly matches a node, the cached result is returned directly, ensuring the sandbox state before the tool is identical to the one in the cache. If the prefix matches a node but additional tools remain, TVCACHE forks the sandbox from that node (using its snapshot if available) and executes only the suffix. This approach relies on the assumption that the sandbox state is fully determined by the ordered sequence of state‑modifying tool calls; read‑only tools can be ignored in prefix matching. *Break condition:* mis‑annotating tools as state‑modifying or ignoring state changes can cause false hits or unnecessary misses.

**Mechanism 2: Selective snapshotting balances memory and reconstruction speed.**  
Snapshots allow nearly instantaneous sandbox forking but consume storage and serialization time. TVCACHE stores a snapshot at a node only if the tool’s execution time exceeds the snapshot overhead measured on the host. This heuristic prioritizes expensive tools (e.g., compiling code, running tests) while avoiding snapshots for cheap operations like file reads. On a partial‑prefix cache miss, if the matched node has a snapshot, the sandbox can be forked quickly; otherwise the entire prefix must be replayed from a clean state, which is slower. *Break condition:* inaccurate snapshot overhead estimation or high variance in tool execution times may misclassify tools, leading to either wasted memory or slow reconstruction.

**Mechanism 3: Proactive forking and background instantiation hide latency.**  
To reduce the cost of waiting for a sandbox on a miss, TVCACHE pre‑creates multiple clean root sandboxes at startup and also forks copies from nodes that have snapshots, keeping them ready in the background. When a rollout later matches such a prefix, it can immediately acquire a pre‑forked sandbox. Additionally, after a tool call finishes and its node is snapshotted, the system offloads the forking of that sandbox to a background thread, so the snapshot becomes available for future reuse without blocking the current rollout. Reference counting ensures that sandboxes are not evicted while in use. *Break condition:* low prefix reuse leads to many idle pre‑forked sandboxes, wasting resources; background instantiation may compete for I/O or memory; excessive forking can exceed the configured sandbox budget.

## Foundational Learning
**Tool Call Statefulness**  
- **Why needed:** Naïve caching that maps a single tool call to a result fails because the same tool can produce different outputs depending on prior modifications to the sandbox (e.g., file edits). Understanding statefulness is essential to reason about when a cached result is valid.  
- **Quick check:** Consider two sequences: (1) `cat data.txt`, `echo "new" > data.txt`, `cat data.txt`; (2) `cat data.txt` alone. Can the second `cat` in (1) reuse the output from the first? Why or why not? How does TVCACHE decide that the sandbox states differ?

**Longest Prefix Matching in a Graph**  
- **Why needed:** The TCG stores sequences of tool calls. To reuse a result, the system must find the longest prefix of the current sequence that has been executed before, because any suffix beyond the matching point may depend on state modifications that differ.  
- **Quick check:** Suppose the TCG contains paths `[t1, t2, t3]` and `[t1, t4]`. A new rollout calls `[t1, t2, t4]`. What is the longest prefix match? What does TVCACHE do on a hit vs a miss? How does the answer change if `t4` is annotated as stateless?

**Selective Snapshotting**  
- **Why needed:** Snapshots enable fast sandbox forking but are expensive to store and create. The system must decide which nodes deserve a snapshot to keep overhead low while still gaining speed on cache misses.  
- **Quick check:** If a tool like `make -j8` takes 30 s and snapshotting takes 2 s, should TVCACHE snapshot after it? What about `ls` (0.01 s)? How might the policy fail if snapshotting overhead is underestimated or tool times are variable?

## Architecture Onboarding
**Component map**  
TVCACHE Server (HTTP API, sharded by task ID) <-- RPC --> Client Library (ToolCallExecutor); Client Library --> Sandbox Environment (Docker / filesystem / DB) with operations start, fork, execute; Background Forking Threads --> Sandbox Environment (pre‑warm snapshots); Sandbox Environment --> Persistent Storage (snapshot images); Concurrency via reference counting on sandboxes; eviction based on depth/children heuristics.

**Critical path**  
1. Client intercepts a tool call and appends its identifier to the current tool sequence.  
2. Client queries the server with the sequence via `/prefix_match` (or `/get` for exact).  
3. Server returns either a cache hit (cached result) or a miss (node ID of longest‑prefix match and snapshot availability).  
4. On hit: client returns cached result to the agent.  
5. On miss: client obtains a sandbox – either by forking from the matched node’s snapshot or starting a fresh sandbox – and executes the remaining suffix. The new node (with result) is sent to the server via `/put`.  
6. Client returns the final result to the agent; RL loop continues.

**Design tradeoffs**  
- **TCG vs hash table:** Hash table only supports exact lookups; TCG enables prefix matching and state reconstruction at O(log N) cost.  
- **Snapshot every node vs selective:** Full snapshotting gives instant forking but explodes memory; selective snapshotting uses a simple time‑threshold heuristic to balance overhead and reuse benefit.  
- **Proactive vs reactive forking:** Proactive reduces miss latency at the cost of extra memory and potential waste; reactive conserves resources but increases critical‑path delay.  
- **Sharding by task ID:** Provides near‑linear scalability but isolates tasks; cross‑task reuse is impossible due to differing sandbox states.

**Failure signatures**  
- **Low cache hit rate:** Check `will_mutate_state` annotations, TCG growth (successful `/put`), tool sequence diversity.  
- **High cache get latency:** Server saturation – add shards; network latency – co‑locate client/server; request batching.  
- **Memory blowout:** Too many snapshots – raise snapshot threshold, adjust eviction policy, verify reference counts.  
- **Cache inconsistency:** Sandbox `fork`/`execute` bugs – review logs, ensure snapshots are valid.  
- **Straggler rollouts despite high hit:** Expensive suffix execution – analyze distribution, consider caching suffix results.

**First 3 experiments**  
1. **Unit test: LPM correctness** Build a small TCG manually; query with prefixes including stateless tools; verify matching and forking behavior.  
2. **Microbenchmark: cache lookup latency and scaling** Populate server with 8 K TCG nodes; generate increasing RPS from simulated clients; measure P95 latency with 1, 2, 4, 8, 16 shards.  
3. **End‑to‑end: terminal‑bench easy task** Train Qwen3‑4B‑Instruct with and without TVCACHE; compare tool call times, rollout durations, hit rates, and reward curves.

## Open Questions the Paper Calls Out
1. **Fuzzy/semantic matching of tool trajectories** – How can TVCACHE extend beyond exact prefix matches to reuse results when trajectories are semantically similar but not identical? The paper suggests applying semantic caching techniques but leaves implementation and evaluation for future work. *What evidence would resolve:* A prototype that embeds tool call histories and validates correctness and hit‑rate gains on the three benchmarks.
2. **Scaling to many tools and long sequences** – The current evaluation uses modest tool sets. How does the TCG’s size, lookup latency, and memory usage grow when the number of distinct tools reaches hundreds and trajectories become very long? *What evidence would resolve:* Experiments on synthetic or additional benchmarks with hundreds of tools and long dependencies, measuring TCG growth and performance.
3. **Optimal snapshot policy** – The heuristic “snapshot if exec time > snapshot overhead” ignores factors like future reuse probability, node depth, and subtree branching. Could a cost‑benefit model improve memory‑speed trade‑offs? *What evidence would resolve:* Design and compare alternative policies in simulation and on real workloads, measuring overall tool‑time reduction and memory consumption.
4. **Impact on exploration diversity** – Caching reuses exact tool results; does this reduce the diversity of trajectories encountered during RL training, potentially harming long‑term policy quality even if immediate reward does not degrade? *What evidence would resolve:* Quantify trajectory diversity (e.g., entropy of tool sequences) with and without TVCACHE across training epochs, and correlate with final performance in extended training runs.
5. **Handling non‑deterministic tools** – Real‑world tools (e.g., LLM‑based APIs, web search) may produce stochastic or time‑varying outputs. TVCACHE assumes determinism given the sandbox state. How can correctness be maintained for such tools? *What evidence would resolve:* Extend TVCACHE with versioning, freshness timestamps, or checksum‑based invalidation; evaluate on workloads with non‑deterministic components.

## Limitations
- **Annotation dependency:** Correctness hinges on accurately marking tools as state‑modifying; errors cause false hits or missed reuse opportunities.  
- **Reproducibility gaps:** Missing details (RL hyperparameters, dataset splits, EgoSchema tool implementations, snapshot thresholds) hinder exact replication.  
- **Generalization scope:** Evaluations cover three domains with ≤ 10 tools; performance on richer, more complex agent environments remains unproven.

## Confidence
- Core correctness of longest‑prefix matching: Medium (depends on correct tool annotations).  
- Selective snapshotting heuristic: Medium (sensitive to timing measurements and tool variability).  
- Proactive forking strategy: Medium (benefits proportional to hit rate; over‑provisioning wastes resources).  
- Overall performance claims (speedup, hit rate, no reward loss): Medium (based on limited benchmarks; may not transfer to other settings).

## Next Checks
1. **Annotation sensitivity test** – Intentionally mislabel 10% of tools as stateful/stateless in a terminal‑bench run; measure hit rate and any reward degradation.  
2. **Snapshot threshold sweep** – Vary the condition for storing snapshots (e.g., exec time > 0.5×, 1×, 2× measured overhead) and plot speedup and memory to find a robust setting.  
3. **Proactive forking pool scaling** – Increase the number of pre‑forked sandboxes (e.g., from 1 to 32); record memory consumption, hit rate, and average miss latency to identify the optimal trade‑off.
