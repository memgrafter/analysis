# mlr3mbo: Bayesian Optimization in R
## Quick Facts
- arXiv ID: 2603.29730
- Source URL: https://arxiv.org/abs/2603.29730
- Reference count: 40
- Primary result: mlr3mbo achieves state-of-the-art performance on numeric HPO benchmarks (mean RSNS 1.19) and competitive results on mixed-hierarchical benchmarks (mean RSNS 0.82) relative to major frameworks.

## Executive Summary
mlr3mbo is a modular Bayesian optimization framework for R that supports single- and multi-objective optimization, mixed-hierarchical search spaces, parallelization, and robust error handling through composable building blocks (surrogate models, acquisition functions, optimizers). It integrates seamlessly with the mlr3 ecosystem for hyperparameter tuning and AutoML.

The authors derived robust default configurations via meta-optimization (coordinate descent) on the YAHPO Gym benchmark suite: for numeric spaces, a Gaussian process with Matérn3/2 kernel, LCB acquisition (λ=3), and CMA-ES optimizer; for mixed-hierarchical spaces, a 500-tree random forest with law-of-total-variance uncertainty estimation, LCB (λ=1), and local search. Benchmarks against Ax, HEBO, SMAC3, and Optuna show state-of-the-art performance on numeric instances and competitive results on mixed-hierarchical instances, with favorable runtime characteristics.

## Method Summary
The study evaluates mlr3mbo by comparing it against four popular Bayesian optimization frameworks (Ax, HEBO, SMAC3, Optuna) on the YAHPO-SO v1 hyperparameter optimization benchmark suite. Experiments use a fixed evaluation budget of ⌈20+40√d⌉ per run across numeric and mixed-hierarchical search spaces. Performance is measured by Random Search Normalized Score (RSNS) averaged over 30 independent runs, and wall-clock runtime is recorded. The default mlr3mbo configuration—derived via greedy coordinate descent—was: GP+Matérn3/2+LCB(λ=3)+CMA-ES for numeric; 500-tree RF+LTV+LCB(λ=1)+local search for mixed. Competitors use their default settings.

The reproduction package is archived on Zenodo (DOI 10.5281/zenodo.18223637) and includes all code, configuration files, and environment specifications (R ≥4.0, Python ≥3.8 plus required packages). To reproduce, install dependencies (e.g., via renv for R), install the yahpo Gym, and execute the provided benchmark scripts. Unknowns that may affect replication include exact versions of competitor frameworks and their transitive dependencies, as well as the cluster environment (OS, hardware, filesystem). Common failure modes involve package/version conflicts, insufficient computational resources for the many repetitions, and surrogate or acquisition errors that trigger fallback behaviors.

## Key Results
- Robust default configurations: for numeric spaces (GP+Matérn3/2, LCB λ=3, CMA-ES) mean RSNS = 1.19; for mixed-hierarchical spaces (500-tree RF with LTV, LCB λ=1, local search) mean RSNS = 0.82.
- mlr3mbo outperforms Ax, HEBO, SMAC3, and Optuna on numeric benchmark instances and remains competitive on mixed-hierarchical problems.
- The framework exhibits favorable runtime characteristics compared to the competitors, particularly on mixed-hierarchical search spaces.

## Why This Works (Mechanism)
### Mechanism 1: Iterative Surrogate-Acquisition Loop
Bayesian optimization in mlr3mbo operates through an iterative loop that alternates between fitting a probabilistic surrogate model to observed evaluations and optimizing an acquisition function derived from that surrogate to propose new evaluation points. The core procedure (Section 2) is: (1) sample an initial design; (2) fit or update the surrogate; (3) compute the acquisition function (e.g., Expected Improvement, Lower Confidence Bound) using the surrogate’s mean and uncertainty; (4) optimize the acquisition function to obtain one or more candidate points; (5) evaluate the black-box objective; (6) repeat until a termination condition (e.g., evaluation budget or runtime limit) is met. This loop replaces expensive direct optimization with cheap acquisition optimization, relying on the assumption that the black-box function is costly to evaluate, no gradients are available, and a limited evaluation budget exists. The surrogate’s uncertainty quantification is crucial for balancing exploration and exploitation. Evidence for this mechanism is found in the abstract, Section 2, and the broader corpus. If errors occur during surrogate fitting or acquisition optimization, the system falls back to random sampling, ensuring robustness.

### Mechanism 2: Modular Building-Block Architecture
The effectiveness of mlr3mbo stems from its highly modular design, where users can compose custom BO algorithms by combining interchangeable components—surrogate models, acquisition functions, and optimizers—through R6 objects and dictionaries. Key classes (e.g., SurrogateLearner, AcqFunction, AcqOptimizer) are stored in dictionaries (`mlr_learners`, `mlr_acqfunctions`, `mlr_acqopt`). The central `OptimizerMbo` assembles these building blocks, enabling users to swap, for example, a Gaussian process for a random forest or Expected Improvement for LCB without modifying the core loop (Section 3). This architecture assumes that different BO variants can be expressed as orthogonal design choices, and decoupling them increases flexibility, reproducibility, and ease of experimentation. The abstract explicitly mentions that researchers can construct custom BO algorithms from its flexible building blocks, and Section 3 details the implementation. The modular pattern is recognized in the broader BO literature, with neighboring packages like NUBO adopting similar approaches. Failures due to incompatible choices are caught by validation checks and may trigger fallbacks.

### Mechanism 3: Meta-Optimization via Coordinate Descent for Defaults
Robust default configurations for numeric and mixed-hierarchical search spaces were obtained by meta-optimizing mlr3mbo’s own hyperparameters using a greedy coordinate descent (CD) on the YAHPO Gym benchmark suite. The configuration space includes choices for surrogate type and hyperparameters, acquisition function parameters (e.g., λ for LCB), and acquisition optimizer. For each parameter, CD exhaustively tests all possible values while holding others fixed and accepts a change if it improves the average Random Search Normalized Score (RSNS) over 30 runs per instance. This yields, for numeric spaces, a Gaussian process with Matérn3/2 kernel, LCB (λ=3), and CMA-ES optimizer (mean RSNS 1.19); for mixed-hierarchical spaces, a 500-tree random forest with law-of-total-variance uncertainty estimation, LCB (λ=1), and local search (mean RSNS 0.82) (Section 8). The approach assumes that a single configuration can perform robustly across diverse HPO instances and that RSNS is a meaningful instance-agnostic metric. Evidence comes from the abstract and Section 8, which describe the CD procedure and report the final configurations and performance. However, CD may miss interactions among parameters and risks overfitting to the benchmark suite, as acknowledged in the limitations.

## Architecture Onboarding
### Component Map
bbotk: Objective -> OptimInstance. mlr3mbo: Surrogate (srlrn) + AcqFunction (acqf) + AcqOptimizer (acqo) -> OptimizerMbo (opt('mbo')) -> optimize(instance). Integration: TunerMbo (tnr('mbo')) wraps OptimizerMbo for mlr3tuning; as_learner() converts graph pipelines into tunable AutoML systems. Dependencies: mlr3 ecosystem (lrn()), paradox (ps(), p_dbl(), p_fct()).

### Critical Path
1. Define problem: Create Objective (e.g., ObjectiveRFun$new(f, domain, codomain)).
2. Create instance: oi(objective, search_space, terminator).
3. Set initial design: Generate via generate_design_*() and instance$eval_batch().
4. Configure BO: Either (a) use opt("mbo") with defaults (auto-detects mixed/hierarchical → RF), or (b) manually construct surrogate, acq_function, acq_optimizer and pass to optimizer = opt("mbo", ...).
5. Run: optimizer$optimize(instance).
6. (HPO) Wrap: Use ti() for tuning tasks and tnr("mbo")$optimize(tuning_instance).

### Design Tradeoffs
- **Defaults vs. customization**: opt("mbo") provides robust defaults per search space type; manual configuration is for research or special cases.
- **Surrogate choice**: GP (Matérn kernel, log output transformation) best for low-dimensional numeric spaces; RF (500 trees, LTV estimator) for mixed-hierarchical spaces. GP more accurate but cubic scaling; RF scales better.
- **Acquisition optimizer**: CMA-ES for numeric spaces; Local Search for mixed-hierarchical (Table 14,15 ablations). Gradient-based (L-BFGS-B) tends to underperform without advanced gradient estimation (as in Ax’s autodiff).
- **Error handling**: catch_errors = TRUE (default) falls back to a random forest if surrogate modeling fails; random interleaving (random_interleave_iter) prevents getting stuck but reduces sample efficiency.
- **Parallelization**: Batch bayesopt_mpcl vs. asynchronous OptimizerAsyncMbo. Asynchronous better for heterogeneous runtimes but requires a rush shared database.

### Failure Signatures
- **SM fitting errors**: Often due to near-duplicate points or numerical issues in GP. Default fallback: switch to a random forest with 10 trees; inspect surrogate$learner_model for warnings.
- **Acquisition optimization failures**: Occur if surrogate predictions are unstable (e.g., RF with too few trees). acq_optimizer$catch_errors = TRUE (default) falls back to random sampling.
- **Mixed space violations**: Local search must respect hierarchical dependencies; mis-specified depends in ps() can yield invalid proposals. Validate search space with paradox::check_ps().
- **Runtime blowup**: High-dimensional spaces increase acq_optimizer budget (default 100*d²). Monitor instance$archive size; consider reducing maxeval in acqo().

### First 3 Experiments
1. **Simple numeric BO**: Run the sinusoidal example from Section 3 verbatim. Verify the final point is near the global minimum (~0.79). Inspect instance$archive$data to see the convergence trajectory.
2. **Change surrogate & acquisition**: Replace the default GP with a random forest (lrn("regr.ranger", num.trees = 100)) and switch LCB to Expected Improvement. Compare resulting best value and convergence curve; expect worse performance on numeric (per Table 14).
3. **Mixed-hierarchical test**: Use the AutoML pipeline example from Section 6. Confirm that when branch.selection == "svm", only svm.cost and svm.gamma are active. Check that termination respects the budget and the final branch.selection is non-NA. Monitor whether BO proposes invalid configurations (it should not if dependencies are correctly specified).

## Open Questions the Paper Calls Out
- Does mlr3mbo maintain performance on real, noisy HPO tasks (with cross-validation) rather than deterministic surrogate benchmarks? The paper notes further work on real problems is needed.
- How does mlr3mbo perform in parallel and asynchronous settings? The study focused exclusively on sequential BO; parallel features exist but were not evaluated.
- Are the default configurations overfitted to the YAHPO Gym benchmark suite? The coordinate descent and comparison were done on the same instances, risking overfitting.
- Can the configuration be improved via joint optimization instead of coordinate descent? CD may miss parameter interactions; a joint meta-optimization could yield better defaults.

## Limitations
- Meta-optimization via coordinate descent risks overfitting to the YAHPO benchmark suite and may miss important interactions among BO components.
- Performance claims rely solely on YAHPO benchmarks; generalizability to other benchmark suites (e.g., HPOBench, BBOB) or real-world AutoML tasks remains unverified.
- Reproduction details for competitor frameworks (exact versions, system environment) are under-specified, potentially affecting runtime and performance comparisons.

## Confidence
- Core BO loop and modular architecture: High
- Default configurations and SOTA claims on YAHPO: Medium
- Universal robustness across all problem types: Low

## Next Checks
1. **Cross-benchmark validation**: Test the default configurations on additional benchmark suites (e.g., BBOB for numeric, HPOBench for mixed) to evaluate robustness beyond YAHPO.
2. **Controlled replication**: Pin exact versions of all frameworks (mlr3mbo, Ax, HEBO, SMAC3, Optuna) and run on identical hardware to isolate environment effects on runtime and performance.
3. **Scalability stress test**: Increase problem dimensionality (e.g., >100 parameters) and evaluation budget to determine whether the defaults remain effective or require adaptation.
