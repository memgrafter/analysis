# ReFuGe: Feature Generation for Prediction Tasks on Relational Databases with LLM Agents

## Quick Facts
- **ArXiv ID:** 2601.17735
- **Source URL:** https://arxiv.org/abs/2601.17735
- **Reference count:** 20
- **Primary result:** ReFuGe achieves superior predictive performance on relational databases, ranking best on average (1.3) versus the next-best method (4.2) in AUROC across seven benchmark datasets and eleven tasks.

## Executive Summary
ReFuGe introduces an LLM-agent framework for automatic feature generation from relational databases (RDBs) to enhance prediction tasks. It employs three specialized agents in an iterative loop: schema selection narrows the relevant tables and columns, feature generation produces candidate features with diversity via multiple LLM instances, and a two-stage filtering (reasoning plus validation) retains only those features that empirically improve validation performance. Validation feedback is fed back to guide subsequent iterations. Evaluated on seven benchmark datasets covering eleven tasks, ReFuGe attains state-of-the-art AUROC, achieving an average rank of 1.3 compared to 4.2 for the next-best method. Ablation studies confirm that both filtering stages and the iterative feedback are critical; performance consistently improves over iterations and benefits from increased LLM instance diversity.

## Method Summary
ReFuGe addresses the combinatorial challenge of relational feature engineering through an iterative agentic pipeline. Given an RDB schema (including PK-FK relationships), a target table, and a task description, the **schema selection agent** uses LLM reasoning to pick a focused subset of tables and columns most likely to yield predictive features, thereby pruning the search space. The **feature generation agent** then runs multiple LLM instances (with temperature > 0) to independently propose candidate features—expressed as SQL-like expressions or natural language descriptions—from the selected schema, encouraging semantic diversity. Candidates undergo two-stage filtering: first, a **reasoning-based filter** screens out implausible features using the LLM’s semantic knowledge; second, a **validation module** temporarily joins each feature to the target table, trains a LightGBM model on a sampled training subset, and computes the change in validation AUROC. Features that yield positive improvement are retained. The validation outcomes are formatted into a textual summary by a **feedback generator** and provided to all agents in the next iteration. The loop controlled by a **loop controller** continues until no new features pass validation or a maximum iteration limit is reached, finally outputting the enriched target table with appended feature columns.

## Key Results
- Outperforms all baselines on seven benchmark datasets (eleven tasks), achieving an average rank of 1.3 vs. 4.2 for the next-best method in AUROC.
- Ablations demonstrate that removing either the reasoning filter (ReFuGe-FF) or the feedback loop (ReFuGe-FB) leads to major performance drops, confirming their essential contributions.
- Performance improves with more iterations and with increased feature diversity (more LLM instances), though diminishing returns are observed beyond three instances.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Schema selection reduces the combinatorial search space by identifying only the relevant relational context for the prediction task.
- **Mechanism:** The schema selection agent processes the full RDB schema (tables, columns, PK-FK relationships) and the task description. Using LLM reasoning, it ranks and selects a subset of tables/columns most likely to contain predictive signals, discarding irrelevant parts of the database.
- **Core assumption:** Not all relational information is equally useful; a meaningful subset exists that focuses the search.
- **Evidence anchors:**
  - [abstract]: "a schema selection agent identifies the tables and columns relevant to the task"
  - [section 3.1]: "identifies the subset of tables and columns... This step effectively reduces the search space"
  - [corpus]: Weak direct evidence; neighboring papers ([243743], [103145]) discuss RDB-to-graph modeling challenges but do not address schema selection for feature generation.
- **Break condition:** If the selected schema omits critical tables/columns containing the true predictive signal, subsequent feature generation will be ineffective regardless of quality.

### Mechanism 2
- **Claim:** Feature generation agent diversity produces a wide pool of candidate relational features, increasing the chance of including informative ones.
- **Mechanism:** Multiple LLM instances (with temperature >0) independently generate candidate features from the selected schema. Their outputs are aggregated, introducing semantic diversity in the feature proposals (e.g., different aggregations, joins, or transformations).
- **Core assumption:** Different LLM reasoning traces will propose distinct, potentially complementary features from the same schema.
- **Evidence anchors:**
  - [abstract]: "To encourage diversity... the agent employs multiple LLM instances"
  - [section 3.2]: "To encourage diversity in the generated features, the agent employs multiple LLM instances"
  - [section 4.2 RQ5]: "using more LLM instances... tends to improve performance"
  - [corpus]: No direct evidence; corpus focuses on relational foundation models ([100116], [264565]) not feature generation diversity.
- **Break condition:** If diversity leads to predominantly redundant or low-quality features, the increased pool size only adds noise without improving the chance of finding good features.

### Mechanism 3
- **Claim:** The two-stage filtering (reasoning + validation) combined with iterative feedback progressively refines feature quality by leveraging both semantic screening and empirical utility signals.
- **Mechanism:** Reasoning-based filtering (Step 3.1) uses LLM semantic understanding to prune obviously poor candidates. Validation-based filtering (Step 3.2) trains a model on a sample to empirically measure each feature's impact on validation performance. Feedback summarizing "feature X changed AUROC by Y" is fed back to all agents in the next iteration, guiding them toward promising directions.
- **Core assumption:** Features can be effectively screened by semantic reasoning and that small-sample validation performance is a noisy but useful proxy for true feature utility, with feedback enabling self-correction.
- **Evidence anchors:**
  - [abstract]: "evaluates and retains promising features through reasoning-based and validation-based filtering"
  - [section 3.3]: "reasoning-based filtering narrows... validation-based filtering evaluates the empirical utility"
  - [section 4.2 RQ2]: Ablation shows ReFuGe-FF (random filtering) and ReFuGe-FB (no feedback) cause major performance drops.
  - [section 4.2 RQ3]: Performance generally improves over iterations.
  - [corpus]: No direct evidence; corpus includes general RDL papers ([7], [8]) but none on iterative LLM-based feature generation with validation feedback.
- **Break condition:** If validation scores are too noisy (due to small sample size or unstable models) to provide a clear signal, or if the LLM's reasoning in Step 3.1 is consistently misaligned with true utility, the loop may discard good features or retain poor ones, stalling improvement.

## Foundational Learning
**Concept: Relational Database Schema Reasoning**  
- *Why needed here:* Agents must understand PK-FK relationships, table purposes, and data types to select relevant tables (Step 1) and generate valid relational features (Step 2).  
- *Quick check question:* Given a schema with `Orders(order_id, customer_id)`, `Customers(customer_id, signup_date)`, `OrderItems(order_id, product_id)`, which tables/columns would be relevant for predicting `order_total`?

**Concept: Tabular Feature Engineering Semantics**  
- *Why needed here:* Feature generation (Step 2) requires knowing which operations (e.g., count, average, recent, distinct) on which grouped/joined entities are likely predictive for a classification task.  
- *Quick check question:* For predicting user churn, what is the semantic difference between a feature capturing "average transaction amount in last 7 days" versus "count of distinct product categories purchased"?

**Concept: LLM Agent Orchestration & Iterative Refinement**  
- *Why needed here:* The system is not a single LLM prompt but a coordinated loop where agents specialize, and past empirical results (validation scores) are distilled into textual feedback to guide future generations.  
- *Quick check question:* How does the feedback string "Feature 'X' increased AUROC from 0.65 to 0.67" functionally differ from just seeing that AUROC improved, in terms of guiding the next generation round?

## Architecture Onboarding
### Component map
- **Input:** RDB schema dump + statistical summaries + task description.
- **Schema Selection Agent:** LLM call → outputs selected table/column list.
- **Feature Generation Agent:** Multiple parallel LLM calls (N instances) → candidate feature list (SQL-like expressions or natural language descriptions).
- **Feature Filtering Agent (Stage 1):** LLM call → shortlisted features based on reasoning.
- **Validation Module:** Python script that (a) temporarily appends a candidate feature to target table via a SQL join/aggregation, (b) trains a LightGBM on a training sample, (c) computes validation AUROC.
- **Feature Filtering Agent (Stage 2):** Logic that retains features with positive validation delta.
- **Feedback Generator:** Formats validation results into natural language summary for next iteration.
- **Loop Controller:** Iterates until no features pass Stage 2 or max iterations.
- **Output:** Enriched target table with appended feature columns.

### Critical path
Schema Selection → (for each of M feature gen instances) Feature Generation → Aggregation → Reasoning Filter → (for each shortlisted feature) Validation → Validation Filter → (if any retained) Feedback Generation → back to Schema Selection (next iteration). The loop terminates when the validation filter retains zero new features.

### Design tradeoffs
- **Diversity vs. Noise:** More LLM instances (M) increase candidate diversity but also increase computational cost and noise in the pool. The paper finds diminishing returns, fixing M=3.
- **Validation Sample Size vs. Speed/Accuracy:** Using a subset of training data for validation speeds up iterations but introduces noise that may mislead filtering. Tradeoff is explicit.
- **Feedback Verbosity vs. Context Length:** Feedback strings summarizing many features can consume significant LLM context window, potentially crowding out schema information in later iterations.

### Failure signatures
- **Schema Misselection:** Early iterations show near-zero AUROC gain; selected schema consistently omits key tables (e.g., ignoring `Transactions` for a `CustomerChurn` task). Diagnose by inspecting agent outputs.
- **Validation Noise Stalling:** AUROC fluctuates randomly across iterations without clear trend; many features with small positive/negative deltas. Indicates sample size too small or model unstable.
- **Reasoning Filter Override:** Stage 1 filter consistently removes features that Stage 2 validation later finds useful. Suggests the LLM's semantic screening is misaligned; may need prompt engineering or few-shot examples.
- **Feedback Misleading:** Performance degrades after a few iterations. Could be because feedback emphasizes short-term validation spikes on small samples that don't generalize.

## Open Questions the Paper Calls Out
**Open Question 1:** Can ReFuGe handle non-classification tasks like regression or link prediction? The paper's future work mentions extending to regression and link prediction, but evaluation so far is limited to binary classification (AUROC). Feasibility for other task types and metrics remains unknown. What evidence would resolve it: Evaluate ReFuGe on standard regression and link prediction benchmarks with appropriate metrics.

**Open Question 2:** How does ReFuGe's performance and cost scale with schema size? The feature space is "combinatorially large" but experiments are limited to ≤7 tables. Real databases can have hundreds of tables; scalability of the iterative loop and feature quality is unclear. What evidence would resolve it: Test on synthetic/real DBs with varying table counts, measure runtime, memory, and AUROC changes.

**Open Question 3:** How sensitive is ReFuGe to the choice of LLM backbone? The authors do not report which LLM they used, nor do they compare different models or assign distinct models to agents. LLM capabilities vary; results may depend on a specific high-cost model. What evidence would resolve it: Run identical ReFuGe pipelines with multiple open-source and closed-source LLMs, compare performance and cost.

**Open Question 4:** Does the iterative validation-based feature selection overfit the validation set? Features are selected based on validation AUROC improvement across iterations, repeatedly using the same validation split. This could tailor features to that specific validation partition, inflating scores; no separate hold-out during iterations is mentioned. What evidence would resolve it: Use nested cross-validation or a strictly held-out test set untouched during feature selection to compare generalization gap.

## Limitations
- LLM model selection, inference parameters (temperature, max tokens), and exact validation sample size are unspecified, hindering reproducibility and obscuring sources of noise.
- Evaluation is confined to seven relatively small benchmark datasets, leaving uncertain how ReFuGe generalizes to larger, noisier, or domain-specific relational databases with hundreds of tables.
- The design of the feedback mechanism (format, verbosity) and its precise influence on agent behavior lack systematic ablation, limiting understanding of optimal configuration.

## Confidence
- **High:** Core performance claims (AUROC superiority, average rank) are strongly supported by benchmark results and ablations.
- **Medium:** Proposed mechanisms (schema selection, diversity, iterative feedback) are plausible and partially validated by ablations (e.g., ReFuGe-FB drop) but lack direct causal isolation.
- **Low:** Claims about broad scalability and robustness across diverse real-world RDB schemas and tasks; limited dataset diversity and potential overfitting to benchmark structures.
