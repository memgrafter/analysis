# Dual-Phase LLM Reasoning: Self-Evolved Mathematical Frameworks

## Quick Facts
- **ArXiv ID:** 2601.05616  
- **Source URL:** https://arxiv.org/abs/2601.05616  
- **Reference count:** 6  
- **Primary result:** A two-stage SFT pipeline with self-generated multi-turn CoT and difficulty-aware rejection sampling yields reasoning chains >4× longer and improves AIME24 accuracy from 6.70% to 16.70% on Qwen2.5-7B-Instruct.

## Executive Summary
This paper proposes a compute-efficient alternative to reinforcement learning for enhancing LLM mathematical reasoning. It introduces a dual-phase supervised fine-tuning (SFT) framework where the model first generates its own multi-turn dialogue reasoning data (including verification and backtracking), which is filtered and used for initial fine-tuning. A second stage applies difficulty-aware rejection sampling to refine the data distribution, producing a final model that achieves significant gains on challenging benchmarks like AIME24 while maintaining output conciseness through learned marker-based control. The approach demonstrates that carefully curated self-generated data can effectively activate a model's intrinsic reasoning capabilities without the overhead of RL.

## Method Summary
The method consists of two supervised stages using the Qwen2.5-7B-Instruct base model and the DeepScaleR dataset. **Stage 1** generates multi-turn dialogue data (Problem → Answer1 → Evaluation → Answer2 → Summary) via the base model. Generated chains are classified into four correctness categories (e.g., False-to-True corrections) and filtered to create a balanced dataset `D_multi` (prioritizing False-to-True, with a 1:1 ratio of correct to incorrect initial answers). The base model is fine-tuned on `D_multi` to obtain `π_sft`. **Stage 2** performs difficulty-aware rejection sampling on `π_sft`: problems are sampled with increasing attempt counts (starting with n₁=2) if no correct response is found, building a rejection dataset `D_rej` of medium-length correct chains. `D_multi` and `D_rej` are merged with appended test-time markers (e.g., `\n\nUsing the solution style from multi-turns data.`). `π_sft` is fine-tuned on this merged set to produce the final model. At inference, markers can be appended to steer behavior.

## Key Results
- Reasoning chain length increases by over 4× compared to base model outputs.
- AIME24 accuracy improves from 6.70% to 16.70%; MATH500 from 74.20% to 76.00%.
- Final outputs remain concise or become more concise despite longer training chains, due to Stage 2 refinement.
- Marker injection at test time allows controlled specialization: multi-turn marker benefits AMC23, rejection marker benefits MATH500.

## Why This Works (Mechanism)
The dual-phase design separates **reasoning structure acquisition** from **efficiency refinement**. Stage 1’s multi-turn dialogues expose the model to explicit verification and backtracking patterns, teaching it to generate long, iterative CoTs. The balanced filtering prevents reward hacking from ubiquitous incorrect initial attempts. Stage 2’s rejection sampling selectively amplifies correct reasoning on harder problems (identified by zero success in early trials), while the merged training with markers teaches the model to modulate output style at test time—producing long chains when needed but compressing final answers. This avoids the instability and high compute of RL by using SFT on a curated, self-evolved curriculum.

## Foundational Learning
- **Self-synthesized data generation:** Model creates its own training examples via multi-turn prompting. *Why needed:* Avoids manual annotation and tailors data to model’s capability gaps. *Quick check:* Verify `D_multi` contains diverse problem types and the four correctness categories.
- **Difficulty-aware sampling:** Problems unsolved in initial low-trial rounds receive more sampling attempts. *Why needed:* Efficiently allocates compute to hard problems without manual difficulty labels. *Quick check:* Plot acceptance rate vs. number of sampling rounds; harder problems should require more rounds.
- **Marker-based test-time control:** Appended tokens at inference trigger different reasoning policies. *Why needed:* Decouples chain length from final answer conciseness, allowing post-training steering. *Quick check:* Compare token counts and accuracy with/without markers on a held-out set.
- **Balanced rejection filtering:** Maintaining a 1:1 ratio of correct/incorrect first answers in `D_multi`. *Why needed:* Prevents trivial solutions where model only learns to fake corrections from wrong starts. *Quick check:* Sample `D_multi` and confirm initial answer correctness distribution.

## Architecture Onboarding
**Component map:**  
Base Model (Qwen2.5-7B-Instruct) -> Stage1 Data Synthesis (multi-turn dialogue generator) -> Filtered `D_multi` -> `π_sft` (Stage1 fine-tuned model) -> Stage2 Rejection Sampling (iterative filter, n₁=2, n₂=10, …) -> `D_rej` -> Merged `D_multi`+`D_rej` with markers -> `π_final` (Stage2 fine-tuned model).

**Critical path:**  
1. Generate `D_multi` from base model.  
2. Fine-tune base on `D_multi` → `π_sft`.  
3. Run rejection sampling on `π_sft` to build `D_rej`.  
4. Merge `D_multi` and `D_rej` with markers.  
5. Fine-tune `π_sft` on merged set → `π_final`.

**Design tradeoffs:**  
- *Data balancing vs. reward hacking:* Prioritizing False-to-True corrections risks models learning artificial correction patterns. Mitigated by strict 1:1 ratio.  
- *Marker simplicity vs. expressiveness:* Single-token markers are lightweight but may only trigger shallow decoding heuristics rather than distinct reasoning policies.  
- *Rejection sampling cost vs. coverage:* Iterative sampling on unsolved problems increases compute but focuses on model’s true weak points.

**Failure signatures:**  
- `D_multi` shows skewed Answer1 correctness (e.g., >80% correct) → reward hacking.  
- Rejection sampling acceptance rate plateaus early → filter too lenient or sampling budget insufficient.  
- Marker injection degrades performance on one benchmark while helping another → marker semantics not learned, causing distribution shift.

**First three experiments to run:**  
1. Generate `D_multi` from base model; measure category distribution and Answer1 correctness ratio. Adjust filter if ratio deviates from 1:1.  
2. Implement rejection sampling; track acceptance rate after each iteration (n₁, n₂, …). Verify unsolved problems receive progressively more attempts.  
3. Evaluate `π_final` on AIME24 and MATH500 with and without markers; compare token counts to paper’s reported length increase.

## Open Questions the Paper Calls Out
**Open Question 1:** Does the two-turn constraint in the multi-turn synthesis phase fundamentally limit the model's ability to learn deep, multi-step reasoning patterns required for competition-level problems like AIME24?  
*Basis:* Limitations section notes two-turn inadequacy for deep reasoning. Gains on AIME24 are attributed to overall framework.  
*Resolution evidence:* Ablate with 3–4 turn generations; compare AIME24 accuracy, coherence, stability.

**Open Question 2:** What causes the non-monotonic relationship between training data volume and response length (peak at 1k samples then decline)?  
*Basis:* Table 5 shows token count spike from 0.5k to 1k then drop despite accuracy rise.  
*Resolution evidence:* Analyze generation content (redundancy, backtracking) and training dynamics (loss curves) at each data size.

**Open Question 3:** Is the zero-correct proxy for difficulty in rejection sampling optimal compared to other metrics?  
*Basis:* Uses binary filter (“zero correct responses”) and notes need for adaptive metrics.  
*Resolution evidence:* Replace with alternative estimators (solution length, concept entropy); evaluate on hard subsets; correlate with human-rated difficulty.

**Open Question 4:** Why do multi-turn and rejection markers induce divergent test-time behaviors, and do they learn distinct reasoning strategies?  
*Basis:* Multi-turn marker better for AMC23 (interactive), rejection for MATH500 (proofs). Complementary strengths noted but mechanism unclear.  
*Resolution evidence:* Analyze trace structures (verification steps, backtracking) and internal representations (probing for marker-specific clustering).

**Open Question 5:** How does compute-efficiency of this SFT approach compare to RL-based methods (e.g., DeepSeek-R1) when normalizing for total training and inference compute?  
*Basis:* Claims SFT is compute-efficient but RL baseline achieves higher accuracy with much longer responses (19k vs 4k tokens). Trade-off unquantified.  
*Resolution evidence:* Estimate FLOPs for SFT training, RL training on same base, and inference cost per benchmark; compare cost-normalized accuracy.

## Limitations
- Missing critical reproduction details: exact prompt templates, hyperparameters, DeepScaleR preprocessing rules, and marker strings; all referenced in omitted appendices.
- Evaluation limited to Qwen2.5-7B; scalability to larger models or other architectures not established.
- No direct replication of RL baseline for fair compute-efficiency comparison; claims rely on external result contrasts.

## Confidence
- **Dual-phase SFT improves reasoning:** Medium (idea sound, but replication hindered by missing details).
- **SFT vs. RL efficiency:** Low (no RL baseline reproduced; inference cost of long chains not fully accounted).
- **Self-generated data activates reasoning:** Medium (depends on fidelity of data pipeline; category balancing critical).
