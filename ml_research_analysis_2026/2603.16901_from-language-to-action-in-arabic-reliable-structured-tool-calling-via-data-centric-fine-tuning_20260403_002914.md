# From Language to Action in Arabic: Reliable Structured Tool Calling via Data-Centric Fine-Tuning

## Quick Facts
- **arXiv ID:** 2603.16901
- **Source URL:** https://arxiv.org/abs/2603.16901
- **Reference count:** 32
- **Primary result:** Parse failures reduced from 87% to below 1%; function name accuracy increased over eightfold across five Arabic dialects and eight domains.

## Executive Summary
This paper tackles the critical problem of structural instability in Arabic function-calling for agentic AI systems. Existing models suffer from high parse failures and poor tool selection. The authors introduce a data-centric fine-tuning framework applied to the 270M-parameter FunctionGemma model. Key innovations include systematic dataset auditing, schema repair (enum normalization, tool pruning), tool-aware prompt sampling to prevent truncation, and full-parameter supervised fine-tuning with completion-only masking. On a held-out test set, the method reduces parse failures from 87% to under 1% and boosts function name accuracy by more than eight times. Error analysis reveals a shift from structural collapse to semantic misalignment, demonstrating that serialization stability and decision-level reasoning can be separated. The approach achieves near-perfect format validity and robust performance across dialects, offering a production-ready solution for reliable Arabic tool invocation.

## Method Summary
The work employs a dataset-centric pipeline to stabilize Arabic function-calling. First, the AISA-AR-FunctionCall dataset undergoes structural auditing to identify empty queries, enum violations, and duplicate tools. Schema repair includes fixing enum handling to allow None values, normalizing enum surface variants to canonical forms, and pruning unstable or overlapping tools (reducing tools from 36 to 27). Second, tool-aware prompt sampling selects exactly five tools per sample (the correct tool plus four distractors), cutting median prompt length from ~4900 to ~793 tokens and avoiding truncation within the 2048-token context. Third, the FunctionGemma model is fine-tuned using full-parameter supervised training with completion-only masking, focusing loss only on the assistant’s function-call tokens. Training uses BF16 precision, an 8-bit AdamW optimizer, a cosine learning rate schedule (peak 2e-5), gradient checkpointing, and runs for two epochs with an effective batch size of 32. The provided train/val/test splits (41,104/4,568/5,079 samples) are used without leakage.

## Key Results
- Parse failures dropped from 87% to below 1% on the held-out test set.
- Function name accuracy increased by a factor of eight compared to baseline.
- Substantial improvements in argument alignment across five Arabic dialects and eight domains, with near-perfect format validity.

## Why This Works (Mechanism)
Three key mechanisms underlie the success:

**1. Systematic dataset auditing and schema repair**  
*Claim:* Eliminating inconsistencies in the dataset ensures valid supervision signals, preventing structural collapse.  
*Mechanism:* Enum compliance correction (allowing None values) restores thousands of samples and reactivates dead tools. Enum normalization aligns surface variants (Arabic/English spellings) to canonical values, reducing label noise. Tool pruning removes unstable/overlapping tools, decreasing schema variability.  
*Evidence:* Repair re-activated six tools that had zero valid samples after the None-is-valid fix (Section 3.2) and parse failures dropped dramatically (Table 2).  
*Break condition:* If parse failure remained >50% after repair, the dataset-inconsistency hypothesis would be falsified.

**2. Stochastic tool sampling**  
*Claim:* Selecting a fixed number of tools per sample prevents prompt truncation and provides implicit data augmentation.  
*Mechanism:* Each training example includes exactly five tools (the correct one plus four distractors). This reduces median prompt length from ~4900 to ~793 tokens, fitting within the 2048-token window. Random distractor selection across epochs exposes the model to diverse negative contexts, enhancing discrimination.  
*Evidence:* Token reduction confirmed (Section 3.3); training converged more stably compared to untruncated baselines.  
*Break condition:* If truncation was not observed or performance did not improve with sampling, its necessity would be undermined.

**3. Full-parameter fine-tuning with completion-only masking**  
*Claim:* Updating all model parameters while focusing loss on the structured output fully realigns the model’s representations for Arabic execution.  
*Mechanism:* Completion-only masking computes loss only on the assistant’s function-call tokens, concentrating training on structured output. Full-parameter updates allow the entire model to adapt to Arabic dialectal nuances and schema constraints, unlike light adapters that showed instability.  
*Evidence:* Partial adaptation (LoRA) failed to converge; full FT achieved parse failures <1% (Section 3.6).  
*Break condition:* If a lower-rank LoRA (e.g., r=64) achieved comparable parse failure rates, full FT would not be necessary.

## Foundational Learning
- **Structured Output Generation**  
  *Why needed:* The task requires emitting machine-readable function calls instead of free text, demanding strict control over formatting and tokens.  
  *Quick check:* What happens if the model outputs invalid JSON during function calling? (Answer: Execution failure or system unreliability.)

- **Dataset Quality and Schema Consistency**  
  *Why needed:* Inconsistent labels or enum variants confuse learning and cause systemic parse failures. Cleaning the dataset is essential for stable supervised learning.  
  *Quick check:* How would an enum parameter with multiple surface forms (e.g., "Cairo", "cairo", "القاهرة") hinder the model’s ability to match the correct tool schema? (Answer: It could learn spurious correlations and fail to produce the canonical value required by the schema.)

- **Supervision Masking in Fine-Tuning**  
  *Why needed:* Masking ensures the model learns to generate the function call rather than mimic the prompt, focusing gradients on the executable format.  
  *Quick check:* Why compute loss only on the assistant’s response tokens? (Answer: To ignore the context and train the model to produce the desired structured output, preventing it from simply copying the input.)

## Architecture Onboarding
**Component map**  
Raw dataset → Audit → Schema repair → Tool pruning → Tool sampling → Chat serialization → Full fine-tuning (completion masking) → Evaluation → Deployment.

**Critical path**  
1. Audit raw dataset (detect empty queries, enum violations, duplicates).  
2. Apply schema repairs: None-is-valid fix, enum normalization, prune redundant tools.  
3. For each sample, stochastically sample 5 tools (true + 4 distractors), shuffle order, and serialize using FunctionGemma’s chat format with a timestamp.  
4. Split data into train/val/test with stratification; ensure no leakage.  
5. Train with full-parameter FT: BF16, gradient checkpointing, 8-bit AdamW, cosine LR (peak 2e-5), 2 epochs, effective batch size 32.  
6. Monitor validation metrics: parse failure, function accuracy, argument alignment.  
7. Package best checkpoint for production (e.g., Hugging Face).

**Design tradeoffs**  
- *Full FT vs LoRA:* Full FT yields robust stability but higher compute; LoRA reduces cost but may sacrifice convergence.  
- *Sampling size:* Smaller set (e.g., 5 tools) avoids truncation and augments data but may not expose model to full tool diversity; larger sets risk truncation.  
- *Repair aggressiveness:* Pruning removes noise but risks discarding rare but valid tools; normalization may erase dialect-specific variants.  
- *Reasoning augmentation:* Adding reasoning blocks improves interpretability but conflicts with strict parsers and alters output format.

**Failure signatures**  
- Structural: Parse failure >10% (indicating format instability, possibly from truncation).  
- Semantic: Low function-name accuracy despite good parse rates (tool disambiguation failure).  
- Dialect gap: >20% accuracy difference between MSA and a dialect (insufficient dialect coverage).  
- Argument mismatch: Low argument F1 (extraction or normalization issues).

**First 3 experiments**  
1. **Baseline evaluation:** Run the original FunctionGemma on the Arabic test set; expect high parse failure (>80%).  
2. **Repair + sampling impact:** Train using only repaired data and tool sampling (keeping base model); parse failures should plummet; verify token counts drop to ~793.  
3. **Full FT vs lightweight adaptation:** Compare full FT against a LoRA baseline (e.g., rank 16); full FT should achieve significantly lower parse failures.

## Open Questions the Paper Calls Out
1. **Separability of serialization stability and decision-level reasoning:** Are these truly independent capability dimensions? The paper shows a shift from structural to semantic errors but does not prove causation. Controlled ablations isolating format supervision from semantic supervision across languages are needed.

2. **Integration of reasoning-augmented outputs into production pipelines:** Reasoning variants yield extra tokens that break strict validators. A format-agnostic parsing or validator adaptation is required to reconcile interpretable outputs with deterministic function calls.

3. **Domain-specific performance gaps:** Government Services domain lags despite near-perfect format validity. The root cause may be data granularity or tool schema design; error analysis by query complexity and targeted augmentation could pinpoint the bottleneck.

4. **Comparison of semantic error reduction techniques:** Contrastive supervision, tool-ranking refinement, and confidence calibration are proposed but not compared empirically. A systematic study measuring their isolated and combined effects on semantic error types is needed.

5. **Cross-linguistic generalizability:** The dialect narrowing effect might be specific to Arabic. Testing the AISA pipeline on multilingual benchmarks (e.g., MASSIVE-Agents) across morphologically rich low-resource languages would determine if the findings generalize.

## Limitations
- Exact tool pruning criteria and enum normalization rules are not fully detailed; reconstruction relies on the released dataset.
- The solution is tightly coupled to FunctionGemma’s tokenizer and chat template; variations could break serialization.
- Evaluation is limited to a held-out test set from the same distribution; real-world scenarios may introduce novel dialects, tools, or longer contexts.

## Confidence
- Mechanism 1 (Dataset auditing & schema repair): **High** – direct evidence from parse failure reduction and tool re-activation.
- Mechanism 2 (Stochastic tool sampling): **High** – token reduction confirmed and performance improved.
- Mechanism 3 (Full-parameter fine-tuning): **High** – partial adaptation failed; full FT achieved the target <1% parse failures.
