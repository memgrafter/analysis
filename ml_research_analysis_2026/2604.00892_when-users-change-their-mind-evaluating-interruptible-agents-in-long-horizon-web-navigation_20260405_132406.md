# When Users Change Their Mind: Evaluating Interruptible Agents in Long-Horizon Web Navigation

## Quick Facts
- arXiv ID: 2604.00892  
- Source URL: https://arxiv.org/abs/2604.00892  
- Reference count: 40  
- Primary result: All evaluated LLM agents struggle with user interruptions; top model Claude-Opus achieves at most 41.82% success after three interruptions.

## Executive Summary
This paper tackles the problem of making long-horizon web navigation agents robust to user interruptions. The authors introduce InterruptBench, a benchmark that adds realistic, essential updates to existing web tasks while maintaining semantic consistency. Testing six state-of-the-art LLM agents, they find that all struggle significantly with interruptions, with even the best model (Claude-Opus) achieving only 41.82% success after three updates. Token overhead is a major cost, and larger models cope better with late interruptions. The work highlights a critical gap in current agent design for dynamic user interactions.

## Method Summary
The authors built InterruptBench by extending WebArena-Lite with synthetically generated interruptions (addition, revision, retraction) that preserve semantic equivalence to the original task. They simulate mid‑task user updates at a fixed relative progress point (60% of the pre‑generated baseline trajectory length) during replay. Six LLM agents (Claude variants, Qwen3, DeepSeek, Mistral) using the WebAgent‑R1 scaffold are evaluated on success rate, efficiency (token/action counts), and paired outcome analysis across interruption types and counts.

## Key Results
- All six LLM agents perform poorly on interrupted tasks; Claude‑Opus reaches only 41.82% success after three interruptions.  
- Token overhead dominates the adaptation cost, especially in failed episodes (e.g., Haiku +2624 tokens).  
- Larger models (Claude‑Opus) handle later interruptions better, while smaller models peak early and degrade.  
- Additional updates often improve success rates but gains are non‑monotonic and sometimes unstable (e.g., DeepSeek regresses at three interruptions).

## Why This Works (Mechanism)
### Mechanism 1
- Claim: Strict semantic constraints ensure synthetic interruptions remain semantically equivalent to the original task while being necessary and natural, preserving benchmark validity.  
- Mechanism: The data synthesis pipeline uses Claude-Opus-4.5 to rewrite the initial user query and generate interruption messages, enforcing three constraints: (1) Ground Truth Consistency – combined meaning yields same ground truth answer as original intent; (2) Necessity – each interruption must be essential; (3) Authenticity – expressed in realistic user tone. Manual review verifies each interruption.  
- Core assumption: A strong LLM can produce high-quality, necessary updates that maintain semantic equivalence when explicitly guided by constraints.  
- Evidence anchors:  
  - [abstract]: "...synthesizes high-quality interruption scenarios under strict semantic constraints."  
  - [section 2.2]: "We enforce the following strict constraints: (1) Ground Truth Consistency... (2) Necessity... (3) Authenticity... All generated data are manually reviewed by the authors to ensure that each interruption message is necessary..."  
  - [corpus]: No direct corpus evidence; neighboring papers address interruption handling in conversational robots or multi‑robot supervision but do not cover synthetic web navigation interruptions.  
- Break condition: If synthetic interruptions drift from semantic equivalence, the evaluation no longer measures interruption handling but a different task. Manual checks catch such failures, but scale could break this constraint.

### Mechanism 2
- Claim: Trajectory‑grounded simulation with relative progress alignment enables controlled comparison across tasks of varying lengths by standardizing the interruption point relative to the agent’s pre‑interruption progress.  
- Mechanism: For each task, a full no‑interruption trajectory is generated and its length L recorded. The interruption is injected at position ⌊ω·L⌋ (ω=0.6 default) during replay. The post‑interruption actions are then indexed from k=1 onward, producing aligned success curves SR(k) independent of absolute task length.  
- Core assumption: Baseline trajectory length is a stable proxy for “progress” such that the same relative fraction corresponds to comparable intermediate states across tasks.  
- Evidence anchors:  
  - [abstract]: "Using a unified interruption simulation framework, we evaluate... analyzing both their effectiveness... and efficiency in recovering from mid‑task changes."  
  - [section 2.3]: "We simulate user‑agent interactions... based on relative progress rather than a fixed global step. Specifically, for each task, the interruption is introduced at a predefined proportion of the initial trajectory... This trajectory‑grounded design enables controlled and comparable evaluation..."  
  - [corpus]: No direct corpus evidence; the concept of trajectory replay for evaluation is used in other agent benchmarks but not in the neighbor set.  
- Break condition: If tasks contain significant non‑determinism or variable‑length preparatory actions, the relative fraction may not align state meaningfully, requiring per‑domain or absolute step thresholds.

### Mechanism 3
- Claim: Paired outcome quadrants (S/F, F/S, S/S, F/F) disentangle whether changes in token or action counts are due to outcome shifts or true cost differences, revealing hidden restarts versus efficient reuse.  
- Mechanism: For each task, label the baseline and interrupted results (success/failure). Group episodes by joint outcome. Compute average action/token differences within each group. This isolates, e.g., the overhead when both fail (F/F) versus the cost‑saving when both succeed (S/S).  
- Core assumption: The no‑interruption baseline is a clean counterfactual for what would have happened without the interruption, enabling attribution of marginal cost to the update itself.  
- Evidence anchors:  
  - [abstract]: "...analyzing both their effectiveness in adapting to updated intents and their efficiency in recovering from mid‑task changes."  
  - [section 4.2]: "Paired‑outcome quadrants. To disentangle the effect of an update on outcome from its effect on cost, we assign each episode a paired label (obase, oint) ∈ {S, F}²... This yields four exhaustive and mutually exclusive outcome quadrants..."  
  - [corpus]: Not present; the neighbors discuss interruption detection or cooperative perception, not paired analysis of agent cost.  
- Break condition: If the baseline trajectory is not truly independent (e.g., interference from previous runs or shared random seeds), the pairing may produce correlated biases that misinterpret cost differences.

## Foundational Learning
- Concept: Interruption scenarios (Addition, Revision, Retraction)  
  Why needed here: These three types capture the spectrum of realistic user updates: adding missing details, correcting errors, and removing extras. Understanding them is key to interpreting why agents succeed or fail on different cases.  
  Quick check question: Provide a concrete example of an addition, a revision, and a retraction interruption for a single web task (e.g., shopping query).

- Concept: Budget-limited success curves SR(k)  
  Why needed here: The paper emphasizes not just final success but how quickly the agent recovers after interruption under a tight remaining budget. SR(k) quantifies adaptation dynamics and reveals plateau effects.  
  Quick check question: If SR(10) = 0.4 and SR(20) = 0.55, what fraction of successful tasks required more than 10 post‑interruption actions?

- Concept: Paired outcome analysis (quadrants)  
  Why needed here: This analysis shows whether interruptions cause inefficiency (e.g., more tokens in F/F) or harmless reuse (S/S small delta). It uncovers hidden costs like unproductive re‑planning.  
  Quick check question: In the F/F quadrant, what did the paper observe across models regarding token overhead? (Answer: substantial increase, indicating prolonged unproductive re‑planning.)

## Architecture Onboarding
- Component map:
  - Web Environment (WebArena-Lite): Simulates a browser; exposes observations (DOM tree or visual screenshot) and executes atomic actions (click, type, navigate). Maintains persistent state (DOM, cookies, etc.).
  - LLM Agent (WebAgent-R1 scaffolding): Takes conversation history (initial query + any interruptions) and current observation; outputs reasoning (<think>) and action (<answer>). May include tool‑calling for APIs.
  - Interruption Handler: In production, receives asynchronous user messages and appends them to the conversation history at the appropriate moment. In the benchmark, it injects synthesized updates at a relative‑progress point during replay.
  - Controller/Trajectory Manager: Drives the execution loop: sends actions to environment, collects observations, tracks progress (step count), decides when to trigger interruption (based on relative progress or real‑time user input).
  - Evaluation Harness: Runs rolled‑out trajectories, compares final state to expected ground truth post‑update, computes success, token cost, and action count. Also performs paired outcome grouping.

- Critical path:
  1. Start task with initial user query.
  2. Agent acts repeatedly on environment; controller monitors progress ratio = completed steps / baseline length.
  3. When progress reaches threshold (e.g., 0.6), interruption injected: user message appended to history.
  4. Agent, upon receiving observation that includes interruption, should integrate update and continue generating actions.
  5. Process repeats until task completion, budget limit, or max steps.
  6. Evaluation metric recorded against updated intent.

- Design tradeoffs:
  - Timing: Early interruptions (small progress) are easier because less committed state; late interruptions test repair of persistent UI changes and may require more expensive rollback/replan. A robust system should handle both.
  - Replan vs. incremental edit: Full replan from scratch ensures consistency but costs tokens and time; incremental edit (e.g., editing form fields) is cheaper but may miss dependent state changes. Hybrid approaches (selective re‑execution) could balance.
  - Context length vs. history: Interruptions increase history length; may need summarization or pruning to stay within model context. Summaries risk dropping details needed for precise navigation.
  - Efficiency measures: Token overhead is dominant; models that reuse pre‑interruption progress show lower overhead. Engineering goal: minimize unnecessary regeneration of prior reasoning.

- Failure signatures:
  - Stale state: Agent acknowledges interruption but continues with old parameters (e.g., does not change form field that was set earlier). Outcome: answer based on wrong state; typically S/F or F/F.
  - Unproductive loops: Agent repeatedly attempts to undo an action that the environment cannot revert (e.g., trying to “uncheck” a non‑toggleable element). Visible as many actions with no state change, high token usage.
  - Performance decay with late interruption: Success rate drops significantly when interruption at 0.8 vs 0.2, indicating inability to repair committed state.
  - Cost inflation: F/F quadrant shows large positive token deltas; S/F also costly. Healthy adaptation shows S/S with near‑zero overhead.

- First 3 experiments:
  1. Baseline sanity check: Run 10 tasks with no interruptions. Record success rate (~70% for strong models) and average tokens/actions. Establish that agents can complete tasks without updates.
  2. Single‑turn addition (ω=0.6): Inject addition interruption. Compute SR(k) curves and compare to baseline. Expect models to show adaptation (gap between curves) but plateau below 100%. Record token deltas by quadrant; F/F should show high overhead.
  3. Multi‑turn sequence (3 interruptions): Apply random mix of addition, revision, retraction at progressive points (0.3, 0.6, 0.8). Check if success improves monotonically; note any instability (e.g., DeepSeek regression at n=3). Verify that later interruptions increase cost and may cause failure.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: What architectural changes can reduce the token overhead of interruption handling without compromising success?
- Basis in paper: [inferred] The study finds token overhead dominates adaptation cost, especially in unsuccessful episodes (e.g., Haiku +2624 tokens), while action changes are small.
- Why unresolved: The paper does not isolate whether overhead stems from increased deliberation, redundant reasoning, or inefficient prompting.
- What evidence would resolve it: Controlled experiments varying reasoning length, using separate state‑trackers, measuring token distribution across thought vs. action.

### Open Question 2
- Question: Why do larger LLMs benefit from later interruptions while smaller ones perform best with early interruptions?
- Basis in paper: [inferred] Interruption position experiments (Appendix E) show Claude‑Opus improves as interruption is delayed (0.8 position), whereas Haiku/DeepSeek peak early and degrade later.
- Why unresolved: The authors speculate about stale assumptions but lack evidence on internal planning/repair mechanisms.
- What evidence would resolve it: Analyzing how models update internal representations after an interruption, varying irreversible action ratios, or measuring ability to localize and repair plan fragments.

### Open Question 3
- Question: What causes the non‑monotonic performance gains when multiple interruptions accumulate (e.g., DeepSeek regresses at n=3)?
- Basis in paper: [inferred] Table 2 shows DeepSeek success: 12.12% (n=1) → 21.21% (n=2) → 20.61% (n=3); similar patterns for Mistral.
- Why unresolved: It's unclear whether later updates conflict with earlier ones, context saturation, or inability to reconcile incremental changes.
- What evidence would resolve it: Error analysis on multi‑turn trajectories, measuring update incorporation fidelity, testing different context management (summaries, explicit state updates).

## Limitations
- Synthetic interruptions rely on Claude‑Opus and manual review; may not capture natural language diversity or truly “necessary” updates.
- Baseline trajectory length as a progress proxy can misalign state for tasks with variable‑complexity steps or nondeterminism.
- Paired efficiency analysis assumes baselines are independent counterfactuals; shared random seeds might introduce bias.
- Unspecified details: WebAgent‑R1 agent implementation, multi‑turn interrupt schedule, and exact evaluation budgets hinder faithful replication.
- Qwen3‑480B‑A35B is not publicly accessible, limiting full reproducibility.
