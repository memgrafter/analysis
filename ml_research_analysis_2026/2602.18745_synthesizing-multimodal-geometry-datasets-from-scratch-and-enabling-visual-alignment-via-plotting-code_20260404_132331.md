# Synthesizing Multimodal Geometry Datasets from Scratch and Enabling Visual Alignment via Plotting Code

## Quick Facts
- **arXiv ID:** 2602.18745
- **Source URL:** https://arxiv.org/abs/2602.18745
- **Reference count:** 40
- **Primary result:** Introduces GeoCode dataset and code-based alignment, boosting VLM geometry accuracy from 17.9% to 37.7% on held-out test and +11.52 on OlympiadBench.

## Executive Summary
Vision-language models struggle with multimodal geometry reasoning due to scarce training data and weak visual-symbolic alignment. This paper addresses both challenges by synthesizing GeoCode, an 18K-problem dataset via a modular pipeline with rigorous multi-stage verification, ensuring consistency across symbolic structure, text, reasoning, and diagrams. It further introduces plotting-code prediction as an explicit alignment objective, converting visual understanding into a supervised structured prediction task. Experiments on multiple geometry benchmarks show substantial improvements; ablations confirm that code-based supervision significantly outperforms caption-based alignment.

## Method Summary
The synthesis pipeline decouples generation into three stages: (1) symbolic seed construction using GenesisGeo to produce predicate graphs; (2) grounded instantiation with an Instructor LLM to generate problem statements, chain-of-thought, and answers; (3) a Coder LLM emits executable plotting code (coordinates, segments, circles, annotations). Multi-stage verification—semantic (LLM judge), geometric (numeric constraints), code execution, and image quality filtering—removes invalid samples, while a debiaser eliminates textual shortcuts. For training, models are fine-tuned via SFT on a multi-task loss (plotting code + CoT + answer) followed by GRPO reinforcement learning with rewards on answer correctness and format. This explicit structural supervision bridges the gap between diagrams and symbolic reasoning.

## Key Results
- Held-out test accuracy rises from 17.9% to 37.7% after SFT and GRPO.
- Qwen3-VL gains +11.52 points on OlympiadBench.
- Plotting-code supervision substantially outperforms caption-based alignment (Table 6); segment-level F1 correlates with solving accuracy.

## Why This Works (Mechanism)

### Mechanism 1: Decoupled Synthesis with Verification
**Claim:** Modular stages with multi‑stage verification maintain strict cross‑modal consistency (structure ↔ text ↔ reasoning ↔ image).  
**Mechanism:** GenesisGeo builds predicate graphs; Instructor LLM grounds them numerically; Coder LLM generates plotting code; semantic and geometric verifiers check logical and numeric validity; renderer produces diagrams; debiaser removes textual shortcuts. Evidence: abstract and Section 3.1 detail stages; Table 5 shows rejection counts per stage, isolating error modes. Break condition: any verification failure (semantic inconsistency, coordinate mismatch, execution error, visual ambiguity) discards the sample.

### Mechanism 2: Plotting-Code Prediction as Explicit Alignment
**Claim:** Supervising plotting-code prediction forces explicit geometric structure reconstruction from diagrams, strengthening visual-symbolic alignment more than caption-based or answer-only supervision.  
**Mechanism:** Models output structured code (points, segments, circles, annotations) given an image and question, converting visual understanding into a supervised structured prediction task. Evidence: abstract; Section 3.2 explains advantage over implicit text alignment; Section 4.5 ablation shows code supervision yields larger gains than caption-based (Table 6) and correlates with segment-level F1 (Fig 5). Break condition: low parsing rate or low segment F1 diminishes alignment benefit; annotation errors strongly predict reasoning failure (Fig 6).

### Mechanism 3: Multi-Stage Validation as Complementary Quality Gates
**Claim:** A series of automated checks filters distinct error modes (semantic incoherence, geometric invalidity, construction non-executability, visual clutter) to ensure dataset correctness and difficulty.  
**Mechanism:** After seed selection, samples undergo semantic validation (LLM judge), numeric geometric checks (lengths, angles, collinearity with tolerance ϵ=1e‑6), code execution in sandbox, and image quality filtering (ambiguity detection). Evidence: Section 3.1.2 describes verification; Table 5 reports rejection counts per stage; Section 4.2 manual inspection of 1% subset found no incorrect samples. Break condition: overly strict thresholds prune diversity; overly lenient admit errors.

## Architecture Onboarding
**Component map:**  
Seed Generator (GenesisGeo) -> Instructor LLM -> Coder LLM -> Verifiers (semantic, geometric, execution) -> Renderer -> Debiaser -> Quality Checker -> Trainer (SFT + GRPO)

**Critical path:** Symbolic seed -> Instructor (text + reasoning) -> Coder (meta‑code) -> Verification -> Rendering -> Debiasing -> Plotting code final -> Training (code prediction + reasoning)

**Design tradeoffs:**  
- Modularity simplifies development but requires careful handoffs between stages.  
- LLM reliance introduces hallucination risks, mitigated by verification but causing high rejection rates (~50%).  
- Code‑based alignment offers strong supervision but limits output format; captions are flexible but weaker.

**Failure signatures:**  
- High instantiation rejection: semantic inconsistencies or coordinate mismatches (Table 5 rows 1‑2).  
- Meta‑code execution failures: syntactically invalid or non‑executable code (Table 5 row 3).  
- Visual quality filter discarding ambiguous diagrams (Table 5 row 4).  
- Training instability: low parsing rate or segment‑level F1 on plotting code (Fig 6a); annotation errors correlate with solving drops (Fig 6b).

**First 3 experiments:**  
1. **Dataset quality analysis:** Confirm correctness (manual inspection), diversity (predicate distribution, Fig 8), and complexity (segment/annotation counts, Table 1) relative to benchmarks (Table 2).  
2. **Transfer evaluation:** Train on GeoCode, test on held‑out Test‑mini and public benchmarks (Geometry3K, GeoQA, OlympiadBench, MathVerse, MathVista); measure SFT and GRPO gains (Tables 3‑4).  
3. **Ablation on alignment:** Compare no alignment, caption‑based, and code‑based supervision (± debiasing) on Test‑mini and Geometry3K; correlate segment‑level F1 with solving accuracy (Table 6, Fig 5‑6).

## Open Questions the Paper Calls Out
1. To what extent does the performance gain from code‑based alignment depend on the specific visual‑language model backbone, and can the benefits transfer to non‑Qwen VLMs without substantial retraining?
2. Which specific components of the plotting code (e.g., segment topology, circle parameters, annotation constraints) are most predictive of improved geometric reasoning, and does the model learn to prioritize certain structural elements over others?
3. Can the pipeline's text‑seeded synthesis (Appendix E) be generalized to geometry benchmarks with sparser or less structured textual descriptions (e.g., Geometry3K), and what modifications are needed to handle such inputs robustly?
4. Beyond planar Euclidean geometry, can the synthesis pipeline be extended to three‑dimensional geometry or non‑Euclidean contexts (e.g., spherical, hyperbolic) while maintaining the same level of automatic verification and visual rendering?

## Limitations
- Instructor and Coder prompts are not disclosed; reliance on GPT‑OSS‑120B hinders replication.
- GenesisGeo sampling parameters (ρ, M) are missing, affecting seed distribution and diversity.
- Evaluation is limited to Qwen VLMs; generalizability to other architectures is unknown.
- 18K samples may be small; synthetic data could have narrow coverage compared to real human problems.
