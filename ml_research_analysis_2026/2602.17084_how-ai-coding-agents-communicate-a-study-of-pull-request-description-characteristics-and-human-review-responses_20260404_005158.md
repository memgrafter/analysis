# How AI Coding Agents Communicate: A Study of Pull Request Description Characteristics and Human Review Responses
## Quick Facts
- **arXiv ID**: 2602.17084  
- **Source URL**: https://arxiv.org/abs/2602.17084  
- **Reference Count**: 22  
- **Primary Result**: AI agents exhibit distinct pull request description styles (e.g., Codex: structured; Copilot: code-dense), which correlate with significantly different human review outcomes like merge rate (43.0%–82.6%) and time to completion.

## Executive Summary
This study analyzes 33,596 pull requests generated by five AI coding agents (GitHub Copilot, OpenAI Codex, Claude Code, Devin, Cursor) to understand how their communication characteristics affect human reviewer responses. Using the AIDev dataset, the authors compare 11 structural features of PR descriptions (e.g., use of headers, lists, code blocks, emoji) against review outcomes including merge rate, timing, comment volume, and sentiment. Key findings reveal agent-specific patterns: for instance, Codex uses highly structured descriptions and achieves the fastest review cycles and highest merge rate, while Copilot generates more code blocks and comments but has the lowest merge rate. All measured differences between agents are statistically significant, though the observational nature of the study limits causal claims due to potential confounding by code quality or task difficulty.

## Method Summary
The study uses the AIDev dataset, filtering out bot accounts and null/whitespace records. It computes 11 PR description features via regex parsing (headers, lists, code blocks, emoji, politeness phrases, etc.) and derives per-PR densities (per 1,000 characters) except for raw character count and a binary Conventional Commits flag. All features and outcome metrics (e.g., comments per PR, time to completion, sentiment) are normalized using Z-scores (dataset-wide mean and standard deviation) for cross-agent comparison. Statistical significance is assessed with Kruskal-Wallis tests for continuous metrics and Chi-square tests for categorical ones. Sentiment is analyzed using a RoBERTa model fine-tuned on software engineering text, applied only to English comments.

## Key Results
- Agent PR styles differ markedly: Codex favors headers/lists; Copilot uses more code blocks; Cursor shows high politeness and plain text.
- Merge rates vary widely: Codex (82.6%), Cursor (65.22%), Copilot (43.0%).
- Faster completion times correlate with structured descriptions (Codex: 0.02 hours median); Copilot’s high comment volume does not translate to higher merge rates.
- Negative sentiment is highest for Cursor yet it maintains a moderately high merge rate, suggesting critique may target presentation over code substance.

## Why This Works (Mechanism)
### Mechanism 1: Structured descriptions accelerate review
**Claim**: PRs with explicit structural markers (headers, lists) are completed faster.  
**Mechanism**: Clear organization reduces reviewer cognitive load, speeding initial feedback and final decision, which prevents context decay.  
**Core assumption**: Description readability is the primary bottleneck for time-to-first-comment, not code complexity.  
**Evidence anchors**: Codex shows high header/list use, fastest time_to_completion (0.02h), and highest merge rate (82.6%).  
**Break condition**: If controlling for code quality metrics (e.g., test coverage) eliminates the association between structure and completion time.

### Mechanism 2: High comment volume indicates inefficient review cycles
**Claim**: More reviewer comments do not imply higher merge probability; may reflect entanglement over minor issues.  
**Mechanism**: High code block density (Copilot style) prompts extensive discussion focused on presentation or clarification rather than core functionality, prolonging engagement without convergence.  
**Core assumption**: Comment volume reflects review inefficiency rather than thorough vetting.  
**Evidence anchors**: Copilot has highest comments_per_pr (Z=1.68) but lowest merge rate (43.0%).  
**Break condition**: If sentiment analysis shows Copilot’s comments are disproportionately about clarifying intent vs. debating correctness.

### Mechanism 3: Negative sentiment can coexist with merging
**Claim**: Negative review comments do not preclude merge; may critique presentation, not code substance.  
**Mechanism**: Agents with plain-text, polite descriptions (Cursor) attract negative sentiment on style/formatting while the code itself is acceptable, leading to eventual merge.  
**Core assumption**: Sentiment classifiers can distinguish communication critique from code rejection.  
**Evidence anchors**: Cursor has highest negative_sentiment_pct (Z=0.64) but 65.22% merge rate; discussion notes negative comments often target presentation.  
**Break condition**: If manual annotation shows most Cursor negative comments explicitly reject code functionality.

## Foundational Learning
- **Concept**: Z-score normalization for cross-agent comparison  
  **Why needed**: Raw metrics (e.g., lines added, emoji count) have different scales; Z-scores allow direct heatmap comparison of relative agent tendencies.  
  **Quick check**: If Agent A has `header` Z-score +1.2 and Agent B -0.8, what does this indicate about their relative header use?

- **Concept**: Observational study limitations and confounding  
  **Why needed**: All claims are associative; unmeasured variables (task difficulty, repo norms, code quality) could drive both PR style and outcomes.  
  **Quick check**: Why can’t we conclude that using more Markdown headers *causes* faster merges based on this study?

- **Concept**: Effect size interpretation (ε², V) beyond p-values  
  **Why needed**: Statistical significance (p<0.001) is universal, but practical importance varies: ε²=0.280 (comments/PR) is substantial; ε²=0.006 (comment length) is trivial.  
  **Quick check**: Which metric suggests agent differences matter most in practice: merge rate (V=0.349) or time_to_first_comment (ε²=0.018)?

## Architecture Onboarding
- **Component map**: Raw PR data (AIDev tables) -> Feature extraction (regex parsers, git logs) -> Normalization (Z-scoring) -> Statistical testing (Kruskal-Wallis, Chi-square) -> Visualization (heatmaps, bar charts)
- **Critical path**: Preserve PR-agent linkage across tables through all transformation steps; data quality at extraction stage determines downstream validity.
- **Design tradeoffs**:  
  Automated regex parsing enables scalability but loses nuance (e.g., header semantics).  
  Filtering non-English sentiment comments improves model validity but biases toward English-heavy repos/agents.  
  Using median times robustly handles outliers but discards distribution shape (e.g., long-tail waits).
- **Failure signatures**:  
  `conventional_commit` flag may be too strict if repos don’t enforce Conventional Commits.  
  Sentiment model [22] may not generalize to AI-generated text despite SE fine-tuning.  
  No pairing of PR difficulty (e.g., LOC churn) with outcome; could dominate style effects.
- **First 3 experiments**:  
  1. Replicate Table 1 metrics on a subset; manually validate regex counts for 50 PRs per agent.  
  2. Run matched-pair analysis: For each agent, select PRs with identical `files_changed` ±1, compare merge rates by `header` Z-score quartile.  
  3. Train logistic regression: Merge ~ header + code + politeness + agent; check if agent effects diminish after controlling for description features.

## Open Questions the Paper Calls Out
**Open Question 1**: What is the causal effect of PR description structure on review outcomes, independent of code quality?  
*Basis*: Observational study cannot establish causality due to confounding by code quality, task complexity, repository norms (Section 4).  
*Why unresolved*: Associations may be driven by simpler code changes rather than descriptions.  
*What evidence would resolve*: Controlled experiments or advanced statistical methods isolating description effects while holding code constant.

**Open Question 2**: How do AI agents tailor their PR descriptions across task types (e.g., bug fix vs. feature), and does this tailoring affect reviewer responses?  
*Basis*: Threat to validity: "RQ1 is not conditioned on task categories" (Section 4).  
*Why unresolved*: Without task stratification, we cannot know if agent styles are task-agnostic or if certain styles work better for specific tasks.  
*What evidence would resolve*: Re-analyze by task type (using commit messages or manual labeling) to compare characteristics and outcomes per task.

**Open Question 3**: How should we interpret reviewer sentiment in AI-PR discussions? Does negative sentiment primarily critique presentation or the code, and how does this impact merges?  
*Basis*: Discussion warns negative comments often target presentation, not code rejection; sentiment is contextual (Section 6).  
*Why unresolved*: Sentiment tool does not distinguish target, limiting predictive power for merge decisions.  
*What evidence would resolve*: Fine-grained sentiment analysis classifying aspect commented on (e.g., description clarity vs. code correctness), validated against merge outcomes.

**Open Question 4**: How generalizable are these findings to other AI coding agents and platforms?  
*Basis*: External validity threat: "Generalization to other agents, time periods, and non GitHub workflows may be limited" (Section 4).  
*Why unresolved*: Study examined only five agents on GitHub; newer agents or different workflows may yield different patterns.  
*What evidence would resolve*: Multi-agent, multi-platform studies replicating methodology on diverse datasets.

## Limitations
- **Confounding**: Unmeasured variables (task difficulty, repo norms, code quality) likely influence both PR style and outcomes, limiting causal claims.
- **Measurement validity**: Regex-based feature extraction and SE-sentiment model may misclassify nuanced communication, especially for AI-generated text.
- **Dataset biases**: English-only sentiment analysis and bot filtering may skew results; agent versions/repos are uncontrolled.

## Confidence
- **High**: Descriptive differences in PR features and outcomes across agents (e.g., Codex’s structured style, Copilot’s comment volume).
- **Medium**: Associations between style and outcomes (e.g., structure → faster completion; comment volume → lower merge rate). Plausible but confounded.
- **Low**: Mechanistic interpretations (e.g., “negative sentiment reflects presentation critique, not code rejection”). Requires granular comment annotation.

## Next Checks
1. **Matched-pair analysis**: For each agent, compare merge rates/times between PRs with high vs. low `header` Z-score, matching on `files_changed` and repository.
2. **Manual sentiment audit**: Randomly sample 100 “negative” Cursor comments; annotate whether critique targets description style vs. code functionality.
3. **Regex reliability test**: Manually code description structure (headers/lists/code blocks) for 50 PRs per agent; compute agreement with automated counts.
