# Schema on the Inside: A Two-Phase Fine-Tuning Method for High-Efficiency Text-to-SQL at Scale

## Quick Facts
- arXiv ID: 2603.24023
- Source URL: https://arxiv.org/abs/2603.24023
- Reference count: 6
- Primary result: Two-phase fine-tuning internalizes a static database schema, reducing input tokens by >99% (from ~17k to <100) while achieving 98.4% execution success and 92.5% semantic accuracy, surpassing a prompt-engineered Gemini Flash 2.0 baseline.

## Executive Summary
The paper tackles the high per-token API costs and latency in text-to-SQL systems that rely on long, schema-heavy prompts with external LLMs. It introduces a two-phase fine-tuning method for an 8B self-hosted model (Qwen 3 8B) that internalizes the database schema. Phase 1 jointly trains on full-context SQL generation and explicit schema memorization tasks. Phase 2 then trains on minimal prompts containing only a database ID trigger, forcing the model to recall the internalized schema. This reduces input tokens by over 99% and yields superior execution and semantic accuracy compared to a strong external LLM baseline on a cricket statistics database.

## Method Summary
The approach uses supervised fine-tuning (SFT) with LoRA on Qwen 3 8B in two distinct phases. Phase 1 trains on a mixed dataset: 80k full-context SQL examples (prompts include complete schema and query) and 15k explicit schema memorization examples (prompts request full schema given a database ID). Training uses a large context length of 20,480 tokens. Phase 2 resumes the LoRA adapter, reduces context to 1,024 tokens, and trains on 150k minimal-prompt examples where prompts contain only the user query and a database ID trigger (e.g., "cricket stats db v1"). Optimization uses AdamW (lr=2e-5) with a cosine scheduler, distributed across 8x NVIDIA H100 GPUs via DDP. Deployment leverages vLLM for efficient inference.

## Key Results
- Input token reduction: over 99%, from ~17,000 to under 100 tokens per query.
- Execution success: 98.4% on a 30k holdout set of real user queries.
- Semantic accuracy: 92.5% (LLM-judged), surpassing Gemini Flash 2.0 (95.6% execution, 89.4% semantic).

## Why This Works (Mechanism)
The two-phase method decouples schema acquisition from minimal-prompt adaptation. Phase 1 exposes the model repeatedly to the full schema in a large context, enabling it to learn the database structure while generating SQL. Explicit memorization tasks further reinforce schema retention. Phase 2 then removes explicit schema from prompts, using only a database ID as a retrieval cue. This forces the model to rely on its internalized schema representation, effectively compressing the schema into its parameters. LoRA efficiently adapts the model across both phases without full retraining. The large context in Phase 1 ensures the complete schema is seen multiple times, which is critical for memorization, while the minimal prompts in Phase 2 directly train the desired deployment behavior.

## Foundational Learning
- **Two-phase fine-tuning**: Separates schema learning (Phase 1) from deployment-style prompting (Phase 2). *Why needed*: Prevents the model from overfitting to full-context cues and ensures it can operate with minimal prompts. *Quick check*: Train only on minimal prompts without Phase 1; accuracy should collapse.
- **Schema internalization**: Encoding static database schema into model weights. *Why needed*: Eliminates the need to transmit schema in every prompt, reducing cost/latency. *Quick check*: After Phase 1, prompt with only the database ID and evaluate if the model can accurately reproduce the schema.
- **Token reduction via prompting**: Minimizing input tokens by replacing full schema with a short identifier. *Why needed*: Directly addresses API cost and latency scales with token count. *Quick check*: Tokenize a full-context prompt and a minimal prompt; confirm >90% reduction.
- **LoRA for parameter-efficient fine-tuning**: Updates only low-rank matrices of the model. *Why needed*: Enables training large models with limited GPU memory and preserves base model knowledge. *Quick check*: Count trainable parameters; should be ~1-2% of total model parameters.
- **Context window scaling**: Using 20k tokens in Phase 1 to fit the entire schema, then dropping to 1k in Phase 2. *Why needed*: Balances the memory requirement for schema exposure against the target deployment context size. *Quick check*: Verify the serialized schema fits within 20k tokens using the target tokenizer.
- **Self-hosted inference vs. external API**: Deploying a fine-tuned 8B model instead of calling a proprietary LLM. *Why needed*: Avoids per-token costs and reduces latency after training investment. *Quick check*: Compare inference latency per query between self-hosted vLLM and an API like Gemini Flash.

## Architecture Onboarding
Component map: [Synthetic Data Generation (Qwen/QwQ 32B)] -> [Phase1 SFT (Full-context + Memorization)] -> [Phase2 SFT (Minimal Prompt Adaptation)] -> [Deployment (vLLM)]

Critical path:
1. Generate synthetic training data: start from 11k user queries, use a reasoning model (e.g., Qwen/QwQ 32B) in a loop to produce SQL, execute, and on failure append error and retry to create ground-truth query-SQL pairs.
2. Build Phase 1 dataset: combine 80k full-context examples (schema + query) and 15k memorization examples (db ID -> full schema).
3. Train Phase 1: load Qwen 3 8B, apply LoRA (r=64, alpha=128, target q/k/v), train on 20k context with AdamW (lr=2e-5).
4. Build Phase 2 dataset: 150k minimal-prompt examples (user query + db ID trigger).
5. Train Phase 2: resume Phase 1 LoRA adapter, reduce context to 1k, continue training on minimal prompts.
6. Deploy: serve the adapted model with vLLM for low-latency inference.

Design tradeoffs:
- Token reduction vs. accuracy: Extreme token reduction risks schema recall failure; mitigated by aggressive Phase 1 memorization.
- Static schema assumption: Works only for fixed databases; any schema change requires retraining.
- Large Phase 1 context: Demands high GPU memory (20k tokens) but is necessary to fit the full schema for memorization.

Failure signatures:
- CUDA OOM during Phase 1 training due to 20k sequence length.
- Low schema reconstruction accuracy when prompting Phase 1 model with only db ID.
- Sharp execution accuracy drop when switching from full-context to minimal prompts in Phase 2.
- Persistent semantic errors on queries with ambiguous column aliases or complex temporal logic.

First experiments:
1. After Phase 1, evaluate schema memorization: prompt with db ID only and compute F1 between predicted and ground-truth schema (tables/columns); target >95%.
2. After Phase 2, run minimal-prompt queries on a validation set; measure execution accuracy; should match or exceed full-context Phase 1 baseline.
3. Measure token counts: use the tokenizer to compute average tokens for full-context vs. minimal prompts; confirm >99% reduction.

## Open Questions the Paper Calls Out
- **Direct Preference Optimization (DPO)**: Can DPO further improve accuracy on remaining failure cases involving ambiguous column aliasing and complex temporal reasoning? The paper identifies this as a promising direction but has not yet applied it.
- **Schema evolution robustness**: How to update the internalized schema without complete retraining when the database schema changes? The paper acknowledges the static schema limitation but offers no incremental update mechanism.
- **Cross-domain generalizability**: Does the two-phase recipe work for diverse database domains and schema complexities? The paper claims generalizability but only validates on a single cricket statistics database.

## Limitations
- Critical replication details missing: exact full-context prompt template, schema serialization format, and the synthetic data generation loop (retry logic, error formatting).
- Evaluation confined to one domain (cricket statistics); no evidence of performance on standard text-to-SQL benchmarks (e.g., Spider, BIRD).
- Semantic accuracy relies on an LLM judge, introducing subjectivity and potential bias.

## Confidence
- Token reduction claim: **High** (directly measured, inherent to architecture).
- Execution/semantic accuracy vs. Gemini Flash: **Medium** (holdout evaluation on proprietary dataset; LLM-judged metric).
- Generalizability to other schemas: **Low** (no empirical cross-domain validation).

## Next Checks
1. **Pre-Phase 2 Schema Recall Test**: Before Phase 2, prompt the Phase 1 model with the db ID trigger and measure exact schema reconstruction accuracy (table/column F1). Target >95% to ensure memorization.
2. **Prompt Template Audit**: Reconstruct the 17k-token full-context prompt exactly (schema + domain context) and verify token count using the same tokenizer; document serialization (e.g., `CREATE TABLE` vs. JSON).
3. **Cross-Schema Generalization**: Apply the same two-phase pipeline to a different public database (e.g., `academic` or `geo`), using minimal prompts. Report execution accuracy drop relative to cricket schema; significant drop indicates overfitting.
