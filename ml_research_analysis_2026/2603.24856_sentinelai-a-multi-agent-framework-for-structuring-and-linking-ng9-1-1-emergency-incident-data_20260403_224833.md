# SentinelAI: A Multi-Agent Framework for Structuring and Linking NG9-1-1 Emergency Incident Data

## Quick Facts
- **arXiv ID:** 2603.24856
- **Source URL:** https://arxiv.org/abs/2603.24856
- **Reference count:** 10
- **Primary result:** SentinelAI integrates heterogeneous emergency response data into a unified, standards-compliant view by implementing a multi-agent framework with an EIDO transformer, an incident correlator, and a geocoding enricher.

## Executive Summary
The paper introduces SentinelAI, a multi-agent framework designed to solve the long-standing challenge of integrating disparate emergency response data sources—such as CAD notes, weather alerts, and news reports—into a single, NENA EIDO-compliant operational view. It achieves this through three collaborating agents: the EIDO Agent structures raw inputs into standardized JSON, the IDX Agent correlates related records into evolving composite incidents, and the Geocoding Agent enriches informal location descriptions. The work provides a reference architecture aligned with NENA standards, demonstrates enterprise interoperability via FME, and validates the approach with a case study linking a flood warning and news article. However, it lacks quantitative performance evaluation and leaves key parameters unspecified.

## Method Summary
The framework transforms heterogeneous raw emergency communications (e.g., call-taker notes, dispatch summaries, NWS alerts, news articles) into NENA EIDO-JSON objects and links related objects into dynamic composite incidents. The EIDO Agent leverages an LLM with configurable templates to extract entities, timestamps, and codes, mapping them to the EIDO schema. The IDX Agent computes a weighted similarity score—combining temporal proximity, geospatial distance, and semantic text similarity—to determine if a new EIDO belongs to an existing incident cluster. The Geocoding Agent resolves colloquial location references via local gazetteers and external APIs, adding coordinates and confidence measures. The system treats each EIDO as an immutable event, enabling incremental updates and audit trails.

## Key Results
- Reference architecture aligned with NENA standards.
- Operational linked-incident data model supporting incremental updates.
- Demonstrated enterprise interoperability through FME integration.
- Case study successfully links an NWS flood warning and a news report into a single incident context.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** The EIDO Agent transforms heterogeneous raw emergency communications into standardized NENA EIDO-JSON documents by using a language model and configurable templates.
- **Mechanism:** The agent interprets unstructured inputs (call notes, transcripts) to extract entities, timestamps, and codes, then maps them to the EIDO schema's structured fields (e.g., `incidentTypeCommonRegistryText`, `callStartTimestamp`). Configurable templates define required/optional fields per incident type, decoupling business rules from core logic.
- **Core assumption:** A language model can reliably interpret domain-specific jargon and partial information to populate a fixed schema when guided by templates.
- **Evidence anchors:** [abstract] "The EIDO Agent ingests raw communications and produces NENA-compliant Emergency Incident Data Object JSON." [section 3.1] Detailed table showing legacy field-to-EIDO mappings; description of template-based structuring. [corpus] Weak external validation. Neighbors (e.g., Auto311, LogiDebrief) explore LLM use in emergency response but provide no direct comparative evidence for this specific templated approach. Average neighbor citations=0.0.
- **Break condition:** If input format variability exceeds template coverage or LLM hallucinations produce invalid EIDO-JSON, the output fails schema validation or loses critical information.

### Mechanism 2
- **Claim:** The IDX Agent correlates new EIDO documents with existing incident contexts via a weighted similarity score (temporal, spatial, semantic) to maintain a linked, evolving composite incident.
- **Mechanism:** For each new EIDO, the agent computes Σ(E_new, I) = w_t·ϕ_t(Δt) + w_g·ϕ_g(Δg) + w_s·ϕ_s(text embeddings) against all active incidents I. If the max score exceeds threshold τ, the EIDO is linked to incident I*; otherwise, it starts a new incident. Composite views are dynamically aggregated from linked EIDOs.
- **Core assumption:** A linear weighted combination of temporal proximity, geospatial distance, and semantic text similarity effectively captures incident relatedness across disparate sources.
- **Evidence anchors:** [abstract] "The Incident Data Exchange (IDX) Agent correlates related EIDOs into evolving composite incidents via a weighted scoring function." [section 3.2] Equation (2) defines the scoring function; cascade filter logic described; Figure 2 shows decision flow. [corpus] No direct validation of this scoring function. Neighbor "Dependency Aware Incident Linking" deals with cloud incidents, not emergency data; techniques are not directly transferable. FMR scores ~0.5 suggest topical similarity but no methodological validation.
- **Break condition:** If incident evolution involves non-linear patterns (e.g., multi-day events with intermittent updates) or semantic similarity fails on reports with minimal text, the linear score may mis-link or miss valid updates.

### Mechanism 3
- **Claim:** The Geocoding Agent enriches informally described locations by combining local landmark knowledge, external mapping APIs, and incident context to produce machine-interpretable coordinates and preserved descriptive text.
- **Mechanism:** The agent first queries a curated local gazetteer of colloquial place names; if ambiguous, it defers to services like Google Maps/OpenStreetMap. Incident context (type, jurisdiction) disambiguates candidates. Output includes coordinates, civic address, original descriptive text, and a confidence measure.
- **Core assumption:** Local landmark databases and contextual disambiguation can resolve emergency caller vernacular (e.g., "the big market by the river") more reliably than standard geocoders alone.
- **Evidence anchors:** [section 3.3] Explicitly states the three-pronged process and differentiates from "general-purpose geocoders"; cites Goodchild & Li [7] on VGI quality challenges. [section 5.3] Case study shows "Central San Diego County" polygon resolved via Geocoding Agent. [corpus] No supporting papers on emergency-specific geocoding with local knowledge integration. Neighbors focus on UAV networks or semantic perception, not location resolution.
- **Break condition:** If local knowledge base is incomplete for a jurisdiction and incident context is insufficient (e.g., a vague report with no type), the agent may return wrong coordinates or low-confidence results, propagating errors downstream.

## Foundational Learning
- **Concept: EIDO-JSON as an event-sourced, composite incident model**
  - **Why needed:** SentinelAI's core innovation is treating each EIDO as an immutable update to an incident, not a replacement. Understanding this avoids data loss and enables audit trails.
  - **Quick check:** How would you reconstruct the full timeline of an incident from the stored EIDO set, and what rule would you use to determine the current "status"?
- **Concept: Multi-agent decomposition for interoperability**
  - **Why needed:** Separating structuring (EIDO Agent), correlation (IDX Agent), and enrichment (Geocoding Agent) allows independent scaling, template updates, and reuse in different pipelines.
  - **Quick check:** If a new data source (e.g., social media feeds) were added, which agent(s) would need modification and why?
- **Concept: Controlled vocabularies and IANA registries for semantic interoperability**
  - **Why needed:** EIDO relies on standardized codes (incident types, priorities) to avoid local code ambiguity. Learning this ensures correct mapping from legacy systems.
  - **Quick check:** What problem does mapping agency-specific codes like "Code 3" to a numeric priority scale solve, and where in the EIDO structure is this enforced?

## Architecture Onboarding
- **Component map:** EIDO Agent → (writes) Shared EIDO-JSON Store; IDX Agent ↔ (reads/writes) Store; Geocoding Agent ↔ Store. FME integration provides EIDOWriter (structured data → EIDO-JSON) and EIDOReader (EIDO-JSON → features) at the boundary.
- **Critical path:** Data ingestion → EIDO Agent structuring → EIDO persisted → IDX Agent correlation (reads new EIDO, queries existing incidents, writes linkage) → Geocoding Agent asynchronous enrichment (reads EIDO, updates location fields). The IDX Agent's scoring loop is the central synchronization point for incident evolution.
- **Design tradeoffs:** Template-based structuring (EIDO Agent) offers configurability but requires SME maintenance; configurable weights/thresholds (IDX Agent) allow tuning but need operational calibration; local gazetteer (Geocoding) improves accuracy for informal locations but requires curation effort. The system favors flexibility and standards compliance over real-time performance guarantees.
- **Failure signatures:**
  - EIDO Agent: Invalid JSON output or missing mandatory fields (check schema validation logs).
  - IDX Agent: High false-positive linking (check score distributions for new EIDOs) or incident fragmentation (many small incidents).
  - Geocoding Agent: Low confidence scores or coordinate jitter (check resolved geometries against raw text).
- **First 3 experiments:**
  1. **Schema compliance test:** Feed a raw CAD record into the EIDO Agent; validate output against the NENA EIDO-JSON schema. Check mapping accuracy for a sample of known legacy-to-standard code translations.
  2. **Linkage threshold sweep:** Ingest a stream of temporally ordered reports from a single known event (e.g., the NWS/news example). Vary τ and measure: (a) number of incidents created vs. expected (1), (b) precision/recall of linking (requires manual labeling of ground-truth links).
  3. **Geocoder comparison:** Take a set of informal location strings from call transcripts. Compare Geocoding Agent's resolved coordinates/confidence against a baseline Google Maps geocoder. Evaluate improvement using local landmark knowledge via precision@1 for known places.

## Open Questions the Paper Calls Out
1. How should the IDX Agent's correlation threshold τ be optimally configured or dynamically adapted for different incident types, jurisdictions, or data source qualities to minimize both false positives (over-aggregation) and false negatives (under-aggregation)?
2. What is the relative effectiveness and operational impact of using semantic similarity (via text embeddings) versus purely temporal or spatial features for incident correlation in real-world, multi-source emergency data streams?
3. How reliably can the Geocoding Agent resolve informal, colloquial, or locally specific location descriptions (e.g., "the big market on Main," "the river bend") into accurate spatial representations without introducing systematic errors that could misinform incident correlation or response?
4. Does the SentinelAI framework's multi-agent, event-sourced model for composite incidents (where a composite view is dynamically computed from linked EIDOs) provide tangible advantages in terms of data integrity, auditability, and system resilience compared to traditional approaches that create or update a single mutable incident record?
5. What are the practical barriers and required workflows for jurisdictions and agencies to adopt the NENA EIDO standard and the SentinelAI reference architecture within their existing, often legacy, emergency dispatch and reporting systems?

## Limitations
- Core parameters (LLM model/prompts, IDX weights/threshold, geocoding gazetteer/APIs) are unspecified, hindering faithful reproduction.
- No quantitative performance metrics (precision/recall, latency) are reported; efficacy relies on a single illustrative case study.
- Operational scalability, maintenance burden, and real-world adoption challenges are not addressed.

## Confidence
- Framework design & interoperability: High
- Agent mechanisms: Medium
- Operational efficacy & scalability: Low
