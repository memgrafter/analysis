# stable-worldmodel-v1: Reproducible World Modeling Research and Evaluation

## Quick Facts
- **arXiv ID:** 2602.08968
- **Source URL:** https://arxiv.org/abs/2602.08968
- **Reference count:** 40
- **Primary result:** Introduces SWM, a modular ecosystem with a unified World API supporting 16 environments and controllable factors of variation; reveals DINO-WM's poor zero-shot robustness (94% on expert data, 12% on random policy data, <20% on most visual/geometric/physical perturbations).

## Executive Summary
World model research suffers from fragmented implementations and inconsistent evaluation, hindering reproducibility. This paper presents stable-worldmodel (SWM), a unified, open-source ecosystem that standardizes core abstractions (World, Policy), supports 16 environments with controllable factors of variation (FoV), and provides planning solvers and evaluation protocols. As a case study, SWM is used to evaluate DINO-WM’s zero-shot robustness, revealing severe performance drops when encountering distribution shifts (e.g., agent color, background). SWM offers superior documentation and testing (73% coverage) compared to existing codebases, aiming to become a community standard for robust and reproducible world model benchmarking.

## Method Summary
SWM defines a `World` object that wraps Gymnasium-compatible environments, manages state (`infos`), and binds a policy. Data collection and evaluation use identical loops: reset → step (with policy action) → record/score. Environments expose a `variation_space` dictionary for fine-grained control over visual, geometric, and physical attributes via `options` during reset/recording. For planning, SWM provides `MPCPolicy` with configurable solvers (CEM, MPPI) and two evaluation protocols: `evaluate` (online sampling of initial/goal states) and `evaluate_from_dataset` (offline, using recorded trajectories). The case study trains DINO-WM on expert demonstrations collected via SWM, then evaluates under various FoV perturbations using MPC with a fixed 50-step budget.

## Key Results
- DINO-WM achieves 94.0% success on expert demonstrations but only 12.0% on random-policy data.
- Across 20+ Push-T factor-of-variation tests, success rates fall below 20% for most perturbations (e.g., agent color 18%, background 10%, agent size 4%).
- SWM provides a reusable, documented ecosystem with 73% test coverage and 16 integrated environments, outperforming existing codebases in documentation and maintenance.

## Why This Works (Mechanism)

**Mechanism 1: Unified World-Policy Interface**  
A decoupled `World` object encapsulates environment execution and state storage (`infos`), while policies implement `get_action`. This separation allows swapping control logic without modifying environment code and ensures identical evaluation loops across environments and policies. The standard loop (reset → step → eval) reduces implementation fragmentation, a major bottleneck in reproducibility.  
*Break condition:* If the overhead of wrapping environments is too high or the community does not adopt the pattern, adoption fails.

**Mechanism 2: Controllable Factors of Variation (FoV)**  
Each environment exposes a tunable parameter space (visual, geometric, physical). During reset/recording/evaluation, `options` inject distribution shifts programmatically. This enables systematic zero-shot robustness studies without altering task logic.  
*Break condition:* If FoV manipulations unintentionally alter task difficulty or dynamics, robustness measurements become confounded.

**Mechanism 3: Bundled Planning and Evaluation Protocols**  
SWM provides `MPCPolicy` with solvers (CEM, MPPI) and fixed evaluation protocols (`evaluate`, `evaluate_from_dataset`). This ensures consistent planning budgets and success criteria across experiments, addressing incomparable evaluation settings.  
*Break condition:* If solvers are inefficient or protocols mismatch a world model’s representation, comparisons may be biased.

## Foundational Learning

**Concept: World-Centric API**  
*Why needed:* All interaction (data collection, evaluation, debugging) funnels through the `World` object. Understanding its `infos` dictionary and synchronous multi-environment stepping is prerequisite.  
*Quick check:* How does adding a new environment to SWM differ from creating a standard Gymnasium environment, and where is the `infos` state populated?

**Concept: Factors of Variation as Configuration Spaces**  
*Why needed:* FoVs are the primary tool for creating robustness tests. Engineers must understand hierarchical naming (e.g., `agent.color`) and how `options` inject distribution shift.  
*Quick check:* To test sensitivity to object size and lighting while fixing colors, how would you configure the `options` dictionary for `PushT`?

**Concept: Goal-Conditioned Evaluation Protocols**  
*Why needed:* SWM defines success via goal reaching. Distinguish between online (sample initial/goal per episode) and offline (sample trajectory, pick states) evaluation, as they measure different capabilities.  
*Quick check:* When would you use `world.evaluate_from_dataset()` instead of `world.evaluate()`, and what does each assume about the data?

## Architecture Onboarding

**Component map**  
World (core) -> Policy (user-defined or MPCPolicy) -> Solver (CEM/MPPI)  
World -> Data (HDF5Dataset)  
World -> Environments (16 IDs, each with variation_space)  
World manages infos, recording, and evaluation loops.

**Critical path**  
1. Instantiate `World(env_id)`.  
2. Attach policy via `world.set_policy()`.  
3. Data collection: `world.record_dataset(name, episodes, options)`.  
4. Training: Load data with `HDF5Dataset`, train model with `get_cost`.  
5. Evaluation: Create `MPCPolicy(solver, config)`, set it, run `world.evaluate()`.

**Design tradeoffs**  
- Standardization vs. Flexibility: Conforming to SWM’s `infos` interface may add friction for novel simulators.
- Ease-of-use vs. Performance: Synchronous, `infos`-centric design simplifies code but limits extreme-scale parallelization.
- Breadth vs. Depth: Supporting 16 environments with FoV may sacrifice physics fidelity compared to specialized single-env codebases.

**Failure signatures**  
- Policy misconfiguration: `get_action` returns wrong shape/NaN, causing silent environment failure.
- FoV mismatch: Specifying non-existent FoV key raises error; forgetting `variation` may yield no distribution shift.
- Evaluation mismatch: Using `evaluate()` with a model trained on expert data may fail due to state-space coverage mismatch (as with DINO-WM’s 12% on random-data goals).
- Test coverage gaps: Untested environment–FoV combinations may produce undefined states.

**First 3 experiments**  
1. Hello World: Run `swm.World('swm/PushT-v1')`, attach random policy, step 10 times, print `infos` keys.
2. FoV Sanity Check: Record two datasets: one with `options={"variation": ["all"]}` and one with `options={"variation": []}`. Visually inspect or check `infos` for changed attributes.
3. Baseline MPC: Use `CEMSolver` with trivial `WorldModelPolicy` (e.g., `get_cost` returns distance to fixed goal). Run `world.evaluate()` to validate end-to-end stack.

## Open Questions the Paper Calls Out

**Open Question 1**  
*Question:* What causes the poor zero-shot robustness of world models to visual, geometric, and physical variations?  
*Basis:* DINO-WM achieves 94% on expert demonstrations but <20% on most factors of variation.  
*Why unresolved:* The study reports performance but does not analyze which components (e.g., visual encoder, dynamics) or representational factors lead to failures.  
*What evidence would resolve:* Ablation experiments isolating model parts, analyzing prediction errors, and comparing latent representations across varied conditions.

**Open Question 2**  
*Question:* How does training data distribution (expert vs. random) affect world model planning performance?  
*Basis:* Success drops from 94% (expert) to 12% (random).  
*Why unresolved:* The drop is noted but not explored whether due to state coverage, dynamics complexity, or other factors.  
*What evidence would resolve:* Controlled experiments measuring state space coverage, dynamics model accuracy, and planning success across datasets with varying policies; using SWM to generate such datasets.

**Open Question 3**  
*Question:* What should a standardized benchmark for controllable world models include to track progress and encourage robustness?  
*Basis:* Authors propose a future standardized benchmark (e.g., Hugging Face Benchmark).  
*Why unresolved:* The design (environments, variations, metrics) is unspecified; unclear what would make it comprehensive and fair.  
*What evidence would resolve:* Community-driven specification, evaluation of candidate environments and metrics, and empirical studies showing the benchmark's ability to differentiate methods and correlate with real-world performance.

## Limitations
- SWM requires environments to conform to its `infos`-based interface, potentially adding friction for integrating novel simulators.
- FoV manipulations may inadvertently alter task difficulty or core dynamics, confounding robustness measurements.
- Reported 73% test coverage leaves gaps; untested environment–FoV interactions may cause silent failures.

## Confidence
- *Infrastructure superiority* (unified API, 16 environments, documentation, testing): **Medium** – supported by internal description and metrics but not independently verified.
- *FoV-driven robustness evaluation*: **Medium** – case study demonstrates usage, but generalizability and potential confounds remain open.
- *DINO-WM empirical results* (94% expert, 12% random, low FoV success): **High** – specific numbers with clear methodology; reproducible within SWM.

## Next Checks
1. **Full DINO-WM replication:** Obtain exact training hyperparameters (vision backbone, latent dimension, optimizer, stable-pretraining schedule) from original work and reproduce all reported success rates. Any discrepancy indicates missing implementation details.
2. **FoV solvability audit:** For each PushT FoV, run a random policy and an oracle policy to verify goal reachability within the MPC budget. If oracle success is near zero for any factor, that factor invalidates robustness conclusions.
3. **Independent quality and adoption audit:** Conduct mutation testing to measure real defect detection rate (beyond line coverage) and analyze GitHub metrics (stars, forks, CI status) over a 6-month period to substantiate maintenance and community impact claims.
