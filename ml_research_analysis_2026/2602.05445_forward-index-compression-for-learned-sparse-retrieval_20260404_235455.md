# Forward Index Compression for Learned Sparse Retrieval
## Quick Facts
- **arXiv ID**: 2602.05445
- **Source URL**: https://arxiv.org/abs/2602.05445
- **Reference count**: 25
- **Primary result**: DotVByte reduces forward index size by up to 22% while being 3× faster than StreamVByte and only 20% slower than uncompressed, maintaining retrieval accuracy on MsMarco.

## Executive Summary
The forward index in learned sparse retrieval systems consumes significant memory, hindering deployment. This paper evaluates integer compression techniques for the forward index and introduces DotVByte, an enhanced version of StreamVByte optimized for inner product computation via SIMD and per-document alignment. On the MsMarco dataset with Splade and LiLsr models, DotVByte reduces the forward index size by up to 22% compared to uncompressed storage, adds only 20% query latency relative to uncompressed, and is three times faster than the baseline StreamVByte, all while preserving retrieval accuracy. The combination of RGB permutation for gap reduction and DotVByte's decoding optimizations yields the best known trade-off between memory footprint, latency, and accuracy.

## Method Summary
The authors compress the components array (term IDs) of learned sparse vectors using variable-length integer coding after optional permutation via Recursive Graph Bisection (RGB). Their key contribution is DotVByte, which redesigns StreamVByte in three ways: it uses 16-bit components to decode eight values per SIMD register, fuses decoding with arithmetic via gather-multiply-add operations entirely in registers, and enforces per-document alignment on control-byte boundaries to avoid cross-document partial decoding. Values may be stored as 16-bit floats or 8-bit fixed-point. The compression modules plug into the Seismic approximate nearest neighbor index, where they are used for exact re-ranking of candidate documents. The evaluation focuses on memory usage (bits per component), inner product scan time, and retrieval recall.

## Key Results
- DotVByte reduces forward index size by up to 22% compared to uncompressed storage.
- Query latency is only 20% higher than uncompressed and 3× faster than StreamVByte.
- Retrieval accuracy is maintained; DotVByte achieves the best trade-off between size, latency, and recall.

## Why This Works (Mechanism)
The paper’s success hinges on three mechanisms. First, integer compression algorithms (e.g., VByte, Elias, Zeta, StreamVByte) encode gaps between consecutive sorted component indices; the average gap size determines compression ratio, while decoding cost varies with algorithm complexity. Learned sparse vectors exhibit small gaps after RGB permutation, making them highly compressible. Second, DotVByte overcomes StreamVByte’s generic decoding overhead by exploiting SIMD: 16-bit components allow eight values per register, inner products are computed directly in registers without intermediate writes, and per-document alignment eliminates cross-document partial decoding. Third, RGB permutation reorders the vocabulary by recursively bisecting the document-term bipartite graph to cluster co-occurring terms, further shrinking gaps and improving compression for all algorithms. Experiments confirm that these mechanisms jointly yield superior size-latency trade-offs.

## Architecture Onboarding
**Component map**  
Seismic ANN Index → Forward Index Storage (components, values, offsets) → Compression Module (e.g., DotVByte) → Query Processor. Configuration parameters influence all components.

**Critical path**  
1. Query encoded to sparse vector.  
2. Seismic uses inverted index to retrieve candidate docIDs.  
3. Offsets locate each candidate's compressed component/value stream.  
4. Compression decoder processes the stream: decodes term IDs, gathers query values, multiplies by document values, accumulates inner products.  
5. Results sorted; top‑k returned.  
Step 4 is the latency bottleneck targeted by DotVByte.

**Design tradeoffs**  
- Size vs. speed: Zeta compresses best but decodes slowest; StreamVByte is fast but larger; DotVByte aims for near‑uncompressed speed with moderate compression.  
- Compression vs. accuracy: Aggressive value quantization (fixedU8) may harm recall.  
- Indexing time: RGB permutation adds one‑time O(n log n) cost.  
- Implementation complexity: DotVByte’s SIMD and alignment logic is more complex.

**Failure signatures**  
- High query latency: slow decoder (e.g., Zeta) or software floating‑point emulation for values.  
- Accuracy drop: over‑aggressive value compression or detrimental RGB permutation.  
- Excessive index size: inappropriate algorithm for the data or padding from alignment.  
- Build failure: RGB may not scale to very large vocabularies.

**First 3 experiments**  
1. **Baseline measurement**: Build Seismic with uncompressed forward index; record query latency and index size.  
2. **Compression comparison**: Test components compression (Zeta, StreamVByte, DotVByte) with/without RGB; measure size, scan time, and Recall@100. Expect DotVByte to be within 20 % latency of uncompressed with ~10 % size reduction.  
3. **Value representation**: For DotVByte, compare float16 vs. fixedU8 for values; assess size reduction and recall loss at target accuracies (e.g., 97 %, 99 %).

## Open Questions the Paper Calls Out
**Open Question 1**  
Can DotVByte be extended with sub‑byte encoding for small gaps to improve compression ratio without excessive latency? The authors propose incorporating sub‑byte capability for frequent small dgaps.

**Open Question 2**  
To what extent are the reported results generalizable to other retrieval datasets (e.g., TREC DL, ClueWeb) and learned sparse models (e.g., SPLADE v2, DeepCT)? Evaluation was limited to MsMarco with two models.

**Open Question 3**  
Can joint compression of components and values outperform separate compression, achieving a better trade‑off between index size and retrieval accuracy? Separate compression ignores possible correlations between term positions and values.

## Limitations
- **Reproducibility gaps**: Exact RGB hyperparameters and query sampling are unspecified; these affect reported numbers.
- **External validity**: Results are limited to MsMarco with Splade/LiLsr; generalizability to other models/datasets/hardware is unknown.
- **Implementation sensitivity**: DotVByte’s 3× speedup relies on precise control-byte handling and SIMD fusion; minor deviations may degrade benefits.

## Confidence
- DotVByte achieves near‑uncompressed speed with ~10–22 % size reduction on MsMarco/Splade: **High**.
- RGB permutation consistently improves compression ratios across algorithms: **Medium**.
- DotVByte provides the best latency‑size trade‑off among all sparse retrieval compression methods: **Low**.
