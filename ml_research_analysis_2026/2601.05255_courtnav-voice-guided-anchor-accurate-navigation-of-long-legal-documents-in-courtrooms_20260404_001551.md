# CourtNav: Voice-Guided, Anchor-Accurate Navigation of Long Legal Documents in Courtrooms

## Quick Facts
- **arXiv ID:** 2601.05255
- **Source URL:** https://arxiv.org/abs/2601.05255
- **Reference count:** 11
- **Primary result:** Voice-guided navigation reduces median time-to-relevance from 3–5 minutes to 10–15 seconds for direct jumps, with strict-hit F1 of 0.92, while increasing breadth of record consulted under time pressure.

## Executive Summary
CourtNav is a voice-driven system designed to help judges quickly locate specific passages within lengthy legal documents during hearings. It converts spoken commands (e.g., “go to paragraph 23”) into precise, highlighted document locations by combining layout-aware indexing, a hybrid retrieval system (lexical BM25 + dense vectors), and an LLM-backed router. A pilot on Indian legal documents demonstrated dramatic reductions in navigation time and high accuracy in retrieving correct anchors, enabling judges to consult more of the record without sacrificing verification transparency.

## Method Summary
The system begins with a layout-aware ingest pipeline that parses PDFs (scanned or born-digital) into minimal displayable anchors—paragraphs, headings, table cells—each with stable geometric metadata (page, bounding box, span ID). Two parallel indices are built: a lexical BM25 index (Elasticsearch) optimized for exact legal terms and a dense vector index (Milvus) using sliding windows to preserve local context. At query time, a grammar-first router first attempts regex matching for predictable commands (e.g., temporal references); failures trigger an LLM for structured intent classification. Hybrid retrieval combines scores from both indices (α=0.7), deduplicates by anchor overlap, and maps results back to canonical anchors. A fine-tuned Whisper ASR transcribes voice, with a confirmation loop before the PDF.js-based viewer scrolls and highlights the target anchors.

## Key Results
- Time-to-relevance dropped from 3–5 minutes (manual PDF navigation) to 10–15 seconds for direct jumps, and 30–45 seconds including visual verification.
- Hybrid retrieval achieved a strict-hit F1 score of 0.92 at the anchor level.
- Under fixed time budgets, the navigation-first design increased the breadth of the record consulted while maintaining full auditability via anchored evidence.

## Why This Works
### Mechanism 1: Grammar-first command router
A two-tiered router first matches spoken queries against a compact grammar (regex/slot-filling) for high-frequency, structured intents (e.g., “go to paragraph X”). Only on failure or ambiguity does a lightweight LLM back-off produce a structured action with few-shot examples. This ensures low latency and determinism for the majority of predictable judicial commands while handling edge cases. Core assumption: a substantial portion of in-hearing commands are anchor-specific and follow a repetitive grammar. Evidence: [abstract] and [section 3.2] describe the grammar-first, LLM-backed design; related work (CaseHOLD, LeCaRD) focuses on document-level tasks, highlighting the need for granular command parsing. Break condition: queries outside grammar scope combined with LLM misclassification or ASR noise can cause failures; limitations note “absolute guarantees are impossible.”

### Mechanism 2: Layout-aware indexing and anchor mapping
During ingest, every minimal displayable unit is treated as an anchor with stable coordinates (page, bbox, span_id, type). This layout metadata is stored alongside text. At retrieval, text offsets from results are mapped back to these anchors using tolerant matching, enabling the viewer to scroll and highlight exact source locations. Core assumption: legal documents have a stable logical structure that can be normalized and is essential for verification. Evidence: [section 3.1] defines anchors; [section 3.3] describes deterministic mapping; [section 3.5] enforces anchored evidence. Break condition: ingest failures on complex layouts (multi-column, hyphenation, poor OCR) lead to mismatched mappings; limitations note responsiveness issues for documents >350 pages.

### Mechanism 3: Hybrid retrieval with late-interaction sliding windows
Parallel lexical (BM25) and dense vector indices are queried; results are interleaved and deduplicated by anchor overlap before optional re-ranking. The dense index uses overlapping paragraph windows to preserve context for semantic queries, while lexical search handles exact citations. This hybrid design targets both anchor-pointing (“paragraph 23”) and content-seeking (“contradiction about call records”) queries. Core assumption: legal queries bifurcate into exact-reference and descriptive modes. Evidence: [section 3.3] details hybrid retrieval; [section 4.2] reports strict-hit F1=0.92 for the late-window+keyword variant. Break condition: suboptimal weighting (α=0.7) or window size introduces noise for highly localized queries.

## Architecture Onboarding
ASR Service -> Router Service (Grammar/LLM) -> Hybrid Retrieval (Elasticsearch + Milvus) -> Anchor Mapper -> Viewer. Ingest Pipeline (layout parser -> anchor generation) feeds both indices.
Critical path: Voice -> ASR -> Router -> Retrieval (Hybrid) -> Anchor Mapper -> Viewer. Latency dominated by retrieval.
Design tradeoffs: Grammar-first vs. LLM-only (speed/determinism vs. coverage); late-window dense indexing (context vs. noise); enforced audit trail (trust/verifiability vs. no synthesis).
Failure signatures: Routing failure (LLM returns “unknown”/low confidence); Retrieval failure (no anchors pass threshold); Mapping failure (OCR drift causes span mismatch); ASR failure (high WER on jargon).
First 3 experiments: 1. Grammar Coverage Test: run 100 real logged queries through grammar parser alone; target >70% coverage, 0% false positives. 2. Ablation Retrieval Benchmark: compare F1 for keyword-only, dense-only (fixed-chunk), dense-only (late-window), hybrid (α=0.7). 3. End-to-End Latency & TTR Simulation: script 20 mixed queries on a 100-page doc; target <15s for temporal, <10s for contextual (retrieval-only), <45s with verification.

## Open Questions the Paper Calls Out
1. **Parameter optimization across domains**: Can α=0.7 be generalized for diverse legal document types and query families? Basis: α fixed for pilot corpus; unknown generalizability to common vs. civil law systems. Evidence needed: Systematic ablation varying α across multiple legal datasets (e.g., US federal, EU directives) measuring strict-hit F1 and latency per query type.
2. **Robustness to real-world speech**: How does the router handle malformed, heavily accented, or code-switched commands in noisy courtrooms without human confirmation? Basis: Limitations note ASR errors “non-negligible” and LLM stochasticity; pilot may not capture spontaneous stressed speech. Evidence needed: Field recordings from live hearings evaluating intent classification accuracy with/without confirmation loops, measuring false positives/negatives in time-sensitive scenarios.
3. **Scalability to massive records**: How does navigation-first design affect efficiency and judicial cognition for >350-page documents given viewer performance decline? Basis: Limitations state responsiveness “declines” beyond 350 pages; many Indian cases exceed thousands of pages. Evidence needed: Scalability benchmark with 500–2000 page docs measuring TTR, scroll/render latency, memory; longitudinal study on judge satisfaction with custom viewer.
4. **Judge-in-the-loop feedback**: Can a feedback mechanism iteratively improve models without disrupting workflow? Basis: Feedback system identified as missing and “essential” for improving query classification. Evidence needed: Design/minimally intrusive feedback UI (e.g., voice “that’s wrong,” dwell-time signals) in field trial, measuring performance drift correction and judicial burden.
5. **Impact on holistic understanding**: Does anchor-accurate, evidence-first design discourage broader context exploration, leading to fragmented case comprehension? Basis: Evaluation measures TTR and strict-hit, not downstream comprehension; system prioritizes pinpoint over holistic reading. Evidence needed: Controlled study comparing comprehension (quizzes, decision memo quality) and citation breadth between CourtNav and traditional reading over multi-session hearings.

## Limitations
- **Unrealized scalability**: Viewer performance degrades for documents >350 pages; many legal records exceed this, risking loss of time savings.
- **Generalizability**: Evaluation limited to Indian legal documents; applicability to other jurisdictions (e.g., US/UK with different structures) is unproven.
- **Grammar coverage ceiling**: Assumes large portion of commands follow predictable grammar; no breakdown of 100k+ corpus by type, leaving coverage target speculative.

## Confidence
- **High**: Layout-aware indexing and anchor mapping mechanism; strict-hit F1=0.92; grammar-first router design.
- **Medium**: Real-world time savings from single-site pilot; hybrid retrieval (α=0.7) optimality claim.
- **Low**: System behavior on multi-jurisdiction documents; true ceiling of grammar coverage in varied discourse; long-document (>500p) stability.

## Next Checks
1. **Grammar coverage test**: Run the logged 100k+ command corpus through *only* the grammar parser; report exact coverage % and failure modes (e.g., “exhibit 5” vs. “the fifth exhibit”).
2. **Cross-dataset hybrid tuning**: Re-run retrieval ablation (F1 benchmark) on a held-out set of US federal court PDFs; tune α and window size; report delta from claimed F1=0.92.
3. **Stress-test large docs**: Process a 600-page mixed-format Indian case file; measure end-to-end latency, memory footprint, and viewer scroll/render time; verify if 350-page limitation is hard or observed threshold.
