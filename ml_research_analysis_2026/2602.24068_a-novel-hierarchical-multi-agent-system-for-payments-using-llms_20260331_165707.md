# A Novel Hierarchical Multi-Agent System for Payments Using LLMs

## Quick Facts
- **arXiv ID:** 2602.24068
- **Source URL:** https://arxiv.org/abs/2602.24068
- **Reference count:** 25
- **Primary result:** HMASP achieves feasible end-to-end agentic payments with task success rates ≥95.6% (Qwen2.5:32b) and near-perfect (GPT-4.1), demonstrating the first LLM-based multi-agent system for complete payment workflows.

## Executive Summary
The paper addresses a critical gap: existing LLM agents cannot perform end-to-end payment workflows. It introduces the Hierarchical Multi-Agent System for Payments (HMASP), a modular architecture with four agent levels (Conversational Payment Agent, Supervisors, Routing, Process Summary) that uses structured handoffs and shared state variables to coordinate tasks. Evaluation on a 1000-point proprietary dataset shows HMASP achieves high task success rates (≥95.6% for Qwen2.5:32b, up to 100% for GPT-4.1) and accurate agent handoffs (F1-scores up to 99.0%). This demonstrates HMASP as the first LLM-based multi-agent system capable of supporting complete agentic payment workflows.

## Method Summary
HMASP is built on LangGraph and employs a hierarchical agent structure: a top-level Conversational Payment Agent (CPA) classifies user requests and delegates to domain-specific Supervisors; Supervisors forward to Routing agents that trigger task-specific subgraphs (e.g., card registration); finally, a Process Summary agent formats the outcome. Crucially, the system isolates sensitive data using role-specific state classes (PayAgentState, CardsState, PaymentState) with a minimal set of shared variables (e.g., user ID) and uses deterministic validation functions inside subgraphs. Human-in-the-loop interrupts handle sensitive inputs (e.g., OTP) by pausing the workflow, validating user responses, and resuming. This design modularizes decision-making while ensuring data integrity and security.

## Key Results
- Task success rates for Qwen2.5:32b reach ≥95.6% across all four tasks; agent handoff F1-scores up to 99.0%.
- GPT-4.1 achieves near-perfect results (99.6%-100% success and handoff F1).
- HMASP is the first LLM-based multi-agent system to demonstrate end-to-end agentic payment workflows.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** A hierarchical, role-based agent structure enables reliable modular execution of diverse payment workflows by isolating decision-making and delegation.
- **Mechanism:** The CPA acts as a single entry point, classifying requests and delegating to domain-specific Supervisors. Supervisors then delegate to Routing agents, which trigger specific task workflows (e.g., card registration). This creates a clear chain of command and scope, where each agent level handles a distinct abstraction (conversation -> domain orchestration -> workflow execution).
- **Core assumption:** LLM-based classification and delegation at each level can be sufficiently reliable to route requests correctly to the appropriate downstream workflow.
- **Evidence anchors:**
  - [abstract]: "modular architecture consisting of the Conversational Payment Agent (CPA - first agent level), Supervisor agents (second agent level), Routing agents (third agent level), and the Process summary agent (fourth agent level)."
  - [section 3.1]: "Agents were prompted on their roles, expected responses, possible handoffs, and tasks that are within their scope."
  - [corpus]: Weak evidence. Corpus shows related work on hierarchical MAS for other domains but does not directly evaluate HMASP's routing logic.
- **Break condition:** If the CPA or Supervisor agents frequently misclassify inputs and route to the wrong domain/workflow (evidenced by low task success rates for relevant inputs and/or low handoff F1-scores from CPA-to-Supervisor, as seen with Llama3.1 models on Task 4 in Table 2).

### Mechanism 2
- **Claim:** Isolated, role-specific state variables with carefully defined shared variables ensure information determinism and security by preventing cross-agent data contamination and LLM hallucination of critical payment data.
- **Mechanism:** The system defines separate state classes (PayAgentState, CardsState, PaymentState). Agents/modules only read/write their assigned state. A limited set of shared variables (e.g., user ID, card ID) are explicitly defined and passed between states. Critical information (like validated card numbers) is stored in state variables and retrieved by functions, not regenerated by LLMs.
- **Core assumption:** Enforcing strict state access controls within the orchestration framework (LangGraph) is sufficient to isolate sensitive data and prevent LLM-based agents from altering or fabricating persisted payment information.
- **Evidence anchors:**
  - [section 3.2]: "Agents and modules can only access their assigned states, preventing unauthorized read or write across state variables... This ensures modularity, where only necessary information is propagated and all other sensitive information is isolated."
  - [section 3.3]: "State Variables for Determinism. User input information and certain workflow outputs are stored in state variables to enforce information determinism and persistence... critical information needed to complete workflows can never be tampered or hallucinated."
  - [corpus]: Missing. Corpus papers focus on protocol security (AP2) or different agent architectures; they do not evaluate state isolation patterns.
- **Break condition:** If validation failures or security audits reveal leakage of sensitive PCI-like data (e.g., full card numbers) into non-payment state contexts or message histories, or if workflow failures occur because a state variable was overwritten or not correctly retrieved by a downstream function module.

### Mechanism 3
- **Claim:** Structured handoffs combined with an interrupt-based human-in-the-loop mechanism provide a reliable coordination pattern that separates LLM-driven conversational control from deterministic, validated payment operations.
- **Mechanism:** Agents use explicit "handoff" commands within LangGraph to pass the conversation and control to the next agent in the hierarchy. For operations requiring sensitive user input (e.g., card details), the workflow triggers an `interrupt`, pausing execution. The system then collects natural language input, runs it through validation functions (e.g., Luhn check), stores the result in the state, and resumes.
- **Core assumption:** The orchestration framework's handoff and interrupt primitives are robust enough to manage control flow reliably, and that validation functions can cleanly separate from LLM reasoning to ensure data integrity.
- **Evidence anchors:**
  - [section 3.1]: "We implemented structured handoffs using LangGraph... Agents will decide where to handoff to based on the input."
  - [section 3.3]: "We utilized LangGraph’s interrupt mechanism for persistent and reliable human-in-the-loop... Users can then respond in natural language, and the respond goes through a series of validation and checks... Upon successful validation, the workflow resumes."
  - [corpus]: Indirect. Related papers on "agentic payment protocols" (e.g., AP2) discuss authorization but not this specific interrupt/handoff pattern for LLM coordination.
- **Break condition:** If the interrupt mechanism fails to pause/resume workflows correctly, or if validation functions reject valid user input due to poor parsing, causing unnecessary workflow termination (evidenced by Process Summary agents generating error responses for what should be valid, interrupt-driven tasks).

## Foundational Learning
#### Concept: Role-Based Multi-Agent Systems
- **Why needed here:** HMASP's core innovation is its strict hierarchical roles (CPA, Supervisor, etc.). Understanding why roles are defined and how they delegate is key to grasping the architecture's modularity and failure modes.
- **Quick check question:** What is the primary risk if the CPA agent's role prompt is ambiguous about its delegation responsibility to Supervisors?

#### Concept: State Management in Distributed/Workflow Systems
- **Why needed here:** The entire determinism and security argument hinges on the careful design of shared vs. isolated state variables. Misunderstanding this leads to believing LLMs handle sensitive data directly.
- **Quick check question:** Why is storing a validated card number in a state variable safer than having a Routing agent's LLM generate that number in its response to the Supervisor?

#### Concept: Payment Processing Workflows (Tokenization, 3DS, etc.)
- **Why needed here:** To understand what "end-to-end" means in this context and why the paper's simulation decouples "payment modules." It contextualizes the functional modules (like `Authorize 3DS`) mentioned as subgraphs.
- **Quick check question:** In a real payment, why would a merchant agent not directly call a payment API with a user's raw card number, and how might HMASP's state pattern relate to that constraint?

## Architecture Onboarding
- **Component map:**  
  User -> CPA (Level 1) -> Supervisor (Level 2) -> Routing (Level 3) -> Task Workflow Subgraph -> Process Summary (Level 4) -> Supervisor -> CPA -> User  
  States: PayAgentState (CPA), CardsState (Card Supervisor/Routing), PaymentState (Payment Supervisor/Routing) with shared_vars (user_id, card_id, etc.)  
  Orchestration: LangGraph manages state machine, handoffs, interrupts.

- **Critical path (successful payment request):**  
  1. User says "Buy item X" to CPA.  
  2. CPA hands off to Payments Supervisor.  
  3. Payments Supervisor hands off to Payment Routing agent.  
  4. Payment Routing invokes Payment Workflow subgraph.  
  5. Subgraph executes: get payment methods, select method, initiate authorization, handle 3DS (interrupt for OTP).  
  6. Subgraph completes; Process Summary formats success.  
  7. Message flows back up to CPA.  
  8. CPA responds "Payment successful."

- **Design tradeoffs:**  
  - Hierarchy vs. Latency: 4-level handoff adds overhead but provides modularity and failure isolation.  
  - State Isolation vs. Convenience: Strict scoping enhances security but increases development complexity.  
  - LLM Autonomy vs. Determinism: LLMs handle routing/conversation; critical data changes are deterministic code, limiting LLM creativity where it matters.

- **Failure signatures:**  
  - Task failure: Routing agent triggers wrong workflow or workflow terminates early (check handoff F1 from Supervisor to workflow).  
  - Spurious handoff: CPA incorrectly delegates irrelevant requests (check CPA handoff F1 on irrelevant tasks).  
  - State inconsistency: Workflow uses wrong card/user ID (trace shared state after input).  
  - Interrupt stall: Workflow pauses at interrupt and never resumes (check if user response is routed correctly).

- **First 3 experiments:**  
  1. **Irrelevant Input Rejection:** Feed 25 "joke"/"weather" queries. Verify CPA rejects 100% without handoff (high F1 on Task 4).  
  2. **Single-Task Routing Fidelity:** For Task 1 ("register new card"), feed 25 clear requests. Trace handoff path: CPA -> Cards Supervisor -> Card Registration Routing. Verify all 25 follow this path.  
  3. **Interrupt & State Persistence:** Use Task 3 payment requiring OTP. After interrupt, provide valid OTP. Verify: (a) payment_state contains correct transaction ID after resume, (b) final summary includes correct last 4 digits from CardsState.

## Open Questions the Paper Calls Out
- **Open Question 1:** How does HMASP's performance scale with larger, more diverse datasets that capture complex, real-world payment workflows and user intents? The paper acknowledges its 1000-point dataset is small and may not fully capture complexity; future work includes testing on larger datasets.
- **Open Question 2:** What specific architectural patterns or mechanisms can be integrated to provide robust, payment-centric security guardrails while maintaining modularity and coordination efficiency? The paper mentions future work on security guardrails and tokenization of sensitive information within state variables.
- **Open Question 3:** How does the hierarchical, role-based architecture of HMASP compare to alternative multi-agent coordination protocols (e.g., peer-to-peer, swarm, consensus) for payment workflows in terms of reliability, latency, and error recovery? The paper calls for a comparative study of agentic architectures and protocols.
- **Open Question 4:** To what extent do production-grade payment infrastructure constraints—such as real-time fraud detection, 3D-Secure, and regulatory compliance (PCI DSS, PSD2)—impact HMASP's viability and performance when integrated with actual payment rails? The paper notes production complexities are expected to affect latency and are not yet evaluated.

## Limitations
- Proprietary 1000-point dataset limits external validation and may not capture real-world complexity.
- Exact agent system prompts and simulated payment module implementations are unspecified, hindering faithful reproduction.
- Evaluation conducted in a simulated environment; performance on live payment gateways with network latency, failures, and compliance checks remains unknown.

## Confidence
- **High**: HMASP achieves ≥95.6% task success on its proprietary dataset with strong models (Qwen2.5:32b, GPT-4.1) and high handoff F1-scores (up to 99.0%).
- **Medium**: The hierarchical architecture and state isolation patterns are conceptually sound and align with workflow best practices, but lack production validation.
- **Low**: Claims of being the "first" and demonstrating generalizable "end-to-end agentic payments" are premature without public datasets, open-source release, or integration tests with actual financial APIs.

## Next Checks
1. **Dataset Independence Test:** Re-evaluate HMASP using a new, publicly available transaction intent dataset (e.g., subset of MultiWOZ with payment dialogues) to assess overfitting to the authors' data distribution.
2. **Prompt Ablation Study:** Systematically vary the specificity of the CPA's delegation prompt to quantify sensitivity to role ambiguity, measuring resulting handoff F1-score changes.
3. **Real-API Stress Test:** Deploy the Routing agents' subgraphs against a sandboxed payment processor (e.g., Stripe test mode) to measure failure rates under network timeouts, API errors, and malformed user inputs.
