# SQL-Trail: Multi-Turn Reinforcement Learning with Interleaved Feedback for Text-to-SQL

## Quick Facts
- **arXiv ID:** 2601.17699
- **Source URL:** https://arxiv.org/abs/2601.17699
- **Reference count:** 40
- **Primary result:** Achieves state-of-the-art execution accuracy on BIRD/Spider, with 7B/14B models outperforming larger proprietary systems by 5% on average and up to 18× higher data efficiency.

## Executive Summary
SQL-Trail introduces a multi-turn reinforcement learning framework for Text-to-SQL that replaces single-pass generation with interactive database probing and execution feedback. Its core innovations are an adaptive turn-budget allocation matching query difficulty and a composite reward panel combining execution correctness with efficiency incentives. On BIRD and Spider benchmarks, SQL-Trail achieves state-of-the-art execution accuracy, with 7B/14B models outperforming larger proprietary systems by 5% on average. Notably, it delivers up to 18× higher data efficiency than prior single-pass RL methods, gaining 4.6% EX per 1,000 training samples on BIRD-dev while using under 2,000 examples.

The method employs a two-stage training pipeline: first, supervised fine-tuning (SFT) distills multi-turn agent behavior from a teacher model (Claude Sonnet) into a base LLM; second, reinforcement learning with Group Relative Policy Optimization (GRPO) fine-tunes the agent using a composite reward that encourages correctness, efficiency, and proper formatting. This interactive paradigm allows the agent to iteratively test and debug queries, leading to robust performance on complex, ambiguous schemas.

## Method Summary
SQL-Trail uses a two-stage pipeline. Stage 1: SFT generates 1,000 correct multi-turn trajectories from 3,000 Spider-train questions using Claude Sonnet (max 10 turns). These trajectories are used to fine-tune a base LLM (Qwen2.5-Coder 3B/7B/14B) with standard language modeling objective (2 epochs, lr=1e-5). Stage 2: RL starting from the SFT checkpoint. For each of 1,027 curated questions (700 difficulty-balanced + 327 exploration), the agent generates 6 rollouts (temperature 1.0, top-p 0.99, max turns 10). A composite reward combines: 5× execution correctness, 2× turn efficiency (if within difficulty-dependent threshold), and unit weights for schema grounding, bigram overlap, syntax validity, and format compliance. GRPO with asymmetric clipping updates the policy. Training runs for 108 steps with lr=1e-6.

## Key Results
- State-of-the-art execution accuracy on BIRD and Spider benchmarks; 7B/14B models outperform larger proprietary systems by 5% on average.
- Up to 18× higher data efficiency than prior single-pass RL methods: gains 4.6% EX per 1,000 training samples on BIRD-dev.
- Effective adaptive turn-budget allocation: agent uses fewer turns on simpler queries and more on hard ones, balancing accuracy and efficiency.

## Why This Works (Mechanism)
### Mechanism 1: Iterative Database Probing and Execution Feedback
- **Claim:** Iterative database probing and execution feedback enable the agent to correct errors, refine hypotheses, and better understand schema complexity, leading to higher accuracy on challenging queries.
- **Mechanism:** The agent operates in a closed loop: generate reasoning and SQL, execute against database, receive observation (result set or error), and adjust subsequent reasoning/queries. This mimics human expert behavior of testing intermediate results and debugging.
- **Core assumption:** Human experts rely on such iterative interaction; emulating this in an LLM agent improves performance on complex, ambiguous, or noisy schemas.
- **Evidence anchors:** Abstract states "replaces single-pass generation with interactive database probing and execution feedback." Section 1 describes human experts "iteratively interact with the database... decompose complex problems... refine or debug their queries based on execution feedback." Corpus neighbors (MTIR-SQL, MTSQL-R1) also investigate multi-turn RL with tool integration.
- **Break condition:** If database environment inaccessible or execution feedback delayed/noisy, the loop may become ineffective or cause infinite loops. Agent must correctly interpret observations; misparsing errors can entrench mistakes.

### Mechanism 2: Adaptive Turn-Budget Allocation
- **Claim:** Adaptive turn-budget allocation matches interaction depth to query difficulty, improving efficiency without sacrificing accuracy.
- **Mechanism:** Agent receives a turn reward only if it solves the query within a difficulty-dependent threshold (e.g., ≤2 turns for simple, ≤3 for medium, more for hard). This incentivizes concise solutions for easy questions while allowing sufficient exploration for hard ones.
- **Core assumption:** Query difficulty can be categorized (simple/medium/hard) and thresholds can be set appropriately; the agent will learn to allocate effort accordingly.
- **Evidence anchors:** Abstract mentions "adaptive turn-budget allocation matching query difficulty." Section 3.3.2 defines turn reward with explicit thresholds per difficulty. Figure 4 empirically shows agent taking more turns on harder queries and fewer on easier ones.
- **Break condition:** Inaccurate difficulty estimation (e.g., misclassifying a hard query as simple) may force premature termination. Thresholds too tight discourage necessary exploration; too loose may encourage overthinking.

### Mechanism 3: Composite Reward Panel
- **Claim:** A composite reward panel provides dense, multi-faceted supervision that guides the agent toward correct, efficient, and well-formed SQL, overcoming the sparsity of binary execution rewards.
- **Mechanism:** Total reward combines six terms: execution correctness (primary), turn count (efficiency), and auxiliary shaping rewards (syntax validity, schema grounding, bigram overlap, format compliance). Weighted sum (5× execution, 2× turns, others unit) balances end-task success with intermediate behavioral signals.
- **Core assumption:** Execution-only reward is too sparse for multi-turn RL; auxiliary rewards densify the signal without introducing harmful biases if properly weighted.
- **Evidence anchors:** Abstract mentions "composite reward panel combining execution correctness with efficiency incentives." Section 3.3.2 details each term and weighting. Ablation studies (Table 6) show removing bigram or turn reward degrades performance, confirming contribution.
- **Break condition:** Poorly weighted auxiliary rewards may cause reward hacking (e.g., optimizing for bigram overlap without semantic correctness). Some rewards become redundant when others are strong, suggesting careful tuning required. Over-reliance on auxiliary signals could reduce generalization.

## Architecture Onboarding
**Component map:**  
Multi-turn Rollout Engine -> SFT Module -> RL Module -> Reward Calculator -> Difficulty Categorizer

**Critical path:**  
1. Input (question, schema) is fed to the agent.  
2. Agent emits <reasoning> and <sql>; system extracts and executes SQL.  
3. Observation (result or error) is returned and appended to context.  
4. Steps 2–3 repeat until <solution> is emitted or turn limit reached.  
5. Final SQL is executed; reward is computed across all rollout group members.  
6. GRPO update uses group-relative advantages to adjust policy parameters.

**Design tradeoffs:**  
- Multi-turn accuracy vs. latency: More turns improve robustness but increase inference cost and database load.  
- Turn-budget strictness: Tight thresholds boost efficiency but risk premature termination on hard queries; loose thresholds waste resources.  
- Reward weighting: Heavier execution weight ensures primary goal, but auxiliary terms require tuning to avoid reward hacking (e.g., bigram similarity gaming).  
- SFT cold-start: Provides stable initialization for RL but may bias toward teacher’s suboptimalities; RL without SFT can be unstable.

**Failure signatures:**  
- Excessive turns with low accuracy: agent stuck in loops or failing to learn from errors.  
- Repeated formatting errors: agent not adhering to <reasoning>/<sql>/<solution> tags, breaking the rollout loop.  
- High syntax error rate: agent not internalizing SQL grammar despite execution feedback.  
- Poor cross-domain generalization: overfitting to training schemas; low performance on BIRD if trained only on Spider.  
- Auxiliary reward dominance: high bigram/schema scores but low execution accuracy indicates reward hacking.

**First 3 experiments:**  
1. **Format compliance sanity check:** Run the SFT model on 10 diverse examples with max turns=1. Verify that outputs strictly follow the required tag structure and produce executable SQL. This confirms the system prompt and parsing logic work.  
2. **Turn reward ablation:** Train two RL models on a small subset (e.g., 200 examples) with and without the turn reward. Compare average turns per query and execution accuracy on a held-out set. Expect the version with turn reward to use fewer turns without sacrificing accuracy.  
3. **Multi-turn vs. single-pass comparison:** Using identical base model and RL hyperparameters, train a single-pass RL agent (no tool calls) and the full multi-turn agent on the same 700-difficulty-balanced set. Evaluate on BIRD-dev (out-of-distribution) to verify that multi-turn yields a meaningful accuracy gap (as in Table 2).

## Open Questions the Paper Calls Out
### Open Question 1: Can multi-turn Text-to-SQL agents operate without real-time database execution?
- **Question:** Can multi-turn Text-to-SQL agents operate without real-time database execution?
- **Basis in paper:** Explicitly states that the interactive execution environment is infeasible in settings with restricted connectivity, strict privacy controls, or expensive query execution (Limitations).
- **Why unresolved:** The iterative refinement process fundamentally relies on execution feedback; removing it prevents self-correction and limits deployment scenarios.
- **What evidence would resolve it:** Develop neural simulators that predict execution results or architectures that internalize feedback without external database calls.

### Open Question 2: How can we reduce the computational overhead of multi-turn Text-to-SQL agents?
- **Question:** How can we reduce the computational overhead of multi-turn Text-to-SQL agents?
- **Basis in paper:** Explicitly notes that multi-turn interaction increases inference cost and latency (more tokens, more database calls) (Limitations).
- **Why unresolved:** Adaptive turn-budget allocation mitigates but does not eliminate worst-case overhead compared to single-pass systems.
- **What evidence would resolve it:** Measure token/turn trade-offs across difficulty levels; design early-exit mechanisms or response compression that preserve accuracy.

### Open Question 3: How can reward design in multi-turn RL for Text-to-SQL avoid spurious correlations and inductive biases?
- **Question:** How can reward design in multi-turn RL for Text-to-SQL avoid spurious correlations and inductive biases?
- **Basis in paper:** Explicitly warns that reward shaping can introduce inductive biases and RL optimization may exploit spurious correlations (Limitations).
- **Why unresolved:** Lexical rewards (e.g., bi-gram similarity) may encourage superficial matches over semantic correctness; turn reward may incentivize truncation.
- **What evidence would resolve it:** Ablate each reward term on diverse benchmarks; replace lexical metrics with semantic equivalence or intermediate execution-based checks.

### Open Question 4: Does SQL-Trail's performance generalize to real-world production settings beyond standardized benchmarks?
- **Question:** Does SQL-Trail's performance generalize to real-world production settings beyond standardized benchmarks?
- **Basis in paper:** Explicitly states that empirical study is centered on Spider/BIRD and does not fully represent production constraints and real-world use cases (Limitations).
- **Why unresolved:** Benchmarks may not capture enterprise schema complexity, user intent ambiguity, or operational constraints like latency and cost.
- **What evidence would resolve it:** Evaluate on private enterprise datasets across varied domains; conduct deployment studies measuring utility, robustness, and resource usage.

## Limitations
- Proprietary teacher (Claude Sonnet) for SFT introduces cost and reproducibility barriers.
- Critical hyperparameters (GRPO clip bounds, difficulty thresholds) omitted, impeding exact replication.
- Multi-turn inference increases latency and database load, limiting real‑time use.
