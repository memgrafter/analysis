# APEX-Searcher: Augmenting LLMs' Search Capabilities through Agentic Planning and Execution

## Quick Facts
- **arXiv ID:** 2603.13853
- **Source URL:** https://arxiv.org/abs/2603.13853
- **Reference count:** 40
- **Primary result:** APEX-Searcher (Qwen2.5-7B-Instruct) achieves a 0.376 average Exact Match on multi-hop QA benchmarks, improving standard RAG by +0.226 and the best agentic baseline by +8.2%.

## Executive Summary
APEX-Searcher tackles the inefficiencies of multi-hop retrieval-augmented generation (RAG), where models struggle with ambiguous intermediate steps and sparse reward signals. It introduces a decoupled two-stage framework: first, a reinforcement learning (RL) planner generates a logical sequence of sub-questions; second, a supervised fine-tuned (SFT) executor performs iterative retrieval to answer each sub-question. This separation allows each component to be optimized with targeted rewards and high-quality demonstration data. Evaluated on HotpotQA and 2WikiMultiHopQA, the approach with a 7B parameter model significantly outperforms both standard RAG pipelines and prior agentic methods, demonstrating the value of specialized planning and execution modules.

## Method Summary
The method trains two distinct models from a shared base (e.g., Qwen2.5-7B-Instruct). **Stage 1 (Planning)** uses Group Relative Policy Optimization (GRPO), an RL algorithm, to train a planner on 10,473 MuSiQue training examples. The reward is an F1 score measuring alignment between the predicted sub-question sequence and a gold decomposition, computed via optimal bipartite matching on sub-question embeddings (cosine similarity threshold τ=0.8). **Stage 2 (Execution)** trains an executor via full-parameter SFT on 14,604 curated multi-turn trajectories. These trajectories are generated by a stronger model (e.g., Qwen2.5-32B-Instruct) following an iterative retrieval loop: for a given sub-question, generate a query, retrieve documents, decide if context is sufficient, and either answer or continue. At inference, the planner first decomposes the user question; the executor then sequentially resolves each sub-question with its retrieval loop before synthesizing the final answer.

## Key Results
- APEX-Searcher (Qwen2.5-7B) attains 0.376 average Exact Match across HotpotQA and 2WikiMultiHopQA.
- This represents a +0.226 absolute gain over a standard RAG baseline and an 8.2% relative improvement over the strongest prior agentic baseline.
- Ablation studies confirm both RL-optimized planning and SFT-based execution are essential; the full model shows a 36.6% gain over the base 7B model.

## Why This Works (Mechanism)
The paper does not provide a dedicated mechanism analysis section. Its corevalue proposition is that decoupling the complex multi-hop RAG process into two discrete, optimizable stages—planning (strategy) and execution (action)—allows each to overcome specific failure modes. The RL planner is trained with a dense, decomposition-specific reward to produce coherent, reference-linked sub-question sequences, addressing the ambiguity of identifying correct reasoning steps. The SFT executor is trained on high-quality, curated trajectories to perform robust, context-aware iterative retrieval and termination, overcoming sparse feedback during live execution.

## Foundational Learning
- **Multi-hop RAG:** The task requiring evidence synthesis from multiple documents. *Why needed:* Defines the problem scope where standard single-step retrieval fails. *Quick check:* Can a model answer a question requiring linking facts from two separate Wikipedia articles?
- **Agentic Planning:** Using an LLM to generate a strategy (sub-questions) before execution. *Why needed:* Replaces monolithic, error-prone end-to-end generation with a structured, inspectable plan. *Quick check:* Does decomposing "Did Obama's 2008 opponent win a Nobel Prize?" into "Who was Obama's 2008 opponent?" and "Did [that person] win a Nobel Prize?" improve answer accuracy?
- **RL with Decomposition Reward (GRPO):** Training a policy model via reinforcement learning where the reward is the F1 match to a gold decomposition. *Why needed:* Provides dense supervision for planning quality in the absence of a clear execution outcome. *Quick check:* Does optimizing for sub-question F1 correlation improve final answer EM, or does it overfit to superficial plan features?
- **SFT on Curated Trajectories:** Supervised fine-tuning on multi-step interaction logs (query, retrieval, decision, answer). *Why needed:* Teaches the model the nuanced dynamics of iterative retrieval and sufficiency judgment better than RL or few-shot prompting. *Quick check:* Does an SFT-trained executor outperform a prompted base model on single-hop sub-questions within a trajectory?
- **Iterative Retrieval with Continuation Decision:** A loop performing query generation, document retrieval, and a binary "sufficient?" decision. *Why needed:* Allows adaptive evidence gathering, stopping when enough context is found. *Quick check:* Does the learned termination policy correctly identify when retrieved docs contain the answer to a sub-question?
- **Bipartite Matching for Reward:** Aligning predicted and gold sub-questions via embedding similarity to compute sequence-level reward. *Why needed:* Handles variations in wording while assessing semantic and referential equivalence of plan steps. *Quick check:* Is the reward sensitive to reordering of semantically equivalent sub-questions?

## Architecture Onboarding
**Component Map:**  
Planning Model (RL-trained) -> Sub-question Sequence -> Execution Model (SFT-trained) -> [Iterative Retrieval Loop] x N -> Final Answer Synthesis

**Critical Path:**  
1. Input question → Planning model outputs numbered sub-questions with `#n` references.  
2. For each sub-question in order: Execution model enters iterative loop (query generation → document retrieval → sufficiency evaluation → answer or continue).  
3. Final synthesis combines intermediate answers.

**Design Tradeoffs:**  
- Decoupling increases system complexity (two models/stages) but enables specialized optimization.  
- RL planning requires gold decompositions (from MuSiQue), limiting transfer to other datasets.  
- SFT execution depends heavily on the quality and diversity of curated trajectories; curation is resource-intensive.

**Failure Signatures:**  
- Planning failure: Sub-questions lack logical ordering, miss key entities, or have incorrect reference links (`#n` points to nonexistent step).  
- Execution failure: Irrelevant query generation, failure to terminate (infinite loop), or answering from retrieved context that doesn't address the sub-question.  
- Integration failure: Execution model ignores the plan's reference structure or synthesizes an answer without completing all sub-questions.

**First Three Experiments:**  
1. **Planning Reward Sanity Check:** Compute decomposition F1 (via bipartite matching) between human-written gold decompositions and outputs from the untrained base model. Expect low random-level F1; confirms reward signal is learnable.  
2. **Execution Trajectory Audit:** Manually inspect 50 curated SFT trajectories. Verify each has: (a) a clear sub-question, (b) queries that retrieve partially relevant docs, (c) a correct "sufficient" decision only when the answer is present.  
3. **Baseline Reconstruction:** Implement a standard RAG baseline (single query, top-k retrieval, answer synthesis) with the same Wikipedia index and base model (Qwen2.5-7B) to confirm the reported +0.226 gap on HotpotQA dev set.

## Limitations
- Critical retrieval setup details (Wikipedia dump version, chunk size, BM25 vs. dense retriever) are unreported, blocking exact replication.
- Execution-stage specifics (exact prompt templates, filtering thresholds, termination logic implementation) are absent.
- Evaluation relies solely on Exact Match; no analysis of robustness, hallucination rates, or human judgment of plan quality.
- Results are demonstrated only on Qwen2.5-7B; scalability to other model families or larger sizes is not established.

## Confidence
- **EM gains (+0.226 over RAG):** Medium. The improvement is large and statistically plausible, but depends on unreproducible retrieval and execution details.
- **Ablation necessity (both stages needed):** Medium. Ablation results are provided, but exact training configurations for ablations are not fully specified.
- **Training design (RL planning + SFT execution):** Medium. The core approach is clearly described with key hyperparameters, but missing implementation nuances (e.g., GRPO variant, SFT data filtering) introduce uncertainty.
- **Generalizability to other models:** Low. No experiments with non-Qwen models are presented.

## Next Checks
1. Rebuild the standard RAG baseline using a known Wikipedia snapshot (e.g., 2023-05) and BM25 with 100-word chunks to verify the baseline EM numbers reported.
2. Implement the bipartite matching reward (cosine embedding similarity, τ=0.8) on the MuSiQue training set; compute the reward distribution tovalidate its gradient signal for GRPO.
3. Generate a small pilot SFT execution dataset (~500 trajectories) using recovered prompts and Qwen2.5-32B, train an executor, and measure its single-hop accuracy vs. a prompted base model on a held-out set of sub-questions.
