# PrefillShare: A Shared Prefill Module for KV Reuse in Multi-LLM Disaggregated Serving
## Quick Facts
- arXiv ID: 2602.12029
- Source URL: https://arxiv.org/abs/2602.12029
- Reference count: 23
- Primary result: Matches full fine-tuning accuracy while achieving up to 4.5× lower p95 latency and 3.9× higher throughput vs. disaggregated baselines, with ~89% prefix cache hit ratio under high concurrency.

## Executive Summary
PrefillShare tackles the problem of redundant prefill computation and duplicated KV storage in multi-model LLM serving, where multiple fine-tuned models process a shared context. The core idea is to factorize each model into a frozen shared prefill module and task-specific decode modules that are conditioned on the shared KV cache. The prefill module processes the shared prefix once, generating a KV cache that multiple decode modules can consume, thereby eliminating redundant work. The authors also propose a prefix-aware routing mechanism in a disaggregated serving system (based on vLLM) to direct requests to consistent prefill workers and efficiently hand off KV caches between prefill and decode workers. Across multi-model agent workloads (ReAct/Reflexion), PrefillShare achieves accuracy comparable to full fine-tuning on math, coding, and tool-calling benchmarks, while reducing p95 latency by up to 4.5× and increasing throughput by up to 3.9× relative to a disaggregated baseline, maintaining ~89% prefix cache hit ratio under high concurrency.

## Method Summary
PrefillShare factorizes each fine-tuned model into two components: a frozen base prefill module and a task-specific decode module. The prefill module runs only during the prefix phase, producing the KV cache for the shared context. The decode module, which is fine-tuned on the specific downstream task, initializes its cache with the KV from the prefill module and generates output autoregressively. To ensure accurate token prediction despite using an external cache, the authors introduce cache-conditioned fine-tuning: during training, the KV cache from the frozen prefill module is computed once and treated as a constant while only the decode module’s parameters are updated via standard next‑token prediction. At inference time, a disaggregated serving system (extending vLLM) employs a proxy that routes all requests from a given user session to the same prefill worker, preserving prefix locality. After a (partial) prefill, the KV cache is transferred to the appropriate decode worker for the requested model, allowing subsequent model switches within a multi‑model agent workflow to reuse the same shared cache without recomputation.

## Key Results
- Matches full fine‑tuning accuracy across math, coding, and tool‑calling tasks.
- Reduces p95 latency by up to 4.5× and increases throughput by up to 3.9× vs. disaggregated baseline.
- Maintains ~89% prefix cache hit ratio under high concurrency in multi‑model agent workloads.

## Why This Works (Mechanism)
#### Mechanism 1
- **Claim:** PrefillShare eliminates redundant prefill computation and duplicate KV storage by factorizing models into a shared prefill module and multiple task‑specific decode modules.
- **Mechanism:** A frozen base prefill module processes the shared context once to generate a KV cache. Multiple decode modules, each fine‑tuned for a specific task, consume this shared KV cache during decoding, avoiding recomputation of the prefix for each model.
- **Core assumption:** The KV cache produced by the base model can be effectively used by diverse decode modules without accuracy loss, provided they are trained to condition on that cache.
- **Evidence anchors:**
  - [abstract] *"PrefillShare factorizes the model into prefill and decode modules, freezes the prefill module, and fine‑tunes only the decode module. This design allows multiple task‑specific models to share a prefill module and the KV cache generated for the same prompt."*
  - [section 3.1] *"Base Prefill Module… responsible only for the prefill phase… Specialized Decode Module… initializes its cache with C ← C_base and generates the output sequence."*
  - [corpus] Neighbors like DroidSpeak and ICaRus explore cross‑model KV reuse but with different assumptions; PrefillShare’s factorization is novel. Corpus evidence is indirect but supportive of the problem space.
- **Break condition:** If the base prefill module’s KV distribution is too dissimilar from what decode modules expect (e.g., due to architectural differences), accuracy may drop despite cache‑conditioned fine‑tuning.

#### Mechanism 2
- **Claim:** Cache‑conditioned fine‑tuning aligns task‑specific decode modules to reliably generate tokens conditioned on the shared KV cache from the frozen base model, preserving accuracy.
- **Mechanism:** During fine‑tuning, for each training example, the base KV cache is computed using the frozen base model and treated as a constant. The decode module is then fine‑tuned to predict targets while attending to this fixed cache, matching the inference‑time cache usage.
- **Core assumption:** The decode module can adapt to the KV representations of a different model through training, and the next‑token prediction objective with the fixed cache is sufficient for alignment.
- **Evidence anchors:**
  - [abstract] *"We introduce a cache‑conditioned fine‑tuning procedure… freezes the prefill module, and fine‑tunes only the decode module conditioned on the shared KV cache."*
  - [section 3.2] Equation (7) and description: *"cache‑conditioned fine‑tuning… explicitly trains the decode module to consume C_base… By optimizing (7), the decode module learns to align its attention features… with the KV cache distribution produced by Mbase."*
  - [corpus] The paper contrasts with naive sharing (accuracy collapse) and references ICaRus, which uses a frozen encoder but requires extra compute. Cache‑conditioned fine‑tuning is a key innovation; corpus shows related works on KV sharing but not this specific training method.
- **Break condition:** If the base and fine‑tuned models have very different architectures (e.g., different attention mechanisms), cache‑conditioned fine‑tuning might not fully align them, leading to accuracy drops. Tests on LLaMA and Qwen (both decoder‑only Transformers) support the assumption within that family.

#### Mechanism 3
- **Claim:** The prefix‑aware routing and cache‑handoff mechanism enable efficient shared‑prefill inference across heterogeneous models in a disaggregated system while preserving prefix cache locality.
- **Mechanism:** A proxy maintains a routing table mapping user sessions to a consistent prefill worker. When a request arrives, the prompt is sent to the prefill worker to compute (or hit) the shared KV cache, which is transferred to the appropriate decode worker. For subsequent model switches, partial prefill updates the shared cache incrementally.
- **Core assumption:** The overhead of transferring KV caches between workers is outweighed by savings from avoided redundant prefill, and prefix cache locality can be maintained via consistent routing.
- **Evidence anchors:**
  - [abstract] *"We further introduce a routing mechanism that enables effective prefill sharing across heterogeneous models in a vLLM‑based disaggregated system."*
  - [section 3.3] *"Prefix‑Aware Routing… keeps requests with the same shared prefix pinned to a consistent prefill worker… Execution Pipeline… shared/partial prefill… selective decode… cache handoff."*
  - [corpus] Neighbors like DistServe and Splitwise focus on disaggregation but not cross‑model sharing. SUN (Shared Use of Next‑token Prediction) is related but focuses on decode sharing; PrefillShare’s routing is tailored for KV reuse. Corpus evidence is moderate—context exists, but specific routing is novel.
- **Break condition:** If model switching is extremely frequent or KV transfers are very large, communication overhead could negate benefits. Routing failures (e.g., due to load balancing) reduce cache hit ratios.

## Architecture Onboarding
- **Component map:**  
  Client → Proxy → Shared Prefill Worker → Task‑specific Decode Worker; KV cache is stored in GPU memory of workers and transferred during handoff.

- **Critical path:**  
  1. Client sends initial prompt → Proxy routes to a prefill worker.  
  2. Prefill worker computes KV cache for full prompt (cache miss) or hits existing prefix.  
  3. KV cache transferred to designated decode worker for first model.  
  4. Decode worker generates output tokens autoregressively using shared cache.  
  5. Output appended to context; proxy routes next request (possibly different model) to same prefill worker.  
  6. Prefill worker does partial prefill for new tokens only, updates shared cache.  
  7. Steps 3–6 repeat for each model in the agent workflow.

- **Design tradeoffs:**  
  - Shared prefill vs. routing overhead: Consistent routing maximizes cache locality but may load‑imbalance prefill workers. System trades load balancing for cache hit ratio.  
  - Cache‑conditioned fine‑tuning cost: Requires extra training per task but yields inference efficiency. Worthwhile when multiple models serve shared contexts frequently.  
  - KV transfer latency: Moving large KV caches introduces overhead; minimized by incremental updates and locality‑aware routing.  
  - Memory pressure on decode side: Shared KV reduces overall footprint, but many concurrent sessions pressure decode GPU memory, leading to CPU staging (observed in vLLM prototype).

- **Failure signatures:**  
  - Low prefix cache hit ratio (<80% in multi‑model workloads) indicates routing failure or insufficient fine‑tuning alignment.  
  - High tail latency despite sharing suggests KV transfer bottlenecks or decode‑side memory pressure causing staging.  
  - Accuracy drop relative to Full‑FT indicates cache‑conditioned fine‑tuning failure; check for architectural mismatch or training issues.  
  - Throughput saturation at lower concurrency than expected may signal routing inefficiency or handoff overhead.

- **First 3 experiments:**  
  1. Accuracy validation: Compare PrefillShare (cache‑conditioned fine‑tuned) vs. Full‑FT on domain‑specific benchmarks (GSM8K, HumanEval, BFCL) to confirm no significant accuracy loss.  
  2. Multi‑model agent workload test: Run ReAct/Reflexion with 4‑model sequential invocation, measure p95 latency and throughput under varying arrival rates against disaggregated baseline.  
  3. Concurrency scaling: Vary max concurrent sessions, measure prefix cache hit ratio and throughput to demonstrate KV memory savings and sustained performance.

## Open Questions the Paper Calls Out
#### Open Question 1
- **Question:** How can the KV cache handoff overhead between prefill and decode workers be minimized in PrefillShare under high‑concurrency regimes that exceed GPU memory capacity?
- **Basis in paper:** [explicit] The authors explicitly note that at high concurrency, decode‑side KV pressure causes staging and reload in their vLLM prototype, which degrades throughput, and they state that exploring alternative designs (e.g., admission control, backpressure, GPU‑resident KV reservations) is left to future system optimizations.
- **Why unresolved:** The current implementation inherits vLLM's generic staging mechanism, which is not optimized for shared‑prefill scenarios. No concrete solution or evaluation is provided.
- **What evidence would resolve it:** A systematic characterization of handoff overhead across concurrency levels, together with prototype implementations of candidate optimizations (e.g., dynamic admission control, priority‑based backpressure, per‑session KV buffer reservations) and quantitative measurements of their impact on p95 latency and throughput.

#### Open Question 2
- **Question:** Does cache‑conditioned fine‑tuning generalize to model architectures beyond decoder‑only Transformers (e.g., encoder‑decoder, Mixture‑of‑Experts) and to tasks that heavily rely on prefill semantics (e.g., summarization, retrieval‑augmented generation)?
- **Basis in paper:** [inferred] Experiments are restricted to decoder‑only models (LLaMA, Qwen) on math, coding, and tool‑calling benchmarks. The core assumption—that a frozen prefill KV distribution suffices for diverse downstream tasks—is not validated beyond these settings.
- **Why unresolved:** The paper does not test on alternative architectures or broader task distributions, leaving open whether the approach is universally applicable or limited to specific model‑task combinations.
- **What evidence would resolve it:** Extending evaluation to include encoder‑decoder (e.g., T5) and MoE models (e.g., Mixtral) on tasks such as summarization, QA, and RAG, measuring accuracy relative to full fine‑tuning and analyzing KV cache compatibility metrics.

#### Open Question 3
- **Question:** How does the prefix‑locality‑aware routing policy scale with the number of prefill workers, and could alternative routing strategies (e.g., load‑aware, model‑aware) further improve throughput or tail latency under heterogeneous multi‑model workloads?
- **Basis in paper:** [inferred] The routing mechanism pins requests to a consistent prefill worker to preserve cache locality, but the study fixes the infrastructure (4 prefill/4 decode GPUs) and does not explore scalability or compare to other policies. The design may become suboptimal as the number of workers or workload heterogeneity increases.
- **Why unresolved:** The lack of empirical data on routing behavior under varying system scales and request patterns prevents understanding of potential bottlenecks or better alternatives.
- **What evidence would resolve it:** Large‑scale simulations or testbed experiments that vary the number of prefill workers and compare consistent hashing (current) with dynamic load‑balancing policies, using metrics like cache hit ratio, worker utilization, and p95 latency under realistic agent traces.

#### Open Question 4
- **Question:** Could partially fine‑tuning the frozen prefill module—rather than keeping it completely static—improve task accuracy while retaining most benefits of KV sharing?
- **Basis in paper:** [explicit] The authors explicitly freeze the entire prefill module and only fine‑tune the decode module, noting that this acts as a regularizer and sometimes boosts performance, but they do not consider any degree of prefill adaptation.
- **Why unresolved:** The trade‑off between maintaining a shared prefill representation and aligning it with task‑specific needs is not investigated; some tasks might suffer from a rigid prefill distribution.
- **What evidence would resolve it:** An ablation study that fine‑tunes increasing fractions of the prefill layers (e.g., the last 1–2 transformer blocks) and measures the impact on task accuracy and KV cache sharing ratio, thereby identifying any sweet spot where limited prefill updates yield net gains.

## Limitations
- Exact module split and any required architectural tweaks for consuming external KV remain unspecified.
- Hyperparameters for cache‑conditioned fine‑tuning (learning rate, batch size, etc.) not fully reported, hindering exact replication.
- Routing and cache‑handoff algorithms lack low‑level details; their robustness under diverse workloads is unclear.

## Confidence
- Redundant prefill elimination: High for demonstrated mechanism and gains, Medium for cross‑architecture generality.
- Cache‑conditioned alignment: Medium (matches Full‑FT accuracy but relies on specific fine‑tuning setup).
- Routing & handoff efficiency: Medium (achieves ~89% hit ratio in tests, yet failure modes not fully mapped).
