# GRAFITE: Generative Regression Analysis Framework for Issue Tracking and Evaluation

## Quick Facts
- **arXiv ID:** 2603.18173
- **Source URL:** https://arxiv.org/abs/2603.18173
- **Reference Count:** 20
- **Primary Result:** A web platform that detects model regressions (e.g., Llama-3.2 reasoning drop) via issue-based testing, achieving high user satisfaction (mean 4.0–4.33) and 87.5% recommendation rate in a study with 8 users.

## Executive Summary
GRAFITE is a web-based framework designed to combat LLM benchmark contamination and enable continuous, domain-specific regression tracking. It constructs a dynamic benchmark repository from real-world user feedback, where subject matter experts synthesize "issues" (error behaviors) and create corresponding "tests" (prompts with reference answers and evaluation guidelines). Models are evaluated via an ensemble of LLM-as-a-judge models, with human oversight for low-confidence cases. The system stores all historical results, providing visual trend analysis to detect performance changes across model versions. In an evaluation with 20 issues and 110 tests across four Llama models, GRAFITE identified regressions (e.g., Llama-3.2’s reasoning decline) and produced granular domain pass rates (e.g., Code: 64.7%–100%). A small user study reported strong satisfaction with core features.

## Method Summary
The method involves a four-stage pipeline: (1) **Issue Management**: User dissatisfaction signals (thumbs down) are triaged by experts to define domain-specific issues. (2) **Test Creation**: Each issue is paired with manually crafted tests—input prompts, reference answers, and judge guidelines. (3) **Evaluation Execution**: A "test run" queues asynchronous jobs via RabbitMQ: the target model generates an output, then an ensemble of judge LLMs scores it against the reference using binary prompts. A human can override scores. (4) **Analysis**: All results are stored; dashboards compare pass/fail rates and score distributions across model versions and domains to detect regressions. The framework is implemented as a full-stack web app (Next.js/FastAPI/MongoDB) with integrations for local (Ollama) or cloud (WatsonX.ai) model serving.

## Key Results
- Detected a significant reasoning performance regression in Llama-3.2 compared to Llama-3.1 via trend analysis.
- Reported granular domain-level pass rates, showing variability (e.g., Code pass rates ranged from 64.7% to 100% across models).
- User study (n=8) yielded mean satisfaction ratings of 4.0–4.33 for core features and an 87.5% recommendation rate.

## Why This Works (Mechanism)

### Mechanism 1: Dynamic, Issue-Based Benchmarking Mitigates Contamination
- **Claim:** GRAFITE mitigates benchmark contamination by creating a moving target for evaluation derived from real-time user feedback, which is less likely to be present in training corpora.
- **Mechanism:** End-user dissatisfaction signals (thumbs down) are triaged by subject matter experts to synthesize domain-specific "issues" (descriptions of erroneous behavior). Each issue is paired with manually created "tests" (prompts + reference answers + evaluation guidelines). This repository evolves continuously, providing novel, failure-mode-focused benchmarks.
- **Core Assumption:** User-sourced tests are sufficiently novel and represent meaningful, real-world failure modes not memorized by models.
- **Evidence Anchors:** 
  - [abstract] "...addresses LLM benchmark contamination...by introducing a web-based platform for issue-based model evaluation. It creates a repository of model issues from user feedback..."
  - [section 2.1] "An issue is the erroneous behavior of a model during testing. It is synthesized from multiple sources of domain-specific feedback...A test is an example that exhibits the erroneous behavior of the issue."

### Mechanism 2: Ensemble Judging with Human Oversight Improves Robustness
- **Claim:** Using an ensemble of diverse LLM-as-a-judge models, complemented by human-in-the-loop verification, yields more robust and less biased performance scores than a single judge.
- **Mechanism:** For each test, multiple judge LLMs (e.g., Llama, Phi, GPT) evaluate the model's output using structured prompts and binary scoring. The test passes if the average judge score exceeds 0.5. Human annotators can override the aggregated score and justification if the output is deemed inadequate. This design averages out individual model biases while correcting for systematic judge failures.
- **Core Assumption:** A diverse judge panel aggregates to a more accurate assessment, and human experts can reliably identify and correct judge errors.
- **Evidence Anchors:**
  - [abstract] "...evaluates models using an ensemble of LLM-as-a-judge scores with human-in-the-loop verification."
  - [section 2.2] "To mitigate the potential bias or quality issues associated with the LLM-as-a-judge technique, GRAFITE incorporates an ensemble of LLM-judges and determines whether a test passes or fails based on the average. Users have the flexibility to configure the judge models...When the judge model’s output is inadequate, users can add a human evaluation, overriding the judge’s score."

### Mechanism 3: Historical Trend Analysis Enables Continuous Regression Tracking
- **Claim:** Storing and visualizing all historical evaluation results per issue/test allows developers to detect meaningful performance changes (regressions or improvements) across model versions that aggregate benchmarks might miss.
- **Mechanism:** Every test run generates a report stored in a database. The "trend analysis" dashboard lets users filter by domain tags and compare pass/fail rates, score distributions, and individual test outcomes across multiple model runs (e.g., Llama-3.1 vs. 3.2). This issue-granular, version-aware view highlights degradation on specific, previously identified failure modes.
- **Core Assumption:** Fixed, issue-specific test sets re-evaluated over time provide a sensitive measure of regression.
- **Evidence Anchors:**
  - [abstract] "...facilitating regression detection across different releases."
  - [section 2.3] "Trend analysis enables comprehensive assessments of trends for a single model or across multiple models...Comparing multiple models is a useful feature for exploring how model performance has changed over time across different versions..."
  - [section 4] "Our assessment demonstrates how users can perform continuous evaluations of model iterations through GRAFITE." (Example showing Llama-3.2 regression in Reasoning).

## Foundational Learning
- **Concept:** LLM-as-a-Judge
  - **Why needed:** Core automated evaluation technique; understanding its binary scoring prompt structure, reliance on judge guidelines, and known limitations (bias, preference leakage) is essential to interpret GRAFITE's pass/fail metrics and the rationale for an ensemble.
  - **Quick Check:** How does changing the "judge guideline" for a Code domain test (e.g., "alternative implementations are acceptable") potentially change the pass/fail outcome for a functionally correct but non-standard code generation?
- **Concept:** Benchmark Contamination
  - **Why needed:** Primary problem GRAFITE aims to solve; grasping how exposure to test data during training inflates performance metrics explains why a dynamic, user-feedback-driven issue repository is proposed as a countermeasure.
  - **Quick Check:** Why would a model's high score on a 2024 math benchmark become less trustworthy by 2026, even if the model hasn't been updated?
- **Concept:** Regression Analysis (in ML model evaluation)
  - **Why needed:** The platform's key output is detecting performance "regressions" (declines) on specific issues across model versions; this requires understanding that regression is measured relative to a prior state on a fixed set of tasks, not just absolute performance on a new benchmark.
  - **Quick Check:** If Model v2 has a 5% lower pass rate than Model v1 on a specific "Geometry" issue test set, what are the two main possible interpretations of this finding?

## Architecture Onboarding
**Component map:** Frontend (Next.js + Carbon Design System) -> Backend (FastAPI) -> Task Queue (RabbitMQ) -> Database (MongoDB). Model Serving integrates with Ollama (local) or WatsonX.ai (cloud) for target and judge model inference.

**Critical path:** Issue Creation -> Test Creation -> "Test Run" Trigger (queues jobs) -> (Model Inference -> Judge Scoring) for each test -> Result Storage -> Report/Dashboard Generation.

**Design trade-offs:**
- Web GUI vs. CLI: Sacrifices CLI flexibility (e.g., HELM) for accessibility and integrated visualization, targeting non-experts.
- Human-in-the-loop vs. Full Automation: Manual issue/test creation and judge override ensure quality but create a bottleneck requiring SME time.
- Ensemble Judges vs. Single Judge: Increases cost and latency but aims to improve robustness against individual judge bias.

**Failure signatures:**
- High rate of judge justification failures or "N/A" responses from judge models.
- Very low usage of human override feature, suggesting judges are trusted blindly or the UI is inaccessible.
- Inability to find existing "similar" issues during triage, leading to issue duplication and fragmented test sets.
- Slow test run completion due to judge model queueing or high inference latency.

**First 3 experiments:**
1.  **Issue/Test Creation:** Log in as an "Expert," search for an existing issue (e.g., "Math - Geometry"). If not found, create a new issue from a user complaint. Attach a new test: write a geometry prompt, provide a reference answer, select a judge template (e.g., "answer must match reference exactly"). Run a single test.
2.  **Ensemble Evaluation & Report:** Execute a "test run" for a specific issue suite (e.g., all "Code" issues) using a target model (e.g., `llama3.2:3b`). Configure the run to use 3 different judge models. After completion, inspect the test report: verify the pass/fail pie chart, check individual test scores/justifications from each judge, and practice overriding one judge score with a human evaluation.
3.  **Trend Analysis & Regression Detection:** Create two model runs: one with `llama3.1:8b` and one with `llama3.2:3b` on the *same* set of issues/tests. Use the "Comparison Mode" in trend analysis to view the winning/tied/losing chart. Identify which issue domains (e.g., Reasoning) show the largest performance drop for the smaller model, simulating the regression detection described in Section 4.

## Open Questions the Paper Calls Out
- **Open Question 1:** How can GRAFITE's issue categorization system be made more adaptable to support large-scale, automated issue management? (Basis: Conclusion states plans for "more adaptable issue categorization tools.")
- **Open Question 2:** Can synthetic data generation effectively augment test sets to automate and diversify issue-based evaluations without compromising validity? (Basis: Conclusion mentions exploring "augmenting test sets through synthetic data generation.")
- **Open Question 3:** How effective are the user-suggested interface improvements (e.g., automatic detection of underperforming issues, customizable dashboards) at improving user satisfaction and efficiency? (Basis: Section 5 user study participants suggested these features.)
- **Open Question 4:** Does the use of an ensemble of LLM judges sufficiently mitigate bias (e.g., preference leakage) to ensure reliable trend analysis for regression detection? (Basis: Footnote 11 acknowledges preference leakage when using same/family models as judges; ensemble approach is proposed but its efficacy for robust trend analysis is unevaluated.)
- **Open Question 5:** How does the reliance on human expert triaging and test creation affect the scalability and maintenance cost of the issue repository over time? (Basis: Pipeline depends on SMEs; no data on issue volume growth or expert time burden provided.)
- **Open Question 6:** To what extent do variations in judge prompt templates and guidelines affect the binary pass/fail outcomes for the same model responses? (Basis: Users can configure judge templates/guidelines; impact on reported pass rates not analyzed.)

## Limitations
- Full 110-test dataset and domain-specific judge guidelines are not publicly released; reproduction relies on incomplete seed data.
- User study undersized (n=8); satisfaction metrics lack statistical power and demographic diversity.
- Corpus evidence for all three mechanisms is weak; conclusions drawn from internal demos without external validation.
