# Federated Learning and Unlearning for Recommendation with Personalized Data Sharing

## Quick Facts
- arXiv ID: 2603.11610
- Source URL: https://arxiv.org/abs/2603.11610
- Reference count: 40
- Primary result: Enables personalized data sharing and unlearning in federated recommendation, achieving HR@20: 0.4773 on MovieLens-1M with significantly reduced storage for unlearning.

## Executive Summary
FedShare is a federated recommender system framework that addresses two key limitations of existing works: it allows users to voluntarily share data for improved performance (personalized sharing) and supports efficient model unlearning to honor later deletion requests. The server constructs a high-order user-item graph from shared interactions and employs contrastive learning to align local (client-derived) and global (server-derived) item representations during training. For unlearning, it leverages a small buffer of historical embedding snapshots to generate "forgotten views" and applies a contrastive loss to erase the influence of unshared data without storing extensive historical gradients. Evaluations on three datasets show that FedShare achieves superior recommendation accuracy and competitive unlearning effectiveness while drastically reducing storage overhead compared to state-of-the-art unlearning methods. This work balances utility, privacy, and compliance with regulations like GDPR.

## Method Summary
FedShare introduces a federated recommendation system with personalized data sharing and efficient unlearning. Users partition their interactions into local-only, shared, and optionally unshared subsets. The server aggregates shared data to build a high-order bipartite user-item graph, used to produce global item embeddings via multi-layer Light Graph Convolution (LGC). In each training round, clients perform local updates on their first-order graphs (1-layer LGC + BPR) and upload item embeddings; the server aggregates these via FedAvg to obtain local-view embeddings. A contrastive loss (InfoNCE) aligns local-view and global-view (from server graph) embeddings, combined with a BPR loss on the shared graph. For unlearning, upon a user's retraction of shared data, the server removes corresponding edges and creates a forgotten graph from the unshared data. It maintains M historical global embedding snapshots. Unlearning runs for several rounds: remaining clients retrain on updated local data; new local views are aggregated; global views are inferred from the updated shared graph; forgotten views are generated by initializing LGC on the forgotten graph with each snapshot; a contrastive unlearning loss aligns new local/global views while pushing new local views away from forgotten views. This avoids storing per-client gradients, achieving high storage efficiency.

## Key Results
- Superior learning performance: On MovieLens-1M, FedShare achieves HR@20: 0.4773, outperforming baselines like CDCGNNFed and PDC-FRS.
- Competitive unlearning accuracy: After unlearning, model performance remains close to a fully retrained model, satisfying effectiveness requirements.
- Drastically reduced storage: Uses only M historical embedding tables (e.g., M=5) instead of per-client gradient histories, lowering storage by orders of magnitude compared to FRU/CUFRU.

## Why This Works (Mechanism)

### Mechanism 1: Dual-View Contrastive Learning for Representation Alignment
**Claim:** Aligning client-side (local) and server-side (global) item representations via contrastive learning improves recommendation performance under personalized data sharing.  
**Mechanism:** The server builds a high-order user-item graph from shared interactions. Each item has two views: a local view from FedAvg on client-updated embeddings and a global view from LGC propagation on the server graph. The InfoNCE loss pulls these positive pairs together while pushing apart embeddings of other items.  
**Core assumption:** The global view captures high-order cross-user collaborative signals missing from isolated client graphs; aligning these complementary views yields more robust embeddings.  
**Evidence anchors:** Abstract mentions aligning local and global representations; Section IV-B3 defines the positive pairs and uses InfoNCE; neighboring papers suggest the pairing's novelty in federated context.  
**Break condition:** If sharing is extremely sparse, the server graph becomes too thin, global views become noisy, and misalignment degrades performance below FedAvg.

### Mechanism 2: Contrastive Unlearning with Historical Snapshots
**Claim:** Selective removal of unshared data's influence is achievable by contrasting new representations against forgotten views derived from a small number of historical embedding snapshots, avoiding extensive gradient storage.  
**Mechanism:** After an unlearning request, the server runs continued federated training on remaining clients to get new local views and infers new global views from the updated shared graph. It constructs forgotten views by initializing LGC on the forgotten graph (from unshared edges) using old snapshot embeddings as initialization. The contrastive unlearning loss aligns new local/global views while pushing new local views away from their corresponding forgotten views.  
**Core assumption:** Historical snapshots sufficiently encode the representation space induced by now-forgotten interactions; contrasting against them reverses that influence without altering remaining-data-supported representations.  
**Evidence anchors:** Abstract describes snapshot-based contrastive unlearning; Section IV-D2 details forgotten graph construction and LGC inference with snapshots; neighboring unlearning methods store gradients, making snapshots a structural alternative.  
**Break condition:** If unlearning requests are highly delayed (snapshots too old), forgotten views become stale and fail to capture target influence accurately, leading to incomplete forgetting or collateral damage.

### Mechanism 3: Personalized Data Sharing Enables High-Order Graph Construction
**Claim:** Allowing users to voluntarily share data creates a server-side high-order user-item graph that provides cross-user collaborative signals unavailable in standard federated recommenders, boosting performance.  
**Mechanism:** Users choose subsets of interactions to upload (I_share^u). The server aggregates these into a shared dataset D_s and constructs a bipartite graph G_s. This graph connects users who do not directly share a client, enabling multi-hop propagation that enriches item embeddings beyond each client's local ego-graph.  
**Core assumption:** The high-order structural information in G_s (e.g., users sharing items with similar patterns) is valuable for recommendation and cannot be efficiently learned through FedAvg alone from isolated client graphs.  
**Evidence anchors:** Abstract states the graph captures both low-order and high-order signals; Section IV-A notes the server leverages collaborative information unavailable in traditional federated systems; papers like CDCGNNFed and PDC-FRS also exploit server-side aggregation, indirectly supporting the value.  
**Break condition:** If sharing users are highly non-representative (e.g., only niche users share), G_s may introduce bias or noise that harms recommendations for non-sharing users.

## Foundational Learning

**Concept: Federated Averaging (FedAvg)**  
- **Why needed:** The core aggregation primitive that produces local-view embeddings from client updates.  
- **Quick check:** How does FedShare's global view update differ conceptually from standard FedAvg aggregation of V_u tables?

**Concept: Graph Neural Network Message Passing (LGC)**  
- **Why needed:** The backbone for generating global and forgotten views via embedding propagation on bipartite graphs.  
- **Quick check:** Why can higher-order LGC propagation only run on server-side graphs and not on each client's local ego-graph?

**Concept: Contrastive Learning (InfoNCE)**  
- **Why needed:** The optimization framework for aligning representations during learning and inducing selective separation during unlearning.

## Architecture Onboarding

**Component map:**  
Client module (holds D_u, V_u, θ_u) → local training (1-layer LGC + BPR) → upload V_u → Server module (V_s, θ_s, Graph Constructor, View Inferrer, Contrastive Engine, Snapshot Manager) → FedAvg aggregation → local view V_s,loc → View Inferrer (LGC on G_s) → global view → Contrastive Engine (L_CL) → update V_s. For unlearning: Unlearn request → Graph Constructor updates G_s and builds G_f → new client training rounds → new local views → View Inferrer (new global on G_s, forgotten on G_f with snapshots) → Contrastive Engine (L_CU) → update V_s.

**Critical path:**  
1. Personalized sharing: Users upload I_share^u → server builds G_s.  
2. Learning round: Sample clients → local train on I_local^u → upload V_u → FedAvg → V_s,loc → infer global view on G_s (L=3) → minimize L = BPR + λ₁L_CL → update V_s and θ_s.  
3. Unlearning trigger: User submits I_unlearn^u → server removes edges from G_s and constructs G_f.  
4. Unlearning rounds (T_un): Sample remaining clients → local train on remaining data → upload V_u → FedAvg → new local view → infer new global view on updated G_s → for each snapshot m, infer forgotten view on G_f → minimize L_CU → update V_s.

**Design tradeoffs:**  
- Storage vs. unlearning fidelity: Snapshot count M trades storage for accuracy of forgotten views; too few leads to inaccurate forgetting, too many increases storage.  
- Client participation vs. server autonomy: Unlearning requires remaining clients to retrain, balancing client overhead against unlearning accuracy; server-only approaches may be less faithful.  
- Graph richness vs. privacy: More shared data yields a richer G_s and better performance, but users may share less for privacy, risking sparse graphs.

**Failure signatures:**  
- Learning phase: HR@20/NDCG@20 much lower than FedShare-FedAvg → contrastive alignment failing (e.g., λ₁ mis-set, extreme heterogeneity, or incorrect global view computation).  
- Unlearning phase: Post-unlearning HR@20 near pre-unlearning → incomplete forgetting; or far below Retrain baseline → over-unlearning (collateral damage). Monitor L_CU convergence.  
- System: Snapshots not regularly updated → stale forgotten views; high client dropout during unlearning → new local views highly non-iid, harming alignment.  
- Unlearning performance degrades sharply with delayed requests → snapshots too old to capture forgotten influence.

## Open Questions the Paper Calls Out

- **Open Question 1:** How can FedShare eliminate the need for remaining clients to participate in the unlearning phase while maintaining unlearning effectiveness? (The paper acknowledges it still requires client assistance, increasing overhead.)  
- **Open Question 2:** Can FedShare be extended to handle unlearning requests from users who never shared data but only participated via model updates? (Current framework does not support this, leaving a gap for full GDPR compliance.)  
- **Open Question 3:** What are the theoretical bounds on the discrepancy between the FedShare unlearned model and a model retrained from scratch? (No formal analysis exists to guarantee approximation quality.)  
- **Open Question 4:** How does FedShare perform in large-scale, highly non-IID settings with millions of users/items? (Experiments used small datasets; scalability and extreme heterogeneity remain untested.)

## Limitations

- Exact LGC propagation details (normalization, layer aggregation) are not fully specified, requiring inference from LightGCN.  
- The FedShare-FedAvg baseline implementation is ambiguous (server-as-client participation and aggregation).  
- Hyperparameter values (λ₁, M, τ) per dataset are undisclosed, hindering exact replication of reported numbers.  
- Contrastive unlearning batch composition and handling of empty negative sets are not described.  
- Theoretical guarantees for unlearning fidelity are absent.  
- Scalability to real-world large-scale, highly heterogeneous settings is unproven.
