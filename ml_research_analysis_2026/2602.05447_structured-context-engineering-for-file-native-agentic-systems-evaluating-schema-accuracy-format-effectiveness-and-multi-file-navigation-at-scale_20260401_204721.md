# Structured Context Engineering for File-Native Agentic Systems: Evaluating Schema Accuracy, Format Effectiveness, and Multi-File Navigation at Scale

## Quick Facts
- **arXiv ID:** 2602.05447
- **Source URL:** https://arxiv.org/abs/2602.05447
- **Reference count:** 0
- **Primary result:** File-native retrieval boosts frontier models (+2.7%) but harms open-source (-7.7%); model tier dominates (21-point gap); YAML most token-efficient; TOON incurs "grep tax"; scaling via domain partitioning to 10k tables.

## Executive Summary
This paper investigates context engineering for LLM agents using SQL generation as a benchmark. Through 9,649 experiments across 11 models, four schema formats (YAML, Markdown, JSON, TOON), and schemas up to 10,000 tables, the authors compare file-native agents (using grep/read tools) against prompt injection (full schema in prompt). Key findings reveal that file-native retrieval improves accuracy for frontier models but harms open-source models; model capability is the strongest predictor of success with a 21-point gap between tiers; format choice does not significantly impact accuracy, though YAML is the most token-efficient; and domain partitioning enables scaling to massive schemas, while compact formats like TOON incur a "grep tax" due to pattern unfamiliarity.

## Method Summary
The evaluation uses the TPC-DS benchmark schema and 100 curated SQL queries spanning complexity tiers L1–L5. Two architectures are tested: (1) File Agent with grep/read tools for on-demand retrieval, and (2) Prompt Baseline with full schema injection. Experiments cover 11 models (frontier, frontier-lab, open-source), four formats, and scale conditions where schemas are partitioned by domain (~250 tables per domain) up to 10,000 tables. Primary metric is accuracy (Jaccard similarity ≥0.9); secondary metrics include token usage and navigation accuracy. Statistical significance is assessed via t-tests, chi-square, and ANOVA with Benjamini–Hochberg correction. All evaluations are single-run with temperature=0 where supported.

## Key Results
- File-native retrieval improves frontier model accuracy (+2.7%, p=0.029) but reduces open-source model accuracy (-7.7%, p<0.001).
- Model tier is the dominant predictor, with a ~21 percentage point gap between frontier and open-source models; format has no significant aggregate effect on accuracy (p=0.484), but YAML is most token-efficient (12,729 tokens, 28–60% less than others).
- File-native agents scale to 10,000 tables via domain partitioning, but compact formats like TOON incur a "grep tax" (higher token usage) due to pattern unfamiliarity.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** File-native context retrieval improves accuracy for frontier models but harms accuracy for many open-source models.
- **Mechanism:** Frontier models possess robust tool-use training and can efficiently `grep` and synthesize information from retrieved file fragments. Open-source models often lack this capability, leading to context fragmentation, missed relationships, and incorrect path selection when forced to retrieve piecemeal.
- **Core assumption:** Differences in training data and reinforcement learning for tool use create a capability gap in managing retrieved context windows.
- **Evidence anchors:**
  - [abstract]: "file-based retrieval improved frontier model accuracy by +2.7% (p=0.029) but reduced open source model accuracy by -7.7% (p<0.001)."
  - [section 4.1]: Table 6 shows File Agent winning for frontier models (Opus, GPT-5.2, Gemini Pro, Haiku, GPT-5-mini) but Prompt Engineering winning for open-source models (DeepSeek, Llama Maverick, Qwen).
  - [corpus]: Weak signal; neighboring papers discuss SLMs for agentic workloads but do not directly address this architecture dichotomy.
- **Break condition:** If open-source models implement comparable tool-use training or if context window sizes increase enough to make full schema injection feasible without loss.

### Mechanism 2
- **Claim:** Token efficiency during execution is not predicted by static file size; compact/novel formats can incur a "grep tax" due to output density and pattern unfamiliarity.
- **Mechanism:** A format's token efficiency during agent operation depends on (a) the density of schema information per line (affecting `grep` output volume) and (b) the model's ability to predict correct search patterns. Novel formats (TOON) with unfamiliar keywords force models to iterate through multiple failed `grep` attempts before finding matches, increasing total tool call tokens.
- **Core assumption:** Models rely on memorized, common patterns (e.g., YAML spacing, DDL) for initial `grep` queries; deviation from these patterns increases exploratory tool use.
- **Evidence anchors:**
  - [abstract]: "compact formats like TOON incurred a 'grep tax' due to pattern unfamiliarity, increasing token use despite smaller file sizes."
  - [section 5.3]: Describes the two components of the grep tax and provides the example of Haiku requiring 16 vs. 3 grep attempts for the same query in TOON vs. YAML at scale.
  - [corpus]: No direct evidence; this is a novel finding of the paper.
- **Break condition:** If models are explicitly prompted with format-specific `grep` patterns or if novel formats become common enough in training data to be recognized natively.

### Mechanism 3
- **Claim:** Model capability tier is the dominant determinant of task success, with a ~21-point gap between frontier and open-source models that overwhelms format and architecture choices.
- **Mechanism:** Higher-tier models possess superior reasoning, instruction following, and ambiguity resolution capabilities. This allows them to correctly interpret schemas, join paths, and complex SQL features regardless of representation (format) or retrieval method (file vs. prompt). Lower-tier models are more easily misled by format-specific cues or fail to effectively retrieve/parse necessary context.
- **Core assumption:** Complex programmatic tasks like text-to-SQL scale with general reasoning prowess more than with context engineering optimizations.
- **Evidence anchors:**
  - [abstract]: "model capability is the dominant factor, with a 21 percentage point accuracy gap between frontier and open source tiers that dwarfs any format or architecture effect."
  - [section 4.3]: Frontier tier 86.0%, Frontier Lab 76.7%, Open Source 64.6%. Figure 4 shows divergence at higher complexity tiers (L4-L5).
  - [section 5.5]: Practical guidance prioritizes "model capability" investment before format optimization.
  - [corpus]: Neighboring paper "Small Language Models for Agentic Systems" suggests SLMs can be superior for constrained tasks, providing a counterpoint that nuance exists within "open source" tier.
- **Break condition:** If open-source models achieve parity in base reasoning capabilities with frontier models, or if tasks become so context-dependent that retrieval/prompt engineering becomes the primary bottleneck.

## Foundational Learning
- **Concept:** File-Native vs. Prompt-Injected Architectures
  - **Why needed here:** The core finding hinges on understanding *how* context reaches the model. A File-Native agent uses tools (`grep`, `read`) to dynamically retrieve schema fragments, while Prompt Engineering injects the full schema into the system prompt. This architectural choice has opposite effects for different model tiers.
  - **Quick check question:** For a model that struggles with tool use, what is the likely outcome of using a file-native architecture versus prompt injection?

- **Concept:** Schema Format and Information Density
  - **Why needed here:** Formats (YAML, MD, JSON, TOON) have different static sizes and syntactic structures. This study shows that runtime token consumption depends on grep output density (tokens per match) and pattern familiarity, not just file size. YAML's spaced key-value pairs return fewer tokens per hit than TOON's packed syntax.
  - **Quick check question:** Why might a 25% smaller file (TOON) result in 38% more tokens consumed during a file-native operation?

- **Concept:** Partitioning for Scale
  - **Why needed here:** The study demonstrates that file-native agents can handle schemas up to 10,000 tables by using domain-based partitioning (e.g., separating "sales" and "inventory" domains). This keeps the per-query context bounded and maintains navigation accuracy, defeating the "lost in the middle" problem for massive schemas.
  - **Quick check question:** What is the primary architectural innovation that allows a file-native agent to work with a 10,000-table schema, and what problem does it solve?

## Architecture Onboarding
- **Component map:**
  1. **Schema Repository:** Persistent storage of schema files in chosen formats (YAML/MD/JSON/TOON), partitioned by domain.
  2. **Navigator File:** A `navigator.md` providing a high-level overview and table descriptions (common across formats).
  3. **Agent Runtime:** The LLM with tool access (`grep`, `read`) for file-native conditions.
  4. **Evaluation Harness:** Script that generates schema, runs queries, and computes Jaccard similarity against ground truth.
  5. **Model Provider API:** Interface to frontier or open-source models with configurable parameters.

- **Critical path:**
  1. Receive SQL generation query.
  2. Agent reasons about required tables/columns and issues `grep` commands.
  3. System returns matching file lines (context retrieval).
  4. Agent `read`s full relevant sections if needed.
  5. Agent generates SQL based on retrieved context.
  6. Execute SQL, compare results to ground truth, log metrics.

- **Design tradeoffs:**
  - **File-Native vs. Prompt:** File-native scales with schema size and benefits frontier models but requires reliable tool use. Prompt injection guarantees full context but hits hard limits and harms performance for tool-inept models.
  - **Format Choice:** Prioritize YAML for token efficiency and grep-friendliness. Use Markdown for human-editable documentation-heavy schemas. Avoid novel formats like TOON without providing explicit grep pattern guidance in the system prompt.
  - **Partitioning Granularity:** More partitions (smaller files) improve navigation speed but increase cross-domain join complexity for the agent. ~250 tables per domain was effective in the study.

- **Failure signatures:**
  - High token consumption with low retrieval specificity: Agent makes many broad `grep` calls or repeatedly searches due to pattern mismatch (grep tax).
  - Consistently low accuracy on multi-join queries (L3+): Agent likely cannot properly link tables across retrieved fragments, a common file-native failure for weaker models.
  - Incorrect join path on ambiguous columns (e.g., `state`): Agent is following format-specific cues (e.g., MD's flat structure) rather than reasoning semantically. Navigator disambiguation rules are needed.
  - Scale failure (S6+): Agent cannot locate relevant partitioned file or loses context across domain boundaries.

- **First 3 experiments:**
  1. **Architecture Baseline:** Run 20 TPC-DS queries (mixed L1-L3) with your target model in *both* File-Agent and Prompt-Injected modes. Expect the differential predicted by model tier (positive for frontier, negative for many open-source).
  2. **Format Tokens Test:** Using File-Agent only, run the same 20 queries with all four formats. Measure total tokens consumed *per query*. Verify YAML is most efficient and identify if TOON incurs a grep tax (excessive tool calls).
  3. **Partitioning Stress Test:** For your largest schema (or a synthetic 5k+ table schema), implement domain partitioning. Run 20 queries that require joins across two domains. Measure navigation accuracy (did agent find both relevant files?) and final SQL accuracy. Validate the partitioned approach scales.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Does file-native context engineering improve accuracy for non-SQL agentic tasks (e.g., API calling, code generation)?
- **Basis in paper:** [explicit] "Future work should extend experiments to non-SQL tasks" (Conclusion).
- **Why unresolved:** The study uses SQL generation as a proxy; other programmatic operations may involve different reasoning patterns or context sensitivities.
- **What evidence would resolve it:** A comparable systematic study across diverse agent tasks (e.g., REST API interaction, software engineering) with same models, formats, and architectures.

### Open Question 2
- **Question:** Can prompt engineering mitigate the "grep tax" for compact/novel formats like TOON by providing format-specific search patterns?
- **Basis in paper:** [explicit] "Providing TOON-specific grep examples in the system prompt may mitigate this effect and is a candidate for future work" (Section 5.3); also "format-specific prompt guidance... was outside our methodology" (Limitations).
- **Why unresolved:** The study tested native LLM comprehension without format-optimized prompts; the observed inefficiency may be reducible.
- **What evidence would resolve it:** Repeat core experiments with system prompts including tailored grep patterns for TOON, measuring token usage and accuracy against baselines.

### Open Question 3
- **Question:** Do scale findings (navigation accuracy up to 10,000 tables) hold across LLM providers and tool implementations beyond the Claude Agent SDK?
- **Basis in paper:** [explicit] "Scale experiments used Claude models and the Claude Agent SDK only; other models and SDKs may show different patterns" (Section 5.3); also "validate scale findings across providers" (Conclusion).
- **Why unresolved:** Scaling validation was limited to one provider's tooling; different SDKs or model tool-use capabilities could affect navigation performance.
- **What evidence would resolve it:** Replicate scale experiments (S0-S9) using other provider SDKs (e.g., OpenAI, Anthropic's other interfaces) and open-source model tool frameworks, measuring navigation accuracy and tool call efficiency.

### Open Question 4
- **Question:** Does allowing multi-turn self-correction change the relative effectiveness of file-native vs. prompt architectures and format sensitivities?
- **Basis in paper:** [explicit] "Single-shot evaluation may understate accuracy achievable with multi-turn correction" (Limitations); "investigate multi-turn evaluation" (Conclusion).
- **Why unresolved:** The single-run design may miss recovery from initial errors; multi-turn could reduce architecture/format gaps, especially for weaker models.
- **What evidence would resolve it:** Conduct experiments with agents allowed multiple reasoning/actuation turns per query, comparing accuracy and token costs across architectures/formats, and analyzing correction patterns.

## Limitations
- **Tool behavior opacity:** The exact implementation of `grep`/`read` tools (e.g., line limits, pattern matching) in the Claude Agent SDK is unreported, making the "grep tax" effect tool-dependent and hard to isolate.
- **Query bank absence:** The 100 TPC-DS-derived queries are not provided, blocking exact replication of per-complexity-tier results and ambiguous-case analyses (e.g., `state` joins).
- **External validation gap:** Neighboring literature shows low citation impact and limited direct corroboration; the frontier/open-source dichotomy and grep tax remain novel, unverified claims outside this study.

## Confidence
- **Mechanism 1 (frontier vs. open-source dichotomy):** Medium confidence. Strong internal statistical evidence (p<0.001, Table 6) but depends on unreported model training specifics; corpus provides only weak/adjacent signals.
- **Mechanism 2 (grep tax from format unfamiliarity):** Medium confidence. Novel internal finding with concrete example (Haiku 16 vs. 3 attempts), yet tool-dependence and lack of external replication limit generalizability.
- **Mechanism 3 (model tier dominance):** High confidence. Large, consistent effect (21-point gap) across multiple analyses; minor corpus counterpoints (e.g., SLM survey) do not negate the observed hierarchy.

## Next Checks
1. **Tool specification audit:** Reverse-engineer and document the exact tokenization, return limits, and pattern-matching rules of the `grep`/`read` tools used; re-run TOON experiments with standardized tool behavior to isolate format effects.
2. **Query bank public release:** Publish the full 100-query set with tier labels and ground truth; enable independent labs to reproduce complexity-tier breakdowns and probe ambiguous join cases.
3. **Format familiarity ablation:** Fine-tune a mid-tier open-source model on TOON syntax and common `grep` patterns; re-test to quantify whether pattern familiarity eliminates the "grep tax" and closes token-efficiency gaps.
