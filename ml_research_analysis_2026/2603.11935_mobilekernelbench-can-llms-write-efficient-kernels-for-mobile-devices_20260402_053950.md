# MobileKernelBench: Can LLMs Write Efficient Kernels for Mobile Devices?

## Quick Facts
- **arXiv ID:** 2603.11935
- **Source URL:** https://arxiv.org/abs/2603.11935
- **Reference count:** 40
- **Primary result:** MoKA achieves 93.7% compilation success and 27.4% of generated kernels produce measurable speedups over native MNN libraries on mobile CPU, vastly outperforming baseline LLMs and fine-tuning.

## Executive Summary
The paper addresses the challenge of using large language models (LLMs) to generate efficient kernels for mobile devices. Current LLMs suffer from high compilation failure rates (>54%) and minimal performance improvements, largely due to hallucinations about framework APIs and a scarcity of high-quality mobile kernel data. To enable systematic evaluation, the authors introduce MobileKernelBench, a benchmark of 190 tasks covering 95 ONNX operators with an automated on-device verification pipeline. They also propose the Mobile Kernel Agent (MoKA), a multi-agent system that employs repository-aware reasoning and iterative plan-and-execute. Evaluated on MNN’s CPU backend, MoKA achieves a 93.7% compilation success rate, with 27.4% of kernels delivering measurable speedups over native libraries, significantly surpassing baseline LLMs and fine-tuning methods.

## Method Summary
MobileKernelBench constructs a task set by selecting 95 distinct ONNX operators and generating diverse input shapes and attributes, resulting in 190 concrete kernel generation tasks. Each task is evaluated through an automated pipeline that compiles the generated kernel, deploys it to a real mobile device, and verifies both functional correctness and performance against a reference implementation.

MoKA is a multi-agent framework. A Planner synthesizes a high-level implementation plan using retrieved MNN API documentation. Code Agents then write the kernel code according to the plan. An Execution Agent compiles and runs the code on the target device, while a Verification Agent checks output correctness and measures execution time. If verification fails, detailed feedback is sent to the Planner to revise the plan and iterate, enabling progressive refinement and error recovery.

## Key Results
- MobileKernelBench provides a rigorous, automated benchmark for mobile kernel generation with on-device verification.
- MoKA achieves 93.7% compilation success and 27.4% speedup rate on MNN CPU, far surpassing baseline LLMs and fine-tuning approaches.
- The multi-agent design significantly reduces API hallucinations and improves iterative error recovery.

## Why This Works (Mechanism)
MoKA’s effectiveness stems from decomposing the complex kernel generation task into specialized agents and explicit verification steps. Repository-aware reasoning ensures that code generation adheres to actual MNN APIs, minimizing hallucinations. The iterative plan-and-execute loop detects compilation or runtime errors early, refines the plan, and regenerates code, thereby increasing robustness. Automated on-device verification grounds evaluation in real hardware, avoiding simulator inaccuracies and ensuring that measured speedups are meaningful on target devices.

## Foundational Learning
- **ONNX operator specifications**  
  Why needed: Define a common, framework-agnostic interface for kernel tasks; MobileKernelBench maps each task to an ONNX op.  
  Quick check: List the inputs, outputs, and attributes for ONNX’s Conv operator.

- **Mobile inference runtime (MNN)**  
  Why needed: The target platform where generated kernels will be executed; understanding its API and memory model is essential.  
  Quick check: Describe how to allocate a tensor and launch a convolution in MNN.

- **LLM code generation hallucinations**  
  Why needed: Core problem that MoKA addresses; LLMs often produce code that uses non-existent APIs or incorrect semantics.  
  Quick check: Prompt an LLM to write a matrix multiply using a non-existent library function; observe that it may not detect the error.

- **Iterative refinement with verification**  
  Why needed: Enables error recovery and progressive improvement of kernel correctness and performance.  
  Quick check: Simulate a two-step loop: generate code, compile, if fail, ask LLM to fix based on error message.

## Architecture Onboarding
- **Component map:** RepositoryRetriever -> Planner -> CodeAgent -> ExecutionAgent -> VerificationAgent; verification results -> Planner (feedback loop).
- **Critical path:** 1) Input: ONNX op spec + MNN repository documents. 2) Planner synthesizes a high-level implementation plan. 3) CodeAgent writes kernel code. 4) ExecutionAgent compiles and runs on target device. 5) VerificationAgent validates correctness and measures performance. 6) If verification passes, kernel accepted; else, failure details trigger plan revision and repeat.
- **Design tradeoffs:**  
  - High-level MNN APIs vs low-level intrinsics: High-level APIs ensure portability and reduce bugs but limit peak performance; adding intrinsics could boost speed but increases complexity and error risk.  
  - Iteration count: More iterations improve success rates but increase total generation time.  
  - Repository-aware reasoning: Including API docs reduces hallucinations but adds retrieval overhead.
- **Failure signatures:**  
  - Compilation errors: syntax errors, missing symbols, type mismatches.  
  - Runtime crashes: segmentation faults, illegal memory access.  
  - Semantic errors: output mismatches compared to reference.  
  - Performance failures: kernel runs but is slower than baseline.
- **First experiments:**  
  1. **Smoke test:** Run MoKA on a simple operator (e.g., Add) to validate end-to-end pipeline functionality.  
  2. **Ablation of repository-awareness:** Disable the retrieval component and measure impact on compilation success and hallucinations.  
  3. **Iteration budget study:** Vary the maximum number of refinement iterations (e.g., 1, 3, 5) to assess effect on success rate and generation time.

## Open Questions the Paper Calls Out
1. **Can MoKA generate NEON intrinsics or inline assembly for further speedups on mobile CPUs?**  
   - **Basis:** [explicit] Future work mentions “low-level optimizations such as multi-threaded NEON and inline assembly.”  
   - **Why unresolved:** Current MoKA only uses high-level MNN APIs; intrinsics could unlock more performance.  
   - **Resolving evidence:** Add NEON-generation tools to Accelerator, test on a representative operator subset, measure extra speedup and correctness.

2. **Does MoKA generalize to other mobile frameworks (e.g., NCNN) and hardware backends (e.g., GPU, NPU)?**  
   - **Basis:** [explicit] Conclusion says “exploring diverse hardware backends and frameworks beyond MNN.”  
   - **Why unresolved:** MNN-specific; other frameworks have different APIs and semantics.  
   - **Resolving evidence:** Port evaluation pipeline to another framework, run MoKA on common operators, compare metrics and failure reasons.

3. **Is the multi-agent iterative design essential, or could a single agent with more data match MoKA's performance?**  
   - **Basis:** [inferred] Fine-tuning failed with limited data; unclear if data scale is the bottleneck.  
   - **Why unresolved:** No ablation of agents; no comparison with large-data fine-tuning.  
   - **Resolving evidence:** (a) Ablate MoKA agents; (b) collect larger mobile kernel dataset, fine-tune same LLM, compare to MoKA.

## Limitations
- Benchmark confined to ONNX operators and MNN CPU backend; extension to other frameworks/accelerators is uncertain.
- Speedup distribution and statistical significance are not reported; only aggregate percentages of “measurable” gains are given.
- Evaluation lacks hardware diversity, run counts, and variance metrics, limiting confidence in general performance claims.

## Confidence
- Benchmark coverage: Medium
- MoKA’s success rate & speedups: Medium
- Cross-platform generalizability: Low
