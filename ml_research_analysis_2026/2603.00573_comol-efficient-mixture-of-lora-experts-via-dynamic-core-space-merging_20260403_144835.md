# CoMoL: Efficient Mixture of LoRA Experts via Dynamic Core Space Merging
## Quick Facts
- **arXiv:** 2603.00573  
- **Source:** https://arxiv.org/abs/2603.00573  
- **References:** 9  
- **Key result:** Achieves 84.48% avg. accuracy on mathematical reasoning (Qwen3-8B) with 25.16M trainable parameters and sets SOTA pass@1 (48.11%) on code generation with 24.97M parameters, while matching LoRA's parameter efficiency.

## Executive Summary
CoMoL is a Mixture-of-Experts (MoE) extension to Low-Rank Adaptation (LoRA) that addresses two major shortcomings of existing MoE-LoRA approaches: limited parameter efficiency and coarse-grained adaptation. The method re-parameterizes each LoRA expert’s weight update using a shared low-rank singular subspace and a small expert-specific core matrix. Token-level routing operates within this core space, allowing dynamic soft-merging of experts with minimal computational overhead. The router itself is also projected into the core space, drastically reducing its parameter cost. Experiments on Qwen3-8B for mathematical reasoning and code generation demonstrate that CoMoL yields substantial gains over standard LoRA and other MoE-LoRA variants while using a comparable number of trainable parameters.

## Method Summary
CoMoL builds on LoRA’s decomposition \(W + \Delta W = W + B A\) where \(\Delta W\) is a rank‑\(r\) update. Instead of storing full \(B \in \mathbb{R}^{m \times r}\) and \(A \in \mathbb{R}^{r \times n}\) per expert, CoMoL applies a reduced SVD to obtain shared bases \(U_B \in \mathbb{R}^{m \times r}\) (left singular vectors of \(B\)) and \(V_A^\top \in \mathbb{R}^{r \times n}\) (right singular vectors of \(A\)). Each expert \(i\) then maintains only a core matrix \(M_i \in \mathbb{R}^{r \times r}\) such that \(\Delta W_i = U_B M_i V_A^\top\). During inference, an input token \(x\) is first projected to the low‑rank space \(\hat{x} = V_A^\top x\). A router (a linear layer) processes \(\hat{x}\) to produce token‑level weights \(G(\hat{x}) \in \mathbb{R}^N\) for \(N\) experts. The core matrices are merged: \(M_{\text{merged}} = \sum_i G_i(\hat{x}) M_i\). The final low‑rank update is \(U_B M_{\text{merged}} \hat{x}\), which is added to the frozen \(W x\). This design reduces the per‑expert parameter cost from \(O((m+n)r)\) to \(O(r^2)\) and the router parameters from \(O(N \cdot n)\) to \(O(N \cdot r)\), while still enabling fine‑grained token‑level adaptation.

## Key Results
- **Mathematical reasoning:** On Qwen3-8B, CoMoL reaches **84.48%** average accuracy across GSM8K, SVAMP, MultiArith, AddSub, AQuA, and SingleEq, using **25.16M** trainable parameters. It outperforms standard LoRA (82.78%, 24.77M) and MoE‑LoRA variants with >100M parameters.
- **Code generation:** On HumanEval, CoMoL attains **48.11%** pass@1 with Qwen3-8B and only **24.97M** parameters, setting a new state‑of‑the‑art.
- **Parameter efficiency:** CoMoL maintains a parameter count close to standard LoRA while providing token‑level adaptation, demonstrating that MoE benefits can be achieved without sacrificing efficiency.

## Why This Works (Mechanism)
### Core‑Space Experts Reduce Parameter Overhead
- **Claim:** By storing each expert’s adaptation in a compact \(r \times r\) core matrix and sharing the left/right singular bases, CoMoL drastically cuts the number of expert‑specific parameters.
- **Mechanism:** The LoRA update \(\Delta W = B A\) is re‑expressed as \(\Delta W = U_B M V_A^\top\) via reduced SVD, where \(U_B\) and \(V_A^\top\) are shared across all experts and only \(M\) is expert‑specific. This changes the expert parameter complexity from \(O(N \cdot (m+n)r)\) to \(O((m+n)r + N \cdot r^2)\).
- **Evidence:** Section 3.2 shows the reduction analytically and experimentally; the abstract notes the compact storage preserves diversity while controlling parameter growth.
- **Break condition:** If experts require fundamentally different singular subspaces, the shared‑basis assumption could limit expressiveness and harm performance on highly diverse tasks.

### Token‑Level Soft‑Merging Enables Fine‑Grained Adaptation Efficiently
- **Claim:** CoMoL merges core experts on a per‑token basis, achieving fine‑grained adaptation without the \(O(N)\) cost of applying separate LoRA experts.
- **Mechanism:** For each token, after computing \(\hat{x} = V_A^\top x\), the router provides weights \(G(\hat{x})\). The core matrices are merged \(M_{\text{merged}} = \sum_i G_i M_i\) (cost \(O(r^2 N)\)). The final update \(U_B M_{\text{merged}} \hat{x}\) is a single low‑rank multiply, avoiding \(N\) separate \(B_i A_i x\) computations.
- **Evidence:** Section 3.2 derives the FLOP reduction: core‑space merging reduces primary expert overhead by a factor of \(1/N\) compared to output‑level fusion, because \(r^2 \ll n\).
- **Break condition:** If the rank \(r\) is too small (e.g., 2), the shared subspaces may become a bottleneck and the merged core could lose specialist information, limiting expressiveness.

### Core‑Space Routing Compresses Router Parameters
- **Claim:** Routing on the low‑rank projection \(\hat{x}\) reduces the router’s parameter count from \(O(N \cdot n)\) to \(O(N \cdot r)\) without sacrificing routing quality.
- **Mechanism:** Instead of taking the full hidden state \(x \in \mathbb{R}^n\) as input, the router uses \(\hat{x} \in \mathbb{R}^r\). Its weight matrix shape changes from \(N \times n\) to \(N \times r\).
- **Evidence:** Section 3.3 explicitly states the reduction; Section 4.4 (Table 5) shows comparable performance between CoMoL with and without core‑space routing, while router params become negligible as experts scale.
- **Break condition:** If routing decisions critically depend on information lost in \(V_A^\top\) (e.g., certain high‑frequency features), router quality could degrade, harming expert selection.

## Foundational Learning
- **Low‑Rank Adaptation (LoRA):** LoRA freezes the original model and injects a low‑rank update \(\Delta W = B A\) where \(B \in \mathbb{R}^{m \times r}, A \in \mathbb{R}^{r \times n}\). This is the base building block for CoMoL. *Quick check:* Compare the parameter count and inference FLOPs of a standard LoRA layer (rank \(r\)) to a fully fine‑tuned linear layer of size \(m \times n\).
- **Mixture‑of‑Experts (MoE) Routing:** MoE allows different inputs to activate different subsets of experts, commonly via token‑level soft or sparse routing. CoMoL adapts this idea to LoRA experts. *Quick check:* For soft‑weighted MoE‑LoRA with \(N\) experts of rank \(r\), how do parameter count and FLOPs scale relative to sparse MoE‑LoRA (top‑k active)?
- **Singular Value Decomposition (SVD) & Matrix Re‑parameterization:** SVD decomposes a matrix into orientation (singular vectors) and magnitude (singular values). CoMoL uses reduced SVD on \(B\) and \(A\) to separate shared orientation (\(U_B, V_A\)) from expert‑specific coupling (\(M\)). *Quick check:* Given \(B \in \mathbb{R}^{m \times r}\) and \(A \in \mathbb{R}^{r \times n}\), what are the dimensions of the SVD components \(U_B, \Sigma_B, V_B^\top\)? How does combining the SVDs of \(B\) and \(A\) yield the core matrix \(M\)?

## Architecture Onboarding
- **Component map:** Input \(x\) → \(V_A^\top\) → \(\hat{x}\) → Router → \(G(\hat{x})\) → Core Experts \(M_i\) (soft‑merge) → \(M_{\text{merged}}\) → \(U_B\) → \(U_B M_{\text{merged}} \hat{x}\) → add \(W x\) → Output \(h\).
- **Critical path:**
  1. Compute \(\hat{x} = V_A^\top x\).
  2. Router on \(\hat{x}\) to obtain token‑level expert weights \(G(\hat{x})\).
  3. Merge core matrices: \(M_{\text{merged}} = \sum_i G_i M_i\).
  4. Apply merged update: \(U_B M_{\text{merged}} \hat{x}\).
  5. Add to frozen backbone output: \(h = W x +\) update.
- **Design tradeoffs:**
  - Rank \(r\): smaller \(r\) reduces all parameters but risks underfitting; larger \(r\) increases capacity.
  - Expert count \(N\): more experts increase potential diversity but raise merging FLOPs (\(O(r^2 N)\)) and risk redundancy.
  - Router capacity: router input dimension is only \(r\); even a linear router is lightweight. More complex routers add negligible parameters but may overfit.
  - Shared bases initialization: \(U_B\) and \(V_A^\top\) are derived from initial LoRA matrices and frozen (or optionally trained). Assuming a shared subspace; if this fails, performance may drop.
- **Failure signatures:**
  - **Routing collapse:** All \(G(\hat{x})_i \approx 1/N\); check router gradient norms and entropy.
  - **Expert redundancy:** All \(M_i\) converge to nearly identical values; monitor pairwise Frobenius norms.
  - **OOM at scale:** While parameters scale favorably, FLOPs for merging (\(L \cdot r^2 \cdot N\)) may become large at high \(r/N\); monitor per‑token FLOPs.
  - **Performance drop vs. LoRA:** If CoMoL underperforms standard LoRA at similar parameter count, the shared‑subspace constraint may be too restrictive.
- **First 3 experiments:**
  1. Validate core‑space FLOP reduction by implementing a toy MoE‑LoRA (\(N=4, r=8, m=n=4096\)) and comparing per‑token FLOPs of output‑level fusion vs. core‑space merging; expect ≈\(N\)× reduction in primary expert FLOPs.
  2. Router parameter scaling test: Fix \(N\), vary \(r\), and measure trainable router parameters for standard MoE‑LoRA (\(O(N \cdot n)\)) vs. CoMoL (\(O(N \cdot r)\)). Show scaling independence from \(n\).
  3. Token‑level vs. instance‑level routing ablation: Replace token‑level \(\hat{x}\) with a sequence‑pooled representation (instance‑level) and evaluate on a fine‑grained task (e.g., code generation). Token‑level should yield a measurable gain.

## Open Questions the Paper Calls Out
1. **Systematic benchmark for PEFT learning capacity:** The authors note that current research lacks a comprehensive benchmark to evaluate different PEFT methods’ ability to acquire new knowledge without catastrophic forgetting. Existing comparisons are task‑specific and do not measure retention of base capabilities. Such a benchmark would test task performance, forgetting, and multi‑domain adaptation.
2. **Validity of the shared‑subspace assumption:** CoMoL assumes that distinct LoRA experts share similar singular subspaces (\(U_B, V_A^\top\)). This assumption underlies the parameter efficiency but is not analyzed. Its validity likely varies with model architecture, data distribution, and expert specialization; subspace similarity metrics and correlation with performance drops could illuminate this.
3. **Impact on calibration and uncertainty:** Token‑level soft‑merging may affect model calibration (confidence‑accuracy alignment). The paper only reports accuracy; no analysis of expected calibration error or uncertainty is provided. The effect could be task‑dependent, especially under ambiguity.
4. **Fundamental limits of core‑space routing:** The router’s expressiveness is constrained by the low‑rank dimension \(r\). While experiments use \(r=8\), the theoretical lower bound of \(r\) that still permits meaningful token‑level routing is unknown. A systematic study varying \(r\) and measuring router quality (load balancing, loss) and downstream performance would clarify this trade‑off.

## Limitations
- The method relies on the assumption that experts share a common low‑rank singular subspace. For highly diverse tasks or models, this may not hold, potentially harming expressiveness.
- The core‑space dimension \(r\) must be sufficiently large; too small a rank could bottleneck both the expert representations and the router’s input quality.
- Router decisions depend on the projection \(V_A^\top x\). If important routing cues are lost in this projection, expert selection may degrade.

## Confidence
- **Parameter efficiency reduction** (from \(O(N \cdot (m+n)r)\) to \(O((m+n)r + N \cdot r^2)\)): **High** (theoretically sound and reflected in reported parameter counts).
- **Token‑level adaptation benefit** over instance‑level methods: **Medium** (supported by comparisons against SMEAR‑like baselines but limited direct ablation).
- **Router compression** (router params \(O(N \cdot r)\) vs \(O(N \cdot n)\)): **High** (explicit analysis and Table 5 show negligible performance change when removing router projection).
- **Overall SOTA** on math and code benchmarks: **Medium** (strong empirical results but generalizability to other models/tasks is uncertain).
