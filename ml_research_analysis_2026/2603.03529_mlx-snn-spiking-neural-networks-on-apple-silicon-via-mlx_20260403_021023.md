# mlx-snn: Spiking Neural Networks on Apple Silicon via MLX

## Quick Facts
- arXiv ID: 2603.03529
- Source URL: https://arxiv.org/abs/2603.03529
- Reference count: 5
- Primary result: First native SNN library for Apple Silicon (MLX) achieves up to 97.28% MNIST accuracy with 2.0–2.5× faster training and 3–10× lower peak GPU memory vs. snnTorch on M3 Max.

## Executive Summary
mlx-snn addresses the lack of native spiking neural network (SNN) support on Apple Silicon by introducing the first SNN library built on Apple's MLX framework. It provides six neuron models, four surrogate gradient functions, and four spike encoding methods, all designed to leverage MLX's unified memory and composable transforms for efficient computation. Validation on MNIST classification demonstrates the library's effectiveness: with a two-layer spiking network, it achieves up to 97.28% test accuracy, while training 2.0–2.5× faster and using 3–10× less peak GPU memory compared to snnTorch on the same M3 Max hardware. These gains stem from MLX's unified memory, which eliminates CPU–GPU transfers during temporal unrolling, and its lazy evaluation, which enables graph-level optimizations.

## Method Summary
The authors evaluate mlx-snn on the MNIST dataset using a simple two-layer feedforward spiking neural network. Input images (28×28) are flattened to 784-dimensional vectors and normalized to [0,1]. These are rate-encoded into Poisson spike trains over T=25 timesteps via `mlxsnn.rate_encode`. The network consists of two linear layers (784→h→10) with LIF neuron layers in between; the output layer uses `reset_mechanism="none"` to retain the final membrane potential for classification. Training employs backpropagation-through-time (BPTT) over the unrolled timesteps, with the forward pass manually unrolled in a Python loop. Loss is computed as cross-entropy on the final membrane output. The Adam optimizer is used with hyperparameters from five configurations (Table 2). MLX's lazy evaluation builds the full computation graph before a single `mx.eval()` call, allowing the runtime to optimize memory allocation and kernel scheduling. This workflow, combined with MLX's unified memory, yields the reported speed and memory improvements.

## Key Results
- Up to 97.28% test accuracy on MNIST (configuration C1 with β=0.85, hidden size 256, learning rate 1e-3, 25 epochs).
- Training speedup of 2.0–2.5× over snnTorch on M3 Max.
- Peak GPU memory reduction of 3–10× compared to snnTorch.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** MLX's unified memory architecture eliminates CPU–GPU data transfers, a primary bottleneck for SNN state-heavy temporal loops.
- **Mechanism:** SNN simulation requires passing neuron state (membrane potential, adaptation variables) between timesteps. On traditional backends like PyTorch with discrete GPU memory, these state tensors must be copied between CPU (for preprocessing/control flow) and GPU (for parallel neuron updates) each timestep. MLX's unified memory allows both host and device to access the same physical memory pool, so state tensors remain in place across the entire unrolled computation.
- **Core assumption:** The SNN workload's mix of Python control flow (temporal unrolling) and heavy tensor operations makes frequent host-device transfers a dominant cost on non-unified systems.
- **Evidence anchors:**
  - [abstract] "...leveraging MLX's unified memory and composable transforms for efficient computation."
  - [section 4] "For SNN workloads that mix data preprocessing (CPU) with neuron simulation (GPU), this eliminates a common bottleneck."
  - [corpus] Corpus evidence is indirect; neighboring papers (e.g., "Benchmarking On-Device Machine Learning on Apple Silicon with MLX") confirm unified memory is a key MLX differentiator but do not analyze SNN-specific state transfer costs.
- **Break condition:** If an SNN implementation on MLX inadvertently forces data to the CPU (e.g., via NumPy conversion or non-MLX ops) within the temporal loop, the benefit is lost. Performance would regress to that of a discrete-memory backend.

### Mechanism 2
- **Claim:** MLX's lazy evaluation allows the full temporal unrolled computation graph for BPTT to be built before execution, enabling graph-level optimizations for memory and kernel scheduling.
- **Mechanism:** In an SNN training loop, the forward pass over T timesteps builds a large computation graph. With lazy evaluation, operations are queued without immediate execution. The graph is only materialized when `mx.eval()` is called at the end of the epoch. This lets the MLX runtime analyze the entire unrolled graph to optimize memory allocation (e.g., reuse buffers for intermediate states) and fuse operations across timesteps.
- **Core assumption:** The cost of building and optimizing a large, dynamic unrolled graph for BPTT is amortized by savings from reduced memory footprint and more efficient kernel launches compared to eager execution where each timestep's operations execute immediately.
- **Evidence anchors:**
  - [abstract] "...lazy evaluation... to enable efficient SNN research."
  - [section 4] "This is advantageous for SNNs because the temporal unrolling loop can build the full computation graph for T timesteps before executing, allowing the MLX runtime to optimize memory allocation and kernel scheduling."
  - [corpus] No direct evidence; "mlx-vis" paper uses lazy evaluation for visualization pipelines but not for BPTT loops.
- **Break condition:** If the training loop forces evaluation (`mx.eval()`) inside the temporal unrolling loop (e.g., to log intermediate states), lazy evaluation's graph-building advantage is negated, leading to higher memory use and slower execution similar to an eager backend.

### Mechanism 3
- **Claim:** MLX's composable function transforms (`mx.grad`, `mx.compile`) enable a clean BPTT implementation with explicit state management, bypassing framework-specific "retain graph" semantics and enabling potential JIT compilation.
- **Mechanism:** BPTT requires differentiating through the unrolled temporal loop. `mx.grad` computes gradients of a function that internally performs the unrolling, naturally handling the history. The explicit state-dict (Python dictionary) passed to neurons is immutable-friendly, making the forward function pure and thus eligible for `mx.compile` JIT (though not yet applied in v0.2.1 due to Python control flow). This contrasts with PyTorch, where hidden state is often a mutable tensor requiring `retain_graph=True` and careful memory management.
- **Core assumption:** A functional, state-explicit API composes correctly with automatic differentiation transforms and will allow JIT compilation once Python control flow in unrolling is minimized (e.g., via `mx.scan` in future versions).
- **Evidence anchors:**
  - [abstract] "...composable function transforms (`mx.grad`, `mx.compile`) to enable efficient SNN research."
  - [section 3.5] "The `bptt_forward` utility unrolls a model over T timesteps... `mx.grad` transform computes gradients of arbitrary functions, enabling clean BPTT without framework-specific 'retain graph' semantics."
  - [section 6] "`mx.compile` is not yet applied to the training loop due to Python control flow in temporal unrolling."
- **Break condition:** If the SNN model includes non-differentiable or non-MLX operations inside the unrolled loop, `mx.compile` cannot fuse the graph. Currently, manual unrolling with Python `for` loops prevents JIT compilation, leaving performance on the table until a `mx.scan`-based implementation is adopted.

## Foundational Learning
- **Concept: Spiking Neuron Dynamics & State Management**
  - **Why needed here:** mlx-snn's entire API is built around discrete-time state updates (membrane potential, adaptation, synaptic currents). A user must understand how state dictionaries are initialized (`init_state`), passed through each timestep, and reset to design correct models (e.g., output layers use `reset_mechanism="none"`). Misunderstanding state leads to incorrect temporal integration or gradient flow issues.
  - **Quick check question:** If an LIF neuron has `beta=0.9` and initial membrane `0.0`, what is the membrane after 5 timesteps of constant input `0.5` (threshold `1.0`, no spikes)?
- **Concept: Surrogate Gradient Learning for BPTT**
  - **Why needed here:** The non-differentiable spike function (`Heaviside`) is replaced by a smooth surrogate during backward passes. The choice of surrogate (fast sigmoid, arctan, STE) and its hyperparameters directly impacts training stability and final accuracy. The paper's STE workaround is a critical implementation detail stemming from MLX's limitations.
  - **Quick check question:** Why does the Straight-Through surrogate underperform in Table 3 compared to fast sigmoid, given they both use a STE pattern?
- **Concept: Apple Silicon Unified Memory & Immutability**
  - **Why needed here:** MLX arrays are immutable and live in a unified memory space. Code that works in PyTorch with in-place ops (`mem += x`) will fail in MLX. Users must adopt functional updates (`mem = beta * mem + x`). Understanding that "GPU memory" in MLX metrics is actually Metal's allocation from the unified pool is key to interpreting the 3–10× memory reduction claim.
  - **Quick check question:** How does the immutability requirement affect the typical SNN training loop pattern where you accumulate gradients over multiple timesteps before an optimizer step?

## Architecture Onboarding
- **Component map:** Encoder -> (Linear -> Neuron)*T -> FinalState -> Loss -> BPTT (mx.grad) -> Optimizer -> mx.eval
- **Critical path:** Input batch → Spike encoder → [T times: (Linear → Neuron layer update with state)] → Extract final state (membrane) → Cross-entropy loss → `mx.grad` → Optimizer step → `mx.eval()`
- **Design tradeoffs:**
  - **API compatibility vs. MLX idioms:** The snnTorch-compatible API lowers migration friction but may obscure MLX-specific optimizations (e.g., using `mx.compile` requires rethinking unrolling).
  - **STE surrogate vs. custom VJP:** The STE pattern (Eq. 12) is a workaround for an MLX shape bug; it's functionally equivalent but may have subtle numerical differences. A true custom VJP would be cleaner but is currently unstable.
  - **Manual unrolling vs. `mx.scan`:** Manual Python loops are simple and work but prevent JIT compilation. Future versions should use `mx.scan` for the temporal loop to enable `mx.compile`.
- **Failure signatures:**
  - **Accuracy ~46%:** Using Straight-Through surrogate with default scale (s=1) on MNIST (Table 3). Fix: use fast sigmoid or arctan with tuned hyperparameters.
  - **Memory blowup (>1GB GPU):** Accidentally keeping references to all intermediate states across timesteps (e.g., appending to a list inside the loop) prevents garbage collection under lazy evaluation. Fix: ensure only final state or minimal needed intermediates are retained.
  - **Slow training (close to snnTorch CPU):** Forcing `mx.eval()` inside the timestep loop or using non-MLX ops (NumPy) that break the lazy graph. Fix: move all data processing to MLX ops and call `mx.eval()` only once per batch/epoch.
- **First 3 experiments:**
  1. **Replicate MNIST baseline (C5):** Train the exact model from Listing 2 with `beta=0.95`, `h=128`, `lr=2e-3`, `T=25`, fast sigmoid. Verify test accuracy ~94-95% and 2–2.5× speedup vs. snnTorch MPS. This validates end-to-end setup and hardware advantage.
  2. **Neuron dynamics sanity check:** Simulate each of the 6 neuron models with constant input (as in Figure 2). Visually confirm characteristic traces (LIF reset, Izhikevich recovery, ALIF adaptation). This ensures core neuron implementations are correct independent of training.
  3. **Surrogate gradient sweep:** On a single small config (e.g., `h=64`, 5 epochs), test fast sigmoid (k=25), arctan (α=2), and STE (s=1). Expect fast sigmoid > arctan > STE. This confirms the surrogate gradient is the primary source of the ~1% accuracy gap to snnTorch.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** What is the root cause of the accuracy gap between mlx-snn and snnTorch on MNIST, and how can the STE-based surrogate gradient be improved within MLX's constraints?
- **Basis in paper:** The paper attributes the ~1 percentage point accuracy gap to the STE workaround used due to MLX's shape inconsistency in mx.custom_function, expecting it to narrow as MLX matures.
- **Why unresolved:** The STE pattern limits gradient flow compared to native custom VJP definitions, which are currently unusable in MLX.
- **What evidence would resolve it:** Fixing the MLX shape bug and implementing native custom VJPs for surrogate gradients, followed by empirical accuracy comparisons on MNIST configurations.

### Open Question 2
- **Question:** How can the BPTT training loop in mlx-snn be restructured to enable JIT compilation with mx.compile, overcoming Python control flow in temporal unrolling?
- **Basis in paper:** The paper states mx.compile is not applied due to Python control flow in the unrolled temporal loop.
- **Why unresolved:** Explicit for-loops over timesteps prevent MLX from capturing the full computation graph for optimization.
- **What evidence would resolve it:** A functional or vectorized redesign of the forward pass (e.g., using mx.scan) that eliminates Python loops, allowing mx.compile to optimize memory and kernel scheduling.

### Open Question 3
- **Question:** Do mlx-snn's efficiency advantages in training speed and memory usage generalize to neuromorphic datasets and larger SNN architectures?
- **Basis in paper:** The library is validated only on MNIST, and the roadmap calls for larger-scale benchmarks and neuromorphic dataset loaders.
- **Why unresolved:** MNIST uses rate coding and is low-dimensional; neuromorphic data (e.g., DVS) has sparse, event-driven spikes that may challenge unified memory and lazy evaluation.
- **What evidence would resolve it:** Implementing loaders for datasets like N-MNIST, DVS-Gesture, and SHD, then benchmarking training time, peak memory, and accuracy on these tasks compared to other backends.

## Limitations
- Rate encoding specifics: The exact scaling of pixel values to Poisson spike probabilities in `mlxsnn.rate_encode` is not documented, hindering precise replication.
- STE surrogate workaround: The library uses a Straight-Through estimator due to a shape bug in MLX's custom function support, which may lead to suboptimal gradient flow and contribute to the accuracy gap.
- Validation scope: Evaluation is limited to MNIST; performance on neuromorphic datasets (e.g., DVS, N-MNIST) and with deeper architectures remains unproven.
