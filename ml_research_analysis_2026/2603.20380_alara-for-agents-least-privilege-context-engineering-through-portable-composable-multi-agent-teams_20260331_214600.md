# ALARA for Agents: Least-Privilege Context Engineering Through Portable Composable Multi-Agent Teams

## Quick Facts
- **arXiv ID:** 2603.20380  
- **Source URL:** https://arxiv.org/abs/2603.20380  
- **Reference count:** 40  
- **Primary result:** The CAT framework enforces least-privilege tool access via structural constraints, demonstrating that tool-use reliability is a distinct capability strongly correlated with general intelligence (MMLU r≈0.8).

## Executive Summary
Multi-agent systems often rely on fragmented behavioral specifications—prose files, framework configs, and external servers—making it difficult to share, version, and enforce consistent capabilities. This fragmentation leads to capability degradation and security vulnerabilities. To address this, the authors propose a declarative context-agent-tool (CAT) data layer, where interrelated files structurally define each agent's minimal tool set (called a Jinx list), context, and team roles. By enforcing least-privilege access at the schema level, the system prevents agents from invoking tools outside their Jinx list, guaranteeing behavioral change through structural constraints rather than interpretive prompts.

The authors evaluate the framework on a benchmark of 115 tasks across 13 categories using 22 locally-hosted models (0.6B–35B parameters) and approximately 2,500 executions. Key findings include: tool-use reliability is a distinct, trainable capability; model performance correlates strongly with general intelligence as measured by MMLU (r≈0.8), though outliers indicate skill-specific training effects; tool call volume is the strongest predictor of success (r≈0.7); and delegation tasks are consistently the hardest, with the lowest pass rate (~20%) and minimal retry gain. The results underscore the importance of structural enforcement and provide insights into the nature of tool use in language models.

## Method Summary
The core contribution is the NPC shell (npcsh), an implementation of the CAT data layer. Agents are defined by a set of portable, composable files: a Jinx list specifies allowed tools; context files provide persistent memory; and team role files define inter-agent responsibilities. The framework reads these specifications to gate tool usage: any tool call not present in the agent's Jinx is rejected at runtime. To assess effectiveness, the authors constructed a benchmark of 115 tasks covering 13 operational categories (e.g., file operations, shell commands, web search, delegation). Each task includes a natural-language instruction and a filesystem-state verification command. Using Ollama, they ran 22 open-source models (0.6B to 35B parameters) on consumer hardware. Each task was given a 360-second timeout and up to five retry attempts with error feedback. The primary metric was pass rate (successful verification), supplemented by tool call count, task duration, attempt count, and retry gain by category. No model training was performed; the study focuses on the impact of structural constraints and model characteristics on agency performance.

## Key Results
- Structural constraints (Jinx lists) enforce least-privilege tool access, preventing any unauthorized tool invocation.
- Tool-use reliability is a distinct capability: overall performance correlates with MMLU scores (r≈0.8), and tool call volume is an even stronger predictor of success (r≈0.7). Inter-family differences dominate scaling trends, and outliers suggest skill-specific training effects.
- Delegation tasks are the most failure-prone, with a pass rate around 20% and negligible improvement upon retries, highlighting a fundamental challenge in multi-agent orchestration.

## Why This Works (Mechanism)
The mechanism hinges on shifting behavioral control from prompts, which can be ignored or overridden, to a schema-level allowlist that is programmatically enforced. Each agent's Jinx list is a manifest of approved tools; the npcsh runtime checks every attempted tool call against this manifest before execution. This airtight gating eliminates the possibility of an agent using a tool it shouldn't, thereby enforcing least-privilege by construction. Moreover, the declarative files are portable and versionable, allowing teams of agents to be assembled and shared easily, reducing fragmentation. The separation of specification (what tools) from execution (how to use) ensures consistent behavior across different models and environments. The strong correlation between tool call volume and success suggests that models which effectively leverage their permitted tools—making more calls and chaining them—solve more tasks, which the framework naturally encourages by allowing only those tools that are necessary and safe.

## Foundational Learning
- **Declarative specification:** Why needed? To separate policy from code, enabling version control, reproducibility, and composition of agent behaviors without modifying runtime logic. Quick check: Can agent capabilities be altered by editing a configuration file without touching the shell's source?
- **Least-privilege access:** Why needed? To minimize potential damage from agent mistakes or malicious outputs, a core security principle. Quick check: Does the system block attempts to use tools not listed in the Jinx?
- **Schema validation:** Why needed? To catch structural errors in CAT files early, preventing runtime failures. Quick check: Are malformed Jinx or context files rejected at load time?
- **Delegation as a first-class primitive:** Why needed? To enable complex multi-agent workflows where tasks are broken down and assigned to sub-teams. Quick check: Can an agent invoke a delegation tool to spawn a sub-team defined in separate CAT files?

## Architecture Onboarding
**Component map:** CAT Spec (Jinx, Context, Roles) -> NPC Shell -> Model Inference -> Tool Execution (Jinx validated) -> Environment -> Verification

**Critical path:** (1) Load CAT Spec; (2) Construct initial prompt with task instruction and context; (3) Model generates an action (tool call or answer); (4) If tool call, NPC Shell checks Jinx allowlist; (5) If allowed, Tool Execution runs and returns output; (6) Output appended to context; (7) Repeat from (2) until verification passes or timeout/retries exhausted.

**Design Tradeoffs:**  
- Declarative vs. imperative: Declarative improves security and reproducibility but may lack dynamic adaptation.  
- Local models vs. cloud APIs: Local execution reduces cost and increases control but limits model scale and speed.  
- Strict Jinx gating vs. flexibility: Sound security but risks over-restriction; finding the right permission set is a manual tradeoff.  
- Fixed team roles vs. dynamic delegation: Fixed roles simplify orchestration; dynamic delegation can handle unforeseen sub-tasks but complicates context and permission management.

**Failure Signatures:**  
- "Tool not found": indicates missing Jinx entry or tool misnaming.  
- Repetitive identical tool calls: model stuck, possibly from context overflow or insufficient feedback.  
- Early termination with non-zero verification: agent gave an incorrect final answer.  
- Delegation failures: errors like "sub-team not found" or permission errors in delegation tool, often due to missing delegation Jinx or incomplete sub-team specs.  
- Timeouts: excessive steps or slow model, may point to delegation overhead or reasoning inefficiency.

**First Experiments:**  
1. Run a simple file listing task with a single agent to confirm that only tools in the Jinx (e.g., `ls`) succeed and others (e.g., `rm`) are blocked, checking logs for "tool not found".  
2. Create a two-agent team where the primary agent delegates a web search to a secondary agent; verify that delegation is allowed in the primary's Jinx and that the secondary has the search tool, and observe the handoff and result integration.  
3. Compare three tasks of varying difficulty across a small (0.6B) and medium (7B) model to empirically measure tool call frequency, success rates, and retry improvements, testing the reported correlations.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** Why does delegation remain the most failure-prone task category with negligible retry improvement?
- **Basis in paper:** Delegation has the lowest pass rate (~20%) and smallest retry gain (~3 percentage points) across all models (Figure 5, Section III).
- **Why unresolved:** The paper identifies delegation as difficult but does not analyze trace-level failure modes to determine whether issues stem from orchestrator routing, sub-team communication, context management, or Jinx delegation design.
- **What evidence would resolve it:** Fine-grained trace analysis of failed delegation tasks, categorizing errors by stage (routing decision, sub-team invocation, result synthesis) and correlating with model size, team structure, and retry feedback.

### Open Question 2
- **Question:** What training or architectural factors cause certain models (e.g., Qwen3.5:2b, Gemma3:27b) to deviate significantly from the strong MMLU-agency correlation (r≈0.8), indicating disproportionately high or low tool-use reliability?
- **Basis in paper:** Figure 3 shows several labeled outliers beyond the 1σ band of the regression line, suggesting skill-specific training effects.
- **Why unresolved:** The paper notes these outliers but does not investigate the specific characteristics (e.g., tool-use fine-tuning data, reinforcement learning from human feedback, architectural modifications) that lead to such divergence.
- **What evidence would resolve it:** Comparative studies of outlier models' training curricula, ablation experiments removing tool-related objectives, and analysis of internal representations during tool selection tasks.

### Open Question 3
- **Question:** Does higher tool call volume directly cause better benchmark scores by enabling effective multi-step chaining, or is it merely a proxy for an underlying sequential reasoning capacity that could achieve similar results with fewer calls?
- **Basis in paper:** The paper reports a strong positive correlation (r≈0.7) between mean tool calls per task and agency score, but the observational design cannot establish causality.
- **Why unresolved:** The correlation could reflect efficient problem-solving or wasteful retries; the two behavioral clusters (persisting without convergence vs. genuine multi-step with fast failure exits) hint at distinct strategies but are not experimentally disentangled.
- **What evidence would resolve it:** Controlled interventions that limit tool call budgets or incentivize minimal-step solutions, measuring impact on success rates, coupled with success-trace analysis to identify necessary versus redundant calls per task category.

## Limitations
- **Benchmark transparency:** Exact task definitions, verification commands, and their mapping to agent Jinx lists are not fully described, impeding exact replication.
- **Hardware ambiguity:** The evaluation mentions "consumer hardware" and Ollama but does not specify GPU models, memory, or inference parameters, leading to potential performance variability.
- **Causal claims unverified:** Reported correlations (e.g., tool call volume vs. success, MMLU vs. agency) are observational; without controlled ablations, causality cannot be established.
- **Scope limitation:** Experiments used local open-source models; results may not generalize to proprietary or cloud-based models with different tool-use implementations or safety filters.
