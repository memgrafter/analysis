# No Single Best Model for Diversity: Learning a Router for Sample Diversity
## Quick Facts
*   **arXiv ID:** 2604.02319
*   **Source URL:** https://arxiv.org/abs/2604.02319
*   **Reference Count:** 40
*   **Primary Result:** A learned router using binary classification with model-specific query encodings achieves 26.3% diversity coverage on NB-WildChat, beating the best single-model baseline (23.8%) by 2.5% absolute.

## Executive Summary
This paper addresses the challenge of generating comprehensive, high-quality, and diverse answer sets for open-ended queries using large language models (LLMs). It finds that no single LLM consistently produces the best answer set across all queries. To exploit model-specific strengths, the authors propose a routing system that predicts, for each new query, which model from a pool will yield the most diverse and high-quality answers. The router is trained using a novel "diversity coverage" metric that rewards unique, high-quality answers relative to an ideal set. Empirical evaluation on multiple benchmarks shows the router significantly outperforms always selecting the top overall model, with modest inference overhead compared to brute-force oracle selection.

## Method Summary
The core method is a query-dependent router that selects the best model from a pool of 18 LLMs to maximize a proposed "diversity coverage" metric. Training requires oracle labels: for each training query, all models generate 50 answers using a "generate all" prompt, and the model with the highest diversity coverage score is labeled as the best. The router uses a binary classification framework. For each candidate model `m_i`, a separate two-layer MLP classifier `r_i(θ)` takes a query representation and predicts whether `m_i` is the oracle best. At inference, all classifiers score a new query, and the model with the highest score is selected to generate its answers. The query representation is model-specific: it is the last-layer hidden state when `m_i` itself processes the query, which proved most effective.

## Key Results
*   The router (Binary MLP with model-specific encodings) achieves 26.3% diversity coverage on NB-WildChat test, a 2.5% absolute gain over the top single-model baseline (23.8%).
*   It generalizes to the out-of-distribution NB-Curated dataset, achieving 40.7% vs. the baseline's 38.6%.
*   Inference overhead is modest (2–3× versus using the single best overall model), far below the 19× cost of the brute-force oracle that evaluates all models.

## Why This Works (Mechanism)
### Mechanism 1
*   **Claim:** A learned router can predict which LLM will generate the most diverse and high-quality answer set for a given query without brute-force sampling from all models.
*   **Mechanism:** The router uses a binary classification framework. For each candidate model `m_i`, a separate classifier `r_i(θ)` takes a query encoding and predicts the probability that `m_i` is the oracle best model. At inference, all classifiers score the query and the model with the highest score is selected. This avoids the exponential cost of evaluating diversity coverage across all models.
*   **Core assumption:** The representation of a query (using model-specific last-layer hidden states) contains signal about which model's decoding behavior will yield a more diverse and higher-quality answer set for that query.
*   **Evidence anchors:**
    *   [abstract] "...a router that predicts the best model for each query...using binary classification with model-specific query encodings."
    *   [section 4.1] Describes the binary classification setup and model-specific encodings (`spec`).
*   **Break condition:** If model-specific query representations fail to correlate with downstream diversity coverage (e.g., due to distribution shift in new query domains), the router's predictions will not identify the best model, and performance will degrade to a random or overall-best baseline.

### Mechanism 2
*   **Claim:** The "diversity coverage" metric effectively captures the joint goal of maximizing the number of distinct, high-quality answers for open-ended queries.
*   **Mechanism:** For a generated answer set `A` of size `B`, the metric sums the quality scores of all *unique* answers (determined by an equivalence classifier) and normalizes by the maximum achievable score with `B` distinct, maximum-quality answers. This rewards sets that cover more of the valid answer space with high quality.
*   **Core assumption:** A well-calibrated reward model can reliably score the quality of individual answers for open-ended queries, and an equivalence classifier can accurately determine semantic uniqueness.
*   **Evidence anchors:**
    *   [abstract] Introduces diversity coverage as measuring "cumulative quality of unique answers relative to an ideal set."
    *   [section 2.2] Formal definition and comparison to prior metrics.
*   **Break condition:** If the reward model's quality scores are biased or miscalibrated, or if the equivalence classifier incorrectly merges distinct answers or splits equivalent ones, the computed diversity coverage will not reflect true human-perceived diversity and quality.

### Mechanism 3
*   **Claim:** Ensembling outputs from multiple LLMs by selecting the best model *per query* yields significant gains over using a single top-performing model across all queries.
*   **Mechanism:** Pilot experiments show that different LLMs excel on different queries (no single model dominates). An oracle that always picks the best model per query achieves a large gap over the single best overall model (33.0% vs 23.8% div-cov on NB-WildChat). The router approximates this oracle.
*   **Core assumption:** The models in the pool have sufficiently complementary strengths—their areas of "best performance" are not perfectly correlated across the query distribution.
*   **Evidence anchors:**
    *   [section 3.1] Figure 1 and analysis showing no single model dominates; many models are best on disjoint query subsets.
    *   [section 3.2] Table 2: Oracle "Top model per query" substantially outperforms "Top overall model".
*   **Break condition:** If all models' performance is highly correlated across queries (e.g., one model is always best or rankings are nearly identical), then per-query selection provides minimal benefit over a single top model.

## Foundational Learning
*   **Concept: Diversity Coverage Metric**
    *   **Why needed here:** It is the core optimization objective. The entire routing system is trained to maximize this metric. Understanding its calculation (unique answer extraction, quality scoring, normalization) is crucial to interpret results.
    *   **Quick check question:** Why is a normalized metric necessary instead of just summing the quality scores of unique answers?
*   **Concept: Model-Specific Query Encodings**
    *   **Why needed here:** The router's best-performing variant (Binary MLP (spec)) uses the last-layer hidden state of each candidate model when processing the query. This encodes how *that specific model* internally represents the query.
    *   **Quick check question:** What is the hypothesized advantage of model-specific encodings over a single model-agnostic encoder (like Inf-Retriever)?
*   **Concept: Binary Classification per Model vs. Multi-class Classification**
    *   **Why needed here:** The paper's best router uses `|M|` independent binary classifiers rather than a single `|M|`-way classifier. This design choice impacts training data construction, loss function, and prediction logic.
    *   **Quick check question:** What are the potential advantages of the binary setup? (Hint: consider label imbalance and model ties.)

## Architecture Onboarding
*   **Component map:** Query Encoder -> Scoring Heads -> Router Logic -> Generation Module -> (Offline) Diversity Coverage Calculator.
    *   **Query Encoder:** Generates a representation of the input query. Two variants: (a) Model-agnostic (Inf-Retriever), (b) Model-specific (final layer hidden state from each candidate model `m_i`).
    *   **Scoring Heads:** For Binary MLP: `|M|` separate 2-layer MLP classifiers, each taking the query representation (for its corresponding model) and outputting a score in [0,1]. For M-way MLP: a single MLP taking a model-agnostic query representation and outputting a distribution over `|M|` models.
    *   **Router Logic:** At inference, run all relevant scoring heads on the query, select the model(s) with the highest score(s).
    *   **Generation Module:** The selected LLM(s) generate up to `B` answers using a "generate all" style prompt.
    *   **Diversity Coverage Calculator:** (Offline, for training/evaluation) Uses an equivalence classifier and reward model to process the generated set and compute the metric.
*   **Critical path:**
    *   **Training:** For each training query `q_j`, compute oracle label `i*_j` by finding the model with highest diversity coverage (requires brute-force generation from all `|M|` models). Store `(q_j, i*_j)`. Train the router (binary or multi-class) to predict `i*_j`.
    *   **Inference:** Given a new query `q`, encode it, run the trained classifier(s) to get scores for each model, pick the top model (or top-2), then run that model's generation to produce the answer set.
*   **Design tradeoffs:**
    *   **Encoding choice:** Model-specific (`spec`) encodings yield best in-domain performance (NB-WildChat) but worse OOD generalization (NB-Curated) compared to model-agnostic (`agn`).
    *   **Number of models to route:** Routing to one model is cheaper (2-3x overhead vs. top model). Routing to two models gives further gains but doubles sampling cost. The paper finds marginal benefit beyond two models in oracle experiments.
    *   **Prompt strategy:** The "generate all" prompt maximizes diversity coverage for the router but suffers from decreasing answer quality later in the list. "Generate one" has higher per-answer quality but lower overall diversity.
*   **Failure signatures:**
    *   **Poor generalization:** Router trained on `G-All` prompt performs poorly when used with `G-1` or `G-2` prompts (Table 7). Similarly, `spec` encodings generalize worse OOD.
    *   **Overfitting to training distribution:** If the training queries are not representative, the router may learn spurious correlations. The paper mitigates this by using a large, diverse dataset (NB-WildChat) and showing improvement with more training data (Figure 2, Table 5).
    *   **Inference overhead:** While much lower than brute-force oracle, routing still adds latency because the selected model is often larger than the "top overall" model (which was a small 1B parameter model).
*   **First 3 experiments:**
    1.  **Pilot Study (Section 3.1):** Evaluate 18 models on NB-WildChat. Show that no single model is best for all queries (Figure 1) and that a significant portion of queries have a clear "dominant" model (using a 5% margin threshold). This establishes the potential for per-query routing.
    2.  **Oracle Ensembling Upper Bound (Section 3.2):** For a fixed budget `B`, compare strategies: top overall model, top two overall models, random model per query, and *oracle* top model per query. The oracle shows the maximum possible gain from per-query selection (Table 2), motivating the router's goal.
    3.  **Router Training & Evaluation (Section 5.1):** Implement several router baselines (KNN, BERT, MLP with `agn`/`spec` encodings). Train on NB-WildChat train split. Evaluate on test splits (in-domain) and NB-Curated (OOD). Key result: Binary MLP (spec) achieves 26.3% div-cov on NB-WildChat, significantly beating the top overall baseline (23.8%) and generalizing competitively to NB-Curated (Table 3).

## Limitations
*   The diversity coverage metric depends entirely on an external reward model (Skywork-Reward-Gemma-2-27B-v0.2) and an equivalence classifier; biases or miscalibration in these components invalidate results.
*   The router's best in-domain performance (Binary MLP with model-specific encodings) generalizes poorly out-of-domain compared to model-agnostic variants, limiting deployment flexibility.
*   Training requires exhaustive oracle labels from brute-force sampling across all models for every training query, which is computationally expensive and may not scale to larger model pools or query distributions.

## Confidence
*   **Per-query routing gains:** High. Solid empirical evidence from oracle experiments and consistent router improvements over strong baselines on in-domain data.
*   **Router prediction mechanism (binary classification with model-specific encodings):** Medium. Strong in-domain results but OOD degradation and sensitivity to encoding extraction suggest the learned signal is fragile and dataset-dependent.
*   **Diversity coverage metric validity:** Medium. The formulation is clear and motivated, but ultimate validity hinges on un-calibrated reward/equivalence models whose decisions are not human-validated in the paper.
