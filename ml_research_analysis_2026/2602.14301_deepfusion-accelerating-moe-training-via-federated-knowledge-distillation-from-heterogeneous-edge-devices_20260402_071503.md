# DeepFusion: Accelerating MoE Training via Federated Knowledge Distillation from Heterogeneous Edge Devices
## Quick Facts
- **arXiv ID**: 2602.14301
- **Source URL**: https://arxiv.org/abs/2602.14301
- **Reference count**: 36
- **Primary result**: Matches centralized MoE training while achieving up to 71% lower communication cost and up to 5.28% better token perplexity compared to federated baselines.

## Executive Summary
DeepFusion is a one-shot federated learning framework for training large Mixture-of-Experts (MoE) language models on resource-constrained edge devices. Instead of requiring devices to host large local MoE models, each device trains its own lightweight LLM on private data and uploads it once to a central server. The server clusters these heterogeneous models into K knowledge domains, creates proxy models by weight averaging, and then performs cross-architecture knowledge distillation into K MoE base models using a novel View-Aligned Attention (VAA) module. The base models are merged into a global MoE and fine-tuned. Evaluated on medical QA (Qwen-MoE) and financial open-ended QA (DeepSeek-MoE), DeepFusion matches the performance of centralized training (DeepSpeed) and outperforms existing federated baselines, with significant reductions in communication overhead and improvements in token-level perplexity.

## Method Summary
DeepFusion operates in three server-side stages after a single round of local uploads. First, the server clusters the uploaded on-device LLMs into K groups (K = number of desired MoE experts) using low-rank feature embeddings derived from the devices' private data; each cluster yields a proxy model by averaging weights. Second, for each proxy, a separate MoE base model is trained via knowledge distillation, where the student uses the VAA module to align its multi-stage features with the teacher's perspective, combined with standard KD losses (KL divergence, cross-entropy). Third, the K base models are merged: FFN layers are copied to individual experts while other parameters are averaged; then the shared layers, embedding, and gating are fine-tuned on public benchmark data while experts are frozen. This approach scales to many devices, supports heterogeneous local architectures, and dramatically reduces communication by eliminating iterative rounds.

## Key Results
- Matches DeepSpeed centralized training performance on both medical and financial QA benchmarks.
- Outperforms federated baselines (FedJETS, FedKMT, OFA-KD) in token accuracy/perplexity.
- Reduces total communication cost by up to 71% and improves token perplexity by up to 5.28% relative to the best prior federated method.

## Why This Works (Mechanism)
### Mechanism 1: One-Shot Federated Knowledge Transfer
- **Claim**: DeepFusion reduces communication overhead by employing a one-shot federated learning paradigm where edge devices upload their locally trained on-device LLMs only once, shifting all knowledge distillation to the server.
- **Mechanism**: Each edge device trains a lightweight LLM on its private data until local convergence. The trained model is then transmitted to the central server in a single round. The server aggregates knowledge from all uploaded models via federated knowledge distillation to form the global MoE model, eliminating repeated communications.
- **Core assumption**: Local training on diverse private data yields models that capture domain-specific knowledge transferable via distillation; and the server possesses adequate computational resources to perform distillation centrally.
- **Evidence anchors**:
  - Abstract: "Once local training is sufficient, the trained LLMs are uploaded in a single round to the central FL server for knowledge transfer."
  - Section IV.A: "In contrast to traditional FL with multiple communication rounds, DEEP FUSION employs a one-shot FL design to enhance communication efficiency... total communication cost ..."
  - Corpus signals indicate related work on federated knowledge distillation (e.g., FedKMT, OFA-KD) but none implement a one-shot approach for MoE; DeepFusion appears novel in combining one-shot with MoE.
- **Break condition**: If local data is highly non-IID, local models may not converge to useful representations; if server resources are insufficient, distillation becomes a bottleneck.

### Mechanism 2: Local Knowledge Clustering for Scalable Fusion
- **Claim**: To handle a large number of participating devices, DeepFusion clusters on-device LLMs into K knowledge domains (matching the number of MoE experts) and creates a single proxy model per cluster via weight averaging, enabling scalable knowledge transfer.
- **Mechanism**: Upon receiving an on-device LLM, the server also obtains low-rank feature embeddings computed from the device's training data (preserving privacy). Using cosine similarity of these embeddings, the server groups models into K clusters via KMeans. For each cluster, a proxy model is generated by element-wise averaging of the model weights.
- **Core assumption**: Models trained on semantically similar data (as indicated by feature embeddings) will have similar weight landscapes such that averaging produces a meaningful proxy; and the number of clusters K aligns with the MoE expert count.
- **Evidence anchors**:
  - Section IV.B: "These feature embeddings en capture the semantic information of local data while preserving privacy... Based on this similarity matrix Π, the on-device LLMs are grouped into K local knowledge domains {Ci}K i=1 using KMeans. Then... a proxy model ¯mi is generated by averaging the weights of the clustered on-device LLMs."
  - Abstract: "the central server clusters the collected on-device LLMs into K knowledge domains, creates proxy models by weight averaging"
  - Corpus: Related work on federated clustering (e.g., HFedMoE) but DeepFusion's use of feature embeddings for MoE expert alignment is distinctive.
- **Break condition**: If feature embeddings fail to capture domain similarity, clustering may be erroneous; if cluster sizes vary drastically, proxy models may be biased toward larger clusters.

### Mechanism 3: View-Aligned Attention for Cross-Architecture Distillation
- **Claim**: The View-Aligned Attention (VAA) module resolves the view-mismatch problem between heterogeneous teacher (local proxy) and student (MoE base) models by aligning their predictive perspectives via multi-stage feature integration.
- **Mechanism**: Both teacher and student models are split into J representation stages. The student's features from all stages are patched, projected, and concatenated into a matrix F^S. A multi-head self-attention module processes F^S to produce a blended feature F^{S'} that captures a perspective aligned with the teacher. The blended features are split back into stage-wise features {F^{S'}_j} which are then matched to the teacher's stage features via MSE loss, combined with KL divergence on logits.
- **Core assumption**: The student can mimic the teacher's predictive behavior by adaptively reweighting its multi-stage features; and aligning intermediate features is more effective than aligning only final logits for cross-architecture transfer.
- **Evidence anchors**:
  - Section IV.C: "the proposed VAA module employs a multi-head attention mechanism, enabling the student model to integrate its features from various representation stages, thus acquiring a predictive perspective comparable to that of the teacher model."
  - Abstract: "proposes a novel View-Aligned Attention (VAA) module that integrates multi-stage feature representations from the global MoE model to construct a predictive perspective aligned with on-device LLMs"
  - Corpus: Corpus includes OFA-KD which aligns via logits space; VAA differs by using multi-stage attention for perspective alignment.
- **Break condition**: If the student's architecture is too shallow to provide informative multi-stage features, attention may fail; if teacher and student have totally different inductive biases, alignment may be impossible.

## Architecture Onboarding
**Component map**:
Edge Devices (trained local LLMs + feature embeddings) -> Upload -> Central Server (Local Knowledge Clustering -> Proxy Model Generator -> Cross-Architecture Distillation (with public data) -> Global MoE Merge -> Global MoE Fine-Tuning) -> Global MoE Model

**Critical path**:
1. Local training: Each device trains its LLM on private data until convergence.
2. Upload: Devices send model weights and feature embeddings to server.
3. Clustering: Server computes similarity matrix via embeddings, runs KMeans to get K clusters.
4. Proxy creation: For each cluster, average weights to form proxy model.
5. Distillation: For each proxy, distill into a separate MoE base model using VAA (with public data).
6. Merging: Combine K base models into global MoE as per merging rule (copy FFN layers, average others).
7. Fine-tuning: Update non-expert parameters (embedding, self-attention, gating, output) of global MoE on public data while freezing experts.

**Design tradeoffs**:
- One-shot vs. multi-round: One-shot reduces communication but requires server to handle all computation; multi-round could distribute load but increase communication.
- Clustering vs. individual: Clustering improves scalability (only K distillations) but may lose per-device nuances; individual distillation would be O(N) server workload.
- Feature-based vs. logits-based: Feature matching (via VAA) captures intermediate knowledge but adds complexity; logits-only is simpler but may miss fine-grained patterns.
- Heterogeneity support: Allowing any on-device LLM increases participation but complicates distillation; requiring same architecture simplifies but limits device inclusion.
- Expert freezing: Freezing experts after merging reduces fine-tuning cost but may limit adaptation; full fine-tuning could improve performance but is expensive.

**Failure signatures**:
- High token perplexity on validation set indicates poor knowledge transfer.
- Low inter-cluster similarity (experts not specializing) suggests clustering or merging failed.
- VAA loss diverges or remains high indicates alignment module not learning.
- Communication cost higher than expected suggests one-shot not implemented correctly.
- Server memory exhaustion during distillation indicates scalability issues.

**First 3 experiments**:
1. Communication cost benchmark: Compare DeepFusion's total upload size (sum of on-device model sizes) against FedJETS (which requires multiple rounds and larger local models) across varying device counts.
2. Performance validation: Evaluate global MoE's token perplexity and accuracy on test data for both case studies (medical QA, financial QA) and compare against centralized (DeepSpeed) and other federated baselines (FedJETS, FedKMT, OFA-KD).
3. Ablation on VAA: Replace VAA with standard logits-based distillation (e.g., OFA-KD) and measure performance drop to validate the importance of view alignment.

## Limitations
- VAA module design details (patch size, stage selection, projection dimensions) are underspecified, risking implementation drift.
- Clustering embedding hyperparameters (MiniLM variant, layer, output dimension) are vague, affecting domain separation quality.
- Evaluation is limited to two domains (medical and financial), so broader generalization remains unknown.

## Confidence
- One-shot communication reduction: **High**
- Clustering-based scalable fusion: **Medium**
- VAA cross-architecture effectiveness: **Medium**
- Overall performance parity with centralized training: **Medium**
