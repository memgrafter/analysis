# PaperVoyager : Building Interactive Web with Visual Language Models
## Quick Facts
- arXiv ID: 2603.22999
- Source URL: https://arxiv.org/abs/2603.22999
- Reference count: 20
- Primary result: Achieves an 84.4% task success rate on a benchmark of 19 research papers, outperforming the strongest baseline (Claude Code at 72.9%).

## Executive Summary
PaperVoyager is an end-to-end agent that transforms a research paper PDF into an interactive web system. It operates in three stages: (1) understanding the paper to extract a structured specification of interactive modules, (2) system modeling to define user controls and visual outputs, and (3) interactive webpage synthesis by generating multiple React/TypeScript component candidates per module, filtering them via a vision-language model that evaluates rendered interaction trajectories, and merging the best components. This addresses the limitation of static document agents by explicitly modeling dynamic mechanisms and state transitions. On a custom benchmark of 19 papers, PaperVoyager achieves an 84.4% task success rate, significantly beating the strongest baseline (72.9%).

## Method Summary
The pipeline uses pre-trained LLMs and VLMs at inference with no additional training. First, a PDF is analyzed to produce a Module Plan (a structured list of interactive modules, controls, and outputs). Then, for each module, a code-specialized LLM generates *k* independent React/TypeScript components. Each candidate is built and rendered in a headless browser (Playwright) while a scripted interaction captures screenshots to form a trajectory. A lightweight VLM (Qwen3-VL-4B-Instruct) evaluates the trajectory against the module spec, producing a continuous score from raw Yes/No token logits. The top candidate per module is selected and merged via an LLM into a single-page app. Key innovations are block-level generation to reduce complexity and VLM-based filtering of rendered interactions to ensure functional completeness.

## Key Results
- **Task success rate:** 84.4% on a 19-paper benchmark, outperforming Claude Code (72.9%).
- **Ablation insights:** Full interaction trajectories and *k*=6 candidates yield the best performance.
- **Functional modules:** Interactive components exhibit observable state changes during automated probing at a high rate.

## Why This Works (Mechanism)
### Mechanism 1: Structured Specification Generation
**Claim:** Decomposing a complex interactive system into discrete, implementable modules via a structured specification improves completeness.  
**Mechanism:** The agent performs multimodal analysis of the PDF to identify core mechanisms (e.g., algorithm steps, state transitions) and explicitly enumerates them in a “Module Plan” before any code is written. This chain-of-thought forces reasoning about *what* should be interactive.  
**Core assumption:** Accurate identification of interactive-worthy mechanisms from text is possible and leads to more complete system designs.  
**Evidence anchors:** Abstract mentions explicit modeling of mechanisms; Section 3 describes constructing a structured generation specification; neighboring corpus lacks focus on mechanism extraction.  
**Break condition:** If the specification omits a critical interactive component (e.g., a parameter slider), the downstream pipeline cannot recover it.

### Mechanism 2: Block-Level Generation
**Claim:** Generating multiple independent candidates per module reduces complexity and increases diversity of correct implementations.  
**Mechanism:** Each module from the specification is treated as an independent block; the system generates *k* separate React components for it, isolating the generation challenge.  
**Core assumption:** Focused per-module generation has a higher probability of correctness than a monolithic generation call.  
**Evidence anchors:** Section 3 states block-level generation reduces per-call complexity; Section 5.5 quantitative analysis shows monolithic generation omits specification details.  
**Break condition:** If the module specification is flawed or ambiguous, multiple generations may perpetuate the same error.

### Mechanism 3: VLM-Based Trajectory Evaluation
**Claim:** Evaluating rendered interaction trajectories with a VLM selects functionally complete and visually coherent components.  
**Mechanism:** Each candidate is compiled and rendered in a headless browser; screenshots during scripted interactions form a trajectory. A VLM judges if the rendered result matches the block spec; raw logits yield a continuous score for ranking.  
**Core assumption:** A VLM can assess functional completeness and visual fidelity from a sequence of screenshots better than a text-only LLM or a single screenshot.  
**Evidence anchors:** Abstract describes VLM evaluation of trajectories; Section 3 explains logit extraction; Section 5.4 ablation shows performance increases with full trajectory and *k*=6.  
**Break condition:** If VLM judgment is misaligned with the spec (e.g., scores a flashy but functionally incorrect component highly), poor candidates may be selected.

## Foundational Learning
**Concept: React/TypeScript Component Architecture**  
*Why needed:* The final output is a single-page React app in TypeScript. Engineers must understand component state, props, hooks (e.g., `useState`), and effect hooks for dynamic visualizations.  
*Quick check:* “How would you structure a React component to accept a ‘learning rate’ slider value and re-render a gradient descent visualization in real-time as the slider moves?”

**Concept: Vision-Language Model (VLM) Evaluation**  
*Why needed:* The core innovation uses a VLM to score rendered interactive components. Engineers need to understand that the VLM treats the *sequence of screenshots* as a proxy for user experience—assessing whether interactions produce expected visual state changes.  
*Quick check:* “Why is providing the VLM with a *trajectory* of screenshots (e.g., before/after a button click) more informative for judging functionality than a single screenshot?”

**Concept: State Management for Interactive Simulations**  
*Why needed:* Every module models a dynamic system (e.g., N-body gravity, page replacement). The engineer must translate the paper’s mathematical/algorithmic state transitions into JavaScript state and bind UI controls (sliders, buttons) to mutate that state.  
*Quick check:* “In a ‘Virtual Memory’ module, what key state variables (e.g., `pageTable`, `TLB`) would you need to track to visualize a TLB miss?”

## Architecture Onboarding
- **Component map:** PDF Parser & Extractor -> Spec Generator (LLM) -> Block Generator (LLM, *k* candidates) -> Build & Render Engine -> VLM Evaluator -> Merger (LLM) -> Final Build & Serve.
- **Critical path:** Paper Text -> Spec Generator -> Block Gen × *k* -> Build/Render -> VLM Eval -> Select Top-1 per Block -> Merger -> Final App.
- **Design tradeoffs:**  
  • *k* (candidates per module): higher *k* increases chance of a correct block but multiplies VLM evaluation cost.  
  • Trajectory length: more screenshots give VLM more evidence but increase rendering time.  
  • Block granularity: finer blocks reduce complexity but increase merging overhead; coarser blocks risk monolithic failures.
- **Failure signatures:**  
  1. Prompt Misalignment (43.3%): Generated module omits or simplifies a spec’d feature (e.g., missing Adam optimizer).  
  2. Visual Grounding Issue (35.6%): UI elements render as broken/placeholder (e.g., blank canvases).  
  3. Hallucination (14.8%): Adds unspec’d features or visualizations.  
  4. Navigation Stuck (6.3%): Interactions cause no visible state change (e.g., slider moves but plot does not update).
- **First 3 experiments:**  
  1. **Isolate Spec Generation:** Feed a paper (e.g., “Gradient Descent”) to the Spec Generator. Validate the Module Plan manually—does it list all key interactive elements?  
  2. **Block Generation Sanity Check:** Take a simple module spec (e.g., “Visualize sorting steps for Bubble Sort”). Generate *k*=3 candidates. Do they all compile? Do they all show a sorted array after interaction?  
  3. **VLM Evaluation Alignment:** For a known-good and known-bad candidate of a block, run the full render+eval pipeline. Does the VLM score the correct one higher? Does the score correlate with manual inspection?

## Open Questions the Paper Calls Out
1. **Scaling the benchmark** – How can the benchmark be scaled to more papers without sacrificing annotation quality? *Basis:* Section 7 Limitations notes limited resources led to only 19 papers. *Why unresolved:* Expert annotation of interactive systems is labor-intensive. *What evidence would resolve:* Semi-automated annotation pipelines (LLM drafts + expert verification) or standardized schemas for interactive module specifications.  
2. **Alternative VLM evaluators** – Would alternative VLMs (e.g., GPT-4V, Claude 3.5 Sonnet) as evaluators improve candidate selection fidelity? *Basis:* Only one VLM (Qwen3-VL-4B-Instruct) is evaluated. *Why unresolved:* VLMs vary in visual reasoning and instruction-following; no comparative study exists. *What evidence would resolve:* Re-run filtering with multiple VLMs on fixed generated components, measure correlation with human assessments, and report variance in final task success rates.  
3. **Block-wise decomposition analysis** – What specific aspects of block-wise decomposition reduce prompt misalignment (the top failure cause at 43.3%), and can the structured specification be further optimized? *Basis:* Inferred from Section 5.5 failure analysis. *Why unresolved:* Unclear whether misalignment stems from specification clarity, model capacity per module, or integration issues. *What evidence would resolve:* Ablation varying specification detail (e.g., granularity) and generation scope (monolithic vs. block-wise), with fine-grained error classification to isolate which mismatch types are reduced.

## Limitations
- Exact prompts for paper understanding and component generation, as well as VLM evaluation protocol details, are unpublished, hindering precise replication.
- The benchmark of 19 research papers is private and may not cover diverse domains, raising generalizability concerns.
- The choice of VLM (Qwen3-VL-4B-Instruct) lacks comprehensive comparison to alternatives (e.g., GPT-4V).
- Build and rendering nuances (e.g., Vite configuration, Playwright scripted interactions) are underspecified, affecting trajectory consistency.

## Confidence
- Overall pipeline superiority (84.4% TSR vs. 72.9%): **High**
- Structured specification generation: **Medium** (no ablation isolating its contribution; failure analysis suggests it can be a bottleneck)
- Block-level generation (*k*=6) and VLM trajectory filtering: **High** (consistent ablation improvements across *k* and trajectory length)

## Next Checks
1. **Independent domain generalizability test:** Build a new benchmark of 10 papers from distinct subfields (e.g., theory, systems, HCI), manually derive interactive specs, run PaperVoyager, and measure TSR variance.
2. **VLM evaluation ablation:** Replace the VLM with a text-only LLM judging component code, or use a single-screenshot VLM, and quantify TSR drop versus full trajectory evaluation.
3. **Automated failure signature profiling:** Develop scripts to detect the four failure modes (omission, visual break, hallucination, stuck interaction) from code and screenshot diffs; correlate prevalence with VLM scores to validate the selection mechanism.
