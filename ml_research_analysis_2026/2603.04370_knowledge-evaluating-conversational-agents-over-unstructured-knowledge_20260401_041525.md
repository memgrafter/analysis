# $τ$-Knowledge: Evaluating Conversational Agents over Unstructured Knowledge
## Quick Facts
- **arXiv ID:** 2603.04370
- **Source URL:** https://arxiv.org/abs/2603.04370
- **Reference count:** 40
- **Primary result:** Frontier models achieve only ~25.5% pass¹ on τ-Banking, with performance dropping to 13.40% pass⁴ and only 39.69% pass¹ under golden retriever conditions.

## Executive Summary
τ-Knowledge extends the τ-Bench framework with τ-Banking, a novel fintech customer support domain requiring agents to integrate retrieval from 698 interconnected natural-language documents with tool execution to produce verifiable, policy-compliant state changes over long conversations. Benchmark results reveal severe limitations: even state-of-the-art models succeed in merely ~25.5% of tasks on first attempt, falling to 13.4% by the fourth try. Crucially, providing gold documents raises success to just 39.69%, exposing substantial reasoning and policy-application deficits beyond retrieval. The work underscores a critical gap in building agents that robustly combine unstructured knowledge with complex, multi-step actions for real-world deployments.

## Method Summary
τ-Knowledge builds upon τ-Bench by introducing τ-Banking, a simulation of fintech customer support workflows. The environment includes a knowledge base of 698 interlinked natural-language documents containing policies and procedures. Agents engage in multi-turn dialogues, using a terminal interface to search documents and invoke tools (e.g., transaction processing, account updates) that modify a shared state. Each episode ends with an automatic verifier checking if the final state satisfies task-specific constraints. This design forces agents to coordinate retrieval, reasoning over interdependent policies, and tool use across extended horizons, mirroring the complexity of live human-facing systems.

## Key Results
- Frontier models (e.g., Claude 3.5 Sonnet, GPT-4o) achieve only ~25.5% pass¹ (success on first trial), with reliability dropping sharply to 13.40% pass⁴.
- In the golden retriever setting (oracle documents provided), the best model attains merely 39.69% pass¹, indicating severe reasoning bottlenecks even with perfect retrieval.
- Terminal-based freeform search improves pass¹ for high-reasoning models (e.g., o1) relative to dense retrieval but incurs ~9× longer durations and significantly more tool calls.

## Why This Works (Mechanism)
τ-Knowledge effectively stress-tests integrated agent capabilities by: (1) coupling a richly interconnected document corpus with dynamic state changes, requiring synthesis across multiple sources; (2) enforcing objective, verifiable outcomes that eliminate subjective success judgments; and (3) simulating long-horizon interactions where early errors propagate, measuring robustness. The terminal-based retrieval interface, while costly, allows precise query formulation, exposing the need for strategic search planning. Together, these elements create a realistic proxy for knowledge-intensive deployments where retrieval and reasoning are inseparable.

## Foundational Learning
- **Retrieval-Augmented Generation (RAG):** Why needed: Agents must fetch relevant documents from a large corpus during conversation. Quick check: Can the agent retrieve the correct policy doc for a user's loan inquiry?
- **Tool-Augmented Reasoning:** Why needed: State changes require executing actions (e.g., refunds) via tools. Quick check: Does the agent call the correct tool with right parameters after retrieving the policy?
- **Long-Horizon Dialog Management:** Why needed: Conversations span many turns with evolving context. Quick check: Does the agent maintain state consistency over 20+ turns?
- **Policy Compliance Verification:** Why needed: Success is defined by objective state constraints. Quick check: Is the final account balance exactly as required by the task?
- **Inter-Document Dependency Reasoning:** Why needed: Policies reference other documents (e.g., fee rules cite account types). Quick check: Does the agent resolve cross-references correctly?
- **Unstructured Knowledge Integration:** Why needed: Corpus is natural language, not structured DB. Quick check: Can the agent extract numeric thresholds (e.g., "up to $500") from text?

## Architecture Onboarding
Component map: User Simulator -> Agent (Planner + Retriever + Tool Executor) -> Environment (KB + State Verifier). Critical path: Query -> KB_search (terminal or dense) -> Document reading -> Policy reasoning -> Tool call -> State update -> Repeat until verifier passes. Design tradeoffs: Terminal search (flexible, high accuracy) vs. dense retrieval (fast, limited); unrestricted queries (better performance) vs. constrained (realistic cost). Failure signatures: (a) Incorrect document selection, (b) Misapplied policy steps, (c) Wrong tool parameters, (d) State inconsistencies. First experiments: (1) Implement baseline with dense retrieval only; (2) Enable terminal search with no query limits; (3) Test golden retriever (oracle documents) to isolate reasoning.

## Open Questions the Paper Calls Out
### Open Question 1
- Question: How can user simulations in τ-Knowledge be enhanced to better mimic real human interaction patterns, such as varied user expertise, colloquial language, and ambiguous inputs, without compromising controlled evaluation?
- Basis in paper: [explicit] The limitations state: "Our user simulations are simplified and do not capture many characteristics of real human interaction, such as variation in user expertise, colloquial or localized language, and grammatically imperfect or ambiguous inputs."
- Why unresolved: Current simulator likely underestimates deployment challenges; improving realism would yield more robust agent evaluations.
- What evidence would resolve it: Integrate a sophisticated simulator incorporating these characteristics, then re-run benchmarks to measure shifts in agent performance and failure mode distribution.

### Open Question 2
- Question: How does restricting retrieval queries (e.g., one- or few-shot search) impact agent performance on τ-Knowledge compared to unrestricted search, and which retrieval configurations are most robust under such constraints?
- Basis in paper: [explicit] The paper notes: "We evaluate agents under a fully agentic search regime with unrestricted access..., whereas many real-world systems operate under one- or few-shot search constraints; under such limits, we expect retrieval configuration to play a more decisive role in performance."
- Why unresolved: Unlimited searches may not reflect real-world cost/performance trade-offs; understanding constrained search is critical for practical deployment.
- What evidence would resolve it: Conduct experiments with varying limits on KB_search or shell calls, measure pass^k and efficiency metrics across retrieval methods, and identify strategies that maintain accuracy with fewer queries.

### Open Question 3
- Question: To what extent can agents leverage write tools in the terminal interface to actively manage and reorganize knowledge (e.g., note-taking, summarization) to improve long-horizon reasoning and reduce context bloat?
- Basis in paper: [explicit] From Limitations: "Our terminal-use setting warrants deeper investigation, particularly the role of write tools, as more deliberate agent designs may better exploit note-taking, state tracking, and knowledge reorganization to improve long-horizon reasoning."
- Why unresolved: Preliminary tests showed models rarely use write commands, possibly due to lack of prompting or capability; encouraging this behavior could enhance efficiency and success.
- What evidence would resolve it: Prompt agents to use write tools for knowledge management, compare against read-only baselines on performance, context length, and turn efficiency, and analyze whether written artifacts are subsequently referenced.

### Open Question 4
- Question: What specific reasoning deficiencies cause the low success rates (~39.69% pass^1) in the golden retriever setting (where gold documents are provided), and how can models be improved to correctly apply complex policies and cross-document dependencies?
- Basis in paper: [inferred] Golden retriever results show a significant performance gap despite perfect retrieval, implying reasoning bottlenecks. Qualitative analysis lists error modes (e.g., complex interdependencies, ordering failures) but does not isolate the precise reasoning capabilities lacking.
- Why unresolved: Without identifying exact reasoning failures—whether in comprehension, multi-hop inference, or procedural logic—targeted model improvements remain elusive.
- What evidence would resolve it: Design fine-grained diagnostics within the same corpus, such as synthetic tasks testing single-vs-multi-document reasoning, policy application steps, or dependency resolution, and analyze model outputs to pinpoint missing skills.

### Open Question 5
- Question: How can retrieval strategies be optimized to balance accuracy and interaction efficiency in human-facing deployments, given that freeform search (terminal) improves reliability for high-reasoning models but incurs much higher latency and tool usage?
- Basis in paper: [inferred] Paper shows terminal-use yields higher pass^1 than dense retrieval for some models but with ~9× longer duration and more tool calls. This trade-off between reliability and efficiency is discussed but not optimized.
- Why unresolved: Current retrieval choices are static; adaptive or hybrid strategies could provide better accuracy-efficiency trade-offs essential for user experience.
- What evidence would resolve it: Develop adaptive retrieval policies (e.g., start with dense, switch to terminal if uncertain), define composite metrics (success per token/turn), and evaluate across models/tasks to map Pareto frontiers and identify optimal configurations.

## Limitations
- Evaluation confined to a single domain (τ-Banking), raising concerns about generalizability to other knowledge-intensive sectors.
- Low success rates cannot be cleanly decomposed into retrieval vs. reasoning failures due to the benchmark's integrated design.
- User simulations lack realism (e.g., no colloquial language or ambiguous inputs), potentially understating deployment challenges.

## Next Checks
1. **Cross-Benchmark Replication:** Test the same models on established multi-turn tool-use benchmarks (e.g., AgentProcessBench) to determine if τ-Banking is anomalously difficult.
2. **Error Mode Analysis:** Manually audit failure trajectories to quantify errors traceable to (a) retrieval of wrong documents, (b) mis-parsing of retrieved policies, or (c) incorrect tool calls.
3. **Architecture-Agnostic Evaluation:** Open-source the benchmark and run a broader set of models (including smaller, specialized RAG systems) to test if the performance ceiling is model-size-dependent or inherent to the task structure.
