# Quantum-Secure-By-Construction (QSC): A Paradigm Shift For Post-Quantum Agentic Intelligence

## Quick Facts
- **arXiv ID:** 2603.15668  
- **Source URL:** https://arxiv.org/abs/2603.15668  
- **Reference Count:** 40  
- **Primary Result:** Introduces a runtime-adaptive orchestration layer integrating PQC, QRNG, and QKD to secure long-lived agentic AI systems, demonstrating sub-millisecond cryptographic overhead, cloud-scale latency dominated by networking, and 100% detection of tampering and replay attacks across 100,000 adversarial vectors.

## Executive Summary
This paper presents Quantum-Secure-By-Construction (QSC), a design paradigm that embeds quantum-resistant security directly into the architecture of distributed agentic AI systems. Unlike retrofitting post-quantum cryptography, QSC treats quantum-secure communication as a foundational property through a policy-driven orchestration layer that dynamically selects among PQC, QRNG, and QKD based on latency, cost, compliance, and availability. Empirical validation on a cloud-scale testbed confirms that cryptographic overhead remains modest (sub-millisecond to low milliseconds) and that the system robustly detects adversarial tampering and replay attempts, establishing a practical pathway for future-ready agent deployments.

## Method Summary
The evaluation combines isolated micro-benchmarks, cloud deployment, and adversarial simulation. Phase I measures raw cryptographic operation times (Kyber, Dilithium, QRNG) on a local Apple M3 Pro testbed, modeling QKD latency from literature. Phase II deploys a full agentic system on Azure East US using a custom Nginx-OQS sidecar for PQC-TLS termination, injecting modeled QKD delays where physical quantum links are unavailable. Cloud latency and scalability are assessed across increasing worker pools. Phase III injects 100,000 malicious vectors (tampering and replay) into the communication pipeline to validate detection mechanisms via PQC signatures and QRNG nonce freshness.

## Key Results
- PQC encapsulation overhead reaches 78.2% but remains sub-millisecond in absolute terms.
- End-to-end cloud latency averages ~297 ms, dominated by network factors; cryptographic contribution is minor.
- Security tests achieve a 100% detection and blocking rate against 100,000 adversarial tampering and replay vectors.

## Why This Works (Mechanism)
### Mechanism 1: Dynamic Posture Selection
The policy agent optimizes a utility function over possible postures (PQC, PQC+QRNG, QKD+PQC+QRNG) per communication link, balancing security, latency, cost, and regional compliance. This runtime adaptation ensures that each link uses the strongest feasible cryptography without manual reconfiguration. Evidence includes the formal model (Eq. 6 & 7) and the abstract’s “runtime-adaptive, policy-driven orchestration layer.” Break conditions include mis-calibrated weights or unmodeled regulatory changes, which could lead to insecure or non-compliant configurations.

### Mechanism 2: Hybrid Session Key Derivation
Session keys combine QKD material, PQC secrets, and QRNG entropy via HKDF: \( K_{u,v} = \text{HKDF}(1[K_{qkd}\neq\perp] \cdot K_{qkd} \parallel K_{pqc} \parallel r_{u,v}) \). This preserves the strongest entropy even if one component is compromised. Evidence: abstract’s “derives unified session keys by composing PQC, QRNG, and (when available) QKD” and Section 3.3. Break conditions include weak QRNG entropy, unauthenticated QKD, or flawed HKDF that could enable predictability or MITM attacks.

### Mechanism 3: Lifecycle-Wide Security Integration
The orchestrator uniformly applies PQC, QRNG, and optional QKD to all critical agent operations (session bootstrap, task graph creation, execution, memory access, tool invocation, audit logging). This treats quantum security as a core architectural property rather than an add-on. Evidence: abstract’s emphasis on “first-class architectural property” and Section 4’s operational steps. Break conditions include orchestrator compromise or excessive overhead from fine-grained enforcement.

## Architecture Onboarding
**Component map:**  
Client -> Orchestrator -> Specialist Agents; Agents <-> MCP Server; MCP Server -> Shared Memory; All components <-> Quantum Crypto Stack; Orchestrator & Agents -> Audit Ledger

**Critical path:**  
Session bootstrap → Secure client request → Build task graph → Secure agent execution → Merge & reason → Finalize & respond → Record audit trail

**Design tradeoffs:**  
- QKD offers information‑theoretic security but limited availability; PQC provides wide deployability with modest overhead.  
- Centralized orchestration simplifies policy enforcement but risks bottlenecks; mitigated by sidecar pattern and parallel verification.  
- Fallback strategies (PQC‑only, DRBG for QRNG) ensure availability at the cost of reduced security.

**Failure signatures:**  
- High handshake latency: QKD deployment issues or PQC computational overhead.  
- Audit log gaps: Missing Dilithium signatures or QRNG nonce reuse indicate cryptographic failures.  
- Policy agent errors: Inconsistent posture selection across links suggests constraint misconfiguration.  
- QRNG degradation alerts: Entropy source failure forces fallback to weaker randomness.

**First 3 experiments:**  
1. Posture selection test: Simulate multi‑region deployment with varying QKD availability; verify the policy agent selects correct postures per link.  
2. Scalability benchmark: Measure end‑to‑end latency with increasing agent pool (N=1 to 50) to confirm linear scaling and that cryptographic overhead is masked by cloud networking.  
3. Adversarial resilience test: Inject 100,000 tampered and replay vectors; confirm 100% detection via PQC signature verification and QRNG nonce freshness checks.

## Open Questions the Paper Calls Out
### 1. Scalable QKD: beyond point‑to‑point links
How can QKD be scaled beyond point‑to‑point links to support multi‑hop key distribution and dynamic routing in globally distributed, heterogeneous agentic AI networks? Current QKD relies on fixed nodes and lacks quantum networking (repeaters, entanglement swapping) needed for large‑scale, dynamic agent meshes, limiting QKD to niche high‑assurance links.

### 2. Quantum IP stack: protocol layers for agent‑level cryptographic APIs
What are the design principles and required abstractions for a quantum‑native protocol stack that exposes cryptographic APIs at the agent level, enabling crypto‑agnostic application logic while managing key provenance and fallbacks? Presently, agent frameworks integrate cryptography as a backend service, not as a composable, lifecycle‑aware layer, hindering seamless cryptographic agility and auditability.

### 3. Inter‑jurisdictional crypto policy: cross‑border use of quantum cryptography
How can cross‑jurisdictional cryptographic policy constraints (e.g., data sovereignty, export controls) be automatically embedded into the runtime cryptographic posture selection of distributed agents to ensure legal compliance without manual configuration? The policy agent’s generic optimization function lacks operational mapping from regional laws to cryptographic parameters.

### 4. AI crypto‑awareness: context‑driven cryptographic decision‑making
What architectural mechanisms enable “crypto‑aware” agents to dynamically adjust their cryptographic posture (e.g., escalate from PQC+QRNG to QKD) based on real‑time threat assessment, mission context, and peer trust, without compromising coordination or introducing new attack surfaces? The paper’s orchestration layer does not detail autonomous agent‑level decisions during execution.

### 5. Agent self‑sovereignty: decentralized identity and credential management
How can agent self‑sovereign identity (SSI) be realized using decentralized identifiers (DIDs) and verifiable credentials bound to post‑quantum keys, enabling trust establishment and credential verification without centralized authorities in open multi‑agent ecosystems? Integration of PQC‑based credentials with DID standards, revocation propagation, and Sybil attack prevention remain unspecified.

## Limitations
- QKD parameters are model‑based; real hardware latency and availability vary and may be inaccessible in many regions.
- Azure deployment specifics (VM sizes, network topology, sidecar implementation) are omitted, blocking exact replication of latency and scaling results.
- Policy agent assumes static, accurate metric weights and compliance rules; dynamic regulation or mis‑calibration could select insecure postures.

## Confidence
- Feasibility & practicality: **Medium** (micro‑benchmarks solid; cloud results plausible but network‑dominated and lack physical QKD)
- Adaptive posture selection: **Medium** (optimization logic sound but unverified weight calibration and compliance enforcement)
- Hybrid key derivation: **Medium** (standard HKDF composition but no empirical entropy stress tests)
- Tampering/replay detection: **High** (within controlled tests; generalizability uncertain)
- Performance overhead: **High** for PQC primitives; **Medium** for cloud latency due to variance and no QKD
