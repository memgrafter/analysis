# SkillRouter: Skill Routing for LLM Agents at Scale

## Quick Facts
- arXiv ID: 2603.22455
- Source URL: https://arxiv.org/abs/2603.22455
- Reference count: 34
- Primary result: Excluding skill body text causes a 31-44 percentage point accuracy drop; SkillRouter achieves 74.0% Hit@1 on a 75-query benchmark with 1.2B parameters, using 13× fewer parameters and running 5.8× faster than the strongest baseline, enabling on-device deployment.

## Executive Summary
Skill routing—selecting the correct skill from a large pool (∼80K) for a given user query—is a critical yet under-explored component of LLM agent systems. Current systems assume that a skill’s name and description suffice for matching, overlooking the full body text. This paper shows that the body is decisive: its exclusion leads to a catastrophic 31–44 percentage point drop in accuracy. To address this, the authors introduce SkillRouter, a lightweight retrieve-and‑rerank pipeline that processes full skill text (name, description, body) in both stages. With only 1.2B parameters (two 0.6B models), it achieves state‑of‑the‑art 74.0% Hit@1 on a challenging 75‑query benchmark, outperforming larger baselines while being 13× smaller and 5.8× faster—making on‑device deployment feasible. Improved routing also transfers to higher task success in downstream agent evaluations, underscoring the practical impact.

## Method Summary
SkillRouter employs a two‑stage architecture. First, a bi‑encoder (SR‑Emb-0.6B) encodes queries and skills into a shared embedding space; approximate nearest neighbor search over a FAISS index retrieves the top‑20 candidates from the ∼80K pool. Second, a cross‑encoder (SR-Rank-0.6B) applies token‑level cross‑attention over the full skill body (and metadata) of each candidate to compute fine‑grained relevance scores, after which the list is reranked. Both stages use the complete skill text.

Training involves synthetic query generation (via GPT‑4o‑mini), hard negative mining (semantic, lexical, taxonomy, random), and three‑layer false negative filtering (remove exact name matches, body trigram Jaccard >0.6, embedding cosine >0.92). The reranker uses listwise cross‑entropy loss, which optimizes the order of the candidate list—a crucial adaptation for homogeneous pools with many near‑duplicate skills. Key hyperparameters: encoder batch size 8 (gradient accumulation 4), reranker batch size 1 (gradient accumulation 16), learning rate 2e‑5, cosine decay with warmup, one epoch, and truncation (body ≤2500 tokens for encoder, ≤3000 for reranker). Evaluation uses 75 expert‑verified queries from SkillBench, across Easy (78,361 skills) and Hard (79,141 skills + 780 LLM‑generated distractors) tiers, reporting Hit@1, MRR@10, nDCG@10, Recall@K, and FC@10.

## Key Results
- Excluding skill body text reduces accuracy by 31–44 percentage points.
- SkillRouter attains 74.0% Hit@1, the best average top‑1 performance among baselines.
- The pipeline uses 13× fewer parameters and runs 5.8× faster than the strongest base pipeline, enabling on‑device deployment.

## Why This Works (Mechanism)
### The body is the decisive signal
Full skill body text is essential for accurate routing; relying only on name and description leads to catastrophic failure. The body contains implementation details that differentiate skills with similar metadata. Cross‑encoder attention analysis reveals that 91.7% of attention concentrates on body tokens, indicating the model depends on body content for the final relevance decision. This mechanism assumes large skill ecosystems exhibit pervasive functional overlap, making metadata insufficient. Evidence: the 31–44 pp drop when body is excluded (abstract) and the attention distribution (Section 3.2). Break conditions: if bodies are inaccessible (truncation, privacy) or the pool has minimal functional overlap (each skill uniquely named), the body becomes irrelevant.

### Retrieve‑and‑rerank with full body in both stages
The two‑stage pipeline efficiently leverages full body content: the bi‑encoder quickly narrows candidates via ANN search (∼80K → top‑20), while the cross‑encoder refines rankings with fine‑grained cross‑attention over each candidate’s full body. This design balances accuracy and efficiency. Core assumption: the correct skill appears within the top‑K retrieved; otherwise reranking cannot recover it. Evidence includes the reported 74.0% Hit@1, superior speed and size versus baselines, and explicit ablation showing full body is necessary in both stages (Section 4.1). Break conditions: low encoder recall@K (correct skill missing from top‑20) or bodies exceeding context length (truncation loses signal) cause failure.

### Task‑specific fine‑tuning with curriculum and listwise loss
In homogeneous pools with many near‑duplicate skills, standard contrastive learning fails. The paper introduces three innovations: (1) hard negative mining from semantically similar skills, (2) three‑layer false negative filtering (Jaccard >0.6, cosine >0.92) to remove functionally duplicate negatives, and (3) listwise ranking loss that optimizes the order of the entire candidate list. Hard negatives provide challenging examples; false negative filtering prevents contrastive corruption; listwise loss directly compares skills, essential when candidates are nearly identical. Pointwise loss collapses in this regime, as shown by a 30.7 pp gap. Core assumption: significant functional overlap in the pool. Evidence: ablations—removing false negative filtering degrades Hit@1 by 4.0 pp; listwise loss yields huge gains over pointwise (Section 5.4). Break conditions: in pools with little overlap, these measures may be unnecessary, but typical large repositories require them.

## Foundational Learning
- **Bi‑encoder dense retrieval**  
  *Why needed*: Enables efficient approximate nearest neighbor search over the large skill pool by encoding queries and skills into a shared embedding space.  
  *Quick check*: What is the computational tradeoff between bi‑encoders and cross‑encoders for large‑scale retrieval?

- **Cross‑encoder reranking**  
  *Why needed*: After bi‑encoder retrieval, a cross‑encoder applies token‑level cross‑attention over full skill bodies to discriminate between candidates with similar embeddings, providing fine‑grained matching.  
  *Quick check*: Why can’t the bi‑encoder alone achieve the required precision, and how does cross‑attention help?

- **Listwise ranking loss**  
  *Why needed*: The reranker is trained with listwise cross‑entropy to directly optimize the ordering of a candidate list, which is critical in homogeneous pools where pointwise scoring fails.  
  *Quick check*: What is the key difference between listwise and pointwise loss, and why does listwise work better here?

## Architecture Onboarding
- **Component map**:  
  Query Encoder (SR-Emb-0.6B) -> Skill Index (FAISS) -> ANN Retriever -> Reranker (SR-Rank-0.6B) -> Rank Sorter

- **Critical path**:  
  1. Receive user query.  
  2. Encode query with SR-Emb-0.6B.  
  3. ANN search over precomputed skill embeddings to get top‑20 candidates.  
  4. For each candidate, format as “flat‑full” input (name|description|body with truncation limits) and feed to SR-Rank-0.6B.  
  5. Collect scores, sort descending, return ranked list.

- **Design tradeoffs**:  
  - Model size: 0.6B models enable CPU‑friendly on‑device deployment but sacrifice ∼2 pp accuracy vs. 8B models.  
  - Candidate set size (K): K=20 balances recall (∼75%) and compute; larger K increases recall but adds noise.  
  - Input truncation: Limiting body length (2500/3000 tokens) ensures feasibility but may lose critical details; impact unmeasured.  
  - Full body requirement: Necessitates storing and processing full bodies, increasing storage/latency, but is necessary for accuracy.  
  - Training complexity: Hard negative mining, false negative filtering, and listwise loss add preprocessing/training overhead but yield large gains (e.g., +30.7 pp over pointwise).

- **Failure signatures**:  
  - Low encoder recall@20 (<70%): indicates poor embedding learning; may need better fine‑tuning or more hard negatives.  
  - Pipeline Hit@1 < encoder‑only Hit@1: suggests reranker degradation, possibly due to pointwise loss or positives missing from top‑K.  
  - Large Easy–Hard gap (>15 pp): reveals inadequate handling of LLM‑generated distractors; may require harder negative mining.  
  - Memory overflow during reranking: caused by excessive body length; enforce truncation or gradient accumulation.  
  - Metrics diverge from reported values: risk of data leakage or hyperparameter mismatch; check train/test separation.

- **First 3 experiments**:  
  1. **Full pipeline evaluation**: Train encoder and reranker as described, index evaluation pools, run on all 75 queries, and report Hit@1, MRR@10, nDCG@10. Expect ∼74.0% Hit@1.  
  2. **Body exclusion ablation**: Train encoder with only name+description (no body), keep other settings identical, evaluate on same queries. Expect a 31–44 pp drop in Hit@1.  
  3. **Listwise vs. pointwise loss comparison**: Train two rerankers on the same encoder outputs: one with listwise cross‑entropy (τ=0.05) and one with pointwise BCE. Evaluate both pipelines. Expect listwise >70% Hit@1 and pointwise <45%.

## Open Questions the Paper Calls Out
- **Open Question 1**: How can skill routing benchmarks be scaled and diversified to provide more statistically reliable and generalizable evaluation?  
  *Basis*: The authors note their benchmark has only 75 queries, limiting statistical power, and call for larger‑scale benchmarks with broader domain coverage.  
  *Why unresolved*: The benchmark is small and from a single source (SkillBench); findings may not generalize.  
  *Evidence needed*: Create and release a benchmark with hundreds or thousands of queries spanning multiple skill domains, with standardized evaluation protocols.

- **Open Question 2**: To what extent do the findings on the importance of skill body generalize to other skill ecosystems beyond the coding‑focused skills in this study?  
  *Basis*: The authors state their findings are validated on a single benchmark derived from SkillBench; generalization to other ecosystems remains to be verified.  
  *Why unresolved*: The studied pool is predominantly coding‑related; other domains (creative, scientific, everyday tasks) may have different textual structures where name/description carry more weight.  
  *Evidence needed*: Replicate the study with skill pools from diverse domains (e.g., cooking, travel, education) and compare the impact of skill body access on routing accuracy.

- **Open Question 3**: How can skill routing systems handle queries requiring multi‑hop reasoning across multiple skills, given that 22% of queries are missed by current retrieval methods?  
  *Basis*: The authors note that 22% of queries are missed by both encoder and reranker, suggesting some scenarios require reasoning beyond retrieval.  
  *Why unresolved*: SkillRouter is a pure retrieval pipeline; it does not reason about combining skills or inferring intermediate steps.  
  *Evidence needed*: Develop and evaluate hybrid models that integrate retrieval with LLM‑based reasoning (e.g., generating intermediate queries or skill chains) on the missed queries.

- **Open Question 4**: Does improved skill routing accuracy translate into measurable gains in end‑to‑end task completion for LLM agents in real‑world scenarios?  
  *Basis*: The authors acknowledge their downstream scenario analysis using SkillsBench is a calibrated estimate rather than direct end‑to‑end evidence.  
  *Why unresolved*: It is unclear whether retrieval gains on the benchmark actually improve agent performance during execution, as agents may fail for other reasons or not fully utilize retrieved skills.  
  *Evidence needed*: Integrate SkillRouter into production agent systems (e.g., coding assistants) and measure task success rates on diverse user tasks, comparing against weaker routing baselines.

## Limitations
- The exact community skill corpus source and preprocessing steps are unreleased, hindering exact reconstruction of the 80K pool and its category distribution.
- Reranker training details (loss temperature, handling of multi‑skill queries) are unspecified, introducing uncertainty in replication.
- The evaluation benchmark contains only 75 queries, limiting statistical reliability and generalizability.

## Confidence
- **Mechanism 1 (full body decisive)**: **High** – body exclusion ablations cause a 31–44 pp drop, and cross‑encoder attention shows 91.7% focus on body tokens.
- **Mechanism 2 (retrieve‑and‑rerank pipeline)**: **High** – the pipeline achieves 74.0% Hit@1 with 13× fewer parameters and 5.8× speedup; ablations confirm full body necessity.
- **Mechanism 3 (training recipe)**: **Medium** – false‑negative filtering and listwise loss yield large gains, but effects may be dataset‑specific and hyperparameters (temperature) are not fully documented.
