## Executive Summary
RelBench v2 addresses the need for scalable, realistic benchmarks for relational deep learning as models grow. It expands the benchmark with four large‑scale datasets (22 M rows, 29 tables), introduces autocomplete tasks (predicting missing attribute values within tables under temporal constraints), and integrates external benchmarks (TGB, ReDeLEx, 4DBInfer). Evaluations show that relational deep learning models (GraphSAGE/ID‑GNN) consistently outperform single‑table baselines (LightGBM) across autocomplete (up to 99% accuracy on multiclass), forecasting (+12% AUROC), and recommendation (MAP improvements up to +35) in diverse domains. This work demonstrates the critical role of explicit relational modeling for multi‑table data.

The paper does not provide a detailed mechanistic analysis (e.g., ablation studies, attention visualization). However, the superior performance of GraphSAGE/ID‑GNN can be attributed to their ability to explicitly model relationships between tuples via graph edges (foreign keys), enabling information flow across tables. This relational inductive bias allows the model to leverage context from related tables, which single‑table models like LightGBM cannot. ## Foundational Learning
- **Relational databases:** Structured data organized in tables with primary/foreign keys. *Why needed:* Forms the domain of the benchmark. *Quick check:* Can identify foreign key relationships that define joins.
- **Graph Neural Networks (GNNs):** Neural networks operating on graph‑structured data via message passing. *Why needed:* They provide the relational inductive bias for RDL models. *Quick check:* Understand how node features are aggregated from neighbors.
- **Temporal validation:** Splitting data based on time to prevent leakage. *Why needed:* Ensures realistic evaluation for time‑sensitive tasks like autocomplete. *Quick check:* Verify that test timestamps are after training timestamps.
- **Join graph construction:** Representing tables and foreign keys as a graph. *Why needed:* Enables applying GNNs to relational data. *Quick check:* Confirm that each foreign key becomes an undirected edge between tuple nodes.
- **Inductive bias:** Assumptions built into model architecture. *Why needed:* GNNs bias toward relational patterns, contrasting with tabular models. *Quick check:* Compare performance on tasks where cross‑table info is predictive.

## Architecture Onboarding
- **Component map:** Raw relational tables → Join graph builder → Feature extractor → GNN model (GraphSAGE/ID‑GNN) → Prediction head → Evaluation metrics.
- **Critical path:** (1) Load tables and schema; (2) Construct join graph (nodes = tuples, edges = foreign keys); (3) Extract node features (e.g., categorical embeddings, numerical scalars); (4) Train GNN with message passing; (5) Generate predictions for task‑specific targets; (6) Compute metrics (accuracy, AUROC, MAP).
- **Design tradeoffs:** Scalability (large tables) vs. memory efficiency (graph sparsity); Generality (supporting multiple tasks) vs. task‑specific optimization; Realism (domain diversity) vs. data quality (synthetic noise).
- **Failure signatures:** Out‑of‑memory during graph construction for highly connected tables; Degraded performance when foreign key relationships are sparse or noisy; Temporal leakage if splits are not properly enforced; Overfitting on small datasets due to high model capacity.
- **First experiments:** (1) Replicate main results: train GraphSAGE and ID‑GNN on all tasks, compare against LightGBM; (2) Ablate relational structure: replace GNN with MLP on concatenated table features; (3) Test scaling: measure training time/memory as a function of data size (rows/tables).
