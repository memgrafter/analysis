# SimuScene: Training and Benchmarking Code Generation to Simulate Physical Scenarios

## Quick Facts
- **ArXiv ID:** 2602.10840  
- **Source URL:** https://arxiv.org/abs/2602.10840  
- **Reference count:** 40  
- **Primary result:** Existing LLMs struggle with physical simulation code generation (best: 21.5% pass rate); training with SimuScene's automated dataset and vision-based RL boosts a 7B model from 0% to 34.4% and a 32B model to 72.2%.

## Executive Summary
SimuScene is a benchmark and dataset for evaluating large language models (LLMs) on generating executable Python code that simulates physical scenarios described in text. The authors build a fully automated pipeline to produce 7,659 training scenarios and a human-verified test set of 334. Evaluation is end-to-end: generated code is executed to render a video, which is then judged by a vision-language model (VLM) using multiple verification questions. Results show that even frontier LLMs perform poorly, with the best model (DeepSeek-R1-0528) achieving only a 21.5% average pass rate. However, supervised fine-tuning (SFT) followed by reinforcement learning with VLM-based rewards (RLVR) dramatically improves performance. A 7B model's pass rate rises from 0% to 34.4%, and a 32B model reaches 72.2%, surpassing larger untrained models while also enhancing general code generation capabilities.

## Method Summary
The task requires an LLM to generate Python code from a textual description of a physical scenario. The code must be executable, render a video of the simulation, and accurately reflect the described motion. The SimuScene dataset is created through an automated multi-stage pipeline: starting from 52 core physics concepts, GPT-4o generates basic scenarios, which are enriched with additional conditions (e.g., collisions, forces), filtered for physical plausibility, paired with verification questions, and cross-validated using DeepSeek-R1-0528. The test set of 334 scenarios is human-verified. Evaluation uses a Code-Video-VLM pipeline: code is executed, the rendered video is fed to Qwen2.5-VL-72B-Instruct along with verification questions, and a simulation passes only if all questions are answered "True." Primary metrics include Executable Rate (E.R.), Render Rate (R.R.), Playable Rate (P.R.), and end-to-end accuracy (Pass@N). Training proceeds in two stages: first, SFT on 3,000 scenarios with validated correct code; second, RL with Group Relative Policy Optimization (GRPO), where the binary reward comes from the VLM judge (with ensemble voting during training to mitigate bias).

## Key Results
- Baseline frontier model (DeepSeek-R1-0528) attains only 21.5% Avg@8 and 52.7% Pass@8 on the test set.
- SFT on a 7B model increases accuracy from 0% to 4.4%.
- RL with VLM rewards raises the 7B model's pass rate to 34.4% (Avg@8) and a 32B model to 72.2%, exceeding larger untrained models and improving general code generation.

## Why This Works (Mechanism)

**Mechanism 1: Automated, high-quality data generation.**  
A multi-stage pipeline starting from 52 core physics concepts uses GPT-4o to generate basic scenarios, enriches them with conditions (collisions, forces, non-uniform properties), filters for physical plausibility, generates verification questions, and cross-validates with DeepSeek-R1-0528. This ensures diversity, controlled difficulty, and built-in quality checks. *Core assumption:* LLMs can generate and critique physics scenarios accurately when guided by templates and filtering. *Evidence:* Pipeline detailed in Section 3.1; human verification on test set ensures quality. *Break condition:* Systematic inaccuracies in initial GPT-4o generation or DeepSeek-R1 review that pass filters would corrupt training data, preventing models from learning correct physics.

**Mechanism 2: VLM-as-judge evaluation.**  
The pipeline executes generated code to render videos, then uses Qwen2.5-VL-72B-Instruct to answer multiple verification questions per scenario; a simulation passes only if all answers are "True." This evaluates the final rendered output rather than proxy text metrics. *Core assumption:* A sufficiently capable VLM can accurately judge physical motions in videos against textual descriptions. *Evidence:* VLM achieves 87.8% agreement with human annotators on the test set (Section 3.3); error analysis shows main failures are object correspondence (36%) and motion judgment (35%), but overall reliability is high. *Break condition:* If the VLM systematically misjudges key motions (e.g., subtle trajectories), the reward signal becomes noisy or misaligned, and RL would not improve true simulation quality.

**Mechanism 3: Reinforcement learning with vision-based rewards.**  
GRPO optimizes the LLM policy using the VLM's binary pass/fail signal as reward. Multiple verification questions per scenario and ensemble VLM voting during training mitigate reward hacking, directly optimizing for end-to-end video plausibility. *Core assumption:* The VLM-based binary reward provides a denser, more faithful signal than text-only LLM judging for this multi-modal, dynamic task. *Evidence:* RL with VLM rewards yields better simulation performance than LLM-as-judge (Section 5.4); post-RL VLM judgments agree with humans at 86.9% (Section 5.5); no clear evidence of reward hacking observed. *Break condition:* If the policy learns to exploit biases in the training VLMs (e.g., generating videos with specific textures that trigger false positives) without improving true physics, performance would drop on the held-out test set using a different VLM judge. The observed improvement on the test set suggests this did not happen.

## Foundational Learning
- **Executable Code Generation for Dynamic Simulations**  
  *Why needed:* The model must output syntactically correct, complete Python code that, when executed, renders a video of a dynamic physical process. This requires mapping linguistic descriptions to correct physics equations, initial conditions, and animation loops.  
  *Quick check:* Given "a ball falling under gravity," write a minimal Python script using OpenCV/Matplotlib that updates position each frame and saves an MP4.

- **Physical Plausibility and Constraint Satisfaction**  
  *Why needed:* The simulation must respect basic physical laws (e.g., force directions, conservation) and match qualitative motion in the text (e.g., "spiraling upward with decreasing speed"). The model must translate these constraints into code.  
  *Quick check:* For "a ball rolls down a frictionless incline," what key physical constraints must the code's motion reflect? (Acceleration direction along the incline, constant total mechanical energy.)

- **Vision-Language Model (VLM) Verification**  
  *Why needed:* Evaluation and RL reward rely on a VLM judging videos. Understanding its strengths (observing motion, spatial relations) and weaknesses (object correspondence, out-of-frame issues) is crucial for interpreting results and designing rewards.  
  *Quick check:* What are two common failure modes for a VLM when judging a physics simulation video? (Object correspondence errors—tracking which object is which across frames; motion judgment errors—misperceiving direction or magnitude of movement.)

## Architecture Onboarding

**Component map:**  
Data Generation Module (GPT-4o, DeepSeek-R1) -> Code Generation Module (LLM) -> Execution & Rendering Engine (Python sandbox, video renderer) -> VLM Judge Module (Qwen2.5-VL-72B-Instruct) -> RL Training Module (AgentFly/GRPO) -> Evaluation Harness

**Critical path:** Scenario Text -> Code Generation -> Python Code -> Execute/Render -> Video -> VLM Judge -> Reward/Accuracy. The VLM judge is the bottleneck; its reliability directly impacts training signal quality.

**Design tradeoffs:**  
- *Automation vs. Quality:* Fully automated pipeline enables scale (7k+ scenarios) but relies on LLM self-critique; human verification only on test set (334).  
- *Reward Granularity:* Binary reward (all questions TRUE) is high-variance but prevents reward hacking via multi-question aggregation; ratio reward (fraction TRUE) is smoother but allows partial success.  
- *VLM vs. LLM Judge:* VLM observes actual motion but is slower and more expensive; LLM-as-judge is cheap but disagrees more with humans (69.1% vs 87.8%) and yields worse RL results.

**Failure signatures:**  
- High Executable Rate (E.R.) but low Accuracy (Acc.): Model generates runnable code that produces videos, but videos are physically implausible (e.g., objects move wrong direction).  
- Reward hacking: Model performance degrades on test set (different VLM) despite high training reward; VLM judge shows systematic disagreement with humans on model outputs.  
- Concept skew: Very low performance on specific domains (e.g., Optics: 8.4% Avg@8 for DeepSeek-R1) indicates data scarcity or inherent difficulty.

**First 3 experiments:**  
1. **Reproduce baseline evaluation:** Run the VLM-judge pipeline on DeepSeek-R1-0528 for all 334 test scenarios (8 samples each) to verify the reported 21.5% Avg@8 and 52.7% Pass@8. Confirm VLM-human agreement on a subset.  
2. **SFT warm-start:** Take DeepSeek-R1-Distill-Qwen-7B, fine-tune on 3,000 SFT examples (scenario + correct code). Measure jump in Executable/Render/Playable rates and Accuracy from baseline (0%→4.4% Acc.).  
3. **RL with VLM reward:** Initialize from SFT model, run GRPO for 150 steps on 4,325 RL scenarios using binary VLM reward (ensemble voting). Target: Playable Rate ~95% and Acc. ~34.4% for 7B model. Verify length trend (decreasing then stable) and inspect failure cases post-RL.

## Limitations
- **Data Pipeline Quality:** Training data (7,659 scenarios) is generated and filtered by LLMs with only the test set human-verified; potential systematic biases or subtle inaccuracies in auto-generated data may limit learning.  
- **VLM Judge Reliability:** Qwen2.5-VL-72B shows 87.8% human agreement but known failure modes (36% object correspondence errors, 35% motion judgment errors) introduce noise into the reward signal.  
- **Evaluation Scope:** Test set size (334) is modest; exact code rendering backend and VLM prompting details are repository-dependent, hindering exact replication; generalization beyond the 52-core physics concepts is untested.

## Confidence
- **Claim: VLM-as-judge provides a reliable end-to-end metric.** Confidence: **High** (strong evidence via high human-VLM agreement and consistent model performance separation).  
- **Claim: Automated pipeline produces high-quality, diverse training data.** Confidence: **Medium** (pipeline is principled but lack of full human audit on training data leaves residual doubt).  
- **Claim: RL with VLM rewards improves true physical simulation.** Confidence: **Medium** (positive results on held-out test set, but ultimate proof requires broader human evaluation to rule out reward hacking).

## Next Checks
1. **Judge Robustness Check:** Re-evaluate the RL-trained model using a different held-out VLM (e.g., GPT-4o, Claude-3.5-Sonnet). A significant drop in Pass@8 would indicate overfitting to the Qwen2.5-VL judge's biases.  
2. **Data Sanity Audit:** Manually inspect a random sample of 100 training scenarios and their associated "correct" code. Confirm physical plausibility of scenario descriptions and that the reference code executes without error and produces qualitatively correct motion.  
3. **Zero-Shot Generalization Test:** Evaluate the best RL-trained model (72.2% Pass@8) on a small, held-out human-written test set of 50 novel physical scenarios (e.g., from a physics textbook) outside the 52-core concept distribution. This tests whether learning transferred or overfitted to the auto-generated data distribution.
