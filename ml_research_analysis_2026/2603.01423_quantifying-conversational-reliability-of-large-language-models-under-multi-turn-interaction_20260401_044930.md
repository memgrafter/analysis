# Quantifying Conversational Reliability of Large Language Models under Multi-Turn Interaction

## Quick Facts

- **arXiv ID:** 2603.01423  
- **Source URL:** https://arxiv.org/abs/2603.01423  
- **Reference count:** 40  
- **Primary result:** Multi-turn interactions cause significant reliability degradation in LLMs across instruction following, tool selection, and entity extraction tasks.

## Executive Summary

This paper presents a framework to quantify conversational reliability of large language models (LLMs) under multi‑turn interaction. The authors design three pass/fail tasks—global instruction following, tool selection amid topic shifts, and entity extraction under revisions—each with a single‑turn counterpart. Synthetic dialogues are generated by GPT‑5 and evaluated on models including GPT‑4o, Gemini‑2.5‑Flash, Qwen‑8B/32B, and Mistral‑8B.

Results reveal substantial performance drops in multi‑turn settings for all tasks (McNemar *p* < 1e‑6). Instruction following suffers the steepest decline (e.g., GPT‑4o from 96% to 63%). Tool selection remains high for frontier models but falls below 50% for many smaller ones. Entity extraction proves most resilient, with only a minor decrease (84–89%). Error analysis identifies three dominant failure modes: instruction drift, intent confusion, and contextual overwriting. The study concludes that degradation correlates more with task complexity and model capacity than with dialogue length.

## Method Summary

The authors construct controlled multi‑turn dialogues using GPT‑5 to simulate realistic conversations. Three tasks are defined:  
1. **Global instruction following** – the model must obey a high‑level instruction across all turns.  
2. **Tool selection** – the model must choose the correct tool when the conversation topic shifts.  
3. **Entity extraction** – the model must extract specific slots (date, time, people) despite user revisions and chit‑chat.  
Each task has a single‑turn version as a baseline. The selected LLMs are prompted with the dialogues, and their outputs are judged pass/fail according to strict criteria. Statistical significance of multi‑turn degradation is assessed with McNemar’s test. A qualitative error analysis then categorizes failures into instruction drift, intent confusion, and contextual overwriting.

## Key Results

- All models exhibit significant multi‑turn degradation across tasks (McNemar *p* < 1e‑6).  
- Instruction following shows the steepest drop (e.g., GPT‑4o: 96% → 63%; smaller models ~20%).  
- Tool selection remains ≥97% for large models but many smaller ones fall below 50% (e.g., Qwen‑32B 47%); entity extraction stays mostly resilient (84–89%).

## Why This Works (Mechanism)

The error analysis highlights three failure mechanisms:  

- **Instruction drift** – the model gradually deviates from the original instruction as the conversation progresses, often due to competing user demands or distractors.  
- **Intent confusion** – after a topic shift, the model misinterprets which intent should guide its response, leading to inappropriate tool selection or ignored constraints.  
- **Contextual overwriting** – earlier information (e.g., a date) is overwritten by later, more salient but irrelevant details, causing errors in entity extraction or instruction adherence.  

These mechanisms are exacerbated by limited model capacity and increased task complexity, explaining why degradation correlates more with these factors than with simple dialogue length.

## Foundational Learning

- **Multi‑turn context management**  
  *Why needed:* LLMs must retain and update relevant information across turns to maintain coherent, task‑oriented conversations.  
  *Quick check:* Present a dialogue where the user gives an instruction, then adds irrelevant small talk, then asks a follow‑up dependent on the instruction; verify if the model still follows the original instruction.

- **Instruction fidelity**  
  *Why needed:* In many applications the model must obey a global instruction consistently; drift leads to task failure.  
  *Quick check:* Give a multi‑step instruction and after each turn introduce a conflicting user demand; check if the model adheres to the original instruction.

- **Tool selection robustness**  
  *Why needed:* Models that can invoke external tools must correctly identify when and which tool to use, even after topic changes.  
  *Quick check:* Simulate a conversation that starts with a topic requiring Tool A, then shifts to a topic requiring Tool B; assess whether the model chooses Tool B at the appropriate turn.

- **Entity extraction stability**  
  *Why needed:* Extracting and updating slot values (dates, names) under user revisions and chatter is essential for task completion.  
  *Quick check:* Ask for a date, then later revise it, then insert chit‑chat; check if the final extracted date matches the latest explicit user input.

## Architecture Onboarding

- **Component map:** GPT‑5 Generator → Synthetic Dialogues → Model Under Test (GPT‑4o, Gemini, Qwen, Mistral) → Output Parser → Pass/Fail Evaluator → Statistical Analysis (McNemar) → Error Taxonomy Categorization  
- **Critical path:** The model’s output at each turn must satisfy the task’s pass criteria; any failure leads to an overall fail.  
- **Design tradeoffs:** Binary pass/fail simplifies analysis but discards nuance; synthetic dialogues provide control but lack natural diversity and may embed GPT‑5 biases; limited model set reduces generalizability; single‑turn baseline isolates multi‑turn effects but ignores cumulative knowledge growth.  
- **Failure signatures:**  
  - *Instruction drift:* gradual divergence from the original instruction (e.g., ignoring global instruction after several turns).  
  - *Intent confusion:* after a topic shift, applying previous intent or tools incorrectly.  
  - *Contextual overwriting:* earlier critical information replaced by later irrelevant content, causing entity extraction errors.  
- **First experiments:**  
  1. Establish single‑turn baseline accuracy for each task and model.  
  2. Run multi‑turn dialogues and compare to baselines using McNemar’s test to confirm degradation.  
  3. Manually annotate failures to classify them into the three error modes.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How does the degradation in multi‑turn entity extraction change when the task requires implicit contextual inference (e.g., mapping "the pizza with pineapple" to "Hawaiian pizza") rather than explicit slot filling?  
- **Basis in paper:** [explicit] "We hypothesize that if the extraction targets had required richer contextual understanding, for example, mapping free‑form user mentions like 'the pizza with pineapple' to a canonical menu item (Hawaiian pizza), the degradation would have been much more pronounced."  
- **Why unresolved:** The current entity extraction task uses explicit date/time/people slots; the hypothesis is not empirically tested.  
- **What evidence would resolve it:** Generate a variant of the entity extraction task where slot values require semantic mapping or implicit resolution, then compare multi‑turn degradation against the current explicit‑slot version across models.

### Open Question 2
- **Question:** Why is the date slot consistently the weakest component in entity extraction across scenario types (change in mind, intermediate chit chat, multiple mention)?  
- **Basis in paper:** [explicit] "The date slot is consistently weakest, reflecting difficulty in temporal tracking."  
- **Why unresolved:** The paper reports this pattern but does not investigate the underlying cause (e.g., linguistic ambiguity, model limitations in temporal reasoning, or susceptibility to temporal distractors).  
- **What evidence would resolve it:** Perform a fine‑grained error analysis categorizing date‑related failures (e.g., misparsing relative dates, confusion with chit‑chat dates) or probe models' temporal reasoning on isolated date‑parsing tasks.

### Open Question 3
- **Question:** What specific dialogue characteristics (e.g., topic shift frequency, intent ambiguity, distractor relevance) most strongly predict reliability degradation for each failure mode (instruction drift, intent confusion, contextual overwriting)?  
- **Basis in paper:** [inferred] The paper states degradation is not dominated by length but by "specific distractors or competing user demands," and shows varying sensitivity to tool count and scenario types. However, no systematic correlation between fine‑grained dialogue features and error rates is quantified.  
- **Why unresolved:** The appendix provides breakdowns by turns and tool count but does not annotate or model dialogues for features like shift count, distractor type, or intent clarity.  
- **What evidence would resolve it:** Annotate synthetic dialogues for features (e.g., number of topic shifts, ambiguity level of user intents, distractor relevance) and model error probability as a function of these features across tasks and model sizes.

## Limitations

- **Synthetic Dialogue Bias:** All test dialogues were generated by GPT‑5, potentially embedding its stylistic biases and not reflecting the full diversity of human‑LLM interaction patterns.  
- **Limited Model Scope:** Testing focused on a narrow set of frontier and small models; findings may not generalize to other model families, architectures, or sizes.  
- **Binary Evaluation Granularity:** Pass/fail metrics for complex tasks may obscure partial successes or specific failure modes, oversimplifying reliability.

## Confidence

- Significant multi‑turn performance degradation exists across all evaluated tasks and models (McNemar *p* < 1e‑6). **High**  
- The observed task‑specific degradation patterns are accurate for the tested models and synthetic dialogues. **Medium**  
- Degradation correlates primarily with task complexity and model capacity rather than dialogue length. **Low**

## Next Checks

1. Replicate with human‑authored or diverse open‑source dialogue corpora to test robustness against data source bias and real conversational variability.  
2. Expand model evaluation to a wider range of sizes (e.g., 13B–70B) and architectures (e.g., Mixture‑of‑Experts, encoder‑decoders) to verify the capacity‑degradation relationship.  
3. Replace binary metrics with fine‑grained, error‑type‑specific scoring (e.g., partial instruction adherence, nuanced tool intent) to disentangle *where* and *how* reliability fails within each task.
