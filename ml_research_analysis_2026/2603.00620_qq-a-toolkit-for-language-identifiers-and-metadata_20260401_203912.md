# QQ: A Toolkit for Language Identifiers and Metadata
## Quick Facts
- arXiv ID: 2603.00620
- Source URL: https://arxiv.org/abs/2603.00620
- Reference count: 13
- Primary result: QQ is a lightweight (~2 MB) Python library that unifies language metadata into a graph database with 27,256 languoids, enabling identifier conversion and cross-lingual integration, and is adopted in multilingual NLP workflows.

## Executive Summary
QQ (QwanQwa) addresses fragmentation in language identifiers and metadata for multilingual NLP. It compiles a unified, graph-based database from sources like Glottolog and LinguaMeta, creating a canonical representation of language entities (languoids, scripts, regions) and their relationships. The resulting toolkit provides a Python API for resolving any identifier (BCP-47, ISO, Glottocode) to a canonical node, converting between standards, and traversing the graph (e.g., family trees, shared scripts). Evaluations include auditing 1,476 Hugging Face datasets—revealing widespread use of deprecated codes—and integrating three cross-lingual resources for colexification analysis, which showed psycholinguistic ratings smooth over the colexification graph. QQ is now used in production for dataset auditing, language reporting, and metadata normalization.

## Method Summary
QQ builds its database through a pipeline: source importers extract and normalize data from Glottolog, LinguaMeta, pycountry, and other resources; a merger resolves conflicts (e.g., discrepancies in region codes) via manual rules or source priority; and a compressed graph database (≈2 MB) is written with nodes for languoids, scripts, regions, and edges encoding relationships (genealogy, region, script). The Python interface (`qq.Database`) loads this database and offers methods like `get()` for identifier resolution, `convert()` for cross-standard mapping, and traversal properties (e.g., `.family_tree`). The toolkit’s utility is demonstrated via a large-scale Hugging Face audit and a case study linking BabelNet, Concepticon, and NoRaRe for colexification analysis, showing seamless integration of heterogeneous linguistic resources.

## Key Results
- Unified graph database: 27,256 Languoids, 227 Scripts, 5,361 Regions, linked by 97,288 edges.
- Hugging Face audit: identified 8,189 unique language codes across 1,476 datasets, including 67 deprecated codes used in 165 datasets.
- Colexification analysis: psycholinguistic ratings (valence, concreteness) smooth significantly over the colexification graph (Rayleigh quotient R < 1, p < .001 across 10 languages).
- Adoption: integrated into multilingual NLP research workflows for dataset auditing, language reporting, and metadata normalization.

## Why This Works (Mechanism)
### Mechanism 1: Resolving Identifier Fragmentation
**Claim:** QQ resolves identifier fragmentation by unifying multiple metadata sources into a single, canonical graph of language entities.  
**Mechanism:** The system compiles a graph database where core nodes (Languoid, Script, Region) are sourced from Glottolog, LinguaMeta, pycountry, etc. Importers extract, normalize, and merge data, resolving conflicts via manual rules or source priority. A single `db.get()` call resolves any provided identifier (BCP-47, ISO, Glottocode) to a canonical Languoid object.  
**Core assumption:** Conflicts and overlaps between sources can be systematically merged into a coherent, non-contradictory graph without loss of critical information for NLP workflows.  
**Evidence anchors:** [abstract] "compiling a unified, graph-based database from sources like Glottolog and LinguaMeta"; [section 2.1] "QQ is structured as a graph... importers extract relevant values from sources, normalize, resolve, and merge them".  
**Break condition:** If upstream sources introduce irreconcilable contradictions (e.g., mutually exclusive genealogical classifications), the graph's coherence fails, leading to ambiguous results or resolution failures. The system logs conflicts but cannot automatically resolve fundamental ontological disagreements.

### Mechanism 2: Scalable Identifier Conversion
**Claim:** QQ enables scalable identifier conversion and reporting by abstracting identifier types behind a normalized Languoid interface.  
**Mechanism:** After resolving an input code to a canonical node, `db.convert()` or attribute access retrieves any desired identifier type from that node's merged metadata. This avoids pairwise mapping tables between every standard.  
**Core assumption:** All meaningful identifiers for a language entity can co-exist as properties on a single canonical node without semantic collision.  
**Evidence anchors:** [abstract] "enables identifier conversion, conflict resolution"; [section 2.2] Code examples showing `db.convert("nl", IdType.ISO_639_3) -> "nld"` and assertions that multiple codes resolve to the same object.  
**Break condition:** Deprecated or erroneous codes without a clear mapping to a canonical node will fail to resolve or produce incorrect mappings.

### Mechanism 3: Graph-Based Cross-Lingual Integration
**Claim:** The graph structure facilitates cross-lingual integration for research by enabling traversal of linguistic relationships (family, region, script).  
**Mechanism:** Edges link Languoid nodes to other Languoids (genealogy), Scripts, and Regions. Methods like `.languoids_with_same_script` or `.family_tree` perform graph hops, allowing users to find all languages sharing a writing system or belonging to a family without manual joins.  
**Core assumption:** These relational edges are consistently defined and present across the merged sources for the languages of interest.  
**Evidence anchors:** [abstract] "graph-based structure that enables traversal across families, regions, writing systems"; [section 2.2] Examples: `amharic.languoids_with_same_script` returns related languages; `dutch.family_tree` returns lineage; [section 4] Case study 3: "using QQ, we can analyze variations... by integrating three different resources" via the graph.  
**Break condition:** Sparse or missing edge data for low-resource or ancient languages breaks traversal (e.g., a Languoid with no linked Script node). The colexification analysis relies on complete graph connectivity; missing edges would fragment the semantic topology.

## Foundational Learning
### Languoid as a Neutral Super-Type
**Why needed here:** Avoids political/classification disputes (language vs. dialect) by treating all genealogical entities as Languoid nodes with a level property. This allows ISO codes, Glottocodes, and family codes to map to the same node type.  
**Quick check question:** If you have a Glottocode for a dialect (`stan1293` for Standard Arabic) and an ISO 639-3 code for its parent language (`ara` for Arabic), should these map to the same Languoid node? Why or why not?

### Graph-Based Data Integration
**Why needed here:** Language metadata is inherently relational (languages belong to families, are spoken in regions, use scripts). A graph model naturally represents these many-to-many relationships, enabling queries like "find all languoids related to Amharic by region" via traversal.  
**Quick check question:** Why would a relational (SQL) table with foreign keys be less ergonomic for the query "list all languoids related to Amharic by region" than QQ's `amharic.languoids_in_same_region`?

### Identifier Normalization vs. Parsing
**Why needed here:** QQ assumes identifiers are well-formed and exist in its graph. It does *not* parse BCP-47 strings (that's `langcodes`' job). Normalization is a lookup/merge activity, not a syntactic one. This separation of concerns is critical for correct usage.  
**Quick check question:** You have the code `"yue-Hant-HK"`. Should you pass this directly to `db.get()`? What step must you take first using a tool like `langcodes`?

## Architecture Onboarding
**Component map:** CLI (`qq rebuild`) → Source Importers (per-source data extraction/normalization) → Merger/Resolver (conflict resolution) → Graph Database (compressed .db file) → Python Interface (`qq.Database`).  
**Critical path:** `qq rebuild` triggers all importers → merger resolves conflicts → graph DB written → `Database.load()` loads DB → user queries (`get`, `convert`, traversal). Rebuild is a full pipeline; individual importer updates require a full rebuild.  
**Design tradeoffs:**  
- Coverage vs. Accuracy: Merging maximizes coverage (27k languoids) but risks propagating errors; conflicts are logged but resolution may introduce inaccuracies.  
- Size vs. Richness: The ~2 MB DB is lightweight by excluding large name translations; including all metadata would increase size.  
- Graph traversal vs. Pairwise distances: QQ provides structural traversal (family trees), not pre-computed linguistic distances (e.g., DistaLs); it is a complementary building block.  
**Failure signatures:**  
- `db.get("xyz")` returns `None` or raises `KeyError`: identifier invalid, not in any source, or discarded during conflict resolution.  
- `db.convert("nl", IdType.GLOTTOCODE)` returns a deprecated/incorrect code: check source priority order; canonical node's glottocode may be wrong.  
- Traversal (`.family_tree`) returns incomplete/empty lists: Languoid may have missing parent edges due to sparse source data.  
- Performance lag on `query()`: Complex in-memory filters over the full graph could be slow for large traversals despite small DB size.  
**First 3 experiments:**  
1. Identifier resolution sanity check: Load DB, pick 10 random ISO 639-3, BCP-47, and Glottocodes from the UpSet plot (Fig 4). Assert `db.get(code1) == db.get(code2)` for codes known to map to the same language; verify deprecated codes raise a warning.  
2. Graph traversal validation: For a well-documented language (e.g., `"amharic"`), verify `.languoids_with_same_script` includes known Ethiopic-script languages and `.family_tree` includes expected levels (e.g., Afro-Asiatic → Semitic).  
3. Colexification replication: Re-run the smoothness analysis (Section 4) using QQ-merged BabelNet, Concepticon, and NoRaRe. Confirm Rayleigh quotient R < 1 for valence across the 10 languages.

## Open Questions the Paper Calls Out
1. **How do different conflict resolution strategies (manual vs. source priority) during database compilation impact the accuracy and consistency of the unified language graph for downstream NLP tasks?**  
   *Basis:* The paper describes QQ's merging process and conflict resolution but does not evaluate impact.  
   *Why unresolved:* No quantitative assessment of resolution strategy impact is provided.  
   *What evidence would resolve:* A controlled study comparing output graphs under different policies against a manually verified gold standard, measuring changes in node/edge correctness and downstream task performance.

2. **To what extent do deprecated language identifiers in real-world datasets actually hinder reproducible multilingual NLP research, and can QQ's deprecation warnings measurably improve reporting practices?**  
   *Basis:* The Hugging Face audit identified 67 deprecated codes used in 165 datasets, but the paper does not investigate practical consequences.  
   *Why unresolved:* No analysis of whether deprecated codes cause integration errors or misclassification; effectiveness of warnings unmeasured.  
   *What evidence would resolve:* Longitudinal studies tracking adoption of QQ, comparing pre/post rates of deprecated code usage; case studies on specific deprecated codes revealing integration errors.

3. **How generalizable are the colexification findings (e.g., valence smoothing) across the full diversity of languages in QQ's graph, given that the analysis was limited to 10 languages with available psycholinguistic norms?**  
   *Basis:* The analysis used NoRaRe data for only 10 languages, acknowledging coverage gaps for many languages.  
   *Why unresolved:* The smoothness results are demonstrated for a small, typologically narrow subset; it remains open whether the pattern holds for under-resourced, indigenous, or ancient languages.  
   *What evidence would resolve:* Extending the analysis to all languages with any rating data, using imputation or partial-graph methods; statistical tests assessing moderation by language family, script, or region; manual validation on low-resource languages.

## Limitations
- Coverage gaps: Source data incomplete for low-resource/endangered languages; missing edges break traversal for some languoids.
- Conflict resolution opacity: Merger rules not fully transparent; undetected contradictions may persist in the canonical graph.
- Limited validation scope: Colexification smoothness claim relies on only 10 languages; generalizability across broader linguistic diversity is uncertain.

## Confidence
- Identifier unification: Medium
- Conversion abstraction: High
- Graph traversal utility: Medium
