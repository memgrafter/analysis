# CompactRAG: Reducing LLM Calls and Token Overhead in Multi-Hop Question Answering

## Quick Facts
- **arXiv ID:** 2602.05728
- **Source URL:** https://arxiv.org/abs/2602.05728
- **Reference count:** 40
- **Primary result:** Reduces token consumption per query to ~1.9K while maintaining competitive accuracy on multi-hop QA benchmarks, by limiting LLM calls to two per query regardless of hop count.

## Executive Summary
Multi-hop retrieval-augmented generation (RAG) systems typically suffer from high token overhead and repeated LLM invocations during iterative reasoning. CompactRAG addresses this by decoupling offline corpus restructuring from online query processing. Offline, an LLM converts the raw corpus into an atomic question–answer knowledge base, compressing information into self-contained factual units. Online, a complex query is decomposed once; each sub-question is resolved via dense retrieval and lightweight, trainable modules (Answer Extractor, Sub-Question Rewriter) to maintain entity continuity. Only two LLM calls are made per query—one for decomposition and one for final synthesis—drastically reducing token usage. Across HotpotQA, 2WikiMultiHopQA, and MuSiQue, CompactRAG achieves accuracy competitive with iterative baselines while lowering per-query token consumption by 60–80%. The initial offline cost is amortized over many queries, yielding substantial cumulative savings.

## Method Summary
The method operates in two stages. **Offline:** The entire corpus is processed by an LLM using a specialized prompt to generate atomic `(question, answer)` pairs, each expressing a single fact with entities explicitly included. These pairs are encoded with a dense retriever (Contriever) to build a searchable vector index. **Online:** For a user query, an LLM decomposes it into a dependency-ordered set of sub-questions. For each sub-question, the system retrieves top-*k* QA pairs from the index, uses a trained RoBERTa-based Answer Extractor to select the correct answer span, and uses a Flan-T5-based Sub-Question Rewriter to ground the next sub-question with the extracted entity. After resolving all sub-questions, a second LLM call synthesizes the final answer from the collected evidence. This design fixes the number of LLM calls per query at two, independent of hop count.

## Key Results
- Achieves 70.4% Exact Match on HotpotQA with LLaMA3.1-8B, competitive with iterative RAG baselines.
- Reduces average token consumption per query to ~1.9K, compared to 4.7K–10.2K for iterative methods.
- The offline restructuring cost is amortized; cumulative token usage falls below iterative baselines after ~1500 queries on HotpotQA.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Decoupling corpus representation from reasoning reduces retrieval redundancy and grounds evidence in fact-level units.
- **Mechanism:** An offline LLM pass converts raw passages into atomic `(question, answer)` pairs, each encoding one self-contained fact. This compresses the corpus by discarding non-essential text and aligns the knowledge space with query semantics, since LLM-generated questions match user query forms better than raw passages.
- **Core assumption:** Atomic QA pairs preserve all necessary factual content for multi-hop composition while eliminating lexical and topical redundancy present in original documents.
- **Evidence anchors:** 
  - Abstract: "...converts it into an atomic QA knowledge base, which represents knowledge as minimal, fine-grained question–answer pairs."
  - Section 3.1: "Each pair expresses a single factual statement with minimal granularity... ensuring non-overlapping information units suitable for multi-hop composition."
  - Corpus: Neighbors (e.g., EfficientRAG) also target redundancy, but CompactRAG's *offline restructuring* is the key differentiator.

### Mechanism 2
- **Claim:** Substituting iterative LLM reasoning with lightweight, trainable modules for answer extraction and question rewriting fixes the number of LLM calls per query to two.
- **Mechanism:** After initial decomposition, each sub-question is resolved by (1) retrieving top-*k* QA pairs via dense retriever, (2) using a RoBERTa-based span extractor to pick the correct answer from retrieved candidates, and (3) feeding that answer to a Flan-T5 rewriter to disambiguate the next sub-question. Only decomposition and final synthesis invoke the main LLM.
- **Core assumption:** A trained extractor can reliably select the correct answer span from a small set of retrieved QA pairs, and a rewriter can ground pronouns/ellipses using the extracted entity, preserving entity continuity without LLM intervention.
- **Evidence anchors:** 
  - Abstract: "...the LLM is invoked only twice in total—once for sub-question decomposition and once for final answer synthesis—regardless of the number of reasoning hops."
  - Section 3.2: Describes the `Answer Extractor` (Eq. 1) and `Sub-Question Rewriter` (Eq. 2) with their training objectives and data construction.
  - Section 5.3: Ablation shows removing either module hurts accuracy (e.g., w/o Rewriter on HotpotQA: 70.4 → 63.2), confirming their necessity for maintaining performance with fixed LLM calls.

### Mechanism 3
- **Claim:** Amortizing the one-time offline corpus restructuring cost across many user queries yields much lower cumulative token consumption than iterative online LLM calls.
- **Mechanism:** The offline stage processes the entire corpus *once* (high but fixed token cost). The online stage per-query cost is bounded (~1.9K tokens) because it uses only two LLM calls and lightweight modules, independent of hop count. As query count *N* increases, *Total Tokens = Offline Cost + N × (Low Per-Query Cost)*, while iterative baselines scale as *N × (High Per-Query Cost)*.
- **Core assumption:** The system will serve a sufficiently large volume of queries (*N*) such that the initial offline investment is outweighed by per-query savings.
- **Evidence anchors:** 
  - Abstract: "The initial offline cost is amortized, yielding much lower cumulative token usage as queries accumulate."
  - Section 5.2: Figure 3 shows cumulative token curves: CompactRAG's curve starts higher (offline cost) but grows slower, crossing and staying below iterative baselines after ~1500 queries on HotpotQA.
  - Corpus: Neighbors (e.g., Iter-RetGen, IRCoT) show linear token growth with hops; no neighbor challenges the amortization principle itself.

## Foundational Learning
- **Concept:** Multi-hop question answering decomposition and entity drift.
  - **Why needed:** The system decomposes complex questions into sub-questions; understanding *dependency ordering* and the *entity drift* problem (e.g., "Where was he born?" losing the entity) is essential to grasp why the rewriter module exists.
  - **Quick check:** Given the query "What is the capital of the state where the author of 'Pride and Prejudice' was born?", list the dependency-ordered sub-questions and identify where entity drift could occur without a rewriter.
- **Concept:** Dense retrieval vs. sparse retrieval (e.g., BM25).
  - **Why needed:** The online retrieval over atomic QA pairs uses Contriever (dense). Understanding that dense retrieval matches *semantic* similarity, not just lexical overlap, explains why it can find relevant QA pairs even when sub-question wording differs from the original corpus fact.
  - **Quick check:** Why might a dense retriever better match the sub-question "Who directed the sequel to 'Lilli'?" to the atomic QA pair `{"question": "What film is a sequel to 'Lilli'?", "answer": "Lilli's Marriage"}` than BM25?
- **Concept:** RAG efficiency metrics (tokens per query, LLM call count).
  - **Why needed:** The core innovation is reducing *token consumption* and *LLM invocations*. An engineer must measure these correctly (counting input + output tokens, all LLM calls) to evaluate the claimed gains.
  - **Quick check:** For an iterative RAG system that makes 3 LLM calls per query with an average 2000-token context per call, and CompactRAG with 2 calls averaging 950 tokens, what is the per-query token ratio? How does this ratio change if the iterative system goes to 5 hops?

## Architecture Onboarding
- **Component map:**
  Offline: Corpus Parser (spaCy) -> Atomic QA Generator (LLM) -> Dense Encoder (Contriever) -> QA Vector Index
  Online: Query Decomposer (LLM) -> Sub-question Dispatcher -> for each sub-question: Dense Retriever -> Answer Extractor (RoBERTa-base) -> Sub-question Rewriter (Flan-T5-small) -> Synthesis (LLM)
- **Critical path:**
  1. User query Q -> Decompose into dependency graph {q1, q2, ... qn}.
  2. For i=1 to n:
     a. Retrieve top-k QA pairs Pi for qi from vector index.
     b. Run Extractor on (qi, Pi) -> get answer ai.
     c. If i < n, run Rewriter on (qi+1, ai) -> get grounded qi+1.
  3. Aggregate all (qi, ai, Pi) -> Synthesis -> final answer.
- **Design tradeoffs:**
  - **Offline cost vs. online latency:** High initial token/compute cost to build QA index vs. low, predictable per-query latency. Justifiable only with non-trivial query volume.
  - **Knowledge base fidelity vs. automation:** Using a stronger LLM (GPT-4) for offline QA generation improves accuracy but increases offline cost; using a smaller LLM (LLaMA3.1-8B) is cheaper but caps upper-bound performance.
  - **Module complexity vs. robustness:** Adding Extractor & Rewriter increases system complexity and training requirements but is necessary to maintain accuracy with only two LLM calls. Removing them degrades performance (Table 3).
- **Failure signatures:**
  - **Poor offline QA generation:** Hallucinated or incomplete atomic facts -> retriever returns irrelevant passages -> extractor fails -> cascading error. Detect by evaluating random sampled QA pairs from the index.
  - **Rewriter failure:** Does not correctly insert entity (e.g., outputs ambiguous question unchanged) -> next retrieval loses grounding -> entity drift -> wrong final answer. Detect by logging rewritten sub-questions and comparing to gold dependency chains.
  - **Retriever mismatch:** Dense retriever fails to find relevant QA pairs for a sub-question due to lexical/semantic gap. Detect by low extractor confidence scores or empty top-k results.
- **First 3 experiments:**
  1. Reproduce token efficiency: Run CompactRAG and a baseline (e.g., Iter-RetGen) on 250 sampled HotpotQA queries. Log total input/output tokens per query. Expect CompactRAG ~1.9K vs. Iter-RetGen ~4.7K. Verify fixed 2 LLM calls for CompactRAG vs. hop-dependent calls for baseline.
  2. Ablation of rewriter: Disable the Sub-Question Rewriter (pass extracted answer ai as-is to next retrieval). Run on all three benchmarks. Expect significant EM drop, especially on MuSiQue (41.2 → 35.8 per Table 3), confirming rewriter's role in preventing entity drift.
  3. Knowledge base quality sensitivity: Build two CompactRAG systems: one with QA pairs from LLaMA3.1-8B, one from GPT-4 (as in paper). Keep online modules identical. Compare accuracy on test sets. Expect GPT-4-Reading to be higher (e.g., HotpotQA 70.4 → 77.2), proving offline knowledge quality is a performance lever.

## Open Questions the Paper Calls Out
- **Question:** Can smaller, cheaper LLMs generate atomic QA pairs without degrading CompactRAG's accuracy?
  - **Basis:** Table 2 shows a performance gap between LLaMA3.1-8B and GPT-4 as offline readers, with GPT-4 yielding higher EM/F1/Acc on all benchmarks.
  - **Why unresolved:** The paper only compares these two extremes and does not explore whether model scaling, distillation, or prompt tuning can narrow the gap cost-effectively.
  - **What evidence would resolve it:** Evaluate a range of model sizes (e.g., LLaMA 7B, 13B, 70B) and fine-tuned variants on the offline QA generation task; report downstream accuracy and total token/monetary cost.
- **Question:** Does CompactRAG generalize to multi-hop QA in specialized domains (e.g., biomedical, legal) that differ from Wikipedia?
  - **Basis:** The conclusion explicitly lists "cross-domain generalization of QA knowledge bases" as a future research direction.
  - **Why unresolved:** All experiments are on Wikipedia-derived benchmarks; domain-specific language and structure may impair atomic QA generation and retrieval.
  - **What evidence would resolve it:** Test CompactRAG on a multi-hop QA dataset from another domain (e.g., BioASQ) and compare accuracy and token consumption against iterative baselines; analyze error patterns.
- **Question:** How robust is CompactRAG to errors in the initial query decomposition, and can the lightweight downstream modules recover from such errors?
  - **Basis:** The pipeline relies on a single LLM decomposition call, but the paper provides no analysis of decomposition accuracy; training data for the answer extractor and rewriter assumes perfect decompositions.
  - **Why unresolved:** Incorrect or incomplete sub-questions can derail the reasoning chain; it is unclear whether the extractor and rewriter can detect or correct decomposition mistakes.
  - **What evidence would resolve it:** Introduce systematic noise into the decomposition (e.g., omit, duplicate, or misorder sub-questions) and measure the impact on final answer correctness; also correlate human-judged decomposition quality with end-to-end performance.

## Limitations
- Training data construction details for the Answer Extractor and Sub-Question Rewriter are underspecified (prompt templates, distractor sampling, split sizes), risking performance variance in reproduction.
- Decomposition and retrieval implementation specifics (exact prompt, graph resolution algorithm, top-k value, handling of parallel sub-questions) are not fully detailed, affecting online behavior.
- The amortization break-even point depends on corpus size and query distribution; the paper's ~1500-query threshold may not generalize to all deployment scenarios.

## Confidence
- **Fixed 2 LLM calls & token reduction:** High (empirically validated across three benchmarks).
- **Atomic QA knowledge base preserving facts:** Medium (ablation shows sensitivity to offline LLM choice, but hallucination risks unquantified).
- **Generalizability of break-even analysis:** Medium (analysis assumes static corpus and query stream; real-world usage patterns may differ).
