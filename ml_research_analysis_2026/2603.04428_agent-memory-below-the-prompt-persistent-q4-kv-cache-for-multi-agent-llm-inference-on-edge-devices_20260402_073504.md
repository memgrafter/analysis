# Agent Memory Below the Prompt: Persistent Q4 KV Cache for Multi-Agent LLM Inference on Edge Devices

## Quick Facts
- **arXiv ID:** 2603.04428  
- **Source URL:** https://arxiv.org/abs/2603.04428  
- **Reference count:** 40  
- **Primary result:** Persistent Q4 KV caches reduce time-to-first-token by up to 136× and enable 4× more agents versus FP16 with quality impact within ±3%.

## Executive Summary
Multi-agent LLM inference on edge devices is severely memory-constrained: only a few agents' KV caches fit in RAM, and eviction forces a costly re-prefill (e.g., 15.7 seconds per agent at 4K context). This work introduces persistent Q4 KV caches: each agent's cache is quantized to 4-bit and saved to disk in safetensors format, then reloaded directly into the attention layer, eliminating redundant prefill computation. The system provides per-agent isolation, batched quantized inference, and cross-phase context accumulation. Evaluated on Gemma 3 12B, DeepSeek‑Coder‑V2‑Lite 16B, and Llama 3.1 8B, cache restoration reduces time-to-first-token by up to 136× (22–136× for Gemma at 4K–32K). Q4 quantization shrinks per-agent cache by 72%, enabling 4× more agents versus FP16. Perplexity impact ranges from –0.7% (Gemma) to +3.0% (DeepSeek). Against FP16 prefix caching, Q4 matches latency but persists across restarts and high memory pressure, while FP16 fails. Multi-phase workflows show 1.9× TTFT improvement by phase 5.

## Method Summary
The system comprises three core components: (1) a block pool that partitions each agent's KV cache into 256-token blocks, quantizes to 4‑bit (uint32 packed with bfloat16 scales/biases, group size 64), and persists as safetensors; (2) a BatchQuantizedKVCache that merges, updates, fetches, and extracts batched quantized caches for concurrent inference, with a scheduler that chunks prefill and interleaves decode steps while respecting MLX's single‑threaded evaluation constraint; (3) a cross‑phase context injection mechanism that accumulates KV state across conversation phases via prompt extension (EXTEND match). Quantized attention is implemented via a fused kernel patched into mlx‑lm, handling GQA mask broadcasting and sliding‑window attention for Gemma.

## Key Results
- **TTFT reduction:** up to 136× (22–136× for Gemma across 4K–32K context lengths).
- **Memory efficiency:** Q4 quantization shrinks per‑agent cache by 72%, enabling 4× more agents compared to FP16.
- **Quality:** Perplexity impact modest, ranging from –0.7% (Gemma) to +3.0% (DeepSeek) on WikiText‑2.
- **Reliability:** Q4 persistent caches survive restarts and high memory pressure where FP16 prefix caching fails; multi‑phase workflows achieve 1.9× TTFT improvement by phase 5.

## Why This Works (Mechanism)
The persistent Q4 KV cache approach eliminates the need for repeated prefill computation by storing the intermediate key‑value states in a compressed format on disk. Quantization to 4‑bit drastically reduces memory footprint (72% shrinkage) and I/O volume, enabling more agents to be accommodated within limited RAM. The block pool design allows fine‑grained management of cache segments, while the batched quantized inference scheduler efficiently interleaves prefill and decode across agents, maximizing hardware utilization. Cross‑phase context accumulation extends the cache across multiple turns without re‑computation. The fused Q4 attention kernel integrates seamlessly with the quantized cache format, ensuring that the dequantization and attention computation are performed efficiently on Apple Silicon via MLX. Together, these innovations shift the bottleneck from compute‑bound prefill to I/O‑bound cache loading, which is orders of magnitude faster, thereby achieving massive TTFT reductions.

## Foundational Learning
- **KV Cache:** Stores computed key/value tensors for each token to avoid recomputation during autoregressive decoding. *Why needed:* Without caching, each token requires recomputation of all previous tokens' keys/values, which is prohibitively expensive for long contexts. *Quick check:* For a model with `n_layers`, `n_heads`, and `d_head`, the KV cache for `T` tokens has shape `[batch, n_layers, 2, n_heads, T, d_head]` (or similar).
- **Quantization (Q4):** 4‑bit integer representation with per‑group scaling factors (often group size 64) and optional bias. *Why needed:* Reduces memory footprint and I/O for persistent storage, enabling more agents to be cached. *Quick check:* Dequantize by reshaping packed int32 to int4, multiplying by scale, and adding bias.
- **Safetensors:** A safe, fast format for storing tensors (used by Hugging Face). *Why needed:* Avoids pickle security issues and provides memory‑mapped I/O. *Quick check:* Load with `mx.load_safetensors` (MLX) or `safetensors.torch.load_file`.
- **Grouped‑Query Attention (GQA):** Shares key/value heads across multiple query heads. *Why needed:* Reduces memory and compute compared to multi‑head attention while maintaining quality. *Quick check:* In GQA, `n_kv_heads` < `n_q_heads`; each query head attends to the same set of KV heads.
- **Multi‑head Latent Attention (MLA):** Used in models like DeepSeek, where KV cache is stored in a compressed latent space and expanded on‑the‑fly. *Why needed:* Further reduces KV memory for large models. *Quick check:* In MLA, `K` and `V` may have different dimensions; the attention kernel must handle asymmetric shapes.
- **Chunked Prefill and Interleaved Decode:** A scheduling strategy that processes prefill in chunks and mixes decode steps to keep the GPU busy. *Why needed:* Balances batch efficiency and latency in multi‑agent scenarios with varying context lengths. *Quick check:* The scheduler should ensure that each decode step uses the most recent KV state and that prefill chunks respect memory limits.

## Architecture Onboarding
**Component map:**  
Block Pool → BatchQuantizedKVCache → Quantized Attention Kernel (fused) → Model Output  
Block Pool also interacts with Disk (safetensors I/O) and Cross‑phase Context Injector modifies the prompt before prefill.

**Critical path:**  
1. On agent creation: load or initialize KV cache blocks (persisted to disk if available).  
2. For each turn: extend prompt (EXTEND match) to accumulate previous context; run chunked prefill for new tokens; interleave decode steps until generation complete.  
3. After turn: save updated KV blocks back to disk (asynchronously).

**Design tradeoffs:**  
- Quantization bit‑width: Lower bits reduce memory and I/O but increase perplexity; Q4 chosen as sweet spot.  
- Block size: 256 tokens balances fragmentation and I/O granularity.  
- Batching: Batch > 1 improves throughput but requires careful graph evaluation to avoid crashes (MLX thread‑safety).  
- Persistence: Disk storage enables survival across restarts but adds I/O latency; however, I/O is still far cheaper than recomputation.

**Failure signatures:**  
- MLX concurrency crashes: due to parallel `mx.eval()` calls; fix by serializing evaluation on one thread.  
- Batch = 2 warm cache produces EOS tokens: likely cache merging/padding bug or unfused batch support in Q4 kernel.  
- Sliding‑window attention misbehaves in Gemma: check mask generation and window size per layer.  
- Q4 quality variance: DeepSeek and Llama show +2–3% PPL; verify MLA handling and group scaling.  
- FP16 cache eviction: occurs around 8K context with multiple agents; monitor memory usage.

**First experiments:**  
1. Implement the block pool with Q4 quantization and safetensors persistence; verify that cache can be saved and reloaded without loss (compare FP16 and Q4 dequantized values).  
2. Build the BatchQuantizedKVCache and single‑threaded scheduler; test with batch = 1 and batch = 2 for simple prompts, ensuring no crashes and correct output.  
3. Run TTFT benchmarks for one model (e.g., Gemma 3 12B) at 4K context, measuring cold, warm, and hot latencies; compare against Table 3.

## Open Questions the Paper Calls Out
1. How does Q4 KV cache quality vary with context length and model architecture (GQA, MLA, MoE), and what layers are most sensitive? The paper notes longer‑context evaluation and per‑layer sensitivity analysis are future work.
2. Can persistent KV caches be shared across multiple edge devices with acceptable overhead? This would require cache transfer over interconnects like Thunderbolt or network.
3. Does the approach remain viable for 70B+ models on edge hardware? Larger models have larger KV dimensions; Q4 may still not fit many agents, and reload latency could dominate.
4. Can we use even lower bit‑widths (e.g., 2‑bit) with error correction for persistent caches? Adaptive quantization (e.g., RotateKV, CommVQ) is suggested but not integrated.

## Limitations
- Exact fused Q4 attention kernel and mlx‑lm modifications are not fully detailed; reproduction requires the GitHub repository.
- Benchmark harness specifics (thermal cooldown timing, corpus tokenization, server restarts) are high‑level; exact reproducibility depends on the original infrastructure.
- Warm vs hot cache performance depends on system I/O caching and MLX buffer management, with some conditions (e.g., warm beating hot at short contexts) not fully explained.
- Multi‑agent prompt templates and EXTEND match logic for cross‑phase accumulation are under‑specified.
- Evaluation limited to Apple M4 Pro and three models; generalizability to other hardware and model families remains unknown.
