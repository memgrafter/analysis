# Panini: Continual Learning in Token Space via Structured Memory

## Quick Facts
- **ArXiv ID:** 2602.15156
- **Source URL:** https://arxiv.org/abs/2602.15156
- **Reference count:** 40
- **Primary result:** PANINI achieves the highest average performance (56.1 F1) on six QA benchmarks, outperforming HippoRAG2 by 5–7% absolute while using 2–30× fewer answer-context tokens.

## Executive Summary
PANINI reimagines retrieval-augmented generation by replacing raw document chunks with a structured, non-parametric memory called the Generative Semantic Workspace (GSW). The GSW encodes each document as a network of entity- and event-aware question-answer (QA) pairs, transforming verbose text into a compact, pre-interrogated knowledge graph. At query time, a single decomposition step followed by a Reasoning-grounded Chain Traversal (RICR) performs beam search over this network, retrieving only the minimal set of QA pairs needed for multi-hop reasoning. This design eliminates the repeated processing of irrelevant context that plagues standard RAG, yielding state-of-the-art accuracy and dramatic token efficiency on six QA benchmarks.

## Method Summary
PANINI operates in two phases. During **write-time**, each document is parsed by an LLM into a per-document GSW: a graph where entity nodes (with roles/states) connect via verb-phrase/event nodes, and each verb-phrase instantiates bidirectional QA edges (e.g., "Who was born in X?" ↔ "Where was Y born?"). These atomic QA pairs are then indexed into a corpus-level dual index: a sparse BM25 index over entity surface forms and a dense vector index over QA-pair text. During **read-time**, a user query is first decomposed into ordered atomic sub-questions by an LLM. The RICR engine then performs a single beam search over the GSW: for each sub-question, it retrieves candidate QA pairs from both indices, reranks them, and maintains *B* parallel chains. Chains are scored by the geometric mean of per-hop reranker scores, with low-scoring paths pruned. Finally, the deduplicated set of retrieved QA pairs is supplied to an answer-generation LLM to produce the final response (with abstention logic for unanswerable queries).

## Key Results
- **SOTA efficiency and accuracy:** Highest average F1 (56.1) across six QA benchmarks, beating strong baselines like HippoRAG2 by 5–7% absolute.
- **Dramatic token reduction:** Uses 2–30× fewer answer-context tokens compared to baselines while maintaining or improving performance.
- **Robust abstention:** Best balance of answerable accuracy (79.8) and unanswerable abstention (74.0) on curated splits.

## Why This Works (Mechanism)

### Mechanism 1: Structured Memory (GSW) for Compact, Pre-Interrogated Facts
**Claim:** Storing information as atomic, entity-linked QA pairs rather than raw text chunks improves retrieval efficiency and accuracy.
**Mechanism:** At write-time, each document is converted into a GSW: a semantic graph where entity nodes (with roles/states) connect via verb-phrase/event nodes. Each verb-phrase instantiates bidirectional QA edges (e.g., "Who was born in X?" and "Where was Y born?"). This transforms verbose text into a network of pre-interrogated facts. At read-time, RICR traverses this network by following entity chains from decomposed sub-questions, retrieving only the QA pairs that constitute reasoning steps. This avoids repeatedly processing irrelevant raw chunks and ensures retrieved evidence is already formatted for LLM consumption.
**Core assumption:** A sufficiently complete set of atomic QA pairs—grounded in explicit entity mentions and verb-phrases—is adequate for an LLM to reconstruct the situation and answer complex queries via chain traversal.
**Evidence anchors:**
- [abstract] "writes each document into a structured Generative Semantic Workspace (GSW)—a network of entity- and event-aware question-answer pairs—and reads by performing a single reasoning-grounded chain traversal (RICR) over this memory."
- [section 2.1] Details GSW representation: "entity nodes... verb-phrase/event nodes... question–answer (QA) pairs that attach to verb phrases and point to entities." Also describes dual indexing: "BM25 index over entities... dense vector index over all QA pairs."
**Break condition:** GSW construction errors (missing verb-phrase nodes, incomplete QA pairs) break chains, as shown in qualitative error analysis [section F.2]. If a required relation is not encoded as a QA edge, the chain cannot traverse it.

### Mechanism 2: Reasoning Inference Chain Retrieval (RICR) for Single-Call Composition
**Claim:** RICR enables efficient multi-hop composition without iterative LLM calls by performing a single decomposition followed by beam-search over entity-linked QA chains.
**Mechanism:** RICR first decomposes a multi-hop query into ordered atomic sub-questions (e.g., Q1: "Who was mother of X?" → Q2: "When did <ENTITY_Q1> die?"). It then retrieves evidence hop-by-hop: for each sub-question, it uses dual search (entity BM25 + dense QA) to get candidate QA pairs, reranks them, and maintains *B* parallel chains. Chains are scored by the geometric mean of per-hop reranker scores, pruning low-scoring paths. This beam search explores multiple entity paths in parallel while keeping LLM calls minimal (only one for decomposition; subsequent steps are non-parametric).
**Core assumption:** Query decomposition produces a correct, minimal sequence of single-hop questions, and the chain scoring function (geometric mean) effectively prioritizes chains with consistently strong per-hop evidence.
**Evidence anchors:**
- [abstract] "reads by performing a single reasoning-grounded chain traversal (RICR)... uses 2–30× fewer answer-context tokens."
- [section 2.2] Details Algorithm 1: "At each subsequent hop t > 1... we maintain B chains in parallel... score(C) = (∏ sl)^(1/t)". Notes: "We decompose once; all subsequent steps are non-parametric retrieval."
- [section E.1.4] Ablation shows cumulative geometric scoring outperforms greedy last-hop selection (52.3 vs 50.81 on MuSiQue).
**Break condition:** Imperfect question decomposition leads to misaligned chains [section F.2, Row 3]. If the initial decomposition is wrong (e.g., dropping "co-official" constraint), subsequent hops follow incorrect paths even with perfect retrieval.

### Mechanism 3: Dual Indexing for Complementary Retrieval Signals
**Claim:** Combining sparse BM25 over entities and dense vectors over QA pairs increases recall of relevant QA pairs while keeping evidence compact.
**Mechanism:** PANINI builds two indices over the GSW: (1) a sparse BM25 index over entity surface forms + role/state strings, and (2) a dense vector index over QA-pair text. At each retrieval hop, both are queried, and results are merged and reranked. Entity retrieval helps when the query mentions known entities; QA-pair retrieval helps when the query is semantically similar to a stored question. This dual approach covers both alias matching (e.g., "Lothair II's mother" vs stored "Ermengarde of Tours") and paraphrased question matching.
**Core assumption:** Entity mentions and question phrasing provide two largely orthogonal retrieval signals; combining them yields higher recall of correct QA evidence than either alone.
**Evidence anchors:**
- [section 2.1] "We build two corpus-level indices... First, we create a sparse BM25 index over entities... Second, we build a dense vector index over all QA pairs."
- [section E.1.2] Ablation: "No dual search (entity-only)" drops to 39.5 F1 on MuSiQue (vs 52.3 full); "QA-only" is slightly weaker (52.3 vs 52.3 but likely less robust). This shows both components contribute.
**Break condition:** If either index is corrupted (e.g., entity resolution fails, QA pairs malformed), the dual advantage diminishes. For highly ambiguous entities, BM25 may retrieve spurious entities; if reranking fails to downrank them, chains may diverge.

## Foundational Learning
- **Retrieval-Augmented Generation (RAG)**  
  *Why needed:* PANINI is positioned as an improved NPCL framework relative to standard RAG. Understanding standard RAG's limitations (repeated chunk processing, irrelevant context injection) is prerequisite to seeing why Panini's structured memory and chain retrieval are novel.  
  *Quick check:* What are the two main failure modes of standard chunk-based RAG that Panini targets?
- **Beam Search in Structured Prediction**  
  *Why needed:* RICR uses a beam-search-like procedure to maintain multiple candidate chains. Understanding beam pruning, scoring, and the trade-off between beam width and accuracy is key to interpreting ablation results.  
  *Quick check:* How does Panini's chain scoring (geometric mean of per-hop scores) differ from greedy last-hop selection, and why might it be more robust?
- **Knowledge Graph Traversal vs. QA-Pair Networks**  
  *Why needed:* Panini contrasts with graph-based methods like HippoRAG2. Recognizing that Panini's GSW is a directed QA-pair network (not a traditional knowledge graph with PPR) explains its different retrieval dynamics (explicit chain-following vs. diffusion).  
  *Quick check:* Why does Personalized PageRank in HippoRAG2 lead to "retrieval drift" that Panini's RICR avoids?

## Architecture Onboarding
**Component map:**  
GSW Builder → Dual Indexer (corpus indices)  
Query Decomposer → RICR Engine → Answer Generator  
*Note:* Write-time flow: Document → GSW Builder → Dual Indexer. Read-time flow: Query → Query Decomposer → RICR Engine → Answer Generator.

**Critical path:** Document ingestion → GSW construction → Dual indexing → Query → Decomposition → RICR (hop-by-hop retrieval + beam pruning) → Answer generation.

**Design tradeoffs:**
- **Write-time vs. Read-time compute:** PANINI invests heavily in write-time (per-document LLM parsing + indexing) to achieve lightweight, token-efficient read-time. Favorable for static/slowly evolving corpora but costly for frequent updates.
- **Beam width (B):** Larger *B* (default 5) improves multi-hop accuracy marginally but increases token usage. Ablation shows *B*=3 nearly matches *B*=5 while cutting tokens ~25% [Table 13].
- **Granularity of GSW:** More QA pairs increase coverage but also indexing cost and potential noise. Design favors atomic, bidirectional QA to enable flexible chain formation.

**Failure signatures:**
- **Write-time GSW errors:** Missing verb-phrase nodes (no QA edges for a relation), orphaned entities (entities not in any QA answer), malformed bidirectional QA pairs. Detected via validation rules in the second-pass refinement prompt [Figure 5].
- **Read-time retrieval failures:** "Missing second hop" where first-hop answer is retrieved but subsequent hops fail (often due to entity alias mismatch or insufficient QA coverage). "Retrieval drift" where chains wander to semantically related but incorrect entities (less common than in graph-based methods due to hop-specific querying).
- **Decomposition errors:** Over-decomposition or dropped constraints (e.g., ignoring "co-official" language) leading to misaligned chains.

**First 3 experiments:**
1. **Ablate dual search:** Run Panini with entity-only and QA-only retrieval to confirm both indices contribute [section E.1.2].
2. **Vary beam width:** Test *B*=1,3,5,10 to characterize accuracy-token tradeoff [Table 13].
3. **Open-source pipeline replication:** Replace proprietary components (decomposer, reader, GSW builder) with open-source models (Qwen3) to assess robustness and minimum viable model sizes [Appendix D]. Validates that gains are framework-driven, not model-specific.

## Limitations
- **Write-time scalability:** GSW construction requires per-document LLM parsing and QA pair generation. Cost and latency for large, frequently updated corpora remain unclear.
- **GSW construction robustness:** Performance hinges on completeness and accuracy of initial GSW extraction. Errors in entity/verb-phrase detection or QA generation (e.g., missing a critical relation) break reasoning chains; boundary conditions for "sufficiently complete" GSWs are not quantified.
- **Beam search pruning optimality:** The geometric mean scoring for chain pruning is a design choice. Its optimality relative to other scoring functions (e.g., product of top-*k* hop scores, learned reranker) and sensitivity to noise in early hops are open questions.

## Confidence
- **High:** Claims about token efficiency and absolute performance gains over baselines on static benchmarks (directly supported by reported results and ablations).
- **Medium:** Superiority of dual indexing (entity BM25 + dense QA) for retrieval recall (ablations show benefit, but orthogonality of signals is inferred).
- **Low:** General sufficiency of the GSW representation for arbitrary multi-hop reasoning (core, untested assumption; only demonstrated on specific QA benchmarks).

## Next Checks
1. **Stress-test GSW construction:** Process a corpus with known, complex relational facts (e.g., a synthetic knowledge graph) and measure the percentage of required atomic relations that are *not* encoded as valid QA pairs. Quantifies the "completeness" assumption.
2. **Ablate chain scoring function:** Replace geometric mean chain score with greedy last-hop selector and a learned reranker (trained on chain-level labels) to determine if the current heuristic is optimal or merely sufficient.
3. **Test on dynamic corpora:** Simulate a streaming setting where documents are incrementally added. Measure degradation in recall/accuracy over time without periodic full re-indexing, to assess true "continual learning" robustness versus static benchmark performance.
