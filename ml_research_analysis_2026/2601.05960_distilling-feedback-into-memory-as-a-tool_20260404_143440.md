# Distilling Feedback into Memory-as-a-Tool

## Quick Facts
*   **arXiv ID:** 2601.05960
*   **Source URL:** https://arxiv.org/abs/2601.05960
*   **Reference count:** 40
*   **Primary result:** A memory-augmented agent that distills feedback into file-based guidelines matches self-critique performance after two iterations and significantly outperforms baselines in long-horizon mixed tasks (H=12).

## Executive Summary
This paper addresses the high computational cost of inference-time self-critique, where models repeatedly generate and revise responses for each query. It proposes the Memory-as-a-Tool framework, where an LLM agent actively distills transient feedback from a judge into persistent, file-based memory during inference. These distilled principles are later retrieved via explicit tool calls (`ls`, `read file`) to improve performance on subsequent tasks. On the Rubric Feedback Bench, the approach achieves performance comparable to expensive self-critique with near-zero-shot cost at test time, demonstrating effective knowledge accumulation across tasks with lower variance.

## Method Summary
The method introduces a lifelong learning protocol during inference. An agent equipped with file-system tool calls generates a response for a task, receives structured feedback and a score from a separate evaluator LLM, and then updates a persistent memory store (`/memories/`). The update involves abstracting general principles from the specific feedback and deciding to either create a new file (`write file`) or update an existing one (`edit file`). For all subsequent tasks, the agent first lists memory filenames, reasons about their relevance, and explicitly reads applicable files before generating its response. No model parameters are updated; learning occurs solely through this agent-managed memory consolidation process.

## Key Results
*   On sequential tasks within a rubric category (H=3), the memory agent matches the performance of a per-task self-critique baseline after just two feedback iterations, achieving similar scores at a fraction of the cumulative inference cost.
*   In a long-horizon mixed-task setting (H=12, interleaved categories), the memory agent achieves a score of 0.78±0.10, significantly higher than the zero-shot baseline (0.52±0.25) and with much lower variance.
*   The cost analysis shows the memory agent's score-cost trade-off is comparable to self-critique but operates at near-zero-shot cost for new queries after the initial learning phase, effectively amortizing the reasoning expense.

## Why This Works (Mechanism)

### Mechanism 1: Amortization via Distillation
The framework amortizes the high computational cost of inference-time self-critique by distilling transient feedback into persistent, reusable guidelines stored in a file-based memory system. Instead of recomputing critique-and-revision cycles for each new query, the LLM synthesizes abstract principles from episodic feedback and writes them to a memory file. Future tasks retrieve and prime the model with these principles via `read file` calls, enabling near-zero-shot application of learned nuances. The core assumption is that the LLM can successfully abstract generalizable "lessons learned" from specific feedback instances and apply them to novel but related tasks. Evidence includes the probabilistic formulation of a separate memory update operation and the paper's stated goal of converting "transient critiques into retrievable guidelines." A break condition occurs if memory files become cluttered with contradictory, redundant, or overly specific rules, degrading retrieval utility.

### Mechanism 2: Interpretable, Agent-Driven Retrieval
Retrieval is agent-driven and interpretable via explicit filename reasoning (`ls` then `read file`), avoiding opaque vector similarity search and enabling human inspection of the memory journal. Before generating a response, the agent must first list memory filenames (e.g., `chaos cinema critique rubric.txt`) and reason about their semantic relevance to the current task. This forces the model to consider memory organization during the write phase (choosing descriptive filenames) and during retrieval. The core assumption is that the LLM's reasoning over filenames is sufficient for effective retrieval without semantic embedding search, up to a certain memory scale. Evidence is found in the protocol description requiring `ls(path="/memories/")` and the stated benefit of "human-interpretable memory." A break condition is scalability; as the number of memory files grows (e.g., thousands), the agent's ability to scan lists and judge relevance via filenames diminishes.

### Mechanism 3: Agent-Managed Consolidation
Memory consolidation (deduplication and conflict resolution during `write file`/`edit file`) transforms noisy episodic feedback into a curated knowledge base of semantic principles, preventing simple log accumulation. During the memory update step, the LLM is instructed to abstract principles and decide whether to create a new file or update an existing one. This agent-controlled edit/merge policy allows for handling contradictions (e.g., replacing an old rule with a new, corrected one) and thematic grouping. The core assumption is that the LLM can perform reliable knowledge integration—identifying when new feedback contradicts or refines existing memory entries and making appropriate structural edits. Evidence is in the described "Conflict resolution" step and appendix details on checking for redundancy. A break condition is poor consolidation decisions, such as merging incompatible principles or failing to update a critical outdated rule.

## Foundational Learning
*   **Concept:** Inference-Time Scaling / "System 2" Thinking
    *   **Why needed:** The paper's premise is to amortize the cost of expensive critique-revision loops (multiple forward passes per query). Understanding this computational burden is key to grasping the efficiency problem.
    *   **Quick check:** Why is running a critique-revision loop for every user query computationally prohibitive in a production deployment?
*   **Concept:** Tool-Augmented Agents / Function Calling
    *   **Why needed:** The memory system is accessed exclusively via `ls`, `read file`, `write file`, `edit file` tool calls. The agent's orchestration of these tools is fundamental to the protocol.
    *   **Quick check:** How does treating memory as an external tool (vs. a hidden context buffer) change the agent's reasoning responsibilities?
*   **Concept:** Continual / Lifelong Learning (Episodic-to-Semantic Memory)
    *   **Why needed:** The benchmark tests sequential task learning without catastrophic interference. The memory's purpose is to accumulate useful, generalizable knowledge across episodes.
    *   **Quick check:** What is the key difference between storing raw past interactions (episodic) and the distilled "lessons learned" files (semantic)?

## Architecture Onboarding
*   **Component map:**
    Agent Core (LLM) -> Tool Interface (`ls`, `read file`, `write file`, `edit file`) -> Memory Backend (filesystem) <- Evaluator/Judge (LLM) <- Task Generator (Rubric Feedback Bench)
*   **Critical path:** Task `z_i` -> Agent generates `x_i` -> Judge gives `feed_i` and score -> **Memory Update** (Agent abstracts principle, decides `write/edit`) -> (Next task `z_j`) -> Agent `ls` & `reads` relevant files -> generates improved `x_j'`.
*   **Design tradeoffs:**
    *   Interpretability vs. Scalability: Human-readable files are transparent but may not scale to thousands; vector search scales but is opaque.
    *   Amortization vs. Freshness: Distilled rules persist but may become stale; self-critique is always current but expensive.
    *   Agent Autonomy vs. Control: LLM-managed files are flexible but risky; a fixed schema would be predictable but less adaptive.
*   **Failure signatures:**
    *   Memory Silence: Agent never calls `write file` after feedback.
    *   Semantic File Bloat: Creates overly-specific filenames or fails to merge similar principles.
    *   Retrieval Failure: Lists files but selects none or wrong ones for a new task.
    *   Principle Corruption: Writes contradictory rules to the same file or overwrites a good principle.
*   **First 3 experiments:**
    1.  **Baseline Replication:** Run zero-shot and self-critique baselines on a single rubric category (H=3) to establish the performance gap and cost baseline.
    2.  **Single-File Memory Test:** Force the agent to use only one memory file (`principles.txt`). Does it still improve across H=3? Tests distillation without organizational complexity.
    3.  **Retrieval Ablation:** Disable the `ls` step, provide *all* memory content as context every time. Compare performance and context length to standard `ls`+`read` to isolate the value of agent-driven selection.

## Open Questions the Paper Calls Out
### Open Question 1
*   **Question:** How does the file-based memory retrieval mechanism scale in terms of both cognitive load on the LLM and performance when the number of stored memory files grows into the thousands, as required for lifelong learning?
*   **Basis in paper:** In the Limitations section, the authors state that "scalability challenges as the memory namespace grows into thousands of files" are a key limitation and that "future work could implement hierarchical file structures... thereby mimicking how human experts efficiently locate information."
*   **Why unresolved:** The experiments only used a maximum horizon of H=12 tasks, resulting in at most 8 memory files. The system's reliance on the LLM reasoning over filenames via `ls` was not stress-tested for large-scale retrieval.
*   **What evidence would resolve it:** A scalability experiment where the agent accumulates thousands of memory files across diverse tasks, measuring (a) retrieval accuracy (correct file selection rate), (b) generation performance relative to an optimal semantic search baseline, and (c) inference latency/cost as a function of memory size.

### Open Question 2
*   **Question:** To what extent do the learned, distilled memory guidelines generalize beyond the specific creative writing and stylistic rubric domains of the Rubric Feedback Bench to other fundamental LLM capability areas like code generation, mathematical reasoning, or factual question answering?
*   **Basis in paper:** The entire evaluation is confined to the Rubric Feedback Bench, which focuses on "open-ended writing" tasks across categories like creative, analytical, behavioral, and ethical domains. The methodology for distilling feedback into "abstract principles" is demonstrated on stylistic rubrics. The paper does not test whether the same memory consolidation process yields effective, reusable guidelines for non-linguistic or non-stylistic tasks.
*   **Why unresolved:** The paper's claim that the framework enables "accumulate[d] knowledge across heterogeneous task types" is supported only by mixing different *writing* rubric categories. There is no evidence that the memory mechanism handles tasks requiring different cognitive processes (e.g., debugging code, solving an equation).
*   **What evidence would resolve it:** Running identical memory-augmented experiments on established benchmarks for coding (e.g., HumanEval), math (e.g., GSM8K), or factual QA (e.g., MMLU), using rubrics that define correctness or style for those domains.

### Open Question 3
*   **Question:** How robust is the memory consolidation process to receiving contradictory feedback from different rubrics or evaluators over time, and does the LLM's self-directed conflict resolution successfully prevent catastrophic interference or the corruption of previously correct knowledge?
*   **Basis in paper:** The framework design includes a "Conflict resolution" step where the LLM "decides whether to create a new file... or update an existing one" and updates "contradictory information based on newer feedback." However, the experiments use a single, consistent evaluator model per task category and rubrics that are internally coherent for a given task type. The long-horizon mixed-task experiment interleaves *different* task *types*, but it does not introduce scenarios where a single principle might receive conflicting feedback from different rubrics.
*   **Why unresolved:** The paper demonstrates knowledge accumulation but not knowledge *integration* under conflict. The observed improvement could be due to simply adding non-overlapping guidelines for distinct tasks, not resolving contradictions.
*   **What evidence would resolve it:** A controlled study where an agent receives a sequence of tasks with rubrics that impose opposing requirements on a shared dimension (e.g., Task 1: "Write formally," Task 2: "Write informally"). Measuring (a) the content of the relevant memory file(s) after each update, (b) the agent's ability to correctly apply the *most recent* rule on a probe task, and (c) performance degradation on earlier task types after the contradictory update.

### Open Question 4
*   **Question:** Does distilling feedback from a *model-based evaluator* (as used in the paper) produce memory guidelines that are as effective and robust as those distilled from *human-generated feedback*, given that human critiques may be noisier, more nuanced, or grounded in different intents?
*   **Basis in paper:** The paper consistently uses "simulated feedback" from an LLM judge ("we utilize a different Claude model variant... to serve as the evaluator"). The Rubric Feedback Bench is designed for models to act as judges. This is a methodological choice, not an evaluation of its equivalence to human feedback.
*   **Why unresolved:** The entire efficacy claim is based on a closed loop of LLM-generated tasks, rubrics, feedback, and memory updates. The core assumption is that model-generated feedback is a suitable proxy for human feedback for the purpose of learning stylistic principles. However, human feedback often contains different nuances. The framework's performance ceiling with real human-in-the-loop feedback remains unknown.
*   **What evidence would resolve it:** A comparative experiment where two agent populations are trained: one with feedback from the LLM judge (as in the paper) and one with feedback from human evaluators on the same set of tasks. The resulting memory guidelines would be compared for (a) quality (via human evaluation), (b) transfer performance on new tasks (using human judges), and (c) stability.

## Limitations
*   The evaluation is confined to a specific benchmark of open-ended writing tasks (Rubric Feedback Bench); applicability to domains like code, math, or factual QA is unproven.
*   The file-based retrieval mechanism likely does not scale to thousands of memory files, a key limitation for lifelong learning scenarios.
*   The robustness of the consolidation process to contradictory feedback from different evaluators or drifting rubrics is not evaluated.

## Confidence
*   **Mechanism 1 (Amortization via distillation):** Medium. Paper’s formulation supports it, but evidence is indirect; relies on unverified assumption that LLMs consistently abstract generalizable principles.
*   **Mechanism 2 (Filename-driven retrieval):** Medium. Protocol is explicit, but scalability beyond hundreds of files is suspect and not tested.
*   **Mechanism 3 (Agent-managed consolidation):** Low-Medium. Operational details are inferred; no evidence that LLM-driven edit/merge decisions avoid corruption or interference.
*   **Main empirical result (long-horizon improvement):** High. The H=12 experiment is clear and shows a significant, low-variance gain over the baseline.
*   **Scalability claim:** Low. The paper itself identifies this as a major unresolved limitation with no empirical test.

## Next Checks
1.  **Memory Abstraction Quality Audit:** Manually inspect a sample of `write_file` outputs after first feedback across 10 tasks. Verify content abstracts *principles* (e.g., “Prioritize clarity”) vs. raw episode logs. Low abstraction rate invalidates amortization premise.
2.  **Retrieval Scalability Stress Test:** Scale memory to 1,000+ synthetic files. Measure agent’s `ls`→`read` accuracy and performance drop vs. a vector-retrieval baseline. Failure to maintain >80% relevant-file retrieval breaks Mechanism 2.
3.  **Consolidation Decision Logging:** Intercept all `edit_file` vs. `write_file` calls. Quantify merge rate and conflict-resolution accuracy by cross-referencing with ground-truth theme clusters (rubric categories). >30% erroneous merges falsifies Mechanism 3.
