# Towards Dynamic Dense Retrieval with Routing Strategy

## Quick Facts
- arXiv ID: 2602.22547
- Source URL: https://arxiv.org/abs/2602.22547
- Reference count: 38
- Primary result: DDR-prior achieves superior average NDCG@10 on six zero-shot BEIR tasks while training only ~2% of parameters.

## Executive Summary
Traditional dense retrieval models require full fine-tuning to adapt to new domains, which is costly and data-intensive. This paper introduces Dynamic Dense Retrieval (DDR), a method that uses prefix tuning to create lightweight, domain-specialized modules and a routing strategy to dynamically combine them during inference. This allows efficient domain adaptation without retraining the entire model. On six zero-shot BEIR benchmarks, DDR-prior outperforms standard dense retrievers like Contriever and ANCE, with only about 2% of parameters updated.

## Method Summary
DDR employs a dual-encoder architecture with a frozen pre-trained backbone (coCondenser). It introduces a general prefix (applied to both query and passage encoders) and eight domain-specific prefixes (applied only to the query encoder). During inference, a router uses the layer-wise [CLS] representation of the query to compute importance weights β via a softmax layer. These weights are masked by a prior domain set M (e.g., the domains relevant to a specific BEIR task), then combined with the general prefix: \( P_q = P^g + \sum_{i \in M} \beta_i P^d_i \). Training proceeds in two phases: (1) the general prefix is trained on MS-MARCO using contrastive loss; (2) the general prefix is frozen, and the domain prefixes plus router are trained on the BERRI dataset, which includes domain labels and instructions, with masking. Only approximately 2% of the model’s parameters are trained.

## Key Results
- DDR-prior achieves higher average NDCG@10 than Contriever and ANCE across six zero-shot BEIR tasks.
- The approach trains only about 2% of the model’s parameters.
- Ablation studies confirm that both the routing mechanism and the prior domain masking are essential for performance.

## Why This Works (Mechanism)
The frozen backbone retains general retrieval knowledge, while the small, specialized prefixes inject domain-specific features efficiently. The router dynamically determines the contribution of each domain prefix based on the incoming query, allowing the model to adapt its representation without altering the core encoder. Masking with prior domain information constrains the routing to relevant experts, preventing noise from unrelated domains. This design balances parameter efficiency with expressive specialization, enabling zero-shot adaptation to new domains.

## Foundational Learning
- Prefix Tuning: Why needed: Enables parameter-efficient adaptation by modifying only input embeddings. Quick check: Does adding prefix tokens to the input alter model behavior while training a tiny fraction of parameters?
- Dual-Encoder Architecture: Why needed: Allows efficient retrieval by encoding queries and passages separately. Quick check: Are query and passage encoders symmetric? In DDR, they share the backbone but differ in prefix application.
- Contrastive Learning (InfoNCE): Why needed: Trains the retriever to distinguish positive from negative examples. Quick check: Is the loss computed as the negative log-likelihood of the positive pair against in-batch negatives?
- Dynamic Routing: Why needed: Combines multiple expert modules based on input-specific relevance. Quick check: Does the router output a probability distribution (via softmax) over domain prefixes?
- Zero-Shot Domain Adaptation: Why needed: Evaluates model performance on unseen domains without target-domain training. Quick check: Are evaluation datasets (BEIR tasks) disjoint from training domains (BERRI)?
- Parameter-Efficient Fine-Tuning (PEFT): Why needed: Avoids catastrophic forgetting and reduces computational cost. Quick check: What percentage of total parameters are updated? (~2% in DDR).

## Architecture Onboarding
Component map: Backbone (frozen) -> Encoder Layers; General Prefix -> added to both query and passage encoders; Domain Prefixes (8) -> added only to query encoder; Router -> takes layer-wise query [CLS] states x^l -> computes β weights; Combined Prefix = General Prefix + Σ (β_i * Domain Prefix_i); Query Encoding = Backbone + Combined Prefix; Passage Encoding = Backbone + General Prefix; Retrieval = maximum inner product search between encoded queries and passages.

Critical path: For each query layer l, extract [CLS] state x^l → router computes β = softmax(W_r x^l) → mask β with domain set M → combine prefixes → encode query → dot-product similarity with pre-encoded passage corpus → return top-k results.

Design tradeoffs: Parameter efficiency vs. expressive power (prefix length 128 limits capacity); routing complexity vs. interpretability (top-2 vs. prior-masked routing); reliance on manual domain labels vs. automation (BERRI provides domain sets).

Failure signatures: Router collapse (β becomes uniform or constant across queries); overwriting general knowledge (performance on general tasks degrades after phase 2); incorrect domain mapping (assigning wrong domain set M to a BEIR task).

Three first experiments:
1. Train only the general prefix on MS-MARCO and evaluate on BEIR tasks to establish a strong general retrieval baseline.
2. Train domain prefixes and router on BERRI with prior masking, then evaluate each BEIR task using its predefined domain set M.
3. Ablate the routing mechanism by replacing learned β with uniform weights, and ablate the prior by removing domain masking, measuring the drop in NDCG@10.

## Limitations
- Domain mapping ambiguity: The exact mapping from the 8 domain-specific modules to the higher-level domain labels (e.g., Science, QA) and their assignment to the six BEIR test tasks is not specified.
- Router implementation gaps: Unclear whether router weights are shared across layers, which layer output x^l is used (e.g., after attention or feed-forward), and full training hyperparameters (epochs, batch size, negative mining details).
- Stability risks: The dual-phase training could cause router collapse or overwrite general knowledge, but specific mitigations (e.g., entropy regularization, L2 penalties) are not detailed.
