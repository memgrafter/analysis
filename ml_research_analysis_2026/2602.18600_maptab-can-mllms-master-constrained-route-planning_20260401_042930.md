# MapTab: Can MLLMs Master Constrained Route Planning?
## Quick Facts
- **arXiv ID**: 2602.18600
- **Source URL**: https://arxiv.org/abs/2602.18600
- **Reference count**: 40
- **Primary result**: Introduces a multimodal route planning benchmark; top model (Gemini-3-Flash-Preview) achieves only ~69% exact match accuracy, while most open-source models score below 30%.

## Executive Summary
MapTab addresses the lack of benchmarks for constrained multimodal reasoning by introducing a route planning benchmark that fuses map images with structured node/edge tables. It comprises 328 real-world maps (160 metromaps, 168 travelmaps) and nearly 200,000 route planning queries plus 4,000 QA instances, incorporating constraints on time, price, comfort, and reliability. Evaluation of 15 MLLMs reveals substantial performance gaps: the best model reaches ~69% exact match accuracy, with open-source models trailing below 30%. Key findings indicate that visual perception remains a bottleneck, multimodal inputs often degrade performance relative to tabular-only baselines, models rely on shortest-path heuristics and fail at multi-constraint optimization, and explicit reasoning chains offer limited benefits. The benchmark underscores critical challenges in constrained reasoning, numerical computation, and long-horizon planning for MLLMs.

## Method Summary
The benchmark provides for each map a raster image and two structured tables: `Edge_tab` (edge attributes: travel time, price, comfort, reliability) and `Vertex_tab` (node attributes: station names, transfer indicators). Queries are of two types: route planning (RP), requiring an optimal station sequence with transfer markers, and QA, asking factual attributes. Ground-truth routes are generated deterministically via Dijkstra's algorithm combined with a weighted aggregation of constraints, ensuring a single optimal solution per query.

Fifteen MLLMs (including GPT-4o, Gemini-3-Flash-Preview, and Qwen3-VL) are evaluated in zero- or few-shot settings with fixed decoding parameters (temperature=0, max_tokens=2048). Models receive either multimodal inputs (image + tables) or tabular-only inputs. Performance is measured by Exact Match Accuracy (EMA), Partial Match Accuracy (PMA), Difficulty-aware Score (DS) for RP tasks, and plain Accuracy for QA. No training is performed; the focus is on inference capability.

## Key Results
- **Benchmark scale**: 328 maps, 196,800 RP queries, 3,936 QA queries.
- **Performance extremes**: Gemini-3-Flash-Preview leads with ~69% EMA on metromap with full modalities; most open-source models score below 30%.
- **Diagnostic insights**: Visual perception is a bottleneck; multimodal inputs often hinder compared to tabular-only; models default to shortest-path heuristics and struggle with multi-constraint trade-offs; explicit reasoning chains yield minor gains.

## Why This Works (Mechanism)
MapTab effectively tests constrained multimodal reasoning by requiring models to integrate spatial information from map images with precise numerical data from tables to find optimal routes under multiple objectives. The design uses authentic map topologies to introduce complex graph structures, while the tables encode quantifiable attributes that demand arithmetic and comparison. By generating ground truth with a deterministic algorithm, the benchmark isolates model reasoning from ambiguity. The separation of RP and QA tasks probes both planning and factual retrieval. This combination exposes the limitations of current MLLMs in fusing modalities, performing numerical optimization, and maintaining consistency over long sequences.

## Foundational Learning
- **Constrained Route Optimization**  
  *Why needed*: Core problem where models must balance multiple attributes (time, price, comfort, reliability) to find the best path.  
  *Quick check*: Implement Dijkstra with a linear combination of edge weights. Can you reproduce the optimal routes for a small graph?

- **Multimodal Fusion**  
  *Why needed*: MapTab requires aligning visual layout with tabular data; models must extract stations and connections from images and correlate them with table entries.  
  *Quick check*: Given a map image, can you list all stations and transfer points without using any OCR? How would you match them to rows in `Vertex_tab`?

- **Graph Representation via Node/Edge Tables**  
  *Why needed*: The tables provide the formal graph structure with attributes; understanding this representation is essential for reasoning.  
  *Quick check*: From `Edge_tab` and `Vertex_tab`, reconstruct adjacency lists and identify edges that correspond to transfers.

- **Evaluation Metrics (EMA, PMA, DS)**  
  *Why needed*: Quantify model performance with varying strictness and difficulty weighting.  
  *Quick check*: For a given query, compare model output to reference: if one station is wrong, what are the scores? How does DS reflect query rarity?

## Architecture Onboarding
**Component Map**  
The evaluation pipeline flows as: `Map Image + Edge Tab + Vertex Tab -> Multimodal Model Inference -> Response Generation -> Output Parsing -> Metric Computation`.

**Critical Path**  
1. Obtain official data files (images, CSVs, query lists) from the GitHub repository.  
2. Configure model environment (API keys or local checkpoints) and match decoding settings (temperature=0, max_tokens=2048, appropriate context length).  
3. Run inference on the provided test split (110 images) for desired modalities.  
4. Parse model outputs strictly (hyphen-separated station IDs, optional "(transfer)" markers).  
5. Compute EMA, PMA, DS, and QA accuracy using the official script.

**Design Tradeoffs**  
- Real-world maps increase ecological validity but introduce uncontrolled variations in style and annotation.  
- Using a Gemini model to auto-generate tables balances cost and scalability, yet the version and prompts affect numerical values.  
- Four constraints cover common factors but omit others (e.g., number of transfers), limiting scope.  
- Providing both image and tables enables multimodal assessment but may cause interference if models ignore one modality.

**Failure Signatures**  
- *Format violations*: Model output missing transfer markers, containing spaces, or multi-line; often due to weak prompt enforcement.  
- *Score regression on Hard queries*: Performance drops sharply on metromap Hard subset, typically because visual perception fails or table values drift.  
- *Heuristic reliance*: Models output shortest paths (fewest hops) even when constraints conflict, indicating lack of true multi-objective optimization.

**Three First Experiments**  
1. **Fidelity Check**: Randomly select 20 maps and verify that `Edge_tab`/`Vertex_tab` values lie within the ranges reported in the paper (e.g., Time 0–3 minutes).  
2. **Score Replication**: Run the evaluation script on the test split for GPT‑4o and Qwen3‑VL‑8B with the exact settings; confirm EMA, PMA, DS match published numbers within a small tolerance.  
3. **Modality Ablation**: Re-run a subset of queries with tabular-only inputs (no map image) and measure the change in EMA; this directly tests the claim that multimodal input degrades performance.

## Limitations
- Data provenance: exact sources and licensing of the 328 map images are not fully documented, which may hinder long-term reproducibility and generalizability.
- Table generation: the Gemini model version and decoding parameters used to produce `Edge_tab` and `Vertex_tab` are unspecified, risking numerical drift if regenerated.
- Benchmark scope: limited to metro and travel maps with four constraints; conclusions about broader constrained reasoning capabilities remain tentative.

## Confidence
- *Benchmark release*: High – Code, data splits, and query lists are publicly available, enabling straightforward replication of the evaluation framework.
- *Reported model scores*: Medium – Numbers depend on precise model checkpoints, API versions, and fidelity of the provided tables; variations are expected but can be systematically controlled.
- *Diagnostic conclusions* (visual bottleneck, multimodal hindrance, reasoning chain limitations): Low‑Medium – Inferred from aggregate patterns; alternative explanations (e.g., prompt design, tokenization) are not fully ruled out.
