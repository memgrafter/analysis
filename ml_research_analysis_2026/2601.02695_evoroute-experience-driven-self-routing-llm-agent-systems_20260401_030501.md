# EvoRoute: Experience-Driven Self-Routing LLM Agent Systems
## Quick Facts
- **arXiv ID:** 2601.02695
- **Source URL:** https://arxiv.org/abs/2601.02695
- **Reference count:** 10
- **Primary result:** EvoRoute maintains or improves task success rates on GAIA (63.19%) and BrowseComp+ while reducing monetary cost by up to 80% and execution latency by over 70%, demonstrating a practical resolution to the agent system trilemma.

## Executive Summary
EvoRoute tackles the LLM-powered multi-agent system trilemma—balancing performance, cost, and latency—by replacing static model assignments with dynamic, experience-driven routing. It constructs a self-evolving knowledge base of step-level execution records and, for each new sub-task, retrieves analogous past experiences, filters for Pareto-optimal LLM candidates, and selects a model via Thompson sampling. Integrated with frameworks like CK-Pro, it achieves comparable or better success rates on benchmarks like GAIA while drastically cutting cost and delay.

## Method Summary
EvoRoute maintains a knowledge base K containing records of past sub-task executions, including the sub-task description, tools used, the LLM model selected, and performance metrics (cost, delay, success). For an incoming sub-task, it first uses a lightweight PredictTools function to infer required tools. It then retrieves historically similar experiences from K based on sub-task embedding and tool congruence, yielding a candidate set of models. These candidates are filtered to retain only Pareto-optimal models (non-dominated in cost, delay, and performance). Thompson sampling is applied over this Pareto set to probabilistically select a model, balancing exploration and exploitation. After execution, the new experience is added to K, allowing the system to continuously improve. A cold-start phase with uniform random selection over 50 tasks initializes the knowledge base.

## Key Results
- On GAIA benchmark, EvoRoute achieved 63.19% success rate (comparable to state-of-the-art) while reducing monetary cost by up to 80% and latency by over 70%.
- Similar improvement in cost-efficiency and speed observed on BrowseComp+.
- Integration with CK-Pro and Smolagent frameworks confirmed consistent trilemma mitigation.

## Why This Works (Mechanism)
EvoRoute’s effectiveness stems from its data-driven routing and principled multi-objective optimization. By leveraging historical step-level records, it matches sub-tasks to models that have performed well on similar problems. The Pareto-optimal filter ensures only models that are non-dominated in cost, delay, and performance are considered, eliminating explicitly inferior choices. Thompson sampling naturally explores the Pareto frontier while exploiting known good models, adapting as more data accumulates. The tool congruence retrieval further refines candidate selection by aligning tool requirements, increasing the relevance of retrieved experiences. Together, these mechanisms allow the system to allocate the right model to each sub-task, achieving high task success while minimizing resource usage.

## Architecture Onboarding
**Component map:**  
New Subtask → PredictTools → Dual Retrieval (Experience & Tool) → Candidate Set (Lcand) → Pareto Filtration → Pareto Set (Lpareto) → Thompson Sampling → Selected Model → Execution → Record Experience → Update Knowledge Base (K)  
(Knowledge Base K is indexed for both embedding-based and tool-based retrieval.)

**Critical path:** The sequence from receiving a sub-task to producing its result, passing through prediction, retrieval, filtering, selection, execution, and logging. The knowledge base is continuously updated, influencing future routing decisions.

**Design tradeoffs:**  
- Cold-start random exploration adds overhead but populates K.
- Utility weights manually set; different preferences could require adjustment.
- Reliance on PredictTools accuracy; mispredictions degrade retrieval quality.
- Pareto filter may yield empty set if no non-dominated candidate exists, necessitating fallback.

**Failure signatures:**  
- Persistent high cost or latency despite K growth.
- Frequent empty Pareto sets.
- Low precision of PredictTools leading to irrelevant retrievals.
- Thompson sampling not converging (high variance in model selections).
- Degrading success rates over time, indicating distribution shift not captured.

**First three experiments:**  
1. Cold-start analysis: Run EvoRoute in random mode for 50 tasks, collect K, and examine diversity of models and coverage of tool combinations.
2. Retrieval relevance test: For a held-out set of sub-tasks with known optimal models, measure the fraction of retrieved experiences that include those models.
3. Pareto ablation: Compare EvoRoute against random model selection and a static cheapest-router baseline on a subset of GAIA tasks, measuring cost, latency, and success.

## Open Questions the Paper Calls Out
1. **Generalization across agent frameworks**  
   *Basis*: Evaluation only on CK-Pro and Smolagent.  
   *Why unresolved*: Different frameworks have distinct architectures (communication, hierarchies) that may interact uniquely with routing.  
   *Evidence needed*: Systematically integrate EvoRoute into other frameworks (e.g., OWL, AgentOrchestra, AIME) and test on the same benchmarks.

2. **Sensitivity of utility weights**  
   *Basis*: Utility function weights (wp=1.0, wc=0.1, wd=0.05) are manually configured.  
   *Why unresolved*: Fixed weights may not suit all tasks or user preferences; no sensitivity analysis provided.  
   *Evidence needed*: Ablation varying weights across a range or learning them adaptively; measure impact on Pareto frontier.

3. **Cold-start exploration efficiency**  
   *Basis*: Cold-start uses uniform random over 50 tasks from TaskCraft.  
   *Why unresolved*: Random exploration may yield redundant records, missing critical regions of the model-subtask space; sample efficiency unknown.  
   *Evidence needed*: Compare random initialization against targeted strategies (e.g., maximizing uncertainty in Thompson sampling) in terms of time-to-competence.

4. **Robustness to PredictTools inaccuracies**  
   *Basis*: PredictTools uses a heuristic (keyword dict + cheap LLM) to infer tools.  
   *Why unresolved*: Mispredictions could lead to irrelevant experiences being retrieved, harming candidate set quality; no evaluation of PredictTools accuracy.  
   *Evidence needed*: Measure PredictTools precision/recall on a held-out set; run ablations where tool congruence retrieval is replaced with perfect knowledge or random tools.

5. **Handling empty Pareto frontiers**  
   *Basis*: The paper assumes Pareto-optimal models exist among candidates.  
   *Why unresolved*: Some sub-tasks may yield a candidate set where every model is dominated; current method lacks a fallback.  
   *Evidence needed*: Analyze frequency of empty Pareto cases; define and evaluate fallback strategies (e.g., default to a high-performance model).

## Limitations
- Implementation specifics (Pareto filtration details, Thompson sampling priors) not fully described, impeding exact replication.
- Evaluation confined to GAIA and BrowseComp+ benchmarks; generalizability to diverse, real-world agentic tasks remains unproven.
- Absence of ablations isolating the contribution of experience retrieval and selection policy, and no evidence on robustness to noisy experiences or distribution shift.

## Confidence
- **Core framing (trilemma and experience-driven routing)**: High
- **Reported improvements on GAIA/BrowseComp+ (cost/latency reductions)**: Medium
- **Generalizability to other frameworks, domains, or pricing landscapes**: Low
- **Robustness to hyperparameter choices and data drift**: Low
- **Claim of “practical resolution” of the trilemma**: Low (lacks real-world deployment evidence)
