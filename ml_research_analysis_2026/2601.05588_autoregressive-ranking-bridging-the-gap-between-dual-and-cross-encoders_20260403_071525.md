# Autoregressive Ranking: Bridging the Gap Between Dual and Cross Encoders

## Quick Facts
- **arXiv ID:** 2601.05588  
- **Source URL:** https://arxiv.org/abs/2601.05588  
- **Reference count:** 24  
- **Primary result:** SToICaL, a rank‑aware loss for autoregressive ranking, nearly eliminates constraint violations and boosts top‑k ranking metrics on WordNet and ESCI.

## Executive Summary
The paper addresses two gaps in Autoregressive Ranking (ARR): the lack of a theoretical foundation for its expressiveness relative to Dual Encoders (DEs), and the inadequacy of standard next‑token loss for ranking. It introduces **SToICaL** (Score‑aware Token‑level Importance‑weighted Cross‑entropy for Autoregressive Ranking), a loss that uses item‑level reweighting and prefix‑tree marginalization to inject relevance information into token predictions. Theoretically, ARR can represent arbitrary rankings with a constant hidden dimension, while DEs require dimension growing linearly with corpus size. Experiments on WordNet and ESCI show that SToICaL drastically reduces constraint violation rates (from 27.66% to near 0% on WordNet) and significantly improves ranking metrics, especially for top‑k retrieval beyond the first result.

## Method Summary
SToICaL reformulates next‑token prediction as a rank‑sensitive objective. For each query, given a ranked list of relevant document IDs (docIDs), the method builds a prefix tree (trie) over those docIDs with rank ≥ r, where r denotes the target docID’s gold rank. Each leaf (docID) is assigned a weight λ(rank) (e.g., 1/rank^α). During training, for the selected target docID d_r, the token‑wise cross‑entropy loss compares the model’s next‑token logits (restricted to valid docID tokens) against a dynamic target distribution y(r,t). This distribution is computed by marginalizing the weights of all docIDs sharing the prefix up to token position t, thereby smoothing the one‑hot target and injecting relevance information from the entire ranked list. At inference, the model generates docIDs via constrained beam search; candidates are scored by averaging token log‑probabilities, and the top‑k are returned. The approach operates in‑context: the prompt contains the query and an unordered list of candidate docIDs, leveraging the LLM’s copying abilities.

## Key Results
- **Theoretical expressiveness:** ARR can realize any ranking with a constant hidden dimension, whereas DEs require dimension at least linear in the corpus size.
- **Constraint violation reduction:** On WordNet, SToICaL lowers the CVR from 27.66% (standard next‑token prediction) to near 0%.
- **Improved ranking metrics:** SToICaL yields substantial gains in nDCG and Recall@K for K>1, with e.g., R@5 improving by ~30% on WordNet and similar improvements on ESCI.

## Why This Works (Mechanism)

**Mechanism 1: ARR’s superior expressiveness**  
- **Claim:** Autoregressive Ranking models have strictly superior theoretical expressiveness compared to Dual Encoders for ranking tasks.  
- **Mechanism:** DEs compress query‑document interaction into a fixed‑dimension score; representing all orderings of *k* documents requires embedding dimension *n* ≥ *k*/(2 ln *k*). ARR models generate docIDs token‑by‑token via constrained decoding and can represent arbitrary probability distributions over docID sequences with constant *n*, provided `rank([E_docIDs | 1]) = |V_docIDs|`. This avoids the linear dimension growth requirement.

**Mechanism 2: SToICaL’s rank‑aware token‑level training**  
- **Claim:** The SToICaL loss improves ranking by making token‑level training aware of the full relevance order through prefix‑tree marginalization.  
- **Mechanism:** Instead of a one‑hot target, SToICaL constructs y(r,t) by marginalizing over all docIDs sharing a prefix at timestep *t*, weighted by relevance‑derived score μ(r)=1/r^β. This smooths the target distribution for each token, injecting information about the ranked list without increasing sequence length.

**Mechanism 3: In‑context ranking with shuffled docIDs**  
- **Claim:** In‑context ARR with shuffled docIDs in the prompt leverages the LLM’s in‑context learning and copying abilities to perform ranking via beam search over generated docIDs.  
- **Mechanism:** The prompt contains the query and an unordered list of candidate docIDs. During training, the model learns to generate the correct docID (with SToICaL loss) conditioned on this context. At inference, beam search over docID tokens produces a ranked list by ordering generations by conditional probability, exploiting the model’s ability to copy and reason over the provided docIDs.

## Architecture Onboarding
**Component map**  
1. Tokenizer & DocID Constructor: Converts documents to token sequences or synthetic numeric IDs (e.g., sparse codes).  
2. Causal LM (Mistral‑7B‑it): Base model that processes a prompt `¯𝑞` (query + shuffled candidate docIDs) and autoregressively generates next‑token logits.  
3. Constrained Decoder: During training, restricts next‑token probabilities to the set of valid docID tokens `V_docIDs`.  
4. Prefix Tree Builder: Preprocesses the ranked docID list for a query into a trie, assigning node scores based on relevance (e.g., 1/rank^β).  
5. SToICaL Loss Calculator: Computes token‑level target distribution `y(r,t)` via trie marginalization and evaluates weighted cross‑entropy loss.  
6. Inference Beam Search: Generates ranked docID lists by beam search over token sequences, scoring each by average token log‑probability.

**Critical path**  
1. *Data preprocessing:* For each query, construct the ranked list of docIDs and tokenize them; build a global trie.  
2. *Training loop:* For each training example (query, docID with rank r), compute `y(r,t)` using the trie for ranks ≥ r; forward through LM with constrained decoding; compute loss = λ(r) × CE(y, p_θ); backpropagate.  
3. *Validation:* Greedy/beam generate docIDs for held‑out queries; compute constraint violation rate (CVR), nDCG, and R@k.  
4. *Baselines:* Implement DE (matrix product) and CE (concatenation + MLP) with comparable loss reweighting for fair comparison.

**Design tradeoffs**  
- *Item‑level (λ(r)) vs. Token‑level (trie) loss:* Item‑level reweighting is simpler and more effective per Table 1 but requires training on each docID individually; token‑level marginalization is more efficient (single pass per query) but slightly less effective.  
- *DocID design:* Short, prefix‑sharing IDs (e.g., numeric codes) work best; overly long or random tokens reduce trie benefits.  
- *Context length:* In‑context ranking lists all candidates in the prompt, limiting candidate set size (~hundreds). For larger corpora, a hybrid retrieve‑then‑rerank approach is needed.

**Failure signatures**  
- High CVR (>20%): Model scores an irrelevant negative above relevant docs; indicates rank deficiency in embeddings or inadequate rank‑aware loss.  
- Good R@1 but poor R@K>1: Model focuses only on top rank; suggests λ(r) over‑downweights lower ranks or trie marginalization is ineffective.  
- Generated docIDs not in candidate set: Constrained decoding failed; verify `V_docIDs` and trie cover all candidates.  
- Training instability: Loss magnitude or gradients become erratic; adjust hyperparameters α/β or loss scaling.

**First 3 experiments**  
1. Trie construction sanity check: Manually build a trie for a small batch; verify that valid next‑token sets at each prefix match the continuations of docIDs sharing that prefix.  
2. Loss equivalence test: Set β→∞ (trie → one‑hot) and α→∞ (λ(r)=𝕀(r=1)). Confirm SToICaL reduces to standard next‑token prediction and training metrics match a baseline NTP run.  
3. In‑context copy verification: With a frozen LM, prompt it with a query and shuffled 2‑3 docIDs (one clearly relevant). Greedy decode and check if the correct relevant docID is generated; if not, the model’s in‑context copying may be insufficient.

## Limitations
- The theoretical advantage relies on the full‑rank condition `rank([E_docIDs | 1]) = |V_docIDs|`, which may be violated when using frozen pretrained embeddings without adaptation.  
- Experimental validation is limited to narrow datasets (WordNet taxonomy, ESCI product codes), leaving performance on standard large‑scale ad‑hoc retrieval benchmarks with natural text unknown.  
- The in‑context ranking approach assumes all candidates fit in the context window and have short, prefix‑sharing docIDs, limiting scalability to large corpora.

## Confidence
- Theoretical expressiveness: High  
- SToICaL loss effectiveness: Medium  
- In‑context ARR with shuffled docIDs: Medium  

## Next Checks
1. Rank condition stress test: Freeze the LLM’s token embeddings and apply a random low‑rank projection to the docID embedding matrix. Train ARR and observe ranking performance degradation as rank decreases.  
2. Cross‑dataset generalization: Apply SToICaL to a standard passage ranking benchmark (e.g., MS MARCO) using natural document titles as docIDs (without special sparse coding). Compare NDCG and CVR against a dual encoder baseline.  
3. Prefix‑sharing ablation: On WordNet, replace synset names with random token strings of similar length statistics (destroying meaningful prefix relationships). Compare SToICaL with trie marginalization against one‑hot loss; a significant drop would confirm trie’s dependence on shared prefixes.
