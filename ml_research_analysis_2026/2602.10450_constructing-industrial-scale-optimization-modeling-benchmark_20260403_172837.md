# Constructing Industrial-Scale Optimization Modeling Benchmark

## Quick Facts

- **arXiv ID:** 2602.10450  
- **Source URL:** https://arxiv.org/abs/2602.10450  
- **Reference count:** 40  
- **Primary result:** Introduced MIPLIB-NL, an industrial-scale NL-to-Opt benchmark; state-of-the-art systems’ Pass@1 accuracy plummets from ~80% on toy benchmarks to ~20% on MIPLIB-NL.

## Executive Summary

Existing natural-language-to-optimization (NL-to-Opt) benchmarks are玩具-sized and synthetic, failing to capture the scale (thousands to millions of variables/constraints) and structural complexity (indexed variable/constraint families) of real industrial mixed-integer linear programs (MILPs). This paper presents MIPLIB-NL, a new benchmark derived from MIPLIB 2017 via a structure-aware reverse generation pipeline. The pipeline recovers loop-based scaffolds from flattened MPS files, produces compact natural-language descriptions with strict model–data separation, and validates semantic correctness through expert review and independent LLM reconstruction. Evaluation shows that leading NL-to-Opt systems suffer drastic performance drops on MIPLIB-NL, exposing modeling challenges previously hidden by small-scale benchmarks.

## Method Summary

The construction of MIPLIB-NL follows a three-stage process. First, **structural abstraction**: experts examine MIPLIB 2017 MPS files to extract loop-based scaffolds—identifying indexed variable groups and repeated constraint families from variable naming patterns, constraint blocks, and sparsity. Second, **Opt-to-NL generation**: expert-designed blueprints map these scaffolds to natural language, producing `model.md` and structured data files (CSVs) under a strict model–data separation scheme. Third, **semantic validation**: multiple LLMs attempt to reconstruct solver-executable models from the NL and data; failures trigger iterative expert–LLM debugging until at least one LLM yields a solution matching the original optimum. The final benchmark comprises 223 self-contained instance directories with unified schemas.

## Key Results

- MIPLIB-NL contains 223 industrial-scale MILP instances ranging from 0.5k to over 1 million variables/constraints, achieving significant compression ratios vs. flattened MPS.
- State-of-the-art NL-to-Opt systems (fine-tuned and base LLMs) see Pass@1 accuracy drop from ~80% on existing toy benchmarks to ~20% on MIPLIB-NL.
- Failure analysis: modeling errors (48.3%, e.g., missing constraint families, index mishandling) and execution failures (45.0%, e.g., code bugs) dominate; these errors scale with problem size and are largely invisible on small instances.

## Why This Works (Mechanism)

### Mechanism 1
- **Claim:** Recovering loop-based structural scaffolds from flat MPS formulations allows MIPLIB-NL to preserve the scale and compositional complexity of industrial MILPs.
- **Mechanism:** Expert analysts examine variable naming patterns, constraint blocks, and sparsity structures to identify indexed variable groups and repeated constraint families. These are encoded as loop templates (e.g., "for each facility and time period") rather than enumerating every algebraic row.
- **Core assumption:** Industrial MILPs are fundamentally generated by concise, reusable modeling logics (loops over indices) rather than by independent constraints.
- **Evidence anchors:**
  - [abstract] "recovers compact, reusable model structure from flat MPS formulations"
  - [section 3.2] "Our approach centers on recovering a loop-based structural scaffold"
  - [corpus] Not required; paper presents self-contained evidence.
- **Break condition:** If original MPS files use opaque variable names or aggressive presolving that destroys loop structure (Appendix I), recovery becomes infeasible and the benchmark loses its structural fidelity.

### Mechanism 2
- **Claim:** Strict model–data separation enables natural‑language descriptions that remain compact even as problem scale grows to millions of variables/constraints.
- **Mechanism:** The NL description references parameter tables (CSV files) instead of embedding numerical values. The description specifies constraint families (e.g., "for each product `p` and time period `t`") while data files define the actual index sets and coefficients.
- **Core assumption:** The semantic content of an industrial problem is captured by the relationship between index sets and constraint templates, not by the raw numbers.
- **Evidence anchors:**
  - [abstract] "significant compression ratios between flattened MPS and NL+data"
  - [section B.2] "strict model–data separation, enabling scalable construction"
  - [figure 9] "MIPLIB-NL maintains moderate description length"
- **Break condition:** If data files become too large or structurally inseparable (e.g., fully dense coupling), the description length would again balloon, undermining the scalability benefit.

### Mechanism 3
- **Claim:** Iterative semantic validation via independent NL→Opt reconstruction and expert review ensures the reverse‑generated instances are semantically sufficient and faithful to the original MPS models.
- **Mechanism:** For each candidate instance, multiple LLMs attempt to reconstruct a solver‑executable model from the NL and data. If none succeed, experts interactively debug and refine the NL/data until at least one LLM produces a solution matching the original optimum.
- **Core assumption:** If a strong LLM can correctly reconstruct and solve the problem from the NL specification, the NL is likely semantically adequate; conversely, systematic reconstruction failures reveal specification gaps.
- **Evidence anchors:**
  - [section 3.4] "Primary validation: independent NL‑to‑Opt reconstruction"
  - [section 3.4] "Secondary validation: expert‑driven human–LLM interaction"
  - [appendix E] detailed case studies of interactive debugging.
- **Break condition:** If no LLM (even with expert help) can reconstruct a correct model despite the NL being internally consistent, the instance may rely on implicit domain knowledge that cannot be captured textually, leading to exclusion from the benchmark.

## Foundational Learning

### Indexed Constraint Families
- **Why needed here:** Industrial MILPs derive their scale and complexity from loops that generate thousands/millions of constraints from a few templates. Without understanding how constraints are replicated over index sets (e.g., "for each product `p`, for each time period `t`"), one cannot grasp the structural challenge that MIPLIB-NL exposes.
- **Quick check:** Given a constraint template `balance[p,t] = sum(ship[p,t,w] for w in warehouses) - demand[p,t] = 0`, what loop structure and index sets would generate this family in a typical production planning model?

### Model–Data Separation
- **Why needed here:** The benchmark's compression and scalability hinge on keeping the abstract model (variables, constraints, indices) separate from concrete numbers (coefficients, bounds). This separates structural complexity from data volume.
- **Quick check:** Why does embedding all numerical values directly into the natural language description cause the prompt length to explode for large‑scale instances?

### Semantic Validation via Reconstruction
- **Why needed here:** The reverse generation process could accidentally introduce omissions or ambiguities. Reconstruction acts as a check: if an LLM can correctly produce a solver‑ready model from the NL and data, the specification is likely complete.
- **Quick check:** What does it mean if several LLMs generate code that runs but yields an objective value far from the known optimum? How should the instance creator respond?

## Architecture Onboarding

### Component map
Input (MIPLIB 2017 .mps files) -> Stage 1: Structural abstraction -> Stage 2: Opt-to-NL generation -> Stage 3: Semantic validation -> Output (self-contained instance directories with NL, data, math reference, solver code, verification logs)

### Critical path
1. Select an MIPLIB 2017 instance with interpretable variable names and moderate size.
2. Recover loop scaffold → design NL blueprint → generate raw NL and data files.
3. Run batched LLM reconstruction (pass@8).
4. If failure rate high, engage expert review to pinpoint missing/implicit constraints.
5. Revise NL/data accordingly and re‑test.
6. Upon success by at least one LLM, finalize instance and add to benchmark.

### Design tradeoffs
- **Coverage vs. effort:** Manual structure recovery limits scale (223 instances); future automation may expand coverage but risks losing accuracy for highly presolved MPS files.
- **Compression vs. expressiveness:** Model–data separation achieves huge compression; however, some structural nuances (e.g., irregular subset constraints) may require lengthy NL explanations if the index sets are complex.
- **Validation rigor vs. cost:** Multi‑LLM reconstruction and expert interaction are expensive; cheaper heuristics might miss subtle semantic gaps.

### Failure signatures
- **Structure recovery failure:** Variable names are generic (e.g., `x1, x2…`) or constraint matrix is heavily presolved, making loop scaffolding unintelligible.
- **Model‑data misalignment:** NL refers to a parameter not present in the data files or mismatches index set names.
- **Validation deadlock:** All LLMs consistently fail reconstruction even after expert polishing, suggesting the instance relies on unstated domain assumptions.

### First 3 experiments
1. **Overall performance drop:** Table 1 shows that state‑of‑the‑art NL‑to‑Opt systems that achieve ~80% Pass@1 on toy benchmarks fall to ~20% on MIPLIB‑NL, demonstrating that existing evaluations overestimate capability.
2. **Scale‑dependent trend:** Figure 6 reports accuracy across model size buckets; performance generally declines as instance scale grows, confirming that large‑scale structure poses additional challenges.
3. **Error mode analysis:** Figure 7 breaks down failures into modeling errors (48.3%, e.g., missing constraint families, index mishandling) and execution errors (45.0%, e.g., API misuse, bugs), highlighting structural difficulties that become dominant at industrial scale.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question:** How can the structure-aware reverse generation pipeline be automated to scale MIPLIB-NL to cover a larger fraction of MIPLIB 2017 instances, particularly those with ambiguous variable names or extreme scale?
- **Basis in paper:** [explicit] The paper states that current coverage is limited to 223 instances due to manual effort, and future work should automate verification and reverse-generation (Appendix I).
- **Why unresolved:** Manual expert analysis is time-consuming and not scalable; automation requires solving challenges like interpreting presolved MPS files and recovering semantics from generic variable names.
- **What evidence would resolve it:** Development of an automated system that can replicate expert-level structure recovery on a diverse subset of MIPLIB instances, validated by human experts on a held-out set.

### Open Question 2
- **Question:** Why do state-of-the-art LLMs exhibit such high rates of modeling errors (e.g., missing/incorrect constraint families, index mishandling) on industrial-scale problems, and what training or architectural interventions can mitigate these?
- **Basis in paper:** [inferred] The paper's error analysis (Section 4.4) shows 48.3% of failures are modeling mistakes, especially in handling indexed variable groups and constraint families. The authors note these are invisible in toy benchmarks.
- **Why unresolved:** The paper does not investigate the root causes (e.g., lack of structural reasoning in pretraining, insufficient exposure to loop-based patterns). Thus, targeted interventions are unknown.
- **What evidence would resolve it:** Ablation studies isolating loop-based structure in training data; designing probing tasks to diagnose LLMs' understanding of index handling and constraint family instantiation; evaluating if specialized fine-tuning on scaffolded data improves performance.

### Open Question 3
- **Question:** Can the proposed loop-based structural scaffold taxonomy be operationalized as a standard evaluation metric for NL-to-Opt systems, and does it correlate with real-world modeling difficulty better than existing semantic constraint type taxonomies?
- **Basis in paper:** [inferred] The authors introduce a taxonomy of loop-based scaffolds (Table 5) and argue that semantic constraint types alone underestimate complexity (Appendix D). However, they use it only for analysis, not as a metric.
- **Why unresolved:** It is unclear whether this taxonomy can be reliably annotated across diverse systems or if it predicts difficulty beyond problem size. Current benchmarks lack such structural annotations.
- **What evidence would resolve it:** Annotating multiple benchmarks with scaffold types and correlating with model performance; designing controlled studies where scaffold complexity is varied while holding semantic types constant.

### Open Question 4
- **Question:** Does the enforced model-data separation format in MIPLIB-NL introduce novel failure modes for LLMs (e.g., data-binding errors, incorrect file path handling) that are not present in benchmarks where data is embedded in the NL description?
- **Basis in paper:** [inferred] MIPLIB-NL uses separate data files to keep NL compact at scale, but error analysis (Section 4.4) does not distinguish whether errors stem from data binding vs. structural modeling. Existing benchmarks embed data, so comparison is confounded.
- **Why unresolved:** The paper's evaluation aggregates all errors; we do not know if data separation adds overhead. LLMs might struggle with external data integration, a key skill for industrial use.
- **What evidence would resolve it:** Error analysis stratified by whether the error is in data loading/processing versus model logic; comparing performance on equivalent problems with embedded vs. separate data; measuring sensitivity to data file format and path complexity.

## Limitations

- Manual scaffold extraction restricts benchmark size (223 instances) and may not generalize to heavily presolved MPS files.
- Exact extraction heuristics and LLM validation parameters (temperature, sampling) are underspecified, raising reproducibility concerns.
- Instances where all LLMs fail reconstruction are excluded, potentially biasing the benchmark toward “solvable” cases and omitting the hardest structural challenges.
- Model–data separation could become inefficient for problems with highly irregular index sets; the trade-off between compression and descriptive clarity is not fully mapped.
- Evaluation used older LLMs; it is unknown whether newer models will show the same performance degradation.

## Confidence

- **Performance drop claim:** High (empirical across diverse instances).
- **Loop-based scaffold recovery preserves structural complexity:** Medium (expert-driven, limited automation; break condition for opaque MPS).
- **Model–data separation yields compact, scalable NL formulations:** Medium (demonstrated compression, but expressiveness for complex index sets remains uncertain).
- **Semantic validation via reconstruction ensures faithfulness:** Medium (depends on LLM capability and costly expert iteration; possible hidden domain knowledge).

## Next Checks

1. **Automate scaffold extraction:** Build a tool that infers indexed families from variable naming and sparsity patterns; compare its output to the manual scaffolds to measure coverage and fidelity.
2. **Re‑evaluate with state‑of‑the‑art LLMs:** Test current NL-to-Opt systems (e.g., GPT‑5, Claude 4) on MIPLIB‑NL to verify that the performance drop persists and the benchmark remains challenging.
3. **Correlate instance features with failure modes:** Analyze the relationship between structural metrics (number of indexed families, constraint density, size) and error types (modeling vs. execution) to identify which aspects of industrial scale are most detrimental to LLM performance.
