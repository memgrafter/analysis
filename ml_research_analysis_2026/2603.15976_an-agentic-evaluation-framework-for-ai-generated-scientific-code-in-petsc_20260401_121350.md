# An Agentic Evaluation Framework for AI-Generated Scientific Code in PETSc

## Quick Facts
- **arXiv ID:** 2603.15976
- **Source URL:** https://arxiv.org/abs/2603.15976
- **Reference count:** 33
- **Primary result:** Introduces petscagent-bench, an agentic framework that reveals modest composite scores (46.4–39.9) and critical gaps in library-specific conventions (52–59) and correctness (46–72), with 67% compilation pass rates and universal failure on Navier-Stokes.

## Executive Summary
Traditional pass/fail tests are insufficient for evaluating AI-generated HPC library code as they miss critical dimensions like solver selection and API conventions. This paper presents petscagent-bench, an agentic evaluation framework where a tool-augmented evaluator agent (Green) assesses code from a separate model agent (Purple) via standardized protocols. Empirical analysis of frontier models shows modest performance (46.4–39.9 composite scores) and highlights persistent weaknesses: models produce readable code but fail on PETSc-specific conventions and correctness, with only 67% of generated code compiling and all models failing complex PDE problems like Navier-Stokes.

## Method Summary
The framework employs a decoupled agentic architecture: a Green evaluator agent communicates with a Purple model-under-test agent using the A2A protocol, receiving generated code artifacts. The Green agent then uses MCP tools to compile and run the code in a sandboxed PETSc/MPI environment, executing a 14-evaluator pipeline. Evaluation proceeds in three stages: hard gates (compilation, execution, memory safety, API usage) filter out non-viable code early; passing code undergoes numerical accuracy and performance metrics; finally, LLM-based quality assessments evaluate dimensions like readability, style, and library-specific conventions. Scores are confidence-weighted and aggregated into category and composite scores.

## Key Results
- Frontier models achieve modest composite scores between 46.4 (GPT-4o) and 39.9 (Gemini 1.5 Pro).
- Models consistently score lower on library-specific conventions (52–59) and correctness (46–72) compared to code readability and appropriateness.
- Compilation gate pass rate is 67%, with all models failing the 2D Navier-Stokes problem.

## Why This Works (Mechanism)
### Mechanism 1: Agentic Decoupling
**Claim:** Decoupling evaluation via an agentic architecture enables multi-dimensional, black-box assessment of library-based HPC code.
**Mechanism:** The Green agent orchestrates evaluation by sending problem specifications to the Purple agent via A2A, receiving generated code, then using MCP tools to compile/run in a sandboxed PETSc environment before running a 14-evaluator pipeline. This separation allows any A2A-compliant coding agent to be evaluated without source-code access.
**Core assumption:** Standardized protocols (A2A, MCP) abstract implementation details.
**Evidence anchors:** [abstract], [section 3.2]; weak neighbor corpus (105026, 25111, 266929).
**Break condition:** Malformed A2A messages or MCP tool unavailability halts the pipeline.

### Mechanism 2: Staged Evaluation Pipeline
**Claim:** A staged pipeline with gates efficiently allocates resources while capturing nuanced failures.
**Mechanism:** Hard gates filter early failures (compilation, execution, memory safety, API usage). Only passing code proceeds to metrics (accuracy, performance) then costly LLM-based quality assessments across five categories. Scores are confidence-weighted and aggregated.
**Core assumption:** Most failures occur at compilation (section 6.4), so early gates prevent wasted resources; library-specific weaknesses require LLM judgment.
**Evidence anchors:** [section 4] pipeline details; [section 6.4] compilation dominates failures; [section 6.5] low library-specific scores despite high code/appropriateness.
**Break condition:** Gate pass rate near 0% or 100% renders staging ineffective.

### Mechanism 3: Tool-Augmented Execution
**Claim:** Tool augmentation permits dynamic compilation, execution, and measurement in a sandboxed environment, which static analysis cannot provide.
**Mechanism:** The Green agent invokes MCP’s compile/run tools to build code against a custom PETSc installation, execute with MPI, and capture outputs, errors, and metrics (e.g., Valgrind for memory safety).
**Core assumption:** Accurate assessment requires real build/run to verify solver behavior, API compliance, resource management.
**Evidence anchors:** [section 3.3] MCP tools; [section 4.1] gates rely on compilation/execution; [section 6.6] compilation errors dominate, runtime crashes detectable only via execution.
**Break condition:** Sandbox divergence from target deployment (PETSc version, MPI config) compromises validity.

## Foundational Learning
- **Concept: HPC library conventions vs. from-scratch implementation.**
  Why needed: Benchmark tests *library usage* (solver selection, API patterns, error handling), not algorithmic novelty. Understanding PETSc conventions (e.g., `PetscCall()` macro, `DM` abstractions) explains poor library-specific scores.
  Quick check: What PETSc-specific pattern replaces `CHKERRQ()`, and why might models still use the old form?

- **Concept: Staged evaluation pipelines with gating.**
  Why needed: Pipeline efficiency hinges on early failure detection. Knowing gate filtering explains why compilation is the main bottleneck and why later stages (LLM quality) run only for passing code.
  Quick check: If code compiles but crashes due to missing Jacobian diagonals, which gate(s) catch this? Which stage assesses numerical accuracy?

- **Concept: Agent protocols for black-box evaluation (A2A, MCP).**
  Why needed: Architecture’s plug-and-play nature depends on these protocols. A2A decouples evaluator/model; MCP decouples evaluator/tools. Without this separation, one might conflate model’s code-generation with evaluator’s tooling.
  Quick check: How does the Green agent access PETSc’s compilation tools? What changes if the Purple agent is on a different network?

## Architecture Onboarding
- **Component map:**
  Green Agent -> A2A -> Purple Agent
  Green Agent -> MCP tools -> Sandboxed PETSc/MPI/Valgrind
  Benchmark Suite -> Green Agent
  Leaderboard <- Green Agent

- **Critical path:**
  1. Green reads problem spec → A2A task to Purple.
  2. Purple returns artifacts (code files).
  3. Green calls MCP compile → success? else gate failure.
  4. Green calls MCP run → success? else gate failure.
  5. If gates pass, run metrics then quality evaluators.
  6. Aggregate category scores → composite.
  7. Repeat for all problems/runs.

- **Design tradeoffs:**
  - Black-box evaluation vs. diagnostic depth: A2A/MCP enable plug-and-play but limit internal inspection of Purple agent’s reasoning.
  - Modular evaluators vs. orchestration overhead: 14 evaluators allow fine-grained scoring but increase pipeline complexity and LLM call cost.
  - Deterministic gates vs. subjective quality: Early gates are cheap/objective; later LLM scores introduce stochasticity despite temperature 0.

- **Failure signatures:**
  - Gate failures: Compilation (syntax/API errors), API Usage (missing `PetscInitialize`).
  - Metric failures: Low numerical accuracy (loose solver tolerances on stiff problems).
  - Quality failures: Low library-specific (missing `PetscCall()`), low appropriateness (suboptimal solver).
  - Pipeline breaks: MCP tool timeout, malformed A2A message.

- **First 3 experiments:**
  1. Smoke test: Run `Vec/MPI Scatter` with trivial Purple agent (hardcoded correct code) to verify end-to-end pipeline.
  2. Gate failure injection: Submit code omitting `PetscInitialize()` to trigger API Usage gate failure; confirm evaluation stops, composite=0.
  3. Category isolation: Compare scores on Robertson ODE (stiff) vs. Rosenbrock Opt (easy) to see correctness drop; check library-specific consistency across problems.

## Open Questions the Paper Calls Out
### Open Question 1
Question: How can training data staleness in PETSc error-handling conventions (e.g., use of deprecated `CHKERRQ()` instead of `PetscCall()`) be effectively mitigated?
Basis: Discussion identifies staleness as key bottleneck; suggests retrieval augmentation over fine-tuning.
Why unresolved: No mitigation strategy evaluated.
What evidence: Controlled experiments comparing agent performance with/without retrieval augmentation or fine-tuning on fresh PETSc examples, measuring gains in library-specific error-handling score.

### Open Question 2
Question: What fundamental knowledge gaps cause universal failure on complex PDE problems like 2D Navier–Stokes, and how do they differ across models?
Basis: All models fail: Gemini via compilation errors (`DMStagCreate2d` args), Claude/GPT via runtime crashes (missing Jacobian diagonals, divergent solves). Authors declare it beyond current capabilities without dissecting root causes.
Why unresolved: Failure symptoms reported but not categorized (API misuse, FEM reasoning, solver config errors).
What evidence: Systematic failure analysis by experts or automated fault localization to classify error types.

### Open Question 3
Question: Can multi-turn compile–fix loops substantially improve compilation gate pass rates and overall scores?
Basis: Authors note compilation errors dominate and propose multi-turn agents with compile–fix loops could improve pass rates using compiler diagnostics.
Why unresolved: Evaluation uses single-shot generation; no iterative repair implemented/tested.
What evidence: Deploy agent that iterates (compile → parse errors → regenerate/patch → recompile); compare gate pass rates and composite scores against single-shot baseline.

## Limitations
- Protocol opacity: Exact A2A message schemas and MCP interfaces not publicly documented, hindering replication.
- LLM evaluator black box: Internal prompts, rubrics, confidence-calibration for LLM-based evaluators undisclosed, impairing score interpretation.
- Environment specificity: Evaluation depends on custom PETSc/MPI/Valgrind sandbox; results may not generalize to other HPC environments or PETSc versions.

## Confidence
- Mechanism 1 (Agentic Decoupling): Medium. Described clearly but evidence self-contained; no external validation of protocol robustness.
- Mechanism 2 (Staged Pipeline): High. Strong internal evidence: gate statistics (6.4) and category score deltas (6.5) demonstrate filtering and nuanced capture.
- Mechanism 3 (Tool-Augmented Execution): Medium. Gates well-specified but validity hinges on MCP’s faithful emulation of target deployment—undiscussed assumption.
