# Building Effective AI Coding Agents for the Terminal: Scaffolding, Harness, Context Engineering, and Lessons Learned

## Quick Facts

- **arXiv ID**: 2603.05344
- **Source URL**: https://arxiv.org/abs/2603.05344
- **Reference count**: 40
- **Primary result**: OPENDEV reduces peak context consumption by 54%, extends session length to 30–40 turns, and cuts input cost ~88% via prompt caching, using a compound architecture with adaptive compaction, dual-agent separation, and specialized model routing.

## Executive Summary

OPENDEV addresses the challenge of enabling AI coding agents to perform complex, multi-step development tasks directly in the terminal without running into context window limits, safety risks, or excessive costs. Its core innovation lies in a compound AI architecture that routes different reasoning phases to specialized models, a dual-agent design that structurally prevents destructive actions during planning, and an adaptive context compaction pipeline that proactively manages token pressure. The system demonstrates substantial gains: peak context consumption is reduced by 54%, typical session lengths increase from 15–20 to 30–40 turns without emergency compaction, and input costs drop by approximately 88% when using Anthropic’s prompt caching. Safety is enforced through a five-layer defense-in-depth architecture, with schema-level tool gating making violations structurally impossible rather than relying on runtime checks alone.

## Method Summary

OPENDEV is built as a compound AI system that composes multiple specialized language models and components. It features five model roles—action, thinking, critique, vision, and compact—each independently configurable, allowing optimal trade-offs between cost, latency, and capability. The agent operates through an extended ReAct loop that interleaves reasoning and tool use, with an optional thinking phase for internal deliberation. The architecture employs a dual-agent separation: a Planner subagent (read‑only tools) explores the codebase and produces a structured plan, which the user must approve before the MainAgent (full tool access) executes. Safety is enforced at the schema level, preventing write tools from being presented to the Planner, thus making destructive operations impossible during planning. To manage finite context windows, Adaptive Context Compaction (ACC) implements a five‑stage progressive pipeline (warning, observation masking, fast pruning, aggressive masking, full summarization) that activates at increasing token‑pressure thresholds, reducing peak usage by ~54% and extending session length. Additional mechanisms include lazy tool discovery via Model Context Protocol (MCP), event‑driven system reminders to combat instruction fade‑out, and an automated memory pipeline for cross‑session knowledge. The system is implemented in Rust, supports multiple frontends (CLI/TUI/Web), and uses tool schemas for robust safety and composability.

## Key Results

- **Context efficiency**: 54% reduction in peak context consumption; session length extended from 15–20 to 30–40 turns without emergency compaction.
- **Cost savings**: Approximately 88% reduction in input cost via prompt caching (Anthropic provider).
- **Safety guarantees**: Five-layer defense-in-depth architecture with schema-level tool gating makes destructive violations structurally impossible.

## Why This Works (Mechanism)

### Mechanism 1: Adaptive Context Compaction (ACC)
- **Claim**: ACC reduces peak context consumption by ~54% and extends typical session length from 15–20 to 30–40 turns by managing token pressure proactively.
- **Mechanism**: At the start of each ReAct iteration, token usage is evaluated against the context window. Five graduated stages activate at increasing pressure thresholds (70%, 80%, 85%, 90%, 99%): warning, observation masking (replace old tool outputs with reference pointers), fast pruning (replace with `[pruned]` markers), aggressive masking, and full LLM-based summarization. This progressive approach avoids emergency compaction and preserves recent outputs.
- **Core assumption**: Tool outputs (file contents, command results) dominate context usage and become irrelevant after a few turns; they can be aggressively compressed without losing decision‑relevant information.
- **Evidence anchors**: [abstract]; [Section 2.3.6] details the five‑stage pipeline and the 54% reduction; [corpus] (weak or missing).
- **Break condition**: If compressed references are not re‑accessed when needed, the agent may lose critical details; over‑compression could also remove subtle but important context.

### Mechanism 2: Dual‑Agent Architecture (Planning vs Execution)
- **Claim**: Separating planning (read‑only) from execution (full tool access) prevents destructive operations during planning and reduces state‑management complexity.
- **Mechanism**: A Planner subagent is spawned with a schema that excludes all write tools. It explores the codebase using read‑only tools, writes a structured plan file, and returns its path. The main agent then presents the plan to the user for approval. Only after approval does the main agent (in Normal Mode) execute the plan with full tool access.
- **Core assumption**: The agent cannot invoke tools it does not see in its schema; removing write tools from the planner’s schema makes destructive actions structurally impossible during planning.
- **Evidence anchors**: [abstract]; [Section 2.2] describes the Planner and `present_plan` workflow; [Section 2.1] notes schema‑level restrictions as a safety layer; [corpus] (weak or missing).
- **Break condition**: If planning requires code execution to validate hypotheses (e.g., running tests on a proposed design), the read‑only constraint may force the planner to delegate back to the main agent, blurring the separation and re‑introducing risk.

### Mechanism 3: Workload‑Specialized Model Routing
- **Claim**: Routing different cognitive phases to specialized models optimizes cost, latency, and capability trade‑offs, and makes the system model‑agnostic by construction.
- **Mechanism**: Five model roles (action, thinking, critique, vision, compact) are defined. Each role selects a model independently via user configuration, with fallback chains (e.g., thinking falls back to action). Model clients are lazily initialized. This per‑workflow binding allows switching providers or models without code changes.
- **Core assumption**: Distinct reasoning tasks have different optimal model characteristics (e.g., thinking benefits from extended chain‑of‑thought without tool pressure; summarization from fast, cheap models).
- **Evidence anchors**: [abstract]; [Section 2.2.5] lists the five roles and routing logic; [Section 2] frames the system as a compound AI system; [corpus] (weak or missing).
- **Break condition**: Misrouting (e.g., using a low‑capability compact model for complex reasoning) degrades performance; fallback chains may introduce latency if primary models are unavailable.

## Architecture Onboarding

**Component Map**:  
Entry & UI (CLI/TUI/Web frontends, slash-command dispatch) -> Agent (Main agent, subagents, ReAct executor, safety enforcer) -> Tool & Context (Tool registry, prompt composer, compaction, memory) -> Persistence (Session storage, undo logs, configuration cache)

**Critical Path**:  
User query (non‑slash) → REPL → `MainAgent.run_sync()` → ReAct iteration loop: context assembly → optional thinking → action LLM call → tool dispatch (with safety checks) → outcome → repeat until completion → session persistence.

**Design Tradeoffs**:
- Eager vs lazy prompt building: Eager construction avoids first‑call latency and tool‑discovery race conditions.
- Schema gating vs runtime checks: Gating is more robust but requires careful schema assembly.
- Graduated compaction vs single emergency compaction: Gradual stages preserve more context and reduce LLM cost, but add complexity.

**Failure Signatures**:
- Context overflow: Excessive tool outputs without compaction; session truncation.
- Safety violation: Attempted write in Plan Mode indicates schema gating failure.
- Doom-loop: Same tool called ≥3 times with identical arguments; system warns or pauses.
- Edit failure: `old_content not found` indicates stale read or fuzzy‑match pass failure.

**First 3 Experiments**:
1. Run a simple query (`opendev -p "read README.md"`) and trace the ReAct loop via debug logs to see tool calls and context assembly.
2. Switch to Plan Mode (`/mode plan`) and ask the agent to explore the codebase; verify that no write tools appear in the planner’s schema.
3. Trigger context compaction by running a long session (e.g., multiple `read_file` on large files) and observe the compaction stages in the logs; check that offloaded outputs appear in the scratch directory.

## Open Questions the Paper Calls Out

1. **Multi-model cost/latency/capability balance**: The paper asks how to optimally allocate different models to various cognitive tasks in a compound system. OPENDEV introduces per‑workflow routing but does not evaluate the optimal strategies. Resolution requires systematic experiments comparing routing schemes (single‑model, task‑specific, ensembles) across diverse coding tasks, measuring cost, latency, and success rates.
2. **Safety mechanisms**: What safety mechanisms prevent destructive operations without hampering developer productivity? The defense-in-depth architecture is described but lacks empirical validation against misuse. Resolving this would require rigorous safety audits (red‑team testing) measuring violation rates under various trust settings, combined with user studies to assess productivity trade‑offs.
3. **Sustaining long‑running conversations**: How can systems sustain long‑running conversations within finite context limits? OPENDEV introduces adaptive compaction and dual‑memory, but the most effective techniques for long‑horizon coding tasks remain unknown. Resolution requires long‑horizon benchmarking (e.g., Terminal‑Bench, LongCLI‑Bench) comparing compaction stages, memory indexing, and reminder timing on session length and task completion quality.

## Limitations

- **Compaction implementation details**: Exact threshold mappings (e.g., “preserve last 6 message pairs”) and full LLM summarization artifact format are not documented, limiting faithful replication.
- **Prompt composition**: Only partial templates are provided; complete conditional sections and variable substitution rules are missing.
- **Quantitative claims lack independent validation**: Reported 54% context reduction and 88% cost saving rely on internal experiments; no external benchmark or artifact is available.
