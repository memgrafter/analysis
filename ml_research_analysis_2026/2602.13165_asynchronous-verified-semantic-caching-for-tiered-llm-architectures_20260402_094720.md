# Asynchronous Verified Semantic Caching for Tiered LLM Architectures

## Quick Facts
- arXiv ID: 2602.13165
- Source URL: https://arxiv.org/abs/2602.13165
- Reference count: 11
- Primary result: Krites increases the fraction of requests served with curated static answers by up to 3.9 times relative to tuned baselines, with unchanged latency.

## Executive Summary
Krites addresses the similarity threshold trade-off in tiered LLM semantic caching. It asynchronously verifies static cache misses in a similarity grey zone using an LLM judge; approved responses are promoted to the dynamic cache, expanding static coverage without altering critical path decisions. In trace-driven simulations on two benchmarks, Krites increased static-origin served fraction by up to 3.9×, with no latency increase.

## Method Summary
Krites extends a baseline GPTCache-style tiered caching policy. The static tier contains curated prompt-answer pairs selected to cover 60% of equivalence class frequency from the first 20% of a trace. The dynamic tier stores online-generated and promoted responses. For each request, the system computes the prompt embedding and finds the nearest static neighbor. If the cosine similarity exceeds τ_static (taken from the vCache Pareto frontier), the static answer is served. If the similarity falls in the grey zone [σ_min, τ_static), an asynchronous verification task is enqueued. This task invokes an LLM judge (instantiated as an oracle using equivalence class labels in the evaluation) to decide whether the static answer is acceptable for the new prompt. If approved, the pair is upserted into the dynamic cache under the new prompt key. The on-path logic remains unchanged: after a static miss, the system checks the dynamic cache or calls the backend. The primary metric is static-origin served fraction, encompassing direct static hits and dynamic hits from verified promotions. Evaluation uses two benchmarks (SemCacheLMArena and SemCacheSearchQueries), with the remaining 80% of each trace as the online stream.

## Key Results
- On SemCacheLMArena, static-origin served fraction rose from 8.2% to 19.4% (+136.5%).
- On SemCacheSearchQueries, it rose from 2.2% to 8.6% (+290.3%).
- Gains relative to tuned baselines reached up to 3.9×.
- End-to-end latency remained unchanged.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Krites identifies static cache misses that are potentially semantically equivalent and schedules off‑path verification without impacting request latency.
- **Mechanism:** For an incoming prompt *q*, the system computes cosine similarity *s*<sub>static</sub> with the nearest static entry *h*<sub>static</sub>. If *s*<sub>static</sub> falls in the interval [*σ*<sub>min</sub>, *τ*<sub>static</sub>), a background task `VerifyAndPromote(q, h_static, v_q)` is enqueued. The serving path immediately proceeds to check the dynamic tier or call the backend; verification happens later.
- **Core assumption:** There exists a range of similarity scores (the “grey zone”) where embedding similarity alone is insufficient to decide correctness, but additional verification can safely recover static hits.
- **Evidence anchors:** [Abstract]: “When the nearest static neighbor of the prompt falls just below the static threshold, Krites asynchronously invokes an LLM judge to verify whether the static response is acceptable for the new prompt.” [Section 3.1]: “We introduce a lower similarity cutoff *σ*<sub>min</sub> < *τ*<sub>static</sub> that defines the grey zone for static candidates.” [Corpus]: vCache shows overlapping similarity distributions for correct and incorrect hits, creating a grey zone; Krites targets this zone.
- **Break condition:** If *σ*<sub>min</sub> is set too high (close to *τ*<sub>static</sub>) or few static misses fall in the grey zone, the verification trigger rarely fires, limiting gains. Conversely, setting *σ*<sub>min</sub> too low floods the verification pipeline, increasing cost with diminishing returns.

### Mechanism 2
- **Claim:** An LLM‑based judge, prompted with a strict rubric, accurately determines whether a static response is acceptable for a new prompt, enabling safe promotion into the dynamic cache.
- **Mechanism:** The function *J*(*q*, *h*<sub>static</sub>, *a*<sub>static</sub>) runs in background workers. Given the incoming prompt *q*, the cached prompt *h*<sub>static</sub>, and its curated answer *a*<sub>static</sub>, the judge checks intent alignment, entity/constraint consistency, and freshness, returning a binary APPROVE/REJECT decision (temperature 0). Approved pairs are later upserted into *C*<sub>dynamic</sub>.
- **Core assumption:** LLM judges can reliably assess semantic equivalence for prompt‑response pairs with high accuracy, matching human judgment.
- **Evidence anchors:** [Abstract]: “LLM‑as‑a‑judge provides such an equivalence check… pairwise equivalence questions with explicit criteria are particularly tractable.” [Section 3.2]: “Using the same strict rubric… the judge agreed with human accept/reject labels on 99/100 pairs.” [Corpus]: Broader research on LLM‑as‑a‑judge indicates progress; the paper’s own validation supports feasibility.
- **Break condition:** If the judge’s false‑approve rate (ε) is non‑negligible, promoted entries could introduce semantic errors. A too‑strict judge reduces promotion volume. Judge latency can cause backlog if worker capacity is insufficient.

### Mechanism 3
- **Claim:** Approved static responses are inserted into the dynamic tier under the new prompt key, effectively creating a mutable pointer layer that expands static‑origin coverage without modifying the curated static cache.
- **Mechanism:** Upon judge approval, `VerifyAndPromote` performs an idempotent upsert of the tuple (*q*, *A*(*h*<sub>static</sub>), *v*<sub>*q*</sub>) into *C*<sub>dynamic</sub>. This entry inherits the dynamic tier’s eviction policy. Future requests that retrieve this dynamic entry receive the curated static answer.
- **Core assumption:** The dynamic tier can safely store entries that reference static answers, and its eviction policies will eventually refresh stale pointers without compromising correctness.
- **Evidence anchors:** [Abstract]: “Approved responses are promoted to the dynamic cache, allowing future repeats and paraphrases to reuse curated static answers and expanding static reach over time.” [Section 3.3]: “The auxiliary overwrite in `VerifyAndPromote` up serts (*q*, *A*(*h*), *v*<sub>*q*</sub>) into *C*<sub>dynamic</sub>.” [Corpus]: Tiered caching is well‑established; neighbors like SCALM and MeanCache employ static‑dynamic tiering for LLM caching.
- **Break condition:** If the dynamic cache’s eviction policy is too aggressive (short TTL or small size), promoted entries may be evicted before reuse. Also, if paraphrases do not closely match the inserted key’s embedding, they may miss the dynamic entry.

## Architecture Onboarding
**Component map:**  
Embedding model Φ -> Static cache C_static -> (on hit) serve; else -> Dynamic cache C_dynamic -> (on hit) serve; else -> Agentic backend B -> C_dynamic. Asynchronous path: from static miss with similarity in [σ_min, τ_static) -> verification task queue -> LLM judge J -> if approved -> auxiliary overwrite -> C_dynamic.

**Critical path:**  
1) Embed q. 2) Nearest neighbor in C_static: if s_static ≥ τ_static, return static answer. 3) Else nearest neighbor in C_dynamic: if s_dynamic ≥ τ_dynamic, return dynamic answer. 4) Else call B(q), insert result into C_dynamic, return. Asynchronously, if s_static ∈ [σ_min, τ_static), enqueue verification task (non‑blocking).

**Design tradeoffs:**  
- σ_min tuning: lower values increase judge volume and promotion potential but raise compute cost; higher values reduce cost but may miss safe reuses.  
- Judge model size: larger models typically offer higher accuracy but cost more per call; smaller models are cheaper but may lower precision/recall.  
- Dynamic cache eviction: aggressive eviction frees memory but may evict promoted entries before they are reused; conservative settings retain pointers longer but consume more resources.  
- Verification pipeline: deduplication and rate limiting control load but may delay promotions.

**Failure signatures:**  
- Low promotion rate: σ_min too high, judge too strict, or static cache coverage insufficient.  
- High error rate on promoted dynamic hits: indicates judge false approvals; sample and audit.  
- Judge queue backlog: verification capacity overwhelmed; scale workers or adjust σ_min.  
- Dynamic cache churn: if promoted entries are quickly evicted, ROI diminishes; monitor hit distribution on promoted keys.

**First 3 experiments:**  
1. Baseline comparison: Replicate Table 1 by running trace‑driven simulations on SemCacheLMArena and SemCacheSearchQueries. Measure static‑origin served fraction for tuned static‑threshold baseline vs. Krites. Expect gains of ~136% and ~290% respectively.  
2. Latency validation: Under identical load, compare end‑to‑end request latency distributions (p50, p99) between baseline and Krites. Asynchronous design should show no statistically significant increase in critical‑path latency.  
3. Parameter sweep: Vary σ_min across its feasible range and plot static‑origin served fraction versus judge request rate. This reveals the tradeoff curve and helps select an operating point balancing coverage and verification cost.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** How sensitive are Krites's gains in static-origin coverage to the false positive and false negative rates of the LLM judge, and what judge design (model, prompt) optimally balances verification cost against error introduction?  
- **Basis in paper:** Section 5 states that production verifiers may have nonzero false rates and that false approves add incremental errors; the paper uses an oracle and a small-sample check (Claude Opus 4.5, 99% agreement).  
- **Why unresolved:** The paper does not measure how varying judge accuracy affects caching metrics; the single 100‑pair audit is insufficient to characterize sensitivity across workloads.  
- **What evidence would resolve it:** Systematic experiments with multiple judge models and prompts, measuring verification accuracy and resulting static‑origin fraction/error rates, to derive robustness guidelines.

### Open Question 2
- **Question:** What is the optimal setting for the grey zone lower bound σ_min and judge scheduling (rate limiting, deduplication) to maximize static-origin coverage per unit of judge compute under a given workload?  
- **Basis in paper:** Section 5.1 discusses the trade‑off: lowering σ_min increases coverage but also judge load, and mentions deduplication/rate limiting as practical but leaves configuration open.  
- **Why unresolved:** The evaluation uses σ_min=0, maximizing judge load; operators lack guidance on how to choose σ_min and scheduling parameters to achieve the best ROI for their workload and cost constraints.  
- **What evidence would resolve it:** A parametric study varying σ_min and scheduling policies across different workload traces (grey zone fraction, recurrence patterns) to produce a model or heuristic for optimal configuration.

### Open Question 3
- **Question:** Can the dynamic cache eviction policy be improved to retain static-origin entries longer, thereby increasing the long-term static coverage of Krites without increasing cache size?  
- **Basis in paper:** Krites promotes verified static answers into the dynamic cache but subjects them to standard LRU/TTL eviction (Section 3.3). This design choice is made for simplicity but may cause premature eviction of valuable curated entries.  
- **Why unresolved:** The paper does not evaluate whether standard eviction policies are optimal for preserving static-origin hits; if static-origin entries are evicted quickly, the benefits of verification are wasted.  
- **What evidence would resolve it:** Comparative simulations of alternative eviction policies (e.g., giving static‑origin entries lower eviction priority) measuring static‑origin served fraction and overall cache performance over time.

## Limitations
- Exact hyperparameters (τ_static, σ_min) and static cache construction details (60% coverage selection, tie‑breaking) are not disclosed.
- LLM judge evaluation based on only 100 human‑labeled pairs; representativeness uncertain.
- Simulation may not capture real‑world verification queue backlogs or cost overheads; results limited to two datasets.
- Generalizability beyond the evaluated benchmarks remains unknown.

## Confidence
- **Krites increases static‑origin served fraction:** High (consistent large gains on two benchmarks with reproducible setup).
- **LLM judge ensures safe promotion:** Medium (99% agreement on small validation; untested on worst‑case inputs).
- **No critical‑path latency increase:** Medium (asynchronous design sound, but queueing effects not fully explored).
