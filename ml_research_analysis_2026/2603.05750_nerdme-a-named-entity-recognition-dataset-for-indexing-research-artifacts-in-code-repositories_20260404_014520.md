# NERdME: a Named Entity Recognition Dataset for Indexing Research Artifacts in Code Repositories

## Quick Facts
- **arXiv ID:** 2603.05750
- **Source URL:** https://arxiv.org/abs/2603.05750
- **Reference count:** 14
- **Primary result:** NERdME is the first manually annotated dataset of GitHub READMEs for extracting both paper-level (e.g., CONFERENCE) and implementation-level (e.g., SOFTWARE) scholarly entities; fine-tuned transformers substantially outperform zero-shot LLMs on exact-match F1.

## Executive Summary
This paper introduces NERdME, a novel dataset of 200 GitHub README files annotated with 10 types of scholarly entities (10,691 spans) to bridge the gap in scholarly information extraction (SIE) by covering implementation-level details often missing from scientific paper corpora. The dataset’s annotations follow guidelines derived from the NFDI4DS ontology and achieve substantial inter-annotator agreement (α=0.70). Baselines show that fine-tuned transformer models (SciBERT, RoBERTa) achieve large gains over zero-shot LLMs in exact-match F1, with particularly strong improvements for SOFTWARE (23.12%→72.46%) and DATASET (45.30%→63.94%). A downstream entity-linking experiment to Zenodo records yields 47.75% F1, demonstrating the dataset’s potential for artifact discovery and metadata integration.

## Method Summary
Data collection starts with selecting READMEs from Papers with Code to ensure coverage of both paper-level and implementation-level entities. Three annotators label spans in INCEpTION using a 10-type schema aligned with NFDI4DS, with curation rules (two-annotator agreement, sentence-level consistency) and a final expert review. The dataset is split by document (70% train, 10% validation, 20% test). For baselines, per-type token classifiers are trained using BIO tagging on sentences containing at least one span of the target type. Zero-shot LLMs are prompted per sentence without type filtering during training. Evaluation uses both exact-match (character-level) and partial-match F1 per entity type. The linking experiment matches extracted surface forms to Zenodo records using semantic similarity.

## Key Results
- Fine-tuned transformers achieve substantial exact-match F1 gains over zero-shot LLMs: SOFTWARE from 23.12% to 72.46%, DATASET from 45.30% to 63.94%.
- Entity linking to Zenodo yields 47.75% F1, outperforming fuzzy matching (17.67%), indicating that README mentions contain actionable linking signals.
- The dataset introduces a long-tail distribution of entity types, revealing challenges for rare types (e.g., WORKSHOP at 0% exact-match F1).

## Why This Works (Mechanism)
### Mechanism 1: Dataset Enables Dual-Level Extraction
The manual annotation of 200 READMEs with 10 entity types creates supervisory signals for both paper-level (e.g., CONFERENCE) and implementation-level (e.g., SOFTWARE) concepts absent in prior SIE datasets. The two-stage sampling ensures coverage, and the annotation guidelines based on NFDI4DS provide consistency (IAA α=0.70). This allows models to learn boundary patterns and contextual cues specific to README prose, such as informal mentions, versioned names, and embedded code snippets.  
*Core assumption:* READMEs contain a semantically rich mix of paper references and implementation details that can be consistently identified and learned.  
*Break condition:* Insufficient entity diversity or degraded IAA (<0.60) would undermine reliability.

### Mechanism 2: Fine-Tuning Gains from Domain-Specific Patterns
Fine-tuned transformers outperform zero-shot LLMs because NERdME’s span annotations capture surface-form variations and boundary conventions unique to README text (e.g., URLs, nested spans). The per-type training isolates entity-specific patterns despite natural long-tail distribution.  
*Core assumption:* The dataset’s size (200 files) and coherence are sufficient for token classifiers to generalize to unseen README content, especially for frequent types.  
*Break condition:* Inadequate diversity or extreme ambiguity in boundaries (as suggested by large partial-to-exact gaps) would narrow the fine-tuning advantage.

### Mechanism 3: Linking Utility via Discriminative Surface Forms
Entities extracted from NERdME can be linked to repositories like Zenodo because mentions often include canonical titles or identifiers that overlap with metadata records. Semantic similarity matching leverages this lexical and contextual overlap, as shown by the 47.75% linking F1, which exceeds fuzzy matching.  
*Core assumption:* README surface forms are sufficiently formal or canonical to match repository entries.  
*Break condition:* Overly informal, abbreviated, or ambiguous mentions would prevent reliable linking and collapse precision.

## Architecture Onboarding
### Component Map
Raw README corpus (Papers with Code) → Manual annotation in INCEpTION (3 annotators, expert curation) → TSV export → Document-level split (70/10/20) → Per-type sentence filtering → Tokenization (BIO) → Per-type transformer fine-tuning (cross-entropy loss) → Test evaluation (exact/partial match F1) → Linking (semantic similarity to Zenodo) → F1/MRR.

### Critical Path
1. Acquire diverse READMEs ensuring entity coverage.
2. Annotate with IAA ≥0.70; resolve mixed-type disagreements.
3. Train per-type classifiers on sentences containing target spans; tune on validation.
4. Evaluate per-type exact/partial F1 on test.
5. Link extracted spans to Zenodo via embedding similarity; evaluate linking metrics.

### Design Tradeoffs
- **Annotation scale vs. quality:** 200 READMEs balance cost and IAA; larger scale risks consistency.
- **Per-type vs. joint NER:** Per-type models isolate patterns but ignore label dependencies; joint training could suffer from imbalance and interference.
- **Exact vs. partial match:** Exact measures boundary precision; partial is forgiving. Reporting both highlights boundary challenges.
- **Zero-shot vs. fine-tuned:** Zero-shot tests generalization; fine-tuned tests learnability from dataset.

### Failure Signatures
- **Annotation inconsistency:** IAA below 0.60 or many filtered sentences due to mixed-type disagreement.
- **Poor long-tail performance:** Very low F1 (<10%) for rare types (WORKSHOP, ONTOLOGY), indicating insufficient examples or ambiguous definitions.
- **Linking precision collapse:** Semantic similarity F1 near fuzzy match baseline, suggesting non-canonical README mentions.
- **Partial-to-exact gap widening:** >40% drop for common types (e.g., SOFTWARE) indicating boundary prediction errors, possibly from nested spans or tokenization issues.

### First 3 Experiments
1. **Replicate SOFTWARE NER baseline:** Fine-tune RoBERTa-base on train split for SOFTWARE; verify exact-match F1 ≥70% on test (expected 72.46%).
2. **Boundary error analysis:** Sample 50 false-positive exact-match predictions for CONFERENCE; categorize as over-span, under-span, or type confusion; quantify proportions.
3. **Linking strategy ablation for DATASET:** Compare semantic similarity (all-MiniLM-L6-v2) against TF-IDF cosine and character n-gram Jaccard; report F1 and MRR.

## Open Questions the Paper Calls Out
### Open Question 1: Improving Long-Tail Performance
How can NER performance for long-tail entity types (e.g., WORKSHOP, ONTOLOGY) be improved given their extreme scarcity in NERdME?  
*Basis:* WORKSHOP (79 spans) and ONTOLOGY (112 spans) are heavily outnumbered by SOFTWARE (4,332 spans); fine-tuned models achieve 0% exact-match F1 for WORKSHOP.  
*Why unresolved:* Standard training fails in low-resource scenarios; additional data or few-shot methods are needed.  
*Resolution evidence:* Collect more tail-class annotations or apply data augmentation; measure exact-match F1 gains with increased tail data.

### Open Question 2: Reducing Partial-to-Exact Gap
What causes the substantial partial-to-exact-match F1 gap (e.g., CONFERENCE: 82.29% → 58.38%), and how can boundary precision be enhanced?  
*Basis:* Large drops indicate boundary detection difficulty, likely due to flexible, nested, or URL-embedded mentions.  
*Why unresolved:* Token-classification models may not handle boundary ambiguity well; annotation allows multi-sentence and nested spans.  
*Resolution evidence:* Error analysis to categorize boundary errors; implement span-enumeration or character-level modules and evaluate improvements.

### Open Question 3: Extending Entity Linking to All Types
Can entity linking be extended to all NERdME types (not just DATASET) using suitable external knowledge bases, and which KBs are most effective per type?  
*Basis:* Linking experiment only covers DATASET→Zenodo; other types (SOFTWARE, PUBLICATION, LICENSE) remain unexplored.  
*Why unresolved:* Different types map to different KBs (e.g., Software Heritage, Wikidata); feasibility and coverage per type are unknown.  
*Resolution evidence:* For each type, identify candidate KBs, apply linking methods, and evaluate ranking/classification metrics; compare KB suitability.

## Limitations
- Dataset size (200 READMEs) and diversity may not fully represent real-world repositories.
- Inter-annotator agreement α=0.70 indicates moderate consistency; boundary ambiguity persists.
- Exact-match F1 lags partial-match, highlighting boundary detection challenges.
- Entity linking F1 (47.75%) may be insufficient for robust practical use; generalizability beyond Zenodo untested.
