# From Static Inference to Dynamic Interaction: A Survey of Streaming Large Language Models

## Quick Facts
- **arXiv ID**: 2603.04592
- **Source URL**: https://arxiv.org/abs/2603.04592
- **Reference count**: 40
- **Key outcome**: Survey establishes unified definition and taxonomy for streaming LLMs, analyzing three paradigms (output-, sequential-, concurrent-streaming) and cataloging methods, applications, and open challenges.

## Executive Summary
This survey addresses fragmented definitions in streaming LLM research by introducing a unified taxonomy based on data flow and dynamic interaction. It defines three distinct paradigms—output-streaming, sequential-streaming, and concurrent-streaming—each with unique mechanisms for handling input and output in real time. The authors provide a comprehensive analysis of representative methods, covering streaming generation, incremental encoding, context management, architectural adaptations, and interaction policies. By reviewing real-world applications and outlining open challenges, the survey offers a structured framework to guide future advances in streaming intelligence.

## Method Summary
The survey systematically classifies streaming LLM approaches into three paradigms based on data flow and interaction characteristics. It surveys representative techniques under each paradigm, covering streaming generation mechanisms (token/block generation, speculative decoding), incremental encoding (atomic/fragmented), context management (memory retention, KV cache eviction/compression), architectural adaptations (re-encoding, concatenated, interleaved, grouped), and interaction policies (rule-based, SFT, RL). The paper catalogs numerous recent approaches and maintains an online repository of relevant papers. It further reviews real-world applications such as simultaneous translation, streaming video understanding, and interactive agents, while outlining key open challenges and future research directions.

## Why This Works (Mechanism)

### Mechanism 1: Output-streaming LLMs
- **Claim**: Output-streaming LLMs generate tokens in a streaming fashion after the entire input context has been statically processed.
- **Mechanism**: The model first performs a single "prefill" pass over the complete input to compute all KV states. During decoding, it emits tokens one-by-one (or in blocks) using cached KV values, avoiding re-encoding. This enables low-latency progressive output without modifying the input processing pipeline.
- **Core assumption**: The full input is available before any output is needed, so incremental input handling is unnecessary.
- **Evidence anchors**:
  - [abstract] "Output-streaming LLMs... retain static input processing but support streaming output generation."
  - [section 3] "Output-streaming emphasizes streaming generation mechanisms and efficient generation."
- **Break condition**: The paradigm collapses if the input is not fully present at generation start (e.g., live speech).

### Mechanism 2: Sequential-streaming LLMs
- **Claim**: Sequential-streaming LLMs process an unbounded input stream incrementally while deferring generation until a (possibly full) context is built.
- **Mechanism**: Incoming tokens/chunks are encoded one-by-one, updating the KV cache without re-computing past states. Context management (eviction, compression) keeps memory bounded. Generation only begins after the input stream is (partially or fully) accumulated, using the current KV state.
- **Core assumption**: Input arrives sequentially and can be encoded incrementally; memory must be constrained for long streams.
- **Evidence anchors**:
  - [abstract] "Sequential-streaming LLMs... process streaming inputs incrementally but generate with full input."
  - [section 4] "Incremental encoding... avoids quadratic re-computation" and "Streaming context management... under limited memory."
- **Break condition**: If the input rate exceeds encoding throughput or cache management discards too much context, quality degrades.

### Mechanism 3: Concurrent-streaming LLMs
- **Claim**: Concurrent-streaming LLMs interleave input reading and output generation in real time, requiring both architectural adaptations and an interaction policy.
- **Mechanism**: New input tokens are inserted into the same sequence as generated outputs, but attention and positional encodings must be handled to avoid conflicts. Four adaptation styles (re-encoding, concatenated, interleaved, grouped) resolve these. An interaction policy (rule-based, SFT, RL) decides at each step whether to read more input or emit an output token.
- **Core assumption**: The model can safely mix input and output tokens in a single forward pass and learn a timely read/write schedule.
- **Evidence anchors**:
  - [abstract] "Concurrent-streaming LLMs... perform streaming generation while streaming reading."
  - [section 5] "Architecture adaptation mitigates structural conflicts... Interaction policy governs read-write synchronization."
- **Break condition**: Poor policy (e.g., waiting too long) yields high latency; architectural conflicts cause attention errors or degraded coherence.

## Foundational Learning

### Concept: Streaming Generation Granularity
- **Why needed here**: The choice of generation unit (token, block, refinement) directly impacts latency, coherence, and hardware utilization in all streaming paradigms.
- **Quick check question**: What is the latency-quality trade-off when using block-wise semi-autoregressive decoding versus token-wise autoregressive decoding?

### Concept: Incremental Encoding and Context Management
- **Why needed here**: Sequential- and concurrent-streaming must process inputs without full recomputation and operate under bounded memory; these techniques are the foundation for infinite-context perception.
- **Quick check question**: How does attention-aware eviction (e.g., StreamingLLM) differ from representation compression (e.g., KIVI) in preserving salient information?

### Concept: Interaction Policy
- **Why needed here**: In concurrent-streaming, the system's responsiveness and output quality hinge on when to read vs. write; the policy is the decision-making core.
- **Quick check question**: Why might an RL-based interaction policy outperform a rule-based Wait-k policy on heterogeneous input streams?

## Architecture Onboarding

### Component map
1. **Input Stream Handler** – Buffers and segments raw streaming data (e.g., audio chunks, video frames) into model-compatible units.
2. **Incremental Encoder** – Processes each input unit through the model's embedding and transformer layers, updating the KV cache.
3. **KV Cache Manager** – Maintains the cache, applying eviction (e.g., sliding window, heavy hitter) or compression (quantization, merging) to respect memory budgets.
4. **Interaction Policy Module** – Observes current states (e.g., entropy, attention patterns) and emits a binary decision: read (accept more input) or write (generate next token/block).
5. **Output Stream Generator** – Invokes the decoder head to produce output tokens (or multimodal tokens) and streams them out; may also handle refinement or block updates.

### Critical path
- Receive input unit → Encode → Update KV cache → Query interaction policy → If *read*, loop back; if *write*, generate token → Update output state → (optionally re-evaluate policy after each generation step).

### Design tradeoffs
- **Latency vs. Quality**: Aggressive early writing reduces latency but risks incoherent output due to insufficient context.
- **Memory vs. Context Length**: Stronger cache compression/eviction saves memory but may lose long-range dependencies.
- **Policy Complexity vs. Adaptability**: Rule-based policies are predictable but brittle; RL/SFT policies adapt but require training data and tuning.

### Failure signatures
- **High tail latency** – Policy stalls too long before writing; check for overly conservative thresholds.
- **Attention anomalies** – Interleaved input/output cause misaligned attention; verify positional encoding scheme.
- **Memory overflow** – KV cache growth outpaces eviction; inspect budget parameters.
- **Degraded semantics** – Over-compression or aggressive eviction discards critical context; monitor accuracy on long sequences.

### First 3 experiments
1. **Generation Mechanism Benchmark** – Compare token-wise, block-wise, and refinement-based streaming on a fixed task (e.g., streaming speech transcription) measuring latency (ms/token) and quality (WER).
2. **Interaction Policy Evaluation** – On simultaneous translation, implement Wait-k, threshold-based, and SFT policies; plot quality-latency curves (BLEU vs. AL) to identify admissible regions.
3. **KV Cache Management Stress Test** – Apply different eviction/compression strategies on a long video QA task; track memory footprint, throughput, and accuracy over time to find sustainable configurations.

## Open Questions the Paper Calls Out

### Open Question 1
- **Question**: What alternative architectural paradigms beyond interleaved and grouped streaming are viable for concurrent input-output processing in streaming LLMs?
- **Basis in paper**: [explicit] "Alternative Concurrent Streaming Paradigms. Beyond interleaved and group-based strategies, more effective streaming paradigms remain to be explored. In particular, extending streaming interaction to semi-autoregressive or block-wise generation frameworks presents a promising yet underexplored direction."
- **Why unresolved**: Current concurrent-streaming architectures (re-encoded, concatenated, interleaved, grouped) each have trade-offs in efficiency, memory growth, and structural compatibility with pre-training. Semi-autoregressive or block-wise generation could alter the granularity of interaction but lack dedicated designs for concurrent setting.
- **What evidence would resolve it**: Development and empirical comparison of semi-autoregressive/block-wise concurrent streaming frameworks on latency-sensitive tasks (e.g., streaming translation), measuring quality-latency trade-offs against existing paradigms.

### Open Question 2
- **Question**: How can interaction policies (read/write scheduling) be made both efficient and content-adaptive without requiring expensive reinforcement learning or large-scale fine-tuning?
- **Basis in paper**: [explicit] "Efficient Interaction Policies. Designing interaction policies that adaptively balance reading and generation is essential for real-time streaming performance."
- **Why unresolved**: Rule-based policies are interpretable but rigid; SFT-based policies need labeled data; RL-based policies optimize quality-latency rewards but are sample-inefficient and unstable. A truly efficient policy that is both adaptive and cheap to obtain remains elusive.
- **What evidence would resolve it**: A framework that achieves RL-level adaptability with SFT-like data efficiency, perhaps via lightweight auxiliary classifiers or in-context decision mechanisms, validated on diverse streaming tasks with varying dynamics.

### Open Question 3
- **Question**: How can streaming LLMs be extended to handle complex, continuous modalities beyond text, audio, and video (e.g., spatial tactile streams, radar signals) while maintaining low latency?
- **Basis in paper**: [explicit] "Expansion of Streaming Modalities. Current streaming LLMs primarily focus on text, audio, and basic video interactions. Extending streaming LLMs to additional modalities requires transcending these limitations toward complex, omni-modal continuous streams (e.g., spatial streaming, tactile, radar) to achieve real-time streaming multimodal understanding and generation in highly dynamic environments."
- **Why unresolved**: Existing streaming techniques (incremental encoding, context management) are tailored to discrete token streams from well-defined tokenizers (e.g., speech codecs, video frames). Multimodal streams like tactile data lack such discrete representations and have unique temporal/spatial characteristics.
- **What evidence would resolve it**: Demonstrate a streaming LLM backbone that natively ingests a novel continuous modality (e.g., 3D point cloud streams or biosignals) via learned tokenization, with benchmarks for real-time reasoning tasks.

### Open Question 4
- **Question**: What standardized evaluation benchmarks and metrics are needed to fairly compare streaming LLM approaches across paradigms and applications?
- **Basis in paper**: [inferred] From the Scope section: "we do not aim to provide an exhaustive comparison of all existing implementations or a comprehensive empirical evaluation across tasks and systems." Also, the taxonomy itself reveals fragmented evaluation: output-streaming focuses on generation quality/speed; sequential-streaming on context retention; concurrent-streaming on quality-latency trade-offs. No unified suite exists.
- **Why unresolved**: Papers report task-specific metrics (e.g., BLEU for translation, latency penalty). This makes cross-paradigm comparison difficult. There is no consensus on streaming-specific metrics that balance responsiveness, coherence, and resource usage across diverse modalities and tasks.
- **What evidence would resolve it**: A comprehensive benchmark suite covering all three paradigms with standardized metrics (e.g., streaming-aware versions of AL/BLEU, memory overhead, interaction quality scores) and reference implementations for fair reproducibility.

## Limitations
- Paradigm boundaries may blur in multimodal or complex streaming scenarios, leading to ambiguous classifications.
- Absence of standardized benchmarks prevents rigorous cross-paradigm performance comparison.
- Survey coverage might lag behind the fastest-moving subfields, especially for very recent concurrent-streaming techniques.

## Confidence
- **Output-streaming**: High (solid theoretical foundation and widespread implementation via KV caching).
- **Sequential-streaming**: High (incremental encoding and context management validated in multiple systems, e.g., StreamingLLM).
- **Concurrent-streaming**: Medium (promising adaptations and policies exist, but real-world deployment and policy robustness remain under-explored).
