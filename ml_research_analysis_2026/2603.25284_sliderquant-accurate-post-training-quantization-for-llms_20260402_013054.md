# SliderQuant: Accurate Post-Training Quantization for LLMs

## Quick Facts
- **arXiv ID:** 2603.25284
- **Source URL:** https://arxiv.org/abs/2603.25284
- **Reference count:** 40
- **Primary result:** Outperforms SOTA PTQ across multiple LLM families; e.g., W4A4 on Llama2-13B yields WikiText2 perplexity 5.00 vs 5.02 (CBQ).

## Executive Summary
Post-training quantization (PTQ) for large language models (LLMs) often applies uniform treatment across layers, but empirical evidence shows that shallow and deep layers (especially first and last) are more sensitive to quantization, leading to significant accuracy degradation in low-bit settings. SliderQuant addresses this by introducing adaptive sliding windows: window sizes progressively expand for shallow layers, remain fixed for intermediate layers, and progressively contract for deep layers. Within each window, quantization is performed incrementally using a few learnable parameters to build inter-layer synergies. Evaluations on Llama, Llama2, Llama3, Qwen2.5, MoE, and DeepSeek-R1 distilled models demonstrate state-of-the-art results: for W4A4, it reduces WikiText2 perplexity (Llama2-13B: 5.00 vs CBQ's 5.02) and improves zero-shot accuracy (Qwen2.5-14B avg: 58.96% vs CBQ's 53.50%). On DeepSeek-R1, it achieves near-lossless accuracy on math/code tasks at W4A16 and remains robust at W2A16.

## Method Summary
SliderQuant rethinks sequential PTQ by assigning distinct window sizes to different layers based on their depth. Shallow layers (first few) receive progressively larger windows to allocate more optimization resources; intermediate layers use a fixed window size; deep layers use progressively smaller windows. Each window is quantized incrementally: layers inside the window are optimized jointly with a small set of learnable parameters (e.g., scaling factors) that are adjusted on a calibration dataset to minimize quantization error. The overlapping windows ensure that adjacent layers share some context, building inter-layer synergies that mitigate error accumulation. The approach requires only a few extra parameters per window, making it parameter-efficient while significantly improving low-bit accuracy.

## Key Results
- Outperforms SOTA PTQ methods (OmniQuant, CBQ) across diverse model families including Llama, Llama2, Llama3, Qwen2.5, MoE, and DeepSeek-R1 distilled models.
- At W4A4, achieves WikiText2 perplexity 5.00 on Llama2-13B (vs. CBQ's 5.02) and zero-shot accuracy 58.96% on Qwen2.5-14B (vs. CBQ's 53.50%).
- On DeepSeek-R1, attains near-lossless performance on math/code tasks at W4A16 and maintains robustness even at extreme W2A16.

## Why This Works (Mechanism)
SliderQuant works because it aligns quantization effort with layer sensitivity, which empirically varies with depth: first/last layers are more sensitive, intermediate layers less so. By adaptively enlarging windows for sensitive shallow/deep layers, the method allocates more degrees of freedom (via incremental optimization) to preserve critical information. The fixed window for intermediate layers avoids unnecessary overhead. Overlapping windows enable error propagation and synergy: quantizing a layer within a window that includes neighbors allows the learnable parameters to adjust scales to maintain consistency across layer boundaries. This incremental, window-based approach reduces the accumulated quantization error that typically plagues uniform sequential PTQ, especially at low bit-widths.

## Foundational Learning
- **Post-Training Quantization (PTQ):** Technique to reduce bit-width of weights/activations after training without retraining. *Why needed:* Enables deployment of large models on resource-constrained devices. *Quick check:* Can you explain the difference between PTQ and QAT?
- **Layer Sensitivity in LLMs:** Not all layers contribute equally to model accuracy when quantized; early and late layers often have higher impact. *Why needed:* Guides adaptive quantization strategies. *Quick check:* For a transformer, which layers are typically more sensitive: embedding, middle, or output?
- **Sliding Window Optimization:** Optimizing a subset of consecutive layers jointly to capture local dependencies. *Why needed:* Balances accuracy and memory; larger windows capture more context but cost more. *Quick check:* How does increasing window size affect memory and potential accuracy gain?
- **Incremental Quantization:** Sequentially quantizing layers within a window while updating a small set of parameters. *Why needed:* Allows fine-tuning of quantization scales with minimal overhead. *Quick check:* What parameters are typically learned during incremental quantization?
- **Inter-layer Synergy:** The idea that quantizing layers in isolation can cause error accumulation; coordinating quantization across layers improves overall fidelity. *Why needed:* Critical for low-bit PTQ success. *Quick check:* Why might overlapping windows help synergy?
- **Adaptive Scheduling:** Dynamically adjusting hyperparameters (like window size) based on layer depth. *Why needed:* Recognizes non-uniform sensitivity across the network. *Quick check:* What pattern does SliderQuant use for window size vs. depth?

## Architecture Onboarding
**Component map:**  
Calibration Data → Adaptive Scheduler → Sliding Window Assigner → For each window: Incremental Quantization Engine (with Learnable Parameters) → Quantized Model

**Critical path:**  
The model's layers are traversed from input to output. The scheduler assigns a window size for each layer based on its depth (expanding for shallow layers, fixed for middle, contracting for deep). For each window, the quantizer jointly processes the layers in that window, using a few learnable parameters to optimize quantization scales on calibration data. Overlap between consecutive windows ensures adjacent layers appear in multiple windows, promoting synergy. The process proceeds sequentially until all layers are quantized.

**Design tradeoffs:**  
- *Window size vs. memory:* Larger windows capture more inter-layer dependencies but require storing more activations for backpropagation within the window, increasing memory footprint.  
- *Overlap vs. redundancy:* Overlap improves synergy but duplicates computation and may not linearly improve accuracy.  
- *Adaptive schedule vs. tuning cost:* The expansion/contraction rates (L_s, L_d) are hyperparameters; too aggressive expansion can waste resources on less sensitive layers, while too conservative may under-protect sensitive ones.

**Failure signatures:**  
- Poor performance on architectures where sensitivity gradient is reversed or flat (e.g., some uniform CNNs) because the fixed schedule misallocates resources.  
- Memory overflow when window sizes are too large for available GPU memory, especially in huge models (>100B).  
- Divergence during incremental optimization if the learnable parameters are not properly regularized or if calibration data is insufficient.

**Three first experiments:**  
1. **Replicate baseline results:** Run SliderQuant on Llama2-13B with W4A4, measure WikiText2 perplexity and compare to reported 5.00 vs CBQ's 5.02.  
2. **Generalization test:** Apply SliderQuant to a non-Transformer LLM (e.g., Mamba) at W4A4 and evaluate perplexity; compare against uniform PTQ to see if adaptive windows still help.  
3. **Ablation of adaptivity:** Replace adaptive windows with a uniform sliding window of the same average size; evaluate accuracy on a medium-sized model (e.g., Llama2-7B) to isolate the benefit of the adaptive schedule.

## Open Questions the Paper Calls Out
### Open Question 1
- **Question:** What is the fundamental theoretical reason behind the observed sensitivity gradient—where first/last layers are most sensitive and intermediate layers are less so—in LLM quantization across different architectures?
- **Basis in paper:** [explicit] The authors state "we revisit the predominant sequential quantization framework via questioning whether different layers of currently prevailing LLMs have similar quantization impacts on model accuracy" and empirically observe this gradient across Llama2, Llama3, and Qwen2.5 models. They note it "implies that the quantization design for different layers of LLMs is required" but do not provide a theoretical explanation.
- **Why unresolved:** The paper presents empirical evidence and designs a heuristic sliding window scheme but does not analyze whether this sensitivity pattern stems from inherent properties like layer function (embedding/output versus internal representations), gradient flow, or activation distribution characteristics. Without theory, the approach may not generalize to novel architectures (e.g., hybrid MoE or future designs).
- **What evidence would resolve it:** A formal analysis linking layer sensitivity to measurable properties (e.g., activation kurtosis, gradient magnitudes, or information-theoretic importance) across diverse model families, supported by controlled ablations that isolate architectural factors.

### Open Question 2
- **Question:** Can the adaptive sliding window parameters (e.g., expansion/contraction rates, window sizes) be learned automatically from model statistics rather than hand-tuned (e.g., L_s=4,L_d=4), and would such a dynamic scheme improve performance across a wider range of models and bit-widths?
- **Basis in paper:** [inferred] SliderQuant uses fixed hyperparameters (L_s=4, s=2, etc.) chosen via limited ablations on Llama2-7B. The paper acknowledges the potential for better settings ("there is still room to get improved quantization performance by choosing better settings") but does not explore automated tuning. The method’s reliance on manual schedule design limits scalability and adaptability.
- **Why unresolved:** Hand-tuning may not capture model-specific sensitivity patterns (e.g., very deep vs. shallow networks, MoE routing layers). An automated mechanism could adjust windows based on calibration data metrics (e.g., per-layer error estimates) and would make the method more general-purpose.
- **What evidence would resolve it:** Experiments with a meta-learning or reinforcement learning controller that optimizes window schedules on a validation set across multiple models, compared against the static schedule, showing consistent gains, especially on out-of-distribution architectures like transformers with novel norms or attention mechanisms.

### Open Question 3
- **Question:** How does SliderQuant’s performance degrade on extremely large-scale models (e.g., >100B parameters) and non-autoregressive architectures, and what modifications are needed to maintain its synergy benefits without prohibitive memory overhead from overlapping windows?
- **Basis in paper:** [inferred] The paper tests up to 70B dense models and one 30B MoE model, but does not address scaling to >100B models or architectures like encoders (BART), diffusion models, or state-space models. The sliding window design’s memory cost grows with window size and overlap (e.g., storing intermediate activations for backpropagation within windows). For massive models, this could become a bottleneck.
- **Why unresolved:** The memory-accuracy trade-off noted in ablations (larger windows improve accuracy but increase memory) may have a different optimal point for 100B+ models or non-causal networks. The method’s reliance on sequential window optimization might also be less effective if layers have different interconnectivity patterns.
- **What evidence would resolve it:** Scaling experiments on publicly available >100B models (e.g., GPT-4 variants if accessible, or Mixtral 8x22B) measuring perplexity, memory footprint, and total calibration time; plus adaptations like hierarchical sliding windows or gradient checkpointing to reduce memory. Results should show whether the sensitivity pattern holds and if window parameters need re-tuning.

## Limitations
- **Implementation complexity:** Adaptive sliding window logic and incremental quantization schedule are not fully detailed, hindering replication.
- **Generalizability:** Evaluated only on Transformer-based LLMs; performance on non-Transformer or highly sparse architectures remains unknown.
- **Computational overhead:** Calibration cost (samples, time) relative to SOTA methods like OmniQuant is not reported.
