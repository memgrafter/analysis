# CRE-T1 Preview Technical Report: Beyond Contrastive Learning for Reasoning-Intensive Retrieval
## Quick Facts
- **arXiv ID**: 2603.17387
- **Source URL**: https://arxiv.org/abs/2603.17387
- **Reference count**: 30
- **Primary result**: T1-4B achieves average nDCG@10 of 37.1 on BRIGHT, outperforming larger contrastive models by over 11 points and matching retrieval+reranking pipelines without extra inference overhead.

## Executive Summary
Reasoning-intensive retrieval tasks require models to infer latent relationships between queries and documents, a capability that contrastive learning fails to provide due to its fixed geometric encoding of relevance. Thought1 (T1) introduces a generative retrieval approach that dynamically constructs a query-specific reasoning trajectory, aggregates its semantics into a special embedding token (<emb_token>), and encodes documents with an instruction+text+<emb_token> format to align representations. Training proceeds via a three-stage curriculum culminating in Group Relative Policy Optimization (GRPO) to directly optimize reasoning paths for retrieval performance. On the BRIGHT benchmark, T1-4B (4B parameters) attains an average nDCG@10 of 37.1, surpassing contrastive baselines such as ReasonIR-8B (24.4) and RaDeR-7B (25.5) by more than 11 points, and matches the effectiveness of retrieval+reranking systems without additional inference cost.

## Method Summary
Thought1 reimagines retrieval as a generative process. For each query, an LLM generates a reasoning trajectory—a sequence of logical steps that connect the query to relevant evidence. The semantics of this trajectory are then condensed into a single dense vector, realized as the embedding of a special token called <emb_token>. Documents are processed by feeding an instruction, the document text, and the <emb_token> token into the same LLM; the model’s hidden state at the <emb_token> position serves as the document embedding. The similarity between the query’s <emb_token> embedding and a corpus of document embeddings determines retrieval. Training employs a curriculum: first, supervised fine-tuning on synthetic reasoning data teaches the model to produce coherent trajectories; second, a contrastive-style stage aligns query and document embeddings; third, GRPO—a reinforcement learning method—optimizes the reasoning generator directly against retrieval metrics (e.g., nDCG). This end-to-end optimization ensures that the generated reasoning is tailored for retrieval performance.

## Key Results
- T1-4B reaches an average nDCG@10 of **37.1** on the BRIGHT benchmark.
- It outperforms state-of-the-art contrastive models ReasonIR-8B (24.4) and RaDeR-7B (25.5) by **>11 points**.
- The model matches the performance of retrieval+reranking pipelines while maintaining single-stage inference efficiency.

## Why This Works (Mechanism)
Contrastive learning collapses relevance into a static vector space, which struggles when queries and documents lack lexical overlap or require multi-hop reasoning. T1 overcomes this by generating a query-specific reasoning trajectory that explicitly bridges the gap; the trajectory’s steps can introduce intermediate concepts that align with document content. The <emb_token> aggregation transforms this variable-length reasoning into a fixed-dimensional representation that is directly comparable to document embeddings. Because both query and document representations are produced by the same LLM under aligned formatting (instruction+text+<emb_token>), they share a consistent semantic space. Finally, GRPO fine-tunes the reasoning generator with a reward derived from retrieval metrics, closing the loop: the model learns to produce trajectories that not only are logically sound but also yield high retrieval effectiveness. This synergy explains the substantial gains over purely contrastive approaches.

## Foundational Learning
- **Generative Retrieval**: Shifts from encoding fixed vectors to generating token sequences whose states serve as embeddings. *Why needed*: Enables dynamic, context-aware representations. *Quick check*: Model can generate diverse reasoning paths for the same query conditioned on different sub prompts.
- **Reasoning Trajectory**: A chain-of-thought style output that decomposes the query into inferential steps. *Why needed*: Captures multi-hop relationships and compensates for lexical mismatch. *Quick check*: Each step is relevant to the query and contributes to establishing document relevance.
- **<emb_token> Aggregation**: Summarizes the trajectory into a single embedding token. *Why needed*: Provides a fixed-size vector for efficient similarity search while preserving the trajectory’s semantics. *Quick check*: The embedding of <emb_token> correlates with human judgments of query-document relevance.
- **Three-Stage Curriculum**: Staged training from supervised fine-tuning to contrastive alignment to RL fine-tuning. *Why needed*: Stabilizes learning by gradually increasing task complexity. *Quick check*: Ablating any stage leads to a measurable drop in final nDCG.
- **Group Relative Policy Optimization (GRPO)**: An RL algorithm that updates the reasoning policy using group-level rewards. *Why needed*: Directly optimizes for retrieval metrics, which are non-differentiable. *Quick check*: Policy updates increase the reward on a held-out validation set.
- **Instruction-Tuned Encoding**: Documents are formatted with an instruction followed by text and <emb_token>. *Why needed*: Ensures the document encoder operates under the same objectives as the query reasoning generator. *Quick check*: Changing the instruction wording significantly affects retrieval performance.

## Architecture Onboarding
**Component map** (plain text):
Query -> Reasoning Generator (LLM) -> Reasoning Trajectory -> Semantic Aggregator -> <emb_token> (Query Embedding); Document -> Encoder (LLM with instruction + text + <emb_token>) -> Document Embedding; Similarity Scoring -> Ranking

**Critical path**: During inference, the query passes through the reasoning generator to produce a trajectory; the aggregator converts this into the <emb_token> embedding; the system then computes cosine similarities between this query embedding and the precomputed document embeddings in the corpus; top-k documents are returned.

**Design tradeoffs**: The generative reasoning step introduces non-negligible latency but yields richer query representations; the <emb_token> aggregation balances expressivity and efficiency; using the same LLM for both query and document encoding ensures distributional alignment but requires a larger model; GRPO improves performance at the cost of complex training.

**Failure signatures**: 
- Incoherent or overly generic reasoning trajectories produce <emb_token> embeddings that are dissimilar to relevant documents, leading to low recall.
- Misalignment between document instruction and query processing causes distribution shift, degrading similarity estimates.
- Overfitting during RL stage may cause the generator to produce trajectories that perform well on training queries but fail to generalize.
- High reasoning length increases inference cost; truncation may harm performance.

**First experiments** (exactly 3):
1. **Replication**: Run the full T1-4B training and evaluation on BRIGHT with 3 random seeds; report mean nDCG@10 and confidence intervals to verify the 37.1 claim.
2. **Ablation of reasoning**: Remove the reasoning trajectory and encode queries directly (e.g., with a single forward pass without generation) to quantify the contribution of the generative reasoning component.
3. **Efficiency profiling**: Measure end-to-end query latency and memory footprint of T1-4B compared to ReasonIR-8B and a two-stage retrieval+reranking pipeline (e.g., BM25 + RankZephyr) on the same hardware.
