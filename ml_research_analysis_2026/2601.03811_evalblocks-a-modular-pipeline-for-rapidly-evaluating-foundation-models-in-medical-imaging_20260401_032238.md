# EvalBlocks: A Modular Pipeline for Rapidly Evaluating Foundation Models in Medical Imaging

## Quick Facts
- arXiv ID: 2601.03811
- Source URL: https://arxiv.org/abs/2601.03811
- Reference count: 14
- Primary result: EvalBlocks is a Snakemake-based framework that automates evaluation of medical imaging foundation models, enabling reproducible, scalable execution with caching and parallelism; demonstrated on five models across three malignancy classification tasks, producing comprehensive AUC and accuracy metrics and reducing evaluation wall-time.

## Executive Summary
Evaluating foundation models for medical imaging malignancy classification is typically slow and error-prone due to ad-hoc workflows. EvalBlocks addresses this with a modular, automated pipeline built on Snakemake. It defines experiments declaratively through configurable blocks for datasets, models, aggregation, and evaluation. The system leverages caching and parallel execution to scale efficiently and ensure reproducibility. In demonstrations across three datasets and five pre-trained models, EvalBlocks generated standard metrics (AUC, accuracy) and visualization analyses (LDA, PCA, t-SNE), substantially cutting evaluation time and facilitating rapid iteration. The open-source framework bridges the gap between benchmarking and practical model development.

## Method Summary
EvalBlocks orchestrates evaluation via a Snakemake pipeline composed of interchangeable blocks: (1) Feature extraction applies pre-trained foundation models to generate embeddings from image patches; (2) Optional aggregation merges multi-modal inputs; (3) Evaluation trains a lightweight downstream classifier (kNN or linear probing) and computes metrics. Inputs consist of preprocessed patches from three medical imaging datasets (AMARA, PANORAMA, PI-CAI) and five foundation models (CT-FM, Curia, UMedPT, DINOv2, DINOv3). Users declare experiments in a YAML configuration file, specifying datasets, models, aggregation, and evaluation strategies. The pipeline automatically handles dependencies, caches intermediate embeddings to avoid redundant computation, and supports parallel or cluster execution. No model training is performed; only frozen inference and lightweight downstream training are executed.

## Key Results
- Evaluated five foundation models on three malignancy classification tasks, yielding comprehensive AUC and accuracy results (e.g., CT-FM achieved 0.80 AUC on PANORAMA).
- Produced visualization analyses (LDA, PCA, t-SNE) for feature interpretability.
- Significantly reduced evaluation wall-time through caching and parallelism, enabling rapid iterative experimentation.

## Why This Works (Mechanism)
EvalBlocks works by enforcing a structured, automated workflow that eliminates manual errors and optimizes resource usage. Its modular design allows independent development of dataset loading, model inference, aggregation, and evaluation components, while Snakemake manages dependencies and execution. Caching stores embeddings after first computation, so subsequent experiments using the same features skip expensive inference. Parallel execution distributes tasks across CPU/GPU cores or cluster nodes, cutting wall-clock time. The declarative configuration makes experiments reproducible and versionable. Together, these mechanisms accelerate the evaluation cycle while maintaining rigor.

## Foundational Learning
**Concept 1: Modular Pipeline Design**  
*Why needed*: Enables swapping components (e.g., datasets, models) without rewriting entire workflow; supports flexible experimentation.  
*Quick check*: Can you replace the feature extraction block with a new model and only adjust its configuration, without altering downstream blocks?

**Concept 2: Workflow Management (Snakemake)**  
*Why needed*: Automates task sequencing, handles dependencies, and ensures reproducibility through rule-based execution.  
*Quick check*: Does `snakemake -n` produce a consistent directed acyclic graph (DAG) for a given config?

**Concept 3: Caching Intermediate Results**  
*Why needed*: Avoids redundant computation of expensive embeddings; speeds up iterative testing.  
*Quick check*: After a successful run, does deleting a single cached embedding file cause only that block to re-run on next invocation?

**Concept 4: Parallel and Cluster Execution**  
*Why needed*: Leverages multi-core or cluster resources to reduce wall-time for large-scale evaluations.  
*Quick check*: Does increasing `--cores` lead to more tasks running concurrently (monitor with `htop` or job scheduler)?

**Concept 5: Declarative Configuration**  
*Why needed*: Separates experiment parameters from code, enabling versioning and easy sharing of experimental setups.  
*Quick check*: Can you copy a YAML config and its results directory to another machine with identical dependencies and reproduce the outputs?

**Concept 6: Standard Evaluation Metrics (AUC, Accuracy)**  
*Why needed*: Provides quantitative comparison across models and datasets; widely accepted in medical imaging.  
*Quick check*: Do the reported metrics match what you would compute from predictions using standard libraries (e.g., scikit-learn)?

## Architecture Onboarding
**Component Map**
config.yaml -> Dataset -> FeatureModel -> (optional) Aggregation -> Evaluation -> results/

**Critical Path**
The shortest execution path for a configuration without aggregation and with cached features is: Evaluation block directly reading cached embeddings and training a downstream classifier. Without cache, the critical path becomes: Dataset -> FeatureModel -> Evaluation.

**Design Tradeoffs**
- *Modularity vs overhead*: Snakemake introduces some startup overhead but gains flexibility; suitable for research workflows.
- *Caching vs storage*: Cached embeddings consume disk space, often tens of GB, but drastically reduce repeated inference costs.
- *Declarative config vs complexity*: YAML files are human-readable but can become complex for large combinatorial experiments; may require scripting to generate.

**Failure Signatures**
- Missing file errors: often due to incorrect dataset paths in config or missing patches.
- Dimension mismatches: e.g., model expects 3-channel input but receives single-channel; check preprocessing block.
- Dependency conflicts: check Conda/container environments defined in `envs/` directory; ensure GPU drivers match.
- Cache staleness: if a model block code changes but cache not invalidated, old embeddings are reused; clear cache manually.

**First Three Experiments**
1. **Smoke test**: Run the pipeline on a single dataset (e.g., PANORAMA) with one model (CT-FM) and a small patch subset to verify installation and data paths.
2. **Evaluation comparison**: Compare kNN (k=20) vs linear probing on the same features to understand performance differences.
3. **Cache impact**: Run the same config twice; measure wall-time with `time` and verify second run skips FeatureModel block due to caching.

## Limitations
- The `config.yaml` schema is not formally documented; users must rely on repository examples, increasing onboarding friction.
- Model-specific preprocessing steps are encapsulated within code blocks and not detailed, potentially leading to inconsistent input normalization across models.
- Evaluation was limited to three datasets and five foundation models; the framework's generalizability to other tasks or models remains unevaluated.

- Modularity & reproducibility: High
- Scalability & speed: Medium
