# EngGPT2: Sovereign, Efficient and Open Intelligence

## Quick Facts
- **arXiv ID:** 2603.16430
- **Source URL:** https://arxiv.org/abs/2603.16430
- **Reference count:** 40
- **Primary result:** 16B total/3B active MoE model matches dense 8B-16B models on MMLU-Pro/GSM8K with 1/5th to 1/2 inference FLOPs and 1/10th to 1/6th training data.

## Executive Summary
EngGPT2-16B-A3B is a sovereign European LLM achieving high efficiency via a Mixture-of-Experts architecture. With 16 billion total parameters but only 3 billion active per inference, it matches the performance of dense 8B-16B models on key benchmarks while using a fraction of the compute. A four-stage training pipeline—pre-training, long-context adaptation, mid-training, and post-training—consolidates broad language knowledge, long-context handling, structured reasoning, and instruction following. Special control tokens enable multiple reasoning modes (e.g., English/Italian, turbo) from a single model. The model demonstrates particular strength in Italian and European NLP, trained on a corpus with 25% Italian content, aligning with EU AI Act requirements for open-weight, efficient models.

## Method Summary
EngGPT2 is trained from scratch in four distinct phases. Phase 1 (pre-training) uses a three-stage curriculum on 2.5 trillion tokens from diverse sources (Fineweb-edu, Fineweb2-ita, Finemath, etc.) with a 4096 sequence length. Phase 2 (long-context adaptation) extends context to 32k tokens using YARN scaling on a specialized dataset. Phase 3 (mid-training) reinforces structured reasoning with templates from reasoning-focused datasets. Phase 4 (post-training) includes supervised fine-tuning (SFT), Anchored Preference Optimization (APO), and model soups to align the model to instruction formats and control tokens. The architecture comprises 24 transformer layers with Grouped-Query Attention, RMSNorm, and SwiGLU activations. Each layer contains 64 experts; a router selects the top 8 experts per token, yielding 3 billion active parameters. Training uses Megatron-LM with tensor/pipeline/expert parallelism on up to 128 A100 nodes. Evaluation follows standard protocols (lm-evaluation-harness, EvalScope) with specified generation hyperparameters.

## Key Results
- Matches dense 8B-16B models on MMLU-Pro and GSM8K while using one-fifth to half the inference FLOPs and one-tenth to one-sixth of the training tokens.
- When normalized for compute, outperforms larger baselines in efficiency across multiple benchmarks.
- Achieves strong Italian and European NLP performance, attributed to a 25% Italian pre-training corpus.

## Why This Works (Mechanism)
### Mechanism 1
- **Claim:** Sparse Mixture-of-Experts (MoE) architecture with 16B total parameters but only 3B active per inference achieves competitive performance with dense 8B–16B models at a fraction of the compute cost.
- **Mechanism:** The model uses 64 experts per layer, routing each token to 8 experts. This selective activation means only ~20% of parameters are used during forward passes, drastically reducing FLOPs per token while maintaining total parameter capacity for knowledge storage.
- **Core assumption:** Expert specialization emerges during training, allowing the router to assign tokens to the most relevant sub-models, preserving expressive power despite lower activation.
- **Evidence anchors:** Abstract states "16 billion parameters with 3 billion active per inference"; Section 2 describes 64 experts per layer with 8 activated per token; neighboring sovereign models (Dicta-LM 3.0, Typhoon-S) also use MoE for efficiency.
- **Break condition:** If load balancing fails (routing collapses to a few experts), effective capacity drops and performance degrades sharply relative to dense models.

### Mechanism 2
- **Claim:** A phased training pipeline (pre-training → long-context adaptation → mid-training → post-training) efficiently consolidates capabilities without catastrophic interference.
- **Mechanism:** Each stage has a distinct objective and dataset mixture, allowing the model to first acquire broad language foundations, then specialize in long-context handling, reinforce structured reasoning, and finally align to instruction formats. Sequential isolation minimizes negative transfer.
- **Core assumption:** Skills from earlier stages provide a stable foundation that can be refined rather than overwritten in later stages, given appropriate data curation and learning rate schedules.
- **Evidence anchors:** Abstract notes training on only 2.5T tokens matches dense models; Section 4 details three-stage pre-training with different data mixes and LR schedules; neighboring papers describe multi-stage training but not identical phasing (weak external support).
- **Break condition:** If later-stage data distributions conflict heavily with earlier stages (e.g., post-training overwrites pretrained knowledge), benchmark scores on pre-trained capabilities (like MMLU) drop significantly.

### Mechanism 3
- **Claim:** Explicit reasoning control tokens (`/reasoning_en`, `/turbo`, etc.) enable multiple inference modes from a single model without retraining.
- **Mechanism:** During SFT, the model learns to associate special tokens with specific output formats. At inference, prepending these tokens conditions the decoder to generate structured traces (``) or concise bullet-points, and to output reasoning in the specified language.
- **Core assumption:** The model's generation process is controllable via token steering, and SFT data taught robust associations between control tokens and desired patterns.
- **Evidence anchors:** Abstract mentions multiple reasoning modes; Section 7.1 defines control tokens and templates; neighbors mention reasoning enhancements but not token-based mode switching (appears novel).
- **Break condition:** If control tokens are ignored or overridden by prompt semantics (as in turbo mode with mismatched languages), mode switching fails, leading to unreliable deployment.

## Foundational Learning
- **Mixture-of-Experts (MoE) routing and load balancing:** Understanding token assignment and load-balancing loss prevents expert collapse, which would render most experts unused and defeat efficiency. **Quick check:** If load-balancing coefficient is too high, what primary training dynamic is disrupted—router learning or expert specialization?
- **Multi-stage training curriculum design:** Each phase has different data mixes, learning rates, and objectives. Engineers must understand these changes to diagnose performance issues (e.g., why long-context adaptation has lower MFU). **Quick check:** Why might long-context adaptation have lower MFU (~14%) vs. pre-training (~21%) beyond longer sequences?
- **Instruction tuning with structured reasoning traces:** Post-training teaches the model to output `<think>` blocks and respect control tokens. Without explicit templates, the model wouldn't learn discrete token patterns for mode switching. **Quick check:** How does packing multiple examples into a 32k sequence with attention masking prevent cross-example associations during SFT?

## Architecture Onboarding
- **Component map:** Tokenizer → Router (per layer) → Selected Experts (8/layer) → GQA Attention → SwiGLU → Output.
- **Critical path:** Data → Tokenizer → Router (per layer) → Selected Experts (8/layer) → GQA attention → SwiGLU → Output.
- **Design tradeoffs:**
  - Expert size vs. number: Larger experts (GPT-OSS 24.9M) may specialize better but increase per-expert compute; smaller experts (Qwen3 4.7M) allow more experts but risk dilution. EngGPT2 chose intermediate (~9.3M) to balance.
  - Active params vs. total params: 3B active is a design target for 16B total; changing this ratio affects efficiency and peak capacity.
  - Sequence length vs. MFU: Long-context training (32k) lowers MFU due to communication overhead but is necessary for RULER performance.
  - SFT dataset diversity vs. depth: SFT mix covers many tasks but may underrepresent code/tool-calling, leading to lower BFCL/HumanEval scores.
- **Failure signatures:**
  - Load imbalance: Routing loss not decreasing; expert utilization variance high.
  - Long-context degradation: Sharp drop in RULER accuracy beyond 16k tokens before adaptation.
  - Reasoning mode failure: Turbo reasoning in Italian follows prompt language instead of `/reasoning_ita` token.
  - Post-training regression: Drop in MMLU after SFT/APO indicating catastrophic forgetting.
- **First 3 experiments:**
  1. Router sanity check: Run a few batches through a mid-training checkpoint, log routing decisions per layer. Verify each token activates 8 unique experts and no expert dominates >25% of tokens.
  2. Long-context extension test: Take Stage-3 pre-trained checkpoint, apply YARN with scaling factor 2, evaluate on RULER at 32k tokens. Expect significant drop vs. long-context-adapted model.
  3. Control token validation: Generate responses with `/reasoning_en` vs. `/reasoning_ita` on a multilingual prompt. Check that intermediate `<think>` blocks are in specified language and final answers consistent.

## Open Questions the Paper Calls Out
1. **What training budget and data characteristics are necessary for EngGPT2 to achieve competitive performance on long-context benchmarks like RULER beyond 64k tokens?**  
   Basis: Conclusion and Long-Context Adaptation sections state long-context performance limited and would benefit from extended schedule.  
   Why unresolved: Adaptation constrained by time/budget; optimal duration, data mixture, sequence scaling unknown.  
   Evidence needed: Systematic runs with longer adaptation phases (2×, 4× compute) on varied long-context datasets, evaluated at 64k–128k+.

2. **How can the SFT phase be redesigned to improve coding and function-calling capabilities without degrading reasoning performance?**  
   Basis: Authors acknowledge SFT too short and disproportionately reasoning-focused, resulting in weaker tool-calling/coding.  
   Why unresolved: Current SFT composition heavily favors reasoning; optimal balance between reasoning, coding, tool-interaction data and schedule unexplored.  
   Evidence needed: Ablations varying SFT data proportions (increase coding/tool share by 20%, 40%) and epochs, measuring trade-offs on HumanEval, BFCLv3, AIME/GSM8K.

3. **Why does turbo reasoning mode fail to reliably adhere to explicit reasoning language control tokens, and how can this behavior be corrected?**  
   Basis: Paper observes turbo reasoning language follows prompt language rather than specified token, attributed to smaller turbo SFT dataset.  
   Why unresolved: Exact mechanism (insufficient language-switched examples, token skew, capacity) not diagnosed; no mitigation proposed.  
   Evidence needed: Controlled fine-tuning on turbo data with enforced language-switch prompts, probing reasoning language fidelity across mismatches.

4. **What is the trade-off between copyright filtration aggressiveness and model performance/licensing compliance in the pre-training pipeline?**  
   Basis: Copyright filtering applies composite risk score and removes ~23% of records, but impact on diversity, capability, residual risk unevaluated.  
   Why unresolved: Filtration implemented for compliance but performance impact of removed content not measured; higher thresholds' risk-vs-performance trade-off unknown.  
   Evidence needed: Train pre-training variants with graduated filtration thresholds (e.g., risk >0.3, >0.4, >0.5), compare benchmark scores, audit residual data.

## Limitations
- Preprocessing details (dataset versions, filters, deduplication scripts) unspecified, hindering exact reconstruction and risking distribution shift.
- MoE implementation specifics (capacity factor, token dropping, load-balancing loss normalization) omitted, affecting memory usage, throughput, and possibly performance.
- No test set contamination assessment; benchmark scores may be inflated due to n-gram overlap with pre-training data.

## Confidence
- Sparse MoE efficiency claim: High
- Phased training pipeline claim: Medium
- Control token reasoning modes claim: Medium
